### Title
Silent `tx_bytes` Truncation to Zeroed Buffer in `internal_safe_verify_deposit_entry` Permanently Locks Protocol UTXOs - (File: contracts/satoshi-bridge/src/btc_light_client/deposit.rs)

---

### Summary

`internal_safe_verify_deposit_entry` validates the caller-supplied `tx_bytes` correctly, then silently replaces the stored UTXO's `tx_bytes` with 300 zero bytes whenever the input exceeds 10,000 bytes. The corrupted bytes are persisted to contract state. Any UTXO stored this way becomes permanently unspendable because subsequent withdrawal PSBT construction must re-decode the stored `tx_bytes` to recover the `TxOut` witness data.

---

### Finding Description

In `internal_safe_verify_deposit_entry`, the transaction is first decoded and fully validated against the original `tx_bytes`: [1](#0-0) 

Then, after validation passes, the code silently replaces `tx_bytes` with a 300-byte zero buffer if the original exceeded 10,000 bytes: [2](#0-1) 

The UTXO is then constructed and stored using this corrupted buffer: [3](#0-2) 

The `tx_id` is computed from the original (valid) transaction, so the UTXO storage key is correct and the UTXO appears legitimate in state. However, the stored `tx_bytes` field is `[0u8; 300]` — not a valid Bitcoin or Zcash transaction.

The `UTXO` struct stores `tx_bytes` as the raw transaction bytes: [4](#0-3) 

When the bridge later attempts to spend this UTXO in a withdrawal, it must decode `tx_bytes` to reconstruct the `TxOut` (amount + `script_pubkey`) needed as the PSBT witness input. For example, in the burn callback: [5](#0-4) 

Decoding `vec![0u8; 300]` as a Bitcoin/Zcash transaction will fail with a panic (`expect("Deserialization tx_bytes failed")`), making the UTXO permanently unspendable.

The `Transaction::decode` implementation for Bitcoin: [6](#0-5) 

This is the direct analog to the BlockhashRegistry bug: binary input data is partially validated (the decoded transaction is checked), but the data actually persisted to state is silently corrupted — analogous to the RLP parser that validated some fields but stored incorrect derived data.

---

### Impact Explanation

The affected UTXO represents real BTC/ZEC locked in the bridge's on-chain address. With corrupted `tx_bytes`, the bridge cannot construct a valid PSBT to spend this UTXO in any withdrawal or active UTXO management operation. The funds are permanently locked inside the bridge's custody address with no recovery path, since there is no mechanism to update a stored UTXO's `tx_bytes` after the fact. This constitutes permanent locking of protocol funds.

---

### Likelihood Explanation

Bitcoin transactions can legitimately exceed 10,000 bytes — for example, consolidation transactions with many inputs, or Zcash transactions carrying Orchard bundles. A trusted relayer submitting such a transaction via `verify_deposit_v2` with `safe_deposit` set (the Omni Bridge path) would trigger this silently with no indication of the corruption. The relayer need not act maliciously; the bug fires on any oversized but otherwise valid transaction. The `verify_deposit_v2` entry point is `#[trusted_relayer]`-gated: [7](#0-6) 

---

### Recommendation

Remove the truncation branch entirely. If oversized transactions must be rejected for storage cost reasons, fail explicitly with a `require!` before any decoding, mirroring the pattern already used in `internal_request_refund`: [8](#0-7) 

Apply the same pattern to `internal_safe_verify_deposit_entry`:
```rust
require!(
    tx_bytes.len() <= MAX_SAFE_DEPOSIT_TX_BYTES,
    "tx_bytes too large for safe deposit"
);
```

---

### Proof of Concept

1. A trusted relayer calls `verify_deposit_v2` with a valid BTC/ZEC transaction where `tx_bytes.len() > 10_000` and `deposit_msg.safe_deposit.is_some()`.
2. The contract decodes the transaction, validates the output at `vout` matches the deposit address, and confirms `deposit_amount > 0` — all checks pass.
3. The code replaces `tx_bytes` with `vec![0u8; 300]` and stores the UTXO with this corrupted buffer.
4. nBTC is minted to the user (correct), and the UTXO appears in the bridge's UTXO pool with the correct `balance` and `tx_id`.
5. When any subsequent withdrawal or active UTXO management operation attempts to spend this UTXO, `WrappedTransaction::decode(&utxo.tx_bytes, &chain)` is called on the zero buffer, panics with `"Deserialization tx_bytes failed"`, and the UTXO is permanently stuck — the corresponding BTC/ZEC is locked in the bridge's custody address with no recovery path.
