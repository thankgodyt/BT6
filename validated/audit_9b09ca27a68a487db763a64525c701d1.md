### Title
TOCTOU in `fast_fin_transfer`: Finalization Check Not Re-Verified After External Call Enables Double-Spending - (File: `near/omni-bridge/src/lib.rs`)

---

### Summary

In `fast_fin_transfer`, the contract checks `is_unified_transfer_finalised` before making an external cross-contract call to `check_or_pay_ft_storage`. Because NEAR cross-contract calls span multiple blocks, a `fin_transfer` call can execute during this window, finalizing the same transfer and sending tokens to the recipient. When `fast_fin_transfer_to_near_callback` subsequently executes, it does not re-check finalization status and proceeds to send tokens a second time, causing a double-spend.

---

### Finding Description

**Time of Check** — In `fast_fin_transfer`, the contract verifies the transfer has not already been finalized:

```rust
if self.is_unified_transfer_finalised(&fast_fin_transfer_msg.transfer_id) {
    env::panic_str(BridgeError::TransferAlreadyFinalised.to_string().as_str());
}
``` [1](#0-0) 

**External Call Delay** — Immediately after, an external cross-contract call is made to `check_or_pay_ft_storage`, which spans at least one additional NEAR block:

```rust
Self::check_or_pay_ft_storage(&deposit_action, ...)
    .then(Self::ext(...).fast_fin_transfer_to_near_callback(...))
``` [2](#0-1) 

**Time of Use** — In `fast_fin_transfer_to_near_callback`, the contract calls `add_fast_transfer` and then `send_tokens` **without re-checking** `is_unified_transfer_finalised`:

```rust
let required_balance = self
    .add_fast_transfer(fast_transfer, relayer_id, storage_payer.clone())
    .saturating_add(ONE_YOCTO);
...
self.send_tokens(fast_transfer.token_id.clone(), recipient, amount_without_fee, ...)
``` [3](#0-2) 

**Why the race window is exploitable:** `add_fast_transfer` inserts into the `fast_transfers` map and panics only if the same `FastTransferId` is already present. It does **not** check `finalised_transfers`. Meanwhile, `process_fin_transfer_to_near` (called by `fin_transfer`) reads `get_fast_transfer_status` to decide whether to redirect tokens to the relayer or the original recipient:

```rust
let fast_transfer_status = self.get_fast_transfer_status(&fast_transfer.id());
let (recipient, msg, fee_recipient) = match fast_transfer_status {
    Some(status) => { ... (status.relayer.clone(), ...) }
    None => (recipient, transfer_message.msg.clone(), predecessor_account_id.clone()),
};
``` [4](#0-3) 

If `fin_transfer` executes during the external call window, `fast_transfer_status` is `None` (because `add_fast_transfer` has not yet been called), so `process_fin_transfer_to_near` sends tokens to the original recipient. Then `fast_fin_transfer_to_near_callback` executes, `add_fast_transfer` succeeds (the `fast_transfers` map is empty for this ID), and `send_tokens` fires again — delivering tokens to the recipient a second time.

`add_fin_transfer` (called by `fin_transfer`) inserts into `finalised_transfers` and would prevent a second `fin_transfer` call, but it does not block the already-in-flight `fast_fin_transfer_to_near_callback`: [5](#0-4) 

---

### Impact Explanation

For **bridged (deployed) tokens**, `send_tokens` calls `mint` on the token contract. The second mint in the callback creates tokens beyond what is locked on the source chain — **unauthorized minting**. For **native (locked) tokens**, the bridge transfers from its own reserves twice — **direct loss of bridge funds**. In both cases the recipient receives `2 × (amount − fee)` tokens while only `amount` was locked on the source chain.

---

### Likelihood Explanation

`fin_transfer` is gated by `#[trusted_relayer]`, so the race requires a trusted relayer to submit the proof during the multi-block external call window. A trusted relayer who is also the recipient (or colluding with the recipient) can deliberately sequence the two calls to profit: they front `amount` tokens via `fast_fin_transfer`, then immediately submit `fin_transfer` with the valid proof. They receive `2 × (amount − fee)` tokens on NEAR while only `amount` was locked on the source chain, netting `amount − 2 × fee`. Even without malicious intent, a relayer submitting `fin_transfer` for a transfer that has a concurrent fast transfer in the external-call phase will accidentally trigger the double-spend.

---

### Recommendation

Re-check `is_unified_transfer_finalised` at the start of `fast_fin_transfer_to_near_callback` before calling `add_fast_transfer` or `send_tokens`. If the transfer has been finalized during the external call window, the callback should abort and return the relayer's fronted tokens rather than proceeding with the token send.

```rust
pub fn fast_fin_transfer_to_near_callback(...) -> Promise {
    // Re-check: abort if fin_transfer raced ahead
    if self.is_unified_transfer_finalised(&fast_transfer.transfer_id) {
        // refund relayer's fronted tokens
        return self.send_tokens(fast_transfer.token_id.clone(), storage_payer, ...);
    }
    ...
}
```

### Proof of Concept

1. A transfer originates on Ethereum (origin_chain: Eth, origin_nonce: N). A valid proof exists.
2. Trusted Relayer R (who is also the NEAR recipient) calls `ft_transfer_call` on the token contract, sending `amount` tokens to the bridge. This triggers `fast_fin_transfer`.
3. `fast_fin_transfer` passes the `is_unified_transfer_finalised` check (false) and issues the `check_or_pay_ft_storage` cross-contract call. Execution suspends.
4. In the next NEAR block, before `fast_fin_transfer_to_near_callback` executes, Relayer R submits `fin_transfer` with the valid proof.
5. `fin_transfer` → `fin_transfer_callback` → `process_fin_transfer_to_near`: `add_fin_transfer` marks the transfer finalized; `get_fast_transfer_status` returns `None`; `send_tokens` mints/transfers `amount − fee` tokens to Relayer R (as recipient).
6. `fast_fin_transfer_to_near_callback` executes: `add_fast_transfer` succeeds (the `fast_transfers` map has no entry for this ID); `send_tokens` mints/transfers another `amount − fee` tokens to Relayer R.
7. Relayer R has received `2 × (amount − fee)` tokens. Only `amount` was locked on the source chain. Net gain: `amount − 2 × fee`.
