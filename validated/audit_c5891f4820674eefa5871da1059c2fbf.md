Audit Report

## Title
Detached `send_tokens` Promise After Permanent State Mutation in UTXO Fast Transfer Finalization Causes Irrecoverable Relayer Fund Loss — (`near/omni-bridge/src/lib.rs`)

## Summary
In `utxo_fin_transfer_fast()` and the fast-transfer branch of `process_fin_transfer_to_other_chain()`, the fast-transfer accounting record is permanently mutated (deleted via `remove_fast_transfer` or locked via `mark_fast_transfer_as_finalised`) before `send_tokens()` is dispatched. Because the promise is `.detach()`ed, any failure of the underlying token transfer is silently discarded. If `send_tokens` fails, the relayer's fronted tokens remain permanently frozen inside the bridge contract with no recovery mechanism. The code itself acknowledges this with an explicit `TODO` comment.

## Finding Description
In `utxo_fin_transfer_fast()`, the fast-transfer state is irreversibly mutated first: if the destination is NEAR, `remove_fast_transfer()` deletes the record; if the destination is another chain, `mark_fast_transfer_as_finalised()` permanently locks it. Immediately after, `send_tokens(...).detach()` is called — the `.detach()` means the NEAR runtime will never surface the promise failure back to the contract. If `send_tokens` fails (e.g., `ft_transfer` panics because the recipient has no storage deposit registered with the token contract, or for any other runtime reason), the state mutation has already committed and cannot be rolled back. The relayer's fronted tokens, which were transferred into the bridge during `fast_fin_transfer`, remain in the bridge with no withdrawal or recovery function exposed.

The same pattern exists in `process_fin_transfer_to_other_chain()`: `send_tokens(...).detach()` is called and then `mark_fast_transfer_as_finalised()` is called in the same synchronous frame, so a promise failure cannot undo the state change.

By contrast, the non-UTXO fast-transfer-to-NEAR path uses a chained `resolve_fast_transfer` callback that checks the promise result and reverts state on failure — the UTXO path has no equivalent.

## Impact Explanation
When `send_tokens` fails silently: (1) the fast-transfer record is either deleted or permanently locked — neither state can be undone; (2) the relayer's fronted tokens remain in the bridge contract with no withdrawal or recovery function; (3) the UTXO connector's tokens consumed by the bridge are also unrecoverable. This constitutes permanent freezing of bridged funds, matching the Critical allowed impact: *"permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet, Bitcoin, Zcash, or Wormhole-routed flows."*

## Likelihood Explanation
`send_tokens` with an empty `msg` on a non-deployed token calls `ft_transfer` on the token contract. `ft_transfer` panics if the recipient (the relayer) does not have a storage deposit registered with that specific token contract. Additionally, any other runtime panic inside the detached promise (e.g., insufficient contract balance, gas exhaustion in the callee) produces the same silent failure. No malicious action is required — this is a normal protocol failure mode. The UTXO connector is a DAO-configured protocol participant whose `ft_transfer_call` is the standard finalization entry point, making the trigger path reachable through normal protocol operation.

## Recommendation
Replace the `.detach()` call in `utxo_fin_transfer_fast` with a chained callback analogous to `resolve_fast_transfer` that: (1) checks whether `send_tokens` succeeded; (2) if it failed, reverts the fast-transfer state — re-inserts the fast-transfer record (or un-marks it as finalised) so the relayer's tokens can be recovered on a subsequent retry. Apply the same fix to the fast-transfer branch of `process_fin_transfer_to_other_chain`. The state mutation should only be committed after the promise result is confirmed successful.

## Proof of Concept
1. A trusted relayer calls `ft_transfer_call` on the bridged UTXO token contract to the bridge with a `FastFinTransferMsg`, fronting `amount - fee` tokens to the recipient. The bridge stores the fast-transfer record.
2. The UTXO connector later calls `ft_transfer_call` to the bridge with a `UtxoFinTransferMsg` matching the same transfer. This triggers `utxo_fin_transfer` → `utxo_fin_transfer_fast`.
3. Inside `utxo_fin_transfer_fast`, `remove_fast_transfer()` is called, permanently deleting the record.
4. `send_tokens(token_id, relayer, amount, "").detach()` is dispatched. The underlying `ft_transfer` panics (e.g., relayer has no storage registered with the UTXO token contract, or any other runtime failure).
5. The panic is silently discarded by `.detach()`. The fast-transfer record is gone. The relayer's fronted tokens remain in the bridge. No recovery path exists.

To reproduce: write a NEAR integration test that (a) registers a fast transfer, (b) calls `utxo_fin_transfer` with a recipient account that has no storage deposit on the token contract, and (c) asserts that the fast-transfer record is deleted while the relayer balance on the token contract is unchanged — confirming the funds are frozen.
