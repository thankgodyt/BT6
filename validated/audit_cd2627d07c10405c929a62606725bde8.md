Audit Report

## Title
Missing Pre-Lock Normalization Check Causes Permanent Token Freeze — (`near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer_internal` locks or burns user tokens before any check that the normalized destination-chain amount is non-zero. The only guard against a zero normalized amount lives in `sign_transfer`, which executes in a separate, later transaction. When that guard fires, the tokens are already irrecoverably committed and no public cancel or refund path exists.

## Finding Description
`normalize_amount` applies floor division to convert a NEAR-side amount to destination-chain precision:

```rust
// lib.rs L2784-2786
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

For any token whose NEAR `origin_decimals` exceeds its destination `decimals` (e.g. 24 vs 6, divisor = `10^18`), any transfer amount below the divisor normalizes to zero.

`init_transfer` validates only `fee < amount` before proceeding: [1](#0-0) 

`init_transfer_internal` then immediately burns (for deployed/bridged tokens) and locks (for native tokens) the full amount, committing the state in the same transaction: [2](#0-1) 

`burn_tokens_if_needed` fires a detached cross-contract call to the token contract — the burn is not conditional on any later check: [3](#0-2) 

The zero-amount guard appears only in `sign_transfer`, a separate transaction called later by a relayer: [4](#0-3) 

When `sign_transfer` panics with `InvalidAmountToTransfer`, NEAR's transaction model reverts only `sign_transfer`'s own state changes. The prior `init_transfer` transaction — which committed the lock/burn — is unaffected. The transfer message remains in `pending_transfers` indefinitely.

`remove_transfer_message` is a private helper that only frees storage; it does not unlock or un-burn tokens: [5](#0-4) 

There is no public cancel, withdraw, or refund function for pending transfers. `claim_fee` requires a proof from the destination chain that can never exist for an unsigned transfer. `set_locked_tokens` (DAO/TokenLockController only) adjusts accounting but does not return tokens to users: [6](#0-5) 

## Impact Explanation
Any user who initiates a NEAR→EVM (or NEAR→other-chain) transfer with `amount - fee < 10^(origin_decimals − decimals)` permanently loses their tokens. For a token with 24 NEAR decimals and 6 EVM decimals the threshold is one full token unit (`10^18` base units). This constitutes **permanent freezing of bridged funds**, which is a Critical allowed impact under the scope (stealing, loss, or permanent freezing of bridged funds).

## Likelihood Explanation
The scenario is reachable by any unprivileged user via the public `ft_transfer_call` NEP-141 entry point with no special role required. It arises organically from users who misjudge the decimal gap or send dust-cleanup transfers. The decimal difference is a fixed, on-chain-visible protocol parameter, so a determined actor can also craft the exact amount deliberately and repeatably.

## Recommendation
Add the normalization check **before** locking or burning tokens, either inside `init_transfer` (after the fee check at L557) or at the top of `init_transfer_internal`. This mirrors the existing guard in `sign_transfer` but fires before any state mutation:

```rust
let token_address = self.get_token_address(
    transfer_message.get_destination_chain(),
    self.get_token_id(&transfer_message.token),
);
if let Some(decimals) = token_address.and_then(|a| self.token_decimals.get(&a)) {
    let normalized = Self::normalize_amount(
        transfer_message.amount_without_fee().expect("fee < amount"),
        decimals,
    );
    require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
}
```

## Proof of Concept
1. Register a token with NEAR-side `origin_decimals = 24` and EVM-side `decimals = 6` (divisor = `10^18`).
2. Call `ft_transfer_call` on the NEP-141 token with `amount = 999_999_999_999_999_999` (just below `10^18`) and a valid EVM recipient. `init_transfer` accepts the call (`fee=0 < amount`), `init_transfer_internal` locks/burns the tokens, and emits `InitTransferEvent`.
3. A relayer calls `sign_transfer` for the resulting transfer ID. `normalize_amount(999_999_999_999_999_999, {origin:24, dest:6}) = 0`; the call panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.
4. The panic reverts only `sign_transfer`'s state. The `init_transfer` transaction already committed: tokens are burned (for deployed tokens) or locked (for native tokens), the transfer message remains in `pending_transfers`, and no public recovery path exists. The user has permanently lost their funds.
