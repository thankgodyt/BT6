### Title
ChainSync Client Uses Hardcoded Empty Peras Weight Snapshot in Forecast-Horizon Disconnect Check, Causing Incorrect Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

`checkPreferTheirsOverOurs` in the ChainSync client hardcodes `emptyPerasWeightSnapshot` (zero certificate boosts) instead of reading the live `PerasWeightSnapshot` when deciding whether to disconnect from a peer whose headers are beyond the forecast horizon. This is the direct analog of the external report's pattern: a security-critical comparison reads a stale/zeroed value instead of the current one, causing the node to make an incorrect chain-selection decision.

---

### Finding Description

When the ChainSync client cannot forecast a ledger view for an incoming header (the header is beyond the forecast horizon), it calls `checkPreferTheirsOverOurs` to decide whether to wait or disconnect. The function calls `preferAnchoredCandidate` with a hardcoded `emptyPerasWeightSnapshot`:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← always zero; actual weights never consulted
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
```

`emptyPerasWeightSnapshot` is defined as `PerasWeightSnapshot Map.empty` — a map with no entries, meaning every block's Peras certificate boost is treated as zero. [1](#0-0) [2](#0-1) 

By contrast, every other call site that performs chain comparison — the BlockFetch client interface and the ChainDB chain-selection loop — passes the live `weights :: PerasWeightSnapshot blk` that reflects actual Peras certificate boosts:

```haskell
-- BlockFetch/ClientInterface.hs line 284
Just _ -> shouldSwitch $ preferAnchoredCandidate bcfg weights ours cand
``` [3](#0-2) [4](#0-3) 

`preferAnchoredCandidate` short-circuits to a pure block-count comparison whenever `isEmptyPerasWeightSnapshot weights` is true:

```haskell
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      -- falls back to SelectView / block-number comparison only
      ...
  | otherwise =
      -- uses weightedSelectView which accounts for Peras boosts
      ...
``` [5](#0-4) 

So `checkPreferTheirsOverOurs` always compares chains by block count alone, never by Peras weight.

---

### Impact Explanation

Under Peras, a chain can be **heavier** (and therefore canonical) even if it has **fewer blocks**, because Peras certificate boosts add weight on top of block count. The `WeightedSelectView` total weight is `blockNo + weightBoost`:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [6](#0-5) 

When `checkPreferTheirsOverOurs` evaluates a peer's candidate chain using `emptyPerasWeightSnapshot`:

1. The peer's chain has fewer blocks than the local chain but carries Peras certificate boosts that make it heavier (canonical under Peras).
2. With empty weights, `preferAnchoredCandidate` sees only block count: the peer's chain appears shorter → `shouldSwitch` returns `ShouldNotSwitch`.
3. The node throws `CandidateTooSparse` and **disconnects** from the peer.
4. The node remains on its current chain, which is lighter (non-canonical) under Peras.

This is a **chain-selection error**: an honest node is made to prefer a non-canonical, less-secure chain. The node will not adopt the heavier canonical chain because it has severed the connection to the peer offering it.

---

### Likelihood Explanation

The code path is reachable by any unprivileged peer:

1. The peer serves a sequence of headers that extends beyond the local node's forecast horizon (a normal condition during syncing or after a slot gap larger than the stability window).
2. The ChainSync client enters `readLedgerStateHelper`, `prj lst` returns `Nothing` (forecast unavailable), and `checkPreferTheirsOverOurs` is called. [7](#0-6) 

No special privileges, key material, or stake majority are required. The condition (headers beyond the forecast horizon) arises naturally during bulk sync and after network partitions. In a Peras-enabled network where certificate boosts are regularly issued, chains with fewer blocks but higher weight are an expected, common occurrence.

The TODO comment in the source explicitly acknowledges the issue is known and unresolved:

---

### Recommendation

Replace `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live `PerasWeightSnapshot` that is already threaded through the rest of the chain-selection machinery (e.g., the `weights` field in `ChainSelEnv`). The ChainSync client environment must be extended to carry the current `PerasWeightSnapshot` so that `checkPreferTheirsOverOurs` can read it, mirroring how `BlockFetch/ClientInterface.hs` and `ChainDB/Impl/ChainSel.hs` already pass `weights` to `preferAnchoredCandidate`. Alternatively, if the check is to be removed entirely (as the TODO suggests), the removal must be accompanied by a proof that the Genesis density argument still holds without it under Peras.

---

### Proof of Concept

**Setup (private testnet with Peras enabled):**

1. Node A is on chain `C_long`: 100 blocks, zero Peras certificate boosts → total weight = 100.
2. Peer B offers chain `C_heavy`: 95 blocks, Peras boosts totalling weight 10 → total weight = 105. `C_heavy` is canonical under Peras.
3. `C_heavy`'s tip slot is beyond A's forecast horizon (e.g., there is a slot gap > stability window between A's intersection and B's tip).

**Trigger:**

4. A's ChainSync client calls `readLedgerStateHelper`; `prj lst` returns `Nothing` (forecast unavailable for B's tip slot).
5. `checkPreferTheirsOverOurs` is called with `ourFrag = C_long` and `theirFrag = C_heavy`.
6. `preferAnchoredCandidate cfg emptyPerasWeightSnapshot C_long C_heavy` compares block counts only: 100 vs 95 → `ShouldNotSwitch`.
7. Node A throws `CandidateTooSparse` and disconnects from B.

**Observed result:** Node A stays on `C_long` (total weight 100), ignoring the canonical `C_heavy` (total weight 105). With the actual `PerasWeightSnapshot`, step 6 would yield `ShouldSwitch` (105 > 100) and A would wait for its chain to advance before validating B's headers.

preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"
        Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
          case preferCandidate
            (projectChainOrderConfig cfg)
            (weightedSelectView cfg weights oursSuffix)
            (weightedSelectView cfg weights candSuffix) of
            ShouldSwitch r -> ShouldSwitch (Left r)
            ShouldNotSwitch o -> ShouldNotSwitch o
