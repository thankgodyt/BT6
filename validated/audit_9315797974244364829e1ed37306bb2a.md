### Title
Storage Growth Without Fee Collection in `ft_on_transfer` Withdrawal Path — (File: `contracts/satoshi-bridge/src/api/token_receiver.rs`, `contracts/satoshi-bridge/src/account.rs`)

---

### Summary

The bridge's `ft_on_transfer` NEP-141 callback permanently creates new `Account` entries in contract storage without collecting any storage deposit from the caller. Any nBTC holder can use many distinct NEAR accounts to repeatedly trigger this path, permanently growing the bridge's on-chain storage at the bridge contract's own NEAR expense, with no cost to the attacker beyond gas (since the underlying BTC is returned after withdrawal verification).

---

### Finding Description

When a user calls `ft_transfer_call` on the nBTC token contract with a `Withdraw` message, the nBTC contract invokes `ft_on_transfer` on the bridge. The bridge's implementation is not `#[payable]`, so no NEAR deposit can be attached by the caller:


This dispatches to `create_btc_pending_info`, which unconditionally creates a new `Account` entry in the bridge's `accounts` `IterableMap` if one does not already exist:

```rust
// contracts/satoshi-bridge/src/api/token_receiver.rs
let account = self.internal_unwrap_or_create_mut_account(&sender_id);
```

```rust
// contracts/satoshi-bridge/src/account.rs
pub fn internal_unwrap_or_create_mut_account(
    &mut self,
    account_id: &AccountId,
) -> &mut Account {
    self.data_mut()
        .accounts
        .entry(account_id.clone())
        .or_insert(Account::new(account_id).into())
        .into()
}
```

The `Account` entry is **permanent** — it is never removed after the withdrawal is processed. No storage deposit is collected from `sender_id` at any point in this path. The bridge contract's own NEAR balance pays for the storage.

By contrast, other storage-growing operations in the same contract explicitly require attached deposits:

- `request_refund`: `require!(env::attached_deposit() >= self.required_balance_for_request_refund(), ...)`
- `execute_refund`: `require!(env::attached_deposit() >= self.required_balance_for_execute_refund(), ...)`

The withdrawal initiation path has no equivalent guard.

---

### Impact Explanation

An attacker who holds any amount of nBTC (above `min_withdraw_amount`) can:

1. Use many distinct NEAR accounts, each holding a minimal nBTC balance.
2. Call `ft_transfer_call` from each account with a valid `Withdraw` message.
3. Each call permanently inserts a new `Account` entry into `self.data_mut().accounts` at the bridge's storage cost.
4. After the bridge processes each withdrawal (signing and broadcasting the BTC transaction), the attacker's BTC is returned to their specified address.
5. The bridge's NEAR balance is permanently reduced by the cumulative storage cost of all created account entries.

If the bridge's NEAR balance is sufficiently drained, the contract will be unable to pay for future storage writes (new UTXOs, pending infos, refund requests), causing the bridge to enter a stuck state requiring operator intervention to top up the balance.

This matches the allowed impact: **Medium — harmful smart-contract behavior without direct funds theft, including stuck bridge state requiring operator intervention.**

---

### Likelihood Explanation

- Any nBTC holder can trigger this path permissionlessly via the standard NEP-141 `ft_transfer_call` interface.
- The attacker recovers their BTC after each withdrawal is verified; the net attacker cost is only NEAR gas fees.
- The default `pending_sign_count` limit of 1 per account is bypassed by using many accounts, each requiring only a minimal nBTC balance above `min_withdraw_amount`.
- No privileged role or leaked key is required.

---

### Recommendation

Collect a storage deposit from the initiating account before creating a new `Account` entry in `create_btc_pending_info`. Since `ft_on_transfer` is not `#[payable]`, one approach is to require that the user pre-register their account (paying a storage deposit) before initiating a withdrawal, and reject `ft_on_transfer` calls from unregistered accounts. Alternatively, deduct a storage reservation from the nBTC amount being withdrawn and refund it upon account cleanup.

---

### Proof of Concept

1. Attacker acquires 1000 NEAR accounts, each funded with a minimal nBTC balance (e.g., 1000 satoshis, above `min_withdraw_amount`).
2. From each account, attacker calls:
   ```
   nbtc.ft_transfer_call(
     receiver_id: "bridge.near",
     amount: "1000",
     msg: '{"Withdraw":{"target_btc_address":"<attacker_btc_addr>","input":[],"output":[...],"max_gas_fee":null,"chain_specific_data":null}}'
   )
   ```
3. Each call triggers `ft_on_transfer` → `create_btc_pending_info` → `internal_unwrap_or_create_mut_account`, inserting a permanent `Account` entry into `bridge.data.accounts` at the bridge's storage cost.
4. The bridge signs and broadcasts 1000 BTC transactions; the attacker receives their BTC back.
5. 1000 permanent `Account` entries remain in bridge storage, paid for entirely by the bridge's NEAR balance.
