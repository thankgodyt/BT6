### Title
Attacker Can Front-Run `request_refund` to Redirect User BTC Refund to Attacker-Controlled Address — (File: `contracts/satoshi-bridge/src/api/bridge.rs`, `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

The `refund_address` parameter in `request_refund` is an arbitrary, caller-supplied value that is stored in the `RefundRequest` but is **not** part of the refund request identifier (`utxo_storage_key = {tx_id}@{vout}`). Because `request_refund` is publicly callable and the duplicate-prevention check is keyed only on the UTXO, an attacker can front-run a legitimate user's refund call — copying the `deposit_msg` from the NEAR mempool and substituting their own BTC address — causing the user's BTC to be sent to the attacker after the timelock expires.

---

### Finding Description

`request_refund` in `contracts/satoshi-bridge/src/api/bridge.rs` accepts a `refund_address` parameter with no caller-identity check: [1](#0-0) 

The function is not gated by `#[trusted_relayer]` or any role check (unlike `verify_refund_finalize` and `remove_refund_pending_tx_id` in the same `impl` block, which carry individual `#[trusted_relayer]` annotations). Any NEAR account can call it.

Inside `request_refund_callback`, the refund request is stored keyed by `utxo_storage_key` (`{tx_id}@{vout}`), and a duplicate-prevention guard fires: [2](#0-1) 

The `refund_address` is stored verbatim in the `RefundRequest`: [3](#0-2) 

The only constraint on `refund_address` is that, when `deposit_msg.refund_address` is `Some`, it must match: [4](#0-3) 

When `deposit_msg.refund_address` is `None` (the common case for users who did not pre-authorize a refund address), **any** `refund_address` string is accepted and stored. The identifier (`utxo_storage_key`) does not include `refund_address`, so the first caller to land a valid request for a given UTXO permanently sets the destination address.

After the `unsafe_refund_timelock_sec` elapses, `execute_refund` is publicly callable with no access control: [5](#0-4) 

`finalize_refund_with_psbt` uses the stored `refund_address` to build the Bitcoin output: [6](#0-5) [7](#0-6) 

---

### Impact Explanation

An attacker who successfully front-runs the legitimate user's `request_refund` call sets their own BTC address as `refund_address`. Once the `unsafe_refund_timelock_sec` expires without a DAO/Operator rejection, anyone (including the attacker) can call `execute_refund`, which constructs and MPC-signs a Bitcoin transaction paying the attacker's address. The user's deposited BTC is permanently redirected. This constitutes **significant theft of user funds** (Critical) or, if the DAO rejects in time, **attacker-triggered temporary locking of bridged funds** (Medium).

---

### Likelihood Explanation

The attack is realistic:

1. **`deposit_msg` is observable**: When the legitimate user calls `request_refund`, the full `deposit_msg` is a call argument visible in the NEAR mempool before block inclusion. The attacker copies it verbatim.
2. **No caller restriction**: `request_refund` has no role check; any NEAR account can submit a competing request.
3. **First-writer wins**: The duplicate guard at line 544–547 of `refund.rs` ensures the legitimate user's subsequent call reverts.
4. **DAO mitigation is not guaranteed**: The `unsafe_refund_timelock_sec` gives the DAO a window to reject, but the DAO may be offline, slow, or unaware. The protocol comment acknowledges this risk but does not enforce rejection. [8](#0-7) 

---

### Recommendation

Include `refund_address` in the refund request identifier (e.g., key on `sha256({tx_id}@{vout}@{refund_address})`), or enforce that only the `recipient_id` embedded in `deposit_msg` (or a caller who can prove ownership) may submit a refund request for a given UTXO. Alternatively, require `deposit_msg.refund_address` to always be pre-set (non-`None`) so the destination is cryptographically bound to the deposit address derivation path and cannot be overridden by a third party.

---

### Proof of Concept

1. User A sends BTC to a deposit address derived from `deposit_msg = { recipient_id: "user_a.near", refund_address: None, ... }`. The deposit is never finalized.
2. User A broadcasts `request_refund(deposit_msg, "user_a_btc_addr", tx_bytes, vout, proof, None)` to NEAR.
3. Attacker observes the pending transaction in the NEAR mempool, extracts `deposit_msg`, `tx_bytes`, `vout`, and `proof`.
4. Attacker submits `request_refund(deposit_msg, "attacker_btc_addr", tx_bytes, vout, proof, None)` with higher priority.
5. Attacker's call lands first; `refund_requests["{tx_id}@{vout}"]` is stored with `refund_address = "attacker_btc_addr"`.
6. User A's call reverts: `"Refund request already exists for this UTXO"`.
7. DAO does not reject within `unsafe_refund_timelock_sec`.
8. Attacker calls `execute_refund("{tx_id}@{vout}", None)`. The bridge builds and MPC-signs a Bitcoin transaction paying `"attacker_btc_addr"`.
9. User A's BTC is stolen.
