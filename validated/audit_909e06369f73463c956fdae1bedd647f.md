Audit Report

## Title
Tokens Permanently Burned/Locked When Transfer Amount Normalizes to Zero in `init_transfer_internal` - (File: `near/omni-bridge/src/lib.rs`)

## Summary
`normalize_amount` uses floor division, so any `amount_without_fee` smaller than `10^(origin_decimals - dest_decimals)` produces zero. Tokens are burned or locked inside `init_transfer_internal` in a committed transaction before `sign_transfer` ever applies the normalization check. When `sign_transfer` later panics with `InvalidAmountToTransfer`, the prior burn/lock is already finalized and no cancel or refund function exists, causing permanent, irrecoverable loss of the user's tokens.

## Finding Description

`normalize_amount` performs integer floor division with no rounding guard: [1](#0-0) 

For a 24-decimal NEAR token bridged to a 6-decimal EVM token, the factor is `10^18`. Any `amount_without_fee < 10^18` yields zero.

The user entry point `ft_on_transfer` calls `init_transfer`, which enforces only `fee < amount`: [2](#0-1) 

No normalization pre-check exists here. `init_transfer` then calls `init_transfer_internal`, which **in the same committed transaction** burns (for deployed bridge tokens) or locks (for native tokens) the full amount: [3](#0-2) 

Only later, when a relayer calls `sign_transfer` (a separate transaction), is `normalize_amount` applied and the zero guard enforced: [4](#0-3) 

`sign_transfer` panics, reverting only its own state changes. The burn/lock from the prior transaction is already committed. The transfer remains in `pending_transfers` indefinitely. A grep for `cancel_transfer`, `pub fn refund`, and `pub fn cancel` across `lib.rs` returns zero matches — no recovery path exists.

The code comment above `normalize_amount` acknowledges that "dust stays locked/burned" when `fee = 0`, but this only addresses the remainder after a successful normalization. It does not address the case where the entire amount normalizes to zero and the transfer is permanently unserviceable. [5](#0-4) 

## Impact Explanation

This is a **permanent freezing of bridged funds** triggered by an unprivileged user through the standard `ft_transfer_call` → `ft_on_transfer` → `init_transfer` → `init_transfer_internal` flow. It matches the allowed Critical impact: *"permanent freezing of bridged funds across NEAR, EVM … flows"* and *"decimal/normalization abuse … that changes user or protocol balances."* The loss is irreversible because the burn cross-contract call is detached (`detach()`) and the lock is committed; no admin or DAO function can restore the tokens.

## Likelihood Explanation

No special privileges or coordination are required. Any user who calls `ft_transfer_call` with an amount below the normalization threshold (e.g., less than 1 NEAR-equivalent for a 24→6 decimal pair) triggers the bug. This is a realistic accidental scenario for users unfamiliar with decimal scaling. The condition is repeatable and affects every token pair where `origin_decimals > dest_decimals`.

## Recommendation

Add a normalization pre-check inside `init_transfer` (or at the top of `init_transfer_internal`) **before** burning or locking tokens. Look up the destination token's `Decimals` and assert `normalize_amount(amount_without_fee, decimals) > 0`; if the decimals are not yet registered, reject the transfer early and return the full amount to the caller. As defense-in-depth, implement a public `cancel_transfer` function that allows the original sender to reclaim funds from a transfer that has never been signed.

## Proof of Concept

1. Register a token with `origin_decimals = 24`, `dest_decimals = 6` (normalization factor = `10^18`).
2. User calls `ft_transfer_call` on the NEAR token contract with `amount = 5 * 10^17` (0.5 NEAR-equivalent), `fee = 0`, targeting an EVM recipient.
3. `ft_on_transfer` → `init_transfer`: only guard is `fee < amount` → `0 < 5*10^17` ✓ — passes.
4. `init_transfer_internal`: `burn_tokens_if_needed` or `lock_tokens_if_needed` executes and commits `5 * 10^17` tokens. Transaction succeeds; state is finalized.
5. Relayer calls `sign_transfer` in a new transaction.
6. `normalize_amount(5 * 10^17, {24, 6}) = 5 * 10^17 / 10^18 = 0`.
7. `require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer)` panics — `sign_transfer` reverts its own state only.
8. Transfer remains in `pending_transfers` forever; `5 * 10^17` tokens are permanently burned or locked with no recovery path.

A local unit test can confirm this by constructing a `TransferMessage` with the above parameters, calling `init_transfer_internal` directly, asserting the transfer is stored and tokens are consumed, then calling `sign_transfer` and asserting it panics while the transfer record and zero token balance persist.

    /// to the destination chain. When fee > 0, dust is absorbed into the fee via `claim_fee`.
    /// When fee = 0, dust stays locked/burned. See SECURITY.md for details.
    fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
        let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();

    }
