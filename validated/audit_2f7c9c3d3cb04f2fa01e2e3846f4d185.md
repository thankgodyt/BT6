### Title
Unvalidated `refund_address` in `request_refund` Allows Any NEAR Account to Redirect BTC Refunds to an Attacker-Controlled Address — (File: `contracts/satoshi-bridge/src/api/bridge.rs` / `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`request_refund` is publicly callable by any NEAR account. When `deposit_msg.refund_address` is `None`, the caller-supplied `refund_address` parameter is stored verbatim and used to send BTC during `execute_refund`, with no cryptographic validation that the caller is authorized to specify that address. An attacker can submit a refund request for any unfinalized BTC deposit and redirect the funds to an attacker-controlled BTC address.

---

### Finding Description

The deposit address is derived by hashing the entire `DepositMsg` struct:

```rust
pub fn get_deposit_path(deposit_msg: &DepositMsg) -> String {
    let deposit_msg_string = serde_json::to_string(&deposit_msg).unwrap();
    hex::encode(env::sha256(deposit_msg_string.as_bytes()))
}
```

In `request_refund_callback`, the bridge correctly validates that the BTC transaction output matches the deposit address derived from the provided `deposit_msg`:

```rust
require!(
    deposit_script_pubkey == output.script_pubkey,
    "Output script_pubkey does not match deposit address"
);
```

However, the separately supplied `refund_address` parameter — which determines where the BTC is sent — is **only** validated against `deposit_msg.refund_address` when that field is `Some`:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
```

When `deposit_msg.refund_address` is `None` (the common case for standard deposits), **no validation is performed** on the caller-supplied `refund_address`. The value is stored directly in the `RefundRequest`:

```rust
let refund_request = RefundRequest {
    ...
    refund_address,   // ← attacker-controlled, unvalidated
    ...
};
```

`request_refund` carries no access control restricting it to the `deposit_msg.recipient_id` or to a whitelisted relayer. The function's only guards are the pause check and a non-refundable storage deposit:

```rust
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn request_refund(
    &mut self,
    deposit_msg: DepositMsg,
    refund_address: String,
    tx_bytes: Base64VecU8,
    vout: usize,
    proof: TxInclusionProof,
    gas_fee: Option<U128>,
) -> Promise {
```

`execute_refund` is similarly open to any caller after the timelock elapses, and it pays out to `refund_request.refund_address` without checking who calls it.

**Attack path:**

1. Alice sends BTC to her deposit address (derived from `DepositMsg { recipient_id: alice.near, refund_address: None, ... }`). The `LogDepositAddress` event makes the `deposit_msg` and deposit address public.
2. The relayer has not yet called `verify_deposit` (e.g., it is slow or temporarily offline).
3. Bob (attacker) calls `request_refund(alice_deposit_msg, bob_btc_address, alice_tx_bytes, vout, proof)`.
4. `request_refund_callback` verifies the BTC transaction is included in the chain and that the output script matches Alice's deposit address — both checks pass. The refund request is stored with `refund_address = bob_btc_address`.
5. After `unsafe_refund_timelock_sec` elapses (and if the DAO/Operator has not called `reject_refund`), Bob calls `execute_refund`. The bridge builds a PSBT paying Alice's BTC to Bob's address and initiates MPC signing.
6. Bob broadcasts the signed transaction and receives Alice's BTC.

The only mitigation in the current design is the longer `unsafe_refund_timelock_sec` and the DAO/Operator's ability to call `reject_refund`. This requires constant operator vigilance and creates a systemic risk if the operator is slow, offline, or overwhelmed by many simultaneous malicious requests.

---

### Impact Explanation

An unprivileged NEAR account can redirect any unfinalized BTC deposit to an attacker-controlled BTC address, resulting in permanent loss of user funds. This matches **Critical: Significant loss, theft, destruction, or permanent locking of user or protocol funds** if the DAO/Operator fails to reject the request within the timelock, and **Medium: Bypass of bridge limits or policies** in the general case where operator intervention is required to prevent the theft.

---

### Likelihood Explanation

The attack is realistic and low-cost:

- BTC deposit transactions and their associated `deposit_msg` values are publicly observable on-chain (emitted via `LogDepositAddress` events).
- Any NEAR account can call `request_refund`; the only cost is the non-refundable storage deposit.
- Deposits that are delayed in finalization (relayer downtime, congestion, user error) are permanently exposed to this attack.
- A single attacker can submit many simultaneous malicious refund requests, overwhelming the DAO/Operator's ability to reject them all within the timelock.

---

### Recommendation

Require that the caller of `request_refund` is the `deposit_msg.recipient_id`, or require that `refund_address` is pre-committed in `deposit_msg.refund_address` (making it cryptographically bound to the deposit address). For example:

```rust
// Option A: restrict caller to the intended recipient
require!(
    env::predecessor_account_id() == deposit_msg.recipient_id,
    "Only the deposit recipient can request a refund"
);

// Option B: require refund_address to be pre-committed in deposit_msg
require!(
    deposit_msg.refund_address.is_some(),
    "refund_address must be pre-committed in deposit_msg"
);
```

Option B is the stronger fix because it makes the `refund_address` cryptographically bound to the deposit address (via the `get_deposit_path` hash), eliminating the ability for any third party to redirect the refund.

---

### Proof of Concept

1. Alice calls `get_user_deposit_address(DepositMsg { recipient_id: "alice.near", refund_address: None, ... })`. The bridge emits a `LogDepositAddress` event with the `deposit_msg` and deposit address.
2. Alice sends 1 BTC to the deposit address. The transaction is confirmed on-chain.
3. Before the relayer calls `verify_deposit`, Bob calls:
   ```
   request_refund(
       deposit_msg = alice_deposit_msg,   // public from event
       refund_address = "bc1q_bob_addr",  // attacker-controlled
       tx_bytes = alice_tx_bytes,         // public from Bitcoin chain
       vout = 0,
       proof = alice_inclusion_proof,     // public from Bitcoin chain
   )
   ```
   with sufficient attached NEAR for storage.
4. `request_refund_callback` validates the BTC tx inclusion and the output script — both pass. The `RefundRequest` is stored with `refund_address = "bc1q_bob_addr"`.
5. After `unsafe_refund_timelock_sec` (assuming DAO/Operator does not reject), Bob calls `execute_refund(utxo_storage_key)`.
6. The bridge builds a PSBT paying 1 BTC (minus gas fee) to `"bc1q_bob_addr"` and initiates MPC signing. Bob broadcasts the signed transaction and receives Alice's BTC.
