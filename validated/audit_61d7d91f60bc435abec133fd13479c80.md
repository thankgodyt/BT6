### Title
Fee Rounding Down Favors Users Over Protocol, Leaking Bridge Revenue - (File: contracts/satoshi-bridge/src/config.rs)

### Summary
`BridgeFee::get_fee` and `BridgeFee::get_protocol_and_relayer_fee` both use truncating integer division, rounding down in favor of the user/relayer rather than the protocol. This is the direct analog of the `mulDivDown` penalty-rounding bug in the external report. Any bridge user performing a deposit or withdrawal pays a slightly lower fee than the protocol intends, and the protocol's share of the split fee is also systematically under-collected.

### Finding Description
In `contracts/satoshi-bridge/src/config.rs`, the two fee-computation helpers both truncate:

```rust
// Line 30-35
pub fn get_fee(&self, amount: u128) -> u128 {
    std::cmp::max(
        amount * u128::from(self.fee_rate) / u128::from(MAX_RATIO),  // truncates
        self.fee_min,
    )
}

// Line 37-41
pub fn get_protocol_and_relayer_fee(&self, fee_amount: u128) -> (u128, u128) {
    let protocol_fee = fee_amount * u128::from(self.protocol_fee_rate) / u128::from(MAX_RATIO); // truncates
    let relayer_fee = fee_amount - protocol_fee;
    (protocol_fee, relayer_fee)
}
```

`MAX_RATIO = 10_000`. Both divisions are plain Rust integer division, which truncates toward zero (rounds down).

**`get_fee` call sites:**
- Deposit path: `contracts/satoshi-bridge/src/btc_light_client/deposit.rs` line 52 — `let deposit_fee = config.deposit_bridge_fee.get_fee(deposit_amount);`
- Withdrawal path: `contracts/satoshi-bridge/src/api/token_receiver.rs` line 89 — `let withdraw_fee = self.internal_config().withdraw_bridge_fee.get_fee(amount);`

**`get_protocol_and_relayer_fee` call site:**
- Deposit path: `contracts/satoshi-bridge/src/btc_light_client/deposit.rs` lines 54-56 — splits the already-truncated `deposit_fee` again with a second truncating division.

**Scenario 1 — zero fee when `fee_min = 0` and `fee_rate` is small:**
If the DAO configures `deposit_bridge_fee` with `fee_min = 0` and a non-zero `fee_rate`, any deposit amount satisfying `amount * fee_rate < MAX_RATIO` produces a fee of exactly 0:
```
amount = 9_999, fee_rate = 1 → 9_999 * 1 / 10_000 = 0
```
The `fee_min` floor only rescues this when `fee_min > 0`. The `BridgeFee::assert_valid` check does **not** require `fee_min > 0`.

**Scenario 2 — systematic per-transaction underpayment for all non-trivial amounts:**
For any amount where `amount * fee_rate / MAX_RATIO > fee_min`, the truncation silently discards up to `MAX_RATIO − 1 = 9_999` satoshis of fee per transaction. At current BTC prices this is up to ~$10 per transaction, accumulating unboundedly across the protocol's lifetime.

**Scenario 3 — double truncation in protocol/relayer split:**
`get_protocol_and_relayer_fee` truncates a second time on the already-truncated `deposit_fee`, so the protocol's share is doubly rounded down and the relayer's share is correspondingly inflated.

### Impact Explanation
Every deposit and withdrawal executed by any unprivileged bridge user causes the protocol to collect less fee than the configured rate mandates. When `fee_min = 0` and `fee_rate > 0`, the fee can be driven to exactly zero for amounts below the rounding threshold, completely bypassing the fee policy. This is a publicly reachable, persistent accounting invariant violation in the core bridge revenue path. No funds are directly stolen from users, but the protocol's backed-supply accounting drifts from its intended fee-collection invariant on every transaction.

**Allowed impact match:** Low — publicly reachable invariant-violation in production bridge/token paths without direct theft.

### Likelihood Explanation
Every deposit and withdrawal invokes `get_fee`. The truncation fires on every call where `amount * fee_rate` is not an exact multiple of `MAX_RATIO`, which is the common case for arbitrary user-supplied amounts. The zero-fee scenario requires `fee_min = 0` with a non-zero `fee_rate`, a configuration the DAO can set and that `assert_valid` does not prohibit. Likelihood is high for the underpayment case and medium for the zero-fee case.

### Recommendation
Replace truncating division with ceiling division in both helpers, rounding in favor of the protocol:

```rust
// get_fee: round up
fn ceil_div(a: u128, b: u128) -> u128 {
    (a + b - 1) / b
}

pub fn get_fee(&self, amount: u128) -> u128 {
    std::cmp::max(
        ceil_div(amount * u128::from(self.fee_rate), u128::from(MAX_RATIO)),
        self.fee_min,
    )
}

pub fn get_protocol_and_relayer_fee(&self, fee_amount: u128) -> (u128, u128) {
    let protocol_fee = ceil_div(
        fee_amount * u128::from(self.protocol_fee_rate),
        u128::from(MAX_RATIO),
    );
    let relayer_fee = fee_amount - protocol_fee;
    (protocol_fee, relayer_fee)
}
```

Additionally, consider adding a `require!(self.fee_min > 0 || self.fee_rate == 0, ...)` guard in `assert_valid` to prevent the zero-fee configuration.

### Proof of Concept
Using the bridge's own constants (`MAX_RATIO = 10_000`):

```
// Zero-fee scenario (fee_min = 0, fee_rate = 1):
deposit_amount = 9_999 satoshis
fee = max(9_999 * 1 / 10_000, 0) = max(0, 0) = 0   ← full fee bypass

// Systematic underpayment (fee_min = 50_000, fee_rate = 30):
withdraw_amount = 1_000_001 satoshis
exact_fee  = 1_000_001 * 30 / 10_000 = 3_000.003  → should collect 3_001
actual_fee = 1_000_001 * 30 / 10_000 = 3_000       ← 1 satoshi lost per tx

// Double truncation in protocol split (protocol_fee_rate = 9_000):
deposit_fee = 3_000 (already truncated)
protocol_fee = 3_000 * 9_000 / 10_000 = 2_700      ← exact, no loss here
// but if deposit_fee had been 3_001 (correct), protocol would get 2_700 not 2_700.9
```
