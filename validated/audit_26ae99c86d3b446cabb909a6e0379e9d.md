### Title
Unconditional Acceptance of Peras Certificates Bypasses All Certificate Validation, Enabling Chain Selection Manipulation - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The sole `BlockSupportsPeras` instance implements `validatePerasCert` as an unconditional `Right`, performing zero cryptographic or semantic validation on inbound Peras certificates received from peers. Because `processCerts` relies entirely on this function to gate admission into the `PerasCertDB`, any peer can inject arbitrary certificates that boost any block, directly manipulating Peras-weighted chain selection.

---

### Finding Description

The external report describes a **missing guard**: functions that should enforce a precondition before executing lack the required check, allowing the protected operation to proceed unconditionally. The exact analog here is `validatePerasCert`, which is the sole guard between a network-received `PerasCert` and its admission into the chain-selection-influencing `PerasCertDB`.

The only `BlockSupportsPeras` instance in the codebase — explicitly marked as a "degenerate instance for all blks" — implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This unconditionally returns `Right` for every certificate, regardless of its content. [1](#0-0) 

The inbound certificate processing pipeline in `processCerts` passes this function as the sole validator:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) -> mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _)            -> throw (PerasCertValidationError errs)
``` [2](#0-1) 

Since `validatePerasCert` never produces a `Left`, the `(errs, _)` branch is unreachable. Every certificate from every peer is unconditionally admitted.

The production writer path (`makePerasCertPoolWriterFromChainDB`) passes `validatePerasCert mkPerasParams` directly: [3](#0-2) 

Once admitted, a certificate triggers `chainSelSync`, which calls `chainSelectionForBlock` for the boosted block: [4](#0-3) 

Chain selection then uses `weightedSelectView`, which adds `wsvWeightBoost` (sourced from the fraudulent certificate's `vpcCertBoost = perasWeight params = 15`) to the total weight of the boosted chain: [5](#0-4) 

The `WeightedSelectView` `preferCandidate` compares `wsvTotalWeight = blockNo + weightBoost`: [6](#0-5) 

---

### Impact Explanation

An unprivileged peer can inject a `PerasCert` claiming to boost any block it chooses. With `perasWeight = 15` (the default), the adversary adds 15 weight units to a target chain. Since `wsvTotalWeight = blockNo + weightBoost`, a chain that is 15 blocks shorter than the honest chain becomes equally preferred, and a chain 16 blocks shorter can be made to appear superior. This lets an adversary cause an honest node to switch away from the canonical chain to a non-canonical one, violating chain selection safety beyond the intended security assumptions of the Peras protocol. [7](#0-6) 

**Impact class:** High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.

---

### Likelihood Explanation

- The attack requires only a network connection to a node with Peras enabled; no keys, stake, or operator access are needed.
- The `PerasCert` wire format is simple (round number + boosted block point) and trivially constructable.
- The `processCerts` path is exercised for every inbound certificate batch from any peer.
- The only existing mitigation is the deduplication check (`certsNotAlreadyInDb`), which only prevents re-injection of a certificate for a round already in the DB — it does not prevent injection of a new fraudulent certificate for any other round. [8](#0-7) 

**Likelihood:** High when Peras is enabled. The CHANGELOG notes Peras is disabled by default, but the code path is fully wired and the vulnerability is latent for any deployment that enables it.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with actual validation logic before Peras is enabled in production. At minimum, the function must verify:

1. **Committee membership**: the certificate's signers are eligible committee members for the claimed round.
2. **Cryptographic signatures**: the certificate carries valid signatures from a quorum of committee members.
3. **Round/slot consistency**: the certified block's slot is consistent with the claimed round number and protocol parameters.

The `BlockSupportsPeras` type class already declares the correct interface: [9](#0-8) 

The degenerate instance (tracked in issue #73 and #120) must not be used in any code path that processes network-received certificates.

---

### Proof of Concept

1. Enable Peras on a test node (set `perasWeight > 0` in `mkPerasParams` and enable the feature flag).
2. Connect a crafted peer that sends a `PerasCert` with `pcCertRound = <current round>` and `pcCertBoostedBlock = <point of an adversary-controlled block on a shorter fork>`.
3. The peer's certificate passes `validatePerasCert` unconditionally (returns `Right`).
4. `processCerts` adds it to the `PerasCertDB` via `ChainDB.addPerasCertAsync`.
5. `chainSelSync` triggers chain selection for the boosted block.
6. `preferAnchoredCandidate` now uses the non-empty `PerasWeightSnapshot`; the adversary's fork gains `perasWeight = 15` extra weight units.
7. If the adversary's fork is within 15 blocks of the honest tip, the node switches to the adversary's chain.

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
