Audit Report

## Title
TOCTOU Race in `fast_fin_transfer_to_near_callback` Enables Double-Spend of Bridged Tokens — (`near/omni-bridge/src/lib.rs`)

## Summary
`fast_fin_transfer` checks `is_unified_transfer_finalised` at entry but defers the actual token send and the write to `fast_transfers` to the async callback `fast_fin_transfer_to_near_callback`. That callback never re-checks `finalised_transfers`. A concurrently executing `fin_transfer_callback` can write to `finalised_transfers`, observe `fast_transfers` as empty, and send tokens to the recipient — after which `fast_fin_transfer_to_near_callback` fires, finds no duplicate in `fast_transfers`, and sends tokens a second time, producing a double-spend.

## Finding Description

**Entry point — `fast_fin_transfer` (line 778):**
The only guard against a transfer that has already been finalized is the `is_unified_transfer_finalised` check at entry:
```rust
if self.is_unified_transfer_finalised(&fast_fin_transfer_msg.transfer_id) {
    env::panic_str(BridgeError::TransferAlreadyFinalised.to_string().as_str());
}
```
For a NEAR recipient, the function does **not** write anything to `fast_transfers` or `finalised_transfers` at this point. It only schedules an async promise chain (`check_or_pay_ft_storage` → `fast_fin_transfer_to_near_callback`).

**Callback — `fast_fin_transfer_to_near_callback` (line 838):**
When the callback fires, it calls `add_fast_transfer` (which checks only `fast_transfers`, not `finalised_transfers`) and then unconditionally sends tokens:
```rust
let required_balance = self
    .add_fast_transfer(fast_transfer, relayer_id, storage_payer.clone())
    .saturating_add(ONE_YOCTO);
// ...
self.send_tokens(fast_transfer.token_id.clone(), recipient, amount_without_fee, &fast_transfer.msg)
```
There is no re-check of `is_unified_transfer_finalised` anywhere in the callback.

**Concurrent `fin_transfer` path — `process_fin_transfer_to_near` (line 1875):**
`fin_transfer_callback` calls `add_fin_transfer` (writes to `finalised_transfers`) and then reads `fast_transfers` to decide the recipient:
```rust
let mut required_balance = self.add_fin_transfer(&transfer_message.get_transfer_id());
// ...
let fast_transfer_status = self.get_fast_transfer_status(&fast_transfer.id());
```
If `fast_transfers` does not yet contain the entry (because `fast_fin_transfer_to_near_callback` has not run yet), `process_fin_transfer_to_near` falls into the `None` branch and sends tokens to the original recipient:
```rust
None => (recipient, transfer_message.msg.clone(), predecessor_account_id.clone()),
```
followed by `send_tokens` at line 1957.

**`add_fast_transfer` (line 2246):**
Only guards against a duplicate fast transfer (two `fast_fin_transfer` calls), not against a fast transfer that races with a completed `fin_transfer`:
```rust
require!(
    self.fast_transfers.insert(&fast_transfer.id(), ...).is_none(),
    BridgeError::FastTransferAlreadyPerformed.as_ref()
);
```

**Race window:**
```
Block N   : fin_transfer tx submitted → verify_proof receipt scheduled
            fast_fin_transfer tx submitted → check_or_pay_ft_storage receipt scheduled
            → is_unified_transfer_finalised check passes (finalised_transfers empty)

Block N+1 : verify_proof receipt executes → fin_transfer_callback receipt scheduled
            check_or_pay_ft_storage receipt executes → fast_fin_transfer_to_near_callback receipt scheduled

Block N+2 : fin_transfer_callback runs (created first, executes first)
            → add_fin_transfer writes X to finalised_transfers
            → get_fast_transfer_status returns None  ← fast_transfers still empty
            → send_tokens to recipient  ← FIRST payment

            fast_fin_transfer_to_near_callback runs
            → add_fast_transfer writes X to fast_transfers (no finalised_transfers check)
            → send_tokens to recipient  ← SECOND payment (double-spend)
```

## Impact Explanation
The recipient receives `amount_without_fee` tokens twice for a single cross-chain transfer. The bridge's token supply is inflated by exactly that amount. This constitutes direct theft of bridged funds — a double-spend of bridged tokens — matching the Critical allowed impact: "Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds."

## Likelihood Explanation
Trusted relayer registration is permissionless via `apply_for_trusted_relayer` with a NEAR stake deposit. Any user can become a trusted relayer, submit both `fast_fin_transfer` and `fin_transfer` for their own cross-chain transfer, and time the submissions so that `fin_transfer_callback` executes during the async gap of `fast_fin_transfer`. The gap spans at least one full block (the `check_or_pay_ft_storage` cross-contract call). Submitting `fin_transfer` before `fast_fin_transfer` in the same block ensures its callback receipt is created first and thus executes first in the subsequent block, making the ordering deterministic and the exploit repeatable.

## Recommendation
Re-check `is_unified_transfer_finalised` at the top of `fast_fin_transfer_to_near_callback`, before calling `add_fast_transfer` or sending any tokens. If the transfer has already been finalized, panic and allow the NEP-141 `ft_transfer_call` to refund the relayer's tokens:
```rust
// At the start of fast_fin_transfer_to_near_callback:
if self.is_unified_transfer_finalised(&fast_transfer.transfer_id) {
    env::panic_str(BridgeError::TransferAlreadyFinalised.to_string().as_str());
}
```
This mirrors the guard already present in `fast_fin_transfer` itself and closes the TOCTOU window.

## Proof of Concept
1. Attacker stakes NEAR and waits for `apply_for_trusted_relayer` activation.
2. Attacker initiates a transfer of 1000 USDC from Ethereum to their NEAR account.
3. In block N, attacker submits `fin_transfer` with the valid Ethereum proof. `verify_proof` is async; the callback `fin_transfer_callback` fires one block later.
4. In the same block N, attacker submits `fast_fin_transfer` via `ft_transfer_call` (fronting 999 USDC, fee = 1 USDC). The call schedules `check_or_pay_ft_storage` → `fast_fin_transfer_to_near_callback` but does not yet write to `fast_transfers`.
5. Block N+1: both first-level receipts execute; both callbacks are scheduled.
6. Block N+2: `fin_transfer_callback` executes first (its receipt was created first): `add_fin_transfer` writes the transfer ID to `finalised_transfers`; `get_fast_transfer_status` returns `None` (step 4's callback has not run yet); `send_tokens` sends 999 USDC to attacker's NEAR account. **First payment.**
7. Block N+2: `fast_fin_transfer_to_near_callback` fires: `add_fast_transfer` succeeds (no entry in `fast_transfers`); `send_tokens` sends 999 USDC to attacker's NEAR account. **Second payment.**
8. Attacker receives 1998 USDC total for a single 1000 USDC cross-chain transfer.

A local integration test can reproduce this by calling `process_fin_transfer_to_near` (simulating `fin_transfer_callback`) on a contract state where `finalised_transfers` is empty and `fast_transfers` is empty, asserting tokens are sent, then calling `fast_fin_transfer_to_near_callback` on the same state (now with `finalised_transfers` populated but `fast_transfers` still empty), and asserting tokens are sent a second time.
