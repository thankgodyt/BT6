### Title
Unconditional `validatePerasCert` Stub Allows Any Peer to Inject Arbitrary Peras Certificates and Manipulate Chain Selection - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `BlockSupportsPeras` typeclass instance used in production unconditionally accepts every inbound Peras certificate without performing any cryptographic or structural validation. An unprivileged peer can send a crafted `PerasCert` naming any block as the boosted target; the node will store it and apply its full Peras chain-selection boost weight to that block, potentially causing the node to prefer a non-canonical or attacker-controlled chain.

---

### Finding Description

**Root cause — stub validation that always returns `Right`:**

The `instance StandardHash blk => BlockSupportsPeras blk` in `SupportsPeras.hs` is the only concrete implementation of `validatePerasCert` in the codebase (confirmed by grep: the function is defined only in `SupportsPeras.hs` and called only in `PerasCert.hs`). Its body is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

It accepts every certificate unconditionally and assigns it the full `perasWeight params` boost. [1](#0-0) 

**Production inbound path wires this stub directly:**

`makePerasCertPoolWriterFromChainDB` — the writer used by the live node-to-node diffusion handler — passes `(validatePerasCert mkPerasParams)` as the validation callback to `processCerts`:

```haskell
processCerts
  systemTime
  (ChainDB.getPerasCertIds chainDB)
  -- TODO replace when actual plumbing is in place
  (validatePerasCert mkPerasParams)
  (void . ChainDB.addPerasCertAsync chainDB)
  certs
``` [2](#0-1) 

`processCerts` calls `validateCert <$> certsNotAlreadyInDb`; because the stub always returns `Right`, every certificate passes and is forwarded to `ChainDB.addPerasCertAsync`. [3](#0-2) 

**The live node-to-node handler uses this writer:**

```haskell
, hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      ...
``` [4](#0-3) 

**What a valid certificate should contain and verify:**

A real Peras certificate (`PerasCert` in `Peras/Cert/V1.hs`) carries `pcRoundNo`, `pcBoostedBlock`, `pcVoters` (with per-voter VRF eligibility proofs), and `pcSignature` (an aggregate BLS signature over the election ID and boosted block). The WFALS committee verifier (`WFALS.hs`) checks the aggregate signature, per-voter stake, and batch-verifies VRF outputs with linearization to prevent swap attacks. None of this is invoked through the stub. [5](#0-4) [6](#0-5) 

**Analog to the external report:**

| External report | This codebase |
|---|---|
| ERC-2612 permit signature authorizes token transfer | `PerasCert` aggregate BLS signature should authorize which block is boosted |
| `amountOutMin` is a critical parameter not bound to the permit | `pcBoostedBlock` / `pcRoundNo` are critical parameters not bound to any verified proof |
| Attacker calls the function with a valid signature but sets `amountOutMin = 0` | Attacker sends a crafted `PerasCert` with any `pcBoostedBlock`; the stub accepts it unconditionally |
| Result: MEV loss for the original user | Result: arbitrary chain-selection boost applied to attacker-chosen block |

### Impact Explanation

**Impact: High — chain selection manipulation by an unprivileged peer.**

A peer with no stake and no cryptographic credentials can send a `PerasCert` naming any block (including a non-canonical or minority-fork block) as `pcCertBoostedBlock`. The node stores it and applies `perasWeight params` as a chain-selection boost to that block. If the boost weight is large enough relative to the honest chain's density, the node will switch to the attacker's preferred fork, diverging from the canonical chain. Because every honest node running this code is equally vulnerable, a single attacker can cause network-wide chain-selection divergence without holding any stake.

This falls under: *"Chain selection, rollback, forecast, genesis, or header-state bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

---

### Likelihood Explanation

**Likelihood: High.**

The attack requires only a TCP connection to a Cardano node with Peras diffusion enabled. No stake, no keys, no prior knowledge beyond the target block's hash and a valid round number are needed. The attacker simply sends a `PerasCert` CBOR message over the object-diffusion mini-protocol. The stub is the only implementation wired into the production handler, so there is no fallback check.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
1. Verifies the aggregate BLS vote signature over `(pcRoundNo, pcBoostedBlock)` using the committee's aggregate verification key.
2. Verifies each voter's VRF eligibility proof (with linearization to prevent VRF-output swap attacks, as already implemented in `linearizeAndVerifyVRFs`).
3. Checks that the total stake of verified voters meets the quorum threshold.

Until the full committee-selection plumbing is in place, the inbound Peras certificate diffusion handler should either be disabled or should reject all inbound certificates rather than accept them unconditionally.

---

### Proof of Concept

A peer connects to a node with Peras diffusion enabled and sends a single object-diffusion message containing a `PerasCert` with:
- `pcCertRound` = any round number not yet in the DB
- `pcCertBoostedBlock` = hash of any block the attacker wants to boost (e.g., a minority-fork tip)
- `pcVoters` = empty / arbitrary
- `pcSignature` = zeroed / arbitrary bytes

`processCerts` calls `validatePerasCert mkPerasParams cert`, which returns:

```haskell
Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
```

The certificate is forwarded to `ChainDB.addPerasCertAsync`. Chain selection now treats the attacker-chosen block as having received a full Peras quorum boost, potentially causing the node to reorganize onto the attacker's fork. [1](#0-0) [2](#0-1) [4](#0-3)
