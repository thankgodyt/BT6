### Title
Peras Certificate Validation Is a No-Op Stub — Any Peer Can Inject Arbitrary Weight-Boosting Certificates - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` function in the production `BlockSupportsPeras` instance is a stub that unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or protocol-level checks. Because this function is the sole gate between a peer-supplied `PerasCert` and the `PerasCertDB` / chain-selection engine, any unprivileged peer can inject a crafted certificate that boosts an arbitrary block, causing the victim node to prefer a non-canonical fork over the honest chain.

---

### Finding Description

**Root cause — stub validation in the only production instance:**

The `BlockSupportsPeras` type class declares `validatePerasCert` as the mandatory certificate-validation hook. The sole concrete instance (the "degenerate instance for all blks", explicitly marked as a placeholder) implements it as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature, no committee-membership proof, no VRF output, no round-number bounds, no boosted-block reachability check — every certificate is accepted.

**Attacker-controlled entry path:**

Inbound certificates arrive via the object-diffusion mini-protocol. `makePerasCertPoolWriterFromChainDB` (the production writer) calls `processCerts` with `validatePerasCert mkPerasParams` as the validation callback:

```haskell
processCerts
  systemTime
  (ChainDB.getPerasCertIds chainDB)
  -- TODO replace when actual plumbing is in place
  (validatePerasCert mkPerasParams)
  (void . ChainDB.addPerasCertAsync chainDB)
  certs
``` [2](#0-1) 

`processCerts` partitions results into errors and successes; because `validatePerasCert` always returns `Right`, the error list is always empty and every certificate is forwarded to `ChainDB.addPerasCertAsync`: [3](#0-2) 

**How the accepted certificate corrupts chain selection:**

`addPerasCertAsync` enqueues the certificate for synchronous processing in `chainSelSync`. The handler adds it to `PerasCertDB` and, if the boosted block is in the VolatileDB, immediately triggers `chainSelectionForBlock`: [4](#0-3) 

Chain selection reads the `PerasWeightSnapshot` from `PerasCertDB.getWeightSnapshot`, which sums the boost of every stored certificate over the current fragment: [5](#0-4) 

`preferAnchoredCandidate` then compares chains using `weightedSelectView`, which adds `wsvWeightBoost` (from the injected certificate) to the candidate's block number. A fork carrying the attacker-boosted block can therefore appear heavier than the honest chain and be selected: [6](#0-5) 

---

### Impact Explanation

**Severity: Critical — chain-selection safety failure.**

An unprivileged peer that can speak the object-diffusion protocol can craft a `PerasCert` naming any block hash and any round number. Because `validatePerasCert` never rejects it, the certificate is stored and its boost is applied during chain selection. If the boosted block is on a minority fork, the victim node will switch to that fork, diverging from the honest majority. This is a direct consensus-safety failure: an honest node accepts and extends a non-canonical chain based on a fabricated certificate, with no stake or key compromise required.

**Likelihood: High.** The entry point is a standard peer-to-peer mini-protocol connection. No special privileges, no key material, and no majority stake are needed. The attacker only needs to be a connected peer.

---

### Likelihood Explanation

The object-diffusion mini-protocol is reachable by any peer the node accepts connections from. The degenerate `BlockSupportsPeras` instance is the only instance in the codebase and is used in both the `PerasCertDB`-direct and `ChainDB`-backed production writers. There is no secondary validation layer between `processCerts` and `PerasCertDB.addCert`.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that checks, at minimum:

1. **Committee membership**: the certificate must be signed by a quorum of eligible committee members for the claimed round.
2. **Cryptographic signature**: each committee member's signature over `(round, boostedBlock)` must verify against their registered key.
3. **Round-number bounds**: the round must be within the current Peras window (not arbitrarily far in the past or future).
4. **Boosted-block reachability**: the boosted block must be a known, valid block within the volatile window.

Until the real implementation is in place, the node should refuse to accept inbound certificates from peers (i.e., the object-diffusion server for certificates should not be started), rather than silently accepting all of them.

---

### Proof of Concept

1. Connect to a victim node as a peer that speaks the Peras object-diffusion protocol.
2. Craft a `PerasCert` with `pcCertRound = <current round>` and `pcCertBoostedBlock = <tip of a minority fork>`.
3. Send the certificate via the object-diffusion channel.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams })` unconditionally.
5. The certificate is enqueued via `ChainDB.addPerasCertAsync`.
6. `chainSelSync` adds it to `PerasCertDB` and calls `chainSelectionForBlock` for the boosted block.
7. `preferAnchoredCandidate` computes `wsvTotalWeight` for the minority fork as `blockNo + boost`, which now exceeds the honest chain's `blockNo + 0`.
8. The node switches to the minority fork.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
