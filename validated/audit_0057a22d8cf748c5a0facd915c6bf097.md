### Title
Peras Certificate and Vote Validation Bypass via Stub `validatePerasCert`/`validatePerasVote` — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance used for all block types unconditionally accepts every inbound Peras certificate and performs no cryptographic signature verification on votes. An unprivileged peer can inject a crafted `PerasCert` for any round and any block point; the certificate passes validation, is stored in the `PerasCertDB`, and triggers chain selection that may cause the honest node to prefer a non-canonical, adversarially-boosted chain.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines two validation methods:

```haskell
validatePerasCert :: PerasCfg blk -> PerasCert blk
                  -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)

validatePerasVote :: PerasCfg blk -> PerasVoteStakeDistr -> PerasVote blk
                  -> Either (PerasValidationErr blk) (ValidatedPerasVote blk)
```

The only concrete instance in the codebase — explicitly labelled a "degenerate instance for all blks to get things to compile" — implements `validatePerasCert` as an unconditional `Right`:

```haskell
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [1](#0-0) 

`validatePerasVote` only checks whether the voter ID appears in the stake distribution; it performs no signature check:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr = Right ...
  | otherwise = Left PerasValidationErr
``` [2](#0-1) 

Critically, the degenerate `PerasCert` and `PerasVote` data types carry **no signature field at all**:

```haskell
data PerasCert blk = PerasCert { pcCertRound :: PerasRoundNo, pcCertBoostedBlock :: Point blk }
data PerasVote blk = PerasVote { pvVoteRound :: PerasRoundNo, pvVoteBlock :: Point blk, pvVoteVoterId :: PerasVoterId }
``` [3](#0-2) 

The real BLS-signed certificate type (`Peras/Cert/V1.hs`) with `pcSignature :: AggregateVoteSignature PerasBLSCrypto` is not yet wired into the `BlockSupportsPeras` class. [4](#0-3) 

These stub implementations are called directly in the production inbound-certificate pipeline. `makePerasCertPoolWriterFromChainDB` passes `validatePerasCert mkPerasParams` as the validator to `processCerts`:

```haskell
(validatePerasCert mkPerasParams)  -- TODO replace when actual plumbing is in place
``` [5](#0-4) 

`processCerts` filters out already-known round numbers, then calls `validateCert` on the remainder. Because `validatePerasCert` always returns `Right`, every novel-round certificate from any peer is accepted: [6](#0-5) 

Once accepted, the certificate is added to the `PerasCertDB` and `chainSelSync` triggers chain selection for the boosted block, potentially switching the node to a non-canonical fork: [7](#0-6) 

The same stub path applies to votes via `makePerasCertPoolWriterFromChainDB` / `processVotes`: [8](#0-7) 

---

### Impact Explanation

When Peras is enabled, an unprivileged peer can send a crafted `PerasCert` claiming that an arbitrary block on a minority or adversarial fork was boosted by a quorum of committee members. Because `validatePerasCert` always returns `Right`, the certificate is stored and chain selection is re-run with the artificial weight boost. If the boosted block is on a fork that is otherwise shorter than the honest chain, the added `perasWeight` may make it heavier, causing the honest node to switch to the adversarial chain. This constitutes a chain-selection manipulation that lets an unprivileged peer make an honest node prefer a non-canonical chain — matching the **High** impact tier (chain selection bug) and potentially **Critical** (bypass of Peras certificate checks enabling unauthorized certificate acceptance).

---

### Likelihood Explanation

The Peras mini-protocol for certificate diffusion is reachable by any connected peer. The only barrier is that Peras must be enabled (it is disabled by default). Once enabled, the attack requires only sending a well-formed CBOR-encoded `PerasCert` with a fresh `pcCertRound` and a target `pcCertBoostedBlock` pointing to a block the node has already received. No key material, stake, or prior knowledge beyond the block hash is required.

---

### Recommendation

1. **Do not ship `validatePerasCert`/`validatePerasVote` as always-`Right` stubs in any code path reachable from the network.** Gate the Peras certificate/vote diffusion mini-protocols behind a runtime check that Peras is fully initialised with real validation logic before accepting external objects.
2. Wire the real `PerasCert` type from `Peras/Cert/V1.hs` (which carries `pcSignature :: AggregateVoteSignature PerasBLSCrypto`) into the `BlockSupportsPeras` class and implement `validatePerasCert` to verify the aggregate BLS signature against the declared voter set and the `(roundNo, boostedBlock)` message.
3. Implement `validatePerasVote` to verify the individual BLS vote signature and the VRF eligibility proof before accepting a vote from a peer.
4. Track the analogy to the original report: just as `Payment.sol` needed a per-payment nonce to prevent replay, Peras certificates need a verifiable aggregate signature binding the certificate to a specific `(roundNo, boostedBlock, voterSet)` tuple so that a peer cannot fabricate or replay a certificate for a different block.

---

### Proof of Concept

On a private testnet with Peras enabled:

1. Observe a valid block `B` on a minority fork at slot `s`, with hash `h`.
2. Construct a `PerasCert` CBOR value: `[roundNo, Point(s, h)]` (two-field encoding per the `Serialise` instance).
3. Send this certificate to the target node via the Peras certificate object-diffusion mini-protocol with a `pcCertRound` not yet in the node's `PerasCertDB`.
4. `processCerts` calls `validatePerasCert mkPerasParams cert` → `Right ValidatedPerasCert{..}`.
5. The certificate is stored; `chainSelSync` calls `chainSelectionForBlock` for block `B`.
6. The node's chain selection now adds `perasWeight` to any chain containing `B`, potentially switching to the adversarial fork. [9](#0-8) [10](#0-9)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
