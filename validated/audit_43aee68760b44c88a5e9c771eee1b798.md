### Title
Stale `praosStatePreviousEpochNonce` Initialized During TPraos→Praos Era Transition — (File: `ouroboros-consensus-protocol/src/ouroboros-consensus-protocol/Ouroboros/Consensus/Protocol/Praos.hs`)

---

### Summary

During the Alonzo→Babbage hard-fork (TPraos→Praos `ChainDepState` translation), `praosStatePreviousEpochNonce` is initialized to the **same value** as the current epoch nonce rather than the actual previous epoch nonce. This is the direct analog of the external report: accumulated state is set to a "last known" snapshot value instead of the properly computed current value. The field is explicitly documented as required for Peras certificate validation; when Peras validation is fully activated, nodes that crossed the Alonzo→Babbage boundary will evaluate certificates against the wrong nonce, diverging from nodes that did not cross that boundary.

---

### Finding Description

In `TranslateProto (TPraos c) (Praos c)`, the `translateChainDepState` function constructs the initial `PraosState` from the final `TPraosState`:

```haskell
translateChainDepState _ tpState =
    PraosState
      { ...
      , praosStateEpochNonce          = epochNonce
      , praosStatePreviousEpochNonce  = epochNonce  -- same as current epoch nonce
      , ...
      }
  where
    epochNonce = SL.ticknStateEpochNonce csTickn
``` [1](#0-0) 

The comment `-- same as current epoch nonce` acknowledges the approximation. The correct value is the epoch nonce from the **preceding** epoch — i.e., the value that `tickChainDepState` would have stored in `praosStatePreviousEpochNonce` had Praos been running for the prior epoch:

```haskell
-- tickChainDepState, on every new-epoch tick:
praosStatePreviousEpochNonce = praosStateEpochNonce st   -- stores current → previous
``` [2](#0-1) 

The field's purpose is stated explicitly in the same function's comment:

> "Store the existing current epoch nonce as the 'previous epoch' nonce. **This is needed to validate Peras certificates when they appear in blocks.**" [3](#0-2) 

The `praosStatePreviousEpochNonce` field is defined in `PraosState`: [4](#0-3) 

Peras certificate validation is currently a stub (`validatePerasCert` always returns `Right`): [5](#0-4) 

When that stub is replaced with real validation (which must use the previous epoch nonce to verify committee election proofs), every node whose `PraosState` was produced by `translateChainDepState` will carry `praosStatePreviousEpochNonce == praosStateEpochNonce` for the first Babbage epoch, which is incorrect.

---

### Impact Explanation

**Impact: High** — Hard-fork era-transition bug that breaks cross-era consensus invariants for production Cardano nodes.

When Peras certificate validation is activated, the incorrect `praosStatePreviousEpochNonce` causes a split in certificate acceptance:

- Nodes whose `PraosState` was produced by `translateChainDepState` (i.e., all nodes that crossed the Alonzo→Babbage boundary) will evaluate Peras certificates for the first Babbage epoch against `epochNonce` (wrong).
- Nodes that bootstrapped from a snapshot taken after the transition will have the correct value once one full epoch has elapsed.

An adversary who knows the wrong nonce value can craft a Peras certificate that passes validation on transition-crossing nodes but fails on fresh nodes (or vice versa), causing those two populations to assign different weight boosts to the same chain fragment. This is a chain-selection divergence: the two populations may prefer different chains, violating the safety property that honest nodes converge on a single chain.

The `weightedSelectView` / `preferAnchoredCandidate` path in chain selection uses `PerasWeightSnapshot` derived from accepted certificates: [6](#0-5) 

A certificate accepted by one population but not the other directly alters `wsvWeightBoost` and therefore `wsvTotalWeight`, the primary chain-selection comparator: [7](#0-6) 

---

### Likelihood Explanation

**Likelihood: High** — The Alonzo→Babbage transition is a historical fact on Cardano mainnet. Every node that has been running since before the Babbage era has a `PraosState` that was produced by `translateChainDepState`, and therefore carries the incorrect `praosStatePreviousEpochNonce` for the first Babbage epoch. The incorrect value is serialized and persisted: [8](#0-7) 

No operator action is required to trigger the bug; it is latent in every existing node's on-disk `ChainDepState` snapshot and will activate automatically when Peras certificate validation is enabled.

---

### Recommendation

During `translateChainDepState`, `praosStatePreviousEpochNonce` should not be set to the current epoch nonce. Since the TPraos `TicknState` does not store the previous epoch nonce directly, the safest fix is to initialize it to `SL.NeutralNonce` (signalling "unknown") and document that Peras certificate validation must treat a `NeutralNonce` previous-epoch nonce as unverifiable for the first Babbage epoch. Alternatively, the Peras certificate validation logic should explicitly handle the case where `praosStatePreviousEpochNonce == praosStateEpochNonce` (the degenerate post-transition state) by refusing to accept certificates whose committee election proof relies on the previous epoch nonce during that epoch.

---

### Proof of Concept

The root cause is a single line:

```haskell
-- File: ouroboros-consensus-protocol/src/ouroboros-consensus-protocol/Ouroboros/Consensus/Protocol/Praos.hs, line 768
praosStatePreviousEpochNonce = epochNonce  -- same as current epoch nonce
``` [9](#0-8) 

Concrete divergence sequence:

1. Node A crossed the Alonzo→Babbage boundary; its `praosStatePreviousEpochNonce` for epoch `E_babbage_0` equals `epochNonce_E_babbage_0` (wrong — should be `epochNonce_E_alonzo_last`).
2. Node B bootstrapped from a snapshot taken after epoch `E_babbage_1`; after one full epoch of `tickChainDepState` updates, its `praosStatePreviousEpochNonce` for epoch `E_babbage_0` is correct.
3. An adversary submits a Peras certificate whose committee election VRF proof is valid under `epochNonce_E_babbage_0` but invalid under `epochNonce_E_alonzo_last`.
4. Node A accepts the certificate; Node B rejects it.
5. The accepted certificate adds `wsvWeightBoost` to a chain fragment on Node A but not Node B, causing `preferAnchoredCandidate` to return `ShouldSwitch` on Node A and `ShouldNotSwitch` on Node B for the same candidate chain — a consensus safety failure. [10](#0-9)
