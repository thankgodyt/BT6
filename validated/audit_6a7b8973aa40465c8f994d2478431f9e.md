### Title
Tokens Permanently Stuck at Bridge When `safe_mint` Recipient Is Unregistered — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

In `safe_mint`, nBTC tokens are minted to `bridge_id` **before** checking whether the intended recipient account is registered. If the recipient is not registered, the function silently returns `U128(0)` and the minted tokens remain at `bridge_id` with no recovery path for the depositor and no `lost_found` entry created.

---

### Finding Description

The `safe_mint` function in `contracts/nbtc/src/lib.rs` follows this sequence:

1. **Mint to bridge first** — `self.token.internal_deposit(&self.bridge_id, amount.into())` unconditionally credits the full deposit amount to `bridge_id`.
2. **Check recipient registration** — `if self.token.accounts.get(&account_id).is_none()` checks whether the intended recipient has a registered storage slot.
3. **Silent early return** — If the recipient is not registered, the function returns `PromiseOrValue::Value(U128(0))` immediately, leaving the tokens at `bridge_id`. [1](#0-0) 

No `lost_found` entry is created for the user, no event signals the failure, and no mechanism exists in the nbtc contract to redirect or recover those tokens to the intended recipient later.

The `lost_found` mechanism in the bridge contract is populated only by `transfer_nbtc_callback` when an `ft_transfer` cross-contract call fails. [2](#0-1) 

`safe_mint` never goes through `ft_transfer`, so the `lost_found` path is never triggered. The minted tokens are silently absorbed into the bridge's own balance.

The `mint` function (used in the standard deposit flow) avoids this by calling `mint_inner`, which auto-registers the account before depositing. [3](#0-2) 

`safe_mint` deliberately skips auto-registration (to preserve atomicity for integrations), but provides no compensating recovery mechanism.

---

### Impact Explanation

A user who deposits BTC via the `safe_deposit` flow with a `recipient_id` that has not pre-registered for nBTC storage will have their entire deposit value minted to `bridge_id` and permanently inaccessible to them. There is no on-chain mechanism for the user to claim these tokens, and no `lost_found` record is created for operators to identify and return the stuck funds. The depositor's BTC is effectively lost until manual operator intervention — if the operator can even identify the affected accounts.

This matches: **Medium — stuck bridge state requiring operator intervention / permanent loss of user funds without direct theft.**

---

### Likelihood Explanation

The `safe_deposit` flow is specifically designed for smart contract integrations (e.g., Omni Bridge). Smart contracts that deposit BTC and specify a `recipient_id` that has not called `storage_deposit` on the nBTC contract will trigger this path. New users or integrations that do not pre-register storage are a realistic and common scenario. The trigger requires no privileged access — any relayer submitting a `verify_deposit` proof for a deposit with a `safe_deposit` message pointing to an unregistered account will cause this.

---

### Recommendation

Move the registration check **before** minting, or auto-register the account before calling `internal_deposit`. Alternatively, if the account is not registered, do not mint at all and instead emit an event or create a `lost_found` entry so the funds can be recovered. The current pattern — mint first, check second, silently discard — is the root cause of the stuck-funds condition.

---

### Proof of Concept

1. User (or smart contract) sends BTC to a deposit address derived from a `DepositMsg` with `safe_deposit` set and `recipient_id = alice.near`, where `alice.near` has never called `storage_deposit` on the nBTC contract.
2. Relayer calls `verify_deposit` on the bridge with the BTC inclusion proof.
3. Bridge verifies the proof and calls `safe_mint(alice.near, amount, Some(msg))` on the nbtc contract.
4. `safe_mint` executes `self.token.internal_deposit(&self.bridge_id, amount.into())` — nBTC is minted to `bridge_id`.
5. `self.token.accounts.get(&alice.near)` returns `None` — alice is not registered.
6. `safe_mint` returns `PromiseOrValue::Value(U128(0))`.
7. The minted nBTC remains at `bridge_id`. No `lost_found` entry is created for `alice.near`. Alice's BTC deposit is permanently stuck. [4](#0-3)

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }
