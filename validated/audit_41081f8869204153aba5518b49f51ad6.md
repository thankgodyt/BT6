### Title
Permissionless `request_refund` Allows Any Caller to Register an Attacker-Controlled BTC Refund Address When `deposit_msg.refund_address` Is `None` — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

The `request_refund` function is callable by any NEAR account and does not bind the `refund_address` parameter to the caller's identity. When a user's `DepositMsg` has `refund_address: None`, an attacker who observes the Bitcoin deposit can race to call `request_refund` first — supplying the attacker's own BTC address — before the legitimate depositor does. The first registration wins; the victim's subsequent call panics with `"Refund request already exists for this UTXO"`, and the stored refund record points to the attacker's BTC address.

---

### Finding Description

`request_refund` is a public, payable function with no caller-identity restriction on the `refund_address` argument: [1](#0-0) 

The only guard on `refund_address` is inside `request_refund_callback`:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [2](#0-1) 

When `deposit_msg.refund_address` is `None` (the common case for users who did not pre-commit a BTC refund address), this branch is skipped entirely. Any caller may pass any BTC address. The `utxo_storage_key` is derived solely from the Bitcoin transaction data (`tx_id@vout`), not from the caller: [3](#0-2) 

The duplicate-request guard then makes the first registration permanent: [4](#0-3) 

The stored `refund_address` is written verbatim into the `RefundRequest` with no further ownership check: [5](#0-4) 

`execute_refund` later builds the Bitcoin PSBT paying out to exactly that stored address: [6](#0-5) 

---

### Impact Explanation

**Attack outcome — two tiers:**

1. **Theft (if DAO/Operator does not intervene):** After the `unsafe_refund_timelock_sec` elapses, anyone can call `execute_refund`. The MPC network signs a Bitcoin transaction paying the attacker's BTC address. The victim's BTC is permanently transferred to the attacker. This matches the allowed Critical impact: *"Significant loss, theft, destruction, or permanent locking of user or protocol funds."*

2. **Stuck state requiring operator intervention (if DAO/Operator is monitoring):** The DAO/Operator must call `reject_refund` to clear the attacker's entry before the victim can re-register. This matches the allowed Medium impact: *"stuck bridge state requiring operator intervention."* [7](#0-6) 

---

### Likelihood Explanation

All information the attacker needs is public:

- The `DepositMsg` (including `refund_address: None`) is emitted as an on-chain event by `get_user_deposit_address`.
- The Bitcoin transaction bytes and Merkle proof are publicly available from the Bitcoin blockchain.
- `request_refund` has no role restriction; any NEAR account paying the storage deposit can call it.

The attacker simply monitors the Bitcoin blockchain for deposits to known bridge addresses and races to call `request_refund` before the depositor does. No privileged access, leaked key, or majority hash-rate is required. The NEAR storage deposit cost is the only barrier, and it is economically rational to pay it when the stolen BTC value exceeds it. [8](#0-7) 

---

### Recommendation

Bind the `refund_address` to the caller's identity when `deposit_msg.refund_address` is `None`. Two complementary fixes:

1. **Require `deposit_msg.refund_address` to be `Some` for permissionless calls.** If the user did not pre-commit a BTC refund address in the `DepositMsg`, only a privileged role (DAO/Operator) should be allowed to register a refund address on their behalf.

2. **Store the NEAR caller alongside the refund request and enforce that only the original registrant (or a privileged role) can call `execute_refund`.** This prevents a racing attacker from benefiting even if they register first.

---

### Proof of Concept

**Setup:** Alice deposits BTC using a `DepositMsg` with `refund_address: None`. The deposit is never finalized by a relayer.

**Step 1 — Attacker races `request_refund`:**

```
Attacker calls:
  request_refund(
    deposit_msg  = Alice's DepositMsg { refund_address: None, ... },  // from on-chain event
    refund_address = "attacker_btc_address",                          // attacker's address
    tx_bytes     = <Alice's BTC tx bytes>,                            // from Bitcoin blockchain
    vout         = 0,
    proof        = <valid Merkle proof>,                              // from Bitcoin blockchain
    gas_fee      = None,
  )
```

The Light Client validates the proof. `request_refund_callback` stores:
```
RefundRequest {
    utxo_storage_key: "<alice_txid>@0",
    refund_address: "attacker_btc_address",   // ← attacker's address
    ...
}
```

**Step 2 — Alice's call fails:**

```
Alice calls request_refund(..., refund_address = "alice_btc_address", ...)
→ PANIC: "Refund request already exists for this UTXO"
```

**Step 3 — Attacker executes the refund:**

After `unsafe_refund_timelock_sec` elapses (and if DAO/Operator does not reject):

```
Attacker (or anyone) calls:
  execute_refund(utxo_storage_key = "<alice_txid>@0", ...)
```

The bridge builds a PSBT paying `"attacker_btc_address"`, the MPC network signs it, and Alice's BTC is sent to the attacker. [9](#0-8)

    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);

    pub(crate) fn finalize_refund_with_psbt(
        &mut self,
        caller: AccountId,
        mut refund_request: RefundRequest,
        psbt: PsbtWrapper,
        refund_amount: u128,
        utxo_storage_key: String,
    ) {
        let gas_fee = refund_request.gas_fee;
        let refund_address = refund_request.refund_address.clone();

        let deposit_msg = refund_request.deposit_msg();
        let path = get_deposit_path(&deposit_msg);
        let vutxo = VUTXO::Current(UTXO {
            path,
            tx_bytes: refund_request.tx_bytes.0.clone(),
            vout: refund_request.vout,
            balance: u64::try_from(refund_request.amount)
                .unwrap_or_else(|_| env::panic_str("Amount overflow")),
        });

        let psbt_hex = psbt.serialize();
        let btc_pending_id = psbt.get_pending_id();

        if !self.check_account_exists(&caller) {
            self.internal_set_account(&caller, crate::Account::new(&caller));
        }
        self.require_pending_sign_capacity(&caller);

        let btc_pending_info = BTCPendingInfo {
            account_id: caller.clone(),
            btc_pending_id: btc_pending_id.clone(),
            transfer_amount: 0,
            actual_received_amount: refund_amount,
            withdraw_fee: 0,
            gas_fee,
            burn_amount: 0,
            psbt_hex,
            vutxos: vec![vutxo],
            signatures: vec![None; 1],
            tx_bytes_with_sign: None,
            create_time_sec: nano_to_sec(env::block_timestamp()),
            last_sign_time_sec: 0,
            state: PendingInfoState::Refund(OriginalState {
                stage: PendingInfoStage::PendingSign,
                max_gas_fee: gas_fee,
                last_rbf_time_sec: None,
                cancel_rbf_reserved: None,
            }),
        };

        require!(
            self.data_mut()
                .btc_pending_infos
                .insert(btc_pending_id.clone(), btc_pending_info.into())
                .is_none(),
            "pending info already exist"
        );
        self.internal_unwrap_mut_account(&caller)
            .btc_pending_sign_ids
            .insert(btc_pending_id.clone());

        // Mark UTXO as verified to prevent verify_deposit later
        self.data_mut()
            .verified_deposit_utxo
            .insert(utxo_storage_key.clone());

        Event::RefundExecuted {
            utxo_storage_key: utxo_storage_key.clone(),
            amount: refund_request.amount.into(),
            refund_address,
        }
        .emit();

        Event::GenerateBtcPendingInfo {
            account_id: &caller,
            btc_pending_id: &btc_pending_id,
        }
        .emit();

        // Keep the request (so `execute_refund` can be called again to re-create
        // the transaction) but mark it executed; it is removed only when the
        // refund is finalized in `verify_refund_finalize`.
        refund_request.executed = true;
        self.data_mut()
            .refund_requests
            .insert(utxo_storage_key, refund_request.into());
