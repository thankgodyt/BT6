### Title
nBTC Permanently Locked When Sent Directly via `ft_transfer` Instead of `ft_transfer_call` - (File: contracts/satoshi-bridge/src/api/token_receiver.rs)

### Summary
The bridge's `ft_on_transfer` accounting handler is only invoked when nBTC arrives via `ft_transfer_call`. If a user sends nBTC to the bridge contract using the standard NEP-141 `ft_transfer` call, the tokens are credited to the bridge's nBTC balance but no accounting entry is created. There is no recovery path — no admin sweep function, no `lost_found` entry, no refund — so the tokens are permanently locked.

### Finding Description
The bridge implements `FungibleTokenReceiver::ft_on_transfer` as its sole entry point for receiving and accounting for nBTC:

```
contracts/satoshi-bridge/src/api/token_receiver.rs, lines 21–67
```

This callback is only triggered by `ft_transfer_call` on the nBTC contract. When a user calls `ft_transfer` directly (a fully valid standard NEP-141 operation), the nBTC contract transfers tokens to the bridge's account without invoking `ft_on_transfer`. The bridge has no hook, no fallback, and no admin function to detect or recover these tokens.

The bridge tracks nBTC in exactly three accounting buckets, all of which are populated exclusively inside `ft_on_transfer`:

1. `BTCPendingInfo.burn_amount` — withdrawal-bound nBTC received via `ft_transfer_call` with `Withdraw` message
2. `cur_available_protocol_fee` / `acc_collected_protocol_fee` — nBTC received via `ft_transfer_call` with `DepositProtocolFee` message
3. `lost_found` — nBTC that failed to be returned to users during cancel-withdraw (populated in `transfer_nbtc_callback`, `contracts/satoshi-bridge/src/token_transfer.rs` lines 54–74)

None of these buckets are populated by a direct `ft_transfer`. The bridge has no function to sweep or recover unaccounted nBTC from its own balance. The `claim_lost_found` function only returns amounts explicitly recorded in the `lost_found` map; it cannot access the untracked surplus.

This is a direct structural analog to the reported `StakingEscrow` bug: tokens that arrive through an unaccounted path (direct transfer rather than the expected callback) are invisible to every release/recovery mechanism the contract exposes.

### Impact Explanation
Any nBTC sent directly to the bridge contract via `ft_transfer` is permanently lost to the sender. The bridge's nBTC balance increases, but the user has no way to recover their tokens. There is no admin function to sweep stuck nBTC, no `lost_found` entry is created, and no refund mechanism exists. The tokens are effectively burned from the user's perspective while inflating the bridge's unaccounted balance. This constitutes permanent locking of user funds.

### Likelihood Explanation
`ft_transfer` is a standard, well-documented NEP-141 method. Any user or integrator who sends nBTC to the bridge contract address using `ft_transfer` instead of `ft_transfer_call` — a realistic mistake when scripting or using generic wallet tooling — permanently loses their tokens. No privileged access or special conditions are required; the loss is triggered by a single ordinary transaction from any NEAR account.

### Recommendation
Add a DAO-restricted admin function that can transfer a specified amount of the bridge's nBTC balance to a designated recovery address, covering the gap between the bridge's actual nBTC balance and the sum of all tracked accounting buckets. Alternatively, document prominently that `ft_transfer` to the bridge address results in permanent, unrecoverable token loss.

### Proof of Concept
1. User holds nBTC and calls `ft_transfer(bridge_account_id, amount, None)` on the nBTC contract.
2. The nBTC contract debits the user and credits the bridge's account — a valid NEP-141 transfer.
3. `ft_on_transfer` is **not** called (it is only called by `ft_transfer_call`).
4. The bridge's nBTC balance increases by `amount`, but no entry is created in `btc_pending_infos`, `cur_available_protocol_fee`, or `lost_found`.
5. The user calls `claim_lost_found` — it panics with "The account does not have lostfound".
6. There is no other public or admin function that can return the tokens. The `amount` nBTC is permanently locked.
