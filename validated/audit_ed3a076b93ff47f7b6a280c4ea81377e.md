### Title
`validatePerasCert` Unconditionally Accepts Any Certificate, Allowing Unprivileged Peers to Inflate `PerasWeightSnapshot` and Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance's `validatePerasCert` always returns `Right` for any certificate, bypassing all Peras certificate validation. This is the direct analog to the external report's pattern: an accumulator (`PerasWeightSnapshot`) is updated with a **pre-validation** value (the full claimed boost) instead of a **post-validation** value (a boost only from certificates that pass committee/signature/quorum checks). An unprivileged peer can inject arbitrary certificates via the ObjectDiffusion mini-protocol, inflating the weight snapshot for any block on any fork, and causing honest nodes to prefer non-canonical chains.

---

### Finding Description

**Root cause — `validatePerasCert` always returns `Right`:** [1](#0-0) 

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This is the **only** `BlockSupportsPeras` instance in the codebase — a blanket instance over all `StandardHash blk` — so it applies to every block type including Cardano production blocks. [2](#0-1) 

**Inbound certificate path — no rejection possible:**

When a peer sends certificates via the ObjectDiffusion protocol, `processCerts` calls `validatePerasCert`, which always succeeds: [3](#0-2) 

Every certificate — regardless of whether it carries a valid committee signature, a legitimate quorum, or a real boosted block — is timestamped and forwarded to `ChainDB.addPerasCertAsync`.

**Accumulator updated with pre-validation value:**

`implGetWeightSnapshot` builds the `PerasWeightSnapshot` directly from every certificate stored in `pcdsCertsByTicket`, with no further filtering: [4](#0-3) 

The `implAddCert` function itself also carries an explicit TODO acknowledging that non-trivial validation is missing: [5](#0-4) 

**Weight snapshot drives chain selection:**

`chainSelectionForBlock` reads the weight snapshot atomically and passes it to `preferAnchoredCandidate`, which uses `wsvTotalWeight` (block number + weight boost) to decide whether to switch chains: [6](#0-5) [7](#0-6) 

**Analog to the external report:**

| External report (AdapterVault) | Ouroboros Consensus |
|---|---|
| `total_assets_deposited += _asset_amount` (pre-slippage) | `PerasWeightSnapshot` += `perasWeight params` for every inbound cert (pre-validation) |
| Should use post-slippage actual amount | Should use boost only from certs passing committee/quorum checks |
| Accumulator overestimates vault assets → wrong fee yield | Accumulator overestimates chain weight → wrong chain selection |

### Impact Explanation

An unprivileged peer can craft a `PerasCert` with `pcCertBoostedBlock` pointing to any block on any fork. Because `validatePerasCert` always returns `Right`, the certificate is accepted, stored, and its boost is added to the `PerasWeightSnapshot`. Chain selection then compares `wsvTotalWeight` values; a fork boosted by even one injected certificate gains `perasWeight params` extra weight (a configurable value, e.g., 15 on mainnet parameters). An attacker who injects enough certificates for a fork can make an honest node switch to a non-canonical chain, constituting a **chain selection safety failure** and a **bypass of Peras certificate validation**.

---

### Likelihood Explanation

The attack requires only a peer connection via the ObjectDiffusion mini-protocol. No stake, no keys, no admin access. The only guard in `chainSelSync` is that the boosted block must not be older than the immutable tip: [8](#0-7) 

Any recent block on any fork satisfies this check. The attack is repeatable and requires no brute force.

---

### Recommendation

1. Implement a real `validatePerasCert` for Cardano blocks that verifies committee membership, individual vote signatures, and quorum threshold before producing a `ValidatedPerasCert`.
2. The `PerasWeightSnapshot` accumulator must only be populated from certificates that have passed this full validation — i.e., use the **post-validation** boost value, not the pre-validation claimed boost.
3. `implAddCert` should enforce the same invariant at the DB boundary (the existing TODO at line 167–168 of `Impl.hs` must be resolved before the ObjectDiffusion path is enabled in production).

---

### Proof of Concept

1. Connect to a node via the Peras certificate ObjectDiffusion mini-protocol.
2. Craft a `PerasCert { pcCertRound = freshRound, pcCertBoostedBlock = blockPointOnFork }` where `blockPointOnFork` is a recent block on a competing fork.
3. Send the certificate. `processCerts` calls `validatePerasCert`, which returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }` unconditionally.
4. The certificate is stored in `PerasCertDB`; `implGetWeightSnapshot` now includes `(blockPointOnFork, perasWeight params)` in the snapshot.
5. `chainSelSync (ChainSelAddPerasCert ...)` triggers `chainSelectionForBlock` for the boosted block.
6. `preferAnchoredCandidate` computes `wsvTotalWeight` for the fork, which now exceeds the honest chain's weight by `perasWeight params`.
7. The node switches to the adversarial fork.

  WithFingerprint pcds fp <- readTVar pcdbState
