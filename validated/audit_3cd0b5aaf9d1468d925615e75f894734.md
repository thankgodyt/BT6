### Title
Small-Amount Transfer Permanently Locked When `normalize_amount` Returns Zero in `sign_transfer` — (`near/omni-bridge/src/lib.rs`)

---

### Summary

In `near/omni-bridge/src/lib.rs`, the `sign_transfer` function normalizes the transfer amount to the destination chain's decimal precision before requesting an MPC signature. When the user's `amount - fee` is smaller than the decimal scaling factor (`10^(origin_decimals - decimals)`), `normalize_amount` returns `0` via integer floor division. The subsequent `require!(amount_to_transfer > 0)` guard then permanently blocks signing. Because `init_transfer` only validates `fee < amount` (not that the normalized remainder is non-zero), such a transfer is accepted and stored, but can never be signed or completed, permanently locking the user's tokens in `pending_transfers` with no cancellation path.

---

### Finding Description

`sign_transfer` computes the on-chain amount to sign:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message
        .amount_without_fee()
        .near_expect(BridgeError::InvalidFee),
    decimals,
);

require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
``` [1](#0-0) 

`normalize_amount` performs integer floor division:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [2](#0-1) 

If `amount_without_fee() < 10^(origin_decimals - decimals)`, the result is `0`, and `sign_transfer` panics with `ERR_INVALID_AMOUNT_TO_TRANSFER` every time it is called for that transfer.

The `init_transfer` entry point only validates:

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
``` [3](#0-2) 

There is no check that `normalize_amount(amount - fee, decimals) > 0` at deposit time. A transfer with `amount = 1` and `fee = 0` passes the fee guard and is stored in `pending_transfers`, but `sign_transfer` will always revert for it.

`update_transfer_fee` only allows fees to increase (never decrease), so the user cannot reduce the fee to recover a non-zero normalized amount. [4](#0-3) 

`remove_transfer_message` is only called from `claim_fee_callback` (which requires a completed `sign_transfer` first) and `process_fin_transfer_to_other_chain`. There is no user-callable cancel or refund function. [5](#0-4) 

---

### Impact Explanation

Any user who bridges a token amount smaller than `10^(origin_decimals - decimals)` — for example, bridging fewer than `10^18` yocto-units of a NEAR-native token (24 decimals) to an EVM chain where it is registered with 6 decimals — will have their tokens permanently locked in the bridge's `pending_transfers` storage. The transfer cannot be signed, finalized, or cancelled. This constitutes permanent freezing of bridged funds.

---

### Likelihood Explanation

Low. It requires a user to bridge a dust amount relative to the decimal gap. For tokens with large decimal differences (e.g., NEAR 24-decimal tokens mapped to 6-decimal EVM representations, a gap of 18), any amount below `10^18` base units triggers the bug. This is a realistic user mistake (e.g., bridging `0.000001` of a token without understanding precision loss), and no UI-level guard is enforced at the contract level.

---

### Recommendation

Add a normalization check at `init_transfer` time, before storing the transfer:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

This mirrors the existing guard in `sign_transfer` but applies it eagerly so that un-signable transfers are rejected at deposit time rather than after funds are locked.

---

### Proof of Concept

1. A token is registered with `origin_decimals = 24`, `decimals = 6` (decimal gap = 18).
2. A user calls `ft_transfer_call` with `amount = 10^17` (below the `10^18` threshold) and `fee = 0`.
3. `init_transfer` checks `fee < amount` → `0 < 10^17` ✓ — transfer is stored in `pending_transfers`.
4. A relayer calls `sign_transfer` for this transfer.
5. `normalize_amount(10^17, diff=18)` = `10^17 / 10^18` = `0` (integer floor division).
6. `require!(0 > 0)` panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.
7. Every subsequent call to `sign_transfer` for this transfer ID produces the same panic.
8. The user's `10^17` base-unit tokens remain locked in `pending_transfers` with no recovery path. [1](#0-0) [2](#0-1) [3](#0-2)
