### Title
Unhandled `send_tokens` Promise Result Causes Permanent Loss of Fast-Transfer Relayer Funds - (File: `near/omni-bridge/src/lib.rs`)

### Summary
In two code paths that repay a fast-transfer relayer after the canonical cross-chain proof is finalized, the `send_tokens()` promise is fired with `.detach()`, meaning its success or failure is never observed. The bridge's internal state (fast-transfer marked as finalised, locked-token counters adjusted) is committed unconditionally. If the underlying `ft_transfer` or `mint` call fails for any reason, the relayer's pre-funded tokens are permanently unrecoverable and the bridge's accounting is left in an inconsistent state. A developer-authored `TODO` comment in the UTXO path explicitly acknowledges this gap.

---

### Finding Description

**Root cause 1 — `process_fin_transfer_to_other_chain`**

When `fin_transfer_callback` routes a proof for a transfer whose destination is a non-NEAR chain and a fast-transfer entry exists, the bridge calls `send_tokens()` to repay the relayer and immediately calls `.detach()` on the returned promise, then unconditionally marks the fast transfer as finalised:

```rust
// near/omni-bridge/src/lib.rs  ~2028-2040
if let Some(relayer) = recipient {
    self.send_tokens(
        token,
        relayer,
        U128(transfer_message.amount_without_fee()...),
        "",
    )
    .detach();                                          // ← result ignored
    self.mark_fast_transfer_as_finalised(&fast_transfer.id()); // ← state committed
}
``` [1](#0-0) 

**Root cause 2 — `utxo_fin_transfer_fast`**

The UTXO fast-transfer settlement path repeats the same pattern. Notably, the developers left an explicit `TODO` comment acknowledging the unhandled failure case:

```rust
// near/omni-bridge/src/lib.rs  ~2483-2484
// TODO: check how to deal with failed send_tokens
return self.utxo_fin_transfer_fast(fast_transfer, status, utxo_fin_transfer_msg);
```

Inside `utxo_fin_transfer_fast`:

```rust

    fast_transfer.token_id.clone(),

    amount,

)
.detach();   // ← result ignored; fast transfer already removed/finalised above
``` [2](#0-1) [3](#0-2) 

**Root cause 3 — `fin_transfer_send_tokens_callback` fee payments**

Fee payments to the fee recipient (relayer) after a successful NEAR-destination transfer are also detached:

```rust
ext_token::ext(token)
    .with_static_gas(MINT_TOKEN_GAS)
    .mint(fee_recipient.clone(), transfer_message.fee.fee, None)
    .detach();   // ← fee payment result ignored
``` [4](#0-3) 

**Contrast with the correctly handled path**

The NEAR-destination `process_fin_transfer_to_near` path correctly chains a callback (`fin_transfer_send_tokens_callback`) that checks the promise result and reverts state on failure. The fast-transfer repayment paths have no equivalent callback. [5](#0-4) 

---

### Impact Explanation

For native (non-deployed) tokens: if `ft_transfer` to the relayer fails (e.g., the relayer's account lacks storage registration on the token contract, or the token contract is paused/upgraded), the tokens remain locked inside the bridge contract. Because `mark_fast_transfer_as_finalised` has already been called, the fast-transfer entry is permanently closed; there is no re-entry point to retry the repayment. The relayer's pre-funded tokens are permanently frozen inside the bridge.

For deployed (bridged) tokens: if `mint()` fails, the tokens are simply never created for the relayer. The relayer's pre-funded amount is unrecoverable.

In both cases the bridge's `locked_tokens` accounting has already been adjusted (unlocked from origin chain, locked to destination chain) before the failure, leaving the accounting permanently inconsistent with actual token balances.

---

### Likelihood Explanation

The `send_tokens` call can fail due to:
- Insufficient gas forwarded to the detached promise (the gas budget is computed dynamically and the `TODO` comment signals developer uncertainty).
- The relayer's account lacking NEP-141 storage registration on the specific token contract at the time of repayment.
- The token contract being paused or upgraded between the fast-transfer execution and the canonical finalization.

The fast-transfer relayer is a trusted but unprivileged bridge participant. Any of the above conditions — some of which can be induced by a malicious token deployer or a race condition — permanently destroys the relayer's funds with no recovery path. The developer `TODO` at line 2484 confirms this is a known unresolved gap.

---

### Recommendation

Replace `.detach()` with a proper callback (analogous to `fin_transfer_send_tokens_callback`) that:
1. On success: emits the finalisation event and cleans up state.
2. On failure: reverts `mark_fast_transfer_as_finalised` (or re-inserts the fast-transfer entry) so the repayment can be retried, and emits a failure event.

This mirrors the pattern already used in `process_fin_transfer_to_near` → `fin_transfer_send_tokens_callback`.

---

### Proof of Concept

1. Trusted relayer R executes a fast transfer for a cross-chain transfer T (ETH → SOL), sending tokens to the user on NEAR.
2. The canonical `fin_transfer` proof for T is submitted and `process_fin_transfer_to_other_chain` is called.
3. `send_tokens(token, R, amount, "").detach()` is called. At this moment, R's account has no storage registered on the token contract (e.g., the token was recently deployed and R never called `storage_deposit`).
4. `mark_fast_transfer_as_finalised` is called — the fast-transfer entry is permanently closed.
5. The detached `ft_transfer` promise fails silently. R's tokens are never received.
6. R attempts to claim repayment again — the bridge rejects with `ERR_FAST_TRANSFER_ALREADY_FINALISED`.
7. R's pre-funded tokens are permanently frozen in the bridge contract with no recovery mechanism. [6](#0-5) [7](#0-6)
