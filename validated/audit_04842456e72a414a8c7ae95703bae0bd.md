### Title
Double Integer Division in Fee Split Causes Systematic Protocol Fee Under-Collection - (File: contracts/satoshi-bridge/src/config.rs)

### Summary
`BridgeFee::get_fee` and `BridgeFee::get_protocol_and_relayer_fee` are called sequentially in both the deposit and withdrawal paths. Each call performs an independent integer division by `MAX_RATIO`, introducing two truncation steps where one combined division would suffice. The intermediate truncation systematically reduces the `protocol_fee` computed in the second step, causing the protocol treasury to receive less than the configured share on every fee-bearing transaction.

### Finding Description
`BridgeFee` exposes two methods:

```rust
// config.rs:30-35
pub fn get_fee(&self, amount: u128) -> u128 {
    std::cmp::max(
        amount * u128::from(self.fee_rate) / u128::from(MAX_RATIO),
        self.fee_min,
    )
}

// config.rs:37-41
pub fn get_protocol_and_relayer_fee(&self, fee_amount: u128) -> (u128, u128) {
    let protocol_fee = fee_amount * u128::from(self.protocol_fee_rate) / u128::from(MAX_RATIO);
    let relayer_fee = fee_amount - protocol_fee;
    (protocol_fee, relayer_fee)
}
```

In the deposit path (`deposit.rs:52-56`):

```rust
let deposit_fee = config.deposit_bridge_fee.get_fee(deposit_amount);   // division 1
let (protocol_fee, relayer_fee) =
    config.deposit_bridge_fee.get_protocol_and_relayer_fee(deposit_fee); // division 2
```

In the withdrawal path, `withdraw_fee` is computed via `get_fee` in `token_receiver.rs:89` and stored in `BTCPendingInfo`. Later, `verify_withdraw_burn_promise` in `burn.rs:14-16` calls `get_protocol_and_relayer_fee(btc_pending_info.withdraw_fee)` — again a second division on an already-truncated value.

The mathematically correct single-step protocol fee would be:

```
protocol_fee_correct = amount * fee_rate * protocol_fee_rate / (MAX_RATIO * MAX_RATIO)
```

The actual two-step result is:

```
deposit_fee  = floor(amount * fee_rate / MAX_RATIO)          // loses up to MAX_RATIO-1
protocol_fee = floor(deposit_fee * protocol_fee_rate / MAX_RATIO)  // loses up to MAX_RATIO-1 again
```

The intermediate truncation in step 1 reduces the base passed to step 2, so `protocol_fee` is always `≤` the single-step value. The deficit (up to 1 satoshi per division) is silently absorbed into `relayer_fee = deposit_fee - protocol_fee`, meaning the relayer consistently receives more than the configured share.

### Impact Explanation
On every fee-bearing deposit and withdrawal the protocol treasury (`cur_available_protocol_fee`) receives up to 1 satoshi less than the configured `protocol_fee_rate` fraction of the total fee. The relayer receives the corresponding surplus. Over a high volume of transactions this constitutes a persistent, compounding accounting invariant violation: the on-chain protocol fee balance diverges from what the configured rate implies. No funds are lost from users; the discrepancy is entirely between the protocol treasury and the relayer.

This is a **Low** severity finding: a publicly reachable invariant violation in a production bridge fee path without direct theft.

### Likelihood Explanation
The bug is triggered unconditionally on every deposit and withdrawal where `fee_rate > 0` and `protocol_fee_rate > 0` and the ratio-based fee exceeds `fee_min`. No attacker action is required; any ordinary bridge user depositing or withdrawing nBTC triggers it.

### Recommendation
Combine the two divisions into a single expression so only one truncation occurs:

```rust
pub fn get_protocol_fee_from_amount(&self, amount: u128) -> (u128, u128, u128) {
    let total_fee = std::cmp::max(
        amount * u128::from(self.fee_rate) / u128::from(MAX_RATIO),
        self.fee_min,
    );
    // Single combined division avoids double truncation
    let protocol_fee = amount
        * u128::from(self.fee_rate)
        * u128::from(self.protocol_fee_rate)
        / (u128::from(MAX_RATIO) * u128::from(MAX_RATIO));
    let relayer_fee = total_fee - protocol_fee;
    (total_fee, protocol_fee, relayer_fee)
}
```

When `fee_min` is active (flat fee), the second division is unavoidable, but the combined form still eliminates the first truncation from the base.

### Proof of Concept
Concrete example with `fee_rate = 1000`, `protocol_fee_rate = 9000`, `MAX_RATIO = 10000`, `amount = 500001`:

**Current (two divisions):**
- `deposit_fee = floor(500001 * 1000 / 10000) = floor(50000.1) = 50000`
- `protocol_fee = floor(50000 * 9000 / 10000) = floor(45000) = 45000`
- `relayer_fee = 50000 - 45000 = 5000`

**Correct (single combined division):**
- `protocol_fee = floor(500001 * 1000 * 9000 / (10000 * 10000)) = floor(45000.09) = 45000`

In this case the result is the same, but with `amount = 500009`:
- `deposit_fee = floor(500009 * 1000 / 10000) = floor(50000.9) = 50000` ← truncated
- `protocol_fee = floor(50000 * 9000 / 10000) = 45000`
- Correct: `floor(500009 * 1000 * 9000 / 100000000) = floor(45000.81) = 45000`

With `amount = 500100`:
- `deposit_fee = floor(500100 * 1000 / 10000) = 50010`
- `protocol_fee = floor(50010 * 9000 / 10000) = floor(45009) = 45009`
- Correct: `floor(500100 * 9000000 / 100000000) = floor(45009) = 45009`
