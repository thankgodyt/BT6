### Title
DAO Rejection of Executed Refund Is Bypassed Due to Stale `BTCPendingInfo` — (File: `contracts/satoshi-bridge/src/refund.rs`)

### Summary
When `reject_refund` is called by DAO/Operator after `execute_refund` has already created a `BTCPendingInfo`, the rejection only removes the `RefundRequest` from storage but leaves the `BTCPendingInfo` intact. The user (or anyone) can still call `sign_btc_transaction` on the stale entry, obtain an MPC signature, broadcast the refund transaction to Bitcoin, and have a trusted relayer finalize it via `verify_refund_finalize`. The DAO's rejection is completely ineffective once `execute_refund` has been called.

### Finding Description

`internal_reject_refund` in `contracts/satoshi-bridge/src/refund.rs` removes only the `RefundRequest` from `refund_requests`:

```rust
pub(crate) fn internal_reject_refund(&mut self, utxo_storage_key: String) {
    require!(
        self.data_mut()
            .refund_requests
            .remove(&utxo_storage_key)
            .is_some(),
        "Refund request not found"
    );
    Event::RefundRejected { utxo_storage_key }.emit();
}
``` [1](#0-0) 

It does **not** remove or invalidate any `BTCPendingInfo` entries that were created by a prior `execute_refund` call. `finalize_refund_with_psbt` inserts a `BTCPendingInfo` into `btc_pending_infos` and adds the `btc_pending_id` to the account's `btc_pending_sign_ids`: [2](#0-1) 

`sign_btc_transaction` has no check that the underlying `RefundRequest` still exists — it only asserts the pending info is in `PendingSign` stage and dispatches to MPC: [3](#0-2) 

`verify_refund_finalize_callback` explicitly treats a missing `RefundRequest` as a harmless no-op and proceeds to clean up the `BTCPendingInfo` and finalize:

```rust
// If it was already removed, this is harmlessly a no-op.
self.data_mut().refund_requests.remove(&utxo_storage_keys[0]);
self.internal_remove_btc_pending_info(&tx_id);
``` [4](#0-3) 

The `reject_refund` public entry point explicitly allows DAO/Operator to reject an executed refund (the `executed` flag check is there precisely to gate the permissionless path, not to block privileged rejection): [5](#0-4) 

### Impact Explanation

The DAO's rejection of a refund is a bridge authorization control. After `execute_refund` is called, `reject_refund` is supposed to be the DAO's last line of defense (e.g., to block a refund to a suspicious or sanctioned address, or to cancel a refund that was executed in error). Because `internal_reject_refund` leaves the `BTCPendingInfo` alive, the user can:

1. Call `sign_btc_transaction` on the stale entry — MPC signs the transaction.
2. Broadcast the signed transaction to Bitcoin — it confirms on-chain.
3. A trusted relayer calls `verify_refund_finalize` — the callback treats the missing `RefundRequest` as a no-op and finalizes successfully.

The DAO's rejection is completely bypassed. This is a bypass of bridge authorization controls with real security impact (e.g., funds sent to a sanctioned address, or a refund completed that the protocol intended to block).

**Allowed impact matched:** *Bypass of bridge verification, authorization, migration, or upgrade controls with real security impact* (Critical); or at minimum *Bypass of bridge limits or policies* (Medium).

### Likelihood Explanation

The scenario requires the DAO to call `reject_refund` after `execute_refund` has already been called. This is a realistic operational scenario: the DAO may discover a problem with the refund address or the request after the user has already executed it. The code explicitly supports DAO rejection of executed refunds (the `executed` flag check in `reject_refund` is designed for this case), so the DAO would reasonably believe the rejection is effective. The user's subsequent steps (`sign_btc_transaction`, broadcast, relayer finalization) are all normal bridge operations with no additional privilege required.

### Recommendation

`internal_reject_refund` must also invalidate all `BTCPendingInfo` entries associated with the rejected UTXO. Concretely, when rejecting an executed refund request, the function should:

1. Enumerate all `BTCPendingInfo` entries whose PSBT spends the rejected UTXO (or track them explicitly in the `RefundRequest`).
2. Remove each such entry from `btc_pending_infos` and from the owning account's `btc_pending_sign_ids` / `btc_pending_verify_list`.
3. Remove the UTXO from `verified_deposit_utxo` if the only reason it was inserted was the now-rejected `execute_refund`.

Alternatively, `sign_btc_transaction` and `verify_refund_finalize` should check that the underlying `RefundRequest` still exists (and has not been rejected) before proceeding for `Refund`-state pending infos.

### Proof of Concept

1. User calls `request_refund` → `RefundRequest` stored with `executed = false`.
2. User calls `execute_refund` → `BTCPendingInfo` created in `btc_pending_infos`, `RefundRequest.executed` set to `true`, UTXO inserted into `verified_deposit_utxo`.
3. DAO calls `reject_refund` → `RefundRequest` removed from `refund_requests`. **`BTCPendingInfo` remains.**
4. User (or anyone) calls `sign_btc_transaction(btc_pending_id, 0, key_version)` → `sign_btc_transaction` finds the `BTCPendingInfo`, asserts `PendingSign` stage, dispatches MPC signing. No check that `RefundRequest` exists. MPC returns signature.
5. `sign_btc_transaction_callback` stores the signature, transitions state to `PendingVerify`, moves id to `btc_pending_verify_list`.
6. User broadcasts the signed transaction to Bitcoin. It confirms.
7. Trusted relayer calls `verify_refund_finalize(tx_id, proof)` → `verify_refund_finalize_callback` runs: `refund_requests.remove(...)` is a no-op (already gone), `BTCPendingInfo` is removed, returns `true`.
8. Refund is complete. DAO rejection was ineffective.

    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
