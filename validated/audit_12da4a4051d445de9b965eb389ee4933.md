Looking at the bridge's withdrawal lifecycle, I need to map the "signer cannot cancel their signature before a deadline" vulnerability class to this codebase.

**Key observations:**

1. When a user initiates a withdrawal via `ft_on_transfer`, their nBTC is transferred to the bridge and a `BTCPendingInfo` is created in `PendingSign` stage — the user's funds are now locked.

2. `withdraw_rbf` is the only user-facing function for pending withdrawals, but it enforces the same target address and output count as the original transaction — it cannot redirect funds back to the user.

3. `cancel_withdraw` is gated behind `#[access_control_any(roles(Role::DAO, Role::Operator))]` and additionally requires `max_btc_tx_pending_sec` to have elapsed (default 24 hours).

4. There is no user-facing cancel/invalidate function analogous to `useNonce()`.

---

### Title
User Cannot Self-Cancel a Pending Withdrawal Before On-Chain Verification — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary
Once a user initiates a withdrawal via `ft_on_transfer`, their nBTC is locked in the bridge and a `BTCPendingInfo` is created. The user has no mechanism to cancel this pending withdrawal themselves. Only DAO/Operator can cancel via `cancel_withdraw`, and only after `max_btc_tx_pending_sec` (default 24 hours) has elapsed. This is the direct analog of the external report's "signer cannot cancel their signature before a deadline" vulnerability.

### Finding Description
When a user calls `nbtc.ft_transfer_call(bridge, amount, WithdrawMsg)`, the bridge's `ft_on_transfer` handler calls `create_btc_pending_info`, which locks the nBTC in the bridge and creates a `BTCPendingInfo` with state `WithdrawOriginal(PendingSign)`. [1](#0-0) 

From this point, the user has no way to cancel the withdrawal:

**`withdraw_rbf` (user-facing, no role restriction)** — This is the only public function a user can call on their own pending withdrawal. However, `internal_withdraw_rbf` enforces `assert_withdraw_original_pending_verify_tx()` (requires `PendingVerify` stage, i.e., already MPC-signed), and `check_withdraw_rbf_psbt_valid` re-validates the same target address extracted from the original transaction — the user cannot redirect funds to themselves. [2](#0-1) [3](#0-2) 

**`cancel_withdraw` (DAO/Operator only)** — Gated behind `#[access_control_any(roles(Role::DAO, Role::Operator))]` and additionally requires that `block_timestamp - create_time_sec > max_btc_tx_pending_sec` (default 24 hours), meaning even privileged roles cannot cancel immediately. [4](#0-3) [5](#0-4) 

There is no user-facing cancel function analogous to `useNonce()` from the external report's fix.

### Impact Explanation
A user who initiates a withdrawal to a wrong address, or who changes their mind for any reason, has no self-service recourse. Their nBTC remains locked in the bridge until either:
- The withdrawal is verified on-chain (nBTC burned, BTC received at the original — possibly wrong — address), or
- DAO/Operator cancels it via `cancel_withdraw` after the 24-hour wait.

This constitutes a **stuck bridge state requiring operator intervention**, matching the allowed Medium impact category. The 24-hour mandatory wait before even the operator can act amplifies the severity.

### Likelihood Explanation
Medium. Withdrawal mistakes (wrong BTC address, wrong amount, changed market conditions) are realistic user scenarios. The `ft_on_transfer` path is the primary user-facing bridge entry point and is callable by any nBTC holder. No special conditions are required to reach the stuck state — a single normal withdrawal initiation suffices.

### Recommendation
Add a user-facing self-cancel function, callable only by the withdrawal's `account_id`, that allows the user to initiate a `WithdrawCancelRbf` RBF transaction redirecting all funds back to the bridge's change address (and subsequently returning nBTC to the user via the existing `lost_found` / `claim_lost_found` mechanism). This is the direct analog of the `useNonce()` fix: give the initiator a way to invalidate their own pending action without requiring privileged operator intervention.

### Proof of Concept
1. User calls `nbtc.ft_transfer_call(bridge, 200_000, WithdrawMsg { target_btc_address: "wrong_address", ... })`.
2. Bridge `ft_on_transfer` → `create_btc_pending_info` locks nBTC in bridge; `BTCPendingInfo` created in `PendingSign` stage.
3. User realizes the target address is wrong and wants to cancel.
4. User calls `withdraw_rbf` → reverts: `assert_withdraw_original_pending_verify_tx` fails because the tx is still in `PendingSign` (not yet MPC-signed).
5. Even after MPC signing moves it to `PendingVerify`, `withdraw_rbf` enforces the same wrong target address — cancellation is still impossible.
6. User has no other callable function. Must contact DAO/Operator.
7. DAO/Operator calls `cancel_withdraw` — but only after 24 hours (`max_btc_tx_pending_sec`).
8. Until then, user's nBTC is stuck in the bridge with no self-service exit. [6](#0-5) [7](#0-6)

        original_tx_btc_pending_info: &BTCPendingInfo,
        withdraw_rbf_psbt: &PsbtWrapper,
    ) -> (u128, u128) {

            &original_tx_btc_pending_info.vutxos,
            original_tx_btc_pending_info.transfer_amount,
            original_tx_btc_pending_info.withdraw_fee,
