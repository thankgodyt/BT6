### Title
Unregistered Token Transfer Permanently Locks User Funds in NEAR Bridge - (File: `near/omni-bridge/src/lib.rs`)

### Summary
The `init_transfer` function in the NEAR bridge contract accepts any NEAR token without verifying that it has been registered (i.e., has `token_decimals` set and a corresponding address on the destination chain via `bind_token` or `deploy_token`). A user who initiates a transfer with an unregistered token will have their funds permanently locked in the bridge, because the subsequent `sign_transfer` call will always panic with `ERR_FAILED_TO_GET_TOKEN_ADDRESS` or `ERR_TOKEN_DECIMALS_NOT_FOUND`, and no user-accessible cancellation path exists.

### Finding Description

`init_transfer` (the private function called from `ft_on_transfer`) performs only two checks before storing the transfer message and keeping the user's tokens: [1](#0-0) 

There is no check that the token has been registered via `bind_token` or `deploy_token`. The transfer message is stored in `pending_transfers` and the tokens are retained by the bridge (the function returns `U128(0)` to the NEP-141 callback, meaning zero tokens are refunded).

When a relayer later calls `sign_transfer` to complete the outbound leg, it unconditionally requires both a registered destination-chain address and a `token_decimals` entry: [2](#0-1) 

Both lookups panic if the token was never registered. Because there is no public `cancel_transfer` or user-accessible refund function, the transfer message stays in `pending_transfers` forever and the locked tokens cannot be recovered by the user.

The same pattern exists on the inbound (EVM → NEAR) path: `fin_transfer_callback` also requires `token_decimals` to be present: [3](#0-2) 

The only recovery path is the DAO-gated `transfer_token_as_dao`, which requires privileged intervention. [4](#0-3) 

### Impact Explanation

Any user who calls `ft_transfer_call` on a NEAR token that has not been registered with the bridge will have their tokens permanently locked in the bridge contract. `sign_transfer` will always revert for that transfer ID, and no user-level escape hatch exists. This constitutes permanent freezing of bridged funds, matching the "Critical" impact tier.
