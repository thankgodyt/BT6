Audit Report

## Title
Trusted-Relayer Gate on `claim_fee` Permanently Freezes Earned Fee Tokens When Relayer Status Changes — (`near/omni-bridge/src/lib.rs`)

## Summary

`claim_fee` is decorated with `#[trusted_relayer]`, which rejects any caller not currently in the active trusted-relayer set. Simultaneously, `claim_fee_callback` enforces that only the `fee_recipient` embedded in the destination-chain proof can collect the fee. If a relayer resigns or is revoked after executing a fast transfer to a non-NEAR chain but before submitting the destination-chain proof, neither the original relayer nor any substitute can ever call `claim_fee` for that transfer. The fee tokens and the `pending_transfers` entry are permanently frozen with no permissionless recovery path.

## Finding Description

Two independent restrictions in `claim_fee` and `claim_fee_callback` create an irrecoverable dead-end:

**Restriction 1** — `claim_fee` carries `#[trusted_relayer]` (imported from `omni_utils::macros::trusted_relayer`), which rejects any caller not presently in the active relayer set: [1](#0-0) 

**Restriction 2** — `claim_fee_callback` enforces `fee_recipient == predecessor_account_id`, where `fee_recipient` is cryptographically bound in the destination-chain event proof. No substitute account can satisfy this check: [2](#0-1) 

When a trusted relayer executes a fast transfer to a non-NEAR chain, `fast_fin_transfer_to_other_chain` burns/locks the principal and stores a second-leg `TransferMessage` in `pending_transfers` with the fee still accounted for inside the bridge: [3](#0-2) 

The fee is only released when `claim_fee_callback` calls `send_fee_internal`. If the relayer's trusted status is removed before the proof is submitted, neither restriction can be satisfied simultaneously by any account. The `pending_transfers` entry also persists indefinitely as a storage leak.

The integration test confirms that `resign_trusted_relayer` immediately removes trusted status and returns stake, with no grace period for pending fee claims: [4](#0-3) 

## Impact Explanation

Fee tokens earned by a relayer for executing a fast transfer to a non-NEAR destination chain are permanently frozen in the bridge contract. The `pending_transfers` entry for the second leg is never removed. The only escape is DAO intervention via `transfer_token_as_dao`, which is an out-of-band privileged action and does not restore the fee to the rightful relayer. This constitutes **fee mis-accounting and permanent freezing of bridged funds**, matching the allowed Critical impact scope.

## Likelihood Explanation

Low. The window requires a relayer to resign or be revoked after submitting a fast transfer but before the destination-chain proof is finalized and submitted. The window is narrow for fast chains but realistic for chains with longer finality (e.g., Ethereum mainnet). The DAO-revocation path (revoking a misbehaving relayer who has pending fee claims) is a plausible operational scenario that does not require any victim mistake.

## Recommendation

Remove the `#[trusted_relayer]` gate from `claim_fee`. The `fee_recipient == predecessor_account_id` check in `claim_fee_callback` already ensures only the correct party can collect the fee; the additional trusted-relayer check adds no security benefit and creates the described dead-end. The fee was earned at the time the fast transfer was executed, and the relayer's current status is irrelevant to their right to collect it.

## Proof of Concept

1. Relayer A becomes a trusted relayer (stake deposited, waiting period elapsed).
2. Relayer A calls `ft_transfer_call` with a `FastFinTransferMsg` targeting a Base-chain recipient. `fast_fin_transfer_to_other_chain` burns the principal, stores a second-leg `TransferMessage` in `pending_transfers` with `origin_transfer_id = Some(fast_transfer_id)`, and records `FastTransferStatus { relayer: RelayerA, finalised: false }`.
3. A regular relayer calls `sign_transfer` on the second-leg transfer. Because `fee > 0`, the `TransferMessage` remains in `pending_transfers` after signing.
4. Relayer A calls `resign_trusted_relayer`. Stake is returned; Relayer A is removed from the trusted set.
5. The signed payload is submitted to Base. Base emits `FinTransfer` with `fee_recipient = RelayerA`.
6. Relayer A attempts `claim_fee` with the Base proof → **panics at `#[trusted_relayer]`** because Relayer A is no longer active.
7. Any other trusted relayer attempts `claim_fee` with the same proof → **panics at `OnlyFeeRecipientCanClaim`** because `fee_recipient (RelayerA) != predecessor_account_id`.
8. The fee tokens and the `pending_transfers` entry are permanently stuck. No permissionless path exists to recover them. [1](#0-0) [2](#0-1) [5](#0-4)
