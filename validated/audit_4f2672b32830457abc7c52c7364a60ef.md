### Title
`safe_mint` Mints Tokens to Bridge Balance Instead of User, Silently Returns Zero for Unregistered Accounts - (File: `contracts/nbtc/src/lib.rs`)

### Summary

`safe_mint` in the nBTC token contract unconditionally mints `amount` tokens into the bridge contract's own balance (`bridge_id`) before checking whether the recipient account is registered. If the recipient is not registered, the function silently returns `U128(0)` without transferring any tokens to the user. The minted tokens remain permanently in the bridge's balance, inflating total supply without backing, while the user receives nothing.

### Finding Description

In `contracts/nbtc/src/lib.rs`, the `safe_mint` function follows this sequence:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into()); // (1) mints to bridge's own balance

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0)); // (2) silently returns 0 — tokens already minted, never transferred
    }

    if let Some(msg) = msg {
        self.ft_transfer_call(account_id, amount, None, msg)
    } else {
        self.ft_transfer(account_id, amount, None); // (3) only reached if account IS registered
        PromiseOrValue::Value(amount)
    }
}
```

Step (1) calls `internal_deposit(&self.bridge_id, amount)`, which immediately and irrevocably increases the bridge's nBTC balance and the total supply. Step (2) then checks whether `account_id` is registered — but this check comes **after** the mint. If the account is unregistered, the function returns `U128(0)` without ever calling `ft_transfer`. The `amount` tokens are now permanently held in the bridge's balance with no code path to route them to the user.

This is the direct analog of the Flan `safeTransfer` bug: instead of checking the correct account's state before acting, the function performs the critical state mutation (minting to the contract's own balance) first, then silently short-circuits when the intended recipient cannot receive tokens. [1](#0-0) 

### Impact Explanation

**Supply/accounting failure and permanent token lock.** In NEAR, cross-contract calls are not atomic. The `internal_deposit(&self.bridge_id, amount)` executes and is committed in the `safe_mint` transaction. Even if the bridge's callback subsequently panics (treating `U128(0)` as a failure), the state change inside `safe_mint` is **not** rolled back — only the callback's own state changes revert. The result:

- Total nBTC supply is inflated by `amount` with no corresponding user balance.
- The minted tokens are stranded in the bridge's balance with no recovery path for the user.
- `CLAUDE.md` documents the safe-deposit flow as "reverts the whole transaction if minting fails (no lost & found)" — but the revert of the bridge callback cannot undo the already-committed `internal_deposit` in the nbtc contract.
- If the bridge callback does **not** treat `U128(0)` as a failure (interprets it as "0 tokens transferred, success"), the deposit UTXO is marked verified, the user's BTC is permanently locked in the bridge's UTXO set, and the user receives 0 nBTC.

This matches the **Medium** impact class: permanent burning below backed supply / broken callback rollback causing stuck bridge state, and potentially **Critical** (significant loss of user funds) depending on how the bridge callback handles the zero return. [2](#0-1) [3](#0-2) 

### Likelihood Explanation

The safe-deposit path (`safe_verify_deposit` / `verify_deposit_v2` with `deposit_msg.safe_deposit = Some(..)`) is the documented flow for Omni Bridge integrations. Any user whose NEAR account has not called `storage_deposit` on the nBTC contract before initiating a BTC deposit will trigger this path. This is a realistic scenario for first-time bridge users or accounts created specifically for a deposit. No special privileges are required — the attacker-controlled input is simply the `deposit_msg.account_id` field pointing to an unregistered account. [4](#0-3) [5](#0-4) 

### Recommendation

Reverse the order of operations: check whether `account_id` is registered **before** calling `internal_deposit`. If the account is not registered, either panic (reverting the entire call) or register the account automatically before minting.

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "safe_mint: account_id must not be the bridge");

    // Check BEFORE minting
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0)); // no tokens minted yet — safe to return
    }

    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ... proceed with transfer
}
```

Alternatively, panic on unregistered accounts so the bridge callback can detect the failure and the entire cross-contract sequence is cleanly aborted.

### Proof of Concept

1. User Alice deposits BTC to the bridge using the safe-deposit flow, with her NEAR account `alice.near` as the recipient.
2. `alice.near` has never called `storage_deposit` on the nBTC contract and is therefore unregistered.
3. The bridge's deposit verification succeeds and calls `nbtc.safe_mint("alice.near", 100000, None)`.
4. Inside `safe_mint`: `internal_deposit(&bridge_id, 100000)` executes — bridge's nBTC balance increases by 100000, total supply increases by 100000.
5. `self.token.accounts.get(&"alice.near")` returns `None`.
6. `safe_mint` returns `U128(0)` without calling `ft_transfer`.
7. Alice's nBTC balance: 0. Bridge's nBTC balance: +100000. Total supply: +100000 (unbacked).
8. Alice's BTC is locked in the bridge's UTXO set. She has no nBTC and no recovery path. [6](#0-5)
