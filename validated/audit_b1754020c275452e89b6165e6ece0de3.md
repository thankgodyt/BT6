### Title
`PBftSignatureThreshold` Stored as `Double` Causes Imprecise `floor`-Based Block-Acceptance Threshold — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Protocol/PBFT.hs`)

---

### Summary

The PBFT signature-window threshold is stored as a `Double` and converted to an integer count via `floor`. Because IEEE 754 `Double` cannot represent all rational values exactly, the computed integer threshold can be one less than the mathematically intended value for certain `(t, k)` pairs. When the threshold is one too low, a PBFT core node is permitted to sign one more block in the window than the protocol allows, bypassing the signature-frequency check that is the sole PBFT safety guard against a single key dominating the chain. The codebase itself acknowledges the problem: the test helper adds an explicit `epsilon = 1/10000` to "avoid problematic floating point round-off," a workaround that is absent from the production path.

---

### Finding Description

`PBftSignatureThreshold` wraps a `Double`: [1](#0-0) 

The effective integer threshold is derived in `pbftWindowParams` by multiplying the `Double` by the window size and applying `floor`: [2](#0-1) 

That integer is then the sole comparand in `pbftWindowExceedsThreshold`, which decides whether `updateChainDepState` accepts or rejects a block: [3](#0-2) [4](#0-3) 

The problem is that `Double` cannot represent many rationals exactly. For instance, `0.3` in IEEE 754 is `0.2999999999999999888…`, so `floor(0.3 × 10) = floor(2.9999…) = 2` instead of the intended `3`. Depending on the direction of the rounding error for a given `(t, k)` pair:

- **Threshold too low** (`floor` rounds down when the exact product is an integer): the check passes for `numSigned = threshold + 1`, i.e., one extra block per window is silently accepted.
- **Threshold too high** (`floor` rounds up when the exact product is just below an integer): a legitimately-within-budget block is rejected.

The test infrastructure explicitly patches around this with a magic constant: [5](#0-4) 

No equivalent guard exists in the production `byronPBftParams` / `defaultPBftSignatureThreshold` path: [6](#0-5) [7](#0-6) 

---

### Impact Explanation

The PBFT signature-window check is the only mechanism preventing a single genesis-key delegate from signing an unbounded fraction of blocks in the Byron era. If `floor(t × k)` is computed one lower than the exact mathematical value, the enforced limit is `t_effective = (floor(t × k) - 1) / k` instead of `floor(t × k) / k`. A core node aware of this discrepancy can sign exactly `floor(t × k)` blocks in the window — one more than the operator intended — and every honest node will accept those blocks because `numSigned (= floor(t×k)) > threshold (= floor(t×k) - 1)` is false, so no `PBftExceededSignThreshold` error is raised. Over many windows this shifts the effective safety bound below the specification's required interval `[1/5, 1/4]`, weakening the PBFT safety guarantee against a single-key chain takeover.

**Impact: Medium** — bypass of the PBFT per-key signing-frequency check; maps to "bypass of PBFT voting or certificate checks that enables unauthorized block acceptance."

---

### Likelihood Explanation

The off-by-one manifests only when `t × k` is extremely close to an integer and the `Double` rounding goes in the permissive direction. For the hardcoded production value `t = 0.22`, `k = 2160`, the product is `475.2`, well away from an integer boundary, so the default deployment is not currently affected. However, any operator or private-testnet deployment that chooses a threshold whose `Double` representation times `k` lands just below an integer (e.g., `t = 0.3`, `k = 10`) will silently get a weaker threshold. The test code's explicit `epsilon` workaround confirms the developers have already encountered this failure mode.

**Likelihood: 3/10** — not triggered by the mainnet default, but reachable on any private-testnet or alternative Byron deployment with a different `(t, k)` pair, without any special key material beyond holding a PBFT genesis-delegate key.

---

### Recommendation

Replace `Double` with `Rational` for `PBftSignatureThreshold`:

```haskell
newtype PBftSignatureThreshold = PBftSignatureThreshold
  { getPBftSignatureThreshold :: Rational   -- was: Double
  }
```

Update `pbftWindowParams` to use exact rational arithmetic before the final `floor`:

```haskell
threshold =
    floor $
      getPBftSignatureThreshold pbftSignatureThreshold * fromIntegral winSize
      -- 'floor' on Rational is exact; no floating-point rounding
```

This eliminates the need for the ad-hoc `epsilon = 1/10000` workaround in the test helper and makes the threshold computation deterministic and exact for all `(t, k)` pairs, consistent with how `PerasQuorumStakeThreshold` and `PerasQuorumStakeThresholdSafetyMargin` are already typed as `Rational` in the Peras parameters. [8](#0-7)

### Proof of Concept

Concrete counter-example showing the off-by-one:

```
t  = 0.3   (Double representation: 0.2999999999999999888…)
k  = 10    (window size)

Exact:   floor(3/10 × 10) = floor(3.0)   = 3
Double:  floor(0.2999… × 10) = floor(2.9999…) = 2   ← threshold is 2, not 3
```

With `threshold = 2`, `pbftWindowExceedsThreshold` passes for `numSigned = 3` (since `3 > 2` is true, the block is rejected — this is the "too restrictive" direction). Conversely, for a value where the `Double` rounds up:

```
t  = 1/3 + ε_double   (Double rounds 1/3 upward to 0.3333333333333333703…)
k  = 3

Exact:   floor(1/3 × 3) = floor(1.0)   = 1
Double:  floor(0.3333…703 × 3) = floor(1.0000…109) = 1   ← same here
```

But for:
```
t  = 0.1 + tiny_negative_ulp   (operator intends floor(0.1 × 30) = 3)
k  = 30

If Double gives 0.09999… × 30 = 2.9999… → floor = 2
Threshold is 2 instead of 3: a node signing 3 blocks is incorrectly rejected.
```

The test-library workaround at line 36 of `Test/ThreadNet/Infra/Byron/Genesis.hs` is direct evidence that this failure mode was encountered and patched locally rather than fixed at the type level. [9](#0-8)
