Audit Report

## Title
`fin_transfer_send_tokens_callback` Silently Treats Failed Token Delivery as Success, Permanently Locking Bridged Funds - (File: `near/omni-bridge/src/lib.rs`)

## Summary

`process_fin_transfer_to_near` inserts the transfer ID into `finalised_transfers` before the token delivery promise resolves. If the subsequent `ft_transfer` or `near_withdraw` call fails, `fin_transfer_send_tokens_callback` — which carries no `#[callback_result]` parameter — delegates entirely to `is_refund_required(false)`, which unconditionally returns `false` for all non-`ft_transfer_call` paths without ever reading the promise result. The callback then emits `FinTransferEvent` as success, pays the relayer fee, and leaves the tokens permanently locked in the bridge with no recovery path.

## Finding Description

**Step 1 — Permanent replay-prevention entry written before delivery:**
`process_fin_transfer_to_near` calls `add_fin_transfer` at line 1875, inserting the transfer ID into `finalised_transfers` before `send_tokens` is dispatched. Any subsequent call to `fin_transfer` with the same proof panics with `TransferAlreadyFinalised`.

**Step 2 — `send_tokens` dispatches the delivery promise:**
For non-deployed tokens with an empty `msg`, `send_tokens` dispatches `ft_transfer` (lines 2102–2106). For wNEAR with an empty `msg`, it dispatches `near_withdraw` chained with `near_withdraw_callback` (lines 2071–2081). In both cases `is_ft_transfer_call` is set to `!msg.is_empty()` = `false` (line 1973).

**Step 3 — Callback has no promise-result inspection:**
`fin_transfer_send_tokens_callback` (lines 1692–1699) has no `#[callback_result]` parameter. It calls `Self::is_refund_required(is_ft_transfer_call)`.

**Step 4 — `is_refund_required` unconditionally returns `false` for non-`ft_transfer_call` paths:**
```rust
} else {
    // Not ft_transfer_call: don't refund
    false
}
```
(lines 1800–1803). The promise result is never read.

**Step 5 — Success branch executes regardless of delivery outcome:**
With `is_refund_required` returning `false`, the callback takes the `else` branch (lines 1719–1746): it pays the relayer fee and emits `FinTransferEvent`. `remove_fin_transfer` is never called.

**wNEAR compounding factor:** When `near_withdraw` fails, `near_withdraw_callback` calls `env::panic_str` (line 1050), making the promise result for `fin_transfer_send_tokens_callback` an error. But since `is_ft_transfer_call = false` for wNEAR, `is_refund_required` still returns `false` and the callback still emits success.

**`resolve_utxo_fin_transfer` has the identical flaw** (lines 1016–1044): it calls `is_refund_required(is_ft_transfer_call)` with the same logic, so UTXO-chain inbound transfers with empty `msg` are equally affected.

## Impact Explanation

This is a **Critical** impact matching "permanent freezing of bridged funds." For any inbound transfer to a NEAR recipient where token delivery fails:
- The transfer ID is permanently in `finalised_transfers`, blocking any replay or re-finalization.
- For non-deployed tokens (USDC, USDT, etc.): the tokens remain locked in the bridge contract with no admin recovery function.
- For wNEAR: the wNEAR remains locked in the bridge contract.
- The relayer fee is paid despite the recipient receiving nothing.
- The user's source-chain funds are already committed; they are irrecoverably lost.

## Likelihood Explanation

**Medium.** No privileged access is required. Realistic triggers include:
- **USDC/USDT recipient blacklisting**: Circle and Tether can blacklist NEAR addresses. A recipient blacklisted after a cross-chain transfer is initiated but before `fin_transfer` executes on NEAR causes `ft_transfer` to revert.
- **Token contract global pause**: USDC, USDT, and other regulated tokens have pause mechanisms. Any in-flight transfer during a pause window is permanently lost.
- **wNEAR contract failure**: Any failure in `near_withdraw` (contract paused, insufficient balance) permanently locks wNEAR.

All triggers are caused by external token contract behavior outside the bridge's control, and any relayer can submit the finalizing proof.

## Recommendation

1. Add a `#[callback_result] call_result: Result<(), near_sdk::PromiseError>` parameter to `fin_transfer_send_tokens_callback` to capture the promise outcome for all delivery paths.
2. Extend `is_refund_required` (or replace it) to return `true` whenever the promise result is `Err(_)`, regardless of `is_ft_transfer_call`. For the `ft_transfer` and `near_withdraw` paths, a failed promise should always trigger the refund/revert branch.
3. In the refund branch, call `remove_fin_transfer` to allow the transfer to be re-submitted, or emit a `FailedFinTransferEvent` and provide a separate admin/user-triggered retry mechanism.
4. Apply the same fix to `resolve_utxo_fin_transfer` (lines 1016–1044).

## Proof of Concept

**Scenario: USDC recipient is blacklisted**

1. User initiates transfer of 10,000 USDC from Ethereum to `alice.near` via the EVM bridge contract. Source-chain funds are locked.
2. A relayer submits the proof to `fin_transfer` on NEAR.
3. `fin_transfer_callback` → `process_fin_transfer_to_near`:
   - `add_fin_transfer` inserts the transfer ID into `finalised_transfers` (line 1875).
   - `send_tokens` dispatches `ft_transfer(alice.near, 10000 USDC)` (lines 2102–2106).
   - `.then(fin_transfer_send_tokens_callback(..., is_ft_transfer_call=false, ...))` is registered (lines 1967–1977).
4. The USDC contract rejects the transfer because `alice.near` is blacklisted. The `ft_transfer` promise fails.
5. `fin_transfer_send_tokens_callback` executes. `is_refund_required(false)` returns `false` (lines 1800–1803) without reading the promise result.
6. The `else` branch executes: relayer fee is paid, `FinTransferEvent` is emitted (lines 1719–1745).
7. Any subsequent `fin_transfer` call with the same proof panics with `TransferAlreadyFinalised` (line 2229–2230).
8. 10,000 USDC is permanently locked in the bridge contract. `alice.near` receives nothing.

**Minimal test plan:** Deploy a mock USDC token contract that rejects `ft_transfer` calls. Submit a valid inbound finalization proof targeting a blacklisted recipient. Assert that `FinTransferEvent` is emitted, the transfer ID is in `finalised_transfers`, and the USDC balance of the bridge contract is unchanged while the recipient balance is zero. Confirm that re-submitting the same proof panics with `TransferAlreadyFinalised`.
