Audit Report

## Title
Unchecked `ft_transfer` Promise Result in `is_refund_required` Causes Permanent Freezing of Bridged Funds — (File: `near/omni-bridge/src/lib.rs`)

## Summary

`is_refund_required` unconditionally returns `false` when `is_ft_transfer_call == false`, without inspecting the promise result. When a plain `ft_transfer` (dispatched for non-deployed tokens with an empty `msg`) fails, all three callbacks that rely on this function — `fin_transfer_send_tokens_callback`, `resolve_utxo_fin_transfer`, and `resolve_fast_transfer` — treat the failure as success. For the `fin_transfer_send_tokens_callback` path, this permanently finalizes the transfer while the recipient receives nothing, with no replay or recovery mechanism.

## Finding Description

**Root cause:** `is_refund_required` at L1800–1802 returns `false` unconditionally for the non-`ft_transfer_call` branch, never calling `env::promise_result_checked`:

```rust
} else {
    // Not ft_transfer_call: don't refund
    false
}
```

**Trigger path for `fin_transfer_send_tokens_callback`:**

1. `process_fin_transfer_to_near` calls `add_fin_transfer` at L1875, permanently recording the transfer ID in `finalised_transfers` before any token send occurs.
2. `unlock_tokens_if_needed` is called at L1881–1885, decrementing `locked_tokens` for the origin chain.
3. `send_tokens` at L2102–2106 dispatches a plain `ft_transfer` (not `ft_transfer_call`) when `msg.is_empty()` and the token is non-deployed.
4. The callback is registered at L1970–1976 with `is_ft_transfer_call = !msg.is_empty()` — which is `false` for empty `msg`.
5. If the `ft_transfer` promise fails, `fin_transfer_send_tokens_callback` at L1702 calls `is_refund_required(false)`, which returns `false`.
6. The `else` branch at L1719 executes: fee is paid to the relayer, `FinTransferEvent` is emitted. `revert_lock_actions` is never called.

**Result:** `finalised_transfers` contains the transfer ID (replay impossible), `locked_tokens` is permanently decremented, and the recipient receives 0 tokens.

**Same blind spot in `resolve_utxo_fin_transfer`** (L1024–1025): when `msg` is empty, `is_ft_transfer_call = false`, and a failed `ft_transfer` is silently treated as success, emitting `UtxoTransferEvent` without delivering tokens.

**Additional issue in `resolve_fast_transfer`** (L904, L906): `burn_tokens_if_needed` is called unconditionally before the refund check. When `is_ft_transfer_call == false` and `ft_transfer` fails, `is_refund_required(false)` returns `false`, the fast-transfer record is not removed, and the relayer's collateral is burned — a separate accounting loss.

## Impact Explanation

This is a **critical** escrow mis-accounting and permanent freezing of bridged funds. For every inbound EVM/Wormhole/MPC transfer to NEAR with an empty `msg` targeting a non-deployed (locked) NEP-141 token:

- The source-chain contract has already burned/locked the user's tokens.
- `finalised_transfers` records the transfer as complete — no replay is possible.
- `locked_tokens` is decremented — the accounting is permanently corrupted.
- The recipient receives nothing.
- There is no on-chain recovery path.

This matches the allowed critical impact: **permanent freezing of bridged funds** and **escrow mis-accounting**.

## Likelihood Explanation

`ft_transfer` can fail without any privileged action:

1. **Token contract paused by its own governance** — the bridge has no control over third-party NEP-141 contracts; a governance pause causes every in-flight `ft_transfer` to fail.
2. **Recipient account deleted or never created** — NEAR accounts can be deleted; if the recipient account no longer exists at settlement time, `ft_transfer` panics inside the token contract.
3. **Token contract upgrade introduces a panic** — a routine upgrade between proof submission and callback execution can cause `ft_transfer` to revert.

All three scenarios are reachable by an unprivileged external user or by normal protocol operation. No admin key compromise is required.

## Recommendation

`is_refund_required` must inspect the promise result for the non-`ft_transfer_call` path:

```rust
fn is_refund_required(is_ft_transfer_call: bool) -> bool {
    if is_ft_transfer_call {
        match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
            Ok(value) => {
                near_sdk::serde_json::from_slice::<U128>(&value)
                    .map_or(false, |amount| amount.0 == 0)
            }
            Err(_) => false,
        }
    } else {
        // ft_transfer: treat any promise failure as requiring a refund/revert
        env::promise_result_checked(0, 0).is_err()
    }
}
```

Additionally, in `resolve_fast_transfer`, `burn_tokens_if_needed` should only be called in the success branch (after confirming `!is_refund_required`), so a failed `ft_transfer` does not burn the relayer's collateral.

## Proof of Concept

1. Alice bridges 1,000 USDC from Ethereum to `alice.near` with empty `msg`. The EVM bridge contract locks 1,000 USDC.
2. A relayer submits the proof via `fin_transfer`. `process_fin_transfer_to_near` runs:
   - `add_fin_transfer` inserts the transfer ID into `finalised_transfers` (L1875).
   - `unlock_tokens_if_needed` decrements `locked_tokens[Eth][usdc]` by 1,000 (L1881–1885).
   - `send_tokens` dispatches `ft_transfer(alice.near, 1000)` to the USDC token contract (L2102–2106).
   - Callback registered with `is_ft_transfer_call = false` (L1973).
3. Before the callback, the USDC token contract is paused by its governance (or `alice.near` is deleted). The `ft_transfer` promise fails.
4. `fin_transfer_send_tokens_callback` is invoked. `is_refund_required(false)` returns `false` (L1800–1802). The `else` branch fires (L1719): relayer fee is minted, `FinTransferEvent` is emitted.
5. **Result:** `finalised_transfers` contains the transfer ID (no replay), `locked_tokens` is permanently decremented by 1,000, Alice receives 0 USDC. The 1,000 USDC remain locked on Ethereum with no recovery mechanism.

A unit test can reproduce this by mocking `env::promise_result_checked` to return `Err(PromiseError::Failed)` and asserting that `fin_transfer_send_tokens_callback` incorrectly emits `FinTransferEvent` instead of `FailedFinTransferEvent`.
