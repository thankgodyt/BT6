Audit Report

## Title
Race Condition in `fast_fin_transfer_to_near_callback` Allows Double-Spending of Bridged Funds — (File: near/omni-bridge/src/lib.rs)

## Summary
`fast_fin_transfer` checks `is_unified_transfer_finalised` before scheduling an async callback but does not atomically record the fast transfer in `fast_transfers`. A proof-based `fin_transfer` can execute in the inter-block window, find no fast-transfer record, and pay the recipient. When `fast_fin_transfer_to_near_callback` subsequently runs, it performs no re-check against `finalised_transfers` and calls `add_fast_transfer`, which only guards against the `fast_transfers` map, allowing a second payment to the same recipient.

## Finding Description

**Step 1 — `fast_fin_transfer` (Transaction 1):**
`is_unified_transfer_finalised` is checked at L778 and returns `false`. The function then schedules `check_or_pay_ft_storage → fast_fin_transfer_to_near_callback` as a promise chain. Critically, the fast transfer is **not** inserted into `fast_transfers` at this point; that insertion happens only inside the callback. [1](#0-0) [2](#0-1) 

**Step 2 — `fin_transfer` executes between the two transactions:**
`process_fin_transfer_to_near` calls `add_fin_transfer`, inserting the transfer ID into `finalised_transfers`. It then calls `get_fast_transfer_status`, which queries only the `fast_transfers` map. Because the callback has not yet run, the map has no entry, so `fast_transfer_status` is `None`. The `None` branch sends tokens directly to the original recipient. [3](#0-2) 

**Step 3 — `fast_fin_transfer_to_near_callback` (Transaction 2):**
The callback contains no call to `is_unified_transfer_finalised`. It calls `add_fast_transfer`, which only checks whether the `fast_transfers` map already contains the key. Since `fin_transfer` never wrote to `fast_transfers` (it only wrote to `finalised_transfers`), the `require!` passes, the entry is inserted, and `send_tokens` dispatches a second payment to the recipient. [4](#0-3) [5](#0-4) [6](#0-5) 

The two state sets (`finalised_transfers` and `fast_transfers`) are checked independently and never cross-validated inside the callback, breaking the mutual-exclusion invariant the protocol relies on.

## Impact Explanation
This is a concrete double-spending of bridged funds. For every exploited transfer:
- **Bridged (mintable) tokens**: the bridge mints tokens in `fin_transfer` and again transfers the relayer's deposited tokens in the callback — unauthorized double issuance.
- **Native (locked) tokens**: the bridge unlocks from its escrow in `fin_transfer` and transfers the relayer's deposited tokens in the callback — the recipient receives 2× the bridged amount.

The relayer's deposited tokens are consumed without reimbursement because `process_fin_transfer_to_near` found no fast-transfer record and paid the original recipient directly. This matches the Critical impact class: stealing/double-spending of bridged funds.

## Likelihood Explanation
The Ethereum (or other chain) finality proof is available before a relayer submits the fast transfer. A recipient who monitors the NEAR mempool can observe the `ft_transfer_call` that triggers `fast_fin_transfer`, immediately submit `fin_transfer` with the pre-obtained proof, and race the callback. The exploitable window is 2–3 NEAR blocks (~2–6 seconds). No special privileges are required; any token holder can act as both recipient and proof submitter. The attack is repeatable for every fast-transfer-eligible cross-chain transfer.

## Recommendation
Add a re-check of `is_unified_transfer_finalised` at the top of `fast_fin_transfer_to_near_callback`, before `add_fast_transfer` or `send_tokens` are called. If the transfer has already been proof-finalized, refund the relayer's tokens and abort:

```rust
pub fn fast_fin_transfer_to_near_callback(
    &mut self,
    fast_transfer: &FastTransfer,
    storage_payer: AccountId,
    relayer_id: AccountId,
) -> Promise {
    require!(Self::check_storage_balance_result(0), ...);

    // Re-check: abort if proof-based fin_transfer already ran
    if self.is_unified_transfer_finalised(&fast_transfer.transfer_id) {
        // Refund relayer and return without double-paying recipient
        return self.send_tokens(
            fast_transfer.token_id.clone(),
            storage_payer,
            fast_transfer.amount,
            "",
        );
    }

    let required_balance = self
        .add_fast_transfer(fast_transfer, relayer_id, storage_payer.clone())
        ...
}
```

Alternatively, insert the fast-transfer record into `fast_transfers` synchronously inside `fast_fin_transfer` (before the promise chain), so that a concurrent `fin_transfer` will find the record and redirect payment to the relayer instead of the recipient.

## Proof of Concept

1. User initiates a transfer of 100 USDC from Ethereum to NEAR. The Ethereum transaction finalizes; the proof is available.
2. Relayer calls `ft_transfer_call` on USDC with a `FastFinTransferMsg`. `fast_fin_transfer` runs: `is_unified_transfer_finalised` → `false`. `check_or_pay_ft_storage` is scheduled. Transaction 1 ends; `fast_transfers` is still empty.
3. Recipient submits `fin_transfer` with the Ethereum proof. `fin_transfer_callback` → `process_fin_transfer_to_near` → `add_fin_transfer` (inserts into `finalised_transfers`). `get_fast_transfer_status` → `None`. `send_tokens` → recipient receives 100 USDC. Transaction 2 ends.
4. `fast_fin_transfer_to_near_callback` runs. No `is_unified_transfer_finalised` check. `add_fast_transfer` succeeds (entry absent from `fast_transfers`). `send_tokens` → recipient receives another 100 USDC. Transaction 3 ends.

Recipient holds 200 USDC. Relayer's 100 USDC is consumed without reimbursement. The attack is repeatable for any fast-transfer-eligible cross-chain transfer. [1](#0-0) [7](#0-6) [3](#0-2) [8](#0-7)
