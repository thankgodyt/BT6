### Title
Token Accounting Mismatch in `safe_mint`: nBTC Minted to Bridge but Not Delivered to Recipient - (`contracts/nbtc/src/lib.rs`)

---

### Summary

The `safe_mint` function in the nBTC token contract unconditionally mints tokens to the bridge's own account (`bridge_id`) before checking whether the intended recipient (`account_id`) is registered. If the recipient is unregistered, the function returns `U128(0)` early, leaving the freshly minted tokens permanently stranded in the bridge's nBTC balance with no accounting entry to track or recover them.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, `safe_mint` executes in this order:

```rust
// Step 1 — always mints to bridge_id, increasing total supply and bridge balance
self.token.internal_deposit(&self.bridge_id, amount.into());

// Step 2 — if recipient is unregistered, returns early; tokens stay in bridge_id
if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0));
}

// Step 3 — only reached if recipient is registered
self.ft_transfer(account_id, amount, None);
``` [1](#0-0) 

The `internal_deposit` call at line 112 atomically increases both the NEP-141 total supply and the bridge contract's own token balance. If the recipient account is absent from the token contract's storage (line 114), the function returns `U128(0)` without ever transferring the tokens. The minted amount is now credited to `bridge_id` in the nBTC ledger, but the satoshi-bridge's `ContractData` has no field that tracks this surplus: [2](#0-1) 

The only recovery path visible in the codebase is `lost_found`, which is populated exclusively inside `transfer_nbtc_callback` for failed *transfers*, not for failed *mints*: [3](#0-2) 

There is no analogous callback or accounting update for the `U128(0)` path of `safe_mint`.

---

### Impact Explanation

- The nBTC total supply increases by `amount`, but the tokens are stranded in the bridge's own nBTC balance with no on-chain record in `ContractData`.
- The depositor's BTC UTXO is consumed by the deposit flow (marked in `verified_deposit_utxo`) before `safe_mint` is called, so the user cannot re-submit the deposit proof.
- The user permanently loses their BTC deposit and receives zero nBTC.
- The bridge's nBTC balance silently grows beyond what its internal accounting tracks, breaking the backed-supply invariant.

This matches the **Medium** allowed impact: *permanent burning below backed supply, broken callback rollback, or stuck bridge state requiring operator intervention*, and potentially **Critical** (*significant loss or permanent locking of user funds*) depending on whether the UTXO is marked verified before the mint callback resolves.

---

### Likelihood Explanation

Any depositor whose NEAR account has not called `storage_deposit` on the nBTC contract triggers this path. This is a realistic and common condition: a first-time bridge user who sends BTC before registering their account on the token contract. No special privileges or attacker cooperation are required — the depositor themselves is the victim.

---

### Recommendation

Reverse the order of operations: check recipient registration *before* minting, or mint only after confirming the transfer will succeed. A minimal fix:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "safe_mint: account_id must not be the bridge");

    // Guard BEFORE minting
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));
    }

    self.token.internal_deposit(&self.bridge_id, amount.into());

    if let Some(msg) = msg {
        self.ft_transfer_call(account_id, amount, None, msg)
    } else {
        self.ft_transfer(account_id, amount, None);
        PromiseOrValue::Value(amount)
    }
}
```

---

### Proof of Concept

1. Alice sends BTC to her deposit address but has never called `storage_deposit` on the nBTC contract.
2. A relayer submits the Merkle proof; the satoshi-bridge verifies it and marks the UTXO in `verified_deposit_utxo`.
3. The bridge calls `safe_mint(alice.near, 100_000, None)` on the nBTC contract.
4. `internal_deposit(&bridge_id, 100_000)` executes — bridge's nBTC balance: `100_000`, total supply: `100_000`.
5. `self.token.accounts.get(&alice.near)` returns `None` → function returns `U128(0)`.
6. Alice's nBTC balance: `0`. Bridge's nBTC balance: `100_000` (untracked). Alice's BTC UTXO: permanently consumed.
7. Alice cannot re-submit the deposit (UTXO already in `verified_deposit_utxo`) and has received nothing. [4](#0-3)
