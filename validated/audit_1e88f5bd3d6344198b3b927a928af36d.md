Audit Report

## Title
Floor Division in `normalize_amount` Causes Permanent Token Loss When Net Transfer Amount Normalizes to Zero - (File: `near/omni-bridge/src/lib.rs`)

## Summary

`normalize_amount` uses integer floor division to scale token amounts to the bridge's internal precision. When a user initiates a transfer whose net amount (after fee) is smaller than `10^(origin_decimals - decimals)`, the normalized result is zero. By this point, `init_transfer_internal` has already irreversibly burned or locked the user's tokens. The subsequent `sign_transfer` call always panics with `InvalidAmountToTransfer`, and no cancel or refund path exists, leaving the tokens permanently frozen.

## Finding Description

`normalize_amount` at lines 2784–2787 performs floor division:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

`sign_transfer` (lines 475–485) computes this value and panics if it is zero:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

However, `init_transfer_internal` (lines 1850–1857) burns or locks the full token amount **before** `sign_transfer` is ever called:

```rust
self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
self.lock_tokens_if_needed(
    transfer_message.get_destination_chain(),
    &token_id,
    transfer_message.amount.0,
);
```

The only guard at `init_transfer` time (lines 554–557) is `fee < amount`, which does not prevent a zero normalized net amount:

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```

`sign_transfer_callback` (lines 655–658) only removes the transfer record on a **successful** MPC signature. There is no `cancel_transfer` or `refund_transfer` public function anywhere in the contract. The transfer record stays in `pending_transfers` indefinitely, and the burned/locked tokens are unrecoverable.

## Impact Explanation

This constitutes **permanent freezing of bridged funds**, matching the Critical impact class. A user's tokens are irreversibly burned (for deployed tokens) or locked (for native tokens) inside the bridge contract with no on-chain recovery path. The transfer record persists in state forever, and the MPC signing step can never succeed for this transfer.

## Likelihood Explanation

Any unprivileged user can trigger this by calling `ft_transfer_call` with a token amount (after fee) below the normalization threshold. No special permissions are required for `init_transfer`. For tokens where `origin_decimals - decimals = 6` (e.g., a 24-decimal NEAR token bridged to an 18-decimal EVM representation), any net transfer below `1,000,000` base units triggers the bug. This is a realistic and repeatable scenario requiring no coordination or privileged access.

## Recommendation

Add a normalization check in `init_transfer` (or at the start of `init_transfer_internal`) **before** tokens are burned or locked. Retrieve the token address and decimals for the destination chain, compute `normalize_amount(amount_without_fee, decimals)`, and require the result to be greater than zero. This mirrors the existing guard in `sign_transfer` but places it before any irreversible state change.

## Proof of Concept

1. Register a token with `origin_decimals = 24`, `decimals = 18` (divisor = `1_000_000`).
2. User calls `ft_transfer_call` sending `500_000` base units with `fee = 0`.
3. `init_transfer_internal` burns/locks `500_000` tokens and stores the transfer in `pending_transfers`.
4. Relayer calls `sign_transfer` for this transfer.
5. `normalize_amount(500_000, decimals)` = `500_000 / 1_000_000` = `0`.
6. `require!(amount_to_transfer > 0, ...)` panics; MPC signing is never reached.
7. `sign_transfer_callback` is never invoked; the transfer record is never removed.
8. The `500_000` tokens are permanently burned/locked with no recovery path.
