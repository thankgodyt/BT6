### Title
Concurrent `request_refund` Calls for the Same UTXO Cause Permanent Loss of Second Caller's NEAR Storage Deposit — (`contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

Two concurrent `request_refund` calls for the same UTXO can both pass the light-client verification phase before either callback executes. When the second `request_refund_callback` fires, it hits the `refund_requests.contains_key` guard and panics — but the NEAR storage deposit attached to the second caller's initial call is already consumed and is never returned, causing permanent loss of that deposit.

---

### Finding Description

The public entrypoint `internal_request_refund` requires an attached NEAR deposit for storage: [1](#0-0) 

It then fires a cross-contract call to the light client and chains `request_refund_callback` as a subsequent receipt: [2](#0-1) 

Because the light-client call and the callback are separate receipts (processed in later blocks), two independent `request_refund` calls for the same UTXO submitted in the same block will both have their light-client receipts processed in block N+1 and both callback receipts scheduled for block N+2.

In `request_refund_callback`, the duplicate guard is: [3](#0-2) 

When the second callback executes, the first has already inserted the `RefundRequest`, so `refund_requests.contains_key` returns `true` and `require!` panics. The NEAR runtime reverts only the state changes from that callback receipt. The storage deposit that was transferred to the contract during the **initial** call receipt (which succeeded) is **not** reverted and is **not** returned to the second caller. There is no `Promise::new(predecessor).transfer(deposit)` anywhere in the callback or any error-path handler. [4](#0-3) 

---

### Impact Explanation

The second caller permanently loses their attached NEAR storage deposit. The deposit is consumed by the contract on the initial call receipt, and the callback panic does not trigger any refund. This is a broken callback rollback: the invariant that a failed `request_refund` returns the caller's storage deposit is violated.

Impact category: **Medium — broken callback rollback causing permanent loss of user NEAR funds**.

---

### Likelihood Explanation

- `request_refund` is fully public and unpermissioned; any account can call it for any UTXO they know the `deposit_msg` for.
- Two calls in the same block is a normal occurrence on NEAR mainnet, especially if a user retries or two parties independently attempt to request a refund for the same stuck deposit.
- An attacker can deliberately front-run a victim's `request_refund` to guarantee the victim's callback fires second and loses their deposit.
- No privileged role is required.

---

### Recommendation

In `request_refund_callback`, when the duplicate-request guard fires (or any other guard after the deposit has been accepted), explicitly return the storage deposit to the original caller before panicking:

```rust
// Before the require! for duplicate check:
if self.data().refund_requests.contains_key(&utxo_storage_key) {
    // Return the storage deposit to the original caller
    Promise::new(env::signer_account_id())
        .transfer(env::attached_deposit());
    env::panic_str("Refund request already exists for this UTXO");
}
```

Alternatively, restructure the flow so that the storage deposit is only accepted inside the callback (after all guards pass), not in the initial call. This is the standard NEAR pattern for payable cross-contract flows.

---

### Proof of Concept

1. Alice calls `request_refund(deposit_msg, tx_bytes, vout, proof)` with deposit D — receipt R1 to light client created, deposit D transferred to contract.
2. Bob calls `request_refund(deposit_msg, tx_bytes, vout, proof)` with deposit D in the same block — receipt R2 to light client created, deposit D transferred to contract.
3. Block N+1: both light-client receipts execute and return `true`; callback receipts C1 and C2 are scheduled.
4. Block N+2: C1 executes — `refund_requests` is empty, `verified_deposit_utxo` does not contain the key → `RefundRequest` inserted successfully.
5. Block N+2: C2 executes — `refund_requests.contains_key` returns `true` → `require!` panics with "Refund request already exists for this UTXO". State changes from C2 are reverted. Bob's deposit D is **not** returned.

Assert: Bob's NEAR balance decreased by D with no corresponding storage allocation or refund.

    #[private]
    pub fn request_refund_callback(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        gas_fee: Option<u128>,
    ) -> bool {
        let result_bytes = env::promise_result_checked(0, MAX_BOOL_RESULT)
            .expect("Call verify_transaction_inclusion failed");
        let is_valid = serde_json::from_slice::<bool>(&result_bytes)
            .expect("verify_transaction_inclusion return not bool");
        require!(is_valid, "verify_transaction_inclusion return false");

        let config = self.internal_config();
        let transaction = crate::WrappedTransaction::decode(&tx_bytes.0, &config.chain)
            .expect("Deserialization tx_bytes failed");
        let output = &transaction.output()[vout];

        // Verify that the output script matches the deposit address derived from deposit_msg
        let path = get_deposit_path(&deposit_msg);
        let deposit_address = self.generate_utxo_chain_address(&path);
        let deposit_script_pubkey = deposit_address
            .script_pubkey()
            .expect("Invalid deposit address");
        require!(
            deposit_script_pubkey == output.script_pubkey,
            "Output script_pubkey does not match deposit address"
        );

        let amount = u128::from(output.value.to_sat());
        let tx_id = transaction.compute_txid().to_string();
        let utxo_storage_key = generate_utxo_storage_key(
            tx_id,
            u32::try_from(vout).unwrap_or_else(|_| env::panic_str("vout overflow")),
        );

        // Double-check not finalized (could have been verified between request and callback)
        require!(
            !self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key),
            "UTXO already verified via deposit"
        );

        // Double-check no duplicate (another request_refund could have landed between our check and callback)
        require!(
            !self.data().refund_requests.contains_key(&utxo_storage_key),
            "Refund request already exists for this UTXO"
        );

        let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
        require!(
            resolved_gas_fee < amount,
            "Gas fee must be less than deposit amount"
        );

        Event::RefundRequested {
            deposit_msg: deposit_msg.clone(),
            utxo_storage_key: utxo_storage_key.clone(),
            amount: amount.into(),
            refund_address: refund_address.clone(),
            gas_fee: resolved_gas_fee.into(),
        }
        .emit();

        let refund_request = RefundRequest {
            deposit_msg_json: serde_json::to_string(&deposit_msg).unwrap(),
            utxo_storage_key: utxo_storage_key.clone(),
            tx_bytes,
            vout,
            amount,
            refund_address,
            gas_fee: resolved_gas_fee,
            created_at_sec: nano_to_sec(env::block_timestamp()),
            executed: false,
        };

        self.data_mut()
            .refund_requests
            .insert(utxo_storage_key, refund_request.into());

        true
    }
