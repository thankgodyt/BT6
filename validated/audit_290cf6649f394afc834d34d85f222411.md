Audit Report

## Title
Sub-Unit Outbound Transfer Permanently Freezes User Funds — (`near/omni-bridge/src/lib.rs`)

## Summary

`init_transfer` validates only that `fee.fee < amount`, allowing a transfer where `amount - fee` is positive but normalizes to zero on the destination chain. Once stored in `pending_transfers` and tokens burned/locked by `init_transfer_internal`, the transfer can never be signed (because `sign_transfer` hard-panics on a zero normalized amount) and no cancel or refund path exists, permanently freezing the user's funds.

## Finding Description

**Root cause:** `init_transfer` (via `ft_transfer_call`) enforces only:

```rust
// L554-557
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```

No normalization check is performed at creation time. `init_transfer_internal` then immediately burns or locks the full token amount:

```rust
// L1851-1857
self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
self.lock_tokens_if_needed(
    transfer_message.get_destination_chain(),
    &token_id,
    transfer_message.amount.0,
);
```

Later, when a relayer calls `sign_transfer`, `normalize_amount` is applied via floor division:

```rust
// L2784-2786
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

If `amount_without_fee < 10^(origin_decimals - decimals)`, the result is `0`, and `sign_transfer` hard-panics:

```rust
// L482-485
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

**No recovery path exists.** Confirmed by code search:
- `sign_transfer_callback` removes the transfer only on MPC signing success (L655-658), which requires `sign_transfer` to not panic first.
- `claim_fee_callback` (L1094) requires a `FinTransfer` proof from the destination chain, which can never exist because the transfer was never signed.
- No `cancel`, `refund_transfer`, or equivalent public function exists in the contract.
- `update_transfer_fee` enforces `fee.fee >= current_fee.fee` (L400), making `amount_without_fee` smaller — worsening the condition.

The `normalize_amount` doc comment (L2781-2783) acknowledges dust truncation only for the remainder case, not the total-amount-to-zero case.

## Impact Explanation

Permanent freezing of bridged funds. The user's tokens are burned or locked in the bridge with zero possibility of recovery. This matches the Critical allowed impact: *"permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet..."* The loss is irreversible because the same inputs always produce the same panic, and no administrative or user-facing escape hatch exists.

## Likelihood Explanation

Any token whose NEAR-side `origin_decimals` exceeds its destination `decimals` (e.g., a token with `origin_decimals = 24`, `decimals = 18`, giving `diff = 6`) is affected. A user sending fewer than `10^6` base units triggers the freeze. This is a realistic user error — sending a small or "dust" amount — and requires no special privileges. The user only needs to call `ft_transfer_call` with a standard `InitTransferMsg` payload, which is a normal public bridge entry point.

## Recommendation

Add a normalization check inside `init_transfer` (or at the top of `init_transfer_internal`) before storing the transfer and burning/locking tokens:

```rust
let decimals = self.token_decimals.get(&token_address)
    .near_expect(BridgeError::TokenDecimalsNotFound);
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee()
        .near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

This mirrors the check already present in `sign_transfer` (L482-485) but must be enforced at creation time, before tokens are burned/locked and the transfer is stored in `pending_transfers`.

## Proof of Concept

1. Register a token with `origin_decimals = 24`, `decimals = 18` (diff = 6).
2. User calls `ft_transfer_call` with `amount = 500_000`, `fee = 0`, destination = any EVM address.
3. `init_transfer` passes: `0 (fee) < 500_000 (amount)`. ✓
4. `init_transfer_internal` burns 500,000 tokens and stores the transfer in `pending_transfers`. ✓
5. Relayer calls `sign_transfer`. `normalize_amount(500_000, diff=6)` = `500_000 / 1_000_000` = `0`.
6. `require!(amount_to_transfer > 0)` panics → `InvalidAmountToTransfer`. Transfer stays in `pending_transfers` forever.
7. No cancel function exists. Tokens are permanently gone.

A unit test can be written against the NEAR contract directly: construct a `TransferMessage` with the above parameters, call `init_transfer_internal` to confirm tokens are burned and the transfer is stored, then call `sign_transfer` and assert it panics with `InvalidAmountToTransfer`, then confirm the transfer still exists in `pending_transfers` with no removal path reachable.
