Audit Report

## Title
TOCTOU in `fast_fin_transfer_to_near_callback`: Finalization Not Re-Verified After Cross-Contract Call Enables Double-Spending - (File: `near/omni-bridge/src/lib.rs`)

## Summary
`fast_fin_transfer` checks `is_unified_transfer_finalised` before issuing a cross-contract call to `check_or_pay_ft_storage`. Because NEAR cross-contract calls span multiple blocks, a trusted relayer can submit `fin_transfer` with a valid proof during this window. `process_fin_transfer_to_near` finds no fast-transfer entry (since `add_fast_transfer` has not yet executed) and sends tokens to the recipient. When `fast_fin_transfer_to_near_callback` subsequently runs, it does not re-check finalization status, `add_fast_transfer` succeeds (the `fast_transfers` map has no entry for this ID), and `send_tokens` fires a second time — delivering `2 × (amount − fee)` tokens while only `amount` was locked on the source chain.

## Finding Description

**Time of Check (L778–780):** `fast_fin_transfer` verifies the transfer is not yet finalized:
```rust
if self.is_unified_transfer_finalised(&fast_fin_transfer_msg.transfer_id) {
    env::panic_str(BridgeError::TransferAlreadyFinalised.to_string().as_str());
}
```

**External Call Delay (L812–826):** Immediately after, execution suspends across at least one NEAR block:
```rust
Self::check_or_pay_ft_storage(&deposit_action, ...)
    .then(Self::ext(...).fast_fin_transfer_to_near_callback(...))
```

**Time of Use (L854–882):** The callback calls `add_fast_transfer` and then `send_tokens` with no re-check of `is_unified_transfer_finalised`:
```rust
let required_balance = self
    .add_fast_transfer(fast_transfer, relayer_id, storage_payer.clone())
    .saturating_add(ONE_YOCTO);
...
self.send_tokens(fast_transfer.token_id.clone(), recipient, amount_without_fee, ...)
```

**Why existing guards fail:**

- `add_fast_transfer` (L2246–2268) only checks the `fast_transfers` map and panics if the same `FastTransferId` is already present. It does **not** consult `finalised_transfers`.
- `process_fin_transfer_to_near` (L1875–1902) calls `add_fin_transfer` first (inserting into `finalised_transfers`), then calls `get_fast_transfer_status`. If `fast_transfer_status` is `None` — which it is, because `add_fast_transfer` has not yet executed — tokens are sent to the original recipient rather than the relayer.
- `add_fin_transfer` (L2226–2234) prevents a second `fin_transfer` call but does not cancel the already-in-flight `fast_fin_transfer_to_near_callback`.

The two maps (`finalised_transfers` and `fast_transfers`) are updated independently with no cross-check in the callback, creating a window where both `fin_transfer` and `fast_fin_transfer_to_near_callback` complete successfully for the same transfer ID.

## Impact Explanation

For **bridged (deployed) tokens**, `send_tokens` calls `mint` on the token contract. The second mint in the callback creates tokens beyond what is locked on the source chain — **unauthorized minting**. For **native (locked) tokens**, the bridge transfers from its own reserves twice — **direct loss of bridge funds**. Both outcomes match the allowed critical impact: *"Stealing, loss, double-spending, or unauthorized minting of bridged funds."*

## Likelihood Explanation

`fin_transfer` is gated by `#[trusted_relayer]` (confirmed at L756 for `fast_fin_transfer`; the same guard applies to `fin_transfer`). The race requires a trusted relayer to submit `fin_transfer` during the multi-block external-call window. This can occur:

1. **Accidentally:** An honest relayer sees a valid proof and submits `fin_transfer` without knowing a concurrent `fast_fin_transfer` is in the callback phase. The multi-block window makes this a realistic operational scenario.
2. **Deliberately:** A trusted relayer who is also the recipient (or colluding with the recipient) fronts `amount` tokens via `fast_fin_transfer`, then immediately submits `fin_transfer` with the valid proof. They receive `2 × (amount − fee)` tokens while only `amount` was locked, netting `amount − 2 × fee`.

Relayer flows are explicitly within scope. The accidental path requires no malicious intent, only normal concurrent operation.

## Recommendation

Re-check `is_unified_transfer_finalised` at the start of `fast_fin_transfer_to_near_callback`, before calling `add_fast_transfer` or `send_tokens`. If the transfer was finalized during the external-call window, abort and refund the relayer's fronted tokens:

```rust
pub fn fast_fin_transfer_to_near_callback(...) -> Promise {
    if self.is_unified_transfer_finalised(&fast_transfer.transfer_id) {
        // fin_transfer raced ahead; refund relayer's fronted tokens
        return self.send_tokens(
            fast_transfer.token_id.clone(),
            storage_payer,
            fast_transfer.amount,
            &String::new(),
        );
    }
    // ... existing logic
}
```

## Proof of Concept

1. A transfer originates on Ethereum (origin_chain: Eth, origin_nonce: N). A valid proof exists.
2. Trusted Relayer R (who is also the NEAR recipient) calls `ft_transfer_call` on the token contract, sending `amount` tokens to the bridge, triggering `fast_fin_transfer`.
3. `fast_fin_transfer` passes the `is_unified_transfer_finalised` check (returns false) and issues the `check_or_pay_ft_storage` cross-contract call. Execution suspends.
4. In the next NEAR block, before `fast_fin_transfer_to_near_callback` executes, Relayer R submits `fin_transfer` with the valid proof.
5. `fin_transfer` → `fin_transfer_callback` → `process_fin_transfer_to_near`: `add_fin_transfer` inserts into `finalised_transfers`; `get_fast_transfer_status` returns `None` (no entry in `fast_transfers`); `send_tokens` mints/transfers `amount − fee` tokens to Relayer R as recipient.
6. `fast_fin_transfer_to_near_callback` executes: `add_fast_transfer` succeeds (no entry in `fast_transfers` for this ID); `send_tokens` mints/transfers another `amount − fee` tokens to Relayer R.
7. Relayer R has received `2 × (amount − fee)` tokens. Only `amount` was locked on the source chain. Net gain: `amount − 2 × fee`.

**Test plan:** Deploy the bridge on a NEAR localnet. Submit `ft_transfer_call` to trigger `fast_fin_transfer`. Before the callback resolves, submit `fin_transfer` with a valid proof in the next block. Observe that both `send_tokens` calls succeed and the recipient's balance equals `2 × (amount − fee)`.
