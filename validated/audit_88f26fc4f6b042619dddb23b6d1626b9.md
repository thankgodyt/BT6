### Title
User-Supplied `gas_fee` in `request_refund` Not Validated Against Protocol Minimum, Enabling Permanent UTXO Lock - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary

The `request_refund` entry point accepts an optional user-supplied `gas_fee` parameter. In `request_refund_callback`, the only validation applied is that the fee is strictly less than the deposit amount. There is no check that the supplied value meets or exceeds `config.min_btc_gas_fee`. On the Bitcoin execution path, `internal_execute_refund` builds and submits the refund PSBT using whatever fee was stored at request time, with no further floor check. A user who supplies `gas_fee = 0` (or any value below the protocol minimum) causes the bridge to sign and broadcast a Bitcoin transaction that will never be mined, while simultaneously marking the deposit UTXO as verified — permanently locking the user's BTC.

### Finding Description

`request_refund_callback` resolves the gas fee as follows:

```rust
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
``` [1](#0-0) 

The sole constraint is `resolved_gas_fee < amount`. There is no lower-bound check against `config.min_btc_gas_fee`. The value is then stored verbatim in the `RefundRequest`:

```rust
gas_fee: resolved_gas_fee,
``` [2](#0-1) 

When `execute_refund` is later called on the Bitcoin path, `refund_execution_inputs` computes `refund_amount = amount - gas_fee` and `internal_execute_refund` builds the PSBT directly from that value with no gas-fee floor enforcement:

```rust
pub(crate) fn internal_execute_refund(
    &mut self,
    utxo_storage_key: String,
    timelock_sec: u64,
    _chain_specific_data: Option<ChainSpecificData>,
) -> PromiseOrValue<()> {
    let refund_request = self.load_refund_request_for_execute(&utxo_storage_key, timelock_sec);
    let RefundExecutionInputs { outpoint, deposit_output, refund_amount } =
        self.refund_execution_inputs(&refund_request);
    let refund_output = self.build_refund_output(&refund_request.refund_address, refund_amount);
    let mut psbt = PsbtWrapper::new(vec![outpoint], vec![refund_output]);
    psbt.set_input_utxo(vec![deposit_output]);
    ...
    self.finalize_refund_with_psbt(caller, refund_request, psbt, refund_amount, utxo_storage_key);
``` [3](#0-2) 

`finalize_refund_with_psbt` then inserts the UTXO into `verified_deposit_utxo`, blocking any future `verify_deposit` call for that UTXO:

```rust
self.data_mut()
    .verified_deposit_utxo
    .insert(utxo_storage_key.clone());
``` [4](#0-3) 

This is in direct contrast to the withdrawal path, where `check_withdraw_psbt` enforces both a floor and a ceiling:

```rust
require!(
    gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee,
    ...
);
``` [5](#0-4) 

And the Zcash refund path, which calls `check_psbt_chain_specific` to validate the fee against the ZIP-317 minimum: [6](#0-5) 

The Bitcoin refund path has no equivalent check.

### Impact Explanation

A user who supplies `gas_fee = 0` (which passes `0 < amount`) causes the bridge to:

1. Store a `RefundRequest` with `gas_fee = 0`.
2. Build a Bitcoin PSBT where the output equals the full deposit amount and the miner fee is 0 satoshis.
3. Have MPC sign that PSBT.
4. Insert the UTXO into `verified_deposit_utxo`, blocking `verify_deposit` permanently.

The signed 0-fee transaction will never be mined. The gas fee stored in `RefundRequest` is immutable — re-executing `execute_refund` produces the identical PSBT (same txid), which fails with "pending info already exist." The user's BTC is permanently locked in the bridge's deposit address: it is not in the bridge's spendable UTXO set, not refundable, and not depositable.

If the DAO rejects the refund request *before* `execute_refund` is called, the UTXO is not yet in `verified_deposit_utxo` and `verify_deposit` remains possible. However, `internal_reject_refund` does **not** remove the UTXO from `verified_deposit_utxo` if rejection happens after `execute_refund`:

```rust
pub(crate) fn internal_reject_refund(&mut self, utxo_storage_key: String) {
    require!(
        self.data_mut()
            .refund_requests
            .remove(&utxo_storage_key)
            .is_some(),
        "Refund request not found"
    );
    Event::RefundRejected { utxo_storage_key }.emit();
}
``` [7](#0-6) 

This matches the **Medium** impact category: bypass of bridge limits/policies (`min_btc_gas_fee`) and stuck bridge state requiring operator intervention, with escalation to permanent fund loss if the DAO does not intervene within the refund timelock window.

### Likelihood Explanation

The `gas_fee` parameter is optional and publicly documented. Any bridge user who calls `request_refund` can supply `gas_fee: Some(0)`. A user might do so intentionally (to maximize the refund amount) or by mistake. The pre-authorized refund address path has only a 2-day timelock, giving the DAO a narrow window to reject before `execute_refund` can be called. The non-pre-authorized path has a 14-day window but is callable by any NEAR account for any unverified deposit UTXO.

### Recommendation

Add a minimum gas fee check in `request_refund_callback` mirroring the withdrawal path:

```rust
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
require!(
    resolved_gas_fee >= config.min_btc_gas_fee,
    "Gas fee below protocol minimum"
);
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
```

Additionally, add the same floor check inside `internal_execute_refund` (Bitcoin) before building the PSBT, consistent with the Zcash path's `check_psbt_chain_specific` call.

### Proof of Concept

1. Alice deposits 100,000 satoshis to her bridge deposit address.
2. Alice calls `request_refund` with `gas_fee: Some(0)` and her `deposit_msg` (with `refund_address` pre-set).
3. `request_refund_callback` accepts the request: `0 < 100000` passes.
4. After 2 days, Alice calls `execute_refund`.
5. `refund_execution_inputs` computes `refund_amount = 100000 - 0 = 100000`.
6. A PSBT is built: one input (100,000 sat), one output (100,000 sat), miner fee = 0.
7. `finalize_refund_with_psbt` inserts the UTXO into `verified_deposit_utxo`.
8. MPC signs the 0-fee transaction.
9. The transaction is broadcast but never mined (0-fee).
10. `verify_deposit` for the same UTXO now panics: "Already deposit utxo".
11. Alice's 100,000 satoshis are permanently locked.
