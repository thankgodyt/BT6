### Title
Off-by-one gas boundary allows depositor to silently drop their own post_action via panic in `handle_post_action` — (`contracts/nbtc/src/lib.rs`)

### Summary
`MIN_PER_POST_ACTIONS_GAS` (bridge validation) and `GAS_FOR_FT_TRANSFER_CALL` (nBTC execution guard) are both 30 Tgas, but the bridge uses a strict `<` check while the nBTC contract uses a strict `>` check. A depositor who sets `post_action.gas = Some(30 Tgas)` passes bridge validation but causes `handle_post_action` to panic, silently dropping the DeFi action.

### Finding Description
The bridge validates per-post-action gas with:

```rust
// deposit_msg.rs:157
if gas.as_gas() < MIN_PER_POST_ACTIONS_GAS.as_gas() { return None; }
```

This allows `gas == 30 Tgas` through. [3](#0-2) 

`handle_post_actions` then dispatches with exactly that gas:

```rust
// lib.rs:372-375
Self::ext(env::current_account_id())
    .with_static_gas(gas)
    .handle_post_action(...)
    .detach();
``` [5](#0-4) 

Inside `handle_post_action`, the first statement is:

```rust
// lib.rs:393-396
require!(
    env::prepaid_gas() > GAS_FOR_FT_TRANSFER_CALL,
    "More gas is required"
);
``` [4](#0-3) 

With `prepaid_gas == 30 Tgas` and `GAS_FOR_FT_TRANSFER_CALL == 30 Tgas`, the condition `30 > 30` is false, causing a panic. Because the promise was `.detach()`-ed, the panic is silent — no rollback of the outer mint, no error surfaced to the depositor.

### Impact Explanation
The panic fires before `self.token.internal_transfer` executes, so the nBTC tokens are never forwarded to the DeFi `receiver_id`. They remain in the depositor's account. The intended `ft_on_transfer` call to the DeFi protocol never happens. The depositor's cross-contract DeFi action is silently dropped with no on-chain error visible to them. This violates the invariant that a `post_action` passing bridge-side validation must execute successfully in the nBTC contract.

### Likelihood Explanation
Any unprivileged depositor can trigger this by setting `post_action.gas = 30_000_000_000_000` in their deposit message. The path is fully public, requires no special role, and is deterministic. The boundary value is the natural minimum a user would choose.

### Recommendation
Align the two guards to use the same comparison operator. Either:
- Change the bridge validation to `gas.as_gas() <= MIN_PER_POST_ACTIONS_GAS.as_gas()` (reject `gas == 30 Tgas`), or
- Change the nBTC guard to `env::prepaid_gas() >= GAS_FOR_FT_TRANSFER_CALL` (accept `prepaid_gas == 30 Tgas`).

The first option is safer because `handle_post_action` genuinely needs gas beyond 30 Tgas to perform the transfer and schedule the resolver callback.

### Proof of Concept
1. Construct a deposit message with `post_actions: [{ receiver_id: "some-defi.near", amount: "1", msg: "", gas: 30_000_000_000_000 }]`.
2. Submit the BTC deposit; the bridge relayer calls `verify_deposit` → `mint` → `handle_post_actions`.
3. `handle_post_actions` dispatches `handle_post_action` with `static_gas = 30 Tgas`.
4. `handle_post_action` evaluates `30 Tgas > 30 Tgas` → false → panics with `"More gas is required"`.
5. The detached promise fails silently; `some-defi.near` never receives the nBTC transfer; the depositor's DeFi action is dropped.
