### Title
Caller-Supplied `gas_fee` in Refund Request Lacks Minimum Threshold — (File: contracts/satoshi-bridge/src/refund.rs)

---

### Summary

The `internal_request_refund` function accepts a caller-controlled `gas_fee: Option<u128>` parameter that is forwarded verbatim into the stored `RefundRequest`. The only validation applied is that `resolved_gas_fee < amount`. There is no minimum threshold enforced. Any unprivileged user submitting a refund request can pass `gas_fee = Some(0)`, causing the bridge to store a refund request with zero gas fee, which sets `refund_amount = full_deposit_amount`. This is a direct analog to the external report's vulnerability class: an unsigned/unvalidated parameter that can be set to an extreme value to bypass a bridge policy.

---

### Finding Description

In `contracts/satoshi-bridge/src/refund.rs`, the `request_refund_callback` function resolves the gas fee as follows:

```rust
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
``` [1](#0-0) 

The only guard is `resolved_gas_fee < amount`. There is no lower-bound check (e.g., `resolved_gas_fee >= config.min_refund_gas_fee`). A caller who passes `gas_fee = Some(0)` satisfies `0 < amount` trivially, and the refund request is stored with `gas_fee = 0`.

This stored value is later consumed in `refund_execution_inputs`:

```rust
let refund_amount = refund_request
    .amount
    .checked_sub(refund_request.gas_fee)
    .expect("Deposit amount too small to cover gas fee");
require!(refund_amount > 0, "Refund amount is zero after gas fee");
``` [2](#0-1) 

With `gas_fee = 0`, `refund_amount = amount` (the full deposit). The check `refund_amount > 0` passes for any non-dust deposit. The bridge then attempts to construct a refund PSBT paying the full deposit amount to the user, leaving zero margin for the actual on-chain BTC transaction fee.

The `gas_fee` parameter flows from the public API through `internal_request_refund`:

```rust
pub(crate) fn internal_request_refund(
    &self,
    deposit_msg: DepositMsg,
    refund_address: String,
    tx_bytes: Base64VecU8,
    vout: usize,
    proof: TxInclusionProof,
    gas_fee: Option<u128>,
) -> Promise {
``` [3](#0-2) 

and is forwarded directly into the `#[private]` callback:

```rust
.then(
    Self::ext(env::current_account_id())
        .with_static_gas(GAS_FOR_REQUEST_REFUND_CALLBACK)
        .request_refund_callback(deposit_msg, refund_address, tx_bytes, vout, gas_fee),
)
``` [4](#0-3) 

No sanitization occurs between the public entry point and the stored value.

---

### Impact Explanation

**Medium — Bypass of bridge limits or policies / attacker-triggered stuck bridge state requiring operator intervention.**

When `gas_fee = Some(0)` is supplied:

1. The refund request is stored with `gas_fee = 0` and `refund_amount = full_deposit_amount`.
2. `execute_refund` attempts to build a PSBT paying the full deposit to the user. The actual BTC on-chain fee must come from the input UTXO, but the output already consumes the entire input value, making the PSBT arithmetically invalid (outputs ≥ inputs).
3. The PSBT construction or the `min_btc_gas_fee` validation (enforced in `check_withdraw_psbt` / `check_psbt_output_all_change_address`) will reject it.
4. The refund request remains in contract storage in a permanently un-executable state. The deposit UTXO is marked as verified (blocking `verify_deposit`) and the refund request blocks re-submission for the same UTXO.
5. Recovery requires a privileged `RefundOperator` or `DAO` account to call `reject_refund`, constituting operator intervention. [5](#0-4) 

---

### Likelihood Explanation

**Medium.** Any unprivileged NEAR account that holds a valid deposit UTXO and a BTC inclusion proof can call `request_refund` with `gas_fee = Some(0)`. No special role, leaked key, or privileged access is required. The attacker only needs to be the legitimate depositor (or anyone, if `deposit_msg.refund_address` is `None`). The attack is cheap: it only requires the storage deposit attached to `request_refund`. [6](#0-5) 

---

### Recommendation

Enforce a minimum threshold on the caller-supplied `gas_fee`, mirroring the fix described in the external report. After resolving the fee, add:

```rust
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
require!(
    resolved_gas_fee >= config.min_refund_gas_fee,  // enforce lower bound
    "Gas fee is below the minimum threshold"
);
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
```

Alternatively, reject any caller-supplied `gas_fee` that is below `config.min_btc_gas_fee`, or simply disallow caller-supplied values entirely and always use `self.get_refund_gas_fee()`.

---

### Proof of Concept

1. Attacker holds a valid BTC deposit UTXO and obtains its inclusion proof.
2. Attacker calls the public `request_refund` entry point (in `bridge.rs`) with `gas_fee = Some(0)` and a valid `proof`.
3. `internal_request_refund` passes `gas_fee = Some(0)` to `request_refund_callback`.
4. `request_refund_callback` resolves `resolved_gas_fee = 0`; the check `0 < amount` passes; the `RefundRequest` is stored with `gas_fee = 0`.
5. Any subsequent call to `execute_refund` for this UTXO attempts to build a PSBT where `refund_amount = amount` (full deposit), leaving no margin for the BTC transaction fee. The PSBT is rejected by the on-chain fee validation.
6. The refund request is stuck. The UTXO is blocked from being claimed via `verify_deposit` (it is inserted into `verified_deposit_utxo` by `finalize_refund_with_psbt` if `execute_refund` partially succeeds, or remains in `refund_requests` blocking re-submission). Operator must call `reject_refund` to recover. [7](#0-6)
