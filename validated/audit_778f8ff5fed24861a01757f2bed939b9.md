### Title
Detached `burn` Call with Insufficient Gas in `safe_mint_callback` Silently Fails, Leaving Unbacked nBTC in Circulation and Allowing UTXO Re-submission — (File: `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

### Summary

In `safe_mint_callback`, when the OmniBridge's `ft_on_transfer` signals failure (returns 0 used tokens), the bridge fires a fire-and-forget `.detach()`ed `burn` call with only `GAS_FOR_BURN_CALL = 5 TGas` and no error-handling callback. If this burn silently fails, the bridge retains unbacked nBTC tokens in its own balance, while simultaneously removing the UTXO from `verified_deposit_utxo`. This allows the same UTXO to be re-submitted via `safe_verify_deposit`, repeating the cycle and further inflating the unbacked nBTC supply. This is the direct NEAR analog of Solidity's `.send()` — a fixed-gas, fire-and-forget transfer with no failure recovery.

### Finding Description

In `safe_mint_callback` (deposit.rs lines 422–468), when `is_refund_required()` returns `true` (the `safe_mint` call failed because the receiver used 0 tokens), the bridge executes two critical state changes and two detached promises:

```rust
// State change 1: UTXO removed from verified set — re-submission now possible
self.data_mut()
    .verified_deposit_utxo
    .remove(&pending_utxo_info.utxo_storage_key);

// Fire-and-forget burn — only 5 TGas, no callback, no error handling
ext_nbtc::ext(self.internal_config().nbtc_account_id.clone())
    .with_static_gas(GAS_FOR_BURN_CALL)   // GAS_FOR_BURN_CALL = 5 TGas
    .burn(env::current_account_id(), mint_amount, relayer_account_id, U128(0))
    .detach();                              // no callback, failure is silent

// Fire-and-forget NEAR transfer — also no error handling
Promise::new(env::signer_account_id())
    .transfer(self.required_balance_for_safe_deposit())
    .detach();
```

`GAS_FOR_BURN_CALL` is defined as `Gas::from_tgas(5)`. The nBTC `burn` function must perform authorization checks, balance updates, total-supply updates, and event emission — operations that can easily exceed 5 TGas. If the burn runs out of gas or panics for any reason, NEAR silently drops the failure because `.detach()` discards the promise result entirely. There is no callback, no rollback, and no `lost_found` accounting for this path.

The state after a silent burn failure:
- The bridge contract holds `mint_amount` of nBTC tokens that were refunded back from the failed `safe_mint` — these are real, transferable tokens inflating total supply.
- The UTXO key is absent from `verified_deposit_utxo` (removed on line 440–442).
- The UTXO is also absent from UTXO storage (it was never added in the failure branch).

Because `verified_deposit_utxo` no longer contains the key, the guard `require!(!self.data().verified_deposit_utxo.contains(&utxo_storage_key), "Already deposit utxo")` in `verify_safe_deposit_callback` (line 399–403) passes again. An attacker can re-submit the same UTXO via `safe_verify_deposit`, triggering another mint-and-failed-burn cycle, accumulating more unbacked nBTC with each iteration.

### Impact Explanation

Each failed burn cycle leaves `mint_amount` of nBTC permanently in the bridge contract's balance with no corresponding BTC backing. The total nBTC supply grows beyond the amount of BTC held by the bridge, breaking the 1:1 peg invariant. While the attacker does not directly receive the extra tokens (they sit at the bridge contract address), the supply inflation is permanent and cumulative: every re-submission of the same UTXO adds another `mint_amount` of unbacked tokens. This constitutes harmful smart-contract behavior — permanent minting above backed supply — matching the Medium impact category: *"permanent burning below backed supply, broken callback rollback, or stuck bridge state requiring operator intervention."*

### Likelihood Explanation

The `safe_verify_deposit` entry point is fully public. An attacker needs only:
1. A real BTC deposit to an address derived from a `DepositMsg` where `recipient_id` is a contract they control (or any contract whose `ft_on_transfer` can be made to return 0 — e.g., by crafting a malformed `msg`).
2. A valid Merkle proof for that deposit (obtainable from the Bitcoin blockchain).

The attacker controls the `msg` field passed to `ft_on_transfer`. A malformed or unexpected `msg` can cause the OmniBridge's `ft_on_transfer` to return 0 (or panic, which `is_refund_required()` also treats as "refund required" per the comment on line 479). The 5 TGas allocation for `burn` is tight for a function that must perform storage reads/writes and event emission; gas exhaustion is a realistic failure mode. No privileged access is required.

### Recommendation

1. **Replace `.detach()` with a chained callback**: The burn in the failure branch of `safe_mint_callback` must have a callback that handles failure — either re-queuing the burn, adding the amount to a `lost_found`-style recovery map, or re-inserting the UTXO into `verified_deposit_utxo` to prevent re-submission.

2. **Increase gas allocation**: `GAS_FOR_BURN_CALL = 5 TGas` is insufficient for a cross-contract call that performs storage operations. Align it with the gas budgets used in the non-detached burn paths (`GAS_FOR_WITHDRAW_BURN_CALL_BACK = 20 TGas`).

3. **Do not remove from `verified_deposit_utxo` before confirming burn success**: The UTXO should remain in `verified_deposit_utxo` until the burn is confirmed, preventing re-submission during the window of uncertainty.

### Proof of Concept

1. Attacker deploys a NEAR contract `attacker.near` whose `ft_on_transfer` always returns `"0"` (zero tokens used).
2. Attacker constructs `DepositMsg { recipient_id: "attacker.near", safe_deposit: Some({msg: "..."}), refund_address: "bc1q..." }` and calls `get_user_deposit_address` to obtain the BTC deposit address.
3. Attacker sends BTC to that address and waits for confirmation.
4. Attacker calls `safe_verify_deposit(deposit_msg, tx_bytes, vout, proof)`.
5. Bridge calls `safe_mint` on nBTC → nBTC minted → `ft_on_transfer` on `attacker.near` returns `"0"` → nBTC refunded back to bridge.
6. `safe_mint_callback` fires: `is_refund_required() = true`, `is_success = false`.
7. Bridge removes UTXO from `verified_deposit_utxo` (line 440–442).
8. Bridge fires detached `burn(bridge, mint_amount, ...)` with 5 TGas — burn fails silently due to gas exhaustion.
9. Bridge now holds `mint_amount` unbacked nBTC; UTXO is no longer in `verified_deposit_utxo`.
10. Attacker repeats step 4 with the same UTXO — the guard passes again, another `mint_amount` of unbacked nBTC accumulates.
