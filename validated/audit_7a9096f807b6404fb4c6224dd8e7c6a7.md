### Title
Peras Certificate Validation Unconditionally Accepts All Peer-Supplied Certificates — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The sole production `BlockSupportsPeras` instance implements `validatePerasCert` as a stub that unconditionally returns `Right` for every certificate it receives, performing no cryptographic or structural checks. Because this function is the gatekeeper called on every inbound Peras certificate received from a peer over the object-diffusion mini-protocol, any unprivileged peer can inject an arbitrary crafted certificate into the node's `PerasCertDB`. The accepted certificate then applies its Peras weight boost during chain selection, allowing the attacker to make the node prefer a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` type class declares `validatePerasCert` as the mandatory validation gate for inbound Peras certificates:

```haskell
validatePerasCert ::
  PerasCfg blk ->
  PerasCert blk ->
  Either (PerasValidationErr blk) (ValidatedPerasCert blk)
```

The only concrete instance in the codebase is the degenerate catch-all `instance StandardHash blk => BlockSupportsPeras blk`, which implements this function as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

The `params` argument (`PerasCfg blk` / `PerasParams`) is stored, required at construction time, and passed through the entire call chain — but it is never used to validate anything about the certificate. The only field read from it is `perasWeight params`, which is used to assign a boost value to the unconditionally accepted certificate. No round-number bounds, no cryptographic signature check, no quorum proof, no eligibility check — nothing is verified. [1](#0-0) 

This stub is the function called in the live inbound-certificate processing path. In `PerasCert.hs`, both `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB` pass `(validatePerasCert mkPerasParams)` directly to `processCerts`:

```haskell

``` [2](#0-1) [3](#0-2) 

`processCerts` then calls `validateCert` on each inbound certificate and, if all pass (which they always do), adds them to the database: [4](#0-3) 

The `PerasVoteDbArgs` record also stores `pvdbaPerasCfg` as a required field, and `createDB` extracts and passes it to `implAddVote`, but the analogous `validatePerasVote` similarly ignores its `_params` argument entirely (note the wildcard):

### Impact Explanation

A Peras certificate accepted into the `PerasCertDB` contributes a `PerasWeight` boost to the block it references during chain selection. Because `validatePerasCert` unconditionally accepts every certificate, an attacker can:

1. Craft a `PerasCert` for any round number, referencing any block point (including a block on a minority or adversarial fork).
2. Deliver it to an honest node via the object-diffusion mini-protocol.
3. The node accepts it as `ValidatedPerasCert` with full `perasWeight` boost.
4. During chain selection, the boosted adversarial fork gains a weight advantage, causing the honest node to prefer the non-canonical chain.

This is a **bypass of Peras certificate validation** enabling unauthorized certificate acceptance, and a **chain selection bug** allowing an unprivileged peer to make an honest node prefer a non-canonical chain beyond the intended security assumptions.

---

### Likelihood Explanation

The attack requires only network access to a node running the Peras object-diffusion mini-protocol. No keys, no stake, no admin access are needed. The attacker simply sends a well-formed `PerasCert` CBOR message with an arbitrary round number and block point. The serialization format for `PerasCert` is public: [8](#0-7) 

The likelihood is **High** for any deployment where the Peras object-diffusion mini-protocol is enabled and reachable by untrusted peers.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real one that:
- Verifies the certificate's aggregate signature against the declared voter set and the claimed election ID / candidate.
- Checks that the voter set meets the quorum threshold defined in `PerasParams`.
- Validates that the round number falls within the expected window.
- Verifies voter eligibility against the current stake distribution.

Until a real implementation is available, the object-diffusion mini-protocol for Peras certificates should not be enabled in production, or inbound certificates should be rejected entirely rather than unconditionally accepted.

---

### Proof of Concept

**Attacker-controlled entry path:**

1. Peer connects to an honest node and sends a crafted `PerasCert` via the object-diffusion mini-protocol targeting an adversarial block `B_adv` in round `R`.
2. `makePerasCertPoolWriterFromChainDB` → `processCerts` → `validatePerasCert mkPerasParams cert_adv` is called.
3. `validatePerasCert` returns `Right (ValidatedPerasCert { vpcCert = cert_adv, vpcCertBoost = perasWeight mkPerasParams })` unconditionally.
4. `cert_adv` is added to the `PerasCertDB` via `ChainDB.addPerasCertAsync`.
5. Chain selection now sees `B_adv` with a `PerasWeight` boost of `perasWeight mkPerasParams` (default: `PerasWeight 15`), making it preferred over the honest canonical chain tip even if the honest chain is longer by up to 15 blocks. [9](#0-8) [4](#0-3) [1](#0-0)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
