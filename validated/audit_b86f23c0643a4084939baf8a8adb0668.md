### Title
No Emergency Escape for Withdrawals Stuck in `PendingSign` State — Permanent nBTC Lock — (File: `contracts/satoshi-bridge/src/api/bridge.rs`, `contracts/satoshi-bridge/src/chain_signature.rs`)

### Summary
The satoshi-bridge has no emergency cancellation path for a withdrawal that is stuck in the `PendingSign` stage. Once a user's nBTC tokens are transferred into the bridge and a `BTCPendingInfo` record is created in `PendingSign` state, the only forward path is a successful MPC signature. If MPC signing permanently fails (key rotation, network upgrade, or sustained outage), neither the user nor the DAO can cancel the pending withdrawal and return the nBTC. This is the direct analog of the MasterChef `emergencyWithdraw` gap: the underlying signing infrastructure has a failure mode, but the bridge contract provides no escape hatch.

### Finding Description

**Withdrawal initiation** locks nBTC in the bridge and creates a `BTCPendingInfo` in `PendingSign` state: [1](#0-0) [2](#0-1) 

The `BTCPendingInfo` is created with `PendingInfoStage::PendingSign`: [3](#0-2) 

**MPC signing failure is non-fatal but leaves state unchanged.** When `sign_btc_transaction_callback` receives a failed MPC response, it simply returns `false` without modifying the pending info: [4](#0-3) 

The pending info remains in `PendingSign`. The user can retry, but if MPC is permanently unavailable, the withdrawal is stuck indefinitely.

**`cancel_withdraw` is gated on `PendingVerify` state.** The only operator-level cancellation function explicitly asserts the original transaction must be in `PendingVerify` (i.e., already broadcast to Bitcoin): [5](#0-4) 

A `PendingSign` withdrawal fails this assertion and cannot be cancelled.

**No other escape exists.** The cleanup helpers are type-restricted:
- `clear_invalid_pending_verify_rbf` — only for RBF-type pending infos
- `remove_refund_pending_tx_id` — only for `Refund`-state pending infos [6](#0-5) [7](#0-6) 

There is no `cancel_pending_sign_withdrawal` or equivalent function anywhere in the contract.

**The `PendingSign` capacity limit compounds the problem.** Each account defaults to a limit of 1 pending sign transaction: [8](#0-7) 

A stuck `PendingSign` withdrawal blocks the user from initiating any new withdrawal, and blocks the DAO from calling `cancel_withdraw` (which also checks capacity): [9](#0-8) 

### Impact Explanation

If MPC signing is permanently unavailable (key rotation making the PSBT's `key_version` stale, a NEAR chain-signatures network upgrade, or a sustained outage), the user's nBTC tokens remain locked inside the bridge contract with no on-chain path to recover them. The DAO cannot force-cancel the pending info. This constitutes permanent loss of user funds — a Critical impact under the allowed scope ("significant loss, theft, destruction, or permanent locking of user or protocol funds") or at minimum a Medium impact ("stuck bridge state requiring operator intervention").

### Likelihood Explanation

MPC key rotation is a planned operational event for NEAR Chain Signatures. When the `key_version` increments, PSBTs signed with the old version become invalid. Any withdrawal that was in `PendingSign` at the time of rotation cannot be completed and cannot be cancelled. This is a realistic, non-adversarial trigger that requires no privileged attacker — any ordinary user who happened to have an in-flight withdrawal at rotation time is affected.

### Recommendation

Add an emergency cancellation function for `PendingSign` withdrawals, analogous to MasterChef's `emergencyWithdraw`. The function should:
1. Be callable by the DAO (or the user themselves after a timeout).
2. Assert the pending info is in `PendingSign` state and is a `WithdrawOriginal`.
3. Remove the `BTCPendingInfo`, restore the consumed UTXOs to the bridge's UTXO pool (or return them), and transfer the locked nBTC back to the user (with `lost_found` fallback on transfer failure).

### Proof of Concept

1. Alice calls `ft_transfer_call` on nBTC → bridge receives tokens → `create_btc_pending_info` creates a `WithdrawOriginal / PendingSign` record.
2. Alice calls `sign_btc_transaction`. MPC is unavailable; `sign_btc_transaction_callback` returns `false`. State is unchanged.
3. NEAR Chain Signatures performs a key rotation; `key_version` increments. Alice's PSBT is now permanently unsignable.
4. Alice retries `sign_btc_transaction` with the new `key_version` — the PSBT hash changes, making the stored PSBT invalid.
5. Alice attempts no other recovery — there is none. Her nBTC is locked in the bridge.
6. DAO attempts `cancel_withdraw(alice_pending_id, ...)` — panics: `"Not pending verify stage"` (from `assert_withdraw_original_pending_verify_tx`).
7. Alice's nBTC remains permanently locked. [10](#0-9) [11](#0-10)
