### Title
Stub `validatePerasCert` Unconditionally Accepts Any Peer-Supplied Certificate, Enabling Forged Weight Boost and Forced Chain-Selection Switch — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production Peras certificate ingest path wires `validatePerasCert` — a stub that unconditionally returns `Right` for every certificate — as the sole validation gate for certificates received from untrusted peers. Because no cryptographic, quorum, or structural check is performed, any peer can craft a `PerasCert` targeting any block in the VolatileDB, have it accepted and stored in the `PerasCertDB`, and trigger a chain-selection re-run that may cause the node to abandon its canonical chain in favour of a lighter fork that now appears heavier due to the injected weight boost.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub wired into production**

The universal `BlockSupportsPeras` instance defines `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This function performs **zero** checks: no BLS aggregate-signature verification, no quorum threshold check, no committee-membership check, no round-number bounds check. It accepts every `PerasCert` and stamps it with the full protocol-defined `perasWeight`.

**Production wiring — the stub is the live validation function for peer-supplied certs**

`makePerasCertPoolWriterFromChainDB` — explicitly documented as the production writer — passes `validatePerasCert mkPerasParams` directly to `processCerts`:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

`processCerts` maps `validateCert` over every new certificate; if all pass (they always do), each is timestamped and forwarded to `ChainDB.addPerasCertAsync`: [3](#0-2) 

**Chain-selection consequence**

`addPerasCertAsync` enqueues a `ChainSelAddPerasCert` event. `chainSelSync` processes it: after storing the cert in `PerasCertDB`, it calls `chainSelectionForBlock` for the boosted block: [4](#0-3) 

Chain selection computes `wsvTotalWeight` as `BlockNo + weightBoostOfFragment`, where `weightBoostOfFragment` sums all `PerasWeight` entries from the `PerasWeightSnapshot` for every block on the candidate fragment: [5](#0-4) 

A forged certificate injects `perasWeight params` (e.g. 15 on mainnet parameters) of artificial weight onto any attacker-chosen block. If that block is the tip of a fork that was previously lighter than the current selection, the node switches to the fork.

**Analog to the external report**

The NounsDAO bug: an unbounded attacker-controlled input (long `reason` string) inflates a measurement (gas used) that drives a critical calculation (ETH refund), draining the contract.

Here: an unvalidated attacker-controlled input (forged `PerasCert`) inflates a measurement (`wsvWeightBoost`) that drives a critical calculation (chain selection), causing the node to switch to a non-canonical chain.

---

### Impact Explanation

**Critical — bypass of certificate verification enabling unauthorized chain-selection manipulation.**

An unprivileged peer with a single TCP connection can:

1. Observe the VolatileDB contents via the existing ChainSync mini-protocol to identify a block on a weaker fork.
2. Craft a `PerasCert { pcCertRound = r, pcCertBoostedBlock = weakForkTip }` with an arbitrary round number.
3. Deliver it via the Peras certificate diffusion mini-protocol.
4. The node accepts it without any cryptographic check, stores it, and re-runs chain selection.
5. If `weakForkTip`'s total weight now exceeds the current selection's total weight, the node switches forks — accepting a chain that honest nodes have not certified.

This violates the core Peras safety property: only blocks that have received a genuine quorum of committee votes should receive a weight boost. The attack requires no stake, no keys, and no prior relationship with the target node.

---

### Likelihood Explanation

**High.** The Peras certificate diffusion mini-protocol is an externally reachable network endpoint. Any peer that can connect to the node can send certificates. The stub is the only validation function in the production path (confirmed by the two call sites in `PerasCert.hs`), and the `TODO` comment acknowledges the gap. No secondary defence (rate-limiting, stake check, signature check) exists at the consensus layer for this path.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:

1. Verifies the aggregate BLS vote signature against the claimed committee public keys.
2. Checks that the total stake of the signers meets the quorum threshold (`stakeAboveThorum` / `PerasQuorumStakeThreshold`).
3. Validates the round number is within the acceptable window.
4. Confirms the boosted block hash is a known, valid block.

Until the real implementation is ready, the production writer `makePerasCertPoolWriterFromChainDB` must not be deployed with Peras enabled, or must gate certificate acceptance behind a feature flag that is off by default.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do

  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
