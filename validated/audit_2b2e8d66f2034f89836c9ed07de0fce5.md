### Title
Missing Cryptographic Signature Verification in Peras Vote Validation Allows Any Peer to Forge Votes and Manufacture Quorum Certificates - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasVote` implementation performs no cryptographic signature check. The `PerasVote blk` data type carries no signature field, and the validation function only looks up the voter ID in the stake distribution. Any unprivileged peer can craft a `PerasVote` message claiming to be any committee member, have it accepted as valid, and have its stake counted toward quorum. By sending enough such forged votes, a peer can manufacture a Peras certificate for an arbitrary block.

---

### Finding Description

The `PerasVote blk` data type is defined with only three fields — round number, block point, and voter ID — and carries no cryptographic signature: [1](#0-0) 

The `validatePerasVote` implementation (the universal `StandardHash blk` instance) only checks whether the claimed voter ID appears in the stake distribution. It performs no signature verification, no VRF eligibility proof, and no committee membership proof: [2](#0-1) 

The TODO comment at the call site in `implAddVote` confirms this is the active production path: [3](#0-2) 

Inbound votes from peers are processed by `processVotes`, which calls `validateVote` (bound to `validatePerasVote`) inside an `atomically` block, then calls `addVote` for each vote that passes: [4](#0-3) 

The production writer `makePerasVotePoolWriterFromChainDB` wires `validatePerasVote` directly as the validator and `ChainDB.addPerasVoteWithAsyncCertHandling` as the adder: [5](#0-4) 

Once enough forged votes accumulate in `implAddVote`, `updatePerasRoundVoteStates` fires and a certificate is forged: [6](#0-5) 

The `PerasVoteId` deduplication guard (`pvdsVoteIds`) only prevents the same `(voterId, roundNo)` pair from being counted twice. It does not prevent an attacker from impersonating *different* committee members — one forged vote per committee member ID is sufficient to reach quorum.

---

### Impact Explanation

An unprivileged peer can send a batch of `PerasVote` messages, each claiming a different `PerasVoterId` drawn from the public stake distribution. Each vote passes `validatePerasVote` (stake lookup succeeds, no signature required), is inserted into the `PerasVoteDB`, and its stake is accumulated. When the sum of claimed stakes crosses the quorum threshold, `forgePerasCert` is called and a `ValidatedPerasCert` is produced for an attacker-chosen block. This certificate is then used by the chain-selection logic to boost that block's weight, causing honest nodes to prefer the attacker's chain. This is a **Critical** bypass of Peras voting/certificate checks enabling unauthorized certificate acceptance and chain-selection manipulation.

---

### Likelihood Explanation

The stake distribution (`PerasVoteStakeDistr`) is derived from the public ledger state and is known to all participants. The `PerasVoterId` values are public key hashes, also publicly observable. Constructing a valid-looking `PerasVote` requires only knowing a voter ID that appears in the distribution — no private key material is needed. The attack is trivially executable by any connected peer.

---

### Recommendation

1. Add a `pvVoteSignature` field (or equivalent VRF/eligibility proof) to `PerasVote blk`.
2. Implement `validatePerasVote` to verify the cryptographic signature over `(pvVoteRound, pvVoteBlock)` using the public key corresponding to `pvVoteVoterId`, as the `WFALS` committee implementation already does for its own vote type via `implVerifyVote` / `checkVoteSignature`.
3. Track the referenced issue (`cardano-peras/issues/120`) as a security-critical blocker before any Peras-enabled deployment. [7](#0-6) 

---

### Proof of Concept

```
1. Observe the public stake distribution; extract N voter IDs whose combined
   stake exceeds the quorum threshold.

2. For each voter ID V_i, construct:
     PerasVote { pvVoteRound = R, pvVoteBlock = adversarialBlock, pvVoteVoterId = V_i }
   No signing key is required.

3. Send all N votes in a single batch to the target node via the Peras vote
   object-diffusion mini-protocol.

4. processVotes atomically checks alreadyInDb (empty for fresh round R) and
   calls validatePerasVote for each vote. Each passes because V_i is in the
   stake distribution.

5. Each vote is added via implAddVote. updatePerasRoundVoteStates accumulates
   stake. After the N-th vote, stakeAboveThreshold returns True, forgePerasCert
   is called, and a ValidatedPerasCert for adversarialBlock is stored.

6. Chain selection now treats adversarialBlock as boosted by a Peras certificate,
   causing the node to prefer the adversary's chain.
```

```haskell
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
```
