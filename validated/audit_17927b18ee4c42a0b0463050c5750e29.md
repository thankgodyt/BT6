### Title
Hardcoded `boundX = 3` in `taylorExpCmpFirstNonLower` Produces Incorrect Local Sortition Seat Counts When `lambda > ln(3)` - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/LS.hs`)

---

### Summary

`localSortitionNumSeats` calls `taylorExpCmpFirstNonLower` with a hardcoded `boundX = 3`. The function's own contract requires `boundX = e^{|x|}` for correct error bounds. The `x` argument passed is `-lambda`, so the correct bound is `e^lambda`. When `lambda > ln(3) ≈ 1.099` — a realistic condition for any non-persistent voter holding more than roughly `1.1 / numNonPersistentVoters` of the non-persistent stake — the error term is underestimated, the Taylor comparison terminates prematurely with a wrong result, and the voter is assigned an incorrect number of non-persistent seats. Because both the forger path (`implCheckShouldVote`) and the verifier path (`implVerifyVote`, `implVerifyCert`) call the same function with the same wrong constant, the forger may self-assign a seat count that the verifier independently recomputes as a different value, or both may agree on a seat count that diverges from the mathematically correct one.

---

### Finding Description

**Root cause — inconsistent precision rule between the mathematical specification and the implementation:**

`taylorExpCmpFirstNonLower` is a Taylor-series-based comparison of `e^x` against a list of thresholds. Its error bound at each step is:

```
errorTerm = abs(err' * boundX)
```

The comment at line 121 is explicit:

> `-- IMPORTANT: boundX must be e^{|x|} for correct error bounds (see taylorExpCmp).`

The call site in `localSortitionNumSeats` passes `x = -lambda` and `boundX = 3`:

```haskell
-- LS.hs lines 94-99
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      3          -- ← hardcoded; should be exp lambda
      orders
      (-lambda)
```

`lambda` is computed as:

```haskell
-- LS.hs lines 65-70
lambda :: FixedPoint
lambda =
  fromRational $
    fromIntegral numNonPersistentVoters
      * voterStake
      / totalNonPersistentStake
```

`lambda` is the expected number of non-persistent seats for this voter under the Poisson model. It is unbounded above 1. For example, with `numNonPersistentVoters = 100` and `voterStake / totalNonPersistentStake = 0.02`, `lambda = 2.0` and `e^lambda ≈ 7.39`. The hardcoded `3` is less than half the correct bound.

**Consequence — underestimated error term:**

When `boundX < e^lambda`, `errorTerm` is too small. Inside `decideOne`:

```haskell
-- LS.hs lines 165-169
| cmp >= acc' + errorTerm = Stop   -- declared "certainly above" too early
| cmp < acc' - errorTerm = Below … -- declared "certainly below" too early
| otherwise = decideOne …          -- uncertain region is artificially narrow
```

The algorithm exits the "uncertain" region prematurely. A threshold that is genuinely within the true error interval of `e^{-lambda}` may be declared "certainly above" or "certainly below", returning the wrong index — i.e., the wrong number of seats.

**The inconsistency is structural, not accidental.** The `3` was copied from the Ledger's `checkLeaderNatValue`, where `|x| = sigma * |ln(1-f)| ≤ 0.05` for typical active-slot coefficients, making `e^{|x|} ≈ 1.05` and `3` a safe overestimate. For local sortition `lambda` has no such small upper bound, so the same constant is an underestimate in the general case. The developers themselves flagged this with a TODO:

```haskell
-- LS.hs lines 86-92
-- TODO(peras): evaluate whether the limit used below (3) makes sense in
-- this context. One possible starting point would be to understand why
-- @checkLeaderNatValue@ (in Ledger) also uses 3 as its own limit when
-- computing slot leadership proofs.
--
-- Tracked by this issue:
-- https://github.com/tweag/cardano-peras/issues/234
```

**Affected call sites:**

`localSortitionNumSeats` is called in three places in `WFALS.hs`:

1. `implCheckShouldVote` (line 286) — forger self-checks eligibility
2. `implVerifyVote` (line 376) — verifier checks a received vote
3. `implVerifyCert` (line 529) — verifier checks a received certificate

All three use the same wrong constant, so the forger and verifier agree on the wrong seat count. The divergence is between the computed seat count and the mathematically correct one.

---

### Impact Explanation

`LocalSortitionNumSeats` directly controls two security-critical decisions:

1. **Eligibility gate**: `nonZero numSeats` at lines 291 and 381 determines whether a non-persistent voter is admitted at all. An incorrect seat count of 0 when the correct count is ≥ 1 silently rejects a legitimate voter; an incorrect count of ≥ 1 when the correct count is 0 admits an ineligible voter, bypassing the Peras non-persistent committee eligibility check.

2. **Vote weight**: `implEligiblePartyVoteWeight` (lines 421–432) multiplies `unLocalSortitionNumSeats` directly into the voter's `VoteWeight`. An inflated seat count grants a voter more voting power than their stake entitles them to, weakening the quorum threshold and potentially allowing a minority-stake coalition to forge a valid Peras certificate.

This maps to the allowed impact: **bypass of Peras voting or certificate checks that enables unauthorized vote or certificate acceptance**.

---

### Likelihood Explanation

The condition `lambda > ln(3) ≈ 1.099` is reached whenever:

```
numNonPersistentVoters * voterStake / totalNonPersistentStake > 1.099
```

With a committee of 100 non-persistent candidates, any voter holding more than ~1.1% of the non-persistent stake triggers the bug. This is a normal operating condition, not an edge case. The attacker-controlled entry path is a crafted `WFALSNonPersistentVote` or `WFALSCert` submitted over the network; the verifier recomputes `localSortitionNumSeats` from the on-chain stake distribution and the VRF output included in the message, both of which are attacker-supplied.

---

### Recommendation

Replace the hardcoded `3` with the correct bound. Since `FixedPoint` supports `exp` via `Cardano.Ledger.BaseTypes`, the fix is:

```haskell
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      (exp lambda)   -- correct: e^{|x|} = e^lambda
      orders
      (-lambda)
```

If `exp` on `FixedPoint` is unavailable or too expensive, a conservative integer ceiling `ceiling (exp (toRational lambda))` cast back to `FixedPoint` is also correct and safe.

---

### Proof of Concept

Consider a committee with:
- `numNonPersistentVoters = 100`
- `voterStake / totalNonPersistentStake = 0.02`
- `lambda = 2.0`, `e^lambda ≈ 7.389`

At the boundary where `e^{-lambda} ≈ 0.135` lies between two consecutive `orders` thresholds, the true error interval has width proportional to `e^lambda ≈ 7.39`, but the computed interval uses `3`. A threshold within `(3, 7.39)` multiples of the next Taylor term from `e^{-lambda}` will be misclassified. Concretely:

- Forger computes `numSeats = k` (wrong, due to premature Stop)
- Correct value is `numSeats = k-1` or `k+1`
- Verifier recomputes the same wrong `k` (same bug), so the vote passes signature and VRF checks but carries an incorrect seat count and vote weight
- A voter with `lambda = 2` and wrong `numSeats = 2` instead of correct `numSeats = 1` has double the intended voting power [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7)
