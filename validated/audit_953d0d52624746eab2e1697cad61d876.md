I need to look more carefully at how `locked_tokens` is used in the finalization flow and what happens to pending transfers after `migrate_deployed_token`.

### Title
`migrate_deployed_token` Orphans `locked_tokens` Entries, Permanently Breaking Escrow Accounting for the New Token ID — (`File: near/omni-bridge/src/lib.rs`)

---

### Summary

`migrate_deployed_token` updates every token-ID mapping in the bridge state except `locked_tokens`. After migration the old entries are permanently orphaned under `old_token`, and the new key `(chain_kind, new_token)` never exists, so every subsequent lock/unlock call for the migrated token silently no-ops. The `ERR_INSUFFICIENT_LOCKED_TOKENS` safety invariant is bypassed for all future transfers of the migrated token.

---

### Finding Description

`migrate_deployed_token` (lines 1604–1664, `near/omni-bridge/src/lib.rs`) updates five data structures:

- `deployed_tokens` — removes `old_token`, inserts `new_token`
- `deployed_tokens_v2` — removes `old_token`, inserts `new_token → origin_chain`
- `token_id_to_address` — removes `(origin_chain, old_token)`, inserts `(origin_chain, new_token)`
- `token_address_to_id` — overwrites `origin_address → new_token`
- `migrated_tokens` — inserts `old_token → new_token`

It does **not** touch `locked_tokens : LookupMap<(ChainKind, AccountId), u128>`. [1](#0-0) 

`locked_tokens` is the bridge's escrow ledger: it records how many tokens of a given NEAR token ID are currently locked on each foreign chain. The locking and unlocking primitives in `token_lock.rs` both guard on key existence:

```rust

    return LockAction::Unchanged;   // silently skips if key absent

```

```rust

let Some(available) = self.locked_tokens.get(&key) else {
    return LockAction::Unchanged;   // silently skips, bypassing the require! below
};
require!(available >= amount, TokenLockError::InsufficientLockedTokens.as_ref());
``` [2](#0-1) 

After `migrate_deployed_token`:

1. Every `(chain_kind, old_token)` entry in `locked_tokens` is permanently orphaned — it can never be decremented because all routing now resolves to `new_token`.
2. `(chain_kind, new_token)` does not exist in `locked_tokens`, so `lock_tokens_if_needed` and `unlock_tokens_if_needed` both return `LockAction::Unchanged` for every future call involving `new_token`. [3](#0-2) 

`get_token_origin_chain` now returns the origin chain for `new_token` (via `deployed_tokens_v2`), so the `if self.get_token_origin_chain(token_id) == chain_kind` guard in `lock_tokens_if_needed` / `unlock_tokens_if_needed` does not short-circuit the call — the call reaches `lock_tokens` / `unlock_tokens`, which then silently no-ops because the key is absent. [4](#0-3) 

---

### Impact Explanation

**Orphaned locked_tokens (permanent accounting error):** Any amount previously locked under `(chain_kind, old_token)` is frozen forever. The bridge's view of how many tokens are outstanding on each foreign chain is permanently inflated for `old_token`.

**Bypassed `ERR_INSUFFICIENT_LOCKED_TOKENS` for `new_token`:** Because `(chain_kind, new_token)` never exists, every `unlock_tokens` call for `new_token` returns `Unchanged` without executing the `require!(available >= amount, ...)` guard. The invariant that prevents releasing more tokens than were locked is gone for the migrated token. A relayer presenting a valid proof for a `new_token` transfer can finalize it even when the bridge's escrow ledger shows zero locked tokens, breaking the accounting invariant that backs cross-chain token supply.

This matches the "escrow mis-accounting that changes protocol balances" impact class.

---

### Likelihood Explanation

Token migration is an explicitly supported, production-ready feature: the `migrated_tokens` map, the `swap_migrated_token` function, and the `MigrateTokenEvent` log all exist in the current codebase. Any DAO-initiated call to `migrate_deployed_token` for a token that has non-zero `locked_tokens` entries triggers the issue. No attacker action is required beyond normal bridge usage after the migration. [5](#0-4) 

---

### Recommendation

Inside `migrate_deployed_token`, after updating the token-ID mappings, iterate over all `ChainKind` variants and migrate every existing `locked_tokens` entry from `old_token` to `new_token`:

```rust
for chain_kind in ChainKind::all() {
    let old_key = (chain_kind, old_token.clone());
    if let Some(amount) = self.locked_tokens.remove(&old_key) {
        self.locked_tokens.insert(&(chain_kind, new_token.clone()), &amount);
    }
}
```

Alternatively, add a dedicated `migrate_locked_tokens(old_token, new_token, chain_kinds)` admin function callable immediately after `migrate_deployed_token`, and document that it must be called atomically as part of any token migration.

### Proof of Concept

1. Token `eth-usdc.factory.bridge.near` (`old_token`) is deployed; the bridge has `locked_tokens[(Sol, old_token)] = 500_000` (500 k units locked on Solana).
2. DAO calls `migrate_deployed_token(Eth, old_token, new-usdc.omni.near)`.
3. State after migration:
   - `locked_tokens[(Sol, old_token)] = 500_000` — orphaned, unreachable.
   - `locked_tokens[(Sol, new-usdc.omni.near)]` — **does not exist**.
4. A user calls `ft_on_transfer` sending `new-usdc.omni.near` tokens to bridge to Solana. `lock_tokens_if_needed(Sol, new-usdc.omni.near, 1_000)` hits `lock_tokens`, finds no key, returns `Unchanged`. No lock is recorded.
5. A relayer submits a valid Solana proof and calls `fin_transfer`. `unlock_tokens_if_needed(Sol, new-usdc.omni.near, 1_000)` hits `unlock_tokens`, finds no key, returns `Unchanged` — the `require!(available >= amount)` check is never reached. Tokens are released on NEAR with zero escrow backing.
6. The bridge's escrow ledger now permanently misrepresents the outstanding cross-chain supply for this token. [6](#0-5) [2](#0-1)

                .is_none(),

impl Contract {
    fn lock_tokens(
        &mut self,
        chain_kind: ChainKind,
        token_id: &AccountId,
        amount: u128,
    ) -> LockAction {
        let key = (chain_kind, token_id.clone());
        let Some(current_amount) = self.locked_tokens.get(&key) else {
            return LockAction::Unchanged;
        };
        let new_amount = current_amount
            .checked_add(amount)
            .near_expect(TokenLockError::LockedTokensOverflow);

        self.locked_tokens.insert(&key, &new_amount);

        LockAction::Locked {
            chain_kind,
            token_id: token_id.clone(),
            amount,
        }
    }

    fn unlock_tokens(
        &mut self,
        chain_kind: ChainKind,
        token_id: &AccountId,
        amount: u128,
    ) -> LockAction {
        let key = (chain_kind, token_id.clone());
        let Some(available) = self.locked_tokens.get(&key) else {
            return LockAction::Unchanged;
        };
        require!(
            available >= amount,
            TokenLockError::InsufficientLockedTokens.as_ref()
        );

        let remaining = available - amount;
        self.locked_tokens.insert(&key, &remaining);

        LockAction::Unlocked {
            chain_kind,
            token_id: token_id.clone(),
            amount,
        }
    }
