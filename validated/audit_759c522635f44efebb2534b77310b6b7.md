### Title
Silent nBTC Inflation via Unregistered Recipient in `safe_mint` — (File: `contracts/nbtc/src/lib.rs`)

### Summary

`safe_mint` unconditionally deposits `amount` nBTC tokens into the bridge contract's own token balance **before** checking whether the intended recipient has a registered NEP-141 storage account. When the recipient is unregistered, the function silently returns `U128(0)` without reverting the deposit, leaving the minted tokens permanently stranded in the bridge's nBTC balance and inflating total supply beyond the BTC-backed amount.

### Finding Description

In `contracts/nbtc/src/lib.rs`, the `safe_mint` function executes as follows:

```rust
// line 112
self.token.internal_deposit(&self.bridge_id, amount.into());

// line 114-116
if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0));
}
```

`internal_deposit` to `self.bridge_id` is a **committed state change** in the nBTC contract. It executes and persists regardless of what happens next. Only after that write does the code check whether `account_id` is registered. If the account is absent, the function returns the synchronous value `U128(0)` — not a panic, not a revert — leaving `amount` tokens credited to the bridge's own nBTC balance with no transfer to the user and no recovery path.

This is the direct analog of the reported `IpNFT.sol` pattern: a per-address state entry (`royaltyVaults[recipient]`) is assumed to exist but is never created on demand, so funds flow to a dead end (zero address there; the bridge's own stranded balance here).

The `mint_inner` helper used by the standard `mint` path auto-registers accounts:

```rust
// line 342-345
fn mint_inner(&mut self, account_id: &AccountId, amount: U128) {
    if self.token.accounts.get(account_id).is_none() {
        self.token.internal_register_account(account_id);
    }
    self.token.internal_deposit(account_id, amount.into());
```

`safe_mint` deliberately omits this auto-registration (the caller is expected to pre-register via attached NEAR), but it does **not** guard the `internal_deposit` call behind the registration check. The deposit to `bridge_id` fires unconditionally.

### Impact Explanation

**Scenario A — bridge callback panics on `U128(0)` return:**
NEAR's cross-contract call model commits the nBTC contract's state change (bridge balance +`amount`) independently of the bridge callback's outcome. If the bridge callback panics, only the bridge's own state is rolled back; the nBTC contract's `internal_deposit` to `bridge_id` is already finalized. The UTXO is not marked verified (bridge state rolled back), so the user can retry. But the bridge now holds `amount` extra nBTC tokens not backed by any BTC — a permanent supply inflation / unauthorized mint.

**Scenario B — bridge callback treats `U128(0)` as success:**
The UTXO is marked verified (BTC consumed), the bridge holds `amount` extra nBTC, and the user receives nothing. The user's BTC is permanently lost with no lost-and-found entry and no refund path.

Both scenarios result in total nBTC supply exceeding the BTC-backed amount, satisfying the "unauthorized minting" and "significant loss of user funds" impact criteria.

### Likelihood Explanation

The `safe_deposit` flow (used by Omni Bridge and similar integrations) requires the relayer to pre-register the recipient's storage. Any gap — a new account, a failed storage registration, or a recipient account that unregistered — leaves the recipient absent from `token.accounts`. Because `safe_mint` does not enforce registration before the deposit write, this condition is reachable by any unprivileged user whose NEAR account is not yet registered in the nBTC token at the moment the relayer submits `verify_deposit_v2` with `safe_deposit`.

### Recommendation

Move the registration check **before** the `internal_deposit` call, or mirror `mint_inner` by auto-registering the account inside `safe_mint`:

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "...");

    // Guard: fail early before any state change
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));
    }

    // Only deposit after confirming the recipient can receive
    self.token.internal_deposit(&self.bridge_id, amount.into());
    ...
}
```

Alternatively, auto-register the account (funded by the attached NEAR deposit the caller is already required to provide) before the `internal_deposit`, consistent with how `mint_inner` handles unregistered accounts.

### Proof of Concept

1. Alice sends 0.01 BTC to her deposit address with a `safe_deposit` message naming `bob.near` as `recipient_id`.
2. `bob.near` has never called `storage_deposit` on the nBTC contract and is absent from `token.accounts`.
3. Relayer calls `verify_deposit_v2`; light-client verification succeeds; bridge calls `safe_mint(bob.near, 1_000_000, None)`.
4. Inside `safe_mint`: `self.token.internal_deposit(&self.bridge_id, 1_000_000)` executes and commits — bridge's nBTC balance is now +1,000,000 satoshis.
5. `self.token.accounts.get(&bob.near)` returns `None`; function returns `U128(0)`.
6. Bridge callback receives `0`. Depending on callback logic:
   - **Panic path**: bridge state rolled back, UTXO not verified, but nBTC supply is permanently inflated by 1,000,000 sat.
   - **Success path**: UTXO marked verified, Bob's BTC is consumed, Bob has 0 nBTC, bridge holds 1,000,000 extra nBTC.
7. In either case, 1,000,000 sat of nBTC exist in the bridge's account with no corresponding BTC backing, violating the 1:1 peg invariant.
