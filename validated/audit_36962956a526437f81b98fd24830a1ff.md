### Title
Peras Certificate Validation Stub Unconditionally Accepts Any Peer-Supplied Certificate, Permanently Corrupting `pcdsLatestCertSeen` Voting State via Irreversible Ratchet — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs` / `File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Storage/PerasCertDB/Impl.hs`)

---

### Summary

The global `BlockSupportsPeras` instance's `validatePerasCert` is a stub that unconditionally returns `Right` for every certificate it receives. Any unprivileged peer can therefore inject an arbitrary `PerasCert` (e.g., one boosting a non-canonical block, or one carrying a far-future round number) through the Peras certificate diffusion mini-protocol. Once accepted, the certificate is committed to `PerasCertDB` and its round number is ratcheted into `pcdsLatestCertSeen`. That field is a monotonically increasing, one-way state variable: it is never decremented, never reset, and — critically — is **not cleared by garbage collection**. There is no mechanism to revoke or "un-see" a fraudulently accepted certificate. This is the direct consensus analog of the "deposit with no withdrawal" pattern in the external report: the entry path (`addCert`) is open to any peer, and the resulting state (`pcdsLatestCertSeen`) is permanently locked.

---

### Finding Description

**Root cause 1 — stub validation always returns `Right`**

The universal `BlockSupportsPeras` instance (used for all block types until Peras-specific plumbing is in place) implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

Every certificate, regardless of its content, is wrapped in `ValidatedPerasCert` and returned as valid. No signature, committee membership, round-number range, or boosted-block reachability check is performed.

**Root cause 2 — `implAddCert` also carries a TODO for non-trivial validation**

The `PerasCertDB` implementation's `implAddCert` is similarly marked as incomplete:

```haskell
-- TODO: we will need to update this method with non-trivial validation logic
-- see https://github.com/tweag/cardano-peras/issues/120
implAddCert ...
``` [2](#0-1) 

**Root cause 3 — `pcdsLatestCertSeen` is a one-way ratchet with no GC reset**

`implAddCert` updates `pcdsLatestCertSeen` to whichever certificate carries the highest round number seen so far:

```haskell
pcdsLatestCertSeen' = case pcdsLatestCertSeen pcds of
  Nothing -> Just cert
  Just prev
    | getPerasCertRound cert > getPerasCertRound prev -> Just cert
    | otherwise -> Just prev
``` [3](#0-2) 

`implGarbageCollect` filters `pcdsCertsByTicket` and rebuilds `pcdsCertIds`, but `pcdsLatestCertSeen` is passed through unchanged — it is never cleared or rolled back: [4](#0-3) 

The API documentation confirms the security relevance of this field:

> "This field impacts voting directly because having seen a certificate is a precondition for voting in any round except for the very first one (at origin)." [5](#0-4) 

**Root cause 4 — the production inbound path uses the stub**

Both `makePerasCertPoolWriterFromChainDB` (the live ChainDB path) and `makePerasCertPoolWriterFromCertDB` call `validatePerasCert mkPerasParams` directly: [6](#0-5) 

`processCerts` then adds every cert that passes this stub check to the database: [7](#0-6)

### Impact Explanation

**Chain selection weight corruption (High):** `getWeightSnapshot` derives Peras boost weights directly from `pcdsCertsByTicket`. A fraudulent certificate boosting an attacker-controlled block grants that block extra chain-selection weight, potentially causing an honest node to prefer a non-canonical chain over the honest chain. [8](#0-7) 

**Permanent voting-state corruption (Critical — Peras certificate check bypass):** A certificate with a far-future round number (e.g., `maxBound :: PerasRoundNo`) is accepted, ratchets `pcdsLatestCertSeen` to that round, and is never undone by GC. Because `latestCertSeen` is a precondition for voting in all subsequent rounds, the node's voting eligibility is permanently distorted. The `PerasVotingView` consumed by the voting rules carries this corrupted value: [9](#0-8) 

The combination — unconditional acceptance of any certificate plus an irreversible state ratchet — is the direct analog of the "deposit with no withdrawal" pattern: the entry path is open to any peer, and the resulting state cannot be recovered.

---

### Likelihood Explanation

Any node participating in the Peras certificate diffusion mini-protocol is reachable. An unprivileged peer needs only to send a single well-formed `PerasCert` message (correct serialization, arbitrary content) to trigger the full attack path. No stake, no keys, no prior relationship with the target node is required. The `processCerts` function is called on every inbound batch of certificates from a peer. [7](#0-6) 

---

### Recommendation

1. **Replace the `validatePerasCert` stub** with a real implementation that verifies committee membership, cryptographic signatures, round-number bounds, and boosted-block reachability before accepting any certificate. [1](#0-0) 

2. **Extend `implGarbageCollect`** to also clear or update `pcdsLatestCertSeen` when the certificate it references is garbage-collected, so that the voting-state ratchet cannot be permanently locked by a fraudulent certificate. [4](#0-3) 

3. **Add an equivocation check** in `implAddCert` (currently only enforced in the test model's precondition) to reject certificates for a round that already has a certificate boosting a different block. [2](#0-1)

```haskell
processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
