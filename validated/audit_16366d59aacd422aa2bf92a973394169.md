### Title
Missing Post-Normalization Amount Validation in `update_transfer_fee` Causes Permanent Token Lock — (File: near/omni-bridge/src/lib.rs)

### Summary

`update_transfer_fee` validates only that `fee.fee < transfer.message.amount` (raw NEAR-side units) but never checks that `normalize_amount(amount − fee, decimals) > 0`. Because normalization (decimal down-scaling for the destination chain) is the implicit "fee deduction" step, a sender who raises their fee close to the transfer amount can silently reduce the normalized recipient amount to zero. `sign_transfer` then always panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`, and because fees can only be raised (never lowered), the transfer is permanently bricked and the locked/burned tokens are irrecoverable.

### Finding Description

`update_transfer_fee` enforces a single invariant on the token fee: [1](#0-0) 

This check operates on the raw NEAR-side amount. It does not account for the decimal normalization that `sign_transfer` applies before producing the on-chain payload: [2](#0-1) 

`normalize_amount` performs floor division by `10^(origin_decimals − decimals)`: [3](#0-2) 

For a token whose NEAR representation has 24 decimals and whose Ethereum representation has 18 decimals, the divisor is `10^6`. A sender who sets `fee = amount − 1` (passes the `fee < amount` guard) leaves `amount_without_fee = 1`. After normalization: `1 / 10^6 = 0`. `sign_transfer` panics unconditionally.

The fee ratchet in `update_transfer_fee` makes this irreversible: [1](#0-0) 

`fee.fee >= current_fee.fee` means the fee can never be reduced. There is no public cancel or refund entry point; `remove_transfer_message` is only reachable through `claim_fee_callback` (requires a successful destination-chain finalization) or `sign_transfer_callback` (requires a successful MPC signing), neither of which can complete when `sign_transfer` always panics.

The same gap exists in `init_transfer` itself — the only guard is `fee.fee < transfer_message.amount` with no normalization pre-check: [4](#0-3) 

### Impact Explanation

Tokens are burned or locked in `init_transfer_internal` before any normalization check is ever reached: [5](#0-4) 

Once locked/burned, the only recovery paths (`claim_fee_callback`, `sign_transfer_callback`) both require a successful `sign_transfer`, which will always panic. The user's bridged assets are permanently frozen inside the NEAR omni-bridge contract. This matches the **Critical** impact class: permanent freezing of bridged funds.

### Likelihood Explanation

Any NEAR → foreign-chain transfer where `origin_decimals > decimals` (e.g., NEAR 24-decimal token → Ethereum 18-decimal token, a standard and documented configuration) is susceptible. A sender who raises their fee to `amount − k` where `k < 10^(origin_decimals − decimals)` triggers the condition. This is reachable by any unprivileged bridge user calling `ft_transfer_call` → `ft_on_transfer` → `init_transfer`, followed by `update_transfer_fee`. No special role or privilege is required.

### Recommendation

In both `update_transfer_fee` and `init_transfer`, after computing `amount_without_fee`, look up the destination token's `Decimals` and assert that `normalize_amount(amount_without_fee, decimals) > 0` before accepting the operation. Concretely, in `update_transfer_fee`:

```rust
// After updating transfer.message.fee, before persisting:
let token_address = self.get_token_address(
    transfer.message.get_destination_chain(),
    self.get_token_id(&transfer.message.token),
).near_expect(BridgeError::TokenNotFound);
let decimals = self.token_decimals.get(&token_address)
    .near_expect(BridgeError::TokenDecimalsNotFound);
let normalized = Self::normalize_amount(
    transfer.message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

Apply the same guard in `init_transfer` when the token's decimals are already registered.

### Proof of Concept

1. Token `tok.near` is registered with `origin_decimals = 24`, `decimals = 18` (Ethereum side). Divisor = `10^6`.
2. User calls `ft_transfer_call` with `amount = 2_000_000` (2 × 10^6 raw units) and `fee = 0`. Transfer is stored; `amount_without_fee = 2_000_000`; `normalize_amount(2_000_000, …) = 2` — valid.
3. User calls `update_transfer_fee` with `fee.fee = 1_999_999`. Guard: `1_999_999 < 2_000_000` ✓. Fee is persisted.
4. `amount_without_fee = 1`. `normalize_amount(1, {decimals:18, origin_decimals:24}) = 0`.
5. Any call to `sign_transfer` panics: `ERR_INVALID_AMOUNT_TO_TRANSFER`.
6. Fee cannot be lowered (`fee.fee >= current_fee.fee` enforced). No cancel path exists.
7. The 2_000_000 raw units of `tok.near` are permanently locked in the bridge. [6](#0-5) [7](#0-6) [3](#0-2)

    pub fn update_transfer_fee(&mut self, transfer_id: TransferId, fee: UpdateFee) {
        match fee {
            UpdateFee::Fee(fee) => {
                let mut transfer = self.get_transfer_message_storage(transfer_id);

                require!(
                    transfer.message.origin_transfer_id.is_none(),
                    BridgeError::UpdateFeeNotAllowedForTransfer.as_ref()
                );

                let current_fee = transfer.message.fee;
                require!(
                    fee.fee >= current_fee.fee && fee.fee < transfer.message.amount,
                    BridgeError::InvalidFee.as_ref()
                );

                require!(
                    fee.fee == current_fee.fee
                        || OmniAddress::Near(env::predecessor_account_id())
                            == transfer.message.sender,
                    BridgeError::SenderCanUpdateTokenFeeOnly.as_ref()
                );

                let diff_native_fee = fee
                    .native_fee
                    .0
                    .checked_sub(current_fee.native_fee.0)
                    .near_expect(BridgeError::LowerFee);

                require!(
                    NearToken::from_yoctonear(diff_native_fee) == env::attached_deposit(),
                    BridgeError::InvalidAttachedDeposit.as_ref()
                );

                transfer.message.fee = fee;
                self.insert_raw_transfer(transfer.message.clone(), transfer.owner);

                env::log_str(
                    &OmniBridgeEvent::UpdateFeeEvent {
                        transfer_message: transfer.message,
                    }
                    .to_log_string(),
                );
            }
            UpdateFee::Proof(_) => {
                env::panic_str(BridgeError::UnsupportedFeeUpdateProof.to_string().as_str())
            }
        }
    }

    pub fn sign_transfer(

            .token_decimals

            transfer_message
                .amount_without_fee()
                .near_expect(BridgeError::InvalidFee),
            decimals,
        );

        require!(
            amount_to_transfer > 0,
            BridgeError::InvalidAmountToTransfer.as_ref()
        );

    fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
        let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
        amount / (10_u128.pow(diff_decimals))
    }
