### Title
Peras Weight Snapshot Omitted in `checkPreferTheirsOverOurs`, Causing Incorrect Chain Selection Disconnection — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

`checkPreferTheirsOverOurs` in the ChainSync client evaluates whether a candidate chain is preferable to the local selection when a header lies beyond the forecast horizon. It calls `preferAnchoredCandidate` with a hardcoded `emptyPerasWeightSnapshot` instead of the live `PerasWeightSnapshot`. Every other chain-selection call site in the codebase passes the real weight snapshot. The omission means Peras certificate boosts are invisible to this check: a candidate chain that is heavier than the local chain solely because of Peras boosts (but is equal or shorter in raw block count) is incorrectly judged non-preferable, causing the node to throw `CandidateTooSparse` and disconnect from the peer. The node then stays on the lighter, non-canonical chain.

---

### Finding Description

**Inconsistent state in two code paths — the direct analog to the external report.**

In `chainSelectionForBlock` and `constructPreferableCandidates` (ChainSel.hs), the live `PerasWeightSnapshot` is fetched from `cdbPerasCertDB` and passed to every `preferAnchoredCandidate` / `compareAnchoredFragments` call:

```haskell
-- ChainSel.hs ~line 629-634
(invalid, curChain, weights) <-
  atomically $
    (,,)
      <$> ...
      <*> Query.getCurrentChain cdb
      <*> (forgetFingerprint <$> Query.getPerasWeightSnapshot cdb)
``` [1](#0-0) 

In `checkPreferTheirsOverOurs` (Client.hs), the same `preferAnchoredCandidate` function is called, but with `emptyPerasWeightSnapshot` hardcoded:

```haskell
-- Client.hs ~line 1838-1844
shouldSwitch $
  preferAnchoredCandidate
    (configBlock cfg)
    -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
    emptyPerasWeightSnapshot   -- ← always zero weight
    ourFrag
    theirFrag
``` [2](#0-1) 

`checkPreferTheirsOverOurs` is invoked inside `readLedgerStateHelper` whenever `forecastFor` returns `OutsideForecastRange` — i.e., whenever the next header from a peer is beyond the current forecast horizon:

```haskell
-- Client.hs ~line 1814-1817
case prj lst of
  Nothing -> do
    checkPreferTheirsOverOurs kis'
    retry
``` [3](#0-2) 

`preferAnchoredCandidate` itself short-circuits to pure block-count comparison when the weight snapshot is empty:

```haskell
-- AnchoredFragment.hs ~line 186-203
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      -- falls through to selectView / block-count comparison only
      ...
  | otherwise =
      -- uses weightedSelectView, which adds Peras boosts
      ...
``` [4](#0-3) 

The result: when Peras certificates are present and a peer's chain is heavier by weight but equal or shorter by block count, `checkPreferTheirsOverOurs` concludes `ShouldNotSwitch` and throws `CandidateTooSparse`, disconnecting from the peer. [5](#0-4) 

---

### Impact Explanation

A node running with Peras active will incorrectly disconnect from a peer that is advertising the canonical (heavier) chain whenever that chain's next header falls outside the forecast window. The node remains on its current lighter chain. This is a **chain-selection bug**: the node persistently prefers a non-canonical chain over the correct one, violating the Peras chain-selection invariant that the heaviest chain wins. In a network where Peras certificates are regularly produced, this can cause a node to diverge from the honest majority chain without any operator fault.

---

### Likelihood Explanation

The trigger condition — a header beyond the forecast horizon — occurs naturally during syncing, after large slot gaps, or when a peer is ahead of the local chain by more than one stability window. With Peras active and certificates being issued, a candidate chain that is heavier by boost but not by raw length is a normal expected state (e.g., a chain of length N with a certificate boost vs. a chain of length N+1 with no boost). No special privileges are required; any peer can present such a chain. The TODO comment in the code (`https://github.com/tweag/cardano-peras/issues/64`) confirms the developers have identified this as a known defect.

---

### Recommendation

Pass the live `PerasWeightSnapshot` to `preferAnchoredCandidate` inside `checkPreferTheirsOverOurs`, sourced from the same `ChainDB.getPerasWeightSnapshot` STM action used in `chainSelectionForBlock`. Alternatively, if the intent is to remove the check entirely (as the TODO suggests), do so and rely on the Genesis Density Disconnection logic to handle the sparse-chain case, ensuring Peras weight is consistently applied across all chain-comparison sites.

---

### Proof of Concept

1. Peras is active; a certificate boosts block `B` at slot `S` with weight `W > 1`.
2. Local chain: `[..., B]` — length `N`, total weight `N + W`.
3. Peer advertises a chain `[..., B, C]` — length `N+1`, total weight `N + W + 1` (heavier).
4. Header `C` is at slot `S + forecast_window + 1`, beyond the forecast horizon.
5. `readLedgerStateHelper` calls `checkPreferTheirsOverOurs`.
6. `preferAnchoredCandidate` is called with `emptyPerasWeightSnapshot`.
7. With empty weights, the suffix comparison reduces to block count: peer suffix length = 1, our suffix length = 0 → peer is longer → `ShouldSwitch` → no disconnect. *(This case passes.)*
8. Now consider: local chain `[..., B, D]` — length `N+1`, weight `N + W + 1`. Peer chain `[..., B, C]` — length `N+1`, weight `N + W + 1` (same). Peer has a *second* certificate boosting `C` with weight `W2`, making peer total weight `N + W + 1 + W2 > N + W + 1`.
9. With empty weights: suffix lengths equal → `ShouldNotSwitch` → `CandidateTooSparse` thrown → peer disconnected.
10. Node stays on the lighter chain `[..., B, D]` instead of switching to the heavier `[..., B, C]`. [2](#0-1) [4](#0-3) [1](#0-0)
