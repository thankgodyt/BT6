### Title
`execute_refund` Re-Execution Blocked by Default Pending-Sign Capacity Limit — (`contracts/satoshi-bridge/src/refund.rs`, `contracts/satoshi-bridge/src/bitcoin_utils/refund.rs`)

### Summary

`finalize_refund_with_psbt` unconditionally calls `require_pending_sign_capacity` before inserting a new refund `BTCPendingInfo`. When `execute_refund` is called a second time (the intended re-execution path after a consensus-branch change), the first pending info is still occupying the user's single default slot, causing the call to panic with `"Too many pending sign transactions"`. The only remedies are operator intervention (`set_pending_tx_limit`, DAO-only) or the user signing the now-invalid first tx to move it out of `btc_pending_sign_ids`.

**Step 2 — Second `execute_refund` (re-execution)**

`require_pending_sign_capacity` evaluates `pending_sign_count() < get_max_pending_sign_txs()`: [5](#0-4) 

Default limit is **1**: [6](#0-5) 

With the first pending info still in `btc_pending_sign_ids`, `pending_sign_count() == 1`, so `1 < 1` is false → **panic: "Too many pending sign transactions"**.

**Step 3 — No self-service escape**

The refund request is only removed by `verify_refund_finalize_callback`, which requires a confirmed on-chain tx — impossible if the first refund tx used the wrong consensus branch.

**The test itself acknowledges the problem** by calling the DAO-only `set_pending_tx_limit` to raise the cap to 2 before the second `execute_refund`: [8](#0-7) 

`set_pending_tx_limit` is gated behind `Role::DAO`: [9](#0-8)

### Impact Explanation

A user whose refund was built against a now-invalid consensus branch (e.g., Zcash NU6 → NU6.2 activation) cannot re-execute their refund without either:

- Operator/DAO raising their `pending_tx_limit` (privileged), or
- Signing the invalid first tx to move it from `btc_pending_sign_ids` to `btc_pending_verify_list` (non-obvious workaround; leaves a permanently unverifiable stale entry).

The refund is stuck in a state requiring operator intervention. User funds (the deposit UTXO) remain locked in the bridge until resolved. This matches **Medium — stuck bridge state requiring operator intervention**.

---

### Likelihood Explanation

On **Bitcoin**, the refund tx is deterministic (same inputs/outputs → same txid), so the second call hits `"pending info already exist"` at the same capacity barrier — same stuck outcome, different error message.

On **Zcash**, a consensus branch change (a scheduled, real network event) produces a different txid, making re-execution genuinely necessary and the capacity block directly reachable. The Zcash test suite explicitly exercises this path and works around it only via a privileged call.

Any user who calls `execute_refund` and does not immediately sign the resulting pending tx is in this state by default.

---

### Recommendation

Before calling `require_pending_sign_capacity` in `finalize_refund_with_psbt`, check whether the caller already has a **refund-type** pending info for the same UTXO (i.e., `refund_request.executed == true`). If so, remove the stale pending info first (freeing the slot) before inserting the new one. This makes re-execution self-service and removes the dependency on operator intervention or the non-obvious sign-then-re-execute workaround.

---

### Proof of Concept

```
1. execute_refund(utxo_key)          // btc_pending_sign_ids = {tx1}, executed=true
2. // do NOT sign tx1
3. execute_refund(utxo_key)          // panics: "Too many pending sign transactions"
                                     // (pending_sign_count=1, max=1)
```

The Zcash test `test_zcash_execute_refund_twice` reproduces this exactly — it only succeeds because it inserts a DAO call to `set_pending_tx_limit(max_pending=2)` between the two `execute_refund` calls. [10](#0-9)
