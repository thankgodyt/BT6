### Title
Unit Mismatch in Peras Quorum Stake Comparison Enables Certificate Forgery with Insufficient Stake - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

`stakeAboveThreshold` compares a `PerasVoteStake` value (which may carry absolute/unnormalized ledger stake) against `perasQuorumStakeThreshold` (a relative value, hardcoded to `3/4`). The code itself documents that normalization is missing. If the `PerasVoteStakeDistr` is populated with absolute lovelace amounts — the natural representation from the ledger's pool distribution — any single vote from any registered pool would satisfy the quorum check, allowing an adversary to forge a Peras certificate for an arbitrary block with a single vote.

### Finding Description

`stakeAboveThreshold` in `SupportsPeras.hs` performs the quorum check:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake     = unPerasVoteStake voteStake          -- Rational from PerasVoteStakeDistr
  quorumThreshold = unPerasQuorumStakeThreshold
                      (perasQuorumStakeThreshold params)  -- = 3/4
  safetyMargin    = unPerasQuorumStakeThresholdSafetyMargin
                      (perasQuorumStakeThresholdSafetyMargin params)  -- = 2/100
``` [1](#0-0) 

The code carries an explicit TODO acknowledging the unit mismatch:

> "TODO: this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [2](#0-1) 

The `PerasVoteStake` type itself carries a parallel note:

> "At the moment there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee (given that the quorum is expressed as a relative value of the voting committee total stake)." [3](#0-2) 

The `perasQuorumStakeThreshold` is set to `3/4` (a relative fraction in `[0,1]`): [4](#0-3) 

The `PerasVoteStake` for each vote is taken directly from `PerasVoteStakeDistr` via `lookupPerasVoteStake` without any normalization step: [5](#0-4) 

The `PerasVoteStakeDistr` is provided to the vote pool writer from the ledger's stake distribution: [6](#0-5) 

If the ledger populates `PerasVoteStakeDistr` with absolute lovelace amounts (e.g., a pool holding 1 billion ADA = 10¹⁵ lovelace), then `unPerasVoteStake voteStake` evaluates to a number vastly larger than `3/4 + 2/100 = 0.77`. The comparison `stake >= 0.77` is trivially `True` for any single vote from any pool with any positive stake.

The quorum check is called in `votesReachQuorum` (used in `updateCandidateVoteState`) and in the model: [7](#0-6) [8](#0-7) 

### Impact Explanation

A Peras certificate forged from a single adversarial vote boosts the adversarial block's chain weight by `perasWeight` (15 block-equivalents by default): [9](#0-8) 

Chain selection uses `totalWeightOfFragment`, which adds `weightLength` (block count) plus `weightBoost` (Peras boost): [10](#0-9) 

An adversary who is a registered stake pool (even with minimal stake) can:
1. Send a single `PerasVote` for an adversarial block via the node-to-node mini-protocol.
2. The vote passes `validatePerasVote` (the pool is in the stake distribution).
3. `stakeAboveThreshold` returns `True` immediately due to the unit mismatch.
4. A Peras certificate is forged for the adversarial block.
5. The adversarial block gains a 15-block weight boost.
6. Honest nodes running chain selection prefer the adversarially boosted chain over the honest chain.

This is a **High** chain-selection bug: an unprivileged peer (any registered stake pool) can make honest nodes prefer a non-canonical chain beyond the intended security assumptions of Peras.

### Likelihood Explanation

The likelihood depends on whether `PerasVoteStakeDistr` is populated with absolute or relative values. The TODO comment explicitly states the normalization has not been implemented. The natural source for `PerasVoteStakeDistr` is the ledger's `PoolDistr`, which in Shelley-era uses relative stake fractions (`IndividualPoolStake.sigma`). If the integration uses relative values, the comparison is correct. However, the acknowledged absence of normalization and the open design question ("no consensus from researchers/engineers") means the risk is real and the code is not safe by construction. Any future integration that uses absolute lovelace values (the raw ledger representation) would immediately trigger the bug. Likelihood is **Medium** given the active development state of Peras and the explicit acknowledgment of the missing normalization.

### Recommendation

`stakeAboveThreshold` must normalize `PerasVoteStake` before comparing it to the relative quorum threshold. The function should either:

1. Accept the total stake distribution and compute the relative fraction internally:
   ```haskell
   stakeAboveThreshold :: PerasParams -> PerasVoteStakeDistr -> PerasVoteStake -> Bool
   stakeAboveThreshold params distr voteStake =
     normalizedStake >= quorumThreshold + safetyMargin
    where
     totalStake = sum (unPerasVoteStakeDistr distr)
     normalizedStake = unPerasVoteStake voteStake / totalStake
     ...
   ```
2. Or enforce at the `PerasVoteStakeDistr` construction site that all values are already normalized relative fractions summing to 1, and add a type-level or runtime invariant to prevent absolute values from being stored.

The TODO comment at lines 155–161 of `SupportsPeras.hs` must be resolved before Peras is activated on any production network.

### Proof of Concept

Assume a private testnet with Peras enabled and a `PerasVoteStakeDistr` populated with absolute lovelace values (e.g., pool `P` has 1,000,000 ADA = 10¹² lovelace, so `PerasVoteStake = 10¹²/1`):

1. Adversary controls pool `P` (registered in the stake distribution).
2. Adversary sends one `PerasVote` for adversarial block `B_adv` at round `r`.
3. `validatePerasVote mkPerasParams stakeDistr vote` succeeds: pool `P` is in the distribution, `vpvVoteStake = PerasVoteStake (10¹² % 1)`.
4. `votesReachQuorum cfg [validatedVote]` calls `stakeAboveThreshold cfg (PerasVoteStake (10¹² % 1))`.
5. `10¹² >= 3/4 + 2/100` → `True`. Quorum is declared.
6. `forgePerasCert` produces a `ValidatedPerasCert` with `vpcCertBoost = PerasWeight 15`.
7. `totalWeightOfFragment` for any chain containing `B_adv` gains +15 weight.
8. Honest nodes running chain selection adopt the adversarially boosted chain.
