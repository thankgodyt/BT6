### Title
Anyone Can Call `sign_btc_transaction` With Arbitrary `key_version`, Causing Withdrawal Transactions to Be Signed With the Wrong MPC Key and Become Unbroadcastable — (`contracts/satoshi-bridge/src/api/chain_signatures.rs`)

### Summary

`sign_btc_transaction` is a public function with no caller-identity check. Any NEAR account can invoke it for any pending withdrawal transaction and supply an arbitrary `key_version`. Because `key_version` is forwarded verbatim to the MPC chain-signatures service, a wrong value causes the MPC to produce a signature under a different key than the one that controls the UTXO. Once a signature slot is filled the contract rejects a second attempt for the same index ("Already signed"), so the legitimate signer is permanently blocked. The assembled transaction carries an invalid signature, cannot be broadcast to Bitcoin, and the user's withdrawal is stuck until an operator intervenes.

### Finding Description

`sign_btc_transaction` in `contracts/satoshi-bridge/src/api/chain_signatures.rs` is decorated only with `#[pause]`; there is no `#[access_control_any]` guard and no check that `env::predecessor_account_id()` matches `btc_pending_info.account_id`. [1](#0-0) 

The function accepts three caller-supplied parameters — `btc_pending_sign_id`, `sign_index`, and `key_version` — and passes them directly to `internal_sign_btc_transaction` without validating any of them against the stored pending-info state. [2](#0-1) 

The `key_version` value is forwarded to the NEAR chain-signatures MPC service. The MPC derives the signing key from the path **and** the version; a different version produces a signature under a different public key than the one that locked the UTXO on Bitcoin. The resulting signature is stored in `btc_pending_info.signatures[sign_index]`.

Once a slot is filled the contract refuses a second signing attempt for the same index:

```
"Already signed"
```

as confirmed by the integration test suite. [3](#0-2) 

When all inputs are signed (even with wrong-key signatures) the pending info transitions to `PendingVerify` state. In that state `withdraw_rbf` (which requires `PendingSign`) is no longer available to the user. The only recovery path is an operator-initiated `cancel_withdraw`. [4](#0-3) [5](#0-4) 

### Impact Explanation

An attacker who front-runs the legitimate signer fills every signature slot with MPC-produced but cryptographically invalid signatures (wrong key). The assembled Bitcoin transaction cannot be broadcast. The user's nBTC remains locked in the pending state (it is burned only after `verify_withdraw` confirms the transaction on-chain), and the BTC is unreachable until an operator calls `cancel_withdraw`. This matches the **Medium** allowed impact: *attacker-triggered temporary locking of bridged funds*.

### Likelihood Explanation

All `BTCPendingInfo` entries and their IDs are publicly readable via `get_btc_pending_infos_paged`. Any NEAR account can observe a newly created withdrawal pending ID and immediately call `sign_btc_transaction` with an arbitrary `key_version` before the legitimate relayer does. No special privilege, token balance, or off-chain resource is required beyond a small NEAR gas fee.

### Recommendation

Add a caller-identity check at the top of `sign_btc_transaction` so that only the account that owns the pending transaction (i.e., `btc_pending_info.account_id`) or a privileged role (DAO / Operator / UnrestrictedRelayer) may sign it:

```rust
pub fn sign_btc_transaction(
    &mut self,
    btc_pending_sign_id: String,
    sign_index: usize,
    key_version: u32,
) -> PromiseOrValue<bool> {
    let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
    btc_pending_info.assert_pending_sign();

    // ── NEW: only the owning account or a privileged role may sign ──
    let caller = env::predecessor_account_id();
    require!(
        caller == btc_pending_info.account_id
            || self.acl_has_any_role(
                vec![Role::DAO.into(), Role::UnrestrictedRelayer.into()],
                caller
            ),
        "Not authorized to sign this transaction"
    );
    // ────────────────────────────────────────────────────────────────
    ...
}
```

Additionally, validate that `key_version` matches the value stored in the contract configuration (or the value used when the deposit address was derived) to prevent signing with an unintended key version even by the legitimate caller.

### Proof of Concept

1. Alice initiates a withdrawal; a `BTCPendingInfo` with `account_id = alice` is created in `PendingSign` state. Its ID (`btc_pending_sign_id`) is visible via `get_btc_pending_infos_paged`.
2. Attacker (any NEAR account) calls:
   ```
   sign_btc_transaction(btc_pending_sign_id, 0, 999)
   ```
   The MPC signs input 0 with key version 999 (a different key than the UTXO's controlling key). The signature is stored in `signatures[0]`.
3. The legitimate relayer calls:
   ```
   sign_btc_transaction(btc_pending_sign_id, 0, 0)
   ```
   The contract panics with `"Already signed"`.
4. If the transaction has only one input, it is now in `PendingVerify` state with an invalid signature. `withdraw_rbf` is unavailable. The assembled Bitcoin transaction is rejected by the network. Alice's withdrawal is stuck until an operator calls `cancel_withdraw`. [1](#0-0) [5](#0-4)

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> PromiseOrValue<bool> {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        btc_pending_info.assert_pending_sign();
        if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {
            if !self.check_btc_pending_info_exists(original_tx_id) {
                require!(
                    self.internal_unwrap_mut_account(&btc_pending_info.account_id.clone())
                        .btc_pending_sign_ids
                        .remove(&btc_pending_sign_id),
                    "Internal error"
                );
                self.internal_remove_btc_pending_info(&btc_pending_sign_id);
                return PromiseOrValue::Value(true);
            }
        }
        self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
            .into()
    }
