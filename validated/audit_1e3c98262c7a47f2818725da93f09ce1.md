Looking at the actual contract code to verify all claims in the report.

Audit Report

## Title
Missing `multiTokens` Registration Check in `initTransfer1155` Permanently Freezes ERC-1155 Tokens - (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

## Summary

`initTransfer1155` accepts and locks ERC-1155 tokens into the bridge without verifying that the `(tokenAddress, tokenId)` pair has been registered via `logMetadata1155`. If a user calls `initTransfer1155` for an unregistered pair, the tokens are transferred into the bridge but can never be released: the NEAR side has no registered token to mint against, and the EVM-side `finTransfer` path for ERC-1155 is gated on `multiTokens[deterministicToken].tokenAddress != address(0)`, which remains zero. No on-chain recovery function exists for stuck ERC-1155 tokens.

## Finding Description

`logMetadata1155` is the only function that populates `multiTokens[deterministicToken]`:

```solidity
// L243-255
MultiTokenInfo storage multiToken = multiTokens[deterministicToken];
if (multiToken.tokenAddress == address(0)) {
    multiToken.tokenAddress = tokenAddress;
    multiToken.tokenId = tokenId;
}
```

`initTransfer1155` computes `deterministicToken` and immediately calls `safeTransferFrom` with no guard on `multiTokens`:

```solidity
// L453-464
address deterministicToken = deriveDeterministicAddress(tokenAddress, tokenId);
IERC1155(tokenAddress).safeTransferFrom(msg.sender, address(this), tokenId, amount, "");
```

The `onERC1155Received` callback (L522-535) only blocks transfers where `operator != address(this)`. Because the bridge contract itself calls `safeTransferFrom` inside `initTransfer1155`, `operator` equals `address(this)` and the guard passes — the transfer always succeeds regardless of registration state.

On the release path, `finTransfer` (L323) only enters the ERC-1155 branch when `multiToken.tokenAddress != address(0)`. If `logMetadata1155` was never called, this is zero, so the code falls through to `IERC20(payload.tokenAddress).safeTransfer(...)` against the deterministic address, which is not a deployed contract and reverts. No other branch releases the locked ERC-1155 tokens. There is no admin rescue or refund function for ERC-1155 in the contract.

## Impact Explanation

Any user who calls `initTransfer1155` for an unregistered `(tokenAddress, tokenId)` pair suffers **permanent, irrecoverable loss of their ERC-1155 tokens**. This matches the Critical allowed impact: *permanent freezing of bridged funds*. The ERC-20 `initTransfer` flow requires no prior `logMetadata` call, creating a natural but incorrect analogy that makes this mistake likely. The contract provides no revert, no warning, and no recovery path.

## Likelihood Explanation

The function is fully permissionless and requires no special role. A user bridging a new ERC-1155 token for the first time, or using a `tokenId` different from the one previously registered, will trigger the freeze. The ERC-20 analogy (no prior step required) makes this a realistic user path, not a contrived one. The mistake is repeatable across any ERC-1155 token and any token ID.

## Recommendation

Add a registration guard at the top of `initTransfer1155`, before the `safeTransferFrom` call:

```solidity
address deterministicToken = deriveDeterministicAddress(tokenAddress, tokenId);
if (multiTokens[deterministicToken].tokenAddress == address(0)) {
    revert ERC1155NotRegistered();
}
```

This mirrors the collision-check pattern already present in `logMetadata1155` and ensures the NEAR side always has a registered token before EVM-side custody is taken.

## Proof of Concept

1. Deploy any ERC-1155 contract; mint `amount` tokens to `user`.
2. `user` approves the bridge and calls `bridge.initTransfer1155(erc1155Addr, tokenId, amount, 0, 0, "user.near", "")` **without** first calling `bridge.logMetadata1155(erc1155Addr, tokenId)`.
3. `onERC1155Received` passes because `operator == address(this)`; `amount` tokens are now held by the bridge.
4. `InitTransfer` is emitted with `deterministicToken = address(bytes20(keccak256(abi.encodePacked(erc1155Addr, tokenId))))`.
5. The NEAR relayer finds no registered token for that deterministic address; NEAR-side processing fails; no valid `finTransfer` signature is produced.
6. If `finTransfer` is attempted anyway with `payload.tokenAddress = deterministicToken`: `multiTokens[deterministicToken].tokenAddress == address(0)` → ERC-1155 branch skipped → falls to `IERC20(deterministicToken).safeTransfer(...)` → reverts (not a contract).
7. Tokens are permanently locked with no recovery path.
