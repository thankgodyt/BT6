### Title
Attacker Can Redirect BTC Refund to Arbitrary Address When `deposit_msg.refund_address` Is `None` - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
When a user deposits BTC without embedding a `refund_address` in their `DepositMsg`, any unprivileged NEAR account can call `request_refund` with an attacker-controlled BTC address. Because the contract imposes no caller restriction and no address validation in this path, the attacker can front-run the legitimate depositor, permanently storing their own BTC address as the refund destination. If the DAO/Operator does not reject the request within `unsafe_refund_timelock_sec`, the depositor's BTC is irreversibly sent to the attacker.

### Finding Description
`request_refund` in `contracts/satoshi-bridge/src/api/bridge.rs` is a public, permissionless function. It delegates to `internal_request_refund` in `contracts/satoshi-bridge/src/refund.rs`. The only address validation performed is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [1](#0-0) 

When `deposit_msg.refund_address` is `None`, the branch is skipped entirely and the caller-supplied `refund_address` string is accepted without restriction. There is no check on `env::predecessor_account_id()` to verify the caller is the original depositor. [2](#0-1) 

The accepted `refund_address` is stored verbatim in `RefundRequest`: [3](#0-2) 

It is later used directly in `build_refund_output` to construct the Bitcoin transaction output that the MPC signs: [4](#0-3) 

And in the Bitcoin path, `internal_execute_refund` builds the PSBT output from the stored address: [5](#0-4) 

Additionally, a duplicate-request guard in `request_refund_callback` ensures only one request can exist per UTXO: [6](#0-5) 

This means a front-running attacker who wins the race permanently blocks the legitimate depositor from registering their own address.

The `DepositMsg.refund_address` field is explicitly optional: [7](#0-6) 

Users who omit it (a common pattern shown throughout the test suite) are fully exposed.

### Impact Explanation
**Critical.** If the attacker's `request_refund` call lands before the legitimate depositor's, the stored `refund_address` is the attacker's BTC address. After `unsafe_refund_timelock_sec` elapses without a DAO/Operator rejection, `execute_refund` builds and signs a Bitcoin transaction paying the attacker. The depositor's BTC is permanently and irreversibly transferred to the attacker. No recovery path exists once the signed transaction is broadcast.

### Likelihood Explanation
**Medium.** The preconditions are:
1. The depositor omits `refund_address` from `DepositMsg` (common pattern).
2. The deposit is never finalized (relayer outage, user changed mind, etc.).
3. The attacker observes the deposit transaction on the public Bitcoin blockchain and calls `request_refund` before the legitimate depositor does.
4. The DAO/Operator does not reject the malicious request within `unsafe_refund_timelock_sec`.

Conditions 1–3 are realistic. Condition 4 is the only mitigation, and it is not guaranteed — the DAO/Operator may be offline, slow, or simply miss the event.

### Recommendation
Restrict who may supply a `refund_address` when `deposit_msg.refund_address` is `None`. The simplest fix is to require `env::predecessor_account_id() == deposit_msg.recipient_id` in `internal_request_refund` when `deposit_msg.refund_address` is `None`. Alternatively, require `deposit_msg.refund_address` to always be set (non-`None`) so the address is committed at deposit time and cannot be overridden by a third party.

### Proof of Concept
1. Alice calls `get_user_deposit_address(DepositMsg { recipient_id: "alice.near", refund_address: None, ... })` and sends BTC to the returned address.
2. The deposit is never finalized (relayer is down).
3. Bob observes Alice's BTC transaction on the public Bitcoin blockchain.
4. Bob calls `request_refund(alice_deposit_msg, "bob_btc_address", alice_tx_bytes, vout, proof, None)` with sufficient attached NEAR for storage.
5. `internal_request_refund` skips the address check (since `deposit_msg.refund_address` is `None`) and proceeds to verify the transaction inclusion proof — which passes because the tx is real.
6. `request_refund_callback` verifies the script_pubkey matches the deposit address derived from `alice_deposit_msg` — which also passes because Bob used the correct `deposit_msg`.
7. The contract stores `RefundRequest { refund_address: "bob_btc_address", ... }`.
8. Alice subsequently calls `request_refund` but receives `"Refund request already exists for this UTXO"`.
9. After `unsafe_refund_timelock_sec` passes without DAO/Operator rejection, Bob calls `execute_refund`.
10. `build_refund_output` constructs a Bitcoin output paying `"bob_btc_address"`, the MPC signs it, and Alice's BTC is permanently sent to Bob.

    /// Build a transparent refund output paying `refund_amount` to `refund_address`.
    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
    }

    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
