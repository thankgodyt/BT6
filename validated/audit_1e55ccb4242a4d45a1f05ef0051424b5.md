### Title
Missing Round-Number Expiration Check on Inbound Peras Votes Allows Unauthorized Certificate Acceptance - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Storage/PerasVoteDB/Impl.hs`)

---

### Summary

The Peras vote ingestion pipeline (`processVotes` → `implAddVote`) accepts votes for **any arbitrary round number** from an unprivileged peer without checking whether the vote's round is current or within a valid window. This is the direct consensus analog of the "missing deadline check" vulnerability: just as a DeFi transaction can sit in a mempool and execute at a stale price, a Peras vote for a long-past round can be injected at any time and, if quorum is reached, cause the node to forge a certificate for a past block — materially altering chain-weight and chain selection.

---

### Finding Description

**Entry path — `processVotes` in `ObjectPool/PerasVote.hs`:**

When a peer delivers a batch of votes via the ObjectDiffusion mini-protocol, `processVotes` is called. It filters out already-known votes, then calls `validatePerasVote` on each remaining vote. [1](#0-0) 

**Stub validation — `validatePerasVote` in `BlockSupportsPeras.hs`:**

The `validatePerasVote` implementation is an acknowledged stub. It ignores `_params` entirely (note the underscore) and only checks whether the voter ID appears in the stake distribution. It performs **no round-number check** and **no cryptographic signature verification**: [2](#0-1) 

**Missing expiration check — `implAddVote` in `PerasVoteDB.Impl.hs`:**

The implementation itself carries an explicit TODO acknowledging the missing validation: [3](#0-2) 

Inside `implAddVote`, the only guard is a duplicate-ID check. If the vote is new, it is unconditionally inserted and its round-vote state is updated via `updatePerasRoundVoteStates`. There is no check that `getPerasVoteRound vote` equals the current Peras round, nor any upper or lower bound on the round number: [4](#0-3) 

**Quorum forging — `updatePerasRoundVoteStates` in `Vote/Aggregation.hs`:**

Once enough stake-weighted votes accumulate for any round (past or future), `updatePerasRoundVoteStates` automatically forges a `ValidatedPerasCert` for that round: [5](#0-4) 

**GC cannot compensate:**

The garbage-collector in `implGarbageCollect` only removes rounds whose *youngest targeted slot* is older than the GC threshold. The code itself notes that an attacker can prevent GC by targeting far-future slots: [6](#0-5)

### Impact Explanation

Peras certificates boost chain weight. A certificate forged for a past block (round N, where the current round is N+K) causes the node to assign extra weight to that block's chain. This can make the node prefer a non-canonical chain over the honest chain, constituting a **chain-selection safety failure** reachable by an unprivileged peer.

Additionally, because `validatePerasVote` does not verify the BLS signature, an adversary does not need to compromise any key: they only need to know the public voter IDs (which are on-chain), construct votes claiming to be from those operators for any round, and send them. The node will accept them as "validated" and accumulate stake toward quorum.

This maps to the allowed impact scope:
- **Critical**: Bypass of Peras voting/certificate checks enabling unauthorized certificate acceptance.
- **High**: Chain-selection bug letting an unprivileged peer make an honest node prefer a non-canonical chain.

---

### Likelihood Explanation

- The ObjectDiffusion mini-protocol is reachable by any peer without authentication.
- The `validatePerasVote` stub is in the production source tree and is the active implementation used by `makePerasVotePoolWriterFromChainDB` (the production writer).
- No round-number bound, no signature check, no wall-clock check — three independent missing guards, all acknowledged by TODO comments pointing to the same open issue (`cardano-peras/issues/120`).
- An adversary needs only to know public voter IDs and send a crafted batch of votes for a chosen past round.

---

### Recommendation

1. **Add a round-number expiration check** in `implAddVote` (or in `processVotes` before calling `addVote`): reject any vote whose `getPerasVoteRound vote` is not within `[currentRound - maxRoundLag, currentRound]` for a small configurable `maxRoundLag`. This is the direct analog of the `ensure(deadline)` modifier in Uniswap.

2. **Implement full `validatePerasVote`**: verify the BLS signature and the eligibility proof against the committee selection data, as tracked in `cardano-peras/issues/120`.

3. **Add a round-number upper bound** in `implAddVote` to reject votes for future rounds beyond the current round, preventing pre-staging attacks.

---

### Proof of Concept

```
Attacker (unprivileged peer)
  │
  │  ObjectDiffusion mini-protocol
  │  sends: [PerasVote { pvVoteRound = 0, pvVoteVoterId = <any known pool ID>, ... }]
  │         × (quorum threshold / avg stake per pool) times
  ▼
processVotes
  └─ validatePerasVote _params stakeDistr vote
       -- _params ignored; only checks lookupPerasVoteStake
       -- returns Right (ValidatedPerasVote ...) for any known pool ID
       -- NO round-number check, NO signature check
  └─ implAddVote perasCfg env (WithArrivalTime now validatedVote)
       -- addOrIgnoreVote: vote ID not in DB → tryAddVote
       -- updatePerasRoundVoteStates: accumulates stake for round 0
       -- once quorum reached → VoteGeneratedNewCert cert
       -- cert for round 0 / past block is now in PerasVoteDB
       -- ChainDB.addPerasVoteWithAsyncCertHandling triggers chain-weight boost
       -- node may switch to adversary's boosted chain
```

The node accepts the certificate for round 0 (a long-past round) and boosts the corresponding block's chain weight, potentially causing it to prefer the adversary's chain over the honest chain — a consensus safety failure triggered by a single unprivileged peer with no key material.
