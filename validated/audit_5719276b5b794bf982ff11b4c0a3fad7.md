Audit Report

## Title
User Tokens Permanently Locked When Transfer Amount Normalizes to Zero — (`near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer_internal` locks or burns a user's NEP-141 tokens and returns `U128(0)` (tokens consumed) before any check that the normalized transfer amount is greater than zero. The zero-amount guard lives exclusively in `sign_transfer`, which is called later by a relayer. When the guard fires there, the transfer record is never removed and no on-chain path exists to recover the locked tokens, resulting in permanent loss.

## Finding Description

**Token lock without normalization check — `init_transfer_internal`:** [1](#0-0) 

Tokens are burned/locked unconditionally. The function then returns `U128(0)` at line 1864, signalling to the NEP-141 contract that all tokens were consumed — no refund is issued.

**Zero-amount guard fires only in `sign_transfer`, after the lock:** [2](#0-1) 

`sign_transfer` is a separate, relayer-initiated transaction. When `normalize_amount` returns 0, `require!` panics and the transaction reverts — but the transfer record in `pending_transfers` is untouched.

**`normalize_amount` uses floor division:** [3](#0-2) 

For a token with `origin_decimals = 24` and `decimals = 6` (standard NEAR → EVM pairing), the divisor is `10^18`. Any amount below `10^18` yoctoNEAR normalizes to zero.

**No recovery path exists:**

`remove_transfer_message` is called only inside `sign_transfer_callback` (requires a successful MPC signature response) and `claim_fee_callback` (requires a successful finalization proof from the destination chain). [4](#0-3) 

Because `sign_transfer` panics before the MPC call is ever dispatched, `sign_transfer_callback` is never scheduled. No public `cancel_transfer` function exists anywhere in the contract.

## Impact Explanation
This is a **Critical** impact matching "permanent freezing of bridged funds." A user's tokens are irrecoverably locked inside the bridge contract. The transfer record sits in `pending_transfers` indefinitely; no relayer can ever sign it, and no on-chain path returns the tokens to the user.

## Likelihood Explanation
The 24 → 6 decimal gap between NEAR-native tokens and EVM tokens is standard and well-known. Any user sending an amount below `10^18` yoctoNEAR (i.e., below 1 NEAR in absolute terms) through the normal, publicly documented `ft_transfer_call` flow triggers this. No special role, privilege, or attacker capability is required — a user testing with a small amount or miscalculating units is sufficient.

## Recommendation
Add a normalization check inside `init_transfer_internal` (or in `ft_on_transfer` before calling it) that rejects the transfer — and refunds the tokens — if the normalized amount would be zero:

```rust
// Before locking/burning, after building transfer_message:
let token_address = self.get_token_address(
    transfer_message.get_destination_chain(),
    self.get_token_id(&transfer_message.token),
);
if let Some(addr) = token_address {
    if let Some(decimals) = self.token_decimals.get(&addr) {
        let normalized = Self::normalize_amount(
            transfer_message.amount_without_fee()
                .near_expect(BridgeError::InvalidFee),
            decimals,
        );
        if normalized == 0 {
            // Return the full amount so the NEP-141 contract refunds the user
            return transfer_message.amount;
        }
    }
}
```

Alternatively, add a `cancel_transfer` function that allows the original sender to reclaim tokens from a transfer that has never been signed.

## Proof of Concept

1. Register a token with `origin_decimals = 24`, `decimals = 6`.
2. Call `ft_transfer_call` with `amount = 999_999_999_999_999_999` (< `10^18`), `msg` encoding `fee = 0`, `native_token_fee = 0`, and a valid EVM recipient.
3. `init_transfer_internal` succeeds: tokens are locked, transfer stored in `pending_transfers`, `ft_on_transfer` returns `U128(0)` — tokens consumed, no refund.
4. Relayer calls `sign_transfer` for the new `TransferId`.
5. `normalize_amount(999_999_999_999_999_999, Decimals { decimals: 6, origin_decimals: 24 })` = `999_999_999_999_999_999 / 10^18` = `0`.
6. `require!(0 > 0, BridgeError::InvalidAmountToTransfer)` panics — transaction reverts, transfer record untouched.
7. No further call can complete or cancel this transfer; the user's tokens are permanently locked.
