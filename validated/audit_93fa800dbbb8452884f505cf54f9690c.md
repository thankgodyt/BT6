Audit Report

## Title
`initTransfer1155` Accepts ERC1155 Deposits Without Requiring Prior `multiTokens` Registration, Permanently Freezing Funds - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
`initTransfer1155` computes a deterministic virtual address for an ERC1155 `(tokenAddress, tokenId)` pair and accepts the token deposit, but never verifies that `multiTokens[deterministicToken]` has been populated by a prior `logMetadata1155` call. When NEAR later signs a `finTransfer` payload referencing the deterministic address, `finTransfer` finds an empty `multiTokens` entry and falls through to an ERC20 transfer path that reverts unconditionally, permanently locking the deposited ERC1155 tokens with no admin recovery path.

## Finding Description
`logMetadata1155` is the sole writer of `multiTokens[deterministicToken]`:

```solidity
// Lines 243-255
MultiTokenInfo storage multiToken = multiTokens[deterministicToken];
if (multiToken.tokenAddress == address(0)) {
    multiToken.tokenAddress = tokenAddress;
    multiToken.tokenId = tokenId;
}
```

`initTransfer1155` (lines 439-490) computes the same deterministic address, transfers the ERC1155 tokens into the bridge, and emits `InitTransfer` — but contains zero check that `multiTokens[deterministicToken]` is already set:

```solidity
// Lines 453-489
address deterministicToken = deriveDeterministicAddress(tokenAddress, tokenId);
IERC1155(tokenAddress).safeTransferFrom(msg.sender, address(this), tokenId, amount, "");
// ...
emit BridgeTypes.InitTransfer(msg.sender, deterministicToken, ...);
```

The `onERC1155Received` guard (lines 522-535) does not block this: it only rejects transfers where `operator != address(this)`. Since the bridge contract itself calls `safeTransferFrom`, the ERC1155 token sets `operator = address(this)`, so the guard passes.

When NEAR processes the `InitTransfer` event and signs a `finTransfer` payload with `tokenAddress = deterministicToken`, `finTransfer` dispatches as follows (lines 315-355):

1. `multiToken = multiTokens[deterministicToken]` → `{address(0), 0}` (never set)
2. `payload.tokenAddress == address(0)` → false
3. `multiToken.tokenAddress != address(0)` → false (skips ERC1155 path)
4. `customMinters[deterministicToken] != address(0)` → false
5. `isBridgeToken[deterministicToken]` → false
6. Falls through to `IERC20(deterministicToken).safeTransfer(recipient, amount)` → reverts because `deterministicToken` has no deployed code

There is no admin rescue function for ERC1155 tokens in the contract. The tokens are permanently locked.

## Impact Explanation
Any user who calls `initTransfer1155` without a prior `logMetadata1155` for the same `(tokenAddress, tokenId)` pair suffers permanent, irreversible loss of their bridged ERC1155 tokens. This matches the allowed Critical impact: **permanent freezing of bridged funds**. The contract has no escape hatch — no `rescueERC1155`, no admin withdrawal, no re-registration path that would unblock the stuck `finTransfer`.

## Likelihood Explanation
`initTransfer1155` is a public, permissionless function. The contract enforces no call ordering. A first-time user bridging a new ERC1155 token will naturally call `initTransfer1155` directly without knowing that `logMetadata1155` must precede it. The `evm/SECURITY.md` does not document this ordering requirement. Likelihood is moderate-to-high for any novel ERC1155 token being bridged for the first time.

## Recommendation
Add a guard at the top of `initTransfer1155` that requires the mapping to already be populated:

```solidity
address deterministicToken = deriveDeterministicAddress(tokenAddress, tokenId);
require(
    multiTokens[deterministicToken].tokenAddress != address(0),
    "ERR_ERC1155_NOT_REGISTERED"
);
```

Alternatively, inline the same registration logic from `logMetadata1155` atomically inside `initTransfer1155` so that a single call both registers and deposits.

## Proof of Concept
1. Deploy an ERC1155 contract; mint token ID `42` to Alice.
2. Alice approves the bridge and calls `initTransfer1155(erc1155, 42, 10, 0, 0, "alice.near", "")` — **without** any prior `logMetadata1155(erc1155, 42)`.
3. `onERC1155Received` passes (`operator == address(this)`). Bridge holds 10 units. `multiTokens[deterministicToken]` remains `{address(0), 0}`.
4. NEAR observes the `InitTransfer` event and records the transfer with `tokenAddress = deterministicToken`.
5. Alice initiates a return on NEAR; NEAR MPC signs a `finTransfer` payload: `tokenAddress = deterministicToken, amount = 10, recipient = Alice`.
6. Anyone calls `finTransfer(sig, payload)` on the EVM bridge.
7. `multiTokens[deterministicToken].tokenAddress == address(0)` → all ERC1155/custom-minter/bridge-token branches skipped → `IERC20(deterministicToken).safeTransfer(Alice, 10)` → reverts (no code at `deterministicToken`).
8. Alice's 10 ERC1155 tokens are permanently locked; `completedTransfers[nonce]` is set to `true`, so the `finTransfer` can never succeed even after a fix is deployed.
