### Title
`max_btc_gas_fee` Hard Cap Blocks User RBF During BTC Fee Spikes, Permanently Locking Pending Withdrawal Funds Without Operator Intervention - (File: `contracts/satoshi-bridge/src/psbt.rs`, `contracts/satoshi-bridge/src/rbf/withdraw.rs`)

---

### Summary

`check_withdraw_psbt` enforces a hard upper bound `gas_fee <= config.max_btc_gas_fee` on every withdrawal PSBT, including user-initiated RBF attempts. When Bitcoin network fees spike above the configured `max_btc_gas_fee`, users with funds already locked in a `PendingVerify` withdrawal cannot accelerate their stuck transaction via `withdraw_rbf`. The only rescue path — `cancel_withdraw` — is restricted to `Role::DAO` or `Role::Operator`. This is the direct analog of the OpenLeverage anti-flashloan check that blocked liquidations during rapid market downturns: a protective threshold that, under sustained adverse conditions, prevents the very operation needed to resolve the stuck state.

---

### Finding Description

`check_withdraw_psbt` in `contracts/satoshi-bridge/src/psbt.rs` unconditionally enforces:

```rust
require!(
    gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee,
    format!("Invalid gas fee ({}). valid range: [{}, {}].", ...)
);
``` [1](#0-0) 

This function is called for both the initial withdrawal PSBT and for every user RBF attempt. In `check_withdraw_rbf_psbt_valid`:

```rust
let (_, _, actual_received_amount, gas_fee) = self.check_withdraw_psbt(
    withdraw_rbf_psbt,
    ...
);
``` [2](#0-1) 

So `internal_withdraw_rbf` — the function backing the public `withdraw_rbf` entry point — inherits the same `max_btc_gas_fee` ceiling. [3](#0-2) 

The only alternative path, `cancel_withdraw`, is gated behind `Role::DAO` or `Role::Operator`:

```rust
#[access_control_any(roles(Role::DAO, Role::Operator))]
pub fn cancel_withdraw(&mut self, original_btc_pending_verify_id: String, output: Vec<TxOut>) {
``` [4](#0-3) 

`cancel_withdraw` internally calls `check_psbt_output_all_change_address` with `is_cancel = true`, which skips the `max_btc_gas_fee` ceiling — so the cancel path itself is not blocked. But it is inaccessible to ordinary users. [5](#0-4) 

---

### Impact Explanation

When BTC network fees spike above `max_btc_gas_fee`:

1. A user whose withdrawal is already in `PendingVerify` state (nBTC already transferred to the bridge, BTC transaction broadcast but unconfirmed) calls `withdraw_rbf` to accelerate confirmation.
2. `check_withdraw_psbt` reverts with `"Invalid gas fee"` because the market fee exceeds `max_btc_gas_fee`.
3. The user's nBTC remains locked inside the bridge contract. The BTC transaction sits in the mempool, potentially for days or indefinitely if fees stay elevated.
4. The only exit is operator-initiated `cancel_withdraw`, which requires `Role::DAO` or `Role::Operator`. If the operator is slow or unavailable, user funds are stuck for an unbounded period.

This matches the allowed impact: **Medium — stuck bridge state requiring operator intervention**.

---

### Likelihood Explanation

Bitcoin fee spikes are a well-documented, recurring market event (e.g., Ordinals inscription waves, halving periods). The `max_btc_gas_fee` is a static config value that cannot be updated atomically with the fee market. During a spike, every user with a pending withdrawal is simultaneously blocked from self-rescue. The condition can persist for hours or days, exactly mirroring the OpenLeverage scenario where spot price continuously traded below TWAP.

---

### Recommendation

Apply the same fix the OpenLeverage judge recommended: do not revert the critical user-facing operation (RBF) based on the fee ceiling. Instead:

- Remove the `gas_fee <= config.max_btc_gas_fee` check from `check_withdraw_psbt` when called in the RBF context, or introduce a separate `check_withdraw_rbf_psbt` that omits the upper bound.
- Alternatively, allow users to call `cancel_withdraw` on their own pending transactions (with appropriate timelock), removing the operator-only gate for self-rescue.
- At minimum, document that `max_btc_gas_fee` must be updated promptly during fee spikes, and add an on-chain mechanism (e.g., a DAO-callable `set_max_btc_gas_fee`) that can be executed quickly.

---

### Proof of Concept

1. Alice calls `ft_transfer_call` → `ft_on_transfer` → `create_btc_pending_info`. Config has `max_btc_gas_fee = 50_000 sat`. Gas fee at submission time is `10_000 sat`. PSBT passes validation.
2. MPC signs the transaction. State transitions to `PendingVerify`.
3. BTC mempool congestion spikes. Network fee rate rises; the transaction is stuck. Alice needs to RBF with `gas_fee = 80_000 sat`.
4. Alice calls `withdraw_rbf(original_btc_pending_verify_id, new_output, None)`.
5. `internal_withdraw_rbf` → `check_withdraw_rbf_psbt_valid` → `check_withdraw_psbt`:
   ```
   require!(80_000 >= 1_000 && 80_000 <= 50_000, "Invalid gas fee (80000). valid range: [1000, 50000].")
   ```
   → **panics**. Alice's RBF is rejected.
6. Alice's nBTC remains locked in the bridge. The BTC transaction is unconfirmed. Only a DAO/Operator calling `cancel_withdraw` can unblock her funds. [1](#0-0) [2](#0-1) [6](#0-5)
