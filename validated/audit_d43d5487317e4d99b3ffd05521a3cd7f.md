Audit Report

## Title
Tokens Permanently Locked/Burned When Transfer Amount Normalizes to Zero - (File: `near/omni-bridge/src/lib.rs`)

## Summary

`init_transfer_internal` unconditionally burns or locks the full token amount before any decimal-normalization check occurs. When `normalize_amount(amount - fee, decimals)` floors to zero (e.g., a 24→18 decimal bridge with `amount_without_fee < 10^6`), `sign_transfer` panics on its `amount_to_transfer > 0` guard, leaving the transfer message stranded in `pending_transfers` with no user-accessible recovery path. Burned tokens are permanently destroyed; locked native tokens are permanently stranded in the contract.

## Finding Description

`normalize_amount` applies integer floor division: [1](#0-0) 

For a 24→18 decimal bridge the divisor is `10^6`; any `amount_without_fee < 1_000_000` normalizes to `0`.

`init_transfer` only validates `fee.fee < amount`: [2](#0-1) 

No normalization pre-check exists at initiation time. `init_transfer_internal` then unconditionally burns or locks the full amount: [3](#0-2) 

Only afterward, in `sign_transfer`, does the normalization guard fire: [4](#0-3) 

When this `require!` panics, the transaction reverts but the prior burn/lock (executed in a separate earlier transaction) is not rolled back. The transfer message remains in storage. No public cancel, refund, or user-initiated unlock function exists; `sign_transfer_callback` and `claim_fee_callback` are only reachable after a successful MPC signature, which can never be obtained for a zero-amount transfer.

The contract's own comment acknowledges dust-locking but only for sub-unit remainders, not for the case where the entire `amount_without_fee` normalizes to zero: [5](#0-4) 

## Impact Explanation

This is a **Critical** impact matching the allowed scope: *permanent freezing of bridged funds across NEAR and EVM flows*. Burned bridge tokens are irreversibly destroyed. Locked native tokens are permanently stranded in the contract with no unlock path. Any user who initiates a transfer with `amount_without_fee` below the normalization threshold suffers a total, unrecoverable loss of those funds.

## Likelihood Explanation

The exploit requires no special permissions. Any unprivileged user can trigger it via `ft_transfer_call` on a NEP-141 token — a standard public callback. The condition is especially likely for:
- Users holding small residual balances after prior transfers.
- The standard NEAR (24 decimals) → EVM (18 decimals) pair, where the threshold is `10^6` base units (~0.000001 NEAR-equivalent).
- Users who set a non-zero fee that pushes `amount_without_fee` below the threshold.

No admin compromise, oracle manipulation, or external collusion is required.

## Recommendation

Add a normalization check inside `init_transfer` (or at the top of `init_transfer_internal`) before tokens are burned or locked. Retrieve the destination token's `Decimals` at initiation time and assert:

```rust
require!(
    Self::normalize_amount(
        transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
        decimals
    ) > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

This mirrors the guard already present in `sign_transfer` but applies it before funds are committed, allowing the NEP-141 `ft_transfer_call` callback to refund the user (by returning the full amount) instead of locking their tokens.

## Proof of Concept

1. Register a NEAR token with `origin_decimals = 24`, `decimals = 18` (standard NEAR→EVM mapping). Normalization divisor: `10^6`.
2. Alice calls `ft_transfer_call` sending `500_000` base units with `fee = 0` and an EVM recipient.
3. `init_transfer` accepts (`0 < 500_000`). `init_transfer_internal` burns the 500,000 units and stores the transfer message. Transaction succeeds.
4. A trusted relayer calls `sign_transfer` for Alice's transfer. `normalize_amount(500_000, {24, 18}) = 0`. The `require!(amount_to_transfer > 0)` guard panics. The relayer's transaction reverts.
5. Alice's 500,000 base units are permanently burned. The transfer message remains in `pending_transfers`. No recovery path exists for Alice or any other unprivileged caller.
