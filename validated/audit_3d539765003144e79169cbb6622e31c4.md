### Title
Single Invalid Vote in Batch Causes Silent Suppression of All Valid Peras Votes, Preventing Quorum - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasVote.hs`)

---

### Summary

`processVotes` and `processCerts` use an all-or-nothing batch rejection strategy: if **any single** vote or certificate in an inbound batch fails validation, the **entire batch is thrown away** — including all valid items. An unprivileged peer can exploit this by mixing one crafted invalid vote into a batch of otherwise-valid votes, permanently suppressing those votes on the receiving node and preventing Peras quorum from being reached.

---

### Finding Description

`processVotes` in `PerasVote.hs` iterates over all inbound votes, validates each one, then uses `partitionEithers` to split results:

```haskell
case partitionEithers validationResults of
  ([], validatedVotes) ->
    mapM_ (addVote . WithArrivalTime now) validatedVotes
  (errs, _) ->
    throw (PerasVoteInboundException errs)
``` [1](#0-0) 

When `errs` is non-empty (even a single invalid vote), the entire batch — including the `_` (valid votes) — is discarded by throwing `PerasVoteInboundException`. The valid votes in the batch are **permanently lost**; they are never added to the `PerasVoteDB`.

The same pattern exists in `processCerts`:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) -> mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _)            -> throw (PerasCertValidationError errs)
``` [2](#0-1) 

Both functions are wired directly into the production node-to-node handlers via `makePerasVotePoolWriterFromChainDB` and `makePerasCertPoolWriterFromChainDB`, which are passed as `ObjectPoolWriter` instances to `objectDiffusionInbound`: [3](#0-2) 

The `opwAddObjects` field of `ObjectPoolWriter` is called directly from the inbound protocol loop: [4](#0-3) 

The comment in the code itself acknowledges the design tension:

> "This assumes that vote validation is cheap, which may not be true in practice depending on the actual crypto/committee selection scheme. Hence we may revisit this to lazily abort validation upon the first error encountered." [5](#0-4)

### Impact Explanation

In Peras, votes from committee members must accumulate in the `PerasVoteDB` to reach quorum. Once quorum is reached, a certificate is forged and added to the `PerasCertDB`. Certificates provide weight boosts to blocks, directly influencing chain selection via `getPerasWeightSnapshot`. [6](#0-5) 

An adversarial peer that sends a batch of `[vote_1_valid, vote_2_valid, ..., vote_N_valid, vote_crafted_invalid]` causes all `N` valid votes to be permanently dropped. Since votes are not re-requested from the same peer (it is disconnected), and may not be available from other peers (e.g., if the adversary is the only diffuser of those votes at that moment), quorum for that round may never be reached. This:

1. Prevents Peras certificate generation for the affected round.
2. Removes the weight boost from the honest chain's blocks.
3. Materially weakens Peras chain selection security, causing the node to fall back to pure Praos security assumptions — a bypass of the Peras voting/certificate authorization mechanism.

**Impact class**: Medium — public miniprotocol flaw that materially weakens Peras vote and certificate authorization without relying on DoS.

---

### Likelihood Explanation

Any unprivileged peer connected via the Peras vote diffusion miniprotocol can trigger this. The attacker needs only to:
1. Observe valid vote IDs being diffused (via the outbound side of the protocol).
2. Craft one invalid vote (e.g., with a `PerasVoterId` not in the stake distribution).
3. Include it in a batch alongside valid votes when responding to a `MsgRequestObjects`.

No key compromise, stake majority, or privileged access is required. The attack is repeatable across rounds.

---

### Recommendation

Replace the all-or-nothing batch rejection with per-item handling: validate each vote/certificate independently, add valid ones to the DB, and only disconnect the peer if the proportion or count of invalid items exceeds a threshold (or always). The valid items in the batch should never be silently discarded.

```haskell
-- Instead of:
case partitionEithers validationResults of
  ([], validatedVotes) -> mapM_ (addVote . WithArrivalTime now) validatedVotes
  (errs, _)            -> throw (PerasVoteValidationError errs)

-- Consider:
let (errs, validatedVotes) = partitionEithers validationResults
mapM_ (addVote . WithArrivalTime now) validatedVotes
unless (null errs) $ throw (PerasVoteValidationError errs)
```

This ensures valid votes are always persisted before the peer is disconnected for sending invalid ones.

### Proof of Concept

**Setup**: A private testnet with Peras enabled. Node A connects to adversarial peer B.

1. Peer B has `N` valid votes for round `R` (obtained by observing the network).
2. Peer B crafts one invalid vote `v_bad` (e.g., `pvVoteVoterId` not in the stake distribution, so `validatePerasVote` returns `Left PerasValidationErr`).
3. Peer B responds to Node A's `MsgRequestObjects` with `[v_1, v_2, ..., v_N, v_bad]`.
4. Node A calls `processVotes` → `partitionEithers` yields `errs = [PerasValidationErr]`, `validatedVotes = [v_1..v_N]`.
5. Node A executes `throw (PerasVoteValidationError errs)` — all `N` valid votes are dropped.
6. Node A disconnects from peer B.
7. If no other peer diffuses `v_1..v_N`, quorum for round `R` is never reached.
8. No certificate is generated for round `R`; the honest chain receives no Peras weight boost.

The same sequence applies to `processCerts` with `PerasCert` objects. [7](#0-6) [8](#0-7)

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
