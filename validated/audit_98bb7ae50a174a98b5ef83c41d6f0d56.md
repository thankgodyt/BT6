Audit Report

## Title
Decimal Normalization to Zero Permanently Freezes Bridged Funds - (File: `near/omni-bridge/src/lib.rs`)

## Summary

`init_transfer` accepts and locks user tokens without verifying that the post-normalization transfer amount is non-zero. `sign_transfer` subsequently always panics with `InvalidAmountToTransfer` for such transfers. Because no cancel or refund path exists, the locked tokens are permanently irrecoverable.

## Finding Description

`normalize_amount` applies floor division to convert a NEAR-side token amount to the destination chain's decimal precision: [1](#0-0) 

The code's own doc-comment acknowledges this: *"When fee = 0, dust stays locked/burned."* However, the problem is not limited to sub-unit dust — when the entire net amount is smaller than `10^(origin_decimals - decimals)`, the whole transfer amount normalizes to zero.

`init_transfer` performs only one amount check before locking tokens: [2](#0-1) 

There is no guard that `normalize_amount(amount - fee) > 0`. `init_transfer_internal` then locks or burns the tokens and returns `U128(0)`, signalling to the NEP-141 runtime that zero tokens should be refunded to the caller: [3](#0-2) 

When a relayer later calls `sign_transfer`, it computes the normalized amount and enforces: [4](#0-3) 

This `require!` panics, reverting the entire `sign_transfer` call while leaving the transfer message in `pending_transfers`. `sign_transfer_callback` only removes the transfer message on MPC signing success when the fee is zero — a branch that is never reached because `sign_transfer` panics before the MPC call: [5](#0-4) 

No public `cancel_transfer` or refund function exists in the contract. The grep results confirm `remove_transfer_message` is only called internally in the two paths above, neither of which is reachable for a zero-normalized transfer.

## Impact Explanation

This directly matches the Critical allowed impact: **permanent freezing of bridged funds**. The user's tokens are locked or burned inside the bridge contract with no mechanism to recover them. The transfer can never be signed (always panics at the normalization guard), never finalized, and never refunded. The funds are unrecoverable.

## Likelihood Explanation

The condition is reachable by any unprivileged user via the standard `ft_transfer_call` NEP-141 entry point — no special role or privilege is required. It is triggered for any token registered with `origin_decimals > decimals` (e.g., 24 NEAR-side decimals bridging to an 18-decimal EVM chain, a common real-world configuration). Any transfer of fewer than `10^(origin_decimals - decimals)` base units triggers the freeze. Sending small or "dust" amounts is a common user pattern, making accidental triggering realistic.

## Recommendation

Add a normalization check inside `init_transfer` before accepting and locking tokens, mirroring the existing guard in `sign_transfer`:

```rust
if let Some(token_address) = self.get_token_address(
    init_transfer_msg.get_destination_chain(),
    self.get_token_id(&OmniAddress::Near(token_id.clone())),
) {
    if let Some(decimals) = self.token_decimals.get(&token_address) {
        let normalized = Self::normalize_amount(
            transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
            decimals,
        );
        require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
    }
}
```

This prevents the irrecoverable locked-funds state by rejecting the transfer before tokens are taken from the user.

## Proof of Concept

1. Register a token with `origin_decimals = 24`, `decimals = 18` (factor of `10^6`).
2. Alice calls `ft_transfer_call` with `amount = 500_000` and `fee = 0`.
3. `init_transfer` passes the `fee < amount` check (0 < 500_000), locks 500,000 units, stores the transfer message, and returns `U128(0)` — Alice's tokens are taken with no refund.
4. A relayer calls `sign_transfer` for Alice's transfer ID.
5. `normalize_amount(500_000, {origin: 24, dest: 18}) = 500_000 / 1_000_000 = 0`.
6. `require!(0 > 0, BridgeError::InvalidAmountToTransfer)` panics → transaction reverts, transfer message remains in storage.
7. Steps 4–6 repeat indefinitely. Alice's 500,000 units are permanently frozen with no recovery path.
