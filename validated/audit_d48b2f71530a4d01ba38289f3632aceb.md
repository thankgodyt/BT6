### Title
Front-Running `request_refund` Allows Attacker to Redirect User's BTC Refund to Attacker-Controlled Address — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

The `request_refund` function uses `utxo_storage_key` (`{txid}@{vout}`) as the sole identifier for refund requests without binding the `refund_address` parameter to the caller's identity. When `deposit_msg.refund_address` is `None`, an attacker who observes a user's pending `request_refund` transaction can front-run it with the same UTXO proof but substitute their own BTC address as `refund_address`. The user's transaction is then rejected as a duplicate, and after the timelock the BTC is sent to the attacker.

---

### Finding Description

`request_refund` is a publicly callable, payable function: [1](#0-0) 

It delegates to `internal_request_refund`, which verifies the BTC transaction via the Light Client and then calls `request_refund_callback`. Inside the callback, the refund request key is derived exclusively from the transaction ID and output index: [2](#0-1) 

The duplicate guard then rejects any second request for the same UTXO: [3](#0-2) 

The `RefundRequest` struct stores `refund_address` as a plain field — it is not part of the key and is not bound to the caller's identity: [4](#0-3) 

The only guard against `refund_address` substitution is the optional pre-authorization check: [5](#0-4) 

This check is skipped entirely when `deposit_msg.refund_address` is `None` — the "unsafe" refund path. In that case the deposit address is derived solely from `deposit_msg` (without the `refund_address` parameter), so the script-pubkey verification passes regardless of what `refund_address` the caller supplies: [6](#0-5) 

After the timelock, `execute_refund` is callable by anyone (no role restriction beyond the timelock duration), and `finalize_refund_with_psbt` builds the refund output directly from the stored `refund_address`: [7](#0-6) 

---

### Impact Explanation

**Critical.** An attacker who wins the race stores a `RefundRequest` with their own BTC address for the victim's UTXO. The legitimate user's `request_refund` call is permanently blocked by the duplicate guard. After the timelock elapses, `execute_refund` constructs and signs a Bitcoin transaction paying the attacker's address via MPC. The victim's deposited BTC is irreversibly transferred to the attacker. The victim also loses the attached NEAR storage deposit paid with `request_refund`.

---

### Likelihood Explanation

**Low.** NEAR Protocol does not expose a public mempool in the same way as Ethereum, making reliable front-running harder. However, NEAR transactions are observable by validators and infrastructure operators before finalization, and the attack requires no special privilege — only the ability to submit a transaction with the same UTXO proof and a different `refund_address` before the victim's transaction is included. The attack is most practical for a malicious relayer or validator who can observe and reorder transactions within a shard. The required attached deposit raises the cost but is negligible compared to the BTC value at stake.

---

### Recommendation

1. **Short term:** Bind the `refund_address` to the caller's NEAR account ID by including `predecessor_account_id()` in the `RefundRequest` and verifying it on `execute_refund`. Alternatively, require that `deposit_msg.refund_address` is always set (eliminating the unsafe path entirely).
2. **Long term:** Include the caller's account ID in the `utxo_storage_key` (e.g., `{txid}@{vout}@{caller}`) so that each user can register their own refund request for the same UTXO independently, analogous to using `swapId` (which includes the initiator) as the primary identifier in MesonPools.

---

### Proof of Concept

1. Alice sends BTC to her deposit address derived from `DepositMsg { recipient_id: "alice.near", refund_address: None, ... }`.
2. Alice calls `request_refund(deposit_msg, refund_address="alice_btc_addr", tx_bytes, vout, proof, None)` with the required NEAR storage deposit attached.
3. An attacker observes Alice's pending transaction and immediately calls `request_refund(deposit_msg, refund_address="attacker_btc_addr", tx_bytes, vout, proof, None)` with the same UTXO proof but their own BTC address.
4. The attacker's transaction is included first. `request_refund_callback` derives the deposit address from `deposit_msg` (which does not include `refund_address`), passes the script-pubkey check, and stores `RefundRequest { refund_address: "attacker_btc_addr", ... }` under `utxo_storage_key`.
5. Alice's transaction is included next. The duplicate guard at `refund.rs:544–547` fires: `"Refund request already exists for this UTXO"`. Alice's transaction reverts and she loses her attached deposit.
6. After `unsafe_refund_timelock_sec` elapses (assuming the DAO does not intervene), the attacker calls `execute_refund(utxo_storage_key, None)`.
7. `finalize_refund_with_psbt` builds a Bitcoin transaction paying `"attacker_btc_addr"` and submits it to MPC for signing. Alice's BTC is sent to the attacker.
