### Title
`validatePerasCert` Unconditionally Accepts All Inbound Peras Certificates Without Cryptographic Verification, Enabling Unauthorized Certificate Injection - (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` function always returns `Right` (success) for every certificate it receives, performing zero cryptographic or structural validation. This function is wired directly into the live Peras certificate diffusion inbound handler. Any unprivileged peer can craft and submit arbitrary `PerasCert` values — one per round — that are unconditionally accepted and persisted to the `ChainDB`, injecting unauthorized Peras weight boosts that manipulate chain selection.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub wired into production:**

The degenerate `BlockSupportsPeras` instance in `Block/SupportsPeras.hs` is the only instance in scope (it matches all `StandardHash blk`). Its `validatePerasCert` implementation is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

The `PerasCert` data type in this same instance carries only a round number and a block point — **no signature field exists**:

```haskell
data PerasCert blk = PerasCert
  { pcCertRound :: PerasRoundNo
  , pcCertBoostedBlock :: Point blk
  }
``` [2](#0-1) 

**Production inbound handler wires this stub directly:**

`makePerasCertPoolWriterFromChainDB` passes `validatePerasCert mkPerasParams` as the validation callback with an explicit `TODO` noting it is not yet replaced:

```haskell
opwAddObjects = \certs ->
    processCerts
      systemTime
      (ChainDB.getPerasCertIds chainDB)
      -- TODO replace when actual plumbing is in place
      (validatePerasCert mkPerasParams)
      (void . ChainDB.addPerasCertAsync chainDB)
      certs
``` [3](#0-2) 

This writer is then passed directly to the live `hPerasCertDiffusionClient` handler in `NodeToNode.hs`:

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      ...
``` [4](#0-3) 

**`processCerts` only deduplicates by round number — it does not add any validation:**

```haskell
let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
``` [5](#0-4) 

**Contrast with `validatePerasVote` (votes):** The analogous vote path passes `pure (PerasVoteStakeDistr mempty)` as the stake distribution, which causes all votes to fail the `lookupPerasVoteStake` check and be rejected. No such mitigation exists for certificates — `validatePerasCert` accepts every cert regardless. [6](#0-5) 

---

### Impact Explanation

**Impact: Critical — Bypass of Peras certificate verification enabling unauthorized certificate acceptance.**

The Peras protocol assigns a weight boost (`vpcCertBoost`) to blocks referenced by accepted certificates, directly influencing chain selection. By injecting one forged `PerasCert` per round (the only deduplication gate), an unprivileged peer can:

1. Boost an arbitrary block point for any round, causing honest nodes to prefer a non-canonical chain.
2. Suppress the legitimate certificate for a round by pre-filling the round's slot in the DB with a forged cert (since `processCerts` skips certs whose round is already present).
3. Cause divergent chain selection across nodes that receive different forged certificates, breaking consensus safety.

This matches the allowed impact scope: **"Critical. Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance."**

---

### Likelihood Explanation

**High.** The attacker precondition is only a standard peer connection to any node running the Peras cert diffusion protocol. No keys, stake, or privileged access are required. The `PerasCert` wire format is fully specified and serialisable: [7](#0-6) 

The attack is one crafted CBOR message per round over the existing `perasCertDiffusionProtocol` miniprotocol channel.

---

### Recommendation

1. **Immediate:** Add a guard in `makePerasCertPoolWriterFromChainDB` (or `processCerts`) that rejects all certificates until a real `validatePerasCert` implementation is in place — mirroring the `PerasVoteStakeDistr mempty` guard used for votes.
2. **Structural:** The `PerasCert` wire type must include a cryptographic aggregate signature (analogous to `WFALSCert`'s `AggregateVoteSignature`), and `validatePerasCert` must verify it against the registered committee keys before accepting any certificate.
3. **Tracking:** Resolve `https://github.com/tweag/cardano-peras/issues/120` before enabling Peras cert diffusion on any network where chain selection integrity matters.

---

### Proof of Concept

**Attacker-controlled entry path:**

```
Attacker peer
  → sends MsgObjects [PerasCert { pcCertRound = R, pcCertBoostedBlock = B }]
    over perasCertDiffusionProtocol channel
  → objectDiffusionInbound calls opwAddObjects [cert]
  → processCerts: cert not in DB for round R → passes filter
  → validatePerasCert mkPerasParams cert → Right (ValidatedPerasCert cert boost)
  → ChainDB.addPerasCertAsync: cert stored, weight boost applied to block B
  → chain selection now prefers B over honest tip
```

No cryptographic material is needed. The `PerasCert` CBOR encoding is two fields (round number + block point hash), both attacker-controlled. One such message per round is sufficient to permanently occupy that round's certificate slot in the DB and influence chain selection for all downstream consumers of that node's state. [8](#0-7)
