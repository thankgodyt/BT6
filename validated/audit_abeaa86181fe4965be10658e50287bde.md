### Title
Attacker Can Front-Run `request_refund()` to DOS or Redirect Refund Funds — (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary
The publicly callable `request_refund()` function accepts a BTC transaction proof that is visible in the NEAR mempool before inclusion. An attacker can front-run a legitimate `request_refund()` call by submitting the same proof with an attacker-controlled `refund_address`, causing the original transaction to fail and potentially redirecting the user's BTC to the attacker.

### Finding Description

`request_refund()` is publicly callable — it has no individual `#[trusted_relayer]` guard, unlike `verify_refund_finalize` and `remove_refund_pending_tx_id` in the same impl block which do carry that guard individually. [1](#0-0) 

When `deposit_msg.refund_address` is `None`, the function accepts any caller-supplied `refund_address` without binding it to the depositor's identity: [2](#0-1) 

In `request_refund_callback`, the uniqueness check is keyed only on `utxo_storage_key` (derived from `tx_id` and `vout`), not on `refund_address`: [3](#0-2) 

**Attack path:**

1. User calls `request_refund(deposit_msg={..., refund_address: None}, refund_address="user_btc_addr", tx_bytes, vout, proof, None)`.
2. Attacker observes the pending NEAR transaction in the mempool and extracts `deposit_msg`, `tx_bytes`, `vout`, and `proof`.
3. Attacker submits `request_refund(deposit_msg={..., refund_address: None}, refund_address="attacker_btc_addr", tx_bytes, vout, proof, None)` with higher priority.
4. Attacker's callback runs first; a `RefundRequest` is stored with `refund_address = "attacker_btc_addr"`.
5. User's callback panics: `"Refund request already exists for this UTXO"`. [4](#0-3) 

6. After `unsafe_refund_timelock_sec` elapses (the longer timelock applied when `deposit_msg.refund_address` is `None`), the attacker calls `execute_refund` and the BTC is sent to the attacker's address. [5](#0-4) 

### Impact Explanation

**DOS (certain):** The legitimate user's `request_refund` call always fails once the attacker's request is registered for the same UTXO. The user cannot re-submit until the attacker's request is resolved.

**Fund redirection (conditional):** If the DAO/Operator does not actively monitor and reject the malicious refund request within `unsafe_refund_timelock_sec`, the user's deposited BTC is sent to the attacker's Bitcoin address. This constitutes a theft of bridged funds from a user who was attempting a legitimate refund.

The `unsafe_refund_timelock_sec` is a partial mitigation but relies entirely on off-chain operator vigilance; it is not an on-chain guarantee.

### Likelihood Explanation

NEAR Protocol transactions are visible in the mempool before block inclusion. The attacker needs only to:
- Monitor the NEAR mempool for `request_refund` calls where `deposit_msg.refund_address` is `None`.
- Replay the same proof with a different `refund_address`.

No privileged access, leaked keys, or third-party compromise is required. The attack is straightforward for any NEAR node operator or mempool observer.

### Recommendation

1. **Bind `refund_address` to the depositor**: Require `deposit_msg.refund_address` to be set (non-`None`) so the refund destination is fixed at deposit time and cannot be overridden by a front-runner.
2. **Idempotent duplicate handling**: If a refund request already exists for the UTXO with identical parameters, treat the second call as a no-op (success) rather than a panic, analogous to the try/catch pattern recommended in M-02.
3. **Caller binding**: Record the `predecessor_account_id` of the `request_refund` caller and require that only that account (or DAO/Operator) can call `execute_refund` for the resulting request.

### Proof of Concept

```
1. Alice sends BTC to deposit address derived from
   deposit_msg = { recipient_id: "alice.near", refund_address: None, ... }

2. Alice calls on NEAR:
   request_refund(deposit_msg, "alice_btc_addr", tx_bytes, vout, proof, None)
   [Transaction is visible in NEAR mempool]

3. Attacker calls on NEAR (higher gas / same block):
   request_refund(deposit_msg, "attacker_btc_addr", tx_bytes, vout, proof, None)

4. Attacker's request_refund_callback executes first:
   → RefundRequest { refund_address: "attacker_btc_addr", ... } stored

5. Alice's request_refund_callback panics:
   → "Refund request already exists for this UTXO"

6. DAO/Operator does not reject within unsafe_refund_timelock_sec.

7. Attacker calls execute_refund(utxo_storage_key, None).
   → BTC is sent to "attacker_btc_addr" via MPC signing pipeline.
   → Alice's deposit is stolen.
``` [6](#0-5) [7](#0-6)

    pub fn request_refund(

        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,

        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
