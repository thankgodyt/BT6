### Title
Missing `refund_address` Validation in `request_refund` Allows Attacker to Permanently Brick a Victim's Refund Request — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`request_refund` stores the caller-supplied `refund_address` string into persistent state without validating it as a well-formed Bitcoin/Zcash address. Address parsing is deferred to `execute_refund`, where a panic on an invalid address leaves the refund request permanently un-executable. Because a duplicate-request guard blocks any second `request_refund` for the same UTXO, the victim's refund path is bricked until a DAO/Operator manually rejects the stuck entry.

---

### Finding Description

In `request_refund_callback`, the `refund_address` argument is written directly into `RefundRequest` with no format check: [1](#0-0) 

The only address-related guard is a string-equality check against `deposit_msg.refund_address` when that field is `Some`; for the common case where `deposit_msg.refund_address` is `None`, any arbitrary string is accepted: [2](#0-1) 

Validation is deferred to `build_refund_output`, called inside `execute_refund`, where `Address::parse(...).expect("Invalid refund address")` panics on a malformed string: [3](#0-2) 

Once the bad request is stored, the duplicate guard in `request_refund_callback` prevents any corrective re-submission for the same UTXO: [4](#0-3) 

`request_refund` carries no caller-identity restriction — any NEAR account can submit a refund request for any deposit UTXO whose `deposit_msg.refund_address` is `None`: [5](#0-4) 

This is the direct analog of the reported `setInterestRateModel` pattern: state (the refund request) is committed before the new "model" (the address) is validated, and a faulty value leaves the system in a broken intermediate state that cannot self-recover.

---

### Impact Explanation

An attacker who front-runs a victim's `request_refund` call with an identical `deposit_msg`/`tx_bytes` but an invalid `refund_address` (e.g., `"x"`) causes:

1. The refund request to be stored with the invalid address.
2. Every subsequent `execute_refund` call to panic, making the refund permanently un-executable through the normal path.
3. The victim to be blocked from re-submitting (duplicate guard).
4. The victim's BTC deposit to remain inaccessible via the refund mechanism until a DAO/Operator calls `reject_refund`.

This matches **Medium — attacker-triggered temporary locking of bridged funds / stuck bridge state requiring operator intervention**.

---

### Likelihood Explanation

- `request_refund` is fully public (no role gate, only a NEAR storage deposit).
- Deposit events (`LogDepositAddress`) are emitted on-chain, giving the attacker the `deposit_msg` needed to reconstruct the correct deposit path.
- The attacker only needs to pay the storage deposit (a small, fixed NEAR amount) and submit before the victim.
- The attack is repeatable: after DAO rejects the stuck request, the attacker can immediately re-submit another bad one.

Likelihood: **Medium**.

---

### Recommendation

Validate `refund_address` against the configured chain inside `request_refund_callback` before persisting the `RefundRequest`. The existing `Config::string_to_script_pubkey` (or a non-panicking variant) can be reused:

```rust
// In request_refund_callback, before building RefundRequest:
config.string_to_script_pubkey(&refund_address); // panics early, rolls back atomically
```

Alternatively, expose a `Result`-returning address parser and `require!` it succeeds, so the transaction reverts cleanly rather than storing an un-executable request. [6](#0-5) 

---

### Proof of Concept

1. Alice sends BTC to her bridge deposit address; the UTXO is not yet verified by a relayer.
2. Attacker observes the `LogDepositAddress` event, reconstructs `deposit_msg`, and calls:
   ```
   request_refund(
       deposit_msg = alice_deposit_msg,   // correct, matches on-chain output
       refund_address = "not_a_btc_addr", // invalid
       tx_bytes = alice_tx_bytes,
       vout = 0,
       proof = valid_inclusion_proof,
       gas_fee = None,
   )
   ```
   with the required NEAR storage deposit attached.
3. Light-client verification succeeds; `request_refund_callback` stores the `RefundRequest` with `refund_address = "not_a_btc_addr"`.
4. Anyone calls `execute_refund(alice_utxo_key, None)` → panics at `Address::parse("not_a_btc_addr", chain).expect(...)`.
5. Alice calls `request_refund` herself → reverts: `"Refund request already exists for this UTXO"`.
6. Alice's BTC refund is bricked; only a DAO/Operator `reject_refund` call can unblock her, and the attacker can immediately repeat step 2 after rejection.
