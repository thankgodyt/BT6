### Title
Peras Certificate Pool Accepts Arbitrary Future-Round Certificates, Enabling Indefinite Voting Suppression — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` implementation in the production `BlockSupportsPeras` instance is a stub that unconditionally returns `Right` for every certificate. Combined with the `PerasCertDB` invariant that `latestCertSeen` is always updated to the highest round number seen, any unprivileged peer can inject certificates for arbitrarily far future rounds. This makes the Peras voting rules VR-1A and VR-2A permanently unsatisfiable, suppressing honest node voting indefinitely — an exact structural analog to the Blend reward-dilution bug, where a time-based window is repeatedly extended with no rate limit.

---

### Finding Description

**Root cause 1 — stub validation always passes:** [1](#0-0) 

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

No check is performed on the certificate's round number, boosted block, committee membership, or signature. Every certificate from every peer passes.

**Root cause 2 — `processCerts` accepts any peer-supplied certificate:** [2](#0-1) 

`processCerts` calls `validateCert` (bound to the stub above), timestamps the certificate with the local wall-clock, and adds it to the database. The only deduplication guard is a round-number set membership check — it does not bound how far into the future a round number may be.

**Root cause 3 — `latestCertSeen` is monotonically updated to the highest round number:** [3](#0-2) 

```haskell
pcdsLatestCertSeen' = case pcdsLatestCertSeen pcds of
  Nothing -> Just cert
  Just prev
    | getPerasCertRound cert > getPerasCertRound prev -> Just cert
    | otherwise -> Just prev
```

The `prop_addCertLatestCertSeenMonotonic` invariant in the API confirms this is by design. [4](#0-3) 

**Root cause 4 — both voting rules depend on `latestCertSeen.round`:**

VR-1A requires the latest cert seen to be from exactly the previous round: [5](#0-4) 

VR-2A (cooldown exit) requires the latest cert seen to be at least `R = 487` rounds old: [6](#0-5) 

A node votes only if `VR-1 ∨ VR-2` holds: [7](#0-6) 

**Attack chain:**

If `latestCertSeen.round = N + K` (a future round) and the current round is `N`:
- VR-1A: `N == (N+K) + 1` → false for any `K > 1`
- VR-2A: `(N+K) + 487 ≤ N` → false for any `K ≥ 0`

The attacker sends a new cert for round `N + K + 1` before round `N + K + 1` is reached, keeping `latestCertSeen` perpetually ahead of the current round. This is structurally identical to the Blend `gulp_emissions` dilution: each call extends the window by a fixed amount with no minimum interval enforced.

The Peras parameters confirm the severity: `perasIgnoranceRounds = 487` and `perasCooldownRounds = 1928`, meaning a single future-round cert injection can suppress voting for hundreds of rounds. [8](#0-7) 

---

### Impact Explanation

An unprivileged peer can prevent any honest node from ever satisfying the Peras voting rules by repeatedly injecting certificates for future rounds. With no honest votes, no quorum is reached, no Peras certificates are generated, and chain selection degrades to pure Praos. This removes the stronger finality and adversarial-fork-resistance guarantees that Peras is designed to provide — a bypass of Peras voting authorization beyond the intended security assumptions.

This maps to the allowed scope: **"Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance"** and **"chain selection … bug that lets an unprivileged peer make an honest node prefer a … less-secure chain beyond the intended security assumptions."**

---

### Likelihood Explanation

Any peer connected via the object diffusion mini-protocol can send `PerasCert` objects. No stake, no keys, and no special privileges are required. The attack is repeatable with no rate limit: the only deduplication guard is per-round-number, so the attacker simply increments the round number on each injection. The attack is cheap and deterministic.

---

### Recommendation

1. **Implement real round-number bounds in `validatePerasCert`**: reject any certificate whose round number exceeds `currentRound + maxFutureRoundOffset` for a protocol-defined constant.
2. **Add a future-round guard in `processCerts` or `implAddCert`**: before updating `latestCertSeen`, verify the certificate's round is within a valid window of the current round.
3. **Enforce a minimum inter-injection interval** analogous to the Blend fix: track the last time a certificate for a given round range was accepted and reject new ones that arrive too soon.
4. **Resolve the TODO** at `BlockSupportsPeras.hs` issue #120 before any Peras-enabled deployment.

---

### Proof of Concept

```
1. Attacker connects as a peer to an honest node running Peras.
2. Attacker sends PerasCert { pcCertRound = currentRound + 1_000_000, ... }
   via the object diffusion mini-protocol.
3. processCerts calls validatePerasCert → always Right → cert is accepted.
4. implAddCert sets latestCertSeen.round = currentRound + 1_000_000.
5. VR-1A: currentRound == (currentRound + 1_000_000) + 1  → FALSE
   VR-2A: (currentRound + 1_000_000) + 487 ≤ currentRound → FALSE
6. Node cannot vote.
7. Before round currentRound + 1_000_001 is reached, attacker sends
   PerasCert { pcCertRound = currentRound + 2_000_000 }.
8. latestCertSeen.round advances again; voting remains suppressed.
9. Repeat indefinitely with no rate limit.
```

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
