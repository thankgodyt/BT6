### Title
Front-Running `request_refund` Redirects BTC Refund to Attacker-Controlled Address — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`request_refund` follows a two-step async pattern identical in structure to the vulnerable `depositWithPermit2` in the reference report: it first makes an external cross-contract call (`verify_transaction_inclusion_promise`) and then, in a callback, writes state (`refund_requests`). Because the callback's duplicate-check panics if the UTXO key already exists, an attacker who submits the same UTXO proof with a **different `refund_address`** before the victim's callback lands will (a) store a refund request pointing to the attacker's BTC address and (b) cause the victim's callback to revert, consuming the victim's attached storage deposit.

---

### Finding Description

`request_refund` is a public, permissionless function (no `#[trusted_relayer]` guard on the function itself, only an attached-deposit requirement): [1](#0-0) 

It calls `verify_transaction_inclusion_promise` (an external async call to the light-client contract) and chains `request_refund_callback` as the continuation: [2](#0-1) 

Inside `request_refund_callback`, the only guard against a duplicate is a hard `require!` that panics if the key already exists: [3](#0-2) 

When `deposit_msg.refund_address` is `None`, the caller-supplied `refund_address` is accepted without any ownership check: [4](#0-3) 

**Attack flow:**

1. Victim submits `request_refund(deposit_msg, "bc1q_victim…", tx_bytes, vout, proof, None)` with the required attached deposit.
2. The call dispatches `verify_transaction_inclusion_promise`; the callback is scheduled for the next block.
3. Attacker observes the in-flight transaction (NEAR mempool is public), copies `deposit_msg`, `tx_bytes`, `vout`, and `proof`, substitutes `refund_address = "bc1q_attacker…"`, and submits their own `request_refund` with the required deposit.
4. If the attacker's transaction is ordered before the victim's in the same block (or submitted in an earlier block), the attacker's `request_refund_callback` runs first and inserts the refund request keyed by `{tx_id}@{vout}` with the attacker's BTC address.
5. The victim's `request_refund_callback` then panics on `"Refund request already exists for this UTXO"`. The victim's attached deposit is consumed by the contract with no refund request created for them.
6. After `unsafe_refund_timelock_sec` elapses, anyone (including the attacker) calls `execute_refund`, and the bridge MPC-signs a transaction paying the victim's BTC to the attacker's address. [5](#0-4) 

---

### Impact Explanation

The attacker receives the victim's BTC refund. The victim additionally loses the NEAR storage deposit attached to `request_refund`. The bridge's `execute_refund` has no caller restriction and no ownership check on who receives the funds — it simply pays whatever `refund_address` is stored in the request: [6](#0-5) 

This constitutes **unauthorized redirection and theft of user BTC** — a Critical bridge impact.

The DAO/Operator can call `reject_refund` to cancel the malicious request, but this requires active monitoring. The `unsafe_refund_timelock_sec` window exists precisely to allow this intervention, but it is not guaranteed.

---

### Likelihood Explanation

- `request_refund` is publicly callable by any NEAR account that attaches the required deposit.
- All transaction parameters (`deposit_msg`, `tx_bytes`, `vout`, `proof`) are visible on-chain the moment the victim's transaction is submitted.
- The attacker's cost is only the storage deposit (a small NEAR amount), while the gain is the full BTC refund amount.
- NEAR's mempool ordering is not gas-price-based, but an attacker can submit in the same block or a prior block to win the race.
- The attack is especially viable for high-value refunds where the attacker's deposit cost is negligible relative to the stolen BTC.

---

### Recommendation

Wrap the duplicate-check in `request_refund_callback` in a non-panicking branch (analogous to the try-catch fix in the reference report). If a refund request already exists for the UTXO, verify that the stored `refund_address` matches the one in the current callback; if it does not, either reject silently and refund the caller's deposit, or require that `deposit_msg.refund_address` always be pre-set (making the `refund_address` parameter immutable and bound to the deposit message). The simplest fix is to bind `refund_address` to the deposit path at deposit time (i.e., require `deposit_msg.refund_address` to be `Some`) so that no caller-supplied address can differ from what was committed on-chain.

---

```
near call satoshi-bridge request_refund \
  '{"deposit_msg": {..., "refund_address": null}, "refund_address": "bc1q_victim", \

  --deposit 0.5 --accountId victim.near

  '{"deposit_msg": {..., "refund_address": null}, "refund_address": "bc1q_attacker", \
    "tx_bytes": "<base64>", "vout": 0, "proof": {...}, "gas_fee": null}' \
  --deposit 0.5 --accountId attacker.near

# After unsafe_refund_timelock_sec:
near call satoshi-bridge execute_refund \
  '{"utxo_storage_key": "<txid>@0", "chain_specific_data": null}' \
  --deposit 0.1 --accountId attacker.near
# → BTC sent to bc1q_attacker
```

```rust
    pub(crate) fn finalize_refund_with_psbt(
        &mut self,
        caller: AccountId,
        mut refund_request: RefundRequest,
        psbt: PsbtWrapper,
        refund_amount: u128,
        utxo_storage_key: String,
    ) {
        let gas_fee = refund_request.gas_fee;
        let refund_address = refund_request.refund_address.clone();

        let deposit_msg = refund_request.deposit_msg();
        let path = get_deposit_path(&deposit_msg);
        let vutxo = VUTXO::Current(UTXO {
            path,
            tx_bytes: refund_request.tx_bytes.0.clone(),
            vout: refund_request.vout,
            balance: u64::try_from(refund_request.amount)
                .unwrap_or_else(|_| env::panic_str("Amount overflow")),
        });

        let psbt_hex = psbt.serialize();
        let btc_pending_id = psbt.get_pending_id();

        if !self.check_account_exists(&caller) {
            self.internal_set_account(&caller, crate::Account::new(&caller));
        }
        self.require_pending_sign_capacity(&caller);

        let btc_pending_info = BTCPendingInfo {
            account_id: caller.clone(),
            btc_pending_id: btc_pending_id.clone(),
            transfer_amount: 0,
            actual_received_amount: refund_amount,
            withdraw_fee: 0,
            gas_fee,
            burn_amount: 0,
            psbt_hex,
            vutxos: vec![vutxo],
            signatures: vec![None; 1],
            tx_bytes_with_sign: None,
            create_time_sec: nano_to_sec(env::block_timestamp()),
            last_sign_time_sec: 0,
            state: PendingInfoState::Refund(OriginalState {
                stage: PendingInfoStage::PendingSign,
                max_gas_fee: gas_fee,
                last_rbf_time_sec: None,
                cancel_rbf_reserved: None,
            }),
        };

        require!(
            self.data_mut()
                .btc_pending_infos
                .insert(btc_pending_id.clone(), btc_pending_info.into())
                .is_none(),
            "pending info already exist"
        );
        self.internal_unwrap_mut_account(&caller)
            .btc_pending_sign_ids
            .insert(btc_pending_id.clone());

        // Mark UTXO as verified to prevent verify_deposit later
        self.data_mut()
            .verified_deposit_utxo
            .insert(utxo_storage_key.clone());

        Event::RefundExecuted {
            utxo_storage_key: utxo_storage_key.clone(),
            amount: refund_request.amount.into(),
            refund_address,
        }
        .emit();

        Event::GenerateBtcPendingInfo {
            account_id: &caller,
            btc_pending_id: &btc_pending_id,
        }
        .emit();

        // Keep the request (so `execute_refund` can be called again to re-create
        // the transaction) but mark it executed; it is removed only when the
        // refund is finalized in `verify_refund_finalize`.
        refund_request.executed = true;
        self.data_mut()
            .refund_requests
            .insert(utxo_storage_key, refund_request.into());
    }
```
