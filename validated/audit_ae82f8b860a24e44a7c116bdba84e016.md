### Title
Hardcoded `mkPerasParams` in Production Peras Certificate Ingest Fixes Chain-Selection Boost Weight and Quorum Threshold Without Any Governance Update Path — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs`)

---

### Summary

The production Peras certificate ingest path (`makePerasCertPoolWriterFromChainDB`) hardcodes `mkPerasParams` as the validation configuration for every inbound certificate received from an unprivileged peer. `mkPerasParams` is a compile-time constant that fixes the chain-selection boost weight (`perasWeight = 15`), the quorum stake threshold (`perasQuorumStakeThreshold = 3/4`), and all other Peras security parameters. There is no mechanism to update these values through on-chain governance, protocol-parameter updates, or node configuration. Any future need to adjust these parameters requires a code change and a hard fork.

---

### Finding Description

`mkPerasParams` is defined as a pure Haskell constant in `Ouroboros/Consensus/Peras/Params.hs`: [1](#0-0) 

It hardcodes, among others:
- `perasWeight = PerasWeight 15` — the weight boost added to any chain containing a Peras-certified block, used directly in chain selection.
- `perasQuorumStakeThreshold = PerasQuorumStakeThreshold (3/4)` — the fraction of stake required to form a valid certificate.
- `perasQuorumStakeThresholdSafetyMargin = PerasQuorumStakeThresholdSafetyMargin (2/100)`.

In the **production** certificate ingest path, this constant is passed directly as the validation configuration: [2](#0-1) 

The inline comment `-- TODO replace when actual plumbing is in place` confirms this is a known placeholder, but it is present in production code, not a test stub. The companion function `makePerasCertPoolWriterFromCertDB` carries the same hardcoding: [3](#0-2) 

The `vpcCertBoost` field of every accepted `ValidatedPerasCert` is set to `perasWeight params`, which is always `PerasWeight 15` when `params = mkPerasParams`: [4](#0-3) 

This boost value is then stored in the `PerasWeightSnapshot` and consumed by `weightBoostOfFragment` during chain selection: [5](#0-4) 

The security parameter `k` bounds the maximum rollback weight (`maxRollbackWeight`): [6](#0-5) 

With `k = 2160` and `perasWeight = 15`, the ratio `k / perasWeight = 144` certificates is the adversarial budget to overcome the rollback bound through accumulated boost weight. If the correct production value of `perasWeight` should be higher (as the Peras design document may require), the hardcoded value of 15 makes the chain-selection weight bound weaker than intended, and there is no on-chain path to correct it.

---

### Impact Explanation

**High — Chain selection bug that lets an unprivileged peer influence chain weight beyond intended security assumptions.**

The `perasWeight` field is the direct multiplier between the number of Peras certificates and the total chain weight boost. Because it is hardcoded at 15 and cannot be updated through governance or protocol parameters, two concrete problems arise:

1. **Wrong boost weight cannot be corrected without a hard fork.** If the finalized Peras CIP or security analysis requires a different value, the node will apply the wrong chain-selection weight to every certificate it processes, potentially causing it to prefer a less-secure chain or reject a more-secure one.

2. **Quorum threshold is equally frozen.** The hardcoded `perasQuorumStakeThreshold = 3/4` is used in `stakeAboveThreshold` and `votesReachQuorum`. If the threshold needs to be tightened or relaxed (e.g., in response to stake distribution changes), there is no update path. [7](#0-6) 

---

### Likelihood Explanation

**Medium.** Peras is not yet active on Cardano mainnet, so the immediate exploitability is limited to private testnets or future deployments. However, the code is in the production module (not a test library), is explicitly flagged as a TODO for replacement, and the hardcoded values are already being used in the `ChainDB`-level certificate writer. Any node that activates Peras will use these hardcoded parameters with no ability to adjust them through governance.

---

### Recommendation

Replace the hardcoded `mkPerasParams` call in both `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB` with a `PerasParams` value threaded from the node's `TopLevelConfig` (or equivalent configuration source). The `PerasParams` should be derived from on-chain protocol parameters (analogous to how `pbftSignatureThreshold` is read from the genesis config in `byronPBftParams`): [8](#0-7) 

This ensures that `perasWeight`, `perasQuorumStakeThreshold`, and all other Peras security parameters can be updated through the standard Cardano governance mechanism without requiring a code change or hard fork.

---

### Proof of Concept

**Entry path (unprivileged peer → production certificate ingest):**

1. A remote peer sends a `PerasCert` message over the Peras object-diffusion mini-protocol.
2. `makePerasCertPoolWriterFromChainDB` calls `processCerts` with `validatePerasCert mkPerasParams` as the validator.
3. `validatePerasCert` (degenerate instance) unconditionally returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight mkPerasParams }` — i.e., `PerasWeight 15` — regardless of the certificate's content.
4. The accepted certificate is stored in the `PerasCertDB` / `ChainDB` with boost weight 15.
5. On the next chain selection, `weightBoostOfFragment` adds 15 to the total weight of any chain fragment containing the boosted block.
6. Because `mkPerasParams` is a compile-time constant with no governance update path, step 3–5 will always use `PerasWeight 15` and `PerasQuorumStakeThreshold (3/4)`, even if the correct production values differ. [9](#0-8)

mkPerasParams :: PerasParams
mkPerasParams =
  -- Many of these parameters are provided with sensible default values for now,
  -- waiting for a final decision (in a future stage of the project) on the
  -- exact values to use. See https://github.com/tweag/cardano-peras/issues/97.
  --
  -- We set tentatively T_heal to 2B/asc = 600 slots, as the CIP suggests a
  -- bigO(B/asc) for that value so that sufficiently many blocks are produced to
  -- overcome an adversarially boosted block.
  --
  -- We also set tentatively perasCertArrivalThreshold (= X in the formal spec)
  -- to 30 slots (it must be strictly smaller than perasRoundLength)
  -- See https://github.com/tweag/cardano-peras/issues/88 and
  -- https://github.com/tweag/cardano-peras/issues/99 for more information on
  -- this parameter.
  --
  -- We also have T_cp = 129_600 and T_cq = 43_200 as per the design document
  PerasParams
    { -- ceil(T_heal + T_cq) / perasRoundLength) as per the design document
      perasIgnoranceRounds =
        PerasIgnoranceRounds 487
    , -- ceil(T_heal + T_cq + T_cp) / perasRoundLength) + 1 as per the design document
      perasCooldownRounds =
        PerasCooldownRounds 1928
    , -- must be between 30 and 900 as per the design document
      perasBlockMinSlots =
        PerasBlockMinSlots 90
    , -- equal to perasIgnoranceRounds as per the design document
      perasCertMaxRounds =
        PerasCertMaxRounds 487
    , perasCertArrivalThreshold =
        PerasCertArrivalThreshold 30
    , perasRoundLength =
        PerasRoundLength 90
    , perasWeight =
        PerasWeight 15
    , perasQuorumStakeThreshold =
        PerasQuorumStakeThreshold (3 / 4)
    , perasQuorumStakeThresholdSafetyMargin =
        PerasQuorumStakeThresholdSafetyMargin (2 / 100)
    }

makePerasCertPoolWriterFromChainDB ::
  (StandardHash blk, IOLike m) =>
  SystemTime m ->
  ChainDB m blk ->
  ObjectPoolWriter PerasRoundNo (PerasCert blk) m
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwObjectId = getPerasCertRound
    , opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          -- We do not want to block the writer thread on waiting for ChainSel
          -- side-effects to complete, so we use the async version of adding
          -- certs to the ChainDB and ignore the returned promise.
          -- The async action is still launched and executed behind the scenes
          -- even though we drop the promise.
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    , opwHasObject = do
        certIds <- ChainDB.getPerasCertIds chainDB
        pure $ \roundNo -> Set.member roundNo certIds
    }
