Audit Report

## Title
Missing EVM `block.chainid` in `finTransfer` Signed Payload Enables Cross-Chain Replay After Hard Fork - (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

## Summary
`OmniBridge.finTransfer` constructs its Borsh-encoded signed payload using `omniBridgeChainId`, a stored `uint8` protocol identifier, rather than the EVM-native `block.chainid`. After an EVM hard fork both chains share the same `omniBridgeChainId` and `nearBridgeDerivedAddress`, making any NEAR-MPC-signed `finTransfer` payload accepted on the canonical chain equally valid on the forked chain. Because `completedTransfers` is independent per-chain state, a nonce consumed on the canonical chain remains open on the fork, enabling an attacker to replay the transfer and receive tokens twice.

## Finding Description
`finTransfer` at lines 289–313 constructs the signed payload as:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.TransferMessage)),
    Borsh.encodeUint64(payload.destinationNonce),
    bytes1(payload.originChain),
    Borsh.encodeUint64(payload.originNonce),
    bytes1(omniBridgeChainId),          // stored uint8, NOT block.chainid
    Borsh.encodeAddress(payload.tokenAddress),
    Borsh.encodeUint128(payload.amount),
    bytes1(omniBridgeChainId),          // same stored uint8 again
    Borsh.encodeAddress(payload.recipient),
    ...
);
bytes32 hashed = keccak256(borshEncoded);
if (ECDSA.recover(hashed, signatureData) != nearBridgeDerivedAddress) {
    revert InvalidSignature();
}
``` [1](#0-0) 

`omniBridgeChainId` is a `uint8` set once at `initialize()` and never updated: [2](#0-1) [3](#0-2) 

The only replay guard is `completedTransfers[payload.destinationNonce]`, which is independent per-chain storage: [4](#0-3) 

After an EVM hard fork, both chains have identical `omniBridgeChainId`, identical `nearBridgeDerivedAddress`, and independent `completedTransfers` mappings. A signature produced by NEAR MPC for the canonical chain is byte-for-byte identical to what the forked chain would accept, because no EVM consensus-layer chain ID is included in the signed payload. Any `finTransfer` calldata submitted on the canonical chain after the fork point can be replayed on the forked chain where the nonce is still unset.

`SECURITY.md` explicitly documents `deployToken` as intentionally chain-agnostic, but makes no such statement for `finTransfer`, confirming the omission is unintentional: [5](#0-4) 

## Impact Explanation
This is a **chain/domain separation flaw enabling double-spending** of bridged funds, matching the Critical allowed impact: *"Cross-chain replay... or chain/domain separation flaw enabling invalid finalization or double-spending."* An attacker replays a legitimate `finTransfer` on the forked chain, causing the contract to mint bridge tokens or transfer native ETH to the recipient a second time while the NEAR side records only a single outbound transfer. For `tokenAddress == address(0)` transfers, the contract drains its own ETH balance on the forked chain.

## Likelihood Explanation
EVM hard forks are rare but have concrete historical precedent: the ETH/ETC split (2016, the original motivation for EIP-155) and the ETH/ETHPoW fork (2022, at the Merge). The attack requires no privileged access — any observer can collect signed `finTransfer` calldata from the canonical chain's mempool or transaction history and submit it on the forked chain. Relayers routinely batch and delay submissions, widening the window of exploitable nonces. No victim mistake or external collusion is required.

## Recommendation
Include `block.chainid` in the Borsh-encoded payload so that a NEAR MPC signature is cryptographically bound to a specific EVM consensus-layer chain ID:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.TransferMessage)),
    Borsh.encodeUint64(payload.destinationNonce),
    bytes1(payload.originChain),
    Borsh.encodeUint64(payload.originNonce),
    bytes1(omniBridgeChainId),
    Borsh.encodeAddress(payload.tokenAddress),
    Borsh.encodeUint128(payload.amount),
    bytes1(omniBridgeChainId),
    Borsh.encodeAddress(payload.recipient),
    Borsh.encodeUint256(block.chainid),   // add EVM chain ID
    ...
);
```

The NEAR side must include `block.chainid` when constructing the payload before requesting the MPC signature. This is the standard EIP-155 / EIP-712 domain-separation approach.

## Proof of Concept
1. At block N (pre-fork) a user initiates a NEAR → Ethereum transfer. NEAR MPC signs a `finTransfer` payload for `destinationNonce = 42`.
2. The EVM hard fork occurs at block N+1. Both chains now have identical `completedTransfers` state (nonce 42 unused on both) and identical `omniBridgeChainId` / `nearBridgeDerivedAddress`.
3. A relayer submits `finTransfer(sig, payload)` on the canonical chain at block N+2. `completedTransfers[42]` is set to `true` on the canonical chain; tokens are minted/transferred to the recipient.
4. An attacker copies the identical calldata and submits it on the forked chain. `completedTransfers[42]` is still `false` there. `ECDSA.recover(keccak256(borshEncoded), sig)` returns `nearBridgeDerivedAddress` (same on both chains). The signature check passes. Tokens are minted/transferred again to the recipient on the forked chain.
5. The recipient holds tokens on both chains; the NEAR bridge escrow has only been debited once.

A local fork test can reproduce this by: deploying `OmniBridge` on a local Anvil instance, snapshotting state, submitting a valid `finTransfer` on the snapshot, reverting to the snapshot (simulating the fork), and confirming the identical calldata succeeds again with a different `block.chainid` — demonstrating that the current code does not bind the signature to `block.chainid`.
