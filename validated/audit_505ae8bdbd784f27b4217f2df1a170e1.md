### Title
`min_withdraw_amount` guard in `ft_on_transfer` incorrectly blocks `DepositProtocolFee` messages — (File: `contracts/satoshi-bridge/src/api/token_receiver.rs`)

---

### Summary

The `require!` check enforcing `min_withdraw_amount` is placed at the top of `ft_on_transfer`, before the message type is parsed. It is semantically a withdrawal guard, but it applies equally to `DepositProtocolFee` transfers. Any protocol fee deposit whose amount falls below `min_withdraw_amount` causes the function to panic, the NEP-141 transfer to revert, and the fee accounting to be skipped — an exact structural analog to the external report's "guard meant for one action silently skips a separate accounting update."

---

### Finding Description

`ft_on_transfer` handles two logically distinct operations: [1](#0-0) 

```rust
let amount = amount.into();
require!(
    amount >= self.internal_config().min_withdraw_amount,
    "Invalid amount"
);
```

This guard is placed **before** the message is parsed, so it fires for every incoming token transfer regardless of intent. The two branches that follow are: [2](#0-1) 

- `DepositProtocolFee` — updates `acc_collected_protocol_fee` and `cur_available_protocol_fee`, then accepts all tokens (returns `U128(0)`).
- `Withdraw` — initiates the BTC withdrawal pipeline.

`min_withdraw_amount` is a withdrawal-specific policy. It has no semantic relationship to protocol fee deposits. When a `DepositProtocolFee` transfer arrives with an amount below that threshold, the `require!` panics, the NEP-141 contract reverts the transfer (tokens returned to sender), and the fee accounting lines are never reached: [3](#0-2) 

```rust
TokenReceiverMessage::DepositProtocolFee => {
    self.data_mut().acc_collected_protocol_fee += amount;   // never reached
    self.data_mut().cur_available_protocol_fee += amount;   // never reached
    ...
    PromiseOrValue::Value(U128(0))
}
```

This is structurally identical to the external report: a guard meant to stop one action (small withdrawals) also silently stops a separate accounting update (protocol fee collection).

---

### Impact Explanation

**Medium.** Any `DepositProtocolFee` transfer below `min_withdraw_amount` is rejected. The bridge's fee accounting (`acc_collected_protocol_fee`, `cur_available_protocol_fee`) is not updated. While tokens are returned to the sender (no permanent lock in this case), the bridge cannot collect protocol fees below the withdrawal threshold, breaking the fee-collection invariant. This constitutes harmful smart-contract behavior: a broken callback path that silently drops valid protocol-level inputs, matching the "broken callback rollback / stuck bridge state" medium impact class.

---

### Likelihood Explanation

**Medium.** The `DepositProtocolFee` message type is a distinct, documented bridge operation callable by any token holder or operator. The `min_withdraw_amount` is a withdrawal-specific configuration value with no documented relationship to fee deposits. Any caller — including the protocol itself — who sends a fee deposit below that threshold will have the transaction silently fail. The misconfiguration is reachable by any unprivileged NEAR account that calls `ft_transfer_call` on the nBTC contract with a `DepositProtocolFee` message.

---

### Recommendation

Move the `min_withdraw_amount` check inside the `Withdraw` match arm so it only applies to withdrawal messages:

```rust
fn ft_on_transfer(...) -> PromiseOrValue<U128> {
    let amount = amount.into();
    // Remove the top-level require! here
    let message = serde_json::from_str::<TokenReceiverMessage>(&msg).expect("INVALID MSG");
    let token_id = env::predecessor_account_id();
    require!(token_id == self.internal_config().nbtc_account_id, "Invalid token_id");
    match message {
        TokenReceiverMessage::DepositProtocolFee => {
            // No minimum-amount restriction for fee deposits
            self.data_mut().acc_collected_protocol_fee += amount;
            self.data_mut().cur_available_protocol_fee += amount;
            ...
        }
        TokenReceiverMessage::Withdraw { ... } => {
            require!(
                amount >= self.internal_config().min_withdraw_amount,
                "Invalid amount"
            );
            ...
        }
    }
}
```

---

### Proof of Concept

1. Alice holds nBTC and wants to deposit a small protocol fee (e.g., 500 satoshis) into the bridge.
2. Alice calls `ft_transfer_call` on the nBTC contract with `amount = 500` and `msg = "DepositProtocolFee"`.
3. The nBTC contract calls `ft_on_transfer` on the bridge.
4. The bridge's `require!(amount >= self.internal_config().min_withdraw_amount, "Invalid amount")` fires (500 < `min_withdraw_amount`).
5. The call panics; the NEP-141 standard reverts the transfer and returns 500 satoshis to Alice.
6. `acc_collected_protocol_fee` and `cur_available_protocol_fee` are never updated.
7. The bridge cannot collect protocol fees below the withdrawal threshold, and any caller attempting to do so receives a misleading "Invalid amount" error unrelated to the actual operation they requested. [4](#0-3)
