### Title
Missing Ownership Validation in `withdraw_rbf` Allows Any User to Initiate RBF on Another User's Pending Withdrawal - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary
`withdraw_rbf` is a public, unpermissioned function that allows any caller to trigger a Replace-By-Fee (RBF) operation on any pending withdrawal, regardless of ownership. The function uses `env::predecessor_account_id()` (the caller) for both the capacity check and the account passed to `withdraw_rbf_chain_specific`, without ever verifying that the caller owns the pending withdrawal identified by `original_btc_pending_verify_id`. This is the direct analog of the reported NFT bug: the wrong address is used in the authorization check — the caller's own account is checked instead of the pending withdrawal owner's account.

### Finding Description

In `bridge.rs`, `withdraw_rbf` is defined as a public function with no role guard:

```rust
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,
    output: Vec<TxOut>,
    chain_specific_data: Option<ChainSpecificData>,
) {
    let account_id = env::predecessor_account_id();       // ← caller, not owner
    self.require_pending_sign_capacity(&account_id);      // ← checks caller's capacity

    self.withdraw_rbf_chain_specific(
        account_id,                                        // ← caller passed as owner
        original_btc_pending_verify_id,
        output,                                            // ← attacker-controlled outputs
        chain_specific_data,
    );
}
```

Every `BTCPendingInfo` record stores the original withdrawal owner in its `account_id` field. The correct pattern — demonstrated by the privileged `cancel_withdraw` function — is to look up the owner from the pending info and use that account for both the capacity check and downstream logic:

```rust
// cancel_withdraw (DAO/Operator only) — correct pattern
let user_account_id = self
    .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
    .account_id
    .clone();                                              // ← owner from pending info
self.require_pending_sign_capacity(&user_account_id);     // ← checks owner's capacity
self.cancel_withdraw_chain_specific(
    user_account_id, ...                                   // ← owner passed downstream
);
```

`withdraw_rbf` performs no equivalent ownership lookup. An attacker with zero pending sign transactions trivially passes `require_pending_sign_capacity` on their own account, then drives `withdraw_rbf_chain_specific` with their own `account_id` and fully attacker-controlled `output: Vec<TxOut>` against any victim's `original_btc_pending_verify_id`.

### Impact Explanation

The attacker-controlled `output` parameter specifies the Bitcoin transaction outputs for the replacement transaction. If `withdraw_rbf_chain_specific` does not independently re-validate that the destination address matches the original withdrawal's `target_btc_address` (a check that is absent from the public entry point), the attacker can redirect the victim's BTC to an attacker-controlled Bitcoin address. The MPC network will sign the replacement transaction because it is presented as a valid PSBT from the bridge contract. Once broadcast and confirmed, the victim's locked nBTC is burned while their BTC is delivered to the attacker. This constitutes unauthorized redirection of bridge-controlled funds — a Critical impact under the allowed scope. At minimum, even if output validation exists downstream, the attacker associates the new RBF pending info with their own account instead of the victim's, corrupting per-account pending-sign accounting and potentially causing stuck withdrawal state requiring operator intervention (Medium impact).

### Likelihood Explanation

`withdraw_rbf` is a fully public function with no `#[access_control_any]` or `#[trusted_relayer]` guard. Any NEAR account can call it at any time. The only prerequisite is knowing a valid `original_btc_pending_verify_id`, which is emitted as a public on-chain event (`Event::GenerateBtcPendingInfo`) at withdrawal initiation. Likelihood is High.

### Recommendation

Mirror the ownership lookup used in `cancel_withdraw`: retrieve the `account_id` from the pending info and assert it equals `env::predecessor_account_id()` before proceeding.

```rust
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,
    output: Vec<TxOut>,
    chain_specific_data: Option<ChainSpecificData>,
) {
    let caller = env::predecessor_account_id();
    let account_id = self
        .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
        .account_id
        .clone();
    require!(
        account_id == caller,
        "Only the withdrawal owner can initiate RBF"
    );
    self.require_pending_sign_capacity(&account_id);
    self.withdraw_rbf_chain_specific(
        account_id,
        original_btc_pending_verify_id,
        output,
        chain_specific_data,
    );
}
```

### Proof of Concept

1. Alice calls `ft_transfer_call` with a `Withdraw` message, creating a `BTCPendingInfo` with `account_id = alice` and emitting `btc_pending_id = X`.
2. Attacker (Bob) observes `X` from on-chain events.
3. Bob calls `withdraw_rbf(X, [TxOut { value: alice_amount - fee, script_pubkey: bob_btc_address }], None)`.
4. Bob's own account has no pending sign transactions, so `require_pending_sign_capacity(&bob)` passes.
5. `withdraw_rbf_chain_specific(bob, X, bob_outputs, None)` is invoked with Bob's account and Bob's BTC address as the output.
6. The MPC signs the replacement PSBT; the signed transaction is broadcast.
7. Alice's BTC is delivered to Bob's Bitcoin address; Alice's nBTC is burned. [1](#0-0) [2](#0-1) [3](#0-2)
