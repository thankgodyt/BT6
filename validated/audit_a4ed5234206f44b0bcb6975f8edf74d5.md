### Title
Front-Running `request_refund` Allows Attacker to Redirect BTC Refunds to Attacker-Controlled Address — (File: `contracts/satoshi-bridge/src/refund.rs`, `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

`request_refund` is a public, permissionless function. When a user submits a refund request with `deposit_msg.refund_address = None`, any NEAR account can observe the pending transaction and front-run it using the same `deposit_msg`, `tx_bytes`, `vout`, and `proof` — but substituting an attacker-controlled `refund_address`. The first request to land wins the `utxo_storage_key` slot, blocking the legitimate user's refund and routing the BTC to the attacker's address once the timelock expires.

---

### Finding Description

`request_refund` in `bridge.rs` carries no `#[trusted_relayer]` guard and no caller-ownership check: [1](#0-0) 

Inside `internal_request_refund`, the only constraint on `refund_address` is that it must equal `deposit_msg.refund_address` **when that field is `Some`**. When it is `None`, any address is accepted without restriction: [2](#0-1) 

After the Light Client callback resolves, `request_refund_callback` derives the storage key from the Bitcoin transaction and checks for duplicates: [3](#0-2) 

The key `utxo_storage_key = {tx_id}@{vout}` is deterministic and public (the Bitcoin transaction is on-chain). There is **no check** that the caller is the `recipient_id` named in `deposit_msg`, and no check that `refund_address` is controlled by the depositor.

**Attack path:**

1. User sends BTC to a bridge deposit address derived from `deposit_msg` (with `refund_address: None`).
2. User submits `request_refund` with their own BTC address as `refund_address`.
3. Attacker observes the pending NEAR transaction, copies `deposit_msg`, `tx_bytes`, `vout`, and `proof`, and submits their own `request_refund` with an attacker-controlled `refund_address`.
4. Attacker's transaction lands first; `refund_requests[utxo_storage_key]` is populated with the attacker's address.
5. User's `request_refund` fails: `"Refund request already exists for this UTXO"`.
6. `execute_refund` is public — anyone can call it after `unsafe_refund_timelock_sec` elapses: [4](#0-3) 

7. The refund PSBT is built using `refund_request.refund_address` (the attacker's address): [5](#0-4) 

The `unsafe_refund_timelock_sec` path (triggered when `deposit_msg.refund_address` is `None`) is explicitly designed to give DAO/Operator time to reject suspicious requests: [6](#0-5) 

However, `reject_refund` is restricted to DAO/Operator — the legitimate user cannot self-rescue: [7](#0-6) 

---

### Impact Explanation

**Immediate (guaranteed):** The legitimate user's `request_refund` is permanently blocked for that UTXO — a stuck bridge state requiring operator intervention.

**Escalated (if DAO/Operator fails to monitor and reject within `unsafe_refund_timelock_sec`):** The user's deposited BTC is sent to the attacker's Bitcoin address via the MPC signing pipeline. This constitutes a significant, direct loss of user funds.

This matches the allowed impact: *"Medium. Bypass of bridge limits or policies, or attacker-triggered temporary locking of bridged funds"* at minimum, escalating to *"Critical. Significant loss, theft, destruction, or permanent locking of user or protocol funds"* if the operator window is missed.

---

### Likelihood Explanation

- `request_refund` is fully public and requires only a small NEAR storage deposit.
- All inputs (`deposit_msg`, `tx_bytes`, `vout`, `proof`) are visible in the NEAR mempool before the transaction is finalized.
- NEAR's mempool is public; an attacker running a node or monitoring the RPC can observe pending transactions.
- The attacker only needs to submit one transaction with a higher nonce priority or in the same block before the victim's callback resolves.
- No special role, leaked key, or privileged access is required.

---

### Recommendation

1. **Bind the refund request to the caller:** Store `env::predecessor_account_id()` in `RefundRequest` and require that only that account (or DAO/Operator) can be the `refund_address` beneficiary, or at minimum that only the original requester can call `execute_refund`.
2. **Require `deposit_msg.refund_address` to be pre-set:** Enforce that `deposit_msg.refund_address` is always `Some` for refund requests, so the destination is committed at deposit time and cannot be substituted by a front-runner.
3. **Alternatively, restrict `request_refund` to the `recipient_id`:** Add `require!(env::predecessor_account_id() == deposit_msg.recipient_id, "Only recipient can request refund")` before the Light Client call.

---

### Proof of Concept

```
1. Alice sends 0.01 BTC to the bridge deposit address derived from:
   deposit_msg = { recipient_id: "alice.near", refund_address: None, ... }

2. Alice's deposit is never finalized (e.g., wrong amount). She submits:
   request_refund(deposit_msg, "alice_btc_addr", tx_bytes, 0, proof, None)
   with attached NEAR storage deposit.

3. Attacker (Bob) observes Alice's pending transaction in the NEAR mempool.
   Bob submits (in the same or earlier block):
   request_refund(deposit_msg, "bob_btc_addr", tx_bytes, 0, proof, None)
   with the same deposit_msg, tx_bytes, vout=0, proof — only refund_address differs.

4. Bob's callback lands first:
   refund_requests["<alice_txid>@0"] = RefundRequest { refund_address: "bob_btc_addr", ... }

5. Alice's callback panics: "Refund request already exists for this UTXO".

6. After unsafe_refund_timelock_sec, Bob calls:
   execute_refund("<alice_txid>@0", None)
   → MPC signs a Bitcoin transaction paying 0.01 BTC (minus gas) to "bob_btc_addr".

7. Alice's BTC is gone. Only DAO/Operator intervention (reject_refund) before step 6
   could have prevented the theft.
```

    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
