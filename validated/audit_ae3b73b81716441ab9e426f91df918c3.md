### Title
Missing Lower-Bound Check on User-Supplied `gas_fee` in Refund Request Allows Zero-Fee Bitcoin Refund Transactions - (File: contracts/satoshi-bridge/src/refund.rs)

---

### Summary

The `request_refund` flow accepts a user-supplied `gas_fee: Option<u128>` parameter. The only validation applied is an upper-bound check (`resolved_gas_fee < amount`). There is no lower-bound check (e.g., `>= config.min_btc_gas_fee`). A user can pass `gas_fee = Some(0)`, causing the bridge to build and sign a Bitcoin refund transaction with zero miner fee. That transaction will not confirm on-chain, while the deposit UTXO is simultaneously marked as verified in bridge state, permanently blocking both the deposit and any corrected refund path until privileged operator intervention.

---

### Finding Description

In `request_refund_callback` the resolved gas fee is validated only against an upper bound:

```rust
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
``` [1](#0-0) 

`resolved_gas_fee = 0` satisfies `0 < amount` for any non-zero deposit, so the check passes. The zero value is then stored verbatim in the `RefundRequest`:

```rust
let refund_request = RefundRequest {
    ...
    gas_fee: resolved_gas_fee,   // 0
    ...
};
``` [2](#0-1) 

Later, `refund_execution_inputs` computes the amount returned to the user as `deposit_amount - gas_fee`. With `gas_fee = 0`, `refund_amount = deposit_amount`, and the only guard is `refund_amount > 0`, which also passes:

```rust
let refund_amount = refund_request
    .amount
    .checked_sub(refund_request.gas_fee)
    .expect("Deposit amount too small to cover gas fee");
require!(refund_amount > 0, "Refund amount is zero after gas fee");
``` [3](#0-2) 

`build_refund_output` then creates a Bitcoin output equal to the full deposit amount, leaving zero satoshis as the miner fee (inputs − outputs = 0): [4](#0-3) 

By contrast, the withdrawal path explicitly enforces both bounds:

```rust
require!(
    gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee,
    ...
);
``` [5](#0-4) 

The refund path has no equivalent lower-bound guard. The `Config::assert_valid` function validates that `min_btc_gas_fee < max_btc_gas_fee` but never enforces that user-supplied refund gas fees respect `min_btc_gas_fee`: [6](#0-5) 

After `execute_refund` runs, `finalize_refund_with_psbt` marks the UTXO as verified to block a later `verify_deposit`:

```rust
self.data_mut()
    .verified_deposit_utxo
    .insert(utxo_storage_key.clone());
``` [7](#0-6) 

Because the zero-fee transaction will not confirm, and the UTXO is now blocked from the deposit path, the user's funds are stuck.

---

### Impact Explanation

**Medium — attacker-triggered temporary locking of bridged funds.**

A user who submitted a deposit but wants a refund can call `request_refund` with `gas_fee = Some(0)`. After the timelock elapses, `execute_refund` builds and MPC-signs a zero-fee Bitcoin transaction. That transaction is broadcast but will not be mined (mempool eviction or indefinite delay). Meanwhile the deposit UTXO is flagged `verified_deposit_utxo`, so `verify_deposit` is also blocked. The user's BTC is inaccessible until a DAO/Operator calls `reject_refund` and manually cleans up state — requiring privileged intervention and causing a stuck bridge state.

---

### Likelihood Explanation

**Medium.** Any unprivileged user who has made a deposit and is eligible to call `request_refund` can trigger this. The parameter is optional (`Option<u128>`), so passing `Some(0)` is a trivial one-field change in the JSON call. No special knowledge or tooling is required beyond knowing the public API.

---

### Recommendation

Add a lower-bound check on the resolved gas fee in `request_refund_callback`, mirroring the check already present in the withdrawal path:

```rust
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
require!(
    resolved_gas_fee >= config.min_btc_gas_fee,
    "Gas fee is below the minimum required"
);
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
```

Additionally, add the same lower-bound guard in `refund_execution_inputs` as a defense-in-depth check before building the refund PSBT.

---

### Proof of Concept

1. Alice deposits 10 000 sat to the bridge-derived address.
2. Alice calls `request_refund` with `gas_fee: Some("0")` and a valid Merkle proof.
3. `request_refund_callback` resolves `resolved_gas_fee = 0`; the check `0 < 10000` passes; the `RefundRequest` is stored with `gas_fee = 0`.
4. After `refund_timelock_sec` elapses, anyone calls `execute_refund`.
5. `refund_execution_inputs` computes `refund_amount = 10000 - 0 = 10000`; `10000 > 0` passes.
6. `build_refund_output` creates a Bitcoin output of 10 000 sat; the transaction has 0 sat miner fee.
7. The MPC signs and the transaction is broadcast. Bitcoin nodes reject or indefinitely defer it (zero fee).
8. `finalize_refund_with_psbt` marks the UTXO in `verified_deposit_utxo`; `verify_deposit` is now blocked.
9. Alice's 10 000 sat are locked: the deposit path is closed and the refund transaction will not confirm.
