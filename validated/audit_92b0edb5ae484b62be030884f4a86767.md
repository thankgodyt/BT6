Audit Report

## Title
`is_refund_required` Returns `false` on Promise Failure, Permanently Locking Bridged Funds - (File: `near/omni-bridge/src/lib.rs`)

## Summary
When `ft_transfer_call` (or `ft_transfer`) dispatched by `send_tokens` fails with a NEAR promise error, `is_refund_required` returns `false` via the `Err(_) => false` branch. The callback then takes the success path: `revert_lock_actions` is skipped (leaving `locked_tokens` permanently decremented), `remove_fin_transfer` is skipped (leaving the finalization record in `finalised_transfers` and blocking any re-submission), and a false `FinTransferEvent` is emitted. The user's tokens remain in the bridge with no recovery path.

## Finding Description

The finalization flow for NEAR-recipient transfers is:

1. `process_fin_transfer_to_near` calls `add_fin_transfer` (inserts into `finalised_transfers`) and `unlock_tokens_if_needed` (decrements `locked_tokens`), then dispatches `send_tokens` with a `.then(fin_transfer_send_tokens_callback(...))`. [1](#0-0) 

2. `send_tokens` dispatches either `ft_transfer_call` (non-empty `msg`) or `ft_transfer` (empty `msg`) to the token contract. [2](#0-1) 

3. The callback `fin_transfer_send_tokens_callback` is invoked. It calls `is_refund_required(is_ft_transfer_call)` to decide whether to clean up. [3](#0-2) 

4. Inside `is_refund_required`, when the promise result is `Err` (token contract panicked), the function returns `false`: [4](#0-3) 

With `is_refund_required == false`, the callback takes the `else` branch: `revert_lock_actions` is not called, `remove_fin_transfer` is not called, and `FinTransferEvent` (success) is emitted. [5](#0-4) 

`add_fin_transfer` uses a `require!` that panics on re-insertion, so the transfer ID permanently blocks re-submission: [6](#0-5) 

`revert_lock_actions` — which would restore `locked_tokens` — is only reached on the refund path: [7](#0-6) 

For the `ft_transfer` (empty-msg) path, `is_ft_transfer_call = false` is passed to the callback (line 1973), so `is_refund_required` returns `false` at line 1800–1802 unconditionally, regardless of whether `ft_transfer` itself succeeded or failed — the same broken path applies. [8](#0-7) 

## Impact Explanation

When `ft_transfer_call` or `ft_transfer` fails with a promise error:

- **Permanent fund freeze**: NEAR atomically reverts the failed token transfer, so the tokens remain in the bridge's account. However, the finalization record in `finalised_transfers` blocks any re-submission with `BridgeError::TransferAlreadyFinalised`. There is no admin escape hatch or public retry mechanism to remove the record.
- **Escrow mis-accounting**: `locked_tokens[origin_chain][token]` is permanently decremented below its true value. Over time this allows the bridge to over-unlock tokens on future transfers, breaking the escrow invariant.
- **False success event**: `FinTransferEvent` is emitted, misleading off-chain relayers and indexers.

This matches the Critical impact class: permanent freezing of bridged funds and escrow mis-accounting.

## Likelihood Explanation

The `Err` branch is reachable without any privileged access whenever the destination token contract rejects the call. Concrete realistic triggers include: a token contract with a pause mechanism that is paused at finalization time; a minimum transfer amount guard that the bridged amount does not meet; a token contract upgrade between proof submission and callback execution; or gas exhaustion inside the token contract's `ft_transfer_call` logic. None of these require attacker privilege — any user whose transfer coincides with such a condition loses their funds permanently.

## Recommendation

Handle the `Err` branch in `is_refund_required` as a cleanup-required case:

```rust
// Unexpected case: treat as refund-required so cleanup runs
Err(_) => true,
```

Additionally, for the `ft_transfer` (empty-msg) path, the callback should also check the promise result and trigger cleanup on failure, rather than unconditionally returning `false`. A dedicated `Err` arm in `fin_transfer_send_tokens_callback` that calls `revert_lock_actions`, `remove_fin_transfer`, and emits `FailedFinTransferEvent` would ensure consistent state regardless of why the token transfer failed.

## Proof of Concept

1. Deploy a NEP-141 token contract with a `pause` function. Register it as a non-deployed (locked) token in the bridge with a `locked_tokens` entry for the origin chain.
2. Initiate a cross-chain transfer from Ethereum to a NEAR recipient with a non-empty `msg` field.
3. Before the relayer calls `fin_transfer`, pause the token contract.
4. The relayer calls `fin_transfer` with a valid proof. `process_fin_transfer_to_near` runs: `add_fin_transfer` inserts the transfer ID into `finalised_transfers`, `unlock_tokens_if_needed` decrements `locked_tokens`, and `send_tokens` dispatches `ft_transfer_call` to the paused token contract.
5. The token contract panics (paused). The NEAR runtime returns a `Failed` promise result.
6. `fin_transfer_send_tokens_callback` is invoked. `is_refund_required` hits `Err(_) => false` at line 1798 and returns `false`.
7. The callback takes the success path: `revert_lock_actions` is skipped, `remove_fin_transfer` is skipped, `FinTransferEvent` is emitted.
8. Observable state: the user's tokens are not received; any subsequent `fin_transfer` call for the same transfer ID panics with `BridgeError::TransferAlreadyFinalised`; `locked_tokens` is permanently lower than the actual bridge balance; no recovery is possible without a privileged `set_locked_tokens` call and a contract upgrade to clear the finalization record.
