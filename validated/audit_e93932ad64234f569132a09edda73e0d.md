Peras Certificate Validation Bypass Allows Unprivileged Peer to Manipulate Chain Selection via Fake Weight Boosts - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `BlockSupportsPeras` instance for all block types implements `validatePerasCert` as an unconditional stub that always returns `Right` without performing any cryptographic or semantic verification. Any unprivileged peer connected via the ObjectDiffusion miniprotocol can send a crafted `PerasCert` that passes this stub validation, gets stored in the `PerasCertDB`, and triggers chain selection with an artificial Peras weight boost — potentially causing an honest node to abandon its canonical chain in favor of a shorter adversarial fork.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub in production code:**

The `BlockSupportsPeras` instance defined for all `StandardHash blk` types contains the following implementation:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub unconditionally accepts every certificate, assigning it the full `perasWeight` boost (currently `PerasWeight 15` in `mkPerasParams`).

**Inbound certificate processing uses this stub in the production ChainDB path:**

`makePerasCertPoolWriterFromChainDB` — the production writer used when Peras is enabled — calls `validatePerasCert mkPerasParams` directly:

```haskell
(validatePerasCert mkPerasParams)  -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` filters out round numbers already in the DB, then calls `validateCert` on the remainder. Because `validateCert` always returns `Right`, every novel-round certificate from any peer is accepted: [3](#0-2) 

**`implAddCert` also carries an explicit TODO acknowledging missing validation:** [4](#0-3) 

**Chain selection is triggered with the artificial boost:**

After a certificate is added, `chainSelSync` retrieves the boosted block from the VolatileDB and calls `chainSelectionForBlock`, which re-runs chain selection with the new `PerasWeightSnapshot`: [5](#0-4) 

**Chain selection arithmetic makes a single fake certificate decisive:**

`wsvTotalWeight` sums `BlockNo` and `wsvWeightBoost`: [6](#0-5) 

With `perasWeight = PerasWeight 15`, a single fake certificate can make a fork that is up to 14 blocks shorter than the current chain preferred over it.

**Attack path:**

1. Attacker connects to a Peras-enabled node as a normal peer via the ObjectDiffusion miniprotocol.
2. Attacker observes a block `B` on a fork that is shorter than the current canonical chain by at most 14 blocks.
3. Attacker sends a `PerasCert { pcCertRound = freshRound, pcCertBoostedBlock = B }` to the node.
4. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right`.
5. The certificate is added to `PerasCertDB`; `chainSelSync` is triggered.
6. `chainSelectionForBlock` runs for block `B`; the fork's `wsvTotalWeight` now exceeds the canonical chain's weight.
7. The node switches to the attacker's fork, rolling back up to 14 honest blocks.

---

### Impact Explanation

**Critical/High — Peras certificate verification bypass enabling unauthorized chain selection manipulation.**

An unprivileged peer with no keys, no stake, and no special access can force an honest node to abandon its canonical chain and adopt a shorter adversarial fork, by sending a single crafted `PerasCert` message. This violates the core Ouroboros chain selection invariant that a node only switches to a chain with strictly greater weight. The rollback depth is bounded by `perasWeight - 1 = 14` blocks per fake certificate, but an attacker can send multiple certificates for different rounds to compound the effect. This constitutes a consensus safety failure: the node accepts an invalid chain state driven by a forged certificate.

---

### Likelihood Explanation

**Medium** — Peras is disabled by default (`eraPerasRoundLength = HardFork.NoPerasEnabled`) and is not yet deployed to Cardano mainnet. However, the vulnerable code is in the production codebase, not gated behind a compile-time flag, and will become exploitable as soon as Peras is enabled on any network (testnet or mainnet). The attack requires only a standard peer connection and knowledge of a block hash in the target node's VolatileDB — both trivially obtainable via ChainSync.

---

### Recommendation

1. **Replace the `validatePerasCert` stub** with real cryptographic verification (BLS aggregate signature check, VRF eligibility proof, quorum stake threshold check) before Peras is enabled on any network. The concrete V1 types in `Ouroboros.Consensus.Peras.Cert.V1` and `Ouroboros.Consensus.Peras.Crypto.BLS` already provide the necessary primitives.
2. **Block inbound certificates from being accepted** until real validation is wired in — e.g., by having `processCerts` reject all certificates when the validation function is the stub, or by disabling the ObjectDiffusion inbound handler for Peras certs until issue #120 is resolved.
3. **Enforce the invariant** that `implAddCert` only stores certificates that have passed full cryptographic validation, not merely structural deduplication by round number.

---

### Proof of Concept

On a Peras-enabled node (private testnet with `eraPerasRoundLength` set), connect as a peer and send via the ObjectDiffusion protocol:

```
PerasCert
  { pcCertRound    = <any round not yet in the node's PerasCertDB>
  , pcCertBoostedBlock = <Point of a block on a fork shorter than the current chain by ≤14 blocks>
  }
```

`processCerts` will call `validatePerasCert mkPerasParams cert` → `Right (ValidatedPerasCert { vpcCertBoost = PerasWeight 15 })`. The cert is stored. `chainSelSync` fires. The fork's `wsvTotalWeight = (fork_length + 15)` exceeds the canonical chain's `wsvTotalWeight = canonical_length` whenever `fork_length ≥ canonical_length - 14`. The node rolls back to the fork. processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts

-- Process a Peras certificate by adding it to the PerasCertDB and potentially
-- performing chain selection if a candidate is now better than our selection.
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
