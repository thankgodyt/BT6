### Title
`revalidateHeader` silently discards envelope validation result in production builds via `assertWithMsg` no-op — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/HeaderValidation.hs`)

---

### Summary

In production builds (without the `ENABLE_ASSERTIONS` compile flag), `assertWithMsg` is a complete no-op that silently discards its `Either String ()` argument. `revalidateHeader` wraps the entire `validateEnvelope` call inside `assertWithMsg`, meaning the envelope check result — block number, slot number, and prev-hash chain integrity — is computed but its outcome is unconditionally thrown away at runtime. This is the direct structural analog to the ERC20 `approve`/`transfer` return-value-ignored bug: a critical validation function's return value is silently discarded, causing the check to have no effect.

---

### Finding Description

**`assertWithMsg` is a CPP-conditional no-op in production:** [1](#0-0) 

```haskell
assertWithMsg :: HasCallStack => Either String () -> a -> a
#if ENABLE_ASSERTIONS
assertWithMsg (Left msg) _ = error msg
#endif
assertWithMsg _ a = a
```

Without `ENABLE_ASSERTIONS`, the definition collapses to `assertWithMsg _ a = a`. The first argument — the validation result — is bound to `_` and discarded. This is not a lazy-evaluation issue; the pattern match on `_` unconditionally ignores the value regardless of whether it is `Left` or `Right`.

**`revalidateHeader` relies entirely on `assertWithMsg` for its envelope check:** [2](#0-1) 

```haskell
revalidateHeader cfg ledgerView hdr st =
  assertWithMsg envelopeCheck $
    HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'
 where
  envelopeCheck :: Either String ()
  envelopeCheck =
    runExcept $ withExcept show $
      validateEnvelope cfg ledgerView (untickedHeaderStateTip st) hdr
```

`validateEnvelope` checks three structural invariants: consecutive block numbers, non-decreasing slot numbers, and hash-chain linkage (prev-hash). In production, all three checks are silently bypassed because `assertWithMsg` discards `envelopeCheck`.

Additionally, `reupdateChainDepState` (used instead of `updateChainDepState`) intentionally skips expensive cryptographic checks (VRF proof and KES signature verification). [3](#0-2) 

**`revalidateHeader` is called unconditionally during `reapplyBlockLedgerResult`:** [4](#0-3) 

```haskell
reapplyBlockLedgerResult evs cfg blk TickedExtLedgerState{..} =
    (\l -> ExtLedgerState l hdr) <$> castLedgerResult ledgerResult
   where
    ...
    hdr =
      revalidateHeader
        (getExtLedgerCfg cfg)
        ledgerView
        (getHeader blk)
        tickedHeaderState
```

`reapplyBlockLedgerResult` is the path taken when replaying blocks from an on-disk LedgerDB snapshot. The resulting `ExtLedgerState` — containing the unchecked `hdr` — is written back as the authoritative ledger state.

---

### Impact Explanation

**Impact: High** — LedgerDB snapshot replay/rollback bug that causes durable use of the wrong ledger state without operator fault.

A node loading from a crafted or corrupted on-disk snapshot will replay blocks through `reapplyBlockLedgerResult`. Because `revalidateHeader` silently discards the envelope check in production, blocks with:
- Non-consecutive block numbers,
- Out-of-order or duplicate slot numbers, or
- Broken hash-chain linkage (wrong `prevHash`)

…are accepted without error. The resulting `ExtLedgerState` is stored as the canonical ledger state. All subsequent chain selection, ledger queries, and block forging operate on this corrupted state. The node permanently diverges from the honest chain without any error being raised.

---

### Likelihood Explanation

**Likelihood: Medium.** The attack requires the ability to supply a crafted snapshot file to the node's data directory — achievable in a local reproduction or private-testnet scenario by writing a malformed snapshot to the path the node reads on startup. No key compromise, stake majority, or privileged network access is required. The node operator has no indication anything is wrong because no exception is thrown.

---

### Recommendation

Replace `assertWithMsg` with an unconditional check in `revalidateHeader`. The envelope check is cheap (no cryptography) and must not be guarded by a compile-time flag:

```haskell
revalidateHeader cfg ledgerView hdr st =
  case envelopeCheck of
    Left err -> error ("revalidateHeader: envelope invariant violated: " <> err)
    Right () ->
      HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'
```

Alternatively, if the intent is to trust previously-validated blocks, document and enforce the invariant that `reapplyBlockLedgerResult` is only ever called with blocks that have already passed `applyBlockLedgerResult`, and add a separate integrity check at snapshot load time that runs the full `validateHeader` (not `revalidateHeader`) on each replayed block.

---

### Proof of Concept

1. Build the node **without** `-DENABLE_ASSERTIONS` (the default production build).
2. Write a snapshot to the LedgerDB snapshot directory where a block's `prevHash` field does not match the hash of the preceding block.
3. Start the node. It calls `reapplyBlockLedgerResult` for each block in the snapshot.
4. `revalidateHeader` is called; `envelopeCheck` evaluates to `Left "UnexpectedPrevHash ..."`.
5. `assertWithMsg (Left "...") result` — because `ENABLE_ASSERTIONS` is absent — reduces to `assertWithMsg _ result = result`.
6. The broken-chain block is accepted; the node's `ExtLedgerState` is built on top of the corrupted header state.
7. The node proceeds to sync and forge on top of a ledger state with an invalid header chain, permanently diverging from honest peers. [1](#0-0) [2](#0-1) [4](#0-3)
