### Title
Strict Equality Check on Token Supply Allows Any nBTC Holder to Grief Token Migration - (File: contracts/satoshi-bridge/src/nbtc/migration.rs)

### Summary

The `migrate_to_new_token_mint` callback enforces `sum == total_supply` using strict equality. Because the `accounts` list is caller-supplied and enumerated off-chain, any nBTC holder who is not included in that list — whether accidentally omitted or deliberately acquiring tokens after the list is compiled — causes the migration to revert. An unprivileged attacker holding even 1 satoshi of nBTC can permanently grief the migration.

### Finding Description

`internal_migrate_to_new_token` queries `ft_total_supply()` and `ft_balance_of()` for each account in the caller-supplied `accounts` list, then fires a callback: [1](#0-0) 

```rust
let total_supply = Self::parse_ft_result(0);
let mut sum: u128 = 0;
...
for (index, account) in accounts.into_iter().enumerate() {
    let balance = Self::parse_ft_result(index as u64 + 1);
    sum += balance;
    ...
}
require!(
    sum == total_supply,
    "Sum of account balances does not match total supply"
);
```

The `total_supply` is the live on-chain value at callback time. The `sum` is only the aggregate of the balances for the accounts the operator chose to enumerate. If any nBTC holder is absent from the list — even one holding 1 satoshi — `sum < total_supply` and the `require!` panics, reverting the entire migration.

The attack is trivially executable:

1. Attacker acquires any nonzero nBTC balance (e.g., via `ft_transfer` from any holder, or via a normal deposit).
2. Attacker ensures their account is not in the `accounts` list passed to `migrate_to_new_token`.
3. Every call to `migrate_to_new_token` reverts at the `sum == total_supply` check.

Because nBTC is a freely transferable NEP-141 token, the attacker can also front-run the migration call: observe the `accounts` list in the mempool, transfer a tiny amount to a fresh account not in the list, and cause the migration to fail. The operator must then re-enumerate all holders and retry — but the attacker can repeat the attack indefinitely at negligible cost. [2](#0-1) 

### Impact Explanation

The token migration — which updates `nbtc_account_id` in the bridge config and mints equivalent balances on the new token — is permanently blocked as long as the attacker holds any nBTC not included in the enumerated list. This constitutes an attacker-triggered stuck bridge state requiring operator intervention, and critically, if the migration is needed for a security upgrade (e.g., migrating away from a compromised token), the inability to complete it has direct protocol-level consequences.

**Impact: Medium** — Attacker-triggered temporary (but indefinitely renewable) locking of the migration path, requiring operator intervention each time.

### Likelihood Explanation

Any unprivileged nBTC holder can execute this. The cost is holding 1 satoshi of nBTC. The attack can be repeated after every operator retry by transferring to a new unlisted account. Likelihood is **High**.

### Recommendation

Replace the strict equality with a `>=` check, or better, remove the check entirely and instead derive the migration list from on-chain enumeration rather than a caller-supplied list. If the equality check is kept for accounting integrity, use `>=`:

```rust
require!(
    sum >= total_supply,
    "Sum of account balances does not match total supply"
);
```

Alternatively, redesign the migration to pull balances from a snapshot or use a paginated approach that does not depend on the caller enumerating every holder perfectly.

### Proof of Concept

1. Bridge operator calls `migrate_to_new_token(new_token, [alice, bob, charlie])` where alice/bob/charlie are the known holders.
2. Attacker calls `ft_transfer` on the nBTC contract to send 1 satoshi to a fresh account `attacker.near` (not in the list).
3. `migrate_to_new_token_mint` callback fires: `total_supply = alice_bal + bob_bal + charlie_bal + 1`, `sum = alice_bal + bob_bal + charlie_bal`.
4. `require!(sum == total_supply)` → `sum < total_supply` → migration reverts.
5. Operator retries with `[alice, bob, charlie, attacker.near]`; attacker transfers 1 satoshi to `attacker2.near` and the cycle repeats. [3](#0-2) [4](#0-3)

    pub(crate) fn internal_migrate_to_new_token(
        &mut self,
        new_token: AccountId,
        accounts: Vec<AccountId>,
    ) -> Promise {
        let old_token = self.internal_config().nbtc_account_id.clone();
        require!(
            new_token != old_token,
            "New token must differ from the current token"
        );

        let mut queries = ext_nbtc::ext(old_token.clone())
            .with_static_gas(GAS_FOR_FT_QUERY)
            .ft_total_supply();
        for account in &accounts {
            queries = queries.and(
                ext_nbtc::ext(old_token.clone())
                    .with_static_gas(GAS_FOR_FT_QUERY)
                    .ft_balance_of(account.clone()),
            );
        }

        let callback_gas = Gas::from_gas(
            GAS_FOR_MIGRATION_MINT_CALL_BACK.as_gas()
                + GAS_FOR_MIGRATION_RESOLVE_CALL_BACK.as_gas()
                + GAS_FOR_MINT_ACTION.as_gas() * accounts.len() as u64,
        );
        queries.then(
            Self::ext(env::current_account_id())
                .with_static_gas(callback_gas)
                .migrate_to_new_token_mint(new_token, accounts),
        )
    }

    pub fn migrate_to_new_token_mint(
        &mut self,
        new_token: AccountId,
        accounts: Vec<AccountId>,
    ) -> PromiseOrValue<()> {
        require!(
            env::promise_results_count() == accounts.len() as u64 + 1,
            "Unexpected number of promise results"
        );

        let total_supply = Self::parse_ft_result(0);
        let mut sum: u128 = 0;
        let mut entries: Vec<(AccountId, u128)> = Vec::new();
        for (index, account) in accounts.into_iter().enumerate() {
            let balance = Self::parse_ft_result(index as u64 + 1);
            sum += balance;
            if balance > 0 {
                entries.push((account, balance));
            }
        }
        require!(
            sum == total_supply,
            "Sum of account balances does not match total supply"
        );

        let accounts_count = entries.len();
        let mut mint_batch = Promise::new(new_token.clone());
        for (account, amount) in entries {
            let args = serde_json::to_vec(&json!({
                "mint_account_id": account,
                "mint_amount": U128(amount),
                "protocol_fee": U128(0),
                "relayer_account_id": env::current_account_id(),
                "relayer_fee": U128(0),
                "post_actions": null,
            }))
            .unwrap_or_else(|_| env::panic_str("Failed to serialize mint args"));
            mint_batch = mint_batch.function_call(
                "mint".to_string(),
                args,
                NearToken::from_yoctonear(0),
                GAS_FOR_MINT_ACTION,
            );
        }
        mint_batch
            .then(
                Self::ext(env::current_account_id())
                    .with_static_gas(GAS_FOR_MIGRATION_RESOLVE_CALL_BACK)
                    .migrate_to_new_token_resolve(new_token, accounts_count, U128(total_supply)),
            )
            .into()
    }
