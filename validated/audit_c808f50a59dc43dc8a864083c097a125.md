Audit Report

## Title
Permanent Freezing of Bridged Funds When EVM Recipient Is Token-Blacklisted — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
`OmniBridge.finTransfer` unconditionally pushes tokens to `payload.recipient` via `safeTransfer`. If the recipient is blacklisted by a transfer-restricted token (e.g., USDC), every finalization attempt reverts and rolls back the nonce mark, leaving the relayer permanently stuck. Because the NEAR side exposes no public cancel or redirect function, tokens burned or locked on NEAR are irrecoverable.

## Finding Description
In `finTransfer`, the destination nonce is marked consumed at line 287 before any token movement:

```solidity
completedTransfers[payload.destinationNonce] = true;   // line 287
```

However, if the subsequent `safeTransfer` at lines 351–354 reverts (e.g., USDC blacklist check fails), the EVM transaction reverts entirely, rolling back the nonce mark as well. The relayer can retry indefinitely, but every attempt hits the same revert. No alternative delivery path exists inside `finTransfer`.

On the NEAR side, `init_transfer_internal` burns or locks tokens and stores a `TransferMessage` in `pending_transfers`. The only function that removes a `pending_transfers` entry is `remove_transfer_message`, which is `fn` (private) and is only called from finalization callbacks that require proof of EVM-side completion — proof that can never be produced when `finTransfer` always reverts. There is no public `cancel_transfer`, `refund_transfer`, or equivalent function exposed to users.

## Impact Explanation
This matches the allowed critical impact: **permanent freezing of bridged funds across NEAR and EVM flows**. For bridged/deployed tokens, the tokens are burned on NEAR and never minted on EVM — permanently destroyed. For native tokens, they are locked in the NEAR bridge contract with no release path. The loss is irreversible without a protocol upgrade.

## Likelihood Explanation
Low. The condition requires that the EVM recipient address be on the USDC (or equivalent) blocklist at the time of finalization. USDC blacklisting is a documented, real-world event (OFAC sanctions, exchange enforcement). No attacker action is required; the user may be blacklisted after initiating the transfer, or may unknowingly bridge to a sanctioned address. The scenario is not theoretical — Centre/Circle has blacklisted hundreds of addresses on mainnet.

## Recommendation
Replace the push pattern in `finTransfer` with a pull pattern: instead of calling `safeTransfer` to `payload.recipient` inside `finTransfer`, record the claimable amount in a `mapping(address => mapping(address => uint256)) claimable` and emit an event. Provide a separate `claimTransfer(address token, address recipient)` function that the recipient (or a designated address) calls to withdraw. This decouples nonce finalization from token delivery, so a blacklisted recipient does not block the protocol and the user retains the ability to redirect funds via an alternative address.

## Proof of Concept
1. Alice holds USDC on NEAR and calls `ft_transfer_call` to bridge 1000 USDC to `0xAlice`. NEAR burns the tokens and stores the `TransferMessage` in `pending_transfers`.
2. Alice calls `sign_transfer`; the MPC signs a `TransferMessagePayload` with `recipient = 0xAlice`.
3. Before the relayer submits the signature, `0xAlice` is added to the USDC blocklist on Ethereum.
4. The relayer calls `OmniBridge.finTransfer(sig, payload)`. Execution reaches line 351: `IERC20(USDC).safeTransfer(0xAlice, 1000e6)`. USDC reverts. The entire transaction reverts, including the `completedTransfers[nonce] = true` write at line 287.
5. Every subsequent `finTransfer` attempt reverts identically.
6. `remove_transfer_message` on NEAR is private and only reachable via finalization callbacks requiring EVM proof. No such proof can ever be produced. Alice's 1000 USDC are permanently frozen.
