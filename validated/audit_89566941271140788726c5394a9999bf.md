Audit Report

## Title
`init_transfer` Accepts Deposits That `sign_transfer` Will Always Reject, Permanently Freezing User Tokens — (File: `near/omni-bridge/src/lib.rs`)

## Summary

`init_transfer_internal` locks or burns user tokens without verifying that `normalize_amount(amount_without_fee) > 0`. When `amount_without_fee < 10^(origin_decimals - decimals)`, floor division in `normalize_amount` yields zero, causing `sign_transfer` to always panic with `ERR_INVALID_AMOUNT_TO_TRANSFER`. Because the lock/burn is committed in the user's own transaction and no cancel or refund path exists, the tokens are permanently frozen.

## Finding Description

`init_transfer_internal` validates only that `fee.fee < amount` [1](#0-0)  before locking or burning the full token amount: [2](#0-1) 

Later, in a separate transaction, `sign_transfer` computes:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
``` [3](#0-2) 

`normalize_amount` uses floor division: [4](#0-3) 

`amount_without_fee` is `amount - fee`: [5](#0-4) 

If `amount_without_fee < 10^(origin_decimals - decimals)`, the result is 0 and `sign_transfer` panics — permanently. `update_transfer_fee` enforces `fee.fee >= current_fee.fee`, so the fee can only increase, making `amount_without_fee` smaller, not larger. [6](#0-5)  No public cancel or refund function exists in the contract. The internal `remove_transfer_message_without_refund` is only called in paths where tokens were never locked. [7](#0-6) 

The code comment on `normalize_amount` acknowledges "dust stays locked/burned" for the remainder case, but does not address the case where the entire normalized amount is zero. [8](#0-7) 

## Impact Explanation

Permanent freezing of bridged funds. A user who calls `ft_transfer_call` with `amount_without_fee < 10^(origin_decimals - decimals)` has their tokens locked or burned in the bridge with no recovery path. For a token pair with `origin_decimals = 24` and `decimals = 18` (a standard NEAR-to-EVM pairing), the threshold is 1,000,000 base units. This matches the allowed critical impact: "permanent freezing of bridged funds."

## Likelihood Explanation

Any unprivileged user can trigger this by calling `ft_transfer_call` with a sufficiently small `amount_without_fee`. The condition is not exotic: for a 6-decimal difference, any net transfer below 1,000,000 base units hits this path. The deposit-time validation (`fee < amount`) does not prevent it, and users receive no warning. The condition is self-inflicted but requires no attacker — a user making a small transfer in good faith is sufficient.

## Recommendation

Add the normalization check inside `init_transfer_internal`, before locking or burning tokens, so the deposit is rejected and tokens are returned rather than accepted and permanently frozen:

```rust
// After building transfer_message, before burn/lock:
let token_address = self.get_token_address(...);
let decimals = self.token_decimals.get(&token_address)...;
require!(
    Self::normalize_amount(
        transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
        decimals,
    ) > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

This mirrors the existing check in `sign_transfer` but moves it to the point where a graceful rejection (token refund via `ft_transfer_call` return value) is still possible.

## Proof of Concept

1. Register a token with `origin_decimals = 24`, `decimals = 18` (divisor = 1,000,000).
2. User calls `ft_transfer_call` with `amount = 500_000`, `fee = 0`.
3. `init_transfer_internal` passes (`fee < amount` ✓). Tokens are locked. Transfer message stored.
4. Any caller invokes `sign_transfer` for this transfer ID.
5. `normalize_amount(500_000, {24, 18}) = 500_000 / 1_000_000 = 0`.
6. `require!(0 > 0, ...)` → panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.
7. The panic does not revert the lock from step 3. The transfer message remains in `pending_transfers`. The user's 500,000 tokens are permanently frozen with no recovery path.
