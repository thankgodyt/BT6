### Title
`fin_transfer_send_tokens_callback` Removes Finalization Record After Failed Delivery, Enabling Proof Replay Double-Spend — (`File: near/omni-bridge/src/lib.rs`)

### Summary

`fin_transfer_send_tokens_callback` calls `remove_fin_transfer` when an `ft_transfer_call` delivery is rejected by the recipient, erasing the transfer's entry from `finalised_transfers`. Because the bridge's only replay guard is that set, the same source-chain proof can be re-submitted by a relayer and accepted a second time, minting or unlocking tokens a second time for a single source-chain lock/burn event.

### Finding Description

The inbound finalization path for NEAR-recipient transfers is:

1. `fin_transfer_callback` → `process_fin_transfer_to_near`
2. `process_fin_transfer_to_near` calls `add_fin_transfer`, which inserts the `TransferId` into `finalised_transfers` (the sole replay guard), then calls `send_tokens` with the user-supplied `msg`.
3. When `msg` is non-empty, `send_tokens` issues an `ft_transfer_call` to the recipient contract.
4. The callback `fin_transfer_send_tokens_callback` is invoked. If `is_refund_required` returns `true` (i.e., `ft_on_transfer` returned `0` — "used amount zero"), the callback:
   - Burns the minted tokens (`burn_tokens_if_needed`)
   - Reverts lock accounting (`revert_lock_actions`)
   - **Calls `remove_fin_transfer`, deleting the `TransferId` from `finalised_transfers`**
   - Emits `FailedFinTransferEvent`

After step 4, `finalised_transfers` no longer contains the transfer ID. A subsequent call to `fin_transfer` with the identical proof passes `add_fin_transfer`'s uniqueness check and proceeds to mint/unlock tokens a second time.
