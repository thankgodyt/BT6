### Title
Unchecked `u128` Addition in `check_deposit_msg` Causes Deterministic Panic on Overflow-Crafted `DepositMsg` — (`contracts/satoshi-bridge/src/deposit_msg.rs`)

---

### Summary

A depositor can craft a `DepositMsg` containing two `PostAction` entries each with `amount = U128::MAX/2 + 1`. When the relayer calls `verify_deposit_v2` with this message, the plain `+=` accumulation at `deposit_msg.rs:85` overflows `u128`, triggering a panic because `overflow-checks = true` is set in the workspace release profile. The UTXO is never marked processed and the deposit becomes permanently stuck.

---

### Finding Description

The accumulation loop in `check_deposit_msg` uses bare integer addition:

```rust
let mut total_amount = 0u128;
for (index, post_action) in post_actions.iter().enumerate() {
    total_amount += post_action.amount.0;   // line 85 — no checked_add
    ...
}
``` [1](#0-0) 

`post_action.amount` is a user-supplied `U128` field with no upper-bound validation before this loop. The workspace `Cargo.toml` explicitly enables overflow trapping in release builds:

```toml
[profile.release]
overflow-checks = true
``` [2](#0-1) 

With two `PostAction` entries each carrying `amount = (u128::MAX / 2) + 1 = 170141183460469231731687303715884105728`, the sum is `u128::MAX + 1`, which panics unconditionally in any build produced from this workspace.

The whitelist check that would otherwise silently return `None` appears **after** the overflow line, so it cannot rescue the execution: [3](#0-2) 

`check_deposit_msg` is called synchronously inside `internal_verify_deposit`, before any promise is scheduled: [4](#0-3) 

`internal_verify_deposit` is reached from both `verify_deposit` and `verify_deposit_v2`: [5](#0-4) 

---

### Impact Explanation

When the panic fires, the NEAR runtime reverts the entire transaction. The UTXO is never inserted into `verified_deposit_utxo`, so the deposit is not finalized. Because the `DepositMsg` is deterministically tied to the deposit address (via `get_deposit_path` / SHA-256), every subsequent relayer attempt with the same `DepositMsg` will panic identically. The depositor's BTC is permanently unprocessable through the normal deposit flow, constituting a stuck-state fault. No funds are stolen, but the bridge's invariant that any user-supplied `DepositMsg` can be safely validated without panicking is violated.

---

### Likelihood Explanation

The attack requires only:
1. Calling the public, read-only `get_user_deposit_address` with the crafted `DepositMsg` to obtain a valid deposit address.
2. Sending any amount of BTC to that address.
3. Waiting for the relayer's automation to pick up the on-chain `LogDepositAddress` event and call `verify_deposit_v2`.

The depositor needs no privileged role. The `#[trusted_relayer]` gate on `verify_deposit_v2` is satisfied by the relayer itself; the depositor's leverage is entirely through the user-controlled `DepositMsg` content, which is a public input. The relayer's automation has no pre-flight amount-overflow check before submitting. [6](#0-5) 

---

### Recommendation

Replace the bare `+=` with `checked_add` and return `None` (emitting an `InvalidPostAction` event) on overflow, consistent with how all other validation failures in this function are handled:

```rust
total_amount = match total_amount.checked_add(post_action.amount.0) {
    Some(v) => v,
    None => {
        Event::InvalidPostAction {
            index: Some(index),
            err_msg: "post_action amounts overflow u128.".to_string(),
        }.emit();
        return None;
    }
};
```
