### Title
Stub `validatePerasCert` Always Accepts Any Peer-Supplied Certificate, Inflating `PerasWeightSnapshot` and Corrupting Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance ships a stub `validatePerasCert` that unconditionally returns `Right` for every certificate it receives. This stub is wired directly into the production inbound certificate path (`makePerasCertPoolWriterFromChainDB`). An unprivileged peer can therefore send a crafted `PerasCert` naming any block as its boosted target, have it accepted without any cryptographic or eligibility check, and cause the node's `PerasWeightSnapshot` — the global accumulator used as the weight numerator in chain selection — to be inflated for an adversarial block. If the resulting boosted weight exceeds the honest chain's weight, the node switches to the adversarial chain.

---

### Finding Description

**Vulnerability class (mapped from the reference report):** A global accumulator is updated without an eligibility/validity gate, allowing an ineligible participant to inflate it through a no-op or post-boundary operation. Here the accumulator is `PerasWeightSnapshot` and the ineligible operation is a peer-supplied certificate that bypasses all validation.

**Root cause — stub validation always returns `Right`:**

The `BlockSupportsPeras` instance for all block types contains:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature, no committee membership, no round-eligibility, and no boosted-block existence check is performed. Every certificate is accepted and assigned the full `perasWeight params` boost.

**Wiring into the production inbound path:**

`makePerasCertPoolWriterFromChainDB` — the handler invoked for every batch of certificates received from a peer — passes this stub directly as the `validateCert` argument:

```haskell
(validatePerasCert mkPerasParams)  -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

**`processCerts` accepts all certificates because validation never fails:**

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [3](#0-2) 

Since `validatePerasCert` always returns `Right`, the `(errs, _)` branch is unreachable. Every certificate from every peer is added to `PerasCertDB`.

**`PerasWeightSnapshot` is derived directly from all stored certificates:**

```haskell
implGetWeightSnapshot PerasCertDbEnv{pcdbState} = do
  WithFingerprint pcds fp <- readTVar pcdbState
  let weights =
        mkPerasWeightSnapshot
          [ (getPerasCertBoostedBlock cert, getPerasCertBoost cert)
          | cert <- Map.elems (pcdsCertsByTicket pcds)
          ]
  pure (WithFingerprint weights fp)
``` [4](#0-3) 

Every accepted certificate — including adversarially crafted ones — contributes its `vpcCertBoost` to the snapshot for the named `pcCertBoostedBlock` point.

**Chain selection uses this snapshot as the decisive weight:**

```haskell

  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [5](#0-4) 

```haskell

  case compare (wsvTotalWeight ours) (wsvTotalWeight cand) of
    LT -> ShouldSwitch ...
``` [6](#0-5) 

A fraudulent boost on an adversarial block directly shifts `wsvTotalWeight` for that candidate, potentially making `ShouldSwitch` fire when it should not.

### Impact Explanation

An unprivileged peer can make an honest node permanently switch to a non-canonical adversarial chain by:

1. Sending a `PerasCert` whose `pcCertBoostedBlock` names a block on the adversarial fork.
2. The stub validation accepts it unconditionally.
3. The `PerasWeightSnapshot` is inflated by `perasWeight params` for that adversarial block.
4. Chain selection re-runs and, if the boosted adversarial chain's total weight now exceeds the honest chain's weight, the node adopts the adversarial chain.

This is a **High** chain-selection bug: an unprivileged peer can make an honest node prefer a non-canonical chain beyond the intended security assumptions of Ouroboros Peras.

---

### Likelihood Explanation

The attack requires only that the adversary:
- Connect to the target node via the Peras certificate diffusion mini-protocol (standard peer connection).
- Know the hash of a block on an adversarial fork that is within the node's VolatileDB (i.e., a recently diffused block).

No key material, stake majority, or privileged access is needed. The one-cert-per-round deduplication (`Set.member roundNo pcdsCertIds`) limits the attack to one boost per Peras round, but an adversary can repeat across rounds. The attack is straightforward and repeatable.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
1. The aggregate BLS signature over the claimed voter set.
2. Each voter's committee membership and eligibility proof (persistent or non-persistent seat via VRF).
3. That the boosted block's slot falls within the valid range for the claimed round.
4. That the round number is not in the future beyond the current slot.

Until real validation is in place, the inbound certificate path (`processCerts` / `makePerasCertPoolWriterFromChainDB`) should reject all certificates rather than accept them unconditionally, or the Peras weight boost should be disabled in chain selection.

---

### Proof of Concept

```
1. Adversary connects to an honest node as a peer.
2. Adversary has previously diffused block B_adv (on an adversarial fork) to the node,
   so B_adv is in the node's VolatileDB.
3. Adversary sends a PerasCert { pcCertRound = R, pcCertBoostedBlock = point(B_adv) }
   via the Peras certificate mini-protocol.
4. processCerts calls validatePerasCert mkPerasParams on the cert.
   validatePerasCert always returns Right { vpcCert = cert, vpcCertBoost = perasWeight params }.
5. The cert is added to PerasCertDB; implGetWeightSnapshot now includes
   (point(B_adv), perasWeight params) in the PerasWeightSnapshot.
6. chainSelSync triggers chainSelectionForBlock for B_adv with the inflated snapshot.
7. weightedSelectView computes wsvTotalWeight for the adversarial fragment as
   blockNo(B_adv) + perasWeight params, which may exceed the honest chain's weight.
8. preferCandidate returns ShouldSwitch; the node adopts the adversarial chain.
```

The deduplication check (`Set.member roundNo pcdsCertIds`) only prevents the same round from being boosted twice; the adversary can use a fresh round number each time to boost a different adversarial block or re-boost after garbage collection.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
