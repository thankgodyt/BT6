### Title
Tokens Minted to `bridge_id` Before Recipient Registration Check in `safe_mint` — (File: `contracts/nbtc/src/lib.rs`)

### Summary
The `safe_mint` function in the nbtc contract mints tokens to `bridge_id` **before** checking whether the recipient `account_id` is registered. If the recipient is not registered, the function returns `U128(0)` and the already-minted tokens remain permanently stuck in `bridge_id` with no automatic recovery path inside the nbtc contract.

### Finding Description
In `contracts/nbtc/src/lib.rs`, `safe_mint` executes `self.token.internal_deposit(&self.bridge_id, amount.into())` — a state-mutating mint — and only **afterwards** checks `if self.token.accounts.get(&account_id).is_none()`. If the recipient is unregistered, the function returns `PromiseOrValue::Value(U128(0))` without transferring the freshly minted tokens. The tokens remain credited to `bridge_id` with no automatic burn or refund triggered within the nbtc contract itself.

```rust
// contracts/nbtc/src/lib.rs  lines 112-116
self.token.internal_deposit(&self.bridge_id, amount.into()); // ← tokens minted here

if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0)); // ← tokens already minted, now stuck
}
```

This is the direct analog of the reported pattern: a consequential computation (minting) is performed using a precondition (recipient registration) that has not yet been verified, leaving the contract in an inconsistent state when the precondition fails.

### Impact Explanation
When a BTC deposit is processed through the safe-deposit flow (`verify_deposit_v2` with `safe_deposit = Some(..)`), if the recipient NEAR account is not registered on the nbtc contract at callback time, the corresponding nBTC tokens are minted into `bridge_id` but never delivered to the user. The user's BTC is locked in the bridge and they receive zero nBTC. Recovery requires privileged operator intervention to call `burn` on `bridge_id` — a stuck bridge state requiring operator intervention. This matches the **Medium** allowed impact: *broken callback rollback / stuck bridge state requiring operator intervention*.

### Likelihood Explanation
The safe-deposit flow is triggered by a relayer calling `verify_deposit_v2` with `deposit_msg.safe_deposit = Some(..)`. The nbtc contract's `safe_mint` does **not** register the recipient account — it only checks for existing registration. If the recipient account was never registered on the nbtc contract, or was unregistered (zero-balance `storage_unregister`) between deposit and finalization, the bug fires. A user can deliberately send BTC to a deposit address whose `recipient_id` is unregistered, causing their own tokens to be permanently stuck. The relayer is documented to attach NEAR for storage, but `safe_mint` does not consume that NEAR to register the account.

### Recommendation
Move the registration check (or an explicit `internal_register_account` call) **before** `internal_deposit`:

```rust
// Check (or register) before minting
if self.token.accounts.get(&account_id).is_none() {
    self.token.internal_register_account(&account_id);
    // or: return PromiseOrValue::Value(U128(0));  ← before any state change
}
self.token.internal_deposit(&self.bridge_id, amount.into());
```

### Proof of Concept
1. `alice.near` is not registered on the nbtc contract.
2. Alice sends BTC to a deposit address derived from `DepositMsg { recipient_id: "alice.near", safe_deposit: Some(..), .. }`.
3. Relayer calls `verify_deposit_v2` with the BTC inclusion proof.
4. Bridge verifies the proof and calls `nbtc.safe_mint("alice.near", amount, msg)`.
5. `safe_mint` executes `internal_deposit(&bridge_id, amount)` — nBTC tokens are minted to `bridge_id` (state committed).
6. `safe_mint` checks `accounts.get("alice.near").is_none()` → `true`.
7. `safe_mint` returns `PromiseOrValue::Value(U128(0))`.
8. Alice receives 0 nBTC. Her BTC is locked. The minted tokens sit in `bridge_id` with no automatic recovery. Operator must manually call `burn` to clean up.
