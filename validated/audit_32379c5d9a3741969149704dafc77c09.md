### Title
MPC Unavailability Permanently Locks User nBTC Tokens and Bridge UTXOs With No Operator Escape Hatch - (File: `contracts/satoshi-bridge/src/chain_signature.rs`)

---

### Summary

When the Chain Signatures (MPC) service is unavailable or returns an error, `sign_btc_transaction_callback` silently returns `false` without releasing the UTXOs or refunding the user's nBTC tokens. Because `cancel_withdraw` also requires a fresh MPC signature, neither the user nor the operator has any mechanism to recover locked funds without MPC being restored. This is a direct analog to M-1: one broken external component (MPC instead of Aave) causes the entire withdrawal path to stall, and the operator's own remediation path depends on the same broken component.

---

### Finding Description

The withdrawal flow proceeds as follows:

1. User calls `nbtc.ft_transfer_call(bridge, amount, withdraw_msg)`. The nBTC contract calls `bridge.ft_on_transfer`, which returns `0`, keeping all tokens in the bridge balance permanently.

2. Inside `ft_on_transfer`, `create_btc_pending_info` is called. This removes the selected UTXOs from `data().utxos` and stores them inside `BTCPendingInfo.vutxos`. The UTXOs are now locked.

3. The user calls `sign_btc_transaction`, which dispatches a cross-contract call to the MPC service via `sign_promise`.

4. If MPC is unavailable or returns an error, `sign_btc_transaction_callback` executes the `else` branch:

```rust
// contracts/satoshi-bridge/src/chain_signature.rs, lines 210-212
} else {
    false
}
```

There is **no state rollback**: the `BTCPendingInfo` remains in `PendingSign` state, the UTXOs remain locked inside it, and the user's nBTC tokens remain in the bridge balance with no refund path.

5. The operator's only remediation is `cancel_withdraw`, which calls `cancel_withdraw_chain_specific`. This constructs a new RBF transaction that **also requires an MPC signature**. If MPC is down, `cancel_withdraw` also fails, leaving the operator with no escape hatch.

The UTXO removal happens eagerly in `generate_vutxos` called from `create_btc_pending_info` before any MPC interaction:

```rust
// contracts/satoshi-bridge/src/api/token_receiver.rs, line 79
let (utxo_storage_keys, vutxos) = self.generate_vutxos(&mut psbt);
```

And the nBTC tokens are irrevocably kept by the bridge at `ft_on_transfer` return:

```rust
// contracts/satoshi-bridge/src/api/token_receiver.rs, lines 57-65
TokenReceiverMessage::Withdraw { ... } => self.ft_on_transfer_withdraw_chain_specific(...)
// ft_on_transfer returns PromiseOrValue::Value(U128(0)) → bridge keeps all tokens
```

---

### Impact Explanation

**Medium.** When MPC is unavailable (maintenance window, bug, network partition):

- All in-flight withdrawals are stuck: `BTCPendingInfo` entries remain in `PendingSign` state indefinitely.
- Users' nBTC tokens are locked in the bridge balance with no refund mechanism.
- Bridge UTXOs are locked inside pending infos and cannot be used for other withdrawals, degrading available liquidity.
- `cancel_withdraw` (the operator's only remediation tool) also requires MPC signing and therefore also fails.
- The bridge enters a stuck state requiring operator intervention, but the operator has no on-chain action available without MPC.

This matches the allowed impact: **"Medium. Harmful smart-contract behavior without direct funds theft, including … stuck bridge state requiring operator intervention."**

---

### Likelihood Explanation

MPC (Chain Signatures) is an external service operated by the NEAR validator set. Temporary unavailability is a realistic operational scenario (upgrades, bugs, network issues). The original M-1 report used Aave's `paused()` modifier as the trigger — MPC unavailability is the direct analog here. Any period of MPC downtime during which users initiate withdrawals results in permanently stuck state until MPC is restored, with no on-chain recovery path.

---

### Recommendation

1. **Add a no-MPC UTXO release path**: Introduce an admin function (DAO-only) that can forcibly remove a `BTCPendingInfo` in `PendingSign` state, restore its UTXOs to `data().utxos`, and trigger an nBTC refund to the user — without requiring an MPC signature.

2. **Rollback on signing failure**: In `sign_btc_transaction_callback`, when the MPC call fails, restore the UTXOs from `BTCPendingInfo.vutxos` back into `data().utxos` and initiate an nBTC refund (`ft_transfer`) to the user, so the withdrawal is atomically unwound.

3. **Mirror the M-1 recommendation**: Consider a `paused()` check on the MPC service (if it exposes one) so that `ft_on_transfer` rejects new withdrawals (returns `amount` instead of `0`) when MPC is known to be unavailable, preventing new funds from being locked.

---

### Proof of Concept

**Step 1**: MPC service becomes unavailable (maintenance, bug).

**Step 2**: Alice calls `nbtc.ft_transfer_call(bridge, 100_000, withdraw_msg)`. Bridge's `ft_on_transfer` returns `0` — 100,000 nBTC are now in bridge balance. UTXOs are removed from `data().utxos` and locked in `BTCPendingInfo`.

**Step 3**: Alice calls `sign_btc_transaction(pending_id, 0, 0)` with attached deposit. The MPC cross-contract call fails.

**Step 4**: `sign_btc_transaction_callback` executes:
```rust
// chain_signature.rs line 141
if let Ok(result_bytes) = env::promise_result_checked(0, MAX_SIGNATURE_RESULT) {
    // ... success path
} else {
    false  // ← silent failure, no rollback
}
```
Alice's 100,000 nBTC remain in bridge balance. UTXOs remain locked.

**Step 5**: Operator calls `cancel_withdraw(pending_id, output)`. This calls `cancel_withdraw_chain_specific`, which constructs an RBF transaction and calls `sign_btc_transaction` → MPC → fails again. Operator is blocked.

**Result**: Alice's nBTC and the bridge UTXOs are permanently locked until MPC is restored. No on-chain recovery path exists. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

```rust
    #[private]
    pub fn sign_btc_transaction_callback(
        &mut self,
        account_id: AccountId,
        btc_pending_sign_id: String,
        sign_index: usize,
    ) -> bool {
        if let Ok(result_bytes) = env::promise_result_checked(0, MAX_SIGNATURE_RESULT) {
            let signature = serde_json::from_slice::<SignatureResponse>(&result_bytes)
                .expect("Invalid signature");

            let public_key = self
                .generate_btc_public_key(
                    &self
                        .internal_unwrap_btc_pending_info(&btc_pending_sign_id)
                        .vutxos[sign_index]
                        .get_path(),
                )
                .inner;
            let btc_pending_info = self.internal_unwrap_mut_btc_pending_info(&btc_pending_sign_id);
            require!(
                btc_pending_info.signatures[sign_index].is_none(),
                "Already signed"
            );
            btc_pending_info.signatures[sign_index] = Some(signature.clone());
            btc_pending_info.last_sign_time_sec = nano_to_sec(env::block_timestamp());
            Event::BtcInputSignature {
                account_id: &account_id,
                btc_pending_id: &btc_pending_sign_id,
                sign_index,
                signature: &signature,
            }
            .emit();
            let mut psbt = btc_pending_info.get_psbt();
            psbt.save_signature(sign_index, signature, public_key);

            btc_pending_info.psbt_hex = psbt.serialize();
            if btc_pending_info.is_all_signed() {
                let tx_bytes_with_sign = psbt.extract_tx_bytes_with_sign();

                // For ZCash chains, use base64 encoding to save space (1.33x vs 2x overhead for hex)
                // ZCash transactions with Orchard bundles are larger and benefit from compact encoding
                // For Bitcoin chains, keep hex encoding for backward compatibility

                #[cfg(feature = "zcash")]
                let tx_bytes_base64 = {
                    use near_sdk::base64::{engine::general_purpose::STANDARD, Engine};
                    STANDARD.encode(&tx_bytes_with_sign)
                };

                Event::SignedBtcTransaction {
                    account_id: &account_id,
                    tx_id: btc_pending_sign_id.clone(),
                    #[cfg(not(feature = "zcash"))]
                    tx_bytes: &tx_bytes_with_sign,
                    #[cfg(feature = "zcash")]
                    tx_bytes_base64,
                }
                .emit();

                btc_pending_info.tx_bytes_with_sign = Some(tx_bytes_with_sign);
                btc_pending_info.to_pending_verify_stage();

                let is_original_tx = btc_pending_info.get_original_tx_id().is_none();
                let account = self.internal_unwrap_mut_account(&account_id);
                require!(
                    account.btc_pending_sign_ids.remove(&btc_pending_sign_id),
                    "Internal error"
                );
                if is_original_tx {
                    account
                        .btc_pending_verify_list
                        .insert(btc_pending_sign_id.clone());
                }
            }
            true
        } else {
            false
        }
    }
```
