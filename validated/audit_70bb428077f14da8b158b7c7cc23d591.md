### Title
Unauthenticated Peras Certificate Accepted from Any Peer Corrupts Chain Selection Weight — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`, `Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs`, `Ouroboros/Consensus/Network/NodeToNode.hs`)

### Summary

The degenerate `instance StandardHash blk => BlockSupportsPeras blk` provides a stub `validatePerasCert` that unconditionally returns `Right` for every inbound certificate. The Peras cert diffusion miniprotocol is wired up for all NodeToNode connections without any era or version gate. An unprivileged peer can therefore send a crafted `PerasCert` pointing to any block in the VolatileDB, have it accepted without any cryptographic or era check, and trigger chain selection with an artificial boost weight of 15, potentially causing the node to prefer a non-canonical fork.

### Impact Explanation

An unprivileged peer that has established a NodeToNode connection can:
1. Observe a fork block hash in the VolatileDB (via ChainSync headers)
2. Craft a `PerasCert` with `pcCertBoostedBlock = <fork block point>`
3. Send it over the Peras cert diffusion miniprotocol
4. The cert passes `validatePerasCert` unconditionally
5. Chain selection is triggered; the fork gains +15 weight
6. If the fork is within `k` blocks of the current tip, the node switches to the adversarial fork

This violates the invariant that Peras boosts must only be applied when backed by a quorum of valid committee votes with verified cryptographic signatures. The impact is **chain selection corruption by an unprivileged peer**, matching the "High" scope: *"Chain selection, rollback, forecast, genesis, or header-state bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

### Likelihood Explanation

- The Peras cert diffusion protocol is active for all NodeToNode connections (no version gate)
- The stub `validatePerasCert` requires zero cryptographic material — any `PerasCert` value passes
- The attacker only needs a standard NodeToNode connection and knowledge of a fork block hash (observable via ChainSync)
- No stake, keys, or operator access required
- Locally reproducible with io-sim

### Recommendation

1. **Immediate**: Add an era guard in `makePerasCertPoolWriterFromChainDB` that rejects all certs when the node is not in a Peras-enabled era (check `eraPerasRoundLength` from the current ledger state).
2. **Short-term**: Replace the stub `validatePerasCert` with a real implementation that verifies the certificate's cryptographic proof and committee quorum before issue [#120](https://github.com/tweag/cardano-peras/issues/120) is resolved.
3. **Short-term**: Gate the Peras cert/vote diffusion miniprotocols on a NodeToNode version that is only negotiated when both peers are in a Peras-enabled era.
4. **Tracking**: Resolve [#73](https://github.com/tweag/cardano-peras/issues/73) before any production deployment; the degenerate instance must not reach mainnet.
