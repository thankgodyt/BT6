### Title
VolatileDB Block Deserialization Without Integrity Validation by Default - (File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Storage/VolatileDB/Impl.hs)

---

### Summary

The `VolatileDB` component, which stores the last `k` volatile blocks used for chain selection, defaults to `NoValidation` when parsing blocks from disk on startup. Under this policy, deserialized blocks are accepted into the in-memory index without invoking the `isNotCorrupt` integrity check (which verifies block signatures and hashes). A crafted or corrupted on-disk block file can therefore be loaded into the VolatileDB index and subsequently offered to chain selection as a valid candidate block, bypassing the block-level integrity gate that would otherwise reject it.

---

### Finding Description

`VolatileDB.defaultArgs` sets `volValidationPolicy = NoValidation`:

```haskell
defaultArgs =
  VolatileDbArgs
    { ...
    , volValidationPolicy = NoValidation
    }
```

This default flows directly into `openDB` → `mkOpenState` → `mkOpenStateHelper` → `parseBlockFile`. Inside `parseBlockFile`, the `noValidation` flag short-circuits the `isNotCorrupt blk` predicate entirely:

```haskell
noValidation :: Bool
noValidation = validationPolicy == NoValidation

checkEntries parsed stream =
  S.next stream >>= \case
    ...
    Right ((offset, (size, blk)), stream')
      | noValidation || isNotCorrupt blk ->   -- <-- integrity check skipped when NoValidation
          let !blockInfo = extractBlockInfo blk
              ...
```

When `noValidation` is `True`, every CBOR-decodable block is accepted into `currentRevMap` (the in-memory reverse index) regardless of whether its signature, hash, or other integrity properties are valid. The `isNotCorrupt` predicate — which for Cardano blocks calls `verifyBlockIntegrity` / `verifyHeaderIntegrity` (checking PBFT/Praos signatures) — is never invoked.

The `ChainDbArgs.defaultArgs` composes `VolatileDB.defaultArgs` directly, meaning any deployment that does not explicitly call `ensureValidateAll` (which sets `volValidationPolicy = ValidateAll`) starts with validation disabled. The production node path in `Ouroboros.Consensus.Node` does pass a validation policy, but the default itself is `NoValidation`, and the `completeChainDbArgs` function does not override `volValidationPolicy`, leaving it at whatever the caller's `defArgs` specifies.

Once a block with a forged or corrupted signature is indexed in the VolatileDB, it participates in chain selection: `filterByPredecessor` and `getBlockInfo` return it as a known candidate, and the ChainDB's chain selection logic can select a chain that includes it. The block is only re-checked by `GetVerifiedBlock` (which calls `checkIntegrity`) at the point of copying to the ImmutableDB — but by then, chain selection may already have switched to the adversarial chain and applied the block's ledger state.

---

### Impact Explanation

**High — ChainDB/VolatileDB corruption/replay bug that causes durable use of the wrong ledger state.**

An adversary with write access to the node's VolatileDB directory (e.g., a local reproduction scenario, a private testnet with a shared filesystem, or a Mithril-bootstrapped snapshot that is tampered with before the node starts) can place a crafted `blocks-N.dat` file containing a CBOR-valid but cryptographically invalid block. On startup with `NoValidation`, this block is indexed without signature verification. Chain selection may then prefer a chain containing this block, causing the node to apply an invalid ledger transition and diverge from the honest chain. The ledger state derived from the invalid block is persisted to the LedgerDB snapshot, making the corruption durable across restarts.

---

### Likelihood Explanation

**Likelihood: 2 out of 5.**

Exploitation requires the ability to write to the node's on-disk VolatileDB directory before or during startup. This is not achievable by a remote unprivileged peer over the network alone. However, it is realistic in:
- Private testnets or CI environments with shared storage.
- Nodes bootstrapped via Mithril or external snapshot providers where the snapshot content is not independently verified before being placed on disk.
- Scenarios where a co-located process has filesystem access.

The `NoValidation` default is the shipped default for `defaultArgs`, meaning any integrator who does not explicitly call `ensureValidateAll` is exposed.

---

### Recommendation

1. Change `defaultArgs` in `VolatileDB.Impl` to default to `ValidateAll` instead of `NoValidation`, or document clearly that callers must explicitly opt into `NoValidation` for performance reasons.
2. Ensure `completeChainDbArgs` always sets `volValidationPolicy = ValidateAll` unless the caller explicitly overrides it, rather than inheriting the `NoValidation` default.
3. Add a startup-time warning or assertion when `NoValidation` is active, so operators are aware that block integrity checks are disabled.

  noValidation = validationPolicy == NoValidation

  checkEntries ::
    [ParsedBlockInfo blk] ->
    Stream
      (Of (Word64, (Word64, blk)))
      m
      (Maybe (ReadIncrementalErr, Word64)) ->
    m
      ( [ParsedBlockInfo blk]
      , Maybe (ParseError blk, BlockOffset)
      )
  checkEntries parsed stream =
    S.next stream >>= \case
      Left mbErr ->
        return (reverse parsed, bimap BlockReadErr BlockOffset <$> mbErr)
      Right ((offset, (size, blk)), stream')
        | noValidation || isNotCorrupt blk ->
            let !blockInfo = extractBlockInfo blk
                !newParsed =
                  ParsedBlockInfo
                    { pbiBlockOffset = BlockOffset offset
                    , pbiBlockSize = BlockSize $ fromIntegral size
                    , pbiBlockInfo = blockInfo

                        DepPair nestedCtxt _ -> SomeSecond nestedCtxt
                    }
