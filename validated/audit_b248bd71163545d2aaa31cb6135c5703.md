### Title
`validatePerasCert` Universal Degenerate Instance Unconditionally Accepts All Peer-Supplied Peras Certificates, Enabling Unauthorized Chain Selection Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `BlockSupportsPeras` typeclass declares `validatePerasCert` as the cryptographic gate that must be passed before a Peras certificate is admitted to the node's `PerasCertDB` and allowed to influence chain selection. However, the universal degenerate instance — which covers every block type in production — implements `validatePerasCert` as an unconditional `Right`, performing zero cryptographic or structural checks. The validation infrastructure is fully wired up and called on every inbound certificate, but the enforcement mechanism is a no-op, making the entire certificate validation system useless. An unprivileged peer can send a crafted `PerasCert` for any block in the VolatileDB and have it accepted, triggering chain selection that artificially boosts a weaker fork.

---

### Finding Description

**Root cause — `validatePerasCert` always returns `Right`:**

The `BlockSupportsPeras` typeclass in `SupportsPeras.hs` declares `validatePerasCert` as the required validation step:

```haskell
validatePerasCert ::
  PerasCfg blk ->
  PerasCert blk ->
  Either (PerasValidationErr blk) (ValidatedPerasCert blk)
```

The universal degenerate instance (lines 318–389) that covers all block types implements it as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
```

This always returns `Right` regardless of the certificate's content. No signature is checked, no quorum proof is verified, no round-number bounds are enforced.

**The validation call-site is fully wired up in production:**

`processCerts` in `PerasCert.hs` (lines 156–180) is the inbound certificate handler. It calls the supplied `validateCert` function on every new certificate before admitting it:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _) ->
      throw (PerasCertInboundException errs)
```

`makePerasCertPoolWriterFromChainDB` (lines 113–137 of `PerasCert.hs`) wires this into the production ChainDB path, passing `validatePerasCert mkPerasParams` as the validator:

```haskell
(validatePerasCert mkPerasParams)
```

Because `validatePerasCert` always returns `Right`, `partitionEithers` always produces an empty error list, and every certificate is unconditionally admitted.

**Admitted certificates trigger chain selection:**

`addPerasCertAsync` in `ChainSel.hs` (lines 481–535) processes each admitted certificate. It adds it to the `PerasCertDB` and then calls `chainSelectionForBlock` for the boosted block, potentially switching the node to a fork that is now artificially heavier due to the fake certificate's boost weight.

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` that claims to boost any block currently in the node's VolatileDB. Because `validatePerasCert` never rejects any certificate, the crafted certificate is admitted, stored, and used to inflate the chain-selection weight of the targeted block. If the boosted block is on a weaker fork, the node may switch to that fork, abandoning its current canonical chain. This is a **chain selection manipulation** vulnerability: an attacker with no stake and no keys can cause an honest node to prefer a non-canonical, less-secure chain, violating the core Peras security assumption that only legitimately quorum-certified blocks receive a boost.

**Severity: High** — matches "Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."

---

### Likelihood Explanation

The Peras certificate mini-protocol is wired into the production diffusion layer. Any peer that can establish a connection and send a `PerasCert` message reaches `processCerts` → `validatePerasCert`. No stake, no keys, and no privileged access are required. The attacker only needs to know the hash of a block in the target node's VolatileDB (obtainable via normal ChainSync) and construct a `PerasCert` record pointing to it. The degenerate instance is the only instance in scope for all current block types.

---

### Recommendation

Replace the degenerate `validatePerasCert` implementation with a real cryptographic check that verifies the aggregate vote signature and quorum threshold before returning `Right`. Until the full committee-selection plumbing (tracked in issue #73 and #120) is in place, the certificate inbound path should either be disabled entirely or gated behind a feature flag so that no peer-supplied certificate can influence chain selection without a valid proof.

---

### Proof of Concept

1. Node A is running with the degenerate `BlockSupportsPeras` instance (all current production configurations).
2. Attacker peer connects to Node A via the Peras certificate mini-protocol.
3. Attacker reads Node A's VolatileDB tip via ChainSync to learn the hash of a block `B` on a weaker fork.
4. Attacker constructs `PerasCert { pcCertRound = r, pcCertBoostedBlock = pointOf(B) }` with an arbitrary round number.
5. Attacker sends the certificate to Node A.
6. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right ValidatedPerasCert{vpcCertBoost = perasWeight params}` unconditionally.
7. The certificate is added to `PerasCertDB` and `chainSelectionForBlock` is triggered for `B`.

-- Process a Peras certificate by adding it to the PerasCertDB and potentially
-- performing chain selection if a candidate is now better than our selection.
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes

  -- Deliver promise indicating that we processed the cert.
  lift $ atomically $ putTMVar varProcessed certResult
