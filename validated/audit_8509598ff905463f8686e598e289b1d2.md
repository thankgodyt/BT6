### Title
Peras Vote Signature Lacks Network Domain Binding — `KeyScope` Not Concretely Instantiated in Production (`hashVoteSignature`) - (File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Peras/Crypto/BLS.hs)

---

### Summary

The `hashVoteSignature` function in `PerasBLSCrypto` produces a signed digest that contains only `roundNo`, `boostedBlockSlot`, and `boostedBlockHash`. The BLS signing context is supposed to bind signatures to a specific network via a `KeyScope` augmentation string (e.g., `"VOTE:PERAS/MAINNET:V0"`), but `KeyScope` is never concretely instantiated with a network-specific value in production code — the comment explicitly marks it as "later instantiated." Additionally, `KeyScope` is not serialized as part of the `PublicKey` or `Signature` wire format, so it must be injected at deserialization time. If two networks use the same (or empty) scope, a vote signature produced on one network is cryptographically valid on the other, enabling cross-network vote replay via the Peras vote diffusion miniprotocol.

---

### Finding Description

**Root cause — `hashVoteSignature` contains no network identifier:** [1](#0-0) 

The signed payload is `hash(roundNo || boostedBlockSlot || boostedBlockHash)`. No genesis hash, network magic, or chain identifier is included in the message itself.

**The `KeyScope` mechanism is designed to fill this gap but is not yet instantiated:** [2](#0-1) 

The comment reads: *"Key scope, later instantiated with usage and network id (e.g. PERAS/MAINNET)"*. No production code sets this to a network-specific value. The only concrete value seen in the entire codebase is `"TEST"` in test helpers. [3](#0-2) 

**The `KeyScope` is not serialized — it must be injected at deserialization time:**

`rawSerialisePublicKey` serializes only `unPublicKey` (the raw BLS point), discarding `publicKeyScope`: [4](#0-3) 

`rawDeserialisePublicKey` requires the caller to supply the scope: [5](#0-4) 

This means the scope used during verification is entirely determined by the deserializing node, not by the on-chain key registration. If two networks deserialize committee keys with the same scope (or an empty one), the BLS augmentation context `"VOTE:" <> keyScope <> ":V0"` is identical across both networks: [6](#0-5) 

**Signing and verification both use the scope from the key object:** [7](#0-6) 

**Exploit path — vote diffusion miniprotocol:**

Inbound Peras votes are received from untrusted peers via `hPerasVoteDiffusionClient` and validated by `validatePerasVote`: [8](#0-7) 

The vote structure `PerasVote` carries `pvSignature :: VoteSignature PerasBLSCrypto` with no scope field: [9](#0-8) 

Verification in `implVerifyVote` calls `verifyVoteSignature` using the public key from the committee's stake distribution, whose `publicKeyScope` is whatever the local node injected at deserialization time: [10](#0-9) 

---

### Impact Explanation

If two Cardano networks (e.g., mainnet and a private testnet, or two testnets) both instantiate `KeyScope` with the same value — which is the current state since no network-specific value is set anywhere — a vote signature produced by a legitimate committee member on network A is cryptographically valid on network B for the same `(roundNo, boostedBlock)` pair. An unprivileged peer can collect valid vote signatures from one network and inject them into another via the vote diffusion miniprotocol, causing a node to accept unauthorized Peras votes. This weakens Peras voting authorization and, if enough replayed votes reach quorum, could cause a node to accept a fraudulent Peras certificate boosting a non-canonical chain.

**Impact category**: Medium — public miniprotocol flaw that materially weakens Peras vote/certificate authorization without requiring DoS.

---

### Likelihood Explanation

Peras is actively being developed and integrated (CHANGELOG shows ongoing work on `PerasVoteDB`, `PerasCertDB`, chain selection weight, and diffusion). The `KeyScope` gap is explicitly deferred ("later instantiated"). When Peras is enabled on a real network, if the scope is not concretely set to a network-specific value before deployment, the vulnerability is immediately reachable by any peer connected to the vote diffusion miniprotocol. The likelihood is medium-high: the mechanism exists but the critical instantiation step is missing and not enforced by the type system.

---

### Recommendation

1. **Concretely instantiate `KeyScope`** with a network-specific value (e.g., including the genesis hash or network magic) before Peras is deployed. Do not leave it as an unset `ByteString`.
2. **Include the network identifier in `hashVoteSignature`** directly in the signed payload (analogous to how Praos VRF includes the epoch nonce), so the domain binding is cryptographic and independent of the key deserialization path.
3. **Serialize `publicKeyScope` as part of the `PublicKey` wire format**, or enforce at the ledger layer that registered keys carry a scope that matches the local network configuration.

---

### Proof of Concept

1. Run two private Cardano testnets A and B, both with Peras enabled and `KeyScope` unset (defaulting to the same value, e.g., empty or `"TEST"`).
2. On network A, a legitimate committee member signs a vote for `(roundNo=42, boostedBlock=X)`.
3. Collect the serialized `PerasVote` (containing `pvSignature`) from network A's vote diffusion stream.
4. Inject the same `PerasVote` bytes into network B's vote diffusion miniprotocol as an inbound peer message.
5. Network B's `validatePerasVote` calls `verifyVoteSignature` using the committee member's public key (deserialized with the same scope). Since `hashVoteSignature(42, X)` is identical on both networks and the BLS context `"VOTE:" <> "" <> ":V0"` is identical, verification succeeds.
6. The replayed vote is accepted into network B's `PerasVoteDB` and may contribute to a fraudulent quorum.

  ElectionId PerasBLSCrypto ->

hashVoteSignature roundNo boostedBlock =
  Hash.castHash
    . Hash.hashWith id
    . runByteBuilder (8 + 8 + 32)
    $ roundNoBytes
      <> boostedBlockSlotBytes
      <> boostedBlockHashBytes

    BS.word64BE
