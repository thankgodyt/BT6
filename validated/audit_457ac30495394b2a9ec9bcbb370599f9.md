### Title
Hardcoded `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` Causes Incorrect Chain Disconnection Beyond Forecast Horizon - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

### Summary

In the ChainSync client, when a peer's header is beyond the forecast horizon, the `checkPreferTheirsOverOurs` guard uses a hardcoded `emptyPerasWeightSnapshot` instead of the live `PerasWeightSnapshot` when comparing the candidate chain against the local selection. This is the direct analog of the external report's "stale cached state" class: a frozen/empty value is substituted for the current one, causing the comparison to ignore all Peras certificate boosts. The result is that a node can be made to disconnect from a peer offering a legitimately heavier (Peras-boosted) chain, leaving the node on a less-secure selection.

### Finding Description

Inside `checkTime`, the local helper `checkPreferTheirsOverOurs` is invoked whenever `projectLedgerView` returns `Nothing` (i.e., the incoming header is beyond the forecast horizon). Its job is to decide whether to disconnect from the peer or to `retry` (block) waiting for the local chain to advance:

```haskell
-- Client.hs ~1834
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← hardcoded empty snapshot
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse
          mostRecentIntersection
          (ourTipFromChain ourFrag)
          (theirTipFromChain theirFrag)
``` [1](#0-0) 

The call site that triggers this path is:

```haskell
-- Client.hs ~1814
case prj lst of
  Nothing -> do
    checkPreferTheirsOverOurs kis'
    retry
``` [2](#0-1) 

By contrast, every other chain-comparison site in the codebase fetches the live snapshot. For example, `chainSelectionForBlock` reads it atomically from the `PerasCertDB`:

```haskell
-- ChainSel.hs ~629
(invalid, curChain, weights) <-
  atomically $
    (,,)
      <$> (forgetFingerprint <$> readTVar cdbInvalid)
      <*> Query.getCurrentChain cdb
      <*> (forgetFingerprint <$> Query.getPerasWeightSnapshot cdb)
``` [3](#0-2) 

The `PerasWeightSnapshot` is maintained in `PerasCertDB` and updated every time a new certificate is added:

```haskell
-- PerasCertDB/Impl.hs ~203
implGetWeightSnapshot PerasCertDbEnv{pcdbState} = do
  WithFingerprint pcds fp <- readTVar pcdbState
  let weights =
        mkPerasWeightSnapshot
          [ (getPerasCertBoostedBlock cert, getPerasCertBoost cert)
          | cert <- Map.elems (pcdsCertsByTicket pcds) ]
  pure (WithFingerprint weights fp)
``` [4](#0-3) 

`checkPreferTheirsOverOurs` never reads from `PerasCertDB`; it always passes `emptyPerasWeightSnapshot` to `preferAnchoredCandidate`, so the comparison is performed as if no Peras certificates exist.

The `emptyPerasWeightSnapshot` constant is simply an empty map:

```haskell
emptyPerasWeightSnapshot :: PerasWeightSnapshot blk
emptyPerasWeightSnapshot = PerasWeightSnapshot Map.empty
``` [5](#0-4) 

### Impact Explanation

In the Peras protocol, certificates boost specific blocks, so a chain with fewer blocks can be heavier (and thus canonical) than a longer chain. When a peer sends a header beyond the forecast horizon, `checkPreferTheirsOverOurs` compares the candidate against the local selection using only block count (because Peras boosts are zeroed out). If the candidate chain is heavier due to Peras boosts but shorter in block count, the comparison will incorrectly conclude the candidate is not preferable, and the node throws `CandidateTooSparse`, disconnecting from the peer. The node then remains on its current, lighter (less-secure) selection instead of adopting the canonical chain. This is a chain-selection error: an honest node is made to prefer a non-canonical chain beyond the intended Peras security assumptions.

**Impact: High** — Chain selection bug that causes an honest node to reject the canonical Peras-weighted chain and remain on a less-secure selection.

### Likelihood Explanation

**Likelihood: Medium.** The conditions required are: (1) Peras is active and certificates have been issued boosting blocks on a candidate chain; (2) the candidate's tip slot is beyond the forecast horizon at the current intersection (a normal occurrence during sync or when a peer is ahead by more than the stability window); (3) the candidate is heavier by Peras weight but shorter by block count. An adversary who controls the node's current chain can engineer condition (3) by ensuring the node is on a longer but unboosted chain, then having an honest peer offer a shorter but boosted chain. The entry path is fully reachable by any unprivileged peer via the ChainSync `MsgRollForward` message.

### Recommendation

Replace the hardcoded `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live snapshot fetched from the `ChainDbView`. The `ChainDbView` record already exposes `getPerasWeightSnapshot :: STM m (WithFingerprint (PerasWeightSnapshot blk))` and is in scope inside `checkTime` via `chainDbView`. The corrected comparison should be:

```haskell
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis = do
  weights <- forgetFingerprint <$> getPerasWeightSnapshot chainDbView
  if shouldSwitch $
       preferAnchoredCandidate (configBlock cfg) weights ourFrag theirFrag
    then pure ()
    else throwSTM $ CandidateTooSparse ...
```

This mirrors the pattern used in `chainSelectionForBlock` and `chainSelSync`, which both read the live snapshot atomically before performing any chain comparison.

### Proof of Concept

1. Node N holds chain C1: 100 blocks, 0 Peras boosts → total weight 100.
2. Peer P holds chain C2: 95 blocks, Peras boosts summing to 10 → total weight 105 (canonical under Peras).
3. P sends the tip header of C2 to N via `MsgRollForward`. The header's slot is beyond the forecast horizon at the current intersection.
4. `rollForward` → `checkTime` → `readLedgerStateHelper` → `projectLedgerView` returns `Nothing`.
5. `checkPreferTheirsOverOurs` is called. It invokes `preferAnchoredCandidate cfg emptyPerasWeightSnapshot ourFrag theirFrag`.
6. With `emptyPerasWeightSnapshot`, C2 has effective weight 95 < C1's weight 100. `ShouldNotSwitch` is returned.
7. `CandidateTooSparse` is thrown; N disconnects from P.
8. N remains on C1 (weight 100) and never adopts C2 (weight 105), the canonical chain.
