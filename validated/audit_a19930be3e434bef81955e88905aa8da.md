### Title
Unit Mismatch in Peras Quorum Check Enables Unauthorized Certificate Forging - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` compares a `PerasVoteStake` value directly against the relative (normalized) `perasQuorumStakeThreshold` without any unit normalization. The code itself documents that `PerasVoteStake` must be a normalized relative value for the comparison to be correct, but no normalization is enforced or performed before the comparison. When the actual committee selection plumbing populates `PerasVoteStakeDistr` with absolute ledger stake values (lovelace), the comparison will always evaluate to `True`, allowing any single voter to unilaterally forge a Peras certificate for any block they choose.

---

### Finding Description

`stakeAboveThreshold` in `SupportsPeras.hs` performs the core Peras quorum check:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake         = unPerasVoteStake voteStake
  quorumThreshold = unPerasQuorumStakeThreshold (perasQuorumStakeThreshold params)
  safetyMargin  = unPerasQuorumStakeThresholdSafetyMargin (...)
```

Both `stake` and `quorumThreshold` are `Rational`, but they represent values in **different units**. The `perasQuorumStakeThreshold` is a relative fraction of total committee stake (e.g., `3 % 4` for 75%), while `PerasVoteStake` is populated directly from `PerasVoteStakeDistr` without normalization:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
```

The code itself acknowledges this mismatch with an explicit TODO comment:

> "this function assumes that the 'PerasVoteStake' and the quorum threshold used in 'PerasParams' are expressed in the same units … this function only makes sense when both values are relative (normalized) values, so we should either normalize the 'PerasVoteStake' before calling this function, or change this function to accept a stake distribution and perform the normalization internally."

When the actual committee selection data is connected (replacing the current placeholder `PerasVoteStakeDistr mempty`), `PerasVoteStakeDistr` will naturally be populated with absolute ledger stake values (lovelace, e.g., `1_000_000_000`). Summing even a single voter's absolute stake produces a `totalVoteStake` far exceeding the relative threshold of `0.75`, so `stakeAboveThreshold` returns `True` unconditionally.

`votesReachQuorum` calls `stakeAboveThreshold` on the accumulated `totalVoteStake`:

```haskell
totalVoteStake      = mconcat (vpvVoteStake <$> votes)
votesHaveEnoughStake = stakeAboveThreshold cfg totalVoteStake
```

A single vote from any voter with non-zero absolute stake would satisfy the quorum check, causing `votesReachQuorum` to return `Just votesWithQuorum` and triggering `forgePerasCert`.

---

### Impact Explanation

A Peras certificate boosts the chain weight of the block it certifies via `vpcCertBoost :: PerasWeight`. Any node that accepts a fraudulently forged certificate will assign inflated weight to the attacker's chosen block, causing it to be preferred over the honest canonical chain in chain selection. This is a **bypass of Peras certificate/vote verification** that enables unauthorized certificate acceptance and a chain-selection safety failure — matching the "Critical" and "High" impact tiers in the allowed scope.

---

### Likelihood Explanation

The production diffusion layer currently passes `PerasVoteStakeDistr mempty` (empty distribution), so all votes are currently rejected and the bug is not yet exploitable on mainnet. However, the code is under active development and the TODO comment explicitly anticipates connecting real committee selection data. Once that plumbing is wired in — a necessary step before Peras can function — any peer with any positive ledger stake can trigger the bug with a single vote over the `PerasVoteDiffusion` mini-protocol. No special privileges, key compromise, or stake majority is required.

---

### Recommendation

Normalize `PerasVoteStake` to a relative value before it is stored in `PerasVoteStakeDistr` or before it is passed to `stakeAboveThreshold`. Concretely, divide each voter's absolute ledger stake by the total committee stake when constructing the distribution, so that `unPerasVoteStake` is always in `[0, 1]` and directly comparable to `perasQuorumStakeThreshold`. Alternatively, change `stakeAboveThreshold` to accept the total committee stake and perform the normalization internally, eliminating the implicit unit assumption.

---

### Proof of Concept

1. Populate `PerasVoteStakeDistr` with a single voter whose absolute stake is `1_000_000_000` lovelace (a realistic small pool).
2. That voter sends one `PerasVote` via the `PerasVoteDiffusion` mini-protocol.
3. `validatePerasVote` looks up the voter's stake: `vpvVoteStake = PerasVoteStake (1_000_000_000 % 1)`.
4. `votesReachQuorum` computes `totalVoteStake = PerasVoteStake (1_000_000_000 % 1)`.
5. `stakeAboveThreshold` evaluates `1_000_000_000 >= 0.75 + safetyMargin` → `True`.
6. `forgePerasCert` is called, producing a `ValidatedPerasCert` boosting the attacker's chosen block.
7. Any node that processes this certificate will prefer the attacker's chain over the honest chain.
