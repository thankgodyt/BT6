### Title
Stub `validatePerasCert` Always Accepts Any Peer-Supplied Peras Certificate, Enabling Unauthorized Chain-Selection Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` is an acknowledged stub that unconditionally returns `Right` (success) for every certificate it receives, performing zero cryptographic or structural checks. Because the Peras certificate diffusion path calls this stub directly on every inbound peer certificate before adding it to the ChainDB, any unprivileged peer can inject an arbitrary `PerasCert` (claiming any round number and any boosted block point) that will be accepted as `ValidatedPerasCert` and trigger chain selection with a weight boost of `perasWeight` (currently 15). This is the direct analog of the HopFacetOptimized missing-authorization bug: a function that should enforce a privileged check instead performs no check at all, allowing any caller to produce an authorized-looking result.

---

### Finding Description

**Root cause — stub validation that always succeeds:** [1](#0-0) 

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This is the **only** `BlockSupportsPeras` instance in the codebase (a catch-all `instance StandardHash blk => BlockSupportsPeras blk`), explicitly marked as a "degenerate instance for all blks to get things to compile." [2](#0-1) 

**Production inbound path — cert diffusion writer calls the stub:**

Both `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB` pass `validatePerasCert mkPerasParams` as the validation function to `processCerts`: [3](#0-2) [4](#0-3) 

**`processCerts` — the inbound gate that relies entirely on the stub:** [5](#0-4) 

`processCerts` calls `validateCert` (bound to the stub) on each inbound cert. Because the stub always returns `Right`, the `([], validatedCerts)` branch is always taken and every cert is timestamped and forwarded to `addCert` (i.e., `ChainDB.addPerasCertAsync`).

**Chain selection is then triggered with the injected boost:** [6](#0-5) 

`addPerasCertAsync` enqueues the `ValidatedPerasCert` (carrying `vpcCertBoost = perasWeight params = 15`) into the `ChainSelQueue`, where `chainSelSync` processes it and may switch the node to a different chain.

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` with:
- `pcCertRound` set to any round number not yet in the DB (bypassing the deduplication check at line 166 of `PerasCert.hs`), and
- `pcCertBoostedBlock` pointing to any block point the attacker wants to boost.

The cert passes the stub validation unconditionally, is stored as `ValidatedPerasCert` with a weight boost of 15, and triggers chain selection. If the attacker's chosen block is on a fork, the honest node may switch to that fork, preferring a non-canonical chain over the canonical one. This satisfies the **High** impact criterion: *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

---

### Likelihood Explanation

The attack requires only a network connection to a Cardano node running the Peras cert diffusion mini-protocol. No keys, stake, or privileged access are needed. The attacker simply sends a well-formed `PerasCert` CBOR message. The stub is the **only** instance in the codebase and is wired into both the `PerasCertDB`-backed and `ChainDB`-backed production writers. Likelihood is **High** once Peras cert diffusion is enabled on mainnet.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
1. The aggregate vote signature over the claimed `(electionId, candidate)` pair using the committee's public keys (as already implemented in `implVerifyCert` in `WFALS.hs` and `EveryoneVotes.hs`).
2. That the claimed voters constitute a quorum of the committee for the relevant epoch.
3. That the boosted block point exists and is within the valid age window (`perasCertMaxRounds`).

Until the full committee-selection plumbing is in place, the cert diffusion inbound handler should refuse all inbound certificates rather than accept them unconditionally, to avoid the chain-selection manipulation vector. [7](#0-6) 

---

### Proof of Concept

1. Connect to a node with Peras cert diffusion enabled.
2. Send a `PerasCert` message with:
   - `pcCertRound = R` (any round not yet in the node's `PerasCertDB`)
   - `pcCertBoostedBlock = Point` of a block on a minority fork
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right (ValidatedPerasCert { vpcCertBoost = 15 })`.
4. The cert is enqueued via `addPerasCertAsync`.
5. `chainSelSync` runs, applies the 15-unit weight boost to the minority fork's tip, and if the boosted fork now outweighs the canonical chain, the node switches to the minority fork.
6. Repeat with incrementing `pcCertRound` values to continuously re-trigger chain selection toward the attacker's preferred fork. [8](#0-7) [9](#0-8) [6](#0-5)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
