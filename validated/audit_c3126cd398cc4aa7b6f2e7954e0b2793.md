### Title
Peras Certificate Verification Bypass via Stub `validatePerasCert` Implementation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance provides a stub `validatePerasCert` that unconditionally returns `Right` (success) for every inbound certificate, performing zero cryptographic or structural checks. This stub is wired directly into the production certificate-ingest path. An unprivileged peer can send a crafted `PerasCert` for any round number and any block point; the node will accept it, store it, and apply its chain-selection boost weight without any verification.

---

### Finding Description

The `BlockSupportsPeras` type class declares `validatePerasCert` as the mandatory gate before a certificate is stored or acted upon. The repository ships a catch-all instance for every `StandardHash blk`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is the **only** instance in the repository. No more-specific instance for `CardanoBlock` or any Shelley-era block overrides it. The production certificate-ingest path in `makePerasCertPoolWriterFromChainDB` calls `validatePerasCert mkPerasParams` directly:

```haskell
(validatePerasCert mkPerasParams)
``` [2](#0-1) 

`processCerts` then uses the result of this call to decide whether to add the certificate to the `PerasCertDB` / `ChainDB`: [3](#0-2) 

The same stub is used in `makePerasCertPoolWriterFromCertDB`: [4](#0-3) 

The `implAddCert` path in `PerasCertDB.Impl` also carries a matching TODO acknowledging that non-trivial validation is absent: [5](#0-4) 

**Analog to `safeApprove`:** Just as `safeApprove` was supposed to check and reset the existing allowance state before setting a new one (but skipped that check, allowing the operation to proceed when it should have failed), `validatePerasCert` is supposed to check the certificate's cryptographic validity before accepting it (but the stub skips all checks, allowing any certificate to be accepted when it should be rejected). In both cases, a required guard is absent, and the operation proceeds unconditionally.

---

### Impact Explanation

A `ValidatedPerasCert` carries a `vpcCertBoost` weight that directly influences chain selection via the Peras boosting mechanism. Any peer can craft a `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock` (pointing to any block point, including a non-canonical or attacker-controlled fork tip). Because `validatePerasCert` always returns `Right`, the certificate passes the ingest gate, is stored in the `PerasCertDB`, and its boost weight is applied during chain selection. This enables an unprivileged peer to steer an honest node toward a non-canonical chain by injecting fabricated Peras certificates — a chain-selection integrity failure.

Impact classification: **Critical — bypass of Peras certificate verification enabling unauthorized certificate acceptance and chain-selection manipulation.**

---

### Likelihood Explanation

The Peras certificate mini-protocol is reachable by any connected peer. No authentication or privilege is required to submit a `PerasCert` message. The stub is the only implementation in the codebase; there is no fallback or override. Any peer that sends a well-formed CBOR-encoded `PerasCert` (round number + block point) will have it accepted. Likelihood is **High** once the Peras protocol is active on a network.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
1. The certificate's aggregate BLS signature over the claimed round and boosted block.
2. That the signers were eligible committee members for the claimed round (VRF eligibility proofs).
3. That the total stake of the signers meets the quorum threshold.
4. That the boosted block point exists and is within the valid boosting window for the round.

Until a real implementation is available, the stub should not be wired into any production ingest path. The `processCerts` / `makePerasCertPoolWriterFromChainDB` functions should be gated behind a feature flag that is disabled by default.

---

### Proof of Concept

**Attacker-controlled entry path:**

1. Peer connects to a Cardano node running with Peras enabled.
2. Peer sends a `PerasCert` message via the Peras certificate mini-protocol containing:
   - `pcCertRound = <any round number>`
   - `pcCertBoostedBlock = <point of attacker's preferred fork tip>`
3. `makePerasCertPoolWriterFromChainDB` receives the cert and calls `processCerts`.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`.
5. The stub returns `Right ValidatedPerasCert{vpcCert = cert, vpcCertBoost = perasWeight params}` unconditionally.
6. The cert is stored in `PerasCertDB` / `ChainDB` with its boost weight applied.
7. Chain selection now treats the attacker's fork as having a Peras certificate boost, potentially causing the honest node to prefer the attacker's chain over the canonical chain.

**Root cause line:**
