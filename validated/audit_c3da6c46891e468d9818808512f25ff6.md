### Title
Ambiguous Zero Return from `safe_mint` / `ft_transfer_call` Causes UTXO to Be Unlocked for Re-Submission, Enabling Unauthorized nBTC Double-Minting — (File: `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

---

### Summary

`safe_mint_callback` uses `is_refund_required()` to decide whether to burn minted tokens and remove the UTXO from the verified set. `is_refund_required()` returns `true` whenever `safe_mint` returns `U128(0)`. However, `safe_mint` returns `U128(0)` in two distinct situations: (1) the recipient is not registered, and (2) `ft_transfer_call` completed successfully and the receiver used **all** tokens. The bridge cannot distinguish these cases. In case (2), the bridge incorrectly enters the failure branch, removes the UTXO from `verified_deposit_utxo`, and fires a detached `burn` that silently fails (because `bridge_id` has no balance left). The UTXO is now unlocked for re-submission, enabling an attacker to mint nBTC for the same BTC UTXO a second time.

---

### Finding Description

**`safe_mint` in `contracts/nbtc/src/lib.rs`** mints `mint_amount` tokens to `bridge_id`, then:

- If recipient is unregistered → returns `PromiseOrValue::Value(U128(0))` immediately.
- If `msg` is `None` → calls `ft_transfer` and returns `PromiseOrValue::Value(amount)` (non-zero).
- If `msg` is `Some` → calls `ft_transfer_call` and returns its result directly. [1](#0-0) 

`ft_transfer_call` returns the amount **not used** by the receiver (the NEP-141 standard). When the receiver's `ft_on_transfer` returns `0` (all tokens consumed), `ft_transfer_call` resolves to `U128(0)`.

**`is_refund_required()` in `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`** treats any `U128(0)` result as "refund required": [2](#0-1) 

So when `ft_transfer_call` succeeds and the receiver uses all tokens, `is_refund_required()` incorrectly returns `true`.

**`safe_mint_callback`** then enters the failure branch: [3](#0-2) 

1. Removes the UTXO from `verified_deposit_utxo` (unlocking it for re-submission).
2. Fires `burn(bridge_id, mint_amount).detach()` — but `bridge_id` has zero balance (all tokens were transferred to the receiver via `ft_transfer_call`), so `internal_withdraw` panics inside the nbtc contract.
3. Because the call is `.detach()` with no callback, the panic is silently discarded.

The UTXO is now absent from `verified_deposit_utxo` and absent from the bridge's UTXO set. The only guard against re-submission is: [4](#0-3) 

Since the key was removed, this `require!` passes on re-submission, and the attacker receives a second mint for the same BTC UTXO.

---

### Impact Explanation

An attacker who controls the `recipient_id` contract can receive nBTC for a single BTC UTXO an unbounded number of times. Each re-submission passes light-client proof verification (the Bitcoin transaction is valid and confirmed), and the bridge's only replay guard (`verified_deposit_utxo`) is cleared by the bug. This constitutes **unauthorized minting** of nBTC unbacked by BTC, directly inflating supply and draining the bridge's backing.

---

### Likelihood Explanation

The attack requires:
1. Making a BTC deposit with a non-empty `msg` field in `SafeDepositMsg` — fully user-controlled input accepted by `safe_verify_deposit`.
2. Controlling the `recipient_id` contract so that `ft_on_transfer` returns `0` (uses all tokens) — trivial for any NEAR developer.
3. Re-submitting the same `tx_bytes`/`vout` proof — the Bitcoin transaction is already on-chain and the proof is public.

No privileged role, leaked key, or operator cooperation is required. Any NEAR account can execute this.

---

### Recommendation

`is_refund_required()` must distinguish between the two zero-return cases. One approach: have `safe_mint` return a sentinel value (e.g., `U128(u128::MAX)`) when the recipient is unregistered, and treat `U128(0)` from `ft_transfer_call` as success (all tokens used). Alternatively, add a separate boolean flag or use a wrapper return type so the callback can unambiguously determine whether minting succeeded.

Additionally, the detached `burn` call should be replaced with a chained callback that handles failure explicitly — analogous to how `internal_transfer_nbtc` uses `transfer_nbtc_callback` with `lost_found` tracking. [5](#0-4) 

---

### Proof of Concept

1. Attacker deploys a NEAR contract `attacker.near` whose `ft_on_transfer` always returns `"0"` (uses all tokens).
2. Attacker sends BTC to the bridge deposit address derived from a `DepositMsg` with `recipient_id = attacker.near` and a non-empty `msg`.
3. Attacker (or any relayer) calls `safe_verify_deposit` with the BTC transaction proof.
4. `verify_safe_deposit_callback` runs: UTXO added to `verified_deposit_utxo`, `safe_mint(attacker.near, mint_amount, Some(msg))` called.
5. `safe_mint` mints `mint_amount` to `bridge_id`, calls `ft_transfer_call(attacker.near, mint_amount, None, msg)`.
6. `attacker.near::ft_on_transfer` returns `"0"` — all tokens consumed.
7. `ft_resolve_transfer` returns `U128(0)` (0 refunded).
8. `safe_mint_callback` sees `U128(0)`, `is_refund_required() = true`, enters failure branch.
9. UTXO removed from `verified_deposit_utxo`. `burn(bridge_id, mint_amount).detach()` panics silently (bridge_id balance = 0).
10. Attacker calls `safe_verify_deposit` again with the same proof.
11. `verify_safe_deposit_callback` runs: `verified_deposit_utxo.insert(...)` succeeds (key was removed). `safe_mint` called again → second mint of `mint_amount` to attacker.
12. Repeat indefinitely.

fn is_refund_required() -> bool {
    match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
        Ok(value) => {
            if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {
                // Normal case: refund if the used token amount is zero
                // The amount can be zero if the `ft_on_transfer` in the receiver contract returns an amount instead of `0`, or if it panics.
                amount.0 == 0
            } else {
                // Unexpected case: don't refund
                false
            }
        }
        // Unexpected case: don't refund
        Err(_) => false,
    }
}
