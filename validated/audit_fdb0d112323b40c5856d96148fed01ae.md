### Title
Missing Cryptographic Signature Verification in `validatePerasVote` Allows Any Peer to Forge Votes for Registered Voters — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasVote` implementation performs no cryptographic signature verification and ignores the protocol configuration parameter entirely. Any unprivileged peer can send a `PerasVote` claiming to be any registered voter in the stake distribution. The vote passes validation, is stored in the `PerasVoteDB`, and its stake is counted toward quorum. If enough such forged votes accumulate for the same target, a Peras certificate is forged and the targeted block's chain-selection weight is boosted — without any legitimate voter having actually cast a vote.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasVote` as the gate that must accept a raw `PerasVote` before it enters the vote aggregation pipeline. The production instance — applied universally to all blocks via `instance StandardHash blk => BlockSupportsPeras blk` — is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right
        ValidatedPerasVote
          { vpvVote = vote
          , vpvVoteStake = stake
          }
  | otherwise =
      Left PerasValidationErr
``` [1](#0-0) 

The only check performed is whether `pvVoteVoterId` (the claimed voter identity) exists as a key in the `PerasVoteStakeDistr` map. The function:

- Ignores `_params` entirely (the leading underscore is intentional — the parameter is discarded).
- Performs **no cryptographic signature verification** over the vote body.
- Performs **no round-number validation** (the vote could be for any past or future round).
- Performs **no block-point validation** (the vote could target any block point).

The `PerasVote blk` data type carries only three fields: `pvVoteRound`, `pvVoteBlock`, and `pvVoteVoterId`. All three are attacker-controlled in a network message. [2](#0-1) 

The stake distribution (`PerasVoteStakeDistr`) is a `Map PerasVoterId PerasVoteStake` whose keys are the registered voter IDs — a publicly known set derived from the ledger state. [3](#0-2) 

The validated vote flows directly into `processVotes`, which is called from both `makePerasVotePoolWriterFromVoteDB` and `makePerasVotePoolWriterFromChainDB` — the two entry points for inbound votes received from peers over the object-diffusion mini-protocol:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [4](#0-3) 

After passing `validatePerasVote`, the vote is timestamped and passed to `PerasVoteDB.addVote` (or `ChainDB.addPerasVoteWithAsyncCertHandling`), which calls `updatePerasRoundVoteStates`. That function accumulates stake per `(roundNo, blockPoint)` target and forges a `ValidatedPerasCert` the moment the accumulated stake crosses `stakeAboveThreshold`: [5](#0-4) 

The forged certificate boosts the chain-selection weight of the targeted block, directly influencing which chain the node considers canonical.

The parallel to the external report is exact:
- **External**: `referralInfoMap[referrer]` is written with caller-supplied values; no access control; downstream `createTaker` reads `referralInfoMap[msg.sender]` and allocates bonuses based on the corrupted state.
- **Consensus**: `pvdsVoteIds` / `pvdsRoundVoteStates` are written with peer-supplied voter IDs and stake; no signature check; downstream `stakeAboveThreshold` reads the accumulated stake and forges a certificate based on the corrupted tally.

The `validatePerasCert` method has the same defect — it unconditionally accepts any certificate:

```haskell
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [6](#0-5) 

The `V1.hs` module defines a richer `PerasVote` type that includes a `pvSignature` field and an eligibility proof, confirming that the intended design requires signature verification — but this is not wired into the production `validatePerasVote` path. [7](#0-6) 

---

### Impact Explanation

An unprivileged peer can forge Peras votes for any registered voter in the stake distribution (a public set). By sending enough forged votes targeting a specific block, the attacker can cause the receiving node to:

1. Reach the Peras quorum threshold for an attacker-chosen block.
2. Forge a `ValidatedPerasCert` for that block.
3. Apply a chain-selection boost (`vpcCertBoost = perasWeight params`) to that block.
4. Prefer a non-canonical or adversarially chosen chain over the honest chain.

This is a **Critical** bypass of Peras voting authorization: the certificate check that is supposed to require a quorum of legitimate stake-weighted votes is entirely circumvented. The impact matches: "Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance."

---

### Likelihood Explanation

The attack requires only network access to a node running the Peras object-diffusion mini-protocol. The attacker needs to know the set of registered voter IDs (derivable from the public ledger state) and send well-formed `PerasVote` CBOR messages. No keys, stake, or privileged access are required. The `processVotes` entry point is reachable from any connected peer.

---

### Recommendation

1. Implement cryptographic signature verification inside `validatePerasVote` using the BLS infrastructure already present in `V1.hs` and `Ouroboros.Consensus.Committee.WFALS` (which already calls `checkVoteSignature` and `verifyAggregateVoteSignature`).
2. Validate `pvVoteRound` against the current protocol round before accepting a vote.
3. Validate `pvVoteBlock` against the node's known chain before accepting a vote.
4. Remove the `_params` wildcard and enforce protocol-parameter checks (e.g., round bounds, committee eligibility).
5. Apply the same fix to `validatePerasCert` — it must verify the aggregate BLS signature before accepting a certificate.

---

### Proof of Concept

A private-testnet node running the Peras object-diffusion protocol receives the following sequence from an attacker peer:

1. Attacker reads the current `PerasVoteStakeDistr` (derivable from the ledger state) and identifies `N` voter IDs whose combined stake exceeds `perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin`.
2. Attacker constructs `N` `PerasVote` messages, each with:
   - `pvVoteRound = <target round>`
   - `pvVoteBlock = <attacker-chosen block point>`
   - `pvVoteVoterId = <one of the N legitimate voter IDs>`
   - No valid signature (the field does not exist in the degenerate `PerasVote blk` type used by `validatePerasVote`).
3. Attacker sends the batch via the object-diffusion mini-protocol.
4. `processVotes` calls `validatePerasVote mkPerasParams sd vote` for each; all pass because `pvVoteVoterId` is in `sd`.
5. Each vote is added to `PerasVoteDB`; `updatePerasRoundVoteStates` accumulates stake.
6. Once the threshold is crossed, `forgePerasCert` is called and a `ValidatedPerasCert` is stored for the attacker-chosen block.
7. Chain selection applies `perasWeight` boost to the attacker-chosen block, causing the node to prefer it over the honest chain tip. [8](#0-7) [9](#0-8)

processVotes ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
