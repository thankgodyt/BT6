### Title
Missing Ownership Check on `refund_address` in Permissionless `request_refund` Allows Attacker to Redirect Victim's BTC Refund — (File: `contracts/satoshi-bridge/src/api/bridge.rs`, `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

The `request_refund` function is callable by any unprivileged NEAR account. When the original `deposit_msg.refund_address` field is `None`, the function accepts any caller-supplied `refund_address` BTC address without verifying that the caller has any authority over the deposit or is the intended recipient. An attacker who learns the victim's `deposit_msg` (trivially obtainable from on-chain NEAR events) can register a refund request pointing to their own BTC address, and after the timelock elapses, execute the refund to steal the victim's BTC.

---

### Finding Description

`request_refund` in `bridge.rs` is a permissionless, payable function with no caller identity check: [1](#0-0) 

It delegates to `internal_request_refund`, which only enforces a `refund_address` match when `deposit_msg.refund_address` is already set: [2](#0-1) 

When `deposit_msg.refund_address` is `None` — the common case for users who did not pre-authorize a BTC return address — **no ownership or authority check is performed**. Any caller may supply any BTC address as `refund_address`, and it is stored verbatim in the `RefundRequest`: [3](#0-2) 

The only mitigation is a longer `unsafe_refund_timelock_sec` applied when `deposit_msg.refund_address` is `None`, giving the DAO/Operator a window to reject suspicious requests: [4](#0-3) 

This is an operator-dependent mitigation, not a cryptographic guarantee. If the DAO is slow, unavailable, or the timelock is long enough for the attacker to wait, the theft succeeds.

The victim's `deposit_msg` is not secret. `get_user_deposit_address` emits a `LogDepositAddress` event containing the full `deposit_msg` in plaintext: [5](#0-4) 

Any NEAR observer can harvest these events to learn the `deposit_msg` for every deposit address ever generated.

---

### Impact Explanation

If the attack succeeds (DAO does not reject in time), the victim's BTC — which was deposited on-chain but never finalized via `verify_deposit` — is sent to the attacker's BTC address via the MPC signing pipeline. The victim loses their BTC entirely. This is a direct, permanent theft of user funds, matching the Critical impact class: *Significant loss or theft of user funds*.

---

### Likelihood Explanation

**Medium.** The attacker needs:
1. The victim's `deposit_msg` — freely available from `LogDepositAddress` NEAR events.
2. The victim's BTC deposit to remain unfinalized (relayer delay, network issue, or deliberate griefing).
3. The DAO/Operator to fail to reject the malicious `RefundRequest` within `unsafe_refund_timelock_sec`.

Conditions 1 and 2 are realistic in normal bridge operation (relayer downtime, congestion). Condition 3 is the only blocker, and it is not guaranteed — the DAO is not required to monitor 24/7, and the timelock value is a configuration parameter with no enforced minimum.

---

### Recommendation

Require that the caller of `request_refund` is either:
- The `deposit_msg.recipient_id` (the intended NEAR recipient of the deposit), or
- A privileged role (DAO/Operator/RefundOperator).

Alternatively, when `deposit_msg.refund_address` is `None`, require the caller to prove ownership of the `recipient_id` account (i.e., `env::predecessor_account_id() == deposit_msg.recipient_id`) before accepting a caller-supplied `refund_address`. This mirrors the fix applied in the referenced report: checking that the account supplied in a permissionless operation matches the actual owner.

---

### Proof of Concept

1. Victim calls `get_user_deposit_address` with `deposit_msg = { recipient_id: "victim.near", refund_address: None, ... }`. The `LogDepositAddress` event is emitted, exposing the full `deposit_msg`.
2. Victim sends BTC to the derived deposit address. The relayer is delayed and does not call `verify_deposit`.
3. Attacker reads the NEAR event, reconstructs `deposit_msg`, and calls:
   ```
   request_refund(
     deposit_msg = { recipient_id: "victim.near", refund_address: None, ... },
     refund_address = "attacker_btc_address",
     tx_bytes = <victim's BTC tx>,
     vout = 0,
     proof = <valid inclusion proof>,
     gas_fee = None
   )
   ```
   No ownership check is performed; the request is stored with `refund_address = "attacker_btc_address"`.
4. Attacker waits for `unsafe_refund_timelock_sec` to elapse (DAO does not reject).
5. Attacker calls `execute_refund(utxo_storage_key)`. The MPC pipeline signs a BTC transaction paying the victim's BTC to the attacker's address.
6. Victim's BTC is permanently stolen.

    pub fn request_refund(

        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,

            deposit_msg,
            refund_address,
            tx_bytes,
            vout,

        )
    }
