Audit Report

## Title
`init_transfer` Lacks Normalization Guard, Permanently Freezing Tokens That `sign_transfer` Cannot Process - (File: `near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer` locks tokens after only verifying `fee < amount`, without checking that `normalize_amount(amount - fee) > 0`. `sign_transfer` applies this normalization check before dispatching the MPC signing call, so any transfer whose post-fee amount is below the decimal-difference factor will panic in `sign_transfer` and leave the `TransferMessage` permanently in storage with no recovery path. Affected tokens are irretrievably frozen.

## Finding Description
`sign_transfer` computes the on-chain transferable amount and enforces it is non-zero before calling the MPC signer:

```rust
// near/omni-bridge/src/lib.rs L475-485
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
``` [1](#0-0) 

`normalize_amount` performs floor division by `10^(origin_decimals − decimals)`:

```rust
// near/omni-bridge/src/lib.rs L2784-2787
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [2](#0-1) 

`init_transfer` only enforces:

```rust
// near/omni-bridge/src/lib.rs L554-557
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
``` [3](#0-2) 

Tokens are locked (or burned for bridge tokens) inside `init_transfer_internal`, which is called immediately after this guard. Once locked, the `TransferMessage` is stored. The only call sites of `remove_transfer_message` in `sign_transfer_callback` are gated on a successful MPC signature response:

```rust
// near/omni-bridge/src/lib.rs L655-658
if let Ok(signature) = call_result {
    if fee.is_zero() {
        self.remove_transfer_message(message_payload.transfer_id);
    }
``` [4](#0-3) 

Because `sign_transfer` panics at the `require!(amount_to_transfer > 0)` line — before the MPC cross-contract call is ever dispatched — `sign_transfer_callback` is never invoked, and `remove_transfer_message` is never reached. The `TransferMessage` and the locked tokens remain permanently in contract storage.

The `normalize_amount` docstring itself acknowledges partial awareness of this class of issue: [5](#0-4) 
but the SECURITY.md contains only a generic exclusion list with no project-specific carve-out for this scenario. [6](#0-5) 

## Impact Explanation
Permanent freezing of bridged funds. Any user who calls `ft_transfer_call` with `amount - fee < 10^(origin_decimals − decimals)` will have their tokens locked in the bridge contract with no mechanism to recover them. This matches the critical impact class: *permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet, Bitcoin, Zcash, or Wormhole-routed flows*.

## Likelihood Explanation
The condition is reachable by any unprivileged user through the standard `ft_transfer_call` entry point. No special role or access is required. For a 6-decimal gap (e.g., a 24-decimal NEAR token bridged to an 18-decimal EVM token), any transfer of fewer than 1,000,000 base units after fee deduction triggers the freeze. This is a realistic amount for small transfers or tokens with large decimal gaps. The condition is repeatable and requires no coordination.

## Recommendation
Add the normalization guard inside `init_transfer` (or `init_transfer_internal`) before tokens are locked:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

Alternatively, implement a user-facing cancel/refund function that removes the `TransferMessage` and returns locked tokens when no MPC signature has been produced for the transfer.

## Proof of Concept
1. Register a token with `origin_decimals = 24`, `decimals = 18` (normalization factor = 10⁶).
2. Call `ft_transfer_call` with `amount = 500_000`, `fee = 0`.
3. `init_transfer` passes its only guard: `0 < 500_000` ✓. Tokens are locked. `TransferMessage` is stored.
4. Relayer calls `sign_transfer` for this transfer.
5. `normalize_amount(500_000 - 0) = 500_000 / 1_000_000 = 0` (floor division).
6. `require!(0 > 0, BridgeError::InvalidAmountToTransfer)` panics. Transaction reverts. MPC call never dispatched.
7. `sign_transfer_callback` is never called. `remove_transfer_message` is never called.
8. The `TransferMessage` remains in storage. The 500,000 tokens are permanently frozen.

A local integration test can reproduce this by: (a) registering a token with the above decimals, (b) calling `ft_transfer_call` with the above parameters, (c) asserting the `TransferMessage` exists in storage, (d) calling `sign_transfer` and asserting it panics with `InvalidAmountToTransfer`, (e) asserting the `TransferMessage` still exists and the token balance of the bridge contract is unchanged.
