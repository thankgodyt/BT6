Audit Report

## Title
Missing `unlock_tokens_if_needed` for Destination Chain During Fast Transfer Finalization Enables Double-Minting of Bridged Tokens - (File: `near/omni-bridge/src/lib.rs`)

## Summary

In `process_fin_transfer_to_other_chain`, when a fast transfer to a non-NEAR chain (e.g., Solana) is finalized, the bridge pays the relayer `amount_without_fee` tokens via `send_tokens` (which mints for deployed tokens) but never calls `unlock_tokens_if_needed` on the destination chain to clear the identical amount locked during `fast_fin_transfer_to_other_chain`. This permanently inflates `locked_tokens[(Sol, token)]` by `amount_without_fee`, allowing a subsequent legitimate Sol→NEAR return transfer to pass the `unlock_tokens` guard and trigger a second minting of the same amount — resulting in 2× tokens minted on NEAR against 1× Ethereum escrow backing.

## Finding Description

**Step 1 — `fast_fin_transfer_to_other_chain` (lines 932–938):**

When a relayer fronts an Eth→Sol transfer, the bridge burns the relayer's deposited tokens and locks `amount_without_fee` on the destination chain:

```rust
self.burn_tokens_if_needed(fast_transfer.token_id.clone(), amount_without_fee.into());
self.lock_tokens_if_needed(
    fast_transfer.get_destination_chain(),   // Sol
    &fast_transfer.token_id,
    amount_without_fee,                      // locked on Sol
);
```

After this, `locked_tokens[(Sol, token)] = amount_without_fee`.

**Step 2 — `process_fin_transfer_to_other_chain` (lines 1997–2040):**

When the Ethereum proof arrives, the function:
- Calls `unlock_tokens_if_needed(Eth, token, amount)` — this is a **no-op** for Eth-origin tokens because `get_token_origin_chain(token) == ChainKind::Eth` satisfies the early-return condition at `token_lock.rs:115`.
- Calls `lock_tokens_if_needed(Sol, token, fee)` — locks only the fee.
- In the fast-transfer branch: calls `send_tokens(token, relayer, amount_without_fee)` which, for deployed tokens, calls `mint` (lines 2094–2101), paying the relayer.
- Calls `mark_fast_transfer_as_finalised`.
- **Never calls `unlock_tokens_if_needed(Sol, token, amount_without_fee)`.**

After Step 2, `locked_tokens[(Sol, token)]` = `amount_without_fee` (from Step 1) + `fee` (from Step 2's lock). After `send_fee_internal` unlocks the fee at line 2684, the residual is exactly `amount_without_fee` — permanently stranded.

**Step 3 — `process_fin_transfer_to_near` (lines 1881–1885):**

The user on Sol legitimately holds `amount_without_fee` tokens (received from the relayer). They initiate a Sol→NEAR return transfer. The bridge calls:

```rust
let lock_actions = vec![self.unlock_tokens_if_needed(
    transfer_message.get_origin_chain(),   // Sol
    &token,
    transfer_message.amount.0,             // amount_without_fee
)];
```

For an Eth-origin token, `Sol != Eth`, so `unlock_tokens_if_needed` is **not** a no-op. Since `locked_tokens[(Sol, token)] == amount_without_fee`, the `available >= amount` check at `token_lock.rs:81–84` passes. The bridge then calls `send_tokens` again (line 1957), which mints `amount_without_fee` tokens for the user.

**Net result:** The bridge has minted `2 × amount_without_fee` NEAR-side tokens (once for the relayer in Step 2, once for the user in Step 3) while the Ethereum escrow holds only `1 × amount_without_fee` in backing.

**Why existing checks fail:**
- `add_fin_transfer` (line 1985) prevents replay of the *same* transfer ID, but the Sol→NEAR transfer carries a distinct transfer ID — no collision.
- `unlock_tokens` enforces `available >= amount` (token_lock.rs:81), but the inflated `locked_tokens[(Sol, token)]` makes this check pass when it should not.
- `mark_fast_transfer_as_finalised` (line 2040) only prevents re-finalization of the *same* fast transfer; it does not affect the Sol→NEAR path.

## Impact Explanation

This is a **Critical** impact matching "Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds." For every Eth→Sol fast transfer that is finalized, an attacker (or any user who received tokens on Sol from the relayer) can bridge back to NEAR and receive a second minting of `amount_without_fee` deployed tokens. The Ethereum escrow is never double-debited, so the bridge's total NEAR-side supply grows unboundedly relative to its cross-chain backing, enabling theft of protocol reserves or inflation of the bridged token supply.

## Likelihood Explanation

The exploit requires only standard, unprivileged bridge operations: (1) any Eth→Sol transfer that a relayer chooses to fast-front (a normal, incentivized relayer action), (2) the Ethereum proof arriving and being submitted (normal bridge finalization), and (3) the Sol-side token holder bridging back to NEAR (a normal user action). No special roles, leaked keys, or external compromises are needed. The sequence is repeatable for every fast-fronted Eth→Sol transfer, making it systematically exploitable at scale.

## Recommendation

In `process_fin_transfer_to_other_chain`, inside the fast-transfer branch (after confirming `status.finalised == false`), add an explicit unlock of the destination-chain lock that was created in `fast_fin_transfer_to_other_chain`:

```rust
if let Some(relayer) = recipient {
    // Unlock the amount_without_fee that was locked on the destination chain
    // during fast_fin_transfer_to_other_chain
    self.unlock_tokens_if_needed(
        transfer_message.get_destination_chain(),
        &token,
        transfer_message
            .amount_without_fee()
            .near_expect(BridgeError::InvalidFee),
    );
    self.send_tokens(...).detach();
    self.mark_fast_transfer_as_finalised(&fast_transfer.id());
}
```

This mirrors the symmetric unlock already present in `process_fin_transfer_to_near` for the NEAR-destination fast-transfer case and restores correct `locked_tokens` accounting.

## Proof of Concept

**Minimal call sequence (private testnet):**

1. Deploy the NEAR omni-bridge contract and a deployed (mintable) Eth-origin token.
2. Register a relayer. Relayer deposits `amount_without_fee` tokens.
3. Call `fast_fin_transfer` with `recipient = Sol::<address>` — triggers `fast_fin_transfer_to_other_chain`. Assert `locked_tokens[(Sol, token)] == amount_without_fee`.
4. Submit an Ethereum proof for the same transfer (Eth→Sol). This triggers `process_fin_transfer_to_other_chain` in the fast-transfer branch. Assert relayer balance increased by `amount_without_fee`. Assert `locked_tokens[(Sol, token)]` is still `amount_without_fee` (not zero).
5. Construct a Sol→NEAR `fin_transfer` proof for `amount_without_fee` tokens. Submit it. Assert the call succeeds (it should not panic on `unlock_tokens`). Assert the user's NEAR token balance increased by `amount_without_fee`.
6. **Invariant check:** Total NEAR-side minted supply for the token should equal the Ethereum escrow balance. After step 5 it will be `2 × amount_without_fee` vs. `1 × amount_without_fee` — proving the double-mint.
