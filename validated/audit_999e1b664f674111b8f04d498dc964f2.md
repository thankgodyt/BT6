### Title
Unnecessary `#[trusted_relayer]` restriction on `claim_fee` permanently locks fee tokens when fee recipient is no longer an active relayer — (File: `near/omni-bridge/src/lib.rs`)

---

### Summary

`claim_fee` is gated by `#[trusted_relayer]`, but its callback already enforces `fee_recipient == predecessor_account_id` from the verified proof. The trusted-relayer guard is therefore redundant and harmful: any fee recipient who is no longer an active trusted relayer (resigned or DAO-revoked) is permanently blocked from claiming legitimately earned fees, causing those tokens to be frozen inside the bridge contract.

---

### Finding Description

`claim_fee` carries two independent access-control layers:

**Layer 1 — `#[trusted_relayer]` macro (outer gate):** [1](#0-0) 

This macro (configured at the `impl` block level) calls `is_trusted_relayer(predecessor)` and panics if the caller is not an active staker in the relayer registry. [2](#0-1) 

**Layer 2 — `fee_recipient == predecessor_account_id` (inner gate, inside callback):** [3](#0-2) 

The `fee_recipient` is extracted from the cryptographically verified proof submitted to the prover contract. It is the account that was encoded into the MPC-signed `TransferMessagePayload` at `sign_transfer` time: [4](#0-3) 

Because the proof is verified on-chain and the `fee_recipient` field is bound to the MPC signature, Layer 2 already provides complete, unforgeable authorization. Layer 1 adds nothing to security — it only restricts *who* may exercise a right they already legitimately hold.

---

### Impact Explanation

**Scenario — relayer resigns after signing but before claiming:**

1. Trusted relayer R calls `sign_transfer(transfer_id, fee_recipient = Some(R), fee)`. The MPC signs a payload that encodes `fee_recipient = R`.
2. The transfer is finalized on the foreign chain; the `FinTransfer` event records `fee_recipient = R`.
3. R calls `resign_trusted_relayer` (or the DAO calls `reject_relayer_application` on R). R is removed from the active relayer set.
4. R submits a valid proof to `claim_fee`. The `#[trusted_relayer]` macro fires before any proof verification and panics — the call is rejected.
5. The fee tokens remain locked inside the bridge's token balance. The corresponding `TransferMessage` stays in `pending_transfers` indefinitely. [5](#0-4) 

For **fast transfers to other chains**, the relayer pre-pays the recipient from their own balance and expects to recover that amount (plus fee) via `claim_fee` after the origin-chain proof arrives. If `claim_fee` is blocked, the relayer's pre-paid tokens are also frozen. [6](#0-5) 

The only recovery path is a DAO call to `transfer_token_as_dao`, which requires admin intervention, does not clean up `pending_transfers`, and is not guaranteed to be executed. [7](#0-6) 

**Impact class:** Permanent (absent DAO intervention) freezing of bridged fee tokens; loss of pre-paid fast-transfer funds for the relayer.

---

### Likelihood Explanation

Relayer churn is a normal operational event: relayers resign voluntarily, or the DAO revokes them for policy reasons. The window between `sign_transfer` (which records `fee_recipient`) and `claim_fee` (which requires a foreign-chain proof) spans at minimum the finality time of the source chain (minutes to hours for EVM L2s via Wormhole, longer for Ethereum L1). Any relayer who resigns or is revoked during this window loses their fee claim. This is a realistic, non-exotic scenario.

---

### Recommendation

Remove `#[trusted_relayer]` from `claim_fee`. The proof verification and the `fee_recipient == predecessor_account_id` check in `claim_fee_callback` already provide complete, cryptographically sound authorization. Any account that can produce a valid proof naming itself as `fee_recipient` is the legitimate claimant — no additional relayer-status check is needed or beneficial.

// After

### Proof of Concept

```
1. Trusted relayer R calls sign_transfer(transfer_id=T, fee_recipient=Some(R), fee=F).
   → MPC signs payload; fee_recipient=R is embedded in the signature.

2. Foreign chain finalizes the transfer; emits FinTransfer(transfer_id=T, fee_recipient=R, amount=A).

3. R calls resign_trusted_relayer().
   → is_trusted_relayer(R) now returns false.

4. R calls claim_fee(ClaimFeeArgs { chain_kind, prover_args: proof_of_step_2 }).
   → #[trusted_relayer] macro checks is_trusted_relayer(R) → false → PANIC.
   → Proof is never verified; claim_fee_callback is never reached.

5. Fee tokens (F) remain in the bridge's token balance.
   pending_transfers[T] is never removed.
   R cannot recover F by any permissionless means.
``` [1](#0-0) [8](#0-7)
