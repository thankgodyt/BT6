### Title
`validatePerasCert` Stub Always Accepts Any Peer-Supplied Certificate, Enabling Unauthorized Chain-Selection Boost - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` function is a stub that unconditionally returns `Right` for every certificate it receives, performing no signature, quorum, round-validity, or any other check. This is the only instance in the codebase and is wired directly into the live Peras certificate diffusion inbound handler. An unprivileged peer can therefore send a crafted `PerasCert` naming any block as the boosted target; the certificate will pass "validation," be stored in the `PerasCertDB`, and trigger chain selection for the attacker-chosen block with the full Peras boost weight applied.

---

### Finding Description

The `BlockSupportsPeras` typeclass declares `validatePerasCert` as the gate that must be passed before a received certificate is treated as `ValidatedPerasCert` and acted upon. The sole production instance is:

```haskell

-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }

The inbound cert-diffusion writer, used in production, passes this stub directly as the `validateCert` argument to `processCerts`:

```haskell

`processCerts` applies `validateCert` to every new certificate and, because the stub never returns `Left`, every certificate is unconditionally forwarded to `addCert`:

Once a certificate is stored, `chainSelSync` in `ChainSel.hs` processes it: it looks up the boosted block in the `VolatileDB` and calls `chainSelectionForBlock` with the full Peras boost weight, potentially switching the node's selection to the attacker-chosen fork:

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  ...
  lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment

### Impact Explanation

An unprivileged peer can craft a `PerasCert` naming any block hash as `pcCertBoostedBlock`. Because `validatePerasCert` performs no checks whatsoever (no aggregate BLS signature verification, no quorum check, no round-number validity check, no committee membership check), the certificate is accepted as `ValidatedPerasCert` and stored. The stored certificate contributes `perasWeight params` to the chain-selection weight of the boosted block. If the attacker targets a block on a minority fork that is already close to the honest chain's weight, the artificial boost can tip chain selection in favour of the fork, causing the honest node to roll back and adopt a non-canonical chain. This directly matches the **High** impact category: an unprivileged peer can make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.

---

### Likelihood Explanation

The Peras certificate diffusion miniprotocol is active in the production node-to-node handler. Any peer that can establish a connection can send crafted certificates. No special privileges, keys, or stake are required. The attack requires only that the attacker's target block is present in the victim node's `VolatileDB` (i.e., has been received but not yet finalized), which is a normal condition during any active fork.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real one that verifies:
1. The aggregate BLS signature over the election identifier and boosted block hash.
2. That the signing committee members form a valid quorum (sufficient stake).
3. That the round number is within the expected range relative to the current slot.
4. That each voter's eligibility proof (persistent membership or VRF proof) is valid.

Until a real implementation is available, the inbound cert-diffusion handler should either be disabled or should reject all inbound certificates rather than accepting them unconditionally.

---

### Proof of Concept

1. Connect to a target node via the `PerasCertDiffusion` miniprotocol.
2. Construct a `PerasCert` with:
   - `pcCertRound` = any round number not yet seen by the target node.
   - `pcCertBoostedBlock` = the `Point` of a block on a minority fork that is present in the target node's `VolatileDB`.
3. Send the certificate. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams })` unconditionally.
4. The certificate is forwarded to `ChainDB.addPerasCertAsync`.
5. `chainSelSync` retrieves the boosted block from the `VolatileDB` and calls `chainSelectionForBlock` for it.
6. Chain selection now evaluates the fork with the additional Peras boost weight. If the fork's total weight (natural + boost) exceeds the current chain's weight, the node switches to the fork, rolling back honest blocks. [1](#0-0) [7](#0-6) [8](#0-7)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
