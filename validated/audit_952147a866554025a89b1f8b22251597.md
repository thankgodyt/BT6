Audit Report

## Title
Native ETH Delivery Revert in `finTransfer` Permanently Freezes Bridged Funds — (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

## Summary
In `OmniBridge.finTransfer`, the destination nonce is marked consumed at L287 before ETH delivery is attempted at L317–322. If the recipient contract cannot accept ETH, `revert FailedToSendEther()` rolls back the entire transaction including the nonce marking, leaving the nonce unconsumed. Because the NEAR side has already burned or locked the user's tokens with no user-callable cancel path, the funds are permanently frozen.

## Finding Description
`finTransfer` sets `completedTransfers[payload.destinationNonce] = true` at L287 before performing any token delivery. For native ETH transfers (`payload.tokenAddress == address(0)`), it then executes a low-level call at L319–321 and reverts the entire transaction with `FailedToSendEther()` at L322 if the call fails. Because Solidity reverts are atomic, the nonce marking at L287 is also rolled back. The nonce remains unconsumed, so the relayer can retry — but every retry produces the same revert for a recipient that structurally cannot accept ETH (no `receive`/`fallback`, or one that explicitly reverts).

On the NEAR side, `init_transfer_internal` calls `burn_tokens_if_needed` and `lock_tokens_if_needed` at L1851–1857 of `near/omni-bridge/src/lib.rs` before emitting the `InitTransferEvent`. The `remove_transfer_message` function is only reachable through internal callbacks, not by the original sender. There is no user-callable cancel or refund entry point for a pending transfer whose EVM finalization is permanently blocked.

## Impact Explanation
This is a **Critical** impact matching the allowed scope: **permanent freezing of bridged funds**. The user's NEAR-side tokens (burned or locked at transfer initiation) can never be recovered. The EVM `finTransfer` will always revert for a recipient that rejects ETH, the relayer's ETH is returned on each revert, but the user's NEAR tokens remain permanently locked or burned with no on-chain recovery mechanism.

## Likelihood Explanation
Low-to-medium. Any unprivileged bridge user can trigger this by specifying as the EVM recipient a contract that cannot receive ETH — for example, a Gnosis Safe deployment without a `receive` function, a token contract address, or any contract that was upgraded and had its `receive` function removed. No privileged access is required; the trigger is a normal `ft_transfer_call` on NEAR with a bad EVM recipient address.

## Recommendation
Replace the hard revert on ETH delivery failure with a pull-payment (escrow) pattern so the nonce is consumed and ETH is held safely:

```solidity
if (payload.tokenAddress == address(0)) {
    (bool success, ) = payload.recipient.call{value: payload.amount}("");
    if (!success) {
        pendingWithdrawals[payload.recipient] += payload.amount;
        emit EthDeliveryFailed(payload.recipient, payload.amount, payload.destinationNonce);
    }
}
```

This ensures the nonce is consumed (preventing replay), ETH is escrowed in the contract, and the recipient or an admin-assisted path can later claim it. Alternatively, add a NEAR-side user-callable cancel mechanism that allows token recovery when EVM finalization is provably impossible.

## Proof of Concept
1. Deploy a contract `C` on EVM with no `receive` or `fallback` function.
2. User on NEAR calls `ft_transfer_call` targeting the bridge, specifying `C` as the EVM recipient and native ETH as the token. NEAR tokens are burned/locked; `TransferMessage` is stored.
3. Relayer calls `finTransfer` on EVM with `msg.value = payload.amount`.
4. L287: `completedTransfers[nonce] = true`.
5. L319–321: `C.call{value: amount}("")` returns `success = false`.
6. L322: `revert FailedToSendEther()` — entire transaction rolls back including L287.
7. Relayer retries; every attempt reverts identically. Relayer's ETH is returned each time.
8. User's NEAR tokens remain permanently locked/burned. No user-callable NEAR-side cancel exists. Funds are permanently frozen.
