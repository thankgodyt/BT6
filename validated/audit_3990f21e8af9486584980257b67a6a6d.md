Audit Report

## Title
`signer_account_id` Used as Storage Payer in `ft_on_transfer` Enables Permanent Locking of Victim's NEAR Storage Balance via Malicious Token - (File: `near/omni-bridge/src/lib.rs`)

## Summary

`ft_on_transfer` uses `env::signer_account_id()` — NEAR's `tx.origin` analog — as the storage payer identity when recording a pending transfer. A malicious NEP-141 token can call `ft_on_transfer` on the bridge while a victim is the transaction signer, causing the bridge to deduct the victim's pre-deposited storage balance to fund a bogus transfer record. Because no `cancel_transfer` path exists and the bogus transfer (using an unregistered token) can never be completed or removed, the victim's NEAR tokens are permanently locked in the bridge.

## Finding Description

In `near/omni-bridge/src/lib.rs` at line 260, `ft_on_transfer` explicitly substitutes `env::signer_account_id()` for `sender_id` as the storage payer:

```rust
// We can't trust sender_id to pay for storage as it can be spoofed.
let signer_id = env::signer_account_id();
```

`signer_id` is then passed to `init_transfer` as the storage payer. Inside `init_transfer` (lines 566–583), the bridge checks whether `signer_id` has sufficient storage balance and, if so, deducts it and calls `init_transfer_internal`:

```rust
|| (self.has_storage_balance(&signer_id, ...) && ...)
{
    PromiseOrPromiseIndexOrValue::Value(
        self.init_transfer_internal(transfer_message, signer_id),
    )
}
```

Inside `init_transfer_internal` (lines 1834–1848), `try_update_storage_balance` deducts from `signer_id`'s `available` balance:

```rust
let required_storage_balance = self
    .add_transfer_message(transfer_message.clone(), storage_owner.clone())
    .saturating_add(...);
if self.try_update_storage_balance(storage_owner, required_storage_balance, ...).is_err() {
    self.remove_transfer_message_without_refund(...);
    return transfer_message.amount;
}
```

`lock_tokens_if_needed` in `near/omni-bridge/src/token_lock.rs` (lines 96–107) is a no-op for unregistered tokens — it returns `LockAction::Unchanged` when the token is absent from `locked_tokens`. So a transfer with `token = evil.near` (unregistered) passes through `init_transfer_internal` successfully, stores the pending transfer, deducts alice's storage balance, and emits `InitTransferEvent`.

The stored transfer can never be removed: `remove_transfer_message` is only called from `sign_transfer_callback` (after MPC signing), `claim_fee_callback` (after proof verification), and `submit_transfer_to_utxo_chain_connector` (UTXO-only). All three paths require the token to be registered in the bridge. There is no `cancel_transfer` function. `storage_unregister(force: true)` only refunds `required_balance_for_account() + storage.available` — the portion locked for the pending transfer is not returned.

## Impact Explanation

The victim's NEAR storage balance — real NEAR tokens deposited via `storage_deposit` — is permanently locked in the bridge contract. The locked portion (the storage cost of the bogus pending transfer) cannot be recovered via `storage_withdraw` (only `available` balance is withdrawable) or `storage_unregister(force: true)` (only refunds `required_balance_for_account() + available`). Repeated attacks drain the victim's entire deposited balance. This is a concrete balance manipulation: real NEAR tokens are mis-accounted from the victim's storage balance to fund attacker-crafted state, with no recovery path. This matches the critical impact class: **Balance manipulation / escrow mis-accounting that changes user balances**.

## Likelihood Explanation

The attack requires only that the victim (1) has a storage balance registered in the bridge (required for any bridge user who has ever initiated a transfer) and (2) calls any function on a malicious NEP-141 token that makes a cross-contract call to `omni-bridge::ft_on_transfer`. This is a realistic scenario: users regularly interact with unknown tokens via airdrops, DEX swaps, or yield protocols. The malicious token does not need to go through `ft_transfer_call` — it can call `ft_on_transfer` directly as a cross-contract call from any function the victim invokes. The attack is permissionless, requires no admin access, and is repeatable until the victim's balance is exhausted.

## Recommendation

Replace `env::signer_account_id()` with a properly authenticated identity for storage payment:

1. **Require `sender_id == predecessor_account_id()`**: Only allow `ft_on_transfer` to proceed when the token contract is the immediate predecessor and `sender_id` matches it, ensuring the storage payer is the actual user who initiated `ft_transfer_call`.
2. **Require an explicit attached deposit**: Instead of drawing from a pre-registered balance attributed to `signer_account_id()`, require `env::attached_deposit()` to cover storage costs, passed through `ft_transfer_call`.
3. **Remove all uses of `signer_account_id()` for authorization or balance deduction**, consistent with NEAR security best practices that treat `signer_account_id()` as untrusted in cross-contract call contexts.

## Proof of Concept

1. `alice.near` has 1 NEAR of storage balance in the omni-bridge (registered via `storage_deposit`).
2. Attacker deploys `evil.near`, a NEP-141 token. Its `ft_transfer_call` (or any callable function) makes a cross-contract call to `omni-bridge.near::ft_on_transfer("attacker.near", 1, <valid InitTransferMsg with EVM recipient>)`.
3. Attacker airdrops `evil.near` tokens to `alice.near`.
4. `alice.near` calls `evil.near::ft_transfer_call(omni-bridge.near, 1, "")` to dispose of the airdrop.
5. `evil.near` calls `omni-bridge.near::ft_on_transfer("attacker.near", 1, <crafted msg>)`.
6. Inside `ft_on_transfer`: `token_id = evil.near`, `sender_id = "attacker.near"`, `signer_id = alice.near`.
7. Bridge checks `alice.near`'s storage balance — sufficient — and deducts it to record the bogus transfer (`token=evil.near`, `sender=attacker.near`, `owner=alice.near`).
8. `lock_tokens_if_needed` is a no-op (evil.near not registered); `InitTransferEvent` is emitted.
9. The pending transfer can never be signed (`get_token_address` fails for evil.near), claimed, or cancelled. Alice's NEAR tokens are permanently locked.
10. Repeat from step 4 (or via additional malicious calls) until alice's entire storage balance is exhausted.

**Local test plan**: Deploy the bridge on a NEAR sandbox, register alice with a storage deposit, deploy a mock NEP-141 whose `ft_transfer_call` directly calls `ft_on_transfer` on the bridge with a crafted `InitTransferMsg`, invoke it as alice, and assert that alice's `storage_balance_of` `available` field is reduced while no recovery path (sign, claim, cancel) succeeds for the resulting pending transfer.
