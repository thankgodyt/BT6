### Title
`migrate_to_new_token_mint` Uses `ft_total_supply()` That Includes Bridge-Held In-Flight Tokens, Allowing Any nBTC Holder to Permanently Block Token Migration - (File: contracts/satoshi-bridge/src/nbtc/migration.rs)

### Summary

`migrate_to_new_token_mint` enforces a strict equality check `sum == total_supply` where `total_supply` is `ft_total_supply()` of the old nBTC token. However, `ft_total_supply()` always includes tokens held by the bridge contract itself — both accumulated protocol fees and tokens transferred to the bridge during pending withdrawals. Any unprivileged nBTC holder can initiate a withdrawal (transferring tokens to the bridge) to ensure the bridge always holds tokens, causing migration to fail whenever the bridge account is omitted from the `accounts` list. Because protocol fees accumulate in the bridge's balance on every deposit and withdrawal, the bridge's balance is non-zero in any live system, making migration structurally impossible without including the bridge account — a requirement that is neither enforced nor documented in the production code.

### Finding Description

The `migrate_to_new_token` entry point calls `internal_migrate_to_new_token`, which queries `ft_total_supply()` and `ft_balance_of(account)` for each account in the caller-supplied list, then in the callback enforces:

```rust
require!(
    sum == total_supply,
    "Sum of account balances does not match total supply"
);
``` [1](#0-0) 

The `total_supply` value comes from `ft_total_supply()` on the old nBTC token: [2](#0-1) 

`ft_total_supply()` on the nBTC contract returns the full circulating supply including the bridge contract's own balance: [3](#0-2) 

The bridge contract accumulates nBTC in its own account through two mechanisms:

**1. Protocol fees** — every `verify_deposit` and `verify_withdraw` call mints or retains protocol fees directly into the bridge's balance. Tests confirm this is always non-zero in a live system: [4](#0-3) 

**2. Pending withdrawals** — when a user initiates a withdrawal, tokens are transferred to the bridge via `ft_transfer_call` and remain there until `verify_withdraw` is called and `burn()` executes. During this window the bridge holds the full withdrawal amount: [5](#0-4) 

The withdrawal flow is documented as intentional: tokens are transferred to the bridge first, burned only after BTC-side verification. This means the bridge's balance is part of `ft_total_supply()` but is not a user-owned balance that would appear in any user's `ft_balance_of` result.

An unprivileged nBTC holder can exploit this by calling `nbtc.ft_transfer_call(bridge, amount, WithdrawMsg)` to transfer tokens to the bridge, ensuring the bridge always holds tokens. If the migration operator's `accounts` list does not include the bridge's own account ID, `sum < total_supply` and the migration panics. The attacker can repeat this on every migration retry, persistently blocking the upgrade.

Even without an active attacker, protocol fees alone guarantee `ft_balance_of(bridge) > 0` in any live deployment, so migration will structurally always fail unless the bridge account is explicitly included — a requirement absent from the production code.

### Impact Explanation

Token migration is the bridge's upgrade path for the nBTC token contract. Blocking migration prevents the protocol from deploying critical fixes or improvements to the token layer. This is a stuck bridge state requiring operator intervention — the operator must discover the undocumented requirement to include the bridge account, and even then an attacker can continuously initiate withdrawals to shift the bridge's balance between migration attempts (though since the balance is queried at call time, including the bridge account does resolve the issue once the operator is aware).

The impact matches: **Medium — stuck bridge state requiring operator intervention**.

### Likelihood Explanation

High. Protocol fees accumulate in the bridge's balance on every deposit and withdrawal. In any live deployment the bridge's balance is non-zero, so migration will fail on the first attempt without the bridge account. Any nBTC holder can amplify this by initiating a withdrawal. No special privileges are required.

### Recommendation

Two complementary fixes:

1. **Exclude the bridge's own balance from the completeness check.** Query `ft_balance_of(bridge_id)` separately and subtract it from `total_supply` before comparing:

```rust
let bridge_balance = Self::parse_ft_result(bridge_balance_index);
require!(
    sum == total_supply - bridge_balance,
    "Sum of account balances does not match total supply"
);
```

2. **Alternatively, always inject the bridge account into the accounts list** inside `internal_migrate_to_new_token` so the caller cannot accidentally omit it, and mint the bridge's balance to the bridge on the new token (which is correct, since pending withdrawals will burn from the new token's bridge balance after migration).

### Proof of Concept

1. Alice deposits BTC → receives 500,000 nBTC. Protocol fee of 45,000 nBTC is minted to the bridge.
2. Alice initiates a withdrawal of 200,000 nBTC → tokens transferred to bridge. Bridge now holds `45,000 + 200,000 = 245,000` nBTC. `ft_total_supply() = 500,000`.
3. MigrationOperator calls `migrate_to_new_token(new_token, [alice])`.
4. Callback: `sum = ft_balance_of(alice) = 255,000`. `total_supply = 500,000`. `255,000 != 500,000` → panic: `"Sum of account balances does not match total supply"`.
5. Migration fails. Attacker repeats step 2 on every retry to keep the bridge's balance non-zero and unpredictable. [6](#0-5) [7](#0-6)
