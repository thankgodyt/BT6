### Title
Irreversible `sync_chain_signatures_root_public_key` Prevents MPC Key Rotation Recovery — (File: `contracts/satoshi-bridge/src/api/management.rs`)

---

### Summary
`sync_chain_signatures_root_public_key` enforces a strict one-way gate: once the MPC root public key is stored, the function permanently panics on any subsequent call. No alternative update path exists in the codebase. If NEAR's Chain Signatures MPC rotates its root public key — a normal operational event — the bridge's stored key becomes permanently stale, breaking deposit-address derivation, withdrawal signing, and the change-address, with no operator-accessible remedy short of a full contract upgrade.

---

### Finding Description

`sync_chain_signatures_root_public_key` in `management.rs` guards itself with:

```rust
require!(
    self.internal_config()
        .chain_signatures_root_public_key
        .is_none(),
    "Already sync"
);
``` [1](#0-0) 

Once the callback `sync_root_public_key_callback` writes the key and the derived `change_address` into config, both fields are frozen:

```rust
self.internal_mut_config().chain_signatures_root_public_key = Some(root_public_key);
...
self.internal_mut_config().change_address = Some(change_address);
``` [2](#0-1) 

Neither `chain_signatures_root_public_key` nor `change_address` appears in `ConfigUpdate`, the only general-purpose admin update path: [3](#0-2) 

`ConfigUpdate.apply` iterates only the fields it knows about via `set_if_some!` macros, and neither frozen field is present: [4](#0-3) 

There is no separate `update_chain_signatures_root_public_key` or `force_sync` function anywhere in the management API.

---

### Impact Explanation

`chain_signatures_root_public_key` is the cryptographic anchor for every deposit-address derivation and every withdrawal signing path in the bridge. If NEAR's Chain Signatures MPC rotates its root key:

1. **Deposit addresses** derived from the stale root key no longer correspond to keys the MPC can sign for. BTC sent to newly-derived addresses is permanently unspendable by the bridge.
2. **Withdrawal signing** (`sign_btc_transaction`) requests signatures over paths derived from the stale root key; the MPC will produce signatures for a different key, causing verification failures and permanently locking user funds already transferred into the bridge.
3. **`change_address`** — set once from the stale root key — directs all UTXO change outputs to an address the bridge can no longer control, leaking protocol-owned BTC.

The bridge enters a permanently broken state. The DAO cannot call `sync_chain_signatures_root_public_key` again (panics "Already sync"), cannot patch the value via `update_config` (field absent), and has no other on-chain remedy. Recovery requires a full contract upgrade and state migration.

**Impact:** Medium — stuck bridge state requiring operator intervention (contract upgrade), with secondary risk of permanent loss of user and protocol funds if the stale key is used to derive new deposit addresses before the issue is detected.

---

### Likelihood Explanation

NEAR's Chain Signatures MPC is an active, evolving system. Key rotation is a documented operational possibility (e.g., for security upgrades or validator set changes). The bridge has already been through multiple state migrations (`V0`–`V5`), demonstrating that operational changes requiring contract-level responses do occur. The one-way gate makes the bridge fragile to any such rotation.

---

### Recommendation

Remove the `is_none()` guard from `sync_chain_signatures_root_public_key` so it can be called again after a key rotation, or add a dedicated `update_chain_signatures_root_public_key` DAO function that unconditionally overwrites the stored key and recomputes `change_address`. Additionally, add both `chain_signatures_root_public_key` and `change_address` as optional fields in `ConfigUpdate` so they can be patched via the standard `update_config` path.

---

### Proof of Concept

1. DAO calls `sync_chain_signatures_root_public_key()`. `sync_root_public_key_callback` stores `root_public_key = K1` and `change_address = addr(K1)`.
2. NEAR's Chain Signatures MPC rotates its root key to `K2` (normal operational event).
3. DAO calls `sync_chain_signatures_root_public_key()` again to update the bridge.
4. `require!(... .is_none(), "Already sync")` panics — call reverts.
5. Bridge continues deriving deposit addresses and signing paths from stale `K1`.
6. MPC signs with `K2`; all signatures are invalid against `K1`-derived keys.
7. All pending and future withdrawals fail; change outputs go to `addr(K1)`, which the MPC (now using `K2`) cannot spend.
8. No on-chain DAO action can fix this; a full contract upgrade is the only remedy.
