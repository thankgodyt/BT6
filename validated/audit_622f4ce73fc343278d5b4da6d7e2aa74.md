### Title
u128 Overflow Panic in `check_deposit_msg` Permanently Locks Deposit UTXO — (`contracts/satoshi-bridge/src/deposit_msg.rs`)

### Summary

`check_deposit_msg` accumulates `PostAction` amounts into a bare `u128` with `+=`. The workspace release profile explicitly enables `overflow-checks = true`. A depositor can encode a `DepositMsg` with two `PostAction` entries each carrying `amount = u128::MAX/2 + 1` into a BTC OP_RETURN output. When the trusted relayer calls `verify_deposit_v2` with that message, the addition overflows, the WASM runtime panics, the transaction reverts, and the deposit UTXO is permanently unprocessable.

### Finding Description

`check_deposit_msg` iterates over at most `MAX_POST_ACTIONS_NUM = 2` post-actions and accumulates their amounts:

```rust
let mut total_amount = 0u128;          // line 83
for (index, post_action) in post_actions.iter().enumerate() {
    total_amount += post_action.amount.0;  // line 85 — unchecked addition
    ...
}
if total_amount > actual_mintable_amount { ... }  // line 181
``` [1](#0-0) 

The workspace release profile is:

```toml
[profile.release]
overflow-checks = true   # line 27
panic = "abort"
``` [2](#0-1) 

With `overflow-checks = true`, any `u128` addition that exceeds `u128::MAX` causes an immediate panic (trap) in the WASM runtime. With two actions each carrying `amount = (u128::MAX / 2) + 1`:

- Iteration 1: `total_amount = u128::MAX/2 + 1` — fine.
- Iteration 2: `total_amount += u128::MAX/2 + 1` → `u128::MAX + 2` → **overflow panic**.

The guard at line 181 (`total_amount > actual_mintable_amount`) is never reached. [3](#0-2) 

### Impact Explanation

`verify_deposit_v2` is gated by `#[trusted_relayer]`, so the depositor cannot call it directly. [4](#0-3) 

However, the depositor controls the `DepositMsg` that is embedded in the BTC transaction's OP_RETURN output. The relayer reads that OP_RETURN verbatim and passes it to `verify_deposit_v2`. A depositor who encodes the overflow `DepositMsg` in their OP_RETURN causes the relayer's call to panic deterministically on every retry attempt, because the deposit address is derived from the `DepositMsg` hash — the relayer must always use the same `DepositMsg` to verify that UTXO. The UTXO is permanently unprocessable (stuck state). The relayer also loses gas on each attempt.

`check_deposit_msg` is called from `internal_verify_deposit` before the light-client proof callback is scheduled: [5](#0-4) 

The panic reverts the entire transaction, leaving no on-chain record that the UTXO was attempted, so the relayer will retry indefinitely and always panic.

### Likelihood Explanation

Any depositor can craft this `DepositMsg` at zero cost (no BTC is required to be large; the amounts are in the message, not the UTXO value). The `overflow-checks = true` flag is unconditionally set in the shared workspace profile and applies to every crate in the workspace including `satoshi-bridge`. The path from depositor-controlled OP_RETURN → relayer call → `check_deposit_msg` panic is direct and deterministic.

### Recommendation

Replace the bare `+=` with a checked or saturating addition and return `None` (invalid) on overflow:

```rust
total_amount = total_amount
    .checked_add(post_action.amount.0)
    .unwrap_or(u128::MAX + 1); // saturate; the > actual_mintable_amount check will reject it
```

Or more cleanly:

```rust
total_amount = match total_amount.checked_add(post_action.amount.0) {
    Some(v) => v,
    None => {
        Event::InvalidPostAction { index: Some(index), err_msg: "amount overflow".into() }.emit();
        return None;
    }
};
``` [6](#0-5)
