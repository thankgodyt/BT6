Audit Report

## Title
Missing `token::authority` Constraint on `from` Account Allows Delegate to Drain Victim Tokens — (`solana/programs/bridge_token_factory/src/instructions/user/init_transfer.rs`)

## Summary

The `from` account in the `InitTransfer` account struct is constrained only by `token::mint` and `token::token_program`, with no `token::authority = user` check. Because SPL Token's `transfer_checked` and `burn` accept either the token account owner **or** an approved delegate as the authority, any attacker who holds a valid SPL delegation over a victim's token account can supply `from = victim_ata` and `user = attacker` (signer), causing the bridge to lock or burn the victim's tokens and post a Wormhole message crediting an attacker-controlled NEAR account.

## Finding Description

In `solana/programs/bridge_token_factory/src/instructions/user/init_transfer.rs`, the `from` account is declared at lines 34–39 as:

```rust
#[account(
    mut,
    token::mint = mint,
    token::token_program = token_program,
)]
pub from: Box<InterfaceAccount<'info, TokenAccount>>,
```

There is no `token::authority = user` constraint. Anchor's `token::authority` constraint would enforce `from.owner == user.key()` at account-validation time, before `process()` is called. Without it, the only runtime enforcement is the SPL Token CPI itself.

In `process()` (lines 90–102), the native-token path issues:

```rust
TransferChecked {
    from: self.from.to_account_info(),
    to: vault.to_account_info(),
    authority: self.user.to_account_info(),  // attacker is the signer
    mint: self.mint.to_account_info(),
}
```

And the bridged-token path (lines 110–120) issues:

```rust
Burn {
    mint: self.mint.to_account_info(),
    from: self.from.to_account_info(),
    authority: self.user.to_account_info(),  // attacker is the signer
}
```

SPL Token's `transfer_checked` and `burn` instructions accept **either** the token account owner **or** an approved delegate as the `authority`. If the victim has previously called `spl_token::approve` granting the attacker (or a program the attacker controls) delegate authority over their ATA, both CPIs succeed with `from = victim_ata` and `authority = attacker`.

After the tokens are moved, the Wormhole message is posted at lines 123–127:

```rust
self.common.post_message(payload.serialize_for_near((
    self.common.sequence.sequence,
    self.user.key(),   // attacker's pubkey becomes the "sender"
    self.mint.key(),
))?)?;
```

The `recipient` field in `InitTransferPayload` is fully attacker-controlled (no validation per `solana/SECURITY.md` known issues), so the NEAR-side finalization releases the tokens to an attacker-controlled NEAR account.

No guard in `InitTransfer::process` checks `from.owner == user.key()`. The `solana/SECURITY.md` does not list this as a known or accepted design decision.

## Impact Explanation

- **Native tokens (vault path):** victim's SPL tokens are permanently locked in the bridge vault; attacker receives equivalent tokens on NEAR.
- **Bridged tokens (burn path):** victim's bridged SPL tokens are permanently burned; attacker receives equivalent tokens on NEAR.

Both outcomes constitute direct, irreversible theft of bridged funds — matching the Critical impact class: *Stealing, loss, or permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet, Bitcoin, Zcash, or Wormhole-routed flows.*

## Likelihood Explanation

SPL token delegations are a standard, widely-used mechanism across DEXes, lending protocols, and yield aggregators. A victim who has ever approved any program or wallet as a delegate over their token account is vulnerable if the attacker controls that delegate key. The attacker requires no privileged access, no key compromise, and no victim interaction beyond the pre-existing delegation. The attack is fully on-chain, permissionless, and repeatable up to the delegated amount.

## Recommendation

Add `token::authority = user` to the `from` account constraint in `InitTransfer`:

```rust
#[account(
    mut,
    token::mint = mint,
    token::token_program = token_program,
    token::authority = user,   // enforce from.owner == user.key()
)]
pub from: Box<InterfaceAccount<'info, TokenAccount>>,
```

This causes Anchor to enforce `from.owner == user.key()` at account-validation time, before any CPI is attempted, closing the delegation-drain path entirely.

```rust
//            amount: X,
//            recipient: "attacker.near".to_string(),

//            message: "".to_string(),
//        }
// 4. Assert: victim_ata.amount decreased by X
// 5. Assert: vault.amount increased by X  (native path)

//            AND recipient == "attacker.near"
```

The SPL Token CPI at lines 90–102 (native) or 110–120 (bridged) succeeds because `attacker` is a valid delegate of `victim_ata`. No guard in `InitTransfer::process` checks `from.owner == user.key()`.
