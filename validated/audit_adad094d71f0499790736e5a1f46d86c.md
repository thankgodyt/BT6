### Title
Malicious `ft_on_transfer` Receiver Can Manipulate `is_refund_required()` Return-Data to Trigger UTXO Refund Path — (File: `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

### Summary
The `safe_mint` deposit flow in `satoshi-bridge` trusts the return data from a user-controlled receiver contract's `ft_on_transfer` to decide whether to refund the deposited UTXO. A malicious receiver can return the full token amount (claiming it used zero tokens), causing `is_refund_required()` to return `true`. This triggers the UTXO refund path in `safe_mint_callback`, which removes the UTXO from `verified_deposit_utxo`, while the nBTC contract simultaneously refunds the minted tokens back to the user. The user then holds their nBTC back **and** can re-submit the same deposit proof to mint again — a double-mint.

### Finding Description
In `verify_safe_deposit_callback`, the bridge:
1. Verifies the light-client proof and inserts the UTXO into `verified_deposit_utxo`.
2. Calls `nbtc.safe_mint(recipient, amount, msg)`, which internally calls `ft_transfer_call` on the nBTC contract, which in turn calls `ft_on_transfer` on the **user-specified receiver contract**.
3. Chains `safe_mint_callback`, which calls `is_refund_required()`. [1](#0-0) 

`is_refund_required()` reads the return bytes of `safe_mint` and trusts them: [2](#0-1) 

The logic is: if `safe_mint` returns `0` (meaning the receiver claimed it used zero tokens), the function returns `true` — signalling that the UTXO should be un-verified and the deposit treated as failed.

The receiver contract is entirely user-controlled. A malicious receiver can return the full token amount to `ft_on_transfer`, causing the nBTC contract to refund all tokens back to the recipient, and causing `safe_mint` to return `0`. `is_refund_required()` then returns `true`.

The comment in the code itself acknowledges this concern:
> "Refund only if `safe_mint` returned 0. Any other outcome (non-zero amount, unparseable payload, panic) is treated as 'UTXO spent, no refund' — for safety, to avoid a potential double spend." [3](#0-2) 

Despite this conservative intent, the return value of `0` is still reachable by a malicious receiver simply by returning the full amount to `ft_on_transfer`. The bridge cannot distinguish between a legitimate failed transfer and a malicious one — it trusts the return data.

The parallel in `mint_callback` (the non-safe path) shows the pattern: when the mint fails, the UTXO is removed from `verified_deposit_utxo`: [4](#0-3) 

`safe_mint_callback` follows the same pattern — when `is_refund_required()` returns `true`, it removes the UTXO from `verified_deposit_utxo`, re-opening the deposit slot.

### Impact Explanation
**Critical.** The attacker:
1. Deposits BTC to a bridge address derived from a `SafeDepositMsg` that specifies their malicious receiver contract.
2. A relayer submits the deposit proof; `verify_safe_deposit_callback` marks the UTXO as verified and calls `safe_mint`.
3. The malicious receiver's `ft_on_transfer` returns the full token amount → nBTC refunds all tokens back to the attacker.
4. `safe_mint` returns `0` → `is_refund_required()` returns `true` → `safe_mint_callback` removes the UTXO from `verified_deposit_utxo`.
5. The attacker re-submits the same deposit proof. The UTXO is no longer in `verified_deposit_utxo`, so the `require!` at line 369 passes again.
6. The attacker receives a second mint of nBTC for the same BTC deposit.

This constitutes **unauthorized reminting** — the attacker receives more nBTC than the BTC they deposited, breaking the 1:1 backing invariant. [5](#0-4) 

### Likelihood Explanation
**High.** The `safe_mint` path is a public, user-facing deposit flow. Any user can specify an arbitrary receiver contract in the `msg` field of `SafeDepositMsg`. Deploying a malicious receiver on NEAR requires no special privileges. The attacker only needs to make one BTC deposit and then exploit the callback to mint unbacked nBTC repeatedly.

### Recommendation
Do not trust the return data from `safe_mint` / `ft_on_transfer` to determine whether the UTXO should be un-verified. Instead, treat any outcome where the promise **succeeded** (regardless of the returned amount) as "UTXO spent." Only remove the UTXO from `verified_deposit_utxo` if the promise itself **failed** (i.e., `is_promise_success()` returns `false`), not based on the receiver-controlled return value. This mirrors the fix recommended in the original report: use only the success/failure of the transaction, not the return data.

Concretely, replace `is_refund_required()` with a check on `is_promise_success()` in `safe_mint_callback`, consistent with how `mint_callback` handles the non-safe path. [6](#0-5) 

### Proof of Concept
1. Attacker deploys a NEAR contract `evil.near` implementing `ft_on_transfer` that always returns the full `amount` (i.e., "I used 0 tokens").
2. Attacker sends 0.01 BTC to the bridge deposit address derived from a `SafeDepositMsg` with `receiver = evil.near`.
3. Relayer calls `safe_verify_deposit(...)` with the Merkle proof.
4. `verify_safe_deposit_callback` runs: UTXO inserted into `verified_deposit_utxo`, `safe_mint` called.
5. nBTC calls `evil.near.ft_on_transfer(attacker, 1_000_000, msg)` → returns `1_000_000` (full amount).
6. nBTC refunds `1_000_000` satoshis of nBTC back to attacker. `safe_mint` returns `U128(0)`.
7. `safe_mint_callback` runs: `is_refund_required()` returns `true`. UTXO removed from `verified_deposit_utxo`.
8. Attacker re-submits the same Merkle proof via `safe_verify_deposit(...)`.
9. `verify_safe_deposit_callback` runs again: UTXO re-inserted, `safe_mint` called again → attacker receives another `1_000_000` nBTC.
10. Repeat step 8–9 indefinitely. Attacker mints unbacked nBTC, draining the protocol's backing. [2](#0-1) [7](#0-6)

/// Refund only if `safe_mint` returned 0. Any other outcome (non-zero
/// amount, unparseable payload, panic) is treated as "UTXO spent, no
/// refund" — for safety, to avoid a potential double spend.
fn is_refund_required() -> bool {
    match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
        Ok(value) => {
            if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {
                // Normal case: refund if the used token amount is zero
                // The amount can be zero if the `ft_on_transfer` in the receiver contract returns an amount instead of `0`, or if it panics.
                amount.0 == 0
            } else {
                // Unexpected case: don't refund
                false
            }
        }
        // Unexpected case: don't refund
        Err(_) => false,
    }
}
