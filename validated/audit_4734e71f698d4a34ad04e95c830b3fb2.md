Audit Report

## Title
`denormalize_amount()` Unchecked Multiplication Overflow Permanently Freezes Bridged Funds - (File: near/omni-bridge/src/lib.rs)

## Summary

`Contract::denormalize_amount()` performs a bare `amount * (10_u128.pow(diff_decimals))` with no overflow guard. With `overflow-checks = true` in the workspace `Cargo.toml`, any overflow is a hard runtime panic. When a user initiates a sufficiently large transfer on a foreign chain for a token whose NEAR-side `origin_decimals` exceeds the foreign-chain `decimals`, the panic fires inside `fin_transfer_callback` after the source-chain transaction is already irreversible, permanently freezing the user's funds.

## Finding Description

`denormalize_amount` is defined at: [1](#0-0) 

```rust
fn denormalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount * (10_u128.pow(diff_decimals))   // ← unchecked
}
```

It is called unconditionally in `fin_transfer_callback` before any transfer is recorded: [2](#0-1) 

And again in `fast_fin_transfer` before any state is written: [3](#0-2) 

And a third call site exists in the `claim_fee` path: [4](#0-3) 

The workspace enforces `overflow-checks = true`: [5](#0-4) 

Token decimals are stored via `add_token`, which is called from `bind_token_callback` and `deploy_token_callback` using values sourced directly from on-chain proofs (EVM `DeployToken` event, Wormhole VAA, Starknet event): [6](#0-5) 

The EVM `initTransfer` accepts a raw `uint128 amount` from the caller and emits it verbatim — no normalization is applied before emission: [7](#0-6) 

The NEAR prover parses this raw value directly into `InitTransferMessage.amount`: [8](#0-7) 

**Exploit path:**

1. A token is registered with `origin_decimals > decimals` (e.g., NEAR-originated token with 24 decimals, EVM token with 6 decimals → `diff_decimals = 18`).
2. A user calls `initTransfer` on EVM with an amount exceeding `u128::MAX / 10^diff_decimals` (e.g., for `diff_decimals = 18`, threshold ≈ `3.4 × 10^20` raw EVM units).
3. The relayer submits the proof to NEAR's `fin_transfer`.
4. `fin_transfer_callback` calls `denormalize_amount`, which overflows and panics.
5. The callback exits without recording the transfer or minting tokens.
6. The EVM `initTransfer` is irreversible (tokens already locked/burned).
7. Resubmitting the same proof always reproduces the same overflow — the panic is deterministic.

The CLAUDE.md false-positive note #2 ("Decimal Arithmetic Underflow") addresses only the **subtraction** `origin_decimals - decimals` underflowing due to misconfiguration. It explicitly does not address the **multiplication** overflow triggered by a legitimate user sending a large amount: [9](#0-8) 

## Impact Explanation

When `fin_transfer_callback` panics due to overflow:

- The user's tokens are already locked or burned on the source chain — the `initTransfer` transaction is irreversible.
- The NEAR-side callback panics before recording the transfer or minting tokens.
- The same proof, when resubmitted, will overflow again — the panic is deterministic.
- The user's funds are **permanently frozen**: unrecoverable on the source chain and never minted on NEAR.

This matches the critical impact criterion: *permanent freezing of bridged funds*.

## Likelihood Explanation

The overflow condition is `amount > u128::MAX / 10^diff_decimals`. For a NEAR-originated token with 24 decimals bridged to EVM with 6 decimals (`diff_decimals = 18`), the threshold is approximately `3.4 × 10^20` raw EVM units (`3.4 × 10^14` tokens). For high-supply tokens (meme tokens, governance tokens with large supplies), this threshold is reachable by a single large holder. The exploit requires no special privileges — any token holder on the source chain can trigger it by submitting a sufficiently large `initTransfer`. The panic is deterministic and reproducible on every resubmission of the same proof. The claim's likelihood table overstates the risk for typical configurations (it assumes `origin_decimals = 36` for the `diff_decimals = 18` row), but the core vulnerability is real for any token where `diff_decimals` is large enough that the total supply can exceed the overflow threshold.

## Recommendation

Replace the bare multiplication with a checked variant:

```rust
fn denormalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount
        .checked_mul(10_u128.pow(diff_decimals))
        .unwrap_or_else(|| env::panic_str("denormalize_amount: overflow"))
}
```

Alternatively, validate at ingestion inside `fin_transfer_callback` that `amount ≤ u128::MAX / 10^diff_decimals` and reject the proof with a recoverable error rather than a hard panic, so the relayer can handle the failure gracefully without permanently freezing funds.

## Proof of Concept

1. Register a token with `origin_decimals = 24`, `decimals = 6` (`diff_decimals = 18`).
2. On EVM, call `initTransfer(tokenAddress, 3_400_000_000_000_000_000_001, 0, 0, "near:victim.near", "")` — an amount just above `u128::MAX / 10^18 ≈ 3.4 × 10^20` raw units.
3. Submit the resulting proof to NEAR's `fin_transfer`.
4. `fin_transfer_callback` calls `denormalize_amount(3_400_000_000_000_000_000_001, Decimals { origin_decimals: 24, decimals: 6 })`.
5. Computes `3_400_000_000_000_000_000_001 * 10^18`, which exceeds `u128::MAX`.
6. With `overflow-checks = true`, the NEAR runtime panics.
7. The callback exits without recording the transfer or minting tokens.
8. The user's EVM tokens are permanently locked; no NEAR tokens are ever minted.
9. Resubmitting the proof always reproduces the same panic.
