### Title
Missing Self-Recipient Guard in `mint()` Allows nBTC to Be Minted to the Bridge, Permanently Locking User BTC — (File: contracts/nbtc/src/lib.rs)

---

### Summary

The `mint()` function in the nbtc token contract lacks the `mint_account_id != bridge_id` guard that `safe_mint()` explicitly enforces. A user who encodes `recipient_id = <bridge account>` in their `DepositMsg` will cause the bridge to call `mint()` with `mint_account_id = bridge_id`, minting nBTC to the bridge itself. The user's BTC is permanently locked with no recovery path, and the bridge accumulates untracked nBTC that distorts its internal accounting.

---

### Finding Description

`safe_mint()` in `contracts/nbtc/src/lib.rs` contains an explicit guard:

```rust
require!(
    account_id != self.bridge_id,
    "safe_mint: account_id must not be the bridge"
);
``` [1](#0-0) 

The standard `mint()` function, used by the non-safe deposit path, has no equivalent check:

```rust
pub fn mint(
    &mut self,
    mint_account_id: AccountId,
    mint_amount: U128,
    ...
) {
    self.assert_bridge();
    self.mint_inner(&mint_account_id, mint_amount);   // no guard on mint_account_id
    ...
}
``` [2](#0-1) 

The same protective pattern also appears in `handle_post_action()`:

```rust
require!(
    receiver_id != self.bridge_id,
    "handle_post_action: receiver_id must not be the bridge"
);
``` [3](#0-2) 

The bridge's standard deposit entry points (`verify_deposit`, `verify_deposit_v2`) call `mint()` with `mint_account_id` derived directly from `deposit_msg.recipient_id`: [4](#0-3) 

`recipient_id` is a free `AccountId` field supplied by the user. There is no validation in the bridge that rejects `recipient_id == bridge_id` before the cross-contract `mint()` call is issued.

---

### Impact Explanation

When `recipient_id = bridge_id`:

1. `nbtc.mint()` is called with `mint_account_id = bridge_id`, crediting nBTC to the bridge's own token balance.
2. The user receives zero nBTC.
3. The deposit is recorded as finalized in `verified_deposit_utxo`, so the refund path (`request_refund`) is permanently blocked for that UTXO.
4. The bridge accumulates nBTC that is invisible to its internal accounting variables (`cur_available_protocol_fee`, `lost_found`, etc.), creating a silent balance surplus that can mask future accounting errors or be silently consumed by protocol-fee withdrawals.

The user's BTC is permanently locked with no on-chain recovery mechanism — matching the **Critical: significant loss or permanent locking of user funds** impact class.

---

### Likelihood Explanation

The `DepositMsg.recipient_id` field is a plain `AccountId` set by the depositing user (or a dApp on their behalf). No validation in the bridge or the nbtc contract rejects the bridge's own account ID as a recipient on the standard `mint()` path. A user error (copy-paste of the bridge address instead of their own), a malicious dApp, or a deliberate griefing attempt can all trigger this. The attack requires no special role or privileged access — any NEAR account that can send BTC and have a relayer submit the proof is sufficient.

---

### Recommendation

Add the same guard to `mint()` that already exists in `safe_mint()`:

```rust
pub fn mint(
    &mut self,
    mint_account_id: AccountId,
    ...
) {
    self.assert_bridge();
    require!(
        mint_account_id != self.bridge_id,
        "mint: mint_account_id must not be the bridge"
    );
    self.mint_inner(&mint_account_id, mint_amount);
    ...
}
``` [2](#0-1) 

Optionally, enforce the same check inside `mint_inner()` to provide a single, unforgeable invariant point.

---

### Proof of Concept

1. Attacker (or user) constructs a `DepositMsg` with `recipient_id` set to the satoshi-bridge contract's account ID.
2. Attacker sends BTC to the deposit address derived from that `DepositMsg` via `get_deposit_path()`. [5](#0-4) 
3. A relayer submits `verify_deposit_v2(deposit_msg, tx_bytes, vout, proof)`. [6](#0-5) 
4. The bridge verifies the Merkle proof and calls `nbtc.mint(bridge_id, amount, ...)`.
5. `mint()` calls `mint_inner(&bridge_id, amount)` — no guard fires. [7](#0-6) 
6. The UTXO is inserted into `verified_deposit_utxo`, permanently blocking any future `request_refund` for this UTXO.
7. The user holds zero nBTC; their BTC is locked forever in the bridge's custody address.
