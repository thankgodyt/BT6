### Title
`DepositProtocolFee` Permanently Blocked by Withdrawal Minimum-Amount Guard — (File: `contracts/satoshi-bridge/src/api/token_receiver.rs`)

### Summary
`ft_on_transfer` applies the `min_withdraw_amount` guard unconditionally before branching on the message type. This means the `DepositProtocolFee` path — which has nothing to do with Bitcoin dust limits — is silently blocked whenever the deposited token amount falls below `min_withdraw_amount`, mirroring the external report's pattern of a single condition incorrectly gating two independent code paths.

### Finding Description
In `ft_on_transfer`, the very first substantive check is:

```rust
require!(
    amount >= self.internal_config().min_withdraw_amount,
    "Invalid amount"
);
```

Only *after* this guard passes does the code deserialise `msg` and branch:

```rust
match message {
    TokenReceiverMessage::DepositProtocolFee => { … }
    TokenReceiverMessage::Withdraw { … }      => { … }
}
```

`min_withdraw_amount` exists to prevent dust UTXOs on the Bitcoin network — a concern that is entirely irrelevant to `DepositProtocolFee`, which simply credits `acc_collected_protocol_fee` / `cur_available_protocol_fee` on NEAR and never touches a Bitcoin output. Because the guard is placed before the branch, any `DepositProtocolFee` call whose `amount` is below `min_withdraw_amount` is rejected with `"Invalid amount"`, regardless of how large or small the configured threshold is.

This is structurally identical to the reported bug: a single condition (`maxChunks > mintedChunks` / `amount >= min_withdraw_amount`) gates two independent paths, causing one path that should always be reachable to become blocked whenever the condition is false. [1](#0-0) [2](#0-1) 

### Impact Explanation
Any `ft_transfer_call` carrying a `DepositProtocolFee` message with `amount < min_withdraw_amount` reverts. Because `min_withdraw_amount` is a legitimate operational parameter (set to prevent dust withdrawals), it will routinely be non-zero. Protocol-fee deposits in small denominations — or any deposit whose amount happens to fall below the threshold — are permanently rejected at the contract level without any recourse for the caller. This is a publicly reachable stuck-state / invariant-violation in a production bridge token-receiver path. [3](#0-2) [4](#0-3) 

### Likelihood Explanation
Medium. `min_withdraw_amount` is expected to be set to a meaningful satoshi value (e.g. 10 000 sat) to prevent dust. Any protocol-fee deposit below that value — a realistic operational scenario — triggers the bug. No special attacker capability is required; any token holder calling `ft_transfer_call` with a `DepositProtocolFee` message and a sub-threshold amount will hit the revert.

### Recommendation
Move the `min_withdraw_amount` guard inside the `Withdraw` match arm so it only applies to actual withdrawal messages:

```rust
fn ft_on_transfer(&mut self, sender_id: AccountId, amount: U128, msg: String)
    -> PromiseOrValue<U128>
{
    let amount: u128 = amount.into();
    // removed: the blanket min_withdraw_amount check
    let message = serde_json::from_str::<TokenReceiverMessage>(&msg).expect("INVALID MSG");
    let token_id = env::predecessor_account_id();
    require!(token_id == self.internal_config().nbtc_account_id, "Invalid token_id");
    match message {
        TokenReceiverMessage::DepositProtocolFee => { /* no amount floor needed */ … }
        TokenReceiverMessage::Withdraw { … } => {
            require!(
                amount >= self.internal_config().min_withdraw_amount,
                "Invalid amount"
            );
            …
        }
    }
}
```

### Proof of Concept
1. DAO configures `min_withdraw_amount = 10_000` (satoshis).
2. An integrator calls `nbtc.ft_transfer_call(bridge, "5000", '{"DepositProtocolFee":{}}')`.
3. `ft_on_transfer` is invoked with `amount = 5000`.
4. `require!(5000 >= 10000, "Invalid amount")` panics → the call reverts.
5. The protocol-fee deposit is permanently rejected; the tokens are returned to the sender.
6. No amount of retrying with the same value will succeed; the caller must send ≥ `min_withdraw_amount` even though the fee deposit has no Bitcoin-side dust concern. [5](#0-4)
