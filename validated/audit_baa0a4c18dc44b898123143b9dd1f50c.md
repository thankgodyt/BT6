### Title
Peras Certificate Verification Bypass: `validatePerasCert` Unconditionally Accepts All Peer-Supplied Certificates - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary
The default `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` for every certificate it receives, performing no cryptographic or structural verification. This stub is wired directly into the production node-to-node Peras certificate diffusion handler. Any unprivileged peer can therefore send a crafted `PerasCert` claiming any block was boosted by the Peras voting protocol, and the receiving node will accept it, store it, and trigger chain selection for the adversarially chosen block.

### Finding Description

The `BlockSupportsPeras` typeclass declares `validatePerasCert` as the gate that must be passed before a received certificate influences the node's state. The sole concrete instance in production is the degenerate placeholder:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature check, no committee membership check, no round-number bounds check, and no boosted-block existence check is performed. The function simply wraps the raw, unverified certificate in the `ValidatedPerasCert` constructor and returns it as valid.

This stub is the function passed to `processCerts` inside `makePerasCertPoolWriterFromChainDB`:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

That writer is wired directly into the live `hPerasCertDiffusionClient` handler in the node-to-node protocol stack:

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
``` [3](#0-2) 

Every certificate that passes the degenerate validator is forwarded to `ChainDB.addPerasCertAsync`, which enqueues a `ChainSelAddPerasCert` message:

```haskell
addPerasCertAsync CDB{cdbTracer, cdbChainSelQueue} =
  addPerasCertToQueue (TraceAddPerasCertEvent >$< cdbTracer) cdbChainSelQueue
``` [4](#0-3) 

The background chain-selection thread then processes the message: it stores the certificate in `PerasCertDB` and calls `chainSelectionForBlock` for the block named in the certificate's `pcCertBoostedBlock` field:

```haskell
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [5](#0-4) 

The Peras weight boost (`vpcCertBoost`) assigned to the boosted block is taken directly from `perasWeight params` — a protocol parameter — without any relationship to the actual votes that supposedly produced the certificate. [6](#0-5) 

### Impact Explanation

An adversary who can establish a peer connection (any unprivileged network peer) can:

1. Craft a `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock` pointing to a non-canonical block the adversary has already diffused.
2. Send it over the Peras certificate diffusion mini-protocol.
3. The receiving node accepts it unconditionally, stores it, and re-runs chain selection with the adversarially chosen block receiving the full Peras weight boost.
4. If the boosted block is on a fork, the node may switch to that fork, diverging from the canonical chain.

This is a **bypass of Peras certificate/vote verification** that enables unauthorized certificate acceptance and chain-selection manipulation — matching the "Critical: bypass of Peras voting or certificate checks" impact category.

### Likelihood Explanation

The vulnerable code path is active in the production node-to-node handler. No special privileges, keys, or stake are required; any peer that can open a connection and speak the Peras certificate diffusion mini-protocol can trigger the bug. The attack is deterministic and requires no brute force.

### Recommendation

Replace the stub `validatePerasCert` implementation with a real one that:
- Verifies the aggregate BLS signature over the claimed voter set against the claimed election ID and boosted block.
- Checks that every voter in the certificate was a legitimate committee member for the claimed round (using the epoch stake snapshot and committee selection algorithm).
- Validates that the round number falls within the acceptable window relative to the current chain tip.
- Rejects certificates whose `pcCertBoostedBlock` does not correspond to a known, structurally valid block point.

Until the real implementation is ready, the stub should at minimum reject all externally received certificates (return `Left PerasValidationErr` unconditionally) rather than accept them all, so that the diffusion layer cannot be used as an attack vector.

### Proof of Concept

```
Attacker peer  -->  PerasCertDiffusion mini-protocol
  sends: PerasCert { pcCertRound = R, pcCertBoostedBlock = <fork tip> }

Node receives cert
  calls: validatePerasCert mkPerasParams cert
  result: Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })
  -- no signature checked, no committee checked

Node calls: addPerasCertAsync chainDB (WithArrivalTime now validatedCert)
  --> ChainSelAddPerasCert enqueued

Background thread:
  PerasCertDB.addCert  (cert stored)
  chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
  --> fork tip now carries full Peras weight boost
  --> node may switch to adversary's fork
```
