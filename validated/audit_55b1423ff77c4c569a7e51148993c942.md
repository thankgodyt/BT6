### Title
Unconditional Burn Before Refund Check in `resolve_fast_transfer` Enables Double-Minting of Bridge Tokens — (File: `near/omni-bridge/src/lib.rs`)

### Summary

`resolve_fast_transfer` calls `burn_tokens_if_needed` unconditionally before checking whether a refund is required. When a fast-transfer recipient rejects the tokens (returns a non-zero unused amount from `ft_on_transfer`), the burn is scheduled as a detached promise against a balance that is subsequently zeroed by the outer NEP-141 `ft_resolve_transfer` refund. The burn fails silently, the fast-transfer record is deleted, and a later `fin_transfer` proof submission mints a fresh `amount` of bridge tokens for the recipient — while the relayer has already recovered their fronted tokens via the refund. The net result is `amount` extra bridge tokens in circulation.

### Finding Description

The fast-transfer flow for a NEAR recipient is:

1. Trusted relayer calls `ft_transfer_call` on the bridge token, sending `amount` tokens to the bridge and triggering `fast_fin_transfer`.
2. `fast_fin_transfer_to_near_callback` records the fast-transfer entry and calls `send_tokens` (itself an `ft_transfer_call`) to forward `amount_without_fee` to the recipient.
3. `resolve_fast_transfer` is chained as the callback of `send_tokens`.

Inside `resolve_fast_transfer`:

```rust
// near/omni-bridge/src/lib.rs  L895-L912
pub fn resolve_fast_transfer(
    &mut self,
    token_id: &AccountId,
    fast_transfer_id: &FastTransferId,
    amount: U128,
    is_ft_transfer_call: bool,
) -> U128 {
    // Burn the tokens to ensure the locked tokens are not double-minted
    self.burn_tokens_if_needed(token_id.clone(), amount);   // ← always fires

    if Self::is_refund_required(is_ft_transfer_call) {
        self.remove_fast_transfer(fast_transfer_id);        // ← record deleted
        amount                                              // ← triggers relayer refund
    } else {
        U128(0)
    }
}
```

`burn_tokens_if_needed` issues a `.detach()`-ed cross-contract `burn` call:

```rust
// near/omni-bridge/src/lib.rs  L1806-L1813
fn burn_tokens_if_needed(&self, token: AccountId, amount: U128) {
    if self.is_deployed_token(&token) {
        ext_token::ext(token)
            .with_static_gas(BURN_TOKEN_GAS)
            .burn(amount)
            .detach();          // ← fire-and-forget; failure is silent
    }
}
```

When `is_refund_required` returns `true` (recipient's `ft_on_transfer` returned the full amount, i.e., the NEP-141 `ft_transfer_call` result is `0`):

* The token contract's own `ft_resolve_transfer` has already returned `amount` tokens from the recipient back to the bridge.
* `resolve_fast_transfer` returns `amount` as "unused."
* The outer `ft_resolve_transfer` (from the relayer's original `ft_transfer_call`) refunds `amount` from the bridge to the relayer — zeroing the bridge's token balance.
* The detached `burn` receipt then executes against a zero bridge balance and fails silently.
* The fast-transfer record has been deleted by `remove_fast_transfer`.

When the cross-chain proof is later submitted via `fin_transfer` → `process_fin_transfer_to_near`:

```rust
// near/omni-bridge/src/lib.rs  L1888-L1901
```

With no fast-transfer record, the bridge mints `amount` bridge tokens for the original recipient as a normal inbound transfer. The relayer has already recovered their `amount` tokens via the refund. The burn that was supposed to prevent this double-minting failed silently.

### Impact Explanation

For any deployed (bridge-issued) token:

* The relayer recovers their fronted `amount` tokens (refund succeeds).
* The bridge mints a fresh `amount` tokens for the recipient (proof finalisation succeeds).
* The detached burn fails silently (bridge balance was 0).
* Net: `amount` extra tokens exist on NEAR that have no corresponding locked/burned collateral on the source chain — **unauthorized token minting / permanent supply inflation**.

### Likelihood Explanation

An unprivileged attacker on any supported foreign chain can:

1. Deploy a malicious NEAR contract whose `ft_on_transfer` always returns the full `amount` (rejecting all tokens).
2. Initiate a legitimate cross-chain transfer to that contract on the foreign chain.
3. Wait for a trusted relayer to observe the transfer and call `fast_fin_transfer` (relayers are economically incentivised to do so for the fee).
4. After the relayer's refund is processed, submit the cross-chain proof via the public `fin_transfer` entry point.

No privileged access is required beyond the attacker's ability to deploy a NEAR contract and initiate a foreign-chain transfer. The relayer's participation is automatic and incentive-driven.

### Recommendation

Move `burn_tokens_if_needed` inside the `else` branch so it only fires when the tokens were successfully consumed by the recipient (no refund needed):

```rust
pub fn resolve_fast_transfer(
    &mut self,
    token_id: &AccountId,
    fast_transfer_id: &FastTransferId,
    amount: U128,
    is_ft_transfer_call: bool,
) -> U128 {
    if Self::is_refund_required(is_ft_transfer_call) {
        // Recipient rejected tokens; return them to the relayer.
        // Do NOT burn — the tokens will be refunded, not retained.
        self.remove_fast_transfer(fast_transfer_id);
        amount
    } else {
        // Tokens were consumed by the recipient; burn to prevent double-minting.
        self.burn_tokens_if_needed(token_id.clone(), amount);
        U128(0)
    }
}
```

### Proof of Concept

1. Attacker deploys `MaliciousRecipient` on NEAR — `ft_on_transfer` always returns `amount` (rejects all tokens).
2. Attacker initiates a transfer of `X` bridge tokens from Ethereum to `MaliciousRecipient` on NEAR.
3. Trusted relayer calls `fast_fin_transfer` with `msg` non-empty (triggering `ft_transfer_call` path), fronting `X` tokens.
4. `fast_fin_transfer_to_near_callback` records the fast transfer and calls `send_tokens` → `ft_transfer_call(MaliciousRecipient, X, msg)`.
5. `MaliciousRecipient.ft_on_transfer` returns `X`; token contract refunds `X` to bridge.
6. `resolve_fast_transfer` fires: detached `burn(X)` scheduled; `remove_fast_transfer` deletes the record; returns `X`.
7. Outer `ft_resolve_transfer` refunds `X` from bridge to relayer (bridge balance → 0).
8. Detached `burn(X)` executes against bridge balance 0 — fails silently.
9. Attacker calls `fin_transfer` with the Ethereum proof.
10. `process_fin_transfer_to_near` finds no fast-transfer record → mints `X` tokens for `MaliciousRecipient`.

**Result:** Relayer holds `X` tokens (refunded). `MaliciousRecipient` holds `X` freshly minted tokens. `X` tokens were burned on Ethereum. Net: `X` unbacked tokens in circulation on NEAR. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

```rust
    fn is_refund_required(is_ft_transfer_call: bool) -> bool {
        if is_ft_transfer_call {

                Ok(value) => {

                        // Unexpected case: don't refund

                    }
                }

                Err(_) => false,
            }
        } else {
            // Not ft_transfer_call: don't refund
            false
        }
    }
```
