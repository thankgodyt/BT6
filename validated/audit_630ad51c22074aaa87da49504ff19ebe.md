### Title
Peras Certificate Validation Stub Unconditionally Accepts All Peer-Supplied Certificates, Enabling Chain Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` function in the degenerate `BlockSupportsPeras` instance is a stub that unconditionally returns `Right` for every certificate, performing no cryptographic or semantic checks. The production certificate ingest path (`processCerts`) uses this stub directly. Any unprivileged peer can therefore inject arbitrary Peras certificates that are stored in `PerasCertDB` and used to inflate the `PerasWeightSnapshot`, causing chain selection to prefer a non-canonical chain.

---

`processCerts` calls the supplied validator on every inbound certificate. Because `validatePerasCert mkPerasParams` always returns `Right`, every certificate passes: [3](#0-2)

This snapshot is consumed by `preferAnchoredCandidate` during chain selection. When the snapshot is non-empty, the weighted comparison path is taken instead of the standard longest-chain rule: [6](#0-5)

### Impact Explanation

An unprivileged peer can craft Peras certificates referencing any block point with any round number. Because `validatePerasCert` never rejects anything, these certificates are stored and their boosted-block weights are added to the `PerasWeightSnapshot`. Chain selection then uses `totalWeightOfFragment` (block count + boost) to compare candidates. By injecting certificates that boost blocks on a shorter or weaker fork, an attacker can make an honest node's `preferAnchoredCandidate` return `ShouldSwitch` for a non-canonical chain, causing the node to adopt a chain that would otherwise be rejected.

This is a **Critical** impact: bypass of Peras certificate validation that enables unauthorized certificate acceptance and chain-selection divergence from the canonical chain.

---

### Likelihood Explanation

The entry point is the Peras certificate mini-protocol object pool, reachable by any connected peer once Peras certificate diffusion is active. No special privileges, keys, or stake are required — only the ability to send a well-formed (but semantically invalid) `PerasCert` message. The stub is explicitly acknowledged in two separate TODO comments referencing open issues (#73, #120), confirming the validation logic was intentionally deferred and has not been implemented.

---

### Recommendation

Replace the degenerate `validatePerasCert` stub with a real implementation that verifies:
- The aggregate BLS signature over `(roundNo, boostedBlock)` against the claimed committee members' keys.
- That the claimed voters hold sufficient stake to form a quorum.
- That the certificate round number is within the valid window relative to the current chain tip.

Until real validation is in place, the `processCerts` ingest path should refuse all inbound certificates (or the Peras certificate mini-protocol should not be activated).

---

### Proof of Concept

1. Connect to a node with Peras certificate diffusion enabled.
2. Send a `PerasCert` message with `pcCertRound = R` and `pcCertBoostedBlock = P` where `P` is the tip of a shorter fork `F`.
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right ValidatedPerasCert{..}` unconditionally.
4. The certificate is stored; `implGetWeightSnapshot` now returns a snapshot with `P → perasWeight params`.
5. When the node next runs chain selection and `F` is a candidate, `preferAnchoredCandidate` computes `totalWeightOfFragment snap F > totalWeightOfFragment snap canonical` and returns `ShouldSwitch`, causing the node to adopt `F`. [7](#0-6) [8](#0-7)

preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"
        Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
          case preferCandidate
            (projectChainOrderConfig cfg)
            (weightedSelectView cfg weights oursSuffix)
            (weightedSelectView cfg weights candSuffix) of
            ShouldSwitch r -> ShouldSwitch (Left r)
