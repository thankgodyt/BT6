### Title
Stub `validatePerasCert` Unconditionally Accepts Any Certificate, Enabling Unprivileged Peers to Bypass Peras Certificate Validation and Corrupt Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` function is a stub that unconditionally returns `Right` for every input certificate, performing zero cryptographic or semantic validation. Because Peras certificates received from unprivileged peers via the `PerasCertDiffusion` miniprotocol are passed through this function before being stored and used to update the `PerasWeightSnapshot` that drives chain selection, any peer can inject crafted certificates that boost arbitrary blocks and cause an honest node to prefer a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` typeclass declares `validatePerasCert` as the mandatory gate that must produce a `ValidatedPerasCert` before a certificate may enter the system. The universal production instance — `instance StandardHash blk => BlockSupportsPeras blk` — implements this gate as a no-op stub:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

Every field of the incoming `PerasCert` — round number, boosted block point, and any future cryptographic material — is copied verbatim into the `ValidatedPerasCert` wrapper without inspection. The `Either` return type is structurally `Right` for all inputs; the `Left` branch is unreachable.

The inbound `PerasCertDiffusion` miniprotocol handler in `NodeToNode.hs` wires an `ObjectPoolWriter` for certificates to `objectDiffusionInbound`, mirroring the vote path (`makePerasVotePoolWriterFromChainDB`). The pool writer calls `validatePerasCert` to gate admission. Because that function always succeeds, every certificate a peer sends is wrapped in `ValidatedPerasCert` and forwarded to `addPerasCertAsync` in the `ChainDB` API:

```haskell
addPerasCertAsync :: WithArrivalTime (ValidatedPerasCert blk) -> m (AddPerasCertPromise m)
```

`addPerasCertAsync` enqueues the certificate on `cdbChainSelQueue`. The background `chainSelSync` thread dequeues it, stores it in `PerasCertDB`, and recomputes the `PerasWeightSnapshot`. That snapshot is the sole source of Peras weight boosts used by `preferAnchoredCandidate` during chain selection:

```haskell
assert (all (shouldSwitch . preferAnchoredCandidate bcfg weights curChain . fst) candidates) $
```

A crafted certificate with an attacker-chosen `pcCertBoostedBlock` therefore injects an artificial weight boost for an arbitrary block into every subsequent chain-selection comparison.

---

### Impact Explanation

An unprivileged peer can construct a `PerasCert` with any `pcCertRound` and any `pcCertBoostedBlock` (e.g., the tip of a minority fork). After the stub accepts it, the `PerasWeightSnapshot` is updated to boost that block. Chain selection then prefers chains that include the boosted block over chains that do not, even if the boosted chain is shorter or less secure by the base Praos/Ouroboros metric. This constitutes:

- **Bypass of Peras certificate validation** — the cryptographic and semantic checks that are supposed to prove a quorum of committee members endorsed the boosted block are entirely absent.
- **Chain-selection manipulation** — an honest node can be made to prefer a non-canonical chain solely on the basis of a forged weight boost, violating the security assumptions of the Peras protocol.

This falls under the allowed scope: *Critical — bypass of Peras voting or certificate checks that enables unauthorized certificate acceptance*, and *High — chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain*.

---

### Likelihood Explanation

The `PerasCertDiffusion` miniprotocol is active in the node-to-node stack. Any connected peer — no keys, no stake, no privilege required — can send a `PerasCert` message. The stub is the universal production instance; there is no era guard, feature flag, or secondary check that would reject the certificate after `validatePerasCert` returns `Right`. The TODO comment and linked issue confirm the stub is intentional but unfinished, not a deliberate security boundary.

---

### Recommendation

Implement real validation inside `validatePerasCert` before the `PerasCertDiffusion` miniprotocol is enabled in production. At minimum, validation must verify:

1. The certificate's cryptographic proof that a quorum of eligible committee members signed the boosted block.
2. That the boosted block exists and is on a plausible chain (not an arbitrary point).
3. That the round number is within the expected window relative to the current slot.

Until full validation is implemented, the `PerasCertDiffusion` inbound handler should reject all externally received certificates (analogous to the empty-stake-distribution guard already applied to the `PerasVoteDiffusion` path).

---

### Proof of Concept

1. Connect to a node that has the `PerasCertDiffusion` miniprotocol active.
2. Craft a `PerasCert` with `pcCertRound = <any round>` and `pcCertBoostedBlock = <tip of a minority fork>`.
3. Send it via the `PerasCertDiffusion` inbound channel.
4. The certificate reaches `validatePerasCert` (stub), which returns `Right ValidatedPerasCert{...}` unconditionally.
5. `addPerasCertAsync` enqueues the certificate; `chainSelSync` stores it in `PerasCertDB` and recomputes `PerasWeightSnapshot` to include the attacker-chosen boost.
6. Subsequent calls to `preferAnchoredCandidate` use the inflated weight, causing the node to switch to or retain the minority fork.
