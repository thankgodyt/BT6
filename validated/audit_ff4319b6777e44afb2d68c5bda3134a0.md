### Title
Adversary Can Pre-empt Refund Request to Redirect User BTC to Attacker-Controlled Address - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary

`request_refund` is publicly callable by any NEAR account. The refund request key (`utxo_storage_key = {tx_id}@{vout}`) is fully deterministic from on-chain observable data. An adversary can call `request_refund` for any deposit UTXO before the legitimate depositor does, inserting their own `refund_address`. The callback then blocks the legitimate user's identical call with "Refund request already exists for this UTXO". After the `unsafe_refund_timelock_sec` (14 days), anyone can call `execute_refund` to send the BTC to the adversary's address.

### Finding Description

`request_refund` in `contracts/satoshi-bridge/src/api/bridge.rs` is in a `#[trusted_relayer]` impl block but carries no individual `#[trusted_relayer]` guard — unlike `verify_refund_finalize` and `remove_refund_pending_tx_id` in the same block which do carry it. The function is therefore callable by any NEAR account that attaches the required storage deposit. [1](#0-0) 

The callback `request_refund_callback` derives the storage key deterministically: [2](#0-1) 

It then hard-reverts if a request already exists for that key: [3](#0-2) 

The stored `refund_address` comes directly from the caller's argument — there is no check that the caller is the `deposit_msg.recipient_id` or any party related to the deposit: [4](#0-3) 

After the `unsafe_refund_timelock_sec` window, `execute_refund` is also publicly callable with no ownership check, so the adversary can trigger the MPC signing pipeline to send BTC to their own address: [5](#0-4) 

The `unsafe_refund_timelock_sec` is 14 days by default, giving DAO/Operator a window to reject — but this is an off-chain operational dependency, not an on-chain invariant: [6](#0-5) 

### Impact Explanation

When `deposit_msg.refund_address` is `None` (the common case — users do not pre-authorize a refund address), the adversary supplies an arbitrary `refund_address`. If the DAO does not reject the adversary's request within 14 days, `execute_refund` can be called by anyone to construct and MPC-sign a Bitcoin transaction paying the adversary. This constitutes a complete theft of the depositor's BTC. Even if the DAO intervenes, the legitimate user's refund is blocked for the entire period, constituting a forced temporary lock of bridged funds.

### Likelihood Explanation

All inputs needed to construct the attack are publicly observable:
- `deposit_msg` is emitted as an event by `get_user_deposit_address` [7](#0-6) 
- `tx_bytes`, `vout`, and the Merkle proof are readable from the Bitcoin blockchain.

The adversary only needs to watch for unfinalized deposits and submit `request_refund` before the legitimate depositor does. No privileged access, leaked key, or third-party compromise is required. The NEAR deposit cost is the only deterrent, and it is non-refundable even on rejection — but it is negligible compared to the BTC value at stake.

### Recommendation

1. Require that the caller of `request_refund` is either the `deposit_msg.recipient_id` or a trusted relayer.
2. Alternatively, bind the `refund_address` to the `deposit_msg` at deposit time (i.e., require `deposit_msg.refund_address` to be set) so that the adversary cannot substitute their own address even if they front-run the call.
3. If permissionless refund submission must be preserved, store the caller's identity alongside the request and require the same caller to execute it, or require DAO approval before `execute_refund` can proceed for requests where `deposit_msg.refund_address` is `None`.

### Proof of Concept

1. Alice deposits 1 BTC. Her `deposit_msg` has `refund_address: None`. The deposit event is emitted on NEAR.
2. The relayer never calls `verify_deposit`. Alice calls `request_refund(deposit_msg, alice_btc_addr, tx_bytes, vout, proof, None)`.
3. Bob (adversary) observes Alice's pending NEAR transaction and submits `request_refund(deposit_msg, bob_btc_addr, tx_bytes, vout, proof, None)` with higher gas so his callback lands first.
4. Bob's `request_refund_callback` succeeds: `refund_requests["{tx_id}@{vout}"] = RefundRequest { refund_address: bob_btc_addr, ... }`.
5. Alice's `request_refund_callback` panics: `"Refund request already exists for this UTXO"`.
6. After 14 days, Bob calls `execute_refund("{tx_id}@{vout}", None)`. The bridge builds a Bitcoin transaction paying Bob's address and requests an MPC signature.
7. Alice's 1 BTC is sent to Bob.

    #[allow(clippy::too_many_arguments)]
    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
