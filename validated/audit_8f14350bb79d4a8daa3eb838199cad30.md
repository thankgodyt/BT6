### Title
`validatePerasCert` Performs No Actual Certificate Validation, Allowing Forged Peras Certificates to Influence Chain Selection — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The blanket `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` (success) for every certificate it receives, performing zero cryptographic or semantic checks. This is the exact analog of the external report's `safeTransferMany()` bug: a function whose name implies a safety/validation check but silently skips it. Because this "validation" is wired directly into the production certificate-ingestion path (`processCerts`), any unprivileged peer can inject a forged Peras certificate that passes the gate, is stored in the `PerasCertDB`, and triggers chain selection with an artificial weight boost — potentially causing an honest node to prefer a non-canonical chain.

---

### Finding Description

In `SupportsPeras.hs`, the only `BlockSupportsPeras` instance in the codebase is a blanket instance covering every block type:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
``` [1](#0-0) 

Its `validatePerasCert` method is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [2](#0-1) 

No signature verification, no committee membership check, no round-number bounds check, no boosted-block validity check — the function wraps the raw certificate in `ValidatedPerasCert` and assigns it the full `perasWeight` unconditionally.

This "validator" is called directly in the production certificate-ingestion path. `makePerasCertPoolWriterFromChainDB` passes `validatePerasCert mkPerasParams` as the validation callback:

```haskell
(validatePerasCert mkPerasParams)
-- TODO replace when actual plumbing is in place
``` [3](#0-2) 

`processCerts` then uses this callback to gate certificate acceptance:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _) ->
      throw (PerasCertValidationError errs)
``` [4](#0-3) 

Because `validatePerasCert` always returns `Right`, the `(errs, _)` branch is never taken. Every certificate — including forged ones — is accepted and forwarded to `ChainDB.addPerasCertAsync`.

Once stored, the certificate triggers `chainSelSync`, which calls `chainSelectionForBlock` for the boosted block:

```haskell
-- Trigger chain selection for the boosted block.
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [5](#0-4) 

Chain selection now uses Peras weight (`wsvTotalWeight = blockNo + weightBoost`) to compare candidates:

```haskell
case compare (wsvTotalWeight ours) (wsvTotalWeight cand) of
    LT -> ShouldSwitch (Heavier $ ...)
``` [6](#0-5) 

A forged certificate injects `perasWeight params` of artificial weight onto any block the attacker chooses, potentially tipping chain selection toward a non-canonical fork.

---

### Impact Explanation

**High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain.**

Peras weight is additive to block number in chain comparison (`wsvTotalWeight`). A single forged certificate with `perasWeight params` boost can make a shorter fork appear heavier than the honest chain. The security parameter `k` is defined in terms of total weight (block number + weight boost), so a sufficiently large forged boost can exceed the rollback threshold and cause the node to permanently adopt a minority fork. This directly undermines the Common Prefix property of Ouroboros.

---

### Likelihood Explanation

**Medium.** The full attack path is wired in production code and requires only that the Peras Object Diffusion mini-protocol is active. The CHANGELOG notes that "if Peras is disabled (which is the default), there is no observable difference," meaning the vulnerability is dormant until Peras is enabled. However, the code is already deployed in production files with no runtime guard preventing the broken validator from being called once Peras is switched on. No key compromise, stake majority, or operator access is required — any peer that can send a Peras certificate message can trigger this.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
1. Verifies the aggregate BLS signature over `(electionId, candidate)` against the committee's aggregate verification key.
2. Checks that the certificate's round number falls within the valid window (not too old, not in the future).
3. Verifies that the boosted block's slot satisfies `PerasBlockMinSlots`.
4. Confirms that the voters in the certificate form a quorum (total stake ≥ threshold).

Until a real implementation is available, the `processCerts` path should refuse all inbound certificates (return `Left PerasValidationErr` unconditionally) rather than accept them all. The current stub inverts the safe default.

---

### Proof of Concept

**Attacker-controlled entry path:**

1. Peer connects and the Peras Object Diffusion mini-protocol is active.
2. Peer sends a `PerasCert` message with `pcCertRound = R` and `pcCertBoostedBlock = B`, where `B` is a block on a minority fork.
3. `makePerasCertPoolWriterFromChainDB` → `opwAddObjects` → `processCerts` is called with this certificate.
4. `validatePerasCert mkPerasParams cert` is called — returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams })` unconditionally. [7](#0-6) 
5. The certificate is stored via `ChainDB.addPerasCertAsync`.
6. `chainSelSync` processes the certificate, looks up block `B` in the VolatileDB, and calls `chainSelectionForBlock` for it. [8](#0-7) 
7. Chain selection now computes `wsvTotalWeight` for the candidate fragment containing `B`, which includes the forged boost. If `blockNo(B) + perasWeight > blockNo(honest_tip)`, the node switches to the minority fork. [9](#0-8)
