### Title
ChainSync Client Ignores Peras Weight Boosts in `checkPreferTheirsOverOurs`, Causing Incorrect Peer Disconnection and Chain Selection Failure - (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

The `checkPreferTheirsOverOurs` function in the ChainSync client evaluates whether a candidate chain (whose tip is beyond the forecast horizon) is preferred over the node's current chain. It does so using `emptyPerasWeightSnapshot` — explicitly ignoring all Peras certificate weight boosts — instead of the actual `PerasWeightSnapshot`. This mirrors the OracleMaker analog exactly: a guard mechanism evaluates only the **current** state (chain length, no boosts) rather than the **full resulting state** (chain length plus Peras boosts). As a result, a node can incorrectly disconnect from a peer offering a legitimately heavier Peras-boosted chain, causing the node to remain on a lighter, non-canonical fork.

---

### Finding Description

In `checkPreferTheirsOverOurs`, the ChainSync client calls `preferAnchoredCandidate` with a hardcoded `emptyPerasWeightSnapshot`:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← always zero weight boost
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
``` [1](#0-0) 

This check fires when a received header is beyond the forecast horizon. Its purpose is to disconnect from peers whose chain is not preferred over ours, to avoid wasting resources. However, by passing `emptyPerasWeightSnapshot`, the comparison is performed **as if no Peras certificates exist**, ignoring all weight boosts accumulated by the candidate chain.

The correct comparison — used everywhere else in chain selection — computes the `weightedSelectView` of the suffix after the intersection point, summing `wsvBlockNo` and `wsvWeightBoost`:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [2](#0-1) 

And `preferAnchoredCandidate` correctly uses the actual snapshot when it is non-empty:

```haskell
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights = ...  -- tip-only comparison
  | otherwise =
      case AF.intersect ours cand of
        Just (_, _, oursSuffix, candSuffix) ->
          case preferCandidate cfg
            (weightedSelectView cfg weights oursSuffix)
            (weightedSelectView cfg weights candSuffix) of ...
``` [3](#0-2) 

By forcing `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs`, the guard takes the `isEmptyPerasWeightSnapshot weights = True` branch, comparing only block numbers (chain length) and ignoring all Peras boosts. This is the direct analog of the OracleMaker bug: the guard evaluates the **current** state (block count only) rather than the **full resulting state** (block count + Peras weight boost).

The `PerasWeightSnapshot` is available in the ChainDB and is used correctly in all other chain selection paths: [4](#0-3) 

The actual snapshot is read and passed to `constructPreferableCandidates`, `chainSelection`, and `switchTo`: [5](#0-4) 

Only `checkPreferTheirsOverOurs` uses the empty snapshot.

---

### Impact Explanation

When Peras is active and a candidate chain contains blocks boosted by Peras certificates, the candidate's true total weight (block count + boost) may exceed the current chain's weight even if the candidate is shorter by block count. The `checkPreferTheirsOverOurs` check, ignoring boosts, concludes the candidate is not preferred and throws `CandidateTooSparse`, disconnecting from the peer. The node then remains on its current lighter chain.

This is a **chain selection failure**: the node prefers a non-canonical (lighter) chain over the canonical (heavier, Peras-boosted) chain. In the Peras protocol, weight boosts are the mechanism by which the network achieves faster settlement — a node that ignores them in this critical guard will diverge from the canonical chain under adversarial or even normal network conditions.

This matches the OracleMaker analog precisely: just as the Maker evaluates spread based only on the current position (ignoring the resulting position after a large trade crosses zero), the ChainSync client evaluates chain preference based only on block count (ignoring the resulting Peras-boosted weight), leading to incorrect decisions that expose the node to more risk than intended.

---

### Likelihood Explanation

- **Peras activation**: Peras is implemented in production code and the weight infrastructure is fully wired into chain selection. The `checkPreferTheirsOverOurs` path is exercised whenever a received header is beyond the forecast horizon, which is a normal network condition.
- **Attacker-controlled entry**: Any unprivileged peer can send headers beyond the forecast horizon. No key compromise, stake majority, or privileged access is required.
- **Trigger condition**: The bug manifests whenever the candidate chain has Peras-boosted blocks and the candidate tip is beyond the forecast horizon of the intersection point. This is a realistic scenario during normal syncing or when a peer is slightly ahead.
- **Known issue**: The TODO comment referencing `https://github.com/tweag/cardano-peras/issues/64` confirms the developers are aware the check is incorrect in the Peras context, but the fix has not been applied — the production code still uses `emptyPerasWeightSnapshot`.

---

### Recommendation

Replace `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the actual `PerasWeightSnapshot` obtained from the ChainDB (via `getPerasWeightSnapshot`), consistent with how all other chain selection comparisons are performed. Alternatively, if the TODO's intent is to remove the check entirely (as suggested by the linked issue), the check should be removed rather than left in a broken state that silently ignores Peras boosts.

The fix should mirror the pattern used in `constructPreferableCandidates` and `chainSelectionForBlock`, where the weight snapshot is read atomically from the ChainDB before performing any chain comparison.

---

### Proof of Concept

**Setup**: Peras is active. The current chain has tip at block `N` with no Peras boosts. A peer offers a candidate chain with tip at block `N` (same length) but containing a block boosted by a Peras certificate with weight `B > 0`. The candidate tip is beyond the forecast horizon.

**Execution**:
1. The ChainSync client receives the candidate header beyond the forecast horizon.
2. `checkPreferTheirsOverOurs` is called.
3. `preferAnchoredCandidate cfg emptyPerasWeightSnapshot ourFrag theirFrag` is evaluated.
4. Since `isEmptyPerasWeightSnapshot emptyPerasWeightSnapshot = True`, the comparison uses only `selectView` (block number), finding `ourTip.blockNo == theirTip.blockNo`.
5. `preferCandidate` returns `ShouldNotSwitch EQ` (equal block numbers, no switch).
6. `checkPreferTheirsOverOurs` throws `CandidateTooSparse`, disconnecting from the peer.

**Expected behavior**: With the actual weight snapshot, `weightedSelectView` would compute `wsvTotalWeight = N + B > N`, returning `ShouldSwitch (Heavier ...)`, and the node would remain connected and eventually adopt the heavier chain.

**Result**: The node disconnects from the peer offering the canonical (heavier) chain and remains on the lighter fork, violating Peras chain selection invariants. [6](#0-5) [7](#0-6) [3](#0-2)
