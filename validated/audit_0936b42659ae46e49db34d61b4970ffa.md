### Title
Unconditional Peras Certificate Acceptance Bypasses All Validation, Enabling Adversarial Chain-Selection Weight Injection - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `validatePerasCert` implementation is a stub that unconditionally accepts every inbound `PerasCert` without performing any cryptographic or structural validation. Any unprivileged peer can send a crafted certificate for an arbitrary block in an arbitrary round; the certificate is stored in `PerasCertDB`, its boost weight is reflected in `getWeightSnapshot`, and `preferAnchoredCandidate` uses that weight to drive chain selection. This lets a single malicious peer inject a weight boost onto any volatile block and cause an honest node to switch to a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` type-class instance for all blocks contains a degenerate `validatePerasCert` that always returns `Right`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature, no round-number bounds, no boosted-block existence check, no committee-membership proof — nothing is verified. The same instance also stubs `validatePerasVote` to only perform a stake-distribution lookup, skipping all cryptographic vote-signature verification:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
``` [2](#0-1) 

This stub is wired into the live inbound-certificate pipeline. `processCerts` in the object-diffusion layer calls `validatePerasCert mkPerasParams` directly:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          (validatePerasCert mkPerasParams)   -- ← stub, always Right
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [3](#0-2) 

`processCerts` partitions results and only rejects a batch when `validateCert` returns `Left`. Because the stub never returns `Left`, every certificate from every peer is accepted and forwarded to `addPerasCertAsync`: [4](#0-3) 

`addPerasCertAsync` enqueues the certificate for the chain-selection background thread, which calls `PerasCertDB.addCert`. `addCert` updates the in-memory weight snapshot (`getWeightSnapshot`): [5](#0-4) 

`getWeightSnapshot` is consumed by `preferAnchoredCandidate` during every chain-selection comparison:

```haskell
| otherwise =
    case AF.intersect ours cand of
      ...
      Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
        case preferCandidate
          (projectChainOrderConfig cfg)
          (weightedSelectView cfg weights oursSuffix)
          (weightedSelectView cfg weights candSuffix) of
``` [6](#0-5) 

The weight snapshot is also read by the BlockFetch `readChainComparison` path, which governs which candidate chains are downloaded: [7](#0-6)

### Impact Explanation

An adversary who can connect as a peer and send a single crafted `PerasCert` message can:

1. Boost any volatile block (including one on an adversarial fork) by `perasWeight` (currently 15 block-lengths worth of weight).
2. Cause `preferAnchoredCandidate` to return `ShouldSwitch` for a fork that would otherwise lose chain selection.
3. Make the honest node permanently adopt the adversarially-chosen chain, constituting a chain-selection safety failure.

Because the boost is applied to the `PerasWeightSnapshot` that is also used by the BlockFetch plausibility check, the node will also download blocks on the adversarial fork, compounding the effect.

This matches the allowed impact: **Critical — bypass of Peras certificate checks enabling unauthorized certificate acceptance**, and **High — chain-selection bug letting an unprivileged peer make an honest node prefer a non-canonical chain**.

---

### Likelihood Explanation

- The object-diffusion mini-protocol for Peras certificates is reachable by any connected peer without authentication.
- The attacker needs only to craft a `PerasCert` with a `pcCertBoostedBlock` pointing to a block on their fork and send it over the wire.
- No stake, no keys, no prior knowledge beyond the target block hash is required.
- The stub is the **only** implementation of `validatePerasCert` in the codebase (the `BlockSupportsPeras` instance is a catch-all `instance StandardHash blk => BlockSupportsPeras blk`). [8](#0-7) 

---

### Recommendation

1. **Implement real certificate validation** in `validatePerasCert`: verify the aggregate BLS/committee signature, check that `pcCertRound` is within the valid window, and confirm that `pcCertBoostedBlock` refers to a known volatile block.
2. **Implement real vote validation** in `validatePerasVote`: verify the cryptographic vote signature against the voter's registered key, not merely a stake-distribution lookup.
3. Until real validation is in place, **gate the Peras object-diffusion mini-protocol** so that it is not activated on production nodes (feature-flag or protocol-version negotiation).
4. Track the open issues (`cardano-peras/issues/120`, `cardano-peras/issues/73`) as security-blocking items, not merely correctness TODOs.

---

### Proof of Concept

**Attacker-controlled entry path:**

```
peer connects via node-to-node protocol
  → Peras cert object-diffusion server handler
  → makePerasCertPoolWriterFromChainDB.opwAddObjects [craftedCert]
  → processCerts ... (validatePerasCert mkPerasParams) ...
      validatePerasCert mkPerasParams craftedCert
        = Right (ValidatedPerasCert { vpcCert = craftedCert
                                    , vpcCertBoost = PerasWeight 15 })
      -- no Left branch ever reached; cert passes
  → addPerasCertAsync chainDB (WithArrivalTime now validatedCert)
  → PerasCertDB.addCert updates weight snapshot
  → preferAnchoredCandidate reads boosted weights
  → ShouldSwitch fires for adversarial fork
  → switchTo commits adversarial chain to ChainDB
``` [9](#0-8) [10](#0-9)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
