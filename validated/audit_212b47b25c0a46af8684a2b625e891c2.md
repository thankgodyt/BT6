Audit Report

## Title
`init_transfer` Missing Normalization Guard Causes Permanent Freezing of Bridged Funds - (File: `near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer` locks tokens after only checking `fee < amount`, without verifying that `normalize_amount(amount - fee) > 0`. `sign_transfer` enforces this normalization check and panics when the result is zero, but by that point tokens are already locked. Because no cancel or refund path exists for an unsigned `TransferMessage`, any transfer whose `amount - fee` is below the normalization threshold results in permanently frozen funds.

## Finding Description
`sign_transfer` computes the destination-chain amount via floor division and enforces a non-zero guard before calling the MPC signer:

```rust
// near/omni-bridge/src/lib.rs L475-485
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
``` [1](#0-0) 

`normalize_amount` performs floor division by `10^(origin_decimals - decimals)`:

```rust
// near/omni-bridge/src/lib.rs L2784-2786
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [2](#0-1) 

The docstring at L2781-2783 explicitly acknowledges that when `fee = 0`, dust "stays locked/burned," but does not address the case where the *entire* `amount - fee` normalizes to zero. [3](#0-2) 

`init_transfer` only enforces:

```rust
// near/omni-bridge/src/lib.rs L554-557
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
``` [4](#0-3) 

Tokens are locked (or burned for bridge tokens) immediately after this check inside `init_transfer_internal`. The `require!(amount_to_transfer > 0, ...)` in `sign_transfer` fires before the MPC call at L508, so `sign_transfer_callback` is never reached and `remove_transfer_message` is never called. [5](#0-4) 

`sign_transfer_callback` calls `remove_transfer_message` only on a successful MPC signature when `fee.is_zero()`: [6](#0-5) 

Since `sign_transfer` panics before the MPC call, this callback path is unreachable for the affected transfer. No other public function removes the stuck `TransferMessage` or refunds the locked tokens.

## Impact Explanation
Permanent freezing of bridged funds — a Critical impact under the allowed scope. A user's tokens are locked in the bridge contract with no recovery path: `sign_transfer` will always reject the transfer, no cancel/refund function exists, and `update_transfer_fee` cannot reduce the fee to make `amount - fee` larger (it only permits fee increases). The locked tokens are irrecoverable.

## Likelihood Explanation
Any unprivileged user can trigger this via the standard `ft_transfer_call` entry point. No special role or access is required. The condition is met for any token where `origin_decimals > decimals` (e.g., a 24-decimal NEAR token bridged to an 18-decimal EVM chain, normalization factor = 10⁶). Any transfer where `amount - fee < 10⁶` base units triggers the freeze. This is a realistic amount for small transfers or tokens with large decimal gaps, and the condition is repeatable across any such token registration.

## Recommendation
Add the normalization guard inside `init_transfer` (or `init_transfer_internal`) before tokens are locked, mirroring the check already present in `sign_transfer`:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

Alternatively, implement a user-facing cancel/refund function that removes the `TransferMessage` and returns locked tokens when no MPC signature has been produced for the transfer.

## Proof of Concept
1. Register a token with `origin_decimals = 24`, `decimals = 18` (normalization factor = 10⁶).
2. User calls `ft_transfer_call` with `amount = 500_000`, `fee = 0`.
3. `init_transfer` passes its only guard: `0 < 500_000` ✓. Tokens are locked.
4. Relayer calls `sign_transfer` for the resulting `TransferMessage`.
5. `normalize_amount(500_000 - 0) = 500_000 / 1_000_000 = 0` (floor division).
6. `require!(0 > 0, BridgeError::InvalidAmountToTransfer)` panics — before the MPC call.
7. `sign_transfer_callback` is never invoked; `remove_transfer_message` is never called.
8. The `TransferMessage` remains in storage; the 500,000 tokens are permanently frozen with no recovery path.
