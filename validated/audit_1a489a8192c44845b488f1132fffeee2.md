### Title
Unconditional `validatePerasCert` Stub Allows Any Peer to Inject Arbitrary Peras Certificates and Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` (success) for every certificate it receives, performing zero cryptographic or semantic checks. This stub is wired directly into the production certificate ingestion path (`makePerasCertPoolWriterFromChainDB`). Any unprivileged peer can therefore craft and send a `PerasCert` for an arbitrary block, have it accepted as "validated," and trigger chain selection for that block with a full Peras weight boost — without holding any committee key or stake.

---

### Finding Description

**Root cause — stub validation always succeeds:**

In `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`, the catch-all `BlockSupportsPeras` instance (the only instance in the repository) implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

No signature check, no committee membership check, no round-number sanity check — the function wraps the raw, peer-supplied `PerasCert` in a `ValidatedPerasCert` and returns it as valid unconditionally. [1](#0-0) 

**Production wiring — stub is called on every inbound certificate:**

`makePerasCertPoolWriterFromChainDB` in `MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs` is the production writer used by the node's object-diffusion layer. It passes `validatePerasCert mkPerasParams` — which resolves to the stub above — as the validation callback to `processCerts`:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

**`processCerts` accepts every certificate that passes the stub:**

`processCerts` partitions validation results; because the stub always returns `Right`, every certificate is placed in the "all valid" branch and forwarded to `addCert`: [3](#0-2) 

**Chain selection is triggered for the boosted block:**

`chainSelSync` in `ChainSel.hs` processes the accepted certificate. If the boosted block is in the VolatileDB and not on the current chain, it calls `chainSelectionForBlock` for that block, giving it the full `perasWeight` boost: [4](#0-3) 

The `addPerasCertAsync` API comment confirms the intended security consequence: *"If this leads to a fork to be weightier than our current selection, this will trigger a fork switch."* [5](#0-4) 

---

### Impact Explanation

Peras certificates exist specifically to boost a block's weight in chain selection beyond what its slot position alone would provide. The `perasWeight` boost is designed to make a certified block's chain preferred over competing forks. By bypassing `validatePerasCert`, any peer — without any stake, committee membership, or cryptographic key — can:

1. Craft a `PerasCert` pointing to any block hash in the VolatileDB.
2. Send it to a target node via the object-diffusion mini-protocol.
3. Have the node accept it as `ValidatedPerasCert` with full `perasWeight`.
4. Trigger `chainSelectionForBlock` for that block, potentially causing the node to switch to an adversarial fork that would otherwise lose chain selection.

This is a **Critical** bypass of Peras certificate/vote verification: an unprivileged peer can cause unauthorized certificate acceptance and manipulate chain selection, matching the "bypass of certificate/vote verification checks that enables unauthorized certificate acceptance" impact class.

---

### Likelihood Explanation

The vulnerability is reachable by any peer connected to the node's object-diffusion endpoint. No stake, no committee key, and no prior chain knowledge beyond a valid block hash in the VolatileDB is required. The stub is the only `validatePerasCert` implementation in the repository (no more-specific Cardano block instance overrides it), and it is unconditionally wired into the production `makePerasCertPoolWriterFromChainDB` path. The TODO comment and linked issue (`cardano-peras/issues/120`) confirm this is an acknowledged placeholder, not a deliberate design choice, meaning the guard is simply absent.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
- Verifies the aggregate BLS signature over `(roundNo, boostedBlock)` against the aggregate public key of the claimed voters.
- Checks that each claimed voter seat index is within bounds and corresponds to a committee member with non-zero stake.
- Verifies that the certificate's round number is within the acceptable window (not stale, not from the future).
- Rejects certificates whose `boostedBlock` hash does not correspond to a known, valid block.

Until the real implementation is in place, the stub should at minimum return `Left PerasValidationErr` (reject all) rather than `Right` (accept all), so that the production node does not process peer-supplied certificates at all while the feature is incomplete.

---

### Proof of Concept

1. Connect to a target node's object-diffusion port.
2. Identify a block hash `H` present in the node's VolatileDB (obtainable via ChainSync).
3. Construct a `PerasCert { pcCertRound = <any round>, pcCertBoostedBlock = H }`.
4. Send the certificate via the Peras certificate object-diffusion mini-protocol.
5. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })`.
6. `addPerasCertAsync chainDB` enqueues the certificate.
7. `chainSelSync` processes it: if `H` is not on the current chain and is in the VolatileDB, `chainSelectionForBlock` runs with the full Peras weight boost for the chain containing `H`.
8. If the boosted chain's weighted length now exceeds the current selection, the node switches forks — driven entirely by the attacker's unauthenticated certificate.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
