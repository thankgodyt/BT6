### Title
Stub `validatePerasCert` Unconditionally Accepts All Inbound Peras Certificates, Enabling Chain Selection Manipulation by Any Peer - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production inbound certificate processing path (`makePerasCertPoolWriterFromChainDB`) calls `validatePerasCert` on every peer-supplied `PerasCert`, but the only deployed instance of `validatePerasCert` is a stub that unconditionally returns `Right` for every input. No cryptographic or semantic check is performed. Any unprivileged peer can therefore inject arbitrary Peras certificates that boost attacker-chosen blocks, causing the receiving node to store those certificates and trigger chain selection toward a non-canonical fork.

---

### Finding Description

**Root cause — stub validation always succeeds.**

In `SupportsPeras.hs`, the sole deployed `BlockSupportsPeras` instance (the "degenerate instance for all blks to get things to compile") implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

Every `PerasCert` received from any peer is unconditionally promoted to a `ValidatedPerasCert` with full boost weight. No committee membership, quorum proof, BLS signature, round-number range, or boosted-block validity is checked.

**Production code path that consumes this stub.**

`makePerasCertPoolWriterFromChainDB` — the writer used in production — passes this stub directly as the `validateCert` argument to `processCerts`:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

**`processCerts` — check-then-act with a check that never rejects.**

`processCerts` reads the current DB state atomically, filters out already-known rounds, calls `validateCert` on the remainder, and — because the stub always returns `Right` — immediately calls `addCert` on every certificate in the batch:

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (...) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _) -> throw (PerasCertValidationError errs)
``` [3](#0-2) 

The `(errs, _)` branch is unreachable because `validateCert` never produces a `Left`.

**Downstream effect — chain selection triggered for attacker-chosen block.**

`addCert` resolves to `ChainDB.addPerasCertAsync`, which enqueues a `ChainSelAddPerasCert` message. `chainSelSync` then:
1. Stores the certificate in `PerasCertDB` (atomically, so it persists).
2. Looks up the boosted block in the `VolatileDB`.
3. If the block is present, calls `chainSelectionForBlock`, which re-evaluates all candidate fragments using the updated `PerasWeightSnapshot` — now inflated by the attacker's boost. [4](#0-3) 

**Secondary effect — voting precondition poisoned.**

`getLatestCertSeen` is updated whenever a certificate with a higher round number is stored. This field is the direct input to voting rule VR-1A, which requires the voter to have seen the certificate for the immediately preceding round. An attacker can inject a certificate for a far-future round, making VR-1A permanently unsatisfiable for the honest node until the chain catches up. [5](#0-4) [6](#0-5) 

---

### Impact Explanation

**Chain selection manipulation (High).** A peer that has already diffused a valid block `B` on a minority fork can send a crafted `PerasCert{pcCertRound=R, pcCertBoostedBlock=point(B)}`. The certificate is accepted without any proof of quorum. The `PerasWeightSnapshot` is updated to include the boost for `B`, and `chainSelectionForBlock` is invoked. Because Peras weight is additive on top of chain length, even a short minority fork can become "heavier" than the honest chain, causing the node to roll back and switch forks.

**Peras voting disruption (Medium).** Injecting a certificate for a round far ahead of the current round poisons `getLatestCertSeen`, breaking VR-1A for the honest node and silencing its votes for an extended period.

Both effects are reachable by any peer connected via the Object Diffusion mini-protocol, with no stake, no keys, and no prior relationship with the target node.

---

### Likelihood Explanation

The Object Diffusion mini-protocol is a standard node-to-node protocol; any peer that completes the handshake can submit certificate batches. The attack requires only knowledge of a block hash present in the target node's VolatileDB (obtainable via ChainSync) and the ability to craft a `PerasCert` struct (a plain CBOR-serialised pair of `PerasRoundNo` and `Point blk`). No cryptographic material is needed. The attack is executable by any node operator running a modified client.

The only mitigating factor is that Peras is disabled by default; nodes that have explicitly enabled it are immediately exposed.

---

### Recommendation

1. **Block deployment until real validation is wired in.** The stub must not be reachable from the production inbound path. Until `validatePerasCert` performs actual committee-membership and quorum-proof verification, `makePerasCertPoolWriterFromChainDB` should reject all inbound certificates (return a hard error or silently drop) when Peras is in its current stub state.

2. **Implement `validatePerasCert` per the Peras specification.** The real implementation must verify: (a) the certificate's round number is within the current epoch's valid range; (b) the boosted block point is a known, valid block; (c) the quorum proof (BLS aggregate signature or equivalent) is valid against the registered committee for that round.

3. **Add a type-level or runtime guard** that prevents `ValidatedPerasCert` values from being constructed by any path other than a fully-implemented `validatePerasCert`, analogous to how `ValidatedPerasVote` is gated on stake-distribution lookup.

---

### Proof of Concept

**Setup:** Two nodes, A (honest, Peras enabled) and B (attacker). Node B has previously diffused block `X` (on a minority fork) to node A, so `X` is in A's VolatileDB.

**Steps:**

1. Node B connects to node A via the Object Diffusion mini-protocol for Peras certificates.
2. Node B sends a single-element batch: `[PerasCert { pcCertRound = currentRound, pcCertBoostedBlock = point(X) }]`.
3. Node A's `processCerts` reads `alreadyInDb` (does not contain `currentRound`), calls `validatePerasCert mkPerasParams cert` → `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams })`.
4. `addCert` is called → `ChainDB.addPerasCertAsync` enqueues `ChainSelAddPerasCert`.
5. `chainSelSync` stores the certificate in `PerasCertDB`, looks up `X` in VolatileDB (found), calls `chainSelectionForBlock` for `X`.
6. `constructPreferableCandidates` now computes the weight of the fork containing `X` as `blockNo(X) + perasWeight`, which exceeds the honest chain's weight `blockNo(tip)` if the boost is large enough.
7. Node A switches to the minority fork containing `X`.

**Expected outcome without the bug:** Step 3 returns `Left (PerasValidationErr ...)`, the batch is rejected, and node A disconnects from B.

**Actual outcome:** Node A accepts the certificate and may switch chains.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.

      throw (PerasCertValidationError errs)

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
