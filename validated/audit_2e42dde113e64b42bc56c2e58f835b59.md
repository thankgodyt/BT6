Audit Report

## Title
Silent Swallowing of Failed `mint`/`ft_transfer` Permanently Loses Bridged Funds in `fin_transfer_send_tokens_callback` — (File: `near/omni-bridge/src/lib.rs`)

## Summary
When a cross-chain transfer (EVM/Solana/Starknet → NEAR) is finalized with no message payload, `fin_transfer_send_tokens_callback` calls `is_refund_required(false)`, which returns `false` unconditionally without ever inspecting the NEAR promise result. If the underlying `mint` or `ft_transfer` call fails, the callback silently takes the success path, emits `FinTransferEvent`, and leaves the transfer permanently finalized — while the recipient receives nothing and the source-chain tokens are already burned or locked.

## Finding Description

**Step 1 — Transfer is permanently finalized before tokens are sent.**

In `process_fin_transfer_to_near`, `add_fin_transfer` is called at line 1875 before `send_tokens` is dispatched. The transfer ID is recorded as finalized at this point with no rollback unless `remove_fin_transfer` is explicitly called later.

**Step 2 — Callback is chained with `is_ft_transfer_call = !msg.is_empty()`.**

At lines 1957–1977, `send_tokens` is called and `fin_transfer_send_tokens_callback` is chained. When the transfer carries no message, `msg` is empty, so `is_ft_transfer_call = false` is passed to the callback.

**Step 3 — Root cause: `is_refund_required(false)` never reads the promise result.**

```rust
// near/omni-bridge/src/lib.rs L1800-1803
} else {
    // Not ft_transfer_call: don't refund
    false
}
```

When `is_ft_transfer_call` is `false`, the function returns `false` immediately without calling `env::promise_result_checked`. A failed `mint` or `ft_transfer` promise is completely ignored.

**Step 4 — Callback takes the success path unconditionally.**

Because `is_refund_required` returns `false`, the `if` branch at line 1702 (which contains `remove_fin_transfer` and `FailedFinTransferEvent`) is never entered. The `else` branch at line 1719 runs instead: fees are paid and `FinTransferEvent` is emitted, signaling success to all observers.

**Step 5 — No recovery path exists.**

`remove_fin_transfer` at line 1714 is the only mechanism to un-finalize a transfer. It is gated entirely behind `is_refund_required` returning `true`. With `is_ft_transfer_call = false`, this is structurally unreachable regardless of the actual token-transfer outcome.

## Impact Explanation
This is a **Critical** impact matching "Permanent freezing/loss of bridged funds." The source-chain tokens are burned or locked at `initTransfer` time on EVM/Solana/Starknet. If the NEAR-side `mint` or `ft_transfer` fails and the callback silently marks the transfer as finalized, the transfer ID can never be re-submitted (it is already recorded as finalized), the source-chain tokens cannot be recovered, and the recipient receives nothing. The loss is permanent and irrecoverable.

## Likelihood Explanation
Any condition that causes the token contract's `mint` or `ft_transfer` call to fail triggers this path. Realistic conditions include: the token contract being paused or rate-limited, a storage exhaustion panic inside the token contract, a token contract upgrade that introduces a regression, or a native token contract that enforces additional transfer restrictions. The bridge does not control third-party native token contracts. A relayer submitting a valid proof is the only actor needed; no privileged access is required. The bug is deterministic and repeatable for every affected transfer.

## Recommendation
`is_refund_required` must inspect the promise result for both the `ft_transfer_call` and the plain `mint`/`ft_transfer` cases. For the `else` branch, check `env::promise_result_checked(0, ...)` and return `true` (refund required) on `Err(_)`:

```rust
} else {
    // Plain mint or ft_transfer: check whether the promise succeeded
    env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT).is_err()
}
```

This ensures that a failed token transfer triggers `remove_fin_transfer`, `revert_lock_actions`, and `FailedFinTransferEvent`, allowing the transfer to be retried or the source-chain funds to be recovered.

## Proof of Concept
1. Deploy the NEAR omni-bridge on a local sandbox.
2. Bind a native NEP-141 token whose contract can be paused (or mock one that panics on `ft_transfer`).
3. Initiate a cross-chain transfer from EVM → NEAR targeting this token with an empty `msg`.
4. Pause the token contract (or configure the mock to panic).
5. Submit a valid finalization proof via `fin_transfer`.
6. Observe: `process_fin_transfer_to_near` records the transfer as finalized, `ft_transfer` panics, `fin_transfer_send_tokens_callback` is invoked with `is_ft_transfer_call = false`, `is_refund_required` returns `false`, and `FinTransferEvent` is emitted.
7. Verify: the transfer ID is permanently in the finalized set; re-submitting the proof is rejected; the recipient balance is unchanged; source-chain tokens are locked/burned with no recovery path.
