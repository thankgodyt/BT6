### Title
Unconditional `validatePerasCert` Stub Bypasses All Peras Certificate Validation, Enabling Unauthorized Chain-Weight Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance implements `validatePerasCert` as a stub that unconditionally returns `Right` for every certificate it receives, performing zero validation. Any unprivileged peer connected via the Peras object-diffusion mini-protocol can inject a crafted `PerasCert` with an arbitrary round number and an arbitrary boosted-block point. The certificate will be accepted, stored in `PerasCertDB`, and used to trigger chain selection with a weight boost, potentially causing an honest node to prefer a fork over the canonical chain.

---

### Finding Description

The `BlockSupportsPeras` class declares `validatePerasCert` as the mandatory gate for accepting inbound certificates: [1](#0-0) 

The universal instance that covers all block types implements this gate as a no-op: [2](#0-1) 

The comment explicitly acknowledges the omission and references a tracking issue (`#120`), but the stub is wired into the production inbound-certificate pipeline via `processCerts`: [3](#0-2) 

`processCerts` calls `validateCert` on every inbound certificate and only rejects a batch when at least one call returns `Left`. Because the stub always returns `Right`, the rejection branch is unreachable: [4](#0-3) 

After acceptance, the certificate is timestamped and forwarded to `ChainDB.addPerasCertAsync`, which stores it in `PerasCertDB` and triggers chain selection for the boosted block: [5](#0-4) 

The weight boost applied is `perasWeight params` (default `PerasWeight 15`), which is added to the total chain weight used in chain selection: [6](#0-5) 

The checks that are supposed to be enforced but are not include: quorum of votes behind the certificate, cryptographic signatures of committee members, validity of the round number relative to the current round, and the minimum age of the boosted block (`perasBlockMinSlots`). None of these are checked.

---

### Impact Explanation

**Critical — Bypass of Peras certificate checks enabling unauthorized chain-weight manipulation.**

A malicious peer can craft a `PerasCert` pointing to any block in the VolatileDB (e.g., a block on a minority fork) and assign it an arbitrary round number. The certificate will be accepted unconditionally, stored, and its weight boost (`PerasWeight 15`) applied to that block during chain selection. Since the security parameter `k` is interpreted as a weight bound (`maxRollbackWeight`), a sufficiently large or repeated injection of fake certificates can push the total weight of a fork past the rollback threshold, causing the honest node to permanently prefer the adversarial chain and be unable to switch back. [7](#0-6) 

Additionally, the accepted certificate updates `shelleyLedgerLatestPerasCertRound`, which feeds into the Peras voting rules (VR-1A, VR-2A), corrupting the node's local view of the latest certified round and potentially suppressing or triggering votes incorrectly. [8](#0-7) 

---

### Likelihood Explanation

**High when Peras is enabled.** The object-diffusion mini-protocol for Peras certificates is a peer-facing network endpoint. Any node that connects to a Peras-enabled node can send crafted certificates. No stake, key material, or privileged access is required — only a network connection. The stub is in a production source file, not a test or mock, and is the only implementation of `validatePerasCert` that is actually wired into the diffusion layer. Peras is currently disabled by default, but the code is present and the attack surface activates as soon as the feature flag is turned on.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real validator that checks at minimum:

1. The certificate's round number is within the valid range relative to the current chain tip.
2. The boosted block's slot satisfies the `perasBlockMinSlots` (L) age requirement.
3. The certificate carries a valid quorum of cryptographic signatures from the elected committee for that round.
4. The boosted block point is a known, valid block on a chain the node has already validated.

The `PerasParams` constraints that are currently only documented in comments (e.g., `perasCertArrivalThreshold < perasRoundLength`, `perasIgnoranceRounds < perasCooldownRounds`) should also be enforced at construction time in `mkPerasParams` or via a smart constructor, analogous to the fix applied in the Audius report where `_updateDecreaseStakeLockupDuration` was made to enforce `decreaseStakeLockupDuration > votingPeriod + executionDelay`. [9](#0-8)

### Proof of Concept

**Private-testnet sequence with Peras enabled:**

1. Enable Peras on a local two-node testnet (node A = honest, node B = attacker).
2. Node B constructs a `PerasCert` with:
   - `pcCertRound = PerasRoundNo 9999` (far-future round, no quorum ever formed)
   - `pcCertBoostedBlock = blockPoint forkBlock` where `forkBlock` is a block on a minority fork already in node A's VolatileDB
3. Node B sends this certificate to node A via the Peras object-diffusion mini-protocol.
4. Node A's `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{vpcCertBoost = PerasWeight 15}` unconditionally.
5. The certificate is stored in `PerasCertDB` and `addPerasCertAsync` is called.
6. `chainSelSync` triggers chain selection for `forkBlock`; the fork's total weight is now `length(fork) + 15`, which may exceed the honest chain's weight.
7. Node A switches to the fork.

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
```

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```

```haskell
      perasIgnoranceRounds =
        PerasIgnoranceRounds 487

        PerasCertArrivalThreshold 30
    , perasRoundLength =
        PerasRoundLength 90
    , perasWeight =
        PerasWeight 15
```
