### Title
Silent Permanent Token Lock in `safe_mint` When Recipient Has No Storage Registration — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

The `safe_mint` function in the nBTC token contract mints tokens to the bridge's own balance (`bridge_id`) before checking whether the recipient has storage registered. If the recipient has no storage, the function silently returns `U128(0)` — leaving the minted tokens permanently stuck in the bridge's nBTC balance with no per-user accounting, no `lost_found` entry, and no recovery path for the user.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, `safe_mint` executes in this order:

1. `self.token.internal_deposit(&self.bridge_id, amount.into())` — unconditionally mints `amount` nBTC into the bridge contract's own token balance.
2. `if self.token.accounts.get(&account_id).is_none() { return PromiseOrValue::Value(U128(0)); }` — if the recipient has no storage registered, the function returns `U128(0)` without transferring anything to the user. [1](#0-0) 

The tokens are now in `bridge_id`'s nBTC balance. There is no `lost_found` entry created for the user, no event emitted to track the stuck amount, and no recovery function analogous to `claim_lost_found` for this code path.

Contrast this with the standard deposit flow, which routes failures through `transfer_nbtc_callback` and records stuck amounts in `lost_found`: [2](#0-1) 

The `safe_mint` path has no equivalent safety net.

Additionally, in NEAR Protocol, if the bridge's callback panics upon receiving the `U128(0)` return (treating it as a failure), the bridge's own state changes are reverted — but the nBTC contract's `internal_deposit` to `bridge_id` is **not** reverted, since it is a state change in a separate contract. This creates an accounting inconsistency: the deposit UTXO may be un-verified (allowing re-submission), while the nBTC tokens are already minted to the bridge's balance. [3](#0-2) 

---

### Impact Explanation

A user's BTC deposit is consumed (the deposit UTXO is marked as verified on the bridge side), but the corresponding nBTC tokens are minted to the bridge's own balance and never reach the user. There is no mechanism to recover these tokens on a per-user basis. The tokens are permanently locked in the bridge's nBTC balance, constituting a significant permanent loss of user funds.

This maps to the allowed impact: **Critical — Significant loss, theft, destruction, or permanent locking of user or protocol funds.**

---

### Likelihood Explanation

The `safe_deposit` flow (e.g., used by Omni Bridge) requires the caller to attach NEAR for the recipient's storage registration. However:

- The `safe_mint` function itself does **not** enforce that storage was registered — it silently handles the missing-storage case by returning 0.
- A race condition exists: a user's NEAR account storage could be unregistered (via `storage_unregister`) between the storage deposit step and the `safe_mint` call.
- An integrating dApp or relayer could omit the storage registration step, triggering this path for any deposit.
- The recipient's account could simply never have registered storage in the nBTC contract.

Likelihood: **Medium** — requires a specific recipient-side condition (no storage), but this condition is reachable by any user and is not prevented at the `safe_mint` level.

---

### Recommendation

Move the storage check **before** `internal_deposit`, or panic (rather than silently returning 0) when the recipient has no storage, so the entire transaction reverts cleanly. Alternatively, mirror the standard deposit flow: if the transfer cannot be completed, record the amount in `lost_found` keyed by `account_id` so the user can recover via `claim_lost_found`.

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    // Check storage BEFORE minting to bridge_id
    require!(
        self.token.accounts.get(&account_id).is_some(),
        "safe_mint: recipient has no storage registered"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ... rest of transfer logic
}
```

### Proof of Concept

1. Alice sends 0.01 BTC to a deposit address derived from a `DepositMsg` with `safe_deposit = Some(..)` and `recipient_id = alice.near`.
2. Alice's NEAR account `alice.near` has no storage registered in the nBTC contract (or unregisters between steps).
3. The relayer calls `verify_deposit_v2` with the `safe_deposit` message. The bridge verifies the BTC transaction via the Light Client and calls `safe_mint(alice.near, amount, msg)` on the nBTC contract.
4. Inside `safe_mint`: `self.token.internal_deposit(&self.bridge_id, amount)` executes — nBTC tokens are minted to the bridge's balance.
5. `self.token.accounts.get(&alice.near).is_none()` is `true` → function returns `U128(0)`.
6. No `lost_found` entry is created for `alice.near`. No recovery event is emitted.
7. Alice's BTC deposit UTXO is consumed. Alice receives 0 nBTC. The minted tokens are permanently stuck in the bridge's nBTC balance with no per-user recovery path. [1](#0-0) [4](#0-3)

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }

    pub fn transfer_nbtc_callback(&mut self, account_id: AccountId, amount: U128) -> bool {
        let promise_success = is_promise_success();
        let event = Event::TransferNbtc {
            account_id: &account_id,
            amount,
            success: promise_success,
        };
        if !promise_success {
            self.data_mut()
                .lost_found
                .entry(account_id.clone())
                .and_modify(|v| *v += amount.0)
                .or_insert(amount.0);
            Event::LostFoundNbtc {
                account_id: &account_id,
                amount,
            }
            .emit();
        }
        event.emit();
        promise_success
    }
