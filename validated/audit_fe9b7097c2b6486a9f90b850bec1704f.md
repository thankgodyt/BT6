Looking at the production code carefully across `contracts/satoshi-bridge/src/nbtc/migration.rs`, `contracts/satoshi-bridge/src/nbtc/burn.rs`, and `contracts/nbtc/src/lib.rs`.

---

**Tracing the migration snapshot mechanism:**

`internal_migrate_to_new_token` fires `ft_balance_of` queries for every account in the caller-supplied list (including the bridge itself) as async cross-contract calls, then chains the callback `migrate_to_new_token_mint`. [1](#0-0) 

`migrate_to_new_token_mint` reads the promise results (snapshot values) and enforces:

```rust
require!(
    sum == total_supply,
    "Sum of account balances does not match total supply"
);
``` [2](#0-1) 

**This check does NOT prevent the race.** Both `sum` and `total_supply` are snapshot values from the same batch of `ft_balance_of`/`ft_total_supply` calls. A transfer between snapshot execution and callback execution changes no account's snapshot value and does not change total supply, so the check passes with stale data.

---

**Tracing the burn path:**

`verify_withdraw_burn_promise` reads `config.nbtc_account_id` at call time (post-migration = new token) and calls `burn(bridge, burn_amount)` on it. [3](#0-2) 

`burn()` on the token contract calls `internal_withdraw(&self.bridge_id, burn_amount)`, which panics if the bridge's balance on the new token is insufficient. [4](#0-3) 

On burn failure, `verify_withdraw_burn_callback` reverts the pending info to `pending_verify_stage` — the withdrawal can be retried, but if the bridge's new-token balance is permanently below `burn_amount`, every retry fails forever. [5](#0-4) 

---

**Checking whether the bridge is required to be paused during migration:**

`migrate_to_new_token` carries `#[pause(except(roles(Role::DAO)))]`, meaning it can be called even while paused, but there is **no enforcement that the bridge must be paused before migration is initiated**. [6](#0-5) 

If the bridge is not paused, a user can call `ft_transfer_call` on the old token to the bridge (withdrawal initiation) in the 1–2 block window between snapshot execution and the mint callback. This is a public, unprivileged call.

---

**However — the scenario as described does not hold under the actual withdrawal model:**

The withdrawal initiation via `ft_transfer_call` to the bridge calls the bridge's `ft_on_transfer`. Looking at the bridge's token receiver (the `ft_on_transfer` handler at `contracts/satoshi-bridge/src/api/token_receiver.rs`), the bridge records the `burn_amount` in `BTCPendingInfo` at initiation time. The tokens transferred to the bridge stay in the bridge's old-token balance until `verify_withdraw` burns them.

After migration, `nbtc_account_id = new_token`. The bridge's new-token balance = X (stale snapshot, does not include the in-flight withdrawal amount). When `verify_withdraw` fires, it calls `burn(bridge, burn_amount)` on the **new token**, but the bridge only has X there. If `burn_amount > X`, the burn panics permanently.

The `sum == total_supply` guard does not close this window because it compares snapshot-to-snapshot, not snapshot-to-current. [7](#0-6) 

---

**Realistic likelihood assessment:**

- The NEAR block time is ~1 second. The window between snapshot promise execution and the mint callback is at least 1–2 blocks.
- The migration is a privileged operator action, but the race is triggered by an **unprivileged** `ft_transfer_call` on the old token.
- There is no on-chain enforcement requiring the bridge to be paused before `migrate_to_new_token` is called.
- The bridge's pre-existing balance X (accumulated protocol fees) may or may not exceed the in-flight withdrawal amount. If X is small (e.g., early in the bridge's life or after a fee sweep), the burn permanently fails.
- The `verify_withdraw_burn_callback` retry loop cannot self-heal: the bridge's new-token balance can only grow via future BTC deposits generating protocol fees, which is not guaranteed and may never reach the required amount.

---

### Title
Migration balance snapshot race allows in-flight withdrawal to permanently lock user BTC — (`contracts/satoshi-bridge/src/nbtc/migration.rs`)

### Summary
`migrate_to_new_token` snapshots account balances via async `ft_balance_of` calls. A user can transfer tokens to the bridge for withdrawal in the 1–2 block window between snapshot execution and the mint callback. The migration mints the stale (lower) bridge balance to the new token. After migration, `verify_withdraw` calls `burn(bridge, burn_amount)` on the new token, but the bridge's new-token balance is insufficient, causing a permanent panic and locking the user's BTC.

### Finding Description
`internal_migrate_to_new_token` fires `ft_balance_of` queries for all accounts (including the bridge) as async cross-contract calls, then chains `migrate_to_new_token_mint` as a callback. [1](#0-0) 

`migrate_to_new_token_mint` reads the snapshot results and enforces `sum == total_supply`. This check uses only snapshot values; a transfer between snapshot and callback does not change total supply and does not alter any snapshot value, so the check passes with stale data. [7](#0-6) 

The mint batch mints the stale bridge balance X to the new token. `migrate_to_new_token_resolve` then sets `nbtc_account_id = new_token`. [8](#0-7) 

`verify_withdraw_burn_promise` reads `config.nbtc_account_id` at call time (now the new token) and calls `burn(bridge, burn_amount)`. [3](#0-2) 

`burn()` calls `internal_withdraw(&self.bridge_id, burn_amount)`, which panics if the bridge's new-token balance < `burn_amount`. [4](#0-3) 

On failure, the pending info reverts to `pending_verify_stage` and can be retried, but if the bridge's new-token balance is permanently below `burn_amount`, every retry fails. [5](#0-4) 

### Impact Explanation
The in-flight withdrawal's `burn_amount` is permanently unburnable on the new token. The BTC has already been sent on-chain; the NEAR-side burn can never complete. The user's BTC is locked with no recovery path unless the bridge accumulates enough new-token protocol fees to cover the deficit — which is not guaranteed.

### Likelihood Explanation
- The race window is 1–2 NEAR blocks (~1–2 seconds), which is short but non-zero and exploitable by a motivated user watching the mempool.
- No on-chain guard requires the bridge to be paused before `migrate_to_new_token` is called.
- The `sum == total_supply` invariant check does not close the window.
- The attacker's only required action is a standard public `ft_transfer_call` on the old token.

### Recommendation
1. **Require the bridge to be paused before migration**: Add an on-chain check inside `internal_migrate_to_new_token` that asserts the bridge is in a paused state before firing the snapshot queries.
2. **Re-query bridge balance at mint time**: In `migrate_to_new_token_mint`, re-query the bridge's current balance (not the snapshot) immediately before minting to the new token, or mint the full `total_supply` to the bridge and let it distribute from there.
3. **Drain in-flight withdrawals before migration**: Document and enforce (on-chain) that all pending withdrawals must be finalized before migration begins.

### Proof of Concept
```
1. Bridge has bridge_balance = 0 on old token, total_supply = 1000 (all held by users).
2. MigrationOperator calls migrate_to_new_token(new_token, [bridge, user_a, user_b]).
3. ft_balance_of queries fire: bridge=0, user_a=600, user_b=400, total=1000. sum==total ✓
4. Before migrate_to_new_token_mint callback fires:
   user_a calls ft_transfer_call(bridge, 500, WithdrawMsg) on old token.
   Bridge's old-token balance = 500. user_a's old-token balance = 100.
5. migrate_to_new_token_mint fires with stale values: mints 0 to bridge, 600 to user_a, 400 to user_b on new token.
6. migrate_to_new_token_resolve: nbtc_account_id = new_token.
7. BTC confirms. Relayer calls verify_withdraw for user_a's withdrawal.
8. verify_withdraw_burn_promise calls burn(bridge, 500) on new token.
9. Bridge's new-token balance = 0. internal_withdraw panics. Burn fails permanently.
10. user_a's BTC is locked; withdrawal can never complete.
```
