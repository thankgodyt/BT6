### Title
Unauthorized Refund Redirection — Any Caller Can Hijack an Unfinalized Deposit's Refund to an Attacker-Controlled BTC Address - (File: `contracts/satoshi-bridge/src/refund.rs`, `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

`request_refund` imposes no ownership check on the caller. When a victim's `DepositMsg` was created with `refund_address: None`, any unprivileged NEAR account can submit a refund request for that deposit and supply an arbitrary attacker-controlled BTC address. After `unsafe_refund_timelock_sec` elapses — and only if the DAO/Operator fails to reject — the attacker calls the permissionless `execute_refund` and receives the victim's BTC.

---

### Finding Description

**Root cause — no caller-ownership check in `request_refund`:**

`request_refund` is a public, unpermissioned function. It accepts a `deposit_msg` (which identifies the deposit address) and a caller-supplied `refund_address`. The only guard on `refund_address` is:

```rust
// contracts/satoshi-bridge/src/refund.rs  line 154-159
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
```

When `deposit_msg.refund_address` is `None` (the common case — users rarely pre-set a refund address), this branch is skipped entirely. The caller can pass any BTC address as `refund_address`, and it is stored verbatim in the `RefundRequest`:

```rust
// contracts/satoshi-bridge/src/refund.rs  line 564-574
let refund_request = RefundRequest {
    ...
    refund_address,          // ← attacker-supplied address
    ...
};
```

**`execute_refund` is also permissionless:**

```rust
// contracts/satoshi-bridge/src/api/bridge.rs  line 582-589
pub fn execute_refund(
    &mut self,
    utxo_storage_key: String,
    chain_specific_data: Option<ChainSpecificData>,
) -> PromiseOrValue<()> {
    let timelock_sec = self.resolve_execute_refund_timelock(&utxo_storage_key);
    self.internal_execute_refund(utxo_storage_key, timelock_sec, chain_specific_data)
}
```

No check that the caller matches the original requester. After the timelock, anyone — including the attacker — can trigger execution.

**The refund output is built from the stored (attacker-supplied) address:**

```rust
// contracts/satoshi-bridge/src/refund.rs  line 323-324
let refund_address = refund_request.refund_address.clone();
```

```rust
// contracts/satoshi-bridge/src/refund.rs  line 294-308

    let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
        .expect("Invalid refund address");
    ...

```

The MPC-signed BTC transaction therefore pays the attacker's address.

**Attack scenario (analog to OmnichainStaking substitution):**

| OmnichainStaking | BTC Bridge |
|---|---|
| Attacker stakes their own NFT to get voting power | Attacker observes victim's public `DepositMsg` (emitted by `get_user_deposit_address`) |
| Attacker uses that power to `unstakeToken` victim's NFT | Attacker calls `request_refund(victim_deposit_msg, attacker_btc_addr, ...)` |
| Victim's locked tokens transferred to attacker | After `unsafe_refund_timelock_sec`, attacker calls `execute_refund`; victim's BTC sent to attacker |

Step-by-step:
1. Alice deposits 1 BTC with `deposit_msg = { recipient_id: alice, refund_address: None, ... }`.
2. The relayer fails to finalize the deposit (network issue, censorship, etc.).
3. Bob observes Alice's `deposit_msg` from on-chain events and her BTC transaction on the Bitcoin chain.
4. Bob calls `request_refund(alice_deposit_msg, bob_btc_address, alice_tx_bytes, vout, proof, None)`, paying only the small anti-spam NEAR deposit.
5. The `request_refund_callback` verifies the BTC proof and stores Bob's address as the refund destination.
6. If the DAO/Operator does not call `reject_refund` within `unsafe_refund_timelock_sec`, Bob calls `execute_refund`.
7. The bridge constructs and MPC-signs a BTC transaction paying Bob's address. Alice loses her 1 BTC.

---

### Impact Explanation

If the DAO/Operator fails to reject within the timelock, the result is **direct, irreversible theft of the victim's BTC**. The bridge's MPC key signs a transaction paying the attacker; once confirmed on Bitcoin, the funds cannot be recovered. This matches: *"Critical. Unauthorized minting, reminting, unlocking, release, or claiming of nBTC/nZEC or underlying BTC/ZEC"* and *"Critical. Significant loss, theft, destruction, or permanent locking of user or protocol funds."*

---

### Likelihood Explanation

- **`deposit_msg` is public**: emitted by `get_user_deposit_address` and passed in plaintext to `verify_deposit` by relayers. Any observer can reconstruct it.
- **BTC transactions are public**: the attacker can identify unfinalized deposits by watching the Bitcoin chain for outputs to known bridge deposit addresses.
- **Cost to attacker is low**: only the NEAR anti-spam deposit for `request_refund`, which is small relative to any meaningful BTC deposit.
- **Mitigation is operational, not cryptographic**: the only defense is the DAO/Operator monitoring and calling `reject_refund` within `unsafe_refund_timelock_sec`. Any monitoring gap, misconfiguration, or operator unavailability opens the window.
- **Deposits that are never finalized are a realistic scenario**: relayer downtime, censorship, or bugs can leave deposits unfinalized for extended periods — exactly the window the attacker exploits.

---

### Recommendation

Add a caller-ownership check to `request_refund`. The simplest fix is to require that `env::predecessor_account_id()` matches `deposit_msg.recipient_id` when `deposit_msg.refund_address` is `None`:

```rust
if deposit_msg.refund_address.is_none() {
    require!(
        env::predecessor_account_id() == deposit_msg.recipient_id,
        "Only the deposit recipient can request a refund without a pre-authorized refund address"
    );
}
```

Alternatively, always require `deposit_msg.refund_address` to be set at deposit time (enforced off-chain in the UI/SDK), so the on-chain check always enforces the pre-authorized address path.

    pub(crate) fn resolve_execute_refund_timelock(&self, utxo_storage_key: &str) -> u64 {
        require!(
            env::attached_deposit() >= self.required_balance_for_execute_refund(),
            "Insufficient deposit for storage"
        );
        let caller = env::predecessor_account_id();
        let is_privileged =
            self.acl_has_any_role(vec![Role::DAO.into(), Role::RefundOperator.into()], caller);
        let refund_request: RefundRequest = self
            .data()
            .refund_requests
            .get(utxo_storage_key)
            .expect("Refund request not found")
            .into();
        let config = self.internal_config();
        if refund_request.deposit_msg().refund_address.is_some() {
            // Pre-authorized refund address: privileged users can fast-track.
            if is_privileged {
                0
            } else {
                config.refund_timelock_sec
            }
        } else {
            // Refund address supplied by caller of `request_refund`: longer
            // timelock to give DAO/Operator time to reject suspicious requests.
            config.unsafe_refund_timelock_sec
        }
    }

    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
    }
