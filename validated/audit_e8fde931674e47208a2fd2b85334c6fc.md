### Title
Missing Caller Ownership Check on `sign_btc_transaction` Allows Anyone to Trigger Signing of Any User's Pending Transaction - (File: contracts/satoshi-bridge/src/api/chain_signatures.rs)

### Summary
`sign_btc_transaction` does not verify that `env::predecessor_account_id()` matches the `account_id` stored in the target `BTCPendingInfo`. Any unprivileged NEAR account can call this function against any other user's pending withdrawal or refund transaction, supplying arbitrary `sign_index` and `key_version` values.

### Finding Description
`sign_btc_transaction` is the sole public entry point for advancing a pending transaction from the `PendingSign` stage to a signed state. It fetches the pending info, asserts it is in the pending-sign state, and immediately delegates to `internal_sign_btc_transaction` — but it never checks that the caller is the owner of the pending transaction. [1](#0-0) 

Compare this with `internal_withdraw_rbf`, the user-RBF path, which **does** perform the ownership check: [2](#0-1) 

No equivalent guard exists in `sign_btc_transaction`. The `BTCPendingInfo` struct records the legitimate owner in its `account_id` field: [3](#0-2) 

but this field is never consulted during signing.

### Impact Explanation
An attacker can call `sign_btc_transaction` on any victim's pending transaction and supply an arbitrary `key_version`. If the MPC network accepts the call but produces a signature under the wrong key, the resulting serialised transaction (`tx_bytes_with_sign`) is cryptographically invalid and can never be confirmed on Bitcoin. The bridge has no mechanism to detect this at signing time; it will wait indefinitely for on-chain confirmation that never arrives. The victim's nBTC was transferred to the bridge at withdrawal initiation and is not returned until `verify_withdraw` succeeds — meaning the victim's funds are permanently locked in the bridge without operator intervention. This maps to **Medium — stuck bridge state requiring operator intervention**, and borders on critical if the MPC silently accepts an incorrect `key_version`.

### Likelihood Explanation
The function is publicly callable by any NEAR account with no role restriction and no attached-deposit guard beyond `#[payable]`. The only cost to the attacker is the NEAR gas for the cross-contract MPC call. The `btc_pending_sign_id` values are emitted as on-chain events (`GenerateBtcPendingInfo`), so they are trivially discoverable by any observer. [4](#0-3) 

### Recommendation
Add an ownership assertion at the top of `sign_btc_transaction`, mirroring the pattern already used in `internal_withdraw_rbf`:

```rust
let caller = env::predecessor_account_id();
require!(
    btc_pending_info.account_id == caller,
    "Only the owner can sign this transaction"
);
```

This single guard closes the missing-owner-check gap for all pending-info types (withdraw, refund, RBF cancel).

### Proof of Concept
1. Alice initiates a withdrawal; the bridge emits `GenerateBtcPendingInfo { btc_pending_id: "abc123" }`.
2. Attacker Bob calls `sign_btc_transaction("abc123", 0, 999)` (wrong `key_version`).
3. The bridge forwards the signing request to the MPC contract with `key_version = 999`.
4. The MPC returns a signature under the wrong key; the bridge stores it as `tx_bytes_with_sign`.
5. The signed transaction is invalid on Bitcoin and is never confirmed.
6. `verify_withdraw` is never called; Alice's nBTC remains locked in the bridge indefinitely.
7. No privileged action was required from Bob; he only needed Alice's publicly visible `btc_pending_id`.

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> PromiseOrValue<bool> {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        btc_pending_info.assert_pending_sign();
        if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {
            if !self.check_btc_pending_info_exists(original_tx_id) {
                require!(
                    self.internal_unwrap_mut_account(&btc_pending_info.account_id.clone())
                        .btc_pending_sign_ids
                        .remove(&btc_pending_sign_id),
                    "Internal error"
                );
                self.internal_remove_btc_pending_info(&btc_pending_sign_id);
                return PromiseOrValue::Value(true);
            }
        }
        self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
            .into()
    }
