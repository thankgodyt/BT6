### Title
Unauthenticated `request_refund` Allows Attacker to Redirect Victim's Deposit BTC to Attacker-Controlled Address - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary

`request_refund` is a public, permissionless function. When a victim's `deposit_msg` was constructed without a pre-authorized `refund_address` (i.e., `deposit_msg.refund_address == None`), any attacker who learns the `deposit_msg` can call `request_refund` first with their own BTC address, causing the bridge to store a `RefundRequest` that routes the victim's deposited BTC to the attacker. The DAO can reject the request during the timelock window, but this requires active monitoring and timely response; if the DAO misses the window, the BTC is permanently lost to the attacker.

### Finding Description

The `request_refund` entry point in `contracts/satoshi-bridge/src/api/bridge.rs` carries only `#[payable]` and `#[pause]` attributes — no `#[trusted_relayer]` at the function level and no caller-identity check: [1](#0-0) 

Inside `internal_request_refund`, the only guard on `refund_address` is: [2](#0-1) 

When `deposit_msg.refund_address` is `None` this guard is skipped entirely, so the caller-supplied `refund_address` is accepted verbatim and stored in the `RefundRequest`: [3](#0-2) 

The stored `refund_address` is later used unconditionally as the BTC destination in `finalize_refund_with_psbt`: [4](#0-3) 

The `deposit_msg` needed to mount the attack is publicly broadcast: `get_user_deposit_address` emits a `LogDepositAddress` event containing the full `deposit_msg`: [5](#0-4) 

The duplicate-request guard in `request_refund_callback` means only the **first** caller's `refund_address` is accepted: [6](#0-5) 

### Impact Explanation

If the attacker's `request_refund` call lands before the victim's, the victim's call reverts with "Refund request already exists for this UTXO." After `unsafe_refund_timelock_sec` elapses, anyone (including the attacker) calls `execute_refund`, and the bridge's MPC pipeline constructs and signs a Bitcoin transaction paying the attacker's address. The victim's deposited BTC is permanently transferred to the attacker. This is a direct, complete theft of user funds — **Critical** impact.

### Likelihood Explanation

The attack requires no privileged role. All inputs are publicly observable:
- `deposit_msg` is emitted in a NEAR event by `get_user_deposit_address`.
- `tx_bytes`, `vout`, and the Merkle proof are all readable from the public Bitcoin blockchain.

An attacker passively monitoring NEAR events and the Bitcoin mempool/chain can execute this against every deposit that lacks a pre-authorized `refund_address`. The only mitigation is DAO rejection during the `unsafe_refund_timelock_sec` window, which requires continuous, timely operator vigilance — a human-process dependency, not a code-level guarantee.

### Recommendation

Bind the `refund_address` to the depositor at the time of deposit, not at the time of refund request. Concretely:

1. **Require `deposit_msg.refund_address` to be non-`None`** for any deposit that may later be refunded, so the BTC destination is committed on-chain before the deposit is made and cannot be overridden by a third party.
2. **Alternatively**, restrict `request_refund` so that only the `deposit_msg.recipient_id` (the intended NEAR recipient) can submit a refund request when `deposit_msg.refund_address` is `None`, enforcing `env::predecessor_account_id() == deposit_msg.recipient_id`.

### Proof of Concept

1. Victim calls `get_user_deposit_address` with `deposit_msg = {recipient_id: "victim.near", refund_address: None}`. The bridge emits `LogDepositAddress` containing the full `deposit_msg`.
2. Victim sends 1 BTC to the derived deposit address on Bitcoin.
3. The deposit is never finalized via `verify_deposit` (e.g., wrong amount, relayer delay).
4. Attacker reads the `LogDepositAddress` event, obtains `deposit_msg`, fetches `tx_bytes` and Merkle proof from Bitcoin, and calls:
   ```
   request_refund(
     deposit_msg = {recipient_id: "victim.near", refund_address: None},
     refund_address = "attacker_btc_address",
     tx_bytes = <victim's deposit tx>,
     vout = 0,
     proof = <valid merkle proof>,
     gas_fee = None
   )
   ```
   attaching the required NEAR storage deposit.
5. `request_refund_callback` verifies the proof, finds `deposit_msg.refund_address == None` (no guard), and stores `RefundRequest { refund_address: "attacker_btc_address", ... }`.
6. Victim's subsequent `request_refund` call reverts: "Refund request already exists for this UTXO."
7. After `unsafe_refund_timelock_sec`, attacker calls `execute_refund("txid@0", None)`.
8. `finalize_refund_with_psbt` builds a Bitcoin transaction paying `"attacker_btc_address"` and submits it to the MPC signing pipeline.
9. The signed transaction is broadcast; attacker receives the victim's 1 BTC minus gas fee.

    #[allow(clippy::too_many_arguments)]
    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
