### Title
Re-execution of `execute_refund` Permanently Blocked by Stale `BTCPendingInfo` State — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

The `RefundRequest.executed` flag is explicitly set to `true` and the request is kept alive so that `execute_refund` can be called again to re-create a refund transaction (e.g., after a Zcash consensus branch change). However, `finalize_refund_with_psbt` does not remove the old `BTCPendingInfo` or its ID from the account's `btc_pending_sign_ids` before inserting a new one. On re-execution, `require_pending_sign_capacity` fails because the account is already at its pending-sign limit from the first execution. Because the deposit UTXO was simultaneously inserted into `verified_deposit_utxo` during the first execution, the user can neither complete the refund nor re-deposit, permanently locking their funds.

---

### Finding Description

**State set on first execution — never cleared for re-execution.**

`finalize_refund_with_psbt` is called by `execute_refund` both on the first execution and on every subsequent re-execution (the `executed` flag bypasses the `verified_deposit_utxo` guard in `load_refund_request_for_execute`).

On the **first** call, `finalize_refund_with_psbt`:

1. Calls `require_pending_sign_capacity(&caller)` — passes (account is empty).
2. Inserts a new `BTCPendingInfo` keyed by `btc_pending_id` into `btc_pending_infos`.
3. Inserts `btc_pending_id` into `caller.btc_pending_sign_ids`.
4. Inserts `utxo_storage_key` into `verified_deposit_utxo`.
5. Sets `refund_request.executed = true` and re-saves the request. [1](#0-0) 

On the **second** call (re-execution), `finalize_refund_with_psbt` is entered again with the same `caller`. Step 1 now fails:

```
require_pending_sign_capacity(&caller)
→ pending_sign_count() == 1 >= get_max_pending_sign_txs() == 1
→ panic: "Too many pending sign transactions"
``` [2](#0-1) 

The old `BTCPendingInfo` (for the now-invalid transaction) is never removed before the new one is created. There is no cleanup path: `internal_remove_refund_pending_tx_id` explicitly requires the refund request to be absent before it will remove a pending info entry:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_keys[0]),
    "refund request still active"
);
``` [3](#0-2) 

But the refund request is intentionally kept alive (with `executed = true`) precisely to allow re-execution. So the old `BTCPendingInfo` can never be cleaned up while the request exists, and the request can never be re-executed while the old `BTCPendingInfo` exists — a deadlock.

**The `verified_deposit_utxo` entry compounds the lock.** Inserted during the first `execute_refund`, it blocks both `verify_deposit` and a fresh `request_refund` for the same UTXO:

```rust
require!(
    !self.data().verified_deposit_utxo.contains(&utxo_storage_key),
    "UTXO already verified via deposit"
);
``` [4](#0-3) 

There is no operator-accessible function to remove an entry from `verified_deposit_utxo`. Even if an operator rejects the refund request and clears the stale `BTCPendingInfo`, the UTXO remains permanently blocked from both deposit and refund paths.

---

### Impact Explanation

**Critical — permanent locking of user funds.**

After the first `execute_refund` succeeds and the refund transaction subsequently fails to confirm (e.g., Zcash consensus branch change invalidates the signed transaction), the user's deposited BTC/ZEC is permanently locked:

- `verify_deposit` is blocked by `verified_deposit_utxo`.
- A new `request_refund` is blocked by `verified_deposit_utxo`.
- Re-execution of `execute_refund` is blocked by `require_pending_sign_capacity`.
- Operator cleanup of the stale `BTCPendingInfo` requires rejecting the refund request, which removes the only path to re-execution.
- No function exists to remove the `verified_deposit_utxo` entry without a contract upgrade.

The user's on-chain BTC/ZEC is stranded at the deposit address with no recovery path short of a contract upgrade.

---

### Likelihood Explanation

**Medium.** The scenario requires:

1. A user submits a valid `request_refund` (permissionless, after attaching the required storage deposit).
2. `execute_refund` is called once — permissionless after the timelock elapses.
3. The resulting signed transaction fails to confirm. This is a documented and expected scenario for Zcash (consensus branch changes invalidate transactions), and the `executed` flag was added specifically to handle it.
4. `execute_refund` is called again by the same account — the re-execution the protocol explicitly intends to support.

Steps 1–4 are all reachable by an unprivileged NEAR account. The Zcash consensus-branch-change scenario is not hypothetical; it is the stated motivation for keeping the request alive after execution.

---

### Recommendation

In `finalize_refund_with_psbt`, detect when `refund_request.executed == true` (i.e., this is a re-execution) and, before creating the new `BTCPendingInfo`:

1. Retrieve the old `btc_pending_id` from the existing `BTCPendingInfo` associated with this refund (e.g., by scanning the account's `btc_pending_sign_ids` for a refund-state entry whose PSBT references the same UTXO).
2. Remove the old `BTCPendingInfo` from `btc_pending_infos`.
3. Remove the old `btc_pending_id` from `caller.btc_pending_sign_ids`.

Alternatively, store the `btc_pending_id` directly on `RefundRequest` when it is first executed, so re-execution can look it up and clean it up atomically before inserting the replacement.

Additionally, add an operator function to remove a specific key from `verified_deposit_utxo` (guarded by `DAO` or `RefundOperator` role) to allow recovery from stuck states without a full contract upgrade.

---

### Proof of Concept

```
1. Alice deposits 0.01 BTC to a bridge deposit address.

2. Alice calls request_refund(deposit_msg, refund_address, tx_bytes, vout, proof)
   → Light client verifies inclusion
   → request_refund_callback stores RefundRequest { executed: false, ... }

3. Timelock elapses. Alice calls execute_refund(utxo_storage_key, ...)
   → resolve_execute_refund_timelock: passes (timelock elapsed)
   → load_refund_request_for_execute:
       verified_deposit_utxo.contains(key) == false  → passes
   → finalize_refund_with_psbt:
       require_pending_sign_capacity(&alice)  → passes (0 < 1)
       btc_pending_infos.insert("id_A", ...)  → OK
       alice.btc_pending_sign_ids = {"id_A"}
       verified_deposit_utxo.insert(key)      ← UTXO now locked
       refund_request.executed = true         ← re-execution enabled

4. The Zcash consensus branch changes. The signed transaction for "id_A"
   is invalid on the new branch. Alice cannot broadcast it.

5. Alice calls execute_refund(utxo_storage_key, ...) again
   → resolve_execute_refund_timelock: passes
   → load_refund_request_for_execute:
       verified_deposit_utxo.contains(key) == true
       refund_request.executed == true  → passes (intended re-execution path)
   → finalize_refund_with_psbt:
       require_pending_sign_capacity(&alice)
       → alice.pending_sign_count() == 1 >= limit 1
       → PANIC: "Too many pending sign transactions"

6. Alice tries request_refund again for the same UTXO:
   → request_refund_callback:
       verified_deposit_utxo.contains(key) == true
       → PANIC: "UTXO already verified via deposit"

7. Alice's 0.01 BTC is permanently locked. No recovery path exists
   without a contract upgrade to clear verified_deposit_utxo.
```
