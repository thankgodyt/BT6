### Title
Attacker Can Front-Run `request_refund` to Redirect BTC Refunds to an Attacker-Controlled Address - (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

The `utxo_storage_key` used to key every `RefundRequest` in storage is derived solely from `tx_id` and `vout`, without including the `refund_address`. Because `request_refund` is permissionless and all deposit data is publicly observable on-chain, an attacker can race the legitimate depositor to register a `RefundRequest` for any unfinalized UTXO while supplying an attacker-controlled `refund_address`. The legitimate user's subsequent `request_refund` is then rejected with "Refund request already exists for this UTXO", and after `unsafe_refund_timelock_sec` elapses the attacker can call `execute_refund` to drain the UTXO to their own Bitcoin address.

---

### Finding Description

**Root cause — key excludes `refund_address`**

`generate_utxo_storage_key` builds the map key from only `txid` and `vout`:

```rust
// contracts/satoshi-bridge/src/utils.rs
pub fn generate_utxo_storage_key(txid: String, vout: u32) -> String {
    format!("{}{}{}", txid, UTXO_STORAGE_KEY_TAG, vout.to_string().as_str())
}
```

`refund_address` is stored inside the `RefundRequest` value but plays no role in the key. This is the direct analog of the audited Solana bug where `refund_token` was excluded from the PDA seed hash.

**Permissionless entry point**

`request_refund` carries no caller restriction beyond the `#[pause]` guard:

```rust
// contracts/satoshi-bridge/src/api/bridge.rs  (lines 508-535)
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn request_refund(
    &mut self,
    deposit_msg: DepositMsg,
    refund_address: String,
    tx_bytes: Base64VecU8,
    vout: usize,
    proof: TxInclusionProof,
    gas_fee: Option<U128>,
) -> Promise { ... }
```

Any NEAR account can call it for any UTXO.

**`refund_address` is only validated against `deposit_msg.refund_address` when that field is `Some`**

```rust
// contracts/satoshi-bridge/src/refund.rs  (lines 154-159)
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
```

When `deposit_msg.refund_address` is `None` — the common case for standard deposits — the caller supplies an arbitrary `refund_address` with no on-chain binding to the depositor.

**Duplicate guard fires in the callback, not before the cross-contract call**

The "already exists" check lives in `request_refund_callback`, which runs only after the Light Client cross-contract call resolves:

```rust
// contracts/satoshi-bridge/src/refund.rs  (lines 544-547)
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
```

Once an attacker's callback has committed a `RefundRequest`, the legitimate user's callback will always hit this guard and revert.

**`execute_refund` is also permissionless and uses the stored `refund_address` verbatim**

```rust
// contracts/satoshi-bridge/src/bitcoin_utils/refund.rs  (line 30)
let refund_output = self.build_refund_output(&refund_request.refund_address, refund_amount);
```

After `unsafe_refund_timelock_sec` elapses, anyone — including the attacker — can call `execute_refund`, which builds and signs a PSBT paying the attacker's address.

---

### Impact Explanation

A successful attack redirects the entire deposit UTXO (minus gas fee) to the attacker's Bitcoin address. The legitimate depositor loses their BTC permanently; the bridge's MPC infrastructure signs and broadcasts the attacker-directed transaction. This constitutes a **significant theft of user funds** matching the Critical impact tier.

---

### Likelihood Explanation

All inputs required for the attack are publicly observable:

- The `deposit_msg` is emitted via `Event::LogDepositAddress` when the user generates their deposit address, and is also a parameter of `verify_deposit_v2`.
- The `tx_bytes`, `vout`, and Merkle proof are readable from any Bitcoin full node or block explorer once the deposit transaction confirms.

The attacker simply monitors the Bitcoin chain for deposits to known bridge addresses, constructs the matching `deposit_msg`, and calls `request_refund` with their own `refund_address` before the depositor does. No privileged access is required. The only on-chain mitigation is `unsafe_refund_timelock_sec` plus a manual DAO/Operator `reject_refund` call — an operational control that can be missed, especially under volume or targeted griefing.

---

### Recommendation

Include `refund_address` in the storage key so that each `(utxo, refund_address)` pair is independently addressable, or — more robustly — require that `deposit_msg.refund_address` be set at deposit time and enforce that the `request_refund` caller supplies a matching address. This mirrors the patch described in the reference report: binding the refund destination into the identifier used to locate the request prevents any third party from registering a competing entry for the same UTXO.

---

### Proof of Concept

1. User generates a deposit address via `get_user_deposit_address(deposit_msg)` where `deposit_msg.refund_address = None`. The `Event::LogDepositAddress` event exposes `deposit_msg` publicly.
2. User sends BTC to that address; the deposit transaction confirms on Bitcoin but is never finalized on NEAR (relayer outage, user error, etc.).
3. Attacker observes the confirmed UTXO on-chain, reconstructs `deposit_msg` from the emitted event, and calls:
   ```
   request_refund(deposit_msg, attacker_btc_addr, tx_bytes, vout, proof, None)
   ```
   attaching the required NEAR storage deposit.
4. Light Client verifies inclusion; `request_refund_callback` stores `RefundRequest { refund_address: attacker_btc_addr, … }` under key `{txid}@{vout}`.
5. Legitimate user calls `request_refund` with their own `refund_address`; the callback panics: *"Refund request already exists for this UTXO"*.
6. After `unsafe_refund_timelock_sec` elapses, attacker calls `execute_refund("{txid}@{vout}", None)`.
7. `internal_execute_refund` builds a PSBT paying `attacker_btc_addr` the full `deposit_amount - gas_fee`, the MPC signs it, and the transaction is broadcast — permanently transferring the user's BTC to the attacker. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5)

    pub(crate) fn resolve_execute_refund_timelock(&self, utxo_storage_key: &str) -> u64 {
        require!(
            env::attached_deposit() >= self.required_balance_for_execute_refund(),
            "Insufficient deposit for storage"
        );
        let caller = env::predecessor_account_id();
        let is_privileged =
            self.acl_has_any_role(vec![Role::DAO.into(), Role::RefundOperator.into()], caller);
        let refund_request: RefundRequest = self
            .data()
            .refund_requests
            .get(utxo_storage_key)
            .expect("Refund request not found")
            .into();
        let config = self.internal_config();
        if refund_request.deposit_msg().refund_address.is_some() {
            // Pre-authorized refund address: privileged users can fast-track.
            if is_privileged {
                0
            } else {
                config.refund_timelock_sec
            }
        } else {
            // Refund address supplied by caller of `request_refund`: longer
            // timelock to give DAO/Operator time to reject suspicious requests.
            config.unsafe_refund_timelock_sec
        }
    }

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
