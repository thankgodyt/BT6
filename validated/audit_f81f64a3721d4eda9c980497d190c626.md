Audit Report

## Title
Unchecked Arithmetic Overflow in `denormalize_amount` Permanently Freezes Bridged Funds on Inbound EVM→NEAR Transfers — (File: `near/omni-bridge/src/lib.rs`)

## Summary

`denormalize_amount` performs a bare `u128` multiplication with no overflow guard. With `overflow-checks = true` confirmed in the workspace release profile, a sufficiently large EVM-side transfer amount causes `fin_transfer_callback` to panic and revert on every invocation. Because the EVM tokens are already locked or burned before the proof is submitted, the user's funds are permanently unrecoverable.

## Finding Description

`denormalize_amount` at `near/omni-bridge/src/lib.rs:2776-2779` computes:

```rust
fn denormalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount * (10_u128.pow(diff_decimals))   // ← bare multiplication, no checked_mul
}
``` [1](#0-0) 

This is called unconditionally inside `fin_transfer_callback` at lines 725 and 727:

```rust
amount: Self::denormalize_amount(init_transfer.amount.0, decimals).into(),
fee: Self::denormalize_fee(&init_transfer.fee, decimals),
``` [2](#0-1) 

`denormalize_fee` also delegates to `denormalize_amount`: [3](#0-2) 

The workspace release profile explicitly sets `overflow-checks = true`: [4](#0-3) 

With this flag, any `u128` multiplication that overflows causes a NEAR runtime trap (panic), reverting the entire `fin_transfer_callback` transaction. For a token with `origin_decimals = 24` and `decimals = 18`, `diff_decimals = 6`, and the overflow threshold is `u128::MAX / 10^6 ≈ 3.4 × 10^32` in 18-decimal EVM units (~340 trillion whole tokens). Any EVM `initTransfer` with an amount above this threshold locks/burns the tokens on EVM, and every subsequent relay attempt to NEAR will always panic. There is no admin escape hatch or rescue function.

## Impact Explanation

Permanent, total, unrecoverable loss of bridged funds. Once the EVM transaction is mined, the proof is immutable. Every call to `fin_transfer_callback` with that proof will overflow and revert. This matches the Critical allowed impact: **permanent freezing of bridged funds across EVM→NEAR flows**.

## Likelihood Explanation

Low-to-medium. The overflow threshold in whole tokens is approximately `u128::MAX / 10^origin_decimals`. For tokens with 24 NEAR-side decimals this is ~340 trillion whole tokens — reachable by any unprivileged holder of a high-supply token (e.g. meme tokens). No special role or key is required; the attacker only needs to call the public EVM `initTransfer` function with a sufficiently large balance. The risk increases as more high-supply tokens are registered on the bridge.

## Recommendation

Replace the bare `*` with `checked_mul` and propagate the error:

```rust
fn denormalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount
        .checked_mul(10_u128.pow(diff_decimals))
        .near_expect(BridgeError::AmountOverflow)
}
```

Additionally, add a pre-flight validation in `fin_transfer_callback` that rejects proofs whose denormalized amount would overflow before any state is mutated, so the relayer receives a clean, actionable error rather than a panic.

## Proof of Concept

1. Register a token with `origin_decimals = 24`, `decimals = 18` (`diff_decimals = 6`).
2. On EVM, call `initTransfer` with `amount = u128::MAX / 10^6 + 1`. The EVM transaction succeeds; tokens are locked/burned.
3. A relayer submits the proof to NEAR `fin_transfer`.
4. Inside `fin_transfer_callback`, `denormalize_amount` computes `(u128::MAX / 10^6 + 1) * 10^6`, which overflows `u128`.
5. With `overflow-checks = true` (confirmed in `near/Cargo.toml`): the NEAR runtime traps; the transaction reverts. The proof is valid and can be re-submitted indefinitely — it will always revert. The user's EVM tokens are permanently frozen with no recovery path.
