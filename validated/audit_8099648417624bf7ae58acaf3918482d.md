### Title
Truncation Branch in `internal_safe_verify_deposit_entry` Stores Zeroed `tx_bytes` While `tx_id` Is Computed from Original Transaction, Creating Permanently Inconsistent UTXO State — (`contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

---

### Summary

`internal_safe_verify_deposit_entry` decodes `tx_bytes`, validates the output, computes `tx_id` and `utxo_storage_key` from the original transaction — but then silently replaces `tx_bytes` with `vec![0u8; 300]` (300 zero bytes, not a truncation) before constructing the `UTXO`. The stored UTXO has a `tx_id` derived from the real transaction and `tx_bytes` that is not a valid Bitcoin transaction at all, violating the core invariant that `UTXO.tx_bytes` must re-encode to `UTXO.tx_id`.

---

### Finding Description

In `internal_safe_verify_deposit_entry`, after all validation passes, the following branch fires unconditionally when `tx_bytes.len() > 10000`: [1](#0-0) 

The log message says "truncating to 300 bytes" but the implementation replaces the entire buffer with `vec![0u8; 300]` — 300 zero bytes — which is not a valid Bitcoin transaction encoding. This is not truncation; it is replacement with garbage.

Immediately after, `tx_id` and `utxo_storage_key` are computed from the **original** decoded transaction (the one that was validated): [2](#0-1) 

The `UTXO` struct is then constructed with the zeroed `tx_bytes` but the real `tx_id`: [3](#0-2) 

This UTXO is passed through `PendingUTXOInfo` and, on successful `safe_mint`, stored permanently via `internal_set_utxo`: [4](#0-3) 

The `UTXO` struct stores `tx_bytes` as a first-class field alongside `balance`, `vout`, and `path`: [5](#0-4) 

The invariant that `Transaction::decode(utxo.tx_bytes).compute_txid() == utxo_storage_key` is permanently broken for any UTXO deposited via a >10000-byte transaction.

### Impact Explanation

The stored UTXO has:
- `tx_bytes = vec![0u8; 300]` — not a valid Bitcoin transaction
- `tx_id` = txid of the real 10001-byte transaction
- `balance` = correct satoshi value
- `utxo_storage_key` = derived from the real txid

Any downstream code path that attempts to decode `utxo.tx_bytes` to reconstruct the transaction (e.g., to populate `witness_utxo` in a PSBT for signing, or to verify the output script) will either panic or produce a wrong result. The UTXO is permanently stuck in contract storage — it cannot be spent in a withdrawal because the `tx_bytes` cannot be decoded to a valid transaction. The bridge holds BTC it cannot move.

This matches: **Low — Publicly reachable invariant-violation, stuck-state, or panic-driven fault in production bridge/token paths without direct theft.**

### Likelihood Explanation

The entry function `internal_safe_verify_deposit_entry` only enforces an attached NEAR deposit check: [6](#0-5) 

There is no ACL guard in this function. A caller who can submit a valid Bitcoin transaction with `tx_bytes.len() > 10000` (10001 bytes is sufficient) and a valid output at `vout` can trigger this path. Bitcoin transactions with many inputs or large scripts can legitimately exceed 10000 bytes. The condition is reachable in normal bridge operation.

---

### Recommendation

Replace the truncation branch with a hard rejection:

```rust
require!(
    tx_bytes.len() <= 10000,
    "tx_bytes length exceeds 10000 bytes"
);
```

Do not silently replace `tx_bytes` with zeroed data. If large transactions must be supported, store only the relevant `TxOut` fields (`value` + `script_pubkey`) separately rather than the full raw transaction, and update all downstream consumers accordingly.
