### Title
`batch_clear_invalid_pending_verify_rbf` Batch Griefing via Permissionless Front-Running — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary
`batch_clear_invalid_pending_verify_rbf` is a publicly callable function that iterates over a list of RBF pending-info IDs and panics atomically if any single entry fails validation. Because the companion single-entry function `clear_invalid_pending_verify_rbf` is also permissionless, any unprivileged NEAR account can front-run a batch call by pre-clearing one of its IDs, causing the entire batch to revert. This forces the off-chain program to fall back to individual calls and leaves invalid RBF pending infos stuck in contract storage until manually re-submitted.

### Finding Description

`batch_clear_invalid_pending_verify_rbf` iterates over caller-supplied IDs and delegates each to `internal_clear_invalid_pending_verify_rbf`:

```rust
// contracts/satoshi-bridge/src/api/bridge.rs
#[pause(except(roles(Role::DAO)))]
pub fn batch_clear_invalid_pending_verify_rbf(&mut self, btc_pending_verify_ids: Vec<String>) {
    for btc_pending_verify_id in btc_pending_verify_ids {
        self.internal_clear_invalid_pending_verify_rbf(btc_pending_verify_id);
    }
}
```

`internal_clear_invalid_pending_verify_rbf` panics (reverting the whole transaction) on any of three conditions:

```rust
// contracts/satoshi-bridge/src/btc_pending_info.rs
pub fn internal_clear_invalid_pending_verify_rbf(&mut self, btc_pending_id: String) {
    let btc_pending_info = self.internal_remove_btc_pending_info(&btc_pending_id); // panics: "BTC pending info not exist"
    btc_pending_info.assert_pending_verify();                                       // panics: "Not pending verify stage"
    let original_tx_id = btc_pending_info
        .get_original_tx_id()
        .expect("Not rbf transaction");                                             // panics
    require!(
        !self.data().rbf_txs.contains_key(original_tx_id),
        "Not invalid pending verify rbf"                                            // panics
    );
}
```

Neither `batch_clear_invalid_pending_verify_rbf` nor `clear_invalid_pending_verify_rbf` carries an `#[access_control_any]` guard — only `#[pause(except(roles(Role::DAO)))]`. Both are therefore callable by any unprivileged NEAR account while the contract is unpaused. [1](#0-0) [2](#0-1) [3](#0-2) 

### Impact Explanation

The off-chain program uses `batch_clear_invalid_pending_verify_rbf` to clean up stale RBF pending infos after the original transaction is verified on-chain. The contract comment explicitly states this batch path exists because individual gas limits make per-entry calls impractical at scale:

> "Since there can be many RBFs, removing all RBF pending info at once after verifying the transaction on-chain might not have enough gas. Therefore, the off-chain program uses this interface to perform the cleanup." [4](#0-3) 

When the batch is griefed, invalid RBF `BTCPendingInfo` entries remain in `btc_pending_infos` storage indefinitely until the off-chain program resubmits. While no user funds are directly stolen, this constitutes a publicly reachable stuck-state fault in a production bridge path: storage is not freed, the off-chain cleanup pipeline is disrupted, and repeated griefing can force the operator to intervene manually.

**Impact class: Low** — Publicly reachable stuck-state / panic-driven fault in production bridge paths without direct theft.

### Likelihood Explanation

NEAR transactions are visible in the mempool before finalization. Any unprivileged account can:
1. Monitor for a pending `batch_clear_invalid_pending_verify_rbf` call.
2. Extract one ID from the argument list.
3. Submit `clear_invalid_pending_verify_rbf` with that single ID at a higher priority (NEAR does not have miner-extractable ordering guarantees, but transaction ordering within a block is observable and influenceable).
4. The batch call then hits `"BTC pending info not exist"` and reverts entirely.

The attack costs only the gas for one single-entry call and can be repeated indefinitely at low cost.

### Recommendation

**Short term:** Mirror the pattern already used for deposits — add a `NoThrow` variant of the inner loop that skips (logs) entries that fail validation rather than panicking:

```rust
pub fn batch_clear_invalid_pending_verify_rbf(&mut self, btc_pending_verify_ids: Vec<String>) {
    for id in btc_pending_verify_ids {
        if self.data().btc_pending_infos.contains_key(&id) {
            // attempt cleanup; skip silently on any validation failure
            self.internal_clear_invalid_pending_verify_rbf_nothrow(id);
        }
    }
}
```

**Long term:** Apply the same defensive pattern to all batch state-mutation functions: validate each entry independently and continue processing the remainder rather than aborting the entire batch on a single failure.

### Proof of Concept

1. Off-chain program observes N invalid RBF pending infos and submits:
   `batch_clear_invalid_pending_verify_rbf(["id_A", "id_B", "id_C"])`

2. Attacker sees the pending transaction and immediately submits:
   `clear_invalid_pending_verify_rbf("id_A")`

3. Attacker's transaction executes first; `id_A` is removed from `btc_pending_infos`.

4. The batch transaction executes; on the first iteration `internal_remove_btc_pending_info("id_A")` calls `.expect("BTC pending info not exist")` → panic → entire batch reverts.

5. `id_B` and `id_C` remain in storage. The off-chain program must resubmit, and the attacker can repeat step 2 for `id_B`, then `id_C`, indefinitely. [5](#0-4) [2](#0-1)
