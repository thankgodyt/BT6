### Title
Unvalidated `refund_address` When `deposit_msg.refund_address` Is `None` Enables Frontrunning to Steal BTC Refunds - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary

When a user calls `request_refund` with a `DepositMsg` that has `refund_address: None`, the contract accepts any caller-supplied BTC `refund_address` without any ownership validation. Because `request_refund` is publicly callable and the first valid submission for a given UTXO wins, an attacker can frontrun the legitimate user's transaction — supplying identical proof parameters but substituting their own BTC address — causing the bridge to send the refunded BTC to the attacker.

### Finding Description

`request_refund` in `contracts/satoshi-bridge/src/api/bridge.rs` is a public, permissionless function (no `#[trusted_relayer]` or `#[access_control_any]` on the method itself, unlike `verify_refund_finalize` and `remove_refund_pending_tx_id` in the same impl block which do carry `#[trusted_relayer]`).

The only validation of `refund_address` inside `internal_request_refund` is conditional:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [1](#0-0) 

When `deposit_msg.refund_address` is `None` the `if let` arm is skipped entirely, and the caller-supplied `refund_address` is stored verbatim into the `RefundRequest`:

```rust
let refund_request = RefundRequest {
    ...
    refund_address,   // ← attacker-controlled, never validated
    ...
};
self.data_mut().refund_requests.insert(utxo_storage_key, refund_request.into());
``` [2](#0-1) 

The UTXO key (`{tx_id}@{vout}`) is deterministic from the Bitcoin transaction. A duplicate-submission guard prevents a second `request_refund` for the same UTXO:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [3](#0-2) 

So the first caller to land a valid submission owns the stored `refund_address`. After `unsafe_refund_timelock_sec` elapses, the public `execute_refund` function builds and signs a Bitcoin transaction paying that address via the MPC pipeline. [4](#0-3) 

The `refund_address` stored in the request is used directly to build the refund output:

```rust
pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
    let config = self.internal_config();
    let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
        .expect("Invalid refund address");
``` [5](#0-4) 

### Impact Explanation

A user whose BTC deposit cannot be finalized (e.g., wrong metadata in `DepositMsg`) relies entirely on the refund path to recover their funds. If an attacker frontrunning `request_refund` succeeds, the attacker's BTC address is permanently stored as the refund destination. The legitimate user cannot submit a competing request (duplicate guard), and only DAO/Operator can reject the fraudulent request — a trust-based mitigation, not a code-level guarantee. If the DAO does not act before `unsafe_refund_timelock_sec` expires, anyone (including the attacker) can call `execute_refund` and the BTC is irrecoverably sent to the attacker. This constitutes **significant theft of user funds**.

### Likelihood Explanation

- `request_refund` is publicly callable by any NEAR account with a small attached storage deposit.
- All inputs needed to frontrun (`deposit_msg`, `tx_bytes`, `vout`, `proof`) are visible in the NEAR transaction being frontrun.
- The `deposit_msg.refund_address: None` case is the common path for users who did not pre-specify a refund address (the field is `#[serde(skip_serializing_if = "Option::is_none")]`, so omitting it is the default).
- The only code-level defence is the longer `unsafe_refund_timelock_sec`, which is a window for DAO intervention, not a guarantee. [6](#0-5) 

### Recommendation

When `deposit_msg.refund_address` is `None`, bind the refund address to the NEAR `predecessor_account_id()` of the `request_refund` caller (e.g., require the caller to prove ownership, or store `predecessor_account_id` and only allow that account to later specify the BTC address at `execute_refund` time). Alternatively, make `refund_address` mandatory in `DepositMsg` and always enforce the match, removing the unvalidated branch entirely.

### Proof of Concept

1. Alice sends BTC to a deposit address derived from `DepositMsg { recipient_id: "alice.near", refund_address: None, ... }`. The deposit cannot be finalized (e.g., wrong metadata).
2. Alice constructs a `request_refund` call with her own BTC address `alice_btc_addr` and broadcasts it to the NEAR network.
3. Attacker Bob observes Alice's pending transaction in the NEAR mempool. Bob submits an identical `request_refund` with the same `deposit_msg`, `tx_bytes`, `vout`, and `proof`, but sets `refund_address = "bob_btc_addr"`.
4. Bob's transaction lands first. The contract stores `RefundRequest { refund_address: "bob_btc_addr", ... }` for Alice's UTXO key.
5. Alice's transaction reverts: `"Refund request already exists for this UTXO"`.
6. After `unsafe_refund_timelock_sec` elapses (and assuming DAO does not intervene), Bob (or anyone) calls `execute_refund`. The bridge's MPC pipeline signs a Bitcoin transaction paying Alice's BTC to `bob_btc_addr`.
7. Alice's BTC is permanently transferred to Bob. [7](#0-6) [1](#0-0)

    #[allow(clippy::too_many_arguments)]
    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
