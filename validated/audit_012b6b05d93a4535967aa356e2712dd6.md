### Title
Peras Vote Stake Weight Read from Live Mutable Distribution Instead of Round-Epoch Snapshot, Enabling Certificate Forgery via Late Votes - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasVote.hs`)

---

### Summary

The Peras vote validation pipeline reads the voter's stake weight from a **live, mutable STM reference** (`getStakeDistrSTM`) at the moment a vote arrives for processing, rather than from a snapshot of the stake distribution that was active at the start of the voting round. This is the direct analog of the external report's "finalize-window" bug: just as the Solidity contract read `SBF_BMX.balanceOf(user)` at finalization time instead of epoch-end time, the Ouroboros Consensus node reads `PerasVoteStakeDistr` at vote-arrival time instead of at round-start time. A pool operator whose stake increases across an epoch boundary can send a late vote for a past round and have it validated with the inflated new-epoch stake, potentially pushing the tally over quorum and forging a certificate for a block that should not have been certified.

---

### Finding Description

In `makePerasVotePoolWriterFromChainDB` and `makePerasVotePoolWriterFromVoteDB`, the vote validation callback is:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
```

`getStakeDistrSTM` is an `STM m PerasVoteStakeDistr` — a live mutable reference that reflects the **current** ledger stake distribution, which changes at every epoch boundary. [1](#0-0) 

`validatePerasVote` then embeds the looked-up stake directly into the `ValidatedPerasVote`:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
``` [2](#0-1) 

This `vpvVoteStake` is then accumulated in `updateTargetVoteTally` and compared against the quorum threshold in `votesReachQuorum`: [3](#0-2) [4](#0-3) 

Critically, **neither `processVotes` nor `implAddVote` nor `updatePerasRoundVoteStates` checks that the vote's round number falls within the current or recent epoch**. A vote for any past round is accepted without expiry validation: [5](#0-4) [6](#0-5) 

The `InterEpochVotingCommittee` module acknowledges that votes from previous epochs must be handled, but the stake-distribution binding is never pinned to the round's originating epoch: [7](#0-6) 

---

### Impact Explanation

When a certificate is forged by `updateCandidateVoteState` → `forgePerasCert`, it is stored in the `PerasCertDB` and exposed via `getWeightSnapshot`. The `vpcCertBoost` field adds chain weight to the certified block, directly influencing chain selection. A fraudulently forged certificate — produced by a late vote carrying inflated cross-epoch stake — causes honest nodes to assign extra weight to a block that did not legitimately reach quorum, potentially making them prefer a non-canonical chain. This is a **High** impact chain-selection bug: an unprivileged pool operator can make honest nodes prefer a less-secure chain beyond the intended security assumptions of the Peras protocol. [8](#0-7) [9](#0-8) 

---

### Likelihood Explanation

The attack requires only that a pool operator's delegated stake increases between two consecutive epochs — a routine occurrence on Cardano mainnet as delegators move stake. The attacker must send a vote for a past round after the epoch transition but before the vote is garbage-collected (GC threshold is the immutability window, ~2160 blocks / ~12 hours). No key compromise, admin access, or stake majority is required. The vote diffusion mini-protocol (`ObjectDiffusion`) is publicly reachable by any peer.

---

### Recommendation

1. **Pin the stake distribution to the round's epoch**: When validating a vote for round `r`, determine which epoch `r` belongs to (using `perasRoundLength` and the epoch boundary slot), then look up the stake distribution snapshot for that epoch rather than the current live distribution.

2. **Enforce a round-expiry window**: In `processVotes` / `implAddVote`, reject votes whose `pvVoteRound` is older than the current round minus a configurable tolerance (e.g., the immutability window expressed in rounds). This mirrors the `autoEffectiveEpoch` fix suggested in the external report.

3. **Use `InterEpochVotingCommittee` for epoch-bound validation**: The existing `getVotingCommitteeForElection` already selects between `currEpochVotingCommittee` and `prevEpochVotingCommittee`; extend this to also bind the stake weight used in `validatePerasVote` to the committee's epoch, not the current ledger tip. [10](#0-9)

### Proof of Concept

**Setup**: Two consecutive epochs E and E+1. Pool P has 1% stake in epoch E and 40% stake in epoch E+1 (due to large delegation inflow). Quorum threshold is 75%.

**Steps**:

1. Voting round N occurs during epoch E. Pool P is a committee member with 1% weight. Honest votes accumulate to 74% — just below quorum. No certificate is forged.

2. Epoch E ends; the node's `getStakeDistrSTM` TVar is updated to reflect epoch E+1 stake distribution, where Pool P now holds 40%.

3. Pool P sends a `PerasVote` for round N (targeting the same block as the 74% honest votes) to the node via the vote diffusion mini-protocol.

4. `processVotes` calls `getStakeDistrSTM` inside the STM transaction, reading the **epoch E+1** distribution. `validatePerasVote` looks up Pool P's stake: 40%.

5. `implAddVote` calls `updatePerasRoundVoteStates` with the vote carrying `vpvVoteStake = 40%`. `updateCandidateVoteState` calls `votesReachQuorum`: 74% + 40% = 114% > 75% threshold. `forgePerasCert` is called.

6. The forged certificate is stored in `PerasCertDB`. `getWeightSnapshot` now returns a boost for the certified block. Chain selection on the honest node is influenced to prefer the chain containing that block, even though it never legitimately reached quorum during round N.

-- | This module extends a given voting committee to work across epochs.
--
-- This is needed to support the case of validating an old vote or certificate
-- from a previous epoch arriving too late. In the general case, this means we
-- would need to store an arbitrary number of past voting committee selections.
-- However, since:
--   1. the length of an epoch is much larger than the immutability window, and
--   2. we don't care about validating votes older than the immutability window,
--      it follows that we only need to store the voting committee selection for
--      the current and previous epochs.
--  NOTE: this rationale might need to be revisited if we ever want to support
--  validating votes and certificates older than the immutability window, e.g.,
--  for historical queries.
