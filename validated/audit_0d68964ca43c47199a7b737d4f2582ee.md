### Title
Repeated `execute_refund` Calls Create Unbounded Duplicate Pending Infos for the Same UTXO - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary

`execute_refund` is a public, permissionless function. After the first execution sets `refund_request.executed = true`, the guard in `load_refund_request_for_execute` allows the function to be called again without limit. Each call creates a brand-new `BTCPendingInfo` (with a fresh PSBT and unique pending ID) and inserts it into `btc_pending_infos` and the caller's `btc_pending_sign_ids`, without removing the previous one. The result is an unbounded accumulation of stale pending-refund entries for a single UTXO — a state invariant violation that cannot be cleaned up until after `verify_refund_finalize` completes, requiring operator intervention.

### Finding Description

**Root cause — the re-execution guard is one-sided.**

`load_refund_request_for_execute` intentionally permits re-execution when `executed == true`: [1](#0-0) 

```rust
require!(
    !self.data().verified_deposit_utxo.contains(utxo_storage_key)
        || refund_request.executed,
    "UTXO already verified via deposit, cannot refund"
);
```

The design intent (re-create the refund tx after a consensus branch change) is legitimate, but `finalize_refund_with_psbt` never removes the *previous* `BTCPendingInfo` before inserting a new one: [2](#0-1) 

```rust
require!(
    self.data_mut()
        .btc_pending_infos
        .insert(btc_pending_id.clone(), btc_pending_info.into())
        .is_none(),
    "pending info already exist"
);
```

The uniqueness check is on `btc_pending_id`, which is derived from the PSBT content. Because each call builds a fresh PSBT (potentially with a different fee or timestamp), the IDs differ, so the check never fires for the *same UTXO* being re-submitted.

**Accumulation path.**

Each successful `execute_refund` call:
1. Calls `finalize_refund_with_psbt`, which inserts a new `BTCPendingInfo` into `btc_pending_infos`.
2. Adds the new pending ID to the caller's `btc_pending_sign_ids`.
3. Triggers a new MPC signing request for the same UTXO.
4. Leaves the previous `BTCPendingInfo` untouched. [3](#0-2) 

**Cleanup is blocked until finalization.**

`internal_remove_refund_pending_tx_id` — the only cleanup path — explicitly requires the refund request to be absent before it will remove a pending info: [4](#0-3) 

```rust
require!(
    !self
        .data()
        .refund_requests
        .contains_key(&utxo_storage_keys[0]),
    "refund request still active"
);
```

The refund request is only removed inside `verify_refund_finalize_callback` after on-chain confirmation. Until then, every stale `BTCPendingInfo` is permanently stuck. [5](#0-4) 

**`execute_refund` is fully public.** [6](#0-5) 

No role restriction exists on `execute_refund`. Any NEAR account can call it once the timelock has elapsed, and different accounts can each create their own `BTCPendingInfo` for the same refund request.

### Impact Explanation

- **State invariant violation:** `btc_pending_infos` accumulates multiple entries for a single UTXO. Only one refund transaction can ever confirm on Bitcoin; all others are permanently unconfirmable.
- **MPC resource waste:** Each call triggers a real MPC signing round for a transaction that will never be valid on-chain.
- **Stuck bridge state requiring operator intervention:** Stale entries cannot be removed until `verify_refund_finalize` completes. If the winning refund tx is delayed or the MPC pipeline stalls, the stale entries block the account's `pending_sign_count` quota and require manual operator cleanup via `remove_refund_pending_tx_id`.
- **Pending-sign capacity exhaustion:** Because each call consumes a slot in `btc_pending_sign_ids`, an attacker (or multiple accounts) can exhaust the per-account pending-sign limit, blocking the legitimate refund owner from initiating withdrawals.

This matches the allowed Medium impact: *"stuck bridge state requiring operator intervention."*

### Likelihood Explanation

- `execute_refund` is permissionless and callable by any NEAR account after the timelock.
- The only cost to the attacker is the `required_balance_for_execute_refund()` storage deposit per call.
- The attack is repeatable across different caller accounts, each independently creating a new stale entry.
- No special knowledge or privilege is required beyond knowing the `utxo_storage_key` of an executed refund request (which is publicly observable on-chain via `RefundExecuted` events).

### Recommendation

Before inserting a new `BTCPendingInfo` in `finalize_refund_with_psbt`, store the previous pending ID in `RefundRequest` (e.g., a `pending_tx_id: Option<String>` field) and remove the old entry:

```rust
// In finalize_refund_with_psbt, before inserting the new entry:
if let Some(old_id) = &refund_request.pending_tx_id {
    if self.data().btc_pending_infos.contains_key(old_id) {
        self.internal_remove_btc_pending_info(old_id);
        self.internal_unwrap_mut_account(&caller)
            .btc_pending_sign_ids
            .remove(old_id);
    }
}
// Then insert the new one and update refund_request.pending_tx_id = Some(btc_pending_id.clone());
```

Alternatively, limit re-execution to privileged roles (DAO/Operator) since the "consensus branch change" scenario is an operator-level recovery action, not a user-facing feature.

### Proof of Concept

1. User deposits BTC and calls `request_refund` with a valid proof. The refund request is stored under `utxo_storage_key = "{tx_id}@{vout}"`.
2. Timelock elapses. Attacker account A calls `execute_refund(utxo_storage_key, None)` → `BTCPendingInfo` P1 is created under account A; MPC signs TX1 spending the UTXO; `refund_request.executed = true`.
3. Attacker account B calls `execute_refund(utxo_storage_key, None)` → `BTCPendingInfo` P2 is created under account B; MPC signs TX2 spending the same UTXO.
4. Attacker account C calls `execute_refund` again → P3 created, MPC signs TX3.
5. At most one of TX1/TX2/TX3 can confirm on Bitcoin. The others remain as unconfirmable entries in `btc_pending_infos`.
6. `remove_refund_pending_tx_id` cannot clean up P2 or P3 while the refund request still exists (it is only removed in `verify_refund_finalize_callback`).
7. Accounts B and C have their `pending_sign_count` permanently inflated until finalization, blocking their future withdrawal operations.
