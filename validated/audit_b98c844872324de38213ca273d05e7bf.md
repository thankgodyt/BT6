### Title
Unauthenticated `request_refund` Allows Any Caller to Register an Attacker-Controlled BTC Refund Address, Redirecting User Funds — (File: `contracts/satoshi-bridge/src/api/bridge.rs`, `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`request_refund` is a public, permissionless function. When `deposit_msg.refund_address` is `None`, the caller freely supplies any BTC address as `refund_address`. Because the `deposit_msg` is emitted publicly via `Event::LogDepositAddress` and the BTC transaction is visible on-chain, any attacker can be the first to register a refund request for a victim's unfinalized deposit, substituting their own BTC address. The legitimate user is then permanently blocked from filing their own request for the same UTXO, and after the timelock the BTC is sent to the attacker.

---

### Finding Description

`request_refund` in `contracts/satoshi-bridge/src/api/bridge.rs` carries no `#[trusted_relayer]` or role guard:

```rust
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn request_refund(
    &mut self,
    deposit_msg: DepositMsg,
    refund_address: String,
    ...
) -> Promise {
``` [1](#0-0) 

Inside `internal_request_refund`, the only guard on `refund_address` is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [2](#0-1) 

When `deposit_msg.refund_address` is `None` (the common case — it is an optional field), this block is skipped entirely and the caller-supplied `refund_address` is stored verbatim in the `RefundRequest`:

```rust
let refund_request = RefundRequest {
    ...
    refund_address,   // ← attacker-controlled
    ...
};
self.data_mut()
    .refund_requests
    .insert(utxo_storage_key, refund_request.into());
``` [3](#0-2) 

The `deposit_msg` needed to pass the script-pubkey check is fully public: `get_user_deposit_address` emits it via `Event::LogDepositAddress`:

```rust
Event::LogDepositAddress {
    deposit_msg,
    path,
    deposit_address: deposit_address.clone(),
}
.emit();
``` [4](#0-3) 

Once a refund request exists for a UTXO, the callback enforces a hard uniqueness check that permanently blocks any second request:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [5](#0-4) 

`execute_refund` then builds the refund output paying `refund_request.refund_address` — the attacker's address — and initiates the MPC signing pipeline:

```rust
pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
``` [6](#0-5) 

The `unsafe_refund_timelock_sec` (default 14 days) is the only mitigation — it gives DAO/Operator a window to call `reject_refund`. However, this is an active, manual intervention that is not guaranteed. [7](#0-6) 

---

### Impact Explanation

If the DAO/Operator fails to reject the malicious request within the 14-day window, `execute_refund` is called (by anyone — also permissionless) and the victim's BTC is permanently sent to the attacker's address. The victim has no recourse: their own `request_refund` call will revert with "Refund request already exists for this UTXO," and `verify_deposit` is also blocked because `execute_refund` inserts the UTXO into `verified_deposit_utxo`. This constitutes **permanent, irrecoverable theft of user BTC funds**.

---

### Likelihood Explanation

The attack requires no special privilege. The attacker only needs to:
1. Observe the public `LogDepositAddress` event to obtain `deposit_msg`.
2. Observe the BTC transaction on-chain.
3. Call `request_refund` before the legitimate user does, paying only the storage deposit (`required_balance_for_request_refund()`).

Deposits with `refund_address: None` are the standard case (the field is `skip_serializing_if = "Option::is_none"`). The attacker does not need to race a mempool transaction — NEAR has no public mempool in the Ethereum sense, but the attacker simply needs to submit their call before the victim does, which is straightforward given that unfinalized deposits are observable on-chain for extended periods. The 14-day timelock reduces likelihood only if the DAO/Operator actively monitors every refund request.

---

### Recommendation

Bind the refund address to the depositor's identity at deposit time. Concretely:

1. **Require `deposit_msg.refund_address` to be set** for any refund to be eligible, so the BTC destination is committed to in the deposit address derivation hash and cannot be overridden by a third party.
2. **Alternatively**, record `env::predecessor_account_id()` as the `requester` in `RefundRequest` and restrict `execute_refund` so that only the requester (or DAO/Operator) can execute it, preventing a third party from triggering payout to an address they registered.
3. **At minimum**, add a `#[trusted_relayer]` or equivalent role guard to `request_refund` so that only whitelisted relayers (who are accountable) can file refund requests on behalf of users.

---

### Proof of Concept

1. Alice calls `get_user_deposit_address(DepositMsg { recipient_id: "alice.near", refund_address: None, ... })`. The contract emits `Event::LogDepositAddress` with the full `deposit_msg` and derived BTC address.
2. Alice sends 1 BTC to the derived address. The deposit is never finalized by a relayer.
3. Attacker Bob reads the `LogDepositAddress` event, obtains `deposit_msg` and the BTC `tx_bytes` from the Bitcoin chain.
4. Bob calls `request_refund(deposit_msg, "bob_btc_address", tx_bytes, vout, proof, None)` with sufficient attached NEAR. The Light Client verifies the proof; `request_refund_callback` stores `RefundRequest { refund_address: "bob_btc_address", ... }`.
5. Alice attempts `request_refund(deposit_msg, "alice_btc_address", ...)` — it reverts: `"Refund request already exists for this UTXO"`.
6. After 14 days (`unsafe_refund_timelock_sec`), Bob (or anyone) calls `execute_refund(utxo_storage_key, None)`. The bridge builds a BTC transaction paying 1 BTC (minus gas fee) to `"bob_btc_address"` and submits it to MPC for signing.
7. Alice's 1 BTC is permanently transferred to Bob.
