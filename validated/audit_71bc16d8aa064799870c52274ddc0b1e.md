### Title
Stub `validatePerasCert` Always Accepts Certificates, Enabling Unbounded `PerasWeightSnapshot` Inflation and Chain-Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance ships a `validatePerasCert` stub that unconditionally returns `Right` for every certificate, performing zero cryptographic or quorum verification. Because this is the only instance in the production codebase, any peer can inject arbitrary Peras certificates through the object-diffusion protocol. Each accepted certificate is added to the `PerasCertDB` and immediately reflected in the global `PerasWeightSnapshot` accumulator. An inflated snapshot causes `chainSelection` to prefer non-canonical forks and causes `takeVolatileSuffix` to shrink the volatile window, potentially treating blocks that should be rollback-eligible as immutable — a direct analog to the "global daily limit counter manipulation" class from the reference report.

---

### Finding Description

**Root cause — unconditional certificate acceptance:**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This is the **only** `BlockSupportsPeras` instance in the codebase (the catch-all `instance StandardHash blk => BlockSupportsPeras blk`). No signature, no committee membership check, no quorum proof — every `PerasCert` is stamped `ValidatedPerasCert` with the full configured `perasWeight`. [2](#0-1) 

**Inbound path — `processCerts` calls the stub:**

The object-diffusion inbound handler calls `validateCert` on every received certificate. Because the only available implementation is the stub, the entire batch is accepted unless the round is already in the DB. [3](#0-2) 

**Global accumulator — `PerasWeightSnapshot` inflated without bound:**

`addToPerasWeightSnapshot` uses `Map.insertWith (<>)`, so repeated certificates for the same block accumulate weight without any cap. [4](#0-3) 

**Chain selection reads the snapshot on every block addition:**

```haskell
(succsOf, lookupBlockInfo, curChain, weights) <- atomically $ do
  ...
  <*> (forgetFingerprint <$> Query.getPerasWeightSnapshot cdb)
``` [5](#0-4) 

The snapshot feeds `weightedSelectView`, which computes `wsvTotalWeight = blockNo + weightBoost`. A fork whose tip block has been boosted by injected certificates will appear heavier than the honest chain. [6](#0-5) 

**Immutability boundary corrupted — `takeVolatileSuffix` shrinks:**

```haskell
takeVolatileSuffix snap secParam
  | Map.null $ getPerasWeightSnapshot snap = AF.anchorNewest (unPerasWeight k)
  | otherwise = takeLongestSuffix (totalWeightOfFragment snap) (<= k)
``` [7](#0-6) 

If the attacker boosts blocks on the current chain, `totalWeightOfFragment` exceeds `k` sooner, the volatile suffix shrinks, and blocks that should still be rollback-eligible are treated as immutable. This prevents the node from ever switching to a better chain that forks before those now-"immutable" blocks.

**Pruning does not protect against a live attacker:**

`prunePerasWeightSnapshot` only removes entries strictly older than the immutable tip slot. An attacker who continuously injects certificates for the most recent volatile blocks keeps the snapshot permanently inflated. [8](#0-7) 

---

### Impact Explanation

**Chain selection manipulation (High):** By injecting certificates that boost a non-canonical fork's tip block, an unprivileged peer causes `wsvTotalWeight` of that fork to exceed the honest chain's weight. `chainSelection` then switches to the adversarial fork, accepting an invalid or less-secure chain beyond the intended security assumptions.

**Immutability boundary corruption (High):** By boosting blocks on the current chain, the attacker shrinks `takeVolatileSuffix` below `k` blocks, causing the node to treat volatile blocks as immutable. The node can no longer roll back to adopt a better chain, constituting a durable use of the wrong ledger state without operator fault — matching the "ChainDB/LedgerDB rollback bug" category in the allowed impact scope.

---

### Likelihood Explanation

Any peer reachable via the object-diffusion miniprotocol can send `PerasCert` messages. No stake, no key material, and no prior chain knowledge is required. The attacker only needs to know the `Point` of a block currently in the target node's VolatileDB (obtainable via ChainSync). The attack is repeatable and persistent as long as the connection is maintained.

---

### Recommendation

Replace the stub with a real implementation of `validatePerasCert` that verifies:
1. The certificate's cryptographic signature(s) against the claimed committee members.
2. That the signers are eligible committee members for the stated round (VRF-based sortition check).
3. That the aggregate stake of the signers meets the configured `perasQuorumStakeThreshold`.

Until the real implementation is ready, the inbound `processCerts` handler should reject all certificates at the network boundary (return a validation error unconditionally) rather than accept them all. This is the safer default for an incomplete feature.

### Proof of Concept

1. Connect to a target node via the object-diffusion protocol.
2. Observe (via ChainSync) the `Point` of a block `B` on a minority fork currently in the node's VolatileDB.
3. Craft a `PerasCert { pcCertRound = r, pcCertBoostedBlock = B }` for any round `r`.
4. Send the certificate. `processCerts` calls `validatePerasCert`, which returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }` unconditionally.
5. The certificate is stored in `PerasCertDB`; `addPerasCertAsync` triggers `chainSelectionForBlock` for `B`.
6. `getPerasWeightSnapshot` now returns a snapshot where `B`'s point carries `perasWeight` extra weight.
7. `preferAnchoredCandidate` compares `wsvTotalWeight` of the honest chain against the fork containing `B`; if the boost is large enough (or repeated), the fork wins and the node switches.
8. Repeat step 3–7 with fresh round numbers to keep the snapshot inflated and prevent pruning from catching up. [1](#0-0) [9](#0-8) [4](#0-3) [10](#0-9) [7](#0-6)

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
