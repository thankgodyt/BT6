Audit Report

## Title
Race Condition in `fast_fin_transfer_to_near_callback` Allows Double-Mint of Bridged Tokens — (`near/omni-bridge/src/lib.rs`)

## Summary
`fast_fin_transfer` for NEAR-bound recipients initiates an async cross-contract storage-deposit call before registering the fast transfer in the `fast_transfers` map. During this async window a trusted relayer can submit the normal `fin_transfer` proof, which sees no fast transfer record and mints tokens to the original recipient. When `fast_fin_transfer_to_near_callback` subsequently executes it finds no duplicate in `fast_transfers`, registers the entry, and mints tokens to the same recipient a second time. For deployed (bridged) tokens this is an unauthorized double-mint; for native tokens it drains the bridge's locked balance.

## Finding Description

**Step 1 — `fast_fin_transfer` (lines 748–836):**
The function checks `is_unified_transfer_finalised` (line 778) and, if the transfer is not yet finalized, initiates `check_or_pay_ft_storage` as a cross-contract call (line 812). The fast transfer is **not** inserted into `self.fast_transfers` at this point; that happens only inside the callback.

**Step 2 — async window:**
Between the storage-deposit receipt being created (block N) and `fast_fin_transfer_to_near_callback` executing (block N+1 or later), the contract state contains no entry for this transfer in `fast_transfers`.

**Step 3 — `fin_transfer` / `fin_transfer_callback` (lines 673–746) submitted in the window:**
`fin_transfer` is also `#[trusted_relayer]`. The callback calls `process_fin_transfer_to_near` (line 735), which:
- Calls `add_fin_transfer` → inserts into `finalised_transfers` (line 1875).
- Calls `get_fast_transfer_status` → returns `None` because the fast transfer is not yet registered (line 1879).
- Falls through to the `None` branch (lines 1897–1901) and calls `send_tokens` → **mints tokens to the original recipient** (first mint).

**Step 4 — `fast_fin_transfer_to_near_callback` (lines 838–893) executes:**
There is **no check** for `is_unified_transfer_finalised` or `finalised_transfers` in this callback. It calls `add_fast_transfer` (line 855) — which succeeds because `fast_transfers` has no entry for this ID — and then calls `send_tokens` → **mints tokens to the same recipient again** (second mint).

The `resolve_fast_transfer` burn (line 904) calls `burn_tokens_if_needed` with `.detach()`, which fires-and-forgets against the bridge's own token balance; it does not undo the second mint to the recipient.

## Impact Explanation
For deployed (bridged) tokens `send_tokens` calls `mint` on the token contract (lines 2094–2101). Both `process_fin_transfer_to_near` and `fast_fin_transfer_to_near_callback` call `send_tokens` for the same recipient, resulting in **unauthorized double-minting of bridged funds**. This matches the Critical impact class: *"Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds."*

## Likelihood Explanation
Both `fast_fin_transfer` (via `ft_on_transfer`) and `fin_transfer` require `#[trusted_relayer]`. A single malicious trusted relayer who controls or is the recipient can:
1. Submit the fast transfer (block N).
2. Submit `fin_transfer` with a valid proof in the very next block (block N+1).
3. Collect double the token amount through the recipient account.

The relayer sends X tokens to the bridge and receives 2X tokens back (X from the fast-transfer mint, X from the normal-finalization mint), netting X tokens profit per exploit. The attack is repeatable for every transfer the relayer processes.

## Recommendation
Add a guard at the start of `fast_fin_transfer_to_near_callback` that aborts (and refunds the relayer) if the transfer has already been finalized via the normal path:

```rust
if self.is_unified_transfer_finalised(&fast_transfer.transfer_id) {
    // Refund the relayer and return early
    return <refund promise>;
}
```

Alternatively, register the fast transfer entry **synchronously inside `fast_fin_transfer`** (before the storage-deposit cross-contract call) so that any concurrent `fin_transfer` call will observe the record and redirect tokens to the relayer rather than the original recipient.

## Proof of Concept

**Private-testnet transaction sequence:**

1. Deploy the bridge with a registered trusted relayer account `R` that also controls recipient account `U`.
2. Initiate a cross-chain transfer T (origin chain → NEAR, recipient = `U`, deployed bridged token).
3. From `R`, call `ft_transfer_call` on the bridged token with the `FastFinTransferMsg` for T (triggers `fast_fin_transfer`; storage-deposit receipt is now in-flight, `fast_transfers` is empty for T).
4. In the **immediately following block**, from `R`, call `fin_transfer` with a valid proof for T. Observe: `process_fin_transfer_to_near` finds no fast transfer record, mints `amount_without_fee` tokens to `U`.
5. Allow `fast_fin_transfer_to_near_callback` to execute. Observe: `add_fast_transfer` succeeds, `send_tokens` mints `amount_without_fee` tokens to `U` a second time.
6. Assert `U`'s token balance equals `2 × amount_without_fee` while the bridge's accounting reflects only one transfer.
