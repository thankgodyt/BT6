### Title
Permissionless `execute_refund` Allows Any Caller to Grief User Refunds by Seizing Pending-Info Ownership — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

`execute_refund` carries no caller restriction beyond the timelock. Any NEAR account that calls it first after the timelock expires becomes the `account_id` owner of the resulting `BTCPendingInfo`. A malicious actor who front-runs the legitimate user can seize ownership of the pending refund transaction, refuse to sign it, and leave the user's BTC permanently locked with no on-chain recovery path.

---

### Finding Description

`execute_refund` is declared with only `#[payable]` and `#[pause]` guards — no `#[trusted_relayer]` or caller-identity check: [1](#0-0) 

The API documentation explicitly states "After the timelock period, **anyone** can call `execute_refund` to initiate the return."

Inside `finalize_refund_with_psbt`, the `BTCPendingInfo` is created with `account_id: caller` — whoever called `execute_refund`: [2](#0-1) 

The PSBT is deterministic (same deposit UTXO → same inputs/outputs → same transaction ID → same `btc_pending_id`). A second call with the same UTXO key therefore always fails: [3](#0-2) 

The existing test `test_refund_execute_twice_different_account` only validates the case where the **legitimate** user calls first and a second account is blocked. It does not test the inverse — a malicious account calling first. [4](#0-3) 

After the malicious first call:

1. `refund_request.executed = true` and the UTXO is inserted into `verified_deposit_utxo`.
2. The legitimate user's subsequent `execute_refund` call reaches `finalize_refund_with_psbt` (the `executed == true` guard allows re-entry) but fails at the `btc_pending_infos.insert` with `"pending info already exist"`.
3. The malicious owner simply does not call `sign_btc_transaction`, leaving the refund unsigned indefinitely.

**No on-chain recovery path exists.** The DAO can call `reject_refund` to remove the `RefundRequest`, which then allows `remove_refund_pending_tx_id` to clean up the stale `BTCPendingInfo`. However, `finalize_refund_with_psbt` already inserted the UTXO key into `verified_deposit_utxo`: [5](#0-4) 

`reject_refund` and `remove_refund_pending_tx_id` do **not** remove this entry. There is no contract function to evict a key from `verified_deposit_utxo`. A new `request_refund` for the same UTXO therefore fails with `"UTXO already verified via deposit"`, and the user's BTC remains locked in the bridge's MPC-controlled address until a contract upgrade.

---

### Impact Explanation

The user's deposited BTC is locked in the bridge's MPC key path with no signing party willing to release it and no on-chain mechanism to restart the refund. Resolution requires a contract upgrade to purge the stale `verified_deposit_utxo` entry. This matches **Medium — stuck bridge state requiring operator intervention** and borders on **Critical — permanent locking of user funds** absent an upgrade.

---

### Likelihood Explanation

Any NEAR account can monitor the `RefundRequested` event emitted by `request_refund_callback`, compute the timelock expiry, and submit `execute_refund` in the first block after expiry. No special privilege, leaked key, or off-chain coordination is required. The cost is only the 1 NEAR attached deposit required by `required_balance_for_execute_refund`. [6](#0-5) 

---

### Recommendation

Store the `requester` account ID inside `RefundRequest` at `request_refund_callback` time, and in `resolve_execute_refund_timelock` / `internal_execute_refund` enforce that `env::predecessor_account_id() == refund_request.requester || is_privileged`. This mirrors the pattern already used for `cancel_withdraw` (DAO/Operator only) and eliminates the griefing surface while preserving the DAO/RefundOperator fast-track path.

---

### Proof of Concept

1. Alice calls `request_refund` with `deposit_msg.refund_address = None` (unsafe path). After the callback, `RefundRequest` is stored with `executed: false`.
2. The `unsafe_refund_timelock_sec` elapses (default 14 days).
3. Mallory monitors the chain, sees the timelock expire, and calls `execute_refund(utxo_storage_key)` with 1 NEAR attached — before Alice.
4. `finalize_refund_with_psbt` runs: `BTCPendingInfo { account_id: mallory, … }` is inserted; `verified_deposit_utxo` gains the UTXO key; `refund_request.executed = true`.
5. Alice calls `execute_refund` — the `executed == true` guard passes, but `btc_pending_infos.insert` panics with `"pending info already exist"`.
6. Mallory never calls `sign_btc_transaction`. The refund PSBT is never signed.
7. DAO calls `reject_refund` → removes `RefundRequest`. DAO calls `remove_refund_pending_tx_id` → removes Mallory's `BTCPendingInfo`. But `verified_deposit_utxo` still contains the UTXO key.
8. Alice calls `request_refund` again → `request_refund_callback` panics: `"UTXO already verified via deposit"`. Alice's BTC is permanently locked without a contract upgrade.

```rust
/// A *different* account cannot duplicate or hijack a refund that is already being
/// executed. Two protections apply on Bitcoin:
///   1. a non-privileged account is still gated by the timelock;
///   2. once past the timelock it rebuilds the identical tx (same id), so the
///      insert is rejected — the pending tx stays owned by the original caller.
#[tokio::test]
#[cfg(not(feature = "zcash"))]
async fn test_refund_execute_twice_different_account() {
    let worker = near_workspaces::sandbox().await.unwrap();
    let context = Context::new(&worker, Some(CHAIN.to_string())).await;

    let refund_btc_address = TARGET_ADDRESS;
    let deposit_msg = DepositMsg {
        recipient_id: context.get_account_by_name("alice").sdk_id(),
        post_actions: None,
        extra_msg: None,
        safe_deposit: None,
        refund_address: Some(refund_btc_address.to_string()),
    };
    let deposit_address = context
        .get_user_deposit_address(deposit_msg.clone())
        .await
        .unwrap();
    let tx_bytes = generate_transaction_bytes(
        vec![(
            "a2a5069f02ad4ca31a16113903ab9fe9e8da6ddf20cad4b461b71e8b96050f19",
            0,
            None,
        )],
        vec![(deposit_address.as_str(), 100_000)],
    );
    let vout: u32 = 0;

    check!(context.request_refund(
        "alice",
        deposit_msg.clone(),
        TARGET_ADDRESS,
        tx_bytes.clone(),
        vout,
        "0000000000000c3f818b0b6374c609dd8e548a0a9e61065e942cd466c426e00d".to_string(),
        1,
        vec![],
        None
    ));
    let key = utxo_storage_key(&tx_bytes, vout);

    // Short timelock so we can fast-forward past it deterministically.
    context
        .get_account_by_name("root")
        .call(context.bridge_contract.id(), "update_config")
        .args_json(json!({"update": {"refund_timelock_sec": 200}}))
        .deposit(near_sdk::NearToken::from_yoctonear(1))
        .max_gas()
        .transact()
        .await
        .unwrap()
        .unwrap();

    // root (DAO) fast-tracks the pre-authorized address (timelock 0).
    check!(print "execute_refund #1 (root)" context.execute_refund("root", &key));
    let pending1 = context.get_btc_pending_infos_paged().await.unwrap();
    assert_eq!(pending1.len(), 1);
    let id1 = pending1.keys().next().unwrap().clone();

    // (1) A non-privileged different account (bob) is still gated by the timelock.
    check!(
        context.execute_refund("bob", &key),
        "Refund timelock has not passed yet"
    );

    // (2) After the timelock, bob's call reaches the finalize step but rebuilds the
    // identical tx (same id) and is rejected — no duplicate, no hijack.
    worker.fast_forward(4000).await.unwrap();
    check!(
        context.execute_refund("bob", &key),
        "pending info already exist"
    );
```
