### Title
Concurrent `execute_refund` Calls Create Duplicate `BTCPendingInfo` Entries for the Same Deposit UTXO — (File: `contracts/satoshi-bridge/src/zcash_utils/refund.rs`)

### Summary

The Zcash `execute_refund` path makes an async cross-contract call to fetch the current block height **before updating any state** to mark the refund as in-progress. During the window between that call and its callback, a second `execute_refund` call for the same `utxo_storage_key` passes all checks identically and schedules a second callback. Both callbacks then independently call `finalize_refund_with_psbt`, creating two separate `BTCPendingInfo` entries for the same deposit UTXO and issuing two MPC signing requests for the same funds.

### Finding Description

`execute_refund` in `api/bridge.rs` delegates to `internal_execute_refund` in `zcash_utils/refund.rs`:

```rust
pub(crate) fn internal_execute_refund(
    &mut self,
    utxo_storage_key: String,
    timelock_sec: u64,
    chain_specific_data: Option<ChainSpecificData>,
) -> PromiseOrValue<()> {
    let caller = env::predecessor_account_id();
    PromiseOrValue::Promise(
        self.get_last_block_height_promise().then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_EXECUTE_REFUND_CALLBACK)
                .execute_refund_callback(
                    utxo_storage_key,
                    caller,
                    timelock_sec,
                    chain_specific_data,
                ),
        ),
    )
}
```

No state is mutated before the async call. The `RefundRequest.executed` flag and `verified_deposit_utxo` set are only updated inside `finalize_refund_with_psbt`, which runs inside the callback. [1](#0-0) 

The callback `execute_refund_callback` calls `load_refund_request_for_execute`, which checks:

```rust
require!(
    !self.data().verified_deposit_utxo.contains(utxo_storage_key)
        || refund_request.executed,
    "UTXO already verified via deposit, cannot refund"
);
``` [2](#0-1) 

After the **first** callback runs, `finalize_refund_with_psbt` sets `refund_request.executed = true` and inserts the key into `verified_deposit_utxo`. When the **second** callback runs, the guard evaluates as `!true || true = true` — it passes. The second callback then also reaches `finalize_refund_with_psbt`. [3](#0-2) 

Because the two callbacks execute in different NEAR blocks, they receive different `last_block_height` values, producing PSBTs with different `expiry_height` fields and therefore different `btc_pending_id` hashes. The uniqueness check inside `finalize_refund_with_psbt`:

```rust
require!(
    self.data_mut()
        .btc_pending_infos
        .insert(btc_pending_id.clone(), btc_pending_info.into())
        .is_none(),
    "pending info already exist"
);
```

passes for both, because the IDs differ. [4](#0-3) 

The result is two live `BTCPendingInfo` entries in `Refund / PendingSign` state for the same deposit UTXO, both queued for MPC signing.

### Impact Explanation

Two MPC signing requests are issued for the same deposit UTXO. Both signed transactions are broadcast to the Zcash network. Only one can confirm (the other is a double-spend and is rejected by the network). The orphaned `BTCPendingInfo` entry remains permanently in `btc_pending_sign_ids` / `btc_pending_verify_list` and can never be finalized via `verify_refund_finalize` (its transaction will never confirm). Cleanup requires privileged operator intervention via `remove_refund_pending_tx_id`. This matches the **Medium** impact class: stuck bridge state requiring operator intervention.

### Likelihood Explanation

`execute_refund` is a public, unprivileged function (no role restriction beyond the timelock). Once the timelock elapses, any NEAR account can call it. An attacker submits two `execute_refund` transactions for the same `utxo_storage_key` in the same NEAR block. Both are processed before either callback executes, scheduling two independent callbacks. This is straightforward to execute with no special privileges. [5](#0-4) 

### Recommendation

Mark the refund request as in-progress **before** the async call, so a concurrent second call is rejected. The simplest approach is to set `refund_request.executed = true` and persist it at the start of `internal_execute_refund`, before `get_last_block_height_promise()` is called. If the callback fails, roll back the flag. Alternatively, introduce a dedicated `in_progress` boolean or remove the request from `refund_requests` at the start of `execute_refund` and re-insert it only on callback failure.

### Proof of Concept

1. A deposit UTXO exists with a valid `RefundRequest` whose timelock has elapsed (`executed = false`).
2. Attacker submits two `execute_refund(utxo_storage_key, ...)` transactions in the same NEAR block.
3. Both transactions execute synchronously: both call `resolve_execute_refund_timelock` (passes, no state change), both call `internal_execute_refund`, both schedule `execute_refund_callback` with different `last_block_height` values.
4. Callback A executes: `load_refund_request_for_execute` passes (`executed=false`), `finalize_refund_with_psbt` creates `BTCPendingInfo_A`, sets `executed=true`, inserts UTXO into `verified_deposit_utxo`.
5. Callback B executes: `load_refund_request_for_execute` — `verified_deposit_utxo` contains the key but `refund_request.executed == true`, so the guard passes. `finalize_refund_with_psbt` creates `BTCPendingInfo_B` (different `btc_pending_id` due to different block height), inserts it successfully.
6. Both entries are signed by MPC. Both transactions are broadcast. Only one confirms; the other is permanently stuck in the bridge state. [6](#0-5) [7](#0-6)

    pub fn execute_refund_callback(
        &mut self,
        utxo_storage_key: String,
        caller: AccountId,
        timelock_sec: u64,
        chain_specific_data: Option<ChainSpecificData>,
        #[callback_unwrap] last_block_height: u32,
    ) {
        // Enforce the timelock and that the UTXO has not been finalized via deposit.
        let refund_request = self.load_refund_request_for_execute(&utxo_storage_key, timelock_sec);
        let RefundExecutionInputs {
            outpoint,
            deposit_output,
            refund_amount,
        } = self.refund_execution_inputs(&refund_request);

        let expiry_height = REFUND_EXPIRY_HEIGHT;
        let orchard_bundle = chain_specific_data.map(|c| c.orchard_bundle_bytes.0);

        // Shielded refund routes funds through the Orchard bundle (no transparent
        // output); transparent refund pays a single t-address output.
        let output = if orchard_bundle.is_some() {
            Vec::new()
        } else {
            vec![self.build_refund_output(&refund_request.refund_address, refund_amount)]
        };

        let mut psbt = PsbtWrapper::new(
            vec![outpoint],
            output,
            orchard_bundle,
            expiry_height,
            last_block_height,
            Some(refund_request.refund_address.clone()),
            self.internal_config(),
        );
        psbt.set_input_utxo(vec![deposit_output]);

        // Validate the gas fee covers the Zcash minimum and, for shielded refunds,
        // that the Orchard bundle pays out to `refund_address`.
        self.check_psbt_chain_specific(
            &psbt,
            refund_request.gas_fee,
            refund_request.refund_address.clone(),
        );

        // `validate_orchard_bundle` only checks the recipient and the bundle's
        // internal value balance, not that it matches the deposit economics.
        // Enforce that the shielded output equals deposit - gas, otherwise the
        // resulting transaction would not balance against the chosen gas fee.
        if psbt.has_orchard_bundle() {
            require!(
                psbt.get_orchard_output_amount() == refund_amount,
                format!(
                    "Orchard output amount ({}) does not match refund amount ({})",
                    psbt.get_orchard_output_amount(),
                    refund_amount
                )
            );
        }

        self.finalize_refund_with_psbt(
            caller,
            refund_request,
            psbt,
            refund_amount,
            utxo_storage_key,
        );
    }

    pub(crate) fn finalize_refund_with_psbt(
        &mut self,
        caller: AccountId,
        mut refund_request: RefundRequest,
        psbt: PsbtWrapper,
        refund_amount: u128,
        utxo_storage_key: String,
    ) {
        let gas_fee = refund_request.gas_fee;
        let refund_address = refund_request.refund_address.clone();

        let deposit_msg = refund_request.deposit_msg();
        let path = get_deposit_path(&deposit_msg);
        let vutxo = VUTXO::Current(UTXO {
            path,
            tx_bytes: refund_request.tx_bytes.0.clone(),
            vout: refund_request.vout,
            balance: u64::try_from(refund_request.amount)
                .unwrap_or_else(|_| env::panic_str("Amount overflow")),
        });

        let psbt_hex = psbt.serialize();
        let btc_pending_id = psbt.get_pending_id();

        if !self.check_account_exists(&caller) {
            self.internal_set_account(&caller, crate::Account::new(&caller));
        }
        self.require_pending_sign_capacity(&caller);

        let btc_pending_info = BTCPendingInfo {
            account_id: caller.clone(),
            btc_pending_id: btc_pending_id.clone(),
            transfer_amount: 0,
            actual_received_amount: refund_amount,
            withdraw_fee: 0,
            gas_fee,
            burn_amount: 0,
            psbt_hex,
            vutxos: vec![vutxo],
            signatures: vec![None; 1],
            tx_bytes_with_sign: None,
            create_time_sec: nano_to_sec(env::block_timestamp()),
            last_sign_time_sec: 0,
            state: PendingInfoState::Refund(OriginalState {
                stage: PendingInfoStage::PendingSign,
                max_gas_fee: gas_fee,
                last_rbf_time_sec: None,
                cancel_rbf_reserved: None,
            }),
        };

        require!(
            self.data_mut()
                .btc_pending_infos
                .insert(btc_pending_id.clone(), btc_pending_info.into())
                .is_none(),
            "pending info already exist"
        );
        self.internal_unwrap_mut_account(&caller)
            .btc_pending_sign_ids
            .insert(btc_pending_id.clone());

        // Mark UTXO as verified to prevent verify_deposit later
        self.data_mut()
            .verified_deposit_utxo
            .insert(utxo_storage_key.clone());

        Event::RefundExecuted {
            utxo_storage_key: utxo_storage_key.clone(),
            amount: refund_request.amount.into(),
            refund_address,
        }
        .emit();

        Event::GenerateBtcPendingInfo {
            account_id: &caller,
            btc_pending_id: &btc_pending_id,
        }
        .emit();

        // Keep the request (so `execute_refund` can be called again to re-create
        // the transaction) but mark it executed; it is removed only when the
        // refund is finalized in `verify_refund_finalize`.
        refund_request.executed = true;
        self.data_mut()
            .refund_requests
            .insert(utxo_storage_key, refund_request.into());
```
