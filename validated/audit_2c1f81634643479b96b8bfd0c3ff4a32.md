### Title
Re-execution of `execute_refund` Permanently Blocked by Stale Pending-Sign Capacity Check - (File: `contracts/satoshi-bridge/src/refund.rs`)

### Summary
`finalize_refund_with_psbt` calls `require_pending_sign_capacity` before inserting a new `BTCPendingInfo`. When `execute_refund` is called a second time on the same refund request (an explicitly supported re-execution path, e.g. after a consensus branch change), the old pending info from the first execution is still counted in `pending_sign_count()`. The capacity check does not subtract the existing pending entry that belongs to the same refund being re-executed, so the check fails and the re-execution reverts — permanently locking the user's deposit UTXO in a stuck state that requires operator intervention.

### Finding Description

The bridge explicitly supports re-executing a refund after the first attempt. In `finalize_refund_with_psbt`, the request is kept with `executed = true` so that `execute_refund` can be called again:

```rust
// Keep the request (so `execute_refund` can be called again to re-create
// the transaction) but mark it executed; it is removed only when the
// refund is finalized in `verify_refund_finalize`.
refund_request.executed = true;
self.data_mut()
    .refund_requests
    .insert(utxo_storage_key, refund_request.into());
```

However, the same function also calls `require_pending_sign_capacity` before inserting the new pending info:

```rust
self.require_pending_sign_capacity(&caller);
// ...
self.internal_unwrap_mut_account(&caller)
    .btc_pending_sign_ids
    .insert(btc_pending_id.clone());
```

`require_pending_sign_capacity` checks:

```rust
account.pending_sign_count() < self.get_max_pending_sign_txs(account_id)
```

The default `max_pending` is `1`. After the first `execute_refund`, the old `btc_pending_id` is in `btc_pending_sign_ids`, so `pending_sign_count()` is already `1`. On the second call, the check `1 < 1` fails and the transaction reverts.

The old pending info cannot be cleaned up via `remove_refund_pending_tx_id` either, because that function requires the refund request to be absent:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_keys[0]),
    "refund request still active"
);
```

But the refund request is still present (marked `executed = true`). There is no code path that removes the old pending info while keeping the refund request active, so the user is permanently stuck.

This is the direct analog of the royalty bug: the capacity check `pending_sign_count() < max_pending` does not subtract the existing pending entry that belongs to the same refund being updated/re-executed, mirroring `existingRoyalty + share < FEE_DENOMINATOR` failing to subtract the collector's current share before adding the new one.

### Impact Explanation

A user whose refund transaction was built but never confirmed on-chain (e.g. after a consensus branch change, which is the documented reason for re-execution) cannot re-execute the refund. Their deposit UTXO is permanently locked in the bridge until an operator manually intervenes — for example, by calling `reject_refund` to remove the request, allowing `remove_refund_pending_tx_id` to clean up the stale pending info, and then requiring the user to restart the entire refund flow from `request_refund`. This is a stuck bridge state requiring operator intervention, matching the Medium impact class.

### Likelihood Explanation

The scenario is realistic: a refund transaction can fail to confirm due to fee market conditions, a chain reorganization, or a consensus branch change. The code was explicitly written to support re-execution for exactly this reason. Any user with a pending refund in the `executed = true` state and a default `max_pending` of `1` will hit this revert on their second `execute_refund` call. No privileged access is required; `execute_refund` is a public function callable by anyone after the timelock.

### Recommendation

In `finalize_refund_with_psbt`, when the refund request is already `executed == true` (re-execution path), remove the stale pending info entries that belong to the same refund before performing the capacity check and inserting the new one. Concretely, before calling `require_pending_sign_capacity`, iterate over the caller's `btc_pending_sign_ids`, identify any entries whose `BTCPendingInfo` is a `PendingInfoState::Refund` for the same `utxo_storage_key`, remove them from both `btc_pending_infos` and `btc_pending_sign_ids`, and only then check capacity and insert the new entry.

### Proof of Concept

1. User calls `request_refund` for UTXO `txid@0`. Timelock passes.
2. User calls `execute_refund("txid@0", ...)`. `finalize_refund_with_psbt` runs:
   - `require_pending_sign_capacity` passes (`pending_sign_count = 0 < 1`).
   - `BTCPendingInfo` with id `pending_id_A` is inserted; `btc_pending_sign_ids = {"pending_id_A"}`.
   - Refund request is kept with `executed = true`.
3. The refund transaction `pending_id_A` is broadcast but never confirmed (e.g. fee too low after a reorg).
4. User calls `execute_refund("txid@0", ...)` again (explicitly supported by the design).
5. `finalize_refund_with_psbt` runs:
   - `require_pending_sign_capacity` checks `pending_sign_count() < max_pending` → `1 < 1` → **panics: "Too many pending sign transactions"**.
6. User cannot re-execute. `remove_refund_pending_tx_id` also fails because the refund request is still active. The deposit UTXO is permanently stuck. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5)
