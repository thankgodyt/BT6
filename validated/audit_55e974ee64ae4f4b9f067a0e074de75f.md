### Title
Unconditional `validatePerasCert` Stub Allows Unprivileged Peer to Inject Arbitrary Peras Weight Boosts, Corrupting Chain Selection - (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` unconditionally returns `Right` (a stub marked TODO). The `PerasCert` object-diffusion inbound handler is wired into the production NodeToNode protocol stack without any feature-flag gate at the handler level. An unprivileged peer can therefore send crafted `PerasCert` messages that pass "validation", are stored in `PerasCertDB`, and contribute a non-zero `PerasWeightSnapshot` that is consumed by both `chainSelSync` (triggering an immediate chain-selection re-run for the boosted block) and the GSM's `getCandidateOverSelection`. This allows an adversary to make an honest node prefer a shorter adversarial fork over the honest chain.

---

### Finding Description

**Step 1 – Stub validation.**

The default `BlockSupportsPeras blk` instance defines `validatePerasCert` as:

```haskell
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [1](#0-0) 

No committee-signature check, no round-number range check, no boosted-block existence check — every cert is accepted.

**Step 2 – Production inbound handler uses the stub.**

`makePerasCertPoolWriterFromChainDB` passes `validatePerasCert mkPerasParams` directly as the validation callback:

```haskell
opwAddObjects = \certs ->
  processCerts systemTime (ChainDB.getPerasCertIds chainDB)
    (validatePerasCert mkPerasParams)          -- ← always Right
    (void . ChainDB.addPerasCertAsync chainDB)
    certs
``` [2](#0-1) 

`processCerts` partitions results with `partitionEithers (validateCert <$> certsNotAlreadyInDb)`. Because the left list is always empty, every cert is forwarded to `addCert`: [3](#0-2) 

**Step 3 – Handler is always active in the NodeToNode protocol bundle.**

`hPerasCertDiffusionClient` is wired unconditionally into both `initiator` and `initiatorAndResponder` bundles: [4](#0-3) [5](#0-4) 

**Step 4 – Cert is stored and triggers chain selection.**

`ChainDB.addPerasCertAsync` enqueues a `ChainSelAddPerasCert` message. `chainSelSync` adds the cert to `PerasCertDB` and, if the boosted block is already in the `VolatileDB`, immediately calls `chainSelectionForBlock` for it: [6](#0-5) 

**Step 5 – Weight snapshot is built from all stored certs.**

`implGetWeightSnapshot` iterates over every cert in `pcdsCertsByTicket` and calls `mkPerasWeightSnapshot`: [7](#0-6) 

**Step 6 – `preferAnchoredCandidate` switches to weighted comparison.**

Once the snapshot is non-empty (`isEmptyPerasWeightSnapshot` returns `False`), `preferAnchoredCandidate` uses `weightedSelectView`, which adds `PerasWeight` boosts to block numbers: [8](#0-7) 

`wsvTotalWeight = PerasWeight(blockNo) + wsvWeightBoost`, so a single injected cert with a large `perasWeight` can make a shorter fork appear heavier than the honest chain. [9](#0-8) 

**Step 7 – GSM also reads the poisoned snapshot.**

`getCandidateOverSelection` in the GSM reads `ChainDB.getPerasWeightSnapshot chainDB` and passes `forgetFingerprint weights` to `preferAnchoredCandidate`, so the GSM's caught-up determination is also affected: [10](#0-9) 

---

### Impact Explanation

An unprivileged peer connecting via `NodeToNodeV_16` can send one or more `PerasCert` messages whose `pcCertBoostedBlock` points to a block on the peer's adversarial fork. Because `validatePerasCert` never rejects any cert, the boost is stored and immediately used in chain selection. If the adversary's fork tip is in the local `VolatileDB`, chain selection is re-run with the boosted weight, potentially switching the node to the adversarial fork. Even if the fork tip is not yet present, the weight snapshot is poisoned for all future chain-selection calls. This violates the invariant that Peras weight boosts must only be applied for certificates whose committee signatures have been cryptographically verified.

---

### Likelihood Explanation

The `perasCertDiffusionProtocol` is active for any peer that negotiates `NodeToNodeV_16`. The attack requires no special privileges, no stake, and no key material — only the ability to open a NodeToNode connection and send a well-formed CBOR-encoded `PerasCert`. The exploit is deterministic and locally reproducible with `io-sim` or a private testnet.

---

### Recommendation

1. **Immediate**: Gate `makePerasCertPoolWriterFromChainDB` (and the inbound handler) behind a feature flag that is off by default, so that nodes not running Peras never accept cert diffusion messages.
2. **Short-term**: Replace the `validatePerasCert` stub with a real implementation that verifies committee signatures before the cert is stored (tracked in [tweag/cardano-peras#120](https://github.com/tweag/cardano-peras/issues/120)).
3. **Defence-in-depth**: Add a check in `chainSelSync` / `implAddCert` that rejects certs whose `pcCertBoostedBlock` is not already known to the local node, preventing weight injection for blocks the node has never seen.

---

### Proof of Concept

Using `io-sim` or the existing `Test.Consensus.MiniProtocol.ObjectDiffusion.PerasCert.Smoke` harness:

1. Create two nodes A (honest) and B (adversary). A has an honest chain of length N.
2. B has a fork of length N-3 (shorter by 3 blocks).
3. B sends A a single `PerasCert { pcCertRound = 1, pcCertBoostedBlock = <tip of B's fork> }` via the `perasCertDiffusionProtocol`.
4. Because `validatePerasCert` returns `Right` unconditionally, the cert is stored in A's `PerasCertDB` with `vpcCertBoost = perasWeight mkPerasParams` (a large value).
5. `chainSelSync` triggers `chainSelectionForBlock` for B's fork tip.
6. `preferAnchoredCandidate` computes `wsvTotalWeight` for B's fork as `(N-3) + perasWeight`, which exceeds A's honest chain weight of `N + 0`.
7. Assert: `preferAnchoredCandidate` returns `ShouldSwitch` for B's fork, and A adopts it — despite B's fork being shorter and carrying no valid committee signatures. [11](#0-10) [12](#0-11) [13](#0-12)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool

-- Process a Peras certificate by adding it to the PerasCertDB and potentially
-- performing chain selection if a candidate is now better than our selection.
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes

  -- Deliver promise indicating that we processed the cert.
  lift $ atomically $ putTMVar varProcessed certResult

preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"
        Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
          case preferCandidate
            (projectChainOrderConfig cfg)
            (weightedSelectView cfg weights oursSuffix)
