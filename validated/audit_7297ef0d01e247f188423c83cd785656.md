### Title
Pending-Sign Capacity Enforced Against `sender_id` (Intermediary DApp) Instead of End-User — Attacker Can Permanently Block All Withdrawals Through Any DApp Intermediary - (File: `contracts/satoshi-bridge/src/api/token_receiver.rs`, `contracts/satoshi-bridge/src/account.rs`)

### Summary
The bridge enforces a per-account pending-sign capacity limit (default: 1) keyed on `sender_id` from `ft_on_transfer`. When a DApp intermediary contract calls `ft_transfer_call` on behalf of multiple end-users, all those users share the same `sender_id` (the DApp's account). A single attacker-controlled withdrawal through the DApp fills the DApp's 1-slot capacity, blocking every other user from withdrawing through that DApp until the slot is freed.

### Finding Description

`ft_on_transfer` receives `sender_id` — the NEAR account that called `ft_transfer_call` on the nBTC token contract — and passes it directly to `create_btc_pending_info`: [1](#0-0) 

Inside `create_btc_pending_info`, the pending-sign capacity is checked and the `BTCPendingInfo` is attributed to that same `sender_id`: [2](#0-1) 

The capacity limit is fetched from `pending_tx_limits`, which defaults to **1** for any account not explicitly configured: [3](#0-2) 

The enforcement check panics if the account already holds `max_pending` (≥ 1) pending sign transactions: [4](#0-3) 

In NEAR's NEP-141 standard, `sender_id` in `ft_on_transfer` is the `predecessor_account_id()` of the `ft_transfer_call` call — i.e., the DApp intermediary contract, **not** the human end-user. When a DApp (e.g., a DEX, bridge aggregator, or yield protocol) calls `ft_transfer_call` on behalf of multiple users, every one of those users shares the DApp's `sender_id`. The default limit of 1 means the DApp's slot is consumed by the first withdrawal, and every subsequent user's withdrawal reverts with `"Too many pending sign transactions"` until the first one completes the full MPC-sign → verify cycle.

### Impact Explanation

An attacker who is also a user of the DApp intermediary can initiate a single withdrawal through the DApp, filling its 1-slot capacity. All other users of that DApp are then unable to withdraw their nBTC until the attacker's pending transaction is fully resolved (MPC signing + on-chain confirmation + `verify_withdraw`). This constitutes attacker-triggered temporary locking of bridged funds for all users of any DApp intermediary that has not been individually whitelisted by the DAO via `set_pending_tx_limit`.

**Severity: Medium** — matches "attacker-triggered temporary locking of bridged funds."

### Likelihood Explanation

DApp intermediaries calling `ft_transfer_call` on behalf of users is a standard NEAR DeFi pattern. Any DApp that integrates nBTC withdrawals without a DAO-granted higher limit is vulnerable by default. The attacker needs only to be a user of the same DApp and submit one withdrawal first.

### Recommendation

Track pending-sign capacity against the actual end-user identity, not the intermediary's `sender_id`. One approach: require the `Withdraw` message to carry an explicit `account_id` field identifying the true beneficiary, and use that for both capacity accounting and `BTCPendingInfo` attribution. Alternatively, grant DApp intermediaries a higher `pending_tx_limit` automatically upon whitelisting, or enforce capacity per `(sender_id, recipient_btc_address)` pair rather than per `sender_id` alone.

### Proof of Concept

1. DApp contract `dapp.near` is integrated with the bridge. It calls `ft_transfer_call` on behalf of users.
2. Alice calls `dapp.near` → `dapp.near` calls `nbtc.ft_transfer_call(receiver_id: bridge, amount: X, msg: Withdraw{...})`.
3. Bridge's `ft_on_transfer` fires with `sender_id = "dapp.near"`. `create_btc_pending_info` checks `get_max_pending_sign_txs("dapp.near")` → returns 1 (default). Capacity is 0 < 1, so the withdrawal proceeds. `dapp.near`'s pending count is now 1.
4. Bob calls `dapp.near` → `dapp.near` calls `nbtc.ft_transfer_call(...)` for Bob.
5. Bridge's `ft_on_transfer` fires with `sender_id = "dapp.near"`. `require_pending_sign_capacity("dapp.near")` checks: pending count (1) < max (1) → **false** → panics: `"Too many pending sign transactions"`. Bob's withdrawal is reverted; his nBTC is returned.
6. Attacker (step 2) can deliberately delay or never finalize their withdrawal (e.g., by not broadcasting the signed tx), keeping `dapp.near`'s slot occupied indefinitely and blocking all other users. [2](#0-1) [5](#0-4)

    fn ft_on_transfer(
        &mut self,
        sender_id: AccountId,
        amount: U128,
        msg: String,
    ) -> PromiseOrValue<U128> {
        let amount = amount.into();
        require!(
            amount >= self.internal_config().min_withdraw_amount,
            "Invalid amount"
        );
        let message = serde_json::from_str::<TokenReceiverMessage>(&msg).expect("INVALID MSG");
        let token_id = env::predecessor_account_id();
        require!(
            token_id == self.internal_config().nbtc_account_id,
            "Invalid token_id"
        );
        match message {
            TokenReceiverMessage::DepositProtocolFee => {
                self.data_mut().acc_collected_protocol_fee += amount;
                self.data_mut().cur_available_protocol_fee += amount;
                Event::DepositProtocolFee {
                    account_id: &sender_id,
                    amount: U128(amount),
                }
                .emit();
                PromiseOrValue::Value(U128(0))
            }
            TokenReceiverMessage::Withdraw {
                target_btc_address,
                input,
                output,
                max_gas_fee,
                chain_specific_data,
            } => self.ft_on_transfer_withdraw_chain_specific(
                sender_id,
                amount,
                target_btc_address,
                input,
                output,
                max_gas_fee,
                chain_specific_data,
            ),
        }

    pub fn get_max_pending_sign_txs(&self, account_id: &AccountId) -> u32 {
        self.data()
            .pending_tx_limits
            .get(account_id)
            .copied()
            .unwrap_or(1)
    }

    pub fn require_pending_sign_capacity(&self, account_id: &AccountId) {
        require!(
            self.get_account(account_id)
                .unwrap_or_else(|| {
                    env::panic_str(&format!("ERR_ACCOUNT_NOT_REGISTERED: {}", account_id))
                })
                .pending_sign_count()
                < self.get_max_pending_sign_txs(account_id),
            "Too many pending sign transactions"
        );
    }
