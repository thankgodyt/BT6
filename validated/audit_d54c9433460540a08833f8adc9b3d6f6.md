### Title
Unconditional `validatePerasCert` Acceptance Bypasses Peras Certificate Verification, Enabling Arbitrary Chain-Weight Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance — the only instance in the codebase, covering all block types including production Cardano blocks — implements `validatePerasCert` as an unconditional stub that always returns `Right`, accepting every inbound certificate without any cryptographic or semantic validation. When Peras is enabled, an unprivileged peer can inject a crafted `PerasCert` pointing to any block on any fork, have it accepted as a `ValidatedPerasCert`, and cause the receiving node to boost that block's chain-selection weight by the full `perasWeight` parameter, potentially switching the node to a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` class declares `validatePerasCert` as the mandatory gate for accepting inbound Peras certificates:

```haskell
validatePerasCert ::
  PerasCfg blk ->
  PerasCert blk ->
  Either (PerasValidationErr blk) (ValidatedPerasCert blk)
```

The sole instance — explicitly marked as a "degenerate instance for all blks to get things to compile" — implements this as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub performs **zero validation**: no quorum check, no aggregate signature verification, no round-number bounds check, no check that the boosted block exists or is on any known chain. Every `PerasCert` received from any peer is unconditionally wrapped in `ValidatedPerasCert` and assigned the full `perasWeight` boost.

The same pattern applies to `validatePerasVote`, which only checks whether the claimed voter ID appears in the stake distribution map, with no cryptographic signature verification:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [2](#0-1) 

The inbound vote-processing path in `makePerasVotePoolWriterFromChainDB` calls this stub directly:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [3](#0-2) 

Once a `ValidatedPerasCert` is accepted, `chainSelSync` in `ChainDB.Impl.ChainSel` adds it to the `PerasCertDB` and immediately triggers chain selection for the boosted block:

```haskell
certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
...
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

The `WeightedSelectView` chain-order comparison then uses the injected boost directly:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [5](#0-4)

### Impact Explanation

When Peras is enabled via `rnFeatureFlags`, an unprivileged peer can:

1. Craft a `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock` pointing to a block on a minority or adversarial fork.
2. Send it over the Peras certificate diffusion mini-protocol.
3. The receiving node calls `validatePerasCert`, which returns `Right` unconditionally.
4. The certificate is stored in `PerasCertDB` and chain selection is re-run with the boosted block receiving `perasWeight` additional weight.
5. If the boosted fork's total weight (`BlockNo + perasWeight`) exceeds the honest chain's weight, the node switches to the adversarial fork.

This constitutes a **High** impact chain-selection bug: an unprivileged peer can make an honest node prefer a non-canonical, less-secure chain beyond the intended security assumptions of the Peras protocol, violating the core invariant that only legitimately quorum-backed certificates should influence chain selection.

The `validatePerasVote` bypass compounds this: an attacker who knows any registered voter ID (publicly available from the stake distribution) can submit votes impersonating that voter for any block, accumulate fabricated quorum, and trigger local certificate forging — all without possessing the voter's private key.

---

### Likelihood Explanation

- **Peras is disabled by default** (per CHANGELOG: "if Peras is disabled (which is the default), there is no observable difference"), so this is not exploitable on mainnet today.
- However, the code is present in production files, the feature is activatable via `rnFeatureFlags`, and the TODO comments reference a tracked issue (`cardano-peras/issues/120`), confirming this is intended production code awaiting completion.
- The attack requires only a network connection to a Peras-enabled node and knowledge of the diffusion mini-protocol — no keys, no stake, no admin access.
- The `PerasCert` data type contains only `pcCertRound :: PerasRoundNo` and `pcCertBoostedBlock :: Point blk`, both trivially constructable by any peer. [6](#0-5) 

---

### Recommendation

Replace the stub `validatePerasCert` implementation with real validation before Peras is enabled in any production deployment. At minimum, validation must check:

1. **Aggregate signature**: verify the BLS/aggregate signature over the certificate against the declared committee members' public keys.
2. **Quorum**: confirm the aggregate stake of signers exceeds the configured `perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin`.
3. **Round bounds**: confirm `pcCertRound` is within the valid window relative to the current slot.
4. **Boosted block existence**: confirm `pcCertBoostedBlock` refers to a known block.

Similarly, `validatePerasVote` must verify the cryptographic vote signature and VRF eligibility proof before accepting a vote, not merely check stake-distribution membership.

The `BlockSupportsPeras` class should not provide a universal default instance that silently accepts all inputs; the class should either have no default or should require an explicit opt-in stub for testing only.

---

### Proof of Concept

With Peras enabled on a private testnet node:

1. Connect to the node's Peras certificate diffusion mini-protocol endpoint.
2. Construct a `PerasCert` with `pcCertRound = <any round>` and `pcCertBoostedBlock = <point of a block on a minority fork>`.
3. Send the certificate. The node calls `validatePerasCert`, which returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }` unconditionally.
4. `chainSelSync` adds the cert to `PerasCertDB` and calls `chainSelectionForBlock` for the boosted block.
5. `WeightedSelectView` now scores the minority fork as `BlockNo(fork) + perasWeight`, which — for a sufficiently large `perasWeight` — exceeds the honest chain's score of `BlockNo(honest)`.
6. The node switches to the minority fork, diverging from the honest network. [7](#0-6) [8](#0-7) [9](#0-8)

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
