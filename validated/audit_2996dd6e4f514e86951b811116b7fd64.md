Audit Report

## Title
Relayer Fee Not Paid to Relayer in Non-Fast UTXO-to-NEAR Transfers — (File: near/omni-bridge/src/lib.rs)

## Summary
In `utxo_fin_transfer_to_near`, the full `amount` received from the UTXO connector is forwarded to the recipient without deducting `utxo_fin_transfer_msg.relayer_fee`, and no separate payment is made to the relayer. As a result, for every non-fast UTXO-to-NEAR finalization, the relayer receives zero fee while the recipient receives the full amount including the fee portion. This is confirmed by the project's own integration tests.

## Finding Description
**Code path:**

1. The UTXO connector calls `ft_transfer_call` on the bridge token, which triggers `ft_on_transfer` on the bridge contract.
2. The bridge dispatches to `utxo_fin_transfer` (line 2456), which receives the full `amount` from the connector.
3. When `utxo_fin_transfer_msg.recipient` is `OmniAddress::Near(recipient)`, the code calls `utxo_fin_transfer_to_near` (line 2498) passing the full `amount` unchanged.
4. `utxo_fin_transfer_to_near` (line 2563) schedules `utxo_fin_transfer_to_near_callback` with the same full `amount` and the `utxo_fin_transfer_msg` (which carries `relayer_fee`), but never deducts `relayer_fee` from `amount` and never issues a separate transfer of `relayer_fee` to the relayer.

**Contrast with the other-chain path:** `utxo_fin_transfer_to_other_chain` (line 2595) stores `relayer_fee` inside the `TransferMessage.fee` field so it can be claimed after destination-chain finalization. No equivalent mechanism exists for the NEAR-recipient path.

**Test confirmation:** The project's own integration test at `near/omni-tests/src/utxo_fin_transfer.rs` line 218–223 explicitly encodes this behavior:
```rust
let (recipient_change, relayer_change) = match (is_fast_transfer, is_transfer_to_near) {
    (true, true)  => (0, amount),
    (true, false) => (0, amount - utxo_msg.relayer_fee.0),
    (false, true) => (amount, 0),   // ← relayer gets 0; recipient gets full amount
    (false, false) => (0, 0),
};
```
For `(false, true)` the test asserts `relayer_change == 0` and `recipient_change == amount`, confirming the fee is silently absorbed by the recipient.

**Existing guards:** There are no checks or deductions applied to `relayer_fee` anywhere in the `utxo_fin_transfer_to_near` / `utxo_fin_transfer_to_near_callback` path. The `relayer_fee` field is carried in the message but never acted upon for NEAR recipients.

## Impact Explanation
This is fee mis-accounting that concretely changes user balances: the relayer loses `relayer_fee` tokens on every non-fast UTXO-to-NEAR finalization, and the recipient gains those same tokens in excess of what they are owed. This matches the Critical allowed impact: *"fee mis-accounting that changes user or protocol balances."* The magnitude scales with the fee value and the volume of UTXO-to-NEAR transfers.

## Likelihood Explanation
Every non-fast UTXO-to-NEAR transfer triggers this path unconditionally. No special attacker capability is required — any user who initiates a UTXO-to-NEAR transfer with a non-zero `relayer_fee` causes the relayer to forfeit that fee. The relayer cannot avoid the loss once they submit the finalization. The condition is always met and is repeatable for every such transfer.

## Recommendation
In `utxo_fin_transfer_to_near` (or its callback), before transferring tokens to the recipient:
1. Deduct `utxo_fin_transfer_msg.relayer_fee` from `amount` to compute `recipient_amount = amount - relayer_fee`.
2. Transfer `recipient_amount` to the recipient.
3. Transfer `relayer_fee` to the relayer (the `signer_id` / `storage_owner` passed into `utxo_fin_transfer`), mirroring the fee-payment logic already present in `fin_transfer_send_tokens_callback` (line 1721–1733) and `send_fee_internal` (line 2650–2701).

## Proof of Concept
The existing integration test in `near/omni-tests/src/utxo_fin_transfer.rs` already demonstrates the bug. Modify the assertion at line 221 to the correct expected value:
```rust
(false, true) => (amount - utxo_msg.relayer_fee.0, utxo_msg.relayer_fee.0),
```
Run `cargo test` — the test will fail, proving the relayer receives 0 instead of `relayer_fee` and the recipient receives `amount` instead of `amount - relayer_fee`. No private testnet or external setup is required; the sandbox integration test is self-contained.
