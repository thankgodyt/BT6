### Title
Peras Certificate Validation Unconditionally Accepts All Inbound Certificates, Enabling Unprivileged Peer to Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The sole production instance of `BlockSupportsPeras` implements `validatePerasCert` as an unconditional `Right`, meaning every Peras certificate received from any peer passes validation without any cryptographic or structural check. An unprivileged peer can craft arbitrary certificates that boost any block in the VolatileDB, causing the receiving node to re-run chain selection and potentially switch to a non-canonical chain. The same instance also omits signature verification in `validatePerasVote`.

### Finding Description

`BlockSupportsPeras` is the typeclass that governs Peras certificate and vote validation. A grep for `instance.*BlockSupportsPeras` returns exactly two hits in the same file — the class definition and one catch-all instance — confirming there is no override for any concrete block type. [1](#0-0) 

That catch-all instance implements `validatePerasCert` as: [2](#0-1) 

The function body is `Right ValidatedPerasCert { … }` with no guard, no signature check, no committee membership check, and no round-number bound check. Every certificate unconditionally becomes a `ValidatedPerasCert`.

The production inbound path is `makePerasCertPoolWriterFromChainDB`, which passes this function directly as the validator: [3](#0-2) 

`processCerts` then partitions results: because `validatePerasCert` never returns `Left`, the `([], validatedCerts)` branch is always taken and every certificate is forwarded to `addCert`: [4](#0-3) 

Once a certificate is in the `PerasCertDB`, `chainSelSync` re-runs chain selection for the boosted block: [5](#0-4) 

The only guard at this stage is whether the boosted block's hash exists in the `VolatileDB`. If it does, full chain selection is triggered with the attacker-supplied weight boost applied.

`validatePerasVote` has the same class of defect — it checks stake-distribution membership but performs no signature verification: [6](#0-5) 

### Impact Explanation

When Peras is enabled, an unprivileged peer can send a crafted `PerasCert` naming any block hash present in the target node's `VolatileDB`. Because `validatePerasCert` always returns `Right`, the certificate is stored and its weight boost is applied during chain selection. If the boosted block is on a competing fork, the node's `preferAnchoredCandidate` comparison will now favour that fork, causing the node to roll back its current selection and adopt the attacker-chosen chain. This is a bypass of Peras certificate/vote checks that enables unauthorized certificate acceptance and a chain-selection manipulation, matching the **Critical** impact category (bypass of Peras certificate validation) and the **High** impact category (chain-selection bug letting an unprivileged peer make an honest node prefer a non-canonical chain).

### Likelihood Explanation

The attack requires only network connectivity to a Peras-enabled node and knowledge of a block hash in the target's VolatileDB (observable via ChainSync). No keys, stake, or operator access are needed. The code path is exercised for every inbound certificate batch when Peras is active.

### Recommendation

Replace the stub body of `validatePerasCert` with real committee-membership and aggregate-signature verification, analogous to the `implVerifyCert` logic already implemented for `EveryoneVotes` and `WFALS` committees: [7](#0-6) 

Until real validation is in place, the Peras feature flag must remain disabled in all production deployments. Similarly, `validatePerasVote` must be extended to verify the vote signature before accepting a vote.

### Proof of Concept

1. Attacker connects to a Peras-enabled node via the object-diffusion mini-protocol.
2. Attacker observes (via ChainSync) a block hash `H` on a competing fork present in the node's VolatileDB.
3. Attacker sends a `PerasCert { pcCertRound = freshRound, pcCertBoostedBlock = BlockPoint slot H }`.
4. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right`.
5. Certificate is inserted into `PerasCertDB`; `chainSelSync` fires `chainSelectionForBlock` for `H`.
6. `preferAnchoredCandidate` now sees the fork carrying `H` as heavier than the honest chain; the node rolls back and adopts the attacker-chosen fork. [8](#0-7) [4](#0-3) [9](#0-8)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts

              case nonZero voterStake of
                Nothing ->

                  pure

                        seatIndex
                        nonZeroVoterStake
                    , voterVerificationKey

              Left (MissingSeatIndex seatIndex)

      bimap CryptoError id $ do
