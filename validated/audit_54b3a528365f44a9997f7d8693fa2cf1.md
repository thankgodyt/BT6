### Title
Unauthenticated `request_refund` Allows Any Caller to Redirect Victim's Deposit BTC to Attacker-Controlled Address - (File: `contracts/satoshi-bridge/src/refund.rs`)

### Summary

The `internal_request_refund` function accepts a caller-supplied `refund_address` without verifying that the caller is the original depositor. When a deposit's `DepositMsg` was created with `refund_address: None`, any unprivileged NEAR account can submit a refund request for that deposit and specify their own Bitcoin address as the destination. After the `unsafe_refund_timelock_sec` elapses without DAO/Operator intervention, the bridge's MPC will sign a transaction sending the victim's BTC to the attacker's address.

### Finding Description

The entry point is `internal_request_refund` in `contracts/satoshi-bridge/src/refund.rs`. The only guard on `refund_address` is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [1](#0-0) 

This check is only enforced when `deposit_msg.refund_address` is `Some`. When it is `None` — the common case for users who did not pre-authorize a refund address — the check is skipped entirely, and the caller's arbitrary `refund_address` is stored verbatim into the `RefundRequest`:

```rust
let refund_request = RefundRequest {
    ...
    refund_address,   // ← attacker-controlled
    ...
};
self.data_mut().refund_requests.insert(utxo_storage_key, refund_request.into());
``` [2](#0-1) 

There is no `require!(env::predecessor_account_id() == deposit_msg.recipient_id, ...)` or equivalent ownership check anywhere in the refund request path.

All inputs the attacker needs are public:
- `deposit_msg` — observable from the NEAR blockchain (the user called a view/derive-address function passing it)
- `tx_bytes` and Merkle `proof` — publicly available on the Bitcoin blockchain
- `vout` — readable from the Bitcoin transaction

The stored `refund_address` is later used unconditionally in `finalize_refund_with_psbt` → `build_refund_output` to construct the PSBT output that MPC signs:

```rust
pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
    let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
        .expect("Invalid refund address");
``` [3](#0-2) 

The `resolve_execute_refund_timelock` function acknowledges this risk by applying a longer `unsafe_refund_timelock_sec` for the no-pre-authorized-address case, but this is only a mitigation window for operator intervention, not a fix:

```rust
// Refund address supplied by caller of `request_refund`: longer
// timelock to give DAO/Operator time to reject suspicious requests.
config.unsafe_refund_timelock_sec
``` [4](#0-3) 

### Impact Explanation

If the DAO/Operator does not reject the fraudulent refund request within `unsafe_refund_timelock_sec`, the bridge's MPC will sign a Bitcoin transaction sending the victim's deposited BTC to the attacker's address. This is a direct, permanent theft of user funds — the victim loses their BTC and receives no nBTC (the deposit UTXO is marked verified, blocking a later `verify_deposit`). This matches the Critical impact category: **significant loss or theft of user funds**.

### Likelihood Explanation

The attacker requires no privileged access. All inputs (`deposit_msg`, `tx_bytes`, Merkle proof) are publicly observable on-chain. The only barrier is the `unsafe_refund_timelock_sec` window during which the DAO/Operator must notice and call `internal_reject_refund`. If the operator is slow, offline, or the timelock is short, the attack succeeds. Likelihood is **Low-Medium** due to the operator mitigation window, but the window is not guaranteed to be acted upon.

### Recommendation

Add a caller-ownership check at the start of `internal_request_refund`. The simplest fix is to require that `env::predecessor_account_id() == deposit_msg.recipient_id` when `deposit_msg.refund_address` is `None`. Alternatively, require that the caller pre-registers a refund address (i.e., always require `deposit_msg.refund_address` to be `Some`) and remove the unsafe path entirely.

### Proof of Concept

1. Victim deposits BTC to the address derived from `deposit_msg = { recipient_id: "victim.near", refund_address: None }`.
2. The deposit is not yet finalized (UTXO not in `verified_deposit_utxo`).
3. Attacker observes the Bitcoin transaction (`tx_bytes`, `vout`, Merkle proof) and the victim's `deposit_msg` from NEAR blockchain history.
4. Attacker calls `request_refund(deposit_msg, refund_address="attacker_btc_addr", tx_bytes, vout, proof, gas_fee=None)`.
5. `request_refund_callback` stores `RefundRequest { refund_address: "attacker_btc_addr", ... }`.
6. After `unsafe_refund_timelock_sec` elapses without DAO rejection, attacker calls `execute_refund`.
7. `finalize_refund_with_psbt` builds a PSBT paying `refund_amount` to `"attacker_btc_addr"`.
8. MPC signs the PSBT; attacker broadcasts it; victim's BTC is permanently redirected to the attacker.
