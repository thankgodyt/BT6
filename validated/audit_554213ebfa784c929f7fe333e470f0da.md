Audit Report

## Title
Detached `send_tokens` Promise in UTXO Fast Transfer Finalization Causes Permanent Relayer Fund Freezing — (`near/omni-bridge/src/lib.rs`)

## Summary
In `utxo_fin_transfer_fast()` and `process_fin_transfer_to_other_chain()`, the fast-transfer accounting state is permanently mutated — either via `remove_fast_transfer()` or `mark_fast_transfer_as_finalised()` — before the `send_tokens()` promise is confirmed. Because the promise is `.detach()`ed, any failure of the underlying token transfer is silently discarded. If `send_tokens` fails, the relayer's fronted tokens remain locked inside the bridge contract with no recovery path. The code itself acknowledges this gap with an explicit `TODO` comment.

## Finding Description

**`utxo_fin_transfer_fast()` (lines 2518–2561):**

The function first permanently mutates state:
- NEAR destination: `self.remove_fast_transfer(&fast_transfer.id())` deletes the record (line 2530).
- Other-chain destination: `self.mark_fast_transfer_as_finalised(&fast_transfer.id())` permanently locks the record (line 2533).

Then it calls `send_tokens(...).detach()` (lines 2542–2548), discarding the promise result entirely. [1](#0-0) 

The entry point at line 2483–2485 contains an explicit `TODO` acknowledging the unresolved failure case: [2](#0-1) 

**`process_fin_transfer_to_other_chain()` (lines 1980–2054):**

The same pattern: `send_tokens(...).detach()` is called (lines 2029–2039), then `mark_fast_transfer_as_finalised()` is called (line 2040) in the same synchronous frame. The detached promise's failure cannot roll back the state update. [3](#0-2) 

**Contrast with the correctly handled path:**

`fast_fin_transfer_to_near_callback` (lines 838–893) correctly chains a `resolve_fast_transfer` callback that checks the promise result and reverts state on failure: [4](#0-3) [5](#0-4) 

`resolve_fast_transfer` (lines 896–912) calls `remove_fast_transfer` on refund, providing a recovery path that the UTXO path entirely lacks. [6](#0-5) 

**Root cause in `send_tokens`:**

When `msg` is empty and the token is neither wNEAR nor a deployed bridge token, `send_tokens` calls `ft_transfer` (line 2106) on the UTXO token contract. NEP-141's `ft_transfer` panics if the recipient has no storage deposit registered with that token contract, causing the detached promise to fail silently. [7](#0-6) 

## Impact Explanation

When `send_tokens` fails silently:
1. The fast transfer record is either deleted (`remove_fast_transfer`) or permanently locked (`mark_fast_transfer_as_finalised`). Neither state can be undone — there is no un-finalize or re-insert function.
2. The relayer's fronted tokens (transferred to the bridge during `fast_fin_transfer`) remain in the bridge contract with no withdrawal or recovery function.
3. The UTXO connector's tokens consumed by the bridge are also unrecoverable.

This constitutes **permanent freezing of bridged funds**, matching the Critical allowed impact: *"permanent freezing of bridged funds across … Bitcoin, Zcash"*.

## Likelihood Explanation

`ft_transfer` panics if the recipient (the relayer) has no storage deposit registered with the UTXO token contract (e.g., wrapped BTC). A trusted relayer who has not explicitly registered storage with every UTXO-chain token will trigger this failure path during normal protocol operation — no malicious action is required. The UTXO connector is a DAO-configured protocol participant whose `ft_transfer_call` is the standard finalization entry point, making this reachable through the ordinary cross-chain finalization flow. The `TODO` comment in the code confirms the developers are aware this case is unhandled.

## Recommendation

Replace the `.detach()` call in `utxo_fin_transfer_fast` with a chained callback analogous to `resolve_fast_transfer` that:
1. Checks whether `send_tokens` succeeded.
2. If it failed, reverts the fast-transfer state: re-inserts the fast transfer record (or un-marks it as finalised) so the relayer's tokens can be recovered on a subsequent retry.

Apply the same fix to the fast-transfer branch of `process_fin_transfer_to_other_chain`. Additionally, ensure the relayer's storage registration with the UTXO token contract is verified before state mutation, or pre-register storage as part of the relayer onboarding flow.

## Proof of Concept

1. A trusted relayer calls `ft_transfer_call` on the UTXO token contract to the bridge with a `FastFinTransferMsg`, fronting `amount - fee` tokens to the recipient. The bridge stores the fast transfer record via `add_fast_transfer`.
2. The UTXO connector later calls `ft_transfer_call` to the bridge with a `UtxoFinTransferMsg` matching the same transfer. This triggers `utxo_fin_transfer` → `utxo_fin_transfer_fast`.
3. Inside `utxo_fin_transfer_fast`, `remove_fast_transfer()` is called (NEAR destination), permanently deleting the record.
4. `send_tokens(token_id, relayer, amount, "").detach()` is dispatched. Because the relayer has no storage deposit registered with the UTXO token contract, `ft_transfer` panics inside the detached promise.
5. The panic is silently discarded. The fast transfer record is gone. The relayer's fronted tokens remain in the bridge. No recovery function exists.

**Test plan:** Deploy a local NEAR testnet with the bridge contract and a mock NEP-141 UTXO token. Register a trusted relayer without storage on the token contract. Execute steps 1–5 above. Confirm: (a) `ft_transfer` receipt shows failure, (b) fast transfer record no longer exists in bridge state, (c) relayer token balance is unchanged, (d) bridge token balance retains the fronted amount with no withdrawal path.
