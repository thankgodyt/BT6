### Title
NEAR Storage Deposits for Refund Requests Accumulate Permanently with No Recovery Mechanism - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
Every call to `request_refund` and `execute_refund` requires the caller to attach a NEAR storage deposit. These deposits are transferred into the contract's balance and are never returned to users — not on successful finalization, not on rejection. Over time, all attached NEAR tokens accumulate irretrievably in the contract, mirroring the LamboVEthRouter pattern of per-operation dust accumulation with no sweep path.

### Finding Description
The `internal_request_refund` function enforces a minimum attached NEAR deposit: [1](#0-0) 

Similarly, `resolve_execute_refund_timelock` (called by every `execute_refund` entrypoint) enforces a second deposit: [2](#0-1) 

Both deposits flow into the contract's NEAR balance. When a refund request is finalized via `verify_refund_finalize_callback`, the storage entry is removed from `refund_requests`: [3](#0-2) 

No NEAR is returned to the original depositor. The same is true for `internal_reject_refund`, which removes the request without any refund of the attached deposit: [4](#0-3) 

There is no sweep function, no `refund_storage_deposit` path, and no mechanism in `internal_withdraw_protocol_fee` (which only handles nBTC, not NEAR) to recover these accumulated NEAR tokens: [5](#0-4) 

The `ContractData` struct tracks nBTC protocol fees across multiple accounting fields but has no analogous field or recovery path for accumulated NEAR storage deposits: [6](#0-5) 

### Impact Explanation
Every refund lifecycle (request + execute) permanently locks at least two NEAR storage deposits in the contract. As refund volume grows — especially during periods of misconfigured deposits or user errors that trigger the refund path — the cumulative NEAR locked becomes significant. Neither users nor the DAO can recover these funds. This constitutes a permanent, irreversible loss of user-supplied NEAR tokens with no exploit required beyond normal bridge usage.

This matches the allowed Medium impact: **harmful smart-contract behavior without direct funds theft** — specifically, stuck bridge-side funds requiring operator intervention that is structurally impossible given no recovery function exists.

### Likelihood Explanation
The refund path is a publicly reachable, documented bridge feature. Any user whose deposit cannot be processed (wrong amount, configuration mismatch, etc.) will call `request_refund` and `execute_refund`. Each such call permanently loses the attached NEAR deposit. The likelihood is high because the refund flow is a normal operational path, not an edge case.

### Recommendation
Return the storage deposit to the original caller when a refund request is finalized or rejected. Concretely:

1. Track the depositor and deposit amount in `RefundRequest` at `request_refund_callback` time.
2. In `verify_refund_finalize_callback` and `internal_reject_refund`, issue a `Promise::new(depositor).transfer(deposit_amount)` to return the freed storage deposit.
3. Alternatively, add a DAO-callable sweep function that transfers accumulated NEAR above the minimum storage requirement to a designated treasury account.

### Proof of Concept

1. User calls `request_refund(...)` attaching `required_balance_for_request_refund()` NEAR (e.g. 2 NEAR for a large `tx_bytes`).
2. Light client verifies the transaction; `request_refund_callback` stores the `RefundRequest` in `self.data_mut().refund_requests`. The 2 NEAR is now in the contract's balance.
3. After the timelock, user calls `execute_refund(...)` attaching `required_balance_for_execute_refund()` NEAR. Another deposit enters the contract.
4. Relayer calls `verify_refund_finalize(...)`. `verify_refund_finalize_callback` removes the entry from `refund_requests` — freeing the storage — but issues no `Promise::transfer` back to the user.
5. Both NEAR deposits remain permanently in the contract. Repeat for every refund request. No function exists to recover them. [7](#0-6)

    pub fn verify_refund_finalize_callback(&mut self, tx_id: String) -> bool {
        let result_bytes = env::promise_result_checked(0, MAX_BOOL_RESULT)
            .expect("Call verify_transaction_inclusion failed");
        let is_valid = serde_json::from_slice::<bool>(&result_bytes)
            .expect("verify_transaction_inclusion return not bool");
        require!(is_valid, "verify_transaction_inclusion return false");

        let btc_pending_info = self.internal_unwrap_btc_pending_info(&tx_id).clone();
        btc_pending_info.assert_refund_pending_verify_tx();

        let account_id = btc_pending_info.account_id.clone();

        // A refund spends exactly one deposit UTXO, whose key is the refund request
        // key. More than one input would be abnormal for a refund.
        let utxo_storage_keys = btc_pending_info.get_psbt().get_utxo_storage_keys();
        require!(
            utxo_storage_keys.len() == 1,
            "refund transaction must spend exactly one input"
        );
        // Refund confirmed on-chain → drop the request so no further execute_refund
        // is possible. If it was already removed, this is harmlessly a no-op.
        self.data_mut()
            .refund_requests
            .remove(&utxo_storage_keys[0]);

        // Clean up: remove pending info
        self.internal_remove_btc_pending_info(&tx_id);
        self.internal_unwrap_mut_account(&account_id)
            .btc_pending_verify_list
            .remove(&tx_id);

        true
    }
