Audit Report

## Title
Native SOL Fee Payments Permanently Locked in `sol_vault` with No Withdrawal Mechanism — (File: `solana/programs/bridge_token_factory/src/instructions/user/init_transfer.rs`)

## Summary

When a user calls `init_transfer` with a non-zero `native_fee`, that SOL is transferred into the `sol_vault` PDA. No instruction in the program permits withdrawal of these accumulated fee lamports. The NEAR side compensates the relayer by minting wrapped SOL, leaving the actual deposited SOL permanently locked in `sol_vault` with no recovery path.

## Finding Description

In `init_transfer.rs` (L75–86), when `payload.native_fee > 0`, the user's SOL is transferred to `sol_vault`: [1](#0-0) 

In `finalize_transfer_sol.rs` (L79–88), the only instruction that withdraws from `sol_vault` transfers exactly `data.amount` — the bridged SOL principal — to the recipient, never touching any accumulated `native_fee`: [2](#0-1) 

The complete set of program instructions defined in `lib.rs` is: `initialize`, `get_version`, `deploy_token`, `finalize_transfer`, `finalize_transfer_sol`, `log_metadata`, `init_transfer`, `init_transfer_sol`, `pause`, `unpause`, `set_admin`, `set_pausable_admin`, `set_metadata_admin`, `set_derived_near_bridge_address`, `update_metadata`. None of these withdraw `native_fee` lamports from `sol_vault`: [3](#0-2) 

The four admin instructions (`change_config`, `initialize`, `pause`, `update_metadata`) do not reference `sol_vault` for withdrawal:


The `native_fee` from `init_transfer_sol` is similarly locked: both `amount` and `native_fee` are deposited together, but `finalize_transfer_sol` only withdraws `data.amount`: [4](#0-3) 

## Impact Explanation

Every `init_transfer` call with `native_fee > 0` permanently locks that SOL in `sol_vault`. The `sol_vault` balance grows monotonically beyond what is needed to service `finalize_transfer_sol` withdrawals. The excess is irrecoverable without a program upgrade. This constitutes permanent freezing of fee funds and fee mis-accounting — the protocol collects SOL fees on-chain but has no mechanism to distribute or recover them, matching the allowed critical impact of "permanent freezing of bridged funds" and "fee mis-accounting… that changes user or protocol balances." [1](#0-0) 

## Likelihood Explanation

Any unprivileged user bridging SPL tokens with a non-zero `native_fee` triggers this condition through a standard public contract call. The `native_fee` mechanism is the normal operating mode for relayer compensation — it is not an edge case. Every such transfer permanently locks SOL, and the condition is repeatable and cumulative. [5](#0-4) 

## Recommendation

Add an admin-gated `withdraw_fees` instruction that transfers excess lamports from `sol_vault` (i.e., `sol_vault.lamports() - rent_exempt_minimum`) to a designated fee recipient, using a PDA signer with `SOL_VAULT_SEED`. This mirrors the pattern already used in `finalize_transfer_sol` for PDA-signed transfers. [6](#0-5) 

## Proof of Concept

1. Deploy the program and call `initialize`.
2. Call `init_transfer` with `payload.native_fee = 5_000_000` (5 mSOL) for an SPL token transfer. Observe 5_000_000 lamports transferred from user to `sol_vault`.
3. Inspect `sol_vault` balance — it has increased by 5_000_000 lamports.
4. Attempt to call any existing instruction to recover those lamports — none exist.
5. Repeat step 2 N times. `sol_vault` balance grows by `N * 5_000_000` lamports with no recovery path.
6. Confirm via the mollusk test suite: `test_init_transfer.rs` can be extended to assert that `sol_vault` lamports increase by `native_fee` after each call, and that no subsequent instruction reduces `sol_vault` below `sol_vault_initial + sum(native_fees)`. [7](#0-6)
