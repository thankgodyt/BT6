### Title
Batch-abort in `processVotes`/`processCerts` silently discards valid Peras votes and certificates when any single item in a peer-supplied batch fails validation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasVote.hs` and `PerasCert.hs`)

---

### Summary

`processVotes` and `processCerts` implement an all-or-nothing batch policy: if **any** item in a peer-supplied batch fails validation, the **entire** batch is thrown away and the peer is disconnected. Valid votes and certificates co-present in the same batch are silently discarded. An unprivileged peer can exploit this by injecting one crafted-invalid item into a batch that also carries legitimately valid votes/certificates from honest committee members, causing the receiving node to permanently discard those valid objects for that delivery attempt and disconnect from the sender. This is the direct structural analog of the AMM `settleFunding` revert-instead-of-skip bug: one item not satisfying a condition aborts processing for all others.

---

### Finding Description

**`processVotes`** in `PerasVote.hs`:

```haskell
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (...) votes
    mapM validateVote votesNotAlreadyInDb          -- validate ALL
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    ([], validatedVotes) ->
      mapM_ (addVote . WithArrivalTime now) validatedVotes   -- add only if ALL valid
    (errs, _) ->
      throw (PerasVoteValidationError errs)                  -- throw if ANY invalid
``` [1](#0-0) 

The `(errs, _)` branch discards the `_` component — the already-validated valid votes — and throws unconditionally. The identical pattern exists in `processCerts`: [2](#0-1) 

Both functions are wired into the production node-to-node diffusion path via `makePerasVotePoolWriterFromChainDB` and `makePerasCertPoolWriterFromChainDB`, which are called from `hPerasVoteDiffusionClient` / `hPerasCertDiffusionClient` in `NodeToNode.hs`: [3](#0-2) 

The thrown exception (`PerasVoteInboundException` / `PerasCertInboundException`) propagates up through the ObjectDiffusion inbound mini-protocol runner and causes the peer connection to be torn down, as documented in the code comments themselves. [4](#0-3) 

**Aggravating production detail**: the current production wiring passes `(pure (PerasVoteStakeDistr mempty))` as the stake distribution, which the code itself notes "will cause all votes to be considered invalid." [5](#0-4) 

This means that in the current production build, **every non-empty vote batch from every peer is unconditionally rejected**, making the entire Peras vote diffusion path non-functional.

---

### Impact Explanation

Peras certificates directly affect chain selection. A `ValidatedPerasCert` is stored in the `PerasCertDB`, which feeds `implGetWeightSnapshot` to produce a `PerasWeightSnapshot`. [6](#0-5) 

That snapshot is consumed by `weightBoostOfFragment` and `preferAnchoredCandidate` during chain selection: [7](#0-6) [8](#0-7) 

If an adversary can prevent a node from accumulating enough valid votes to reach quorum, no certificate is forged, no weight boost is applied, and the node's chain selection operates without the Peras security boost. A chain that should be preferred due to its Peras weight may not be selected, or a fork that should be rejected may be preferred. This satisfies the **High** impact criterion: an unprivileged peer can make an honest node prefer a non-canonical or less-secure chain beyond the intended Peras security assumptions.

Additionally, `addPerasCertAsync` is documented to trigger a chain-selection fork switch when a certificate makes a candidate heavier: [9](#0-8) 

Suppressing certificate delivery therefore directly suppresses fork switches that Peras is designed to enforce.

---

### Likelihood Explanation

The attack entry path is the ObjectDiffusion inbound mini-protocol, reachable by any unprivileged peer. The adversary needs only to:

1. Connect to the target node as a peer (no stake, no keys required).
2. Collect legitimate votes/certificates from honest committee members via the same diffusion network.
3. Append one crafted-invalid item (e.g., a vote with a voter ID absent from the stake distribution, or a certificate with an invalid round number) to the batch before forwarding it.
4. The target node's `processVotes`/`processCerts` rejects the entire batch, discards the valid items, and disconnects.

The adversary can reconnect (or use multiple sybil peers) and repeat. Because the valid items are never added to the local DB, the node must re-obtain them from other honest peers — which the adversary can also poison. The attack requires no cryptographic material and no stake. Likelihood is **High** once Peras is activated.

---

### Recommendation

Replace the all-or-nothing policy with a skip-and-continue policy, mirroring the fix suggested in the original AMM report:

```haskell
-- Instead of:
case partitionEithers validationResults of
  ([], validatedVotes) -> mapM_ (addVote . WithArrivalTime now) validatedVotes
  (errs, _)            -> throw (PerasVoteValidationError errs)

-- Do:
case partitionEithers validationResults of
  ([], validatedVotes) -> mapM_ (addVote . WithArrivalTime now) validatedVotes
  (errs, validVotes)   -> do
      mapM_ (addVote . WithArrivalTime now) validVotes   -- persist valid items
      throw (PerasVoteValidationError errs)              -- still disconnect for the invalid ones
```

This ensures valid votes/certificates from honest committee members are never discarded because an adversary co-mingled one invalid item in the same batch. The peer is still disconnected for sending invalid data, preserving the punishment semantics. Apply the same fix to `processCerts`.

Additionally, the hardcoded `(pure (PerasVoteStakeDistr mempty))` in `NodeToNode.hs` must be replaced with the actual committee stake distribution before Peras vote diffusion can function at all.

---

### Proof of Concept

**Setup**: Node A is the victim. Adversary peer E connects to A. Honest committee members V1…Vn have cast valid votes for round R, block B. E has collected these votes via the diffusion network.

**Attack**:
1. E constructs a batch: `[vote_V1, vote_V2, …, vote_Vn, vote_crafted_invalid]` where `vote_crafted_invalid` has a voter ID not present in the stake distribution.
2. E sends this batch to A via the ObjectDiffusion inbound protocol.
3. A calls `processVotes`. `mapM validateVote` validates all items. `vote_crafted_invalid` returns `Left PerasValidationErr`.
4. `partitionEithers` yields `(errs=[PerasValidationErr], validVotes=[vote_V1..vote_Vn])`.
5. The `(errs, _)` branch fires: `throw (PerasVoteValidationError errs)`. The `_` (valid votes) is discarded.
6. A disconnects from E. `vote_V1…vote_Vn` are never added to A's `PerasVoteDB`.
7. E reconnects (or sybil peers E2, E3 repeat the same attack from different connections).
8. A never accumulates enough votes to reach quorum for round R. No certificate is forged for block B. Block B receives no Peras weight boost. Chain selection proceeds without the Peras security guarantee for this round. [10](#0-9) [11](#0-10)
