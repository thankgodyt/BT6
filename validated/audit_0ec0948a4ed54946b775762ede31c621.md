### Title
Peras Certificate Validation Unconditionally Returns Success, Allowing Unauthorized Certificate Acceptance from Any Peer — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The degenerate `BlockSupportsPeras` instance used for all block types implements `validatePerasCert` as a stub that unconditionally returns `Right` (success) without performing any cryptographic or semantic checks. This instance is wired directly into the production inbound Peras certificate diffusion handler. As a result, any Peras certificate received from an unprivileged peer is accepted and stored in the ChainDB without validation, bypassing the entire Peras certificate verification layer.

### Finding Description

**Root cause:** The `BlockSupportsPeras` instance in `SupportsPeras.hs` (lines 320–358) is explicitly labelled a "degenerate instance for all blks to get things to compile." Its `validatePerasCert` implementation ignores all certificate fields and unconditionally returns a `ValidatedPerasCert`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is passed directly as the `validateCert` callback in both `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB`:

```haskell
(validatePerasCert mkPerasParams)  -- TODO replace when actual plumbing is in place
``` [2](#0-1) [3](#0-2) 

`makePerasCertPoolWriterFromChainDB` is the production writer wired into the `hPerasCertDiffusionClient` handler in `NodeToNode.hs`:

```haskell
(makePerasCertPoolWriterFromChainDB systemTime getChainDB)
``` [4](#0-3) 

**Exploit path:**

1. An unprivileged peer connects to a node via the standard node-to-node protocol.
2. The peer sends a batch of crafted `PerasCert` objects over the `hPerasCertDiffusionClient` mini-protocol channel.
3. `processCerts` calls `validateCert` (bound to `validatePerasCert mkPerasParams`) on each certificate.
4. `validatePerasCert` returns `Right ValidatedPerasCert{...}` for every certificate regardless of content.
5. `processCerts` sees no errors and calls `addCert` (bound to `void . ChainDB.addPerasCertAsync chainDB`) for each certificate.
6. The crafted certificates are stored in the ChainDB with their full `vpcCertBoost` weight applied. [5](#0-4) 

**Analog to the ERC20 report:** Just as `JBERC20PaymentTerminal#_transferFrom` calls `IERC20#transfer` without checking the return value — allowing a failed transfer to silently proceed — `validatePerasCert` returns a success value unconditionally, allowing any certificate (including cryptographically invalid or semantically malformed ones) to silently pass validation and be accepted into the node's state.

### Impact Explanation

A Peras certificate stored in the ChainDB contributes a `vpcCertBoost` weight to the boosted block during chain selection. An attacker who can inject arbitrary certificates can boost any block — including one on a non-canonical or adversarial fork — causing an honest node to prefer that fork over the canonical chain. This is a **Critical** bypass of Peras certificate verification: an unprivileged peer can make a node accept an invalid certificate and use it to influence chain selection, violating the Peras finality guarantee.

### Likelihood Explanation

The vulnerability is reachable by any peer that can establish a standard node-to-node connection. No privileged keys, stake majority, or special access is required. The `hPerasCertDiffusionClient` handler is active whenever Peras certificate diffusion is enabled. The attacker only needs to send a well-formed CBOR-encoded `PerasCert` with a `pcCertRound` not already in the database and a `pcCertBoostedBlock` pointing to a target block.

### Recommendation

Replace the stub `validatePerasCert` implementation with one that performs the full cryptographic and semantic checks required by the Peras specification — including aggregate BLS signature verification, voter eligibility checks, quorum threshold enforcement, and round/block consistency checks — before returning `Right`. Until the real implementation is ready, the stub should return `Left PerasValidationErr` (reject all) rather than `Right` (accept all), so that the safe default is rejection rather than acceptance. The pattern mirrors the ERC20 fix: use a safe helper (`SafeERC20`) that enforces correct handling; here, enforce that `validatePerasCert` never silently succeeds on unvalidated input.

### Proof of Concept

1. Start a node with Peras certificate diffusion enabled.
2. Connect as a peer and send a `PerasCert` with:
   - `pcCertRound` set to any round not yet in the database.
   - `pcCertBoostedBlock` pointing to a block on an adversarial fork.
3. Observe that `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams}`.
4. The certificate is added to the ChainDB via `ChainDB.addPerasCertAsync`.
5. Chain selection now applies the boost weight to the adversarial fork's block, potentially causing the node to switch to the adversarial chain.

The deterministic root cause is at:
- `SupportsPeras.hs` lines 353–358: `validatePerasCert` returns `Right` unconditionally.
- `PerasCert.hs` lines 126, 168–173: the stub is used as the sole validator for all inbound peer certificates.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
