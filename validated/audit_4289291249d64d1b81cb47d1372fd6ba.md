### Title
Peras Certificate Validation Bypass via Stub `validatePerasCert` Enables Unauthorized Chain-Weight Manipulation — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance in `SupportsPeras.hs` provides a stub `validatePerasCert` that unconditionally returns `Right` for every inbound certificate, performing no cryptographic or semantic checks. Any unprivileged peer can therefore inject an arbitrary `PerasCert` through the Peras certificate miniprotocol. The certificate is accepted, stored in `PerasCertDB`, and immediately triggers chain selection for the boosted block. Because Peras weight is additive to block count in chain comparison, a crafted certificate can make a shorter, adversary-controlled chain appear heavier than the honest chain, causing the node to switch away from the canonical chain.

---

### Finding Description

**Root cause — stub validation always succeeds**

The catch-all instance for `BlockSupportsPeras` (which applies to every block type, including production Cardano blocks) contains:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature, round-number, boosted-block, or committee-membership check is performed. The function returns `Right` for every input.

**Inbound path — reachable by any peer**

`processCerts` in the Peras certificate object-pool writer calls `validatePerasCert mkPerasParams` on every certificate received from a remote peer:

```haskell
(validatePerasCert mkPerasParams)  -- TODO replace when actual plumbing is in place
``` [2](#0-1) [3](#0-2) 

A batch of certificates passes validation if and only if none of them fail `validatePerasCert`. Because the stub never fails, every batch passes.

**Chain-selection consequence**

After a certificate is stored in `PerasCertDB`, `chainSelSync` triggers chain selection for the boosted block:

```haskell
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

Chain selection uses `totalWeightOfFragment`, which adds the Peras weight boost to the block count:

```haskell
totalWeightOfFragment weightSnap frag =
  weightLength <> weightBoost
 where
  weightLength = PerasWeight $ fromIntegral $ AF.length frag
  weightBoost  = weightBoostOfFragment weightSnap frag
``` [5](#0-4) 

A crafted certificate with a large `PerasWeight` (drawn from `perasWeight params`, which is a static config value) applied to a block on a shorter adversary chain can make that chain's total weight exceed the honest chain's weight, causing the node to switch.

**Compounding factor — certificates are never extracted from blocks**

The same stub instance also provides:

```haskell
-- TODO: extract actual Peras certificates from blocks when the HFC plumbing is in place.
getPerasCertInBlock _ = Nothing
``` [6](#0-5) 

This means the `PerasWeightSnapshot` used for chain selection is populated **exclusively** from the gossip network, not from on-chain data. The entire Peras weight signal is therefore under adversary control via the certificate miniprotocol.

**Analog to the original vulnerability class**

The original H-8 bug involves reading from an uninitialized data structure that returns a default value (0), which is then treated as a valid initialized value in an arithmetic formula, producing an inflated result that corrupts downstream state. Here, the "uninitialized" validation stub returns a default success value (`Right`) for every input, treating every unauthenticated certificate as a fully validated one. Both bugs share the pattern: *a placeholder/default return value is consumed by downstream logic as if it were a genuine, verified result*, corrupting the invariant that downstream logic depends on (fee accounting in the original; chain weight in this case).

---

### Impact Explanation

An unprivileged peer can send a `PerasCert` message boosting any block hash it chooses. The certificate is accepted without any check, stored in `PerasCertDB`, and immediately triggers chain selection. If the boosted block is on a chain that is shorter than the honest chain by fewer blocks than the configured `PerasWeight` boost, the node will switch to the adversary's chain. This is a **consensus safety failure**: the node accepts a non-canonical chain that it would otherwise reject under the standard longest-chain rule.

---

### Likelihood Explanation

The Peras certificate miniprotocol is wired into the production diffusion layer (`makePerasCertPoolWriterFromChainDB`). Any peer that can establish a connection and speak the Peras object-diffusion protocol can send crafted certificates. No stake, keys, or operator access is required. The only prerequisite is that the Peras certificate gossip protocol is active in the node's network configuration. Given that the code is present and compiled into the production binary, the attack surface exists for any deployment that enables Peras.

---

### Recommendation

1. Replace the stub `validatePerasCert` with a real implementation that verifies the certificate's cryptographic aggregate signature against the claimed committee members and checks that the boosted block and round number are within valid bounds.
2. Until real validation is implemented, the stub should be guarded by a feature flag that prevents the Peras certificate miniprotocol from being activated in production builds.
3. `getPerasCertInBlock` should be implemented so that the authoritative source of Peras weight is the on-chain record, not the unauthenticated gossip network.

---

### Proof of Concept

1. Establish a peer connection to a target node that has the Peras certificate miniprotocol enabled.
2. Construct a `PerasCert` with `pcCertRound = <any round>` and `pcCertBoostedBlock = <point on a shorter adversary chain>`.
3. Send the certificate via the miniprotocol. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right` unconditionally.
4. The certificate is stored in `PerasCertDB`. `chainSelSync` calls `chainSelectionForBlock` for the boosted block.
5. `totalWeightOfFragment` for the adversary's chain now equals `adversaryChainLength + perasWeight params`. If `perasWeight params > honestChainLength - adversaryChainLength`, the node switches to the adversary's chain.
6. The node has accepted a non-canonical chain without any cryptographic justification.
