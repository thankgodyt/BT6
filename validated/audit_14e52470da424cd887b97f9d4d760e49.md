### Title
Unconditional Peras Certificate Acceptance Enables Arbitrary Chain-Weight Inflation via Crafted Peer Messages - (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `validatePerasCert` implementation is a stub that unconditionally accepts every inbound `PerasCert` regardless of its cryptographic content. An unprivileged peer can send a crafted certificate naming any block as the boosted target; the certificate is stored in `PerasCertDB`, the `PerasWeightSnapshot` is updated, and chain selection is immediately re-triggered with the inflated weight. This is the Ouroboros-Consensus analog of the external "dilution" report: just as an attacker front-runs a donation to inflate their pool share, here an attacker injects fake certificates to inflate the Peras weight of an adversarial chain fragment, causing honest nodes to prefer it over the canonical chain.

---

### Finding Description

**Root cause — stub validation always returns `Right`** [1](#0-0) 

```haskell
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
```

No signature, committee-membership, round-number, or boosted-block checks are performed. Every `PerasCert` that arrives from the network is immediately wrapped in `ValidatedPerasCert` and returned as `Right`.

**Entry path — inbound certificate diffusion**

Both production pool-writer constructors call this stub with a hardcoded `mkPerasParams`: [2](#0-1) 

`processCerts` calls `validateCert` on each inbound certificate. Because `validatePerasCert` never returns `Left`, the `(errs, _)` branch is never taken; every certificate in the batch is timestamped and forwarded to `addCert`.

**Chain-selection trigger**

Once stored, `addPerasCertAsync` queues a `ChainSelAddPerasCert` message. The single-threaded chain-selection loop processes it: [3](#0-2) 

After adding the certificate to `PerasCertDB`, the code calls `chainSelectionForBlock` for the boosted block. Chain selection reads the `PerasWeightSnapshot` derived from all stored certificates: [4](#0-3) 

The snapshot is a plain sum of `(boostedBlock, boost)` pairs from every certificate in the DB — no authenticity check at read time either.

**Chain-order comparison uses the inflated snapshot** [5](#0-4) 

`preferCandidate` compares `wsvTotalWeight` (block-count + weight boost). A fake certificate with a large `perasWeight` can make a shorter adversarial fragment appear heavier than the honest chain, triggering a `ShouldSwitch`.

---

### Impact Explanation

**Impact class:** Critical — Bypass of Peras certificate/vote verification checks that enables unauthorized certificate acceptance and chain-selection manipulation.

An unprivileged peer that can send a single well-formed CBOR-encoded `PerasCert` message (no keys, no stake, no committee membership required) can:

1. Name any block in the VolatileDB as the boosted target.
2. Have that block's Peras weight inflated by `perasWeight params` (a static protocol parameter).
3. Force the victim node to re-run chain selection with the inflated weight, potentially switching to an adversarial fork.

Because `takeVolatileSuffix` uses the same `PerasWeightSnapshot` to determine the immutability boundary: [6](#0-5) 

a sufficiently large fake boost can also shrink the volatile suffix, causing blocks that should still be rollback-eligible to be treated as immutable, permanently locking in an adversarial chain segment.

---

### Likelihood Explanation

- Peras is opt-in (disabled by default per the CHANGELOG), so the attack surface is limited to nodes that enable it.
- When Peras is enabled, the certificate diffusion mini-protocol is active and reachable from any connected peer without authentication.
- The attacker needs only to construct a valid CBOR encoding of `PerasCert` (round number + block point) — no cryptographic material is required because validation is entirely skipped.
- The TODO comment and linked issue (`cardano-peras/issues/120`) confirm this is a known placeholder, not an intentional design.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
1. The aggregate BLS signature over `(roundNo, boostedBlock)` against the committee's aggregate verification key.
2. That the claimed voters are eligible committee members for the given round (VRF/sortition proof).
3. That the total stake of the signers exceeds the quorum threshold.

Until the real implementation is in place, inbound certificates from untrusted peers should be rejected at the diffusion layer when Peras is enabled, or the `PerasWeightSnapshot` should not be used in `preferCandidate` until certificate validation is complete.

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes

  -- Deliver promise indicating that we processed the cert.
  lift $ atomically $ putTMVar varProcessed certResult
