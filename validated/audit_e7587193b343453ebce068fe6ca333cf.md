### Title
Peras Vote Signature Verification Bypass Allows Unbounded Fake Stake Accumulation and Unauthorized Certificate Forging — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `validatePerasVote` implementation omits all cryptographic signature and committee-eligibility verification, accepting any vote whose voter ID merely appears in the stake distribution. An unprivileged peer can craft votes impersonating arbitrary stake pools without possessing their private keys. Because the per-round deduplication guard is keyed on `(roundNo, voterId)`, the attacker bypasses it by cycling through different voter IDs — exactly mirroring the external report's pattern of bypassing a per-epoch check by transferring state to a new identifier. The accumulated fake stake can exceed the quorum threshold, causing a fraudulent Peras certificate to be forged for an attacker-chosen block and directly manipulating chain selection on honest nodes.

---

### Finding Description

**Vulnerability class:** Bypass of Peras vote/certificate signature validation enabling unauthorized certificate acceptance and chain-selection manipulation.

**Root cause — `validatePerasVote` stub (production instance):**

The `BlockSupportsPeras` typeclass declares `validatePerasVote` as the mandatory gate for all inbound votes. The only production instance — the blanket `instance StandardHash blk => BlockSupportsPeras blk` — implements it as a stub that performs no cryptographic check whatsoever:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [1](#0-0) 

The only check performed is `lookupPerasVoteStake`, which is a plain `Map.lookup` on the voter ID:

```haskell
lookupPerasVoteStake vote distr =
  Map.lookup (pvVoteVoterId vote) (unPerasVoteStakeDistr distr)
``` [2](#0-1) 

No signature is verified. No VRF-based committee-eligibility proof is checked. The `_params` argument is discarded entirely.

**Production entry path — `makePerasVotePoolWriterFromChainDB`:**

This stub is wired directly into the live vote-ingestion pipeline:

```haskell
(\vote -> getStakeDistrSTM >>= \sd ->
    pure $ validatePerasVote mkPerasParams sd vote)
``` [3](#0-2) 

Every vote received from a peer over the object-diffusion mini-protocol passes through this call before being stored.

**Per-round deduplication guard — the bypassed check:**

`implAddVote` prevents a voter from voting twice in the same round by checking membership in `pvdsVoteIds`, which is a `Set (PerasVoteId blk)` where `PerasVoteId = (roundNo, voterId)`:

```haskell
addOrIgnoreVote pvds voteId
  | Set.member voteId (pvdsVoteIds pvds) = voteAlreadyInDB pvds
  | otherwise = tryAddVote pvds voteId
``` [4](#0-3) 

Because `validatePerasVote` does not verify signatures, an attacker can submit votes using **different voter IDs** from the public stake distribution — each with a distinct `PerasVoteId` — bypassing this guard entirely. This is the direct analog of the external report: just as `Voter.reset()` is bypassed by transferring voting power to a new `tokenId` via `merge()`, the per-round deduplication is bypassed by cycling through different voter IDs, none of which require the corresponding private key.

**Quorum and certificate forging:**

`updateCandidateVoteState` calls `votesReachQuorum` after each vote is tallied. Once the accumulated fake stake crosses the threshold, `forgePerasCert` is called and a `ValidatedPerasCert` is produced for the attacker's chosen block: [5](#0-4) 

The forged certificate is then stored in `PerasCertDB` and used to boost the weight of the targeted block in chain selection.

**Companion stub — `validatePerasCert` also unconditionally accepts any certificate:**

```haskell
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [6](#0-5) 

This means a peer can also skip the vote-accumulation step entirely and inject a pre-formed certificate directly, which is accepted without any cryptographic check via `makePerasCertPoolWriterFromChainDB`. [7](#0-6) 

---

### Impact Explanation

An unprivileged peer can forge Peras certificates for arbitrary blocks by submitting fake votes impersonating stake pools whose IDs appear in the public stake distribution. The forged certificate is stored in `PerasCertDB` and applied as a weight boost to the attacker's chosen block during chain selection. Honest nodes will prefer the boosted (non-canonical) chain, constituting a **critical consensus safety failure**: an invalid ledger state is accepted as the preferred chain without any operator fault or key compromise.

This matches the allowed critical impact: *"Bypass of… certificate/signature validation… that enables unauthorized… certificate acceptance."*

---

### Likelihood Explanation

**High.** The vulnerable code is the sole production instance of `BlockSupportsPeras`, active for all block types. It is reachable by any connected peer via the object-diffusion mini-protocol with no authentication barrier. The stake distribution is public on-chain data. No private keys, stake majority, or special privileges are required.

---

### Recommendation

1. **`validatePerasVote`**: Implement full cryptographic verification — verify the vote signature against the voter's registered public key, and for non-persistent committee members verify the VRF-based local-sortition eligibility proof (as already implemented in `implVerifyVote` for the `WFALS` committee scheme).
2. **`validatePerasCert`**: Implement aggregate-signature verification over the certificate's `(roundNo, boostedBlock)` payload, verifying that the signers constitute a quorum of eligible committee members for that round.
3. Track the GitHub issues already filed (`cardano-peras/issues/120`, `cardano-peras/issues/73`) and treat them as security-critical blockers before any Peras-enabled deployment.

---

### Proof of Concept

```
Precondition: attacker is a connected peer; stakeDistr is public.

1. Read stakeDistr = { pool_A: 0.30, pool_B: 0.30, pool_C: 0.30, ... }
   (quorum threshold = 0.75)

2. Craft three votes for round r, targeting attacker-controlled block p:
     vote1 = PerasVote { pvVoteRound=r, pvVoteBlock=p, pvVoteVoterId=pool_A }
     vote2 = PerasVote { pvVoteRound=r, pvVoteBlock=p, pvVoteVoterId=pool_B }
     vote3 = PerasVote { pvVoteRound=r, pvVoteBlock=p, pvVoteVoterId=pool_C }
   (no private keys needed)

3. Send vote1, vote2, vote3 via object-diffusion mini-protocol.

4. On the receiving node:
   - validatePerasVote accepts each (voter IDs are in stakeDistr).
   - Per-round deduplication passes (three distinct PerasVoteIds).
   - Accumulated stake = 0.90 > 0.75 quorum threshold.
   - updateCandidateVoteState calls forgePerasCert → ValidatedPerasCert for block p, round r.

5. Certificate stored in PerasCertDB; block p receives weight boost.
   Honest nodes switch to the attacker's chain containing block p.
```

    case votesReachQuorum cfg voteList of
