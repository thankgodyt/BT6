Audit Report

## Title
Missing `storage.total` Update in `try_to_transfer_balance_from_message_account` Causes Withdrawal Failure for Transferred Native Fee Funds — (File: `near/omni-bridge/src/storage.rs`)

## Summary

`try_to_transfer_balance_from_message_account` credits the message account's full balance into the storage-payer's `available` field without updating `total`, violating the `total >= available` invariant required by `storage_withdraw`. Any NEAR deposited to a message account becomes unwithdrawable via the normal withdrawal path, and the only escape (`storage_unregister(force: true)`) is destructive, abandoning the in-flight transfer and leaving orphaned transfer state in the contract.

## Finding Description

In `near/omni-bridge/src/storage.rs` lines 276–289, `try_to_transfer_balance_from_message_account` reads the message account's `balance.total`, adds it to `storage.available` of the storage-payer, then writes back only the modified `storage` struct and removes the message account:

```rust
storage.available = storage.available.saturating_add(balance.total);  // available grows
// storage.total is never touched
self.accounts_balances.insert(storage_payer, &storage);
self.accounts_balances.remove(account_id);
```

After this call the storage-payer's `StorageBalance` satisfies `available > total`.

`storage_withdraw` (lines 193–205) uses `storage.available` as the default withdrawal amount and subtracts it from `storage.total`:

```rust
let to_withdraw = amount.unwrap_or(storage.available);
storage.total = storage.total.checked_sub(to_withdraw).near_expect(...);
```

Because `to_withdraw` (= inflated `available`) exceeds `total`, `checked_sub` returns `None` and the call panics. The storage-payer can never withdraw the portion of their `available` balance that originated from the message account.

The only alternative exit is `storage_unregister(force: true)` (lines 214–237), which refunds `required_balance_for_account() + storage.available` and removes the account. However, this is called after `init_transfer_internal` has already stored the pending transfer message under the storage-payer's account. Force-unregistering removes the storage-payer's balance record while leaving the orphaned `TransferMessageStorage` entry in the contract, corrupting transfer state and making the in-flight transfer unfinalizeable.

The same bug is triggered in the yield-resume path at `lib.rs` lines 635–645, so both the synchronous and asynchronous message-account flows are affected.

## Impact Explanation

This is a concrete escrow/fee mis-accounting impact: every NEAR deposited to a message account to pre-fund a native fee is rendered unwithdrawable once `try_to_transfer_balance_from_message_account` succeeds. The storage-payer's `available` is inflated (so storage-cost checks pass and the transfer proceeds), but the corresponding `total` is not updated, making the extra funds permanently inaccessible through the standard NEP-145 withdrawal interface. The only recovery path is destructive and leaves orphaned contract state. This matches the allowed Critical impact class: "Balance manipulation, escrow mis-accounting, fee mis-accounting … that changes user or protocol balances."

## Likelihood Explanation

The vulnerable path requires no privilege. Any user can:
1. Call `storage_deposit` on the bridge for a message-account address (public, payable).
2. Call `ft_transfer_call` on any registered token with an `InitTransfer` message referencing that message account.

`try_to_transfer_balance_from_message_account` is invoked unconditionally inside `init_transfer` whenever the message account has sufficient balance (`lib.rs` lines 566–573). The pattern is documented and intended for production use, so it will be triggered by ordinary bridge users, not just adversarial actors.

## Recommendation

Add the missing `storage.total` update immediately before the `available` update so both fields reflect the transferred amount:

```rust
storage.total   = storage.total.saturating_add(balance.total);   // add this line
storage.available = storage.available.saturating_add(balance.total);
```

Apply the same fix in both call sites: the synchronous path in `init_transfer` and the yield-resume path in `init_transfer_resume`.

## Proof of Concept

1. Alice calls `storage_deposit` for `msg.alice.near` with 2 NEAR attached; `msg.alice.near` now has `{total: 2 NEAR, available: ~1.9 NEAR}`.
2. Alice calls `ft_transfer_call` with `native_token_fee = 1 NEAR` and an `InitTransfer` message referencing `msg.alice.near`.
3. `try_to_transfer_balance_from_message_account` runs:
   - Alice's signer `storage.available` += 2 NEAR.
   - Alice's signer `storage.total` is **unchanged**.
   - `msg.alice.near` account is removed.
4. `init_transfer_internal` proceeds, storing the pending transfer and deducting storage cost from `available`.
5. Alice calls `storage_withdraw` with no amount:
   - `to_withdraw = storage.available` (original + ~2 NEAR).
   - `storage.total.checked_sub(to_withdraw)` → `None` → panic.
6. Alice calls `storage_withdraw` with `amount = 1 yoctoNEAR` less than `total`:
   - Succeeds only up to the original `total`; the ~2 NEAR from the message account is inaccessible.
7. Alice calls `storage_unregister(force: true)`:
   - Recovers `required_balance_for_account() + storage.available` but abandons the pending transfer, leaving an orphaned `TransferMessageStorage` entry in the contract.

A unit test can reproduce step 5 by constructing a `StorageBalance` with `available > total` and asserting that `storage_withdraw` panics.
