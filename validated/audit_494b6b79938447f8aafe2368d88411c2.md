Audit Report

## Title
Removed Custom Tokens Can Still Be Bridged via `initTransfer` After `removeCustomToken` — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
`removeCustomToken` clears all four EVM-side mappings for a token but has no corresponding NEAR-side removal. After removal, `initTransfer` contains no registration check, so the call silently falls through to the native-lock `else` branch — locking tokens instead of burning them — while the NEAR side, whose `token_decimals` and `token_address_to_id` entries remain intact, processes the proof and mints/unlocks NEAR-side tokens normally. This inflates the cross-chain token supply with every such transfer.

## Finding Description

`removeCustomToken` clears `isBridgeToken`, `nearToEthToken`, `nearToEthToken`, and `customMinters` for the given address: [1](#0-0) 

`initTransfer` evaluates the token against three branches with no prior registration check: [2](#0-1) 

After removal, `customMinters[tokenAddress]` is `address(0)` and `isBridgeToken[tokenAddress]` is `false`, so execution falls through to the final `else` branch, which calls `safeTransferFrom` to lock tokens in the contract rather than burning them. The `InitTransfer` event is then emitted unconditionally: [3](#0-2) 

On the NEAR side, `fin_transfer_callback` looks up `token_decimals` using the EVM address from the event: [4](#0-3) 

Because `removeCustomToken` is EVM-only and there is no NEAR-side removal function, `token_decimals` and `token_address_to_id` still contain the removed token's entry. `get_token_id` succeeds: [5](#0-4) 

The NEAR side then mints or unlocks NEAR-side tokens for the recipient, completing the transfer as if the token had never been removed. The root cause is the absence of any registration guard at the entry of `initTransfer` and the absence of any NEAR-side removal path in `removeCustomToken`.

## Impact Explanation

**Critical — balance manipulation and escrow mis-accounting.** Before removal, `initTransfer` burns EVM tokens via the custom minter, maintaining the cross-chain supply invariant. After removal, EVM tokens are merely locked (supply not reduced) while the NEAR side still mints the corresponding NEAR tokens, inflating total cross-chain supply with every transfer. If the removed token is malicious (e.g., its contract allows the owner to mint arbitrary amounts), the attacker can mint unlimited EVM tokens at zero cost, call `initTransfer` repeatedly, and drain the NEAR bridge's token reserves indefinitely. This matches the allowed impact class: *balance manipulation, escrow mis-accounting that changes user or protocol balances*.

## Likelihood Explanation

**Medium.** The precondition is that an admin has called `removeCustomToken` — an action taken specifically because the token is problematic. Once that state exists, the exploit window is unbounded: because there is no NEAR-side removal function, the NEAR registry retains the token mapping permanently. Any unprivileged external user (including the token's own deployer) can call `initTransfer` without any special privilege. The only available mitigation is `pauseAll()`, which halts the entire bridge. [6](#0-5) 

## Recommendation

Add a registration check at the top of the `else` branch in `initTransfer` (and analogously in `initTransfer1155`) before any token movement occurs:

```solidity
} else {
    require(
        bytes(ethToNearToken[tokenAddress]).length > 0 ||
        multiTokens[tokenAddress].tokenAddress != address(0),
        "ERR_TOKEN_NOT_REGISTERED"
    );
    IERC20(tokenAddress).safeTransferFrom(
        msg.sender,
        address(this),
        amount
    );
}
```

Alternatively, add the check at the very top of `initTransfer` for all non-zero token addresses, before any branching. Additionally, `removeCustomToken` should either (a) emit an event that triggers NEAR-side de-registration, or (b) be accompanied by a NEAR-side admin function that removes the corresponding `token_decimals` and `token_address_to_id` entries.

## Proof of Concept

1. Admin calls `addCustomToken("tok.near", tokenAddr, customMinter, 18)` — all four EVM mappings set; NEAR side registers `token_decimals` and `token_address_to_id` via the relayed `DeployToken` event.
2. Admin calls `removeCustomToken(tokenAddr)` — all four EVM mappings cleared; NEAR side unchanged.
3. Attacker (controlling the malicious token contract) mints `N` tokens to themselves.
4. Attacker calls `initTransfer(tokenAddr, N, 0, 0, "attacker.near", "")`:
   - `customMinters[tokenAddr]` == `address(0)` → first branch skipped.
   - `isBridgeToken[tokenAddr]` == `false` → second branch skipped.
   - `safeTransferFrom(attacker, bridge, N)` executes — tokens locked, not burned.
   - `InitTransfer` event emitted.
5. Relayer submits proof to NEAR `fin_transfer`.
6. NEAR `fin_transfer_callback` finds `token_decimals` entry (never removed), resolves NEAR token ID via `token_address_to_id` (never removed), and mints/unlocks NEAR tokens to `attacker.near`.
7. Attacker repeats from step 3, draining NEAR-side reserves indefinitely.

A local integration test can reproduce this by: (a) deploying `OmniBridge` and a mock ERC-20 with unrestricted minting, (b) calling `addCustomToken`, then `removeCustomToken`, (c) minting tokens and calling `initTransfer`, (d) asserting that the `InitTransfer` event is emitted and tokens are locked rather than burned, and (e) simulating the NEAR-side callback with the retained `token_decimals` entry to confirm minting succeeds.
