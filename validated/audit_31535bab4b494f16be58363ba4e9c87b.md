### Title
Peras Certificate Signature Verification Bypass via `validatePerasCert` Stub — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` function unconditionally returns `Right` (success) for every inbound Peras certificate, performing zero cryptographic or structural validation. This function is wired directly into the live node-to-node `hPerasCertDiffusionClient` handler. Any unprivileged peer can therefore inject arbitrary forged `PerasCert` values that are accepted, stored in the `PerasCertDB`, and fed into chain selection, where they apply a Peras weight boost to any block the attacker names — including blocks on competing forks.

---

### Finding Description

**Vulnerability class (analog mapping):** The external report describes a three-party authorization bypass: `transferFrom(from, to, amount)` checks `msg.sender` and `to` for blacklisting but omits the check on `from`. The analog here is the Peras certificate ingest path, which checks the receiving node's state and the sending peer's connection status, but entirely omits verification of the certificate's *issuer* (the committee voters whose aggregate signature should authorize the cert).

**Root cause — `validatePerasCert` stub:**

The only production `BlockSupportsPeras` instance is the universal `instance StandardHash blk => BlockSupportsPeras blk` defined in `SupportsPeras.hs`. Its `validatePerasCert` implementation is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

No signature is verified, no round-number bounds are checked against the ledger, no committee membership is confirmed. Every certificate is unconditionally promoted to `ValidatedPerasCert`.

**Production wiring — `hPerasCertDiffusionClient`:**

In `NodeToNode.hs` the cert ingest handler is assembled as:

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      ...
```

`makePerasCertPoolWriterFromChainDB` calls `processCerts` with `validatePerasCert mkPerasParams` as the validation function. `processCerts` partitions results: if all certs pass, they are added; if any fail, the batch is rejected. Because `validatePerasCert` never fails, every batch passes.

**Chain-selection side-effect:**

`makePerasCertPoolWriterFromChainDB` passes accepted certs to `ChainDB.addPerasCertAsync chainDB`, which enqueues a `ChainSelAddPerasCert` message. `chainSelSync` then:
1. Checks the cert is not too old (boosted block slot ≥ immutable tip).
2. Adds it to `PerasCertDB`.
3. If the boosted block is in the `VolatileDB`, triggers `chainSelectionForBlock` for that block, applying the Peras weight boost (`vpcCertBoost`) to its chain.

**Three-party bypass mapping:**

| Role | `transferFrom` | Peras cert path |
|---|---|---|
| Checked party 1 | `msg.sender` (Bob) | Sending peer (connected, not banned) |
| Checked party 2 | `to` | Receiving node (not in error state) |
| **Unchecked party** | **`from` (Mallory)** | **Certificate issuer / committee voters** |

The `from` address's blacklist status is never checked in `transferFrom`; the certificate issuer's cryptographic authorization is never checked in `validatePerasCert`.

---

### Impact Explanation

An unprivileged peer that has already diffused a valid competing fork's blocks into the target node's `VolatileDB` can send a forged `PerasCert` naming any block on that fork. The cert passes `validatePerasCert` unconditionally, is stored, and triggers chain selection with the Peras weight boost applied to the attacker's chosen block. If the boost is sufficient to make the competing fork preferred, the honest node switches chains — a chain-selection manipulation driven entirely by a forged, unauthenticated certificate.

The Peras weight boost is the protocol's primary mechanism for accelerating finality and resolving forks. Bypassing its authentication completely undermines the security guarantee that only genuine committee-backed certificates can influence chain selection. This constitutes a **bypass of Peras certificate verification enabling unauthorized certificate acceptance**, which falls under the Critical/High impact scope.

---

### Likelihood Explanation

The `hPerasCertDiffusionClient` handler is registered in the production node-to-node protocol stack and is reachable by any peer that negotiates a node-to-node connection. No privileged keys, stake, or operator access are required. The attacker only needs to:
1. Connect as a normal peer.
2. Construct a `PerasCert{pcCertRound, pcCertBoostedBlock}` naming a block already present in the target's `VolatileDB`.
3. Send it via the `PerasCertDiffusion` mini-protocol.

The `PerasVote` path is currently mitigated in production by the empty stake distribution (`pure (PerasVoteStakeDistr mempty)`) passed at the call site in `NodeToNode.hs` (lines 398–408), which causes all votes to fail the stake lookup. The cert path has no equivalent mitigation.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies the aggregate BLS/committee signature over the certificate's `(electionId, candidate)` payload against the declared voter set, checks that the voter set meets the quorum threshold, and confirms each voter's eligibility against the current committee selection data. Until that implementation is ready, the `hPerasCertDiffusionClient` handler should either be disabled or gated behind a feature flag that is off by default in production builds.

---

### Proof of Concept

**Step 1 — Attacker connects as a normal peer** and observes that block `B` at point `p` is present on a competing fork in the target node's `VolatileDB` (e.g., via ChainSync headers).

**Step 2 — Attacker crafts a forged certificate:**
```haskell
forgeCert :: Point blk -> PerasRoundNo -> PerasCert blk
forgeCert boostedBlock round = PerasCert
  { pcCertRound       = round        -- any round not yet in PerasCertDB
  , pcCertBoostedBlock = boostedBlock -- block on attacker's preferred fork
  }
```

**Step 3 — Attacker sends the cert** via the `PerasCertDiffusion` mini-protocol to the target node.

**Step 4 — `processCerts` runs** in `makePerasCertPoolWriterFromChainDB`:
```haskell
-- validatePerasCert always returns Right:
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) -> mapM_ (addCert . WithArrivalTime now) validatedCerts
```
The cert is accepted and `ChainDB.addPerasCertAsync chainDB` is called.

**Step 5 — `chainSelSync` processes the cert** (`ChainSelAddPerasCert`):
- Boosted block is found in `VolatileDB`.
- `chainSelectionForBlock` runs with the Peras weight boost applied.
- If the boosted fork now outweighs the current chain, the node switches.

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
