### Title
Decimal Normalization Floor Division Permanently Locks User Dust When Fee Is Zero — (`near/omni-bridge/src/lib.rs`)

### Summary
`normalize_amount` uses integer floor division to scale token amounts from origin-chain precision to NEAR-chain precision. The truncated remainder ("dust") is irrecoverably locked in the bridge escrow (or silently burned for bridge-minted tokens) whenever a transfer is initiated with `fee = 0`. This is the direct structural analog of the SqwidMarketplace raffle division bug: a division truncates value, and the truncated portion is never returned to the user.

### Finding Description
`normalize_amount` is defined as:

```rust
// near/omni-bridge/src/lib.rs  lines 2784-2787
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))   // floor division — remainder silently dropped
}
``` [1](#0-0) 

It is called inside `sign_transfer` to compute the amount that will be signed and delivered to the destination chain:

```rust
// near/omni-bridge/src/lib.rs  lines 475-480
let amount_to_transfer = Self::normalize_amount(
    transfer_message
        .amount_without_fee()
        .near_expect(BridgeError::InvalidFee),
    decimals,
);
``` [2](#0-1) 

The destination chain therefore receives `denormalize(normalize(amount - fee))` tokens. Because `denormalize(normalize(x)) ≤ x` by floor division, the difference `(amount - fee) - denormalize(normalize(amount - fee))` — the dust — never leaves the NEAR bridge.

The code itself acknowledges both paths:

```
// near/omni-bridge/src/lib.rs  lines 2781-2783
/// Uses floor division — any sub-unit remainder ("dust") is truncated and not transferred
/// to the destination chain. When fee > 0, dust is absorbed into the fee via `claim_fee`.
/// When fee = 0, dust stays locked/burned. See SECURITY.md for details.
``` [3](#0-2) 

**Fee > 0 path (dust recovered):** `claim_fee_callback` computes `fee = transfer_message.amount.0 - denormalized_amount`, which naturally absorbs the dust into the fee payout:

```rust
// near/omni-bridge/src/lib.rs  lines 1128-1131
// Fee includes both the user-specified fee and any dust lost during decimal
// normalization (see `normalize_amount`). Since `denormalize(normalize(x)) <= x`
// due to floor division, the difference naturally captures the normalization remainder.
let fee = transfer_message.amount.0 - denormalized_amount;
``` [4](#0-3) 

**Fee = 0 path (dust permanently lost):** There is no `fee_recipient`, so `claim_fee` is never called. The dust has no recovery path. For native tokens it remains locked in the NEAR bridge escrow forever; for bridge-minted tokens it is burned without being credited anywhere.

`SECURITY.md` is referenced by the comment but contains only a generic bug-bounty exclusion list and does not document this as an accepted design trade-off. [5](#0-4) 

### Impact Explanation
Every user who bridges a token whose `origin_decimals > decimals` (e.g., a 24-decimal NEAR-native token bridged to an 18-decimal EVM representation) and sets `fee = 0` permanently loses up to `10^(origin_decimals − decimals) − 1` base units per transfer. For a 6-decimal difference that is up to 999 999 base units per transfer, silently locked in the escrow with no recovery mechanism. This is escrow mis-accounting / decimal normalization abuse that permanently changes user balances.

### Likelihood Explanation
The condition is reachable by any unprivileged bridge user: set `fee = 0` (the natural default for self-relayed transfers) and send an amount whose low-order digits are non-zero relative to the decimal gap. No admin access, key compromise, or collusion is required. The `sign_transfer` entry point is public to trusted relayers, and users can act as their own relayer.

### Recommendation
Mirror the `claim_fee` dust-recovery logic unconditionally: after normalization, compute the remainder and either (a) refund it to the sender before finalizing the transfer, or (b) require that the submitted amount is already a clean multiple of `10^(origin_decimals − decimals)` and revert otherwise. This eliminates the silent truncation entirely, matching the external report's recommendation to "remove the division" (or make it lossless).

### Proof of Concept
1. Token registered with `origin_decimals = 24`, `decimals = 18` (diff = 6).
2. User initiates a NEAR → EVM transfer of `1_000_000_000_000_000_000_000_001` (1 NEAR + 1 base unit) with `fee = Fee { fee: 0, native_fee: 0 }`.
3. `sign_transfer` calls `normalize_amount(1_000_000_000_000_000_000_000_001, decimals)` → `1_000_000_000_000_000_000_000_001 / 1_000_000 = 1_000_000_000_000_000_000` (the trailing `1` is dropped).
4. EVM receives `1_000_000_000_000_000_000` (exactly 1 token in 18-decimal units).
5. The 1 base unit of dust remains locked in the NEAR bridge escrow with no recovery path, because `fee = 0` means `claim_fee` is never callable for this transfer. [1](#0-0) [2](#0-1) [6](#0-5)
