Audit Report

## Title
Missing Factory Existence Check in `init_transfer` Enables Permanent Burning of Deployed Tokens — (File: near/omni-bridge/src/lib.rs)

## Summary
`init_transfer` accepts outbound transfers to any `ChainKind` variant without verifying that a factory is registered for the destination chain. For deployed (bridge-minted) tokens, this causes an immediate, irreversible `burn()` call with no recovery path — not even DAO intervention can restore burned tokens. For native tokens, funds are stranded in the bridge contract recoverable only via DAO. The inbound path (`fin_transfer_callback`) already enforces the factory check that the outbound path omits.

## Finding Description
`init_transfer` performs only one chain-level validation:

```rust
require!(
    init_transfer_msg.recipient.get_chain() != ChainKind::Near,
    BridgeError::InvalidRecipientChain.as_ref()
);
```

No check against `self.factories` is performed. Execution proceeds to `init_transfer_internal`, which calls:

```rust
self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
self.lock_tokens_if_needed(
    transfer_message.get_destination_chain(),
    &token_id,
    transfer_message.amount.0,
);
```

`burn_tokens_if_needed` issues a detached `ext_token::burn()` cross-contract call for any token in `self.deployed_tokens`. This call is fire-and-forget (`detach()`), so there is no callback to revert it. The burn is permanent and irreversible regardless of whether the destination chain has a factory.

By contrast, `fin_transfer_callback` (the inbound path) correctly guards with:

```rust
require!(
    self.factories
        .get(&init_transfer.emitter_address.get_chain())
        == Some(init_transfer.emitter_address),
    BridgeError::UnknownFactory.as_ref()
);
```

The asymmetry means the outbound path has no equivalent protection.

Recovery paths after `init_transfer_internal` completes:
- `sign_transfer_callback`: only removes the pending entry when `fee.is_zero()`; tokens are already burned/locked regardless.
- `claim_fee_callback`: requires a cryptographic proof from the destination chain — impossible if no factory exists there.
- `transfer_token_as_dao`: DAO-only; cannot restore burned tokens, only transfers locked native tokens.

## Impact Explanation
For deployed (bridge-minted) tokens: the `burn()` call is permanent and irreversible. Even DAO cannot restore burned supply. This is direct, permanent loss of bridged funds — matching the Critical impact class "Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds."

For native tokens: funds are stranded in the bridge contract with no user-accessible recovery, requiring DAO intervention — constituting permanent freezing from the user's perspective.

## Likelihood Explanation
The entry point is fully public: any token holder can call `ft_transfer_call` on any NEP-141 token, triggering `ft_on_transfer` → `init_transfer`. The precondition — a `ChainKind` variant with no registered factory — is realistic in two concrete scenarios: (1) the window between when a new chain variant is added to the `OmniAddress` parser (e.g., `fogo`, `abs`, `zcash`) and when its factory is deployed and registered on-chain; (2) if a factory is ever removed for a deprecated chain. No special privileges are required. The exploit is repeatable for every affected token type.

## Recommendation
Add a factory existence check at the top of `init_transfer`, mirroring the guard in `fin_transfer_callback`:

```rust
require!(
    self.factories
        .get(&init_transfer_msg.get_destination_chain())
        .is_some(),
    BridgeError::UnknownFactory.as_ref()
);
```

Additionally, consider adding a user-accessible `cancel_transfer` function that returns locked native tokens to the sender for transfers that have not yet been signed, to provide a recovery path for any edge cases that bypass the factory check.

## Proof of Concept
1. Deploy or identify a deployed (bridge-minted) token registered in `self.deployed_tokens`.
2. Confirm that chain `Fogo` (or any `ChainKind` variant) has no entry in `self.factories`.
3. Call `ft_transfer_call` on the token contract:
   ```json
   {
     "receiver_id": "omni.bridge.near",
     "amount": "1000000",
     "msg": "{\"InitTransfer\":{\"recipient\":\"fogo:AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA\",\"fee\":\"0\",\"native_token_fee\":\"0\"}}"
   }
   ```
4. `ft_on_transfer` → `init_transfer` runs. The `!= Near` check passes.
5. `init_transfer_internal` calls `burn_tokens_if_needed`, issuing a detached `burn(1000000)` on the token contract.
6. The transfer is stored in `pending_transfers`.
7. No relayer can finalize the transfer on Fogo (no factory contract exists).
8. No user-callable function can cancel the transfer or restore the burned tokens.
9. 1,000,000 tokens are permanently destroyed.

A unit test can be written against the NEAR sandbox: initialize the contract without registering a factory for `ChainKind::Fogo`, register a deployed token, call `ft_transfer_call` with a Fogo recipient, and assert that the token's total supply decreases while the transfer remains permanently stuck in `pending_transfers`.
