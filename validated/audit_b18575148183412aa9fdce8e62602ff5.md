### Title
`validatePerasCert` Unconditionally Accepts Any Peer-Supplied Peras Certificate, Enabling Chain-Selection Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or structural validation. Because this instance covers all block types (including production Cardano blocks) and is wired directly into the live inbound-certificate processing path (`processCerts`), any unprivileged peer can inject arbitrary Peras certificates into a node's `PerasCertDB`. Those certificates carry a boost weight that feeds into chain selection, allowing an attacker to make an honest node prefer a non-canonical chain without holding any keys or stake.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub wired into production:**

`BlockSupportsPeras.hs` lines 318–358 define a universal instance that applies to every `StandardHash blk`, including the live Cardano block type. No more-specific override exists anywhere in the repository (confirmed by exhaustive grep for `validatePerasCert` and `validatePerasVote`):

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

The function ignores every field of `cert` — round number, boosted-block hash, and any signature — and always returns `Right`. The `PerasValidationErr` data constructor is a single opaque token with no variants, so there is no mechanism to express a rejection.

**Propagation into the live inbound path:**

`makePerasCertPoolWriterFromChainDB` in `PerasCert.hs` passes `(validatePerasCert mkPerasParams)` as the validation callback to `processCerts`:

```haskell
(validatePerasCert mkPerasParams)
``` [2](#0-1) 

`processCerts` then calls `partitionEithers (validateCert <$> certsNotAlreadyInDb)`. Because `validateCert` always returns `Right`, the left partition is always empty and every certificate is unconditionally forwarded to `addCert`:

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (...) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _) -> throw (PerasCertValidationError errs)
``` [3](#0-2) 

**Compounding issue — `validatePerasVote` also skips signature verification:**

The same universal instance's `validatePerasVote` only checks whether the claimed voter ID appears in the stake distribution. The default `PerasVote` data type carries no signature field, so there is nothing to verify cryptographically. An attacker can therefore also fabricate votes attributed to any legitimate stake pool, accumulate enough stake-weighted votes to trigger `updatePerasRoundVoteStates`, and cause the node to forge a certificate internally — bypassing even the inbound-certificate path. [4](#0-3)

### Impact Explanation

Peras certificates carry a `vpcCertBoost` weight (set to `perasWeight params`) that is applied during chain selection to boost the certified block. An attacker who can inject a certificate for an arbitrary `Point blk` can therefore make an honest node assign a boost to a non-canonical or adversarially-chosen block. Depending on the configured `perasWeight`, this boost can be large enough to override the honest chain's length advantage, causing the node to switch to a shorter or adversarially-controlled fork. This is a chain-selection integrity failure: an unprivileged peer can make an honest node prefer a non-canonical chain beyond the intended security assumptions of the Ouroboros protocol.

---

### Likelihood Explanation

The attack requires only a standard peer connection — no keys, no stake, no privileged access. The Object Diffusion mini-protocol for Peras certificates is reachable from any connected peer. The attacker needs only to craft a `PerasCert` CBOR message with a chosen `pcCertRound` and `pcCertBoostedBlock`, send it over the wire, and the node will accept and store it. The deduplication check (`alreadyInDb`) only prevents re-injection of the same round number, so the attacker can inject one certificate per round. Given that Peras rounds are short (parameterized by `eraPerasRoundLength`), an attacker can continuously inject certificates for every round, persistently biasing chain selection.

---

### Recommendation

1. **Implement real certificate validation** in `validatePerasCert` before the Peras feature is enabled on any network. At minimum, verify: (a) the certificate's round number falls within the current or recent valid window; (b) the boosted block hash corresponds to a block that exists on the node's chain; (c) the certificate carries a valid aggregate BLS signature over the election identifier and vote message, verified against the committee's public keys.

2. **Implement real vote validation** in `validatePerasVote`: verify the BLS signature in `pvSignature` (present in the V1 vote type) against the voter's registered public key before accepting the vote as carrying any stake weight.

3. **Remove the universal stub instance** (`instance StandardHash blk => BlockSupportsPeras blk`) or gate it behind a compile-time flag that is disabled for production Cardano builds, so that any block type that has not yet received a real implementation fails to compile rather than silently accepting all inputs.

### Proof of Concept

**Setup:** A private testnet with one honest node running the Peras-enabled consensus code and one attacker node connected as a peer via the Object Diffusion mini-protocol.

**Steps:**

1. Attacker identifies the current slot and computes the corresponding Peras round number.
2. Attacker selects a target block `P` on a minority fork (or a block that does not yet exist).
3. Attacker serialises a `PerasCert { pcCertRound = <current round>, pcCertBoostedBlock = P }` using the CBOR encoding defined in `SupportsPeras.hs` lines 400–409.
4. Attacker sends this certificate to the honest node via the Object Diffusion protocol.
5. The honest node's `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }` unconditionally.
6. The certificate is stored in the `PerasCertDB` with the current wall-clock arrival time.
7. Chain selection now applies `vpcCertBoost` to block `P`, potentially causing the honest node to switch to the attacker's fork.

**Expected outcome:** The honest node accepts the forged certificate and adjusts its chain-selection preference accordingly, demonstrating that an unprivileged peer can manipulate chain selection without any cryptographic material.
