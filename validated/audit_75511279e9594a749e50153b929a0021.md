### Title
Stale `emptyPerasWeightSnapshot` in ChainSync Disconnect Check vs. Real Weights in Chain Selection Causes Canonical-Chain Rejection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

When Peras is active, `checkPreferTheirsOverOurs` in the ChainSync client evaluates whether to disconnect from a peer using a hardcoded `emptyPerasWeightSnapshot` (zero Peras weight), while every other chain-selection site reads the live `PerasWeightSnapshot` from the `PerasCertDB`. A peer offering a chain that is heavier due to Peras certificate boosts but shorter in raw block count will be incorrectly judged as "not preferred" and the node will disconnect from it, permanently refusing to adopt the canonical chain.

---

### Finding Description

The ChainSync client calls `checkPreferTheirsOverOurs` when a peer's header is beyond the forecast horizon and the ledger view cannot yet be projected. The function decides whether to keep the connection or throw `CandidateTooSparse`:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← always zero Peras weight
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
``` [1](#0-0) 

Every other chain-selection call site reads the live weight snapshot atomically:

- `chainSelectionForBlock` reads `forgetFingerprint <$> Query.getPerasWeightSnapshot cdb` before calling `constructPreferableCandidates` and `chainSelection`.
- `chainSelSync` (LoE reprocess path) reads `forgetFingerprint <$> Query.getPerasWeightSnapshot cdb`.
- `BlockFetch`'s `readChainComparison` wraps `getPerasWeightSnapshot chainDB`. [2](#0-1) [3](#0-2) [4](#0-3) 

`getPerasWeightSnapshot` is backed by `implGetWeightSnapshot`, which recomputes the full weight map from all certificates currently in the `PerasCertDB`: [5](#0-4) 

The discrepancy is therefore structural and exact:

| Site | Weight used |
|---|---|
| `checkPreferTheirsOverOurs` (ChainSync) | `emptyPerasWeightSnapshot` — always zero |
| `chainSelectionForBlock` (ChainDB) | live `PerasWeightSnapshot` from `PerasCertDB` |
| `constructPreferableCandidates` (ChainDB) | live `PerasWeightSnapshot` |
| `readChainComparison` (BlockFetch) | live `PerasWeightSnapshot` |

`preferAnchoredCandidate` with `emptyPerasWeightSnapshot` falls into the `isEmptyPerasWeightSnapshot` branch and compares chains purely by block count (`BlockNo`), ignoring all Peras certificate boosts: [6](#0-5) 

---

### Impact Explanation

When Peras is active, a peer may offer a candidate chain that is **shorter in block count but heavier in total Peras weight** than the local selection. This is the intended Peras scenario: a certificate boosts a block on a fork, making that fork the canonical chain even though it has fewer blocks.

`checkPreferTheirsOverOurs` evaluates this candidate with zero Peras weight. The candidate appears lighter than the local chain. The node throws `CandidateTooSparse` and disconnects from the peer. The node then never downloads the boosted fork, never runs `chainSelectionForBlock` on it, and permanently stays on the lighter (non-canonical) chain.

This is a **chain-selection error**: an honest node is made to prefer a non-canonical, less-secure chain by a crafted (or simply honest) peer interaction, without any operator fault. The impact matches: *"High. Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

---

### Likelihood Explanation

- **Peras must be enabled.** The CHANGELOG confirms Peras is currently disabled by default, so the bug is dormant on mainnet today. However, the code is present and the feature is being actively developed for production deployment.
- **No special privileges required.** Any peer that has received a Peras certificate boosting a fork can trigger this path simply by serving headers from that fork. The peer need not be malicious; an honest peer serving the canonical chain is sufficient.
- **The forecast-horizon condition is routinely hit.** During initial sync or after a slot gap larger than the stability window, headers are regularly beyond the forecast horizon, making `checkPreferTheirsOverOurs` the active code path.
- **The developers acknowledge the bug.** The inline `TODO` comment explicitly references `https://github.com/tweag/cardano-peras/issues/64` and notes the check should be removed. [7](#0-6) 

---

### Recommendation

Replace `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live snapshot obtained from the ChainDB, consistent with every other chain-comparison site. Because `checkPreferTheirsOverOurs` already runs inside `STM`, the snapshot can be read atomically in the same transaction:

```haskell
checkPreferTheirsOverOurs kis = do
  weights <- forgetFingerprint <$> getPerasWeightSnapshot chainDB
  if shouldSwitch $
       preferAnchoredCandidate (configBlock cfg) weights ourFrag theirFrag
    then pure ()
    else throwSTM $ CandidateTooSparse ...
```

This is consistent with the resolution tracked in the referenced issue and eliminates the cached-vs-actual discrepancy.

---

### Proof of Concept

**Setup (private testnet with Peras enabled):**

1. Node A holds chain `C_A`: blocks `[B0, B1, B2, B3]` (length 4, no Peras boosts).
2. A Peras certificate is issued boosting block `B2'` on fork `C_B`: `[B0, B1, B2']` (length 3, Peras weight boost = 5).
3. Under the live weight snapshot, `totalWeight(C_B) = 3 + 5 = 8 > totalWeight(C_A) = 4`, so `C_B` is canonical.

**Trigger:**

4. Peer P serves headers of `C_B` to Node A. The slot gap between `B1` and `B2'` exceeds the forecast window, so `prj lst` returns `Nothing` and `checkPreferTheirsOverOurs` is invoked.
5. `checkPreferTheirsOverOurs` calls `preferAnchoredCandidate … emptyPerasWeightSnapshot ourFrag theirFrag`. With zero Peras weight, `C_B` (length 3) loses to `C_A` (length 4). `shouldSwitch` returns `False`.
6. Node A throws `CandidateTooSparse` and disconnects from P.

**Outcome:**

Node A never fetches `B2'`, never runs `chainSelectionForBlock`, and remains on `C_A` — the non-canonical chain — indefinitely. Any subsequent peer offering `C_B` will be disconnected for the same reason. Node A has diverged from the canonical chain without any operator fault or adversarial key compromise.   forall blk h h'.
  ( BlockSupportsProtocol blk
  , HasCallStack
  , GetHeader1 h
  , GetHeader1 h'
  , HeaderHash (h blk) ~ HeaderHash blk
  , HeaderHash (h blk) ~ HeaderHash (h' blk)
  , HasHeader (h blk)
  , HasHeader (h' blk)
  ) =>
  BlockConfig blk ->
  -- | Peras weights used to judge this chain.
  PerasWeightSnapshot blk ->
  -- | Our chain
  AnchoredFragment (h blk) ->
  -- | Candidate
  AnchoredFragment (h' blk) ->
  ShouldSwitch (ReasonForSwitch' blk)
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"
        Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
          case preferCandidate
            (projectChainOrderConfig cfg)
            (weightedSelectView cfg weights oursSuffix)
            (weightedSelectView cfg weights candSuffix) of
            ShouldSwitch r -> ShouldSwitch (Left r)
            ShouldNotSwitch o -> ShouldNotSwitch o
