Audit Report

## Title
Pause Bypass on `TokenDeployer::deploy_token` — Missing `#[pause]` Attribute Renders Pause Mechanism Ineffective - (File: near/token-deployer/src/lib.rs)

## Summary
`TokenDeployer` derives `Pausable` and configures a `PauseManager` role, but its sole operational function `deploy_token` lacks the `#[pause]` procedural macro attribute. In `near-plugins`, the pause check is opt-in per function; without it, `deploy_token` executes unconditionally regardless of the contract's pause state. A relayer or any external actor can submit a valid cross-chain proof to the bridge's `deploy_token` (which is not paused), causing the bridge to call `token_deployer.deploy_token()` and bypass the deployer's pause entirely.

## Finding Description
`TokenDeployer` is configured with the full `Pausable` infrastructure:

```rust
// near/token-deployer/src/lib.rs L27-28
#[derive(Pausable, Upgradable, PanicOnDefault)]
#[pausable(manager_roles(Role::PauseManager))]
```

However, `deploy_token` — the contract's only meaningful function — carries only `#[payable]` and `#[access_control_any]`, with no `#[pause]` gate:

```rust
// near/token-deployer/src/lib.rs L58-73
#[payable]
#[access_control_any(roles(Role::Controller, Role::LegacyController))]
pub fn deploy_token(&mut self, account_id: AccountId, metadata: &BasicMetadata) -> Promise {
```

Contrast this with the bridge's own `deploy_token`, which correctly applies `#[pause(except(roles(Role::DAO)))]`:

```rust
// near/omni-bridge/src/lib.rs L1136-1145
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn deploy_token(&mut self, #[serializer(borsh)] args: DeployTokenArgs) -> Promise {
```

The `near-plugins` `Pausable` trait does not automatically gate all methods; each method must explicitly opt in with `#[pause]`. Without it, calling `pa()` on the `TokenDeployer` has zero effect on `deploy_token`.

**Exploit path:**
1. A vulnerability is discovered in the current omni-token WASM (`global_code_hash`).
2. `PauseManager` calls `pa()` on the `TokenDeployer` to halt new deployments while a fix is staged.
3. A relayer (or any external actor) submits a valid cross-chain proof to the bridge's `deploy_token`. The bridge is not paused, so its `#[pause(except(roles(Role::DAO)))]` gate passes.
4. The bridge's `deploy_token_callback` calls `token_deployer.deploy_token(account_id, metadata)` via cross-contract call.
5. The call succeeds — the deployer's pause state is never checked — and a new token account is created using the current (potentially vulnerable) `global_code_hash`.

The `global_code_hash` is not attacker-supplied; it is stored in contract state and only DAO can update it via `set_global_code_hash`. The risk is deploying tokens with the current, potentially vulnerable WASM during the emergency pause window.

## Impact Explanation
This is a confirmed **pause bypass** matching the Critical allowed impact: "Unauthorized transaction, authorization bypass, role bypass, pause bypass, or signer/prover verification bypass that lets an attacker execute bridge, token, deployer, relayer, or admin-equivalent actions." The `TokenDeployer`'s pause mechanism is completely inoperative for its primary function. During an emergency pause intended to halt deployments (e.g., a critical bug found in the omni-token WASM), the bridge can still deploy new token contracts bound to the vulnerable implementation. Those tokens are then registered in the bridge's `deployed_tokens` / `token_address_to_id` maps and become live bridge assets. If the WASM vulnerability allows unauthorized minting or burning, bridged funds are at risk.

## Likelihood Explanation
The pause bypass is unconditional — it requires no attacker, no key compromise, and no social engineering. It is triggered by the normal operation of the bridge contract (the `Controller`) processing a valid cross-chain proof submitted by any relayer. The only precondition is that an operator pauses the deployer but not the bridge, which is the exact scenario the pause mechanism is designed for. Any relayer can submit a valid `LogMetadata` proof to the bridge's `deploy_token` to trigger the cross-contract call to the deployer.

## Recommendation
Add `#[pause]` to `deploy_token` in `near/token-deployer/src/lib.rs`, consistent with how the bridge's own `deploy_token` is gated. If DAO must be able to deploy during a pause, use `#[pause(except(roles(Role::DAO)))]`:

```rust
#[payable]
#[pause]   // or #[pause(except(roles(Role::DAO)))]
#[access_control_any(roles(Role::Controller, Role::LegacyController))]
pub fn deploy_token(&mut self, account_id: AccountId, metadata: &BasicMetadata) -> Promise {
```

## Proof of Concept
On a local NEAR sandbox (`near-workspaces`):

1. Deploy `token-deployer` with `controller = bridge.near`, `dao = dao.near`.
2. Grant `Role::PauseManager` to `pause_manager.near` via `acl_grant_role`.
3. Call `pa()` from `pause_manager.near` → deployer is now paused.
4. Call `deploy_token(account_id, metadata)` from `bridge.near` (Controller).
5. **Assert:** the call succeeds and the new token account exists — demonstrating the pause had no effect.

Alternatively, on a private testnet:
1. Deploy both `omni-bridge` and `token-deployer` contracts.
2. Pause the `token-deployer` via `pa()`.
3. Submit a valid `LogMetadata` proof to the bridge's `deploy_token`.
4. Observe that `deploy_token_callback` successfully calls `token_deployer.deploy_token()` and the new token account is created, confirming the deployer's pause is bypassed.
