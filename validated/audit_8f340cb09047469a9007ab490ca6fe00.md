### Title
Duplicate `sign_btc_transaction` calls for the same index cause second callback to panic and lose attached NEAR deposit — (`contracts/satoshi-bridge/src/chain_signature.rs`)

---

### Summary

`internal_sign_btc_transaction` performs a read-only guard (`signatures[sign_index].is_none()`) but writes **no state** before dispatching the MPC sign promise. Two calls for the same `btc_pending_sign_id` and `sign_index` can both pass this guard and both dispatch MPC sign promises. When the second callback fires, it hits the identical guard inside `sign_btc_transaction_callback` and panics — after the attached deposit has already been forwarded irrecoverably to the MPC contract.

---

### Finding Description

`internal_sign_btc_transaction` checks the slot at line 91–94 but makes no write to contract state before returning the promise chain: [1](#0-0) 

Because no state is written, a second call for the same `(btc_pending_sign_id, sign_index)` pair — submitted in any block before either callback lands — also passes the guard and dispatches a second MPC sign promise.

The entire caller-attached deposit is forwarded to the MPC contract unconditionally: [2](#0-1) 

When the second callback fires, the first callback has already written `signatures[sign_index] = Some(...)`: [3](#0-2) 

The `require!` at line 154–157 panics. NEAR rolls back the callback's state changes, but the deposit forwarded to the MPC contract in the second call is already spent and is not returned.

---

### Impact Explanation

- The attached NEAR deposit of the second `sign_btc_transaction` caller is permanently lost; the MPC contract consumed it and the panicking callback cannot recover it.
- If the first callback was the last input to sign and already called `to_pending_verify_stage()` + removed the ID from `btc_pending_sign_ids`, the second callback panics after those writes are already committed, leaving the `BTCPendingInfo` in `PendingVerify` (correct) but the second caller's deposit gone. [4](#0-3) 

No funds are stolen and no stuck state results, placing this squarely in the **Low** category: a publicly reachable panic-driven fault in a production bridge path without direct theft.

---

### Likelihood Explanation

`sign_btc_transaction` is a public, payable function with no role guard beyond the contract-pause check: [5](#0-4) 

`btc_pending_sign_id` values are emitted as on-chain events and are publicly observable. Any account can submit a duplicate call. The window is the latency between the first call's dispatch and its callback landing (typically several blocks), which is wide enough for a retry, a race, or a deliberate duplicate submission.

---

### Recommendation

Write a sentinel to contract state **before** dispatching the MPC promise in `internal_sign_btc_transaction` — for example, set `signatures[sign_index]` to a placeholder/in-progress marker — so that any concurrent call for the same index fails the pre-check immediately rather than dispatching a second paid MPC request. Alternatively, introduce a per-`(btc_pending_sign_id, sign_index)` in-flight lock that is set before the promise and cleared (or confirmed) in the callback.

---

### Proof of Concept

```
1. Ensure a BTCPendingInfo exists in PendingSign stage with at least one unsigned input at sign_index=0.
2. Submit call A: sign_btc_transaction(btc_pending_sign_id, 0, key_version) with deposit D_A.
   → internal_sign_btc_transaction reads signatures[0] == None ✓, dispatches MPC promise. No state written.
3. Before callback A lands, submit call B: sign_btc_transaction(btc_pending_sign_id, 0, key_version) with deposit D_B.
   → internal_sign_btc_transaction reads signatures[0] == None ✓ (still unwritten), dispatches second MPC promise.
4. Invoke callback A: signatures[0] = Some(sig_A). If all signed → PendingVerify.
5. Invoke callback B: env::promise_result_checked returns Ok(sig_B).
   → require!(btc_pending_info.signatures[0].is_none()) → PANICS.
   → D_B (forwarded to MPC in step 3) is permanently lost.
```
