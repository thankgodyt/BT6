### Title
Unvalidated `refund_address` Chain Compatibility Causes Panic-Driven Stuck Refund State - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
The `request_refund_callback` stores the caller-supplied `refund_address` into a `RefundRequest` without validating it against the bridge's configured chain. The chain-compatibility check is deferred to `build_refund_output` inside `execute_refund`, where a hard `.expect("Invalid refund address")` panic fires if the address is incompatible. This leaves the refund request permanently unexecutable and requires privileged operator intervention to clean up.

### Finding Description
In `request_refund_callback` the `refund_address` string is written directly into the `RefundRequest` struct with no call to `Address::parse` or any other chain-compatibility check: [1](#0-0) 

The only guard that exists is a string-equality check against `deposit_msg.refund_address` when that optional field is set: [2](#0-1) 

Neither check validates that the address is parseable for the bridge's configured `Chain`. The actual chain-compatibility validation is deferred to `build_refund_output`, which calls `Address::parse(refund_address, config.chain.clone()).expect("Invalid refund address")`: [3](#0-2) 

Because `build_refund_output` is called inside `execute_refund` after the refund request has already been committed to storage, a panic there reverts the `execute_refund` call but leaves the `RefundRequest` intact in `refund_requests`. The UTXO is **not** inserted into `verified_deposit_utxo` (that insertion happens in `finalize_refund_with_psbt`, which is never reached): [4](#0-3) 

The `Chain` enum covers Bitcoin, Litecoin, Zcash, and Dogecoin variants, each with distinct address prefixes and HRP values: [5](#0-4) 

An address valid on one chain (e.g., a Litecoin mainnet P2PKH address with prefix `0x30`) will fail `Address::parse` when the bridge is configured for Bitcoin mainnet (prefix `0x00`), triggering the panic.

### Impact Explanation
Every call to `execute_refund` for the poisoned request panics and reverts. The `RefundRequest` entry remains in `refund_requests` indefinitely, blocking any further `request_refund` for the same UTXO (the duplicate check in `request_refund_callback` rejects it). Clearing the stuck state requires a privileged `reject_refund` call from DAO or Operator. This is a publicly reachable panic-driven stuck-state in a production bridge path, matching the Low allowed impact: *"stuck-state, or panic-driven fault in production bridge/token paths without direct theft."*

### Likelihood Explanation
`request_refund` is a public, permissionless function callable by any NEAR account. The only prerequisites are attaching the required storage deposit and supplying a BTC transaction that passes Light Client verification. The `deposit_msg` needed to reconstruct the deposit path is emitted in the public `LogDepositAddress` event when the deposit address is generated. An attacker can observe this event, locate the corresponding unverified on-chain deposit, and call `request_refund` with a cross-chain or malformed `refund_address`. The anti-spam deposit is lost by the attacker, but the victim's refund is rendered unexecutable until an operator intervenes.

### Recommendation
Validate `refund_address` against the configured chain inside `request_refund_callback` (or in `internal_request_refund` before the Light Client cross-contract call) by calling `Address::parse(&refund_address, config.chain.clone())` and returning an error or emitting a failure event if parsing fails. This mirrors the validation already applied to `target_btc_address` in the withdrawal path via `config.target_script_pubkey`.

### Proof of Concept
1. Observe the `LogDepositAddress` event to obtain the `deposit_msg` for an unverified deposit on a Bitcoin-configured bridge.
2. Call `request_refund(deposit_msg, "LWrHnw5xztWiPafMhKYTQued8iuhaET7Yd" /* Litecoin mainnet address */, tx_bytes, vout, proof, None)` with the required attached deposit.
3. `internal_request_refund` passes (no chain check on `refund_address`); the Light Client verifies the transaction; `request_refund_callback` stores the `RefundRequest` with the Litecoin address.
4. Call `execute_refund(utxo_storage_key, None)` — execution reaches `build_refund_output`, which calls `Address::parse("LWrHnw5xztWiPafMhKYTQued8iuhaET7Yd", Chain::BitcoinMainnet)`, which returns `Err("Unknown address format or unsupported chain")`, triggering `.expect("Invalid refund address")` and panicking.
5. The `RefundRequest` remains in storage; `execute_refund` will panic on every subsequent call; the UTXO is not marked verified; the state is stuck until DAO/Operator calls `reject_refund`.
