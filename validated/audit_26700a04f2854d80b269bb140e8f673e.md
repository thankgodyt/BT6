### Title
Stub `validatePerasCert` unconditionally accepts all inbound Peras certificates, enabling chain-selection manipulation by any unprivileged peer — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance ships a `validatePerasCert` implementation that is a no-op stub: it always returns `Right` without performing any cryptographic or structural validation. Because this is the instance used in the live `processCerts` inbound-certificate pipeline, any unprivileged peer can submit arbitrarily crafted Peras certificates that are accepted unconditionally, stored in the `PerasCertDB`, and used to boost arbitrary blocks during chain selection.

---

### Finding Description

**Root cause — the stub validator**

`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`, lines 318–358, defines the universal default instance:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

Every certificate, regardless of its content, is wrapped in `Right ValidatedPerasCert` and assigned the full `perasWeight`. No signature, no round-number binding, no boosted-block existence check, no quorum check — nothing.

**Entry path — inbound certificate pipeline**

`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs`, lines 121–133, wires this stub directly into the peer-facing receive path:

```haskell
opwAddObjects = \certs ->
    processCerts
      systemTime
      (ChainDB.getPerasCertIds chainDB)
      (validatePerasCert mkPerasParams)   -- ← always Right
      (void . ChainDB.addPerasCertAsync chainDB)
      certs
``` [2](#0-1) 

`processCerts` (lines 164–180) calls `validateCert` on each received certificate; if all pass it adds them via `addCert`. Because `validatePerasCert` always returns `Right`, every certificate passes. [3](#0-2) 

**Chain-selection consequence**

`addPerasCertAsync` feeds into `chainSelSync` in `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Storage/ChainDB/Impl/ChainSel.hs` (lines 483–535). Once a certificate is stored, `chainSelectionForBlock` is called for the boosted block. The `WeightedSelectView` in `Peras/SelectView.hs` (lines 63–87) adds `wsvWeightBoost` to the block number when comparing candidates, so a crafted certificate can make a shorter or otherwise non-preferred fork appear heavier than the honest chain. [4](#0-3) [5](#0-4) 

**Analog to the reported PDA bug**

| Reported bug | This finding |
|---|---|
| Handler does not derive/verify the PDA from the expected seeds; any account passes | `validatePerasCert` does not verify the certificate's cryptographic content; any certificate passes |
| Attacker supplies a different PDA belonging to another authority | Attacker supplies a crafted certificate boosting an arbitrary block |
| Result: unauthorized clearing of another authority's bitmap data | Result: unauthorized weight boost applied to a non-canonical fork, causing chain-selection divergence |

---

### Impact Explanation

**Severity: High**

An unprivileged peer can cause an honest node to prefer a non-canonical chain by submitting a crafted Peras certificate that boosts a block on a weaker fork. Because `wsvTotalWeight = blockNo + weightBoost`, a sufficiently large `perasWeight` can make a shorter fork appear heavier than the honest chain, triggering a rollback and chain switch. This directly satisfies the "chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain" impact category.

---

### Likelihood Explanation

**Likelihood: High**

- The entry point is the public peer-to-peer object diffusion protocol; no credentials are required.
- The stub is the *universal default* instance — there is no override for any production block type in the repository.
- The two TODO comments (issues #73 and #120) confirm the validation was intentionally deferred, not accidentally omitted, meaning the gap is structural and persistent.
- Crafting a syntactically valid `PerasCert` value requires only knowledge of the wire format, which is public.

---

### Recommendation

Replace the stub with a real implementation that, at minimum:

1. Verifies the aggregate BLS signature over `(electionId, candidate)` against the claimed voter keys.
2. Verifies each voter's eligibility (persistent: seat index within persistent range; non-persistent: VRF proof valid against the epoch nonce and election id).
3. Checks that the claimed quorum weight meets the protocol threshold.
4. Binds the certificate's `electionId` (round number) to the current or recent epoch to prevent replay of old certificates.

Until a real implementation is available, the node should refuse to process inbound Peras certificates entirely rather than accepting them unconditionally.

---

### Proof of Concept

**Setup**: private testnet with Peras object diffusion enabled, two nodes A (honest) and B (attacker).

1. Node A has a current chain of length N with tip hash `H_A`.
2. Attacker B constructs a `PerasCert` value with:
   - `pcCertRound` = any round number not yet in A's `PerasCertDB`
   - `pcCertBoostedBlock` = `BlockPoint slot H_fork` where `H_fork` is the hash of a block on a shorter fork known to A's VolatileDB
3. B sends this certificate to A via the Peras object diffusion mini-protocol.
4. A's `processCerts` calls `validatePerasCert` → `Right ValidatedPerasCert { vpcCertBoost = perasWeight }`.
5. The certificate is stored; `addPerasCertAsync` triggers `chainSelSync`.
6. `chainSelectionForBlock` is called for `H_fork`; `weightBoostOfFragment` adds `perasWeight` to the fork's `wsvTotalWeight`.
7. If `perasWeight` is large enough, `preferCandidate` returns `ShouldSwitch`; A rolls back to the fork.

**Expected (correct) outcome**: step 4 returns `Left (InvalidCertSignature ...)` and the certificate is rejected.  
**Actual outcome**: step 4 returns `Right`; A switches to the attacker's fork. [6](#0-5)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes

  -- Deliver promise indicating that we processed the cert.
  lift $ atomically $ putTMVar varProcessed certResult
