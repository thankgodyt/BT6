### Title
`safe_mint` Unconditionally Mints to Bridge Before Recipient Registration Check, Permanently Inflating nBTC Supply — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

The `safe_mint` function in the nBTC token contract mints `amount` tokens to the bridge's own balance **before** checking whether the intended recipient account is registered. If the recipient is unregistered, the function returns `U128(0)` (no tokens transferred) but the already-minted tokens remain in the bridge's nBTC balance with no burn-back path, permanently inflating the nBTC total supply beyond the amount of BTC actually locked in the bridge.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, `safe_mint` executes in this order:

1. **Mint unconditionally** — `self.token.internal_deposit(&self.bridge_id, amount.into())` increases the nBTC total supply and credits the bridge's own balance by `amount`.
2. **Check registration** — `if self.token.accounts.get(&account_id).is_none() { return PromiseOrValue::Value(U128(0)); }` — if the recipient is not registered, the function returns early with zero. [1](#0-0) 

The early return at line 115 exits without burning or otherwise removing the tokens that were just deposited into `bridge_id` at line 112. The total supply has increased by `amount`, but the caller (satoshi-bridge) receives `U128(0)`, signalling that no tokens were delivered. There is no burn-back path in this code branch, so the minted tokens are permanently stranded in the bridge's nBTC balance.

This is structurally analogous to the UlyssesToken bug: an accounting operation (minting) is performed with one set of assumptions (recipient exists), but the subsequent state-check (registration guard) uses a different assumption, leaving the contract's supply invariant broken after the operation.

---

### Impact Explanation

The nBTC total supply can exceed the amount of BTC actually locked in the bridge. Every call to `safe_mint` for an unregistered recipient silently inflates supply by `amount` satoshis worth of nBTC. The excess tokens sit in the bridge's own nBTC balance and cannot be burned through any normal user-facing flow (the `burn` function is also restricted to the bridge, and the bridge has no automatic recovery path for this case). Restoring the 1:1 backing invariant requires privileged operator intervention to identify and burn the stranded balance.

This matches the **Medium** impact class: broken supply invariant / stuck bridge state requiring operator intervention, without direct theft of user funds.

---

### Likelihood Explanation

This is triggered whenever a BTC deposit is verified and `safe_mint` is called for a NEAR account that has not yet registered with the nBTC contract. Users who send BTC to the bridge before registering their NEAR account — a realistic ordering, since the BTC transaction is submitted on-chain independently — will trigger this path. The satoshi-bridge calls `safe_mint` as part of the deposit flow, and the registration check is entirely inside the nBTC contract, invisible to the depositor.

---

### Recommendation

Move the registration check **before** the `internal_deposit` call so that no tokens are minted if the recipient cannot receive them:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    // Guard BEFORE minting — no tokens enter supply if recipient is unregistered
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));
    }
    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ... rest of transfer logic
}
```

---

### Proof of Concept

1. User sends BTC to the bridge deposit address without first calling `storage_deposit` on the nBTC contract.
2. A relayer submits the Merkle proof; the satoshi-bridge verifies the deposit and calls `nbtc.safe_mint(user_account, amount, None)`.
3. Inside `safe_mint`, `internal_deposit(&bridge_id, amount)` executes — nBTC total supply increases by `amount`, bridge's nBTC balance increases by `amount`.
4. `self.token.accounts.get(&user_account).is_none()` returns `true` — user is not registered.
5. Function returns `PromiseOrValue::Value(U128(0))` — satoshi-bridge receives 0, interprets as "no tokens delivered."
6. No burn is performed. `amount` nBTC tokens are permanently stranded in the bridge's own balance.
7. nBTC `ft_total_supply()` now exceeds the BTC actually locked, breaking the 1:1 backing invariant. [2](#0-1)
