Audit Report

## Title
`initTransfer1155` Emits `InitTransfer` Without Actual Token Lock for Non-Existent ERC-1155 Contracts — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`initTransfer1155` casts `tokenAddress` directly to `IERC1155` and calls `safeTransferFrom` with no contract-existence check. On the EVM, a `CALL` to an address with no deployed code returns `(true, "")`. Because `safeTransferFrom` is void, Solidity accepts the empty return data without reverting, the call is treated as successful, and `InitTransfer` is emitted as if real tokens were locked. The NEAR `fin_transfer_callback` treats any proven `InitTransfer` event as authoritative and mints the stated amount to the recipient, enabling unauthorized minting of bridged funds with zero collateral.

## Finding Description

**EVM side — `initTransfer1155` (lines 439–490):**

`IERC1155(tokenAddress).safeTransferFrom(msg.sender, address(this), tokenId, amount, "")` is a raw interface dispatch. Solidity compiles this to a `CALL` opcode. When `tokenAddress` has no code, the EVM returns `(returnSuccess=1, returnData="")`. Because `IERC1155.safeTransferFrom` has no return type, the ABI decoder performs no length or content check on the return data, so execution continues normally. The `InitTransfer` event is then emitted with the caller-supplied `amount`.

Contrast with the ERC-20 path at lines 407–412, which uses `IERC20(tokenAddress).safeTransferFrom(...)` via OpenZeppelin's `SafeERC20` library. `SafeERC20` routes through `Address.functionCall` → `verifyCallResultFromTarget`, which explicitly checks `target.code.length == 0` and reverts with `AddressEmptyCode`. No equivalent wrapper exists for ERC-1155.

The bridge's `onERC1155Received` guard (lines 522–535) checks `operator != address(this)` and reverts for direct sends, but this callback is only invoked by a real ERC-1155 contract during its own `safeTransferFrom` execution. When the token address has no code, no callback is ever dispatched, so this guard is never reached.

**EVM side — `logMetadata1155` (lines 234–270):**

`logMetadata1155` performs no existence check on `tokenAddress`. It stores the `multiTokens` mapping and emits `LogMetadata(deterministicToken, hex(A), "", 0)` for any address, including undeployed ones. The emitted `symbol=""` and `decimals=0` are passed verbatim.

**NEAR side — `deploy_token_callback` (lines 1147–1175):**

`deploy_token_callback` receives the proven `LogMetadata` event and calls `deploy_token_internal` with `metadata.name`, `metadata.symbol`, and `metadata.decimals` directly — no validation that `symbol` is non-empty or `decimals > 0`. The NEAR `log_metadata_callback` (for NEAR-originated tokens, lines 336–338) does enforce `!metadata.symbol.is_empty()`, but this check is absent for EVM-originated `LogMetadata` proofs. `decimals=0` is therefore accepted, and `token_decimals` is set for `deterministicToken`.

**NEAR side — `fin_transfer_callback` (lines 700–746):**

`fin_transfer_callback` decodes the proven `InitTransfer` event, checks only that the emitter is a registered factory, looks up `token_decimals` for `init_transfer.token`, and proceeds to mint or unlock `denormalize_amount(init_transfer.amount, decimals)` tokens to the recipient. There is no secondary verification that the EVM-side token transfer actually occurred.

**Full exploit path:**

1. Attacker calls `logMetadata1155(A, tokenId)` where `A` has no deployed code. `multiTokens[deterministicToken]` is written; `LogMetadata(deterministicToken, hex(A), "", 0)` is emitted.
2. Relayer submits proof of `LogMetadata` to NEAR `deploy_token`. `deploy_token_callback` accepts `decimals=0`, `symbol=""`, and registers `deterministicToken` with `token_decimals[deterministicToken] = 0`.
3. Attacker calls `initTransfer1155(A, tokenId, 1_000_000e18, 0, 0, "attacker.near", "")`. `IERC1155(A).safeTransferFrom(...)` succeeds silently (no code at `A`). `InitTransfer(attacker, deterministicToken, nonce, 1_000_000e18, 0, 0, "attacker.near", "")` is emitted.
4. Relayer submits proof of `InitTransfer` to NEAR `fin_transfer`. `fin_transfer_callback` reads `amount = 1_000_000e18` from the proven log and mints the corresponding NEAR-side tokens to `attacker.near`.

No admin role, no victim interaction, and no privileged access is required at any step.

## Impact Explanation

This is a Critical unauthorized minting vulnerability. An attacker can mint an arbitrary quantity of NEAR-side bridged tokens backed by zero locked EVM collateral. The minted tokens can be redeemed for real assets on NEAR or routed to other chains via the bridge, constituting direct theft of bridged funds. This matches the allowed Critical impact class: "unauthorized minting of bridged funds."

## Likelihood Explanation

Both `logMetadata1155` and `initTransfer1155` are fully permissionless — no role check, no whitelist, no admin approval. The attacker needs only a funded EVM account and a NEAR account. The two-step registration (EVM `logMetadata1155` → NEAR `deploy_token`) is the standard bridge onboarding flow and is explicitly documented as permissionless in `SECURITY.md`. The attack is repeatable with different `(tokenAddress, tokenId)` pairs, each producing a fresh `deterministicToken`. No self-destruct or CREATE2 prediction is required; calling `logMetadata1155` with any address that has no code (e.g., a freshly generated EOA-style address with no contract) is sufficient.

## Recommendation

1. Add a contract-existence check at the top of `initTransfer1155` before the `safeTransferFrom` call:
   ```solidity
   require(tokenAddress.code.length > 0, "ERR_TOKEN_NOT_DEPLOYED");
   ```
2. Apply the same check in `logMetadata1155` before writing `multiTokens` and emitting `LogMetadata`, to prevent registration of undeployed addresses.
3. Consider wrapping ERC-1155 calls in a helper analogous to `SafeERC20` that verifies `target.code.length > 0` before dispatching, consistent with how the ERC-20 path is protected.
4. On the NEAR side, add validation in `deploy_token_callback` that `metadata.symbol` is non-empty, consistent with the existing check in `log_metadata_callback` for NEAR-originated tokens.

## Proof of Concept

```
// Step 1 — Register a non-existent ERC-1155 address
address A = address(0xdead...); // no code at this address
uint256 tokenId = 1;
omniBridge.logMetadata1155(A, tokenId);
// Emits: LogMetadata(deterministicToken, hex(A), "", 0)

// Step 2 — NEAR: submit proof of LogMetadata to deploy_token
// deploy_token_callback accepts decimals=0, symbol=""
// token_decimals[deterministicToken] = 0 is now set on NEAR

// Step 3 — Trigger fake transfer
omniBridge.initTransfer1155(A, tokenId, 1_000_000e18, 0, 0, "attacker.near", "");
// IERC1155(A).safeTransferFrom(...) → A has no code → EVM returns (true, "")
// Solidity accepts void return → no revert
// Emits: InitTransfer(attacker, deterministicToken, nonce, 1_000_000e18, ...)

// Step 4 — NEAR: submit proof of InitTransfer to fin_transfer
// fin_transfer_callback reads amount=1_000_000e18 from proven log
// Mints 1,000,000 bridged tokens to attacker.near
```

A Foundry test can confirm step 3 by deploying `OmniBridge`, calling `initTransfer1155` with an address that has no code, and asserting that `InitTransfer` is emitted and no token balance change occurs on the bridge.
