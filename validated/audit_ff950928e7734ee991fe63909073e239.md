### Title
Peras Quorum Check Bypassed Due to Unit Mismatch in `stakeAboveThreshold` — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` compares a `PerasVoteStake` value directly against a relative quorum threshold (`3/4`) without any normalization step. The code itself acknowledges — via a TODO comment — that this comparison is only correct when both operands are in the same unit (both relative/normalized). Because there is no enforcement of this invariant and no consensus on how to normalize absolute ledger stake into a relative vote stake, any caller that supplies absolute lovelace values will cause the quorum check to trivially pass for any vote, bypassing the Peras certificate-forging requirement.

---

### Finding Description

`stakeAboveThreshold` in `SupportsPeras.hs` performs:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake        = unPerasVoteStake voteStake
  quorumThreshold = unPerasQuorumStakeThreshold (perasQuorumStakeThreshold params)
  safetyMargin    = unPerasQuorumStakeThresholdSafetyMargin (perasQuorumStakeThresholdSafetyMargin params)
``` [1](#0-0) 

The default `PerasParams` sets `perasQuorumStakeThreshold = 3/4` and `perasQuorumStakeThresholdSafetyMargin = 2/100`, both **relative** (normalized) values. [2](#0-1) 

The code itself carries an explicit TODO acknowledging the unit assumption is unverified:

> *"this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally."* [3](#0-2) 

The `PerasVoteStake` type itself carries a NOTE confirming the normalization step is unresolved:

> *"At the moment there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee."* [4](#0-3) 

`stakeAboveThreshold` is called in two production paths:

1. `votesReachQuorum` → `updateCandidateVoteState` (certificate forging path): [5](#0-4) 

2. `updateLoserVoteState` (multiple-winner detection path): [6](#0-5) 

The `PerasVoteStake` for each vote is sourced from `PerasVoteStakeDistr` via `lookupPerasVoteStake` inside `validatePerasVote`: [7](#0-6) 

If `PerasVoteStakeDistr` is populated with absolute lovelace values from the ledger (the natural source), then a voter with even 1 lovelace has `PerasVoteStake = 1/1 = 1.0`. Since `1.0 >= 0.75 + 0.02 = 0.77` is `True`, **a single vote from any stakeholder reaches quorum immediately**, regardless of their actual relative stake. Conversely, if the threshold were ever expressed in absolute lovelace while votes are normalized, no quorum would ever be reached.

---

### Impact Explanation

This is a **Critical bypass of Peras certificate/voting checks**. An unprivileged peer with any positive stake can cause a Peras certificate to be forged for an adversarially chosen block by submitting a single vote. The forged certificate carries a `PerasWeight` boost (default: 15) applied during chain selection, causing honest nodes to prefer the adversarially boosted chain over the canonical chain. This directly undermines the Peras fast-finality guarantee and can cause irreversible chain divergence.

---

### Likelihood Explanation

The Peras vote pipeline is reachable by any peer that can submit votes via the Peras miniprotocol. The normalization step is explicitly documented as missing and unresolved. Any integration that sources `PerasVoteStakeDistr` from raw ledger stake (absolute lovelace) — the only available source — will trigger the bypass. The likelihood is **High** once Peras is activated on a live network.

---

### Recommendation

Normalize `PerasVoteStake` to a relative value (dividing each voter's absolute stake by the total active stake) before it is stored in `PerasVoteStakeDistr` and before `stakeAboveThreshold` is called. Alternatively, change `stakeAboveThreshold` to accept the total stake distribution and perform the normalization internally, analogous to the fix recommended in the external report (`tokenAmount * RATE_DECIMALS_MULTIPLIER >= stopTime - startTime`).

---

### Proof of Concept

Given `mkPerasParams` defaults (`quorumThreshold = 3/4`, `safetyMargin = 2/100`):

1. Attacker holds 1 lovelace out of 45,000,000,000,000,000 total lovelace (negligible relative stake ≈ 2.2 × 10⁻¹⁷).
2. Ledger populates `PerasVoteStakeDistr` with absolute value: `PerasVoteStake (1 % 1)`.
3. Attacker submits one vote for an adversarial block `B_adv` in round `r`.
4. `validatePerasVote` looks up stake → `PerasVoteStake (1 % 1)`.
5. `votesReachQuorum` calls `stakeAboveThreshold`: `1 % 1 >= 3 % 4 + 2 % 100` → `True`.
6. `forgePerasCert` is called; a `ValidatedPerasCert` with `vpcCertBoost = PerasWeight 15` is produced for `B_adv`.
7. Honest nodes receiving this certificate apply the boost to `B_adv` in chain selection, preferring it over the canonical chain.
