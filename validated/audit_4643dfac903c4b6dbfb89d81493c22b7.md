### Title
Peras Certificate Validation Is a Permanent No-Op with No Configuration Path — (`Ouroboros/Consensus/Block/SupportsPeras.hs` + `ObjectPool/PerasCert.hs`)

---

### Summary

The sole `BlockSupportsPeras` instance unconditionally accepts every inbound Peras certificate (`validatePerasCert` always returns `Right`), and the inbound-certificate processing pipeline hard-codes `mkPerasParams` instead of reading parameters from the node configuration. There is no mechanism to supply real validation logic or real protocol parameters at runtime. An unprivileged peer can therefore inject an arbitrary crafted certificate, have it stored in the `PerasCertDB`, and cause the node's chain-selection logic to switch from the standard longest-chain rule to Peras-weighted chain selection — boosting a fork of the attacker's choice by a fixed weight of 15 — without any quorum, signature, or round-number check ever being performed.

---

### Finding Description

**1. `validatePerasCert` is a permanent stub that accepts every certificate**

The only `BlockSupportsPeras` instance in the codebase is explicitly labelled a "degenerate instance for all blks to get things to compile":

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

Every certificate, regardless of its content, round number, or claimed quorum, is accepted and assigned a boost of `perasWeight params`.

**2. The inbound pipeline hard-codes `mkPerasParams` — no configuration path exists**

`processCerts`, the function that handles certificates arriving from peers over the network, calls:

```haskell
(validatePerasCert mkPerasParams)
``` [2](#0-1) 

`mkPerasParams` is a compile-time constant. There is no function, genesis-file field, or runtime argument that can supply different `PerasParams` to this call site. The `PerasParams` data type is fully defined and consumed by voting rules, certificate-inclusion rules, and chain selection, but — exactly like `fee_protocol` in the reference report — there is no setter or configuration path that would allow the node operator (or the protocol itself) to supply real values at runtime. [3](#0-2) 

**3. Accepted certificates directly drive chain selection**

`preferAnchoredCandidate` branches on whether the `PerasWeightSnapshot` is empty:

```haskell
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      -- standard longest-chain rule
  | otherwise =
      -- Peras-weighted comparison using weightedSelectView
``` [4](#0-3) 

Once a single certificate is injected, the snapshot becomes non-empty, Peras-weighted chain selection activates, and the boosted fork gains a `PerasWeight 15` advantage over every competing chain that lacks a certificate. [5](#0-4) 

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` that names any block point and any round number. Because `validatePerasCert` always returns `Right`, the certificate passes `processCerts`, is timestamped, and is inserted into the `PerasCertDB` via `addPerasCertAsync`. Chain selection is then triggered for the boosted block. If the attacker's fork tip has block number `N` and the honest chain tip has block number `N`, the attacker's fork wins by `PerasWeight 15` — enough to cause the node to roll back to the attacker's fork. This constitutes an unprivileged-peer-triggered chain-selection manipulation: the node accepts a non-canonical chain that it would otherwise reject under the standard longest-chain rule.

---

### Likelihood Explanation

The `processCerts` function is reachable from the Peras certificate mini-protocol object pool, which is wired into the node's peer-to-peer diffusion layer. Any connected peer can submit a batch of certificates. No stake, key material, or operator access is required. The only prerequisite is that Peras is active (i.e., the node is running a build that includes the Peras diffusion code), which is the direction the codebase is moving.

---

### Recommendation

1. **Implement real `validatePerasCert` logic** that checks the certificate's quorum proof, round number bounds, and cryptographic signatures before returning `Right`. Remove the stub instance and replace it with a proper era-specific implementation.

2. **Thread `PerasParams` from the node configuration** (genesis file or `BlockConfig`) into `processCerts` and all other call sites that currently hard-code `mkPerasParams`. The `mkPerasParams` constant should only be used as a fallback default during the bootstrapping phase, not in production validation paths.

3. **Guard `addPerasCertAsync`** so that a certificate whose boosted block is not yet known to the node cannot silently activate Peras-weighted chain selection.

---

### Proof of Concept

1. Connect to a node running the Peras-enabled build as an ordinary peer.
2. Construct a `PerasCert` with `pcCertRound = PerasRoundNo 0` and `pcCertBoostedBlock` pointing to the tip of a fork that is one block shorter than the honest chain.
3. Send the certificate via the Peras certificate mini-protocol.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert { vpcCertBoost = PerasWeight 15 }` unconditionally.
5. The certificate is stored; `addPerasCertAsync` triggers `chainSelectionForBlock` for the boosted block.
6. `preferAnchoredCandidate` now uses Peras-weighted comparison: the fork's total weight = `blockNo fork_tip + 15`, which exceeds the honest chain's total weight = `blockNo honest_tip + 0` whenever `blockNo fork_tip >= blockNo honest_tip - 14`.
7. The node rolls back to the attacker's fork. [6](#0-5) [7](#0-6)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
