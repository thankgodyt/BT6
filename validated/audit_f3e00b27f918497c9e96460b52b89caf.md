### Title
Missing Network-Specific Domain Separator in Peras BLS Vote Signature Hash Enables Cross-Network Vote Replay - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Peras/Crypto/BLS.hs`)

---

### Summary

The `hashVoteSignature` function used to sign and verify Peras BLS votes does not include any network-specific identifier (network magic, genesis hash, or domain tag) in its hash preimage. A valid Peras vote signature produced on one Cardano network is cryptographically indistinguishable from a valid vote on any other network that shares the same `(roundNo, boostedBlockSlot, boostedBlockHash)` tuple. An unprivileged peer can replay a vote received from one network onto another, bypassing vote authorization and potentially contributing to a false quorum.

---

### Finding Description

`hashVoteSignature` in `Ouroboros.Consensus.Peras.Crypto.BLS` constructs the 48-byte preimage that is hashed and then BLS-signed for every Peras vote:

```haskell
hashVoteSignature roundNo boostedBlock =
  Hash.castHash
    . Hash.hashWith id
    . runByteBuilder (8 + 8 + 32)
    $ roundNoBytes
      <> boostedBlockSlotBytes
      <> boostedBlockHashBytes
```

The preimage is strictly `roundNo (8 B) || boostedBlockSlot (8 B) || boostedBlockHash (32 B)`. No network magic, genesis hash, or any other chain-specific domain separator is mixed in. [1](#0-0) 

Both `signVote` and `verifyVoteSignature` in the `CryptoSupportsVoteSigning PerasBLSCrypto` instance call this function directly:

```haskell
signVote sk roundNo boostedBlock =
    PerasBLSCryptoVoteSignature . BLS.signWithRole @SIGN sk
      $ hashVoteSignature roundNo boostedBlock

verifyVoteSignature pk roundNo boostedBlock (PerasBLSCryptoVoteSignature sig) =
    BLS.verifyWithRole @SIGN pk (hashVoteSignature roundNo boostedBlock) sig
``` [2](#0-1) 

The same pattern is present in the aggregate-signature path used for certificate verification:

```haskell
verifyAggregateVoteSignature _ aggPk roundNo boostedBlock aggSig =
    BLS.verifyWithRole @SIGN
      (unPerasBLSCryptoAggregateVoteVerificationKey aggPk)
      (hashVoteSignature roundNo boostedBlock)
      (unPerasBLSCryptoAggregateVoteSignature aggSig)
``` [3](#0-2) 

Votes arrive over the network via the `PerasVoteDiffusion` mini-protocol. `processVotes` in `ObjectPool.PerasVote` validates each inbound vote by calling `validatePerasVote` and, on success, stores it in the `PerasVoteDB` / `ChainDB`. The validation path ultimately calls `verifyVoteSignature` above. [4](#0-3) 

Because the hash preimage contains no network-specific context, a BLS signature that is valid on Network A is also valid on Network B whenever the same `(roundNo, boostedBlockSlot, boostedBlockHash)` triple exists on both networks.

---

### Impact Explanation

**Impact: Critical — bypass of Peras vote authorization enabling unauthorized vote acceptance.**

If an attacker can replay votes across networks, they can contribute to a quorum on the target network without holding the required stake on that network. A quorum produces a `PerasCert` that boosts a specific block's chain-selection weight by `perasWeight` (currently 15 blocks' worth). Replayed votes that push a round over the quorum threshold cause the target node to accept a certificate it should reject, directly corrupting the Peras chain-selection invariant and potentially causing an irreversible divergence from the canonical chain.

The `PerasCert` produced from replayed votes is stored in the `PerasCertDB` and used in chain selection, making the impact durable. [5](#0-4) 

---

### Likelihood Explanation

**Likelihood: Medium.**

The `boostedBlockHash` field is a hash of a specific block header, which chains the vote to a particular block. Two networks share the same block hash only if they share the same chain history up to that block. This is a realistic scenario in the following cases:

1. **Testnet forked from mainnet**: A private testnet or preview network created from a mainnet snapshot shares all block hashes up to the fork point. Any Peras round that falls within the shared history has an identical `(roundNo, slot, hash)` tuple on both networks.
2. **Hard-fork transition**: If Peras is activated at the same epoch on two networks that share a common ancestor chain, early-round votes are replayable.
3. **Deliberate cross-network attack**: An operator running nodes on both mainnet and a testnet (e.g., for testing) uses the same BLS signing key on both. A vote cast on the testnet is automatically valid on mainnet for any block that exists on both chains.

The Peras diffusion layer (`hPerasVoteDiffusionClient`) is reachable by any unprivileged peer without authentication. [6](#0-5) 

---

### Recommendation

Include a network-specific domain separator in `hashVoteSignature`. The natural choice is the network magic (already present in `ShelleyConfig`) or the genesis hash. For example:

```haskell
hashVoteSignature networkMagic roundNo boostedBlock =
  Hash.castHash
    . Hash.hashWith id
    . runByteBuilder (4 + 8 + 8 + 32)
    $ networkMagicBytes
      <> roundNoBytes
      <> boostedBlockSlotBytes
      <> boostedBlockHashBytes
 where
  networkMagicBytes = BS.word32BE (unNetworkMagic networkMagic)
  ...
```

The same fix must be applied to `hashVRFInput` (which also lacks a network separator) and to the `TestCrypto` implementation in `Test.Consensus.Committee.TestCrypto` to keep the test crypto consistent. [7](#0-6) [8](#0-7)

### Proof of Concept

**Setup:** Network A (mainnet) and Network B (a testnet forked from mainnet at slot `S_fork`). Both share identical block history up to `S_fork`, so any block at slot `S ≤ S_fork` has the same hash on both networks.

**Steps:**

1. Peras round `R` is active on both networks. The boosted block candidate is `(slot=S, hash=H)` where `S ≤ S_fork`.

2. A committee member on Network A signs a vote:
   ```
   preimage = encode(R) || encode(S) || H   -- 48 bytes, no network tag
   sig = BLS.sign(sk, Blake2b_256(preimage))
   vote_A = PerasVote { pvRoundNo=R, pvBoostedBlock=(S,H), ..., pvSignature=sig }
   ``` [9](#0-8) 

3. An attacker relays `vote_A` to a node on Network B via the `PerasVoteDiffusion` mini-protocol.

4. Network B's `processVotes` calls `validatePerasVote` → `verifyVoteSignature`:
   ```
   preimage_B = encode(R) || encode(S) || H   -- identical to preimage on A
   BLS.verify(pk, Blake2b_256(preimage_B), sig)  -- succeeds
   ``` [10](#0-9) 

5. The vote is accepted and stored in Network B's `PerasVoteDB`. If enough replayed votes accumulate, a `PerasCert` is forged for block `(S, H)` on Network B, boosting it in chain selection — without any legitimate committee member on Network B having voted. [11](#0-10)

processVotes ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
