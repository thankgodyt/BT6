### Title
Peras Certificate Inbound Validation Bypass Accepts Any Peer-Crafted Certificate - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` method in the degenerate `BlockSupportsPeras` instance unconditionally returns `Right` (success) for every inbound certificate, performing no cryptographic, round-number, or quorum checks. The `processCerts` inbound pipeline calls this function directly on peer-supplied certificates before adding them to the `PerasCertDB` and triggering chain selection. An unprivileged peer can therefore inject a crafted `PerasCert` for any round and any block point, causing the receiving node to treat that certificate as valid and boost the weight of an attacker-chosen chain.

---

### Finding Description

`processCerts` is the entry point for all Peras certificates received over the object-diffusion miniprotocol. It filters out round numbers already in the database, then calls the caller-supplied `validateCert` function on every remaining certificate: [1](#0-0) 

Both production pool-writer constructors wire in `validatePerasCert mkPerasParams` as that function: [2](#0-1) [3](#0-2) 

`validatePerasCert` is defined in the degenerate `BlockSupportsPeras` instance as an unconditional `Right`: [4](#0-3) 

The `PerasValidationErr` data type is likewise a single constructor with no fields, and the `implAddCert` implementation carries an explicit TODO noting that non-trivial validation logic is still missing: [5](#0-4) 

The `BlockSupportsPeras` class signature shows that `validatePerasCert` is the designated gate for all certificate acceptance: [6](#0-5) 

No check is performed on:
- the certificate's `pcCertRound` against the current Peras round,
- the aggregate signature / quorum proof,
- the boosted block point against the local chain,
- or any expiry / staleness window.

This is structurally identical to the external report's root cause: a validation function that is supposed to check temporal/contextual validity of an externally supplied object simply does not do so, allowing any object to pass.

---

### Impact Explanation

A successfully injected certificate is stored in `PerasCertDB` and forwarded to `ChainDB.addPerasCertAsync`, which triggers chain selection. The Peras protocol uses certificate weight to prefer one chain over another. By injecting a certificate whose `pcCertBoostedBlock` points to an attacker-controlled or non-canonical block, an adversary can cause an honest node to prefer a chain it would otherwise reject, constituting a **bypass of certificate validation that enables unauthorized certificate acceptance** and a potential chain-selection safety failure.

**Impact: Critical** — matches "Bypass of … certificate … checks … that enables unauthorized … certificate acceptance."

---

### Likelihood Explanation

The object-diffusion miniprotocol is reachable by any peer that can establish a connection to the node. No stake, key material, or privileged access is required. The attacker only needs to send a well-formed CBOR-encoded `PerasCert` with an arbitrary round number and block point. The degenerate instance is the only instance in the codebase and is used in both the `PerasCertDB`-backed and `ChainDB`-backed production writers.

**Likelihood: High** — zero-privilege network peer, no brute force required, single crafted message suffices.

---

### Recommendation

- **Short term**: `validatePerasCert` must receive the current Peras round number (or a window thereof) and reject certificates whose `pcCertRound` falls outside the acceptable window (analogous to the external report's recommendation to check a timestamp window). It must also verify the aggregate signature and quorum proof before accepting any certificate.
- **Long term**: Replace the degenerate `BlockSupportsPeras` instance with a proper era-aware implementation that performs full certificate validation (signature, quorum, round bounds, boosted-block reachability) before any certificate is admitted to the `PerasCertDB` or forwarded to chain selection.

---

### Proof of Concept

1. Connect to a node running the object-diffusion miniprotocol for Peras certificates.
2. Craft a `PerasCert` with `pcCertRound = <any past or future round>` and `pcCertBoostedBlock = <point of an attacker-chosen block>`.
3. Send the certificate as a batch via the miniprotocol.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{...}` unconditionally.
5. The certificate is stored in `PerasCertDB` and `ChainDB.addPerasCertAsync` is called, triggering chain selection with the boosted weight applied to the attacker-chosen block.

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
```
