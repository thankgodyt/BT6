### Title
Unvalidated Caller-Controlled `key_version` in Public `sign_btc_transaction` Enables Attacker to Corrupt MPC Signatures and Temporarily Lock Bridged Funds - (File: contracts/satoshi-bridge/src/api/chain_signatures.rs)

### Summary

`sign_btc_transaction` is a public, role-unrestricted function that any NEAR account can call for any pending withdrawal, refund, or UTXO-management transaction. It accepts a caller-controlled `key_version: u32` parameter that is forwarded unvalidated to the MPC chain-signatures service. An attacker who observes a pending-sign event can race the legitimate signer, supply a wrong `key_version`, and cause the MPC to produce a signature under a different root key than the one that controls the bridge's UTXO. The resulting signed transaction is invalid on Bitcoin and cannot be broadcast, leaving the user's funds stuck in the pending-sign pipeline until operator intervention.

### Finding Description

`sign_btc_transaction` carries only `#[payable]` and `#[pause]` decorators — no `#[access_control_any]` or caller-identity check is present. [1](#0-0) 

The only guard inside the function body is `assert_pending_sign()`, which verifies the pipeline state, not the caller's identity. [2](#0-1) 

`key_version` is passed straight through to `internal_sign_btc_transaction` without any comparison against a contract-configured expected value. In NEAR chain signatures, `key_version` selects which root key the MPC uses to derive the signing key for the given path. The bridge derives all deposit and change addresses from one specific root key. If a caller supplies a different `key_version`, the MPC signs the PSBT hash under a different root key, producing a signature that does not satisfy the `scriptPubKey` of any bridge-controlled UTXO. The signed transaction bytes stored in `tx_bytes_with_sign` are therefore permanently invalid for broadcast.

Pending-sign transaction IDs are emitted publicly via `GenerateBtcPendingInfo` events: [3](#0-2) 

Any observer can extract the `btc_pending_id` from the event log and immediately race the legitimate signer.

### Impact Explanation

**Medium — attacker-triggered temporary locking of bridged funds.**

Once `sign_btc_transaction` completes with a wrong `key_version`, the `BTCPendingInfo` transitions out of `PendingSign` state (the `assert_pending_sign()` guard would block a second call), so the legitimate signer can no longer re-sign the same pending entry. The user's nBTC has already been transferred to the bridge contract and the corresponding BTC UTXO is locked in the bridge's UTXO set. Recovery requires operator intervention (e.g., creating a new RBF or cancel-withdraw transaction). A persistent attacker can repeat the attack on every newly created RBF entry, indefinitely blocking the withdrawal.

### Likelihood Explanation

**High.** No privileged access is required. The attacker only needs to:
1. Monitor the NEAR event stream for `GenerateBtcPendingInfo` events (public).
2. Submit `sign_btc_transaction(id, 0, <wrong_version>)` before the relayer does.

NEAR transaction ordering is deterministic within a block; a well-timed submission or a simple front-run on the relayer's signing call is sufficient. The cost is a small attached NEAR deposit (the `#[payable]` requirement), which is negligible.

### Recommendation

1. **Validate `key_version` on entry.** Store the expected key version in `Config` and `require!` that the caller-supplied value matches:
   ```rust
   require!(
       key_version == self.internal_config().chain_signatures_key_version,
       "Invalid key_version"
   );
   ```
2. **Restrict the caller** to the account that owns the pending transaction (`btc_pending_info.account_id`) or to a whitelisted relayer role, consistent with how other sensitive pipeline steps are guarded.

### Proof of Concept

1. Alice calls `ft_transfer_call` on the nBTC contract with a `Withdraw` message. The bridge creates a `BTCPendingInfo` in `PendingSign` state and emits:
   ```
   GenerateBtcPendingInfo { account_id: "alice", btc_pending_id: "abc123..." }
   ```
2. Attacker observes the event and immediately submits:
   ```
   sign_btc_transaction("abc123...", 0, 999)   // key_version=999 is wrong
   ```
   No role check blocks this call.
3. The MPC chain-signatures contract signs the PSBT hash using root key version 999, which does not correspond to any bridge-controlled address.
4. The bridge stores the resulting (invalid) signature in `tx_bytes_with_sign` and advances the state out of `PendingSign`.
5. The relayer attempts to broadcast the signed transaction; Bitcoin nodes reject it because the signature does not satisfy the input's `scriptPubKey`.
6. Alice's nBTC is held by the bridge and her BTC UTXO is locked. The `assert_pending_sign()` guard prevents re-signing the same entry. Operator must manually create a cancel-withdraw or new RBF transaction — and the attacker can repeat step 2 on each new entry.

    pub fn sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,

        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        btc_pending_info.assert_pending_sign();
        if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {
            if !self.check_btc_pending_info_exists(original_tx_id) {
