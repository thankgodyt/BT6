### Title
`ft_on_transfer` applies `min_withdraw_amount` to `DepositProtocolFee`, inadvertently blocking small-amount protocol-fee deposits — (File: `contracts/satoshi-bridge/src/api/token_receiver.rs`)

---

### Summary

The `ft_on_transfer` entry point enforces `min_withdraw_amount` on **every** incoming token transfer before the message is even parsed. This guard is semantically correct for `Withdraw` messages, but it also silently rejects the `DepositProtocolFee` variant when the transferred amount is below the configured minimum, even though protocol-fee deposits carry no minimum-amount requirement.

---

### Finding Description

`ft_on_transfer` is the NEP-141 receiver callback invoked whenever nBTC tokens are sent to the bridge via `ft_transfer_call`. It handles two distinct message variants:

```
TokenReceiverMessage::DepositProtocolFee   // deposit fees into the bridge pool
TokenReceiverMessage::Withdraw { … }       // initiate a BTC withdrawal
```

The minimum-amount guard fires **before** the message is decoded:

```rust
// contracts/satoshi-bridge/src/api/token_receiver.rs  lines 30-34
require!(
    amount >= self.internal_config().min_withdraw_amount,
    "Invalid amount"
);
let message = serde_json::from_str::<TokenReceiverMessage>(&msg).expect("INVALID MSG");
```

Because the `require!` is unconditional, any `ft_transfer_call` that carries a `DepositProtocolFee` message with `amount < min_withdraw_amount` panics with `"Invalid amount"` and never reaches the match arm that would credit the fee pool. The `min_withdraw_amount` threshold exists to ensure a BTC withdrawal can cover on-chain gas fees; it has no relevance to a protocol-fee deposit, which is a pure accounting operation on NEAR with no BTC transaction involved.

This is structurally identical to the reported `Guard::checkTransaction` pattern: a blanket data-length (or, here, amount-size) guard designed for one operation class is applied uniformly to all operations, inadvertently blocking a legitimate zero-constraint variant.

---

### Impact Explanation

**Low.** When `ft_on_transfer` panics, the NEP-141 standard requires the token contract's `ft_resolve_transfer` callback to refund the caller's tokens, so funds are not permanently lost. The concrete harm is:

- Any caller attempting to deposit protocol fees below `min_withdraw_amount` receives a hard revert ("Invalid amount") and must retry with a larger amount or not at all.
- The bridge's `acc_collected_protocol_fee` / `cur_available_protocol_fee` counters are never incremented for that call, silently under-counting available protocol fees.
- If the nBTC token contract's `ft_resolve_transfer` has any defect, the tokens could become stuck — a secondary risk that cannot be ruled out without auditing the nBTC contract.

This matches the allowed scope: *"Publicly reachable invariant-violation, stuck-state, or panic-driven fault in production bridge/token paths without direct theft."*

---

### Likelihood Explanation

Any unprivileged NEAR account can call `ft_transfer_call` on the nBTC token with `msg = "DepositProtocolFee"` and a small amount. The `DepositProtocolFee` variant is a documented, public-facing message type. The condition is trivially reachable whenever the deposited amount is below the configured `min_withdraw_amount`.

---

### Recommendation

Move the `min_withdraw_amount` guard inside the `Withdraw` match arm, where it is semantically meaningful, rather than applying it to all incoming transfers:

```rust
fn ft_on_transfer(
    &mut self,
    sender_id: AccountId,
    amount: U128,
    msg: String,
) -> PromiseOrValue<U128> {
    let amount: u128 = amount.into();
    let message = serde_json::from_str::<TokenReceiverMessage>(&msg).expect("INVALID MSG");
    let token_id = env::predecessor_account_id();
    require!(token_id == self.internal_config().nbtc_account_id, "Invalid token_id");
    match message {
        TokenReceiverMessage::DepositProtocolFee => { /* no minimum needed */ … }
        TokenReceiverMessage::Withdraw { … } => {
            require!(
                amount >= self.internal_config().min_withdraw_amount,
                "Invalid amount"
            );
            …
        }
    }
}
```

---

### Proof of Concept

1. Configure the bridge with `min_withdraw_amount = 10_000` satoshis.
2. As any NEAR account, call:
   ```
   nbtc.ft_transfer_call(
       receiver_id = bridge,
       amount      = "5000",          // below min_withdraw_amount
       msg         = "\"DepositProtocolFee\""
   )
   ```
3. `ft_on_transfer` panics at the `require!` on line 31 with `"Invalid amount"` before the message is parsed.
4. The nBTC token contract's `ft_resolve_transfer` refunds the 5 000 satoshis.
5. `bridge.acc_collected_protocol_fee` is unchanged; the deposit is silently rejected.

The root cause is the unconditional guard at [1](#0-0)  applied before the message variant is known, while the `DepositProtocolFee` branch at [2](#0-1)  has no minimum-amount requirement of its own.
