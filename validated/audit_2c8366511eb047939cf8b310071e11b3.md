### Title
Peras Certificate Validation Bypass Allows Unprivileged Peer to Inject Arbitrary Chain-Weight Boosts - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The universal `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or eligibility checks. Because this is the function invoked on every certificate received from a remote peer via the object-diffusion mini-protocol, any unprivileged peer can inject an arbitrary `PerasCert` that boosts any block in the VolatileDB, directly influencing chain selection when Peras is enabled.

### Finding Description

The degenerate `BlockSupportsPeras` instance, declared for all `StandardHash blk` types, stubs out `validatePerasCert` as an unconditional success:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/120
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

No committee membership check, no round-number validity check, no cryptographic signature verification, and no boosted-block eligibility check are performed. The function accepts every certificate unconditionally.

This stub is the exact function wired into the production inbound-certificate path. `makePerasCertPoolWriterFromChainDB` passes `validatePerasCert mkPerasParams` as the validator to `processCerts`:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

`processCerts` calls `validateCert` on each inbound certificate; because `validatePerasCert` always returns `Right`, every certificate passes and is forwarded to `ChainDB.addPerasCertAsync`: [3](#0-2) 

`chainSelSync` then processes the certificate, looks up the boosted block in the VolatileDB, and triggers `chainSelectionForBlock` for it: [4](#0-3) 

Chain selection compares candidates using `WeightedSelectView`, where `wsvWeightBoost` is the sum of all certificate boosts for blocks on the fragment. A forged certificate with a large boost can make an adversarial fork appear heavier than the honest chain: [5](#0-4) 

The same stub also applies to `validatePerasVote`, which only checks stake-distribution membership but performs no signature verification, allowing forged votes to accumulate toward a quorum and produce a locally-forged certificate: [6](#0-5) 

### Impact Explanation

When Peras is enabled, an unprivileged peer can send a crafted `PerasCert` that boosts any block already present in the local VolatileDB. Because `validatePerasCert` never rejects any certificate, the node accepts the boost unconditionally, updates its `PerasWeightSnapshot`, and re-runs chain selection. A sufficiently large forged boost can cause the node to switch away from the honest chain to an adversarial fork, constituting a **chain-selection safety failure**: an honest node is made to prefer a non-canonical, potentially less-secure chain purely through a crafted network message, with no stake majority or key compromise required.

This maps to: **High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.**

### Likelihood Explanation

Peras is currently disabled by default (the CHANGELOG notes "if Peras is disabled (which is the default), there is no observable difference"). However, the code is present and wired into the production path; any operator who enables Peras exposes their node to this attack. The exploit requires only a TCP connection to the object-diffusion port and the ability to send a well-formed CBOR-encoded `PerasCert` message — no credentials, no stake, no key material.

### Recommendation

Replace the stub `validatePerasCert` (and `validatePerasVote`) with implementations that perform the full cryptographic and eligibility checks mandated by the Peras protocol specification: committee membership verification, round-number range checks, and aggregate BLS/VRF signature verification. Until real validation is implemented, inbound Peras certificates from untrusted peers should be rejected entirely rather than accepted unconditionally. The existing `TODO` tracking issue (`https://github.com/tweag/cardano-peras/issues/120`) should be treated as a security-critical blocker before Peras is enabled in any production deployment.

### Proof of Concept

1. Enable Peras on a test node (set the Peras feature flag in `RunNodeArgs`).
2. Connect a malicious peer that speaks the object-diffusion mini-protocol.
3. The peer sends a `PerasCert` with `pcCertRound = <any round>` and `pcCertBoostedBlock = <hash of an adversarial block already in the VolatileDB>`, serialised as valid CBOR.
4. `processCerts` calls `validatePerasCert mkPerasParams` on the certificate; it returns `Right` unconditionally.
5. The certificate is inserted into `PerasCertDB` and `ChainDB.addPerasCertAsync` is called.
6. `chainSelSync` retrieves the boosted block from the VolatileDB and calls `chainSelectionForBlock`.
7. `constructPreferableCandidates` now computes a `WeightedSelectView` for the adversarial fork that includes the injected boost; if the boost exceeds the honest chain's weight advantage, `chainSelection` switches the node to the adversarial fork.
8. The node's selected chain is now the adversarial fork, with no cryptographic proof of legitimacy ever having been checked.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
