### Title
Refund Execution Blocked During Pause While Deposit Finalization Races on Unpause, Permanently Locking User Funds — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

The bridge's pause mechanism blocks both `execute_refund` and `request_refund` for unprivileged users, but the refund timelock continues to elapse during the pause. On unpause, automated relayer bots can immediately call `verify_deposit_v2` to finalize a deposit, permanently marking the UTXO as verified and blocking any pending refund request. Users who wanted to recover their BTC (e.g., due to a wrong `receiver_id` in the `DepositMsg`) have no grace period to execute their refund before the deposit is irreversibly finalized.

---

### Finding Description

The `satoshi-bridge` contract uses `near-plugins`' `Pausable` trait. The following public functions are all gated by `#[pause(except(roles(Role::DAO)))]`:

- `request_refund` — users cannot submit new refund requests while paused.
- `execute_refund` — users cannot execute pending refund requests while paused.
- `verify_deposit_v2` — relayers cannot finalize deposits while paused. [1](#0-0) [2](#0-1) [3](#0-2) 

All three become callable simultaneously the moment the `UnpauseManager` calls `pa_unpause_feature`. Relayers are automated bots that will immediately submit `verify_deposit_v2` on unpause. The refund timelock, however, is computed purely from wall-clock time stored at request creation (`created_at_sec`) versus `env::block_timestamp()` at execution time — it does not pause: [4](#0-3) 

This means a refund request created just before the pause may have its timelock fully expired by the time the protocol is unpaused, yet the user was unable to call `execute_refund` during that entire window.

Critically, `verify_deposit_v2` does **not** check for the existence of a pending `RefundRequest`. It only checks `verified_deposit_utxo`. Once a relayer calls `verify_deposit_v2` and the deposit is finalized, the UTXO is inserted into `verified_deposit_utxo`, and any subsequent `execute_refund` call will fail: [5](#0-4) 

The `reject_refund` function carries **no** `#[pause]` guard, meaning the DAO/Operator can reject refund requests during the pause while users cannot execute them — further tilting the asymmetry. [6](#0-5) 

---

### Impact Explanation

A user who sent BTC to a deposit address derived from a `DepositMsg` with an incorrect `receiver_id` (or any other parameter they wish to correct) and submitted a `request_refund` before the pause will find their refund permanently blocked on unpause. The relayer bot finalizes the deposit via `verify_deposit_v2`, minting nBTC to the wrong NEAR account. The user's BTC is irreversibly lost to an account they do not control. This matches the **Medium** impact class: attacker-triggered (relayer-triggered) permanent loss of user funds without direct theft by the relayer.

---

### Likelihood Explanation

- Protocol pauses are a documented, expected operational event (the `PauseManager` role exists precisely for this).
- Relayers are automated bots that will race to submit `verify_deposit_v2` immediately on unpause to collect fees.
- Users who made a mistake in their `DepositMsg` (wrong `receiver_id`, wrong `refund_address`) are the most vulnerable; they have a narrow window between sending BTC and the pause to submit `request_refund`.
- No grace period exists after unpause in the current code. [7](#0-6) 

---

### Recommendation

1. **Grace period after unpause**: After `pa_unpause_feature` is called, block `verify_deposit_v2` (and other deposit-finalizing functions) for a configurable grace period (e.g., `refund_timelock_sec`) to allow users to execute pending refunds first.
2. **Pause the refund timelock**: Subtract the total paused duration from the timelock check in `load_refund_request_for_execute`, so the effective timelock does not elapse while the contract is paused.
3. **Deposit-vs-refund awareness**: Make `verify_deposit_v2` check for an existing `RefundRequest` for the UTXO and revert (or route to lost-and-found) if one is present, giving the refund path priority.

---

### Proof of Concept

1. User sends BTC to a deposit address derived from `DepositMsg { receiver_id: "wrong.near", ... }`.
2. User realizes the mistake and calls `request_refund(deposit_msg, "user_btc_addr", tx_bytes, vout, proof, None)`. The `RefundRequest` is stored with `created_at_sec = T` and `refund_timelock_sec = 86400` (24 h).
3. At `T + 1 hour`, `PauseManager` calls `pa_pause_feature("ALL")`. Both `execute_refund` and `verify_deposit_v2` are now blocked for non-DAO callers.
4. 24 hours pass. The refund timelock expires at `T + 86400`, but the user cannot call `execute_refund` — it panics with the `Pausable` guard.
5. `UnpauseManager` calls `pa_unpause_feature("ALL")`. Both functions are now callable.
6. In the same NEAR block (or the next), the relayer bot calls `verify_deposit_v2(deposit_msg, tx_bytes, vout, proof)`. The deposit is finalized; `verified_deposit_utxo` now contains the UTXO key.
7. User calls `execute_refund(utxo_storage_key, None)`. The call reaches `load_refund_request_for_execute`, which checks:
   ```rust
   require!(
       !self.data().verified_deposit_utxo.contains(utxo_storage_key)
           || refund_request.executed,
       "UTXO already verified via deposit, cannot refund"
   );
   ``` [5](#0-4) 
   The call panics. The user's BTC has been minted as nBTC to `wrong.near`, which the user does not control. The refund path is permanently closed.

    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
