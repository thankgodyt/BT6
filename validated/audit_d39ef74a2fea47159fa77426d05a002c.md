Audit Report

## Title
Vault-Omission Bypass Enables Unauthorized `mint_to` on Native Solana Tokens — (`solana/programs/bridge_token_factory/src/instructions/user/finalize_transfer.rs`)

## Summary
`finalize_transfer` uses `vault: Option<...>` to distinguish native tokens (release from vault) from bridged tokens (mint). Anchor does not enforce that an optional PDA must be provided when it exists on-chain. An attacker who deploys a token, registers it as native via `log_metadata` (creating the vault PDA), then transfers `mint_authority` to the bridge authority PDA via SPL Token's `set_authority`, can subsequently call `finalize_transfer` with `vault=None`. The program enters the `mint_to` branch, the `mint_authority` check passes, and tokens are minted without releasing any from the vault — inflating supply beyond locked collateral.

## Finding Description

**Root cause:** The `vault` field in `FinalizeTransfer` is declared as `Option<Box<InterfaceAccount<'info, TokenAccount>>>` with PDA seeds `[VAULT_SEED, mint.key().as_ref()]`. When the caller omits this account, Anchor sets `self.vault = None` without verifying whether the vault PDA is initialized on-chain. No constraint enforces that `vault=None` implies the vault PDA does not exist.

**Exploit flow:**

**Step 1 — Registration:** `log_metadata` enforces `!mint.mint_authority.contains(authority.key)` at line 42. An attacker-controlled token (attacker is `mint_authority`) passes this check. The vault PDA `[VAULT_SEED, mint]` is created via `init_if_needed` at lines 50–62.

**Step 2 — Authority transfer:** The attacker calls SPL Token's `set_authority` (external to the bridge) to transfer `mint_authority` to the bridge authority PDA. The bridge has no mechanism to detect or prevent this.

**Step 3 — Legitimate lock:** The attacker calls `init_transfer` providing the vault account. The vault path at lines 88–102 executes `transfer_checked` into the vault. The NEAR bridge receives the lock event and the attacker initiates a transfer back, causing the NEAR MPC to sign a valid `FinalizeTransferPayload`.

**Step 4 — Exploit:** The attacker submits `finalize_transfer` omitting the vault account. `self.vault` is `None`. The `else` branch at lines 117–135 executes: `self.mint.mint_authority.contains(self.authority.key)` passes (because `mint_authority` was transferred to the bridge authority PDA in Step 2), and `mint_to` executes, minting tokens to the recipient's ATA. The vault still holds the originally locked tokens — supply is inflated.

**Why existing checks fail:** The `mint_authority` check at line 119–122 was designed to gate bridged tokens (tokens the bridge deployed and controls). It cannot distinguish between a legitimately bridged token and a native token whose `mint_authority` was post-hoc transferred to the bridge authority. The vault's PDA constraints (lines 60–70) only apply when the account is provided; they are entirely skipped when `vault=None`.

## Impact Explanation
This is unauthorized minting of a native token, directly matching the critical impact class: *"Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds."* The vault retains the locked collateral while the attacker receives freshly minted tokens, breaking the core bridge invariant that native tokens are only ever released from the vault. The attacker can repeat this for any amount they can lock and for which they can obtain a valid NEAR MPC signature, bounded only by their own token supply (which they control as the original issuer).

## Likelihood Explanation
All preconditions are achievable by a single unprivileged actor:
1. Deploy an SPL token — trivial.
2. Call `log_metadata` — permissionless.
3. Call SPL Token `set_authority` — permissionless for the current authority.
4. Execute a round-trip bridge transfer to obtain a valid NEAR MPC signature — achievable through normal bridge usage.
5. Call `finalize_transfer` with `vault=None` — permissionless (any relayer can submit).

No admin compromise, key leak, or MPC collusion is required.

## Recommendation
In `finalize_transfer`, add an explicit on-chain check: when `vault=None`, verify that the vault PDA for the given mint is uninitialized (zero lamports or not owned by the token program). Concretely, after account deserialization, derive the vault PDA and assert its account has zero lamports if `self.vault.is_none()`:

```rust
if self.vault.is_none() {
    let (vault_pda, _) = Pubkey::find_program_address(
        &[VAULT_SEED, self.mint.key().as_ref()],
        ctx.program_id,
    );
    let vault_info = ctx.accounts./* remaining_accounts or passed explicitly */;
    require!(
        vault_info.lamports() == 0,
        ErrorCode::VaultExistsButNotProvided
    );
}
```

Alternatively, change `vault` from `Option` to a required account and use a separate instruction for bridged-token finalization, eliminating the ambiguity entirely.
