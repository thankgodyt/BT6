### Title
Unauthenticated Caller in `sign_btc_transaction` Allows Attacker to Corrupt MPC Signing with Wrong `key_version` — (File: `contracts/satoshi-bridge/src/api/chain_signatures.rs`)

---

### Summary

`sign_btc_transaction` does not verify that the caller (`env::predecessor_account_id()`) is the owner of the referenced pending transaction (`btc_pending_info.account_id`). Any unprivileged NEAR account can invoke it for any pending signing task and supply an arbitrary `key_version`. This allows an attacker to front-run the legitimate user, cause the MPC to produce a signature under the wrong key, permanently fill the signature slot, and leave the transaction in an unrecoverable corrupted state — permanently locking the user's funds.

---

### Finding Description

`sign_btc_transaction` is a public, payable function with no caller-identity check: [1](#0-0) 

The function accepts a `btc_pending_sign_id` and a caller-supplied `key_version`, looks up the pending info, and immediately delegates to `internal_sign_btc_transaction`: [2](#0-1) 

`internal_sign_btc_transaction` passes the attacker-controlled `key_version` directly to the MPC `sign` call. The `path` is derived from the UTXO (deterministic), but `key_version` selects which MPC root key is used for signing: [3](#0-2) 

In the callback, the returned signature is stored unconditionally (after a one-time "Already signed" guard), and the PSBT is updated with the signature paired against the public key derived from the bridge's configured key (version 0): [4](#0-3) 

If the attacker supplied `key_version: 1` (or any version ≠ 0), the MPC signs with a different root key. The stored signature is cryptographically invalid for the public key embedded in the PSBT. The "Already signed" guard then permanently blocks any re-signing attempt: [5](#0-4) 

The `BTCPendingInfo` struct records the owner in `account_id` but this field is never compared to `env::predecessor_account_id()` inside `sign_btc_transaction`: [6](#0-5) 

---

### Impact Explanation

**Critical — Permanent locking of user or protocol funds.**

- **Withdrawal path:** The user transfers nBTC to the bridge via `ft_on_transfer`, which creates a `BTCPendingInfo` in `PendingSign` state. An attacker front-runs `sign_btc_transaction` with a wrong `key_version`. The corrupted signature fills the slot. The resulting Bitcoin transaction (assembled in `extract_tx_bytes_with_sign`) is cryptographically invalid and will never confirm on-chain. `verify_withdraw` never succeeds, so the nBTC held by the bridge is never burned and never returned — permanently locked.
- **Refund path:** After `execute_refund` builds the refund PSBT, an attacker can similarly corrupt the signing. The BTC UTXO remains locked in the bridge's MPC-controlled address with no recovery path.

There is no mechanism to cancel a `PendingSign` transaction and recover the locked tokens once a signature slot is filled.

---

### Likelihood Explanation

NEAR is a public blockchain. All pending signing IDs are observable via `get_btc_pending_infos_paged` (a public view call). An attacker only needs to monitor for new `BTCPendingInfo` entries and submit `sign_btc_transaction` with a wrong `key_version` before the legitimate user. The attacker must attach a small NEAR deposit (for the MPC signing fee), which is the only cost. No special privilege is required.

---

### Recommendation

Add a caller-identity check at the top of `sign_btc_transaction`:

```rust
let caller = env::predecessor_account_id();
let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
require!(
    caller == btc_pending_info.account_id,
    "Only the transaction owner can trigger signing"
);
```

Additionally, validate that `key_version` matches the version recorded at PSBT creation time (or enforce a fixed version from contract config), so even an authorized caller cannot supply an arbitrary key version.

---

### Proof of Concept

1. Alice calls `ft_transfer_call` on the nBTC contract, triggering `ft_on_transfer` on the bridge. A `BTCPendingInfo` is created with `account_id = alice.near` and state `PendingSign`.
2. Attacker calls `get_btc_pending_infos_paged()` (public view), observes Alice's `btc_pending_sign_id`.
3. Attacker calls `sign_btc_transaction(btc_pending_sign_id: "<alice's id>", sign_index: 0, key_version: 999)` with a 1-yoctoNEAR deposit.
4. The bridge calls MPC `sign` with `key_version: 999`. MPC returns a signature under a different root key.
5. `sign_btc_transaction_callback` stores the invalid signature at `signatures[0]`. The "Already signed" guard is now set.
6. Alice calls `sign_btc_transaction(..., sign_index: 0, key_version: 0)` — the call panics with `"Already signed"`.
7. The assembled Bitcoin transaction contains an invalid signature and is rejected by the Bitcoin network. Alice's nBTC is permanently locked in the bridge contract with no recovery path.

    pub fn sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> PromiseOrValue<bool> {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        btc_pending_info.assert_pending_sign();
        if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {
            if !self.check_btc_pending_info_exists(original_tx_id) {
                require!(
                    self.internal_unwrap_mut_account(&btc_pending_info.account_id.clone())
                        .btc_pending_sign_ids
                        .remove(&btc_pending_sign_id),
                    "Internal error"
                );
                self.internal_remove_btc_pending_info(&btc_pending_sign_id);
                return PromiseOrValue::Value(true);
            }
        }
        self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
            .into()
    }

    pub fn internal_sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> Promise {
        let pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);

        let public_keys: Vec<_> = pending_info
            .vutxos
            .iter()
            .map(|vutxo| self.generate_btc_public_key(&vutxo.get_path()))
            .collect();

        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        require!(
            btc_pending_info.signatures[sign_index].is_none(),
            "Already signed"
        );
        let payload = btc_pending_info
            .get_psbt()
            .get_hash_to_sign(sign_index, &public_keys);
        let path = btc_pending_info.vutxos[sign_index].get_path();
        self.sign_promise(SignRequest {
            payload,
            path,
            key_version,
        })
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_SIGN_BTC_TRANSACTION_CALL_BACK)
                .sign_btc_transaction_callback(
                    btc_pending_info.account_id.clone(),
                    btc_pending_sign_id,
                    sign_index,
                ),
        )
    }
