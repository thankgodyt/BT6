### Title
Unprivileged Caller Can Inject Wrong `key_version` via Race on `sign_btc_transaction`, Permanently Locking Bridge UTXOs — (`contracts/satoshi-bridge/src/api/chain_signatures.rs` / `src/chain_signature.rs`)

---

### Summary

`sign_btc_transaction` has no caller ACL check and no "signing-in-progress" lock. Any NEAR account can call it with an arbitrary `key_version`. Two concurrent calls for the same `(btc_pending_sign_id, sign_index)` both pass the synchronous `is_none()` guard, both dispatch a `sign_promise` to the MPC contract, and whichever callback lands first wins. If the winning callback used a wrong `key_version`, an invalid signature is permanently stored in the PSBT, the state machine advances to `PendingVerify`, and the UTXO is irrecoverably locked.

---

### Finding Description

**Step 1 – No caller restriction on `sign_btc_transaction`.**

`sign_btc_transaction` carries only `#[payable]` and `#[pause]`; there is no `#[trusted_relayer]`, no `#[access_control_any]`, and no check that `env::predecessor_account_id() == btc_pending_info.account_id`. [1](#0-0) 

Any NEAR account may call it with any `btc_pending_sign_id`, `sign_index`, and `key_version`.

**Step 2 – No "in-progress" lock before the async call.**

`internal_sign_btc_transaction` reads `signatures[sign_index].is_none()` synchronously, then immediately fires `sign_promise` without writing anything back to storage to mark the slot as pending. [2](#0-1) 

Because NEAR's async model allows multiple transactions in the same block to read the same unmodified state, two callers both observe `is_none() == true` and both dispatch a `sign` call to the MPC contract.

**Step 3 – `key_version` is forwarded verbatim to the MPC contract.**

The `SignRequest` struct carries `key_version` and it is passed directly to `ext_chain_signatures::sign`. [3](#0-2) [4](#0-3) 

A wrong `key_version` causes the MPC contract to sign with a different root key, producing a signature that does not satisfy the UTXO's spending script.

**Step 4 – First callback wins; second callback panics harmlessly.**

`sign_btc_transaction_callback` re-checks `is_none()` before writing. The first callback stores the (potentially invalid) signature; the second panics with "Already signed" and reverts cleanly, leaving the first signature intact. [5](#0-4) 

**Step 5 – No path back to `PendingSign`.**

Once all inputs are signed, `to_pending_verify_stage()` is called and the state machine advances irreversibly. There is no `PendingVerify → PendingSign` transition anywhere in the codebase. [6](#0-5) [7](#0-6) 

The PSBT is serialized with the invalid signature and stored; the UTXO can never be spent.

---

### Impact Explanation

The bridge-controlled UTXO is permanently locked. The user's nBTC has already been burned (or the withdrawal is in flight), and the corresponding BTC cannot be recovered because the only signed transaction is invalid and the state machine has no rollback. This is a direct, permanent loss of user funds.

---

### Likelihood Explanation

- `btc_pending_sign_id` and `sign_index` are observable on-chain from emitted events and storage.
- The attacker needs only to submit a `sign_btc_transaction` call with a wrong `key_version` (e.g., `key_version = 1` instead of `0`) in the same block as the legitimate signing call, or slightly before it.
- No privileged access, leaked key, or social engineering is required.
- The attack is cheap: the attacker pays only NEAR gas and the attached deposit forwarded to the MPC contract.

---

### Recommendation

1. **Restrict the caller.** Add a check that `env::predecessor_account_id()` is either the owner of the pending info or a trusted relayer/operator role.
2. **Lock the slot before the async call.** Write a sentinel value (e.g., a placeholder `SignatureResponse` or a separate `signing_in_progress: Vec<bool>`) to `signatures[sign_index]` *before* dispatching `sign_promise`, and clear it in the callback on failure. This prevents any second concurrent call from passing the `is_none()` guard.
3. **Validate `key_version`.** Enforce that `key_version` matches the contract's configured value before dispatching the MPC call.

---

### Proof of Concept

```
Block N:
  Tx A (attacker):    sign_btc_transaction(id, 0, key_version=99)
  Tx B (legitimate):  sign_btc_transaction(id, 0, key_version=0)

  Both read signatures[0].is_none() == true  →  both dispatch sign_promise

Block N+k (callbacks):
  Callback A arrives first:
    signatures[0].is_none() == true  →  stores sig_wrong (from key_version=99)
    psbt updated with invalid signature
    is_all_signed() == true  →  to_pending_verify_stage()

  Callback B arrives second:
    signatures[0].is_none() == false  →  panic "Already signed"

Result: BTCPendingInfo is in PendingVerify with an invalid PSBT.
        The Bitcoin transaction will never confirm.
        The UTXO is permanently locked.
```
