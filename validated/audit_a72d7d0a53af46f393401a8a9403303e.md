### Title
Peras Certificate and Vote Signature Verification Bypass — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance used for all production blocks unconditionally accepts any inbound Peras certificate (`validatePerasCert`) and accepts any Peras vote without verifying its BLS signature (`validatePerasVote`). An unprivileged peer can send a crafted certificate or vote with a forged, replayed, or otherwise invalid BLS signature and have it accepted, counted toward quorum, and used to boost an attacker-chosen block in chain selection.

---

### Finding Description

The `BlockSupportsPeras` type class defines two validation functions that are supposed to perform cryptographic checks on inbound Peras objects:

- `validatePerasCert` — must verify the aggregate BLS signature on a certificate before it is stored and used to boost a block.
- `validatePerasVote` — must verify the individual BLS vote signature before the vote is counted toward quorum.

The repository ships a single **degenerate default instance** for all `StandardHash blk` blocks (explicitly noted as "TODO: degenerate instance for all blks to get things to compile"):

`validatePerasCert` returns `Right` unconditionally — **no BLS aggregate signature check is performed**. `validatePerasVote` only checks that the voter ID appears in the stake distribution — **the BLS vote signature is never verified**.

These functions are called on the live inbound path. `processVotes` in the Peras vote diffusion layer calls `validatePerasVote` on every vote received from a peer:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [3](#0-2)

The `PerasVoteId` used for deduplication is `(voterId, roundNo)`: [5](#0-4) 

This means the deduplication check only prevents the exact same `(voterId, roundNo)` pair from being inserted twice. It does **not** prevent a different voter's identity from being impersonated, nor does it prevent a vote with a replayed or fabricated BLS signature from being accepted as a fresh vote for a different voter.

---

### Impact Explanation

**Certificate bypass (Critical):** `validatePerasCert` returns `Right` for any certificate regardless of its aggregate BLS signature. An attacker can craft a `PerasCert` for any `(roundNo, boostedBlock)` pair and have it accepted by the node. Once accepted, the certificate is stored in the `PerasCertDB` and used to boost the attacker's chosen block in chain selection, causing honest nodes to prefer a non-canonical chain. This is a bypass of Peras certificate verification enabling unauthorized certificate acceptance.

**Vote forgery (Critical):** `validatePerasVote` does not verify the BLS vote signature. An attacker who knows any voter ID present in the stake distribution can submit votes on behalf of that voter for any round and any block. Because the deduplication key is `(voterId, roundNo)`, the attacker can submit one forged vote per voter per round. With enough forged votes, the attacker can artificially reach quorum for an attacker-chosen block, causing a certificate to be forged and the attacker's block to be boosted in chain selection.

Both paths lead to **chain selection manipulation**: honest nodes are made to prefer a non-canonical or attacker-chosen chain, violating the Peras safety guarantee that only honestly-certified blocks receive a boost.

---

### Likelihood Explanation

The Peras vote and certificate diffusion mini-protocols are wired into the production node codebase (`ObjectPool/PerasVote.hs`, `ChainDB.API`). Any peer connected to a node running this code can send crafted votes or certificates. No key material, stake, or privileged access is required — only knowledge of a valid voter ID from the public stake distribution (which is publicly observable on-chain). The attack is therefore reachable by any unprivileged network peer once the Peras diffusion layer is active.

---

### Recommendation

1. **Implement `validatePerasCert`** to verify the aggregate BLS signature over `(roundNo, boostedBlock)` using the aggregate verification key derived from the declared voters' public keys, as specified in the WFALS committee scheme (`verifyCert` in `WFALS.hs`). [6](#0-5) 

2. **Implement `validatePerasVote`** to verify the individual BLS vote signature using `verifyVoteSignature` against the voter's public key from the stake distribution, as already implemented in `implVerifyVote` in `WFALS.hs`. [7](#0-6) 

3. **Track used `(voterId, roundNo)` pairs** across rounds to prevent a replayed vote signature from a previous round being submitted with a different `roundNo` field but the same underlying BLS bytes (analogous to the nonce-tracking recommendation in the original report).

4. Resolve GitHub issue `tweag/cardano-peras#120` before enabling the Peras diffusion layer on any network where adversarial peers are possible.

---

### Proof of Concept

An attacker peer executes the following steps:

1. Observe the public stake distribution to obtain any valid `PerasVoterId` (e.g., voter `V` with non-zero stake).
2. Craft a `PerasVote` with:
   - `pvVoteRound = <target round>`
   - `pvVoteBlock = <attacker-chosen block point>`
   - `pvVoteVoterId = V`
   - `pvSignature = <any bytes, e.g., a BLS signature from a completely different round>`
3. Send the crafted vote to the victim node via the Peras vote diffusion mini-protocol.
4. `processVotes` calls `validatePerasVote`, which checks only that `V` is in the stake distribution — the BLS signature is never verified. The vote is accepted.
5. Repeat for enough voter IDs to exceed the quorum threshold.
6. `updatePerasRoundVoteStates` reaches quorum and calls `forgePerasCert`, producing a `ValidatedPerasCert` for the attacker's chosen block.
7. Chain selection boosts the attacker's block, causing the victim node to prefer the attacker's chain.

Alternatively, for the certificate path:

1. Craft a `PerasCert` with `pcRoundNo = <any round>`, `pcBoostedBlock = <attacker-chosen block>`, `pcSignature = <any bytes>`.
2. Submit it via `addPerasCertSync`.
3. `validatePerasCert` returns `Right` unconditionally. [8](#0-7) 
4. The certificate is stored and used to boost the attacker's block in chain selection, with no valid aggregate BLS signature ever having been checked.

            electionId

              VRFVerifyContext voterVRFVerificationKey vrfOutput
