Audit Report

## Title
Unchecked `.detach()` on Relayer Repayment in Fast-Transfer Finalization Causes Permanent Fund Loss and Escrow Mis-accounting — (File: `near/omni-bridge/src/lib.rs`)

## Summary

In `process_fin_transfer_to_other_chain` and `utxo_fin_transfer_fast`, the bridge repays a fast-transfer relayer via `send_tokens(...).detach()` — a fire-and-forget cross-contract call with no callback or error-recovery path. All state mutations (`locked_tokens` decrement, fast-transfer and inbound-transfer finalization) are committed before the call and are never reverted on failure. A failed token transfer permanently destroys the relayer's pre-paid funds and leaves `locked_tokens` permanently under-counted, freezing the surplus tokens inside the bridge with no administrative recovery path.

## Finding Description

**`process_fin_transfer_to_other_chain` (lines 1980–2054)**

The function commits five irreversible state mutations and then fires a detached cross-contract call:

1. `add_fin_transfer` (line 1985) — inserts the inbound transfer ID into `finalised_transfers`; a duplicate insert panics, so this can never be retried.
2. `unlock_tokens_if_needed` (lines 1997–2001) — decrements `locked_tokens[(origin_chain, token)]` by `amount`.
3. `lock_tokens_if_needed` (lines 2002–2005) — increments `locked_tokens[(dest_chain, token)]` by the fee.
4. `send_tokens(...).detach()` (lines 2029–2039) — schedules `ft_transfer` or `mint` to the relayer with no callback.
5. `mark_fast_transfer_as_finalised` (line 2040) — sets `finalised = true` on the fast-transfer entry.

If the `ft_transfer` call panics (e.g., relayer has no storage registration for the token, or the token contract is paused), NEAR silently discards the failure because `.detach()` drops the promise result. All five mutations above remain committed with no rollback.

**`utxo_fin_transfer_fast` (lines 2518–2548)**

The identical pattern appears in the UTXO fast-transfer path. For a non-NEAR destination, `mark_fast_transfer_as_finalised` (line 2533) is called before `send_tokens(...).detach()` (lines 2542–2548). For a NEAR destination, `remove_fast_transfer` (line 2530) is called before the detached send. The developer `// TODO: check how to deal with failed send_tokens` comment at line 2484 explicitly acknowledges the unresolved failure case.

**Contrast with the correctly handled path**

`process_fin_transfer_to_near` (lines 1957–1977) chains a `.then(fin_transfer_send_tokens_callback(...))` that, on failure, calls `burn_tokens_if_needed`, `revert_lock_actions`, and `remove_fin_transfer` (lines 1702–1718), fully restoring pre-call state. The other-chain and UTXO fast-transfer paths have no equivalent recovery.

**Why `send_tokens` can fail**

For non-deployed (native) tokens with an empty `msg`, `send_tokens` dispatches `ft_transfer` (line 2106). `ft_transfer` panics if the recipient account has no storage registration for that token. For deployed tokens, `mint` is used (line 2097); a paused or broken token contract produces the same silent failure.

## Impact Explanation

**Permanent loss of relayer funds.** The relayer pre-paid `amount_without_fee` tokens to the user on the destination chain. When the original transfer is finalized, the bridge is supposed to repay the relayer from locked escrow. If `send_tokens` fails silently, the relayer never receives repayment. The tokens remain physically inside the bridge contract but are now unaccounted for.

**Permanent escrow mis-accounting / token freeze.** `locked_tokens[(origin_chain, token)]` is decremented by `amount` (line 1997–2001) without a corresponding actual outflow. The counter is permanently under-counted. Any future `unlock_tokens` call that tries to unlock the full legitimate amount will hit the `InsufficientLockedTokens` guard (lines 81–84 of `token_lock.rs`) and revert, permanently freezing the surplus tokens inside the bridge with no administrative recovery path.

This matches the allowed critical impact classes: permanent freezing of bridged funds and escrow mis-accounting that changes protocol balances.

## Likelihood Explanation

Missing storage registration for `ft_transfer` is a standard, well-known NEAR failure mode. A relayer whose account has not explicitly called `storage_deposit` on the specific bridged token contract will trigger it. The `// TODO` comment at line 2484 confirms the team is aware the scenario is reachable. The fast-transfer feature is a live, publicly accessible code path reachable by any trusted relayer through the relayer flow. The failure is repeatable: every fast transfer whose finalization triggers a failing `send_tokens` call permanently corrupts the accounting.

## Recommendation

Mirror the pattern used in `process_fin_transfer_to_near`: replace `.detach()` with `.then(callback)` in both `process_fin_transfer_to_other_chain` and `utxo_fin_transfer_fast`. The callback should, on failure, re-increment `locked_tokens`, un-mark (or re-insert) the fast transfer as not finalized, and remove the inbound transfer from `finalised_transfers`. Alternatively, defer all state mutations to the success branch of the callback, keeping pre-call state intact until the cross-contract call result is confirmed.

## Proof of Concept

1. Trusted relayer `R` calls `ft_transfer_call` on a non-deployed (native) token with a `FastFinTransferMsg` targeting a non-NEAR destination. `R` has not called `storage_deposit` on the token contract for its own account (or has since unregistered).
2. `fast_fin_transfer_to_other_chain` runs: `add_fast_transfer`, `burn_tokens_if_needed`, `lock_tokens_if_needed`, `add_transfer_message` all commit to state.
3. A separate relayer submits the proof via `fin_transfer` → `fin_transfer_callback` → `process_fin_transfer_to_other_chain`.
4. `add_fin_transfer` inserts the transfer ID into `finalised_transfers`. `unlock_tokens_if_needed` decrements `locked_tokens[(origin_chain, token)]` by `amount`. `mark_fast_transfer_as_finalised` sets `finalised = true`. `send_tokens(token, R, amount_without_fee, "").detach()` fires `ft_transfer` to `R`.
5. `ft_transfer` panics: `R` has no storage registration. The panic is silently swallowed because `.detach()` discards the result.
6. `R` never receives tokens. `locked_tokens` is permanently under-counted by `amount_without_fee`. The fast transfer entry is permanently `finalised = true`. The inbound transfer is permanently in `finalised_transfers`. Future `unlock_tokens` calls for the full legitimate amount revert with `InsufficientLockedTokens`. No recovery is possible.
