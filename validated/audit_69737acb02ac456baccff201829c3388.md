Audit Report

## Title
Detached `send_tokens` Promise in Fast-Transfer Relayer Repayment Paths Causes Permanent Fund Freezing - (File: `near/omni-bridge/src/lib.rs`)

## Summary
In `process_fin_transfer_to_other_chain` and `utxo_fin_transfer_fast`, the promise returned by `send_tokens()` is immediately `.detach()`-ed, discarding its result. Bridge state — including `mark_fast_transfer_as_finalised` and `locked_tokens` accounting adjustments — is committed unconditionally before the detached promise resolves. If the underlying `ft_transfer` or `mint` call fails for any reason, the relayer's pre-funded tokens are permanently frozen inside the bridge with no re-entry or retry path. A developer `TODO` comment at line 2484 explicitly acknowledges this unresolved gap.

## Finding Description

**Path 1 — `process_fin_transfer_to_other_chain` (lines 2029–2040):**

```rust
self.send_tokens(token, relayer, U128(...), "")
    .detach();                                        // result discarded
self.mark_fast_transfer_as_finalised(&fast_transfer.id()); // state committed unconditionally
```

`unlock_tokens_if_needed` and `lock_tokens_if_needed` have already adjusted `locked_tokens` accounting (lines 1997–2006) before this point. If the detached `ft_transfer` or `mint` fails, the fast-transfer entry is permanently closed (`finalised = true`), the accounting is permanently inconsistent, and the relayer has no recourse.

**Path 2 — `utxo_fin_transfer_fast` (lines 2529–2548):**

```rust
// destination != Near branch:
self.mark_fast_transfer_as_finalised(&fast_transfer.id()); // line 2533
// ...
self.send_tokens(fast_transfer.token_id.clone(), fast_transfer_status.relayer, amount, "")
    .detach();   // result discarded
```

The developer `TODO` at line 2484 (`// TODO: check how to deal with failed send_tokens`) confirms this is a known unresolved gap. State is committed before the promise fires.

**Contrast with the correctly handled path — `process_fin_transfer_to_near` (lines 1957–1977):**

```rust
self.send_tokens(token.clone(), recipient, U128(...), &msg)
    .then(Self::ext(...).fin_transfer_send_tokens_callback(...))
```

This path chains a callback that checks the promise result and reverts state on failure. The fast-transfer repayment paths have no equivalent callback.

**`send_tokens` gas budget (lines 2063–2067):**

```rust
let ft_transfer_call_gas = env::prepaid_gas()
    .saturating_sub(env::used_gas())
    .saturating_sub(SEND_TOKENS_CALLBACK_GAS) // TODO: not all send_tokens callbacks has the same gas.
    .saturating_sub(MINT_TOKEN_GAS)
    .min(FT_TRANSFER_CALL_GAS);
```

The gas budget is computed dynamically and the inline `TODO` signals developer uncertainty about correctness, creating an additional failure vector.

## Impact Explanation

This matches the critical allowed impact: **permanent freezing of bridged funds**. For native tokens, if `ft_transfer` to the relayer fails (e.g., relayer account lacks NEP-141 storage registration on the token contract), the tokens remain locked inside the bridge contract forever — `mark_fast_transfer_as_finalised` has already been called, so any retry attempt is rejected with `ERR_FAST_TRANSFER_ALREADY_FINALISED`. For deployed (bridged) tokens, if `mint()` fails, the relayer's pre-funded amount is simply never created. In both cases the bridge's `locked_tokens` accounting has been permanently adjusted without a corresponding token movement, leaving the protocol in an inconsistent state with no recovery path.

## Likelihood Explanation

The `send_tokens` call can fail under realistic, non-exotic conditions:
- **Storage registration gap**: NEP-141 `ft_transfer` requires the recipient to have storage registered on the token contract. A relayer who has never interacted with a specific token contract will lack this registration. This is a normal operational condition, not a victim mistake.
- **Token contract paused/upgraded**: A malicious or buggy token deployer can pause the token contract between fast-transfer execution and canonical finalization, causing `ft_transfer` or `mint` to revert.
- **Gas exhaustion**: The dynamic gas budget computation (with its own `TODO`) may leave insufficient gas for the detached promise, causing silent failure.

None of these conditions require privileged access. The `fin_transfer` function is publicly callable by anyone with a valid cross-chain proof, and the relayer flow is an explicitly supported bridge participant path.

## Recommendation

Replace `.detach()` in both `process_fin_transfer_to_other_chain` and `utxo_fin_transfer_fast` with a chained callback analogous to `fin_transfer_send_tokens_callback`:

1. **On success**: emit the finalization event and clean up state (current behavior).
2. **On failure**: revert `mark_fast_transfer_as_finalised` (set `finalised = false` or re-insert the entry) so the repayment can be retried, and emit a failure event.

This mirrors the pattern already correctly implemented in `process_fin_transfer_to_near` → `fin_transfer_send_tokens_callback`. The fee-payment `.detach()` calls in `fin_transfer_send_tokens_callback` (lines 1721–1733) should be similarly hardened.

## Proof of Concept

1. Relayer R executes a fast transfer for a cross-chain transfer T (ETH → SOL), pre-funding the user's tokens on NEAR.
2. R's account has no storage registered on the token contract (e.g., a newly deployed bridged token R has never interacted with).
3. Anyone submits the canonical `fin_transfer` proof for T, triggering `process_fin_transfer_to_other_chain`.
4. `unlock_tokens_if_needed` adjusts accounting; `send_tokens(token, R, amount, "").detach()` fires a detached `ft_transfer` promise.
5. `mark_fast_transfer_as_finalised` is called — the fast-transfer entry is permanently closed.
6. The detached `ft_transfer` promise fails silently (storage not registered). R receives nothing.
7. R attempts to claim repayment again — the bridge rejects with `ERR_FAST_TRANSFER_ALREADY_FINALISED`.
8. R's pre-funded tokens are permanently frozen in the bridge contract.

**Reproducible test**: Deploy a NEP-141 token contract; have a relayer account that has never called `storage_deposit` on it; execute a fast transfer; submit the canonical finalization proof; observe that the relayer receives no tokens and the fast-transfer entry is permanently finalized.
