### Title
`init_rbf_btc_pending_info` Initializes `signatures` Vec to Original Input Count, Causing Out-of-Bounds Panic When Cancel PSBT Has Different Input Count — (`contracts/satoshi-bridge/src/rbf/cancel_withdraw.rs`)

### Summary

`init_rbf_btc_pending_info` sizes the `signatures` vec to the **original** PSBT's input count. The cancel PSBT is accepted from the caller without any check that its input count matches the original's. If they differ, `sign_btc_transaction` panics on an out-of-bounds index, permanently breaking cancel-RBF signing for that transaction.

### Finding Description

In `contracts/satoshi-bridge/src/rbf/mod.rs`, `init_rbf_btc_pending_info` constructs the new `BTCPendingInfo` for the cancel RBF:

```rust
signatures: vec![None; original_tx_btc_pending_info.signatures.len()],
vutxos:     original_tx_btc_pending_info.vutxos.clone(),
``` [1](#0-0) 

Both `signatures` and `vutxos` are sized/populated from the **original** transaction, not from the cancel PSBT that is stored in `psbt_hex`.

The cancel PSBT is provided externally by the caller of `internal_cancel_withdraw` and is validated only by `check_cancel_withdraw_rbf_psbt_valid`, which calls `check_psbt_output_all_change_address` — a check on **outputs**, not on input count: [2](#0-1) 

No guard enforces that `cancel_withdraw_rbf_psbt.get_input_num() == original_tx_btc_pending_info.signatures.len()`.

When `sign_btc_transaction` is later called, `internal_sign_btc_transaction` indexes into both `signatures` and the cancel PSBT's inputs using the caller-supplied `sign_index`:

```rust
require!(btc_pending_info.signatures[sign_index].is_none(), "Already signed");
let payload = btc_pending_info.get_psbt().get_hash_to_sign(sign_index, &public_keys);
let path = btc_pending_info.vutxos[sign_index].get_path();
``` [3](#0-2) 

Two panic paths exist:
- **Cancel PSBT has more inputs than original**: `signatures[sign_index]` panics for `sign_index >= original_count`.
- **Cancel PSBT has fewer inputs than original**: `get_hash_to_sign(sign_index, ...)` panics inside `self.psbt.inputs[vin]` for `sign_index >= cancel_count`. [4](#0-3) 

### Impact Explanation

Once the cancel PSBT is stored with a mismatched input count, every subsequent call to `sign_btc_transaction` for that cancel RBF ID will panic. The cancel RBF entry is permanently stuck in `PendingSign` state with no recovery path. The original withdrawal is already marked canceled (`do_cancel` was called), so the user's funds are locked in a state where neither the original nor the cancel transaction can be finalized.

This matches the allowed Low impact: *"Publicly reachable invariant-violation, stuck-state, or panic-driven fault in production bridge/token paths without direct theft."*

### Likelihood Explanation

`internal_cancel_withdraw` is reachable from the public `cancel_withdraw` API in `contracts/satoshi-bridge/src/api/bridge.rs`. The only privileged check is for the excess-gas-fee branch; the cancel PSBT itself is accepted from any caller after the timeout. A malicious or buggy relayer can submit a cancel PSBT with a different input count (e.g., adding a fee-bumping UTXO), triggering the stuck state. [5](#0-4) 

### Recommendation

After constructing `btc_pending_info` via `init_rbf_btc_pending_info`, add an explicit guard before storing:

```rust
require!(
    cancel_withdraw_rbf_psbt.get_input_num() == btc_pending_info.signatures.len(),
    "Cancel PSBT input count must match original"
);
```

Alternatively, re-derive `signatures` from the cancel PSBT's actual input count rather than copying the original's length.

### Proof of Concept

1. Submit a withdrawal with a 1-input PSBT → `original.signatures.len() == 1`.
2. After timeout, call `cancel_withdraw` with a cancel PSBT that has 2 inputs.
3. `init_rbf_btc_pending_info` creates `signatures = [None]` (length 1).
4. Call `sign_btc_transaction(cancel_rbf_id, sign_index=1, ...)`.
5. `signatures[1]` → index out of bounds → panic. Cancel RBF permanently stuck. [6](#0-5)
