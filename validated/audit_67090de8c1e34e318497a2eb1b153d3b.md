Audit Report

## Title
Asymmetric Transfer Hook Enforcement Enables Permanent Vault Fund Lock — (File: `solana/programs/bridge_token_factory/src/instructions/user/finalize_transfer.rs`)

## Summary
Both `init_transfer` and `finalize_transfer` call `transfer_checked` without providing SPL Token-2022 transfer hook extra accounts. A malicious token creator can register a Token-2022 mint with `TransferHook` extension set to `hook_program_id = None` (causing `init_transfer` to succeed and accumulate vault funds), then activate a real hook program via `UpdateTransferHook`, permanently blocking `finalize_transfer` from releasing those funds. Users who bridge back from NEAR have their NEAR-side tokens burned irreversibly while their Solana-side tokens remain permanently locked in the vault with no recovery path.

## Finding Description
`init_transfer.rs` L90–102 calls `transfer_checked` with a bare `CpiContext::new` containing only the four standard accounts (`from`, `to`, `authority`, `mint`): [1](#0-0) 

`finalize_transfer.rs` L103–116 does the same with `CpiContext::new_with_signer`: [2](#0-1) 

Neither CPI resolves or appends transfer hook extra account metas. `log_metadata.rs` inspects only the `MetadataPointer` extension for name/symbol; it performs no check for the `TransferHook` extension and creates the vault PDA unconditionally: [3](#0-2) 

The only constraint on the mint in `LogMetadata` is that the bridge authority is not the mint authority — the attacker retains mint authority and can call `UpdateTransferHook` at any time: [4](#0-3) 

**Exploit asymmetry:** When `hook_program_id = None`, SPL Token-2022 skips hook invocation entirely, so `init_transfer` succeeds and tokens accumulate in the vault. After the attacker calls `UpdateTransferHook` to set a real hook program, every subsequent `finalize_transfer` CPI fails because the hook program is now active but no hook extra accounts are present in the context. Because Solana transactions are atomic, the nonce consumption at L91–99 also reverts on each failed attempt: [5](#0-4) 

The nonce is therefore never consumed, retries always fail, and there is no admin drain or alternative exit path for vault funds. The `SECURITY.md` acknowledges the missing hook support but misclassifies it as "denial, not fund loss": [6](#0-5) 

This classification is incorrect for the asymmetric attack path: `init_transfer` succeeds (hook inactive), funds accumulate, hook is activated, `finalize_transfer` permanently fails — producing irreversible fund loss, not mere denial.

## Impact Explanation
**Critical — Permanent freezing of bridged funds.** Users who lock native Token-2022 tokens via `init_transfer` and then bridge back from NEAR have their NEAR-side tokens burned (irreversible) while their Solana vault tokens are permanently locked with no recovery mechanism. This directly matches the allowed Critical impact: *permanent freezing of bridged funds across NEAR and Solana*. The vault can accumulate funds from multiple users before the hook is activated, amplifying total loss.

## Likelihood Explanation
**Medium.** The attack requires a deliberate malicious token creator but no privileged bridge role. `log_metadata` is permissionless — any caller can register any mint whose mint authority is not the bridge authority. `UpdateTransferHook` is a standard, documented SPL Token-2022 instruction callable by the mint authority at any time. The `SECURITY.md` itself confirms the vulnerable code path is present in production. The only prerequisite is that legitimate users bridge the malicious token before the hook is activated, which is achievable by briefly operating the token legitimately to build user trust.

## Recommendation
**Option A (preferred):** In `log_metadata`, deserialize the mint's Token-2022 extensions and reject registration if the `TransferHook` extension is present (regardless of whether `hook_program_id` is currently `None`), since the hook program can be set at any future time by the mint authority. This is the minimal, safe fix.

**Option B:** Add full transfer hook support to both `init_transfer` and `finalize_transfer` by resolving extra account metas from the mint's `TransferHook` extension and appending them to the `CpiContext` via `with_remaining_accounts`, following the pattern in `spl_transfer_hook_interface::onchain::add_extra_accounts_for_execute_cpi`.

## Proof of Concept
```
1. Attacker creates Token-2022 mint M with TransferHook extension, hook_program_id = None.
2. Attacker calls log_metadata(M) → vault PDA V created. No TransferHook check performed.
3. User A calls init_transfer(M, amount=1000):
   - transfer_checked(A → V) invoked; hook_program_id=None → SPL skips hook → succeeds.
   - Wormhole message emitted; NEAR bridge mints 1000 bridged-M to User A on NEAR.
4. Attacker calls UpdateTransferHook(M, hook_program_id = <malicious_program>).
5. User A calls ft_on_transfer on NEAR bridge to bridge back 1000 bridged-M.
   - NEAR bridge burns 1000 bridged-M (irreversible).
   - Transfer event emitted; relayer picks up finalize_transfer call.
6. Relayer calls finalize_transfer(M, amount=1000, recipient=A):
   - UsedNonces::use_nonce() runs (L91-99).
   - transfer_checked(V → A_token_account) invoked; hook now active; hook accounts
     missing from CpiContext → SPL Token-2022 returns error.
   - Entire transaction reverts atomically; nonce not consumed.
7. All retry attempts by relayer produce identical failure.
8. Result: 1000 tokens permanently locked in vault V; User A's NEAR tokens burned.
   No admin instruction exists to recover vault funds.
```
