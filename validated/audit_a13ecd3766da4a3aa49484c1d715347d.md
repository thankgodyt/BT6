### Title
`shelleyAfterVoting` Counts All Post-Deadline Blocks Instead of Only Those in the Stability Window, Allowing Premature Era Transition During Chain Growth Violation - (File: `ouroboros-consensus-cardano/src/shelley/Ouroboros/Consensus/Shelley/Ledger/Ledger.hs`)

---

### Summary

The `ShelleyTransitionInfo.shelleyAfterVoting` counter, used to gate hard-fork era transitions in all Shelley-based eras, counts every block whose slot falls at or after the voting deadline — across the entire remaining epoch — rather than counting only blocks that fall within the single stability window immediately following the deadline. The guard `shelleyAfterVoting >= k` in `shelleyTransition` therefore passes even when the critical stability window contains fewer than `k` blocks (a Chain Growth violation), causing the Hard Fork Combinator to commit to an era transition that the protocol's own safety argument requires to be suppressed.

---

### Finding Description

The Shelley ledger state carries a `ShelleyTransition` value:

```haskell
newtype ShelleyTransition = ShelleyTransitionInfo
  { shelleyAfterVoting :: Word32
  -- ^ The number of blocks in this epoch past the voting deadline
  ...
  -- 3. If we count how many blocks we have seen post deadline, and we have
  --    reached k of them, we know that that last pre-deadline block won't
  --    be rolled back anymore.
  }
``` [1](#0-0) 

The counter is incremented in `applyHelper` whenever a block's slot is at or after the voting deadline:

```haskell
shelleyAfterVoting =
    (if blockSlot blk >= votingDeadline then succ else id) $
      shelleyAfterVoting tickedShelleyLedgerTransition
``` [2](#0-1) 

The voting deadline is `startOfNextEpoch - 2*swindow`, so the counter accumulates blocks across the full `2*swindow`-slot window from the deadline to the epoch boundary:

```haskell
votingDeadline = subSlots (2 * swindow) startOfNextEpoch
``` [3](#0-2) 

The Hard Fork Combinator gate in `shelleyTransition` then fires as soon as this total reaches `k`:

```haskell
guard $ shelleyAfterVoting >= fromIntegral k
return newPParamsEpochNo
``` [4](#0-3) 

The **intended** behavior, documented explicitly as a known bug in the project's own `civic_time.md`, is to count only blocks in the **first** stability window after the deadline (slots `[votingDeadline, votingDeadline + swindow)`). The Chain Growth property guarantees that this window contains at least `k` blocks under normal conditions; if it does not, the transition must be suppressed. The current code counts blocks from the entire `2*swindow` window, so blocks that arrive in the **second** stability window (slots `[votingDeadline + swindow, epoch_end)`) are incorrectly included in the tally:

---

### Impact Explanation

When Chain Growth is violated — the first stability window after the voting deadline contains fewer than `k` blocks — the HFC is supposed to silently suppress the era transition and remain in the current era. Because `shelleyAfterVoting` accumulates blocks from the entire `2*swindow` post-deadline window, a node can reach `shelleyAfterVoting >= k` by counting blocks from the second stability window even though the first window was sparse. The node then reports the transition as stable and the HFC commits to the new era.

Nodes that correctly enforce the single-window check (or that happen to observe a different chain density) will stay in the current era. The result is a **cross-era consensus split**: some nodes transition while others do not, breaking the hard-fork invariant that all honest nodes must agree on the era boundary. This falls squarely under:

> *High. Hard-fork, era transition, ledger-view, query, or network-version mismatch that breaks cross-era consensus or ledger invariants for production Cardano nodes.*

---

### Likelihood Explanation

The bug is latent under normal network conditions (Chain Growth holds, so the first stability window always has ≥ k blocks and the distinction between the two windows is irrelevant). It becomes exploitable when Chain Growth is violated, which can occur:

1. **Passively**, during a severe network partition lasting on the order of hours.
2. **Actively**, by an adversary holding enough stake to be elected leader in a non-trivial fraction of slots in the stability window after the voting deadline. The adversary withholds their blocks during the first stability window (keeping the count below `k`), then releases them in the second window. The total `shelleyAfterVoting` reaches `k`, the transition fires, and nodes that did not observe the withheld blocks diverge on the era boundary.

No stake majority is required; the adversary only needs to suppress block production in a single `3k/f`-slot window, which is feasible with a minority stake position. The attack is therefore realistic for a motivated adversary targeting an era transition epoch.

---

### Recommendation

Replace the slot-based `blockSlot blk >= votingDeadline` predicate with a window-bounded check that increments `shelleyAfterVoting` only for blocks whose slot falls strictly within `[votingDeadline, votingDeadline + swindow)`. The guard in `shelleyTransition` should then require `shelleyAfterVoting >= k` over this narrower window, matching the Chain Growth guarantee that the protocol's safety argument actually relies on. This mirrors the fix applied in the referenced external report: replacing a raw block-depth count with a proper finality/stability check.

---

### Proof of Concept

**Setup:** Cardano Shelley-based era, security parameter `k = 2160`, active slot coefficient `f = 0.05`, stability window `swindow = 3k/f = 129600` slots. Voting deadline = `startOfNextEpoch - 2*129600`.

**Attack sequence:**

1. An adversary holds ~5% stake and is elected leader for ~6480 slots in the first stability window after the voting deadline (expected value under honest conditions).
2. The adversary withholds all their blocks during `[votingDeadline, votingDeadline + swindow)`, leaving only ~6000 honest blocks in that window — below `k = 2160`? No, wait: with 5% stake and 129600 slots, expected honest blocks ≈ 6480. The adversary needs to suppress enough that the window has < 2160 blocks. With 5% adversarial stake and 95% honest, honest blocks ≈ 6156 in the window — still above k. The adversary would need a larger stake share or a network partition to reduce the window below k.

**More realistic scenario (network partition):**

1. A network partition reduces block production in the first stability window to < k blocks.
2. After the partition heals, blocks accumulate in the second stability window `[votingDeadline + swindow, epoch_end)`.
3. `shelleyAfterVoting` reaches `k` using blocks from the second window.
4. `shelleyTransition` returns `Just newEpochNo` and the HFC commits to the era transition.
5. Nodes that were isolated during the partition and never saw the second-window blocks remain in the current era.
6. The two groups of nodes now disagree on the era boundary, producing a consensus split.

The root cause is the overly broad accumulation window in `applyHelper`: [6](#0-5) 

combined with the gate that does not distinguish which stability window the `k` blocks came from: [7](#0-6)
