### Title
Peras Vote Inbound Processing Lacks Round-Number Temporal Validation, Allowing Acceptance of Votes for Arbitrary Rounds - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasVote.hs`)

---

### Summary

The `processVotes` function, which handles all inbound Peras votes received from peers via the object-diffusion mini-protocol, validates votes only against the current stake distribution at execution time. It performs no check that a vote's `pvVoteRound` field corresponds to the current Peras round or falls within any acceptable temporal window. An unprivileged peer can therefore send votes for arbitrary past or future rounds; if enough such votes accumulate, a `ValidatedPerasCert` is forged for that round and injected into chain selection, bypassing the Peras voting rules entirely.

---

### Finding Description

The production inbound path for Peras votes is:

```
peer → object-diffusion mini-protocol
     → makePerasVotePoolWriterFromChainDB (PerasVote.hs:131)
     → processVotes (PerasVote.hs:178)
         ├─ validateVote  ← calls validatePerasVote (SupportsPeras.hs:363)
         └─ addVote       ← calls ChainDB.addPerasVoteWithAsyncCertHandling
```

`processVotes` performs validation atomically in STM and then timestamps and stores every vote that passes: [1](#0-0) 

The validation delegate is `validatePerasVote`, whose only production implementation is the degenerate stub that ships for all block types: [2](#0-1) 

This stub checks only that the voter appears in the current stake distribution. It does **not** check:

- Whether `pvVoteRound` equals the current Peras round.
- Whether `pvVoteRound` falls within any acceptable window relative to the current slot or wall-clock time.
- Whether the vote's target block (`pvVoteBlock`) is a plausible candidate for the claimed round.

The `PerasVote` data type carries the round number in `pvVoteRound`: [3](#0-2) 

Once a vote passes `validatePerasVote`, it is stored in `PerasVoteDB`. When enough votes for the same `(round, block)` target accumulate, `updatePerasRoundVoteStates` forges a `ValidatedPerasCert` for that round: [4](#0-3) 

The certificate is then forwarded to `ChainDB.addPerasVoteWithAsyncCertHandling`, which feeds it into chain selection. The Peras voting rules (VR-1A, VR-1B, VR-2A, VR-2B) that govern *when a local node should vote* are evaluated only for the node's own forging decision: [5](#0-4) 

These rules are never applied to *inbound* votes from peers. The temporal constraint in VR-1A (`lcsArrivalSlot cert :<=: lcsRoundStartSlot cert + _X`) is checked only for the local node's own voting decision, not for accepting peer-supplied votes.

The degenerate instance is explicitly acknowledged as incomplete: [6](#0-5)

### Impact Explanation

An adversarial peer can send a batch of `PerasVote` objects whose `pvVoteRound` is set to any past or future round. Each vote passes `validatePerasVote` as long as the voter's key appears in the current stake distribution. Once a quorum of such votes accumulates in `PerasVoteDB`, a `ValidatedPerasCert` is forged for that arbitrary round and injected into chain selection. Peras certificates carry a boost weight that influences which chain the node prefers. A certificate forged for a past round over an adversary-chosen block can cause the node to prefer a non-canonical chain, constituting a bypass of Peras certificate checks and a chain-selection manipulation. This falls under the allowed impact: *bypass of Peras voting or certificate checks that enables unauthorized certificate acceptance*, and *chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain*.

---

### Likelihood Explanation

The entry path requires only a network connection: any peer participating in the object-diffusion mini-protocol can send `PerasVote` messages. No key compromise, stake majority, or privileged access is needed. The adversary needs only to control enough voter keys to reach the quorum threshold for a target round — keys that are legitimately in the stake distribution. Because `validatePerasVote` does not check the round number at all, the attack is straightforward to execute once Peras is active.

---

### Recommendation

`processVotes` (or the `validatePerasVote` implementation) must validate that each incoming vote's `pvVoteRound` falls within an acceptable window relative to the current Peras round at the time of receipt. Concretely:

1. Determine the current Peras round from the wall clock and the hard-fork summary (analogous to how `perasRoundStart` is used in `Peras.Voting.View`).
2. Reject any vote whose `pvVoteRound` is not the current round (or at most one round behind, to tolerate minor clock skew).
3. Enforce this check inside `validatePerasVote` or as a pre-filter in `processVotes` before the STM validation block.

This mirrors the fix described in the external report: validate the temporal context of the request at execution time, not just the structural/stake validity.

---

### Proof of Concept

1. Connect to a node running with Peras enabled via the object-diffusion mini-protocol.
2. Construct a batch of `PerasVote` objects with `pvVoteRound = 0` (genesis round) and `pvVoteBlock` pointing to any block, signed by voter keys that appear in the current stake distribution.
3. Send the batch. `processVotes` calls `validatePerasVote` for each vote; each passes because the voter has stake.
4. Repeat with enough distinct voter keys to exceed the quorum threshold.
5. Observe that `PerasVoteDB` emits `AddedPerasVoteAndGeneratedNewCert` for round 0, and the resulting certificate is forwarded to chain selection, boosting the chosen block regardless of whether any honest node ever voted for it in round 0. [7](#0-6) [8](#0-7)

processVotes ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)

-- | VR-1A: the voter has seen the certificate for the previous round, and the
-- certificate was received in the first X slots after the start of the round.
perasVR1A ::
  HasPerasCertRound cert =>
  PerasVotingView cert ->
  Pred PerasVotingRule
perasVR1A
  PerasVotingView
    { perasParams
    , currRoundNo
    , latestCertSeen
    } =
    VR1A := vr1a1 :/\: vr1a2
   where
    -- The latest certificate seen is from the previous round
    vr1a1 =
      case latestCertSeen of
        -- We have seen a certificate ==> check its round number
        NotOrigin cert ->
          currRoundNo :==: getPerasCertRound (lcsCert cert) + 1
        -- We have never seen a certificate ==> check if we are voting in round 0
        Origin ->
          currRoundNo :==: PerasRoundNo 0

    -- The latest certificate seen was received within X slots from the start
    -- of its round
    vr1a2 =
      case latestCertSeen of
        -- We have seen a certificate ==> check its arrival time
        NotOrigin cert ->
          lcsArrivalSlot cert :<=: lcsRoundStartSlot cert + _X
        -- We have never seen a certificate ==> vacuously true
        Origin ->
          Bool True

    _X =
      SlotNo $
        unPerasCertArrivalThreshold $
          perasCertArrivalThreshold perasParams
