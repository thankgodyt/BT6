### Title
Peras Certificate and Vote Validation Stubs Unconditionally Accept All Inbound Objects, Enabling Unauthorized Chain-Weight Manipulation — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `BlockSupportsPeras` class defines `validatePerasCert` and `validatePerasVote` as the mandatory cryptographic guards that must be satisfied before a Peras certificate or vote is admitted into the node's storage and chain-selection pipeline. The inbound-diffusion handlers (`processCerts`, `processVotes`) correctly call these guards. However, the sole production instance of `BlockSupportsPeras` implements both guards as unconditional stubs: `validatePerasCert` always returns `Right` regardless of content, and `validatePerasVote` checks only stake-distribution membership while skipping all signature verification. An unprivileged peer can therefore inject arbitrary crafted certificates and votes that pass "validation", accumulate weight boosts in the `PerasCertDB`, and cause the node to prefer a non-canonical chain.

---

### Finding Description

`BlockSupportsPeras` is the typeclass that every block type must satisfy to participate in the Peras protocol. It exposes two validation methods:

```haskell
validatePerasCert ::
  PerasCfg blk ->
  PerasCert blk ->
  Either (PerasValidationErr blk) (ValidatedPerasCert blk)

validatePerasVote ::
  PerasCfg blk ->
  PerasVoteStakeDistr ->
  PerasVote blk ->
  Either (PerasValidationErr blk) (ValidatedPerasVote blk)
```

The sole production instance (covering all `StandardHash blk`) implements both as stubs:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
```

`validatePerasCert` unconditionally wraps any certificate in `Right`, performing zero cryptographic checks. [1](#0-0) 

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
```

`validatePerasVote` only checks that the claimed voter ID appears in the stake distribution; it never verifies the vote's cryptographic signature. [2](#0-1) 

These stubs are the validators passed directly into the inbound-diffusion handlers. `processCerts` calls `validateCert` on every inbound certificate and only rejects a batch when at least one returns `Left`:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) -> mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _)            -> throw (PerasCertValidationError errs)
``` [3](#0-2) 

Because `validatePerasCert` always returns `Right`, the `(errs, _)` branch is unreachable; every certificate a peer sends is admitted. The same pattern applies to `processVotes`: [4](#0-3) 

Admitted certificates are stored in `PerasCertDB` and immediately affect chain selection via `addPerasCertAsync`, which can trigger a fork switch: [5](#0-4) 

The `PerasCertDB.implAddCert` implementation itself also carries an explicit TODO noting that non-trivial validation logic is still missing: [6](#0-5) 

The parallel for votes: `implAddVote` carries the same TODO: [7](#0-6)

### Impact Explanation

**Unauthorized certificate acceptance / chain-weight manipulation (Critical/High).**

A Peras certificate carries a weight boost (`vpcCertBoost`) that is added to the chain containing the boosted block during chain selection. Because `validatePerasCert` never rejects any certificate, an unprivileged peer can:

1. Craft a `PerasCert` naming any block point and any round number.
2. Send it via the Peras object-diffusion mini-protocol.
3. The node's `processCerts` calls `validatePerasCert`, receives `Right`, timestamps the cert, and stores it in `PerasCertDB`.
4. `addPerasCertAsync` is triggered, which enqueues a chain-selection event.
5. The forged weight boost causes the node to prefer a non-canonical (potentially adversarial) chain over the honest chain.

For votes, an attacker who knows any legitimate voter ID in the current stake distribution can forge votes for that voter (no signature check), accumulate enough forged stake to cross the quorum threshold, and cause the node to internally generate a certificate for an adversarial block — again feeding into chain selection.

This matches the allowed impact scope: **bypass of Peras certificate/vote checks that enables unauthorized certificate acceptance**, and **chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain**.

### Likelihood Explanation

The Peras object-diffusion mini-protocol is wired into the production node's diffusion layer via `makePerasCertPoolWriterFromChainDB` and `makePerasVotePoolWriterFromChainDB`. [8](#0-7) [9](#0-8) 

Any peer that can connect to the node and speak the Peras object-diffusion protocol can exploit this. No special keys, stake, or privileges are required. The attack requires only knowledge of the protocol wire format and, for vote forgery, any voter ID visible in the public stake distribution.

---

### Recommendation

1. **`validatePerasCert`**: Implement full cryptographic verification of the certificate's aggregate signature against the claimed committee members and the boosted block, as specified by the Peras protocol. Remove the unconditional `Right` stub. [1](#0-0) 

2. **`validatePerasVote`**: Add signature verification of the vote body against the voter's public key (looked up from the stake distribution or committee selection context) before returning `Right`. [2](#0-1) 

3. **`implAddCert` / `implAddVote`**: Resolve the TODO items that acknowledge missing validation logic at the DB layer as a defence-in-depth measure. [6](#0-5) [7](#0-6) 

4. Until real validation is in place, consider gating the Peras object-diffusion handlers behind a feature flag so that nodes not yet running Peras do not expose the unauthenticated ingest path.

---

### Proof of Concept

**Crafted certificate injection:**

1. Attacker connects to a node and speaks the Peras certificate object-diffusion mini-protocol.
2. Attacker sends a `PerasCert { pcCertRound = R, pcCertBoostedBlock = adversarialBlockPoint }`.
3. Node calls `processCerts` → `validatePerasCert mkPerasParams cert` → `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams })`.
4. Certificate is stored in `PerasCertDB`; `addPerasCertAsync` triggers chain selection.
5. The adversarial block now carries a weight boost; if the adversarial chain's boosted weight exceeds the honest chain's weight, the node switches forks.

**Forged vote leading to certificate generation:**

1. Attacker observes the public stake distribution and picks any voter ID `V` with sufficient stake.
2. Attacker sends `PerasVote { pvVoteRound = R, pvVoteBlock = adversarialBlockPoint, pvVoteVoterId = V }` (no valid signature needed).
3. Node calls `processVotes` → `validatePerasVote mkPerasParams stakeDistr vote` → `Right (ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stakeOf(V) })`.
4. If the attacker repeats this for enough voter IDs to cross the quorum threshold, `implAddVote` internally forges a certificate for the adversarial block.
5. The forged certificate is added via `addPerasCertAsync`, triggering the same chain-selection manipulation as above.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
