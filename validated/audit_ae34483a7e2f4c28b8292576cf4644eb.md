### Title
Peras Certificate Validation Stub Unconditionally Accepts Any Peer-Supplied Certificate - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` method in the production `BlockSupportsPeras` instance is a stub that unconditionally returns `Right` (success) for every certificate, performing no cryptographic checks. The production inbound certificate pool writer (`makePerasCertPoolWriterFromChainDB`) wires this stub directly into the live object-diffusion receive path. Any unprivileged peer can therefore inject arbitrary Peras certificates over the standard node-to-node protocol; each injected certificate is accepted without verification, stored in the `PerasCertDB`, and immediately triggers chain selection for the boosted block, allowing an attacker to manipulate chain selection weight.

---

### Finding Description

**Root cause — stub validation always succeeds**

`BlockSupportsPeras` declares `validatePerasCert` as a class method. The catch-all instance for `StandardHash blk` (which covers every concrete block type that has not overridden it) is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

Every certificate, regardless of its cryptographic content, is returned as `ValidatedPerasCert` with the full configured weight boost. No signature, quorum, committee-membership, or round-number check is performed.

**Production inbound path uses the stub**

`makePerasCertPoolWriterFromChainDB` — the writer used by the live ChainDB — passes this stub as the validation function:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { ...
    , opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

The TODO comment confirms this is a known placeholder, not a deliberate design choice.

**`processCerts` calls the stub and adds every certificate**

`processCerts` partitions the batch into valid/invalid using the supplied validator. Because the stub always returns `Right`, the "invalid" partition is always empty and every certificate is forwarded to `addCert`:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [3](#0-2) 

**Chain selection is triggered for the boosted block**

`ChainDB.addPerasCertAsync` enqueues a `ChainSelAddPerasCert` event. `chainSelSync` then calls `chainSelectionForBlock` for the block named in the certificate:

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  ...
  lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

If the boosted block is present in the VolatileDB, chain selection re-runs with the injected weight boost applied, potentially switching the node's selection to a non-canonical chain.

**Analogy to the flash-loan report**

| Flash-loan report | This finding |
|---|---|
| `onFlashLoan` trusts the caller-supplied `initiator` instead of hardcoding `msg.sender` | `processCerts` trusts the peer-supplied certificate content; `validatePerasCert` never rejects |
| Missing state-variable semaphore to track own `flashLoan()` calls | No semaphore or nonce tracking outgoing certificate requests; any inbound cert is processed |
| Anyone can call `flashLoan(receiver=FlasherFTM, initiator=FlasherFTM, …)` and pass the check | Any peer can send a `PerasCert` object over the diffusion protocol and pass the check |
| Attacker executes arbitrary actions under the victim's identity | Attacker injects arbitrary weight boosts, manipulating chain selection |

---

### Impact Explanation

An unprivileged peer can inject a `PerasCert` that names any block currently in the node's VolatileDB as the boosted block. The injected certificate receives the full `perasWeight` boost (configured via `mkPerasParams`). Chain selection then re-evaluates that block with the artificial weight, potentially causing the node to switch its selection to a non-canonical fork. Because Peras weight is additive and unbounded in the number of injected certificates (one per round number, since the DB deduplicates by round), an attacker with many round numbers available can accumulate enough weight to override the honest chain's length advantage. This is a **critical bypass of Peras certificate/vote verification** enabling unauthorized certificate acceptance and a **high chain-selection bug** allowing a non-canonical chain to be preferred.

---

### Likelihood Explanation

The attack path is direct and requires no special privileges:

1. The Peras certificate diffusion protocol (`aPerasCertDiffusionServer` / `aPerasCertDiffusionClient`) is wired into the standard node-to-node application bundle.
2. Any peer that establishes a connection can send `PerasCert` objects.
3. The stub validation never rejects, so no cryptographic material is needed.
4. The only partial mitigations are: (a) the certificate must name a block already in the VolatileDB, and (b) one certificate per round number is stored (deduplication). Neither prevents the attack; an attacker can use distinct round numbers and target blocks already downloaded by the victim.

---

### Recommendation

1. **Implement real cryptographic validation** in `validatePerasCert` before enabling the Peras certificate diffusion protocol in any production deployment. The validation must verify the aggregate BLS signature, committee membership, quorum threshold, and round-number constraints.
2. **Gate the diffusion protocol behind a feature flag** that is disabled until validation is complete, analogous to how other experimental features are handled.
3. **Add a state-variable semaphore** (analogous to the `_paramsHash` hotfix described in the report) that records which round numbers the local node has itself voted in, and reject inbound certificates for rounds where no local vote was cast — providing defense-in-depth even if the cryptographic check is bypassed.
4. **Enforce `hash != 0` / non-empty certificate checks** at the entry point of `processCerts` to prevent trivially malformed objects from reaching chain selection.

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
