Audit Report

## Title
Decimal Normalization Floor Division Produces Zero in `sign_transfer`, Permanently Freezing User Funds - (File: `near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer` locks or burns user tokens after only verifying `fee < amount`, without checking whether `normalize_amount(amount - fee, decimals) > 0`. When a token has a large decimal gap between origin and destination chains, a small net transfer amount is silently truncated to zero by floor division inside `sign_transfer`, which then panics unconditionally with `ERR_INVALID_AMOUNT_TO_TRANSFER`. Because no `cancel_transfer` function exists anywhere in the contract, the locked tokens are permanently unrecoverable.

## Finding Description
`init_transfer` constructs the `TransferMessage` and applies a single guard before locking tokens:

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
``` [1](#0-0) 

This guard does not verify that the net amount survives decimal normalization. Tokens are then locked or burned inside `init_transfer_internal` and the `TransferMessage` is stored immutably in `pending_transfers`.

Later, when a relayer calls `sign_transfer`, the net amount is normalized via floor division:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
``` [2](#0-1) 

`normalize_amount` performs integer floor division:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [3](#0-2) 

`amount_without_fee` is a simple checked subtraction: [4](#0-3) 

If `amount - fee < 10^(origin_decimals - destination_decimals)`, the floor division yields `0`, and `sign_transfer` panics unconditionally. Every subsequent relayer call for that transfer ID produces the same panic because the stored `TransferMessage` is immutable. A grep across the entire repository confirms no `cancel_transfer` function exists anywhere in the contract.

The code comment at L2781–2783 acknowledges dust truncation for small remainders but frames it as an accepted behavior absorbed by fees. It does not address the case where the entire net amount truncates to zero, causing `sign_transfer` to be permanently unexecutable. [5](#0-4) 

## Impact Explanation
This constitutes **permanent freezing of bridged funds**, which is an explicitly listed Critical impact. Tokens are locked or burned at `init_transfer` time. The transfer is stored in `pending_transfers` with no mutation path. `sign_transfer` always reverts for this transfer ID. No `cancel_transfer` or equivalent recovery function exists. The user's funds are irrecoverably frozen in the bridge contract.

## Likelihood Explanation
The scenario is reachable by any unprivileged user via the standard `ft_transfer_call` → `ft_on_transfer` → `init_transfer` path. The required conditions are realistic: NEAR-native tokens bridged to EVM chains commonly have `origin_decimals = 24` and `destination_decimals = 6`, giving a divisor of `10^18`. Any user who submits `amount = 2, fee = 1` (net = 1, which is less than `10^18`) will trigger the freeze. The `init_transfer` guard accepts the transaction, giving the user no indication that their transfer is permanently unprocessable.

## Recommendation
Add a pre-flight normalization check inside `init_transfer` (or `init_transfer_internal`) before locking tokens, after looking up the destination token's `Decimals` (already done in `sign_transfer`):

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

Alternatively, implement a `cancel_transfer` function that allows the original sender to reclaim locked tokens for transfers that can never be signed, providing a recovery path for already-frozen funds.

## Proof of Concept
1. Register a token with `origin_decimals = 24`, `decimals = 6` (divisor = `10^18`).
2. Alice calls `ft_transfer_call` with `amount = 2` and `fee = 1` targeting an EVM recipient.
3. `init_transfer` passes the guard (`1 < 2`). Alice's 2 tokens are locked. The transfer is stored in `pending_transfers`.
4. A relayer calls `sign_transfer` for Alice's transfer ID.
5. `normalize_amount(1, {decimals: 6, origin_decimals: 24})` = `1 / 10^18` = `0`.
6. `require!(0 > 0, ...)` panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.
7. Every future call to `sign_transfer` for this transfer ID produces the same panic.
8. Alice's 2 tokens remain permanently locked with no recovery path.

A unit test can be written directly against `normalize_amount` and `init_transfer` in `near/omni-bridge/src/tests/lib_test.rs` to confirm step 5, and a contract-level integration test can confirm that `sign_transfer` always reverts for such a transfer ID while `pending_transfers` still holds the entry.
