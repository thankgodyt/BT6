### Title
u128 Overflow Panic in `check_deposit_msg` Permanently Sticks Deposit UTXO — (`contracts/satoshi-bridge/src/deposit_msg.rs`)

---

### Summary

`check_deposit_msg` accumulates `post_action.amount.0` into a bare `u128` with `+=` before any amount guard is reached. The workspace release profile sets `overflow-checks = true`, so a depositor who crafts two `PostAction` entries each carrying `amount = u128::MAX/2 + 1` causes a deterministic arithmetic-overflow trap the first time a trusted relayer submits the containing `DepositMsg` to `verify_deposit_v2`. The relayer's transaction aborts, and because the deposit address is derived from the hash of the exact `DepositMsg`, no alternative `DepositMsg` can ever claim the same UTXO — the deposit is permanently stuck.

---

### Finding Description

**Overflow-checks are on in release:** [1](#0-0) 

`overflow-checks = true` is set at the workspace level, so every `u128` addition in the compiled WASM will trap on overflow.

**The vulnerable accumulation:** [2](#0-1) 

`total_amount` is a plain `u128` initialised to `0`. The loop adds each `post_action.amount.0` with `+=` — no `checked_add`, no `saturating_add`. The overflow guard (`total_amount > actual_mintable_amount`) is only reached **after** the loop completes: [3](#0-2) 

**Maximum post-actions is 2:** [4](#0-3) 

Exactly two entries are permitted, which is the minimum needed to overflow: `(u128::MAX/2 + 1) + (u128::MAX/2 + 1) = u128::MAX + 2`.

**Entry point — depositor controls `DepositMsg`, relayer submits it:**

`get_user_deposit_address` is a public view function that accepts any `DepositMsg` without validating `post_action.amount` values: [5](#0-4) 

The deposit address is the SHA-256 hash of the serialised `DepositMsg`. Once BTC is sent to that address, the relayer must use the **exact same** `DepositMsg` to call `verify_deposit_v2`: [6](#0-5) 

`check_deposit_msg` is called synchronously inside `internal_verify_deposit` before any cross-contract call is dispatched: [7](#0-6) 

The `#[trusted_relayer]` gate on `verify_deposit_v2` does not help here — it only prevents an unprivileged account from calling the function directly. The depositor never needs to call it; the trusted relayer does so on their behalf, carrying the attacker-supplied `DepositMsg`.

---

### Impact Explanation

- The relayer's `verify_deposit_v2` transaction traps (WASM arithmetic overflow) and reverts every time it is attempted with this `DepositMsg`.
- Because the deposit address is bound to the hash of the `DepositMsg`, no other `DepositMsg` can redeem the UTXO.
- The deposit UTXO is permanently unprocessable — a stuck-state requiring operator intervention (e.g., a manual refund path, if one exists for this UTXO).
- The relayer loses gas on every retry.

Impact category: **Low** — publicly reachable panic-driven stuck-state in a production bridge path, no direct theft.

---

### Likelihood Explanation

The attack requires only:
1. Calling the public `get_user_deposit_address` view with a crafted `DepositMsg`.
2. Sending any amount of BTC to the returned address.
3. Waiting for the relayer to attempt processing.

No privileged access, no key compromise, no third-party dependency. The overflow is deterministic and reproducible in a local sandbox.

---

### Recommendation

Replace the bare `+=` with `checked_add` and return `None` (emitting an `InvalidPostAction` event) on overflow, consistent with how every other validation failure in `check_deposit_msg` is handled:

```rust
// contracts/satoshi-bridge/src/deposit_msg.rs  line 85
total_amount = match total_amount.checked_add(post_action.amount.0) {
    Some(v) => v,
    None => {
        Event::InvalidPostAction {
            index: Some(index),
            err_msg: "post_action amounts overflow u128.".to_string(),
        }
        .emit();
        return None;
    }
};
```

The same pattern should be applied to `total_gas` on line 167 for consistency, though `u64` overflow there is practically unreachable given the per-action gas caps.
