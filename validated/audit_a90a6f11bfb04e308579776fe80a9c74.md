### Title
Tokens Minted to Shared Bridge Balance Without Per-User Tracking in `safe_mint` — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

The `safe_mint` function in the nBTC token contract mints tokens to the bridge's shared account (`bridge_id`) **before** checking whether the recipient's account is registered. If the recipient is unregistered, the function returns `U128(0)` without transferring the tokens, leaving them permanently accumulated in the bridge's shared balance with no per-user accounting record. This is a direct analog to the XVS Vault bug: a shared global balance is used as an intermediate instead of per-entity tracking, causing an accounting divergence where minted supply is not matched to any user.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, the `safe_mint` function executes in this order: [1](#0-0) 

```rust
self.token.internal_deposit(&self.bridge_id, amount.into());  // (1) mints to shared bridge balance

if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0));                     // (2) returns 0 — no transfer
}
```

Step (1) unconditionally increases `bridge_id`'s token balance and the global total supply by `amount`. Step (2) then checks whether the intended recipient (`account_id`) is registered. If they are not, the function returns `U128(0)` — **without transferring the tokens and without recording which user they belong to**.

The return value `U128(0)` is indistinguishable from "zero tokens were minted." The calling satoshi-bridge contract receives this value in its mint callback and has no way to know that `amount` tokens were already deposited into `bridge_id`. If the bridge interprets `U128(0)` as "mint did not occur," it will not add the amount to `lost_found` or any per-user recovery ledger. The tokens are then stranded in the bridge's shared balance with no accounting link to the depositing user.

This is structurally identical to the XVS Vault bug: instead of tracking minted tokens per-user, they are deposited into a shared pool (`bridge_id`), and when the per-user step fails, the shared pool silently absorbs the funds with no corrective record. [2](#0-1) 

The `lost_found` recovery mechanism in the satoshi-bridge is only populated by `transfer_nbtc_callback` when an explicit `ft_transfer` call fails: [3](#0-2) 

`safe_mint` does not go through this path — it returns early before any transfer is attempted, so `transfer_nbtc_callback` is never reached and `lost_found` is never updated.

---

### Impact Explanation

A user deposits BTC/ZEC to the bridge. The relayer submits a valid `TxInclusionProof`, the UTXO is verified and consumed on-chain, and the bridge calls `safe_mint` on the nBTC contract. If the user's NEAR account is not registered in the nBTC token contract, `safe_mint` mints `amount` nBTC to `bridge_id` and returns `U128(0)`. The user's BTC is permanently locked in the bridge's UTXO set (the deposit is marked verified), but they receive zero nBTC. The minted tokens accumulate silently in the bridge's shared balance. This constitutes **significant permanent loss of user funds** — the user's BTC is consumed with no corresponding token issuance and no on-chain recovery path.

Impact classification: **Critical** — permanent loss of user funds; or at minimum **Medium** — stuck bridge state requiring operator intervention to manually identify and redistribute the stranded tokens.

---

### Likelihood Explanation

The trigger condition is a user depositing BTC/ZEC whose NEAR account (`account_id`) is not registered in the nBTC token contract at the time the mint callback executes. This is a realistic scenario for:

- New users who have not called `storage_deposit` on the nBTC contract before depositing BTC.
- Users whose storage registration expired or was unregistered between deposit and proof submission.
- Automated relayer flows where the relayer submits the proof without verifying the recipient's registration status.

The deposit flow is publicly accessible — any bridge user can trigger this path without any privileged access.

---

### Recommendation

Reverse the order of operations in `safe_mint`: check whether `account_id` is registered **before** minting tokens to `bridge_id`. If the account is not registered, either revert the call (forcing the caller to handle the failure) or register the account automatically before minting. This ensures that tokens are never minted to the shared bridge balance without a guaranteed per-user transfer path.

Alternatively, if the two-step mint-then-transfer pattern is intentional, the return value when the account is unregistered must be changed from `U128(0)` to the actual minted `amount`, so the satoshi-bridge callback can correctly add the stranded amount to `lost_found` for later recovery.

---

### Proof of Concept

1. Alice deposits 1 BTC to her bridge deposit address. Her NEAR account `alice.near` exists but has **not** called `storage_deposit` on the nBTC contract.
2. A relayer submits a valid `TxInclusionProof`. The satoshi-bridge verifies the proof, marks the UTXO as verified (consumed), and calls `safe_mint(alice.near, 100_000_000, None)` on the nBTC contract.
3. Inside `safe_mint`:
   - `self.token.internal_deposit(&self.bridge_id, 100_000_000)` executes — `bridge_id`'s balance increases by 100,000,000 satoshis-worth of nBTC; total supply increases by the same amount.
   - `self.token.accounts.get(&"alice.near")` returns `None` — Alice is not registered.
   - The function returns `PromiseOrValue::Value(U128(0))`.
4. The satoshi-bridge mint callback receives `U128(0)`, interprets it as "mint did not occur," and does not add 100,000,000 to `lost_found["alice.near"]`.
5. Alice's 1 BTC is permanently locked. The 100,000,000 nBTC tokens sit in `bridge_id`'s balance with no per-user record. Alice has no on-chain mechanism to recover her funds. [1](#0-0) [4](#0-3)

```rust
    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }
```

```rust
                amount,
```
