### Title
Peras Vote and Certificate Validation Bypass via Stub `validatePerasVote`/`validatePerasCert` — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance in `SupportsPeras.hs` ships stub implementations of `validatePerasVote` and `validatePerasCert` that perform no cryptographic verification whatsoever. `validatePerasCert` unconditionally returns `Right` for every certificate, and `validatePerasVote` only checks whether the claimed voter ID appears in the stake distribution — it never verifies the vote signature, eligibility proof, or VRF output. Because this catch-all instance (`instance StandardHash blk => BlockSupportsPeras blk`) is the only one in the codebase, it is the implementation used for all Cardano block types. An unprivileged peer connected via the Peras object-diffusion mini-protocol can therefore forge votes for any registered voter, trigger quorum for an arbitrary block, and cause honest nodes to accept a fabricated Peras certificate that boosts an attacker-chosen chain.

---

### Finding Description

**Root cause — missing validation in the default `BlockSupportsPeras` instance**

`SupportsPeras.hs` defines a catch-all instance with an explicit TODO acknowledging it is a placeholder:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/120
instance StandardHash blk => BlockSupportsPeras blk where
```

The `PerasVote blk` data type in this instance carries no signature or eligibility-proof field at all:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound  :: PerasRoundNo
  , pvVoteBlock  :: Point blk
  , pvVoteVoterId :: PerasVoterId
  }
```

The `validatePerasVote` implementation ignores the `_params` argument entirely and only checks stake-distribution membership:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
```

`validatePerasCert` is even weaker — it always returns `Right` regardless of the certificate content:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
```

**Attacker-controlled entry path**

`makePerasVotePoolWriterFromChainDB` (and its `VoteDB` variant) wires the inbound object-diffusion mini-protocol directly to `validatePerasVote`:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
```

`processVotes` in `PerasVote.hs` calls this validator for every vote batch received from a peer, then passes all votes that pass validation straight to `addVote` / `ChainDB.addPerasVoteWithAsyncCertHandling`. There is no second validation layer inside `implAddVote` (the TODO at line 172 of `Impl.hs` explicitly acknowledges this).

**Exploit flow**

1. Attacker connects to an honest node as a normal peer.
2. Attacker reads the current `PerasVoteStakeDistr` (publicly derivable from the ledger state via the local-state-query protocol).
3. Attacker crafts `PerasVote` messages claiming to be any set of registered voters whose combined stake exceeds the quorum threshold, all voting for an attacker-chosen block point.
4. `processVotes` calls `validatePerasVote` for each forged vote; the stub passes every vote whose `pvVoteVoterId` appears in the stake distribution.
5. `implAddVote` calls `updatePerasRoundVoteStates`; once the accumulated stake crosses the quorum threshold, `forgePerasCert` is invoked.
6. `forgePerasCert` (also a stub that always returns `Right`) produces a `ValidatedPerasCert` with `vpcCertBoost = perasWeight params`.
7. The certificate is stored in the `PerasVoteDB` and propagated to `ChainDB`, where it boosts the attacker-chosen block's chain-selection weight.
8. Honest nodes that receive this certificate may prefer the attacker's chain over the honest chain.

---

### Impact Explanation

**Severity: Critical — Bypass of Peras voting/certificate checks enabling unauthorized certificate acceptance.**

The Peras protocol's security guarantee is that a certificate can only be forged when a quorum of legitimately elected committee members have signed the same block. The stub `validatePerasVote` removes the only gate that enforces this: any peer can impersonate any registered voter without possessing their private key. A single malicious peer with knowledge of the stake distribution can unilaterally forge a quorum of votes and cause honest nodes to accept a certificate for an arbitrary block, directly manipulating chain selection. This maps to the allowed impact category: *"Bypass of … Peras voting or certificate checks … that enables unauthorized … vote, or certificate acceptance."*

---

### Likelihood Explanation

The attack requires only:
- A standard peer connection (no privileged access).
- Knowledge of the current `PerasVoteStakeDistr`, which is publicly queryable.
- The ability to send well-formed CBOR-encoded `PerasVote` messages over the object-diffusion mini-protocol.

No cryptographic material needs to be compromised. The attack is deterministic and reproducible on any private testnet running this codebase with Peras vote diffusion enabled.

---

### Recommendation

1. **Implement real cryptographic validation** in `validatePerasVote` before Peras vote diffusion is enabled in any environment. At minimum, verify the vote signature against the voter's registered public key and, for non-persistent committee members, verify the VRF eligibility proof — exactly as the concrete `PerasVote` type in `Peras/Vote/V1.hs` carries (`pvEligibilityProof`, `pvSignature`).
2. **Replace the catch-all stub instance** with a proper per-era instance that uses the `V1.hs` vote type and the `WFALS`/`EveryoneVotes` committee verification logic already present in `Committee/WFALS.hs` and `Committee/EveryoneVotes.hs`.
3. **Gate the object-diffusion mini-protocol** behind a feature flag that is disabled until the real validation is in place, so the stub cannot be reached from the network.

---

### Proof of Concept

**Setup**: private testnet, two nodes A (honest) and B (attacker), Peras vote diffusion enabled.

**Steps**:

1. Query node A's local-state-query endpoint for the current `PerasVoteStakeDistr`. Identify voter IDs whose combined stake exceeds the quorum threshold (e.g., the top-5 stakers).
2. Construct `PerasVote` messages for each of those voter IDs, all with `pvVoteBlock` set to an attacker-chosen block point P (e.g., a block on a minority fork).
3. Send the batch to node A via the Peras object-diffusion mini-protocol from node B.
4. `processVotes` on node A calls `validatePerasVote mkPerasParams sd vote` for each message. Because each `pvVoteVoterId` is present in `sd`, all votes pass.
5. `implAddVote` accumulates stake; once the quorum threshold is crossed, `forgePerasCert` produces a `ValidatedPerasCert` boosting block P.
6. Observe that node A's chain-selection now assigns extra weight to block P, potentially causing it to prefer the minority fork over the honest chain.

**Expected outcome**: Node A accepts a Peras certificate for an attacker-chosen block without any legitimate committee member having signed it.

```haskell
processVotes ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
```
