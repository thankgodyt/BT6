### Title
Unauthenticated `request_refund` Caller Allows Frontrunner to Redirect BTC Refund to Attacker Address - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary
`request_refund` does not verify that the caller (`env::predecessor_account_id()`) is the `deposit_msg.recipient_id`. When `deposit_msg.refund_address` is `None`, any NEAR account can supply an arbitrary `refund_address`. A frontrunner who observes a pending `request_refund` call in the NEAR mempool can race it with their own call using an attacker-controlled BTC address, causing the victim's transaction to revert and locking the refund path until DAO/Operator intervention.

### Finding Description

`request_refund` is a public, payable function with no caller-identity restriction: [1](#0-0) 

The only caller check inside the function body is on the optional `gas_fee` parameter (DAO/Operator only). No check ties the caller to `deposit_msg.recipient_id`: [2](#0-1) 

Inside `internal_request_refund`, the `refund_address` validation only fires when `deposit_msg.refund_address` is already set. When it is `None`, the caller-supplied address is accepted verbatim: [3](#0-2) 

The callback then stores the caller-supplied `refund_address` directly into the `RefundRequest`: [4](#0-3) 

A duplicate-request guard prevents a second `request_refund` for the same UTXO from succeeding: [5](#0-4) 

So once the attacker's request is stored, the victim cannot create a competing one.

### Impact Explanation

After the `unsafe_refund_timelock_sec` elapses, `execute_refund` is callable by anyone: [6](#0-5) 

`finalize_refund_with_psbt` builds the Bitcoin refund transaction paying `refund_request.refund_address` — the attacker's address — and initiates MPC signing: [7](#0-6) 

If the DAO/Operator does not reject the malicious request before the timelock expires, the BTC is irrecoverably sent to the attacker. This constitutes direct theft of user funds.

### Likelihood Explanation

The NEAR mempool is publicly observable. The attacker needs only to:
1. Watch for `request_refund` calls where `deposit_msg.refund_address` is `None`.
2. Resubmit the same `deposit_msg`, `tx_bytes`, `vout`, and `proof` with their own `refund_address` and a competitive gas price.
3. Wait for the timelock and call `execute_refund`.

No privileged access is required. The storage deposit cost is the only barrier. The attack is fully automatable.

### Recommendation

When `deposit_msg.refund_address` is `None`, require the caller to be the `deposit_msg.recipient_id`:

```rust
pub fn request_refund(...) -> Promise {
    // existing gas_fee check ...

    if deposit_msg.refund_address.is_none() {
        let caller = env::predecessor_account_id();
        require!(
            caller == deposit_msg.recipient_id,
            "Caller must be the deposit recipient when refund_address is not pre-authorized"
        );
    }

    self.internal_request_refund(...)
}
```

Alternatively, require `deposit_msg.refund_address` to always be set at deposit time (embed it in the deposit address derivation path), eliminating the open-ended caller-supplied address entirely.

### Proof of Concept

1. Alice sends BTC to the deposit address derived from `deposit_msg = {recipient_id: "alice.near", refund_address: None}`.
2. The deposit is never finalized (bridge paused, etc.).
3. Alice broadcasts `request_refund(deposit_msg, "alice_btc_addr", tx_bytes, 0, proof, None)` on NEAR.
4. Attacker observes the pending transaction, extracts `deposit_msg`, `tx_bytes`, `vout`, and `proof`.
5. Attacker submits `request_refund(deposit_msg, "attacker_btc_addr", tx_bytes, 0, proof, None)` with higher priority.
6. Attacker's transaction lands first; `refund_requests["txid@0"] = {refund_address: "attacker_btc_addr", ...}` is stored.
7. Alice's transaction reverts: `"Refund request already exists for this UTXO"`.
8. After `unsafe_refund_timelock_sec`, attacker calls `execute_refund("txid@0", None)`.
9. MPC signs a Bitcoin transaction paying `"attacker_btc_addr"`.
10. Alice's BTC is stolen. Recovery requires DAO to have rejected the request before step 8.
