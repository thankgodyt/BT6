### Title
Unconditional `validatePerasCert` Accepts Any Crafted Peras Certificate Without Checking Conditions - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` function unconditionally accepts every inbound Peras certificate as valid, performing zero cryptographic or protocol checks. An unprivileged peer can send a crafted `PerasCert` through the Peras certificate object-diffusion mini-protocol; the certificate bypasses all validation, is stored in the `PerasCertDB`, and its `vpcCertBoost` weight is applied to chain selection. This allows an attacker to arbitrarily boost any block's chain-selection weight, potentially causing an honest node to prefer a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must be passed before a certificate is accepted as `ValidatedPerasCert`. The production catch-all instance (the only instance in the codebase) is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This is the **only** instance; the comment explicitly marks it as a degenerate stub:

``` [2](#0-1) 

The production inbound-certificate handler in the Peras certificate object-diffusion mini-protocol calls this function directly:

```haskell
, opwAddObjects = \certs ->
    processCerts
      systemTime
      (ChainDB.getPerasCertIds chainDB)
      -- TODO replace when actual plumbing is in place
      (validatePerasCert mkPerasParams)
      (void . ChainDB.addPerasCertAsync chainDB)
      certs
``` [3](#0-2) 

`processCerts` partitions the batch into valid/invalid using `validateCert`; since `validatePerasCert` always returns `Right`, every certificate in every batch is accepted:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) -> throwIO (PerasCertValidationError errs)
``` [4](#0-3) 

Once stored, the `PerasCertDB` exposes a `getWeightSnapshot` that feeds `vpcCertBoost` weights into chain selection via `preferAnchoredCandidate`. The `vpcCertBoost` is set to `perasWeight params` (the configured Peras weight constant) for every accepted certificate, regardless of whether the certificate was legitimately produced by a quorum of stake holders. [5](#0-4) 

The analog to the external report is exact: the transition from "unvalidated `PerasCert`" to "`ValidatedPerasCert`" (the "successful" state) does not check any precondition — no quorum proof, no cryptographic signature, no round-number bounds, no boosted-block existence check.

---

### Impact Explanation

An attacker controlling any peer connected via the Peras certificate mini-protocol can:

1. Craft a `PerasCert` naming an arbitrary block point and any round number.
2. Send it; `validatePerasCert` returns `Right` unconditionally.
3. The certificate is stored in `PerasCertDB` with `vpcCertBoost = perasWeight params`.
4. `getWeightSnapshot` returns this boost, which `preferAnchoredCandidate` uses to prefer the boosted chain fragment over the honest chain.

This constitutes a **bypass of Peras certificate validation** enabling unauthorized certificate acceptance and chain-selection manipulation. An attacker can make an honest node prefer a non-canonical chain by boosting an adversarial fork, directly undermining the Peras protocol's chain-quality guarantee.

**Impact class**: High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions; also a bypass of certificate checks enabling unauthorized certificate acceptance.

---

### Likelihood Explanation

The Peras certificate object-diffusion mini-protocol is wired into the production node kernel. Any peer that can establish a connection and speak the Peras cert mini-protocol can send crafted certificates. No stake, no keys, and no prior knowledge of the chain are required. The attack is deterministic and requires a single crafted message per target block.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that checks, at minimum:

1. **Quorum proof**: the certificate must embed or reference a set of votes whose total stake exceeds `perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin`.
2. **Vote signatures**: each vote in the quorum set must carry a valid cryptographic signature from a registered stake pool key.
3. **Round-number bounds**: the certificate's round number must be within the current valid window (not expired, not from the future).
4. **Boosted-block existence**: the `pcCertBoostedBlock` point must refer to a block that exists on a known chain fragment.

Until the real implementation is ready, the mini-protocol endpoint should be disabled or the node should refuse to apply any Peras weight boost from externally received certificates.

---

### Proof of Concept

```
1. Attacker connects to a victim node via the Peras certificate mini-protocol.

2. Attacker constructs:
     PerasCert
       { pcCertRound      = PerasRoundNo 999
       , pcCertBoostedBlock = <point of attacker's fork tip>
       }

3. Attacker sends the certificate batch to the victim.

4. processCerts calls (validatePerasCert mkPerasParams cert)
   → returns Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams })
   → no error path is taken.

5. addCert stores the ValidatedPerasCert in PerasCertDB.

6. getWeightSnapshot now returns a non-zero boost for the attacker's fork tip.

7. preferAnchoredCandidate computes the weighted SelectView for the attacker's
   fragment as strictly greater than the honest chain's SelectView.

8. chainSelection adopts the attacker's fork.
``` [1](#0-0) [6](#0-5)
