### Title
Peras Quorum Bypass via Unit Mismatch in `stakeAboveThreshold()` — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` compares a `PerasVoteStake` value (which may carry absolute lovelace units from the ledger) directly against a `PerasQuorumStakeThreshold` (documented as a relative/normalized fraction). The function contains an explicit self-admitted TODO acknowledging that the two operands are not guaranteed to be in the same units. If the stake distribution is populated with absolute ledger values — the natural source — a single vote from any registered pool with positive stake satisfies the quorum check, allowing unauthorized Peras certificate forging.

---

### Finding Description

`stakeAboveThreshold` in `SupportsPeras.hs` performs the comparison:

```haskell
stake >= quorumThreshold + safetyMargin
```

where `stake = unPerasVoteStake voteStake` and `quorumThreshold = unPerasQuorumStakeThreshold (perasQuorumStakeThreshold params)`.

The code's own comment at lines 153–161 states:

> "TODO: this function assumes that the 'PerasVoteStake' and the quorum threshold used in 'PerasParams' are expressed in the same units. That is, both are either absolute or relative (normalized) values. Under the current implementation of 'PerasParams', this function only makes sense when both values are relative (normalized) values, so we should either normalize the 'PerasVoteStake' before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [1](#0-0) 

The `PerasVoteStake` type is a bare `Rational` with no unit enforcement: [2](#0-1) 

The `PerasQuorumStakeThreshold` is also a bare `Rational`, documented as a relative value (e.g., `0.75` for 75%): [3](#0-2) 

The stake distribution fed into vote validation is provided externally via `getStakeDistrSTM` with no normalization step anywhere in the pipeline: [4](#0-3) 

`stakeAboveThreshold` is called in `votesReachQuorum`, which is the gate for forging a `ValidatedPerasCert`: [5](#0-4) 

And in `updateCandidateVoteState`, which drives the live vote aggregation state machine: [6](#0-5) 

The analog to the external report is exact: the external bug applies a single collateral factor to an aggregated multi-asset balance (mixing per-asset factors), producing a result that is too permissive. Here, an absolute per-voter stake value is compared against a relative quorum threshold without normalization, producing a comparison that is always `True` when absolute values are large.

---

### Impact Explanation

**Concrete scenario:**

- Total network stake: 1,000,000,000 lovelace
- `perasQuorumStakeThreshold`: `0.75` (relative, 75%)
- Adversary's pool stake: `1,000` lovelace (0.0001% of total)
- `PerasVoteStakeDistr` populated with absolute ledger values: adversary's `PerasVoteStake = 1000`
- `stakeAboveThreshold`: `1000 >= 0.75` → `True`

A single vote from the adversary's pool forges a `ValidatedPerasCert`. The certificate assigns a `PerasWeight` boost (from `perasWeight params`) to the adversary's chosen block. Chain selection in `WeightedSelectView.preferCandidate` then uses `wsvTotalWeight` — the sum of block number and weight boost — to prefer chains: [7](#0-6) 

An adversary with any positive registered stake can repeatedly forge certificates for their own blocks, inflating their chain's total weight and causing honest nodes to prefer the adversary's chain over the honest chain. This is a bypass of the Peras quorum certificate check enabling unauthorized certificate acceptance and chain selection manipulation.

---

### Likelihood Explanation

The ledger naturally exposes stake as absolute lovelace values. The comment at lines 136–143 explicitly states there is "no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake." This means the normalization step is absent by design uncertainty, not by oversight. Any deployment that populates `PerasVoteStakeDistr` from the raw ledger stake distribution — the only documented source — triggers the bug. An unprivileged peer that is a registered stake pool (any positive stake) can send a single valid `PerasVote` message over the object diffusion mini-protocol to trigger certificate forging. [8](#0-7) 

---

### Recommendation

`stakeAboveThreshold` must not compare values of different units. The fix should follow one of the two paths the TODO already identifies:

1. **Normalize at input**: Before storing values in `PerasVoteStakeDistr`, divide each voter's absolute stake by the total stake in the distribution, producing relative values in `[0,1]`.
2. **Normalize at comparison**: Change `stakeAboveThreshold` to accept the total stake as an additional parameter and compute `stake / totalStake >= quorumThreshold` internally.

The type system should enforce the distinction — e.g., a `newtype AbsoluteStake` vs. `newtype RelativeStake` — so that the compiler rejects any future comparison of values in different units.

---

### Proof of Concept

1. Register a stake pool with 1 lovelace of stake on a private testnet.
2. Populate `PerasVoteStakeDistr` with the raw ledger value: `Map.singleton voterId (PerasVoteStake 1)`.
3. Set `perasQuorumStakeThreshold = PerasQuorumStakeThreshold 0.75` (the default relative threshold).
4. Send a single `PerasVote` for any block via the object diffusion mini-protocol.
5. Observe that `stakeAboveThreshold params (PerasVoteStake 1)` evaluates `1 >= 0.75` → `True`.
6. `votesReachQuorum` returns `Just votesWithQuorum`; `forgePerasCert` produces a `ValidatedPerasCert` with boost `perasWeight params`.
7. The certificate is stored and the boosted block gains unearned chain weight, causing honest nodes to prefer the adversary's chain via `WeightedSelectView.preferCandidate`. [9](#0-8) [10](#0-9) [6](#0-5)

```haskell
votesReachQuorum ::
  StandardHash blk =>
  PerasCfg blk ->
  [ValidatedPerasVote blk] ->
  Maybe (ValidatedPerasVotesWithQuorum blk)
votesReachQuorum cfg votes =
  case votes of
    -- We need at least one vote to determine who these votes are for, so we
    -- can't vacuously reach a quorum, even if the quorum threshold is 0.
    [] -> Nothing
    -- If we have at least one vote, we must check that all votes are for the
    -- same target, and that their total stake of is above the quorum threshold.
    (v0 : vs)
      | not (allVotesMatchTarget v0 vs) ->
          Nothing
      | not votesHaveEnoughStake ->
          Nothing
      | otherwise ->
          Just
            ValidatedPerasVotesWithQuorum
              { vpvqTarget = getPerasVoteTarget v0
              , vpvqVotes = v0 :| vs
              , vpvqPerasCfg = cfg
              }
 where
  totalVoteStake =
    mconcat (vpvVoteStake <$> votes)
  votesHaveEnoughStake =
    stakeAboveThreshold cfg totalVoteStake
```
