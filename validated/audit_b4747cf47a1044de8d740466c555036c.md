### Title
Incomplete Hex Character Range in `isHexDigit` Causes Valid Snapshot Checksum Files to Be Permanently Rejected - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Util/CRC.hs`)

---

### Summary

The `isHexDigit` predicate in `readCRC` only accepts lowercase hex digits (`'a'`–`'f'`), silently rejecting any uppercase hex digit (`'A'`–`'F'`). A `.checksum` file written by an external tool, the forthcoming `lsm-tree` dependency, or the `snapshot-converter` utility using uppercase hex causes `readCRC` to return `CRCInvalid` for a structurally valid file. The node then permanently rejects the corresponding LedgerDB snapshot as corrupted, forcing a full re-sync from genesis or an older snapshot without any operator fault.

---

### Finding Description

In `Ouroboros.Consensus.Util.CRC`, the local `isHexDigit` predicate used by `readCRC` is:

```haskell
isHexDigit :: Char -> Bool
isHexDigit c =
  (c >= '0' && c <= '9')
    || (c >= 'a' && c <= 'f') -- lower case only
``` [1](#0-0) 

The range `'a'`–`'f'` covers only lowercase hex letters. Uppercase `'A'`–`'F'` (ASCII 65–70) are not covered. The validation gate in `readCRC` is:

```haskell
if not (BSC.length str == 8 && BSC.all isHexDigit str)
  then pure (Left CRCInvalid)
``` [2](#0-1) 

Any 8-character hex string containing at least one uppercase letter (e.g., `"A1B2C3D4"`) is rejected as `CRCInvalid` even though it is a perfectly valid CRC32 representation.

A secondary latent bug exists in `hexdigitToWord`: if an uppercase digit somehow bypassed `isHexDigit`, the expression `ord c - ord 'a' + 10` would underflow for `'A'`–`'F'` (since `ord 'A'` < `ord 'a'`), producing a wildly incorrect nibble value. [3](#0-2) 

The `readCRC` function reads the snapshot `.checksum` file whose path is constructed by `snapshotToChecksumPath`: [4](#0-3) 

The module itself explicitly imports `Data.Char` while hiding the standard `isHexDigit` (`import Data.Char hiding (isHexDigit)`), replacing it with this incomplete local definition. The TODO comment in the same file acknowledges the implementation is temporary pending `lsm-tree` adoption: [5](#0-4) 

---

### Impact Explanation

When `readCRC` returns `Left CRCInvalid`, the snapshot loading path in `Snapshots.hs` treats the snapshot as corrupted: [6](#0-5) 

The CHANGELOG documents the intended behavior: "Return an error if the checksum is different or invalid." A `CRCInvalid` result is a hard error (unlike `CRCNoFile`, which is a warning). The node permanently rejects the snapshot and must fall back to an older snapshot or re-sync from genesis. This constitutes a **LedgerDB snapshot rejection bug that causes permanent rejection of a valid snapshot without operator fault**, matching the High impact category.

---

### Likelihood Explanation

The bug is triggered whenever a `.checksum` file is written with uppercase hex digits. Three realistic paths exist:

1. **`lsm-tree` interoperability**: The TODO comment explicitly states the local `isHexDigit` will be removed when the codebase starts depending on `lsm-tree`. If `lsm-tree`'s CRC writer uses uppercase hex (a common default in many C/Haskell `printf`-style formatters using `%X`), every LSM-backend snapshot would be unreadable by consensus.
2. **`snapshot-converter` tool**: The `snapshot-converter` utility reads and writes snapshots across backends. If it produces uppercase hex in the checksum file, the converted snapshot is permanently rejected.
3. **Cross-platform or operator-generated files**: An operator manually creating or copying a checksum file using standard system tools (e.g., `sha256sum`, `crc32` utilities) that output uppercase hex would trigger the bug.

---

### Recommendation

Extend `isHexDigit` to cover both cases:

```haskell
isHexDigit :: Char -> Bool
isHexDigit c =
  (c >= '0' && c <= '9')
    || (c >= 'a' && c <= 'f')
    || (c >= 'A' && c <= 'F')
```

Additionally, fix `hexdigitToWord` to handle uppercase:

```haskell
hexdigitToWord :: Char -> Word
hexdigitToWord c
  | let !dec = fromIntegral (ord c - ord '0')
  , dec <= 9 = dec
  | c >= 'a' && c <= 'f'
  = fromIntegral (ord c - ord 'a' + 10)
  | otherwise
  = fromIntegral (ord c - ord 'A' + 10)
```

Alternatively, normalize the input to lowercase before validation and parsing, or use the standard `Data.Char.isHexDigit` (which covers both cases) that was explicitly hidden.

### Proof of Concept

A `.checksum` file containing `"A1B2C3D4"` (a valid CRC32 in uppercase hex) is placed at the path returned by `snapshotToChecksumPath` for a valid snapshot. On node startup, `readCRC` is called:

1. `BSC.all isHexDigit "A1B2C3D4"` → `False` (because `'A'`, `'B'`, `'C'`, `'D'` fail `isHexDigit`)
2. `readCRC` returns `Left CRCInvalid`
3. The snapshot loading path receives `CRCInvalid` and raises `ReadSnapshotDataCorruption`
4. The node discards the valid snapshot and re-syncs from genesis or an older snapshot

The same outcome occurs for any uppercase hex digit in the 8-character CRC string, covering 6 out of 16 possible hex digit values (`A`–`F`). [7](#0-6)
