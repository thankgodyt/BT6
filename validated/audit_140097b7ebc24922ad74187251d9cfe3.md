### Title
`ft_transfer` silently redirects tokens to the nbtc contract itself when `withdraw_relayer` is unset, permanently locking user funds - (File: `contracts/nbtc/src/lib.rs`)

### Summary

The `ft_transfer` implementation in the `nbtc` token contract overrides the standard NEP-141 `ft_transfer` to support a legacy Near Intents withdrawal flow. When the `withdraw_relayer` address is not configured, the function silently falls through and transfers tokens to `env::current_account_id()` (the nbtc contract itself) instead of reverting. If the nbtc contract account is registered in its own token ledger, the tokens are permanently locked with no recovery path.

### Finding Description

The `FungibleTokenCore` implementation of `ft_transfer` in `contracts/nbtc/src/lib.rs` contains a special branch for the legacy withdrawal flow:

```rust
fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
    // Legacy bridging flow used by Near Intents
    if receiver_id == env::current_account_id()
        && memo.as_ref().is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
    {
        if let Some(withdraw_relayer) = Self::read_withdraw_relayer_address() {
            return self.token.ft_transfer(withdraw_relayer, amount, memo);
        }
    }
    self.token.ft_transfer(receiver_id, amount, memo);   // ← executed when relayer is None
}
``` [1](#0-0) 

When both conditions of the outer `if` are satisfied (`receiver_id == nbtc_contract` and `memo` starts with `"WITHDRAW_TO:"`), but `read_withdraw_relayer_address()` returns `None`, the inner `if let` block is skipped entirely. Execution falls through to the unconditional `self.token.ft_transfer(receiver_id, amount, memo)` at the bottom, where `receiver_id` is still `env::current_account_id()` — the nbtc contract itself. [2](#0-1) 

The `set_withdraw_relayer_address` function is gated to the controller, so there is a deployment window (or a misconfiguration window) during which the relayer is unset. [3](#0-2) 

The nbtc contract's `new()` only registers `bridge_id` in the token ledger, not the contract itself. However, any account — including an attacker — can call the public `storage_deposit` to register the nbtc contract address as a token holder, enabling the silent transfer to succeed and permanently lock funds. [4](#0-3) 

### Impact Explanation

Once the nbtc contract account is registered in its own ledger (a permissionless action via `storage_deposit`), any user who calls `ft_transfer(nbtc_contract_id, amount, "WITHDRAW_TO:<btc_addr>")` while the `withdraw_relayer` is unset will have their nBTC permanently transferred into the nbtc contract's own balance. There is no `rescue`, `sweep`, or admin-withdrawal function in the nbtc contract that can recover tokens held by the contract account. The tokens are effectively burned from the user's perspective while remaining in the ledger, reducing the backed supply below the circulating supply.

This matches the **Medium** allowed impact: *permanent burning below backed supply* and *stuck bridge state requiring operator intervention*.

### Likelihood Explanation

The `withdraw_relayer` is an optional, controller-set address stored in raw contract storage. It is `None` at deployment and after any migration that does not explicitly re-set it. Any user of the Near Intents legacy flow who calls `ft_transfer` with the nbtc contract as receiver and a `WITHDRAW_TO:` memo during this window triggers the bug. An attacker can front-run by calling `storage_deposit` to register the nbtc contract account before the first such user transaction, ensuring the silent transfer succeeds rather than panicking.

### Recommendation

Inside the outer `if` block, when `read_withdraw_relayer_address()` returns `None`, the function must explicitly panic instead of falling through:

```rust
if receiver_id == env::current_account_id()
    && memo.as_ref().is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
{
    let withdraw_relayer = Self::read_withdraw_relayer_address()
        .unwrap_or_else(|| env::panic_str("Withdraw relayer not configured"));
    return self.token.ft_transfer(withdraw_relayer, amount, memo);
}
```

This mirrors the correct analog fix from the referenced report: instead of silently deviating, the standard interface function must either succeed with the intended operation or revert with a clear error.

### Proof of Concept

1. Deploy the nbtc contract (withdraw relayer is `None` by default).
2. Attacker calls `storage_deposit(nbtc_contract_id, ...)` to register the nbtc contract as a token holder.
3. User holds 100,000 nBTC and calls:
   ```
   ft_transfer(
     receiver_id = nbtc_contract_id,
     amount = 100000,
     memo = Some("WITHDRAW_TO:bc1q...")
   )
   ```
4. The outer `if` condition is satisfied; `read_withdraw_relayer_address()` returns `None`; the inner `if let` is skipped.
5. `self.token.ft_transfer(nbtc_contract_id, 100000, memo)` executes successfully (nbtc contract is registered).
6. User's 100,000 nBTC are now in the nbtc contract's own balance — permanently inaccessible. [1](#0-0)
