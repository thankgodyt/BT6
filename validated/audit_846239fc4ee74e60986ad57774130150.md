Audit Report

## Title
Failed `fin_transfer` Removes Replay Guard, Enabling Proof Replay and Double-Minting — (File: near/omni-bridge/src/lib.rs)

## Summary
When a `fin_transfer` to a NEAR recipient fails because the recipient's `ft_on_transfer` returns 0 (all tokens unused), `fin_transfer_send_tokens_callback` calls `remove_fin_transfer`, which permanently deletes the `TransferId` from `finalised_transfers`. This erases the sole replay-protection entry for that source-chain event, allowing the identical proof to be submitted again via `fin_transfer`. A single on-chain `InitTransfer` event can therefore cause multiple NEAR-side token mints or unlocks, breaking the 1:1 bridge invariant.

## Finding Description
`finalised_transfers: LookupSet<TransferId>` is the only replay guard for inbound NEAR-destined transfers. The `TransferId` is `(origin_chain, origin_nonce)` derived directly from the source-chain event.

**Step 1 — Guard inserted:** `process_fin_transfer_to_near` calls `add_fin_transfer` (L1875), which inserts the `TransferId` and panics with `BridgeError::TransferAlreadyFinalised` if it already exists (L2226–2234).

**Step 2 — Token delivery attempted:** `send_tokens` issues an `ft_transfer_call` when `msg` is non-empty. The result is inspected in `is_refund_required` (L1784–1803): if the promise result is a `U128` equal to `0`, the function returns `true`, meaning the recipient consumed no tokens.

**Step 3 — Guard deleted on failure:** In `fin_transfer_send_tokens_callback` (L1702–1718), when `is_refund_required` returns `true`, the code burns the minted tokens, reverts lock actions, and then calls `remove_fin_transfer` (L1714), which removes the `TransferId` from `finalised_transfers` (L2322–2333).

**Step 4 — Proof is now replayable:** Because `finalised_transfers` no longer contains the `TransferId`, a subsequent call to `fin_transfer` with the identical proof passes `add_fin_transfer` without reverting. `get_next_destination_nonce` always returns `0` for NEAR-destined transfers (L1816–1817), providing no additional protection. The bridge mints or unlocks tokens a second time.

The existing guard (`add_fin_transfer` panic on duplicate) is the only check, and it is rendered ineffective by `remove_fin_transfer` on the failure path.

## Impact Explanation
A single source-chain `InitTransfer` event (which locked or burned tokens exactly once on the origin chain) can cause the NEAR bridge to mint or unlock the same token amount multiple times. This constitutes unauthorized minting and escrow mis-accounting — unbacked tokens circulate on NEAR, directly causing loss of funds for the protocol. This matches the critical impact class: "unauthorized minting" and "nonce/replay misuse enabling invalid finalization or double-spending."

## Likelihood Explanation
`fin_transfer` requires the caller to hold the `trusted_relayer` role (L671), which is permissionless to obtain by staking NEAR and waiting the configured period (default 1000 NEAR, 7-day waiting period). The trigger condition — a recipient contract whose `ft_on_transfer` transiently rejects tokens (e.g., a DEX router at capacity, a vault under maintenance, or any contract with conditional acceptance logic) — is realistic and not contrived. Critically, the exploit path is the natural good-faith retry flow: a legitimate relayer observing a `FailedFinTransferEvent` and resubmitting the same proof after conditions change causes the double-mint without any malicious intent. The exploit is repeatable as many times as the failure/retry cycle can be induced.

## Recommendation
Do not remove the `TransferId` from `finalised_transfers` on failure. The replay guard must be permanent regardless of whether downstream token delivery succeeded. If retry with different `storage_deposit_actions` is desired, track the failure state separately (e.g., a `failed_transfers: LookupMap<TransferId, FailedTransferState>`) and allow the relayer to re-attempt delivery without re-verifying the proof. The `remove_fin_transfer` call at L1714 inside the `is_refund_required` branch of `fin_transfer_send_tokens_callback` must be removed; only the storage refund accounting needs to be handled differently.

## Proof of Concept
1. Deploy a NEAR recipient contract `receiver.near` whose `ft_on_transfer` rejects (returns full amount) when an internal capacity counter exceeds a threshold.
2. Alice initiates a transfer of 10,000 USDC from Ethereum. Relayer calls `fin_transfer` with the valid EVM proof. `add_fin_transfer` inserts `TransferId{Eth, nonce=42}`. Bridge mints 10,000 USDC and calls `ft_transfer_call` → `receiver.near::ft_on_transfer` → rejects (capacity full), returns `10000` unused.
3. `is_refund_required` returns `true`. `fin_transfer_send_tokens_callback` burns the minted tokens and calls `remove_fin_transfer`, deleting `TransferId{Eth, nonce=42}` from `finalised_transfers`.
4. `receiver.near` drains its balance (capacity now available).
5. Relayer resubmits the identical proof. `add_fin_transfer` succeeds (entry was deleted). Bridge mints another 10,000 USDC and delivers them to `receiver.near`.
6. Result: 20,000 USDC minted on NEAR from a single 10,000 USDC lock on Ethereum.

**Test plan:** Write a NEAR sandbox integration test using `near-workspaces`. Deploy a mock token, a mock recipient contract that rejects on first call and accepts on second, and the bridge. Register a trusted relayer. Call `fin_transfer` with a mock proof for `nonce=42` → observe `FailedFinTransferEvent`. Assert `finalised_transfers` no longer contains `{Eth, 42}`. Call `fin_transfer` again with the same proof → assert it succeeds and tokens are minted a second time. Assert total minted supply exceeds the single locked amount on the source chain.
