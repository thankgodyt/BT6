### Title
Malicious Slot Leader Can Omit Required Peras Certificate from Block Without Peer Detection — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Peras/Cert/Inclusion.hs`)

---

### Summary

The `needCert` function in `Peras/Cert/Inclusion.hs` defines when a Peras certificate **must** be included in a block per CIP-0140. This is a proposer-only local decision. No corresponding enforcement exists in the block validation path: receiving nodes have no mechanism to reject a block that omits a certificate that the inclusion rules require. A malicious slot leader can therefore silently skip certificate inclusion, and honest peers cannot detect or penalise this omission.

---

### Finding Description

`needCert` evaluates three conjunctive rules (`noCertsFromTwoRoundsAgo`, `latestCertSeenIsNotExpired`, `latestCertSeenIsNewerThanLatestCertOnChain`) and returns `IncludeCert` when all three hold, signalling that the forger **must** embed the latest seen certificate in the block it is building. [1](#0-0) 

This function is consumed exclusively by the block-forging path (the proposer's local loop). There is no symmetric validation call on the receiving side. The `BlockSupportsPeras` typeclass exposes `getPerasCertInBlock` to extract a certificate from an incoming block: [2](#0-1) 

However, the production instance unconditionally returns `Nothing` and carries an explicit TODO acknowledging that enforcement is absent: [3](#0-2) 

Neither `validateHeader` nor `updateChainDepState` nor `applyBlock` calls any function that checks whether an incoming block satisfies the certificate-inclusion obligation. The `needCert` logic is therefore a **proposer-only, unverifiable action**: exactly the vulnerability class of the reference report.

The parallel to the Allora `PrepareProposalHandler` HTTP call is direct:

| Allora | Ouroboros Consensus |
|---|---|
| HTTP call in `PrepareProposalHandler` | `needCert` / certificate embed in `forgeBlock` |
| Other nodes cannot verify the call was made | No validation of cert inclusion in received blocks |
| Malicious proposer skips the call | Malicious slot leader omits the certificate |
| `blockless` never receives the request | Certificate never reaches the chain |

---

### Impact Explanation

Peras certificates propagate to the chain exclusively through block bodies. When a slot leader omits a certificate that `needCert` requires, that certificate is never anchored on-chain. Honest nodes that later apply the block via `getPerasCertInBlock` (once implemented) will see no certificate and will not trigger the Peras chain-selection boost for the boosted block. Over multiple rounds this silently degrades Peras finality: the `PerasCertDB`-driven chain-selection weight (`chainSelSync` / `ChainSelAddPerasCert`) never fires for the suppressed certificate, so the honest chain loses the security boost that Peras is designed to provide. [4](#0-3) 

This maps to the **High** allowed impact: *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

---

### Likelihood Explanation

Any stake pool that wins a slot-leader election can exploit this. Slot leadership requires no majority stake — a single pool with modest stake is sufficient. The attack is passive (simply do not include the certificate) and leaves no detectable trace in the block, because the receiving path has no enforcement. The attack is therefore low-cost, low-risk, and repeatable across every slot the adversarial pool leads.

---

### Recommendation

1. **Enforce inclusion during block validation.** Add a check in the block-application path (e.g., inside `applyBlock` or a dedicated `validatePerasCertInclusion` step) that reconstructs the `PerasCertInclusionView` from the receiving node's own state and rejects blocks that omit a certificate when `needCert` returns `IncludeCert`.

2. **Complete `getPerasCertInBlock`.** The current stub `getPerasCertInBlock _ = Nothing` must be replaced with a real implementation before any enforcement is possible. [5](#0-4) 

3. **Consider a two-phase approach.** Because the inclusion rules depend partly on the proposer's local certificate view (which peers may not share), the enforcement check should be based on the on-chain state visible to all nodes (e.g., `latestCertOnChain` from the ledger) rather than the proposer's off-chain `latestCertSeen`. CIP-0140 should be consulted to confirm which sub-rules are verifiable by all peers.

---

### Proof of Concept

**Private-testnet sequence:**

1. Run a two-node private testnet with Peras enabled.
2. Allow a certificate for round `r` to be produced and gossiped (it reaches both nodes' `PerasCertDB`).
3. On the adversarial node, patch `forgeBlock` to ignore the `IncludeCert` decision returned by `needCert` and always produce a block with no certificate.
4. When the adversarial node wins a slot, it forges and broadcasts a block without the certificate.
5. The honest node calls `validateHeader` → `updateChainDepState` → `applyBlock`. None of these steps check for the missing certificate. The block is accepted.
6. Observe via `getLatestPerasCertOnChainRound` that the chain's latest on-chain certificate round has not advanced, even though a valid certificate for round `r` exists in the `PerasCertDB`.
7. Confirm that `chainSelSync` / `ChainSelAddPerasCert` does not trigger the Peras boost for the suppressed certificate, weakening chain selection security. [6](#0-5) [7](#0-6)

```haskell
-- | Evaluate whether we need to include a certificate in the block we are building.
needCert ::
  PerasCertInclusionView cert blk ->
  PerasCertInclusionRulesDecision cert
needCert pciv =
  evalPred (needCertRules pciv) $ \e ->
    case e of
      ETrue{} -> IncludeCert e (lcsCert (latestCertSeen pciv))
      EFalse{} -> DoNotIncludeCert e
```

```haskell
-- | We need to include a certificate in the block we are building if all the

needCertRules ::
  PerasCertInclusionView cert blk ->
  Pred PerasCertInclusionRule
needCertRules pciv =
  noCertsFromTwoRoundsAgo pciv
    :/\: latestCertSeenIsNotExpired pciv
    :/\: latestCertSeenIsNewerThanLatestCertOnChain pciv
```

```haskell
-- Process a Peras certificate by adding it to the PerasCertDB and potentially
-- performing chain selection if a candidate is now better than our selection.
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```

```haskell
validateHeader ::
  (BlockSupportsProtocol blk, ValidateEnvelope blk) =>
  TopLevelConfig blk ->
  LedgerView (BlockProtocol blk) ->
  Header blk ->
  Ticked (HeaderState blk) ->

validateHeader cfg ledgerView hdr st = do
  withExcept HeaderEnvelopeError $
    validateEnvelope
      cfg
      ledgerView
      (untickedHeaderStateTip st)
      hdr
  chainDepState' <-
    withExcept HeaderProtocolError $
      updateChainDepState
        (configConsensus cfg)
        (validateView (configBlock cfg) hdr)
        (blockSlot hdr)
        (tickedHeaderStateChainDep st)
```
