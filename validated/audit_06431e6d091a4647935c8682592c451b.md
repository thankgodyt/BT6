### Title
Native ETH `finTransfer` Permanently Broken Due to Incorrect `msg.value` Forwarding in `OmniBridgeWormhole.finTransferExtension` — (File: `evm/src/omni-bridge/contracts/OmniBridgeWormhole.sol`)

---

### Summary

`OmniBridgeWormhole.finTransferExtension` unconditionally forwards the full `msg.value` to Wormhole's `publishMessage`. For native ETH finalizations (`tokenAddress == address(0)`), `msg.value` must cover both the ETH amount sent to the recipient **and** the Wormhole fee. After the ETH amount is disbursed to the recipient inside `finTransfer`, the contract's remaining balance equals only the Wormhole fee — far less than `msg.value`. The subsequent `publishMessage{value: msg.value}` call therefore always reverts due to insufficient contract balance, making native ETH finalization permanently impossible and freezing users' ETH on NEAR.

---

### Finding Description

`OmniBridge.finTransfer` handles native ETH payouts when `payload.tokenAddress == address(0)`: [1](#0-0) 

```solidity
if (payload.tokenAddress == address(0)) {
    (bool success, ) = payload.recipient.call{value: payload.amount}("");
    if (!success) revert FailedToSendEther();
}
```

After this call, the contract's ETH balance is reduced by `payload.amount`. Control then passes to `finTransferExtension`: [2](#0-1) 

```solidity
function finTransferExtension(
    BridgeTypes.TransferMessagePayload memory payload
) internal override {
    ...
    _wormhole.publishMessage{value: msg.value}(   // ← full original msg.value
        wormholeNonce,
        messagePayload,
        _consistencyLevel
    );
}
```

`msg.value` here is the **original** call value, which for a native ETH transfer equals `payload.amount + wormholeFee`. After disbursing `payload.amount` to the recipient, the contract holds only `wormholeFee`. Attempting to forward `msg.value` (= `payload.amount + wormholeFee`) to Wormhole exceeds the available balance, causing an EVM revert. Because the entire transaction reverts, the nonce is not consumed, but the transfer can never succeed — every retry hits the same wall.

By contrast, `initTransferExtension` correctly computes a separate `value` parameter (`msg.value - nativeFee`) and passes only that to Wormhole: [3](#0-2) 

`finTransferExtension` lacks this separation entirely.

---

### Impact Explanation

Any user who bridges native ETH from NEAR to an EVM chain served by `OmniBridgeWormhole` will have their ETH permanently locked on NEAR. The EVM-side finalization always reverts; the NEAR-side lock is never released. This constitutes **permanent freezing of bridged funds**, which is explicitly within the critical impact scope.

---

### Likelihood Explanation

`OmniBridge.finTransfer` explicitly supports `tokenAddress == address(0)` (native ETH). `OmniBridgeWormhole` inherits this path unchanged. Every native ETH finalization attempt triggers the bug deterministically — no special attacker action is required. Any user initiating a native ETH bridge transfer is affected.

---

### Recommendation

Replace the hardcoded `msg.value` forwarding in `finTransferExtension` with the exact Wormhole fee:

```solidity
function finTransferExtension(
    BridgeTypes.TransferMessagePayload memory payload
) internal override {
    uint256 wormholeFee = _wormhole.messageFee();
    bytes memory messagePayload = ...;
    _wormhole.publishMessage{value: wormholeFee}(
        wormholeNonce,
        messagePayload,
        _consistencyLevel
    );
    wormholeNonce++;
}
```

Similarly audit `deployTokenExtension` and `logMetadataExtension` — they also pass `msg.value` directly, which is correct only because those callers send no ETH to recipients. Switching all three to `_wormhole.messageFee()` makes the intent explicit and eliminates the class of bug entirely. [4](#0-3) [5](#0-4) 

---

### Proof of Concept

1. `OmniBridgeWormhole` is deployed on Ethereum; Wormhole `messageFee()` = 10 000 wei.
2. User bridges 1 ETH of native ETH from NEAR → EVM.
3. Relayer calls `finTransfer(sig, payload)` with `msg.value = 1 ETH + 10 000 wei`.
4. `finTransfer` sends `1 ETH` to `payload.recipient` — contract balance drops to `10 000 wei`.
5. `finTransferExtension` executes `_wormhole.publishMessage{value: msg.value}(...)` where `msg.value = 1 ETH + 10 000 wei`.
6. EVM reverts: contract balance (`10 000 wei`) < forwarded value (`1 ETH + 10 000 wei`).
7. Entire transaction reverts; recipient receives nothing; nonce is not consumed.
8. Every subsequent relay attempt reproduces the same revert.
9. User's 1 ETH is permanently frozen on NEAR with no recovery path. [6](#0-5) [7](#0-6)
