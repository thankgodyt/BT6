### Title
Single Invalid Peras Vote/Certificate in a Batch Causes Entire Batch Rejection, Silently Dropping Valid Votes/Certificates — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasVote.hs` and `PerasCert.hs`)

---

### Summary

`processVotes` and `processCerts` use an all-or-nothing batch policy: if **any** item in an inbound batch fails validation, the **entire** batch is thrown away via an exception. A malicious peer can exploit this by sending a batch that mixes one crafted invalid vote/certificate with otherwise-valid items, causing valid Peras votes and certificates from honest committee members to be permanently dropped. Because Peras certificates directly boost chain-selection weight, suppressing certificate formation lets an adversary tilt chain selection away from the honest chain.

---

### Finding Description

`processVotes` in `PerasVote.hs` and `processCerts` in `PerasCert.hs` share the same batch-rejection pattern:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  -- Some certs are invalid => reject the whole batch
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [1](#0-0) 

The identical structure appears for votes: [2](#0-1) 

The code comment at line 174 of `PerasCert.hs` and line 190 of `PerasVote.hs` explicitly documents this as a deliberate design choice, referencing PR review [#1768](https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186), but the security consequence of permanently discarding co-batched valid items was not addressed.

The inbound path is wired directly into the production node-to-node handler:

```haskell
hPerasVoteDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound ... (makePerasVotePoolWriterFromChainDB ...) ...
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound ... (makePerasCertPoolWriterFromChainDB ...) ...
``` [3](#0-2) 

Any peer that connects over the ObjectDiffusion miniprotocol can send a batch. The `objectDiffusionInbound` handler calls `opwAddObjects` (which resolves to `processVotes`/`processCerts`) directly on the received batch. [4](#0-3) 

Peras certificates boost chain-selection weight: `wsvTotalWeight = blockNo + weightBoost`. Chain selection compares `wsvTotalWeight` values, so a chain whose certificate was dropped has a lower apparent weight than one whose certificate was accepted. [5](#0-4) 

When a certificate is added to the `PerasCertDB`, `chainSelSync` is triggered and may switch the node to a heavier chain: [6](#0-5) 

Suppressing certificate delivery therefore directly suppresses the chain-selection re-evaluation that would have favoured the honest chain.

---

### Impact Explanation

**High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain.**

Peras certificates assign weight boosts to specific blocks. An adversary who can prevent a node from receiving the certificate for the honest chain's tip block causes that node to see the honest chain as lighter than a competing chain that carries a certificate. The node then switches to the adversary's chain. This is a direct chain-selection manipulation that goes beyond the intended security assumptions of the Peras protocol, which assumes that valid certificates diffuse to all honest nodes.

The valid votes/certificates are permanently lost from the perspective of the receiving node for that round; they are not retried because the ObjectDiffusion protocol only delivers each object once per peer connection, and the peer is disconnected after the exception.

---

### Likelihood Explanation

**Medium.** Any peer that participates in the ObjectDiffusion miniprotocol can send a crafted batch. No stake, key material, or privileged access is required. The attacker only needs to:

1. Observe valid votes/certificates already circulating in the network (they are public gossip objects).
2. Construct one syntactically well-formed but semantically invalid item (e.g., a vote with a `pvVoteVoterId` not present in the stake distribution, which causes `validatePerasVote` to return `Left PerasValidationErr`).
3. Bundle it with the observed valid items in a single batch and send it to the target node.

The attacker is disconnected after the exception, but can reconnect immediately and repeat for the next round. The attack is most effective in the narrow time window of a Peras voting round, which is a bounded, predictable interval.

---

### Recommendation

Replace the all-or-nothing batch policy with per-item handling:

- In `processCerts`: replace `throw (PerasCertValidationError errs)` with logic that adds the valid subset (`validatedCerts` from `partitionEithers`) and logs or traces the invalid items. Disconnect the peer only if the protocol itself was violated (e.g., duplicate IDs), not merely because one certificate failed domain validation.
- Apply the same fix symmetrically to `processVotes`.
- Consider whether a peer sending even one invalid item warrants disconnection (current behaviour) or only a warning, given that valid items in the same batch are lost either way.

---

### Proof of Concept

**Setup:** Two nodes A (honest) and M (malicious), both connected to a victim node V.

1. Node A is a Peras committee member and produces a valid `PerasVote` `v_A` for round `r`, targeting the honest chain tip.
2. Node M observes `v_A` via the gossip network before V has received it.
3. M constructs an invalid vote `v_bad` with a `pvVoteVoterId` that is absent from the current stake distribution (so `validatePerasVote` returns `Left PerasValidationErr`).
4. M opens an ObjectDiffusion connection to V and sends the batch `[v_A, v_bad]`.
5. V calls `processVotes [v_A, v_bad]`. `partitionEithers` yields `([PerasValidationErr], [validatedV_A])`. The `(errs, _)` branch fires and throws `PerasVoteInboundException`, discarding `v_A`. [7](#0-6) 

6. M is disconnected. V never accumulates enough votes for round `r` to reach quorum; no certificate is formed for the honest chain tip.
7. M's own chain, for which M has ensured a certificate exists (by not poisoning its own cert delivery), now has a higher `wsvTotalWeight` at V.
8. V's chain selection, triggered by the next block arrival, compares weights and switches to M's chain. [8](#0-7)

-- Process a Peras certificate by adding it to the PerasCertDB and potentially
-- performing chain selection if a candidate is now better than our selection.
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
