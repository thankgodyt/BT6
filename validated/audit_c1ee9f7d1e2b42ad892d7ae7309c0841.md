Audit Report

## Title
Malformed `recipient` in EVM `initTransfer` permanently freezes bridged tokens — (`evm/src/omni-bridge/contracts/OmniBridge.sol`, `near/omni-types/src/evm/events.rs`)

## Summary
`OmniBridge.initTransfer` accepts an arbitrary `string calldata recipient` with no format validation, burns or locks the caller's tokens, and emits the event. When the EVM prover later parses the log, it calls `OmniAddress::from_str` on that raw string; any parse failure causes the prover promise to fail, which causes `fin_transfer_callback` to panic with `InvalidProofMessage` before recording any transfer. The EVM-locked or burned tokens have no on-chain recovery path and are permanently frozen.

## Finding Description
`OmniBridge.initTransfer` performs no validation on the `recipient` string before burning or locking tokens and emitting `BridgeTypes.InitTransfer`: [1](#0-0) 

The EVM prover's `TryFromLog` implementation for `InitTransferMessage` calls `.parse()` on the raw recipient string, propagating any error as `Err`: [2](#0-1) 

`OmniAddress::from_str` returns `Err` for any unknown chain prefix and for invalid address bytes on known chains: [3](#0-2) 

`verify_proof_callback` is decorated with `#[handle_result]` and calls `parse_evm_proof`, which propagates the `Err` — causing the prover promise to fail: [4](#0-3) 

`fin_transfer_callback` uses a `let Ok(...)` guard that panics on a failed prover promise, before any transfer record is written: [5](#0-4) 

No cancellation or refund path exists. The same parse-and-propagate pattern is present in the Wormhole prover path (`near/omni-prover/wormhole-omni-prover-proxy/src/parsed_vaa.rs:173`) and the Starknet prover path (`near/omni-types/src/starknet/events.rs:61`).

## Impact Explanation
Permanent freezing of bridged funds. Any user who calls `initTransfer` with a recipient string that is valid UTF-8 but not a valid `OmniAddress` (e.g., `"!!!invalid!!!"`, `"eth:0xGGGG..."`, `"near:INVALID!!!"`) will have their tokens burned or locked on EVM with no possibility of finalization or recovery on NEAR. This matches the Critical allowed impact: *permanent freezing of bridged funds*.

## Likelihood Explanation
Any unprivileged external user can call `initTransfer` directly. A deliberate attacker can pass an invalid recipient to destroy their own tokens (or grief themselves). More critically, a user who makes a typo in the recipient address (e.g., a non-hex character in an EVM address, or an invalid NEAR account ID) will permanently lose funds. The EVM contract provides no guard whatsoever, and the `#[trusted_relayer]` restriction on `fin_transfer` does not mitigate this — even if a relayer attempts finalization, it will always fail for such transfers.

## Recommendation
Add recipient format validation in `OmniBridge.initTransfer` on the EVM side before burning or locking tokens. Since Solidity cannot run `OmniAddress::from_str`, the minimal fix is to validate that the `recipient` string matches the expected `chain:address` pattern (e.g., a whitelist of valid chain prefixes with length and character constraints). Alternatively — or additionally — `fin_transfer_callback` should handle a failed prover promise gracefully (log and return rather than panic), so that the transfer can be retried or administratively cancelled, and a corresponding on-chain cancellation/refund mechanism should be added for EVM-originated transfers whose finalization permanently fails.

## Proof of Concept
1. Deploy the EVM bridge on a local testnet.
2. Call `initTransfer(tokenAddress, amount, fee, 0, "!!!invalid!!!", "")` — tokens are burned, `InitTransfer` event emitted with `recipient = "!!!invalid!!!"`.
3. Confirm tokens are deducted from the caller's balance.
4. Submit the EVM proof to NEAR `fin_transfer`. The EVM prover calls `parse_evm_proof` → `event.data.recipient.parse()` → `OmniAddress::from_str("!!!invalid!!!")` → `Err("Chain !!! is not supported")` → prover promise fails.
5. `fin_transfer_callback` hits the `let Ok(...)` guard, panics with `InvalidProofMessage`. No transfer record is written to `pending_transfers`. Tokens are permanently frozen with no recovery path.
