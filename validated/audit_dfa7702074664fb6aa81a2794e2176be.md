Audit Report

## Title
Missing Freeze Authority Validation on Native Token Mint Allows Permanent Freezing of Bridge Vault Funds — (`solana/programs/bridge_token_factory/src/instructions/user/log_metadata.rs`)

## Summary
The `log_metadata` instruction registers a native Solana token and creates a PDA vault without verifying that the mint's `freeze_authority` is `None`. Any token creator can register a mint that retains a freeze authority, accumulate user funds in the vault via `init_transfer`, then call SPL Token's `freeze_account` on the vault PDA, permanently trapping all deposited tokens and blocking all future transfers for that token.

## Finding Description
In `log_metadata.rs` (L41–44), the only constraint on the mint is:

```rust
#[account(
    constraint = !mint.mint_authority.contains(authority.key),
    mint::token_program = token_program,
)]
pub mint: Box<InterfaceAccount<'info, Mint>>,
```

There is no check that `mint.freeze_authority.is_none()`. The vault PDA is then initialized at L50–62 with `token::authority = authority` (the bridge's PDA), but SPL Token's freeze authority is independent of token account ownership — the freeze authority of a mint can call `freeze_account` on **any** associated token account, including PDAs owned by other programs.

Once the vault is frozen:

- `init_transfer` (L88–102 of `init_transfer.rs`) calls `transfer_checked(..., from: self.from, to: vault, ...)` — this fails with `AccountFrozen`.
- `finalize_transfer` (L101–116 of `finalize_transfer.rs`) calls `transfer_checked(..., from: vault, to: self.token_account, ...)` — this also fails with `AccountFrozen`.

In `finalize_transfer`, the nonce is consumed via `UsedNonces::use_nonce` at L91–99 **before** the transfer. Because Solana transactions are atomic, a frozen-vault failure reverts the entire transaction, so the nonce is not consumed on-chain. However, the NEAR-side burn that triggered the `finalize_transfer` is already irreversible, meaning users who burned NEAR-side assets lose them permanently.

The bridge program contains no `thaw_account` instruction and no admin escape hatch for frozen vaults.

## Impact Explanation
This directly matches the Critical allowed impact: **permanent freezing of bridged funds**. Tokens deposited via `init_transfer` into a frozen vault are permanently inaccessible. Users who initiated NEAR → Solana transfers (burning NEAR-side assets) cannot finalize them and cannot recover their funds. The bridge is fully halted for the affected token with no on-chain recovery path.

## Likelihood Explanation
`log_metadata` is permissionless — any caller can invoke it for any mint satisfying the single existing constraint. A malicious token issuer deploys a mint with a retained freeze authority, calls `log_metadata` (the constraint `!mint.mint_authority.contains(authority.key)` passes trivially since the attacker's key differs from the bridge authority PDA), waits for meaningful value to accumulate in the vault, then calls `freeze_account`. No admin compromise, no key leakage, and no bridge-operator action is required. The freeze authority is a standard, publicly visible field on the mint account.

## Recommendation
Add a freeze authority constraint to the `mint` account in `LogMetadata`:

```rust
#[account(
    constraint = !mint.mint_authority.contains(authority.key),
    constraint = mint.freeze_authority.is_none() @ ErrorCode::FreezeAuthorityNotAllowed,
    mint::token_program = token_program,
)]
pub mint: Box<InterfaceAccount<'info, Mint>>,
```

This prevents any mint with an active freeze authority from being registered as a native bridge token.

## Proof of Concept
1. Attacker deploys SPL Token mint `M` with `freeze_authority = ATTACKER_KEY` and `mint_authority ≠ bridge_authority_PDA`.
2. Attacker (or anyone) calls `log_metadata` with mint `M`. The constraint passes; vault PDA `V = PDA([VAULT_SEED, M])` is created.
3. Legitimate users call `init_transfer` with mint `M`, depositing tokens into `V`. NEAR-side processes the Wormhole messages.
4. Attacker calls SPL Token's `freeze_account(account: V, authority: ATTACKER_KEY)`. Vault `V` is now frozen.
5. Any `finalize_transfer` routing through `V` calls `transfer_checked(from: V, ...)` and receives `AccountFrozen`; the transaction reverts atomically. The NEAR-side burn is already final — users lose their assets.
6. All tokens in `V` are permanently inaccessible. `init_transfer` for mint `M` also fails, halting all bridge activity for that token.

A local integration test can demonstrate this by: (a) creating a mint with freeze authority, (b) calling `log_metadata`, (c) depositing via `init_transfer`, (d) calling `freeze_account` on the vault PDA, and (e) asserting that both `init_transfer` and `finalize_transfer` return `AccountFrozen`.
