### Title
Unconditional `validatePerasCert` Acceptance Lets Any Peer Manipulate Peras Chain-Selection Weights - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance used for all block types unconditionally accepts every inbound Peras certificate from any peer without performing any cryptographic or structural validation. Because the accepted certificate's `pcCertBoostedBlock` field is taken verbatim from the peer-supplied message and inserted into the `PerasWeightSnapshot` used by chain selection, an unprivileged peer can craft a certificate that artificially boosts any block in the VolatileDB, causing the node to prefer a non-canonical adversarial chain.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must be passed before a peer-supplied `PerasCert` is stored and acted upon. The degenerate instance that covers all block types (including `CardanoBlock`) is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This function **always returns `Right`** regardless of the certificate's content. [1](#0-0) 

The inbound certificate processing pipeline in `processCerts` calls this validator and, on `Right`, immediately timestamps and stores the certificate:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [2](#0-1) 

The production-facing pool writer that feeds the ChainDB uses this same validator:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [3](#0-2) 

Once stored, `addPerasCertAsync` enqueues the certificate for `chainSelSync`, which reads the `PerasWeightSnapshot` and triggers `chainSelectionForBlock` for the boosted block:

```haskell
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

Chain selection computes `wsvTotalWeight` as `blockNo + weightBoost`, where `weightBoost` is the sum of all certificate boosts for blocks in the candidate fragment:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [5](#0-4) 

A candidate with a higher `wsvTotalWeight` than the current chain causes a chain switch:

```haskell
preferCandidate cfg ours cand =
  case compare (wsvTotalWeight ours) (wsvTotalWeight cand) of
    LT -> ShouldSwitch (Heavier $ ...)
``` [6](#0-5) 

---

### Impact Explanation

An unprivileged peer can send one or more crafted `PerasCert` messages whose `pcCertBoostedBlock` points to blocks on an adversarial fork. Because `validatePerasCert` never rejects any certificate, each crafted certificate is accepted, stored, and its weight boost is added to the `PerasWeightSnapshot`. If the accumulated boost on the adversarial fork's blocks raises its `wsvTotalWeight` above the honest chain's total weight, the node switches to the adversarial chain — accepting an invalid or non-canonical ledger state. This is a **High** chain-selection bug: an unprivileged peer can make an honest node prefer a non-canonical chain beyond the intended security assumptions of the Peras weight mechanism.

---

### Likelihood Explanation

The ObjectDiffusion mini-protocol for Peras certificates is a standard peer-to-peer channel. Any connected peer can send arbitrary `PerasCert` messages. The degenerate instance is the only `BlockSupportsPeras` instance in the codebase (it covers all `StandardHash blk` types, including `CardanoBlock`), and the production pool writer explicitly uses it with a `TODO` comment acknowledging the missing validation. The attack requires only a network connection and knowledge of a block hash in the target node's VolatileDB — both trivially obtainable via the ChainSync protocol.

---

### Recommendation

Replace the unconditional `Right` in `validatePerasCert` with real validation before the Peras certificate diffusion path is enabled in production. At minimum, the certificate must be checked for:
1. A valid BLS aggregate signature over the claimed committee votes.
2. That the `pcCertBoostedBlock` corresponds to a block that was actually eligible for boosting in the claimed round (slot range, era, committee membership).
3. That the round number is within the acceptable window relative to the current chain tip.

Until real validation is implemented, the ObjectDiffusion inbound handler for Peras certificates should not be wired into the production ChainDB path.

---

### Proof of Concept

**Attacker-controlled entry path:**

1. Peer connects to the target node via the ObjectDiffusion mini-protocol (standard NtN connection).
2. Peer sends a `PerasCert` message:
   ```
   PerasCert { pcCertRound = <any round>, pcCertBoostedBlock = <hash of adversarial fork block> }
   ```
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }`.
4. Certificate is stored in `PerasCertDB`; `addPerasCertAsync` enqueues a `ChainSelAddPerasCert` message.
5. `chainSelSync` reads the updated `PerasWeightSnapshot` (now containing the boost for the adversarial block) and calls `chainSelectionForBlock` for that block.
6. `preferAnchoredCandidate` computes `wsvTotalWeight` for the adversarial candidate. If `blockNo(adversarial tip) + boost > blockNo(honest tip)`, `ShouldSwitch` is returned and the node adopts the adversarial chain.

**Necessary vulnerable step:** `validatePerasCert` at [7](#0-6)  is the sole gate between a peer-supplied certificate and the `PerasWeightSnapshot` that drives chain selection. Its unconditional `Right` is the direct root cause.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
