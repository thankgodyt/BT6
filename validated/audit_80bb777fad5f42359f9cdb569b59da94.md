### Title
Unchecked `PostAction.msg` Content When No Templates Are Configured for a Whitelisted Receiver — (File: `contracts/satoshi-bridge/src/deposit_msg.rs`)

### Summary
`check_deposit_msg` enforces a receiver-ID whitelist for `PostAction` entries but only validates the `msg` field against `post_action_msg_templates` when templates have been explicitly configured for that receiver. When a receiver is whitelisted but has no templates registered, the `msg` field is accepted without any content check, allowing any unprivileged depositor to pass arbitrary cross-contract call instructions to the whitelisted receiver contract.

### Finding Description
`check_deposit_msg` in `contracts/satoshi-bridge/src/deposit_msg.rs` performs two security checks on each `PostAction`:

1. The `receiver_id` must be present in `post_action_receiver_id_white_list`.
2. The `msg` must match a registered template in `post_action_msg_templates` — **but only if** an entry for that receiver exists in the map. [1](#0-0) 

The conditional `if let Some(msg_templates) = self.data().post_action_msg_templates.get(&post_action.receiver_id)` means that when the DAO adds a receiver to the whitelist without also calling `extend_post_action_msg_templates` for it, the entire `msg` validation block is silently skipped. Any string — including one that triggers unintended operations on the receiver — passes validation.

The validated (or unvalidated) `post_actions` are forwarded through the deposit pipeline: [2](#0-1) 

They are then passed to `nbtc.mint`, which calls `handle_post_actions`: [3](#0-2) 

`handle_post_action` performs an `internal_transfer` and then calls `ft_on_transfer` on the receiver with the unvalidated `msg`: [4](#0-3) 

The management API confirms that whitelisting a receiver and registering its templates are two independent, optional DAO operations: [5](#0-4) [6](#0-5) 

There is no enforcement that templates must be configured before a receiver is usable.

### Impact Explanation
Any user can embed a `DepositMsg` with `post_actions` targeting a whitelisted-but-template-less receiver and supply an arbitrary `msg`. After the BTC deposit is verified on-chain, the bridge mints nBTC and immediately calls `ft_on_transfer` on the receiver with the attacker-controlled `msg`. For a DEX receiver this allows setting `min_amount_out = 0` and redirecting swap output to an attacker-controlled address; for a lending protocol it allows triggering unintended borrow/supply actions under the `recipient_id` account. The `recipient_id` can be set to any NEAR account, meaning the attacker can use a victim's account as the `sender_id` in the receiver's `ft_on_transfer` call, causing the victim's freshly minted nBTC to be consumed by an attacker-crafted instruction. This constitutes a bypass of the bridge's `msg`-template policy and can result in loss of the nBTC allocated to the `post_action`.

### Likelihood Explanation
The DAO must whitelist a receiver before it is usable, but there is no on-chain enforcement requiring templates to be set at the same time. Operational deployments that add a new integration (e.g., a DEX or lending protocol) to the whitelist before configuring templates — a common incremental rollout pattern — are immediately exploitable by any depositor. The attack requires only a valid BTC deposit to the address derived from the malicious `DepositMsg`; no privileged role or leaked key is needed.

### Recommendation
Enforce that `post_action_msg_templates` contains at least one entry for a receiver before it may be used in a `PostAction`. In `check_deposit_msg`, replace the optional `if let Some(...)` guard with a mandatory lookup that rejects any `PostAction` whose `receiver_id` has no registered templates:

```rust
let msg_templates = match self.data().post_action_msg_templates.get(&post_action.receiver_id) {
    Some(t) => t,
    None => {
        Event::InvalidPostAction { index: Some(index), err_msg: "No msg templates configured for receiver.".to_string() }.emit();
        return None;
    }
};
// existing is_match check against msg_templates ...
```

Alternatively, require `extend_post_action_msg_templates` to be called atomically with `extend_post_action_receiver_id_white_list`.

### Proof of Concept

1. DAO calls `extend_post_action_receiver_id_white_list(["dex.near"])` but does **not** call `extend_post_action_msg_templates` for `dex.near`.
2. Attacker constructs:
   ```json
   {
     "recipient_id": "victim.near",
     "post_actions": [{
       "receiver_id": "dex.near",
       "amount": "100000",
       "msg": "{\"actions\":[{\"pool_id\":0,\"token_in\":\"nbtc\",\"min_amount_out\":\"0\",\"token_out\":\"usdc\",\"to\":\"attacker.near\"}]}",
       "gas": "50000000000000"
     }]
   }
   ```
3. Attacker derives the deposit address from this `DepositMsg` via `get_deposit_path` and sends BTC to it.
4. A relayer calls `verify_deposit_v2` with the attacker's `DepositMsg`.
5. `check_deposit_msg` passes: `dex.near` is whitelisted; the `if let Some(msg_templates)` block is skipped because no templates exist.
6. After light-client verification, `nbtc.mint` is called with the `post_actions`; `handle_post_action` transfers 100 000 nBTC from `victim.near` to `dex.near` and calls `ft_on_transfer("victim.near", 100000, "{...attacker msg...}")`.
7. The DEX executes the swap with `min_amount_out = 0` and sends USDC output to `attacker.near`. [7](#0-6) [4](#0-3)

    #[private]
    pub fn handle_post_action(
        &mut self,
        sender_id: AccountId,
        receiver_id: AccountId,
        amount: U128,
        memo: Option<String>,
        msg: String,
    ) {
        require!(
            env::prepaid_gas() > GAS_FOR_FT_TRANSFER_CALL,
            "More gas is required"
        );
        require!(
            receiver_id != self.bridge_id,
            "handle_post_action: receiver_id must not be the bridge"
        );
        let amount = amount.into();
        self.token
            .internal_transfer(&sender_id, &receiver_id, amount, memo);
        let receiver_gas = env::prepaid_gas()
            .checked_sub(GAS_FOR_FT_TRANSFER_CALL)
            .unwrap_or_else(|| env::panic_str("Prepaid gas overflow"));
        // Initiating receiver's call and the callback
        ext_ft_receiver::ext(receiver_id.clone())
            .with_static_gas(receiver_gas)
            .ft_on_transfer(sender_id.clone(), amount.into(), msg)
            .then(
                ext_ft_resolver::ext(env::current_account_id())
                    .with_static_gas(GAS_FOR_RESOLVE_TRANSFER)
                    .ft_resolve_transfer(sender_id, receiver_id, amount.into()),
            )
            .detach();

    pub fn extend_post_action_msg_templates(
        &mut self,
        contract_id: AccountId,
        templates: HashSet<String>,
    ) {
        assert_one_yocto();
        require!(!templates.is_empty(), "empty templates.");
        if let Some(msg_templates) = self
            .data_mut()
            .post_action_msg_templates
            .get_mut(&contract_id)
        {
            for template in templates {
                let is_success = msg_templates.insert(template.clone());
                require!(is_success, format!("{:?} is exist.", template));
            }
        } else {
            self.data_mut()
                .post_action_msg_templates
                .insert(contract_id, templates);
        }
    }
