### Title
Hardcoded `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` Causes Incorrect Chain Preference Decisions Under Peras — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

`checkPreferTheirsOverOurs` in the ChainSync client unconditionally passes `emptyPerasWeightSnapshot` (an empty, zero-weight collection) to `preferAnchoredCandidate` instead of the live Peras weight snapshot. When Peras is active and certificates have boosted blocks on either the local or candidate chain, this function makes chain preference decisions as if no Peras boosts exist. The result is that the node either (a) incorrectly disconnects from an honest peer offering a legitimately heavier Peras-boosted chain, or (b) incorrectly retains a connection to a peer offering a longer-but-lighter chain it should reject. This is a direct analog to the SafEth "empty derivatives" bug: a critical operation proceeds with an empty/uninitialized collection instead of the actual populated state, silently producing wrong behavior.

---

### Finding Description

`checkPreferTheirsOverOurs` is called inside `readLedgerStateHelper` whenever a received header is beyond the current forecast horizon. Its purpose is to decide whether the peer's candidate chain is still preferred over the node's current chain; if not, the node disconnects with `CandidateTooSparse`. The function calls `preferAnchoredCandidate` with a hardcoded `emptyPerasWeightSnapshot`: [1](#0-0) 

The code itself acknowledges this is wrong with an inline TODO: [2](#0-1) 

`preferAnchoredCandidate` branches on `isEmptyPerasWeightSnapshot weights`. When the snapshot is empty it falls into the non-Peras path and compares chains purely by block count (length). When the snapshot is non-empty it uses `weightedSelectView`, which accounts for certificate-granted boosts: [3](#0-2) 

The live Peras weight snapshot is available via `getPerasWeightSnapshot` on the `ChainDB` API and is already read and used correctly in every other chain-selection call site (e.g., `chainSelSync`, `chainSelAddBlock`, the BlockFetch `readChainComparison`): [4](#0-3) 

`checkPreferTheirsOverOurs` is the sole call site that ignores it.

---

### Impact Explanation

**Scenario A — Incorrect disconnection from an honest peer (higher severity):**

1. Peras is active. A certificate has boosted block B on the peer's candidate chain, making that chain heavier than the local chain even though it has fewer blocks.
2. The peer sends a header H beyond the local forecast horizon.
3. `readLedgerStateHelper` calls `checkPreferTheirsOverOurs`.
4. With `emptyPerasWeightSnapshot`, `preferAnchoredCandidate` compares only block counts. The peer's chain is shorter → `ShouldNotSwitch` → the node throws `CandidateTooSparse` and disconnects.
5. The node has now disconnected from the honest peer offering the correct, heavier Peras chain. It will not adopt that chain until it reconnects and re-syncs, during which time it may select a less-secure chain.

**Scenario B — Incorrect retention of a connection to a lighter chain:**

1. A certificate has boosted block B on the local chain, making the local chain heavier.
2. A peer offers a longer-but-lighter chain (more blocks, no Peras boost).
3. `checkPreferTheirsOverOurs` sees the peer's chain as longer → `ShouldSwitch` → the node keeps waiting for the forecast horizon to advance.
4. The node wastes resources waiting for a chain it should have rejected, and may eventually adopt it if the forecast horizon advances.

Both scenarios cause the node to make chain preference decisions inconsistent with the Peras security model, which is precisely the invariant Peras is designed to enforce.

---

### Likelihood Explanation

- **Reachable by any unprivileged peer**: Any peer can send headers beyond the forecast horizon; this is a normal ChainSync operation.
- **Triggered automatically**: The bug fires whenever `prj lst == Nothing` (forecast horizon not yet reached) and the peer's chain has a different Peras-weight relationship to the local chain than its block-count relationship.
- **Peras deployment**: Once Peras certificates are issued on mainnet, boosted blocks will exist and this code path will produce incorrect results on every node.
- **No special attacker capability required**: An honest peer offering the correct Peras-boosted chain is sufficient to trigger Scenario A.

---

### Recommendation

Replace the hardcoded `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the actual live Peras weight snapshot, consistent with every other chain-selection call site. The snapshot should be read from the `ChainDB` view (already available in the `ConfigEnv` or `DynamicEnv` passed to the ChainSync client) and passed into `preferAnchoredCandidate`:

```haskell
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        liveWeights   -- use actual snapshot, not emptyPerasWeightSnapshot
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
```

where `liveWeights` is obtained from `forgetFingerprint <$> getPerasWeightSnapshot chainDB` (already available in the `ChainDbView`).
