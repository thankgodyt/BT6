### Title
Unauthenticated `request_refund` Allows Any Caller to Redirect Another User's BTC Deposit to an Attacker-Controlled Address — (File: `contracts/satoshi-bridge/src/api/bridge.rs`, `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`request_refund` is a public, permissionless function that accepts a caller-supplied `refund_address` without verifying that the caller owns or is authorized to act on the deposit identified by `deposit_msg`. An unprivileged attacker can submit a refund request for any unverified BTC deposit, specifying their own BTC address as the destination. After the timelock elapses (and if the DAO/Operator does not reject the request), `execute_refund` will route the victim's BTC to the attacker.

---

### Finding Description

`request_refund` in `contracts/satoshi-bridge/src/api/bridge.rs` (lines 507–535) accepts three caller-controlled inputs: `deposit_msg` (which identifies whose deposit is being refunded), `refund_address` (the BTC address to send funds to), and the on-chain proof. There is no check that `env::predecessor_account_id()` matches the NEAR account embedded in `deposit_msg`. [1](#0-0) 

The only guard against a mismatched `refund_address` is in `request_refund_callback` (refund.rs lines 154–158): if `deposit_msg.refund_address` is `Some`, the provided `refund_address` must match. But when `deposit_msg.refund_address` is `None` — the common case for standard deposits — the caller may supply any BTC address: [2](#0-1) 

The stored `RefundRequest` then permanently records the attacker's `refund_address`: [3](#0-2) 

After the `unsafe_refund_timelock_sec` elapses, `execute_refund` (bridge.rs line 582) is also permissionless — anyone can call it — and it uses the stored `refund_address` to build the BTC output: [4](#0-3) [5](#0-4) 

The `resolve_execute_refund_timelock` function acknowledges the risk with a longer `unsafe_refund_timelock_sec` for caller-supplied addresses, but this is only a delay — not a prevention: [6](#0-5) 

---

### Impact Explanation

An attacker can permanently redirect a victim's BTC deposit to an attacker-controlled Bitcoin address. The bridge's MPC signing pipeline will sign and broadcast a transaction paying the attacker. The victim loses their BTC entirely. This is a direct, irreversible theft of bridge-controlled funds, matching the Critical impact class: *Significant loss or theft of user funds* and *unauthorized release of bridge-controlled BTC*.

---

### Likelihood Explanation

- BTC deposits to bridge addresses are publicly visible on the Bitcoin blockchain.
- The `deposit_msg` is derivable from the depositor's NEAR account ID (a public identifier), and the bridge exposes `get_user_deposit_address` as a public view function to verify the mapping.
- The only cost to the attacker is the storage deposit required by `request_refund` (an anti-spam fee, not a meaningful deterrent for a BTC theft).
- The DAO/Operator rejection window is the sole mitigation, but it requires continuous monitoring. A single missed window is sufficient for the attack to succeed.
- Any deposit that is delayed in verification (e.g., relayer downtime, congestion, or a deposit the user genuinely wants to refund) is a target.

Likelihood: **Medium** (requires DAO inaction during the timelock window, but the attack surface is always open for unverified deposits).

---

### Recommendation

Add an ownership check in `request_refund` (or `request_refund_callback`) that asserts `env::predecessor_account_id()` equals the NEAR account embedded in `deposit_msg`. Alternatively, require that `deposit_msg.refund_address` always be pre-set (i.e., disallow the `None` path for caller-supplied addresses entirely), so the BTC destination is committed at deposit time and cannot be overridden by a third party.

---

### Proof of Concept

1. Alice sends 1 BTC to her bridge deposit address (derived from her NEAR account `alice.near` and her `deposit_msg`).
2. The relayer has not yet called `verify_deposit` (e.g., waiting for confirmations).
3. Bob (attacker) observes the BTC transaction on-chain, reconstructs Alice's `deposit_msg` from her public NEAR account ID, and calls:
   ```
   request_refund(
     deposit_msg = alice_deposit_msg,   // deposit_msg.refund_address = None
     refund_address = "bob_btc_address",
     tx_bytes = <alice's deposit tx>,
     vout = 0,
     proof = <valid merkle proof>,
     gas_fee = None
   )
   ```
   with the required storage deposit attached.
4. `request_refund_callback` verifies the proof, finds `deposit_msg.refund_address == None`, and stores `refund_address = "bob_btc_address"` in the `RefundRequest`.
5. After `unsafe_refund_timelock_sec` elapses (and if the DAO does not reject), Bob calls `execute_refund(utxo_storage_key, None)`.
6. The bridge builds a PSBT paying 1 BTC (minus gas fee) to `bob_btc_address`, requests an MPC signature, and broadcasts the transaction.
7. Alice's BTC is permanently transferred to Bob.

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
