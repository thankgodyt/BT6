### Title
`hashVoteSignature` Does Not Commit to `pvSeatIndex`, Enabling Cross-Seat Vote Replay - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Peras/Crypto/BLS.hs`)

---

### Summary

The `hashVoteSignature` function that produces the BLS-signed message for every Peras vote omits the voter's seat index (`pvSeatIndex`). Because a non-persistent committee member can hold multiple seats—all backed by the same public key—an on-path adversary who intercepts one valid vote can replay its signature under every other seat the same voter holds, manufacturing additional valid votes without possessing the voter's private key. This enables fraudulent quorum for a block that would not otherwise reach it.

---

### Finding Description

`hashVoteSignature` in `BLS.hs` constructs the signed message as a fixed-width concatenation of three fields only:

```
roundNoBytes (8 B) || boostedBlockSlotBytes (8 B) || boostedBlockHashBytes (32 B)
``` [1](#0-0) 

The concrete `PerasVote` wire type carries five fields:

```
pvRoundNo | pvBoostedBlock | pvSeatIndex | pvEligibilityProof | pvSignature
``` [2](#0-1) 

`pvSeatIndex` is serialised and transmitted with the vote but is **never included in the signed hash**. The comment on `pvSignature` even acknowledges the omission implicitly: *"BLS signature on the hash of the election identifier and vote message"*—the seat index is not part of the message. [3](#0-2) 

In the WFALS committee scheme, a non-persistent voter's number of seats is computed from their VRF output and stake via `localSortitionNumSeats`. A voter with high stake or a favourable VRF output can hold several consecutive seat indices, **all of which resolve to the same public key** in the committee's extended stake distribution array. [4](#0-3) 

Vote verification in `implVerifyVote` uses `seatIndex` only to look up the voter's public key; it then verifies the signature against that key. Because the same key is stored at every seat the voter holds, a signature produced for seat *i* passes verification when presented under seat *j* (same voter, different seat index). [5](#0-4) 

The same gap exists in the aggregate-certificate path: `verifyAggregateVoteSignature` calls `hashVoteSignature` with only `electionId` and `candidate`; the voter map (keyed by seat index) is never committed to the signed message. [6](#0-5) 

---

### Impact Explanation

An adversary who intercepts a single valid `PerasVote` from a non-persistent committee member holding *N* seats can produce *N − 1* additional structurally valid votes—one per remaining seat—by copying the BLS signature verbatim and substituting a different `pvSeatIndex`. Each replayed vote passes `implVerifyVote` independently. Aggregating these votes into a certificate allows the adversary to forge a Peras certificate for a block that has not genuinely reached quorum, causing honest nodes to boost that block in chain selection. This is a bypass of Peras vote-signature validation that enables unauthorized vote acceptance and materially weakens the quorum guarantee of the Peras boosting mechanism.

---

### Likelihood Explanation

The attacker must be on-path for Peras vote gossip (e.g., a malicious relay node or a peer that the victim connects to). No private key material is required; only one intercepted vote is needed. The attack is most effective when non-persistent committee members hold multiple seats, which is the normal case for high-stake pools under local sortition. The entry path is a standard network peer connection, reachable by any unprivileged participant.

---

### Recommendation

Include `pvSeatIndex` (serialised as a fixed-width big-endian integer) in the byte string hashed by `hashVoteSignature`. This binds each signature to exactly one seat, making cross-seat replay produce a hash mismatch and fail verification. The `runByteBuilder` size hint should be updated accordingly (e.g., `8 + 2 + 8 + 32` for a `Word16` seat index). [7](#0-6) 

---

### Proof of Concept

1. Voter A is a non-persistent committee member whose VRF output grants them seats `[5, 6, 7]`; all three entries in `extWFAStakeDistr` resolve to Voter A's BLS public key.
2. Voter A submits one vote: `PerasVote { pvRoundNo=R, pvBoostedBlock=B, pvSeatIndex=5, pvEligibilityProof=..., pvSignature=σ }` where `σ = BLS.sign(sk, hashVoteSignature(R, B))`.
3. An adversary intercepts this vote and constructs two additional messages: `pvSeatIndex=6, pvSignature=σ` and `pvSeatIndex=7, pvSignature=σ` (all other fields identical).
4. `implVerifyVote` for seat 6: `getCandidateIfSeatWithinBounds 6` returns Voter A's public key → `verifyVoteSignature pk R B σ` calls `hashVoteSignature R B` → same hash → **verification succeeds**.
5. Same for seat 7.
6. The adversary now holds three independently valid votes for block B from Voter A, tripling their contribution toward quorum without Voter A's participation or knowledge. [8](#0-7) [5](#0-4)

hashVoteSignature ::
  ElectionId PerasBLSCrypto ->
  VoteCandidate PerasBLSCrypto ->
  Hash HASH (SigDSIGN BLS12381MinSigDSIGN)
hashVoteSignature roundNo boostedBlock =
  Hash.castHash
    . Hash.hashWith id
    . runByteBuilder (8 + 8 + 32)
    $ roundNoBytes
      <> boostedBlockSlotBytes
      <> boostedBlockHashBytes
 where
  roundNoBytes =
    BS.word64BE
      . unPerasRoundNo
      $ roundNo
  boostedBlockSlotBytes =
    BS.word64BE
      . unSlotNo
      . bytes32RealPointSlot
      . unPerasBoostedBlock
      $ boostedBlock
  boostedBlockHashBytes =
    BS.byteStringCopy
      . BS.fromShort
      . bytes32RealPointHash
      . unPerasBoostedBlock
      $ boostedBlock
```
