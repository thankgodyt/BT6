### Title
Silent `tx_bytes` Zeroing in `internal_safe_verify_deposit_entry` Permanently Locks Bridge UTXO — (File: `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

---

### Summary

When `safe_verify_deposit` is called with a BTC transaction whose raw bytes exceed 10 000 bytes, the bridge silently replaces the stored `tx_bytes` with a 300-byte zero vector before writing the UTXO to its pool. The deposit is verified and nBTC is minted normally, but the UTXO entry is permanently corrupted. Any subsequent attempt to spend that UTXO in a withdrawal will panic on deserialization, permanently locking the corresponding BTC in the bridge-controlled deposit address.

---

### Finding Description

In `internal_safe_verify_deposit_entry`, after the deposit transaction is decoded and validated, the following branch silently corrupts the bytes that will be stored: [1](#0-0) 

```rust
let tx_bytes = if tx_bytes.len() > 10000 {
    env::log_str("tx_bytes length exceeds 10000, truncating to 300 bytes");
    vec![0u8; 300]          // ← stored bytes are now all-zero garbage
} else {
    tx_bytes
};
```

The `transaction` object (decoded from the *original* bytes before this branch) is still used to compute the correct `tx_id`, `vout`, and `balance`, so the UTXO key and balance are valid. However, the `tx_bytes` field of the `UTXO` struct is set to the zeroed vector: [2](#0-1) 

```rust
let utxo = UTXO {
    path,
    tx_bytes,          // ← 300 zero bytes
    vout,
    balance: transaction.output()[vout].value.to_sat(),
};
```

On successful `safe_mint`, `safe_mint_callback` writes this corrupted UTXO into the bridge's live UTXO pool: [3](#0-2) 

```rust
self.internal_set_utxo(&pending_utxo_info.utxo_storage_key, pending_utxo_info.utxo);
```

Later, when any withdrawal selects this UTXO as an input, the PSBT construction layer calls `WrappedTransaction::decode` on the stored `tx_bytes`. Decoding 300 zero bytes as a Bitcoin transaction will fail, triggering the `.expect("Deserialization tx_bytes failed")` panic: [4](#0-3) 

```rust
pub fn get_transaction(&self, chain: &network::Chain) -> WrappedTransaction {
    WrappedTransaction::decode(
        self.tx_bytes_with_sign
            .as_ref()
            .expect("Missing tx_bytes_with_sign"),
        chain,
    )
    .expect("Deserialization tx_bytes failed")
}
```

The UTXO is permanently unspendable; the BTC it represents is locked in the deposit address forever.

---

### Impact Explanation

The bridge's UTXO pool is the source of funds for all withdrawals. A stuck UTXO with corrupted `tx_bytes` can never be selected as a valid withdrawal input. The BTC locked in the corresponding deposit address is irrecoverable without an operator-driven migration or contract upgrade. This matches the **Medium** impact class: *stuck bridge state requiring operator intervention*, with a secondary risk of *permanent locking of protocol funds* if the operator cannot recover the UTXO.

---

### Likelihood Explanation

Bitcoin transactions exceeding 10 000 bytes are uncommon in normal usage but are entirely valid on-chain. A consolidation transaction spending hundreds of P2PKH inputs (each ~148 bytes) easily crosses this threshold. Any user who deposits BTC via such a transaction and uses `safe_verify_deposit` will silently corrupt their UTXO. No special privileges are required; the path is reachable by any bridge user.

---

### Recommendation

Remove the silent zeroing branch entirely. Either:

1. **Reject** the call with a clear error if `tx_bytes.len() > 10000`, consistent with how `request_refund` enforces `MAX_REQUEST_REFUND_TX_BYTES`; or
2. **Store the full bytes** regardless of size (accepting the storage cost, which the attached deposit already covers).

The current log-and-zero approach is the worst of both worlds: it silently accepts the deposit while making the resulting UTXO permanently unusable.

---

### Proof of Concept

1. Construct a valid Bitcoin transaction that sends BTC to a safe-deposit address and whose serialized size exceeds 10 000 bytes (e.g., a consolidation of ~70+ P2PKH inputs).
2. Call `safe_verify_deposit` with this transaction's bytes, a valid Merkle proof, and a `DepositMsg` containing `safe_deposit`.
3. The Light Client accepts the proof; `verify_safe_deposit_callback` marks the UTXO verified and calls `safe_mint`.
4. `safe_mint_callback` succeeds; nBTC is minted to the recipient; the UTXO is written to the pool with `tx_bytes = vec![0u8; 300]`.
5. Any subsequent withdrawal that selects this UTXO as an input will call `WrappedTransaction::decode` on the zeroed bytes, panic with `"Deserialization tx_bytes failed"`, and leave the UTXO permanently stuck.
