### Title
Panic in `safe_mint` Cross-Contract Call Silently Treated as Success, Permanently Locking User BTC — (File: `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

---

### Summary

In the `safe_verify_deposit` flow, the callback `safe_mint_callback` uses `is_refund_required()` to determine whether the upstream `safe_mint` cross-contract call succeeded. When `safe_mint` panics (any `Err` result from `env::promise_result_checked`), `is_refund_required()` returns `false`, which causes `safe_mint_callback` to treat the panic as a **successful mint**. The UTXO is then permanently added to the bridge's available set, but no nBTC is ever minted to the user. The user's BTC is irreversibly locked with no recovery path.

---

### Finding Description

The `safe_verify_deposit` / `verify_deposit_v2` (with `safe_deposit = Some(...)`) flow proceeds as follows:

1. `verify_safe_deposit_callback` verifies the light-client proof, inserts the UTXO key into `verified_deposit_utxo` (replay guard), then calls `ext_nbtc::safe_mint`.
2. `safe_mint_callback` is called with the result of `safe_mint`.

Inside `safe_mint_callback`:

```rust
let is_success = !is_refund_required();
```

`is_refund_required()` is:

```rust
fn is_refund_required() -> bool {
    match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
        Ok(value) => {
            if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {
                amount.0 == 0
            } else {
                false   // unparseable → no refund
            }
        }
        Err(_) => false,  // panic → no refund
    }
}
```

When `safe_mint` panics, NEAR delivers `Err(_)` to the callback. The function returns `false` (no refund needed), so `is_success = true`. The callback then executes the **success branch**:

```rust
if is_success {
    self.internal_set_utxo(&pending_utxo_info.utxo_storage_key, pending_utxo_info.utxo);
}
```

The UTXO is added to the bridge's spendable UTXO pool. However, because `safe_mint` panicked, NEAR rolled back all state changes inside the nbtc contract — **zero nBTC was minted**. The `verified_deposit_utxo` set already contains the UTXO key (inserted in `verify_safe_deposit_callback`), so any future re-submission of the same deposit proof will be rejected with "Already deposit utxo".

The code comment explicitly acknowledges this case but gives incorrect reasoning:

```
/// Refund only if `safe_mint` returned 0. Any other outcome (non-zero
/// amount, unparseable payload, panic) is treated as "UTXO spent, no
/// refund" — for safety, to avoid a potential double spend.
```

The "double spend" concern is unfounded: in NEAR, a panicking cross-contract call atomically rolls back all its own state mutations. If `safe_mint` panics, no tokens exist to double-spend. The correct treatment of a panic is **refund required**.

---

### Impact Explanation

When `safe_mint` panics:
- The user's BTC UTXO is permanently absorbed into the bridge's spendable pool.
- No nBTC is minted to the user.
- The UTXO key is in `verified_deposit_utxo`, blocking any re-deposit attempt.
- There is no operator recovery function to retroactively mint nBTC or return the UTXO.

This constitutes **permanent locking / destruction of user funds** — the user loses their BTC with no recourse.

**Allowed impact matched**: *Critical — Significant loss, theft, destruction, or permanent locking of user or protocol funds.*

---

### Likelihood Explanation

`safe_mint` is designed to return `U128(0)` rather than panic for the "account not registered" case. However, panics remain reachable via:

- **Gas exhaustion**: `GAS_FOR_MINT_CALL` is a static allocation; if the nbtc contract's `safe_mint` consumes more gas than allocated (e.g., after a contract upgrade), it panics.
- **Storage exhaustion**: If the nbtc contract's storage is full, internal writes panic.
- **nbtc contract upgrade**: Any future change to `safe_mint` that introduces a new panic path silently activates this bug for all subsequent `safe_verify_deposit` calls.
- **Arithmetic overflow**: Any unchecked arithmetic inside `safe_mint` panics in release mode (the project sets `overflow-checks = true`).

The `safe_verify_deposit` path is actively used by Omni Bridge integration, making this a live production surface. Any of the above conditions affecting a single deposit permanently destroys that user's funds.

---

### Recommendation

Treat `Err(_)` (panic) in `is_refund_required()` as **refund required**, not success:

```rust
fn is_refund_required() -> bool {
    match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
        Ok(value) => {
            if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {
                amount.0 == 0
            } else {
                true  // unparseable → treat as failure, refund
            }
        }
        Err(_) => true,  // panic → safe_mint failed, refund required
    }
}
```

This mirrors the GMX fix: catch all failure modes (including panics) and roll back state rather than silently accepting them as success.

---

### Proof of Concept

1. User (or Omni Bridge on behalf of user) calls `verify_deposit_v2` with a valid BTC proof and `deposit_msg.safe_deposit = Some(SafeDepositMsg { ... })`.
2. `verify_safe_deposit_callback` runs: UTXO key inserted into `verified_deposit_utxo`, `safe_mint` is called on the nbtc contract.
3. `safe_mint` panics (e.g., due to gas exhaustion or a storage write failure inside nbtc).
4. NEAR delivers `Err(_)` to `safe_mint_callback`.
5. `is_refund_required()` returns `false` → `is_success = true`.
6. `internal_set_utxo` adds the UTXO to the bridge's spendable pool.
7. No nBTC is minted (nbtc state was rolled back on panic).
8. User attempts to re-submit the same deposit proof → rejected: "Already deposit utxo".
9. User's BTC is permanently locked in the bridge with no nBTC received and no recovery path.

/// Refund only if `safe_mint` returned 0. Any other outcome (non-zero
/// amount, unparseable payload, panic) is treated as "UTXO spent, no
/// refund" — for safety, to avoid a potential double spend.
fn is_refund_required() -> bool {
    match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
        Ok(value) => {
            if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {
                // Normal case: refund if the used token amount is zero
                // The amount can be zero if the `ft_on_transfer` in the receiver contract returns an amount instead of `0`, or if it panics.
                amount.0 == 0
            } else {
                // Unexpected case: don't refund
                false
            }
        }
        // Unexpected case: don't refund
        Err(_) => false,
    }
}
