Audit Report

## Title
Unconstrained `fee_recipient` in `sign_transfer` Allows Any Trusted Relayer to Steal Transfer Fees — (File: `near/omni-bridge/src/lib.rs`)

## Summary

`sign_transfer` accepts a caller-supplied `fee_recipient` with no validation that it matches `predecessor_account_id()`. Because the MPC signs whatever `fee_recipient` is embedded in the payload, any active trusted relayer can obtain a valid MPC signature naming themselves as fee recipient for any pending fee-bearing transfer, finalize it on the destination chain with their own signature, and claim the full fee — stealing it from the legitimate relayer.

## Finding Description

**Root cause:** `sign_transfer` (L447–521) embeds the caller-supplied `fee_recipient` verbatim into `TransferMessagePayload` with no identity check:

```rust
pub fn sign_transfer(
    &mut self,
    transfer_id: TransferId,
    fee_recipient: Option<AccountId>,   // no check against predecessor_account_id()
    fee: &Option<Fee>,
) -> Promise {
``` [1](#0-0) 

The payload is then signed by the MPC with `fee_recipient` baked in: [2](#0-1) 

**Transfer record not consumed for fee-bearing transfers:** `sign_transfer_callback` (L648–668) only removes the pending transfer when `fee.is_zero()`. For any transfer with a non-zero fee, the record remains in storage, so multiple relayers can each call `sign_transfer` for the same `transfer_id` with different `fee_recipient` values and each receive a distinct, valid MPC signature: [3](#0-2) 

**`claim_fee` / `claim_fee_callback` flow:** `claim_fee` (L1057–1063) is gated by `#[trusted_relayer]` and captures `predecessor_account_id` at call time, passing it to `claim_fee_callback`: [4](#0-3) 

`claim_fee_callback` (L1068–1086) reads `fee_recipient` from the proof of the destination-chain `FinTransfer` event and enforces `fee_recipient == predecessor_account_id`: [5](#0-4) 

This check is against the `fee_recipient` that was baked into the MPC-signed payload and emitted on the destination chain — so whoever wins the race to finalize with their own `fee_recipient` passes this check trivially.

**Exploit path:**
1. Malicious trusted relayer B observes any pending fee-bearing transfer in `pending_transfers`.
2. B calls `sign_transfer(transfer_id, fee_recipient = B, fee)` — succeeds because there is no identity check.
3. MPC returns `sig_B` with `fee_recipient = B` embedded.
4. B submits `finTransfer` on the EVM destination chain using `sig_B`, emitting a `FinTransfer` event with `fee_recipient = B`.
5. B calls `claim_fee` on NEAR with the EVM proof. `claim_fee_callback` reads `fee_recipient = B`, checks `B == predecessor_account_id()` (passes), and transfers the full fee to B.
6. The legitimate relayer's signature (with `fee_recipient = A`) is now worthless — the destination chain nonce is consumed and the transfer message has been removed from NEAR state.

**Existing guards are insufficient:** The `#[trusted_relayer]` gate only confirms the caller is a staked relayer; it does not bind `fee_recipient` to the caller's identity. The `claim_fee_callback` check enforces consistency between the proof and the caller, but the proof itself was produced using the attacker-controlled `fee_recipient` value.

## Impact Explanation

This is a concrete **fee mis-accounting** impact: the fee locked in bridge escrow is paid to the wrong party. The `fee` and `native_fee` amounts are set by the user at transfer initiation and can be substantial. The legitimate relayer receives nothing for their work, and the attacker receives the full fee without having originated or legitimately serviced the transfer. This matches the allowed critical impact: *"fee mis-accounting... that changes user or protocol balances."*

## Likelihood Explanation

Trusted relayer status is permissionlessly obtainable: any account can call `apply_for_trusted_relayer` with the required stake (default 1,000 NEAR) and wait out the waiting period (default ~7 days) with no admin approval required. [6](#0-5) [7](#0-6) 

The attacker does not need to front-run any NEAR transaction. They can call `sign_transfer` independently at any time (the transfer record is not locked or consumed by a prior `sign_transfer` call for fee-bearing transfers), obtain their own valid MPC signature, and race to finalize on the destination chain — a straightforward EVM transaction submission.

## Recommendation

Enforce that `fee_recipient` is bound to the caller's identity inside `sign_transfer`:

```rust
let effective_fee_recipient = Some(env::predecessor_account_id());
```

Or validate the supplied value:

```rust
if let Some(ref r) = fee_recipient {
    require!(
        *r == env::predecessor_account_id(),
        BridgeError::InvalidFeeRecipient.as_ref()
    );
}
let fee_recipient = fee_recipient.or_else(|| Some(env::predecessor_account_id()));
```

This mirrors the pattern already used in `fin_transfer` where `predecessor_account_id` is captured at call time and threaded through the callback chain. [8](#0-7) 

## Proof of Concept

1. User calls `ft_transfer_call` → `init_transfer` on NEAR, locking 10,000 tokens with `fee = 500`.
2. Legitimate Relayer A calls `sign_transfer(transfer_id, fee_recipient = A, fee)` → MPC returns `sig_A`.
3. Malicious Relayer B (a separately staked trusted relayer) calls `sign_transfer(transfer_id, fee_recipient = B, fee)` → MPC returns `sig_B`. This succeeds because `sign_transfer` does not check `fee_recipient == predecessor_account_id()` and the transfer record is still present (fee ≠ 0 so `sign_transfer_callback` did not remove it). [3](#0-2) 
4. Relayer B submits `finTransfer` on the EVM destination chain using `sig_B`, emitting a `FinTransfer` event with `fee_recipient = B`.
5. Relayer B calls `claim_fee` on NEAR with the EVM proof. `claim_fee_callback` reads `fee_recipient = B` from the proof, checks `B == predecessor_account_id()` (passes), and transfers 500 tokens to B. [9](#0-8) 
6. Relayer A's `sig_A` is now useless — the destination chain nonce is consumed and `claim_fee` with A's proof would fail because the transfer message has already been removed from NEAR state. [10](#0-9) 

**Test plan:** Write an integration test using the existing `setup_trusted_relayer` helper to create two relayer accounts (A and B), initiate a fee-bearing transfer, have B call `sign_transfer` with `fee_recipient = B`, simulate the EVM `FinTransfer` event proof with `fee_recipient = B`, call `claim_fee` as B, and assert that B receives the fee while A receives nothing.
