### Title
nBTC Sent to Bridge via `ft_transfer` Bypasses `ft_on_transfer` Accounting, Permanently Locking Tokens — (File: `contracts/nbtc/src/lib.rs`, `contracts/satoshi-bridge/src/api/token_receiver.rs`)

---

### Summary

The bridge's entire withdrawal-initiation logic lives inside `ft_on_transfer`, which is only invoked by the NEP-141 `ft_transfer_call` path. Any nBTC sent to the bridge contract via the plain `ft_transfer` path silently credits the bridge's internal nBTC balance with no withdrawal initiated, no `BTCPendingInfo` created, and no recovery mechanism available. The tokens are permanently locked. This is the direct NEAR analog of the PaymentSplitter ink! issue: a second, publicly reachable transfer path exists that completely bypasses the contract's accounting hook.

---

### Finding Description

The bridge's `ft_on_transfer` handler in `token_receiver.rs` is the sole on-chain entry point for withdrawal initiation: [1](#0-0) 

This function is only reachable via `ft_transfer_call` on the nBTC contract. The nBTC contract also exposes a plain `ft_transfer`: [2](#0-1) 

When a caller invokes `ft_transfer` with `receiver_id = satoshi-bridge`, the NEP-141 standard performs a direct balance update on the nBTC contract with **no cross-contract callback to the bridge**. The bridge's `ft_on_transfer` is never called. The nBTC tokens are credited to the bridge's `bridge_id` account balance inside the nBTC contract, but the bridge contract itself has no state change, no `BTCPendingInfo`, and no `lost_found` entry.

Additionally, the nBTC contract contains a legacy bridging path that explicitly routes tokens through `ft_transfer` (not `ft_transfer_call`): [3](#0-2) 

When `withdraw_relayer` is set, tokens are forwarded to the relayer via `ft_transfer` — again with no on-chain callback to the bridge. The entire withdrawal tracking for this path is off-chain. If the relayer is offline or fails, the tokens are permanently stuck with the relayer account with no on-chain recovery path.

The bridge has no `receive`-equivalent hook, no fallback handler, and no administrative function to sweep or recover nBTC that arrives via `ft_transfer`.

---

### Impact Explanation

Any nBTC sent to the bridge via `ft_transfer` is permanently locked. The bridge's `burn` function withdraws from `bridge_id`'s nBTC balance: [4](#0-3) 

Extra nBTC silently accumulated in `bridge_id`'s balance from stray `ft_transfer` calls can be consumed by the bridge during a legitimate `burn` call, effectively destroying user funds without any corresponding BTC release. This constitutes a permanent, unrecoverable loss of user nBTC with no on-chain audit trail.

**Impact class**: Low — publicly reachable stuck-state / permanent token loss in production bridge paths without direct attacker theft.

---

### Likelihood Explanation

The entry path is fully public: any NEAR account can call `ft_transfer` on the nBTC contract. Likelihood is low-to-medium because:
- Sophisticated integrators (DeFi protocols, wallets) may call `ft_transfer` instead of `ft_transfer_call` when composing with the bridge programmatically.
- The legacy `WITHDRAW_TO:` memo path in the nBTC contract explicitly advertises an `ft_transfer`-based withdrawal flow, increasing the chance that users or integrators attempt it without a configured relayer.
- There is no on-chain guard in the nBTC contract rejecting `ft_transfer` to the bridge address.

---

### Recommendation

1. In `nbtc/src/lib.rs`, override `ft_transfer` to reject transfers where `receiver_id == bridge_id` (or `receiver_id == env::current_account_id()` in the legacy path) with a clear error message directing users to `ft_transfer_call`.
2. Alternatively, add a privileged `recover_stray_nbtc` function on the bridge that can detect and return nBTC received outside the `ft_on_transfer` path.
3. For the legacy `WITHDRAW_TO:` path, require `withdraw_relayer` to be set before the nBTC contract is deployed, and add an explicit `require!` that panics if the relayer is unset rather than silently falling through to a self-transfer.

---

### Proof of Concept

1. Alice holds 1 nBTC and wants to withdraw to Bitcoin.
2. Alice calls `nbtc.ft_transfer({ receiver_id: "satoshi-bridge", amount: "100000000", memo: null })` instead of `ft_transfer_call`.
3. The nBTC contract executes `self.token.ft_transfer(satoshi-bridge, 100000000, None)` — a pure balance update.
4. The bridge's `ft_on_transfer` is **never called**. No `BTCPendingInfo` is created. No `Withdraw` event is emitted.
5. Alice's 1 nBTC is now in the bridge's `bridge_id` nBTC balance with no associated withdrawal state.
6. Alice has no on-chain mechanism to recover her tokens. The bridge has no `lost_found` entry for her.
7. A subsequent legitimate `burn` call by the bridge consumes `bridge_id`'s balance, silently destroying Alice's tokens. [5](#0-4) [2](#0-1) [6](#0-5)

impl FungibleTokenReceiver for Contract {
    #[pause(except(roles(Role::DAO)))]
    fn ft_on_transfer(
        &mut self,
        sender_id: AccountId,
        amount: U128,
        msg: String,
    ) -> PromiseOrValue<U128> {
        let amount = amount.into();
        require!(
            amount >= self.internal_config().min_withdraw_amount,
            "Invalid amount"
        );
        let message = serde_json::from_str::<TokenReceiverMessage>(&msg).expect("INVALID MSG");
        let token_id = env::predecessor_account_id();
        require!(
            token_id == self.internal_config().nbtc_account_id,
            "Invalid token_id"
        );
        match message {
            TokenReceiverMessage::DepositProtocolFee => {
                self.data_mut().acc_collected_protocol_fee += amount;
                self.data_mut().cur_available_protocol_fee += amount;
                Event::DepositProtocolFee {
                    account_id: &sender_id,
                    amount: U128(amount),
                }
                .emit();
                PromiseOrValue::Value(U128(0))
            }
            TokenReceiverMessage::Withdraw {
                target_btc_address,
                input,
                output,
                max_gas_fee,
                chain_specific_data,
            } => self.ft_on_transfer_withdraw_chain_specific(
                sender_id,
                amount,
                target_btc_address,
                input,
                output,
                max_gas_fee,
                chain_specific_data,
            ),
        }
    }

            if self.token.accounts.get(&relayer_account_id).is_none() {
                self.token.internal_register_account(&relayer_account_id);

                relayer_fee.into(),
                None,
            );
        }
        near_contract_standards::fungible_token::events::FtBurn {
            owner_id: &burn_account_id,
            amount: burn_amount,
            memo: None,
        }
        .emit();
    }

    fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
        // Legacy bridging flow used by Near Intents
        if receiver_id == env::current_account_id()
            && memo
                .as_ref()
                .is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))

            if let Some(withdraw_relayer) = Self::read_withdraw_relayer_address() {
                return self.token.ft_transfer(withdraw_relayer, amount, memo);
            }
        }

        self.token.ft_transfer(receiver_id, amount, memo);
    }
