### Title
Missing Peras Weight Check in `checkPreferTheirsOverOurs` Enables Chain-Selection Bypass When Peras Is Active - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

`checkPreferTheirsOverOurs` in the ChainSync client unconditionally passes `emptyPerasWeightSnapshot` to `preferAnchoredCandidate` when deciding whether to disconnect from a peer whose header is beyond the forecast horizon. When Ouroboros Peras is active and blocks carry vote-weight boosts, this missing weight check causes the node to compare chains by raw block count only, ignoring total Peras weight. An adversary can exploit this to cause the node to disconnect from honest peers serving the heavier (more secure) chain and instead retain a connection to — and ultimately select — a lighter adversarial chain, bypassing the Peras security guarantees.

---

### Finding Description

`checkPreferTheirsOverOurs` is invoked inside `readLedgerStateHelper` whenever `projectLedgerView` returns `Nothing` (i.e., the peer's header is beyond the forecast horizon). Its purpose is to disconnect from peers whose candidate chain is not preferable to the node's current selection, preventing the node from waiting indefinitely for a chain it will never adopt. [1](#0-0) 

The function calls `preferAnchoredCandidate` with a hardcoded `emptyPerasWeightSnapshot`: [2](#0-1) 

`preferAnchoredCandidate` branches on whether the weight snapshot is empty. When it is empty (as hardcoded here), it falls into the standard block-number comparison path, ignoring all Peras vote boosts: [3](#0-2) 

When Peras is active, the correct comparison must use `weightedSelectView`, which sums raw block count plus accumulated vote boosts: [4](#0-3) 

The `SecurityParam` type explicitly documents that under Peras, `k` is a *weight* bound, not a block-count bound: [5](#0-4) 

The developers acknowledge the problem with a TODO referencing an open issue, but the check remains in production code: [6](#0-5) 

---

### Impact Explanation

When Peras is active and vote boosts are present, `checkPreferTheirsOverOurs` makes the wrong disconnect decision in the following scenario:

- **Our chain**: 10 raw blocks, 0 Peras boosts → total weight 10.
- **Honest peer's chain**: 9 raw blocks, 5 Peras boosts → total weight 14 (heavier, more secure).
- The honest peer's header is beyond the forecast horizon, so `checkPreferTheirsOverOurs` is invoked.
- With `emptyPerasWeightSnapshot`, `preferAnchoredCandidate` sees 9 < 10 raw blocks → `ShouldNotSwitch` → the node throws `CandidateTooSparse` and **disconnects from the honest peer**.

Simultaneously, an adversary serving a chain with 11 raw blocks and 0 Peras boosts (total weight 11, lighter than the honest chain) passes the raw-block check and is **kept connected**. The node then selects the adversary's lighter chain, bypassing the Peras weight-based security guarantee. This matches the "High" impact category: a chain-selection bug that lets an unprivileged peer make an honest node prefer a less-secure chain beyond the intended security assumptions.

---

### Likelihood Explanation

This requires Peras to be active and producing vote boosts on-chain. The Peras infrastructure is already integrated into production code (`PerasWeightSnapshot`, `takeVolatileSuffix`, `weightedSelectView`, `maxRollbackWeight` are all wired into chain selection), and the TODO comment confirms the developers intend to address this before or during Peras deployment. The trigger condition — a header beyond the forecast horizon (~36 hours of slots at `3k/f`) — is reachable during normal syncing or after a network partition. No privileged access is required; any peer can serve a chain with more raw blocks and fewer boosts.

---

### Recommendation

Either:

1. **Remove the check entirely** as the TODO suggests (the referenced issue https://github.com/tweag/cardano-peras/issues/64 tracks this), since the check is fundamentally incompatible with Peras chain selection semantics; or
2. **Pass the actual `PerasWeightSnapshot`** from the node's current state to `preferAnchoredCandidate` inside `checkPreferTheirsOverOurs`, so that the comparison uses total Peras weight rather than raw block count.

The analogous correct pattern is already used in `initialChainSelection` and `chainSelection`, where the real `weights` value is threaded through: [7](#0-6)

### Proof of Concept

Reproducible on a private testnet with Peras enabled:

1. Configure a two-peer private testnet with Peras active and vote boosts enabled.
2. Peer A (honest) produces a chain: 9 blocks, with 5 Peras vote boosts on its tip block (total weight 14).
3. Peer B (adversary) produces a chain: 11 blocks, 0 Peras boosts (total weight 11).
4. Arrange for Peer A's tip header to be beyond the node's forecast horizon (e.g., by introducing a slot gap > `3k/f` slots).
5. Observe: `readLedgerStateHelper` calls `checkPreferTheirsOverOurs` for Peer A. `preferAnchoredCandidate` with `emptyPerasWeightSnapshot` compares block numbers: 9 (Peer A) < current tip → `ShouldNotSwitch` → `CandidateTooSparse` exception → **Peer A disconnected**.
6. Peer B's chain (11 raw blocks > current tip) passes the check → Peer B kept connected.
7. Node selects Peer B's chain (total weight 11) instead of Peer A's chain (total weight 14), violating the Peras security invariant.

  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of

              ShouldNotSwitch o -> ShouldNotSwitch o
