### Title
Silent Replacement of Oversized `tx_bytes` with Zero-Bytes Permanently Locks Deposited UTXOs - (File: `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

### Summary

In `internal_safe_verify_deposit_entry`, when the caller-supplied `tx_bytes` exceed 10,000 bytes, the code silently replaces them with 300 zero bytes (`vec![0u8; 300]`) rather than rejecting the deposit. The deposit verification and nBTC minting proceed normally against the original decoded transaction, but the UTXO is persisted with entirely invalid (zeroed) transaction bytes. Any subsequent withdrawal attempt that decodes those bytes to reconstruct the transaction will fail, permanently locking the UTXO in the bridge while the corresponding nBTC remains in circulation unbacked.

### Finding Description

The root cause is in `internal_safe_verify_deposit_entry`:

```rust
// lines 191-193: transaction decoded and deposit verified from real tx_bytes
let transaction = WrappedTransaction::decode(&tx_bytes, &self.internal_config().chain)
    .expect("Deserialization tx_bytes failed");
let deposit_amount = transaction.output()[vout].value.to_sat().into();
// ... address check, deposit_amount > 0 check ...

// lines 204-209: tx_bytes silently replaced with zeros
let tx_bytes = if tx_bytes.len() > 10000 {
    env::log_str("tx_bytes length exceeds 10000, truncating to 300 bytes");
    vec![0u8; 300]   // ← NOT a truncation; 300 zero bytes, not the first 300 real bytes
} else {
    tx_bytes
};

// lines 211-216: UTXO stored with zeroed tx_bytes but correct balance
let utxo = UTXO {
    path,
    tx_bytes,          // ← zeros
    vout,
    balance: transaction.output()[vout].value.to_sat(),  // ← correct
};
``` [1](#0-0) 

The log message says "truncating to 300 bytes" but the implementation creates `vec![0u8; 300]` — 300 zero bytes — not the first 300 bytes of the original transaction. This is a discrepancy between stated intent and actual behavior.

The UTXO struct stores `tx_bytes` as the raw serialized transaction: [2](#0-1) 

These bytes are later used to reconstruct the previous-output data required for PSBT/signing during withdrawal. Decoding 300 zero bytes as a Bitcoin or Zcash transaction will fail, causing the withdrawal to panic and leaving the UTXO permanently stuck.

The `verified_deposit_utxo` set is already updated before the UTXO is stored, so the deposit cannot be replayed: [3](#0-2) 

There is no operator path to overwrite a stored UTXO's `tx_bytes` without a contract upgrade.

### Impact Explanation

A UTXO deposited via a transaction larger than 10,000 bytes will be permanently unspendable by the bridge. The corresponding nBTC is minted and enters circulation, but the BTC/ZEC backing it cannot be recovered. This is a stuck bridge state requiring operator intervention (contract upgrade or manual state surgery). Repeated exploitation degrades the bridge's collateral ratio.

### Likelihood Explanation

Standard Bitcoin transactions are well under 10,000 bytes, but transactions with many inputs (e.g., consolidation transactions with 50+ inputs) or large OP_RETURN payloads can exceed this threshold. Zcash transactions carrying Orchard bundles are substantially larger and more likely to cross 10,000 bytes. Any unprivileged user who can broadcast such a transaction on-chain and call `safe_verify_deposit` (which only requires an attached storage deposit, not a privileged role) can trigger this path. [4](#0-3) 

### Recommendation

Reject the deposit outright when `tx_bytes` exceed the size limit, rather than silently replacing them with zeros:

```rust
require!(
    tx_bytes.len() <= 10000,
    "tx_bytes exceeds maximum allowed size"
);
```

If storage-cost reduction for large transactions is genuinely desired, store only the first N bytes of the real transaction (a true truncation), and ensure the withdrawal path can handle partial `tx_bytes` by re-fetching the full transaction from an on-chain source. The current behavior — replacing with zeros — is never safe.

### Proof of Concept

1. Construct a Bitcoin transaction with enough inputs (or a large OP_RETURN) so that its serialized size exceeds 10,000 bytes, with one output paying to the bridge's deposit address for account `alice.near`.
2. Broadcast the transaction on Bitcoin and wait for the required confirmations.
3. Call `safe_verify_deposit` on the bridge contract with the full `tx_bytes` (> 10,000 bytes), valid Merkle proof, and `deposit_msg` for `alice.near`.
4. Observe: `verify_safe_deposit_callback` succeeds, nBTC is minted to `alice.near`, and the UTXO is inserted into `data().utxos` with `tx_bytes = [0u8; 300]`.
5. Attempt a withdrawal using that UTXO. The PSBT construction step calls `WrappedTransaction::decode(&utxo.tx_bytes, ...)` on 300 zero bytes, which fails, causing a panic and leaving the UTXO permanently locked.
