### Title
Peras Quorum Check Unit Mismatch Enables Unauthorized Certificate Forging — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The Peras vote aggregation quorum check in `stakeAboveThreshold` compares accumulated `PerasVoteStake` values directly against a relative quorum threshold (`perasQuorumStakeThreshold`, set to `3/4`) without performing normalization. The code itself acknowledges this unit mismatch in a TODO comment. Meanwhile, `implEligiblePartyVoteWeight` in the WFALS committee assigns persistent committee members their raw absolute ledger stake as vote weight, while non-persistent members receive a normalized value. When absolute ledger stake values are summed and compared against a relative threshold, the comparison is semantically invalid, potentially allowing a single persistent voter with sufficient absolute stake to satisfy the quorum check alone and forge a Peras certificate for an arbitrary block.

---

### Finding Description

**Root cause — `stakeAboveThreshold` in `SupportsPeras.hs`:**

The function compares the accumulated `PerasVoteStake` (a `Rational`) directly against `perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin` (also `Rational`, defaulting to `3/4 + 2/100 = 0.77`):

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
```

The code's own TODO comment (lines 155–161) explicitly states:

> "this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … Under the current implementation of `PerasParams`, this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [1](#0-0) 

**Root cause — `implEligiblePartyVoteWeight` in `WFALS.hs`:**

Persistent committee members receive their raw absolute ledger stake as vote weight, with no normalization:

```haskell
WFALSPersistentMember _seatIndex (LedgerStake stake) ->
  VoteWeight stake
```

Non-persistent members receive a normalized value (`stake / nonPersistentStake`). This creates a mixed-unit situation: persistent members contribute absolute stake values while the quorum threshold is a relative fraction. [2](#0-1) 

**Aggregation path — `votesReachQuorum` in `SupportsPeras.hs`:**

```haskell
totalVoteStake = mconcat (vpvVoteStake <$> votes)
votesHaveEnoughStake = stakeAboveThreshold cfg totalVoteStake
```

The `mconcat` sums all `vpvVoteStake` values. If these carry absolute ledger stake (e.g., in lovelace or ADA fractions), the sum can trivially exceed `0.77`, satisfying the quorum check with a single vote. [3](#0-2) 

**Certificate forging path — `updateCandidateVoteState` in `Aggregation.hs`:**

```haskell
case votesReachQuorum cfg voteList of
  Just votesWithQuorum -> do
    cert <- forgePerasCert cfg votesWithQuorum
    pure $ BecameWinner (PerasTargetVoteWinner newVoteTally cert)
```

Once `votesReachQuorum` returns `Just`, a certificate is immediately forged. There is no secondary normalization check. [4](#0-3) 

---

### Impact Explanation

A Peras certificate boosts the weight of the certified block in chain selection. An adversary who can forge a certificate for their own block gains an illegitimate chain-selection advantage proportional to `perasWeight` (default: 15 blocks). This constitutes a **bypass of Peras certificate checks that enables unauthorized certificate acceptance**, directly matching the allowed impact scope. If the absolute stake of a single persistent committee member exceeds `0.77` in the same numeric units as the quorum threshold, that member can forge a certificate unilaterally, without the participation of any other honest voter.

---

### Likelihood Explanation

**Medium.** The attacker must be a legitimate stake pool operator who is a persistent Peras committee member (i.e., holds enough stake to qualify for a persistent seat). The exploit does not require key compromise, social engineering, or a stake majority — only that the absolute ledger stake value, when treated as a `Rational`, numerically exceeds `0.77`. Whether this condition holds depends on the concrete unit of `LedgerStake` used at runtime. The code's own TODO acknowledges the normalization is absent and the comparison is only meaningful with relative values, confirming the defect is present in production code. The object diffusion miniprotocol provides the externally reachable entry point for delivering the crafted vote.

---

### Recommendation

1. **Normalize `PerasVoteStake` before comparison.** Either normalize inside `stakeAboveThreshold` by accepting the total stake distribution as an additional parameter, or ensure that every call site (including `validatePerasVote` implementations) converts absolute ledger stake to a relative fraction before constructing `ValidatedPerasVote`.

2. **Resolve the persistent-member unit inconsistency in `implEligiblePartyVoteWeight`.** Persistent members currently receive raw `LedgerStake` while non-persistent members receive a normalized value. Both paths should produce values in the same unit (relative fraction of total committee stake) before they are stored in `vpvVoteStake`.

3. **Add a type-level or runtime invariant** asserting that any `PerasVoteStake` value passed to `stakeAboveThreshold` is in `[0, 1]`, so that unit mismatches are caught immediately rather than silently producing incorrect quorum decisions.

---

### Proof of Concept

**Setup:** A private testnet with Peras enabled. One stake pool operator holds a persistent committee seat with `LedgerStake = 1.0` (in whatever absolute unit the runtime uses).

**Steps:**

1. The operator constructs a `PerasVote` for their own block in round `R`.
2. The vote is validated by `validatePerasVote`; the resulting `ValidatedPerasVote` carries `vpvVoteStake = PerasVoteStake 1.0` (absolute ledger stake, not normalized).
3. The vote is diffused to an honest node via the object diffusion miniprotocol.
4. The honest node calls `updatePerasRoundVoteStates`, which calls `updateCandidateVoteState`, which calls `votesReachQuorum`.
5. Inside `votesReachQuorum`, `totalVoteStake = PerasVoteStake 1.0`. `stakeAboveThreshold` evaluates `1.0 >= 0.75 + 0.02 = 0.77` → `True`.
6. `forgePerasCert` is called; a certificate is forged for the operator's block with a single vote.
7. The certificate is stored and the boosted block gains `perasWeight = 15` extra chain-selection weight, causing honest nodes to prefer the operator's chain over a denser honest chain. [5](#0-4) [6](#0-5) [4](#0-3) [7](#0-6)

implEligiblePartyVoteWeight ::
  VotingCommittee crypto WFALS ->
  EligibilityWitness crypto WFALS ->
  VoteWeight
implEligiblePartyVoteWeight committee = \case
  -- Persistent members have their voting power equal to their stake
  WFALSPersistentMember
    _seatIndex
    (LedgerStake stake) ->
      VoteWeight stake
  -- Non-persistent members have their voting power proportional to their
  -- number of seats granted by local sortition and their stake (normalized
  -- by the total non-persistent stake)
  WFALSNonPersistentMember
    _seatIndex
    (LedgerStake stake)
    _vrfOutput
    numSeats ->
      VoteWeight $
        fromIntegral (unLocalSortitionNumSeats (unNonZero numSeats))
          * stake
          / nonPersistentStake
     where
      TotalNonPersistentStake (Cumulative (LedgerStake nonPersistentStake)) =
        totalNonPersistentStake committee
