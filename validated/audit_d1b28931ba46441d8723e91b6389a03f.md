Audit Report

## Title
Native ETH `finTransfer` Always Reverts Due to Stale `msg.value` Forwarding in `finTransferExtension` — (File: `evm/src/omni-bridge/contracts/OmniBridgeWormhole.sol`)

## Summary

`OmniBridgeWormhole.finTransferExtension` forwards the full original `msg.value` to `_wormhole.publishMessage`. For native ETH finalizations (`tokenAddress == address(0)`), `msg.value` must cover both `payload.amount` (sent to the recipient) and the Wormhole fee. After `OmniBridge.finTransfer` disburses `payload.amount` to the recipient, the contract's ETH balance is reduced to only the Wormhole fee, yet `finTransferExtension` attempts to forward the full original `msg.value`, which exceeds the remaining balance and causes an EVM revert. Every native ETH finalization attempt fails deterministically, permanently freezing bridged ETH on NEAR.

## Finding Description

`OmniBridge.finTransfer` is `external payable` with no access restriction beyond the pause flag. For native ETH (`payload.tokenAddress == address(0)`), it first sends `payload.amount` to the recipient: [1](#0-0) 

Control then passes to `finTransferExtension`: [2](#0-1) 

Inside `OmniBridgeWormhole.finTransferExtension`, the full original `msg.value` is forwarded to Wormhole: [3](#0-2) 

In Solidity, `msg.value` always reflects the ETH sent with the original call — it does not decrease as ETH is forwarded out. For a native ETH finalization, the caller must supply `msg.value = payload.amount + wormholeFee`. After the `payload.amount` is sent to the recipient, the contract holds only `wormholeFee`. The subsequent `publishMessage{value: msg.value}` attempts to forward `payload.amount + wormholeFee`, which exceeds the contract's remaining balance, causing an EVM revert. Because the entire transaction reverts, `completedTransfers[payload.destinationNonce]` is also rolled back, so the nonce is not consumed — but every retry hits the same revert.

By contrast, `initTransfer` correctly computes a separate `extensionValue` that excludes the ETH amount before passing it to `initTransferExtension`: [4](#0-3) 

And `initTransferExtension` uses that pre-computed `value` parameter rather than raw `msg.value`: [5](#0-4) 

`finTransferExtension` has no equivalent separation.

## Impact Explanation

Any user bridging native ETH from NEAR to an EVM chain served by `OmniBridgeWormhole` will have their ETH permanently locked on NEAR. The EVM-side finalization always reverts; the NEAR-side lock is never released. This constitutes permanent freezing of bridged funds, which falls squarely within the Critical impact scope ("permanent freezing of bridged funds across NEAR, EVM, or Wormhole-routed flows").

## Likelihood Explanation

`finTransfer` is a public, permissionless, payable function. The native ETH path (`tokenAddress == address(0)`) is explicitly supported by `OmniBridge`. The revert is deterministic — no special attacker action, no race condition, no external dependency failure is required. Every relay attempt for a native ETH transfer triggers the bug unconditionally.

## Recommendation

Replace the hardcoded `msg.value` in `finTransferExtension` with the exact Wormhole fee, mirroring the pattern used in `initTransferExtension`:

```solidity
function finTransferExtension(
    BridgeTypes.TransferMessagePayload memory payload
) internal override {
    uint256 wormholeFee = _wormhole.messageFee();
    bytes memory messagePayload = bytes.concat(
        bytes1(uint8(MessageType.FinTransfer)),
        bytes1(payload.originChain),
        Borsh.encodeUint64(payload.originNonce),
        bytes1(omniBridgeChainId),
        Borsh.encodeAddress(payload.tokenAddress),
        Borsh.encodeUint128(payload.amount),
        Borsh.encodeString(payload.feeRecipient)
    );
    _wormhole.publishMessage{value: wormholeFee}(
        wormholeNonce,
        messagePayload,
        _consistencyLevel
    );
    wormholeNonce++;
}
```

`deployTokenExtension` and `logMetadataExtension` also pass `msg.value` directly, but those callers send no ETH to recipients so the bug does not manifest there. Switching all three to `_wormhole.messageFee()` makes intent explicit and eliminates the entire class of issue. [6](#0-5) [7](#0-6) 

## Proof of Concept

1. Deploy `OmniBridgeWormhole` on a local testnet; set Wormhole `messageFee()` = 10 000 wei.
2. Configure a native ETH bridge transfer from NEAR → EVM with `payload.amount = 1 ETH`.
3. Relayer calls `finTransfer(sig, payload)` with `msg.value = 1 ETH + 10 000 wei`.
4. `finTransfer` executes `payload.recipient.call{value: 1 ETH}("")` — succeeds; contract balance drops to `10 000 wei`.
5. `finTransferExtension` executes `_wormhole.publishMessage{value: 1 ETH + 10 000 wei}(...)`.
6. EVM reverts: contract balance (`10 000 wei`) < forwarded value (`1 ETH + 10 000 wei`).
7. Entire transaction reverts; recipient receives nothing; nonce is not consumed.
8. Every subsequent relay attempt reproduces the identical revert.
9. User's 1 ETH is permanently frozen on NEAR with no recovery path.

A minimal Foundry test can confirm this by mocking `IWormhole` to assert the forwarded value and verifying the transaction reverts when `payload.tokenAddress == address(0)` and `payload.amount > 0`.
