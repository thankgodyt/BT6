### Title
Bridge Pause Permanently Blocks User nBTC Recovery via `claim_lost_found` — (`File: contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

When the bridge is paused, users who have nBTC stranded in the `lost_found` map cannot retrieve it. The recovery function `claim_lost_found` is gated by `#[pause(except(roles(Role::DAO)))]`, which blocks all non-DAO callers. Critically, the function resolves the beneficiary from `env::predecessor_account_id()`, so the DAO cannot call it on behalf of affected users. The result is that user nBTC is permanently inaccessible for the duration of any pause, with no operator-accessible rescue path.

---

### Finding Description

**How nBTC enters `lost_found`**

`internal_transfer_nbtc` is called whenever the bridge needs to return nBTC to a user (e.g., after a `cancel_withdraw`). It issues an `ft_transfer` cross-contract call and registers a callback `transfer_nbtc_callback`. If the transfer fails — for example because the user is not registered in the nBTC contract — the amount is written into the `lost_found` map keyed by the user's account ID:

```rust
// contracts/satoshi-bridge/src/token_transfer.rs:54-74
pub fn transfer_nbtc_callback(&mut self, account_id: AccountId, amount: U128) -> bool {
    let promise_success = is_promise_success();
    if !promise_success {
        self.data_mut()
            .lost_found
            .entry(account_id.clone())
            .and_modify(|v| *v += amount.0)
            .or_insert(amount.0);
        ...
    }
    ...
}
```

**The blocked recovery path**

The only public function that lets a user retrieve their `lost_found` nBTC is `claim_lost_found`:

```rust
// contracts/satoshi-bridge/src/api/bridge.rs:449-460
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn claim_lost_found(&mut self) -> Promise {
    assert_one_yocto();
    let account_id = env::predecessor_account_id();   // ← caller-bound
    let amount = self
        .data_mut()
        .lost_found
        .remove(&account_id)
        .expect("The account does not have lostfound");
    self.internal_transfer_nbtc(&account_id, amount)
}
```

The `#[pause(except(roles(Role::DAO)))]` macro causes the function to revert with `"Method is paused"` for any caller that does not hold the `DAO` role. When the bridge is paused:

- **Regular users** cannot call `claim_lost_found` → their nBTC stays locked.
- **DAO** is exempt from the pause check and can call the function, but the beneficiary is resolved as `env::predecessor_account_id()` — i.e., the DAO account itself. The DAO calling `claim_lost_found` would attempt to remove the DAO's own entry from `lost_found` (which likely does not exist), not the affected user's entry. There is no parameter to specify a target account.

No other function in the production surface provides an alternative path to drain a specific user's `lost_found` balance.

---

### Impact Explanation

Any nBTC that has accumulated in `lost_found` for a user becomes completely inaccessible for the entire duration of a bridge pause. The DAO has no mechanism to rescue it on the user's behalf. The nBTC is already held by the bridge contract (it was never successfully transferred out), so it represents real user value that is stuck. This matches the allowed impact: **Medium — harmful smart-contract behavior without direct funds theft, including stuck bridge state requiring operator intervention**.

---

### Likelihood Explanation

Bridge pauses are a documented, reachable operational action. The `pa_pause_feature("ALL")` call is exercised in the test suite and is callable by any account holding the `PauseManager` role. The `lost_found` map is populated whenever an `ft_transfer` to a user fails, which can happen if the user is not registered in the nBTC contract — a realistic scenario. The combination of a pause event and at least one user with a non-zero `lost_found` balance is plausible during any emergency pause.

---

### Recommendation

Remove the `#[pause(except(roles(Role::DAO)))]` guard from `claim_lost_found`, or add an overloaded admin variant that accepts an explicit `account_id` parameter so the DAO can rescue funds on behalf of affected users while the bridge is paused. The analogous fix in the referenced amAMM report is to remove the "enabled" requirement from fund-recovery paths.

---

### Proof of Concept

1. User Alice initiates a withdrawal (`ft_transfer_call` → bridge).
2. The withdrawal is later cancelled via `cancel_withdraw`, which calls `internal_transfer_nbtc` to return Alice's nBTC.
3. The `ft_transfer` to Alice fails (Alice is not registered in the nBTC contract). `transfer_nbtc_callback` writes Alice's nBTC into `lost_found["alice"]`.
4. An emergency occurs; a `PauseManager` calls `pa_pause_feature("ALL")`.
5. Alice calls `claim_lost_found` with 1 yoctoNEAR attached → transaction reverts: `"Method is paused"`.
6. DAO calls `claim_lost_found` → the function removes `lost_found[DAO_ACCOUNT]`, which does not exist → transaction reverts: `"The account does not have lostfound"`.
7. Alice's nBTC remains locked in `lost_found` for the entire duration of the pause with no rescue path available.
