### Title
`execute_refund` Re-execution Blocked by Pending Sign Capacity Limit — (`contracts/satoshi-bridge/src/refund.rs`)

### Summary

The `execute_refund` function is explicitly designed to be called multiple times on the same refund request (to re-create the refund transaction after a consensus branch change or signing failure). However, `finalize_refund_with_psbt` applies `require_pending_sign_capacity` unconditionally before creating a new pending sign entry. When the same caller already holds a pending sign slot from the first execution, re-execution is permanently blocked, and no cleanup path exists while the refund request is still active.

### Finding Description

`execute_refund` (public, callable by any NEAR account) delegates to `internal_execute_refund`, which calls `finalize_refund_with_psbt`. Inside that function:

```rust
// refund.rs line 342
self.require_pending_sign_capacity(&caller);
```

`require_pending_sign_capacity` enforces:

```rust
// account.rs lines 113-123
require!(
    account.pending_sign_count() < self.get_max_pending_sign_txs(account_id),
    "Too many pending sign transactions"
);
```

The default limit returned by `get_max_pending_sign_txs` is **1** for any account not explicitly listed in `pending_tx_limits`.

After the first successful `execute_refund` call:
- A `BTCPendingInfo` entry is inserted into `btc_pending_infos` with state `Refund(PendingSign)`.
- The `btc_pending_id` is inserted into the caller's `btc_pending_sign_ids`.
- The refund request is kept with `executed = true` (explicitly documented: *"Keep the request so `execute_refund` can be called again"*).

If the chain-signature MPC network fails to sign the refund transaction, the pending sign entry remains in `btc_pending_sign_ids`. When the caller attempts re-execution (e.g., with a different gas fee producing a different PSBT hash / `btc_pending_id`), `require_pending_sign_capacity` fires and reverts with `"Too many pending sign transactions"`.

The caller cannot self-rescue via `remove_refund_pending_tx_id` because that function requires the refund request to be absent:

```rust
// refund.rs lines 419-424
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_keys[0]),
    "refund request still active"
);
```

Since the refund request is still active (`executed = true` but not finalized), this path is blocked. The caller's pending sign slot is permanently occupied by a stale entry until privileged operator action.

### Impact Explanation

The caller's pending sign capacity is exhausted by a stale, unsigned refund entry. The caller:
- Cannot re-execute their own refund (blocked by capacity check).
- Cannot remove the stale pending sign entry (blocked by "refund request still active").
- Cannot initiate any new withdrawal (same capacity check applies in `create_btc_pending_info`).

Resolution requires operator intervention: either `set_pending_tx_limit` to raise the caller's cap, or `reject_refund` to remove the request (which then allows `remove_refund_pending_tx_id`). This is a stuck bridge state requiring operator intervention, matching the medium-severity impact class.

### Likelihood Explanation

The scenario is reachable by any unprivileged user who:
1. Has a BTC deposit that was never finalized (e.g., amount below `min_deposit_amount`, or deposit address used before the bridge was ready).
2. Calls `request_refund` and waits for the timelock.
3. Calls `execute_refund` — the MPC signing pipeline stalls or the signed transaction is never broadcast.
4. Attempts to re-execute with a different gas fee.

MPC signing delays or failures are a realistic operational condition in a chain-signatures-based bridge. The default limit of 1 means any ordinary user hits this immediately.

### Recommendation

In `finalize_refund_with_psbt`, before calling `require_pending_sign_capacity`, check whether the caller already holds a stale pending sign entry for this specific refund request (i.e., a `BTCPendingInfo` in `Refund(PendingSign)` state whose UTXO key matches the current refund request). If so, remove the stale entry first, then proceed. This mirrors the intended re-execution semantics already documented in the code comments, and avoids treating a legitimate update as a new capacity-consuming operation.

Alternatively, introduce a dedicated `cancel_refund_pending_sign` function (callable by the refund request owner) that removes a stale `Refund(PendingSign)` entry even while the refund request is still active, restoring the capacity slot without requiring operator intervention.

### Proof of Concept

1. Alice deposits BTC; the deposit is never finalized (amount below `min_deposit_amount`).
2. Alice calls `request_refund(...)` — succeeds after Light Client verification.
3. After the timelock, Alice calls `execute_refund(utxo_key, None)`.
   - `finalize_refund_with_psbt` runs: `require_pending_sign_capacity` passes (count 0 < limit 1).
   - A `BTCPendingInfo` with `btc_pending_id = H1` is inserted; `btc_pending_sign_ids = {H1}`.
   - Refund request kept with `executed = true`.
4. MPC signing stalls; `H1` remains in `PendingSign` state indefinitely.
5. Alice calls `execute_refund(utxo_key, None)` again (same or different gas fee → same or different PSBT hash):
   - Same PSBT: panics with `"pending info already exist"`.
   - Different PSBT (e.g., higher gas fee): `require_pending_sign_capacity` fires → `"Too many pending sign transactions"`.
6. Alice calls `remove_refund_pending_tx_id(H1)` → panics with `"refund request still active"`.
