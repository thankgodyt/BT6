Audit Report

## Title
ERC1155 `safeTransferFrom` in `finTransfer` Permanently Freezes Bridged Tokens When Recipient Is a Non-Receiver Contract - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
`OmniBridge.finTransfer` delivers ERC1155 tokens via `IERC1155.safeTransferFrom`, which mandates that contract recipients implement `IERC1155Receiver`. If the MPC-signed `payload.recipient` is a contract that does not implement this interface, every relay attempt reverts unconditionally. Because the recipient address is committed inside the MPC signature and cannot be changed without a new signature, the ERC1155 tokens are permanently locked inside the bridge escrow with no user-accessible recovery path.

## Finding Description
In `finTransfer`, the nonce guard and nonce consumption occur at lines 283–287, before the ERC1155 transfer at lines 323–330:

```solidity
// L283-287
if (completedTransfers[payload.destinationNonce]) {
    revert NonceAlreadyUsed(payload.destinationNonce);
}
completedTransfers[payload.destinationNonce] = true;

// L323-330
} else if (multiToken.tokenAddress != address(0)) {
    IERC1155(multiToken.tokenAddress).safeTransferFrom(
        address(this),
        payload.recipient,
        multiToken.tokenId,
        payload.amount,
        ""
    );
```

Because Solidity transactions are atomic, a revert inside `safeTransferFrom` rolls back the `completedTransfers` write, leaving the nonce unconsumed. The same signed payload can therefore be resubmitted indefinitely — but every attempt will revert identically because `payload.recipient` is fixed by the MPC signature (line 298: `Borsh.encodeAddress(payload.recipient)`). Per EIP-1155, `safeTransferFrom` MUST invoke `onERC1155Received` on any contract recipient and MUST revert if the correct selector is not returned. Contracts that do not implement `IERC1155Receiver` (Gnosis Safe, DAO treasuries, yield vaults, generic proxy wallets) will always cause this revert. There is no admin rescue function, no pull-based fallback, and no alternative delivery path for ERC1155 tokens in the contract. The UUPS upgrade path exists but is not user-accessible. The `evm/SECURITY.md` does not list this as a known issue or accepted design decision.

## Impact Explanation
Any ERC1155 tokens bridged from EVM to NEAR and then back to an EVM contract address that does not implement `IERC1155Receiver` are permanently frozen inside `OmniBridge` with no on-chain user recovery path. This is a concrete, irreversible loss of bridged funds matching the critical impact class: **permanent freezing of bridged funds**.

## Likelihood Explanation
No privileged access is required. A user need only specify a non-`IERC1155Receiver` contract (e.g., a Gnosis Safe multisig, a DAO treasury, a yield vault) as the EVM recipient when initiating the return transfer on NEAR. Such contracts are ubiquitous in DeFi. The MPC nodes sign the payload as presented; they perform no validation of whether the recipient can accept ERC1155 tokens. The scenario is realistic, repeatable, and requires no attacker — a well-intentioned user bridging to their own multisig triggers it.

## Recommendation
Replace the `safeTransferFrom` delivery with a pull-based (claimable) pattern for ERC1155 tokens. On delivery failure, store the pending amount in a mapping keyed by `(nonce, recipient, tokenAddress, tokenId)` and expose a `claimERC1155` function that the recipient (or any caller on their behalf) can invoke. This avoids the receiver-callback requirement while preserving the nonce-consumption guarantee. Alternatively, wrap the `safeTransferFrom` in a `try/catch` and fall back to the claimable store on revert. A raw `transferFrom` without the "safe" prefix does not exist in the EIP-1155 standard and cannot be used as a drop-in replacement (the recommendation in the submitted report is incorrect on this point, but the vulnerability itself is valid).

## Proof of Concept
1. Deploy `NoReceiver`: a contract with no `onERC1155Received` implementation.
2. User holds ERC1155 token `T` (id=`X`, amount=`N`) on EVM. User calls `initTransfer1155(T, X, N, ...)` — tokens are locked in `OmniBridge`.
3. NEAR side mints wrapped tokens to the user.
4. User initiates return transfer on NEAR, specifying `NoReceiver`'s EVM address as recipient. MPC signs `TransferMessagePayload` with `recipient = address(NoReceiver)`.
5. Relayer calls `finTransfer(sig, payload)`.
6. `completedTransfers[nonce]` is set to `true` (L287).
7. `IERC1155(T).safeTransferFrom(bridge, NoReceiver, X, N, "")` is called (L324).
8. The ERC1155 token calls `NoReceiver.onERC1155Received(...)` — no such function → revert.
9. Entire transaction reverts; `completedTransfers[nonce]` is not persisted.
10. Every subsequent relay attempt with the same signed payload reverts at step 7.
11. Token `T` (id=`X`, amount=`N`) remains locked in `OmniBridge` forever; NEAR-side tokens are already burned. Net result: permanent loss of `N` units of ERC1155 token `T`.
