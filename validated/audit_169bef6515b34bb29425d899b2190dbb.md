## Title
Pending Transfer Not Removed After Non-Zero-Fee MPC Signing Enables Fee Recipient Manipulation — (File: near/omni-bridge/src/lib.rs)

## Summary

In `sign_transfer_callback`, the pending transfer is only removed from state when the fee is zero. For all fee-bearing transfers, the `TransferMessage` remains in `pending_transfers` indefinitely after a successful MPC signing. Because `fee_recipient` is a caller-supplied parameter not stored in `TransferMessage` and not validated against any prior signing, any trusted relayer can call `sign_transfer` again for the same `transfer_id` with an arbitrary `fee_recipient`, obtain a second valid MPC signature, and submit it to the destination chain to steal the bridge fee.

## Finding Description

`sign_transfer` accepts `fee_recipient: Option<AccountId>` as a caller-supplied argument and embeds it directly into the signed `TransferMessagePayload` without any validation against a stored value: [1](#0-0) 

The callback `sign_transfer_callback` only removes the transfer when the fee is zero: [2](#0-1) 

When `fee` is non-zero, `remove_transfer_message` is never called, leaving the transfer in `pending_transfers` after a successful signing. There is no signing-in-progress flag, no lock, and no record of which `fee_recipient` was previously signed for. The `TransferMessageStorageValue` struct stores no `fee_recipient` field: [3](#0-2) 

Any trusted relayer can therefore call `sign_transfer` again for the same `transfer_id` with a different `fee_recipient`, and the MPC signer will produce a second valid signature over a payload naming the attacker as fee recipient. The fee validation only checks that the supplied `fee` matches the stored transfer fee amount — it does not bind the signing to a specific recipient: [4](#0-3) 

## Impact Explanation

The attacker submits the fraudulent signature to the destination chain, which finalizes the transfer recording `fee_recipient = attacker`. The attacker then calls `claim_fee` on NEAR. In `claim_fee_callback`, the check `fee_recipient == predecessor_account_id` passes because the attacker is the fee recipient in the submitted proof: [5](#0-4) 

The transfer is then removed and the fee is paid to the attacker: [6](#0-5) 

The legitimate relayer's signature is rendered useless (destination nonce already consumed). This is direct theft of bridge fees — a concrete fee mis-accounting impact matching the allowed Critical scope.

## Likelihood Explanation

Any account can become a trusted relayer by calling `apply_for_trusted_relayer` with the required stake deposit and waiting for the activation period to elapse — no DAO approval is required in the default auto-promotion flow: [7](#0-6) 

Once registered, the attacker can exploit every fee-bearing transfer for the entire lifetime of the transfer in `pending_transfers`. No special timing, front-running, or external coordination is required. The window of exploitation is unbounded.

## Recommendation

After a successful MPC signing for a fee-bearing transfer, record the `fee_recipient` inside the stored `TransferMessage` (or in a separate map keyed by `transfer_id`). On any subsequent call to `sign_transfer` for the same `transfer_id`, require that the supplied `fee_recipient` matches the stored value. Alternatively, remove the transfer from `pending_transfers` immediately upon successful signing (regardless of fee) and re-insert it with the locked `fee_recipient`, so that no second signing with a different recipient is possible.

## Proof of Concept

1. User initiates a transfer with `fee = 100` tokens via `ft_on_transfer → init_transfer`. Transfer is stored in `pending_transfers` with `transfer_id = T`.
2. Malicious trusted relayer calls `sign_transfer(T, fee_recipient = attacker, fee = Some(100))`. MPC produces `sig_B`. `sign_transfer_callback` runs: fee is non-zero, so `remove_transfer_message` is skipped — transfer remains in `pending_transfers`.
3. Malicious relayer submits `sig_B` to the destination chain. The destination chain finalizes the transfer and records `fee_recipient = attacker`.
4. Malicious relayer calls `claim_fee` on NEAR with the proof from step 3. `claim_fee_callback` verifies `fee_recipient == predecessor_account_id` (attacker == attacker ✓), removes the transfer, and sends the fee to the attacker.
5. Any legitimate relayer's signature for the same transfer is now useless (destination nonce consumed). The fee is fully stolen.

A private-testnet integration test can reproduce this by: (a) registering two trusted relayer accounts, (b) initiating a fee-bearing transfer, (c) having the malicious relayer call `sign_transfer` with its own account as `fee_recipient`, (d) mocking the destination-chain proof with `fee_recipient = attacker`, and (e) calling `claim_fee` — asserting the attacker receives the fee and the legitimate relayer receives nothing.
