### Title
Peras Vote and Certificate Signature Verification Bypass via Degenerate `BlockSupportsPeras` Instance - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance used in production inbound vote and certificate handlers performs no cryptographic authorization checks. `validatePerasCert` unconditionally accepts every certificate, and `validatePerasVote` only checks that a claimed voter ID exists in the stake distribution — it never verifies a cryptographic signature proving the submitter controls that voter's key. Because the `PerasVote` data type in this instance carries no signature field at all, authorization cannot be verified even in principle. An unprivileged peer can submit votes impersonating any registered stake pool and certificates for any block, causing the node to forge and accept Peras weight-boost certificates for attacker-chosen blocks.

---

### Finding Description

**Root cause — `validatePerasCert` (no-op validation):**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

Every certificate received from any peer is unconditionally accepted and assigned a weight boost. No aggregate signature, no voter eligibility, no round-number consistency check is performed. [1](#0-0) 

**Root cause — `validatePerasVote` (stake-lookup only, no signature):**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
```

The only check is whether `pvVoteVoterId` (a `KeyHash StakePool` embedded in the vote) appears in the stake distribution. There is no signature field in the `PerasVote` data type and no cryptographic proof that the submitter controls the claimed voter key. [2](#0-1) 

**Structural gap — `PerasVote` carries no signature:**

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound  :: PerasRoundNo
  , pvVoteBlock  :: Point blk
  , pvVoteVoterId :: PerasVoterId
  }
```

Unlike the `WFALS` and `EveryoneVotes` committee implementations (which include a `VoteSignature` field and call `verifyVoteSignature`), the degenerate instance's `PerasVote` type has no cryptographic content. Authorization is structurally impossible. [3](#0-2) 

**Attacker-reachable entry path — production inbound handlers:**

Both production inbound handlers for network-received votes wire directly to the degenerate `validatePerasVote`:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [4](#0-3) [5](#0-4) 

Both production inbound handlers for network-received certificates wire directly to the degenerate `validatePerasCert`:

```haskell
(validatePerasCert mkPerasParams)
``` [6](#0-5) [7](#0-6) 

The `processVotes` and `processCerts` functions accept any vote/cert that passes these checks and add it to the database, potentially triggering certificate forging and chain-selection side-effects. [8](#0-7) [9](#0-8) 

**Contrast with correct committee implementations:**

The `EveryoneVotes` and `WFALS` committee implementations both call `verifyVoteSignature` and `verifyCert` with full aggregate-signature verification. The degenerate instance skips all of this. [10](#0-9) [11](#0-10)

### Impact Explanation

**Bypass of Peras voting and certificate checks enabling unauthorized certificate acceptance.**

An unprivileged peer that knows any registered stake pool's `KeyHash` (publicly available on-chain) can:

1. Craft `PerasVote` messages claiming to be that pool, for any block of the attacker's choice.
2. Submit enough such votes to reach quorum (the attacker controls the claimed voter IDs and their associated stake weights from the public stake distribution).
3. The node's `updatePerasRoundVoteState` logic will forge a `ValidatedPerasCert` boosting the attacker-chosen block.
4. Alternatively, submit a crafted `PerasCert` directly; it is accepted unconditionally.

The forged certificate adds `perasWeight` to the attacker-chosen block in chain selection. Under Peras, this weight boost can cause an honest node to prefer a chain it would otherwise reject, constituting a chain-selection integrity failure. This maps to the allowed impact: **bypass of Peras voting/certificate checks enabling unauthorized certificate acceptance**.

---

### Likelihood Explanation

**High.** The attacker needs only:
- A network connection to a Cardano node running Peras-enabled code (no privileged access).
- Knowledge of registered stake pool key hashes (fully public, available from any chain explorer or the ledger state).
- The ability to send well-formed `PerasVote` or `PerasCert` wire messages.

No key material, no stake, no special role is required. The degenerate instance is the active instance for all `StandardHash blk` blocks, which covers all Cardano block types. The inbound handlers are wired and active in the codebase.

---

### Recommendation

1. **Remove or gate the degenerate instance.** The `instance StandardHash blk => BlockSupportsPeras blk` at line 320 is explicitly marked as a temporary placeholder. It must not be reachable from production inbound handlers. Either remove it entirely or guard it behind a compile-time flag that is never set in production builds. [12](#0-11) 

2. **Add a signature field to `PerasVote`.** The degenerate `PerasVote` type carries no `VoteSignature`. Any production `PerasVote` type must include a cryptographic signature (as `EveryoneVotes` and `WFALS` do) so that `validatePerasVote` can verify it. [13](#0-12) 

3. **Implement real validation before wiring to inbound handlers.** The `validatePerasCert` and `validatePerasVote` functions called from `makePerasVotePoolWriterFromChainDB` and `makePerasCertPoolWriterFromChainDB` must perform full cryptographic verification (aggregate signature check for certs, individual signature + eligibility proof for votes) before any vote or certificate is admitted to the database.

---

### Proof of Concept

**Preconditions:** Attacker has a TCP connection to a node with Peras inbound handlers active. Attacker reads the current stake distribution to obtain any registered pool's `PerasVoterId` (= `KeyHash StakePool`).

**Steps:**

1. Attacker constructs `N` `PerasVote` messages, each with:
   - `pvVoteRound` = current Peras round
   - `pvVoteBlock` = attacker-chosen block point
   - `pvVoteVoterId` = `PerasVoterId` of a real pool with sufficient stake

2. Attacker sends these votes to the target node via the Peras vote diffusion mini-protocol.

3. `processVotes` calls `validatePerasVote mkPerasParams sd vote` for each vote. Since `lookupPerasVoteStake` finds the claimed voter ID in the stake distribution, each vote returns `Right ValidatedPerasVote{..}` with the pool's stake weight. [14](#0-13) 

4. Votes are added to the `PerasVoteDB`. `updatePerasRoundVoteStates` accumulates stake. Once `stakeAboveThreshold` is satisfied, `forgePerasCert` is called and a `ValidatedPerasCert` is produced for the attacker-chosen block. [15](#0-14) 

5. The certificate is stored and its weight boost is applied in chain selection, causing the node to prefer the attacker-chosen block over the honest chain.

**For the certificate path:** Attacker directly sends a `PerasCert{pcCertRound=r, pcCertBoostedBlock=attackerBlock}`. `validatePerasCert` returns `Right` unconditionally, the certificate is stored, and the weight boost is applied. [16](#0-15)

  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool

      mapM_
        (addVote . WithArrivalTime now)

    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
