### Title
Silent Token Retention on Unregistered Recipient in `safe_mint` — (File: `contracts/nbtc/src/lib.rs`)

### Summary

`safe_mint` in the nBTC contract mints tokens to the bridge's own account **before** checking whether the recipient has registered storage. If the recipient is unregistered, the function silently returns `U128(0)` and exits, leaving the minted nBTC permanently stranded in the bridge's account while the user's BTC deposit is already locked in the bridge's Bitcoin UTXO.

### Finding Description

In `contracts/nbtc/src/lib.rs`, the `safe_mint` function executes in this order:

1. `self.token.internal_deposit(&self.bridge_id, amount.into())` — unconditionally mints `amount` nBTC into the bridge's own token balance.
2. `if self.token.accounts.get(&account_id).is_none() { return PromiseOrValue::Value(U128(0)); }` — if the intended recipient has no registered storage account, the function returns early with zero, **without transferring or burning the already-minted tokens**. [1](#0-0) 

The minted tokens remain credited to `self.bridge_id` inside the nBTC contract. There is no automatic burn, no lost-and-found entry, and no refund of the underlying BTC UTXO triggered by this silent early return. The `lost_found` map in the bridge contract is only populated on failed `ft_transfer` cross-contract calls, not on this synchronous early-return path. [2](#0-1) 

The analog to the reported `SEuroOffering` bug is exact: an `if` guard silently skips the asset delivery instead of reverting, leaving assets inaccessible inside the contract.

### Impact Explanation

- The user's BTC is locked in a bridge-controlled Bitcoin UTXO (derived from the deposit address).
- The corresponding nBTC is minted to the bridge's own account and is not accessible to the user.
- The user holds no nBTC and therefore cannot initiate a withdrawal to recover their BTC.
- Without explicit operator intervention (manual transfer or burn + BTC refund), the funds are permanently lost to the user.

**Impact class: Critical — Significant permanent locking of user funds.**

### Likelihood Explanation

Any deposit where the `recipient_id` in the `DepositMsg` has not called `storage_deposit` on the nBTC contract triggers this path. This is a realistic and common scenario: a user may specify a fresh account, a smart-contract account, or any account that has never interacted with the nBTC token. No special attacker knowledge is required; the victim triggers it themselves by depositing BTC with an unregistered recipient. [3](#0-2) 

### Recommendation

Revert (panic) instead of silently returning when the recipient account is unregistered:

```rust
require!(
    self.token.accounts.get(&account_id).is_some(),
    "Recipient account is not registered in the nBTC contract"
);
```

This ensures the entire deposit transaction fails atomically before any tokens are minted, so the bridge can handle the failure in its callback and either retry or initiate a refund. Alternatively, auto-register the recipient account (charging the caller for storage) before minting.

### Proof of Concept

1. Alice sends 0.01 BTC to the bridge deposit address derived from `DepositMsg { recipient_id: "alice-new.near", ... }`.
2. A relayer calls `verify_deposit` on `satoshi-bridge`. The light-client proof passes.
3. The bridge calls `safe_mint("alice-new.near", 1_000_000, None)` on the nBTC contract.
4. `internal_deposit(&self.bridge_id, 1_000_000)` executes — 1,000,000 satoshi-nBTC are credited to the bridge's account.
5. `self.token.accounts.get(&"alice-new.near")` returns `None` (Alice never registered storage).
6. The function returns `PromiseOrValue::Value(U128(0))` — no transfer, no burn, no revert.
7. Alice's BTC UTXO is now owned by the bridge's MPC key. Alice holds 0 nBTC and has no mechanism to recover her BTC without operator intervention. [1](#0-0)

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }
