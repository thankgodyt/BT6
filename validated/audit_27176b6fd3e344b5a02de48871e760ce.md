### Title
Peras Certificate Validation Bypass: `validatePerasCert` Unconditionally Returns Success - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary
The universal `BlockSupportsPeras` instance provides a `validatePerasCert` implementation that unconditionally returns `Right` (success) without performing any cryptographic or structural validation. Any Peras certificate received from an unprivileged peer via the object-diffusion mini-protocol is accepted as valid, enabling unauthorized chain boosting and chain-selection manipulation.

### Finding Description
The external report describes a `conditionCheck` modifier that fails to revert when all conditions are `Logic.OR`-typed and none return `true` — the loop exits without a failure flag, so execution proceeds as if validation passed. The structural analog here is `validatePerasCert` in the catch-all `BlockSupportsPeras` instance: instead of iterating over conditions that all silently pass, the function skips every condition entirely and always returns success.

In `SupportsPeras.hs`, the universal instance is declared for all block types:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
instance StandardHash blk => BlockSupportsPeras blk where
``` [1](#0-0) 

Within that instance, `validatePerasCert` is implemented as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [2](#0-1) 

No signature check, no quorum check, no round-number check, no structural check — the function returns `Right` for every input. The `PerasValidationErr` type exists but is never raised:

```haskell
data PerasValidationErr blk
  = PerasValidationErr
  deriving stock (Show, Eq)
``` [3](#0-2) 

The validated certificate carries a `vpcCertBoost` field that directly feeds into chain-weight computation:

```haskell
data ValidatedPerasCert blk = ValidatedPerasCert
  { vpcCert      :: !(PerasCert blk)
  , vpcCertBoost :: !PerasWeight
  }
``` [4](#0-3) 

The call site is the production object-diffusion mini-protocol pool for Peras certificates:

```
ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/

```



Grep confirms `validatePerasCert` is referenced in exactly two files: the definition site and `PerasCert.hs`, meaning the production network ingestion path is the only consumer.

The same pattern applies to `validatePerasVote`, which omits signature verification and only checks stake-distribution membership:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [5](#0-4) 

### Impact Explanation
A `ValidatedPerasCert` produced by this function is used to apply a `PerasWeight` boost to a chain during chain selection. Because `validatePerasCert` accepts every certificate unconditionally, an adversary can craft a `PerasCert` with an arbitrary boosted block and an invalid (or entirely absent) aggregate BLS signature. The node will wrap it in a `ValidatedPerasCert` with the full configured `perasWeight` boost and use it to prefer the adversary's chosen chain over the honest canonical chain. This is a bypass of Peras certificate/signature validation that enables unauthorized certificate acceptance and chain-selection manipulation — matching the "Critical: bypass of Peras voting or certificate checks" impact class.

### Likelihood Explanation
The entry path is the object-diffusion mini-protocol, reachable by any unprivileged peer that can establish a connection to the node. No key material, stake, or operator access is required. The attacker only needs to send a well-formed `PerasCert` CBOR message; the node's validation layer will accept it without any cryptographic check.

### Recommendation
Replace the stub `validatePerasCert` implementation with a real one that:
1. Verifies the aggregate BLS signature over `(electionId, candidate)` using the aggregated verification keys of the listed voters.
2. Checks that the certificate's round number is consistent with the current ledger view.
3. Checks that the boosted block point is a known, valid block on the candidate chain.
4. Raises a concrete `PerasValidationErr` variant for each failure mode.

Until the real implementation is in place, the node should refuse to process incoming Peras certificates from the network (e.g., by returning `Left PerasValidationErr` unconditionally) rather than accepting them all.

The same remediation applies to `validatePerasVote`: add actual vote-signature verification before accepting a vote as `ValidatedPerasVote`.

### Proof of Concept
1. Attacker connects to a node running the Peras object-diffusion mini-protocol.
2. Attacker constructs a `PerasCert` with `pcCertRound = <current round>` and `pcCertBoostedBlock = <attacker-chosen block point>`, with a zeroed or random aggregate signature.
3. Attacker sends the certificate over the mini-protocol.
4. The node calls `validatePerasCert params cert`, which executes:
   ```haskell
   Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
   ```
   — no signature check is performed, `Right` is returned.
5. The node stores the `ValidatedPerasCert` and applies `vpcCertBoost` to the attacker-chosen block's chain weight.
6. Chain selection now prefers the attacker-chosen chain over the honest canonical chain, violating Peras safety.
