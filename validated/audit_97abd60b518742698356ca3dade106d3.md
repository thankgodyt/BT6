### Title
ChainSync `checkPreferTheirsOverOurs` Uses Zero Peras Weight, Creating Dual-Path Chain-Selection Conflict When Peras Is Enabled — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

When Peras is enabled, the ChainSync client's `checkPreferTheirsOverOurs` function compares candidate chains against the current selection using `emptyPerasWeightSnapshot` (zero Peras weight), while the main chain-selection path in `chainSelectionForBlock` uses the real, live `PerasWeightSnapshot`. This dual-path conflict is the direct analog of the JBX delegate architecture forcing zero slippage: one code path zeroes out the critical weight parameter, making the downstream comparison inconsistent with the authoritative path. A peer serving a legitimately heavier Peras-boosted chain that has fewer raw blocks than the node's current selection will be incorrectly disconnected, and the node will remain on the lighter (non-canonical) chain.

---

### Finding Description

**Root cause — the zeroed weight in `checkPreferTheirsOverOurs`:**

In `Ouroboros.Consensus.MiniProtocol.ChainSync.Client`, the function `checkPreferTheirsOverOurs` is invoked when a received header lies beyond the forecast horizon. Its purpose is to decide whether to keep syncing from the peer or disconnect (`CandidateTooSparse`). The comparison is:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← always zero Peras weight
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
```

`emptyPerasWeightSnapshot` is `PerasWeightSnapshot Map.empty`, which returns `mempty` (i.e. `PerasWeight 0`) for every point. The comparison therefore reduces to a pure block-count comparison, ignoring all Peras certificate boosts.

**The conflicting authoritative path — `chainSelectionForBlock`:**

The main chain-selection path reads the live weight snapshot from the ChainDB and uses it for every candidate comparison:

```haskell
chainSelectionForBlock cdb@CDB{..} blockCache hdr punish = electric $ do
  (invalid, curChain, weights) <-
    atomically $
      (,,)
        <$> (forgetFingerprint <$> readTVar cdbInvalid)
        <*> Query.getCurrentChain cdb
        <*> (forgetFingerprint <$> Query.getPerasWeightSnapshot cdb)  -- real weights
  ...
  ShouldSwitch reason <- [preferAnchoredCandidate bcfg weights curChain $ Diff.getSuffix chain]
```

`preferAnchoredCandidate` with a non-empty snapshot computes `wsvTotalWeight = blockNo + weightBoost` for each fragment suffix after their intersection, so Peras boosts are fully accounted for.

**The conflict:**

| Code path | Weight snapshot used | Comparison basis |
|---|---|---|
| `checkPreferTheirsOverOurs` | `emptyPerasWeightSnapshot` | Block count only |
| `chainSelectionForBlock` | Live `PerasWeightSnapshot` | Block count + Peras boosts |

When Peras is active and a peer's chain has fewer blocks but enough Peras boosts to make it heavier:

1. `checkPreferTheirsOverOurs` evaluates `preferAnchoredCandidate ... emptyPerasWeightSnapshot ourFrag theirFrag` → `ShouldNotSwitch` (their block count is lower) → throws `CandidateTooSparse` → **disconnects from the peer**.
2. Had the real snapshot been used, `preferAnchoredCandidate` would have computed `wsvTotalWeight` including the boosts → `ShouldSwitch` → the peer would have been kept and the heavier chain eventually adopted.

The node is left on the lighter (non-canonical) chain with no path to recover from that peer.

---

### Impact Explanation

**High. Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.**

Concretely: an adversary holding a chain with more raw blocks but less total Peras weight than the honest canonical chain can cause a victim node to:

1. Disconnect from every honest peer whose Peras-boosted chain has fewer blocks than the adversary's chain.
2. Remain permanently on the adversary's lighter chain.

The node's selection diverges from the canonical Peras-weighted chain without any cryptographic compromise. The adversary needs only to have served the node a longer-but-lighter chain before the honest peers' Peras-boosted chain arrives beyond the forecast horizon.

---

### Likelihood Explanation

**Medium.** Peras is not yet enabled on Cardano mainnet, but the code is present and the feature is under active development. Once Peras is activated, any scenario where the canonical chain has fewer blocks but higher Peras weight than a competing chain (the normal operating condition after a quorum of certificates is issued) will trigger this bug for nodes that receive the Peras-boosted chain headers beyond their forecast horizon. The TODO comment at line 1841 explicitly acknowledges the issue is known and unresolved.

---

### Recommendation

Replace `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live `PerasWeightSnapshot` read from the ChainDB, consistent with how `chainSelectionForBlock` obtains it. The comparison must use the same weight basis as the authoritative chain-selection path to avoid the dual-path conflict. The existing TODO at line 1841 points to issue #64 in the Peras tracker, which should be resolved before Peras is enabled in production.

---

### Proof of Concept

**Setup (private testnet with Peras enabled, boost weight B = 15):**

1. Node N has current selection: chain C₀ of length 100, no Peras boosts → total weight = 100.
2. Honest peer P serves chain C₁: length 95, two Peras-boosted blocks each with boost 15 → total weight = 95 + 30 = 125.
3. C₁'s tip is beyond N's forecast horizon (e.g. the intersection is at block 80, and C₁ extends 15 blocks past the forecast window).

**Execution:**

4. ChainSync client on N receives a header from P that is beyond the forecast horizon.
5. `checkPreferTheirsOverOurs` is called with `ourFrag` = C₀ suffix (length 20), `theirFrag` = C₁ suffix (length 15).
6. `preferAnchoredCandidate ... emptyPerasWeightSnapshot ourFrag theirFrag`:
   - `wsvTotalWeight ours` = `PerasWeight 20` (block count only, no boosts)
   - `wsvTotalWeight cand` = `PerasWeight 15` (block count only, boosts ignored)
   - Result: `ShouldNotSwitch GT` → `throwSTM CandidateTooSparse` → **P is disconnected**.
7. Had real weights been used: `wsvTotalWeight cand` = `PerasWeight (15 + 30)` = 45 > 20 → `ShouldSwitch` → P would have been retained and C₁ eventually adopted.

preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"
        Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
          case preferCandidate
            (projectChainOrderConfig cfg)
            (weightedSelectView cfg weights oursSuffix)
            (weightedSelectView cfg weights candSuffix) of
            ShouldSwitch r -> ShouldSwitch (Left r)
            ShouldNotSwitch o -> ShouldNotSwitch o
