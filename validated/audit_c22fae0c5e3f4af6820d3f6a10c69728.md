Audit Report

## Title
Unchecked Multiplication Overflow in `denormalize_amount()` Causes Permanent Loss of Bridged Funds - (File: `near/omni-bridge/src/lib.rs`)

## Summary

`denormalize_amount()` performs a bare `u128` multiplication with no overflow guard. With `overflow-checks = true` in the workspace profile, any call where `amount × 10^(origin_decimals − decimals)` exceeds `u128::MAX` panics and reverts all NEAR state. Because the user's tokens are already burned or locked on the EVM side before the NEAR proof is submitted, and no EVM-side refund path exists, the funds are permanently lost. This is a distinct issue from the CLAUDE.md false-positive #2, which covers only the subtraction underflow when `origin_decimals < decimals`.

## Finding Description

**Root cause — unchecked multiplication:**

`denormalize_amount` at lines 2776–2779 of `near/omni-bridge/src/lib.rs`:

```rust
fn denormalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount * (10_u128.pow(diff_decimals))   // panics on overflow
}
``` [1](#0-0) 

`overflow-checks = true` is set in the workspace release profile: [2](#0-1) 

**Call site — `fin_transfer_callback`:**

The function is called at line 725 with `init_transfer.amount.0`, a value read directly from the verified EVM `InitTransfer` event proof: [3](#0-2) 

**EVM side — no upper-bound validation:**

The EVM `initTransfer` accepts any `uint128 amount` and only validates `fee < amount`. It burns or locks the tokens and emits the event with the raw amount:

```solidity
function initTransfer(address tokenAddress, uint128 amount, uint128 fee, ...)
    external payable whenNotPaused(PAUSED_INIT_TRANSFER) {
    if (fee >= amount) { revert InvalidFee(); }
    // burns/locks tokens, then:
    emit BridgeTypes.InitTransfer(..., amount, fee, ...);
}
```

**Overflow condition:**

`Decimals` stores `decimals` (NEAR-side) and `origin_decimals` (origin-chain-side): [4](#0-3) 

The design explicitly expects `origin_decimals >= decimals` (CLAUDE.md false-positive #2 confirms this is the intended configuration): [5](#0-4) 

When `origin_decimals > decimals` (e.g., `origin_decimals=24`, `decimals=18`, `diff=6`), overflow occurs for any `amount > u128::MAX / 10^6 ≈ 3.4 × 10^32`. The EVM contract accepts up to `uint128::MAX`, so a user can supply an amount in this overflow range.

**Why existing checks are insufficient:**

- The EVM contract has no upper-bound check beyond `fee < amount`.
- The NEAR prover verifies cryptographic proof validity but does not validate the magnitude of the amount field.
- The `fin_transfer_callback` validates the factory address and token decimals existence, but performs no range check on `amount` before calling `denormalize_amount`.
- The CLAUDE.md false-positive note #2 explicitly covers only the subtraction underflow (`origin_decimals < decimals`), not this multiplication overflow.

## Impact Explanation

When the panic fires inside `fin_transfer_callback`:

1. NEAR's transaction atomicity reverts all state mutations in the callback (no `TransferMessage` is stored, no tokens are minted or released).
2. The EVM tokens were already burned or locked irreversibly before the proof was submitted.
3. There is no EVM-side refund mechanism triggered by NEAR finalization failure.
4. Every subsequent retry of `fin_transfer` with the same proof will produce the same overflow panic, making recovery impossible.

This constitutes **permanent freezing/loss of bridged funds** — a concrete match to the Critical allowed impact: *"Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds."*

## Likelihood Explanation

- **Precondition 1:** A token must be registered with `origin_decimals > decimals`. This is an explicitly supported and expected configuration per the design.
- **Precondition 2:** The user must supply an `amount` on EVM that, after multiplication by `10^diff_decimals`, exceeds `u128::MAX`. For `diff=6`, the threshold is `~3.4 × 10^32` in normalized units — astronomically large for high-value tokens, but reachable for low-value, high-supply tokens (e.g., meme tokens) where `uint128::MAX` supply is plausible.
- **Trigger:** The user calls `initTransfer` on EVM with the overflow-inducing amount. A trusted relayer then submits the proof via `fin_transfer`, which calls `fin_transfer_callback`. The relayer is not required to pre-validate amount magnitudes.
- **Repeatability:** The panic is deterministic; every retry fails identically.

Likelihood is **low** for high-value tokens but **non-zero** for low-value tokens with large supplies. The impact when triggered is irreversible.

## Recommendation

Replace the bare multiplication with a checked variant and handle overflow gracefully rather than panicking:

```rust
fn denormalize_amount(amount: u128, decimals: Decimals) -> Option<u128> {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    let multiplier = 10_u128.checked_pow(diff_decimals)?;
    amount.checked_mul(multiplier)
}
```

In `fin_transfer_callback`, if `denormalize_amount` returns `None`, the callback should return an error or emit a failure event rather than panicking, so that the transfer ID is recorded as permanently unprocessable and an off-chain refund flow can be initiated. Additionally, consider adding an upper-bound validation on `amount` at the EVM `initTransfer` level to reject amounts that would overflow after denormalization.

## Proof of Concept

**Minimal unit test (add to `near/omni-bridge/src/tests/lib_test.rs`):**

```rust
#[test]
#[should_panic]
fn test_denormalize_overflow_panics() {
    // origin_decimals=24, decimals=18 → diff=6
    // u128::MAX * 10^6 overflows u128
    Contract::denormalize_amount(
        u128::MAX,
        Decimals {
            decimals: 18,
            origin_decimals: 24,
        },
    );
}
```

This test will pass (i.e., the panic is confirmed) when compiled with `overflow-checks = true` (the release profile setting). The existing test suite already tests non-overflowing cases with `u64::MAX` inputs: [6](#0-5) 

**End-to-end scenario:**

1. Register a token with `origin_decimals=24`, `decimals=18` on the NEAR bridge.
2. On EVM, call `initTransfer(tokenAddress, amount=u128::MAX, fee=0, ...)` — tokens are burned.
3. Submit the resulting proof via `fin_transfer` on NEAR.
4. Observe `fin_transfer_callback` panic with an arithmetic overflow.
5. Confirm no `TransferMessage` was stored and no tokens were minted on NEAR.
6. Confirm no refund is available on EVM.
