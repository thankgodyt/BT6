Audit Report

## Title
Silent Permanent Loss of Native Fees via Detached Promise in `send_fee_internal` — (`near/omni-bridge/src/lib.rs`)

## Summary

`claim_fee_callback` unconditionally removes the transfer message from storage at line 1094 before dispatching fee payments. The native-fee leg inside `send_fee_internal` is dispatched with `.detach()` (lines 2669–2672), making it fire-and-forget. If the native-token `mint` call fails for any reason (e.g., unregistered storage on the token contract), the failure is silently discarded, the transfer record is already gone, and the relayer permanently loses their earned native fee with no recovery path.

## Finding Description

**Exact code path:**

1. `claim_fee_callback` (line 1094) calls `self.remove_transfer_message(fin_transfer.transfer_id)`, permanently deleting the transfer record from storage. This state mutation is committed synchronously and is not rolled back by any subsequent promise failure in NEAR's execution model.

2. At line 1133, `send_fee_internal` is called. Inside (lines 2656–2673), when `native_fee > 0` and the origin chain is an EVM chain, the following executes:
   ```rust
   ext_token::ext(self.get_native_token_id(origin_chain))
       .with_static_gas(MINT_TOKEN_GAS)
       .mint(fee_recipient.clone(), transfer_message.fee.native_fee, None)
       .detach();  // failure silently discarded
   ```
   The `.detach()` call schedules the cross-contract call but never inspects its result. If the token contract panics (e.g., `fee_recipient` has no storage registered), the panic is silently swallowed.

3. Because the transfer record was already removed at step 1, there is no state to retry from. The native fee is permanently undeliverable.

**Why existing checks fail:**

`process_fin_transfer_to_near` (lines 1935–1948) enforces that the caller pre-registers storage for the native fee recipient via `StorageNativeFeeRecipientOmitted`. The `claim_fee` entry point (lines 1057–1064) has no equivalent check — it accepts no `storage_deposit_actions` parameter and performs no storage registration for the native token contract before dispatching the mint.

## Impact Explanation

This is a concrete instance of **fee mis-accounting** under the allowed Critical impact scope: a relayer who completes a cross-chain transfer with `native_fee > 0` (EVM → NEAR) permanently loses their earned native fee (a bridged wrapped-native token, e.g., wETH) if the `mint` call fails. The fee is neither delivered nor recoverable — the transfer record is gone, the detached promise result is never inspected, and no retry mechanism exists. This constitutes permanent loss of bridged funds belonging to the relayer.

## Likelihood Explanation

- `native_fee > 0` is a supported fee path for EVM-origin transfers.
- NEAR's NEP-141 token standard requires storage registration before receiving tokens. A relayer who has not previously interacted with the wrapped-native-token contract will have no storage registered.
- `claim_fee` provides no mechanism to pre-register storage (unlike `fin_transfer`), so a first-time relayer on a given native token is structurally exposed.
- No privileged access or external collusion is required — any trusted relayer processing such a transfer triggers this path via a normal public contract call.
- The condition is repeatable and deterministic: every `claim_fee` call with `native_fee > 0` where the relayer lacks storage registration on the native token contract will silently lose the native fee.

## Recommendation

1. **Remove the transfer message only after fee delivery succeeds.** Restructure `claim_fee_callback` to dispatch fees first and handle the result in a subsequent callback (mirroring the `fin_transfer_send_tokens_callback` pattern) that removes the transfer message only on success.
2. **Do not use `.detach()` for value-bearing promises.** Chain the native-fee mint into the main promise sequence so failures are observable and state can be rolled back or retried.
3. **Require storage-deposit actions for the native-token recipient in `claim_fee`**, consistent with the `StorageNativeFeeRecipientOmitted` guard already enforced in `process_fin_transfer_to_near` (lines 1935–1948).

## Proof of Concept

1. A relayer executes a fast transfer for an EVM → NEAR message where `native_fee = 1e18` (1 wETH equivalent). The relayer has **not** registered storage on the wrapped-native-token contract.
2. The relayer calls `claim_fee` with a valid `FinTransfer` proof.
3. `claim_fee_callback` fires:
   - Line 1094: `remove_transfer_message` — transfer record deleted, state committed.
   - Line 1133: `send_fee_internal` called.
4. Inside `send_fee_internal` (lines 2669–2672): the native-token `mint` is dispatched with `.detach()`. The token contract panics (no storage for `fee_recipient`). The panic is silently discarded.
5. The token-fee `ft_transfer` or `mint` (lines 2686–2698) is returned as the main promise and succeeds.
6. **Result**: the relayer receives the token fee but permanently loses the native fee. The transfer message is gone; no retry is possible.

**Test plan**: Write a NEAR sandbox integration test that (a) sets up a transfer message with `native_fee > 0` on an EVM-origin chain, (b) calls `claim_fee` from a relayer account with no storage registered on the native token contract, and (c) asserts that the transfer record is absent post-call while the relayer's native token balance remains zero — confirming silent loss.
