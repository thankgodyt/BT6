### Title
Caller-Controlled `gas_fee` in Refund Request Enables Near-Total Theft of User Refund Funds — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

The `request_refund` flow accepts a caller-supplied `gas_fee` parameter with no upper-bound validation beyond requiring it to be strictly less than the deposit amount. Any unprivileged account that front-runs the legitimate relayer can submit a refund request with `gas_fee = amount - 1`, causing the user to receive only 1 satoshi from their refund while the remainder is consumed as a Bitcoin miner fee. The user's original deposit transaction is the only "confirmation" they ever provide, and it contains no gas-fee commitment; the actual signed refund transaction can therefore carry a fee radically different from any reasonable expectation.

---

### Finding Description

In `request_refund_callback` the resolved gas fee is either the caller-supplied value or the configured default:

```rust
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
``` [1](#0-0) 

The only guard is `resolved_gas_fee < amount`. There is no check against a configured maximum refund gas fee (e.g., `config.max_btc_gas_fee` or a dedicated `max_refund_gas_fee`). The resolved value is then stored verbatim in the `RefundRequest`:

```rust
let refund_request = RefundRequest {
    ...
    gas_fee: resolved_gas_fee,
    ...
};
``` [2](#0-1) 

Later, `refund_execution_inputs` computes the user's payout as `amount - gas_fee` with no further validation:

```rust
let refund_amount = refund_request
    .amount
    .checked_sub(refund_request.gas_fee)
    .expect("Deposit amount too small to cover gas fee");
require!(refund_amount > 0, "Refund amount is zero after gas fee");
``` [3](#0-2) 

The duplicate-request guard (`"Refund request already exists for this UTXO"`) means only the **first** caller for a given UTXO wins: [4](#0-3) 

The timelock comments in `resolve_execute_refund_timelock` explicitly acknowledge that `request_refund` is callable by untrusted public accounts:

```rust
// Refund address supplied by caller of `request_refund`: longer
// timelock to give DAO/Operator time to reject suspicious requests.
config.unsafe_refund_timelock_sec
``` [5](#0-4) 

This confirms the public entry path. The DAO's ability to call `internal_reject_refund` is an operational mitigation, not a code-level bound, and it requires the DAO to monitor every request and act within the timelock window.

---

### Impact Explanation

A user deposits BTC with a `deposit_msg` that embeds a `refund_address`. If the deposit cannot be claimed (e.g., wrong amount, invalid message), the user expects a refund of `deposit_amount - reasonable_gas_fee`. An attacker who front-runs the legitimate relayer can store a refund request with `gas_fee = deposit_amount - 1`. After the timelock elapses, `execute_refund` builds and signs a Bitcoin transaction that pays the user 1 satoshi and sends the rest to miners. The user suffers near-total loss of their deposited BTC. This satisfies **Critical — Significant loss of user funds**.

---

### Likelihood Explanation

The attack is straightforward for any NEAR account:

1. Monitor the Bitcoin chain for deposits whose `deposit_msg` indicates a refund scenario (e.g., the deposit address is already known to be unclaimable).
2. Obtain the deposit transaction bytes and a Merkle inclusion proof (both publicly available on-chain).
3. Call `request_refund` with `gas_fee = deposit_amount - 1` before the legitimate relayer does.
4. Wait for the timelock; the DAO must actively detect and reject the request within that window.

No privileged key, leaked secret, or third-party compromise is required. The race is winnable by any well-connected NEAR node. Likelihood is **Medium** (requires front-running, and the DAO can reject within the timelock), but the window is realistic in practice.

---

### Recommendation

Add an explicit upper-bound check on the caller-supplied gas fee, mirroring the withdrawal path's `max_btc_gas_fee` guard used in `check_withdraw_psbt`:

```rust
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
require!(
    resolved_gas_fee <= config.max_btc_gas_fee,   // or a dedicated max_refund_gas_fee
    "Gas fee exceeds maximum allowed refund gas fee"
);
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
``` [6](#0-5) 

This mirrors the existing withdrawal-path guard and closes the unbounded caller-controlled fee vector.

---

### Proof of Concept

1. Alice deposits 0.01 BTC to the bridge with `deposit_msg = { recipient_id: "alice.near", refund_address: Some("bc1qalice...") }`.
2. The deposit cannot be claimed (e.g., the bridge is paused or the amount is below the minimum).
3. Attacker Bob observes the deposit on-chain, fetches `tx_bytes` and constructs a valid Merkle proof.
4. Bob calls `request_refund(deposit_msg, "bc1qalice...", tx_bytes, vout=0, proof, gas_fee=Some(999_999))` where the deposit was 1_000_000 satoshis.
5. `request_refund_callback` resolves `resolved_gas_fee = 999_999`, passes the only check (`999_999 < 1_000_000`), and stores `RefundRequest { amount: 1_000_000, gas_fee: 999_999, ... }`.
6. The legitimate relayer's subsequent call fails: `"Refund request already exists for this UTXO"`.
7. After `refund_timelock_sec` elapses (assuming DAO does not reject), `execute_refund` calls `refund_execution_inputs`, computes `refund_amount = 1_000_000 - 999_999 = 1`, and builds a PSBT paying Alice 1 satoshi.
8. MPC signs and broadcasts the transaction. Alice receives 1 satoshi; 999_999 satoshis go to the Bitcoin miner. [7](#0-6)

    pub(crate) fn refund_execution_inputs(
        &self,
        refund_request: &RefundRequest,
    ) -> RefundExecutionInputs {
        let config = self.internal_config();
        let transaction =
            crate::WrappedTransaction::decode(&refund_request.tx_bytes.0, &config.chain)
                .expect("Deserialization tx_bytes failed");
        let txid = transaction.compute_txid();
        let outpoint = OutPoint {
            txid,
            vout: u32::try_from(refund_request.vout)
                .unwrap_or_else(|_| env::panic_str("vout overflow")),
        };
        let deposit_output = transaction.output()[refund_request.vout].clone();

        let refund_amount = refund_request
            .amount
            .checked_sub(refund_request.gas_fee)
            .expect("Deposit amount too small to cover gas fee");
        require!(refund_amount > 0, "Refund amount is zero after gas fee");

        RefundExecutionInputs {
            outpoint,
            deposit_output,
            refund_amount,
        }
    }
