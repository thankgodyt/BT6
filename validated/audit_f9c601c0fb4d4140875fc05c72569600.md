### Title
Unconditional `Right` Return in `validatePerasCert` Degenerate Instance Bypasses All Peras Certificate Validation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance used in production unconditionally returns `Right` from `validatePerasCert`, accepting every inbound Peras certificate without any cryptographic or structural check. This is the direct analog of the ERC20 "no-revert-on-transfer" pattern: a function that is supposed to reject invalid inputs silently succeeds instead. Any unprivileged peer can send a crafted `PerasCert` that names an arbitrary block as the boosted target; the certificate will be stored in the `PerasCertDB` and trigger chain selection, potentially causing an honest node to switch to a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` typeclass declares `validatePerasCert` as the gate that must be passed before a certificate is stored or acted upon. The production code ships a single catch-all instance (marked `-- TODO: degenerate instance for all blks to get things to compile`) whose implementation is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature, quorum, committee membership, round-number range, or boosted-block plausibility check is performed. The function wraps the raw, unverified `cert` directly into a `ValidatedPerasCert` and returns `Right`.

This validator is wired into the production inbound-certificate pipeline in `makePerasCertPoolWriterFromChainDB`:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` is designed to throw a `PerasCertInboundException` (causing peer disconnection) when any certificate fails validation:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) -> mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _)            -> throw (PerasCertValidationError errs)
``` [3](#0-2) 

Because `validatePerasCert` never returns `Left`, the rejection branch is structurally unreachable. Every certificate from every peer is forwarded to `ChainDB.addPerasCertAsync`, which enqueues a `ChainSelAddPerasCert` message: [4](#0-3) 

The background chain-selection thread then processes the certificate, stores it in `PerasCertDB`, and triggers `chainSelectionForBlock` for the block named in `pcCertBoostedBlock`: [5](#0-4) 

The boost weight applied is `perasWeight mkPerasParams = PerasWeight 15`, which is the same weight as a legitimately certified block. [6](#0-5) 

---

### Impact Explanation

Peras certificates exist specifically to boost a block's chain-selection weight beyond its raw length, enabling fast finality. An adversary who can inject a certificate for an arbitrary block can make an honest node treat that block as having `perasWeight` additional weight. If the adversary's chain is otherwise equal in length to the honest chain, the spurious boost is sufficient to cause the node to switch. This is a **chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain**, matching the "High" impact tier.

The `CHANGELOG` confirms that chain selection now uses Peras weight rather than raw length when Peras is enabled:

> "the candidate fragment is now selected based on its Peras weight, instead of its length" [7](#0-6) 

---

### Likelihood Explanation

The vulnerability is reachable by any peer that participates in the Peras object-diffusion mini-protocol. No special privileges, keys, or stake are required — only the ability to send a well-formed `PerasCert` message over the network. The `PerasCert` data type contains only a round number and a block point, both of which are trivially constructable: [8](#0-7) 

The TODO comment and the linked issue (`cardano-peras/issues/120`) confirm this is a known placeholder, not an intentional design choice, making it a live defect in the shipped code.

---

### Recommendation

Replace the unconditional `Right` body of `validatePerasCert` with a real implementation that checks at minimum:

1. **Committee membership and quorum**: the certificate must carry signatures from a sufficient fraction of the eligible voting committee for the claimed round.
2. **Aggregate signature verification**: the aggregate BLS/DSIGN signature must verify against the aggregated public keys of the claimed voters.
3. **Round-number plausibility**: the round number must be within the acceptable window relative to the current tip.
4. **Boosted-block plausibility**: the boosted block point must be consistent with the round's eligible targets.

Until the real implementation is in place, the `processCerts` pipeline in `makePerasCertPoolWriterFromChainDB` should refuse all inbound certificates (return `Left PerasValidationErr` unconditionally) rather than accept them all, so that the security boundary is closed even before full validation logic is written.

---

### Proof of Concept

An attacker node connects to an honest node via the Peras certificate object-diffusion protocol and sends:

```haskell
PerasCert
  { pcCertRound      = PerasRoundNo <current_round>
  , pcCertBoostedBlock = <point of adversary's fork tip>
  }
```

`processCerts` calls `validatePerasCert mkPerasParams cert`, which returns:

```haskell
Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = PerasWeight 15 })
``` [9](#0-8) 

The certificate is timestamped and passed to `ChainDB.addPerasCertAsync`. The background thread stores it in `PerasCertDB` and calls `chainSelectionForBlock` for the adversary's fork tip. Because the fork tip now carries `PerasWeight 15` of extra weight, the honest node's `WeightedSelectView` comparison may prefer the adversary's chain over the honest chain of equal length, causing a chain switch without any legitimate quorum having been reached. [10](#0-9)

```haskell
-- Process a Peras certificate by adding it to the PerasCertDB and potentially
-- performing chain selection if a candidate is now better than our selection.
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
