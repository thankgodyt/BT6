Audit Report

## Title
Decimal Normalization to Zero Permanently Locks User Tokens in `init_transfer_internal` — (`near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer_internal` burns or locks a user's tokens before any check that the normalized destination-chain amount is non-zero. The only guard against a zero normalized amount lives in `sign_transfer`, which is gated to trusted relayers and is called after the tokens are already gone. Any transfer whose `amount_without_fee` is below the normalization divisor (e.g., < 1,000,000 for a 24→18 decimal token) results in permanent, unrecoverable loss of the user's funds.

## Finding Description
`normalize_amount` performs floor division:

```rust
// near/omni-bridge/src/lib.rs L2784-2787
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

The code comment on this function (L2781-2783) acknowledges that sub-unit *remainder* dust stays locked/burned when `fee = 0`, but this is distinct from the zero-normalization case: when the **entire** `amount_without_fee` is below the divisor, `normalize_amount` returns `0`, and the transfer can never be finalized.

`init_transfer` only validates `fee < amount` (L554-557) — no normalization check. `init_transfer_internal` then immediately burns/locks the full amount (L1851-1857) with no zero-normalization guard:

```rust
// near/omni-bridge/src/lib.rs L1850-1857
if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
    self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
    self.lock_tokens_if_needed(
        transfer_message.get_destination_chain(),
        &token_id,
        transfer_message.amount.0,
    );
```

The zero-amount guard exists only in `sign_transfer` (L482-485), which is `#[trusted_relayer]`-gated and called after the tokens are already consumed:

```rust
// near/omni-bridge/src/lib.rs L482-485
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

When `sign_transfer` panics with `InvalidAmountToTransfer`, the transfer message remains in `pending_transfers` indefinitely. No user-callable cancellation or withdrawal function exists to recover the locked/burned tokens.

The code comment at L2781-2783 references "See SECURITY.md for details," but the SECURITY.md contains only a generic exclusion list with no mention of this zero-normalization scenario, confirming it is not a documented accepted risk.

## Impact Explanation
This is a concrete instance of **permanent freezing of bridged funds**: a user's tokens are burned or locked inside the bridge contract and can never be recovered. The transfer cannot be finalized (relayer's `sign_transfer` always reverts), and no refund path exists. This matches the Critical impact class of "permanent freezing of bridged funds" and "escrow mis-accounting / decimal/normalization abuse that changes user or protocol balances."

## Likelihood Explanation
Any token bridging from NEAR (24 decimals) to an EVM chain (18 decimals) has a divisor of 10^6. A user sending fewer than 1,000,000 units of such a token triggers the bug. The absolute value is tiny (fractions of a cent), making this realistic for automated scripts, bots, or users testing with small amounts. No privileged access is required — any unprivileged user calling `ft_transfer_call` with a dust amount can trigger it. Likelihood is **low-medium**: the amounts are small, but the loss is total and unrecoverable.

## Recommendation
Add a normalization check inside `init_transfer` or `init_transfer_internal` **before** burning or locking tokens, mirroring the existing guard in `sign_transfer`:

```rust
if let Some(token_address) = self.get_token_address(
    transfer_message.get_destination_chain(),
    self.get_token_id(&transfer_message.token),
) {
    if let Some(decimals) = self.token_decimals.get(&token_address) {
        let normalized = Self::normalize_amount(
            transfer_message.amount_without_fee()
                .near_expect(BridgeError::InvalidFee),
            decimals,
        );
        require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
    }
}
```

This ensures tokens are never burned or locked for a transfer that can never be finalized.

## Proof of Concept
**Setup**: Token registered with `origin_decimals = 24`, `decimals = 18`. Divisor = `10^6`.

1. User calls `ft_transfer_call(bridge, 500_000, init_transfer_msg)` with `fee = 0`, valid EVM recipient.
2. `ft_on_transfer` → `init_transfer` → `init_transfer_internal`:
   - `fee (0) < amount (500_000)` ✓ passes (L554-557)
   - `burn_tokens_if_needed(token, 500_000)` — tokens burned (L1851)
   - `lock_tokens_if_needed(Eth, token, 500_000)` — locked (L1853-1857)
   - Returns `U128(0)` → NEP-141 keeps all tokens in bridge
3. Trusted relayer calls `sign_transfer(transfer_id, ...)`:
   - `normalize_amount(500_000, {24, 18}) = 500_000 / 1_000_000 = 0`
   - `require!(0 > 0)` → **PANIC: `ERR_INVALID_AMOUNT_TO_TRANSFER`** (L482-485)
4. Transfer message stays in `pending_transfers`. User's 500,000 units are permanently burned. No cancellation path exists.

A unit test can reproduce this by registering a token with the above decimals, calling `init_transfer_internal` with `amount = 500_000`, and asserting that `sign_transfer` panics while the transfer remains in `pending_transfers` with no recovery function callable by the user.
