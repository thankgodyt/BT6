Audit Report

## Title
`normalize_amount` Truncation to Zero Permanently Freezes User Funds in `init_transfer` — (File: `near/omni-bridge/src/lib.rs`)

## Summary
When a user initiates a NEAR→foreign transfer with an amount below the decimal normalization threshold, `normalize_amount` returns zero via integer floor division. `init_transfer` locks the user's tokens without verifying the normalized amount is non-zero. Every subsequent `sign_transfer` call deterministically panics on the non-zero check, and no cancel or refund path exists, permanently freezing the funds.

## Finding Description

**Root cause — `normalize_amount` floor division:**

`normalize_amount` is called inside `sign_transfer` at [1](#0-0)  and performs integer floor division. When `amount < 10^(origin_decimals - decimals)`, the result is `0`.

**`init_transfer` locks tokens without a normalized-amount check:**

`init_transfer` only validates `fee.fee < amount` at [2](#0-1)  before storing the `TransferMessage` and returning `0` from `ft_on_transfer` (keeping all tokens). No check on `normalize_amount(amount_without_fee, decimals) > 0` is performed at any point in `init_transfer` or `init_transfer_internal`.

**`sign_transfer` always panics for this transfer:**

`sign_transfer` computes the normalized amount and enforces the non-zero invariant at [3](#0-2)  via `require!`, which panics the transaction. The `TransferMessage` is never removed on panic.

**`sign_transfer_callback` cannot clean up:**

`sign_transfer_callback` only calls `remove_transfer_message` when `fee.is_zero()` AND MPC signing succeeded at [4](#0-3) . Since `sign_transfer` panics before reaching the MPC call, this callback is never reached.

**`claim_fee_callback` is unreachable:**

`claim_fee_callback` calls `remove_transfer_message` at [5](#0-4)  but requires a valid `ProverResult::FinTransfer` proof from the destination chain at [6](#0-5) . A destination-chain finalization proof can never exist because the transfer was never signed and broadcast.

**`update_transfer_fee` cannot rescue the transfer:**

`update_transfer_fee` enforces `fee.fee >= current_fee.fee` at [7](#0-6) , so the fee can only be raised, not lowered. The user cannot increase `amount_without_fee` to cross the normalization threshold.

## Impact Explanation

The user's tokens are permanently frozen inside the bridge contract. The `TransferMessage` occupies storage indefinitely and can never be finalized, cancelled, or refunded. This is a concrete instance of **permanent freezing of bridged funds**, matching the Critical allowed impact scope for the NEAR Omni Bridge program.

## Likelihood Explanation

The condition is reachable by any unprivileged user through the standard `ft_transfer_call` → `ft_on_transfer` → `init_transfer` public flow. No special privileges are required. A realistic example: a token with `origin_decimals = 24` (NEAR-native) bridged to an EVM token with `decimals = 6` gives `diff = 18`, so any transfer below `10^18` base units (i.e., below 1 token unit) triggers the bug. This decimal configuration is common across the supported chains. The user-facing API accepts the transaction without error, giving no indication that funds are permanently lost.

## Recommendation

Add a normalized-amount non-zero check inside `init_transfer` (or `init_transfer_internal`) before storing the `TransferMessage` and locking tokens. Specifically, after computing `amount_without_fee`, look up the token decimals and call `normalize_amount`; if the result is zero, revert immediately (return the full amount from `ft_on_transfer` so the token contract refunds the user). Additionally, consider adding a user-callable cancel/refund path for pending transfers that have never been successfully signed, to provide a safety net for edge cases.

## Proof of Concept

1. Register a token pair with `origin_decimals = 24`, `decimals = 6` (diff = 18, threshold = `10^18`).
2. Call `ft_transfer_call` on the NEAR token contract with `amount = 10^17` (below threshold) and a valid `InitTransferMsg` targeting the EVM chain.
3. Observe that `ft_on_transfer` returns `0` (tokens locked) and a `TransferMessage` is stored in `pending_transfers`.
4. Call `sign_transfer` for the resulting `transfer_id` (as a trusted relayer).
5. Observe the transaction panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.
6. Repeat step 4 indefinitely — it always panics.
7. Confirm no `claim_fee`, `fin_transfer`, or `update_transfer_fee` call can recover the funds.
