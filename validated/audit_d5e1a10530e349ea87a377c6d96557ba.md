### Title
Silent Token Lock When `read_withdraw_relayer_address` Returns `None` in `ft_transfer` - (File: `contracts/nbtc/src/lib.rs`)

### Summary
In `contracts/nbtc/src/lib.rs`, the `ft_transfer` function contains a legacy Near Intents withdrawal path that reads the withdraw relayer address from storage via `read_withdraw_relayer_address()`. If that function returns `None` (storage key absent or deserialization failure), the code silently falls through and executes `self.token.ft_transfer(receiver_id, amount, memo)` where `receiver_id` is `env::current_account_id()` — the nbtc contract itself. The user's tokens are transferred into the nbtc contract's own token balance with no recovery path, permanently locking them.

### Finding Description
`read_withdraw_relayer_address()` is defined as:

```rust
// contracts/nbtc/src/lib.rs:354-356
fn read_withdraw_relayer_address() -> Option<AccountId> {
    env::storage_read(WITHDRAW_RELAYER_ADDRESS).and_then(|data| borsh::from_slice(&data).ok())
}
```

It returns `None` whenever the `WITHDRAW_RELAYER_ADDRESS` storage key has not been written (e.g., fresh deployment, migration that skipped `set_withdraw_relayer_address`, or a borsh deserialization error).

The caller in `ft_transfer` is:

```rust
// contracts/nbtc/src/lib.rs:183-196
fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
    if receiver_id == env::current_account_id()
        && memo.as_ref().is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
    {
        if let Some(withdraw_relayer) = Self::read_withdraw_relayer_address() {
            return self.token.ft_transfer(withdraw_relayer, amount, memo);
        }
        // ← NO else-branch: falls through silently
    }
    self.token.ft_transfer(receiver_id, amount, memo);
}
```

When `read_withdraw_relayer_address()` returns `None`, there is no `else` branch, no `require!`, and no revert. Execution falls through to `self.token.ft_transfer(receiver_id, amount, memo)` where `receiver_id` is still `env::current_account_id()` (the nbtc contract). The nbtc contract is registered as a token account (done in `new()` at line 88), so the NEP-141 transfer succeeds. The tokens land in the nbtc contract's own balance with no function available to retrieve or burn them.

### Impact Explanation
User tokens sent via the legacy Near Intents withdrawal path are permanently locked inside the nbtc contract when the withdraw relayer address is unset. The nbtc contract exposes no owner-rescue, sweep, or administrative transfer function that could recover tokens held in its own balance. The `burn` function withdraws from `bridge_id` (the satoshi-bridge contract), not from the nbtc contract's self-balance, so it cannot be used to recover these tokens. This constitutes permanent, irrecoverable loss of user funds — matching the medium impact class: *harmful smart-contract behavior including permanent burning below backed supply or stuck bridge state requiring operator intervention*.

### Likelihood Explanation
The withdraw relayer address is an optional, separately configured storage slot set via `set_withdraw_relayer_address`. It is absent on any fresh deployment of the nbtc contract that does not call `set_withdraw_relayer_address` before going live, and absent after any migration path that does not re-write the key. Any unprivileged token holder who uses the legacy Near Intents withdrawal flow (sending to `nbtc_contract_id` with a `WITHDRAW_TO:` memo) during such a window loses their tokens silently. The triggering condition is fully attacker-observable (the storage key is public) and the call requires no special role.

### Recommendation
Add an explicit guard in `ft_transfer` so that the absence of a configured withdraw relayer causes a hard revert rather than a silent fallthrough:

```rust
if receiver_id == env::current_account_id()
    && memo.as_ref().is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
{
    let withdraw_relayer = Self::read_withdraw_relayer_address()
        .unwrap_or_else(|| env::panic_str("ERR_WITHDRAW_RELAYER_NOT_SET"));
    return self.token.ft_transfer(withdraw_relayer, amount, memo);
}
```

This is the direct analog of the recommended `require(address != address(0))` check from the external report.

### Proof of Concept

1. Deploy the nbtc contract without calling `set_withdraw_relayer_address` (or after a migration that omits it).
2. As any token holder (`alice`), call:
   ```
   ft_transfer(
     receiver_id = <nbtc_contract_account_id>,
     amount      = 100_000,
     memo        = "WITHDRAW_TO:bc1q..."
   )
   ```
   with 1 yoctoNEAR attached.
3. `receiver_id == env::current_account_id()` → `true`.
4. `memo.starts_with("WITHDRAW_TO:")` → `true`.
5. `read_withdraw_relayer_address()` → `None` (key absent).
6. No revert; falls through to `self.token.ft_transfer(nbtc_contract_id, 100_000, memo)`.
7. NEP-141 transfer succeeds (alice ≠ nbtc contract, nbtc contract is registered).
8. `alice`'s balance decreases by 100,000; nbtc contract's self-balance increases by 100,000.
