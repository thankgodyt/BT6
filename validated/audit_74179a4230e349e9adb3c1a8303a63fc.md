### Title
Blocklisted ERC20 Recipient Permanently Locks Bridged Funds With No Recovery Path - (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

The `finTransfer` function in `OmniBridge.sol` uses `safeTransfer` to deliver native ERC20 tokens (e.g., USDC, USDT) to the MPC-signed `payload.recipient`. If that address is blocklisted by the token contract, every `finTransfer` call reverts. Because the MPC signature cryptographically commits to the specific recipient and there is no mechanism on NEAR to cancel an outbound transfer or re-sign with a different recipient, the user's tokens burned/locked on NEAR during `init_transfer` are permanently unrecoverable.

---

### Finding Description

**NEAR → EVM outbound flow:**

1. A user calls `ft_transfer_call` on a NEAR NEP-141 token (e.g., a USDC-equivalent), which triggers `ft_on_transfer` → `init_transfer` on the NEAR bridge contract.
2. `init_transfer_internal` burns (for deployed tokens) or locks (for native tokens) the user's tokens and stores the `TransferMessage` — including the EVM `recipient` address — in `pending_transfers`.
3. A trusted relayer calls `sign_transfer`, which asks the MPC network to sign a `TransferMessagePayload` that encodes `recipient` as a fixed field.
4. In `sign_transfer_callback`, if the fee is zero, the transfer message is **removed** from `pending_transfers` immediately after signing; if non-zero it remains, but the `recipient` field is immutable — `update_transfer_fee` only allows updating the fee amount.
5. The relayer submits the signed payload to `OmniBridge.finTransfer` on the EVM chain.
6. If `payload.tokenAddress` is a native ERC20 (not a bridge token, not a custom minter, not ERC1155), the contract reaches the `else` branch and calls `IERC20(payload.tokenAddress).safeTransfer(payload.recipient, payload.amount)`.
7. If `payload.recipient` is blocklisted by the token (USDC/USDT maintain admin-controlled blocklists), `safeTransfer` reverts, rolling back the entire transaction including the `completedTransfers[payload.destinationNonce] = true` write.
8. The nonce is not consumed, but the MPC signature is permanently bound to the blocklisted recipient. No valid `finTransfer` call can ever succeed for this transfer. The user's funds burned/locked on NEAR in step 2 are permanently lost.

**Key code references:**

- `init_transfer_internal` burns/locks tokens unconditionally before any EVM-side confirmation: [1](#0-0) 

- `sign_transfer_callback` removes the pending transfer (zero-fee case) after signing, eliminating any on-chain record that could be used for recovery: [2](#0-1) 

- `sign_transfer` encodes `recipient` from the stored `TransferMessage` — the caller cannot substitute a different address: [3](#0-2) 

- `finTransfer` calls `safeTransfer` directly to `payload.recipient` with no fallback for a failed transfer: [4](#0-3) 

- There is no public cancel or refund function for outbound transfers anywhere in the NEAR bridge contract; `remove_transfer_message` is private and only called internally: [5](#0-4) 

---

### Impact Explanation

Permanent, irreversible loss of bridged funds. The user's tokens are burned/locked on NEAR at `initTransfer` time. If the EVM recipient is or becomes blocklisted by the token contract, `finTransfer` will revert on every attempt. Because the MPC signature is fixed to that recipient and there is no cancel/refund path on NEAR, the funds are frozen forever. This matches the "permanent freezing of bridged funds" category in the allowed impact scope.

---

### Likelihood Explanation

USDC (Circle) and USDT (Tether) both maintain admin-controlled address blocklists and are among the most commonly bridged assets. A recipient address can be blocklisted:

- **Before** the transfer is initiated (user error — specifying an already-blocklisted address).
- **After** initiation but before finalization (regulatory action, exchange compliance, or a compromised account being sanctioned).

The window between `initTransfer` on NEAR and `finTransfer` on EVM can span multiple blocks and involves MPC signing latency, making the second scenario realistic. The bridge explicitly supports USDC/USDT-class tokens via the `safeTransfer` path.

---

### Recommendation

1. **Pull-payment pattern in `finTransfer`:** Instead of pushing tokens directly to `payload.recipient`, store the claimable amount in a mapping and let the recipient withdraw. This is the standard mitigation for blocklist-sensitive transfers.

2. **Fallback storage on revert:** Wrap the `safeTransfer` in a try/catch (using a low-level call or OpenZeppelin's `SafeERC20.safeTransfer` with a success check) and, on failure, store the amount in a per-recipient escrow that can be claimed later or refunded to the origin chain.

3. **Cancel/refund path on NEAR:** Add a permissioned (DAO or user-initiated after timeout) `cancel_transfer` function that re-mints/unlocks the tokens on NEAR for a pending transfer whose EVM finalization has provably failed.

---

### Proof of Concept

1. User holds 1,000 USDC on NEAR (as a bridged NEP-141 token).
2. User calls `ft_transfer_call` with `msg` encoding `InitTransferMsg { recipient: OmniAddress::Eth(0xBLOCKLISTED), fee: 0, ... }`.
3. `init_transfer_internal` burns 1,000 USDC on NEAR and stores the `TransferMessage`.
4. Relayer calls `sign_transfer`; MPC signs a payload with `recipient = 0xBLOCKLISTED`. `sign_transfer_callback` removes the transfer message from `pending_transfers` (fee = 0).
5. Relayer submits `finTransfer(signature, payload)` to `OmniBridge` on Ethereum.
6. Execution reaches line 351: `IERC20(usdcAddress).safeTransfer(0xBLOCKLISTED, 1000e6)` — USDC reverts because `0xBLOCKLISTED` is on Circle's blocklist.
7. The entire transaction reverts; `completedTransfers[nonce]` is not set.
8. No valid `finTransfer` call can ever succeed (signature is bound to the blocklisted address).
9. The 1,000 USDC burned on NEAR in step 3 is permanently lost — no cancel function exists, no pending transfer record remains. [6](#0-5) [7](#0-6)

    fn init_transfer_internal(
        &mut self,
        transfer_message: TransferMessage,
        storage_owner: AccountId,
    ) -> U128 {
        let required_storage_balance = self
            .add_transfer_message(transfer_message.clone(), storage_owner.clone())
            .saturating_add(NearToken::from_yoctonear(transfer_message.fee.native_fee.0));

        if self
            .try_update_storage_balance(
                storage_owner,
                required_storage_balance,
                NearToken::from_yoctonear(0),
            )
            .is_err()
        {
            self.remove_transfer_message_without_refund(transfer_message.get_transfer_id());
            return transfer_message.amount;
        }

        if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
            self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);

            self.lock_tokens_if_needed(
                transfer_message.get_destination_chain(),
                &token_id,
                transfer_message.amount.0,
            );
        } else {
            self.remove_transfer_message_without_refund(transfer_message.get_transfer_id());
            return transfer_message.amount;
        }

        env::log_str(&OmniBridgeEvent::InitTransferEvent { transfer_message }.to_log_string());
        U128(0)
    }

    fn remove_transfer_message(&mut self, transfer_id: TransferId) -> TransferMessage {
        let storage_usage = env::storage_usage();
        let transfer = self
            .pending_transfers
            .remove(&transfer_id)
            .map(storage::TransferMessageStorage::into_main)
            .near_expect(BridgeError::TransferNotExist);

        let refund =
            env::storage_byte_cost().saturating_mul((storage_usage - env::storage_usage()).into());

        if let Some(mut storage) = self.accounts_balances.get(&transfer.owner) {
            storage.available = storage.available.saturating_add(refund);
            self.accounts_balances.insert(&transfer.owner, &storage);
        }

        transfer.message
    }
