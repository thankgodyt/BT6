### Title
Missing Proof-of-Possession Verification Before BLS Key Aggregation Enables Rogue-Key Attack on Peras Certificate Verification - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/Crypto/BLS.hs`)

### Summary

`aggregatePublicKeys` in `BLS.hs` explicitly documents a precondition that proofs of possession (PoP) must be verified for all keys before aggregation, as a defense against the BLS rogue-key (key-cancellation) attack. However, `verifyProofOfPossession` is defined in `BLS.hs` but is **never called anywhere in the production codebase**. Every certificate verification path (`implVerifyCert` in `WFALS.hs` and `EveryoneVotes.hs`) calls `aggregateVoteVerificationKeys` → `aggregatePublicKeys` without first verifying PoP. A malicious stake pool operator can register a crafted rogue BLS public key that cancels out a legitimate voter's key, then forge a valid aggregate signature for a Peras certificate they should not be able to produce.

### Finding Description

`aggregatePublicKeys` in `BLS.hs` carries an explicit precondition comment:

```
-- PRECONDITION: this assumes that proofs of possession have already been
-- verified for all keys in advance.
``` [1](#0-0) 

The function `verifyProofOfPossession` is defined and exported from `BLS.hs`: [2](#0-1) 

A `grep` across the entire repository shows `verifyProofOfPossession` appears **only in `BLS.hs`** (its definition and internal references) — it is never called in any production code path.

The certificate verification path in `WFALS.implVerifyCert` calls `aggregateVoteVerificationKeys` directly on keys taken from the ledger stake distribution, with no PoP check: [3](#0-2) 

The same pattern holds in `EveryoneVotes.implVerifyCert`: [4](#0-3) 

Both delegate to `aggregateVoteVerificationKeys` → `aggregatePublicKeys`: [5](#0-4) 

The `PerasBLSCrypto` instance also calls `aggregatePublicKeys` without PoP verification: [6](#0-5) 

**Rogue-key attack mechanics:**

1. Honest voter `A` has registered public key `pk_A`.
2. Attacker (a stake pool operator) registers `pk_rogue = pk_attacker_real - pk_A` (computed by the attacker using `pk_A`, which is public).
3. When `aggregatePublicKeys` computes `pk_agg = pk_A + pk_rogue + pk_others = pk_attacker_real + pk_others`, voter `A`'s contribution is silently cancelled.
4. The attacker signs with `pk_attacker_real` and produces a valid aggregate signature over the manipulated aggregate key.
5. `verifyAggregateVoteSignature` passes, accepting a certificate that voter `A` never actually signed. [7](#0-6) 

### Impact Explanation

An attacker can forge a valid Peras certificate claiming a block was boosted by a quorum of committee members, when in reality the required votes were never cast. This is a direct bypass of Peras certificate/vote verification. Honest nodes receiving this crafted certificate over the network will accept it as valid, potentially causing them to boost and prefer a block that did not legitimately win the Peras election. This falls squarely under: **Critical — Bypass of Peras voting or certificate checks that enables unauthorized certificate acceptance.**

### Likelihood Explanation

Any entity that can register as a stake pool operator on the network (a low barrier — no majority stake required) can register a rogue BLS public key. The attack requires only knowledge of other committee members' public keys (which are public on-chain data) and the ability to craft a key satisfying `pk_rogue = pk_attacker_real - pk_victim`. This is straightforward elliptic-curve arithmetic on BLS12-381. No privileged access, leaked keys, or social engineering is required.

### Recommendation

Before calling `aggregatePublicKeys` (or `aggregateVoteVerificationKeys`) during certificate verification, verify the proof of possession for each voter's BLS public key using `verifyProofOfPossession`. Proofs of possession should either be stored alongside the public keys in the ledger stake distribution, or verified at committee construction time in `mkVotingCommittee`. The existing `verifyProofOfPossession` function already implements the correct check; it simply needs to be called. [2](#0-1) 

### Proof of Concept

```
1. Observe that verifyProofOfPossession is defined but never called:
   grep -r "verifyProofOfPossession" . 
   → only matches in BLS.hs (definition site)

2. Attacker (stake pool operator) computes:
   pk_rogue = pk_attacker_real - pk_victim   (BLS12-381 G1 subtraction)

3. Attacker registers pk_rogue as their committee BLS key on-chain.

4. Attacker constructs a WFALSCert / EveryoneVotesCert containing:
   - voters = {seatIndex_victim, seatIndex_attacker}
   - aggSig  = sign(sk_attacker_real, electionId || candidate)

5. Node receives the cert and calls implVerifyCert:
   aggregateVoteVerificationKeys([pk_victim, pk_rogue])
   → aggregatePublicKeys([pk_victim, pk_rogue])
   → pk_agg = pk_victim + pk_rogue = pk_attacker_real   ✓ (no PoP check)

6. verifyAggregateVoteSignature(pk_agg, electionId, candidate, aggSig)
   → verifyWithRole @SIGN pk_attacker_real msg aggSig   → PASSES

7. Certificate accepted. Voter A's participation was forged.
```

aggregatePublicKeys ::
  NE [PublicKey r] ->
  Either String (PublicKey r)
aggregatePublicKeys keys@(firstKey :| restKeys) = do
  -- Ensure all keys have the same scope before aggregation
  when (any (/= publicKeyScope firstKey) (fmap publicKeyScope restKeys)) $
    Left "Cannot aggregate public keys with different scopes"
  aggKey <-
    uncheckedAggregateVerKeysDSIGN
      . fmap unPublicKey
      . NonEmpty.toList
      $ keys
  pure $
    PublicKey
      { unPublicKey = aggKey
      , publicKeyScope = publicKeyScope firstKey
      }
