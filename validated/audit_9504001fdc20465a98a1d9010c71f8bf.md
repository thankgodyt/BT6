### Title
Unauthorized Refund Redirection via Missing Caller Authorization in `request_refund` — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

The public `request_refund` function accepts a caller-supplied `refund_address` (BTC destination) for any deposit whose `deposit_msg.refund_address` is `None`, but never verifies that the caller is the `recipient_id` named in the `deposit_msg`. Any unprivileged NEAR account can submit a refund request for a victim's unfinalized BTC deposit and redirect the entire deposit to an attacker-controlled BTC address.

---

### Finding Description

When a user deposits BTC, the deposit address is derived from a `DepositMsg` that includes `recipient_id` (the NEAR account that will receive nBTC) and an optional `refund_address` (the BTC address to use if the deposit is never finalized). Many users omit `refund_address`, leaving it as `None`.

The public entry point `request_refund` is: [1](#0-0) 

It delegates to `internal_request_refund`, which only enforces that if `deposit_msg.refund_address` is already set it must match the caller-supplied value — but performs **no check** when `deposit_msg.refund_address` is `None`: [2](#0-1) 

There is no assertion of the form `require!(env::predecessor_account_id() == deposit_msg.recipient_id, ...)` anywhere in the call chain. The `deposit_msg` is public: `get_user_deposit_address` emits it as an on-chain event, and it also appears in relayer transaction data. [3](#0-2) 

The `DepositMsg` structure showing `recipient_id` and the optional `refund_address`: [4](#0-3) 

After the refund request is stored, `execute_refund` is also callable by anyone once the timelock elapses: [5](#0-4) 

The only mitigation in the code is `unsafe_refund_timelock_sec` — a longer delay intended to give the DAO time to reject suspicious requests: [6](#0-5) 

This is a trust assumption, not an authorization control. If the DAO is slow, unavailable, or overwhelmed with many simultaneous malicious requests, the attacker's request survives and the BTC is redirected.

Additionally, `request_refund_callback` enforces a first-come-first-served rule: [7](#0-6) 

This means an attacker who front-runs the victim's own legitimate refund request wins the race and locks in the attacker-controlled `refund_address`.

---

### Impact Explanation

**Critical.** A victim's entire BTC deposit — which was never finalized into nBTC — can be permanently redirected to an attacker-controlled BTC address. The victim loses their deposited BTC with no recourse once `execute_refund` is called after the timelock. This is direct, irreversible theft of user funds from the bridge's custody.

---

### Likelihood Explanation

**Medium.** The attacker needs:
1. Knowledge of the victim's `deposit_msg` — publicly available from on-chain events emitted by `get_user_deposit_address` or from relayer transaction calldata.
2. The BTC transaction bytes and Merkle proof — publicly available on the Bitcoin blockchain.
3. Either: front-run the victim's own refund submission (feasible on NEAR), or wait for the `unsafe_refund_timelock_sec` to pass without DAO intervention.

The DAO-rejection window is the only barrier, and it can be bypassed by front-running or by submitting many simultaneous requests to overwhelm monitoring.

---

### Recommendation

Add an authorization check in `request_refund` requiring that the caller is the `recipient_id` named in the `deposit_msg` when `deposit_msg.refund_address` is `None`:

```rust
if deposit_msg.refund_address.is_none() {
    require!(
        env::predecessor_account_id() == deposit_msg.recipient_id,
        "Only the deposit recipient can request a refund without a pre-authorized refund address"
    );
}
```

Alternatively, require that `deposit_msg.refund_address` always be set at deposit time (enforced during address generation), so the permissionless refund path always uses a pre-committed address that the attacker cannot override.

---

### Proof of Concept

1. Victim calls `get_user_deposit_address` with `deposit_msg = { recipient_id: "victim.near", refund_address: None, ... }`. The full `deposit_msg` is emitted as a `LogDepositAddress` event.
2. Victim sends BTC to the derived deposit address. The relayer fails to call `verify_deposit` (network issue, or attacker delays it).
3. Attacker reads the victim's `deposit_msg` from the NEAR event log and the BTC transaction from the Bitcoin blockchain.
4. Attacker calls `request_refund(deposit_msg=victim_msg, refund_address="attacker_btc_addr", tx_bytes=..., vout=..., proof=...)`. No authorization check prevents this.
5. The refund request is stored with `refund_address = "attacker_btc_addr"`.
6. After `unsafe_refund_timelock_sec` elapses (assuming the DAO does not reject), attacker calls `execute_refund(utxo_storage_key)`.
7. The bridge constructs a Bitcoin transaction paying `"attacker_btc_addr"` and submits it to MPC for signing. Victim's BTC is permanently lost.
