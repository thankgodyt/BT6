### Title
Peras Certificate Validation Bypass: `validatePerasCert` Unconditionally Accepts Any Peer-Provided Certificate — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` method is a stub that unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or structural validation. This stub is wired directly into the live node-to-node Peras certificate diffusion handler. Any unprivileged peer can inject an arbitrary `PerasCert` for any block and round into the node's `PerasCertDB` and `ChainDB`, bypassing the Peras certificate authorization gate entirely.

---

### Finding Description

**Root cause — unconditional acceptance in the only production instance:** [1](#0-0) 

The comment at line 318 labels this as a "degenerate instance … to get things to compile," yet it is the **only** `BlockSupportsPeras` instance in the codebase and is therefore the one used at runtime. `validatePerasCert` ignores every field of the certificate and returns `Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }` unconditionally — no signature check, no committee-membership check, no round-validity check, no boosted-block existence check.

**Attacker-controlled entry path — production network handler:**

`makePerasCertPoolWriterFromChainDB` passes `validatePerasCert mkPerasParams` as the validation callback to `processCerts`: [2](#0-1) 

This writer is wired into the live node-to-node handler: [3](#0-2) 

`processCerts` calls `validateCert` on every inbound cert and, because `validatePerasCert` always returns `Right`, every cert passes and is forwarded to `ChainDB.addPerasCertAsync`: [4](#0-3) 

**Cert stored and weight snapshot updated:**

Once accepted, the cert is stored in `PerasCertDB` and the `PerasWeightSnapshot` is derived from it: [5](#0-4) 

The weight snapshot is the input to `preferAnchoredCandidate` in chain selection, meaning fraudulent certs directly influence which chain the node selects once Peras weight is applied.

---

### Impact Explanation

**Impact class:** Critical — Bypass of Peras certificate verification that enables unauthorized certificate acceptance and chain-selection manipulation.

An unprivileged peer can craft a `PerasCert` pointing to any block (including an adversarial fork) for any round number. Because `validatePerasCert` never rejects, the cert is stored with a full `vpcCertBoost = perasWeight params` weight. The `PerasWeightSnapshot` derived from the `PerasCertDB` is then used by `preferAnchoredCandidate` in chain selection. A peer can therefore artificially boost an adversarial chain's weight, causing an honest node to prefer a non-canonical chain — a direct consensus safety failure.

The `emptyPerasWeightSnapshot` TODO in `ChainSync/Client.hs` (line 1842) shows that one specific comparison currently bypasses Peras weight, but the `PerasCertDB`'s `getWeightSnapshot` is the authoritative source for chain selection and is not similarly guarded. Even if the full weight path is not yet activated on mainnet, the cert injection path is live and the stored fraudulent certs will take effect the moment Peras weight is enabled — with no way for the node to distinguish them from legitimate certs after the fact.

---

### Likelihood Explanation

**High.** The `PerasCertDiffusion` mini-protocol is active in the production node-to-node handler. No special privileges, keys, or stake are required. Any peer that can establish a node-to-node connection can send crafted `PerasCert` messages. The `PerasCert` type contains only a `PerasRoundNo` and a `Point blk` — both freely constructable by an attacker: [6](#0-5) 

---

### Recommendation

1. **Do not enable the `PerasCertDiffusion` mini-protocol in production** until `validatePerasCert` performs real cryptographic validation (aggregate signature verification, committee-membership proof, round-validity bounds, and boosted-block existence).
2. Replace the degenerate stub instance with a proper implementation that verifies the certificate's aggregate BLS/KES signature against the committee's public keys and the claimed stake distribution before returning `Right`.
3. Track this via the referenced issue (`cardano-peras/issues/120`) and gate the diffusion handler behind a feature flag that is disabled until validation is complete.

---

### Proof of Concept

1. Establish a node-to-node connection to a target node running the Peras-enabled consensus code.
2. Initiate the `PerasCertDiffusion` mini-protocol (client side).
3. Advertise a `PerasCert` with `pcCertRound = <any round>` and `pcCertBoostedBlock = <point of an adversarial block>`.
4. The target node calls `validatePerasCert mkPerasParams cert` → always `Right`.
5. `processCerts` forwards the cert to `ChainDB.addPerasCertAsync`.
6. `PerasCertDB.implAddCert` stores the cert; `getWeightSnapshot` now returns a non-zero boost for the adversarial block.
7. Chain selection via `preferAnchoredCandidate` uses this snapshot, preferring the adversarial chain over the honest chain. [7](#0-6) [8](#0-7) [3](#0-2)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
