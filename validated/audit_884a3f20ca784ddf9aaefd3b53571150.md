### Title
Hardcoded `BranchId::Nu6_2` in `Transaction::decode` Ignores Chain Parameter, Causing Wrong Txid Computation for Pre-Nu6.2 Transactions - (File: contracts/satoshi-bridge/src/zcash_utils/transaction.rs)

---

### Summary

`Transaction::decode` unconditionally uses `BranchId::Nu6_2` and silently ignores the `_chain` parameter it receives. For any Zcash V5 transaction that was created under an earlier consensus branch (Nu6 or Nu6_1), the txid computed from the decoded transaction will be wrong. This directly breaks the refund request flow, where the bridge computes the txid from the decoded deposit transaction and passes it to the light client for inclusion verification.

---

### Finding Description

In `contracts/satoshi-bridge/src/zcash_utils/transaction.rs`, the `decode` function is:

```rust
pub fn decode(data: &[u8], _chain: &network::Chain) -> Result<Self, std::io::Error> {
    let mut cursor = std::io::Cursor::new(data);
    let branch_id = BranchId::Nu6_2;          // ← always Nu6_2
    let tx = ZCashTransaction::read(&mut cursor, branch_id)?;
    Ok(Self { inner_tx: tx })
}
``` [1](#0-0) 

The `_chain` parameter (note the underscore) is completely discarded. The codebase elsewhere correctly derives the branch ID from the current block height via `BranchIdUpdateBlockHeight`:

```rust
Chain::ZcashMainnet => Self { nu6_1_update: 3146400, nu6_2_update: 3364600 },
Chain::ZcashTestnet => Self { nu6_1_update: 3536500, nu6_2_update: 4052000 },
``` [2](#0-1) 

`PsbtWrapper::new` correctly calls `get_branch_id(current_height, config)` when *constructing* a transaction. [3](#0-2) 

But `Transaction::decode` — used when *reading back* a transaction — hardcodes Nu6_2 unconditionally, creating an asymmetry.

In Zcash ZIP-244, the txid for V5 transactions is a BLAKE2b hash that covers the consensus branch ID in its `header_digest`. Passing the wrong branch ID to `ZCashTransaction::read` stores the wrong branch ID in the transaction data structure, so every subsequent call to `compute_txid()` returns a hash that does not match the real on-chain txid.

---

### Impact Explanation

The refund request entry point (`internal_request_refund`) decodes the user-supplied deposit `tx_bytes` and immediately recomputes the txid from the decoded transaction:

```rust
let transaction =
    crate::WrappedTransaction::decode(&tx_bytes.0, &self.internal_config().chain)
        .expect("Deserialization tx_bytes failed");
let tx_id = transaction.compute_txid().to_string();
// ...
self.verify_transaction_inclusion_promise(
    config.btc_light_client_account_id.clone(),
    tx_id,   // ← wrong txid when branch_id is wrong
    ...
)
``` [4](#0-3) 

The same wrong txid is then used in `request_refund_callback` to derive the `utxo_storage_key`: [5](#0-4) 

And in `refund_execution_inputs` to reconstruct the outpoint for the refund transaction: [6](#0-5) 

For any deposit transaction whose actual on-chain branch ID is Nu6 or Nu6_1 (i.e., created before the Nu6_2 activation height), the light client will return `false` because the txid the bridge presents does not match the txid in the Merkle tree. The refund request is rejected, and the user's ZEC remains permanently locked in the deposit address until a contract upgrade corrects the branch ID.

**Impact class**: Medium — stuck bridge state requiring operator intervention; user funds locked without direct theft.

---

### Likelihood Explanation

On Zcash testnet, Nu6_2 activates at block 4,052,000. [7](#0-6)  Any deposit made while the testnet is below that height carries a Nu6_1 branch ID. Any user who deposited ZEC on testnet before that activation and whose deposit failed (triggering the refund path) is immediately affected. On mainnet, Nu6_2 activated at block 3,364,600; historical deposits before that block are similarly affected. No special privileges are required — any user who calls `request_refund` with a pre-Nu6.2 deposit transaction triggers the failure.

---

### Recommendation

Pass the block height into `Transaction::decode` (or derive it from the transaction's `expiry_height` field as a conservative lower bound) and use `chain.get_branch_id(height)` — the same helper already used in `PsbtWrapper::new` — to select the correct branch ID:

```rust
pub fn decode(data: &[u8], chain: &network::Chain, block_height: u32) -> Result<Self, std::io::Error> {
    let mut cursor = std::io::Cursor::new(data);
    let branch_id = chain.get_branch_id(block_height);
    let tx = ZCashTransaction::read(&mut cursor, branch_id)?;
    Ok(Self { inner_tx: tx })
}
```

All call sites that currently pass `_chain` must be updated to also supply the relevant block height (fetched from the light client where needed, or stored alongside the `tx_bytes` in `RefundRequest`).

---

### Proof of Concept

1. Zcash testnet is at block height 3,900,000 (below Nu6_2 activation at 4,052,000). All transactions carry `BranchId::Nu6_1`.
2. User sends ZEC to a deposit address. The deposit fails (e.g., bridge misconfiguration). User calls `request_refund` with the raw deposit `tx_bytes` and a valid Merkle proof.
3. Bridge calls `WrappedTransaction::decode(&tx_bytes.0, &config.chain)`. Inside, `BranchId::Nu6_2` is hardcoded. [1](#0-0) 
4. `transaction.compute_txid()` returns a hash computed with Nu6_2 — different from the real Nu6_1 txid on-chain.
5. The bridge calls `verify_transaction_inclusion_promise` with the wrong txid. [8](#0-7) 
6. The light client returns `false`; `request_refund_callback` panics with `"verify_transaction_inclusion return false"`.
7. The refund request is never stored. The user's ZEC is permanently locked in the deposit address.
