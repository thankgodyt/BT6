### Title
Stub `validatePerasCert` Unconditionally Accepts Any Peer-Supplied Peras Certificate, Enabling Unauthorized Chain-Selection Weight Boost - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production Peras certificate inbound pipeline uses a placeholder `validatePerasCert` implementation that unconditionally returns `Right` for every certificate, performing zero cryptographic or structural checks. Any unprivileged peer can send a crafted `PerasCert` for an arbitrary block over the ObjectDiffusion mini-protocol, and the node will accept it, timestamp it, and add it to the `ChainDB` with a weight boost, potentially causing the node to prefer a non-canonical chain.

### Finding Description

**Root cause — stub validator always succeeds:**

The `BlockSupportsPeras` instance for all block types is a degenerate placeholder. The `validatePerasCert` method is explicitly marked TODO and unconditionally returns `Right`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature verification, no quorum check, no round-number validity check, no boosted-block existence check — every certificate is accepted as `ValidatedPerasCert` carrying the full `perasWeight` boost.

**Production inbound handler wires this stub directly:**

Both production pool writers call `validatePerasCert mkPerasParams` as the validation function passed to `processCerts`:

```haskell

          systemTime

          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

The production node-to-node handler in `NodeToNode.hs` wires `makePerasCertPoolWriterFromChainDB` directly into the live `hPerasCertDiffusionClient` handler: [3](#0-2) 

**`processCerts` accepts the stub-validated cert and adds it to ChainDB:**

`processCerts` calls `partitionEithers (validateCert <$> certsNotAlreadyInDb)`. Because the stub always returns `Right`, the `([], validatedCerts)` branch is always taken and every cert is passed to `addCert` (i.e., `ChainDB.addPerasCertAsync`), which the comment explicitly states "properly handles any needed chain selection side-effects": [4](#0-3) 

**Accepted cert carries a weight boost used in chain selection:**

The `ValidatedPerasCert` produced by the stub carries `vpcCertBoost = perasWeight params` (currently `PerasWeight 15`). The `PerasCertDB` weight snapshot derived from accepted certs is used by chain selection to boost the weight of the certified block: [5](#0-4) 

**Analog to the external report:**

The external report describes inputs (gnark public inputs) accepted without canonicalization/bounds checks, bypassing the intended validation boundary. Here, the analogous boundary is the Peras certificate validator: the `BlockSupportsPeras` class defines `validatePerasCert` as the mandatory gate before a cert may be treated as `ValidatedPerasCert` and acted upon. The stub removes that gate entirely — every peer-supplied cert passes unconditionally, exactly as the gnark verifier accepted every string without length or field-element checks.

### Impact Explanation

An unprivileged peer on the node-to-node network can send a `PerasCert` for any block — including a non-canonical, adversarially chosen block — and the receiving node will:

1. Accept it as `ValidatedPerasCert` with full `perasWeight` boost (currently 15 units).
2. Store it in the `PerasCertDB` / `ChainDB`.
3. Apply the weight boost to the certified block during chain selection.

This lets an attacker make an honest node assign Peras weight to an arbitrary block, potentially causing it to prefer a non-canonical or adversarially controlled chain over the honest chain. This is a **High** impact chain-selection integrity failure: an unprivileged peer can materially influence chain selection beyond the intended security assumptions of the Peras protocol, which requires a quorum of honest stake to certify a block.

### Likelihood Explanation

The ObjectDiffusion Peras certificate mini-protocol is active in the production node-to-node handler. Any peer that can establish a node-to-node connection — which requires no credentials — can send crafted certificates. The attack requires only constructing a valid CBOR-encoded `PerasCert` (two fields: `PerasRoundNo` and `Point blk`), which is trivially achievable from the public serialization instance: [6](#0-5) 

No key material, no stake, no privileged access is required.

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that checks at minimum:

1. The certified block exists and is on a valid chain.
2. The certificate's round number is within the valid window (`perasCertMaxRounds`).
3. The aggregate BLS signature over the voter set is valid (using the WFALS/EveryoneVotes committee verification path already implemented in `WFALS.hs` / `EveryoneVotes.hs`).
4. The voter set reaches the quorum stake threshold (`perasQuorumStakeThreshold`).

Until real validation is implemented, the `hPerasCertDiffusionClient` handler should be disabled or should reject all inbound certificates rather than silently accepting them.

### Proof of Concept

1. Connect to a target node as a peer (standard node-to-node handshake).
2. Send an ObjectDiffusion batch containing a `PerasCert` with `pcCertRound = <current round>` and `pcCertBoostedBlock = <point of any block, e.g., a non-canonical fork tip>`.
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right ValidatedPerasCert{vpcCertBoost = PerasWeight 15}`.
4. `ChainDB.addPerasCertAsync` is called; chain selection side-effects fire.
5. The target node now treats the attacker-chosen block as having a Peras weight boost of 15, potentially switching to the attacker's fork if it is otherwise competitive. [7](#0-6) [8](#0-7)

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
