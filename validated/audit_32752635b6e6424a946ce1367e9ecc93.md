Audit Report

## Title
Unregistered Tokens Accepted by `init_transfer` Without Registry Check, Causing Permanent Fund Freeze - (File: near/omni-bridge/src/lib.rs)

## Summary

The `ft_on_transfer` entry point routes any NEP-141 token transfer to `init_transfer` without verifying the token is registered in the bridge's `token_id_to_address` registry. The contract consumes the tokens (returns `U128(0)`), stores a pending transfer, and only fails irrecoverably when `sign_transfer` is later called — at which point the tokens are permanently held by the bridge with no user-accessible recovery path.

## Finding Description

`ft_on_transfer` (L252–283) accepts any NEP-141 token and dispatches to `init_transfer` for `InitTransfer` messages. Inside `init_transfer` (L523–619), the only validation is that the recipient chain is not NEAR and that `fee < amount`. There is no lookup against `token_id_to_address` or `token_address_to_id` to confirm the token is a registered bridge asset. The function proceeds to call `init_transfer_internal`, which stores the `TransferMessage` in `pending_transfers` and returns `U128(0)`, causing the NEP-141 token contract to keep all tokens in the bridge's account.

By contrast, `fast_fin_transfer` (L758–763) correctly calls `get_token_address(...).near_expect(BridgeError::TokenNotFound)` before proceeding, demonstrating the pattern is known but was not applied to `init_transfer`.

When a relayer later calls `sign_transfer`, the contract attempts to resolve the token address at L462–469 and panics with `ERR_FAILED_TO_GET_TOKEN_ADDRESS` for any unregistered token. The `init_transfer_resume` path (L631–642) does return the amount on storage-payment failure, but this is a separate yield/resume code path and does not apply to the main execution path where storage is available. No public `cancel_transfer`, `rescue_token`, or equivalent user-accessible recovery function is present; the documented public API (CLAUDE.md L57–70) lists only `ft_on_transfer`, `fin_transfer`, `sign_transfer`, `deploy_token`, `bind_token`, `log_metadata`, `update_transfer_fee`, and `claim_fee`.

## Impact Explanation

Any unprivileged user who sends an unregistered NEP-141 token to the bridge via `ft_transfer_call` with an `InitTransfer` message loses those tokens permanently. The bridge holds them with no user-accessible withdrawal or cancellation mechanism. This directly matches the allowed critical impact: **permanent freezing of bridged funds on NEAR**.

## Likelihood Explanation

The `ft_transfer_call` → `ft_on_transfer` path is the standard, documented mechanism for initiating a bridge transfer. Realistic triggering scenarios include: a user bridging a token before `deploy_token`/`bind_token` has finalized registration on the destination chain; a user sending the wrong token contract address; or a token being deregistered after a transfer is initiated. No special privileges are required — any token holder can trigger this with a single `ft_transfer_call` invocation.

## Recommendation

Add a registration check at the start of `init_transfer` before incrementing the nonce or storing any state. If the token is not found in the registry for the destination chain, return the full `amount` (triggering a NEP-141 refund) rather than consuming the tokens:

```rust
fn init_transfer(...) -> PromiseOrPromiseIndexOrValue<U128> {
    require!(
        init_transfer_msg.recipient.get_chain() != ChainKind::Near,
        BridgeError::InvalidRecipientChain.as_ref()
    );
    // Add before mutating state:
    require!(
        self.get_token_address(
            init_transfer_msg.get_destination_chain(),
            token_id.clone(),
        ).is_some(),
        BridgeError::TokenNotFound.as_ref()
    );
    // ... rest of function
}
```

Returning a non-zero `U128` from `ft_on_transfer` causes the NEP-141 token contract to refund the sender, preventing any fund loss.

## Proof of Concept

1. Deploy any NEP-141 token `unregistered-token.near` not present in the bridge's `token_id_to_address` map.
2. Call `ft_transfer_call` on `unregistered-token.near` with `receiver_id = omni-bridge.near`, `amount = 1000`, and `msg = {"InitTransfer": {"recipient": "eth:0x...", "fee": "0", "native_token_fee": "0"}}`.
3. The bridge's `ft_on_transfer` invokes `init_transfer`. No registration check fires. `init_transfer_internal` stores the pending transfer and returns `U128(0)`. The 1000 tokens are now held by the bridge.
4. Call `sign_transfer` with the resulting `TransferId`. The call panics at L467–468: `ERR_FAILED_TO_GET_TOKEN_ADDRESS`.
5. The 1000 tokens remain in the bridge's account. No public function exists to recover them. The user has permanently lost their funds.
