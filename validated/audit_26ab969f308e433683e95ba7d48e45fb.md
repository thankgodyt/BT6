### Title
Decimal Normalization Floor Division Produces Zero in `sign_transfer`, Permanently Freezing User Funds - (File: `near/omni-bridge/src/lib.rs`)

### Summary

`init_transfer` accepts and locks user tokens when `fee < amount`, but does not verify that `normalize_amount(amount - fee, decimals) > 0`. For tokens with a large decimal difference between origin and destination chains, a small net transfer amount is silently truncated to zero by floor division inside `sign_transfer`, which then permanently reverts with `ERR_INVALID_AMOUNT_TO_TRANSFER`. Because no cancel path exists for `pending_transfers`, the user's tokens are frozen in the bridge forever.

### Finding Description

`init_transfer` stores the transfer and locks/burns the user's tokens after a single guard:

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
``` [1](#0-0) 

This guard does **not** check whether the net amount survives decimal normalization. Later, when a relayer calls `sign_transfer`, the bridge normalizes the net amount with floor division:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message
        .amount_without_fee()
        .near_expect(BridgeError::InvalidFee),
    decimals,
);

require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
``` [2](#0-1) 

`normalize_amount` performs integer floor division:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [3](#0-2) 

`amount_without_fee` is a simple checked subtraction:

```rust
pub fn amount_without_fee(&self) -> Option<u128> {
    self.amount.0.checked_sub(self.fee.fee.0)
}
``` [4](#0-3) 

If `amount_without_fee < 10^(origin_decimals - decimals)`, the floor division yields `0`, and `sign_transfer` panics unconditionally. Every subsequent call to `sign_transfer` for that transfer ID will also panic, because the stored `TransferMessage` is immutable after creation.

### Impact Explanation

The user's tokens are locked or burned at `init_transfer` time (inside `init_transfer_internal`). The transfer is stored in `pending_transfers`. Because `sign_transfer` always reverts for this transfer and no `cancel_transfer` function exists in the contract, the locked tokens can never be recovered. This constitutes **permanent freezing of bridged funds**.

### Likelihood Explanation

The scenario is reachable by any unprivileged bridge user via the standard `ft_transfer_call` → `ft_on_transfer` → `init_transfer` path. It is triggered whenever:

- A token is registered with a large decimal gap (e.g., `origin_decimals = 24`, `decimals = 6`, divisor = `10^18`), which is a realistic configuration for NEAR-native tokens bridged to EVM chains.
- The user's `amount - fee` is less than the divisor (e.g., `amount = 2`, `fee = 1`, net = `1 < 10^18`).

The `init_transfer` guard only checks `fee < amount`, so the transaction is accepted and tokens are locked before the normalization check in `sign_transfer` is ever reached. A user who does not understand the decimal normalization semantics will have no indication that their transfer is permanently unprocessable.

### Recommendation

Add a pre-flight normalization check inside `init_transfer` (or `init_transfer_internal`) before locking tokens:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

This requires looking up the destination token's `Decimals` at `init_transfer` time, which is already done in `sign_transfer`. Alternatively, add a `cancel_transfer` function that allows the original sender to reclaim locked tokens for transfers that can never be signed.

### Proof of Concept

1. A token is registered with `origin_decimals = 24`, `decimals = 6` (divisor = `10^18`).
2. Alice calls `ft_transfer_call` with `amount = 2` and `fee = 1` targeting an EVM recipient.
3. `init_transfer` passes the guard (`1 < 2`). Alice's 2 tokens are locked in the bridge. The transfer is stored in `pending_transfers`.
4. A relayer calls `sign_transfer` for Alice's transfer.
5. `normalize_amount(1, {decimals: 6, origin_decimals: 24})` = `1 / 10^18` = `0`.
6. `require!(0 > 0, ...)` panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.
7. Every future call to `sign_transfer` for this transfer ID produces the same panic.
8. Alice's 2 tokens remain locked in the bridge with no recovery path. [2](#0-1) [3](#0-2) [1](#0-0)
