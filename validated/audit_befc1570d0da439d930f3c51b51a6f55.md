### Title
Missing Ownership Check in `sign_btc_transaction` Allows Anyone to Force MPC Signing of Any Pending Transaction - (File: `contracts/satoshi-bridge/src/api/chain_signatures.rs`)

### Summary

`sign_btc_transaction` is a public, unpermissioned function that accepts a caller-supplied `btc_pending_sign_id` and triggers MPC signing for the corresponding pending transaction without verifying that the caller is the owner of that pending info. Any NEAR account can call it for any other user's pending withdrawal or refund, forcing the MPC service to sign and finalize a transaction the owner may have intended to cancel.

### Finding Description

The `sign_btc_transaction` entry point in `chain_signatures.rs` accepts a `btc_pending_sign_id` string, looks up the corresponding `BTCPendingInfo`, and immediately delegates to `internal_sign_btc_transaction` — which issues a cross-contract call to the MPC chain-signatures service — without ever checking that `env::predecessor_account_id()` matches `btc_pending_info.account_id`.

```rust
pub fn sign_btc_transaction(
    &mut self,
    btc_pending_sign_id: String,
    sign_index: usize,
    key_version: u32,
) -> PromiseOrValue<bool> {
    let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
    btc_pending_info.assert_pending_sign();
    // ← no check: env::predecessor_account_id() == btc_pending_info.account_id
    ...
    self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
        .into()
}
``` [1](#0-0) 

Every `BTCPendingInfo` record carries an `account_id` field that identifies the legitimate owner of the pending transaction. [2](#0-1) 

The `require_pending_sign_capacity` guard used elsewhere (e.g., in `withdraw_rbf`) is entirely absent here. [3](#0-2) 

The parallel to the external report is exact: just as `voteExtraordinary(account_)` accepted any address and let an attacker act on behalf of every token holder, `sign_btc_transaction(btc_pending_sign_id, ...)` accepts any pending-info ID and lets an attacker act on behalf of any user's pending transaction.

### Impact Explanation

Once all inputs of a PSBT are signed by the MPC service, the transaction is ready to broadcast. The bridge's RBF/cancel path (`withdraw_rbf`, `cancel_withdraw`) is the only mechanism a user has to redirect or abort an in-flight withdrawal. If an attacker races to call `sign_btc_transaction` for every unsigned input of a victim's pending withdrawal before the victim can issue an RBF, the transaction becomes irrevocably committed to the original outputs. The victim loses the ability to cancel or redirect their withdrawal. For refund transactions the same applies: the attacker can force a refund PSBT to be fully signed and broadcast before the operator can reject the refund request.

This matches: **Medium — attacker-triggered temporary locking / bypass of bridge cancellation policy.**

### Likelihood Explanation

All `BTCPendingInfo` IDs are emitted as on-chain events (`GenerateBtcPendingInfo`), making them trivially enumerable by any observer. The function carries no access-control decorator, no `assert_one_yocto`, and no role check. Any NEAR account can call it at zero cost (beyond gas). The window of opportunity is the entire `PendingSign` stage, which lasts until the relayer broadcasts and the withdrawal is verified on-chain. [4](#0-3) 

### Recommendation

Add an ownership assertion at the top of `sign_btc_transaction`:

```rust
let caller = env::predecessor_account_id();
require!(
    btc_pending_info.account_id == caller,
    "Only the transaction owner can trigger signing"
);
```

Alternatively, restrict the function to whitelisted relayers or operators via `#[access_control_any]`, consistent with how other sensitive pipeline steps are guarded.

### Proof of Concept

1. Alice calls `ft_transfer_call` on the nBTC contract to initiate a withdrawal. The bridge emits a `GenerateBtcPendingInfo` event containing `btc_pending_id = "abc123"`.
2. Alice decides to cancel and prepares to call `cancel_withdraw`.
3. Mallory observes the event off-chain, immediately calls:
   ```
   sign_btc_transaction("abc123", 0, 0)
   sign_btc_transaction("abc123", 1, 0)
   ... (for each input)
   ```
4. The MPC service signs all inputs. The PSBT is now fully signed; `tx_bytes_with_sign` is populated.
5. Alice's subsequent `cancel_withdraw` call fails or produces an RBF that can never replace the already-signed transaction once broadcast.
6. The relayer broadcasts the original transaction; Alice's funds are sent to the original `target_btc_address` with no possibility of cancellation. [1](#0-0) [5](#0-4)

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> PromiseOrValue<bool> {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        btc_pending_info.assert_pending_sign();
        if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {
            if !self.check_btc_pending_info_exists(original_tx_id) {
                require!(
                    self.internal_unwrap_mut_account(&btc_pending_info.account_id.clone())
                        .btc_pending_sign_ids
                        .remove(&btc_pending_sign_id),
                    "Internal error"
                );
                self.internal_remove_btc_pending_info(&btc_pending_sign_id);
                return PromiseOrValue::Value(true);
            }
        }
        self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
            .into()
    }
