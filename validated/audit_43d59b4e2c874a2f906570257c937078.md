### Title
`revalidateHeader` Silently Discards Envelope Validation Result in Production Builds — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Util/Assert.hs`, `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/HeaderValidation.hs`)

---

### Summary

`revalidateHeader` wraps its envelope-validation result in `assertWithMsg`, which is a **compile-time no-op** in production builds (when `ENABLE_ASSERTIONS` is not defined). The `Either String ()` returned by `validateEnvelope` is computed but its `Left` (failure) branch is unconditionally discarded at runtime. This is a direct structural analog of the ERC20 unchecked-return-value pattern: a function returns a success/failure indicator, the caller ignores it, and state is updated as if the operation succeeded.

---

### Finding Description

`assertWithMsg` is defined with a CPP guard:

```haskell
assertWithMsg :: HasCallStack => Either String () -> a -> a
#if ENABLE_ASSERTIONS
assertWithMsg (Left msg) _ = error msg
#endif
assertWithMsg _ a = a
```

When `ENABLE_ASSERTIONS` is absent (the default in production/optimized builds), this compiles to `assertWithMsg _ a = a` — the first argument is completely ignored. [1](#0-0) 

`revalidateHeader` uses this to guard its envelope check:

```haskell
revalidateHeader cfg ledgerView hdr st =
  assertWithMsg envelopeCheck $
    HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'
 where
  envelopeCheck =
    runExcept $ withExcept show $
      validateEnvelope cfg ledgerView (untickedHeaderStateTip st) hdr
``` [2](#0-1) 

`validateEnvelope` enforces four structural invariants:
- Block numbers are consecutive (`UnexpectedBlockNo`)
- Slot numbers are monotonically increasing (`UnexpectedSlotNo`)
- The previous-hash pointer is correct (`UnexpectedPrevHash`)
- Checkpoint hashes match (`CheckpointMismatch`) [3](#0-2) 

In production, `assertWithMsg envelopeCheck result` reduces to `result` regardless of whether `envelopeCheck` is `Left` (failure) or `Right` (success). The new `HeaderState` is always returned, even when the header fails every one of those four checks.

The comment on `revalidateHeader` says "Expensive validation checks are skipped (`reupdateChainDepState` vs. `updateChainDepState`)." The expensive check being intentionally skipped is the VRF/KES cryptographic re-verification. The envelope check is **not** expensive — it is a handful of integer and hash comparisons — yet it is also silently dropped in production via `assertWithMsg`. [4](#0-3) 

---

### Impact Explanation

`revalidateHeader` is called from `Extended.hs` during the re-application path (e.g., `reapplyBlockLedgerResult`), which is exercised during chain selection when the node switches to a fork and re-applies previously-seen headers against a new ledger view. If the `LedgerView` supplied at re-application time differs from the one used during original validation (a realistic scenario across era boundaries or after a rollback), the envelope check may legitimately fail — but the failure is silently discarded and the `HeaderState` is updated with the invalid header anyway. This can corrupt the `HeaderState` (wrong tip, wrong `ChainDepState`) that is subsequently used for further header validation, chain selection, and ledger-state forecasting, potentially causing the node to accept an invalid chain or diverge from honest peers.

**Impact class:** High — header-state corruption / chain-selection bug that can cause an honest node to accept structurally invalid headers and diverge from the canonical chain.

---

### Likelihood Explanation

`revalidateHeader` is only called for headers that were previously validated, so the precondition is usually satisfied. However:
1. The `ENABLE_ASSERTIONS` flag is not set in production Cardano node builds, so the guard is always absent.
2. Any code path that calls `revalidateHeader` with a mismatched `LedgerView` (e.g., after a hard-fork era transition or a rollback that changes the forecast horizon) will silently accept a structurally invalid header.
3. A crafted peer that induces a specific fork-switch sequence could trigger this path with a header whose previous-hash or block-number is inconsistent with the supplied ledger view.

Likelihood: **Medium** — requires a specific fork-switch or era-transition sequence, but no privileged access or key compromise.

---

### Recommendation

Replace `assertWithMsg` with an unconditional check in `revalidateHeader`. The envelope check is not expensive and must not be guarded by a compile-time flag:

```haskell
revalidateHeader cfg ledgerView hdr st =
  case runExcept (withExcept show (validateEnvelope cfg ledgerView (untickedHeaderStateTip st) hdr)) of
    Left err -> error ("revalidateHeader: envelope check failed: " ++ err)
    Right () -> HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'
```

Alternatively, if the intent is truly that the envelope check is always expected to pass at this call site, the check should be promoted to a hard runtime error (not a CPP-guarded assertion) so that any violation is caught in production.

---

### Proof of Concept

1. Build `ouroboros-consensus` without `-DENABLE_ASSERTIONS` (the default production configuration).
2. Construct a `Header blk` whose `blockNo` is not `expectedNextBlockNo` relative to the supplied `Ticked (HeaderState blk)`.
3. Call `revalidateHeader cfg ledgerView hdr st` with this header.
4. Observe that the function returns a `HeaderState` with `NotOrigin (getAnnTip hdr)` and the updated `chainDepState'` — no exception is raised and no error is returned, despite the envelope check returning `Left "UnexpectedBlockNo ..."`.
5. The returned `HeaderState` now records the invalid header as the chain tip, corrupting all subsequent header validation and chain-selection decisions that depend on it.

The root cause is `assertWithMsg _ a = a` (the production branch of the CPP guard), which unconditionally discards the `Either String ()` validation result — a direct analog of ignoring the `bool` return value of ERC20 `transfer()`. [1](#0-0) [5](#0-4)
