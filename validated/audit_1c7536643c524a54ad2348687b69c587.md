### Title
`validatePerasCert` Unconditionally Accepts Any Certificate Without Association or Cryptographic Checks, Enabling Chain-Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` function unconditionally accepts every inbound `PerasCert` as valid, returning `Right` without verifying any cryptographic signature, without checking that the certificate's boosted-block reference corresponds to a real block on the chain, and without checking that the certificate's round number is consistent with the current chain state. An unprivileged peer can craft and diffuse a certificate that references an arbitrary block, causing the receiving node to apply a Peras weight boost to that block and prefer a non-canonical chain in chain selection.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that turns a raw `PerasCert` into a `ValidatedPerasCert`. The only production instance of this typeclass is the blanket `instance StandardHash blk => BlockSupportsPeras blk` in `SupportsPeras.hs`. Its implementation of `validatePerasCert` is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

The `PerasCert` type carries two fields: `pcCertRound :: PerasRoundNo` and `pcCertBoostedBlock :: Point blk`. [2](#0-1) 

Neither field is checked. The function does not verify:

1. **Cryptographic validity** — no aggregate signature or quorum proof is checked.
2. **Round–block association** — there is no check that `pcCertBoostedBlock` was actually voted on in round `pcCertRound`.
3. **Block existence** — there is no check that `pcCertBoostedBlock` exists anywhere on the chain.
4. **Round validity** — there is no check that `pcCertRound` is a plausible round for the current chain tip.

The resulting `ValidatedPerasCert` carries a `vpcCertBoost` equal to `perasWeight params`, which is the full configured Peras weight boost. [3](#0-2) 

This `ValidatedPerasCert` is then stored in the ChainDB via `addPerasCertAsync` and exposed through `getPerasWeightSnapshot`, which is consumed by chain selection to prefer chains containing boosted blocks. [4](#0-3) 

The same blanket instance's `validatePerasVote` also only checks stake-distribution membership and skips all cryptographic signature verification, meaning an attacker can also forge votes for any `PerasVoterId` in the distribution to trigger local certificate forging: [5](#0-4)

### Impact Explanation

**Impact: High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain.**

A crafted `PerasCert` accepted via `validatePerasCert` is stored as a `ValidatedPerasCert` with the full `perasWeight` boost. The `getPerasWeightSnapshot` STM action exposes this boost to the chain-selection logic. Because the boosted block is chosen by the attacker (any `Point blk`), the attacker can cause the node to assign a large weight to an adversarial fork, making it appear heavier than the honest canonical chain. The node will then switch to the adversarial fork, constituting a chain-selection safety failure driven entirely by a crafted network message from an unprivileged peer.

---

### Likelihood Explanation

**Likelihood: High.**

The Peras certificate diffusion protocol (`addPerasCertAsync`, `getPerasCertsAfter`) is a public miniprotocol endpoint reachable by any connected peer without authentication. The attacker only needs to serialize a `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock` and send it over the wire. No key material, stake, or privileged access is required. The blanket instance is the only instance in the codebase and is compiled into every node.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real one that:

1. Verifies the aggregate cryptographic signature over `(pcCertRound, pcCertBoostedBlock)` against the quorum of committee members' public keys.
2. Checks that `pcCertBoostedBlock` is a known block on the node's chain (or at least a plausible candidate).
3. Checks that `pcCertRound` is consistent with the current chain tip's slot and the configured round length.
4. Enforces the association between the certificate's round and the block it claims to boost (i.e., the block's slot must fall within the voting window for that round).

Similarly, `validatePerasVote` must verify the cryptographic signature of each vote before accepting it, to prevent vote forgery that triggers spurious local certificate forging.

---

### Proof of Concept

1. Connect an adversarial peer to an honest Cardano node running the Peras-enabled consensus.
2. Serialize a `PerasCert` with:
   - `pcCertRound = <any round number>`
   - `pcCertBoostedBlock = <Point of an adversarial fork block>`
3. Send this cert via the Peras object-diffusion miniprotocol.
4. The node calls `validatePerasCert params cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })` unconditionally. [6](#0-5) 

5. The cert is stored via `addPerasCertAsync` and the `PerasWeightSnapshot` is updated to reflect the boost on the adversarial fork block.
6. Chain selection now sees the adversarial fork as heavier than the honest chain and switches to it, completing the chain-selection manipulation.
