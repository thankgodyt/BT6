### Title
Batch Peras Vote/Certificate Processing Silently Discards Valid Items When Any Single Item Fails Validation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs`, `PerasVote.hs`)

---

### Summary

`processCerts` and `processVotes` reject the **entire inbound batch** of Peras certificates/votes if any single item fails validation, silently discarding all valid items in the same batch. An unprivileged peer can exploit this by crafting a batch that mixes valid votes/certs with one invalid item, causing the valid ones to be permanently lost from the local database for that round.

---

### Finding Description

The vulnerability class from the external report is **incomplete batch processing**: a function iterates over multiple items but only handles a subset, silently ignoring the rest, leading to incorrect state. The analog here is the inverse form of the same class: instead of processing only the first item and ignoring the rest, `processCerts` and `processVotes` discard **all** valid items whenever any single item in the batch is invalid.

In `processCerts`:

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (...) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
    -- Some certs are invalid => reject the whole batch
    -- @POC: validatedCerts (the valid ones) are silently discarded here
    (errs, _) ->
      throw (PerasCertValidationError errs)
``` [1](#0-0) 

The identical pattern exists in `processVotes`: [2](#0-1) 

Both functions are wired as `opwAddObjects` in the `ObjectPoolWriter` for the inbound side of the ObjectDiffusion miniprotocol: [3](#0-2) [4](#0-3) 

`opwAddObjects` is called directly from the inbound protocol handler when a batch of objects is collected from a peer: [5](#0-4) 

The `alreadyInDb` pre-filter only removes items already present in the local DB. Items not yet received from any peer pass through to validation, making the attack effective during the early propagation window of a new round's votes.

The code comment at lines 177–183 of `PerasCert.hs` explicitly acknowledges the all-or-nothing design but does not address the consequence that valid items are discarded alongside invalid ones: [6](#0-5) 

---

### Impact Explanation

Peras votes accumulate stake toward a quorum threshold. When quorum is reached, a certificate is forged and added to the `PerasCertDB`, which then triggers chain selection via `addPerasCertAsync`. The certificate's weight boost is applied to the boosted block in `getPerasWeightSnapshot`, directly influencing which candidate chain is preferred: [7](#0-6) 

If valid votes for a round are discarded because they arrived in a batch with one invalid vote, quorum may not be reached for that round. No certificate is forged. The Peras weight boost for the canonical chain is absent. Chain selection then proceeds on Praos rules alone, materially weakening the Peras security guarantees for that round. This fits the allowed impact scope: **a miniprotocol flaw that materially weakens vote and certificate authorization**.

**Severity**: Medium.

---

### Likelihood Explanation

An unprivileged peer participating in the ObjectDiffusion miniprotocol can craft a response batch containing `N` valid votes/certs and `1` invalid one. The protocol requests objects by ID and the peer fulfills the request with the crafted batch. The attack requires no keys, no stake, and no operator compromise. It is most effective during the early propagation window of a round's votes, before the victim node has received those votes from any other peer.

**Probability**: High — the attack is trivially constructable by any peer that can respond to object requests.

---

### Recommendation

`processCerts` and `processVotes` should process each item independently rather than applying all-or-nothing semantics:

1. Validate each item individually.
2. Add valid items to the DB regardless of whether other items in the batch are invalid.
3. Collect all validation errors and throw the exception (to disconnect the peer) only after the valid items have been persisted.

This mirrors the fix applied in staking-indexer PR 124 for the analogous bug: iterate over all items and handle each one, rather than short-circuiting on the first (or any) failure.

---

### Proof of Concept

**Attack scenario** (votes; identical for certs):

1. Honest node requests vote IDs `[V1, V2, V3]` from attacker peer via ObjectDiffusion.
2. Attacker responds with objects `[validVote_V1, validVote_V2, invalidVote_V3]`.
3. `processVotes` is called with this batch.
4. `alreadyInDb` filter passes all three (none yet in DB).
5. `mapM validateVote [V1, V2, V3]` returns `[Right v1, Right v2, Left err]`.
6. `partitionEithers` yields `([err], [v1, v2])`.
7. The `(errs, _)` branch fires: `throw (PerasVoteValidationError [err])`.
8. `v1` and `v2` — the valid votes — are **never added** to the `PerasVoteDB`.
9. The attacker peer is disconnected.
10. If no other peer re-sends `V1`/`V2` before the round ends, quorum is not reached, no certificate is forged, and the Peras weight boost for that round is lost. [2](#0-1)

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.

      throw (PerasVoteValidationError errs)

-- Process a Peras certificate by adding it to the PerasCertDB and potentially
-- performing chain selection if a candidate is now better than our selection.
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
