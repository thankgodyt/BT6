### Title
Missing Round-Expiry Enforcement in `validatePerasVote` Allows Stale Vote Acceptance and Spurious Certificate Forging - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasVote` API in `BlockSupportsPeras` structurally omits the current round number from its signature, making it impossible to enforce round expiry. The production inbound-vote processing path calls this function directly. An unprivileged peer can send `PerasVote` messages for arbitrary past or future rounds; these pass validation and are stored in the `PerasVoteDB`. If enough such votes accumulate for a past round, a spurious Peras certificate is forged, which—when included in a block—grants that block an unearned chain-weight boost, corrupting chain selection.

---

### Finding Description

The `BlockSupportsPeras` type class defines the vote-validation interface as:

```haskell
validatePerasVote ::
  PerasCfg blk ->
  PerasVoteStakeDistr ->
  PerasVote blk ->
  Either (PerasValidationErr blk) (ValidatedPerasVote blk)
``` [1](#0-0) 

The function receives only the static `PerasCfg` and the stake distribution. It does **not** receive the current round number. The `PerasVote` structure carries `pvVoteRound :: PerasRoundNo`:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound :: PerasRoundNo
  , pvVoteBlock :: Point blk
  , pvVoteVoterId :: PerasVoterId
  }
``` [2](#0-1) 

The only implemented body of `validatePerasVote` checks nothing about the round; it accepts any vote whose voter ID appears in the stake distribution:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [3](#0-2) 

The production inbound-vote path in `makePerasVotePoolWriterFromChainDB` calls this function directly for every vote received from a peer:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [4](#0-3) 

`processVotes` then timestamps and stores every vote that passes this check: [5](#0-4) 

Inside `implAddVote`, accepted votes are unconditionally fed into `updatePerasRoundVoteStates`, which creates a fresh round-vote-state for any round number it has not seen before and accumulates stake toward a quorum: [6](#0-5) 

When accumulated stake crosses the quorum threshold, `forgePerasCert` is called and a `ValidatedPerasCert` is produced for that round—regardless of whether the round is current, past, or future.

The `PerasCertMaxRounds` parameter exists to limit certificate age for block inclusion, but it is never consulted during vote validation: [7](#0-6) 

---

### Impact Explanation

A Peras certificate forged for a past round, when included in a block, grants that block a `perasWeight` boost in chain selection. An attacker who can inject enough votes for a past round (one vote per eligible voter ID, all passing the stake-distribution check) causes the node to forge a certificate it should never have produced. The resulting chain-weight distortion can make an honest node prefer a non-canonical chain, constituting a **High** chain-selection bug: an unprivileged peer causes an honest node to prefer a less-secure chain beyond the intended security assumptions.

---

### Likelihood Explanation

The attack requires sending `PerasVote` messages over the Peras vote-diffusion mini-protocol. No key material is needed: the degenerate `PerasVote` structure carries no cryptographic signature, so any peer can construct votes for any voter ID and any round. The only barrier is knowing which voter IDs appear in the stake distribution, which is public ledger state. The attack is therefore reachable by any unprivileged peer on a private testnet running the current code.

---

### Recommendation

1. Add the current `PerasRoundNo` (or current `SlotNo` from which the round can be derived) as a parameter to `validatePerasVote` so that implementations can enforce `pvVoteRound == currentRound`.
2. Introduce a `PerasVoteMaxRounds` parameter (analogous to `PerasCertMaxRounds`) and reject votes whose round is more than that many rounds in the past or future.
3. Ensure the `BlockSupportsPeras` class contract documents the round-currency invariant as a required check for all instances.

---

### Proof of Concept

1. Node A is running with the current code and is connected to a malicious peer B.
2. Peer B reads the public stake distribution and identifies voter IDs with sufficient combined stake to exceed the quorum threshold.
3. Peer B constructs `PerasVote` messages with `pvVoteRound = R` (a past round), `pvVoteBlock = someBlock`, and `pvVoteVoterId` set to each chosen voter ID. No signatures are required.
4. Peer B sends these votes to node A via the Peras vote-diffusion mini-protocol.
5. `processVotes` calls `validatePerasVote mkPerasParams sd vote` for each vote. Each passes because the voter ID is in the stake distribution.
6. `implAddVote` accumulates the votes in `pvdsRoundVoteStates` under round `R`. Once the quorum threshold is crossed, `forgePerasCert` produces a `ValidatedPerasCert` for round `R`.
7. This certificate is stored and eventually included in a block, granting that block an unearned `perasWeight` boost, skewing chain selection on node A.
