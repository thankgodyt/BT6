### Title
Missing cleanup path for cancel RBF stuck in `PendingSign` permanently freezes original withdraw tx — (`contracts/satoshi-bridge/src/rbf/cancel_withdraw.rs`)

### Summary
When a cancel-withdraw RBF is created via `internal_cancel_withdraw`, its ID is inserted into `rbf_txs[original_id]` and the original tx is marked canceled (`cancel_rbf_reserved = Some(...)`). If the subsequent MPC signing permanently fails, the cancel RBF remains in `PendingSign` indefinitely. The only available cleanup function, `clear_invalid_pending_verify_rbf`, unconditionally asserts `PendingVerify` and panics on a `PendingSign` entry. There is no `clear_invalid_pending_sign_rbf` equivalent. The original tx is then permanently frozen: `assert_not_canceled` blocks all future RBFs, and the stale cancel RBF entry in `rbf_txs` and `btc_pending_infos` cannot be removed without a DAO upgrade.

### Finding Description
`internal_cancel_withdraw` calls `set_rbf_pending_info`, which inserts the cancel RBF into `btc_pending_infos` at `PendingSign` stage and into `rbf_txs[original_id]`. It also calls `do_cancel` on the original tx, setting `cancel_rbf_reserved = Some(...)`. If `sign_btc_transaction_callback` returns `false` (MPC failure), no rollback occurs. The cancel RBF stays at `PendingSign`. `clear_invalid_pending_verify_rbf` calls `assert_pending_verify()` first, which panics on a `PendingSign` entry. No other cleanup function exists for this state. Because `assert_not_canceled()` checks `cancel_rbf_reserved.is_none()`, the original tx is permanently blocked from receiving any new RBF. [7](#0-6) [4](#0-3) 

### Impact Explanation
The original withdraw tx is permanently frozen in `PendingVerify` with no ability to create a new cancel or user RBF. The cancel RBF entry in `rbf_txs` and `btc_pending_infos` cannot be removed by any existing public function. Resolution requires a DAO contract upgrade. No direct fund theft occurs, but the user's BTC UTXOs remain locked in the bridge's pending state indefinitely. This matches: **Low — stuck-state invariant violation in production bridge paths without direct theft.**

### Likelihood Explanation
MPC signing failures are rare but documented (transient network issues, MPC node downtime). A permanent failure for a specific cancel RBF PSBT is unlikely under normal operation since signing can be retried. However, the cleanup gap is unconditional: if permanent failure occurs, there is zero recovery path without a DAO upgrade. The `cancel_withdraw` entrypoint has no privileged role check (beyond the DAO check for excess gas fee), making the precondition reachable by relayers.

### Recommendation
Add a `clear_invalid_pending_sign_rbf` function (or extend `clear_invalid_pending_verify_rbf` to handle `PendingSign` stage) that:
1. Removes the cancel RBF from `btc_pending_infos`
2. Removes the cancel RBF ID from `rbf_txs[original_id]`
3. Resets `cancel_rbf_reserved` on the original tx to `None` (rolling back `do_cancel`)
4. Restores any reserved protocol fee to `cur_available_protocol_fee`

### Proof of Concept
1. User withdraws nBTC → original tx in `PendingVerify`
2. Timeout passes; relayer calls `cancel_withdraw` → cancel RBF created in `PendingSign`; `rbf_txs[original_id]` now contains cancel RBF ID; original tx has `cancel_rbf_reserved = Some(...)`
3. MPC signing permanently fails → `sign_btc_transaction_callback` returns `false`; cancel RBF stays in `PendingSign`
4. Relayer calls `clear_invalid_pending_verify_rbf(cancel_rbf_id)` → `assert_pending_verify()` panics with "Not pending verify stage"
5. Relayer calls `cancel_withdraw` again → `assert_not_canceled()` panics with "already canceled"
6. Original tx and cancel RBF are permanently stuck; no public function can resolve the state [8](#0-7) [5](#0-4)
