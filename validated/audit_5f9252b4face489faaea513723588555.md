### Title
Unauthenticated `request_refund` Allows Front-Running to Permanently Block a User's Refund Request and Redirect BTC - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
`request_refund` is publicly callable by any NEAR account and does not verify that the caller is the `deposit_msg.recipient_id`. An attacker who observes a pending `request_refund` transaction can race it with an identical call that substitutes their own BTC `refund_address`. Because `request_refund_callback` enforces a strict one-request-per-UTXO invariant, the legitimate user's call is permanently rejected. The attacker's request then sits in the queue pointing to their own BTC address, and after the `unsafe_refund_timelock_sec` elapses, anyone can call `execute_refund` to drain the deposit to the attacker.

### Finding Description

`request_refund` is declared inside a `#[trusted_relayer]` impl block but carries no `#[trusted_relayer]` attribute on the function itself. [1](#0-0) 

Compare with `verify_deposit`, which carries `#[trusted_relayer]` on both the impl block and the function. `execute_refund` in the same block is explicitly documented as callable by anyone, confirming that the impl-level attribute does not restrict individual methods that omit it.

The function accepts a caller-supplied `refund_address` and only validates it against `deposit_msg.refund_address` when that optional field is set: [2](#0-1) 

When `deposit_msg.refund_address` is `None` (the common case where the user supplies the address at request time), no ownership check is performed. The callback then enforces a hard uniqueness constraint: [3](#0-2) 

This creates a first-come-first-served race: whoever registers the UTXO key first wins, and all subsequent callers are permanently rejected for that UTXO.

The attacker's attack path:
1. Monitor the NEAR RPC for a pending `request_refund` call (all arguments are visible in the transaction payload).
2. Submit an identical call with the same `deposit_msg`, `tx_bytes`, `vout`, and `proof`, but substitute `refund_address` with an attacker-controlled BTC address.
3. If the attacker's transaction is included first, `request_refund_callback` stores a `RefundRequest` keyed by `{tx_id}@{vout}` pointing to the attacker's address.
4. The legitimate user's callback hits the duplicate check and panics: `"Refund request already exists for this UTXO"`.
5. After `unsafe_refund_timelock_sec` (default **14 days**), anyone calls `execute_refund`, which builds a refund PSBT paying the attacker's address and initiates MPC signing. [4](#0-3) [5](#0-4) 

### Impact Explanation

**Immediate (Medium):** The legitimate user's `request_refund` call fails. They lose the NEAR anti-spam deposit (non-refundable per the docs) and their BTC deposit is locked until the DAO manually rejects the malicious request. This is an attacker-triggered stuck bridge state requiring operator intervention.

**Escalated (Critical):** If the DAO does not reject the malicious request within 14 days, `execute_refund` can be called by anyone, causing the MPC network to sign a Bitcoin transaction that sends the user's BTC to the attacker's address — a direct theft of bridged funds. [6](#0-5) 

### Likelihood Explanation

NEAR transactions are submitted to validators and are observable via the NEAR RPC (`broadcast_tx_async` / `tx` endpoints) before they are included in a block. A bot monitoring the RPC for `request_refund` calls can extract all parameters from the pending transaction and resubmit with a substituted `refund_address`. Unlike Ethereum, NEAR has no gas-price auction, but transaction ordering within a shard is not guaranteed to be FIFO for competing submissions, and a validator-colluding attacker has a straightforward advantage. The attack requires no special privilege — only a NEAR account and the ability to pay the storage deposit.

### Recommendation

1. **Bind the refund request to the deposit owner.** In `request_refund_callback`, verify that `env::predecessor_account_id()` (the original caller, passed through the callback chain) equals `deposit_msg.recipient_id`. Since the deposit address is derived deterministically from `deposit_msg`, only the intended recipient should be able to initiate a refund for their own deposit.

2. **Alternatively, require `deposit_msg.refund_address` to be pre-set.** Reject `request_refund` calls where `deposit_msg.refund_address` is `None` and the caller is not the `recipient_id`, eliminating the unauthenticated path entirely.

3. **Emit the caller's account ID in the refund request** so off-chain monitoring can detect mismatches quickly.

### Proof of Concept

    }

    pub(crate) fn resolve_execute_refund_timelock(&self, utxo_storage_key: &str) -> u64 {
        require!(
            env::attached_deposit() >= self.required_balance_for_execute_refund(),
            "Insufficient deposit for storage"
        );
        let caller = env::predecessor_account_id();
        let is_privileged =
            self.acl_has_any_role(vec![Role::DAO.into(), Role::RefundOperator.into()], caller);
        let refund_request: RefundRequest = self
            .data()
            .refund_requests
            .get(utxo_storage_key)
            .expect("Refund request not found")
            .into();
        let config = self.internal_config();
        if refund_request.deposit_msg().refund_address.is_some() {
            // Pre-authorized refund address: privileged users can fast-track.
            if is_privileged {
                0
            } else {
                config.refund_timelock_sec
            }
        } else {
            // Refund address supplied by caller of `request_refund`: longer
            // timelock to give DAO/Operator time to reject suspicious requests.
            config.unsafe_refund_timelock_sec
        }
    }

    pub(crate) fn finalize_refund_with_psbt(
        &mut self,
        caller: AccountId,
        mut refund_request: RefundRequest,
        psbt: PsbtWrapper,
        refund_amount: u128,
        utxo_storage_key: String,
    ) {
        let gas_fee = refund_request.gas_fee;
        let refund_address = refund_request.refund_address.clone();

        let deposit_msg = refund_request.deposit_msg();
        let path = get_deposit_path(&deposit_msg);
        let vutxo = VUTXO::Current(UTXO {
            path,
            tx_bytes: refund_request.tx_bytes.0.clone(),
            vout: refund_request.vout,
            balance: u64::try_from(refund_request.amount)
                .unwrap_or_else(|_| env::panic_str("Amount overflow")),
        });

        let psbt_hex = psbt.serialize();
        let btc_pending_id = psbt.get_pending_id();

        if !self.check_account_exists(&caller) {
            self.internal_set_account(&caller, crate::Account::new(&caller));
        }
        self.require_pending_sign_capacity(&caller);

        let btc_pending_info = BTCPendingInfo {
            account_id: caller.clone(),
            btc_pending_id: btc_pending_id.clone(),
            transfer_amount: 0,
            actual_received_amount: refund_amount,
            withdraw_fee: 0,
            gas_fee,
            burn_amount: 0,
            psbt_hex,
            vutxos: vec![vutxo],
            signatures: vec![None; 1],
            tx_bytes_with_sign: None,
            create_time_sec: nano_to_sec(env::block_timestamp()),
            last_sign_time_sec: 0,
            state: PendingInfoState::Refund(OriginalState {
                stage: PendingInfoStage::PendingSign,
                max_gas_fee: gas_fee,
                last_rbf_time_sec: None,
                cancel_rbf_reserved: None,
            }),
        };

        require!(
            self.data_mut()
                .btc_pending_infos
                .insert(btc_pending_id.clone(), btc_pending_info.into())
                .is_none(),
            "pending info already exist"
        );
        self.internal_unwrap_mut_account(&caller)
            .btc_pending_sign_ids
            .insert(btc_pending_id.clone());

        // Mark UTXO as verified to prevent verify_deposit later
        self.data_mut()
            .verified_deposit_utxo
            .insert(utxo_storage_key.clone());

        Event::RefundExecuted {
            utxo_storage_key: utxo_storage_key.clone(),
            amount: refund_request.amount.into(),
            refund_address,
        }
        .emit();

        Event::GenerateBtcPendingInfo {
            account_id: &caller,
            btc_pending_id: &btc_pending_id,
        }
        .emit();

        // Keep the request (so `execute_refund` can be called again to re-create
        // the transaction) but mark it executed; it is removed only when the
        // refund is finalized in `verify_refund_finalize`.
        refund_request.executed = true;
        self.data_mut()
            .refund_requests
            .insert(utxo_storage_key, refund_request.into());
