### Title
Silent Token Stranding in `safe_mint` When Recipient Is Unregistered — (File: `contracts/nbtc/src/lib.rs`)

### Summary
`safe_mint` in the nbtc token contract mints nBTC to `bridge_id` **before** checking whether the intended recipient account is registered. If the recipient is unregistered, the function returns `U128(0)` silently — without panicking, without burning the already-minted tokens, and without adding them to any recovery ledger. The minted nBTC is permanently stranded in the bridge's own token balance, inflating total supply while the depositing user receives nothing.

### Finding Description
In `contracts/nbtc/src/lib.rs`, `safe_mint` executes in this order:

1. `internal_deposit(&self.bridge_id, amount)` — unconditionally mints `amount` nBTC into the bridge contract's own token balance.
2. Checks whether `account_id` is registered: `self.token.accounts.get(&account_id).is_none()`.
3. If unregistered → `return PromiseOrValue::Value(U128(0))` — a **successful synchronous return of zero**, not a panic. [1](#0-0) 

The tokens minted in step 1 remain in `bridge_id`'s nbtc balance. There is no subsequent `internal_withdraw`, no `lost_found` entry, and no burn. The bridge's `safe_verify_deposit` comment explicitly states this path is supposed to "revert the whole transaction if minting fails," but `safe_mint` does not panic — it returns a value of 0, which the bridge callback receives as a **successful** cross-contract call result. [2](#0-1) 

The regular `mint` path avoids this entirely by auto-registering the account inside `mint_inner`: [3](#0-2) 

`safe_mint` deliberately skips auto-registration but fails to compensate by burning the pre-minted tokens on the unregistered-account branch.

The `lost_found` map in the satoshi-bridge is only populated by `transfer_nbtc_callback` (failed `ft_transfer` after a withdrawal), not by any `safe_mint` failure path: [4](#0-3) 

### Impact Explanation
- nBTC total supply increases by `amount` with no corresponding user balance — the bridge holds more nBTC than it should, permanently.
- The depositing user's BTC is locked in the bridge's Bitcoin UTXO set; they receive zero nBTC and have no on-chain recovery path (no `lost_found` entry, no refund triggered).
- This constitutes a **permanent loss of user funds** and a **broken supply invariant**: total nBTC supply no longer equals total BTC locked.

### Likelihood Explanation
Any user who deposits BTC via the `safe_deposit` flow (e.g., Omni Bridge integration) without having previously registered their NEAR account for nbtc storage triggers this path. NEAR NEP-141 requires explicit storage registration; new users or users interacting for the first time will commonly lack it. No privileged access is required — the attacker-controlled input is simply the deposit transaction itself.

### Recommendation
Move `internal_deposit` **after** the registration check, or panic (rather than returning 0) when the recipient is unregistered so the bridge callback can detect and handle the failure:

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "...");

    // Check registration BEFORE minting
    require!(
        self.token.accounts.get(&account_id).is_some(),
        "safe_mint: recipient account not registered"
    );

    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ... proceed with transfer
}
```

Alternatively, if a silent-zero return is intentional, the bridge's deposit callback must explicitly detect a zero return and burn the pre-minted tokens from `bridge_id`'s balance.

### Proof of Concept
1. User Alice deposits 0.01 BTC to the bridge's deposit address derived from her NEAR account `alice.near`, which has **never** called `storage_deposit` on the nbtc contract.
2. Relayer calls `verify_deposit_v2` with `deposit_msg.safe_deposit = Some(...)`.
3. Bridge verifies the Merkle proof and calls `nbtc.safe_mint(alice.near, 1_000_000, None)`.
4. `safe_mint` executes `internal_deposit(&bridge_id, 1_000_000)` — nBTC total supply increases by 1,000,000 satoshis, all credited to `bridge_id`.
5. `self.token.accounts.get(&alice.near)` returns `None` → function returns `PromiseOrValue::Value(U128(0))`.
6. Bridge callback receives a successful result of 0; Alice's BTC remains locked; Alice holds 0 nBTC; the 1,000,000 nBTC sits in `bridge_id`'s balance with no recovery mechanism. [5](#0-4)
