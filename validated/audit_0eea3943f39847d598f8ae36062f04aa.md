Audit Report

## Title
Dust-Amount Transfer Permanently Freezes Bridged Tokens Due to Missing Pre-Normalization Validation — (File: `near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer` applies only a `fee < amount` guard before locking or burning tokens and storing the pending transfer. For tokens where `origin_decimals > decimals`, any amount below the normalization threshold (`10^(origin_decimals - decimals)`) will cause every subsequent `sign_transfer` call to panic at the `amount_to_transfer > 0` require, and no public cancel or refund path exists. The user's tokens are permanently frozen.

## Finding Description

**Guard in `init_transfer`** (L554–557): The only amount-level check is: [1](#0-0) 

A transfer with `amount = 500_000` and `fee = 0` satisfies `0 < 500_000` and proceeds.

**Tokens locked/burned in `init_transfer_internal`** (L1850–1857): After `add_transfer_message` stores the entry, tokens are immediately burned or locked with no pre-normalization check: [2](#0-1) 

**Failure in `sign_transfer`** (L475–485): The normalization check that rejects dust amounts only runs here, after tokens are already gone: [3](#0-2) 

**`normalize_amount` uses floor division** (L2784–2787): For `origin_decimals=24`, `decimals=18`, any `amount < 10^6` floors to 0: [4](#0-3) 

The code comment at L2781–2783 explicitly acknowledges this: *"When fee = 0, dust stays locked/burned. See SECURITY.md for details."* — but SECURITY.md contains no such documentation or exclusion. [5](#0-4) 

**No recovery path**: `remove_transfer_message` is only called from `sign_transfer_callback` when the MPC call succeeds and `fee.is_zero()`. Since `sign_transfer` panics before the MPC call is ever made, the callback is never reached: [6](#0-5) 

A search for `cancel_transfer` across the entire repository returns zero matches. There is no public user-accessible refund or cancellation function.

## Impact Explanation
Tokens are either burned (for deployed bridge tokens) or locked inside the bridge contract with no mechanism to release them. This is **permanent, irreversible token loss** for the affected user, matching the Critical allowed impact: *"permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet, Bitcoin, Zcash, or Wormhole-routed flows."*

## Likelihood Explanation
The condition requires a token registered with `origin_decimals > decimals` (common for NEAR-native tokens with 24 decimals bridging to EVM chains with 18 decimals) and a user submitting an amount below the normalization threshold. No privileged access is required — any user can call `ft_transfer_call` directly. The condition can arise from user error or a UI that does not enforce a minimum transfer amount. Likelihood is **Low**, but the impact is irreversible.

## Recommendation
Add a pre-normalization check inside `init_transfer` (or `init_transfer_internal`) before locking or burning tokens. After resolving the token address and decimals, verify:

```rust
let normalized = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

This mirrors the guard already present in `sign_transfer` and prevents tokens from being locked before the unsignable state is detected. [3](#0-2) 

## Proof of Concept

1. Register a token with `origin_decimals = 24`, `decimals = 18` (diff = 6; threshold = 1,000,000 raw units).
2. Alice calls `ft_transfer_call` with `amount = 500_000` and `fee = 0`.
3. `init_transfer` checks `0 < 500_000` → passes. Tokens are burned/locked. Transfer stored in `pending_transfers`.
4. Relayer calls `sign_transfer` for Alice's transfer.
5. `normalize_amount(500_000, {origin=24, dest=18}) = 500_000 / 10^6 = 0`.
6. `require!(0 > 0, BridgeError::InvalidAmountToTransfer)` panics → transaction reverts.
7. Steps 4–6 repeat indefinitely. Alice's 500,000 raw units are permanently frozen with no cancel path.
