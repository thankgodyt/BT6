### Title
Tokens Permanently Stuck in Bridge Balance When `safe_mint` Is Called for an Unregistered Account - (File: contracts/nbtc/src/lib.rs)

### Summary
The `safe_mint` function in the nBTC token contract unconditionally deposits tokens into `bridge_id`'s balance **before** checking whether the recipient account is registered. When the account is not registered, the function returns early with `U128(0)`, leaving the minted tokens permanently stuck in `bridge_id`'s nBTC balance with no automatic recovery path.

### Finding Description
In `safe_mint` (`contracts/nbtc/src/lib.rs`, lines 101–124), the call to `self.token.internal_deposit(&self.bridge_id, amount.into())` at line 112 is unconditional. Only after that deposit is committed does the function check whether the recipient account is registered:

```rust
self.token.internal_deposit(&self.bridge_id, amount.into());   // ← tokens credited to bridge

if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0));                      // ← early return, no transfer
}
``` [1](#0-0) 

When the early-return branch is taken, `bridge_id`'s nBTC balance has already been increased by `amount`, but no transfer to `account_id` is ever issued. There is no rollback of the `internal_deposit`, no automatic `burn`, and no re-delivery mechanism. The tokens are stranded in the bridge's own nBTC balance.

By contrast, the non-safe `mint` path uses `mint_inner`, which auto-registers the account before depositing, so it never leaves tokens in an undeliverable state:

```rust
fn mint_inner(&mut self, account_id: &AccountId, amount: U128) {
    if self.token.accounts.get(account_id).is_none() {
        self.token.internal_register_account(account_id);   // ← registers first
    }
    self.token.internal_deposit(account_id, amount.into()); // ← then deposits directly
``` [2](#0-1) 

The structural parallel to the external report is exact: just as `SecurityCouncilMemberRemovalGovernor.initialize` performed all the subsidiary setup steps but omitted the critical `__Governor_init` call that initializes the state required for the function to work correctly, `safe_mint` performs the deposit step but omits the prerequisite registration check, leaving the contract in a broken intermediate state with no self-correction.

### Impact Explanation
Medium — stuck bridge state requiring operator intervention. A user who deposits BTC but has not registered their NEAR account with the nBTC token contract will have their deposit processed by the bridge (UTXO marked verified, BTC locked), yet receive zero nBTC. The corresponding nBTC tokens accumulate silently in `bridge_id`'s balance. Because the UTXO is marked verified, the refund system cannot be used. Recovery requires manual operator action (calling `burn` on the stranded balance and separately arranging restitution), and there is no guarantee the operator will detect the silent failure promptly.

### Likelihood Explanation
Medium. In NEAR, NEP-141 tokens require an explicit `storage_deposit` registration step before an account can hold a balance. A user unfamiliar with NEAR's storage model — or one who deposits BTC before completing registration — will trigger this silently. The `safe_mint` entry point is specifically designed for the "safe deposit" flow (`deposit_msg.safe_deposit` set), which is a documented, publicly reachable path.

### Recommendation
Move the account-registration check **before** the `internal_deposit` call so that no tokens are credited to `bridge_id` unless the transfer can actually complete:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );

    // Guard BEFORE any state mutation
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));
    }

    self.token.internal_deposit(&self.bridge_id, amount.into());

    if let Some(msg) = msg {
        self.ft_transfer_call(account_id, amount, None, msg)
    } else {
        self.ft_transfer(account_id, amount, None);
        PromiseOrValue::Value(amount)
    }
}
```

### Proof of Concept
1. User deposits BTC to the bridge with a `safe_deposit` message, but has **not** called `storage_deposit` on the nBTC contract for their NEAR account.
2. The bridge verifies the deposit proof and calls `safe_mint(user_account, amount, msg)` on the nBTC contract.
3. `safe_mint` executes `self.token.internal_deposit(&self.bridge_id, amount.into())` — `bridge_id`'s nBTC balance increases by `amount`. [3](#0-2) 
4. `self.token.accounts.get(&user_account).is_none()` returns `true`.
5. `safe_mint` returns `PromiseOrValue::Value(U128(0))` — no transfer is issued. [4](#0-3) 
6. The deposit UTXO is marked verified; the refund path is closed.
7. The user holds zero nBTC; their BTC is locked in the bridge; `amount` nBTC tokens are stranded in `bridge_id`'s balance with no automatic recovery.
