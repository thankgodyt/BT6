### Title
Missing Caller Ownership Check in `sign_btc_transaction` Enables Attacker to Inject Invalid Signature and Permanently Freeze Victim's Funds — (`contracts/satoshi-bridge/src/api/chain_signatures.rs`)

---

### Summary

`sign_btc_transaction` is a public, unpermissioned function. It accepts any `btc_pending_sign_id` from any caller and forwards an attacker-controlled `key_version` to the chain-signatures MPC contract. There is no check that `env::predecessor_account_id()` matches `btc_pending_info.account_id`. The callback that receives the MPC signature also performs no cryptographic validation — it blindly stores whatever signature the MPC returns. An attacker who calls this function with a victim's pending-sign ID and a non-zero `key_version` causes the MPC to sign with a different derived key than the one committed in the PSBT's `witness_utxo`. The resulting invalid signature fills the slot; the victim can never re-sign (the "Already signed" guard blocks them), the PSBT is permanently broken, and the victim's nBTC — already transferred to the bridge — is frozen.

---

### Finding Description

**Root cause 1 — no ownership check.**

`sign_btc_transaction` reads `btc_pending_info.account_id` but never asserts it equals `env::predecessor_account_id()`:

```rust
// contracts/satoshi-bridge/src/api/chain_signatures.rs  lines 21-43
pub fn sign_btc_transaction(
    &mut self,
    btc_pending_sign_id: String,
    sign_index: usize,
    key_version: u32,
) -> PromiseOrValue<bool> {
    let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
    btc_pending_info.assert_pending_sign();
    // ← NO require!(env::predecessor_account_id() == btc_pending_info.account_id)
    ...
    self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version).into()
}
``` [1](#0-0) 

**Root cause 2 — attacker-controlled `key_version` forwarded verbatim to MPC.**

`internal_sign_btc_transaction` passes the caller-supplied `key_version` directly to the chain-signatures contract:

**Root cause 3 — callback stores signature without cryptographic validation.**

`sign_btc_transaction_callback` derives the expected public key from `path` alone (no `key_version`), then stores the MPC response without verifying the signature is valid for that key:

```rust

`save_signature` constructs the witness from whatever `(signature, public_key)` pair it receives — no ECDSA verification:

```rust

        Some(Witness::p2wpkh(&signature.to_btc_signature(), &public_key));

**The "Already signed" guard blocks re-signing after the slot is filled.**

Once the attacker's callback lands first, the victim's subsequent call to `internal_sign_btc_transaction` hits:

```rust
require!(btc_pending_info.signatures[sign_index].is_none(), "Already signed");
``` [6](#0-5) 

The slot is permanently occupied by an invalid signature.

**nBTC is transferred to the bridge at withdrawal initiation and only burned after on-chain verification.**

From `CLAUDE.md`:
> Tokens TRANSFERRED to bridge (not burned yet!) … Burns from bridge balance (tokens already there!) [7](#0-6) 

The burn call only happens in `verify_withdraw_burn_promise`, which is triggered by a relayer after the BTC transaction confirms on-chain: [8](#0-7) 

A PSBT with an invalid signature will never confirm on Bitcoin, so `verify_withdraw` is never called, the burn never happens, and the nBTC is permanently locked in the bridge.

---

### Impact Explanation

The victim's nBTC is transferred to the bridge at step 1 of the withdrawal flow. If the PSBT is poisoned with an invalid signature, the Bitcoin transaction is unbroadcastable. The victim cannot re-sign (slot filled), cannot RBF (the same attack applies to any RBF replacement), and cannot recover the nBTC. This constitutes **permanent freezing of user funds** — the nBTC is stuck in the bridge balance indefinitely.

---

### Likelihood Explanation

- The `btc_pending_sign_id` is the Bitcoin txid of the PSBT, emitted in a public `GenerateBtcPendingInfo` event and queryable via `get_btc_pending_infos_paged`. It is fully public.
- The attack requires the NEAR chain-signatures MPC contract to accept `key_version ≥ 1`. The MPC contract is designed to support key rotation via `key_version`; whether version 1 is currently active is deployment-dependent, but the bridge contract imposes no restriction whatsoever.
- No privileged role is required. Any NEAR account can call `sign_btc_transaction`.
- The race is trivially won by calling before the victim has signed, or in the same block.

---

### Recommendation

1. **Add an ownership check** at the top of `sign_btc_transaction`:
   ```rust
   require!(
       env::predecessor_account_id() == btc_pending_info.account_id,
       "Not authorized"
   );
   ```
2. **Validate `key_version`** — enforce `key_version == 0` (or whatever the contract's canonical version is) before dispatching the MPC call.
3. **Validate the returned signature** in `sign_btc_transaction_callback` against the expected public key using `secp256k1::Secp256k1::verify_ecdsa` before storing it.

---

### Proof of Concept

```
1. Alice calls nbtc.ft_transfer(bridge, 100_000, WithdrawMsg{...})
   → bridge.ft_on_transfer creates BTCPendingInfo{account_id: alice, signatures: [None]}
   → btc_pending_sign_id = "<txid>" is emitted in GenerateBtcPendingInfo event

2. Attacker observes "<txid>" from chain events.

3. Attacker calls:
   bridge.sign_btc_transaction(
       btc_pending_sign_id = "<txid>",
       sign_index = 0,
       key_version = 1,          // ← wrong key version
   )
   → internal_sign_btc_transaction: signatures[0].is_none() == true → passes
   → MPC signs payload with key derived from (path, key_version=1)
   → callback: signatures[0].is_none() == true → stores invalid signature

4. Alice calls bridge.sign_btc_transaction("<txid>", 0, 0)
   → internal_sign_btc_transaction: signatures[0].is_none() == false
   → PANIC: "Already signed"

5. PSBT now contains a signature from key_version=1 but the witness_utxo
   script_pubkey commits to the key_version=0 public key.
   Bitcoin network rejects the transaction.

6. Alice's 100_000 nBTC is permanently locked in the bridge.
   verify_withdraw is never called. burn never executes.
```

    pub fn sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> PromiseOrValue<bool> {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        btc_pending_info.assert_pending_sign();
        if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {
            if !self.check_btc_pending_info_exists(original_tx_id) {
                require!(

                        .btc_pending_sign_ids

                    "Internal error"
                );
                self.internal_remove_btc_pending_info(&btc_pending_sign_id);
                return PromiseOrValue::Value(true);
            }
        }
        self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
            .into()
    }
