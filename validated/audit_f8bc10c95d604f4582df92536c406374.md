### Title
Missing Stake Normalization in Peras Quorum Check Enables Unauthorized Certificate Forging - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` compares a `PerasVoteStake` value directly against a relative quorum threshold without enforcing that the vote stake has been normalized to the same unit. The code itself documents this assumption as unverified. Because `PerasVoteStake` is an untagged `Rational`, any caller that populates `PerasVoteStakeDistr` with absolute ledger-stake values (lovelace) instead of relative values will cause the quorum check to be trivially satisfied by a single vote from any stake pool, allowing an unprivileged peer to forge a Peras certificate for an arbitrary block and manipulate chain selection.

---

### Finding Description

`stakeAboveThreshold` in `SupportsPeras.hs` performs the quorum gate for Peras certificate forging:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
```

The function's own documentation acknowledges the unit assumption is not enforced:

> "TODO: this function assumes that the 'PerasVoteStake' and the quorum threshold used in 'PerasParams' are expressed in the same units … this function only makes sense when both values are relative (normalized) values, so we should either normalize the 'PerasVoteStake' before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [1](#0-0) 

`PerasVoteStake` is a bare `Rational` newtype with no type-level tag distinguishing absolute from relative stake: [2](#0-1) 

The `validatePerasVote` implementation (the degenerate instance used for all blocks) assigns the stake from `PerasVoteStakeDistr` directly to `vpvVoteStake` with no normalization step:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
``` [3](#0-2) 

`votesReachQuorum` then sums the raw `vpvVoteStake` values and passes the total directly to `stakeAboveThreshold`:

```haskell
totalVoteStake = mconcat (vpvVoteStake <$> votes)
votesHaveEnoughStake = stakeAboveThreshold cfg totalVoteStake
``` [4](#0-3) 

The `PerasQuorumStakeThreshold` is defined as a relative `Rational` (e.g. `3/4`): [5](#0-4) 

If `PerasVoteStakeDistr` is populated with absolute lovelace values (e.g. `1_000_000 % 1` for 1 ADA), then `totalVoteStake` will be on the order of millions while `quorumThreshold` is `3 % 4`. The comparison `1000000 >= 0.75` is trivially true, so a **single vote** from any stake pool reaches quorum.

The production node-to-node handler currently passes `PerasVoteStakeDistr mempty` as a placeholder, explicitly noting this will be replaced with real committee selection data:

```haskell
-- TODO: when actual plumbing for Peras is ready, we will have to
-- extract the committee selection data from the chainDB to pass
-- it here, instead of relying on an empty the stake distribution.
(pure (PerasVoteStakeDistr mempty))
``` [6](#0-5) 

When that TODO is resolved and real ledger stake values are wired in without normalization, the vulnerability becomes immediately exploitable.

---

### Impact Explanation

**Impact: High — Bypass of Peras voting/certificate checks enabling unauthorized certificate acceptance and chain selection manipulation.**

A forged certificate causes `weightBoostOfFragment` to assign `perasWeight` (a large `Word64` boost) to the attacker's chosen block. `wsvTotalWeight` then adds this boost to the block number, making the attacker's chain appear heavier than the honest chain in `preferCandidate`. Honest nodes will switch to the attacker's boosted chain, violating chain-selection safety. [7](#0-6) 

---

### Likelihood Explanation

**Likelihood: Medium.** The vulnerability is latent: the production code currently uses an empty `PerasVoteStakeDistr`, so all inbound votes are rejected and the bug is not yet triggerable on mainnet. However, the empty distribution is an explicitly temporary placeholder. The moment real ledger stake values are wired in without normalization — which is the stated next step — any peer controlling a registered stake pool can exploit this with a single crafted vote message. The attack requires no special privileges beyond being a registered stake pool operator.

---

### Recommendation

1. **Enforce units at the type level.** Introduce distinct newtypes `AbsolutePerasVoteStake` and `RelativePerasVoteStake` so that `stakeAboveThreshold` can only accept the relative variant, making unit confusion a compile-time error.

2. **Normalize inside `validatePerasVote`.** Pass the total committee stake to `validatePerasVote` and divide the voter's absolute stake by the total before storing it in `vpvVoteStake`. Alternatively, move normalization into `stakeAboveThreshold` by accepting the total stake as an additional parameter.

3. **Remove the TODO and enforce the invariant before wiring real data.** The comment in `NodeToNode.hs` and the TODO in `stakeAboveThreshold` must be resolved together; the fix must be in place before real committee selection data is connected.

---

### Proof of Concept

**Private-testnet sequence:**

1. Start a private Cardano testnet with Peras enabled and a known stake distribution.
2. Populate `PerasVoteStakeDistr` with absolute lovelace values from the ledger (e.g. pool A has 1,000,000 lovelace → `PerasVoteStake (1000000 % 1)`).
3. Send a single `PerasVote` message from pool A targeting an attacker-controlled block `B_adv` via the node-to-node Peras vote diffusion miniprotocol.
4. `processVotes` calls `validatePerasVote`, which looks up `1000000 % 1` from the distribution and stores it in `vpvVoteStake`.
5. `updatePerasRoundVoteStates` → `updateCandidateVoteState` → `votesReachQuorum` computes `totalVoteStake = 1000000 % 1` and calls `stakeAboveThreshold`: `1000000 >= 0.75 + safetyMargin` → `True`.
6. A `ValidatedPerasCert` is forged for `B_adv` with boost `perasWeight`.
7. The ChainDB adds the certificate; `weightBoostOfFragment` assigns the full boost to `B_adv`'s fragment.
8. `preferCandidate` computes `wsvTotalWeight` for the attacker's chain as `blockNo(B_adv) + perasWeight`, which exceeds the honest chain's weight.
9. Honest nodes switch to the attacker's chain, achieving unauthorized chain selection manipulation with a single crafted vote. [8](#0-7) [9](#0-8)
