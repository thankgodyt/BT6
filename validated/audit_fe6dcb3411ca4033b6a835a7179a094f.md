Audit Report

## Title
Push-Based Token Delivery in `finTransfer` Permanently Freezes Bridged Funds When Recipient Cannot Receive Tokens - (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

## Summary

`OmniBridge.finTransfer` pushes tokens directly to a cryptographically-bound recipient address in the same atomic transaction as nonce finalization. If any delivery branch reverts, the entire transaction rolls back, but the MPC-signed payload permanently encodes the failing recipient, making every future `finTransfer` attempt revert identically. For NEAR-deployed bridge tokens, the corresponding burn on NEAR is issued with `.detach()` and is irreversible, leaving the funds permanently frozen with no EVM-side rescue path.

## Finding Description

`finTransfer` marks the nonce consumed at line 287, then immediately attempts push delivery across four branches (lines 317–355). If delivery reverts, the EVM rolls back all state — including the nonce flag — but the MPC-signed payload permanently encodes `payload.recipient` via `Borsh.encodeAddress(payload.recipient)` at line 298. Because `ECDSA.recover(hashed, signatureData) != nearBridgeDerivedAddress` would reject any payload with a different recipient, no alternative delivery address can ever be submitted. Every subsequent `finTransfer` call with the valid signature hits the same revert.

The three failing delivery branches are:

1. **Native ETH (lines 319–322):** `payload.recipient.call{value: payload.amount}("")` returns `success = false` for any contract with a reverting or absent `receive()`, triggering `revert FailedToSendEther()`.
2. **ERC1155 (lines 324–330):** `safeTransferFrom` invokes `onERC1155Received` on the recipient; a reverting hook propagates the revert to `finTransfer`.
3. **ERC20 (lines 351–354):** `safeTransfer` to a USDC/USDT-blacklisted address reverts unconditionally.

On the NEAR side, `init_transfer_internal` (line 1851) calls `burn_tokens_if_needed` with `.detach()` for NEAR-deployed bridge tokens — a fire-and-forget burn with no callback and no rollback path. There is no `claimTransfer`, `rescue`, or pull-based delivery function anywhere in the EVM contract, confirmed by code inspection.

## Impact Explanation

This matches the Critical allowed impact: **permanent freezing of bridged funds**. For NEAR-deployed bridge tokens, the burn at `near/omni-bridge/src/lib.rs:1808–1811` is unconditionally irreversible. The only EVM-side recovery path is a successful `finTransfer`, which can never succeed when the recipient is a reverting contract or a blacklisted address. Funds are burned on NEAR and undeliverable on EVM with no admin rescue function available.

## Likelihood Explanation

Three realistic, unprivileged trigger conditions exist:

- **USDC/USDT blacklisting:** A user initiates a NEAR→EVM USDC transfer; USDC's issuer subsequently blacklists the user's EVM address (e.g., due to regulatory action). Every `safeTransfer` call reverts permanently.
- **ETH to non-receiving contract:** A user specifies a multisig, proxy, or recently-upgraded contract that lacks or reverts in `receive()`. This is a common real-world mistake with contract addresses.
- **ERC1155 reverting hook:** A user specifies a contract recipient whose `onERC1155Received` reverts, blocking all ERC1155-backed bridge finalizations.

None of these require privileged access. USDC is a primary asset on Arbitrum, Base, and Polygon — all chains in scope.

## Recommendation

Adopt a pull-based delivery pattern: instead of pushing tokens inside `finTransfer`, credit the amount to a `mapping(uint64 => ClaimRecord) public claimable` mapping and emit an event. Add a separate `claimTransfer(uint64 destinationNonce)` function that the recipient calls to pull their tokens. This decouples nonce finalization from token delivery entirely.

Alternatively, wrap each delivery branch in a `try/catch` and, on failure, store the amount in a per-recipient claimable escrow rather than reverting the whole transaction, ensuring the nonce is consumed and the transfer is not permanently blocked.

## Proof of Concept

1. Deploy a NEAR-originated bridge token (deployed by the bridge, so `isBridgeToken[addr] = true`).
2. On NEAR, call `ft_transfer_call` to `omni-bridge.near` with `recipient = OmniAddress::Eth(<RevertingReceiver>)`. `init_transfer_internal` calls `burn_tokens_if_needed` with `.detach()` — tokens are burned irreversibly.
3. MPC signs a `TransferMessagePayload` with `recipient = <RevertingReceiver>`.
4. Any relayer calls `OmniBridge.finTransfer(signature, payload)`. The `IBridgeToken.mint(payload.recipient, payload.amount)` call succeeds (minting to a contract is fine), but for the ETH branch: `payload.recipient.call{value: amount}("")` returns `success = false`, triggering `revert FailedToSendEther()`. All state rolls back.
5. Every subsequent `finTransfer` with the same valid signature reverts identically. The bridge tokens are permanently burned on NEAR; no delivery is possible on EVM.

For the USDC variant: replace step 2 with a USDC transfer (locked, not burned, on NEAR), initiate the transfer, then have USDC's issuer blacklist the recipient EVM address. `safeTransfer` reverts on every `finTransfer` attempt.
