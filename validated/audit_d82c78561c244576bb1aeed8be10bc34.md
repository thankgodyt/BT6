### Title
Unconditional `validatePerasCert` Stub Accepts Any Peer-Supplied Peras Certificate, Enabling Chain-Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance contains a stub `validatePerasCert` that unconditionally returns `Right` (success) for every certificate it receives, performing no cryptographic or structural validation. This stub is wired directly into the live Peras certificate diffusion inbound handler. Any unprivileged peer can send a crafted `PerasCert` over the node-to-node Peras cert diffusion mini-protocol; the cert will be accepted, stored in the `PerasCertDB`, and its weight boost will be applied to chain selection, allowing the attacker to steer the node toward an adversarially chosen chain.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must authenticate a received Peras certificate before it is stored and its boost applied. The sole production instance (a "degenerate instance for all blks to get things to compile") implements this gate as an unconditional pass-through:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is called directly in the production inbound cert pool writer, which is the handler invoked for every cert received from a remote peer:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [2](#0-1) [3](#0-2) 

Both `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB` use this stub. The ChainDB variant is wired into the live node-to-node handler:

```haskell
(makePerasCertPoolWriterFromChainDB systemTime getChainDB)
``` [4](#0-3) 

Once a `ValidatedPerasCert` is stored, its boost is applied to chain selection via `weightBoostOfFragment`, which feeds into `preferAnchoredCandidate`. When Peras weights are non-empty, chain selection uses `wsvTotalWeight` (block number + weight boost) rather than block number alone:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [5](#0-4) 

The default `perasWeight` is `PerasWeight 15`, meaning a single fake cert can add 15 units of weight to any block the attacker names, potentially overriding the honest longest-chain preference. [6](#0-5) 

---

### Impact Explanation

**Critical.** This is a complete bypass of Peras certificate validation. An unprivileged peer can:

1. Craft a `PerasCert` naming any block as the boosted block.
2. Send it over the Peras cert diffusion mini-protocol.
3. The node accepts it unconditionally (stub returns `Right`).
4. The cert is stored and its `PerasWeight 15` boost is applied to chain selection.
5. The node may switch to a chain it would otherwise reject under honest Praos chain selection.

This satisfies the allowed impact: **Bypass of Peras certificate checks that enables unauthorized certificate acceptance**, and **chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain**.

---

### Likelihood Explanation

**High.** The attacker-controlled entry path is the standard node-to-node Peras cert diffusion mini-protocol, which is wired up in the production `NodeToNode.hs` handler. No special privileges, keys, or stake are required. Any peer that can establish a node-to-node connection can send crafted certs. The stub is explicitly marked as incomplete with a TODO, confirming it is not a deliberate design choice.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with real cryptographic and structural validation before the Peras cert diffusion handler is active in any production deployment. Until real validation is implemented, the inbound cert diffusion handler should either be disabled or should reject all inbound certs unconditionally. The analogous `validatePerasVote` stub (which does check stake distribution membership but performs no signature verification) should be reviewed under the same lens. [7](#0-6) 

---

### Proof of Concept

**Attacker-controlled entry path:**

1. Peer connects to a node via the node-to-node protocol.
2. Peer sends a `PerasCert` message via `hPerasCertDiffusionClient` naming a block on a minority fork as the boosted block. [8](#0-7) 

3. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = PerasWeight 15 })` unconditionally. [9](#0-8) 

4. The cert is stored via `addPerasCertAsync chainDB`, which triggers chain selection.
5. `preferAnchoredCandidate` now uses `weightedSelectView` with the fake boost, making the minority fork appear heavier. [10](#0-9) 

6. The node switches to the adversarially chosen chain.
