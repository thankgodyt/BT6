### Title
Peras Quorum Check Compares Unnormalized Vote Stake Against Relative Threshold, Enabling Unauthorized Certificate Acceptance — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` directly compares a `PerasVoteStake` value — which may carry an absolute (unnormalized) ledger stake — against a relative quorum threshold of `3/4`. The function's own inline comment admits the comparison is only meaningful when both operands are in the same unit (relative), and that normalization is not currently performed. This is the direct analog of the Hinkal.sol bug: a missing normalization step (analogous to missing parentheses) causes the arithmetic comparison to produce a systematically wrong result, here potentially allowing any single vote to satisfy quorum or preventing quorum from ever being reached.

---

### Finding Description

`stakeAboveThreshold` in `SupportsPeras.hs` is the sole gate that decides whether accumulated vote stake has reached the Peras quorum:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake         = unPerasVoteStake voteStake          -- Rational, unit unknown
  quorumThreshold = unPerasQuorumStakeThreshold ...   -- 3/4 (relative)
  safetyMargin    = unPerasQuorumStakeThresholdSafetyMargin ... -- 2/100 (relative)
``` [1](#0-0) 

The code comment immediately above the function explicitly states:

> *"this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally."* [2](#0-1) 

The `vpvVoteStake` field of a `ValidatedPerasVote` is assigned directly from `lookupPerasVoteStake vote stakeDistr` with no normalization step:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
``` [3](#0-2) 

The `PerasVoteStakeDistr` is supplied at runtime via `getStakeDistrSTM` in the production vote-ingestion path:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [4](#0-3) 

If the distribution contains absolute ledger stake values (e.g., lovelace amounts, which are integers ≥ 1), then for any voter with positive stake the comparison `stake >= 3/4 + 2/100` evaluates to `True` unconditionally, because any integer ≥ 1 exceeds `0.77`. A single vote from any voter with positive stake would therefore satisfy quorum. The same path is taken in `updateLoserVoteState` and `votesReachQuorum`: [5](#0-4) [6](#0-5) 

The default `mkPerasParams` sets `perasQuorumStakeThreshold = 3/4` and `perasQuorumStakeThresholdSafetyMargin = 2/100`: [7](#0-6) 

---

### Impact Explanation

**Scenario A — absolute stake values ≥ 1 (e.g., lovelace):** `stakeAboveThreshold` returns `True` for every vote from any voter with positive stake. A single crafted vote triggers certificate forging. The forged certificate boosts the adversary's chosen block by `perasWeight = 15` in chain selection, causing honest nodes to prefer the adversary's chain. This is a complete bypass of the Peras quorum check — unauthorized certificate acceptance — matching the Critical impact tier: *"Bypass of… Peras voting or certificate checks… that enables unauthorized… certificate acceptance."*

**Scenario B — absolute stake values < 3/4 (e.g., normalized fractions that happen to be small):** `stakeAboveThreshold` always returns `False`; quorum is never reached; the Peras boosting mechanism is permanently disabled, degrading chain-quality guarantees.

---

### Likelihood Explanation

The attack path is fully reachable by an unprivileged peer. Any node participating in the Peras vote miniprotocol can send `PerasVote` messages. `processVotes` → `validatePerasVote` → `stakeAboveThreshold` is the mandatory production code path for every inbound vote. No privileged access, key compromise, or stake majority is required. The only precondition is that the `PerasVoteStakeDistr` supplied at runtime contains unnormalized values — a condition the code itself acknowledges as unresolved.

---

### Recommendation

Normalize `PerasVoteStake` values to the interval `[0, 1]` before invoking `stakeAboveThreshold`. Concretely, divide each voter's absolute stake by the sum of all voters' stakes in the distribution before storing it in `PerasVoteStakeDistr`, or modify `stakeAboveThreshold` to accept the total stake as an additional parameter and perform the division internally:

```haskell
stakeAboveThreshold :: PerasParams -> Rational -> PerasVoteStake -> Bool
stakeAboveThreshold params totalStake voteStake =
  (unPerasVoteStake voteStake / totalStake) >= quorumThreshold + safetyMargin
```

This mirrors the fix for the Hinkal.sol bug: apply the normalization (division) in the correct order relative to the threshold comparison, rather than omitting it entirely.

### Proof of Concept

1. A peer constructs a `PerasVote` for an adversarial block `B_adv` in round `r`, signed by a pool with any positive absolute stake `s` (e.g., `s = 1_000_000` lovelace).
2. The vote is sent over the Peras vote miniprotocol to an honest node.
3. `processVotes` calls `validatePerasVote mkPerasParams sd vote`; `lookupPerasVoteStake` returns `PerasVoteStake (1_000_000 % 1)`.
4. `stakeAboveThreshold` evaluates `1_000_000 >= 3/4 + 2/100` → `True`.
5. `votesReachQuorum` returns `Just votesWithQuorum`; `forgePerasCert` is called.
6. A `ValidatedPerasCert` for `B_adv` with `vpcCertBoost = PerasWeight 15` is stored.
7. Chain selection now weights `B_adv`'s chain 15 blocks heavier than competing honest chains, causing the honest node to switch to the adversary's chain.
