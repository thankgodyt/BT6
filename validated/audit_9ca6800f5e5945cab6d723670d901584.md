Audit Report

## Title
Failed `fin_transfer` Removes Replay Protection, Enabling Proof Reuse - (File: near/omni-bridge/src/lib.rs)

## Summary

When an inbound `fin_transfer` to NEAR fails because the recipient contract rejects the token transfer via `ft_on_transfer`, `fin_transfer_send_tokens_callback` calls `remove_fin_transfer`, which deletes the `TransferId` from `finalised_transfers`. This set is the sole on-chain replay guard for inbound proofs. After deletion, the identical foreign-chain proof can be re-submitted, causing tokens to be minted or released a second time for a single foreign-chain deposit.

## Finding Description

The inbound transfer flow (Foreign → NEAR) is:

1. `fin_transfer` verifies the foreign-chain proof via the prover.
2. `fin_transfer_callback` calls `process_fin_transfer_to_near`.
3. `process_fin_transfer_to_near` calls `add_fin_transfer` (L2226–2234), which inserts the `TransferId` into `finalised_transfers` — the only replay guard — and panics if already present.
4. Tokens are sent via `send_tokens`. When `msg` is non-empty, `ft_transfer_call` is used, which invokes `ft_on_transfer` on the recipient contract.
5. `fin_transfer_send_tokens_callback` (L1692–1747) is invoked. `is_refund_required` (L1784–1804) returns `true` when the `ft_transfer_call` result (tokens actually used) is `0`. In NEAR's `ft_transfer_call` protocol, the used amount is `transferred − refunded`; if `ft_on_transfer` returns the full amount (rejecting all tokens), the used amount is `0`, so `is_refund_required` returns `true`.
6. On that path, `remove_fin_transfer` (L2322–2333) is called at L1714, unconditionally deleting the `TransferId` from `finalised_transfers`.

After step 6, the replay guard is gone. The prover holds no per-transfer state; it only validates the cryptographic proof against the foreign chain. Re-submitting the identical proof passes the prover again, `add_fin_transfer` succeeds (the set no longer contains the entry), and a second token release is executed.

The root cause is that the replay guard (an effect) is undone after the proof has already been accepted, violating the CEI pattern.

## Impact Explanation

**For bridge-deployed (wrapped) tokens**: `burn_tokens_if_needed` destroys the tokens after rejection. Re-submitting the proof mints a fresh batch. The attacker receives tokens on NEAR corresponding to a single foreign-chain burn — unauthorized minting and wrapped-token supply inflation.

**For native (locked) tokens**: `burn_tokens_if_needed` is a no-op. The bridge still holds the locked tokens. Re-submitting the proof transfers them to the attacker a second time, draining the bridge's reserve beyond what was deposited on the foreign chain — direct theft of bridged funds.

Both cases constitute unauthorized minting or permanent loss of bridged funds, matching the Critical allowed impact: *"Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds"* and *"Cross-chain replay … enabling invalid finalization or double-spending."*

## Likelihood Explanation

The attacker must:
1. Initiate a legitimate transfer on a supported foreign chain with a non-empty `msg` field so that `ft_transfer_call` is used on the NEAR side.
2. Control the NEAR recipient address — deploy a contract whose `ft_on_transfer` returns the full amount on the first call (rejecting tokens) and `0` on the second (accepting tokens).
3. Submit the proof twice — `fin_transfer` is a public, permissionless function.

No privileged access, leaked keys, or external dependency failure is required. The attacker funds only the initial foreign-chain deposit; all subsequent steps are free. This is a realistic, low-barrier attack path that can be repeated indefinitely.

## Recommendation

Do **not** remove the `TransferId` from `finalised_transfers` on a failed token delivery. The entry must remain permanently to prevent proof replay. Instead:

- Keep the `TransferId` in `finalised_transfers` after proof acceptance, regardless of delivery outcome.
- Store the undelivered amount in a claimable escrow keyed by the recipient, allowing the recipient to retry or withdraw without re-verifying the proof.
- If a storage refund is needed, handle it separately without touching `finalised_transfers`.

This restores the CEI pattern: the replay guard (effect) must never be undone after the proof has been accepted (check).

   - First call to ft_on_transfer: returns `amount` (rejects all tokens → ft_transfer_call result = 0).
   - Second call to ft_on_transfer: returns `0` (accepts all tokens).

2. Attacker calls initTransfer on EVM/Solana/Starknet:
   - token: any bridged token
   - recipient: RecipientContract
   - msg: "<non-empty>"   ← forces ft_transfer_call on NEAR side
   - amount: X

3. Relayer (or attacker) submits proof to NEAR fin_transfer.
   - process_fin_transfer_to_near → add_fin_transfer inserts TransferId.
   - ft_transfer_call → RecipientContract.ft_on_transfer returns X (reject).

   - add_fin_transfer succeeds (TransferId absent from set).
   - ft_transfer_call → RecipientContract.ft_on_transfer returns 0 (accept).
   - Attacker receives X tokens.

Result: Attacker received X tokens on NEAR for a single deposit of X on the

    fn is_refund_required(is_ft_transfer_call: bool) -> bool {
        if is_ft_transfer_call {
            match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
                Ok(value) => {
                    if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {
                        // Normal case: refund if the used token amount is zero
                        // The amount can be zero if the `ft_on_transfer` in the receiver contract returns an amount instead of `0`, or if it panics.
                        amount.0 == 0
                    } else {
                        // Unexpected case: don't refund
                        false
                    }
                }
                // Unexpected case: don't refund
                Err(_) => false,
            }
        } else {
            // Not ft_transfer_call: don't refund
            false
        }
    }

    fn remove_fin_transfer(&mut self, transfer_id: &TransferId, storage_owner: &AccountId) {
        let storage_usage = env::storage_usage();
        self.finalised_transfers.remove(transfer_id);

        let refund =
            env::storage_byte_cost().saturating_mul((storage_usage - env::storage_usage()).into());

        if let Some(mut storage) = self.accounts_balances.get(storage_owner) {
            storage.available = storage.available.saturating_add(refund);
            self.accounts_balances.insert(storage_owner, &storage);
        }
    }
