### Title
Peras Certificate Validation Bypass via Degenerate `BlockSupportsPeras` Instance — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `BlockSupportsPeras` type class provides a degenerate global instance (`instance StandardHash blk => BlockSupportsPeras blk`) where `validatePerasCert` unconditionally returns `Right` (accepting every certificate), `validatePerasVote` skips cryptographic signature verification entirely, and `getPerasCertInBlock` always returns `Nothing`. This degenerate instance is wired directly into the production Peras certificate and vote diffusion pipelines. The result is a split-brain analogous to the external report: one code path (peer-received certificates) writes to `PerasCertDB` without any validation, while the complementary code path (block-embedded certificates) never extracts anything because `getPerasCertInBlock` is permanently stubbed out. Chain selection consults `PerasCertDB` for Peras boost weights, so an unprivileged peer can inject fake certificates that manipulate which chain the node selects.

---

### Finding Description

**Root cause — degenerate instance with no validation:** [1](#0-0) 

The global instance at line 320 covers every `StandardHash blk`. Three methods are relevant:

1. `validatePerasCert` (lines 353–358) always returns `Right ValidatedPerasCert{…}` — no signature, no round-number bounds, no boosted-block existence check.
2. `validatePerasVote` (lines 363–371) only checks whether the voter ID appears in the stake distribution; it performs **no cryptographic signature verification**.
3. `getPerasCertInBlock` (line 389) always returns `Nothing` — certificates embedded in blocks are never extracted.

**Production call-site — certificate diffusion pipeline:** [2](#0-1) 

`makePerasCertPoolWriterFromChainDB` (the production writer used by the diffusion layer) passes `validatePerasCert mkPerasParams` directly to `processCerts`. Because the degenerate instance is in scope, every inbound certificate from every peer passes validation unconditionally. [3](#0-2) 

`processCerts` calls `validateCert` on each certificate; any that pass are timestamped and stored in `PerasCertDB` (or forwarded to `ChainDB.addPerasCertAsync`).

**Production call-site — vote diffusion pipeline:** [4](#0-3) 

`makePerasVotePoolWriterFromChainDB` calls `validatePerasVote mkPerasParams sd vote` for every inbound vote. Because signature verification is absent, any peer can forge votes for any voter whose ID appears in the public stake distribution.

**The split-brain (analog to the external report):**

The Shelley ledger's `applyBlockLedgerResultWithValidation` calls `getPerasCertInBlock` to update `shelleyLedgerLatestPerasCertRound`: [5](#0-4) 

Because `getPerasCertInBlock` always returns `Nothing`, `shelleyLedgerLatestPerasCertRound` is never updated from on-chain blocks. Meanwhile, `PerasCertDB` accumulates unvalidated peer-supplied certificates. Chain selection consults `PerasCertDB` for Peras boost weights: [6](#0-5) 

`chainSelSync` adds the certificate to `PerasCertDB` and then calls `chainSelectionForBlock` for the boosted block. The ledger state and the chain-selection subsystem therefore track Peras certificate state from two entirely different, inconsistent sources — exactly the split-brain pattern from the external report.

The `TestBlock` implementation explicitly documents this inconsistency: [7](#0-6)

### Impact Explanation

**Chain selection manipulation (High).** An unprivileged peer connected via the Peras certificate diffusion mini-protocol can craft a `PerasCert` whose `pcCertBoostedBlock` points to any block in the node's VolatileDB. Because `validatePerasCert` always returns `Right`, the certificate is stored in `PerasCertDB` and `chainSelSync` triggers `chainSelectionForBlock` for the boosted block. If the Peras boost weight tips the `ChainOrder` comparison, the node switches to a non-canonical chain. This satisfies the "chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain" criterion.

**Vote forgery enabling fake certificate creation (High).** Because `validatePerasVote` skips signature verification, any peer can forge votes for any committee member whose voter ID appears in the public stake distribution. Accumulating enough forged votes satisfies `votesReachQuorum`, causing the node to forge and store a certificate for an attacker-chosen block, compounding the chain-selection manipulation above.

---

### Likelihood Explanation

The Peras diffusion layer (`makePerasCertPoolWriterFromChainDB`, `makePerasVotePoolWriterFromChainDB`) is production code, not gated behind a feature flag in the files examined. Any peer that speaks the Peras object-diffusion mini-protocol can reach `processCerts` / `processVotes`. The stake distribution used by `validatePerasVote` is public on-chain data, so constructing valid-looking forged votes requires no privileged information. The TODO comments confirm the developers are aware the validation is absent, but the code is live in the production module path.

---

### Recommendation

1. **`validatePerasCert`**: Implement full cryptographic verification — check the aggregate BLS signature over `(pcCertRound, pcCertBoostedBlock)`, verify quorum membership and stake threshold, and validate round-number bounds against the current ledger state before accepting any certificate.
2. **`validatePerasVote`**: Add cryptographic signature verification (e.g., via `CryptoSupportsVoteSigning`) before accepting a vote; stake-distribution membership alone is insufficient.
3. **`getPerasCertInBlock`**: Implement proper extraction of Peras certificates embedded in blocks so that `shelleyLedgerLatestPerasCertRound` is updated from on-chain data, eliminating the split-brain between `PerasCertDB` and the ledger state.
4. Remove or gate the degenerate global instance behind a compile-time flag so it cannot silently be selected for production block types.

---

### Proof of Concept

1. Connect to a target node as an unprivileged peer via the Peras certificate diffusion mini-protocol.
2. Identify a block `B` in the node's VolatileDB that sits on a competing fork (e.g., obtained via ChainSync headers).
3. Craft `PerasCert { pcCertRound = <any round>, pcCertBoostedBlock = blockPoint B }`.
4. Send the certificate batch to the node. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right` unconditionally.
5. The certificate is stored in `PerasCertDB`. `chainSelSync` calls `chainSelectionForBlock` for `B`.
6. If the Peras boost weight assigned to `B`'s chain exceeds the weight of the node's current selection, the node switches to the non-canonical chain containing `B`.

No keys, no stake, no privileged access required — only the ability to send a well-formed CBOR-encoded `PerasCert` over the diffusion protocol.

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes

  -- Deliver promise indicating that we processed the cert.
  lift $ atomically $ putTMVar varProcessed certResult
 where
  tracer :: Tracer m (TraceAddPerasCertEvent blk)
  tracer = TraceAddPerasCertEvent >$< cdbTracer

  certRound :: PerasRoundNo
  certRound = getPerasCertRound cert

  boostedBlock :: Point blk
  boostedBlock = getPerasCertBoostedBlock cert
