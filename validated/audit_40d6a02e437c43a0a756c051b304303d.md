### Title
Unconditional `validatePerasCert` Acceptance Enables Crafted Certificate to Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or structural checks. An unprivileged peer can craft a `PerasCert` boosting any fork block and inject it via the object-diffusion mini-protocol. Because the certificate passes "validation" without any check, it is stored in the `PerasCertDB` and immediately triggers chain selection. The injected boost weight (`PerasWeight 15` by default) is added to the fork's total weight, potentially causing the honest node to switch away from the canonical chain.

---

### Finding Description

The `BlockSupportsPeras` typeclass requires implementors to supply a `validatePerasCert` function. The only concrete instance in the codebase is the degenerate catch-all instance:

`processCerts` calls this validator on every inbound certificate. If all certificates pass (which they always do), they are timestamped and forwarded to `ChainDB.addPerasCertAsync`: [3](#0-2) 

`addPerasCertAsync` enqueues the certificate for `chainSelSync`, which adds it to the `PerasCertDB` and then calls `chainSelectionForBlock` for the boosted block: [4](#0-3) 

Chain selection compares total weights using `wsvTotalWeight`, which is `BlockNo + PerasWeightBoost`. The default `perasWeight` is `PerasWeight 15`: [5](#0-4) [6](#0-5) 

No check is performed on:
- The aggregate BLS signature over the certificate message
- Whether the claimed voters actually formed a quorum
- Whether the `pcCertRound` is plausible given the current slot
- Whether the `pcCertBoostedBlock` corresponds to a block the peer is authorized to certify

The concrete BLS-capable `PerasCert` type exists in `Peras/Cert/V1.hs` but is not yet wired into the validation path: [7](#0-6)

### Impact Explanation

An adversary maintaining a fork that is at most 14 blocks behind the honest tip can send a single crafted `PerasCert` pointing to their fork's tip. The certificate passes `validatePerasCert` unconditionally, is stored in the `PerasCertDB`, and triggers chain selection. The fork's total weight becomes `fork_block_number + 15`, which exceeds the honest chain's `honest_block_number + 0` whenever the fork is within 15 blocks of the tip. The honest node switches to the adversarial fork, constituting a chain selection manipulation that can enable double-spend or rollback of recently confirmed transactions.

This matches the **High** impact category: a chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain beyond the intended security assumptions.

---

### Likelihood Explanation

The attack entry point is the standard Peras certificate object-diffusion mini-protocol, reachable by any connected peer without any special privileges. The crafted certificate requires only valid CBOR encoding of a `PerasCert` record (round number + block point), which is trivially constructable. No key material, stake, or VRF output is needed. The attack is deterministic and repeatable.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
1. Verifies the aggregate BLS signature against the claimed voters' public keys.
2. Checks that the set of voters constitutes a valid quorum (total stake ≥ threshold + safety margin).
3. Verifies each voter's eligibility proof (`PerasVoteEligibilityProof`) for the claimed round.
4. Rejects certificates whose `pcCertRound` is outside the acceptable window relative to the current slot.

The concrete BLS infrastructure already exists in `Ouroboros.Consensus.Peras.Cert.V1` and `Ouroboros.Consensus.Peras.Vote.V1`; it needs to be plumbed into the `BlockSupportsPeras` instance used by the production node. [8](#0-7) 

---

### Proof of Concept

1. Connect to a target node as a peer via the Peras certificate object-diffusion mini-protocol.
2. Construct a `PerasCert` (CBOR-encoded list of 2 items: a `PerasRoundNo` and a `Point blk`) pointing to a block on a fork that is ≤14 blocks behind the honest tip.
3. Send the certificate batch to the target node.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = PerasWeight 15 })` unconditionally.
5. The certificate is forwarded to `ChainDB.addPerasCertAsync`, enqueued, and processed by `chainSelSync`.
6. `chainSelSync` adds the cert to `PerasCertDB` and calls `chainSelectionForBlock` for the fork block.
7. `preferAnchoredCandidate` computes `fork_block_number + 15 > honest_block_number`, and the node switches to the fork.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
