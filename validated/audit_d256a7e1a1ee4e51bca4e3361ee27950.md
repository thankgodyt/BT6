### Title
Missing Cryptographic Signature Verification in `validatePerasVote` Allows Unprivileged Peer to Inject Forged Peras Votes and Trigger Unauthorized Certificate Acceptance — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate production instance of `validatePerasVote` (and `validatePerasCert`) in `SupportsPeras.hs` performs no cryptographic verification whatsoever. It only checks whether the claimed voter ID exists in the stake distribution. An unprivileged peer can craft a `PerasVote` claiming to be from any committee member in the stake distribution, bypass the "validation" step, have the vote counted toward quorum, and cause honest nodes to forge and accept a Peras certificate for an attacker-chosen block — directly influencing chain selection.

---

### Finding Description

The `BlockSupportsPeras` type class defines `validatePerasVote` and `validatePerasCert` as the gatekeepers for accepting Peras votes and certificates. The only concrete instance currently in the production codebase is the degenerate catch-all instance:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
``` [1](#0-0) 

The `validatePerasVote` implementation in this instance is:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [2](#0-1) 

This only checks that `pvVoteVoterId` is a key in the stake distribution map. It does **not** verify:
- The BLS signature on the vote body (`pvSignature` in the V1 concrete type)
- The VRF eligibility proof (`pvEligibilityProof`)
- The round number validity
- Any other cryptographic property

Similarly, `validatePerasCert` unconditionally returns `Right` for every certificate:

```haskell
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [3](#0-2) 

The production inbound vote processing path in `processVotes` calls this validation function directly:

```haskell
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
``` [4](#0-3) 

And `makePerasVotePoolWriterFromChainDB` wires this up for the live node:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [5](#0-4) 

Once a vote passes this non-check, `implAddVote` in `PerasVoteDB/Impl.hs` inserts it into the vote tally and calls `updatePerasRoundVoteStates`, which may forge a certificate if quorum is reached: [6](#0-5) 

The deduplication guard in `implAddVote` only checks `pvdsVoteIds` (a `Set (PerasVoteId blk)` where `PerasVoteId = {roundNo, voterId}`): [7](#0-6) 

This means: the first crafted vote for a given `(roundNo, voterId)` pair is accepted and counted. An attacker who sends forged votes for multiple distinct voter IDs in the stake distribution can accumulate enough stake to cross the quorum threshold and trigger certificate forging for an attacker-chosen block.

The `PerasVoteId` type itself is `{pviRoundNo :: PerasRoundNo, pviVoterId :: PerasVoterId}` — it does not include the block being voted for: [8](#0-7) 

This is the direct analog to the plugin-selector collision: the deduplication key (`PerasVoteId`) is a short identifier that does not encode the full vote content, and the "validation" step that should enforce cryptographic authenticity is a no-op stub.

---

### Impact Explanation

**Critical — Bypass of vote/certificate verification enabling unauthorized certificate acceptance.**

A Peras certificate boosts a block's weight in chain selection. If an attacker can forge enough votes to reach quorum for a block of their choice, honest nodes will:
1. Forge a `ValidatedPerasCert` for the attacker's block
2. Store it in `PerasVoteDB` and propagate it
3. Apply the certificate's boost to that block during chain selection

This allows an unprivileged peer to make honest nodes prefer a non-canonical or adversarially-chosen chain, violating Peras's core safety guarantee.

---

### Likelihood Explanation

The stake distribution is public on-chain. An attacker can enumerate all current committee member voter IDs from it. The object diffusion mini-protocol (`ObjectDiffusion/ObjectPool/PerasVote.hs`) is reachable by any peer. The only barrier is that the degenerate instance is a known placeholder — but it is the only instance compiled into the node today, and the TODO issue (#120) is open.

---

### Recommendation

Replace the degenerate `validatePerasVote` and `validatePerasCert` stubs with implementations that perform full cryptographic verification before the Peras vote diffusion path is enabled in any network-connected node. Specifically:

1. `validatePerasVote` must verify the BLS signature over `(roundNo, boostedBlock)` using the voter's registered hot key, and verify the VRF eligibility proof for non-persistent committee members.
2. `validatePerasCert` must verify the aggregate BLS signature over the certificate body against the claimed voter set.
3. Until these checks are implemented, the inbound vote processing path (`processVotes` / `makePerasVotePoolWriterFromChainDB`) should be disabled or gated behind a feature flag that is off by default. [9](#0-8) 

---

### Proof of Concept

An attacker connected as a peer:

1. Reads the current `PerasVoteStakeDistr` (public, derived from the ledger state).
2. For a target round `R` and an attacker-chosen block point `B_attacker`, constructs `N` `PerasVote` values:
   ```
   PerasVote { pvVoteRound = R, pvVoteBlock = B_attacker, pvVoteVoterId = V_i }
   ```
   for `N` distinct voter IDs `V_i` drawn from the stake distribution, with total stake exceeding the quorum threshold. No valid signature is needed.
3. Sends these votes to the target node via the object diffusion protocol.
4. `processVotes` calls `validatePerasVote` for each; each passes because `V_i` is in the stake distribution.
5. Each vote is inserted into `PerasVoteDB` via `implAddVote` → `updatePerasRoundVoteStates`.
6. Once cumulative stake crosses the quorum threshold, `updateCandidateVoteState` calls `forgePerasCert` and returns `AddedPerasVoteAndGeneratedNewCert cert`.
7. The node now holds a `ValidatedPerasCert` boosting `B_attacker`, which is applied to chain selection — causing the node to prefer the attacker's block over the honest chain. [10](#0-9)
