### Title
Arithmetic Underflow in `check_withdraw_psbt` Panics Before Gas-Fee Bounds Validation — (File: `contracts/satoshi-bridge/src/psbt.rs`)

---

### Summary

In `check_withdraw_psbt`, three plain integer subtractions execute before the gas-fee range guard. Because the workspace compiles with `overflow-checks = true`, any underflow aborts the transaction. An unprivileged withdrawal user can craft a PSBT whose output values make `gas_fee` exceed `amount − withdraw_fee`, triggering an arithmetic underflow panic before the documented gas-fee bounds are ever checked. The panic propagates through `ft_on_transfer`, causing the NEP-141 callback to refund the user's tokens, but the ordering flaw means the contract's own validation logic is bypassed by the panic path.

---

### Finding Description

`check_withdraw_psbt` in `psbt.rs` performs three consecutive plain subtractions:

**Line 238** — `gas_fee` derivation:
```rust
let gas_fee = total_input_amount - total_output_amount;
``` [1](#0-0) 

**Lines 242–243** — received-amount window:
```rust
let max_received_amount = amount - withdraw_fee - gas_fee;
let min_received_amount = max_received_amount - config.min_change_amount;
``` [2](#0-1) 

The gas-fee range guard that is supposed to reject out-of-bounds values appears only at **lines 252–258**, after all three subtractions:
```rust
require!(
    gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee,
    ...
);
``` [3](#0-2) 

The workspace release profile enables `overflow-checks = true`: [4](#0-3) 

This is the direct analog to the Cobb-Douglas report: the bounds check is intended to gate invalid inputs, but the arithmetic operation panics before the check is reached, so the documented invariant (`min_btc_gas_fee ≤ gas_fee ≤ max_btc_gas_fee`) is never enforced for these inputs.

The call chain is:

`ft_on_transfer` → `ft_on_transfer_withdraw_chain_specific` → `create_btc_pending_info` → `check_withdraw_psbt_valid` → `check_withdraw_psbt` [5](#0-4) [6](#0-5) 

`create_btc_pending_info` removes UTXOs from the bridge's UTXO set via `generate_vutxos` **before** calling `check_withdraw_psbt_valid`: [7](#0-6) 

Because the panic occurs inside a single NEAR transaction, all state mutations (including the UTXO removal) are rolled back atomically, and the NEP-141 `ft_resolve_transfer` callback refunds the user's tokens. No funds are permanently lost, but the contract's own gas-fee validation is never executed for these inputs.

---

### Impact Explanation

**Low.** This is a publicly reachable, panic-driven fault in a production bridge path without direct theft. The user's tokens are refunded by the NEP-141 callback, and the bridge UTXO state is restored by NEAR's transactional rollback. No other user's funds or operations are affected. The impact matches the allowed Low category: "Publicly reachable … panic-driven fault in production bridge/token paths without direct theft."

---

### Likelihood Explanation

**Medium.** Any holder of nBTC tokens can trigger this by initiating a withdrawal (`ft_transfer_call`) and supplying a PSBT whose total output value is small relative to the selected UTXO inputs. No privileged access, leaked keys, or external dependency compromise is required. The only precondition is holding a non-zero nBTC balance above `min_withdraw_amount`. [8](#0-7) 

---

### Recommendation

Reorder the validation so the gas-fee range check executes **before** the subtractions that depend on it. Replace the plain subtractions with `checked_sub` (returning a descriptive error on underflow) so that malformed PSBTs are rejected gracefully rather than via a panic:

```rust
// Check gas_fee bounds BEFORE using it in subtraction
let gas_fee = total_input_amount
    .checked_sub(total_output_amount)
    .unwrap_or_else(|| env::panic_str("output exceeds input"));
require!(
    gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee,
    format!("Invalid gas fee ({}). valid range: [{}, {}].",
            gas_fee, config.min_btc_gas_fee, config.max_btc_gas_fee)
);
let max_received_amount = amount
    .checked_sub(withdraw_fee)
    .and_then(|v| v.checked_sub(gas_fee))
    .unwrap_or_else(|| env::panic_str("amount too small to cover fees"));
```

---

### Proof of Concept

1. Alice holds 1 000 satoshis of nBTC (`amount = 1_000`, above `min_withdraw_amount`).
2. The bridge UTXO set contains a 1 BTC UTXO (`total_input_amount = 100_000_000`).
3. Alice calls `nbtc.ft_transfer_call(bridge, "1000", WithdrawMsg { input: [large_utxo], output: [TxOut { value: 1 sat, script: alice_addr }], … })`.
4. Inside `check_withdraw_psbt`:
   - `gas_fee = 100_000_000 − 1 = 99_999_999`
   - `max_received_amount = 1_000 − withdraw_fee − 99_999_999` → **underflow panic** (line 242)
5. The gas-fee range check at lines 252–258 is never reached.
6. `ft_on_transfer` panics; NEAR rolls back all state changes; `ft_resolve_transfer` refunds Alice's 1 000 satoshis.
7. The bridge's own `max_btc_gas_fee` guard — the control that should have rejected this PSBT — was never evaluated. [9](#0-8) [3](#0-2) [10](#0-9)
