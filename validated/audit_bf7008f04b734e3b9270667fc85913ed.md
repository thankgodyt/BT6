### Title
Zcash `execute_refund` Lacks Reentrancy Guard, Enabling Duplicate Pending Refund Transactions for the Same UTXO — (File: `contracts/satoshi-bridge/src/refund.rs`, `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

The public `execute_refund` entry point makes an async cross-contract call (Zcash path) before committing the critical state update that would block a second execution. During the async window, any unprivileged account can call `execute_refund` again for the same `utxo_storage_key`, bypassing all duplicate-execution guards and creating a second pending refund transaction for the same deposit UTXO. This results in stuck bridge state requiring operator intervention.

---

### Finding Description

`execute_refund` in `bridge.rs` is a public, payable function with no reentrancy guard:

```rust
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn execute_refund(
    &mut self,
    utxo_storage_key: String,
    chain_specific_data: Option<ChainSpecificData>,
) -> PromiseOrValue<()> {
    let timelock_sec = self.resolve_execute_refund_timelock(&utxo_storage_key);
    self.internal_execute_refund(utxo_storage_key, timelock_sec, chain_specific_data)
}
``` [1](#0-0) 

The function delegates to `internal_execute_refund`, which for the Zcash path makes an async cross-contract call before state is committed. The state update — marking `executed = true` and inserting the UTXO into `verified_deposit_utxo` — only happens inside `finalize_refund_with_psbt`, which the codebase itself documents runs inside a `#[private]` callback on Zcash:

> `caller` is the account that will own the pending info — it must be passed explicitly because **on Zcash this runs inside a `#[private]` callback** where `predecessor` is the contract itself. [2](#0-1) 

The guard in `load_refund_request_for_execute` that is supposed to block duplicate execution reads:

```rust
require!(
    !self.data().verified_deposit_utxo.contains(utxo_storage_key)
        || refund_request.executed,
    "UTXO already verified via deposit, cannot refund"
);
``` [3](#0-2) 

Both `executed` and `verified_deposit_utxo` membership are only set inside `finalize_refund_with_psbt`:

```rust
self.data_mut()
    .verified_deposit_utxo
    .insert(utxo_storage_key.clone());
// ...
refund_request.executed = true;
self.data_mut()
    .refund_requests
    .insert(utxo_storage_key, refund_request.into());
``` [4](#0-3) 

Because these writes happen only in the callback, the state visible to any concurrent call during the async window still shows `executed = false` and the UTXO absent from `verified_deposit_utxo`. A second caller invoking `execute_refund` for the same `utxo_storage_key` before the first callback is processed will pass every check and proceed to create a second `BTCPendingInfo` for the same deposit UTXO.

The `require_pending_sign_capacity` check inside `finalize_refund_with_psbt` is per-account:

```rust
self.require_pending_sign_capacity(&caller);
``` [5](#0-4) 

Two different accounts calling `execute_refund` concurrently each pass their own capacity check independently, so both callbacks can succeed and insert separate `BTCPendingInfo` entries for the same UTXO.

---

### Impact Explanation

Two pending refund transactions are created for the same deposit UTXO. Both are forwarded to the MPC chain-signature service for signing. Only one can be confirmed on the Zcash chain (the UTXO can only be spent once). The second signed transaction is permanently invalid, leaving a stale `BTCPendingInfo` entry in bridge state that can never be finalized via `verify_refund_finalize`. Cleanup requires privileged operator intervention via `remove_refund_pending_tx_id`. This matches the allowed Medium impact: **stuck bridge state requiring operator intervention**.

---

### Likelihood Explanation

`execute_refund` is a fully public, permissionless function (no `#[trusted_relayer]`, no role check). Any NEAR account can call it after attaching the small required storage deposit. The only prerequisite is a valid, timelock-expired refund request, which any user can create via `request_refund`. The attack requires two transactions submitted in the same block (or before the first callback receipt is processed), which is straightforward to arrange on NEAR.

---

### Recommendation

Set an "in-flight" flag on the `RefundRequest` **before** the async call, and check it at the start of `execute_refund`. For example, add an `in_flight: bool` field to `RefundRequest` (alongside the existing `executed` field), set it to `true` immediately in `execute_refund` before dispatching the async call, and `require!(!refund_request.in_flight, "Refund already in flight")` in `load_refund_request_for_execute`. Clear the flag in the callback if the async call fails, and leave it set (or transition to `executed = true`) on success. This follows the checks-effects-interactions pattern by committing the blocking state change before any external call.

---

### Proof of Concept

1. A Zcash deposit UTXO `X@0` has a valid, timelock-expired refund request in `refund_requests`.
2. Account `attacker_a` calls `execute_refund("X@0", Some(orchard_bundle_a))` with the required attached deposit.
3. The Zcash path dispatches an async cross-contract call (Orchard bundle verification or similar). State is **not yet updated**: `executed == false`, `verified_deposit_utxo` does not contain `"X@0"`.
4. In the same block, before the callback receipt is processed, account `attacker_b` calls `execute_refund("X@0", Some(orchard_bundle_b))` with the required attached deposit.
5. `load_refund_request_for_execute` passes for `attacker_b`: `executed == false` and `"X@0"` is not in `verified_deposit_utxo`.
6. Both callbacks eventually execute `finalize_refund_with_psbt` — one for `attacker_a`, one for `attacker_b` — each inserting a distinct `BTCPendingInfo` for the same UTXO.
7. Both pending transactions are forwarded to MPC for signing. Only one can be broadcast and confirmed on Zcash. The other leaves a permanently stale `BTCPendingInfo` that can never be finalized, requiring operator cleanup via `remove_refund_pending_tx_id`.
