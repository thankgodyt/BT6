### Title
First-Caller Griefing via Deterministic `btc_pending_id` Permanently Locks Deposit UTXO in Refund Limbo — (`contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

The question's stated mechanism (capacity exhaustion via repeated calls) is **incorrect** — the PSBT is fully deterministic, so every call to `execute_refund` for the same UTXO produces the **same** `btc_pending_id`. The second call fails at the `"pending info already exist"` guard, not at `require_pending_sign_capacity`. However, the underlying vulnerability is **real and critical**: any unprivileged caller can invoke `execute_refund` first, seize ownership of the deterministic pending slot, refuse to sign, and permanently lock the victim's deposit UTXO because `verified_deposit_utxo` is set and **never removed** anywhere in the codebase.

---

### Finding Description

**Step 1 — Public entrypoint, no role check.**

`execute_refund` carries only `#[pause]`; any account can call it after the timelock elapses. [1](#0-0) 

**Step 2 — Deterministic `btc_pending_id`.**

`internal_execute_refund` builds the PSBT from the stored `RefundRequest` fields (fixed `outpoint`, fixed `refund_output`, fixed `deposit_output`). `get_pending_id()` returns the unsigned transaction's `txid`, which is a pure function of those fields. [2](#0-1) [3](#0-2) 

Every caller for the same UTXO gets the **identical** `btc_pending_id`.

**Step 3 — First caller wins the slot; second caller is permanently blocked.**

`finalize_refund_with_psbt` inserts the pending info and hard-requires the slot was empty: [4](#0-3) 

The attacker calls first (capacity check passes: 0 < 1). The victim's subsequent call passes `load_refund_request_for_execute` (because `executed == true` bypasses the deposit guard), passes `require_pending_sign_capacity` (victim has 0 pending), but then panics at `"pending info already exist"`. [5](#0-4) 

**Step 4 — `verified_deposit_utxo` is set and never removed.**

`finalize_refund_with_psbt` unconditionally inserts the UTXO key into `verified_deposit_utxo`: [6](#0-5) 

A grep across the entire production source confirms there is **no** `verified_deposit_utxo.remove()` call anywhere. This flag blocks:
- `verify_deposit` (deposit path checks membership)
- `request_refund_callback` (re-requesting a refund is blocked)

**Step 5 — No recovery path exists.**

`remove_refund_pending_tx_id` is `#[trusted_relayer]`-gated and only removes the `BTCPendingInfo`; it does not touch `verified_deposit_utxo`. [7](#0-6) 

DAO can call `reject_refund`, which removes the `refund_requests` entry but again does not touch `verified_deposit_utxo`. [8](#0-7) 

After DAO rejection + relayer cleanup of the pending info:
- `refund_requests` is empty → `execute_refund` panics "Refund request not found"
- `verified_deposit_utxo` still contains the key → `request_refund_callback` panics "UTXO already verified via deposit"
- `verify_deposit` is also blocked

The BTC remains at the bridge-controlled deposit address with no on-chain path to recover it.

---

### Impact Explanation

An unprivileged attacker pays a small NEAR storage deposit, calls `execute_refund` once on any pending refund request after the timelock, and permanently locks the victim's BTC. The deposit UTXO is unspendable by the bridge (no signed tx was ever broadcast) and unrecoverable by the user (all three recovery paths — deposit, refund, re-request — are blocked). This constitutes **permanent, irreversible loss of user funds** with no on-chain remedy.

---

### Likelihood Explanation

- `execute_refund` is fully public; the only precondition is that the timelock has elapsed (observable on-chain via the `RefundRequested` event).
- The attacker's cost is the NEAR storage deposit for `execute_refund` (a few tenths of a NEAR).
- The `utxo_storage_key` is emitted in the `RefundRequested` event and is trivially computable as `{txid}@{vout}`.
- No special knowledge, role, or key is required.
- The attack is a single transaction.

---

### Recommendation

1. **Remove `verified_deposit_utxo` on refund rejection/cleanup.** When `reject_refund` or `remove_refund_pending_tx_id` is called for a request whose `executed == true`, also remove the corresponding key from `verified_deposit_utxo` so the user can re-request.

2. **Tie the pending info to the UTXO, not the caller.** Before inserting, check whether a pending info for this `btc_pending_id` already exists and, if so, either reuse it (if the caller is the same) or reject the call with a clear error rather than allowing a different caller to seize the slot.

3. **Restrict `execute_refund` to DAO/Operator/RefundOperator**, or at minimum to the original depositor, so an unprivileged third party cannot seize the pending slot.

---

### Proof of Concept

```
// Precondition: Alice's refund request exists, timelock has passed.
// utxo_storage_key = "abc123@0" (from RefundRequested event)

// Step 1: Attacker calls execute_refund
attacker.call("execute_refund", { utxo_storage_key: "abc123@0", chain_specific_data: null })
// → succeeds; BTCPendingInfo inserted with btc_pending_id = X (deterministic txid)
// → verified_deposit_utxo now contains "abc123@0"
// → refund_request.executed = true
// Attacker never calls sign_btc_transaction.

// Step 2: Alice tries to execute the refund
alice.call("execute_refund", { utxo_storage_key: "abc123@0", chain_specific_data: null })
// → load_refund_request_for_execute passes (executed=true bypasses deposit guard)
// → require_pending_sign_capacity passes (Alice has 0 pending)
// → builds same PSBT → same btc_pending_id = X
// → PANICS: "pending info already exist"

// Step 3: DAO rejects the refund request
dao.call("reject_refund", { utxo_storage_key: "abc123@0" })
// → refund_requests entry removed; verified_deposit_utxo unchanged

// Step 4: Alice tries to re-request a refund
alice.call("request_refund", { ... })
// → request_refund_callback PANICS: "UTXO already verified via deposit"

// Result: Alice's BTC is permanently locked.
// verified_deposit_utxo has no removal function anywhere in the codebase.
```

```rust
    pub(crate) fn internal_execute_refund(
        &mut self,
        utxo_storage_key: String,
        timelock_sec: u64,
        _chain_specific_data: Option<ChainSpecificData>,
    ) -> PromiseOrValue<()> {
        let refund_request = self.load_refund_request_for_execute(&utxo_storage_key, timelock_sec);
        let RefundExecutionInputs {
            outpoint,
            deposit_output,
            refund_amount,
        } = self.refund_execution_inputs(&refund_request);
        let refund_output = self.build_refund_output(&refund_request.refund_address, refund_amount);

        let mut psbt = PsbtWrapper::new(vec![outpoint], vec![refund_output]);
        psbt.set_input_utxo(vec![deposit_output]);

        let caller = env::predecessor_account_id();
        self.finalize_refund_with_psbt(
            caller,
            refund_request,
            psbt,
            refund_amount,
            utxo_storage_key,
        );
        PromiseOrValue::Value(())
    }
```
