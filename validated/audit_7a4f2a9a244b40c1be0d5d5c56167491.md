### Title
Peras Certificate Validation Bypass Allows Unprivileged Peer to Manipulate Chain Selection Weight — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance used for all block types implements `validatePerasCert` as an unconditional `Right`, performing zero cryptographic or structural checks on inbound Peras certificates. Any unprivileged peer can send a crafted `PerasCert` that is accepted without verification, stored in the `PerasCertDB`, and immediately used to boost a target block's weight in chain selection. This can cause an honest node to prefer a non-canonical, attacker-controlled fork over the legitimate chain.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub:**

The `BlockSupportsPeras` instance declared for all `StandardHash blk` in `SupportsPeras.hs` is explicitly labelled a "degenerate instance … to get things to compile" and contains:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This function **always returns `Right`** regardless of the certificate's content, round number, boosted block, or any cryptographic proof. No signature, no VRF check, no committee membership check is performed.

**Inbound path — `processCerts` calls this stub as the sole validator:**

`makePerasCertPoolWriterFromChainDB` (the production writer used by the node kernel) passes `validatePerasCert mkPerasParams` directly as the validation callback to `processCerts`:

```haskell
(validatePerasCert mkPerasParams)
``` [2](#0-1) [3](#0-2) 

`processCerts` rejects a batch only if `validateCert` returns `Left`; since the stub always returns `Right`, every inbound certificate from every peer passes validation unconditionally: [4](#0-3) 

**State mutation — accepted certificate triggers chain selection:**

The accepted `ValidatedPerasCert` (carrying `vpcCertBoost = perasWeight params`) is added to `PerasCertDB` via `addPerasCertAsync`, which enqueues a `ChainSelAddPerasCert` event. `chainSelSync` then calls `chainSelectionForBlock` for the boosted block: [5](#0-4) 

The weight boost is reflected in `PerasWeightSnapshot`, which is read by `weightedSelectView` and `preferAnchoredCandidate` during chain selection: [6](#0-5) 

The `PerasCertDB/Impl.hs` itself also carries the same TODO acknowledging missing validation: [7](#0-6) 

**Analogous secondary issue — `validatePerasVote` skips signature verification:**

The vote validator only checks stake-distribution membership but performs no signature or VRF proof check, allowing any peer to forge votes on behalf of any registered stake pool: [8](#0-7) 

---

### Impact Explanation

An unprivileged peer can send a crafted `PerasCert` claiming to certify any block (including one on an attacker-controlled fork). Because `validatePerasCert` unconditionally returns `Right`, the certificate is stored and its weight boost is applied to chain selection. If the boosted fork's `wsvTotalWeight` (block number + Peras boost) exceeds the honest chain's weight, the node switches to the attacker's fork — accepting an invalid or non-canonical chain. This is a **Critical** bypass of Peras certificate verification enabling unauthorized certificate acceptance and chain-selection manipulation.

---

### Likelihood Explanation

The Peras mini-protocol is active in the production node kernel (`makePerasCertPoolWriterFromChainDB` is wired into `NodeKernel`). Any peer that can establish a connection can send certificates. The stub is the only instance in the codebase and is used unconditionally. No privilege, key material, or stake is required. Likelihood is **High** for any deployment where the Peras certificate diffusion mini-protocol is enabled.

---

### Recommendation

1. **Implement real certificate validation** in `validatePerasCert`: verify the certificate's aggregate signature against the declared committee members, check that the boosted block's slot falls within the correct Peras round window, and confirm the round number is not stale.
2. **Implement real vote validation** in `validatePerasVote`: verify the vote signature against the voter's registered key and check the VRF eligibility proof.
3. Until real validation is implemented, **gate the Peras certificate and vote mini-protocols** so they are not reachable from untrusted peers.
4. Add a compile-time or runtime guard that prevents the degenerate stub instance from being used in any non-test context.

---

### Proof of Concept

```
1. Attacker connects to a target node as a peer via the Peras certificate
   mini-protocol.

2. Attacker constructs a PerasCert:
     PerasCert { pcCertRound    = <any round>
               , pcCertBoostedBlock = <point on attacker fork> }

3. Attacker sends the certificate batch to the node.

4. processCerts calls:
     validatePerasCert mkPerasParams cert
   → always returns Right (ValidatedPerasCert { vpcCertBoost = perasWeight params })
   → certificate passes "validation".

5. addPerasCertAsync enqueues ChainSelAddPerasCert.

6. chainSelSync adds the cert to PerasCertDB and calls
   chainSelectionForBlock for the boosted block.

7. weightedSelectView computes wsvTotalWeight for the attacker's fork
   as (blockNo + perasWeight), which may exceed the honest chain's weight.

8. preferAnchoredCandidate returns ShouldSwitch → node adopts the
   attacker's non-canonical fork.
```

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

```haskell
-- Process a Peras certificate by adding it to the PerasCertDB and potentially
-- performing chain selection if a candidate is now better than our selection.
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
