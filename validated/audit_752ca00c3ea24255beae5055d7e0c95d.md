### Title
Hardcoded `BranchId::Nu6_2` in `Transaction::decode` Permanently Blocks Refund Path for Pre-NU6.2 Zcash Deposits — (`contracts/satoshi-bridge/src/zcash_utils/transaction.rs`)

### Summary

`Transaction::decode` unconditionally passes `BranchId::Nu6_2` to `ZCashTransaction::read`. For Zcash V5 transactions the consensus branch ID is encoded in the transaction header bytes; the library validates the provided `branch_id` against the one read from the wire. Any deposit transaction created before NU6.2 activation (carrying `BranchId::Nu6` or `BranchId::Nu6_1`) therefore fails to deserialize, causing every call-site that uses `.expect("Deserialization tx_bytes failed")` to panic and permanently blocking the refund path for those deposits.

### Finding Description

`Transaction::decode` hardcodes the branch ID:

```rust
// contracts/satoshi-bridge/src/zcash_utils/transaction.rs, line 53
let branch_id = BranchId::Nu6_2;
let tx = ZCashTransaction::read(&mut cursor, branch_id)?;
``` [1](#0-0) 

The codebase already contains the correct per-height lookup in `Chain::get_branch_id`:

```rust
// contracts/satoshi-bridge/src/network.rs, lines 53-65
pub fn get_branch_id(&self, block_height: u32) -> BranchId {
    ...
    BranchId::Nu6_2 / Nu6_1 / Nu6 depending on height
}
``` [2](#0-1) 

`Transaction::decode` ignores this function entirely.

`WrappedTransaction::decode` is called with `.expect("Deserialization tx_bytes failed")` in two places on the refund path:

1. **`internal_request_refund`** (refund.rs line 161–163) — called synchronously inside the public `request_refund` entry point before the light-client promise is dispatched. [3](#0-2) 

2. **`refund_execution_inputs`** (refund.rs line 269–271) — called inside `execute_refund_callback` to rebuild the outpoint and deposit output. [4](#0-3) 

Both sites panic on a branch-ID mismatch.

`request_refund` is a public, payable function with no `#[trusted_relayer]` at the method level:

```rust
#[allow(clippy::too_many_arguments)]
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn request_refund(...)
``` [5](#0-4) 

The impl-block-level `#[trusted_relayer]` does **not** blanket-restrict all methods in the block — user-facing methods such as `withdraw_rbf` (line 258) and `execute_refund` (line 582) in the same blocks carry no method-level `#[trusted_relayer]` and are clearly public. [6](#0-5) 

### Impact Explanation

Any user whose ZEC deposit transaction was broadcast before NU6.2 activation (block 3 364 600 on mainnet, 4 052 000 on testnet) holds a V5 transaction with `BranchId::Nu6` or `BranchId::Nu6_1` in its header. If that deposit was never finalized via `verify_deposit`, the refund path is the **only** recovery mechanism. Because `Transaction::decode` rejects those bytes, both `request_refund` and `execute_refund_callback` panic, permanently locking the deposited ZEC with no operator-independent recovery path.

The `RefundRequest` comment even acknowledges re-running `execute_refund` "after a consensus branch change" but the stored deposit `tx_bytes` carry the **original** branch ID, which can never be changed retroactively. [7](#0-6) 

### Likelihood Explanation

The NU6.2 activation heights are concrete and already configured in the codebase. Any deposit made before those heights and not yet finalized is affected. The call path is fully public and requires only a NEAR storage deposit. The panic message is deterministic and locally reproducible.

### Recommendation

Replace the hardcoded `BranchId::Nu6_2` in `Transaction::decode` with a height-aware lookup. Because the deposit transaction's block height is available (it is part of the `TxInclusionProof` submitted with `request_refund`), pass it through to `decode` and call `chain.get_branch_id(tx_block_height)`. Alternatively, for decoding a **stored** deposit transaction whose original branch ID is unknown at decode time, try all known branch IDs in order and accept the first that succeeds.

### Proof of Concept

1. Construct a Zcash V5 transparent transaction signed under `BranchId::Nu6` (consensus branch ID `0xC2D6D0B4`).
2. Serialize it to bytes.
3. Call `Transaction::decode(&bytes, &Chain::ZcashMainnet)` — this passes `BranchId::Nu6_2` to `ZCashTransaction::read`; the library reads `0xC2D6D0B4` from the header, finds it does not match `Nu6_2`, and returns an `Err`, causing `.expect("Deserialization tx_bytes failed")` to panic.
4. Call `Transaction::decode` again with `BranchId::Nu6` passed directly — deserialization succeeds, confirming the bytes are valid and the only fault is the hardcoded branch ID.
5. On-chain: submit `request_refund` with those bytes; the call panics at line 163 of `refund.rs`, the refund request is never stored, and the deposited ZEC is permanently unrecoverable. [1](#0-0) [8](#0-7) [9](#0-8)

        let block_height_update = BranchIdUpdateBlockHeight::new(self);
        if block_height_update.nu6_2_update != 0 && block_height >= block_height_update.nu6_2_update
        {

    }
