Audit Report

## Title
`MetadataPayload` for `deployToken` Lacks Chain-ID Binding, Enabling Cross-Chain Signature Replay — (`evm/src/omni-bridge/contracts/OmniBridge.sol`, `near/omni-types/src/lib.rs`, `starknet/src/bridge_types.cairo`, `solana/programs/bridge_token_factory/src/state/message/deploy_token.rs`)

## Summary

The MPC-signed `MetadataPayload` used by `deployToken` across all destination chains contains no chain identifier in the signed data. Because the same `nearBridgeDerivedAddress` (derived from a single MPC key and fixed derivation path `"bridge-1"`) is used across every EVM deployment, a valid `deployToken` signature obtained for one EVM chain can be replayed verbatim on every other EVM chain. This allows an unprivileged attacker to deploy unauthorized bridge token contracts on any EVM chain and subsequently bind those attacker-triggered addresses as the canonical token addresses on NEAR, corrupting all future cross-chain transfers for the affected token on those chains.

## Finding Description

**Root cause — no chain-id in `MetadataPayload`:**

`OmniBridge.sol:142-149` constructs the signed blob as:

```
keccak256( PayloadType::Metadata | borsh(token) | borsh(name) | borsh(symbol) | decimals )
```

No chain identifier is included. The same five-field encoding is confirmed in:
- `near/omni-types/src/lib.rs:696-702` — `MetadataPayload` struct has no `chain_kind` field; `log_metadata_callback` signs `borsh::to_vec(&metadata_payload)` directly.
- `starknet/src/bridge_types.cairo:36-44` — `MetadataPayload.to_borsh()` encodes the same five fields with no chain-id.
- `solana/programs/bridge_token_factory/src/state/message/deploy_token.rs:19-26` — `serialize_for_near()` encodes `IncomingMessageType::Metadata` followed by the four metadata fields, no chain-id.

**Contrast with `finTransfer`:**

`OmniBridge.sol:289-309` encodes `omniBridgeChainId` twice in the signed payload. `starknet/src/bridge_types.cairo:61-84` likewise encodes `chain_id` in both positions. The developers demonstrably applied chain-binding to `finTransfer` but omitted it from `deployToken`.

**Same `nearBridgeDerivedAddress` across all EVM chains:**

`evm/hardhat.config.ts:78-82` shows `nearBridgeDerivedAddress` is derived from `(nearBridgeAccountId, "bridge-1", mpcRootPublicKey)` — a fixed derivation path with no chain-specific component. Every EVM OmniBridge deployment stores the same `nearBridgeDerivedAddress` value. Therefore `ECDSA.recover(hashed, signatureData) == nearBridgeDerivedAddress` passes identically on Ethereum, Arbitrum, Base, Polygon, BNB, HyperEVM, and Abstract.

**Exploit path:**

1. Attacker observes a legitimate `deployToken(signatureData, {token, name, symbol, decimals})` call on Ethereum. The signature and payload are public on-chain.
2. Attacker calls `OmniBridge(Arbitrum).deployToken(signatureData, payload)` with the identical arguments. The `ERR_TOKEN_EXIST` guard (`OmniBridge.sol:155-158`) only checks `isBridgeToken[nearToEthToken[metadata.token]]` on the *local* chain — Arbitrum's mapping is empty, so the check passes. `ECDSA.recover` returns `nearBridgeDerivedAddress` (same hash, same key). An unauthorized bridge token `0xBBB` is deployed and registered in Arbitrum's `nearToEthToken` mapping.
3. The Arbitrum OmniBridge emits a `DeployToken(0xBBB, token, ...)` event. Wormhole guardians attest to this real on-chain event, producing a valid VAA.
4. Attacker calls NEAR's `bind_token` with the Wormhole VAA. `bind_token_callback` (`near/omni-bridge/src/lib.rs:1249-1267`) expects `ProverResult::DeployToken`, verifies the emitter is a registered factory (Arbitrum OmniBridge is registered), and calls `add_token(&deploy_token.token, &deploy_token.token_address, ...)` — registering `0xBBB` as the canonical NEAR→Arbitrum address for the token.
5. The `locked_tokens.insert` guard (`lib.rs:1269-1280`) only prevents double-binding; if the attacker acts before the legitimate relayer, it passes.
6. All subsequent NEAR→Arbitrum `finTransfer` calls resolve the token address to `0xBBB` (attacker-chosen contract). The attacker has achieved unauthorized token address binding for every replayed chain.

**Why existing guards are insufficient:**

- `ERR_TOKEN_EXIST` is per-chain local state; it cannot prevent replay on other chains.
- The `factories` check in `bind_token_callback` only verifies the emitter is a known factory, not that the deployment was legitimately authorized.
- There is no nonce or replay-prevention mechanism in `MetadataPayload`.
- The `locked_tokens.insert` uniqueness check is a race condition the attacker wins by acting first.

## Impact Explanation

This is a **Critical** impact matching two allowed categories:

1. **Token metadata binding confusion that changes user or protocol balances**: The attacker forces NEAR to register an attacker-chosen EVM contract as the canonical bridge token for a given chain. All future `finTransfer` minting on that chain flows into the attacker-controlled contract, permanently misdirecting bridged funds.

2. **Unauthorized transaction / role bypass**: The `deployToken` function is gated by MPC signature verification intended to authorize only NEAR-sanctioned deployments. The replay bypasses this authorization entirely, allowing an unprivileged actor to perform deployer-equivalent actions on any EVM chain using a signature obtained for a different chain.

Additionally, if the attacker replays before the legitimate relayer reaches a given chain, `ERR_TOKEN_EXIST` permanently blocks the legitimate deployment on that chain, constituting permanent freezing of the bridge for that token on that chain.

## Likelihood Explanation

**High.** The attack requires:
1. Reading a public `deployToken` transaction from any EVM chain (zero privilege).
2. Submitting the same calldata to other EVM OmniBridge contracts (permissionless, gas cost only).
3. Obtaining a Wormhole VAA for the resulting on-chain event (permissionless relayer action).

No private keys, admin access, MPC compromise, or victim cooperation is required. Any unprivileged actor — including a competing relayer, a malicious token issuer, or a front-runner — can execute this immediately upon observing the first legitimate `deployToken` transaction.

## Recommendation

Include the destination chain identifier in the `MetadataPayload` signed by the MPC, mirroring the pattern already used in `TransferMessagePayload`/`finTransfer`.

**EVM** (`OmniBridge.sol`):
```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
+   bytes1(omniBridgeChainId),          // bind to this chain
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
```

**NEAR** (`omni-types/src/lib.rs`):
```rust
pub struct MetadataPayload {
    pub prefix: PayloadType,
+   pub chain_kind: ChainKind,   // destination chain
    pub token: String,
    pub name: String,
    pub symbol: String,
    pub decimals: u8,
}
```

Apply the equivalent fix to Starknet's `MetadataPayload.to_borsh()` and Solana's `DeployTokenPayload::serialize_for_near()`. The NEAR `log_metadata_callback` must be updated to accept a `chain_kind` parameter and include it in the signed payload and the MPC sign request.

## Proof of Concept

**Minimal reproducible call sequence (local testnet):**

```
1. Deploy OmniBridge on two local EVM chains (chain A = Ethereum, chain B = Arbitrum),
   both initialized with the same nearBridgeDerivedAddress.

2. Obtain signature S by calling NEAR log_metadata for token "usdc.near"
   → MetadataPayload{prefix, token="usdc.near", name="USD Coin", symbol="USDC", decimals=6}
   → MPC signs keccak256(borsh(payload)) → S

3. Call OmniBridge(chain A).deployToken(S, payload)
   → Succeeds: USDC bridge token deployed at 0xAAA on chain A ✓

4. Call OmniBridge(chain B).deployToken(S, payload)   // identical S and payload
   → ECDSA.recover(keccak256(borsh(payload)), S) == nearBridgeDerivedAddress ✓ (no chain-id in hash)
   → ERR_TOKEN_EXIST check: nearToEthToken["usdc.near"] == address(0) on chain B → passes ✓
   → USDC bridge token deployed at 0xBBB on chain B (unauthorized) ✓
   → DeployToken(0xBBB, "usdc.near", ...) event emitted ✓

5. Construct mock ProverResult::DeployToken with emitter = chain B OmniBridge address,
   token_address = OmniAddress::Eth(0xBBB), token = "usdc.near"
   (In production: obtain real Wormhole VAA for the chain B DeployToken event)

6. Call NEAR bind_token with the proof
   → factories check: chain B OmniBridge is registered factory → passes ✓
   → locked_tokens.insert(("Arbitrum", "usdc.near"), 0) → first insertion, passes ✓
   → add_token("usdc.near", OmniAddress::Eth(0xBBB), ...) → NEAR now maps usdc.near→0xBBB on chain B ✓

7. Verify: NEAR's token_id_to_address lookup for ("Arbitrum", "usdc.near") returns 0xBBB
   → All future finTransfer calls for USDC on chain B will mint into 0xBBB (attacker-chosen contract)
```

The existing NEAR integration test harness in `near/omni-tests/src/helpers.rs:272-292` demonstrates that `deploy_token` and `bind_token` accept mock `ProverResult` values directly, making this sequence straightforwardly reproducible in the sandbox test environment without requiring real Wormhole infrastructure.
