### Title
Missing Cryptographic Signature Check in `validatePerasVote` Allows Forged Votes to Bypass Authorization in `processVotes` — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance's `validatePerasVote` only checks stake-distribution membership but **skips cryptographic signature verification entirely**. This function is the per-item validation callback passed into `processVotes`, the batch inbound-vote handler called from `makePerasVotePoolWriterFromVoteDB` and `makePerasVotePoolWriterFromChainDB`. Any unprivileged peer that knows the public stake distribution can forge votes attributed to any eligible voter, drive the node to reach quorum, and cause it to accept an unauthorized Peras certificate that boosts a non-canonical block in chain selection.

---

### Finding Description

`processVotes` is the batch processing function for inbound Peras votes received over the ObjectDiffusion mini-protocol. It iterates over every vote not already in the database and calls the supplied `validateVote` callback:

```haskell
validationResults <- atomically $ do
  alreadyInDb <- alreadyInDbSTM
  let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
  mapM validateVote votesNotAlreadyInDb
``` [1](#0-0) 

The callback wired in by both production pool-writer constructors is `validatePerasVote mkPerasParams sd`:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [2](#0-1) 

The implementation of `validatePerasVote` in the only `BlockSupportsPeras` instance in the codebase is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [3](#0-2) 

The function checks only whether the claimed voter ID appears in the stake distribution. It **never verifies the vote's cryptographic signature**. Because the stake distribution is public, any peer can construct a `PerasVote` with an arbitrary `pvVoteVoterId` that belongs to a real stakepool and have it accepted as a `ValidatedPerasVote`.

The same structural problem exists for certificates: `validatePerasCert` unconditionally returns `Right` for every certificate, making `processCerts` accept any peer-supplied certificate with no checks at all. [4](#0-3) 

---

### Impact Explanation

Once forged votes pass `validatePerasVote`, they are stored as `ValidatedPerasVote` objects. `implAddVote` in the `PerasVoteDB` then calls `updatePerasRoundVoteStates`, which accumulates vote stake and checks quorum. Because the forged votes carry the real stake of the impersonated pools, an attacker who forges enough votes can push the node past the quorum threshold and trigger `VoteGeneratedNewCert`, causing the node to forge and store a `ValidatedPerasCert` for an attacker-chosen block. That certificate then provides a `perasWeight` boost to the targeted block during Peras chain selection, making the node prefer a non-canonical or adversarially chosen chain over the honest canonical chain.

This matches the allowed impact: **Critical — bypass of Peras voting checks that enables unauthorized vote and certificate acceptance**, and **High — chain-selection manipulation that lets an unprivileged peer make an honest node prefer a non-canonical chain**. [5](#0-4) 

---

### Likelihood Explanation

The attack entry point is the ObjectDiffusion mini-protocol, reachable by any network peer without any credentials. The stake distribution is public on-chain data. An attacker needs only to enumerate eligible voter IDs from the distribution and craft `PerasVote` records with those IDs. No key material, operator access, or stake majority is required. The attack is fully automated and repeatable. [6](#0-5) 

---

### Recommendation

1. **Implement signature verification in `validatePerasVote`**: the function must verify the vote's cryptographic signature against the claimed voter's public key before accepting it as valid. The `VotingCommittee.verifyVote` abstraction already exists for this purpose.
2. **Implement full certificate verification in `validatePerasCert`**: the function must verify the aggregate BLS signature and VRF outputs against the committee's public keys before accepting a certificate.
3. Until real implementations are in place, the ObjectDiffusion pool writers should refuse to accept inbound votes and certificates from remote peers rather than silently accepting them through stub validators. [7](#0-6) 

---

### Proof of Concept

1. Attacker connects to an honest node as a peer via the ObjectDiffusion mini-protocol.
2. Attacker reads the public stake distribution to enumerate eligible voter IDs (e.g., pool key hashes with non-zero stake).
3. Attacker constructs a batch of `PerasVote` objects, each with `pvVoteVoterId` set to a real eligible pool ID, `pvVoteRound` set to the current Peras round, and `pvVoteBlock` set to the attacker's chosen block point.
4. Attacker sends the batch to the node. `makePerasVotePoolWriterFromChainDB`'s `opwAddObjects` calls `processVotes`.
5. `processVotes` calls `validatePerasVote mkPerasParams sd` for each vote. Since only `lookupPerasVoteStake` is checked (no signature), all votes pass.
6. Votes are stored in the `PerasVoteDB`. `updatePerasRoundVoteStates` accumulates their stake; once quorum is reached, `VoteGeneratedNewCert` fires and a `ValidatedPerasCert` boosting the attacker's chosen block is stored.
7. Peras chain selection now assigns extra weight to the attacker's chosen block, causing the honest node to prefer it over the canonical chain tip. [8](#0-7) [9](#0-8)
