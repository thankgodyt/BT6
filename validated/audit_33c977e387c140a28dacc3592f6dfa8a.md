### Title
Unconditional `validatePerasCert` Stub Accepts Any Forged Peras Certificate, Enabling Adversarial Chain-Selection Weight Injection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance used across all block types implements `validatePerasCert` as an unconditional `Right` — it accepts every inbound certificate without any cryptographic or semantic check. An unprivileged peer can send a crafted `PerasCert` naming any block in the local VolatileDB as the boosted block. The certificate passes "validation," is stored in the `PerasCertDB`, and immediately triggers chain selection with a weight boost of `perasWeight params = PerasWeight 15`. If the adversarial chain's total weight (block number + boost) exceeds the honest chain's weight, the node switches to the adversarial chain.

---

### Finding Description

**Root cause — unconditional certificate acceptance:**

In `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs` lines 350–358, the only deployed instance of `validatePerasCert` is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This stub returns `Right` for every input, regardless of the certificate's round number, boosted-block identity, aggregate BLS signature, voter eligibility proofs, or quorum threshold. [1](#0-0) 

**Production inbound path uses this stub:**

`makePerasCertPoolWriterFromChainDB` in `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs` is the production handler for Peras certificates received from peers over the object-diffusion mini-protocol. It passes `validatePerasCert mkPerasParams` directly to `processCerts`:

```haskell
processCerts
  systemTime
  (ChainDB.getPerasCertIds chainDB)
  -- TODO replace when actual plumbing is in place
  (validatePerasCert mkPerasParams)
  (void . ChainDB.addPerasCertAsync chainDB)
  certs
``` [2](#0-1) 

`processCerts` calls `validateCert` on each inbound certificate; if all pass (which they always do), it calls `addCert` — i.e., `ChainDB.addPerasCertAsync` — for each one. [3](#0-2) 

**Chain selection is then triggered with the injected weight:**

`chainSelSync` in `ChainSel.hs` processes the certificate. Its only guards are: (1) the boosted block's slot must be ≥ the immutable tip's slot, and (2) the boosted block must be present in the VolatileDB. If both hold, it calls `chainSelectionForBlock` for the boosted block, which re-runs chain selection using the updated `PerasWeightSnapshot` that now includes the attacker-supplied boost. [4](#0-3) 

`preferAnchoredCandidate` compares chains by `wsvTotalWeight = blockNo + weightBoost`. A boost of `PerasWeight 15` means a fork that is up to 15 blocks shorter than the honest chain can be made to appear heavier. [5](#0-4) 

**Analog to the external report:**

The external report describes `challengeRootL2Block` as a special function that *always wins* the root claim subgame, overriding normal resolution and stealing a bond from an honest challenger. The analog here is `validatePerasCert` acting as a special path that *always succeeds*, overriding normal certificate verification and injecting an illegitimate weight boost into chain selection — exactly the same "unconditional override" pattern.

### Impact Explanation

An unprivileged peer can force an honest node to switch to a non-canonical chain by:

1. Observing a block `B_adv` on an adversarial fork that is present in the target node's VolatileDB (learnable via ChainSync).
2. Sending a crafted `PerasCert { pcCertRound = r, pcCertBoostedBlock = B_adv }` over the object-diffusion mini-protocol.
3. The certificate passes `validatePerasCert` unconditionally, is stored, and triggers chain selection.
4. The adversarial fork gains `PerasWeight 15` extra weight. If the honest chain leads by ≤ 15 blocks, the node switches to the adversarial fork.

This is a **Critical** impact: bypass of Peras certificate validation that enables unauthorized certificate acceptance and causes an honest node to adopt a non-canonical chain, violating chain-selection safety.

---

### Likelihood Explanation

The object-diffusion mini-protocol for Peras certificates is reachable by any connected peer. No stake, key material, or operator privilege is required. The attacker only needs to know a block hash present in the target's VolatileDB, which is observable via the ChainSync protocol. The `PerasWeight 15` default boost is large enough to override a 15-block lead on the honest chain, which is well within normal network variance.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
- The aggregate BLS signature over `(roundNo, boostedBlock)` against the aggregated voter verification keys.
- Voter eligibility proofs (VRF outputs, seat indices, stake).
- Quorum threshold: total voter stake ≥ `perasQuorumStakeThreshold`.
- Round number is within the valid window (not expired, not from the future).

Until the real implementation is in place, the object-diffusion inbound handler for Peras certificates should be disabled or gated behind a feature flag so that no peer-supplied certificate can influence chain selection.

### Proof of Concept

1. Node N has an honest chain of length 100 and an adversarial fork of length 90 in its VolatileDB (the fork was received but not selected because it is shorter).
2. Attacker A connects to N and observes via ChainSync that block `B_adv` at height 90 exists on the fork.
3. A sends a single `PerasCert { pcCertRound = 1, pcCertBoostedBlock = BlockPoint slot (hash B_adv) }` via the object-diffusion protocol.
4. `processCerts` calls `validatePerasCert mkPerasParams cert` → `Right (ValidatedPerasCert { vpcCertBoost = PerasWeight 15 })`.
5. `addPerasCertAsync` enqueues the certificate; `chainSelSync` adds it to `PerasCertDB` and calls `chainSelectionForBlock` for `B_adv`.
6. `preferAnchoredCandidate` computes: honest chain total weight = 100 + 0 = 100; adversarial chain total weight = 90 + 15 = 105. Since 105 > 100, `ShouldSwitch` is returned.
7. N switches to the adversarial fork, rolling back 10 honest blocks. [6](#0-5) [7](#0-6) [8](#0-7) [9](#0-8)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
