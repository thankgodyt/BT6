### Title
`min_withdraw_amount` Validation Incorrectly Applied to `DepositProtocolFee` Path - (File: contracts/satoshi-bridge/src/api/token_receiver.rs)

### Summary

The `ft_on_transfer` entry point enforces `min_withdraw_amount` on every inbound nBTC transfer before the message type is parsed. This means the withdrawal-specific minimum is also applied to `DepositProtocolFee` transfers, which are not withdrawals at all. Any attempt to deposit a protocol fee smaller than `min_withdraw_amount` is unconditionally rejected, even though no minimum amount is semantically required for that path.

### Finding Description

In `ft_on_transfer`, the guard:

```rust
require!(
    amount >= self.internal_config().min_withdraw_amount,
    "Invalid amount"
);
```

is placed **before** the message is deserialized and the branch is selected. [1](#0-0) 

The function then dispatches on two distinct message variants: [2](#0-1) 

- `TokenReceiverMessage::Withdraw` — a user withdrawal; the minimum is appropriate here.
- `TokenReceiverMessage::DepositProtocolFee` — an administrative fee deposit; the minimum is **not** appropriate here.

`min_withdraw_amount` is documented as "The minimum amount allowed for the user to withdraw." [3](#0-2) 

In the deployed/test configuration this is set to **70 000 satoshis** (`min_withdraw_amount: 70000`). [4](#0-3) 

Because the check precedes message parsing, any `ft_transfer_call` carrying a `DepositProtocolFee` payload with `amount < min_withdraw_amount` panics with `"Invalid amount"` and the entire call is reverted. The nBTC is returned to the sender.

This is the direct analog of the reported vulnerability class: a minimum-amount guard is applied to the wrong context (the wrong "direction" of the operation), causing valid operations to be unconditionally rejected.

### Impact Explanation

Any NEAR account that calls `ft_transfer_call` on the nBTC contract targeting the bridge with a `DepositProtocolFee` message and an amount below `min_withdraw_amount` will have the call rejected. Protocol fee accumulation in small increments is blocked. If the bridge's fee-collection design relies on small or incremental protocol-fee deposits, those deposits are permanently stuck at the caller until they batch enough to exceed the withdrawal floor — a publicly reachable stuck-state on a production bridge path.

Severity: **Low** — no direct theft of funds; the nBTC is returned to the sender on revert, but the operation is incorrectly gated and the bridge state cannot be updated as intended.

### Likelihood Explanation

The entry path is fully public: any nBTC holder can call `ft_transfer_call` on the nBTC contract with a `DepositProtocolFee` message. No privileged role is required. The condition triggers deterministically whenever `amount < min_withdraw_amount`, which is a normal scenario for small fee deposits.

### Recommendation

Move the `min_withdraw_amount` guard inside the `Withdraw` branch only, so it does not affect `DepositProtocolFee`:

```rust
match message {
    TokenReceiverMessage::DepositProtocolFee => {
        // No minimum required for fee deposits
        self.data_mut().acc_collected_protocol_fee += amount;
        self.data_mut().cur_available_protocol_fee += amount;
        ...
        PromiseOrValue::Value(U128(0))
    }
    TokenReceiverMessage::Withdraw { ... } => {
        require!(
            amount >= self.internal_config().min_withdraw_amount,
            "Invalid amount"
        );
        self.ft_on_transfer_withdraw_chain_specific(...)
    }
}
```

### Proof of Concept

1. Deploy the bridge with `min_withdraw_amount = 70_000`.
2. As any NEAR account, call `nbtc.ft_transfer_call(bridge_id, "50000", '{"DepositProtocolFee": {}}')`.
3. `ft_on_transfer` is invoked with `amount = 50_000`.
4. The guard `require!(50_000 >= 70_000, "Invalid amount")` panics.
5. The call reverts; the 50 000 nBTC is returned to the sender; `acc_collected_protocol_fee` is not updated.
6. The same call with `amount = 70_001` succeeds, confirming the guard is the sole blocker.
