### Title
Attached NEAR Storage Deposit Permanently Locked on Failed `request_refund_callback` - (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`internal_request_refund` requires callers to attach a NEAR storage deposit before the light-client verification cross-contract call is dispatched. If the subsequent `request_refund_callback` panics for any reason (failed proof, already-verified UTXO, duplicate request), NEAR's async execution model does not refund the original attached deposit — it is permanently locked in the contract with no recovery path.

---

### Finding Description

`internal_request_refund` enforces an attached deposit at the call site: [1](#0-0) 

The deposit is accepted into the contract's balance at this point. The function then dispatches a cross-contract call to the BTC light client and chains `request_refund_callback`: [2](#0-1) 

Inside `request_refund_callback`, multiple `require!` guards can panic:

- Light-client verification returns false (line 509)
- The UTXO is already verified via deposit (lines 535–541)
- A duplicate refund request already exists (lines 544–547) [3](#0-2) 

In NEAR's async execution model, when a callback panics, only the callback's own state mutations are rolled back. The original function's side-effect — the contract receiving the attached NEAR deposit — is **not** reversed. The deposit stays in the contract's balance permanently. No function in the contract allows recovery of these stranded deposits.

This is the NEAR analog of the Solidity `transfer()` anti-pattern: a fund-transfer mechanism (here, the storage deposit flow) that can silently strand user funds with no rollback or recovery path.

---

### Impact Explanation

Every user whose refund request fails validation (invalid proof, race condition with a concurrent deposit verification, or duplicate submission) permanently loses their NEAR storage deposit. The deposit accumulates in the contract balance with no on-chain recovery mechanism. This is a stuck-state fault in a publicly reachable production bridge path.

**Severity: Low** — matches "Publicly reachable invariant-violation, stuck-state, or panic-driven fault in production bridge/token paths without direct theft."

---

### Likelihood Explanation

The failure paths are all reachable by any unprivileged user:

- A user submitting a refund request for a UTXO that was concurrently claimed by a `verify_deposit` call will hit the "UTXO already verified" guard.
- A user submitting a duplicate request (e.g., retrying after a network timeout) will hit the "Refund request already exists" guard.
- A user providing a proof that the light client rejects will hit the `is_valid` guard.

All three paths are realistic in normal bridge operation, making this a medium-likelihood trigger for the stuck-deposit outcome.

---

### Recommendation

Return the attached deposit to the caller when `request_refund_callback` fails. The standard NEAR pattern is to call `Promise::new(env::signer_account_id()).transfer(env::attached_deposit())` inside the callback branch that panics, or to restructure the callback to return the deposit via `PromiseOrValue` rather than panicking. Alternatively, store the depositor's account ID and deposit amount in transient state before the cross-contract call and issue a refund transfer in the failure branch of the callback.

---

### Proof of Concept

1. User A calls `request_refund` (or the public API wrapper) for a UTXO, attaching the required storage deposit.
2. Concurrently, a relayer calls `verify_deposit` for the same UTXO, which succeeds and inserts the key into `verified_deposit_utxo`.
3. `request_refund_callback` executes and hits:
   ```rust
   require!(
       !self.data().verified_deposit_utxo.contains(&utxo_storage_key),
       "UTXO already verified via deposit"
   );
   ``` [4](#0-3) 
4. The callback panics. NEAR rolls back the callback's state mutations but the attached NEAR deposit (already in the contract's balance from step 1) is not returned.
5. User A's NEAR storage deposit is permanently locked in the contract.
