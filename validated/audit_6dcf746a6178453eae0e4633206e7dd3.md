### Title
Stub `validatePerasCert` Always Accepts Any Peer-Supplied Peras Certificate, Enabling Unprivileged Chain-Selection Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance implements `validatePerasCert` as an unconditional stub that returns `Right` for every certificate, performing zero cryptographic or structural checks. Any unprivileged peer can send a crafted `PerasCert` over the object-diffusion mini-protocol; the certificate bypasses all validation, is stored in the `PerasCertDB`, and immediately triggers `chainSelectionForBlock` for the boosted block. This lets an attacker cause an honest node to prefer a non-canonical fork by injecting a certificate that boosts a block on that fork.

---

### Finding Description

**Root cause — unconditional `Right` in `validatePerasCert`:**

The catch-all `instance StandardHash blk => BlockSupportsPeras blk` in `SupportsPeras.hs` provides the only production implementation of `validatePerasCert`. It is an explicit stub:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

No signature, quorum, round-number, boosted-block, or committee-membership check is performed. Every certificate, regardless of content, is accepted. [1](#0-0) 

**Entry path — object-diffusion pool writer:**

`makePerasCertPoolWriterFromChainDB` is the production writer that receives certificates from remote peers. It calls `processCerts` with `validatePerasCert mkPerasParams` as the validation function:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` partitions the batch into valid/invalid using the supplied validator. Because `validatePerasCert` always returns `Right`, the "invalid" partition is always empty and every peer-supplied certificate is accepted and timestamped: [3](#0-2) 

**Chain-selection trigger:**

After acceptance, the certificate is forwarded to `ChainDB.addPerasCertAsync`, which enqueues a `ChainSelAddPerasCert` event. `chainSelSync` processes it: it adds the certificate to the `PerasCertDB` and, if the boosted block is present in the `VolatileDB`, immediately calls `chainSelectionForBlock` for that block:

```haskell
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

The only guard before this call is a slot-age check against the immutable tip — not a cryptographic or committee-membership check. [5](#0-4) 

---

### Impact Explanation

**High — chain-selection manipulation by an unprivileged peer.**

Peras certificates carry a weight boost (`vpcCertBoost = perasWeight params`) that is added to the boosted block's chain during selection. Because `validatePerasCert` never rejects a certificate, an attacker who has already propagated a competing fork block to the target node can send a crafted certificate boosting that block. The node will re-run chain selection with the artificial weight boost and may switch to the attacker's fork, abandoning the canonical chain. This violates the chain-selection security assumption that only legitimately quorum-certified blocks receive a weight boost.

---

### Likelihood Explanation

The object-diffusion mini-protocol is reachable by any peer that can establish a connection to the node. No keys, stake, or privileged access are required. The attacker only needs to (a) have a competing block already in the target node's `VolatileDB` (achievable by normal block propagation) and (b) send a `PerasCert` pointing at that block. The stub is the active production code path — there is no more-specific `BlockSupportsPeras` instance that overrides it for Cardano blocks.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
1. The aggregate BLS/committee signature over `(electionId, candidate)`.
2. That the certificate's round number is consistent with the current epoch and Peras parameters.
3. That the boosted block's slot falls within the valid range for the claimed round.
4. That the signing committee reached the required quorum threshold.

Until the real implementation is in place, the pool writer should refuse all inbound certificates from peers (return a hard error rather than calling the stub), so that the chain-selection weight boost cannot be triggered by unauthenticated input. [6](#0-5) 

---

### Proof of Concept

1. Attacker connects to a target node as a normal peer.
2. Attacker propagates a valid but non-canonical block `B_fork` (slot `s`, hash `h`) to the target node via the normal block-diffusion path. The block lands in the target's `VolatileDB`.
3. Attacker constructs a `PerasCert { pcCertRound = r, pcCertBoostedBlock = BlockPoint s h }` for any round `r` not yet in the target's `PerasCertDB`.
4. Attacker sends this certificate to the target via the object-diffusion mini-protocol.
5. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight mkPerasParams }` unconditionally.
6. The certificate is stored in `PerasCertDB`; `chainSelSync` calls `chainSelectionForBlock` for `B_fork` with the artificial weight boost.
7. If `B_fork`'s boosted weight now exceeds the current selection's weight, the node switches to the attacker's fork.

No cryptographic material, stake, or operator access is required at any step. [7](#0-6) [1](#0-0)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
