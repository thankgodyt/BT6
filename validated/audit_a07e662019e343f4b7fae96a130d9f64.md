Audit Report

## Title
Partial `ft_on_transfer` Rejection Leaves Tokens Permanently Stuck in Bridge, Inflating Deployed-Token Supply — (`near/omni-bridge/src/lib.rs`)

## Summary

`is_refund_required` in `fin_transfer_send_tokens_callback` only triggers a refund/burn when the full transferred amount is rejected (`amount.0 == 0`). When a recipient contract partially accepts tokens (returning `0 < unused < amount` from `ft_on_transfer`), NEP-141's `ft_resolve_transfer` returns the **used** amount (e.g., 500), which is non-zero, so no refund is triggered. The undelivered remainder is permanently stranded in the bridge's own token balance: for deployed (bridge-minted) tokens this inflates circulating supply on NEAR while the source-chain tokens were already fully burned; for native (escrowed) tokens the funds are permanently frozen in the bridge.

## Finding Description

**Promise result semantics:** NEP-141's `ft_resolve_transfer` returns the **used** amount (`amount − unused`). If `ft_on_transfer` returns `unused = 500` out of `amount = 1000`, `ft_resolve_transfer` transfers 500 back to the sender (the bridge) and returns `U128(500)` as the promise result.

**Root cause — binary check in `is_refund_required`:**

```rust
// near/omni-bridge/src/lib.rs L1791
amount.0 == 0   // only triggers refund when ALL tokens were rejected
```

For partial rejection (`used = 500`), `500 == 0` is `false`, so `is_refund_required` returns `false`.

**Exploit flow for deployed tokens:**
1. `send_tokens` calls `mint(malicious.near, 1000, Some("msg"))` on the deployed token contract.
2. Inside `OmniToken::mint` (L135–139), the bridge deposits 1000 tokens to itself, then calls `ft_transfer_call(malicious.near, 1000, None, msg)`.
3. `MaliciousReceiver::ft_on_transfer` returns `500` (unused). `ft_resolve_transfer` returns `U128(500)` to the bridge and emits `used = 500`.
4. `fin_transfer_send_tokens_callback` calls `is_refund_required(true)` → reads `U128(500)` → `500 == 0` → `false`.
5. The `else` branch executes: fees are paid and `FinTransferEvent` is emitted for the full 1000 tokens.
6. The 500 returned tokens sit in the bridge's own balance. No burn is scheduled. No recovery path exists.

**Existing guard is insufficient:** The `else` branch at L1719–1746 unconditionally emits `FinTransferEvent` for the full `transfer_message.amount`, regardless of how many tokens actually reached the recipient.

## Impact Explanation

**Deployed (bridge-minted) tokens:** The bridge mints `amount` tokens but only `used < amount` reach the recipient. The `unused` portion is permanently stranded in the bridge's balance without being burned. The source chain already burned the full `amount`. Result: circulating supply on NEAR exceeds the locked/burned supply on the source chain — direct supply inflation / unauthorized minting equivalent. This matches the Critical impact: *"unauthorized minting… of bridged funds"* and *"balance manipulation, escrow mis-accounting… that changes user or protocol balances."*

**Native (escrowed) tokens:** The bridge transfers `amount` from escrow but `unused` tokens return to the bridge's balance. The `fin_transfer` is marked complete. The bridge's internal locked-token accounting does not credit these returned tokens, so they are permanently unrecoverable — matching *"permanent freezing of bridged funds."*

## Likelihood Explanation

Both required conditions are fully user-controlled with no admin involvement:
1. A non-empty `msg` field in the cross-chain transfer (standard DeFi-integration path, set by the initiator on the source chain).
2. A NEAR recipient contract whose `ft_on_transfer` returns a non-zero unused amount (attacker deploys such a contract trivially).

The relayer finalizes the transfer normally; no relayer compromise is needed. The attack is repeatable and scalable.

## Recommendation

In `fin_transfer_send_tokens_callback`, pass the expected amount into `is_refund_required` and compare the actual used amount against it:

```rust
fn is_refund_required(is_ft_transfer_call: bool, expected: u128) -> bool {
    if is_ft_transfer_call {
        match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
            Ok(value) => {
                if let Ok(used) = near_sdk::serde_json::from_slice::<U128>(&value) {
                    used.0 < expected  // refund/burn if ANY tokens were not delivered
                } else {
                    false
                }
            }
            Err(_) => false,
        }
    } else {
        false
    }
}
```

For partial delivery, burn only the undelivered portion (`expected - used`) for deployed tokens, or emit a recoverable-stuck-funds event for native tokens, and do **not** emit `FinTransferEvent` for the full amount. Consider also emitting a `PartialFinTransferEvent` so the source chain can be informed of the shortfall.

## Proof of Concept

1. Attacker deploys `MaliciousReceiver` on NEAR implementing `ft_on_transfer` that always returns `amount / 2` (half unused).
2. On EVM, attacker calls `OmniBridge.initTransfer(token, 1000, 0, 0, "near:malicious.near", "trigger")` — the non-empty `message` field propagates as `msg`.
3. Relayer submits proof; `fin_transfer` → `process_fin_transfer_to_near` → `send_tokens(token, malicious.near, 1000, "trigger")`.
4. `mint(malicious.near, 1000, Some("trigger"))` mints 1000 tokens to bridge, calls `ft_transfer_call(malicious.near, 1000, ...)`.
5. `MaliciousReceiver::ft_on_transfer` returns `500` (unused). `ft_resolve_transfer` returns 500 to bridge, result = `U128(500)`.
6. `is_refund_required(true)`: `500 != 0` → `false`. Callback emits `FinTransferEvent` for 1000 tokens.
7. EVM: 1000 tokens burned. NEAR: 500 tokens in `malicious.near`, 500 tokens stuck in bridge (not burned). Supply inflated by 500.

**Minimal unit test plan:** Deploy a test token implementing `ft_on_transfer` returning `amount/2`. Call `fin_transfer` with a non-empty `msg` targeting this contract. Assert that after the callback: (a) the bridge's token balance equals `amount/2` (stuck tokens), (b) `FinTransferEvent` was emitted for the full amount, and (c) total supply exceeds locked/burned supply by `amount/2`.
