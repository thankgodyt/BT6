### Title
`checkPreferTheirsOverOurs` Uses `emptyPerasWeightSnapshot` Instead of Actual Peras Weights, Causing Incorrect Peer Disconnection During Chain Selection - (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

When a candidate header is beyond the forecast horizon, the ChainSync client calls `checkPreferTheirsOverOurs` to decide whether to disconnect from the peer or keep waiting. This function evaluates chain preference using a hardcoded `emptyPerasWeightSnapshot` — ignoring all Peras certificate weight boosts — while the actual chain selection in `ChainSel.hs` uses the real `PerasWeightSnapshot` populated from `cdbPerasCertDB`. The inconsistency means the disconnection guard uses a different (weaker) comparison than the final chain selection, directly analogous to the Uniswap `beforeSwap` bug that used a spot price instead of a stable TWAP for a security-critical calculation.

---

### Finding Description

In `checkPreferTheirsOverOurs` (lines 1834–1857 of `Client.hs`), the comparison is:

```haskell
preferAnchoredCandidate
  (configBlock cfg)
  emptyPerasWeightSnapshot   -- ← always ignores Peras certificate boosts
  ourFrag
  theirFrag
``` [1](#0-0) 

The code itself acknowledges this is wrong with an inline TODO:

```haskell

``` [2](#0-1) 

By contrast, the actual chain selection in `ChainSel.hs` and `AnchoredFragment.hs` uses the real `PerasWeightSnapshot` from the `PerasCertDB`, which computes total weight as `blockNo + Peras boost`:

```haskell

  | isEmptyPerasWeightSnapshot weights = ...  -- block-count only
  | otherwise = ...                           -- uses wsvTotalWeight = blockNo + boost
``` [3](#0-2)

### Impact Explanation

When Peras is active, the following chain selection error is reachable:

**Scenario A — Honest peer disconnected incorrectly:**
- The honest network produces chain A: block count = N, Peras boost = B, total weight = N + B.
- An adversary serves chain B: block count = N + 1, Peras boost = 0, total weight = N + 1.
- Chain A is Peras-weight-preferred (N + B > N + 1 when B > 1), but chain B is longer by block count.
- When a header of chain A is beyond the forecast horizon, `checkPreferTheirsOverOurs` compares by block count only: chain A (N) < chain B (N+1) → the node disconnects from the peer serving chain A.
- The node keeps the connection to the adversary serving chain B.
- Eventually the node validates chain B's headers and finds it is NOT preferred by total weight — but it has already disconnected from peers serving the correct chain.

**Scenario B — Adversary keeps node waiting on wrong chain:**
- An adversary serves a chain that is longer by block count but lighter by Peras weight.
- `checkPreferTheirsOverOurs` (using `emptyPerasWeightSnapshot`) says "their chain is preferred" → node keeps waiting for the forecast horizon to advance.
- The node wastes time and resources on a chain it will ultimately reject, while potentially missing the correct Peras-weight-preferred chain.

This is a **chain selection error**: an unprivileged peer can cause an honest node to disconnect from peers serving the canonical (Peras-weight-preferred) chain and/or keep connections to peers serving a non-canonical chain.

---

### Likelihood Explanation

- **Entry path**: Any unprivileged peer can serve headers beyond the forecast horizon. No special keys, stake, or privileges are required to trigger the inconsistency.
- **Condition**: Peras must be active. The CHANGELOG notes "if Peras is disabled (which is the default), there is no observable difference." The vulnerability is latent in the current codebase and will become exploitable when Peras is enabled.
- **Acknowledgment**: The TODO comment in the production code explicitly references the issue (`https://github.com/tweag/cardano-peras/issues/64`), confirming the developers are aware the current check is incorrect. [6](#0-5) 

---

### Recommendation

Replace `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the actual `PerasWeightSnapshot` from the node's `PerasCertDB`. The check must use the same weight comparison as the actual chain selection in `ChainSel.hs` to ensure consistency. Specifically, `checkPreferTheirsOverOurs` should receive the current `PerasWeightSnapshot` (the same one passed to `preferAnchoredCandidate` in `chainSelectionForBlock`) so that the disconnection decision and the final chain selection decision agree on which chain is preferred.

---

### Proof of Concept

The inconsistency is directly visible by comparing the two call sites:

**`checkPreferTheirsOverOurs` (disconnection guard — uses empty weights):**
```haskell
preferAnchoredCandidate
  (configBlock cfg)
  emptyPerasWeightSnapshot   -- ← ignores Peras boosts
  ourFrag
  theirFrag
``` [7](#0-6) 

**`chainSelectionForBlock` (actual chain selection — uses real weights):**
```haskell
preferAnchoredCandidate bcfg weights curChain $ Diff.getSuffix chain
``` [8](#0-7) 

Where `weights` is the real `PerasWeightSnapshot` populated from `cdbPerasCertDB`: [9](#0-8) 

The two comparisons diverge whenever any block on either fragment has a non-zero Peras boost, which is exactly the case when Peras is active and certificates have been issued. A peer serving a chain that is longer by block count but lighter by Peras weight will pass the disconnection guard (keeping the connection alive) while a peer serving the correct Peras-weight-preferred but block-count-shorter chain will be disconnected — the exact inversion of the intended behavior.
