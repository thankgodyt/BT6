### Title
`request_refund` Can Be Frontrun to Redirect or DoS User BTC Refunds - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary

The `request_refund` function is publicly callable by any NEAR account. Its refund-request storage key is derived solely from the BTC transaction ID and output index (`txid@vout`), both of which are publicly observable. An attacker can frontrun a legitimate user's `request_refund` call using the same on-chain proof data but substituting their own BTC address as `refund_address`, either permanently blocking the user's refund (DoS) or redirecting the BTC to the attacker's address (theft).

### Finding Description

`request_refund` is declared in a `#[trusted_relayer]` impl block but carries no individual `#[trusted_relayer]` attribute of its own, making it callable by any NEAR account. [1](#0-0) 

The function accepts a caller-supplied `refund_address`. When `deposit_msg.refund_address` is `None` (the common case), the caller's `refund_address` is stored verbatim with no binding to `env::predecessor_account_id()`. [2](#0-1) 

In the callback, the refund request is keyed by `utxo_storage_key`, which is `format!("{txid}@{vout}")` — a value fully determined by the public BTC transaction: [3](#0-2) 

The duplicate-request guard (`"Refund request already exists for this UTXO"`) means whichever caller lands first wins the slot. A second caller for the same UTXO is permanently rejected until the first request is removed. [4](#0-3) 

The stored `refund_address` is later used verbatim when `execute_refund` builds the Bitcoin output: [5](#0-4) 

### Impact Explanation

**DoS path (Medium):** The attacker frontruns the user's `request_refund` with the same `deposit_msg`, `tx_bytes`, `vout`, and proof, but any `refund_address`. The user's transaction reverts with "Refund request already exists for this UTXO". The user's BTC is stuck until a DAO/Operator manually rejects the fraudulent request. The attacker can repeat this every time the user retries.

**Theft path (Critical):** If the DAO/Operator does not reject the fraudulent request within `unsafe_refund_timelock_sec`, anyone can call `execute_refund`, which builds a Bitcoin transaction paying the attacker's address and submits it for MPC signing. The user's deposited BTC is sent to the attacker. [6](#0-5) 

### Likelihood Explanation

- `request_refund` is publicly callable with no role restriction.
- All inputs needed to frontrun (`tx_bytes`, `vout`, `proof`) are visible in the pending NEAR transaction.
- The attacker's only cost is the non-refundable storage deposit (`required_balance_for_request_refund`), a small deterrent relative to the BTC value at stake.
- The `unsafe_refund_timelock_sec` window is the only on-chain mitigation, and it relies entirely on off-chain operator vigilance.

### Recommendation

Bind the refund request key to the caller's identity. The simplest fix is to include `env::predecessor_account_id()` in the storage key:

```rust
let utxo_storage_key = format!(
    "{}@{}@{}",
    tx_id,
    vout,
    env::predecessor_account_id()
);
```

Alternatively, require that `deposit_msg.refund_address` is always pre-set (non-`None`) so the `refund_address` is committed to before the BTC transaction is broadcast, eliminating the caller-supplied address path entirely.

### Proof of Concept

1. Alice deposits BTC to the address derived from her `deposit_msg` (`recipient_id: alice.near`, `refund_address: None`). The deposit is never finalized via `verify_deposit`.
2. Alice broadcasts `request_refund(deposit_msg, "alice_btc_addr", tx_bytes, 0, proof, None)`.
3. Attacker observes the pending NEAR transaction, extracts `deposit_msg`, `tx_bytes`, `vout=0`, `proof`.
4. Attacker submits `request_refund(deposit_msg, "attacker_btc_addr", tx_bytes, 0, proof, None)` with higher priority.
5. Attacker's callback executes first. `utxo_storage_key = "{txid}@0"` is stored with `refund_address = "attacker_btc_addr"`.
6. Alice's callback executes and panics: `"Refund request already exists for this UTXO"`.
7. After `unsafe_refund_timelock_sec` elapses without operator intervention, attacker calls `execute_refund("{txid}@0", None)`.
8. `finalize_refund_with_psbt` builds a Bitcoin PSBT paying `"attacker_btc_addr"` and queues it for MPC signing.
9. Alice's BTC is sent to the attacker. [7](#0-6)

        )
    }

    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())

            ),

    pub(crate) fn finalize_refund_with_psbt(
        &mut self,
        caller: AccountId,
        mut refund_request: RefundRequest,
        psbt: PsbtWrapper,
        refund_amount: u128,
        utxo_storage_key: String,
    ) {
        let gas_fee = refund_request.gas_fee;
        let refund_address = refund_request.refund_address.clone();

        let deposit_msg = refund_request.deposit_msg();
        let path = get_deposit_path(&deposit_msg);
        let vutxo = VUTXO::Current(UTXO {
            path,
            tx_bytes: refund_request.tx_bytes.0.clone(),
            vout: refund_request.vout,
            balance: u64::try_from(refund_request.amount)
                .unwrap_or_else(|_| env::panic_str("Amount overflow")),
        });

        let psbt_hex = psbt.serialize();
        let btc_pending_id = psbt.get_pending_id();

        if !self.check_account_exists(&caller) {
            self.internal_set_account(&caller, crate::Account::new(&caller));
        }
        self.require_pending_sign_capacity(&caller);

        let btc_pending_info = BTCPendingInfo {
            account_id: caller.clone(),
            btc_pending_id: btc_pending_id.clone(),
            transfer_amount: 0,
            actual_received_amount: refund_amount,
            withdraw_fee: 0,
            gas_fee,
            burn_amount: 0,
            psbt_hex,
            vutxos: vec![vutxo],
            signatures: vec![None; 1],
            tx_bytes_with_sign: None,
            create_time_sec: nano_to_sec(env::block_timestamp()),
            last_sign_time_sec: 0,
            state: PendingInfoState::Refund(OriginalState {
                stage: PendingInfoStage::PendingSign,
                max_gas_fee: gas_fee,
                last_rbf_time_sec: None,
                cancel_rbf_reserved: None,
            }),
        };

        require!(
            self.data_mut()
                .btc_pending_infos
                .insert(btc_pending_id.clone(), btc_pending_info.into())
                .is_none(),
            "pending info already exist"
        );
        self.internal_unwrap_mut_account(&caller)
            .btc_pending_sign_ids
            .insert(btc_pending_id.clone());

        // Mark UTXO as verified to prevent verify_deposit later
        self.data_mut()
            .verified_deposit_utxo
            .insert(utxo_storage_key.clone());

        Event::RefundExecuted {
            utxo_storage_key: utxo_storage_key.clone(),
            amount: refund_request.amount.into(),
            refund_address,
        }
        .emit();

        Event::GenerateBtcPendingInfo {
            account_id: &caller,
            btc_pending_id: &btc_pending_id,
        }
        .emit();

        // Keep the request (so `execute_refund` can be called again to re-create
        // the transaction) but mark it executed; it is removed only when the
        // refund is finalized in `verify_refund_finalize`.
        refund_request.executed = true;
        self.data_mut()
            .refund_requests
            .insert(utxo_storage_key, refund_request.into());
