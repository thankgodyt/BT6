Audit Report

## Title
Decimal Normalization Dust Permanently Locked When Transfer Fee Is Zero - (File: `near/omni-bridge/src/lib.rs`)

## Summary
`normalize_amount` uses floor integer division to convert token amounts from higher-decimal source chains to lower-decimal destination chains. The truncated remainder ("dust") is permanently locked or burned in the NEAR bridge contract whenever a user initiates a transfer with `fee = 0`. When `fee > 0`, dust is correctly recovered by the relayer via `claim_fee`, but no equivalent recovery path exists for the zero-fee case.

## Finding Description

**Root cause — floor division in `normalize_amount`:** [1](#0-0) 

The function divides by `10^diff_decimals` with no rounding or remainder return. The developer-added comment at line 2781 explicitly acknowledges: *"When fee = 0, dust stays locked/burned."*

**Full amount (including dust) is locked/burned in `init_transfer_internal`:** [2](#0-1) 

The entire `transfer_message.amount` — including the sub-unit dust — is burned or locked at this point.

**`sign_transfer` normalizes only the transferred amount, discarding dust:** [3](#0-2) 

Only the floor-divided value is signed and sent to the destination chain.

**When `fee = 0`, `sign_transfer_callback` removes the transfer message immediately with no dust recovery:** [4](#0-3) 

After this removal, no `claim_fee` call follows, so the dust is permanently unrecoverable.

**Contrast: when `fee > 0`, `claim_fee` correctly absorbs dust into the relayer fee:** [5](#0-4) 

`fee = transfer_message.amount.0 - denormalized_amount` captures both the user-specified fee and the normalization remainder. This path is entirely absent for the zero-fee case.

## Impact Explanation

This is a direct, permanent loss of bridged user funds matching the allowed impact class of *"permanent freezing of bridged funds"* and *"escrow mis-accounting, decimal/normalization abuse."* For tokens with large decimal differences (e.g., 24 decimals on NEAR, 6 decimals on EVM), the maximum dust per transfer is `10^18 - 1` native units — nearly 1 full token of value. The dust is either permanently locked in the NEAR bridge escrow (for non-deployed tokens) or burned (for deployed tokens), with no recovery mechanism.

## Likelihood Explanation

`ft_transfer_call` is fully public and permissionless. Any user can set `fee = 0` and transfer a non-round amount, triggering the dust loss. No special role or privilege is required. The condition fires on every transfer where `amount % 10^diff_decimals != 0` and `fee = 0`. The `sign_transfer` function requires a `#[trusted_relayer]`, but this is part of the normal protocol flow and does not prevent the loss — it merely determines when the loss is finalized.

## Recommendation

1. **Round down the transfer amount before locking:** In `init_transfer_internal` (or before), compute `effective_amount = normalize_amount(amount_without_fee) * 10^diff_decimals + fee` and return the remainder (`dust = amount - effective_amount`) to the sender via `ft_transfer`.
2. **Alternatively, reject zero-fee transfers when `origin_decimals != decimals`:** Require `fee > 0` when a decimal difference exists, ensuring dust is always recoverable via `claim_fee`.

## Proof of Concept

**Setup:** Token with `origin_decimals = 24` on NEAR, `decimals = 6` on EVM. `diff_decimals = 18`.

1. User calls `ft_transfer_call` with `amount = 1_999_999_999_999_999_999_000_000` and `fee = 0`.
2. `init_transfer_internal` locks the full `1_999_999_999_999_999_999_000_000` units.
3. `sign_transfer` computes `normalize_amount(1_999_999_999_999_999_999_000_000, {decimals:6, origin_decimals:24})` = `1_999_999_999_999_999_999_000_000 / 10^18` = `1_999_999`.
4. MPC signs payload for `amount = 1_999_999` (6 decimals).
5. `sign_transfer_callback`: `fee.is_zero()` → `remove_transfer_message(transfer_id)`. Transfer message deleted.
6. EVM receives `1_999_999` units (6 decimals).
7. Dust = `1_999_999_999_999_999_999_000_000 - 1_999_999 * 10^18` = `999_000_000_000_000_000` units (≈0.000999 tokens, 24 decimals) remains permanently locked in the NEAR bridge with no recovery path.

A unit test can be written against `normalize_amount` and `sign_transfer_callback` in the NEAR contract test harness to confirm that `locked_balance_before - locked_balance_after < amount_sent` when `fee = 0` and `amount % 10^diff_decimals != 0`.
