### Title
Missing `assert_one_yocto()` on `withdraw_rbf` Allows Function Call Key to Redirect User's BTC Withdrawal — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

The `withdraw_rbf` function in the `satoshi-bridge` contract is publicly callable by any user, accepts an attacker-controlled `output: Vec<TxOut>` that specifies where the replacement Bitcoin transaction sends funds, and lacks both `#[payable]` and `assert_one_yocto()`. This means a website holding a NEAR Function Call key for the bridge contract can call `withdraw_rbf` on behalf of a user — without the user signing with their Full Access key — and supply a malicious output that redirects the user's in-flight BTC withdrawal to an attacker-controlled Bitcoin address.

---

### Finding Description

NEAR's Function Call access keys can only invoke contract methods that do not attach NEAR as a deposit. The standard defense for functions that transfer valuable assets is to require exactly one yoctoNEAR via `assert_one_yocto()`, which forces the caller to use a Full Access key and therefore requires explicit user approval.

`withdraw_rbf` is the user-facing RBF (Replace-By-Fee) entrypoint. It:

- Carries **no role restriction** — any NEAR account can call it.
- Is **not** marked `#[payable]` and calls **no** `assert_one_yocto()`.
- Accepts a caller-supplied `output: Vec<TxOut>` that becomes the outputs of the replacement Bitcoin transaction.
- Derives the acting account from `env::predecessor_account_id()`, so it operates on the caller's own pending withdrawal — exactly the withdrawal a malicious dApp would target. [1](#0-0) 

Compare this with the sibling privileged functions `cancel_withdraw`, `active_utxo_management`, and `active_utxo_management_rbf`, all of which are correctly marked `#[payable]` and call `assert_one_yocto()` before touching Bitcoin outputs: [2](#0-1) [3](#0-2) 

`withdraw_rbf` is the only user-facing function in this file that modifies a pending Bitcoin transaction's outputs without this protection.

---

### Impact Explanation

A successful exploit redirects the user's in-flight BTC withdrawal to an attacker-controlled Bitcoin address. The user loses their native BTC permanently. This matches the **Critical** impact class: *significant theft of user funds* and *chain-signature / PSBT transaction-construction failure that enables unauthorized redirection of bridge-controlled funds*.

---

### Likelihood Explanation

The attack is realistic whenever a user interacts with any dApp that integrates the satoshi-bridge contract and stores a Function Call key for it. The attacker only needs to:

1. Obtain a Function Call key for the `satoshi-bridge` contract (standard dApp sign-in flow).
2. Wait for the victim to initiate a withdrawal (creating a `BTCPendingInfo` entry).
3. Call `withdraw_rbf` with the victim's `btc_pending_verify_id` and a `output` vector pointing to the attacker's Bitcoin address.

No privileged role, leaked key, or operator cooperation is required. The Function Call key is obtained through the normal NEAR dApp sign-in flow.

---

### Recommendation

Apply the same pattern already used by `cancel_withdraw`, `active_utxo_management`, and `active_utxo_management_rbf`:

```rust
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,
    output: Vec<TxOut>,
    chain_specific_data: Option<ChainSpecificData>,
) {
    assert_one_yocto();
    let account_id = env::predecessor_account_id();
    self.require_pending_sign_capacity(&account_id);
    self.withdraw_rbf_chain_specific(
        account_id,
        original_btc_pending_verify_id,
        output,
        chain_specific_data,
    );
}
```

---

### Proof of Concept

1. Victim signs into a dApp that integrates `satoshi-bridge`. The dApp receives a Function Call key permitting calls to `satoshi-bridge` methods (standard NEAR sign-in).
2. Victim calls `ft_transfer_call` on the `nbtc` contract with a `Withdraw` message, creating a `BTCPendingInfo` entry with `btc_pending_id = X` and the victim's intended Bitcoin destination.
3. The malicious dApp — using its stored Function Call key — immediately calls:
   ```
   withdraw_rbf(
       original_btc_pending_verify_id: X,
       output: [TxOut { value: <full_amount>, script_pubkey: <attacker_btc_address> }],
       chain_specific_data: None,
   )
   ```
   Because `withdraw_rbf` is not `#[payable]` and has no `assert_one_yocto()`, the Function Call key is sufficient — no Full Access key approval is needed.
4. The bridge's MPC signing pipeline now signs the replacement PSBT, which pays the attacker's Bitcoin address.
5. The signed transaction is broadcast; the victim's BTC is permanently transferred to the attacker. [1](#0-0)
