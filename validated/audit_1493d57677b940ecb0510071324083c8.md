### Title
Arithmetic Underflow in `check_withdraw_psbt` Blocks Withdrawal Verification When Net Received Amount Falls Below `min_change_amount` — (File: `contracts/satoshi-bridge/src/psbt.rs`)

---

### Summary

In `contracts/satoshi-bridge/src/psbt.rs`, the `check_withdraw_psbt` function computes `min_received_amount` via an unchecked subtraction. With `overflow-checks = true` enforced in `Cargo.toml`, this subtraction panics (arithmetic underflow) whenever the net user-received amount after fees is smaller than `config.min_change_amount`. Because the BTC transaction is already broadcast to the Bitcoin network before `verify_withdraw` is called, a panic here leaves the bridge in a permanently stuck state: the user has received BTC on-chain, but the corresponding nBTC tokens cannot be burned and remain locked in the bridge's balance.

---

### Finding Description

`check_withdraw_psbt` is the core validation function for withdrawal PSBTs. After computing the gas fee and the maximum amount the user can receive, it derives a minimum acceptable received amount:

```rust
// psbt.rs lines 238–243
let gas_fee = total_input_amount - total_output_amount;
// ...
let max_received_amount = amount - withdraw_fee - gas_fee;   // line 242
let min_received_amount = max_received_amount - config.min_change_amount; // line 243
``` [1](#0-0) 

`config.min_change_amount` is the minimum satoshi value a change output must carry (the dust threshold). The subtraction on line 243 is intended to give the relayer a tolerance of up to `min_change_amount` satoshis that can be shaved from the user's output to fund a dust-sized change output. However, if `max_received_amount < config.min_change_amount`, the subtraction wraps below zero on a `u128`, which with `overflow-checks = true` causes an immediate panic instead of a graceful error. [2](#0-1) 

The condition that triggers the panic is:

```
amount - withdraw_fee - gas_fee  <  config.min_change_amount
```

i.e., the user's net payout (after bridge fee and BTC miner fee) is smaller than the configured dust threshold. This is reachable whenever:
- A withdrawal amount is close to `min_withdraw_amount`, **and**
- The miner fee is near `max_btc_gas_fee`, **and**
- `min_withdraw_amount` is not strictly greater than `max_withdraw_fee + max_btc_gas_fee + min_change_amount`.

The bridge does not enforce this compound inequality in `Config::assert_valid`. [3](#0-2) 

The panic occurs inside `check_withdraw_psbt`, which is called by `check_withdraw_psbt_valid`, which is called during `verify_withdraw`. At that point in the withdrawal lifecycle, the BTC transaction has already been signed by Chain Signatures and broadcast to the Bitcoin network (step 4 of the documented flow), but `nbtc.burn` has not yet been called (step 6). [4](#0-3) 

---

### Impact Explanation

When `verify_withdraw` panics, the NEAR transaction reverts. The bridge state is:

- The user's nBTC tokens were transferred to the bridge in step 1 (`ft_transfer_call`) and remain in the bridge's balance — they are not returned to the user automatically.
- The BTC transaction is already confirmed (or pending confirmation) on-chain — the user has received BTC.
- `nbtc.burn` is never called, so the nBTC supply is not reduced to match the BTC that left the bridge.

The result is a permanently inflated nBTC supply relative to the BTC held by the bridge, and nBTC tokens locked in the bridge contract with no automatic recovery path. This matches the **Medium** impact category: broken callback/rollback and stuck bridge state requiring operator intervention.

---

### Likelihood Explanation

**Low.** The panic requires the net user payout (`amount − withdraw_fee − gas_fee`) to be smaller than `min_change_amount`. In a well-tuned deployment where `min_withdraw_amount > max_btc_gas_fee + max_withdraw_fee + min_change_amount`, this cannot occur. However, the contract does not enforce this compound invariant in `Config::assert_valid`, so a misconfigured deployment or a period of unusually high BTC fees (pushing `gas_fee` toward `max_btc_gas_fee`) can make the condition reachable for small withdrawals.

---

### Recommendation

1. **Add a compound invariant check in `Config::assert_valid`** to ensure `min_withdraw_amount > max_btc_gas_fee + max_withdraw_fee + min_change_amount`, preventing the configuration from ever allowing the underflow.

2. **Replace the bare subtraction on line 243 with a checked or saturating variant** and return a proper validation error instead of panicking:

```rust
// Before (panics on underflow):
let min_received_amount = max_received_amount - config.min_change_amount;

// After (graceful error):
let min_received_amount = max_received_amount.saturating_sub(config.min_change_amount);
```

Or, equivalently, guard with an explicit check:

```rust
require!(
    max_received_amount >= config.min_change_amount,
    "Net received amount is below min_change_amount; withdrawal cannot be constructed"
);
let min_received_amount = max_received_amount - config.min_change_amount;
``` [5](#0-4)

### Proof of Concept

**Setup (example config values):**
- `min_withdraw_amount` = 10 000 sat
- `max_btc_gas_fee` = 9 000 sat
- `withdraw_bridge_fee.fee_rate` = 50 bps → fee on 10 000 sat = 50 sat
- `min_change_amount` = 1 000 sat

**Trigger:**
1. User calls `nbtc.ft_transfer_call(bridge, 10_000, WithdrawMsg{...})` — 10 000 nBTC transferred to bridge.
2. Bridge constructs BTC tx; Chain Signatures signs; tx broadcast with miner fee = 9 000 sat.
3. Relayer calls `verify_withdraw(tx_proof, psbt_hex, ...)`.
4. Inside `check_withdraw_psbt`:
   - `gas_fee = 9 000`
   - `withdraw_fee = 50`
   - `max_received_amount = 10_000 − 50 − 9_000 = 950`
   - `min_received_amount = 950 − 1_000` → **u128 underflow → panic**
5. `verify_withdraw` reverts. BTC is on-chain; nBTC tokens remain locked in bridge balance; `burn` is never called. [6](#0-5) [7](#0-6)
