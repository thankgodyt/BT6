## Title
Unvalidated UTXO Output Values Allow Malicious Trusted Relayer to Steal Bridged BTC Funds - (File: `near/omni-bridge/src/btc.rs`)

## Summary
`submit_transfer_to_utxo_chain_connector` in `near/omni-bridge/src/btc.rs` deserializes the relayer-supplied `msg` into a `TokenReceiverMessage::Withdraw` but explicitly discards the `input` and `output` fields with `_` wildcards, forwarding the raw `msg` verbatim to the UTXO connector. No check enforces that the sum of `output` values equals the transfer amount minus the gas fee. A malicious trusted relayer can craft an `output` list that delivers only 1 satoshi to the user while the remainder silently becomes miner fees, permanently destroying the user's bridged nBTC.

## Finding Description
In `submit_transfer_to_utxo_chain_connector`, the relayer-controlled `msg` is deserialized and the `output` field is bound to `_` and never inspected:

```rust
if let TokenReceiverMessage::Withdraw {
    target_btc_address,
    input: _,   // never checked
    output: _,  // never checked
    max_gas_fee,
} = message
``` [1](#0-0) 

The only validations performed are that `target_btc_address` matches the stored recipient and that `max_gas_fee` matches the stored value when present. [2](#0-1) 

The correct transfer amount is computed from on-chain state:

```rust
let amount = U128(transfer.message.amount.0 - transfer.message.fee.fee.0);
``` [3](#0-2) 

The transfer is removed from `pending_transfers` before the cross-contract call, and the raw `msg` (containing the unchecked `output` list) is forwarded verbatim to the connector: [4](#0-3) 

The `TokenReceiverMessage::Withdraw` type confirms `output` is a free-form `Vec<TxOut>` with no on-chain constraints: [5](#0-4) 

The callback `submit_transfer_to_btc_connector_callback` only re-adds the transfer if the connector rejects the tokens (returns `> 0` unused). If the connector accepts all tokens and constructs a Bitcoin transaction with a 1-satoshi output, it returns 0 and the transfer is permanently consumed with no rollback. [6](#0-5) 

There is no assertion anywhere that `sum(output[i].value) + actual_gas_fee == amount`.

## Impact Explanation
This is a concrete instance of **permanent loss of bridged funds** — a Critical allowed impact. The user's nBTC is burned on NEAR (removed from `pending_transfers` before the cross-contract call), but the Bitcoin transaction constructed by the connector from the attacker-supplied `output` list delivers only a trivial amount to the recipient. The remainder of the satoshis becomes miner fees and is unrecoverable. The loss is permanent and proportional to the transfer amount, bounded only by the size of individual withdrawal requests.

## Likelihood Explanation
The trusted relayer role is open to any account: any party can call `apply_for_trusted_relayer`, deposit the required NEAR stake, and after the waiting period elapses, be automatically promoted to trusted relayer status with no DAO approval required. [7](#0-6) 

The staking requirement is a financial deterrent, not a cryptographic guarantee. For large BTC withdrawals, the profit from stealing the bridged funds can far exceed the stake. The attack is repeatable across multiple victims before detection, and the attacker can resign and recover their stake after the attack window closes. [8](#0-7) 

## Recommendation
Before forwarding `msg` to the connector, bind and validate the `output` field instead of discarding it. Specifically, inside the `TokenReceiverMessage::Withdraw` match arm, replace `output: _` with `output`, then assert:

1. `output.iter().map(|o| o.value).sum::<u64>() + actual_gas_fee == amount.0` — total outputs plus gas fee must equal the transfer amount.
2. At least one output's `script_pubkey` corresponds to `target_btc_address` and its `value` equals `amount.0 - actual_gas_fee`.

This ensures the relayer cannot silently redirect satoshis to miner fees.

## Proof of Concept
1. Attacker calls `apply_for_trusted_relayer` with the required NEAR stake and waits for the activation period to elapse.
2. User initiates a NEAR → BTC transfer of 1,000,000 satoshis, paying a 1,000-satoshi bridge fee. The bridge stores `amount = 999,000` in `pending_transfers`.
3. Attacker (now a trusted relayer) calls `submit_transfer_to_utxo_chain_connector` with:
   ```json
   {
     "Withdraw": {
       "target_btc_address": "<user's BTC address>",
       "input": ["<valid UTXO outpoint>"],
       "output": [{"value": 1, "script_pubkey": "<user's scriptPubKey>"}],
       "max_gas_fee": null
     }
   }
   ```
4. The bridge validates `target_btc_address` ✓ and `max_gas_fee` (absent) ✓. It does not check that `output[0].value (1) + gas_fee == 999,000`.
5. `remove_transfer_message` is called at line 84, permanently removing the transfer from state.
6. `ft_transfer_call` sends 999,000 nBTC to the connector with the crafted `msg`.
7. The connector constructs a Bitcoin transaction with a single 1-satoshi output; the remaining 998,999 satoshis become miner fees.
8. The connector accepts all tokens (returns 0 unused), so the callback takes the fee-payment branch and does not roll back.
9. The user receives 1 satoshi on Bitcoin. Their 999,000 nBTC is permanently burned.
