### Title
Publicly Reachable `unimplemented!()` Panic in `data()` / `data_mut()` Freezes All Bridge Operations During Upgrade Window - (File: contracts/satoshi-bridge/src/lib.rs)

### Summary
The `data()` and `data_mut()` accessor methods in `satoshi-bridge` terminate with `unimplemented!()` for every `VersionedContractData` variant except `Current`. Because every public contract method delegates through one of these two accessors, any call to any bridge function while the on-chain state is still in a legacy variant (V0–V5) will panic and abort the transaction. This window exists between the moment new WASM code is deployed and the moment `migrate_state()` completes its receipt, a gap that is observable on-chain and exploitable by any unprivileged account.

### Finding Description
`data()` and `data_mut()` are the sole gateway to `ContractData` for every public method in the contract:

```rust
// contracts/satoshi-bridge/src/lib.rs  lines 234-248
fn data(&self) -> &ContractData {
    match &self.data {
        VersionedContractData::Current(data) => data,
        _ => unimplemented!(),          // panics for V0..V5
    }
}

fn data_mut(&mut self) -> &mut ContractData {
    match &mut self.data {
        VersionedContractData::Current(data) => data,
        _ => unimplemented!(),          // panics for V0..V5
    }
}
```

`migrate_state()` is the only function that converts a legacy variant to `Current`:

```rust
// contracts/satoshi-bridge/src/upgrade.rs  lines 9-21
#[private]
#[init(ignore_state)]
pub fn migrate_state() -> Self {
    let mut contract: Contract = env::state_read().expect("NOT INIT");
    contract.data = match contract.data {
        VersionedContractData::V0(data) => VersionedContractData::Current(data.into()),
        // … V1..V5 …
        VersionedContractData::Current(data) => VersionedContractData::Current(data),
    };
    contract
}
```

In NEAR, deploying new WASM and scheduling the `migrate_state` callback are two separate receipts processed sequentially within the same block. Any transaction submitted by an unprivileged account that lands between those two receipts (i.e., after the new code is live but before `migrate_state` has written `Current` back to state) will hit the `unimplemented!()` arm and panic. The panic aborts the transaction and leaves the contract state unchanged, so the bridge remains in the legacy variant until the migration receipt finally executes.

Affected entry points include every public bridge function: `verify_deposit_v2`, `ft_on_transfer` (withdrawal), `request_refund`, `execute_refund`, `verify_withdraw_v2`, `claim_lost_found`, and all management/RBF methods — all of which call `self.data()` or `self.data_mut()` as their first substantive operation.

### Impact Explanation
During the upgrade window every bridge operation — deposits, withdrawals, refunds, UTXO management — panics and reverts. Any in-flight cross-contract callback (e.g., a `verify_deposit` callback that tries to mint nBTC) also panics, causing the callback to fail and potentially leaving the user's funds in an intermediate state (lost-and-found or stuck pending info) that requires operator intervention to resolve. This matches the **Low** allowed impact: "Publicly reachable invariant-violation, stuck-state, or panic-driven fault in production bridge/token paths without direct theft."

### Likelihood Explanation
The window is narrow (sub-block) but deterministic and observable: the deployment transaction is public on-chain. A monitoring bot can detect the new WASM deployment and immediately submit a cheap read-only or state-mutating call (e.g., `get_version`, `ft_on_transfer`, `claim_lost_found`) in the same block before the migration receipt executes. No special privilege is required.

### Recommendation
Replace the `unimplemented!()` arms with a graceful error that does not panic, for example:

```rust
_ => env::panic_str("Contract state not migrated; call migrate_state first"),
```

This preserves the migration guard semantics while producing a recoverable NEAR transaction failure instead of an unrecoverable Rust panic, and avoids any risk of mid-upgrade stuck state for concurrent callers.

Alternatively, ensure `migrate_state` is called atomically in the same receipt batch as the WASM deployment (i.e., as a `then` callback on `env::deploy_contract`) so no external receipt can interleave.

### Proof of Concept

1. Operator calls `up_deploy_code()` (or equivalent) — new WASM is deployed; on-chain state is still `VersionedContractData::V5(…)`.
2. The `migrate_state` callback receipt is queued but not yet executed.
3. Attacker submits `ft_on_transfer` (withdrawal) or `request_refund` in the same block.
4. The new code runs `self.data_mut()`, matches `VersionedContractData::V5(_)`, hits `_ => unimplemented!()`, and panics.
5. The transaction aborts; if it was a callback carrying user funds (e.g., a mint callback), those funds are left in an intermediate state.
6. All bridge operations remain broken until the `migrate_state` receipt executes. [1](#0-0) [2](#0-1) [3](#0-2)
