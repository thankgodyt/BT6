### Title
Permissionless `request_refund` Allows Any Caller to Hijack Refund Destination and Steal User BTC — (File: `contracts/satoshi-bridge/src/api/bridge.rs`, `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`request_refund` is a fully permissionless function. When a deposit's `DepositMsg` does not contain a pre-authorized `refund_address`, any external account can race the legitimate depositor to call `request_refund` first with an attacker-controlled BTC address. Because the first accepted request permanently locks the `refund_address` for that UTXO, the attacker can subsequently call the equally permissionless `execute_refund` after the timelock and redirect the user's BTC to themselves.

---

### Finding Description

`request_refund` accepts a caller-supplied `refund_address` whenever `deposit_msg.refund_address` is `None`:

```rust
// contracts/satoshi-bridge/src/refund.rs  line 154-159
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [1](#0-0) 

There is no check that the caller is the original depositor or any other authorized party. The function is decorated only with `#[pause]` — no role gate:

```rust
// contracts/satoshi-bridge/src/api/bridge.rs  line 508-518
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn request_refund(
    &mut self,
    deposit_msg: DepositMsg,
    refund_address: String,
    ...
``` [2](#0-1) 

Once the light-client callback succeeds, the request is stored and a duplicate-prevention guard fires for any later caller:

```rust
// contracts/satoshi-bridge/src/refund.rs  line 544-547
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [3](#0-2) 

The `refund_address` stored at this point is whatever the **first caller** supplied. The legitimate depositor's subsequent `request_refund` call is permanently rejected.

`execute_refund` is equally permissionless — no caller check exists:

```rust
// contracts/satoshi-bridge/src/api/bridge.rs  line 580-589
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn execute_refund(
    &mut self,
    utxo_storage_key: String,
    chain_specific_data: Option<ChainSpecificData>,
) -> PromiseOrValue<()> {
    let timelock_sec = self.resolve_execute_refund_timelock(&utxo_storage_key);
    self.internal_execute_refund(utxo_storage_key, timelock_sec, chain_specific_data)
}
``` [4](#0-3) 

After the `unsafe_refund_timelock_sec` elapses, the attacker calls `execute_refund` and `finalize_refund_with_psbt` builds a PSBT paying the attacker's BTC address:

```rust
// contracts/satoshi-bridge/src/refund.rs  line 323-324
let gas_fee = refund_request.gas_fee;
let refund_address = refund_request.refund_address.clone();
``` [5](#0-4) 

The MPC then signs and broadcasts a Bitcoin transaction paying the attacker.

---

### Impact Explanation

The attacker receives the full deposit UTXO value (minus gas fee) at their own BTC address. The legitimate depositor loses their BTC entirely. This is a direct, complete theft of user funds — a **Critical** impact matching "Significant loss or theft of user funds."

---

### Likelihood Explanation

- All Bitcoin/Zcash deposit transactions are publicly visible on-chain. An attacker passively monitors for deposits to bridge-derived addresses where `deposit_msg.refund_address` is `None` (the common case for standard deposits).
- The attacker only needs to submit `request_refund` before the legitimate user does — no special timing or MEV infrastructure is required; a simple monitoring bot suffices.
- The only protocol-level mitigation is `unsafe_refund_timelock_sec`, which gives the DAO a window to call `reject_refund`. However, this depends entirely on the DAO actively monitoring every incoming refund request and correctly identifying fraudulent ones — an operational assumption that is not enforced on-chain.
- The attacker's only cost is the small NEAR storage deposit required by `request_refund`, which is negligible relative to any meaningful BTC deposit.

---

### Recommendation

1. **Bind `request_refund` to the depositor**: Derive the authorized caller from `deposit_msg.near_account_id` (or an equivalent field) and require `env::predecessor_account_id() == deposit_msg.near_account_id`. This ensures only the original depositor can initiate a refund when no `refund_address` is pre-authorized.
2. **Alternatively, require `deposit_msg.refund_address` to always be set**: Enforce that `refund_address` is embedded in the `DepositMsg` at deposit time, making the address immutable and removing the caller-supplied path entirely.
3. **Restrict `execute_refund` to the original requester or privileged roles**: Record `env::predecessor_account_id()` at `request_refund` time and enforce it at `execute_refund` time.

---

### Proof of Concept

1. Alice sends 1 BTC to a bridge deposit address derived from a `DepositMsg` with `refund_address = None`.
2. The deposit fails to finalize (e.g., incorrect `near_account_id`). Alice prepares to call `request_refund` with her own BTC address.
3. Bob (attacker) observes Alice's pending NEAR transaction (or simply monitors the Bitcoin chain for unfinalized bridge deposits) and submits `request_refund` first, passing the same `deposit_msg` and `tx_bytes` but with Bob's BTC address as `refund_address`.
4. Bob's `request_refund_callback` succeeds and stores `RefundRequest { refund_address: Bob's address, ... }`.
5. Alice's `request_refund` call reverts: `"Refund request already exists for this UTXO"`.
6. After `unsafe_refund_timelock_sec` elapses (assuming the DAO does not intervene), Bob calls `execute_refund(utxo_storage_key)`.
7. `finalize_refund_with_psbt` builds a PSBT with output to Bob's BTC address; MPC signs it; the transaction is broadcast.
8. Bob receives Alice's 1 BTC (minus gas fee). Alice's funds are permanently lost.
