### Title
Peras Vote Signature Verification Bypass Enables Unprivileged Peer to Forge Votes and Inflate Stake Toward Unauthorized Certificate — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasVote` function does not verify the cryptographic signature of a vote. It only checks whether the voter ID appears in the stake distribution. An unprivileged peer can send crafted votes bearing any eligible voter ID, causing the node to accept them as valid and accumulate their stake toward quorum, potentially forging a certificate for an attacker-chosen block.

---

### Finding Description

In `SupportsPeras.hs` at lines 363–371, the only `BlockSupportsPeras` instance in the codebase implements `validatePerasVote` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right
        ValidatedPerasVote
          { vpvVote = vote
          , vpvVoteStake = stake
          }
  | otherwise =
      Left PerasValidationErr
```

The `_params` argument is discarded entirely. The function accepts any vote whose `pvVoteVoterId` field appears in the stake distribution, without verifying that the vote was actually signed by the corresponding private key. [1](#0-0) 

This function is the sole validation gate in the inbound vote-processing path. The call chain is:

1. A peer sends a batch of `PerasVote` objects over the network via the object-diffusion mini-protocol.
2. `processVotes` (lines 178–200 of `PerasVote.hs`) reads the current vote-ID set atomically, filters out already-known IDs, then calls `validatePerasVote` for each remaining vote inside the same STM transaction. [2](#0-1) 
3. Because `validatePerasVote` only performs a `Map.lookup` on the stake distribution, any vote whose `pvVoteVoterId` matches a known committee member passes validation and is stamped with that member's full stake.
4. The validated votes are added to the `PerasVoteDB` via `implAddVote`, which deduplicates only by `(roundNo, voterId)`. An attacker can therefore submit one forged vote per committee member per round. [3](#0-2) 
5. `updateTargetVoteTally` accumulates the stake of each accepted vote. Once the total exceeds the quorum threshold, `forgePerasCert` is called and a `ValidatedPerasCert` is produced for the attacker-chosen block. [4](#0-3) 

The analog to the ZeroLocker `merge()` bug is direct: just as `merge()` fails to record `ownershipChange[_to]`, allowing the same stake to be re-used for voting, `validatePerasVote` fails to verify the vote's cryptographic proof of ownership, allowing any peer to claim any committee member's stake for an arbitrary target block.

The `PerasVoteId` is defined as `(pviRoundNo, pviVoterId)` — a pair of round number and voter key hash. [5](#0-4)  Since the key hash is never verified against a signature, an attacker can freely populate this field with any key hash present in the stake distribution.

The production writer used by the node is `makePerasVotePoolWriterFromChainDB`, which passes `validatePerasVote mkPerasParams sd vote` as the validation callback. [6](#0-5) 

---

### Impact Explanation

An unprivileged peer can forge one vote per committee member per round, accumulating their combined stake toward any block of the attacker's choice. If the forged stake exceeds the quorum threshold, the node forges a `ValidatedPerasCert` for that block. This certificate is then used in chain selection to boost the attacker's chain. This constitutes a **critical bypass of Peras voting checks that enables unauthorized certificate acceptance**, matching the allowed impact scope: *"Bypass of … PBFT/Praos/TPraos/Peras voting or certificate checks … that enables unauthorized … vote, or certificate acceptance."*

---

### Likelihood Explanation

Any peer that can establish an object-diffusion connection to the node can exploit this. No key material, stake, or special privilege is required beyond network connectivity. The attack is deterministic and requires only knowledge of the current stake distribution, which is public on-chain data. The `processVotes` function is the live inbound handler for the mini-protocol and is reachable from any connected peer.

---

### Recommendation

Implement proper cryptographic signature verification inside `validatePerasVote`. The function must verify that the vote body is signed by the private key whose public key hashes to `pvVoteVoterId`. Until a real implementation is in place, the degenerate instance should reject all votes unconditionally (return `Left PerasValidationErr` for every input) rather than accept any vote whose voter ID appears in the stake distribution. The existing TODO at [cardano-peras issue #120](https://github.com/tweag/cardano-peras/issues/120) tracks this work and should be treated as a security-critical blocker before the Peras vote-diffusion path is enabled on any network.

### Proof of Concept

```
Attacker connects to a target node via the object-diffusion mini-protocol.

Assume public stake distribution:
  stakeDistr = { V1 → 0.15, V2 → 0.15, V3 → 0.15, V4 → 0.15, V5 → 0.15, V6 → 0.15 }
  quorumThreshold = 0.75

Attacker sends 6 crafted PerasVote objects in one batch:
  PerasVote { pvVoteRound = R, pvVoteBlock = maliciousBlock, pvVoteVoterId = V1 }
  PerasVote { pvVoteRound = R, pvVoteBlock = maliciousBlock, pvVoteVoterId = V2 }
  PerasVote { pvVoteRound = R, pvVoteBlock = maliciousBlock, pvVoteVoterId = V3 }
  PerasVote { pvVoteRound = R, pvVoteBlock = maliciousBlock, pvVoteVoterId = V4 }
  PerasVote { pvVoteRound = R, pvVoteBlock = maliciousBlock, pvVoteVoterId = V5 }
  PerasVote { pvVoteRound = R, pvVoteBlock = maliciousBlock, pvVoteVoterId = V6 }

processVotes:
  - alreadyInDb is empty (first votes for round R)
  - validatePerasVote accepts all 6 (each VoterId is in stakeDistr, no sig check)

updateTargetVoteTally accumulates: 6 × 0.15 = 0.90 > 0.75 (quorum reached)

forgePerasCert is called → ValidatedPerasCert for maliciousBlock is produced.
Chain selection boosts maliciousBlock by perasWeight.
```
