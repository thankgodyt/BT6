Audit Report

## Title
Refunded Tokens Permanently Locked in `HyperliquedBridgeToken` on NEAR-Side Failure — (`evm/src/omni-bridge/contracts/HlBridgeToken.sol`)

## Summary

When a HyperCore user initiates a cross-chain transfer via `coreReceiveWithData` with `ACTION_INIT_TRANSFER`, the `InitTransfer` event records `sender = address(HyperliquedBridgeToken)` rather than the originating user. If the NEAR-side transfer fails and triggers an EVM refund, `finTransfer` mints the refunded tokens back to `address(HyperliquedBridgeToken)` via the 2-arg `mint` path, which does not forward tokens to `_systemAddress`. No withdrawal or rescue function exists, so those tokens are permanently locked. The code itself acknowledges this in a developer comment at lines 104–105.

## Finding Description

**Step 1 — `coreReceiveWithData` ACTION_INIT_TRANSFER branch**

`HlBridgeToken.sol` lines 127–135 move `amount` from `_systemAddress` to `address(this)`, then call `OmniBridge.initTransfer` with `address(this)` as the first argument. Because `coreReceiveWithData` is called by the system address (not the HyperCore user), `msg.sender` inside `OmniBridge.initTransfer` is `address(HyperliquedBridgeToken)`.

**Step 2 — `OmniBridge.initTransfer` burns and emits**

`OmniBridge.sol` line 405 burns from `msg.sender` (= `address(HyperliquedBridgeToken)`). Lines 427–436 emit `InitTransfer` with `sender = msg.sender = address(HyperliquedBridgeToken)`. The originating HyperCore user address (`from`) is never threaded through.

**Step 3 — NEAR-side prover reads `sender` as the refund target**

`near/omni-types/src/evm/events.rs` line 132 parses the `InitTransfer` log and sets `sender: OmniAddress::new_from_evm_address(chain_kind, H160(event.data.sender.into()))`. `near/omni-bridge/src/lib.rs` line 728 stores this as `sender: init_transfer.sender` in the `TransferMessage`. When the NEAR-side delivery fails, the bridge emits `FailedFinTransferEvent` carrying this `TransferMessage`; the MPC relayer uses `sender` as the refund recipient and calls `finTransfer` on EVM with `payload.recipient = address(HyperliquedBridgeToken)`.

**Step 4 — `finTransfer` mints to the token contract via 2-arg `mint`**

`OmniBridge.sol` lines 337–342: because `isBridgeToken[payload.tokenAddress]` is true and `payload.message.length == 0` (refund carries no message), the 2-arg `IBridgeToken.mint(payload.recipient, payload.amount)` is called. `HyperliquedBridgeToken` does **not** override the 2-arg `mint`; it inherits `BridgeToken.mint` (lines 50–52), which simply calls `_mint(beneficiary, amount)` with no subsequent `_update(account, _systemAddress, value)`. Tokens are minted directly to `address(HyperliquedBridgeToken)`.

**Step 5 — No recovery path**

`HyperliquedBridgeToken` has no `withdraw`, `rescue`, or `sweep` function. The `ACTION_TRANSFER` path sources from `_systemAddress`, not `address(this)`. The `ACTION_INIT_TRANSFER` path moves a fresh `amount` from `_systemAddress` to `address(this)` and then burns exactly that `amount`; any pre-existing balance at `address(this)` (the refunded tokens) is never consumed. Tokens minted to `address(HyperliquedBridgeToken)` are irrecoverable.

## Impact Explanation

Every HyperCore-originated `ACTION_INIT_TRANSFER` that fails on the NEAR side results in the refunded amount being permanently frozen inside the token contract. This is a direct, permanent loss of bridged funds matching the Critical scope: **permanent freezing of bridged funds**.

## Likelihood Explanation

NEAR-side delivery failures are routine operational events: unregistered recipient accounts, insufficient storage deposits, or a paused bridge contract. No attacker action is required. Any such failure for a HyperCore-originated `ACTION_INIT_TRANSFER` deterministically triggers the loss. The vulnerability is repeatable for every affected transfer.

## Recommendation

Pass the originating HyperCore user address (`from`) through the call chain so it is recorded as `sender` in `InitTransfer`:

1. Add a `sender` parameter to `IOmniBridgeInitTransfer.initTransfer` (or a separate overload).
2. In `coreReceiveWithData`, pass `from` as the sender instead of `address(this)`.
3. In `OmniBridge.initTransfer`, use the explicit `sender` argument for the event rather than `msg.sender`.

Alternatively, store a `pendingRefund[nonce] = from` mapping in `HyperliquedBridgeToken` before calling `initTransfer`, and implement a `claimRefund` function that transfers tokens from `address(this)` back to the stored originator when a refund arrives.

Additionally, override the 2-arg `mint` in `HyperliquedBridgeToken` to apply the same `_update(account, _systemAddress, value)` logic as the 3-arg override, so that any tokens minted to a HyperCore-bound address are correctly forwarded to `_systemAddress`.

## Proof of Concept

```solidity
// 1. System address calls coreReceiveWithData with ACTION_INIT_TRANSFER
//    from = alice (HyperCore user), amount = 100e18
token.coreReceiveWithData(
    alice,
    bytes32(0), uint32(0),
    100e18, uint64(0),
    abi.encodePacked(uint8(1), abi.encode(uint128(0), "near:bob.near", ""))
);
// InitTransfer emitted: sender = address(token), NOT alice

// 2. Simulate NEAR-side failure: relayer calls finTransfer with recipient = address(token)
bridge.finTransfer(
    validSignature,
    TransferMessagePayload({
        tokenAddress: address(token),
        recipient:    address(token),   // refund target = token contract
        amount:       100e18,
        message:      "",               // empty → 2-arg mint path
        ...
    })
);

// 3. Assert tokens are locked
assert(token.balanceOf(address(token)) == 100e18);
// No function exists to recover them; alice's 100e18 is permanently lost.
```

A local Foundry integration test can reproduce this by: (a) deploying `OmniBridge` and `HyperliquedBridgeToken`, (b) calling `coreReceiveWithData` from the mock system address, (c) calling `finTransfer` with `recipient = address(token)` and empty `message`, and (d) asserting `token.balanceOf(address(token)) == amount` with no callable exit path.
