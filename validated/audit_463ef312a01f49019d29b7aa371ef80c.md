### Summary

`getVotingCommitteeForElection` is a publicly exported production function in the Peras voting-committee layer whose entire body is `error "TODO: implement getVotingCommitteeForElection"`. The module that contains it explicitly exists to validate votes and certificates that arrive from a **previous epoch**. Because the function is unimplemented, any code path that invokes it to look up the correct committee for a cross-epoch election will either crash the node at runtime or, if the call site is simply absent because the function was never wired in, silently skip cross-epoch committee validation entirely — allowing votes or certificates referencing a previous epoch's `ElectionId` to bypass the committee membership and signature checks that `verifyVote` / `verifyCert` depend on.

> "This is needed to support the case of validating an old vote or certificate from a previous epoch arriving too late."

It defines `InterEpochVotingCommittee`, which holds both the current and previous epoch's `VotingCommittee`: [1](#0-0)

Its entire implementation is: [2](#0-1) 

A `grep` across the entire repository confirms the function is **never called** outside of its own definition file. This means the cross-epoch validation path described in the module comment is simply absent from the running system.

The `CryptoSupportsVotingCommittee` typeclass defines `verifyVote` and `verifyCert` as the authoritative checks: [3](#0-2) 

Both require a `VotingCommittee` value to be supplied by the caller. `getVotingCommitteeForElection` is the only mechanism in `AcrossEpochs` to obtain that value for a previous-epoch election. Without it, any vote or certificate whose `ElectionId` belongs to the previous epoch cannot be validated against the correct committee.

---

### Impact Explanation

**Impact: Critical — Bypass of Peras certificate/vote verification checks.**

Two concrete failure modes exist:

1. **Runtime crash (node crash):** If any future or current code path calls `getVotingCommitteeForElection` (e.g., when a late-arriving vote from the previous epoch is processed), Haskell's `error` throws an impure exception that is not caught by the `Either`-based error handling used throughout the committee layer. The node process terminates.

2. **Silent validation bypass:** Because the function is unimplemented and never called, the cross-epoch validation path is entirely absent. A crafted vote or certificate carrying a previous-epoch `ElectionId` cannot be checked against the previous epoch's committee. If the Peras integration wires up vote/certificate ingestion without first implementing this function, such objects will either be accepted without committee membership or signature verification, or the lookup will return `Nothing` (if a caller wraps the `error` in a `catch`), causing the certificate to be silently dropped — both outcomes break the Peras safety invariant that every accepted certificate must be verified against the committee that was active for its election.

The `verifyVote` and `verifyCert` implementations in `EveryoneVotes` and `WFALS` perform full cryptographic checks only when given the correct `VotingCommittee`: [4](#0-3) [5](#0-4) 

Without `getVotingCommitteeForElection` supplying the right committee, those checks are never reached for cross-epoch objects.

---

### Likelihood Explanation

The `AcrossEpochs` module is a production file in the core `ouroboros-consensus` library, exported and compiled into every build. The module comment explicitly documents the cross-epoch validation use-case as a design requirement. As Peras vote/certificate diffusion is integrated (the `ObjectDiffusion` inbound handler already exists in production code), call sites for `getVotingCommitteeForElection` will be added. At that point the `error` stub will either crash nodes on receipt of any previous-epoch vote/certificate, or — if the call site is guarded — silently skip the validation. An unprivileged peer can trigger this by replaying a legitimately-formed vote or certificate from the previous epoch over the `ObjectDiffusion` miniprotocol. [6](#0-5) 

---

### Recommendation

Implement `getVotingCommitteeForElection` to correctly resolve an `ElectionId` to either `currEpochVotingCommittee` or `prevEpochVotingCommittee` based on the epoch embedded in the `ElectionId`. Until the implementation is complete and tested, the function should not be exported, and any call site that would invoke it must be gated behind a feature flag or compile-time guard to prevent the stub from reaching production nodes.
