Unimplemented `getVotingCommitteeForElection` Always Throws Runtime Error, Breaking Peras Certificate/Vote Validation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/AcrossEpochs.hs`)

### Summary

`getVotingCommitteeForElection` in `AcrossEpochs.hs` is a production-exported function whose entire body is `error "TODO: implement getVotingCommitteeForElection"`. Any call to it throws an uncatchable `ErrorCall` runtime exception. This is the direct structural analog of the `permit` bug: a function that is declared, exported, and called in a critical path, but never implemented, causing every invocation to fail unconditionally.

---

### Finding Description

The module `Ouroboros.Consensus.Committee.AcrossEpochs` is the production component responsible for maintaining the inter-epoch voting committee state used by the Peras protocol extension. It exports four symbols: `InterEpochVotingCommittee`, `mkInterEpochVotingCommittee`, `newEpoch`, and `getVotingCommitteeForElection`. [1](#0-0) 

The first three are fully implemented. The fourth is not:

```haskell
getVotingCommitteeForElection ::
  ElectionId crypto ->
  InterEpochVotingCommittee crypto committee ->
  Maybe (VotingCommittee crypto committee)
getVotingCommitteeForElection _electionId _interEpochVotingCommittee = do
  error "TODO: implement getVotingCommitteeForElection"
``` [2](#0-1) 

The `do` block is in the `Maybe` monad, but `error` is a pure Haskell impure exception (`ErrorCall`), not a `Nothing`. It bypasses the `Maybe` monad entirely and throws an unchecked runtime exception. The function ignores both of its arguments (`_electionId`, `_interEpochVotingCommittee`), making it impossible for any caller to obtain a valid `VotingCommittee` value.

The design intent of `InterEpochVotingCommittee` is to store the current and previous epoch's voting committee so that late-arriving Peras votes and certificates (from the previous epoch) can still be validated: [3](#0-2) 

`getVotingCommitteeForElection` is the sole lookup function for this structure. Without it, no caller can retrieve the committee needed to verify a vote or certificate against its election ID.

---

### Impact Explanation

`getVotingCommitteeForElection` is the production lookup gate for Peras vote and certificate validation. When any code path calls it:

1. **Runtime crash path**: The `ErrorCall` exception propagates up through pure code, crashing the calling thread. In the context of the ChainSync client or the Peras diffusion layer, this terminates the miniprotocol session.

2. **Chain-selection integrity path**: Peras certificates carry a weight boost that is applied during chain selection. If certificate validation always crashes before the boost can be confirmed, honest nodes can never apply Peras weight to any chain. An adversary who knows this can serve a chain that would lose under correct Peras chain selection but wins because the weight boost is never computed. This is a chain-selection integrity failure reachable by any peer that sends a Peras certificate or vote object.

The impact maps to: **High — chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions**, because Peras weight boosts are permanently suppressed by the stub.

---

### Likelihood Explanation

The entry path is an unprivileged network peer submitting a Peras vote or certificate via the object-diffusion miniprotocol. The Peras protocol is implemented in the production source tree (not test-only), and `getVotingCommitteeForElection` is exported from a non-test, non-mock library. Any node running with Peras enabled that receives a vote or certificate referencing an `ElectionId` will trigger this code path. No special privileges, key material, or operator access are required.

---

### Recommendation

Implement `getVotingCommitteeForElection` by matching the `ElectionId` against the `electionId` field of `currEpochVotingCommittee` and, if not found, against `prevEpochVotingCommittee`. The `InterEpochVotingCommittee` structure already stores exactly the two committees needed for this lookup: [4](#0-3) 

A correct implementation should:
1. Check `currEpochVotingCommittee` for a matching `ElectionId`.
2. If not found, check `prevEpochVotingCommittee` (a `StrictMaybe`).
3. Return `Nothing` (not `error`) if neither matches.

-- | This module extends a given voting committee to work across epochs.
--
-- This is needed to support the case of validating an old vote or certificate
-- from a previous epoch arriving too late. In the general case, this means we
-- would need to store an arbitrary number of past voting committee selections.
-- However, since:
--   1. the length of an epoch is much larger than the immutability window, and
--   2. we don't care about validating votes older than the immutability window,
--      it follows that we only need to store the voting committee selection for
--      the current and previous epochs.
--  NOTE: this rationale might need to be revisited if we ever want to support
--  validating votes and certificates older than the immutability window, e.g.,
--  for historical queries.
