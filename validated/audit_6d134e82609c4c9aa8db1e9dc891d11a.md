### Title
Any NEAR Account Can Front-Run `request_refund` to Redirect BTC/ZEC Refunds to an Attacker-Controlled Address — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

When a user's `DepositMsg` has `refund_address: None`, any NEAR account can call `request_refund` before the legitimate user and inject an attacker-controlled BTC/ZEC address as the `refund_address`. The `refund_requests` map is keyed only by `utxo_storage_key` (`{tx_id}@{vout}`) — the caller's identity is not part of the key. The first caller wins and permanently sets the destination address; a duplicate-check blocks all subsequent requests for the same UTXO.

---

### Finding Description

`request_refund` carries no caller-identity restriction beyond an attached-deposit anti-spam fee:

```rust
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn request_refund(
    &mut self,
    deposit_msg: DepositMsg,
    refund_address: String,   // ← caller-supplied, unchecked when deposit_msg.refund_address is None
    tx_bytes: Base64VecU8,
    vout: usize,
    proof: TxInclusionProof,
    gas_fee: Option<U128>,
) -> Promise {
``` [1](#0-0) 

Inside `internal_request_refund`, the only guard on `refund_address` is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [2](#0-1) 

When `deposit_msg.refund_address` is `None` this block is skipped entirely, so any caller may supply any BTC/ZEC address. The callback then stores the request keyed only on `utxo_storage_key`:

```rust
self.data_mut()
    .refund_requests
    .insert(utxo_storage_key, refund_request.into());
``` [3](#0-2) 

A subsequent call for the same UTXO is rejected:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [4](#0-3) 

So the first caller permanently owns the stored `refund_address`. The legitimate depositor cannot override it.

After `unsafe_refund_timelock_sec` elapses, `execute_refund` is also callable by anyone:

```rust
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn execute_refund(
    &mut self,
    utxo_storage_key: String,
    chain_specific_data: Option<ChainSpecificData>,
) -> PromiseOrValue<()> {
``` [5](#0-4) 

The refund PSBT is built using `refund_request.refund_address` — the attacker-controlled address stored at request time — and the MPC signs a transaction paying that address. [6](#0-5) 

---

### Impact Explanation

An attacker who front-runs `request_refund` for a deposit whose `DepositMsg.refund_address` is `None` causes the bridge's MPC to sign a Bitcoin/Zcash transaction that pays the attacker's address. The legitimate depositor receives nothing. This constitutes theft of user funds locked in the bridge.

If the DAO/Operator is online and monitoring, they can reject the malicious request during `unsafe_refund_timelock_sec`, restoring the UTXO to an unencumbered state. However, the attacker can immediately re-submit another front-run request, creating an indefinite griefing loop that permanently locks the depositor's BTC/ZEC in the bridge until the DAO/Operator intervenes every single time.

---

### Likelihood Explanation

All inputs to `request_refund` are public:
- `deposit_msg` — derivable from the NEAR recipient account ID (public) and the deposit address observed on-chain.
- `tx_bytes`, `vout`, `proof` — all on the Bitcoin/Zcash blockchain.

The attacker only needs to observe the BTC/ZEC chain for deposits to bridge-controlled addresses and race the legitimate user to NEAR. The attached-deposit anti-spam fee is a minor cost relative to the value of a typical BTC deposit. The attack is realistic for any deposit where the user did not pre-authorize a `refund_address` in their `DepositMsg`.

---

### Recommendation

Include the caller's NEAR account ID as part of the `refund_requests` key, or restrict `request_refund` so that only the `deposit_msg.recipient_id` (or a pre-authorized address) may submit a refund request for a given UTXO. Alternatively, require that when `deposit_msg.refund_address` is `None`, the caller must prove ownership of the deposit address (e.g., via a signed message), preventing arbitrary third parties from injecting a malicious destination.

---

### Proof of Concept

1. Alice deposits 1 BTC to the bridge with `DepositMsg { recipient_id: "alice.near", refund_address: None, ... }`. The relayer never calls `verify_deposit`.
2. Bob observes the BTC transaction on-chain and derives Alice's `deposit_msg` from her public NEAR account ID.
3. Bob calls `request_refund(alice_deposit_msg, bob_btc_address, tx_bytes, vout, proof, None)` with the required attached deposit. The callback verifies the script_pubkey matches the deposit address (it does — Bob used the correct `deposit_msg`), and stores `RefundRequest { refund_address: bob_btc_address, ... }` under `utxo_storage_key`.
4. Alice calls `request_refund(...)` — rejected: `"Refund request already exists for this UTXO"`.
5. After `unsafe_refund_timelock_sec` elapses (if DAO/Operator does not reject), Bob calls `execute_refund(utxo_storage_key, None)`. The bridge builds a PSBT paying `bob_btc_address` and requests an MPC signature.
6. The MPC signs; Bob broadcasts the transaction. Alice's 1 BTC is sent to Bob.
