### Title
Peras Certificate Validation Bypass Allows Any Peer to Inject Arbitrary Chain-Weight Boosts - (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance's `validatePerasCert` function unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or semantic validation. This function is wired directly into the production node-to-node Peras certificate diffusion inbound handler. Any unprivileged peer can send a crafted `PerasCert` pointing to an adversarial block, have it accepted as `ValidatedPerasCert`, stored in the `PerasCertDB`, and have its weight boost applied during chain selection — potentially causing an honest node to prefer a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the function responsible for validating Peras certificates received from peers before they are stored and used in chain selection. The only instance of this class — a universal instance covering all `StandardHash blk` blocks — unconditionally accepts every certificate:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This is the **only** instance, declared as `instance StandardHash blk => BlockSupportsPeras blk`, meaning it applies to all block types in production. [2](#0-1) 

This stub is called in the production inbound certificate processing path. `makePerasCertPoolWriterFromChainDB` passes `(validatePerasCert mkPerasParams)` as the validation function to `processCerts`: [3](#0-2) 

`processCerts` calls `validateCert` on each inbound certificate and adds all that return `Right` to the database: [4](#0-3) 

`makePerasCertPoolWriterFromChainDB` is wired directly into the production node-to-node diffusion handler in `NodeToNode.hs`: [5](#0-4) 

Accepted certificates are stored in `PerasCertDB`. The `getWeightSnapshot` field of `PerasCertDB` returns a `PerasWeightSnapshot` that includes the weight boost from every stored certificate. This snapshot is passed directly into `initialChainSelection` and `chainSelection` in `ChainSel.hs`: [6](#0-5) 

Chain selection uses this snapshot via `preferAnchoredCandidate`, which computes `wsvTotalWeight` as the sum of block number and the Peras weight boost: [7](#0-6) 

The rollback limit check `forksAtMostKWeight` also uses the weight snapshot, meaning an injected certificate boost can affect whether a deep fork is considered within the rollback limit: [8](#0-7) 

---

### Impact Explanation

An unprivileged peer can inject a `PerasCert` with `pcCertBoostedBlock` pointing to any block — including a block on an adversarial fork. Because `validatePerasCert` performs no validation (no signature check, no quorum check, no committee eligibility check, no round validity check), the certificate is unconditionally accepted and stored. Its weight boost is then applied during chain selection, causing the honest node to prefer the adversarial chain over the canonical chain. This is a chain selection safety failure: an unprivileged peer can make an honest node prefer a non-canonical chain beyond the intended security assumptions of Ouroboros Praos/Peras.

---

### Likelihood Explanation

The Peras certificate diffusion mini-protocol is active in the production node-to-node handler (`NodeToNode.hs`). Any peer that connects and negotiates the Peras cert diffusion protocol can send crafted certificates. No keys, stake, or special privileges are required. The attack requires only a network connection to a target node.

---

### Recommendation

Implement actual cryptographic and semantic validation inside `validatePerasCert`. At minimum, the implementation must:

1. Verify the aggregate signature over the certificate using the committee's verification keys.
2. Verify that the signers constitute a valid quorum of the committee for the claimed round.
3. Verify that `pcCertBoostedBlock` refers to a block that actually exists on a known chain.
4. Verify that `pcCertRound` is within a valid range relative to the current chain tip.

Until this is implemented, the Peras certificate diffusion inbound handler should either be disabled or should reject all inbound certificates rather than accepting them unconditionally.

---

### Proof of Concept

**Attacker-controlled entry path:**

1. Adversarial peer connects to an honest node and negotiates the Peras certificate diffusion mini-protocol (handled by `hPerasCertDiffusionClient` in `NodeToNode.hs`).
2. Peer sends a `PerasCert` with `pcCertBoostedBlock = <point on adversarial fork>` and `pcCertRound = <any round number not yet in DB>`.
3. `makePerasCertPoolWriterFromChainDB` calls `processCerts` with `validatePerasCert mkPerasParams` as the validator.
4. `validatePerasCert` returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })` unconditionally.
5. The certificate is stored in `PerasCertDB` via `ChainDB.addPerasCertAsync`.
6. On the next chain selection event, `getWeightSnapshot` returns a snapshot that includes the adversarial certificate's boost.
7. `preferAnchoredCandidate` computes `wsvTotalWeight` for the adversarial chain as `blockNo + perasWeight`, which may exceed the honest chain's weight, causing the node to switch to the adversarial fork.

**Root cause (single line):** [9](#0-8) 

The function returns `Right` for every input without inspecting the certificate's content, signatures, or quorum — the exact analog of the `multiHopBuyCollateral` function that checks `collateralAmount` allowance but skips the `borrowAmount` allowance check entirely.
