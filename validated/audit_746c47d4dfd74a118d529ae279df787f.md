### Title
`checkPreferTheirsOverOurs` Uses `emptyPerasWeightSnapshot` Instead of Actual Peras Weights, Bypassing Peras-Weighted Chain Preference Check — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

The `checkPreferTheirsOverOurs` guard in the ChainSync client is responsible for disconnecting from a peer whose candidate chain is no longer preferable to the node's current chain when a header is beyond the forecast horizon. However, it evaluates chain preference using a hardcoded `emptyPerasWeightSnapshot` instead of the actual live Peras weight snapshot. This is structurally identical to the ENS bug: a protection check uses a wrong/empty secondary state as a proxy, causing the protection to be bypassed when Peras boosts are present. When Peras is active, a candidate chain that is heavier by Peras weight but shorter by block count will be incorrectly judged as non-preferable, causing the node to disconnect from a peer offering the legitimately heavier (canonical) chain.

---

### Finding Description

**Root cause:**

In `readLedgerStateHelper`, when `prj lst` returns `Nothing` (the ledger view cannot be forecast because the header is beyond the forecast horizon), the code calls `checkPreferTheirsOverOurs` before retrying. This guard is meant to disconnect from peers whose candidate chain is no longer worth waiting for. [1](#0-0) 

The guard calls `preferAnchoredCandidate` with a hardcoded `emptyPerasWeightSnapshot`:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        emptyPerasWeightSnapshot   -- ← hardcoded empty, ignores all Peras boosts
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
```

The `preferAnchoredCandidate` function branches on whether the weight snapshot is empty: [2](#0-1) 

When `isEmptyPerasWeightSnapshot weights` is `True` (which it always is here, because `emptyPerasWeightSnapshot = PerasWeightSnapshot Map.empty`), the function falls into the block-count-only comparison path, completely ignoring Peras weight boosts. The Peras-aware path (lines 204–213) is never reached. [3](#0-2) 

**Contrast with the actual chain selection path**, which correctly passes the live `weights` snapshot: [4](#0-3) 

The `checkPreferTheirsOverOurs` guard is the only call site that substitutes `emptyPerasWeightSnapshot` for the real snapshot. The code even carries a TODO acknowledging this is wrong: [5](#0-4) 

**Exploit path:**

1. Peras is active; the network has issued certificates boosting blocks on the canonical chain, making it heavier by Peras weight but shorter by raw block count than a competing fork.
2. An adversarial peer (or a set of peers performing an eclipse) has fed the victim node a longer-by-block-count but lighter-by-Peras-weight fork.
3. The victim node receives a header from an honest peer that is beyond the forecast horizon (e.g., a large slot gap). `readLedgerStateHelper` calls `checkPreferTheirsOverOurs`.
4. Because `emptyPerasWeightSnapshot` is used, the comparison reduces to block count only. The victim's current (adversarial) chain has more blocks → `shouldSwitch` returns `ShouldNotSwitch` → `throwSTM CandidateTooSparse` → the honest peer is disconnected.
5. The victim node remains on the lighter, non-canonical fork and never adopts the canonical chain.

---

### Impact Explanation

This is a **High** chain-selection bug. When Peras is active, an unprivileged peer can cause an honest node to disconnect from peers offering the canonical (Peras-heavier) chain by first feeding it a longer-by-block-count but lighter-by-Peras-weight fork. The node then incorrectly evaluates the canonical chain as non-preferable and severs the connection. The node is left on a non-canonical chain, violating the Peras chain-selection invariant. This matches the allowed impact category: *"Chain selection, rollback, forecast, genesis, or header-state bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

---

### Likelihood Explanation

Peras is an in-development protocol in this codebase. Once Peras certificates are issued on mainnet, any scenario where the canonical chain has Peras boosts but fewer raw blocks than a competing fork (a normal occurrence during Peras operation) creates the precondition. An adversarial peer needs only to (a) be a peer of the victim, (b) have previously provided a longer-by-block-count fork, and (c) wait for the victim to receive a header beyond the forecast horizon from an honest peer. No privileged keys or stake majority are required.

---

### Recommendation

Replace `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the actual live `PerasWeightSnapshot` read from the ChainDB (the same snapshot used in `chainSelectionForBlock`). Alternatively, remove the check entirely as the linked TODO (`https://github.com/tweag/cardano-peras/issues/64`) suggests, since the check is acknowledged as a temporary measure.

---

### Proof of Concept

```
Setup (Peras active, weight boost = 5 per certificate):

  Victim's current chain (adversarial fork):
    Genesis → B1 → B2 → B3 → B4 → B5 → B6 → B7 → B8 → B9 → B10
    Block count = 10, Peras weight = 10 (no boosts)

  Canonical chain (honest peer):
    Genesis → B1 → B2 → B3 → B4 → B5 → B6 → B7 → B8 → B9'
    Block count = 9, Peras weight = 9 + 5 (cert on B9') = 14

  B9' is beyond the forecast horizon from the victim's current ledger state.

Step 1: Victim receives header for B9' from honest peer.
Step 2: `readLedgerStateHelper` cannot forecast the ledger view → calls `checkPreferTheirsOverOurs`.
Step 3: `preferAnchoredCandidate cfg emptyPerasWeightSnapshot ourFrag theirFrag`
        → block count comparison: 10 > 9 → ShouldNotSwitch
Step 4: `throwSTM CandidateTooSparse` → honest peer disconnected.
Step 5: Victim remains on the 10-block adversarial fork (weight 10) instead of
        adopting the 9-block canonical chain (weight 14).
```
