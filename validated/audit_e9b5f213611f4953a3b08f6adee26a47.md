### Title
Stub `validatePerasCert` Unconditionally Accepts All Peras Certificates, Enabling Unprivileged Chain-Selection Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `validatePerasCert` implementation is a placeholder that returns `Right` for every inbound certificate without performing any cryptographic or protocol validation. When Peras is enabled, any peer can inject crafted certificates that boost arbitrary blocks on attacker-controlled forks. Because the same block point can be boosted by multiple certificates (one per round), an attacker can accumulate unbounded weight on a fork and cause an honest node to abandon the canonical chain.

---

### Finding Description

The `BlockSupportsPeras` typeclass declares `validatePerasCert` as the mandatory gate for certificate acceptance. The only production instance — explicitly labelled a "degenerate instance for all blks" pending real plumbing — unconditionally returns `Right`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No BLS aggregate-signature check, no committee-membership proof, no quorum-threshold verification, and no round-number sanity check is performed. The `PerasValidationErr` data type itself is a stub with a single constructor carrying no information: [2](#0-1) 

This stub is wired directly into the production peer-facing certificate ingestion path. `makePerasCertPoolWriterFromChainDB` — the writer used when receiving certificates from remote peers via the object-diffusion mini-protocol — calls `validatePerasCert mkPerasParams` as its sole validation step:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [3](#0-2) 

`processCerts` then timestamps and forwards every certificate that passes this non-check to `ChainDB.addPerasCertAsync`: [4](#0-3) 

`chainSelSync` for `ChainSelAddPerasCert` adds the certificate to the `PerasCertDB` and immediately triggers `chainSelectionForBlock` for the boosted block: [5](#0-4) 

Chain selection then computes the `WeightedSelectView` for each candidate fragment. The total weight is `blockNo + weightBoost`, where `weightBoost` is the sum of all `PerasWeight` values for every boosted point on the fragment: [6](#0-5) 

The `PerasCertDB` deduplicates by `PerasRoundNo` (one certificate per round), but the glossary explicitly states: **"the same point can be boosted multiple times."** An attacker can send certificates for N distinct round numbers, all with `pcCertBoostedBlock` pointing to the same block on a fork. `weightBoostOfFragment` sums all boosts across all points on the fragment: [7](#0-6) 

With `perasWeight = PerasWeight 15` (from `mkPerasParams`), sending 145 crafted certificates for distinct rounds all boosting the same fork block yields a weight boost of 2175, exceeding the security parameter `k = 2160`. The fork then outweighs the honest chain regardless of block count.

The `PerasCertDB.implAddCert` itself also carries a TODO noting that non-trivial validation logic is still missing: [8](#0-7) 

---

### Impact Explanation

**High.** An unprivileged peer can cause an honest node to prefer a non-canonical, attacker-controlled fork by injecting crafted Peras certificates that accumulate arbitrary weight boosts, directly violating the chain-selection security assumptions of Ouroboros Praos/Peras. The node will roll back up to `k` blocks and adopt the attacker's chain, constituting a chain-selection safety failure reachable from the network layer without any key material or stake.

---

### Likelihood Explanation

**Medium.** Peras is disabled by default (`"Note that if Peras is disabled (which is the default), there is no observable difference"`), but the full code path — object-diffusion protocol, certificate ingestion, `PerasCertDB`, and weight-aware chain selection — is already wired into production. The attack requires only that Peras be enabled (the intended future state) and that the attacker be able to connect as a peer, which is the normal operating condition for any public Cardano node.

---

### Recommendation

1. **Replace the stub** `validatePerasCert` with a real implementation that verifies the BLS aggregate signature over `(pcCertRound, pcCertBoostedBlock)`, checks committee-membership eligibility proofs for each voter, and confirms the quorum-stake threshold is met before returning `Right`.
2. **Bound per-point weight accumulation** in `weightBoostOfFragment` or `mkPerasWeightSnapshot` so that a single block point cannot receive more than one certificate's worth of boost (one certificate per round is already enforced by the DB, but the weight snapshot should enforce the same invariant).
3. **Add a round-number validity check** in `chainSelSync` (or `processCerts`) to reject certificates whose round number is implausibly far in the future relative to the current slot, mirroring the "not stale" recommendation in the external report.

---

### Proof of Concept

1. Enable Peras on a private testnet node.
2. Connect to the target node as a peer via the object-diffusion mini-protocol for Peras certificates.
3. Construct N `PerasCert` values, each with a distinct `pcCertRound ∈ {0, 1, …, N−1}` and `pcCertBoostedBlock` pointing to a block on an attacker-controlled fork `F` that is one block shorter than the honest chain.
4. Send all N certificates. Each passes `validatePerasCert` (returns `Right` unconditionally) and is stored in the `PerasCertDB`.
5. Each certificate triggers `chainSelectionForBlock` for the boosted block on `F`.
6. After all N certificates are processed, `weightBoostOfFragment` for `F` returns `N × 15`. With `N = 145`, the fork's total weight exceeds the honest chain's total weight by `2175 − 2160 = 15`.
7. The node switches to fork `F`, rolling back up to `k` honest blocks.

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
