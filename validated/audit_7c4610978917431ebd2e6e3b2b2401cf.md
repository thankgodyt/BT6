### Title
Stub `validatePerasCert` Unconditionally Accepts All Inbound Peras Certificates, Enabling Unprivileged Peers to Inject Fake Certificates and Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` function is a stub that unconditionally returns `Right` for every input, bypassing all quorum and signature checks. Any unprivileged peer can send a crafted `PerasCert` naming an arbitrary round and an arbitrary boosted block. The certificate passes the inbound validation gate in `processCerts`, is stored in the `PerasCertDB`, and triggers `chainSelectionForBlock` for the attacker-chosen block, potentially causing the node to prefer a non-canonical chain.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub in production code**

`BlockSupportsPeras` declares `validatePerasCert` as the mandatory gate for accepting inbound Peras certificates. The only concrete instance — the one used for all block types in production — is explicitly labelled a "degenerate instance" and always succeeds:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

No signature, no quorum membership check, no round-range check — every certificate is unconditionally promoted to `ValidatedPerasCert` with full boost weight.

**Inbound processing path — `processCerts` calls the stub**

`processCerts` in the Peras certificate miniprotocol pool handler reads the current DB state once atomically, filters out already-known rounds, then calls `validateCert` (bound to `validatePerasCert mkPerasParams`) on each remaining certificate:

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb =
        filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _) ->
      throw (PerasCertValidationError errs)
``` [2](#0-1) 

Because `validatePerasCert` always returns `Right`, `partitionEithers` always produces an empty error list, and every peer-supplied certificate is forwarded to `addCert`.

Both the production `ChainDB`-backed writer and the `PerasCertDB`-backed writer use this path: [3](#0-2) 

**Chain selection consequence — fake cert triggers `chainSelectionForBlock`**

Once stored, `chainSelSync` processes the certificate and calls `chainSelectionForBlock` for the attacker-chosen boosted block:

```haskell
-- Trigger chain selection for the boosted block.
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

The `PerasWeightSnapshot` is also updated with the injected boost weight, which is then used in all subsequent chain comparisons: [5](#0-4) 

**Analog to the reported vulnerability class**

The EthenaMinting bug was: a shared mapping could be overwritten by an unprivileged actor, causing the authorization check to use attacker-controlled state and produce an incorrect result. Here the analog is structurally identical: the authorization check (`validatePerasCert`) is the shared mutable "gate" — but it has been reduced to a function that accepts every input unconditionally, so any unprivileged peer can write arbitrary entries into the certificate store and trigger chain-selection side-effects, exactly as Bob could overwrite `delegatedSigner[Alice]` to corrupt `verifyOrder`.

### Impact Explanation

**Critical — Bypass of Peras certificate validation enabling unauthorized certificate acceptance and chain-selection manipulation.**

A `PerasCert` carries only `pcCertRound` and `pcCertBoostedBlock`: [6](#0-5) 

There is no signature field in the wire type, and the validation stub performs zero checks. An attacker can therefore:

1. Inject a certificate for any round `R` boosting any block `B` on a weaker fork.
2. The node applies full Peras weight to `B` in its `PerasWeightSnapshot`.
3. `chainSelectionForBlock` is triggered for `B`; if the boosted weight tips the comparison, the node switches to the non-canonical chain.

This directly undermines Peras's chain-quality guarantee: the protocol's entire purpose is to make the canonical chain heavier than any fork, but fake certificates allow an attacker to artificially inflate the weight of a fork.

---

### Likelihood Explanation

**High.** The attack requires only a peer connection and the ability to send a well-formed `PerasCert` CBOR message. No stake, no keys, no quorum participation is needed. The miniprotocol is reachable from any node-to-node connection. The stub is the only instance in the codebase and is used in both the `PerasCertDB`-backed and `ChainDB`-backed production writers.

---

### Recommendation

1. **Implement real validation in `validatePerasCert`**: verify that the certificate is accompanied by (or derivable from) a quorum of committee-member signatures for the claimed round, that each signer was eligible, and that the boosted block is within the valid slot window.
2. **Until real validation exists, reject all inbound certificates at the miniprotocol boundary** rather than silently accepting them. The `processCerts` function should treat the absence of a real validator as a hard rejection.
3. **Consider requiring inbound certificates to carry the underlying votes** so that `validatePerasCert` can re-derive and verify the quorum rather than trusting a bare `(round, block)` pair.

---

### Proof of Concept

**Setup**: a private two-node testnet with Peras enabled, node A (honest) and node B (attacker).

1. Node B connects to node A via the Peras certificate object-diffusion miniprotocol.
2. Node B sends a batch containing one `PerasCert`:
   ```
   PerasCert { pcCertRound = 42, pcCertBoostedBlock = <hash of a block on a weaker fork> }
   ```
3. Node A's `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right ValidatedPerasCert{..}` unconditionally.
4. The certificate is stored in `PerasCertDB`; `implAddCert` inserts it into `pcdsCertsByTicket` and updates `pcdsLatestCertSeen`.
5. `chainSelSync` is invoked; `chainSelectionForBlock` runs for the fork block.
6. Node A's `PerasWeightSnapshot` now shows a boost for the fork block; if the fork's total weight (chain length + Peras boost) exceeds the canonical chain's weight, node A switches chains.

**Expected (correct) behaviour**: step 3 should return `Left (PerasValidationErr ...)` because no quorum proof was supplied.
**Actual behaviour**: step 3 returns `Right`, the certificate is accepted, and chain selection is triggered for an attacker-chosen block. [7](#0-6) [8](#0-7) [4](#0-3)
