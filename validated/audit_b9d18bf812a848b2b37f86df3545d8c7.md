### Title
`deposit_fee` Can Exceed `deposit_amount` Causing Permanent BTC Locking via Arithmetic Underflow - (File: `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

---

### Summary

`BridgeFee::get_fee()` returns `max(amount * fee_rate / MAX_RATIO, fee_min)`. When `fee_min > deposit_amount >= min_deposit_amount`, the computed `deposit_fee` exceeds `deposit_amount`, and the unchecked subtraction `deposit_amount - deposit_fee` at line 53 of `deposit.rs` panics (u128 underflow). Because `Config::assert_valid()` never enforces `deposit_bridge_fee.fee_min <= min_deposit_amount`, this misconfiguration is silently accepted, and every deposit in the range `[min_deposit_amount, fee_min)` permanently fails — locking the user's BTC with no recovery path.

---

### Finding Description

**`BridgeFee::get_fee()` — `config.rs` lines 30–35**

```rust
pub fn get_fee(&self, amount: u128) -> u128 {
    std::cmp::max(
        amount * u128::from(self.fee_rate) / u128::from(MAX_RATIO),
        self.fee_min,
    )
}
```

The fee is floored at `fee_min`. When `fee_min > amount`, the returned fee exceeds the deposit amount. [1](#0-0) 

**`internal_verify_deposit()` — `deposit.rs` lines 45–53**

```rust
if deposit_amount < config.min_deposit_amount {
    // route to unavailable_utxo_callback
} else {
    let deposit_fee = config.deposit_bridge_fee.get_fee(deposit_amount);
    let mint_amount = deposit_amount - deposit_fee;   // ← panics when fee_min > deposit_amount
```

The only guard is `deposit_amount >= min_deposit_amount`. There is no guard that `deposit_fee <= deposit_amount`. When `fee_min > deposit_amount`, the subtraction underflows and the entire `verify_deposit` transaction reverts. [2](#0-1) 

**`Config::assert_valid()` — `config.rs` lines 124–158**

The validation function checks `fee_rate < MAX_RATIO` and `protocol_fee_rate <= MAX_RATIO`, but **never** checks that `deposit_bridge_fee.fee_min <= min_deposit_amount`. This missing invariant allows the DAO to set, for example, `fee_min = 100_000` while `min_deposit_amount = 20_000`, silently creating the vulnerable range. [3](#0-2) 

---

### Impact Explanation

When `fee_min > min_deposit_amount`, any BTC deposit whose on-chain output value falls in `[min_deposit_amount, fee_min)` satoshis will:

1. Pass the `deposit_amount < config.min_deposit_amount` guard (so it is not routed to `unavailable_utxo_callback`).
2. Compute `deposit_fee = fee_min > deposit_amount`.
3. Panic at `deposit_amount - deposit_fee` (u128 underflow with `overflow-checks = true`, the NEAR standard).
4. Revert the entire `verify_deposit` call — the UTXO is never registered in `verified_deposit_utxo`, the nBTC is never minted, and the relayer's retry will always produce the same panic.

The user's BTC is permanently locked in the deposit address with no on-chain recovery mechanism. This matches the **Critical / Medium** impact class: *permanent locking of user funds* and *stuck bridge state requiring operator intervention*.

---

### Likelihood Explanation

The DAO can update `deposit_bridge_fee` and `min_deposit_amount` independently via `update_config`. Because `assert_valid()` does not enforce `fee_min <= min_deposit_amount`, a routine fee increase (e.g., raising `fee_min` to cover higher on-chain costs) without a corresponding raise of `min_deposit_amount` silently creates the vulnerable window. Once the misconfiguration exists, **any unprivileged user** whose deposit falls in `[min_deposit_amount, fee_min)` triggers the panic — no attacker coordination is required.

---

### Recommendation

Add the following invariant to `Config::assert_valid()`:

```rust
require!(
    self.deposit_bridge_fee.fee_min <= self.min_deposit_amount,
    "deposit fee_min must not exceed min_deposit_amount"
);
require!(
    self.withdraw_bridge_fee.fee_min <= self.min_withdraw_amount,
    "withdraw fee_min must not exceed min_withdraw_amount"
);
```

Alternatively, replace the bare subtraction with a saturating or checked variant and route zero-mint deposits to `unavailable_utxo_callback`:

```rust
let mint_amount = deposit_amount.saturating_sub(deposit_fee);
if mint_amount == 0 {
    return promise.then(/* unavailable_utxo_callback */);
}
```

### Proof of Concept

**Configuration** (set by DAO via `update_config`):
```
deposit_bridge_fee.fee_min  = 100_000  (satoshis)
min_deposit_amount          =  20_000  (satoshis)
```

**Trigger** (any unprivileged relayer submitting a valid BTC proof for a 50_000-sat deposit):
```
deposit_amount = 50_000   ≥ min_deposit_amount (20_000)  → passes guard
deposit_fee    = fee_min  = 100_000
mint_amount    = 50_000 - 100_000  → u128 underflow → PANIC
```

Every `verify_deposit` call for this UTXO reverts. The 50_000-sat UTXO is never registered; the user's BTC is permanently locked. [4](#0-3) [1](#0-0)
