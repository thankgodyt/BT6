Audit Report

## Title
Resigned or Revoked Trusted Relayer Permanently Loses Earned Fees Due to Conflicting Guards on `claim_fee` — (`near/omni-bridge/src/lib.rs`)

## Summary
`claim_fee` is gated by `#[trusted_relayer]`, which checks the caller's **current** trusted status. A relayer who earned a fee (by signing a transfer with themselves as `fee_recipient`) and then resigned or was revoked before claiming is permanently blocked: they fail the `#[trusted_relayer]` gate, and no substitute caller (including DAO) can succeed because `claim_fee_callback` enforces `fee_recipient == predecessor_account_id`. The result is permanent freezing of the fee portion of bridged funds and persistent mis-accounting in `pending_transfers` and `locked_tokens`.

## Finding Description
The `claim_fee` function at line 1054 carries `#[trusted_relayer]`, which is resolved against the impl-block configuration at lines 245–249 with `bypass_roles(Role::DAO, Role::UnrestrictedRelayer)`. This means only currently-active trusted relayers, DAO members, or `UnrestrictedRelayer` role holders can pass the outer gate.

Inside `claim_fee_callback` (lines 1083–1086), a second independent check enforces:
```rust
require!(
    fee_recipient == *predecessor_account_id,
    BridgeError::OnlyFeeRecipientCanClaim.as_ref()
);
```
where `predecessor_account_id` is the original caller of `claim_fee`, captured at line 1062 via `&env::predecessor_account_id()`.

The deadlock arises as follows:
1. A trusted relayer calls `sign_transfer` (line 447) with `fee_recipient: Some(relayer_account_id)`. The `fee_recipient` is embedded in the signed `TransferMessagePayload` and broadcast to the destination chain.
2. The destination chain finalizes the transfer and emits a `FinTransfer` event with `fee_recipient = relayer_account_id`. The relayer's entitlement is irrevocably recorded.
3. The relayer calls `resign_trusted_relayer` (generated by the `#[trusted_relayer]` macro's `manager_roles`) to recover their staked NEAR. Trusted status is immediately removed, as confirmed by the test at lines 346–353.
4. The relayer calls `claim_fee` — rejected at the `#[trusted_relayer]` gate because they are no longer trusted.
5. A DAO member calls `claim_fee` with the same proof — passes the `#[trusted_relayer]` gate (via `bypass_roles`) but `predecessor_account_id` is now the DAO account, not `fee_recipient`. The `claim_fee_callback` check at line 1083 fails with `BridgeError::OnlyFeeRecipientCanClaim`.
6. `remove_transfer_message` at line 1094 is never reached. The `pending_transfers` entry persists indefinitely and `locked_tokens` is never decremented.

There is no admin escape hatch that both removes the `pending_transfers` entry and correctly adjusts `locked_tokens`. The `transfer_token_as_dao` function (lines 1511–1529) can move tokens but does not touch `pending_transfers` or `locked_tokens`, leaving the accounting permanently corrupted.

## Impact Explanation
This constitutes **permanent freezing of bridged funds**: the fee portion of the user's original locked deposit (calculated as `transfer_message.amount.0 - denormalized_amount` at line 1131) is irrecoverably locked inside the bridge contract. Additionally, `locked_tokens` is never corrected (the `remove_transfer_message` call at line 1094 that triggers the accounting update is never reached), constituting **fee mis-accounting** and **escrow mis-accounting** that compounds with each affected transfer. Both match allowed Critical impact categories.

## Likelihood Explanation
The scenario requires no admin compromise and no victim mistakes. Any trusted relayer can trigger it unintentionally by resigning (a normal, documented lifecycle action to recover staked NEAR) before claiming all pending fees. The window between `sign_transfer` and a provable `FinTransfer` event on NEAR spans minutes to hours depending on destination chain finality and relayer latency, making it easy to resign in between. The scenario is repeatable across any number of relayers and transfers.

## Recommendation
Remove the `#[trusted_relayer]` guard from `claim_fee` entirely. The inner `require!(fee_recipient == *predecessor_account_id, ...)` check in `claim_fee_callback` already ensures only the rightful recipient can collect the fee — the outer trusted-relayer gate adds no security benefit and introduces this permanent-loss scenario. Alternatively, add a dedicated bypass that allows any account to call `claim_fee` provided the proof's `fee_recipient` matches `env::predecessor_account_id()`.

## Proof of Concept
1. DAO sets `stake_required = 1 yoctoNEAR`, `waiting_period_ns = 0` (mirrors test setup at lines 592–601).
2. `relayer.near` calls `apply_for_trusted_relayer` with 1 yoctoNEAR deposit → becomes trusted immediately.
3. `relayer.near` calls `sign_transfer(transfer_id, fee_recipient = Some("relayer.near"), fee = Some(...))`.
4. The destination chain finalizes the transfer; a mock prover returns a `ProverResult::FinTransfer` with `fee_recipient = "relayer.near"`.
5. `relayer.near` calls `resign_trusted_relayer` → stake returned, trusted status removed (confirmed by `assert!(!is_trusted)` at line 353).
6. `relayer.near` calls `claim_fee` with a valid borsh-encoded `ClaimFeeArgs` → **panics at the `#[trusted_relayer]` gate**.
7. DAO account calls `claim_fee` with the same args → passes the `#[trusted_relayer]` gate but **panics at line 1083** with `BridgeError::OnlyFeeRecipientCanClaim` because `DAO ≠ "relayer.near"`.
8. `pending_transfers` retains the entry; `locked_tokens` is never corrected; the fee is permanently frozen.
