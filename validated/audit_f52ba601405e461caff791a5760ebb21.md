### Title
Peras Certificate Validation Stub Always Accepts Any Inbound Certificate — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance provides a `validatePerasCert` implementation that unconditionally returns `Right` (success) for every certificate, performing zero cryptographic or semantic checks. The production inbound-certificate pipeline (`processCerts`) relies on this function as its only cryptographic gate; the sole remaining protection is a round-number deduplication check. An unprivileged peer can therefore inject an arbitrary, forged Peras certificate for any round not yet in the database, causing the node to accept it and apply its chain-selection weight boost to an attacker-chosen block.

---

### Finding Description

**Root cause — stub validation that always succeeds:**

The `BlockSupportsPeras` type class declares `validatePerasCert` as the mandatory cryptographic gate for inbound certificates. The universal instance (the only instance present in the codebase) implements it as an unconditional `Right`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This instance is declared as a catch-all for all block types:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/120
instance StandardHash blk => BlockSupportsPeras blk where
``` [2](#0-1) 

No more-specific instance for Cardano blocks exists in the repository to override this stub.

**Exploit path — production inbound pipeline:**

The production certificate ingest function `processCerts` (called from `makePerasCertPoolWriterFromChainDB`, the live peer-facing writer) applies exactly two filters before accepting a certificate:

1. A round-number deduplication check (`alreadyInDb`).
2. A call to `validateCert` — which is wired to the stub above.

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb =
        filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _) ->
      throw (PerasCertValidationError errs)
``` [3](#0-2) 

Because `validateCert` never returns `Left`, the `(errs, _)` branch is unreachable. Every certificate whose round number is not already in the database is unconditionally accepted and stored.

The production writer that feeds this pipeline:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { ...
    , opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [4](#0-3) 

**Analog to the external report:**

The external report describes a pattern where a secondary hash-based deduplication check (`processed[_borrowHash]`) is redundant because the primary nonce mechanism already prevents replay. Here the situation is the inverse but structurally identical: the round-number deduplication (`alreadyInDb`) is the *only* protection because the primary cryptographic check (`validatePerasCert`) is a no-op stub. Removing or bypassing the deduplication check (e.g., by using a fresh round number) leaves zero protection — exactly the gap the external report's pattern exposes when the "redundant" check is the only real guard.

### Impact Explanation

An unprivileged peer can craft a `PerasCert` with:
- Any `pcCertRound` not yet present in the node's certificate database.
- Any `pcCertBoostedBlock` pointing to an attacker-controlled block.

The certificate bypasses all cryptographic checks (no aggregate BLS signature verification, no committee membership check, no VRF eligibility proof) and is stored as a `ValidatedPerasCert`. Its `vpcCertBoost` weight is then applied to the attacker-chosen block during chain selection via `getPerasWeightSnapshot`, potentially causing the honest node to prefer a non-canonical or adversarial chain over the honest chain.

**Severity: Critical** — matches the allowed scope item: *"Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance."*

---

### Likelihood Explanation

The object-diffusion mini-protocol for Peras certificates is the live peer-to-peer dissemination path. Any connected peer (no credentials required) can send a `PerasCert` message. The stub is present in the only `BlockSupportsPeras` instance in the repository and is explicitly wired into both the `PerasCertDB`-backed and `ChainDB`-backed production writers. The TODO comments confirm this is not a test artifact but an acknowledged incomplete implementation shipped in production source.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real cryptographic validator that:
1. Verifies the aggregate BLS signature against the declared voter set and election ID.
2. Confirms each declared voter is a legitimate committee member for the given round (VRF eligibility proof).
3. Checks that the quorum threshold is met by the declared voters' combined stake.
4. Validates that `pcCertBoostedBlock` refers to a block that actually exists and is consistent with the round's candidate.

Until this is done, inbound certificates from untrusted peers should be rejected at the network boundary rather than silently accepted.

---

### Proof of Concept

```
Attacker (unprivileged peer) → sends PerasCert {
    pcCertRound    = <any round not in DB>,
    pcCertBoostedBlock = <attacker's preferred block point>
  }

processCerts:
  1. alreadyInDb check → passes (fresh round number)
  2. validatePerasCert mkPerasParams cert → always Right (stub)
  3. addCert (WithArrivalTime now validatedCert) → stored in PerasCertDB

Chain selection:
  getPerasWeightSnapshot returns boost for attacker's block
  → node may switch to attacker's chain

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
