### Title
Peras Certificate Validation Bypass Allows Unprivileged Peer to Trigger Unauthorized Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary
The production Peras certificate ingest path uses a degenerate `validatePerasCert` stub that unconditionally returns `Right` (success) for every inbound certificate, bypassing all cryptographic and semantic checks. This stub is wired directly into the live node-to-node Peras certificate diffusion miniprotocol handler. An unprivileged peer can therefore inject an arbitrary crafted certificate that will be accepted without any committee-membership, BLS-signature, or round-number verification, triggering chain selection for any block in the VolatileDB.

### Finding Description

**Root cause — degenerate `validatePerasCert` stub:**

The `BlockSupportsPeras` type class defines `validatePerasCert` as the mandatory gate that must verify a received certificate before it is admitted to the ChainDB. The catch-all instance for all block types provides a stub that always succeeds:

```haskell
-- TODO: perform actual validation against all possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
    Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [1](#0-0) 

This is the catch-all instance covering every block type including `CardanoBlock`:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
``` [2](#0-1) 

**Propagation into the production ingest path:**

`makePerasCertPoolWriterFromChainDB` — the production writer used by the live miniprotocol handler — passes this stub directly as the `validateCert` argument to `processCerts`:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
(void . ChainDB.addPerasCertAsync chainDB)
``` [3](#0-2) 

`processCerts` calls `validateCert` on every inbound certificate and, because the stub always returns `Right`, unconditionally forwards every certificate to `ChainDB.addPerasCertAsync`:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _) ->
      throw (PerasCertValidationError errs)
``` [4](#0-3) 

**Live network handler wiring:**

This writer is wired into the production node-to-node stack:

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      version
      controlMessageSTM
``` [5](#0-4) 

**Downstream chain selection effect:**

`addPerasCertAsync` enqueues a `ChainSelAddPerasCert` message. The ChainSel background thread processes it by calling `chainSelectionForBlock` for the boosted block:

```haskell
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [6](#0-5) 

The accepted `ValidatedPerasCert` carries `vpcCertBoost = perasWeight mkPerasParams`. This boost is applied to the boosted block's chain weight in the `PerasWeightSnapshot`, which is consulted during `compareAnchoredFragments` in chain selection. If the boosted block is on a fork that is otherwise not preferred, the artificial weight boost may cause the honest node to switch to that fork.

**Analog to the external report:**

The external report describes an intermediary contract (ConvexStakingWrapper) that calls a downstream contract (MasterChef) without properly verifying the actual user's identity — using `_msgSender()` (the intermediary's own address) instead of the real user's address. The result is that all accounting is attributed to the intermediary, allowing any caller to steal accumulated rewards.

The structural analog here is: the Peras certificate diffusion layer (intermediary) calls `addPerasCertAsync` (downstream component) without properly verifying the actual certificate issuer's identity (committee membership and BLS signature). The result is that any peer's crafted certificate is attributed the same weight as a legitimately-issued committee certificate, allowing any peer to manipulate chain selection weight.

### Impact Explanation

An unprivileged peer can craft a `PerasCert` naming any block hash present in the VolatileDB as the boosted block and any round number not yet in the certificate database. The certificate is accepted without any BLS-signature, committee-membership, or quorum check. The resulting `ValidatedPerasCert` carries a non-zero `vpcCertBoost`, which is applied to the boosted block's chain weight during chain selection. If the boosted block is on a fork that is otherwise not preferred, the artificial weight boost may cause the honest node to switch to that fork, violating chain selection safety.

This matches the allowed impact scope: **bypass of Peras certificate checks that enables unauthorized certificate acceptance**, and **chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain**.

### Likelihood Explanation

The Peras certificate diffusion miniprotocol handler is compiled into the production node binary and wired up in `NodeToNode.hs`. Any peer that negotiates a `NodeToNodeVersion` that includes the Peras certificate diffusion miniprotocol can send crafted certificates. No special privileges, keys, or stake are required. The degenerate instance covers all block types including `CardanoBlock` via the catch-all `instance StandardHash blk => BlockSupportsPeras blk`.

### Recommendation

1. Replace the degenerate `validatePerasCert` stub with a proper implementation that verifies the aggregate BLS signature against the claimed committee members' public keys, checks committee membership via VRF-based sortition against the stake distribution, verifies the quorum threshold is met, and validates the round number and boosted block hash against protocol parameters.
2. Until the proper implementation is in place, guard the `processCerts` call with a feature flag that rejects all inbound certificates, or disable the Peras certificate diffusion miniprotocol entirely.
3. Track this via the referenced issues: [#73](https://github.com/tweag/cardano-peras/issues/73) and [#120](https://github.com/tweag/cardano-peras/issues/120).

### Proof of Concept

1. Connect to a target node as an unprivileged peer and negotiate a `NodeToNodeVersion` that includes the Peras certificate diffusion miniprotocol.
2. Construct a `PerasCert` with `pcCertRound` set to a round number not yet in the node's certificate database, and `pcCertBoostedBlock` set to the hash of a block on a fork present in the VolatileDB but not currently the node's preferred chain.
3. Send the certificate via the Peras certificate diffusion miniprotocol.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right` unconditionally regardless of the certificate's contents.
5. `ChainDB.addPerasCertAsync` is called with the crafted certificate, enqueuing a `ChainSelAddPerasCert` message.
6. The ChainSel background thread processes the message, applies the `vpcCertBoost` weight to the boosted block's chain, and calls `chainSelectionForBlock` for that block.
7. If the boost weight (`perasWeight mkPerasParams`) is sufficient to make the fork preferred over the current selection, the node switches to the non-canonical chain.

  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
