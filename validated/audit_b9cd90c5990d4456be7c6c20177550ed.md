### Title
Missing Peras Certificate Validation Allows Unauthorized Certificate Acceptance and Chain Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `validatePerasCert` implementation in `BlockSupportsPeras.hs` is a stub that unconditionally accepts every inbound Peras certificate without performing any validation — including no check that the certificate's round number falls within a valid window relative to the current protocol state (the direct analog of the external report's "missing time limit"), and no cryptographic signature verification. Any unprivileged peer can inject a certificate for an arbitrary round number and an arbitrary boosted block, which is stored in the `PerasCertDB` and used to trigger chain selection.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the mandatory gate for all inbound Peras certificates. The sole production instance of this function is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is called directly by `processCerts`, the inbound certificate handler wired into both the `PerasCertDB` and `ChainDB` pool writers:

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
``` [2](#0-1) 

The production `ChainDB` pool writer passes `validatePerasCert mkPerasParams` as the validator: [3](#0-2) 

Because `validatePerasCert` always returns `Right`, the only deduplication guard is a round-number membership check against the in-memory set (`alreadyInDb`). A certificate for any previously-unseen round number — including round 1,000,000 when the current round is 5 — passes unconditionally and is stored with the current wall-clock arrival time.

The missing checks that the external report's "time limit" pattern maps to are:

1. **No round-number window check**: There is no enforcement that `certRound ∈ [currRound - maxAge, currRound + smallFutureTolerance]`. The Peras protocol defines `PerasCertMaxRounds` (_A) as the maximum age for a certificate to be included in a block, but this parameter is never consulted during inbound validation. [4](#0-3) 

2. **No cryptographic signature verification**: The aggregate BLS signature over the quorum of votes is never verified.

---

### Impact Explanation

**Chain selection manipulation (Critical):** After `processCerts` stores the certificate, `makePerasCertPoolWriterFromChainDB` calls `ChainDB.addPerasCertAsync`, which enqueues a `ChainSelAddPerasCert` event. `chainSelSync` then calls `chainSelectionForBlock` for the boosted block: [5](#0-4) 

If the adversary's certificate boosts a block on a competing fork that is already in the node's VolatileDB, the node re-evaluates chain selection with that block receiving a `perasWeight` boost (default: 15 blocks of equivalent weight). A fork that would otherwise lose chain selection can win if the fake certificate tips the weight comparison.

**Voting suppression (High):** `getLatestCertSeen` returns the certificate with the highest round number seen since the DB was opened: [6](#0-5) 

A certificate injected with round number `maxBound` (or any large value) becomes the permanent `latestCertSeen`. The Peras voting rules VR-1A and VR-2A both fail against such a value:

- VR-1A requires `currRoundNo == latestCertRound + 1` — impossible if `latestCertRound` is far in the future.
- VR-2A requires `latestCertRound + R <= currRoundNo` — impossible for the same reason. [7](#0-6) 

This permanently silences the honest node's Peras vote production, degrading the protocol's fast-finality guarantee.

---

### Likelihood Explanation

The Peras object-diffusion mini-protocol is reachable from any connected peer. No authentication or stake ownership is required to send a `PerasCert` message. The attack requires only a TCP connection to the node and knowledge of the wire format. On a private testnet running the Peras extension, this is trivially exploitable.

---

### Recommendation

Replace the stub with a real implementation that enforces, at minimum:

1. **Round-number window**: Reject certificates whose `pcCertRound` is more than `perasCertMaxRounds` (_A) rounds behind the current round, or more than a small tolerance ahead of it (analogous to the KES period window check in `doValidateKESSignature`).

2. **Aggregate signature verification**: Verify the BLS aggregate signature against the claimed quorum of committee members, using the committee selection context for the relevant epoch.

3. **Boosted block plausibility**: Reject certificates whose `pcCertBoostedBlock` is already immutable (this check exists in `chainSelSync` but should also be a pre-filter in `processCerts`).

The `validatePerasCert` signature already accepts `PerasCfg blk` (which carries `PerasParams`) and should additionally receive the current round number and the hard-fork summary to perform the slot/round translation needed for check (1).

---

### Proof of Concept

On a private testnet node with Peras enabled:

1. Connect to the node's object-diffusion endpoint.
2. Send a `PerasCert` message with `pcCertRound = maxBound` and `pcCertBoostedBlock` set to any block hash present in the node's VolatileDB (observable via the ChainSync protocol).
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → `Right (ValidatedPerasCert ...)`.
4. The certificate is stored; `getLatestCertSeen` now returns this certificate.
5. On the next voting tick, `perasVR1A` evaluates `currRoundNo :==: maxBound + 1` (wraps to 0) — false. `perasVR2A` evaluates `maxBound + R <= currRoundNo` — false. The node produces no votes for any subsequent round.
6. Simultaneously, `addPerasCertAsync` triggers `chainSelectionForBlock` for the boosted block, potentially causing the node to switch to the adversary's fork. [1](#0-0) [8](#0-7) [9](#0-8)

perasVR1A ::
  HasPerasCertRound cert =>
  PerasVotingView cert ->
  Pred PerasVotingRule
perasVR1A
  PerasVotingView
    { perasParams
    , currRoundNo
    , latestCertSeen
    } =
    VR1A := vr1a1 :/\: vr1a2
   where
    -- The latest certificate seen is from the previous round
    vr1a1 =
      case latestCertSeen of
        -- We have seen a certificate ==> check its round number
        NotOrigin cert ->
          currRoundNo :==: getPerasCertRound (lcsCert cert) + 1
        -- We have never seen a certificate ==> check if we are voting in round 0
        Origin ->
          currRoundNo :==: PerasRoundNo 0

    -- The latest certificate seen was received within X slots from the start
    -- of its round
    vr1a2 =
      case latestCertSeen of
        -- We have seen a certificate ==> check its arrival time
        NotOrigin cert ->
          lcsArrivalSlot cert :<=: lcsRoundStartSlot cert + _X
        -- We have never seen a certificate ==> vacuously true
        Origin ->
          Bool True

    _X =
      SlotNo $
        unPerasCertArrivalThreshold $
          perasCertArrivalThreshold perasParams
