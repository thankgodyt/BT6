### Title
`validatePerasCert` Stub Unconditionally Accepts Any Peer-Supplied Peras Certificate, Enabling Chain-Selection Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance ships a stub `validatePerasCert` that unconditionally returns `Right` for every certificate it receives. Because the Peras certificate diffusion inbound handler calls this function before storing received certificates, any unprivileged peer can inject an arbitrarily crafted `PerasCert` — boosting any block of the adversary's choice — without possessing the required aggregate BLS signature or committee membership proof. The stored certificate then influences chain selection via its `vpcCertBoost` weight, allowing the adversary to make an honest node prefer a non-canonical chain.

---

### Finding Description

**Root cause — `validatePerasCert` stub:** [1](#0-0) 

```haskell
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
```

This is the **only** `BlockSupportsPeras` instance in the codebase (a catch-all "degenerate instance for all blks to get things to compile"): [2](#0-1) 

**Inbound path — `processCerts` calls the stub:** [3](#0-2) 

`processCerts` passes `validatePerasCert mkPerasParams` as the validation function. Because the stub always returns `Right`, every certificate in every inbound batch is accepted and timestamped, then forwarded to `ChainDB.addPerasCertAsync`.

**Production wiring — cert diffusion is live in node-to-node handlers:** [4](#0-3) 

The `hPerasCertDiffusionClient` handler is wired into the production `Handlers` record, meaning any connected peer can trigger this path.

**Analog to the external report:** Just as `TieredBountyCore#receiveNFT` stored a user-supplied tier index without bounds-checking (filling limited NFT slots with entries for non-existent tiers), `processCerts` stores peer-supplied certificates without any cryptographic or structural validation (filling the `PerasCertDB` with entries for adversary-chosen blocks). In both cases the bounded/authoritative structure is polluted with attacker-controlled data that the system then acts upon.

---

### Impact Explanation

A `ValidatedPerasCert` carries a `vpcCertBoost` weight derived from `perasWeight params`. Chain selection uses this boost to prefer the certified block over competing tips. An adversary who injects a certificate for their own (potentially invalid or minority) block causes the honest node to add that block's chain weight by `vpcCertBoost`, potentially making the node select a non-canonical chain. This is a **High** impact chain-selection manipulation: an unprivileged peer makes an honest node prefer a less-secure chain beyond the intended security assumptions of Peras. [5](#0-4) 

---

### Likelihood Explanation

- The Peras cert diffusion mini-protocol is unconditionally wired into the production node-to-node handler record.
- No stake, key material, or special privilege is required — any connected peer can send a `PerasCert` message.
- The stub contains an explicit TODO referencing a known issue (`cardano-peras#120`), confirming the validation gap is acknowledged but not yet closed.
- The attack requires only a single well-formed CBOR-encoded `PerasCert` message targeting the adversary's preferred block.

---

### Recommendation

Replace the stub with a real implementation of `validatePerasCert` that:
1. Verifies the aggregate BLS signature against the claimed voter set and the committee's public keys for the relevant epoch.
2. Checks that the claimed voter seat indices are within bounds of the current committee (`getCandidateIfSeatWithinBounds` already exists in `WFA.hs`).
3. Verifies that the total certified stake meets the quorum threshold.
4. Checks that the certified round number is within a valid window relative to the current chain tip.

Until the real implementation is ready, the inbound cert diffusion handler should be disabled or should reject all certificates rather than accept them unconditionally. [6](#0-5) 

---

### Proof of Concept

1. Connect to a target node as a peer (no special privileges required).
2. Craft a `PerasCert` with `pcCertRound = <current round>` and `pcCertBoostedBlock = <adversary block point>`.
3. Send it via the Peras cert diffusion mini-protocol (`hPerasCertDiffusionClient`).
4. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }`.
5. The certificate is stored in `PerasCertDB` via `ChainDB.addPerasCertAsync`.
6. Chain selection now applies `vpcCertBoost` to the adversary's block, causing the node to prefer the adversary's chain over the honest chain. [7](#0-6)
