### Title
Peras Quorum Check Passes on Unnormalized Absolute Stake — `stakeAboveThreshold` Compares Incompatible Units - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

`stakeAboveThreshold` compares the raw sum of `PerasVoteStake` values against a normalized (relative) quorum threshold without enforcing that both operands are in the same unit. The code itself documents this assumption as unresolved. If the `PerasVoteStakeDistr` is populated with absolute lovelace amounts — which is the natural ledger representation and which the codebase explicitly acknowledges has no agreed normalization path — the comparison is always satisfied, allowing any single vote from a registered voter to forge a Peras certificate for an arbitrary block and inject a chain-weight boost.

### Finding Description

`stakeAboveThreshold` in `SupportsPeras.hs` is the sole gate that decides whether accumulated votes constitute a quorum:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake         = unPerasVoteStake voteStake          -- Rational
  quorumThreshold = unPerasQuorumStakeThreshold ...   -- 3/4
  safetyMargin    = unPerasQuorumStakeThresholdSafetyMargin ... -- 2/100
```

The default `PerasParams` sets `perasQuorumStakeThreshold = 3/4` and `perasQuorumStakeThresholdSafetyMargin = 2/100`, so the right-hand side is `0.77` — a relative fraction of total committee stake.

The left-hand side, `stake`, is the `Monoid`-summed `PerasVoteStake` values drawn from `PerasVoteStakeDistr`. The code carries two explicit warnings about this:

1. The `PerasVoteStake` type note (lines 136–143) states: *"At the moment there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee."*

2. The `stakeAboveThreshold` TODO (lines 155–161) states: *"this function assumes that the 'PerasVoteStake' and the quorum threshold … are expressed in the same units … this function only makes sense when both values are relative (normalized) values, so we should either normalize the 'PerasVoteStake' before calling this function, or change this function to accept a stake distribution and perform the normalization internally."*

No normalization is performed anywhere in the call chain. `validatePerasVote` copies the stake value verbatim from the distribution:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
```

`updateTargetVoteTally` then accumulates these raw values:

```haskell
ptvtTotalStake + vpvVoteStake (forgetArrivalTime vote)
```

and `votesReachQuorum` / `updateCandidateVoteState` call `stakeAboveThreshold` on the accumulated total to decide whether to forge a certificate.

If the `PerasVoteStakeDistr` is populated from the ledger with absolute lovelace amounts (e.g., a voter with 1 000 000 lovelace), the comparison becomes `1_000_000 >= 0.77`, which is trivially true. A single vote from any registered voter — regardless of their actual fractional stake — would satisfy the quorum check and trigger `forgePerasCert`, producing a `ValidatedPerasCert` with a `perasWeight = 15` boost that is then stored in the `PerasCertDB` and applied to chain selection via `totalWeightOfFragment`.

### Impact Explanation

A forged certificate boosts the weight of an arbitrary block by `perasWeight = 15` (the default). `totalWeightOfFragment` adds this boost to the block-count length of any chain fragment containing that block. Chain selection in `ChainDB` uses this total weight to prefer one chain over another. An attacker who can inject a certificate for a block on their own fork causes honest nodes to assign that fork a weight 15 units higher than its honest block count, potentially making it preferred over the canonical chain. This is a chain-selection safety failure: an unprivileged peer can make an honest node prefer a non-canonical, less-secure chain beyond the intended security assumptions of Praos/Peras.

### Likelihood Explanation

The `PerasVoteStakeDistr` is constructed from the ledger's stake distribution, where stake is naturally expressed in lovelace (absolute). The codebase explicitly states there is no agreed method to normalize it. The production wiring in `makePerasVotePoolWriterFromChainDB` and `makePerasVotePoolWriterFromVoteDB` passes `getStakeDistrSTM` — an STM action returning the current distribution — directly into `validatePerasVote` with no normalization step. Any voter registered in the distribution (even one holding a trivially small absolute stake) can trigger the always-true comparison. The attack requires only that the adversary be a registered voter and can send a single well-formed vote message to the target node.

### Recommendation

1. **Normalize before comparing.** Before calling `stakeAboveThreshold`, divide each voter's absolute stake by the total stake of the committee to obtain a relative value in `[0,1]`. Alternatively, change `stakeAboveThreshold` to accept the total committee stake and perform the normalization internally.
2. **Enforce units at the type level.** Introduce distinct newtypes for absolute and relative stake (e.g., `AbsoluteStake` vs `RelativeStake`) so that the compiler rejects comparisons between incompatible units.
3. **Resolve the open research question.** The NOTE on `PerasVoteStake` acknowledges that the normalization path is unresolved. This must be settled before the Peras voting path is enabled on any production network.

### Proof of Concept

1. Node A is an honest Cardano node running with Peras enabled.
2. Attacker controls a registered stake pool with 1 lovelace of stake. The ledger populates `PerasVoteStakeDistr` with `{ attackerPoolId → PerasVoteStake 1 }` (absolute lovelace).
3. Attacker sends a single `PerasVote` for round `r`, targeting a block `B` on the attacker's fork, via the object-diffusion mini-protocol.
4. Node A calls `validatePerasVote mkPerasParams stakeDistr vote`, which returns `Right (ValidatedPerasVote { vpvVoteStake = PerasVoteStake 1 })`.
5. `votesReachQuorum` calls `stakeAboveThreshold params (PerasVoteStake 1)`, evaluating `1 >= 0.75 + 0.02 = 0.77` → `True`.
6. `forgePerasCert` is called, producing a `ValidatedPerasCert` boosting block `B` by weight 15.
7. The certificate is stored in `PerasCertDB` and `implGetWeightSnapshot` returns a `PerasWeightSnapshot` with `B → PerasWeight 15`.
