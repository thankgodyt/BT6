### Title
Missing Cryptographic Validation in `validatePerasCert` Enables Spoofed Peras Certificate Injection Before First Legitimate Certificate Is Seen - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The `BlockSupportsPeras` instance in `SupportsPeras.hs` provides a degenerate stub for `validatePerasCert` that unconditionally returns `Right` for every certificate, performing zero cryptographic verification. An unprivileged peer can inject a crafted `PerasCert` via the ObjectDiffusion protocol; the stub wraps it into a `ValidatedPerasCert` without any check, stores it in `PerasCertDB`, updates `latestCertSeen`, and inflates chain-selection weights for an arbitrary block. The attack is most impactful before the first legitimate certificate is seen, because voting rule VR-1B is vacuously satisfied at `Origin` and the attacker can anchor the node's entire voting view to a chosen block before any honest certificate arrives.

### Finding Description

**Root cause — `validatePerasCert` stub always returns `Right`** [1](#0-0) 

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This is the **only** `BlockSupportsPeras` instance in the codebase (the catch-all `instance StandardHash blk => BlockSupportsPeras blk`). [2](#0-1) 

Every `PerasCert` received from any peer is unconditionally promoted to `ValidatedPerasCert` with a full weight boost equal to `perasWeight params`. No aggregate-signature check, no voter-set check, no round-number plausibility check is performed.

**Inbound path from peers**

Peras votes arrive via `makePerasVotePoolWriterFromChainDB`, which calls `validatePerasVote` (also a stub — only checks stake-distribution membership, no signature) and then `ChainDB.addPerasVoteWithAsyncCertHandling`. [3](#0-2) 

Certificates generated from quorum-reaching votes are produced by `forgePerasCert` (also a stub, always `Right`) and forwarded to `addPerasCertAsync`. [4](#0-3) 

The `ChainDB` API also exposes `addPerasCertAsync` accepting `ValidatedPerasCert` directly, which is the entry point for certificates received from peers via ObjectDiffusion. [5](#0-4) 

**Effect on `latestCertSeen` and chain-selection weights**

Every accepted certificate updates `pcdsLatestCertSeen` in `PerasCertDB` if its round number is higher than the current latest. [6](#0-5) 

`getLatestCertSeen` is documented as directly controlling voting eligibility: [7](#0-6) 

**Initial-state window — the precise analog to the "initial deposit" vulnerability**

Before any certificate has been seen (`latestCertSeen = Origin`), voting rule VR-1B is vacuously `True`: [8](#0-7) 

```haskell
-- We have never seen a certificate ==> vacuously true
Origin ->
  Bool True
```

VR-1A at `Origin` only requires `currRoundNo == PerasRoundNo 0`: [9](#0-8) 

An attacker who injects a spoofed certificate before any honest certificate arrives:
1. Sets `latestCertSeen` to an arbitrary `(round, block)` pair.
2. Forces VR-1A to require `currRoundNo == attacker_round + 1`, suppressing voting in all other rounds.
3. Forces VR-1B to require that the candidate block extends the attacker-chosen block, steering honest nodes toward a non-canonical chain.
4. Injects a weight boost for the attacker-chosen block into `getWeightSnapshot`, directly influencing `preferAnchoredCandidate` during chain selection. [10](#0-9) 

After the first honest certificate is seen the attacker must inject a cert with a strictly higher round number to update `latestCertSeen`, but `validatePerasCert` still returns `Right` unconditionally, so the attack remains possible at any time.

**`implAddVote` also carries an explicit TODO for missing validation** [11](#0-10) 

### Impact Explanation

**Critical — Bypass of Peras certificate/vote validation.** `validatePerasCert` is the designated cryptographic gate for all inbound Peras certificates. Its unconditional `Right` return means the gate is permanently open. Any unprivileged peer can present a certificate claiming to certify any block in any round; the node will accept it, boost that block's chain-selection weight, and update its voting view accordingly.

**High — Chain-selection manipulation.** The spoofed certificate's weight boost is fed directly into `preferAnchoredCandidate`, which governs whether the node switches to a candidate chain. A sufficiently large boost for a non-canonical block can cause an honest node to prefer and adopt an adversarial chain.

**High — Voting-rule manipulation.** By controlling `latestCertSeen`, the attacker controls which round the node is willing to vote in (VR-1A) and which block it requires the candidate to extend (VR-1B), effectively steering or suppressing the node's Peras votes.

### Likelihood Explanation

Any peer reachable via the ObjectDiffusion mini-protocol can send a crafted `PerasCert`. No stake, no key material, and no prior interaction is required. The attack is most effective in the initial window (before the first honest certificate is seen), which occurs at every node restart and at the very start of Peras operation on the network. The stub is the only `BlockSupportsPeras` instance in the production source tree.

### Recommendation

1. Implement real cryptographic verification in `validatePerasCert`: verify the aggregate BLS/KES signature over `(electionId, candidate)` against the aggregated public keys of the claimed voter set, and confirm the voter set meets the quorum threshold from the stake distribution.
2. Similarly, implement signature verification in `validatePerasVote` — currently only stake-distribution membership is checked, not the vote's cryptographic signature.
3. Until proper validation is implemented, gate the ObjectDiffusion certificate/vote inbound handlers behind a feature flag that is disabled by default in production builds.
4. Add an explicit `assertWithMsg` or `error` in `validatePerasCert` that fails loudly if called in a non-test context before the TODO is resolved, preventing silent deployment of the stub.

### Proof of Concept

```
1. Connect to a target node as a peer via the ObjectDiffusion protocol.

2. Craft a PerasCert:
     pcCertRound        = PerasRoundNo 999999   -- far-future round
     pcCertBoostedBlock = <point of attacker-controlled block>

3. Send the crafted PerasCert to the node.

4. validatePerasCert is called:
     validatePerasCert params cert
       = Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
   -- No signature check; returns Right unconditionally.

5. The ValidatedPerasCert is passed to addCert in PerasCertDB.
   pcdsLatestCertSeen is updated to this cert (round 999999 > any prior round).

6. getWeightSnapshot now returns a weight boost for the attacker-chosen block.
   preferAnchoredCandidate uses this snapshot; the attacker's block is preferred.

7. Voting rules are now anchored to round 999999:
   - VR-1A requires currRoundNo == 1000000 to vote normally.
   - VR-1B requires the candidate block to extend the attacker's block.
   Honest voting is suppressed until round 1000000 is reached.

Expected outcome: the node accepts the spoofed certificate, boosts the
attacker-chosen block in chain selection, and suppresses honest Peras
voting for all rounds except 1000000.
```
