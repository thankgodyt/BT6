### Title
Stale Peras Weight Snapshot in `checkPreferTheirsOverOurs` Causes Incorrect Chain-Selection Disconnect — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

`checkPreferTheirsOverOurs` in the ChainSync client always passes a hardcoded `emptyPerasWeightSnapshot` to `preferAnchoredCandidate` when deciding whether to disconnect from a peer. This is the structural analog of the external report's `health()` returning 0 regardless of asset-removal state: a validity check ignores a critical piece of live state (Peras certificate weights), produces an incorrect result, and drives a consequential downstream action (peer disconnection). When Peras is enabled, a node will incorrectly disconnect from peers serving the canonical chain if that chain is heavier due to Peras boosts but shorter in block count, leaving the node permanently on a non-canonical chain.

---

### Finding Description

In `Ouroboros.Consensus.MiniProtocol.ChainSync.Client`, `checkPreferTheirsOverOurs` (lines 1834–1857) verifies that a peer's candidate fragment is still preferred over the node's current chain. If not, it throws `CandidateTooSparse`, disconnecting the peer. The call site hardcodes `emptyPerasWeightSnapshot`:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot          -- ← always ignores Peras certificate weights
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse
          mostRecentIntersection
          (ourTipFromChain ourFrag)
          (theirTipFromChain theirFrag)
``` [1](#0-0) 

`preferAnchoredCandidate` with `emptyPerasWeightSnapshot` takes the `isEmptyPerasWeightSnapshot` branch and compares chains by `BlockNo` only. When Peras is enabled, the correct comparison uses `weightedSelectView`, which computes `BlockNo + PerasWeight` (the `wsvTotalWeight`):

```haskell
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      -- block-count-only comparison
      ...
  | otherwise =
      -- full Peras-weighted comparison via weightedSelectView
      case preferCandidate ... (weightedSelectView cfg weights oursSuffix)
                               (weightedSelectView cfg weights candSuffix) of ...
``` [2](#0-1) 

A chain with N−1 blocks but a Peras certificate boost of weight ≥ 2 has total weight N+1, which is heavier than a chain with N blocks and no boost (total weight N). Because `checkPreferTheirsOverOurs` always passes `emptyPerasWeightSnapshot`, it computes `ShouldNotSwitch` for such a peer and disconnects them, even though the peer is serving the heavier canonical chain.

The root cause is structurally identical to the external report: a health/validity function (`checkPreferTheirsOverOurs` / `health()`) ignores a live state change (Peras certificate weights / asset removal) and returns an incorrect result (disconnect / health = 0), which drives an incorrect consequential action (missing the canonical chain / liquidating a healthy position).

The `PerasWeightSnapshot` is correctly threaded through every other chain-selection call site — `chainSelectionForBlock`, `constructPreferableCandidates`, `initialChainSelection`, and `switchTo` — but is absent only in `checkPreferTheirsOverOurs`. [3](#0-2) 

---

### Impact Explanation

When Peras is enabled and the canonical chain has Peras weight boosts that make it heavier than the node's current chain despite having fewer blocks, the node disconnects from every peer serving that canonical chain via `CandidateTooSparse`. The node remains on its current (non-canonical, lighter) chain indefinitely. This is a chain-selection bug: an honest node is made to prefer a non-canonical, less-secure chain over the canonical chain, violating the Peras chain-selection invariant. This matches the **High** impact category — a chain-selection bug that lets an unprivileged peer (one serving the canonical chain with valid Peras certificates) cause an honest node to prefer a non-canonical chain beyond the intended security assumptions.

---

### Likelihood Explanation

Peras is disabled by default, so this does not affect mainnet today. However, the code is active when Peras is enabled (private testnets, future mainnet activation). Once Peras is enabled, the scenario is routine: Peras certificates are issued every round, and a chain with one fewer block but a certificate boost is a normal occurrence. Any peer serving such a chain to a node whose current chain has more blocks (but no boosts) will trigger the incorrect disconnect. No special privileges are required — the peer only needs to serve a valid chain with valid Peras certificates.

---

### Recommendation

Replace `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the actual `PerasWeightSnapshot` from the node's current state, consistent with how `preferAnchoredCandidate` is called in `chainSelectionForBlock` and `constructPreferableCandidates`. The existing TODO comment (`-- TODO: remove this entire check`) suggests the developers intend to remove the check entirely, which would also resolve the issue. [4](#0-3) 

---

### Proof of Concept

1. Enable Peras on a private testnet.
2. Node N is on chain A: blocks `[B1, B2, B3]` — 3 blocks, no Peras boosts, total weight = 3.
3. Peer P serves chain B: blocks `[B1, B2, B2']` where `B2'` carries a valid Peras certificate boost of weight 2 — total weight = 2 + 2 = 4 > 3.
4. ChainSync client calls `checkPreferTheirsOverOurs` with `emptyPerasWeightSnapshot`.
5. `preferAnchoredCandidate` compares by block count only: chain B has 2 blocks vs chain A's 3 → `ShouldNotSwitch`.
6. Node disconnects from P with `CandidateTooSparse`.
7. Node N stays on chain A (total weight 3) and never adopts chain B (total weight 4, the canonical chain). [5](#0-4) [6](#0-5)

preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"
        Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
          case preferCandidate
            (projectChainOrderConfig cfg)
            (weightedSelectView cfg weights oursSuffix)
            (weightedSelectView cfg weights candSuffix) of
            ShouldSwitch r -> ShouldSwitch (Left r)
            ShouldNotSwitch o -> ShouldNotSwitch o
