### Title
Permanent Deposit UTXO Locking With No Operator Recovery Path When MPC Signing Stalls After `execute_refund` — (File: `contracts/satoshi-bridge/src/bitcoin_utils/refund.rs`)

### Summary

`execute_refund` is a public function (no ACL check on the caller, only a timelock). When it succeeds, `finalize_refund_with_psbt` atomically inserts into both `btc_pending_infos` and `verified_deposit_utxo`, then marks the refund request `executed = true`. If MPC signing never completes, the contract enters a state where every recovery path is blocked and the deposit UTXO is permanently locked with no operator escape hatch short of a contract upgrade.

### Finding Description

**Call sequence:**

1. Anyone calls `execute_refund` after the timelock elapses. [1](#0-0) 

2. `internal_execute_refund` builds the PSBT and calls `finalize_refund_with_psbt`. [2](#0-1) 

3. `finalize_refund_with_psbt` inserts into `btc_pending_infos` (panics if already present), inserts into `verified_deposit_utxo`, and re-saves the request with `executed = true`. [3](#0-2) 

**Stuck state when MPC signing never completes:**

- `btc_pending_infos` holds the entry in `PendingSign` stage.
- `verify_refund_finalize` requires `PendingVerify` stage → blocked. [4](#0-3) 
- Re-calling `execute_refund` passes `load_refund_request_for_execute` (because `executed == true` satisfies the guard), but `finalize_refund_with_psbt` panics with `"pending info already exist"` because the same deterministic `btc_pending_id` is already in the map. [5](#0-4) 
- `remove_refund_pending_tx_id` / `internal_remove_refund_pending_tx_id` requires the refund request to be absent first. [6](#0-5) 

**Attempted operator recovery — still fails:**

1. DAO/Operator calls `reject_refund` → removes the entry from `refund_requests` only; `verified_deposit_utxo` and `btc_pending_infos` are untouched. [7](#0-6) 

2. Trusted relayer calls `remove_refund_pending_tx_id` → now allowed (request is gone), removes `btc_pending_infos` entry.

3. **`verified_deposit_utxo` still contains the key.** No function removes from this set except `safe_mint_callback` on a rollback path, which is unrelated here. [8](#0-7) 

4. `verify_deposit_callback` / `unavailable_utxo_callback` both call `verified_deposit_utxo.insert(...)` and panic if the key is already present (`"Already deposit utxo"`), so the deposit path is permanently blocked. [8](#0-7) 

5. A new `request_refund` is also blocked: `request_refund_callback` checks `verified_deposit_utxo` and panics with `"UTXO already verified via deposit"`. [9](#0-8) 

The UTXO is permanently locked: no deposit path, no new refund path, no operator cleanup path.

### Impact Explanation

The deposit UTXO is permanently unrecoverable without a contract upgrade. The user's BTC is locked on-chain with no mechanism to mint nBTC or return the BTC. This matches **Critical — permanent locking of user funds**.

### Likelihood Explanation

`execute_refund` is public and callable by anyone after the timelock. MPC signing stalling is a realistic operational condition: the chain-signature contract can be paused for upgrades or security incidents, or the signing callback can fail to be invoked. The design comment explicitly anticipates re-execution after a consensus branch change, confirming the scenario is expected — yet the implementation provides no escape hatch. Likelihood is **Medium** (requires a signing stall that does not self-resolve), but the impact when triggered is irreversible.

### Recommendation

1. **Add an operator-only `force_remove_refund_pending_info` function** that removes the `btc_pending_infos` entry AND clears `verified_deposit_utxo` for the associated key when the pending info is in `PendingSign` stage and the refund request is still active. This restores the pre-`execute_refund` state.
2. **Alternatively**, before inserting into `btc_pending_infos` in `finalize_refund_with_psbt`, check whether an entry already exists and remove it (replacing the stale signing attempt) rather than panicking.
3. **Decouple `verified_deposit_utxo` insertion from `execute_refund`**: only insert into `verified_deposit_utxo` once the signed transaction is broadcast (i.e., after MPC signing succeeds), not at PSBT-creation time.

### Proof of Concept

```
1. request_refund(deposit_msg, refund_address, tx_bytes, vout, proof, None)
   → refund_requests[key] = RefundRequest { executed: false }

2. [timelock elapses]

3. execute_refund(key, None)
   → finalize_refund_with_psbt:
       btc_pending_infos[pending_id] = BTCPendingInfo { state: Refund(PendingSign) }
       verified_deposit_utxo.insert(key)
       refund_requests[key].executed = true

4. [MPC signing never completes — chain-signature contract paused]

5. execute_refund(key, None)  // re-attempt
   → load_refund_request_for_execute: passes (executed == true)
   → finalize_refund_with_psbt: PANICS "pending info already exist"

6. remove_refund_pending_tx_id(pending_id)
   → internal_remove_refund_pending_tx_id: PANICS "refund request still active"

7. reject_refund(key)  // DAO/Operator
   → refund_requests.remove(key)  // only this

8. remove_refund_pending_tx_id(pending_id)  // now succeeds
   → btc_pending_infos.remove(pending_id)

9. verified_deposit_utxo still contains key
   → verify_deposit_callback: PANICS "Already deposit utxo"
   → request_refund_callback: PANICS "UTXO already verified via deposit"
   // UTXO permanently locked, no recovery path
```

```rust
    pub(crate) fn internal_execute_refund(
        &mut self,
        utxo_storage_key: String,
        timelock_sec: u64,
        _chain_specific_data: Option<ChainSpecificData>,
    ) -> PromiseOrValue<()> {
        let refund_request = self.load_refund_request_for_execute(&utxo_storage_key, timelock_sec);
        let RefundExecutionInputs {
            outpoint,
            deposit_output,
            refund_amount,
        } = self.refund_execution_inputs(&refund_request);
        let refund_output = self.build_refund_output(&refund_request.refund_address, refund_amount);

        let mut psbt = PsbtWrapper::new(vec![outpoint], vec![refund_output]);
        psbt.set_input_utxo(vec![deposit_output]);

        let caller = env::predecessor_account_id();
        self.finalize_refund_with_psbt(
            caller,
            refund_request,
            psbt,
            refund_amount,
            utxo_storage_key,
        );
        PromiseOrValue::Value(())
    }
```
