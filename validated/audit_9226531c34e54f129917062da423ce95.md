### Title
Unprotected `new()` Initializer Allows Front-Running to Seize `bridge_id` and Enable Unauthorized nBTC Minting — (`contracts/nbtc/src/lib.rs`)

---

### Summary

The `nbtc` token contract's `new()` constructor is callable by **any** NEAR account during the window between contract deployment and initialization. An attacker who calls it first can supply their own account as `bridge_id`, after which they satisfy the only guard on `mint()` (`assert_bridge`) and can mint arbitrary nBTC to any recipient.

---

### Finding Description

`contracts/nbtc/src/lib.rs` exposes a public `#[init]` constructor: [1](#0-0) 

```rust
#[init]
pub fn new(
    controller: AccountId,
    bridge_id: AccountId,
    ...
) -> Self {
    require!(!env::state_exists(), "Already initialized");
    ...
    Self { controller, bridge_id, ... }
}
```

The only guard is `require!(!env::state_exists(), ...)`. There is **no check** that the caller is the contract account, the deployer, or any privileged party. Any NEAR account can call `new()` before the legitimate deployer does.

Once the attacker controls `bridge_id`, the sole authorization check on `mint()` is trivially satisfied: [2](#0-1) 

```rust
fn assert_bridge(&self) {
    require!(self.bridge_id == env::predecessor_account_id(), "Not Allow");
}
```

`mint()` itself performs no further validation: [3](#0-2) 

```rust
pub fn mint(&mut self, mint_account_id: AccountId, mint_amount: U128, ...) {
    self.assert_bridge();
    self.mint_inner(&mint_account_id, mint_amount);
    ...
}
```

The same root cause applies to `satoshi-bridge`'s `new()`, where the caller is unconditionally granted `super_admin`, `DAO`, `PauseManager`, and `UnpauseManager` roles: [4](#0-3) 

---

### Impact Explanation

An attacker who front-runs `new()` on the `nbtc` contract and supplies their own account as `bridge_id` can immediately call `mint()` with arbitrary `mint_account_id` and `mint_amount`, creating unbacked nBTC out of thin air. This constitutes **unauthorized minting of nBTC**, directly matching the critical impact class.

Additionally, by supplying their own account as `controller`, the attacker can call `upgrade_and_migrate()` and `attach_full_access_key()` to permanently take over the contract. [5](#0-4) 

---

### Likelihood Explanation

In NEAR Protocol, deployment and initialization are separate transactions unless the deployer explicitly batches them. Any deployment script, CI pipeline, or manual process that issues a `DeployContract` action and then a separate `FunctionCall` to `new()` creates an exploitable window. A mempool-watching bot or a racing transaction submitted immediately after the deploy transaction is confirmed is sufficient to exploit this. No privileged access, leaked keys, or third-party compromise is required — only the ability to submit a NEAR transaction.

---

### Recommendation

Restrict the `new()` initializer to the contract's own account (i.e., the deployer) by asserting `env::predecessor_account_id() == env::current_account_id()` at the top of the function, or — preferably — always batch the `DeployContract` and `new()` call in a single atomic NEAR batch transaction so no external account can race the initialization.

```rust
#[init]
pub fn new(controller: AccountId, bridge_id: AccountId, ...) -> Self {
    require!(
        env::predecessor_account_id() == env::current_account_id(),
        "Only the contract account may initialize"
    );
    require!(!env::state_exists(), "Already initialized");
    ...
}
```

---

### Proof of Concept

1. Deployer broadcasts `DeployContract` for `nbtc` WASM — state is empty, `new()` has not been called.
2. Attacker observes the deploy transaction and immediately broadcasts:
   ```
   nbtc.new({
     controller: "attacker.near",
     bridge_id:  "attacker.near",
     name: "nBTC", symbol: "nBTC", decimals: 8
   })
   ```
3. Attacker's `new()` call lands first (or races successfully). `bridge_id` is now `attacker.near`.
4. Attacker calls:
   ```
   nbtc.mint({
     mint_account_id: "attacker.near",
     mint_amount: "100000000000",   // 1000 nBTC
     protocol_fee: "0",
     relayer_account_id: "attacker.near",
     relayer_fee: "0"
   })
   ```
5. `assert_bridge()` passes because `predecessor == bridge_id == attacker.near`.
6. `mint_inner` credits 1000 nBTC to `attacker.near` with no BTC backing. [6](#0-5)
