### Title
Peras Certificate and Vote Validation Unconditionally Accepts All Inputs, Enabling Unauthorized Chain-Weight Boost - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The degenerate `BlockSupportsPeras` instance, which is the active catch-all instance for all `StandardHash blk` types, implements both `validatePerasCert` and `validatePerasVote` as stubs that unconditionally return `Right` (success) regardless of the certificate or vote content. An unprivileged peer can send crafted Peras certificates or votes with valid voter IDs but invalid cryptographic signatures via the Peras object-diffusion miniprotocol. These pass validation, are stored, and can cause the node to forge certificates for adversary-chosen blocks, granting them an unearned Peras weight boost that manipulates chain selection.

### Finding Description

**Root cause — `validatePerasCert` always succeeds:**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
```

This is the degenerate catch-all instance (`instance StandardHash blk => BlockSupportsPeras blk`). Every certificate, regardless of its content or cryptographic validity, is accepted and assigned the full `perasWeight params` boost. No signature, round number, boosted-block, or quorum check is performed.

**Root cause — `validatePerasVote` skips signature verification:**

```haskell
validatePerasVote _params stakeDistr vote
    | Just stake <- lookupPerasVoteStake vote stakeDistr =
        Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
    | otherwise =
        Left PerasValidationErr
```

The only check is whether the voter ID appears in the stake distribution. The cryptographic signature is never verified. A vote with a valid voter ID but a completely fabricated signature passes validation and is stored with the voter's full ledger stake.

**Production call site — `processVotes` in `ObjectPool/PerasVote.hs`:**

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
```

This is the inbound vote handler for the Peras vote diffusion miniprotocol. It calls the degenerate `validatePerasVote` directly. After validation, valid votes are passed to `PerasVoteDB.addVote` or `ChainDB.addPerasVoteWithAsyncCertHandling`, which calls `updatePerasRoundVoteStates` → `votesReachQuorum` → `forgePerasCert` when the accumulated stake crosses the quorum threshold.

**Analog to the external report:**

| External report | This codebase |
|---|---|
| `_calculatePortfolioRatio` returns `0` when debt is zero | `validatePerasCert` returns `Right` for every certificate |
| Guard `ratio <= redCoeff` always passes because `0 <= redCoeff` | Guard "is this a valid cert?" always passes because the function never returns `Left` |
| Debt-free account is liquidated | Adversary-chosen block receives a Peras weight boost |

### Impact Explanation

**Impact: High — Chain selection bug via unauthorized Peras certificate acceptance.**

A Peras certificate stored in a block grants that block a `perasWeight` boost in `wsvTotalWeight`, used by `preferAnchoredCandidate` and `compareAnchoredFragments` during chain selection. An adversary who can inject a certificate for a block of their choice causes honest nodes to assign that block extra weight, potentially making the adversarial chain preferred over the honest chain. This is a chain-selection integrity violation reachable by an unprivileged peer.

### Likelihood Explanation

**Likelihood: High.**

The Peras vote diffusion miniprotocol is a public peer-to-peer interface. Any connected peer can send `PerasVote` objects. The stake distribution is public on-chain data. An attacker needs only to:
1. Read the current stake distribution to find high-stake voter IDs.
2. Craft `PerasVote` objects with those IDs targeting an adversarial block, with any byte string as the signature.
3. Send them to a target node.

No privileged keys, stake majority, or cryptographic break is required.

### Recommendation

The degenerate instance must be replaced with a real implementation before Peras is activated. Specifically:

1. `validatePerasCert` must verify the aggregate BLS signature over the certificate's round number and boosted block, and confirm the certificate references a known block within the valid round window.
2. `validatePerasVote` must verify the per-voter cryptographic signature (e.g., via `verifyVoteSignature`) before accepting the vote, and must reject votes with zero stake.

The existing `EveryoneVotes` committee implementation in `implVerifyVote` demonstrates the correct pattern: it calls `verifyVoteSignature` and then checks `nonZero voterStake` before returning `Right`.

### Proof of Concept

```
1. Attacker connects to a target node as a peer via the Peras vote diffusion miniprotocol.

2. Attacker reads the public stake distribution and identifies voter IDs V1, V2, ..., Vn
   with combined stake exceeding (perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin).

3. For each Vi, attacker crafts:
     PerasVote { pvVoteRound    = currentRound
               , pvVoteBlock    = adversarialBlockPoint
               , pvVoteVoterId  = Vi }
   with an arbitrary (invalid) signature field.

4. Attacker sends these votes to the target node.

5. processVotes calls validatePerasVote for each vote.
   validatePerasVote looks up Vi in the stake distribution, finds a non-zero stake,
   and returns Right (ValidatedPerasVote { vpvVoteStake = stakeOf(Vi) }).
   No signature check is performed.

6. Each vote is passed to updatePerasRoundVoteStates.
   Once totalVoteStake >= quorumThreshold + safetyMargin,
   votesReachQuorum returns Just, and forgePerasCert is called.

7. A ValidatedPerasCert is stored for adversarialBlockPoint with boost = perasWeight params.

8. compareAnchoredFragments / preferAnchoredCandidate now assigns adversarialBlockPoint
   extra weight via weightBoostOfFragment, potentially causing the node to prefer
   the adversarial chain over the honest chain.

processVotes ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
