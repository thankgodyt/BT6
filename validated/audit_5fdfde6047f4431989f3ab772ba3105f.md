### Title
Unauthenticated `deposit_msg` in `request_refund` Allows Any Caller to Front-Run and Redirect a User's BTC Refund to an Attacker-Controlled Address - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary

The `request_refund` function accepts a caller-supplied `refund_address` with no authentication that the caller is the intended `recipient_id` of the deposit. When a user's `deposit_msg` was constructed with `refund_address: None`, any NEAR account can call `request_refund` first — using the same public `deposit_msg` but substituting an attacker-controlled BTC address — and register a refund request that redirects the user's BTC to the attacker. This is a direct analog to the Squads unauthenticated `create_key` front-running pattern: an unauthenticated public parameter is used to derive/register a critical state entry, and any caller can hijack that entry with their own parameters.

### Finding Description

`request_refund` is publicly callable by any NEAR account. It accepts a `deposit_msg` (which determines the deposit address path) and a separate `refund_address` parameter (the BTC destination for the refund). The only constraint on `refund_address` is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [1](#0-0) 

This check only fires when `deposit_msg.refund_address` is `Some(...)`. When it is `None`, the caller-supplied `refund_address` is accepted unconditionally and stored verbatim in the `RefundRequest`:

```rust
let refund_request = RefundRequest {
    ...
    refund_address,   // ← attacker-controlled
    ...
};
self.data_mut().refund_requests.insert(utxo_storage_key, refund_request.into());
``` [2](#0-1) 

The `deposit_msg` itself is fully public: `get_user_deposit_address` emits it as a NEAR event every time a user queries their deposit address:

```rust
Event::LogDepositAddress {
    deposit_msg,
    path,
    deposit_address: deposit_address.clone(),
}.emit();
``` [3](#0-2) 

The deposit address is derived deterministically from the `deposit_msg` hash:

```rust
pub fn get_deposit_path(deposit_msg: &DepositMsg) -> String {
    let deposit_msg_string = serde_json::to_string(&deposit_msg).unwrap();
    hex::encode(env::sha256(deposit_msg_string.as_bytes()))
}
``` [4](#0-3) 

So an attacker who reads the NEAR event log has everything needed to call `request_refund` with the victim's `deposit_msg` and their own BTC address.

The `request_refund` function itself has no caller-identity check — no `#[trusted_relayer]` attribute on the method, no check that `env::predecessor_account_id()` matches `deposit_msg.recipient_id`:

```rust
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn request_refund(
    &mut self,
    deposit_msg: DepositMsg,
    refund_address: String,
    ...
) -> Promise {
``` [5](#0-4) 

The only post-registration protection is the `unsafe_refund_timelock_sec` — a longer timelock applied when `deposit_msg.refund_address` is `None` — which gives the DAO time to reject suspicious requests:

```rust
} else {
    // Refund address supplied by caller of `request_refund`: longer
    // timelock to give DAO/Operator time to reject suspicious requests.
    config.unsafe_refund_timelock_sec
}
``` [6](#0-5) 

This is a reactive, off-chain mitigation, not a protocol-level authentication fix.

### Impact Explanation

If the DAO fails to reject the malicious refund request within `unsafe_refund_timelock_sec`, any account (including the attacker) can call `execute_refund` and the bridge's MPC pipeline will sign a Bitcoin transaction sending the victim's BTC to the attacker's address. The victim's BTC is permanently redirected. Even if the DAO does reject, the victim's refund is blocked until they can re-submit — but the attacker can repeat the front-run indefinitely, permanently denying the victim access to their BTC refund.

This maps to: **Medium — attacker-triggered temporary locking of bridged funds** (guaranteed), with escalation to **Critical — theft of user BTC** if the DAO does not act within the timelock.

### Likelihood Explanation

- The `deposit_msg` is emitted as a public NEAR event, so the attacker has all inputs needed without any privileged access.
- The BTC transaction is public on-chain.
- `request_refund` requires only a small NEAR storage deposit (anti-spam fee), which is a negligible cost for an attacker targeting a large BTC deposit.
- The attack does not require front-running in the strict mempool sense — the attacker can call `request_refund` at any time before the victim does, since unfinalized UTXOs can sit for extended periods.
- The DAO's rejection window is finite and depends on human vigilance; a targeted attack timed to weekends or high-activity periods reduces the chance of timely rejection.

### Recommendation

**Short term:** In `internal_request_refund`, when `deposit_msg.refund_address` is `None`, require that `env::predecessor_account_id()` matches `deposit_msg.recipient_id`. This ensures only the intended recipient can register a refund with an arbitrary BTC address.

**Long term:** Consider requiring `deposit_msg.refund_address` to always be pre-committed in the `deposit_msg` (i.e., disallow `None`), so the refund destination is locked at deposit-address-derivation time and cannot be supplied by any third party at refund time.

### Proof of Concept

1. Alice calls `get_user_deposit_address` with `DepositMsg { recipient_id: "alice.near", refund_address: None, ... }`. The contract emits a `LogDepositAddress` event containing the full `deposit_msg`.
2. Alice sends 1 BTC to the returned deposit address. The relayer never finalizes the deposit.
3. Eve reads Alice's `deposit_msg` from the NEAR event log and the BTC `tx_bytes` from the Bitcoin blockchain.
4. Eve calls `request_refund(deposit_msg=Alice's, refund_address="eve_btc_addr", tx_bytes=..., vout=0, proof=...)` with a small NEAR storage deposit. The contract verifies the BTC inclusion proof, confirms the output script matches Alice's deposit address, and stores `RefundRequest { refund_address: "eve_btc_addr", ... }`.
5. Alice attempts `request_refund` — it fails: `"Refund request already exists for this UTXO"`. [7](#0-6) 
6. The DAO does not notice or does not act within `unsafe_refund_timelock_sec`.
7. Eve calls `execute_refund(utxo_storage_key)`. The bridge builds a PSBT paying 1 BTC to `"eve_btc_addr"`, submits it to MPC signing, and broadcasts it. Alice's BTC is stolen. [8](#0-7)
