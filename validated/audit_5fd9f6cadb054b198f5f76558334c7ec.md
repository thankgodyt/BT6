Looking at the withdrawal flow in `contracts/satoshi-bridge/src/nbtc/burn.rs` and `contracts/satoshi-bridge/src/btc_pending_info.rs`, I need to trace the state machine and gas allocation to find an analog to M-1's "callback runs out of gas after external call, leaving state permanently stuck."

### Title
Insufficient Gas Allocation to `verify_withdraw_burn_callback` Can Permanently Brick Bridge State After Committed nBTC Burn — (File: `contracts/satoshi-bridge/src/nbtc/burn.rs`)

---

### Summary

The `verify_withdraw_burn_callback` is allocated a fixed `GAS_FOR_WITHDRAW_BURN_CALL_BACK = 20 Tgas`. If this callback panics (e.g., due to out-of-gas for large Zcash transactions with Orchard bundles), the preceding `ext_nbtc::burn` call is already committed on-chain, but the callback's state-cleanup is reverted. The `BTCPendingInfo` is left permanently in `PendingBurn` stage with no retry path, the bridge's change UTXOs are never registered, and the UTXO pool is silently corrupted.

---

### Finding Description

The withdrawal finalization is a two-step cross-contract call chain:

**Step 1 — Burn promise construction** (`verify_withdraw_burn_promise`):

```
ext_nbtc::burn(...)          ← GAS_FOR_BURN_CALL = 5 Tgas
  .then(verify_withdraw_burn_callback)  ← GAS_FOR_WITHDRAW_BURN_CALL_BACK = 20 Tgas
``` [1](#0-0) [2](#0-1) 

**Step 2 — State transition before the burn** (`to_pending_burn_stage`): The state is moved from `PendingVerify` → `PendingBurn` *before* the burn promise is dispatched, inside `internal_verify_withdraw_callback`. [3](#0-2) 

**Step 3 — Callback work** (`verify_withdraw_burn_callback`): On the success path, the callback must:
1. Decode the full signed transaction bytes via `WrappedTransaction::decode` (expensive for large Zcash/Orchard transactions)
2. Iterate all outputs and write each change UTXO to storage
3. Handle RBF state (additional storage reads/removes)
4. Update fee accounting fields
5. Call `internal_remove_btc_pending_info`
6. Emit events [4](#0-3) [5](#0-4) 

**The gap**: In NEAR's promise model, if `verify_withdraw_burn_callback` panics (OOG or otherwise), the callback's state changes are reverted, but the `ext_nbtc::burn` receipt is already committed in a prior execution context. The result:

- nBTC is permanently burned (user's tokens gone from the token contract)
- `BTCPendingInfo` reverts to `PendingBurn` stage
- Change UTXOs are never registered into the bridge's UTXO pool
- `btc_pending_verify_list` and `rbf_txs` are not cleaned up

**No retry path from `PendingBurn`**: The only retry mechanism in the codebase is the `else` branch at line 150–152, which calls `to_pending_verify_stage()` when the *burn call itself* fails. There is no function that accepts a `PendingBurn`-stage entry and re-dispatches the burn. `verify_withdraw_v2` requires `PendingVerify` state and will panic if called on a `PendingBurn` entry. [6](#0-5) [7](#0-6) 

---

### Impact Explanation

If the callback panics after a successful burn:

1. **Bridge UTXO pool is silently corrupted**: Change outputs from the confirmed BTC transaction are never registered. The bridge permanently loses track of its own on-chain funds, reducing the effective UTXO pool below the true on-chain balance.
2. **Stuck pending state**: The `BTCPendingInfo` entry remains in `PendingBurn` indefinitely. No public function can advance or remove it. Operator intervention (upgrade or manual state surgery) is required.
3. **nBTC supply reduced without corresponding UTXO accounting**: The peg invariant (nBTC supply ↔ bridge-controlled BTC) is broken for the affected change amount.

This matches the allowed medium impact: *"stuck bridge state requiring operator intervention"* and *"broken callback rollback."*

---

### Likelihood Explanation

The trigger is the callback running out of its fixed 20 Tgas budget. This is realistic in the following scenario:

- **Zcash withdrawals with Orchard shielded outputs**: The wiki explicitly notes that Zcash transactions containing Orchard bundles are "significantly larger than standard Bitcoin transactions." The callback calls `WrappedTransaction::decode(tx_bytes, chain)` on the full signed transaction bytes, which for an Orchard-bundle transaction can be several kilobytes. Borsh/binary deserialization of large byte arrays is gas-intensive in NEAR Wasm.
- **Multiple change outputs**: A withdrawal transaction with several change outputs causes multiple storage writes inside the output-iteration loop, each consuming additional gas.
- **RBF path**: The RBF branch adds extra storage reads and removes (`internal_remove_btc_pending_info` on the original tx), further increasing gas consumption.

The user controls the PSBT structure (inputs/outputs) submitted at `ft_on_transfer` time, so a user can legitimately construct a withdrawal that maximizes callback gas consumption without violating any bridge validation rules. [8](#0-7) 

---

### Recommendation

1. **Add a `retry_burn` entry point** that accepts a `tx_id` in `PendingBurn` stage and re-dispatches `verify_withdraw_burn_promise`. This mirrors the replayability guarantee the bridge provides for `PendingVerify`.
2. **Increase `GAS_FOR_WITHDRAW_BURN_CALL_BACK`** to account for worst-case Zcash/Orchard transaction decoding and multi-output iteration. Benchmark the callback with maximum-size Zcash transactions to establish a safe floor.
3. **Move `to_pending_burn_stage()` into the callback** (after confirming `is_promise_success()`), so that a callback panic leaves the state in `PendingVerify` rather than `PendingBurn`, preserving the retry path.

---

### Proof of Concept

1. User initiates a Zcash withdrawal with Orchard shielded outputs, producing a large signed transaction (several KB of `tx_bytes_with_sign`).
2. MPC signs the transaction; state moves to `PendingVerify`.
3. Relayer calls `verify_withdraw_v2`; light client confirms inclusion; `to_pending_burn_stage()` is called; `verify_withdraw_burn_promise` is dispatched.
4. `ext_nbtc::burn` executes successfully in its receipt — nBTC is burned and committed.
5. `verify_withdraw_burn_callback` begins execution with 20 Tgas. `WrappedTransaction::decode` on the large Zcash/Orchard transaction bytes, combined with multiple UTXO storage writes and RBF state cleanup, exhausts the 20 Tgas budget. The callback panics with OOG.
6. NEAR runtime reverts the callback's state changes. `BTCPendingInfo` remains in `PendingBurn`. Change UTXOs are not registered.
7. No public function can advance the `PendingBurn` entry. The bridge's UTXO pool is permanently short the change amount. Operator intervention is required. [1](#0-0) [9](#0-8) [3](#0-2)
