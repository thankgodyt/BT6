Audit Report

## Title
Missing Pre-Lock Normalization Check Permanently Freezes Bridged Funds - (File: `near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer` locks user tokens after only verifying `fee.fee < amount`, without checking that `normalize_amount(amount_without_fee())` is non-zero. When the post-fee amount is below the decimal-conversion threshold, `sign_transfer` permanently panics with `InvalidAmountToTransfer`, and no cancel or refund path exists to recover the locked tokens.

## Finding Description
`normalize_amount` performs floor division to convert NEAR-side token amounts to destination-chain representation:

```rust
// near/omni-bridge/src/lib.rs L2784-2787
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

The code comment at L2781-2783 explicitly acknowledges: *"When fee = 0, dust stays locked/burned."* However, the issue extends beyond dust — the entire transferred amount can be locked when it falls below the normalization threshold.

`init_transfer_internal` stores the transfer and locks tokens after only checking:

```rust
// near/omni-bridge/src/lib.rs L554-557
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```

No check is performed that `normalize_amount(amount_without_fee()) > 0`. Later, `sign_transfer` computes and validates the normalized amount:

```rust
// near/omni-bridge/src/lib.rs L475-485
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

`amount_without_fee()` is a simple subtraction:

```rust
// near/omni-types/src/lib.rs L593-595
pub fn amount_without_fee(&self) -> Option<u128> {
    self.amount.0.checked_sub(self.fee.fee.0)
}
```

If `amount_without_fee()` is positive but less than `10^(origin_decimals - decimals)`, `normalize_amount` returns 0 and `sign_transfer` always panics — permanently.

**No recovery path exists.** `remove_transfer_message` is called in:
- `sign_transfer_callback` (L657) — only when fee is zero AND the MPC signature succeeds, which never happens because `sign_transfer` panics before reaching the MPC call.
- `fin_transfer_callback` area (L1094) — requires a valid finalization proof from the destination chain, which cannot exist since the transfer was never signed.

`update_transfer_fee` (L399-401) only allows the fee to be **increased** (`fee.fee >= current_fee.fee`), which further reduces `amount_without_fee()` and cannot rescue the transfer.

## Impact Explanation
This is a **Critical** impact: permanent freezing of bridged funds. Any user who initiates a transfer where `amount_without_fee() < 10^(origin_decimals - decimals)` will have their tokens locked in the bridge contract with no recovery mechanism. The tokens are neither transferred to the destination chain nor refundable to the sender.

## Likelihood Explanation
The condition is reachable by any unprivileged user calling `ft_transfer_call`. No special role or permission is required. The NEAR (24 decimals) to EVM (18 decimals) configuration is a standard production deployment, making the minimum threshold 1,000,000 NEAR-side units — a realistic amount for low-value transfers. Users can also accidentally trigger this by setting a fee that leaves a sub-threshold remainder (e.g., amount = 1,500,000, fee = 1,000,000 → `amount_without_fee()` = 500,000 → normalized = 0).

## Recommendation
In `init_transfer_internal`, after constructing the `TransferMessage`, look up the token's registered `Decimals` and compute `normalize_amount(amount_without_fee())` before locking tokens. If the result is zero, return the full `amount` from `ft_on_transfer` (non-zero return triggers the NEP-141 automatic refund to the sender) instead of storing the transfer message.

Alternatively, implement a `cancel_transfer` function callable by the original sender that removes the pending transfer message and refunds the locked tokens via `ft_transfer`, which would also mitigate other stuck-transfer scenarios.

## Proof of Concept
1. Register a token with `origin_decimals = 24`, `decimals = 18` (divisor = 1,000,000).
2. Call `ft_transfer_call` with `amount = 500_000`, `fee = 0`, recipient on Ethereum.
3. `init_transfer` passes the `fee < amount` check (0 < 500,000 ✓) and locks 500,000 units.
4. Relayer calls `sign_transfer` → `normalize_amount(500_000, {24, 18})` = 500,000 / 1,000,000 = 0 → panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.
5. No cancel path exists. Tokens remain locked permanently.

Variant: `amount = 1_500_000`, `fee = 1_000_000` → `amount_without_fee()` = 500,000 → same result. `update_transfer_fee` cannot help because it only allows fee increases.
