### Title
Unconditional Peras Certificate Acceptance Bypasses All Cryptographic Validation, Enabling Unprivileged Peer to Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` implementation is a stub that unconditionally returns `Right` for every certificate received, performing zero cryptographic checks. This stub is wired directly into the live node-to-node `PerasCertDiffusion` mini-protocol handler. Any unprivileged peer can send a crafted `PerasCert` for an arbitrary block in an arbitrary round, have it accepted as "validated," and trigger chain selection with an illegitimate Peras weight boost applied to that block.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must verify a received Peras certificate before it is stored and acted upon. The universal degenerate instance — which is the only instance in the codebase and therefore the one used in production — implements this gate as an unconditional pass-through:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No BLS aggregate signature is verified, no quorum of eligible voters is checked, no voter eligibility proofs are examined, and no round-number bounds are enforced. Every `PerasCert` — regardless of content — is stamped `ValidatedPerasCert` and assigned the full `perasWeight` boost.

This stub is consumed directly in both certificate pool writers:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [2](#0-1) [3](#0-2) 

Both `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB` pass this stub as the `validateCert` argument to `processCerts`. The `processCerts` function calls `validateCert` on every inbound certificate and, if it returns `Right`, immediately adds it to the database and triggers chain selection: [4](#0-3) 

The production node-to-node handler wires `makePerasCertPoolWriterFromChainDB` directly into the `hPerasCertDiffusionClient` handler, making this reachable from any connected peer:

```haskell
, hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
``` [5](#0-4) 

Note the asymmetry with vote validation: the vote diffusion handler explicitly passes `PerasVoteStakeDistr mempty` (an empty distribution), which causes all votes to fail `validatePerasVote` via `lookupPerasVoteStake`. Certificates have no equivalent guard — they are accepted unconditionally. [6](#0-5)

### Impact Explanation

A `ValidatedPerasCert` carrying a `vpcCertBoost` is stored in the ChainDB and used by chain selection to apply a Peras weight boost to the `pcCertBoostedBlock`. An attacker who injects a certificate for a non-canonical or adversarial block causes the receiving node to prefer that block over the honest chain, constituting a chain selection safety failure. The attacker can target any block hash and any round number, and can repeat the attack for multiple rounds to sustain the preference for the adversarial chain.

This matches the allowed impact scope: **High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.**

---

### Likelihood Explanation

The `PerasCertDiffusion` mini-protocol is enabled in the production node-to-node handler and is reachable from any peer that establishes a connection. No special privileges, keys, or stake are required. The attacker only needs to send a well-formed CBOR-encoded `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock`. The `PerasCert` wire format is public and straightforward to construct. [7](#0-6) 

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real cryptographic validator that:

1. Verifies the aggregate BLS signature (`pcSignature`) against the aggregate public key derived from the declared voters (`pcVoters`) and the signed message `hashVoteSignature pcRoundNo pcBoostedBlock`.
2. Checks that the declared voters constitute a quorum (total stake above the configured threshold).
3. Verifies each voter's eligibility proof (persistent membership or VRF output for non-persistent members).
4. Enforces that `pcRoundNo` falls within the valid range relative to the current chain tip.

Until the real implementation is in place, the `hPerasCertDiffusionClient` handler should reject all inbound certificates (analogous to how the vote handler rejects all votes via the empty stake distribution), rather than accepting them unconditionally.

### Proof of Concept

**Attacker-controlled entry path:**

1. Attacker connects to a target node and establishes a node-to-node session.
2. Attacker sends a `PerasCert` message over the `PerasCertDiffusion` mini-protocol with:
   - `pcCertRound` = any round number (e.g., the current Peras round)
   - `pcCertBoostedBlock` = hash of an adversarial or non-canonical block
3. The message reaches `hPerasCertDiffusionClient` → `objectDiffusionInbound` → `makePerasCertPoolWriterFromChainDB` → `processCerts`.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`.
5. `validatePerasCert` returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })` without inspecting the certificate content.
6. The certificate is passed to `ChainDB.addPerasCertAsync`, which stores it and triggers chain selection.
7. Chain selection applies the Peras weight boost to the adversarial block, causing the node to prefer the non-canonical chain.
