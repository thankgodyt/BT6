### Title
Peras Certificate and Vote Validation Unconditionally Accepts Unverified Input — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance — which is the only active instance for all block types — implements `validatePerasCert` as an unconditional `Right` that accepts every certificate without any check, and implements `validatePerasVote` without verifying the vote signature or checking for zero stake. This is directly analogous to the oracle price not being checked for zero: a value returned from an external source is accepted without adequate verification. An unprivileged peer can submit crafted Peras certificates or forged votes via the object-diffusion mini-protocol, causing honest nodes to accept them and apply an unearned weight boost to an adversarial chain fragment.

---

### Finding Description

**Root cause — `validatePerasCert`:**

The `BlockSupportsPeras` class requires implementors to supply `validatePerasCert`. The only concrete instance in the codebase is the catch-all `instance StandardHash blk => BlockSupportsPeras blk` at line 320. Its implementation is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

Every certificate, regardless of content or origin, is unconditionally accepted and assigned the full `perasWeight` boost. No cryptographic check, no quorum check, no round-number check, no block-point check is performed.

**Root cause — `validatePerasVote`:**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
```

The `_params` argument is discarded (note the underscore). The only check is whether the voter's ID appears in the stake distribution via `lookupPerasVoteStake`. There is no signature verification (the `PerasVote` data type carries no signature field at all), and there is no check that the returned `stake` is non-zero. A voter whose `PerasVoteStake` is `0 :: Rational` in the distribution passes validation and produces a `ValidatedPerasVote` with zero weight.

**Attacker-controlled entry path:**

`processVotes` in `ObjectPool/PerasVote.hs` is the inbound handler for Peras votes received from peers over the object-diffusion mini-protocol. It calls `validatePerasVote` for each vote and, on success, forwards the `ValidatedPerasVote` to `PerasVoteDB.addVote`. Inside `implAddVote`, `updatePerasRoundVoteStates` accumulates votes and calls `forgePerasCert` once `votesReachQuorum` returns `Just`. The forged `ValidatedPerasCert` is then stored and used by `weightBoostOfPoint` / `weightBoostOfFragment` to inflate the `WeightedSelectView` of the targeted chain fragment during chain selection.

Because `validatePerasVote` does not verify signatures, an adversary who knows any voter ID present in the stake distribution can submit votes on behalf of that voter for an arbitrary block without possessing the voter's private key. By submitting enough such forged votes to exceed the quorum threshold, the adversary causes the node to forge a certificate for an adversarial block and apply the full `perasWeight` boost to it.

---

### Impact Explanation

Peras certificates provide a `PerasWeight` boost that is added to the block number when comparing chain fragments in `WeightedSelectView.preferCandidate`. A fraudulently obtained certificate for an adversarial block causes honest nodes to prefer that block over a longer honest chain, constituting a chain-selection safety failure. The `vpcCertBoost` field is set to `perasWeight params` unconditionally by `validatePerasCert`, so the full configured boost is applied regardless of whether the certificate is legitimate.

---

### Likelihood Explanation

The object-diffusion mini-protocol for Peras votes is reachable by any unprivileged peer. `processVotes` is the production inbound handler wired into `makePerasVotePoolWriterFromChainDB`, which is used in the node kernel. The only barrier is knowing a voter ID present in the current `PerasVoteStakeDistr`, which is derivable from the public ledger state. No key material, no stake, and no operator access is required.

---

### Recommendation

1. **`validatePerasCert`**: Implement real certificate validation — verify the aggregate signature over the claimed voter set, check that the voter set meets the quorum threshold against the current stake distribution, and verify the round number and block point are consistent with the current chain state. Return `Left` on any failure.

2. **`validatePerasVote`**: Add a signature field to `PerasVote` and verify it in `validatePerasVote`. Additionally, reject votes whose resolved `PerasVoteStake` is zero:

```haskell
validatePerasVote params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr
  , stake > 0
  , verifyVoteSignature vote = Right ValidatedPerasVote { ... }
  | otherwise = Left PerasValidationErr
```

### Proof of Concept

1. Observe the current `PerasVoteStakeDistr` from the public ledger state to obtain any valid `PerasVoterId`.
2. Construct `PerasVote { pvVoteRound = r, pvVoteBlock = adversarialPoint, pvVoteVoterId = knownId }` for a target adversarial block.
3. Send enough such votes (one per known voter ID) via the object-diffusion protocol to exceed `perasQuorumStakeThreshold`.
4. `processVotes` calls `validatePerasVote`; each vote passes because `lookupPerasVoteStake` finds the voter ID and no signature is checked.
5. `updatePerasRoundVoteStates` → `votesReachQuorum` → `forgePerasCert` produces a `ValidatedPerasCert` with `vpcCertBoost = perasWeight params` for the adversarial block.
6. `weightBoostOfFragment` adds this boost to the adversarial fragment's `WeightedSelectView`, causing `preferCandidate` to prefer it over the honest chain. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7)

processVotes ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
