Audit Report

## Title
Detached `send_tokens` with No Failure Callback Permanently Locks Relayer Funds - (File: near/omni-bridge/src/lib.rs)

## Summary
In both `process_fin_transfer_to_other_chain` and `utxo_fin_transfer_fast`, the bridge irrevocably commits fast-transfer state (marking it finalised or removing it) and then fires the relayer repayment via `send_tokens(...).detach()` with no failure callback. If the underlying `ft_transfer` or `mint` call fails, the fast-transfer record is already gone and the relayer's fronted tokens are permanently frozen inside the bridge with no recovery path.

## Finding Description

**`process_fin_transfer_to_other_chain`** (lines 2027–2040):
```rust
if let Some(relayer) = recipient {
    self.send_tokens(token, relayer, amount, "")
        .detach();                                         // no failure callback
    self.mark_fast_transfer_as_finalised(&fast_transfer.id()); // state committed
}
```
The fast-transfer record is marked finalised synchronously after the detached promise is scheduled. NEAR's execution model means the promise result is never observed; if `send_tokens` fails, the state is already committed and cannot be rolled back.

**`utxo_fin_transfer_fast`** (lines 2529–2548):
```rust
let amount = if fast_transfer.get_destination_chain() == ChainKind::Near {
    self.remove_fast_transfer(&fast_transfer.id());   // state committed
    fast_transfer.amount
} else {
    self.mark_fast_transfer_as_finalised(&fast_transfer.id()); // state committed
    ...
};
self.send_tokens(...).detach();   // no failure callback
```
Same pattern: state is mutated before the promise fires, and `.detach()` ensures no callback ever runs.

**`send_tokens`** (lines 2102–2106) resolves to `ft_transfer` when `msg` is empty and the token is not a deployed token:
```rust
ext_token::ext(token)
    .with_attached_deposit(ONE_YOCTO)
    .with_static_gas(FT_TRANSFER_GAS)
    .ft_transfer(recipient, amount, None)
```
`ft_transfer` panics if the recipient has no storage deposit for the token. The developers themselves acknowledge the gap at line 2484:
```rust
// TODO: check how to deal with failed send_tokens
return self.utxo_fin_transfer_fast(fast_transfer, status, utxo_fin_transfer_msg);
```

## Impact Explanation
A relayer who executes a fast transfer fronts the recipient's tokens from their own balance. The bridge owes those tokens back when the canonical proof arrives. If `send_tokens` fails after state is committed, the relayer's fronted tokens remain inside the bridge contract with no mechanism to retry or recover them. This constitutes **permanent freezing of bridged funds**, matching the Critical allowed impact scope.

## Likelihood Explanation
`ft_transfer` requires the recipient (the relayer) to have a storage deposit for the specific token contract. A relayer operating across many tokens may not have pre-registered storage for every token they relay. Additionally, any transient panic in the token contract (e.g., a paused token) produces the same outcome. The developer-acknowledged TODO comment confirms this is a known, unresolved risk. The scenario requires no attacker — it can be triggered by ordinary operational conditions.

## Recommendation
Replace `.detach()` with a proper callback that handles both success and failure. On failure, the fast-transfer record should be restored (un-finalised or re-inserted) so the repayment can be retried:

```rust
self.send_tokens(token, relayer, amount, "")
    .then(
        Self::ext(env::current_account_id())
            .with_static_gas(REPAY_RELAYER_CALLBACK_GAS)
            .repay_relayer_callback(fast_transfer_id, relayer, amount),
    );
// In callback: if promise failed, restore fast_transfer state for retry
```
Apply the same pattern in both `process_fin_transfer_to_other_chain` and `utxo_fin_transfer_fast`, and remove the TODO comment once resolved.

## Proof of Concept
1. Relayer calls `ft_transfer_call` on the bridge, triggering `fast_fin_transfer` with a NEAR recipient. Bridge records the fast transfer and sends tokens to the recipient from the relayer's balance.
2. Canonical proof arrives; trusted relayer calls `fin_transfer` → `fin_transfer_callback` → `process_fin_transfer_to_other_chain`.
3. Bridge calls `send_tokens(token, relayer, amount, "").detach()` and immediately calls `mark_fast_transfer_as_finalised`.
4. The `ft_transfer` to the relayer fails because the relayer has no storage deposit for this token contract.
5. No callback fires. The fast-transfer record is permanently finalised. The relayer's fronted tokens remain locked in the bridge with no retry or refund path.
6. Same sequence applies via `utxo_fin_transfer` → `utxo_fin_transfer_fast` for UTXO-origin transfers, where `remove_fast_transfer` is called before the detached promise.
