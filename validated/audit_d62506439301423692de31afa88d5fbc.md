Audit Report

## Title
Fee-on-Transfer Token Mis-Accounting in `initTransfer`: Emitted Amount Exceeds Actual Locked Amount — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
The `initTransfer` function in `OmniBridge.sol` calls `safeTransferFrom` with the caller-supplied `amount` and then emits that same `amount` in the `InitTransfer` event without measuring the actual balance delta. For fee-on-transfer ERC-20 tokens, the contract receives `amount - token_fee` while the event records `amount`. The NEAR `fin_transfer_callback` reads the emitted `amount` from the prover result and mints that full value to the recipient, creating a persistent escrow shortfall that grows with each transfer and eventually renders the EVM escrow insolvent.

## Finding Description
In `OmniBridge.sol`, the non-bridge-token, non-custom-minter path of `initTransfer` executes:

```solidity
IERC20(tokenAddress).safeTransferFrom(
    msg.sender,
    address(this),
    amount          // input parameter, not actual received amount
);
``` [1](#0-0) 

Immediately after, the function emits:

```solidity
emit BridgeTypes.InitTransfer(
    msg.sender,
    tokenAddress,
    currentOriginNonce,
    amount,         // same input parameter, not balance delta
    fee,
    nativeFee,
    recipient,
    message
);
``` [2](#0-1) 

No balance-before/balance-after check is performed anywhere in the function. There is also no on-chain token whitelist enforced in `initTransfer` that would exclude fee-on-transfer tokens.

On the NEAR side, `fin_transfer_callback` reads the `InitTransferMessage` produced by the EVM prover, which parses the `amount` field directly from the emitted event log:

```rust
let transfer_message = TransferMessage {
    ...
    amount: Self::denormalize_amount(init_transfer.amount.0, decimals).into(),
    ...
};
``` [3](#0-2) 

This `amount` is then passed to `send_tokens` via `amount_without_fee()`, which mints or transfers the full event-recorded value to the recipient:

```rust
self.send_tokens(
    token.clone(),
    recipient,
    U128(transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee)),
    &msg,
)
``` [4](#0-3) 

For a fee-on-transfer token with a 1% transfer fee, each `initTransfer(amount = X)` call causes the EVM contract to hold `0.99X` tokens while NEAR mints `X` tokens (minus bridge fee). The shortfall accumulates linearly with each transfer.

The same structural flaw exists in the Starknet bridge, where `transfer_from` is called with `amount` and the same `amount` is emitted in the `InitTransfer` event without a balance delta check. [5](#0-4) 

## Impact Explanation
This is a **Critical** escrow mis-accounting vulnerability. Every `initTransfer` call with a fee-on-transfer token causes NEAR to mint more tokens than the EVM contract holds. Over N transfers, the EVM escrow holds `N × (amount - token_fee)` tokens while NEAR has minted `N × amount` — a cumulative shortfall of `N × token_fee`. Users who bridge back from NEAR to EVM after the escrow is depleted will find the EVM contract unable to release their full amount, resulting in permanent loss of bridged funds for late redeemers. This matches the Critical impact class: escrow mis-accounting that changes user and protocol balances, and permanent freezing/loss of bridged funds.

## Likelihood Explanation
The bridge is permissionless with respect to which ERC-20 tokens can be locked — `initTransfer` accepts any token address with no on-chain whitelist. Fee-on-transfer tokens (deflationary tokens, reflection tokens, tokens with protocol fees) are a well-established and widely deployed token class. Any unprivileged external user can trigger this path by calling `initTransfer` with such a token; no privileged access is required. The attack is repeatable and the damage compounds with each call.

## Recommendation
Replace the fixed-`amount` transfer with a balance-delta pattern in `OmniBridge.sol`:

```solidity
uint256 balanceBefore = IERC20(tokenAddress).balanceOf(address(this));
IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
uint256 actualReceived = IERC20(tokenAddress).balanceOf(address(this)) - balanceBefore;
emit BridgeTypes.InitTransfer(..., uint128(actualReceived), ...);
```

Apply the same balance-delta fix to the Starknet `init_transfer` function. The NEAR `fin_transfer` path already reads the event-recorded value from the proof, so no NEAR-side changes are needed — the fix propagates end-to-end once the EVM and Starknet events emit the correct `actualReceived` value.

## Proof of Concept
1. Deploy or use any ERC-20 token that deducts a 1% fee on every `transferFrom` (e.g., a reflection token).
2. Call `OmniBridge.initTransfer(tokenAddress, 1_000_000, 0, 0, nearRecipient, "")`.
3. The contract receives `990_000` tokens; the `InitTransfer` event emits `amount = 1_000_000`.
4. A relayer submits the EVM Merkle proof to NEAR `fin_transfer`.
5. NEAR `fin_transfer_callback` reads `amount = 1_000_000` from the prover result and mints `1_000_000` tokens to `nearRecipient`.
6. Repeat N times. After N transfers the EVM escrow holds `N × 990_000` tokens but NEAR has minted `N × 1_000_000` — a `N × 10_000` token shortfall.
7. The first `~N × 0.99` redeemers can withdraw normally; the remaining redeemers find the EVM contract insolvent and suffer permanent loss.

A local integration test can be written using the existing `near/omni-tests` framework: deploy a mock ERC-20 with a 1% `transferFrom` fee, call `initTransfer`, simulate `fin_transfer_callback` with the emitted `amount`, and assert that the EVM contract balance is less than the total NEAR-minted supply.
