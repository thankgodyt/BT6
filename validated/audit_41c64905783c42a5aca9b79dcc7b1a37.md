### Title
Peras Certificate Validation Unconditionally Accepts Any Peer-Supplied Certificate, Enabling Unauthorized Chain-Selection Boost - (`SupportsPeras.hs`)

---

### Summary

The catch-all `BlockSupportsPeras` instance — the only production instance — implements `validatePerasCert` as an unconditional `Right`, accepting every inbound Peras certificate without any cryptographic or quorum proof. An unprivileged peer can craft a `PerasCert` for any round and any block hash, have it accepted by the node, and cause chain selection to award that block the full configured `perasWeight` boost, potentially making the node switch to an attacker-controlled fork.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must verify a certificate received from a peer before it is stored and used in chain selection. The only concrete instance in the codebase is the catch-all:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

No field of the certificate is inspected: not the round number, not the boosted block, and not any aggregate BLS signature proving that a quorum of committee members actually voted. The function always returns `Right` and assigns the full protocol-configured boost weight `perasWeight params`.

The inbound network path wires this directly to the Peras certificate diffusion mini-protocol. In `NodeToNode.hs`, the handler for inbound certificates is:

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      ...
``` [2](#0-1) 

`makePerasCertPoolWriterFromChainDB` calls `processCerts` with `validatePerasCert mkPerasParams` as the validation function:

```haskell
opwAddObjects = \certs ->
    processCerts
      systemTime
      (ChainDB.getPerasCertIds chainDB)
      -- TODO replace when actual plumbing is in place
      (validatePerasCert mkPerasParams)
      (void . ChainDB.addPerasCertAsync chainDB)
      certs
``` [3](#0-2) 

`processCerts` passes every certificate that is not already in the DB through `validateCert`. Because `validatePerasCert` always returns `Right`, every certificate passes, is timestamped, and is forwarded to `addPerasCertAsync`: [4](#0-3) 

`addPerasCertAsync` stores the certificate in `PerasCertDB` and triggers `chainSelectionForBlock` for the boosted block: [5](#0-4) 

Chain selection then uses `vpcCertBoost` — set to `perasWeight params` by the stub — to compute the `WeightedSelectView` total weight for the boosted block's chain fragment:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [6](#0-5) 

The `PerasWeightSnapshot` is built directly from the stored `vpcCertBoost` values: [7](#0-6)

### Impact Explanation

An unprivileged peer can submit a single crafted `PerasCert` (two CBOR fields: a round number and a block point) for any block in the node's VolatileDB. The node will:

1. Accept it unconditionally.
2. Store it with boost weight `perasWeight params`.
3. Re-run chain selection for the boosted block.
4. Potentially switch its preferred chain to a fork containing that block, if the boost tips the `WeightedSelectView` comparison.

This is a **chain-selection manipulation** vulnerability: an attacker with no stake and no cryptographic keys can cause an honest node to prefer a non-canonical fork, violating the Peras security assumption that only a legitimately certified block (backed by a quorum of committee votes) receives a boost.

The analog to the original report is exact: just as a user could renew a protection position for the maximum token value without having originally purchased that amount, a peer here can claim the maximum Peras boost for any block without having the votes to back it up.

---

### Likelihood Explanation

The Peras certificate diffusion mini-protocol is an active node-to-node handler wired in `NodeToNode.hs`. Any peer that connects to the node can send a `PerasCert` message. The `PerasCert` type carries only a round number and a block point — no signature field exists — so crafting a valid-looking certificate requires no cryptographic material whatsoever. The attack is trivially reproducible on a private testnet with two nodes.

---

### Recommendation

`validatePerasCert` must verify:

1. **Aggregate BLS signature**: the certificate must carry a valid aggregate signature over the voted block, verifiable against the public keys of the claimed committee members.
2. **Quorum proof**: the aggregate must represent stake above the configured `perasQuorumStakeThreshold`.
3. **Round/slot consistency**: the certified block's slot must fall within the correct Peras round window.

Until the full BLS/committee plumbing (tracked in issue #73 and #120) is in place, the stub should return `Left PerasValidationErr` (reject all) rather than `Right` (accept all), so that the network handler disconnects from peers sending unverifiable certificates rather than acting on them.

---

### Proof of Concept

On a private two-node testnet running the current code:

1. Node A connects to Node B via the Peras certificate diffusion mini-protocol.
2. Node A observes that Node B's VolatileDB contains block `B_fork` on a competing fork (obtainable via ChainSync headers).
3. Node A sends a single `PerasCert { pcCertRound = R, pcCertBoostedBlock = point(B_fork) }` to Node B.
4. Node B's `processCerts` calls `validatePerasCert mkPerasParams cert` → `Right (ValidatedPerasCert { vpcCertBoost = perasWeight params })`.
5. Node B stores the certificate and calls `chainSelectionForBlock` for `B_fork`.
6. Chain selection computes `wsvTotalWeight` for the fork's fragment, which now includes `perasWeight params` extra weight.
7. If `perasWeight params` exceeds the length difference between the two forks, Node B switches to the fork containing `B_fork`.

No stake, no keys, no prior relationship with Node B is required.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
