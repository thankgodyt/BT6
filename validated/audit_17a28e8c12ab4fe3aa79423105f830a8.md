Peras Certificate Validation Bypass: `validatePerasCert` Unconditionally Accepts All Inbound Certificates — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production inbound Peras certificate handler calls `validatePerasCert` on every certificate received from a peer. The current implementation of `validatePerasCert` in the degenerate `BlockSupportsPeras` instance unconditionally returns `Right` — it performs zero cryptographic or structural checks. Any certificate sent by an unprivileged peer is accepted, stored in the `PerasCertDB`, and used to boost chain-selection weight, allowing an attacker to steer an honest node toward a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must be passed before a certificate is admitted into the node's state. The only deployed instance — a catch-all for every `StandardHash blk` — is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature, quorum proof, committee membership, or round-number plausibility check is performed. Every certificate is stamped `ValidatedPerasCert` and assigned the full `perasWeight` boost.

This function is called directly in the production inbound pipeline via `processCerts`:

```haskell
(validatePerasCert mkPerasParams)  -- TODO replace when actual plumbing is in place
``` [2](#0-1) [3](#0-2) 

`processCerts` is the function that handles every batch of certificates arriving from a remote peer. It partitions results into valid/invalid; because `validatePerasCert` never returns `Left`, every certificate lands in the "valid" bucket and is added to the `PerasCertDB`: [4](#0-3) 

Certificates stored in the `PerasCertDB` are consumed by `implGetWeightSnapshot`, which feeds `PerasWeightSnapshot` into chain selection. The `preferAnchoredCandidate` function uses `weightedSelectView` — which sums `weightBoostOfFragment` over the candidate suffix — to decide whether to switch chains: [5](#0-4) [6](#0-5) 

The analog to the Amp.sol report is direct: just as `operatorTransferByPartition` accepted a transfer when *either* the sender was an operator *or* the allowance was sufficient (OR instead of AND), `validatePerasCert` here requires *no* condition at all — the logical gate is entirely absent.

### Impact Explanation

**High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain.**

A malicious peer can craft a `PerasCert` naming any block point and any round number, send it over the ObjectDiffusion miniprotocol, and have it accepted without any check. The accepted certificate is stored with the full `perasWeight` boost (currently `PerasWeight 15`, equivalent to 15 extra blocks of chain length). When chain selection next runs, `preferAnchoredCandidate` will compare the boosted candidate against the honest chain and may switch to the attacker's fork. Because Peras weight is additive and unbounded in the number of fake certificates an attacker can inject, the attacker can manufacture an arbitrarily large weight advantage for any target chain, overriding the honest longest-chain rule.

---

### Likelihood Explanation

**High.** The ObjectDiffusion miniprotocol for Peras certificates is a public peer-to-peer interface. Any node that connects to an honest node can send certificate batches. No stake, key material, or privileged access is required. The attack requires only the ability to open a network connection and send a well-formed (but cryptographically fabricated) `PerasCert` message. The code path from network ingress to chain-selection influence is fully wired in production (`makePerasCertPoolWriterFromChainDB` → `processCerts` → `PerasCertDB.addCert` → `implGetWeightSnapshot` → `ChainSel`).

---

### Recommendation

1. Implement real cryptographic validation inside `validatePerasCert` before the ObjectDiffusion miniprotocol is enabled on any network. At minimum, verify the quorum certificate's aggregate signature against the claimed committee and the claimed boosted block, and verify that the round number is plausible given the current chain state.
2. Until real validation is in place, gate the ObjectDiffusion inbound handler so that it rejects all certificates (returns a hard error rather than silently accepting them), preventing the stub from being exploited.
3. Track the open issue (`cardano-peras/issues/120`) as a security-blocking item, not merely a correctness TODO.

---

### Proof of Concept

1. Connect to a target node's ObjectDiffusion endpoint for Peras certificates.
2. Send a `PerasCert` with `pcCertRound = <any round>` and `pcCertBoostedBlock = <point of an adversarial fork block>`.
3. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = PerasWeight 15 })` unconditionally.
4. The certificate is stored in `PerasCertDB` via `addCert`.
5. On the next chain selection event, `implGetWeightSnapshot` returns a snapshot containing the fake boost; `weightBoostOfFragment` adds `PerasWeight 15` to the adversarial fragment's total weight.
6. `preferAnchoredCandidate` compares `wsvTotalWeight` and, if the adversarial chain's boosted weight exceeds the honest chain's weight, returns `ShouldSwitch`, causing the node to adopt the adversarial fork.

Repeat step 2 with additional fake certificates on the same block to accumulate weight without bound. [7](#0-6) [8](#0-7) [9](#0-8)

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
