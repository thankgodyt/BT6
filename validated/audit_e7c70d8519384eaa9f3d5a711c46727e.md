### Title
Incorrect Operation Order in `safe_mint` Permanently Locks Minted Tokens When Recipient Is Unregistered - (File: contracts/nbtc/src/lib.rs)

### Summary
In the `nBTC` token contract, `safe_mint` calls `internal_deposit` to mint tokens to the bridge's own account **before** checking whether the recipient `account_id` is registered. When the recipient is not registered, the function returns early with `U128(0)` without burning or recovering the already-minted tokens. Those tokens are permanently stranded in the bridge's balance, inflating total supply without BTC backing, while the depositing user receives nothing.

### Finding Description
In `contracts/nbtc/src/lib.rs`, the `safe_mint` function executes in this order:

```rust
// Line 112: tokens are minted to bridge's own account FIRST
self.token.internal_deposit(&self.bridge_id, amount.into());

// Line 114-116: THEN checks if recipient is registered
if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0));  // returns without cleanup
}
``` [1](#0-0) 

When `account_id` is not registered in the token contract, the function returns `U128(0)` after having already credited `amount` tokens to `self.bridge_id`. There is no subsequent burn or reversal. The minted tokens remain in the bridge's balance indefinitely.

By contrast, the regular `mint` path uses `mint_inner`, which auto-registers the account before depositing:

```rust
fn mint_inner(&mut self, account_id: &AccountId, amount: U128) {
    if self.token.accounts.get(account_id).is_none() {
        self.token.internal_register_account(account_id);
    }
    self.token.internal_deposit(account_id, amount.into());
``` [2](#0-1) 

`safe_mint` performs neither auto-registration nor a pre-check before minting, making the registration check at line 114 a dead guard that only prevents the transfer while leaving the mint irreversible.

### Impact Explanation
- **User fund loss**: A user who deposits BTC and whose NEAR account is not registered in the nBTC contract will have their deposit consumed by the bridge (the BTC UTXO is marked used) but will receive zero nBTC. The deposit is unrecoverable without operator intervention.
- **Supply inflation**: `ft_total_supply` increases by `amount` with no corresponding BTC backing. The bridge holds orphaned tokens that can be spent in future operations, breaking the 1:1 BTC-to-nBTC invariant.

This matches **Critical: Significant loss, theft, destruction, or permanent locking of user or protocol funds.**

### Likelihood Explanation
Any user who has never interacted with the nBTC contract (i.e., has no storage deposit / registered account) and submits a deposit proof that routes through `safe_mint` (deposits with a `msg` post-action) will trigger this path. New bridge users are the common case. The attacker-controlled entry is the deposit proof submission, which is a fully public, permissionless operation.

### Recommendation
Perform the registration check **before** calling `internal_deposit`, mirroring the `mint_inner` pattern:

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "...");

    // Check BEFORE minting
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));
    }

    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ... transfer logic
}
```

Alternatively, auto-register the account (as `mint_inner` does) so the early return path is never reached.

### Proof of Concept
1. User `alice.near` has never registered a storage deposit in the nBTC contract (account not in `token.accounts`).
2. Alice deposits BTC to the bridge address and submits a deposit proof with a `msg` field (triggering the `safe_mint` code path).
3. The bridge calls `safe_mint("alice.near", 100_000_000, Some("..."))`.
4. `internal_deposit(&self.bridge_id, 100_000_000)` executes — bridge's nBTC balance increases by 100,000,000 satoshis; `ft_total_supply` increases by the same.
5. `self.token.accounts.get(&"alice.near")` returns `None`.
6. Function returns `U128(0)`. Alice receives 0 nBTC.
7. The 100,000,000 satoshi-worth of nBTC sits permanently in the bridge's balance. Alice's BTC UTXO is consumed. Alice has no recourse without operator intervention. [3](#0-2)
