### Title
`deployToken()` Uses `create` Opcode for Bridge Token Proxy Deployment, Enabling Reorg-Based Token Address Hijacking - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

### Summary

The `deployToken()` function in `OmniBridge.sol` deploys new `ERC1967Proxy` bridge token contracts using the Solidity `new` keyword (the `create` opcode). The resulting proxy address depends solely on the `OmniBridge` contract's nonce. On EVM chains susceptible to block reorganizations (Arbitrum, Base, BSC, Polygon — all confirmed deployment targets), an attacker can exploit a reorg to deploy a different token at the same address that a legitimate token previously occupied, corrupting the bridge's token registry and causing `finTransfer` to mint the wrong token to recipients.

### Finding Description

In `OmniBridge.deployToken()`, the bridge token proxy is deployed as:

```solidity
address bridgeTokenProxy = address(
    new ERC1967Proxy(
        tokenImplementationAddress,
        abi.encodeWithSelector(
            BridgeToken.initialize.selector,
            metadata.name,
            metadata.symbol,
            decimals
        )
    )
);
``` [1](#0-0) 

`new ERC1967Proxy(...)` compiles to the `create` opcode. The deployed address is `keccak256(rlp(OmniBridge_address, nonce))[12:]` — it depends only on the `OmniBridge` contract's nonce, not on any token-specific data. There is no `create2` salt derived from `metadata.token`.

After deployment, the bridge registers the proxy:

```solidity
isBridgeToken[address(bridgeTokenProxy)] = true;
ethToNearToken[address(bridgeTokenProxy)] = metadata.token;
nearToEthToken[metadata.token] = address(bridgeTokenProxy);
``` [2](#0-1) 

`finTransfer()` uses `isBridgeToken[payload.tokenAddress]` to decide whether to mint:

```solidity
} else if (isBridgeToken[payload.tokenAddress]) {
    IBridgeToken(payload.tokenAddress).mint(payload.recipient, payload.amount);
``` [3](#0-2) 

The `finTransfer` signature covers `payload.tokenAddress` (the raw EVM address), not the NEAR token ID string. After a reorg, if a different token occupies the same EVM address, the original NEAR-signed `finTransfer` payload remains cryptographically valid and will mint the replacement token.

### Impact Explanation

**Critical.** After a reorg:

1. Token A's `deployToken` transaction is reverted; the `OmniBridge` nonce resets to `N`.
2. An attacker (holding a valid NEAR-signed metadata payload for their own token B) calls `deployToken` for token B. Token B's proxy is deployed at the same address `X` (nonce `N`).
3. The bridge now records `nearToEthToken["token-b"] = X` and `isBridgeToken[X] = true`.
4. The relayer re-broadcasts the original `finTransfer` transaction (NEAR-signed for token A at address `X`, with a destination nonce not yet marked used because the reorg wiped `completedTransfers`).
5. `ECDSA.recover` succeeds (the signed address is still `X`), `isBridgeToken[X]` is true, and `IBridgeToken(X).mint(recipient, amount)` mints token B tokens to the recipient instead of token A tokens.
6. Token A's bridge mapping (`nearToEthToken["token-a"]`) is permanently absent — all future token A transfers are broken.

The result is: recipients receive the wrong token, and token A's bridge path is permanently destroyed.

### Likelihood Explanation

The bridge is confirmed deployed on Arbitrum One, Base, BSC, and Polygon (all shown in `.openzeppelin/` manifests). These chains have documented reorg histories. The attacker only needs: (a) a legitimately obtained NEAR-signed metadata payload for any token they control, and (b) to submit their `deployToken` call before the original transaction is re-mined after a reorg. No privileged access is required.



### Recommendation

Replace `new ERC1967Proxy(...)` with a `create2` deployment using a salt derived from the NEAR token ID:

```solidity
bytes32 salt = keccak256(abi.encodePacked(metadata.token));
address bridgeTokenProxy = address(
    new ERC1967Proxy{salt: salt}(
        tokenImplementationAddress,
        abi.encodeWithSelector(
            BridgeToken.initialize.selector,
            metadata.name,
            metadata.symbol,
            decimals
        )
    )
);
```

This makes the proxy address a deterministic function of the NEAR token ID. A reorg cannot change which token occupies a given address, because the address is bound to the token identity rather than the deployer nonce.

### Proof of Concept

1. Observe `OmniBridge` at nonce `N` on Arbitrum.
2. Legitimate relayer calls `deployToken(sigA, metadataA)` → token A proxy deployed at address `X`; bridge records `nearToEthToken["token-a"] = X`.
3. NEAR signs a `finTransfer` for token A at `X`; relayer broadcasts it.
4. A reorg removes both transactions; `OmniBridge` nonce reverts to `N`; `completedTransfers[nonce]` is cleared.
5. Attacker calls `deployToken(sigB, metadataB)` (valid NEAR signature for attacker's own token B) → token B proxy deployed at `X` (same nonce `N`); bridge records `nearToEthToken["token-b"] = X`, `isBridgeToken[X] = true`.
6. Relayer re-broadcasts the original `finTransfer` for token A at `X`.
7. Signature check passes (address `X` is in the signed payload). `isBridgeToken[X]` is true. `IBridgeToken(X).mint(recipient, amount)` executes — minting token B tokens to the recipient.
8. Token A's bridge mapping is permanently absent; token A transfers are bricked. [4](#0-3)
