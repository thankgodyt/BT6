### Title
Static `max_btc_gas_fee` Cap Renders RBF Inoperable During Bitcoin Network Congestion, Locking User nBTC - (File: contracts/satoshi-bridge/src/psbt.rs)

---

### Summary

The bridge enforces a static absolute-satoshi ceiling (`max_btc_gas_fee`) on every Bitcoin transaction gas fee, including RBF replacements. When Bitcoin mempool fees spike above this ceiling, a user whose withdrawal is already pending cannot bump the fee via RBF — the same cap is re-checked on every RBF attempt — leaving their nBTC permanently locked in the pending state until a DAO governance action raises the ceiling.

---

### Finding Description

`check_withdraw_psbt` (the shared fee-validation routine) enforces:

```
gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee
``` [1](#0-0) 

`max_btc_gas_fee` is a plain `u128` field in `Config` — a value fixed at deployment time with no on-chain oracle or dynamic adjustment: [2](#0-1) 

The RBF path (`internal_withdraw_rbf`) does **not** bypass this check. It calls `check_withdraw_rbf_psbt_valid`, which in turn calls the same `check_withdraw_psbt`: [3](#0-2) 

So the ceiling that caused the original transaction to be under-priced is the same ceiling that blocks every subsequent RBF attempt. There is no escape hatch short of a DAO `update_config` call.

The cancel-withdraw RBF path (`check_cancel_withdraw_rbf_psbt_valid`) calls `check_psbt_output_all_change_address` with `is_cancel = true`, which skips the gas-fee range check: [4](#0-3) 

However, the cancel path redirects all funds back to the bridge's change address — the user receives nothing — and requires the DAO when the gas fee exceeds the user's balance. It is not a user-accessible remedy for a stuck withdrawal.

---

### Impact Explanation

When a user calls `ft_transfer_call` to withdraw, `ft_on_transfer` returns `U128(0)`, consuming the nBTC immediately. The nBTC is not returned to the user; it is held by the bridge pending Bitcoin confirmation. If the Bitcoin transaction is stuck (fee too low for current mempool) and every RBF attempt is rejected because the required fee now exceeds `max_btc_gas_fee`, the user's nBTC remains locked in `BTCPendingInfo` indefinitely. Resolution requires a DAO governance transaction to raise `max_btc_gas_fee`, followed by a new RBF submission — an operator-gated process with no user-side remedy.

**Impact class:** Medium — attacker-triggered (or congestion-triggered) temporary locking of bridged funds; stuck bridge state requiring operator intervention.

---

### Likelihood Explanation

Bitcoin mempool fee spikes are a well-documented, recurring phenomenon (e.g., Ordinals inscription waves, halving periods). A deployment-time `max_btc_gas_fee` that was reasonable at launch can become insufficient within days. Any user who initiated a withdrawal just before a fee spike will find both their original transaction and all RBF attempts rejected by the contract, with no self-service remedy.

---

### Recommendation

Replace the absolute-satoshi ceiling with a per-byte fee-rate ceiling (e.g., `max_fee_rate_sat_per_vbyte`) and compute the allowed maximum dynamically from the actual transaction weight. Alternatively, allow the user-supplied `max_gas_fee` parameter (already accepted in `ft_on_transfer`) to override `max_btc_gas_fee` for RBF submissions, so a user can voluntarily pay more to unblock their own pending withdrawal without requiring a DAO config change.

---

### Proof of Concept

1. DAO deploys bridge with `max_btc_gas_fee = 50_000` sat (reasonable at launch).
2. Alice calls `ft_transfer_call` with 200 000 nBTC; `ft_on_transfer` accepts a PSBT with `gas_fee = 10_000` sat and returns `U128(0)` — Alice's nBTC is consumed.
3. Bitcoin mempool spikes; the 10 000-sat transaction is stuck. Miners now require ≥ 80 000 sat.
4. Alice calls `withdraw_rbf_chain_specific` with a new PSBT setting `gas_fee = 80_000` sat.
5. `check_withdraw_rbf_psbt_valid` → `check_withdraw_psbt` → `require!(gas_fee <= config.max_btc_gas_fee)` → **panics** with `"Invalid gas fee (80000). valid range: [10000, 50000]."` [1](#0-0) 
6. Alice's nBTC remains locked. She has no further recourse until the DAO raises `max_btc_gas_fee` via `update_config`.
