### Title
Hardcoded `boundX = 3` Violates `taylorExpCmpFirstNonLower` Contract, Corrupting Peras Non-Persistent Seat Allocation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/LS.hs`)

### Summary

`localSortitionNumSeats` passes the literal constant `3` as the `boundX` argument to `taylorExpCmpFirstNonLower`, but the function's own contract requires `boundX = e^{|x|}`. The actual exponent `x = -lambda` grows with voter stake and committee size, so whenever `lambda > ln(3) ≈ 1.099` the error bound is underestimated, the Taylor convergence test fires at the wrong iteration, and the returned seat count is wrong. Both `implVerifyVote` and `implVerifyCert` in `WFALS.hs` gate non-persistent Peras vote acceptance on this count, so the bug is reachable by any peer that sends a crafted vote or certificate.

### Finding Description

`taylorExpCmpFirstNonLower` computes a bounded Taylor expansion of `e^x` and compares it against a list of thresholds. Its error term on each iteration is:

```
errorTerm = abs (err' * boundX)
```

The inline contract is unambiguous: [1](#0-0) 

The caller passes `boundX = 3` and `x = -lambda`: [2](#0-1) 

`lambda` is the Poisson parameter for the voter:

```
lambda = numNonPersistentVoters * voterStake / totalNonPersistentStake
``` [3](#0-2) 

For `boundX = 3` to satisfy the contract, `e^lambda ≤ 3` must hold, i.e. `lambda ≤ ln(3) ≈ 1.099`. This is violated by any voter whose expected seat count exceeds ~1.1. With a committee of 300 non-persistent voters, any voter holding more than ~0.37 % of non-persistent stake already exceeds this threshold. Large pools (e.g. 5 % stake, 300-voter committee) produce `lambda = 15`, making `e^lambda ≈ 3.3 × 10^6` while `boundX = 3` is used.

When `boundX` is too small, `errorTerm` is too small, so the convergence test in `decideOne` fires prematurely: [4](#0-3) 

- Line 167: `cmp >= acc' + errorTerm` → `Stop` (declares "ABOVE", returns current index as first non-lower). With an underestimated error band this fires when the true `e^{-lambda}` is still below `cmp`, granting the voter more seats than the Poisson distribution warrants.
- Line 168: `cmp < acc' - errorTerm` → `Below` (declares "BELOW", advances to next threshold). With an underestimated error band this fires when the true `e^{-lambda}` is actually above `cmp`, denying the voter seats they are entitled to.

The code itself acknowledges the uncertainty with an open TODO: [5](#0-4) 

### Impact Explanation

`localSortitionNumSeats` is called in two production verification paths in `WFALS.hs`:

**`implVerifyVote`** — called for every incoming `WFALSNonPersistentVote`: [6](#0-5) 

**`implVerifyCert`** — called for every non-persistent voter entry in an incoming `WFALSCert`: [7](#0-6) 

In both paths, `nonZero numSeats == Nothing` rejects the vote/certificate as `ZeroNonPersistentSeats`, and a non-zero result accepts it. A wrong seat count therefore directly controls whether a non-persistent Peras vote or certificate is accepted or rejected:

- **False positive (ineligible voter accepted):** When the underestimated error band causes `decideOne` to return `Stop` prematurely at index `i` while the true `e^{-lambda}` is still below `orders[i]`, the voter is credited with `i` seats they do not deserve. An ineligible non-persistent voter can cast a vote that passes `implVerifyVote`, or be counted in a quorum inside `implVerifyCert`, corrupting Peras certificate validity.

- **False negative (eligible voter rejected):** The symmetric case silently drops legitimate votes, weakening quorum formation.

The false-positive direction is the critical one: it constitutes a bypass of the Peras voting committee eligibility check, allowing unauthorized votes and certificates to be accepted by honest nodes.

### Likelihood Explanation

The condition `lambda > ln(3)` is met by any non-persistent voter whose expected seat count exceeds ~1.1. With a realistic committee of 300 non-persistent voters, this threshold is crossed by any pool holding more than ~0.37 % of non-persistent stake — a condition satisfied by the majority of active Cardano stake pools. The bug is therefore triggered on every election for every large pool participating as a non-persistent voter. No special attacker capability is required beyond submitting a vote or certificate through the standard Peras diffusion path.

### Recommendation

Replace the hardcoded `3` with the correct value `e^lambda`, computed using a sufficiently accurate fixed-point exponential (e.g. the existing `Cardano.Ledger.NonIntegral` facilities):

```haskell
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      (exp lambda)   -- correct: e^{|x|} where x = -lambda
      orders
      (-lambda)
```

Alternatively, follow the approach used by `checkLeaderNatValue` in `cardano-ledger` and derive the bound analytically from the known range of `lambda`. The open issue at https://github.com/tweag/cardano-peras/issues/234 should be resolved before this code is used in production.

### Proof of Concept

Consider a committee with:
- `numNonPersistentVoters = 300`
- voter holds 5 % of non-persistent stake → `lambda = 300 × 0.05 = 15`
- correct `boundX = e^15 ≈ 3,269,446`; used `boundX = 3`

At iteration `n`, `errorTerm = |err_n| × 3` instead of `|err_n| × 3,269,446`. The convergence test fires roughly when `|err_n| × 3 < ε` rather than `|err_n| × 3,269,446 < ε`, i.e. about 14.7 iterations too early (since `ln(3,269,446/3) / ln(15) ≈ 14.7`). The partial sum at that premature stopping point can be above or below the true `e^{-15} ≈ 3.06 × 10^{-7}` depending on parity, causing `decideOne` to return `Stop` (ABOVE) when the true value is BELOW, granting the voter a non-zero seat count and allowing their vote to pass `implVerifyVote` / `implVerifyCert` even if the Poisson draw should have yielded zero seats.
