### Title
DAO `cancel_withdraw` permanently blocked by user filling `btc_pending_sign_ids` to capacity — (`contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary
`cancel_withdraw` checks `require_pending_sign_capacity` against the **withdrawal owner's** account before inserting the cancel-RBF pending ID. A user can keep their `btc_pending_sign_ids` at the maximum (default: 1) by maintaining a second withdrawal in `PendingSign` stage, causing every DAO `cancel_withdraw` call on their stuck withdrawal to revert. Bridge UTXOs tied to the stuck withdrawal cannot be reclaimed.

### Finding Description
`cancel_withdraw` (lines 285–299, `api/bridge.rs`) retrieves the `account_id` of the withdrawal owner and calls `require_pending_sign_capacity(&user_account_id)`. This guard enforces that `pending_sign_count() < get_max_pending_sign_txs(account_id)`. The default limit returned by `get_max_pending_sign_txs` for any account without an explicit override is **1**.

The cancel flow creates a new `WithdrawCancelRbf` `BTCPendingInfo` entry that must be inserted into the user's `btc_pending_sign_ids`. The capacity check is there to ensure room for this entry. However, the user can fill that slot by creating a second withdrawal (W2) immediately after W1 moves to `PendingVerify`. Since W2 occupies the single slot, the capacity check for canceling W1 always fails.

### Impact Explanation
The DAO/Operator loses the ability to cancel any stuck withdrawal belonging to a user who deliberately keeps their `btc_pending_sign_ids` at capacity. The UTXOs locked in the stuck withdrawal's `vutxos` cannot be reclaimed by the protocol. If the user's W1 transaction never confirms on-chain (e.g., due to a deliberately low fee), those UTXOs are permanently locked. This matches: **Medium — attacker-triggered temporary/permanent locking of bridged funds**.

### Likelihood Explanation
The attack requires only two sequential public withdrawals. The default limit of 1 makes it trivially reproducible. No privileged access, leaked keys, or external dependencies are needed. The user controls the timing of W2 creation relative to W1's signing.

### Recommendation
Remove the `require_pending_sign_capacity` check from `cancel_withdraw` (and `cancel_active_utxo_management`). The cancel-RBF pending ID should be inserted into the **DAO/Operator caller's** `btc_pending_sign_ids` (or a protocol-owned account), not the withdrawal owner's. Alternatively, add a DAO/Operator role bypass inside `require_pending_sign_capacity` when the caller is privileged and the operation is a cancel.

### Proof of Concept
```
1. Set user's pending_tx_limits to 1 (or rely on the default).
2. User calls ft_on_transfer → withdraw (W1). btc_pending_sign_ids = {W1}.
3. MPC signs W1. btc_pending_sign_ids = {} (W1 now in PendingVerify, stuck on-chain).
4. User calls ft_on_transfer → withdraw (W2). btc_pending_sign_ids = {W2}.
5. DAO calls cancel_withdraw(W1, output).
   → require_pending_sign_capacity(&user): pending_sign_count()=1, max=1 → 1 < 1 is false → PANIC.
6. Assert: cancel_withdraw reverts with "Too many pending sign transactions".
   W1 UTXOs remain locked. DAO cannot reclaim them.
```
