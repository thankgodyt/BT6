### Title
`revalidateHeader` Envelope Check Silently Discarded in Production Builds via No-Op `assertWithMsg` — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/HeaderValidation.hs`)

---

### Summary

`revalidateHeader` computes a full `validateEnvelope` result and passes it to `assertWithMsg`, but `assertWithMsg` is a CPP-guarded no-op in every production build where the `asserts` Cabal flag is `False` (the default). The envelope check return value is computed but never enforced, directly mirroring the ERC20 unchecked-return-value pattern. Any header with an invalid block number, slot, or prev-hash that reaches `revalidateHeader` is silently accepted in production, yielding a corrupt `HeaderState`.

---

### Finding Description

**`assertWithMsg` is a compile-time no-op in production.**

`Ouroboros.Consensus.Util.Assert` defines:

```haskell
assertWithMsg :: HasCallStack => Either String () -> a -> a
#if ENABLE_ASSERTIONS
assertWithMsg (Left msg) _ = error msg
#endif
assertWithMsg _ a = a
```

`ENABLE_ASSERTIONS` is only set when the `asserts` Cabal flag is enabled:

```
if flag(asserts)
  ghc-options: -fno-ignore-asserts
  cpp-options: -DENABLE_ASSERTIONS
```

That flag defaults to `False`:

```
flag asserts
  description: Enable assertions
  manual: False
  default: False
```

So in every default production build, `assertWithMsg (Left "…") x` silently returns `x`.

**`revalidateHeader` relies entirely on `assertWithMsg` for its envelope check.**

```haskell
revalidateHeader cfg ledgerView hdr st =
  assertWithMsg envelopeCheck $
    HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'
 where
  envelopeCheck =
    runExcept $ withExcept show $
      validateEnvelope cfg ledgerView (untickedHeaderStateTip st) hdr
```

`envelopeCheck` is evaluated (it runs `validateEnvelope`, which checks block-number consecutiveness, slot monotonicity, and prev-hash continuity), but its `Left` branch is never acted upon in production. The function unconditionally returns a `HeaderState` built from the supplied header regardless of whether the envelope is valid.

**`revalidateHeader` is called on every block reapplication.**

`reapplyBlockLedgerResult` for `ExtLedgerState` calls `revalidateHeader` directly:

```haskell
reapplyBlockLedgerResult evs cfg blk TickedExtLedgerState{..} =
  (\l -> ExtLedgerState l hdr) <$> castLedgerResult ledgerResult
 where
  hdr = revalidateHeader (getExtLedgerCfg cfg) ledgerView
                         (getHeader blk) tickedHeaderState
```

This path is exercised during ImmutableDB replay at node initialisation and during chain selection whenever a block is in the `prevApplied` set (i.e., `ReapplyRef`/`ReapplyVal` branches in `mkAps`).

---

### Impact Explanation

In a production node (default build, `asserts = False`), `revalidateHeader` never rejects a header on envelope grounds. A crafted ImmutableDB or snapshot that contains blocks with valid per-block checksums and inter-chunk hash links (both checked by `validateChunk`) but with invalid block numbers, non-monotonic slots, or a broken prev-hash chain will pass ImmutableDB-level validation and then pass `revalidateHeader` silently. The resulting `HeaderState` — carrying the wrong `annTipBlockNo`, `annTipSlotNo`, or `annTipInfo` — becomes the authoritative header state for all subsequent chain operations. This constitutes durable use of the wrong ledger/header state, satisfying the High impact criterion: *ImmutableDB/snapshot replay/rollback bug that causes durable use of the wrong ledger state without operator fault*.

---

### Likelihood Explanation

Medium. The ImmutableDB validation layer (`validateChunk`) checks per-block checksums and inter-chunk hash continuity but does **not** independently verify block-number consecutiveness or slot monotonicity — those checks live exclusively in `validateEnvelope`. A crafted snapshot (e.g., in a local reproduction or private-testnet scenario) that preserves checksums while embedding incorrect block numbers or slots would survive ImmutableDB validation and then be silently accepted by `revalidateHeader` in any production binary. The `noAsserts` Nix variant (`nix/haskell.nix`, line 94–99) explicitly clears `cabal/asserts.cabal`, confirming that assertion-free builds are a first-class deployment target.

---

### Recommendation

Replace the `assertWithMsg` guard in `revalidateHeader` with a hard error that is unconditional (not CPP-gated), or promote the envelope check to a proper `Except`-returning path analogous to `validateHeader`. At minimum, the `envelopeCheck` result must be inspected and acted upon in all build configurations, not only when `ENABLE_ASSERTIONS` is set.
