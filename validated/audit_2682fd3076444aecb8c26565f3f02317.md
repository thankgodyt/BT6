### Title
3-arg `mint` in `HlBridgeToken` Silently Redirects All Bridged Tokens to `_systemAddress` on NEAR→HyperEVM Finalization with Non-Empty Message — (`evm/src/omni-bridge/contracts/HlBridgeToken.sol`)

---

### Summary

`OmniBridge.finTransfer` dispatches to the 3-arg `mint(address, uint256, bytes)` whenever `payload.message.length > 0`. `HlBridgeToken` overrides this function to call `_mint(account, value)` followed immediately by `_update(account, _systemAddress, value)`, producing a net balance change of zero for the declared recipient. All minted tokens land at `_systemAddress`. NEAR marks the transfer complete. The recipient is permanently deprived of the full bridged amount with no refund path.

---

### Finding Description

**Step 1 — `OmniBridge.finTransfer` dispatch logic** [1](#0-0) 

When `isBridgeToken[payload.tokenAddress]` is true and `payload.message.length > 0`, the contract calls the 3-arg overload:

```solidity
IBridgeToken(payload.tokenAddress).mint(
    payload.recipient,
    payload.amount,
    payload.message   // non-empty → 3-arg path
);
```

**Step 2 — Base `BridgeToken` 3-arg mint (safe)**

The base implementation simply mints to the recipient: [2](#0-1) 

**Step 3 — `HlBridgeToken` overrides and breaks the invariant**

`HlBridgeToken` overrides the 3-arg mint with destructive accounting: [3](#0-2) 

```solidity
function mint(address account, uint256 value, bytes memory) external override onlyOwner {
    _mint(account, value);              // account += value, totalSupply += value
    _update(account, _systemAddress, value); // account -= value, _systemAddress += value
}
```

Net result for `account`: **+value − value = 0**. All tokens land at `_systemAddress`.

**Step 4 — `IBridgeToken` confirms the 3-arg overload is part of the interface** [4](#0-3) 

The 3-arg `mint` is a declared interface method, so `OmniBridge` legitimately calls it through the interface.

**Step 5 — Design intent vs. actual dispatch**

The NatSpec comment explains the 3-arg mint is intended for the HyperCore accounting model — tokens minted to HyperCore are parked at `_systemAddress` to mirror the HyperCore-side balance: [5](#0-4) 

However, `OmniBridge.finTransfer` has no awareness of this semantic. It selects the 3-arg path purely on `payload.message.length > 0`, which is a user-controlled field in any NEAR→HyperEVM transfer. A regular HyperEVM recipient with a non-empty `msg` field triggers the HyperCore accounting path, which is semantically wrong and financially destructive.

---

### Impact Explanation

- Recipient's `balanceOf` = 0 after finalization despite being the declared beneficiary.
- `_systemAddress.balanceOf` increases by the full bridged amount.
- `completedTransfers[destinationNonce]` is set to `true` before the mint call, so the nonce is consumed and the transfer cannot be re-finalized.
- NEAR has already locked/burned the origin tokens. No refund mechanism exists.
- **Full loss of bridged funds for any NEAR→HyperEVM transfer that includes a non-empty `msg` field.**

---

### Likelihood Explanation

- The `msg` field is a standard, documented field in the NEAR bridge transfer flow.
- Any user who attaches a memo, routing hint, or application-layer message to a NEAR→HyperEVM transfer triggers this path.
- No special attacker capability is required — a legitimate user can trigger this accidentally.
- The MPC signature covers the full payload including `message`, so the signature is valid; no signature bypass is needed.
- The relayer submits the finalization in the normal flow.

---

### Recommendation

The 3-arg `mint` in `HlBridgeToken` must not be reachable from `OmniBridge.finTransfer` for HyperEVM-destined transfers. Two concrete fixes:

1. **Override `mint(address, uint256, bytes)` in `HlBridgeToken` to behave identically to the 2-arg version** (i.e., just call `_mint(account, value)` without the subsequent `_update`). The HyperCore pool-parking logic belongs exclusively in `coreReceiveWithData`, not in the NEAR→EVM finalization path.

2. **Alternatively**, remove the `message`-based dispatch from `OmniBridge.finTransfer` for `HlBridgeToken` tokens, or add a token-type check so that HyperLiquid tokens always use the 2-arg mint during `finTransfer`.

---

### Proof of Concept

```solidity
// 1. Deploy HlBridgeToken registered as isBridgeToken in OmniBridge.
// 2. NEAR user initiates transfer to freshEOA with msg = "hello" (non-empty).
// 3. MPC signs the payload (legitimate signature).
// 4. Relayer calls OmniBridge.finTransfer(sig, payload) where payload.message = "hello".
// 5. OmniBridge enters the isBridgeToken branch, message.length > 0 → calls 3-arg mint.
// 6. HlBridgeToken.mint(freshEOA, amount, "hello"):
//      _mint(freshEOA, amount)              → freshEOA.balance = amount
//      _update(freshEOA, _systemAddress, amount) → freshEOA.balance = 0
// 7. Assert: token.balanceOf(freshEOA) == 0       ✓
//    Assert: token.balanceOf(_systemAddress) == amount ✓
//    Assert: completedTransfers[nonce] == true      ✓ (no re-finalization possible)
// Funds permanently lost to _systemAddress; NEAR transfer marked complete.
```
