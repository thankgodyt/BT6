### Title
Unit-Unsafe Quorum Threshold Comparison in Peras Vote Aggregation Allows Incorrect Certificate Forging - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

`stakeAboveThreshold` compares a `PerasVoteStake` value directly against the `perasQuorumStakeThreshold` (a relative `Rational`, e.g., `3/4`) without any normalization or unit enforcement. The code itself carries a `TODO` comment acknowledging that the two operands may be in incompatible units (absolute vs. relative stake). If `PerasVoteStake` is populated with absolute ledger stake rather than a normalized fraction, the comparison is meaningless: quorum is either trivially reached with a single vote (absolute stake >> 3/4) or permanently unreachable, both of which corrupt Peras certificate forging and chain selection.

### Finding Description

`stakeAboveThreshold` is the sole gate that decides whether accumulated votes reach quorum and trigger Peras certificate forging:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake         = unPerasVoteStake voteStake          -- bare Rational
  quorumThreshold = unPerasQuorumStakeThreshold ...   -- relative, e.g. 3/4
  safetyMargin    = unPerasQuorumStakeThresholdSafetyMargin ...
``` [1](#0-0) 

Both `PerasVoteStake` and `PerasQuorumStakeThreshold` are bare `Rational` newtypes with no unit annotation. The default parameters set the threshold to `3/4`: [2](#0-1) 

The code's own `TODO` comment explicitly acknowledges the unit mismatch:

> "this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … Under the current implementation of `PerasParams`, this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [3](#0-2) 

A companion note on `PerasVoteStake` itself states there is "no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee": [4](#0-3) 

The `implEligiblePartyVoteWeight` function in `WFALS.hs` shows the divergence concretely: persistent members receive their raw `LedgerStake` as their `VoteWeight`, while non-persistent members receive a value normalized by `nonPersistentStake`. There is no single, enforced normalization step before the value is stored as `PerasVoteStake` and passed to `stakeAboveThreshold`: [5](#0-4) 

`stakeAboveThreshold` is called in three production paths:

1. `votesReachQuorum` — the smart constructor for `ValidatedPerasVotesWithQuorum`, which gates certificate forging.
2. `updateLoserVoteState` in `Peras/Vote/Aggregation.hs` — detects the `RoundVoteStateLoserAboveQuorum` error.
3. The `PerasVoteDB` model used in the ChainDB state machine. [6](#0-5) [7](#0-6) 

### Impact Explanation

**Scenario A — Trivial quorum (absolute stake >> 3/4):** If `PerasVoteStake` carries absolute lovelace-denominated stake (e.g., `500_000_000_000 % 1`), then `stake >= 3/4` is always `True`. A single vote from any pool causes `votesReachQuorum` to return `Just`, immediately forging a Peras certificate for the voted block. An adversarial peer can boost any block — including a non-canonical or adversarially crafted one — with a single network message, directly manipulating Peras chain selection.

**Scenario B — Quorum never reached (normalized stake << 3/4 but threshold also relative):** If the normalization is applied inconsistently (e.g., stake is normalized to `[0,1]` per-voter but the threshold is `3/4` of total committee stake), the accumulated sum of all honest votes may never reach `3/4`, permanently disabling Peras certificate forging and degrading the protocol to plain Praos without the boosting security guarantee.

Both outcomes constitute a chain-selection bug triggered by an unprivileged peer sending crafted or ordinary votes.

### Likelihood Explanation

The vulnerability is reachable whenever a concrete `BlockSupportsPeras` instance populates `vpvVoteStake` with a value that is not normalized to the same unit as `perasQuorumStakeThreshold`. The type system provides no barrier: both are `Rational`. The acknowledged `TODO` and the absence of any normalization call-site in the production code paths confirm this is not a theoretical concern but an unresolved design gap in the current implementation. Any peer that can send a Peras vote message triggers the affected code path.

### Recommendation

1. **Enforce units at the type level.** Introduce distinct newtypes `AbsoluteStake` and `RelativeStake` (or `NormalizedStake`) so that `stakeAboveThreshold` can only accept a `RelativeStake`, making unit confusion a compile-time error.
2. **Normalize inside `stakeAboveThreshold`.** Change the function signature to accept the total committee stake alongside `PerasVoteStake`, perform the normalization internally, and compare the result against the relative threshold.
3. **Resolve the open research question.** The comment "no consensus from researchers/engineers" must be resolved before this code is used in production. Until then, the quorum check is semantically undefined.

### Proof of Concept

```

  perasQuorumStakeThreshold = 3/4   (relative, as set in mkPerasParams)
  perasQuorumStakeThresholdSafetyMargin = 2/100

Attacker sends one vote with vpvVoteStake = PerasVoteStake (1_000_000_000 % 1)
  (absolute lovelace stake of a pool with 1 ADA delegated)

stakeAboveThreshold params (PerasVoteStake (1_000_000_000 % 1))
  = 1_000_000_000 >= (3/4 + 2/100)
  = 1_000_000_000 >= 0.77
  = True   ← quorum declared with a single vote

Result: votesReachQuorum returns Just, forgePerasCert is called,
        an adversarial block receives a Peras boost, chain selection
        is manipulated without any honest majority of stake.

implEligiblePartyVoteWeight ::
  VotingCommittee crypto WFALS ->
  EligibilityWitness crypto WFALS ->
  VoteWeight
implEligiblePartyVoteWeight committee = \case
  -- Persistent members have their voting power equal to their stake
  WFALSPersistentMember
    _seatIndex
    (LedgerStake stake) ->
      VoteWeight stake
  -- Non-persistent members have their voting power proportional to their
  -- number of seats granted by local sortition and their stake (normalized
  -- by the total non-persistent stake)
  WFALSNonPersistentMember
    _seatIndex
    (LedgerStake stake)
    _vrfOutput
    numSeats ->
      VoteWeight $
        fromIntegral (unLocalSortitionNumSeats (unNonZero numSeats))
          * stake
          / nonPersistentStake
     where
      TotalNonPersistentStake (Cumulative (LedgerStake nonPersistentStake)) =
        totalNonPersistentStake committee
