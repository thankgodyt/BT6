### Title
Silent Replacement of Oversized `tx_bytes` with Zero-Filled Buffer Permanently Locks Bridge UTXOs — (File: `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

---

### Summary

In `internal_safe_verify_deposit_entry`, when the caller-supplied `tx_bytes` exceeds 10 000 bytes, the code silently replaces the real transaction bytes with `vec![0u8; 300]` — 300 zero bytes — before storing the UTXO in the bridge's on-chain UTXO set. Every subsequent operation that must decode those stored bytes (withdrawal PSBT construction, refund execution) will panic, permanently locking the deposited BTC inside the bridge while the corresponding nBTC has already been minted to the user.

---

### Finding Description

Inside `internal_safe_verify_deposit_entry`, the deposit address and amount are validated correctly against the *original* `tx_bytes` (lines 191–202). Immediately after that validation, the following block runs:

```rust
let tx_bytes = if tx_bytes.len() > 10000 {
    env::log_str("tx_bytes length exceeds 10000, truncating to 300 bytes");
    vec![0u8; 300]          // ← NOT a truncation; replaces with 300 zero bytes
} else {
    tx_bytes
};
``` [1](#0-0) 

The log message says "truncating", but the actual code produces an entirely synthetic, zero-filled buffer. This corrupted buffer is then placed into the `UTXO` struct that is stored in the bridge's UTXO set:

```rust
let utxo = UTXO {
    path,
    tx_bytes,          // ← now vec![0u8; 300]
    vout,
    balance: transaction.output()[vout].value.to_sat(),
};
``` [2](#0-1) 

The `deposit_amount` and the UTXO `balance` are computed from the *original* transaction before the replacement, so nBTC minting proceeds normally. The corruption is invisible at deposit time.

When the bridge later selects this UTXO as an input for a withdrawal or refund, it must decode the stored bytes:

```rust
let transaction =
    crate::WrappedTransaction::decode(&refund_request.tx_bytes.0, &config.chain)
        .expect("Deserialization tx_bytes failed");
``` [3](#0-2) 

Deserializing 300 zero bytes as a Bitcoin/Zcash transaction will always fail, causing an irrecoverable panic. The UTXO — and the BTC it represents — is permanently inaccessible.

---

### Impact Explanation

- nBTC is minted correctly to the user, so the token supply grows.
- The backing BTC is locked in the bridge's deposit address and can never be spent, because every code path that would spend it first decodes `tx_bytes` and panics.
- The bridge's BTC holdings become permanently under-collateralised by the amount of the affected deposit.
- This matches the allowed impact: **permanent locking of user or protocol funds** (Medium–Critical depending on deposit size).

---

### Likelihood Explanation

Bitcoin transactions exceed 10 000 bytes when they consolidate many small UTXOs (e.g., a user sweeping dust from a mining pool or exchange). This is uncommon but entirely normal on mainnet. No special privilege is required: the user simply deposits BTC using such a transaction; the trusted relayer observes it on-chain and submits it to `verify_deposit_v2`. The relayer has no reason to reject a valid, confirmed Bitcoin transaction.

---

### Recommendation

Replace the silent substitution with an explicit rejection before any state is mutated:

```rust
require!(
    tx_bytes.len() <= 10_000,
    "tx_bytes exceeds maximum allowed length"
);
```

This causes the call to revert cleanly with no UTXO stored and no nBTC minted, leaving the user's BTC safely spendable on the Bitcoin network.

---

### Proof of Concept

1. User consolidates many small UTXOs into a single deposit output, producing a Bitcoin transaction whose serialised size exceeds 10 000 bytes.
2. User sends the output to the bridge deposit address derived from their `DepositMsg`.
3. Trusted relayer observes the confirmed transaction and calls `verify_deposit_v2` with `deposit_msg.safe_deposit = Some(...)` and the full `tx_bytes`.
4. `internal_safe_verify_deposit_entry` validates the deposit address and amount against the original bytes (lines 191–202) — both checks pass.
5. The `tx_bytes.len() > 10000` branch fires; `tx_bytes` is replaced with `vec![0u8; 300]`.
6. The UTXO `{ path, tx_bytes: vec![0u8;300], vout, balance }` is stored in the bridge's UTXO set.
7. The light-client verification succeeds; `verify_deposit_callback` mints nBTC to the user — the user now holds nBTC.
8. Any future withdrawal that selects this UTXO calls `WrappedTransaction::decode(&utxo.tx_bytes, ...)`, which panics with `"Deserialization tx_bytes failed"`.
9. The BTC is permanently locked; the bridge holds nBTC-backed liabilities with no corresponding spendable BTC.
