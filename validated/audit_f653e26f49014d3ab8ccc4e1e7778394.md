### Title
`validatePerasCert` Stub Unconditionally Accepts All Inbound Peras Certificates Without Any Cryptographic or Structural Validation — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `BlockSupportsPeras` catch-all instance for all `StandardHash blk` block types implements `validatePerasCert` as an unconditional stub that always returns `Right` (success) regardless of the certificate's content. This is the implementation wired into the production `makePerasCertPoolWriterFromChainDB` path. Any unprivileged peer can therefore inject an arbitrary `PerasCert` — with any round number and any boosted block point — and it will be accepted, timestamped, and stored in the ChainDB without any cryptographic or structural check. Because Peras certificates carry a chain-selection boost weight (`vpcCertBoost`), this allows a peer to manipulate which block is preferred by the local node.

---

### Finding Description

**Root cause — the stub implementation:** [1](#0-0) 

The catch-all instance `instance StandardHash blk => BlockSupportsPeras blk` is explicitly marked as a degenerate placeholder ("TODO: degenerate instance for all blks to get things to compile"). Its `validatePerasCert` method performs zero checks:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

Every field of the inbound certificate — round number, boosted block point, committee membership proof, aggregate BLS signature — is silently accepted. The returned `ValidatedPerasCert` carries a non-zero `vpcCertBoost = perasWeight params`, meaning the certificate immediately influences chain selection.

**Production wiring — the inbound processing path:** [2](#0-1) 

`makePerasCertPoolWriterFromChainDB` — the production writer used by the node kernel — passes `validatePerasCert mkPerasParams` directly as the validation callback:

```haskell
(validatePerasCert mkPerasParams)  -- TODO replace when actual plumbing is in place
```

**The `processCerts` gate:** [3](#0-2) 

`processCerts` performs only one real gate: it skips certificates whose `PerasRoundNo` is already present in the database. For any round number not yet seen, it calls `validateCert` (the stub) and, on `Right`, immediately stores the certificate via `addCert . WithArrivalTime now`. No signature, no committee membership, no round-number range, no boosted-block existence check is performed.

**Analog to the external report:**

The external `recoverERC20` bug checked `tokenAddress != stakingToken` but omitted the symmetric check `tokenAddress != rewardsToken`. Here, `validatePerasCert` checks *nothing at all* — the incompleteness is total rather than partial, making it a strictly more severe instance of the same vulnerability class: a privileged/sensitive resource (chain-selection boost) is reachable through a function that was supposed to guard it but does not.

---

### Impact Explanation

**High — Chain selection manipulation via injected certificates.**

A Peras certificate stored in the ChainDB carries `vpcCertBoost = perasWeight params`. Chain selection consults these boosts when comparing candidate chains. An attacker who can inject a certificate pointing to an arbitrary block can cause an honest node to prefer a non-canonical or adversarially-chosen chain tip, violating the chain-selection security assumption of Ouroboros Peras. Because the attacker controls both the `pcCertRound` and `pcCertBoostedBlock` fields of the injected certificate, they can target any block they wish to boost, including one on a minority fork.

---

### Likelihood Explanation

The attack requires only that:
1. The Peras object-diffusion miniprotocol is negotiated between the attacker and the victim node (no privileged keys needed — any peer connection suffices).
2. The attacker sends a `PerasCert` for a round number not yet in the victim's database.

Both conditions are trivially satisfiable by any unprivileged network peer once Peras is active. The `processCerts` deduplication check (one certificate per round) limits the attacker to one injected certificate per round, but across many rounds this is sufficient to persistently skew chain selection.

---

### Recommendation

Replace the stub with a real implementation that validates at minimum:

1. **Aggregate BLS signature** over `(electionId, candidate)` using the aggregated public keys of the claimed committee members.
2. **Committee membership** — each claimed voter must appear in the stake distribution for the relevant epoch with positive stake.
3. **Quorum threshold** — the total stake of the signers must meet the Peras quorum parameter.
4. **Round number range** — the certificate's round number must fall within the current or recent Peras window.
5. **Boosted block existence** — `pcCertBoostedBlock` must refer to a block that is known and on a valid chain.

Until a real implementation exists, the inbound Peras certificate miniprotocol should be disabled or the `opwAddObjects` handler should unconditionally reject all inbound certificates rather than accepting them.

---

### Proof of Concept

**Setup:** A private Cardano testnet with Peras enabled. Attacker runs a node that connects to the victim.

**Steps:**

1. Attacker constructs a `PerasCert` with:
   - `pcCertRound = <any round not yet in victim's DB>`
   - `pcCertBoostedBlock = <point of attacker's preferred minority-fork block>`
2. Attacker sends this certificate to the victim via the Peras object-diffusion miniprotocol.
3. Victim's `processCerts` checks: round not in `alreadyInDb` → proceeds to validate.
4. `validatePerasCert mkPerasParams cert` returns `Right ValidatedPerasCert{vpcCertBoost = perasWeight params}` unconditionally.
5. Certificate is stored in ChainDB via `ChainDB.addPerasCertAsync`.
6. Chain selection now applies `vpcCertBoost` to the attacker's chosen block, potentially causing the victim to switch to the attacker's fork.

**Expected (correct) behavior:** Step 4 should fail with a `PerasValidationErr` because the certificate carries no valid aggregate BLS signature and no valid committee membership proof.

**Observed behavior:** Step 4 always succeeds; the certificate is accepted and stored. [4](#0-3) [5](#0-4) [3](#0-2)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
