### Title
Unauthenticated `sign_btc_transaction` Allows Any Caller to Trigger MPC Signing for Any User's Pending Transaction - (File: contracts/satoshi-bridge/src/api/chain_signatures.rs)

### Summary
`sign_btc_transaction` performs no check that `env::predecessor_account_id()` matches the `account_id` stored in the target `BTCPendingInfo`. Any unprivileged NEAR account can call it with any `btc_pending_sign_id`, forcing the MPC signing pipeline to execute on another user's pending withdrawal or refund transaction.

### Finding Description
`sign_btc_transaction` is a public, payable function that accepts a `btc_pending_sign_id`, a `sign_index`, and a caller-supplied `key_version`. It looks up the pending info, asserts it is in `PendingSign` stage, and immediately delegates to `internal_sign_btc_transaction`, which issues a `sign()` call to the Chain Signatures MPC contract. [1](#0-0) 

At no point is `env::predecessor_account_id()` compared against `btc_pending_info.account_id`. The `account_id` field is set at creation time (withdrawal via `ft_on_transfer`, or refund via `finalize_refund_with_psbt`) and is the only record of who owns the pending transaction. [2](#0-1) [3](#0-2) 

The `sign_btc_transaction_callback` stores the returned `SignatureResponse` directly into `btc_pending_info.signatures[sign_index]` without verifying that the signature is valid for the UTXO's expected public key. Once stored, the slot is permanently locked (`"Already signed"` guard). [4](#0-3) 

The `btc_pending_sign_id` values are emitted publicly via `Event::GenerateBtcPendingInfo` and are enumerable through the view API, so an attacker has no barrier to discovering valid IDs.

### Impact Explanation
An attacker can supply an arbitrary `key_version` (e.g., a version not yet deployed or a future version) when calling `sign_btc_transaction` on a victim's pending transaction. If the MPC contract accepts the version and returns a signature, that signature is stored unconditionally. Because the slot is then marked as signed, the legitimate owner can never overwrite it. If all inputs are signed with mismatched-key-version signatures, the transaction advances to `PendingVerify` carrying an invalid Bitcoin signature. The resulting signed transaction bytes cannot be broadcast successfully; the pending info is stuck in `PendingVerify` with no on-chain path to recovery, and the user's nBTC (already transferred to the bridge) cannot be burned or returned without operator intervention.

This matches the **Low** allowed impact: publicly reachable stuck-state fault in production bridge/token paths without direct theft.

### Likelihood Explanation
The `btc_pending_sign_id` is publicly observable on-chain. The function is open to any NEAR account and requires only an attached deposit to cover the MPC fee. The attacker's only cost is the MPC signing fee. The scenario where the MPC accepts an unrecognized `key_version` and returns a usable (but wrong-key) signature depends on MPC contract behavior, which is an external dependency; however, the authorization gap itself is unconditional and reachable today.

### Recommendation
Add a caller-ownership check at the top of `sign_btc_transaction`:

```rust
let caller = env::predecessor_account_id();
require!(
    caller == btc_pending_info.account_id,
    "Unauthorized: caller is not the owner of this pending transaction"
);
```

Additionally, in `sign_btc_transaction_callback`, verify the returned signature against the expected public key before storing it, so that a corrupted or mismatched signature is rejected rather than permanently locked in.

### Proof of Concept

1. Alice calls `nbtc.ft_transfer_call(bridge, 100000, WithdrawMsg{...})`. The bridge creates a `BTCPendingInfo` with `account_id = alice`, emitting `GenerateBtcPendingInfo { btc_pending_id: "abcd1234..." }`.
2. Attacker Eve observes the event and reads `btc_pending_id = "abcd1234..."` from the view API.
3. Eve calls `bridge.sign_btc_transaction("abcd1234...", 0, 999)` with 1 yoctoNEAR attached (MPC fee). No authorization check fires.
4. The MPC contract receives `sign(payload, path, key_version=999)`. If it returns a signature (for a different key), `sign_btc_transaction_callback` stores it at `signatures[0]` without verification.
5. If Alice's transaction has only one input, `is_all_signed()` returns `true`, `extract_tx_bytes_with_sign()` embeds the invalid signature, and the state transitions to `PendingVerify`.
6. Alice attempts to broadcast the transaction; Bitcoin nodes reject it (invalid signature). `verify_withdraw` cannot succeed. Alice's nBTC remains locked in the bridge with no self-service recovery path. [5](#0-4) [6](#0-5)

    pub fn sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> PromiseOrValue<bool> {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        btc_pending_info.assert_pending_sign();
        if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {
            if !self.check_btc_pending_info_exists(original_tx_id) {
                require!(
                    self.internal_unwrap_mut_account(&btc_pending_info.account_id.clone())
                        .btc_pending_sign_ids
                        .remove(&btc_pending_sign_id),
                    "Internal error"
                );
                self.internal_remove_btc_pending_info(&btc_pending_sign_id);
                return PromiseOrValue::Value(true);
            }
        }
        self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
            .into()
    }
