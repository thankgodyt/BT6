### Title
Resigned or Revoked Trusted Relayer Permanently Loses Earned Fees Due to Overly Restrictive `#[trusted_relayer]` Guard on `claim_fee` — (`near/omni-bridge/src/lib.rs`)

---

### Summary

The `claim_fee` function is gated by two independent authorization constraints: the `#[trusted_relayer]` macro (which requires the caller to be a **currently active** trusted relayer) and an inner `require!` in `claim_fee_callback` that enforces `fee_recipient == predecessor_account_id`. These two constraints together create a permanent deadlock: a relayer who earned a fee (by signing a transfer with themselves as `fee_recipient`) and then resigned or was revoked before claiming can never recover those funds. No other account can claim on their behalf either, because any substitute caller fails the `fee_recipient == predecessor_account_id` check.

---

### Finding Description

**Step 1 — Relayer earns a fee.**
A trusted relayer calls `sign_transfer`, supplying `fee_recipient: Some(relayer_account_id)`. The `fee_recipient` is embedded in the signed `TransferMessagePayload` and broadcast to the destination chain. [1](#0-0) 

**Step 2 — Transfer is finalized on the foreign chain.**
The destination chain emits a `FinTransfer` event containing the `fee_recipient` field. At this point the relayer's entitlement to the fee is irrevocably recorded on-chain.

**Step 3 — Relayer resigns (or is revoked).**
The relayer calls `resign_trusted_relayer` to recover their staked NEAR, or the DAO calls `reject_relayer_application` to revoke an active relayer. Either action removes the account from the trusted-relayer set.

**Step 4 — Relayer tries to claim their fee — permanently blocked.**
`claim_fee` carries `#[trusted_relayer]`, which is evaluated against the caller's **current** status. Because the relayer is no longer trusted, the call is rejected before `claim_fee_callback` is ever reached. [2](#0-1) 

**Step 5 — No substitute caller can succeed.**
The `#[trusted_relayer]` macro allows `bypass_roles(Role::DAO, Role::UnrestrictedRelayer)`, so a DAO member can pass the first gate. However, `claim_fee_callback` immediately enforces:

```rust
require!(
    fee_recipient == *predecessor_account_id,
    BridgeError::OnlyFeeRecipientCanClaim.as_ref()
);
``` [3](#0-2) 

Because the DAO account ≠ `fee_recipient`, this check fails. The transfer message is never removed from `pending_transfers`, and the fee is permanently frozen inside the bridge contract.

---

### Impact Explanation

The relayer's earned fee (both the token fee and any native fee embedded in `transfer_message.fee`) is permanently unclaimable. The `remove_transfer_message` call inside `claim_fee_callback` is never reached, so the `pending_transfers` entry persists indefinitely and the locked token accounting (`locked_tokens`) is never corrected. This constitutes permanent freezing of bridged funds and fee mis-accounting. [4](#0-3) 

---

### Likelihood Explanation

The scenario is realistic and requires no admin compromise:

1. A relayer signs one or more transfers and sets themselves as `fee_recipient`.
2. The relayer voluntarily calls `resign_trusted_relayer` to reclaim their staked NEAR — a normal lifecycle action — without first claiming all pending fees.
3. The relayer discovers they cannot claim the fee and has no recourse.

The window between signing a transfer and the corresponding `FinTransfer` event being provable on NEAR can span minutes to hours (depending on finality and relayer latency), making it easy to resign in between. The test suite confirms that `resign_trusted_relayer` immediately removes trusted status. [5](#0-4) 

---

### Recommendation

Remove the `#[trusted_relayer]` guard from `claim_fee` entirely, or add a dedicated bypass that allows any account to call `claim_fee` provided the proof's `fee_recipient` matches `env::predecessor_account_id()`. The existing inner check (`fee_recipient == predecessor_account_id`) already ensures only the rightful recipient can collect the fee; the outer trusted-relayer gate adds no security benefit and introduces this permanent-loss scenario.

---

### Proof of Concept

1. DAO sets `stake_required = 1 yoctoNEAR`, `waiting_period_ns = 0`.
2. `relayer.near` calls `apply_for_trusted_relayer` with 1 yoctoNEAR deposit → becomes trusted immediately.
3. `relayer.near` calls `sign_transfer(transfer_id, fee_recipient = Some("relayer.near"), fee = Some(...))`.
4. The destination chain finalizes the transfer and emits a `FinTransfer` event with `fee_recipient = "relayer.near"`.
5. `relayer.near` calls `resign_trusted_relayer` → stake returned, trusted status removed.
6. `relayer.near` calls `claim_fee` with a valid proof of the `FinTransfer` event → **panics at the `#[trusted_relayer]` gate** with an authorization error.
7. DAO calls `claim_fee` with the same proof → passes the `#[trusted_relayer]` gate but **panics at** `BridgeError::OnlyFeeRecipientCanClaim` because `DAO ≠ "relayer.near"`.
8. The fee is permanently frozen; `pending_transfers` retains the entry forever. [2](#0-1) [6](#0-5)

    #[payable]
    #[trusted_relayer]
    #[pause(except(roles(Role::DAO)))]
    pub fn sign_transfer(
        &mut self,
        transfer_id: TransferId,
        fee_recipient: Option<AccountId>,
        fee: &Option<Fee>,
    ) -> Promise {
        let transfer_message = self.get_transfer_message(transfer_id);

        if let Some(fee) = &fee {
            require!(
                &transfer_message.fee == fee,
                BridgeError::InvalidFee.as_ref()
            );
        }

        let token_address = self
            .get_token_address(
                transfer_message.get_destination_chain(),
                self.get_token_id(&transfer_message.token),
            )
            .unwrap_or_else(|| {
                env::panic_str(BridgeError::FailedToGetTokenAddress.to_string().as_str())
            });

        let decimals = self
            .token_decimals
            .get(&token_address)
            .near_expect(BridgeError::TokenDecimalsNotFound);
        let amount_to_transfer = Self::normalize_amount(
            transfer_message
                .amount_without_fee()
                .near_expect(BridgeError::InvalidFee),
            decimals,
        );

        require!(
            amount_to_transfer > 0,
            BridgeError::InvalidAmountToTransfer.as_ref()
        );

        let message = DestinationChainMsg::from_json(&transfer_message.msg)
            .and_then(|s| s.destination_msg())
            .unwrap_or_default();

        let transfer_payload = TransferMessagePayload {
            prefix: PayloadType::TransferMessage,
            destination_nonce: transfer_message.destination_nonce,
            transfer_id,
            token_address,
            amount: U128(amount_to_transfer),
            recipient: transfer_message.recipient,
            fee_recipient,
            message,
        };
