### Title
Incorrect Block-Counting Window in `shelleyAfterVoting` Causes Premature Era-Transition Signalling - (File: `ouroboros-consensus-cardano/src/shelley/Ouroboros/Consensus/Shelley/Ledger/Ledger.hs`)

---

### Summary

The `applyHelper` function in the Shelley ledger increments the `shelleyAfterVoting` counter for **every** block whose slot is at or after the voting deadline, with no upper-bound cutoff at `votingDeadline + stabilityWindow`. The intended invariant (documented explicitly as a known bug in `civic_time.md`) is that only blocks within the **subsequent stability window** (`[votingDeadline, votingDeadline + swindow)`) should be counted. Because the counter is unbounded, the Hard Fork Combinator (HFC) can reach the threshold `shelleyAfterVoting >= k` using blocks that fall **outside** the stability window, causing it to signal an era transition as stable when it is not — the exact analogue of the `_convert()` missing-case bug, where a missing branch causes an incorrect value to propagate into downstream logic.

---

### Finding Description

**Root cause — `applyHelper`** in `ouroboros-consensus-cardano/src/shelley/Ouroboros/Consensus/Shelley/Ledger/Ledger.hs`:

```haskell
shelleyAfterVoting =
    (if blockSlot blk >= votingDeadline then succ else id) $
      shelleyAfterVoting tickedShelleyLedgerTransition
``` [1](#0-0) 

The condition `blockSlot blk >= votingDeadline` has no upper bound. The missing branch is `blockSlot blk < votingDeadline + swindow`. Blocks in the interval `[votingDeadline + swindow, end_of_epoch)` are counted but must not be, because they lie outside the stability window that Chain Growth guarantees to contain at least `k` blocks.

The `votingDeadline` is computed as:

```haskell
votingDeadline = subSlots (2 * swindow) startOfNextEpoch
``` [2](#0-1) 

So the stability window after the deadline spans `[votingDeadline, votingDeadline + swindow)`, and there is a non-empty interval `[votingDeadline + swindow, end_of_epoch)` of length `swindow` slots where blocks are incorrectly counted.

**Downstream consumer — `shelleyTransition`** in `ouroboros-consensus-cardano/src/shelley/Ouroboros/Consensus/Shelley/ShelleyHFC.hs`:

```haskell
guard $ shelleyAfterVoting >= fromIntegral k
``` [3](#0-2) 

When this guard passes, `singleEraTransition` returns `Just epochNo`, which `reconstructSummaryLedger` / `mostRecentTransitionInfo` uses to set `TransitionKnown`, extending the HFC summary into the next era and committing the node to the transition. [4](#0-3) 

**The bug is explicitly acknowledged** in the project's own documentation:

> "(TODO this is today's intended behavior, but a bug is counting all blocks after the voting deadline instead of only those in the subsequent stability window.)" [5](#0-4) 

---

### Impact Explanation

The HFC's Iteration 4 rule is: *silently ignore the on-chain governance outcome and stay in the current era* if the stability window after the voting deadline contains fewer than `k+1` blocks (a Chain Growth violation). The incorrect counter defeats this rule. When a chain has `k+` blocks in `[votingDeadline, end_of_epoch)` but fewer than `k` in `[votingDeadline, votingDeadline + swindow)`, the node will:

1. Signal `TransitionKnown` and commit to the next era.
2. Extend the HFC `Summary` into the next era, making slot/epoch/time translations and cross-era forecasts use the new era's parameters.
3. Accept and validate headers/blocks as belonging to the next era.

This is a **hard-fork / era-transition bug** that breaks the cross-era ledger invariant: the node transitions to the next era when the stability guarantee has not been met, meaning the transition could still be rolled back. Any node that has applied a different chain (one that does satisfy the stability window constraint) will disagree on which era the chain is in, producing a consensus split.

---

### Likelihood Explanation

A Chain Growth violation — fewer than `k+1` blocks in a `3k/f`-slot window — can arise from:

- A natural network partition lasting more than `3k/f` slots.
- An adversary with sub-majority stake deliberately withholding blocks to create a low-density window immediately after the voting deadline, then flooding blocks outside the stability window to push `shelleyAfterVoting` past `k`.

The second path does not require stake majority; it requires only enough stake to produce `k` blocks in the `swindow`-slot interval `[votingDeadline + swindow, end_of_epoch)` while keeping the earlier window sparse. On mainnet with `f = 0.05` and `k = 2160`, `swindow = 3k/f = 129600` slots, so this interval is large and the required stake is modest.

---

### Recommendation

Add an upper-bound check so that only blocks within the stability window are counted:

```haskell
shelleyAfterVoting =
    (if blockSlot blk >= votingDeadline
          && blockSlot blk < votingDeadline + fromIntegral swindow
       then succ
       else id) $
      shelleyAfterVoting tickedShelleyLedgerTransition
```

This matches the stated intent in `civic_time.md` (Iteration 4) and ensures the `shelleyAfterVoting >= k` guard in `shelleyTransition` is only satisfied when the stability window itself contains at least `k` blocks, preserving the Chain Growth guarantee.

---

### Proof of Concept

Consider a Shelley-era chain with `k = 2160`, `swindow = 129600` slots, epoch length `432000` slots, and `votingDeadline = end_of_epoch - 2*swindow = end_of_epoch - 259200`.

1. Produce 0 blocks in `[votingDeadline, votingDeadline + swindow)` — the stability window is empty (Chain Growth violated).
2. Produce `k = 2160` blocks in `[votingDeadline + swindow, end_of_epoch)` — outside the stability window.
3. After applying these blocks, `shelleyAfterVoting = 2160 >= k`.
4. `shelleyTransition` returns `Just nextEpoch`.
5. `mostRecentTransitionInfo` sets `TransitionKnown nextEpoch`.
6. `reconstructSummaryLedger` extends the HFC summary into the next era.
7. The node now accepts next-era headers and rejects current-era headers for slots after `nextEpoch`, despite the transition not being stable.

A peer node that observed a different chain (one satisfying Chain Growth in the stability window) would remain in the current era, producing a consensus split. [6](#0-5) [7](#0-6) [8](#0-7)
