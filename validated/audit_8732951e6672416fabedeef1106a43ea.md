### Title
`validatePerasCert` Always Returns `Right` (Success), Bypassing All Certificate Validation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary
The default implementation of `validatePerasCert` in the `BlockSupportsPeras` typeclass unconditionally returns `Right` (success) for every certificate it receives, regardless of the certificate's content or cryptographic validity. This is a direct structural analog to the reported `_exitMarket` bug: a function that should signal failure on invalid input instead always signals success.

### Finding Description
In `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`, the `validatePerasCert` default method is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

The function's return type is `Either (PerasValidationErr blk) (ValidatedPerasCert blk)`. The `Left` branch is the error path (invalid certificate); the `Right` branch is the success path (valid certificate). The implementation hard-codes `Right` unconditionally — no signature check, no round-number check, no boosted-block check, no committee membership check is performed. Any certificate, however malformed, is wrapped in `ValidatedPerasCert` and returned as valid.

The `PerasValidationErr` type exists precisely to carry these rejection signals:

```haskell
-- TODO: enrich with actual error types
-- see https://github.com/tweag/cardano-peras/issues/120
data PerasValidationErr blk
  = PerasValidationErr
  deriving stock (Show, Eq)
``` [2](#0-1) 

The accepted `ValidatedPerasCert` carries a `vpcCertBoost :: PerasWeight` field that is directly consumed by chain selection to boost the weight of the certified chain:

```haskell
data ValidatedPerasCert blk = ValidatedPerasCert
  { vpcCert     :: !(PerasCert blk)
  , vpcCertBoost :: !PerasWeight
  }
``` [3](#0-2) 

The inbound vote/certificate processing pipeline in `makePerasVotePoolWriterFromChainDB` calls `validatePerasVote` (which at least checks stake-distribution membership) and then routes accepted votes through `ChainDB.addPerasVoteWithAsyncCertHandling`. Certificates generated or received externally pass through `validatePerasCert` before being stored and applied to chain selection: [4](#0-3) 

### Impact Explanation
A `ValidatedPerasCert` that passes `validatePerasCert` is stored in the `PerasCertDB` and its `vpcCertBoost` weight is applied during chain selection. Because `validatePerasCert` never rejects any certificate, an attacker can craft a `PerasCert` referencing an arbitrary block point and round number, have it accepted as valid, and cause the receiving node to apply a Peras boost to a non-canonical or adversarially chosen chain. This breaks the chain-selection invariant that only legitimately quorum-certified blocks receive a boost, enabling an unprivileged peer to steer an honest node toward a weaker or adversarial chain.

**Impact class:** High — chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain beyond the intended security assumptions; also Critical — bypass of Peras certificate checks enabling unauthorized certificate acceptance.

### Likelihood Explanation
The Peras certificate diffusion miniprotocol is reachable by any peer that connects to the node. No special privileges, keys, or stake are required to send a crafted `PerasCert` message. The default implementation is the only implementation present in the repository (no concrete block type overrides it), so every node running this code is affected. The TODO comment confirms this is the live code path, not a stub gated behind a feature flag.

### Recommendation
Replace the unconditional `Right` with actual certificate validation:
- Verify the aggregate BLS signature over the claimed voters and candidate block.
- Verify that the claimed voters constitute a valid quorum (total stake above threshold).
- Verify that each voter's seat index and VRF proof are consistent with the epoch's committee.
- Only return `Right (ValidatedPerasCert …)` after all checks pass; return `Left PerasValidationErr` on any failure.

Until real validation is implemented, the node should refuse to apply any Peras certificate boost to chain selection, or the certificate diffusion miniprotocol should be disabled.

### Proof of Concept
1. Connect to a target node as an unprivileged peer via the Peras certificate miniprotocol.
2. Craft a `PerasCert` with `pcCertRound = <current round>` and `pcCertBoostedBlock = <point of an adversarial chain tip>`.
3. Send the certificate to the node.
4. `validatePerasCert` is called; it returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }` unconditionally.
5. The certificate is stored in `PerasCertDB` and its boost weight is applied to chain selection.
6. The node now prefers the adversarially chosen chain over the honest canonical chain, constituting a chain-selection safety failure. [1](#0-0)
