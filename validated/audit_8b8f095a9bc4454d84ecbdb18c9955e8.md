### Title
Unit mismatch in `stakeAboveThreshold` enables Peras quorum bypass when vote stake is populated with absolute ledger values — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` in `SupportsPeras.hs` compares a `PerasVoteStake` value (which carries no unit invariant — it can be absolute lovelace or a normalized fraction) directly against `perasQuorumStakeThreshold` (a relative `Rational`, e.g. `3/4`). The function's own TODO comment acknowledges the assumption is unenforceable. The production network handler in `NodeToNode.hs` currently stubs the distribution with `PerasVoteStakeDistr mempty` and explicitly notes it will be replaced with real ledger data. When that replacement is made, if the distribution is populated with absolute lovelace values — the natural representation from the Cardano ledger — the comparison `absolute_lovelace >= 3/4` is trivially `True` for any non-zero vote, allowing a single network peer to forge a Peras certificate and bypass the quorum requirement entirely.

---

### Finding Description

**Root cause — `stakeAboveThreshold`:**

```haskell
-- TODO: this function assumes that the 'PerasVoteStake' and the quorum
-- threshold used in 'PerasParams' are expressed in the same units. That is,
-- both are either absolute or relative (normalized) values. Under the current
-- current implementation of 'PerasParams', this function only makes sense when
-- both values are relative (normalized) values, so we should either normalize
-- the 'PerasVoteStake' before calling this function, or change this function to
-- accept a stake distribution and perform the normalization internally.
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
``` [1](#0-0) 

The `PerasVoteStake` type is a bare `Rational` newtype with no phantom unit tag:

```haskell
-- NOTE: At the moment there is no consensus from researchers/engineers on how
-- we go from the absolute stake of a voter in the ledger to the relative stake
-- of their vote in the voting commitee (given that the quorum is expressed as
-- a relative value of the voting commitee total stake).
newtype PerasVoteStake = PerasVoteStake { unPerasVoteStake :: Rational }
``` [2](#0-1) 

The default quorum threshold is the relative value `3/4`:

```haskell
perasQuorumStakeThreshold = PerasQuorumStakeThreshold (3 / 4)
``` [3](#0-2) 

**Production stub that will be replaced:**

The live network handler in `NodeToNode.hs` currently passes an empty distribution as a placeholder:

```haskell
-- TODO: when actual plumbing for Peras is ready, we will have to
-- extract the committee selection data from the chainDB to pass
-- it here, instead of relying on an empty the stake distribution.
--
-- Note that the empty stake distribution will cause all votes to
-- be considered invalid.
(pure (PerasVoteStakeDistr mempty))
``` [4](#0-3) 

The production vote-pool writer that will consume this distribution calls `validatePerasVote mkPerasParams sd vote`, where `sd` is the `PerasVoteStakeDistr` obtained from the STM action above: [5](#0-4) 

`validatePerasVote` stores whatever `PerasVoteStake` is in the distribution directly into `ValidatedPerasVote.vpvVoteStake` without any normalization: [6](#0-5) 

**Critical path to certificate forging:**

`stakeAboveThreshold` is called from `votesReachQuorum`, which is the gate for `forgePerasCert`: [7](#0-6) 

And from `updateCandidateVoteState` in `Vote/Aggregation.hs`: [8](#0-7) 

**The mismatch:** When the TODO stub is replaced with real ledger data, the Cardano ledger expresses pool stake in lovelace (e.g. `1_000_000_000_000`). The quorum threshold is `3/4`. The comparison `1_000_000_000_000 >= 3/4 + 2/100` is trivially `True`. Every vote from any pool with non-zero lovelace stake would immediately satisfy the quorum check, allowing a single inbound vote from an unprivileged peer to trigger `forgePerasCert`.

This is structurally identical to the Beanstalk bug: a constant (`3/4`) is compared against a value that is expected to be in the same unit but is actually in a different scale (absolute lovelace vs. normalized fraction), causing the branch to always fire incorrectly.

---

### Impact Explanation

If `PerasVoteStakeDistr` is populated with absolute lovelace values when the TODO is resolved:

1. Any single vote received from an unprivileged peer satisfies `stakeAboveThreshold`, bypassing the `>3/4` quorum requirement.
2. `forgePerasCert` is called, producing a `ValidatedPerasCert` with `vpcCertBoost = perasWeight = 15`.
3. The forged certificate boosts the adversary's chosen block by 15 chain-weight units, causing honest nodes to prefer that block in chain selection.
4. An adversary with even a single lovelace of registered stake can deterministically forge certificates for arbitrary blocks in every Peras round, permanently skewing chain selection.

This is a **bypass of Peras certificate/voting checks** enabling unauthorized certificate acceptance, matching the Critical impact tier.

---

### Likelihood Explanation

The likelihood is **medium-high**. The vulnerability is latent today only because the production code uses `PerasVoteStakeDistr mempty`. The TODO comment in `NodeToNode.hs` explicitly states this will be replaced with real ledger data. The comment on `PerasVoteStake` states there is no engineering consensus on how to normalize absolute ledger stake to a relative value. A developer implementing the plumbing who follows the natural path of reading `IndividualPoolStake` (an absolute lovelace `Rational` from the Cardano ledger) and inserting it directly into `PerasVoteStakeDistr` — without reading the TODO on `stakeAboveThreshold` — would introduce the live bug. The absence of a phantom-typed or newtype-enforced distinction between absolute and relative stake makes this error easy to make silently.

---

### Recommendation

1. **Enforce units at the type level.** Introduce distinct newtypes `AbsolutePerasVoteStake` and `RelativePerasVoteStake` so the compiler rejects mixing them. `stakeAboveThreshold` should accept only `RelativePerasVoteStake`.
2. **Normalize at the boundary.** The function that populates `PerasVoteStakeDistr` from the ledger must divide each pool's absolute stake by the total active stake before storing it, producing a value in `[0,1]` comparable to `3/4`.
3. **Resolve the TODO before enabling Peras.** The comment on `stakeAboveThreshold` must be resolved — not just noted — before the `PerasVoteStakeDistr mempty` stub is replaced with live ledger data.

---

### Proof of Concept

```haskell
-- Simulate what happens when the TODO stub is replaced with absolute lovelace values.
let absoluteStakeDistr = PerasVoteStakeDistr $
      Map.singleton someVoterId (PerasVoteStake (1_000_000_000_000 % 1))
    params = mkPerasParams  -- quorumThreshold = 3/4, safetyMargin = 2/100

-- A single vote from someVoterId:
let singleVoteStake = PerasVoteStake (1_000_000_000_000 % 1)

-- stakeAboveThreshold check:
-- 1_000_000_000_000 >= 3/4 + 2/100  =>  True
-- => votesReachQuorum returns Just, forgePerasCert is called
-- => certificate forged with boost=15 for adversary's chosen block
print (stakeAboveThreshold params singleVoteStake)  -- True
```

The comparison `1_000_000_000_000 >= 77/100` is `True`, so `votesReachQuorum` returns `Just` and `forgePerasCert` is invoked after a single inbound vote, bypassing the intended `>3/4` quorum requirement. [9](#0-8) [4](#0-3) [3](#0-2)
