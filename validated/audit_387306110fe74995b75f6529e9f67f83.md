Audit Report

## Title
`NativeFeeRestricted` Role Bypass via Yield Path in `init_transfer_resume` — (File: `near/omni-bridge/src/lib.rs`)

## Summary

The `init_transfer` function enforces the `NativeFeeRestricted` role only inside the branch condition that selects the direct execution path. When a restricted account submits a transfer with `native_token_fee > 0`, the condition evaluates to `false` and execution falls into the NEAR yield path, storing the transfer message (with the non-zero native fee) as yield arguments. The resume callback `init_transfer_resume` contains no `NativeFeeRestricted` check and calls `init_transfer_internal` unconditionally, completing the transfer with the non-zero native fee intact.

## Finding Description

In `init_transfer`, the guard is embedded in the second clause of the OR condition:

```rust
if self.try_to_transfer_balance_from_message_account(...).is_ok()
|| (self.has_storage_balance(&signer_id, ...)
    && (init_transfer_msg.native_token_fee.0 == 0
        || !self.acl_has_role(Role::NativeFeeRestricted.into(), signer_id.clone())))
``` [1](#0-0) 

For a `NativeFeeRestricted` account with `native_token_fee > 0`: the first clause fails (no pre-existing message account), and the second clause fails because `(native_fee == 0 || !NativeFeeRestricted)` is `false`. The overall condition is `false`, so the yield path is taken. The full `TransferMessage` — including the non-zero `native_fee` — is serialised into the yield arguments. [2](#0-1) 

The resume callback `init_transfer_resume` performs no role check before calling `init_transfer_internal`:

```rust
pub fn init_transfer_resume(...) -> U128 {
    self.remove_promise(&message_storage_account_id);
    ...
    if let Err(err) = self.try_to_transfer_balance_from_message_account(...) { ... }
    self.init_transfer_internal(transfer_message, storage_owner)  // ← no NativeFeeRestricted check
}
``` [3](#0-2) 

The yield is triggered by calling the public `storage_deposit` function with `account_id` set to the deterministically derived message-storage account. `storage_deposit` unconditionally calls `resume_promise`, which calls `env::promise_yield_resume`, firing `init_transfer_resume`. [4](#0-3) [5](#0-4) 

## Impact Explanation

This is a concrete role bypass matching the critical impact class: *"Unauthorized transaction, authorization bypass, role bypass… that lets an attacker execute bridge… actions."* Once `init_transfer_internal` completes, the transfer is registered on-chain with the non-zero `native_fee`. When a relayer calls `sign_transfer` and then `claim_fee`, `send_fee_internal` executes: for NEAR-origin transfers it transfers NEAR directly to the relayer; for non-NEAR origin chains it mints wrapped native tokens to the relayer. [6](#0-5) 

The DAO-assigned `NativeFeeRestricted` restriction is rendered completely ineffective for any account that deliberately triggers the yield path.

## Likelihood Explanation

Any account holding the `NativeFeeRestricted` role can exploit this without any additional privileges. The attacker simply submits `ft_transfer_call` without a pre-funded storage balance (or with a balance insufficient to cover the native fee), causing the yield path to be taken, then calls `storage_deposit` on the bridge contract specifying the derived message-storage account ID. The message-storage account ID is deterministically derived from public transfer parameters and is knowable before submission. The exploit is repeatable for every transfer.

## Recommendation

Add the `NativeFeeRestricted` check inside `init_transfer_resume` before calling `init_transfer_internal`, mirroring the guard in the direct path:

```rust
if transfer_message.fee.native_fee.0 != 0
    && self.acl_has_role(Role::NativeFeeRestricted.into(), storage_owner.clone())
{
    env::log_str("NativeFeeRestricted: native fee not allowed");
    return transfer_message.amount;
}
self.init_transfer_internal(transfer_message, storage_owner)
``` [7](#0-6) 

## Proof of Concept

1. DAO grants `NativeFeeRestricted` to `attacker.near`.
2. `attacker.near` calls `ft_transfer_call` on a registered token with `msg` containing `native_token_fee = 1_000_000_000_000_000_000_000_000` (1 NEAR). The attacker does **not** pre-fund their bridge storage balance (or ensures the message account does not yet exist).
3. `init_transfer` evaluates the branch: `try_to_transfer_balance_from_message_account` returns `Err(MessageAccountNotRegistered)`; the second clause is `false` because `NativeFeeRestricted && native_fee != 0`. Yield path is taken; `TransferMessage` with `native_fee = 1 NEAR` is stored as yield arguments.
4. `attacker.near` calls `storage_deposit` on the bridge contract with `account_id = <derived message account>`, attaching enough NEAR to cover `required_balance_for_account + native_fee + required_storage_for_message`.
5. `storage_deposit` calls `resume_promise` → `promise_yield_resume` → `init_transfer_resume` fires.
6. `try_to_transfer_balance_from_message_account` succeeds (message account now funded); `init_transfer_internal` is called with no role check. Transfer is registered with `native_fee = 1 NEAR`.
7. A relayer calls `sign_transfer` then `claim_fee`; `send_fee_internal` transfers 1 NEAR to the relayer. The `NativeFeeRestricted` restriction has been fully bypassed.

A sandbox integration test can reproduce this by extending the existing `test_native_fee_restriction` test in `near/omni-tests/src/native_fee_role.rs` to omit the pre-funded storage balance and add a `storage_deposit` call targeting the derived message account after the `ft_transfer_call`, then asserting that the resulting `TransferMessage` carries a non-zero `native_fee`.
