### Title
Peras Certificate Validation Stub Always Accepts Any Peer-Supplied Certificate, Enabling Unauthorized Chain-Selection Weight Boost - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` is an unconditional stub that returns `Right` for every certificate it receives, performing zero cryptographic or semantic checks. Both production `ObjectPoolWriter` constructors for Peras certificates (`makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB`) pass this stub directly into `processCerts`, which is the inbound handler for peer-supplied certificates. Any unprivileged peer can therefore inject a crafted `PerasCert` naming an arbitrary block, have it accepted as "validated", and cause the node to apply a `PerasWeight 15` boost to that block during chain selection — potentially making an adversarial fork appear heavier than the honest chain.

---

### Finding Description

**Root cause — stub validator that always succeeds**

The universal `BlockSupportsPeras` instance (the only instance in the codebase) implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params   -- always PerasWeight 15
      }
``` [1](#0-0) 

This instance is declared as `instance StandardHash blk => BlockSupportsPeras blk`, making it the sole implementation for all block types including production Cardano blocks. [2](#0-1) 

**Production inbound path uses the stub**

Both production `ObjectPoolWriter` constructors pass `validatePerasCert mkPerasParams` — the always-`Right` stub — as the validation function to `processCerts`:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
``` [3](#0-2)

**Chain-selection side-effect of an accepted certificate**

`addPerasCertAsync` enqueues a `ChainSelAddPerasCert` message. `chainSelSync` processes it: if the boosted block is in the VolatileDB and not on the current chain, it calls `chainSelectionForBlock` for that block:

```haskell
-- Trigger chain selection for the boosted block.
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [5](#0-4) 

`chainSelectionForBlock` reads the current `PerasWeightSnapshot` (which now includes the fraudulent boost) and calls `constructPreferableCandidates` / `preferAnchoredCandidate`. The weight comparison in `WeightedSelectView` is:

```haskell
wsvTotalWeight wsv = PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [6](#0-5) 

A fraudulent `PerasWeight 15` boost (from `mkPerasParams`) is equivalent to 15 extra blocks of chain length. A fork that is up to 15 blocks shorter than the honest chain will now appear heavier and be selected. [7](#0-6)

### Impact Explanation

**Severity: Critical — Peras certificate validation bypass enabling unauthorized chain-selection manipulation.**

An unprivileged peer can craft a `PerasCert` naming any block point it chooses. Because `validatePerasCert` never rejects anything, the cert is stored and its boost is applied to chain selection. The node may then switch to an adversarial fork that is up to 15 blocks shorter than the honest chain, violating the fundamental chain-selection invariant that the node always follows the heaviest valid chain. This constitutes:

- Bypass of Peras certificate checks enabling unauthorized certificate acceptance.
- Chain-selection manipulation that lets an unprivileged peer make an honest node prefer a non-canonical chain beyond the intended security assumptions.

---

### Likelihood Explanation

The Peras object-diffusion mini-protocol is reachable by any connected peer without authentication. The attacker only needs to:
1. Connect to the target node as a normal peer.
2. Send a `PerasCert` message with a crafted `pcCertBoostedBlock` pointing to a block on an adversarial fork.

No stake, no keys, no privileged access required. The only constraint is that the boosted block must be present in the node's VolatileDB (i.e., the attacker must have previously served that block to the node, which is also achievable by an unprivileged peer via the block-fetch protocol).

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
1. The certificate is signed by a quorum of eligible committee members for the claimed round.
2. The committee membership and stake weights are drawn from the correct epoch's ledger snapshot.
3. The boosted block point is consistent with the round number per the Peras protocol rules.

Until the real implementation is ready, the `TODO replace when actual plumbing is in place` comments in `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB` should be treated as blocking security issues, and inbound certificate processing from untrusted peers should be disabled or gated behind a feature flag. [8](#0-7)

### Proof of Concept

**Attacker-controlled entry path:**

1. Attacker connects to a target node as a normal peer via the Peras certificate object-diffusion mini-protocol.
2. Attacker has previously served block `B_adv` (on an adversarial fork, 14 blocks shorter than the honest chain) to the target node via block-fetch, so `B_adv` is in the node's VolatileDB.
3. Attacker sends a single `PerasCert` with `pcCertRound = <any new round>` and `pcCertBoostedBlock = blockPoint B_adv`.

**Processing trace:**

- `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right (ValidatedPerasCert { vpcCertBoost = PerasWeight 15 })` unconditionally.
- `addPerasCertAsync` enqueues the cert.
- `chainSelSync` finds `B_adv` in the VolatileDB, calls `chainSelectionForBlock` for it.
- `constructPreferableCandidates` reads the `PerasWeightSnapshot` which now maps `blockPoint B_adv` to `PerasWeight 15`.
- `preferAnchoredCandidate` computes `wsvTotalWeight` for the adversarial fork: `blockNo(B_adv) + 15`. If this exceeds `blockNo(honest_tip) + 0`, the node switches to the adversarial fork.

**Expected outcome:** The node switches to the adversarial fork, accepting an invalid chain that was only made to appear heavier by a fraudulent, cryptographically unverified certificate injected by an unprivileged peer.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do

  now <- systemTimeCurrent systemTime

    ([], validatedCerts) ->
      mapM_
