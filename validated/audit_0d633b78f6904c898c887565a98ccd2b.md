### Title
Hardcoded `boundX = 3` in `taylorExpCmpFirstNonLower` Causes Incorrect Local Sortition Seat Count for Large-Stake Non-Persistent Voters — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/LS.hs`)

---

### Summary

In `localSortitionNumSeats`, the Taylor-expansion helper `taylorExpCmpFirstNonLower` is called with a hardcoded constant `3` as the `boundX` parameter. The function's own contract requires `boundX = e^{|x|}` for correct error bounds. Because `x = -lambda` is passed, the correct value is `e^lambda`. When `lambda > ln(3) ≈ 1.099`, the hardcoded `3` underestimates the true bound, causing the error term to be too small, which can produce an incorrect `expectedSeats` result. This seat count feeds directly into vote-weight computation and Peras certificate quorum verification.

---

### Finding Description

`localSortitionNumSeats` computes how many non-persistent committee seats a voter is entitled to via a Poisson-distribution check implemented with a Taylor expansion:

```haskell
lambda :: FixedPoint
lambda =
  fromRational $
    fromIntegral numNonPersistentVoters
      * voterStake
      / totalNonPersistentStake

expectedSeats :: Int
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      3          -- ← hardcoded; should be exp lambda
      orders
      (-lambda)
``` [1](#0-0) 

The function signature and its inline documentation are explicit:

```haskell

taylorExpCmpFirstNonLower ::
  -- | boundX = e^{|x|} for correct error estimation
  a ->
``` [2](#0-1) 

The error term inside the algorithm is:

```haskell
errorTerm = abs (err' * boundX)
``` [3](#0-2) 

When `boundX` is smaller than `e^lambda`, `errorTerm` is underestimated. The "certainly BELOW" branch (`cmp < acc' - errorTerm`) fires too eagerly, causing the algorithm to skip past a Poisson-CDF threshold that `e^{-lambda}` is actually above. The returned index is then higher than the true seat count — the voter is granted more seats than the protocol entitles them to.

The codebase itself acknowledges the uncertainty via a TODO:

```haskell
-- TODO(peras): evaluate whether the limit used below (3) makes sense in
-- this context. One possible starting point would be to understand why
-- @checkLeaderNatValue@ (in Ledger) also uses 3 as its own limit when
-- computing slot leadership proofs.
--
-- Tracked by this issue:
-- https://github.com/tweag/cardano-peras/issues/234
``` [4](#0-3) 

The comparison to `checkLeaderNatValue` is misleading: in the Ledger, `3` is the *number of Taylor terms* (a `maxN`-style limit), not a `boundX` error-bound multiplier. The two uses are semantically different.

---

### Impact Explanation

`expectedSeats` flows into two security-critical paths:

**1. Vote weight computation (`implEligiblePartyVoteWeight`):**

```haskell
VoteWeight $
  fromIntegral (unLocalSortitionNumSeats (unNonZero numSeats))
    * stake
    / nonPersistentStake
``` [5](#0-4) 

An inflated `numSeats` directly inflates the `VoteWeight` returned for a non-persistent voter.

**2. Certificate verification (`implVerifyCert`):**

```haskell
let numSeats =
      localSortitionNumSeats
        (nonPersistentCommitteeSize committee)
        (totalNonPersistentStake committee)
        voterStake
        (normalizeVRFOutput vrfOutput)
case nonZero numSeats of
  Nothing ->
    Left (ZeroNonPersistentSeats seatIndex)
  Just nonZeroNumSeats ->
    pure $ WFALSNonPersistentMember ...
``` [6](#0-5) 

An inflated seat count accepted during certificate verification means the aggregate vote weight attributed to non-persistent voters is overstated. The quorum check:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
``` [7](#0-6) 

…can be satisfied with less real stake than the protocol requires, allowing an invalid Peras certificate to be accepted. An accepted certificate grants a `PerasWeight` boost to a block, directly affecting chain selection.

---

### Likelihood Explanation

`lambda = numNonPersistentVoters * voterStake / totalNonPersistentStake`. For `lambda > ln(3) ≈ 1.099` a voter needs to hold more than `1.099 / numNonPersistentVoters` of the total non-persistent stake. With a committee of 10 non-persistent seats, any voter holding more than ~11 % of non-persistent stake triggers the bug. Large stake pools routinely exceed this threshold. The adversary does not control their VRF output, so the direction of the error (inflated vs. deflated seats) is not guaranteed on any single election, but the incorrect error bounds are active on every election where `lambda > ln(3)`, making accidental or deliberate exploitation plausible over many rounds.

---

### Recommendation

Replace the hardcoded `3` with the mathematically correct bound:

```haskell
-- boundX must be e^{|x|} = e^lambda for correct error estimation
expectedSeats :: Int
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      (exp lambda)   -- was: 3
      orders
      (-lambda)
```

If `exp` is not available for `FixedPoint`, a sufficiently large conservative upper bound (e.g., `exp (fromIntegral numNonPersistentVoters)`) should be used, or the computation should be restructured to use exact rational arithmetic for the Poisson CDF comparison.

---

### Proof of Concept

Consider a committee with `numNonPersistentVoters = 10` and a voter holding 20 % of non-persistent stake:

```
lambda = 10 * 0.20 / 1.0 = 2.0
e^lambda = e^2 ≈ 7.389
boundX used = 3   (underestimate by factor ~2.46)
```

At iteration `n`, `errorTerm = |err' * 3|` instead of `|err' * 7.389|`. The "certainly BELOW" condition fires ~2.46× too early. For a VRF output whose normalized value places it near the boundary between 2 and 3 seats in the Poisson CDF, the algorithm may classify the threshold as BELOW (skip it) and return `expectedSeats = 3` instead of the correct `2`. The voter's `VoteWeight` is then `3 * stake / totalNonPersistentStake` instead of `2 * stake / totalNonPersistentStake` — a 50 % inflation. Aggregated across multiple such voters in a certificate, the total vote weight can exceed the quorum threshold even when the true stake-weighted support does not.
