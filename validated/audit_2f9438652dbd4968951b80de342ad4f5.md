### Title
Attacker Can Front-Run `request_refund` to Redirect BTC Refunds to Attacker-Controlled Address — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`request_refund` is publicly callable by any NEAR account. The registry key `utxo_storage_key` (`{tx_id}@{vout}`) is fully deterministic from the Bitcoin transaction. An attacker who observes a deposit's `deposit_msg` (emitted via `LogDepositAddress` events) can race to call `request_refund` first, injecting their own `refund_address`. This blocks the legitimate user's refund request and, if the DAO does not reject the attacker's entry within the `unsafe_refund_timelock_sec` window, allows the attacker to drain the user's BTC via `execute_refund`.

---

### Finding Description

`request_refund_callback` enforces a first-writer-wins uniqueness guard on `refund_requests`: [1](#0-0) 

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
```

The key is constructed as `{tx_id}@{vout}`: [2](#0-1) 

Both fields are fully public on the Bitcoin blockchain. The `deposit_msg` needed to pass the script-pubkey check is broadcast in the `LogDepositAddress` event emitted by `get_user_deposit_address`: [3](#0-2) 

`request_refund` carries no caller restriction — it is `#[payable]` and `#[pause(except(roles(Role::DAO)))]` only, with no `#[trusted_relayer]` at the function level: [4](#0-3) 

When `deposit_msg.refund_address` is `None` (the standard deposit path), the `refund_address` parameter is taken verbatim from the caller: [5](#0-4) 

So an attacker can supply their own BTC address as `refund_address` while using the legitimate user's `deposit_msg`, and the script-pubkey check still passes because the deposit address is derived solely from `deposit_msg`.

After the request is stored, `execute_refund` is also publicly callable by anyone once the timelock elapses: [6](#0-5) 

The timelock applied when `deposit_msg.refund_address` is `None` is `unsafe_refund_timelock_sec`, described as "longer … to give DAO/Operator time to reject suspicious requests": [7](#0-6) 

If the DAO does not reject within that window, `execute_refund` sends the BTC to the attacker's address.

---

### Impact Explanation

- The legitimate user's `request_refund` call panics with `"Refund request already exists for this UTXO"`, permanently blocking their ability to reclaim BTC until the DAO intervenes.
- If the DAO fails to reject the attacker's entry before `unsafe_refund_timelock_sec` expires, `execute_refund` transfers the deposit UTXO to the attacker's BTC address — a complete loss of the user's bridged funds.
- This maps to **Medium** (attacker-triggered temporary locking of bridged funds requiring operator intervention) escalating to **Critical** (theft of user funds) if the DAO does not act in time.

---

### Likelihood Explanation

- `deposit_msg` is publicly observable from `LogDepositAddress` events emitted by `get_user_deposit_address`.
- The Bitcoin `tx_id` and `vout` are public on-chain data.
- The attacker only needs to pay the NEAR storage deposit (`required_balance_for_request_refund`) and submit a valid Light Client proof — both are permissionless.
- No privileged access, key compromise, or majority hash-power is required.
- The attack window is open from the moment the Bitcoin deposit confirms until the legitimate user calls `request_refund`.

---

### Recommendation

1. **Bind `refund_address` to the depositor**: Require the caller of `request_refund` to be the `deposit_msg.recipient_id`, or require `deposit_msg.refund_address` to be pre-set (non-`None`) so the refund destination is fixed at deposit time and cannot be overridden by a third party.
2. **Alternatively**, if open submission must be preserved, store all submitted `refund_address` values per UTXO and let the DAO select the legitimate one, rather than using a first-writer-wins model.

---

### Proof of Concept

1. User calls `get_user_deposit_address(deposit_msg)` — event `LogDepositAddress` is emitted with the full `deposit_msg` (where `refund_address = None`).
2. User sends BTC to the derived address; the deposit is never finalized via `verify_deposit`.
3. Attacker observes the `LogDepositAddress` event and the Bitcoin transaction (`tx_id`, `vout`).
4. Attacker calls `request_refund(deposit_msg, attacker_btc_addr, tx_bytes, vout, proof, None)` with the same `deposit_msg` but `refund_address = attacker_btc_addr`, attaching the required NEAR storage deposit.
5. Light Client verification succeeds; `request_refund_callback` stores the entry keyed by `{tx_id}@{vout}` with `refund_address = attacker_btc_addr`.
6. Legitimate user calls `request_refund` — panics: `"Refund request already exists for this UTXO"`.
7. After `unsafe_refund_timelock_sec` elapses without DAO rejection, attacker calls `execute_refund({tx_id}@{vout}, None)`.
8. The bridge constructs and signs a refund transaction paying `attacker_btc_addr`; user's BTC is stolen.

    #[allow(clippy::too_many_arguments)]
    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
