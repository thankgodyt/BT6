### Title
Users Cannot Claim Lost-Found nBTC or Execute Refunds When Bridge Is Paused — (`contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

The `claim_lost_found` and `execute_refund` functions are both gated by `#[pause(except(roles(Role::DAO)))]`. When the bridge is paused, ordinary users are permanently blocked from retrieving nBTC already held in the bridge's `lost_found` ledger and from executing pending BTC refund requests, even though those funds belong entirely to the user and no new risk is introduced by allowing the retrieval.

---

### Finding Description

The bridge uses the `near-plugins` `Pausable` trait. Every user-facing function in `bridge.rs` and `token_receiver.rs` carries the macro `#[pause(except(roles(Role::DAO)))]`, which causes the function to panic for any non-DAO caller when the contract is paused.

Two functions are directly affected:

**1. `claim_lost_found`** [1](#0-0) 

When a withdrawal is cancelled (via `cancel_withdraw`) and the bridge's attempt to return nBTC to the user fails, `transfer_nbtc_callback` stores the amount in the `lost_found` map: [2](#0-1) 

The nBTC is now held by the bridge contract on behalf of the user. The only recovery path is `claim_lost_found`. Because that function carries `#[pause(except(roles(Role::DAO)))]`, a paused bridge makes the nBTC permanently inaccessible to the user until the DAO unpauses.

**2. `execute_refund`** [3](#0-2) 

A user who has already paid the anti-spam storage deposit and submitted a `request_refund` (proven via Light Client) is waiting only for the timelock to elapse before calling `execute_refund` to recover their BTC. If the bridge is paused during that window, `execute_refund` panics for the user, leaving their BTC stranded in the bridge's deposit address with no permissionless recovery path.

The pause roles are `Role::PauseManager` and `Role::UnpauseManager`: [4](#0-3) 

---

### Impact Explanation

- **`claim_lost_found`**: nBTC that has already been transferred to the bridge and credited to `lost_found` is locked for the entire duration of the pause. The user holds no nBTC and receives no BTC — a direct, temporary loss of bridged funds requiring operator intervention to resolve.
- **`execute_refund`**: BTC deposited to the bridge's MPC-controlled address cannot be returned to the user. The refund request is valid and the timelock has passed, yet the user is blocked. This constitutes a stuck bridge state requiring operator intervention.

Both impacts match: **Medium — stuck bridge state requiring operator intervention / attacker-triggered temporary locking of bridged funds.**

---

### Likelihood Explanation

The bridge is designed to be paused in response to security incidents or operational emergencies. The `PauseManager` role is granted at initialization and is a normal operational lever. Any pause — even a legitimate, non-malicious one — simultaneously blocks all user fund-recovery paths. Users with funds in `lost_found` or with pending refund requests at the moment of a pause have no recourse until the DAO acts. **Likelihood: Medium.**

---

### Recommendation

Remove `#[pause(except(roles(Role::DAO)))]` from `claim_lost_found` and `execute_refund` (and, by extension, `execute_refund`'s Zcash counterpart if present). These functions only return funds that are already owed to the user; blocking them during a pause provides no additional security and directly harms users. Deposits and new withdrawal initiations (`ft_on_transfer`, `verify_deposit_v2`) may remain paused.

---

### Proof of Concept

**Scenario A — `claim_lost_found` blocked:**

1. User calls `ft_transfer_call` on the nBTC contract with a `Withdraw` message (bridge is live). `ft_on_transfer` succeeds; nBTC is held by the bridge.
2. DAO/Operator calls `cancel_withdraw`. The bridge calls `internal_transfer_nbtc` to return nBTC to the user.
3. The `ft_transfer` cross-contract call fails (e.g., user account not registered). `transfer_nbtc_callback` stores the amount in `lost_found`.
4. `PauseManager` pauses the bridge (legitimate security event).
5. User calls `claim_lost_found`. The `#[pause(except(roles(Role::DAO)))]` macro panics: user cannot retrieve their nBTC.
6. nBTC remains locked in `lost_found` until the DAO unpauses.

**Scenario B — `execute_refund` blocked:**

1. User sends BTC to the bridge's deposit address and calls `request_refund` with a valid Light Client proof, paying the storage deposit.
2. `request_refund_callback` stores the `RefundRequest`.
3. The refund timelock elapses.
4. `PauseManager` pauses the bridge.
5. User calls `execute_refund`. The `#[pause(except(roles(Role::DAO)))]` macro panics.
6. User's BTC remains stranded in the bridge's MPC-controlled deposit address until the DAO unpauses.
