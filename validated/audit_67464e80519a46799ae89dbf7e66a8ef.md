### Title
Peras `validatePerasCert` Stub Unconditionally Accepts Any Certificate, Allowing Pre-Computed Future Block Hash to Gain Unearned Chain Selection Weight — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance's `validatePerasCert` method unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or semantic checks. An unprivileged peer can pre-compute the hash of a block it will produce in a future slot, craft a `PerasCert` naming that hash as `pcCertBoostedBlock`, and submit it to honest nodes. Because validation always succeeds, the certificate is stored in the `PerasCertDB` and, when the block later arrives, chain selection is re-triggered with the certificate's full weight boost applied — weight the attacker was never entitled to.

This is the direct consensus analog of the referral-minter bug: just as a minter pre-computes its own future token ID and passes it as `referrerTokenId` to earn referral points for itself, a block producer pre-computes its own future block hash and embeds it in a crafted certificate to earn Peras weight for itself.

---

### Finding Description

In `BlockSupportsPeras.hs`, the catch-all `BlockSupportsPeras` instance (the only instance currently present in the repository) implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This is the **only** `BlockSupportsPeras` instance in the repository. The comment explicitly acknowledges that no validation is performed. Every `PerasCert` received from any peer — regardless of its `pcRoundNo`, `pcBoostedBlock`, `pcVoters`, or `pcSignature` — is wrapped in `ValidatedPerasCert` and accepted.

The `PerasCert` type carries two attacker-controlled fields:

```haskell
data PerasCert blk = PerasCert
  { pcCertRound        :: PerasRoundNo
  , pcCertBoostedBlock :: Point blk
  }
``` [2](#0-1) 

Once a `ValidatedPerasCert` is produced, it is submitted to the ChainDB via `addPerasCertAsync`, which accepts a `WithArrivalTime (ValidatedPerasCert blk)`: [3](#0-2) 

Inside `chainSelSync`, the certificate's `boostedBlock` is extracted and used to look up the block in the `VolatileDB`. If the block is not yet present, the code silently exits early with a trace message — but the certificate **remains stored** in the `PerasCertDB`:

```haskell
Nothing -> do
  lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
  idExitEarly $ addedCertRes
Just boostedHdr -> pure boostedHdr
-- Trigger chain selection for the boosted block.
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

When the attacker's block subsequently arrives and is added to the `VolatileDB`, `chainSelectionForBlock` is called again — this time finding the certificate already in the `PerasCertDB` — and the block receives the full Peras weight boost during chain selection. No check is ever made that the certificate's `pcCertBoostedBlock` was produced by a legitimate quorum, that the round number is consistent with the boosted block's slot, or that the boosted block is not the attacker's own future block.

The `perasVR1B` voting rule is supposed to enforce that a voter only votes for a block that extends the most recently certified one:

```haskell
vr1b =
  case latestCertSeen of
    NotOrigin cert ->
      Bool (lcsCandidateBlockExtendsCert cert)
    Origin ->
      Bool True
``` [5](#0-4) 

But this rule governs **local voting decisions**, not the acceptance of inbound certificates. There is no corresponding inbound check that rejects a certificate whose `pcCertBoostedBlock` does not exist, is in the future, or was produced by the same party submitting the certificate.

### Impact Explanation

An unprivileged peer (a block producer with any non-zero stake) can cause honest nodes to apply a Peras weight boost to a block of the attacker's choosing. By targeting the attacker's own future block, the attacker's chain gains extra weight in `preferAnchoredCandidate` / `compareChainDiffs`, causing honest nodes to switch to the attacker's fork even when an honest chain of equal or greater length exists. This is a chain selection bug that lets an unprivileged peer make honest nodes prefer a non-canonical chain beyond the intended security assumptions of Peras.

**Impact class**: High — chain selection bug enabling an unprivileged peer to make an honest node prefer a non-canonical chain.

---

### Likelihood Explanation

A Peras-era block producer can deterministically compute the hash of a block it will produce at a future slot (the hash is a function of the block body, which the producer controls). The attacker needs only to:
1. Be a registered stake pool (any non-zero stake suffices).
2. Craft a `PerasCert` CBOR payload with the pre-computed hash as `pcCertBoostedBlock`.
3. Deliver it to honest nodes via the Peras certificate miniprotocol before the block is produced.

No key compromise, social engineering, or stake majority is required. The attack is repeatable every round. Likelihood is **medium** (requires being a block producer, but no other privilege).

---

### Recommendation

1. **Implement `validatePerasCert` properly**: verify the BLS aggregate signature over `(pcRoundNo, pcBoostedBlock)`, confirm the voter bitmap is consistent with the committee for that round, and check that `pcBoostedBlock`'s slot falls within the valid candidate window for `pcRoundNo` (i.e., at least `L` slots before the round start).
2. **Add an existence check**: reject certificates whose `pcCertBoostedBlock` is not yet known to the node, or defer acceptance until the block is received and validated — do not store the certificate unconditionally.
3. **Add a self-boost check**: reject or flag certificates where the submitting peer's pool ID matches the producer of `pcCertBoostedBlock`, analogous to the referral-minter fix of verifying `referrerTokenId != newItemId`.

### Proof of Concept

```
1. Attacker (pool operator) computes VRF output for slot S in round R.
2. Attacker constructs the block body B they will forge at slot S.
3. Attacker computes H = hash(B).
4. Attacker serialises PerasCert { pcRoundNo = R-1, pcCertBoostedBlock = Point S H }
   as a valid CBOR payload (no BLS signature required — validatePerasCert ignores it).
5. Attacker sends the certificate to honest nodes via the Peras cert miniprotocol.
6. Honest nodes call validatePerasCert → Right (unconditionally).
7. Certificate is stored in PerasCertDB with boost weight W.
8. At slot S, attacker forges block B and diffuses it.
9. chainSelectionForBlock is called; PerasCertDB already contains the certificate.
10. Attacker's chain receives weight boost W; honest nodes switch to attacker's fork
    even if an honest chain of equal block count exists.
```
