### Title
`revalidateHeader` Envelope Check Silently Discarded in Production Builds via `assertWithMsg` No-Op - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Util/Assert.hs`)

---

### Summary

`revalidateHeader` is the fast-path header revalidation function used during ImmutableDB replay at node startup and during chain-selection fork switches. It guards its envelope check (block number, slot monotonicity, prev-hash chain) exclusively with `assertWithMsg`. However, `assertWithMsg` is a **compile-time conditional no-op**: when the `asserts` Cabal flag is absent — which is the default (`default: False`) — the `ENABLE_ASSERTIONS` CPP symbol is never defined, and `assertWithMsg` unconditionally discards its `Either String ()` argument and returns the value unchanged. In every standard production build, `revalidateHeader` therefore performs **zero validation**: neither the envelope check nor any cryptographic check (KES/VRF are already skipped by design via `reupdateChainDepState`). A crafted or corrupted block in the ImmutableDB with an invalid envelope is silently accepted, and the node builds and durably uses an incorrect ledger state.

---

### Finding Description

**`assertWithMsg` is a no-op in production:**

```haskell
-- Assert.hs
assertWithMsg :: HasCallStack => Either String () -> a -> a
#if ENABLE_ASSERTIONS
assertWithMsg (Left msg) _ = error msg
#endif
assertWithMsg _ a = a   -- ← always reached when flag `asserts` is False
``` [1](#0-0) 

The `asserts` flag defaults to `False`:

```cabal
flag asserts
  description: Enable assertions
  manual: False
  default: False          -- ← ENABLE_ASSERTIONS never set by default
``` [2](#0-1) 

The CPP guard that would set `ENABLE_ASSERTIONS`:

```cabal
if flag(asserts)
  ghc-options: -fno-ignore-asserts
  cpp-options: -DENABLE_ASSERTIONS
``` [3](#0-2) 

**`revalidateHeader` relies entirely on `assertWithMsg` for its envelope check:**

```haskell
revalidateHeader cfg ledgerView hdr st =
  assertWithMsg envelopeCheck $          -- ← no-op in production
    HeaderState
      (NotOrigin (getAnnTip hdr))
      chainDepState'                     -- ← reupdateChainDepState: no KES/VRF
 where
  envelopeCheck = runExcept $ withExcept show $
    validateEnvelope cfg ledgerView (untickedHeaderStateTip st) hdr
``` [4](#0-3) 

The contrast with `validateHeader` (the full-validation path) is stark: `validateHeader` uses `withExcept` inside `Except`, which propagates errors as values in the type system and cannot be compiled away. [5](#0-4) 

**`revalidateHeader` is called from `reapplyBlockLedgerResult`**, the function used to replay blocks from the ImmutableDB during node startup:

```haskell
reapplyBlockLedgerResult evs cfg blk TickedExtLedgerState{..} =
  (\l -> ExtLedgerState l hdr) <$> castLedgerResult ledgerResult
 where
  ...
  hdr = revalidateHeader          -- ← zero validation in production
          (getExtLedgerCfg cfg)
          ledgerView
          (getHeader blk)
          tickedHeaderState
``` [6](#0-5) 

The `reupdateChainDepState` called inside `revalidateHeader` explicitly skips KES and VRF signature verification by design: [7](#0-6)

### Impact Explanation

In a standard production node (built without `-DENABLE_ASSERTIONS`), `revalidateHeader` is a pure state-update function with no guards. A block in the ImmutableDB whose header has:

- a non-consecutive block number,
- a non-monotonic slot number, or
- a broken prev-hash chain

will be silently accepted during startup replay. The resulting `ExtLedgerState` — built on top of an invalid header state — is then used as the authoritative ledger state for all subsequent operations: chain selection, mempool validation, and ledger queries. Because the ImmutableDB is the node's source of truth and its contents are replayed unconditionally at startup, the corrupted ledger state is durable across restarts.

This maps to the **High** impact category: *LedgerDB/ImmutableDB replay bug that causes durable use of the wrong ledger state.*

---

### Likelihood Explanation

The `asserts` flag is `False` by default and is explicitly described as an opt-in for testing/benchmarking only. The documentation explicitly warns operators to enable it only temporarily. Every standard `cardano-node` production deployment runs without assertions. An attacker with write access to the ImmutableDB files (local reproduction, private testnet, or a node operator whose disk is accessible) can craft a block with an invalid envelope. The node will accept it silently on the next startup and operate on the corrupted ledger state indefinitely.

---

### Recommendation

The envelope check in `revalidateHeader` must not be gated behind a compile-time assertion. Replace the `assertWithMsg` guard with a runtime-unconditional check that throws an `error` (or equivalent) regardless of the `asserts` flag, mirroring how `validateHeader` propagates errors through the `Except` monad. The `reupdateChainDepState` skip of cryptographic checks is intentional and acceptable; the envelope check is not.

```haskell
-- Proposed fix: unconditional envelope guard
revalidateHeader cfg ledgerView hdr st =
  case envelopeCheck of
    Left msg -> error ("revalidateHeader: envelope invariant violated: " <> msg)
    Right () -> HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'
 where
  ...
```

---

### Proof of Concept

1. Build `cardano-node` (or any consensus consumer) **without** the `asserts` flag — the default.
2. Locate the ImmutableDB chunk file for any chunk.
3. Corrupt the `blockNo` field of any block header in that chunk so that it is not consecutive with its predecessor (e.g., increment it by 2).
4. Start the node. Observe that startup completes without error.
5. With assertions enabled (`flags: +asserts`), the same corruption causes an immediate `error` call during replay, confirming that the check exists but is compiled away in production.

The root cause is the CPP-conditional `assertWithMsg` in `Ouroboros.Consensus.Util.Assert` combined with the `default: False` for the `asserts` flag in `ouroboros-consensus.cabal`, which together ensure that `revalidateHeader`'s only validation guard is always a no-op in production deployments.
