Audit Report

## Title
Unvalidated `fee_recipient` in `sign_transfer` Allows Any Trusted Relayer to Steal Relayer Fees - (File: near/omni-bridge/src/lib.rs)

## Summary

`sign_transfer` accepts a caller-supplied `fee_recipient: Option<AccountId>` parameter and embeds it verbatim into the MPC-signed `TransferMessagePayload` with no check that it equals `env::predecessor_account_id()` or any stored value. Any trusted relayer can call `sign_transfer` on any pending non-zero-fee transfer, inject their own account as `fee_recipient`, obtain a valid MPC signature over that payload, finalize the transfer on the destination chain, and then successfully call `claim_fee` on NEAR — diverting the entire relayer fee to themselves.

## Finding Description

In `near/omni-bridge/src/lib.rs`, `sign_transfer` (lines 447–521) is gated by `#[trusted_relayer]` but accepts `fee_recipient: Option<AccountId>` as a free caller parameter. The only validation performed is on the `fee` amount (lines 455–460); `fee_recipient` is placed directly into `TransferMessagePayload` at line 498 without any identity check:

```rust
let transfer_payload = TransferMessagePayload {
    ...
    fee_recipient,   // taken verbatim from caller
    ...
};
```

The MPC signer then signs a hash of this payload (lines 502–515). In `sign_transfer_callback` (lines 648–668), the transfer message is only removed from storage when `fee.is_zero()` (lines 656–658); for non-zero-fee transfers it persists, so multiple relayers can race to call `sign_transfer` on the same transfer.

On the destination chain, `OmniBridge.sol::finTransfer` (lines 279–313) verifies the MPC signature over the borsh-encoded payload — which includes `feeRecipient` — and emits a `FinTransfer` event containing the attacker-chosen value.

Back on NEAR, `claim_fee_callback` (lines 1079–1086) checks:

```rust
require!(
    fee_recipient == *predecessor_account_id,
    BridgeError::OnlyFeeRecipientCanClaim.as_ref()
);
```

Because `fee_recipient` in the proof is whatever the attacker embedded at signing time, this check is trivially satisfied by the attacker calling `claim_fee` from their own account.

## Impact Explanation

This is a concrete fee mis-accounting impact: the relayer fee — which is part of the user's locked/burned tokens — is permanently diverted to the attacker. The user's transfer completes correctly (recipient and amount are read from the stored transfer message, not from the caller), but the fee is mis-accounted to the attacker's account. This matches the allowed critical impact class: "fee mis-accounting… that changes user or protocol balances."

## Likelihood Explanation

Becoming a trusted relayer requires only staking the configured amount (default 1,000 NEAR) and waiting the waiting period (default 7 days, ~604,800,000,000,000 ns) — no admin approval is needed. Any economically motivated actor can stake, become a trusted relayer, and systematically call `sign_transfer` on every pending non-zero-fee transfer with their own account as `fee_recipient`. The attack is fully on-chain, requires no off-chain coordination, and is profitable at scale. Because non-zero-fee transfer messages persist in storage after signing, the attacker is not limited to a single block window.

## Recommendation

Bind `fee_recipient` to the caller inside `sign_transfer`. Replace the caller-supplied parameter with `env::predecessor_account_id()`, or add an explicit guard before constructing the payload:

```rust
if let Some(ref recipient) = fee_recipient {
    require!(
        recipient == &env::predecessor_account_id(),
        BridgeError::InvalidFeeRecipient.as_ref()
    );
}
```

This ensures that only the relayer who actually calls `sign_transfer` can be designated as the fee recipient for that signing operation.

## Proof of Concept

1. Attacker stakes 1,000 NEAR via `apply_for_trusted_relayer`, waits the waiting period, becomes a trusted relayer.
2. Attacker observes a `TransferMessage` with `transfer_id: T` and `fee: 100` in `pending_transfers`.
3. Attacker calls `sign_transfer(T, Some("attacker.near"), Some(Fee{fee:100,...}))`.
   - Fee validation passes (matches stored fee).
   - `TransferMessagePayload { ..., fee_recipient: Some("attacker.near"), ... }` is constructed.
   - MPC signs the payload hash.
4. `sign_transfer_callback` fires: fee is non-zero, so the transfer message is **not** removed from storage. `SignTransferEvent` is emitted with the attacker-controlled payload.
5. Attacker submits the signed payload to `OmniBridge.sol::finTransfer`. Signature verifies (MPC signed it). `FinTransfer` event is emitted with `feeRecipient = "attacker.near"`.
6. Attacker generates an EVM Merkle proof of the `FinTransfer` event and calls `claim_fee` on NEAR from `attacker.near`.
7. `claim_fee_callback` extracts `fee_recipient = "attacker.near"` from the proof, checks `"attacker.near" == predecessor_account_id ("attacker.near")` — passes. Attacker receives 100 tokens.
8. The legitimate relayer who was meant to service the transfer receives nothing; the fee is permanently diverted.
