Audit Report

## Title
`normalize_amount` Floor Division Causes `sign_transfer` to Permanently Panic for Sub-Threshold Transfers, Locking User Funds — (File: near/omni-bridge/src/lib.rs)

## Summary
The `normalize_amount` helper uses integer floor division, so any transfer amount (minus fee) smaller than `10^(origin_decimals - decimals)` normalizes to zero. `sign_transfer` unconditionally requires the normalized result to be strictly positive, but `init_transfer` never validates this precondition before accepting and storing the deposit. Once stored, the transfer can never be signed, and no independent cancellation or refund path exists, permanently locking the deposited tokens.

## Finding Description
`normalize_amount` (line 2784–2787) divides by `10^diff_decimals` using integer division:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

`sign_transfer` (lines 475–485) calls this function and then panics if the result is zero:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

`init_transfer` (lines 554–557) only validates `fee < amount`:

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```

There is no check that `normalize_amount(amount - fee) > 0` at deposit time. For any token where `origin_decimals > decimals`, a deposit of `amount - fee < 10^diff_decimals` passes `init_transfer`, stores the transfer message, and then causes every subsequent `sign_transfer` call to panic unconditionally.

The only path that calls `remove_transfer_message` is `sign_transfer_callback` (line 657), which is only reached after a successful MPC signing response — impossible if `sign_transfer` panics before the MPC call is dispatched. `claim_fee_callback` similarly requires a destination-chain finalization proof, which can never be generated without a successful signing. There is no independent `cancel_transfer` entry point.

The code comment at line 2781–2783 acknowledges that "dust stays locked/burned" when fee = 0 and references SECURITY.md, but this describes sub-unit remainder after normalization of a valid (non-zero) normalized amount. The claim's scenario — where the *entire* `amount - fee` is below the normalization threshold, making the normalized amount exactly zero and causing `sign_transfer` to always panic — is a distinct and more severe case: the transfer is completely unprocessable, not merely losing a dust remainder.

## Impact Explanation
Tokens deposited via `ft_transfer_call` → `ft_on_transfer` → `init_transfer` are immediately held by the bridge contract. If `amount - fee < 10^(origin_decimals - decimals)`, the MPC signing step can never succeed, and the tokens are permanently frozen with no recovery mechanism. This is concrete permanent freezing of bridged funds, matching the critical allowed impact scope.

## Likelihood Explanation
The condition requires: (1) a token registered with `origin_decimals > decimals` (standard for bridging high-precision tokens), and (2) a user depositing an amount below the normalization threshold. Both are realistic in normal usage — UI rounding errors, dust amounts, or deliberate small transfers. No privileged access is required; any token holder can trigger this via public `ft_transfer_call`.

## Recommendation
Add a normalization check inside `init_transfer` (or `init_transfer_internal`) before the transfer message is stored:

```rust
let normalized = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

Alternatively, enforce a minimum deposit equal to `10^(origin_decimals - decimals)` at the `ft_on_transfer` entry point so the transfer is rejected before tokens are locked.

## Proof of Concept
1. Register a token with `origin_decimals = 24`, `decimals = 18` (`diff_decimals = 6`, threshold = 1,000,000).
2. Call `ft_transfer_call` with `amount = 500_000`, `fee = 0`. `init_transfer` accepts it: `0 < 500_000` passes. Transfer message is stored; tokens are held by the bridge.
3. Call `sign_transfer` for the stored `transfer_id`.
4. `normalize_amount(500_000, {24, 18}) = 500_000 / 1_000_000 = 0` (floor division).
5. `require!(0 > 0, ...)` panics — `sign_transfer` always fails.
6. `sign_transfer_callback` is never reached, so `remove_transfer_message` is never called.
7. No `cancel_transfer` exists; `claim_fee_callback` requires destination-chain proof that can never be generated. Funds are permanently locked. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
