### Title
`validatePerasCert` Unconditionally Accepts Any Inbound Peras Certificate Without Cryptographic Verification - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance's `validatePerasCert` implementation is a stub that unconditionally returns `Right` (success) for every certificate it receives, performing zero cryptographic or structural validation. This stub is wired directly into the production inbound certificate processing pipeline (`makePerasCertPoolWriterFromChainDB`). An unprivileged peer can send a crafted `PerasCert` with an arbitrary round number and boosted block point; the certificate will pass "validation" and be stored in the `PerasCertDB`, where it influences Peras chain-selection weight boosts.

---

### Finding Description

**Root cause — stub validator always returns `Right`:** [1](#0-0) 

```haskell

-- possible 'PerasValidationErr' variants
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This is the **only** instance of `BlockSupportsPeras` in the codebase — a universal instance covering every block type: [2](#0-1) 

**Production wiring — stub is passed directly to the inbound cert handler:**

Both production pool-writer constructors pass `validatePerasCert mkPerasParams` as the validator: [3](#0-2) 

`processCerts` calls this validator on every certificate received from a peer before storing it: [4](#0-3) 

Because `validatePerasCert` never returns `Left`, the `partitionEithers` branch that would reject the batch is unreachable. Every certificate, regardless of content, is timestamped and stored.

**Secondary missing check — `validatePerasVote` skips signature verification:** [5](#0-4) 

`validatePerasVote` only checks that the voter ID appears in the stake distribution map; it never verifies the vote's cryptographic signature, VRF eligibility proof, or round-number validity. A peer can impersonate any registered pool and inject votes that accumulate toward a quorum, which then triggers `forgePerasCert` — itself another stub that also performs no validation.

**Attacker-controlled entry path:**

```
Peer sends crafted PerasCert over ObjectDiffusion miniprotocol
  → makePerasCertPoolWriterFromChainDB.opwAddObjects
  → processCerts
  → validatePerasCert mkPerasParams cert   ← always Right
  → ChainDB.addPerasCertAsync              ← cert stored
  → Peras weight boost applied to attacker-chosen block
  → chain selection may prefer attacker's fork
```

---

### Impact Explanation

Peras certificates grant a configurable weight boost (`perasWeight`) to the block they certify. Once a fake certificate is stored, `getPerasWeightSnapshot` returns a snapshot that includes the boost for the attacker-chosen block. Chain selection compares candidate fragments using these weights; a sufficiently large boost can cause an honest node to switch to a shorter or non-canonical fork, violating the common-prefix and chain-quality properties that Ouroboros safety relies on.

**Impact category:** High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.

---

### Likelihood Explanation

The attack requires only a network peer connection and the ability to send a well-formed (but cryptographically invalid) `PerasCert` CBOR message. No keys, stake, or privileged access are needed. The Peras certificate diffusion miniprotocol is active whenever the node is running with Peras support compiled in. The stub is the universal instance, so there is no code path that performs real validation.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
1. Verifies the aggregate BLS signature over the claimed voter set against the election ID and candidate block.
2. Checks that the voter set meets the quorum threshold for the given round.
3. Verifies each voter's eligibility (VRF proof for non-persistent members, persistent-membership check for persistent members) against the epoch nonce and stake distribution.
4. Validates the round number is within the acceptable window relative to the current slot.

Until the real implementation is ready, the stub should be replaced with `Left PerasValidationErr` (reject all) rather than `Right` (accept all), so that no unverified certificates can influence chain selection.

Similarly, `validatePerasVote` must verify the vote's cryptographic signature before accepting it.

---

### Proof of Concept

1. Connect to a node running with Peras support as an unprivileged peer.
2. Construct a `PerasCert` CBOR value with `pcCertRound = <target round>` and `pcCertBoostedBlock = <attacker-chosen block point>`.
3. Send it via the ObjectDiffusion miniprotocol's cert channel.
4. Observe via `getPerasWeightSnapshot` that the attacker-chosen block now carries a `perasWeight` boost.
5. If the boosted block is on a competing fork, the node's chain selection will prefer that fork over the honest canonical chain. [1](#0-0) [6](#0-5) [4](#0-3)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
