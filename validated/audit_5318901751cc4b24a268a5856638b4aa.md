### Title
`claim_lost_found` Restricted to `predecessor_account_id()` Permanently Locks nBTC for Smart-Contract Beneficiaries — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

The `claim_lost_found` function enforces that only `env::predecessor_account_id()` can retrieve nBTC that was placed into the `lost_found` map after a failed `internal_transfer_nbtc` callback. If the beneficiary is a smart contract that cannot itself invoke `claim_lost_found` (e.g., an immutable DeFi contract or a contract with no such dispatch path), those nBTC tokens are permanently locked inside the bridge with no operator-accessible recovery path.

---

### Finding Description

When a cross-contract nBTC transfer fails (e.g., during a `cancel_withdraw` refund), `transfer_nbtc_callback` stores the undelivered amount in the `lost_found` map keyed by the beneficiary's `AccountId`: [1](#0-0) 

The only recovery path is `claim_lost_found`: [2](#0-1) 

The function unconditionally uses `env::predecessor_account_id()` as both the lookup key and the transfer recipient. There is no parameter allowing a third party (operator, DAO, or any other account) to claim on behalf of the beneficiary. If the beneficiary is a smart contract that has no code path to call `claim_lost_found` on the bridge, the nBTC is irrecoverably locked.

The `lost_found` map is populated whenever `internal_transfer_nbtc` fails: [3](#0-2) 

`internal_transfer_nbtc` is called from `claim_lost_found` itself (line 459), and from any other bridge path that needs to return nBTC to a user account. A smart-contract account that initiated a withdrawal via `ft_transfer_call` and whose cancel/refund nBTC transfer then fails will have its balance silently moved into `lost_found` with no accessible recovery mechanism.

---

### Impact Explanation

nBTC tokens belonging to a smart-contract beneficiary become permanently locked inside the bridge's `lost_found` map. The bridge holds the underlying BTC backing those tokens, so the BTC is also effectively inaccessible to the user. There is no DAO or operator function to forcibly redirect or recover `lost_found` balances on behalf of another account. This constitutes a permanent, irreversible loss of user funds without any theft — matching the **Medium** impact class: *"stuck bridge state requiring operator intervention"* (and here, even operator intervention is impossible).

---

### Likelihood Explanation

Any NEAR smart contract that:
1. Calls `ft_transfer_call` on nBTC to initiate a withdrawal, and
2. Has its cancel-withdraw nBTC refund fail (e.g., because the contract's nBTC storage is not registered, or the contract is paused/upgraded/immutable),

will have its nBTC silently moved to `lost_found`. This is a realistic scenario for DeFi integrations (e.g., a lending protocol or aggregator that routes BTC withdrawals through the bridge). The failure mode is silent — the `LostFoundNbtc` event is emitted but no revert occurs, so the caller may not notice until they try to access the funds.

---

### Recommendation

Allow an optional `account_id` parameter in `claim_lost_found`, or add a separate privileged (DAO/Operator) function that can transfer `lost_found` balances to their rightful owner. The simplest fix mirrors the referenced report's recommendation: allow any caller to trigger the claim for a specified `account_id`, sending the funds to that account rather than to `predecessor_account_id()`.

---

### Proof of Concept

1. Smart contract `defi.near` calls `ft_transfer_call` on nBTC, triggering `ft_on_transfer` in the bridge and initiating a withdrawal.
2. The bridge operator calls `cancel_withdraw`, which internally calls `internal_transfer_nbtc(&defi.near, amount)`.
3. The nBTC `ft_transfer` to `defi.near` fails (e.g., `defi.near` has no nBTC storage deposit).
4. `transfer_nbtc_callback` fires: `lost_found["defi.near"] += amount`.
5. `defi.near` has no method that calls `claim_lost_found` on the bridge (it is an immutable contract deployed before the bridge existed).
6. No DAO or operator function exists to recover `lost_found["defi.near"]`.
7. The nBTC — and the BTC backing it — is permanently locked. [2](#0-1) [4](#0-3)

    pub fn transfer_nbtc_callback(&mut self, account_id: AccountId, amount: U128) -> bool {
        let promise_success = is_promise_success();
        let event = Event::TransferNbtc {
            account_id: &account_id,
            amount,
            success: promise_success,
        };
        if !promise_success {
            self.data_mut()
                .lost_found
                .entry(account_id.clone())
                .and_modify(|v| *v += amount.0)
                .or_insert(amount.0);
            Event::LostFoundNbtc {
                account_id: &account_id,
                amount,
            }
            .emit();
        }
        event.emit();
        promise_success

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn claim_lost_found(&mut self) -> Promise {
        assert_one_yocto();
        let account_id = env::predecessor_account_id();
        let amount = self
            .data_mut()
            .lost_found
            .remove(&account_id)
            .expect("The account does not have lostfound");
        self.internal_transfer_nbtc(&account_id, amount)
    }
