### Title
Attacker Can Frontrun `request_refund` to Redirect Victim's BTC Refund to Attacker-Controlled Address — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`request_refund` has no caller restriction and, when `deposit_msg.refund_address` is `None`, accepts any caller-supplied Bitcoin `refund_address`. Because the UTXO key (`txid:vout`) is derived from public Bitcoin chain data, an attacker can race the legitimate depositor to register a refund request for the same UTXO with the attacker's own Bitcoin address. The victim's subsequent `request_refund` call is then rejected with "Refund request already exists for this UTXO", and after the `unsafe_refund_timelock_sec` elapses the attacker can call `execute_refund` to receive the victim's BTC.

---

### Finding Description

`internal_request_refund` performs no check that the caller is the NEAR account encoded in `deposit_msg.recipient_id`:

```rust
pub(crate) fn internal_request_refund(
    &self,
    deposit_msg: DepositMsg,
    refund_address: String,
    ...
) -> Promise {
    require!(
        env::attached_deposit() >= self.required_balance_for_request_refund(),
        "Insufficient deposit for storage"
    );
    ...
    if let Some(msg_refund_address) = &deposit_msg.refund_address {
        require!(
            msg_refund_address == &refund_address,
            "refund_address does not match deposit_msg.refund_address"
        );
    }
``` [1](#0-0) 

The `refund_address` guard only fires when `deposit_msg.refund_address` is `Some`. When it is `None` (the common case where the depositor did not pre-authorize a refund address), any caller may supply any Bitcoin address.

In `request_refund_callback`, the UTXO key is derived from the public `txid:vout` pair and a duplicate-request guard rejects any second registration for the same key:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [2](#0-1) 

Once the attacker's request is stored, `build_refund_output` constructs the Bitcoin output paying to `refund_request.refund_address`:

```rust
pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
    ...
    TxOut {
        value: Amount::from_sat(...),
        script_pubkey: refund_script_pubkey,
    }
}
``` [3](#0-2) 

The attacker-controlled `refund_address` is stored verbatim in `RefundRequest` and later used to build the signed Bitcoin transaction that releases the funds. [4](#0-3) 

---

### Impact Explanation

**Critical.** After the `unsafe_refund_timelock_sec` elapses, the attacker calls `execute_refund`, which builds a PSBT paying the full deposit amount (minus gas fee) to the attacker's Bitcoin address. The victim's BTC is permanently redirected. The DAO `reject_refund` mechanism is the only backstop, but it is not guaranteed to act within the timelock window and cannot distinguish a malicious request from a legitimate one without off-chain monitoring.

---

### Likelihood Explanation

**High.** Bitcoin transactions are fully public. Any observer can read the `txid`, `vout`, and OP\_RETURN `deposit_msg` of a failed deposit, reconstruct the exact arguments needed for `request_refund`, and submit the call before the victim. The only cost is the NEAR storage deposit attached to the call (`required_balance_for_request_refund`), which is refunded on success. No special privilege or leaked key is required.

---

### Recommendation

Bind the refund request to the NEAR account encoded in `deposit_msg.recipient_id`. In `internal_request_refund` (or its callback), add:

```rust
require!(
    env::predecessor_account_id() == deposit_msg.recipient_id,
    "Only the deposit recipient may request a refund"
);
```

Alternatively, when `deposit_msg.refund_address` is `None`, derive the `refund_address` from the depositor's registered NEAR account rather than accepting it as a free parameter from the caller.

---

### Proof of Concept

1. Alice sends 0.1 BTC to the bridge with `deposit_msg = { recipient_id: "alice.near", refund_address: None, ... }`. The deposit fails (e.g., light client not yet synced).
2. Bob observes the Bitcoin transaction on-chain, reads `txid`, `vout`, and the OP\_RETURN `deposit_msg`.
3. Bob calls `request_refund(deposit_msg, bob_btc_address, tx_bytes, vout, proof)` with a valid Merkle proof and attaches the required NEAR storage deposit.
4. Bob's `request_refund_callback` succeeds; `refund_requests[utxo_key]` now stores `refund_address = bob_btc_address`.
5. Alice calls `request_refund(deposit_msg, alice_btc_address, ...)`. Her callback panics: `"Refund request already exists for this UTXO"`.
6. After `unsafe_refund_timelock_sec`, Bob calls `execute_refund(utxo_key, ...)`. The bridge builds and signs a Bitcoin transaction paying Alice's 0.1 BTC (minus gas fee) to Bob's address.
7. Bob broadcasts the signed transaction; Alice's BTC is stolen.

    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(

            ),
            script_pubkey: refund_script_pubkey,
        }
