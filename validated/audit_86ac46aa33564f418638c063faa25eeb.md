### Title
Unregistered Recipient in `safe_mint` Permanently Locks Minted nBTC in Bridge Account - (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

In `contracts/nbtc/src/lib.rs`, the `safe_mint` function mints nBTC tokens into the bridge's own account first, then attempts to transfer them to the user. If the recipient's NEAR account is not registered for nBTC storage, the function silently returns without transferring the tokens, leaving them permanently locked in the bridge's nBTC balance with no recovery path.

---

### Finding Description

The `safe_mint` function in the nBTC token contract follows this sequence:

1. Unconditionally mints `amount` tokens into `bridge_id`'s balance via `internal_deposit`.
2. Checks whether `account_id` (the deposit recipient) has a registered storage account.
3. If the account is **not registered**, returns `PromiseOrValue::Value(U128(0))` immediately — the tokens remain in the bridge's nBTC balance and are never forwarded to the user. [1](#0-0) 

The critical path is:

```
internal_deposit(&self.bridge_id, amount)   // tokens minted to bridge
if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0));  // silent return, tokens stuck
}
```

No event is emitted for the failed delivery, no `lost_found` entry is created, and there is no mechanism for the user to retry or recover the tokens. The `lost_found` map that exists in the satoshi-bridge contract is only populated by the `transfer_nbtc_callback` path (used for `ft_transfer` failures), not by `safe_mint` failures. [2](#0-1) 

The bridge's nBTC balance is also used as the source for the `burn` function during withdrawals: [3](#0-2) 

This means the stuck tokens inflate the bridge's nBTC balance and could be silently consumed by future legitimate withdrawal burns, compounding the accounting error.

---

### Impact Explanation

**Critical — Permanent loss of user funds.**

A user who deposits BTC on-chain and whose NEAR account is not registered for nBTC storage will have their nBTC minted into the bridge's own account and permanently inaccessible. There is no refund of the underlying BTC, no event to alert the user, no `lost_found` entry, and no operator-callable recovery function for this specific case. The deposited BTC is locked on the Bitcoin side (spent to the bridge's deposit address) and the corresponding nBTC is locked in the bridge's nBTC balance.

---

### Likelihood Explanation

**Medium.** NEAR NEP-141 requires explicit storage registration before receiving tokens. A user who is new to the nBTC token, or who uses a fresh NEAR account, or who interacts via a smart contract account that has not pre-registered, will trigger this path. The deposit flow is fully permissionless — any user can submit a valid BTC transaction and proof — making this reachable without any privileged access.

---

### Recommendation

Before minting, check whether the recipient account is registered. If not, either:

1. **Reject the mint** and revert the deposit verification, requiring the user to register first; or
2. **Register the account automatically** (paying the storage cost from attached deposit or protocol reserves) before calling `internal_deposit` and transferring; or
3. **Store the undelivered amount in `lost_found`** and emit a `LostFoundNbtc` event so the user can recover it after registering, mirroring the existing `transfer_nbtc_callback` recovery pattern. [4](#0-3) 

---

### Proof of Concept

1. User deposits BTC to their bridge deposit address on-chain.
2. A relayer submits the transaction and Merkle proof to `satoshi-bridge` via `verify_deposit_v2`.
3. The bridge verifies the proof and calls `safe_mint(account_id, amount, msg)` on the nBTC contract.
4. `safe_mint` calls `self.token.internal_deposit(&self.bridge_id, amount.into())` — nBTC is minted into the bridge's own nBTC balance.
5. `self.token.accounts.get(&account_id)` returns `None` because the user's NEAR account has never registered for nBTC storage.
6. `safe_mint` returns `PromiseOrValue::Value(U128(0))` — no transfer occurs, no event is emitted, no `lost_found` entry is created.
7. The user's BTC is spent (locked in the bridge's Bitcoin UTXO set), and the corresponding nBTC sits permanently in the bridge's own nBTC balance with no recovery path. [1](#0-0)

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }
