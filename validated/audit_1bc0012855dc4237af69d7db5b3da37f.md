Audit Report

## Title
Unchecked Burn via `.detach()` Enables Silent Failure and Cross-Chain Double-Spend — (`File: near/omni-bridge/src/lib.rs`)

## Summary

`burn_tokens_if_needed` schedules a cross-contract `burn` call with `.detach()`, permanently discarding the promise result. If the burn fails for any reason — gas exhaustion under the 3 TGas budget, a panic in the token contract, or any future contract upgrade — the bridge emits `InitTransferEvent` unconditionally, the MPC signs the payload, and the destination chain mints tokens while the NEAR-side supply is never reduced. This is a direct cross-chain double-spend.

## Finding Description

`burn_tokens_if_needed` is confirmed in the codebase at lines 1806–1813:

```rust
fn burn_tokens_if_needed(&self, token: AccountId, amount: U128) {
    if self.is_deployed_token(&token) {
        ext_token::ext(token)
            .with_static_gas(BURN_TOKEN_GAS)
            .burn(amount)
            .detach();
    }
}
```

`BURN_TOKEN_GAS = Gas::from_tgas(3)` (line 72). The analogous mint operation uses `MINT_TOKEN_GAS = Gas::from_tgas(5)` (line 73) — a 67% larger budget for a structurally identical cross-contract call — making the 3 TGas budget for burn demonstrably inconsistent and tight.

The token contract's `burn` function (omni-token/src/lib.rs, lines 146–151) executes `assert_controller()` (predecessor check) followed by `internal_withdraw`, which performs a `LookupMap` storage read, a storage write for the updated balance, and a total-supply update. Under 3 TGas this is at risk of exhaustion.

**Outbound path** (`init_transfer_internal`, lines 1850–1863): `burn_tokens_if_needed` is called at line 1851, then `InitTransferEvent` is emitted unconditionally at line 1863 regardless of whether the burn succeeded. There is no callback, no state revert, and no guard between the two.

**Inbound refund path** (`fin_transfer_send_tokens_callback`, lines 1702–1718): when `is_refund_required` is true, `burn_tokens_if_needed` is called at line 1703 to destroy already-minted tokens. A silent failure here leaves those tokens in circulation on NEAR while the cross-chain transfer is supposed to be rolled back.

Existing guards (`is_deployed_token`) only gate whether the burn is attempted at all; they provide no protection against a failed burn.

## Impact Explanation

A silent burn failure on the outbound path allows the same token value to exist simultaneously on NEAR (held by the bridge, unburned) and on the destination chain (freshly minted via `finTransfer`). This is a concrete cross-chain double-spend / unauthorized minting of bridged funds — squarely within the Critical allowed impact scope: *unauthorized minting* and *balance/escrow mis-accounting that changes protocol balances*.

On the inbound refund path, a silent failure inflates the NEAR-side token supply without a corresponding backing on the origin chain.

## Likelihood Explanation

Any user who initiates a cross-chain transfer of a protocol-deployed bridge token can trigger the outbound path. The burn failure condition is not attacker-controlled but is a systemic property of the code: if 3 TGas is insufficient for the current `burn` implementation (plausible given `MINT_TOKEN_GAS = 5 TGas` for an equivalent operation), every such transfer silently fails to burn. No special privileges, social engineering, or external compromise is required. The failure produces no on-chain signal, making it undetectable without off-chain monitoring.

## Recommendation

Replace the fire-and-forget pattern with a chained callback that verifies the burn succeeded before emitting `InitTransferEvent` or finalising the refund path. The callback should panic or revert state on burn failure. At minimum, raise `BURN_TOKEN_GAS` to at least match `MINT_TOKEN_GAS` (5 TGas) or higher (≥ 10 TGas) to provide a safe margin, and add a result-checking callback analogous to the `require(swapToken.transferFrom(...))` pattern.

## Proof of Concept

1. Identify a protocol-deployed bridge token (passes `is_deployed_token` check).
2. Call `ft_transfer_call` on that token targeting the bridge with a valid `InitTransferMsg`.
3. The bridge's `ft_on_transfer` → `init_transfer` → `init_transfer_internal` fires `burn_tokens_if_needed` with 3 TGas and `.detach()`.
4. If the burn promise fails (gas exhausted or any panic), `InitTransferEvent` is still emitted at line 1863 — the bridge retains the tokens.
5. A relayer calls `sign_transfer`; MPC produces a valid signature over the transfer payload.
6. Present the signature on the EVM destination chain via `finTransfer`; the destination chain mints the full amount.
7. Result: tokens exist both at the bridge on NEAR (unburned) and freshly minted on the destination chain — a complete cross-chain double-spend.

To confirm the burn failure condition: instrument a local NEAR testnet, attach a gas profiler to the `burn` call, and verify whether execution cost exceeds 3 TGas.
