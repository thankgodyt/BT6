### Title
Unauthenticated Refund Request Allows Attacker to Redirect BTC Refunds to Arbitrary Address - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary

When a user deposits BTC using a `DepositMsg` with `refund_address: None`, any unprivileged NEAR account can call `request_refund` and supply an arbitrary attacker-controlled BTC address as the refund destination. Because the refund request is not cryptographically tied to the depositor's identity, an attacker can front-run the legitimate depositor's refund request, lock out the depositor from submitting their own, and — if the DAO fails to reject within `unsafe_refund_timelock_sec` — steal the deposited BTC.

### Finding Description

`get_deposit_path` hashes the entire `DepositMsg` (including `recipient_id`) to derive the deposit address, but the `request_refund` entry point performs no check that the caller is the depositor or that the supplied `refund_address` belongs to the caller. [1](#0-0) 

`request_refund` is publicly callable. When `deposit_msg.refund_address` is `None`, the contract accepts any `refund_address` string from the caller without restriction: [2](#0-1) 

The callback stores the attacker-supplied address verbatim: [3](#0-2) 

Only one refund request can exist per UTXO. Once the attacker's request is stored, the legitimate depositor's subsequent `request_refund` call fails with `"Refund request already exists for this UTXO"`: [4](#0-3) 

After `unsafe_refund_timelock_sec` elapses, `execute_refund` is also publicly callable. The refund PSBT is built to pay the stored (attacker-controlled) `refund_address`: [5](#0-4) [6](#0-5) 

The only on-chain mitigation is the longer `unsafe_refund_timelock_sec` and the DAO's ability to reject. This is an operational control, not a cryptographic one. [7](#0-6) 

### Impact Explanation

An attacker who front-runs the depositor's `request_refund` call with their own BTC address as `refund_address` can steal the deposited BTC if the DAO does not reject the request within `unsafe_refund_timelock_sec`. This is a direct, significant loss of user funds — qualifying as Critical under the allowed impact scope ("Significant loss, theft, destruction, or permanent locking of user or protocol funds").

### Likelihood Explanation

- All inputs needed for the attack (`deposit_msg`, `tx_bytes`, `vout`, Merkle proof) are observable on-chain or emitted as NEAR events via `LogDepositAddress`.
- The attack requires only a NEAR account with enough NEAR for the storage deposit (`required_balance_for_request_refund`).
- Deposits without a pre-authorized `refund_address` are a documented and supported use case.
- The DAO must actively monitor every refund request and reject malicious ones within the timelock window — a single missed rejection results in theft.

### Recommendation

Bind the refund request to the depositor's identity. The simplest fix is to record `env::predecessor_account_id()` in the `RefundRequest` at submission time and enforce in `execute_refund` that either (a) the caller matches the stored submitter, or (b) the `refund_address` was pre-authorized in `deposit_msg.refund_address`. Alternatively, require that `deposit_msg.refund_address` always be set before a refund can be requested, eliminating the unauthenticated path entirely.

### Proof of Concept

1. Alice deposits BTC to the address derived from `DepositMsg { recipient_id: alice, refund_address: None, ... }`.
2. The relayer never calls `verify_deposit` (relayer is down).
3. Bob observes Alice's deposit on-chain and calls:
   ```
   request_refund(
     deposit_msg = alice_deposit_msg,   // public, derivable from on-chain data
     refund_address = "bob_btc_address",
     tx_bytes = alice_tx_bytes,
     vout = 0,
     proof = <valid merkle proof>
   )
   ```
4. The contract accepts the call because `alice_deposit_msg.refund_address` is `None` — no identity check is performed.
5. Alice's subsequent `request_refund` fails: `"Refund request already exists for this UTXO"`.
6. After `unsafe_refund_timelock_sec` passes (and if the DAO does not reject), Bob calls `execute_refund(utxo_storage_key)`.
7. The bridge builds and MPC-signs a Bitcoin transaction paying `bob_btc_address`. Alice's BTC is stolen.

    /// Build a transparent refund output paying `refund_amount` to `refund_address`.
    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
    }

    pub(crate) fn internal_execute_refund(
        &mut self,
        utxo_storage_key: String,
        timelock_sec: u64,
        _chain_specific_data: Option<ChainSpecificData>,
    ) -> PromiseOrValue<()> {
        let refund_request = self.load_refund_request_for_execute(&utxo_storage_key, timelock_sec);
        let RefundExecutionInputs {
            outpoint,
            deposit_output,
            refund_amount,
        } = self.refund_execution_inputs(&refund_request);
        let refund_output = self.build_refund_output(&refund_request.refund_address, refund_amount);

        let mut psbt = PsbtWrapper::new(vec![outpoint], vec![refund_output]);
        psbt.set_input_utxo(vec![deposit_output]);

        let caller = env::predecessor_account_id();
        self.finalize_refund_with_psbt(
            caller,
            refund_request,
            psbt,
            refund_amount,
            utxo_storage_key,
        );
        PromiseOrValue::Value(())
    }
