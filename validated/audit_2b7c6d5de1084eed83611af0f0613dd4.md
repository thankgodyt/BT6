### Title
Peras Vote Validation Stub Accepts Forged Votes Without Signature Verification, Enabling Unauthorized Certificate Acceptance and Chain-Selection Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasVote` implementation is an explicitly incomplete stub that performs no cryptographic signature verification on inbound Peras votes. It only checks whether the voter ID appears in the **current** stake distribution, not a historical snapshot from the voting round. Because the `PerasVote` wire type carries no signature field, any unprivileged peer can forge votes for any pool operator in the stake distribution, drive a round to quorum for an attacker-chosen block, and cause a Peras certificate to be forged for that block — directly manipulating chain selection.

---

### Finding Description

**Root cause — no signature field and no signature check in `validatePerasVote`:**

The `PerasVote` data type in the production placeholder instance carries only three fields — round number, block point, and voter ID — with no cryptographic signature:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound   :: PerasRoundNo
  , pvVoteBlock   :: Point blk
  , pvVoteVoterId :: PerasVoterId
  }
``` [1](#0-0) 

The `validatePerasVote` implementation — explicitly marked TODO — accepts any vote whose voter ID appears in the current stake distribution, performing no signature check whatsoever:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [2](#0-1) 

**Attacker-controlled entry path — `processVotes`:**

Inbound votes from peers flow through `processVotes` in the object-diffusion layer. The function reads the current DB vote-ID set atomically, filters out already-seen IDs, then calls `validatePerasVote` for each remaining vote. Because the stub always returns `Right` for any known voter ID, every forged vote passes:

```haskell
validationResults <- atomically $ do
  alreadyInDb <- alreadyInDbSTM
  let votesNotAlreadyInDb =
        filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
  mapM validateVote votesNotAlreadyInDb
``` [3](#0-2) 

Both production writers (`makePerasVotePoolWriterFromChainDB` and `makePerasVotePoolWriterFromVoteDB`) pass the same stub validator:

```haskell
(\vote -> getStakeDistrSTM >>= \sd ->
    pure $ validatePerasVote mkPerasParams sd vote)
``` [4](#0-3) 

**Compounding issue — deduplication key excludes the voted block:**

`PerasVoteId` is `(roundNo, voterId)` with no block field:

```haskell
data PerasVoteId blk = PerasVoteId
  { pviRoundNo :: !PerasRoundNo
  , pviVoterId :: !PerasVoterId
  }
``` [5](#0-4) 

The model explicitly acknowledges this is an unverified assumption:

> "NOTE: this is under the assumption that a voter doesn't cast two different votes for the same round (that is, with the same ID but different body)." [6](#0-5) 

Because the deduplication filter runs once over the snapshot of `alreadyInDb` at the start of the atomic block, a batch containing two forged votes for the same voter and round but different blocks will have **both** pass the filter. The inner `implAddVote` STM check prevents double-counting, but the first vote in the batch determines which block receives the voter's stake — giving the attacker full control over which block is boosted. [7](#0-6) 

**Stake distribution is current, not historical:**

`validatePerasVote` is called with `getStakeDistrSTM`, the live current stake distribution, not a snapshot anchored to the voting round. This mirrors the ERC20VotesUpgradeable removal: vote weight is resolved against the present state rather than the state at the time the vote was cast, breaking the historical-snapshot invariant that prevents stake-weight manipulation across rounds. [8](#0-7)

### Impact Explanation

An unprivileged peer can:

1. Read the public stake distribution to enumerate high-stake pool operators.
2. Construct `PerasVote` objects for those operators targeting an attacker-chosen block (no key material required — the type has no signature field).
3. Submit the forged votes via the object-diffusion mini-protocol.
4. Each forged vote passes `validatePerasVote` and is inserted into `PerasVoteDB` with the real pool's stake weight.
5. Once the accumulated forged stake exceeds the quorum threshold, `updatePerasRoundVoteStates` triggers `forgePerasCert`, producing a `ValidatedPerasCert` for the attacker's block.
6. That certificate boosts the attacker's block in chain selection, causing honest nodes to prefer a non-canonical or adversarially chosen chain.

This satisfies the **Critical** impact class: bypass of Peras vote signature validation enabling unauthorized certificate acceptance, and a **High** chain-selection impact: an unprivileged peer can make honest nodes prefer a non-canonical chain beyond the intended security assumptions. [9](#0-8) 

---

### Likelihood Explanation

The attack requires only a standard peer connection and knowledge of the public stake distribution (available on-chain). No key material, stake majority, or privileged access is needed. The forged vote construction is deterministic. The only prerequisite is that the Peras voting round is active, which is a normal protocol condition. Likelihood is **High**.

---

### Recommendation

1. **Add a cryptographic signature field to `PerasVote`** (e.g., a KES or VRF-derived signature over `(roundNo, block, voterId)`). The `BlockSupportsPeras` typeclass already provides the extension point; the associated `PerasVote blk` type must be enriched before the placeholder instance is replaced.

2. **Implement real signature verification in `validatePerasVote`** — reject any vote whose signature does not verify under the pool's registered cold/hot key.

3. **Anchor vote-weight lookup to a historical stake snapshot** from the epoch corresponding to the voting round, not the live `getStakeDistrSTM`. This directly mirrors the ERC20VotesUpgradeable historical-balance protection.

4. **Detect and reject equivocating votes** (same `(roundNo, voterId)`, different block) at the `processVotes` layer rather than silently ignoring the second vote, to prevent order-of-arrival manipulation of which block receives a voter's stake.

### Proof of Concept

```
-- Attacker connects as a peer and sends a batch of forged votes:

let forgedVotes =
      [ PerasVote
          { pvVoteRound   = targetRound        -- active Peras round
          , pvVoteBlock   = attackerBlock       -- attacker's chosen block
          , pvVoteVoterId = highStakePoolId_1   -- any pool in stake distr
          }
      , PerasVote
          { pvVoteRound   = targetRound
          , pvVoteBlock   = attackerBlock
          , pvVoteVoterId = highStakePoolId_2
          }
      -- ... repeat until combined stake > quorum threshold
      ]

-- processVotes receives the batch:
--   1. alreadyInDb is empty (fresh round) → all votes pass the filter
--   2. validatePerasVote checks only Map.lookup voterId stakeDistr → Right for each
--   3. All forged votes are added to PerasVoteDB with real pool stake weights
--   4. updatePerasRoundVoteStates detects quorum → forgePerasCert fires
--   5. ValidatedPerasCert for attackerBlock is stored and used in chain selection
```

The forged votes require no cryptographic material because `PerasVote` carries no signature field and `validatePerasVote` performs no signature check. [10](#0-9) [11](#0-10)

processVotes ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
