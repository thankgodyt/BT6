### Title
Incorrect `withdraw_fee` Deduction in Cancel-Withdraw Refund Calculation Causes Permanent User Fund Loss - (File: contracts/satoshi-bridge/src/nbtc/burn.rs)

### Summary

In `verify_withdraw_burn_callback`, when a withdrawal is cancelled by the protocol via `cancel_withdraw` (producing a `WithdrawCancelRbf` pending state), the refund returned to the user incorrectly subtracts the original `withdraw_fee` in addition to the cancel gas fee (`burn_amount`). Since the withdrawal never completed and no BTC was delivered, the bridge fee should not be collected. The user permanently loses their bridge fee on every protocol-initiated cancellation.

### Finding Description

When a user initiates a withdrawal via `ft_on_transfer`, the bridge records a `BTCPendingInfo` with:

- `transfer_amount` = total nBTC sent by user (e.g. 200,000)
- `withdraw_fee` = bridge fee (e.g. 50,000)
- `burn_amount` = `actual_received_amount + gas_fee` (e.g. 150,000) [1](#0-0) 

When the protocol calls `cancel_withdraw` (DAO/Operator role, triggered when a withdrawal is stuck past `max_btc_tx_pending_sec`), `internal_cancel_withdraw` creates a new `WithdrawCancelRbf` pending info via `init_rbf_btc_pending_info`, which copies `transfer_amount` and `withdraw_fee` from the original, then overwrites `burn_amount = gas_fee` (only the cancel transaction's gas fee, e.g. 20,000): [2](#0-1) 

After the cancel RBF transaction is signed and confirmed on-chain, `verify_withdraw_burn_callback` computes the user's refund as:

```rust
let refund = if btc_pending_info.is_cancel_withdraw_rbf() {
    btc_pending_info
        .transfer_amount
        .saturating_sub(btc_pending_info.withdraw_fee + btc_pending_info.burn_amount)
} else {
    0
};
``` [3](#0-2) 

This yields `refund = 200,000 − 50,000 − 20,000 = 130,000` instead of the correct `200,000 − 20,000 = 180,000`. The `withdraw_fee` (50,000) is silently absorbed: it is not burned (only `burn_amount = 20,000` is burned), not returned to the user, but is instead credited to `cur_available_protocol_fee` and the relayer via the fee split computed from `withdraw_fee`: [4](#0-3) 

The `init_rbf_btc_pending_info` helper preserves the original `withdraw_fee` field into the cancel RBF record, which is the proximate cause of the erroneous deduction: [5](#0-4) 

### Impact Explanation

Every time the protocol legitimately cancels a stuck withdrawal, the user loses their full `withdraw_fee` in nBTC. With the default config `fee_min = 50,000` satoshis, a user who withdraws the minimum amount loses 50,000 satoshis of nBTC permanently. The lost amount is silently redistributed to the protocol fee pool and relayer — it is not stuck, but it is taken from the user without any BTC having been delivered. This constitutes a significant, permanent loss of user funds on every cancel-withdraw event.

**Impact class:** Critical — Significant loss of user funds.

### Likelihood Explanation

`cancel_withdraw` is a standard protocol operation callable by any DAO or Operator account when a withdrawal transaction has not been confirmed within `max_btc_tx_pending_sec`. This is a routine operational path, not an edge case. Any withdrawal that stalls on-chain (due to low fees, mempool congestion, or chain reorganization) will trigger this path, causing the user to lose their bridge fee on top of the cancel gas cost. [6](#0-5) 

### Recommendation

Remove `withdraw_fee` from the refund subtraction in `verify_withdraw_burn_callback`. When the state is `WithdrawCancelRbf`, the withdrawal was never completed, so no bridge fee should be collected. The correct refund is:

```rust
let refund = if btc_pending_info.is_cancel_withdraw_rbf() {
    btc_pending_info
        .transfer_amount
        .saturating_sub(btc_pending_info.burn_amount)
} else {
    0
};
```

Additionally, ensure the `protocol_fee` and `relayer_fee` are not computed from `withdraw_fee` for cancel-RBF paths, since no bridge fee is owed.

### Proof of Concept

1. Alice sends 200,000 nBTC to the bridge via `ft_transfer_call` with a `Withdraw` message. Bridge records: `transfer_amount=200000`, `withdraw_fee=50000`, `burn_amount=150000`.
2. The withdrawal transaction is broadcast to Bitcoin but is not confirmed within `max_btc_tx_pending_sec`.
3. DAO/Operator calls `cancel_withdraw(original_btc_pending_verify_id, outputs)`. `internal_cancel_withdraw` creates a `WithdrawCancelRbf` record with `transfer_amount=200000`, `withdraw_fee=50000`, `burn_amount=20000` (cancel gas fee).
4. The cancel RBF transaction is signed and confirmed. A relayer calls `verify_withdraw`.
5. `verify_withdraw_burn_callback` computes `refund = 200000 − 50000 − 20000 = 130000` and transfers 130,000 nBTC back to Alice.
6. Alice sent 200,000 nBTC, received 0 BTC (withdrawal cancelled), and got back only 130,000 nBTC. She permanently lost 50,000 nBTC (the bridge fee) despite the withdrawal never completing. [3](#0-2) [7](#0-6)
