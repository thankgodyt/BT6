### Title
Corrupted UTXO Storage via Zero-Byte Replacement in `safe_verify_deposit` Path Permanently Locks Bridged BTC - (File: `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

---

### Summary

In `internal_safe_verify_deposit_entry`, when the submitted `tx_bytes` exceed 10,000 bytes in length, the code replaces the entire transaction byte array with 300 zero bytes (`vec![0u8; 300]`) before storing the UTXO. The log message claims it is "truncating to 300 bytes," but the actual behavior is wholesale replacement with null bytes. The deposit amount and UTXO balance are computed from the original valid transaction before this replacement, so nBTC is minted correctly — but the UTXO is permanently stored with invalid, zeroed `tx_bytes`. Any subsequent withdrawal attempt referencing this UTXO will fail PSBT construction/verification, permanently locking the underlying BTC in the bridge.

---

### Finding Description

In `internal_safe_verify_deposit_entry`, the flow is:

1. **Lines 191–193**: `transaction` is decoded from the caller-supplied `tx_bytes`; `deposit_amount` is extracted from the correct output.
2. **Lines 195–202**: The deposit address is verified against the transaction output.
3. **Lines 204–209**: If `tx_bytes.len() > 10000`, the variable `tx_bytes` is **overwritten** with `vec![0u8; 300]` — 300 null bytes — not a truncation of the real data.
4. **Lines 211–216**: A `UTXO` struct is constructed using the now-zeroed `tx_bytes` but the correct `balance` (from the original transaction).
5. **Lines 217–221**: `tx_id` is correctly computed from the original `transaction` object (not from the zeroed bytes).
6. The UTXO with zeroed `tx_bytes` is passed through `internal_safe_verify_deposit` → `verify_safe_deposit_callback` → `safe_mint_callback` → `internal_set_utxo`, where it is **permanently written to contract state**.

The nBTC minting proceeds normally (using the correct `deposit_amount`), so the user receives their tokens. However, the on-chain UTXO record now contains `tx_bytes = [0u8; 300]`.

When a withdrawal is later constructed referencing this UTXO, the PSBT builder must decode the stored `tx_bytes` to reconstruct the input's previous output. Decoding 300 zero bytes as a Bitcoin transaction will fail (panic or error), making it impossible to ever build a valid PSBT for this UTXO. The BTC it represents is permanently unspendable by the bridge.

The log message `"tx_bytes length exceeds 10000, truncating to 300 bytes"` is itself a documentation/behavior mismatch: "truncating" implies keeping the first 300 real bytes, but the code produces all-zero bytes — a direct analog to the Venus Protocol constant mismatch where the stated value differed from the actual value in code.

---

### Impact Explanation

- nBTC is minted and the user receives tokens backed by a UTXO the bridge can never spend.
- The UTXO is registered in `verified_deposit_utxo` (replay protection), so it cannot be re-submitted.
- No admin function exists to patch stored UTXO `tx_bytes` in place; operator intervention would require a contract migration or upgrade to recover the funds.
- This constitutes **permanent locking of bridged funds** and a **stuck bridge state requiring operator intervention**, matching the Medium allowed impact.

---

### Likelihood Explanation

Bitcoin transactions exceeding 10,000 bytes are uncommon but entirely valid on-chain. They arise from:
- Consolidation transactions with many inputs (50+ UTXOs)
- Taproot transactions with large witness scripts
- Any transaction a user deliberately or inadvertently constructs at that size

An attacker who controls the depositing wallet can craft a transaction of exactly this size to trigger the bug. A regular user with many small UTXOs may trigger it unintentionally. The entry point (`safe_verify_deposit`) is a public, permissionless bridge function callable by any NEAR account.

---

### Recommendation

Replace the silent zero-replacement with an explicit rejection:

```rust
require!(
    tx_bytes.len() <= 10_000,
    "tx_bytes length exceeds maximum allowed size"
);
```

If large transactions must be supported, store the actual bytes (or a content-addressed reference) rather than replacing them with zeroes. The log message "truncating to 300 bytes" must never describe a zero-fill operation.

---

### Proof of Concept

**Attacker steps:**

1. Construct a valid Bitcoin transaction depositing BTC to the bridge's derived address, with enough inputs/witness data that `tx_bytes.len() > 10_000`.
2. Call `safe_verify_deposit` on the satoshi-bridge contract, supplying these `tx_bytes` along with a valid Merkle proof.
3. The bridge executes `internal_safe_verify_deposit_entry`:
   - `deposit_amount` is correctly read from the transaction output.
   - `tx_bytes` is replaced with `vec![0u8; 300]` at line 204–209.
   - The UTXO `{ tx_bytes: [0u8; 300], balance: <correct>, ... }` is stored.
4. `safe_mint` succeeds; the caller receives nBTC.
5. Any future withdrawal attempt that selects this UTXO will fail when the PSBT builder tries to decode `[0u8; 300]` as a Bitcoin transaction — the BTC is permanently locked.
