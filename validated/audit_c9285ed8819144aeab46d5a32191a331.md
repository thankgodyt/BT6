### Title
Peras Certificate Validation Stub Unconditionally Accepts Any Certificate, Enabling Unauthorized Chain-Selection Manipulation — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The universal `BlockSupportsPeras` instance provides a stub `validatePerasCert` that unconditionally returns `Right` (success) for every inbound certificate, performing zero cryptographic or structural checks. This is the exact same vulnerability class as the Zetachain report: a guard that is supposed to reject invalid inputs always passes because the actual check was never implemented. Any unprivileged peer can send a crafted `PerasCert` boosting an arbitrary block; the certificate bypasses all validation, enters the `PerasCertDB`, and injects a weight boost that can flip chain selection toward a non-canonical fork.

### Finding Description

**Root cause — stub that always returns `Right`:**

The universal instance for all `StandardHash blk` is:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/120
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

No signature is verified, no committee membership is checked, no round-number bounds are enforced, and no boosted-block validity is confirmed. Every certificate that arrives is stamped `ValidatedPerasCert` and assigned a weight boost equal to `perasWeight params`.

**Production call-sites that use this stub:**

Both the `PerasCertDB`-backed writer and the `ChainDB`-backed writer call `validatePerasCert mkPerasParams` directly:

`weightedSelectView` adds the certificate-derived `wsvWeightBoost` on top of the block number, so a boosted fork can beat a longer honest chain: [8](#0-7) 

**Attack path (end-to-end):**

1. An unprivileged peer connects and sends a `PerasCert` via the Peras object-diffusion mini-protocol, naming any block hash as the boosted block.
2. `processCerts` calls `validatePerasCert mkPerasParams cert`, which unconditionally returns `Right`.
3. The certificate is stored in `PerasCertDB`; `PerasWeightSnapshot` becomes non-empty.
4. `preferAnchoredCandidate` now uses the weighted path; the attacker-chosen block receives a `PerasWeight` boost.
5. `chainSelection` / `chainSelectionForBlock` may now prefer a fork containing the boosted block over the honest canonical chain.
6. The node switches to the attacker-influenced fork.

### Impact Explanation

**Severity: Critical / High** — Bypass of Peras certificate checks enabling unauthorized certificate acceptance and chain-selection manipulation.

An unprivileged peer can inject arbitrary weight boosts into chain selection without possessing any committee key, stake, or VRF material. Because `validatePerasCert` never rejects, the attacker can boost any block in the VolatileDB, potentially causing an honest node to roll back to and adopt a non-canonical fork. This violates the Peras security assumption that only legitimately certified blocks receive weight boosts, and it directly undermines the chain-selection invariant that the preferred chain is the one with the highest honest weight.

### Likelihood Explanation

The Peras object-diffusion protocol is reachable by any peer that connects to the node. No privileged access, stake, or cryptographic material is required. The stub is the only implementation in the codebase (the universal instance covers all block types including `CardanoBlock`). The attack requires only sending a well-formed CBOR-encoded `PerasCert` message, which is trivially constructable from the public serialisation instances.

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
1. Verifies the aggregate BLS/committee signature over `(certRound, boostedBlock)`.
2. Confirms the signers form a valid quorum of the committee for that round.
3. Checks that `certRound` is within the acceptable window relative to the current chain tip.
4. Rejects certificates whose `boostedBlock` is not a known, header-validated block.

Until the real implementation is in place, the Peras certificate inbound handler should refuse all certificates (return `Left PerasValidationErr` unconditionally) rather than accept them all, so that the stub cannot be exploited.

### Proof of Concept

```
-- Attacker constructs a PerasCert for any block hash H visible in the VolatileDB:
let fakeCert = PerasCert { pcCertRound = someRound, pcCertBoostedBlock = BlockPoint slot H }

-- Send it via the Peras cert diffusion mini-protocol.
-- processCerts calls validatePerasCert mkPerasParams fakeCert
-- => always returns Right (ValidatedPerasCert { vpcCert = fakeCert, vpcCertBoost = perasWeight mkPerasParams })
-- => certificate stored in PerasCertDB
-- => PerasWeightSnapshot now maps H -> perasWeight
-- => preferAnchoredCandidate uses weighted path
-- => any fork containing H now has extra weight
-- => chainSelectionForBlock may switch the node to that fork
```

The `validatePerasCert` stub at lines 353–358 of `SupportsPeras.hs` is the single necessary and sufficient vulnerable step; no other code can compensate for its unconditional `Right` return. [9](#0-8)
