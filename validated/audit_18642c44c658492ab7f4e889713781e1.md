### Title
Missing `storage.total` Update in `try_to_transfer_balance_from_message_account` Causes Permanent Locking of Native Fee Funds — (File: `near/omni-bridge/src/storage.rs`)

---

### Summary

`try_to_transfer_balance_from_message_account` transfers the message account's NEAR balance into the storage-payer's `available` field but never updates the storage-payer's `total` field. This creates an invariant violation (`available > total`) that permanently prevents the storage-payer from withdrawing the transferred funds, locking native-fee NEAR tokens in the contract forever.

---

### Finding Description

When a user initiates a cross-chain transfer via `ft_on_transfer` → `init_transfer`, the bridge supports a "message account" pattern: a dedicated NEAR account pre-funds the native fee and storage cost. The function `try_to_transfer_balance_from_message_account` is supposed to move that pre-funded balance to the storage-payer (the signer) so the transfer can proceed.

The function reads the message account's `balance.total`, adds it to `storage.available` of the storage-payer, verifies the resulting available balance is sufficient, then writes back only the modified `storage` struct and removes the message account:

```rust
// near/omni-bridge/src/storage.rs  lines 276-289
let mut storage = self
    .accounts_balances
    .get(storage_payer)
    .ok_or(StorageError::SignerNotRegistered)?;

storage.available = storage.available.saturating_add(balance.total);  // ← only available updated

if storage.available < required_storage_payer_balance.saturating_add(native_fee) {
    return Err(StorageError::SignerNotEnoughBalance);
}

self.accounts_balances.insert(storage_payer, &storage);   // ← total is NEVER updated
self.accounts_balances.remove(account_id);
``` [1](#0-0) 

`storage.total` is never incremented. After the call the storage-payer's `StorageBalance` satisfies `available > total`, violating the NEP-145 invariant.

`storage_withdraw` uses `storage.available` as the default withdrawal amount and then subtracts it from `storage.total`:

```rust
// near/omni-bridge/src/storage.rs  lines 193-205
let to_withdraw = amount.unwrap_or(storage.available);
storage.total = storage.total.checked_sub(to_withdraw).near_expect(
    StorageError::NotEnoughStorageBalance { ... },
);
storage.available = storage.available.checked_sub(to_withdraw).near_expect(
    StorageError::NotEnoughStorageBalance { ... },
);
``` [2](#0-1) 

Because `to_withdraw` (= `available`) exceeds `total`, `checked_sub` returns `None` and the call panics. The storage-payer can never withdraw the portion of their `available` balance that originated from the message account. Those NEAR tokens are permanently locked inside the bridge contract.

---

### Impact Explanation

Every NEAR deposited to a message account to pre-fund a native fee is irrecoverably locked once `try_to_transfer_balance_from_message_account` succeeds. The storage-payer's `available` balance is inflated (so storage-cost checks pass), but the corresponding `total` is not, making the extra funds unwithdrawable. This is escrow/fee mis-accounting that permanently changes user balances: the message-account depositor loses their NEAR and the storage-payer cannot reclaim it.

---

### Likelihood Explanation

The vulnerable path is triggered by any unprivileged user who:
1. Calls `storage_deposit` on the bridge for a message-account address (a public, payable function).
2. Calls `ft_transfer_call` on any registered token with an `InitTransfer` message that references that message account.

`try_to_transfer_balance_from_message_account` is invoked inside `init_transfer` whenever the message account has sufficient balance:

```rust
// near/omni-bridge/src/lib.rs  lines 566-573
if self
    .try_to_transfer_balance_from_message_account(
        &message_storage_account_id,
        NearToken::from_yoctonear(init_transfer_msg.native_token_fee.0),
        &signer_id,
        required_storage_balance,
    )
    .is_ok()
``` [3](#0-2) 

No privileged role is required. Any bridge user who uses the message-account funding pattern triggers the bug.

---

### Recommendation

Add the missing `storage.total` update so the full transferred amount is reflected in both fields:

```rust
storage.total   = storage.total.saturating_add(balance.total);   // ← add this line
storage.available = storage.available.saturating_add(balance.total);
```

This restores the `total >= available` invariant and allows the storage-payer to withdraw the transferred funds normally.

---

### Proof of Concept

1. Alice registers a message-account `msg.alice.near` with `storage_deposit` and deposits 2 NEAR.
2. Alice calls `ft_transfer_call` with `native_token_fee = 1 NEAR` referencing `msg.alice.near`.
3. `try_to_transfer_balance_from_message_account` runs:
   - `storage.available` for Alice's signer account increases by 2 NEAR.
   - `storage.total` for Alice's signer account is **unchanged**.
4. Alice later calls `storage_withdraw` with no amount (withdraw all available).
   - `to_withdraw = storage.available` (original + 2 NEAR).
   - `storage.total.checked_sub(to_withdraw)` → `None` → panic.
5. Alice can only withdraw up to her original `total`; the 2 NEAR from the message account is permanently locked in the bridge contract.
