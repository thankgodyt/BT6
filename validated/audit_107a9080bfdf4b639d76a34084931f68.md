### Title
Unchecked `post_action.msg` When No Templates Are Registered for a Whitelisted Receiver — (`contracts/satoshi-bridge/src/deposit_msg.rs`)

---

### Summary

The `check_deposit_msg` function validates `PostAction.msg` against registered templates **only if** `post_action_msg_templates` contains an entry for the given `receiver_id`. When a `receiver_id` is on the `post_action_receiver_id_white_list` but has no corresponding entry in `post_action_msg_templates`, the `msg` field is accepted without any restriction. An unprivileged user who controls the `DepositMsg` can therefore pass arbitrary `msg` content to `ft_transfer_call` targeting any such whitelisted contract.

---

### Finding Description

In `check_deposit_msg`, the receiver-id whitelist check is unconditional: [1](#0-0) 

But the `msg` template check is wrapped in an `if let Some(...)` guard: [2](#0-1) 

If `post_action_msg_templates.get(&post_action.receiver_id)` returns `None` — i.e., the DAO added a `receiver_id` to the whitelist but never registered any templates for it — the entire `msg` validation block is skipped. The function proceeds to return `Some(post_actions)` with the unchecked `msg` intact. [3](#0-2) 

The two admin operations that manage these structures are independent: `extend_post_action_receiver_id_white_list` adds to the whitelist, and `extend_post_action_msg_templates` adds templates — there is no enforcement that a whitelisted receiver must have at least one template. [4](#0-3) [5](#0-4) 

The validated (or in this case, unvalidated) `post_actions` are then forwarded to the `nbtc` contract's `mint` call, which executes `ft_transfer_call` to the attacker-chosen `receiver_id` with the attacker-chosen `msg`: [6](#0-5) 

---

### Impact Explanation

An attacker who deposits BTC using a crafted `DepositMsg` can pass an arbitrary `msg` string to `ft_transfer_call` on any whitelisted receiver that lacks registered templates. The receiver's `ft_on_transfer` callback is invoked with attacker-controlled content. Depending on the whitelisted contract's logic, this can:

- Trigger unintended state changes in the receiver (e.g., setting up approvals, registering callbacks, or altering internal accounting).
- Cause the receiver to return 0 (keeping all nBTC), effectively burning the user's tokens in an unintended way.
- Exploit any receiver-side logic that branches on `msg` content to redirect or lock funds.

This is a bypass of the bridge's intended policy (the template system exists precisely to restrict what actions can be triggered via `post_actions`) and constitutes harmful smart-contract behavior reachable without operator intervention.

**Matched impact**: Medium — Bypass of bridge limits or policies; harmful smart-contract behavior without direct funds theft, including broken callback rollback or stuck bridge state requiring operator intervention.

---

### Likelihood Explanation

The condition is reachable whenever the DAO adds a contract to `post_action_receiver_id_white_list` without simultaneously registering templates. This is a plausible operational state: the whitelist and template maps are managed by separate admin calls with no coupling enforced at the contract level. Any user who generates a deposit address using a `DepositMsg` with `post_actions` targeting such a receiver controls the `msg` field entirely. The relayer submits the proof for whatever deposit address was used; the `DepositMsg` content (including `post_actions`) is determined by the user at address-generation time. [7](#0-6) 

---

### Recommendation

Enforce that a `receiver_id` may only appear in `post_action_receiver_id_white_list` if it also has at least one entry in `post_action_msg_templates`, or invert the logic: reject any `post_action` whose `receiver_id` has no registered templates (treat an absent template set as "no messages allowed" rather than "all messages allowed"). Concretely, change the `if let Some(...)` guard to a hard `require!`:

```rust
let msg_templates = self
    .data()
    .post_action_msg_templates
    .get(&post_action.receiver_id)
    .expect("No msg templates registered for this receiver_id");
// ... existing match/is_match logic ...
```

---

### Proof of Concept

1. DAO calls `extend_post_action_receiver_id_white_list(["defi.near"])` but does **not** call `extend_post_action_msg_templates` for `defi.near`.
2. Attacker constructs:
   ```json
   {
     "recipient_id": "attacker.near",
     "post_actions": [{
       "receiver_id": "defi.near",
       "amount": "1000000",
       "msg": "{\"action\":\"register_hook\",\"callback\":\"attacker.near\"}"
     }]
   }
   ```
3. Attacker calls `get_user_deposit_address` with this `DepositMsg`, obtains the derived BTC address, and sends BTC there.
4. A relayer calls `verify_deposit_v2` with the same `DepositMsg` and a valid Merkle proof.
5. `check_deposit_msg` finds `defi.near` on the whitelist; `post_action_msg_templates.get("defi.near")` returns `None`; the `if let Some(...)` block is skipped; `post_actions` is returned as valid.
6. The `nbtc.mint` cross-contract call executes `ft_transfer_call("defi.near", amount, "{\"action\":\"register_hook\",\"callback\":\"attacker.near\"}")`.
7. `defi.near`'s `ft_on_transfer` receives the attacker-crafted `msg` and acts on it — registering a hook, setting an approval, or otherwise altering state — in a way that was never sanctioned by the bridge's template policy. [8](#0-7)

        &self,
        deposit_msg: DepositMsg,
        actual_mintable_amount: u128,
    ) -> Option<Vec<PostAction>> {
        let post_actions = deposit_msg.post_actions?;
        if post_actions.is_empty() {
            Event::InvalidPostAction {
                index: None,
                err_msg: "empty post_actions.".to_string(),
            }
            .emit();
            return None;
        }
        // post_actions supports at most two.
        if post_actions.len() > MAX_POST_ACTIONS_NUM {
            Event::InvalidPostAction {
                index: None,
                err_msg: format!(
                    "The number({}) of post_actions exceeds the limit of {}.",
                    post_actions.len(),
                    MAX_POST_ACTIONS_NUM
                ),
            }
            .emit();
            return None;
        }
        let mut total_gas = 0;
        let mut total_amount = 0;
        for (index, post_action) in post_actions.iter().enumerate() {
            total_amount += post_action.amount.0;
            // The receiver_id cannot be the bridge itself — that would let a
            // deposit immediately drive the bridge's own ft_on_transfer flow
            // (e.g. TokenReceiverMessage::Withdraw) inside the relayer-paid
            // receipt, which is outside the intended deposit semantics.
            if post_action.receiver_id == env::current_account_id() {
                Event::InvalidPostAction {
                    index: Some(index),
                    err_msg: format!(
                        "The receiver_id({}) of the post_action cannot be the bridge itself.",
                        post_action.receiver_id
                    ),
                }
                .emit();
                return None;
            }
            // The receiver_id must be on the whitelist.
            if !self
                .data()
                .post_action_receiver_id_white_list
                .contains(&post_action.receiver_id)
            {
                Event::InvalidPostAction {
                    index: Some(index),
                    err_msg: format!(
                        "The receiver_id({}) of the post_action is not on the whitelist.",
                        post_action.receiver_id
                    ),
                }
                .emit();
                return None;

    pub fn extend_post_action_msg_templates(
        &mut self,
        contract_id: AccountId,
        templates: HashSet<String>,
    ) {
        assert_one_yocto();
        require!(!templates.is_empty(), "empty templates.");
        if let Some(msg_templates) = self
            .data_mut()
            .post_action_msg_templates
            .get_mut(&contract_id)
        {
            for template in templates {
                let is_success = msg_templates.insert(template.clone());
                require!(is_success, format!("{:?} is exist.", template));
            }
        } else {
            self.data_mut()
                .post_action_msg_templates
                .insert(contract_id, templates);
        }
    }
