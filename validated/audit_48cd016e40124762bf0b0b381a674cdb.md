### Title
`update_config` Replaces `nbtc_account_id` Without Migrating `lost_found` Balances, Permanently Locking User nBTC — (File: `contracts/satoshi-bridge/src/api/management.rs`)

---

### Summary

The DAO can update `nbtc_account_id` via `update_config` at any time. After the update, `claim_lost_found` calls `ft_transfer` on the **new** nBTC contract, but the bridge's actual nBTC balance remains in the **old** contract. The transfer fails, the amount is silently re-added to `lost_found`, and the user's nBTC is permanently inaccessible through the normal claim path.

---

### Finding Description

`ConfigUpdate` exposes `nbtc_account_id` as an updatable field: [1](#0-0) 

`update_config` applies the change atomically with no migration of dependent state: [2](#0-1) 

The `lost_found` map stores nBTC amounts owed to users after failed `ft_transfer` callbacks. When `claim_lost_found` is called, it invokes `internal_transfer_nbtc`: [3](#0-2) 

`internal_transfer_nbtc` reads the **current** `nbtc_account_id` from config and calls `ft_transfer` on that contract: [4](#0-3) 

If `nbtc_account_id` was changed to a new contract, the bridge has no balance there, so the transfer fails. `transfer_nbtc_callback` then re-inserts the amount into `lost_found`, creating a permanent loop: [5](#0-4) 

The user can never recover their nBTC through the normal path. The nBTC remains locked in the bridge's account on the old token contract with no on-chain recovery mechanism.

---

### Impact Explanation

User nBTC recorded in `lost_found` becomes permanently inaccessible after a `nbtc_account_id` config update. The bridge holds the nBTC in the old contract but always calls `ft_transfer` on the new contract. Every `claim_lost_found` call fails and re-adds the amount to `lost_found`. Recovery requires operator intervention (reverting `nbtc_account_id` back to the old contract). This matches the **Medium** impact class: *stuck bridge state requiring operator intervention*.

---

### Likelihood Explanation

Token migration is a planned feature, evidenced by the existence of `migrate_to_new_token`: [6](#0-5) 

If DAO uses `update_config` to update `nbtc_account_id` as part of a migration — rather than the dedicated migration path — all existing `lost_found` balances are immediately affected. Any user who had a failed nBTC transfer before the config update loses access to their funds. The scenario is realistic whenever the protocol migrates its token contract.

---

### Recommendation

1. Remove `nbtc_account_id` from `ConfigUpdate` and require all token contract changes to go through `migrate_to_new_token`, which can be extended to handle `lost_found` migration; or
2. Before applying a `nbtc_account_id` change in `update_config`, assert that `lost_found` is empty (i.e., all pending claims have been resolved).

---

### Proof of Concept

1. User A has 1 000 satoshi in `lost_found` (from a failed `ft_transfer` callback on `old_nbtc.near`).
2. DAO calls `update_config` with `nbtc_account_id = "new_nbtc.near"`.
3. User A calls `claim_lost_found`.
4. `internal_transfer_nbtc` calls `ft_transfer` on `new_nbtc.near` for 1 000 satoshi.
5. The bridge has no balance in `new_nbtc.near`; the transfer fails.
6. `transfer_nbtc_callback` re-adds 1 000 satoshi to `lost_found`.
7. Every subsequent `claim_lost_found` call repeats steps 4–6. User A's 1 000 satoshi is permanently stuck.

    pub fn internal_transfer_nbtc(&self, account_id: &AccountId, amount: u128) -> Promise {
        ext_ft_core::ext(self.internal_config().nbtc_account_id.clone())
            .with_attached_deposit(NearToken::from_yoctonear(1))
            .with_static_gas(GAS_FOR_TOKEN_TRANSFER)
            .ft_transfer(account_id.clone(), amount.into(), None)
            .then(
                Self::ext(env::current_account_id())
                    .with_static_gas(GAS_FOR_AFTER_TOKEN_TRANSFER)
                    .transfer_nbtc_callback(account_id.clone(), amount.into()),
            )
    }
