### Title
Unconditional `validatePerasCert` Stub Allows Any Peer to Inject Arbitrary Peras Certificates and Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance implements `validatePerasCert` as an unconditional stub that always returns `Right`, performing zero cryptographic or semantic validation on inbound Peras certificates. This stub is wired directly into the production network ingest path (`makePerasCertPoolWriterFromChainDB`). Any unprivileged peer can send a crafted `PerasCert` with an arbitrary round number and boosted block point; the node will accept it as valid, store it in the `PerasCertDB`, and trigger chain selection with a `PerasWeight 15` boost — potentially switching to a non-canonical fork.

---

### Finding Description

**Root cause — stub validator always succeeds:**

The universal `instance StandardHash blk => BlockSupportsPeras blk` in `SupportsPeras.hs` implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

No signature check, no quorum check, no committee membership check — every certificate unconditionally passes. [1](#0-0) 

**Production ingest path uses this stub:**

`makePerasCertPoolWriterFromChainDB` — the production writer used when Peras is enabled — passes `validatePerasCert mkPerasParams` directly as the validation function for all inbound peer certificates:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

**`processCerts` trusts the validator's output:**

`processCerts` calls `validateCert` on each inbound cert and, if all pass, immediately calls `addCert` (which is `void . ChainDB.addPerasCertAsync chainDB`). Because the stub always returns `Right`, every cert from every peer is accepted and queued for chain selection. [3](#0-2) 

**Chain selection acts on the injected certificate:**

`chainSelSync` processes the queued `ChainSelAddPerasCert` message. If the boosted block is present in the VolatileDB, it calls `chainSelectionForBlock` with the full `PerasWeight 15` boost applied, potentially switching the node to a shorter fork that would otherwise lose chain selection. [4](#0-3) 

**The `PerasCert` wire type is trivially forgeable:**

The stub instance's `PerasCert` contains only `pcCertRound :: PerasRoundNo` and `pcCertBoostedBlock :: Point blk` — no aggregate signature, no voter set. An attacker can craft a valid CBOR encoding of this type for any round number and any block point. [5](#0-4) 

**`implAddCert` also carries a TODO acknowledging missing validation:**

The `PerasCertDB` implementation itself notes: `-- TODO: we will need to update this method with non-trivial validation logic`. [6](#0-5) 

---

### Impact Explanation

**Impact: High — Chain selection manipulation by an unprivileged peer.**

When Peras is enabled, an attacker who can connect as a peer can:

1. Identify any block hash present in the victim's VolatileDB (e.g., a block on a shorter competing fork).
2. Craft a `PerasCert` with `pcCertBoostedBlock = <that block's point>` and any `pcCertRound`.
3. Send it via the Peras certificate object diffusion mini-protocol.
4. The victim node accepts it, stores it, and re-runs chain selection with `PerasWeight 15` added to the fork containing that block.
5. If the boosted fork's weight now exceeds the current chain's weight, the node switches — adopting a non-canonical, potentially adversarially-controlled chain.

The `PerasWeight 15` boost is explicitly designed to be large enough to override normal length-based chain selection. [7](#0-6) 

This matches the "High" impact category: *chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.*

---

### Likelihood Explanation

**Likelihood: Medium (conditional on Peras being enabled).**

Peras is currently disabled by default. However:
- The code is in production files, not test/mock files.
- The object diffusion mini-protocol for Peras certs is fully wired up and active when Peras is enabled.
- Any peer that can establish a node-to-node connection (no credentials required) can send crafted certs.
- The attack requires no cryptographic capability — only the ability to serialize a `(PerasRoundNo, Point blk)` pair in CBOR.
- The boosted block point can be learned by observing the ChainSync protocol (headers are public).

Once Peras is enabled on a production network, this becomes trivially exploitable by any network participant.

---

### Recommendation

1. **Immediate**: Gate the Peras cert ingest path so that it rejects all certificates when no real `validatePerasCert` implementation is available (e.g., return `Left PerasValidationErr` unconditionally until the real implementation is in place), rather than accepting all certificates.
2. **Correct fix**: Implement `validatePerasCert` to verify the aggregate BLS signature over the `(electionId, candidate)` pair against the aggregated verification keys of the claimed voters, and verify that the claimed voters constitute a quorum of the committee for the given round — as already implemented for the `EveryoneVotes` and `WFALS` committee schemes in `implVerifyCert`. [8](#0-7) 
3. Track completion via the referenced issue `https://github.com/tweag/cardano-peras/issues/120`.

---

### Proof of Concept

**Setup**: A private testnet with Peras enabled. Attacker runs a node that connects to the victim.

**Steps**:

1. Victim node has two competing forks in its VolatileDB: chain A (length 10, current selection) and chain B (length 9, one block behind).
2. Attacker learns the hash of the tip of chain B via ChainSync headers (public information).
3. Attacker serializes a `PerasCert` as CBOR:
   ```
   [ roundNo: 1, boostedBlock: (slotNo_B, hash_B) ]
   ```
4. Attacker sends this cert to the victim via the Peras cert object diffusion mini-protocol.
5. `processCerts` calls `validatePerasCert mkPerasParams` → returns `Right (ValidatedPerasCert { vpcCert = craftedCert, vpcCertBoost = PerasWeight 15 })`.
6. Cert is added to `PerasCertDB`; `addPerasCertAsync` is called.
7. `chainSelSync` finds the boosted block (chain B tip) in the VolatileDB and calls `chainSelectionForBlock`.
8. Chain selection now compares: chain A (length 10, weight 0) vs chain B (length 9, weight 15). With `PerasWeight 15 > 0`, chain B wins.
9. Victim switches to chain B — a shorter, non-canonical fork — without the attacker possessing any keys or stake.

**Expected outcome**: Victim's tip changes from chain A's tip to chain B's tip, confirming unauthorized chain selection manipulation via a forged certificate accepted due to the no-op `validatePerasCert` stub.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
