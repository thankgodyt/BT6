### Title
`NativeFeeRestricted` Role Bypass via Yield/Resume Execution Path — (`near/omni-bridge/src/lib.rs`)

### Summary

The `NativeFeeRestricted` role is intended to prevent certain accounts from setting a non-zero native NEAR fee on outbound transfers. However, the restriction check is only present in one branch of the conditional logic inside `init_transfer`. A restricted user can deliberately trigger the yield execution path, which resumes via `init_transfer_resume` — a callback that contains **no** `NativeFeeRestricted` check — allowing the non-zero native fee to be finalized.

### Finding Description

In `init_transfer`, the `NativeFeeRestricted` check appears only inside the second branch of an OR condition: [1](#0-0) 

```rust
if self.try_to_transfer_balance_from_message_account(
        &message_storage_account_id,
        NearToken::from_yoctonear(init_transfer_msg.native_token_fee.0),
        &signer_id,
        required_storage_balance,
    ).is_ok()
    || (self.has_storage_balance(...) && (
            init_transfer_msg.native_token_fee.0 == 0
            || !self.acl_has_role(Role::NativeFeeRestricted.into(), signer_id.clone())  // ← only check
       ))
{
    // immediate path
} else {
    // yield path — no restriction check
    env::promise_yield_create("init_transfer_resume", ...)
}
``` [2](#0-1) 

The `NativeFeeRestricted` role is defined and used here: [3](#0-2) 

The resume callback `init_transfer_resume` (the only code path that runs after a yield) contains **no** role check: [4](#0-3) 

```rust
pub fn init_transfer_resume(
    &mut self,
    transfer_message: TransferMessage,   // ← already contains non-zero native_fee
    message_storage_account_id: AccountId,
    storage_owner: AccountId,
    ...
) -> U128 {
    ...
    if let Err(err) = self.try_to_transfer_balance_from_message_account(...) {
        return transfer_message.amount;
    }
    self.init_transfer_internal(transfer_message, storage_owner)  // ← no NativeFeeRestricted check
}
```

The `transfer_message` is constructed **before** the restriction check and already contains the non-zero `native_fee` from the user's input: [5](#0-4) 

### Impact Explanation

A user assigned `NativeFeeRestricted` can bypass the restriction and successfully submit a transfer with a non-zero native NEAR fee. This is a direct role bypass: the protocol's intended regulatory/compliance control over which accounts may incentivize relayers with native NEAR tokens is rendered ineffective. The bypass is fully self-contained and requires no admin cooperation.

### Likelihood Explanation

The yield path is a standard, documented execution flow in the NEAR bridge. Any `NativeFeeRestricted` user who understands the storage deposit mechanism can trigger it deterministically. The message storage account ID is derived from user-controlled inputs (`external_id`), making it predictable. The attacker only needs to:
1. Call `ft_transfer_call` with non-zero `native_token_fee` while ensuring the message account has no pre-existing balance (so the first branch fails).
2. Deposit to the message storage account after the yield is created.
3. Wait for `init_transfer_resume` to execute.

### Recommendation

Add the `NativeFeeRestricted` check inside `init_transfer_resume` before calling `init_transfer_internal`. Specifically, re-check whether `storage_owner` holds `NativeFeeRestricted` and whether `transfer_message.fee.native_fee.0 != 0`; if both are true, refund the tokens instead of proceeding.

### Proof of Concept

1. Admin grants `NativeFeeRestricted` to `alice.near`.
2. `alice.near` calls `ft_transfer_call` on a token with `msg` containing `native_token_fee = 1_000_000_000_000_000_000_000_000` (1 NEAR) and an `external_id` she controls, while the derived message storage account has zero balance.
3. `try_to_transfer_balance_from_message_account` fails; the second branch also fails because `alice.near` is `NativeFeeRestricted`. Execution is yielded; `transfer_message` with `native_fee = 1 NEAR` is stored on-chain.
4. `alice.near` calls `storage_deposit` targeting the message storage account with sufficient balance.
5. NEAR runtime calls `init_transfer_resume`; `try_to_transfer_balance_from_message_account` now succeeds; `init_transfer_internal` is called with the non-zero native fee — no `NativeFeeRestricted` check is performed.
6. An `InitTransferEvent` is emitted with `native_fee = 1 NEAR`, and relayers are incentivized despite the restriction.

    #[private]
    #[allow(clippy::needless_pass_by_value)]
    pub fn init_transfer_resume(
        &mut self,
        transfer_message: TransferMessage,
        message_storage_account_id: AccountId,
        storage_owner: AccountId,
        #[callback_result] response: Result<(), PromiseError>,
    ) -> U128 {
        self.remove_promise(&message_storage_account_id);
        if response.is_err() {
            env::log_str("Init transfer resume timeout");
        }

        if let Err(err) = self.try_to_transfer_balance_from_message_account(
            &message_storage_account_id,
            NearToken::from_yoctonear(transfer_message.fee.native_fee.0),
            &storage_owner,
            self.required_balance_for_init_transfer_message(transfer_message.clone()),
        ) {
            env::log_str(&format!("Error paying native fee and storage: {err}"));
            return transfer_message.amount;
        }

        self.init_transfer_internal(transfer_message, storage_owner)
    }
