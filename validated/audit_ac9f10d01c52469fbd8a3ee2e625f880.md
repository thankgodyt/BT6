### Title
Inconsistent Peras Weight Criterion in ChainSync Client vs. ChainDB Chain Selection Causes Incorrect Peer Disconnection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

The `checkPreferTheirsOverOurs` guard in the ChainSync client evaluates candidate preference using a hardcoded `emptyPerasWeightSnapshot` (ignoring all Peras certificate weight boosts), while the actual chain selection in `ChainDB` evaluates the same candidate using the real `PerasWeightSnapshot`. When Peras is enabled, this inconsistency causes a node to disconnect from a peer offering a legitimately heavier (Peras-boosted) chain that the node would otherwise adopt, leaving the node on the less-secure, non-canonical chain.

---

### Finding Description

The vulnerability class is **inconsistent criterion evaluation**: two code paths that must agree on whether a candidate chain is preferable use different criteria, producing contradictory decisions.

**Path 1 — ChainSync client disconnect guard (`checkPreferTheirsOverOurs`):**

When a header arrives beyond the forecast horizon, the ChainSync client cannot validate it and instead checks whether the candidate fragment is at least preferable to the current chain. If not, it disconnects. The check is:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        emptyPerasWeightSnapshot   -- ← hardcoded: Peras weight ignored
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
```

The `emptyPerasWeightSnapshot` causes `preferAnchoredCandidate` to take the non-Peras branch, which compares only block numbers (chain length) at the tips. [1](#0-0) 

**Path 2 — ChainDB actual chain selection:**

When blocks are downloaded and chain selection runs, the same `preferAnchoredCandidate` is called with the real `weights` snapshot from `cdbPerasCertDB`:

```haskell
ShouldSwitch reason <- [preferAnchoredCandidate bcfg weights curChain $ Diff.getSuffix chain]
``` [2](#0-1) 

**The divergence in `preferAnchoredCandidate`:**

When `isEmptyPerasWeightSnapshot weights` is true (Path 1), the function compares only the `selectView` at the tips (block number + VRF tiebreaker). When weights are non-empty (Path 2), it computes the intersection, then compares `weightedSelectView` over the suffixes, which adds `wsvWeightBoost` (Peras certificate weight) to the comparison. [3](#0-2) 

The `wsvTotalWeight` is `blockNo + weightBoost`, so a chain with the same block count but Peras-boosted blocks is strictly heavier under Path 2 but appears equal under Path 1. [4](#0-3) 

The developers acknowledge this with a TODO comment referencing issue #64:
```
-- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
emptyPerasWeightSnapshot
``` [5](#0-4)

### Impact Explanation

**Impact: High — Chain selection bug that causes an honest node to prefer a non-canonical, less-secure chain.**

Concrete scenario when Peras is enabled:

1. Our chain has block count N.
2. A peer offers a fork of equal block count N, but one or more of its blocks carry Peras certificate weight boosts, making it the heavier (canonical) chain under the Peras chain order.
3. The peer's tip header is beyond the forecast horizon (e.g., during a slot gap larger than the stability window).
4. `checkPreferTheirsOverOurs` evaluates with `emptyPerasWeightSnapshot` → sees both chains as equal → `shouldSwitch` returns `False` → the node throws `CandidateTooSparse` and **disconnects from the peer**.
5. The node never downloads the blocks, never runs actual chain selection, and remains on the lighter (non-canonical) chain.

The node is thus permanently prevented from adopting the canonical Peras-weighted chain via this peer, weakening its security guarantees under the Peras protocol.

---

### Likelihood Explanation

**Likelihood: Medium** (conditional on Peras being enabled).

- Peras is currently disabled by default (`emptyPerasWeightSnapshot` is the default in most call sites), so this is not exploitable on today's mainnet.
- Once Peras is enabled, the trigger condition — a Peras-boosted chain of equal block count whose tip header falls beyond the forecast horizon — is a normal operational scenario, not an exotic edge case. Any honest peer serving the canonical Peras chain can trigger this.
- No special privileges, keys, or stake majority are required; any unprivileged peer serving a valid Peras-boosted chain suffices.

---

### Recommendation

Pass the real `PerasWeightSnapshot` (obtained from `cdbPerasCertDB` or an equivalent STM read) into `checkPreferTheirsOverOurs` instead of `emptyPerasWeightSnapshot`, so that the disconnect guard uses the same chain-preference criterion as the actual chain selection. The TODO comment already identifies this as a known deficiency. Until Peras is enabled in production, the risk is latent but should be resolved before activation.

---

### Proof of Concept

**Setup:** Peras enabled; our chain tip is block B at height N; a peer's chain tip is block B′ at height N (same block number), but B′ carries a Peras weight boost of W > 0 from a certificate. B′'s slot is beyond the current forecast horizon.

**Trigger:**
1. ChainSync client receives header for B′.
2. `projectLedgerView` returns `Nothing` (beyond forecast horizon).
3. `checkPreferTheirsOverOurs` is called.
4. `preferAnchoredCandidate cfg emptyPerasWeightSnapshot ourFrag theirFrag` enters the `isEmptyPerasWeightSnapshot` branch.
5. Both fragments end with a block at height N → `preferCandidate` on `selectView` returns `ShouldNotSwitch EQ` (assuming equal VRF tiebreaker or same issuer/slot).
6. `shouldSwitch` is `False` → `throwSTM CandidateTooSparse` → peer disconnected.

**Expected (correct) behavior:** `preferAnchoredCandidate cfg realWeights ourFrag theirFrag` would enter the Peras branch, compute `weightedSelectView` over the suffixes, find `wsvTotalWeight(theirs) = N + W > N = wsvTotalWeight(ours)`, and return `ShouldSwitch` — the peer should be kept and the chain adopted.

        case (ours, cand) of

          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
