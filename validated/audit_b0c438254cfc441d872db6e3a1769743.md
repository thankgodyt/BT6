### Title
Reachable u128 Underflow Panic in `check_withdraw_psbt` Before `gas_fee` Bounds Check — (`contracts/satoshi-bridge/src/psbt.rs`)

### Summary

An unprivileged user can craft a withdrawal PSBT with a tiny user-receive output and large UTXO inputs so that `gas_fee = total_input_amount - total_output_amount` exceeds `amount - withdraw_fee`. The subtraction at line 242 then underflows and panics before the `gas_fee` bounds check at line 252 is ever reached. With `overflow-checks = true` in the workspace release profile, this is a hard abort, not a silent wrap.

---

### Finding Description

**Root cause — ordering of arithmetic vs. validation:**

In `check_withdraw_psbt`, `gas_fee` is computed at line 238 from relayer-supplied PSBT data, then immediately used in unchecked arithmetic at line 242, while the bounds check that would reject an out-of-range `gas_fee` only appears at line 252:

```
238: let gas_fee = total_input_amount - total_output_amount;
242: let max_received_amount = amount - withdraw_fee - gas_fee;   // ← underflow here
243: let min_received_amount = max_received_amount - config.min_change_amount;
...
252: require!(gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee, ...);
``` [1](#0-0) 

**What the attacker controls:**

- `amount` — the nBTC sent via `ft_transfer_call`; must be `>= min_withdraw_amount` but can be exactly that minimum.
- `input: Vec<OutPoint>` — which bridge UTXOs to reference; the attacker picks any UTXOs from the contract's live UTXO set, including large ones.
- `output: Vec<TxOut>` — the output values. The user-receive output (matched by `target_address_script_pubkey`) has **no minimum-value check** in the loop; only change outputs are checked against `min_change_amount`. [2](#0-1) 

**Concrete trigger:**

| Variable | Value |
|---|---|
| `amount` | `min_withdraw_amount` (e.g. 10 000 sat) |
| `withdraw_fee` | ~100 sat (1 %) |
| `total_input_amount` | 500 000 sat (one large bridge UTXO) |
| `total_output_amount` | 1 sat (user-receive output set to 1 sat, no change output) |
| `gas_fee` | 499 999 sat |
| `amount - withdraw_fee - gas_fee` | 10 000 − 100 − 499 999 → **underflow** |

**Overflow-checks are enabled project-wide:**

```toml
[profile.release]
overflow-checks = true
``` [3](#0-2) 

This means the subtraction is a hard panic/abort, not a silent wrap.

**Call path:**

`ft_transfer_call` → `ft_on_transfer` → `ft_on_transfer_withdraw_chain_specific` → (async) `ft_on_transfer_callback` → `create_btc_pending_info` → `check_withdraw_psbt_valid` → `check_withdraw_psbt` → **panic at line 242**. [4](#0-3) [5](#0-4) 

---

### Impact Explanation

The panic fires inside `ft_on_transfer_callback`, a `#[private]` cross-contract callback. NEAR's execution model rolls back all state mutations within that callback (including the `generate_vutxos` UTXO removal). The promise returned by `ft_on_transfer` fails, and the nBTC contract's standard `ft_resolve_transfer` refunds the tokens to the sender. [6](#0-5) 

Consequently:
- **No nBTC is permanently stuck** — the refund path works correctly.
- **No bridge state is corrupted** — NEAR rolls back the callback's state changes.
- **No fund theft** — the attacker gains nothing.

The impact is a **publicly reachable panic-driven fault in a production bridge path**: the user's withdrawal transaction aborts, they waste gas, and the bridge emits no useful error. This fits the **Low** allowed impact category.

---

### Likelihood Explanation

Any user who can call `ft_transfer_call` on the nBTC contract (i.e., any nBTC holder) can trigger this. The bridge's UTXO set is public, so the attacker can inspect it for large UTXOs. No privileged role is required. Likelihood is **High** for triggering the panic, but the practical harm is low because the refund mechanism works.

---

### Recommendation

Move the `gas_fee` bounds check **before** the arithmetic that depends on it:

```rust
let gas_fee = total_input_amount - total_output_amount;

// Validate gas_fee FIRST, before using it in further arithmetic
require!(
    gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee,
    format!("Invalid gas fee ({}). valid range: [{}, {}].", gas_fee, config.min_btc_gas_fee, config.max_btc_gas_fee)
);

// Now safe: gas_fee is bounded, so amount - withdraw_fee - gas_fee cannot underflow
// (assuming amount >= min_withdraw_amount and withdraw_fee + max_btc_gas_fee <= min_withdraw_amount)
let max_received_amount = amount - withdraw_fee - gas_fee;
```

Additionally, use `checked_sub` with an explicit error message for the line 242 subtraction as a defence-in-depth measure, consistent with the project's stated arithmetic safety invariant. [7](#0-6)

### Proof of Concept

```rust
// Preconditions:
// - Bridge has a UTXO worth 500_000 sat
// - min_withdraw_amount = 10_000, withdraw_fee ≈ 100
// - min_btc_gas_fee = 1_000, max_btc_gas_fee = 50_000

let amount = 10_000u128;          // min_withdraw_amount
let utxo_value = 500_000u128;     // large bridge UTXO

// Craft PSBT: one input (the large UTXO), one output to target address worth 1 sat
// total_input_amount = 500_000
// total_output_amount = 1
// gas_fee = 499_999  (>> max_btc_gas_fee, but check is at line 252)

// At line 242:
// max_received_amount = 10_000 - 100 - 499_999  →  u128 underflow → PANIC
```

The panic aborts `ft_on_transfer_callback`; `ft_resolve_transfer` refunds the 10 000 nBTC. No funds are lost, but the withdrawal fails with an opaque abort rather than a clean error message, and the gas is consumed.
