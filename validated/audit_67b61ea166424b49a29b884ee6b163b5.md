### Title
Missing Event Emission on Refund Finalization — (`File: contracts/satoshi-bridge/src/refund.rs`)

### Summary
The `verify_refund_finalize_callback` function completes the final, terminal state transition of the refund lifecycle — confirming the refund BTC transaction on-chain and cleaning up all associated state — but emits **no event**. Every other stage of the refund state machine emits a corresponding event, making this gap a direct analog to the Augur M06 finding.

### Finding Description
The refund flow in `satoshi-bridge` has a well-defined lifecycle with event coverage for three of its four state transitions:

| Stage | Function | Event Emitted |
|---|---|---|
| Request | `request_refund_callback` | `RefundRequested` ✓ |
| Reject | `internal_reject_refund` | `RefundRejected` ✓ |
| Execute (build tx) | `finalize_refund_with_psbt` | `RefundExecuted` + `GenerateBtcPendingInfo` ✓ |
| **Finalize (on-chain confirm)** | **`verify_refund_finalize_callback`** | **None ✗** |

In `verify_refund_finalize_callback`, the contract:
1. Verifies the refund BTC transaction is confirmed on-chain
2. Removes the `RefundRequest` from `refund_requests`
3. Removes the `BTCPendingInfo` via `internal_remove_btc_pending_info`
4. Removes the tx from the account's `btc_pending_verify_list`

…and then returns `true` with no event emitted. [1](#0-0) 

Compare with `internal_reject_refund`, which correctly emits `Event::RefundRejected` after removing the request: [2](#0-1) 

And `finalize_refund_with_psbt`, which emits `Event::RefundExecuted` and `Event::GenerateBtcPendingInfo`: [3](#0-2) 

The full event enum confirms there is no `RefundFinalized` variant defined: [4](#0-3) 

### Impact Explanation
Off-chain clients (user interfaces, indexers, monitoring systems) rely exclusively on emitted events to track bridge state transitions. Without a finalization event, they have no on-chain observable signal that a refund has been confirmed on Bitcoin and all associated bridge state has been cleaned up. This creates a permanent observability gap: the refund request and pending info are silently deleted, leaving off-chain state permanently inconsistent with on-chain state. This matches the Low allowed impact: "Publicly reachable invariant-violation, stuck-state, or panic-driven fault in production bridge/token paths without direct theft."

### Likelihood Explanation
Every successful refund that reaches on-chain confirmation goes through `verify_refund_finalize_callback`. The path is triggered by `verify_refund_finalize`, which is callable by any whitelisted relayer — a normal, expected bridge operation. The missing event fires on every successful refund finalization. [5](#0-4) 

### Recommendation
Define a `RefundFinalized` event variant in `event.rs` and emit it at the end of `verify_refund_finalize_callback`, including the `utxo_storage_key`, `account_id`, and `tx_id` so off-chain clients can correlate it with the earlier `RefundExecuted` event.

### Proof of Concept
1. User calls `request_refund` → `RefundRequested` event emitted (observable off-chain).
2. After timelock, anyone calls `execute_refund` → `RefundExecuted` + `GenerateBtcPendingInfo` events emitted (observable off-chain).
3. Relayer calls `verify_refund_finalize` after BTC confirmation → `verify_refund_finalize_callback` executes, removes `refund_requests[utxo_storage_key]`, removes `btc_pending_infos[tx_id]`, removes from `btc_pending_verify_list` — **zero events emitted**. Off-chain clients remain in the "executed but not finalized" state permanently, with no on-chain signal that the refund lifecycle has completed. [6](#0-5)

    pub fn verify_refund_finalize_callback(&mut self, tx_id: String) -> bool {
        let result_bytes = env::promise_result_checked(0, MAX_BOOL_RESULT)
            .expect("Call verify_transaction_inclusion failed");
        let is_valid = serde_json::from_slice::<bool>(&result_bytes)
            .expect("verify_transaction_inclusion return not bool");
        require!(is_valid, "verify_transaction_inclusion return false");

        let btc_pending_info = self.internal_unwrap_btc_pending_info(&tx_id).clone();
        btc_pending_info.assert_refund_pending_verify_tx();

        let account_id = btc_pending_info.account_id.clone();

        // A refund spends exactly one deposit UTXO, whose key is the refund request
        // key. More than one input would be abnormal for a refund.
        let utxo_storage_keys = btc_pending_info.get_psbt().get_utxo_storage_keys();
        require!(
            utxo_storage_keys.len() == 1,
            "refund transaction must spend exactly one input"
        );
        // Refund confirmed on-chain → drop the request so no further execute_refund
        // is possible. If it was already removed, this is harmlessly a no-op.
        self.data_mut()
            .refund_requests
            .remove(&utxo_storage_keys[0]);

        // Clean up: remove pending info
        self.internal_remove_btc_pending_info(&tx_id);
        self.internal_unwrap_mut_account(&account_id)
            .btc_pending_verify_list
            .remove(&tx_id);

        true
    }
