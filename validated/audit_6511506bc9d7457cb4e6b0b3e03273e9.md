### Title
Missing Minimum Transfer Amount Enforcement Causes Permanent Loss of Bridged Funds via Decimal Normalization Truncation - (`near/omni-bridge/src/lib.rs`)

---

### Summary

The `initTransfer` entry points across EVM, NEAR, Solana, and Starknet accept arbitrarily small token amounts with no minimum enforced. When the amount is too small to survive the decimal normalization applied inside `sign_transfer`, the NEAR bridge panics and permanently abandons the transfer — while the user's tokens are already burned or locked on the source chain with no refund path.

---

### Finding Description

Every chain's transfer initiation function enforces only that `fee < amount` (or `fee >= amount` reverts), with no floor on `amount` itself.

**EVM** (`OmniBridge.sol`, `initTransfer`): [1](#0-0) 

**NEAR** (`lib.rs`, `init_transfer`): [2](#0-1) 

**Starknet** (`omni_bridge.cairo`, `init_transfer`): [3](#0-2) 

**Solana** (`init_transfer.rs`): [4](#0-3) 

After a transfer is accepted, `init_transfer_internal` immediately burns or locks the full token amount on the NEAR side: [5](#0-4) 

Later, when a relayer calls `sign_transfer`, the amount is normalized to the destination chain's decimal precision: [6](#0-5) 

`normalize_amount` performs integer floor division by the decimal-difference factor (e.g., `10^10` for an 18→8 decimal token). Any source-chain amount below that factor produces `amount_to_transfer = 0`, causing `sign_transfer` to panic with `InvalidAmountToTransfer`. The transfer message remains in `pending_transfers` indefinitely — there is no cancel or refund path — while the tokens are already gone from the source chain.

The `Fee` struct defaults both fields to zero: [7](#0-6) 

So a user can legitimately call `initTransfer(token, amount=1, fee=0, ...)` and pass all on-chain validation, only to have the transfer permanently stuck.

---

### Impact Explanation

A user who initiates a cross-chain transfer with an amount smaller than the decimal normalization factor (e.g., less than `10^(src_decimals − dst_decimals)` base units) will have their tokens permanently burned or locked on the source chain. `sign_transfer` will always revert for that transfer ID, and no refund mechanism exists. This constitutes **permanent, irreversible loss of bridged funds** for any affected user.

---

### Likelihood Explanation

The condition is reachable by any unprivileged token holder calling the public `initTransfer` / `ft_transfer_call` entry points. Tokens bridged between chains with different decimal precisions (e.g., 18-decimal ERC-20 on Ethereum to 8-decimal representation on Bitcoin/Solana) are the common case in OmniBridge. A user sending a "dust" amount — or a malicious actor deliberately sending 1 wei to grief themselves and demonstrate the bug — triggers the permanent loss. No special role, leaked key, or admin action is required.

---

### Recommendation

1. Enforce a protocol-level minimum transfer amount in each chain's `initTransfer` entry point, sized to guarantee `normalize_amount(amount - fee, decimals) > 0` for every registered token pair.
2. Alternatively, perform the normalization check eagerly inside `init_transfer` on NEAR (before burning/locking) and revert if the normalized amount would be zero.
3. Add a user-callable `cancel_transfer` function that refunds locked/minted tokens for transfers that have been pending beyond a timeout, as a safety net.

---

### Proof of Concept

1. Register a token with 18 decimals on Ethereum and 8 decimals on the destination chain (normalization factor = `10^10`).
2. Call `OmniBridge.initTransfer(tokenAddress, amount=1, fee=0, nativeFee=0, recipient, "")` on Ethereum. The call succeeds; 1 wei is burned; `InitTransfer` is emitted.
3. The NEAR bridge processes the Wormhole VAA and stores the `TransferMessage` with `amount = 1`.
4. A relayer calls `sign_transfer(transfer_id, ...)`. Inside, `normalize_amount(1 - 0, {decimals:18, origin_decimals:8})` returns `0`. The `require!(amount_to_transfer > 0, ...)` check panics.
5. The transfer message stays in `pending_transfers` forever. The 1 wei is permanently lost. No refund is possible. [6](#0-5) [8](#0-7)
