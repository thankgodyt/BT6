### Title
Unconditional Peras Certificate Acceptance Bypasses All Cryptographic and Quorum Verification in Inbound Diffusion Handler — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance ships a stub `validatePerasCert` that unconditionally returns `Right` for every inbound certificate, performing zero cryptographic, quorum, or committee-membership checks. This stub is wired directly into the live Peras certificate diffusion inbound handler (`hPerasCertDiffusionClient`) in `NodeToNode.hs`. Any unprivileged peer that can open a Peras cert-diffusion miniprotocol connection can inject arbitrary `PerasCert` objects — for any round number and any block point — and have them accepted, timestamped, and stored in the ChainDB with a full Peras boost weight, without holding any stake or possessing any valid aggregate signature.

---

### Finding Description

**Root cause — `validatePerasCert` stub always returns `Right`**

The universal `BlockSupportsPeras` instance in `SupportsPeras.hs` provides the following implementation:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No aggregate-signature verification, no quorum check, no committee-membership check, and no round-number bounds check are performed. Every certificate is immediately wrapped in `ValidatedPerasCert` and assigned the full `perasWeight params` boost (currently 15).

**Wiring into the production inbound handler**

`makePerasCertPoolWriterFromChainDB` in `PerasCert.hs` passes this stub directly as the validation function:

```haskell
(validatePerasCert mkPerasParams)
``` [2](#0-1) 

`processCerts` then calls this validator on every inbound certificate batch. Because the validator never returns `Left`, the `(errs, _)` branch that would throw `PerasCertValidationError` and disconnect the peer is never reached; every certificate is accepted and forwarded to `ChainDB.addPerasCertAsync`. [3](#0-2) 

This writer is registered as `hPerasCertDiffusionClient` in the production `mkHandlers` call in `NodeToNode.hs`:

```haskell
, hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      ...
``` [4](#0-3) 

The handler is then bound into the full `initiatorAndResponder` bundle, making it reachable by any peer that negotiates a node-to-node version that includes the Peras cert-diffusion miniprotocol: [5](#0-4) 

**Contrast with the `validatePerasVote` path**

The vote diffusion handler is also broken, but in the opposite direction: it is hardwired with `(pure (PerasVoteStakeDistr mempty))`, so every inbound vote fails the stake-lookup and is rejected. The explicit code comment confirms this:

```
-- Note that the empty stake distribution will cause all votes to
-- be considered invalid.
(pure (PerasVoteStakeDistr mempty))
``` [6](#0-5) 

The asymmetry is security-critical: votes (which should accumulate to form certificates) are silently dropped, while certificates (which carry the Peras chain-selection boost) are unconditionally accepted.

**End-to-end exploit path**

1. Attacker connects to a target node and negotiates a node-to-node version that activates the Peras cert-diffusion miniprotocol.
2. Attacker sends a batch of crafted `PerasCert` values, each with an attacker-chosen `pcCertRound` and `pcCertBoostedBlock` (any `Point blk` the attacker wishes to boost).
3. `processCerts` calls `validatePerasCert mkPerasParams` on each cert; the stub returns `Right ValidatedPerasCert { vpcCertBoost = 15 }` for every one.
4. Each `ValidatedPerasCert` is passed to `ChainDB.addPerasCertAsync`, stored in the `PerasCertDB`, and made available to chain selection with a boost weight of 15.
5. The Peras boost influences the `WeightedSelectView` used in chain selection, potentially causing the node to prefer the attacker-chosen block over the honest chain tip.

---

### Impact Explanation

This is a **Critical bypass of Peras certificate verification**. The `validatePerasCert` stub removes the entire cryptographic gate that is supposed to ensure only legitimately quorum-backed certificates (carrying a valid aggregate BLS signature over the committee's votes) can influence chain selection. An unprivileged peer with a single TCP connection can:

- Inject certificates for arbitrary rounds and arbitrary block points.
- Assign those blocks a Peras boost weight of 15 in the node's chain-selection logic.
- Potentially cause the node to prefer an adversarially-chosen chain fragment over the honest canonical chain, constituting a chain-selection safety failure.

This matches the allowed impact category: **"Bypass of… certificate/signature validation… that enables unauthorized… certificate acceptance"** and **"Chain selection… bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain."**

---

### Likelihood Explanation

The Peras cert-diffusion miniprotocol is wired into the production `initiatorAndResponder` bundle and is gated only by the `CardanoFeatureFlag` set negotiated at connection time. Any peer that can open a connection and negotiate a version that enables the Peras protocols can immediately exploit this. No stake, no keys, and no prior knowledge of the chain state are required — only the ability to serialize a valid `PerasCert` CBOR value (a two-field structure: `pcCertRound :: PerasRoundNo` and `pcCertBoostedBlock :: Point blk`). [7](#0-6) 

---

### Recommendation

1. **Remove the stub and implement real validation** before the Peras cert-diffusion protocol is enabled for any peer-facing connection. `validatePerasCert` must verify the aggregate BLS signature over the claimed voter set, confirm that the claimed voters are members of the correct committee for the given round, and confirm that their combined stake meets the quorum threshold.
2. **Gate the protocol behind a feature flag that is off by default** until the full validation pipeline (committee selection data plumbed from ChainDB, aggregate signature verification, quorum check) is in place.
3. **Mirror the vote-side fix**: once real committee data is available, replace `(pure (PerasVoteStakeDistr mempty))` with the actual per-epoch stake distribution so that vote validation is also functional.

### Proof of Concept

```
-- Attacker constructs a minimal PerasCert targeting an adversarial block:
let craftedCert = PerasCert
      { pcCertRound       = PerasRoundNo 42          -- any round
      , pcCertBoostedBlock = adversarialBlockPoint    -- any Point blk
      }

-- Serialise and send via the Peras cert-diffusion miniprotocol.
-- On the receiving node, processCerts calls:
validatePerasCert mkPerasParams craftedCert
-- => Right (ValidatedPerasCert { vpcCert = craftedCert, vpcCertBoost = 15 })
-- No error is ever returned; the cert is stored in ChainDB with boost = 15.
```

The `PerasCert` CBOR encoding is a two-element list `[pcCertRound, pcCertBoostedBlock]`, fully documented in the `Serialise` instance: [7](#0-6) 

Any peer can construct and transmit this payload without any privileged material.

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
