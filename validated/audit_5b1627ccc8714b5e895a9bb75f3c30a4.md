### Title
Unauthenticated Peras Certificate Injection Enables Chain Selection Manipulation — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` function unconditionally returns `Right` — it performs zero cryptographic or structural validation. Any unprivileged peer can inject arbitrarily crafted `PerasCert` objects via the ObjectDiffusion miniprotocol. Each accepted certificate adds `PerasWeight 15` to the boosted block's chain-selection weight, allowing an attacker to make an honest node prefer a non-canonical fork without holding any stake or keys.

---

### Finding Description

**Root cause — stub validation that always succeeds:**

The catch-all `BlockSupportsPeras` instance, which applies to all `StandardHash blk` types including production Cardano blocks, implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params  -- always PerasWeight 15
      }
``` [1](#0-0) 

This is the only instance in the codebase; no more-specific override exists for Cardano blocks. [2](#0-1) 

**Inbound processing pipeline — no gate before cert DB insertion:**

`makePerasCertPoolWriterFromChainDB` wires `validatePerasCert mkPerasParams` directly as the validation callback for all inbound peer certificates: [3](#0-2) 

`processCerts` calls this validator on every new certificate received from a peer. Because `validatePerasCert` always returns `Right`, the `([], validatedCerts)` branch is always taken and every certificate is forwarded to `addCert`: [4](#0-3) 

**Chain selection impact — injected weight directly alters fork preference:**

`addPerasCertAsync` enqueues the accepted certificate for chain selection. The `PerasWeightSnapshot` is updated with `PerasWeight 15` for the certificate's `pcCertBoostedBlock`. Chain selection then computes `wsvTotalWeight = blockNo + weightBoost` and switches to any candidate whose total weight exceeds the current chain: [5](#0-4) 

The `perasWeight` default is `PerasWeight 15`: [6](#0-5) 

**Deduplication does not prevent the attack:**

`processCerts` deduplicates by `PerasRoundNo`, so only one certificate per round is accepted. However, an attacker can inject one certificate per round, each boosting a different block on their preferred fork, accumulating unbounded weight advantage over the honest chain. [7](#0-6) 

---

### Impact Explanation

**High — chain selection manipulation.** An unprivileged peer can inject fake `PerasCert` objects that boost any block on an adversary-controlled fork by 15 weight units per certificate. Because `wsvTotalWeight` adds block number and weight boost, a fork that is up to 15 blocks shorter than the honest chain can be made to appear heavier after a single injected certificate. With multiple certificates across multiple rounds, the attacker can accumulate an arbitrarily large weight advantage, causing the honest node to permanently prefer and follow a non-canonical chain. This breaks the chain-selection invariant that honest nodes converge on the longest (heaviest) valid chain.

---

### Likelihood Explanation

**High.** The ObjectDiffusion miniprotocol is reachable by any connected peer without authentication. No stake, keys, or special privileges are required. The attacker only needs to craft a `PerasCert` with a `pcCertBoostedBlock` pointing to a block on their preferred fork and a fresh `pcCertRound`. The validation function unconditionally accepts it. This is a single-message exploit requiring no brute force.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with real cryptographic validation before the Peras ObjectDiffusion miniprotocol is enabled in production. At minimum, the function must verify:

1. The certificate's committee membership proof (BLS aggregate signature or equivalent).
2. That the `pcCertBoostedBlock` is a known, valid block on a plausible chain.
3. That the `pcCertRound` is within the valid window relative to the current slot.

Until real validation is implemented, the ObjectDiffusion handler for Peras certificates should be disabled or gated behind a feature flag that is off by default, analogous to how the original `approve()` fix restricted the function to trusted callers only.

---

### Proof of Concept

**Attacker-controlled entry path:**

1. Attacker connects to an honest node as a peer via the ObjectDiffusion miniprotocol for Peras certificates.
2. Attacker sends a batch containing one `PerasCert`:
   ```
   PerasCert { pcCertRound = <fresh round N>, pcCertBoostedBlock = <point on attacker's fork> }
   ```
3. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = PerasWeight 15 })` unconditionally.
4. The certificate is passed to `ChainDB.addPerasCertAsync`, which enqueues it for chain selection.
5. `chainSelSync` processes the certificate; `PerasWeightSnapshot` is updated to add `PerasWeight 15` to the attacker's fork block.
6. `weightedSelectView` computes `wsvTotalWeight` for the attacker's fork as `blockNo + 15`. If the honest chain's tip has `blockNo ≤ attacker_blockNo + 15`, the node switches to the attacker's fork.
7. Repeating with round `N+1`, `N+2`, … accumulates weight indefinitely. [1](#0-0) [3](#0-2) [4](#0-3) [8](#0-7) [6](#0-5)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
