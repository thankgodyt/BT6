### Title
Peras Vote Validation Bypass via Missing Cryptographic Signature Check — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasVote` implementation performs no cryptographic signature verification. Any unprivileged peer can send a crafted `PerasVote` message claiming to be any committee member present in the stake distribution, and the receiving node will accept it as a valid, stake-weighted vote. Accumulating enough such forged votes causes the node to forge a fraudulent Peras certificate, which is then used in chain selection to boost a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasVote` as the gate that must authenticate an inbound vote before it is stored and counted toward quorum. The production instance (the only instance in the codebase, used for all block types) is explicitly a stub:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [1](#0-0) 

The only check performed is a `Map.lookup` of the claimed `pvVoteVoterId` in the stake distribution. No BLS signature is verified, no VRF eligibility proof is checked, and no committee membership proof is required. The `_params` argument (which carries the `PerasCfg` needed for cryptographic context) is discarded entirely.

The same stub pattern applies to `validatePerasCert`, which unconditionally returns `Right` for every certificate:

```haskell
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [2](#0-1) 

These stubs are wired directly into the production inbound vote processing path. `processVotes` — called from both `makePerasVotePoolWriterFromChainDB` and `makePerasVotePoolWriterFromVoteDB` — invokes `validatePerasVote` on every new vote received from a peer before storing it:

```haskell
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
``` [3](#0-2) 

The `validateVote` callback supplied in production is:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [4](#0-3) 

This is the degenerate stub. The `PerasVoteId` deduplication guard (`alreadyInDb` check) only prevents the *same* `(roundNo, voterId)` pair from being counted twice. It does not prevent an attacker from forging votes for *different* committee members — all of whom are visible in the public stake distribution — and submitting them in separate batches or as a single batch with distinct `PerasVoteId`s.

The `PerasVoteId` type is `(PerasRoundNo, PerasVoterId)`: [5](#0-4) 

An attacker who knows the stake distribution (public on-chain data) can craft one vote per committee member per round, each with a distinct `PerasVoteId`, all targeting the same block. Each forged vote passes `validatePerasVote` (stake lookup succeeds), passes the `alreadyInDb` filter (each has a unique ID), and is stored. `updatePerasRoundVoteStates` accumulates their stake: [6](#0-5) 

Once the accumulated stake crosses the quorum threshold, `implAddVote` forges a `ValidatedPerasCert` for the attacker-chosen block: [7](#0-6) 

The same bypass applies to `processCerts` / `validatePerasCert`: a peer can inject a certificate for any round and any block hash with zero cryptographic material, and it will be accepted unconditionally. [8](#0-7) 

---

### Impact Explanation

A fraudulent `ValidatedPerasCert` produced this way is used in Peras chain selection to apply a boost weight to the attacker-chosen block. This causes an honest node to prefer a non-canonical or adversarially-chosen chain over the honest chain, constituting a **chain selection safety failure**. The impact matches the allowed scope:

> *Critical. Bypass of … Peras voting or certificate checks … that enables unauthorized … vote, or certificate acceptance.*
> *High. Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain.*

---

### Likelihood Explanation

The stake distribution is public. The `PerasVote` wire format is serialised and documented: [9](#0-8) 

Any peer connected via the object-diffusion mini-protocol can send a batch of crafted votes. No key material, no stake, and no special privilege is required — only knowledge of the stake distribution and the current round number. The attack is deterministic and repeatable every Peras round.

---

### Recommendation

Replace the stub `validatePerasVote` implementation with one that:

1. Verifies the BLS vote signature using the voter's public key retrieved from the committee selection context (not just the stake distribution), as already implemented in `implVerifyVote` for the `EveryoneVotes` and `WFALS` committee schemes.
2. Verifies VRF eligibility proofs for non-persistent committee members.
3. Checks that the claimed `pvVoteVoterId` / seat index is actually eligible for the current round's committee selection.

Similarly, replace the stub `validatePerasCert` with one that verifies the aggregate BLS signature over the claimed voter set, as already implemented in `implVerifyCert`.

The `InterEpochVotingCommittee` abstraction and the `CryptoSupportsVoteSigning` / `CryptoSupportsAggregateVoteSigning` interfaces are already in place and provide all the primitives needed: [10](#0-9) [11](#0-10) 

---

### Proof of Concept

The following sketch demonstrates the attack path using the existing test infrastructure. An attacker node connects via the object-diffusion protocol and sends one forged `PerasVote` per committee member:

```haskell
-- Attacker knows the stake distribution (public on-chain data)
let stakeDistr = ... -- obtained from ledger state query
    roundNo   = ... -- current Peras round
    targetBlk = ... -- attacker-chosen block to boost

-- Forge one vote per committee member (no key material needed)
let forgedVotes =
      [ PerasVote
          { pvVoteRound   = roundNo
          , pvVoteBlock   = targetBlk
          , pvVoteVoterId = voterId  -- any key in stakeDistr
          }
      | voterId <- Map.keys (unPerasVoteStakeDistr stakeDistr)
      ]

-- Send forgedVotes to the victim node via the object-diffusion mini-protocol.
-- processVotes will:
--   1. Filter: none are in alreadyInDb (all have distinct PerasVoteIds)
--   2. Validate: validatePerasVote succeeds for each (stake lookup passes)
--   3. Add: implAddVote accumulates stake; once quorum is reached,
--      a ValidatedPerasCert for targetBlk is forged automatically.
-- The victim node now boosts targetBlk in chain selection.
```

The `processVotes` function accepts the batch without disconnecting the peer because all votes pass the stub validator: [12](#0-11)
