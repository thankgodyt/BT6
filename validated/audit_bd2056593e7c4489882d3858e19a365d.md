### Title
Lack of Access Control on `execute_refund` Assigns `BTCPendingInfo` to Arbitrary Caller Instead of Original Depositor - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary
`execute_refund` is a public, permissionless function. Any NEAR account can call it for any pending refund request. The caller's account — not the original depositor's — becomes the owner of the resulting `BTCPendingInfo`. This mirrors the external report's pattern: a function that performs an action on behalf of another user without verifying the caller is that user.

### Finding Description
`execute_refund` in `bridge.rs` carries no caller-identity check:

```rust
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn execute_refund(
    &mut self,
    utxo_storage_key: String,
    chain_specific_data: Option<ChainSpecificData>,
) -> PromiseOrValue<()> {
    let timelock_sec = self.resolve_execute_refund_timelock(&utxo_storage_key);
    self.internal_execute_refund(utxo_storage_key, timelock_sec, chain_specific_data)
}
``` [1](#0-0) 

`internal_execute_refund` eventually calls `finalize_refund_with_psbt`, whose own doc comment acknowledges the ownership assignment:

> "`caller` is the account that will own the pending info — it must be passed explicitly because on Zcash this runs inside a `#[private]` callback where `predecessor` is the contract itself." [2](#0-1) 

Inside `finalize_refund_with_psbt`, the caller's account is created if absent, its pending-sign capacity is checked, and the new `BTCPendingInfo` is inserted into the **caller's** `btc_pending_sign_ids`:

```rust
if !self.check_account_exists(&caller) {
    self.internal_set_account(&caller, crate::Account::new(&caller));
}
self.require_pending_sign_capacity(&caller);
...
self.internal_unwrap_mut_account(&caller)
    .btc_pending_sign_ids
    .insert(btc_pending_id.clone());
``` [3](#0-2) 

The original depositor's account receives no `btc_pending_sign_ids` entry for their own refund.

### Impact Explanation
- The original depositor loses all control over when their refund is executed; any third party can force execution after the timelock.
- The `BTCPendingInfo` is permanently associated with the caller's NEAR account, not the depositor's. The depositor cannot observe or manage their own in-flight refund through their account state.
- The BTC itself is sent to the pre-committed `refund_address`, so there is no direct theft. However, the on-chain invariant that a user's pending operations are tracked under their own account is broken.
- If the caller's account is at its `pending_sign_capacity` limit, `require_pending_sign_capacity` panics, blocking execution for that caller — though another caller can retry.

This matches: **Low — Publicly reachable invariant-violation in production bridge paths without direct theft.**

### Likelihood Explanation
`execute_refund` is explicitly documented as callable by anyone after the timelock elapses. No authentication, no deposit-owner check, no role requirement. Any unprivileged NEAR account can trigger this for any existing refund request.

### Recommendation
Resolve the `BTCPendingInfo` ownership to the original depositor rather than the transaction caller. One approach: store the depositor's NEAR account ID in the `RefundRequest` at `request_refund` time, and pass that stored ID — not `env::predecessor_account_id()` — as `caller` to `finalize_refund_with_psbt`. Alternatively, restrict `execute_refund` so only the original depositor or a privileged role can call it:

```rust
pub fn execute_refund(
    &mut self,
    utxo_storage_key: String,
    chain_specific_data: Option<ChainSpecificData>,
) -> PromiseOrValue<()> {
    let caller = env::predecessor_account_id();
    let is_privileged = self.acl_has_any_role(
        vec![Role::DAO.into(), Role::RefundOperator.into()], caller.clone()
    );
    // Only the depositor or a privileged role may execute
    require!(
        is_privileged || /* caller == original depositor stored in RefundRequest */,
        "Only the original depositor or a privileged role can execute this refund"
    );
    let timelock_sec = self.resolve_execute_refund_timelock(&utxo_storage_key);
    self.internal_execute_refund(utxo_storage_key, timelock_sec, chain_specific_data)
}
```

### Proof of Concept
1. User A sends BTC to the bridge deposit address and the deposit is never finalized.
2. User A calls `request_refund`, supplying a `refund_address` (BTC address). The `RefundRequest` is stored under `utxo_storage_key`.
3. The timelock elapses.
4. Attacker B calls `execute_refund(utxo_storage_key, None)`.
5. `finalize_refund_with_psbt` is invoked with `caller = B`. B's account is created if absent; the `BTCPendingInfo` is inserted into B's `btc_pending_sign_ids`.
6. User A's NEAR account has no record of the in-flight refund. A cannot manage, observe, or cancel the pending operation through their own account.
7. BTC is ultimately sent to User A's `refund_address` — no theft — but A had no say in timing and their account state is permanently inconsistent. [1](#0-0) [4](#0-3)
