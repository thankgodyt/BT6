### Title
Unconditional `validatePerasCert` Acceptance Allows Any Peer to Inject Fake Peras Certificates and Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The catch-all `instance StandardHash blk => BlockSupportsPeras blk` implements `validatePerasCert` as an unconditional `Right` — it accepts every inbound certificate without performing any cryptographic or structural verification. This instance is the only one in the codebase and is wired directly into the peer-facing certificate ingestion path (`processCerts`). An unprivileged peer can therefore inject a crafted `PerasCert` boosting any block hash, causing the victim node to add spurious Peras weight to a non-canonical fork and switch to it via chain selection.

### Finding Description

**Root cause — stub validation always succeeds**

The degenerate instance at `SupportsPeras.hs` lines 350–358 is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature, quorum, round-number, or committee-membership check is performed. The caller-supplied `cert` is wrapped verbatim in `ValidatedPerasCert` and returned as valid. This is the only `BlockSupportsPeras` instance in the repository — a `grep` for `BlockSupportsPeras` finds no Cardano-specific override.

**Attacker-controlled entry path — peer certificate ingestion**

`makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB` both wire this stub directly into the object-diffusion mini-protocol handler:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [2](#0-1) [3](#0-2) 

`processCerts` receives a batch of `PerasCert` values from a remote peer, calls `validateCert` on each, and — because the stub always returns `Right` — adds every certificate to the `PerasCertDB` and calls `addCert`: [4](#0-3) 

**Chain-selection impact**

Once a `ValidatedPerasCert` is in the `PerasCertDB`, `chainSelSync` is triggered. It looks up the boosted block in the `VolatileDB` and calls `chainSelectionForBlock`, which rebuilds the `PerasWeightSnapshot` and re-runs chain selection: [5](#0-4) 

Chain selection compares fragments using `WeightedSelectView`, where `wsvTotalWeight = blockNo + wsvWeightBoost`. A fake certificate adds `perasWeight params` to the boosted block's fragment, potentially making a shorter or otherwise non-preferred fork appear heavier: [6](#0-5) 

**Analog to the reported vulnerability**

The original bug: both the Merkle proof and the storage root are taken from the same caller-controlled argument, making `SecureMerkleTrie.verifyInclusionProof` trivially satisfiable. Here: the entire certificate is caller-controlled and `validatePerasCert` performs no independent check — the "proof" (the cert) and the "anchor" (the committee/quorum state) are both ignored, making certificate acceptance unconditional.

### Impact Explanation

**High — chain selection manipulation by an unprivileged peer.**

An attacker who can connect as a normal peer can send a `PerasCert` with an arbitrary `pcCertBoostedBlock` pointing to any block hash in the victim's `VolatileDB`. The victim node will:
1. Accept the certificate without any verification.
2. Add `perasWeight` boost to the attacker-chosen block.
3. Re-run chain selection; if the boosted fork's total weight now exceeds the current selection, the node switches to the non-canonical fork.

This directly matches the allowed impact scope: *"Chain selection, rollback, forecast, genesis, or header-state bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

### Likelihood Explanation

**High.** The entry point is the standard peer-to-peer object-diffusion mini-protocol, reachable by any node that can establish a connection. No keys, stake, or special privileges are required. The stub is the only instance in the codebase and is explicitly wired into both the `PerasCertDB` and `ChainDB` writers with a `TODO` comment acknowledging the missing validation.

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
1. Verifies the aggregate BLS vote signature against the committee's aggregate public key derived from the ledger stake distribution (not from the certificate itself).
2. Checks that the number of signers meets the quorum threshold.
3. Validates that `pcCertRound` is within the acceptable window relative to the current slot.
4. Binds the boosted block hash to the round number to prevent cross-round replay.

Until a real implementation exists, the certificate ingestion path should reject all inbound certificates rather than accept them unconditionally.

### Proof of Concept

1. Attacker node connects to victim via the object-diffusion mini-protocol.
2. Attacker crafts `PerasCert { pcCertRound = r, pcCertBoostedBlock = forkTip }` where `forkTip` is the tip of a fork the attacker wants the victim to adopt.
3. Attacker sends the certificate to the victim.
4. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right (ValidatedPerasCert cert (perasWeight mkPerasParams))` unconditionally.
5. `chainSelSync` adds `perasWeight` to `forkTip` in the `PerasWeightSnapshot`.
6. `constructPreferableCandidates` now sees the fork as heavier; `chainSelection` switches the victim to the attacker's fork. [7](#0-6) [8](#0-7)

data PerasCertInboundException
  = forall blk. PerasCertValidationError [PerasValidationErr blk]

deriving instance Show PerasCertInboundException

instance Exception PerasCertInboundException

-- | Process a batch of inbound Peras certificates received from a peer.
--
-- Certificates whose round number is already present in the database (as
-- determined by @alreadyInDbSTM@) are silently skipped. The remaining
-- certificates are validated; if /any/ certificate in the batch fails
-- validation, the entire batch is rejected by throwing a
-- 'PerasCertInboundException' (which should make us disconnect from the distant
-- peer, see 'withPeer' bracket function from `ouroboros-network`). Otherwise,
-- each valid certificate is timestamped with the current wall-clock time and
-- added to the database via @addCert@.
processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
