Based on my investigation of the production bridge code, here is my finding:

### Title
Unprivileged Account Can Call `request_refund` and Redirect BTC Refund to Attacker-Controlled Address — (`contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary

`request_refund` sits in a `#[trusted_relayer]` impl block but carries **no per-method `#[trusted_relayer]` attribute**. Code-pattern analysis across the entire file proves the impl-level attribute is a configuration/registration decorator only — enforcement requires the per-method attribute. Any NEAR account can therefore call `request_refund`. For deposits whose `deposit_msg.refund_address` is `None`, the caller freely supplies any BTC address, enabling theft of the deposited BTC.

### Finding Description

**The `#[trusted_relayer]` impl-level attribute does not gate all methods in the block.**

Evidence from the same file:

| Method | Per-method `#[trusted_relayer]`? | Notes |
|---|---|---|
| `verify_deposit` | ✅ yes | gated |
| `verify_withdraw` | ✅ yes | gated |
| `verify_refund_finalize` | ✅ yes | gated |
| `remove_refund_pending_tx_id` | ✅ yes | gated |
| `get_user_deposit_address` | ❌ no | intentionally public |
| `reject_refund` | ❌ no | intentionally public (permissionless path) |
| **`request_refund`** | ❌ **no** | **missing — should be gated** | [1](#0-0) 

If the impl-level attribute applied to all methods, `get_user_deposit_address` and `reject_refund` would also be relayer-gated — which contradicts their documented permissionless semantics. The `lib.rs` configuration block further confirms this: `new()` is in a `#[trusted_relayer(...)]` impl block but is clearly not relayer-gated. [2](#0-1) 

`request_refund` itself has only `#[payable]` and `#[pause]`: [3](#0-2) 

**The `refund_address` redirect path:**

In `request_refund_callback`, when `deposit_msg.refund_address` is `None`, the caller-supplied `refund_address` is accepted without restriction: [4](#0-3) 

The stored `RefundRequest` records the attacker-supplied address: [5](#0-4) 

**`execute_refund` is permissionless.** The `request_refund` doc comment states: *"After the timelock period, anyone can call `execute_refund` to initiate the return."* [6](#0-5) 

### Impact Explanation

For any deposit where `deposit_msg.refund_address` is `None`:

1. Attacker observes a BTC deposit on-chain.
2. Attacker reconstructs `deposit_msg` (often trivial: `recipient_id` is a public NEAR account; other fields are commonly `None`).
3. Attacker calls `request_refund` with the correct `deposit_msg` and `refund_address = <attacker BTC address>`, paying only the storage anti-spam fee.
4. After the timelock, attacker (or anyone) calls `execute_refund`.
5. The bridge MPC-signs a BTC transaction sending the deposited funds to the attacker's address.

**Impact: Critical — theft of user BTC.**

### Likelihood Explanation

- `deposit_msg` fields are often trivially guessable (public NEAR account ID, all other fields `None`).
- The anti-spam fee is a small NEAR amount, not a meaningful deterrent for a BTC theft.
- The attack is front-runnable: attacker submits `request_refund` before the relayer calls `verify_deposit`.
- The `request_refund_callback` blocks the attack only if `verified_deposit_utxo` already contains the UTXO — a race the attacker can win on slow or unprocessed deposits. [7](#0-6) 

### Recommendation

Add `#[trusted_relayer]` as a per-method attribute on `request_refund`, consistent with every other sensitive method in the same impl block:

```rust
#[allow(clippy::too_many_arguments)]
#[payable]
#[trusted_relayer]                          // ← add this
#[pause(except(roles(Role::DAO)))]
pub fn request_refund(
``` [8](#0-7) 

Also add a test to `test_unauthorized_account_cannot_call_trusted_relayer_methods` that asserts `request_refund` returns `"Relayer is not active"` for an unprivileged caller, mirroring the existing checks for `verify_deposit`, `safe_verify_deposit`, `verify_withdraw`, and `verify_active_utxo_management`. [9](#0-8) 

### Proof of Concept

```
1. Deploy bridge (sandbox).
2. Create account `attacker` — grant NO roles.
3. Alice deposits BTC to bridge address derived from
   DepositMsg { recipient_id: "alice.near", refund_address: None, ... }.
4. attacker calls request_refund(
       deposit_msg = { recipient_id: "alice.near", refund_address: None, ... },
       refund_address = "attacker_btc_address",
       tx_bytes = <alice's deposit tx>,
       vout = 0,
       proof = <valid merkle proof>,
       gas_fee = None
   ) with required storage deposit attached.
5. Assert: call succeeds (no "Relayer is not active" error).
6. Set refund_timelock_sec = 0 (or wait).
7. attacker calls execute_refund(utxo_storage_key).
8. Assert: BTC refund transaction is constructed paying attacker_btc_address.
```
