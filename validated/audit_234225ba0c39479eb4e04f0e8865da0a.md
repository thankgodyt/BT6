### Title
`checkPreferTheirsOverOurs` Uses Hardcoded `emptyPerasWeightSnapshot`, Ignoring Peras Weight Boosts in Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

When a received header is beyond the forecast horizon, the ChainSync client calls `checkPreferTheirsOverOurs` to decide whether to disconnect from the peer. This function compares the candidate chain against the local selection using a hardcoded `emptyPerasWeightSnapshot` instead of the real Peras weight snapshot from the ChainDB. When Peras is active, this causes the comparison to ignore all certificate-based weight boosts, making a legitimately heavier candidate chain appear lighter than the local selection. The node then disconnects from the peer serving the canonical chain and remains on a less-secure fork.

---

### Finding Description

The function `checkPreferTheirsOverOurs` in `ChainSync/Client.hs` is invoked when `readLedgerStateHelper` cannot obtain a ledger view because the candidate header is beyond the forecast horizon. Its purpose is to guard against a peer serving a chain that can never be adopted: if the candidate is already not preferable to our selection, there is no point waiting, so the node disconnects with `CandidateTooSparse`.

The comparison is performed via `preferAnchoredCandidate`, which accepts a `PerasWeightSnapshot` to account for Peras certificate boosts. However, the call site hardcodes `emptyPerasWeightSnapshot`:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← always empty, ignores real Peras weights
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse ...
``` [1](#0-0) 

The real Peras weight snapshot is available via `getPerasWeightSnapshot` on the `ChainDB` API and is already used correctly in the main chain selection path inside `ChainSel.hs`:

```haskell
(,,)
  <$> (forgetFingerprint <$> readTVar cdbInvalid)
  <*> Query.getCurrentChain cdb
  <*> (forgetFingerprint <$> Query.getPerasWeightSnapshot cdb)
``` [2](#0-1) 

The `preferAnchoredCandidate` function, when given a non-empty snapshot, computes `wsvTotalWeight = BlockNo + PerasWeightBoost` for each fragment suffix and compares them. With `emptyPerasWeightSnapshot`, it falls back to comparing only by `BlockNo`, completely discarding any certificate-derived weight: [3](#0-2) [4](#0-3) 

The analog to the external report is direct: just as `setPayee()` changed payment routing without updating the slope/y-intercept used to compute `totalAssets()`, here a chain comparison function changes the effective "weight accounting" (from real Peras weights to zero) without updating the security-critical decision that depends on it.

---

### Impact Explanation

When Peras is active, a candidate chain can be **shorter by block count but heavier by total Peras weight** — for example, if a block on the candidate received a large certificate boost. In this scenario:

- Our chain: 5 blocks, no boosts → total weight = 5
- Candidate: 4 blocks, one block boosted by weight 3 → total weight = 7

The candidate is the canonical chain (heavier), but `checkPreferTheirsOverOurs` with `emptyPerasWeightSnapshot` sees only block counts (4 < 5) and concludes the candidate is **not preferable**. It throws `CandidateTooSparse`, disconnecting from the peer serving the canonical chain.

The node then remains on the lighter, non-canonical fork. If the only peer serving the canonical chain is disconnected this way, the node permanently diverges from the honest majority. This is a **chain selection error** matching the "High" impact category: an unprivileged peer can cause an honest node to prefer a non-canonical, less-secure chain beyond the intended security assumptions.

---

### Likelihood Explanation

The bug is latent: Peras is currently disabled by default, so there is no observable impact on mainnet today. However, the code is already deployed in production and the Peras feature is being actively developed. Once Peras is enabled, any peer can trigger this path by serving a valid header beyond the forecast horizon — no special privileges, keys, or stake are required. The TODO comment in the code (`-- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64`) confirms the developers are aware the check is incorrect under Peras but have not yet resolved it. [5](#0-4) 

---

### Recommendation

Either:

1. **Pass the real Peras weight snapshot** to `checkPreferTheirsOverOurs`. The snapshot is accessible via `getPerasWeightSnapshot` on the `ChainDbView` already threaded through the ChainSync client environment, so the fix is to read it atomically and pass it to `preferAnchoredCandidate` instead of `emptyPerasWeightSnapshot`.

2. **Remove the check entirely**, as the TODO suggests (tracking issue: `https://github.com/tweag/cardano-peras/issues/64`). The check was designed for the non-Peras case; under Peras, the correct behavior is to wait for the forecast horizon to advance rather than disconnecting based on an incomplete weight comparison.

---

### Proof of Concept

Private-testnet sequence with Peras enabled:

1. Start a node with Peras active. Let the node's current selection be chain `A-B-C-D-E` (5 blocks, no boosts, total weight = 5).
2. A Peras certificate is issued for block `F` on a fork `A-B-C-F`, giving `F` a boost of weight 3. The fork's total weight = 4 + 3 = 7 > 5.
3. A peer serves the fork `A-B-C-F`. The header `F` is beyond the current forecast horizon (e.g., it is in a slot far enough ahead that `ledgerViewForecastAt` returns `OutsideForecastRange`).
4. `readLedgerStateHelper` calls `checkPreferTheirsOverOurs`.
5. `preferAnchoredCandidate` is called with `emptyPerasWeightSnapshot`. It compares block counts: `ourFrag` has 5 blocks, `theirFrag` has 4 blocks. The candidate is **not** preferable by block count alone.
6. `throwSTM (CandidateTooSparse ...)` is executed. The node disconnects from the peer.
7. The node remains on the 5-block chain (total weight 5) and never adopts the canonical 4-block chain (total weight 7). [6](#0-5)

preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"
        Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
          case preferCandidate
            (projectChainOrderConfig cfg)
            (weightedSelectView cfg weights oursSuffix)
