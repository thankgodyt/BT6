### Title
Fee-on-Transfer Token Escrow Under-Collateralization in `initTransfer` - (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

### Summary
`OmniBridge.initTransfer` records and emits the caller-supplied `amount` in the `InitTransfer` event without checking the contract's actual token balance before and after the `safeTransferFrom` call. For fee-on-transfer ERC20 tokens, the bridge receives fewer tokens than `amount`, but the NEAR side finalizes the transfer for the full `amount`, permanently under-collateralizing the EVM escrow.

### Finding Description
In `OmniBridge.initTransfer`, when the token is neither a bridge token nor a custom-minter token, the contract executes:

```solidity
} else {
    IERC20(tokenAddress).safeTransferFrom(
        msg.sender,
        address(this),
        amount
    );
}
``` [1](#0-0) 

Immediately after, the function emits:

```solidity
emit BridgeTypes.InitTransfer(
    msg.sender,
    tokenAddress,
    currentOriginNonce,
    amount,   // ← always the caller-supplied value, never the received value
    fee,
    nativeFee,
    recipient,
    message
);
``` [2](#0-1) 

No balance snapshot is taken before the transfer, and no balance snapshot is compared after it. For a fee-on-transfer token, `address(this)` receives `amount - transfer_fee`, but the event records `amount`. The NEAR light-client or Wormhole prover reads this event as the authoritative proof of how many tokens were locked, and the NEAR bridge finalizes a release of `amount` tokens to the recipient.

The same pattern exists in the Starknet bridge's `init_transfer`, which also calls `transfer_from` and emits the event using the caller-supplied `amount` without a balance delta check: [3](#0-2) 

### Impact Explanation
Every `initTransfer` call with a fee-on-transfer token creates a deficit of `transfer_fee` tokens in the EVM escrow. The NEAR side mints or releases the full `amount`, so the attacker (or any user of such a token) receives more value on NEAR than was actually locked on EVM. Repeated transfers accumulate the deficit. When legitimate users later bridge back from NEAR to EVM, `finTransfer` calls `safeTransfer(recipient, amount)`: [4](#0-3) 

The contract will either revert (denying withdrawals to honest users) or, if the deficit is covered by other users' locked tokens, silently drain those funds. This is a direct escrow mis-accounting / balance manipulation impact: bridged funds are permanently at risk of loss or freezing.

### Likelihood Explanation
The bridge is designed to support arbitrary ERC20 tokens registered via `logMetadata`. Any token holder can call `initTransfer` with a fee-on-transfer token (e.g., tokens with built-in transfer taxes, which are common in DeFi). No admin action or privileged access is required. The attacker-controlled entry path is fully public. Likelihood is moderate given the prevalence of fee-on-transfer tokens and the permissionless nature of `initTransfer`. [5](#0-4) 

### Recommendation
Record the contract's token balance before and after the `safeTransferFrom` call, and use the delta as the canonical locked amount in both internal accounting and the emitted event:

```solidity
uint256 balanceBefore = IERC20(tokenAddress).balanceOf(address(this));
IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
uint256 received = IERC20(tokenAddress).balanceOf(address(this)) - balanceBefore;
// use `received` (cast to uint128) in place of `amount` for the event and accounting
```

Apply the same fix to the Starknet `init_transfer` function.

### Proof of Concept
1. Deploy a standard ERC20 token with a 1% transfer fee (fee-on-transfer).
2. Register the token with the bridge via `logMetadata`.
3. Call `initTransfer(tokenAddress, 1000, 0, 0, "attacker.near", "")`.
4. The bridge receives 990 tokens (`safeTransferFrom` deducts 10 as fee), but emits `InitTransfer(..., amount=1000, ...)`.
5. The NEAR prover reads the event; NEAR bridge mints 1000 tokens to `attacker.near`.
6. Attacker has gained 10 tokens of value on NEAR that are not backed by EVM escrow.
7. Repeat N times; the EVM escrow deficit grows to `N * 10`.
8. The next legitimate user attempting to bridge back from NEAR to EVM via `finTransfer` for 990 tokens will succeed, but the Nth legitimate user will find the escrow insolvent and their `safeTransfer` will revert — their funds are permanently frozen. [6](#0-5)
