### Title
Excess NEAR Attached to `sign_btc_transaction` Is Permanently Lost — (`File: contracts/satoshi-bridge/src/chain_signature.rs`)

---

### Summary

`sign_btc_transaction` is a public `#[payable]` function. It forwards the caller's entire `env::attached_deposit()` to the Chain Signatures MPC contract with no minimum/maximum validation and no refund of any excess. If a user attaches more NEAR than the MPC contract requires, the surplus is permanently transferred to the Chain Signatures contract and never returned to the bridge user.

---

### Finding Description

`sign_btc_transaction` in `contracts/satoshi-bridge/src/api/chain_signatures.rs` is marked `#[payable]` and calls `internal_sign_btc_transaction`, which calls `sign_promise`:

```rust
// chain_signature.rs
pub fn sign_promise(&self, request: SignRequest) -> Promise {
    let config = self.internal_config();
    ext_chain_signatures::ext(config.chain_signatures_account_id.clone())
        .with_static_gas(GAS_FOR_SIGN_CALL)
        .with_attached_deposit(env::attached_deposit())   // ← entire deposit forwarded
        .sign(request)
}
``` [1](#0-0) 

The public entry point:

```rust
// api/chain_signatures.rs
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn sign_btc_transaction(
    &mut self,
    btc_pending_sign_id: String,
    sign_index: usize,
    key_version: u32,
) -> PromiseOrValue<bool> { ... }
``` [2](#0-1) 

There is no guard of the form `require!(env::attached_deposit() == expected_mpc_fee, ...)` and no code path that returns excess NEAR to the caller. The entire `attached_deposit()` is consumed by the cross-contract call to the Chain Signatures service. Any amount above what the MPC contract actually needs is absorbed by that external contract and is unrecoverable by the bridge user.

---

### Impact Explanation

**Impact: Medium — permanent loss of user NEAR funds.**

A bridge user who attaches more NEAR than the MPC signing fee (e.g., due to fee-estimation error, stale fee data, or a race condition where the MPC fee changed between estimation and submission) loses the excess permanently. The funds are transferred to the Chain Signatures contract and the bridge has no mechanism to recover or refund them. This matches the allowed impact: *"Medium. Harmful smart-contract behavior without direct funds theft … or stuck bridge state requiring operator intervention."* The lost asset is NEAR (not nBTC/BTC), so it does not directly compromise the BTC peg, but it is a real, irreversible loss of user funds triggered through a public bridge entry point.

---

### Likelihood Explanation

**Likelihood: Low — requires a user mistake.**

A user must attach more NEAR than the exact MPC signing fee. This can happen if:
- The user over-estimates the fee to "be safe."
- The MPC fee changes between the time the user queries it and the time the transaction lands.
- A front-end or SDK provides an incorrect fee estimate.

This mirrors the original report's likelihood assessment exactly.

---

### Recommendation

Add an exact-match guard before forwarding, or refund any excess after the cross-contract call resolves:

**Option A (strict — preferred):** Require the attached deposit to equal the expected MPC fee exactly:
```rust
let required = self.internal_config().mpc_signing_fee; // or however it is queried
require!(
    env::attached_deposit() == NearToken::from_yoctonear(required),
    "Attached deposit must equal exact MPC signing fee"
);
```

**Option B (refund excess):** After the `sign` call resolves, return `env::attached_deposit() - actual_fee_used` to `env::predecessor_account_id()`.

---

### Proof of Concept

1. User calls `sign_btc_transaction(btc_pending_sign_id, 0, 0)` and attaches `10 NEAR` (over-estimating the MPC fee, which is e.g. `1 NEAR`).
2. `sign_promise` executes `.with_attached_deposit(env::attached_deposit())` — all `10 NEAR` are forwarded to the Chain Signatures contract.
3. The Chain Signatures contract uses `1 NEAR` for the signing operation and retains the remaining `9 NEAR` (or the entire `10 NEAR` depending on its implementation).
4. The bridge contract has no callback logic to detect or refund the surplus.
5. The user's `9 NEAR` excess is permanently lost.

The root cause is the unconditional `with_attached_deposit(env::attached_deposit())` at: [3](#0-2) 
with no corresponding refund path anywhere in `sign_btc_transaction` or its callbacks. [2](#0-1)

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> PromiseOrValue<bool> {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        btc_pending_info.assert_pending_sign();
        if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {
            if !self.check_btc_pending_info_exists(original_tx_id) {
                require!(
                    self.internal_unwrap_mut_account(&btc_pending_info.account_id.clone())
                        .btc_pending_sign_ids
                        .remove(&btc_pending_sign_id),
                    "Internal error"
                );
                self.internal_remove_btc_pending_info(&btc_pending_sign_id);
                return PromiseOrValue::Value(true);
            }
        }
        self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
            .into()
    }
