### Title
Excess NEAR Attached to `sign_btc_transaction` Is Permanently Trapped in the Bridge Contract - (File: contracts/satoshi-bridge/src/chain_signature.rs)

### Summary
`sign_btc_transaction` is `#[payable]` and forwards the caller's entire `env::attached_deposit()` to the MPC chain-signatures contract. When the MPC contract refunds any excess NEAR (above its actual signing fee) back to the bridge, the bridge has no logic to return that excess to the original caller. The surplus is permanently trapped in the bridge contract.

### Finding Description
`sign_btc_transaction` in `api/chain_signatures.rs` is marked `#[payable]` and delegates immediately to `internal_sign_btc_transaction`, which calls `sign_promise`:

```rust
pub fn sign_promise(&self, request: SignRequest) -> Promise {
    let config = self.internal_config();
    ext_chain_signatures::ext(config.chain_signatures_account_id.clone())
        .with_static_gas(GAS_FOR_SIGN_CALL)
        .with_attached_deposit(env::attached_deposit())   // ← full caller deposit forwarded
        .sign(request)
}
```

The entire `attached_deposit()` is forwarded to the MPC contract. The MPC `sign` call charges a fixed fee; any amount above that fee is refunded by the MPC contract back to its caller — which is the bridge contract, not the original user. The subsequent callback `sign_btc_transaction_callback` contains no logic to detect or return this refunded NEAR to the original caller:

```rust
#[private]
pub fn sign_btc_transaction_callback(
    &mut self,
    account_id: AccountId,
    btc_pending_sign_id: String,
    sign_index: usize,
) -> bool {
    if let Ok(result_bytes) = env::promise_result_checked(0, MAX_SIGNATURE_RESULT) {
        // ... signature processing only, no refund of excess deposit
        true
    } else {
        false
    }
}
```

There is no `>=`-vs-exact-fee guard, no refund path, and no event emitted for the trapped amount. The excess silently accumulates in the bridge's balance.

Contrast this with `request_refund` and `execute_refund`, which explicitly document that their deposits are intentional anti-spam fees and are not refunded. `sign_btc_transaction` carries no such documentation or intent — the deposit is purely meant to cover the MPC signing cost.

### Impact Explanation
Any NEAR attached beyond the MPC signing fee is permanently lost to the caller and accumulates in the bridge contract. There is no DAO withdrawal path for this trapped NEAR documented in the codebase. This constitutes a financial loss for bridge users who overpay (e.g., because the MPC fee is not surfaced in the UI, or because the fee changes between the time the user queries it and the time the transaction lands). This matches the **Medium** impact class: harmful smart-contract behavior causing user fund loss without direct theft by an attacker.

### Likelihood Explanation
`sign_btc_transaction` is a public, permissionless entrypoint callable by any NEAR account. The MPC signing fee is not enforced or validated on-chain by the bridge — users must determine the correct amount off-chain. Any user who attaches more than the exact MPC fee (a common defensive practice when fees are uncertain) will silently lose the excess. This is a realistic, recurring scenario for every withdrawal and refund that requires MPC signing.

### Recommendation
In `sign_btc_transaction_callback`, after the MPC promise resolves, compute the difference between `env::attached_deposit()` (captured before the cross-contract call) and the actual MPC fee consumed, then transfer any excess back to the original caller:

```rust
// Option 1 – exact-fee enforcement (analogous to the fix in the external report):
// Require callers to attach exactly the known MPC fee; revert otherwise.

// Option 2 – refund excess in callback:
// Store the original caller and attached amount before the XCC, then in the
// callback transfer (attached_amount - mpc_fee_consumed) back to the caller.
```

Alternatively, expose a `required_balance_for_sign` view function so callers can attach the exact amount, and add an on-chain assertion (`require!(attached == expected_fee, "InvalidFee")`).

### Proof of Concept
1. Alice initiates a withdrawal; a `BTCPendingInfo` is created for her account.
2. Alice calls `sign_btc_transaction` and attaches `2 NEAR` (she is unsure of the exact MPC fee, which is `0.5 NEAR`).
3. `sign_promise` forwards all `2 NEAR` to the MPC contract.
4. The MPC contract charges `0.5 NEAR` and refunds `1.5 NEAR` to the bridge contract.
5. `sign_btc_transaction_callback` runs, processes the signature, and returns `true` — with no refund to Alice.
6. Alice's `1.5 NEAR` is permanently trapped in the bridge contract's balance. [1](#0-0) [2](#0-1) [3](#0-2)

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> PromiseOrValue<bool> {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        btc_pending_info.assert_pending_sign();
        if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {
            if !self.check_btc_pending_info_exists(original_tx_id) {
                require!(
                    self.internal_unwrap_mut_account(&btc_pending_info.account_id.clone())
                        .btc_pending_sign_ids
                        .remove(&btc_pending_sign_id),
                    "Internal error"
                );
                self.internal_remove_btc_pending_info(&btc_pending_sign_id);
                return PromiseOrValue::Value(true);
            }
        }
        self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
            .into()
    }

    #[private]
    pub fn sign_btc_transaction_callback(
        &mut self,
        account_id: AccountId,
        btc_pending_sign_id: String,
        sign_index: usize,
    ) -> bool {
        if let Ok(result_bytes) = env::promise_result_checked(0, MAX_SIGNATURE_RESULT) {
            let signature = serde_json::from_slice::<SignatureResponse>(&result_bytes)
                .expect("Invalid signature");

            let public_key = self
                .generate_btc_public_key(
                    &self
                        .internal_unwrap_btc_pending_info(&btc_pending_sign_id)
                        .vutxos[sign_index]
                        .get_path(),
                )
                .inner;
            let btc_pending_info = self.internal_unwrap_mut_btc_pending_info(&btc_pending_sign_id);
            require!(
                btc_pending_info.signatures[sign_index].is_none(),
                "Already signed"
            );
            btc_pending_info.signatures[sign_index] = Some(signature.clone());
            btc_pending_info.last_sign_time_sec = nano_to_sec(env::block_timestamp());
            Event::BtcInputSignature {
                account_id: &account_id,
                btc_pending_id: &btc_pending_sign_id,
                sign_index,
                signature: &signature,
            }
            .emit();
            let mut psbt = btc_pending_info.get_psbt();
            psbt.save_signature(sign_index, signature, public_key);

            btc_pending_info.psbt_hex = psbt.serialize();
            if btc_pending_info.is_all_signed() {
                let tx_bytes_with_sign = psbt.extract_tx_bytes_with_sign();

                // For ZCash chains, use base64 encoding to save space (1.33x vs 2x overhead for hex)
                // ZCash transactions with Orchard bundles are larger and benefit from compact encoding
                // For Bitcoin chains, keep hex encoding for backward compatibility

                #[cfg(feature = "zcash")]
                let tx_bytes_base64 = {
                    use near_sdk::base64::{engine::general_purpose::STANDARD, Engine};
                    STANDARD.encode(&tx_bytes_with_sign)
                };

                Event::SignedBtcTransaction {
                    account_id: &account_id,
                    tx_id: btc_pending_sign_id.clone(),
                    #[cfg(not(feature = "zcash"))]
                    tx_bytes: &tx_bytes_with_sign,
                    #[cfg(feature = "zcash")]
                    tx_bytes_base64,
                }
                .emit();

                btc_pending_info.tx_bytes_with_sign = Some(tx_bytes_with_sign);
                btc_pending_info.to_pending_verify_stage();

                let is_original_tx = btc_pending_info.get_original_tx_id().is_none();
                let account = self.internal_unwrap_mut_account(&account_id);
                require!(
                    account.btc_pending_sign_ids.remove(&btc_pending_sign_id),
                    "Internal error"
                );
                if is_original_tx {
                    account
                        .btc_pending_verify_list
                        .insert(btc_pending_sign_id.clone());
                }
            }
            true
        } else {
            false
        }
    }
