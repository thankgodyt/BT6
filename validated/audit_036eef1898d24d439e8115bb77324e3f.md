### Title
Peras Certificate Validation Unconditionally Returns Success, Allowing Any Peer to Inject Arbitrary Chain-Selection Boosts - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` method unconditionally returns `Right` (success) for every inbound certificate, performing zero cryptographic or structural checks. Because this is the only deployed instance, any unprivileged peer can send a crafted `PerasCert` naming any block as the boosted target, have it accepted as "validated," and cause the receiving node to apply a `perasWeight = 15` chain-selection boost to that block. This lets a peer steer an honest node's chain selection toward a non-canonical fork without possessing any keys or stake.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub deployed as production code.**

In `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`, the sole `BlockSupportsPeras` instance (covering all `StandardHash blk` types) implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

Every certificate, regardless of content, is wrapped in `Right` and returned as `ValidatedPerasCert`. No signature, quorum, round-number, boosted-block existence, or any other check is performed.

**Attacker-controlled entry path.**

The inbound certificate handler `makePerasCertPoolWriterFromChainDB` in `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs` wires this stub directly into the live processing pipeline:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
```

`processCerts` calls `validateCert` on each inbound certificate and, when all pass (which they always do), forwards them to `addCert`:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
```

`addCert` is bound to `void . ChainDB.addPerasCertAsync chainDB`, which enqueues the certificate for `chainSelSync`. Inside `chainSelSync`, the handler for `ChainSelAddPerasCert` calls `chainSelectionForBlock` for the block named in `pcCertBoostedBlock`, applying the full `perasWeight = 15` boost to that block's chain-selection score.

**End-to-end exploit flow:**

1. Attacker connects as a normal peer and sends a `PerasCert` with `pcCertBoostedBlock` pointing to any block hash the attacker wants to boost (e.g., a block on a minority fork).
2. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{..}` unconditionally.
3. The certificate is added to the `PerasCertDB` and enqueued via `addPerasCertAsync`.
4. `chainSelSync` processes `ChainSelAddPerasCert`, retrieves the boosted block's header from the `VolatileDB`, and calls `chainSelectionForBlock` with the boosted weight.
5. The honest node's chain selection now treats the attacker-chosen block as carrying `perasWeight = 15` extra weight, potentially switching to a fork that would otherwise be rejected.

---

### Impact Explanation

**High — chain selection manipulation by an unprivileged peer.**

An attacker with no keys, no stake, and no special privileges can cause an honest node to prefer a non-canonical chain by injecting certificates that boost arbitrary blocks. The `perasWeight` boost (`15` by default) is added directly to the chain-selection score of the boosted block's chain. If the attacker's target fork is within `perasWeight` units of the canonical chain's score, the node will switch to it. This violates the Peras protocol's security assumption that only certificates backed by a quorum of honest stake can influence chain selection.

---

### Likelihood Explanation

**High.** The ObjectDiffusion miniprotocol for Peras certificates is a standard peer-to-peer channel. Any connected peer can send a `PerasCert` message. The stub is the only deployed instance; there is no fallback or override. The `TODO` comment and linked issue (`cardano-peras/issues/120`) confirm this is known incomplete work that has been shipped in the production code path. No special timing, key material, or network position is required.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real one that verifies:
- The certificate's aggregate BLS signature over the election ID and candidate block, using the aggregate public key derived from the claimed voter set.
- That the claimed voters constitute a valid quorum (total stake ≥ `perasQuorumStakeThreshold`) according to the current stake distribution.
- That the boosted block's slot satisfies `perasBlockMinSlots` and round-number constraints.
- That the certificate's round number is within the valid window (not expired per `perasCertMaxRounds`).

Until a real implementation is available, the inbound certificate handler should reject all certificates (return `Left PerasValidationErr` unconditionally) rather than accept all of them, so that the chain-selection boost cannot be triggered by unauthenticated peers.

### Proof of Concept

**Inputs:**
- Craft a `PerasCert` with `pcCertRound = <any round>` and `pcCertBoostedBlock = <point of a block on a minority fork>`.
- Send it via the ObjectDiffusion miniprotocol to a node running this codebase.

**Expected (correct) behavior:** The node rejects the certificate because no valid quorum signature is present.

**Actual behavior:**
1. `processCerts` calls `validatePerasCert mkPerasParams cert`.
2. `validatePerasCert` returns `Right ValidatedPerasCert{vpcCert = cert, vpcCertBoost = PerasWeight 15}` without inspecting `cert` at all.
3. The certificate is added to the `PerasCertDB` and `chainSelSync` triggers `chainSelectionForBlock` for the attacker-chosen block with a `+15` weight boost.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
