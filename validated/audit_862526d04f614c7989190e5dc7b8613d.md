### Title
Peras Certificate Validation Bypass via Stub `validatePerasCert` Always Returning `Right` - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance in `SupportsPeras.hs` implements `validatePerasCert` as a stub that unconditionally returns `Right` (success) for every inbound certificate, performing zero cryptographic or semantic checks. This stub is the live validation function wired into the production Peras certificate ingest path (`makePerasCertPoolWriterFromChainDB`). An unprivileged peer can therefore send a crafted `PerasCert` with an arbitrary `pcCertBoostedBlock` pointing to any block in the VolatileDB, and the node will accept it as a `ValidatedPerasCert`, store it in the `PerasCertDB`, and trigger chain selection that applies the Peras weight boost to that block — potentially causing the node to switch to an adversary-controlled fork.

---

### Finding Description

**Root cause — stub validator always succeeds:**

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the mandatory gate before any certificate is stored or acted upon. The only deployed instance is the universal one:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No BLS aggregate signature check, no committee membership check, no round-number range check, no boosted-block existence check — every certificate is unconditionally promoted to `ValidatedPerasCert`.

**Attacker-controlled entry path:**

The Peras object-diffusion mini-protocol receives `PerasCert` objects from remote peers and feeds them directly into `processCerts`, which calls the stub validator:

```haskell
(validatePerasCert mkPerasParams)
``` [2](#0-1) 

`processCerts` then passes every "validated" certificate to `ChainDB.addPerasCertAsync`: [3](#0-2) 

**Chain selection consequence:**

`addPerasCertAsync` enqueues the certificate for `chainSelSync`, which calls `chainSelectionForBlock` for the boosted block, applying the Peras weight boost (`perasWeight = 15` by default) to that block's chain fragment: [4](#0-3) 

The weight boost is defined as `PerasWeight 15` in `mkPerasParams`: [5](#0-4) 

A chain boosted by 15 units outweighs 15 honest blocks in chain selection. An adversary who can send a crafted certificate pointing to a block on a minority fork can cause an honest node to prefer that fork over the canonical chain.

**The `ValidatedPerasCert` wrapper provides false assurance:**

The type `ValidatedPerasCert` is intended to be a proof-of-validation token. Because the only live `validatePerasCert` implementation never rejects anything, the wrapper provides no actual security guarantee. All downstream code that trusts `ValidatedPerasCert` — including `PerasCertDB.addCert` and the chain-selection weight computation — is operating on unvalidated attacker-supplied data. [6](#0-5) 

---

### Impact Explanation

**Impact: High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain.**

A remote peer with no special privileges can:
1. Craft a `PerasCert` with `pcCertBoostedBlock` pointing to any block hash present in the target node's VolatileDB (observable via the ChainSync header stream).
2. Send it over the Peras object-diffusion mini-protocol.
3. The node accepts it without any cryptographic check, stores it, and re-runs chain selection with a +15 weight boost on the adversary-chosen block.
4. If the adversary's chosen block is on a minority fork, the node may switch to that fork, diverging from the honest majority chain.

This directly matches the "High" impact category: *chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.*

---

### Likelihood Explanation

**Likelihood: 3 (Medium-High)**

- The Peras object-diffusion protocol is a live network-facing mini-protocol; any connected peer can send `PerasCert` messages.
- No authentication or stake proof is required to send a certificate over the wire.
- The attacker only needs to know a valid block hash in the target's VolatileDB, which is trivially observable from the ChainSync header stream.
- The only barrier is that Peras is still under active development and may not yet be enabled on mainnet; however, the code is present in the production consensus library and the ingest path is fully wired up.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real one that performs, at minimum:
1. **BLS aggregate signature verification** over the certificate's `pcSignature` against the aggregated public keys of the claimed committee members.
2. **Committee membership and quorum check**: verify that the signers are eligible voters for the claimed round and that their combined stake meets the quorum threshold.
3. **Round-number range check**: reject certificates whose `pcCertRound` is outside the acceptable window relative to the current chain tip.
4. **Boosted-block validity**: verify that `pcCertBoostedBlock` refers to a block that satisfies the Peras block-age requirement (`perasBlockMinSlots`).

The `Ouroboros.Consensus.Peras.Cert.V1` module and `Ouroboros.Consensus.Committee.Crypto.BLS` already contain the BLS verification primitives (`verifyWithRole`, `linearizeAndVerifyVRFs`, `verifyAggregateVoteSignature`) needed to implement real validation. [7](#0-6) 

Until real validation is implemented, the `makePerasCertPoolWriterFromChainDB` ingest path should not be exposed to untrusted peers.

### Proof of Concept

**Setup:** Private testnet with Peras object-diffusion enabled. Attacker connects as a normal peer.

**Step 1 — Observe a minority-fork block hash** via ChainSync headers from the target node. Let the hash be `H_fork` at slot `S_fork`.

**Step 2 — Craft a certificate:**
```haskell
craftedCert :: PerasCert TestBlock
craftedCert = PerasCert
  { pcCertRound      = PerasRoundNo 42          -- any round not yet in DB
  , pcCertBoostedBlock = BlockPoint (SlotNo S_fork) H_fork
  }
```

**Step 3 — Send via object-diffusion.** The peer sends `[craftedCert]` as a batch to the target node's Peras cert ingest handler.

**Step 4 — Stub accepts it:**
```
validatePerasCert mkPerasParams craftedCert
-- = Right (ValidatedPerasCert { vpcCert = craftedCert, vpcCertBoost = PerasWeight 15 })
``` [8](#0-7) 

**Step 5 — Chain selection fires** with +15 weight on `H_fork`. If the fork is within `k` blocks of the tip, the node switches to the adversary-chosen fork, diverging from the canonical chain. [9](#0-8)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
