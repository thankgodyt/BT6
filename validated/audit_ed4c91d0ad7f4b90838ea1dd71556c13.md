### Title
Stub `validatePerasCert` Unconditionally Accepts Any Peer-Supplied Certificate, Enabling Unauthorized Chain Selection Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `BlockSupportsPeras` typeclass instance's `validatePerasCert` function is a stub that unconditionally accepts every inbound `PerasCert` as valid, performing no cryptographic or committee-membership checks. Because this function is the sole validation gate in the `ObjectDiffusion` inbound certificate pipeline, any unprivileged peer can inject a crafted certificate that boosts an arbitrary block, causing the receiving node to prefer a non-canonical chain.

---

### Finding Description

**Root cause — stub validation function:**

The `BlockSupportsPeras` instance (the only instance in the codebase, used for all block types) implements `validatePerasCert` as a trivial stub:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This function returns `Right` for every certificate it receives, regardless of the certificate's content, cryptographic proof, round number validity, or committee membership. No signature is verified, no eligibility is checked, and no round-number bounds are enforced.

**Attacker-controlled entry path — ObjectDiffusion inbound pipeline:**

The `processCerts` function in the `PerasCert` object pool module is the inbound handler for certificates received from peers over the `ObjectDiffusion` miniprotocol. It calls `validatePerasCert` as its sole validation step:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  -- All certs are valid => add them to the pool
  ([], validatedCerts) ->
    mapM_
      (addCert . WithArrivalTime now)
      validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [2](#0-1) 

The `validateCert` argument is wired to `validatePerasCert mkPerasParams` in both the `PerasCertDB`-backed and `ChainDB`-backed production writers: [3](#0-2) 

Because `validatePerasCert` always returns `Right`, every certificate sent by any peer passes validation and is forwarded to `addPerasCertAsync` on the `ChainDB`.

**Chain selection consequence:**

Once a `ValidatedPerasCert` is added to the `PerasCertDB`, it contributes a weight boost (`vpcCertBoost`) to the block it references via `getWeightSnapshot`. The `ChainDB` chain selection logic reads this snapshot and uses it to prefer chains containing boosted blocks: [4](#0-3) 

An attacker can therefore craft a `PerasCert` pointing to any block hash and any round number, have it accepted unconditionally, and cause the victim node to boost — and potentially switch to — a non-canonical fork.

**Secondary stub — `validatePerasVote`:**

The same instance also stubs `validatePerasVote` to skip all cryptographic signature verification, only checking stake-distribution membership: [5](#0-4) 

The `implAddVote` implementation in `PerasVoteDB/Impl.hs` carries the same TODO: [6](#0-5) 

This means a peer can forge votes for any voter ID present in the stake distribution, potentially triggering false quorum and causing the node to forge and accept a certificate for an attacker-chosen block.

---

### Impact Explanation

**Severity: High — Chain selection manipulation.**

An unprivileged peer connected via the `ObjectDiffusion` miniprotocol can inject a `PerasCert` that boosts an arbitrary block with the full `perasWeight` boost. The receiving node's chain selection will treat the attacker-chosen fork as heavier than the honest canonical chain, causing the node to switch to a non-canonical chain. This violates the core Peras safety guarantee that only legitimately certified blocks receive weight boosts, and can cause honest nodes to diverge from the canonical chain without any stake majority or key compromise.

---

### Likelihood Explanation

**High.** The `ObjectDiffusion` miniprotocol is a standard peer-to-peer protocol reachable by any connected peer. No privileged access, no keys, and no stake are required. The attacker only needs to:
1. Connect to a node as a peer.
2. Send a `PerasCert` with a crafted `PerasRoundNo` and `Point blk` targeting any block.

The stub is the only instance of `BlockSupportsPeras` in the codebase and is used unconditionally in the production `makePerasCertPoolWriterFromChainDB` path.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real cryptographic validation function that:
1. Verifies the aggregate BLS signature over the certificate against the committee's public keys.
2. Checks that the signers constitute a valid quorum of the committee for the given round.
3. Validates the round number against the current epoch's Peras parameters (e.g., round is not in the future, not already superseded).
4. Verifies that the boosted block exists and is within the valid slot range for the round.

Until the full Peras cryptographic plumbing is in place (tracked in issue #120 and #73), the `ObjectDiffusion` inbound handler for certificates should either be disabled or should reject all inbound certificates from untrusted peers rather than accepting them unconditionally.

The same applies to `validatePerasVote`: it must verify the cryptographic signature of each vote before accepting it, not merely check stake-distribution membership.

### Proof of Concept

**Attacker preconditions:** A peer connection to the target node (no keys, no stake required).

**Steps:**

1. Connect to the target node as a peer via the `ObjectDiffusion` miniprotocol for Peras certificates.
2. Construct a `PerasCert` with:
   - `pcCertRound` = any `PerasRoundNo` not yet in the node's `PerasCertDB`
   - `pcCertBoostedBlock` = the `Point` of any block on a fork the attacker wants the node to prefer
3. Send the certificate via the `ObjectDiffusion` inbound protocol.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{..}` unconditionally. [7](#0-6) 
5. The certificate is added to the `PerasCertDB` via `addPerasCertAsync`, updating the `PerasWeightSnapshot`.
6. Chain selection re-runs and now treats the attacker-chosen block as boosted by `perasWeight`, potentially switching the node's selection to the attacker's fork.

**Expected outcome:** The node's `getCurrentChain` reflects the attacker-boosted fork rather than the honest canonical chain, with no cryptographic proof of legitimate committee certification.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch

    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
