Audit Report

## Title
Decimal Normalization Floor Division Produces Zero in `sign_transfer`, Permanently Freezing User Funds - (File: `near/omni-bridge/src/lib.rs`)

## Summary

`init_transfer` locks user tokens after only checking `fee < amount`, without verifying that `normalize_amount(amount - fee, decimals) > 0`. For tokens with a large decimal gap between origin and destination chains, a net transfer amount smaller than the divisor is silently truncated to zero by floor division inside `sign_transfer`, which then unconditionally panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`. Because no cancel path exists for `pending_transfers`, the locked tokens are permanently frozen.

## Finding Description

`init_transfer` stores the transfer and locks/burns user tokens after a single guard:

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
``` [1](#0-0) 

This guard does not check whether the net amount survives decimal normalization. Later, `sign_transfer` normalizes the net amount with floor division:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message
        .amount_without_fee()
        .near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
``` [2](#0-1) 

`normalize_amount` performs integer floor division:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [3](#0-2) 

`amount_without_fee` is a simple checked subtraction:

```rust
pub fn amount_without_fee(&self) -> Option<u128> {
    self.amount.0.checked_sub(self.fee.fee.0)
}
``` [4](#0-3) 

If `amount_without_fee < 10^(origin_decimals - decimals)`, the floor division yields `0`, and `sign_transfer` panics unconditionally. The stored `TransferMessage` is immutable after creation, so every subsequent call to `sign_transfer` for that transfer ID produces the same panic. The `sign_transfer_callback` only removes the transfer from `pending_transfers` when the MPC signing succeeds and fee is zero — a state that is never reached because `sign_transfer` panics before the MPC call is made. [5](#0-4) 

No `cancel_transfer` function exists in the contract. The `normalize_amount` comment explicitly acknowledges that "When fee = 0, dust stays locked/burned," but this refers to sub-unit remainders, not the case where the entire `amount_without_fee` normalizes to zero. [6](#0-5) 

## Impact Explanation

This constitutes **permanent freezing of bridged funds**. Tokens are locked or burned at `init_transfer` time inside `init_transfer_internal`. The transfer is stored in `pending_transfers` with no recovery path: `sign_transfer` always reverts for this transfer ID, and no `cancel_transfer` function exists to reclaim the locked tokens. This matches the allowed critical impact: "permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet, Bitcoin, Zcash, or Wormhole-routed flows."

## Likelihood Explanation

The scenario is reachable by any unprivileged bridge user via the standard `ft_transfer_call` → `ft_on_transfer` → `init_transfer` path. It is triggered when a token is registered with a large decimal gap (e.g., `origin_decimals = 24`, `decimals = 6`, divisor = `10^18`) — a realistic configuration for NEAR-native tokens bridged to EVM chains — and the user's `amount - fee` is less than the divisor. The `init_transfer` guard only checks `fee < amount`, so the transaction is accepted and tokens are locked before the normalization check in `sign_transfer` is ever reached. While the absolute token value involved is small (sub-unit amounts), the permanent loss is real and the path is fully permissionless.

## Recommendation

Add a pre-flight normalization check inside `init_transfer` (or `init_transfer_internal`) before locking tokens:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

This requires looking up the destination token's `Decimals` at `init_transfer` time, which is already done in `sign_transfer`. Alternatively, add a `cancel_transfer` function that allows the original sender to reclaim locked tokens for transfers that can never be signed.

## Proof of Concept

1. Register a token with `origin_decimals = 24`, `decimals = 6` (divisor = `10^18`).
2. Alice calls `ft_transfer_call` with `amount = 2` and `fee = 1` targeting an EVM recipient.
3. `init_transfer` passes the guard (`1 < 2`). Alice's 2 tokens are locked in the bridge. The transfer is stored in `pending_transfers`.
4. A relayer calls `sign_transfer` for Alice's transfer.
5. `normalize_amount(1, {decimals: 6, origin_decimals: 24})` = `1 / 10^18` = `0`.
6. `require!(0 > 0, ...)` panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.
7. Every future call to `sign_transfer` for this transfer ID produces the same panic.
8. Alice's 2 tokens remain locked in the bridge with no recovery path.
