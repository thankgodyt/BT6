### Title
Passive Management Constraint Off-by-One at Boundary Values Allows Policy Bypass — (`contracts/satoshi-bridge/src/psbt.rs`)

### Summary

`check_withdraw_psbt_valid` uses strict `<` / `>` comparisons for passive UTXO management limits. When `utxo_num` equals exactly `passive_management_lower_limit` or `passive_management_upper_limit`, neither branch fires and no `input_num`/`change_num` constraint is applied, allowing a withdrawal that violates the passive management policy to be accepted.

### Finding Description

In `check_withdraw_psbt_valid`:

```rust
if utxo_num < config.passive_management_lower_limit {
    require!(input_num < change_num, "require input_num < change_num");
} else if utxo_num > config.passive_management_upper_limit {
    require!(input_num > change_num, "require input_num > change_num");
}
``` [1](#0-0) 

Both conditions are strict inequalities. When `utxo_num == passive_management_lower_limit` or `utxo_num == passive_management_upper_limit`, the `else if` chain falls through with no constraint applied.

`utxo_num` is computed as:

```rust
let utxo_num = self.data().utxos.len() + vutxos_len;
``` [2](#0-1) 

`generate_vutxos` removes the spent UTXOs from `self.data().utxos` before this line executes, so `utxo_num` always equals the total UTXO count before the transaction regardless of how many inputs the attacker selects. The attacker cannot manipulate `utxo_num` directly, but can wait for (or observe) the natural state where the count is exactly at a boundary.

The call path from the public entrypoint is:

`ft_on_transfer` (token_receiver.rs:23) → `ft_on_transfer_withdraw_chain_specific` → `create_btc_pending_info` (token_receiver.rs:71) → `check_withdraw_psbt_valid` (psbt.rs:10) [3](#0-2) 

No privilege is required; any holder of nBTC can call `ft_transfer_call` with a `Withdraw` message.

### Impact Explanation

When `utxo_num == passive_management_lower_limit`, the policy intent is to force `input_num < change_num` so that the withdrawal creates more UTXOs than it consumes, keeping the pool healthy. With the bypass, an attacker can submit `input_num > change_num`, consuming more UTXOs than created and pushing the pool below the lower limit. The symmetric case applies at the upper limit. This degrades UTXO pool health and can require operator intervention to restore it. There is no direct fund theft.

This falls under: **Low — Publicly reachable invariant-violation in production bridge/token paths without direct theft.**

### Likelihood Explanation

The attacker cannot force `utxo_num` to a specific value, but the boundary is a natural state reached during normal operation (every deposit/withdrawal changes the count by small increments). The window is narrow (a single exact count value) but real and observable on-chain. Likelihood is low-to-medium depending on how close the configured limits are to typical operating UTXO counts.

### Recommendation

Change the strict inequalities to `<=` / `>=` so the boundary values are covered:

```rust
if utxo_num <= config.passive_management_lower_limit {
    require!(input_num < change_num, "require input_num < change_num");
} else if utxo_num >= config.passive_management_upper_limit {
    require!(input_num > change_num, "require input_num > change_num");
}
``` [1](#0-0) 

This matches the documented intent in `Config`:

> "When the number of UTXOs in the protocol is **less than** this configuration, passive UTXO management will be triggered" [4](#0-3) 

The boundary value itself should trigger the constraint, not be exempt from it.

### Proof of Concept

1. Configure `passive_management_lower_limit = N` (e.g., 5).
2. Arrange the bridge UTXO pool to contain exactly `N` UTXOs.
3. Call `ft_transfer_call` on the nBTC contract with a `Withdraw` message whose PSBT has `input_num = 2`, `change_num = 1` (i.e., `input_num > change_num`).
4. `utxo_num = N - 2 + 2 = N == passive_management_lower_limit` — neither branch in lines 56–60 fires.
5. The withdrawal is accepted; the UTXO pool drops to `N - 1`, below the lower limit, with no constraint enforced.
6. Contrast: with `utxo_num = N - 1` (one fewer UTXO), the `<` branch fires and the same PSBT is rejected with `"require input_num < change_num"`.
