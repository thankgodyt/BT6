### Title
Peras Weight Snapshot Not Consulted in Forecast-Horizon Disconnect Check, Causing Incorrect Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

When the ChainSync client receives a header beyond the forecast horizon, it must decide whether to wait (if the candidate chain is still preferable) or disconnect (`CandidateTooSparse`). The comparison is performed with a hardcoded `emptyPerasWeightSnapshot`, ignoring all Peras certificate boosts. A candidate chain that is shorter by block count but heavier by Peras weight is therefore incorrectly evaluated as non-preferable, causing the node to disconnect from a peer serving the canonical (heaviest) chain and remain on a lighter, non-canonical chain.

---

### Finding Description

The `checkPreferTheirsOverOurs` helper inside `checkTime` in the ChainSync client is called whenever a header arrives beyond the current forecast horizon and the node must decide whether to keep waiting or disconnect:

```haskell
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← always zero Peras weight
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse ...
``` [1](#0-0) 

`preferAnchoredCandidate` dispatches on whether the weight snapshot is empty. When it is empty (as hardcoded here), it falls back to a pure block-count comparison:

```haskell
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      -- pure block-count path
      ...
  | otherwise =
      -- Peras-weighted path
      ...
``` [2](#0-1) 

The actual live Peras weight snapshot is available via `getPerasWeightSnapshot` on the `ChainDB` API and is updated every time a new certificate is added: [3](#0-2) 

But `checkPreferTheirsOverOurs` never reads it. The `emptyPerasWeightSnapshot` constant is defined as a permanently empty map: [4](#0-3) 

The analog to the Fei Protocol bug is exact: just as `getTimeWeight()` returns 0 when `timeWeightInfo.active` is false (because the active flag is never set by passive price movement), `preferAnchoredCandidate` here returns a weight of 0 for all Peras boosts because the snapshot is always empty — regardless of how many certificates have actually been received and stored.

---

### Impact Explanation

Under Peras, the canonical chain is the one with the highest **total weight** = block count + sum of Peras certificate boosts. A candidate chain that is 2–3 blocks shorter than the local selection but carries one or more Peras-boosted blocks can easily be heavier in total weight.

When such a candidate's tip falls beyond the forecast horizon (possible whenever the intersection is far back and the candidate has many empty slots), `checkPreferTheirsOverOurs` evaluates it using only block count. The candidate appears non-preferable, the node throws `CandidateTooSparse`, and disconnects from the peer serving the canonical chain. The node remains on its current, lighter chain — a non-canonical chain under Peras chain-selection rules.

This is a **chain-selection bug**: an unprivileged peer serving the honest canonical chain causes an honest node to prefer a non-canonical, less-secure chain, violating the intended Peras security assumptions.

**Impact class:** High — chain selection bug that lets an unprivileged peer (even an honest one) cause an honest node to prefer a non-canonical chain beyond the intended security assumptions.

---

### Likelihood Explanation

Peras is currently disabled by default (`emptyPerasWeightSnapshot` is the default in all non-Peras paths, and the CHANGELOG notes "if Peras is disabled (which is the default), there is no observable difference"). However:

- The code path is unconditionally compiled into production binaries.
- The TODO comment at line 1841–1842 explicitly acknowledges the problem and references an open issue (`https://github.com/tweag/cardano-peras/issues/64`), confirming the developers are aware but have not yet fixed it.
- Once Peras is enabled on any network (testnet or mainnet), any node whose candidate chain has a Peras-boosted block beyond the forecast horizon will trigger this path.
- No special attacker capability is required: an honest peer serving the canonical chain is sufficient.

**Likelihood:** Medium (dormant until Peras activation; immediately exploitable thereafter without any attacker privilege).

---

### Recommendation

Replace the hardcoded `emptyPerasWeightSnapshot` with the live snapshot obtained from the `ChainDB`:

```haskell
-- In checkTime / readLedgerStateHelper, obtain the live snapshot:
weights <- forgetFingerprint <$> getPerasWeightSnapshot chainDbView
-- Then pass it to preferAnchoredCandidate:
preferAnchoredCandidate (configBlock cfg) weights ourFrag theirFrag
```

Alternatively, as the TODO comment suggests, remove `checkPreferTheirsOverOurs` entirely (the Genesis Density Disconnect logic already handles the equivalent safety property in a Peras-aware way). [5](#0-4)

### Proof of Concept

**Setup (private testnet, Peras enabled):**

1. Node A holds chain C₁: intersection at slot S, then 10 blocks up to slot S+200. No Peras certificates. Total weight = 10.

2. Peer B holds chain C₂: intersection at slot S, then 8 blocks up to slot S+400. One block at slot S+100 carries a Peras certificate boost of weight 5. Total weight = 8 + 5 = 13.

3. The forecast horizon from the intersection is, say, S+300 (one stability window). Peer B's tip at S+400 is beyond the horizon.

**Trigger:**

Peer B sends the header at slot S+400 to Node A via ChainSync. Node A cannot yet forecast a `LedgerView` for slot S+400, so `projectLedgerView` returns `Nothing`. [6](#0-5) 

`readLedgerStateHelper` calls `checkPreferTheirsOverOurs`. [7](#0-6) 

**Evaluation (buggy path):**

`preferAnchoredCandidate cfg emptyPerasWeightSnapshot ourFrag theirFrag` compares block counts: 10 (ours) vs 8 (theirs). `ShouldNotSwitch` is returned. `checkPreferTheirsOverOurs` throws `CandidateTooSparse`.

**Result:**

Node A disconnects from Peer B. Node A remains on C₁ (weight 10). The canonical chain C₂ (weight 13) is never adopted. Node A is on a non-canonical chain for the duration of the Peras boost's validity.

preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"
        Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
          case preferCandidate
            (projectChainOrderConfig cfg)
            (weightedSelectView cfg weights oursSuffix)
            (weightedSelectView cfg weights candSuffix) of
            ShouldSwitch r -> ShouldSwitch (Left r)
            ShouldNotSwitch o -> ShouldNotSwitch o
