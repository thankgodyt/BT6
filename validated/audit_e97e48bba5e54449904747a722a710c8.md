### Title
Permissionless `request_refund` Allows Attacker to Redirect BTC Refund to Attacker-Controlled Address - (File: contracts/satoshi-bridge/src/api/bridge.rs, contracts/satoshi-bridge/src/refund.rs)

### Summary
`request_refund` is callable by any unprivileged NEAR account. When the original `deposit_msg.refund_address` field is `None`, the caller freely supplies any BTC address as the refund destination. An attacker who observes a pending, unfinalized deposit can front-run the legitimate depositor, register a refund request pointing to the attacker's own BTC address, and — if the DAO fails to reject within the 14-day `unsafe_refund_timelock_sec` — trigger `execute_refund` to receive the victim's BTC.

### Finding Description

`request_refund` carries no `#[trusted_relayer]` attribute on the function itself and no caller-identity check:

```rust
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn request_refund(
    &mut self,
    deposit_msg: DepositMsg,
    refund_address: String,
    tx_bytes: Base64VecU8,
    vout: usize,
    proof: TxInclusionProof,
    gas_fee: Option<U128>,
) -> Promise {
``` [1](#0-0) 

Inside `internal_request_refund`, the only guard on `refund_address` is a consistency check against `deposit_msg.refund_address`. When that field is `None` — which is the common case for standard deposits — the caller's supplied address is accepted verbatim:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [2](#0-1) 

The accepted `refund_address` is stored directly in the `RefundRequest` and later used verbatim by `execute_refund` to build the BTC output:

```rust
let refund_request = RefundRequest {
    ...
    refund_address,
    ...
};
self.data_mut()
    .refund_requests
    .insert(utxo_storage_key, refund_request.into());
``` [3](#0-2) 

A duplicate-request guard prevents a second `request_refund` for the same UTXO:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [4](#0-3) 

So whoever submits first wins. The legitimate depositor cannot overwrite an attacker's already-registered request.

The `deposit_msg` used to derive the deposit address is emitted publicly in `get_user_deposit_address`:

```rust
Event::LogDepositAddress {
    deposit_msg,
    path,
    deposit_address: deposit_address.clone(),
}
.emit();
``` [5](#0-4) 

The BTC transaction bytes and Merkle proof are also publicly observable on the Bitcoin chain. An attacker therefore has all inputs needed to construct a valid `request_refund` call.

The only post-submission defense is DAO/Operator rejection within `unsafe_refund_timelock_sec` (default 14 days):

```rust
pub const DEFAULT_UNSAFE_REFUND_TIMELOCK_SEC: u64 = 14 * 24 * 3600;
``` [6](#0-5) 

```rust
} else {
    // Refund address supplied by caller of `request_refund`: longer
    // timelock to give DAO/Operator time to reject suspicious requests.
    config.unsafe_refund_timelock_sec
}

### Impact Explanation
If the DAO does not reject within 14 days, `execute_refund` is callable by anyone and sends the deposit UTXO — the full BTC amount minus gas fee — to the attacker's address. The legitimate depositor permanently loses their BTC. This constitutes a significant, direct theft of user funds.

### Likelihood Explanation
All information required to construct the attack (deposit_msg, tx_bytes, vout, Merkle proof) is publicly observable on NEAR event logs and the Bitcoin chain. The attacker only needs to submit `request_refund` before the legitimate user does, which is straightforward since most users are unaware of the refund mechanism. The 14-day window is a meaningful mitigation but relies entirely on continuous DAO vigilance; a single missed alert, DAO key unavailability, or governance delay is sufficient for the attack to succeed. Deposits with `deposit_msg.refund_address == None` — the default for standard deposits — are universally affected.

### Recommendation
1. **Require pre-authorized refund address**: Reject `request_refund` calls where `deposit_msg.refund_address` is `None`. Force users to embed their BTC refund address in the deposit message at deposit time, making the address immutable and attacker-proof.
2. **Alternatively, restrict caller**: Require `env::predecessor_account_id()` to equal `deposit_msg.recipient_id` (the intended nBTC recipient), so only the original depositor can file a refund request for their own UTXO.
3. **As defense-in-depth**: Emit a prominent on-chain event immediately when a refund request is filed so monitoring systems can alert the DAO promptly.

### Proof of Concept
1. Alice deposits 0.5 BTC using a `deposit_msg` with `refund_address: None` and `recipient_id: alice.near`. The bridge emits `LogDepositAddress` with the full `deposit_msg`.
2. The relayer never finalizes the deposit (e.g., amount below minimum, or relayer outage).
3. Attacker Bob observes the `LogDepositAddress` event and the Bitcoin transaction on-chain.
4. Bob calls `request_refund(deposit_msg, "bc1q_bob_address", tx_bytes, vout, proof, None)` with sufficient NEAR attached. The call succeeds because `deposit_msg.refund_address` is `None` — no ownership check is performed.
5. Alice attempts to call `request_refund` with her own address — it panics: `"Refund request already exists for this UTXO"`.
6. The DAO does not reject within 14 days.
7. Bob calls `execute_refund(utxo_storage_key, None)`. The bridge builds a BTC transaction paying `bc1q_bob_address` and signs it via MPC.
8. Bob's address receives Alice's 0.5 BTC minus gas fee.
