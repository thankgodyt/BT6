### Title
Peras Certificate Validation Bypass Allows Unprivileged Peer to Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary
The default `validatePerasCert` instance unconditionally returns `Right` (success) for every inbound Peras certificate, bypassing all cryptographic and structural checks. When Peras is enabled, any peer can inject arbitrary fake certificates into the `PerasCertDB`, causing chain selection to apply a weight boost to non-canonical blocks and potentially forcing an honest node to switch to an adversary-controlled fork.

### Finding Description
`BlockSupportsPeras` defines `validatePerasCert` as the mandatory gate before a certificate is stored and acted upon. The only instance in the codebase — the degenerate default — always succeeds unconditionally:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

`processCerts` in `ObjectPool/PerasCert.hs` calls this function for every inbound certificate received from a peer:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

Because `validatePerasCert` always returns `Right`, the `partitionEithers` check in `processCerts` never produces errors, and every certificate is wrapped in `ValidatedPerasCert` and forwarded to `addCert`/`addPerasCertAsync`. The `ValidatedPerasCert` wrapper is the type-level proof that a certificate has been validated; here that proof is manufactured without any actual check. [3](#0-2) 

`chainSelSync` in `ChainSel.hs` then adds the certificate to the `PerasCertDB` and triggers chain selection for the boosted block. The Peras weight boost is applied to the boosted block's chain fragment, potentially making it preferred over the honest chain. [4](#0-3) 

The `ValidatedPerasCert` type is supposed to be the type-level guarantee that a certificate passed validation before being stored. The bypass here is structurally identical to the Seaport analog: one code path (inbound peer certificates) skips the validation step that the type contract requires, while the type system is satisfied by unconditionally constructing the "validated" wrapper.

### Impact Explanation
When Peras is enabled, an unprivileged peer can send a crafted certificate boosting any block in the VolatileDB. Because no aggregate BLS signature check, committee membership check, quorum threshold check, or round-number check is performed, the certificate is indistinguishable from a legitimate one. Chain selection applies the full Peras weight boost to the adversary's chosen block, potentially making a non-canonical fork preferred over the honest chain and causing the node to roll back and adopt the adversary-controlled chain. This is a direct bypass of Peras certificate checks enabling unauthorized certificate acceptance and chain-selection manipulation, matching the "Critical — bypass of Peras voting or certificate checks" impact class.

### Likelihood Explanation
Peras is disabled by default (the CHANGELOG explicitly states "if Peras is disabled (which is the default), there is no observable difference"). However, Peras is under active development and is intended to be enabled in production. When enabled, any peer that can establish a connection can exploit this bypass without any special privileges, keys, or stake. The `makePerasCertPoolWriterFromChainDB` function is the live production code path for inbound peer certificates. [5](#0-4) 

### Recommendation
Implement actual cryptographic validation in `validatePerasCert` before enabling Peras in production. The validation must check at minimum: (1) the certificate's aggregate BLS signature against the committee's aggregate verification key, (2) committee membership and quorum threshold, and (3) round number and boosted block point consistency. The existing `PerasCert.V1` module already defines the concrete certificate structure with `pcSignature :: AggregateVoteSignature PerasBLSCrypto` and `verifyAggregateVoteSignature` in `Peras/Crypto/BLS.hs`, which should be wired into `validatePerasCert`. [6](#0-5) [7](#0-6) 

### Proof of Concept
1. Enable Peras on a node (set the feature flag).
2. Connect a malicious peer to the node via the standard node-to-node protocol.
3. The malicious peer sends a crafted `PerasCert` via the object diffusion protocol, with `pcCertBoostedBlock` pointing to a block on a non-canonical fork.
4. `processCerts` calls `validatePerasCert mkPerasParams` — this always returns `Right ValidatedPerasCert{...}` regardless of the certificate's contents.
5. The certificate is forwarded to `addPerasCertAsync`, which enqueues a `ChainSelAddPerasCert` event.
6. `chainSelSync` adds the certificate to the `PerasCertDB` and calls `chainSelectionForBlock` for the boosted block.
7. The Peras weight boost (`perasWeight params`) is applied to the non-canonical fork's fragment, making it heavier than the honest chain.
8. The node switches to the adversary-controlled fork.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
