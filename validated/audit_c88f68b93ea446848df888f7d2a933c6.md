### Title
Missing BTC Address Validation in `request_refund_callback` Enables Attacker-Triggered Stuck Refund State - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
The `request_refund_callback` function stores a caller-supplied `refund_address` string into persistent `RefundRequest` storage without first validating that it is a parseable BTC/ZEC address. The address is only parsed later, inside `build_refund_output`, via `.expect("Invalid refund address")`. If the stored address is unparseable, every subsequent call to `execute_refund` for that request panics and rolls back, leaving the `RefundRequest` permanently in storage. Because the duplicate-request guard blocks any second `request_refund` for the same UTXO, the UTXO's refund path is stuck until a privileged DAO/RefundOperator manually rejects the request.

### Finding Description

`request_refund_callback` (the cross-contract callback that finalises a refund submission) stores the raw `refund_address` string directly into a `RefundRequest` with no format check: [1](#0-0) 

The only guard that could constrain the address is the optional match against `deposit_msg.refund_address`: [2](#0-1) 

When `deposit_msg.refund_address` is `None` (the common case — it is an optional field), the caller may supply any arbitrary string as `refund_address` and it is accepted without validation.

The address is only parsed later in `build_refund_output`: [3](#0-2) 

Both `.expect("Invalid refund address")` and `.expect("Invalid refund script_pubkey")` are hard panics. In NEAR, a panic aborts the call and rolls back all state changes of that call, but the `RefundRequest` was written in the earlier `request_refund_callback` call and is not rolled back. The stuck request then blocks any new `request_refund` for the same UTXO: [4](#0-3) 

### Impact Explanation

The UTXO's refund path is permanently blocked until a DAO or RefundOperator calls `internal_reject_refund`. This constitutes attacker-triggered temporary locking of bridged funds requiring operator intervention, matching the Medium impact class. The depositor cannot recover their BTC/ZEC through the normal refund flow without privileged action.

### Likelihood Explanation

`request_refund` is a public, permissionless entry point — any account that can supply a valid `TxInclusionProof` (all data is publicly available on-chain) and the required storage deposit can call it for any unverified UTXO. An attacker can monitor the Bitcoin/Zcash mempool or NEAR events for new deposits, then race to submit a `request_refund` with a syntactically invalid `refund_address` (e.g., an empty string or a random byte sequence) before the legitimate depositor does. No special privileges are required.

### Recommendation

Validate `refund_address` as a parseable address for the configured chain at the point it is first accepted — either in `internal_request_refund` before the light-client cross-contract call, or at the top of `request_refund_callback` before writing to storage:

```rust
// In request_refund_callback, before inserting the RefundRequest:
let config = self.internal_config();
crate::network::Address::parse(&refund_address, config.chain.clone())
    .unwrap_or_else(|_| env::panic_str("Invalid refund_address"));
```

This mirrors the fix recommended in H-01: validate the critical address parameter at the entry point, before any state is written.

### Proof of Concept

1. Depositor sends BTC to a bridge deposit address derived from a `DepositMsg` with `refund_address: None`.
2. The deposit is not (yet) verified on NEAR.
3. Attacker observes the deposit UTXO on-chain and constructs a valid `TxInclusionProof`.
4. Attacker calls `request_refund(deposit_msg, refund_address="INVALID", tx_bytes, vout, proof, gas_fee)` with a non-parseable `refund_address` string, attaching the required storage deposit.
5. Light-client verification succeeds (the proof is valid). `request_refund_callback` runs, stores a `RefundRequest` with `refund_address = "INVALID"`, and returns `true`.
6. Depositor attempts `request_refund` — rejected: `"Refund request already exists for this UTXO"`.
7. Anyone calls `execute_refund(utxo_storage_key, ...)` — `build_refund_output` panics at `Address::parse("INVALID", ...).expect(...)`. State rolls back; `RefundRequest` remains.
8. The UTXO refund is stuck. The depositor cannot recover funds until DAO calls `internal_reject_refund`, after which the depositor must re-submit with a valid address. [5](#0-4)

    #[private]
    pub fn request_refund_callback(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        gas_fee: Option<u128>,
    ) -> bool {
        let result_bytes = env::promise_result_checked(0, MAX_BOOL_RESULT)
            .expect("Call verify_transaction_inclusion failed");
        let is_valid = serde_json::from_slice::<bool>(&result_bytes)
            .expect("verify_transaction_inclusion return not bool");
        require!(is_valid, "verify_transaction_inclusion return false");

        let config = self.internal_config();
        let transaction = crate::WrappedTransaction::decode(&tx_bytes.0, &config.chain)
            .expect("Deserialization tx_bytes failed");
        let output = &transaction.output()[vout];

        // Verify that the output script matches the deposit address derived from deposit_msg
        let path = get_deposit_path(&deposit_msg);
        let deposit_address = self.generate_utxo_chain_address(&path);
        let deposit_script_pubkey = deposit_address
            .script_pubkey()
            .expect("Invalid deposit address");
        require!(
            deposit_script_pubkey == output.script_pubkey,
            "Output script_pubkey does not match deposit address"
        );

        let amount = u128::from(output.value.to_sat());
        let tx_id = transaction.compute_txid().to_string();
        let utxo_storage_key = generate_utxo_storage_key(
            tx_id,
            u32::try_from(vout).unwrap_or_else(|_| env::panic_str("vout overflow")),
        );

        // Double-check not finalized (could have been verified between request and callback)
        require!(
            !self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key),
            "UTXO already verified via deposit"
        );

        // Double-check no duplicate (another request_refund could have landed between our check and callback)
        require!(
            !self.data().refund_requests.contains_key(&utxo_storage_key),
            "Refund request already exists for this UTXO"
        );

        let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
        require!(
            resolved_gas_fee < amount,
            "Gas fee must be less than deposit amount"
        );

        Event::RefundRequested {
            deposit_msg: deposit_msg.clone(),
            utxo_storage_key: utxo_storage_key.clone(),
            amount: amount.into(),
            refund_address: refund_address.clone(),
            gas_fee: resolved_gas_fee.into(),
        }
        .emit();

        let refund_request = RefundRequest {
            deposit_msg_json: serde_json::to_string(&deposit_msg).unwrap(),
            utxo_storage_key: utxo_storage_key.clone(),
            tx_bytes,
            vout,
            amount,
            refund_address,
            gas_fee: resolved_gas_fee,
            created_at_sec: nano_to_sec(env::block_timestamp()),
            executed: false,
        };

        self.data_mut()
            .refund_requests
            .insert(utxo_storage_key, refund_request.into());

        true
    }
