### Title
Peras Quorum Check Compares Unnormalized Vote Stake Against Relative Threshold, Enabling Unauthorized Certificate Forging - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

`stakeAboveThreshold` directly compares accumulated `PerasVoteStake` values (sourced from the ledger stake distribution without normalization) against a relative quorum threshold (`perasQuorumStakeThreshold`). This is a direct analog to the reported token-decimal normalization bug: values of different scales are compared as if they share the same unit, producing incorrect quorum determinations. The code itself documents the missing normalization as an unresolved TODO.

### Finding Description

`stakeAboveThreshold` at line 162 performs:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake     = unPerasVoteStake voteStake
  quorumThreshold = unPerasQuorumStakeThreshold (perasQuorumStakeThreshold params)
  safetyMargin    = unPerasQuorumStakeThresholdSafetyMargin (...)
``` [1](#0-0) 

The code comment at lines 155–161 explicitly acknowledges the normalization gap:

> "this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … Under the current implementation of `PerasParams`, this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [2](#0-1) 

The `PerasVoteStake` for each vote is obtained by `lookupPerasVoteStake`, which performs a raw map lookup with no normalization:

```haskell
lookupPerasVoteStake vote distr =
  Map.lookup (pvVoteVoterId vote) (unPerasVoteStakeDistr distr)
``` [3](#0-2) 

The quorum threshold (`perasQuorumStakeThreshold`) is typed as a `Rational` and documented as a relative value (fraction of total committee stake): [4](#0-3) 

The `PerasVoteStakeDistr` is populated from the ledger's absolute stake distribution. The comment on `PerasVoteStake` itself states: "there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee." [2](#0-1) 

The full peer-reachable call chain is:

1. Peer sends a `PerasVote` message via the object-diffusion mini-protocol.
2. `processVotes` in `PerasVote.hs` calls `validatePerasVote` with the local `PerasVoteStakeDistr`. [5](#0-4) 

3. `validatePerasVote` looks up the voter's raw stake from the distribution (no normalization applied).
4. The validated vote is accumulated in `updateTargetVoteTally`, adding `vpvVoteStake` directly to `ptvtTotalStake`. [6](#0-5) 

5. `updateCandidateVoteState` calls `votesReachQuorum`, which calls `stakeAboveThreshold` on the unnormalized accumulated stake. [7](#0-6) 

6. `votesReachQuorum` calls `stakeAboveThreshold cfg totalVoteStake` where `totalVoteStake` is the sum of raw (potentially absolute) `PerasVoteStake` values. [8](#0-7) 

**Concrete mismatch:** If `PerasVoteStakeDistr` is populated with absolute lovelace amounts (e.g., a pool with 1,000,000,000 lovelace), while `perasQuorumStakeThreshold` is a relative value such as `3 % 4` (0.75), then `1000000000 >= 0.75` is trivially true. A single vote from any pool with non-trivial absolute stake immediately satisfies the quorum, causing the node to forge a Peras certificate for the peer's chosen block.

### Impact Explanation

An unprivileged peer sends a single crafted `PerasVote` message identifying any pool with non-trivial absolute stake. The receiving node looks up that pool's absolute stake from the ledger distribution, compares it against the relative quorum threshold (which is orders of magnitude smaller), and immediately forges a `ValidatedPerasCert` for the peer's chosen block. This certificate is stored in the `PerasVoteDB` and applied as a chain-weight boost (`perasWeight`) to the targeted block, causing honest nodes running Peras chain selection to prefer the adversarially boosted chain over the canonical one. This constitutes a bypass of Peras certificate/vote verification enabling unauthorized certificate acceptance and chain selection manipulation. [9](#0-8) 

### Likelihood Explanation

The `PerasVoteStakeDistr` is naturally populated from the ledger's absolute stake distribution. No normalization step exists anywhere in the production code path between ledger stake and the quorum comparison. The code explicitly documents the missing normalization as an unresolved open question. Any deployment that reads absolute lovelace values from the ledger into `PerasVoteStakeDistr` — which is the natural and expected implementation — will be vulnerable. The entry path requires only sending a valid `PerasVote` message over the object-diffusion mini-protocol, which is accessible to any peer.

### Recommendation

`stakeAboveThreshold` must normalize `PerasVoteStake` before comparison. Either:

1. Accept the total stake distribution as an additional parameter and divide each voter's absolute stake by the total to obtain a relative value before accumulating and comparing, or
2. Express `perasQuorumStakeThreshold` in absolute terms consistent with the unit used in `PerasVoteStakeDistr`, and enforce this invariant at construction time with a newtype or phantom type distinguishing absolute from relative stake.

The `PerasVoteStake` type should carry a phantom tag (e.g., `Absolute` vs `Relative`) to make unit mismatches a compile-time error, analogous to the recommendation in the external report to standardize all health calculations to a single fixed-point scale.

### Proof of Concept

Suppose `PerasVoteStakeDistr` contains:
```
poolA → PerasVoteStake (1_000_000_000 % 1)   -- 1 billion lovelace (absolute)
```
And `PerasParams` has:
```
perasQuorumStakeThreshold = PerasQuorumStakeThreshold (3 % 4)  -- 75% relative
perasQuorumStakeThresholdSafetyMargin = PerasQuorumStakeThresholdSafetyMargin (1 % 100)
```

A peer sends one `PerasVote { pvVoteRound = r, pvVoteBlock = adversarialBlock, pvVoteVoterId = poolA }`.

`stakeAboveThreshold` evaluates:
```
1_000_000_000 >= (3/4 + 1/100)   -- True
```

`votesReachQuorum` returns `Just votesWithQuorum`, `forgePerasCert` is called, and a `ValidatedPerasCert` boosting `adversarialBlock` by `perasWeight` is stored and applied to chain selection — with a single peer-sent vote, no cryptographic key compromise required. [10](#0-9) [11](#0-10)

```haskell
votesReachQuorum ::
  StandardHash blk =>
  PerasCfg blk ->
  [ValidatedPerasVote blk] ->
  Maybe (ValidatedPerasVotesWithQuorum blk)
votesReachQuorum cfg votes =
  case votes of
    -- We need at least one vote to determine who these votes are for, so we
    -- can't vacuously reach a quorum, even if the quorum threshold is 0.
    [] -> Nothing
    -- If we have at least one vote, we must check that all votes are for the
    -- same target, and that their total stake of is above the quorum threshold.
    (v0 : vs)
      | not (allVotesMatchTarget v0 vs) ->
          Nothing
      | not votesHaveEnoughStake ->
          Nothing
      | otherwise ->
          Just
            ValidatedPerasVotesWithQuorum
              { vpvqTarget = getPerasVoteTarget v0
              , vpvqVotes = v0 :| vs
              , vpvqPerasCfg = cfg
              }
 where
  totalVoteStake =
    mconcat (vpvVoteStake <$> votes)
  votesHaveEnoughStake =
    stakeAboveThreshold cfg totalVoteStake
```
