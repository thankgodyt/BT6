### Title
Peras Vote Verification Bypass: `PerasVote` Carries No Signature and `validatePerasVote` Performs No Cryptographic Check — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `BlockSupportsPeras` degenerate instance — the only active implementation for all block types — defines a `PerasVote` data type that contains no cryptographic signature field, and a `validatePerasVote` function that only checks whether the claimed voter ID appears in the stake distribution. No signature is created, transmitted, or verified at any point in the inbound vote pipeline. Any unprivileged peer can therefore forge votes on behalf of any stakepool in the distribution, accumulate enough fake stake to cross the quorum threshold, and cause the node to forge a `ValidatedPerasCert` boosting an arbitrary block — directly corrupting Peras-based chain selection.

---

### Finding Description

**Root cause — missing signature field in `PerasVote`:**

The `PerasVote` data type (the degenerate instance, which is the only instance in the codebase) is:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound  :: PerasRoundNo
  , pvVoteBlock  :: Point blk
  , pvVoteVoterId :: PerasVoterId
  }
``` [1](#0-0) 

There is no signature, VRF proof, or committee-eligibility proof field. The `CryptoSupportsVoteSigning` interface (`signVote`, `verifyVoteSignature`) and the BLS implementation exist in `Peras/Crypto/BLS.hs`, but they are never wired into the `PerasVote` wire type. [2](#0-1) 

**Root cause — `validatePerasVote` performs no cryptographic check:**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [3](#0-2) 

The function accepts any vote whose `pvVoteVoterId` is a key in the stake distribution map. It does not verify a signature, a VRF eligibility proof, round-number bounds, or committee membership. The `_params` argument is discarded entirely.

This is the **only** `BlockSupportsPeras` instance in the codebase — it is declared as a catch-all `instance StandardHash blk => BlockSupportsPeras blk` with an explicit TODO noting it is a degenerate placeholder: [4](#0-3) 

**Attacker-controlled entry path — `processVotes`:**

Inbound votes from a peer arrive via the object-diffusion mini-protocol and are processed by `processVotes`:

```haskell
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb =
          filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  ...
  mapM_ (addVote . WithArrivalTime now) validatedVotes
``` [5](#0-4) 

The `validateVote` callback used in production is:

```haskell
\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote
``` [6](#0-5) 

This calls the stub `validatePerasVote` above. A peer that knows the current stake distribution (which is public on-chain data) can construct `PerasVote` messages claiming to be any stakepool and pass validation unconditionally.

**Quorum and certificate forging:**

Once enough forged votes are accepted, `updatePerasRoundVoteStates` accumulates their stake. When the total crosses the quorum threshold, `implAddVote` calls `forgePerasCert` — also a stub that always returns `Right` — and stores a `ValidatedPerasCert` in the `PerasVoteDB`: [7](#0-6) 

The forged certificate then boosts the attacker's chosen block in Peras chain selection via `vpcCertBoost`. [8](#0-7) 

---

### Impact Explanation

This is a **Critical** bypass of Peras voting and certificate checks. An unprivileged peer with knowledge of the public stake distribution can:

1. Forge `PerasVote` messages for any set of stakepools whose combined stake exceeds the quorum threshold.
2. Cause the receiving node to forge a `ValidatedPerasCert` for an arbitrary block point.
3. That certificate boosts the attacker's chosen block in chain selection, making the honest node prefer a non-canonical or adversarially-chosen chain.

This directly satisfies the allowed impact: *"Bypass of … Peras voting or certificate checks … that enables unauthorized … vote, or certificate acceptance"* and *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain."*

---

### Likelihood Explanation

The stake distribution is public on-chain data, readable by any node. The `PerasVote` wire type requires only a round number, a block point, and a voter ID — all of which are trivially constructable. No key material is needed. The inbound path (`processVotes` → `validatePerasVote`) is reachable from any connected peer via the object-diffusion mini-protocol. Exploitation requires no special privileges, no operator compromise, and no brute force.

---

### Recommendation

1. **Add a signature field to `PerasVote`**: The wire type must carry a cryptographic signature (e.g., BLS as already implemented in `Peras/Crypto/BLS.hs`) over `(pvVoteRound, pvVoteBlock, pvVoteVoterId)`.

2. **Implement `validatePerasVote` properly**: Verify the signature against the voter's public key from the committee selection context, verify VRF eligibility, and check round-number bounds. Remove the degenerate catch-all instance and replace it with a proper Cardano-era-specific implementation.

3. **Implement `validatePerasCert` properly**: The certificate validation stub also always returns `Right` — it must verify the aggregate BLS signature over the quorum of votes.

4. **Do not ship the degenerate instance to a Peras-enabled network**: The `instance StandardHash blk => BlockSupportsPeras blk` catch-all must be gated or removed before Peras vote diffusion is enabled on any network where the stake distribution is known to peers.

---

### Proof of Concept

An attacker peer performs the following steps:

1. Reads the current `PerasVoteStakeDistr` from the public ledger state (e.g., via a local state query).
2. Selects a set of voter IDs whose combined `PerasVoteStake` exceeds `perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin`.
3. Constructs one `PerasVote { pvVoteRound = r, pvVoteBlock = adversarialPoint, pvVoteVoterId = v }` per selected voter.
4. Sends the batch to the target node via the object-diffusion mini-protocol.
5. `processVotes` calls `validatePerasVote mkPerasParams sd vote` for each; each passes because `lookupPerasVoteStake vote sd` returns `Just stake`.
6. Each vote is added via `implAddVote`; `updatePerasRoundVoteStates` accumulates stake.
7. When the quorum threshold is crossed, `forgePerasCert` is called and a `ValidatedPerasCert` boosting `adversarialPoint` is stored.
8. Peras chain selection now applies `vpcCertBoost` to `adversarialPoint`, causing the node to prefer the attacker's chain.
