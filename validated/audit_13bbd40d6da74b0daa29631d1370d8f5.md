### Title
Peras Quorum Check Bypassed by Unit Mismatch in `stakeAboveThreshold` — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

`stakeAboveThreshold` compares a `PerasVoteStake` (a `Rational`) directly against `perasQuorumStakeThreshold` (also a `Rational`) without any normalization step. The function's own TODO comment acknowledges that the two values may be in different units — one absolute (raw lovelace), one relative (fraction of total committee stake). If a concrete `validatePerasVote` implementation stores an absolute ledger-stake value in `vpvVoteStake`, the comparison is meaningless: absolute lovelace values (billions) will always exceed a relative threshold (e.g. 0.75), so quorum is declared reached on every single vote, enabling any voter to forge a Peras certificate unilaterally.

### Finding Description

`stakeAboveThreshold` is defined as:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake     = unPerasVoteStake voteStake
  quorumThreshold = unPerasQuorumStakeThreshold (perasQuorumStakeThreshold params)
  safetyMargin    = unPerasQuorumStakeThresholdSafetyMargin (perasQuorumStakeThresholdSafetyMargin params)
``` [1](#0-0) 

The function's own documentation explicitly flags the problem:

> "TODO: this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [2](#0-1) 

`PerasVoteStake` is a bare `Rational` with no enforced range: [3](#0-2) 

`perasQuorumStakeThreshold` is also a `Rational`, intended to be a relative fraction (e.g. 0.75): [4](#0-3) 

`votesReachQuorum` — the smart constructor that gates certificate forging — calls `stakeAboveThreshold` directly on the raw sum of `vpvVoteStake` fields without any normalization:

```haskell
totalVoteStake    = mconcat (vpvVoteStake <$> votes)
votesHaveEnoughStake = stakeAboveThreshold cfg totalVoteStake
``` [5](#0-4) 

If a concrete `validatePerasVote` implementation stores the voter's raw ledger stake (e.g. lovelace, on the order of 10^9–10^12) in `vpvVoteStake`, then `totalVoteStake` will be a large absolute number. Compared against a relative threshold of 0.75, the condition `stake >= quorumThreshold + safetyMargin` is trivially true for any non-zero vote, so `votesReachQuorum` returns `Just` on the very first vote received.

The downstream effect is that `updateCandidateVoteState` immediately calls `forgePerasCert` and returns `BecameWinner`: [6](#0-5) 

The forged certificate is then stored in the `PerasWeightSnapshot` and applied to chain selection via `wsvTotalWeight`:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [7](#0-6) 

A chain containing the fraudulently boosted block will appear heavier than honest competing chains, causing `preferCandidate` to switch to it: [8](#0-7) 

### Impact Explanation

A single unprivileged voter — regardless of actual stake — can forge a valid Peras certificate for any block they choose. That certificate injects an arbitrary `PerasWeight` boost (configured via `perasWeight` in `PerasParams`) into the `PerasWeightSnapshot`. Honest nodes performing chain selection will then prefer the adversarially boosted chain over the honest longest chain, constituting a **chain-selection safety failure** and a **bypass of Peras certificate/quorum validation**.

### Likelihood Explanation

The likelihood is **medium**. The vulnerability is latent: it activates only when a concrete `validatePerasVote` instance stores an absolute (unnormalized) ledger-stake value in `vpvVoteStake`. The TODO comment in the production source confirms the normalization step is not yet implemented and the developers acknowledge the risk. Any future or current concrete implementation that follows the natural pattern of reading stake directly from the ledger distribution (as the WFALS committee implementation does, returning raw `LedgerStake` values) will trigger the bug. [9](#0-8) 

### Recommendation

1. **Enforce normalization at the call site**: `votesReachQuorum` (or `stakeAboveThreshold`) must normalize `totalVoteStake` by dividing by the total committee stake before comparing against the relative threshold. The total committee stake should be passed in or derived from the `PerasVoteStakeDistr`.
2. **Use distinct types**: Introduce separate newtypes for absolute stake (`AbsolutePerasVoteStake`) and relative stake (`RelativePerasVoteStake`) so the type system prevents mixing units at the comparison site.
3. **Remove the TODO and add an invariant check**: Assert at the boundary of `validatePerasVote` that the returned `vpvVoteStake` is in `[0, 1]` (relative), or perform the normalization inside `validatePerasVote` itself.

### Proof of Concept

1. A concrete `validatePerasVote` implementation stores the voter's raw lovelace stake (e.g. `1_000_000_000`) as `vpvVoteStake`.
2. `perasQuorumStakeThreshold` is set to `3 % 4` (0.75, the intended 75% quorum).
3. A single adversarial voter submits one vote. `votesReachQuorum` computes `totalVoteStake = PerasVoteStake (1_000_000_000 % 1)`.
4. `stakeAboveThreshold` evaluates `1_000_000_000 >= 3/4 + safetyMargin` → `True`.
5. `forgePerasCert` is called; a certificate is forged for the adversary's chosen block.
6. The certificate is inserted into the `PerasWeightSnapshot` with boost `perasWeight` (e.g. `PerasWeight 15`).
7. The adversary's chain fragment now has `wsvTotalWeight = blockNo + 15`, while the honest chain has `wsvTotalWeight = blockNo`. Honest nodes switch to the adversary's chain.
