### Title
Unprivileged Caller Can Submit Refund Request With Attacker-Controlled BTC Address, Bypassing Authorization via `gas_fee = None` - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary

`request_refund` in `bridge.rs` performs a partial authorization check: it only validates that the caller is DAO/Operator when a custom `gas_fee` is supplied. When `gas_fee` is `None`, the check is skipped entirely, and any unprivileged NEAR account can submit a refund request for any deposit transaction with an arbitrary attacker-controlled BTC `refund_address`. This is a direct analog to H-54: the checked parameter (`gas_fee`) can be zeroed/omitted to bypass the only guard, while the financially critical parameter (`refund_address`) has no authorization check at all.

### Finding Description

`request_refund` is in a `#[trusted_relayer]` impl block, but that attribute on the impl block only generates whitelist-management infrastructure — it does not enforce the relayer check on every method. Methods that individually carry `#[trusted_relayer]` (e.g. `verify_deposit`, `verify_withdraw`, `verify_refund_finalize`) are gated; methods that do not (e.g. `get_user_deposit_address`, `reject_refund`, `execute_refund`, and `request_refund`) are callable by any NEAR account. This is confirmed by the pattern in the first impl block where `get_user_deposit_address` and `get_change_address` carry no individual `#[trusted_relayer]` and are clearly public. [1](#0-0) 

The only authorization check inside `request_refund` is:

```rust
if gas_fee.is_some() {
    let caller = env::predecessor_account_id();
    require!(
        self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller),
        "Only DAO or Operator can specify custom gas_fee"
    );
}
``` [2](#0-1) 

When `gas_fee` is `None` the entire block is skipped. There is no check on who may submit the request or what `refund_address` they may specify.

Inside `internal_request_refund`, the only guard on `refund_address` is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [3](#0-2) 

When `deposit_msg.refund_address` is `None` (the common case for standard deposits), this guard is also skipped, and the caller-supplied `refund_address` is stored verbatim. [4](#0-3) 

After the `unsafe_refund_timelock_sec` elapses, `execute_refund` (also callable by anyone) can be invoked to build and sign a Bitcoin transaction paying the stored `refund_address`. [5](#0-4) 

The `unsafe_refund_timelock_sec` path is taken precisely when `deposit_msg.refund_address` is `None`: [6](#0-5) 

### Impact Explanation

An attacker can redirect a victim's BTC deposit to an attacker-controlled Bitcoin address. The victim's BTC is never minted as nBTC and is instead returned to the attacker. The only on-chain mitigation is DAO/Operator rejection during the `unsafe_refund_timelock_sec` window; if the DAO is slow, offline, or the timelock is short, the theft completes. This constitutes significant loss of user funds — a Critical impact under the allowed scope.

### Likelihood Explanation

The attack requires no privileged access. The attacker needs only:
1. Observe the `LogDepositAddress` event (emitted by `get_user_deposit_address`) to learn the victim's `deposit_msg`.
2. Observe the victim's BTC transaction on-chain (public blockchain data).
3. Call `request_refund` with `gas_fee: None`, the victim's `deposit_msg`, and the attacker's own BTC address.
4. Wait for `unsafe_refund_timelock_sec` and call `execute_refund`.

All inputs are publicly observable. The attack is reachable by any NEAR account with no special role.

### Recommendation

Add an explicit caller-identity check inside `request_refund` that is independent of `gas_fee`. At minimum, require that the caller is either a trusted relayer (add `#[trusted_relayer]` to the method individually, consistent with `verify_refund_finalize`) or that `deposit_msg.refund_address` is pre-set (i.e. the refund destination was committed at deposit time). A concrete fix:

```rust
#[trusted_relayer]   // enforce relayer role, consistent with verify_refund_finalize
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn request_refund(...) -> Promise { ... }
```

Alternatively, if permissionless refund submission is intentional, require that `deposit_msg.refund_address` is always `Some` (pre-authorized at deposit time) so the attacker cannot inject an arbitrary destination.

### Proof of Concept

1. Alice generates a deposit address: `get_user_deposit_address(DepositMsg { recipient_id: alice, refund_address: None, ... })`. The event reveals `deposit_msg`.
2. Alice sends 1 BTC to the deposit address. The transaction is confirmed on-chain but the relayer has not yet called `verify_deposit`.
3. Attacker (any NEAR account) calls:
   ```
   request_refund(
       deposit_msg = <alice's deposit_msg>,
       refund_address = <attacker's BTC address>,
       tx_bytes = <alice's BTC tx>,
       vout = 0,
       proof = <valid inclusion proof>,
       gas_fee = None,   // skips the DAO/Operator check
   )
   ```
   The Light Client validates the proof; `request_refund_callback` stores the request with `refund_address = attacker's address`.
4. After `unsafe_refund_timelock_sec` elapses (and assuming DAO does not reject), attacker calls `execute_refund(utxo_storage_key)`.
5. The bridge builds a Bitcoin transaction paying 1 BTC (minus gas fee) to the attacker's address and submits it for MPC signing.
6. Alice's 1 BTC is stolen; she receives no nBTC.
