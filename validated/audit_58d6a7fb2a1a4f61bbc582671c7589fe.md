### Title
Unprivileged user can permanently block `cancel_withdraw` by filling their pending-sign slot with a refund — (`contracts/satoshi-bridge/src/api/bridge.rs`, `contracts/satoshi-bridge/src/account.rs`)

---

### Summary

`cancel_withdraw` is a DAO/Operator-only function that calls `require_pending_sign_capacity(&user_account_id)` against the **withdrawal owner's** account before proceeding. Because `execute_refund` is a public, unpermissioned function that inserts a `Refund` pending info into the user's `btc_pending_sign_ids`, a user can fill their own pending-sign slot (default limit = 1) and cause every subsequent `cancel_withdraw` call for their withdrawal to panic. The DAO/Operator cannot cancel the withdrawal until they manually clear the blocking refund state.

---

### Finding Description

**Step 1 — The guard in `cancel_withdraw`** [1](#0-0) 

`cancel_withdraw` is role-gated (`Role::DAO | Role::Operator`) but unconditionally calls `require_pending_sign_capacity` on the **user's** account ID, not the caller's.

**Step 2 — What `require_pending_sign_capacity` checks** [2](#0-1) 

It panics with `"Too many pending sign transactions"` when `pending_sign_count() >= max_pending_sign_txs`. The default limit is `1`. [3](#0-2) 

**Step 3 — `execute_refund` is public and fills the slot** [4](#0-3) 

No role gate. Any user with a valid refund request can call it. Internally it reaches `finalize_refund_with_psbt`, which:

1. Calls `require_pending_sign_capacity(&caller)` (succeeds if slot is free).
2. Inserts the new refund `BTCPendingInfo` into `btc_pending_sign_ids`. [5](#0-4) 

After this call the user's `pending_sign_count()` is `1`, which equals `max_pending_sign_txs`.

**Step 4 — `cancel_withdraw` does NOT consume a pending-sign slot**

`internal_cancel_withdraw` calls `set_rbf_pending_info`, which inserts only into `btc_pending_infos` and `rbf_txs` — it never touches `account.btc_pending_sign_ids`. [6](#0-5) 

So the capacity check in `cancel_withdraw` is guarding a slot that will never be consumed, yet it still panics when the user's slot is full.

---

### Impact Explanation

Once the user's `btc_pending_sign_ids` is full (one refund pending info in `PendingSign` state), every `cancel_withdraw` call for that user's withdrawal panics. The withdrawal funds remain locked in the bridge until an operator:

1. Calls `reject_refund` to remove the refund request.
2. Calls `remove_refund_pending_tx_id` to remove the blocking pending info.

This is operator intervention on a per-user basis. If the user repeatedly creates new refund requests (different deposit UTXOs), they can re-block the cancel after each operator cleanup cycle.

---

### Likelihood Explanation

The preconditions are reachable by any user who:
- Has an active withdrawal in `PendingVerify` state (normal bridge usage).
- Has at least one unfinalized deposit UTXO eligible for a refund request (also normal — deposits can fail to be picked up by the relayer).

Both conditions can co-exist in ordinary bridge operation. The user does not need any privileged role.

---

### Recommendation

Remove the `require_pending_sign_capacity` call from `cancel_withdraw` (and `cancel_active_utxo_management`). The cancel RBF path does not add to `btc_pending_sign_ids`, so the check is both unnecessary and harmful. Privileged cancel operations must be unconditionally executable regardless of the user's pending-sign slot count.

---

### Proof of Concept

```
State setup:
  user.btc_pending_sign_ids = {}          // empty
  max_pending_sign_txs = 1 (default)

  // User has a withdrawal stuck in PendingVerify
  btc_pending_infos["withdraw_tx_id"] = WithdrawOriginal { stage: PendingVerify, account_id: user }

  // User has a valid refund request (deposit never finalized)
  refund_requests["utxo_key"] = RefundRequest { created_at_sec: T-timelock-1 }

Attack:
  user calls execute_refund("utxo_key")
    → finalize_refund_with_psbt(caller=user, ...)
    → require_pending_sign_capacity(user)  // passes: 0 < 1
    → btc_pending_sign_ids.insert("refund_pending_id")
    // Now pending_sign_count() == 1

Trigger:
  DAO calls cancel_withdraw("withdraw_tx_id", output)
    → user_account_id = "user"
    → require_pending_sign_capacity("user")
    → pending_sign_count() == 1 >= max_pending_sign_txs == 1
    → PANIC: "Too many pending sign transactions"

Result:
  cancel_withdraw is blocked until operator manually rejects the
  refund request and removes the pending info.
```

    pub fn set_rbf_pending_info(
        &mut self,
        original_btc_pending_verify_id: &str,
        mut btc_pending_info: BTCPendingInfo,
        psbt: PsbtWrapper,
        is_cancel: bool,
    ) -> String {
        let rbf_psbt_hex = psbt.serialize();
        let btc_pending_id = psbt.get_pending_id();
        btc_pending_info.btc_pending_id.clone_from(&btc_pending_id);
        btc_pending_info.psbt_hex = rbf_psbt_hex;
        require!(
            self.data_mut()
                .btc_pending_infos
                .insert(btc_pending_id.clone(), btc_pending_info.into())
                .is_none(),
            "pending info already exist"
        );
        let rbf_txs = self
            .data_mut()
            .rbf_txs
            .entry(original_btc_pending_verify_id.to_owned())
            .or_default();
        require!(rbf_txs.insert(btc_pending_id.clone()), "Rbf already exist");
        if !is_cancel {
            require!(
                rbf_txs.len() <= self.internal_config().rbf_num_limit.into(),
                "Exceed rbf_num_limit"
            );
        }
        btc_pending_id
    }
