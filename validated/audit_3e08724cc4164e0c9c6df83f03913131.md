### Title
Permanently Locked nBTC in `lost_found` With No DAO/Operator Recovery Path - (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary

The `lost_found` map accumulates nBTC balances for users whose cancel-withdraw token refunds failed. The sole recovery mechanism, `claim_lost_found()`, is gated exclusively on `env::predecessor_account_id()` — meaning only the original user can reclaim the funds. There is no DAO or operator emergency withdrawal path. If a user loses wallet access, their nBTC is permanently locked in the contract with no on-chain recovery mechanism.

### Finding Description

When a withdrawal is cancelled (via `cancel_withdraw`), the bridge attempts to return the user's nBTC. If that cross-contract transfer fails, the amount is stored in `data.lost_found` keyed by the user's `AccountId`. The only way to retrieve these funds is:

```rust
pub fn claim_lost_found(&mut self) -> Promise {
    assert_one_yocto();
    let account_id = env::predecessor_account_id();
    let amount = self
        .data_mut()
        .lost_found
        .remove(&account_id)
        .expect("The account does not have lostfound");
    self.internal_transfer_nbtc(&account_id, amount)
}
``` [1](#0-0) 

The function unconditionally uses `env::predecessor_account_id()` as both the key lookup and the transfer destination. There is no alternative path — no DAO override, no operator rescue function, no admin-controlled redirect. The `management.rs` file exposes no function that touches `lost_found` at all. [2](#0-1) 

The `lost_found` field is declared in `ContractData` as `IterableMap<AccountId, u128>`, confirming it accumulates balances over time. [3](#0-2) 

### Impact Explanation

nBTC tokens stranded in `lost_found` represent backed BTC held in the bridge's UTXO set. If those nBTC tokens can never be burned (because the user cannot call `claim_lost_found`), the corresponding BTC UTXOs are also permanently unreleasable for those amounts. This constitutes permanent locking of user funds — a stuck bridge state with no operator intervention possible. This matches the Medium impact category: *"stuck bridge state requiring operator intervention"* (where no such intervention exists).

### Likelihood Explanation

The `lost_found` path is triggered whenever a cancel-withdraw's nBTC refund cross-contract call fails — for example, if the user's NEAR account lacks token storage registration. This is a realistic operational scenario. Once funds land in `lost_found`, any user who subsequently loses access to their NEAR wallet (lost key, account deletion, etc.) has no recourse. The longer the bridge operates, the more likely `lost_found` accumulates orphaned balances.

### Recommendation

Add a DAO-gated emergency recovery function that allows redirecting a `lost_found` balance to a specified account, analogous to the NukeFund recommendation:

```rust
#[payable]
#[access_control_any(roles(Role::DAO))]
pub fn rescue_lost_found(&mut self, account_id: AccountId, recipient: AccountId) -> Promise {
    assert_one_yocto();
    let amount = self
        .data_mut()
        .lost_found
        .remove(&account_id)
        .expect("No lost_found balance for account");
    self.internal_transfer_nbtc(&recipient, amount)
}
```

This preserves the user-self-service path while giving the DAO a recovery option for permanently inaccessible accounts.

### Proof of Concept

1. User calls `ft_transfer_call` on nBTC contract with `Withdraw` message → bridge creates `BTCPendingInfo`.
2. DAO/Operator calls `cancel_withdraw` → bridge attempts to return nBTC via cross-contract call.
3. The nBTC transfer fails (e.g., user account not registered for token storage) → amount is written to `data.lost_found[user]`.
4. User loses access to their NEAR wallet (lost seed phrase).
5. No one — including DAO — can call `claim_lost_found` on behalf of the user, because the function hard-codes `env::predecessor_account_id()` as the key.
6. The nBTC balance in `lost_found` is permanently inaccessible. The backed BTC UTXOs for that amount are also permanently locked in the bridge. [1](#0-0)

#[near]
impl Contract {
    /// Withdraw a specified amount of protocol fee to the owner’s account.
    ///
    /// # Arguments
    ///
    /// * `amount` - Specify the amount to withdraw; if not specified, it will be the full amount.
    ///
    /// # Returns
    ///
    /// bool - Whether the Withdraw was successful.
    #[payable]
    #[access_control_any(roles(Role::DAO))]
    pub fn withdraw_protocol_fee(&mut self, amount: Option<U128>) -> Promise {
        assert_one_yocto();
        let total_protocol_fee = self.data().cur_available_protocol_fee;
        let amount = amount.map_or(total_protocol_fee, |v| v.0);
        require!(amount > 0 && amount <= total_protocol_fee, "Invalid amount");
        self.data_mut().cur_available_protocol_fee -= amount;
        self.data_mut().acc_claimed_protocol_fee += amount;
        self.internal_withdraw_protocol_fee(amount)
    }
}
