Audit Report

## Title
Pause Check Missing on `deploy_token` in Solana `bridge_token_factory` - (`solana/programs/bridge_token_factory/src/lib.rs`)

## Summary
The Solana `bridge_token_factory` program's `deploy_token` instruction performs no check against the `Config.paused` bitmask, while every other state-changing instruction (`init_transfer`, `init_transfer_sol`, `finalize_transfer`, `finalize_transfer_sol`) does. The `ALL_PAUSED` constant in `constants.rs` is defined only as `INIT_TRANSFER_PAUSED | FINALIZE_TRANSFER_PAUSED` with no `DEPLOY_TOKEN_PAUSED` bit, and no such bit is checked in `deploy_token`. This allows any party holding a valid MPC-signed `DeployTokenPayload` to register a new token on Solana while the bridge is fully paused, constituting a pause bypass enabling a deployer-equivalent action.

## Finding Description
In `solana/programs/bridge_token_factory/src/lib.rs`, the `deploy_token` function at L66–76 is:

```rust
pub fn deploy_token(
    ctx: Context<DeployToken>,
    data: SignedPayload<DeployTokenPayload>,
) -> Result<()> {
    msg!("Deploying token");
    data.verify_signature((), &ctx.accounts.common.config.derived_near_bridge_address)?;
    ctx.accounts.initialize_token_metadata(data.payload)?;
    Ok(())
}
```

No pause check is present. By contrast, `finalize_transfer` (L82–85), `finalize_transfer_sol` (L101–104), `init_transfer` (L125–128), and `init_transfer_sol` (L140–143) all gate execution with `require!(ctx.accounts.common.config.paused & <FLAG> == 0, error::ErrorCode::Paused)`.

In `constants.rs`, the pause bitmask constants are:
- `INIT_TRANSFER_PAUSED: u8 = 1 << 0` (L36)
- `FINALIZE_TRANSFER_PAUSED: u8 = 1 << 1` (L39)
- `ALL_PAUSED: u8 = INIT_TRANSFER_PAUSED | FINALIZE_TRANSFER_PAUSED` (L42)

There is no `DEPLOY_TOKEN_PAUSED` bit defined or included in `ALL_PAUSED`.

The `pause` instruction in `pause.rs` (L27) sets `self.config.paused = ALL_PAUSED`, which only covers the two transfer flags. Even with `ALL_PAUSED` set, `deploy_token` proceeds unconditionally.

The EVM implementation guards `deployToken` with `whenNotPaused(PAUSED_DEPLOY_TOKEN)`, and the Starknet implementation asserts `!_is_paused(@self, PAUSE_DEPLOY_TOKEN)`. The Solana implementation is the only one missing this guard.

**Exploit path:**
1. Admin calls `pause`, setting `config.paused = ALL_PAUSED`. All transfer instructions revert.
2. Attacker retrieves a valid MPC-signed `DeployTokenPayload` from previously emitted NEAR on-chain events (publicly observable from `sign_log_metadata_callback` logs).
3. Attacker calls `deploy_token` on the Solana program with the collected signed payload.
4. The instruction executes successfully — signature verification passes, `initialize_token_metadata` runs — and the token is registered in Solana program state, bypassing the emergency freeze.

## Impact Explanation
This is a concrete pause bypass allowing an unprivileged external actor to execute a deployer-equivalent action (registering a new token mapping and initializing token metadata on Solana) while the bridge is in a fully paused emergency state. This matches the allowed critical impact: *"pause bypass that lets an attacker execute bridge, token, deployer, relayer, or admin-equivalent actions."* A token deployed during a pause creates on-chain state (a new wrapped mint with initialized metadata) that enables subsequent `finalize_transfer` calls for that token once the bridge is unpaused, potentially enabling unauthorized minting of bridge tokens for a token the admin intended to block.

## Likelihood Explanation
MPC-signed `DeployTokenPayload` messages are generated by the NEAR bridge and their signatures are emitted as public on-chain log events, observable by any network participant. An attacker only needs to monitor NEAR for such events and retain the signed payloads. The call to `deploy_token` on Solana is fully permissionless — no admin access, key compromise, or collusion is required. The precondition (holding a valid signed payload) is realistic for any active observer of the NEAR chain.

## Recommendation
Introduce a `DEPLOY_TOKEN_PAUSED` bitmask constant in `solana/programs/bridge_token_factory/src/constants.rs` and include it in `ALL_PAUSED`:

```rust
pub const DEPLOY_TOKEN_PAUSED: u8 = 1 << 2;
pub const ALL_PAUSED: u8 = INIT_TRANSFER_PAUSED | FINALIZE_TRANSFER_PAUSED | DEPLOY_TOKEN_PAUSED;
```

Then add the pause check to `deploy_token` in `lib.rs`, importing `DEPLOY_TOKEN_PAUSED` alongside the existing imports:

```rust
pub fn deploy_token(
    ctx: Context<DeployToken>,
    data: SignedPayload<DeployTokenPayload>,
) -> Result<()> {
    require!(
        ctx.accounts.common.config.paused & DEPLOY_TOKEN_PAUSED == 0,
        error::ErrorCode::Paused
    );
    msg!("Deploying token");
    data.verify_signature((), &ctx.accounts.common.config.derived_near_bridge_address)?;
    ctx.accounts.initialize_token_metadata(data.payload)?;
    Ok(())
}
```

## Proof of Concept
1. Deploy the Solana `bridge_token_factory` program locally (anchor test environment).
2. Call `pause` as the `pausable_admin`. Verify `config.paused == ALL_PAUSED`.
3. Confirm `init_transfer` and `finalize_transfer` revert with `Paused`.
4. Construct a valid `SignedPayload<DeployTokenPayload>` using a test MPC keypair (matching `derived_near_bridge_address` in config) for a token not yet deployed.
5. Call `deploy_token` with this payload. Observe it succeeds and the token metadata account is initialized — no pause error is raised.
6. Apply the fix (add `DEPLOY_TOKEN_PAUSED` check). Repeat step 5 and confirm it now reverts with `Paused`.
