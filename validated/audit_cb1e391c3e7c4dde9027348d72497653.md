### Title
Unvalidated `refund_address` in `request_refund` Allows Any Caller to Redirect a Victim's BTC Refund to an Attacker-Controlled Address - (File: `contracts/satoshi-bridge/src/api/bridge.rs`, `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

The `request_refund` function accepts a caller-supplied `refund_address` parameter without validating that the caller is the original depositor or is otherwise authorized to designate where the refund BTC should be sent. Any unprivileged NEAR account can submit a refund request for any unfinalized deposit and specify their own BTC address as the destination, analogous to the SVFHook finding where an unvalidated `key` parameter allowed liquidity to be added to an arbitrary pool.

---

### Finding Description

`request_refund` is a public, payable function with no role restriction beyond the global pause: [1](#0-0) 

It accepts `deposit_msg` (used to derive the deposit address path) and a caller-supplied `refund_address`. The only guard on `refund_address` is: [2](#0-1) 

This check only fires when `deposit_msg.refund_address` is already `Some`. For the common case where `deposit_msg.refund_address` is `None` (standard deposits that do not pre-authorize a refund address), the caller may supply **any** BTC address and it is accepted without further validation.

In `request_refund_callback`, the contract verifies that the transaction output's `script_pubkey` matches the deposit address derived from `deposit_msg`: [3](#0-2) 

This confirms the deposit transaction is genuine, but it does **not** confirm that the caller is the `deposit_msg.recipient_id` or is otherwise authorized to redirect the refund. The `refund_address` is then stored verbatim: [4](#0-3) 

After the `unsafe_refund_timelock_sec` elapses, `execute_refund` is also a public function with no caller validation: [5](#0-4) 

The timelock branch for caller-supplied addresses is: [6](#0-5) 

The `deposit_msg` used to derive the deposit address is publicly observable: `get_user_deposit_address` emits a `LogDepositAddress` event containing the full `deposit_msg`, `path`, and `deposit_address`: [7](#0-6) 

---

### Impact Explanation

An attacker who observes the `LogDepositAddress` event and the corresponding on-chain BTC deposit can:

1. Call `request_refund` with the victim's `deposit_msg` and `tx_bytes`, but substitute their own BTC address as `refund_address`.
2. The callback validates the transaction inclusion and script match — both pass — and stores the attacker's address as the refund destination.
3. After `unsafe_refund_timelock_sec` passes without DAO rejection, the attacker calls `execute_refund`.
4. The bridge's MPC pipeline signs a transaction sending the victim's BTC to the attacker's address.

If successful, this constitutes direct theft of user BTC — a Critical impact under the allowed scope ("Significant loss, theft, destruction, or permanent locking of user or protocol funds").

---

### Likelihood Explanation

The attack is reachable by any unprivileged NEAR account. The `deposit_msg` is publicly emitted on-chain. The attacker only needs to:
- Observe an unfinalized deposit (one not yet in `verified_deposit_utxo`).
- Pay the anti-spam storage deposit (`required_balance_for_request_refund`).
- Wait for `unsafe_refund_timelock_sec` without the DAO rejecting the request.

The sole mitigation is DAO/Operator rejection during the timelock window. If the DAO is offline, slow, or overwhelmed (e.g., during high-volume periods or an incident), the window remains open. Deposits that are delayed in finalization (relayer downtime, chain congestion) extend the attack surface.

---

### Recommendation

Validate that the caller is authorized to designate the refund address. Concrete options:

1. **Require caller to be `deposit_msg.recipient_id`**: Add `require!(env::predecessor_account_id() == deposit_msg.recipient_id, "Unauthorized")` in `internal_request_refund` before the Light Client call.
2. **Require `deposit_msg.refund_address` to be pre-set** for permissionless refund requests: only allow `refund_address` to be caller-supplied when the caller is a privileged role (DAO/Operator/RefundOperator).
3. **Require a NEAR signature** from `deposit_msg.recipient_id` authorizing the specific `refund_address`, similar to how the SVFHook fix validates the pool key against the hook's own pool.

---

### Proof of Concept

1. Alice calls `get_user_deposit_address(deposit_msg)` where `deposit_msg.recipient_id = "alice.near"` and `deposit_msg.refund_address = None`. The contract emits `LogDepositAddress { deposit_msg, path, deposit_address }`.
2. Alice sends BTC to `deposit_address`. The relayer is temporarily offline; the deposit is not yet finalized.
3. Bob (attacker) observes the event and the BTC transaction on-chain. Bob calls:
   ```
   request_refund(
     deposit_msg = <Alice's deposit_msg>,
     refund_address = "bob_btc_address",
     tx_bytes = <Alice's deposit tx>,
     vout = 0,
     proof = <valid inclusion proof>,
     gas_fee = None
   )
   ```
   with the required NEAR storage deposit attached.
4. `request_refund_callback` verifies the transaction is included and the output script matches Alice's deposit address — both pass. The refund request is stored with `refund_address = "bob_btc_address"`.
5. After `unsafe_refund_timelock_sec` elapses without DAO rejection, Bob calls `execute_refund(utxo_storage_key)`.
6. The bridge builds and MPC-signs a Bitcoin transaction sending Alice's BTC to Bob's address.

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
