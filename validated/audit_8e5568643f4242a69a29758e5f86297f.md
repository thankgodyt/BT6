### Title
Peras Certificate Validation Completely Bypassed — Any Peer Can Inject Arbitrary Certificates to Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` is a stub that unconditionally accepts every inbound `PerasCert` without performing any cryptographic or quorum check. This stub is wired directly into the live certificate-diffusion ingest path. Any unprivileged peer can therefore inject a crafted certificate for an arbitrary block, causing honest nodes to apply a Peras chain-selection boost to that block and prefer it over the honest chain — bypassing the entire multi-party quorum requirement that Peras is designed to enforce.

### Finding Description

**Root cause — unconditional acceptance in the production instance**

`BlockSupportsPeras` is the typeclass that the consensus layer calls to validate inbound Peras certificates. The only deployed instance is the catch-all `instance StandardHash blk => BlockSupportsPeras blk` defined at line 320 of `SupportsPeras.hs`. Its `validatePerasCert` method is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature is verified, no voter eligibility is checked, and no quorum threshold is applied. Every `PerasCert` that arrives is immediately wrapped in a `ValidatedPerasCert` carrying the full `perasWeight` boost (15 by default).

**Entry path — live certificate ingest pipeline**

`processCerts` in the object-diffusion layer is the function that handles batches of certificates received from peers. It calls `validatePerasCert mkPerasParams` directly:

```haskell
, opwAddObjects = \certs ->
    processCerts
      systemTime
      (ChainDB.getPerasCertIds chainDB)
      -- TODO replace when actual plumbing is in place
      (validatePerasCert mkPerasParams)
      (void . ChainDB.addPerasCertAsync chainDB)
      certs
``` [2](#0-1) 

`processCerts` partitions the batch into valid/invalid using `validateCert`:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
``` [3](#0-2) 

Because `validateCert` is the stub, the left partition is always empty and every certificate is forwarded to `ChainDB.addPerasCertAsync`.

**What the quorum check is supposed to enforce**

`stakeAboveThreshold` and `votesReachQuorum` exist precisely to enforce that a certificate represents ≥ 3/4 of total stake plus a safety margin before it is accepted:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
``` [4](#0-3) 

These checks are used correctly inside the local vote-aggregation path (`updateCandidateVoteState` → `votesReachQuorum` → `forgePerasCert`), but they are **never called** when a certificate arrives from a remote peer, because `validatePerasCert` short-circuits the entire verification.

**Analog to the external report**

The external report's `autoWithdraw` only required the builder's own signature to drain funds that should have required multi-party consent. Here, `validatePerasCert` requires no authorization at all — a single peer's message is sufficient to inject a certificate that should require ≥ 3/4 of stake to produce. Both bugs allow one party to unilaterally bypass a multi-party trust model.

### Impact Explanation

A `ValidatedPerasCert` carrying `vpcCertBoost = perasWeight params` (15 by default) is applied to chain selection. A block boosted by a certificate is preferred over an unboosted chain of equal or lesser weight. An attacker who injects a certificate for an adversarial block causes honest nodes to prefer that block in chain selection, enabling:

- **Chain selection manipulation**: honest nodes adopt an adversarially-chosen block as the tip, diverging from the canonical chain.
- **Rollback of honest blocks**: once the boosted adversarial block is adopted, honest blocks on the competing fork may be rolled back.
- **Bypass of the entire Peras finality guarantee**: Peras certificates are the mechanism by which blocks gain finality-like weight; accepting forged certificates nullifies this guarantee entirely.

This matches the **High** impact category: a chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.

### Likelihood Explanation

The attack requires only a TCP connection to the node's peer-to-peer port and the ability to send a single well-formed (but cryptographically invalid) `PerasCert` CBOR message. No stake, no keys, and no prior relationship with the node are needed. The stub is unconditional — there is no fallback check, no feature flag, and no environment in which the real validation fires. Any peer that can reach the node can exploit this.

### Recommendation

Replace the stub `validatePerasCert` implementation with a real one that:

1. Verifies the aggregate BLS signature over the certificate's `(electionId, candidate)` pair against the aggregated public keys of the claimed voters.
2. Checks that each claimed voter is a registered stake pool in the current epoch's stake distribution.
3. Computes the total stake of the claimed voters and asserts `stakeAboveThreshold params totalStake` before accepting the certificate.
4. Verifies that the certificate's round number is within the valid window (`perasCertMaxRounds`).

Until the real implementation is ready, the stub should at minimum reject all inbound certificates (return `Left PerasValidationErr`) rather than accept them all, so that the attack surface is closed even before full validation is implemented.

### Proof of Concept

1. Connect to an honest node's peer-to-peer port.
2. Participate in the Peras certificate object-diffusion mini-protocol.
3. Send a `PerasCert` message containing:
   - `pcCertRound`: any valid round number not yet in the node's cert DB.
   - `pcCertBoostedBlock`: the `Point` of any block the attacker wishes to boost (e.g., an adversarial fork tip).
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = PerasWeight 15 })` unconditionally.
5. The certificate is stored in the ChainDB via `addPerasCertAsync`.
6. Chain selection now applies a weight boost of 15 to the adversarial block, causing the honest node to prefer it over the honest chain tip.
