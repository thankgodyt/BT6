Unconditional Peras Certificate Acceptance Bypasses Quorum and Signature Verification, Enabling Unauthorized Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The degenerate `BlockSupportsPeras` instance used across the codebase implements `validatePerasCert` as an unconditional `Right`, meaning every inbound Peras certificate received from an unprivileged peer is accepted without any cryptographic or quorum verification. Because accepted certificates are immediately forwarded into chain selection, a peer can forge a certificate boosting any block in the VolatileDB and cause the receiving node to prefer a non-canonical chain.

---

### Finding Description

`BlockSupportsPeras` is the typeclass that governs Peras certificate and vote validation. Its catch-all instance for any `StandardHash blk` is explicitly marked as a degenerate placeholder:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

This implementation accepts every certificate unconditionally, assigning it the full configured `perasWeight` boost regardless of whether the certificate carries a valid aggregate BLS signature or was produced by a legitimate quorum of committee members.

The inbound certificate diffusion path calls this validator directly. In `processCerts` (used by both `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB`):

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertInboundException ...)
``` [2](#0-1) 

Both pool writers pass `validatePerasCert mkPerasParams` as the validator: [3](#0-2) 

Because `validatePerasCert` always returns `Right`, `partitionEithers` always produces an empty error list, and every peer-supplied certificate is timestamped and stored in the `PerasCertDB`.

Once stored, `chainSelSync` processes the `ChainSelAddPerasCert` message. It calls `chainSelectionForBlock` for the boosted block if that block is present in the VolatileDB and not already on the current chain: [4](#0-3) 

Chain selection then computes `wsvTotalWeight` as `BlockNo + weightBoost`, where `weightBoost` now includes the attacker-supplied certificate's `perasWeight`: [5](#0-4) 

A forged certificate boosting a block on a competing fork can therefore make that fork's total weight exceed the honest chain's weight, causing the node to switch.

---

### Impact Explanation

An unprivileged peer can send a crafted `PerasCert` naming any block hash in the node's VolatileDB as the boosted block. The certificate bypasses all quorum and signature checks, is stored in the `PerasCertDB`, and triggers chain selection. If the boosted block is on a competing fork, the node's `WeightedSelectView` comparison will prefer that fork (higher `wsvTotalWeight`), causing the node to roll back its current chain and adopt the attacker's preferred fork. This constitutes:

- **Bypass of Peras certificate/signature validation** — the quorum requirement (the entire security foundation of Peras) is not enforced.
- **Chain selection error** — an honest node is made to prefer a non-canonical, less-secure chain based on a forged certificate.

---

### Likelihood Explanation

The Peras certificate diffusion mini-protocol is a public, peer-facing interface. Any connected peer can submit certificates. The only guard in `chainSelSync` is a slot-age check (the boosted block must not be older than the immutable tip), which is a weak structural filter, not a cryptographic one. No stake, key ownership, or committee membership is verified. The attack requires only knowledge of a valid block hash in the target node's VolatileDB, which is obtainable via the ChainSync protocol.

---

### Recommendation

Replace the degenerate `validatePerasCert` stub with a real implementation that:
1. Verifies the aggregate BLS signature over `(electionId, boostedBlock)` against the aggregated public keys of the claimed committee members.
2. Confirms that the claimed voters constitute a valid quorum (total stake ≥ configured threshold) using the stake distribution from the epoch corresponding to the certificate's round.
3. Checks that each claimed voter's seat index is within bounds and corresponds to a committee member with positive stake.

Until the real implementation is in place, the certificate diffusion mini-protocol should not be enabled on production nodes, or inbound certificates should be rejected at the transport layer.

---

### Proof of Concept

1. Attacker connects to a target node as a peer.
2. Attacker observes a block hash `H` on a competing fork via ChainSync (e.g., a fork that is 1 block shorter than the honest chain but would become heavier with a boost).
3. Attacker constructs a `PerasCert { pcCertRound = r, pcCertBoostedBlock = H }` with an arbitrary (invalid) signature.
4. Attacker sends this certificate via the Peras certificate diffusion mini-protocol.
5. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })`.
6. The certificate is stored in `PerasCertDB`; `addPerasCertAsync` enqueues a `ChainSelAddPerasCert` message.
7. `chainSelSync` finds block `H` in the VolatileDB, calls `chainSelectionForBlock`.
8. The competing fork's `wsvTotalWeight = BlockNo(fork_tip) + perasWeight` now exceeds the honest chain's `wsvTotalWeight = BlockNo(honest_tip) + 0`.
9. The node rolls back to the attacker's preferred fork. [6](#0-5) [7](#0-6) [8](#0-7)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
