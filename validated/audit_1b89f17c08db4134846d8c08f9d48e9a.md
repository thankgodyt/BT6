### Title
Cancel-Withdraw Blocked for `PendingSign` Withdrawals After Timeout — (`contracts/satoshi-bridge/src/rbf/cancel_withdraw.rs`)

### Summary

`internal_cancel_withdraw` unconditionally requires the original withdrawal to be in `PendingVerify` stage. If signing has not yet completed (`PendingSign`), the cancel path panics and the user's nBTC — already transferred to the bridge — is permanently stuck with no recovery path.

### Finding Description

The withdraw flow begins when a user calls `nbtc.ft_transfer_call(bridge, amount, WithdrawMsg)`. The bridge's `ft_on_transfer` handler calls `ft_on_transfer_withdraw_chain_specific`, which returns `PromiseOrValue::Value(U128(0))`, meaning the bridge keeps all nBTC tokens. [1](#0-0) 

The `BTCPendingInfo` is created with `state: WithdrawOriginal(OriginalState { stage: PendingInfoStage::PendingSign, ... })`. [2](#0-1) 

The state only advances to `PendingVerify` after MPC signing completes. If signing stalls or never completes, the record stays in `PendingSign` indefinitely.

When `cancel_withdraw` is called after `max_btc_tx_pending_sec` elapses, the timeout check passes: [3](#0-2) 

But line 37 immediately calls `assert_withdraw_original_pending_verify_tx()`: [4](#0-3) 

This dispatches to `OriginalState::assert_pending_verify()`: [5](#0-4) 

If `stage == PendingInfoStage::PendingSign`, this panics with `"Not pending verify stage"`. There is no other public function that can cancel or refund a `WithdrawOriginal/PendingSign` record. The user's nBTC is stuck in the bridge contract with no recovery path.

### Impact Explanation

The user's nBTC is transferred to the bridge at withdrawal initiation and is only burned (released from bridge balance) after BTC on-chain verification. If the withdrawal is stuck in `PendingSign` — because MPC signing is delayed, fails, or is never triggered — and the timeout elapses, the cancel path panics. The nBTC is permanently locked in the bridge contract. This is a stuck bridge state requiring operator intervention (e.g., a contract upgrade or admin-level forced removal), which is not available through any public call.

### Likelihood Explanation

MPC/Chain Signatures signing is an external asynchronous process. Network issues, MPC node unavailability, or a relayer bug can leave a withdrawal in `PendingSign` past the `max_btc_tx_pending_sec` deadline. This is a realistic operational scenario, not a theoretical one. Any user who initiates a withdrawal during such a period is affected.

### Recommendation

`assert_withdraw_original_pending_verify_tx` should be replaced with a check that accepts **either** `PendingSign` or `PendingVerify` for the cancel path. Alternatively, add a separate public cancel entry point for `PendingSign` withdrawals that refunds the held nBTC directly (returning it to the user) without requiring a cancel-RBF PSBT.

### Proof of Concept

1. User calls `nbtc.ft_transfer_call(bridge, 100_000, WithdrawMsg{...})`.
2. Bridge creates `BTCPendingInfo` with `stage = PendingSign`. nBTC is held by bridge.
3. MPC signing stalls; no relayer calls `sign_btc_transaction`. Stage remains `PendingSign`.
4. `max_btc_tx_pending_sec` elapses (e.g., 3600 seconds pass).
5. Anyone calls `cancel_withdraw(original_btc_pending_verify_id, cancel_psbt)`.
