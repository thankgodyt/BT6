### Title
Peras Certificate Validation Stub Unconditionally Accepts All Peer-Supplied Certificates — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` method always returns `Right` (success) without performing any cryptographic or semantic verification. Any certificate received from an unprivileged peer over the Peras object-diffusion mini-protocol is accepted unconditionally and stored in the `PerasCertDB`, where it immediately influences chain-selection weight. This is the direct analog of the external report's "missing scope discriminator" class: just as the receipt PDA omitted the sale key from its seeds so any receipt could be redeemed against any sale, the certificate validation path omits all binding checks so any crafted certificate can be injected against any block.

---

### Finding Description

The `BlockSupportsPeras` type class defines `validatePerasCert` as the gate that must cryptographically verify a `PerasCert` before it is admitted to the node's internal state. The catch-all default instance, which applies to every block type that does not override it, is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

The function ignores the certificate's cryptographic content entirely and wraps it in `ValidatedPerasCert` with the full configured boost weight. No signature check, no committee membership check, no round-number binding, no epoch-nonce binding.

This `ValidatedPerasCert` is the type consumed by `processCerts`, the inbound handler for certificates received from remote peers:

```haskell
processCerts ::
  ...
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  ...
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  ...
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _) ->
      throw (PerasCertValidationError errs)
``` [2](#0-1) 

Because `validateCert` always returns `Right`, the `(errs, _)` branch is never taken. Every certificate in the batch is timestamped and forwarded to `addCert`, which stores it in the `PerasCertDB`.

The `PerasCertDB` implementation also carries an explicit TODO for "non-trivial validation logic": [3](#0-2) 

Once stored, the certificate's boost is immediately reflected in `getWeightSnapshot`, which drives chain selection in `chainSelSync`: [4](#0-3) 

The concrete certificate wire format (`PerasCert` in `Cert.V1`) carries `pcRoundNo`, `pcBoostedBlock`, `pcVoters`, and `pcSignature`. None of these fields are verified before the certificate is admitted. [5](#0-4) 

The analog to the external report is precise: the receipt PDA was derived from seeds `[PREFIX, buyer_key]` — the sale key was absent, so any receipt could be replayed against any sale. Here, `validatePerasCert` is derived from zero inputs — no round-number binding, no epoch-nonce binding, no signature binding — so any certificate can be replayed against any block on any chain.

---

### Impact Explanation

A Peras certificate boosts the chain-selection weight of the block it targets by `perasWeight params`. An attacker who can inject a certificate boosting a block on a minority fork causes honest nodes to compute a higher weight for that fork than for the canonical chain. If the injected boost is large enough (or if multiple certificates are injected), the node switches to the attacker-controlled fork. This is a **chain-selection safety failure**: an unprivileged peer causes an honest node to prefer a non-canonical chain, violating the common-prefix property that Peras is designed to strengthen.

**Impact: High** — matches "Chain selection … bug that lets an unpriviled peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."

---

### Likelihood Explanation

The attack requires only the ability to connect to a node and send a well-formed CBOR-encoded `PerasCert` message over the Peras object-diffusion mini-protocol. No stake, no keys, no prior knowledge of the network state is needed. The attacker can target any block hash they choose. The only natural throttle is the deduplication check (`Set.member roundNo (pcdsCertIds pcds)`), which prevents a second certificate for the same round number from being stored — but the attacker can use a fresh round number for each injection.

**Likelihood: High** — reachable by any peer that can open a connection to the node.

---

### Recommendation

1. Implement full cryptographic verification inside `validatePerasCert` before the `ValidatedPerasCert` wrapper is constructed. At minimum this must include: aggregate BLS signature verification over `(pcRoundNo, pcBoostedBlock)`, committee membership verification for every seat index in `pcVoters`, and VRF eligibility verification for non-persistent voters.
2. Bind the certificate to the epoch nonce of the epoch in which its round falls, mirroring the epoch-nonce binding already present in the `WFALS` committee's `implVerifyCert`.
3. Add a round-number range check: reject certificates whose `pcRoundNo` is outside the window `[currRound - A, currRound]` before performing expensive crypto.
4. Track the GitHub issue (`cardano-peras/issues/120`) to ensure the TODO is resolved before any Peras-enabled network is deployed.

---

### Proof of Concept

1. Attacker connects to a node running a Peras-enabled build.
2. Attacker constructs a `PerasCert` with:
   - `pcRoundNo` = any round number not yet in the node's `PerasCertDB`
   - `pcBoostedBlock` = the `Point` of a block on a minority fork the attacker wants to promote
   - `pcVoters` = any non-empty voter map (e.g., seat index 0 with no VRF proof)
   - `pcSignature` = any 48-byte BLS signature (e.g., all zeros)
3. Attacker sends the certificate via the object-diffusion mini-protocol.
4. `processCerts` calls `validatePerasCert` → `Right ValidatedPerasCert{vpcCertBoost = perasWeight params}` is returned unconditionally.
5. The certificate is stored in `PerasCertDB` with full boost weight.
6. `getWeightSnapshot` now reports the minority-fork block as having additional Peras weight.
7. `chainSelSync` triggers chain selection for the boosted block; if the boosted fork's total weight exceeds the current chain's weight, the node switches forks. [1](#0-0) [6](#0-5) [7](#0-6) [8](#0-7)

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

-- Process a Peras certificate by adding it to the PerasCertDB and potentially
-- performing chain selection if a candidate is now better than our selection.
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
