Based on my investigation of the production code, here is my assessment:

**Key code facts established:**

`init_rbf_btc_pending_info` in [1](#0-0)  initializes `signatures: vec![None; original_tx_btc_pending_info.signatures.len()]` and `vutxos: original_tx_btc_pending_info.vutxos.clone()` — both sized to the **original** PSBT's input count.

The cancel PSBT is stored separately via `set_rbf_pending_info` [2](#0-1)  which replaces `psbt_hex` with the cancel PSBT's hex, but `signatures` and `vutxos` retain the original's length.

`check_cancel_withdraw_rbf_psbt_valid` only validates **outputs** via `check_psbt_output_all_change_address` [3](#0-2)  — there is no check that the cancel PSBT's input count matches the original's.

In `internal_sign_btc_transaction`, `signatures[sign_index]` is accessed directly [4](#0-3)  with no bounds guard beyond Rust's default panic. `vutxos[sign_index]` is also accessed at [5](#0-4) .

`sign_btc_transaction` is a public, payable function with no role check beyond `#[pause]` [6](#0-5) .

**Path analysis:**

The invariant mismatch is real: if the cancel PSBT has more inputs than the original, `signatures.len() == original_input_count < cancel_input_count`. Any caller supplying `sign_index >= original_input_count` triggers an out-of-bounds panic at `signatures[sign_index]`.

**However, the critical gating question is who can submit the cancel PSBT.** In `internal_cancel_withdraw`, the DAO role check at [7](#0-6)  is conditional on `excess_gas_fee > 0` only — it is not a blanket gate on the function. I was unable to read `api/bridge.rs` to confirm whether the public `cancel_withdraw` entry point has an additional role guard. If it does not, any user can submit a cancel PSBT with a different input count.

**Impact ceiling:** Even if reachable, the consequence is a panic/stuck state — the cancel RBF signing becomes permanently broken for that pending ID. There is no unauthorized fund movement, minting, or theft. This fits only the Low impact tier: "panic-driven fault in production bridge/token paths without direct theft."

### Title
`signatures` Vec Length Mismatch in Cancel RBF Signing — (`contracts/satoshi-bridge/src/rbf/cancel_withdraw.rs`)

### Summary
`init_rbf_btc_pending_info` initializes the `signatures` vector using the original PSBT's input count, but the cancel PSBT stored in `psbt_hex` may have a different number of inputs. No validation enforces input-count parity. This causes an out-of-bounds panic in `internal_sign_btc_transaction` when `sign_index` is valid for the cancel PSBT but exceeds `signatures.len()`.

### Finding Description
In `internal_cancel_withdraw`, `init_rbf_btc_pending_info` is called with the original `BTCPendingInfo`, producing a new `BTCPendingInfo` where `signatures` has length `original_tx_btc_pending_info.signatures.len()` and `vutxos` is cloned from the original. [1](#0-0) 

The cancel PSBT is then stored via `set_rbf_pending_info`, replacing only `psbt_hex`. [2](#0-1) 

`check_cancel_withdraw_rbf_psbt_valid` validates only outputs, not input count. [8](#0-7) 

When `sign_btc_transaction` is later called with `sign_index >= original_input_count`, the access `btc_pending_info.signatures[sign_index]` panics. [4](#0-3) 

### Impact Explanation
The cancel RBF signing for the affected pending ID becomes permanently broken. No funds are stolen; the stuck state requires operator intervention to resolve. This is Low impact per scope rules.

### Likelihood Explanation
Requires either a legitimate cancel PSBT with a different UTXO set (operator error) or an unprivileged caller submitting such a PSBT if `cancel_withdraw` is not role-gated. The DAO check in `internal_cancel_withdraw` is conditional, not a blanket gate. [9](#0-8) 

### Recommendation
Add an explicit check in `internal_cancel_withdraw` (or in `check_cancel_withdraw_rbf_psbt_valid`) that the cancel PSBT's input count equals `original_tx_btc_pending_info.signatures.len()`. Alternatively, initialize `signatures` using the cancel PSBT's actual input count rather than the original's.

### Proof of Concept
1. Create an original withdraw with 1 input UTXO → `original_input_count = 1`.
2. Submit a cancel PSBT with 2 inputs (e.g., adding a fee-bumping UTXO).
3. `init_rbf_btc_pending_info` sets `signatures = vec![None; 1]`.
4. Call `sign_btc_transaction(cancel_rbf_id, sign_index=1, ...)`.
5. `signatures[1]` panics: index out of bounds (len=1, index=1). [4](#0-3)
