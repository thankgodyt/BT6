Audit Report

## Title
`denormalize_amount()` Unchecked Multiplication Overflow Permanently Freezes Bridged Funds - (File: near/omni-bridge/src/lib.rs)

## Summary

`Contract::denormalize_amount()` performs a bare `amount * (10_u128.pow(diff_decimals))` multiplication with no overflow guard. With `overflow-checks = true` enforced in the workspace `Cargo.toml`, any overflow produces a hard runtime panic. When a user initiates a transfer on a source chain (EVM/Solana/Starknet) for a token whose `origin_decimals` exceeds the foreign-chain `decimals`, and the raw transferred amount is large enough to overflow `u128` after scaling, the NEAR-side `fin_transfer_callback` panics deterministically. Because the source-chain lock/burn is already irreversible at that point, the user's funds are permanently frozen.

## Finding Description

`denormalize_amount` is defined at: [1](#0-0) 

```rust
fn denormalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount * (10_u128.pow(diff_decimals))   // ← unchecked multiplication
}
```

It is called unconditionally inside `fin_transfer_callback` to reconstruct the full-precision NEAR amount from the normalized foreign-chain amount: [2](#0-1) 

And again inside `fast_fin_transfer`: [3](#0-2) 

The workspace enforces `overflow-checks = true`: [4](#0-3) 

This means any integer overflow is a hard panic (`abort`), not silent wrapping.

The `amount` field in `InitTransferMessage` is the raw value emitted verbatim by the source-chain contract (e.g., EVM's `initTransfer` emits the caller-supplied `uint128 amount` directly into the `InitTransfer` event): [5](#0-4) 

No normalization or bounds check is applied to `amount` before it reaches `denormalize_amount`. The `fin_transfer_callback` only validates the emitter address and token decimals lookup before calling `denormalize_amount`: [6](#0-5) 

The `CLAUDE.md` false-positive note #2 addresses only the **subtraction** `origin_decimals - decimals` underflowing due to misconfiguration. It does not address the **multiplication** overflow triggered by a legitimately large user-supplied amount: [7](#0-6) 

## Impact Explanation

This directly satisfies the critical impact criterion: **permanent freezing of bridged funds**. When `fin_transfer_callback` panics:

1. The user's tokens are already locked or burned on the source chain — the `initTransfer` transaction is irreversible.
2. The NEAR-side callback panics before recording the transfer or minting tokens.
3. The same proof, when resubmitted, will overflow again — the panic is deterministic.
4. The user's funds are permanently frozen: unrecoverable on the source chain and never minted on NEAR.

This matches the allowed critical impact: *permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet*.

## Likelihood Explanation

The overflow threshold is `u128::MAX / 10^diff_decimals`. For the common configuration of a NEAR token with 24 `origin_decimals` bridged from an EVM token with 6 `decimals` (`diff_decimals = 18`), the threshold is approximately `3.4 × 10^20` raw EVM units, equivalent to ~340 trillion tokens. While large, this is within the supply range of high-supply meme tokens. For `diff_decimals = 20` or higher (achievable with unusual but valid decimal configurations), the threshold drops to `~3.4 × 10^18` raw units, reachable with far smaller token amounts.

The attack does not require the user to be a trusted relayer. The user only needs to call `initTransfer` on the source chain with a sufficiently large amount. Any legitimate trusted relayer that subsequently submits the proof to NEAR's `fin_transfer` will trigger the panic in `fin_transfer_callback`. The relayer acts in good faith; the overflow is caused entirely by the amount embedded in the proof.

The panic is deterministic and reproducible — no race condition, no timing dependency.

## Recommendation

Replace the bare multiplication with a checked variant:

```rust
fn denormalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount
        .checked_mul(10_u128.pow(diff_decimals))
        .unwrap_or_else(|| env::panic_str("denormalize_amount: overflow"))
}
```

However, since a panic still freezes funds, the better fix is to validate the amount before calling `denormalize_amount` inside `fin_transfer_callback` and `fast_fin_transfer`, and return a recoverable error (rejecting the proof without consuming it) rather than panicking. Additionally, consider enforcing an upper bound on `amount` at the source-chain contract level.

## Proof of Concept

1. Register a token with `origin_decimals = 24`, `decimals = 6` (`diff_decimals = 18`).
2. On EVM, call `initTransfer(tokenAddress, 3_400_000_000_000_000_000_000 /* > u128::MAX / 10^18 */, 0, 0, "near:victim.near", "")`.
3. A trusted relayer submits the resulting proof to NEAR's `fin_transfer`.
4. `fin_transfer_callback` calls `denormalize_amount(3_400_000_000_000_000_000_000, Decimals { origin_decimals: 24, decimals: 6 })`.
5. Computes `3.4 × 10^21 * 10^18 = 3.4 × 10^39 > u128::MAX` — overflow panic.
6. Callback aborts; source-chain tokens are permanently locked; no NEAR tokens are ever minted.

A unit test can reproduce this directly:
```rust
#[test]
#[should_panic]
fn test_denormalize_overflow() {
    Contract::denormalize_amount(
        u128::MAX / 10_u128.pow(17), // just above threshold
        Decimals { decimals: 6, origin_decimals: 24 },
    );
}
