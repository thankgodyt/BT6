### Title
Storage-Unregister Race in `handle_post_action` Burns Unused nBTC Instead of Refunding Sender — (`contracts/nbtc/src/lib.rs`)

### Summary

`handle_post_action` performs an `internal_transfer` from `sender_id` to `receiver_id`, then schedules `ft_on_transfer` → `ft_resolve_transfer` as a detached promise chain. Because the chain is detached, `sender_id` can call `storage_unregister` between receipts (when their balance is 0 after the transfer). If `ft_on_transfer` subsequently returns a non-zero unused amount, `internal_ft_resolve_transfer` finds `sender_id` unregistered and burns the tokens rather than refunding them, permanently reducing `total_supply` below the bridge's BTC custody.

### Finding Description

The execution path in `handle_post_action`: [1](#0-0) 

1. `internal_transfer(&sender_id, &receiver_id, amount, memo)` — moves tokens; `sender_id` balance drops to 0 (if full amount transferred).
2. `ext_ft_receiver::ext(receiver_id).ft_on_transfer(...)` — cross-contract call, separate NEAR receipt.
3. `.then(ext_ft_resolver::ext(...).ft_resolve_transfer(sender_id, receiver_id, amount))` — callback receipt.
4. `.detach()` — the entire chain is fire-and-forget.

Between receipt (1) and receipt (2), `sender_id` holds 0 nBTC and can call `storage_unregister(force: false)`: [2](#0-1) 

When `ft_resolve_transfer` fires and `ft_on_transfer` returned `unused_amount > 0`, the standard NEP-141 `internal_ft_resolve_transfer` checks `self.accounts.get(sender_id)`. Finding no entry, it decrements `total_supply` by `unused_amount` and returns `burned_amount > 0`: [3](#0-2) 

The `burned_amount > 0` log branch is reached, tokens are permanently destroyed, and the bridge's BTC custody exceeds `total_supply`.

### Impact Explanation

The unused nBTC amount is burned without a corresponding BTC withdrawal. `total_supply` falls below the amount of BTC held by the bridge, violating the core bridge invariant. The depositor's funds are permanently lost. This matches: *Low — publicly reachable invariant-violation in production bridge/token paths without direct theft.*

### Likelihood Explanation

**Significantly mitigated by the whitelist guard.** `check_deposit_msg` enforces that `receiver_id` must be on `post_action_receiver_id_white_list` and `msg` must match an approved template in `post_action_msg_templates`: [4](#0-3) 

The attacker **cannot** freely deploy a contract that always returns non-zero from `ft_on_transfer`. They are restricted to whitelisted receivers (e.g., Burrowland) with approved message formats.

The residual risk requires one of:
- A whitelisted contract returning non-zero under a reachable condition (e.g., paused state, failed collateral operation, unsupported token in the approved message template).
- The `ft_on_transfer` call on the whitelisted contract panicking (which the standard resolver also treats as returning the full unused amount).

Both conditions are possible but not fully attacker-controlled. The timing of `storage_unregister` between receipts is feasible on NEAR (receipts execute in separate blocks), but the precondition of a whitelisted contract returning non-zero is not guaranteed.

### Recommendation

1. In `ft_resolve_transfer`, if `burned_amount > 0`, re-register `sender_id` and credit the refund rather than silently burning. Or override `internal_ft_resolve_transfer` to fall back to the bridge account instead of burning.
2. Alternatively, in `handle_post_action`, check that `sender_id` is still registered before calling `internal_transfer`, or re-register `sender_id` in the callback if they are found unregistered.
3. Consider whether `storage_unregister` should be blocked while a pending `ft_resolve_transfer` callback exists for the account (though this is complex to implement on NEAR).

### Proof of Concept

1. Operator whitelists `burrowland.near` with an approved `IncreaseCollateral` message template.
2. Alice deposits BTC with `post_actions: [{receiver_id: burrowland.near, amount: X, msg: <approved template>}]`.
3. Bridge calls `mint(alice, X, ...)` → `handle_post_actions` → `handle_post_action`.
4. `handle_post_action` executes: `internal_transfer(alice → burrowland, X)`. Alice's balance is now 0.
5. Alice submits `storage_unregister(force: false)` — succeeds (balance = 0, 1 yoctoNEAR attached).
6. Burrowland's `ft_on_transfer` returns `X` (e.g., because the collateral operation fails or the contract is paused).
7. `ft_resolve_transfer` fires: `internal_ft_resolve_transfer` finds Alice unregistered, decrements `total_supply` by `X`, returns `burned_amount = X`.
8. Assert: `burned_amount > 0`, `total_supply` decreased by `X` without any BTC withdrawal. [5](#0-4) [6](#0-5)

    pub fn handle_post_action(
        &mut self,
        sender_id: AccountId,
        receiver_id: AccountId,
        amount: U128,
        memo: Option<String>,
        msg: String,
    ) {
        require!(
            env::prepaid_gas() > GAS_FOR_FT_TRANSFER_CALL,
            "More gas is required"
        );
        require!(
            receiver_id != self.bridge_id,
            "handle_post_action: receiver_id must not be the bridge"
        );
        let amount = amount.into();
        self.token
            .internal_transfer(&sender_id, &receiver_id, amount, memo);
        let receiver_gas = env::prepaid_gas()
            .checked_sub(GAS_FOR_FT_TRANSFER_CALL)
            .unwrap_or_else(|| env::panic_str("Prepaid gas overflow"));
        // Initiating receiver's call and the callback
        ext_ft_receiver::ext(receiver_id.clone())
            .with_static_gas(receiver_gas)
            .ft_on_transfer(sender_id.clone(), amount.into(), msg)
            .then(
                ext_ft_resolver::ext(env::current_account_id())
                    .with_static_gas(GAS_FOR_RESOLVE_TRANSFER)
                    .ft_resolve_transfer(sender_id, receiver_id, amount.into()),
            )
            .detach();
    }
