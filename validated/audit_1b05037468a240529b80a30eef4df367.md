### Title
Chain-selection guard `checkPreferTheirsOverOurs` evaluates candidate weight without Peras boosts, causing premature peer disconnection for heavier Peras-boosted chains - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

`checkPreferTheirsOverOurs` is the ChainSync client's guard that disconnects from a peer when its candidate chain is not preferred over the local selection and the header is beyond the forecast horizon. The guard evaluates chain preference using `emptyPerasWeightSnapshot` — ignoring all Peras weight boosts — while the actual chain-selection logic in `ChainDB` uses the real `PerasWeightSnapshot`. This is the direct analog of the reported bug: a protection check is applied to a pre-transformation value (block-count-only weight), but the security-relevant decision is made on the post-transformation value (block-count + Peras boost). A peer serving a Peras-boosted candidate that is heavier than the local selection but shorter by raw block count will be incorrectly disconnected, causing the honest node to permanently prefer the lighter, non-canonical chain.

---

### Finding Description

When the ChainSync client receives a header whose slot is beyond the current forecast horizon, it cannot immediately validate the header. It enters a retry loop waiting for the local selection to advance. Before retrying, it calls `checkPreferTheirsOverOurs` to decide whether the candidate could ever be adopted:

```haskell
-- ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← uses ZERO Peras weight
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse ...
``` [1](#0-0) 

The guard is invoked at line 1816 whenever `prj lst` returns `Nothing` (forecast horizon exceeded): [2](#0-1) 

`preferAnchoredCandidate` with a non-empty `PerasWeightSnapshot` computes `wsvTotalWeight = blockNo + weightBoost` for both fragments and compares them:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [3](#0-2) 

When `emptyPerasWeightSnapshot` is passed, `weightBoost` is always `mempty` (zero), so the comparison degenerates to a pure block-count comparison. The actual chain-selection path in `ChainDB` passes the real `weights` snapshot:

```haskell
ShouldSwitch reason <- [preferAnchoredCandidate bcfg weights curChain $ Diff.getSuffix chain]
``` [4](#0-3) 

The mismatch: the guard checks `blockNo(theirs) > blockNo(ours)` but the real selection checks `blockNo(theirs) + boost(theirs) > blockNo(ours) + boost(ours)`. A candidate chain that is shorter by raw block count but heavier by total Peras weight will fail the guard and trigger `CandidateTooSparse`, disconnecting the peer before the node ever waits long enough to validate and adopt the heavier chain.

---

### Impact Explanation

**High — chain selection error causing an honest node to prefer a non-canonical, lighter chain.**

Consider:
- Local chain: 100 blocks, no Peras boosts → total weight 100.
- Peer's chain: 90 blocks, Peras boost of 20 → total weight 110.
- Peer's tip is beyond the forecast horizon (common during initial sync or after a long slot gap).

`checkPreferTheirsOverOurs` evaluates `90 > 100` → False → throws `CandidateTooSparse` and disconnects. The node never waits for the forecast horizon to advance, never downloads the peer's blocks, and permanently retains the lighter chain. If all peers serving the heavier chain are in this state simultaneously (e.g., during a burst of Peras certificates that boost a fork), the node is stuck on the non-canonical chain with no recovery path short of operator intervention.

---

### Likelihood Explanation

**Medium.** Requires Peras to be enabled and producing certificates (currently under active development and deployment). The scenario is triggered when a candidate chain's tip is beyond the forecast horizon — a normal condition during initial sync or after a node restarts behind. The Peras boost accumulates across all boosted blocks in the candidate suffix, so even a modest number of certificates can produce a weight differential large enough to trigger the mismatch. The TODO comment at line 1841 explicitly acknowledges the defect is known and unresolved. [5](#0-4) 

---

### Recommendation

Replace `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the actual `PerasWeightSnapshot` used by the rest of chain selection. The snapshot is already available in the `ChainDB` environment and is threaded through `chainSelectionForBlock` and `constructPreferableCandidates`. The ChainSync client should receive it (or a read action for it) so the guard evaluates the same total weight as the downstream selection logic.

```diff
- emptyPerasWeightSnapshot
+ weights   -- the real PerasWeightSnapshot from the ChainDB/GSM environment
```

This mirrors the fix in the reference report: move the protection check to operate on the post-transformation value (total Peras weight) rather than the pre-transformation value (raw block count).

---

### Proof of Concept

1. Enable Peras. Issue certificates boosting blocks on fork `F` (90 blocks, boost 20, total weight 110).
2. Local node is on chain `C` (100 blocks, no boost, total weight 100).
3. A peer begins serving `F`. Its tip slot is beyond the local forecast horizon (e.g., the node just restarted).
4. The ChainSync client calls `readLedgerStateHelper` → `prj lst` returns `Nothing` → `checkPreferTheirsOverOurs` is invoked.
5. `preferAnchoredCandidate cfg emptyPerasWeightSnapshot ourFrag theirFrag` computes `90 > 100` → `ShouldNotSwitch` → `throwSTM CandidateTooSparse`.
6. The peer is disconnected. The node retains chain `C` (weight 100) and never adopts `F` (weight 110).
7. If all peers serving `F` are in the same forecast-horizon state, the node is permanently on the lighter, non-canonical chain. [6](#0-5) [7](#0-6) [8](#0-7)
