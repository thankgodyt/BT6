### Title
Tokens Permanently Stuck in Bridge When `safe_mint` Called for Unregistered Account — (`contracts/nbtc/src/lib.rs`)

---

### Summary

The `safe_mint` function in the nBTC token contract mints tokens to the bridge account **before** checking whether the recipient account is registered. If the recipient is not registered, the function returns early with `U128(0)`, leaving the minted tokens permanently trapped in the bridge account with no recovery path.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, `safe_mint` is gated to the bridge only (`assert_bridge()`). Its logic is:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into()); // ← tokens minted here

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));  // ← early return, tokens stuck
    }
    // ... ft_transfer_call or ft_transfer to account_id
}
```

The sequence is:

1. `internal_deposit` credits `amount` to `bridge_id` (total supply increases).
2. The registration check fires — if `account_id` has no storage deposit, the function returns `U128(0)`.
3. The tokens credited to `bridge_id` are never forwarded to the user and are never added to any `lost_found` map.

Contrast this with `transfer_nbtc_callback` in `token_transfer.rs`, which **does** add failed amounts to `lost_found` for later recovery. `safe_mint` has no equivalent safety net. [1](#0-0) [2](#0-1) 

---

### Impact Explanation

When `safe_mint` is invoked for a recipient who has not registered a storage deposit with the nBTC contract:

- Tokens are minted into `bridge_id`'s balance (total supply grows).
- The user receives nothing.
- No `lost_found` entry is created.
- The bridge has no public function to credit the user retroactively from its own balance.

The result is a **permanent, irrecoverable loss of the user's bridged funds** — the nBTC supply is inflated relative to the BTC backing it, and the user's deposit is effectively destroyed. This matches the allowed impact: *significant loss or permanent locking of user funds*. [3](#0-2) [4](#0-3) 

---

### Likelihood Explanation

Any user who deposits BTC without first registering a storage deposit on the nBTC contract triggers this path. Storage registration is a NEAR-specific prerequisite that is easy to miss, especially for new users or integrations that call the bridge without a prior `storage_deposit`. The bridge itself cannot prevent this because `safe_mint` is the only caller-side check, and it silently discards the funds rather than reverting. [5](#0-4) 

---

### Recommendation

Reverse the order of operations: check account registration **before** minting. If the account is unregistered, either revert with a clear error or add the amount to `lost_found` (mirroring the pattern in `transfer_nbtc_callback`) so the user can recover funds after registering storage.

```rust
// Check first, mint second
if self.token.accounts.get(&account_id).is_none() {
    // Option A: revert
    env::panic_str("Account not registered; call storage_deposit first");
    // Option B: record in lost_found for later recovery
}
self.token.internal_deposit(&self.bridge_id, amount.into());
``` [6](#0-5) [7](#0-6) 

---

### Proof of Concept

1. User deposits BTC to their derived bridge address without calling `storage_deposit` on the nBTC contract.
2. Relayer submits the inclusion proof; the bridge verifies it and calls `safe_mint(user_account, amount, msg)`.
3. `internal_deposit(&bridge_id, amount)` executes — nBTC total supply increases by `amount`.
4. `self.token.accounts.get(&user_account)` returns `None` (no storage registration).
5. Function returns `PromiseOrValue::Value(U128(0))`.
6. `amount` nBTC sits in `bridge_id`'s balance permanently; user receives 0 nBTC; no `lost_found` entry exists.
7. The BTC is locked in the bridge UTXO set; the user has lost their funds with no recourse. [1](#0-0)
