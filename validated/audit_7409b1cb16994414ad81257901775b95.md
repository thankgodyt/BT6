The code confirms the vulnerability. Let me verify one key detail about the nonce behavior before writing the report.

In `finTransfer`, the nonce is marked at line 287 (`completedTransfers[payload.destinationNonce] = true`) **before** the `safeTransfer` at lines 351-354. If `safeTransfer` reverts, Solidity rolls back **all** state changes in that transaction, including the nonce marking. So the claim's assertion that "the nonce is consumed on the first failed attempt" is technically incorrect — the nonce is rolled back on revert.

However, the core vulnerability and its impact are real and confirmed by the code:

- The event emits the caller-supplied `amount`, not the actually received amount [2](#0-1)

- There is no admin token-rescue function anywhere in the contract, so the deficit tokens are permanently stuck

The `finTransfer` call will always revert (insufficient balance), but since the revert rolls back the nonce, it can be retried — it will just always fail. Audit Report

## Title
Fee-on-Transfer Token Balance Mismatch Causes Permanent Fund Freezing in `initTransfer` / `finTransfer` - (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

## Summary
`initTransfer` in `OmniBridge.sol` performs no balance-before/balance-after check when pulling native ERC20 tokens from the caller. For fee-on-transfer tokens, the contract receives `amount - fee` but emits `InitTransfer` with the full `amount`. The NEAR side mints the full `amount` to the recipient. When the reverse leg calls `finTransfer`, it attempts to release the full `amount` via `safeTransfer`, which always reverts because the contract only holds `amount - fee`. No admin token-rescue function exists, so the deficit is permanent and the EVM-side tokens are frozen.

## Finding Description
In `initTransfer`, the `else` branch for native ERC20 tokens (not bridge tokens, not custom minters) executes:

```solidity
IERC20(tokenAddress).safeTransferFrom(
    msg.sender,
    address(this),
    amount
);
```

No balance snapshot is taken before or after this call. The function then emits:

```solidity
emit BridgeTypes.InitTransfer(
    msg.sender, tokenAddress, currentOriginNonce,
    amount, fee, nativeFee, recipient, message
);
```

For a fee-on-transfer token with transfer fee `f`, the contract receives `amount - f` but the event records `amount`. The NEAR relayer reads this event and mints `amount` to the recipient on NEAR.

When the recipient bridges back (NEAR → EVM), NEAR burns `amount` tokens and the MPC signs a payload containing `amount`. `finTransfer` on EVM then executes:

```solidity
IERC20(payload.tokenAddress).safeTransfer(
    payload.recipient,
    payload.amount   // = amount, but contract only holds amount - f
);
```

This `safeTransfer` always reverts. Because Solidity reverts roll back all state changes (including the `completedTransfers[payload.destinationNonce] = true` assignment at line 287), the nonce is not permanently consumed — but the call will revert on every retry since the contract's balance deficit is structural and irrecoverable. There is no admin `rescueTokens` or equivalent function in the contract. The `amount - f` tokens are permanently locked in `OmniBridge`, while NEAR has already minted `amount` tokens to the recipient, creating an unbacked surplus.

The same pattern exists in the Starknet bridge's `init_transfer` / `fin_transfer` pair, where `transfer_from` is called without a balance check and the event emits the caller-supplied `amount`.

## Impact Explanation
This matches the allowed critical impact: **permanent freezing of bridged funds** and **escrow mis-accounting**. For any fee-on-transfer ERC20 token used with the bridge:
- The EVM `OmniBridge` contract permanently holds less than the sum of all `InitTransfer` amounts for that token.
- Every `finTransfer` attempting to release the full declared amount will revert indefinitely.
- The EVM-side tokens are permanently locked with no withdrawal path.
- NEAR-side tokens have already been minted to recipients, creating an unbacked surplus relative to the EVM escrow.

## Likelihood Explanation
Fee-on-transfer ERC20 tokens are a well-established token class (redistribution tokens, tokens with configurable transfer fees). The `initTransfer` function imposes no restriction on which ERC20 tokens can be used — any address that is not a bridge token or custom minter falls into the vulnerable `else` branch. No privileged access is required; the entry point is fully public. A single user bridging such a token triggers the irreversible accounting divergence.

## Recommendation
Use a balance-before/balance-after pattern and revert if the received amount differs from the declared amount:

```solidity
uint256 balanceBefore = IERC20(tokenAddress).balanceOf(address(this));
IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
uint256 received = IERC20(tokenAddress).balanceOf(address(this)) - balanceBefore;
require(received == amount, "FeeOnTransferNotSupported");
```

Alternatively, maintain an explicit token allowlist and reject tokens not on it before the `safeTransferFrom` call. Apply the equivalent fix to the Starknet `init_transfer`.

## Proof of Concept
1. Identify or deploy a fee-on-transfer ERC20 token `T` (e.g., 5% fee on every transfer).
2. Call `OmniBridge.initTransfer(T, 1000, 0, 0, "near:alice.near", "")`.
   - `safeTransferFrom` moves 1000 from caller; contract receives 950 (5% fee taken by token).
   - `InitTransfer` event emits `amount = 1000`.
3. NEAR relayer submits the proof; NEAR bridge mints 1000 NEAR-side tokens to `alice.near`.
4. Alice bridges back: NEAR burns 1000 tokens, MPC signs a payload with `amount = 1000`.
5. Relayer calls `OmniBridge.finTransfer(sig, payload)` on EVM.
   - `safeTransfer(alice_evm, 1000)` reverts — contract only holds 950.
   - The entire transaction reverts (nonce marking is also rolled back).
6. Every subsequent retry of step 5 also reverts for the same reason. The 950 EVM tokens are permanently locked in `OmniBridge` with no withdrawal path. Alice's 1000 NEAR-side tokens are burned, and the EVM escrow is permanently underfunded.
