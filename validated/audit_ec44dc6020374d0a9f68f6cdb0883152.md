Audit Report

## Title
`HyperliquedBridgeToken.mint(address,uint256,bytes)` Unconditionally Redirects All Minted Tokens to `_systemAddress`, Causing Permanent Loss of Bridged Funds — (`evm/src/omni-bridge/contracts/HlBridgeToken.sol`)

## Summary
When `OmniBridge.finTransfer` processes an inbound transfer to a `HyperliquedBridgeToken` with a non-empty `payload.message`, it invokes the 3-arg `mint` override. That override mints `value` tokens to `account` and immediately transfers the entire amount to `_systemAddress`, leaving the recipient with zero tokens. The `bytes memory` message parameter is silently ignored, making the redirect unconditional for any non-empty message.

## Finding Description
`OmniBridge.finTransfer` dispatches to the 3-arg `IBridgeToken.mint(recipient, amount, payload.message)` whenever `isBridgeToken[payload.tokenAddress]` is true and `payload.message.length > 0` (L337–349 of `OmniBridge.sol`).

`HyperliquedBridgeToken.mint(address, uint256, bytes)` (L76–83 of `HlBridgeToken.sol`) executes:
```solidity
_mint(account, value);           // OZ: _update(address(0), account, value) → account += value
_update(account, _systemAddress, value); // account -= value, _systemAddress += value
```
Net effect on `account`: `+value − value = 0`. The `bytes memory` parameter is unnamed and never read; the redirect to `_systemAddress` is unconditional regardless of message content.

`_systemAddress` is the Hyperliquid system precompile. Tokens held there can only be released via `coreReceiveWithData`, which requires `msg.sender == _systemAddress` (L114). The recipient has no mechanism to recover the funds; the Hyperliquid system precompile has no awareness of the NEAR bridge transfer and will not spontaneously release the tokens to the correct recipient.

The NatSpec (L29–31) confirms the 3-arg path was designed solely for HyperCore spot-balance parking — a completely different semantic from a general cross-chain message carrying a memo or DeFi callback.

## Impact Explanation
Any inbound cross-chain transfer to a `HyperliquedBridgeToken` that includes a non-empty `message` field results in: (1) correct `totalSupply` inflation, (2) zero tokens delivered to the recipient, and (3) the full bridged amount permanently parked at `_systemAddress` with no user-accessible recovery path. This is a direct, permanent loss of bridged funds for every affected recipient, matching the Critical impact class: *loss or permanent freezing of bridged funds*.

## Likelihood Explanation
The trigger condition — `payload.message.length > 0` — is a standard, user-initiated bridge feature (cross-chain DeFi callbacks, memos, routing instructions). No attacker capability is required beyond initiating a normal bridge transfer from NEAR with a non-empty message field. The NEAR MPC key signs the full payload including `message`, so a valid signature over such a payload is obtainable through the normal bridge flow. Any legitimate relayer submitting a legitimately signed payload is sufficient to trigger the loss. The condition is repeatable for every such transfer.

## Recommendation
Two concrete fixes:

1. **Revert on direct bridge calls with messages**: Override the 3-arg `mint` to revert unconditionally, forcing all `finTransfer` paths through the 2-arg mint (direct delivery to recipient on HyperEVM). Handle HyperCore parking exclusively through `coreReceiveWithData`.

2. **Decode the message to determine routing**: Parse the `bytes memory message` argument; apply the `_systemAddress` redirect only when the message encodes a valid HyperCore-specific instruction (e.g., a recognized action byte prefix). Otherwise, fall through to a plain `_mint(account, value)` delivering tokens directly to the recipient.

Option 1 is simpler and eliminates the ambiguity entirely.
