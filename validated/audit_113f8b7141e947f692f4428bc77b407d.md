Audit Report

## Title
Precision Loss in `normalize_amount` Permanently Locks User Tokens When Transfer Amount Falls Below Decimal Threshold — (File: `near/omni-bridge/src/lib.rs`)

## Summary
When a user initiates a NEAR-to-foreign-chain transfer where the net amount (after fee) is smaller than `10^(origin_decimals − decimals)`, the `normalize_amount` helper returns `0` via floor division. Every subsequent `sign_transfer` call for that transfer ID panics at the `require!(amount_to_transfer > 0, ...)` guard. Because the tokens were already locked or burned inside `init_transfer_internal` before `sign_transfer` is ever invoked, and no public cancel/refund path exists, those tokens are permanently frozen.

## Finding Description
`normalize_amount` performs integer floor division: [1](#0-0) 

When `amount < 10^diff_decimals`, the result is `0`.

`sign_transfer` calls `normalize_amount` and immediately panics if the result is zero: [2](#0-1) 

Critically, the tokens are locked **before** `sign_transfer` is ever called. Inside `init_transfer_internal`, `add_transfer_message` stores the transfer in `pending_transfers`, then `burn_tokens_if_needed` / `lock_tokens_if_needed` consume the tokens, and the function returns `U128(0)` — signaling to the NEP-141 token contract that zero tokens should be refunded: [3](#0-2) 

`remove_transfer_message` is the only function that removes an entry from `pending_transfers`, and it is only reachable from `sign_transfer_callback` when MPC signing **succeeds** and `fee.is_zero()`: [4](#0-3) 

Since `sign_transfer` panics before the MPC call is ever dispatched, `sign_transfer_callback` is never reached. No public `cancel_transfer`, `refund`, or `unlock` function exists in the contract — a search for such entry points returns no matches. The `claim_fee` path requires a finalized proof from the destination chain, which can never exist for an unsigned transfer.

No minimum-amount guard is applied at initiation time in `ft_on_transfer` or `init_transfer`: [5](#0-4) 

The only fee check (`fee.fee < amount`) does not prevent the normalization-to-zero scenario.

## Impact Explanation
This constitutes **permanent freezing of bridged funds**. For non-deployed (native) tokens, `lock_tokens_if_needed` increments the locked balance with no corresponding unlock path. For bridge-deployed tokens, `burn_tokens_if_needed` destroys them outright. In both cases the user's tokens are irrecoverably lost. This matches the critical allowed impact: *"permanent freezing of bridged funds"* and *"decimal/normalization abuse … that changes user or protocol balances."*

## Likelihood Explanation
The condition is reachable by any unprivileged user via a standard `ft_transfer_call`. No special role or privileged access is required. Tokens bridged between chains with large decimal differences (e.g., a NEAR-native 24-decimal token registered on an EVM chain with 6 decimals, giving `diff_decimals = 18`) have a minimum transferable unit of `10^18` yocto. A user sending any amount below that threshold — a plausible mistake given NEAR balances are displayed in yocto units — triggers the freeze. The condition is repeatable for any such token pair and any amount below the threshold.

## Recommendation
1. **Enforce a minimum amount at initiation time**: In `init_transfer` / `init_transfer_internal`, look up the token's `Decimals` and reject (refund) any transfer whose `amount_without_fee()` is less than `10^(origin_decimals − decimals)`, returning the full amount to the caller per the NEP-141 refund convention (return `transfer_message.amount` instead of `U128(0)`).
2. **Add a public `cancel_transfer` function**: Allow the original sender to cancel a pending transfer that has not yet been signed, unlocking/minting back the locked/burned tokens and returning them to the user.
3. **Alternatively**, enforce that `origin_decimals − decimals` never exceeds a safe bound at token registration time (`bind_token`), eliminating the precision-loss class entirely for extreme decimal differences.

## Proof of Concept
**Setup**: Token registered with `origin_decimals = 24`, `decimals = 6` (`diff_decimals = 18`). Minimum transferable unit = `10^18`.

**Steps**:
1. User calls `ft_transfer_call` on the token contract with `amount = 5 × 10^17` and `fee = 0`.
2. Bridge's `ft_on_transfer` → `init_transfer` → `init_transfer_internal`:
   - `add_transfer_message` stores the `TransferMessage` in `pending_transfers`.
   - `lock_tokens_if_needed` (or `burn_tokens_if_needed`) consumes the `5 × 10^17` tokens.
   - Returns `U128(0)` — no refund issued.
3. Relayer calls `sign_transfer(transfer_id, ...)`.
4. Inside `sign_transfer`:
   - `amount_without_fee()` = `5 × 10^17`
   - `normalize_amount(5×10^17, {origin_decimals:24, decimals:6})` = `5×10^17 / 10^18` = **0**
   - `require!(0 > 0, ...)` → **panic: ERR_INVALID_AMOUNT_TO_TRANSFER**
5. Every subsequent relayer call for this `transfer_id` panics identically; `sign_transfer_callback` is never reached.
6. `claim_fee_callback` and `fin_transfer_callback` are unreachable (no signed payload, no destination-chain proof).
7. The user's `5 × 10^17` tokens remain permanently locked/burned in the bridge with no recovery path.
