### Title
Peras Certificate Validation Stub Unconditionally Accepts Any Peer-Supplied Certificate, Enabling Unauthorized Chain-Selection Boost - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance used for all block types contains a stub `validatePerasCert` implementation that unconditionally returns `Right` (success) for every certificate it receives, performing no signature verification, no quorum check, and no round-number validation. An unprivileged peer can send a crafted `PerasCert` pointing to any block, which will be accepted without question, stored in the `PerasCertDB`, and used to apply a `perasWeight` boost to the attacker-chosen block during chain selection. This can cause an honest node to prefer a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must verify a certificate before it is stored and acted upon. The degenerate instance covering all `StandardHash blk` types, explicitly marked as a temporary scaffold, implements this gate as a no-op:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This instance is the one actually wired into the production network path. The miniprotocol inbound handler `processCerts` calls `validatePerasCert mkPerasParams` on every certificate received from a peer:

```haskell
(validatePerasCert mkPerasParams)
``` [2](#0-1) [3](#0-2) 

Because `validatePerasCert` always returns `Right`, every certificate passes. The validated certificate is then forwarded to `ChainDB.addPerasCertAsync`: [4](#0-3) 

`chainSelSync` processes the certificate: it stores it in the `PerasCertDB` and, if the boosted block is in the `VolatileDB`, immediately triggers `chainSelectionForBlock` for that block: [5](#0-4) 

Chain selection then uses `WeightedSelectView`, which computes `wsvTotalWeight = BlockNo + weightBoost`. The default `perasWeight` is 15, meaning a single forged certificate adds 15 units of weight to the attacker-chosen block: [6](#0-5) [7](#0-6) 

The `PerasWeightSnapshot` accumulates boosts per block point, and multiple forged certificates for different rounds can stack: [8](#0-7) 

The analog to the external report is direct: the external system computes a quorum threshold against all active validators but only allows a fixed subset to participate, making the threshold unreachable. Here, the quorum threshold for a Peras certificate (≥ 3/4 of stake) is defined in `PerasParams` but is never actually checked — the validation function that should enforce it is a stub that always succeeds, so any peer-supplied certificate is treated as if it had met the quorum. [9](#0-8) 

---

### Impact Explanation

An unprivileged peer can send a `PerasCert` with `pcCertBoostedBlock` pointing to any block in the node's `VolatileDB`. The node will accept it, store it, and immediately re-run chain selection with the boosted weight applied. With `perasWeight = 15`, a single forged certificate outweighs 15 honest blocks. An attacker who can deliver one certificate per round can continuously boost a minority fork, causing the victim node to diverge from the canonical chain. This is a chain-selection safety failure: the node accepts an unauthorized certificate and may irreversibly prefer a non-canonical chain.

---

### Likelihood Explanation

The Peras object-diffusion miniprotocol is active whenever Peras is enabled. Any connected peer — no stake, no credentials required — can send a `PerasCert` message. The `processCerts` path is the standard inbound handler for all peer-supplied certificates. The stub is the only `BlockSupportsPeras` instance in the codebase and is used in both the `PerasCertDB`-direct path and the `ChainDB` production path. No additional preconditions are needed beyond a TCP connection to the node.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
1. Verifies the aggregate BLS signature over the certificate's `(roundNo, boostedBlock)` payload against the aggregate public key of the claimed committee members.
2. Confirms that the total stake of the signers meets the `perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin` threshold, normalized against the correct reference stake (committee stake, not raw ledger stake — see the existing `TODO` at lines 136–143 of `SupportsPeras.hs`).
3. Validates the round number is within the acceptable window relative to the current slot.

Until the real implementation is in place, Peras certificate acceptance from untrusted peers should be disabled at the miniprotocol level when running in production.

---

### Proof of Concept

On a private testnet with Peras enabled:

1. Connect to a victim node as an unprivileged peer via the node-to-node miniprotocol.
2. Craft a `PerasCert` with:
   - `pcCertRound = <any round number not yet in the victim's PerasCertDB>`
   - `pcCertBoostedBlock = <point of a block on a minority fork that is in the victim's VolatileDB>`
3. Send the certificate via the Peras object-diffusion miniprotocol.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{vpcCertBoost = PerasWeight 15}` unconditionally. [10](#0-9) 
5. The cert is forwarded to `ChainDB.addPerasCertAsync`, which enqueues a `ChainSelAddPerasCert` message.
6. `chainSelSync` stores the cert in `PerasCertDB` and calls `chainSelectionForBlock` for the boosted block. [11](#0-10) 
7. `WeightedSelectView` now computes `wsvTotalWeight` for the minority fork's tip as `BlockNo + 15`, which may exceed the honest chain's `BlockNo + 0`, causing the victim to switch to the minority fork. [12](#0-11)

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
