### Title
Missing Failure Callback in `claim_lost_found` Causes Permanent Loss of User nBTC Funds — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

`claim_lost_found` removes the user's entry from the `lost_found` map **before** the nBTC cross-contract transfer completes, with no `.then()` callback to restore the entry on failure. If the nBTC transfer fails, the user's funds are permanently stuck in the bridge contract with no recovery path.

---

### Finding Description

In `claim_lost_found` (bridge.rs lines 451–460):

```rust
pub fn claim_lost_found(&mut self) -> Promise {
    assert_one_yocto();
    let account_id = env::predecessor_account_id();
    let amount = self
        .data_mut()
        .lost_found
        .remove(&account_id)          // ← state committed immediately
        .expect("The account does not have lostfound");
    self.internal_transfer_nbtc(&account_id, amount)  // ← no failure callback
}
```

On NEAR Protocol, state mutations are committed at the end of the **current** execution frame, before any cross-contract call is dispatched. The `.remove()` on `lost_found` is therefore persisted regardless of whether the subsequent `internal_transfer_nbtc` Promise succeeds or fails. There is no `.then(callback)` chained to the returned Promise to re-insert the entry on failure.

This is the direct analog of the external report's vulnerability class: a state-saving operation (here, the removal that marks the claim as consumed) is not paired with proper error/failure handling around the token transfer, leaving the contract in an inconsistent state.

The `lost_found` map is populated when a cancel-withdraw refund fails to return nBTC to the user (i.e., the bridge already holds the escrowed tokens). `claim_lost_found` is the **only** recovery path for those tokens. [1](#0-0) 

---

### Impact Explanation

If `internal_transfer_nbtc` fails (cross-contract call panics or returns an error), the `lost_found` entry is already gone. The nBTC tokens remain locked inside the bridge contract with no on-chain mechanism for the user to reclaim them. This constitutes **permanent loss of user funds** — the tokens are neither burned nor returned, and the user cannot call `claim_lost_found` again because the entry no longer exists.

This matches the allowed impact: *"Critical. Significant loss, theft, destruction, or permanent locking of user or protocol funds."*

---

### Likelihood Explanation

The failure of `internal_transfer_nbtc` is reachable by any unprivileged user in several realistic scenarios:

- The user has not registered storage on the nBTC contract (common for new accounts).
- The nBTC contract is paused at the time of the call.
- Insufficient gas is forwarded to the cross-contract call.

Any of these conditions, which can occur in normal bridge operation, will trigger the bug. The entry point (`claim_lost_found`) is public and callable by any account that has a `lost_found` balance. [2](#0-1) 

---

### Recommendation

Chain a `#[private]` callback after `internal_transfer_nbtc` that checks `is_promise_success()` and, on failure, re-inserts the `(account_id, amount)` pair back into `lost_found`. The removal should only be finalized once the transfer is confirmed successful:

```rust
pub fn claim_lost_found(&mut self) -> Promise {
    assert_one_yocto();
    let account_id = env::predecessor_account_id();
    let amount = self
        .data_mut()
        .lost_found
        .remove(&account_id)
        .expect("The account does not have lostfound");
    self.internal_transfer_nbtc(&account_id, amount)
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_CLAIM_LOST_FOUND_CALLBACK)
                .claim_lost_found_callback(account_id, amount),
        )
}

#[private]
pub fn claim_lost_found_callback(&mut self, account_id: AccountId, amount: u128) {
    if !is_promise_success() {
        // Restore the entry so the user can retry
        self.data_mut().lost_found.insert(account_id, amount);
    }
}
```

---

### Proof of Concept

1. User initiates a withdrawal; the bridge escrows their nBTC.
2. The withdrawal is cancelled via `cancel_withdraw`; the refund transfer to the user fails (e.g., no storage registration), so the bridge stores `(user, amount)` in `lost_found`.
3. User calls `claim_lost_found` (attaching 1 yoctoNEAR).
4. `lost_found.remove(&account_id)` executes and the state is committed — the entry is gone.
5. `internal_transfer_nbtc` dispatches a cross-contract call to the nBTC contract, which fails (same storage issue as step 2, or nBTC is paused).
6. No callback exists to restore the entry.
7. User calls `claim_lost_found` again → panics with "The account does not have lostfound".
8. The nBTC tokens remain permanently locked in the bridge contract. [1](#0-0) [3](#0-2)
