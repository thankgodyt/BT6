### Title
Zcash `check_withdraw_chain_specific` Is a Complete No-op, Allowing RBF Without Fee Escalation and Corrupting `max_gas_fee` Tracking — (`contracts/satoshi-bridge/src/zcash_utils/contract_methods.rs`)

---

### Summary

The Zcash feature-flag implementation of `check_withdraw_chain_specific` is an empty function body, unlike the Bitcoin version which enforces strict fee escalation. Any user can call `withdraw_rbf` on their own Zcash withdrawal and supply a new output with the same or even a lower gas fee than the original. The call succeeds, a new `WithdrawUserRbf` pending-sign entry is created, and — critically — `update_max_gas_fee` unconditionally overwrites the original pending info's `max_gas_fee` with the new (potentially lower) value, corrupting the fee-tracking state.

---

### Impact Explanation

**Low.** The attacker is the withdrawal owner themselves. Concrete effects:

1. **Invariant violation**: An RBF pending-sign entry is created without any fee increase, violating the protocol's stated RBF semantics.
2. **`max_gas_fee` corruption**: If the RBF fee is lower than the original, `update_max_gas_fee` decreases the recorded `max_gas_fee` on the original `WithdrawOriginal` entry. This corrupts the fee-tracking state used by any subsequent RBF or cancel-withdraw logic.
3. **Stuck pending state**: Both the original and the RBF pending-sign entries exist simultaneously. Since they spend the same UTXOs, only one can be confirmed on-chain. The other remains as an unresolvable pending-sign entry requiring operator intervention (`cancel_withdraw`) to clean up.

There is no theft, no unauthorized minting, and no impact on other users' funds. The user's nZEC is already locked at withdrawal initiation. This fits the **Low** impact category: publicly reachable invariant-violation and stuck-state in production bridge paths without direct theft.

---

### Likelihood Explanation

Any Zcash withdrawal owner can trigger this by calling `withdraw_rbf` with a PSBT whose computed `gas_fee` (derived from `total_input - total_output`) is ≤ the original fee but still within `[min_btc_gas_fee, max_btc_gas_fee]`. This is straightforward to construct and requires no special privileges.

---

### Recommendation

Implement the same fee-escalation guard in the Zcash `check_withdraw_chain_specific`:

```rust
pub(crate) fn check_withdraw_chain_specific(
    original_tx_btc_pending_info: &BTCPendingInfo,
    gas_fee: u128,
) {
    let max_gas_fee = original_tx_btc_pending_info.get_max_gas_fee();
    let additional_gas_amount = gas_fee.saturating_sub(max_gas_fee);
    require!(additional_gas_amount > 0, "No gas increase.");
}
```

Additionally, consider making `update_max_gas_fee` a no-op (or a `max`-update) when the new fee is not strictly greater, as a defense-in-depth measure.

### Proof of Concept

1. Alice initiates a Zcash withdrawal via `ft_on_transfer` with a PSBT whose gas fee is `F` (e.g., `min_btc_gas_fee + 5000`). The original pending info is stored with `max_gas_fee = F`.
2. Alice calls `withdraw_rbf(original_id, new_output, chain_specific_data)` where `new_output` is constructed so that `total_input - total_output = F` (same fee) or `F - 1000` (lower fee, still ≥ `min_btc_gas_fee`).
3. The call succeeds: `check_withdraw_chain_specific` is a no-op, a new `WithdrawUserRbf` pending-sign entry is created, and `update_max_gas_fee(F - 1000)` decreases the original's `max_gas_fee` to `F - 1000`.
4. Assert: two pending-sign entries exist for the same withdrawal; the original's `max_gas_fee` is now lower than the original gas fee; no fee escalation occurred.
