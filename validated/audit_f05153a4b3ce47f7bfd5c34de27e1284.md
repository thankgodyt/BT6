### Title
Wrong Account Used in Burn-on-Failure Path of `safe_mint_callback` Allows Unauthorized nBTC Retention - (File: `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

### Summary

In `safe_mint_callback`, when the safe-deposit flow fails (i.e., `is_refund_required()` returns `true`), the bridge attempts to burn the already-minted nBTC tokens. However, it calls `burn(env::current_account_id(), ...)` — the bridge contract's own account — instead of `burn(recipient_id, ...)`, the account that actually received the tokens. The burn silently fails (`.detach()` discards the result), and the `recipient_id` retains the minted nBTC permanently.

### Finding Description

The `safe_mint_callback` function handles the result of a `safe_mint` cross-contract call. If `is_refund_required()` returns `true` (meaning `safe_mint` returned `0` unused tokens, indicating the downstream `ft_on_transfer` did not consume them), the bridge is supposed to burn the minted tokens to roll back the deposit.

The failure branch is:

```rust
// contracts/satoshi-bridge/src/btc_light_client/deposit.rs, lines 438-451
} else {
    self.data_mut()
        .verified_deposit_utxo
        .remove(&pending_utxo_info.utxo_storage_key);

    ext_nbtc::ext(self.internal_config().nbtc_account_id.clone())
        .with_static_gas(GAS_FOR_BURN_CALL)
        .burn(
            env::current_account_id(),   // ← BUG: should be `recipient_id`
            mint_amount,
            relayer_account_id,
            U128(0),
        )
        .detach();
```

The `recipient_id` parameter is in scope (it is a named argument of `safe_mint_callback`) but is never used in the burn call. The nBTC tokens were minted to `recipient_id` by `safe_mint`, so the bridge contract (`env::current_account_id()`) holds no nBTC balance to burn. The burn cross-contract call therefore fails, and because `.detach()` is used, the failure is silently discarded. The `recipient_id` retains the full `mint_amount` of nBTC.

Additionally, the UTXO is removed from `verified_deposit_utxo` in the same failure branch, which means the deposit UTXO is no longer marked as consumed, potentially allowing it to be re-submitted via a standard `verify_deposit` path for a second mint.

The correct fix mirrors the M-03 recommendation exactly:

```diff
- env::current_account_id(),
+ recipient_id.clone(),
```

### Impact Explanation

**Critical.** Any user whose safe-deposit `ft_on_transfer` returns `0` (e.g., the downstream DeFi protocol rejects the transfer, panics, or returns unused tokens) will permanently retain minted nBTC that is not backed by a finalized deposit. This constitutes unauthorized minting of nBTC. The bridge's nBTC supply becomes unbacked relative to the BTC held, violating the 1:1 peg invariant. The UTXO removal also opens a secondary path for double-minting via a subsequent `verify_deposit` call on the same UTXO.

### Likelihood Explanation

The `safe_mint` / safe-deposit path is a documented, publicly callable flow exposed via `safe_verify_deposit`, `safe_verify_deposit_compact`, and `verify_deposit_v2` (with `deposit_msg.safe_deposit = Some(..)`). Any bridge user can trigger this path. The failure condition (`ft_on_transfer` returning `0`) is a normal NEP-141 outcome when a receiver contract rejects a transfer, which can happen due to slippage, paused protocols, or misconfigured messages. No privileged access is required.

### Recommendation

Replace `env::current_account_id()` with `recipient_id` in the burn call inside the failure branch of `safe_mint_callback`:

```diff
  ext_nbtc::ext(self.internal_config().nbtc_account_id.clone())
      .with_static_gas(GAS_FOR_BURN_CALL)
      .burn(
-         env::current_account_id(),
+         recipient_id.clone(),
          mint_amount,
          relayer_account_id,
          U128(0),
      )
      .detach();
```

### Proof of Concept

1. A user submits a safe deposit via `verify_deposit_v2` with `deposit_msg.safe_deposit = Some(SafeDepositMsg { msg: "<msg targeting a DeFi protocol>" })`.
2. The relayer calls `verify_deposit_v2`; after light-client verification, `verify_safe_deposit_callback` is invoked, which calls `ext_nbtc::safe_mint(recipient_id, mint_amount, msg)`.
3. The nBTC contract mints `mint_amount` tokens to `recipient_id` and calls `ft_transfer_call` on the downstream receiver.
4. The downstream receiver's `ft_on_transfer` returns `0` (e.g., due to a failed DeFi action), causing `safe_mint` to return `U128(0)`.
5. `safe_mint_callback` is invoked. `is_refund_required()` returns `true` (amount == 0).
6. The bridge calls `burn(env::current_account_id(), mint_amount, ...)`. The bridge contract holds no nBTC, so the burn fails. `.detach()` silently discards the failure.
7. `recipient_id` retains `mint_amount` nBTC. The UTXO is removed from `verified_deposit_utxo`.
8. The user now holds unbacked nBTC. They can optionally re-submit the same UTXO via `verify_deposit` for a second mint. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

    #[private]
    pub fn safe_mint_callback(
        &mut self,
        recipient_id: AccountId,
        mint_amount: U128,
        pending_utxo_info: PendingUTXOInfo,
    ) -> bool {
        let is_success = !is_refund_required();
        let relayer_account_id = env::signer_account_id();

        if is_success {
            Event::UtxoAdded {
                utxo_storage_keys: vec![pending_utxo_info.utxo_storage_key.clone()],
                balances: Some(vec![U128(pending_utxo_info.utxo.balance.into())]),
            }
            .emit();
            self.internal_set_utxo(&pending_utxo_info.utxo_storage_key, pending_utxo_info.utxo);
        } else {
            self.data_mut()
                .verified_deposit_utxo
                .remove(&pending_utxo_info.utxo_storage_key);

            ext_nbtc::ext(self.internal_config().nbtc_account_id.clone())
                .with_static_gas(GAS_FOR_BURN_CALL)
                .burn(
                    env::current_account_id(),
                    mint_amount,
                    relayer_account_id,
                    U128(0),
                )
                .detach();

            Promise::new(env::signer_account_id())
                .transfer(self.required_balance_for_safe_deposit())
                .detach();
        }

        Event::VerifyDepositDetails {
            recipient_id: &recipient_id,
            mint_amount,
            protocol_fee: U128(0),
            relayer_account_id: env::signer_account_id(),
            relayer_fee: U128(0),
            success: is_success,
        }
        .emit();
        is_success
    }

/// Refund only if `safe_mint` returned 0. Any other outcome (non-zero
/// amount, unparseable payload, panic) is treated as "UTXO spent, no
/// refund" — for safety, to avoid a potential double spend.
fn is_refund_required() -> bool {
    match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
        Ok(value) => {
            if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {
                // Normal case: refund if the used token amount is zero
                // The amount can be zero if the `ft_on_transfer` in the receiver contract returns an amount instead of `0`, or if it panics.
                amount.0 == 0
            } else {
                // Unexpected case: don't refund
                false
            }
        }
        // Unexpected case: don't refund
        Err(_) => false,
    }
}
