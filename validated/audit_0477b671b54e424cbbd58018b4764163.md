Stub `validatePerasCert` Unconditionally Accepts Any Peer-Supplied Peras Certificate, Enabling Fraudulent Chain-Weight Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The universal `BlockSupportsPeras` instance implements `validatePerasCert` as a stub that unconditionally returns `Right` (success) for every certificate it receives. This stub is wired directly into the production node-to-node Peras certificate diffusion path. Any unprivileged peer can send a crafted `PerasCert` pointing to an arbitrary block; the certificate will pass "validation," be stored in the `PerasCertDB`, and trigger chain selection that boosts the attacker-chosen block by `perasWeight = 15` slots of extra weight, potentially causing honest nodes to prefer a non-canonical fork.

---

### Finding Description

The `BlockSupportsPeras` typeclass declares `validatePerasCert` as the method responsible for authenticating inbound Peras certificates before they are stored and acted upon:

```haskell
validatePerasCert ::
  PerasCfg blk ->
  PerasCert blk ->
  Either (PerasValidationErr blk) (ValidatedPerasCert blk)
```

The single universal instance (covering all `StandardHash blk`, i.e., every block type in production) implements this as a stub that always succeeds:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature check, no committee membership check, no round-number bounds check, no boosted-block eligibility check — the stub accepts every certificate unconditionally.

This stub is used verbatim in both production pool writers. `makePerasCertPoolWriterFromChainDB` (the writer wired into the live node) calls:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` then uses this validator to gate admission:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) -> mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _)            -> throw (PerasCertValidationError errs)
``` [3](#0-2) 

Because `validatePerasCert` never returns `Left`, the `(errs, _)` branch is unreachable; every certificate from every peer is admitted.

The admitted certificate is then forwarded to `ChainDB.addPerasCertAsync`, which feeds `chainSelSync`. That function looks up the boosted block in the `VolatileDB` and, if found, calls `chainSelectionForBlock` for it:

```haskell
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

Chain selection now treats the boosted block as carrying an extra `perasWeight = 15` slots of weight, which can tip the balance in favour of the attacker's fork.

The entire path is wired into the live node-to-node diffusion layer:

```haskell
, hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      ...
``` [5](#0-4)

### Impact Explanation

An unprivileged peer can craft a `PerasCert` whose `pcCertBoostedBlock` points to any block the attacker has already diffused to the victim. Because `validatePerasCert` is a stub, the certificate is accepted without any cryptographic or eligibility check. The fraudulent certificate is stored in the `PerasCertDB` and triggers chain selection that adds `perasWeight` (15 slots) of artificial weight to the attacker's chosen block. If the attacker's fork is within 15 slots of the honest tip, the victim node will switch to the attacker's chain. This constitutes a chain-selection manipulation attack: an unprivileged peer can make an honest node prefer a non-canonical, adversary-controlled chain beyond the intended Peras security assumptions.

**Impact class:** High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.

---

### Likelihood Explanation

The attack requires only a valid peer connection and knowledge of a block hash already present in the victim's `VolatileDB` (easily obtained via the block-fetch protocol). No keys, stake, or operator access are needed. The Peras cert diffusion mini-protocol is active in the production node-to-node stack. Likelihood is **High** once Peras is enabled on a live network.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real one that verifies:
1. The certificate's cryptographic signature against the claimed committee members.
2. That the signers hold sufficient committee stake to meet the quorum threshold.
3. That the round number is within the valid window (`perasCertMaxRounds`).
4. That the boosted block is eligible (age ≥ `perasBlockMinSlots`, not in cooldown).

Until the real implementation is in place, the Peras cert diffusion mini-protocol should not be enabled in production builds, or inbound certificates should be dropped rather than accepted unconditionally.

---

### Proof of Concept

1. Attacker connects to a victim node via the node-to-node protocol.
2. Attacker learns block hash `H` of a block on a minority fork (e.g., via the chain-sync or block-fetch protocol).
3. Attacker sends a single `PerasCert { pcCertRound = R, pcCertBoostedBlock = H }` over the Peras cert diffusion channel.
4. On the victim: `objectDiffusionInbound` → `makePerasCertPoolWriterFromChainDB` → `processCerts` → `validatePerasCert mkPerasParams cert` → `Right ValidatedPerasCert{..}` (stub, no rejection possible).
5. `ChainDB.addPerasCertAsync` stores the cert; `chainSelSync` finds block `H` in `VolatileDB` and calls `chainSelectionForBlock` for it.
6. Chain selection scores the fork containing `H` with an extra `perasWeight = 15` boost.
7. If the honest tip is within 15 slots of the fork tip, the victim switches to the attacker's fork. [6](#0-5) [7](#0-6) [8](#0-7)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
