Audit Report

## Title
Non-Atomic Token Migration Causes Permanent Fund Loss When Recipient Unregistered on New Token — (File: `near/omni-bridge/src/lib.rs`)

## Summary

`swap_migrated_token` constructs a `burn.and(mint)` joint promise with no callback and detaches it, while `ft_on_transfer` simultaneously returns `U128(0)`, permanently accepting the old tokens. Because NEAR's async model executes each sub-promise as an independent action receipt, a panic in `mint` (triggered when the recipient has no storage registration on the new token) does not roll back the already-committed `burn`. The user's old tokens are destroyed and new tokens are never issued, with no recovery path.

## Finding Description

**`ft_on_transfer` handler** (`near/omni-bridge/src/lib.rs` L275–279): immediately returns `U128(0)` and detaches the promise, permanently accepting the old tokens before any cross-contract result is known.

**`swap_migrated_token`** (`near/omni-bridge/src/lib.rs` L2738–2753): constructs `burn.and(mint)` with no `.then(callback)`. In NEAR's runtime, `Promise::and` schedules both sub-promises as independent action receipts. A failure in one does not roll back the other.

- `burn` calls `ext_token::ext(old_token).burn(amount)`, which executes `internal_withdraw` on the bridge's old-token balance — committed and irreversible once the receipt executes.
- `mint` calls `ext_token::ext(new_token).mint(sender_id, amount, None)`, which (with `msg = None`) calls `self.token.internal_deposit(&account_id, amount.into())` (`near/omni-token/src/lib.rs` L141). `FungibleToken::internal_deposit` from `near-contract-standards` panics if `account_id` has no storage registration.

**`migrate_deployed_token`** (`near/omni-bridge/src/lib.rs` L1651–1655): only calls `storage_deposit` for `env::current_account_id()` (the bridge itself) on the new token. Individual users are never pre-registered.

Since the new token is freshly deployed, every existing token holder is unregistered by default. The `mint` sub-promise panics for any such user, but `burn` has already executed.

## Impact Explanation

Permanent, irreversible destruction of user funds: old tokens are burned (total supply decreases), new tokens are never minted (total supply unchanged), and the user ends with zero balance of either token. This is a concrete instance of "permanent freezing / loss of bridged funds" — a Critical allowed impact. No privileged access is required; any token holder triggers it via a standard `ft_transfer_call`.

## Likelihood Explanation

The default state for all existing token holders after `migrate_deployed_token` is called is "unregistered on new token." The natural migration action — sending old tokens with the `SwapMigratedToken` message — is sufficient to trigger the loss. No attacker is needed; ordinary users following the migration flow will lose funds. The condition is near-certain for any user who has not separately called `storage_deposit` on the new token, which is an undocumented prerequisite.

## Recommendation

Reverse the operation order: call `mint` first, then in a `.then(callback)` verify the mint succeeded before calling `burn`. If `mint` fails, the old tokens remain in the bridge's custody and can be returned via `ft_transfer`. Alternatively, add a `then` callback after `burn.and(mint)` that inspects both sub-promise results and, on any failure, re-mints old tokens back to the user or stores a claimable balance. A pre-flight `storage_balance_of` check before issuing the burn+mint would also prevent the loss, though it adds a cross-contract round-trip.

## Proof of Concept

```
1. Deploy old_token and new_token (OmniToken contracts).
2. Call migrate_deployed_token(origin_chain, old_token, new_token) on the bridge.
   → Bridge registers itself on new_token; alice is NOT registered.
3. Mint 1000 old_token to alice (alice is registered on old_token).
4. Alice calls:
     old_token.ft_transfer_call(bridge, "1000", '{"SwapMigratedToken": {}}')
   → ft_on_transfer returns U128(0); bridge holds 1000 old tokens.
   → burn receipt executes: bridge's old_token balance → 0 (committed).
   → mint receipt executes: internal_deposit(alice, 1000) panics
     (alice has no storage on new_token).
5. Assert: old_token.ft_total_supply() decreased by 1000.
6. Assert: new_token.ft_total_supply() == 0.
7. Assert: alice.ft_balance_of(old_token) == 0.
8. Assert: alice.ft_balance_of(new_token) == 0.
   → Alice's 1000 tokens are permanently destroyed.
```
