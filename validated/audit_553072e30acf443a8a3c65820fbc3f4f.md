### Title
Peras Vote and Certificate Validation Stubs Accept Any Peer-Submitted Vote/Certificate Without Cryptographic Eligibility Verification - (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The default `BlockSupportsPeras` instance provides stub implementations of `validatePerasCert` and `validatePerasVote` that perform no cryptographic verification. `validatePerasCert` unconditionally returns `Right` for every certificate, and `validatePerasVote` only checks that a voter ID appears in the stake distribution — it never verifies the BLS vote signature or the VRF eligibility proof embedded in the vote. These stubs are wired directly into the live peer-facing vote ingestion path (`processVotes`), meaning any unprivileged peer can submit crafted Peras votes or certificates that will be accepted and stored, potentially forging a quorum certificate and influencing chain selection weight boosts.

### Finding Description

**Root cause — `validatePerasCert` always returns `Right`:** [1](#0-0) 

The default implementation unconditionally wraps any incoming `PerasCert` in `ValidatedPerasCert` without inspecting the aggregate BLS signature, the voter set, or any eligibility proof.

**Root cause — `validatePerasVote` skips signature and VRF proof verification:** [2](#0-1) 

The only check performed is `lookupPerasVoteStake vote stakeDistr` — i.e., whether the claimed voter ID exists in the stake distribution. The `pvSignature` (BLS vote signature) and `pvEligibilityProof` (VRF output for non-persistent members) fields defined in the concrete `PerasVote` type are never verified. [3](#0-2) 

**Exploit path through the live peer-facing ingestion pipeline:**

`processVotes` is called for every batch of votes received from a peer. It calls the `validatePerasVote` stub, and if validation passes, adds the vote to the database: [4](#0-3) 

The `implAddVote` function in `PerasVoteDB` also carries an explicit TODO acknowledging that non-trivial validation logic is missing: [5](#0-4) 

**Full attack sequence:**

1. Attacker connects as an unprivileged peer via the object-diffusion mini-protocol.
2. Attacker crafts `PerasVote` messages claiming the seat index of any real stake pool (whose ID appears in the stake distribution), with an arbitrary or zeroed `pvSignature` and `pvEligibilityProof`.
3. `processVotes` calls `validatePerasVote`; the only check — stake lookup — passes because the claimed voter ID is real.
4. The vote is stored with the full stake weight of the impersonated pool.
5. By repeating this for enough pools, the attacker accumulates sufficient stake-weighted votes to trigger `updatePerasRoundVoteStates` to reach quorum and forge a certificate.
6. `validatePerasCert` (always `Right`) accepts the forged certificate.
7. The certificate is inserted via `addPerasCertAsync`, adding a Peras weight boost to an attacker-chosen block, directly influencing chain selection. [6](#0-5) 

### Impact Explanation

An unprivileged peer can impersonate any registered stake pool's voting identity and forge a Peras quorum certificate for an arbitrary block. This certificate adds a configurable weight boost (`perasWeight`) to that block, causing honest nodes to prefer it over the canonical chain. This is a **bypass of Peras voting and certificate checks** enabling unauthorized certificate acceptance and chain-selection manipulation — matching the "Critical" impact tier: *bypass of Peras voting or certificate checks that enables unauthorized vote or certificate acceptance*.

### Likelihood Explanation

The attack requires only a valid peer connection (no keys, no stake, no admin access). The attacker needs only to know the `PerasVoterId` (seat index) of any pool with positive stake, which is derivable from the public stake distribution. The object-diffusion mini-protocol is reachable from any connected peer. The missing checks are not gated behind any feature flag in the ingestion path.

### Recommendation

1. In `validatePerasVote`, verify the `pvSignature` field against the voter's registered BLS vote verification key, and for non-persistent members, verify the `pvEligibilityProof` VRF output using `evalVRF` (as already implemented in `implVerifyVote` in `WFALS.hs`).
2. In `validatePerasCert`, verify the aggregate BLS signature against the aggregated verification keys of the claimed voter set (as already implemented in `implVerifyCert` in `WFALS.hs`).
3. The `VotingCommittee` abstraction (`verifyVote`, `verifyCert`) already provides the correct cryptographic verification logic — wire it into the `BlockSupportsPeras` default implementations rather than leaving stubs. [7](#0-6) 

### Proof of Concept

**Deterministic reasoning (no private-testnet execution required):**

1. Construct a `PerasVote` with `pvSeatIndex = 0` (first seat in the stake distribution), `pvEligibilityProof = PersistentPerasVoteEligibilityProof`, and `pvSignature = zeroBLSSignature`.
2. Submit this vote via the object-diffusion protocol to a node running with Peras enabled.
3. `processVotes` calls `validatePerasVote`: `lookupPerasVoteStake` succeeds (seat 0 has positive stake), returning `Right (ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stakeOfSeat0 })`.
4. The vote is stored. Repeat for seats 1, 2, … until `stakeAboveThreshold` is satisfied.
5. `updatePerasRoundVoteStates` triggers `forgePerasCert`, producing a `ValidatedPerasCert` for the attacker's chosen block.
6. `validatePerasCert` returns `Right` unconditionally; the certificate is accepted and boosts the attacker's block in chain selection. [8](#0-7)

processVotes ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
