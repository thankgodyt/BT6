### Title
Missing Committee Eligibility and Signature Validation in Peras Vote Acceptance Allows Unauthorized Quorum Forging - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasVote` function — the only available `BlockSupportsPeras` instance — validates only that a voter ID appears in the stake distribution. It performs no committee eligibility check, no VRF proof verification, and no vote signature check. An unprivileged peer can send crafted `PerasVote` messages for any pool operator in the stake distribution, have those votes accepted and tallied toward quorum, and cause a `ValidatedPerasCert` to be forged for an arbitrary block — without holding any private key.

---

### Finding Description

The degenerate `BlockSupportsPeras` instance in `SupportsPeras.hs` is the only concrete implementation of `validatePerasVote` in the repository:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [1](#0-0) 

The degenerate `PerasVote` data type for this instance carries no signature field at all:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound  :: PerasRoundNo
  , pvVoteBlock  :: Point blk
  , pvVoteVoterId :: PerasVoterId
  }
``` [2](#0-1) 

The production inbound path in `processVotes` calls this validator inside an STM transaction, then unconditionally adds every vote that passes to the `PerasVoteDB`:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [3](#0-2) 

`implAddVote` itself carries an explicit acknowledgement that validation is incomplete:

```haskell

``` [4](#0-3) 

Once a vote passes `validatePerasVote`, `updatePerasRoundVoteStates` accumulates its stake toward the quorum threshold. When the threshold is crossed, `forgePerasCert` is called and a `ValidatedPerasCert` is produced and stored:

```haskell
Right (VoteGeneratedNewCert cert, pvsRoundVoteStates') ->
  pure (AddedPerasVoteAndGeneratedNewCert cert, pvsRoundVoteStates')
``` [5](#0-4) 

The missing checks are:

| Check | Status |
|---|---|
| Voter is in stake distribution | ✅ performed |
| Voter was selected for committee this round (VRF / persistent seat) | ❌ absent |
| Vote carries a valid cryptographic signature | ❌ absent (no signature field) |
| Round number is currently active / not expired | ❌ absent |

The analog to the `Bribe.sol` bug is direct: in `Bribe.sol` the user's balance checkpoint is written with the old non-zero value after claiming, so the user can claim again for epochs they did not vote in. Here, the voter's committee eligibility is never checked, so any party that knows a pool operator's public `PerasVoterId` (a `KeyHash StakePool`, which is public on-chain data) can cast votes on that operator's behalf without their private key, for any round and any block.

---

### Impact Explanation

A `ValidatedPerasCert` produced by this path is used by the `ChainDB` to boost the certified block's weight in chain selection:

```haskell
(Right voteRes@(AddedPerasVoteAndGeneratedNewCert freshCert), perasVoteModel') ->
  let certWithArrival = WithArrivalTime creationTime freshCert
      (certRes, m') = addPerasCert cfg certWithArrival m{perasVoteModel = perasVoteModel'}
``` [6](#0-5) 

An attacker who forges a certificate for an arbitrary block causes honest nodes to prefer that block over the canonical chain. This is a **Critical** bypass of Peras voting/certificate checks: unauthorized certificate acceptance that can produce an irreversible divergent chain preference on any node that receives the crafted votes.

---

### Likelihood Explanation

The attack requires only:
1. Knowledge of pool operator `PerasVoterId` values — these are `KeyHash StakePool` values, publicly derivable from the stake distribution.
2. The ability to send `PerasVote` messages via the object diffusion mini-protocol — available to any unprivileged peer.
3. Enough crafted votes to exceed the quorum threshold — achievable by replaying votes for all pools in the stake distribution.

No private key compromise, no stake majority, and no operator access is required.

---

### Recommendation

1. **Implement full committee eligibility validation** in `validatePerasVote`: verify that the voter was selected for the committee for the given round, including VRF proof verification for non-persistent members (as already implemented in `WFALS.implVerifyVote`).
2. **Add a cryptographic signature field** to the concrete `PerasVote` data type and verify it in `validatePerasVote` before accepting any vote.
3. **Validate round liveness**: reject votes whose round number is outside the currently active window.
4. Track the open issue https://github.com/tweag/cardano-peras/issues/120 as a security-critical blocker before any production deployment of the Peras vote diffusion path.

---

### Proof of Concept

**Attacker-controlled entry path** (`processVotes` → `validatePerasVote` → `implAddVote` → `updatePerasRoundVoteStates` → `forgePerasCert`):

1. Attacker reads the current `PerasVoteStakeDistr` (publicly available via ledger state query).
2. For each pool operator `pid` in the distribution, attacker constructs:
   ```
   PerasVote { pvVoteRound = targetRound, pvVoteBlock = attackerBlock, pvVoteVoterId = pid }
   ```
   No private key is needed — the degenerate `PerasVote` type has no signature field.
3. Attacker sends this batch via the object diffusion mini-protocol to a target node.
4. `processVotes` filters out already-known vote IDs, then calls `validatePerasVote` for each remaining vote. Each vote passes because `lookupPerasVoteStake` finds the voter in the distribution.
5. Each validated vote is added to the `PerasVoteDB` via `implAddVote`. `updatePerasRoundVoteStates` accumulates stake.
6. Once accumulated stake exceeds the quorum threshold, `forgePerasCert` produces a `ValidatedPerasCert` for `attackerBlock`.
7. The certificate is forwarded to the `ChainDB`, which boosts `attackerBlock` in chain selection.
8. The target node now prefers `attackerBlock` over the canonical chain tip. [7](#0-6) [8](#0-7) [9](#0-8)
