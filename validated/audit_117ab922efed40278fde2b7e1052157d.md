Audit Report

## Title
Permanent Loss of Bridged Funds When Token Transfer Fails Without Message in `fin_transfer_send_tokens_callback` — (File: `near/omni-bridge/src/lib.rs`)

## Summary
When a cross-chain transfer is finalized on NEAR with no message payload, `fin_transfer_send_tokens_callback` calls `is_refund_required(false)`, which returns `false` unconditionally without inspecting the promise result of the underlying `mint` or `ft_transfer`. If that token transfer fails for any reason, the transfer is already permanently recorded as finalized via `add_fin_transfer`, the source-chain tokens are already burned or locked, and the recipient never receives their tokens — with no recovery path.

## Finding Description

**Step 1 — `process_fin_transfer_to_near`**

The transfer is immediately and irrevocably recorded as finalized:

```rust
// L1875
let mut required_balance = self.add_fin_transfer(&transfer_message.get_transfer_id());
```

Then `send_tokens` is dispatched and `fin_transfer_send_tokens_callback` is chained with `is_ft_transfer_call = !msg.is_empty()`:

```rust
// L1957–1977
self.send_tokens(token.clone(), recipient, U128(...), &msg)
    .then(
        Self::ext(env::current_account_id())
            .fin_transfer_send_tokens_callback(
                transfer_message, &fee_recipient,
                !msg.is_empty(),   // false when no message
                predecessor_account_id, lock_actions,
            ),
    )
```

**Step 2 — `fin_transfer_send_tokens_callback`**

The callback delegates entirely to `is_refund_required`:

```rust
// L1702
if Self::is_refund_required(is_ft_transfer_call) {
    // revert path: remove_fin_transfer, revert_lock_actions, burn_tokens_if_needed
} else {
    // success path: pay fees, emit FinTransferEvent
}
```

**Root cause — `is_refund_required` when `is_ft_transfer_call = false`**

```rust
// L1784–1803
fn is_refund_required(is_ft_transfer_call: bool) -> bool {
    if is_ft_transfer_call {
        match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
            Ok(value) => { /* checks returned amount */ }
            Err(_) => false,
        }
    } else {
        // Not ft_transfer_call: don't refund
        false   // <-- promise result is NEVER read
    }
}
```

When `msg` is empty, `is_ft_transfer_call = false`, and `is_refund_required` returns `false` without ever calling `env::promise_result_checked`. If `mint` or `ft_transfer` panicked or ran out of gas, the callback still takes the success branch: it emits `FinTransferEvent`, optionally mints/transfers fees, and returns — leaving the transfer permanently finalized with no tokens delivered.

The revert path at L1702–1718 (`remove_fin_transfer`, `revert_lock_actions`, `burn_tokens_if_needed`) is never reached.

## Impact Explanation

This is a **Critical** impact matching: *"Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet, Bitcoin, Zcash, or Wormhole-routed flows."*

Concretely:
- Source-chain tokens (EVM/Solana/Starknet) are already burned or locked at `initTransfer` time.
- The transfer ID is permanently in the finalized set after `add_fin_transfer`; it cannot be re-submitted.
- The recipient receives zero tokens.
- There is no admin recovery path — `remove_fin_transfer` is only called from within the revert branch that is never reached.

The result is permanent, irrecoverable loss of the bridged principal for the user.

## Likelihood Explanation

Any cross-chain transfer with an empty `msg` field is affected if the token transfer fails. Realistic failure conditions include:

1. **Gas exhaustion in the token contract**: If the token contract's `mint` or `ft_transfer` consumes more gas than allocated by `SEND_TOKENS_CALLBACK_GAS`, the promise fails.
2. **Token contract paused**: Many NEP-141 tokens implement a pause mechanism; if the token is paused at finalization time, `ft_transfer`/`mint` panics.
3. **Token contract upgrade or bug**: Any panic in the token contract during execution causes the promise to fail.

Conditions 1 and 2 are realistic in production. Condition 1 can be triggered by a relayer submitting finalization with insufficient gas. Condition 2 can occur during incident response. No privileged access is required to submit a finalization transaction; any relayer (or the user themselves) can call `fin_transfer`.

## Recommendation

In `is_refund_required`, check the promise result for the plain `ft_transfer`/`mint` case as well. A failed promise (non-`Ok` result) should return `true` to trigger the revert path:

```rust
fn is_refund_required(is_ft_transfer_call: bool) -> bool {
    if is_ft_transfer_call {
        match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
            Ok(value) => {
                if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {
                    amount.0 == 0
                } else {
                    false
                }
            }
            Err(_) => false,
        }
    } else {
        // Check whether the plain ft_transfer / mint actually succeeded
        match env::promise_result(0) {
            PromiseResult::Successful(_) => false,
            PromiseResult::Failed => true,
        }
    }
}
```

This ensures that a failed `mint` or `ft_transfer` triggers `remove_fin_transfer`, `revert_lock_actions`, and `burn_tokens_if_needed`, allowing the transfer to be retried or the state to be correctly reverted.
