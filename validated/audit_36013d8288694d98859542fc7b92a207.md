Audit Report

## Title
Missing `multiTokens` Registration Check in `initTransfer1155` Enables Permanent Freezing of ERC-1155 Tokens - (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

## Summary

`initTransfer1155` accepts and locks ERC-1155 tokens without verifying that the `(tokenAddress, tokenId)` pair has been registered via `logMetadata1155`. If a user calls `initTransfer1155` before `logMetadata1155`, the tokens are transferred into the bridge but `multiTokens[deterministicToken]` remains zero, making it impossible for `finTransfer` to release them. No on-chain EVM recovery path exists for stuck ERC-1155 tokens.

## Finding Description

The ERC-1155 bridging flow requires `logMetadata1155` to be called first, which populates `multiTokens[deterministicToken]` at lines 243–255. However, `initTransfer1155` (lines 439–490) performs no such check before calling `IERC1155(tokenAddress).safeTransferFrom(msg.sender, address(this), tokenId, amount, "")` at line 458.

The `onERC1155Received` callback at lines 522–535 checks `operator != address(this)` and reverts for direct sends — but this guard does not block `initTransfer1155`, because the bridge contract itself is the caller of `safeTransferFrom`, making `operator == address(this)`. The transfer succeeds unconditionally.

In `finTransfer` (lines 315–330), the ERC-1155 release branch is only entered when `multiToken.tokenAddress != address(0)` (line 323). If `logMetadata1155` was never called, `multiTokens[deterministicToken]` is zero-valued, so the code falls through to the ERC-20 branch at line 351, which attempts `IERC20(deterministicToken).safeTransfer(...)` against a non-contract deterministic address and reverts. There is no admin rescue function or refund path for ERC-1155 tokens anywhere in the contract.

## Impact Explanation

Any unprivileged user who calls `initTransfer1155` for an unregistered `(tokenAddress, tokenId)` pair will have their ERC-1155 tokens permanently locked in the bridge. The NEAR side receives an `InitTransfer` event referencing an unregistered deterministic address and cannot finalize the transfer. The EVM side cannot release the tokens via `finTransfer` because the `multiTokens` entry is empty. This constitutes permanent freezing of bridged funds, matching the Critical allowed impact class.

## Likelihood Explanation

The function is fully permissionless and requires no special role. A user following ERC-20 bridging UX patterns (where no prior metadata registration step exists) will naturally call `initTransfer1155` directly. The ordering requirement is enforced only by off-chain convention; the contract imposes no on-chain guard. The scenario is trivially reachable by any token holder.

## Recommendation

Add a registration guard at the top of `initTransfer1155`, before the `safeTransferFrom` call:

```solidity
address deterministicToken = deriveDeterministicAddress(tokenAddress, tokenId);
if (multiTokens[deterministicToken].tokenAddress == address(0)) {
    revert ERC1155NotRegistered();
}
```

This mirrors the collision-check pattern already present in `logMetadata1155` and ensures the NEAR side always has a registered token before EVM-side custody is taken.

## Proof of Concept

1. Deploy any ERC-1155 contract and mint tokens to `user`.
2. `user` approves the bridge: `erc1155.setApprovalForAll(bridge, true)`.
3. `user` calls `bridge.initTransfer1155(erc1155Addr, tokenId, amount, 0, 0, "user.near", "")` **without** any prior call to `bridge.logMetadata1155(erc1155Addr, tokenId)`.
4. `safeTransferFrom` succeeds (bridge is `operator`, `onERC1155Received` passes); `amount` tokens are now held by the bridge.
5. `multiTokens[deterministicToken].tokenAddress == address(0)` — never set.
6. The NEAR relayer processes the `InitTransfer` event, finds no registered token for `deterministicToken`, and the NEAR-side transfer fails.
7. Any attempt to call `finTransfer` with `payload.tokenAddress = deterministicToken` skips the ERC-1155 branch (line 323 condition false) and falls to the ERC-20 branch (line 351), which reverts because `deterministicToken` is not a real token contract.
8. Tokens are permanently locked with no on-chain recovery path.
