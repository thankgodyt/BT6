### Title
Peras Certificate and Vote Validation Stubs Unconditionally Accept Any Peer-Supplied Object Without Cryptographic Authorization - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The universal `BlockSupportsPeras` instance implements `validatePerasCert` as an unconditional `Right` — it performs zero cryptographic checks and accepts every certificate from every peer. The companion `validatePerasVote` checks only stake-distribution membership but never verifies any cryptographic signature on the vote. Both stubs are wired directly into the production Peras certificate and vote pool writers (`makePerasCertPoolWriterFromCertDB`, `makePerasCertPoolWriterFromChainDB`, `makePerasVotePoolWriterFromChainDB`), which process inbound objects from untrusted peers. Because accepted Peras certificates carry a chain-selection weight boost, an unprivileged peer can inject arbitrary certificates to manipulate which chain the node considers canonical, bypassing the entire Peras committee-authorization mechanism.

### Finding Description

**Root cause — `validatePerasCert` stub:** [1](#0-0) 

The universal instance `instance StandardHash blk => BlockSupportsPeras blk` (line 320) is the only instance in the codebase. Its `validatePerasCert` implementation (lines 350–358) unconditionally returns `Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }` — no aggregate BLS signature check, no committee membership check, no round validity check. The TODO comment at line 350 explicitly acknowledges this: *"TODO: perform actual validation against all possible 'PerasValidationErr' variants"*.

**Root cause — `validatePerasVote` stub:** [2](#0-1) 

`validatePerasVote` (lines 363–371) only checks that `pvVoteVoterId vote` is present in the stake distribution map. It does not verify any cryptographic signature on the vote. Any peer can forge a vote claiming to be from any registered stake pool without possessing that pool's private key.

**Production wiring — cert pool writers:** [3](#0-2) 

Both `makePerasCertPoolWriterFromCertDB` (line 103) and `makePerasCertPoolWriterFromChainDB` (line 126) pass `validatePerasCert mkPerasParams` as the validation callback to `processCerts`. Since this callback always returns `Right`, every inbound certificate from every peer passes validation and is stored.

**Production wiring — vote pool writers:** [4](#0-3) 

`makePerasVotePoolWriterFromChainDB` (line 141) calls `validatePerasVote mkPerasParams sd vote` for each inbound vote. Because no signature is verified, any peer can submit votes for any registered pool.

**`processCerts` validation gate:** [5](#0-4) 

`processCerts` (lines 164–185) calls `validateCert` on each certificate not already in the DB. With the stub, `partitionEithers` always produces an empty error list, so every certificate is accepted and stored via `addCert`.

**Attacker-controlled entry path:**
1. Attacker connects as a peer via the Peras object diffusion mini-protocol (no privileged keys required).
2. Attacker crafts `PerasCert { pcCertRound = r, pcCertBoostedBlock = targetBlock }` for any block `targetBlock`.
3. Attacker sends the certificate batch to the target node.
4. `processCerts` → `validatePerasCert mkPerasParams cert` → `Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }`.
5. Certificate is stored in `PerasCertDB`/`ChainDB`.
6. `getWeightSnapshot` now returns a Peras weight boost for `targetBlock`, influencing chain selection.

### Impact Explanation

This is a **Critical** bypass of Peras certificate and vote authorization. The Peras protocol's security model requires that only certificates backed by a quorum of legitimately elected committee members (verified via BLS aggregate signatures and VRF-based local sortition proofs) can boost a block's chain-selection weight. The stub eliminates this entire authorization layer. An unprivileged peer with no stake pool keys can:

- Inject fake certificates boosting any block, causing the node to prefer a non-canonical chain.
- Inject fake votes for any registered pool, potentially causing the node to forge spurious certificates when quorum thresholds are met.

This falls squarely within: *"Critical. Bypass of Peras voting or certificate checks that enables unauthorized certificate acceptance"* and *"High. Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain."*

### Likelihood Explanation

Any peer that can reach the Peras object diffusion endpoint can exploit this. No privileged keys, no stake, no social engineering. The only precondition is that the Peras object diffusion protocol is active on the target node. The code is in production files (not test/mock/benchmark), and the pool writers are instantiated in the live `ChainDB` integration path.

### Recommendation

Replace the stub `validatePerasCert` with actual cryptographic validation:
- Verify the aggregate BLS signature over `(electionId, boostedBlock)` using the committee's aggregate verification key.
- Verify committee membership and VRF-based local sortition proofs for each voter listed in the certificate.
- Verify the certificate's round number is within the valid range.

Replace the stub `validatePerasVote` with actual signature verification:
- Verify the BLS vote signature over `(electionId, candidate)` using the voter's registered public key.
- Verify the voter's VRF eligibility proof for non-persistent committee members.

Until these checks are implemented, the Peras cert/vote pool writers must not be active in production, or must reject all inbound objects by default.

### Proof of Concept

```
-- Attacker constructs a fake certificate for any block point
fakeCert :: PerasCert SomeBlock
fakeCert = PerasCert
  { pcCertRound       = PerasRoundNo 42          -- arbitrary round
  , pcCertBoostedBlock = someTargetBlockPoint     -- any block the attacker wants boosted
  }

-- Attacker sends [fakeCert] via the Peras cert diffusion protocol to the target node.
-- processCerts calls:
--   validatePerasCert mkPerasParams fakeCert
--   = Right (ValidatedPerasCert { vpcCert = fakeCert, vpcCertBoost = perasWeight mkPerasParams })
-- Certificate is stored. getWeightSnapshot now returns a boost for someTargetBlockPoint.
-- Chain selection applies the boost; node may switch to attacker-chosen chain.
```

The same applies to votes: an attacker submits `PerasVote { pvVoteRound = r, pvVoteBlock = p, pvVoteVoterId = anyRegisteredPoolId }` — `validatePerasVote` accepts it as long as `anyRegisteredPoolId` is in the stake distribution, with no signature check.

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
