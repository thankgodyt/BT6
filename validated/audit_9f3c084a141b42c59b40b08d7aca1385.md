Audit Report

## Title
Undetected Token Transfer Failure Causes Permanent Loss of Bridged Funds in `fin_transfer_send_tokens_callback` — (File: `near/omni-bridge/src/lib.rs`)

## Summary

When a cross-chain transfer is finalized on NEAR with an empty message payload (`msg.is_empty() == true`), `is_ft_transfer_call` is set to `false` and `is_refund_required` unconditionally returns `false` without inspecting the promise result of the preceding `send_tokens` call. If `mint` or `ft_transfer` fails for any reason, the transfer remains permanently marked as finalized, the source-chain tokens are already burned or locked, and the recipient never receives funds.

## Finding Description

**Step 1 — Permanent finalization before token delivery**

Inside `process_fin_transfer_to_near`, `add_fin_transfer` is called at line 1875 and commits the transfer ID to storage before any token movement occurs:

```rust
let mut required_balance = self.add_fin_transfer(&transfer_message.get_transfer_id());
```

`send_tokens` is then dispatched and `fin_transfer_send_tokens_callback` is chained as its callback with `is_ft_transfer_call = !msg.is_empty()` (line 1973). For a plain transfer with no message, this flag is `false`.

**Step 2 — `is_refund_required` blind spot**

```rust
fn is_refund_required(is_ft_transfer_call: bool) -> bool {
    if is_ft_transfer_call {
        match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) { ... }
    } else {
        // Not ft_transfer_call: don't refund
        false   // ← promise result is NEVER read
    }
}
```

When `is_ft_transfer_call = false`, the function returns `false` without calling `env::promise_result_checked`. A failed `mint` or `ft_transfer` promise is silently ignored.

**Step 3 — Callback takes the success branch unconditionally**

Because `is_refund_required` returns `false`, the callback skips the entire refund block (lines 1702–1718) — which contains `remove_fin_transfer`, `revert_lock_actions`, and `burn_tokens_if_needed` — and instead emits `FinTransferEvent` and pays fees (lines 1719–1746). The transfer ID remains in the finalized set forever, preventing any retry.

**Failure modes for `mint` / `ft_transfer`**

- Gas exhaustion inside the token contract (the allocated `MINT_TOKEN_GAS` / `FT_TRANSFER_GAS` may be insufficient for some token implementations).
- A native token contract that is paused, upgraded, or has a validation bug causing a panic.
- Any transient or permanent panic in the token contract's internal logic.

The storage-deposit pre-check (lines 1905–1913) guards against missing storage registration but does not prevent panics inside the token contract itself.

## Impact Explanation

Permanent, irrecoverable loss of bridged funds: source-chain tokens (EVM/Solana/Starknet) are already burned or locked at `initTransfer`, and the NEAR-side transfer is permanently finalized without delivering tokens to the recipient. This matches the Critical impact class: *permanent freezing of bridged funds across NEAR, EVM, Solana, or Starknet*.

## Likelihood Explanation

Any transfer with an empty `msg` field (the common case for simple token bridges) is affected. The trigger requires the underlying token contract call to fail — possible via gas exhaustion with certain token implementations, a paused or upgraded native token contract, or a panic in token contract logic. While not trivially attacker-controlled, the condition is reachable in normal operational scenarios and affects all no-message transfers systematically.

## Recommendation

In `is_refund_required`, always inspect the promise result regardless of `is_ft_transfer_call`. For the `false` branch, treat a failed promise as requiring a refund:

```rust
} else {
    // Plain ft_transfer or mint: check if the promise failed
    match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
        Ok(_) => false,   // success — no refund needed
        Err(_) => true,   // failure — revert and remove finalization
    }
}
```

This ensures `remove_fin_transfer`, `revert_lock_actions`, and `burn_tokens_if_needed` are invoked on any token-transfer failure, preserving the ability to retry or refund.

## Proof of Concept

1. Deploy a mock NEP-141 token contract whose `ft_transfer` always panics (or configure `MINT_TOKEN_GAS` to be insufficient for the token contract under test).
2. Initiate a cross-chain transfer (EVM → NEAR) with an empty `msg` field targeting a recipient registered on the mock token.
3. Call `fin_transfer` on the NEAR bridge contract with valid proof.
4. Observe that `fin_transfer_send_tokens_callback` is invoked, `is_refund_required` returns `false`, `FinTransferEvent` is emitted, and the transfer ID remains in the finalized set.
5. Confirm the recipient's token balance is unchanged and no retry path exists (re-submitting the same proof is rejected because the transfer ID is already finalized).

A NEAR sandbox integration test using `workspaces-rs` can reproduce this in a local environment by substituting the token contract with one that panics on `ft_transfer`.
