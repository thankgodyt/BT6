### Title
Stub `validatePerasCert` Unconditionally Accepts Any Peer-Supplied Peras Certificate, Enabling Unauthorized Chain-Selection Weight Boost - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` function is an unfinished stub that unconditionally returns `Right` (success) for every inbound `PerasCert`, regardless of its content. No cryptographic signature, no committee membership, and no round-validity check is performed. An unprivileged peer can send a crafted certificate over the Peras object-diffusion mini-protocol, have it accepted as "validated," and cause the node to re-run chain selection with an attacker-chosen block receiving a Peras weight boost — potentially switching the node to a non-canonical fork.

---

### Finding Description

**Root cause — stub validation that always succeeds**

In the default `BlockSupportsPeras` instance (the only instance in the codebase, used for all block types including the production Cardano block), `validatePerasCert` is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

Every field of the peer-supplied `PerasCert` — `pcCertRound` and `pcCertBoostedBlock` — is accepted verbatim. No aggregate BLS signature is verified, no committee membership is checked, and no round-number bounds are enforced. The function is structurally identical to the BatchTrade bug: a field that must be validated against an authoritative source is instead passed through unchecked.

**Inbound path — object diffusion writer**

`makePerasCertPoolWriterFromChainDB` is the production writer used when Peras is enabled. It calls `processCerts` with `validatePerasCert mkPerasParams` as the validation function:

```haskell
(validatePerasCert mkPerasParams)
``` [2](#0-1) 

`processCerts` calls `validateCert` on each inbound certificate; if all pass (which they always do), each is forwarded to `ChainDB.addPerasCertAsync`: [3](#0-2) 

**Chain-selection side-effect**

`addPerasCertAsync` enqueues the certificate for the ChainSel thread. `chainSelSync` processes it: it adds the cert to `PerasCertDB`, looks up the boosted block in the VolatileDB, and calls `chainSelectionForBlock` for that block:

```haskell
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

The CHANGELOG confirms the mechanism: *"the candidate fragment is now selected based on its Peras weight, instead of its length."* [5](#0-4) 

The `PerasWeightSnapshot` derived from the injected certificate is used directly in chain comparison via `getPerasWeightSnapshot`: [6](#0-5) 

**The `PerasCert` data type has no signature field in the default instance**

```haskell
data PerasCert blk = PerasCert
  { pcCertRound      :: PerasRoundNo
  , pcCertBoostedBlock :: Point blk
  }
``` [7](#0-6) 

There is nothing to verify even if the code tried. The concrete `PerasCert` in `Peras/Cert/V1.hs` does carry a `pcSignature` field, but that type is not wired into the production `BlockSupportsPeras` instance — the stub instance is used instead.

---

### Impact Explanation

**High — chain-selection manipulation by an unprivileged peer.**

When Peras is enabled, an attacker with no keys or stake can:

1. Connect to a node as a normal peer via the Peras object-diffusion mini-protocol.
2. Send a crafted `PerasCert` claiming to boost any block currently in the node's VolatileDB (i.e., any block within the last *k* blocks).
3. The node accepts the certificate without any cryptographic check, stores it in `PerasCertDB`, and re-runs chain selection for the boosted block.
4. If the boosted block is on a fork, the node may switch to that fork because the Peras weight boost makes it heavier than the current selection, even if the fork is shorter or otherwise non-canonical.

This matches the allowed impact scope: *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

---

### Likelihood Explanation

**Medium.** Peras is disabled by default in the current release, which limits immediate exposure. However, the code is fully wired into the production `ChainDB` API and `ChainSel` thread. Any deployment that enables Peras (e.g., a private testnet, a future mainnet activation, or a node operator who enables the feature flag) is immediately vulnerable. The attack requires only a TCP connection to the node's Peras diffusion port — no keys, no stake, no prior relationship.

---

### Recommendation

1. **Do not ship `validatePerasCert` as a stub that always returns `Right`.** Replace it with a function that returns `Left PerasValidationErr` (reject all) until real validation is implemented. This is the safe default for unfinished cryptographic checks.
2. **Implement full certificate validation** using the concrete `PerasCert` type from `Peras/Cert/V1.hs`, verifying the aggregate BLS signature over `(pcRoundNo, pcBoostedBlock)` against the committee's aggregate public key, and checking that `pcVoters` are legitimate committee members with sufficient combined stake.
3. **Gate the object-diffusion writer behind the Peras feature flag** so that the inbound path is unreachable when Peras is disabled, providing defense-in-depth.

---

### Proof of Concept

**Attacker preconditions:** TCP access to a node with Peras enabled; no keys or stake required.

**Steps:**

1. Connect to the node's Peras object-diffusion endpoint.
2. Craft a `PerasCert` with:
   - `pcCertRound` = any round number not yet in the node's `PerasCertDB`.
   - `pcCertBoostedBlock` = the `Point` of a block on an attacker-controlled fork currently in the node's VolatileDB.
3. Send the certificate via the object-diffusion protocol.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }` unconditionally. [8](#0-7) 
5. The certificate is forwarded to `ChainDB.addPerasCertAsync`. [9](#0-8) 
6. `chainSelSync` adds the cert to `PerasCertDB`, retrieves the boosted block header from VolatileDB, and calls `chainSelectionForBlock` for it. [10](#0-9) 
7. Chain selection now compares the attacker's fork (with the injected Peras weight boost) against the current selection. If the boost is large enough, the node switches to the attacker's fork.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
