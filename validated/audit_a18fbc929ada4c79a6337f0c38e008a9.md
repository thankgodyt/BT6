### Title
`chain_signatures_account_id` Is Immutable After Deployment, Causing Permanent Withdrawal DOS If the MPC Contract Is Deprecated or Migrated — (File: `contracts/satoshi-bridge/src/config.rs`)

---

### Summary

The `chain_signatures_account_id` field in `Config` cannot be updated through the bridge's `ConfigUpdate` mechanism. If the NEAR chain-signatures MPC contract is deprecated, migrated to a new address, or becomes permanently unavailable, the bridge has no in-protocol path to redirect signing calls. All withdrawal flows that depend on `sign_promise` will fail permanently, leaving nBTC tokens locked in the bridge with no recovery path short of a full contract upgrade.

---

### Finding Description

`Config` stores three critical external contract addresses:

```rust
pub btc_light_client_account_id: AccountId,   // updatable
pub nbtc_account_id: AccountId,               // updatable
pub chain_signatures_account_id: AccountId,   // NOT updatable
``` [1](#0-0) 

`ConfigUpdate`, the only privileged mechanism for changing live configuration, exposes `btc_light_client_account_id` and `nbtc_account_id` as optional fields but omits `chain_signatures_account_id` entirely:

```rust
pub struct ConfigUpdate {
    pub btc_light_client_account_id: Option<AccountId>,
    pub nbtc_account_id: Option<AccountId>,
    // chain_signatures_account_id is absent
    ...
}
``` [2](#0-1) 

`ConfigUpdate::apply()` confirms the omission — `chain_signatures_account_id` is never written:

```rust
set_if_some!(btc_light_client_account_id);
set_if_some!(nbtc_account_id);
// no set_if_some!(chain_signatures_account_id)
``` [3](#0-2) 

Every withdrawal and refund signing call routes through `sign_promise`, which hard-reads the frozen address:

```rust
pub fn sign_promise(&self, request: SignRequest) -> Promise {
    let config = self.internal_config();
    ext_chain_signatures::ext(config.chain_signatures_account_id.clone())
        ...
        .sign(request)
}
``` [4](#0-3) 

The same frozen address is used for the root-public-key sync that derives the bridge's change address:

```rust
pub fn sync_chain_signatures_root_public_key_promise(&mut self) -> Promise {
    ext_chain_signatures::ext(self.internal_config().chain_signatures_account_id.clone())
        .public_key(None)
        ...
}
``` [5](#0-4) 

---

### Impact Explanation

If the chain-signatures contract at the frozen address stops responding (deprecation, migration, or permanent pause by NEAR governance):

1. **All new withdrawals** (`ft_transfer_call` → `ft_on_transfer` → `internal_sign_btc_transaction`) will fail at the `sign_promise` cross-contract call, leaving nBTC tokens transferred into the bridge with no BTC payout.
2. **All pending refunds** (`execute_refund` → `finalize_refund_with_psbt` → signing) will be permanently stuck in `PendingSign` state.
3. **The change-address derivation** (`sync_chain_signatures_root_public_key_promise`) will also fail, blocking any re-initialization.

There is no in-protocol escape hatch: `ConfigUpdate` cannot redirect the signing calls to a replacement contract. Recovery requires a full contract upgrade, which takes time and leaves user funds locked in the interim.

**Allowed impact matched:** Medium — stuck bridge state requiring operator intervention; attacker-triggered temporary (potentially permanent) locking of bridged funds.

---

### Likelihood Explanation

NEAR chain-signatures is an actively evolving MPC service. Contract migrations, version upgrades, or address changes are realistic operational events. The bridge's own `btc_light_client_account_id` and `nbtc_account_id` were explicitly made updatable, demonstrating the protocol authors anticipated the need to redirect external calls — the omission of `chain_signatures_account_id` is an inconsistency, not a design choice. Likelihood is low-to-medium: the event is not imminent but is plausible over the bridge's operational lifetime.

---

### Recommendation

Add `chain_signatures_account_id: Option<AccountId>` to `ConfigUpdate` and a corresponding `set_if_some!(chain_signatures_account_id)` line in `ConfigUpdate::apply()`, mirroring the treatment of `btc_light_client_account_id`. This gives the DAO a privileged, in-protocol path to redirect signing calls without requiring a full contract upgrade.

---

### Proof of Concept

1. Bridge is deployed with `chain_signatures_account_id = "v1.signer.near"`.
2. NEAR deploys a new MPC contract at `"v2.signer.near"` and deprecates `"v1.signer.near"`.
3. DAO calls `update_config` with a `ConfigUpdate` that does not include `chain_signatures_account_id` (because the field does not exist in the struct).
4. `config.chain_signatures_account_id` remains `"v1.signer.near"`.
5. Any user calling `ft_transfer_call` to initiate a withdrawal triggers `internal_sign_btc_transaction` → `sign_promise` → cross-contract call to the deprecated `"v1.signer.near"`, which fails.
6. `sign_btc_transaction_callback` receives a failed promise result and returns `false`; the withdrawal is permanently stuck in `PendingSign` state with no signing possible and no config-level fix available. [6](#0-5)

    pub fn internal_sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> Promise {
        let pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);

        let public_keys: Vec<_> = pending_info
            .vutxos
            .iter()
            .map(|vutxo| self.generate_btc_public_key(&vutxo.get_path()))
            .collect();

        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        require!(
            btc_pending_info.signatures[sign_index].is_none(),
            "Already signed"
        );
        let payload = btc_pending_info
            .get_psbt()
            .get_hash_to_sign(sign_index, &public_keys);
        let path = btc_pending_info.vutxos[sign_index].get_path();
        self.sign_promise(SignRequest {
            payload,
            path,
            key_version,
        })
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_SIGN_BTC_TRANSACTION_CALL_BACK)
                .sign_btc_transaction_callback(
                    btc_pending_info.account_id.clone(),
                    btc_pending_sign_id,
                    sign_index,
                ),
        )
    }
