### Title
`validatePerasCert` Unconditionally Accepts Any Peer-Supplied Peras Certificate, Enabling Adversarial Chain-Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` function is a stub that unconditionally returns `Right` for every certificate it receives, performing no cryptographic or semantic validation whatsoever. Because this function is the sole validation gate in the inbound Peras certificate diffusion path (`processCerts`), any unprivileged peer can inject an arbitrary `PerasCert` — with any `pcCertBoostedBlock` pointing to any block — and have it accepted as a `ValidatedPerasCert`. The accepted certificate is then stored in the `PerasCertDB`, its boosted block is added to the `PerasWeightSnapshot`, and chain selection is re-triggered for that block. This allows an adversary to artificially inflate the Peras weight of a block on a non-canonical fork, causing an honest node to prefer and switch to that fork.

---

### Finding Description

The `BlockSupportsPeras` class defines `validatePerasCert` as the mandatory validation gate before a certificate is accepted into the node's state. The only deployed instance — the default instance for `StandardHash blk` — implements this function as a pass-through stub:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No BLS aggregate signature check, no committee membership check, no round-number plausibility check, and no boosted-block existence check is performed. The function always returns `Right`.

This stub is wired directly into the production inbound certificate processing path. `makePerasCertPoolWriterFromChainDB` — the writer used by the live node kernel — passes `validatePerasCert mkPerasParams` as the validation callback to `processCerts`:

```haskell
(validatePerasCert mkPerasParams)
``` [2](#0-1) 

`processCerts` calls `validateCert` on every new certificate received from a peer, and if all pass (which they always do), adds them via `addCert`: [3](#0-2) 

The accepted `ValidatedPerasCert` is then stored in the `PerasCertDB`. The `implGetWeightSnapshot` function builds the `PerasWeightSnapshot` directly from all stored certificates:

```haskell
mkPerasWeightSnapshot
  [ (getPerasCertBoostedBlock cert, getPerasCertBoost cert)
  | cert <- Map.elems (pcdsCertsByTicket pcds)
  ]
``` [4](#0-3) 

Chain selection then uses `weightedSelectView` to compute `wsvTotalWeight = blockNo + wsvWeightBoost`, where `wsvWeightBoost` is the sum of all Peras boosts for blocks on the candidate fragment: [5](#0-4) 

A candidate chain containing the adversarially-boosted block will appear heavier than the honest chain by `perasWeight params` (the full configured Peras boost weight), causing `preferCandidate` to return `ShouldSwitch`.

Furthermore, `chainSelSync` explicitly re-triggers `chainSelectionForBlock` for the boosted block upon receiving a new certificate: [6](#0-5) 

---

### Impact Explanation

**High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain.**

An adversary who is a connected peer can send a crafted `PerasCert` whose `pcCertBoostedBlock` points to a block on an adversarial fork. Because `validatePerasCert` never rejects any certificate, the fake cert is accepted, stored, and its boost is applied to the weight snapshot. Chain selection then re-evaluates candidates using the inflated weight, and if the adversarial fork's total weight (`blockNo + perasWeight`) exceeds the honest chain's weight, the node switches to the adversarial fork. This constitutes a consensus safety failure: an honest node accepts and adopts a non-canonical chain based on a fabricated certificate, without any stake majority or key compromise by the attacker.

---

### Likelihood Explanation

The Peras certificate diffusion mini-protocol is a production network-facing protocol. Any peer that establishes a connection to the node can send `PerasCert` objects. The attack requires:
- A network connection to the target node (standard peer connectivity).
- Knowledge of a block hash on any fork visible to the target node (obtainable from the chain sync protocol).
- No cryptographic keys, no stake, no operator access.

The only partial mitigations are: (1) the certificate is ignored if `pointSlot boostedBlock < AF.anchorToSlotNo immTip` (too old), and (2) chain selection only switches if the boosted block is actually present in the VolatileDB. However, condition (2) is easily satisfied — the adversary can first deliver the adversarial block via the block fetch protocol (which stores it in the VolatileDB even if not yet selected), then deliver the fake certificate.

---

### Recommendation

Implement real certificate validation in `validatePerasCert`. At minimum, the function must verify:
1. The BLS aggregate signature over the certificate covers the claimed `pcCertBoostedBlock` and `pcCertRound`.
2. The signers are members of the Peras committee for `pcCertRound` (verified against the stake distribution snapshot for that round).
3. The aggregate stake of the signers meets the quorum threshold.
4. `pcCertRound` is plausible given the current chain tip (not arbitrarily far in the future or past).

Until real validation is implemented, the inbound certificate diffusion path (`makePerasCertPoolWriterFromChainDB`) should not be enabled in production nodes, or should be gated behind a feature flag that is off by default.

---

### Proof of Concept

**Attacker-controlled entry path:**

1. Adversary connects to an honest node as a peer via the Peras object-diffusion mini-protocol.
2. Adversary has previously delivered (via block fetch) a block `B_adv` on a fork that is currently shorter than the honest chain by `D` blocks.
3. Adversary sends a single `PerasCert { pcCertRound = R, pcCertBoostedBlock = blockPoint B_adv }`.
4. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })` unconditionally. [7](#0-6) 
5. The cert is added to `PerasCertDB`; `implGetWeightSnapshot` now includes `(blockPoint B_adv, perasWeight params)` in the snapshot. [4](#0-3) 
6. `chainSelSync` calls `chainSelectionForBlock` for `B_adv`. [6](#0-5) 
7. Chain selection computes `wsvTotalWeight(adv_fork) = blockNo(B_adv) + perasWeight`. If `perasWeight > D`, the adversarial fork is now preferred. [8](#0-7) 
8. The honest node switches to the adversarial fork.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
