### Title
Unconditional Peras Certificate Acceptance Enables Unprivileged Chain Selection Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate catch-all `BlockSupportsPeras` instance unconditionally accepts every inbound Peras certificate as valid, performing no cryptographic or structural checks. Because this stub is wired directly into the production inbound-certificate pipeline, any unprivileged peer can send a crafted `PerasCert` that the node accepts, stores, and uses to artificially boost a block's chain-selection weight by `perasWeight = 15` blocks, potentially causing the node to switch to a fork it would otherwise reject.

---

### Finding Description

**Root cause — stub validation always returns `Right`**

The `BlockSupportsPeras` type class declares `validatePerasCert` as the gate that must approve every certificate before it enters the node's state. The only instance currently in the codebase is a degenerate catch-all:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature, quorum, voter-eligibility, or round-number check is performed. Every certificate is stamped `ValidatedPerasCert` and assigned the full `perasWeight` boost unconditionally.

**Wiring into the production inbound pipeline**

`makePerasCertPoolWriterFromChainDB` — the handler invoked for every batch of certificates received from a peer over the ObjectDiffusion mini-protocol — passes this stub directly as the validator:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` then calls this validator for every new certificate and, on success, forwards it to `ChainDB.addPerasCertAsync`: [3](#0-2) 

**Chain-selection side-effect**

`chainSelSync` processes the queued certificate. If the boosted block is present in the VolatileDB, it immediately calls `chainSelectionForBlock` with the updated `PerasWeightSnapshot`:

```haskell
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

`constructPreferableCandidates` then uses `preferAnchoredCandidate bcfg weights curChain`, where `weights` now carries the attacker-injected boost, to decide whether to switch chains: [5](#0-4) 

The default `perasWeight = 15` means a single fake certificate makes a fork appear 15 blocks heavier than it actually is: [6](#0-5)

### Impact Explanation

An unprivileged peer can craft a `PerasCert` naming any block in the target node's VolatileDB. Because `validatePerasCert` never rejects anything, the certificate is accepted, stored, and used to give that block's chain a 15-block artificial weight advantage. This lets the attacker cause the honest node to prefer a fork that is up to 15 blocks shorter than the canonical chain — a direct violation of Peras chain-selection security. This matches the **High** impact category: a chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.

---

### Likelihood Explanation

The attack path requires only a standard peer connection over the ObjectDiffusion mini-protocol, which is open to any node on the network. The attacker needs only the hash of a block in the target's VolatileDB, which is observable via ChainSync. No key material, stake, or elevated privilege is needed. The attack is deterministic and repeatable.

---

### Recommendation

Implement real cryptographic validation inside `validatePerasCert`: verify the aggregate BLS signature over `(roundNo, boostedBlock)`, check each voter's eligibility proof (VRF output for non-persistent members, persistent-committee membership for persistent members), confirm the quorum threshold is met, and reject certificates whose `pcCertRound` is outside the valid window. The existing `WFALS.implVerifyCert` and `EveryoneVotes.implVerifyCert` functions already contain the correct verification logic and should be plumbed through to the `BlockSupportsPeras` instance for `CardanoBlock`. The TODO at issue #120 tracks this work and must be resolved before Peras is enabled on any network where peers are untrusted.

---

### Proof of Concept

1. Attacker connects to a target node via the ObjectDiffusion mini-protocol (no credentials required).
2. Attacker learns the `HeaderHash` of a block on a competing fork via ChainSync.
3. Attacker constructs `PerasCert { pcCertRound = r, pcCertBoostedBlock = forkTip }` for any round `r` and any block point `forkTip` in the VolatileDB.
4. Attacker sends the certificate in a batch to the target node.
5. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{..}` unconditionally. [7](#0-6) 
6. The certificate is forwarded to `addPerasCertAsync` and enqueued. [8](#0-7) 
7. `chainSelSync` finds `forkTip` in the VolatileDB and calls `chainSelectionForBlock` with a `PerasWeightSnapshot` that now includes a +15-block boost for `forkTip`'s chain. [9](#0-8) 
8. If the fork is within 15 blocks of the current tip, `preferAnchoredCandidate` returns `ShouldSwitch` and the node adopts the attacker-chosen fork.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime

    ([], validatedCerts) ->
      mapM_
