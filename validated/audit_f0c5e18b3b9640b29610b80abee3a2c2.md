### Title
Dust-Level Refund Amount Creates Permanently Stuck `BTCPendingInfo` With No Incentive to Finalize — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

When a refund request results in a `refund_amount` below Bitcoin's dust limit after gas-fee deduction, the refund BTC transaction cannot be broadcast to the Bitcoin network. No relayer has economic incentive to call `verify_refund_finalize`. The `BTCPendingInfo` and `RefundRequest` (with `executed = true`) remain permanently stuck in contract storage, the deposit UTXO is permanently marked as verified (blocking future `verify_deposit`), and the user's BTC becomes inaccessible through the bridge without operator intervention.

---

### Finding Description

**Root cause 1 — `request_refund_callback` (refund.rs:549–553):**

```rust
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
```

The only guard is `gas_fee < amount`. There is no minimum `refund_amount` check. If `amount = max_btc_gas_fee + 1`, the stored `refund_amount` is 1 satoshi.

**Root cause 2 — `refund_execution_inputs` (refund.rs:280–284):**

```rust
let refund_amount = refund_request
    .amount
    .checked_sub(refund_request.gas_fee)
    .expect("Deposit amount too small to cover gas fee");
require!(refund_amount > 0, "Refund amount is zero after gas fee");
```

Only `refund_amount > 0` is enforced. There is no check against Bitcoin's dust limit (~294–546 satoshis for P2WPKH at typical fee rates). A 1-satoshi output passes this check but produces a non-standard transaction that Bitcoin nodes will reject.

**Consequence — `finalize_refund_with_psbt` (refund.rs:315–401):**

When `execute_refund` (callable by anyone after the timelock) proceeds with a dust `refund_amount`:

1. A `BTCPendingInfo` is created in `PendingSign` state.
2. The deposit UTXO is permanently inserted into `verified_deposit_utxo`, blocking any future `verify_deposit` for that UTXO.
3. The `RefundRequest` is kept with `executed = true`.

The resulting refund BTC transaction carries a dust output and is non-standard. No relayer will broadcast it or call `verify_refund_finalize`. The state machine has no timeout or self-cleanup path for this case — it is the exact "no incentive to write off bad debt" pattern from M-13.

**Partial operator recovery is incomplete:**

`reject_refund` removes the `RefundRequest` from `refund_requests`, and `remove_refund_pending_tx_id` can then remove the `BTCPendingInfo`. However, neither function removes the entry from `verified_deposit_utxo`. The UTXO remains permanently blocked, so the user's BTC at the deposit address is inaccessible through the bridge even after operator cleanup.

---

### Impact Explanation

**Medium — stuck bridge state requiring operator intervention.**

- The deposit UTXO is permanently marked as verified, blocking `verify_deposit` for that UTXO forever.
- The `BTCPendingInfo` occupies one of the user's limited pending-sign slots, reducing capacity for future withdrawals until an operator manually cleans it up.
- Even after operator cleanup (`reject_refund` + `remove_refund_pending_tx_id`), the `verified_deposit_utxo` entry is never removed, so the user's BTC remains inaccessible through the bridge.
- The user's BTC (small but real) is permanently locked with no protocol-level recovery path.

---

### Likelihood Explanation

**Low.** The scenario requires a user to deposit an amount just above `max_btc_gas_fee` to a deposit address (e.g., `max_btc_gas_fee + 1` satoshis). This is an unusual but fully reachable on-chain action — anyone can send any amount of BTC to a bridge deposit address. The `request_refund` and `execute_refund` calls are both publicly accessible (no role restriction after the timelock). The scenario becomes more likely if `max_btc_gas_fee` is set high relative to `min_deposit_amount`, or during periods of high BTC network fees when the operator raises `max_btc_gas_fee`.

---

### Recommendation

Add a minimum refund amount check in `request_refund_callback` to ensure the net `refund_amount` is above a configurable dust threshold (e.g., `min_change_amount` or a dedicated `min_refund_amount` config parameter):

```rust
let refund_amount = amount.checked_sub(resolved_gas_fee)
    .expect("gas fee exceeds amount");
require!(
    refund_amount >= u128::from(config.min_change_amount),
    "Refund amount after gas fee is below dust threshold"
);
```

This prevents `execute_refund` from ever constructing a non-broadcastable BTC transaction and avoids the permanently stuck state.

---

### Proof of Concept

**Setup:** `max_btc_gas_fee = 1000 sat`, `min_deposit_amount = 10_000 sat`, `min_change_amount = 546 sat`.

1. User sends **1001 satoshis** to a bridge deposit address on Bitcoin.
2. Relayer calls `verify_deposit` → fails: `1001 < min_deposit_amount (10_000)`. No nBTC is minted.
3. User calls `request_refund` with the deposit tx bytes and proof.
   - `request_refund_callback`: `resolved_gas_fee = 1000`, check `1000 < 1001` passes. `RefundRequest` stored with `amount = 1001`, `gas_fee = 1000`.
4. After the timelock, anyone calls `execute_refund(utxo_storage_key, None)`.
   - `refund_execution_inputs`: `refund_amount = 1001 - 1000 = 1`. Check `1 > 0` passes.
   - `finalize_refund_with_psbt`: `BTCPendingInfo` created with `actual_received_amount = 1`. `verified_deposit_utxo.insert(utxo_storage_key)` executes. `RefundRequest.executed = true`.
5. The refund PSBT contains a 1-satoshi P2WPKH output — below Bitcoin's dust limit. Bitcoin nodes reject the transaction as non-standard.
6. No relayer broadcasts the transaction. No relayer calls `verify_refund_finalize`.
7. **Stuck state:** `BTCPendingInfo` in `PendingSign` forever; `RefundRequest` with `executed = true` forever; deposit UTXO permanently in `verified_deposit_utxo`.
8. Operator calls `reject_refund` → removes `RefundRequest`. Operator calls `remove_refund_pending_tx_id` → removes `BTCPendingInfo`. But `verified_deposit_utxo` still contains the key.
9. User's 1001 satoshis remain at the deposit address on Bitcoin but are permanently inaccessible through the bridge. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
