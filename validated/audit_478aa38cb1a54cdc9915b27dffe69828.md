Audit Report

## Title
Unvalidated BTC/Zcash Destination Address Permanently Locks User Tokens in NEAR Bridge - (File: `near/omni-types/src/lib.rs`)

## Summary
`OmniAddress::Btc` and `OmniAddress::Zcash` accept any arbitrary string as an address with no format validation, while all EVM, Solana, Starknet, and NEAR variants enforce structural parsing. A user who supplies a malformed BTC or Zcash address when initiating a NEAR → UTXO transfer will have their tokens burned/locked in the bridge contract with no on-chain recovery path, constituting permanent freezing of bridged funds.

## Finding Description
`UTXOChainAddress` is a plain `String` alias (`near/omni-types/src/lib.rs:171`). In `OmniAddress::from_str`, the `"btc"` and `"zcash"` arms call `recipient.to_string()` with no validation, while every other chain variant calls `.parse()` which enforces structural constraints (`near/omni-types/src/lib.rs:405-406`).

`init_transfer` (`near/omni-bridge/src/lib.rs:523-557`) applies only one guard on the recipient: that the destination chain is not `ChainKind::Near`. No address format check is performed. `init_transfer_internal` then calls `burn_tokens_if_needed` and `lock_tokens_if_needed` (`near/omni-bridge/src/lib.rs:1850-1857`), permanently removing the tokens from the user's balance and recording the transfer in `pending_transfers`.

The only path to progress a NEAR → UTXO transfer is `submit_transfer_to_utxo_chain_connector` (`near/omni-bridge/src/btc.rs:29`), which is gated by the `#[trusted_relayer]` macro. A relayer that attempts to submit a transfer with an invalid address will be rejected by the UTXO connector; the callback at `near/omni-bridge/src/btc.rs:111-126` re-inserts the transfer into `pending_transfers` on failure. If no relayer ever attempts submission (the rational behavior for a known-invalid address), the transfer remains in `pending_transfers` indefinitely.

A grep across `near/omni-bridge/src/` confirms no `pub fn cancel`, `pub fn refund`, or equivalent user-callable recovery function exists. The asymmetry is explicit: EVM addresses are validated by `H160::parse()`, NEAR addresses by `AccountId::parse()`, Solana by `SolAddress::parse()`, Starknet by `H256::parse()` — but BTC and Zcash accept any string.

## Impact Explanation
This directly matches the allowed critical impact: **permanent freezing of bridged funds**. Tokens are burned or locked on NEAR and never delivered on the UTXO chain. The locked amount is removed from circulation with no on-chain mechanism for the user to reclaim it. The impact is concrete and irreversible.

## Likelihood Explanation
The attack surface is fully user-controlled and requires no special role or privilege. Any user calling `ft_transfer_call` with a malformed `OmniAddress::Btc` or `OmniAddress::Zcash` recipient triggers the lock. Accidental mistyping (wrong prefix, wrong character set, truncated address, copy-paste error) is a realistic scenario for ordinary users. The inconsistency with other chains — where invalid input is rejected at parse time — makes this especially dangerous, as users familiar with the bridge's behavior on EVM chains would not expect silent acceptance of invalid UTXO addresses.

## Recommendation
Add format validation inside `OmniAddress::from_str` for the `"btc"` and `"zcash"` arms before constructing the variant. At minimum:
- **BTC**: Enforce Bech32/Bech32m prefix (`bc1`, `tb1`), valid character set, and length bounds per BIP-173 (max 90 chars).
- **Zcash**: Enforce prefix check (`t1`, `t3`, `zs`, `u`) and length bounds per ZIP-316 for Unified Addresses.

As defense-in-depth, add a user-callable `cancel_pending_transfer` function that allows the original sender to reclaim tokens from a transfer that has remained in `pending_transfers` beyond a configurable timeout.

## Proof of Concept
1. User holds wrapped BTC tokens (`nbtc.bridge.near`) on NEAR.
2. User calls `ft_transfer_call` on `nbtc.bridge.near`:
   ```json
   {
     "receiver_id": "omni-bridge.near",
     "amount": "100000",
     "msg": "{\"InitTransfer\":{\"recipient\":\"btc:NOTAVALIDADDRESS!!!\",\"fee\":\"0\",\"native_token_fee\":\"0\"}}"
   }
   ```
3. `OmniAddress::from_str("btc:NOTAVALIDADDRESS!!!")` succeeds, returning `OmniAddress::Btc("NOTAVALIDADDRESS!!!")`.
4. `init_transfer` passes the only guard (`recipient.get_chain() != ChainKind::Near` → true for `Btc`).
5. `init_transfer_internal` burns/locks 100,000 units and inserts the transfer into `pending_transfers`.
6. No trusted relayer will successfully submit this transfer — the UTXO connector rejects the invalid address; the callback re-inserts it on failure.
7. No `cancel_transfer` or equivalent function exists on-chain.
8. The 100,000 units are permanently frozen in the bridge.

A local integration test can be written following the pattern in `near/omni-tests/src/zcash_stale_transfer_poc.rs`, substituting a syntactically invalid address (e.g., `"btc:NOTAVALIDADDRESS!!!"`) and asserting that after `init_transfer` completes, the user's token balance is reduced and no recovery path exists.
