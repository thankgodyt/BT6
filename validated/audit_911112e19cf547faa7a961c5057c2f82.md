### Title
Refund `gas_fee` is caller-supplied without onchain bounds validation, bypassing configured fee policy and enabling stuck refund transactions - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
The `gas_fee` parameter in `request_refund` is accepted from any unprivileged caller and stored without validation against the protocol's configured `min_btc_gas_fee`/`max_btc_gas_fee` bounds. The withdrawal path enforces these bounds onchain; the refund path does not. A caller can set `gas_fee = 0`, producing a zero-fee Bitcoin refund transaction that miners will never include, permanently locking the user's funds in a stuck state requiring operator intervention.

### Finding Description
In `request_refund_callback`, the resolved `gas_fee` is only checked to be strictly less than the deposit amount:

```rust
// refund.rs:549-553
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
```

No check against `config.min_btc_gas_fee` or `config.max_btc_gas_fee` is performed. The withdrawal path in `check_psbt_output_all_change_address` enforces exactly these bounds:

```rust
// psbt.rs:153-159
require!(
    gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee,
    format!(
        "Invalid gas fee ({}). valid range: [{}, {}].",
        gas_fee, config.min_btc_gas_fee, config.max_btc_gas_fee
    )
);
```

The stored `gas_fee` is later consumed in `refund_execution_inputs` to compute the refund amount:

```rust
// refund.rs:280-284
let refund_amount = refund_request
    .amount
    .checked_sub(refund_request.gas_fee)
    .expect("Deposit amount too small to cover gas fee");
require!(refund_amount > 0, "Refund amount is zero after gas fee");
```

No fee-bound validation occurs here either. The refund Bitcoin transaction is built with `refund_amount` as the sole output via `build_refund_output`, making the implicit miner fee equal to `gas_fee`. If `gas_fee = 0`, the transaction carries no fee and will not be mined. If `gas_fee` is set near the deposit amount, the user receives near-zero BTC.

`request_refund` is publicly callable by any account that attaches sufficient NEAR for storage — there is no role check. The only protection against a malicious `gas_fee` is the 14-day `unsafe_refund_timelock_sec` and the DAO's ability to call `reject_refund` — a trust-based, offchain mitigation with no onchain fee-bound enforcement, directly analogous to the original finding's trust gap.

### Impact Explanation
Medium. This is a bypass of bridge fee limits and policies. Setting `gas_fee = 0` produces a zero-fee Bitcoin transaction that miners will not include, permanently locking the user's refund in a stuck state requiring operator intervention. Setting `gas_fee` near the deposit amount causes the user to receive near-zero BTC. Both outcomes deviate from the protocol's configured fee policy without any onchain enforcement, and recovery requires privileged operator action.

### Likelihood Explanation
Low. The attacker must front-run the legitimate user's `request_refund` call (only one refund request can exist per UTXO due to the duplicate check at refund.rs:544-547), attach a NEAR storage deposit, and know the deposit transaction details (which are public on Bitcoin). The DAO has 14 days to reject the malicious request, but this relies entirely on offchain monitoring and trusted operator action — the same trust gap identified in the original report.

### Recommendation
In `request_refund_callback`, validate the resolved `gas_fee` against the configured bounds before storing the refund request, mirroring the enforcement already applied to withdrawal PSBTs:

```rust
let config = self.internal_config();
require!(
    resolved_gas_fee >= config.min_btc_gas_fee && resolved_gas_fee <= config.max_btc_gas_fee,
    format!(
        "Gas fee ({}) out of valid range [{}, {}]",
        resolved_gas_fee, config.min_btc_gas_fee, config.max_btc_gas_fee
    )
);
```

This removes the reliance on offchain operator intervention to enforce fee policy and establishes a trustless onchain connection between the configured fee bounds and the refund path.

### Proof of Concept
1. User deposits 100,000 satoshis to a bridge address derived from a `DepositMsg` with `refund_address: None`. The deposit is confirmed on Bitcoin but cannot be finalized (e.g., below `min_deposit_amount`).
2. Attacker observes the deposit on Bitcoin and calls `request_refund` with the correct `deposit_msg`, `refund_address = attacker_btc_address`, `gas_fee = Some(0)`, and sufficient NEAR attached for storage.
3. The light client verifies transaction inclusion; `request_refund_callback` stores the request with `gas_fee = 0` — passing the only check (`0 < 100_000`).
4. If the DAO does not call `reject_refund` within 14 days, the attacker calls `execute_refund` after the timelock.
5. `refund_execution_inputs` computes `refund_amount = 100_000 - 0 = 100_000`. `build_refund_output` builds a Bitcoin transaction paying 100,000 satoshis to the attacker's address with 0 miner fee.
6. The zero-fee transaction is broadcast but never confirmed by miners, permanently locking the user's 100,000 satoshis in a stuck state. The `verified_deposit_utxo` set is marked, blocking any future `verify_deposit` for this UTXO. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");

            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
    }
