### Title
Zcash Re-execution with Different Orchard Bundle Creates Multiple `BTCPendingInfo` for the Same Deposit UTXO — (`contracts/satoshi-bridge/src/refund.rs` + `zcash_utils/refund.rs`)

### Summary

After a first `execute_refund` succeeds for a Zcash refund request, the `executed=true` flag intentionally allows any caller to invoke `execute_refund` again. On Bitcoin this is harmless because the txid is deterministic. On Zcash, a different `orchard_bundle_bytes` produces a different Zcash txid, so the duplicate-insert guard (`"pending info already exist"`) does not fire, and a second `BTCPendingInfo` is created for the same deposit UTXO.

### Finding Description

**Step 1 — Guard that allows re-execution.**

`load_refund_request_for_execute` in `contracts/satoshi-bridge/src/refund.rs` lines 254-258:

```rust
require!(
    !self.data().verified_deposit_utxo.contains(utxo_storage_key)
        || refund_request.executed,
    "UTXO already verified via deposit, cannot refund"
);
```

When `executed == true` (set by the first successful call), the condition `!true || true` evaluates to `true`, so the check passes unconditionally for any subsequent caller. [1](#0-0) 

**Step 2 — `btc_pending_id` is derived from the Zcash txid, which includes the Orchard bundle.**

`PsbtWrapper::get_pending_id` calls `get_zcash_tx().compute_txid()`. The Zcash txid commits to the Orchard bundle via the transaction digest. Two different valid bundles that both pay `refund_amount` to `refund_address` produce two different txids. [2](#0-1) 

**Step 3 — The only duplicate guard is keyed on `btc_pending_id`.**

`finalize_refund_with_psbt` in `contracts/satoshi-bridge/src/refund.rs` lines 366-372:

```rust
require!(
    self.data_mut()
        .btc_pending_infos
        .insert(btc_pending_id.clone(), btc_pending_info.into())
        .is_none(),
    "pending info already exist"
);
```

Because `btc_pending_id_B ≠ btc_pending_id_A`, the insert succeeds and a second `BTCPendingInfo` is stored. [3](#0-2) 

**Step 4 — The `require_pending_sign_capacity` check does NOT block a different-account attacker.**

The default `max_pending_sign_txs` is 1 (confirmed in test setup at `context.rs:213`). After Account A's first execution, Account A's `btc_pending_sign_ids` has 1 entry, so a second call by Account A is blocked by the capacity check at line 342. However, Account B starts with 0 pending entries, so the capacity check passes for Account B. Account B can call `execute_refund` with `bundle_B` and successfully create `BTCPendingInfo_B`. [4](#0-3) [5](#0-4) 

**Step 5 — Stale entries cannot be cleaned up until finalization.**

`internal_remove_refund_pending_tx_id` requires the refund request to be absent (`!refund_requests.contains_key(...)`), which only happens after `verify_refund_finalize_callback` confirms one of the transactions on-chain. Until then, all stale `BTCPendingInfo` entries are stuck. [6](#0-5) 

**Step 6 — The Bitcoin test explicitly documents that the same-txid guard is the protection, but Zcash breaks this assumption.**

The test comment at `test_refund.rs:1484-1488` states: "once past the timelock it rebuilds the identical tx (same id), so the insert is rejected." This is true for Bitcoin but false for Zcash with a different Orchard bundle. [7](#0-6) 

### Impact Explanation

- Multiple `BTCPendingInfo` entries exist for the same deposit UTXO, each owned by a different account and each representing a distinct signed Zcash transaction.
- Each can be submitted to the Zcash network; only one can confirm (the UTXO can only be spent once).
- The losing entries are stuck in contract state until the winning transaction is finalized on-chain and `verify_refund_finalize_callback` removes the refund request.
- MPC signing resources are wasted for each duplicate entry.
- No direct fund theft is possible; the Zcash network enforces single-spend.

This matches the **Medium** impact category: broken callback/state invariant and stuck bridge state requiring operator intervention.

### Likelihood Explanation

- `execute_refund` is a public, payable function with no role gate.
- After the first execution, any account can call it again with a different valid Orchard bundle.
- Constructing a valid Orchard bundle that passes `validate_orchard_bundle` (correct recipient, correct amount) requires Orchard cryptographic knowledge but is feasible for a motivated attacker.
- The attacker only needs to pay the NEAR storage deposit for `execute_refund`.

### Recommendation

In `finalize_refund_with_psbt`, before inserting the new `BTCPendingInfo`, check whether a `BTCPendingInfo` already exists for the same deposit UTXO (e.g., by storing a mapping from `utxo_storage_key` to `btc_pending_id`). If one exists and the caller is re-executing, remove the old entry first (or reject the re-execution if the old entry is still in `PendingSign` state and has not expired). This ensures at most one live `BTCPendingInfo` per deposit UTXO at any time.

### Proof of Concept

```
1. Alice calls request_refund(utxo_key, ...) → RefundRequest stored, executed=false
2. Timelock passes
3. Alice calls execute_refund(utxo_key, bundle_A)
   → execute_refund_callback fires
   → load_refund_request_for_execute: executed=false, verified_deposit_utxo empty → passes
   → finalize_refund_with_psbt: inserts BTCPendingInfo_A (txid_A), sets executed=true,
     inserts utxo_key into verified_deposit_utxo
4. Bob calls execute_refund(utxo_key, bundle_B)  [bundle_B ≠ bundle_A, same recipient/amount]
   → execute_refund_callback fires
   → load_refund_request_for_execute: verified_deposit_utxo contains utxo_key BUT executed=true
     → condition !true || true = true → PASSES
   → require_pending_sign_capacity(Bob): Bob has 0 pending → PASSES
   → finalize_refund_with_psbt: btc_pending_id_B = txid(bundle_B) ≠ txid_A
     → insert(btc_pending_id_B, ...) returns None (no collision) → PASSES
     → BTCPendingInfo_B inserted
5. Assert: btc_pending_infos contains both txid_A and txid_B for the same deposit UTXO
   → Invariant violated: two refund transactions for one UTXO
```
