Audit Report

## Title
Inverted Success/Failure Check in `submit_transfer_to_btc_connector_callback` Causes Permanent Fund Loss on BTC Withdrawal Failure - (File: near/omni-bridge/src/btc.rs)

## Summary

`submit_transfer_to_btc_connector_callback` in `near/omni-bridge/src/btc.rs` uses an inverted condition to distinguish BTC withdrawal success from failure. Under NEP-141, `ft_transfer_call` returns the number of tokens **not consumed** (refunded). The callback treats `result.0 > 0` (tokens returned = failure) as the success branch and sends the relayer fee, while treating `result.0 == 0` (all tokens consumed = success) as the failure branch and re-inserting the transfer record. On any BTC withdrawal failure, the returned tokens are permanently stranded in the bridge with no associated transfer record, causing irreversible loss of user funds.

## Finding Description

In `submit_transfer_to_utxo_chain_connector`, the bridge sends `amount - fee` tokens to the BTC connector via `ft_transfer_call` and removes the transfer record before the call: [1](#0-0) [2](#0-1) 

The callback that follows: [3](#0-2) 

Under NEP-141, `ft_transfer_call` returns the amount of tokens **not consumed** by the receiver:
- `Ok(result) if result.0 == 0` → all tokens consumed → **BTC withdrawal succeeded**
- `Ok(result) if result.0 > 0` → tokens returned → **BTC withdrawal failed**

The condition `matches!(call_result, Ok(result) if result.0 > 0)` matches the **failure** case, yet the code calls `send_fee_internal` in this branch, paying the relayer fee. The **success** case (`result.0 == 0`) falls into the `else` branch and re-inserts the transfer message via `add_transfer_message`, even though the BTC withdrawal already completed and the tokens were forwarded to the connector.

Compare with the correct pattern in `fin_transfer_send_tokens_callback`, where the refund/failure path reverts state and the success path sends the fee: [4](#0-3) 

`send_fee_internal` transfers `token_fee` tokens from the bridge's balance to the fee recipient: [5](#0-4) 

## Impact Explanation

**On BTC withdrawal failure** (`result.0 > 0`, tokens returned to bridge):
1. The bridge receives back `amount - fee` tokens from the connector.
2. `send_fee_internal` is called, transferring `fee` tokens to the relayer from the bridge's held balance — even though the withdrawal failed.
3. The transfer record is **not restored**. The `amount - fee` returned tokens sit in the bridge with no associated transfer record and no recovery path.
4. The user permanently loses `amount - fee` tokens.

**On BTC withdrawal success** (`result.0 == 0`, all tokens consumed):
1. The transfer record is re-inserted into storage via `add_transfer_message`.
2. The fee is **not** paid to the relayer.
3. A ghost transfer record exists for a transfer whose tokens have already been forwarded. Any subsequent call to `submit_transfer_to_utxo_chain_connector` on this ghost record will fail because the bridge no longer holds the tokens, but the record persists and wastes storage.

The primary critical impact is **permanent freezing of bridged funds** for all BTC/Zcash UTXO chain withdrawals that fail at the connector level, matching the allowed impact class: *permanent freezing of bridged funds across Bitcoin/Zcash*.

## Likelihood Explanation

BTC withdrawals can fail for entirely legitimate, non-adversarial reasons: invalid or already-spent UTXOs, connector-side gas fee limits exceeded, network congestion, or connector contract bugs. The trigger path goes through `submit_transfer_to_utxo_chain_connector` (a trusted relayer flow, explicitly listed as a valid trigger path), and the fund loss is caused by the inverted callback logic — not by any malicious action from the relayer. The user who initiated the transfer has no ability to prevent or recover from this. The code path is live for all BTC and Zcash UTXO chain transfers.

## Recommendation

Invert the condition so that the fee is sent on success (`result.0 == 0`) and the transfer is restored on failure (`result.0 > 0` or `Err`):

```rust
pub fn submit_transfer_to_btc_connector_callback(
    &mut self,
    transfer_msg: TransferMessage,
    transfer_owner: AccountId,
    fee_recipient: AccountId,
    #[callback_result] call_result: &Result<U128, PromiseError>,
) -> PromiseOrValue<()> {
-   if matches!(call_result, Ok(result) if result.0 > 0) {
+   if matches!(call_result, Ok(result) if result.0 == 0) {
        let token_fee = transfer_msg.fee.fee.0;
        self.send_fee_internal(&transfer_msg, fee_recipient, token_fee)
    } else {
        let required_storage_balance =
            self.add_transfer_message(transfer_msg, transfer_owner.clone());
        self.update_storage_balance(
            transfer_owner,
            required_storage_balance,
            NearToken::from_yoctonear(0),
        );
        PromiseOrValue::Value(())
    }
}
```

## Proof of Concept

1. User holds wrapped BTC on NEAR and initiates a BTC withdrawal via `ft_transfer_call` to the bridge, creating a `TransferMessage` with `amount = 1_000_000` and `fee.fee = 10_000`.
2. A trusted relayer calls `submit_transfer_to_utxo_chain_connector`. The bridge removes the transfer record and calls `ft_transfer_call(connector, 990_000, ...)`.
3. The BTC connector's `ft_on_transfer` fails (e.g., UTXO already spent) and returns `990_000` (all tokens refunded to bridge).
4. `submit_transfer_to_btc_connector_callback` is invoked with `Ok(U128(990_000))`.
5. The condition `result.0 > 0` is true → `send_fee_internal` is called, transferring `10_000` tokens to the relayer.
6. The transfer record is **not** restored. The `990_000` returned tokens sit in the bridge with no associated record and no recovery mechanism.
7. The user has permanently lost `990_000` tokens.

A unit test can reproduce this by calling `submit_transfer_to_btc_connector_callback` directly with a mock `call_result` of `Ok(U128(990_000))` and asserting that: (a) the transfer record is re-inserted (currently fails — it is not), and (b) the fee is not sent to the relayer (currently fails — it is sent). The existing integration test in `near/omni-tests/src/btc_storage_fix.rs` tests the storage balance preservation path but does not assert the fee accounting or token recovery correctness. [6](#0-5)
