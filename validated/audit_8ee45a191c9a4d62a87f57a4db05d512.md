### Title
Chain-Sync Client Ignores Peras Weight Boosts in Forecast-Horizon Disconnect Check - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

### Summary

`checkPreferTheirsOverOurs` in the ChainSync client unconditionally passes `emptyPerasWeightSnapshot` to `preferAnchoredCandidate` when deciding whether to disconnect from a peer whose headers are beyond the forecast horizon. This mirrors the external report's pattern exactly: a guard condition causes important state (Peras weight boosts) to be silently omitted from a critical comparison, leading to incorrect chain-selection decisions.

### Finding Description

When a header from an upstream peer is beyond the forecast horizon, the ChainSync client cannot obtain a ledger view and falls into the `Nothing` branch:

```haskell
case prj lst of
  Nothing -> do
    checkPreferTheirsOverOurs kis'
    retry
  Just ledgerView ->
    return $ return $ Intersects kis' ledgerView
```

`checkPreferTheirsOverOurs` then calls `preferAnchoredCandidate` with a **hardcoded** `emptyPerasWeightSnapshot`:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        emptyPerasWeightSnapshot   -- ← always empty; ignores real Peras boosts
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
```

The comment at line 1841 explicitly acknowledges this is wrong:
```
-- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
```

`preferAnchoredCandidate` has two branches: when `isEmptyPerasWeightSnapshot weights` is `True` it falls into the block-number-only comparison path; when `False` it uses `weightedSelectView` which accounts for Peras boosts. Because `emptyPerasWeightSnapshot` is always passed, the Peras-aware branch is **never reached** in this call site, regardless of how many real certificates exist in the node's `PerasCertDB`.

The analog to the external report is direct:

| External (Elfi) | Ouroboros Consensus |
|---|---|
| `if (amount > 0 \|\| unsettledAmount > 0)` gates the loop body | `isEmptyPerasWeightSnapshot weights` guard selects the non-Peras branch |
| `lossAmount` and `unPnl` are non-zero but skipped | Peras weight boosts are non-zero but skipped |
| Pool value is understated → wrong share mint/burn | Chain weight is understated → wrong disconnect decision |

### Impact Explanation

When a peer's chain is heavier than ours **only because of Peras certificate boosts** (i.e., same or fewer blocks but higher total weight), the check incorrectly concludes `ShouldNotSwitch` and throws `CandidateTooSparse`, disconnecting from that peer. The node then fails to adopt the legitimately heavier canonical chain. Conversely, a chain that is longer in raw block count but carries no Peras boosts will pass the check and be preferred, causing the node to select a less-secure chain. This is a **chain-selection error** that violates the Peras security invariant: total weight (block count + boost) must govern chain preference.

### Likelihood Explanation

The code path is reachable by any upstream peer: it is triggered whenever a header arrives beyond the forecast horizon, which is a normal occurrence during initial sync or after a long slot gap. No privileged keys or operator access are required. The TODO comment and linked issue confirm the developers recognise the defect is present in production code.

### Recommendation

Replace the hardcoded `emptyPerasWeightSnapshot` with the actual weight snapshot from the ChainDB state, consistent with how `preferAnchoredCandidate` is called everywhere else in the chain-selection pipeline (e.g., `constructPreferableCandidates`, `chainSelection`). The real snapshot is already available via `Query.getPerasWeightSnapshot cdb` as used in `chainSelectionForBlock`.
