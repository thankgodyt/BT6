### Title
`safe_mint` Mints nBTC to Bridge Before Checking Recipient Registration, Causing Permanent Token Supply Inflation — (`contracts/nbtc/src/lib.rs`)

### Summary
The `safe_mint` function in the nBTC token contract unconditionally mints tokens to `bridge_id` before verifying whether the intended recipient account is registered. If the recipient is unregistered, the function returns `U128(0)` and exits, leaving the freshly minted tokens permanently stranded in the bridge's own balance. This inflates the total nBTC supply beyond what is redeemable by users, creating a backed-supply shortfall analogous to the ERC4626PartnerManager over-mint.

### Finding Description
In `contracts/nbtc/src/lib.rs`, `safe_mint` executes in this order:

1. **Mint unconditionally** — `self.token.internal_deposit(&self.bridge_id, amount.into())` increases `bridge_id`'s balance and the global `total_supply` by `amount`.
2. **Check registration** — `if self.token.accounts.get(&account_id).is_none()` — if the recipient has no storage slot, the function returns `PromiseOrValue::Value(U128(0))` immediately.
3. **Transfer never happens** — the minted tokens remain in `bridge_id`'s balance with no subsequent burn or recovery path inside this function. [1](#0-0) 

Compare with `mint_inner`, which is used by the primary `mint` path and correctly registers the account before depositing: [2](#0-1) 

The `mint` path never leaves tokens stranded because `mint_inner` auto-registers. `safe_mint` does not follow this pattern.

### Impact Explanation
Every time `safe_mint` is called for an unregistered recipient:
- `total_supply` grows by `amount` with no corresponding user-accessible balance.
- The bridge's own nBTC balance is inflated by the same amount.
- The nBTC supply is no longer fully backed on a per-user basis; the stranded tokens sit in `bridge_id` and can be spent by the bridge for other purposes (e.g., protocol-fee withdrawals via `internal_withdraw_protocol_fee`), silently draining backing.
- The depositing user receives zero nBTC for their locked BTC, constituting a permanent loss of their bridged funds unless an out-of-band operator recovery is performed.

This matches the **Medium** allowed impact: *harmful smart-contract behavior without direct funds theft, including permanent burning below backed supply or stuck bridge state requiring operator intervention*, and potentially **Critical** if the stranded tokens are later consumed by the bridge's own fee or burn flows, enabling unauthorized release of BTC backing.

### Likelihood Explanation
At contract initialization only `bridge_id` is registered: [3](#0-2) 

Any NEAR account that has never called `storage_deposit` on the nBTC contract is unregistered. A user who deposits BTC targeting a NEAR account that has not yet paid storage registration will trigger this path. No privileged access is required — any depositor whose recipient account is unregistered causes the bug. This is a realistic, low-friction scenario (e.g., a new user whose wallet has not yet interacted with the nBTC contract).

### Recommendation
Move the registration check **before** the `internal_deposit` call, mirroring the `mint_inner` pattern:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );

    // Guard BEFORE minting — no tokens enter circulation if recipient is unregistered
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));
    }

    self.token.internal_deposit(&self.bridge_id, amount.into());

    if let Some(msg) = msg {
        self.ft_transfer_call(account_id, amount, None, msg)
    } else {
        self.ft_transfer(account_id, amount, None);
        PromiseOrValue::Value(amount)
    }
}
```

This ensures `total_supply` only increases when the tokens can actually be delivered.

### Proof of Concept

1. `user.near` has never called `storage_deposit` on the nBTC contract — their account slot does not exist.
2. `user.near` sends 0.001 BTC to the deposit address derived from their NEAR account ID.
3. A relayer submits the inclusion proof; the satoshi-bridge verifies it and calls `nbtc.safe_mint(user.near, 100_000, None)`.
4. Inside `safe_mint`:
   - `internal_deposit(&bridge_id, 100_000)` executes — `total_supply` increases by 100,000 satoshis, `bridge_id` balance = 100,000.
   - `accounts.get(&user.near)` returns `None`.
   - Function returns `U128(0)` — no transfer occurs.
5. Result: `user.near` holds 0 nBTC; `bridge_id` holds an extra 100,000 nBTC; `total_supply` is inflated by 100,000 beyond what users can redeem.
6. The user's 0.001 BTC remains locked in the bridge's Bitcoin address with no corresponding nBTC issued to them. [4](#0-3)
