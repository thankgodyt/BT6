### Title
Reentrancy in `initTransfer1155` via Malicious ERC1155 `safeTransferFrom` Callback Causes Nonce Collision and Allows `InitTransfer` Event Emission Without Token Custody — (`File: evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

`initTransfer1155` in `OmniBridge.sol` has no reentrancy guard. It increments `currentOriginNonce` at the top of the function but reads `currentOriginNonce` again — by reference — when calling `initTransferExtension` and emitting `InitTransfer`. A malicious ERC1155 token can re-enter `initTransfer1155` inside its `safeTransferFrom` implementation, causing both the inner and outer call to emit `InitTransfer` with the same nonce (N+1) while nonce N is silently skipped. More critically, the malicious token need not transfer any tokens to the bridge at all, yet the bridge emits a valid `InitTransfer` event that the NEAR bridge will finalize, releasing NEAR-side funds to the attacker.

---

### Finding Description

`initTransfer1155` follows this execution order:

1. **Line 448** — `currentOriginNonce += 1;` (nonce becomes N)
2. **Line 458** — `IERC1155(tokenAddress).safeTransferFrom(msg.sender, address(this), tokenId, amount, "")` — external call to an attacker-controlled ERC1155 contract
3. **Line 468** — `initTransferExtension(..., currentOriginNonce, ...)` — reads `currentOriginNonce` at call time
4. **Line 480** — `emit BridgeTypes.InitTransfer(..., currentOriginNonce, ...)` — reads `currentOriginNonce` at call time [1](#0-0) 

There is no `nonReentrant` modifier on `initTransfer1155`, `initTransfer`, or `finTransfer` — confirmed by the complete absence of `ReentrancyGuard` or `nonReentrant` in any `.sol` file in the repository. [2](#0-1) 

**Reentrancy execution trace with a malicious ERC1155 token:**

```
Outer call: currentOriginNonce → N
  → safeTransferFrom() on malicious token
      Inner call: currentOriginNonce → N+1
        → safeTransferFrom() on malicious token (returns, no tokens transferred)
        → initTransferExtension(..., currentOriginNonce=N+1, ...)  ← Wormhole msg published
        → emit InitTransfer(..., currentOriginNonce=N+1, ...)
      [inner call returns]
  → initTransferExtension(..., currentOriginNonce=N+1, ...)  ← Wormhole msg published again
  → emit InitTransfer(..., currentOriginNonce=N+1, ...)
```

**Result:**
- Nonce N is permanently skipped (never emitted).
- Nonce N+1 is emitted twice by two separate `InitTransfer` events.
- The malicious ERC1155 token never actually transfers tokens to the bridge — its `safeTransferFrom` simply re-enters and returns without moving any balance.

The bridge's `onERC1155Received` guard (checking `operator == address(this)`) is irrelevant here: a malicious token's `safeTransferFrom` is not required to call `onERC1155Received` at all; it can re-enter `initTransfer1155` directly and return. [3](#0-2) 

On the NEAR side, `fin_transfer_callback` verifies the emitter address against the registered factory and checks token decimals, but it does not verify that the EVM bridge actually holds the corresponding ERC1155 tokens. It trusts the emitted event. [4](#0-3) 

The NEAR bridge deduplicates by `TransferId` (origin chain + origin nonce), so only one of the two N+1 events will be finalized. However, that one event was emitted without any token being deposited into the bridge, constituting a direct theft of NEAR-side funds.

---

### Impact Explanation

**Critical.** An attacker can emit a valid `InitTransfer` event from the EVM bridge without depositing any ERC1155 tokens. The NEAR bridge verifies the event via light-client or Wormhole proof and releases NEAR-side tokens to the attacker. This is unauthorized minting / theft of bridged funds. The attacker's profit equals the NEAR-side value of the claimed token amount, with no ERC1155 collateral locked on the EVM side.

---

### Likelihood Explanation

**Medium.** The attack requires:
1. Deploying a malicious ERC1155 contract (trivial).
2. Registering the token on NEAR via `logMetadata1155` (permissionless, lines 234–270).
3. Calling `initTransfer1155` with the malicious token (permissionless, no whitelist). [5](#0-4) 

No admin access, no leaked keys, and no oracle manipulation are required. Any unprivileged EVM account can execute this.

---

### Recommendation

Add OpenZeppelin's `ReentrancyGuardUpgradeable` to `OmniBridge` and apply `nonReentrant` to `initTransfer`, `initTransfer1155`, and `finTransfer`. This is the same fix applied to the referenced NFTCollection issue (PR #14).

Additionally, capture the nonce value into a local variable immediately after incrementing it, and use that local variable in all subsequent reads within the same function call, to eliminate the read-after-reentrant-write pattern regardless of guard status.

---

### Proof of Concept

```solidity
contract MaliciousERC1155 {
    OmniBridge public bridge;
    uint256 public tokenId;
    bool private _attacking;

    constructor(address _bridge, uint256 _tokenId) {
        bridge = OmniBridge(_bridge);
        tokenId = _tokenId;
    }

    // Called by bridge inside initTransfer1155
    function safeTransferFrom(
        address, address, uint256, uint256 amount, bytes memory
    ) external {
        if (!_attacking) {
            _attacking = true;
            // Re-enter initTransfer1155 — no tokens are ever moved
            bridge.initTransfer1155(
                address(this), tokenId, uint128(amount), 0, 0,
                "near:attacker.near", ""
            );
            _attacking = false;
        }
        // Return without transferring any tokens
    }

    function balanceOf(address, uint256) external pure returns (uint256) {
        return type(uint256).max; // satisfy any balance checks
    }
}
```

**Steps:**
1. Deploy `MaliciousERC1155` pointing at the `OmniBridge`.
2. Call `bridge.logMetadata1155(maliciousToken, tokenId)` to register the deterministic address on-chain.
3. Register the token on NEAR (via the emitted `LogMetadata` event).
4. Call `bridge.initTransfer1155(maliciousToken, tokenId, amount, 0, 0, "near:attacker.near", "")`.
5. The bridge increments nonce to N, calls `maliciousToken.safeTransferFrom`, which re-enters `initTransfer1155`.
6. Inner call increments nonce to N+1, calls `safeTransferFrom` again (returns immediately), emits `InitTransfer(nonce=N+1)` — no tokens transferred.
7. Outer call resumes, reads `currentOriginNonce = N+1`, emits `InitTransfer(nonce=N+1)` again — no tokens transferred.
8. Relayer submits proof of the N+1 event to the NEAR bridge.
9. NEAR bridge finalizes the transfer and mints NEAR-side tokens to `attacker.near`.
10. Attacker receives NEAR-side value with zero ERC1155 collateral locked.
