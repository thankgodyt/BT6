### Title
Decimal Normalization Dust Permanently Burned When `fee = 0` on NEAR Bridge - (`File: near/omni-bridge/src/lib.rs`)

### Summary

When a user initiates a cross-chain transfer from EVM (or NEAR) to another chain and the token has different decimal precision between origin and destination, `normalize_amount` applies floor division. When `fee = 0`, the truncated sub-unit remainder ("dust") is permanently locked or burned with no recovery path. This is the direct analog of M-02: the bridge does not pre-sanitize amounts to be divisible by the normalization factor before accepting them.

### Finding Description

In `near/omni-bridge/src/lib.rs`, `normalize_amount` performs integer floor division:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [1](#0-0) 

This is called in `sign_transfer` to compute `amount_to_transfer`:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
``` [1](#0-0) [2](#0-1) 

The code comment explicitly acknowledges the problem:

> "When fee > 0, dust is absorbed into the fee via `claim_fee`. When fee = 0, dust stays locked/burned. See SECURITY.md for details." [3](#0-2) 

However, the referenced `SECURITY.md` does not exist in the NEAR module of this repository, meaning the behavior is not formally documented as an accepted known issue. The EVM-side `SECURITY.md` does not mention this either. [4](#0-3) 

The `claim_fee_callback` confirms that when `fee > 0`, dust is recovered:

```rust
let fee = transfer_message.amount.0 - denormalized_amount;
self.send_fee_internal(&transfer_message, fee_recipient, fee)
``` [5](#0-4) 

But when `fee = 0`, no `claim_fee` is ever called, so the dust has no recovery path — it remains permanently locked in the bridge escrow (for native tokens) or burned (for deployed tokens).

### Impact Explanation

Any user who initiates a transfer with `fee = 0` and an amount that is not cleanly divisible by `10^(origin_decimals - decimals)` will permanently lose the sub-unit remainder. For example, with a token having `origin_decimals = 18` and `decimals = 6` (diff = 12), any amount with non-zero lower 12 digits loses up to `10^12 - 1` wei per transfer. These tokens are locked in the NEAR bridge contract forever with no admin or user recovery function. This is a direct balance loss for the user.

### Likelihood Explanation

Medium. Any user bridging with `fee = 0` and a non-round amount triggers this. The `initTransfer` function on EVM accepts arbitrary `uint128 amount` values with no rounding enforcement. The `HyperliquedBridgeToken.coreReceiveWithData` path also passes the raw HyperCore-provided `amount128` directly to `initTransfer` without rounding. [6](#0-5) [7](#0-6) 

### Recommendation

Before accepting a transfer into the bridge (either on the EVM side in `initTransfer`, or on the NEAR side before storing the `TransferMessage`), round down the amount to the nearest multiple of `10^(origin_decimals - decimals)` and refund the remainder to the sender. Alternatively, enforce that `fee > 0` for any token with decimal normalization, so dust is always recoverable via `claim_fee`.

### Proof of Concept

1. Token registered with `origin_decimals = 18`, `decimals = 6` (diff = 12, factor = `10^12`).
2. User calls `initTransfer` on EVM with `amount = 1_000_000_000_001`, `fee = 0`.
3. EVM burns `1_000_000_000_001` tokens and emits `InitTransfer`.
4. NEAR relayer calls `sign_transfer`. `normalize_amount(1_000_000_000_001, decimals)` = `1_000_000_000_001 / 10^12` = `1`.
5. MPC signs for `amount = 1`. Recipient receives `1` NEAR-side unit.
6. `fee = 0`, so `claim_fee` is never called. The `1` sub-unit remainder (`1` EVM wei) is permanently locked in the NEAR bridge escrow.
7. No admin function or user-callable path exists to recover it. [8](#0-7) [9](#0-8)

# Security Notes

## Design Decisions (Non-Issues)

These patterns have been reviewed and confirmed as intentional. Do not flag or "fix" them.

- **Fee-on-transfer tokens not supported**: `initTransfer` emits the requested `amount`, not the actual received balance. Fee-on-transfer and rebasing tokens are intentionally unsupported
- **`logMetadata` and `deployToken` are permissionless**: Anyone can call `logMetadata` for any ERC20, and anyone can submit a valid MPC signature to `deployToken`. This is by design — the bridge is fully permissionless
- **`ENearProxy.burn` uses empty NEAR recipient**: `eNear.transferToNear(amount, "")` is intentional — `transferToNear` is a legacy method used purely as a burn mechanism. The actual NEAR recipient is tracked in the OmniBridge `InitTransfer` event
- **`deployToken` signature has no chain ID**: Metadata signatures are intentionally chain-agnostic — one NEAR-side signature deploys the same token on all EVM chains

## Known Issues

Low-severity items acknowledged but not yet addressed:

- **`addCustomToken` can overwrite existing mappings** (H-01): Admin-only function. No existence check — calling with an already-mapped `nearTokenId` silently overwrites `nearToEthToken`. Accepted as operational risk
- **`pause(flags)` replaces all flags** (H-02): `_pause(flags)` does full replacement, not bitwise OR. Calling `pause(PAUSED_INIT_TRANSFER)` when `PAUSED_FIN_TRANSFER` is set will unpause finTransfer. Use `pauseAll()` for emergencies
- **`BridgeToken.initialize` stores metadata redundantly** (L-01): `__ERC20_init(name_, symbol_)` writes to parent storage that is never read (getters are overridden). Minor gas waste on init
- **`require` strings instead of custom errors** (L-02): Several locations use `require` with string messages instead of custom errors (`OmniBridge.sol:150,204,556`, `SelectivePausableUpgradable.sol:100,107`, `ENearProxy.sol:56,76,86`)
- **`OmniBridgeWormhole` has no `__gap`** (L-04): Three storage variables with no gap array. Safe as a leaf contract but would need a gap if inherited from
- **`PayloadType.ClaimNativeFee` defined but unused** (L-05): Enum value 2 is never referenced. Native fees are recovered via `finTransfer` with `tokenAddress=address(0)`

    function initTransfer(
        address tokenAddress,
        uint128 amount,
        uint128 fee,
        uint128 nativeFee,
        string calldata recipient,
        string calldata message
    ) external payable whenNotPaused(PAUSED_INIT_TRANSFER) {
        currentOriginNonce += 1;
        if (fee >= amount) {
            revert InvalidFee();
        }

        uint256 extensionValue;
        if (tokenAddress == address(0)) {
            if (fee != 0) {
                revert InvalidFee();
            }
            extensionValue = msg.value - amount - nativeFee;
        } else {
            extensionValue = msg.value - nativeFee;
            if (customMinters[tokenAddress] != address(0)) {
                IERC20(tokenAddress).safeTransferFrom(
                    msg.sender,
                    customMinters[tokenAddress],
                    amount
                );
                ICustomMinter(customMinters[tokenAddress]).burn(
                    tokenAddress,
                    amount
                );
            } else if (isBridgeToken[tokenAddress]) {
                BridgeToken(tokenAddress).burn(msg.sender, amount);
            } else {
                IERC20(tokenAddress).safeTransferFrom(
                    msg.sender,
                    address(this),
                    amount
                );
            }
        }

        initTransferExtension(
            msg.sender,
            tokenAddress,
            currentOriginNonce,
            amount,
            fee,
            nativeFee,
            recipient,
            message,
            extensionValue
        );

        emit BridgeTypes.InitTransfer(
            msg.sender,
            tokenAddress,
            currentOriginNonce,
            amount,
            fee,
            nativeFee,
            recipient,
            message
        );
    }
