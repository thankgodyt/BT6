### Title
Stub `validatePerasCert` Unconditionally Accepts All Inbound Peras Certificates, Enabling Unprivileged Chain-Selection Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance ships a stub `validatePerasCert` that unconditionally returns `Right` for every inbound certificate. Because this validator is wired directly into the live Peras certificate diffusion handler, any unprivileged peer can inject a crafted `PerasCert` with an arbitrary round number and boosted-block pointer. The injected certificate is stored in `PerasCertDB`, its boost is included in `getWeightSnapshot`, and chain selection is re-run against the boosted block — allowing the attacker to make an honest node prefer a non-canonical fork.

---

### Finding Description

The `BlockSupportsPeras` type class defines `validatePerasCert` as the gate that must reject structurally or cryptographically invalid certificates before they enter the node's state. The only deployed instance is the degenerate catch-all:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is passed verbatim as the `validateCert` argument inside `makePerasCertPoolWriterFromChainDB`, the production pool writer used for every peer connection:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` calls this validator on every certificate not already in the DB. Because the validator never returns `Left`, the `partitionEithers` branch that would throw `PerasCertValidationError` and disconnect the peer is unreachable: [3](#0-2) 

The validated certificate is then forwarded to `ChainDB.addPerasCertAsync`, which calls `chainSelSync`. That function adds the certificate to `PerasCertDB` and immediately re-runs chain selection for the boosted block: [4](#0-3) 

Chain selection reads `getWeightSnapshot`, which accumulates `getPerasCertBoost` for every stored certificate via `mkPerasWeightSnapshot`. The boost is then added to the fragment length in `totalWeightOfFragment`, directly affecting which fork the node considers canonical: [5](#0-4) [6](#0-5) 

The production node-to-node handler wires `makePerasCertPoolWriterFromChainDB` directly to the live `hPerasCertDiffusionClient` slot, making this reachable from any connected peer: [7](#0-6) 

The state-machine test for `PerasCertDB` explicitly documents the invariant that is missing from production: equivocating certificates (same round, different boosted block) must be rejected: [8](#0-7) 

No such check exists anywhere in the production inbound path.

---

### Impact Explanation

An attacker who can connect as a peer (no stake, no keys required) can:

1. Craft a `PerasCert` with `pcCertRound` set to any round not yet in the DB and `pcCertBoostedBlock` pointing to a block on the attacker's own fork.
2. Send it via the Peras certificate diffusion mini-protocol.
3. The stub validator accepts it unconditionally; it is stored in `PerasCertDB` and its boost (`perasWeight params`) is added to the weight snapshot.
4. Chain selection re-runs and may now prefer the attacker's fork because `totalWeightOfFragment` for that fork exceeds the honest chain's weight.

This satisfies the **High** impact criterion: an unprivileged peer can make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions of Peras.

---

### Likelihood Explanation

The attack requires only a standard peer connection — no stake, no cryptographic material, no operator access. The Peras certificate diffusion mini-protocol is active in the production node-to-node handler. The stub is the only deployed instance of `validatePerasCert` for all block types. Likelihood is **High** once Peras is active on a network running this code.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
- The certificate's committee membership proof and BLS/aggregate signature.
- That the boosted block's slot falls within the valid range for the claimed round.
- That no equivocating certificate (same round, different boosted block) is already stored.

Until real validation is in place, the inbound Peras certificate diffusion handler should be disabled or gated behind a feature flag so that no peer-supplied certificate can influence chain selection.

---

### Proof of Concept

```
Attacker (unprivileged peer)
  │
  │  PerasCert { pcCertRound = R, pcCertBoostedBlock = attacker_fork_tip }
  │  (R not yet in PerasCertDB)
  ▼
hPerasCertDiffusionClient
  → makePerasCertPoolWriterFromChainDB
      → processCerts
          alreadyInDb = {rounds already stored}   -- R ∉ alreadyInDb
          validateCert = validatePerasCert mkPerasParams
                       = \cert -> Right (ValidatedPerasCert cert boost)
                       -- ALWAYS Right, no checks
          → addCert (WithArrivalTime now validatedCert)
              → ChainDB.addPerasCertAsync
                  → chainSelSync (ChainSelAddPerasCert cert)
                      → PerasCertDB.addCert  -- cert stored
                      → chainSelectionForBlock attacker_fork_tip
                          → getWeightSnapshot includes boost for attacker_fork_tip
                          → totalWeightOfFragment(attacker_fork) > totalWeightOfFragment(honest_chain)
                          → node switches to attacker's fork  ← CHAIN SELECTION MANIPULATED
```

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock

        Just boostedHdr -> pure boostedHdr
