### Title
Peras Vote Diffusion Accepts Forged Votes Without Cryptographic Signature Verification - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The `PerasVote blk` type used in the Peras vote diffusion miniprotocol carries no cryptographic signature field. The `validatePerasVote` implementation only checks whether the claimed `pvVoteVoterId` appears in the stake distribution, never verifying that the sender cryptographically controls that voter identity. Any unprivileged peer can therefore forge votes on behalf of any legitimate high-stake pool, manufacture a quorum for an attacker-chosen block, and cause the receiving node to forge and accept a Peras certificate boosting that block in chain selection.

### Finding Description

**Root cause — missing signature field in the wire-level vote type**

The `PerasVote blk` data type that is serialised and transmitted over the network contains only three fields:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound  :: PerasRoundNo
  , pvVoteBlock  :: Point blk
  , pvVoteVoterId :: PerasVoterId   -- attacker-controlled "from"
  }
``` [1](#0-0) 

There is no `pvSignature` or eligibility-proof field. Compare this with the richer `Peras.Vote.V1.PerasVote` type (which is **not** wired into the diffusion protocol) that does carry a `pvSignature :: VoteSignature PerasBLSCrypto` and a `pvEligibilityProof`. [2](#0-1) 

**Root cause — `validatePerasVote` performs no signature check**

The `BlockSupportsPeras` instance's `validatePerasVote` only looks up the claimed voter ID in the stake distribution. If the ID is present, the vote is unconditionally accepted:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [3](#0-2) 

The TODO comment at line 350 acknowledges validation is incomplete, but does not identify the missing signature check as a known gap.

**Exploit path through the diffusion layer**

Inbound votes from peers are processed by `processVotes`, which calls the above `validatePerasVote` and adds passing votes to the `PerasVoteDB`: [4](#0-3) 

The `makePerasVotePoolWriterFromChainDB` function wires this writer into the live node's `hPerasVoteDiffusionClient` handler: [5](#0-4) [6](#0-5) 

Once enough forged votes accumulate, `votesReachQuorum` returns `Just`, triggering `forgePerasCert` to produce a certificate for the attacker-chosen block: [7](#0-6) 

**Current partial mitigation and why it is temporary**

The live `NodeToNode.hs` handler currently passes `(pure (PerasVoteStakeDistr mempty))` as the stake distribution, which causes every vote to fail the `lookupPerasVoteStake` check and be rejected. The inline TODO comment explicitly states this will be replaced with real committee data when Peras plumbing is complete:

```haskell
-- Note that the empty stake distribution will cause all votes to
-- be considered invalid.
(pure (PerasVoteStakeDistr mempty))
``` [8](#0-7) 

When that TODO is resolved and a real stake distribution is supplied, the structural absence of signature verification becomes immediately exploitable with no further code changes required.

### Impact Explanation

**High — Bypass of Peras vote/certificate authorization enabling unauthorized chain boosting.**

An unprivileged peer can craft `PerasVote` messages claiming to originate from any registered high-stake pool. Because `validatePerasVote` never verifies a signature, these votes pass validation and accumulate in the `PerasVoteDB`. Once the forged votes collectively exceed the quorum threshold, the node forges a `PerasCert` for the attacker-chosen block and applies its boost weight to chain selection. This lets an adversary with no stake and no keys cause an honest node to prefer a non-canonical chain, directly violating Peras safety.

### Likelihood Explanation

**Medium.** The attack is blocked today only by the temporary empty-stake-distribution placeholder. The code path is fully wired end-to-end; the only missing piece is the real committee data, which the TODO explicitly plans to add. Any peer that can establish a node-to-node connection (no authentication required) can send crafted votes. No privileged access, key material, or stake is needed.

### Recommendation

1. Add a `pvSignature` field (or equivalent eligibility proof) to `PerasVote blk` in `Block/SupportsPeras.hs`, mirroring the design of `Peras.Vote.V1.PerasVote`.
2. Implement signature verification inside `validatePerasVote` before the stake-distribution lookup, so that a vote is only accepted if the signature over `(pvVoteRound, pvVoteBlock)` verifies under the public key associated with `pvVoteVoterId` in the committee.
3. Resolve the TODO at line 350 of `Block/SupportsPeras.hs` as part of the same change, not after the stake-distribution plumbing is connected.

votesReachQuorum ::
  StandardHash blk =>

votesReachQuorum cfg votes =
  case votes of
    -- We need at least one vote to determine who these votes are for, so we
    -- can't vacuously reach a quorum, even if the quorum threshold is 0.
    [] -> Nothing
    -- If we have at least one vote, we must check that all votes are for the
    -- same target, and that their total stake of is above the quorum threshold.
    (v0 : vs)
      | not (allVotesMatchTarget v0 vs) ->
          Nothing
      | not votesHaveEnoughStake ->
          Nothing
      | otherwise ->
          Just
            ValidatedPerasVotesWithQuorum
              { vpvqTarget = getPerasVoteTarget v0
              , vpvqVotes = v0 :| vs
              , vpvqPerasCfg = cfg
              }

makePerasVotePoolWriterFromChainDB ::
  (StandardHash blk, IOLike m) =>
  SystemTime m ->
  -- | This is needed for validating votes (since its during the validation of
  -- votes that we give them a verified weight. In the future, we won't read it
  -- from the stake distr directly, but rather use the committee selection data)
  STM m PerasVoteStakeDistr ->
  ChainDB m blk ->
  ObjectPoolWriter (PerasVoteId blk) (PerasVote blk) m
makePerasVotePoolWriterFromChainDB systemTime getStakeDistrSTM chainDB =
  ObjectPoolWriter
    { opwObjectId = getPerasVoteId
    , opwAddObjects = \votes ->
        processVotes
          systemTime
          (ChainDB.getPerasVoteIds chainDB)
          -- TODO: in the future we won't need just the stake distribution for
          -- validating votes, but also the whole committee selection context
          -- (containing vote weights of committee members = voters)
          (\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
          -- We do not want to block the writer thread on waiting for ChainSel
          -- side-effects to complete, so we use the async version of adding
          -- votes to the ChainDB and ignore the returned promise.
          -- The async action (if any) is still launched and executed behind the
          -- scenes even though we drop the promise.
          (void . ChainDB.addPerasVoteWithAsyncCertHandling chainDB)
          votes
    , opwHasObject = do
        voteIds <- ChainDB.getPerasVoteIds chainDB
        pure $ \voteId -> Set.member voteId voteIds
    }

```haskell
processVotes ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
