### Title
Silent Zeroing of `tx_bytes` in Safe Deposit Path Permanently Locks Bridge UTXOs - (File: `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

---

### Summary

In `internal_safe_verify_deposit_entry`, when the submitted `tx_bytes` exceed 10,000 bytes, the code silently replaces them with 300 zero bytes (`vec![0u8; 300]`) before storing the UTXO. The stored UTXO's `tx_bytes` field is then permanently corrupted. Any subsequent attempt to construct a withdrawal PSBT using this UTXO will fail to decode the zeroed bytes as a valid Bitcoin transaction, permanently locking the deposited funds in the bridge.

---

### Finding Description

The vulnerability is in `internal_safe_verify_deposit_entry`: [1](#0-0) 

```rust
let tx_bytes = if tx_bytes.len() > 10000 {
    env::log_str("tx_bytes length exceeds 10000, truncating to 300 bytes");
    vec![0u8; 300]   // ← NOT a truncation; replaces with 300 zero bytes
} else {
    tx_bytes
};
```

The log message says "truncating to 300 bytes" but the code does not truncate — it discards the original bytes entirely and substitutes 300 null bytes. These corrupted bytes are then placed into the `UTXO` struct: [2](#0-1) 

```rust
let utxo = UTXO {
    path,
    tx_bytes,   // vec![0u8; 300] when original exceeded 10 000 bytes
    vout,
    balance: transaction.output()[vout].value.to_sat(),
};
```

On a successful `safe_mint`, `safe_mint_callback` calls `internal_set_utxo`, persisting the corrupted UTXO into the bridge's live UTXO set: [3](#0-2) 

Later, when the bridge selects this UTXO to satisfy a withdrawal, the PSBT pipeline must decode `tx_bytes` to reconstruct the previous output (amount + `script_pubkey`) needed to sign the input. Decoding `vec![0u8; 300]` as a Bitcoin transaction will always fail, making the UTXO permanently unspendable.

The analog to the Augur finding is direct: just as Augur's `lookup` silently returned the zero address that was then used as a proxy target without validation, this bridge silently stores zero bytes as the UTXO's transaction data without validation, causing an equally opaque failure at the point of use (PSBT construction) rather than at the point of storage.

---

### Impact Explanation

- **nBTC is minted** to the depositor (the `safe_mint` call succeeds because the transaction was decoded correctly *before* the zeroing).
- **The UTXO is recorded** in the bridge's live UTXO set with the correct `balance` but corrupted `tx_bytes`.
- **The UTXO can never be spent**: every future withdrawal attempt that selects this UTXO will panic/fail at PSBT construction.
- The deposited BTC is permanently locked inside the bridge's MPC-controlled address with no recovery path short of a contract upgrade.
- Over time, repeated occurrences reduce the bridge's spendable liquidity while the total recorded balance remains inflated, creating a growing discrepancy between on-chain BTC and spendable UTXOs.

Impact category: **Critical — Significant permanent locking of user or protocol funds.**

---

### Likelihood Explanation

A Bitcoin transaction exceeds 10,000 bytes when it has many inputs (roughly 40+ P2WPKH inputs or 100+ legacy P2PKH inputs). This is uncommon for a single-user deposit but is realistic for:

- A DApp or bridge aggregator (the primary users of the `safe_deposit` path) that consolidates many small UTXOs into one deposit transaction.
- Any relayer (whitelisted or not — the `#[trusted_relayer]` macro adjusts confirmation counts for non-whitelisted callers but does not block them from submitting) who processes such a transaction.

The `verify_deposit_v2` entry point is publicly reachable with `deposit_msg.safe_deposit = Some(...)`: [4](#0-3) 

Likelihood: **Low-to-Medium** (requires a large deposit transaction, but the safe-deposit path is explicitly designed for DApp integrations that may aggregate UTXOs).

---

### Recommendation

Remove the silent replacement entirely. If oversized transactions must be rejected, do so explicitly with a `require!` before any state changes:

```rust
require!(
    tx_bytes.len() <= 10_000,
    "tx_bytes too large for safe deposit"
);
```

If storage reduction is the goal, store only the specific output being deposited (amount + `script_pubkey`) rather than the full raw transaction, and adjust the PSBT construction path accordingly.

---

### Proof of Concept

1. Construct a Bitcoin transaction with ≥ 40 P2WPKH inputs so that `tx_bytes.len() > 10_000`.
2. Send BTC to the bridge deposit address derived from a `DepositMsg` with `safe_deposit: Some(SafeDepositMsg { msg: "..." })`.
3. Call `verify_deposit_v2` with the large `tx_bytes` and `deposit_msg.safe_deposit = Some(...)`.
4. `internal_safe_verify_deposit_entry` decodes the transaction successfully (verifying amount and script), then replaces `tx_bytes` with `vec![0u8; 300]`.
5. `verify_safe_deposit_callback` → `safe_mint` → `safe_mint_callback` succeeds; `internal_set_utxo` persists the UTXO with zeroed `tx_bytes`.
6. The depositor receives correct nBTC. The UTXO appears in the bridge's UTXO set with the correct balance.
7. Any subsequent withdrawal that selects this UTXO attempts `WrappedTransaction::decode(&utxo.tx_bytes, ...)` on 300 zero bytes → decode fails → withdrawal panics → UTXO is permanently unspendable. [5](#0-4) [6](#0-5)
