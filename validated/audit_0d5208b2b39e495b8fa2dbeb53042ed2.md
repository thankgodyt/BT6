### Title
Peras Quorum Check Unit Mismatch in `stakeAboveThreshold` Bypasses Certificate Validation - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` compares an accumulated `PerasVoteStake` (a `Rational` sourced from the ledger's absolute stake distribution) directly against `perasQuorumStakeThreshold` (a relative fraction, `3/4`). No normalization is performed before the comparison. The code itself acknowledges this with an explicit TODO. Because absolute lovelace values (e.g., `1_000_000 % 1` for 1 ADA) are orders of magnitude larger than the relative threshold `0.75`, the quorum check is trivially satisfied by any single vote from any pool with more than 0.75 lovelace, allowing unauthorized Peras certificates to be forged for arbitrary blocks.

---

### Finding Description

In `SupportsPeras.hs`, the `stakeAboveThreshold` function performs the Peras quorum check:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake     = unPerasVoteStake voteStake          -- Rational from PerasVoteStakeDistr
  quorumThreshold = unPerasQuorumStakeThreshold
                      (perasQuorumStakeThreshold params)   -- = 3/4 (relative)
  safetyMargin = unPerasQuorumStakeThresholdSafetyMargin
                   (perasQuorumStakeThresholdSafetyMargin params)  -- = 2/100 (relative)
``` [1](#0-0) 

The code carries an explicit TODO acknowledging the unit mismatch:

> "this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [2](#0-1) 

The `PerasVoteStake` type comment further confirms the problem:

> "At the moment there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee (given that the quorum is expressed as a relative value of the voting committee total stake)." [3](#0-2) 

The quorum threshold is set to `3/4` (relative) in `mkPerasParams`: [4](#0-3) 

The `PerasVoteStakeDistr` is populated from the ledger's absolute stake distribution. The WFALS committee implementation confirms that `LedgerStake` values are absolute integers (e.g., lovelace counts): [5](#0-4) 

When `validatePerasVote` looks up a voter's stake from `PerasVoteStakeDistr`, it stores the raw absolute value as `PerasVoteStake`: [6](#0-5) 

This absolute value is then summed across votes in `votesReachQuorum` and passed directly to `stakeAboveThreshold`: [7](#0-6) 

The same un-normalized comparison is used in `updateLoserVoteState` in the vote aggregation engine: [8](#0-7) 

---

### Impact Explanation

`perasQuorumStakeThreshold` is `3/4` (i.e., `0.75` as a `Rational`). Any pool with an absolute ledger stake greater than `0.75` lovelace — which is every pool on any real network — will have its single vote satisfy `stake >= 0.75 + 0.02`, making the quorum check trivially true. A single vote from any registered pool immediately forges a Peras certificate for the voted block. That certificate grants the block a `PerasWeight` boost (default: `15`), directly inflating its `wsvTotalWeight` in chain selection: [9](#0-8) 

An adversary with any registered stake can therefore cause honest nodes to prefer an adversarially chosen chain by forging certificates for it, bypassing the intended `>3/4` honest-stake quorum requirement entirely.

---

### Likelihood Explanation

The entry path is fully reachable by an unprivileged peer: a peer sends a `PerasVote` miniprotocol message, which is processed by `processVotes` → `validatePerasVote` → `votesReachQuorum` → `stakeAboveThreshold`. No special privilege is required beyond being a registered stake pool (or sending a vote on behalf of one). The `PerasVoteStakeDistr` is populated from the ledger by the receiving node itself, so the attacker does not need to forge stake data — the mismatch is structural and fires on every real-network vote.

---

### Recommendation

Normalize `PerasVoteStake` to a relative fraction before calling `stakeAboveThreshold`. Specifically, divide each voter's absolute ledger stake by the total stake of the voting committee before storing it in `PerasVoteStakeDistr`, or pass the total committee stake into `stakeAboveThreshold` and perform the division there. The fix mirrors the pattern already used in `localSortitionNumSeats`, which correctly normalizes `voterStake / totalNonPersistentStake` before comparison: [10](#0-9) 

---

### Proof of Concept

Given `mkPerasParams` defaults (`perasQuorumStakeThreshold = 3/4`, `perasQuorumStakeThresholdSafetyMargin = 2/100`):

1. A stake pool with 1,000,000 lovelace (1 ADA) has its absolute stake stored as `PerasVoteStake (1000000 % 1)` in `PerasVoteStakeDistr`.
2. A single `PerasVote` from this pool is received via the miniprotocol.
3. `validatePerasVote` looks up the stake: `vpvVoteStake = PerasVoteStake (1000000 % 1)`.
4. `votesReachQuorum` computes `totalVoteStake = PerasVoteStake (1000000 % 1)`.
5. `stakeAboveThreshold` evaluates: `1000000 >= 3/4 + 2/100` → `True`.
6. `forgePerasCert` is called, producing a `ValidatedPerasCert` with `vpcCertBoost = PerasWeight 15`.
7. The certificate is stored and the boosted block gains `+15` chain weight, influencing `preferCandidate` in chain selection. [11](#0-10) [4](#0-3)

    _seatIndex
