### Title
Missing Caller Ownership Validation in `withdraw_rbf` Allows Attacker to Redirect Another User's BTC Withdrawal — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary
`withdraw_rbf` uses `env::predecessor_account_id()` as the acting user identity without verifying that the caller owns the original pending withdrawal. An unprivileged attacker can supply a victim's `original_btc_pending_verify_id` and a malicious `output` vector, causing the bridge to build and MPC-sign an RBF transaction that redirects the victim's BTC to the attacker's address.

### Finding Description

`withdraw_rbf` is a public, permissionless function (only gated by `#[pause]`) that is intended to let a user bump the fee on their own pending BTC withdrawal. It captures the caller's identity via `env::predecessor_account_id()` and passes it — together with the caller-supplied `output` — directly into `withdraw_rbf_chain_specific`: [1](#0-0) 

```rust
#[pause(except(roles(Role::DAO)))]
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,
    output: Vec<TxOut>,
    chain_specific_data: Option<ChainSpecificData>,
) {
    let account_id = env::predecessor_account_id();   // ← attacker's account
    self.require_pending_sign_capacity(&account_id);
    self.withdraw_rbf_chain_specific(
        account_id,
        original_btc_pending_verify_id,               // ← victim's pending ID
        output,                                        // ← attacker-controlled outputs
        chain_specific_data,
    );
}
```

There is **no check** that `predecessor_account_id()` matches the `account_id` stored inside the `BTCPendingInfo` identified by `original_btc_pending_verify_id`. Compare this with the privileged `cancel_withdraw`, which correctly derives the user from the pending info rather than from the caller: [2](#0-1) 

```rust
pub fn cancel_withdraw(&mut self, original_btc_pending_verify_id: String, output: Vec<TxOut>) {
    assert_one_yocto();
    let user_account_id = self
        .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
        .account_id          // ← correctly taken from the stored record
        .clone();
    ...
    self.cancel_withdraw_chain_specific(user_account_id, ...);
}
```

The `#[trusted_relayer]` attribute that gates every other sensitive relay-facing function (`verify_deposit_v2`, `verify_withdraw_v2`, `verify_refund_finalize`, etc.) is absent from `withdraw_rbf`: [3](#0-2) [4](#0-3) 

Neither the impl-block-level `#[trusted_relayer]` nor any function-level equivalent is present on `withdraw_rbf`, leaving it callable by any NEAR account with no ownership enforcement.

### Impact Explanation

An attacker who observes a victim's `original_btc_pending_verify_id` (all pending info is stored on-chain and emitted via events) can call `withdraw_rbf` with:
- `original_btc_pending_verify_id` = victim's pending withdrawal ID
- `output` = a `TxOut` paying the full amount to the attacker's Bitcoin address

`withdraw_rbf_chain_specific` will build a new RBF PSBT spending the same UTXOs as the victim's original transaction but with the attacker-supplied outputs. The MPC signing pipeline (`sign_btc_transaction`) will then sign this RBF transaction. Once broadcast, the victim's BTC is redirected to the attacker.

**Impact class**: Critical — unauthorized redirection of bridge-controlled BTC funds.

### Likelihood Explanation

- `withdraw_rbf` is fully public; no NEAR tokens, roles, or whitelist membership are required.
- Pending withdrawal IDs are observable on-chain (emitted in `GenerateBtcPendingInfo` events).
- The attacker only needs to submit one transaction before the victim's original withdrawal is confirmed.
- No special knowledge or privileged access is required.

### Recommendation

Derive the acting user from the stored `BTCPendingInfo`, exactly as `cancel_withdraw` does, instead of trusting `predecessor_account_id()`:

```rust
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,
    output: Vec<TxOut>,
    chain_specific_data: Option<ChainSpecificData>,
) {
    // Derive user from the stored record, not from the caller
    let account_id = self
        .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
        .account_id
        .clone();
    // Optionally also assert predecessor == account_id to restrict to owner-only calls
    require!(
        env::predecessor_account_id() == account_id,
        "Only the withdrawal owner may submit an RBF"
    );
    self.require_pending_sign_capacity(&account_id);
    self.withdraw_rbf_chain_specific(
        account_id,
        original_btc_pending_verify_id,
        output,
        chain_specific_data,
    );
}
```

### Proof of Concept

1. Alice initiates a withdrawal via `ft_transfer_call`; the bridge emits `GenerateBtcPendingInfo { account_id: "alice.near", btc_pending_id: "abc123..." }`.
2. Attacker Eve observes `btc_pending_id = "abc123..."` on-chain.
3. Eve calls:
   ```
   withdraw_rbf(
     original_btc_pending_verify_id: "abc123...",
     output: [TxOut { value: <full_amount>, script_pubkey: <eve_btc_address> }],
     chain_specific_data: None
   )
   ```
4. `predecessor_account_id()` returns `"eve.near"`; no ownership check is performed.
5. `withdraw_rbf_chain_specific("eve.near", "abc123...", [eve_output], None)` builds an RBF PSBT spending Alice's UTXOs with Eve's output.
6. Eve (or anyone) calls `sign_btc_transaction` to trigger MPC signing of the RBF PSBT.
7. Eve broadcasts the signed RBF transaction; Alice's BTC is delivered to Eve's address. [1](#0-0) [2](#0-1) [5](#0-4)
