Audit Report

## Title
Tokens Burned/Locked Before Destination Chain Validation Causes Permanent Fund Loss - (File: `near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer` validates only that the destination chain is not `ChainKind::Near`, but does not verify that the destination chain has a registered factory or that the token is registered for that chain. `init_transfer_internal` then immediately burns deployed (bridged) tokens via a detached promise before any destination-chain validity is confirmed. When a relayer later calls `sign_transfer`, it panics on the missing token address lookup, leaving the transfer permanently stuck and the burned tokens irrecoverable.

## Finding Description
`init_transfer` performs a single destination-chain guard:

```rust
// near/omni-bridge/src/lib.rs L531-534
require!(
    init_transfer_msg.recipient.get_chain() != ChainKind::Near,
    BridgeError::InvalidRecipientChain.as_ref()
);
```

No check is made that `self.factories.get(&destination_chain)` or `self.token_id_to_address.get(&(destination_chain, token_id))` is populated. Execution proceeds to `init_transfer_internal` (L1829-1865), which immediately calls:

```rust
// near/omni-bridge/src/lib.rs L1850-1857
self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
self.lock_tokens_if_needed(
    transfer_message.get_destination_chain(),
    &token_id,
    transfer_message.amount.0,
);
```

`burn_tokens_if_needed` (L1806-1813) issues a fire-and-forget detached burn for any deployed (bridged) token — the tokens are destroyed before any destination-chain validity is confirmed:

```rust
fn burn_tokens_if_needed(&self, token: AccountId, amount: U128) {
    if self.is_deployed_token(&token) {
        ext_token::ext(token)
            .with_static_gas(BURN_TOKEN_GAS)
            .burn(amount)
            .detach();
    }
}
```

For native NEAR tokens on an unregistered chain, `lock_tokens_if_needed` → `lock_tokens` (token_lock.rs L55-56) returns `LockAction::Unchanged` when the `(chain_kind, token_id)` key is absent from `locked_tokens`, so the tokens are held by the bridge but completely untracked.

The destination-chain token address lookup only occurs later in `sign_transfer` (L447, gated by `#[trusted_relayer]`):

```rust
// near/omni-bridge/src/lib.rs L462-469
let token_address = self
    .get_token_address(
        transfer_message.get_destination_chain(),
        self.get_token_id(&transfer_message.token),
    )
    .unwrap_or_else(|| {
        env::panic_str(BridgeError::FailedToGetTokenAddress.to_string().as_str())
    });
```

Every relayer call to `sign_transfer` panics with `ERR_FAILED_TO_GET_TOKEN_ADDRESS`. There is no user-accessible cancel or refund function in the contract (confirmed by absence of any `cancel_transfer` / `refund_transfer` entry points). The DAO-only `transfer_token_as_dao` (L1511-1529) can recover untracked native tokens held by the contract, but cannot recover burned deployed tokens.

## Impact Explanation
This matches the critical impact class: **permanent freezing/loss of bridged funds**. For deployed (bridged) tokens (e.g., ETH-originated tokens held on NEAR), `burn_tokens_if_needed` destroys them immediately via a detached promise with no recovery path. The `InitTransferEvent` is emitted, the transfer is stored in `pending_transfers`, and the transfer is permanently unserviceable. Burned tokens cannot be reminted or recovered by any on-chain mechanism.

## Likelihood Explanation
Any unprivileged token holder can trigger this by calling `ft_transfer_call` on a deployed bridged token with an `InitTransfer` message whose `recipient` encodes a chain for which the token has not been registered via `bind_token` / `deploy_token`. The bridge supports many chains (`Eth`, `Sol`, `Arb`, `Base`, `Bnb`, `Pol`, `Abs`, `HyperEvm`, `Strk`, `Fogo`, `Btc`, `Zcash`), and a token is typically registered on only a subset. A user who picks a valid-looking but unregistered chain/token pair will permanently lose their funds. No special privileges, leaked keys, or colluding parties are required.

## Recommendation
Add upfront validation in `init_transfer`, before entering `init_transfer_internal`, that:
1. Confirms `self.factories.get(&destination_chain).is_some()`, and
2. Confirms `self.token_id_to_address.get(&(destination_chain, token_id)).is_some()`.

Both checks must occur before any token state change, mirroring the pattern already used in `sign_transfer` but moved to the point where the transfer is first accepted.

## Proof of Concept
1. Token `weth.near` (an ETH-originated deployed token) is registered for `ChainKind::Eth` but **not** for `ChainKind::Sol`.
2. User calls `weth.near::ft_transfer_call(bridge, amount, InitTransfer { recipient: OmniAddress::Sol(<valid_sol_addr>), fee: 0, ... })`.
3. `init_transfer` passes the only guard (`recipient.get_chain() != Near`). [1](#0-0) 
4. `init_transfer_internal` is entered. `is_deployed_token(&weth.near)` returns `true`; `burn_tokens_if_needed` fires a detached burn — tokens permanently destroyed. [2](#0-1) 
5. `InitTransferEvent` is emitted; transfer stored in `pending_transfers`. [3](#0-2) 
6. Relayer calls `sign_transfer`. `get_token_address(ChainKind::Sol, weth.near)` returns `None` → panic `ERR_FAILED_TO_GET_TOKEN_ADDRESS`. [4](#0-3) 
7. Transfer is permanently stuck. User's tokens are irreversibly burned. No user-accessible cancel or refund path exists. [5](#0-4)
