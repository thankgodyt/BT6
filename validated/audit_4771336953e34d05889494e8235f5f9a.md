### Title
Slot-Based `shelleyAfterVoting` Counter Counts Blocks Beyond the Stability Window, Enabling Premature Era Transition Under Chain Growth Violation — (`File: ouroboros-consensus-cardano/src/shelley/Ouroboros/Consensus/Shelley/Ledger/Ledger.hs`)

---

### Summary

The `ShelleyTransitionInfo.shelleyAfterVoting` counter, which gates whether the Hard Fork Combinator (HFC) reports a Shelley-family era transition as stable, counts **all** blocks whose slot is at or after the voting deadline — including blocks that fall outside the stability window. The intended design (documented in `civic_time.md` as "Iteration 4") requires counting only blocks within the one-stability-window (`3k/f` slots) immediately after the voting deadline. The current implementation counts blocks across the entire remaining epoch (up to `6k/f` slots after the deadline). Under a chain growth violation, this causes the HFC to prematurely declare an era transition stable, potentially triggering a cross-era divergence between nodes.

---

### Finding Description

`ShelleyTransitionInfo` holds a single field:

```haskell
newtype ShelleyTransition = ShelleyTransitionInfo
  { shelleyAfterVoting :: Word32
  -- ^ The number of blocks in this epoch past the voting deadline
  ...
  }
``` [1](#0-0) 

In `applyHelper`, the counter is incremented using a **slot-based** threshold:

```haskell
shelleyAfterVoting =
    (if blockSlot blk >= votingDeadline then succ else id) $
      shelleyAfterVoting tickedShelleyLedgerTransition
``` [2](#0-1) 

The `votingDeadline` is computed as:

```haskell
votingDeadline = subSlots (2 * swindow) startOfNextEpoch
``` [3](#0-2) 

where `swindow = SL.stabilityWindow globals` = `3k/f` slots. This places the voting deadline at `startOfNextEpoch − 6k/f`.

The counter therefore accumulates blocks from slot `startOfNextEpoch − 6k/f` all the way to `startOfNextEpoch` — a window of `6k/f` slots. However, the design intent (Iteration 4 in `civic_time.md`) is to count only blocks within the **one stability window** (`3k/f` slots) immediately after the voting deadline, i.e., from `startOfNextEpoch − 6k/f` to `startOfNextEpoch − 3k/f`. The document explicitly flags this:

> *(TODO this is today's intended behavior, but a bug is counting all blocks after the voting deadline instead of only those in the subsequent stability window.)* [4](#0-3) 

In `shelleyTransition`, the gate is:

```haskell
guard $ shelleyAfterVoting >= fromIntegral k
``` [5](#0-4) 

Because the counter spans `6k/f` slots instead of `3k/f`, blocks in the **last `3k/f` slots of the epoch** (between `startOfNextEpoch − 3k/f` and `startOfNextEpoch`) are incorrectly included. Under normal chain growth these extra blocks are harmless (the stability window already has ≥ k blocks). Under a chain growth violation — where the stability window contains fewer than k blocks — these extra blocks can push `shelleyAfterVoting` past the `k` threshold, causing the HFC to report the transition as stable when it should be suppressed.

The design intent is clear from the report:

> *"The consensus layer therefore does not use the ledger's layer notion of stability, but instead maintains additional state so that it can use block numbers rather than slot numbers to determine stability."* [6](#0-5) 

The Byron transition correctly uses block-depth (`isReallyStable` checks `distance >= k` in block numbers), explicitly noting the slot-based approach is unstable under fork switches: [7](#0-6) 

The Shelley counter, by contrast, uses a slot-based gate (`blockSlot blk >= votingDeadline`) and counts across a window twice as wide as intended.

---

### Impact Explanation

Under a chain growth violation (sparse chain), the stability window after the voting deadline may contain fewer than `k` blocks, but the broader `6k/f`-slot post-deadline window may accumulate `k` or more blocks. The bug causes `shelleyAfterVoting >= k` to become true prematurely, so `singleEraTransition` returns `Just epoch` and the HFC reports the era transition as stable. Nodes that correctly implement Iteration 4 (or future-patched nodes) would suppress the transition; nodes running the current code would proceed. This creates a cross-era divergence: some nodes transition to the next era while others remain in the current era, breaking cross-era consensus and ledger invariants. The `reconstructSummaryLedger` / `epochInfoLedger` path then produces divergent `EpochInfo` values, which propagate into header validation, leader schedule checks, and Plutus `txInfoValidRange` computations. [8](#0-7) [9](#0-8) 

---

### Likelihood Explanation

A chain growth violation is required. This is not a normal condition, but it is reachable: an adversary controlling a non-majority fraction of stake can withhold their own blocks to produce a sparse chain segment spanning the stability window after the voting deadline. No key compromise, admin access, or social engineering is needed — only the ability to selectively not produce blocks during a specific epoch window. The Praos security argument explicitly acknowledges chain growth violations as a possible (if unlikely) scenario, and the HFC's Iteration 4 was designed precisely to handle them. The bug undermines that protection.

---

### Recommendation

Restrict the `shelleyAfterVoting` counter to blocks whose slot falls within the one-stability-window interval after the voting deadline, i.e., `votingDeadline <= blockSlot blk < votingDeadline + swindow`. Alternatively, record the slot of the first post-deadline block and only count blocks within `swindow` slots of that anchor, consistent with the block-counting approach used in the Byron transition (`isReallyStable`) and described in the consensus report. [10](#0-9)

### Proof of Concept

**Setup**: A private testnet running a Shelley-era chain with `k = 2160`, `f = 0.05`, `swindow = 3k/f = 129600` slots.

1. The voting deadline for epoch `E` is at slot `startOfEpoch(E+1) − 6k/f = startOfEpoch(E+1) − 259200`.
2. An adversary withholds their blocks during the stability window `[votingDeadline, votingDeadline + 129600)`, so that window contains only `k − 1 = 2159` blocks (chain growth violation).
3. The adversary resumes block production normally in the final `3k/f` slots of the epoch `[startOfEpoch(E+1) − 129600, startOfEpoch(E+1))`, contributing 1 or more blocks.
4. Because `applyHelper` counts all blocks with `blockSlot >= votingDeadline`, the counter reaches `k = 2160` by including a block from the final window.
5. `shelleyTransition` returns `Just (E+1)`, and the HFC transitions to the next era.
6. A correctly-patched node (counting only the stability window) sees only `2159 < k` blocks in the stability window and suppresses the transition, remaining in the current era.
7. The two nodes now hold divergent ledger states and divergent `EpochInfo`, causing them to disagree on header validity and chain selection for all subsequent blocks. [11](#0-10) [12](#0-11) [13](#0-12)

  --
  -- We record this to make sure that we can tell the HFC about hard forks

  --    reached k of them, we know that that last pre-deadline block won't
  --    be rolled back anymore.

  --    a new protocol version update scheduled on the next epoch boundary,
  --    and notify the HFC that we need to transition into a new era at that

  -- Normally, stability in the ledger is defined in terms of slots, not
  -- blocks. Byron considers the proposal to be stable after the slot is more
  -- than @2k@ old. That is not wrong: after @2k@, the block indeed is stable.
  --
  -- Unfortunately, this means that the /conclusion about stability itself/
  -- is /not/ stable: if we were to switch to a denser fork, we might change
  -- our mind (on the sparse chain we thought the block was already stable,
  -- but on the dense chain we conclude it is it not yet stable).
  --
  -- It is unclear at the moment if this presents a problem; the HFC assumes
  -- monotonicity of timing info, in the sense that that any slot/time
  -- conversions are either unknown or else not subject to rollback.
  -- The problem sketched above might mean that we can go from "conversion
  -- known" to "conversion unknown", but then when we go back again to
  -- "conversion known", we /are/ guaranteed that we'd get the same answer.
  --
  -- Rather than trying to analyse this subtle problem, we instead base
  -- stability on block numbers; after the block is `k` deep, we know for sure
  -- that it is stable, and moreover, no matter which chain we switch to, that
  -- will remain to be the case.
  --
  -- The Byron 'UpdateState' records the 'SlotNo' of the block in which the
  -- proposal became a candidate (i.e., when the last required endorsement
  -- came in). That doesn't tell us very much, we need to know the block
  -- number; that's precisely what the 'ByronTransition' part of the Byron
  -- state tells us.
  isReallyStable :: BlockNo -> Bool
  isReallyStable (BlockNo bno) = distance >= CC.unBlockCount k
   where
    distance :: Word64
    distance = case byronLedgerTipBlockNo state of
      Origin -> bno + 1
      NotOrigin (BlockNo tip) -> tip - bno
