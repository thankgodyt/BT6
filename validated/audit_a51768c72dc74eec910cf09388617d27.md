Audit Report

## Title
Permanent Freezing of Bridged Funds When EVM Recipient Is Token-Blacklisted — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`OmniBridge.sol::finTransfer` unconditionally pushes tokens to `payload.recipient` via `safeTransfer`. If the recipient is blacklisted by a token with transfer restrictions (e.g., USDC), every finalization attempt reverts. Because the MPC signature commits to the exact recipient address and no public cancel or redirect mechanism exists on the NEAR side, tokens burned or locked on NEAR are permanently unrecoverable.

## Finding Description

In `finTransfer`, after signature verification, tokens are pushed directly to `payload.recipient`:

```solidity
// OmniBridge.sol L287
completedTransfers[payload.destinationNonce] = true;
// ...
// L351-354
IERC20(payload.tokenAddress).safeTransfer(
    payload.recipient,
    payload.amount
);
```

If `payload.recipient` is on the USDC blocklist, `safeTransfer` reverts, rolling back the entire transaction (including the nonce mark at L287). The nonce is never consumed, so the relayer can retry indefinitely — but every attempt reverts identically.

The MPC signature is computed over a borsh-encoded payload that includes `Borsh.encodeAddress(payload.recipient)` (L298), binding the signature to the exact recipient. No alternative recipient can be substituted without producing an `InvalidSignature` revert (L311-312). There is no mechanism to re-sign with a different recipient.

On the NEAR side, `sign_transfer_callback` removes the `pending_transfers` entry only when `fee.is_zero()` (L656-658) — but the tokens are already burned or locked at that point. For non-zero-fee transfers, the entry remains in `pending_transfers` indefinitely. The only public path that removes a `pending_transfers` entry is `claim_fee_callback` (L1057-1134), which requires a `ProverResult::FinTransfer` proof — a proof that can never be produced if `finTransfer` always reverts on the EVM side. The `remove_transfer_message` function is private and unreachable by users.

## Impact Explanation

This matches the allowed Critical impact: **permanent freezing of bridged funds across NEAR and EVM flows**.

- **Burned tokens** (deployed/bridged tokens on NEAR): burned on NEAR via `burn_tokens_if_needed` (L1851), never minted on EVM — permanently destroyed.
- **Locked tokens** (native NEAR tokens): locked in the NEAR bridge contract via `lock_tokens_if_needed` (L1853-1857), with no release path — permanently frozen.

## Likelihood Explanation

Low but realistic. USDC blacklisting is a documented real-world event (OFAC sanctions, exchange enforcement actions). A user whose EVM address is sanctioned after initiating a bridge transfer, or who unknowingly bridges to a sanctioned address, triggers this condition. No attacker action is required — the normal bridge flow is sufficient. The condition is also irreversible once triggered.

## Recommendation

Adopt a pull-over-push pattern for EVM token delivery. Instead of pushing tokens to `payload.recipient` inside `finTransfer`, record the claimable balance in a mapping and expose a separate `claimTransfer(nonce)` function. This decouples finalization (nonce consumption, accounting) from delivery, so a blacklisted recipient does not block the protocol and the user retains the ability to redirect funds via an alternative address.

## Proof of Concept

1. Alice holds USDC on NEAR and calls `ft_transfer_call` to bridge 1000 USDC to her EVM address `0xAlice`. NEAR burns the tokens and stores the `TransferMessage` in `pending_transfers` via `init_transfer_internal`.
2. Alice calls `sign_transfer`; the MPC signs a `TransferMessagePayload` with `recipient = 0xAlice`. If `fee.is_zero()`, the `pending_transfers` entry is removed in `sign_transfer_callback` — tokens are already burned.
3. Before the relayer submits the signature, `0xAlice` is added to the USDC blacklist on Ethereum.
4. The relayer calls `OmniBridge.finTransfer(sig, payload)`. Execution reaches L351: `IERC20(USDC).safeTransfer(0xAlice, 1000e6)`. USDC reverts because `0xAlice` is blacklisted. The entire transaction reverts, including the nonce mark at L287.
5. Every subsequent `finTransfer` attempt reverts identically. The signature cannot be reused with a different recipient (signature binds to `0xAlice` at L298/L311).
6. The NEAR `pending_transfers` entry (if fee was non-zero) can never be removed — `claim_fee_callback` requires a `FinTransfer` proof that can never be produced. Alice's 1000 USDC are permanently lost.
