### Title
`safe_mint` Permanently Locks nBTC When Recipient Account Is Unregistered - (File: `contracts/nbtc/src/lib.rs`)

### Summary

The `safe_mint` function in the nBTC token contract mints tokens to `bridge_id` **before** checking whether the intended recipient account is registered for storage. If the recipient is unregistered, the function silently returns `U128(0)` and the minted tokens remain permanently locked in the bridge account with no recovery path for the depositor.

### Finding Description

In `contracts/nbtc/src/lib.rs`, the `safe_mint` function executes in this order:

1. **Line 112**: `self.token.internal_deposit(&self.bridge_id, amount.into())` — unconditionally mints `amount` nBTC into the bridge's own account.
2. **Lines 114–116**: Checks whether `account_id` has a registered storage slot. If not, the function returns `PromiseOrValue::Value(U128(0))` immediately.
3. **Lines 118–123**: Only if the account is registered does it proceed to transfer the tokens from `bridge_id` to `account_id`. [1](#0-0) 

When the recipient is unregistered, the execution path is:

```
internal_deposit(bridge_id, amount)  ← tokens minted here
accounts.get(account_id).is_none()   ← true → early return U128(0)
                                      ← tokens never leave bridge_id
```

There is no `lost_found` entry created, no event emitted, and no operator-accessible recovery function that returns these specific tokens to the depositor. The `burn` function can withdraw from `bridge_id`, but it destroys the tokens rather than returning the underlying BTC to the user. [2](#0-1) 

The `lost_found` map used in `transfer_nbtc_callback` for failed transfers is never populated by `safe_mint`. [3](#0-2) 

### Impact Explanation

A user who deposits BTC to the bridge but has not pre-registered their NEAR account for nBTC storage will have their deposit processed on-chain (BTC is spent, SPV proof accepted), yet receive zero nBTC. The minted tokens accumulate silently in `bridge_id`. This constitutes **permanent locking of user funds** — the depositor loses their BTC with no on-chain recovery path. This matches the allowed impact: *Significant loss or permanent locking of user or protocol funds (Critical)*, or at minimum *broken callback rollback or stuck bridge state requiring operator intervention (Medium)*.

### Likelihood Explanation

The `safe_mint` entrypoint is the bridge's deposit path for users who may not have pre-registered. Any depositor who sends BTC without first calling `storage_deposit` on the nBTC contract triggers this path. This is a realistic scenario for new users unfamiliar with NEAR's storage model, and no on-chain guard prevents the bridge from calling `safe_mint` for an unregistered account.

### Recommendation

Reverse the order of operations: check registration **before** minting, and revert if the account is unregistered, so no tokens are created for an undeliverable recipient:

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "...");

    // Check BEFORE minting
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));
    }

    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ... proceed with transfer
}
```

Alternatively, on the unregistered path, add the amount to `lost_found` so an operator can later recover and forward the tokens once the user registers.

### Proof of Concept

1. Alice sends BTC to her bridge deposit address. The relayer submits a valid SPV proof; the bridge accepts it and calls `nbtc.safe_mint(alice.near, 100_000, None)`.
2. Inside `safe_mint`, `internal_deposit(&bridge_id, 100_000)` executes — 100,000 nBTC are now credited to `bridge_id`.
3. `self.token.accounts.get(&alice.near)` returns `None` (Alice never called `storage_deposit`).
4. The function returns `U128(0)`. Alice receives nothing.
5. The 100,000 nBTC sit in `bridge_id` indefinitely. Alice's BTC is spent on-chain and unrecoverable. [4](#0-3)
