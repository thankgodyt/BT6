### Title
`mkUpperBound` Propagates `NoPerasEnabled` Into First Peras-Enabled Era's Start Bound, Silently Disabling All Peras Round Queries and Skewing Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/HardFork/History/Summary.hs`)

---

### Summary

`mkUpperBound` computes the `boundPerasRound` field of an era's upper `Bound` using `<*>` on `PerasEnabled` (which is `Maybe`). Because `initBound` hard-codes `boundPerasRound = NoPerasEnabled`, the `Maybe`-applicative short-circuit propagates `NoPerasEnabled` into the start bound of the first Peras-enabled era, even when that era's `EraParams` carries a valid `eraPerasRoundLength`. Every downstream Peras round query (`slotToPerasRoundNo`, `perasRoundNoToSlot`, `EPerasRoundLength`) then silently returns `NoPerasEnabled` for that era, effectively treating it as a non-Peras era. Chain selection reverts to pure length comparison, and Peras voting is disabled for the entire first Peras era.

---

### Finding Description

**Root cause — `mkUpperBound`, line 130:**

```haskell
boundPerasRound = addPerasRounds <$> inEraPerasRounds <*> boundPerasRound lo
```

`PerasEnabled` is `newtype PerasEnabled a = MkPerasEnabled (Maybe a)` with the standard `Maybe` `Applicative`. Therefore `f <*> NoPerasEnabled = NoPerasEnabled` unconditionally. `inEraPerasRounds` is:

```haskell
inEraPerasRounds = div <$> PerasEnabled inEraSlots <*> (unPerasRoundLength <$> eraPerasRoundLength)
```

Even when `eraPerasRoundLength = PerasEnabled someLen` (Peras is enabled for this era), if `boundPerasRound lo = NoPerasEnabled`, the whole expression collapses to `NoPerasEnabled`.

**How `lo` becomes `NoPerasEnabled`:**

The chain of era bounds starts from `initBound`:

```haskell
initBound = Bound { ..., boundPerasRound = NoPerasEnabled }
```

The first era's upper bound is `mkUpperBound params initBound epochNo`. Its `boundPerasRound` is `NoPerasEnabled` (by the short-circuit above). That upper bound becomes the `eraStart` of the next era. If that next era is the first Peras-enabled era, its `eraStart.boundPerasRound = NoPerasEnabled`.

**How this poisons all Peras round queries for that era:**

In `Qry.hs`, every Peras-round expression handler reads `boundPerasRound eraStart` via `PerasEnabledT . Just`:

```haskell
go (EAbsToRelPerasRoundNo expr) =
  runPerasEnabledT $ do
    eraStartPerasRound <- PerasEnabledT . Just $ boundPerasRound eraStart
    ...
```

`PerasEnabledT . Just $ NoPerasEnabled` = `PerasEnabledT (Just NoPerasEnabled)`. When `runPerasEnabledT` unwraps this, the `PerasEnabledT` monad short-circuits to `NoPerasEnabled`. The same pattern applies to `ERelToAbsPerasRoundNo` (line 335–343) and `EPerasRoundLength` (line 390–397).

**The `summarize` workaround is test-only:**

The reference implementation `summarize` patches this with:

```haskell
initBoundWithPeras = initBound{boundPerasRound = PerasEnabled . PerasRoundNo $ 0}
```

but the comment explicitly states:

> *as noted in the haddock, this function is only used for testing purposes … TODO(geo2a): revisit this hard-coding of enabling Peras when we're further into the integration process*

The production path uses `reconstructSummaryLedger`, which reads `Bound` values from `HardForkState`. Those `Bound` values are computed by `mkUpperBound` without the workaround, so the production path inherits the same defect.

---

### Impact Explanation

**Chain selection is silently degraded.** `slotToPerasRoundNo` and `perasRoundNoToSlot` return `NoPerasEnabled` for every slot in the first Peras-enabled era. The `ChainDB` chain-selection logic (which was updated to use Peras weight via `PerasCertDB`) cannot compute Peras weight for any block in that era and falls back to pure chain-length comparison. An adversary who withholds Peras certificates but produces a marginally longer chain will be preferred by honest nodes over a shorter chain that carries valid Peras certificates — directly violating the Peras security assumption.

**Peras voting is silently disabled.** `perasRoundStart` in `Voting/View.hs` calls `HF.perasRoundNoToSlot`, which returns `NoPerasEnabled`, causing `perasRoundStart` to throw `PerasQryExceptionPerasDisabled`. Any component that relies on knowing the start slot of a Peras round (e.g., determining the candidate block horizon for voting) will fail or skip voting for the entire first Peras era.

---

### Likelihood Explanation

The defect is structural and deterministic: it fires for every node the moment the chain crosses into the first Peras-enabled era. No special adversarial setup is required to trigger it. The TODO comment in `summarize` confirms the developers identified the tension but deferred the fix. An unprivileged peer serving valid blocks in the first Peras era is sufficient to expose the degraded chain-selection behaviour.

---

### Recommendation

Fix `mkUpperBound` to bootstrap `boundPerasRound` from the era's own `eraPerasRoundLength` when the lower bound carries `NoPerasEnabled`:

```haskell
boundPerasRound =
  case (eraPerasRoundLength, boundPerasRound lo) of
    (PerasEnabled _, NoPerasEnabled) ->
      -- First Peras-enabled era: start round counter at 0
      PerasEnabled (PerasRoundNo 0)
    _ ->
      addPerasRounds <$> inEraPerasRounds <*> boundPerasRound lo
```

Alternatively, resolve the open TODO and make `initBound` configurable so that a Peras-enabled genesis can supply `PerasEnabled (PerasRoundNo 0)` from the start, consistent with what `summarize` already does for tests.
