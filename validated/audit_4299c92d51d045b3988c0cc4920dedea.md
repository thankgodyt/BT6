### Title
Missing Stake Normalization in `stakeAboveThreshold` Enables Quorum Bypass via Unit Mismatch — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` compares a `PerasVoteStake` value directly against `PerasQuorumStakeThreshold` without enforcing that both operands are expressed in the same units (absolute vs. relative/normalized). The function's own TODO comment explicitly acknowledges this assumption is unverified. If the `PerasVoteStakeDistr` supplied at runtime contains absolute ledger-stake values (e.g., lovelace amounts) while the quorum threshold is a relative fraction (e.g., `0.75`), then any voter with even a single lovelace of stake trivially satisfies the comparison, forging a Peras certificate unilaterally and bypassing the quorum requirement entirely.

---

### Finding Description

`stakeAboveThreshold` is defined as:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
``` [1](#0-0) 

The function's own documentation states:

> "TODO: this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … Under the current implementation of `PerasParams`, this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [2](#0-1) 

The companion note on `PerasVoteStake` itself confirms the ambiguity:

> "At the moment there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee." [3](#0-2) 

`stakeAboveThreshold` is called on the hot path in `votesReachQuorum`: [4](#0-3) 

and in `updateCandidateVoteState` (via `votesReachQuorum`) and `updateLoserVoteState`: [5](#0-4) [6](#0-5) 

The `PerasVoteStakeDistr` that feeds stake values into `validatePerasVote` — and therefore into `stakeAboveThreshold` — is supplied externally at runtime via an `STM` action in both production writers: [7](#0-6) [8](#0-7) 

`validatePerasVote` assigns the raw value from the distribution directly to `vpvVoteStake` with no normalization: [9](#0-8)

### Impact Explanation

If the `PerasVoteStakeDistr` is populated with absolute ledger-stake values (e.g., lovelace amounts such as `1_000_000`) while `perasQuorumStakeThreshold` is a relative fraction (e.g., `3 % 4` for 75%), then for any voter with positive stake:

```
1_000_000 >= (3/4 + safetyMargin)   -- always True
```

A single inbound vote from any registered stake pool immediately satisfies `stakeAboveThreshold`, causing `votesReachQuorum` to return `Just`, which triggers `forgePerasCert` and stores a certificate in the `PerasCertDB`. That certificate is then used to boost the chain weight of the voted-for block in chain selection, potentially causing honest nodes to prefer a non-canonical chain over the canonical one.

This is a bypass of the Peras quorum/certificate verification requirement — the entire purpose of the quorum threshold is to require a supermajority of stake to agree before a block is boosted, and that requirement is silently voided by the unit mismatch.

---

### Likelihood Explanation

The `PerasVoteStakeDistr` is injected at runtime from the ledger state. The code explicitly documents that the correct normalization strategy has not yet been decided. Any deployment that populates the distribution with raw lovelace values (the natural representation in the Cardano ledger) while leaving `perasQuorumStakeThreshold` as a relative fraction (its current type and documented intent) triggers the bypass. Any peer that is a registered stake pool — an unprivileged network participant — can send a single vote to exploit this.

---

### Recommendation

1. Enforce a single unit domain at the type level: introduce distinct newtypes for absolute and relative stake so the compiler rejects mixed comparisons.
2. Normalize `PerasVoteStake` values to relative fractions (dividing each voter's stake by the total stake in the distribution) before they are stored in `ValidatedPerasVote` or before `stakeAboveThreshold` is called.
3. Alternatively, change `stakeAboveThreshold` to accept the full `PerasVoteStakeDistr` and perform normalization internally, removing the assumption from the call sites.
4. Resolve the open research question referenced in the TODO comment before any production deployment of Peras voting.

---

### Proof of Concept

**Setup**: A private testnet running the Peras-enabled consensus layer. The `PerasVoteStakeDistr` is populated with absolute lovelace values (e.g., pool A has `1_000_000` lovelace). `perasQuorumStakeThreshold` is set to `3 % 4` (75%) and `perasQuorumStakeThresholdSafetyMargin` to `1 % 100`.

**Attack sequence**:
1. Attacker controls pool A (1 lovelace of stake, far below any honest quorum).
2. Attacker sends a single `PerasVote` for a non-canonical block B' via the Peras vote mini-protocol.
3. `processVotes` → `validatePerasVote` looks up pool A in the distribution, assigns `vpvVoteStake = PerasVoteStake (1_000_000 % 1)`.
4. `updateCandidateVoteState` → `votesReachQuorum` → `stakeAboveThreshold`: `1_000_000 >= (3/4 + 1/100)` evaluates to `True`.
5. `forgePerasCert` is called; a `ValidatedPerasCert` for B' is stored in the `PerasCertDB`.
6. Chain selection applies the `PerasWeight` boost to B', causing the node to prefer B' over the honest canonical chain.

**Expected (correct) behavior**: The single vote from pool A should contribute at most `1_000_000 / total_stake` ≈ 0 relative stake, far below the 75% quorum threshold, and no certificate should be forged.
