Audit Report

## Title
Token-2022 TransferFee Extension Causes Vault Undercollateralization via Silent Fee Withholding — (`solana/programs/bridge_token_factory/src/instructions/user/init_transfer.rs`)

## Summary

When a Token-2022 mint with the TransferFee extension is registered via the permissionless `log_metadata` and then bridged via `init_transfer`, `transfer_checked` silently withholds a fee from the vault (destination), so the vault receives `amount - fee` while the Wormhole message reports the full `payload.amount`. NEAR mints the full amount. The deficit compounds with every transfer, and eventually `finalize_transfer` reverts for the last users because the vault's spendable balance is exhausted, causing permanent loss of bridged funds.

## Finding Description

`init_transfer` handles native tokens by calling `transfer_checked` with the full `payload.amount`: [1](#0-0) 

For a Token-2022 mint with the TransferFee extension, `transfer_checked` credits the vault with `amount - withheld_fee`. The withheld fee is stored inside the vault's token account data and is only claimable by the token's fee authority — not by the bridge program. Immediately after, the program posts a Wormhole message containing the original, unreduced `payload.amount`: [2](#0-1) 

NEAR reads this VAA and mints the full `payload.amount` to the recipient. The vault is now undercollateralized by the withheld fee for every such transfer.

Registration is permissionless: any caller can invoke `log_metadata` for any mint whose `mint_authority` is not the bridge authority. There is no inspection of Token-2022 extensions on the mint — no rejection of TransferFee, ConfidentialTransfer, or any other transfer-altering extension: [3](#0-2) 

On the return path, `finalize_transfer` calls `transfer_checked` from the vault using the full signed `data.amount` from the VAA: [4](#0-3) 

Once the vault's spendable balance is exhausted, this call reverts. The last users to bridge back permanently lose their tokens.

The `solana/SECURITY.md` only acknowledges transfer hooks as unsupported (causing runtime failure, not fund loss), and says nothing about the TransferFee extension: [5](#0-4) 

The EVM `SECURITY.md` explicitly documents fee-on-transfer tokens as unsupported, but no equivalent exclusion exists for Solana: [6](#0-5) 

## Impact Explanation

**Critical — balance manipulation / escrow mis-accounting causing permanent loss of bridged funds.** This matches the allowed impact class: *"Balance manipulation, escrow mis-accounting, fee mis-accounting... that changes user or protocol balances."* For every `init_transfer` of a TransferFee-enabled Token-2022 mint, the vault accrues a deficit equal to the withheld fee. The deficit is irreversible (withheld balance is inaccessible to the bridge). The last users to bridge back to Solana lose their full bridged token balances permanently.

## Likelihood Explanation

**Medium-High.** Token-2022 with TransferFee is a production-grade, widely deployed Solana extension used by multiple DeFi protocols. The program explicitly targets Token-2022 compatibility via `TokenInterface`. `log_metadata` is fully permissionless — no admin action or special privilege is required. Any unprivileged user can register a qualifying mint and begin transferring. The deficit is small per transfer but compounds linearly and is irreversible.

## Recommendation

**Short term**: In `init_transfer`, after calling `transfer_checked`, read the vault's post-transfer token balance and use the actual received amount (not `payload.amount`) in the Wormhole message. This requires a reload of the vault account after the CPI.

**Long term**: In `log_metadata`, after unpacking the mint with `StateWithExtensions`, enumerate Token-2022 extensions and reject any mint that has `TransferFeeConfig`, `ConfidentialTransferMint`, or any other extension that alters transfer semantics. This is consistent with the existing design decision to reject transfer hooks and would prevent the class of issue entirely at registration time.

## Proof of Concept

1. Deploy a Token-2022 mint on Solana devnet with `TransferFeeConfig` set to 1% fee (100 bps).
2. Call `log_metadata` (permissionless) — vault PDA is created for the mint with no extension check.
3. User A calls `init_transfer` with `payload.amount = 1_000_000`. `transfer_checked` deposits `990_000` into the vault (10_000 withheld as fee). Wormhole message reports `1_000_000`. NEAR mints `1_000_000` to User A.
4. Repeat for 100 users. Vault holds `99_000_000` spendable tokens; NEAR has minted `100_000_000`.
5. First 99 users bridge back: each `finalize_transfer` of `1_000_000` succeeds until vault spendable balance reaches `0`.
6. User 100's `finalize_transfer` reverts — vault has `0` spendable balance. User 100 permanently loses `1_000_000` bridged tokens.

A local integration test can demonstrate this by: (a) initializing a Token-2022 mint with `TransferFeeConfig`, (b) calling `log_metadata` and `init_transfer` in sequence, (c) asserting that `vault.amount < payload.amount` after the transfer, and (d) asserting that `finalize_transfer` reverts after sufficient deficit accumulation.
