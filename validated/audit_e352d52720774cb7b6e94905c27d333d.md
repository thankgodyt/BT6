Audit Report

## Title
Missing `chain_id` in `MetadataPayload::to_borsh` Enables Cross-Chain Replay of `deploy_token` MPC Signatures — (`starknet/src/bridge_types.cairo`)

## Summary

`MetadataPayload::to_borsh` serializes the `deploy_token` signed payload without any chain identifier, producing identical Borsh bytes regardless of which OmniBridge instance is targeted. Because the same `omni_bridge_derived_address` (MPC-derived Ethereum key) is shared across all deployments by design, a valid `deploy_token` signature accepted on one Starknet instance can be replayed verbatim on any other instance, registering an unauthorized bridge token and enabling subsequent unauthorized minting via `fin_transfer`.

## Finding Description

`MetadataPayload::to_borsh` encodes only `[payload_type=1, token, name, symbol, decimals]` with no chain binding: [1](#0-0) 

By contrast, `TransferMessagePayload::to_borsh` accepts a `chain_id: u8` parameter and embeds it at two positions in the serialized payload: [2](#0-1) 

`deploy_token` calls `payload.to_borsh()` with no chain argument and passes the result directly to `_verify_borsh_signature`: [3](#0-2) 

`_verify_borsh_signature` verifies the Keccak hash of those bytes against the shared `omni_bridge_derived_address`: [4](#0-3) 

The only guard that could block a replay is the idempotency check on `near_to_starknet_token`: [5](#0-4) 

This mapping is per-contract-instance, so it provides no cross-chain protection. `fin_transfer`, by contrast, correctly binds the signature to the target chain by passing `self.omni_bridge_chain_id.read()` into `to_borsh`: [6](#0-5) 

**Exploit flow:**
1. Attacker observes a valid `(signature, MetadataPayload)` accepted by `deploy_token` on instance A (`omni_bridge_chain_id = 1`).
2. Attacker submits the identical pair to instance B (`omni_bridge_chain_id = 2`). Because `MetadataPayload::to_borsh` produces the same bytes on both instances, `_verify_borsh_signature` accepts the signature.
3. The token is registered in `starknet_to_near_token` and `near_to_starknet_token` on instance B.
4. `fin_transfer` on instance B checks `is_bridge_token` — which reads `starknet_to_near_token` — and calls `mint` on the newly registered token, minting assets the MPC never authorized for chain B. [7](#0-6) 

## Impact Explanation

This is a **Critical** cross-chain domain separation flaw enabling unauthorized minting of bridged assets. Once a token is replayed onto instance B, any attacker can call `fin_transfer` on B with a crafted `TransferMessagePayload` (which does include `chain_id` and thus requires a valid MPC signature for chain B's transfers — but the token registration itself is the prerequisite that `fin_transfer` checks via `is_bridge_token`). The registered token's `mint` function is callable by the bridge, enabling unauthorized creation of bridged tokens on chain B for transfers the MPC never signed for that chain. This matches the allowed impact: *cross-chain replay / chain/domain separation flaw enabling unauthorized minting of bridged assets*. [8](#0-7) 

## Likelihood Explanation

The precondition — the same `omni_bridge_derived_address` across multiple Starknet OmniBridge deployments — is the stated protocol design (one MPC key governs all chains). Valid `deploy_token` signatures are publicly observable on-chain the moment any token is deployed on any instance. No privileged access, key compromise, or threshold collusion is required. The replay is a single public transaction requiring only copying observed calldata. [9](#0-8) 

## Recommendation

Add `chain_id` to `MetadataPayload::to_borsh`, mirroring the pattern in `TransferMessagePayload::to_borsh`:

```cairo
fn to_borsh(self: @MetadataPayload, chain_id: u8) -> ByteArray {
    let mut borsh_bytes: ByteArray = Default::default();
    borsh_bytes.append_byte(PayloadType::Metadata.into());
    borsh_bytes.append_byte(chain_id);  // <-- add this
    borsh_bytes.append(@borsh::encode_byte_array(self.token));
    borsh_bytes.append(@borsh::encode_byte_array(self.name));
    borsh_bytes.append(@borsh::encode_byte_array(self.symbol));
    borsh_bytes.append_byte(*self.decimals);
    borsh_bytes
}
```

Update `deploy_token` to pass `self.omni_bridge_chain_id.read()` to `to_borsh`. Ensure the MPC signing service includes `chain_id` when producing `deploy_token` signatures so that existing signatures are invalidated on other chains. [1](#0-0) 

## Proof of Concept

1. Deploy two OmniBridge instances A (`omni_bridge_chain_id = 1`) and B (`omni_bridge_chain_id = 2`) with the same `omni_bridge_derived_address`.
2. Call `deploy_token` on instance A with a valid MPC-signed `(signature, MetadataPayload{token: "near.token", ...})`. Observe the call succeeds and the `DeployToken` event is emitted.
3. Submit the identical `(signature, MetadataPayload)` to instance B's `deploy_token`. `MetadataPayload::to_borsh` produces the same bytes; `_verify_borsh_signature` accepts the signature; `near_to_starknet_token` on B is empty for this token so the idempotency check passes. The call succeeds.
4. Confirm `near_to_starknet_token` and `starknet_to_near_token` on B are now populated for `"near.token"`.
5. Call `fin_transfer` on B with a `TransferMessagePayload` targeting the newly registered token address. `is_bridge_token` returns `true`; `mint` is called; tokens are minted on chain B without MPC authorization for that chain.

    fn _verify_borsh_signature(
        ref self: ContractState, borsh_bytes: @ByteArray, signature: Signature,
    ) {
        let message_hash_le = compute_keccak_byte_array(borsh_bytes);
        let message_hash = reverse_u256_bytes(message_hash_le);

        let sig = signature_from_vrs(signature.v, signature.r, signature.s);
        verify_eth_signature(message_hash, sig, self.omni_bridge_derived_address.read());
    }
