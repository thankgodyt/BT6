### Title
Permissionless `request_refund` Allows Any Caller to Front-Run and Block a Victim's Refund Request, Temporarily Locking Their BTC — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

`request_refund` carries no restriction on who may call it for a given UTXO. When `deposit_msg.refund_address` is `None`, any NEAR account can supply an arbitrary attacker-controlled BTC `refund_address`. A duplicate-request guard then prevents the legitimate depositor from filing their own request, temporarily locking their BTC until the DAO rejects the fraudulent entry. This is a direct analog of the `unstakeDelay` DoS: a third party resets/hijacks a time-gated state on behalf of a victim at negligible cost.

---

### Finding Description

`request_refund` is a public, payable function with no check that the caller is the `deposit_msg.recipient_id` or any other authorized party: [1](#0-0) 

The only caller-sensitive guard is on the optional `gas_fee` parameter. The `refund_address` argument is accepted verbatim from the caller when `deposit_msg.refund_address` is `None`: [2](#0-1) 

In `request_refund_callback`, the caller-supplied `refund_address` is stored directly into the `RefundRequest`: [3](#0-2) 

A duplicate-request guard then prevents any second `request_refund` for the same UTXO: [4](#0-3) 

Once a fraudulent request exists, the legitimate depositor is locked out. The `unsafe_refund_timelock_sec` (14 days by default) applies because the attacker's request has no pre-authorized `refund_address`: [5](#0-4) [6](#0-5) 

After the timelock, `execute_refund` is also callable by anyone and uses the stored `refund_address` to build the BTC output: [7](#0-6) [8](#0-7) 

The `deposit_msg` embedded in every BTC transaction is public on-chain data, so the attacker can reconstruct it without any privileged access.

---

### Impact Explanation

**Primary (Medium) — Attacker-triggered temporary locking of bridged funds.**

Alice's BTC UTXO is locked in a fraudulent refund request until the DAO/Operator rejects it. Alice cannot file her own request (duplicate guard). The attacker can repeat the front-run immediately after each DAO rejection, creating a persistent DoS at the cost of only the NEAR storage deposit per round (which is non-refundable but small).

**Secondary (Critical, conditional) — Theft of BTC if DAO does not reject within 14 days.**

If the DAO is slow or inactive, `execute_refund` can be called by anyone after `unsafe_refund_timelock_sec`, sending Alice's BTC to the attacker's address. The `finalize_refund_with_psbt` function uses the stored `refund_address` without re-validating ownership: [9](#0-8) 

---

### Likelihood Explanation

- `deposit_msg` is public Bitcoin on-chain data; no privileged access is needed.
- The only cost per attack is the NEAR storage deposit for `request_refund`, which is non-refundable but small relative to any meaningful BTC deposit.
- Front-running on NEAR is straightforward since transaction ordering is observable in the mempool.
- The persistent DoS variant (re-submitting after each DAO rejection) requires no special timing.

---

### Recommendation

1. **Restrict the caller**: require `env::predecessor_account_id() == deposit_msg.recipient_id` inside `request_refund` (or `request_refund_callback`) so only the intended beneficiary can open a refund for their UTXO.
2. **Alternatively**, require `deposit_msg.refund_address` to be non-`None` for permissionless calls, so the BTC destination is fixed at deposit time and cannot be attacker-controlled.
3. As a defense-in-depth measure, consider emitting a richer on-chain event that monitoring infrastructure can use to detect mismatched `recipient_id` vs. caller.

---

### Proof of Concept

1. Alice sends 1 BTC to the bridge with `deposit_msg = { recipient_id: "alice.near", refund_address: None, … }`. The deposit fails to process (e.g., below `min_deposit_amount`).
2. Mallory observes the BTC transaction, reconstructs `deposit_msg`, and calls `request_refund(deposit_msg, mallory_btc_addr, tx_bytes, vout, proof, None)` with a valid Light Client proof — paying only the NEAR storage deposit.
3. `request_refund_callback` stores `RefundRequest { refund_address: mallory_btc_addr, created_at_sec: now, … }`.
4. Alice calls `request_refund` with her own BTC address → panics: `"Refund request already exists for this UTXO"`. Alice's BTC is locked.
5. If the DAO rejects Mallory's request, Mallory immediately repeats step 2, re-locking Alice's funds.
6. If the DAO does not reject within 14 days, Mallory calls `execute_refund(utxo_storage_key, None)` → `internal_execute_refund` builds a BTC transaction paying `mallory_btc_addr` → Alice's 1 BTC is stolen.

    pub(crate) fn internal_execute_refund(
        &mut self,
        utxo_storage_key: String,
        timelock_sec: u64,
        _chain_specific_data: Option<ChainSpecificData>,
    ) -> PromiseOrValue<()> {
        let refund_request = self.load_refund_request_for_execute(&utxo_storage_key, timelock_sec);
        let RefundExecutionInputs {

            deposit_output,
            refund_amount,

        let refund_output = self.build_refund_output(&refund_request.refund_address, refund_amount);

        let mut psbt = PsbtWrapper::new(vec![outpoint], vec![refund_output]);
        psbt.set_input_utxo(vec![deposit_output]);

            caller,
            refund_request,
            psbt,
            refund_amount,
            utxo_storage_key,
        );
