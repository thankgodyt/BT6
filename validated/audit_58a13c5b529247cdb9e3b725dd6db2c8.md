### Title
Mismatched Stake Units in Peras Quorum Check Allows Certificate Forgery with Insufficient Stake - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` in `SupportsPeras.hs` directly compares a `PerasVoteStake` value (whose unit — absolute lovelace vs. normalized fraction — is explicitly undefined and unenforceable) against `perasQuorumStakeThreshold`, which is a relative fraction (`3/4`). The code itself documents this mismatch in a TODO comment. When the `PerasVoteStakeDistr` is populated with absolute ledger stake values (as will happen in production), the sum of even a single vote's stake will vastly exceed the relative threshold `3/4`, causing the quorum check to always pass. This allows an unprivileged peer to trigger Peras certificate forgery for an arbitrary block with a single vote, bypassing the quorum requirement entirely.

---

### Finding Description

`PerasVoteStake` is a bare `Rational` newtype with no enforced unit: [1](#0-0) 

The code explicitly acknowledges the unit ambiguity in a comment immediately above `stakeAboveThreshold`: [2](#0-1) 

The quorum threshold in `PerasParams` is a relative fraction (e.g., `3/4`): [3](#0-2) [4](#0-3) 

`validatePerasVote` assigns the raw value from `PerasVoteStakeDistr` directly to `vpvVoteStake` with no normalization: [5](#0-4) 

`votesReachQuorum` then sums these raw stakes and passes the total directly to `stakeAboveThreshold`: [6](#0-5) 

The production vote-diffusion path (`makePerasVotePoolWriterFromChainDB`) currently passes an empty `PerasVoteStakeDistr` as a placeholder, with a TODO noting that the real ledger stake distribution will be wired in: [7](#0-6) 

When the real ledger stake distribution is wired in (as intended), the `PerasVoteStake` values will be absolute lovelace quantities (e.g., `1_000_000_000_000` for a 1M ADA pool). Summing even one such value and comparing it against the relative threshold `3/4` will always yield `True`, because `1_000_000_000_000 >= 3/4`.

The same mismatch is present in the `PerasVoteDB` model's `stakeAboveThreshold` calls: [8](#0-7) 

And in the vote aggregation path: [9](#0-8) 

---

### Impact Explanation

Peras certificates boost a block's chain weight by `perasWeight` (currently `15`). A node that accepts a fraudulently forged certificate will prefer the boosted chain over the canonical chain, causing a chain selection divergence. Because the quorum check is the sole gate before `forgePerasCert` is called, bypassing it means an adversary can cause any honest node to permanently adopt a non-canonical chain with a single crafted vote. This matches the **High** impact category: a chain selection bug triggered by an unprivileged peer via a crafted network message.

---

### Likelihood Explanation

The vulnerability is latent today (the empty `PerasVoteStakeDistr` placeholder prevents exploitation) but will become active the moment the ledger stake distribution is wired into the vote-diffusion path, which is the explicitly stated next step in the codebase. The attacker entry point is the Peras vote diffusion mini-protocol, which is open to any peer. The attacker only needs to send a single vote from any pool that appears in the ledger stake distribution.

---

### Recommendation

1. **Enforce units at the type level.** Introduce separate newtypes for absolute stake (`AbsolutePerasVoteStake`) and normalized stake (`NormalizedPerasVoteStake`), and require `stakeAboveThreshold` to accept only the normalized variant.
2. **Normalize before comparison.** `stakeAboveThreshold` (or its callers) must divide each voter's absolute stake by the total committee stake before summing and comparing against the relative threshold. Alternatively, convert the threshold to absolute units before comparison.
3. **Remove the TODO and enforce the invariant.** The comment at lines 155–161 of `SupportsPeras.hs` documents a known unit mismatch. This must be resolved before the real stake distribution is wired in, not after.

---

### Proof of Concept

Assume a stake distribution with one pool holding 1,000,000 ADA (= `1_000_000_000_000` lovelace), stored as-is in `PerasVoteStakeDistr`:

```
stakeDistr = PerasVoteStakeDistr { poolA -> PerasVoteStake (1_000_000_000_000 % 1) }
```

An adversary sends a single `PerasVote` for an arbitrary block, signed by `poolA`. `validatePerasVote` looks up `poolA` in `stakeDistr` and assigns `vpvVoteStake = 1_000_000_000_000`. `votesReachQuorum` calls `stakeAboveThreshold` with `totalVoteStake = 1_000_000_000_000`:

```
stake (1_000_000_000_000) >= quorumThreshold (3/4) + safetyMargin (2/100)
-- => True (trivially)
```

`forgePerasCert` is called, producing a `ValidatedPerasCert` boosting the adversary's chosen block by `perasWeight = 15`. The node's chain selection now prefers this adversarially-boosted chain over the honest canonical chain.
