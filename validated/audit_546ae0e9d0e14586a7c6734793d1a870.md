### Title
`validatePerasCert` Unconditionally Accepts All Peras Certificates, Enabling Fraudulent Chain-Selection Weight Boosts - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The sole `BlockSupportsPeras` instance's `validatePerasCert` implementation always returns `Right` regardless of certificate content, performing no cryptographic or structural validation. This is the direct analog of the Liquidator's missing `require` on `ERC20Helper.transfer`: a critical check is absent, so the operation proceeds as if it succeeded even when it should fail. Any unprivileged peer can send a crafted `PerasCert` with an arbitrary `pcCertBoostedBlock`, which will be accepted by `processCerts`, stored in the `PerasCertDB`, and then used to trigger chain selection with a fraudulent Peras weight boost, potentially causing an honest node to switch to a non-canonical chain.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub used in production:**

The only `BlockSupportsPeras` instance is a universal one (`instance StandardHash blk => BlockSupportsPeras blk`). Its `validatePerasCert` method unconditionally wraps the input certificate in `Right` without inspecting any field:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

There are no other instances of `BlockSupportsPeras` in the codebase — this stub is the only implementation for all block types, including production Cardano blocks. [2](#0-1) 

**Production inbound path — `processCerts` calls `validatePerasCert` and adds accepted certs to ChainDB:**

The production pool writer `makePerasCertPoolWriterFromChainDB` passes `validatePerasCert mkPerasParams` as the validation function to `processCerts`:

```haskell
opwAddObjects = \certs ->
    processCerts
      systemTime
      (ChainDB.getPerasCertIds chainDB)
      (validatePerasCert mkPerasParams)   -- always returns Right
      (void . ChainDB.addPerasCertAsync chainDB)
      certs
``` [3](#0-2) 

`processCerts` partitions validation results: if all certs pass (which they always do), each is timestamped and forwarded to `addCert`. Since `validatePerasCert` never returns `Left`, the `throw (PerasCertValidationError errs)` branch is unreachable: [4](#0-3) 

**Chain selection impact — accepted cert triggers weight-boosted chain selection:**

`chainSelSync` processes each accepted certificate. It adds it to `PerasCertDB`, then looks up the `pcCertBoostedBlock` in the `VolatileDB`. If the block is present, it calls `chainSelectionForBlock` for that block, which re-evaluates all candidate chains using `preferAnchoredCandidate` with the new `PerasWeightSnapshot` that now includes the fraudulent boost: [5](#0-4) 

`preferAnchoredCandidate` uses `weightedSelectView`, which sums `wsvBlockNo` and `wsvWeightBoost` into a `wsvTotalWeight`. A fraudulent certificate can make a shorter competing chain appear heavier than the honest chain: [6](#0-5) 

---

### Impact Explanation

**Impact: High — Chain selection bug enabling non-canonical chain preference.**

An unprivileged peer can craft a `PerasCert` with `pcCertBoostedBlock` pointing to any block in the target node's `VolatileDB`. Because `validatePerasCert` always returns `Right`, the cert bypasses all validation and is stored. The resulting `vpcCertBoost = perasWeight params` is then applied to that block's chain fragment during `preferAnchoredCandidate`, potentially making a shorter or otherwise non-preferred fork appear heavier than the honest chain. The node then switches to that fork, diverging from the canonical chain. This satisfies the "High" impact category: a chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain beyond the intended security assumptions.

---

### Likelihood Explanation

**Likelihood: Medium.**

The Peras object-diffusion miniprotocol is the attacker-controlled entry point — any peer that the node connects to can send `PerasCert` objects. The attacker needs only to know a block hash present in the target's `VolatileDB` (observable via the ChainSync protocol) and send a certificate boosting it. No key material, stake, or operator access is required. The constraint is that Peras must be active/enabled on the network; the code is under active development but the production path is wired up.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies the certificate's aggregate BLS signature, committee membership, round number bounds, and boosted-block validity before returning `Right`. Until real validation is implemented, the inbound `processCerts` path should reject all externally received certificates (e.g., return `Left PerasValidationErr` unconditionally) rather than accept them all. The pattern should mirror the existing `validatePerasVote` which at minimum checks stake-distribution membership before accepting.

---

### Proof of Concept

1. Node A is running with Peras enabled. Its `VolatileDB` contains block `B` at hash `H` on a competing fork `F` that is currently shorter than the canonical chain `C`.
2. Attacker peer connects to Node A via the object-diffusion miniprotocol and sends a single `PerasCert { pcCertRound = r, pcCertBoostedBlock = BlockPoint s H }`.
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })` unconditionally.
4. `addPerasCertAsync chainDB` is called; `chainSelSync` processes the cert.
5. `VolatileDB.getBlockComponent cdbVolatileDB GetHeader H` succeeds (block is present).
6. `chainSelectionForBlock` is triggered for block `B`; `preferAnchoredCandidate` now computes `wsvTotalWeight` for fork `F` including the fraudulent `vpcCertBoost`.
7. If `perasWeight params` is large enough, `wsvTotalWeight(F) > wsvTotalWeight(C)`, and Node A switches to fork `F`, diverging from the canonical chain. [7](#0-6) [8](#0-7)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
