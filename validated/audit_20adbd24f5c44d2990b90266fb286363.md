Audit Report

## Title
Re-entrancy via Malicious ERC-1155/ERC-20 Token Causes `originNonce` Collision and Permanent Freezing of Bridged Funds — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`initTransfer` and `initTransfer1155` both increment `currentOriginNonce` at the top of the function but then read `currentOriginNonce` again from storage after an external token-transfer call when passing it to `initTransferExtension` and `emit InitTransfer`. A malicious ERC-1155 token (or ERC-777 token) can re-enter either function during the external call, advance `currentOriginNonce` a second time, and cause the outer call to emit an `InitTransfer` event with the same `originNonce` as the inner call. The NEAR side processes the first event and permanently ignores the second, locking the outer call's tokens in the bridge with no recovery path.

## Finding Description

**Root cause:** `currentOriginNonce` is a storage variable that is incremented once at the top of each function but then re-read from storage after an external call, rather than being snapshotted into a local variable before the external call.

In `initTransfer1155` (lines 448–489):

```
currentOriginNonce += 1;                          // (1) storage becomes N
...
IERC1155(tokenAddress).safeTransferFrom(          // (2) external call to arbitrary token
    msg.sender, address(this), tokenId, amount, ""
);
...
initTransferExtension(..., currentOriginNonce, ...); // (3) re-reads storage — may be N+1
emit BridgeTypes.InitTransfer(..., currentOriginNonce, ...); // (4) re-reads storage
``` [1](#0-0) 

In `initTransfer` (lines 381–436), the same pattern applies: `currentOriginNonce` is incremented at line 381, an external `safeTransferFrom` is made at lines 395–411, and `currentOriginNonce` is re-read at lines 418 and 430. [2](#0-1) 

**No reentrancy guard exists.** The contract imports no `ReentrancyGuard` or `ReentrancyGuardUpgradeable`, and the `whenNotPaused` modifier only checks pause state.

**The `onERC1155Received` guard does not block this attack.** The guard at lines 522–535 checks `operator != address(this)` and reverts if the operator is not the bridge. In `initTransfer1155`, the bridge itself calls `safeTransferFrom`, so `operator == address(this)` — the guard passes. More critically, the re-entry occurs *inside the malicious token's `safeTransferFrom` body*, before `onERC1155Received` is ever invoked. The guard only prevents direct ERC-1155 sends to the bridge, not re-entry through a malicious token's transfer implementation. [3](#0-2) 

**Exploit trace for `initTransfer1155`:**

```
currentOriginNonce = 5 (before attack)

Outer call: initTransfer1155(MaliciousERC1155, ...)
  (1) currentOriginNonce = 6
  (2) MaliciousERC1155.safeTransferFrom → re-enters initTransfer1155
        Inner call:
          (1) currentOriginNonce = 7
          (2) MaliciousERC1155.safeTransferFrom → transfers normally
          (3) initTransferExtension(..., nonce=7, ...)
          (4) emit InitTransfer(originNonce=7)   ← INNER event
        returns
  (3) initTransferExtension(..., currentOriginNonce=7, ...)  ← reads 7, not 6
  (4) emit InitTransfer(originNonce=7)   ← OUTER event, SAME nonce

Result:
  - originNonce 6 never emitted
  - originNonce 7 emitted twice
  - Outer call's tokens locked permanently
```

This directly violates the documented invariant in `evm/CLAUDE.md`:

> "State before external calls: Always mutate state (e.g. mark nonce used) before any external call (token transfer, ETH send, custom minter). This is the primary reentrancy defense" [4](#0-3) 

## Impact Explanation

The NEAR side reconstructs transfers solely from `InitTransfer` events, using `origin_nonce` as the unique transfer identifier. Two `InitTransfer` events with identical `originNonce` are indistinguishable to the NEAR prover: it processes the first and permanently ignores the second. The outer call's tokens — already transferred into the bridge contract at line 458–464 — are locked with no admin-recovery function and no mechanism to re-submit the proof. This constitutes **permanent freezing of bridged funds**, matching the Critical allowed impact scope. The nonce gap (N never emitted) additionally breaks off-chain indexers and relayers that rely on sequential nonce ordering.

## Likelihood Explanation

For `initTransfer1155`, the attack requires only:
1. Deploying a malicious ERC-1155 token (no permission needed).
2. Calling the permissionless `logMetadata1155` to register it with the bridge (lines 234–270).
3. Calling `initTransfer1155` with the malicious token. [5](#0-4) 

No admin keys, MPC compromise, front-running, or external dependency failure are required. Any unprivileged user can execute this on-chain. For `initTransfer`, the same applies using an ERC-777 token registered via the permissionless `logMetadata`.

## Recommendation

Capture `currentOriginNonce` into a local variable immediately after incrementing it, before any external call, and use only that local variable in `initTransferExtension` and `emit`:

```solidity
// initTransfer1155
currentOriginNonce += 1;
uint64 nonce = currentOriginNonce;   // snapshot before external calls
...
IERC1155(tokenAddress).safeTransferFrom(...);
...
initTransferExtension(..., nonce, ...);
emit BridgeTypes.InitTransfer(..., nonce, ...);
```

Apply the same fix to `initTransfer`. As defense-in-depth, add OpenZeppelin's `ReentrancyGuardUpgradeable` with a `nonReentrant` modifier to both functions.

## Proof of Concept

**Minimal contract sequence (private testnet):**

1. Deploy `MaliciousERC1155` whose `safeTransferFrom` re-enters `initTransfer1155` on the first call and transfers normally on the second (inner) call.
2. Call `bridge.logMetadata1155(MaliciousERC1155, tokenId)` to register the token.
3. Call `bridge.initTransfer1155(MaliciousERC1155, tokenId, amount, fee, nativeFee, recipient, "")`.
4. Observe two `InitTransfer` events emitted in the same transaction with identical `originNonce` values, and verify that `originNonce - 1` was never emitted.
5. Submit the proof for the second event to the NEAR side and confirm it is rejected as a duplicate, while the tokens from the outer call remain permanently locked in the bridge.

**Invariant fuzz test:** Assert that after any sequence of `initTransfer1155` calls (including re-entrant ones), all emitted `originNonce` values are strictly monotonically increasing with no gaps and no duplicates.
