### Title
Missing Account-Registration Check Before Token Minting in `safe_mint` Causes Permanent Supply/Accounting Discrepancy — (File: contracts/nbtc/src/lib.rs)

---

### Summary

The `safe_mint` function in the nBTC token contract unconditionally mints tokens into the bridge's own balance **before** verifying that the intended recipient account is registered. When the recipient is unregistered, the function silently returns `U128(0)` — signalling to the bridge that zero tokens were minted — while `amount` tokens have already been permanently deposited into the bridge's balance. This is a direct analog to the "Absence of Check on Initial Tokens Minted" class: a missing pre-condition check before a mint operation produces an irrecoverable supply/accounting discrepancy.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, `safe_mint` executes as follows:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into()); // ← tokens minted here

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));                   // ← early return, tokens already minted
    }
    ...
}
``` [1](#0-0) 

The call to `self.token.internal_deposit(&self.bridge_id, amount.into())` increases the NEP-141 total supply by `amount` and credits those tokens to `bridge_id`. Only **after** this irreversible state change does the function check whether `account_id` is registered. If it is not, the function returns `U128(0)` without transferring or burning the freshly minted tokens.

The analogous flaw in the external report is:

```solidity
mintableSupply = maxSupply_;
// ← no check here
if(initialSupply_ > 0) {
    mint(_msgSender(), initialSupply_);   // mints before validating the cap
}
```

Both share the same root cause: a guard that should precede a mint operation is placed after it (or omitted entirely), leaving the supply in an inconsistent state.

---

### Impact Explanation

**Medium — stuck bridge state / broken accounting requiring operator intervention.**

- The NEP-141 total supply is permanently inflated by `amount` tokens that sit in the bridge's own balance, unbacked by any user-facing delivery.
- The bridge's callback receives `U128(0)`, so its internal accounting records zero tokens as minted for that deposit event.
- The bridge balance of nBTC grows without a corresponding user receiving nBTC, breaking the 1:1 BTC-backing invariant tracked by the protocol.
- Depending on how the bridge interprets the `U128(0)` return value (e.g., treating it as a failed mint and not marking the deposit UTXO as consumed), a secondary replay risk may exist — though confirming that path requires reading the satoshi-bridge callback code not fully explored here. [2](#0-1) 

---

### Likelihood Explanation

**Medium.** Any user who generates a deposit address encoding a NEAR account ID that has never called `storage_deposit` on the nBTC contract will trigger this path. New users, users who generate deposit addresses before registering, or users who deliberately use an unregistered account ID will all reach the vulnerable branch. The bridge has no mechanism to prevent this at the proof-submission layer.

---

### Recommendation

Move the account-registration check **before** `internal_deposit`, mirroring the fix applied in the referenced audit:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    // Guard BEFORE minting
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));
    }
    self.token.internal_deposit(&self.bridge_id, amount.into());
    ...
}
```

This ensures no tokens enter circulation unless the recipient is confirmed to be able to receive them, preserving the supply/accounting invariant.

---

### Proof of Concept

1. User Alice generates a BTC deposit address whose embedded `DepositMsg` encodes a NEAR account ID (`alice.near`) that has **not** called `storage_deposit` on the nBTC contract.
2. Alice sends BTC to that address; a relayer submits the inclusion proof to `satoshi-bridge`.
3. The bridge calls `nbtc.safe_mint(alice.near, amount, None)`.
4. `internal_deposit(&bridge_id, amount)` executes — `amount` nBTC tokens are minted into the bridge's balance; total supply increases by `amount`. [3](#0-2) 
5. `accounts.get(&alice.near).is_none()` is `true` — the function returns `U128(0)`. [4](#0-3) 
6. The bridge's callback receives `U128(0)`, recording zero tokens as minted.
7. `amount` nBTC tokens are permanently stranded in the bridge's balance, the total supply is inflated, and Alice receives nothing — a stuck bridge state requiring operator intervention to resolve.
