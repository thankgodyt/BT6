### Title
`checkPreferTheirsOverOurs` Uses Hardcoded `emptyPerasWeightSnapshot` Instead of Actual Peras Weights, Causing Incorrect Peer Disconnection and Chain Selection Failure Under Peras - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

`checkPreferTheirsOverOurs` in the ChainSync client uses a hardcoded `emptyPerasWeightSnapshot` (zero weights) instead of the live `PerasWeightSnapshot` from the ChainDB when deciding whether to disconnect from a peer whose header is beyond the forecast horizon. The actual chain selection in `ChainSel.hs` always fetches the real snapshot via `Query.getPerasWeightSnapshot`. This mismatch causes the node to incorrectly disconnect from peers serving a heavier (more Peras-certified) chain, leaving the node permanently on a lighter, less-secure chain.

---

### Finding Description

When a peer's header is beyond the forecast horizon, `readLedgerStateHelper` calls `checkPreferTheirsOverOurs` before retrying:

```haskell
case prj lst of
  Nothing -> do
    checkPreferTheirsOverOurs kis'
    retry
  Just ledgerView ->
    return $ return $ Intersects kis' ledgerView
```

`checkPreferTheirsOverOurs` then calls `preferAnchoredCandidate` with a hardcoded empty snapshot:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← hardcoded zero, not the live snapshot
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse ...
``` [1](#0-0) 

`emptyPerasWeightSnapshot` is defined as a `Map` with no entries, so `isEmptyPerasWeightSnapshot` returns `True` and `preferAnchoredCandidate` falls into the pure block-number branch, completely ignoring Peras weight boosts:

```haskell
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      -- compares only by BlockNo / SelectView, no Peras weight
      ...
  | otherwise =
      -- uses weightedSelectView with real boosts
      ...
``` [2](#0-1) 

By contrast, every real chain-selection call in `ChainSel.hs` fetches the live snapshot atomically:

```haskell
(invalid, curChain, weights) <-
  atomically $
    (,,)
      <$> (forgetFingerprint <$> readTVar cdbInvalid)
      <*> Query.getCurrentChain cdb
      <*> (forgetFingerprint <$> Query.getPerasWeightSnapshot cdb)
``` [3](#0-2) 

The live snapshot is exposed as an STM action on the ChainDB API and is available to any component that holds a `ChainDB` handle:

```haskell
, getPerasWeightSnapshot :: STM m (WithFingerprint (PerasWeightSnapshot blk))
-- ^ Get the 'PerasWeightSnapshot', representing the Peras weight boosts for
-- all blocks newer than the current immutable tip.
``` [4](#0-3) 

The `PerasWeightSnapshot` is populated by `addPerasCertAsync` whenever a valid Peras certificate is received, and it is the sole source of truth for Peras weight boosts used in chain selection: [5](#0-4)

### Impact Explanation

**Impact: High** — Chain selection bug that lets an unprivileged peer cause an honest node to prefer a non-canonical, less-secure chain beyond the intended Peras security assumptions.

Consider the following state when Peras is active:

| Chain | Block number | Peras boost | Total weight |
|---|---|---|---|
| Ours | N+1 | 0 | N+1 |
| Peer's | N | B > 1 | N+B > N+1 |

The peer's chain is heavier and is the canonical chain under Peras. A header on the peer's chain is beyond the forecast horizon, so `checkPreferTheirsOverOurs` is invoked.

- **With `emptyPerasWeightSnapshot`**: peer block-number N < our block-number N+1 → `ShouldNotSwitch` → `throwSTM CandidateTooSparse` → node disconnects.
- **With real weights**: peer total weight N+B > our total weight N+1 → `ShouldSwitch` → node should continue waiting and eventually adopt the heavier chain.

The node disconnects from the peer serving the canonical chain and stays on the lighter chain. If all peers serving the heavier chain trigger this code path simultaneously (e.g., during a period of low block density that pushes headers beyond the forecast horizon), the node is permanently stuck on the non-canonical chain. This directly violates the Peras chain-selection invariant that the heaviest chain must be preferred.

---

### Likelihood Explanation

**Likelihood: Medium.** Peras is actively under development and will be deployed on Cardano mainnet. Once Peras certificates are being issued, any scenario where:
1. the peer's chain has accumulated Peras weight boost (valid certificates exist), and
2. the peer's chain has one fewer block than ours, and
3. the next header from that peer is beyond the forecast horizon (a normal occurrence during low-density periods or when the node is slightly behind)

…will trigger the bug. No key compromise, stake majority, or privileged access is required. The peer need not be adversarial; an honest peer serving the canonical chain is sufficient. The TODO comment at line 1841 (`-- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64`) confirms the developers are aware the check is broken but have not yet removed or fixed it.

---

### Recommendation

Replace `emptyPerasWeightSnapshot` with the live `PerasWeightSnapshot` inside `checkPreferTheirsOverOurs`. Because `checkPreferTheirsOverOurs` already runs inside `atomically`, the snapshot can be read in the same transaction:

```haskell
checkPreferTheirsOverOurs kis = do
  weights <- forgetFingerprint <$> getPerasWeightSnapshot  -- STM action from ChainDB
  if shouldSwitch $
       preferAnchoredCandidate (configBlock cfg) weights ourFrag theirFrag
    then pure ()
    else throwSTM $ CandidateTooSparse ...
```

The `getPerasWeightSnapshot` STM action must be threaded into the ChainSync client environment (it is already available on the `ChainDbView` record used by the BlockFetch client interface at `ClientInterface.hs:71`). [6](#0-5) 

Alternatively, if the check is to be removed entirely (as the TODO suggests), it should be removed before Peras is deployed to avoid the window where the bug is exploitable.

---

### Proof of Concept

**Root cause path:**

1. Peras is active; peer holds a chain with block number N and Peras boost B > 1 (total weight N+B).
2. Our chain has block number N+1 and no Peras boost (total weight N+1); N+B > N+1.
3. Peer sends a header at slot S that is beyond the forecast horizon of our intersection ledger state.
4. `readLedgerStateHelper` calls `checkPreferTheirsOverOurs` because `prj lst = Nothing`.
5. `preferAnchoredCandidate cfg emptyPerasWeightSnapshot ourFrag theirFrag` compares block numbers only: N < N+1 → `ShouldNotSwitch`.
6. `throwSTM (CandidateTooSparse ...)` fires; the ChainSync session with this peer is terminated.
7. The node never adopts the heavier chain. If all peers serving the heavier chain are in the same situation, the node is permanently on the lighter chain.

**Contrast with actual chain selection** (`chainSelectionForBlock`):

```haskell
weights <- forgetFingerprint <$> Query.getPerasWeightSnapshot cdb
-- weights contains boost B for the peer's block
-- preferAnchoredCandidate cfg weights ourFrag theirFrag
-- → total weight N+B > N+1 → ShouldSwitch → node would adopt the heavier chain
``` [7](#0-6) 

The divergence between the two code paths — `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` vs. the live snapshot in `chainSelectionForBlock` — is the exact analog of the external report's bug: a locally hardcoded value is used instead of querying the actual shared state, producing a decision that contradicts what the system would do if it used the correct state. [8](#0-7)
