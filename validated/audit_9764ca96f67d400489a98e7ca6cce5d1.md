### Title
Off-by-One Boundary Error in `get_confirmations` Assigns Wrong Confirmation Tier for Exact-Boundary Deposit Amounts - (File: contracts/satoshi-bridge/src/config.rs)

### Summary

The `get_confirmations` function in `config.rs` uses a strict `>` comparison when matching a deposit amount against the `confirmations_strategy` tier keys (which are documented as inclusive upper bounds). When a deposit amount equals exactly one of the non-maximum tier keys, the function skips that tier and returns the next tier's confirmation count instead of the intended one.

### Finding Description

`confirmations_strategy` is documented as "Satoshi upper limit for amount checks -> confirmations" — each key is the inclusive upper bound of a tier. The lookup loop is:

```rust
for key in &keys {
    if *key > satoshi_amount {          // <-- strict >, not >=
        return u64::from(...);
    }
}
// fallback: return max_key's confirmations
```

When `satoshi_amount == key` for any non-maximum key, the condition `*key > satoshi_amount` is `false`, so the loop does not return. Execution falls through to the next key (or the fallback), and the deposit is assigned the next tier's confirmation count.

For a two-tier strategy `{"10_000_000": 2, "100_000_000": 6}`:

| Deposit amount | Expected confirmations | Actual confirmations |
|---|---|---|
| 9_999_999 | 2 | 2 ✓ |
| **10_000_000** | **2** | **6 ✗** |
| 10_000_001 | 6 | 6 ✓ |
| 100_000_000 | 6 | 6 ✓ (fallback path) |

The fallback path (used when no key is strictly greater than the amount) correctly handles the maximum key, so only non-maximum boundary values are affected.

`get_confirmations` is called in every critical bridge verification path:
- `internal_verify_deposit` (deposit flow)
- `internal_verify_withdraw` (withdrawal flow)
- `internal_verify_refund_finalize` (refund flow)
- `internal_verify_active_utxo_management` (UTXO management)

### Impact Explanation

**Low.** This is a publicly reachable invariant-violation in production bridge/token paths without direct theft.

In the typical configuration (confirmation count increases with amount), a deposit at exactly a tier boundary receives the *higher* tier's confirmation count. The deposit is not permanently locked — the relayer simply needs to wait for additional confirmations and resubmit — but the bridge behaves contrary to its documented invariant.

In a configuration where confirmation counts decrease with amount (e.g., `{"10_000_000": 6, "100_000_000": 2}`), a deposit at exactly the boundary would receive *fewer* confirmations than intended, weakening the double-spend protection for that specific amount. While such a configuration is atypical, the contract does not prevent it.

### Likelihood Explanation

Low. The bug is triggered only when a deposit amount equals exactly one of the non-maximum tier boundary values. In practice, deposits are unlikely to land on exact satoshi boundaries, but the condition is publicly reachable by any bridge user without any special role.

### Recommendation

Change the strict `>` to `>=` so that the tier key is treated as an inclusive upper bound, matching the documented semantics:

```rust
// Before
if *key > satoshi_amount {

// After
if *key >= satoshi_amount {
```

### Proof of Concept

Given `confirmations_strategy = {"10000000": 2, "100000000": 6}`:

1. A user deposits exactly `10_000_000` satoshis.
2. `get_confirmations(10_000_000)` is called.
3. Loop: `10_000_000 > 10_000_000` → `false`; `100_000_000 > 10_000_000` → `true` → returns `6`.
4. The bridge requires 6 confirmations for a deposit that should require only 2.
5. A relayer submitting a valid 2-confirmation proof is rejected; the deposit is delayed until 6 confirmations are reached. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
