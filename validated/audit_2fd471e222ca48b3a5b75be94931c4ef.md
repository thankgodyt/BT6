Audit Report

## Title
Unguarded Parallel Cross-Contract Calls in `swap_migrated_token` Cause Permanent Token Loss — (File: `near/omni-bridge/src/lib.rs`)

## Summary
The `swap_migrated_token` helper issues `burn` and `mint` as two parallel, independent NEAR action receipts via `burn.and(mint)` with no failure callback. Because `ft_on_transfer` returns `U128(0)` synchronously before those receipts execute, and because `mint` panics when the recipient is not storage-registered in `new_token`, the `burn` receipt commits unconditionally while the user receives nothing. The result is permanent, unrecoverable destruction of the user's bridged tokens.

## Finding Description
In `ft_on_transfer` (lines 275–279), the `SwapMigratedToken` branch calls `self.swap_migrated_token(...).detach()` and immediately returns `U128(0)`, signaling to `old_token` that zero tokens should be refunded:

```rust
BridgeOnTransferMsg::SwapMigratedToken => {
    self.swap_migrated_token(sender_id, token_id, amount)
        .detach();
    PromiseOrPromiseIndexOrValue::Value(U128(0))
}
```

`swap_migrated_token` (lines 2738–2753) constructs two parallel promises with no `.then()` callback:

```rust
let burn = ext_token::ext(old_token).burn(amount);
let mint = ext_token::ext(new_token).mint(sender_id, amount, None);
burn.and(mint)
```

In NEAR's execution model, `Promise::and()` schedules both action receipts independently. Each receipt executes in its own transaction; a panic in one does not roll back the other. The `burn` receipt calls `internal_withdraw` on `old_token` (the bridge is the controller and holds the transferred balance), which succeeds unconditionally. The `mint` receipt calls `internal_deposit(&account_id, ...)` on `new_token` (lines 140–142 of `near/omni-token/src/lib.rs`). `near_contract_standards::FungibleToken::internal_deposit` panics with "The account is not registered" if `account_id` has no storage entry in `new_token`. Because the promise is detached and no callback is attached, this panic is silently discarded. The `old_token` contract has already processed the `U128(0)` return value and issued no refund. There is no recovery path.

## Impact Explanation
This directly matches the Critical impact class: **permanent loss of bridged funds**. The user's `old_token` balance is irreversibly burned (bridge's balance on `old_token` decreases), and the equivalent `new_token` balance is never credited. The tokens are destroyed with no escrow, no refund, and no on-chain record enabling manual recovery.

## Likelihood Explanation
The entry path is fully unprivileged. Any holder of `old_token` can trigger this by calling `ft_transfer_call` on `old_token` with the `SwapMigratedToken` message. The only prerequisite is that the DAO has previously executed `migrate_deployed_token`, which is a normal, documented operational step. Users who have never interacted with `new_token` — the common case immediately after a migration — will not have storage registered and will silently lose their entire transferred amount. No leaked key, admin collusion, or special role is required. The attack is repeatable for every unregistered user.

## Recommendation
Attach a `.then()` callback to the `burn.and(mint)` promise chain. The callback should inspect the result of `mint` (via `promise_result`). If `mint` failed, the callback should re-mint the equivalent amount of `old_token` back to `sender_id` (since the bridge is the controller of `old_token`). Alternatively, before burning, query `new_token` for `sender_id`'s storage balance and, if absent, return the full `amount` from `ft_on_transfer` (non-zero refund) to abort the swap without burning.

## Proof of Concept
1. DAO calls `migrate_deployed_token(Eth, old_token, new_token)` — normal operational step.
2. `alice` holds 1000 units of `old_token` and has never called `storage_deposit` on `new_token`.
3. Alice calls `old_token.ft_transfer_call(bridge, 1000, '{"SwapMigratedToken": null}')`.
4. `old_token` transfers 1000 units to the bridge and calls `bridge.ft_on_transfer(alice, 1000, ...)`.
5. Bridge executes `swap_migrated_token(alice, old_token, 1000).detach()` and returns `U128(0)`.
6. `old_token` sees `U128(0)` → no refund issued to Alice.
7. Async receipt 1: `burn(1000)` on `old_token` → bridge's balance decreases by 1000. Succeeds.
8. Async receipt 2: `mint(alice, 1000, None)` on `new_token` → `internal_deposit(&alice, 1000)` panics: Alice is not registered. Fails silently (detached, no callback).
9. Alice has permanently lost 1000 units of `old_token`; her `new_token` balance remains 0.
