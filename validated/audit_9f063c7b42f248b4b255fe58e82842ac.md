### Title
Proof Front-Running in `request_refund` Allows Attacker to Redirect User's BTC Refund - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary
`request_refund` does not bind the Bitcoin Merkle proof to the caller's identity or their intended `refund_address`. An attacker who observes a victim's pending `request_refund` NEAR transaction can front-run it using the identical Bitcoin proof but substituting their own BTC address, causing the bridge to register a fraudulent refund request that routes the victim's deposited BTC to the attacker.

### Finding Description
When a user deposits BTC without pre-authorizing a `refund_address` in their `deposit_msg` (i.e., `deposit_msg.refund_address = None`), the deposit address is derived solely from the hash of the `deposit_msg`. If the deposit is never finalized, the user calls `request_refund` supplying their BTC address as the `refund_address` parameter.

The public `request_refund` entry point performs no check that `env::predecessor_account_id()` matches `deposit_msg.recipient_id`: [1](#0-0) 

Inside `internal_request_refund`, the only guard on `refund_address` is that it must equal `deposit_msg.refund_address` **when that field is `Some`**. When it is `None`, any caller-supplied address is accepted without restriction: [2](#0-1) 

The callback that stores the request also performs no caller-identity check: [3](#0-2) 

Because NEAR transactions are publicly visible before finalization, an attacker can observe the victim's `request_refund` call, copy the `deposit_msg`, `tx_bytes`, `vout`, and `proof` verbatim, substitute their own BTC address as `refund_address`, and submit the transaction with higher priority. The first request to land wins; the second is rejected with "Refund request already exists for this UTXO": [4](#0-3) 

The fraudulent request is then stored with the attacker's BTC address: [5](#0-4) 

After `unsafe_refund_timelock_sec` elapses, `execute_refund` is callable by anyone and will build a refund PSBT paying the attacker's address: [6](#0-5) [7](#0-6) 

The longer `unsafe_refund_timelock_sec` is the only mitigation — it gives DAO/Operator a window to reject the fraudulent request — but this is a governance/operational control, not a cryptographic binding. If the operator misses the window or is unavailable, the victim's BTC is irrecoverably sent to the attacker.

### Impact Explanation
A successful attack redirects the victim's entire deposited BTC to the attacker's address. The victim's `request_refund` call fails ("Refund request already exists"), and the victim has no on-chain recourse once `execute_refund` is called after the timelock. This constitutes significant theft of user funds — Critical impact if the DAO/Operator fails to reject within the timelock window.

### Likelihood Explanation
NEAR transaction contents are visible before finalization. Any unprivileged NEAR account can call `request_refund` (it is `#[payable]` with no role restriction at the function level). The attacker only needs to attach the required storage deposit and copy the proof from the victim's pending transaction. The attack is straightforward and requires no special knowledge beyond observing the mempool. Users who do not pre-set `deposit_msg.refund_address` — the common case — are fully exposed.

### Recommendation
Bind the refund address to the caller's identity at the time of the request. Two complementary approaches:

1. **Require caller to be `recipient_id`**: In `request_refund` (or `internal_request_refund`), add `require!(env::predecessor_account_id() == deposit_msg.recipient_id, "Only recipient can request refund")`. This mirrors the NFTSimpleAuction fix of binding the signed code to the specific user.

2. **Enforce pre-authorized `refund_address`**: Require that `deposit_msg.refund_address` is always `Some` (i.e., the refund address must be committed to at deposit time and baked into the deposit address derivation). This makes the refund address cryptographically bound to the Bitcoin UTXO itself, eliminating the front-running surface entirely.

### Proof of Concept
1. Alice deposits BTC to the address derived from `deposit_msg { recipient_id: alice.near, refund_address: None }`.
2. The deposit is never finalized (e.g., relayer is offline).
3. Alice calls `request_refund(deposit_msg, "bc1q_alice...", tx_bytes, vout, proof, None)` attaching the required NEAR storage deposit.
4. Bob observes Alice's pending NEAR transaction, copies `deposit_msg`, `tx_bytes`, `vout`, `proof`, and calls `request_refund(deposit_msg, "bc1q_bob...", tx_bytes, vout, proof, None)` with higher gas priority.
5. Bob's transaction lands first. `request_refund_callback` stores `RefundRequest { refund_address: "bc1q_bob...", ... }`.
6. Alice's transaction fails: "Refund request already exists for this UTXO".
7. After `unsafe_refund_timelock_sec` (assuming DAO/Operator does not reject), Bob or anyone calls `execute_refund(utxo_storage_key, None)`.
8. `finalize_refund_with_psbt` builds a PSBT paying `"bc1q_bob..."` and the MPC signs it.
9. Alice's deposited BTC is sent to Bob's address. [8](#0-7) [9](#0-8)

    pub(crate) fn internal_request_refund(
        &self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<u128>,
    ) -> Promise {
        require!(
            env::attached_deposit() >= self.required_balance_for_request_refund(),
            "Insufficient deposit for storage"
        );
        require!(
            tx_bytes.0.len() <= MAX_REQUEST_REFUND_TX_BYTES,
            "tx_bytes too large for refund request"
        );
        if let Some(msg_refund_address) = &deposit_msg.refund_address {
            require!(
                msg_refund_address == &refund_address,
                "refund_address does not match deposit_msg.refund_address"
            );
        }

        let transaction =
            crate::WrappedTransaction::decode(&tx_bytes.0, &self.internal_config().chain)
                .expect("Deserialization tx_bytes failed");
        let tx_id = transaction.compute_txid().to_string();

        let config = self.internal_config();
        let deposit_amount = u128::from(transaction.output()[vout].value.to_sat());
        let confirmations = self.get_confirmations(config, deposit_amount);

        self.verify_transaction_inclusion_promise(
            config.btc_light_client_account_id.clone(),
            tx_id,
            proof.tx_block_blockhash,
            proof.tx_index,
            proof.merkle_proof,
            Some((proof.coinbase_tx_id, proof.coinbase_merkle_proof)),
            confirmations,
        )
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_REQUEST_REFUND_CALLBACK)
                .request_refund_callback(deposit_msg, refund_address, tx_bytes, vout, gas_fee),
        )
    }
