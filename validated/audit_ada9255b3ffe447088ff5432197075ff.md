### Title
Unpermissioned `request_refund` Allows Any Caller to Redirect Unverified Deposit UTXOs to an Attacker-Controlled BTC Address - (File: contracts/satoshi-bridge/src/api/bridge.rs, contracts/satoshi-bridge/src/refund.rs)

### Summary
`request_refund` is callable by any NEAR account and does not verify that the caller is the original depositor. When `deposit_msg.refund_address` is `None`, the caller freely supplies the `refund_address`. A subsequent call to the equally unpermissioned `execute_refund` then spends the bridge-held deposit UTXO and sends the BTC to that attacker-supplied address. This is the direct analog of M-01: an unpermissioned entry point uses bridge-controlled funds and routes the resulting asset to an address chosen by the caller, not the rightful owner.

### Finding Description
`request_refund` (bridge.rs line 510) accepts a `deposit_msg`, a caller-supplied `refund_address`, and an SPV proof. The only access-control check is a guard on the optional `gas_fee` parameter; the caller's identity is never compared against the NEAR account embedded in `deposit_msg`. [1](#0-0) 

Inside `internal_request_refund` and its callback `request_refund_callback`, the code verifies the SPV proof and confirms the output script matches the deposit address derived from `deposit_msg`. It does **not** check that `env::predecessor_account_id()` equals the account encoded in `deposit_msg`. [2](#0-1) 

When `deposit_msg.refund_address` is `None`, the check in `request_refund_callback` that would enforce a pre-authorized address is simply skipped, and the attacker-supplied `refund_address` is stored verbatim in the `RefundRequest`. [3](#0-2) [4](#0-3) 

`execute_refund` is also unpermissioned. After `unsafe_refund_timelock_sec` elapses it builds a Bitcoin transaction that spends the deposit UTXO and pays the stored `refund_address`. [5](#0-4) 

`resolve_execute_refund_timelock` confirms that for requests where `deposit_msg.refund_address` is `None` (the attacker's case), the longer `unsafe_refund_timelock_sec` applies, but no caller-identity check is performed. [6](#0-5) 

### Impact Explanation
An attacker who successfully executes this path causes the bridge to spend a legitimate user's deposit UTXO and deliver the BTC to the attacker's Bitcoin address. The original depositor permanently loses their BTC. This matches the allowed impact: **significant loss or theft of user funds**.

### Likelihood Explanation
The `deposit_msg` for any deposit is emitted on-chain via the `LogDepositAddress` event, making it fully observable. [7](#0-6) 

An attacker monitors the NEAR chain for `LogDepositAddress` events and the Bitcoin chain for the corresponding unconfirmed or recently confirmed deposit transactions. For deposits where `deposit_msg.refund_address` is `None` (the common case for standard deposits), the attacker submits `request_refund` with their own BTC address before the relayer calls `verify_deposit`. The `unsafe_refund_timelock_sec` gives the DAO/Operator a window to reject, but if the operator is slow, offline, or overwhelmed by many simultaneous requests, the attacker calls `execute_refund` after the timelock and receives the BTC. The attack requires no special privilege, only knowledge of publicly observable on-chain data.

### Recommendation
Add a caller-identity check in `request_refund` (or its callback) that requires `env::predecessor_account_id()` to equal the NEAR account encoded in `deposit_msg`. Alternatively, when `deposit_msg.refund_address` is `None`, require the caller to prove ownership of the deposit (e.g., by signing a message or by matching the NEAR account in `deposit_msg`). This mirrors the recommended mitigation from M-01: funds should only be routable to an address that the rightful owner has authorized, not to an address freely chosen by any caller.

### Proof of Concept
1. User A calls `get_user_deposit_address` with `deposit_msg = { near_account: "alice.near", refund_address: None, ... }`. The `LogDepositAddress` event is emitted on-chain, revealing `deposit_msg`.
2. User A sends BTC to the derived deposit address. The transaction is confirmed on Bitcoin.
3. Attacker B observes both events. Before the relayer calls `verify_deposit`, attacker B calls:
   ```
   request_refund(
     deposit_msg = <alice's deposit_msg>,
     refund_address = "attacker_btc_address",
     tx_bytes = <alice's deposit tx>,
     vout = 0,
     proof = <valid SPV proof>,
     gas_fee = None
   )
   ```
4. `request_refund_callback` verifies the SPV proof and the output script, finds no duplicate request, and stores `refund_address = "attacker_btc_address"` in the `RefundRequest`. No check is made that B == alice.
5. After `unsafe_refund_timelock_sec` elapses (assuming DAO/Operator does not reject), attacker B calls `execute_refund(utxo_storage_key)`.
6. The bridge builds and signs a Bitcoin transaction spending Alice's deposit UTXO, paying `attacker_btc_address`. Alice's BTC is stolen.

    pub(crate) fn internal_request_refund(
        &self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<u128>,
    ) -> Promise {
        require!(
            env::attached_deposit() >= self.required_balance_for_request_refund(),
            "Insufficient deposit for storage"
        );
        require!(
            tx_bytes.0.len() <= MAX_REQUEST_REFUND_TX_BYTES,
            "tx_bytes too large for refund request"
        );
        if let Some(msg_refund_address) = &deposit_msg.refund_address {
            require!(
                msg_refund_address == &refund_address,
                "refund_address does not match deposit_msg.refund_address"
            );
        }

        let transaction =
            crate::WrappedTransaction::decode(&tx_bytes.0, &self.internal_config().chain)
                .expect("Deserialization tx_bytes failed");
        let tx_id = transaction.compute_txid().to_string();

        let config = self.internal_config();
        let deposit_amount = u128::from(transaction.output()[vout].value.to_sat());
        let confirmations = self.get_confirmations(config, deposit_amount);

        self.verify_transaction_inclusion_promise(
            config.btc_light_client_account_id.clone(),
            tx_id,
            proof.tx_block_blockhash,
            proof.tx_index,
            proof.merkle_proof,
            Some((proof.coinbase_tx_id, proof.coinbase_merkle_proof)),
            confirmations,
        )
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_REQUEST_REFUND_CALLBACK)
                .request_refund_callback(deposit_msg, refund_address, tx_bytes, vout, gas_fee),
        )
    }

    pub(crate) fn resolve_execute_refund_timelock(&self, utxo_storage_key: &str) -> u64 {
        require!(
            env::attached_deposit() >= self.required_balance_for_execute_refund(),
            "Insufficient deposit for storage"
        );
        let caller = env::predecessor_account_id();
        let is_privileged =
            self.acl_has_any_role(vec![Role::DAO.into(), Role::RefundOperator.into()], caller);
        let refund_request: RefundRequest = self
            .data()
            .refund_requests
            .get(utxo_storage_key)
            .expect("Refund request not found")
            .into();
        let config = self.internal_config();
        if refund_request.deposit_msg().refund_address.is_some() {
            // Pre-authorized refund address: privileged users can fast-track.
            if is_privileged {
                0
            } else {
                config.refund_timelock_sec
            }
        } else {
            // Refund address supplied by caller of `request_refund`: longer
            // timelock to give DAO/Operator time to reject suspicious requests.
            config.unsafe_refund_timelock_sec
        }
    }
