### Title
Push-Based Token Delivery in `finTransfer` Permanently Freezes Bridged Funds When Recipient Cannot Receive Tokens - (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

The EVM `OmniBridge.finTransfer` function uses a "push" approach to deliver tokens directly to the recipient address inline during finalization. If the token delivery reverts — due to a recipient contract that rejects ETH, an ERC1155 `onERC1155Received` hook that reverts, or a blacklisted address for tokens like USDC — the entire transaction reverts, including the nonce-consumed flag. Because the recipient address is cryptographically bound into the MPC-signed payload, no alternative delivery path exists. The bridged funds are permanently frozen: burned or locked on NEAR, but undeliverable on the EVM destination.

---

### Finding Description

`finTransfer` in `OmniBridge.sol` marks the nonce as used and then immediately attempts to push tokens to `payload.recipient` in the same atomic transaction: [1](#0-0) 

```solidity
if (completedTransfers[payload.destinationNonce]) {
    revert NonceAlreadyUsed(payload.destinationNonce);
}
completedTransfers[payload.destinationNonce] = true;
```

The nonce is marked used at line 287, but if any of the subsequent token delivery branches revert, the EVM rolls back all state changes — including the nonce flag — leaving the transfer in a permanently unfinalizeable state.

The three vulnerable delivery branches are:

**1. Native ETH (line 319–322):** A recipient contract that has no `receive()` or a reverting fallback causes `success == false`, triggering `revert FailedToSendEther()`. [2](#0-1) 

**2. ERC1155 (line 324–330):** `safeTransferFrom` calls `onERC1155Received` on the recipient. A recipient contract that reverts in this hook causes the entire `finTransfer` call to revert. [3](#0-2) 

**3. ERC20 with blacklisting (line 351–354):** `safeTransfer` to a USDC/USDT-blacklisted address reverts. The recipient can deliberately get themselves blacklisted after initiating the transfer on NEAR. [4](#0-3) 

The recipient address is part of the Borsh-encoded payload that is verified against the MPC-derived NEAR bridge address: [5](#0-4) 

This means the recipient cannot be changed after the MPC has signed. There is no cancel, rescue, or redirect function anywhere in the EVM contract. The same structural issue exists in the Starknet bridge: [6](#0-5) 

---

### Impact Explanation

Bridged funds are permanently frozen. The user's tokens are burned or locked on NEAR (via `init_transfer_internal` calling `burn_tokens_if_needed` / `lock_tokens_if_needed`): [7](#0-6) 

Once burned/locked on NEAR, the only recovery path is successful `finTransfer` on EVM. If that call can never succeed, the funds are irrecoverably lost. This matches the Critical allowed impact: **permanent freezing of bridged funds**.

---

### Likelihood Explanation

Three realistic trigger conditions exist, all reachable by an unprivileged bridge user:

- **Deliberate self-blacklisting (USDC/USDT):** A user initiates a NEAR→EVM transfer of USDC, then deliberately gets their EVM address blacklisted (e.g., by interacting with a sanctioned counterparty). The `safeTransfer` will revert on every `finTransfer` attempt.
- **Malicious recipient contract (ETH):** A user specifies a contract address as recipient that has a reverting `receive()`. This is trivially deployable.
- **Malicious ERC1155 receiver:** A user specifies a contract that reverts in `onERC1155Received`, blocking finalization of any ERC1155-backed bridge transfer.

The bridge explicitly supports arbitrary ERC20 tokens as bridgeable assets, and USDC is a primary use-case token on Arbitrum, Base, and Polygon — all Wormhole-supported chains in scope.

---

### Recommendation

Adopt a pull-based delivery pattern. Instead of pushing tokens to the recipient inside `finTransfer`, credit the amount to a per-recipient claimable balance mapping and emit an event. Add a separate `claimTransfer(uint64 destinationNonce)` function that the recipient calls to pull their tokens. This decouples nonce finalization from token delivery, eliminating the revert attack surface entirely.

Alternatively, wrap each delivery branch in a try/catch (where applicable) and, on failure, store the amount in a claimable escrow rather than reverting the entire transaction.

---

### Proof of Concept

1. Deploy a malicious recipient contract on EVM:
   ```solidity
   contract RevertingReceiver {
       receive() external payable { revert("blocked"); }
   }
   ```
2. On NEAR, call `ft_transfer_call` on a NEAR-native token to `omni-bridge.near` with `recipient = OmniAddress::Eth(<RevertingReceiver address>)` and `token = wNEAR`. The bridge burns the wNEAR and emits `InitTransferEvent`.
3. The MPC signs a `TransferMessagePayload` with `tokenAddress = address(0)` (ETH) and `recipient = <RevertingReceiver address>`.
4. Any relayer calls `OmniBridge.finTransfer(signature, payload)`. The ETH `.call{value: amount}("")` to `RevertingReceiver` returns `success = false`. The function reverts with `FailedToSendEther`. The `completedTransfers` flag is rolled back.
5. Every subsequent `finTransfer` attempt with the same valid signature reverts identically. The wNEAR is permanently burned on NEAR with no delivery on EVM. [2](#0-1) [8](#0-7)
