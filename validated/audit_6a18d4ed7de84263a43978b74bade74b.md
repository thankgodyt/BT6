### Title
Deposit and Withdrawal Fee Rates Can Be Arbitrarily Modified by DAO and New Rates Apply Retroactively to All Pending Bridge Operations - (File: contracts/satoshi-bridge/src/config.rs, contracts/satoshi-bridge/src/btc_light_client/deposit.rs)

### Summary

The bridge's `deposit_bridge_fee` and `withdraw_bridge_fee` (including `fee_rate` and `protocol_fee_rate`) are stored in a mutable `Config` that the DAO can update at any time via `update_config`. The deposit fee is computed at `verify_deposit` execution time — not at the moment the user irrevocably committed BTC on-chain. A fee increase between a user's on-chain BTC send and the relayer's `verify_deposit` call causes the user to receive fewer nBTC than the fee schedule in effect when they deposited.

### Finding Description

`BridgeFee` holds `fee_rate` and `protocol_fee_rate` as plain mutable fields: [1](#0-0) 

Both `deposit_bridge_fee` and `withdraw_bridge_fee` live inside `Config`: [2](#0-1) 

`ConfigUpdate` exposes both fields for live replacement: [3](#0-2) 

The DAO can call `update_config` at any time with no time-lock or cap: [4](#0-3) 

`ConfigUpdate::apply` overwrites the live config immediately: [5](#0-4) 

The deposit fee is then computed inside `internal_verify_deposit` using the **current** config at the moment the relayer submits the proof — not the config that was in effect when the user sent BTC: [6](#0-5) 

The resulting `mint_amount` (after fee deduction) is passed into the callback and minted to the user: [7](#0-6) 

No snapshot of the fee rate is taken at deposit-address generation time or at BTC send time. The user's commitment is irrevocable once BTC is broadcast, but the fee that will be charged is not fixed until `verify_deposit` executes.

The same pattern applies to `withdraw_bridge_fee`: a user who initiates a withdrawal (burning nBTC via `ft_transfer_call`) locks in the withdrawal amount, but the fee deducted from the BTC output is read from the live config at signing/execution time.

### Impact Explanation

If the DAO raises `deposit_bridge_fee.fee_rate` (e.g., from 0.1 % to 5 %) after a batch of users have sent BTC but before the relayer calls `verify_deposit`, every one of those users receives materially fewer nBTC than the fee schedule they observed when they deposited. The shortfall is permanent — the BTC is already in the bridge's UTXO set and cannot be returned without a separate refund flow. This constitutes a harmful, non-consensual reduction in the value received by bridge users, matching the Medium impact class: "Bypass of bridge limits or policies."

### Likelihood Explanation

The deposit flow has an inherent latency window: the user sends BTC on-chain, waits for confirmations (the bridge requires between 2 and 100 confirmations per `confirmations_strategy`), and only then does the relayer call `verify_deposit`. This window can span tens of minutes to hours. Any fee update applied during that window silently affects all in-flight deposits. A routine governance fee adjustment — even a well-intentioned one — is sufficient to trigger the impact without any malicious intent, exactly as the referenced judge noted for the analogous InfinityExchange finding.

### Recommendation

1. **Snapshot the fee at deposit-address generation time** — embed the fee rate in the `DepositMsg` or a signed commitment so `verify_deposit` uses the rate the user agreed to.
2. **Apply fee changes only to deposits created after the update** — record a `fee_version` or `fee_effective_from` timestamp in `Config` and store the applicable version in each pending deposit record.
3. **Enforce a maximum fee cap** — add a hard-coded upper bound on `fee_rate` so that even a governance update cannot raise fees beyond a known ceiling, limiting the worst-case impact on in-flight deposits.

### Proof of Concept

1. User observes `deposit_bridge_fee.fee_rate = 10` (0.1 %) and sends 1 BTC to their deposit address.
2. BTC transaction is broadcast; the bridge requires 6 confirmations (~60 min).
3. During the confirmation window, the DAO calls `update_config` with `deposit_bridge_fee.fee_rate = 500` (5 %).
4. After confirmations, the relayer calls `verify_deposit_v2`.
5. `internal_verify_deposit` reads `config.deposit_bridge_fee.get_fee(100_000_000)` → fee = 5 000 000 sat (5 %).
6. `mint_amount = 95_000_000` nBTC is minted instead of the `99_900_000` the user expected.
7. The user silently loses ~4.9 % of their deposit value with no recourse. [8](#0-7) [4](#0-3) [9](#0-8)

    pub fn get_fee(&self, amount: u128) -> u128 {
        std::cmp::max(
            amount * u128::from(self.fee_rate) / u128::from(MAX_RATIO),
            self.fee_min,
        )
    }

    pub fn get_protocol_and_relayer_fee(&self, fee_amount: u128) -> (u128, u128) {
        let protocol_fee = fee_amount * u128::from(self.protocol_fee_rate) / u128::from(MAX_RATIO);
        let relayer_fee = fee_amount - protocol_fee;
        (protocol_fee, relayer_fee)
    }
