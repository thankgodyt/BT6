Audit Report

## Title
Dust Transfers Below Minimum Representable Unit Permanently Lock User Funds Due to Missing Normalization Check in `init_transfer` - (File: `near/omni-bridge/src/lib.rs`)

## Summary

`init_transfer` accepts any transfer where `fee < amount` and immediately locks or burns tokens in `init_transfer_internal`, but performs no check that `normalize_amount(amount - fee, decimals) > 0`. When a user submits a dust amount below the minimum representable unit on the destination chain, tokens are permanently locked in escrow (or burned), `sign_transfer` always panics with `ERR_INVALID_AMOUNT_TO_TRANSFER` before reaching the MPC call, the callback never fires, and no public cancel or refund function exists to recover the stuck funds.

## Finding Description

`normalize_amount` uses floor division, truncating any sub-unit remainder: [1](#0-0) 

`sign_transfer` enforces that the normalized amount is non-zero, but this check occurs **after** tokens have already been locked in a prior transaction: [2](#0-1) 

`init_transfer` only validates `fee < amount` with no normalization check: [3](#0-2) 

Tokens are locked or burned unconditionally inside `init_transfer_internal` before any normalization check can occur: [4](#0-3) 

`sign_transfer_callback` only removes the transfer message on a **successful** MPC signing response. Since `sign_transfer` panics before the MPC cross-contract call is made, the callback never fires: [5](#0-4) 

No public `cancel_transfer` or refund function exists in the contract. The transfer message remains in `pending_transfers` indefinitely, and the locked tokens are irrecoverable.

## Impact Explanation

This is a permanent freezing of bridged funds, matching the Critical allowed impact scope. For any token pair where `origin_decimals > decimals` (e.g., a NEAR token with 24 decimals bridging to an EVM chain registered with 18 decimals, scaling factor `10^6`), any transfer of fewer than `10^6` base units results in `normalize_amount = 0`. The user's tokens are permanently locked in bridge escrow (for native tokens) or permanently burned (for deployed bridge tokens), with no recovery path. This is an irreversible loss of bridged user funds caused by a decimal/normalization gap between the acceptance point (`init_transfer`) and the validation point (`sign_transfer`).

## Likelihood Explanation

Any unprivileged user calling `ft_transfer_call` on a NEAR token can trigger this condition by specifying an amount below the minimum representable unit on the destination chain. The decimal difference between NEAR tokens (commonly 24 decimals) and EVM tokens (commonly 6 or 18 decimals) creates scaling factors of `10^6` to `10^18`. A user unfamiliar with decimal normalization, or one using a UI that does not enforce a minimum transfer amount, can accidentally trigger permanent fund loss. No privileged access is required to lock the funds — the locking occurs entirely within the user-initiated `ft_transfer_call` → `init_transfer` → `init_transfer_internal` flow. [6](#0-5) 

## Recommendation

Add a normalization check inside `init_transfer` (or in `ft_on_transfer` before tokens are locked/burned) to verify that `normalize_amount(amount - fee, decimals) > 0` for the destination chain. The `token_decimals` map and destination chain are already available at this point:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

This guard already exists in `sign_transfer` but must be moved earlier, to `init_transfer`, before tokens are locked or burned. [7](#0-6) 

## Proof of Concept

1. Register a NEAR token with `origin_decimals = 24`, `decimals = 18` for an EVM destination (scaling factor = `10^6`).
2. A user calls `ft_transfer_call` with `amount = 500_000` (below the `10^6` threshold) and `fee = 0`.
3. `init_transfer` accepts the transfer: `fee (0) < amount (500_000)` passes. [3](#0-2) 
4. `init_transfer_internal` locks 500,000 tokens in bridge escrow. [4](#0-3) 
5. A trusted relayer calls `sign_transfer` for this transfer.
6. `normalize_amount(500_000, Decimals { decimals: 18, origin_decimals: 24 }) = 500_000 / 10^6 = 0`. [1](#0-0) 
7. `require!(amount_to_transfer > 0)` panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`. [2](#0-1) 
8. The MPC cross-contract call is never made; `sign_transfer_callback` never fires; the transfer message remains in `pending_transfers` forever; the 500,000 tokens are permanently locked with no recovery path.
