### Title
Unauthorized Refund Request Allows Any Caller to Redirect Another User's BTC to an Arbitrary Address — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`request_refund` contains no check that the caller is the deposit owner (`deposit_msg.recipient_id`). When a deposit was made without a pre-authorized `refund_address` in `deposit_msg`, any unprivileged NEAR account can submit a refund request for that deposit and supply an arbitrary BTC address as the destination. After the `unsafe_refund_timelock_sec` elapses, anyone can call `execute_refund` and the bridge will MPC-sign a transaction that sends the victim's BTC to the attacker's address.

---

### Finding Description

`DepositMsg.refund_address` is optional: [1](#0-0) 

When a user calls `get_user_deposit_address`, the full `deposit_msg` (including `recipient_id` and the fact that `refund_address` is `None`) is emitted in a public on-chain event: [2](#0-1) 

`request_refund` is callable by any NEAR account (no `#[trusted_relayer]` on the method itself, unlike `verify_refund_finalize`). Its only guard when `deposit_msg.refund_address` is `None` is the absence of a matching-address check — meaning the caller may supply any BTC address: [3](#0-2) 

There is no check that `env::predecessor_account_id() == deposit_msg.recipient_id` anywhere in `internal_request_refund` or `request_refund_callback`. The callback only verifies that the transaction output script matches the deposit address derived from `deposit_msg` — a cryptographic proof of the deposit's existence, not of the caller's ownership: [4](#0-3) 

`execute_refund` is similarly unrestricted and passes `env::predecessor_account_id()` as the `caller` to `finalize_refund_with_psbt`. The BTC is sent to `refund_request.refund_address` — the address the attacker supplied in step 1: [5](#0-4) 

The only mitigation is `unsafe_refund_timelock_sec`, a configurable delay intended to give the DAO time to call `reject_refund`. This is an operational control, not a cryptographic one: [6](#0-5) 

---

### Impact Explanation

An attacker who observes a `LogDepositAddress` event for a deposit where `refund_address` is `None` can:

1. Call `request_refund` with the victim's `deposit_msg` and the attacker's own BTC address.
2. Wait for `unsafe_refund_timelock_sec` to elapse.
3. Call `execute_refund` to trigger MPC signing of a Bitcoin transaction that pays the victim's deposited BTC to the attacker's address.

The victim's BTC is permanently lost. No nBTC is involved — the deposit was never finalized — so the bridge's token supply is unaffected, but the user's on-chain BTC is stolen. This is a direct, significant loss of user funds.

**Allowed impact matched:** *Critical — Significant loss, theft, destruction, or permanent locking of user or protocol funds.*

---

### Likelihood Explanation

- `deposit_msg` is fully public via the `LogDepositAddress` event emitted by `get_user_deposit_address`.
- `refund_address` is optional and many users will omit it (it is not required by the API).
- The attack window opens any time the relayer has not yet called `verify_deposit` (relayer downtime, congestion, or a deposit the relayer has not yet processed).
- The only defense is the DAO rejecting the request within `unsafe_refund_timelock_sec`. If the DAO is slow, offline, or the timelock is configured short, the attack succeeds.
- The attacker's cost is only a small NEAR storage deposit; the reward scales with the victim's BTC deposit size.

---

### Recommendation

Add an ownership check in `internal_request_refund` (or `request_refund_callback`) that requires the caller to be the `deposit_msg.recipient_id`:

```rust
require!(
    env::predecessor_account_id() == deposit_msg.recipient_id
        || self.acl_has_any_role(vec![Role::DAO.into(), Role::Operator.into()],
                                  env::predecessor_account_id()),
    "Only the deposit recipient or a privileged role may request a refund"
);
```

Alternatively, require that `deposit_msg.refund_address` is always set (non-`None`) so that the destination is cryptographically committed at deposit time and cannot be overridden by a third party.

---

### Proof of Concept

1. **Alice** calls `get_user_deposit_address({ recipient_id: "alice.near", refund_address: None, ... })`. The bridge emits `LogDepositAddress` with the full `deposit_msg`.
2. Alice sends 1 BTC to the returned deposit address. The relayer has not yet called `verify_deposit`.
3. **Bob** reads the `LogDepositAddress` event, reconstructs Alice's `deposit_msg`, and calls:
   ```
   request_refund(
       deposit_msg = <Alice's deposit_msg>,
       refund_address = "bc1q<bob_address>",
       tx_bytes = <Alice's deposit tx>,
       vout = 0,
       proof = <valid merkle proof>,
       gas_fee = None
   )
   ```
   This succeeds because `deposit_msg.refund_address` is `None` — the address check at line 154–158 of `refund.rs` is skipped.
4. After `unsafe_refund_timelock_sec` elapses (and assuming the DAO does not reject), Bob calls `execute_refund(utxo_storage_key)`.
5. The bridge builds and MPC-signs a Bitcoin transaction paying Alice's 1 BTC to Bob's address.
6. Alice's BTC is permanently redirected to Bob. Alice receives neither BTC nor nBTC. [7](#0-6) [8](#0-7)

impl Contract {
    /// Submit a refund request. Verifies the BTC transaction via Light Client first.
    /// If `deposit_msg.refund_address` is set, it must match the provided `refund_address`.
    /// If `deposit_msg.refund_address` is None, the provided `refund_address` is used.
    #[allow(clippy::too_many_arguments)]
    pub(crate) fn internal_request_refund(
        &self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<u128>,
    ) -> Promise {
        require!(
            env::attached_deposit() >= self.required_balance_for_request_refund(),
            "Insufficient deposit for storage"
        );
        require!(
            tx_bytes.0.len() <= MAX_REQUEST_REFUND_TX_BYTES,
            "tx_bytes too large for refund request"
        );
        if let Some(msg_refund_address) = &deposit_msg.refund_address {
            require!(
                msg_refund_address == &refund_address,
                "refund_address does not match deposit_msg.refund_address"
            );
        }

        let transaction =
            crate::WrappedTransaction::decode(&tx_bytes.0, &self.internal_config().chain)
                .expect("Deserialization tx_bytes failed");
        let tx_id = transaction.compute_txid().to_string();

        let config = self.internal_config();
        let deposit_amount = u128::from(transaction.output()[vout].value.to_sat());
        let confirmations = self.get_confirmations(config, deposit_amount);

        self.verify_transaction_inclusion_promise(
            config.btc_light_client_account_id.clone(),
            tx_id,
            proof.tx_block_blockhash,
            proof.tx_index,
            proof.merkle_proof,
            Some((proof.coinbase_tx_id, proof.coinbase_merkle_proof)),
            confirmations,
        )
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_REQUEST_REFUND_CALLBACK)
                .request_refund_callback(deposit_msg, refund_address, tx_bytes, vout, gas_fee),
        )
    }
