### Title
Overly Strict Batch Rejection in `processCerts` Drops All Valid Peras Certificates When Any Single Certificate Fails Validation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs`)

---

### Summary

`processCerts` and its sibling `processVotes` iterate over a batch of inbound Peras objects received from a peer, filter out already-known items, then validate the remainder. If **any** item fails validation the entire batch is rejected by throwing an exception — discarding all valid items in the same batch. This is the direct analog of the `revokeVotes` `require` bug: a single non-conforming element in a collection causes the whole operation to abort, when the correct behaviour is to treat that element as a no-op and continue processing the rest.

---

### Finding Description

`processCerts` in `PerasCert.hs` (lines 164–185):

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb =
        filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _) ->
      throw (PerasCertValidationError errs)   -- ← entire batch dropped
``` [1](#0-0) 

The function correctly skips certificates already present in the DB (line 166), mirroring the "already processed" guard. However, it then applies an all-or-nothing check: if the `errs` list is non-empty, `throw` is called, discarding every certificate in the batch — including the valid ones in `_`.

The identical structural flaw exists in `processVotes`:

```haskell
case partitionEithers validationResults of
  ([], validatedVotes) -> mapM_ (addVote . WithArrivalTime now) validatedVotes
  (errs, _)            -> throw (PerasVoteValidationError errs)
``` [2](#0-1) 

For `processVotes` the validation is already non-trivial: `validatePerasVote` returns `Left PerasValidationErr` whenever the voter ID is absent from the current stake distribution snapshot:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr = Right ...
  | otherwise                                          = Left PerasValidationErr
``` [3](#0-2) 

This means `processVotes` is **currently exploitable** with real stake-distribution data. `processCerts` carries the same structural flaw and will become exploitable once `validatePerasCert` is replaced with real cryptographic validation (the `TODO` at line 103/126 of `PerasCert.hs`). [4](#0-3) 

Both writers are wired into the production `ChainDB` path (`makePerasCertPoolWriterFromChainDB`, `makePerasVotePoolWriterFromChainDB`), so the code is reachable from any unprivileged peer via the object-diffusion mini-protocol.

---

### Impact Explanation

Peras votes and certificates are the mechanism by which the Peras protocol boosts chain weight. A node that does not accumulate enough votes for a round will not forge a certificate; a node that does not receive a certificate will not apply the Peras weight boost during chain selection. Both outcomes weaken the Peras security guarantee.

An attacker who is a peer of the target node can:

1. Observe, via the ticket-based object-diffusion protocol, which vote/certificate IDs the target has not yet seen.
2. Craft one syntactically well-formed but semantically invalid vote (e.g., a `PerasVote` whose `pvVoteVoterId` is not present in the current epoch's stake distribution).
3. Bundle that invalid vote with N legitimate votes the target needs to reach quorum.
4. Send the batch. `processVotes` validates all N+1 items, finds one failure, and throws `PerasVoteValidationError`, silently discarding all N valid votes.

Because the Peras voting rules are time-sensitive (VR-1A2 requires a certificate to arrive within `_X` slots of its round start), repeated suppression of valid votes can prevent quorum from being reached within the required window, causing the node to enter a cooldown period and weakening the Peras chain-quality guarantee. This maps to the **Medium** allowed impact: a public miniprotocol flaw that materially weakens vote/certificate authorization.

---

### Likelihood Explanation

The attack requires only that the adversary be a connected peer — no key material, stake majority, or privileged access is needed. The object-diffusion protocol's ticket-number mechanism makes it straightforward to infer which votes/certificates the target has not yet received. Crafting an invalid vote (a voter ID not in the stake distribution) is trivial. The attack is therefore realistic for any adversarial peer on the network.

---

### Recommendation

Mirror the fix applied to `revokeVotes` in the external report: treat invalid items as no-ops rather than aborting the entire batch. Replace the all-or-nothing `partitionEithers` branch with per-item handling:

```haskell
-- Instead of:
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) -> mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _)            -> throw (PerasCertValidationError errs)

-- Use:
let (errs, validatedCerts) =
      partitionEithers (validateCert <$> certsNotAlreadyInDb)
unless (null errs) $ logOrDisconnect errs   -- log / punish peer separately
mapM_ (addCert . WithArrivalTime now) validatedCerts
```

If peer disconnection on any invalid item is a deliberate security policy, it should be applied **after** the valid items have been persisted, so that honest certificates/votes are not lost.

---

### Proof of Concept

1. Connect to a target node as an unprivileged peer via the object-diffusion mini-protocol for Peras votes.
2. Read the current `voteIds` set from the peer to determine which votes it has not yet seen.
3. Obtain N legitimate `PerasVote` values targeting the current round (e.g., by relaying them from another honest peer).
4. Append one crafted `PerasVote` whose `pvVoteVoterId` is a random key hash absent from the current epoch's stake distribution.
5. Send the batch of N+1 votes to the target node via `opwAddObjects`.
6. Observe that `processVotes` throws `PerasVoteValidationError` and the target node's `pvdsVoteIds` set remains unchanged — none of the N valid votes were stored.
7. Repeat each round to prevent the target from ever accumulating enough votes to forge a Peras certificate. [5](#0-4) [6](#0-5)

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
