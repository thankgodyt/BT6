Audit Report

## Title
Unchecked `send_tokens` Result in Fast-Transfer Relayer Repayment Causes Permanent Loss of Relayer Funds — (File: `near/omni-bridge/src/lib.rs`)

## Summary
In `utxo_fin_transfer_fast` and `process_fin_transfer_to_other_chain`, the bridge repays a fast-transfer relayer by calling `send_tokens(...).detach()` — the promise result is never inspected. State mutations that permanently mark the fast transfer as finalised or remove it entirely are committed in the same synchronous frame. If the token transfer fails, the relayer's fronted funds are permanently unrecoverable, and a developer-authored `// TODO` comment at the call site confirms the team is aware the failure case is unhandled.

## Finding Description
**Instance 1 — `utxo_fin_transfer_fast` (lines 2529–2548)**

State is mutated first — either `remove_fast_transfer` (line 2530) or `mark_fast_transfer_as_finalised` (line 2533) — then `send_tokens` is called with `.detach()` (line 2548). The caller `utxo_fin_transfer` carries an explicit developer acknowledgement at line 2484:

```rust
// TODO: check how to deal with failed send_tokens
return self.utxo_fin_transfer_fast(fast_transfer, status, utxo_fin_transfer_msg);
```

**Instance 2 — `process_fin_transfer_to_other_chain` (lines 2028–2040)**

`send_tokens(...).detach()` is called at line 2039, and `mark_fast_transfer_as_finalised` is called at line 2040 in the same synchronous frame. Because the promise is detached, its async failure is never observed, yet the state is already committed.

`send_tokens` (lines 2069–2117) dispatches:
- `mint` for deployed bridge tokens (bridge-controlled, less likely to fail)
- `ft_transfer` for non-deployed tokens — this **panics** inside the async promise if the recipient has not registered storage with the token contract

Once the fast transfer record is removed or marked finalised, no retry or recovery path exists anywhere in the contract.

The correct pattern — a chained callback that restores state on failure — is already implemented in `submit_transfer_to_btc_connector_callback` (`near/omni-bridge/src/btc.rs`, lines 103–126), confirming the team knows how to do this correctly.

## Impact Explanation
A relayer fronts the full transfer amount to the recipient during the fast-transfer phase. When canonical finalization occurs, the bridge is supposed to repay the relayer. If `send_tokens` fails silently, the fast transfer record is gone and the relayer has no mechanism to retry or recover. This is a direct, permanent loss of bridged token funds for a protocol participant — matching the allowed impact class: *permanent loss/freezing of bridged funds* and *escrow mis-accounting that changes protocol participant balances*.

**Severity: Critical**

## Likelihood Explanation
`send_tokens` calls `ft_transfer` for non-deployed tokens. On NEAR, `ft_transfer` panics if the recipient account has not registered storage with the token contract. A relayer operating across multiple token types may have registered storage for some but not others. Additionally, if the token contract is paused or upgraded between the fast-transfer phase and finalization, the call fails silently. The developer `// TODO` comment at line 2484 is direct evidence the team considers this an open, unresolved gap.

**Likelihood: Low** — requires a specific failure condition in the token transfer, but the scenario is realistic and the developer TODO confirms it is an acknowledged gap.

## Recommendation
Replace `.detach()` with a chained `#[private]` callback that inspects the promise result. State mutations (`remove_fast_transfer` / `mark_fast_transfer_as_finalised`) must only be committed inside the callback after confirming the transfer succeeded. On failure, restore the fast transfer record so the relayer can retry or be compensated. This mirrors the pattern already used correctly in `submit_transfer_to_btc_connector_callback` (`near/omni-bridge/src/btc.rs`, lines 103–126).

## Proof of Concept
1. Relayer calls `ft_transfer_call` on the token contract with a `FastFinTransferMsg`. The bridge records the fast transfer with the relayer's address and the relayer's tokens are sent to the recipient.
2. The UTXO connector later calls `ft_transfer_call` back into the bridge with a `UtxoFinTransferMsg` matching the same UTXO ID, triggering `utxo_fin_transfer` → `utxo_fin_transfer_fast`.
3. Inside `utxo_fin_transfer_fast`, `remove_fast_transfer` (or `mark_fast_transfer_as_finalised`) is called at lines 2530/2533, permanently updating state.
4. `send_tokens` is called with `.detach()` at line 2548. The relayer's account has no storage registered with the token contract; `ft_transfer` panics inside the async promise — but the detached promise's failure is never observed by the bridge.
5. The fast transfer record is gone. The relayer's fronted funds are permanently lost. The `UtxoTransferEvent` is emitted as if everything succeeded.
