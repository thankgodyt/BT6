### Title
Stub `validatePerasCert` Unconditionally Accepts All Peer-Supplied Peras Certificates, Bypassing Certificate Validation and Enabling Chain-Selection Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance ships a stub `validatePerasCert` that unconditionally returns `Right` for every certificate it receives. The inbound certificate-diffusion path (`processCerts`) iterates over the entire peer-supplied batch without any application-level size cap and calls this stub for each element, so every certificate in the batch is accepted and inserted into the `PerasCertDB`. Because accepted certificates contribute a weight boost to chain selection via `PerasWeightSnapshot`, an unprivileged peer can inject arbitrary certificates that point to any block, causing the honest node to apply artificial weight boosts and potentially prefer a non-canonical chain.

---

### Finding Description

**Root cause — stub validation always returns `Right`:**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No cryptographic check, no committee-membership check, no round-number sanity check, and no boosted-block reachability check is performed. Every `PerasCert` value, regardless of content, is wrapped in `ValidatedPerasCert` and returned as valid.

**Production wiring — stub is used in the live inbound path:**

`makePerasCertPoolWriterFromChainDB` passes this stub directly as the `validateCert` argument to `processCerts`:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

This writer is registered as the live handler for the `PerasCertDiffusionClient` mini-protocol in `NodeToNode.hs`:

```haskell
(makePerasCertPoolWriterFromChainDB systemTime getChainDB)
``` [3](#0-2) 

**Unbounded iteration over the peer-supplied batch — the structural analog:**

`processCerts` iterates over the entire peer-supplied list with no application-level size guard:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
``` [4](#0-3) 

Because `validateCert` always succeeds, every element of `certsNotAlreadyInDb` lands in `validatedCerts` and is unconditionally inserted into the `PerasCertDB`. The only throttle is the protocol-level `perasCertDiffusionMaxObjectsUnacknowledged` window (currently a hardcoded TODO placeholder of `10`), which limits per-message batch size but does not prevent repeated injection across many messages.

**Chain-selection consequence:**

Accepted certificates are stored in `PerasCertDB` and surfaced through `getWeightSnapshot`, which feeds `PerasWeightSnapshot`. Chain selection calls `preferAnchoredCandidate` using this snapshot:

```haskell
| otherwise =
    case AF.intersect ours cand of
      ...
      Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
        case preferCandidate
          (projectChainOrderConfig cfg)
          (weightedSelectView cfg weights oursSuffix)
          (weightedSelectView cfg weights candSuffix) of
``` [5](#0-4) 

`weightedSelectView` sums the `PerasWeight` boost for every point in the fragment that appears in the snapshot:

```haskell
wsvWeightBoost = weightBoostOfFragment weights frag
``` [6](#0-5) 

An adversary who injects a certificate whose `pcCertBoostedBlock` points to a block on a non-canonical fork causes that fork's fragment to accumulate artificial weight, potentially making it heavier than the honest chain.

### Impact Explanation

An unprivileged peer can send crafted `PerasCert` messages whose `pcCertBoostedBlock` field points to any block the honest node has seen. Because `validatePerasCert` performs no checks, every such certificate is accepted, stored, and reflected in the `PerasWeightSnapshot`. Chain selection then computes `wsvTotalWeight = blockNo + weightBoost` for each candidate fragment. By injecting enough certificates targeting a non-canonical fork, the adversary can make that fork's total weight exceed the honest chain's weight, causing the node to switch to the non-canonical chain.

This is a **Critical** bypass of Peras certificate validation: an unprivileged peer can cause unauthorized certificate acceptance and drive chain selection toward a non-canonical chain without possessing any stake, keys, or committee membership.

---

### Likelihood Explanation

The PerasCert diffusion mini-protocol is wired into the live node-to-node stack and is active whenever Peras is enabled. Any connected peer can send `PerasCert` objects. The stub is the only validation gate; there is no secondary check. Likelihood is **High** once Peras is enabled on a network where the stub has not been replaced.

---

### Recommendation

1. Replace the stub `validatePerasCert` with a real implementation that verifies: committee membership of the certificate issuer, BLS/aggregate signature over the boosted block and round number, round-number monotonicity, and that `pcCertBoostedBlock` refers to a block reachable from the current chain.
2. Add an application-level maximum batch size inside `processCerts` (independent of the protocol window) so that even a valid validator cannot be forced to iterate over an unbounded list in a single call.
3. Until real validation is in place, gate the `PerasCertDiffusionClient` handler so that it does not insert certificates into the `PerasCertDB` or trigger chain-selection side-effects.

### Proof of Concept

**Private-testnet reproduction sequence:**

1. Start an honest node with Peras enabled.
2. Connect an adversarial peer that speaks the `PerasCertDiffusion` mini-protocol.
3. The adversary sends a stream of `PerasCert` messages, each with `pcCertBoostedBlock` set to the tip of a pre-prepared non-canonical fork (a fork the honest node has already downloaded via BlockFetch).
4. Each message passes through `processCerts` → `validatePerasCert mkPerasParams` → `Right` → `addCert` → `PerasCertDB`.
5. Observe via tracing that `getWeightSnapshot` now returns a `PerasWeightSnapshot` containing boosts for the non-canonical fork's blocks.
6. Trigger chain selection (e.g., by adding a new block to the non-canonical fork). `preferAnchoredCandidate` computes `wsvTotalWeight` for both fragments; the non-canonical fork's total weight now exceeds the honest chain's weight due to the injected boosts.
7. The honest node switches to the non-canonical chain.
