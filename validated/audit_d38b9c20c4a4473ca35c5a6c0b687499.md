### Title
`shelleyAfterVoting` Counts All Post-Deadline Blocks Instead of Only Those in the First Stability Window, Enabling Premature Era Transition During Chain Growth Violation — (`ouroboros-consensus-cardano/src/shelley/Ouroboros/Consensus/Shelley/Ledger/Ledger.hs`)

---

### Summary

The `shelleyAfterVoting` counter in `ShelleyTransitionInfo` is incremented for every block whose slot is at or after the voting deadline, including blocks that fall in the *second* stability window (between `votingDeadline + swindow` and `startOfNextEpoch`). The intended behavior — explicitly documented as a known bug in the codebase — is to count only blocks in the *first* stability window after the voting deadline. Because the counter is inflated by blocks that should not be included, the Hard Fork Combinator (HFC) can declare an era transition as stable and trigger it even when Chain Growth has been violated, breaking the cross-era consensus invariant the counter was designed to protect.

---

### Finding Description

**Vulnerable type and counter:**

`ShelleyTransitionInfo` holds a single field `shelleyAfterVoting :: Word32`, described as "the number of blocks in this epoch past the voting deadline." [1](#0-0) 

**Where the counter is incremented (root cause):**

In `applyHelper`, the counter is incremented whenever `blockSlot blk >= votingDeadline`:

```haskell
shelleyAfterVoting =
    (if blockSlot blk >= votingDeadline then succ else id) $
      shelleyAfterVoting tickedShelleyLedgerTransition
``` [2](#0-1) 

The voting deadline is computed as:

```haskell
votingDeadline = subSlots (2 * swindow) startOfNextEpoch
``` [3](#0-2) 

This means the counter accumulates blocks in the entire range `[votingDeadline, startOfNextEpoch)`, which spans **two** stability windows. The intended behavior is to count only blocks in the **first** stability window `[votingDeadline, votingDeadline + swindow)`.

**Where the counter is consumed:**

In `shelleyTransition` (ShelleyHFC.hs), the counter is compared against `k` to decide whether to report the era transition to the HFC:

```haskell
guard $ shelleyAfterVoting >= fromIntegral k
``` [4](#0-3) 

**The documented bug:**

The `civic_time.md` design document explicitly acknowledges this as a bug under Iteration 4 of the HFC's Chain Growth violation handling:

> "Silently ignore the on-chain governance — ie the HFC continues with the current era *despite* the on-chain governance outcome having signaled the transition to the next era — if the stability window after the voting deadline contains less than k+1 blocks (ie violates Chain Growth).
> **(TODO this is today's intended behavior, but a bug is counting all blocks after the voting deadline instead of only those in the subsequent stability window.)**" [5](#0-4) 

**Structural analogy to the external report:**

| Hyperdrive | Ouroboros Consensus |
|---|---|
| `totalGovernanceFee` is computed but never subtracted from `shareReserves` | Blocks from the second stability window are counted but should be excluded from `shelleyAfterVoting` |
| Governance fees end up tradeable in the pool | Second-window blocks inflate the count, making the transition appear stable when it is not |
| Governance cannot claim its fees | HFC triggers an era transition it should suppress |

---

### Impact Explanation

The `shelleyAfterVoting >= k` guard is the sole mechanism by which the consensus layer ensures that the last pre-deadline block is immutable before reporting an era transition. When Chain Growth is violated (the first stability window after the voting deadline contains fewer than `k` blocks), the correct behavior is to suppress the transition. The bug allows the count to reach `k` by including blocks from the second stability window, so `shelleyTransition` returns `Just epochNo` and the HFC proceeds with the era transition.

Nodes that have seen `k` total post-deadline blocks (but fewer than `k` in the first stability window) will transition to the next era. Nodes that have not yet seen `k` total post-deadline blocks will stay in the current era. This produces a **hard-fork era mismatch** between honest nodes, breaking cross-era consensus — a High-severity impact under the allowed scope.

---

### Likelihood Explanation

Chain Growth violations do not require stake majority; they can arise from network partitions, eclipse attacks, or sustained low-density periods. The bug is only active in those scenarios, which are rare on mainnet but reproducible on a private testnet with a low active-slot coefficient. The Consensus Team has already identified and documented this as a known bug, confirming it is a real, reachable defect rather than a theoretical concern.

---

### Recommendation

Restrict the increment condition in `applyHelper` to only the first stability window after the voting deadline:

```haskell
shelleyAfterVoting =
    (if blockSlot blk >= votingDeadline
          && blockSlot blk < votingDeadline + swindow
       then succ
       else id) $
      shelleyAfterVoting tickedShelleyLedgerTransition
```

This ensures `shelleyAfterVoting` counts only blocks in `[votingDeadline, votingDeadline + swindow)`, matching the intended semantics described in the design documentation.

---

### Proof of Concept

On a private testnet:

1. Configure a Shelley-era network with a very low active-slot coefficient so that the first stability window after the voting deadline (`[votingDeadline, votingDeadline + swindow)`) produces fewer than `k` blocks.
2. Submit a governance update proposal that increments the major protocol version (triggering the next era).
3. Ensure the proposal is confirmed before the voting deadline.
4. Allow the chain to grow past `votingDeadline + swindow` with fewer than `k` blocks in that window, but accumulate `k` total blocks across both stability windows.
5. Observe that `shelleyTransition` returns `Just epochNo` and the HFC schedules the era transition — even though the Chain Growth invariant was violated and the transition should have been suppressed.

The root cause is confirmed at:
- `applyHelper`, `Ledger.hs` line 720 — counter incremented for all post-deadline blocks
- `shelleyTransition`, `ShelleyHFC.hs` line 224 — counter consumed without distinguishing which stability window the blocks came from
