### Title
Unvalidated `key_version` in `sign_btc_transaction` allows any caller to store an invalid MPC signature, permanently blocking withdrawal signing — (File: `contracts/satoshi-bridge/src/api/chain_signatures.rs`)

---

### Summary

`sign_btc_transaction` is a public, payable function with no role restriction and no validation of the caller-supplied `key_version` parameter. Any account can call it with an incorrect `key_version`, causing the MPC to sign with a different key than the one controlling the UTXO. The resulting invalid signature is stored and can never be overwritten due to the "Already signed" guard. This permanently blocks the legitimate signing of that PSBT input and locks the user's withdrawal funds.

---

### Finding Description

`sign_btc_transaction` in `contracts/satoshi-bridge/src/api/chain_signatures.rs` is decorated only with `#[payable]` and `#[pause(...)]` — there is no role check, no whitelist check, and no restriction on who may call it: [1](#0-0) 

The caller-supplied `key_version: u32` is forwarded without any validation to the MPC signer inside `internal_sign_btc_transaction`: [2](#0-1) 

Before dispatching the sign call, the code checks that the slot is empty: [3](#0-2) 

In the callback, the returned signature is stored unconditionally (after a second "Already signed" guard) and can never be replaced: [4](#0-3) 

The bridge stores no expected `key_version` in the UTXO or in `BTCPendingInfo`, so there is nothing to validate against. The `path` used for key derivation is taken from the stored UTXO (correct), but the `key_version` selects which root key the MPC uses for that path. A wrong `key_version` produces a valid-looking ECDSA signature over the correct hash, but under a completely different public key — one that does not match the script controlling the UTXO. The Bitcoin network will reject the transaction.

Attack steps:
1. Attacker observes a `GenerateBtcPendingInfo` event to learn a live `btc_pending_sign_id`.
2. Attacker calls `sign_btc_transaction(btc_pending_sign_id, sign_index=0, key_version=9999)` with a small NEAR deposit (forwarded to MPC).
3. MPC returns a signature under the wrong key; `sign_btc_transaction_callback` stores it at `signatures[0]`.
4. Legitimate relayer calls `sign_btc_transaction(..., key_version=0)` → panics with `"Already signed"`.
5. All inputs eventually accumulate invalid signatures; `is_all_signed()` triggers broadcast of an invalid transaction.
6. Bitcoin nodes reject the transaction; the withdrawal is permanently stuck. [5](#0-4) 

---

### Impact Explanation

The user's nBTC is held in the bridge balance (not yet burned) and the BTC UTXOs are locked inside the pending transaction. The signed-but-invalid transaction cannot be broadcast. Recovery requires a privileged `cancel_withdraw` call by DAO/Operator, which itself must go through a new RBF signing round — which is also vulnerable to the same attack. In the worst case, the user's BTC UTXOs are permanently locked until the operator successfully races the attacker.

This matches: **Medium — attacker-triggered temporary locking of bridged funds / stuck bridge state requiring operator intervention.** [6](#0-5) 

---

### Likelihood Explanation

- `sign_btc_transaction` is fully public and callable by any NEAR account.
- `btc_pending_sign_id` values are emitted in on-chain events (`GenerateBtcPendingInfo`), so they are trivially discoverable.
- The only cost to the attacker is the NEAR deposit forwarded to the MPC for one signing call — a small, fixed amount.
- NEAR transaction ordering is deterministic within a block; a well-timed call can reliably front-run the relayer.

---

### Recommendation

1. **Store and validate `key_version`**: Record the expected `key_version` in `BTCPendingInfo` at creation time (derived from config or the UTXO's derivation parameters) and `require!` that the caller-supplied value matches before dispatching the MPC call.
2. **Restrict the caller**: Gate `sign_btc_transaction` behind a trusted-relayer or operator role, consistent with how other sensitive bridge operations are protected.

---

    pub fn sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> PromiseOrValue<bool> {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        btc_pending_info.assert_pending_sign();
        if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {
            if !self.check_btc_pending_info_exists(original_tx_id) {
                require!(
                    self.internal_unwrap_mut_account(&btc_pending_info.account_id.clone())
                        .btc_pending_sign_ids
                        .remove(&btc_pending_sign_id),
                    "Internal error"
                );
                self.internal_remove_btc_pending_info(&btc_pending_sign_id);
                return PromiseOrValue::Value(true);
            }
        }
        self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
            .into()
    }

    pub fn internal_sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> Promise {
        let pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);

        let public_keys: Vec<_> = pending_info
            .vutxos
            .iter()
            .map(|vutxo| self.generate_btc_public_key(&vutxo.get_path()))
            .collect();

        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        require!(
            btc_pending_info.signatures[sign_index].is_none(),
            "Already signed"
        );
        let payload = btc_pending_info
            .get_psbt()
            .get_hash_to_sign(sign_index, &public_keys);
        let path = btc_pending_info.vutxos[sign_index].get_path();
        self.sign_promise(SignRequest {
            payload,
            path,
            key_version,
        })
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_SIGN_BTC_TRANSACTION_CALL_BACK)
                .sign_btc_transaction_callback(
                    btc_pending_info.account_id.clone(),
                    btc_pending_sign_id,
                    sign_index,
                ),
        )
    }
