### Title
Lack of Caller Verification in `request_refund` Allows Attacker to Redirect Any User's BTC Refund - (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary
`request_refund` accepts a `deposit_msg` (containing the victim's `recipient_id`) and a caller-supplied `refund_address` without verifying that the caller is the `recipient_id`. When the victim's original `deposit_msg.refund_address` is `None`, any unprivileged NEAR account can call `request_refund` for any unfinalized deposit and supply an attacker-controlled BTC address, then call `execute_refund` after the timelock to steal the victim's BTC.

### Finding Description

`request_refund` is a public, permissionless function (no `#[trusted_relayer]` on the method itself, no `#[access_control_any]`): [1](#0-0) 

The only caller check inside the function body is for the optional `gas_fee` parameter: [2](#0-1) 

There is no check that `env::predecessor_account_id() == deposit_msg.recipient_id`. The function accepts an arbitrary `refund_address` (the BTC destination) and an arbitrary `deposit_msg.recipient_id` (the victim's NEAR account). The API documentation itself confirms the conditional logic: "If `deposit_msg.refund_address` is set, it must match the provided `refund_address`." When `deposit_msg.refund_address` is `None` — which is the common case, as seen throughout the test suite — any caller can supply any BTC address. [3](#0-2) 

`execute_refund` is similarly permissionless — no caller check, anyone can trigger it after the timelock: [4](#0-3) 

Once the attacker's refund request is registered, the victim cannot cancel it. `reject_refund` is restricted to DAO/Operator: [5](#0-4) 

The `#[trusted_relayer]` attribute on the `impl` block does not enforce the relayer check on all methods within it. Methods that actually require the relayer role carry `#[trusted_relayer]` on the method itself (e.g., `verify_refund_finalize`, `remove_refund_pending_tx_id`), while `request_refund`, `reject_refund`, and `execute_refund` do not: [6](#0-5) [7](#0-6) 

### Impact Explanation

An attacker can steal BTC that was deposited by a victim but never finalized by a relayer. The attacker registers a refund request pointing to their own BTC address, waits out the timelock, and calls `execute_refund`. The victim's BTC is permanently redirected. This is a **Critical** impact: significant theft of user funds (BTC) via an unauthorized redirect of bridge-controlled assets.

### Likelihood Explanation

- All inputs needed by the attacker are public: the victim's `deposit_msg` is emitted as an event by `get_user_deposit_address`, and the BTC transaction proof is on-chain.
- Deposits with `refund_address: None` are the default pattern throughout the codebase.
- The attacker only needs to pay a small NEAR anti-spam fee, which is negligible relative to any meaningful BTC deposit.
- The victim has no self-service remedy once the attacker's request is registered.
- Likelihood is **High** for any deposit that stalls (relayer downtime, congestion, or deliberate griefing).

### Recommendation

Add a caller-identity check at the start of `request_refund`:

```rust
let caller = env::predecessor_account_id();
require!(
    caller == deposit_msg.recipient_id
        || self.acl_has_role(Role::DAO.into(), caller.clone())
        || self.acl_has_role(Role::Operator.into(), caller),
    "Only the deposit recipient, DAO, or Operator can request a refund"
);
```

Alternatively, require that `deposit_msg.refund_address` is always set (non-`None`) and enforce that the provided `refund_address` matches it unconditionally, removing the free-form path entirely.

### Proof of Concept

1. Alice deposits 1 BTC using `deposit_msg = { recipient_id: "alice.near", refund_address: None, ... }`. The deposit address is derived and emitted as an event.
2. The relayer never calls `verify_deposit` (downtime, or attacker front-runs with a griefing transaction).
3. Attacker Eve observes Alice's `deposit_msg` from the event log and the BTC transaction on-chain.
4. Eve calls:
   ```
   request_refund(
     deposit_msg = { recipient_id: "alice.near", refund_address: None, ... },
     refund_address = "eve_btc_address",
     tx_bytes = <Alice's BTC tx>,
     vout = 0,
     proof = <valid merkle proof>,
     gas_fee = None
   )
   ```
   with the required NEAR anti-spam deposit attached.
5. The light client verifies the proof. A `RefundRequest` is stored with `refund_address = "eve_btc_address"`.
6. After the timelock, Eve calls `execute_refund(utxo_storage_key)`.
7. The bridge constructs and signs a BTC transaction sending Alice's 1 BTC to Eve's address.
8. Alice's BTC is stolen. [1](#0-0) [4](#0-3)

    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
