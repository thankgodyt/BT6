### Title
`stakeAboveThreshold` Compares Unnormalized `PerasVoteStake` Against a Relative Quorum Threshold, Enabling Unauthorized Peras Certificate Forging - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` directly compares a `PerasVoteStake` value against a relative quorum threshold (`3/4 + safety margin`) without any normalization step. The code itself documents that there is no settled decision on whether `PerasVoteStake` carries absolute lovelace or a normalized ratio. If the `PerasVoteStakeDistr` supplied to `validatePerasVote` is populated with absolute stake values (as the ledger naturally expresses them), the comparison is dimensionally incoherent: any pool holding more than `~0.77` lovelace satisfies the threshold, so a single crafted vote from any registered pool unconditionally forges a Peras certificate for an attacker-chosen block.

---

### Finding Description

`stakeAboveThreshold` in `SupportsPeras.hs` is the sole gate that decides whether accumulated vote stake has reached the Peras quorum:

```haskell
-- TODO: this function assumes that the 'PerasVoteStake' and the quorum
-- threshold used in 'PerasParams' are expressed in the same units. That is,
-- both are either absolute or relative (normalized) values. Under the current
-- current implementation of 'PerasParams', this function only makes sense when
-- both values are relative (normalized) values, so we should either normalize
-- the 'PerasVoteStake' before calling this function, or change this function to
-- accept a stake distribution and perform the normalization internally.
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
```

The quorum threshold is a hard-coded relative value (`3/4`) and the safety margin is `2/100`, giving a combined threshold of `0.77`. [1](#0-0) 

The `PerasVoteStake` type is a bare `Rational`, and the type-level comment explicitly records that no decision has been made on the conversion from absolute ledger stake to the normalized committee stake:

```haskell
-- NOTE: At the moment there is no consensus from researchers/engineers on how
-- we go from the absolute stake of a voter in the ledger to the relative stake
-- of their vote in the voting commitee (given that the quorum is expressed as
-- a relative value of the voting commitee total stake).
newtype PerasVoteStake = PerasVoteStake { unPerasVoteStake :: Rational }
``` [2](#0-1) 

`validatePerasVote` assigns the stake value directly from `PerasVoteStakeDistr` without any normalization:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
``` [3](#0-2) 

The validated stake flows directly into `votesReachQuorum` → `stakeAboveThreshold`, which triggers `forgePerasCert` if the threshold is met:

```haskell
case votesReachQuorum cfg voteList of
  Just votesWithQuorum -> do
    cert <- forgePerasCert cfg votesWithQuorum
    pure $ BecameWinner (PerasTargetVoteWinner newVoteTally cert)
``` [4](#0-3) 

The same unnormalized comparison is also used in `updateLoserVoteState` to detect a second winner: [5](#0-4)

### Impact Explanation

When `PerasVoteStakeDistr` is populated with absolute lovelace values (the natural ledger representation), a pool holding, say, 1,000,000 lovelace contributes a `PerasVoteStake` of `1000000 % 1`. The comparison `1000000 >= 3/4 + 2/100` is trivially `True`. A single vote from any pool with more than ~0.77 lovelace (i.e., every real pool) immediately satisfies the quorum check, causing `forgePerasCert` to produce a `ValidatedPerasCert` for the attacker's chosen block. That certificate carries a `PerasWeight` boost that directly influences chain selection, allowing the attacker to make an honest node prefer a non-canonical chain without holding the required fraction of actual stake. This is a bypass of the Peras voting quorum check.

---

### Likelihood Explanation

The conversion from absolute ledger stake to normalized committee stake is explicitly unresolved (documented in the source). Any implementation that feeds raw ledger lovelace values into `PerasVoteStakeDistr` — the most natural and straightforward approach — triggers the bug. The `PerasVoteStakeDistr` is constructed by the node from its own ledger view and passed into `validatePerasVote`; an unprivileged peer only needs to send a syntactically valid vote referencing a real pool to trigger the path. The `validatePerasCert` and `validatePerasVote` implementations are currently stubs that perform no cryptographic checks, further lowering the bar.

---

### Recommendation

`stakeAboveThreshold` must not accept a raw `PerasVoteStake` whose unit is unspecified. Two concrete fixes mirror the TODO's own suggestions:

1. **Normalize at construction time**: when building `PerasVoteStakeDistr` from the ledger, divide each pool's absolute stake by the total active stake so every entry is already a value in `[0,1]`.
2. **Normalize at comparison time**: change `stakeAboveThreshold` to accept the total active stake as an additional argument and perform the division internally before comparing against the relative threshold.

Either approach eliminates the unit mismatch. The fix is directly analogous to the external report's recommendation: check which "supply" method applies before using the value in a critical calculation.

### Proof of Concept

Assume `PerasVoteStakeDistr` is built from raw ledger lovelace (e.g., pool P holds 2,000,000 lovelace):

```
stakeDistr = PerasVoteStakeDistr { P -> PerasVoteStake (2000000 % 1) }
```

Attacker sends one vote: `PerasVote { pvVoteRound = R, pvVoteBlock = B, pvVoteVoterId = P }`.

1. `validatePerasVote` looks up P → `stake = 2000000 % 1`. Returns `ValidatedPerasVote { vpvVoteStake = 2000000 % 1 }`.
2. `votesReachQuorum` calls `stakeAboveThreshold params (PerasVoteStake (2000000 % 1))`.
3. `2000000 >= 3/4 + 2/100` → `True`.
4. `forgePerasCert` is called → `ValidatedPerasCert { vpcCert = PerasCert R B, vpcCertBoost = 15 }` is produced.
5. Block B receives a weight boost of 15 in chain selection from a single attacker vote, bypassing the intended quorum of 77% of committee stake. [1](#0-0) [2](#0-1) [4](#0-3) [6](#0-5)
