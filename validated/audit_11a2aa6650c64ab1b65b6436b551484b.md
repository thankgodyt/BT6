### Title
Chain Selection Uses Hardcoded Empty Peras Weight Snapshot in `checkPreferTheirsOverOurs`, Enabling Incorrect Peer Disconnection — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

`checkPreferTheirsOverOurs` in the ChainSync client always passes `emptyPerasWeightSnapshot` (all-zero Peras weights) to `preferAnchoredCandidate` when deciding whether to disconnect from a peer whose headers are beyond the forecast horizon. This is the direct analog of the external report's pattern: a stale/incorrect value is used in a critical chain-selection decision instead of the live, accurate value. The actual chain-selection path (`chainSelectionForBlock`) correctly reads the live `PerasWeightSnapshot` from `PerasCertDB`, but this guard function never does.

---

### Finding Description

When a header from a peer is beyond the forecast horizon, `projectLedgerView` returns `Nothing` and the ChainSync client calls `checkPreferTheirsOverOurs` to decide whether to keep tracking the peer or disconnect:

```haskell
-- Client.hs ~1834-1851
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← always zero; never reads live PerasCertDB
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse ...
```

`emptyPerasWeightSnapshot` is a constant `Map.empty`; it assigns zero Peras boost to every block. The comparison therefore degenerates to a pure block-count comparison, identical to pre-Peras behaviour.

The live weight snapshot is available via `PerasCertDB.getWeightSnapshot` (an STM action), which is exactly what `chainSelectionForBlock` reads at line ~634:

```haskell
-- ChainSel.hs ~629-634
(invalid, curChain, weights) <-
  atomically $
    (,,)
      <$> (forgetFingerprint <$> readTVar cdbInvalid)
      <*> Query.getCurrentChain cdb
      <*> (forgetFingerprint <$> Query.getPerasWeightSnapshot cdb)
```

The two code paths use fundamentally different inputs for the same conceptual question ("is the candidate chain preferred?"), creating an inconsistency that can be exploited.

---

### Impact Explanation

Under Peras, the canonical chain is the one with the highest *total weight* = `BlockNo + PerasBoost`. A chain with 100 blocks and a Peras boost of 60 (total weight 160) is canonical over a chain with 130 blocks and no boost (total weight 130).

When headers from both peers are beyond the forecast horizon:

| Peer | Blocks | Peras boost | Total weight | `emptyPerasWeightSnapshot` verdict | Live-weight verdict |
|------|--------|-------------|--------------|-------------------------------------|---------------------|
| Honest (canonical) | 100 | 60 | 160 | **shorter → disconnect** | preferred |
| Adversary | 130 | 0 | 130 | longer → keep | not preferred |

The node disconnects from the honest peer and continues tracking the adversary. Once the adversary's blocks are downloaded and `chainSelectionForBlock` runs with live weights, the adversary's chain (weight 130) beats the node's current chain only if the current chain has weight < 130. If the node has already been on a chain of weight < 130, it adopts the adversary's chain (weight 130) and can no longer reach the canonical chain (weight 160) because it has severed the connection to the only peer offering it.

This is a **chain selection bug** that lets an unprivileged peer cause an honest node to prefer a non-canonical, less-secure chain beyond the intended Peras security assumptions.

---

### Likelihood Explanation

- **Peras must be active** with at least one certificate boosting a block on the canonical chain. This is the intended production state once Peras is deployed.
- **Headers must be beyond the forecast horizon.** This occurs naturally during initial sync or when the intersection point is far back (up to *k* blocks), which is a normal operating condition.
- **The canonical chain must be shorter in block count but heavier in total weight.** This is the exact scenario Peras is designed to handle: a shorter but certificate-boosted chain winning over a longer unboosted chain.
- **No other peer offers the canonical chain.** In a targeted attack, the adversary can eclipse the victim's peer set, or the honest peer may simply not reconnect quickly enough.

The conditions are realistic in a deployed Peras network and are reachable by any unprivileged peer without any key material or stake.

---

### Recommendation

Replace the hardcoded `emptyPerasWeightSnapshot` with the live snapshot read from `PerasCertDB` inside the same STM transaction. Since `checkPreferTheirsOverOurs` already runs in `STM m`, the fix is straightforward:

```haskell
checkPreferTheirsOverOurs kis = do
  weights <- forgetFingerprint <$> PerasCertDB.getWeightSnapshot perasCertDB
  if shouldSwitch $
       preferAnchoredCandidate (configBlock cfg) weights ourFrag theirFrag
    then pure ()
    else throwSTM $ CandidateTooSparse ...
```

Alternatively, if the entire check is to be removed as the TODO comment at line 1841 indicates (referencing `https://github.com/tweag/cardano-peras/issues/64`), the removal should be prioritised before Peras is activated on mainnet, since the current placeholder actively harms chain selection correctness under Peras.

---

### Proof of Concept

1. Peras is active. A certificate boosts block `B₁₀₀` on the honest chain, giving it total weight 160 (100 blocks + 60 boost).
2. An adversary constructs a fork of 130 blocks with no certificate (total weight 130).
3. Both peers' chains extend beyond the current forecast horizon (e.g., intersection is *k* blocks back and both chains are long).
4. For the honest peer: `checkPreferTheirsOverOurs` calls `preferAnchoredCandidate` with `emptyPerasWeightSnapshot`. The honest chain has 100 blocks vs. the node's current chain; if the node's current chain is longer, `shouldSwitch` returns `False` → `throwSTM CandidateTooSparse` → **honest peer disconnected**.
5. For the adversary: same call with empty weights. The adversary's chain has 130 blocks, which is longer → `shouldSwitch` returns `True` → **adversary kept**.
6. The node downloads the adversary's 130 blocks. `chainSelectionForBlock` runs with live weights: adversary weight 130 > current chain weight (say 110) → node **adopts the adversary's chain** (weight 130).
7. The canonical chain (weight 160) is now unreachable because the honest peer was disconnected in step 4.

The node has selected a non-canonical chain, violating the Peras chain-selection invariant, triggered entirely by an unprivileged peer sending headers beyond the forecast horizon. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
