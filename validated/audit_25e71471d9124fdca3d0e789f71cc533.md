### Title
Dijkstra Era `EraParams` Unconditionally Sets `eraPerasRoundLength = NoPerasEnabled`, Silently Disabling Peras Round-Number Queries for the Peras Era — (File: `ouroboros-consensus-cardano/src/shelley/Ouroboros/Consensus/Shelley/Ledger/Ledger.hs`)

---

### Summary

`shelleyEraParams` hardcodes `eraPerasRoundLength = HardFork.NoPerasEnabled` for every Shelley-family era. In `Cardano/Node.hs`, that same function is reused verbatim for all seven Shelley-family eras in the HFC `Shape`, including the Dijkstra era — the era in which Peras is supposed to be active. Consequently the Dijkstra era's `EraParams` carries `NoPerasEnabled`, causing every Peras round-number query issued against the Dijkstra era to silently short-circuit and return `NoPerasEnabled` instead of a valid round number. This is the direct analog of the reported pattern: a single setter/constructor assigns the same value to two logically distinct roles (here, the same `EraParams` record is reused for eras that should differ in `eraPerasRoundLength`), breaking the logic that depends on the distinction.

---

The Dijkstra era is the Peras era; it should carry `eraPerasRoundLength = PerasEnabled (PerasRoundLength 90)` (matching `mkPerasParams`), but instead receives the same `NoPerasEnabled` value as every pre-Peras era.

**Where `eraPerasRoundLength` is consumed**

`EraParams.eraPerasRoundLength` drives two critical subsystems:

1. **`Qry.hs` — Peras round-number queries** (`EPerasRoundLength`, `ERelSlotToPerasRoundNo`, `ERelPerasRoundNoToSlot`, `ERelToAbsPerasRoundNo`). Each of these is wrapped in `PerasEnabledT`; when `eraPerasRoundLength = NoPerasEnabled` the monad short-circuits and returns `NoPerasEnabled` without error. [3](#0-2) 

2. **`Summary.hs` — `Bound` computation**. The `boundPerasRound` field of every era-boundary `Bound` is derived from `eraPerasRoundLength`. With `NoPerasEnabled` for Dijkstra, `boundPerasRound` at the Dijkstra era start is `NoPerasEnabled`, severing the Peras round-number timeline at the era boundary. [4](#0-3) 

The `PerasEnabled` wrapper is defined as a `Maybe`-backed monad that silently propagates `Nothing` (i.e., `NoPerasEnabled`) through any chain of Peras-specific computations: [5](#0-4) 

There is no error raised; every Peras round-number query for the Dijkstra era silently returns `NoPerasEnabled`.

---

### Impact Explanation

When the Peras feature flag is enabled (`rnFeatureFlags`) and the chain enters the Dijkstra era:

- **Peras round-number queries fail silently.** Any component that calls `ERelSlotToPerasRoundNo` or `ERelPerasRoundNoToSlot` for a Dijkstra-era slot receives `NoPerasEnabled` instead of a round number. Code that pattern-matches on `PerasEnabled r` will skip the Peras branch entirely, as if Peras were not active.
- **`boundPerasRound` is `NoPerasEnabled` at the Dijkstra era start.** Peras round-number continuity across the Conway→Dijkstra boundary is broken; any downstream logic that relies on the absolute Peras round number at era start (e.g., certificate round-number validation, committee selection) operates on an undefined baseline.
- **Chain-selection weight boosts are undermined.** If the weight-boost logic queries the HFC interpreter for the round number of a certificate's slot and receives `NoPerasEnabled`, the boost is silently skipped, allowing an adversary to present a chain whose Peras-boosted weight is not correctly accounted for, potentially causing an honest node to prefer a less-secure fork.

This matches the **High** impact category: *Hard-fork, era transition, ledger-view, query, or network-version mismatch that breaks cross-era consensus or ledger invariants for production Cardano nodes.*

---

### Likelihood Explanation

The condition is met on any node that:
1. Enables the Peras feature flag (`rnFeatureFlags`),
2. Runs a chain that has transitioned into the Dijkstra era (private testnet or future mainnet),
3. Receives Peras votes or certificates from peers (standard miniprotocol traffic).

No special attacker capability is required beyond being an ordinary peer that sends Peras protocol messages. The bug is structural and fires deterministically once the Dijkstra era is active.

---

### Recommendation

Replace the single `shelleyEraParams genesisShelley` call for the Dijkstra slot in `Cardano/Node.hs` with a dedicated `dijkstraEraParams` function that sets `eraPerasRoundLength = PerasEnabled (PerasRoundLength (perasRoundLength mkPerasParams))`. This mirrors the pattern already used for Byron (`byronEraParams`) and resolves the TODO at line 178 of `Ledger.hs`.

Alternatively, add an `eraPerasRoundLength` parameter to `shelleyEraParams` and pass `NoPerasEnabled` for all pre-Dijkstra eras and `PerasEnabled roundLen` for Dijkstra, so the two logically distinct roles are no longer conflated by a single shared function call.

---

### Proof of Concept

1. Start a private testnet with `rnFeatureFlags` including Peras and configure the chain to enter the Dijkstra era.
2. Issue a `GetInterpreter` local-state query and call `interpretQuery interpreter (qryFromExpr (EPerasRoundLength (ELit someSlotInDijkstra)))`.
3. Observe the query returns `NoPerasEnabled` (i.e., `Nothing`) instead of the expected `PerasRoundLength 90`.
4. Confirm that `ERelSlotToPerasRoundNo` likewise returns `NoPerasEnabled` for any Dijkstra-era slot, meaning the node cannot determine what Peras round it is in.
5. Confirm that `boundPerasRound` in the `Bound` at the Conway→Dijkstra transition is `NoPerasEnabled`, breaking absolute round-number continuity for all subsequent Peras certificate validation.
