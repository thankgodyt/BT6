### Title
Stub `validatePerasCert` always returns `Right`, allowing any peer-supplied Peras certificate to bypass validation, be stored in PerasCertDB, and trigger chain selection for an invalid cert-boosted fork — (`ObjectPool/PerasCert.hs`)

### Summary
The default implementation of `validatePerasCert` in `BlockSupportsPeras` is a TODO stub that unconditionally accepts every certificate. The production inbound cert diffusion path (`makePerasCertPoolWriterFromChainDB`) passes this stub directly to `processCerts`, which stores any cert that passes and fires `ChainDB.addPerasCertAsync`. An unprivileged peer can therefore inject a cert with a fabricated committee proof, invalid BLS signature, or out-of-range round number, have it stored durably, and cause the node to switch to a fork that is only heavier due to the invalid boost.

### Finding Description
`BlockSupportsPeras` defines a default method:

```haskell
-- SupportsPeras.hs lines 353-358
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
```

No committee membership check, no BLS/VRF signature verification, and no round-constraint check is performed. The production pool writer (`makePerasCertPoolWriterFromChainDB`, `ObjectPool/PerasCert.hs` line 126) passes `validatePerasCert mkPerasParams` as the validator to `processCerts`. `processCerts` only throws `PerasCertValidationError` when `validateCert` returns `Left`; since the stub never does, every peer-supplied cert is accepted, timestamped, and forwarded to `ChainDB.addPerasCertAsync`, which triggers chain selection with the cert's boost weight applied.

### Impact Explanation
A peer can craft a `PerasCert` referencing any block on any fork. The cert passes `validatePerasCert`, is stored in `PerasCertDB`, and the chain selection logic applies `vpcCertBoost` (= `perasWeight params`) to that block. If the boosted fork becomes heavier than the current chain, the node durably switches to it. This constitutes:
- **Critical**: bypass of Peras certificate checks enabling unauthorized cert acceptance.
- **High**: chain selection bug letting an unprivileged peer make an honest node prefer a non-canonical chain.
- **High**: durable use of the wrong ledger state via acceptance of an invalid cert-boosted chain.

### Likelihood Explanation
Any peer participating in the Peras cert object-diffusion miniprotocol can exploit this. No stake, no keys, and no operator compromise are required — only the ability to send a well-formed (but cryptographically invalid) `PerasCert` message over the NodeToNode connection. The path is fully exercised on unmodified code whenever Peras cert diffusion is enabled.

### Recommendation
Replace the stub with real validation before enabling Peras cert diffusion in any environment connected to untrusted peers:
- Implement committee membership verification (VRF-based seat selection against the stake snapshot).
- Implement BLS aggregate signature verification over the cert payload.
- Enforce round-number constraints (cert round must be within the current Peras window, not already superseded, etc.).
- Wire the real `PerasParams` from the ledger state rather than the hardcoded `mkPerasParams`.
- Until real validation is in place, gate the object-diffusion miniprotocol negotiation so it is not offered to untrusted peers.

### Proof of Concept

-- run it through processCerts with the stub validator,
-- assert it is accepted (demonstrating the bug).
let fakeCert = PerasCert
      { pcCertRound        = PerasRoundNo 999
      , pcCertBoostedBlock = somePoint  -- any fork tip
      }
result <- try @SomeException $
  processCerts
    systemTime
    (pure Set.empty)                    -- nothing in DB yet
    (validatePerasCert mkPerasParams)   -- stub: always Right
    (\_ -> pure ())                     -- capture instead of storing
    [fakeCert]
