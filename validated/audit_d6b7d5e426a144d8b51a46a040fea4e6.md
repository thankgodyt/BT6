### Title
Single `HistoricityCutoff` Calibrated to Shelley Stability Window Is Too Permissive for Byron Era Sync — (File: `ouroboros-consensus-diffusion/src/ouroboros-consensus-diffusion/Ouroboros/Consensus/Node/Genesis.hs`)

---

### Summary

`mkGenesisConfig` hardcodes `gcHistoricityCutoff` to the **Shelley** stability window (36 hours + 1 hour margin = 37 hours). Byron's stability window is only **24 hours** (2k slots × 20 s/slot). During Genesis sync over Byron blocks, an adversarial peer can send `MsgRollBackward` or `MsgAwaitReply` messages whose tip is 24–37 hours old and **not be disconnected** by the historicity check, because the single threshold is too permissive for Byron. This is the direct analog of the DeFi report: one hardcoded freshness threshold applied uniformly to all items (eras) when each item has a different correct threshold.

---

### Finding Description

`mkGenesisConfig` in `Genesis.hs` sets:

```haskell
gcHistoricityCutoff = Just $ HistoricityCutoff $ 3 * 2160 * 20 + 3600
-- "Duration in seconds of one Cardano mainnet Shelley stability window
--  (3k/f slots times one second per slot) plus one extra hour as a safety margin."
``` [1](#0-0) 

This evaluates to `129600 + 3600 = 133200 seconds ≈ 37 hours`, which is the Shelley chain-growth window (`3k/f` slots × 1 s/slot, with `k=2160`, `f=0.05`).

`mkCheck` in `HistoricityCheck.hs` applies this single value uniformly to every `MsgRollBackward` and `MsgAwaitReply` received during sync, regardless of which era the rolled-back header belongs to:

```haskell
let actualRollbackAge = arrivalTime `diffRelTime` slotTime
pure $
  when (historicityCutoff < actualRollbackAge) $
    throwError HistoricityException { ... }
``` [2](#0-1) 

The `HistoricityCutoff` documentation itself states the correct requirement:

> "This should be set to at least the maximum duration **(across all eras)** of a stability window." [3](#0-2) 

Byron's stability window is `2k` slots × 20 s/slot = `2 × 2160 × 20 = 86400 s = 24 hours`, as confirmed by `byronEraParams`:

```haskell
eraSafeZone = HardFork.StandardSafeZone (2 * k)
``` [4](#0-3) 

The design document explicitly acknowledges the mismatch and the intended mitigation:

> "One caveat: MaxCaughtUpAge and HistoricityCutoff are indeed **constants** in the implementation, but Sgen is actually implemented to vary as the chain transitions eras."



The stated mitigation is **Lightweight Checkpointing** to exclude Byron from the GDD window. However, `mkGenesisConfig` — the default configuration path — does not enforce that Lightweight Checkpointing is active. The `gcHistoricityCutoff` field is set unconditionally whenever Genesis is enabled, with no guard that Lightweight Checkpointing is also configured. [5](#0-4) 

---

### Impact Explanation

During Genesis sync over the Byron portion of the chain (without Lightweight Checkpointing active), an adversarial peer can:

1. Send a `MsgRollBackward` rewinding to a Byron header whose slot onset is **25–37 hours** before arrival time.
2. The historicity check computes `actualRollbackAge = arrivalTime - slotTime` and compares it to `133200 s`. Since `25–37 hours < 37 hours`, the check **passes** and the peer is **not disconnected**.
3. For Byron, any rollback to a point older than 24 hours already violates the Byron maximum rollback depth (the Byron stability window). An honest caught-up Byron peer would never do this.
4. The adversarial peer remains connected and can continue serving a non-canonical Byron chain, forcing the syncing node to process it through the GDD and LoP — defenses that are more expensive and slower to act than the historicity check.
5. In the worst case, the adversarial peer can keep the syncing node anchored to a stale Byron fork for up to 13 extra hours (37 − 24) before the historicity check would have caught it, during which the GDD must independently detect and disconnect the peer.

This weakens the Genesis sync chain-selection defense for the Byron era, allowing an unprivileged peer to cause an honest syncing node to spend time on a non-canonical chain beyond the intended security assumptions of the historicity check.

---

### Likelihood Explanation

- Any unprivileged peer connected to a syncing node with Genesis enabled can trigger this by sending a crafted `MsgRollBackward` to a Byron point 25–37 hours old.
- No key compromise, stake majority, or operator action is required.
- The condition is reachable on any Cardano node syncing from genesis without Lightweight Checkpointing configured, including private testnets and new mainnet nodes.
- The design document acknowledges the gap but relies on Lightweight Checkpointing as an external guard that is not enforced in `mkGenesisConfig`.

---

### Recommendation

Make `HistoricityCutoff` era-aware, analogous to how `Sgen` is already implemented to vary per era. Specifically:

1. Derive the cutoff from the per-era stability window (available via `EraParams.eraSafeZone` / `eraSlotLength`) rather than hardcoding the Shelley value.
2. At minimum, document and enforce that `gcHistoricityCutoff` must be set to the **Byron** stability window (24 hours + margin) when Lightweight Checkpointing is not active, since Byron has the smallest stability window of any Cardano era.
3. Add a runtime assertion or configuration validation that rejects a `GenesisConfig` where `gcHistoricityCutoff` is set to a value larger than the smallest per-era stability window unless Lightweight Checkpointing is confirmed to exclude that era.

---

### Proof of Concept

**Setup:** A private Cardano testnet with Genesis sync enabled (`enableGenesisConfigDefault`) and Lightweight Checkpointing disabled. The syncing node is in `Syncing` state processing Byron blocks.

**Attacker action:** The adversarial peer, connected via the ChainSync miniprotocol, sends:

```
MsgRollBackward (Point Byron slotX) tip
```

where `slotX` corresponds to a Byron slot whose onset is `T - 90000 s` (25 hours ago), and `T` is the current arrival time.

**Expected behavior (correct):** The historicity check should compute `actualRollbackAge = 90000 s > 86400 s (Byron stability window)` and disconnect the peer.

**Actual behavior (buggy):** The check computes `actualRollbackAge = 90000 s < 133200 s (hardcoded Shelley cutoff)` and **does not disconnect** the peer. The peer remains connected and can continue serving the stale Byron fork, forcing the syncing node to rely solely on the GDD and LoP to eventually detect and disconnect the adversarial peer — a slower and more resource-intensive path.
