### Title
Peras Certificate Validation Stub Unconditionally Accepts All Inbound Certificates, Allowing Unprivileged Peers to Manipulate Chain Selection — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` implementation is a stub that unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or committee-membership verification. Because the production certificate-diffusion pipeline (`processCerts` / `makePerasCertPoolWriterFromChainDB`) calls this function directly on every certificate received from a peer, any unprivileged peer can inject an arbitrary `PerasCert` that will be stored in the database and used to boost the weight of an attacker-chosen block during chain selection, without holding any stake or committee membership.

This is the direct analog of the reported paymaster bug: just as a paymaster could spend locked stake because the `_validateWalletPrepayment` check was absent, here any peer can "spend" the chain-selection boost that is supposed to be gated behind committee membership and cryptographic proof, because `validatePerasCert` never performs that gate.

---

### Finding Description

The `BlockSupportsPeras` type class declares `validatePerasCert` as the mandatory gate for accepting inbound Peras certificates:

```haskell
validatePerasCert ::
  PerasCfg blk ->
  PerasCert blk ->
  Either (PerasValidationErr blk) (ValidatedPerasCert blk)
```

The only concrete instance in the codebase is the catch-all default instance: [1](#0-0) 

That instance's body is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

No signature is verified, no committee membership is checked, no round-number bounds are enforced, and no stake threshold is consulted. Every certificate is unconditionally promoted to `ValidatedPerasCert` and assigned the full `perasWeight` boost.

The production inbound path calls this function directly. `processCerts` in the certificate object-pool module filters only for duplicate round numbers and then calls `validateCert` on every new certificate: [2](#0-1) 

Both pool writers — the one backed by `PerasCertDB` and the one backed by `ChainDB` — wire in `validatePerasCert mkPerasParams` as the validator: [3](#0-2) 

A certificate that passes `processCerts` is timestamped and added to the database via `addCert`, after which it participates in chain selection by boosting the weight of `pcCertBoostedBlock`.

The same pattern applies to `validatePerasVote`, which skips all cryptographic signature verification and only checks whether the voter ID appears in the stake distribution map: [4](#0-3) 

---

### Impact Explanation

**High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain.**

A Peras certificate boosts the chain-selection weight of the block it certifies. An attacker who can inject a fake certificate pointing to a block on a minority fork causes honest nodes to assign that fork a higher weight than the honest majority chain, potentially triggering a chain switch. Because `validatePerasCert` never checks committee membership, stake threshold, BLS aggregate signature, or round-number validity, the attacker needs only to know the `PerasRoundNo` and the `Point` of the target block — both of which are public information observable from the chain. No keys, no stake, and no committee seat are required.

---

### Likelihood Explanation

Any peer connected via the Peras certificate mini-protocol can send a crafted `PerasCert`. The network diffusion code (`makePerasCertPoolWriterFromChainDB`) is present and active whenever Peras is enabled. The attack requires only a TCP connection to a node and knowledge of a block point — information freely available from the ChainSync protocol. Likelihood is **high** for any deployment where Peras certificate diffusion is enabled (including private testnets and pre-production environments).

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real one that:

1. Verifies the BLS aggregate signature over `(pcCertRound, pcCertBoostedBlock)` against the public keys of the claimed committee members.
2. Confirms that the set of signers constitutes a valid quorum according to the epoch's stake distribution and the WFALS/EveryoneVotes committee selection scheme.
3. Checks that `pcCertRound` falls within the acceptable window relative to the current chain tip.
4. Rejects certificates whose `pcCertBoostedBlock` does not correspond to a known block on a plausible chain fragment.

Until a real implementation is available, the stub should at minimum return `Left PerasValidationErr` (reject all) rather than `Right` (accept all), so that the absence of validation is fail-closed rather than fail-open. The same applies to `validatePerasVote`.

---

### Proof of Concept

**Attacker-controlled entry path:**

1. Attacker connects to a Peras-enabled node as a peer via the certificate object-diffusion mini-protocol.
2. Attacker observes a block `B_fork` on a minority fork via ChainSync; records its `SlotNo` and `HeaderHash` (32 bytes).
3. Attacker constructs:
   ```haskell
   PerasCert
     { pcCertRound      = currentRound   -- any valid Word64
     , pcCertBoostedBlock = RealPoint slotNo (coerce hash32)
     }
   ```
4. Attacker sends this certificate to the node.
5. `processCerts` deduplicates by round number only; since this round has no prior certificate, it calls `validatePerasCert mkPerasParams cert`.
6. `validatePerasCert` returns `Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }` — no checks performed.
7. The certificate is stored in the `PerasCertDB` / `ChainDB` with the full Peras weight boost applied to `B_fork`.
8. Chain selection now treats `B_fork`'s chain as heavier than the honest chain by `perasWeight`, potentially causing the node to switch to the attacker's fork.

```haskell
processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
```
