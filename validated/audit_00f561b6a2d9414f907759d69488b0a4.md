### Title
Missing Cryptographic Signature Verification in `validatePerasVote` Allows Any Peer to Forge Peras Votes for Arbitrary Voters - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance's `validatePerasVote` implementation checks only that a voter ID exists in the stake distribution, but performs no cryptographic signature verification on the vote itself. This is the instance wired into the production vote-diffusion path via `makePerasVotePoolWriterFromChainDB`. An unprivileged peer can therefore forge valid-looking Peras votes for any registered stake pool, bypassing the Peras voting authorization entirely.

---

### Finding Description

**Root cause — the ineffective check:**

The degenerate `BlockSupportsPeras` instance in `SupportsPeras.hs` defines `validatePerasVote` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [1](#0-0) 

The check `lookupPerasVoteStake vote stakeDistr` only verifies that the `pvVoteVoterId` field of the vote is present in the stake distribution map. It does **not** verify any cryptographic signature proving that the vote was actually produced by the private key corresponding to that voter ID. The function signature and its position in the validation pipeline create the appearance of a full authorization check, but the checked value (voter ID membership) is orthogonal to the actual authorization proof (signature validity).

This is structurally identical to the reported NFT bug: a check that appears to enforce ownership (`_from == msgSender()`) but does not actually use the checked value in the critical operation. Here, the check verifies voter ID membership but the critical authorization — the signature — is never checked.

**Contrast with the correct implementations:**

Both `EveryoneVotes` and `WFALS` committee implementations do perform full signature verification in their `implVerifyVote` functions:

```haskell
-- EveryoneVotes: verifies BLS vote signature
bimap InvalidVoteSignature id $ do
  verifyVoteSignature voterVerificationKey electionId candidate sig
``` [2](#0-1) 

```haskell
-- WFALS: verifies BLS vote signature + VRF eligibility proof
bimap InvalidVoteSignature id $ do
  verifyVoteSignature voterVoteVerificationKey electionId message sig
``` [3](#0-2) 

However, neither of these is wired into the production vote-diffusion path.

**The reachable production code path:**

`makePerasVotePoolWriterFromChainDB` in `PerasVote.hs` is the entry point for all inbound Peras votes received from peers. It explicitly calls the `BlockSupportsPeras` class method `validatePerasVote`:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [4](#0-3) 

This calls the degenerate instance — not `implVerifyVote` from `EveryoneVotes` or `WFALS`. The `processVotes` function then adds all votes that pass this check to the vote pool and forwards them to `ChainDB.addPerasVoteWithAsyncCertHandling`: [5](#0-4) 

**The `validatePerasCert` is equally broken:**

The same degenerate instance unconditionally accepts every certificate without any validation:

```haskell
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [6](#0-5)

### Impact Explanation

**Severity: Critical — Bypass of Peras voting/certificate checks enabling unauthorized vote and certificate acceptance.**

An attacker who knows any registered stake pool's `KeyHash` (which is public on-chain data) can craft a `PerasVote` with that voter ID and any desired `pvVoteRound`/`pvVoteBlock` target. The vote will pass `validatePerasVote` because the voter ID is in the stake distribution. The node will add it to its vote pool and propagate it.

If the attacker can forge enough such votes (one per registered pool, all public information), `votesReachQuorum` will be satisfied and a `ValidatedPerasVotesWithQuorum` will be produced, allowing `forgePerasCert` to be called and a Peras certificate to be embedded in a block. This certificate boosts an attacker-chosen chain, directly manipulating chain selection in a way that bypasses the intended Peras security guarantees.

This matches the allowed impact: **"Bypass of … Peras voting or certificate checks … that enables unauthorized … vote, or certificate acceptance."**

---

### Likelihood Explanation

**High.** The attack requires no privileged access. Stake pool key hashes are public. The attacker only needs to:
1. Know any registered pool's `PerasVoterId` (public ledger data).
2. Send a crafted `PerasVote` message over the peer-to-peer vote diffusion mini-protocol.

No cryptographic material needs to be compromised. The degenerate instance is the only one wired into the production path.

---

### Recommendation

Replace the degenerate `validatePerasVote` implementation with one that actually verifies the cryptographic signature on the vote, mirroring the pattern already implemented in `implVerifyVote` in `EveryoneVotes.hs` and `WFALS.hs`. The `BlockSupportsPeras` class method should either:

1. Delegate to the committee-specific `verifyVote` function (the correct long-term fix), or
2. At minimum, verify the vote signature using the voter's registered verification key before accepting the vote.

Similarly, `validatePerasCert` must not unconditionally return `Right`. The certificate's aggregate BLS signature must be verified against the claimed voters' keys before the certificate is accepted.

The TODO at `https://github.com/tweag/cardano-peras/issues/120` tracks this work, but the incomplete stub is currently deployed in the reachable production code path.

---

### Proof of Concept

1. Observe that `PerasVote` contains only `pvVoteRound`, `pvVoteBlock`, and `pvVoteVoterId` — no signature field in the degenerate instance. [7](#0-6) 

2. Construct a `PerasVote` with `pvVoteVoterId = PerasVoterId <any_registered_pool_keyhash>` and `pvVoteBlock = <target_block_to_boost>`.

3. Send this vote to a node via the Peras vote diffusion mini-protocol. `makePerasVotePoolWriterFromChainDB` will call `validatePerasVote mkPerasParams sd vote`.

4. `lookupPerasVoteStake vote stakeDistr` succeeds (the pool is registered), so `validatePerasVote` returns `Right`. The vote is added to the pool.

5. Repeat for enough registered pools to satisfy `stakeAboveThreshold`. `votesReachQuorum` returns `Just`, `forgePerasCert` is called, and a certificate boosting the attacker's chosen block is produced and embedded in a block — with no private key material ever used by the attacker.
