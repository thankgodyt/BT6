Audit Report

## Title
Unvalidated BTC/Zcash Destination Address Permanently Locks User Tokens in NEAR Bridge - (File: `near/omni-types/src/lib.rs`)

## Summary
`OmniAddress::Btc` and `OmniAddress::Zcash` accept any arbitrary string as an address with no format validation. When a user initiates a NEAR → BTC or NEAR → Zcash transfer with a malformed address, the bridge locks their tokens and records a pending transfer that no trusted relayer can ever successfully submit. No user-callable cancel or refund function exists, resulting in permanent freezing of the bridged funds.

## Finding Description
`UTXOChainAddress` is a plain `String` alias: [1](#0-0) 

The `OmniAddress` enum wraps it without structural constraint: [2](#0-1) 

The `FromStr` implementation for `OmniAddress` accepts any string for both UTXO chain variants — no checksum, prefix, length, or character-set check is applied: [3](#0-2) 

`init_transfer` performs only one guard on the recipient — that the destination chain is not NEAR itself — before proceeding: [4](#0-3) 

`init_transfer_internal` then burns/locks the tokens and inserts the transfer into `pending_transfers`: [5](#0-4) 

The only way to progress a NEAR → UTXO transfer is `submit_transfer_to_utxo_chain_connector`, which is restricted to trusted relayers: [6](#0-5) 

A trusted relayer that attempts to submit a transfer with an invalid address will be rejected by the UTXO connector. The callback re-inserts the transfer into `pending_transfers` on any failure: [7](#0-6) 

In practice, no trusted relayer will attempt to submit a transfer with a clearly invalid address, so the transfer simply remains in `pending_transfers` indefinitely. No user-callable cancel, withdraw, or refund function exists for pending transfers in `near/omni-bridge/src/`. The codebase itself documents this absence of validation in a test comment: [8](#0-7) 

## Impact Explanation
This constitutes **permanent freezing of bridged funds** — a Critical allowed impact. Tokens are removed from circulation on NEAR (burned or locked) and never delivered on the UTXO chain. There is no on-chain mechanism for the user or any unprivileged party to reclaim them. The missing validation is a contract-level failure: the bridge accepts and irrevocably processes an invalid address without rejection, which is distinct from a mere user mistake. The contract has the responsibility to validate addresses before locking funds, and it fails to do so for BTC and Zcash.

## Likelihood Explanation
The attack surface is fully user-controlled and requires no special role or privilege. Any user calling `ft_transfer_call` with a malformed `OmniAddress::Btc` or `OmniAddress::Zcash` recipient triggers the lock. Accidental mistyping (wrong prefix, wrong character set, truncated address, copy-paste error) is a realistic scenario for ordinary users. The absence of any client-side or contract-side validation makes this a high-likelihood event over the lifetime of the bridge.

## Recommendation
Add format validation inside `OmniAddress::from_str` for the `"btc"` and `"zcash"` arms before constructing the variant:
- **BTC**: Enforce Bech32/Bech32m prefix (`bc1`, `tb1`), valid character set, and length bounds per BIP-173 (max 90 chars).
- **Zcash**: Enforce prefix check (`t1`, `t3`, `zs`, `u`) and length bounds per ZIP-316 for Unified Addresses.

Additionally, add a user-callable `cancel_pending_transfer` function that allows the original sender to reclaim tokens from a transfer that has remained in `pending_transfers` beyond a configurable timeout, as a defense-in-depth recovery path.

## Proof of Concept
1. User holds wrapped BTC tokens (`nbtc.bridge.near`) on NEAR.
2. User calls `ft_transfer_call` on `nbtc.bridge.near`:
   ```json
   {
     "receiver_id": "omni-bridge.near",
     "amount": "100000",
     "msg": "{\"InitTransfer\":{\"recipient\":\"btc:NOTAVALIDADDRESS!!!\",\"fee\":\"0\",\"native_token_fee\":\"0\"}}"
   }
   ```
3. `OmniAddress::from_str("btc:NOTAVALIDADDRESS!!!")` succeeds, returning `OmniAddress::Btc("NOTAVALIDADDRESS!!!")`.
4. `init_transfer` passes the only guard (`recipient.get_chain() != ChainKind::Near` → true for `Btc`).
5. `init_transfer_internal` locks 100,000 units and inserts the transfer into `pending_transfers`.
6. No trusted relayer will ever successfully submit this transfer — the UTXO connector rejects `"NOTAVALIDADDRESS!!!"`.
7. The callback re-inserts the transfer on any failed attempt.
8. No `cancel_transfer` or equivalent function exists on-chain.
9. The 100,000 units are permanently frozen in the bridge.

A local integration test can be written following the pattern in `near/omni-tests/src/zcash_stale_transfer_poc.rs`, substituting a clearly malformed address (e.g., `"btc:NOTAVALIDADDRESS!!!"`) and asserting that after `init_transfer` completes, the user's token balance is reduced and no recovery path exists.
