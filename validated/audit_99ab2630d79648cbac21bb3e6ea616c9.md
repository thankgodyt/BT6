### Title
Peras Certificate and Vote Validation Unconditionally Accepts Any Input — Bypass of Certificate/Vote Authorization Checks (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance used for all block types implements `validatePerasCert` as an unconditional `Right` (always valid) and `validatePerasVote` without any cryptographic signature check. An unprivileged peer can submit arbitrarily forged Peras votes and certificates over the node-to-node object diffusion protocol. These pass validation, accumulate in the vote database, and can trigger certificate forging that boosts attacker-chosen blocks in chain selection — bypassing the Peras voting authorization model entirely.

---

### Finding Description

In `Ouroboros/Consensus/Block/SupportsPeras.hs`, a catch-all `instance StandardHash blk => BlockSupportsPeras blk` is defined as the only deployed implementation of the `BlockSupportsPeras` class. Its `validatePerasCert` method unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or structural checks:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

Its `validatePerasVote` method only checks whether the claimed voter ID appears in the stake distribution — it does not verify any cryptographic signature on the vote:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
```

Voter IDs and stake distributions are public on-chain data. Any peer who knows a valid voter ID can craft a `PerasVote` for any block point and have it accepted.

The inbound path in `ObjectPool/PerasVote.hs` calls `validatePerasVote` inside `processVotes`, and on success immediately stores the vote via `addVote`. Once enough forged votes accumulate for a target block, `forgePerasCert` is called and a certificate is produced. That certificate is then submitted to the `ChainDB` via `addPerasVoteWithAsyncCertHandling`, which triggers chain selection with the boosted block weight.

The `validatePerasCert` bypass is the second gate: when a certificate arrives from a peer (or is produced locally from forged votes), `validatePerasCert` is called and always returns `Right`, so the certificate is accepted and stored in the `PerasCertDB` unconditionally.

---

### Impact Explanation

Peras certificates add a configurable weight (`perasWeight`) to the boosted block during chain selection. An attacker who can forge certificates for an arbitrary block can cause honest nodes to prefer a non-canonical chain — the attacker's chosen block gains extra weight that honest blocks do not have, shifting the outcome of `preferAnchoredCandidate`. This is a chain-selection integrity failure reachable from an unprivileged peer position.

This matches the allowed impact: **Critical — Bypass of Peras voting or certificate checks that enables unauthorized certificate acceptance**, and **High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain**.

---

### Likelihood Explanation

The attack requires only:
1. A standard NTN connection to the target node (no keys, no stake, no operator access).
2. Knowledge of any valid voter ID in the current stake distribution (public on-chain data).
3. Sending crafted `PerasVote` objects via the object diffusion mini-protocol.

No cryptographic material is needed. The degenerate instance is the only deployed instance — there is no per-era override for `CardanoBlock` or `HardForkBlock` that would restore proper validation.

---

### Recommendation

1. Remove or gate the universal `instance StandardHash blk => BlockSupportsPeras blk` so it cannot be used for production block types without an explicit, reviewed override.
2. Implement `validatePerasCert` to verify the certificate's cryptographic proof (committee membership, threshold signature, or equivalent) before returning `Right`.
3. Implement `validatePerasVote` to verify the voter's cryptographic signature over the vote content, not merely the presence of the voter ID in the stake distribution.
4. Until proper validation is implemented, disable the inbound Peras vote/certificate diffusion path for production nodes, or reject all inbound votes/certificates at the protocol handler level.

---

### Proof of Concept

**Entry path:**

1. Attacker connects to a production node via NTN.
2. Attacker reads the current stake distribution (public) and picks any `PerasVoterId` with nonzero stake.
3. Attacker constructs `PerasVote { pvVoteRound = r, pvVoteBlock = attackerChosenPoint, pvVoteVoterId = knownVoterId }` for a target block of their choice.
4. Attacker sends enough such votes (one per known voter ID) to reach the quorum threshold.

**Validation path (no rejection):**

`processVotes` calls `validatePerasVote mkPerasParams sd vote`. The degenerate instance checks only `lookupPerasVoteStake vote stakeDistr` — the voter ID is in the distribution, so `Right ValidatedPerasVote{...}` is returned. No signature is checked. [1](#0-0) 

**Certificate forging:**

Once quorum is reached, `forgePerasCert` is called. The degenerate instance always returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }`. [2](#0-1) 

**Certificate acceptance:**

When the certificate arrives at another node, `validatePerasCert` is called and unconditionally returns `Right`, so the certificate is stored and used to boost the attacker's chosen block in chain selection. [2](#0-1) 

**Chain selection effect:**

The boosted block gains `perasWeight` extra weight. `preferAnchoredCandidate` uses this weight when comparing candidate chains, potentially causing the node to switch to the attacker's chosen chain.

```haskell
processVotes ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
```
