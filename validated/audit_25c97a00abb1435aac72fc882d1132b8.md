### Title
Deposit Fee Bypass via Safe-Deposit Path — (File: `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

### Summary
The `safe_verify_deposit` code path mints the **full** BTC deposit amount as nBTC without deducting the configured `deposit_bridge_fee`, while the standard `verify_deposit` path explicitly deducts that fee. Any user who routes a deposit through the safe-deposit path avoids paying the bridge fee entirely.

### Finding Description
In `internal_verify_deposit` (the standard path), the fee is computed and subtracted before the mint amount is forwarded to the callback:

```rust
// contracts/satoshi-bridge/src/btc_light_client/deposit.rs  lines 52-56
let deposit_fee = config.deposit_bridge_fee.get_fee(deposit_amount);
let mint_amount = deposit_amount - deposit_fee;
let (protocol_fee, relayer_fee) = config
    .deposit_bridge_fee
    .get_protocol_and_relayer_fee(deposit_fee);
```

`verify_deposit_callback` then receives `mint_amount` (fee-reduced) together with non-zero `protocol_fee` and `relayer_fee`, which are tracked in `acc_collected_protocol_fee` / `cur_available_protocol_fee` inside `mint_callback`.

In `internal_safe_verify_deposit` (the safe path), **no fee is computed or subtracted**. The raw `deposit_amount` is forwarded directly:

```rust
// contracts/satoshi-bridge/src/btc_light_client/deposit.rs  lines 104-113
promise.then(
    Self::ext(env::current_account_id())
        .with_static_gas(GAS_FOR_VERIFY_DEPOSIT_CALL_BACK)
        .verify_safe_deposit_callback(
            recipient_id,
            deposit_amount.into(),   // ← full amount, no fee deducted
            deposit_msg.msg,
            pending_utxo_info,
        ),
)
```

`verify_safe_deposit_callback` calls `safe_mint` with that full amount, and `safe_mint_callback` emits the event with `protocol_fee: U128(0)` and `relayer_fee: U128(0)`:

```rust
// contracts/satoshi-bridge/src/btc_light_client/deposit.rs  lines 458-466
Event::VerifyDepositDetails {
    recipient_id: &recipient_id,
    mint_amount,
    protocol_fee: U128(0),
    relayer_account_id: env::signer_account_id(),
    relayer_fee: U128(0),
    success: is_success,
}
.emit();
```

No fee accounting (`acc_collected_protocol_fee`, `cur_available_protocol_fee`) is updated in this path. The bridge fee configured in `deposit_bridge_fee` is silently skipped.

### Impact Explanation
Every satoshi of `deposit_bridge_fee` is bypassed for safe-deposit transactions. A user depositing a large amount (e.g., 1 BTC) through the safe path receives the full 1 BTC worth of nBTC instead of `1 BTC − fee`. The bridge accrues zero protocol or relayer revenue for those deposits. This is a bypass of the bridge's fee policy — a Medium impact per the allowed scope.

### Likelihood Explanation
The safe-deposit entry point (`safe_verify_deposit` / `internal_safe_verify_deposit_entry`) is a public, permissionless function gated only by an attached NEAR storage deposit. Any user or integrator who learns of the path can exploit it. The fee savings on a large BTC deposit far exceed the small NEAR storage cost, making exploitation economically rational.

### Recommendation
Apply the same fee-deduction logic inside `internal_safe_verify_deposit` that exists in `internal_verify_deposit`. Compute `deposit_fee`, subtract it from `deposit_amount` to obtain `mint_amount`, split into `protocol_fee` / `relayer_fee`, and pass all four values to `verify_safe_deposit_callback` so they are tracked and emitted correctly — mirroring the standard deposit path.

### Proof of Concept
1. Attacker identifies a BTC deposit address derived from a `DepositMsg` that includes a `safe_deposit` field.
2. Attacker sends, e.g., 1 BTC to that address and waits for confirmations.
3. Attacker calls `safe_verify_deposit` with the transaction bytes and Merkle proof, attaching the required NEAR storage deposit.
4. `internal_safe_verify_deposit_entry` → `internal_safe_verify_deposit` → `verify_safe_deposit_callback` → `safe_mint` executes with `mint_amount = 100_000_000` satoshis (full 1 BTC).
5. The attacker (or the downstream contract specified in `msg`) receives 100 000 000 nBTC.
6. Had the standard path been used with, e.g., a 0.1 % fee (`fee_rate = 10`), the attacker would have received only 99 900 000 nBTC. The 100 000 nBTC fee is never collected. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
