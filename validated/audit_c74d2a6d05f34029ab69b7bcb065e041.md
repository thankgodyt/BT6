### Title
Hardcoded Mainnet-Specific `HistoricityCutoff` in `mkGenesisConfig` Bypasses Genesis Historicity Check on Non-Mainnet Networks — (File: `ouroboros-consensus-diffusion/src/ouroboros-consensus-diffusion/Ouroboros/Consensus/Node/Genesis.hs`)

---

### Summary

`mkGenesisConfig` hardcodes the `HistoricityCutoff` using Cardano mainnet-specific constants (`k = 2160`, `f = 0.05`) rather than deriving it from the actual chain configuration. On any network whose stability window is shorter than the hardcoded 37-hour value — including private testnets and any future network with different protocol parameters — an unprivileged peer can send `MsgRollBackward` or `MsgAwaitReply` ChainSync messages whose candidate-chain tip is older than the real stability window yet younger than the hardcoded cutoff. The historicity check silently passes, the adversarial peer is never disconnected, and the Genesis chain-selection security guarantee is materially weakened.

---

### Finding Description

In `mkGenesisConfig`, when Genesis is enabled, the historicity cutoff is set unconditionally to a literal arithmetic expression:

```haskell
-- Duration in seconds of one Cardano mainnet Shelley stability window
-- (3k/f slots times one second per slot) plus one extra hour as a safety margin.
gcHistoricityCutoff = Just $ HistoricityCutoff $ 3 * 2160 * 20 + 3600
``` [1](#0-0) 

The three embedded constants encode mainnet-only assumptions:

| Literal | Meaning | Source |
|---|---|---|
| `2160` | security parameter `k` | Cardano mainnet |
| `20` | `1/f` where `f = 0.05` | Cardano mainnet active-slot coefficient |
| `3600` | 1-hour safety margin | design choice |

The product `3 × 2160 × 20 = 129 600 s = 36 h` is the Shelley stability window (`3k/f` slots × 1 s/slot) on mainnet. The total cutoff is therefore **133 200 s ≈ 37 hours**.

This value is never read from `TopLevelConfig`, `ConsensusConfig`, or any genesis file. The function signature accepts only `Maybe GenesisConfigFlags` — no chain-parameter input at all:

```haskell
mkGenesisConfig :: Maybe GenesisConfigFlags -> GenesisConfig
``` [2](#0-1) 

The cutoff is consumed by `mkCheck` in `HistoricityCheck.hs`, which rejects a peer only when `historicityCutoff < actualRollbackAge`:

```haskell
pure $
  when (historicityCutoff < actualRollbackAge) $
    throwError HistoricityException { … }
``` [3](#0-2) 

The module's own documentation states the cutoff "should be set to at least the maximum duration (across all eras) of a stability window": [4](#0-3) 

On a network where the actual stability window is, say, 600 s (k=100, f=0.5), the hardcoded 133 200 s cutoff is **222× too large**. The check `133200 < 1000` evaluates to `False`, so the peer is never flagged.

The same function also hardcodes the ChainSync Jumping jump size with the same mainnet `k`:

```haskell
defaultCSJJumpSize = 2 * 2160 -- Byron forecast range
``` [5](#0-4) 

---

### Impact Explanation

The `HistoricityCutoff` is the sole mechanism that disconnects a peer whose candidate chain is provably stale — i.e., older than one stability window. When the cutoff is too large, the Genesis Density Disconnector (GDD) and Limit on Eagerness (LoE) lose their ability to make progress: the LoE anchor cannot advance past the intersection with the adversarial peer's stale fragment, and the GDD cannot disconnect that peer because the historicity check never fires. A syncing node can therefore be held at a stale chain-selection point indefinitely by a single adversarial peer, allowing that peer to present a denser-looking adversarial chain within the genesis window and cause the node to prefer a non-canonical chain. This directly undermines the Genesis chain-selection security guarantee described in the design document.

**Impact class**: High — chain-selection / Genesis bug that lets an unprivileged peer make an honest syncing node prefer a non-canonical or less-secure chain beyond the intended security assumptions.

---

### Likelihood Explanation

`enableGenesisConfigDefault` (which calls `mkGenesisConfig (Just defaultGenesisConfigFlags)`) is the standard entry point used by `stdLowLevelRunNodeArgsIO` for any node that opts into Genesis. Any private testnet or future network with `k ≠ 2160` or `f ≠ 0.05` is immediately affected. The attacker needs only to be a connected ChainSync peer — no keys, no stake, no special privileges. [6](#0-5) 

---

### Recommendation

Pass the actual chain parameters (`SecurityParam k`, active-slot coefficient `f`, and slot length) into `mkGenesisConfig` (or derive them from `TopLevelConfig`) and compute the cutoff dynamically:

```haskell
-- Correct derivation
historicityCutoff = HistoricityCutoff $
    fromIntegral (3 * unNonZero (maxRollbacks k)) / f * slotLengthToSec slotLen
    + 3600  -- safety margin
```

This mirrors the recommendation in the external report: replace hardcoded environment-specific constants with a governance/configuration function that reads the actual deployment parameters.

---

### Proof of Concept

1. Start a private testnet with `k = 100`, `f = 0.5` (stability window = `3 × 100 / 0.5 = 600` slots = 600 s).
2. Enable Genesis on the victim node via `enableGenesisConfigDefault`; the node receives `gcHistoricityCutoff = 133 200 s`.
3. The adversarial peer connects via ChainSync and serves a candidate chain whose tip slot corresponds to a time **700 s ago** (older than the real 600 s stability window, but far younger than 133 200 s).
4. The peer sends `MsgAwaitReply` at that tip.
5. `judgeMessageHistoricity` in `mkCheck` evaluates `133200 < 700` → `False`; no `HistoricityException` is thrown; the peer is not disconnected.
6. The LoE anchor remains pinned at the intersection with the adversarial fragment; the GDD cannot fire; the syncing node cannot advance its immutable tip past that point.
7. The adversary can now serve a denser adversarial chain in the genesis window, causing the victim to select it over the honest chain. [7](#0-6) [8](#0-7)
