Audit Report

## Title
Transfer Permanently Frozen When `normalize_amount(amount - fee) == 0` Due to Missing Pre-validation — (`near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer` accepts outbound transfers without verifying that `normalize_amount(amount - fee) > 0` for the destination chain's decimal precision. When `sign_transfer` is later called, it computes this normalization and panics if the result is zero. Because the transfer remains in `pending_transfers` with no user-accessible cancel or refund path, the locked tokens are permanently frozen.

## Finding Description
**Root cause — `init_transfer` only validates `fee < amount`:**

At [1](#0-0)  the only amount constraint is `fee < amount`. No normalization check is performed. Tokens are immediately locked when `ft_on_transfer` returns `U128(0)`.

**`normalize_amount` uses floor division:**

At [2](#0-1)  the function computes `amount / 10^(origin_decimals - dest_decimals)`. For a token with `origin_decimals = 18` and `dest_decimals = 6`, any `amount - fee < 10^12` produces 0.

**`sign_transfer` panics unconditionally for such transfers:**

At [3](#0-2)  `sign_transfer` computes `normalize_amount(amount_without_fee())` and requires the result to be `> 0`. Every call for this transfer reverts. The transfer stays in `pending_transfers` indefinitely.

**`amount_without_fee` is a simple subtraction:**

At [4](#0-3)  there is no normalization awareness.

**No cancel path exists for the user.** `sign_transfer_callback` at [5](#0-4)  only removes the transfer message after a *successful* signing when `fee.is_zero()`. A transfer that always panics at the normalization check is never removed. The code comment at [6](#0-5)  acknowledges dust being locked/burned but only addresses sub-unit remainders, not the case where the entire net amount normalizes to zero.

## Impact Explanation
A user's tokens are permanently locked in the bridge with no recovery mechanism. This is concrete **permanent freezing of bridged funds** — a Critical impact under the allowed scope. The bridge's `pending_transfers` retains the entry forever, and the locked NEP-141 tokens cannot be recovered by the user, the relayer, or any non-admin path.

## Likelihood Explanation
Any unprivileged user can trigger this via `ft_transfer_call` with an `InitTransferMsg` whose `amount - fee` is below the normalization threshold. For 18→6 decimal tokens (common ERC-20 bridging scenario), the threshold is `10^12` base units. No special privileges, coordination, or victim mistakes are required. The condition is reachable through normal bridge usage with small transfer amounts.

## Recommendation
Add a normalization check inside `init_transfer_internal` (or immediately after the `fee < amount` check) before accepting the transfer and locking tokens:

```rust
let token_address = self.get_token_address(
    transfer_message.get_destination_chain(),
    self.get_token_id(&transfer_message.token),
).near_expect(BridgeError::FailedToGetTokenAddress);

let decimals = self.token_decimals
    .get(&token_address)
    .near_expect(BridgeError::TokenDecimalsNotFound);

let normalized = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

This mirrors the existing check in `sign_transfer` and ensures rejection at initiation time with a full token refund rather than silent acceptance and permanent freezing.

## Proof of Concept
1. Register a token with `origin_decimals = 18`, `decimals = 6` (diff = 12).
2. Call `ft_transfer_call` with `amount = 999_999_999_999` (i.e., `10^12 - 1`) and `fee = 0`.
3. `init_transfer` accepts: `0 < 999_999_999_999` passes. Tokens are locked.
4. Relayer calls `sign_transfer` for this transfer ID.
5. `normalize_amount(999_999_999_999, {origin:18, dest:6}) = 999_999_999_999 / 10^12 = 0`.
6. `require!(0 > 0, BridgeError::InvalidAmountToTransfer)` panics → transaction reverts.
7. Transfer remains in `pending_transfers`. Tokens remain locked. No user-accessible cancel path exists.
8. Attempting to set a lower fee is rejected with `ERR_INVALID_FEE` (confirmed by integration test at `near/omni-tests/src/init_transfer.rs` L859-892). Increasing the fee worsens the situation. Funds are permanently frozen.
