### Title
Unrestricted `request_refund` Allows Any Caller to Redirect BTC Refunds to an Attacker-Controlled Address - (File: contracts/satoshi-bridge/src/api/bridge.rs)

---

### Summary

`request_refund` in `contracts/satoshi-bridge/src/api/bridge.rs` carries no authentication check. Any unprivileged NEAR account can submit a refund request for any BTC deposit UTXO and supply an arbitrary `refund_address`. Because only one refund request may exist per UTXO, an attacker can front-run a legitimate request, block the real depositor, and—if the DAO/Operator does not reject the request within `unsafe_refund_timelock_sec`—redirect the deposited BTC to themselves via the equally-unrestricted `execute_refund`.

---

### Finding Description

`request_refund` (bridge.rs lines 510–535) is a fully public `#[payable]` function. Its only conditional auth check is for the optional `gas_fee` parameter; the core refund-request creation path is open to any caller: [1](#0-0) 

Inside `internal_request_refund` (refund.rs lines 137–184), the only guard on `refund_address` is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(msg_refund_address == &refund_address, ...);
}
``` [2](#0-1) 

When `deposit_msg.refund_address` is `None`—the standard case for ordinary deposits—the caller may supply **any** BTC address as `refund_address`. There is no check that the caller equals `deposit_msg.recipient_id` or any other authorized party.

The callback enforces that the output script matches the deposit address derived from `deposit_msg`, but it does **not** validate who is calling or where the refund should go: [3](#0-2) 

A duplicate-request guard then prevents a second request for the same UTXO: [4](#0-3) 

`execute_refund` is also fully public with no ownership check: [5](#0-4) 

When `deposit_msg.refund_address` is `None`, `resolve_execute_refund_timelock` applies `unsafe_refund_timelock_sec` (the longer timelock) and then allows **any** caller to proceed: [6](#0-5) 

The `refund_address` stored in the request is used verbatim to build the refund output and send BTC: [7](#0-6) 

---

### Impact Explanation

**Medium (certain):** An attacker front-runs the legitimate depositor's `request_refund` call. The duplicate-request guard then causes the depositor's call to revert with "Refund request already exists for this UTXO." The depositor cannot reclaim their BTC until the DAO/Operator actively rejects the attacker's request—an indefinite, operator-dependent delay.

**Critical (conditional):** If the DAO/Operator does not reject the attacker's request before `unsafe_refund_timelock_sec` elapses, the attacker calls `execute_refund`, and the bridge's MPC pipeline constructs and broadcasts a Bitcoin transaction paying the attacker's `refund_address`. The depositor's BTC is permanently lost.

---

### Likelihood Explanation

All inputs needed to mount the attack are publicly observable:

- `deposit_msg` is emitted in a `LogDepositAddress` event whenever `get_user_deposit_address` is called. [8](#0-7) 
- `tx_bytes`, `vout`, and the Merkle proof are derivable from the public Bitcoin blockchain.
- The only cost to the attacker is the `required_balance_for_request_refund()` storage deposit, which is a small, fixed NEAR amount.

The blocking impact (Medium) is unconditional. The theft impact (Critical) requires the DAO/Operator monitoring to fail for the duration of `unsafe_refund_timelock_sec`, which is a realistic failure mode during incidents, holidays, or monitoring outages.

---

### Recommendation

Introduce a caller whitelist analogous to the fix recommended for `vestFor`. Concretely:

1. **Restrict the caller** to `deposit_msg.recipient_id` or a whitelisted relayer account (e.g., the same `trusted_relayer` whitelist already used for deposit verification). Add a `require!(caller == deposit_msg.recipient_id || is_whitelisted_relayer(&caller), ...)` guard at the top of `request_refund`.
2. **Alternatively**, require `deposit_msg.refund_address` to always be set (non-`None`) so the refund destination is fixed at deposit time and cannot be overridden by an arbitrary caller.

---

### Proof of Concept

1. Alice sends BTC to the deposit address for `deposit_msg = { recipient_id: "alice.near", refund_address: None, … }`.
2. Alice (or the dApp) calls `get_user_deposit_address(deposit_msg)`, emitting a `LogDepositAddress` event that reveals `deposit_msg` publicly.
3. The deposit is never finalized (e.g., the relayer is down), so Alice intends to call `request_refund`.
4. **Attacker** observes the event and the on-chain BTC transaction, then calls:
   ```
   request_refund(
     deposit_msg,
     "attacker_btc_address",   // attacker-controlled refund destination
     tx_bytes, vout, proof,
     None
   )
   ```
   with the required storage deposit attached.
5. `request_refund_callback` succeeds: the output script matches the deposit address, no duplicate exists yet. A `RefundRequest` with `refund_address = "attacker_btc_address"` is stored.
6. Alice calls `request_refund` — it reverts: "Refund request already exists for this UTXO."
7. `unsafe_refund_timelock_sec` elapses without DAO/Operator intervention.
8. Attacker calls `execute_refund(utxo_storage_key, None)`. The bridge builds a Bitcoin transaction paying `"attacker_btc_address"` and submits it to the MPC signer.
9. Alice's BTC is sent to the attacker. Alice has no recourse.

            refund_address,

        )
    }
