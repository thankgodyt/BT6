Audit Report

## Title
Precision Loss in `normalize_amount` Permanently Freezes Small-Amount NEAR-Outbound Transfers — (File: `near/omni-bridge/src/lib.rs`)

## Summary
The `normalize_amount` function uses integer floor division to scale token amounts from NEAR's higher-precision representation to a lower-precision destination chain representation. When a user initiates a transfer with an amount below `10^(origin_decimals - decimals)`, the normalized value truncates to zero, causing every subsequent `sign_transfer` call to panic with `InvalidAmountToTransfer`. No cancel or refund path exists for NEP-141 tokens locked in this state, resulting in permanent freezing of the user's bridged principal.

## Finding Description
`normalize_amount` is defined as pure floor division:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

This is called inside `sign_transfer` **after** tokens have already been locked by `ft_transfer_call → ft_on_transfer`:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

The `ft_on_transfer` entry point stores the `TransferMessage` and accepts all tokens (returning 0 unused) without pre-computing `normalize_amount`. The zero-check only occurs in `sign_transfer`, which is gated by `#[trusted_relayer]` — meaning the user cannot even call it themselves. The only `refund` helper in the contract transfers `NearToken` (native NEAR), not NEP-141 tokens. There is no public cancel, withdraw, or recovery function for a stuck `TransferMessage`.

## Impact Explanation
This is a concrete instance of **permanent freezing of bridged funds** — a Critical impact in scope. The user's NEP-141 tokens are locked in the bridge contract, the associated `TransferId` will always revert on `sign_transfer`, and no on-chain recovery path exists. The entire transfer principal (not just dust) is irrecoverable when the amount is below the normalization threshold.

## Likelihood Explanation
Any token pair where `origin_decimals > decimals` is affected (e.g., NEAR-native 24-decimal tokens bridged to 6-decimal EVM tokens, `diff_decimals = 18`; or 24→18, `diff_decimals = 6`). No special privileges are required — any unprivileged user calling `ft_transfer_call` with an amount below `10^diff_decimals` triggers the bug. The EVM `initTransfer` only enforces `fee < amount` with no minimum floor, so the same class of issue applies to EVM-outbound flows using bridge tokens. The condition is easy to hit accidentally for users thinking in human-readable token units rather than raw on-chain units.

## Recommendation
Add a pre-normalization check at the `ft_on_transfer` / `init_transfer` entry point: compute `normalize_amount` on the incoming amount (minus fee) before storing the `TransferMessage` or locking/burning tokens, and reject (return the full amount to the sender) if the result is zero. This ensures no tokens are committed to a state from which they cannot be recovered.

## Proof of Concept
1. Register a token with `origin_decimals = 24`, `decimals = 18` (`diff_decimals = 6`).
2. Call `ft_transfer_call` on the NEAR token contract with `amount = 999_999`, targeting the bridge with a valid `InitTransferMsg`.
3. Bridge's `ft_on_transfer` stores the `TransferMessage` and returns `0` (tokens locked).
4. Trusted relayer calls `sign_transfer` for the resulting `TransferId`.
5. `normalize_amount(999_999, {origin_decimals: 24, decimals: 18})` → `999_999 / 1_000_000 = 0`.
6. `require!(amount_to_transfer > 0)` panics with `InvalidAmountToTransfer`.
7. Repeat step 4 indefinitely — result is always the same panic.
8. The `999_999` yocto-units are permanently locked with no on-chain recovery path.
