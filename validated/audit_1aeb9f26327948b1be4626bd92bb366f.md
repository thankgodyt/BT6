Audit Report

## Title
Fee-on-Transfer Token Balance Mismatch Causes Permanent Fund Freezing in `initTransfer` - (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

## Summary
`initTransfer` in `OmniBridge.sol` transfers the caller-supplied `amount` via `safeTransferFrom` without performing a balance-before/balance-after check, then emits `InitTransfer` recording the full `amount`. For fee-on-transfer ERC20 tokens the contract receives `amount - fee` while the NEAR side mints the full `amount`. Every subsequent `finTransfer` attempting to release `amount` will revert due to insufficient balance, permanently freezing the deposited tokens in the EVM escrow with no on-chain recovery path.

## Finding Description
In `initTransfer`, the `else` branch for native ERC20 tokens (not bridge tokens, not custom minters) executes:

```solidity
IERC20(tokenAddress).safeTransferFrom(
    msg.sender,
    address(this),
    amount
);
```

No balance snapshot is taken before or after this call. The function then emits:

```solidity
emit BridgeTypes.InitTransfer(
    msg.sender, tokenAddress, currentOriginNonce,
    amount, fee, nativeFee, recipient, message
);
```

For a fee-on-transfer token the contract receives `amount - transfer_fee` while the event records `amount`. The NEAR relayer reads this event and mints the full `amount` to the recipient on NEAR.

When the reverse leg executes, `finTransfer` attempts:

```solidity
IERC20(payload.tokenAddress).safeTransfer(
    payload.recipient,
    payload.amount   // full `amount`, but contract only holds `amount - transfer_fee`
);
```

`safeTransfer` reverts every time because the contract's balance for that token is permanently `transfer_fee` short. Although the Solidity transaction reverts atomically (so `completedTransfers[nonce]` is not permanently consumed on a single failed call), the underlying shortfall is structural and irrecoverable: no amount of retries can succeed, and there is no admin `rescueTokens` or equivalent function in `OmniBridge.sol` to drain or redistribute the stuck tokens. The `amount - transfer_fee` tokens are permanently locked in the contract.

The same pattern exists in `starknet/src/omni_bridge.cairo` `init_transfer` / `fin_transfer`.

## Impact Explanation
This constitutes permanent freezing of bridged funds and escrow mis-accounting, both within the critical impact scope. The EVM escrow permanently holds less than the sum of all `InitTransfer` amounts for the affected token. Every `finTransfer` for that token reverts indefinitely. The NEAR-side tokens already minted to recipients are unbacked relative to the EVM escrow, creating an irrecoverable accounting divergence. There is no admin recovery function in the contract.

## Likelihood Explanation
Fee-on-transfer ERC20 tokens are a well-established token class. The `else` branch in `initTransfer` is reached for any ERC20 token that is not registered as a bridge token or custom minter — there is no allowlist, no token-type check, and no balance verification. A single unprivileged user bridging such a token triggers the irreversible accounting divergence. No privileged access is required; the entry point is fully public.

## Recommendation
Apply a balance-before/balance-after pattern and revert if the received amount differs from the declared amount:

```solidity
uint256 balanceBefore = IERC20(tokenAddress).balanceOf(address(this));
IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
uint256 received = IERC20(tokenAddress).balanceOf(address(this)) - balanceBefore;
require(received == amount, "FeeOnTransferNotSupported");
```

Alternatively, maintain an explicit token allowlist and reject any token not on it before reaching the `safeTransferFrom` call. Apply the equivalent fix to `starknet/src/omni_bridge.cairo` `init_transfer`.

## Proof of Concept
1. Deploy or identify a fee-on-transfer ERC20 token `T` (e.g., 5% fee on every transfer) that is not registered as a bridge token or custom minter in `OmniBridge`.
2. Call `OmniBridge.initTransfer(T, 1000, 0, 0, "near:alice.near", "")`.
   - `safeTransferFrom` moves 1000 from caller; contract receives 950.
   - `InitTransfer` event emits `amount = 1000`.
3. NEAR relayer submits the proof; NEAR bridge mints 1000 NEAR-side tokens to `alice.near`.
4. Alice bridges back: NEAR burns 1000 tokens, MPC signs a payload with `amount = 1000`.
5. Relayer calls `OmniBridge.finTransfer(sig, payload)` on EVM.
   - `safeTransfer(alice_evm, 1000)` reverts — contract only holds 950.
6. The transaction reverts atomically, but the structural shortfall is permanent: every future `finTransfer` call for this payload will also revert. The 950 EVM tokens are permanently locked in `OmniBridge` with no withdrawal path, and the 1000 NEAR-side tokens are already minted and unbacked.
