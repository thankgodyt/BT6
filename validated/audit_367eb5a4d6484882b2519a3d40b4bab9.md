### Title
Unpermissioned `sign_btc_transaction` Allows Any Caller to Inject Wrong `key_version`, Corrupting MPC Signing and Temporarily Locking Withdrawal Funds — (File: `contracts/satoshi-bridge/src/api/chain_signatures.rs`)

---

### Summary

The public `sign_btc_transaction` function in the `satoshi-bridge` contract carries no caller restriction. Any NEAR account can invoke it against any pending withdrawal, supplying an attacker-chosen `key_version`. The MPC service signs the PSBT input with the wrong key, the resulting (invalid) signature is stored in the pending-info slot, and the "Already signed" guard permanently blocks legitimate re-signing of that input. The withdrawal transaction is therefore unbroadcastable on Bitcoin, and the user's funds remain locked until a privileged operator cancels the withdrawal.

---

### Finding Description

`sign_btc_transaction` is declared in a plain `#[near] impl Contract` block with only a `#[pause]` decorator: [1](#0-0) 

The `#[pause]` macro only allows the DAO to pause the contract; it does **not** restrict which account may call the function. There is no `#[trusted_relayer]`, no `#[access_control_any]`, and no manual `env::predecessor_account_id()` check. Compare this with every sensitive bridge entry-point in `bridge.rs`, which carries either `#[trusted_relayer]` or `#[access_control_any(roles(...))]`: [2](#0-1) 

Inside `internal_sign_btc_transaction`, the attacker-supplied `key_version` is forwarded verbatim to the MPC service: [3](#0-2) 

The callback then stores whatever signature the MPC service returns and marks the slot as occupied: [4](#0-3) 

A subsequent legitimate call to sign the same `sign_index` hits the guard: [5](#0-4) 

and is rejected with "Already signed", even though the stored signature is cryptographically invalid for the UTXO's actual controlling key.

---

### Impact Explanation

A withdrawal whose PSBT input has been signed with the wrong MPC key produces a Bitcoin transaction that is permanently invalid. The bridge's `verify_withdraw` / `verify_withdraw_v2` path will never succeed because the transaction cannot be confirmed on Bitcoin. The user's nBTC remains locked in the bridge's pending state until a DAO/Operator calls `cancel_withdraw` to unwind the withdrawal and return the tokens. This matches the **Medium** allowed impact: *attacker-triggered temporary locking of bridged funds*.

---

### Likelihood Explanation

All `btc_pending_sign_id` values are emitted as on-chain events (`Event::SignedBtcTransaction`, `Event::BtcInputSignature`) and are therefore publicly observable. Any NEAR account can monitor the chain, detect a new pending withdrawal, and immediately race to call `sign_btc_transaction` with a wrong `key_version` (e.g., `key_version = 999`). No special privilege, leaked key, or off-chain coordination is required. The attack is cheap (only gas cost) and repeatable against every new withdrawal.

---

### Recommendation

Add a caller restriction to `sign_btc_transaction` so that only the account that initiated the withdrawal (stored in `btc_pending_info.account_id`) or a trusted relayer may trigger signing:

```rust
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn sign_btc_transaction(
    &mut self,
    btc_pending_sign_id: String,
    sign_index: usize,
    key_version: u32,
) -> PromiseOrValue<bool> {
    let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
    // Restrict to the withdrawal owner or a trusted relayer
    let caller = env::predecessor_account_id();
    require!(
        caller == btc_pending_info.account_id
            || self.acl_has_role(Role::Relayer.into(), caller.clone())
            || self.acl_has_role(Role::DAO.into(), caller),
        "Unauthorized: only the withdrawal owner or a trusted relayer may sign"
    );
    ...
}
```

Additionally, validate `key_version` against the value stored in the contract configuration to prevent mismatched-key signatures from being accepted.

---

### Proof of Concept

1. Alice calls `ft_transfer_call` on the nBTC contract with a `WithdrawMsg`, creating a pending withdrawal. The bridge emits an event containing `btc_pending_sign_id = "abc123"` and `sign_index = 0`.

2. Attacker Bob observes the event and immediately calls:
   ```
   sign_btc_transaction(
       btc_pending_sign_id = "abc123",
       sign_index = 0,
       key_version = 9999          // wrong version
   )
   ```

3. The MPC service signs the PSBT hash with key version 9999 (a key that does not control the UTXO). The callback stores the resulting signature in `btc_pending_info.signatures[0]`.

4. The legitimate relayer (or Alice) attempts to call `sign_btc_transaction` with the correct `key_version`. The call reverts with "Already signed".

5. The signed Bitcoin transaction is broadcast but is rejected by the Bitcoin network because the signature does not correspond to the UTXO's controlling public key.

6. Alice's nBTC remains locked. A DAO/Operator must call `cancel_withdraw` to recover the funds, requiring privileged operator intervention. [6](#0-5) [7](#0-6)

    pub fn internal_sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> Promise {
        let pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);

        let public_keys: Vec<_> = pending_info
            .vutxos
            .iter()
            .map(|vutxo| self.generate_btc_public_key(&vutxo.get_path()))
            .collect();

        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        require!(
            btc_pending_info.signatures[sign_index].is_none(),
            "Already signed"
        );
        let payload = btc_pending_info
            .get_psbt()
            .get_hash_to_sign(sign_index, &public_keys);
        let path = btc_pending_info.vutxos[sign_index].get_path();
        self.sign_promise(SignRequest {
            payload,
            path,
            key_version,
        })
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_SIGN_BTC_TRANSACTION_CALL_BACK)
                .sign_btc_transaction_callback(
                    btc_pending_info.account_id.clone(),
                    btc_pending_sign_id,
                    sign_index,
                ),
        )
    }
