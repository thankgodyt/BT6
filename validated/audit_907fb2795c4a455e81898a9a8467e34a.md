Audit Report

## Title
Dust transfers normalizing to zero are permanently locked with no recovery path — (`near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer_internal` burns or locks user tokens and stores the transfer in `pending_transfers` without verifying that the post-normalization amount is non-zero. When a user bridges an amount whose normalized value rounds to zero under integer division, `sign_transfer` permanently reverts with `InvalidAmountToTransfer` for that transfer ID, and no user-accessible path exists to cancel or recover the funds.

## Finding Description
`normalize_amount` uses integer floor division:

```rust
// L2784-2786
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

For a token with `origin_decimals = 18` and `decimals = 6`, any `amount < 10^12` produces `0`.

`sign_transfer` (L475–485) normalizes the stored amount and enforces a non-zero guard:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

The existence of this guard proves the protocol knows `normalize_amount` can return `0`. However, `init_transfer` (L523–618) and `init_transfer_internal` (L1829–1865) perform no equivalent check. `init_transfer_internal` unconditionally:
1. Inserts the transfer into `pending_transfers` via `add_transfer_message` (L1835)
2. Calls `burn_tokens_if_needed` (L1851) — permanently destroying deployed tokens
3. Calls `lock_tokens_if_needed` (L1853) — locking native tokens
4. Returns `U128(0)` so `ft_on_transfer` refunds nothing to the caller

Once stored, the only removal paths are `remove_transfer_message` (called inside `claim_fee_callback`, which is only reachable after a successful `sign_transfer` MPC signing round) and `remove_transfer_message_without_refund` (called only on storage-balance failure at L1846 or non-Near token at L1859). Neither is reachable when `sign_transfer` always reverts at the `require!(amount_to_transfer > 0, ...)` guard. There is no `cancel_transfer` or user-accessible refund function.

The inline comment on `normalize_amount` (L2781–2783) acknowledges dust behavior: *"When fee = 0, dust stays locked/burned."* This refers to the fractional remainder after normalization (e.g., 1_000_001 units → 1 unit transferred, 1 unit dust). The zero-normalization case is qualitatively different: the **entire** transferred amount is lost and nothing reaches the destination chain, yet the transfer record is permanently stuck.

## Impact Explanation
This matches the critical allowed impact class of **permanent freezing/loss of bridged funds** and **decimal/normalization abuse that changes user or protocol balances**:

- **Deployed (bridged) tokens**: `burn_tokens_if_needed` permanently destroys the tokens. Even DAO intervention cannot restore burned supply.
- **Native NEAR tokens**: tokens are held by the bridge contract. Only a DAO call to `transfer_token_as_dao` (a privileged function) could rescue them — no user-accessible recovery exists.

In both cases the user suffers an irrecoverable loss of bridged assets.

## Likelihood Explanation
Any unprivileged user can trigger this by calling `ft_transfer_call` with an amount below `10^(origin_decimals − decimals)` on any token whose NEAR decimal count exceeds the destination chain's decimal count. No special role or permission is required. The condition is realistic for tokens with large decimal mismatches (e.g., 18 vs. 6), and can occur accidentally (user sends a small "test" amount) or be induced by a griefing actor who front-runs or social-engineers the victim into sending a dust amount.

## Recommendation
At the start of `init_transfer_internal` (or inside `init_transfer` before calling it), compute the normalized amount using the same `normalize_amount` logic used in `sign_transfer`. If the result is zero, return the full token amount to the caller (triggering a refund via `ft_on_transfer`) before any tokens are burned or locked and before the transfer is inserted into `pending_transfers`. This mirrors the existing early-return pattern already used for storage-balance failure (L1846–1848) and non-Near tokens (L1859–1860).

## Proof of Concept
1. Register a token with `origin_decimals = 18` on NEAR and `decimals = 6` on Ethereum (via `token_decimals` mapping).
2. User calls `ft_transfer_call` sending `amount = 1` yocto with an `InitTransfer` message targeting Ethereum.
3. `ft_on_transfer` → `init_transfer` → `init_transfer_internal`:
   - `add_transfer_message` stores the transfer in `pending_transfers`.
   - `burn_tokens_if_needed` burns 1 yocto (for a deployed token).
   - Returns `U128(0)` → `ft_on_transfer` refunds nothing.
4. Relayer calls `sign_transfer` for this transfer ID.
5. `normalize_amount(1, Decimals { decimals: 6, origin_decimals: 18 })` → `1 / 10^12 = 0`.
6. `require!(0 > 0, BridgeError::InvalidAmountToTransfer)` panics — call reverts.
7. No other code path removes this transfer or recovers the burned tokens. The user's funds are permanently lost.

A local unit test can reproduce this by: (a) registering token decimals with `origin_decimals=18, decimals=6`, (b) calling `ft_on_transfer` with `amount=U128(1)` and a valid `InitTransfer` message, (c) asserting the transfer is stored in `pending_transfers`, (d) calling `sign_transfer` and asserting it panics with `InvalidAmountToTransfer`, and (e) asserting no removal path is reachable.
