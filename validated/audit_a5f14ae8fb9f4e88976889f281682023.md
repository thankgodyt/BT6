### Title
Permissionless `new()` Initialization Allows Any Caller to Seize `bridge_id` and Mint Arbitrary nBTC - (File: contracts/nbtc/src/lib.rs)

---

### Summary

The `nbtc` token contract's `new()` initializer imposes no restriction on who may call it. Any NEAR account that calls `new()` before the legitimate deployer does so will install itself as both `controller` and `bridge_id`. Because `mint()` and `burn()` are gated solely by `assert_bridge()` — which checks `self.bridge_id == env::predecessor_account_id()` — the attacker immediately gains the ability to mint an unlimited supply of nBTC to any account.

---

### Finding Description

`contracts/nbtc/src/lib.rs` exposes a public `#[init]` function:

```rust
#[init]
pub fn new(
    controller: AccountId,
    bridge_id: AccountId,
    ...
) -> Self {
    require!(!env::state_exists(), "Already initialized");
    ...
}
```

The only guard is `require!(!env::state_exists(), ...)`, which prevents a second call once state exists, but does **nothing** to restrict who makes the first call. There is no check that `env::predecessor_account_id()` equals the contract account, the account owner, or any other authorized party.

The entire privilege model of the token contract flows from two fields set during `new()`:

- `bridge_id` — checked by `assert_bridge()` at line 332–333, which gates `mint()`, `burn()`, and `safe_mint()`
- `controller` — checked by `assert_controller()` at line 336–338, which gates `set_controller()`, `set_metadata()`, `set_withdraw_relayer_address()`, and `upgrade_and_migrate()`

An attacker who calls `new()` first supplies their own account as both `controller` and `bridge_id`, then immediately calls `mint()` with arbitrary `mint_amount` to any recipient.

---

### Impact Explanation

**Critical.** The attacker who front-runs initialization becomes `bridge_id` and can call `mint()` (line 126–148) without restriction, minting an unbacked supply of nBTC to any NEAR account. This constitutes unauthorized minting of the bridge token. Additionally, as `controller`, the attacker can call `upgrade_and_migrate()` (line 78–99 of `migrate.rs`) to replace the contract code entirely, permanently destroying the token contract.

---

### Likelihood Explanation

In NEAR, contract deployment and contract initialization are separate transactions unless the deployer explicitly batches them. Deployment scripts, multisig wallets, and DAO-controlled deployments commonly issue these as two distinct transactions, creating a window — however brief — during which the state does not yet exist and `new()` is callable by anyone. A monitoring attacker watching the mempool or block explorer for a `deploy_contract` action on the `nbtc` account can immediately submit a `new()` call in the next block. The attack requires no special privilege, no funds beyond gas, and no prior relationship with the protocol.

---

### Recommendation

Restrict `new()` to the contract account's own predecessor (i.e., the deploying account) by adding:

```rust
require!(
    env::predecessor_account_id() == env::current_account_id(),
    "Only the contract account may initialize"
);
```

Alternatively, batch the `deploy_contract` and `new()` actions into a single NEAR batch transaction so no intermediate uninitialized state is ever observable on-chain.

---

### Proof of Concept

1. Attacker monitors NEAR for a `deploy_contract` action targeting the `nbtc` account.
2. In the immediately following block, attacker submits:
   ```
   near call <nbtc_account> new '{
     "controller": "attacker.near",
     "bridge_id": "attacker.near",
     "name": "nBTC", "symbol": "nBTC",
     "icon": null, "decimals": 8
   }'
   ```
3. `require!(!env::state_exists(), ...)` passes because state is empty.
4. `controller` and `bridge_id` are both set to `attacker.near`.
5. Attacker calls:
   ```
   near call <nbtc_account> mint '{
     "mint_account_id": "attacker.near",
     "mint_amount": "1000000000000",
     "protocol_fee": "0",
     "relayer_account_id": "attacker.near",
     "relayer_fee": "0",
     "post_actions": null
   }'
   ```
6. `assert_bridge()` passes because `env::predecessor_account_id() == "attacker.near" == self.bridge_id`.
7. `mint_inner()` deposits `1_000_000_000_000` nBTC to `attacker.near` with zero BTC backing.
