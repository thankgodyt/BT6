### Title
Excess Attached NEAR Deposit Permanently Locked in `execute_refund` and `request_refund` - (File: contracts/satoshi-bridge/src/refund.rs, contracts/satoshi-bridge/src/api/bridge.rs)

### Summary
Both `execute_refund` and `request_refund` are `#[payable]` functions that enforce a minimum attached deposit using a `>=` check but never refund any surplus NEAR to the caller. Any NEAR sent above the required threshold is silently absorbed into the contract balance with no recovery path, permanently locking user funds.

### Finding Description
`request_refund` (bridge.rs line 508) and `execute_refund` (bridge.rs line 580) are public, `#[payable]` entry points callable by any unprivileged NEAR account. Both delegate to internal helpers that gate execution on a minimum attached deposit:

In `internal_request_refund` (refund.rs lines 146–149):
```rust
require!(
    env::attached_deposit() >= self.required_balance_for_request_refund(),
    "Insufficient deposit for storage"
);
```

In `resolve_execute_refund_timelock` (refund.rs lines 202–205):
```rust
require!(
    env::attached_deposit() >= self.required_balance_for_execute_refund(),
    "Insufficient deposit for storage"
);
```

Neither function contains any logic to compute the surplus (`attached_deposit - required_balance`) and return it to `env::predecessor_account_id()` via a `Promise::new(...).transfer(surplus)` call. The entire attached deposit — including any amount above the required threshold — is retained by the contract permanently. There is no `claim_excess_deposit` or equivalent recovery mechanism anywhere in the codebase.

The `request_refund` docstring states "The deposit is NOT refunded — it covers request storage and acts as an anti-spam fee," but this justification applies only to the exact required amount. Any NEAR beyond `required_balance_for_request_refund()` has no documented or functional justification for being withheld.

### Impact Explanation
Any NEAR sent above the required storage deposit is permanently locked in the contract with no recovery path. A user who sends, for example, 2× the required amount loses the excess forever. This constitutes a permanent, irreversible loss of user funds triggered by normal bridge usage. The loss is bounded only by what the user attaches, and since the required amounts are not prominently surfaced in UIs, over-payment is a realistic user error.

**Impact: Medium** — Permanent locking of user NEAR funds without any theft of bridged BTC/nBTC assets.

### Likelihood Explanation
Both `execute_refund` and `request_refund` are publicly callable by any NEAR account. Users routinely over-attach NEAR to avoid "Insufficient deposit" rejections, especially when the exact required amount is not displayed in a wallet UI. The `required_balance_for_*` view functions exist but are not enforced as an exact match, making accidental over-payment a realistic and common scenario.

### Recommendation
1. Compute the surplus after the minimum check and refund it immediately:
```rust
let required = self.required_balance_for_execute_refund();
let attached = env::attached_deposit();
require!(attached >= required, "Insufficient deposit for storage");
let surplus = attached.saturating_sub(required);
if surplus > NearToken::from_yoctonear(0) {
    Promise::new(env::predecessor_account_id()).transfer(surplus);
}
```
2. Apply the same pattern to `request_refund` / `internal_request_refund`.
3. Alternatively, change the check to `== required` and document the exact amount callers must attach.

### Proof of Concept
1. Query `required_balance_for_execute_refund()` → returns `R` yoctoNEAR.
2. Call `execute_refund(utxo_storage_key, None)` with `attached_deposit = R + 1_000_000_000_000_000_000_000_000` (1 NEAR extra).
3. The `require!` at refund.rs line 202 passes because `attached >= R`.
4. The function proceeds normally; no transfer back to the caller is issued.
5. The extra 1 NEAR is now part of the contract's balance with no mechanism to retrieve it. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
