### Title
`triggerHardForkDijkstra` Silently Dropped in `protocolInfoCardano` — Conway Never Transitions to Dijkstra Era - (File: `ouroboros-consensus-cardano/src/ouroboros-consensus-cardano/Ouroboros/Consensus/Cardano/Node.hs`)

---

### Summary

`protocolInfoCardano` accepts a `triggerHardForkDijkstra` field in `CardanoProtocolParams` but never extracts it from the pattern match and never wires it into `partialLedgerConfigConway`. Instead, `partialLedgerConfigConway` hardcodes `TriggerHardForkNotDuringThisExecution`, permanently suppressing the Conway→Dijkstra era transition regardless of operator configuration.

---

### Finding Description

`CardanoHardForkTriggers'` has seven trigger fields, one per Shelley-based era: [1](#0-0) 

The pattern in `protocolInfoCardano` only destructures **six** of them — `triggerHardForkDijkstra` is silently omitted: [2](#0-1) 

Every other era's `partialLedgerConfig` correctly passes the trigger for the **next** era. The established pattern is:

| Era config | Trigger used |
|---|---|
| `partialLedgerConfigShelley` | `toTriggerHardFork triggerHardForkAllegra` |
| `partialLedgerConfigAllegra` | `toTriggerHardFork triggerHardForkMary` |
| `partialLedgerConfigMary` | `toTriggerHardFork triggerHardForkAlonzo` |
| `partialLedgerConfigAlonzo` | `toTriggerHardFork triggerHardForkBabbage` |
| `partialLedgerConfigBabbage` | `toTriggerHardFork triggerHardForkConway` |
| **`partialLedgerConfigConway`** | **`TriggerHardForkNotDuringThisExecution` ← BUG** |
| `partialLedgerConfigDijkstra` | `TriggerHardForkNotDuringThisExecution` (correct: last era) |

The Conway config: [3](#0-2) 

Should mirror the Babbage config: [4](#0-3) 

`TriggerHardForkNotDuringThisExecution` is defined to mean the era cannot end within this node process execution: [5](#0-4) 

`singleEraTransition` for a Shelley-based era returns `Nothing` when this variant is set, so the HFC's `extendToSlot` will never advance the telescope past Conway: [6](#0-5) 

---

### Impact Explanation

**High — Hard-fork era transition bug that breaks cross-era consensus for production Cardano nodes.**

When the on-chain protocol version reaches the Dijkstra threshold (via governance), nodes running this code will never call `extendToSlot` past Conway. They will reject Dijkstra-era blocks as belonging to an unknown era and stay on the Conway chain. Nodes with a correct implementation will transition to Dijkstra and build a divergent chain. This is a permanent, irrecoverable chain split between patched and unpatched nodes — a consensus safety failure.

Additionally, `triggerHardForkDijkstra` is accepted as a parameter in `CardanoProtocolParams` and wired through `CardanoHardForkTriggers`: [7](#0-6) 

Operators who configure `CardanoTriggerHardForkAtDefaultVersion` or `CardanoTriggerHardForkAtEpoch` for Dijkstra will receive no error and no warning — the value is silently discarded.

---

### Likelihood Explanation

**High.** This is a production initialization path executed on every node startup. The Dijkstra era is the latest era in the codebase and the transition is expected to occur via on-chain governance. The bug will manifest exactly when the Conway→Dijkstra transition is supposed to happen. No special attacker action is required — the on-chain protocol version update (a normal governance action) is the trigger. The operator has no way to detect the misconfiguration because the parameter is accepted without error.

---

### Recommendation

1. Extract `triggerHardForkDijkstra` in the pattern match inside `protocolInfoCardano`:

```haskell
cardanoHardForkTriggers =
  CardanoHardForkTriggers'
    { triggerHardForkShelley
    , triggerHardForkAllegra
    , triggerHardForkMary
    , triggerHardForkAlonzo
    , triggerHardForkBabbage
    , triggerHardForkConway
    , triggerHardForkDijkstra   -- ADD THIS
    }
```

2. Wire it into `partialLedgerConfigConway`:

```haskell
partialLedgerConfigConway =
  mkPartialLedgerConfigShelley
    transitionConfigConway
    (toTriggerHardFork triggerHardForkDijkstra)   -- WAS: TriggerHardForkNotDuringThisExecution
```

### Proof of Concept

The root cause is directly observable by diffing the Conway and Babbage ledger config definitions:

- **Babbage** (correct): [4](#0-3) 
- **Conway** (buggy): [3](#0-2) 

And the missing field in the destructuring: [8](#0-7) 

A node configured with `triggerHardForkDijkstra = CardanoTriggerHardForkAtEpoch 0` (or any epoch) will still never enter Dijkstra, because `singleEraTransition` for Conway will always return `Nothing` due to `TriggerHardForkNotDuringThisExecution`, and `extendToSlot` will never advance the `HardForkState` telescope past Conway.
