Audit Report

## Title
Floor Division in `normalize_amount` Permanently Freezes User Funds When Transfer Amount Is Below Decimal Threshold - (File: near/omni-bridge/src/lib.rs)

## Summary
`normalize_amount` applies integer floor division to scale a token amount from its origin precision to the bridge's normalized precision. When a user's `amount_without_fee` is smaller than `10^(origin_decimals - decimals)`, the result truncates to zero. `sign_transfer` then panics on the `require!(amount_to_transfer > 0)` guard — before any MPC call is made — so `sign_transfer_callback` is never reached, the `TransferMessage` is never removed, and the already-burned or already-locked tokens are permanently frozen with no recovery path.

## Finding Description
`normalize_amount` is defined with floor division: [1](#0-0) 

The inline comment at line 2781 even acknowledges: *"When fee = 0, dust stays locked/burned"* — but this only contemplates remainder dust, not the case where the entire normalized result is zero.

`sign_transfer` calls `normalize_amount` on `amount_without_fee` and panics immediately if the result is zero, before issuing any cross-contract MPC call: [2](#0-1) 

`init_transfer` only validates `fee < amount`; it does not verify that `normalize_amount(amount_without_fee, decimals) > 0`: [3](#0-2) 

`init_transfer_internal` burns or locks the tokens and stores the `TransferMessage` unconditionally once storage checks pass: [4](#0-3) 

The only code paths that call `remove_transfer_message` are:
- `sign_transfer_callback` (line 657) — only reached after a successful MPC signing response, which never happens because `sign_transfer` panics first.
- `claim_fee_callback` (line 1094) — requires a valid destination-chain finalization proof, which is impossible since no signing ever occurred.

There is no `cancel_transfer` or user-callable refund function anywhere in the contract.

## Impact Explanation
This is a concrete instance of **permanent freezing of bridged funds**. Tokens are burned or locked on NEAR inside `init_transfer_internal`, the `TransferMessage` is stored, and every subsequent `sign_transfer` call reverts with `InvalidAmountToTransfer`. No code path can remove the stuck `TransferMessage` or return the tokens. The funds are irrecoverable. This matches the allowed Critical impact: *"permanent freezing of bridged funds across NEAR."*

## Likelihood Explanation
The condition is reachable by any unprivileged user via a standard `ft_transfer_call`. No special role, leaked key, or privileged access is required. Tokens with a decimal gap between origin and bridge representation (e.g., `origin_decimals = 24`, `decimals = 18`, giving `diff_decimals = 6` and a divisor of 1,000,000) are explicitly supported. Any transfer of fewer than 1,000,000 base units (after fee) triggers the freeze. A user unfamiliar with the minimum effective transfer size will trigger this inadvertently.

## Recommendation
Add a minimum-amount check inside `init_transfer` (before `init_transfer_internal` is called) that verifies `normalize_amount(amount_without_fee, decimals) > 0`. This prevents tokens from being locked or burned when the normalized amount would be zero. As a defense-in-depth measure, add a user-callable `cancel_transfer` function that refunds locked/burned tokens when a transfer has not yet been signed, so that any stuck transfers can be recovered.

## Proof of Concept
1. Register a token with `origin_decimals = 24`, `decimals = 18` (`diff_decimals = 6`, divisor = 1,000,000).
2. User calls `ft_transfer_call` with `amount = 500_000`, `fee = 0`.
3. `init_transfer` passes the `fee < amount` check (`0 < 500_000`). `init_transfer_internal` burns/locks 500,000 base units and stores the `TransferMessage`.
4. Relayer calls `sign_transfer` with the resulting `transfer_id`.
5. `normalize_amount(500_000, {origin_decimals:24, decimals:18})` = `500_000 / 1_000_000` = **0**.
6. `require!(0 > 0, BridgeError::InvalidAmountToTransfer)` panics. No MPC promise is created.
7. `sign_transfer_callback` is never invoked; `remove_transfer_message` is never called.
8. The `TransferMessage` persists in storage indefinitely. The 500,000 base-unit tokens are permanently frozen with no recovery path.
