### Title
Peras Vote and Certificate Verification Bypass via Stub `validatePerasVote`/`validatePerasCert` — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance contains stub implementations of `validatePerasVote` and `validatePerasCert` that skip all cryptographic and committee-eligibility checks. `validatePerasCert` unconditionally returns `Right` for every certificate. `validatePerasVote` accepts any vote whose voter ID appears in the stake distribution, without verifying the BLS signature or committee eligibility proof. Because `validatePerasVote` is called on every inbound vote from peers (via `processVotes`), an unprivileged peer can submit votes for blocks it is not eligible to vote for, accumulate fraudulent quorum, and cause the node to forge and accept a certificate for an attacker-chosen block — directly influencing chain selection.

---

### Finding Description

The `BlockSupportsPeras` class in `SupportsPeras.hs` defines the interface for Peras vote and certificate validation. The catch-all instance `instance StandardHash blk => BlockSupportsPeras blk` is the only instance present in the codebase and is therefore the one used in production. Its implementations are explicit stubs:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }

validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
```

`validatePerasCert` accepts every certificate unconditionally. `validatePerasVote` accepts every vote whose `pvVoteVoterId` is present in the stake distribution — it never verifies the BLS vote signature, never checks the committee eligibility proof (`PersistentPerasVoteEligibilityProof` / `NonPersistentPerasVoteEligibilityProof`), and never checks whether the voter was actually selected into the voting committee for the given round.

The inbound vote path in `makePerasVotePoolWriterFromVoteDB` and `makePerasVotePoolWriterFromChainDB` calls `validatePerasVote` directly on every peer-supplied vote before adding it to the `PerasVoteDB`:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
```

Once a vote passes this stub check, it is timestamped and passed to `implAddVote`, which feeds it into `updatePerasRoundVoteStates`. When accumulated stake crosses the quorum threshold, `forgePerasCert` is called and the resulting certificate is submitted to chain selection via `addPerasVoteWithAsyncCertHandling`.

The analog to the original bug is exact: just as `grantApprover` did not check whether the account had an active submission before granting the approver role, `validatePerasVote` does not check whether the voter holds a valid committee seat before accepting the vote. In both cases, a role/privilege check is missing because the relevant state (committee membership) is not consulted at the point of authorization.

---

### Impact Explanation

An unprivileged peer that controls any staked pool key can:

1. Craft `PerasVote` messages for an arbitrary block, using any voter ID that appears in the stake distribution (no BLS key required — the signature field is never verified).
2. Submit these votes via the Peras vote miniprotocol.
3. Accumulate enough fraudulent stake-weighted votes to exceed the quorum threshold.
4. Cause the receiving node to forge a `ValidatedPerasCert` for the attacker-chosen block.
5. Trigger chain selection for that block, potentially causing the node to switch to a non-canonical chain boosted by the fraudulent certificate.

This is a **bypass of Peras voting/certificate checks** that lets an unprivileged peer make an honest node prefer a non-canonical chain, matching the "Critical — bypass of certificate/vote checks" and "High — chain selection bug" impact categories.

---

### Likelihood Explanation

The entry path is direct and requires no special privileges: any peer connected via the Peras vote miniprotocol can submit votes. The only prerequisite is knowledge of a voter ID present in the stake distribution, which is public on-chain data. No BLS private key is needed because the signature is never verified. The attack is therefore trivially executable by any network peer.

---

### Recommendation

Replace the stub implementations with full validation:

- `validatePerasVote` must verify the BLS vote signature against the voter's public key (looked up from the committee/stake distribution), verify the committee eligibility proof (VRF output for non-persistent members), and confirm the voter was selected into the committee for the given round and election ID.
- `validatePerasCert` must verify the aggregate BLS signature against the aggregate public key of the listed voters, verify each voter's committee membership, and confirm the certificate round and boosted block are consistent.

The `WFALS.implVerifyVote` and `WFALS.implVerifyCert` functions already implement the correct cryptographic checks for the WFALS committee scheme and should be wired into the production `BlockSupportsPeras` instance once the HFC plumbing is in place (tracked in issue #120).

### Proof of Concept

1. Observe that `validatePerasVote` in `SupportsPeras.hs` (lines 363–371) only calls `lookupPerasVoteStake` and never inspects `pvEligibilityProof` or `pvSignature`.
2. Construct a `PerasVote blk` with `pvVoteVoterId` set to any pool ID present in the current stake distribution, `pvVoteBlock` set to the attacker's preferred block point, and `pvSignature` set to an arbitrary/zeroed value.
3. Submit this vote via the Peras vote miniprotocol to a target node.
4. `processVotes` (lines 178–200 of `PerasVote.hs`) calls `validatePerasVote`, which returns `Right` because the voter ID is in the stake distribution.
5. The vote is added to `PerasVoteDB` via `implAddVote` (lines 183–246 of `PerasVoteDB/Impl.hs`).
6. Repeat with enough distinct voter IDs to exceed the quorum threshold; `updatePerasRoundVoteStates` triggers `forgePerasCert`, producing a `ValidatedPerasCert` for the attacker's block.
