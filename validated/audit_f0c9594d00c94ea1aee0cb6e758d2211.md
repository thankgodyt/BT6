### Title
Missing Dust-Threshold Guard on Transparent Refund Amount Causes Permanently Stuck Refund State — (`contracts/satoshi-bridge/src/zcash_utils/contract_methods.rs`, `refund.rs`)

### Summary

An unprivileged user can supply a `gas_fee` equal to `deposit_amount − 1` at `request_refund` time. Every subsequent guard in the refund pipeline only checks `gas_fee >= zip317_min_fee` and `refund_amount > 0`, but never that `refund_amount >= Zcash dust threshold. The bridge builds, signs, and attempts to broadcast a transparent refund transaction with a 1-zatoshi output. Zcash relay nodes reject it as non-standard dust. The deposit UTXO is simultaneously written into `verified_deposit_utxo`, making the stuck state unrecoverable without a contract upgrade.

---

### Finding Description

**Step 1 — `request_refund_callback`: gas_fee is user-controlled with only one guard** [1](#0-0) 

The only constraint is `gas_fee < amount`. With `deposit_amount = 10 001` zatoshis and `gas_fee = 10 000`, the check passes.

**Step 2 — `refund_execution_inputs`: refund_amount only checked for > 0** [2](#0-1) 

`refund_amount = 10 001 − 10 000 = 1` zatoshi. The `require!(refund_amount > 0, …)` guard passes. No dust-threshold check exists anywhere in this function.

**Step 3 — `execute_refund_callback`: transparent output is built unconditionally** [3](#0-2) 

For a transparent refund (no Orchard bundle), `build_refund_output` is called with `refund_amount = 1`.

**Step 4 — `check_psbt_chain_specific`: only validates gas_fee, not refund_amount** [4](#0-3) 

For transparent refunds the Orchard branch is skipped entirely. The sole check is `gas_fee >= min_fee` (10 000 ≥ 10 000 ✓). There is no check that the transparent output value meets the Zcash dust threshold (~294 zatoshis for P2PKH).

**Step 5 — `finalize_refund_with_psbt`: UTXO is irrevocably locked** [5](#0-4) 

The deposit UTXO is inserted into `verified_deposit_utxo` before the transaction is ever broadcast. The refund request is kept with `executed = true`.

**Step 6 — Recovery is impossible without a contract upgrade**

`load_refund_request_for_execute` allows re-execution when `executed = true`: [6](#0-5) 

But the stored `gas_fee` is immutable — every re-execution produces the same 1-zatoshi output. If the operator calls `reject_refund` to remove the request, the UTXO remains in `verified_deposit_utxo`. A fresh `request_refund` for the same UTXO would store a new request with `executed = false`, causing `execute_refund` to fail the `verified_deposit_utxo` check. No function in the codebase removes entries from `verified_deposit_utxo`.

---

### Impact Explanation

The user's deposit UTXO is permanently locked inside the bridge. The refund transaction is rejected by Zcash relay nodes as non-standard (dust output), so it never confirms. The bridge cannot mint nZEC (UTXO is in `verified_deposit_utxo`) and cannot refund (every attempt produces the same rejected transaction). Recovery requires a contract upgrade to clear `verified_deposit_utxo`. This matches the **Medium** impact class: *stuck bridge state requiring operator intervention / permanent locking of bridged funds*.

---

### Likelihood Explanation

The precondition is reachable by any user who holds a valid Zcash deposit UTXO of at least 10 001 zatoshis (the ZIP-317 minimum fee + 1). The user supplies `gas_fee` as an explicit optional parameter to `request_refund`; the bridge imposes no upper bound beyond `gas_fee < amount`. The scenario can be triggered accidentally (misunderstanding the fee field) or deliberately.

---

### Recommendation

Add a Zcash dust-threshold guard in `refund_execution_inputs` (or at the top of `execute_refund_callback`) before building the transparent output:

```rust
// Zcash P2PKH dust threshold (relay policy): 294 zatoshis
const ZCASH_TRANSPARENT_DUST_THRESHOLD: u128 = 294;

require!(
    refund_amount >= ZCASH_TRANSPARENT_DUST_THRESHOLD,
    format!(
        "Refund amount ({}) is below the Zcash dust threshold ({})",
        refund_amount, ZCASH_TRANSPARENT_DUST_THRESHOLD
    )
);
```

Alternatively, enforce the same bound at `request_refund_callback` time so the request is rejected before it is ever stored.

```
gas_fee        = 10_000 zatoshis   // user-supplied; passes gas_fee < amount

1. request_refund(gas_fee = 10_000)
   → request_refund_callback: 10_000 < 10_001 ✓ → stored

   → refund_execution_inputs: refund_amount = 10_001 − 10_000 = 1 > 0 ✓

   → check_psbt_chain_specific: gas_fee(10_000) >= min_fee(10_000) ✓
   → finalize_refund_with_psbt: UTXO inserted into verified_deposit_utxo

3. Broadcast: Zcash node rejects tx (1-zatoshi P2PKH output < 294-zatoshi dust threshold)

4. State: UTXO locked in verified_deposit_utxo; refund_request.executed = true;
   every re-execution produces the same rejected tx; no recovery path without upgrade.
```
