### Title
RBF Pending Info Permanently Stuck in PendingSign Due to Missing `btc_pending_sign_ids` Insert — (`contracts/satoshi-bridge/src/rbf/mod.rs`, `contracts/satoshi-bridge/src/chain_signature.rs`)

### Summary

`set_rbf_pending_info` inserts the new RBF `btc_pending_id` into `btc_pending_infos` and `rbf_txs` but never inserts it into `account.btc_pending_sign_ids`. When the signing service later calls `sign_btc_transaction` for the RBF id and all inputs are signed, `sign_btc_transaction_callback` unconditionally calls `account.btc_pending_sign_ids.remove(&btc_pending_sign_id)`, which returns `false` (the id was never inserted), causing `require!` to panic with `"Internal error"`. The transaction reverts, the RBF pending info remains in `btc_pending_infos` forever in `PendingSign` stage, and the associated vutxos are permanently locked.

### Finding Description

**`set_rbf_pending_info` — no `btc_pending_sign_ids` insert:** [1](#0-0) 

The function inserts into `btc_pending_infos` (line 26) and `rbf_txs` (lines 30–35) but never touches `account.btc_pending_sign_ids`. This applies to every caller: `internal_withdraw_rbf`, `internal_active_utxo_management_rbf`, and `internal_cancel_withdraw`. [2](#0-1) [3](#0-2) [4](#0-3) 

**`sign_btc_transaction_callback` — unconditional remove:**

When all inputs are signed, the callback unconditionally removes the id from `btc_pending_sign_ids` regardless of whether the pending info is an original or RBF transaction: [5](#0-4) 

`HashSet::remove` returns `false` when the element is absent. `require!(false, "Internal error")` panics, reverting the entire callback. The `is_original_tx` guard only controls the subsequent `btc_pending_verify_list.insert`; it does not guard the `remove`.

**`Account.btc_pending_sign_ids` — only one insert site:**

A grep for `btc_pending_sign_ids.insert` across the entire repo returns exactly one match: the `From<AccountV0>` migration path in `account.rs`. There is no insert in any RBF path. [6](#0-5) 

### Impact Explanation

Every RBF pending info created via `set_rbf_pending_info` will panic in `sign_btc_transaction_callback` the moment all its inputs are signed. The panic reverts the callback, leaving the RBF `BTCPendingInfo` permanently in `PendingSign` stage inside `btc_pending_infos`. The vutxos cloned into the RBF pending info are permanently locked with no cleanup path. This affects all three RBF variants: `WithdrawUserRbf`, `ActiveUtxoManagementRbf`, and `WithdrawCancelRbf`.

### Likelihood Explanation

The trigger is the normal, intended lifecycle: user calls `withdraw_rbf` (public), signing service calls `sign_btc_transaction` (normal operation). No adversarial input is required — the bug fires on every successful RBF signing completion. Any user with a valid `WithdrawOriginal` in `PendingVerify` can trigger this.

### Recommendation

In `set_rbf_pending_info`, after inserting into `btc_pending_infos`, also insert the new `btc_pending_id` into the account's `btc_pending_sign_ids`:

```rust
// After inserting into btc_pending_infos and rbf_txs:
let account_id = btc_pending_info.account_id.clone();
self.internal_unwrap_mut_account(&account_id)
    .btc_pending_sign_ids
    .insert(btc_pending_id.clone());
```

Alternatively, guard the `remove` in `sign_btc_transaction_callback` with `is_original_tx`, but that would leave RBF pending infos untracked in `btc_pending_sign_ids` and break the account's pending-sign capacity accounting.

### Proof of Concept

Call sequence:
1. User calls `withdraw_rbf(original_btc_pending_verify_id, psbt)` → `internal_withdraw_rbf` → `set_rbf_pending_info` inserts RBF id into `btc_pending_infos` and `rbf_txs` only.
2. Signing service calls `sign_btc_transaction(rbf_id, 0, key_version)` → `internal_sign_btc_transaction` → chain-signatures cross-contract call → `sign_btc_transaction_callback`.
3. Inside callback, `is_all_signed()` returns `true` (single-input UTXO case).
4. `account.btc_pending_sign_ids.remove(&rbf_id)` returns `false` → `require!` panics with `"Internal error"`.
5. Callback reverts. RBF `BTCPendingInfo` remains in `btc_pending_infos` in `PendingSign` stage forever. Vutxos permanently locked. [7](#0-6)

    pub fn set_rbf_pending_info(
        &mut self,
        original_btc_pending_verify_id: &str,
        mut btc_pending_info: BTCPendingInfo,
        psbt: PsbtWrapper,
        is_cancel: bool,
    ) -> String {
        let rbf_psbt_hex = psbt.serialize();
        let btc_pending_id = psbt.get_pending_id();
        btc_pending_info.btc_pending_id.clone_from(&btc_pending_id);
        btc_pending_info.psbt_hex = rbf_psbt_hex;
        require!(
            self.data_mut()
                .btc_pending_infos
                .insert(btc_pending_id.clone(), btc_pending_info.into())
                .is_none(),
            "pending info already exist"
        );
        let rbf_txs = self
            .data_mut()
            .rbf_txs
            .entry(original_btc_pending_verify_id.to_owned())
            .or_default();
        require!(rbf_txs.insert(btc_pending_id.clone()), "Rbf already exist");
        if !is_cancel {
            require!(
                rbf_txs.len() <= self.internal_config().rbf_num_limit.into(),
                "Exceed rbf_num_limit"
            );
        }
        btc_pending_id
    }
