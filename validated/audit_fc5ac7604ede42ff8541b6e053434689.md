### Title
Attacker Can Front-Run `request_refund` to Redirect Victim's BTC Deposit to Attacker-Controlled Address - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary

`request_refund` is callable by any unprivileged NEAR account and accepts a caller-supplied `refund_address` whenever `deposit_msg.refund_address` is `None`. Because the UTXO storage key (`{tx_id}@{vout}`) is deterministic and only one refund request can exist per key, an attacker who submits a `request_refund` for the same UTXO before the legitimate depositor — using the same `deposit_msg` but their own BTC address — permanently occupies the slot. The victim's subsequent call fails with "Refund request already exists for this UTXO", and after the `unsafe_refund_timelock_sec` elapses the attacker calls the permissionless `execute_refund` to redirect the full deposit (minus gas fee) to their own BTC address.

### Finding Description

**Entry point — `request_refund` has no caller restriction:** [1](#0-0) 

The function carries `#[payable]` and `#[pause]` but no `#[trusted_relayer]` or role guard, so any NEAR account can invoke it.

**Refund address is fully attacker-controlled when `deposit_msg.refund_address` is `None`:** [2](#0-1) 

When the depositor omitted a pre-authorized refund address, the check is skipped entirely and the caller's arbitrary `refund_address` string is forwarded to the callback.

**First writer wins — duplicate check blocks the victim:** [3](#0-2) 

The UTXO key is `{tx_id}@{vout}`, computed deterministically from the public BTC transaction. Whichever `request_refund_callback` executes first inserts the entry; every subsequent call for the same UTXO panics.

**`execute_refund` is permissionless after the timelock:** [4](#0-3) 

No role check exists on `execute_refund`. After `unsafe_refund_timelock_sec` the attacker calls it themselves.

**Refund output is built directly from the stored (attacker-supplied) address:** [5](#0-4) 

The PSBT output script is derived from `refund_request.refund_address`, which is the attacker's address.

### Impact Explanation

The victim's entire BTC deposit (minus the configured gas fee) is sent to the attacker's BTC address via the MPC signing pipeline. The victim cannot register a competing refund request for the same UTXO, and the deposit cannot be claimed via `verify_deposit` either (once `execute_refund` runs, the UTXO is inserted into `verified_deposit_utxo`). [6](#0-5) 

This is a direct, permanent loss of user funds — matching the **Critical** impact tier: *Significant loss, theft, destruction, or permanent locking of user or protocol funds.*

### Likelihood Explanation

- The `deposit_msg` used to derive the deposit address is submitted on-chain via `get_user_deposit_address`, making it publicly observable.
- The BTC transaction (`tx_bytes`, `vout`) is public on the Bitcoin network once confirmed.
- The attacker needs only to submit `request_refund` before the victim's callback finalizes — achievable by monitoring NEAR pending transactions or simply racing the victim to call the function first.
- The only partial mitigation is the `unsafe_refund_timelock_sec` window during which DAO/Operator can reject the request, but this requires active monitoring of every refund request and is not guaranteed.
- The required attached deposit (`required_balance_for_request_refund`) is a negligible cost. [7](#0-6) 

### Recommendation

Bind the refund request to the caller's identity. Two complementary approaches:

1. **Require `deposit_msg.refund_address` to be set** — reject any `request_refund` call where `deposit_msg.refund_address` is `None`, forcing depositors to pre-authorize their refund address at deposit time (already enforced when the field is present).
2. **Record and enforce the original requester** — store `env::predecessor_account_id()` in `RefundRequest` and require that only the original requester (or DAO/Operator) can call `execute_refund` for that entry.

Either change ensures that an attacker who did not create the deposit cannot redirect the refund output.

### Proof of Concept

1. **Alice** calls `get_user_deposit_address` with `DepositMsg { recipient_id: "alice.near", refund_address: None, … }`. This transaction is public on NEAR.
2. Alice sends BTC to the returned deposit address. The BTC transaction (`tx_id`, `vout`) is public on Bitcoin.
3. The relayer never calls `verify_deposit` (e.g., relayer is down).
4. **Bob** (attacker) observes Alice's `deposit_msg` from step 1 and the BTC transaction from step 2.
5. Bob calls `request_refund(deposit_msg=Alice's, refund_address="bob_btc_addr", tx_bytes=…, vout=…, proof=…)` with sufficient attached NEAR deposit.
6. Bob's `request_refund_callback` executes first, storing `RefundRequest { refund_address: "bob_btc_addr", … }` under key `{tx_id}@{vout}`. [8](#0-7) 

7. Alice calls `request_refund` — her callback panics: *"Refund request already exists for this UTXO"*.
8. After `unsafe_refund_timelock_sec` elapses, Bob calls `execute_refund("{tx_id}@{vout}", None)`.
9. The bridge builds a PSBT paying `deposit_amount - gas_fee` satoshis to `"bob_btc_addr"`, requests an MPC signature, and broadcasts the transaction.
10. Alice's BTC is permanently transferred to Bob. [9](#0-8)

    #[payable]

    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,

        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }

    pub(crate) fn internal_execute_refund(
        &mut self,
        utxo_storage_key: String,
        timelock_sec: u64,
        _chain_specific_data: Option<ChainSpecificData>,
    ) -> PromiseOrValue<()> {
        let refund_request = self.load_refund_request_for_execute(&utxo_storage_key, timelock_sec);
        let RefundExecutionInputs {
            outpoint,
            deposit_output,
            refund_amount,
        } = self.refund_execution_inputs(&refund_request);
        let refund_output = self.build_refund_output(&refund_request.refund_address, refund_amount);

        let mut psbt = PsbtWrapper::new(vec![outpoint], vec![refund_output]);
        psbt.set_input_utxo(vec![deposit_output]);

        let caller = env::predecessor_account_id();
        self.finalize_refund_with_psbt(
            caller,
            refund_request,
            psbt,
            refund_amount,
            utxo_storage_key,
        );
        PromiseOrValue::Value(())
    }
