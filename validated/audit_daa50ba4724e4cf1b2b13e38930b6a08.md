### Title
Unvalidated `sign_index` Causes Index-Out-of-Bounds Panic in `sign_btc_transaction` — (`contracts/satoshi-bridge/src/api/chain_signatures.rs`)

---

### Summary

`sign_btc_transaction` accepts a caller-controlled `sign_index: usize` with no upper-bound check. Any unprivileged caller who supplies an out-of-range index against a valid pending-sign ID triggers a Rust index-out-of-bounds panic inside `internal_sign_btc_transaction`, aborting the transaction and consuming all attached gas.

---

### Finding Description

`sign_btc_transaction` is a public, payable function with no caller-identity restriction (only a pausable guard that any account can bypass when the contract is unpaused): [1](#0-0) 

`sign_index` is passed directly to `internal_sign_btc_transaction` without any bounds validation. Inside that function, the first use of `sign_index` is a direct slice index: [2](#0-1) 

Both `btc_pending_info.signatures[sign_index]` (line 92) and `btc_pending_info.vutxos[sign_index]` (line 98) are raw Rust slice indexing operations. `signatures` is initialized as `vec![None; need_signature_num]` and `vutxos` is populated from `generate_vutxos`, both bounded by the number of PSBT inputs: [3](#0-2) 

There is no `require!(sign_index < btc_pending_info.signatures.len(), ...)` guard anywhere in the call path. Supplying `sign_index >= signatures.len()` (e.g., `sign_index = 1` on a single-input refund transaction) causes an immediate Rust panic.

---

### Impact Explanation

- **Severity: Low** — publicly reachable panic in a production bridge path without direct fund theft.
- Any caller can enumerate live pending-sign IDs via `get_btc_pending_infos_paged`, then call `sign_btc_transaction` with an out-of-bounds `sign_index`.
- The call panics at `btc_pending_info.signatures[sign_index]`, aborting the transaction. In NEAR, the attached deposit is refunded on panic, but all prepaid gas is consumed.
- The pending-sign state is not corrupted (the panic rolls back all state changes), so the bridge is not permanently stuck — but the legitimate signer's gas is wasted and the signing round must be retried.

---

### Likelihood Explanation

- The function is publicly callable with no role gate when the contract is unpaused.
- Pending-sign IDs are publicly readable from contract state.
- The exploit requires only a single contract call with a crafted integer argument — no special knowledge, keys, or prior state manipulation needed.

---

### Recommendation

Add an explicit bounds check at the top of `internal_sign_btc_transaction` before any slice access:

```rust
require!(
    sign_index < btc_pending_info.signatures.len(),
    "sign_index out of bounds"
);
```

This should be placed immediately after fetching `btc_pending_info` and before line 92 in `contracts/satoshi-bridge/src/chain_signature.rs`. [4](#0-3) 

---

### Proof of Concept

Using the existing test harness pattern (e.g., from `test_refund.rs` where a single-input refund pending-sign is created):

```rust
// A refund BTCPendingInfo has signatures.len() == 1 and vutxos.len() == 1
// Calling with sign_index = 1 (== signatures.len()) triggers the panic:
context.sign_btc_transaction("alice", &pending_keys[0], 1 /* out-of-bounds */, 0).await
// Expected: transaction panics with index-out-of-bounds
// Actual without fix: NEAR runtime reports ExecutionError with panic
``` [5](#0-4)
