Audit Report

## Title
`finTransfer` Push-Transfer Pattern Permanently Freezes Bridged Funds for Blacklisted Recipients - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`OmniBridge.sol::finTransfer` unconditionally pushes tokens to `payload.recipient` via `safeTransfer`. When the recipient is blacklisted by a transfer-restricted token (e.g., USDC, USDT), the `safeTransfer` reverts the entire transaction. Because no pull-based claim mechanism exists on EVM and no cancel/refund path exists on NEAR for outbound transfers, the user's already-burned or locked tokens are permanently frozen with no recovery path.

## Finding Description

`finTransfer` marks the destination nonce consumed at line 287, then performs signature verification, then executes the token delivery. For native ERC-20 tokens held in escrow by the bridge (the `else` branch), delivery is a direct push:

```solidity
// OmniBridge.sol L283-287
if (completedTransfers[payload.destinationNonce]) {
    revert NonceAlreadyUsed(payload.destinationNonce);
}
completedTransfers[payload.destinationNonce] = true;

// OmniBridge.sol L350-355
} else {
    IERC20(payload.tokenAddress).safeTransfer(
        payload.recipient,
        payload.amount
    );
}
```

Because `completedTransfers[nonce] = true` is set before the transfer and the entire transaction reverts when `safeTransfer` fails, the nonce is not permanently consumed — but every subsequent retry reverts for the same reason. There is no `claim()` function, no `claimable` mapping, and no alternative delivery path anywhere in the EVM contract. A grep across all `.sol` files confirms zero pull-based withdrawal mechanisms exist.

On the NEAR side, `sign_transfer` (lib.rs L447) reads the transfer message and produces an MPC signature. No public `cancel`, `withdraw`, `refund_transfer`, or `revert_transfer` function exists in the NEAR bridge contract — confirmed by exhaustive search. The tokens burned or locked during `init_transfer_internal` (lib.rs L1851) are never returned if EVM finalization fails permanently.

## Impact Explanation

Permanent freezing of bridged funds. A user whose EVM recipient address is on the USDC or USDT blacklist cannot receive their tokens. The relayer cannot finalize the transfer — every `finTransfer` call reverts. The tokens are already burned on NEAR at `initTransfer` time. With no cancel mechanism on NEAR and no alternative claim path on EVM, the funds are unrecoverable. This matches the Critical impact criterion: permanent freezing of bridged funds across NEAR → EVM flows.

## Likelihood Explanation

USDC and USDT are among the most commonly bridged assets and are explicitly supported via `addCustomToken`. Circle and Tether regularly blacklist addresses under OFAC sanctions compliance. A user may be blacklisted after calling `initTransfer` on NEAR but before the relayer finalizes on EVM — the window spans relayer latency plus MPC signing time. No privileged access is required; the blacklisting is an externally triggered, real-world event. The `evm/SECURITY.md` known-issues list does not acknowledge this as an accepted limitation, unlike the explicitly documented "fee-on-transfer tokens not supported" exclusion.

## Recommendation

Replace the push-transfer pattern in `finTransfer` with a pull-based (claim) pattern:

1. Instead of calling `safeTransfer` inside `finTransfer`, record the claimable amount: `claimable[payload.recipient][payload.tokenAddress] += payload.amount`.
2. Add a separate `claim(address tokenAddress)` function allowing the recipient (or a designated address) to withdraw their balance.
3. This decouples delivery failure from finalization: the nonce is consumed, the transfer is recorded, and the recipient can claim when the restriction is lifted or from an alternative address if the protocol allows recipient substitution.

## Proof of Concept

1. Alice holds USDC on NEAR and calls `initTransfer` targeting her EVM address `0xAlice`. USDC is burned on NEAR; a `TransferMessage` is stored in `pending_transfers`.
2. Before the relayer finalizes, Circle blacklists `0xAlice`.
3. The relayer calls `sign_transfer` on NEAR (lib.rs L447), obtaining a valid MPC signature.
4. The relayer calls `finTransfer` on EVM with the signed payload.
5. Execution reaches `OmniBridge.sol` L351: `IERC20(USDC).safeTransfer(0xAlice, amount)` — USDC's `transfer` reverts because `0xAlice` is blacklisted.
6. The entire transaction reverts; `completedTransfers[nonce]` is not set.
7. Every subsequent retry by any relayer produces the same revert.
8. No public cancel or refund function exists on NEAR; the burned USDC is permanently lost.

**Minimal test plan**: Deploy a mock ERC-20 with a blacklist. Call `addCustomToken` to register it. Call `finTransfer` with a payload targeting the blacklisted address. Assert the transaction reverts and `completedTransfers[nonce]` remains false. Confirm no alternative path exists to recover the funds.
