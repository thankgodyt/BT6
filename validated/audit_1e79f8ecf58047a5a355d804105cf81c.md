Audit Report

## Title
Non-Atomic Burn-and-Mint in `swap_migrated_token` Causes Permanent Token Loss - (File: near/omni-bridge/src/lib.rs)

## Summary
`swap_migrated_token` issues a `burn` and a `mint` as two independent parallel cross-contract calls via `burn.and(mint)` with no callback to handle partial failure. Because NEAR cross-contract calls are not atomic, if `burn` succeeds but `mint` fails, the user's old tokens are permanently destroyed while no new tokens are credited. The `ft_transfer_call` refund path then also fails because the bridge holds zero old-token balance.

## Finding Description [1](#0-0) 

`swap_migrated_token` constructs two independent cross-contract calls and returns `burn.and(mint)` with no `.then(...)` callback attached. In NEAR's execution model, `Promise::and` schedules both sub-promises as separate action receipts that execute independently — there is no atomicity guarantee. If the `burn` receipt is processed successfully and the `mint` receipt panics, the joint promise resolves as failed, but the `burn` is not rolled back. [2](#0-1) 

`burn` calls `internal_withdraw` on `env::predecessor_account_id()` (the bridge contract), immediately reducing the bridge's old-token balance to zero. There is no escrow or deferred debit. [3](#0-2) 

`mint` with `msg = None` calls `self.token.internal_deposit(&account_id, amount.into())`. The NEAR FT standard's `internal_deposit` panics if `account_id` has no storage registration in the new token contract, causing the `mint` receipt to fail.

When `ft_on_transfer` returns the failed `burn.and(mint)` promise, the old token contract's `ft_resolve_transfer` interprets the failure as "refund full amount to sender." However, the bridge's old-token balance is already zero, so the refund transfer also panics. The user receives neither old tokens nor new tokens, with no recovery path.

## Impact Explanation
This is a concrete, permanent loss of bridged funds reachable by any unprivileged token holder. A user who sends migrated bridge tokens to the omni-bridge for swapping can lose their entire balance with no on-chain recovery mechanism. This matches the Critical impact class: *loss or permanent freezing of bridged funds*.

## Likelihood Explanation
The failure mode is triggered whenever the recipient (`sender_id`) has not registered a storage deposit in the new token contract — a routine condition for users who are unaware of the migration or have never interacted with the new token. No special privileges or attacker coordination are required; any user holding migrated tokens can self-trigger this by calling `ft_transfer_call` on the old token contract. Additionally, the fixed `MINT_TOKEN_GAS` allocation of 5 TGas is low and could independently cause `mint` to fail on token contracts with non-trivial `mint` implementations. [4](#0-3) 

## Recommendation
Replace the fire-and-forget parallel pattern with a sequential, callback-guarded flow:

1. Call `mint` first.
2. In the `mint` callback, check for success.
3. Only if `mint` succeeded, call `burn`.
4. If `mint` failed, return the full `amount` from `ft_on_transfer` so the old token contract refunds the user (the bridge still holds the tokens at this point).

This ensures the bridge never destroys old tokens unless new tokens have already been successfully credited to the user.

## Proof of Concept
1. Deploy old token contract (`old_token`) and new token contract (`new_token`), both NEP-141 with storage registration required.
2. Register the bridge as controller of both; add `old_token → new_token` to `migrated_tokens`.
3. Alice holds 1000 units of `old_token` and has registered storage there, but has **never** registered storage in `new_token`.
4. Alice calls `old_token.ft_transfer_call(bridge, 1000, msg)`.
5. Bridge's `ft_on_transfer` calls `swap_migrated_token(alice, old_token, 1000)`.
6. `burn.and(mint)` is scheduled: the `burn` receipt executes and removes 1000 old tokens from the bridge's account.
7. The `mint` receipt executes and panics: `alice` has no storage deposit in `new_token`; `internal_deposit` panics.
8. The joint promise fails; `ft_resolve_transfer` on `old_token` attempts to refund 1000 tokens to Alice.
9. The bridge's `old_token` balance is 0 (already burned); the refund transfer panics.
10. Alice has lost 1000 old tokens and received 0 new tokens — permanent, unrecoverable loss.

    fn swap_migrated_token(
        &mut self,
        sender_id: AccountId,
        old_token: AccountId,
        amount: U128,
    ) -> Promise {
        let new_token = self
            .migrated_tokens
            .get(&old_token)
            .near_expect(BridgeError::TokenNotMigrated);

        let burn = ext_token::ext(old_token).burn(amount);
