### Title
Attacker Can Redirect Victim's BTC Refund to Attacker-Controlled Address via `request_refund` — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

`request_refund` accepts a caller-supplied `refund_address` with no validation that the caller is the original depositor. When a deposit was made with `deposit_msg.refund_address = None`, any attacker can front-run the victim's refund request and permanently redirect the BTC to an attacker-controlled address. This is a direct analog to H-42's "arbitrary address input in a multi-step function without caller identity validation."

---

### Finding Description

`request_refund` (bridge.rs:510) is a public, payable function callable by any NEAR account. It accepts a `deposit_msg`, a `refund_address`, and a Merkle proof. The only address validation occurs inside `internal_request_refund` (refund.rs:154–158):

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [1](#0-0) 

This check is **skipped entirely** when `deposit_msg.refund_address` is `None`. In that case, the caller-provided `refund_address` is stored verbatim in the `RefundRequest` with no identity check:

```rust
let refund_request = RefundRequest {
    ...
    refund_address,   // ← attacker-controlled
    ...
};
self.data_mut().refund_requests.insert(utxo_storage_key, refund_request.into());
``` [2](#0-1) 

The `deposit_msg` used to derive the deposit address is **fully public**: `get_user_deposit_address` emits a `LogDepositAddress` event containing the complete `deposit_msg` struct. [3](#0-2) 

Once a refund request is stored, a duplicate-prevention check in `request_refund_callback` blocks any second request for the same UTXO:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [4](#0-3) 

This means the victim cannot overwrite the attacker's malicious request. Only DAO/Operator can cancel it via `reject_refund`, which requires privileged access:

```rust
require!(
    is_privileged || is_already_deposited,
    "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
);
``` [5](#0-4) 

The `unsafe_refund_timelock_sec` is applied when `deposit_msg.refund_address` is `None` (the attacker's scenario), giving the DAO a window to intervene: [6](#0-5) 

However, this is an off-chain operational control, not an on-chain invariant. If the DAO does not act within the timelock, `execute_refund` (callable by anyone) builds and submits the PSBT paying the attacker's address: [7](#0-6) 

---

### Impact Explanation

If the DAO fails to reject the malicious request within `unsafe_refund_timelock_sec`, the victim's BTC is permanently sent to the attacker's address. The victim has no on-chain recourse: they cannot overwrite the request, cannot reject it themselves, and cannot recover the funds once the refund transaction is broadcast and confirmed on Bitcoin. This constitutes a **significant, permanent loss of user funds**.

---

### Likelihood Explanation

The attack requires:
1. The victim to use `deposit_msg.refund_address = None` (common — users who don't pre-specify a refund address)
2. The attacker to observe the `LogDepositAddress` event (trivially public on NEAR)
3. The attacker to observe the victim's BTC deposit transaction (public Bitcoin blockchain)
4. The attacker to call `request_refund` before the victim (a simple front-run with attached NEAR deposit)
5. The DAO to fail to reject the request within `unsafe_refund_timelock_sec`

Steps 1–4 are straightforward for any on-chain observer. Step 5 is the only mitigation, and it is operational, not cryptographic. Likelihood is **medium**: the attack is realistic whenever DAO monitoring is imperfect or the timelock window is missed.

---

### Recommendation

- **Require `deposit_msg.recipient_id == env::predecessor_account_id()`** in `request_refund`, so only the intended nBTC recipient can submit a refund request for their own deposit.
- Alternatively, **require `deposit_msg.refund_address` to always be `Some`**, eliminating the code path where an arbitrary caller-supplied address is accepted.
- As defense-in-depth, store the submitter's NEAR account ID in `RefundRequest` and enforce that `execute_refund` can only be called by the original submitter or a privileged role.

---

### Proof of Concept

1. Alice calls `get_user_deposit_address({ recipient_id: "alice.near", refund_address: None, ... })`. The bridge emits `LogDepositAddress` with the full `deposit_msg`.
2. Alice sends BTC to the returned deposit address. The relayer never calls `verify_deposit`.
3. Attacker reads the `LogDepositAddress` event and Alice's BTC transaction from the public chains.
4. Attacker calls `request_refund(alice_deposit_msg, "attacker_btc_addr", alice_tx_bytes, vout, proof, None)` with the required NEAR storage deposit attached.
5. `internal_request_refund` skips the address check (since `deposit_msg.refund_address` is `None`) and stores `RefundRequest { refund_address: "attacker_btc_addr", ... }`.
6. Alice calls `request_refund` with her own BTC address → panics: `"Refund request already exists for this UTXO"`.
7. After `unsafe_refund_timelock_sec` elapses (and assuming the DAO does not reject), anyone calls `execute_refund(utxo_storage_key)`.
8. `internal_execute_refund` builds a PSBT paying `refund_request.refund_address` = attacker's address, and the MPC signs it.
9. Alice's BTC is permanently sent to the attacker.

            caller,
            refund_request,
            psbt,
            refund_amount,
            utxo_storage_key,
