Audit Report

## Title
Tokens Permanently Locked When `normalize_amount` Returns Zero Due to Decimal Truncation — (`near/omni-bridge/src/lib.rs`)

## Summary
When a NEAR-native token with `origin_decimals > decimals` (e.g., 24-decimal NEAR token bridged to an 18-decimal EVM token) is transferred with an `amount_without_fee` below the decimal-scaling threshold (`10^diff_decimals`), `normalize_amount` returns 0. `sign_transfer` then always panics on the `require!(amount_to_transfer > 0, ...)` guard, but the tokens were already locked during `init_transfer`/`ft_transfer_call`. No cancel or FT-refund path exists in the contract, permanently freezing the locked funds.

## Finding Description
`normalize_amount` performs integer floor division:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [1](#0-0) 

For any token where `origin_decimals > decimals` (e.g., `diff_decimals = 6`), any `amount_without_fee < 10^6` normalizes to 0.

`sign_transfer` calls `normalize_amount` and guards against zero:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
``` [2](#0-1) 

The guard correctly prevents signing, but tokens are already locked. The only check at lock time in `init_transfer` is:

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
``` [3](#0-2) 

There is no pre-lock check that `normalize_amount(amount_without_fee) > 0`. The only `refund` helper in the contract transfers NEAR (native token) only — it does not unlock or return FT tokens: [4](#0-3) 

No `cancel_transfer`, `unlock_transfer`, or equivalent FT-refund function exists in the contract. A search for such functions returns no matches. The EVM `_normalizeDecimals` caps token decimals at 18, making the decimal gap concrete for any NEAR token with more than 18 decimals.

## Impact Explanation
This constitutes **permanent freezing of bridged funds**: an unprivileged user's FT tokens are locked in the bridge contract via `ft_transfer_call` → `init_transfer`, and the transfer can never be completed (every `sign_transfer` call panics deterministically) nor refunded (no FT cancel/refund path exists). This matches the Critical impact tier: "permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet, Bitcoin, Zcash, or Wormhole-routed flows."

## Likelihood Explanation
Any NEAR-native token registered with `origin_decimals > 18` (common in the NEAR ecosystem, e.g., 24-decimal tokens) creates a `diff_decimals ≥ 6` gap. A user transferring fewer than `10^6` base units of such a token triggers the bug. This is reachable by any unprivileged bridge user via the standard `ft_transfer_call` flow with no special privileges required. Small-value transfers, dust sweeps, or user error are all realistic triggers.

## Recommendation
Add a pre-lock validation in `init_transfer` (or in `ft_on_transfer` before tokens are accepted) that computes `normalize_amount(amount_without_fee)` for the target chain's decimals and rejects the transfer if the result is zero, mirroring the guard already present in `sign_transfer`:

```rust
// In init_transfer, after computing the transfer_message:
let normalized = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

Alternatively, implement a cancel/refund function that allows the original sender to reclaim locked FT tokens for transfers that can never be signed.

## Proof of Concept
1. A NEAR token `foo.near` is registered with `origin_decimals = 24`; its EVM counterpart is deployed with `decimals = 18` (capped by `_normalizeDecimals`), giving `diff_decimals = 6`.
2. Alice calls `ft_transfer_call` transferring `500_000` base units with `fee = 0`. `init_transfer` accepts the transfer because `fee (0) < amount (500_000)`. Tokens are locked in the bridge contract.
3. A trusted relayer calls `sign_transfer`. `normalize_amount(500_000, diff_decimals=6)` = `500_000 / 1_000_000` = **0**. The `require!(amount_to_transfer > 0, ...)` guard fires and the call panics.
4. Step 3 repeats indefinitely — it always panics. Alice's `500_000` base units are permanently locked with no refund path.
