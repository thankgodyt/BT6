### Title
`update_transfer_fee` Allows Setting Fee Such That Normalized Transfer Amount Becomes Zero, Permanently Locking Bridged Tokens — (`File: near/omni-bridge/src/lib.rs`)

### Summary
`update_transfer_fee` permits the original sender to raise the token fee up to `amount - 1`. For tokens whose `origin_decimals` exceed the bridge's internal `decimals` (e.g., a 24-decimal NEAR token bridged to an 18-decimal EVM representation), `normalize_amount` performs floor division by `10^(origin_decimals - decimals)`. If the resulting `amount - fee` is smaller than that divisor, `normalize_amount` returns 0. The subsequent `require!(amount_to_transfer > 0)` guard in `sign_transfer` then permanently panics, and because fees can only increase and no cancellation path exists, the user's tokens are frozen in the bridge forever.

### Finding Description
`update_transfer_fee` enforces only:

```
fee.fee >= current_fee.fee && fee.fee < transfer.message.amount
``` [1](#0-0) 

This guarantees `amount - fee >= 1`, but does **not** guarantee that `normalize_amount(amount - fee) > 0`.

`normalize_amount` is:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [2](#0-1) 

`sign_transfer` then computes:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
``` [3](#0-2) 

where `amount_without_fee` is simply:

```rust
pub fn amount_without_fee(&self) -> Option<u128> {
    self.amount.0.checked_sub(self.fee.fee.0)
}
``` [4](#0-3) 

Because `update_transfer_fee` only enforces `fee < amount` (not `normalize_amount(amount - fee) > 0`), a sender can push the fee to `amount - k` for any `k < 10^(origin_decimals - decimals)`. After that update, every future call to `sign_transfer` will hit the `amount_to_transfer > 0` guard and panic. Fees can only be raised, never lowered, so the state is irreversible. No cancel or refund entry point exists in the contract.

### Impact Explanation
The user's tokens are transferred into the bridge at `ft_transfer_call` time and are held in the locker. Once the fee is raised into the "zero-normalized" zone, `sign_transfer` will always revert with `ERR_INVALID_AMOUNT_TO_TRANSFER`. The transfer record remains in `pending_transfers` indefinitely, and the locked tokens can never be released to the destination chain or returned to the sender. This constitutes **permanent freezing of bridged funds**.

### Likelihood Explanation
Any token pair where `origin_decimals > decimals` is affected (e.g., a NEAR-native 24-decimal token bridged to an 18-decimal EVM representation gives a divisor of 10^6). A sender who transfers a small amount (e.g., `amount = 5` in raw units) and then calls `update_transfer_fee` with `fee = 4` leaves `amount - fee = 1`, which normalizes to 0. The sender may do this accidentally (not understanding decimal normalization) or a malicious actor could socially engineer a victim into doing so. The same trap exists at `init_transfer` time without any fee update: a user who sends `amount = 1` with `fee = 0` for such a token pair creates an immediately uncompletable transfer.

### Recommendation
1. In `update_transfer_fee`, after computing the new fee, assert that `normalize_amount(amount - new_fee, decimals) > 0`.
2. In `init_transfer`, add the same check before storing the transfer message.
3. Alternatively, add a `cancel_transfer` entry point that allows the original sender to reclaim tokens from a pending transfer that can never be signed.

### Proof of Concept
**Setup:** Token registered with `origin_decimals = 24`, `decimals = 18` (divisor = 10^6).

1. User calls `ft_transfer_call` with `amount = 1_000_001` and `fee = 0`. Transfer is stored; tokens are locked.
2. User calls `update_transfer_fee` with `fee = Fee { fee: 1_000_000, native_fee: 0 }`. The check `1_000_000 < 1_000_001` passes. Fee is updated.
3. Relayer calls `sign_transfer`. Inside:
   - `amount_without_fee() = 1_000_001 - 1_000_000 = 1`
   - `normalize_amount(1, {origin=24, decimals=18}) = 1 / 10^6 = 0`
   - `require!(0 > 0)` → **panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`**
4. No further call can complete the transfer. The 1,000,001 raw tokens remain locked in the bridge permanently. [1](#0-0) [3](#0-2) [2](#0-1)
