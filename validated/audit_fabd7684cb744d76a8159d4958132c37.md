### Title
Missing BTC/ZEC Address Validation in `request_refund` Enables Attacker-Triggered Stuck Refund State - (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

The `request_refund` function stores a caller-supplied `refund_address` string without validating it as a valid BTC/ZEC address for the configured chain. Address validation only occurs later inside `execute_refund` → `build_refund_output`, which panics on an invalid address. Because the `deposit_msg` used to derive the deposit path is publicly broadcast via `LogDepositAddress` events, an attacker can submit a refund request for any unfinalized deposit with a malformed `refund_address`, permanently blocking `execute_refund` for that UTXO and requiring DAO/Operator intervention to reject the stuck request.

---

### Finding Description

**Root cause — no address validation at request time:**

In `internal_request_refund`, the `refund_address` parameter is accepted and forwarded to the callback without any format check: [1](#0-0) 

The only guard present is an equality check against `deposit_msg.refund_address` when that optional field is set: [2](#0-1) 

When `deposit_msg.refund_address` is `None` (the common case), **any string is accepted as `refund_address`**, including empty strings or garbage values.

**Stored without validation in the callback:**

`request_refund_callback` stores the raw string directly into `refund_requests` after the light-client proof succeeds: [3](#0-2) 

**Deferred panic in `execute_refund`:**

The first and only address parse attempt happens inside `build_refund_output`, called from `execute_refund`: [4](#0-3) 

`Address::parse(...).expect("Invalid refund address")` panics unconditionally for any malformed string, making every future call to `execute_refund` for this request revert. The request is never cleaned up automatically; only a DAO/Operator `reject_refund` call can remove it.

**Attacker entry path — `deposit_msg` is public:**

`get_user_deposit_address` emits a `LogDepositAddress` event containing the full `deposit_msg`: [5](#0-4) 

Any observer of the NEAR blockchain can read the `deposit_msg` for any deposit address ever queried. Combined with the publicly visible Bitcoin transaction and its Merkle proof, an attacker has all inputs needed to call `request_refund` on behalf of a victim's unfinalized deposit.

**`reject_refund` requires privilege when deposit is not yet finalized:** [6](#0-5) 

Until a relayer finalizes the deposit via `verify_deposit` (which adds the UTXO to `verified_deposit_utxo`), only DAO or Operator can reject the stuck request.

---

### Impact Explanation

An attacker-created refund request with an invalid `refund_address` causes `execute_refund` to panic on every invocation. The UTXO is held in the refund system and cannot be refunded until DAO/Operator manually rejects the request. This constitutes **attacker-triggered temporary locking of bridged funds** requiring operator intervention — a Medium-severity bridge impact per the defined scope.

---

### Likelihood Explanation

- The `deposit_msg` is publicly emitted on-chain for every deposit address query.
- Bitcoin transaction data and Merkle proofs are publicly available.
- The attacker only needs to pay the one-time anti-spam storage deposit (`required_balance_for_request_refund`).
- The attack applies to any deposit where `deposit_msg.refund_address` is `None` (the default for standard deposits).
- No privileged access is required.

Likelihood: **Medium**.

---

### Recommendation

Validate `refund_address` against the configured chain at the start of `internal_request_refund`, before the light-client cross-contract call is dispatched:

```rust
// In internal_request_refund, after the deposit_msg.refund_address equality check:
let config = self.internal_config();
crate::network::Address::parse(&refund_address, config.chain.clone())
    .unwrap_or_else(|e| env::panic_str(&format!("Invalid refund_address: {e}")));
```

This mirrors the existing validation pattern in `build_refund_output` and `string_to_script_pubkey`, and ensures a malformed address is rejected before any state is written or fees are consumed.

---

### Proof of Concept

1. User calls `get_user_deposit_address` with `deposit_msg = { recipient_id: "user.near", refund_address: None, ... }`. The `LogDepositAddress` event is emitted on-chain with the full `deposit_msg`.
2. User sends BTC to the derived deposit address. The deposit is not yet finalized by a relayer.
3. Attacker reads the `deposit_msg` from the on-chain event and fetches the BTC transaction + Merkle proof from the Bitcoin network.
4. Attacker calls `request_refund(deposit_msg, "NOT_A_VALID_BTC_ADDRESS", tx_bytes, vout, proof, None)` with the required storage deposit attached.
5. Light-client verification succeeds; `request_refund_callback` stores the request with `refund_address = "NOT_A_VALID_BTC_ADDRESS"`.
6. Any caller invokes `execute_refund(utxo_storage_key, None)` → reaches `build_refund_output` → `Address::parse("NOT_A_VALID_BTC_ADDRESS", ...)` → **panic: "Invalid refund address"**. The call reverts; the request remains.
7. The UTXO is stuck. Only DAO/Operator can call `reject_refund` to unblock it, after which a relayer must re-submit `verify_deposit` to finalize the original deposit.

    pub(crate) fn internal_request_refund(
        &self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<u128>,
    ) -> Promise {
        require!(
            env::attached_deposit() >= self.required_balance_for_request_refund(),
            "Insufficient deposit for storage"
        );
        require!(
            tx_bytes.0.len() <= MAX_REQUEST_REFUND_TX_BYTES,
            "tx_bytes too large for refund request"
        );
        if let Some(msg_refund_address) = &deposit_msg.refund_address {
            require!(
                msg_refund_address == &refund_address,
                "refund_address does not match deposit_msg.refund_address"
            );
        }

        let transaction =
            crate::WrappedTransaction::decode(&tx_bytes.0, &self.internal_config().chain)
                .expect("Deserialization tx_bytes failed");
        let tx_id = transaction.compute_txid().to_string();

        let config = self.internal_config();
        let deposit_amount = u128::from(transaction.output()[vout].value.to_sat());
        let confirmations = self.get_confirmations(config, deposit_amount);

        self.verify_transaction_inclusion_promise(
            config.btc_light_client_account_id.clone(),
            tx_id,
            proof.tx_block_blockhash,
            proof.tx_index,
            proof.merkle_proof,
            Some((proof.coinbase_tx_id, proof.coinbase_merkle_proof)),
            confirmations,
        )
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_REQUEST_REFUND_CALLBACK)
                .request_refund_callback(deposit_msg, refund_address, tx_bytes, vout, gas_fee),
        )
    }

    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
    }

    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
