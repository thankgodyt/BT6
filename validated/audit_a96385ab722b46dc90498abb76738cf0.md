Audit Report

## Title
Hard-Coded Zero-Amount Guard in `sign_transfer` Permanently Freezes User Funds When Decimal Normalization Rounds to Zero - (File: near/omni-bridge/src/lib.rs)

## Summary
In `near/omni-bridge/src/lib.rs`, `sign_transfer` applies a `require!(amount_to_transfer > 0)` guard after floor-dividing `amount_without_fee` by the decimal-precision gap between origin and destination chains. When the net amount is smaller than `10^(origin_decimals − dest_decimals)`, the guard panics unconditionally on every invocation. Because no cancel or user-initiated refund path exists, the locked tokens are permanently frozen inside the bridge contract.

## Finding Description
A user calls `ft_transfer_call` → `init_transfer`. The only fee validation at that stage is `fee.fee < amount`; there is no check that the normalized net amount is non-zero. [1](#0-0) 

Tokens are locked and a `TransferMessage` is stored in `pending_transfers`. A trusted relayer later calls `sign_transfer`, which computes: [2](#0-1) 

`normalize_amount` performs integer (floor) division. For a 24-decimal NEAR token bridging to a 6-decimal EVM token, any `amount_without_fee < 10^18` normalizes to 0, causing the `require!` to panic. Because the panic occurs before the MPC cross-contract call is dispatched, `sign_transfer_callback` is never reached, so the transfer is never removed from `pending_transfers`: [3](#0-2) 

`claim_fee_callback` also calls `remove_transfer_message`, but it requires a proof that the transfer was finalized on the destination chain — an event that can never occur if `sign_transfer` never succeeds: [4](#0-3) 

`update_transfer_fee` only allows the fee to be *increased* (new fee ≥ current fee), which shrinks `amount_without_fee` further and cannot rescue the transfer: [5](#0-4) 

No `cancel_transfer` or user-initiated refund function exists anywhere in the contract.

## Impact Explanation
User tokens are permanently frozen inside the bridge contract. The `pending_transfers` entry can never be removed because every removal path (`sign_transfer_callback` when `fee.is_zero()`, or `claim_fee_callback` after destination-chain proof) requires `sign_transfer` to succeed past the hard-coded guard, which it never will for this transfer. This matches the Critical allowed impact: **permanent freezing of bridged funds**.

## Likelihood Explanation
The condition is reachable by any unprivileged user through two realistic paths without any privileged access:

1. **Small transfer**: Sending fewer than `10^(origin_decimals − dest_decimals)` base units (e.g., < `10^18` yocto-units of a 24-decimal NEAR token to a 6-decimal EVM token).
2. **Fee near total**: Setting a fee that leaves a residual `amount_without_fee` below the precision threshold (e.g., amount = 1000, fee = 999, residual = 1, which normalizes to 0 across an 18-decimal gap).

Both paths are reachable via standard `ft_transfer_call` with no special role or access.

## Recommendation
1. **Validate at `init_transfer` time**: Compute the normalized `amount_without_fee` before locking tokens. If it is 0, reject the transfer immediately and return the tokens to the sender.
2. **Add a user-initiated cancel path**: Implement a `cancel_transfer` function allowing the original sender to reclaim tokens from a pending transfer that cannot be finalized (e.g., when the normalized amount is 0, or after a configurable timeout).

## Proof of Concept
1. Register token `T` with `origin_decimals = 24`, `decimals = 6` (18-decimal gap).
2. User calls `ft_transfer_call` on `T` with `amount = 500`, `fee = 499`, so `amount_without_fee = 1`.
3. `init_transfer` succeeds: 500 units of `T` are locked; `TransferMessage` is stored in `pending_transfers`. The only guard (`fee < amount`) passes.
4. Trusted relayer calls `sign_transfer`.
5. `normalize_amount(1, Decimals { decimals: 6, origin_decimals: 24 })` = `1 / 10^18` = `0` (floor division).
6. `require!(0 > 0, BridgeError::InvalidAmountToTransfer)` panics; the MPC call is never dispatched.
7. Every subsequent relayer call to `sign_transfer` for this `transfer_id` panics identically.
8. `claim_fee_callback` is unreachable (no destination-chain finalization proof exists).
9. The user's 500 units of `T` are permanently frozen with no recovery path.
