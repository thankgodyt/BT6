### Title
`chain_signatures_root_public_key` Cannot Be Updated After Initial Sync — (`contracts/satoshi-bridge/src/api/management.rs`)

---

### Summary

The `chain_signatures_root_public_key` field in `Config` is a one-way state transition: it starts as `None` at initialization, can be set exactly once via `sync_chain_signatures_root_public_key`, and can never be updated afterward. There is no force-update path and the field is absent from `ConfigUpdate`. If the NEAR chain-signatures MPC contract rotates its root public key, the bridge's stored key becomes permanently stale, breaking the entire withdrawal signing pipeline with no on-chain recovery path short of a full contract upgrade.

---

### Finding Description

**Initialization enforces `None`:** [1](#0-0) 

The contract is always initialized with `chain_signatures_root_public_key = None`.

**One-way sync with an irrevocable guard:** [2](#0-1) 

`sync_chain_signatures_root_public_key` hard-requires the field to be `None` before proceeding. Once the key is written, every subsequent call panics with `"Already sync"`. There is no `force_sync`, no `reset_chain_signatures_root_public_key`, and no override path.

**`ConfigUpdate` does not include the field:** [3](#0-2) 

Every other mutable config field is exposed through `ConfigUpdate` and the `update_config` management function. `chain_signatures_root_public_key` is the sole exception — it is structurally absent, so `update_config` cannot touch it.

**The field is stored in `Config` as `Option<PublicKey>`:** [4](#0-3) 

The `Option` wrapper implies the designers anticipated a lifecycle (`None` → `Some`), but the reverse or update direction (`Some(old)` → `Some(new)`) was never implemented.

---

### Impact Explanation

The `chain_signatures_root_public_key` is the cryptographic anchor used to verify that MPC signatures on outgoing Bitcoin/Zcash PSBTs were produced by the legitimate chain-signatures contract. If the MPC contract rotates its root public key (a normal operational event in threshold-signature systems), the bridge's stored key becomes permanently wrong. Every call to `sign_btc_transaction` and the downstream signing callbacks would fail signature verification, making it impossible to complete any withdrawal. User nBTC tokens are already transferred to the bridge at the start of the withdrawal flow; they cannot be recovered without a working signing path. The bridge enters a stuck state that requires a full contract upgrade to resolve — operator intervention that may take days and leaves user funds locked in the interim.

This matches the allowed Medium impact: **stuck bridge state requiring operator intervention**.

---

### Likelihood Explanation

NEAR's chain-signatures MPC network is an active, evolving system. Root public key rotation is a standard operational procedure for threshold-signature schemes (key refresh, participant set changes, security incidents). The bridge explicitly fetches and stores the key precisely because it changes — yet provides no mechanism to re-fetch it. Any key rotation event, however routine, permanently breaks the withdrawal pipeline for all users.

---

### Recommendation

Remove the `is_none()` guard from `sync_chain_signatures_root_public_key` (or add a separate `force_sync_chain_signatures_root_public_key` for the DAO), and add `chain_signatures_root_public_key` as an optional field in `ConfigUpdate` so it can be cleared or overridden directly:

```rust
// In ConfigUpdate
pub chain_signatures_root_public_key: Option<Option<PublicKey>>,

// In ConfigUpdate::apply
if let Some(v) = self.chain_signatures_root_public_key {
    config.chain_signatures_root_public_key = v;
}
```

Alternatively, drop the `"Already sync"` guard and allow `sync_chain_signatures_root_public_key` to overwrite the stored key unconditionally (still DAO-gated).

---

### Proof of Concept

1. DAO deploys the bridge and calls `sync_chain_signatures_root_public_key`. The field is set to `Some(old_key)`.
2. The NEAR chain-signatures MPC contract rotates its root public key to `new_key`.
3. DAO attempts to call `sync_chain_signatures_root_public_key` again — the call panics: `"Already sync"`.
4. DAO attempts `update_config` with a `ConfigUpdate` — `chain_signatures_root_public_key` is not a field in `ConfigUpdate`; the stored key is unchanged.
5. Any user initiating a withdrawal via `ft_transfer_call` → `ft_on_transfer` → `sign_btc_transaction` reaches the MPC signing step. The MPC contract now signs with `new_key`, but the bridge verifies against `old_key`. Signature verification fails; the withdrawal cannot complete.
6. The user's nBTC (already transferred to the bridge at step 5) is stuck. No withdrawal can succeed until a full contract upgrade is deployed and `migrate_state` is called.
