Audit Report

## Title
Missing `recipient` Validation in `initTransfer()` and `initTransfer1155()` Enables Permanent Freezing of Bridged Funds — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`OmniBridge.initTransfer()` and `initTransfer1155()` accept a `recipient` string parameter that is never validated before tokens are irreversibly burned or locked on the EVM side. An empty or malformed `recipient` string causes the relayer's `TryFromLog` parsing of the emitted `InitTransfer` event to fail, permanently blocking finalization on NEAR with no on-chain recovery path. This is not listed as a known issue in `evm/SECURITY.md`, unlike the analogous Solana acknowledgment in `solana/SECURITY.md`.

## Finding Description

`initTransfer` performs only a `fee >= amount` guard before burning or locking tokens and emitting `InitTransfer`:

```solidity
// OmniBridge.sol L373-437
function initTransfer(..., string calldata recipient, ...) external payable {
    currentOriginNonce += 1;
    if (fee >= amount) { revert InvalidFee(); }  // only guard
    // tokens burned/locked here
    emit BridgeTypes.InitTransfer(..., recipient, ...);  // emitted verbatim
}
```

The same omission exists in `initTransfer1155` (L439-490). No check on `bytes(recipient).length == 0` or structural validity exists in either function.

The relayer reads the emitted event and calls `TryFromLog<Log<InitTransfer>> for InitTransferMessage`, which at line 127 of `near/omni-types/src/evm/events.rs` does:

```rust
recipient: event.data.recipient.parse().map_err(stringify)?,
```

`OmniAddress::from_str` (near/omni-types/src/lib.rs L392-411) handles an empty string by falling back to `("eth", "")` via `split_once(':').unwrap_or(("eth", input))`, then attempts to parse `""` as an `H160` EVM address, which fails with `ERR_INVALID_HEX`. The `?` propagates the error, causing `TryFromLog` to return `Err`. The relayer cannot construct a valid `InitTransferMessage` and cannot submit a proof to NEAR. Every relayer attempt to finalize the transfer fails at this parsing stage.

The EVM contract has no admin rescue function and no refund path. `completedTransfers` (L44) is used only to prevent replay of `finTransfer`, not to enable refunds. `evm/CLAUDE.md` explicitly states as an invariant: "any missing or ambiguous field means lost funds."

## Impact Explanation

A user who calls `initTransfer` or `initTransfer1155` with `recipient = ""`:
1. Has tokens burned (`BridgeToken.burn`) or locked (`safeTransferFrom` into the contract) on EVM — irreversible.
2. Triggers an `InitTransfer` event with an empty recipient string.
3. Causes every relayer attempt to parse the event into `InitTransferMessage` to fail at `OmniAddress::from_str`.
4. Has no on-chain mechanism to recover the locked/burned tokens.

This constitutes **permanent freezing of bridged funds**, matching the Critical allowed impact: "Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds across NEAR, EVM..."

## Likelihood Explanation

Any unprivileged external user can call `initTransfer` directly. No admin compromise or privileged access is required. Realistic trigger paths include: a DApp or SDK bug passing an uninitialized recipient string; a user interacting directly via Etherscan who omits the field; or a programmatic integration that fails to populate the recipient before submission. The exploit is repeatable and requires no special conditions beyond holding tokens and calling the public function.

## Recommendation

Add an explicit non-empty check for `recipient` in both `initTransfer` and `initTransfer1155` before any token transfer occurs:

```solidity
error InvalidRecipient();

function initTransfer(..., string calldata recipient, ...) external payable {
+   if (bytes(recipient).length == 0) revert InvalidRecipient();
    if (fee >= amount) revert InvalidFee();
    // ...
}
```

Apply the same guard to `initTransfer1155`. Optionally, add a structural check (e.g., require a `:` separator) to reject malformed but non-empty strings. Document this in `evm/SECURITY.md` as a design invariant, mirroring the Solana acknowledgment pattern.

## Proof of Concept

```solidity
// User holds bridge tokens
BridgeToken(tokenAddress).approve(address(omniBridge), 1000);

// Call initTransfer with empty recipient — passes all existing checks
omniBridge.initTransfer(
    tokenAddress,
    1000,   // amount
    0,      // fee (0 < 1000, passes fee check)
    0,      // nativeFee
    "",     // recipient — empty, not validated
    ""      // message
);
// Tokens are now burned. InitTransfer event emitted with recipient="".
// Relayer calls TryFromLog → "".parse::<OmniAddress>() → split_once fails →
// falls back to ("eth","") → H160::from_str("") → ERR_INVALID_HEX → Err propagated.
// TryFromLog returns Err. No proof submitted to NEAR. Funds permanently frozen.
```

**Verification test plan**: Write a unit test in `near/omni-types/src/tests/` asserting that `"".parse::<OmniAddress>()` returns `Err`, and an integration test in `near/omni-tests/` that submits a mock `InitTransfer` log with `recipient = ""` and confirms `TryFromLog` returns an error, leaving no finalization path. # Security Notes

```markdown
## Design Decisions (Non-Issues)

These patterns have been reviewed and confirmed as intentional. Do not flag or "fix" them.

- **Fee-on-transfer tokens not supported**: `initTransfer` emits the requested `amount`, not the actual received balance. Fee-on-transfer and rebasing tokens are intentionally unsupported
- **`logMetadata` and `deployToken` are permissionless**: Anyone can call `logMetadata` for any ERC20, and anyone can submit a valid MPC signature to `deployToken`. This is by design — the bridge is fully permissionless
- **`ENearProxy.burn` uses empty NEAR recipient**: `eNear.transferToNear(amount, "")` is intentional — `transferToNear` is a legacy method used purely as a burn mechanism. The actual NEAR recipient is tracked in the OmniBridge `InitTransfer` event
- **`deployToken` signature has no chain ID**: Metadata signatures are intentionally chain-agnostic — one NEAR-side signature deploys the same token on all EVM chains

## Known Issues

Low-severity items acknowledged but not yet addressed:

- **`addCustomToken` can overwrite existing mappings** (H-01): Admin-only function. No existence check — calling with an already-mapped `nearTokenId` silently overwrites `nearToEthToken`. Accepted as operational risk
- **`pause(flags)` replaces all flags** (H-02): `_pause(flags)` does full replacement, not bitwise OR. Calling `pause(PAUSED_INIT_TRANSFER)` when `PAUSED_FIN_TRANSFER` is set will unpause finTransfer. Use `pauseAll()` for emergencies
- **`BridgeToken.initialize` stores metadata redundantly** (L-01): `__ERC20_init(name_, symbol_)` writes to parent storage that is never read (getters are overridden). Minor gas waste on init
- **`require` strings instead of custom errors** (L-02): Several locations use `require` with string messages instead of custom errors (`OmniBridge.sol:150,204,556`, `SelectivePausableUpgradable.sol:100,107`, `ENearProxy.sol:56,76,86`)
- **`OmniBridgeWormhole` has no `__gap`** (L-04): Three storage variables with no gap array. Safe as a leaf contract but would need a gap if inherited from
- **`PayloadType.ClaimNativeFee` defined but unused** (L-05): Enum value 2 is never referenced. Native fees are recovered via `finTransfer` with `tokenAddress=address(0)`
```
