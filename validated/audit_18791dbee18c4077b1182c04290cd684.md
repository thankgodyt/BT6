### Title
Silent Token Loss in `safe_mint` When Recipient Account Is Unregistered - (File: `contracts/nbtc/src/lib.rs`)

### Summary

`safe_mint` in the nBTC token contract mints tokens to the bridge's own account first, then silently returns `U128(0)` if the recipient's storage account does not exist — permanently locking the minted nBTC in the bridge's token balance with no user-accessible recovery path.

### Finding Description

In `contracts/nbtc/src/lib.rs`, `safe_mint` executes the following sequence:

1. Calls `self.token.internal_deposit(&self.bridge_id, amount.into())` — unconditionally crediting `amount` nBTC to the bridge's account inside the nBTC token contract.
2. Checks whether `account_id` (the intended recipient) has a registered storage account.
3. If the account is **not** registered, returns `PromiseOrValue::Value(U128(0))` immediately — with no refund, no error, and no entry in the `lost_found` map. [1](#0-0) 

The minted tokens remain credited to `self.bridge_id` inside the nBTC token contract. There is no code path that refunds the user, emits a recoverable event, or writes to `lost_found` for this case.

Compare this with the `transfer_nbtc_callback` in `contracts/satoshi-bridge/src/token_transfer.rs`, which **does** write to `lost_found` on failure: [2](#0-1) 

`safe_mint` has no equivalent safety net.

### Impact Explanation

Any nBTC minted via `safe_mint` for an unregistered recipient is permanently locked in the bridge's nBTC token balance. The user receives zero tokens and has no on-chain mechanism to claim or recover them. The bridge's nBTC balance silently inflates beyond what is owed to users, breaking the 1:1 BTC-to-nBTC backing invariant. This constitutes a **permanent loss of user funds**.

### Likelihood Explanation

A NEAR account that has never interacted with the nBTC token contract will not have a registered storage account. Any user who deposits BTC to the bridge but has not previously called `storage_deposit` on the nBTC contract is at risk. This is a realistic scenario for new users, and the failure is silent — the deposit transaction succeeds on-chain while the user receives nothing and sees no error.

### Recommendation

Replace the silent early-return with one of the following:

- **Register the account automatically** before minting (as `mint_inner` already does via `internal_register_account`): [3](#0-2) 

- **Or**, on detecting an unregistered account, write the minted amount to the bridge-side `lost_found` map (mirroring the pattern in `transfer_nbtc_callback`) so the user can later claim their tokens after registering storage.

### Proof of Concept

1. User deposits BTC to the bridge. Their NEAR account (`alice.near`) has never called `storage_deposit` on the nBTC contract.
2. The bridge calls `safe_mint(alice.near, 100_000, None)`.
3. `internal_deposit(&self.bridge_id, 100_000)` executes — 100,000 nBTC are credited to the bridge's account in the nBTC token.
4. `self.token.accounts.get(&alice.near)` returns `None`.
5. The function returns `U128(0)`. No transfer occurs. No `lost_found` entry is created.
6. Alice's 100,000 nBTC are permanently locked in the bridge's nBTC balance. Alice has no on-chain path to recover them. [4](#0-3)

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }
