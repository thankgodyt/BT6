### Title
Orchard Bundle ZK Proof Never Verified On-Chain; Invalid Proof Permanently Locks Bridge UTXOs — (File: `contracts/satoshi-bridge/src/zcash_utils/orchard_policy.rs`)

---

### Summary

The bridge validates Orchard bundle *policy* components (recipient address, value balance) but never verifies the embedded Halo2 ZK proof or binding signature. Any unprivileged user can submit a withdrawal with a syntactically valid but cryptographically invalid Orchard bundle. The bridge accepts it, burns nZEC, and the MPC signs the transaction. The Zcash network then rejects the transaction, leaving bridge UTXOs locked in a pending withdrawal state that requires privileged operator intervention to resolve.

---

### Finding Description

In `orchard_policy.rs`, `extract_orchard_bundle` (lines 38–78) deserializes the bundle via `read_v5_bundle` and recovers the output using the hardcoded `BRIDGE_OVK = [0u8; 32]`. `validate_orchard_bundle` (lines 86–117) then checks the recipient address and value balance. Neither function calls `bundle.verify_proof(vk)` or verifies the binding signature. The Halo2 proof embedded in the `Authorized` bundle is never cryptographically verified by the bridge contract.

The bridge accepts the bundle based solely on:

1. Successful deserialization
2. Action count == `EXPECTED_ACTIONS_NUMBER` (1)
3. Output recoverable with `BRIDGE_OVK`
4. Recovered recipient matches expected address
5. `value_balance == -amount` [1](#0-0) 

None of these checks verify the ZK proof. This is the direct analog to the Fiat-Shamir transcript incompleteness described in the external report: the verifier checks some components (policy fields) but omits the critical cryptographic component (the proof itself). An attacker can freely choose the proof bytes after observing the policy constraints, exactly as the external report describes choosing omitted algebraic components after seeing the challenge.

The `ProofSizeEnforcement` parameter passed to `read_v5_bundle` only controls whether the proof *size* is checked during deserialization — it does not cryptographically verify the proof. [2](#0-1) 

The validation path in `validate_orchard_bundle` checks recipient and value balance but has no call to any proof verification routine: [3](#0-2) 

The bundle reaches this validation path through `check_psbt_chain_specific` in `contract_methods.rs`, which is called during the withdrawal flow initiated by any token holder via `ft_transfer_call`: [4](#0-3) 

Recovery from a stuck withdrawal requires `cancel_withdraw`, which is gated behind `Role::DAO` or `Role::Operator`: [5](#0-4) 

---

### Impact Explanation

**Medium — attacker-triggered temporary locking of bridged funds.**

When the Zcash network rejects the transaction due to an invalid proof, the bridge UTXOs committed to that pending withdrawal are stuck. The nZEC has already been burned. No automatic recovery exists; only a privileged `cancel_withdraw` call by DAO/Operator can free the UTXOs. An attacker who repeats this pattern across multiple withdrawals can progressively exhaust available bridge UTXOs, degrading or halting bridge operations for all users until operators intervene for each stuck withdrawal.

---

### Likelihood Explanation

**Medium.** The attack entry point is the standard public withdrawal flow (`ft_transfer_call` → `ft_on_transfer` → `ft_on_transfer_callback`), reachable by any nZEC holder. The attacker must burn nZEC to initiate each attack, but if the operator refunds nZEC via the `lost_found` / `cancel_withdraw` path, the attacker recovers their tokens and can repeat. The only cost is gas and the time their nZEC is temporarily locked.

---

### Recommendation

- If on-chain Halo2 proof verification is computationally feasible on NEAR, call `bundle.verify_proof(vk)` inside `extract_orchard_bundle` before accepting the bundle.
- If on-chain proof verification is not feasible, implement an automatic, permissionless recovery path for withdrawals whose Zcash transactions have been pending beyond a configurable timeout, so users can self-recover without operator intervention.
- Add a negative test that provides a bundle with a valid policy but corrupted proof bytes and asserts the withdrawal is rejected or recoverable.

---

### Proof of Concept

1. Attacker holds nZEC and calls `ft_transfer_call` on the nZEC contract with a `WithdrawMsg` containing a `ChainSpecificData` whose `orchard_bundle_bytes` encodes a bundle where:
   - Action count = 1
   - Output is encrypted with `BRIDGE_OVK` (all zeroes, publicly known)
   - Recovered recipient = attacker's own Orchard address
   - `value_balance` = `-withdrawal_amount` (matches nZEC burned)
   - Halo2 proof bytes = 32 bytes of `0xFF` (random garbage)
2. `extract_orchard_bundle` deserializes the bundle — passes (deserialization succeeds, size check passes).
3. `validate_orchard_bundle` checks recipient and value balance — passes (policy is valid).
4. Bridge burns nZEC and creates a `BTCPendingInfo` entry committing the selected UTXOs.
5. MPC signs the Zcash transaction containing the invalid proof.
6. Relayer broadcasts the transaction to the Zcash network.
7. Zcash network rejects the transaction (Halo2 proof verification fails).
8. Bridge UTXOs remain locked in the pending withdrawal; nZEC is already burned.
9. Only DAO/Operator can call `cancel_withdraw` to free the UTXOs.
10. After operator intervention refunds nZEC via `lost_found`, attacker repeats from step 1.

pub fn extract_orchard_bundle(
    orchard_bundle_bytes: Option<Vec<u8>>,
    proof_size_enforcement: ProofSizeEnforcement,
) -> Result<Option<ParsedOrchardBundle>, String> {
    if let Some(orchard_bundle_bytes) = orchard_bundle_bytes {
        let mut reader = Cursor::new(orchard_bundle_bytes);
        let bundle = read_v5_bundle(&mut reader, proof_size_enforcement)
            .map_err(|_| "Failed to read orchard bundle".to_string())?
            .ok_or_else(|| "Orchard bundle is empty".to_string())?;

        // Check action count first per Orchard protocol requirements
        if bundle.actions().len() != EXPECTED_ACTIONS_NUMBER {
            return Err(format!(
                "Orchard bundle must have {} actions, got {}",
                EXPECTED_ACTIONS_NUMBER,
                bundle.actions().len()
            ));
        }

        // Since we require exactly 1 action, directly recover the single output
        let ovk = orchard::keys::OutgoingViewingKey::from(BRIDGE_OVK);
        let (note, addr, _memo) = bundle
            .recover_output_with_ovk(0, &ovk)
            .ok_or_else(|| "Failed to recover Orchard output with bridge OVK".to_string())?;

        let value = note.value().inner();
        if value == 0 {
            return Err("Orchard output value must be non-zero".to_string());
        }

        Ok(Some(ParsedOrchardBundle {
            bundle,
            output: OrchardOutput {
                amount: value,
                recipient_addr: addr.to_raw_address_bytes(),
            },
        }))
    } else {
        Ok(None)
    }
}

pub fn validate_orchard_bundle(
    orchard: &ParsedOrchardBundle,
    expected_recipient: &str,
    chain: &Chain,
) -> Result<(), String> {
    let recipient_address = Address::parse(expected_recipient, chain.clone())?;

    // Validate recipient
    let expected_addr_bytes = recipient_address.extract_orchard_receiver()?;
    if orchard.recipient_addr() != &expected_addr_bytes {
        return Err(format!(
            "Orchard recipient mismatch: expected {} does not match recovered output",
            expected_recipient
        ));
    }

    // Validate value balance: for withdrawal, value flows FROM transparent TO Orchard
    // So value_balance should be negative and equal to the output amount
    let value_balance = orchard.bundle.value_balance();
    let expected_value_balance =
        -i64::try_from(orchard.amount()).map_err(|_| "Orchard amount too large for i64")?;

    let actual_value_balance: i64 = (*value_balance).into();
    if actual_value_balance != expected_value_balance {
        return Err(format!(
            "Orchard value balance mismatch: expected {}, got {}. \
             Value balance must equal negative output amount for withdrawals",
            expected_value_balance, actual_value_balance
        ));
    }

    Ok(())

    pub(crate) fn check_psbt_chain_specific(
        &self,
        psbt: &PsbtWrapper,
        gas_fee: u128,
        target_btc_address: String,
    ) {
        let min_fee = psbt.get_min_fee();
        require!(
            gas_fee >= min_fee.into_u64() as u128,
            format!(
                "Invalid gas fee ({}). min fee = {}.",
                gas_fee,
                min_fee.into_u64()
            )
        );

        // For withdrawals with Orchard bundle, calculate the expected net amount after fees
        if psbt.has_orchard_bundle() {
            psbt.validate_orchard_bundle(target_btc_address, self.internal_config().chain.clone());
        }
    }
