Audit Report

## Title
Permanent Fund Loss When `normalize_amount` Returns Zero in `sign_transfer` After Tokens Are Already Burned/Locked — (File: `near/omni-bridge/src/lib.rs`)

## Summary
The NEAR Omni Bridge burns or locks user tokens inside `init_transfer_internal` before any decimal-normalization check is performed. When the transfer amount (minus fee) is below the normalization divisor, `normalize_amount` returns `0` via floor division, causing `sign_transfer` to panic with `InvalidAmountToTransfer`. Because no public cancel or refund path exists for stuck pending transfers, the user's tokens are permanently lost.

## Finding Description
`normalize_amount` (L2784–2787) performs floor division:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

If `amount < 10^(origin_decimals − decimals)`, the result is `0`.

`init_transfer_internal` (L1850–1857) burns or locks the full token amount unconditionally:

```rust
if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
    self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
    self.lock_tokens_if_needed(...);
}
```

`burn_tokens_if_needed` (L1806–1812) uses `.detach()`, making the burn fire-and-forget — it is dispatched and cannot be rolled back once `init_transfer_internal` returns successfully.

The only zero-amount guard is in `sign_transfer` (L482–485), which executes **after** the irreversible burn/lock:

```rust
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

`init_transfer` (L554–557) only validates `fee < amount`; it does not check that `normalize_amount(amount − fee, decimals) > 0`. No public `cancel_transfer` or refund function exists for transfers stuck in `pending_transfers`. The code comment at L2781–2783 acknowledges "dust stays locked/burned" but does not address the case where the entire normalized amount is zero.

## Impact Explanation
A user sending fewer than `10^(origin_decimals − decimals)` base units has their tokens permanently burned or locked on NEAR with no ability to complete the transfer or recover funds. This is **permanent freezing of bridged funds**, matching the Critical allowed impact: *"permanent freezing of bridged funds across NEAR … flows."*

## Likelihood Explanation
Any token configuration where `origin_decimals > decimals` (e.g., `origin_decimals = 24`, `decimals = 18`, divisor = `10^6`) creates this condition. A user sending fewer than `1,000,000` base units — a realistic "dust" or mistaken amount — triggers the bug through the standard public `ft_transfer_call` → `init_transfer` flow, requiring no privileged access. The trusted relayer calling `sign_transfer` is a normal operational step, not an attacker action.

## Recommendation
Add a normalization check in `init_transfer` (or `init_transfer_internal`) **before** burning or locking tokens:

```rust
let token_address = self.get_token_address(
    init_transfer_msg.get_destination_chain(),
    token_id.clone(),
).near_expect(BridgeError::FailedToGetTokenAddress);

let decimals = self.token_decimals
    .get(&token_address)
    .near_expect(BridgeError::TokenDecimalsNotFound);

let normalized = Self::normalize_amount(
    amount.0 - init_transfer_msg.fee.0,
    decimals,
);
require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

This mirrors the guard already present in `sign_transfer` but places it before the irreversible token burn/lock step.

## Proof of Concept
1. Register a token with `origin_decimals = 24`, `decimals = 18` (divisor = `10^6`).
2. User calls `ft_transfer_call` with `amount = 500_000` and `fee = 0`.
3. `init_transfer_internal` is reached; `burn_tokens_if_needed` dispatches a detached burn of `500_000` units — irreversible.
4. Transfer message is stored in `pending_transfers` with `origin_nonce = N`.
5. Trusted relayer calls `sign_transfer(transfer_id = N, ...)`.
6. `normalize_amount(500_000, Decimals { decimals: 18, origin_decimals: 24 })` → `500_000 / 1_000_000 = 0`.
7. `require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer)` panics — transaction aborted.
8. Transfer message remains in `pending_transfers` indefinitely; user's `500_000` units are permanently burned with no recovery path. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
