### Title
Sequential `origin_nonce` Not Bound to Transfer Content Enables Permanent Fund Loss After EVM Re-org — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`, `near/omni-bridge/src/lib.rs`)

### Summary

The EVM bridge assigns a purely sequential `currentOriginNonce` to every `initTransfer()` call. NEAR uses `TransferId` — which encodes `(origin_chain, origin_nonce)` — as the sole replay-protection key in `finalised_transfers`. Because the nonce is not bound to transfer content, an EVM re-org that drops one user's transaction and causes a second user's transaction to inherit the same nonce will permanently lock the second user's funds: NEAR has already marked that nonce as finalised and will reject any future proof for it.

### Finding Description

**EVM side — sequential nonce assignment:**

In `OmniBridge.sol::initTransfer()`, the nonce counter is incremented unconditionally before any transfer-specific data is recorded: [1](#0-0) 

```solidity
currentOriginNonce += 1;
```

The emitted `InitTransfer` event carries this nonce as the canonical identifier of the transfer: [2](#0-1) 

The nonce is a bare counter with no cryptographic binding to the token address, amount, recipient, or sender.

**NEAR side — nonce-keyed replay protection:**

The NEAR bridge stores finalised transfers in a set keyed by `TransferId`: [3](#0-2) 

`TransferId` encodes `(origin_chain, TransferIdKind::Nonce(origin_nonce))`, as confirmed by the V1 migration path in `storage.rs`: [4](#0-3) 

Once a `(origin_chain, origin_nonce)` pair is inserted into `finalised_transfers`, any subsequent `fin_transfer` call carrying the same pair is rejected — regardless of whether the underlying transfer content has changed due to a re-org.

**Wormhole path amplifies the risk:**

`OmniBridgeWormhole.sol` publishes an `InitTransfer` Wormhole message immediately after the EVM transaction executes, using a configurable `_consistencyLevel`: [5](#0-4) 

If `_consistencyLevel` is set to a low value (e.g., 1 confirmation), Wormhole guardians can issue a VAA for a transaction that is subsequently re-orged away. That VAA remains cryptographically valid and can be submitted to NEAR, which will accept it and permanently mark the nonce as used.

### Impact Explanation

After a re-org on a supported EVM chain:

1. User A's `initTransfer()` (nonce = N) is included in a block; a Wormhole VAA or light-client proof is generated and submitted to NEAR; NEAR finalises the transfer and inserts `(Eth, N)` into `finalised_transfers`.
2. The re-org drops User A's block. User B's independent `initTransfer()` is now assigned nonce = N on the canonical chain.
3. The relayer submits a proof for User B's transfer. NEAR rejects it: `(Eth, N)` is already finalised.
4. User B's tokens are permanently locked in the EVM bridge contract with no recovery path.

This is a **critical, permanent loss of bridged funds** for User B, caused entirely by the bridge's design choice to use a content-free sequential counter as the cross-chain identifier.

### Likelihood Explanation

EVM chains in the bridge's supported set — particularly Polygon — have experienced multi-block re-orgs in production (a 157-block re-org occurred at block 39,599,624). For Wormhole-integrated chains with a low `_consistencyLevel`, the VAA can be issued within one confirmation, making the timing window between proof acceptance on NEAR and re-org detection realistic. The scenario requires only two independent users calling `initTransfer()` in close succession, which is normal bridge activity.

### Recommendation

Replace the purely sequential `origin_nonce` with a content-bound identifier. For example, compute the transfer ID as:

```
keccak256(abi.encode(sender, tokenAddress, amount, fee, recipient, currentOriginNonce))
```

and require the relayer to supply this hash alongside the nonce when submitting proofs to NEAR. NEAR should verify that the hash matches the proven event data before inserting it into `finalised_transfers`. This ensures that even if a re-org causes a different transfer to occupy the same sequential slot, its content-hash will differ and it can still be finalised independently.

### Proof of Concept

```
Block B1 (EVM):
  User A calls initTransfer(USDC, 1000, ...) → currentOriginNonce = 5
  Wormhole VAA issued (consistencyLevel = 1)

NEAR:
  Relayer submits VAA → fin_transfer_callback accepts it
  finalised_transfers.insert((Eth, 5))  ← nonce 5 permanently consumed
  User A receives 1000 USDC on NEAR ✓

Re-org: Block B1 is dropped from the canonical EVM chain.

Block B1' (EVM, canonical):
  User B calls initTransfer(USDC, 500, ...) → currentOriginNonce = 5
  (same nonce, different content, different recipient)

NEAR:
  Relayer submits proof for User B's transfer
  fin_transfer_callback: finalised_transfers.contains((Eth, 5)) == true
  → PANIC / reject
  User B's 500 USDC permanently locked in OmniBridge.sol ✗

        require!(
            self.factories
                .get(&init_transfer.emitter_address.get_chain())
                == Some(init_transfer.emitter_address),

        let transfer_message = TransferMessage {

            token: init_transfer.token,
            amount: Self::denormalize_amount(init_transfer.amount.0, decimals).into(),
            recipient: init_transfer.recipient,
            fee: Self::denormalize_fee(&init_transfer.fee, decimals),
            sender: init_transfer.sender,
            msg: init_transfer.msg,
            destination_nonce,
            origin_transfer_id: None,
        };

        if let OmniAddress::Near(recipient) = transfer_message.recipient.clone() {
            self.process_fin_transfer_to_near(

                &predecessor_account_id,

                storage_deposit_actions,
            )
            .into()

            self.process_fin_transfer_to_other_chain(predecessor_account_id, transfer_message);
            PromiseOrValue::Value(destination_nonce)
        }
    }
