### Title
Return Type Mismatch in `NBtc` Ext-Contract Trait `safe_mint` Declaration — (File: `contracts/satoshi-bridge/src/nbtc/mod.rs`)

---

### Summary
The `NBtc` ext-contract trait used by the bridge declares `safe_mint` with an implicit `()` return type, but the actual `nbtc` contract's `safe_mint` implementation returns `PromiseOrValue<U128>`. This interface/implementation mismatch prevents the bridge from observing the actual return value of `safe_mint`, making it blind to the case where no tokens were transferred to the user (unregistered account), while tokens have already been minted into the bridge's own nbtc balance.

---

### Finding Description

In `contracts/satoshi-bridge/src/nbtc/mod.rs`, the `NBtc` ext-contract trait declares `safe_mint` with no return type (implicitly `()`):

```rust
fn safe_mint(&mut self, account_id: AccountId, amount: U128, msg: Option<String>);
``` [1](#0-0) 

But in `contracts/nbtc/src/lib.rs`, the actual implementation returns `PromiseOrValue<U128>`:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
``` [2](#0-1) 

The `safe_mint` body first mints tokens unconditionally into the bridge's own nbtc balance, then checks whether the recipient account is registered:

```rust
self.token.internal_deposit(&self.bridge_id, amount.into());

if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0));
}
``` [3](#0-2) 

When the recipient account is not registered, `safe_mint` returns `U128(0)` — tokens are already minted into the bridge's nbtc balance but are **not** forwarded to the user. Because the bridge's ext-contract trait declares the return type as `()`, the bridge has no mechanism to read this return value and cannot distinguish a successful transfer from a silent no-op.

The bridge's deposit flow calls `safe_mint` from `contracts/satoshi-bridge/src/btc_light_client/deposit.rs` (4 call sites). The main `mint` path in `contracts/satoshi-bridge/src/nbtc/mint.rs` uses `mint()` and chains a `mint_callback` that checks `is_promise_success()`: [4](#0-3) 

`is_promise_success()` only detects panics — it returns `true` even when `safe_mint` silently returns `U128(0)`. The bridge therefore cannot detect the stuck-token condition.

---

### Impact Explanation

When `safe_mint` is called for an account that has not registered storage with the nbtc contract:
1. Tokens are minted into the bridge's own nbtc balance.
2. `safe_mint` returns `U128(0)` — no tokens reach the user.
3. The bridge cannot detect this because the ext-contract trait declares return type `()`.
4. Any callback using `is_promise_success()` returns `true` (no panic occurred).
5. The bridge proceeds as if the mint succeeded; user tokens are permanently stuck in the bridge's nbtc balance until operator intervention.

This matches: **Medium — broken callback rollback or stuck bridge state requiring operator intervention.**

---

### Likelihood Explanation

Medium. `safe_mint` is called from the deposit flow (4 call sites in `btc_light_client/deposit.rs`). Any new user who has not pre-registered storage with the nbtc contract — a realistic scenario for first-time bridge users — triggers this silent failure path. No attacker action is required; ordinary bridge usage is sufficient.

---

### Recommendation

Update the `NBtc` ext-contract trait to match the actual return type of `safe_mint`:

```rust
fn safe_mint(&mut self, account_id: AccountId, amount: U128, msg: Option<String>) -> PromiseOrValue<U128>;
``` [5](#0-4) 

Then update all call sites in the deposit flow to chain a callback that reads the return value and, when `U128(0)` is returned, either refunds the user or records the amount in the `lost_found` map already present in `ContractData`: [6](#0-5) 

---

### Proof of Concept

1. User sends BTC to a deposit address; relayer submits a valid inclusion proof to the bridge.
2. Bridge calls `ext_nbtc::ext(...).safe_mint(user_account_id, amount, msg)`.
3. `nbtc` contract executes: mints `amount` tokens into `bridge_id`'s balance, then checks `user_account_id` storage registration.
4. `user_account_id` has no registered storage → `safe_mint` returns `PromiseOrValue::Value(U128(0))`.
5. Bridge callback (if any) calls `is_promise_success()` → `true` (no panic).
6. Bridge records the deposit as successful; user receives zero tokens.
7. `amount` nBTC sits permanently in the bridge's own nbtc balance, inaccessible to the user without operator action.
