### Title
Missing Caller Validation in `sign_btc_transaction` Allows Any Account to Corrupt Pending Transaction Signatures — (File: `contracts/satoshi-bridge/src/api/chain_signatures.rs`)

---

### Summary

The public `sign_btc_transaction` function performs no check that the caller is the owner of the referenced pending transaction. Any unprivileged NEAR account can invoke it against any pending withdrawal or refund, supplying an attacker-controlled `key_version`. The MPC service signs with whatever key version is given; the resulting (invalid) signature is stored and the slot is permanently marked "Already signed." The legitimate owner can never overwrite it, the resulting Bitcoin transaction is unbroadcastable, and the user's nBTC remains locked inside the bridge contract.

---

### Finding Description

`sign_btc_transaction` in `contracts/satoshi-bridge/src/api/chain_signatures.rs` carries only `#[payable]` and `#[pause]` guards: [1](#0-0) 

There is no `#[trusted_relayer]`, no `#[access_control_any]`, and no runtime check that `env::predecessor_account_id()` equals `btc_pending_info.account_id`. Compare every other privileged bridge entry-point — `cancel_withdraw`, `active_utxo_management`, `verify_withdraw_v2` — which all carry explicit role guards or relayer restrictions. [2](#0-1) 

The internal signing path forwards the caller-supplied `key_version` directly to the MPC service and attaches whatever NEAR deposit the caller provides: [3](#0-2) 

The callback stores the returned signature unconditionally and marks the slot occupied: [4](#0-3) 

Once stored, the slot is permanently locked — a second call for the same index panics with "Already signed": [5](#0-4) 

When all slots are filled (even with wrong-key signatures), the pending info transitions to `PendingVerify` stage and `tx_bytes_with_sign` is set: [6](#0-5) 

The resulting Bitcoin transaction carries signatures produced under the wrong derivation key and will be rejected by the Bitcoin network. `verify_withdraw` can never succeed for it, so the user's nBTC — already held by the bridge after `ft_on_transfer` — remains locked. [7](#0-6) 

---

### Impact Explanation

**Medium — attacker-triggered temporary locking of bridged funds requiring operator intervention.**

The user's nBTC is transferred to the bridge contract at withdrawal initiation and is only burned upon successful `verify_withdraw`. If the pending transaction is corrupted before signing completes, the nBTC is stuck. Recovery requires a DAO/Operator call to `cancel_withdraw`: [8](#0-7) 

For refund transactions the user can call `execute_refund` again to create a fresh pending info, but the corrupted entry persists in storage and counts against pending-sign capacity, potentially blocking re-execution. [9](#0-8) 

---

### Likelihood Explanation

**Medium.** The `btc_pending_sign_id` is emitted publicly in `Event::GenerateBtcPendingInfo` immediately after a withdrawal or refund is initiated, so any on-chain observer can obtain it. The attacker must attach a small NEAR deposit to cover the MPC signing fee, which is a trivial cost. No privileged access, leaked key, or social engineering is required. [10](#0-9) 

---

### Recommendation

Add an ownership check at the top of `sign_btc_transaction` before any state mutation or cross-contract call:

```rust
pub fn sign_btc_transaction(
    &mut self,
    btc_pending_sign_id: String,
    sign_index: usize,
    key_version: u32,
) -> PromiseOrValue<bool> {
    let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
    // ADD: caller must be the owner of this pending transaction
    require!(
        env::predecessor_account_id() == btc_pending_info.account_id,
        "Only the transaction owner may sign"
    );
    btc_pending_info.assert_pending_sign();
    // ... rest unchanged
}
```

Alternatively, restrict the function to trusted relayers or a designated operator role, consistent with the pattern used by `verify_withdraw_v2` and `verify_deposit_v2`.

---

### Proof of Concept

1. Alice calls `ft_transfer_call(bridge, 1_000_000, '{"Withdraw": {...}}')`. The bridge's `ft_on_transfer` creates a `BTCPendingInfo` with `account_id = alice` and emits `GenerateBtcPendingInfo { btc_pending_id: "abcd1234..." }`.

2. Attacker Bob observes the event on-chain and immediately calls:
   ```
   sign_btc_transaction(
       btc_pending_sign_id = "abcd1234...",
       sign_index = 0,
       key_version = 999,   // wrong version
   )
   ```
   attaching enough NEAR for the MPC fee.

3. The MPC service signs the PSBT sighash under key version 999 (a different derivation path than the bridge's actual key). The callback stores this signature at `signatures[0]` and marks it occupied.

4. Alice now calls `sign_btc_transaction("abcd1234...", 0, 0)`. The callback panics: `"Already signed"`. Alice cannot complete her withdrawal.

5. If the pending info has only one input, it is now in `PendingVerify` stage with an invalid signature. `verify_withdraw` will never succeed because the Bitcoin network rejects the transaction. Alice's nBTC is locked in the bridge until a DAO/Operator calls `cancel_withdraw`. [11](#0-10) [12](#0-11) [4](#0-3)

    pub fn internal_sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> Promise {
        let pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);

        let public_keys: Vec<_> = pending_info
            .vutxos
            .iter()
            .map(|vutxo| self.generate_btc_public_key(&vutxo.get_path()))
            .collect();

        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        require!(
            btc_pending_info.signatures[sign_index].is_none(),
            "Already signed"
        );
        let payload = btc_pending_info
            .get_psbt()
            .get_hash_to_sign(sign_index, &public_keys);
        let path = btc_pending_info.vutxos[sign_index].get_path();
        self.sign_promise(SignRequest {
            payload,
            path,
            key_version,
        })
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_SIGN_BTC_TRANSACTION_CALL_BACK)
                .sign_btc_transaction_callback(
                    btc_pending_info.account_id.clone(),
                    btc_pending_sign_id,
                    sign_index,
                ),
        )
    }
