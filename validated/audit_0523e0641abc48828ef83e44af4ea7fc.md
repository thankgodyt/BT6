### Title
Unguarded `request_refund` Allows Attacker to Hijack Victim's Refund Address and Block Legitimate Refund Requests — (File: `contracts/satoshi-bridge/src/refund.rs`)

### Summary

Any unprivileged caller can invoke `request_refund` for a victim's deposit UTXO and supply an attacker-controlled `refund_address`. Because the contract enforces a one-request-per-UTXO invariant, the legitimate depositor is permanently blocked from submitting their own refund request. If the DAO/Operator does not reject the attacker's request within `unsafe_refund_timelock_sec`, the full deposit is sent to the attacker's Bitcoin address.

### Finding Description

`internal_request_refund` (the shared implementation behind the public `request_refund` entrypoint) accepts a caller-supplied `refund_address` with no restriction on who the caller is: [1](#0-0) 

When `deposit_msg.refund_address` is `None` (the common case — users who did not pre-authorize a refund address on-chain), the only check is that the output script of the supplied transaction matches the deposit address derived from `deposit_msg`. Both the `deposit_msg` and the raw transaction bytes are public data on the Bitcoin blockchain, so any observer can reconstruct them.

After the light-client callback succeeds, `request_refund_callback` stores the `RefundRequest` keyed by `utxo_storage_key` and then enforces a hard uniqueness constraint: [2](#0-1) 

Once the attacker's request is stored, the legitimate depositor's subsequent `request_refund` call will always revert with `"Refund request already exists for this UTXO"`. The attacker's `refund_address` is now the only address recorded in the stored `RefundRequest`: [3](#0-2) 

When `execute_refund` is later called, `resolve_execute_refund_timelock` applies the longer `unsafe_refund_timelock_sec` (because `deposit_msg.refund_address` is `None`), giving the DAO a window to reject: [4](#0-3) 

However, the DAO rejection is an off-chain, manual, reactive control. If the DAO misses the window, `execute_refund` builds and signs a Bitcoin transaction paying the attacker's address, and `finalize_refund_with_psbt` marks the UTXO as verified, permanently blocking any future `verify_deposit` for the same UTXO: [5](#0-4) 

### Impact Explanation

**DoS (certain):** The legitimate depositor can never submit their own refund request once the attacker's request is stored. Their deposit is stuck until the DAO manually rejects the attacker's request.

**Theft (conditional):** If the DAO does not reject within `unsafe_refund_timelock_sec`, `execute_refund` constructs a Bitcoin transaction paying the attacker's address. After on-chain confirmation and `verify_refund_finalize`, the deposit is permanently lost to the attacker. This constitutes a significant loss of user funds.

This matches the allowed impact: *"Medium. Attacker-triggered temporary locking of bridged funds"* (DoS path) and *"Critical. Significant loss, theft, destruction, or permanent locking of user or protocol funds"* (theft path).

### Likelihood Explanation

- The attack requires only a small NEAR storage deposit and knowledge of the victim's `deposit_msg` and raw transaction bytes — both are public on the Bitcoin blockchain.
- No privileged role, leaked key, or third-party compromise is needed.
- The attacker can monitor the Bitcoin mempool and submit the malicious `request_refund` before the legitimate user does (frontrunning on NEAR).
- The DAO rejection window is the only mitigation, and it is a reactive, manual process that can be overwhelmed or missed.

### Recommendation

**Option 1 (Preferred):** Require that the caller of `request_refund` is the `deposit_msg.recipient_id` when `deposit_msg.refund_address` is `None`. This mirrors the "Option 2" fix from the reference report — requiring consent from the receiver on the first action.

**Option 2:** Require `deposit_msg.refund_address` to always be set (non-`None`) so the refund destination is committed at deposit time and cannot be overridden by a third party.

**Option 3:** Allow multiple competing refund requests per UTXO but only permit `execute_refund` to be called by the original `request_refund` submitter, and let the DAO select the canonical one.

### Proof of Concept

1. Alice deposits BTC to the bridge using a `deposit_msg` with `refund_address: None` and `recipient_id: alice.near`.
2. The deposit is confirmed on Bitcoin. Alice's `deposit_msg` and raw transaction bytes are visible on-chain.
3. Before Alice calls `request_refund`, Bob (attacker) calls `request_refund` with:
   - The correct `deposit_msg` (copied from Bitcoin chain data)
   - The correct `tx_bytes` and `vout`
   - `refund_address` = Bob's Bitcoin address
4. The light-client proof passes; `request_refund_callback` stores `RefundRequest { refund_address: Bob's address, ... }` keyed by Alice's UTXO storage key.
5. Alice calls `request_refund` — it reverts: `"Refund request already exists for this UTXO"`.
6. After `unsafe_refund_timelock_sec` elapses (and if the DAO does not reject), Bob calls `execute_refund`. The bridge constructs and signs a Bitcoin transaction paying Bob's address.
7. After on-chain confirmation, `verify_refund_finalize` finalizes the refund. Alice's deposit is gone.
