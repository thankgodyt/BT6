### Title
`validatePerasCert` Performs No Validation While `validatePerasVote` Has a Membership Check, Allowing Any Crafted Certificate to Bypass All Authorization - (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The `BlockSupportsPeras` class defines two parallel validation entry points for inbound Peras objects: `validatePerasVote` and `validatePerasCert`. `validatePerasVote` enforces at least one authorization check (the voter must appear in the stake distribution). `validatePerasCert` performs **no checks whatsoever** — it unconditionally returns `Right` for every certificate it receives. This is structurally identical to the reported ERC1155 pattern: one receiver path has the guard, the sibling path is missing it entirely.

### Finding Description

In `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`, the degenerate `BlockSupportsPeras` instance (the only instance in the codebase, used for all block types) defines:

```haskell

validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params

``` [1](#0-0) 

The sibling function `validatePerasVote` at least gates on stake-distribution membership:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { ... }
  | otherwise =
      Left PerasValidationErr
``` [2](#0-1) 

`validatePerasCert` is the gate that produces a `ValidatedPerasCert blk` value. Downstream code (`addPerasCertAsync`, `addPerasCert` in ChainSel) consumes only `ValidatedPerasCert` values, trusting that the type wrapper guarantees prior validation. [3](#0-2) 

The Peras vote inbound path calls `validatePerasVote` explicitly before handing the result to `addPerasVoteWithAsyncCertHandling`: [4](#0-3) 

The certificate inbound path calls `validatePerasCert` before calling `addPerasCertAsync`. Because `validatePerasCert` always returns `Right`, any peer-supplied certificate — with an arbitrary round number, arbitrary boosted block point, and no cryptographic proof — is wrapped in `ValidatedPerasCert` and injected into chain selection with full boost weight (`perasWeight params`).

### Impact Explanation

Peras certificates directly influence chain selection: a `ValidatedPerasCert` carries a `vpcCertBoost` weight that is applied to the boosted block's chain during candidate comparison. An attacker who can inject an accepted certificate pointing to a non-canonical or adversarially chosen block can cause an honest node to prefer that block over the canonical chain. This satisfies the **High** impact criterion: "Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions." [5](#0-4) 

### Likelihood Explanation

Any peer connected via the Peras certificate ObjectDiffusion miniprotocol can send a certificate. No keys, stake, or privileges are required. The attacker constructs a `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock`, sends it over the wire, and `validatePerasCert` accepts it unconditionally. The only precondition is that the Peras diffusion layer is active on the target node.

### Recommendation

`validatePerasCert` must perform the same class of authorization checks as `validatePerasVote` — at minimum verifying that the certificate's aggregate BLS signature is valid against the claimed voter set and that the voter set collectively holds sufficient stake. Until the full cryptographic check is implemented, the function should return `Left PerasValidationErr` by default rather than `Right`, so that no certificate is accepted without a positive proof of validity. The existing TODO at issue [#120](https://github.com/tweag/cardano-peras/issues/120) should be treated as a security-blocking item.

### Proof of Concept

1. Connect to a node with Peras diffusion enabled as an unprivileged peer.
2. Construct a `PerasCert` with `pcCertRound = <any round>` and `pcCertBoostedBlock = <point of a non-canonical block>`.
3. Send it via the Peras certificate ObjectDiffusion miniprotocol.
4. The node calls `validatePerasCert`, which returns `Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }` unconditionally.
5. The certificate is enqueued via `addPerasCertAsync` and processed by `chainSelSync`.
6. Chain selection now applies `vpcCertBoost` to the attacker-chosen block, potentially causing the node to switch to a non-canonical fork. [6](#0-5)
