### Title
Peras Quorum Check Compares Absolute Vote Stake Against Relative Threshold Without Normalization — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` in `SupportsPeras.hs` directly compares accumulated `PerasVoteStake` values (sourced from the ledger's absolute stake distribution) against a relative quorum threshold (`PerasQuorumStakeThreshold`, a `Rational` fraction like `0.75`), with no normalization step. The function's own TODO comment acknowledges this unit mismatch. Because `PerasVoteStake` is a bare `Rational` with no phantom type distinguishing absolute from relative values, and because `validatePerasVote` assigns the raw ledger stake to `vpvVoteStake` without normalizing, the quorum check is broken: if absolute lovelace values are present in the stake distribution, any single vote from a registered voter will have a stake value (e.g., `1000` lovelace as `Rational`) that vastly exceeds the relative threshold (`0.75`), causing `stakeAboveThreshold` to return `True` immediately. This allows an unprivileged peer to trigger Peras certificate forging for an arbitrary block with a single vote, boosting an adversarial chain's weight in chain selection.

### Finding Description

**Root cause — `stakeAboveThreshold` in `SupportsPeras.hs`:** [1](#0-0) 

The function compares `unPerasVoteStake voteStake` (a `Rational` accumulated from `PerasVoteStakeDistr`) directly against `unPerasQuorumStakeThreshold + safetyMargin` (also `Rational`, but intended to be a relative fraction). The comment explicitly states:

> "this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally."

No normalization is performed anywhere in the call chain.

**Root cause — `validatePerasVote` assigns raw ledger stake without normalization:** [2](#0-1) 

The stake is taken directly from `PerasVoteStakeDistr` via `lookupPerasVoteStake` and assigned to `vpvVoteStake` with no conversion. The comment on `PerasVoteStake` itself confirms the problem: [3](#0-2)

### Impact Explanation

If `PerasVoteStakeDistr` is populated with absolute lovelace values (the natural representation from the Cardano ledger), then a voter with even 1 lovelace of stake has `PerasVoteStake = 1` (as `Rational`), which is already greater than any relative quorum threshold (e.g., `0.75`). `stakeAboveThreshold` returns `True` on the very first vote, causing `votesReachQuorum` to return `Just` and `forgePerasCert` to be called immediately.

The forged `ValidatedPerasCert` is then stored in the `PerasCertDB` and used to compute `PerasWeightSnapshot`, which boosts the certified block's chain weight in `weightedSelectView`: [8](#0-7) 

An adversary can thus cause an honest node to prefer an adversarial chain by sending a single vote for an adversarial block, triggering a spurious Peras certificate that adds `perasWeight` to that chain's total weight. This is a **High** impact chain-selection bug: an unprivileged peer can make an honest node prefer a non-canonical chain beyond the intended security assumptions.

---

### Likelihood Explanation

The `PerasVoteStakeDistr` is sourced from the ledger's stake distribution, which stores absolute lovelace values. The TODO comment in production code confirms the normalization step is missing and unresolved. Any peer that can send a `PerasVote` message for a voter present in the stake distribution (i.e., any registered stake pool) can trigger this. The vote diffusion mini-protocol (`makePerasVotePoolWriterFromChainDB`) is an externally reachable network endpoint. Likelihood is **High** given the confirmed missing normalization.

---

### Recommendation

1. **Enforce unit consistency at the type level**: Introduce a phantom-typed `PerasVoteStake Absolute` vs `PerasVoteStake Relative` to prevent mixing units at compile time.
2. **Normalize in `validatePerasVote`**: Before assigning `vpvVoteStake`, divide the voter's absolute stake by the total stake in the distribution to produce a relative value.
3. **Or normalize in `stakeAboveThreshold`**: Accept the total stake distribution as a parameter and perform normalization internally, as the TODO comment suggests.
4. **Add an invariant assertion**: Until the above is fixed, assert in `stakeAboveThreshold` that `voteStake <= 1` (i.e., it is a relative value) to catch misuse at runtime.

---

### Proof of Concept

**Setup**: A private testnet with `perasQuorumStakeThreshold = 0.75` (relative). The `PerasVoteStakeDistr` is populated from the ledger with absolute lovelace values (e.g., voter A has `500_000_000_000` lovelace = 500k ADA).

**Attack sequence**:
1. Adversary peer sends a single `PerasVote` for an adversarial block `B_adv` in round `r`, signed by voter A (any registered pool).
2. `processVotes` calls `validatePerasVote mkPerasParams sd vote`, which looks up voter A's stake: `PerasVoteStake (500_000_000_000 % 1)`.
3. `updateTargetVoteTally` sets `ptvtTotalStake = 500_000_000_000 % 1`.
4. `votesReachQuorum` calls `stakeAboveThreshold`: `500_000_000_000 >= 0.75 + 0` → `True`.
5. `forgePerasCert` is called, producing a `ValidatedPerasCert` boosting `B_adv` by `perasWeight`.
6. `PerasCertDB` stores the cert; `PerasWeightSnapshot` is updated.
7. `weightedSelectView` now computes `wsvTotalWeight` for any chain containing `B_adv` as `blockNo + perasWeight`, making it heavier than the honest chain.
8. The honest node switches to the adversarial chain.

-- | Check whether a given vote stake is above the quorum threshold.
--
-- TODO: this function assumes that the 'PerasVoteStake' and the quorum
-- threshold used in 'PerasParams' are expressed in the same units. That is,
-- both are either absolute or relative (normalized) values. Under the current
-- current implementation of 'PerasParams', this function only makes sense when
