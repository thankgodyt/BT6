### Title
Unconditional Peras Certificate and Vote Acceptance Bypasses All Cryptographic Validation, Enabling Chain Selection Manipulation — (`Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` and `validatePerasVote` methods perform no cryptographic or protocol-rule checks. Any unprivileged peer can send crafted Peras certificates or votes that are accepted without signature verification, round-number validation, or cooldown-period enforcement. Accepted certificates directly trigger chain selection, allowing an attacker to make an honest node prefer a non-canonical chain by injecting fake boosts.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` and `validatePerasVote` as the gatekeepers for accepting Peras certificates and votes from the network. The production instance (lines 318–389 of `Block/SupportsPeras.hs`) is explicitly marked as a degenerate placeholder with TODO comments referencing issue #120, but it is wired into live production code paths.

**`validatePerasCert` always returns `Right`** for any certificate, regardless of cryptographic signature validity, round number, or whether quorum was actually reached:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

**`validatePerasVote` only checks stake-distribution membership**, skipping BLS signature verification, round-number validity, VRF eligibility proofs, and all cooldown-period rules (VR-1A, VR-1B, VR-2A, VR-2B):

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote{ vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [2](#0-1) 

These stubs are called from two live production paths:

1. **Inbound vote handler** — `makePerasVotePoolWriterFromChainDB` calls `validatePerasVote` for every vote received from a peer via the object-diffusion mini-protocol: [3](#0-2) 

2. **Certificate chain-selection trigger** — `chainSelSync` processes every accepted `ValidatedPerasCert` and calls `chainSelectionForBlock` for the boosted block, potentially switching the node's preferred chain: [4](#0-3) 

Chain selection uses `WeightedSelectView`, which adds `wsvWeightBoost` (sourced from accepted certificates) to `wsvTotalWeight`. A chain with an injected boost of `perasWeight = 15` (the default) is treated as 15 blocks heavier than it actually is: [5](#0-4) 

The `isPerasVotingAllowed` function and the full voting-rule suite (VR-1A, VR-1B, VR-2A, VR-2B) exist and are correct, but they are **only consulted when a node decides whether to forge its own votes** — they are never applied when validating votes received from peers: [6](#0-5) 

This is the direct analog to the external report: just as `addToPosition()` lacked the restriction check that `renewLock()`/`extendLock()` had, `validatePerasVote`/`validatePerasCert` lack the cryptographic and protocol-rule checks that the vote-forging path correctly enforces.

---

### Impact Explanation

An unprivileged peer can:

1. Send a crafted `PerasCert` with `pcCertBoostedBlock` pointing to any block in the VolatileDB. `validatePerasCert` returns `Right` unconditionally.
2. The certificate is stored in `PerasCertDB` and `chainSelSync` calls `chainSelectionForBlock` for the boosted block.
3. The node's `WeightedSelectView` now treats that block as 15 units heavier than its actual chain length, potentially causing a fork switch to a non-canonical chain.

For votes: an attacker who knows any voter ID present in the stake distribution can inject votes for arbitrary rounds and arbitrary block targets without a valid BLS signature. If enough such votes are injected to cross the quorum threshold, a certificate is forged locally and the same chain-selection manipulation follows.

This matches the **High** impact category: a chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.

---

### Likelihood Explanation

The attack requires only network connectivity to a node running the Peras certificate or vote diffusion mini-protocol. No key compromise, stake majority, or operator access is needed. The attacker only needs to know a valid voter ID (derivable from the public stake distribution) to pass the single check in `validatePerasVote`. For certificates, no information beyond the target block's point is required.

---

### Recommendation

Implement the full cryptographic validation in `validatePerasCert` and `validatePerasVote` as indicated by the TODO comments referencing issue #120:

- `validatePerasCert`: verify the aggregate BLS signature over the election ID and boosted block, verify each voter's eligibility proof, and confirm the voter set meets the quorum threshold.
- `validatePerasVote`: verify the BLS vote signature, verify the VRF eligibility proof for non-persistent members, check the round number is current, and enforce the cooldown-period rules (VR-1A/VR-1B or VR-2A/VR-2B) before accepting a vote from a peer.

Until full validation is implemented, the degenerate instance should not be reachable from any code path that accepts network input.

---

### Proof of Concept

1. Connect to a node via the Peras certificate diffusion mini-protocol.
2. Construct a `PerasCert` with `pcCertRound = N` and `pcCertBoostedBlock = <point of a fork block in the VolatileDB>`.
3. Send it. `validatePerasCert` returns `Right ValidatedPerasCert{..., vpcCertBoost = PerasWeight 15}` unconditionally.
4. `chainSelSync` calls `chainSelectionForBlock` for the fork block.
5. `WeightedSelectView` now scores the fork chain as 15 units heavier than the honest chain.
6. If the fork chain's block count plus 15 exceeds the honest chain's block count, the node switches to the fork — accepting an invalid chain without any honest quorum having voted for it. [7](#0-6)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes

  -- Deliver promise indicating that we processed the cert.
  lift $ atomically $ putTMVar varProcessed certResult
