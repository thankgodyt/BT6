### Title
Arithmetic Underflow Panic Before Gas-Fee Validation in `check_withdraw_psbt` Permanently Blocks Withdrawal Attempt - (File: contracts/satoshi-bridge/src/psbt.rs)

### Summary

`check_withdraw_psbt` performs two u128 subtractions that can underflow and panic before the gas-fee range check that would otherwise produce a clean rejection. Because `overflow-checks = true` is set in the workspace profile, any underflow aborts the transaction. An unprivileged user can craft PSBT output amounts that trigger this panic on every withdrawal attempt, causing the `ft_on_transfer` call to abort with a runtime panic rather than a graceful error.

### Finding Description

The withdrawal path is:

`ft_on_transfer` → `ft_on_transfer_withdraw_chain_specific` → `create_btc_pending_info` → `check_withdraw_psbt_valid` → `check_withdraw_psbt`

Inside `check_withdraw_psbt`, the following sequence executes:

```rust
// line 238 – subtraction before any bounds check on total_output_amount
let gas_fee = total_input_amount - total_output_amount;

// line 242 – subtraction before gas_fee is validated
let max_received_amount = amount - withdraw_fee - gas_fee;

// line 243 – subtraction before max_received_amount is validated
let min_received_amount = max_received_amount - config.min_change_amount;

// ... lines 244-251: range check on actual_received_amount ...

// line 252 – gas_fee range check arrives TOO LATE
require!(
    gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee,
    ...
);
``` [1](#0-0) 

**Underflow vector 1 – line 238.** The user supplies the `output` field of the `TokenReceiverMessage::Withdraw` message. Each change output is individually validated to be `< min_input_amount`, but there is no check that the *sum* of all outputs stays below `total_input_amount`. A user can include multiple change outputs each just below `min_input_amount` so that their aggregate exceeds the UTXO input total, making `total_input_amount - total_output_amount` wrap and panic. [2](#0-1) 

**Underflow vector 2 – line 242.** Even when line 238 succeeds, if the resulting `gas_fee` is larger than `amount - withdraw_fee`, the subtraction `amount - withdraw_fee - gas_fee` panics. The gas-fee range check at line 252 would have caught an out-of-range `gas_fee`, but it executes *after* the subtraction, so the panic fires first. [3](#0-2) 

**Underflow vector 3 – line 243.** If `max_received_amount < config.min_change_amount`, the subtraction on line 243 also panics before the range check on `actual_received_amount` at lines 244-251 can produce a meaningful error.

The workspace profile enforces `overflow-checks = true`, so all three cases abort the transaction rather than silently wrapping. [4](#0-3) 

The user-controlled entry point is `ft_on_transfer` via `nbtc.ft_transfer_call(bridge, amount, WithdrawMsg)`. The `output` field of `TokenReceiverMessage::Withdraw` is fully attacker-controlled. [5](#0-4) 

### Impact Explanation

When the panic fires, the entire NEAR transaction reverts atomically. In the Bitcoin (synchronous) path, `ft_on_transfer` itself panics, so the NEP-141 `ft_transfer_call` refunds the tokens to the sender — no token loss. In the Zcash (async) path, the panic occurs inside `ft_on_transfer_callback`; the callback failure causes `ft_resolve_transfer` to refund the tokens as well. UTXOs removed by `generate_vutxos` are also restored by the revert.

The concrete harm is that a user who submits a withdrawal with crafted output amounts receives a runtime panic abort instead of a descriptive error message, and their withdrawal is blocked until they submit a correctly formed transaction. This is a publicly reachable panic-driven fault in the production bridge withdrawal path without direct theft of funds.

**Severity: Low** — matches "Publicly reachable invariant-violation, stuck-state, or panic-driven fault in production bridge/token paths without direct theft."

### Likelihood Explanation

Any NEAR account holding nBTC can trigger this by calling `nbtc.ft_transfer_call` with a `Withdraw` message whose `output` amounts sum to more than the selected UTXO inputs, or whose individual amounts are crafted to make `gas_fee > amount - withdraw_fee`. No special role or privileged access is required. The entry point is fully public. [6](#0-5) 

### Recommendation

Reorder the validation so that bounds checks precede the arithmetic:

1. **Before line 238**: verify `total_output_amount <= total_input_amount` with a `require!` and a descriptive message, or use `total_input_amount.checked_sub(total_output_amount).expect(...)`.
2. **Before line 242**: verify `amount >= withdraw_fee + gas_fee` (using `checked_sub` or an explicit `require!`) before computing `max_received_amount`.
3. **Before line 243**: verify `max_received_amount >= config.min_change_amount` before computing `min_received_amount`.

Move the gas-fee range check (`gas_fee >= min_btc_gas_fee && gas_fee <= max_btc_gas_fee`) to immediately after line 238, before any further arithmetic that depends on `gas_fee`.

### Proof of Concept

Assume the bridge holds one UTXO of 100,000 sats and the config has `min_input_amount = 100,000`, `max_change_number = 10`.

1. Alice calls `nbtc.ft_transfer_call(bridge, 100_000, msg)` where `msg` is a `Withdraw` with:
   - `input`: the single 100,000-sat UTXO outpoint
   - `output`: two change outputs of 99,999 sats each (each individually passes `output_value < min_input_amount = 100,000`) plus one user output of 1 sat
   - `total_output_amount = 99,999 + 99,999 + 1 = 199,999`
   - `total_input_amount = 100,000`
2. Line 238 executes: `gas_fee = 100_000u128 - 199_999u128` → underflow → panic with `overflow-checks = true`.
3. The transaction aborts. Alice's withdrawal fails with a runtime panic. Her nBTC tokens are refunded by `ft_resolve_transfer`. [7](#0-6)

    pub fn check_withdraw_psbt(
        &self,
        psbt: &PsbtWrapper,
        target_btc_address: String,
        withdraw_change_address_script_pubkey: &ScriptBuf,
        vutxos: &[VUTXO],
        amount: u128,
        withdraw_fee: u128,
    ) -> (usize, usize, u128, u128) {
        let config = self.internal_config();
        let (min_input_amount, total_input_amount) = vutxos
            .iter()
            .map(|vutxo| u128::from(vutxo.get_amount()))
            .fold((u128::MAX, 0u128), |(min, sum), v| (min.min(v), sum + v));
        let mut total_output_amount = 0;
        let mut actual_received_amounts = vec![];
        let mut change_amounts = vec![];
        let signer_is_unrestricted =
            self.acl_has_role(Role::UnrestrictedRelayer.into(), env::signer_account_id());

        if !psbt.get_output().is_empty() {
            // `None` when the target is a shielded-only Zcash unified address (no transparent
            // receiver): the user is paid via the Orchard bundle and every transparent output
            // is change, so there is nothing for a transparent output to match against.
            let target_address_script_pubkey = self
                .internal_config()
                .target_script_pubkey(&target_btc_address);

            psbt.get_output().iter().for_each(|output| {
                let output_value = output.value.to_sat() as u128;
                total_output_amount += output_value;
                if target_address_script_pubkey.as_ref() == Some(&output.script_pubkey) {
                    actual_received_amounts.push(output_value);
                } else if &output.script_pubkey == withdraw_change_address_script_pubkey {
                    require!(
                        output_value >= config.min_change_amount,
                        "The change amount is too small"
                    );
                    require!(
                        signer_is_unrestricted || output_value < min_input_amount,
                        "The change amount must be less than the smallest input, or the caller must have the UnrestrictedRelayer role"
                    );
                    change_amounts.push(output_value);
                } else {
                    let output_address =
                        Address::from_script(&output.script_pubkey, config.chain.clone())
                            .expect("Unsupported btc address type");
                    env::panic_str(
                        format!("Invalid transaction output address: {}", output_address).as_str(),
                    );
                }
            });
        }

        total_output_amount += psbt.add_extra_outputs(&mut actual_received_amounts);

        require!(
            actual_received_amounts.len() == 1,
            "only one user output is allowed."
        );
        let actual_received_amount = actual_received_amounts[0];
        let input_num = psbt.get_input_num();
        let change_num = change_amounts.len();
        if input_num > change_num {
            require!(
                change_amounts
                    .into_iter()
                    .all(|v| v < config.max_change_amount),
                format!(
                    "Any change amount should be less than {} when input_num > change_num",
                    config.max_change_amount
                )
            );
        }
        let gas_fee = total_input_amount - total_output_amount;
        // When constructing the withdraw transaction, if the change is less than min_change_amount (dust),
        // the caller may deduct a portion from the user's output to make the change amount meet min_change_amount.
        // Therefore, the contract relaxes the validation.
        let max_received_amount = amount - withdraw_fee - gas_fee;
        let min_received_amount = max_received_amount - config.min_change_amount;
        require!(
            actual_received_amount >= min_received_amount
                && actual_received_amount <= max_received_amount,
            format!(
                "The user's output amount ({}) is out of the valid range ({}, {})",
                actual_received_amount, min_received_amount, max_received_amount
            )
        );
        require!(
            gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee,
            format!(
                "Invalid gas fee ({}). valid range: [{}, {}].",
                gas_fee, config.min_btc_gas_fee, config.max_btc_gas_fee
            )
        );

        self.check_psbt_chain_specific(psbt, gas_fee, target_btc_address);
        (input_num, change_num, actual_received_amount, gas_fee)
    }

#[near]
impl FungibleTokenReceiver for Contract {
    #[pause(except(roles(Role::DAO)))]
    fn ft_on_transfer(
        &mut self,
        sender_id: AccountId,
        amount: U128,
        msg: String,
    ) -> PromiseOrValue<U128> {
        let amount = amount.into();
        require!(
            amount >= self.internal_config().min_withdraw_amount,
            "Invalid amount"
        );
        let message = serde_json::from_str::<TokenReceiverMessage>(&msg).expect("INVALID MSG");
        let token_id = env::predecessor_account_id();
        require!(
            token_id == self.internal_config().nbtc_account_id,
            "Invalid token_id"
        );
        match message {
            TokenReceiverMessage::DepositProtocolFee => {
                self.data_mut().acc_collected_protocol_fee += amount;
                self.data_mut().cur_available_protocol_fee += amount;
                Event::DepositProtocolFee {
                    account_id: &sender_id,
                    amount: U128(amount),
                }
                .emit();
                PromiseOrValue::Value(U128(0))
            }
            TokenReceiverMessage::Withdraw {
                target_btc_address,
                input,
                output,
                max_gas_fee,
                chain_specific_data,
            } => self.ft_on_transfer_withdraw_chain_specific(
                sender_id,
                amount,
                target_btc_address,
                input,
                output,
                max_gas_fee,
                chain_specific_data,
            ),
        }
    }
