### Title
Peras Certificate Validation Stub Unconditionally Accepts All Peer-Supplied Certificates, Enabling Unauthorized Chain-Selection Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance ships a stub `validatePerasCert` that unconditionally returns `Right` for every certificate it receives. Because this function is wired directly into the production Peras certificate diffusion inbound path, any unprivileged peer can inject an arbitrary `PerasCert` (pointing to any block, for any round) into the node's `PerasCertDB`. Once stored, the certificate applies a weight boost to the targeted block and triggers chain selection, potentially causing the node to prefer a non-canonical fork over the honest chain.

---

### Finding Description

**Root cause — stub validation always succeeds**

The `BlockSupportsPeras` type-class defines `validatePerasCert` as the gate that must approve every inbound certificate before it is stored. The only deployed instance of this class is the catch-all `instance StandardHash blk => BlockSupportsPeras blk` in `SupportsPeras.hs`. Its implementation is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No cryptographic signature, no committee-membership check, no round-number plausibility check, and no boosted-block existence check is performed. Every certificate is stamped `ValidatedPerasCert` and assigned the full `perasWeight` boost.

**Inbound diffusion path wires this stub into production**

`makePerasCertPoolWriterFromChainDB` — the writer used for all node-to-node Peras certificate diffusion — passes `validatePerasCert mkPerasParams` as the sole validator:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

This writer is registered as `hPerasCertDiffusionClient` in the node-to-node handler table, meaning it is active for every inbound peer connection: [3](#0-2) 

**`processCerts` adds every "validated" certificate to the ChainDB**

`processCerts` calls `validateCert` on each new certificate; if all pass (which they always do), it calls `addCert` — here `ChainDB.addPerasCertAsync`: [4](#0-3) 

**`addPerasCertAsync` triggers chain selection**

`addPerasCertAsync` enqueues a `ChainSelAddPerasCert` message. `chainSelSync` then adds the certificate to `PerasCertDB` and calls `chainSelectionForBlock` for the boosted block: [5](#0-4) 

**Chain selection uses the injected weight**

`preferAnchoredCandidate` computes `WeightedSelectView` using `weightBoostOfFragment`, which sums `PerasWeightSnapshot` entries for every block on the candidate fragment. The snapshot is derived directly from the `PerasCertDB`: [6](#0-5) 

A peer-injected certificate for a block on a competing fork therefore inflates that fork's weight by `perasWeight params`, potentially making it preferred over the honest chain.

---

### Impact Explanation

When Peras is enabled, an unprivileged peer can:

1. Craft a `PerasCert` whose `pcCertBoostedBlock` points to any block in the node's VolatileDB (e.g., the tip of an adversarial fork).
2. Send it over the `PerasCertDiffusion` mini-protocol.
3. Because `validatePerasCert` always returns `Right`, the certificate is stored without any cryptographic or committee check.
4. Chain selection is re-run with the boosted weight, and the node may switch to the adversarial fork.

This is a **bypass of Peras certificate verification** that enables unauthorized certificate acceptance and chain-selection manipulation — matching the "Critical. Bypass of … certificate … checks … that enables unauthorized … certificate acceptance" impact category.

---

### Likelihood Explanation

The Peras certificate diffusion mini-protocol is already wired into the production node-to-node handler table and active for every peer connection. The stub is the **only** deployed `validatePerasCert` implementation (the catch-all instance covers all block types). Any peer that connects and sends a well-formed `PerasCert` CBOR message will have it accepted. The attack requires no special privileges, no key material, and no stake.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that checks, at minimum:

- The aggregate BLS/committee signature over `(roundNo, boostedBlock)`.
- That the signers are eligible committee members for the claimed round (committee selection check).
- That the round number is within the acceptable window relative to the current chain tip.
- That the boosted block hash is plausible (e.g., exists in the VolatileDB or is a known point).

Until real validation is in place, the inbound cert diffusion path should reject all certificates (return `Left` unconditionally) rather than accept them all, mirroring the safe-fail behavior already applied to votes via the empty `PerasVoteStakeDistr mempty` placeholder. [7](#0-6) 

---

### Proof of Concept

1. Connect to a Peras-enabled node as a peer via the node-to-node protocol.
2. Send a `PerasCertDiffusion` message containing a `PerasCert` with:
   - `pcCertRound = <any round not yet in the DB>`
   - `pcCertBoostedBlock = <tip of an adversarial fork in the VolatileDB>`
3. Observe that `processCerts` calls `validatePerasCert mkPerasParams cert` → `Right ValidatedPerasCert{..}`.
4. The cert is stored via `ChainDB.addPerasCertAsync`.
5. `chainSelSync` runs `chainSelectionForBlock` for the boosted block.
6. `preferAnchoredCandidate` now computes a higher `wsvTotalWeight` for the adversarial fork (block length + `perasWeight params` boost).
7. If the boosted fork's total weight exceeds the current selection's weight, the node switches chains. [8](#0-7) [9](#0-8) [10](#0-9)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
