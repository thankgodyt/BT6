### Title
`sign_btc_transaction` Accepts Arbitrary Attached NEAR Deposit Without Validation, Permanently Trapping User Funds - (File: contracts/satoshi-bridge/src/api/chain_signatures.rs)

### Summary
`sign_btc_transaction` is marked `#[payable]` but never validates, uses, or refunds the attached NEAR deposit. Any NEAR accidentally attached by a caller is silently accepted and permanently trapped in the bridge contract with no recovery path.

### Finding Description
The function `sign_btc_transaction` in `contracts/satoshi-bridge/src/api/chain_signatures.rs` carries the `#[payable]` attribute, which in NEAR SDK means the runtime will accept any attached deposit without reverting. However, the function body performs no deposit check — it does not call `assert_one_yocto()`, does not read `env::attached_deposit()`, and does not forward or refund the deposit. The function simply looks up a pending PSBT and delegates to the internal signing pipeline. [1](#0-0) 

Compare this with every other `#[payable]` function in the same contract that does not legitimately consume a deposit: `cancel_withdraw`, `active_utxo_management`, `active_utxo_management_rbf`, `cancel_active_utxo_management`, `claim_lost_found`, and `migrate_to_new_token` all call `assert_one_yocto()` immediately. [2](#0-1) 

`sign_btc_transaction` has no such guard. Any NEAR attached to the call is credited to the contract's balance but is not tracked in any accounting field (`cur_available_protocol_fee`, `lost_found`, etc.), so it is irrecoverable. [3](#0-2) 

There is no admin sweep or rescue function for untracked NEAR balance in the contract.

### Impact Explanation
A user who calls `sign_btc_transaction` while accidentally attaching NEAR (e.g., a wallet that pre-fills a deposit field, a script error, or a UI bug) permanently loses those funds. The contract accepts the deposit, the signing proceeds normally, and the NEAR is silently absorbed into the contract's untracked balance. No event is emitted, no refund is issued, and no privileged function exists to recover it. This constitutes a permanent, irreversible loss of user funds triggered by a publicly reachable function.

**Impact class:** Medium — harmful smart-contract behavior causing permanent loss of user funds without direct theft, requiring no operator intervention to trigger but also no operator path to recover.

### Likelihood Explanation
`sign_btc_transaction` is a public function callable by any NEAR account with no role restriction beyond the pause guard. It is the function a withdrawal initiator must call during the normal withdrawal flow. Wallets, dApps, and scripts that interact with the bridge are realistic callers. Accidental deposit attachment is a well-documented class of user error on NEAR (analogous to the Dexter/Tezos scenario in the reference report). Likelihood is low-to-medium: the error requires a caller mistake, but the function is on the critical user-facing withdrawal path.

### Recommendation
Add `assert_one_yocto()` at the top of `sign_btc_transaction` (consistent with every other non-deposit-consuming `#[payable]` function in the contract), or remove the `#[payable]` attribute entirely since the function has no legitimate use for an attached deposit.

### Proof of Concept

1. Alice initiates a withdrawal by calling `ft_transfer_call` on the nBTC contract, which triggers `ft_on_transfer` in the bridge and creates a `BTCPendingInfo` entry with `btc_pending_id = X`.
2. Alice (or her wallet/script) calls `sign_btc_transaction("X", 0, 0)` and accidentally attaches `1 NEAR` to the transaction.
3. The NEAR SDK runtime accepts the deposit because the function is `#[payable]`.
4. The function body executes normally — no deposit check, no refund — and the signing proceeds.
5. The 1 NEAR is credited to the bridge contract's balance but is not recorded in `cur_available_protocol_fee`, `lost_found`, or any other tracked field.
6. Alice's 1 NEAR is permanently unrecoverable. No admin function exists to sweep or return untracked NEAR balance. [1](#0-0)

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> PromiseOrValue<bool> {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        btc_pending_info.assert_pending_sign();
        if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {
            if !self.check_btc_pending_info_exists(original_tx_id) {
                require!(
                    self.internal_unwrap_mut_account(&btc_pending_info.account_id.clone())
                        .btc_pending_sign_ids
                        .remove(&btc_pending_sign_id),
                    "Internal error"
                );
                self.internal_remove_btc_pending_info(&btc_pending_sign_id);
                return PromiseOrValue::Value(true);
            }
        }
        self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
            .into()
    }
