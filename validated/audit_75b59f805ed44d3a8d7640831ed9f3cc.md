### Title
Peras Vote and Certificate Validation Is a No-Op Stub, Allowing Any Peer to Forge Votes for Arbitrary Voter IDs - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance implements `validatePerasVote` and `validatePerasCert` as stubs that perform no cryptographic verification. The concrete `PerasVote blk` type carries no signature field. Any unprivileged peer can craft `PerasVote` messages claiming to be any voter in the public stake distribution, causing a node to accumulate forged votes, forge a certificate, and boost an attacker-chosen block — bypassing the entire Peras vote authorization mechanism.

---

### Finding Description

The `BlockSupportsPeras` typeclass in `SupportsPeras.hs` defines `validatePerasVote` and `validatePerasCert` as the security-critical entry points for all inbound Peras votes and certificates. The sole production instance — `instance StandardHash blk => BlockSupportsPeras blk` — implements both as stubs:

**1. `validatePerasCert` unconditionally accepts every certificate:**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

**2. `validatePerasVote` only checks stake distribution membership — no signature verification:**

```haskell
validatePerasVote _params stakeDistr vote
    | Just stake <- lookupPerasVoteStake vote stakeDistr =
        Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
    | otherwise =
        Left PerasValidationErr
``` [2](#0-1) 

**3. The concrete `PerasVote blk` type carries no signature field:**

```haskell
data PerasVote blk = PerasVote
    { pvVoteRound   :: PerasRoundNo
    , pvVoteBlock   :: Point blk
    , pvVoteVoterId :: PerasVoterId
    }
``` [3](#0-2) 

This is the type consumed by the live inbound path. The `processVotes` function in the Peras vote mini-protocol calls `validatePerasVote mkPerasParams sd vote` for every inbound vote, where `sd` is the public stake distribution: [4](#0-3) 

`lookupPerasVoteStake` only performs a `Map.lookup` on the voter ID: [5](#0-4) 

Because the stake distribution is public and the vote type carries no signature, any peer can construct a `PerasVote` with an arbitrary `PerasVoterId` from the distribution and have it accepted as valid. The `PerasVoteDB` deduplication only prevents the same `(roundNo, voterId)` pair from being added twice: [6](#0-5) 

So an attacker can impersonate every distinct voter ID in the distribution across a single round, accumulating their combined stake weight without holding any private key.

The `PerasVoteDB` aggregation logic then forges a certificate once the accumulated stake crosses the quorum threshold: [7](#0-6) 

The forged certificate is then accepted by `validatePerasCert` (which always returns `Right`) and stored in the `PerasCertDB`, where it influences chain selection by boosting the attacker-chosen block.

Note that a fully-specified concrete vote type with a BLS signature field already exists in `Ouroboros.Consensus.Peras.Vote.V1`: [8](#0-7) 

However, this type is not wired into the `BlockSupportsPeras` instance used by the live network path.

---

### Impact Explanation

An unprivileged peer can forge Peras votes for any voter ID in the public stake distribution without possessing any private key. By sending forged votes for enough distinct voter IDs in a single round, the peer causes the target node to:

1. Accept all forged votes as `ValidatedPerasVote` with the real voters' stake weights.
2. Accumulate stake until the quorum threshold is crossed.
3. Forge a `ValidatedPerasCert` boosting an attacker-chosen block.
4. Accept that certificate unconditionally via the stub `validatePerasCert`.
5. Apply the certificate's boost to chain selection, potentially preferring a non-canonical or adversarially-chosen chain.

This is a **Critical** bypass of Peras voting and certificate checks: unauthorized vote and certificate acceptance without any key compromise.

---

### Likelihood Explanation

The attack is reachable by any peer connected via the Peras vote mini-protocol. The stake distribution is public. The `PerasVote` type requires no signature. The only prerequisite is the ability to send crafted network messages, which any peer can do. No operator compromise, leaked keys, or stake majority is required.

---

### Recommendation

1. Add a cryptographic signature field to the concrete `PerasVote blk` type (as already done in `Ouroboros.Consensus.Peras.Vote.V1.PerasVote`), and wire `V1.PerasVote` into the `BlockSupportsPeras` instance.
2. Implement `validatePerasVote` to verify the BLS vote signature against the voter's public key retrieved from the committee context (not just the stake distribution map).
3. Implement `validatePerasCert` to verify the aggregate BLS signature and the VRF proofs for non-persistent members, using the `implVerifyCert` logic already present in `WFALS.hs` and `EveryoneVotes.hs`.
4. Track issue `https://github.com/tweag/cardano-peras/issues/120` as a security-critical blocker before any production deployment of the Peras protocol.

---

### Proof of Concept

```
1. Attacker connects to a node as a peer via the Peras vote mini-protocol.
2. Attacker reads the public PerasVoteStakeDistr to enumerate all voter IDs
   (PerasVoterId values) and their associated stake weights.
3. For each high-stake voter ID V_i in the distribution:
   a. Attacker constructs PerasVote { pvVoteRound = R, pvVoteBlock = B_attacker, pvVoteVoterId = V_i }
      where B_attacker is the block the attacker wants to boost.
   b. Attacker sends this forged vote to the target node.
   c. processVotes calls validatePerasVote, which calls lookupPerasVoteStake.
      Since V_i is in the distribution, the vote is accepted as ValidatedPerasVote
      with V_i's full stake weight — no signature check occurs.
   d. implAddVote inserts the vote into PerasVoteDB and accumulates stake.
4. Once accumulated stake exceeds the quorum threshold, PerasVoteDB forges a
   ValidatedPerasCert for (R, B_attacker).
5. validatePerasCert unconditionally returns Right for this certificate.
6. The certificate is stored in PerasCertDB and its boost is applied to chain
   selection, causing the node to prefer B_attacker over the honest canonical chain.
```
