### Title
Peras Quorum Check Compares Incompatible Stake Units, Enabling Unauthorized Certificate Acceptance - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` in `SupportsPeras.hs` compares a `PerasVoteStake` value (which may carry absolute lovelace-denominated stake from the ledger) against `PerasQuorumStakeThreshold` (which is a relative fraction, e.g. `3/4`). The function's own TODO comment acknowledges the unit mismatch is unresolved. If a concrete implementation populates `PerasVoteStakeDistr` with absolute stake values — the natural representation from the Cardano ledger — the quorum check trivially passes for any voter, allowing a single inbound vote from an unprivileged peer to forge a Peras certificate and inject an illegitimate chain-weight boost.

---

### Finding Description

`stakeAboveThreshold` performs the core Peras quorum gate:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake         = unPerasVoteStake voteStake
  quorumThreshold = unPerasQuorumStakeThreshold (perasQuorumStakeThreshold params)
  safetyMargin  = unPerasQuorumStakeThresholdSafetyMargin (perasQuorumStakeThresholdSafetyMargin params)
``` [1](#0-0) 

The default `PerasParams` sets both threshold fields as relative fractions:

```haskell
perasQuorumStakeThreshold         = PerasQuorumStakeThreshold (3 / 4)   -- 0.75
perasQuorumStakeThresholdSafetyMargin = PerasQuorumStakeThresholdSafetyMargin (2 / 100) -- 0.02
``` [2](#0-1) 

The function's own comment explicitly flags the unresolved unit ambiguity:

> "TODO: this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … Under the current implementation of `PerasParams`, this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [3](#0-2) 

The `vpvVoteStake` field of a `ValidatedPerasVote` is populated by `validatePerasVote`, which simply looks up the voter's entry in `PerasVoteStakeDistr` without any normalization:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
``` [4](#0-3) 

`PerasVoteStakeDistr` is sourced from the ledger's stake distribution. The NOTE on `PerasVoteStake` states there is "no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee." The natural ledger representation is absolute lovelace (e.g., `1_000_000_000 % 1`). If that value is placed in `PerasVoteStakeDistr` without normalization, then `stake = 1_000_000_000` is compared against `quorumThreshold + safetyMargin = 0.77`, and the check always passes. [5](#0-4) 

`stakeAboveThreshold` is the sole gate inside `votesReachQuorum`, which is the smart constructor for `ValidatedPerasVotesWithQuorum` — the type that authorizes `forgePerasCert`:

```haskell
votesHaveEnoughStake = stakeAboveThreshold cfg totalVoteStake
``` [6](#0-5)

### Impact Explanation

A forged certificate causes a block to receive a `PerasWeight` boost. Chain selection in `WeightedSelectView.preferCandidate` compares `wsvTotalWeight`, which sums `BlockNo` and `wsvWeightBoost`:

```haskell
wsvTotalWeight wsv = PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [9](#0-8) 

An illegitimate certificate inflates the weight of an adversary's chain fragment, causing honest nodes to prefer it over the canonical chain. This is a **bypass of Peras certificate/quorum validation** that enables unauthorized certificate acceptance and a chain-selection divergence — matching the Critical impact class.

---

### Likelihood Explanation

The `PerasVoteStakeDistr` is populated from the ledger's stake distribution, where stake is naturally expressed in absolute lovelace. The NOTE in the source explicitly states the normalization question is unresolved. Any concrete Cardano integration that passes raw ledger stake into `PerasVoteStakeDistr` without dividing by total stake triggers the bug. A single vote from any peer with any positive ledger stake suffices to forge a certificate. The attack requires no special privileges — only the ability to send a `PerasVote` message via the mini-protocol.

---

### Recommendation

1. **Enforce units at the type level**: Introduce distinct `AbsolutePerasVoteStake` and `RelativePerasVoteStake` newtypes so the compiler rejects mixing them.
2. **Normalize before comparison**: Either normalize `PerasVoteStake` to a relative fraction (by dividing by total stake) before calling `stakeAboveThreshold`, or pass the total stake into `stakeAboveThreshold` and perform the division internally.
3. **Remove the degenerate instance**: The catch-all `instance StandardHash blk => BlockSupportsPeras blk` with stub `validatePerasVote` and `validatePerasCert` implementations (all returning `Right` unconditionally) should be replaced with a proper opt-in mechanism so blocks that do not support Peras cannot accidentally pass validation.

---

### Proof of Concept

Assume `PerasVoteStakeDistr` is populated with absolute lovelace values (e.g., voter A has `500_000_000_000` lovelace ≈ 500k ADA out of 35 billion total):

```
stake         = 500_000_000_000 % 1
quorumThreshold = 3 % 4          -- 0.75
safetyMargin  = 2 % 100          -- 0.02

stake >= quorumThreshold + safetyMargin
500_000_000_000 >= 0.77          -- TRUE
```

A single vote from voter A causes `votesReachQuorum` to return `Just`, `forgePerasCert` is called, and a `ValidatedPerasCert` with `vpcCertBoost = perasWeight params` (default `PerasWeight 15`) is stored. The boosted block's chain fragment gains weight `blockNo + 15`, making it preferred over an honest chain of equal length, causing the node to switch to the adversary's fork.
