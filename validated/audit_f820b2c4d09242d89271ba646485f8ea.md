Audit Report

## Title
Blacklisted ERC-20 Recipient Permanently Freezes Bridged Funds in `finTransfer` - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`finTransfer` performs an unconditional `safeTransfer` to `payload.recipient` for non-bridge ERC-20 tokens. Because the recipient is cryptographically bound in the MPC-signed payload, no relayer can substitute a different address. If the recipient is blacklisted by the token contract (e.g., USDC, USDT), every finalization attempt reverts, the nonce is never consumed, and the user's tokens — already burned or locked on NEAR — are permanently frozen with no protocol-level recovery path.

## Finding Description

In `finTransfer`, the destination nonce is written at line 287 and the MPC signature is verified at line 311 over a Borsh-encoded payload that includes `payload.recipient` at line 298. The signature check cryptographically binds the recipient: any attempt to substitute a different address produces `InvalidSignature`. For non-bridge, non-multitoken ERC-20s the function reaches the `else` branch at lines 351–354:

```solidity
IERC20(payload.tokenAddress).safeTransfer(
    payload.recipient,
    payload.amount
);
```

If `payload.recipient` is blacklisted by the token contract, `safeTransfer` reverts. Because Solidity reverts roll back all state changes in the same transaction, the `completedTransfers[payload.destinationNonce] = true` write at line 287 is also rolled back. The nonce is therefore never permanently consumed, but the signed payload is immutable — every subsequent retry by any relayer produces the same revert.

On the NEAR side, `init_transfer_internal` burns or locks the user's tokens and records the transfer in `pending_transfers`. There is no public `cancel` or `unlock` function for EVM-destined transfers in `near/omni-bridge/src/lib.rs`. The `fin_transfer_send_tokens_callback` refund path applies only to NEAR-destined transfers (it fires on `ft_transfer_call` failure). No analogous recovery exists for the NEAR → EVM direction. The `evm/SECURITY.md` does not document this scenario as a known or accepted risk.

**Exploit flow:**
1. User calls `init_transfer` on NEAR for USDC targeting an EVM recipient. NEAR burns/locks the tokens and stores the transfer in `pending_transfers`.
2. MPC signs the payload via `sign_transfer`; the signed payload permanently encodes `payload.recipient`.
3. Relayer calls `OmniBridge.finTransfer(sig, payload)`.
4. Line 287: `completedTransfers[nonce] = true` (tentative).
5. Line 351: `USDC.safeTransfer(blacklistedRecipient, amount)` → reverts.
6. Entire transaction reverts; nonce write is rolled back.
7. Every subsequent retry produces the same revert. No relayer can produce a valid signature for a different recipient.
8. NEAR tokens remain burned/locked; no cancel mechanism exists to recover them.

## Impact Explanation

Permanent freezing of bridged funds. The user's source-chain tokens are irrecoverably burned or locked on NEAR, the EVM finalization is permanently blocked, and no protocol-level cancel or re-route mechanism exists. This matches the Critical allowed impact: *permanent freezing of bridged funds across NEAR and EVM flows*.

## Likelihood Explanation

USDC and USDT are among the most commonly bridged assets and both maintain on-chain blacklists controlled by Circle and Tether respectively. An address can be blacklisted at any time — including after a user initiates a bridge transfer — due to regulatory action, sanctions enforcement, or exchange compliance. The triggering condition requires only that a user initiate a normal bridge transfer to an address that is or becomes blacklisted; no privileged access is needed. The scenario is not a victim mistake: the blacklisting is an external, unilateral action by the token issuer.

## Recommendation

Wrap the ERC-20 transfer in a `try/catch` (or low-level call with success check) and, on failure, credit the amount to an escrow mapping keyed by `(recipient, tokenAddress)`. Emit an event so the recipient or a governance process can later redirect or recover the funds:

```solidity
try IERC20(payload.tokenAddress).safeTransfer(payload.recipient, payload.amount) {
    // success
} catch {
    escrow[payload.recipient][payload.tokenAddress] += payload.amount;
    emit TransferEscrowed(payload.recipient, payload.tokenAddress, payload.amount);
}
```

Additionally, add a source-chain cancel/refund mechanism on NEAR so that if EVM finalization is provably impossible (e.g., after a governance-attested failure), the user can recover their locked/burned tokens.

## Proof of Concept

1. Deploy a mock ERC-20 with a blacklist function on a local EVM fork.
2. On NEAR localnet, call `ft_transfer_call` → `init_transfer` targeting the mock token and a recipient address `0xAlice`. Confirm tokens are burned/locked and the transfer appears in `pending_transfers`.
3. Call `sign_transfer` on NEAR; obtain the MPC-signed payload with `payload.recipient = 0xAlice`.
4. Blacklist `0xAlice` on the mock ERC-20.
5. Call `OmniBridge.finTransfer(sig, payload)` on the EVM fork. Assert the transaction reverts.
6. Assert `completedTransfers[nonce]` is `false` (nonce not consumed).
7. Retry `finTransfer` with the same (only valid) signature. Assert it reverts again.
