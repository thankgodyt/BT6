### Title
Caller-Controlled `refund_address` in `request_refund` Allows Attacker to Redirect Victim's BTC Deposit to Attacker-Owned Address — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

`request_refund` accepts a caller-supplied `refund_address` parameter and uses it verbatim when `deposit_msg.refund_address` is `None`. Because there is no check that the caller is the `recipient_id` named in the `deposit_msg`, any unprivileged NEAR account can submit a refund request for a victim's unfinalized BTC deposit and redirect the BTC to an attacker-controlled Bitcoin address.

---

### Finding Description

`request_refund` is a public, payable function (no `#[trusted_relayer]` attribute on the function itself, only on the surrounding `impl` block for management purposes):

```rust
pub fn request_refund(
    &mut self,
    deposit_msg: DepositMsg,
    refund_address: String,
    tx_bytes: Base64VecU8,
    vout: usize,
    proof: TxInclusionProof,
    gas_fee: Option<U128>,
) -> Promise {
``` [1](#0-0) 

Inside `internal_request_refund`, the only guard on `refund_address` is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [2](#0-1) 

When `deposit_msg.refund_address` is `None` (the common case — it is an optional field), the check is skipped entirely and the caller-supplied `refund_address` is stored verbatim in the `RefundRequest`:

```rust
let refund_request = RefundRequest {
    ...
    refund_address,   // ← attacker-controlled
    ...
};
``` [3](#0-2) 

The deposit address is derived from the full `deposit_msg` (including `recipient_id`), so the BTC proof verification succeeds for the victim's real transaction. There is no check that `env::predecessor_account_id()` equals `deposit_msg.recipient_id` anywhere in the refund path.

After the `unsafe_refund_timelock_sec` elapses, `execute_refund` builds a Bitcoin transaction paying `refund_amount` to `refund_request.refund_address`:

```rust
pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
``` [4](#0-3) 

The BTC is then signed by MPC and broadcast to the victim's deposit UTXO — paying the attacker's address.

---

### Impact Explanation

An attacker can steal the full BTC value of any unfinalized deposit whose `deposit_msg.refund_address` was not pre-set. The attacker receives the victim's BTC at their own Bitcoin address. This is unauthorized release of bridge-controlled BTC funds — a Critical impact under the allowed scope.

---

### Likelihood Explanation

- `request_refund` is callable by any NEAR account (no relayer whitelist on the function).
- Deposits with `refund_address: None` in `deposit_msg` are the default and common case.
- The attacker only needs to observe the victim's BTC transaction on-chain (public data) and submit a valid light-client proof — both are trivially available.
- The only mitigation is the `unsafe_refund_timelock_sec` window during which DAO/Operator can reject the request, but this is an operational control, not a cryptographic guarantee. If the operator is slow, offline, or the timelock is short, the attack succeeds.
- Only one refund request can exist per UTXO (`"Refund request already exists for this UTXO"`), so the attacker's preemptive call also blocks the victim from creating a legitimate refund request. [5](#0-4) 

---

### Recommendation

Enforce that the caller is the `recipient_id` named in the `deposit_msg` when `deposit_msg.refund_address` is `None`:

```rust
if deposit_msg.refund_address.is_none() {
    require!(
        env::predecessor_account_id() == deposit_msg.recipient_id,
        "Only recipient_id may supply a refund_address"
    );
}
```

Alternatively, require that `deposit_msg.refund_address` is always pre-set (non-`None`) so the refund destination is committed to at deposit time and cannot be overridden by a third party.

---

### Proof of Concept

1. Victim sends BTC to the address derived from `deposit_msg = { recipient_id: "victim.near", refund_address: None, ... }`.
2. The deposit is never finalized (relayer is down, or the deposit was to a stale address).
3. Attacker observes the BTC transaction on-chain and obtains `tx_bytes`, `vout`, and a valid Merkle proof.
4. Attacker calls:
   ```
   request_refund(
     deposit_msg = { recipient_id: "victim.near", refund_address: None, ... },
     refund_address = "attacker_btc_address",
     tx_bytes = <victim's tx>,
     vout = <victim's vout>,
     proof = <valid proof>,
   )
   ```
5. `internal_request_refund` verifies the proof against the light client — it passes because the BTC transaction is real and was sent to the address derived from the victim's `deposit_msg`.
6. Since `deposit_msg.refund_address` is `None`, the `refund_address` check is skipped and `"attacker_btc_address"` is stored.
7. After `unsafe_refund_timelock_sec`, attacker calls `execute_refund(utxo_storage_key)`.
8. The bridge builds a refund transaction paying the victim's BTC to `"attacker_btc_address"`, signs it via MPC, and broadcasts it.
9. Victim's BTC is permanently transferred to the attacker. [6](#0-5)

    pub(crate) fn internal_request_refund(
        &self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<u128>,
    ) -> Promise {
        require!(
            env::attached_deposit() >= self.required_balance_for_request_refund(),
            "Insufficient deposit for storage"
        );
        require!(
            tx_bytes.0.len() <= MAX_REQUEST_REFUND_TX_BYTES,
            "tx_bytes too large for refund request"
        );
        if let Some(msg_refund_address) = &deposit_msg.refund_address {
            require!(
                msg_refund_address == &refund_address,
                "refund_address does not match deposit_msg.refund_address"
            );
        }

        let transaction =
            crate::WrappedTransaction::decode(&tx_bytes.0, &self.internal_config().chain)
                .expect("Deserialization tx_bytes failed");
        let tx_id = transaction.compute_txid().to_string();

        let config = self.internal_config();
        let deposit_amount = u128::from(transaction.output()[vout].value.to_sat());
        let confirmations = self.get_confirmations(config, deposit_amount);

        self.verify_transaction_inclusion_promise(
            config.btc_light_client_account_id.clone(),
            tx_id,
            proof.tx_block_blockhash,
            proof.tx_index,
            proof.merkle_proof,
            Some((proof.coinbase_tx_id, proof.coinbase_merkle_proof)),
            confirmations,
        )
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_REQUEST_REFUND_CALLBACK)
                .request_refund_callback(deposit_msg, refund_address, tx_bytes, vout, gas_fee),
        )
    }

    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
    }
