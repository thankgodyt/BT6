### Title
Silent nBTC Stranding in `safe_mint` When Recipient Is Unregistered — (File: `contracts/nbtc/src/lib.rs`)

### Summary
`safe_mint` unconditionally mints nBTC tokens into the bridge's own balance before checking whether the recipient account is registered. If the recipient is not registered, the function silently returns `U128(0)` — leaving the freshly-minted tokens stranded in the bridge's nBTC balance with no on-chain recovery path for the depositing user.

### Finding Description
In `contracts/nbtc/src/lib.rs`, `safe_mint` executes in this order:

1. **Mint to bridge unconditionally** — `self.token.internal_deposit(&self.bridge_id, amount.into())` credits the bridge's own nBTC balance regardless of whether the intended recipient is registered.
2. **Silent early-return on unregistered recipient** — `if self.token.accounts.get(&account_id).is_none() { return PromiseOrValue::Value(U128(0)); }` returns zero without reverting, without emitting a failure event, and without any recovery hook.
3. **No stranded-token recovery** — the nBTC contract has no mechanism to reclaim or forward those tokens to the user after this silent return. [1](#0-0) 

Contrast this with `mint_inner`, the path used by the privileged `mint` function, which auto-registers the recipient before depositing: [2](#0-1) 

`safe_mint` deliberately skips that auto-registration, but then silently swallows the failure instead of reverting. The caller (satoshi-bridge) receives `U128(0)` — indistinguishable from a legitimate zero-amount result — and may mark the deposit as processed while the user's nBTC sits permanently in the bridge's own token balance.

This is the direct NEAR analog of TRST-M-4: just as an unsafe ERC20 `transfer()` silently returns without signalling failure for non-standard tokens, `safe_mint` silently returns `U128(0)` after crediting the bridge's balance, giving the caller no reliable signal that the user's tokens were never delivered.

The `lost_found` recovery map used by `transfer_nbtc_callback` in `token_transfer.rs` is only populated on failed *cross-contract* `ft_transfer` calls — it is never populated by the `safe_mint` early-return path. [3](#0-2) 

### Impact Explanation
A user who deposits BTC but has not yet registered storage on the nBTC contract triggers the silent early-return. Their BTC is locked in the bridge's UTXO set, the corresponding nBTC is minted into the bridge's own balance, and the user receives nothing. Because the nBTC contract emits no failure event and returns `U128(0)`, the satoshi-bridge's deposit callback may treat the deposit as finalised, permanently stranding the user's funds. This matches **Critical — significant loss or permanent locking of user funds**, or at minimum **Medium — stuck bridge state requiring operator intervention**.

### Likelihood Explanation
NEAR's NEP-141 standard requires explicit storage registration before an account can hold tokens. Any user who calls the deposit flow without first calling `storage_deposit` on the nBTC contract — a separate, easily-missed step — will trigger this path. The condition is reachable by any unprivileged depositor with no special access required.

### Recommendation
Apply one of the following mitigations inside `safe_mint`:

1. **Auto-register the recipient** before minting (matching `mint_inner`'s behaviour), so the transfer always succeeds.
2. **Revert if the recipient is unregistered** — do not call `internal_deposit` at all until registration is confirmed, so no tokens are minted into a stranded state.
3. **Populate `lost_found`** in the satoshi-bridge's `safe_mint` callback when `U128(0)` is returned, so the user can reclaim their tokens via the existing recovery path.

### Proof of Concept

1. Alice deposits BTC to the bridge without calling `storage_deposit` on the nBTC contract.
2. The satoshi-bridge's deposit verification succeeds and calls `nbtc.safe_mint(alice, amount, None)`.
3. Inside `safe_mint`: `self.token.internal_deposit(&self.bridge_id, amount)` executes — `amount` nBTC is now in the bridge's nBTC balance.
4. `self.token.accounts.get(&alice)` returns `None` → `return PromiseOrValue::Value(U128(0))`.
5. The satoshi-bridge callback receives `U128(0)`. No `lost_found` entry is created. The deposit UTXO is marked verified.
6. Alice's BTC is locked in the bridge UTXO; her nBTC is in the bridge's own token balance; she has no on-chain path to recover either asset. [4](#0-3)

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }
