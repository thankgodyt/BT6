### Title
Peras Certificate Validation Is a No-Op — Any Peer Can Inject Fraudulent Weight Boosts to Corrupt Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The universal `BlockSupportsPeras` instance implements `validatePerasCert` as an unconditional `Right` — it accepts every inbound certificate without performing any cryptographic or semantic check. This no-op validator is wired directly into the production node-to-node Peras certificate diffusion inbound handler. An unprivileged peer can send a crafted `PerasCert` pointing at any block in the volatile DB; the node will accept it, store it, and trigger chain selection with a fraudulent weight boost, potentially causing the node to prefer a non-canonical chain over the honest one.

### Finding Description

**Root cause — `validatePerasCert` is unconditionally `Right`:**

The only `BlockSupportsPeras` instance in the codebase is a universal catch-all:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

No check is performed on:
- The aggregate vote signature over the certificate
- Whether the claimed quorum of stake-weighted voters actually signed
- Whether the `pcCertBoostedBlock` is a real, valid block on any known chain
- Whether the `pcCertRound` is within the valid window for the current epoch

**Inbound path — the no-op validator is used in production:**

`makePerasCertPoolWriterFromChainDB` passes `validatePerasCert mkPerasParams` as the validation function for all inbound certificates received from peers:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)

          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

This writer is registered as the live inbound handler for the Peras certificate diffusion mini-protocol in the node-to-node network stack:

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      ...
``` [3](#0-2) 

**Chain selection impact — fraudulent weight is applied:**

`processCerts` calls `validateCert` on each inbound certificate; if it returns `Right`, the certificate is immediately added to the `PerasCertDB` and `ChainDB.addPerasCertAsync` is called, triggering chain selection: [4](#0-3) 

Chain selection uses `wsvTotalWeight`, which sums `wsvBlockNo` and `wsvWeightBoost`. The fraudulent certificate injects a `PerasWeight 15` boost (from `mkPerasParams`) onto the attacker-chosen block: [5](#0-4) 

The `chainSelSync` path in `ChainSel.hs` then triggers `chainSelectionForBlock` for the boosted block, potentially switching the node's selection to a chain that is heavier only because of the fraudulent certificate: [6](#0-5) 

The `perasWeight` in `mkPerasParams` is hardcoded to `PerasWeight 15`: [7](#0-6) 

### Impact Explanation

**Severity: High — Chain selection bug enabling non-canonical chain preference.**

An unprivileged peer can craft a `PerasCert` with:
- `pcCertRound` set to any round not yet in the local `PerasCertDB`
- `pcCertBoostedBlock` pointing to any block hash present in the node's volatile DB (learnable via normal chain-sync)

The receiving node will accept the certificate without any cryptographic check, store it, and re-run chain selection. Any candidate chain containing the boosted block gains `PerasWeight 15` extra weight. If the honest chain's block-number advantage over a competing fork is less than 15, the node will switch to the adversarially boosted fork. This directly violates the chain selection safety invariant: an honest node is made to prefer a non-canonical chain solely due to a fraudulent certificate from an unprivileged peer.

### Likelihood Explanation

**Likelihood: Low-to-Medium** (conditional on Peras being enabled in the negotiated protocol version).

The Peras mini-protocol is currently disabled by default in production Cardano nodes (the CHANGELOG notes "if Peras is disabled (which is the default), there is no observable difference"). However, the inbound handler is fully wired up in the production network stack and will activate as soon as the Peras protocol version is negotiated. Any peer that speaks the Peras cert diffusion sub-protocol can exploit this with zero stake and zero cryptographic material — the attack requires only the ability to connect as a normal peer and send a well-formed (but fraudulently unsigned) `PerasCert` message.

### Recommendation

Replace the no-op `validatePerasCert` with a real implementation that:
1. Verifies the aggregate BLS vote signature over `(electionId, candidate)` using the aggregated verification keys of the claimed committee members (as implemented in `Ouroboros.Consensus.Committee.WFALS` and `Ouroboros.Consensus.Committee.Crypto.BLS`).
2. Checks that the claimed voters hold sufficient combined stake to meet `perasQuorumStakeThreshold`.
3. Validates that `pcCertRound` falls within the valid window relative to the current epoch.
4. Validates that `pcCertBoostedBlock` is a known, valid block on a plausible chain.

Until the real implementation is ready, the inbound Peras cert diffusion handler (`hPerasCertDiffusionClient`) should either be disabled entirely or should reject all inbound certificates unconditionally (returning `Left PerasValidationErr` for every cert) rather than accepting them all.

### Proof of Concept

**Setup:** Two nodes, A (honest) and B (attacker). Peras cert diffusion is enabled.

1. Node A has a current chain of length N (block number N, weight N).
2. Node B observes via chain-sync that Node A's volatile DB contains a block `blk_fork` at block number `N-5` on a competing fork (weight `N-5`).
3. Node B constructs a `PerasCert { pcCertRound = freshRound, pcCertBoostedBlock = blockPoint blk_fork }` — no signatures, no stake proof, just the two fields.
4. Node B sends this certificate to Node A via the Peras cert diffusion mini-protocol.
5. Node A calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert { vpcCertBoost = PerasWeight 15 }` unconditionally.
6. Node A adds the cert to `PerasCertDB` and calls `chainSelectionForBlock` for `blk_fork`.
7. Chain selection computes: honest chain weight = `N`, fork weight = `(N-5) + 15 = N+10`. Fork wins.
8. Node A rolls back 5 blocks and switches to the adversarially boosted fork.

**Expected:** Certificate rejected with a cryptographic validation error.
**Actual:** Certificate accepted; node switches to the non-canonical fork.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes

mkPerasParams :: PerasParams
mkPerasParams =
  -- Many of these parameters are provided with sensible default values for now,
  -- waiting for a final decision (in a future stage of the project) on the
  -- exact values to use. See https://github.com/tweag/cardano-peras/issues/97.
  --
  -- We set tentatively T_heal to 2B/asc = 600 slots, as the CIP suggests a
  -- bigO(B/asc) for that value so that sufficiently many blocks are produced to
  -- overcome an adversarially boosted block.
  --
  -- We also set tentatively perasCertArrivalThreshold (= X in the formal spec)
  -- to 30 slots (it must be strictly smaller than perasRoundLength)
  -- See https://github.com/tweag/cardano-peras/issues/88 and
  -- https://github.com/tweag/cardano-peras/issues/99 for more information on
  -- this parameter.
  --
  -- We also have T_cp = 129_600 and T_cq = 43_200 as per the design document
  PerasParams
    { -- ceil(T_heal + T_cq) / perasRoundLength) as per the design document
      perasIgnoranceRounds =
        PerasIgnoranceRounds 487
    , -- ceil(T_heal + T_cq + T_cp) / perasRoundLength) + 1 as per the design document
      perasCooldownRounds =
        PerasCooldownRounds 1928
    , -- must be between 30 and 900 as per the design document
      perasBlockMinSlots =
        PerasBlockMinSlots 90
    , -- equal to perasIgnoranceRounds as per the design document
      perasCertMaxRounds =
        PerasCertMaxRounds 487
    , perasCertArrivalThreshold =
        PerasCertArrivalThreshold 30
    , perasRoundLength =
        PerasRoundLength 90
    , perasWeight =
        PerasWeight 15
    , perasQuorumStakeThreshold =
        PerasQuorumStakeThreshold (3 / 4)
    , perasQuorumStakeThresholdSafetyMargin =
        PerasQuorumStakeThresholdSafetyMargin (2 / 100)
    }
