### Title
`PerasVoteId` Partial Key Enables Unprivileged Peer to Forge Votes and Manipulate Peras Chain Boosting — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasVote` does not verify the BLS signature on inbound votes — it only checks that the claimed voter ID exists in the stake distribution. Simultaneously, the deduplication key `PerasVoteId = {roundNo, voterId}` omits the block being voted for. Together, an unprivileged peer can submit a structurally valid but cryptographically unsigned vote for any voter in the stake distribution, targeting an attacker-chosen block. Because the deduplication key is partial (no block field), the fake vote permanently occupies the voter's slot for that round, causing the legitimate vote from that voter to be silently discarded. Repeating this for enough high-stake voters allows the attacker to forge a quorum certificate for an attacker-chosen block, which then receives a Peras boost that steers chain selection.

---

### Finding Description

**Partial deduplication key — the direct structural analog**

`PerasVoteId` is defined as:

```haskell
data PerasVoteId blk = PerasVoteId
  { pviRoundNo :: !PerasRoundNo
  , pviVoterId :: !PerasVoterId
  }
``` [1](#0-0) 

The full vote target is `PerasVoteTarget = {pvtRoundNo, pvtBlock}`, but `PerasVoteId` omits `pvtBlock`. The `PerasVoteDB` implementation uses `pvdsVoteIds :: Set (PerasVoteId blk)` as its deduplication guard:

```haskell
addOrIgnoreVote pvds voteId
  | Set.member voteId (pvdsVoteIds pvds) = voteAlreadyInDB pvds
  | otherwise = tryAddVote pvds voteId
``` [2](#0-1) 

A vote for voter `V` in round `R` targeting block `B_fake` stores `{roundNo=R, voterId=V}` in `pvdsVoteIds`. When the legitimate vote from `V` for block `B_real` arrives, `Set.member` returns `True` and the vote is silently dropped — even though it targets a completely different block.

**Missing signature verification — the enabling condition**

The only `BlockSupportsPeras` instance in the codebase is the catch-all degenerate instance:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [3](#0-2) 

`lookupPerasVoteStake` only performs a `Map.lookup` on the voter ID:

```haskell
lookupPerasVoteStake vote distr =
  Map.lookup (pvVoteVoterId vote) (unPerasVoteStakeDistr distr)
``` [4](#0-3) 

No BLS signature, no VRF eligibility proof, and no round-validity check is performed. The `PerasVote blk` data type carries `pvVoteRound`, `pvVoteBlock`, and `pvVoteVoterId` but no signature field in this instance: [5](#0-4) 

This is the instance used by `processVotes` in the vote diffusion path:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [6](#0-5)

### Impact Explanation

An attacker who can submit fake votes for enough high-stake voters causes `updatePerasRoundVoteStates` to accumulate stake toward an attacker-chosen block and forge a `ValidatedPerasCert` for it: [7](#0-6) 

That certificate carries a `vpcCertBoost :: PerasWeight` that is added to the attacker-chosen block's chain weight during chain selection. This lets an unprivileged peer steer an honest node to prefer a non-canonical chain, constituting a **High** chain-selection manipulation impact.

---

### Likelihood Explanation

The stake distribution is public on-chain data. An attacker needs only a network connection to the node's Peras vote diffusion endpoint and knowledge of which voter IDs are in the current `PerasVoteStakeDistr`. No keys, no stake, and no operator compromise are required. The attack is repeatable every round.

---

### Recommendation

1. **Fix the partial key**: Include the voted block in `PerasVoteId` so that `PerasVoteId = {roundNo, voterId, block}`. This ensures a fake vote for block `B_fake` cannot occupy the deduplication slot for a legitimate vote for block `B_real` from the same voter.

2. **Implement signature verification in `validatePerasVote`**: The concrete `BlockSupportsPeras` instance must verify the BLS vote signature (as already implemented in `PerasBLSCrypto.verifyVoteSignature`) and the VRF eligibility proof for non-persistent committee members before accepting any inbound vote. The TODO at issue #120 must be resolved before Peras is active on any network.

---

### Proof of Concept

Let `V` be a high-stake voter visible in the public stake distribution, and let `B_real` be the block honest nodes are about to vote for in round `R`.

1. Attacker connects to the node via the Peras vote diffusion mini-protocol.
2. Attacker constructs `PerasVote { pvVoteRound = R, pvVoteBlock = B_fake, pvVoteVoterId = V }` — no signature needed.
3. `processVotes` calls `validatePerasVote`: `lookupPerasVoteStake` finds `V` in the stake distribution and returns `Right (ValidatedPerasVote ...)`.
4. `implAddVote` computes `voteId = PerasVoteId { pviRoundNo = R, pviVoterId = V }` and inserts it into `pvdsVoteIds`.
5. The legitimate vote from `V` for `B_real` arrives. `addOrIgnoreVote` finds `{R, V}` already in `pvdsVoteIds` and returns `PerasVoteAlreadyInDB` — the legitimate vote is silently discarded.
6. Attacker repeats steps 2–5 for enough high-stake voters to exceed the quorum threshold for `B_fake`.
7. `updatePerasRoundVoteStates` triggers `VoteGeneratedNewCert` for `B_fake`; a `ValidatedPerasCert` with `vpcCertBoost` is stored.
8. Chain selection now adds `vpcCertBoost` weight to `B_fake`'s chain, causing the honest node to prefer the attacker-chosen fork.
