### Title
Missing Round Staleness Check in Peras Vote Acceptance Allows Stale Certificate Forgery - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Storage/PerasVoteDB/Impl.hs`)

### Summary

The `implAddVote` function in `PerasVoteDB/Impl.hs` contains an explicit TODO acknowledging missing temporal validation logic. The inbound vote processing pipeline (`processVotes` → `validatePerasVote` → `implAddVote`) validates cryptographic properties of votes but performs no check on whether the vote's round number is still within the valid acceptance window. An unprivileged peer can replay legitimately-cast votes from old rounds via the object diffusion mini-protocol; if enough such votes accumulate, a certificate is forged for a stale round, which can then be included in a block and influence Peras-boosted chain selection.

### Finding Description

**Root cause — missing temporal check in `implAddVote`:** [1](#0-0) 

The comment explicitly states:
```haskell
-- TODO: we will need to update this method with non-trivial validation logic
-- see https://github.com/tweag/cardano-peras/issues/120
```

**Inbound path — `processVotes` in the object diffusion layer:** [2](#0-1) 

`processVotes` calls `validateVote` (bound to `validatePerasVote`) for each incoming vote. The validation function receives only the vote and the stake distribution — no current round number is threaded through, making temporal validation structurally impossible at this layer.

**What `validatePerasVote` does check (crypto only):** [3](#0-2) 

Stake distribution is fetched and passed to `validatePerasVote`, which validates eligibility proof and signature — but no round-age bound.

**What `implAddVote` does after validation:** [4](#0-3) 

The function checks only for duplicate vote IDs (`Set.member voteId pvdsVoteIds`), then unconditionally calls `updatePerasRoundVoteStates`, which can forge a certificate if quorum is reached — regardless of how old the round is.

**The certificate expiry check exists only for block production, not vote acceptance:** [5](#0-4) 

`latestCertSeenIsNotExpired` (`currRoundNo <= _A + latestCertSeenRoundNo`) is evaluated only when a block *producer* decides whether to include a certificate. It is not enforced during vote ingestion or certificate storage.

**Attack path:**

1. Adversarial peer collects legitimately-cast votes for round R from the network (these are valid, signed votes).
2. After round R has passed (but within `_A` rounds of the current round), the peer replays these votes to a target node via the object diffusion mini-protocol.
3. `processVotes` → `validatePerasVote` passes (crypto is valid; no round-age check).
4. `implAddVote` stores each vote; `updatePerasRoundVoteStates` forges a certificate for round R once quorum is reached.
5. The certificate is diffused; a block producer includes it (passes `latestCertSeenIsNotExpired` since R is within `_A` rounds).
6. The block carrying the stale certificate receives a Peras weight boost in chain selection.

**GC does not prevent this:** The garbage-collection logic removes rounds only when their *maximum targeted slot* is older than the GC threshold — not when the round number is old. [6](#0-5) 

An adversary targeting a block with a recent slot but an old round number bypasses GC entirely.

### Impact Explanation

Peras certificates boost blocks in chain selection. A node that accepts a stale-round certificate and includes it in a block causes honest peers to see a Peras-boosted block that should not have been boosted. This can make an honest node prefer a non-canonical chain over the canonical one, constituting a **High** chain-selection bug: an unprivileged peer can make an honest node prefer a less-secure chain beyond the intended security assumptions of the Peras protocol.

### Likelihood Explanation

**Medium.** The adversary requires only:
- Access to the object diffusion mini-protocol (any peer).
- A collection of legitimately-cast votes for a past round (obtainable by monitoring the network during that round).
- The target round to still be within `_A` rounds of the current round (a window that grows with `perasCertMaxRounds`).

No key compromise, stake majority, or admin access is required.

### Recommendation

Add a round-staleness guard in `implAddVote` (or in `processVotes` by threading the current round number) that rejects votes whose `pvVoteRound` is more than `_A` rounds behind the current round. This is already acknowledged as necessary in the TODO at line 172–173 of `PerasVoteDB/Impl.hs` and tracked in the linked issue.

### Proof of Concept

```
-- Adversary collects votes for round R from the network during round R.
-- At round R + delta (where delta <= _A = perasCertMaxRounds):
--
-- 1. Adversary sends the collected votes for round R to a target node
--    via the object diffusion mini-protocol.
--
-- 2. processVotes calls validatePerasVote for each vote:
--      validatePerasVote mkPerasParams stakeDistr vote
--    => passes (signatures valid, eligibility proofs valid, no round-age check)
--
-- 3. implAddVote stores each vote; once quorum is reached,
--    updatePerasRoundVoteStates forges a ValidatedPerasCert for round R.
--
-- 4. The certificate is diffused; a block producer evaluates:
--      currRoundNo <= _A + R   -- latestCertSeenIsNotExpired
--    => True (since delta <= _A), so the certificate is included.
--
-- 5. The block carrying the stale certificate receives a Peras boost,
--    causing honest nodes to prefer it over a competing block that
--    should have been preferred under correct Peras semantics.
```

processVotes ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)

-- | latestCertSeenIsNotExpired: the latest certificate seen has not yet expired

latestCertSeenIsNotExpired ::

  Pred PerasCertInclusionRule
latestCertSeenIsNotExpired
  PerasCertInclusionView
    { perasParams
    , currRoundNo
    , latestCertSeen
    } =
    LatestCertSeenIsNotExpired latestCertSeenRoundNo
      := Bool (currRoundNo <= _A + latestCertSeenRoundNo)
   where
    latestCertSeenRoundNo =
      lcsCertRound latestCertSeen

    _A =
      PerasRoundNo $
        unPerasCertMaxRounds $

            perasParams
