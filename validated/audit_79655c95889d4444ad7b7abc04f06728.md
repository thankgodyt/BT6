### Title
Peras Certificate Validation Stub Unconditionally Accepts All Peer-Supplied Certificates, Enabling Unauthorized Chain Weight Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The catch-all `BlockSupportsPeras` instance implements `validatePerasCert` as a stub that unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or structural checks. An unprivileged peer can send a crafted `PerasCert` over the Peras certificate diffusion mini-protocol; the certificate will pass "validation," be stored in the `PerasCertDB`, and trigger chain selection with a weight boost of 15 applied to the attacker-chosen block. This is the direct analog of the "Battle fishing" pattern: a public entry point creates a privileged resource (a `ValidatedPerasCert`) without any real initialization/authorization, allowing an attacker to inject fake authority into the system.

---

### Finding Description

The `BlockSupportsPeras` typeclass declares `validatePerasCert` as the gate that must be passed before a raw `PerasCert` becomes a `ValidatedPerasCert` that can influence chain selection. The production catch-all instance (the only instance in the codebase, used for all block types including Cardano) implements this gate as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params   -- always 15
      }
``` [1](#0-0) 

Every certificate, regardless of its content, is unconditionally promoted to `ValidatedPerasCert` with a boost of `perasWeight mkPerasParams = 15`.

The production inbound path in `makePerasCertPoolWriterFromChainDB` calls `processCerts` with exactly this stub as the validator:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` calls `validateCert` on each inbound certificate and, if all return `Right`, passes them to `addCert` (which is `ChainDB.addPerasCertAsync`): [3](#0-2) 

`addPerasCertAsync` enqueues the certificate for `chainSelSync`, which stores it in the `PerasCertDB` and, if the boosted block is present in the `VolatileDB`, calls `chainSelectionForBlock` with the boosted weight applied: [4](#0-3) 

The `PerasWeightSnapshot` derived from the stored certificate is then used by `preferAnchoredCandidate` / `compareCandidateChains` during chain selection to prefer the boosted fork: [5](#0-4) 

No committee membership check, no aggregate BLS signature verification, no quorum threshold check, and no round-number plausibility check is performed anywhere in this path.

### Impact Explanation

An unprivileged peer can cause an honest node to apply a Peras weight boost of 15 to any block the peer chooses, as long as that block is present in the node's `VolatileDB`. Because the Peras weight boost is additive in chain comparison, a crafted certificate can make a shorter adversarial fork appear heavier than the honest chain, causing the node to switch forks. This is a **chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain**, matching the "High" impact tier. If the attacker can also supply the boosted block (a valid but adversarial block), the entire attack is self-contained.

The `ValidatedPerasCert` type is the consensus layer's privileged token that authorizes a weight boost — analogous to the "manager" role in the original report. The stub `validatePerasCert` hands this token to any caller unconditionally, exactly as `createBattle` bound a fake manager without initialization.

---

### Likelihood Explanation

The Peras certificate diffusion mini-protocol is a public, peer-reachable network endpoint. Any node that connects as a peer can send `PerasCert` messages. The attack requires no keys, no stake, and no prior relationship. The only precondition is that the attacker's chosen block exists in the victim's `VolatileDB`, which is trivially satisfied by first sending a valid (but adversarial) block via the standard block-fetch protocol. Likelihood is **High** for any deployment where the Peras certificate diffusion mini-protocol is enabled.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
1. Verifies the aggregate BLS signature over the certificate against the committee's public keys for the relevant epoch.
2. Checks that the number of signers meets the quorum threshold (`perasQuorumStakeThreshold`).
3. Validates that the `pcCertRound` is plausible given the current chain tip slot and `perasRoundLength`.
4. Validates that `pcCertBoostedBlock` refers to a block that is old enough (`perasBlockMinSlots`) and within the valid certificate age window (`perasCertMaxRounds`).

Until the real implementation is in place, the node should refuse to process inbound Peras certificates from peers (i.e., disable the certificate diffusion mini-protocol) rather than accept all of them unconditionally.

---

### Proof of Concept

**Attacker-controlled entry path:**

1. Attacker connects to a victim node as a peer via the Peras certificate object-diffusion mini-protocol.
2. Attacker sends a `PerasCert` with:
   - `pcCertRound = <any round number>`
   - `pcCertBoostedBlock = <point of a block on the attacker's fork, already in the victim's VolatileDB>`
3. `makePerasCertPoolWriterFromChainDB` receives the cert and calls `processCerts ... (validatePerasCert mkPerasParams) ...`.
4. `validatePerasCert` returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = PerasWeight 15 })` unconditionally. [6](#0-5) 
5. `processCerts` calls `addCert (WithArrivalTime now validatedCert)` → `ChainDB.addPerasCertAsync`. [3](#0-2) 
6. `chainSelSync` stores the cert in `PerasCertDB`, reads the boosted block header from `VolatileDB`, and calls `chainSelectionForBlock` with the boosted weight snapshot. [7](#0-6) 
7. Chain selection now treats the attacker's fork as 15 weight units heavier than it actually is. If the honest chain and the adversarial fork are within 15 weight units of each other, the node switches to the adversarial fork.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
