### Title
Permissionless `request_refund` Allows Attacker to Redirect Victim's Deposited BTC to Arbitrary Address - (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary

When a user deposits BTC using a `DepositMsg` with `refund_address: None`, any unprivileged NEAR account can call `request_refund` on behalf of the victim and supply an attacker-controlled BTC address as the refund destination. After the `unsafe_refund_timelock_sec` elapses — if the DAO/Operator fails to reject the request — the attacker calls `execute_refund` and the victim's deposited BTC is permanently sent to the attacker's address.

### Finding Description

`request_refund` is a fully permissionless public function. It accepts a `deposit_msg` and a separate `refund_address` parameter. The only guard on the refund address is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [1](#0-0) 

When `deposit_msg.refund_address` is `None` (the optional field is absent), this guard is skipped entirely and the caller-supplied `refund_address` is stored verbatim in the `RefundRequest`: [2](#0-1) 

The `deposit_msg` used to derive the deposit address is publicly observable: `get_user_deposit_address` emits a `LogDepositAddress` event containing the full `deposit_msg` including `recipient_id`. [3](#0-2) 

The `request_refund_callback` only verifies that the BTC transaction output's `script_pubkey` matches the deposit address derived from the provided `deposit_msg`. It does **not** verify that the caller is the depositor or that the `refund_address` belongs to the depositor. [4](#0-3) 

After the `unsafe_refund_timelock_sec` passes, `execute_refund` is also permissionless — any account can call it: [5](#0-4) 

The longer `unsafe_refund_timelock_sec` is the only mitigation, intended to give the DAO/Operator time to reject suspicious requests: [6](#0-5) 

This is not a complete mitigation: it relies entirely on the DAO/Operator actively monitoring every refund request and rejecting malicious ones before the timelock expires.

### Impact Explanation

If the DAO/Operator fails to reject the attacker's `request_refund` call (due to inattention, downtime, or a high volume of simultaneous attacks), the attacker calls `execute_refund` after the timelock, and the bridge's MPC signs a Bitcoin transaction sending the victim's deposited BTC to the attacker's address. The victim's BTC is permanently lost — this constitutes **significant theft of user funds**, matching the Critical impact tier. [7](#0-6) 

### Likelihood Explanation

The attack requires two conditions:
1. The victim deposited BTC with `DepositMsg.refund_address = None` and `verify_deposit` was never called (relayer downtime, congestion, or the attacker front-runs by submitting `request_refund` before the relayer submits `verify_deposit`).
2. The DAO/Operator does not reject the malicious refund request before `unsafe_refund_timelock_sec` expires.

Both conditions are realistic in production: relayer downtime is a documented use case for the refund system, and the DAO/Operator cannot guarantee 24/7 monitoring of every refund request. The `deposit_msg` and BTC transaction are fully public on-chain, so the attacker needs no privileged information.

### Recommendation

Restrict `request_refund` so that when `deposit_msg.refund_address` is `None`, only the `deposit_msg.recipient_id` (the intended NEAR recipient) can supply the `refund_address`. Add a caller check:

```rust
if deposit_msg.refund_address.is_none() {
    require!(
        env::predecessor_account_id() == deposit_msg.recipient_id,
        "Only the deposit recipient can specify a refund address"
    );
}
```

Alternatively, require that `refund_address` always be embedded in `deposit_msg` (making it part of the deposit address derivation path), so it cannot be changed after the fact.

### Proof of Concept

1. Alice calls `get_user_deposit_address(DepositMsg { recipient_id: "alice.near", refund_address: None, ... })`. The bridge emits a `LogDepositAddress` event revealing the full `deposit_msg`.
2. Alice sends 1 BTC to the returned deposit address. The transaction is confirmed on-chain.
3. The relayer is temporarily offline; `verify_deposit` is not called.
4. Attacker observes the `LogDepositAddress` event and the BTC transaction. Attacker calls:
   ```
   request_refund(
     deposit_msg = { recipient_id: "alice.near", refund_address: None, ... },
     refund_address = "attacker_btc_address",
     tx_bytes = <alice's deposit tx>,
     vout = 0,
     proof = <valid merkle proof>,
     gas_fee = None
   )
   ```
   The `request_refund_callback` verifies the script matches the deposit address (it does, because `deposit_msg` is correct) and stores `refund_address = "attacker_btc_address"`.
5. The DAO/Operator does not notice or reject the request before `unsafe_refund_timelock_sec` expires.
6. Attacker calls `execute_refund(utxo_storage_key)`. The bridge builds a PSBT paying Alice's 1 BTC to `"attacker_btc_address"`, signs it via MPC, and broadcasts it.
7. Alice's 1 BTC is permanently transferred to the attacker. [8](#0-7) [9](#0-8)

    pub(crate) fn internal_request_refund(
        &self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<u128>,
    ) -> Promise {
        require!(
            env::attached_deposit() >= self.required_balance_for_request_refund(),
            "Insufficient deposit for storage"
        );
        require!(
            tx_bytes.0.len() <= MAX_REQUEST_REFUND_TX_BYTES,
            "tx_bytes too large for refund request"
        );
        if let Some(msg_refund_address) = &deposit_msg.refund_address {
            require!(
                msg_refund_address == &refund_address,
                "refund_address does not match deposit_msg.refund_address"
            );
        }

        let transaction =
            crate::WrappedTransaction::decode(&tx_bytes.0, &self.internal_config().chain)
                .expect("Deserialization tx_bytes failed");
        let tx_id = transaction.compute_txid().to_string();

        let config = self.internal_config();
        let deposit_amount = u128::from(transaction.output()[vout].value.to_sat());
        let confirmations = self.get_confirmations(config, deposit_amount);

        self.verify_transaction_inclusion_promise(
            config.btc_light_client_account_id.clone(),
            tx_id,
            proof.tx_block_blockhash,
            proof.tx_index,
            proof.merkle_proof,
            Some((proof.coinbase_tx_id, proof.coinbase_merkle_proof)),
            confirmations,
        )
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_REQUEST_REFUND_CALLBACK)
                .request_refund_callback(deposit_msg, refund_address, tx_bytes, vout, gas_fee),
        )
    }

    pub(crate) fn internal_execute_refund(
        &mut self,
        utxo_storage_key: String,
        timelock_sec: u64,
        _chain_specific_data: Option<ChainSpecificData>,
    ) -> PromiseOrValue<()> {
        let refund_request = self.load_refund_request_for_execute(&utxo_storage_key, timelock_sec);
        let RefundExecutionInputs {
            outpoint,
            deposit_output,
            refund_amount,
        } = self.refund_execution_inputs(&refund_request);
        let refund_output = self.build_refund_output(&refund_request.refund_address, refund_amount);

        let mut psbt = PsbtWrapper::new(vec![outpoint], vec![refund_output]);
        psbt.set_input_utxo(vec![deposit_output]);

        let caller = env::predecessor_account_id();
        self.finalize_refund_with_psbt(
            caller,
            refund_request,
            psbt,
            refund_amount,
            utxo_storage_key,
        );
        PromiseOrValue::Value(())
    }
