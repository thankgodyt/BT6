Audit Report

## Title
Silent Success on Non-Existent ERC1155 Contract Enables Unauthorized NEAR Token Minting — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`logMetadata1155` is fully permissionless and makes no on-chain call to the ERC1155 contract, allowing any address (including one with no deployed bytecode) to be registered as an ERC1155 token. `initTransfer1155` then calls `IERC1155(tokenAddress).safeTransferFrom(...)` — a void-returning high-level call — which silently succeeds when `tokenAddress` has no code, because the EVM returns `(success=true, returndata=0x)` for calls to empty addresses and Solidity performs no ABI-decode for void returns. The resulting `InitTransfer` event is genuine and verifiable on-chain, causing the NEAR bridge to mint unbacked bridged tokens to the attacker's recipient.

## Finding Description

**Step 1 — Permissionless registration of a non-existent ERC1155 contract:**

`logMetadata1155` (lines 234–270) stores the `(tokenAddress, tokenId) → deterministicToken` mapping and emits `LogMetadata` without making any call to `tokenAddress`. No existence check (`code.length > 0`, `supportsInterface`, or otherwise) is performed:

```solidity
// Lines 234-270: no call to tokenAddress, always succeeds
function logMetadata1155(address tokenAddress, uint256 tokenId) external payable {
    address deterministicToken = deriveDeterministicAddress(tokenAddress, tokenId);
    MultiTokenInfo storage multiToken = multiTokens[deterministicToken];
    if (multiToken.tokenAddress == address(0)) {
        multiToken.tokenAddress = tokenAddress;
        multiToken.tokenId = tokenId;
    }
    ...
    emit BridgeTypes.LogMetadata(deterministicToken, ...);
}
```

The NEAR side uses this `LogMetadata` event to register the bridged token.

**Step 2 — Silent no-op `safeTransferFrom` on a non-existent contract:**

`initTransfer1155` (lines 458–464) makes a high-level Solidity call to `IERC1155(tokenAddress).safeTransferFrom(...)`. `safeTransferFrom` is declared as returning `void`. When `tokenAddress` has no deployed bytecode:
- The EVM `CALL` opcode returns `(success=true, returndata=0x)`.
- Solidity checks the success flag (it does for high-level calls), sees `true`, and does not revert.
- Because the function returns `void`, Solidity performs no ABI-decode of `returndata`.
- No tokens are transferred; execution continues normally.

This is structurally different from the ERC20 path (lines 407–411), which uses `SafeERC20.safeTransferFrom` → `Address.functionCall` → `verifyCallResultFromTarget`, which explicitly reverts with `AddressEmptyCode` when `target.code.length == 0` and `returndata.length == 0`.

**Step 3 — Legitimate `InitTransfer` event emitted:**

After the silent no-op, execution reaches lines 480–490 and emits `InitTransfer` with `deterministicToken`, `amount`, and the attacker's NEAR recipient. This event is genuinely on-chain and passes any light-client or Wormhole VAA verification. The NEAR bridge mints the corresponding bridged tokens to the attacker's recipient without any real ERC1155 tokens ever being locked.

**Additional impact — `finTransfer` ERC1155 path (lines 323–330):**

If `multiToken.tokenAddress` is a non-existent contract at finalization time, the same silent-success pattern applies: the destination nonce is permanently consumed (`completedTransfers[payload.destinationNonce] = true` at line 287), the recipient receives nothing, and there is no recovery path — permanently freezing in-flight bridged funds.

**Existing guards are insufficient:**

- `onERC1155Received` (lines 522–535) checks `operator != address(this)` and reverts for direct sends. This guard is irrelevant here: for a non-existent contract, `safeTransferFrom` never calls `onERC1155Received` at all.
- The `evm/SECURITY.md` notes that `logMetadata` (ERC20) being permissionless is intentional, but `logMetadata` (ERC20) at line 224 makes live calls to `IERC20Metadata(tokenAddress).name/symbol/decimals()` which revert for non-existent contracts. `logMetadata1155` makes no such call, leaving no equivalent guard.

## Impact Explanation

**Critical — Unauthorized minting of bridged tokens.** An unprivileged attacker can mint an arbitrary quantity of unbacked bridged tokens on NEAR at will, with no real ERC1155 tokens locked on the EVM side. This constitutes unauthorized minting and escrow mis-accounting of bridged funds, matching the Critical allowed impact class. The `finTransfer` ERC1155 path additionally enables permanent freezing of in-flight funds with no recovery path.

## Likelihood Explanation

**High.** Both `logMetadata1155` and `initTransfer1155` are fully permissionless — no role, no whitelist, no admin approval. The attacker only needs to supply any address with no deployed bytecode (e.g., a fresh EOA or `address(0xdead)`) and pay the `nativeFee` in ETH. The attack is repeatable with different `tokenId` values to generate distinct deterministic token addresses. No front-running, key compromise, or external dependency failure is required.

## Recommendation

1. **Add a contract existence check in `initTransfer1155`** before calling `safeTransferFrom`. Inline `require(tokenAddress.code.length > 0, "ERC1155: no code at address")` or use OpenZeppelin's `Address.isContract`.

2. **Add a contract existence check in `logMetadata1155`** by making at least one read call to the ERC1155 contract, e.g., `IERC1155(tokenAddress).supportsInterface(type(IERC1155).interfaceId)`, so registration of non-existent contracts reverts.

3. **Wrap the ERC1155 `safeTransferFrom` call in `finTransfer`** (lines 323–330) with an equivalent existence guard to prevent permanent nonce consumption against a non-existent contract.

4. **Consider a `SafeERC1155` helper** analogous to OpenZeppelin's `SafeERC20` that wraps calls with `Address.functionCall` and checks `target.code.length` before dispatching.

## Proof of Concept

```solidity
// SPDX-License-Identifier: GPL-3.0-or-later
pragma solidity ^0.8.24;

// nonExistentERC1155 = any address with no deployed bytecode, e.g. address(0xdead)
// tokenId = any uint256, e.g. 1
// amount = any uint128, e.g. 1_000_000e18

// Step 1: Register the fake ERC1155 token — permissionless, no call to nonExistentERC1155
OmniBridge.logMetadata1155(nonExistentERC1155, tokenId);
// → stores multiTokens[deterministicToken] = {nonExistentERC1155, tokenId}
// → emits LogMetadata(deterministicToken, ...) → NEAR registers the token

// Step 2: Initiate transfer — safeTransferFrom on non-existent contract silently succeeds
OmniBridge.initTransfer1155{value: nativeFee}(
    nonExistentERC1155,
    tokenId,
    amount,
    0,        // fee
    nativeFee,
    "near:attacker.near",
    ""
);
// → IERC1155(nonExistentERC1155).safeTransferFrom(...):
//     EVM CALL to empty address → (success=true, returndata=0x)
//     void return → no ABI-decode → no revert
// → emits InitTransfer(attacker, deterministicToken, nonce, amount, ...)
// → NEAR prover verifies genuine on-chain event
// → NEAR bridge mints `amount` tokens to attacker.near
// → Zero real ERC1155 tokens were ever locked

// Repeatable: increment tokenId to get a fresh deterministicToken each time
```

A local Foundry test can confirm the silent-success behavior by deploying `OmniBridge`, calling both functions against `address(0xdead)`, and asserting that `InitTransfer` is emitted and `currentOriginNonce` increments without any revert, while the ERC1155 balance of `OmniBridge` at `address(0xdead)` remains zero.
