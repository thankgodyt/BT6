### Title
DAO Can Drain Locked Bridge Tokens via `transfer_token_as_dao` Without Checking Pending Transfer Liabilities - (File: `near/omni-bridge/src/lib.rs`)

---

### Summary
`transfer_token_as_dao` allows the DAO role to transfer any amount of any fungible token held by the bridge contract to an arbitrary recipient, with no check against the `locked_tokens` accounting map that tracks outstanding cross-chain transfer liabilities. A DAO key-holder can drain the entire token reserve, rendering all in-flight NEAR-origin transfers permanently unclaimable on their destination chains.

---

### Finding Description
The bridge contract maintains a `locked_tokens: LookupMap<(ChainKind, AccountId), u128>` field that records the total token liability owed to pending outbound transfers. Every time a user initiates a NEAR→foreign transfer, `lock_tokens_if_needed` increments the relevant entry; every time a transfer is finalised or a fee is claimed, `unlock_tokens_if_needed` decrements it. The physical token balance backing these liabilities is held by the bridge contract itself (for non-deployed, NEAR-native tokens such as wNEAR, USDC, etc.).

The privileged function `transfer_token_as_dao` (lines 1511–1529) performs a raw `ft_transfer` or `ft_transfer_call` of an arbitrary `amount` of an arbitrary `token` to an arbitrary `recipient`, with no reference to `locked_tokens` whatsoever:

```rust
#[access_control_any(roles(Role::DAO))]
pub fn transfer_token_as_dao(
    &mut self,
    token: AccountId,
    amount: U128,
    recipient: AccountId,
    msg: Option<String>,
) -> Promise {
    if let Some(msg) = msg {
        ext_token::ext(token)
            .with_attached_deposit(ONE_YOCTO)
            .with_static_gas(FT_TRANSFER_CALL_GAS)
            .ft_transfer_call(recipient, amount, None, msg)
    } else {
        ext_token::ext(token)
            .with_attached_deposit(ONE_YOCTO)
            .with_static_gas(FT_TRANSFER_GAS)
            .ft_transfer(recipient, amount, None)
    }
}
```

There is no surplus check of the form `contract_balance − locked_tokens[token] ≥ amount`. The DAO can therefore transfer the entire token balance, including the portion that is already committed to pending transfers.

---

### Impact Explanation
**Critical — permanent loss of bridged funds.**

For every non-deployed (NEAR-native) token with in-flight outbound transfers, the DAO can call `transfer_token_as_dao` to move the full contract balance to an arbitrary address. After the drain:

- `locked_tokens` still records the outstanding liability.
- When a relayer later calls `fin_transfer` / `claim_fee` for any of those pending transfers, the bridge attempts `ft_transfer` of the locked amount to the recipient, which will fail because the contract no longer holds the tokens.
- Users who locked their tokens into the bridge to initiate a cross-chain transfer permanently lose those funds; the bridge is insolvent for every affected token.

---

### Likelihood Explanation
The DAO role is the highest-privilege role in the contract (it controls factories, provers, token deployers, upgrades, and this withdrawal function). A single DAO key compromise — through phishing, insider threat, or multi-sig threshold failure — is sufficient. The function requires no additional conditions, no time-lock, and no on-chain governance delay, so exploitation is immediate and irreversible once the transfer is submitted.

---

### Recommendation
Mirror the fix applied to the MysteryBox report: compute the total outstanding liability for the requested token across all destination chains before executing the transfer, and only allow the DAO to withdraw the surplus:

```
surplus = ft_balance_of(bridge) − Σ locked_tokens[(chain, token)] for all chains
require!(amount ≤ surplus, "amount exceeds available surplus");
```

Alternatively, introduce a dedicated `withdrawable_balance` view that aggregates `locked_tokens` per token and expose it so governance tooling can enforce the invariant off-chain before submitting the transaction.

---

### Proof of Concept

1. **Setup.** Alice sends 10,000 USDC to the bridge via `ft_transfer_call` with an `InitTransfer` message targeting Ethereum. The bridge holds 10,000 USDC; `locked_tokens[(Eth, usdc.near)]` = 10,000. A `TransferMessage` is stored in `pending_transfers`.

2. **Drain.** DAO calls:
   ```
   transfer_token_as_dao(
       token    = "usdc.near",
       amount   = 10_000,
       recipient = "attacker.near",
       msg      = None
   )
   ```
   No check against `locked_tokens` is performed. The bridge's USDC balance drops to 0; `locked_tokens[(Eth, usdc.near)]` remains 10,000.

3. **Finalization fails.** A relayer submits the EVM proof and calls `fin_transfer`. Inside `process_fin_transfer_to_near`, `unlock_tokens_if_needed` decrements `locked_tokens` and `send_tokens` issues `ft_transfer(alice, 10_000)` against the bridge's USDC account. The NEP-141 call fails (insufficient balance). Alice's funds are permanently lost.

    pub(crate) fn lock_tokens_if_needed(
        &mut self,
        chain_kind: ChainKind,
        token_id: &AccountId,
        amount: u128,
    ) -> LockAction {
        if self.get_token_origin_chain(token_id) == chain_kind || amount == 0 {
            return LockAction::Unchanged;
        }

        self.lock_tokens(chain_kind, token_id, amount)
    }

    pub(crate) fn unlock_tokens_if_needed(
        &mut self,
        chain_kind: ChainKind,
        token_id: &AccountId,
        amount: u128,
    ) -> LockAction {
        if self.get_token_origin_chain(token_id) == chain_kind || amount == 0 {
            return LockAction::Unchanged;
        }

        self.unlock_tokens(chain_kind, token_id, amount)
    }
