### Title
Missing Non-Empty Validation of `confirmations_strategy` in `Config::assert_valid()` Causes Permanent Deposit and Refund Failure - (File: contracts/satoshi-bridge/src/config.rs)

### Summary
`Config::assert_valid()`, called during contract initialization in `Contract::new()`, does not verify that `confirmations_strategy` is non-empty. If the contract is deployed with an empty map, every subsequent call to `verify_deposit` and `request_refund` panics with "confirmations_strategy is empty", permanently blocking all deposit and refund flows until operator intervention.

### Finding Description
`Config::assert_valid()` validates that all values in `confirmations_strategy` fall within the range `2..=100`, but it does not check that the map itself is non-empty:

```rust
pub fn assert_valid(&self) {
    let confirmations_valid_range = 2..=100;
    require!(
        self.confirmations_strategy
            .values()
            .all(|v| confirmations_valid_range.contains(v)),
        "Invalid confirmations_strategy"
    );
    // ...
}
```

In Rust, `.all()` on an empty iterator returns `true` (vacuous truth), so an empty `HashMap` passes this check silently. [1](#0-0) 

The downstream consumer, `Config::get_confirmations()`, does enforce the non-empty invariant, but only at call time:

```rust
pub fn get_confirmations(&self, satoshi_amount: u128) -> u64 {
    require!(
        !self.confirmations_strategy.is_empty(),
        "confirmations_strategy is empty"
    );
    // ...
}
``` [2](#0-1) 

`Contract::new()` calls `config.assert_valid()` and then stores the config, but never independently checks that `confirmations_strategy` is non-empty: [3](#0-2) 

`confirmations_strategy` is not part of `ConfigUpdate`, so it cannot be set via `update_config` after deployment. The only post-deployment remedy is `set_confirmations_strategy`, a privileged call. [4](#0-3) 

### Impact Explanation
Every deposit proof submission calls `self.get_confirmations(config, deposit_amount)`, which internally calls `config.get_confirmations(satoshi_amount)`. With an empty map this panics unconditionally. The same panic occurs in `internal_request_refund` and `internal_verify_refund_finalize`. The result is:

- All `verify_deposit` calls revert → users who sent BTC to derived deposit addresses cannot receive nBTC. Their BTC is locked in deposit addresses with no on-chain mechanism to recover it through the bridge.
- All `request_refund` calls revert → the refund path, which is the intended recovery mechanism for unprocessed deposits, is also blocked.

This matches the allowed Medium impact: **stuck bridge state requiring operator intervention** and **attacker-triggered (or misconfiguration-triggered) temporary locking of bridged funds**. [5](#0-4) 

### Likelihood Explanation
The `Config` struct is a plain JSON-serializable struct with no default values. A deployer who omits `confirmations_strategy` entries (e.g., passes `{}`) will receive no error at initialization. The gap between `assert_valid()` (which passes vacuously) and `get_confirmations()` (which panics) is non-obvious and easy to miss during deployment scripting or testing with mocked light clients that never reach the confirmation check. [6](#0-5) 

### Recommendation
Add an explicit non-empty check inside `Config::assert_valid()`:

```rust
require!(
    !self.confirmations_strategy.is_empty(),
    "confirmations_strategy must not be empty"
);
```

This mirrors the guard already present in `get_confirmations()` and ensures the invariant is enforced at the only point where the full config is validated — initialization. [7](#0-6) 

### Proof of Concept
1. Deploy `Contract::new(config)` where `config.confirmations_strategy = {}` (empty HashMap). `assert_valid()` passes because `.all()` on an empty iterator is vacuously true.
2. Any user calls `verify_deposit(proof, deposit_msg, vout)`.
3. The bridge calls `self.get_confirmations(config, deposit_amount)` → `config.get_confirmations(satoshi_amount)` → `require!(!self.confirmations_strategy.is_empty(), ...)` → **panic: "confirmations_strategy is empty"**.
4. The cross-contract call to the light client is never made; the deposit is never recorded; the user's BTC remains locked in the deposit address.
5. `request_refund` follows the same code path and panics identically, closing the only recovery route.
6. The bridge remains fully non-functional for all deposit and refund operations until a privileged operator calls `set_confirmations_strategy`. [8](#0-7)

    pub fn get_confirmations(&self, satoshi_amount: u128) -> u64 {
        require!(
            !self.confirmations_strategy.is_empty(),
            "confirmations_strategy is empty"
        );
        // The key is constrained to U64 during assignment, so it won't panic.
        let mut keys = self
            .confirmations_strategy
            .keys()
            .map(|k| k.parse::<u128>().unwrap())
            .collect::<Vec<_>>();
        keys.sort_unstable();
        for key in &keys {
            if *key > satoshi_amount {
                return u64::from(*self.confirmations_strategy.get(&key.to_string()).unwrap());
            }
        }
        let max_key = keys.last().unwrap();
        u64::from(
            *self
                .confirmations_strategy
                .get(&max_key.to_string())
                .unwrap(),
        )
    }
