Audit Report

## Title
Non-Atomic `burn.and(mint)` in `swap_migrated_token` Causes Permanent Token Loss on Mint Failure — (File: near/omni-bridge/src/lib.rs)

## Summary
`swap_migrated_token` schedules a burn of old tokens and a mint of new tokens as two parallel, independent NEAR promises via `burn.and(mint)`. The resulting joint promise is `.detach()`ed in `ft_on_transfer`, so any mint failure is silently ignored. If the recipient is not registered (no storage deposit) in the new token contract, `internal_deposit` panics, the mint promise fails, but the burn has already executed and is irreversible — the user permanently loses their tokens and receives nothing.

## Finding Description
In `ft_on_transfer` ( [1](#0-0) ), the `SwapMigratedToken` branch calls `swap_migrated_token(...).detach()` and immediately returns `U128(0)`, meaning the bridge permanently retains the transferred old tokens regardless of downstream promise outcomes.

`swap_migrated_token` ( [2](#0-1) ) constructs two independent cross-contract calls and joins them with `Promise::and()`. In NEAR, `and()` schedules both sub-promises in parallel with no causal dependency — neither sub-promise's execution is conditioned on the other's success, and there is no rollback mechanism.

The `mint` function in `omni-token` ( [3](#0-2) ) calls `FungibleToken::internal_deposit`, which panics if `account_id` has no storage registration in the new token contract. This panic causes the mint promise to fail.

The `burn` function ( [4](#0-3) ) calls `internal_withdraw` on the bridge's balance of old tokens, which succeeds unconditionally because the bridge holds the full amount (returned 0 from `ft_on_transfer`).

`migrate_deployed_token` only registers the bridge itself in the new token ( [5](#0-4) ), never the end users. No guard in `swap_migrated_token` or `ft_on_transfer` checks whether `sender_id` is registered in the new token before issuing the burn.

Execution sequence:
1. User calls `old_token.ft_transfer_call(bridge, amount, "SwapMigratedToken")`.
2. NEP-141 transfers `amount` from user to bridge; `ft_on_transfer` is called.
3. Bridge returns `U128(0)` → bridge permanently holds old tokens.
4. `burn(old_token, amount)` executes → bridge's old-token balance is destroyed. Irreversible.
5. `mint(new_token, sender_id, amount, None)` executes → `internal_deposit` panics (not registered) → promise fails.
6. `.detach()` means the failure is never observed by the bridge.
7. User has lost `amount` of old tokens and received 0 new tokens. Permanent loss.

## Impact Explanation
This is a concrete, critical impact: permanent, unrecoverable destruction of user funds during a legitimate migration flow. Old tokens are burned from the bridge's balance (step 4), new tokens are never minted (step 5), and the bridge has no record of the failure (step 6). The loss matches the allowed critical scope: "Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds across NEAR."

## Likelihood Explanation
The migration flow is a production feature accessible to any token holder via a standard NEP-141 `ft_transfer_call`. NEP-141 storage registration is a separate, non-obvious prerequisite that many users will not know to perform before swapping. No on-chain guard, documentation, or pre-check enforces registration before the swap. The loss is triggered accidentally (not only by a malicious actor), making it a high-likelihood event during any real migration. The exploit is repeatable for every unregistered user who attempts the swap.

## Recommendation
Replace the parallel `burn.and(mint)` with a sequential, callback-guarded pattern:
1. Call `mint(new_token, sender_id, amount, None)` first.
2. In the callback, check success: if mint succeeded, call `burn(old_token, amount)`; if mint failed, refund the old tokens to `sender_id` via `ft_transfer`.

Alternatively, before issuing any promises, verify that `sender_id` is registered in the new token via `storage_balance_of` and panic (causing `ft_resolve_transfer` to refund the full amount) if not registered.

The `.detach()` on the joint promise must also be replaced with a proper callback that can handle partial failure.

## Proof of Concept
```
# Localnet test (no mainnet interaction)
1. Deploy old_token (omni-token), new_token (omni-token), bridge.
2. DAO calls bridge.migrate_deployed_token(chain, old_token, new_token).
3. Register sender in old_token; mint 1000 old tokens to sender.
4. Do NOT call new_token.storage_deposit for sender.
5. sender calls old_token.ft_transfer_call(bridge, 1000, "SwapMigratedToken").
6. Assert: sender's old_token balance = 0 (burned).
7. Assert: sender's new_token balance = 0 (mint failed, not registered).
8. Assert: bridge's old_token balance = 0 (burned).
9. Net result: 1000 tokens permanently destroyed.
```
