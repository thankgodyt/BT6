### Title
Peras Certificate Validation Stub Always Accepts Any Certificate, Enabling Fake Weight Injection into Chain Selection — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` function in the `BlockSupportsPeras` class is an unimplemented stub that unconditionally returns `Right ValidatedPerasCert` for every certificate it receives, performing no cryptographic or semantic checks. Because the object-diffusion mini-protocol feeds peer-supplied certificates directly through this function before inserting them into the `PerasCertDB`, any unprivileged peer can inject arbitrary Peras weight boosts. Chain selection then uses those fake boosts via `preferAnchoredCandidate` / `rollbackExceedsSuffix`, causing the node to prefer a non-canonical adversarial chain over the honest chain.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub** [1](#0-0) 

The function body is:
```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

Every certificate, regardless of its BLS aggregate signature, voter eligibility proofs, committee membership, or round-number plausibility, is wrapped in `ValidatedPerasCert` and returned as `Right`. The `PerasValidationErr` type itself is a single-constructor placeholder with no fields, confirming no real error path exists yet. [2](#0-1) 

**Inbound path — peer certificates reach `validatePerasCert` directly**

`makePerasCertPoolWriterFromChainDB` wires the object-diffusion pool writer to call `validatePerasCert mkPerasParams` on every batch of certificates received from a remote peer, then passes the result straight to `ChainDB.addPerasCertAsync`: [3](#0-2) 

`processCerts` partitions the batch into valid/invalid using the supplied validator. Because the validator always returns `Right`, the "invalid" partition is always empty and every certificate is timestamped and forwarded to `addCert`: [4](#0-3) 

**Fake weights enter chain selection**

`chainSelSync` for `ChainSelAddPerasCert` adds the accepted certificate to the `PerasCertDB` and immediately triggers `chainSelectionForBlock` for the boosted block: [5](#0-4) 

`constructPreferableCandidates` then calls `Diff.rollbackExceedsSuffix weights curChain` to filter candidates and `preferAnchoredCandidate bcfg weights curChain` to rank them, where `weights` is the `PerasWeightSnapshot` that now contains the attacker-injected boosts: [6](#0-5) 

`preferAnchoredCandidate` uses `weightedSelectView` to compute `wsvTotalWeight = BlockNo + PerasWeight` for each fragment. A fake boost large enough to exceed the honest chain's block-number advantage causes `ShouldSwitch` to be returned for the adversarial chain: [7](#0-6) 

**Secondary mismatch — `checkPreferTheirsOverOurs` ignores Peras weights**

When a header is beyond the forecast horizon, the ChainSync client checks whether to stay connected using `emptyPerasWeightSnapshot` (a hardcoded TODO): [8](#0-7) 

This means the disconnect guard uses block-count only, while actual chain selection uses Peras-weighted comparison. An adversary whose chain is shorter by block count but boosted by fake certificates passes the disconnect guard yet wins chain selection — the node stays connected and eventually adopts the adversarial chain.

---

### Impact Explanation

**Impact: High → Chain selection bug / Critical → Certificate verification bypass**

When Peras is enabled, an unprivileged peer can:
1. Craft a certificate claiming to boost any block on an adversarial fork.
2. Deliver it via the object-diffusion mini-protocol.
3. Because `validatePerasCert` never rejects anything, the fake boost is stored in `PerasCertDB` and reflected in `getWeightSnapshot`.
4. Chain selection then computes `wsvTotalWeight` for the adversarial fork as `BlockNo + fakeBoost`, which can exceed the honest chain's total weight.
5. The node switches to the adversarial chain, accepting an invalid or non-canonical ledger state.

This satisfies both:
- **Critical**: Bypass of Peras certificate verification checks enabling unauthorized certificate acceptance.
- **High**: Chain selection bug letting an unprivileged peer make an honest node prefer a non-canonical chain.

---

### Likelihood Explanation

**Likelihood: High** — when Peras is enabled (the CHANGELOG notes it is disabled by default but the code is fully wired up). The attack requires only a TCP connection to the node's object-diffusion port and the ability to send a well-formed CBOR-encoded `PerasCert` message. No stake, keys, or committee membership is required because the validation is entirely absent. The `processCerts` function already handles batches of inbound certificates from untrusted peers, making this a direct, low-effort network-reachable path.

---

### Recommendation

1. **Implement `validatePerasCert`** to perform all checks mandated by CIP-0140 before a certificate is accepted: BLS aggregate signature verification over `(roundNo, boostedBlock)`, voter eligibility proof verification for each seat index (VRF output for non-persistent voters), quorum threshold check, and round-number plausibility against the current ledger state.
2. **Fix `checkPreferTheirsOverOurs`** to use the real `PerasWeightSnapshot` instead of `emptyPerasWeightSnapshot`, eliminating the mismatch between the disconnect guard and actual chain selection (tracked in `https://github.com/tweag/cardano-peras/issues/64`).
3. Until (1) is complete, gate the object-diffusion certificate ingestion path behind the Peras feature flag so that nodes with Peras disabled cannot be reached through this path at all.

---

### Proof of Concept

**Setup**: Peras enabled on a private testnet node. Attacker controls one peer connection.

**Step 1 — Craft a fake certificate** boosting a block on the attacker's fork (e.g., `BlockPoint slot hash`) for round `r`:
```
PerasCert { pcRoundNo = r, pcBoostedBlock = attackerBlockHash,
            pcVoters = <any non-empty bitmap>, pcSignature = <zeroed> }
```
CBOR-encode and send via the Peras certificate object-diffusion mini-protocol.

**Step 2 — `processCerts` calls `validatePerasCert`**:
```haskell
validatePerasCert params cert = Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
```
The certificate passes unconditionally.

**Step 3 — Certificate enters `PerasCertDB`**; `getWeightSnapshot` now returns a snapshot containing `attackerBlockHash → perasWeight params`.

**Step 4 — `chainSelSync` triggers `chainSelectionForBlock`** for `attackerBlockHash`. `constructPreferableCandidates` calls `preferAnchoredCandidate` with the poisoned snapshot. `weightedSelectView` computes `wsvTotalWeight(attackerFrag) = blockNo + perasWeight`, which exceeds the honest chain's `blockNo + 0`. `ShouldSwitch` is returned.

**Step 5 — Node adopts the attacker's chain**, accepting a non-canonical ledger state without any valid quorum of Peras voters having actually voted.

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes

preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"
        Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
          case preferCandidate
            (projectChainOrderConfig cfg)
            (weightedSelectView cfg weights oursSuffix)
            (weightedSelectView cfg weights candSuffix) of
            ShouldSwitch r -> ShouldSwitch (Left r)
            ShouldNotSwitch o -> ShouldNotSwitch o
