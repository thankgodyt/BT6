### Title
Stub `validatePerasCert` Unconditionally Accepts All Inbound Peras Certificates, Enabling Unauthorized Chain-Weight Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production Peras certificate ingest path uses a degenerate `validatePerasCert` implementation that unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or semantic verification. Any unprivileged peer can therefore inject arbitrary Peras certificates into the local `ChainDB`, causing those certificates' chain-weight boosts to be applied to attacker-chosen blocks during chain selection.

---

### Finding Description

`BlockSupportsPeras` is a typeclass whose `validatePerasCert` method is supposed to authenticate inbound Peras certificates before they are stored and used to boost chain weight. The codebase ships a **universal degenerate instance** for all block types:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

This stub is wired directly into the **production** certificate pool writer for the `ChainDB`:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

`processCerts` accepts the entire batch when `validateCert` returns no `Left` values, and throws `PerasCertInboundException` (triggering peer disconnection) only when at least one certificate fails:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) -> mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _)            -> throw (PerasCertValidationError errs)
``` [3](#0-2) 

Because `validatePerasCert` never returns `Left`, **no peer is ever disconnected for sending forged certificates**, and every certificate is stored with `vpcCertBoost = perasWeight params` applied unconditionally.

The same pattern applies to `validatePerasVote`, which skips all signature verification and only checks stake-distribution membership:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
``` [4](#0-3)

### Impact Explanation

**Critical — Bypass of Peras certificate checks enabling unauthorized certificate acceptance and chain-weight manipulation.**

1. **Unauthorized certificate injection**: Any peer on the Peras object-diffusion mini-protocol can send a `PerasCert` for any round and any block point. Because `validatePerasCert` always returns `Right`, the certificate is stored in the `PerasCertDB` / `ChainDB` with the full `perasWeight` boost attached.

2. **Chain selection manipulation**: Stored `ValidatedPerasCert` values contribute their `vpcCertBoost` to the weight of the certified block during chain selection. An attacker can therefore cause an honest node to assign artificially elevated weight to an adversary-controlled chain, potentially making it preferred over the honest chain — a direct violation of Peras chain-selection safety.

3. **Certificate slot squatting**: `implAddCert` silently drops any certificate for a round already present (`PerasCertAlreadyInDB`). An attacker who injects a fake certificate for round `r` first will cause the legitimate certificate for round `r` to be permanently ignored on that node, degrading Peras liveness.

4. **No peer accountability**: Because validation never fails, the disconnect-on-invalid-cert mechanism in `processCerts` is never triggered, so the attacker faces no network-level consequence.

---

### Likelihood Explanation

The vulnerability is reachable by any peer that can speak the Peras object-diffusion mini-protocol. No special privileges, keys, or stake are required — only the ability to connect to the node and send a well-formed `PerasCert` CBOR message. The `makePerasCertPoolWriterFromChainDB` function is explicitly documented as the production path (as opposed to `makePerasCertPoolWriterFromCertDB` which is for isolated tests), and the TODO comments confirm the stub is intentionally left in place pending "actual plumbing."

---

### Recommendation

1. **Implement real `validatePerasCert`**: Replace the stub with a function that verifies committee membership, cryptographic signatures (aggregate BLS / VRF outputs as appropriate), round number bounds, and that the boosted block point is a known, valid block on a plausible chain.

2. **Implement real `validatePerasVote`**: Add signature verification (`verifyVoteSignature`) analogous to the `EveryoneVotes` and `WFALS` committee implementations already present in `Ouroboros.Consensus.Committee`.

3. **Gate the production path**: Until real validation is in place, the `makePerasCertPoolWriterFromChainDB` path should either be disabled or guarded by a feature flag so that the stub cannot be reached from the network.

4. **Enforce round-uniqueness at the network layer**: Even after real validation is added, consider rejecting duplicate-round certificates at the protocol level before they reach the DB, to prevent squatting attacks.

---

### Proof of Concept

An attacker connects to a node running the Peras object-diffusion mini-protocol and sends a batch containing one `PerasCert` with:
- `pcCertRound = r` (any round not yet in the DB)
- `pcCertBoostedBlock = <adversary block point>`

`processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{vpcCert=cert, vpcCertBoost=perasWeight mkPerasParams}` without any check. The certificate is timestamped and stored via `ChainDB.addPerasCertAsync`. Chain selection subsequently reads the `PerasWeightSnapshot` from the `PerasCertDB`, finds the boost for the adversary block, and adds `vpcCertBoost` to that block's chain weight — potentially causing the node to switch to the adversary's chain. No disconnection occurs; the attacker may repeat this for every subsequent round.

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
