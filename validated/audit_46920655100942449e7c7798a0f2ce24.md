### Title
Unchecked Detached `burn` Call in `safe_mint_callback` Leaves UTXO Unprotected and Bridge Supply Inflated — (File: `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

---

### Summary

In `safe_mint_callback`, when `safe_mint` returns `U128(0)` (recipient not registered), the bridge removes the UTXO from `verified_deposit_utxo` and fires a compensating `burn` call with `.detach()`. Because the result of that burn is never checked, a failure leaves the bridge with inflated nBTC supply in its own balance and the UTXO unguarded — allowing the same deposit proof to be re-submitted via the standard `verify_deposit` path to mint a second time.

---

### Finding Description

`safe_mint` in the nBTC contract unconditionally mints `amount` tokens into the bridge's own balance before checking whether the recipient is registered:

```rust
// contracts/nbtc/src/lib.rs:112-115
self.token.internal_deposit(&self.bridge_id, amount.into());
if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0));
}
``` [1](#0-0) 

When `safe_mint_callback` observes that return value of `0`, it treats the deposit as failed, removes the UTXO from `verified_deposit_utxo`, and issues a compensating `burn` — but with `.detach()`, so the outcome is never inspected:

```rust
// contracts/satoshi-bridge/src/btc_light_client/deposit.rs:439-451
self.data_mut()
    .verified_deposit_utxo
    .remove(&pending_utxo_info.utxo_storage_key);   // ← UTXO unguarded immediately

ext_nbtc::ext(self.internal_config().nbtc_account_id.clone())
    .with_static_gas(GAS_FOR_BURN_CALL)
    .burn(env::current_account_id(), mint_amount, relayer_account_id, U128(0))
    .detach();                                        // ← result never checked
``` [2](#0-1) 

`GAS_FOR_BURN_CALL` is only 5 Tgas: [3](#0-2) 

If the `burn` cross-contract call fails for any reason (gas exhaustion, nbtc contract panic, insufficient bridge balance due to a concurrent operation), the two-step rollback is only half-complete:

| State after failed burn | Expected | Actual |
|---|---|---|
| `verified_deposit_utxo` contains UTXO key | yes | **no** (removed at line 441) |
| Bridge nBTC balance | unchanged | **inflated by `mint_amount`** |

Because `verified_deposit_utxo` no longer contains the key, the guard in `verify_deposit_callback` — `require!(self.data_mut().verified_deposit_utxo.insert(...), "Already deposit utxo")` — will succeed for the same UTXO, allowing a second mint: [4](#0-3) 

The standard `verify_deposit_callback` then calls `internal_mint_promise`, which calls `nbtc.mint(recipient, amount, ...)`, minting a fresh batch of tokens to the user on top of the already-inflated bridge balance. [5](#0-4) 

---

### Impact Explanation

**Critical.** A successful exploit produces two distinct harms simultaneously:

1. **Unauthorized double-minting of nBTC.** The same BTC UTXO backs two separate mint operations: the tokens already sitting in the bridge balance (from the failed-burn path) plus a fresh `mint` to the attacker's registered account via `verify_deposit`. Total nBTC supply exceeds the BTC held in custody.

2. **Permanent supply inflation.** Even without a follow-up `verify_deposit`, the tokens minted into the bridge balance by `safe_mint` but never burned remain there indefinitely, inflating the backed supply.

Both outcomes match the allowed Critical impact: *unauthorized minting* and *significant loss/destruction of protocol funds* (backed-supply invariant broken).

---

### Likelihood Explanation

**Medium.** The trigger condition — the `burn` cross-contract call failing — is not directly attacker-controlled under normal operation, but it is realistic:

- **Gas exhaustion:** `GAS_FOR_BURN_CALL = 5 Tgas` is a tight budget. If the NEAR runtime schedules the detached receipt under gas pressure, or if a future nbtc upgrade adds even modest logic to `burn`, the call can run out of gas and silently fail.
- **nbtc contract panic:** Any panic inside `burn` (e.g., arithmetic overflow if bridge balance is unexpectedly low due to a concurrent operation) causes the detached promise to fail with no rollback.
- **Attacker-assisted setup:** An attacker can deliberately target an unregistered account as the deposit recipient, guaranteeing `safe_mint` returns `U128(0)` and the detached burn path is always taken. They then only need to wait for or induce a burn failure before re-submitting the proof via `verify_deposit`.

---

### Recommendation

Replace the fire-and-forget `.detach()` with a chained callback that checks the burn result and re-inserts the UTXO key into `verified_deposit_utxo` if the burn fails, mirroring the pattern already used in `verify_withdraw_burn_callback`:

```rust
ext_nbtc::ext(...)
    .with_static_gas(GAS_FOR_BURN_CALL)
    .burn(env::current_account_id(), mint_amount, relayer_account_id, U128(0))
    .then(
        Self::ext(env::current_account_id())
            .with_static_gas(GAS_FOR_BURN_CALLBACK)
            .safe_mint_burn_callback(pending_utxo_info.utxo_storage_key),
    );
```

In `safe_mint_burn_callback`, if `is_promise_success()` is false, re-insert the UTXO key so the deposit cannot be replayed. Alternatively, keep the UTXO in `verified_deposit_utxo` before firing the burn and only remove it inside a successful burn callback — the same "mutate state before cross-contract call, roll back in callback on failure" pattern documented in the project's own security invariants. [6](#0-5) 

---

### Proof of Concept

1. Attacker controls NEAR account `attacker.near` (not registered on nBTC).
2. Attacker sends `X` satoshis to the deposit address derived from a `DepositMsg` naming `attacker.near` as recipient.
3. Relayer calls `safe_verify_deposit(proof, DepositMsg{recipient: "attacker.near", ...})`.
4. `verify_safe_deposit_callback` inserts UTXO key into `verified_deposit_utxo` and calls `safe_mint("attacker.near", X, ...)`.
5. `safe_mint` mints `X` nBTC to bridge balance, returns `U128(0)` (attacker not registered).
6. `safe_mint_callback` removes UTXO key from `verified_deposit_utxo` and fires `burn(bridge, X).detach()`.
7. The burn fails (e.g., gas exhaustion at 5 Tgas, or attacker times a concurrent operation to drain bridge balance).
8. Attacker registers `attacker.near` on nBTC (trivial: call `storage_deposit`).
9. Attacker (or any relayer) calls `verify_deposit(same_proof)`.
10. `verify_deposit_callback` finds UTXO key absent from `verified_deposit_utxo` → `insert` succeeds → calls `mint("attacker.near", X, ...)`.
11. Attacker receives `X` nBTC. Bridge balance still holds the un-burned `X` nBTC from step 5. Total nBTC supply is now `2X` backed by `X` satoshis.
