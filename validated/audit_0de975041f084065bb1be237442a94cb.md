### Title
Peras Weight Boost Ignored in `checkPreferTheirsOverOurs` Causes Incorrect Peer Disconnection and Chain Selection Failure - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

The `checkPreferTheirsOverOurs` function in the ChainSync client hardcodes `emptyPerasWeightSnapshot` when evaluating whether a candidate chain is preferable to the current chain during the forecast-horizon-exceeded fallback path. This is the direct analog of the GMX bug: the primary code path applies the full check (with Peras weights), but the fallback path silently drops the secondary component (Peras weight boosts), causing the node to incorrectly disconnect from peers offering legitimately heavier Peras-boosted chains.

---

### Finding Description

When a header from a peer is beyond the forecast horizon, `readLedgerStateHelper` calls `checkPreferTheirsOverOurs` to decide whether to keep waiting or disconnect:

```haskell
-- ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← hardcoded empty, ignores all Peras boosts
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse ...
``` [1](#0-0) 

The **primary path** — normal chain selection in `chainSelectionForBlock` and `chainSelection` — correctly passes the live `weights :: PerasWeightSnapshot blk` to `preferAnchoredCandidate`: [2](#0-1) 

The **fallback path** (`checkPreferTheirsOverOurs`) uses `emptyPerasWeightSnapshot`, which causes `preferAnchoredCandidate` to fall into its non-Peras branch and compare only raw block numbers: [3](#0-2) 

In Peras, the total weight of a chain fragment is `blockNo + weightBoost`. A chain with fewer blocks but a large Peras boost can be strictly heavier than a longer chain with no boost: [4](#0-3) 

The `PerasWeightSnapshot` is populated from certificates stored in `PerasCertDB` and is non-empty whenever any Peras certificate has been received: [5](#0-4) 

The structural parallel to the GMX bug is exact:

| GMX (Solidity) | Ouroboros Consensus (Haskell) |
|---|---|
| Happy path: swap succeeds → `outputAmount` combines both tokens → `minOutputAmount` check applied | Happy path: header within forecast horizon → `preferAnchoredCandidate` called with real `weights` |
| Fallback path: swap fails → `secondaryOutputAmount` kept separate → **slippage check skipped** | Fallback path: header beyond forecast horizon → `preferAnchoredCandidate` called with `emptyPerasWeightSnapshot` → **Peras weight check skipped** |

---

### Impact Explanation

Consider:
- **Our chain**: 120 blocks, no Peras boost → total weight 120
- **Candidate chain**: 100 blocks, Peras boost of 50 → total weight 150

With the real weight snapshot, `preferAnchoredCandidate` returns `ShouldSwitch` (candidate is heavier) → node correctly keeps waiting for the forecast horizon to advance.

With `emptyPerasWeightSnapshot`, `preferAnchoredCandidate` compares only block numbers (100 < 120) → returns `ShouldNotSwitch` → node throws `CandidateTooSparse` and **disconnects from the peer offering the heavier chain**.

The node then retains its current lighter chain and never adopts the correct Peras-boosted chain. This is a **chain selection failure**: an honest node is made to prefer a non-canonical, less-heavy chain, violating the Peras chain selection rule and the security guarantees of the protocol.

---

### Likelihood Explanation

The condition is triggered whenever all three hold simultaneously:
1. Peras is active — at least one certificate has been received, making `weights` non-empty.
2. A peer's candidate chain has a Peras-boosted block that makes it heavier than our chain despite having fewer blocks.
3. A header from that peer falls beyond the local forecast horizon (a normal occurrence during syncing or after a slot gap).

All three conditions are routine in a live Peras-enabled network. The TODO comment in the source code (`// TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64`) confirms the developers have already identified this as a defect.

---

### Recommendation

Replace the hardcoded `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live Peras weight snapshot. The ChainSync client already has access to the ChainDB (or can be given a `STM m (PerasWeightSnapshot blk)` reader), so the fix is to read the current snapshot and pass it to `preferAnchoredCandidate` instead of the empty one. Alternatively, as the TODO suggests, remove the check entirely if it can be shown that the Genesis density check subsumes it.

---

### Proof of Concept

1. Peras is active; a certificate has boosted block `B` on a fork chain by weight 50.
2. Our chain has 120 blocks (total weight 120). The fork chain has 100 blocks + boost 50 = total weight 150.
3. A peer sends us header 101 of the fork chain. This header is beyond our forecast horizon (our ledger state is too far behind to forecast the required `LedgerView`).
4. `readLedgerStateHelper` calls `checkPreferTheirsOverOurs`.
5. `preferAnchoredCandidate cfg emptyPerasWeightSnapshot ourFrag theirFrag` compares block numbers: 120 vs 100 → `ShouldNotSwitch GT`.
6. `checkPreferTheirsOverOurs` throws `CandidateTooSparse` → node disconnects from the peer.
7. The node never downloads the fork chain's blocks, never validates them, and never switches to the heavier chain.
8. The node remains on the lighter chain (weight 120) while the rest of the Peras-enabled network has converged on the heavier chain (weight 150). [6](#0-5) [7](#0-6)

wsvTotalWeight :: WeightedSelectView proto -> PerasWeight

wsvTotalWeight wsv =

instance Ord (TiebreakerView proto) => Ord (WeightedSelectView proto) where
  compare =
    mconcat
      [ compare `on` wsvTotalWeight
      , compare `on` wsvTiebreaker

data WeightedSelectViewReasonForSwitch p
  = Heavier (Comparing PerasWeight)
  | WeightedSelectViewTiebreak (ReasonForSwitch (TiebreakerView p))

deriving instance
  Show (ReasonForSwitch (TiebreakerView p)) => Show (WeightedSelectViewReasonForSwitch p)

instance ChainOrder (TiebreakerView proto) => ChainOrder (WeightedSelectView proto) where
  type ChainOrderConfig (WeightedSelectView proto) = ChainOrderConfig (TiebreakerView proto)
  type ReasonForSwitch (WeightedSelectView proto) = WeightedSelectViewReasonForSwitch proto

  preferCandidate cfg ours cand =
    case compare (wsvTotalWeight ours) (wsvTotalWeight cand) of
      LT -> ShouldSwitch (Heavier $ Comparing (wsvTotalWeight ours) (wsvTotalWeight cand))
      EQ -> case preferCandidate cfg (wsvTiebreaker ours) (wsvTiebreaker cand) of
