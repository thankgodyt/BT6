### Title
Peras Certificate Validation Stub Unconditionally Accepts Any Inbound Certificate, Enabling Unauthorized Chain-Weight Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The sole `BlockSupportsPeras` instance in the codebase provides a degenerate stub for `validatePerasCert` that unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or eligibility checks. When Peras is enabled, any unprivileged peer can send a crafted `PerasCert` via the live `hPerasCertDiffusionClient` miniprotocol handler. The node accepts it, stores it in `PerasCertDB`, and triggers chain selection with the artificial weight boost, potentially causing the node to prefer a non-canonical chain.

This is the direct consensus analog of the external report: the system **appears to support** Peras certificate validation (the miniprotocol handler is registered and active) but **lacks the actual mechanism** to perform it (the validation body is a stub that always succeeds), mirroring the pattern of a contract that exposes a `ctx.value` field but has no `receive()` function.

---

### Finding Description

**Root cause — `validatePerasCert` stub:** [1](#0-0) 

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
```

This is the **only** `BlockSupportsPeras` instance in the repository. It applies to every block type, including Cardano blocks, via the `StandardHash blk` constraint. The function body ignores the certificate's content entirely and returns a `ValidatedPerasCert` carrying the full configured `perasWeight params` boost.

**Live miniprotocol handler that feeds into this stub:**

The `hPerasCertDiffusionClient` handler in `NodeToNode.hs` is wired up and active when Peras is enabled: [2](#0-1) 

It calls `makePerasCertPoolWriterFromChainDB`, which validates each inbound certificate using `validatePerasCert` before forwarding it to `ChainDB.addPerasCertAsync`.

**Chain selection consequence:**

Once a `ValidatedPerasCert` is stored in `PerasCertDB`, `chainSelSync` in `ChainSel.hs` is triggered for the boosted block: [3](#0-2) 

If the boosted block is present in the `VolatileDB`, chain selection runs immediately and the node may switch to the chain containing the artificially boosted block.

**End-to-end exploit path:**

1. Attacker connects to a Peras-enabled node as an ordinary peer.
2. Attacker sends a crafted `PerasCert` with `pcCertBoostedBlock` pointing to any block hash the attacker knows is in the node's `VolatileDB` (observable from the ChainSync miniprotocol).
3. `validatePerasCert` returns `Right` unconditionally.
4. The cert is stored in `PerasCertDB` with a weight boost of `perasWeight params`.
5. `chainSelSync` triggers chain selection for the boosted block.
6. The node's `preferAnchoredCandidate` now computes a higher `wsvTotalWeight` for any candidate fragment containing the boosted block, potentially switching to a non-canonical chain. [4](#0-3) 

---

### Impact Explanation

When Peras is enabled, an unprivileged peer can inject an arbitrary number of fake certificates, each granting a full `perasWeight` boost to any block of the attacker's choosing. Because `wsvTotalWeight` is the primary chain-selection criterion under Peras, a sufficiently boosted non-canonical fork can be made to appear heavier than the honest chain, causing the node to roll back and adopt the adversary's fork.

This is a **Critical** impact: bypass of Peras certificate validation that enables unauthorized certificate acceptance and chain-selection manipulation, matching the scope criterion: *"Bypass of … certificate/vote verification … that enables unauthorized block, vote, or certificate acceptance"* and *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain."* [5](#0-4) 

---

### Likelihood Explanation

- Peras is **disabled by default** (`PerasUnsupported` in version data); exploitation requires Peras to be explicitly enabled.
- Once Peras is enabled, the attack requires **no special privileges**: any peer that can complete the node-to-node handshake can send a `PerasCert` message.
- The attacker needs only a block hash present in the target's `VolatileDB`, which is trivially observable via the ChainSync miniprotocol.
- The TODO comment at the issue tracker reference (`cardano-peras/issues/120`) confirms this is a known incomplete implementation, not a deliberate design choice.

---

### Recommendation

Replace the degenerate `validatePerasCert` stub with a real implementation that:

1. Verifies the certificate's aggregate cryptographic signature against the claimed committee members' keys.
2. Checks that the claimed voters are eligible members of the committee for the given `pcCertRound`.
3. Verifies that the aggregate stake of the signers meets the quorum threshold (`stakeAboveThreshold`).
4. Validates that `pcCertBoostedBlock` refers to a block within the valid boosting window for the round.

Until a real implementation is available, the `hPerasCertDiffusionClient` handler should refuse to process inbound certificates (analogous to how the `txSubmissionProt` in `ImmDBServer` stubs out an unsupported protocol with `forever $ threadDelay 10`), rather than silently accepting all of them. [6](#0-5)

### Proof of Concept

```
-- Deterministic reproduction on a private testnet with Peras enabled:

1. Run a Cardano node with Peras enabled (eraPerasRoundLength set).

2. Connect as a peer and complete the NtN handshake.

3. Via the PerasCertDiffusion miniprotocol, send:
     PerasCert
       { pcCertRound    = <any round number>
       , pcCertBoostedBlock = <BlockPoint of a block observed via ChainSync
                               that is on a minority fork in the VolatileDB>
       }

4. Observe (via tracing) that the node logs
   "ChainSelectionForBoostedBlock" and switches to the minority fork,
   because the fake certificate grants it a weight boost of `perasWeight params`
   without any signature or eligibility check.
```

The `validatePerasCert` stub at lines 353–358 of `SupportsPeras.hs` is the single necessary and sufficient vulnerable step: removing it (or replacing it with `Left PerasValidationErr`) eliminates the attack entirely. [7](#0-6)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes

  -- Deliver promise indicating that we processed the cert.
  lift $ atomically $ putTMVar varProcessed certResult
