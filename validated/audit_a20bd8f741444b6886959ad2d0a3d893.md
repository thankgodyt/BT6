### Title
Missing Total-Stake Bounds Check in Peras Vote Accumulation Enables False Quorum and Unauthorized Certificate Forging — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Peras/Vote/Aggregation.hs`, `File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`updateTargetVoteTally` accumulates `ptvtTotalStake` from peer-supplied votes with no upper-bound check against the total stake in the system. `stakeAboveThreshold`, the sole quorum gate, compares this running total against the quorum threshold without enforcing that both values are expressed in the same units. The code itself documents this gap with a TODO. Because `validatePerasVote` is an acknowledged stub that skips all validation beyond voter-ID lookup, an unprivileged peer can send votes whose accumulated stake trivially exceeds the threshold, causing a certificate to be forged for an adversary-chosen block and that block's chain to be boosted in chain selection.

---

### Finding Description

**Step 1 — Unbounded accumulation in `updateTargetVoteTally`.**

`updateTargetVoteTally` adds each incoming vote's `vpvVoteStake` to `ptvtTotalStake` with no cap:

```haskell
-- Aggregation.hs line 453-456
(pvaVotes', pvaTotalStake')
  | (Nothing, votes') <- swapVote vote ptvtVotes =
      (votes', ptvtTotalStake + vpvVoteStake (forgetArrivalTime vote))
```

There is no check that the running total does not exceed 1.0 (for normalized relative stake) or the total lovelace supply (for absolute stake). [1](#0-0) 

**Step 2 — Unit-mismatch in `stakeAboveThreshold`.**

The quorum gate compares the accumulated `PerasVoteStake` (a `Rational`) directly against the quorum threshold, but the function's own documentation acknowledges the comparison is only meaningful when both values are in the same units, with no enforcement:

```haskell
-- SupportsPeras.hs lines 153-173
-- TODO: this function assumes that the 'PerasVoteStake' and the quorum
-- threshold used in 'PerasParams' are expressed in the same units.
-- ...this function only makes sense when both values are relative
-- (normalized) values, so we should either normalize the 'PerasVoteStake'
-- before calling this function...
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
``` [2](#0-1) 

If the `PerasVoteStakeDistr` is populated with absolute lovelace values (the natural Cardano ledger representation), a single vote from any stakeholder with even modest stake (e.g., 1,000,000 lovelace) will produce a `ptvtTotalStake` that trivially exceeds a relative quorum threshold of `0.75`, immediately triggering certificate forging.

**Step 3 — Stub `validatePerasVote` does not prevent crafted stake values.**

The `validatePerasVote` implementation is an acknowledged stub that only checks voter membership in the stake distribution. It does not validate round eligibility, block validity, or cryptographic signatures:

```haskell
-- SupportsPeras.hs lines 360-371
-- TODO: perform actual validation against all possible 'PerasValidationErr' variants
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
``` [3](#0-2) 

**Step 4 — `implAddVote` explicitly defers non-trivial validation.**

The production vote-DB insertion function carries an open TODO acknowledging that the validation logic is incomplete:

```haskell
-- Impl.hs lines 172-173
-- TODO: we will need to update this method with non-trivial validation logic
-- see https://github.com/tweag/cardano-peras/issues/120
``` [4](#0-3) 

**Step 5 — Entry path via the Peras vote miniprotocol.**

`processVotes` in `PerasVote.hs` is the network-facing handler. It calls `validatePerasVote` (the stub above) and, on success, passes the vote directly to `implAddVote`:

```haskell
-- PerasVote.hs lines 178-189
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (...) votes
    mapM validateVote votesNotAlreadyInDb
  ...
  ([], validatedVotes) -> mapM_ (addVote . WithArrivalTime now) validatedVotes
``` [5](#0-4) 

The stake distribution is read from the ledger state at validation time via `getStakeDistrSTM`. [6](#0-5)

### Impact Explanation

When the unit mismatch is present (absolute lovelace in the distribution vs. relative quorum threshold), a single vote from any voter in the distribution causes `stakeAboveThreshold` to return `True`, triggering `updateCandidateVoteState` to call `forgePerasCert` for the adversary's chosen block. [7](#0-6) 

The resulting `ValidatedPerasCert` is stored in the `PerasVoteDB` and propagated to the `ChainDB`, where it boosts the adversary's chain by `perasWeight` in chain selection. This constitutes an unauthorized certificate acceptance and a chain-selection manipulation: honest nodes will prefer the adversary's boosted chain over the canonical chain, a direct Peras consensus safety failure.

**Impact class**: High — bypass of Peras certificate/quorum checks enabling unauthorized certificate acceptance and chain-selection manipulation.

---

### Likelihood Explanation

The `PerasVoteStake` type carries a comment explicitly stating there is no consensus on how to go from absolute ledger stake to relative committee stake, and that the current `Rational` representation is "the best approximation we have at the moment." [8](#0-7) 

The `stakeAboveThreshold` TODO confirms the normalization step is missing. [9](#0-8) 

Any deployment that populates `PerasVoteStakeDistr` with absolute lovelace values (the standard Cardano ledger representation) will exhibit the unit mismatch immediately. The attack requires only that the adversary control a voter ID present in the stake distribution — no key compromise, no stake majority, no admin access.

---

### Recommendation

1. **Enforce normalization before accumulation.** Before inserting a vote's stake into `ptvtTotalStake`, normalize `vpvVoteStake` by dividing by the total stake in the distribution. Add an invariant assertion that the normalized value is in `[0, 1]`.

2. **Add a total-stake cap in `updateTargetVoteTally`.** After accumulation, assert `ptvtTotalStake <= PerasVoteStake 1` (for normalized stake). This is the direct analog to the "total amount checking logic" recommended in the original report.

3. **Complete `stakeAboveThreshold`.** Either accept the total stake as a parameter and normalize internally, or require callers to pass pre-normalized values and enforce this with a type-level invariant.

4. **Complete `validatePerasVote` and `implAddVote`.** Resolve issue #120: validate round eligibility, block validity, and cryptographic signatures before accepting any vote into the DB.

---

### Proof of Concept

```
Precondition:
  - PerasVoteStakeDistr contains voter V with absolute stake S = 1_000_000 (lovelace)
  - perasQuorumStakeThreshold = 0.75 (relative)
  - perasQuorumStakeThresholdSafetyMargin = 0.0

Attack sequence:
  1. Adversary peer sends PerasVote { pvVoteRound = R, pvVoteBlock = adversaryBlock, pvVoteVoterId = V }
  2. processVotes calls validatePerasVote:
       lookupPerasVoteStake returns Just (PerasVoteStake (1_000_000 % 1))
       → ValidatedPerasVote { vpvVoteStake = 1_000_000 }
  3. implAddVote → updatePerasRoundVoteStates → updateCandidateVoteState
  4. updateTargetVoteTally: ptvtTotalStake = 0 + 1_000_000 = 1_000_000
  5. stakeAboveThreshold: 1_000_000 >= 0.75 + 0.0  → True
  6. forgePerasCert called → ValidatedPerasCert for adversaryBlock forged
  7. Certificate stored in PerasVoteDB, propagated to ChainDB
  8. Chain selection boosts adversaryBlock's chain by perasWeight
  9. Honest nodes switch to adversary's chain
``` [10](#0-9) [11](#0-10)

-- | Check whether a given vote stake is above the quorum threshold.
--
-- TODO: this function assumes that the 'PerasVoteStake' and the quorum
-- threshold used in 'PerasParams' are expressed in the same units. That is,
-- both are either absolute or relative (normalized) values. Under the current
-- current implementation of 'PerasParams', this function only makes sense when

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
