### Title
Peras Certificate Verification Bypass Allows Unprivileged Peer to Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal default instance of `BlockSupportsPeras` implements `validatePerasCert` as an unconditional `Right` — accepting every inbound certificate without any cryptographic or semantic check. The Peras certificate diffusion mini-protocol is wired into the production node-to-node handler, so any connected peer can inject a crafted certificate that boosts an arbitrary block. When Peras weights are active, chain selection uses those boosts to compare candidate fragments, meaning the attacker's certificate can cause an honest node to prefer a non-canonical fork.

---

### Finding Description

`validatePerasCert` in the universal default `BlockSupportsPeras` instance always returns `Right`: [1](#0-0)

This is the **universal** instance (`instance StandardHash blk => BlockSupportsPeras blk`), not a test stub: [2](#0-1) 

The Peras certificate diffusion inbound handler is wired into the production node-to-node protocol stack and calls `makePerasCertPoolWriterFromChainDB`, which invokes `validatePerasCert` on every inbound certificate: [3](#0-2) 

`makePerasCertPoolWriterFromChainDB` is confirmed to call `validatePerasCert` (4 call-sites in `ObjectPool/PerasCert.hs`):



Once accepted, the certificate is inserted into the `PerasCertDB` via `addPerasCertAsync`, which explicitly states it may trigger a chain-selection fork switch: [4](#0-3) 

Chain selection uses `preferAnchoredCandidate`, which, when the `PerasWeightSnapshot` is non-empty, compares fragments using `weightedSelectView` — incorporating the attacker-injected certificate boost: [5](#0-4) 

The analog to the external report is direct: just as `createAgent` allowed anyone to mint an `agentID` for any owner without restriction, `validatePerasCert` allows any peer to register a certificate for any block without restriction.

### Impact Explanation

An unprivileged peer can submit a crafted `PerasCert` naming any block as the boosted target. Because `validatePerasCert` performs no cryptographic or eligibility checks, the certificate is unconditionally accepted and stored. The resulting weight boost is reflected in the `PerasWeightSnapshot` used by `preferAnchoredCandidate`. If the attacker's certificate boosts a block on a minority fork, chain selection may switch to that fork, causing the honest node to diverge from the canonical chain. This is a **bypass of Peras certificate verification** enabling unauthorized chain selection manipulation — fitting the "High" impact category: *chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions*, and the "Critical" category: *bypass of Peras certificate checks that enables unauthorized certificate acceptance*.

---

### Likelihood Explanation

The Peras cert diffusion handler is active in the production node-to-node protocol stack (not gated behind a feature flag in the handler registration). Any peer that can establish a node-to-node connection can send a `PerasCert` message. No key material, stake, or privileged access is required. The only partial mitigation is that Peras weight boosts only influence chain selection when the `PerasWeightSnapshot` is non-empty; however, the attacker's own injected certificate populates that snapshot, removing even this barrier.

---

### Recommendation

1. Implement real cryptographic and eligibility validation inside `validatePerasCert` before the Peras cert diffusion handler is active in any network-connected node. At minimum, verify the aggregate BLS signature against the claimed voter set and confirm the voter set was legitimately elected for the stated round.
2. Until full validation is implemented, gate the inbound cert diffusion handler so it rejects all certificates (analogous to how the vote handler currently uses an empty stake distribution to reject all votes).
3. Track and close issue [#120](https://github.com/tweag/cardano-peras/issues/120) before any Peras-enabled release.

---

### Proof of Concept

On a private testnet with the Peras cert diffusion protocol enabled:

1. Connect to a target node as a peer.
2. Craft a `PerasCert` with `pcCertRound = <current round>` and `pcCertBoostedBlock = <tip of a minority fork>`.
3. Send the certificate via the Peras cert diffusion mini-protocol.
4. The node calls `validatePerasCert`, which returns `Right ValidatedPerasCert{..., vpcCertBoost = perasWeight params}` unconditionally.
5. `addPerasCertAsync` inserts the certificate and triggers chain selection.
6. `preferAnchoredCandidate` now uses `weightedSelectView` with the attacker's boost applied to the minority fork.
7. If the boosted fork's weighted suffix exceeds the canonical chain's weighted suffix, the node switches forks — observable via the node's chain-selection trace events (`TraceAddBlockEvent`). [6](#0-5) [4](#0-3) [5](#0-4)
