### Title
Unprotected `request_refund` Allows Attacker to Redirect Victim's BTC Refund to Arbitrary Address - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary

The `request_refund` function is callable by any unprivileged NEAR account and accepts a fully attacker-controlled `refund_address` parameter when the original `deposit_msg.refund_address` is `None`. An attacker can submit a refund request for a victim's unfinalized deposit, supplying their own BTC address as the destination. After the `unsafe_refund_timelock_sec` elapses, the attacker calls `execute_refund` to redirect the victim's BTC to themselves.

### Finding Description

`request_refund` has no access control and no check that the caller is the original depositor (`deposit_msg.recipient_id`): [1](#0-0) 

Inside `internal_request_refund`, the only guard on `refund_address` is a consistency check against `deposit_msg.refund_address` — but only when that field is `Some`. When it is `None`, the caller-supplied `refund_address` is stored verbatim with no further validation: [2](#0-1) 

The stored `refund_address` is later used unconditionally by `execute_refund` → `internal_execute_refund` → `build_refund_output` to construct the BTC output paying the refund: [3](#0-2) 

`execute_refund` itself is also callable by any account: [4](#0-3) 

The protocol acknowledges the risk of an attacker-supplied address by applying a longer `unsafe_refund_timelock_sec`, but this is only a delay — not a prevention: [5](#0-4) 

### Impact Explanation

If the DAO does not actively monitor and reject the malicious request within the `unsafe_refund_timelock_sec` window, the attacker successfully redirects the victim's BTC to their own address. The victim's deposit is permanently lost. This constitutes a significant theft of user funds (BTC/ZEC), matching the Critical allowed impact: *"Significant loss, theft, destruction, or permanent locking of user or protocol funds."*

### Likelihood Explanation

All inputs needed for the attack are publicly observable:
- The victim's `deposit_msg` is emitted on-chain via the `LogDepositAddress` event when the deposit address is generated.
- The BTC transaction is public on the Bitcoin/Zcash blockchain.

The attack is viable whenever a deposit is not finalized by a relayer (e.g., relayer downtime, network congestion, or a failed `verify_deposit` call). The attacker's only cost is the small NEAR storage deposit required by `request_refund` and `execute_refund`. The DAO rejection window is a mitigation but not a guarantee — if the DAO is unavailable, slow, or not monitoring all pending requests, the attack succeeds after the timelock.

### Recommendation

Validate that the caller of `request_refund` is the `deposit_msg.recipient_id` when `deposit_msg.refund_address` is `None`. Alternatively, require that `deposit_msg.refund_address` is always pre-set (i.e., `Some`) so the refund destination is locked at deposit time and cannot be overridden by a third party.

```rust
// In internal_request_refund, add:
if deposit_msg.refund_address.is_none() {
    require!(
        env::predecessor_account_id() == deposit_msg.recipient_id,
        "Only the deposit recipient can request a refund with an external refund_address"
    );
}
```

### Proof of Concept

1. Alice deposits BTC using a `deposit_msg` with `refund_address: None` (the common case for standard deposits).
2. The relayer fails to call `verify_deposit` (e.g., due to downtime).
3. Attacker observes Alice's `deposit_msg` from the on-chain `LogDepositAddress` event and the BTC transaction from the Bitcoin blockchain.
4. Attacker calls `request_refund` with:
   - `deposit_msg` = Alice's original deposit message
   - `refund_address` = attacker's own BTC address
   - `tx_bytes` = the real BTC transaction
   - Valid Light Client proof
5. The `request_refund_callback` verifies the BTC transaction is real and stores the attacker's address as `refund_address`.
6. After `unsafe_refund_timelock_sec` elapses (and if DAO does not reject), attacker calls `execute_refund`.
7. Alice's BTC is sent to the attacker's address via the MPC signing pipeline. [6](#0-5)

    /// Build a transparent refund output paying `refund_amount` to `refund_address`.
    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
    }
