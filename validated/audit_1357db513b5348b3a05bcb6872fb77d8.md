Audit Report

## Title
Reentrancy in `initTransfer1155` via Malicious ERC1155 Callback Allows Fraudulent `InitTransfer` Events Without Locking Tokens — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`initTransfer1155` increments `currentOriginNonce` and then makes an external call to an attacker-controlled ERC1155 contract. Because `currentOriginNonce` is a storage variable read again at emit-time, and because `onERC1155Received` only checks `operator == address(this)` (which a malicious token can satisfy trivially), a re-entrant call chain causes multiple `InitTransfer` events to be emitted — all with the same final nonce value — while zero ERC1155 tokens are ever transferred to the bridge. The NEAR side treats every such event as proof of locked funds and mints bridge tokens accordingly.

## Finding Description

`initTransfer1155` (lines 447–490) follows this order:

1. `currentOriginNonce += 1` — storage written
2. `IERC1155(tokenAddress).safeTransferFrom(msg.sender, address(this), tokenId, amount, "")` — **external call to attacker-controlled contract**
3. `initTransferExtension(msg.sender, deterministicToken, currentOriginNonce, ...)` — reads `currentOriginNonce` from storage
4. `emit BridgeTypes.InitTransfer(..., currentOriginNonce, ...)` — reads `currentOriginNonce` from storage [1](#0-0) 

The `onERC1155Received` guard (lines 522–535) only rejects calls where `operator != address(this)`. When the bridge calls `safeTransferFrom`, the bridge is the operator. A malicious token's `safeTransferFrom` can therefore call `onERC1155Received(msg.sender, ...)` — where `msg.sender` is the bridge — and the guard passes unconditionally. [2](#0-1) 

**Reentrancy chain (depth = 3 as in PoC):**

- Outer call: `currentOriginNonce` → N+1, calls malicious `safeTransferFrom`
  - Re-entry 1: `currentOriginNonce` → N+2, calls malicious `safeTransferFrom`
    - Re-entry 2: `currentOriginNonce` → N+3, calls malicious `safeTransferFrom`
      - Re-entry 3: `currentOriginNonce` → N+4, malicious token calls `onERC1155Received(bridge,…)` (passes), emits `InitTransfer` with **N+4**
    - Re-entry 2 resumes: malicious token calls `onERC1155Received(bridge,…)` (passes), emits `InitTransfer` with **N+4** (storage value unchanged)
  - Re-entry 1 resumes: same, emits `InitTransfer` with **N+4**
- Outer call resumes: same, emits `InitTransfer` with **N+4**

**Correction to the submitted report:** Because `currentOriginNonce` is a storage variable read at emit-time (not captured in a local variable before the external call), all four emitted events carry the same nonce (N+4), not distinct nonces N+1/N+2/N+3 as the report claims. The malicious token never transfers any tokens; it only calls `onERC1155Received` to satisfy the callback and allow each stack frame to proceed to emit.

The NEAR `fin_transfer_callback` validates only that the emitter is a registered factory and that the token has registered decimals — both satisfied for a token registered via the permissionless `logMetadata1155`. [3](#0-2) 

`logMetadata1155` has no access control: [4](#0-3) 

There is no `ReentrancyGuard` or `nonReentrant` modifier anywhere on `OmniBridge`: [5](#0-4) 

If the NEAR side deduplicates by `origin_nonce`, one fraudulent mint is produced per attack transaction. If it does not, all four events are processed independently. Either way, the attacker locks **zero** ERC1155 tokens and receives minted bridge tokens, directly violating the documented invariant: [6](#0-5) 

## Impact Explanation

This is unauthorized minting of bridge tokens without any corresponding locked collateral on EVM — a direct violation of the bridge's core accounting invariant. If the minted token has market value (traded on NEAR DEXes or used as collateral), the attacker profits immediately. If legitimate ERC1155 deposits later accumulate in the bridge for the same token, the inflated NEAR-side supply allows the attacker to redeem more tokens than were ever deposited, constituting direct theft of bridged funds. This matches the allowed critical impact: **unauthorized minting and balance manipulation that changes user or protocol balances**.

## Likelihood Explanation

The attack requires no privileged role and no victim interaction:

1. Deploy a malicious ERC1155 contract (gas only).
2. Call `logMetadata1155` (permissionless, no whitelist).
3. Wait for the NEAR relayer to register the token.
4. Call `initTransfer1155` with the malicious token.

The attack is fully self-contained, repeatable, and available to any EVM user.

## Recommendation

Add `ReentrancyGuardUpgradeable` to `OmniBridge` and apply `nonReentrant` to `initTransfer1155`, `initTransfer`, and `finTransfer`. Additionally, capture `currentOriginNonce` into a local variable before the external call so that each stack frame emits the nonce it incremented, not the final storage value:

```solidity
function initTransfer1155(...) external payable nonReentrant whenNotPaused(PAUSED_INIT_TRANSFER) {
    currentOriginNonce += 1;
    uint64 nonce = currentOriginNonce; // capture before external call
    ...
    IERC1155(tokenAddress).safeTransferFrom(...);
    ...
    emit BridgeTypes.InitTransfer(..., nonce, ...);
}
```

The same local-variable capture should be applied to `initTransfer` for consistency.

## Proof of Concept

**Setup:**
1. Deploy `MaliciousERC1155` pointing at the bridge (as in the submitted PoC).
2. Call `bridge.logMetadata1155(maliciousToken, tokenId)` — permissionless.
3. Wait for NEAR relayer to process the `LogMetadata` event and register token decimals.

**Exploit:**
4. Call `bridge.initTransfer1155(maliciousToken, tokenId, 1, 0, 0, "attacker.near", "")`.
5. Reentrancy fires (depth 0→3): four `InitTransfer` events are emitted, all with nonce N+4, while the bridge's ERC1155 balance of `maliciousToken` remains zero.
6. NEAR relayer submits each event to `fin_transfer` → `fin_transfer_callback`. Factory check passes (registered via `logMetadata1155`). Decimals check passes. Bridge mints tokens to `attacker.near` for each processed event.
7. Attacker repeats from step 4 with a fresh call to obtain additional fraudulent mints indefinitely.

**Verification:** A local Hardhat/Foundry fork test can confirm: (a) four `InitTransfer` events are emitted in a single transaction, (b) the bridge's `balanceOf(maliciousToken, tokenId)` is zero after the call, and (c) `currentOriginNonce` advanced by 4.
