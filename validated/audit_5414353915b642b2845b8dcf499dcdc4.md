### Title
`withdraw_rbf()` Uses Caller's Account Instead of Pending-Info Owner's Account for Capacity Check and RBF Association - (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary

`withdraw_rbf()` reads `env::predecessor_account_id()` (the caller) as the `account_id` for both the pending-sign capacity check and the downstream `withdraw_rbf_chain_specific()` call. The correct value is the `account_id` stored inside the `BTCPendingInfo` identified by `original_btc_pending_verify_id`. The sibling privileged function `cancel_withdraw()` performs this lookup correctly, making the asymmetry explicit.

### Finding Description

In `contracts/satoshi-bridge/src/api/bridge.rs`, `withdraw_rbf()` is a public, unprivileged function (only gated by the pause flag):

```rust
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,
    output: Vec<TxOut>,
    chain_specific_data: Option<ChainSpecificData>,
) {
    let account_id = env::predecessor_account_id();   // ← caller, not pending-info owner
    self.require_pending_sign_capacity(&account_id);

    self.withdraw_rbf_chain_specific(
        account_id,                                    // ← wrong account propagated downstream
        original_btc_pending_verify_id,
        output,
        chain_specific_data,
    );
}
``` [1](#0-0) 

The privileged `cancel_withdraw()` function, which performs the analogous operation, correctly reads the owner from the pending info:

```rust
let user_account_id = self
    .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
    .account_id
    .clone();
self.require_pending_sign_capacity(&user_account_id);
self.cancel_withdraw_chain_specific(user_account_id, ...);
``` [2](#0-1) 

`BTCPendingInfo` carries its own `account_id` field that records the original withdrawal initiator. [3](#0-2) 

The `account_id` passed into `withdraw_rbf_chain_specific` is used to associate the new RBF `BTCPendingInfo` with an account and to insert the new pending-sign id into that account's `btc_pending_sign_ids` set — exactly as `create_btc_pending_info` does for the original withdrawal. [4](#0-3) 

### Impact Explanation

Two concrete harms result from the wrong account being used:

1. **Capacity-check bypass on the pending-info owner.** `require_pending_sign_capacity` is evaluated against the *caller's* account, not the original withdrawal owner's account. An attacker with zero pending transactions always passes this check regardless of how many pending transactions the actual owner has. This bypasses the per-account pending-sign limit that is the bridge's primary rate-control mechanism. [5](#0-4) 

2. **RBF pending info associated with the wrong account.** The new RBF `BTCPendingInfo` is inserted under the caller's account, not the original owner's. The original owner's `btc_pending_sign_ids` is never updated, breaking the invariant that every pending sign id is tracked in the owning account. This corrupts per-account state and can permanently strand the original owner's withdrawal in an untrackable state.

The `output: Vec<TxOut>` parameter is attacker-controlled and is passed directly into the PSBT construction for the RBF transaction. If `withdraw_rbf_chain_specific` does not re-validate the output against the original withdrawal's target address (which is not enforced at the `withdraw_rbf` entry point), an attacker can supply a `TxOut` pointing to their own Bitcoin address, redirecting the victim's BTC. This would constitute unauthorized redirection of bridge-controlled funds.

### Likelihood Explanation

`withdraw_rbf` is a public function with no ownership check — any NEAR account can call it with any `original_btc_pending_verify_id`. No special role, leaked key, or privileged access is required. The attacker only needs to know the pending-verify id of a victim's in-flight withdrawal, which is emitted as an on-chain event (`GenerateBtcPendingInfo`) and is publicly observable. The attack is therefore trivially reachable by any bridge user.

### Recommendation

Replace `env::predecessor_account_id()` with the `account_id` stored in the `BTCPendingInfo`, mirroring the pattern already used in `cancel_withdraw()`:

```rust
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,
    output: Vec<TxOut>,
    chain_specific_data: Option<ChainSpecificData>,
) {
    let account_id = self
        .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
        .account_id
        .clone();
    self.require_pending_sign_capacity(&account_id);

    self.withdraw_rbf_chain_specific(
        account_id,
        original_btc_pending_verify_id,
        output,
        chain_specific_data,
    );
}
```

Additionally, add an explicit ownership check (`require!(account_id == env::predecessor_account_id(), "Not the withdrawal owner")`) so that only the original withdrawal initiator can submit an RBF.

### Proof of Concept

1. User A calls `ft_transfer_call` → `ft_on_transfer` → `create_btc_pending_info`. A `BTCPendingInfo` is created with `account_id = A` and `btc_pending_id = P`. Event `GenerateBtcPendingInfo { account_id: A, btc_pending_id: P }` is emitted publicly.
2. Attacker B (with no pending transactions) observes `P` on-chain.
3. B calls `withdraw_rbf(P, [TxOut { value: X, script_pubkey: B_btc_address }], None)`.
4. Inside `withdraw_rbf`: `account_id = B`. `require_pending_sign_capacity(&B)` passes (B has 0 pending). `withdraw_rbf_chain_specific(B, P, [malicious_output], None)` is called.
5. A new RBF `BTCPendingInfo` is created with `account_id = B`, spending the same UTXO set as A's original withdrawal but with B's Bitcoin address as the output.
6. The MPC signing service signs the RBF transaction. B's BTC address receives A's funds. [1](#0-0) [6](#0-5)
