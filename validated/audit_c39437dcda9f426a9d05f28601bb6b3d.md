Unconditional Peras Certificate Acceptance Bypasses Quorum Validation, Enabling Adversarial Chain Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The `validatePerasCert` implementation for the universal `BlockSupportsPeras` instance is a stub that unconditionally accepts every inbound Peras certificate without performing any quorum, signature, or committee membership check. This stub is wired directly into the production certificate ingestion path (`processCerts`), which is called for every certificate received from a peer via the object diffusion mini-protocol. An unprivileged peer can craft a `PerasCert` for any block and any round, have it accepted without challenge, and cause the receiving node to re-run chain selection with that block artificially boosted by `perasWeight = 15` weight units — potentially making the node prefer a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the mandatory gate for accepting inbound certificates:

```haskell
validatePerasCert ::
  PerasCfg blk ->
  PerasCert blk ->
  Either (PerasValidationErr blk) (ValidatedPerasCert blk)
```

The only concrete instance in the codebase is the degenerate catch-all instance. Its implementation is an explicit stub:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub returns `Right` for **every** certificate, regardless of its content. No quorum threshold is checked, no aggregate BLS signature is verified, no committee membership is validated, and no VRF eligibility proof is examined.

This stub is used in both production pool-writer constructors:

```haskell
-- makePerasCertPoolWriterFromCertDB (line 103):
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place

-- makePerasCertPoolWriterFromChainDB (line 126):
-- TODO replace when actual plumbing is in place
(validatePerasCert mkPerasParams)
``` [2](#0-1) 

The `processCerts` function calls `validateCert` on every inbound certificate from a peer, and since validation always succeeds, every certificate is timestamped and forwarded to `addCert` / `addPerasCertAsync`: [3](#0-2) 

Once accepted, the certificate is processed by `chainSelSync`, which triggers `chainSelectionForBlock` for the boosted block: [4](#0-3) 

Chain selection now uses `WeightedSelectView.preferCandidate`, which compares `wsvTotalWeight` — the sum of `BlockNo` and `wsvWeightBoost`. The boost contributed by the fake certificate is `perasWeight = 15` (from `mkPerasParams`): [5](#0-4) [6](#0-5) 

The analog to the Lido DAO quorum bug is exact: in Lido, the `quorum` variable is not tied to the actual number of guardians, so a single signature suffices. Here, the quorum check (`stakeAboveThreshold`) is never invoked during certificate acceptance — the "quorum" is effectively zero, and a single peer's crafted message suffices to inject a boosted certificate.

---

### Impact Explanation

An adversary controlling a single peer connection can inject a `PerasCert` that boosts any block in the VolatileDB by `perasWeight = 15` weight units. Because `WeightedSelectView` compares `wsvTotalWeight = BlockNo + weightBoost`, a fork that is 15 blocks shorter than the honest chain can be made to appear heavier. This causes the honest node to switch to the adversarially boosted fork, constituting a **chain selection bug** where an unprivileged peer makes an honest node prefer a non-canonical chain beyond the intended security assumptions. [7](#0-6) 

---

### Likelihood Explanation

The attack requires only a single peer connection and the ability to send a crafted `PerasCert` message over the object diffusion mini-protocol. No key material, stake, or privileged access is needed. The entry point (`makePerasCertPoolWriterFromChainDB`) is the production path used by the running node. The stub is unconditional — there is no configuration flag or feature gate that would prevent the bypass.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real one that:
1. Verifies the aggregate BLS vote signature against the declared voter set.
2. Verifies VRF eligibility proofs for non-persistent committee members.
3. Checks that the total stake of the declared voters meets `perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin` (i.e., calls `stakeAboveThreshold`).
4. Verifies that each declared voter is a member of the correct voting committee for the certificate's round.

Until the real implementation is in place, the production pool writers should refuse all inbound certificates (return `Left PerasValidationErr` unconditionally) rather than accept them all.

### Proof of Concept

**Setup:** Node A is running with Peras enabled. Adversary controls peer B.

1. Peer B identifies a block `X` on a minority fork in Node A's VolatileDB (e.g., via ChainSync header exchange).
2. Peer B constructs a `PerasCert { pcCertRound = r, pcCertBoostedBlock = point(X) }` for any round `r` not yet in Node A's `PerasCertDB`.
3. Peer B sends this certificate to Node A via the object diffusion mini-protocol.
4. Node A calls `processCerts` → `validatePerasCert mkPerasParams cert` → returns `Right ValidatedPerasCert { vpcCertBoost = PerasWeight 15 }`.
5. Node A calls `addPerasCertAsync`, which enqueues `ChainSelAddPerasCert` in the chain selection queue.
6. `chainSelSync` processes the entry: adds the cert to `PerasCertDB`, then calls `chainSelectionForBlock` for block `X`.
7. `weightedSelectView` now computes `wsvWeightBoost` for any fragment containing `X` as `PerasWeight 15` higher than before.
8. `preferCandidate` returns `ShouldSwitch` for the fork containing `X` if it was within 15 blocks of the honest tip.
9. Node A switches to the adversarially boosted fork. [8](#0-7) [9](#0-8) [10](#0-9)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
