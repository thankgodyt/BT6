### Title
Peras Certificate Verification Bypass: `validatePerasCert` Unconditionally Accepts Any Certificate — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance, which applies to **all block types** including the production Cardano HFC block, implements `validatePerasCert` as a stub that unconditionally returns `Right` — accepting every inbound Peras certificate without any cryptographic or structural verification. An unprivileged peer can send a crafted certificate for any round and any block point, and the node will accept it as valid, store it, and use it to apply a Peras weight boost during chain selection.

---

### Finding Description

In `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`, the catch-all instance is declared:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
```

Its `validatePerasCert` method is:

```haskell
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

This is the **only** `BlockSupportsPeras` instance in the codebase. No more-specific instance overrides it for the Cardano HFC block type. The method ignores `params` and `cert` entirely and always returns `Right`, assigning the full `perasWeight` boost to whatever certificate was supplied.

The inbound certificate processing path in `processCerts` calls this function directly:

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _) ->
      throw (PerasCertValidationError errs)
``` [2](#0-1) 

Because `validateCert` is `validatePerasCert mkPerasParams` and always returns `Right`, the `(errs, _)` branch is **never reached**. Every certificate in the batch passes, regardless of its content.

The accepted `ValidatedPerasCert` carries a `vpcCertBoost` equal to `perasWeight params` (15 by default from `mkPerasParams`), which is then used in `PerasWeightSnapshot`-based chain selection via `preferAnchoredCandidate`. [3](#0-2) 

---

### Impact Explanation

An unprivileged peer connected via the Peras object-diffusion mini-protocol can craft a `PerasCert` for any `(roundNo, blockPoint)` pair and send it to a target node. The node will:

1. Accept the certificate unconditionally (no BLS/aggregate-signature check, no committee-membership check, no round-validity check).
2. Store it as a `ValidatedPerasCert` with the full Peras weight boost.
3. Apply that boost during chain selection, potentially preferring an adversarially chosen block over the honest canonical chain.

This is a **bypass of Peras certificate/vote verification checks** that enables unauthorized certificate acceptance and materially distorts chain selection — matching the "High" impact tier: *Bypass of certificate checks that enables unauthorized certificate acceptance*.

---

### Likelihood Explanation

The Peras object-diffusion protocol is production infrastructure wired into the node kernel. Any peer that can establish a connection and speak the Peras cert mini-protocol can trigger this path. No stake, no keys, and no prior knowledge of the chain are required — only the ability to construct a well-typed `PerasCert` message (round number + block point), which is trivially serializable. The likelihood is **Medium**: it is gated on Peras being enabled on the network, but once enabled the attack requires no privilege.

---

### Recommendation

Replace the stub with a real implementation that:

1. Verifies the aggregate BLS signature over the certificate's voter set against the registered committee keys for the claimed round.
2. Checks that the claimed `roundNo` is within the valid window relative to the current chain tip.
3. Verifies that the `boostedBlock` point exists in the node's chain and satisfies `perasBlockMinSlots`.
4. Confirms that the voter set meets the quorum threshold against the epoch's stake distribution.

Until a real implementation is available, the Peras cert diffusion mini-protocol should not be activated on any network where the weight boost affects chain selection.

---

### Proof of Concept

1. Connect to a target node that has the Peras cert object-diffusion protocol enabled.
2. Construct a `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock` pointing to an adversarially chosen block.
3. Send the certificate via the mini-protocol.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = 15 })` unconditionally.
5. The certificate is stored in the `PerasCertDB` and its boost is applied in subsequent calls to `preferAnchoredCandidate`, causing the node to prefer the adversarially boosted block over the honest chain tip. [4](#0-3) [5](#0-4)
