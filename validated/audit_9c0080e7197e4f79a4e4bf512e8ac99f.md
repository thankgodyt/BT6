### Title
Unauthorized `request_refund` Caller Can Redirect Victim's BTC Refund to Attacker-Controlled Address - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary
`request_refund` is publicly callable by any NEAR account. When a deposit was made with `deposit_msg.refund_address = None`, an attacker can call `request_refund` using the victim's correct `deposit_msg` and supply their own BTC address as `refund_address`. Because only one refund request can exist per UTXO, the victim is blocked from creating their own request. After `unsafe_refund_timelock_sec` elapses, anyone can call `execute_refund`, sending the victim's BTC to the attacker's address.

### Finding Description

`request_refund` performs no check that the caller is the intended recipient of the deposit or is otherwise authorized to set the `refund_address` for a given UTXO. [1](#0-0) 

Inside `internal_request_refund`, the only guard on `refund_address` is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [2](#0-1) 

When `deposit_msg.refund_address` is `None`, this block is skipped entirely. The attacker supplies the correct `deposit_msg` (derivable from the victim's NEAR account ID when all optional fields are `None`) and their own BTC address as `refund_address`. The callback then verifies only that the transaction output's `script_pubkey` matches the deposit address derived from `deposit_msg`: [3](#0-2) 

Since the attacker uses the correct `deposit_msg`, this check passes. The `RefundRequest` is stored with the attacker's BTC address.

A duplicate-request guard then blocks the victim from filing their own request for the same UTXO: [4](#0-3) 

`execute_refund` is also publicly callable with no ownership check: [5](#0-4) 

After `unsafe_refund_timelock_sec` elapses, the attacker (or anyone) calls `execute_refund`. `finalize_refund_with_psbt` builds a PSBT paying `refund_amount` to `refund_request.refund_address` — the attacker's BTC address: [6](#0-5) 

The MPC signs the transaction and the victim's BTC is broadcast to the attacker's address.

### Impact Explanation

The victim's BTC (held in the bridge's MPC-controlled deposit address) is sent to the attacker's Bitcoin address. The victim permanently loses their BTC. This is a direct theft of user funds from the bridge's custody. Even if the attack is detected and DAO/Operator rejects the request, the victim's funds are temporarily locked — they cannot file their own refund request while the attacker's request is active.

### Likelihood Explanation

- The attack requires the victim's deposit to be unprocessed (nBTC never minted). This is a realistic scenario for failed or stuck deposits.
- The attacker needs the victim's `deposit_msg`. For simple deposits (`recipient_id` only, all other fields `None`), the `deposit_msg` is trivially constructable from the victim's public NEAR account ID.
- The Bitcoin transaction (`tx_bytes`, `vout`) is public on-chain.
- The attacker must wait for `unsafe_refund_timelock_sec` without DAO/Operator intervention. If the operator is not monitoring, the attack succeeds.
- The attacker pays a non-refundable NEAR storage deposit (anti-spam fee), which is a minor economic barrier.

### Recommendation

Add an authorization check in `request_refund` (or its callback) that verifies the caller is either:
1. The `deposit_msg.recipient_id` (the intended nBTC recipient), or
2. A trusted relayer/operator.

Alternatively, when `deposit_msg.refund_address` is `None`, require the caller to be the `recipient_id` before accepting a caller-supplied `refund_address`. This mirrors the protection already in place when `deposit_msg.refund_address` is `Some` (the address is locked at deposit time and cannot be changed by a third party).

### Proof of Concept

1. Alice sends BTC to her deposit address derived from `DepositMsg { recipient_id: "alice.near", refund_address: None, ... }`. The deposit is never processed (nBTC never minted).
2. Attacker constructs the same `DepositMsg` (trivial since `recipient_id` is public and all other fields are `None`).
3. Attacker calls `request_refund(deposit_msg, attacker_btc_address, tx_bytes, vout, proof, None)`. The Light Client verifies the transaction; `request_refund_callback` confirms the `script_pubkey` matches — it does, because the correct `deposit_msg` was used. The `RefundRequest` is stored with `refund_address = attacker_btc_address`.
4. Alice attempts `request_refund` for the same UTXO — it fails: `"Refund request already exists for this UTXO"`.
5. After `unsafe_refund_timelock_sec`, attacker calls `execute_refund(utxo_storage_key, None)`. The bridge builds a PSBT paying Alice's BTC to the attacker's address, MPC signs it, and the transaction is broadcast.
6. Alice's BTC arrives at the attacker's Bitcoin address.

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
