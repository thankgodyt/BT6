### Title
Missing Signature Verification in `validatePerasVote` Allows Any Peer to Forge Peras Votes and Suppress Legitimate Voter Participation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasVote` implementation does not verify any cryptographic signature on incoming votes. The `PerasVote blk` data type itself carries no signature field. Any unprivileged peer can craft a `PerasVote` claiming to be from any legitimate voter, have it accepted and stored in the `PerasVoteDB`, and thereby permanently suppress the legitimate voter's actual vote for that round (duplicate vote IDs are silently ignored). This can prevent quorum from forming for the correct block or redirect Peras boosting weight toward an attacker-chosen block, causing chain selection divergence.

---

### Finding Description

The degenerate `BlockSupportsPeras` instance in `SupportsPeras.hs` defines the `PerasVote blk` data type with no signature field:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound  :: PerasRoundNo
  , pvVoteBlock  :: Point blk
  , pvVoteVoterId :: PerasVoterId
  }
``` [1](#0-0) 

The corresponding `validatePerasVote` implementation only checks whether the claimed `pvVoteVoterId` exists in the stake distribution — it performs no signature verification whatsoever:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [2](#0-1) 

This is the catch-all instance (`instance StandardHash blk => BlockSupportsPeras blk`) used in production. The `lookupPerasVoteStake` function resolves stake purely from the voter ID embedded in the vote data: [3](#0-2) 

The inbound vote processing pipeline in `processVotes` calls this validation and, on success, stores the vote in the `PerasVoteDB` under the key `PerasVoteId{pviRoundNo, pviVoterId}`: [4](#0-3) 

Once a vote with a given `(voterId, roundNo)` pair is stored, all subsequent votes with the same ID are **silently dropped** — both in `processVotes` (pre-filter) and in `implAddVote` (DB-level dedup): [5](#0-4) [6](#0-5) 

The `PerasVoteDB` model confirms the dedup semantics: a voter is considered to have already voted in a round if `(voterId, roundNo)` is present, and the new vote is ignored: [7](#0-6) 

**Attack path:**

1. Attacker (any connected peer) reads the public stake distribution to enumerate valid `PerasVoterId` values.
2. For each target voter, the attacker constructs a `PerasVote` with the victim's `pvVoteVoterId`, the current `pvVoteRound`, and an attacker-chosen `pvVoteBlock` (e.g., a different block than the one the victim would vote for).
3. The attacker sends this crafted vote to the honest node before the legitimate voter's vote arrives.
4. `validatePerasVote` accepts the vote (voter ID is in the stake distribution; no signature to check).
5. The vote is stored under `PerasVoteId{pviRoundNo, pviVoterId}`.
6. When the legitimate voter's actual vote arrives, it is silently dropped as a duplicate.

This is the direct analog of the external report: in that report, `msg.sender` (the caller) is used instead of the identity embedded in the signed data, and the `allocationID` is marked used with zero GRT. Here, the vote's `pvVoteVoterId` is accepted without proof of ownership, and the `(voterId, roundNo)` slot is marked used with an attacker-chosen block target.

---

### Impact Explanation

**High — Peras voting/certificate bypass and chain selection manipulation.**

An unprivileged peer can:

1. **Suppress legitimate votes**: By pre-empting a voter's slot with a crafted vote, the attacker prevents the legitimate vote from being counted. If enough voters are suppressed, quorum is never reached for the correct block, and the Peras boosting mechanism fails to operate.

2. **Redirect boosting weight**: The attacker can forge votes pointing to a different block than the one the legitimate voter would have chosen. If quorum is reached with these forged votes, the `PerasVoteDB` generates a certificate boosting the attacker's preferred block. This directly affects chain selection via the Peras weight mechanism, potentially causing an honest node to prefer a non-canonical chain. [8](#0-7) [9](#0-8) 

---

### Likelihood Explanation

**High.** The attack requires only:
- Being a connected peer (no special privileges).
- Knowledge of the current `PerasVoteStakeDistr` (public on-chain data).
- Sending a crafted vote before the legitimate voter's vote arrives (a race condition, but the attacker controls timing by sending immediately at round start).

No key compromise, stake majority, or social engineering is required.

---

### Recommendation

1. **Add a signature field to `PerasVote blk`** so that votes carry a cryptographic proof of origin (analogous to the `allocationIDProof` in the external report).
2. **Implement signature verification in `validatePerasVote`**: verify that the vote's signature was produced by the private key corresponding to the `pvVoteVoterId`'s registered VRF/KES key before accepting the vote.
3. Until the full committee selection scheme is in place (tracked in issue #120), at minimum reject votes whose `pvVoteVoterId` cannot be cryptographically proven to have authorized the specific `(pvVoteRound, pvVoteBlock)` pair. [10](#0-9)

### Proof of Concept

```
Node N is running with the degenerate BlockSupportsPeras instance.
Stake distribution contains voter V with PerasVoterId = KeyHash("pool1abc...").

Round R begins. Legitimate voter V prepares to send:
  PerasVote { pvVoteRound = R, pvVoteBlock = BlockA, pvVoteVoterId = "pool1abc..." }

Attacker A (connected peer) sends first:
  PerasVote { pvVoteRound = R, pvVoteBlock = BlockB, pvVoteVoterId = "pool1abc..." }

processVotes on node N:
  1. alreadyInDb does not contain PerasVoteId{R, "pool1abc..."} → vote not filtered
  2. validatePerasVote: lookupPerasVoteStake finds "pool1abc..." in stakeDistr → Right (stake)
  3. implAddVote stores PerasVoteId{R, "pool1abc..."} → vote for BlockB recorded

Legitimate voter V's vote arrives:
  processVotes filters: PerasVoteId{R, "pool1abc..."} ∈ alreadyInDb → vote silently dropped

Result: Node N counts V's stake toward BlockB (attacker's choice), not BlockA.
If enough voters are suppressed this way, quorum forms for BlockB, a certificate is
forged boosting BlockB, and chain selection prefers BlockB over the canonical chain.
``` [11](#0-10) [12](#0-11)

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
