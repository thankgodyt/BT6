### Title
Unchecked `vout` Index Causes Reachable Panic in Deposit Verification - (File: contracts/satoshi-bridge/src/btc_light_client/deposit.rs)

### Summary
The caller-supplied `vout` parameter is used to index directly into `transaction.output()` in both `internal_verify_deposit_entry` and `internal_safe_verify_deposit_entry` without first validating that `vout < transaction.output().len()`. An out-of-bounds value causes a Rust index panic, reverting the transaction. This is the direct analog of the reported `params.path` length-not-checked class: an attacker-controlled length/index is consumed by a parser/extractor without a prior bounds guard.

### Finding Description
In `internal_verify_deposit_entry` the decoded transaction's output vector is indexed at the caller-supplied `vout` on three separate lines before any length guard is present:

```rust
let deposit_amount = u128::from(transaction.output()[vout].value.to_sat()); // line 134
...
require!(
    deposit_address_script_pubkey == transaction.output()[vout].script_pubkey, // line 141
    "Invalid deposit tx_bytes"
);
let utxo = UTXO {
    ...
    balance: transaction.output()[vout].value.to_sat(), // line 149
};
```

The identical pattern appears in `internal_safe_verify_deposit_entry` at lines 193, 200, and 215.

`transaction.output()` returns a `Vec<TxOut>` whose length is determined entirely by the attacker-supplied `tx_bytes`. A transaction with zero outputs, or a `vout` value larger than the actual output count, causes Rust to panic with an index-out-of-bounds error. With `overflow-checks = true` (confirmed in `Cargo.toml`) the runtime will not silently wrap; it will panic and revert the call.

### Impact Explanation
The panic reverts the entire transaction. No bridge state is mutated (UTXOs are not yet removed at this point in the call), so there is no stuck state or fund loss. The impact is a publicly reachable panic-driven fault in the core production deposit path (`verify_deposit_v2` / `safe_verify_deposit`), qualifying as **Low** under the allowed scope: *"Publicly reachable invariant-violation, stuck-state, or panic-driven fault in production bridge/token paths without direct theft."*

### Likelihood Explanation
High. Both `verify_deposit_v2` and `safe_verify_deposit` are permissionless public entry points. Any NEAR account can call them with an arbitrary `vout` value (e.g., `vout = usize::MAX`) paired with a minimal valid `tx_bytes` that decodes to a transaction with fewer outputs, triggering the panic deterministically.

### Recommendation
Add an explicit bounds check immediately after decoding the transaction, before any output indexing:

```rust
require!(
    vout < transaction.output().len(),
    format!("vout {} out of bounds (tx has {} outputs)", vout, transaction.output().len())
);
```

Apply the same guard in both `internal_verify_deposit_entry` and `internal_safe_verify_deposit_entry`.

### Proof of Concept
1. Construct a minimal valid Bitcoin/Zcash transaction `tx_bytes` that decodes successfully and contains exactly one output (index 0).
2. Call `verify_deposit_v2` (or `safe_verify_deposit`) with that `tx_bytes` and `vout = 1` (or any value ≥ 1).
3. `WrappedTransaction::decode` succeeds; `transaction.output()` returns a one-element `Vec`.
4. `transaction.output()[1]` panics with index out of bounds.
5. The NEAR runtime reverts the transaction; the caller's attached gas is consumed and no deposit is recorded. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
