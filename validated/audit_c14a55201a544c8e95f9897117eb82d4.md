### Title
Peras Certificate Validation Is a No-Op Stub — Any Peer Can Inject Arbitrary Weight-Boosting Certificates to Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance implements `validatePerasCert` as an unconditional stub that always returns `Right` (success) without performing any cryptographic or committee-membership checks. The production certificate diffusion inbound handler wires this stub directly into the live `ChainDB` path. An unprivileged peer can therefore send a crafted `PerasCert` naming any block it chooses, have it accepted as "validated," and cause the receiving node to apply a `PerasWeight 15` boost to that block during chain selection — potentially making the node switch to a non-canonical chain.

---

### Finding Description

**Root cause — stub validator always accepts:**

`validatePerasCert` in the universal `BlockSupportsPeras` instance unconditionally wraps the incoming certificate in `Right`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature check, no committee-membership check, no round-validity check, and no boosted-block eligibility check is performed. Every inbound certificate passes.

**Production diffusion path wires the stub into ChainDB:**

`makePerasCertPoolWriterFromChainDB` — the handler used for all live node-to-node certificate diffusion — calls `validatePerasCert mkPerasParams` (the stub) and then forwards the result directly to `ChainDB.addPerasCertAsync`:

```haskell
opwAddObjects = \certs ->
    processCerts
      systemTime
      (ChainDB.getPerasCertIds chainDB)
      -- TODO replace when actual plumbing is in place
      (validatePerasCert mkPerasParams)
      (void . ChainDB.addPerasCertAsync chainDB)
      certs
``` [2](#0-1) 

This writer is registered as `hPerasCertDiffusionClient` in the live node-to-node protocol bundle, meaning every inbound certificate from every peer goes through this path: [3](#0-2) 

**`processCerts` accepts the batch and adds it to the DB:**

`processCerts` calls `validateCert` on each certificate; if all pass (they always do), it timestamps and stores them, then triggers chain selection: [4](#0-3) 

**Chain selection applies the weight boost:**

`chainSelSync` processes the certificate, looks up the boosted block in the VolatileDB, and calls `chainSelectionForBlock` for it, applying `PerasWeight 15` to that block's chain selection score: [5](#0-4) 

The weight boost is drawn from `mkPerasParams`:

```haskell
perasWeight = PerasWeight 15
``` [6](#0-5) 

---

### Impact Explanation

**Impact: Critical — Bypass of Peras certificate validation enabling unauthorized certificate acceptance and chain selection manipulation.**

An adversary who can connect to a node via the node-to-node protocol can:

1. Craft a `PerasCert` naming any block already in the target node's VolatileDB (or first deliver that block, then the certificate).
2. Send it via the `perasCertDiffusionProtocol`. The stub validator accepts it unconditionally.
3. The certificate is stored in `PerasCertDB` and triggers `chainSelectionForBlock` for the boosted block.
4. The boosted block now carries `PerasWeight 15` extra weight in chain selection comparisons (`preferAnchoredCandidate`).
5. The node may switch to the adversary's chain even though it would otherwise be rejected as non-canonical.

The Peras weight boost is specifically designed to make a boosted block very hard to roll back — an adversary exploiting this stub can weaponize that property against the honest chain.

---

### Likelihood Explanation

**Likelihood: High.**

- The attack requires only a standard node-to-node connection — no special privileges, no key material, no stake.
- The `perasCertDiffusionProtocol` is an active, registered mini-protocol in the live node bundle.
- The stub is in production source (not test/mock code) and is the only implementation of `validatePerasCert` for all block types.
- The only deduplication guard is a round-number membership check (`Set.member roundNo certIds`); a fresh round number bypasses even that.

---

### Recommendation

Replace the `validatePerasCert` stub with a real implementation that verifies:
- The certificate carries a valid aggregate signature from a quorum of legitimate committee members for the claimed round.
- The boosted block's slot satisfies the Peras eligibility rules (e.g., `perasBlockMinSlots`).
- The round number is within the valid acceptance window relative to the current chain tip.

Until real validation is in place, the `hPerasCertDiffusionClient` handler should either be disabled or gated behind a feature flag that is off by default, so that the stub cannot be reached from untrusted peers on a live network.

---

### Proof of Concept

On a private testnet running this codebase:

1. Connect a malicious peer to an honest node via the node-to-node protocol.
2. Deliver a valid block `B` on a minority fork to the honest node (so `B` is in its VolatileDB).
3. Send a `PerasCert { pcCertRound = <fresh round>, pcCertBoostedBlock = point(B) }` via the `perasCertDiffusionProtocol`.
4. `processCerts` calls `validatePerasCert mkPerasParams cert` → `Right (ValidatedPerasCert { vpcCertBoost = PerasWeight 15 })`.
5. `addPerasCertAsync` enqueues a `ChainSelAddPerasCert` event.
6. `chainSelSync` calls `chainSelectionForBlock` for `B`; `preferAnchoredCandidate` now sees `B`'s chain as heavier by 15 weight units.
7. If the honest node's current chain and the fork containing `B` are otherwise close in length, the node switches to the adversary's fork.

The entire attack requires no cryptographic material beyond a valid node-to-node connection.

```haskell
-- Process a Peras certificate by adding it to the PerasCertDB and potentially
-- performing chain selection if a candidate is now better than our selection.
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
