### Title
No Global Outbound Limit Check Against Destination Chain's u64 Maximum in `sign_transfer` - (File: near/omni-bridge/src/lib.rs)

### Summary
The NEAR Omni Bridge's `sign_transfer` function normalizes the transfer amount for the destination chain but never validates that the normalized amount — or the cumulative total already minted on the destination chain — fits within the destination chain's native `u64` balance type (Solana/Fogo use SPL token `u64` supply). The `locked_tokens` map tracks cumulative outbound amounts in `u128` with no cap against the destination chain's representable maximum. If the cumulative amount bridged to Solana exceeds `u64::MAX`, the SPL token program will reject the mint, permanently freezing the user's tokens that were already burned or locked on NEAR.

### Finding Description

`sign_transfer` in `near/omni-bridge/src/lib.rs` normalizes the transfer amount via `normalize_amount` and stores it as `U128` in the `TransferMessagePayload`. There is no check that the resulting `amount_to_transfer` fits within `u64::MAX` for SVM-family destination chains (`ChainKind::Sol`, `ChainKind::Fogo`):

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message
        .amount_without_fee()
        .near_expect(BridgeError::InvalidFee),
    decimals,
);

require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
// ← No check: amount_to_transfer <= u64::MAX for Sol/Fogo destinations
``` [1](#0-0) 

The cumulative outbound tracking is done via `locked_tokens: LookupMap<(ChainKind, AccountId), u128>`. The `lock_tokens` function only guards against `u128` overflow, not against the destination chain's `u64::MAX`:

```rust
let new_amount = current_amount
    .checked_add(amount)
    .near_expect(TokenLockError::LockedTokensOverflow);
``` [2](#0-1) 

On the Solana side, the `finalize_transfer` instruction does check that the individual transfer amount fits in `u64`:

```rust
data.amount.try_into().map_err(|_| error!(ErrorCode::AmountOverflow))?
``` [3](#0-2) 

But this check only catches a single transfer exceeding `u64::MAX`. It does **not** prevent the SPL token's cumulative total supply from overflowing `u64::MAX` across many individually-valid transfers. The SPL token program enforces `u64` for total supply; once the cumulative minted amount reaches `u64::MAX`, any further mint will be rejected by the SPL runtime — even if the individual transfer amount is small.

The `locked_tokens` map stores the cumulative outbound amount in `u128` with no cap: [4](#0-3) 

`ChainKind::Sol` and `ChainKind::Fogo` are both SVM chains with `u64`-bounded SPL token supplies: [5](#0-4) 

### Impact Explanation

When the cumulative amount bridged to Solana approaches `u64::MAX` (18,446,744,073,709,551,615 base units):

1. A user calls `ft_transfer_call` → `ft_on_transfer` → `init_transfer_internal`. Tokens are **burned or locked on NEAR** and the transfer is stored in `pending_transfers`.
2. A relayer calls `sign_transfer`. NEAR performs no `u64::MAX` check; MPC signs the payload with the full `u128` amount.
3. The relayer submits to Solana. The SPL token program rejects the mint because `current_supply + amount > u64::MAX`.
4. The user's tokens are **permanently frozen**: already burned/locked on NEAR, unmintable on Solana, with no automatic refund path.

This constitutes permanent freezing of bridged funds, which is in the Critical allowed impact scope. [6](#0-5) 

### Likelihood Explanation

**Low.** Reaching `u64::MAX` in cumulative bridged supply requires an astronomically large total volume (~18.4 quintillion base units). For tokens with standard decimals (6–9), this translates to billions of whole tokens. While unlikely under normal conditions, it is a reachable protocol-level state with no on-chain enforcement preventing it, and the impact when triggered is irreversible fund loss.

### Recommendation

In `sign_transfer`, after computing `amount_to_transfer`, add a destination-chain-aware cap check:

```rust
if transfer_message.get_destination_chain().is_svm_chain() {
    require!(
        amount_to_transfer <= u64::MAX as u128,
        BridgeError::AmountOverflow.as_ref()
    );
}
```

Additionally, in `lock_tokens_if_needed` (or `init_transfer_internal`), enforce a cumulative cap for SVM destinations:

```rust
if chain_kind.is_svm_chain() {
    require!(
        new_amount <= u64::MAX as u128,
        TokenLockError::LockedTokensOverflow.as_ref()
    );
}
``` [7](#0-6) 

### Proof of Concept

1. Deploy a bridged token on Solana with 9 decimals (NEAR side also 9 decimals, no normalization).
2. Over many transactions, bridge a cumulative total of `u64::MAX - 1` base units from NEAR to Solana. Each individual transfer is valid; Solana mints succeed.
3. A user initiates one more transfer of `2` base units. NEAR burns the tokens and stores the transfer. `locked_tokens[(Sol, token)]` becomes `u64::MAX + 1` (stored as `u128`, no panic).
4. Relayer calls `sign_transfer`. `amount_to_transfer = 2`, which passes the `> 0` check. MPC signs.
5. Relayer submits to Solana. `data.amount.try_into::<u64>()` succeeds (amount = 2). But the SPL `mint_to` CPI fails because `current_supply (u64::MAX - 1) + 2 > u64::MAX`.
6. The user's 2 base units are permanently lost: burned on NEAR, unmintable on Solana. [8](#0-7) [9](#0-8)

    pub fn sign_transfer(
        &mut self,
        transfer_id: TransferId,
        fee_recipient: Option<AccountId>,
        fee: &Option<Fee>,
    ) -> Promise {
        let transfer_message = self.get_transfer_message(transfer_id);

        if let Some(fee) = &fee {
            require!(
                &transfer_message.fee == fee,
                BridgeError::InvalidFee.as_ref()
            );
        }

        let token_address = self
            .get_token_address(
                transfer_message.get_destination_chain(),
                self.get_token_id(&transfer_message.token),
            )
            .unwrap_or_else(|| {
                env::panic_str(BridgeError::FailedToGetTokenAddress.to_string().as_str())
            });

        let decimals = self
            .token_decimals
            .get(&token_address)
            .near_expect(BridgeError::TokenDecimalsNotFound);
        let amount_to_transfer = Self::normalize_amount(
            transfer_message
                .amount_without_fee()
                .near_expect(BridgeError::InvalidFee),
            decimals,
        );

        require!(
            amount_to_transfer > 0,
            BridgeError::InvalidAmountToTransfer.as_ref()
        );

        let message = DestinationChainMsg::from_json(&transfer_message.msg)
            .and_then(|s| s.destination_msg())
            .unwrap_or_default();

        let transfer_payload = TransferMessagePayload {
            prefix: PayloadType::TransferMessage,
            destination_nonce: transfer_message.destination_nonce,
            transfer_id,
            token_address,
            amount: U128(amount_to_transfer),
            recipient: transfer_message.recipient,
            fee_recipient,
            message,
        };

        let payload = near_sdk::env::keccak256_array(
            transfer_payload
                .encode_hashable()
                .near_expect(BridgeError::Borsh),
        );

        ext_signer::ext(self.mpc_signer.clone())
            .with_static_gas(MPC_SIGNING_GAS)
            .with_attached_deposit(env::attached_deposit())
            .sign(SignRequest {
                payload,
                path: SIGN_PATH.to_owned(),
                key_version: 0,
            })
            .then(
                Self::ext(env::current_account_id())
                    .with_static_gas(SIGN_TRANSFER_CALLBACK_GAS)
                    .sign_transfer_callback(transfer_payload, &transfer_message.fee),
            )
    }

    pub(crate) fn lock_tokens_if_needed(
        &mut self,
        chain_kind: ChainKind,
        token_id: &AccountId,
        amount: u128,
    ) -> LockAction {
        if self.get_token_origin_chain(token_id) == chain_kind || amount == 0 {
            return LockAction::Unchanged;
        }

        self.lock_tokens(chain_kind, token_id, amount)
    }
