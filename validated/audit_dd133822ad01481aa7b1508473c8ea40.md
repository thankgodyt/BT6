### Title
Silent Token Lock in `safe_mint` When Recipient Account Is Unregistered - (File: contracts/nbtc/src/lib.rs)

### Summary

The `safe_mint` function in the nBTC token contract mints tokens to the bridge's own balance **before** checking whether the intended recipient account is registered. When the recipient is unregistered, the function silently returns `U128(0)` and exits, leaving the freshly minted tokens permanently stranded in the bridge's nBTC balance with no recovery path tracked in the bridge's accounting state.

### Finding Description

In `contracts/nbtc/src/lib.rs`, `safe_mint` executes in this order:

1. `self.token.internal_deposit(&self.bridge_id, amount.into())` — mints `amount` nBTC into the bridge contract's own token balance.
2. `if self.token.accounts.get(&account_id).is_none() { return PromiseOrValue::Value(U128(0)); }` — silently aborts if the recipient has no storage registration.
3. Only if the account exists: transfers the tokens from the bridge to the recipient. [1](#0-0) 

The check on line 114 is structurally analogous to the `_enableMode` bug in the external report: it is an overly restrictive gate that fires **after** a state-mutating operation has already occurred, preventing the legitimate completion of that operation. Here, the mint into `self.bridge_id` is irreversible — `internal_deposit` has already updated the token ledger — but the subsequent early return discards the transfer step entirely.

The bridge contract's accounting (`cur_available_protocol_fee`, `cur_reserved_protocol_fee`, `lost_found`) tracks none of these stranded tokens. The `lost_found` map is only populated inside `transfer_nbtc_callback`, which is a separate code path not reached by `safe_mint`. [2](#0-1) 

The bridge's nBTC balance therefore silently accumulates user deposit amounts that were never delivered, with no on-chain record distinguishing them from legitimate protocol-fee accumulations.

### Impact Explanation

Every BTC/ZEC deposit whose NEAR recipient account lacks a storage registration in the nBTC contract results in:

- The deposited BTC/ZEC being consumed (the deposit UTXO is marked verified).
- The corresponding nBTC being minted into the bridge's own token balance.
- No `lost_found` entry, no event, and no recovery mechanism for the user.

The stranded nBTC inflates the bridge's token balance beyond what its accounting tracks, permanently breaking the 1:1 backing invariant for affected users. This matches the **Medium** impact category: "broken callback rollback, or stuck bridge state requiring operator intervention" and potentially "permanent burning below backed supply."

### Likelihood Explanation

Any NEAR account that submits a BTC deposit proof without having previously called `storage_deposit` on the nBTC contract triggers this path. This is a realistic scenario for new users or integrations that automate the deposit step without pre-registering. No privileged access is required; the attacker-controlled input is simply the absence of a storage registration.

### Recommendation

Move the registration check **before** the `internal_deposit` call, or register the account automatically if it is absent (mirroring the pattern used in `mint_inner`):

```rust
// Option A: register on demand (consistent with mint_inner)
if self.token.accounts.get(&account_id).is_none() {
    self.token.internal_register_account(&account_id);
}
self.token.internal_deposit(&self.bridge_id, amount.into());
// ... proceed with transfer
```

Alternatively, if silent failure is intentional, the early return must be placed **before** `internal_deposit` so no tokens are minted when the recipient is unregistered.

### Proof of Concept

1. Alice holds BTC and wants nBTC on NEAR. She has a NEAR account but has **not** called `storage_deposit` on the nBTC contract.
2. A relayer submits Alice's deposit proof to `satoshi-bridge`. The bridge verifies it and calls `safe_mint(alice.near, 100_000, None)`.
3. Inside `safe_mint`: `internal_deposit(&bridge_id, 100_000)` executes — 100,000 nBTC are minted to the bridge's balance.
4. `self.token.accounts.get(&alice.near)` returns `None` → function returns `U128(0)`.
5. Alice receives 0 nBTC. The bridge's nBTC balance is 100,000 units higher than its accounting reflects. No `lost_found` entry exists. Alice's BTC is gone. [3](#0-2)

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }
