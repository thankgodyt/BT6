### Title
Peras Certificate Validation Unconditionally Accepts All Inbound Peer Certificates Using Hardcoded Default Parameters — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs`)

---

### Summary

The object diffusion layer that receives Peras certificates from remote peers calls `validatePerasCert mkPerasParams` — a hardcoded default parameter set — instead of the actual runtime `PerasCfg`. Compounding this, the `validatePerasCert` implementation in the universal `BlockSupportsPeras` instance unconditionally returns `Right` regardless of the certificate content or the parameters supplied. Any certificate sent by an unprivileged peer is therefore accepted into the local `PerasCertDB` and forwarded to the `ChainDB` for chain-selection boosting without any cryptographic or quorum check.

---

### Finding Description

**Root cause 1 — wrong parameter source (direct H-05 analog):**

In `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB`, the validation callback is constructed as `validatePerasCert mkPerasParams`:

```haskell
-- makePerasCertPoolWriterFromCertDB
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place

-- makePerasCertPoolWriterFromChainDB
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
```

`mkPerasParams` is the hardcoded default `PerasParams` value defined in `Ouroboros.Consensus.Peras.Params`. It is not the runtime `PerasCfg` derived from the actual ledger state or node configuration. This is the direct structural analog to H-05: the validation function references a local default value instead of the authoritative configured source. [1](#0-0) 

**Root cause 2 — validation stub always returns `Right`:**

The `BlockSupportsPeras` instance that covers all block types is explicitly a degenerate placeholder. Its `validatePerasCert` implementation performs no checks whatsoever and unconditionally returns `Right`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [2](#0-1) 

The `validatePerasCert` type signature requires a `PerasCfg blk` (the authoritative configuration) and a `PerasCert blk`, and is supposed to return `Left (PerasValidationErr blk)` on failure: [3](#0-2) 

The two defects are independent but compound: even if `validatePerasCert` were properly implemented, it would still receive `mkPerasParams` (the wrong source) rather than the actual runtime quorum threshold and weight parameters.

**The `mkPerasParams` default:**

`mkPerasParams` is defined as a static default bundle with placeholder values pending final protocol decisions: [4](#0-3) 

The `perasQuorumStakeThreshold` and `perasQuorumStakeThresholdSafetyMargin` fields in this default are not derived from the live ledger state, so even a correctly implemented `validatePerasCert` would check against the wrong quorum threshold.

**The inbound processing path:**

`processCerts` is the function that receives batches of certificates from remote peers and applies the validation callback. If validation passes (which it always does), the certificate is inserted into `PerasCertDB` or submitted to `ChainDB` for chain-selection boosting: [5](#0-4) 

The `ChainDB.addPerasCertAsync` path directly feeds into chain selection, where a `ValidatedPerasCert` carries a `vpcCertBoost` weight that can shift the preferred chain: [6](#0-5)

### Impact Explanation

**Impact: Critical / High.**

An unprivileged remote peer can craft and send a `PerasCert` for any block at any round number. Because `validatePerasCert` always returns `Right`, the certificate is accepted into the local `PerasCertDB` and submitted to `ChainDB`. The `vpcCertBoost` weight assigned to the certificate (taken from `mkPerasParams.perasWeight`) is then used in Peras chain selection to boost the certified block's chain weight. This allows an adversary to:

1. **Bypass Peras certificate verification** — no BLS signature, no quorum proof, no eligibility check is performed. This directly satisfies the "Bypass of Peras voting or certificate checks that enables unauthorized certificate acceptance" criterion.
2. **Manipulate chain selection** — by injecting certificates for an adversarially chosen block, the attacker can cause an honest node to prefer a non-canonical chain, satisfying the "chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain" criterion.

---

### Likelihood Explanation

**Likelihood: Medium.**

- The object diffusion mini-protocol for Peras certificates is a live network-facing component, reachable by any connected peer.
- No special privileges, keys, or stake are required — any peer that can establish a connection can send crafted `PerasCert` objects.
- The attack requires Peras to be active on the network. As Peras is currently in active development and integration, this is a near-term realistic scenario.
- The attacker must know the block hash of a target block to certify, which is public information on the chain.

---

### Recommendation

1. **Fix the parameter source**: Replace `mkPerasParams` with the actual runtime `PerasCfg` in both `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB`. The `PerasCfg` must be threaded through from the node's top-level configuration, analogous to how `PerasParams` is passed to `implAddVote` in `PerasVoteDB.Impl`.

2. **Implement `validatePerasCert`**: The stub must be replaced with a real implementation that verifies the BLS aggregate signature, checks that the certificate's voter set meets the quorum threshold from the authoritative `PerasCfg`, and validates voter eligibility proofs. The existing `TODO` at `cardano-peras/issues/120` must be resolved before Peras is enabled on any production network.

3. **Ensure consistency**: The `stakeAboveThreshold` check used in `votesReachQuorum` (for locally forged certificates) must use the same `PerasCfg` source as the inbound certificate validation, to prevent a discrepancy analogous to the H-05 two-table mismatch. [7](#0-6) 

---

### Proof of Concept

1. A peer establishes a connection to an honest node running with Peras enabled.
2. The peer constructs a `PerasCert` for an arbitrary block `B` at round `R`:
   ```
   PerasCert { pcCertRound = R, pcCertBoostedBlock = pointOf(B) }
   ```
   No valid BLS signature, no quorum proof, no eligibility proof is needed.
3. The peer sends this certificate via the object diffusion mini-protocol.
4. The honest node's `makePerasCertPoolWriterFromChainDB` receives the batch and calls:
   ```haskell
   processCerts systemTime getCertIds (validatePerasCert mkPerasParams) addCert [cert]
   ```
5. `validatePerasCert mkPerasParams cert` returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams })` unconditionally.
6. `ChainDB.addPerasCertAsync` is called with the validated certificate.
7. Chain selection now treats block `B` as having a Peras boost, potentially causing the honest node to prefer a chain containing `B` over the canonical chain.
