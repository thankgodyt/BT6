### Title
Unconditional Peras Certificate Acceptance Allows Unprivileged Peer to Manipulate Chain Selection Weight - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` implementation is a stub that unconditionally accepts every inbound Peras certificate without performing any cryptographic or semantic validation. Any unprivileged peer can send a crafted `PerasCert` pointing to an arbitrary block, which will be stored and applied as a weight boost in chain selection via `WeightedSelectView`, causing an honest node to prefer a non-canonical chain.

### Finding Description

The universal `BlockSupportsPeras` instance (the only instance in the codebase, covering all block types including Cardano) implements `validatePerasCert` as a stub that always returns `Right`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This stub is wired directly into the production inbound-certificate processing path. `makePerasCertPoolWriterFromChainDB` passes `(validatePerasCert mkPerasParams)` as the validation callback to `processCerts`. `processCerts` calls this callback on every inbound certificate received from a peer and, if it returns `Right`, stores the certificate in the `ChainDB` via `ChainDB.addPerasCertAsync`.

The stored certificate then influences chain selection. `weightedSelectView` computes a `WeightedSelectView` for each candidate fragment, where `wsvWeightBoost` is derived from `weightBoostOfFragment` applied to the stored certificates. `WeightedSelectView`'s `Ord` instance compares `wsvTotalWeight` (block number + weight boost) first, so a fraudulent certificate boosting an attacker's fork can make it outweigh the honest canonical chain.

The analog to the external report is exact: just as `borrow_collateral` checked `trader` and `pool` in the repay instruction but not the critical `position_account` linkage, `processCerts` here calls a validator that checks nothing at all — not the aggregate BLS signature (`pcSignature`), not the voter eligibility proofs (`pcVoters`), not the round number's relationship to the current epoch, and not whether `pcBoostedBlock` refers to a block that actually exists on any known chain.

**Attack path:**
1. Attacker connects to a victim node as a normal peer (no keys, no stake required).
2. Attacker sends a `PerasCert` via the ObjectDiffusion mini-protocol with `pcBoostedBlock` pointing to a block on the attacker's fork and `pcCertRound` set to any round not yet in the database.
3. `processCerts` calls `validatePerasCert`, which returns `Right` unconditionally.
4. The certificate is stored in the `PerasCertDB`/`ChainDB`.
5. `weightedSelectView` applies the weight boost (`perasWeight params`) to the attacker's fork.
6. Chain selection (`preferCandidate`) compares `wsvTotalWeight` and switches to the attacker's fork if its boosted weight exceeds the honest chain's weight.

### Impact Explanation

**High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain.**

A single crafted certificate from any peer can inject an unbounded weight boost (equal to `perasWeight params`) onto an arbitrary block. Because `WeightedSelectView` ranks chains by total weight (block number + boost) before any tiebreaker, a sufficiently large `perasWeight` can override the honest chain's length advantage, causing the victim node to permanently follow the attacker's fork. This breaks the Peras chain-selection security guarantee that only legitimately quorum-certified blocks receive weight boosts.

### Likelihood Explanation

Any peer reachable via the ObjectDiffusion mini-protocol can trigger this. No stake, no keys, and no prior relationship with the victim node are required. The attack requires only constructing a `PerasCert` value with an attacker-chosen `pcCertRound` and `pcCertBoostedBlock` and sending it over the wire. The deduplication check (`Set.member roundNo certIds`) only prevents re-use of the same round number, so the attacker can use any unused round number.

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
1. The aggregate BLS signature (`pcSignature`) over `(pcRoundNo, pcBoostedBlock)` using the aggregated public keys of the claimed voters.
2. Each voter's eligibility proof (`pcVoters`) against the committee for the given round.
3. That `pcBoostedBlock` refers to a block known to the local chain.
4. That `pcCertRound` falls within the valid range for the current epoch.

Until the real implementation is available, inbound certificates from peers should be rejected entirely (or the ObjectDiffusion writer for Peras certs should not be activated) rather than accepted unconditionally.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
