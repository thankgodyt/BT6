### Title
Hardcoded `boundX = 3` in `taylorExpCmpFirstNonLower` Causes Incorrect Local Sortition Seat Count, Enabling Unauthorized Peras Vote Acceptance - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/LS.hs`)

---

### Summary

`localSortitionNumSeats` in `LS.hs` calls `taylorExpCmpFirstNonLower` with a hardcoded `boundX = 3`. The function's own contract requires `boundX = e^{|x|}` for correct error bounds, where `x = -lambda`. For any voter whose `lambda > ln(3) ≈ 1.099`, the error bound is underestimated, causing the Taylor series comparison to make incorrect eligibility decisions. This can grant a non-persistent Peras committee member more seats than their VRF output entitles them to, bypassing the local sortition eligibility check and allowing unauthorized vote acceptance.

---

The function `taylorExpCmpFirstNonLower` carries an explicit contract at line 121:

```
-- IMPORTANT: boundX must be e^{|x|} for correct error bounds (see taylorExpCmp).
``` [2](#0-1) 

The `x` argument is `-lambda`, so the correct `boundX` is `e^{lambda}`. The hardcoded value `3` is only a valid upper bound when `lambda ≤ ln(3) ≈ 1.099`. For larger `lambda`, `e^{lambda} > 3`, and the error term `errorTerm = abs(err' * boundX)` is underestimated.

**How the error propagates — `LS.hs` lines 165–175:**

```haskell
decideOne maxN n err acc divisor cmp
  | maxN == n = Stop
  | cmp >= acc' + errorTerm = Stop   -- ABOVE: cmp definitely above e^x
  | cmp < acc' - errorTerm = Below   -- BELOW: cmp definitely below e^x
  | otherwise = decideOne ...
 where
  ...
  errorTerm = abs (err' * boundX)    -- ← too small when boundX < e^{lambda}
``` [3](#0-2) 

With underestimated `errorTerm`:
- `acc' + errorTerm` is smaller than it should be, so the **ABOVE** branch (`cmp >= acc' + errorTerm`) fires more easily.
- When `acc'` is below `e^{-lambda}` (which happens on even-numbered Taylor terms), a value of `orders[0]` that is truly **below** `e^{-lambda}` (voter should get 0 seats) can satisfy `orders[0] >= acc' + errorTerm`, causing the algorithm to declare it ABOVE and return seat index 0 — granting the voter 1+ seats they are not entitled to.

**`lambda` computation — `LS.hs` lines 65–70:**

```haskell
lambda :: FixedPoint
lambda =
  fromRational $
    fromIntegral numNonPersistentVoters
      * voterStake
      / totalNonPersistentStake
``` [4](#0-3) 

`lambda > ln(3)` whenever `numNonPersistentVoters * voterStake / totalNonPersistentStake > 1.099`. With 10 non-persistent voters and a pool holding more than ~11% of non-persistent stake, this condition is met — a realistic scenario.

**Attacker-controlled entry path — `WFALS.hs` lines 351–390:**

A pool operator submits a `WFALSNonPersistentVote`. `implVerifyVote` calls `localSortitionNumSeats` with the voter's VRF output and stake. If `numSeats > 0`, the vote is accepted.

### Impact Explanation

**Impact: Critical — Bypass of Peras voting committee eligibility check.**

A pool operator with `lambda > ln(3)` can craft a vote whose VRF output falls in the precision gray zone. Due to the underestimated error bound, `localSortitionNumSeats` returns a non-zero seat count when the correct answer is zero. `implVerifyVote` and `implVerifyCert` accept the vote as valid. The attacker participates in Peras voting with seats they are not entitled to, inflating their voting power. In aggregate, this weakens the security threshold of the Peras finality gadget, potentially allowing a minority-stake coalition to forge or suppress certificates for blocks.

---

### Likelihood Explanation

**Likelihood: Medium.**

The condition `lambda > ln(3) ≈ 1.099` is met whenever a non-persistent voter holds more than `1.099 / numNonPersistentVoters` fraction of the non-persistent stake. With a committee of 10 non-persistent voters, any pool with >11% of non-persistent stake triggers the bug. The precision error only matters when `orders[0]` is close to `e^{-lambda}`, which is a narrow but non-negligible range of VRF outputs. The code itself acknowledges the issue as an open TODO (issue #234), confirming the developers are aware the bound may be wrong.

---

### Recommendation

Replace the hardcoded `boundX = 3` with the mathematically correct value `e^{lambda}`:

```haskell
expectedSeats :: Int
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      (exp lambda)   -- correct: e^{|x|} where x = -lambda
      orders
      (-lambda)
```

Since `lambda` is already a `FixedPoint`, use the fixed-point `exp` function from `Cardano.Ledger.NonIntegral` (the same library used by `checkLeaderNatValue`). Additionally, add an invariant assertion that the returned seat count is consistent with the Poisson CDF to catch future regressions.

---

### Proof of Concept

**Parameters:** `numNonPersistentVoters = 10`, `voterStake / totalNonPersistentStake = 0.15` → `lambda = 1.5`.

Correct `boundX = e^{1.5} ≈ 4.48`; used `boundX = 3`.

At the Taylor iteration where `acc' ≈ 0.20` (below `e^{-1.5} ≈ 0.2231`):
- Correct `errorTerm = |err'| * 4.48`; underestimated `errorTerm = |err'| * 3`.
- For `orders[0] = normalizedVRFOutput / 1.5 = 0.21 / 1.5 = 0.14`:
  - True: `0.14 < e^{-1.5} = 0.2231` → voter should get 0 seats.
  - With `boundX = 3`: if `acc' + errorTerm ≤ 0.14` at some iteration, the algorithm declares ABOVE and returns seat index 0 → voter gets 1 seat.
  - With correct `boundX = 4.48`: `errorTerm` is large enough that the algorithm continues iterating until `acc'` exceeds `0.14`, correctly declaring BELOW → voter gets 0 seats.
