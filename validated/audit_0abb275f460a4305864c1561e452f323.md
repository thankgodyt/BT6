### Title
Missing Access Control on `sign_btc_transaction` Allows Any Account to Force MPC Signing of Any Pending BTC Transaction - (File: contracts/satoshi-bridge/src/api/chain_signatures.rs)

### Summary

The `sign_btc_transaction()` function in the satoshi-bridge contract lacks caller ownership verification. Any unprivileged NEAR account can trigger MPC chain-signature signing of any pending BTC transaction belonging to any user, bypassing the intended flow and preventing cancellation or RBF of in-flight transactions.

### Finding Description

The public entry point `sign_btc_transaction` carries only a `#[pause(except(roles(Role::DAO)))]` attribute. It performs no check that `env::predecessor_account_id()` matches the `account_id` stored inside the `BtcPendingInfo` record it is about to sign.

```rust
// contracts/satoshi-bridge/src/api/chain_signatures.rs
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn sign_btc_transaction(
    &mut self,
    btc_pending_sign_id: String,   // <-- any caller supplies any ID
    sign_index: usize,
    key_version: u32,
) -> PromiseOrValue<bool> {
    let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
    btc_pending_info.assert_pending_sign();
    // ... no require!(caller == btc_pending_info.account_id) ...
    self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
        .into()
}
```

`internal_sign_btc_transaction` immediately issues a cross-contract call to the MPC Chain Signatures service and, on success, the callback `sign_btc_transaction_callback` saves the signature, emits a `SignedBtcTransaction` event containing the fully-signed raw transaction bytes, and transitions the record to `pending_verify` state — removing it from the owner's `btc_pending_sign_ids` set.

All pending transaction types share this single entry point: user withdrawals, refunds, active UTXO management transactions, and their RBF variants.

### Impact Explanation

Once an attacker forces signing of a victim's pending transaction:

1. **Cancellation window is lost.** `cancel_withdraw` (and its UTXO-management equivalent) requires `Role::DAO` or `Role::Operator` and operates on a record still in `pending_sign` state. After the attacker-triggered signing completes, the record moves to `pending_verify`; the operator's cancel path no longer applies to the original transaction.

2. **Signed transaction bytes are broadcast-ready.** The `SignedBtcTransaction` event emits the complete raw Bitcoin transaction. Any observer (including the attacker) can immediately broadcast it to the Bitcoin network, making the transfer irreversible on-chain.

3. **RBF is foreclosed.** A user or operator who intended to fee-bump or redirect the transaction via RBF before signing loses that option the moment the attacker triggers signing.

4. **Stuck bridge state.** If the forced-signed transaction is never broadcast or confirmed (e.g., the attacker does not broadcast it), the record sits in `pending_verify` indefinitely, requiring operator intervention to clean up.

This matches the **Medium** impact category: harmful smart-contract behavior without direct funds theft, including stuck bridge state requiring operator intervention, and bypass of bridge cancellation/RBF policies.

### Likelihood Explanation

The `btc_pending_sign_id` values are emitted as on-chain events and are queryable via `get_btc_pending_infos_paged()` (a public view function). Any NEAR account can enumerate all pending transactions and call `sign_btc_transaction` on any of them. No special knowledge, privilege, or capital is required beyond a small attached deposit for gas.

### Recommendation

Add an ownership check at the top of `sign_btc_transaction` before any state mutation or cross-contract call:

```rust
let caller = env::predecessor_account_id();
let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
require!(
    caller == btc_pending_info.account_id
        || self.acl_has_any_role(vec![Role::DAO.into(), Role::Operator.into()], caller),
    "Unauthorized: caller is not the transaction owner"
);
```

This mirrors the pattern already used in `reject_refund` and `resolve_execute_refund_timelock`, where privileged roles are allowed to act on behalf of any user while unprivileged callers are restricted to their own records.

### Proof of Concept

1. Alice initiates a withdrawal via `ft_on_transfer` → `ft_transfer_call`. A `BtcPendingInfo` record is created with `account_id = alice`.
2. Attacker calls `get_btc_pending_infos_paged()` (public view) to obtain Alice's `btc_pending_sign_id`.
3. Attacker calls `sign_btc_transaction(alice_pending_id, 0, 0)` from their own account. No ownership check exists.
4. The MPC service signs the payload; `sign_btc_transaction_callback` saves the signature, emits `SignedBtcTransaction` with the fully-signed raw transaction bytes, and moves the record to `pending_verify`.
5. Alice's record is removed from her `btc_pending_sign_ids`; the operator can no longer cancel via `cancel_withdraw`.
6. The attacker (or anyone watching the event) broadcasts the signed transaction to Bitcoin, making the withdrawal irreversible — even if Alice or the operator intended to cancel or RBF it. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

    pub fn sign_btc_transaction(

    pub fn internal_sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> Promise {
        let pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);

        let public_keys: Vec<_> = pending_info
            .vutxos
            .iter()
            .map(|vutxo| self.generate_btc_public_key(&vutxo.get_path()))
            .collect();

        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        require!(
            btc_pending_info.signatures[sign_index].is_none(),
            "Already signed"
        );
        let payload = btc_pending_info
            .get_psbt()
            .get_hash_to_sign(sign_index, &public_keys);
        let path = btc_pending_info.vutxos[sign_index].get_path();
        self.sign_promise(SignRequest {
            payload,
            path,
            key_version,
        })
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_SIGN_BTC_TRANSACTION_CALL_BACK)
                .sign_btc_transaction_callback(
                    btc_pending_info.account_id.clone(),
                    btc_pending_sign_id,
                    sign_index,
                ),
        )
    }
