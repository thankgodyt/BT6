### Title
Unauthenticated `sign_btc_transaction` with Unvalidated `key_version` Allows Attacker to Inject Invalid Signatures, Permanently Freezing Bridge Funds — (`contracts/satoshi-bridge/src/api/chain_signatures.rs`, `contracts/satoshi-bridge/src/chain_signature.rs`)

### Summary

`sign_btc_transaction` is a public, unauthenticated function. Any caller can invoke it for any visible pending transaction ID with an arbitrary `key_version`. The `key_version` is forwarded directly to the MPC signing service but is never committed in `BTCPendingInfo` and never validated. The callback stores the returned signature without verifying it against the expected public key. An attacker who calls this before the legitimate signer — using a `key_version` that differs from the one used to derive the UTXO's locking script — injects a cryptographically invalid Bitcoin signature. The "Already signed" guard then permanently blocks re-signing of that input index. When all inputs are "signed", the NEAR state transitions to `PendingVerify` with an unbroadcastable Bitcoin transaction, permanently freezing the underlying BTC.

### Finding Description

**Root cause 1 — No caller authentication:** [1](#0-0) 

`sign_btc_transaction` never checks `env::predecessor_account_id()` against `btc_pending_info.account_id`. Any account can call it for any pending ID visible from public views.

**Root cause 2 — `key_version` is caller-controlled and uncommitted:** [2](#0-1) 

The `payload` and `path` are derived from the stored PSBT and `vutxos` (fixed), but `key_version` is taken verbatim from the caller and forwarded to the MPC. `BTCPendingInfo` stores no `key_version` field, so there is nothing to validate against. [3](#0-2) 

**Root cause 3 — Callback stores signature without verification:** [4](#0-3) 

The callback re-derives the expected public key from the stored path (using the version-0 root key), but never verifies that the returned signature is valid under that key before storing it.

**Root cause 4 — `generate_btc_public_key` ignores `key_version`:** [5](#0-4) 

The NEAR-side key derivation always uses the single stored `chain_signatures_root_public_key` (fetched with `public_key(None)`, i.e., version 0). If the MPC signs with `key_version=1`, it uses a different root key, producing a signature that is invalid for the UTXO's P2WPKH locking script.

**Root cause 5 — `save_signature` writes witness without cryptographic check:** [6](#0-5) 

The signature is written into the PSBT witness unconditionally.

### Impact Explanation

Once an attacker injects a signature for any input index with a wrong `key_version`:

- The "Already signed" guard at line 91–94 of `chain_signature.rs` permanently blocks re-signing of that index.
- When `is_all_signed()` returns `true`, `to_pending_verify_stage()` is called, the NEAR state moves to `PendingVerify`, and `btc_pending_sign_ids` is cleared.
- The resulting Bitcoin transaction contains a witness signed by a key that does not match the UTXO's locking script. It is permanently unbroadcastable.
- The underlying BTC UTXOs remain locked in the bridge's Bitcoin address with no recovery path on the NEAR side (the pending info is now in `PendingVerify`, not `PendingSign`).

This constitutes **permanent freezing of user funds**. [7](#0-6) 

### Likelihood Explanation

- The attack requires no privilege — `sign_btc_transaction` is fully public.
- Pending transaction IDs are derived from the PSBT's unsigned txid (`get_pending_id`) and are visible via public view functions.
- The attacker only needs to submit one NEAR transaction per input index before the legitimate signer, which is trivially achievable by monitoring the chain.
- No special knowledge beyond the pending ID and a non-zero `key_version` value is required.

### Recommendation

1. **Commit `key_version` in `BTCPendingInfo`** at creation time and validate it in `internal_sign_btc_transaction` against the stored value.
2. **Authenticate the caller**: require `env::predecessor_account_id()` to match `btc_pending_info.account_id` (or a trusted relayer role) in `sign_btc_transaction`.
3. **Verify the signature in the callback** before storing it: use `secp256k1::Secp256k1::verify_ecdsa` to confirm the returned signature is valid under the expected public key for the committed payload.

### Proof of Concept

```
// Setup: victim has a pending withdrawal with id = PENDING_ID, 2 inputs
// Attacker observes PENDING_ID from public view

// Step 1: Attacker front-runs signing of input 0 with wrong key_version
attacker.call(
    bridge,
    "sign_btc_transaction",
    { btc_pending_sign_id: PENDING_ID, sign_index: 0, key_version: 1 }
)
// MPC signs payload with key_version=1 (different key than UTXO's locking script)
// Callback stores invalid signature in signatures[0]
// "Already signed" guard now blocks any further signing of index 0

// Step 2: Legitimate signer signs input 1 (succeeds, correct key)
relayer.call(bridge, "sign_btc_transaction",
    { btc_pending_sign_id: PENDING_ID, sign_index: 1, key_version: 0 })

// Step 3: is_all_signed() == true → to_pending_verify_stage()
// NEAR state: PendingVerify, btc_pending_sign_ids cleared
// Bitcoin tx: input 0 has invalid witness (wrong key), input 1 valid
// Result: tx is unbroadcastable; BTC permanently frozen in bridge address
```
