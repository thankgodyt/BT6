### Title
Safe Deposit Path Bypasses `deposit_bridge_fee` Entirely — (File: `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

---

### Summary

The bridge has two deposit verification paths: `internal_verify_deposit` and `internal_safe_verify_deposit`. The standard path correctly deducts the configured `deposit_bridge_fee` before minting nBTC. The safe-deposit path passes the raw `deposit_amount` directly to `safe_mint` with **zero fee deduction**, causing the protocol and relayers to collect no fee revenue on every safe deposit. Any user who can call the public `safe_verify_deposit` entry point can exploit this to receive 100% of their deposited BTC value as nBTC, bypassing all bridge fees.

---

### Finding Description

**Standard path — fee correctly applied:**

In `internal_verify_deposit`, the fee is computed and subtracted before the mint amount is determined:

```rust
let deposit_fee = config.deposit_bridge_fee.get_fee(deposit_amount);
let mint_amount = deposit_amount - deposit_fee;
let (protocol_fee, relayer_fee) = config
    .deposit_bridge_fee
    .get_protocol_and_relayer_fee(deposit_fee);
``` [1](#0-0) 

The callback then receives `mint_amount`, `protocol_fee`, and `relayer_fee` as distinct arguments, and the fee is credited to the protocol and relayer.

**Safe-deposit path — fee entirely absent:**

`internal_safe_verify_deposit` performs no fee calculation whatsoever. It passes `deposit_amount` directly as the mint amount:

```rust
promise.then(
    Self::ext(env::current_account_id())
        .with_static_gas(GAS_FOR_VERIFY_DEPOSIT_CALL_BACK)
        .verify_safe_deposit_callback(
            recipient_id,
            deposit_amount.into(),   // ← full amount, no fee deducted
            deposit_msg.msg,
            pending_utxo_info,
        ),
)
``` [2](#0-1) 

The callback `verify_safe_deposit_callback` then calls `safe_mint(recipient_id, mint_amount, msg)` with this full amount, and `safe_mint_callback` explicitly emits `protocol_fee: U128(0)` and `relayer_fee: U128(0)`: [3](#0-2) 

The entry point `internal_safe_verify_deposit_entry` has no role-based access control — its only barrier is attaching a NEAR storage deposit:

```rust
require!(
    env::attached_deposit() >= self.required_balance_for_safe_deposit(),
    "Insufficient deposit for storage"
);
``` [4](#0-3) 

---

### Impact Explanation

Every safe deposit mints nBTC equal to 100% of the deposited BTC value. The configured `deposit_bridge_fee` (which splits into `protocol_fee` and `relayer_fee` via `get_protocol_and_relayer_fee`) is never applied. The protocol treasury and relayers receive zero compensation for safe deposits. This is a bypass of the bridge's fee policy — a Medium-severity impact under the allowed scope ("Bypass of bridge limits or policies"). [5](#0-4) 

---

### Likelihood Explanation

The entry point is publicly reachable by any NEAR account. The only cost is a small NEAR storage deposit (`required_balance_for_safe_deposit()`), which is trivially affordable. A rational user who discovers this discrepancy will always prefer the safe deposit path to avoid paying fees. Likelihood is **High**.

---

### Recommendation

Apply the same fee deduction in `internal_safe_verify_deposit` as in `internal_verify_deposit`. Before calling `verify_safe_deposit_callback`, compute:

```rust
let deposit_fee = config.deposit_bridge_fee.get_fee(deposit_amount);
let mint_amount = deposit_amount - deposit_fee;
let (protocol_fee, relayer_fee) = config
    .deposit_bridge_fee
    .get_protocol_and_relayer_fee(deposit_fee);
```

Pass `mint_amount`, `protocol_fee`, and `relayer_fee` into the callback so the fee is credited identically to the standard deposit path.

---

### Proof of Concept

1. User constructs a `DepositMsg` with `safe_deposit` set (a `SafeDepositMsg`).
2. User calls `safe_verify_deposit` (the public API entry for `internal_safe_verify_deposit_entry`), attaching only the required NEAR storage deposit.
3. The light-client inclusion proof is verified.
4. `verify_safe_deposit_callback` fires, calling `safe_mint(recipient_id, deposit_amount, msg)` — the full BTC value, with no fee deducted.
5. User receives nBTC equal to 100% of their BTC deposit. Protocol and relayer receive 0 fee.
6. Compare: the same user depositing via the standard `verify_deposit` path would receive `deposit_amount - deposit_bridge_fee.get_fee(deposit_amount)` nBTC, with the fee split between protocol and relayer. [6](#0-5)

    pub fn get_fee(&self, amount: u128) -> u128 {
        std::cmp::max(
            amount * u128::from(self.fee_rate) / u128::from(MAX_RATIO),
            self.fee_min,
        )
    }

    pub fn get_protocol_and_relayer_fee(&self, fee_amount: u128) -> (u128, u128) {
        let protocol_fee = fee_amount * u128::from(self.protocol_fee_rate) / u128::from(MAX_RATIO);
        let relayer_fee = fee_amount - protocol_fee;
        (protocol_fee, relayer_fee)
    }
