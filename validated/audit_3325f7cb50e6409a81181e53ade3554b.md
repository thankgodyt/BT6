Audit Report

## Title
`normalize_amount` Floor Division Allows Zero-Amount Transfers to Permanently Lock Funds in `sign_transfer` — (File: near/omni-bridge/src/lib.rs)

## Summary

`init_transfer` accepts deposits without verifying that the post-normalization transfer amount is non-zero, while `sign_transfer` enforces this check and panics when it is zero. For any token where `origin_decimals > decimals`, any deposited amount below `10^(origin_decimals - decimals)` normalizes to zero via floor division, causing every subsequent `sign_transfer` call to unconditionally panic. No public recovery path exists for non-UTXO chains, permanently freezing the deposited tokens.

## Finding Description

`normalize_amount` performs integer floor division:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [1](#0-0) 

`sign_transfer` calls this and requires the result to be strictly positive:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
``` [2](#0-1) 

`init_transfer` only checks `fee < amount`, with no normalization guard:

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
``` [3](#0-2) 

Once `init_transfer_internal` stores the transfer, tokens are burned or locked: [4](#0-3) 

`remove_transfer_message` is only reachable via:
1. `sign_transfer_callback` — requires a successful MPC signing (impossible if `sign_transfer` panics).
2. `claim_fee_callback` — requires a `ProverResult::FinTransfer` proof from the destination chain, which itself requires a completed `sign_transfer`.
3. `submit_transfer_to_utxo_chain_connector` — only for UTXO chains (BTC/Zcash). [5](#0-4) [6](#0-5) 

For EVM/Solana/Starknet destinations, there is no public cancel or refund function. The code comment on `normalize_amount` acknowledges "dust stays locked/burned" when `fee = 0`, but does not address the case where the entire transfer amount is below the normalization threshold and normalizes to zero. [7](#0-6) 

## Impact Explanation

This is a concrete instance of **permanent freezing of bridged funds**. Tokens deposited via `ft_transfer_call` → `ft_on_transfer` → `init_transfer` are immediately burned or locked in the bridge contract. If `normalize_amount(amount - fee) == 0`, the MPC signing step can never succeed, and no on-chain path exists to recover the tokens. This matches the critical allowed impact: "permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet, Bitcoin, Zcash, or Wormhole-routed flows."

## Likelihood Explanation

The condition is triggered whenever a token is registered with `origin_decimals > decimals` (a standard configuration for bridging high-precision tokens) and a user deposits an amount below `10^(origin_decimals - decimals)`. For a token with `origin_decimals = 24` and `decimals = 18`, any amount below `1,000,000` in the smallest unit triggers this. This is reachable by any unprivileged token holder through the standard `ft_transfer_call` public entry point. Accidental triggering via UI rounding errors or dust amounts is realistic without any attacker involvement.

## Recommendation

Add a normalization check inside `init_transfer` (or `init_transfer_internal`) before storing the transfer message:

```rust
let normalized = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

Alternatively, enforce a minimum deposit amount equal to `10^(origin_decimals - decimals)` at the `ft_on_transfer` entry point so the transfer is rejected before tokens are locked or burned.

## Proof of Concept

1. Register a token with `origin_decimals = 24`, `decimals = 18` (`diff_decimals = 6`, threshold = `1_000_000`).
2. Call `ft_transfer_call` with `amount = 500_000` and `fee = 0`. `init_transfer` accepts it: `0 < 500_000` passes the only guard.
3. `init_transfer_internal` stores the transfer and locks/burns the 500,000 tokens.
4. Call `sign_transfer` for the stored `transfer_id` (via a trusted relayer).
5. `normalize_amount(500_000, {24, 18}) = 500_000 / 1_000_000 = 0` (floor division).
6. `require!(0 > 0, ...)` panics — `sign_transfer` always fails for this transfer.
7. `claim_fee_callback` requires a destination-chain finalization proof, which can never be generated without a successful `sign_transfer`. No other removal path exists for EVM/Solana/Starknet destinations. Funds are permanently frozen.

A local unit test can reproduce this by inserting a `TransferMessage` with `amount = U128(500_000)`, `fee = U128(0)`, and `Decimals { origin_decimals: 24, decimals: 18 }` into `pending_transfers`, then calling `sign_transfer_callback` with a mock successful signature and asserting the panic on the `require!` at line 482–485.

            .remove(&transfer_id)
            .map(storage::TransferMessageStorage::into_main)
            .near_expect(BridgeError::TransferNotExist);
