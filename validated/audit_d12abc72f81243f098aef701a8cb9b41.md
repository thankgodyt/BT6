### Title
`safe_mint` Mints Tokens to Bridge Before Confirming Recipient Registration, Silently Inflating Supply on Failure — (File: `contracts/nbtc/src/lib.rs`)

### Summary
The `safe_mint` function in the `nbtc` contract unconditionally mints tokens to the bridge account (`self.bridge_id`) before verifying that the intended recipient (`account_id`) has a registered storage account. When the recipient is unregistered, the function returns `U128(0)` (signaling failure) without reverting the mint. The tokens remain permanently credited to the bridge's own nBTC balance, inflating the circulating supply without a corresponding BTC deposit backing them.

### Finding Description
`safe_mint` is the "safe" deposit path used by integrations such as Omni Bridge. Its documented guarantee is atomicity: either the user receives nBTC or nothing happens. The implementation violates this guarantee:

```rust
// contracts/nbtc/src/lib.rs, lines 101-124
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into()); // ← tokens minted here unconditionally

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0)); // ← returns failure WITHOUT reverting the mint above
    }
    ...
}
``` [1](#0-0) 

The sequence is:

1. `internal_deposit` credits `amount` nBTC to `self.bridge_id` (the satoshi-bridge contract). This state change is committed to the nbtc contract's storage immediately.
2. The function then checks whether `account_id` has a storage account.
3. If the account is absent, the function returns `PromiseOrValue::Value(U128(0))` — a normal (non-panicking) return. In NEAR, only a panic reverts state; a normal return does not.
4. The `amount` nBTC tokens are now permanently held by the bridge with no corresponding BTC backing and no user to claim them.

Because NEAR cross-contract calls execute in separate receipts, the satoshi-bridge's callback (receipt N+1) cannot retroactively revert the nbtc contract's state change (receipt N). Even if the satoshi-bridge's callback panics upon receiving `U128(0)`, the mint in the nbtc contract is already finalized. [2](#0-1) 

### Impact Explanation
Every time a deposit proof is submitted for a recipient whose nbtc storage account does not exist, `amount` nBTC tokens are minted to the bridge's own balance with no BTC backing. This inflates the nBTC circulating supply beyond the amount of BTC held in custody. If the satoshi-bridge's callback does not mark the deposit as processed (because it received `U128(0)`), a relayer can re-submit the same proof repeatedly, each time minting another `amount` to the bridge — compounding the supply inflation. Even in the single-submission case, the user's BTC is locked on-chain while they receive no nBTC, and the bridge holds unbacked tokens.

This matches the allowed medium impact: **broken callback rollback / stuck bridge state requiring operator intervention**, and potentially escalates to **critical** (unauthorized minting / supply inflation beyond backed supply) if the deposit can be replayed.

### Likelihood Explanation
Any user who deposits BTC to a bridge address derived from a `DepositMsg` without first calling `storage_deposit` on the nbtc contract will trigger this path. This is a realistic and common mistake, especially for first-time users or integrations that do not pre-register accounts. The relayer path (`verify_deposit` → `safe_mint`) is fully permissionless and reachable by any public actor.

### Recommendation
Move `internal_deposit` to occur **after** confirming the recipient account exists (or after a successful transfer), or revert (panic) immediately when the recipient is unregistered instead of returning `U128(0)`:

```rust
if self.token.accounts.get(&account_id).is_none() {
    env::panic_str("safe_mint: recipient account not registered");
}
self.token.internal_deposit(&self.bridge_id, amount.into());
```

Alternatively, auto-register the recipient account (paying for storage from the attached deposit) before minting, consistent with the atomicity guarantee the function name implies.

### Proof of Concept

1. User sends BTC to a bridge deposit address without calling `storage_deposit` on the nbtc contract.
2. Relayer calls `verify_deposit` on the satoshi-bridge with a valid Merkle proof.
3. Satoshi-bridge calls `safe_mint(user_account, amount, None)` on the nbtc contract.
4. `safe_mint` executes `self.token.internal_deposit(&self.bridge_id, amount.into())` — `amount` nBTC is credited to the bridge.
5. `self.token.accounts.get(&user_account)` returns `None` (user never registered).
6. `safe_mint` returns `PromiseOrValue::Value(U128(0))` — no panic, no revert.
7. The nbtc contract's state is finalized: bridge holds `amount` extra nBTC with no BTC backing.
8. The satoshi-bridge callback receives `U128(0)`. If it panics, only its own receipt is reverted; the nbtc mint stands.
9. The user receives 0 nBTC; their BTC is locked; the bridge's nBTC balance is inflated. [1](#0-0) [2](#0-1)
