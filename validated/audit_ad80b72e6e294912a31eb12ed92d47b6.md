### Title
Stub `validatePerasCert` Unconditionally Accepts Any Peer-Supplied Peras Certificate, Enabling Unauthorized Chain-Weight Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The sole production instance of `validatePerasCert` in `BlockSupportsPeras` is a stub that unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or quorum checks. Because this function is wired directly into the production Peras certificate ingest path (`makePerasCertPoolWriterFromChainDB`), any unprivileged peer can send a crafted `PerasCert` for an arbitrary block and round, have it accepted without verification, and cause the receiving node to apply a configurable weight boost to that block during chain selection.

---

### Finding Description

`BlockSupportsPeras` defines the interface for Peras certificate validation. The only instance in the codebase is a catch-all for all `StandardHash blk`:

`processCerts` applies `validateCert` to every inbound certificate and, if all pass, adds them to the ChainDB. Since `validatePerasCert` always returns `Right`, every certificate passes: [3](#0-2) 

The accepted `ValidatedPerasCert` carries `vpcCertBoost = perasWeight params`, which is `PerasWeight 15` from `mkPerasParams`: [4](#0-3) 

This boost is then stored in the `PerasWeightSnapshot` and consumed by `weightedSelectView` during chain selection: [5](#0-4) 

The total weight used for chain comparison is `blockNo + weightBoost`: [6](#0-5) 

`preferAnchoredCandidate` uses this weighted comparison when the `PerasWeightSnapshot` is non-empty: [7](#0-6)

### Impact Explanation

An unprivileged peer can send a crafted `PerasCert` naming any block point and any round number. The stub accepts it unconditionally and the ChainDB stores it with a boost of `PerasWeight 15`. Because `wsvTotalWeight = blockNo + weightBoost`, a chain containing the adversarially boosted block appears 15 weight units heavier than it actually is. With `perasWeight = 15`, an attacker can make a chain that is 15 blocks shorter than the honest chain appear to be the preferred chain, causing the victim node to switch to a non-canonical fork. This directly violates the Peras chain-selection invariant and constitutes a chain-selection safety failure reachable by any unprivileged peer via the object diffusion mini-protocol.

No quorum check, no voter eligibility check, no BLS aggregate signature verification, and no round-number validity check is performed. The checks that are defined in `implVerifyCert` in `WFALS.hs` are never reached because `validatePerasCert` short-circuits before them. [8](#0-7) 

---

### Likelihood Explanation

The object diffusion mini-protocol for Peras certificates is a peer-facing network endpoint. Any node connected to the victim can send a `PerasCert` message. The crafted certificate requires only a valid CBOR encoding of a `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock`; no cryptographic material is needed because the stub skips all checks. The attack is trivially constructible by any peer.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
1. Verifies the aggregate BLS signature over the election identifier and boosted block hash.
2. Checks that the claimed voters are eligible committee members (persistent or non-persistent) for the given round.
3. Verifies VRF outputs for non-persistent voters.
4. Confirms that the total stake of the voters meets the quorum threshold (`perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin`).
5. Validates that `pcCertRound` is within the acceptable window relative to the current chain tip.

Until the real implementation is in place, the certificate ingest path (`makePerasCertPoolWriterFromChainDB`) should reject all inbound certificates rather than accept them unconditionally.

---

### Proof of Concept

1. Attacker connects to a victim node via the object diffusion mini-protocol for Peras certificates.
2. Attacker constructs a `PerasCert` with `pcCertRound = <any round>` and `pcCertBoostedBlock = <point of a block on a shorter fork>`.
3. Attacker sends this certificate to the victim.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert { vpcCertBoost = PerasWeight 15 }` without any checks.
5. The certificate is added to the ChainDB via `ChainDB.addPerasCertAsync`.
6. The `PerasWeightSnapshot` now records a boost of 15 for the attacker-chosen block.
7. On the next chain selection, `preferAnchoredCandidate` computes `wsvTotalWeight` for the fork containing the boosted block as `blockNo + 15`, making a chain 15 blocks shorter appear heavier than the honest chain.
8. The victim node switches to the adversarially boosted fork. [9](#0-8) [10](#0-9) [11](#0-10)
