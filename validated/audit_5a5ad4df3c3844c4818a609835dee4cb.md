### Title
Unsigned `CC.headerProtocolMagicId` Header Field Bypasses Chain-Sync Validation, Enabling ImmutableDB Corruption via Crafted Block Relay - (File: `ouroboros-consensus-cardano/src/byron/Ouroboros/Consensus/Byron/Ledger/Integrity.hs`)

---

### Summary

The Byron block header contains one field — `CC.headerProtocolMagicId` — that is explicitly excluded from the PBFT signature. The live chain-sync validation path never checks this field; only the storage-recovery path (`nodeCheckIntegrity`) does. An unprivileged peer can relay any valid Byron block with this field mutated. The modified block passes all chain-sync and block-application checks, is stored in the ImmutableDB, and then causes the ImmutableDB to truncate the chain during the next recovery cycle, permanently rejecting a valid chain segment without any operator fault.

---

### Finding Description

The Byron block header is constructed in `Forge.hs` with `aHeaderProtocolMagicId` as a standalone annotated field, separate from the `CC.Block.ToSign` structure that is actually signed:

```
toSign = CC.Block.ToSign
  { tsHeaderHash, tsSlot, tsDifficulty, tsBodyProof,
    tsProtocolVersion, tsSoftwareVersion }
-- aHeaderProtocolMagicId is NOT in ToSign
``` [1](#0-0) 

The `validateView` implementation for `ByronBlock` builds the `PBftValidateRegular` view by calling `CC.recoverSignedBytes epochSlots regular` (which recovers only the `ToSign` bytes) and `mkByronContextDSIGN cfg (pbftGenKey pbftFields)` (which takes the protocol magic ID from the **node config**, not from the header field): [2](#0-1) 

The `mkByronContextDSIGN` function pairs the config's `byronProtocolMagicId` with the genesis key as the `ContextDSIGN`: [3](#0-2) 

The `verifyDSIGN` implementation for `ByronDSIGN` then verifies the signature over `recoverBytes a` (the `ToSign` bytes) prefixed with the sign tag derived from the context's magic ID — the `aHeaderProtocolMagicId` field in the wire header is never read: [4](#0-3) 

The chain-sync client calls `validateHeader`, which calls `updateChainDepState` via `validateView` — this is the only cryptographic check performed on incoming headers: [5](#0-4) 

The `verifyHeaderIntegrity` function, which is the **only** place that checks `CC.headerProtocolMagicId h == protocolMagicId`, is explicitly documented as compensating for this gap: [6](#0-5) 

This function is wired exclusively into `nodeCheckIntegrity` via `verifyBlockIntegrity`: [7](#0-6) 

`nodeCheckIntegrity` is invoked only during ImmutableDB and VolatileDB recovery (full-validation mode), not during live block ingestion.

---

### Impact Explanation

An attacker relays a valid Byron block with `aHeaderProtocolMagicId` mutated to any other value. The block passes:

1. **Chain-sync header validation** — `updateChainDepState` verifies the PBFT signature over `ToSign` bytes using the config's magic ID; the header field is never read.
2. **Block application** — the Byron ledger rules operate on the `ToSign`-covered fields; the comment "the only field of a regular header that is not signed, so check it manually" strongly implies the ledger rules do not independently check this field.
3. **ImmutableDB storage** — the block is accepted as canonical and written to the immutable chain.

On the next dirty-shutdown recovery or full-validation pass, `nodeCheckIntegrity` calls `verifyHeaderIntegrity`, which compares `CC.headerProtocolMagicId h` against the config value. The comparison fails. The ImmutableDB truncates the chain to the last valid block before the corrupted entry, permanently discarding all subsequent valid blocks without any operator action. The node must re-sync from that point.

This matches: **High — ImmutableDB corruption/rollback bug that causes permanent rejection of a valid chain without operator fault.**

---

### Likelihood Explanation

The attack requires only the ability to relay network traffic between a block producer and a victim node — no signing key, no stake, no privileged access. Any man-in-the-path peer or a malicious relay node can perform this modification. The `aHeaderProtocolMagicId` field is a plain annotated integer in the CBOR-encoded header; mutating it while preserving the rest of the wire bytes is trivial. The attack is deterministic and reproducible on a private testnet.

---

### Recommendation

The `headerProtocolMagicId` field should be included in the signed payload (`CC.Block.ToSign`) so that the PBFT signature covers it. As an immediate mitigation, `validateView` (or the envelope check layer) should explicitly compare `CC.headerProtocolMagicId` of the incoming header against the config value before constructing the `PBftValidateRegular` view, mirroring what `verifyHeaderIntegrity` already does in the recovery path. This closes the gap between the live validation path and the storage-recovery path.

---

### Proof of Concept

**Private-testnet reproduction steps:**

1. Run a two-node Byron private testnet (node A = block producer, node B = victim).
2. Intercept a valid block relayed from A to B (e.g., via a proxy).
3. Deserialise the CBOR-encoded block; locate the `aHeaderProtocolMagicId` annotated field in the header and change its integer value by 1.
4. Re-serialise and forward to B.
5. Node B's chain-sync client accepts the header: `validateView` extracts `CC.recoverSignedBytes` (which does not include the magic ID field) and constructs `mkByronContextDSIGN cfg ...` from the node config — the `verifySignedDSIGN` call succeeds.
6. Node B downloads and applies the block; the ledger accepts it.
7. The block is stored in B's ImmutableDB.
8. Simulate a dirty shutdown of node B (e.g., `kill -9`).
9. On restart, the ImmutableDB enters full-recovery mode and calls `nodeCheckIntegrity` → `verifyBlockIntegrity` → `verifyHeaderIntegrity`. The check `CC.headerProtocolMagicId h == protocolMagicId` fails.
10. The ImmutableDB truncates the chain to the block before the corrupted entry. Node B must re-sync all subsequent blocks.

-- | Verify whether a header is not corrupted.
--
-- The difference with 'verifyHeaderSignature' is that this function also
-- checks the integrity of the 'CC.headerProtocolMagicId' field, which is the
-- only field of a regular header that is not signed.
--
-- Note that we cannot check this for an EBB, as an EBB contains no signature.
-- This function will always return 'True' for an EBB.
verifyHeaderIntegrity :: BlockConfig ByronBlock -> Header ByronBlock -> Bool
verifyHeaderIntegrity cfg hdr =
  verifyHeaderSignature cfg hdr
    &&
    -- @CC.headerProtocolMagicId@ is the only field of a regular header that
    -- is not signed, so check it manually.
    case byronHeaderRaw hdr of
      CC.ABOBBlockHdr h -> CC.headerProtocolMagicId h == protocolMagicId
      -- EBB, we can't check it
      CC.ABOBBoundaryHdr _ -> True
 where
  protocolMagicId = byronProtocolMagicId cfg
```
