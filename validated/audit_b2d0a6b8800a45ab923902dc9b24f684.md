### Title
Silent nBTC Loss in `safe_mint` When Recipient Account Is Unregistered — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

The `safe_mint` function in the nBTC contract mints tokens into the bridge's own internal balance first, then silently aborts the transfer to the user if the recipient account is not registered in the nBTC contract. The minted amount is never tracked as a shortfall, leaving the user's tokens permanently locked in the bridge's nBTC balance with no recovery path.

---

### Finding Description

In `safe_mint` (lines 101–124 of `contracts/nbtc/src/lib.rs`), the function unconditionally calls `self.token.internal_deposit(&self.bridge_id, amount.into())` to credit the full `amount` to the bridge's own nBTC balance. It then checks whether the intended recipient is registered:

```rust
if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0));
}
```

If the recipient has not registered a storage account in the nBTC contract (via `storage_deposit`), the function returns `U128(0)` immediately. The tokens that were just minted into the bridge's balance are never forwarded to the user, and no shortfall record is created anywhere. The `lost_found` map that exists in the bridge contract (`ContractData.lost_found`) is only populated by `transfer_nbtc_callback` — it is never consulted or updated by `safe_mint`.

By contrast, the `mint` function (lines 126–148) uses `mint_inner`, which calls `self.token.internal_register_account(account_id)` if the account is absent, ensuring tokens always reach the recipient. `safe_mint` deliberately skips this auto-registration but provides no compensating shortfall-tracking mechanism.

---

### Impact Explanation

When `safe_mint` is triggered for an unregistered recipient:

1. The nBTC total supply increases by `amount` (tokens are minted to the bridge's balance).
2. The user receives zero nBTC.
3. No entry is written to `lost_found` or any other shortfall record.
4. The minted tokens are permanently absorbed into the bridge's nBTC balance with no on-chain pointer back to the user.

This constitutes a permanent, irrecoverable loss of the user's entitled nBTC tokens. Because the bridge's nBTC balance grows without a corresponding liability record, the bridge's internal accounting becomes inconsistent with the actual supply owed to users — a supply/accounting failure matching the allowed Medium impact class: *"Harmful smart-contract behavior without direct funds theft, including permanent burning below backed supply, broken callback rollback, or stuck bridge state requiring operator intervention."*

---

### Likelihood Explanation

Any user who triggers a bridge flow that routes through `safe_mint` without having previously called `storage_deposit` on the nBTC contract will silently lose their tokens. New users interacting with the bridge for the first time, or users whose nBTC storage registration has lapsed, are realistic victims. The condition (`accounts.get(&account_id).is_none()`) is a normal, reachable state — not an edge case — and requires no privileged access to trigger.

---

### Recommendation

Apply the same shortfall-tracking pattern already used in `transfer_nbtc_callback`. When `safe_mint` detects an unregistered recipient, record the owed amount in the bridge's `lost_found` map (or an equivalent per-user shortfall mapping in the nBTC contract) before returning, so the user can later claim their tokens once they register storage:

```rust
if self.token.accounts.get(&account_id).is_none() {
    // Track shortfall so user can claim after registering
    // e.g., emit an event or write to a shortfall map
    return PromiseOrValue::Value(U128(0));
}
```

Alternatively, auto-register the account (as `mint_inner` does) before attempting the transfer, eliminating the silent-failure path entirely.

---

### Proof of Concept

1. User deposits BTC; the bridge calls `safe_mint(user_account_id, amount, None)` on the nBTC contract.
2. `safe_mint` executes `self.token.internal_deposit(&self.bridge_id, amount.into())` — `amount` nBTC is now credited to the bridge's own balance; total supply increases.
3. `self.token.accounts.get(&user_account_id).is_none()` evaluates to `true` because the user has never called `storage_deposit` on the nBTC contract.
4. The function returns `PromiseOrValue::Value(U128(0))` — no transfer occurs, no shortfall is recorded.
5. The user's `amount` nBTC tokens remain permanently in the bridge's balance. The user's BTC is locked in the bridge, and they hold zero nBTC. No recovery mechanism exists. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
