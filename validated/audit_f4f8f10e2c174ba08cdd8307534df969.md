### Title
Peras Vote Validation Bypass via Missing Signature and VRF Checks in Degenerate `BlockSupportsPeras` Instance — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance's `validatePerasVote` function — the only instance active for all block types — performs only a stake-distribution membership lookup and completely omits cryptographic verification of the vote signature and VRF eligibility proof. An unprivileged peer can send crafted `PerasVote` messages with a valid voter ID but a fabricated (or absent) signature; these votes pass `validatePerasVote`, are stored in the vote pool, and can accumulate to quorum, causing a certificate to be forged for an attacker-chosen block. The companion `validatePerasCert` function in the same instance accepts every certificate unconditionally.

---

### Finding Description

`BlockSupportsPeras` is the typeclass that gates all Peras vote and certificate acceptance. Its only active instance is the catch-all degenerate one:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
``` [1](#0-0) 

Within this instance, `validatePerasVote` is defined as:

```haskell
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasVote _params stakeDistr vote
    | Just stake <- lookupPerasVoteStake vote stakeDistr =
        Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
    | otherwise =
        Left PerasValidationErr
``` [2](#0-1) 

The only check performed is `lookupPerasVoteStake`, which looks up the voter's ID in the stake distribution map:

```haskell
lookupPerasVoteStake vote distr =
  Map.lookup (pvVoteVoterId vote) (unPerasVoteStakeDistr distr)
``` [3](#0-2) 

The following checks are entirely absent:
- **Vote signature verification** — the `PerasVote` data type in this instance carries no signature field at all, so no BLS/DSIGN check is possible.
- **VRF eligibility proof** — non-persistent committee members must prove eligibility via a VRF output; this is never verified.
- **Round number validity** — the vote's `pvVoteRound` is never checked against the current epoch or committee epoch nonce.

The companion `validatePerasCert` is even more permissive — it accepts every certificate unconditionally:

```haskell
  validatePerasCert params cert =
    Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [4](#0-3) 

These functions are called directly from the production object-diffusion inbound path. `makePerasVotePoolWriterFromChainDB` and `makePerasVotePoolWriterFromVoteDB` both pass `validatePerasVote mkPerasParams sd vote` as the validation callback to `processVotes`:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [5](#0-4) 

`processVotes` then stores every vote that passes this check into the vote pool:

```haskell
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    ...
    mapM validateVote votesNotAlreadyInDb
  ...
  ([], validatedVotes) -> mapM_ (addVote . WithArrivalTime now) validatedVotes
``` [6](#0-5) 

The contrast with the full WFALS `implVerifyVote` — which verifies the BLS vote signature and the VRF eligibility proof — makes the omission concrete:

```haskell
  bimap InvalidVoteSignature id $ do
    verifyVoteSignature voterVoteVerificationKey electionId message sig
  ...
  void $ bimap InvalidVoterEligibilityProof id $ do
    evalVRF vrfContext (mkVRFElectionInput @crypto (epochNonce committee) electionId)
``` [7](#0-6)

### Impact Explanation

**Critical — Bypass of Peras vote/certificate signature validation enabling unauthorized certificate acceptance.**

An attacker who knows any pool ID present in the current `PerasVoteStakeDistr` (public information) can craft a `PerasVote` with that voter ID and an arbitrary (or empty) block target. The vote passes `validatePerasVote`, is stored in the pool, and contributes its full stake weight toward quorum. By sending enough such votes for a single target, the attacker can cause `votesReachQuorum` to return `Just`, triggering `forgePerasCert` for an attacker-chosen block. The resulting `ValidatedPerasCert` is then stored in the ChainDB and applied as a Peras boost, directly influencing chain selection in favour of a non-canonical or adversarially chosen chain.

---

### Likelihood Explanation

The attack requires only:
1. Knowledge of any pool ID in the current stake distribution (publicly available on-chain).
2. The ability to connect to a node and send `PerasVote` objects via the object-diffusion mini-protocol (available to any peer).

No key material, stake majority, or privileged access is needed. The degenerate instance is the only active instance for all block types; there is no override that would restore the missing checks.

---

### Recommendation

Replace the degenerate `validatePerasVote` and `validatePerasCert` implementations with ones that perform full cryptographic verification, mirroring the checks already present in `WFALS.implVerifyVote` and `WFALS.implVerifyCert`:

- Verify the BLS vote signature against the voter's registered public key.
- For non-persistent voters, verify the VRF eligibility proof against the epoch nonce and election ID.
- Verify the certificate's aggregate BLS signature against the aggregated public keys of all listed voters.
- Validate the round number against the current epoch's committee epoch nonce.

Until a full implementation is ready, the inbound `processVotes` path should refuse all votes rather than accept them with only a stake-distribution lookup, to avoid storing cryptographically unverified votes in the pool.

---

### Proof of Concept

1. Observe the current `PerasVoteStakeDistr` (e.g., from a local state-query). Extract any `PerasVoterId` `vid` with positive stake.
2. Construct a `PerasVote { pvVoteRound = r, pvVoteBlock = adversarialBlock, pvVoteVoterId = vid }` for each pool ID in the distribution, targeting `adversarialBlock`.
3. Send these votes to a node via the object-diffusion protocol.
4. `processVotes` calls `validatePerasVote mkPerasParams sd vote` for each; since `lookupPerasVoteStake` finds `vid` in `sd`, each vote is accepted and stored.
5. Once the accumulated stake of stored votes for `adversarialBlock` exceeds the quorum threshold, `votesReachQuorum` returns `Just`, `forgePerasCert` is called, and a `ValidatedPerasCert` boosting `adversarialBlock` is stored in the ChainDB — without any signature ever being checked.

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
