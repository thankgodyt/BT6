### Title
`require_pending_sign_capacity` Check Blocks Re-execution of Refunds When Pending Limit Is Reached - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
`finalize_refund_with_psbt` enforces a pending-sign capacity check (`require_pending_sign_capacity`) that is appropriate for first-time refund execution but incorrectly fires on re-execution of the same refund. Because the code explicitly supports calling `execute_refund` again to rebuild the transaction (e.g., after a consensus branch change), and because the old `BTCPendingInfo` is never removed before the check runs, any user at their pending-sign limit (default: 1) is permanently blocked from re-executing their refund.

### Finding Description
`finalize_refund_with_psbt` in `refund.rs` is the shared helper called by both the first and subsequent invocations of `execute_refund`. At line 342 it unconditionally calls `require_pending_sign_capacity`:

```rust
// refund.rs lines 339-342
if !self.check_account_exists(&caller) {
    self.internal_set_account(&caller, crate::Account::new(&caller));
}
self.require_pending_sign_capacity(&caller);
```

`require_pending_sign_capacity` (account.rs lines 113-123) panics when `pending_sign_count() >= max_pending_sign_txs`. The default limit is **1** (`get_max_pending_sign_txs` returns `1` when no per-account override exists).

After the first successful `execute_refund`:
- A `BTCPendingInfo` is inserted into `btc_pending_infos`.
- Its ID is inserted into `btc_pending_sign_ids` (line 373-375), so `pending_sign_count()` becomes 1.
- The refund request is kept with `executed = true` (lines 398-401) so `execute_refund` can be called again.

On the second call to `execute_refund` (re-execution):
- `pending_sign_count()` is still 1 (the first pending info was never removed).
- `require_pending_sign_capacity` evaluates `1 < 1` → **false** → panics with "Too many pending sign transactions".

The re-execution path is explicitly documented in the code:

```rust
// refund.rs lines 395-401
// Keep the request (so `execute_refund` can be called again to re-create
// the transaction) but mark it executed; it is removed only when the
// refund is finalized in `verify_refund_finalize`.
refund_request.executed = true;
```

Yet the capacity check in the shared `finalize_refund_with_psbt` makes this re-execution impossible for any user at the default limit of 1.

### Impact Explanation
A user whose refund has been executed (pending sign tx created) but not yet finalized on-chain cannot re-execute the refund after a consensus branch change or any other scenario requiring a new transaction. Their refund is stuck in `PendingInfoState::Refund(PendingInfoStage::PendingSign)` indefinitely. Resolution requires privileged operator action (e.g., manually increasing the user's `pending_tx_limits` entry or removing the stale pending info), constituting a stuck bridge state requiring operator intervention.

This matches: **Medium — stuck bridge state requiring operator intervention.**

### Likelihood Explanation
The default `max_pending_sign_txs` is 1 for all accounts without a custom override. Re-execution of `execute_refund` is an explicitly supported and documented code path. Therefore, **every** ordinary user who attempts to re-execute a refund (e.g., after a consensus branch change invalidates the first signed transaction) will hit this revert. The trigger is fully unprivileged and reachable by any refund requester.

### Recommendation
Move `require_pending_sign_capacity` out of `finalize_refund_with_psbt` and into only the first-execution path. Concretely, before calling `finalize_refund_with_psbt` on re-execution, remove the stale `BTCPendingInfo` (and its ID from `btc_pending_sign_ids`) so the slot is freed before the capacity check runs. Alternatively, skip the capacity check entirely when `refund_request.executed == true`, since re-execution does not increase the net number of pending sign transactions.

### Proof of Concept
1. User calls `request_refund` → refund request stored with `executed = false`.
2. User calls `execute_refund` → `finalize_refund_with_psbt` runs:
   - `pending_sign_count()` = 0 < 1 → capacity check passes.
   - `BTCPendingInfo` inserted; its ID added to `btc_pending_sign_ids`.
   - `refund_request.executed` set to `true`.
3. A consensus branch change invalidates the signed transaction; user calls `execute_refund` again.
4. `finalize_refund_with_psbt` runs again:
   - `pending_sign_count()` = 1 (from step 2, never removed).
   - `require_pending_sign_capacity`: `1 < 1` → **false** → panic "Too many pending sign transactions".
