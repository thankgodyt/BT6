### Title
`stakeAboveThreshold` Compares Unnormalized Absolute Stake Against a Relative Quorum Threshold, Enabling Unauthorized Peras Certificate Forging - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` compares a `PerasVoteStake` value directly against the relative `perasQuorumStakeThreshold` without any normalization. The code itself documents this as an unresolved unit mismatch. When the `PerasVoteStakeDistr` is populated from the ledger with absolute stake values (as intended), the comparison is between an absolute quantity and a relative threshold, causing the quorum check to be trivially satisfied by any single vote from any voter with non-trivial stake. This allows an unprivileged peer to trigger unauthorized Peras certificate forging with a single crafted vote message.

---

### Finding Description

`stakeAboveThreshold` in `SupportsPeras.hs` performs the core Peras quorum check:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake         = unPerasVoteStake voteStake
  quorumThreshold = unPerasQuorumStakeThreshold (perasQuorumStakeThreshold params)
  safetyMargin  = unPerasQuorumStakeThresholdSafetyMargin (perasQuorumStakeThresholdSafetyMargin params)
```

The code comment immediately above this function explicitly acknowledges the unit mismatch:

> *"TODO: this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units. That is, both are either absolute or relative (normalized) values. Under the current implementation of `PerasParams`, this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally."* [1](#0-0) 

The `perasQuorumStakeThreshold` field of `PerasParams` is a `Rational` intended to represent a **relative** fraction of total stake (e.g., `0.75` for 75%): [2](#0-1) 

The `PerasVoteStake` values stored in `PerasVoteStakeDistr` are looked up from the ledger's stake distribution and stored **as-is** in `vpvVoteStake` with no normalization: [3](#0-2) 

`votesReachQuorum` then sums these raw values and passes the total directly to `stakeAboveThreshold`: [4](#0-3) 

The ledger's stake distribution uses absolute Lovelace values (e.g., `1_000_000_000_000` for 1M ADA). Comparing such a value against a relative threshold of `0.75` makes the check trivially true for any voter with non-trivial stake. The comment in `SupportsPeras.hs` confirms no conversion mechanism exists yet:

> *"there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee"* [5](#0-4) 

The production network handler in `NodeToNode.hs` currently uses `pure (PerasVoteStakeDistr mempty)` as a placeholder, with an explicit TODO to wire in the real ledger stake distribution: [6](#0-5) 

The `makePerasVotePoolWriterFromChainDB` function, which is the production code path for inbound votes, accepts the `STM m PerasVoteStakeDistr` as a parameter and passes it directly to `validatePerasVote`: [7](#0-6) 

---

### Impact Explanation

When the `PerasVoteStakeDistr` is populated with absolute ledger stake values (the intended future state, as the TODO in `NodeToNode.hs` makes explicit), any single vote from a voter whose absolute stake exceeds `perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin` (e.g., `0.75 + 0.01 = 0.76`) will trivially satisfy the quorum check. Since any voter with more than 0.76 Lovelace of absolute stake satisfies this, **a single crafted vote from any committee member immediately forges a Peras certificate**. A forged certificate boosts the targeted block's chain weight by `perasWeight`, causing honest nodes to prefer an adversarially-chosen chain over the canonical one. This is a bypass of Peras voting/certificate checks enabling unauthorized certificate acceptance — matching the Critical impact tier.

---

### Likelihood Explanation

The vulnerability is currently latent because the production code uses `pure (PerasVoteStakeDistr mempty)`, causing all votes to be rejected at the `lookupPerasVoteStake` step before the quorum check is reached. However, the TODO comment in `NodeToNode.hs` explicitly states the intent to wire in the real ledger stake distribution. Once that plumbing is in place — a planned, tracked change — the vulnerability becomes immediately exploitable by any unprivileged peer that can send a `PerasVote` message over the `PerasVoteDiffusion` mini-protocol. The entry path requires no special privileges, no key compromise, and no stake majority.

---

### Recommendation

`stakeAboveThreshold` must not be called with raw ledger stake values. The fix should follow one of the two approaches the TODO itself identifies:

1. **Normalize before calling**: Divide each voter's absolute stake by the total stake of the entire committee before storing it in `PerasVoteStakeDistr`, so that `PerasVoteStake` values are always in `[0, 1]` and their sum is a fraction of total committee stake.
2. **Accept the full distribution**: Change `stakeAboveThreshold` (or `votesReachQuorum`) to accept the total committee stake as an additional parameter and perform the normalization internally before comparing against the relative threshold.

The normalization must be applied at the point where `PerasVoteStakeDistr` is constructed from the ledger, not deferred to the comparison site.

---

### Proof of Concept

**Setup**: Wire `makePerasVotePoolWriterFromChainDB` with a real `PerasVoteStakeDistr` containing a single entry `{ voter_A -> PerasVoteStake 1_000_000_000_000 }` (1M ADA in Lovelace, a plausible absolute ledger value). Use `mkPerasParams` defaults where `perasQuorumStakeThreshold = 0.75` and `perasQuorumStakeThresholdSafetyMargin = 0.01`.

**Attack**:
1. Adversary sends a single `PerasVote` message for voter_A targeting any block B.
2. `validatePerasVote` looks up voter_A in the distribution → `vpvVoteStake = 1_000_000_000_000`.
3. `votesReachQuorum` computes `totalVoteStake = 1_000_000_000_000`.
4. `stakeAboveThreshold` evaluates `1_000_000_000_000 >= 0.75 + 0.01` → `True`.
5. `forgePerasCert` is called → a `ValidatedPerasCert` boosting block B is produced.
6. The certificate is stored in the ChainDB and diffused to peers, causing all honest nodes to add `perasWeight` to block B's chain weight.

**Result**: A single vote from a single adversarial committee member forges a valid Peras certificate, bypassing the quorum requirement entirely. The quorum threshold parameter — the sole safety parameter protecting against unauthorized certificate forging — is rendered meaningless, directly analogous to the `minPSM` slippage parameter being rendered meaningless in the external report.
