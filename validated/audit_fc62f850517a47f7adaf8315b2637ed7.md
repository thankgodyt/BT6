### Title
Unverified `refund_address` in `request_refund` Allows Any Caller to Redirect BTC Refunds When `DepositMsg.refund_address` Is `None` — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`DepositMsg` has a mandatory `recipient_id` (NEAR account receiving nBTC) but an **optional** `refund_address` (BTC address for refund). When `refund_address` is `None`, the bridge accepts a caller-supplied BTC refund destination with no check that the caller is the original depositor. Because a duplicate-request guard blocks any subsequent `request_refund` for the same UTXO, an attacker who front-runs the legitimate depositor permanently locks the refund destination to an attacker-controlled BTC address.

---

### Finding Description

`DepositMsg` separates the two asset-type recipients: `recipient_id` for the NEAR-side nBTC mint, and the optional `refund_address` for the Bitcoin-side refund. [1](#0-0) 

When `deposit_msg.refund_address` is `None`, `internal_request_refund` performs no ownership check — it simply accepts whatever `refund_address` the caller passes:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
// If None → caller's refund_address is used unconditionally
``` [2](#0-1) 

`request_refund_callback` then stores the caller-supplied address verbatim and enforces a uniqueness guard that blocks any later competing request for the same UTXO:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [3](#0-2) 

The stored `refund_address` is later used verbatim by `execute_refund` to build the Bitcoin output via `build_refund_output`. [4](#0-3) 

The only protection is `unsafe_refund_timelock_sec`, a longer timelock intended to give the DAO time to call `internal_reject_refund`. [5](#0-4) 

However, the DAO has no on-chain way to determine the "correct" refund address when none was pre-committed in `DepositMsg`, making rejection a social/operational process that can fail silently.

---

### Impact Explanation

**Critical / Medium.** An attacker who front-runs the legitimate depositor's `request_refund` call permanently locks the refund destination to an attacker-controlled BTC address. If the DAO does not reject the request within `unsafe_refund_timelock_sec`, `execute_refund` constructs and signs a Bitcoin transaction paying the attacker. The depositor's BTC is stolen. Even if the DAO rejects in time, the UTXO is temporarily locked and the depositor cannot submit a competing refund request until the malicious one is rejected — constituting attacker-triggered temporary locking of bridged funds requiring operator intervention.

---

### Likelihood Explanation

**Medium.** The attack requires:
1. Monitoring BTC deposits whose `DepositMsg` encodes `refund_address: None` (observable on-chain from the OP_RETURN or deposit address derivation path).
2. Identifying deposits that are not finalized (e.g., bridge paused, relayer slow, or deposit below confirmation threshold).
3. Submitting `request_refund` before the legitimate depositor does.

Steps 1–3 are fully permissionless and require no privileged access. Front-running is straightforward on NEAR where transaction ordering is observable. Deposits without a pre-committed `refund_address` are the common case for users who do not anticipate needing a refund.

---

### Recommendation

Adopt the same fix recommended in the referenced report: separate the two recipient roles explicitly.

1. **Make `refund_address` mandatory in `DepositMsg`**, or
2. **Validate in `internal_request_refund` that `env::predecessor_account_id() == deposit_msg.recipient_id`** when `deposit_msg.refund_address` is `None`, binding the refund-request right to the NEAR account that owns the deposit, or
3. **Store the caller's identity alongside the refund request** and enforce that only the original requester (or a privileged role) can proceed to `execute_refund`.

This mirrors the LSSVMRouter fix of separating `tokenRecipient` and `nftRecipient` — here, the NEAR-side recipient (`recipient_id`) and the Bitcoin-side recipient (`refund_address`) must both be pre-committed and immutable so no third party can substitute an attacker-controlled destination.

---

### Proof of Concept

1. Alice deposits 0.1 BTC to the bridge address derived from `DepositMsg { recipient_id: "alice.near", refund_address: None, ... }`.
2. The bridge is temporarily paused; the deposit is not finalized.
3. Attacker Bob observes the unfinalized deposit on-chain, decodes the `DepositMsg` from the deposit address derivation path, and calls:
   ```
   request_refund(
       deposit_msg = { recipient_id: "alice.near", refund_address: None, ... },
       refund_address = "bc1q_attacker_address",
       tx_bytes = <Alice's deposit tx>,
       vout = 0,
       proof = <valid Merkle proof>,
       gas_fee = None
   )
   ```
4. `request_refund_callback` stores `refund_address = "bc1q_attacker_address"` and sets the duplicate guard. [6](#0-5) 
5. Alice attempts `request_refund` with her own address — it reverts: `"Refund request already exists for this UTXO"`. [3](#0-2) 
6. After `unsafe_refund_timelock_sec` elapses without DAO rejection, Bob calls `execute_refund`. The bridge constructs a Bitcoin transaction paying `"bc1q_attacker_address"` and requests an MPC signature. [4](#0-3) 
7. Alice's 0.1 BTC is sent to Bob.

        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
