Audit Report

## Title
Unrestricted `fee_recipient` in `sign_transfer` Allows Trusted Relayer to Steal Transfer Fees — (File: `near/omni-bridge/src/lib.rs`)

## Summary
`sign_transfer` accepts a caller-supplied `fee_recipient` with no validation against any stored value, and `sign_transfer_callback` only removes the transfer from `pending_transfers` when the fee is zero. A malicious trusted relayer can therefore call `sign_transfer` twice for the same `transfer_id` with different `fee_recipient` values, obtain two distinct valid MPC signatures, and submit the one that routes the fee to an attacker-controlled address, stealing 100% of the escrowed fee.

## Finding Description

**Root cause — unvalidated `fee_recipient` parameter:**

`sign_transfer` builds a `TransferMessagePayload` using the caller-supplied `fee_recipient` directly, with no check against any stored or previously committed value: [1](#0-0) 

The only fee-related guard checks that the provided `fee` *amount* matches the stored transfer fee; `fee_recipient` is never validated: [2](#0-1) 

**Root cause — transfer not removed after signing for non-zero fees:**

`sign_transfer_callback` removes the transfer from `pending_transfers` only when `fee.is_zero()`. For any transfer with a non-zero fee the record persists indefinitely, allowing `sign_transfer` to be called again for the same `transfer_id`: [3](#0-2) 

**Exploit chain:**

1. Attacker calls `sign_transfer(transfer_id, fee_recipient=Some("attacker.near"), fee=Some(...))` → MPC produces signature A over `payload_A` (containing `fee_recipient="attacker.near"`). Because fee ≠ 0, the transfer is **not** removed from `pending_transfers`.
2. Attacker calls `sign_transfer` again with `fee_recipient=Some("legitimate.near")` → MPC produces signature B over `payload_B`. Both signatures are valid.
3. Attacker submits `(sig_A, payload_A)` to EVM `finTransfer`. The EVM verifies the MPC signature, marks `destinationNonce` as consumed, and emits a `FinTransfer` event with `feeRecipient = "attacker.near"`: [4](#0-3) 

4. Attacker calls `claim_fee` on NEAR with a proof of that EVM event. `claim_fee_callback` extracts `fee_recipient` from the verified proof and checks it equals `predecessor_account_id`. Since the attacker controls `attacker.near` and calls from that account, the check passes: [5](#0-4) 

5. `send_fee_internal` transfers the full escrowed token fee (and native fee) to `attacker.near`: [6](#0-5) 

## Impact Explanation

A malicious trusted relayer can redirect 100% of the token fee and native fee for any non-zero-fee transfer to an attacker-controlled NEAR account. The principal amount and recipient are unaffected, but the fee escrow is mis-accounted: the legitimate relayer receives nothing and the attacker claims the fee via `claim_fee`. This is fee mis-accounting / escrow mis-accounting, which falls under the Critical impact scope.

## Likelihood Explanation

The trusted relayer role is open to any account that calls `apply_for_trusted_relayer` with the required stake (default 1,000 NEAR) and waits through the activation period (default ~7 days): [7](#0-6) 

No additional privilege beyond that is required. The attack requires no race condition or front-running — the attacker simply calls `sign_transfer` twice before submitting to the destination chain. The only cost is the MPC signing deposit paid twice. The attack is repeatable for every non-zero-fee transfer the attacker chooses to process.

## Recommendation

1. **Remove the transfer from `pending_transfers` after the first successful MPC signing regardless of fee amount.** The current conditional removal in `sign_transfer_callback` is the direct enabler of the second signing call.
2. **Store `fee_recipient` in `TransferMessage` at initiation time** (or lock it in on the first `sign_transfer` call) and require subsequent calls to supply the identical value.
3. As defense-in-depth, add an "in-flight signing" flag set before the MPC cross-contract call and cleared in the callback, preventing concurrent or repeated signing for the same `transfer_id`.

## Proof of Concept

```
// Setup: attacker has staked 1,000 NEAR and waited through activation period.
// User initiates transfer with fee = 100 tokens.
// pending_transfers[transfer_id] = TransferMessage { fee: Fee { fee: 100, ... }, ... }

// Step 1: first sign_transfer call
sign_transfer(transfer_id, fee_recipient=Some("attacker.near"), fee=Some(Fee{fee:100,...}))
// → MPC signs payload_A = hash(... fee_recipient="attacker.near" ...)
// → sign_transfer_callback: fee.is_zero() == false → transfer NOT removed
// → SignTransferEvent { sig_A, payload_A } emitted

// Step 2: second sign_transfer call (transfer still in pending_transfers)
sign_transfer(transfer_id, fee_recipient=Some("legitimate.near"), fee=Some(Fee{fee:100,...}))
// → MPC signs payload_B = hash(... fee_recipient="legitimate.near" ...)
// → SignTransferEvent { sig_B, payload_B } emitted
// Both sig_A and sig_B are valid MPC signatures over the same destination_nonce

// Step 3: submit sig_A + payload_A to EVM finTransfer
// completedTransfers[destination_nonce] = true
// FinTransfer event emitted with feeRecipient = "attacker.near"

// Step 4: attacker calls claim_fee on NEAR with EVM proof
// claim_fee_callback: fee_recipient ("attacker.near") == predecessor → passes
// Attacker receives 100 tokens; legitimate relayer receives nothing
```

Invariant broken: two distinct `SignTransferEvent`s are emitted with the same `destination_nonce` but different `fee_recipient` fields, violating the assumption that only one valid signed payload exists per transfer.
