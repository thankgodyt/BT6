The critical detail is in the root `Cargo.toml`:

```toml
[profile.release]
overflow-checks = true
```

This confirms the vulnerability is real. With `overflow-checks = true`, the subtraction `len - skip_n` when `skip_n > len` will **panic** even in release/wasm builds, not silently wrap.

### Title
Usize Underflow Panic in All Paged View Functions via Out-of-Bounds `from_index` - (`contracts/satoshi-bridge/src/api/view.rs`)

### Summary
Every paged view function in `view.rs` computes `take_n = limit.unwrap_or(len - skip_n)` without guarding against `skip_n > len`. Because the workspace release profile sets `overflow-checks = true`, this subtraction panics when an unprivileged caller passes `from_index = Some(N)` where `N > collection.len()` and omits `limit`.

### Finding Description
All eight paged view functions share the identical unsafe pattern:

```rust
let len   = usize::try_from(self.data().X.len())...;
let skip_n = from_index.unwrap_or(0);
let take_n = limit.unwrap_or(len - skip_n);   // ← panics when skip_n > len
```

Affected functions and their panic lines: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) 

The workspace release profile explicitly enables overflow checks, meaning the wasm binary produced for mainnet will trap on this subtraction: [9](#0-8) 

### Impact Explanation
These are NEAR view calls (read-only), so a panic aborts the call and returns an error to the caller — it does **not** corrupt contract state or lock funds. The concrete impact is that any unprivileged account can make all eight view endpoints return errors for any `from_index` value beyond the current collection size. Relayers and monitoring infrastructure that page through accounts, UTXOs, pending infos, refund requests, RBF txs, etc. will receive panics instead of results, disrupting off-chain observability and relayer operation. This maps to the **Low** allowed impact: "Publicly reachable invariant-violation, stuck-state, or panic-driven fault in production bridge/token paths without direct theft."

### Likelihood Explanation
Trivially reachable by any account with no prerequisites. A single RPC view call with `from_index = Some(999999)` and no `limit` is sufficient. No gas, no tokens, no role required.

### Recommendation
Replace the bare subtraction with a saturating version in all eight functions:

```rust
let take_n = limit.unwrap_or_else(|| len.saturating_sub(skip_n));
```

This returns `0` when `skip_n >= len`, causing the iterator to yield an empty result rather than panicking.

### Proof of Concept
```bash
# Assuming collection has 3 entries:
near view <contract> get_accounts_paged \
  '{"from_index": 9999, "limit": null}'
# → ExecutionError: "attempt to subtract with overflow"
```

The same call pattern triggers the panic on all eight paged functions identically.
