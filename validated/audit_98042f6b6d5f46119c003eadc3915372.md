Audit Report

## Title
Missing `omniBridgeChainId` in `deployToken` Signature Hash Enables Cross-Chain Replay of MPC Deployment Signatures - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
The `deployToken` function in `OmniBridge.sol` constructs a Borsh-encoded hash for MPC signature verification that omits `omniBridgeChainId`, while `finTransfer` correctly binds its hash to the destination chain via `omniBridgeChainId`. Because the hash is chain-agnostic, a valid MPC signature authorizing token deployment on one EVM chain (e.g., Ethereum) can be replayed verbatim on any other EVM chain (e.g., Arbitrum, Base, BNB) by any unprivileged attacker, deploying tokens on chains NEAR never explicitly authorized. The same structural omission is confirmed in the Starknet and Solana implementations.

## Finding Description
In `OmniBridge.sol::deployToken()`, the Borsh-encoded hash used for ECDSA signature verification is:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
bytes32 hashed = keccak256(borshEncoded);
if (ECDSA.recover(hashed, signatureData) != nearBridgeDerivedAddress) {
    revert InvalidSignature();
}
```

No `omniBridgeChainId` is included. Since the hash is a pure function of token metadata, it is identical across every deployed instance of `OmniBridge.sol` for the same token.

In contrast, `finTransfer()` encodes `omniBridgeChainId` twice:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.TransferMessage)),
    Borsh.encodeUint64(payload.destinationNonce),
    bytes1(payload.originChain),
    Borsh.encodeUint64(payload.originNonce),
    bytes1(omniBridgeChainId),   // chain binding
    Borsh.encodeAddress(payload.tokenAddress),
    Borsh.encodeUint128(payload.amount),
    bytes1(omniBridgeChainId),   // chain binding
    Borsh.encodeAddress(payload.recipient),
    ...
);
```

The only guard in `deployToken` against re-use is:

```solidity
require(!isBridgeToken[nearToEthToken[metadata.token]], "ERR_TOKEN_EXIST");
```

This check is per-chain state — it only prevents deploying the same token twice on the *same* chain. It does not prevent replaying the signature on a *different* chain where the token has not yet been deployed.

The same structural omission is confirmed in:
- **Starknet**: `MetadataPayloadImpl::to_borsh()` in `starknet/src/bridge_types.cairo` (lines 36–44) encodes only `PayloadType::Metadata`, token, name, symbol, and decimals — no chain ID — while `TransferMessagePayloadImpl::to_borsh()` (lines 61–84) accepts and encodes `chain_id`.
- **Solana**: `DeployTokenPayload::serialize_for_near()` in `solana/programs/bridge_token_factory/src/state/message/deploy_token.rs` (lines 19–26) serializes only `IncomingMessageType::Metadata` and the payload fields — no chain ID.

`starknet/CLAUDE.md` line 45 explicitly documents: *"Chain ID binding: Destination chain_id encoded in message hash (not in payload) - prevents cross-chain replay"* — but this design intent was applied only to `fin_transfer`, not to `deploy_token`.

**Exploit path (EVM)**:
1. NEAR MPC signs a `MetadataPayload` for `"token.near"` authorizing deployment on Ethereum.
2. A relayer submits `deployToken(signature, payload)` on Ethereum; the signature is publicly visible in calldata.
3. Attacker extracts `(signature, payload)` from the Ethereum transaction.
4. Attacker calls `deployToken(signature, payload)` on Arbitrum with identical arguments.
5. `OmniBridge.sol::deployToken()` computes the same hash (no chain ID) → `ECDSA.recover` returns `nearBridgeDerivedAddress` → signature check passes.
6. `"token.near"` is deployed on Arbitrum; `isBridgeToken`, `ethToNearToken`, `nearToEthToken` are populated; a `DeployToken` event is emitted.
7. NEAR's relayer/light-client observes the `DeployToken` event on Arbitrum and registers `"token.near"` as deployed there.
8. NEAR MPC begins signing `finTransfer` payloads for Arbitrum for `"token.near"`, enabling token flows to a chain NEAR never explicitly authorized.

## Impact Explanation
This is a confirmed chain/domain separation flaw. The NEAR MPC's signature over a `MetadataPayload` is intended to authorize deployment of a specific token on a specific chain. Because `omniBridgeChainId` is absent from the signed hash, a single MPC signature simultaneously authorizes deployment on every EVM chain (Ethereum, Arbitrum, Base, BNB, HyperEVM, Abs). An unprivileged attacker can replay any publicly observed `deployToken` calldata across all EVM chains, deploying tokens on chains where NEAR has not granted authorization. Once NEAR's bridge processes the resulting `DeployToken` event from the unauthorized chain, it registers the token there and begins signing `finTransfer` payloads for that chain — enabling invalid finalization of transfers on chains the NEAR MPC never explicitly approved. This matches the allowed critical impact: *"chain/domain separation flaw enabling invalid finalization."*

## Likelihood Explanation
High. The `deployToken` signature is publicly available in transaction calldata on any EVM chain. No privileged access, leaked keys, or admin compromise is required. The only precondition is that a valid `deployToken` signature exists for the target token on any one EVM chain — which is satisfied for every token already deployed through the bridge. The attack is permissionless, repeatable, and requires only a standard contract call.

## Recommendation
Include `omniBridgeChainId` in the Borsh-encoded hash for `deployToken` signature verification, mirroring the pattern used in `finTransfer`:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
    bytes1(omniBridgeChainId),          // ← add chain binding
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
```

Apply the equivalent fix to `MetadataPayloadImpl::to_borsh()` in `starknet/src/bridge_types.cairo` (accepting `chain_id` as a parameter, as `TransferMessagePayloadImpl::to_borsh()` already does) and to `DeployTokenPayload::serialize_for_near()` in `solana/programs/bridge_token_factory/src/state/message/deploy_token.rs`. The NEAR-side MPC signing logic must also be updated to include the destination chain ID when constructing the metadata payload hash, so that existing signatures for one chain are not valid on others.

## Proof of Concept
**Minimal Foundry test (local fork)**:

```solidity
// 1. Deploy OmniBridge on two local chains (chainId=1, chainId=42161)
// 2. Have the test MPC key sign a MetadataPayload for "token.near" (no chain ID in hash)
// 3. Call deployToken(sig, payload) on chain 1 → succeeds, token deployed
// 4. Call deployToken(sig, payload) on chain 42161 with identical (sig, payload) → succeeds
// 5. Assert: nearToEthToken["token.near"] != address(0) on chain 42161
// 6. Assert: DeployToken event emitted on chain 42161
// The identical sig passes ECDSA.recover on both chains because keccak256(borshEncoded) is identical.
```

**Differential test**: Compute `keccak256(borshEncoded)` for `deployToken` with `omniBridgeChainId=1` and `omniBridgeChainId=42161` — both produce the same digest, confirming the hash is chain-agnostic. Contrast with `finTransfer` where changing `omniBridgeChainId` changes the digest.
