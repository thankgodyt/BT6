### Title
Permissionless `request_refund` Allows Frontrunning to Redirect Victim's BTC Refund to Attacker-Controlled Address - (File: contracts/satoshi-bridge/src/api/bridge.rs, contracts/satoshi-bridge/src/refund.rs)

### Summary

`request_refund` is a fully public, permissionless function. When a deposit was made with `deposit_msg.refund_address = None`, any unprivileged NEAR account can call it for any UTXO and supply an arbitrary `refund_address`. Because `request_refund_callback` hard-blocks duplicate submissions for the same UTXO, an attacker who frontruns the legitimate user's call permanently occupies the refund slot with the attacker's own BTC address, redirecting the victim's funds.

### Finding Description

`request_refund` imposes no caller restriction: [1](#0-0) 

Inside `internal_request_refund`, the `refund_address` is only validated against `deposit_msg.refund_address` when that field is `Some`. When it is `None` (the common case for standard deposits), any BTC address is accepted without restriction: [2](#0-1) 

In `request_refund_callback`, a hard uniqueness check prevents any second submission for the same UTXO: [3](#0-2) 

The stored `refund_address` is then used verbatim when `execute_refund` builds the refund transaction output: [4](#0-3) 

**Attack path:**

1. Victim has a BTC deposit where `deposit_msg.refund_address` is `None` (standard deposit, no pre-authorized refund address).
2. Victim submits `request_refund(deposit_msg, victim_btc_addr, tx_bytes, vout, proof, None)`.
3. Attacker observes the pending NEAR transaction (all parameters are public), copies `deposit_msg`, `tx_bytes`, `vout`, and `proof`, substitutes `attacker_btc_addr`, and submits with a higher gas priority.
4. Attacker's call lands first; `request_refund_callback` stores `refund_address = attacker_btc_addr` for the UTXO key.
5. Victim's call reaches `request_refund_callback` and panics: `"Refund request already exists for this UTXO"`.
6. After `unsafe_refund_timelock_sec` (14 days by default), the attacker calls `execute_refund`; the bridge MPC-signs a transaction paying the attacker's BTC address.

The DAO can call `reject_refund` to cancel the attacker's request, but the attacker can immediately re-frontrun any subsequent victim submission, creating a permanent griefing loop. Even if the DAO is vigilant, the attacker can repeat the attack indefinitely at low cost (only the storage deposit is required). [5](#0-4) 

### Impact Explanation

**Critical.** The attacker can redirect the victim's entire BTC deposit to an attacker-controlled address. The victim loses their BTC permanently. This is a direct theft of user funds via the public bridge refund path, matching the "Significant loss, theft, destruction, or permanent locking of user or protocol funds" criterion.

### Likelihood Explanation

**High.** NEAR transactions are publicly observable before finalization. All parameters needed to frontrun (`deposit_msg`, `tx_bytes`, `vout`, `proof`) are visible in the victim's pending call. The attacker's only cost is the storage deposit for `request_refund`. The attack is repeatable after any DAO rejection, making it a persistent threat for any deposit with `deposit_msg.refund_address = None`.

### Recommendation

Restrict who may submit a refund request for a given UTXO. Two complementary mitigations:

1. **Bind the refund request to the caller**: Record `env::predecessor_account_id()` as the submitter and require that only the submitter (or DAO/Operator) can later call `execute_refund` for that request.
2. **Require `deposit_msg.refund_address` to be set**: Reject `request_refund` calls where `deposit_msg.refund_address` is `None` and the caller is not DAO/Operator, forcing users to pre-authorize their BTC address at deposit time (analogous to the St1inch fix: only the owner may update the lock duration).

### Proof of Concept

```
// Victim's pending NEAR transaction (visible in mempool):
request_refund(
  deposit_msg = { account_id: "victim.near", refund_address: None, ... },
  refund_address = "bc1q...victim...",
  tx_bytes = <victim's deposit tx>,
  vout = 0,
  proof = <valid merkle proof>,
  gas_fee = None
)

// Attacker frontruns with identical parameters except refund_address:
request_refund(
  deposit_msg = { account_id: "victim.near", refund_address: None, ... },  // copied
  refund_address = "bc1q...attacker...",   // <-- attacker's address
  tx_bytes = <same tx_bytes>,              // copied
  vout = 0,                                // copied
  proof = <same proof>,                    // copied
  gas_fee = None
)

// Result:
// - Attacker's request stored with attacker's BTC address
// - Victim's request panics: "Refund request already exists for this UTXO"
// - After 14 days: execute_refund() sends BTC to attacker
```

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
