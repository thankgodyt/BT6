### Title
`min_withdraw_amount` Check Incorrectly Applied to `DepositProtocolFee` in `ft_on_transfer` — (File: contracts/satoshi-bridge/src/api/token_receiver.rs)

### Summary
The `ft_on_transfer` function applies the `min_withdraw_amount` guard unconditionally — before the message type is decoded — so it incorrectly rejects `DepositProtocolFee` transfers whose amount is below the withdrawal minimum. This is a direct structural analog to the Connext "common-part check on the wrong side" class: a guard that belongs only in the `Withdraw` branch is placed in the shared preamble and fires for every message variant.

### Finding Description
`ft_on_transfer` is the NEP-141 callback that handles two logically distinct operations: `DepositProtocolFee` (adding fee reserves to the contract) and `Withdraw` (initiating a BTC withdrawal). The function's preamble enforces a single amount floor before it even inspects the message:

```
require!(
    amount >= self.internal_config().min_withdraw_amount,
    "Invalid amount"
);
```

Only after this check does the code branch on the message variant:

```rust
match message {
    TokenReceiverMessage::DepositProtocolFee => { … }
    TokenReceiverMessage::Withdraw { … }     => { … }
}
```

`min_withdraw_amount` is a withdrawal-specific policy (it guards against dust withdrawals that would be uneconomical on Bitcoin). It has no semantic meaning for `DepositProtocolFee`, which is simply an accounting credit to `acc_collected_protocol_fee` / `cur_available_protocol_fee`. Applying it there is the same structural mistake as the Connext `relayerFee <= txData.amount` check appearing in the common `fulfill` block instead of the receiving-chain block.

### Impact Explanation
Any `ft_transfer_call` carrying a `DepositProtocolFee` message with `amount < min_withdraw_amount` will panic with `"Invalid amount"` and the tokens will be returned to the caller. Because NEP-141 returns the full amount on failure, there is no permanent loss of funds. The impact is a publicly reachable invariant violation: the bridge's own fee-deposit path is broken for any amount below the withdrawal floor, which can prevent the protocol from accumulating fee reserves through small or incremental deposits. This fits the **Low** allowed impact: *"Publicly reachable invariant-violation, stuck-state, or panic-driven fault in production bridge/token paths without direct theft."*

### Likelihood Explanation
The trigger is straightforward and requires no privilege: any NEAR account holding nBTC can call `ft_transfer_call` on the nBTC contract with `msg = "DepositProtocolFee"` and an amount below `min_withdraw_amount`. The likelihood scales with how high `min_withdraw_amount` is configured relative to typical fee-deposit sizes.

### Recommendation
Move the `min_withdraw_amount` guard inside the `Withdraw` match arm so it only fires for withdrawal operations:

```rust
TokenReceiverMessage::Withdraw { … } => {
    require!(
        amount >= self.internal_config().min_withdraw_amount,
        "Invalid amount"
    );
    self.ft_on_transfer_withdraw_chain_specific(…)
}
```

### Proof of Concept
1. `min_withdraw_amount` is configured to `10_000` satoshis (a typical dust threshold).
2. A protocol operator calls `ft_transfer_call` on the nBTC contract:
   - `receiver_id`: bridge contract
   - `amount`: `"5000"` (5 000 satoshis — a valid fee contribution)
   - `msg`: `"DepositProtocolFee"`
3. The bridge's `ft_on_transfer` fires. Before decoding the message it executes:
   ```
   require!(5000 >= 10_000, "Invalid amount");  // panics
   ```
4. The call reverts; the 5 000 nBTC are returned to the caller; `acc_collected_protocol_fee` is not updated.
5. The same failure repeats for every sub-threshold fee deposit, permanently blocking that accumulation path until the operator raises the deposit amount above `min_withdraw_amount`.
