### Title
Peras Certificate and Vote Validation Bypass via Unconditional `Right` in Default `validatePerasCert` — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default implementation of `validatePerasCert` in the `BlockSupportsPeras` type class unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or structural checks. The companion `validatePerasVote` default implementation checks only stake-table membership but never verifies the vote's cryptographic signature. An unprivileged peer on a Peras-enabled network can submit crafted certificates and votes for arbitrary blocks, bypassing the quorum requirement entirely and causing honest nodes to apply illegitimate chain-selection boosts.

---

### Finding Description

`BlockSupportsPeras` is the production type class that links a block type to the Peras protocol extension. It exposes two validation entry points that are called on objects received from the network:

**`validatePerasCert`** — the default implementation:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This unconditionally wraps any incoming `PerasCert` in `Right ValidatedPerasCert` and assigns it the full protocol boost weight (`perasWeight params`). No aggregate-signature check, no quorum check, no round-number consistency check, and no boosted-block ancestry check is performed.

**`validatePerasVote`** — the default implementation:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
```

This checks only that the claimed voter ID appears in the stake distribution, but never verifies the vote's cryptographic signature. Any party that knows a staked voter's ID (public information) can forge a vote on their behalf.

The analogy to the external report is direct: just as `bringUnusedETHBackIntoGiantPool` accepts caller-supplied vault addresses and calls privileged operations on them without verifying the vaults are legitimate, `validatePerasCert` accepts caller-supplied certificates and grants them a full chain-selection boost without verifying the certificate is legitimate. In both cases the trusted context (the pool's `msg.sender` / the node's chain-selection weight) is exploited through an unverified externally-supplied object.

---

### Impact Explanation

Peras certificates boost specific blocks during chain selection. A `ValidatedPerasCert` carrying `vpcCertBoost = perasWeight params` causes the node to prefer the boosted block's chain over competing chains of equal or slightly greater length. Because `validatePerasCert` never checks the aggregate BLS signature, the quorum threshold, or the round number, an attacker can:

1. Craft a `PerasCert` pointing to any block (e.g., the tip of a minority fork).
2. Submit it to a Peras-enabled node via the certificate diffusion protocol.
3. The node calls `validatePerasCert`, which returns `Right` unconditionally.
4. The certificate is stored and applied to chain selection with full boost weight.
5. The node switches to or retains the attacker-chosen fork, diverging from the honest majority chain.

This is a **Critical bypass of Peras certificate/vote verification** that enables unauthorized certificate acceptance and chain-selection manipulation without possessing any cryptographic key or stake.

---

### Likelihood Explanation

The vulnerability is reachable by any unprivileged peer on a Peras-enabled network (private testnet or future mainnet deployment). The attack requires only the ability to send a well-formed `PerasCert` message over the certificate diffusion miniprotocol — no stake, no KES/VRF key, and no BLS key are needed. The TODO comments and the referenced GitHub issue (`tweag/cardano-peras#120`) confirm the incomplete validation is a known, unresolved gap in the production code, not an intentional design choice.

---

### Recommendation

1. **`validatePerasCert`**: Implement full certificate validation before returning `Right`:
   - Verify the aggregate BLS signature over `(electionId, boostedBlock)` against the aggregated verification keys of the claimed voters.
   - Verify each claimed voter's VRF output (for non-persistent seats) against the committee's VRF verification key.
   - Check that the total stake of the claimed voters meets or exceeds the quorum threshold (`perasQuorumThreshold`).
   - Check that the certificate's round number is consistent with the current chain state.

2. **`validatePerasVote`**: Add signature verification before accepting a vote:
   - Verify the vote's cryptographic signature against the voter's public key retrieved from the stake distribution, not just the voter's presence in the distribution.

3. Until full validation is implemented, the default instances should return `Left PerasValidationErr` (reject all) rather than `Right` (accept all), so that the safe default is rejection rather than acceptance.

---

### Proof of Concept

On a private testnet with Peras enabled:

1. Observe the current canonical chain tip `T` and a competing minority fork tip `F`.
2. Construct a `PerasCert { pcCertRound = r, pcCertBoostedBlock = F }` for any round `r` and any block point `F`.
3. Submit the crafted certificate to a target node via the Peras certificate diffusion protocol.
4. The node invokes `validatePerasCert params cert`, which returns `Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }` unconditionally.
5. The certificate is stored in the Peras certificate database and applied to chain selection.
6. The node now assigns `perasWeight params` boost to `F`'s chain, causing it to prefer `F` over `T` even if `T` is the honest majority chain.
7. The node diverges from the honest chain, constituting a chain-selection safety failure triggered by a single unprivileged peer message. [1](#0-0) [2](#0-1) [3](#0-2)
