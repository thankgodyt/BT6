Audit Report

## Title
Native ETH Delivery Failure in `finTransfer` Permanently Freezes Bridged Funds - (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

## Summary
In `OmniBridge.finTransfer`, when delivering native ETH to a smart-contract recipient that cannot accept ETH, the low-level `call` returns `success = false` and the function reverts with `FailedToSendEther()`. Because Solidity reverts roll back all state changes, the `completedTransfers[destinationNonce] = true` write at line 287 is also undone. Since the recipient address is immutably embedded in the MPC-signed payload, every subsequent finalization attempt with the same valid payload hits the identical revert, permanently preventing nonce consumption and leaving the user's source-chain tokens irrecoverable.

## Finding Description
`finTransfer` marks the nonce at line 287 before performing any token delivery:

```solidity
completedTransfers[payload.destinationNonce] = true;   // line 287
```

For native ETH (`tokenAddress == address(0)`), it then executes:

```solidity
(bool success, ) = payload.recipient.call{value: payload.amount}("");
if (!success) revert FailedToSendEther();              // lines 319–322
```

If `payload.recipient` is a contract without a payable `receive()` or `fallback()`, the call returns `success = false`. The `revert FailedToSendEther()` rolls back the entire transaction, including the nonce write. The nonce is never consumed.

The recipient is Borsh-encoded into the MPC-signed payload at line 298:
```solidity
Borsh.encodeAddress(payload.recipient),
```
Altering `payload.recipient` invalidates the MPC signature. There is no admin escape hatch, no alternative-recipient claim function, and no mechanism to mark the nonce as used without successfully delivering ETH. Every future `finTransfer` call with the same valid payload will revert identically. The contract has no per-user ETH balance tracking and no refund path on the source chain.

## Impact Explanation
Permanent freezing of bridged native ETH, matching the allowed Critical impact class: *"Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet, Bitcoin, Zcash, or Wormhole-routed flows."* The user's source-chain tokens are locked or burned with zero recovery path. The bridge contract itself holds the ETH (it has a `receive()` at line 574) but provides no mechanism to release it to an alternative address.

## Likelihood Explanation
Smart-contract recipients are a standard bridge use case: multisigs (e.g., Gnosis Safe without a payable fallback), protocol treasuries, proxy contracts, and DeFi vaults frequently lack a payable `receive()`. The `message` field in the payload already anticipates programmatic/contract recipients. No attacker is required — any user who specifies such an address triggers the freeze with a single transfer. The condition is self-inflicted but the failure mode (permanent loss) is disproportionate and non-obvious to users.

## Recommendation
Apply the pull-over-push pattern for native ETH delivery. Instead of reverting on a failed `call`, record the unclaimed amount in a mapping (e.g., `mapping(uint64 => uint256) public unclaimedEth`) and mark the nonce as used unconditionally. Expose a separate `claimEth(uint64 destinationNonce)` function that allows the original recipient (or an admin-designated fallback) to withdraw. This eliminates the permanent-freeze scenario while preserving replay protection.

Alternatively, enforce EOA-only recipients for native ETH at finalization time:
```solidity
require(payload.recipient.code.length == 0, "ETH recipient must be EOA");
```
This surfaces the failure early (before source-chain funds are committed) rather than silently freezing them after the cross-chain proof is submitted.

## Proof of Concept
1. Deploy a contract `NoReceive` with no `receive()` or `fallback()` on the EVM destination chain.
2. On NEAR, call `initTransfer` with `tokenAddress = address(0)` and `recipient = address(NoReceive)`. Source-chain tokens are locked/burned.
3. The NEAR MPC network signs the `TransferMessage` payload embedding `NoReceive` as `recipient`.
4. A relayer calls `OmniBridge.finTransfer(signatureData, payload)`.
5. `payload.recipient.call{value: payload.amount}("")` returns `success = false`; the function reverts with `FailedToSendEther()`. The `completedTransfers[destinationNonce]` write is rolled back.
6. Repeat step 4 with the same valid payload — identical revert every time. No other function can consume the nonce or release the ETH. Source-chain tokens are permanently frozen.

A minimal Foundry test can demonstrate this: deploy `OmniBridge`, fund it with ETH, deploy `NoReceive`, construct a valid signed payload targeting `NoReceive`, call `finTransfer`, and assert the transaction reverts and `completedTransfers[nonce]` remains `false`.
