### Title
Peras `stakeAboveThreshold` compares un-normalized absolute vote stake against a relative quorum threshold, enabling certificate-quorum bypass - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The `stakeAboveThreshold` function used to gate Peras certificate forging compares accumulated `PerasVoteStake` values directly against a fixed relative quorum threshold (`3/4 + safety_margin = 0.77`) without normalizing the vote stake by total stake. An explicit developer TODO in the production source acknowledges that the function "only makes sense when both values are relative (normalized) values" but that normalization is not currently performed. When the stake distribution plumbing is wired to real ledger stake (absolute lovelace values), any single pool operator can forge a Peras certificate for an arbitrary block with one vote, bypassing the quorum requirement entirely.

### Finding Description

`stakeAboveThreshold` in `SupportsPeras.hs` is the sole gate that decides whether accumulated votes reach quorum:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
``` [1](#0-0) 

The developer comment immediately above this function states:

> "this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [2](#0-1) 

`PerasVoteStake` is a bare `Rational` with no enforced unit:

```haskell
newtype PerasVoteStake = PerasVoteStake { unPerasVoteStake :: Rational }
``` [3](#0-2) 

The stake assigned to a validated vote is taken verbatim from `PerasVoteStakeDistr` — a `Map PerasVoterId PerasVoteStake` — with no normalization step:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
``` [4](#0-3) 

`stakeAboveThreshold` is called inside `votesReachQuorum`, which is the function that triggers certificate forging:

```haskell
votesHaveEnoughStake = stakeAboveThreshold cfg totalVoteStake
``` [5](#0-4) 

And `votesReachQuorum` is called inside `updateCandidateVoteState`, which forges the certificate on `Just`:

```haskell
case votesReachQuorum cfg voteList of
  Just votesWithQuorum -> do
    cert <- forgePerasCert cfg votesWithQuorum
    pure $ BecameWinner (PerasTargetVoteWinner newVoteTally cert)
``` [6](#0-5) 

The production node-to-node handler currently passes `PerasVoteStakeDistr mempty` (empty map) as a placeholder:

```haskell
-- Note that the empty stake distribution will cause all votes to
-- be considered invalid.
(pure (PerasVoteStakeDistr mempty))
``` [7](#0-6) 

When the real ledger stake distribution is wired in (as the TODO comments indicate is planned), if the values are absolute lovelace amounts (e.g., `1_000_000` for 1 ADA), then `totalVoteStake` for a single vote will be `1_000_000`, which is vastly greater than `0.77`. The quorum check passes immediately with one vote.

### Impact Explanation

An unprivileged pool operator whose `PerasVoterId` appears in the stake distribution can send a single crafted `PerasVote` targeting any block. Because `stakeAboveThreshold` compares the absolute lovelace value against the relative threshold `0.77`, the check trivially passes. A `ValidatedPerasCert` is forged and stored in the `PerasVoteDB` / `ChainDB`, boosting the targeted block's chain-selection weight by `perasWeight = 15` slots. This lets the adversary make honest nodes prefer a non-canonical or adversarially-chosen chain, constituting a **bypass of Peras certificate/vote verification** and a **chain-selection manipulation** without requiring stake majority, key compromise, or operator access.

### Likelihood Explanation

The bug is latent: the production code currently uses an empty stake distribution, so no votes are accepted today. However, the developer comments in both `SupportsPeras.hs` and `PerasVote.hs` explicitly state that real committee selection data will replace the placeholder. The comment on `PerasVoteStake` itself says "there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake", meaning the normalization step is undefined and likely to be omitted when the plumbing is completed. Any pool operator becomes an attacker the moment the stake distribution is populated with un-normalized ledger values.

### Recommendation

1. **Enforce normalization at the boundary**: `stakeAboveThreshold` should accept the total stake as an additional parameter and normalize internally: `stake / totalStake >= quorumThreshold + safetyMargin`.
2. **Alternatively**, populate `PerasVoteStakeDistr` with pre-normalized relative values (each entry = pool's absolute stake / total stake) before passing it to `validatePerasVote`.
3. **Add a type-level distinction** between absolute `LedgerStake` and relative `NormalizedStake` to prevent future unit confusion, mirroring the pattern already used in `WFALS.hs` (`LedgerStake` vs `VoteWeight`).
4. **Remove the `mempty` placeholder** only after the normalization contract is enforced and tested.

### Proof of Concept

```
Precondition: stake distribution is populated with absolute lovelace values,
e.g., PerasVoteStakeDistr { poolA -> PerasVoteStake 1_000_000 }

1. Adversary (pool A) sends PerasVote { pvVoteRound = R, pvVoteBlock = adversarialBlock, pvVoteVoterId = poolA }
2. validatePerasVote looks up poolA → stake = PerasVoteStake 1_000_000
3. updateCandidateVoteState calls votesReachQuorum with totalVoteStake = 1_000_000
4. stakeAboveThreshold: 1_000_000 >= 0.75 + 0.02  →  True
5. forgePerasCert is called → ValidatedPerasCert { boost = 15 } stored in ChainDB
6. Chain selection now weights adversarialBlock 15 slots heavier than any competing tip
```
