### Title
Peras Certificate Validation Stub Accepts Any Peer-Crafted Certificate, Enabling Adversarial Chain-Selection Boost - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` implementation in `SupportsPeras.hs` is an acknowledged stub that unconditionally returns `Right` for every certificate it receives, performing zero quorum, signature, or round-validity checks. Because the Peras certificate inbound pipeline (`processCerts`) feeds directly into `PerasCertDB` and then into chain selection, an unprivileged peer can send a crafted `PerasCert` for any block — including one on an adversarial fork — and the node will accept it, boost that block's chain weight, and potentially switch to the adversarial chain.

---

### Finding Description

**Root cause — `validatePerasCert` stub:**

The `BlockSupportsPeras` default instance contains:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

No check is performed on:
- Whether the certificate carries a valid aggregate BLS/quorum signature from ≥ 3/4 of stake
- Whether the `pcCertRound` is a valid, current round
- Whether the `pcCertBoostedBlock` is a block that actually exists on any known chain
- Whether the certificate was produced by an eligible voting committee

**Inbound pipeline unconditionally accepts the stub result:**

`processCerts` in the Peras certificate object-diffusion pool calls `validatePerasCert mkPerasParams` on every inbound certificate. Because the stub always returns `Right`, the entire batch is accepted and timestamped:

```haskell
(validatePerasCert mkPerasParams)
(void . ChainDB.addPerasCertAsync chainDB)
``` [2](#0-1) 

The `processCerts` function only rejects a batch when `validateCert` returns `Left`; since the stub never does, every peer-supplied certificate passes: [3](#0-2) 

**Chain selection is triggered for the boosted block:**

After the certificate is stored, `chainSelSync` triggers chain selection for the boosted block:

```haskell
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

**Chain selection uses the boost to prefer heavier chains:**

`weightedSelectView` computes `wsvTotalWeight = BlockNo + weightBoost`, and `preferCandidate` switches to the candidate chain if its total weight exceeds the current chain's:

```haskell
case compare (wsvTotalWeight ours) (wsvTotalWeight cand) of
    LT -> ShouldSwitch (Heavier ...)
``` [5](#0-4) 

The boost magnitude is `perasWeight params` (a `Word64`). With the default `mkPerasParams` value of 15 (as seen in benchmarks), a single crafted certificate can tip chain selection in favour of an adversarial fork that is up to 15 blocks shorter than the honest chain.

Additionally, `takeVolatileSuffix` uses `totalWeightOfFragment` to determine which blocks are "immutable" (buried under weight ≥ k). A crafted certificate boosting a block near the immutable tip can cause the node to prematurely treat adversarial blocks as immutable, preventing rollback to the honest chain. [6](#0-5) 

---

### Impact Explanation

An unprivileged peer can send a single crafted `PerasCert` pointing to a block on an adversarial fork. The node accepts it without any quorum or signature check, boosts the adversarial fork's chain weight by `perasWeight params`, and may switch its selection to the adversarial chain. This is a **chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain**, matching the "High" impact tier. If `perasWeight` is configured large enough relative to the volatile window, the impact escalates to a **Critical** consensus safety failure (acceptance of an invalid/adversarial ledger state).

---

### Likelihood Explanation

Any peer that can connect to the node's Peras certificate mini-protocol endpoint can exploit this. No stake, keys, or special privileges are required — only the ability to send a well-formed CBOR-encoded `PerasCert` message. The Peras certificate diffusion protocol is a public-facing network endpoint. Likelihood is **High** once Peras is activated on a network running this code.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
1. Verifies the aggregate BLS signature over the certificate against the voting committee's aggregate public key.
2. Checks that the total stake of the signers meets the quorum threshold (`perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin`).
3. Validates that `pcCertRound` is a plausible round number (not in the past beyond the cooldown window, not in the future beyond the current round).
4. Validates that `pcCertBoostedBlock` refers to a block that is at least `perasBlockMinSlots` old.

Until the real implementation is in place, the inbound certificate pipeline should reject all externally received certificates rather than accepting them unconditionally. [7](#0-6)

### Proof of Concept

**Analogy to the external report:**

| External (Market.sol) | Ouroboros Consensus |
|---|---|
| `intent.price` is not bounds-checked | `PerasCert` is not signature/quorum-checked |
| Accepted because collateral check only uses `lastVersion.price` | Accepted because `validatePerasCert` always returns `Right` |
| At settlement, `(Intent.price - lastVersion.price) * taker()` generates huge PnL | At chain selection, `wsvTotalWeight = BlockNo + perasWeight` boosts adversarial fork |
| Attacker steals funds from the contract | Attacker causes honest node to adopt adversarial chain |

**Concrete attack sequence:**

1. Adversary connects to an honest node's Peras certificate diffusion endpoint.
2. Adversary constructs a `PerasCert { pcCertRound = R, pcCertBoostedBlock = adversarialBlockPoint }` where `adversarialBlockPoint` is a block on a fork that is `perasWeight - 1` blocks shorter than the honest chain.
3. Adversary sends the certificate. `processCerts` calls `validatePerasCert mkPerasParams`, which returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }`.
4. `chainSelSync` triggers chain selection for `adversarialBlockPoint`.
5. `weightedSelectView` computes the adversarial fork's total weight as `BlockNo_adv + perasWeight`, which now exceeds the honest chain's `BlockNo_honest`.
6. `preferCandidate` returns `ShouldSwitch`; the node adopts the adversarial chain.

The only precondition is that the adversarial block is present in the node's VolatileDB (i.e., the adversary has also sent the block body, which is independently validated but does not prevent the certificate from being accepted first). [8](#0-7) [1](#0-0)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes

  -- Deliver promise indicating that we processed the cert.
  lift $ atomically $ putTMVar varProcessed certResult
```
