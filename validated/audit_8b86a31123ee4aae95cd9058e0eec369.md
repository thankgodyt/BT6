Audit Report

## Title
Premature Irreversible Burn of Deployed Tokens in `init_transfer_internal` With No Recovery Path — (`File: near/omni-bridge/src/lib.rs`)

## Summary

When a user bridges a deployed (non-native) token from NEAR to a foreign chain, `init_transfer_internal` immediately and unconditionally burns the tokens via a fire-and-forget cross-contract call before any confirmation that the destination chain has finalized the transfer. No cancel or refund path exists anywhere in the contract. If destination-chain finalization permanently fails for any reason, the burned NEAR tokens are irrecoverable while the corresponding locked funds on the destination chain remain stranded.

## Finding Description

**Burn is immediate and detached:**

In `init_transfer_internal` (lines 1850–1857), as soon as the token is identified as a NEAR-origin deployed token, `burn_tokens_if_needed` is called:

```rust
if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
    self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
    ...
}
```

`burn_tokens_if_needed` (lines 1806–1813) fires a cross-contract call with `.detach()` — no callback, no result check:

```rust
fn burn_tokens_if_needed(&self, token: AccountId, amount: U128) {
    if self.is_deployed_token(&token) {
        ext_token::ext(token)
            .with_static_gas(BURN_TOKEN_GAS)
            .burn(amount)
            .detach();   // fire-and-forget
    }
}
```

**No recovery in `sign_transfer_callback`:**

The only callback in the outbound path (lines 648–668) silently drops MPC failures — no refund, no cancel, no state cleanup beyond the success branch:

```rust
pub fn sign_transfer_callback(...) {
    if let Ok(signature) = call_result {  // error branch: nothing
        ...
    }
}
```

**No cancel path exists:**

A grep for `cancel_transfer`, `refund_transfer`, and `revert_transfer` in `lib.rs` returns zero matches. The only function that removes a record from `pending_transfers` is `claim_fee` (lines 1057–1094), which requires a cryptographic proof that the destination chain **successfully finalized** the transfer. If finalization never occurs, the record is orphaned in `pending_transfers` forever.

**Contrast with the inbound path:**

The inbound `fin_transfer` path (lines 1702–1718) correctly calls `revert_lock_actions` and `remove_fin_transfer` on failure — demonstrating the protocol authors know how to implement safe rollback, but did not apply it to the outbound burn path.

**Same pattern in `fast_fin_transfer_to_other_chain`:**

Lines 932–938 show the identical premature-burn pattern for fast transfers to other chains, with no recovery path either.

## Impact Explanation

This directly matches the Critical allowed impact: **permanent loss of bridged funds**. A user who initiates an outbound transfer of any deployed token (wETH, wSOL, or any token whose origin chain is not NEAR) has their tokens burned on NEAR the moment `init_transfer_internal` executes. If destination-chain finalization permanently fails, the user loses their NEAR-side tokens while the corresponding locked funds on the destination chain remain inaccessible — total, irrecoverable loss on both sides with no on-chain remedy.

## Likelihood Explanation

Permanent finalization failure can be triggered by an unprivileged external user or by realistic operational conditions without requiring admin key compromise, MPC threshold collusion, or NEAR validator collusion:

1. **Destination bridge permanently paused or deprecated**: If the destination-chain bridge contract is paused (e.g., due to a security incident on that chain) after the NEAR burn but before the relayer submits `finTransfer`, and is never unpaused (or the contract is replaced/deprecated), finalization is permanently impossible.
2. **Incorrect or missing token mapping on destination**: If the token address registered on the destination chain is wrong or absent, `finTransfer`/`finalize_transfer` reverts permanently. The NEAR side performs no post-burn validation of destination-chain readiness.
3. **Permanent MPC unavailability for a specific transfer**: If the MPC network is unavailable and the transfer's pending record is never signed, the burned tokens have no recovery path.

None of these require privileged access. A normal token holder triggering `ft_transfer_call` is sufficient to enter the vulnerable state.

## Recommendation

1. **Do not burn in `init_transfer_internal`**. Since tokens arrive via `ft_transfer_call`, they are already held by the bridge contract. Keep them locked (not burned) until destination finalization is confirmed.
2. **Burn only upon confirmed finalization**: Move the burn to `claim_fee_callback` (or a new finalization-confirmed callback), triggered only after a valid destination-chain proof is verified.
3. **Add a cancel/timeout path**: Allow the original sender to cancel a pending outbound transfer after a configurable timeout if no finalization proof has been submitted, returning the locked tokens.
4. **Add a callback to `burn_tokens_if_needed`**: At minimum, if the burn-on-init design is retained, attach a callback that reverts the transfer record and returns tokens to the sender if the burn cross-contract call fails.

This mirrors the safe pattern already present in the inbound path at lines 1702–1718, which correctly calls `revert_lock_actions` on failure.

## Proof of Concept

1. Alice holds 1000 wETH.near (a deployed token; origin chain = Ethereum).
2. Alice calls `ft_transfer_call` on `weth.near`, targeting the NEAR Omni Bridge, to bridge back to Ethereum.
3. `init_transfer_internal` executes: `burn_tokens_if_needed` fires a detached burn of 1000 wETH.near. Alice now holds 0 wETH.near. The transfer record is added to `pending_transfers`.
4. The Ethereum `OmniBridge` contract is paused (e.g., due to a security incident on Ethereum) before the relayer submits `finTransfer`.
5. The relayer's `finTransfer` call reverts with `PAUSED`. The relayer cannot finalize.
6. The Ethereum bridge is never unpaused (or is replaced by a new contract that does not recognize the old transfer ID).
7. `claim_fee` cannot be called — it requires a proof of successful `finTransfer`, which never happened.
8. Alice's 1000 wETH.near are permanently burned. The 1000 ETH remain locked in the Ethereum bridge. Alice has suffered total, irrecoverable loss on both chains with no on-chain remedy.

**Minimal test plan**: Deploy the NEAR bridge on localnet with a mock token contract. Call `ft_transfer_call` to initiate an outbound transfer of a deployed token. Confirm the burn fires (check token balance drops to zero). Then simulate MPC failure in `sign_transfer_callback` (return an error). Confirm no refund occurs and the transfer record remains in `pending_transfers` indefinitely. Confirm `claim_fee` cannot be called without a destination-chain proof. Assert Alice's token balance is permanently zero with no recovery path.
