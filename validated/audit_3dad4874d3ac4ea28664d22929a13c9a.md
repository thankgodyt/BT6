Audit Report

## Title
Permanent Fund Loss When `normalize_amount` Returns Zero in `sign_transfer` After Tokens Are Already Burned/Locked — (File: `near/omni-bridge/src/lib.rs`)

## Summary

When a user initiates a NEAR-to-foreign-chain transfer with an amount (minus fee) smaller than the decimal normalization divisor, their tokens are irreversibly burned or locked inside `init_transfer_internal` before any normalization check occurs. The zero-amount guard only fires later in `sign_transfer`, which panics and reverts that transaction while leaving the transfer message permanently in storage with no cancel or refund path.

## Finding Description

`normalize_amount` uses floor division:

```rust
// L2784-2787
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

If `amount - fee < 10^(origin_decimals - decimals)`, the result is `0`.

The only guard against a zero normalized amount is inside `sign_transfer` (L475–485), which executes in a separate transaction from `init_transfer`. By the time `sign_transfer` is called, `init_transfer_internal` has already:

1. Stored the transfer message in `pending_transfers` (L1834–1836).
2. Burned or locked the full token amount (L1850–1857).

The only pre-burn validation in `init_transfer` is `fee < amount` (L554–557); there is no check that `normalize_amount(amount - fee, decimals) > 0`. When `sign_transfer` subsequently hits `require!(amount_to_transfer > 0, ...)`, the NEAR runtime reverts that transaction, but the burn/lock from the prior transaction is already final. No public cancel or refund function exists; `remove_transfer_message_without_refund` is only called internally on storage-balance failure and does not restore tokens.

The code comment at L2781–2783 acknowledges "When fee = 0, dust stays locked/burned" but refers to sub-unit remainder dust, not the case where the entire normalized amount is zero — a qualitatively different and unrecoverable scenario.

## Impact Explanation

Any user who sends an amount below the normalization threshold suffers **permanent, irrecoverable loss** of their bridged tokens: they are burned (for deployed bridge tokens) or locked (for native tokens) on NEAR, the transfer can never be finalized on the destination chain, and no on-chain recovery path exists. This is permanent freezing of bridged funds, matching the Critical allowed impact class.

## Likelihood Explanation

The trigger requires no privileges. Any token holder can call `ft_transfer_call` → `init_transfer` with a sub-threshold amount. Common decimal configurations (e.g., `origin_decimals = 24`, `decimals = 18`, divisor = `10^6`) make the threshold non-trivial (999,999 base units). Users unfamiliar with decimal normalization, or those sending small/test amounts, can hit this without any attacker involvement. The condition is repeatable for every such transfer.

## Recommendation

Add a normalization check in `init_transfer` (or at the start of `init_transfer_internal`) **before** `burn_tokens_if_needed` / `lock_tokens_if_needed` is called:

```rust
let token_address = self.get_token_address(
    transfer_message.get_destination_chain(),
    self.get_token_id(&transfer_message.token),
).near_expect(BridgeError::FailedToGetTokenAddress);

let decimals = self.token_decimals
    .get(&token_address)
    .near_expect(BridgeError::TokenDecimalsNotFound);

let normalized = Self::normalize_amount(
    transfer_message.amount_without_fee()
        .near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

This mirrors the guard already present in `sign_transfer` but places it before the irreversible state change.

## Proof of Concept

1. Register a token with `origin_decimals = 24`, `decimals = 18` (divisor = `10^6`).
2. User calls `ft_transfer_call` with `amount = 500_000` (< `10^6`) and `fee = 0`.
3. `init_transfer_internal` is reached: `burn_tokens_if_needed` burns `500_000` units; transfer message is stored in `pending_transfers`.
4. Trusted relayer calls `sign_transfer` for this transfer ID.
5. `normalize_amount(500_000, Decimals { decimals: 18, origin_decimals: 24 })` → `500_000 / 1_000_000 = 0`.
6. `require!(amount_to_transfer > 0, ...)` panics — `sign_transfer` transaction reverts.
7. The burn from step 3 is final; the transfer message remains in `pending_transfers` indefinitely.
8. User's `500_000` units are permanently burned with no recovery path.

A local integration test can confirm this by: (a) deploying the bridge and a mock fungible token with the above decimal configuration, (b) calling `ft_transfer_call` with the sub-threshold amount, (c) asserting the transfer message is stored and tokens are burned, then (d) asserting that `sign_transfer` panics with `InvalidAmountToTransfer` and the transfer message persists after the panic.
