### Title
Peras Certificate Validation Bypass: `validatePerasCert` Stub Unconditionally Accepts Any Peer-Supplied Certificate — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production default instance of `BlockSupportsPeras` implements `validatePerasCert` as a stub that unconditionally returns `Right` for every certificate, regardless of cryptographic content. The inbound certificate processing pipeline (`processCerts`) relies on this function as its sole validation gate before accepting peer-supplied certificates into the `PerasCertDB` and triggering chain selection. An unprivileged peer can therefore inject arbitrary crafted Peras certificates that boost any block, causing honest nodes to prefer a non-canonical chain.

---

### Finding Description

**Root cause — `validatePerasCert` stub:**

In `SupportsPeras.hs`, the default `BlockSupportsPeras` instance (which applies to all block types, including Cardano blocks, because no era-specific override exists) implements certificate validation as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This is not a test helper — it is the live production default instance, gated only by a TODO comment. No cryptographic check, no committee membership check, no signature verification, and no round-number sanity check is performed.

**Inbound processing pipeline — `processCerts`:**

Certificates received from peers are processed by `processCerts` in `PerasCert.hs`:

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _) ->
      throw (PerasCertInboundException errs)
``` [2](#0-1) 

The `validateCert` argument is wired to `validatePerasCert mkPerasParams`, which always returns `Right`. The only deduplication guard is a round-number membership check against `alreadyInDb`. A peer can therefore supply a certificate for any round not yet seen, and it will pass the `partitionEithers` check unconditionally.

**Chain selection consequence — `addPerasCertAsync`:**

Once accepted, the certificate is stored in `PerasCertDB` and `addPerasCertAsync` is called:

```haskell
(void . ChainDB.addPerasCertAsync chainDB)
``` [3](#0-2) 

Inside `chainSelSync`, the certificate's boosted block is looked up in the VolatileDB and, if found, chain selection is triggered for it:

```haskell
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

The `PerasWeightSnapshot` used during chain selection is derived directly from the accepted (unvalidated) certificate's boost value:

```haskell
let weights =
      mkPerasWeightSnapshot
        [ (getPerasCertBoostedBlock cert, getPerasCertBoost cert)
        | cert <- Map.elems (pcdsCertsByTicket pcds)
        ]
``` [5](#0-4) 

**Analogy to the external report:**

The external report describes a state transition (`withdraw`/burn) that permanently invalidates an authorization check (`isApprovedOrOwner`), making rewards permanently inaccessible. Here, the analogous missing enforcement is the absent cryptographic authorization check in `validatePerasCert`: the function that is supposed to gate certificate acceptance unconditionally grants access (`Right`) to every caller, permanently bypassing the intended authorization boundary for every certificate received from any peer.

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` for any round number and any block point, send it via the Peras certificate mini-protocol, and have it accepted without any cryptographic verification. The accepted certificate is assigned the full `perasWeight` boost and stored permanently in `PerasCertDB` until garbage collection. If the boosted block is present in the VolatileDB, chain selection is immediately triggered, and the node may switch to a non-canonical fork that carries the fraudulent boost weight. This constitutes a **bypass of certificate validation enabling unauthorized certificate acceptance and chain selection manipulation** — matching the Critical impact tier.

---

### Likelihood Explanation

The Peras certificate diffusion infrastructure is fully wired into the production `ChainDB` and diffusion layer. Any peer connected to the node can send a crafted certificate via the object-diffusion mini-protocol. No privileged access, leaked keys, or stake majority is required. The only prerequisite is that the target block hash exists in the node's VolatileDB, which is trivially satisfiable by a peer that has already sent the node a valid block.

---

### Recommendation

Replace the stub default implementation of `validatePerasCert` with a real cryptographic check before the Peras certificate diffusion infrastructure is active on any network. At minimum, enforce:

1. Committee membership and seat eligibility for the claimed round.
2. Aggregate BLS signature verification over the round number and boosted block hash (as defined in `Peras.Cert.V1`).
3. Round-number bounds relative to the current chain tip.

Until a real implementation is available, the inbound `processCerts` pipeline should reject all certificates rather than accept them unconditionally, or the Peras certificate mini-protocol server should not be started.

---

### Proof of Concept

```
1. Attacker connects to a target node as a normal peer.
2. Attacker observes a block B in the VolatileDB (e.g., via the block-fetch protocol).
3. Attacker constructs a PerasCert { pcCertRound = R, pcCertBoostedBlock = point(B) }
   for any round R not yet present in the node's PerasCertDB.
4. Attacker sends the certificate via the Peras certificate mini-protocol.
5. processCerts calls validatePerasCert, which returns Right unconditionally.
6. The certificate is stored in PerasCertDB with boost = perasWeight params.
7. addPerasCertAsync triggers chainSelectionForBlock for B.
8. The node's chain selection now treats B as carrying a full Peras boost,
   potentially switching to a fork that would otherwise be rejected.
```

The relevant code path is:

`processCerts` → `validatePerasCert` (always `Right`) → `addCert` → `PerasCertDB.addCert` → `addPerasCertAsync` → `chainSelSync` → `chainSelectionForBlock`. [1](#0-0) [6](#0-5) [7](#0-6)

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

```haskell
-- Process a Peras certificate by adding it to the PerasCertDB and potentially
-- performing chain selection if a candidate is now better than our selection.
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
