### Title
No Refund or Cancel Mechanism for Permanently Failing NEAR → Foreign Chain Transfers — (File: `near/omni-bridge/src/lib.rs`)

### Summary

When a user initiates a NEAR → foreign chain transfer, their tokens are burned or locked on NEAR before any destination-chain confirmation. If the destination chain permanently rejects the transfer, there is no mechanism to refund or cancel the transfer and recover the user's tokens. For zero-fee transfers the situation is irreversible: `sign_transfer_callback` removes the pending transfer record immediately after MPC signing succeeds, making even a retry impossible.

### Finding Description

**Step 1 — Tokens committed on NEAR.**
`init_transfer_internal` burns (for bridge-deployed tokens) or locks the user's tokens and stores a `TransferMessage` in `pending_transfers`. [1](#0-0) 

**Step 2 — Transfer message removed before destination confirmation (zero-fee path).**
`sign_transfer_callback` removes the `TransferMessage` from `pending_transfers` as soon as MPC signing succeeds and `fee.is_zero()` is true. At this point the signed payload is only emitted as an event; no on-chain confirmation from the destination chain has occurred. [2](#0-1) 

After removal, `get_transfer_message` returns `BridgeError::TransferNotExist` for that transfer ID, so `sign_transfer` cannot be called again.

**Step 3 — No cancel or refund function exists.**
There is no public `cancel_transfer` or user-callable refund entry point. The only paths that remove a `TransferMessage` are `sign_transfer_callback` (zero-fee success) and `claim_fee_callback` (relayer fee claim after destination success). [3](#0-2) 

**Non-zero fee path — also unrecoverable.**
When `fee != 0`, the `TransferMessage` stays in `pending_transfers` indefinitely (until `claim_fee` is called), but there is still no cancel/refund path. If the destination chain permanently rejects the transfer, the user's tokens remain burned/locked and their storage balance continues to be consumed. [4](#0-3) 

**Destination-chain failure scenarios (EVM).**
`finTransfer` on EVM marks the nonce as used before executing the token transfer. If the token transfer itself reverts (e.g., recipient contract rejects ERC-20 tokens), the whole EVM transaction reverts and the nonce is not consumed — so the relayer can retry. However, if the failure is permanent (recipient always reverts, EVM bridge permanently paused via `whenNotPaused`, token contract broken), no amount of retrying helps, and for the zero-fee case the NEAR-side record is already gone. [5](#0-4) 

### Impact Explanation

**Critical — permanent freezing of bridged funds.**

For zero-fee transfers: once `sign_transfer_callback` removes the `TransferMessage`, the user's tokens are burned/locked on NEAR with no on-chain path to recover them if the destination chain permanently rejects the transfer.

For non-zero fee transfers: the `TransferMessage` persists but there is no cancel/refund entry point, so tokens remain locked indefinitely.

Both cases fall under the allowed impact: *permanent freezing of bridged funds across NEAR and EVM flows*.

### Likelihood Explanation

**Medium.** Realistic permanent-failure triggers include:

- User specifies a recipient contract address that always reverts on ERC-20 `transfer` or `safeTransferFrom` (user error, but common).
- The EVM `OmniBridge` is permanently paused after a security incident (`whenNotPaused(PAUSED_FIN_TRANSFER)` always reverts).
- The bridged token contract on EVM is paused or broken after deployment.

These conditions are independent of the NEAR side and can arise after the user has already committed their tokens.

### Recommendation

1. **Add a `cancel_transfer` function** callable by the original sender after a configurable timeout (e.g., after N blocks/epochs with no successful `claim_fee`). It should un-burn (re-mint) or unlock the tokens and remove the `TransferMessage`.
2. **For zero-fee transfers**, consider not removing the `TransferMessage` in `sign_transfer_callback` until the destination chain confirms finalization (e.g., via a proof submitted back to NEAR), or keep the record for a grace period to allow cancellation.
3. **Emit a retrievable transfer ID** in `SignTransferEvent` so off-chain tooling can detect stale signed-but-unfinalized transfers and alert users.

### Proof of Concept

1. User calls `ft_transfer_call` on a NEAR NEP-141 token with `msg = InitTransferMsg { recipient: <EVM contract that always reverts on ERC-20 receipt>, fee: 0, ... }`.
2. `init_transfer_internal` burns the tokens and stores the `TransferMessage` in `pending_transfers`. [6](#0-5) 
3. A trusted relayer calls `sign_transfer` with `fee = None` (zero fee). MPC signs successfully.
4. `sign_transfer_callback` executes: `fee.is_zero()` is `true`, so `remove_transfer_message` is called — the `TransferMessage` is deleted from `pending_transfers` and storage refunded to the owner. [4](#0-3) 
5. The relayer submits `finTransfer` on EVM. The recipient contract's `onERC20Received` (or fallback) always reverts. The EVM transaction reverts on every attempt.
6. The user's tokens are permanently burned on NEAR. `get_transfer_message` returns `TransferNotExist`. `sign_transfer` cannot be called again. No `cancel_transfer` exists. Funds are unrecoverable.

    fn init_transfer_internal(
        &mut self,
        transfer_message: TransferMessage,
        storage_owner: AccountId,
    ) -> U128 {
        let required_storage_balance = self
            .add_transfer_message(transfer_message.clone(), storage_owner.clone())
            .saturating_add(NearToken::from_yoctonear(transfer_message.fee.native_fee.0));

        if self
            .try_update_storage_balance(
                storage_owner,
                required_storage_balance,
                NearToken::from_yoctonear(0),
            )
            .is_err()
        {
            self.remove_transfer_message_without_refund(transfer_message.get_transfer_id());
            return transfer_message.amount;
        }

        if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
            self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);

            self.lock_tokens_if_needed(
                transfer_message.get_destination_chain(),
                &token_id,
                transfer_message.amount.0,
            );
        } else {
            self.remove_transfer_message_without_refund(transfer_message.get_transfer_id());
            return transfer_message.amount;
        }

        env::log_str(&OmniBridgeEvent::InitTransferEvent { transfer_message }.to_log_string());
        U128(0)
    }

    fn remove_transfer_message(&mut self, transfer_id: TransferId) -> TransferMessage {
        let storage_usage = env::storage_usage();
        let transfer = self
            .pending_transfers
            .remove(&transfer_id)
            .map(storage::TransferMessageStorage::into_main)
            .near_expect(BridgeError::TransferNotExist);

        let refund =
            env::storage_byte_cost().saturating_mul((storage_usage - env::storage_usage()).into());

        if let Some(mut storage) = self.accounts_balances.get(&transfer.owner) {
            storage.available = storage.available.saturating_add(refund);
            self.accounts_balances.insert(&transfer.owner, &storage);
        }

        transfer.message
    }

    fn remove_transfer_message_without_refund(

    }
