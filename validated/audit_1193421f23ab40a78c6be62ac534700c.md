### Title
Permissionless `request_refund` With Unguarded `refund_address` Enables Attacker to Redirect User BTC Refund to Arbitrary Address - (File: contracts/satoshi-bridge/src/refund.rs)

---

### Summary

`request_refund` is callable by any NEAR account and accepts a caller-supplied `refund_address` that is stored verbatim when `deposit_msg.refund_address` is `None`. Because only one refund request can exist per UTXO key (a second call panics with "Refund request already exists for this UTXO"), an attacker who front-runs the legitimate user's call can permanently redirect the BTC refund to an attacker-controlled Bitcoin address.

---

### Finding Description

**One-time-only state slot — the direct analog to the reported class:**

In `request_refund_callback`, the UTXO key is inserted into `refund_requests` exactly once:

```rust
// Double-check no duplicate (another request_refund could have landed between our check and callback)
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
// ...
self.data_mut()
    .refund_requests
    .insert(utxo_storage_key, refund_request.into());
``` [1](#0-0) 

Once inserted, no second `request_refund` for the same UTXO can succeed — identical to the `init` vs `init_if_needed` pattern in the report.

**No access control on `request_refund`:**

The function is in a `#[trusted_relayer]` impl block but carries no function-level `#[trusted_relayer]` attribute and no caller identity check. The documentation and tests confirm it is callable by any NEAR account:

```rust

**Caller-supplied `refund_address` stored without ownership check:**

`internal_request_refund` only validates that `refund_address` matches `deposit_msg.refund_address` when the latter is `Some`. When it is `None`, any address is accepted:

```rust

### Impact Explanation

When a user deposits BTC using a `DepositMsg` with `refund_address: None` and the relayer fails to finalize the deposit, the user's only recovery path is `request_refund`. An attacker who front-runs that call with their own Bitcoin address as `refund_address` permanently occupies the one-time slot for that UTXO. The legitimate user's subsequent call is rejected. After the timelock, the attacker executes and signs the refund transaction, causing the bridge's MPC service to send the user's BTC to the attacker's address. This is a complete, irreversible theft of user funds — matching the **Critical** impact tier: "Significant loss, theft, destruction, or permanent locking of user or protocol funds."

---

### Likelihood Explanation

All inputs required for the attack are public:
- The `deposit_msg` is emitted on-chain via `Event::LogDepositAddress` at deposit-address derivation time.
- The BTC transaction and its Merkle proof are on the Bitcoin blockchain.
- The attacker only needs to pay the small NEAR storage deposit (`required_balance_for_request_refund`), which is economically trivial relative to any meaningful BTC deposit.

The attack window is the period between the BTC transaction confirming on Bitcoin and the legitimate user submitting `request_refund`. An attacker monitoring both chains can reliably front-run this. The condition `deposit_msg.refund_address == None` is a valid and documented usage mode, so a meaningful fraction of real deposits are vulnerable.

---

### Recommendation

1. **Require `deposit_msg.refund_address` to be `Some`** for any deposit that may later use the refund path, and enforce this in `internal_request_refund` before the async call.
2. **Alternatively**, restrict `request_refund` so that only `deposit_msg.recipient_id` (or a pre-authorized address) can submit the request, by checking `env::predecessor_account_id() == deposit_msg.recipient_id` in `internal_request_refund`.
3. **At minimum**, document clearly that omitting `refund_address` from `deposit_msg` means any party can redirect the refund, and surface a warning in the SDK/UI.

---

### Proof of Concept

1. Alice calls `get_user_deposit_address(DepositMsg { recipient_id: alice, refund_address: None, ... })`. The bridge emits `Event::LogDepositAddress` with the full `deposit_msg` and derived path.
2. Alice sends 1 BTC to the returned address. The transaction confirms on Bitcoin.
3. The relayer goes offline; `verify_deposit` is never called.
4. Attacker observes the `LogDepositAddress` event and the Bitcoin transaction. Attacker calls:
   ```
   request_refund(
       deposit_msg,           // same as Alice's, refund_address: None
       "attacker_btc_addr",   // attacker's Bitcoin address
       tx_bytes,
       vout,
       proof,
       None
   )
   ```
   with the required NEAR storage deposit attached.
5. `request_refund_callback` verifies the proof, finds no existing entry, and inserts `RefundRequest { refund_address: "attacker_btc_addr", ... }`.
6. Alice calls `request_refund` — it panics: **"Refund request already exists for this UTXO"**. [7](#0-6) 
7. After the timelock, attacker calls `execute_refund(utxo_storage_key, None)`. `finalize_refund_with_psbt` builds a PSBT paying `"attacker_btc_addr"` and assigns the `BTCPendingInfo` to the attacker's NEAR account. [8](#0-7) 
8. Attacker calls `sign_btc_transaction`. The MPC service signs the transaction. Attacker broadcasts it to Bitcoin.
9. Alice's 1 BTC arrives at the attacker's address. Alice has no further recourse — the UTXO is now in `verified_deposit_utxo`, blocking any future `verify_deposit` or `request_refund`.

        &mut self,
        caller: AccountId,
        mut refund_request: RefundRequest,
        psbt: PsbtWrapper,
        refund_amount: u128,
        utxo_storage_key: String,
    ) {
        let gas_fee = refund_request.gas_fee;
        let refund_address = refund_request.refund_address.clone();

        let deposit_msg = refund_request.deposit_msg();
        let path = get_deposit_path(&deposit_msg);
        let vutxo = VUTXO::Current(UTXO {
            path,
            tx_bytes: refund_request.tx_bytes.0.clone(),
            vout: refund_request.vout,
            balance: u64::try_from(refund_request.amount)
                .unwrap_or_else(|_| env::panic_str("Amount overflow")),
        });

        let psbt_hex = psbt.serialize();
        let btc_pending_id = psbt.get_pending_id();

        if !self.check_account_exists(&caller) {
            self.internal_set_account(&caller, crate::Account::new(&caller));
        }
        self.require_pending_sign_capacity(&caller);

        let btc_pending_info = BTCPendingInfo {
            account_id: caller.clone(),
            btc_pending_id: btc_pending_id.clone(),
            transfer_amount: 0,
            actual_received_amount: refund_amount,
            withdraw_fee: 0,
            gas_fee,
            burn_amount: 0,
            psbt_hex,
            vutxos: vec![vutxo],
            signatures: vec![None; 1],
            tx_bytes_with_sign: None,
            create_time_sec: nano_to_sec(env::block_timestamp()),
            last_sign_time_sec: 0,
            state: PendingInfoState::Refund(OriginalState {
                stage: PendingInfoStage::PendingSign,
                max_gas_fee: gas_fee,
                last_rbf_time_sec: None,
                cancel_rbf_reserved: None,
            }),
        };

        require!(
            self.data_mut()
                .btc_pending_infos
                .insert(btc_pending_id.clone(), btc_pending_info.into())
                .is_none(),
            "pending info already exist"
        );
        self.internal_unwrap_mut_account(&caller)
            .btc_pending_sign_ids
            .insert(btc_pending_id.clone());

        // Mark UTXO as verified to prevent verify_deposit later
        self.data_mut()
            .verified_deposit_utxo
            .insert(utxo_storage_key.clone());

        Event::RefundExecuted {
            utxo_storage_key: utxo_storage_key.clone(),
            amount: refund_request.amount.into(),
            refund_address,
        }
        .emit();

        Event::GenerateBtcPendingInfo {
            account_id: &caller,
            btc_pending_id: &btc_pending_id,
        }
        .emit();

        // Keep the request (so `execute_refund` can be called again to re-create
        // the transaction) but mark it executed; it is removed only when the
        // refund is finalized in `verify_refund_finalize`.
        refund_request.executed = true;
        self.data_mut()
            .refund_requests
            .insert(utxo_storage_key, refund_request.into());

    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
