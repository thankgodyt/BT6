### Title
Peras Certificate Validation Bypass Allows Unprivileged Peer to Inject Arbitrary Chain-Weight Boosts — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` function unconditionally returns `Right` for every inbound certificate, performing no cryptographic or structural validation whatsoever. Any peer connected via the Peras certificate diffusion miniprotocol can send a crafted `PerasCert` pointing to an arbitrary block, which will be accepted, stored, and used to boost that block's chain-selection weight, potentially causing the honest node to switch to a non-canonical chain.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op:**

The universal `BlockSupportsPeras` instance (the only instance in the codebase) implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No BLS signature check, no committee membership check, no round-number bounds check, and no quorum proof verification is performed. Every certificate, regardless of origin or content, is wrapped in `ValidatedPerasCert` and returned as valid.

**Inbound path — `processCerts` in the diffusion layer:**

`makePerasCertPoolWriterFromChainDB` (the production writer used when Peras cert diffusion is active) wires `validatePerasCert mkPerasParams` directly as the validation callback:

```haskell
(validatePerasCert mkPerasParams)
-- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` then calls this callback on every new certificate received from a peer. Because `validatePerasCert` always returns `Right`, the `([], validatedCerts)` branch is always taken and every cert is forwarded to `ChainDB.addPerasCertAsync`: [3](#0-2) 

**Chain selection side-effect:**

`addPerasCertAsync` enqueues the accepted certificate into the `cdbChainSelQueue`, which is processed by `chainSelSync`. The certificate's `vpcCertBoost` (set to `perasWeight mkPerasParams = 15`) is added to the `PerasWeightSnapshot` for the boosted block, directly influencing `totalWeightOfFragment` comparisons during chain selection. [4](#0-3) 

The `perasWeight` used is the hardcoded default from `mkPerasParams`: [5](#0-4)

### Impact Explanation

**High — Chain selection manipulation via unauthorized certificate injection.**

An unprivileged peer can craft a `PerasCert` with `pcCertBoostedBlock` pointing to any block in the node's VolatileDB. Because `validatePerasCert` never rejects any certificate, the fraudulent cert is accepted and adds a weight boost of 15 to the targeted block. If the attacker targets a block on a minority fork, the boosted fork's total weight can exceed the honest chain's weight, causing the victim node to switch away from the canonical chain. This constitutes a chain-selection safety failure: an honest node is made to prefer a non-canonical chain through a crafted network message, without any stake majority or key compromise.

The `PerasCert` data type contains only `pcCertRound :: PerasRoundNo` and `pcCertBoostedBlock :: Point blk` — both are attacker-controlled fields with no cryptographic binding. [6](#0-5) 

---

### Likelihood Explanation

**High.** The attack requires only a standard peer connection to the Peras certificate diffusion miniprotocol — no privileged keys, no stake, no prior knowledge beyond the target node's VolatileDB contents (which can be inferred from public chain data). The `processCerts` function is the direct inbound handler for peer-supplied certificates and is reachable from any connected peer. The only existing guard is a deduplication check on `pcCertRound` (one cert per round), but an attacker can use a fresh round number for each injection attempt. [7](#0-6) 

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real one that verifies:
1. The BLS aggregate signature over the certificate's `(roundNo, boostedBlock)` payload against the committee's public keys for that round.
2. That the signing committee members were legitimately elected (VRF/WFA eligibility proofs).
3. That the quorum threshold (≥ 3/4 of total stake) is met by the signers.
4. That `pcCertRound` falls within the valid window relative to the current slot.

Until the full cryptographic plumbing is in place (tracked in [issue #120](https://github.com/tweag/cardano-peras/issues/120)), the Peras certificate diffusion miniprotocol should not be enabled on production nodes, or `processCerts` should reject all inbound certificates with an unconditional error rather than silently accepting them.

### Proof of Concept

**Attacker preconditions:** A peer connection to the victim node's Peras cert diffusion endpoint. Knowledge of any block hash present in the victim's VolatileDB (obtainable from public chain data).

**Steps:**

1. Connect to the victim node via the Peras certificate ObjectDiffusion miniprotocol.
2. Craft a `PerasCert` value:
   ```
   PerasCert
     { pcCertRound = <any round not yet in victim's PerasCertDB>
     , pcCertBoostedBlock = <Point of a block on a minority fork>
     }
   ```
3. Send the crafted cert to the victim via `opwAddObjects`.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{vpcCertBoost = PerasWeight 15}` unconditionally.
5. The cert is passed to `ChainDB.addPerasCertAsync`, enqueued in `cdbChainSelQueue`.
6. `chainSelSync` processes the cert: the boosted block's weight increases by 15 in `PerasWeightSnapshot`.
7. If the boosted fork's `totalWeightOfFragment` now exceeds the current chain's weight, the node switches to the minority fork.

**Expected outcome:** The victim node's current chain tip changes to the attacker-chosen fork, diverging from the canonical chain without any cryptographic authorization. [1](#0-0) [8](#0-7) [4](#0-3)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime

    ([], validatedCerts) ->
      mapM_
