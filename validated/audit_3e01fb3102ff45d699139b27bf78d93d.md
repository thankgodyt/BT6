### Title
Peras Certificate Validation Stub Enables Unbounded Weight Accumulation and Chain Selection Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` function in the production `BlockSupportsPeras` instance is an unconditional stub that always returns `Right` (accepts every certificate). Because `addToPerasWeightSnapshot` accumulates weight boosts from multiple certificates for the same block point, an unprivileged peer can send many crafted certificates — each from a distinct round number — all targeting the same block on an adversarial fork. The accumulated weight inflates that fork's `totalWeightOfFragment` beyond the honest chain's, causing `preferAnchoredCandidate` to return `ShouldSwitch` and the node to adopt the adversarial chain.

This is the direct analog of the external report's merge vulnerability: in the report, two positions with different ages are *combined* via a weighted average to produce a manipulated effective age; here, multiple certificates are *accumulated* via `Map.insertWith (<>)` to produce a manipulated effective chain weight, bypassing the intended Peras security assumptions.

---

### Finding Description

**Root cause — stub validation, production code path** [1](#0-0) 

The degenerate `BlockSupportsPeras` instance (the only instance in the repository, explicitly noted as "for all blks to get things to compile") implements `validatePerasCert` as:

```haskell
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
```

No signature, committee membership, round-number range, or boosted-block validity check is performed. Every certificate from every peer unconditionally passes.

This stub is wired into the production certificate ingestion path: [2](#0-1) 

`makePerasCertPoolWriterFromChainDB` calls `processCerts … (validatePerasCert mkPerasParams)` — the same stub — for every batch of inbound certificates received from a peer over the `ObjectDiffusion` mini-protocol.

**Weight accumulation — the "merge" analog**

The `PerasCertDB` deduplicates by round number only: [3](#0-2) 

An attacker can therefore submit N certificates, each carrying a distinct round number, all naming the same block on an adversarial fork as `pcCertBoostedBlock`. Each is stored.

When the weight snapshot is computed, `implGetWeightSnapshot` iterates all stored certificates and calls `mkPerasWeightSnapshot`, which folds via `addToPerasWeightSnapshot`: [4](#0-3) 

`Map.insertWith (<>)` **adds** the boost of each new certificate to any existing boost for the same point. After N certificates, the adversarial block carries weight `N × perasWeight`.

**Chain selection consequence**

`preferAnchoredCandidate` compares the suffixes of the two chains using `weightedSelectView`, whose `wsvTotalWeight` is `blockNo + weightBoost`: [5](#0-4) [6](#0-5) 

Once the adversarial fork's accumulated boost exceeds the honest chain's block-count advantage, `preferCandidate` returns `ShouldSwitch` and `chainSelectionForBlock` switches the node to the adversarial chain.

Additionally, `takeVolatileSuffix` uses `totalWeightOfFragment` to determine the rollback boundary: [7](#0-6) 

Inflated weight on the current chain shortens the volatile suffix, prematurely advancing the immutable tip and preventing future rollback to the honest chain.

---

### Impact Explanation

**High — Chain selection error.** An unprivileged peer can cause an honest node to permanently prefer a non-canonical chain by sending crafted Peras certificates that inflate the weight of an adversarial fork. Once the node switches and the immutable tip advances past the fork point, recovery requires manual intervention. This violates the Ouroboros Peras security assumption that chain weight reflects only legitimately certified blocks.

---

### Likelihood Explanation

**Medium.** The attack requires only network connectivity to a node running the Peras-enabled code path. No stake, keys, or privileged access are needed. The `ObjectDiffusion` mini-protocol is the standard peer-to-peer certificate propagation channel. The only constraint is that Peras must be active; the code is present in the production repository and the stub is the only instance in scope.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
1. The aggregate BLS signature over `(roundNo, boostedBlock)` against the committee's public keys.
2. That the round number falls within the valid range relative to the current slot.
3. That the boosted block's slot is consistent with the round's voting window.
4. That the committee membership proofs (seat indices, VRF outputs) are valid.

Until real validation is in place, the certificate ingestion path should reject all inbound certificates at the network boundary rather than accepting them unconditionally. The TODO at issue `#120` and `#73` should be treated as a security-critical blocker.

### Proof of Concept

```
Attacker (unprivileged peer) → Node running Peras-enabled code

1. Attacker builds an adversarial fork F branching from block B on the honest chain.
   F has tip block number T_F < T_honest (honest chain tip block number).

2. Attacker crafts N certificates:
     cert_i = PerasCert { pcCertRound = i, pcCertBoostedBlock = tip(F) }
   for i = 1 … N, where N × perasWeight > T_honest − T_F.

3. Attacker sends all N certificates via the ObjectDiffusion mini-protocol.

4. processCerts calls validatePerasCert for each cert_i.
   validatePerasCert (stub) returns Right for every cert_i.

5. Each cert_i is stored in PerasCertDB (distinct round numbers pass dedup check).

6. implGetWeightSnapshot folds all N certs via addToPerasWeightSnapshot:
     weightBoost(tip(F)) = N × perasWeight

7. chainSelSync receives cert_N, looks up tip(F) in VolatileDB, calls
   chainSelectionForBlock.

8. constructPreferableCandidates computes weightedSelectView for F's suffix:
     wsvTotalWeight(F suffix) = T_F + N × perasWeight > T_honest

9. preferAnchoredCandidate returns ShouldSwitch.

10. Node switches to adversarial fork F.
    takeVolatileSuffix advances the immutable tip past the fork point.
    The honest chain can no longer be adopted.
```
