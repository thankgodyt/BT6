### Title
`assert`-Only Guard on `Word64` Subtraction in Hard-Fork Era Boundary Computation Silently Underflows in Production Builds — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/HardFork/History/Util.hs`)

---

### Summary

`countEpochs`, `countSlots`, and `countPerasRounds` in `Util.hs` use Haskell's `Control.Exception.assert` as the sole guard against `Word64` underflow before unsigned subtraction. GHC disables `assert` in optimized (production) builds via `-fignore-asserts` (enabled by default with `-O`). If any caller passes arguments violating the `to >= fr` precondition — which the consensus layer itself never independently validates — the subtraction silently wraps around to a near-maximal `Word64`, corrupting the `History.Summary` used for all slot/epoch/time translations across era boundaries.

---

### Finding Description

**Root cause — `Util.hs`:**

```haskell
countEpochs :: HasCallStack => EpochNo -> EpochNo -> Word64
countEpochs (EpochNo to) (EpochNo fr) = assert (to >= fr) $ to - fr
``` [1](#0-0) 

The same pattern applies to `countSlots` and `countPerasRounds`: [2](#0-1) 

In GHC, `Control.Exception.assert` is a no-op when compiled with `-O` (the standard for production Cardano node builds). There is no `error`, `throwIO`, or `guard` fallback — only the `assert`. If `to < fr`, the subtraction `to - fr` on `Word64` silently wraps around to `maxBound - (fr - to) + 1`.

**Propagation path — `Summary.hs`:**

`mkUpperBound` calls `countEpochs hiEpoch (boundEpoch lo)` with no independent validation that `hiEpoch >= boundEpoch lo`:

```haskell
inEraEpochs = countEpochs hiEpoch (boundEpoch lo)
inEraSlots  = inEraEpochs * unEpochSize eraEpochSize
``` [3](#0-2) 

A wrapped-around `inEraEpochs` (~2^64) multiplied by `eraEpochSize` overflows again, producing a garbage `inEraSlots`. This is then used to compute `boundSlot` and `boundTime` for the era boundary:

```haskell
boundSlot = addSlots inEraSlots $ boundSlot lo
boundTime = addRelTime inEraTime $ boundTime lo
``` [4](#0-3) 

**Call sites that feed attacker-influenced data:**

`mkUpperBound` is called from three production paths, all of which pass the epoch returned by `singleEraTransition'` — a function whose output comes from the ledger state:

1. `reconstructSummary` / `reconstructSummaryLedger` (the primary path for building `EpochInfo` from the live ledger state): [5](#0-4) 

2. `whenExtend` during era-transition ticking (called on every block application): [6](#0-5) 

3. `forecastOne` during ledger-view forecasting: [7](#0-6) 

**The contract that `assert` is supposed to enforce:**

The `SingleEraBlock` documentation states that `singleEraTransition` "must not return an epoch `e` which is less than the epoch in which the era started." This is a contract requirement on every implementor, but the consensus layer enforces it only via `assert` — which is disabled in production. [8](#0-7) 

The Shelley `singleEraTransition` has a `TriggerHardForkAtEpoch epoch` branch that returns a statically configured epoch unconditionally, with no check that it is ≥ the era's start epoch: [9](#0-8) 

---

### Impact Explanation

A corrupted `History.Summary` is the authoritative source for all slot↔epoch↔time translations in the hard-fork combinator. Corruption of `boundSlot` or `boundTime` for an era boundary causes:

- **Wrong era classification** for incoming headers/blocks: a block whose slot falls in the corrupted range may be accepted as belonging to the wrong era, bypassing era-specific header validation.
- **Corrupted `EpochInfo`** fed to every consensus and ledger operation that needs slot-to-epoch conversion, including leader-schedule checks, KES period computation, and forecast horizon enforcement.
- **Corrupted forecast end bounds**: `annForecastEnd` in `AnnForecast` uses the corrupted `Bound`, causing the cross-era forecast to either accept ledger views far beyond the safe zone or reject valid ones, breaking cross-era consensus.
- **Permanent divergence**: once a node's `Summary` is corrupted, its chain-selection decisions diverge from honest nodes, potentially causing it to accept an invalid chain or reject the honest chain.

This matches the allowed impact: **Hard-fork, era transition, ledger-view mismatch that breaks cross-era consensus or ledger invariants for production Cardano nodes.**

---

### Likelihood Explanation

**Medium-low.** The Cardano ledger rules validate that transition epochs are in the future, so a single crafted block on mainnet cannot directly trigger this. However, the vulnerability is reachable via:

1. **A bug in any `singleEraTransition` implementation** (including future eras) that returns an epoch before the era start — the consensus layer has no independent check and would silently corrupt the summary in production.
2. **A private testnet or benchmarking configuration** using `TriggerHardForkAtEpoch` with an epoch value less than the era's start epoch (a realistic misconfiguration, since the static value is not validated against the era start at startup).
3. **A crafted or corrupted ledger snapshot** loaded from disk, where the ledger state encodes a past transition epoch — the `assert` is the only guard and is disabled in production.

The `assert` being the sole guard is a direct analog to the Tracer missing `require` check: both rely on an implicit assumption about a numeric input that is never enforced at runtime in production.

---

### Recommendation

Replace `assert` with a proper runtime check that throws an informative error in all build configurations:

```haskell
countEpochs :: HasCallStack => EpochNo -> EpochNo -> Word64
countEpochs (EpochNo to) (EpochNo fr)
  | to >= fr  = to - fr
  | otherwise = error $ "countEpochs: underflow: to=" <> show to <> " < fr=" <> show fr

countSlots :: HasCallStack => SlotNo -> SlotNo -> Word64
countSlots (SlotNo to) (SlotNo fr)
  | to >= fr  = to - fr
  | otherwise = error $ "countSlots: underflow: to=" <> show to <> " < fr=" <> show fr
```

Additionally, add a validation guard in `mkUpperBound` (or in `singleEraTransition'`) that checks `hiEpoch >= boundEpoch lo` before calling `countEpochs`, returning an error or `Nothing` rather than silently computing a corrupted boundary. This mirrors the Tracer recommendation of adding an explicit `require` check before the arithmetic.

---

### Proof of Concept

**Deterministic reasoning (no mainnet required):**

1. Configure a two-era private testnet with `TriggerHardForkAtEpoch (EpochNo 0)` for an era whose `currentStart` has `boundEpoch = EpochNo 5`.
2. On node startup, `reconstructSummaryLedger` calls `mkUpperBound params currentStart (EpochNo 0)`.
3. `countEpochs (EpochNo 0) (EpochNo 5)` executes `0 - 5` on `Word64` in an optimized build.
4. In debug build (`-O0`): `assert` fires, node crashes with `AssertionFailed`.
5. In production build (`-O1`/`-O2`): `assert` is a no-op; result is `18446744073709551611` (~2^64 - 5).
6. `inEraSlots = 18446744073709551611 * epochSize` overflows to a garbage value.
7. `boundSlot lo + inEraSlots` wraps to a garbage slot number.
8. All subsequent slot/epoch/time queries against this `Summary` return wrong results, causing the node to misclassify blocks by era and diverge from honest peers. [1](#0-0) [10](#0-9)
