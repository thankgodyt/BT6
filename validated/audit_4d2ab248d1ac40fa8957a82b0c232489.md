### Title
Zcash `check_withdraw_chain_specific` No-Op Allows User-RBF Without Fee Increase, Exhausting RBF Slots and Causing Temporary Fund Lock — (`contracts/satoshi-bridge/src/zcash_utils/contract_methods.rs`)

---

### Summary

The Zcash build of the bridge omits the fee-increase guard in `check_withdraw_chain_specific`. An unprivileged Zcash user can call the public `withdraw_rbf` entry point and submit repeated RBF transactions whose `gas_fee` equals (or is lower than) the original transaction's fee. This exhausts the `rbf_num_limit` slots with useless RBFs, prevents any legitimate fee bump, and leaves the original Zcash transaction unconfirmed until operator intervention is required.

---

### Finding Description

**Bitcoin** enforces a strict fee-increase invariant in `check_withdraw_chain_specific`: [1](#0-0) 

```rust
pub(crate) fn check_withdraw_chain_specific(
    original_tx_btc_pending_info: &BTCPendingInfo,
    gas_fee: u128,
) {
    let max_gas_fee = original_tx_btc_pending_info.get_max_gas_fee();
    let additional_gas_amount = gas_fee.saturating_sub(max_gas_fee);
    require!(additional_gas_amount > 0, "No gas increase.");
}
```

**Zcash** overrides this with an empty no-op: [2](#0-1) 

```rust
pub(crate) fn check_withdraw_chain_specific(
    _original_tx_btc_pending_info: &BTCPendingInfo,
    _gas_fee: u128,
) {
}
```

The call site in `internal_withdraw_rbf` invokes this guard unconditionally: [3](#0-2) 

Because the Zcash override is a no-op, the guard never fires. The contract then proceeds to call `update_max_gas_fee(gas_fee)` on the original pending info — updating it to the same value — and registers a new RBF pending entry via `set_rbf_pending_info`.

The `rbf_num_limit` cap is enforced in `set_rbf_pending_info`: [4](#0-3) 

Once that limit is reached, no further RBFs (including legitimate fee bumps) can be submitted for that withdrawal.

The public entry point is `withdraw_rbf` in `bridge.rs`, which requires no role: [5](#0-4) 

---

### Impact Explanation

An unprivileged Zcash user can:

1. Submit a withdrawal (original pending info created with `max_gas_fee = gas_fee`).
2. Repeatedly call `withdraw_rbf` with `gas_fee == original gas_fee` (or any value in `[min_btc_gas_fee, max_btc_gas_fee]` that is ≤ original fee).
3. Each call passes the no-op check, creates a new RBF pending entry, and increments the RBF counter.
4. Once `rbf_num_limit` is exhausted, no legitimate fee-bump RBF can be submitted.
5. All pending Zcash transactions carry the same (or lower) fee and will not replace each other in the mempool; they expire at their respective `expiry_height` values.
6. The bridge UTXOs remain locked in a pending state until an operator calls `cancel_withdraw` after `max_btc_tx_pending_sec` elapses.

This matches **Medium** impact: *attacker-triggered temporary locking of bridged funds requiring operator intervention*, and *bypass of bridge fee-increase policy*.

---

### Likelihood Explanation

- The entry point (`withdraw_rbf`) is public and requires no privilege.
- The attacker only needs to own the original withdrawal's `account_id` (enforced at line 43–44 of `rbf/withdraw.rs`), which is trivially satisfied since the attacker initiated the withdrawal.
- The exploit requires only standard NEAR contract calls; no key compromise or external dependency is needed.
- The `rbf_num_limit` is a small integer (typically a single-digit config value), so it is exhausted with very few calls.

---

### Recommendation

Apply the same fee-increase guard in the Zcash `check_withdraw_chain_specific` as exists in the Bitcoin version:

```rust
pub(crate) fn check_withdraw_chain_specific(
    original_tx_btc_pending_info: &BTCPendingInfo,
    gas_fee: u128,
) {
    let max_gas_fee = original_tx_btc_pending_info.get_max_gas_fee();
    let additional_gas_amount = gas_fee.saturating_sub(max_gas_fee);
    require!(additional_gas_amount > 0, "No gas increase.");
}
``` [2](#0-1) 

---

### Proof of Concept

1. Deploy the bridge in Zcash mode.
2. Alice deposits ZEC and initiates a withdrawal; record `original_btc_pending_verify_id` and the original `gas_fee` (e.g., 10 000 sat).
3. Alice calls `withdraw_rbf(original_btc_pending_verify_id, same_outputs, None)` where the new outputs produce `gas_fee == 10 000` (identical to original).
4. Assert: the call succeeds (no "No gas increase." panic).
5. Assert: the original pending info's `max_gas_fee` is still 10 000 (unchanged).
6. Repeat step 3 until `rbf_num_limit` is reached.
7. Assert: a subsequent legitimate `withdraw_rbf` with `gas_fee = 20 000` is rejected with "Exceed rbf_num_limit".
8. Assert: the original Zcash transaction is unconfirmed and the UTXOs remain locked until an operator cancels.
