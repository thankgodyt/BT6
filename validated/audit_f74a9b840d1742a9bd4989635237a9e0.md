### Title
No Cancellation Mechanism for Withdrawals Stuck in `PendingSign` Stage — (File: `contracts/satoshi-bridge/src/api/bridge.rs`, `contracts/satoshi-bridge/src/rbf/cancel_withdraw.rs`)

---

### Summary

When a user initiates a withdrawal via `ft_transfer_call`, their nBTC tokens are immediately and irrevocably transferred to the bridge contract. A `BTCPendingInfo` is created in `PendingSign` stage. If MPC signing never completes (service outage, relayer inactivity, or persistent failure), the withdrawal is permanently stuck: no function exists to cancel a `PendingSign` withdrawal — not for the user, and not even for DAO or Operator. The user's nBTC is permanently locked with no recovery path.

---

### Finding Description

The withdrawal lifecycle begins when `ft_on_transfer` is called on the bridge. The bridge returns `U128(0)`, keeping all transferred nBTC, and creates a `BTCPendingInfo` in `PendingInfoStage::PendingSign`. [1](#0-0) 

The only operator-callable cancellation function is `cancel_withdraw`, which is gated behind `#[access_control_any(roles(Role::DAO, Role::Operator))]`: [2](#0-1) 

However, `cancel_withdraw` internally calls `assert_withdraw_original_pending_verify_tx()`, which **panics unless the state is `WithdrawOriginal` with `PendingVerify` stage**: [3](#0-2) [4](#0-3) 

Similarly, `withdraw_rbf` (the user-callable speed-up) also requires `PendingVerify`: [5](#0-4) 

There is no function in the contract that removes or cancels a `BTCPendingInfo` in `PendingSign` stage. The cleanup helpers `clear_invalid_pending_verify_rbf` and `remove_refund_pending_tx_id` both assert `PendingVerify` or `Refund` state respectively: [6](#0-5) 

The `PendingInfoState` enum confirms the full set of states — none of the cancellation paths handle `WithdrawOriginal(PendingSign)`: [7](#0-6) 

---

### Impact Explanation

A withdrawal stuck in `PendingSign` results in:

1. The user's nBTC permanently held by the bridge contract (never burned, never returned).
2. The bridge UTXOs selected for the withdrawal remain locked in `unavailable_utxos`.
3. No recovery path exists — not for the user, not for DAO, not for Operator.

This matches the allowed impact: **Medium — stuck bridge state requiring operator intervention, where even operator intervention is impossible**, and borders on **Critical — permanent locking of user funds**.

---

### Likelihood Explanation

The MPC Chain Signatures service is an external dependency. Any of the following realistic conditions trigger the stuck state:

- MPC service is temporarily or permanently unavailable.
- Relayers stop calling `sign_btc_transaction` (no relayer incentive enforcement).
- The MPC signing callback fails due to gas exhaustion or a transient error, and no retry succeeds.

Once stuck in `PendingSign`, the user has no recourse. The `pending_sign_count` cap also means the user's account is blocked from initiating new withdrawals: [8](#0-7) 

---

### Recommendation

Introduce a user-callable (or at minimum DAO/Operator-callable) cancellation function that handles `PendingSign` withdrawals:

1. Allow the original withdrawal owner (or DAO/Operator) to cancel a `PendingSign` `BTCPendingInfo` after a configurable timeout (e.g., `max_btc_tx_pending_sec`).
2. On cancellation: remove the `BTCPendingInfo`, restore the locked UTXOs to the available pool, and return the nBTC to the user (via `lost_found` or direct transfer, consistent with the existing `claim_lost_found` pattern). [9](#0-8) 

---

### Proof of Concept

1. User calls `ft_transfer_call` on nBTC contract with a `Withdraw` message → bridge receives nBTC, creates `BTCPendingInfo` in `PendingSign`.
2. MPC service becomes unavailable; `sign_btc_transaction` calls fail or are never made.
3. User attempts `withdraw_rbf` → panics: `"Not withdraw original tx"` (requires `PendingVerify`).
4. DAO/Operator attempts `cancel_withdraw` → panics: `"Not withdraw original tx"` (requires `PendingVerify`).
5. No other function can remove the `PendingSign` `BTCPendingInfo`.
6. User's nBTC remains locked in the bridge indefinitely with no recovery path. [10](#0-9)
