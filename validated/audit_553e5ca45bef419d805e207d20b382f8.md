### Title
Peras Certificate Validation Bypass via Stub `validatePerasCert` Allows Adversarial Chain Selection Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production inbound-certificate handler in `makePerasCertPoolWriterFromChainDB` calls `validatePerasCert mkPerasParams` to validate Peras certificates received from peers. The bound implementation of `validatePerasCert` is a stub that unconditionally returns `Right` — it performs **no** cryptographic or quorum checks. Any certificate sent by an unprivileged peer is accepted, stored in the `PerasCertDB`, and used to trigger chain selection, potentially causing the node to switch to an adversarially-boosted fork.

---

### Finding Description

The `BlockSupportsPeras` type class defines `validatePerasCert` as the gate for accepting inbound Peras certificates. The only concrete instance in the codebase is a deliberately incomplete stub:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub skips every required check:
- No aggregate BLS signature verification
- No quorum threshold check (that `sum(voterStake) >= perasQuorumStakeThreshold`)
- No voter eligibility or committee membership check
- No round-number or boosted-block validity check

The production inbound path `makePerasCertPoolWriterFromChainDB` wires this stub directly as the validator for all peer-supplied certificates:

```haskell
(validatePerasCert mkPerasParams)  -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` then applies this validator to every inbound certificate. Because the validator always returns `Right`, the `([], validatedCerts)` branch is always taken and every certificate is forwarded to `ChainDB.addPerasCertAsync`: [3](#0-2) 

`addPerasCertAsync` enqueues the certificate for chain selection. `chainSelSync` then calls `chainSelectionForBlock` for the block named in the certificate's `pcCertBoostedBlock` field, potentially switching the node to a fork that carries the fraudulent boost: [4](#0-3) 

The analog to the external report is exact: just as `_relayTransfer` forwards individual fees without ever checking `sum(fees) == msg.value`, `processCerts` forwards individual certificates without ever checking that the aggregate quorum condition `sum(voterStake) >= threshold` was satisfied when the certificate was forged.

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock` pointing to any block in the VolatileDB. The certificate passes validation unconditionally, is stored in the `PerasCertDB`, and triggers `chainSelectionForBlock` for the named block. Because Peras certificates add `perasWeight` (currently 15 blocks' worth of weight) to the boosted block's chain, the node may switch to a fork that would otherwise be rejected under pure chain-length comparison. This is a **chain selection error** that lets an unprivileged peer make an honest node prefer a non-canonical, adversarially-chosen chain, directly undermining Ouroboros Praos/Peras safety. [5](#0-4) 

---

### Likelihood Explanation

The attack requires only network access: any peer connected via the object-diffusion mini-protocol can send a `PerasCert` message. No keys, stake, or privileged access are needed. The `processCerts` function is the sole inbound validation gate and it is wired to the always-`Right` stub in both the `PerasCertDB`-only path and the production `ChainDB` path. The issue is present in the current HEAD of the repository and is not gated behind a feature flag. [6](#0-5) 

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:

1. Verifies the aggregate BLS signature over `(electionId, candidate)` using the aggregate verification key derived from the declared voters' public keys.
2. Checks that the total stake of the declared voters satisfies `sum(voterStake) >= perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin` (the same check performed by `stakeAboveThreshold` during local certificate forging).
3. Verifies each voter's committee membership and, for non-persistent voters, their VRF eligibility proof.
4. Validates the round number and boosted block against the current ledger state.

Until the real implementation is in place, the node should refuse to accept any inbound Peras certificate rather than accept all of them unconditionally. The existing `PerasCertInboundException` mechanism is already wired to disconnect the offending peer on validation failure, so the fix is purely in the validator body. [7](#0-6) 

---

### Proof of Concept

On a private testnet with Peras enabled:

1. Connect a malicious peer to an honest node via the object-diffusion mini-protocol.
2. Identify a block `B` on a minority fork in the honest node's VolatileDB (slot and hash known from chain-sync).
3. Send a `PerasCert { pcCertRound = <any round>, pcCertBoostedBlock = point(B) }` to the honest node.
4. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right`.
5. The certificate is stored and `addPerasCertAsync` is called.
6. `chainSelSync` runs `chainSelectionForBlock` for `B`; the fork containing `B` now carries `perasWeight = 15` extra weight.
7. If the fork's length + 15 exceeds the current selection's weight, the honest node switches to the adversarial fork.

No cryptographic material, stake, or operator access is required beyond a peer connection. [8](#0-7)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
