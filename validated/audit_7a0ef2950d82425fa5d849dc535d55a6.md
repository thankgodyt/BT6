### Title
Peras Vote Voter Identity Never Cryptographically Verified — Any Peer Can Impersonate Any Staked Pool - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `BlockSupportsPeras` instance's `validatePerasVote` accepts inbound `PerasVote blk` messages from peers and stamps them as valid solely by checking that the claimed `pvVoteVoterId` exists in the stake distribution. The `PerasVote blk` data type carries no cryptographic signature field, and no signature is ever verified. An unprivileged peer can craft a vote claiming to be any staked pool, have it accepted with that pool's full stake weight, and — by repeating this for enough pools — trigger fraudulent quorum and certificate generation for an attacker-chosen block.

### Finding Description

The production `instance StandardHash blk => BlockSupportsPeras blk` in `SupportsPeras.hs` defines `PerasVote blk` with only three fields:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound  :: PerasRoundNo
  , pvVoteBlock  :: Point blk
  , pvVoteVoterId :: PerasVoterId   -- just a KeyHash StakePool
  }
``` [1](#0-0) 

There is no signature field. The `validatePerasVote` implementation only performs a stake-distribution lookup on the claimed voter ID:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [2](#0-1) 

`lookupPerasVoteStake` is a plain `Map.lookup` on `pvVoteVoterId`: [3](#0-2) 

The inbound path from a peer is `processVotes` → `validatePerasVote` → `addVote`: [4](#0-3) 

Once a vote passes `validatePerasVote` it is wrapped in `ValidatedPerasVote` and fed into `updatePerasRoundVoteStates`, which accumulates stake and forges a certificate when quorum is reached: [5](#0-4) 

The TODO comment in the same file explicitly acknowledges the validation is incomplete: [6](#0-5) 

By contrast, the committee-level implementations (`EveryoneVotes`, `WFALS`) do verify BLS signatures and VRF proofs before accepting a vote: [7](#0-6) 

The production `BlockSupportsPeras` instance skips all of that.

Additionally, `validatePerasCert` in the same instance accepts **every** inbound certificate unconditionally:

```haskell
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [8](#0-7) 

### Impact Explanation

An unprivileged peer can send crafted `PerasVote blk` messages claiming to be any set of staked pools. Because `validatePerasVote` never verifies a signature, each such vote is accepted with the full stake weight of the impersonated pool. Once the attacker accumulates enough impersonated stake to exceed the quorum threshold, `updatePerasRoundVoteStates` forges a `ValidatedPerasCert` for the attacker's chosen block. That certificate is then used by chain selection to boost the attacker's preferred chain, causing honest nodes to prefer a non-canonical or adversarially-chosen chain. This is a **Critical** bypass of Peras vote authorization and certificate generation.

### Likelihood Explanation

The ObjectDiffusion miniprotocol is reachable by any peer that can establish a node-to-node connection. No stake, no keys, and no prior relationship are required. The attacker only needs to know the `KeyHash StakePool` values of pools with sufficient combined stake (all of which are public on-chain data) and the current `PerasRoundNo` and target block `Point`. Constructing a valid-looking `PerasVote blk` CBOR message is straightforward given the serialization instance: [9](#0-8) 

### Recommendation

1. Add a cryptographic signature field to `PerasVote blk` (analogous to `pvSignature` in the V1 concrete type at `Peras/Vote/V1.hs` lines 47–48).
2. Implement `validatePerasVote` to verify that signature against the public key registered for `pvVoteVoterId` in the stake distribution, following the pattern in `implVerifyVote` for `EveryoneVotes` or `WFALS`.
3. Implement `validatePerasCert` to verify the aggregate certificate signature rather than accepting all certificates unconditionally.
4. Track the open issue https://github.com/tweag/cardano-peras/issues/120 which already acknowledges these TODOs.

### Proof of Concept

1. Observe the current `PerasVote blk` wire format: 3-element CBOR list `[roundNo, blockPoint, voterKeyHash]` — no signature.
2. Query the Cardano ledger for the `KeyHash StakePool` values of pools whose combined stake exceeds the quorum threshold.
3. For each such pool, construct a `PerasVote blk` CBOR message with `pvVoteVoterId = <pool key hash>`, `pvVoteRound = <current round>`, `pvVoteBlock = <target block point>`.
4. Send these votes to a node via the ObjectDiffusion miniprotocol.
5. `processVotes` calls `validatePerasVote`, which calls `lookupPerasVoteStake` — each vote passes because the voter ID exists in the stake distribution.
6. `updatePerasRoundVoteStates` accumulates the impersonated stake; once quorum is reached, a `ValidatedPerasCert` is forged for the attacker's chosen block.
7. Chain selection now boosts the attacker's block, causing the node to prefer a non-canonical chain.
