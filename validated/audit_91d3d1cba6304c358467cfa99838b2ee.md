### Title
Debug Code Left in Production Silently Corrupts UTXO `tx_bytes` for Large Transactions - (File: contracts/satoshi-bridge/src/btc_light_client/deposit.rs)

### Summary
The production function `internal_safe_verify_deposit_entry` contains leftover debug/development code that silently replaces a depositor's real transaction bytes with a 300-byte zeroed buffer whenever the submitted `tx_bytes` exceed 10,000 bytes. The corrupted bytes are then persisted into the bridge's UTXO store, violating the invariant that every stored UTXO carries its authentic raw transaction data.

### Finding Description
Inside `internal_safe_verify_deposit_entry`, after the transaction has already been decoded and all deposit checks have passed, the following block executes:

```rust
let tx_bytes = if tx_bytes.len() > 10000 {
    env::log_str("tx_bytes length exceeds 10000, truncating to 300 bytes");
    vec![0u8; 300]
} else {
    tx_bytes
};

let utxo = UTXO {
    path,
    tx_bytes,          // ← zeroed-out bytes stored here
    vout,
    balance: transaction.output()[vout].value.to_sat(),
};
``` [1](#0-0) 

The `env::log_str` call and the replacement with `vec![0u8; 300]` are unmistakable signs of debug/development code that was never removed. The UTXO is then stored in the bridge's persistent `utxos` map with these zeroed bytes, and the `verified_deposit_utxo` set is updated to mark the UTXO as verified, preventing any future re-deposit of the same output. [2](#0-1) 

The `UTXO.tx_bytes` field is carried forward into `BTCPendingInfo.vutxos` when the UTXO is consumed for a withdrawal or refund, and is part of the serialised on-chain state. [3](#0-2) 

### Impact Explanation
Any UTXO deposited via `safe_verify_deposit` whose raw transaction exceeds 10,000 bytes is stored with `tx_bytes = [0u8; 300]`. This is a publicly reachable invariant violation in the production deposit path:

- The bridge's UTXO store permanently holds a UTXO whose `tx_bytes` cannot be decoded as a valid Bitcoin/Zcash transaction.
- Any downstream code path that attempts to deserialise `UTXO.tx_bytes` (e.g., future refund logic, operator tooling, or chain-specific signing paths that require the full previous transaction) will panic or produce incorrect results, potentially causing a stuck bridge state requiring operator intervention.
- The `verified_deposit_utxo` guard prevents the legitimate UTXO from ever being re-submitted, so the corruption is permanent for that UTXO.

The current withdrawal signing path (`generate_vutxos`) reconstructs the `TxOut` from `balance` and `path` rather than from `tx_bytes`, so ordinary withdrawals are not immediately broken. However, the stored invariant is violated and the UTXO is silently corrupted in persistent state. [4](#0-3) 

### Likelihood Explanation
Zcash transactions carrying an Orchard bundle routinely exceed 10,000 bytes (the test hex in the codebase itself is already several kilobytes before truncation in the test file). Any relayer or user submitting such a transaction via `safe_verify_deposit` will silently trigger the corruption. No special privileges are required — the function is publicly callable by any bridge user. [5](#0-4) 

### Recommendation
Remove the debug block entirely:

```rust
// DELETE these lines:
let tx_bytes = if tx_bytes.len() > 10000 {
    env::log_str("tx_bytes length exceeds 10000, truncating to 300 bytes");
    vec![0u8; 300]
} else {
    tx_bytes
};
```

If a maximum transaction size is a desired policy, enforce it with an explicit `require!` that rejects oversized inputs rather than silently corrupting them.

### Proof of Concept
1. Construct (or obtain) a Bitcoin/Zcash transaction whose serialised byte length exceeds 10,000 bytes and whose output at index `vout` pays to the correct bridge deposit address for a given `DepositMsg`.
2. Call `safe_verify_deposit` (the public entry point that routes to `internal_safe_verify_deposit_entry`) with this transaction, a valid Merkle proof, and the required attached deposit.
3. The bridge verifies the proof and mints nBTC correctly.
4. Inspect the stored UTXO via the view API (`get_utxos_paged`): the `tx_bytes` field will be `[0, 0, …, 0]` (300 zero bytes) instead of the real transaction bytes.
5. Any attempt to decode `UTXO.tx_bytes` as a transaction (e.g., in a refund or operator recovery flow) will fail with a deserialisation error, leaving the UTXO permanently stuck in the bridge's UTXO pool with corrupted state. [6](#0-5)

    pub fn generate_vutxos(&mut self, psbt: &mut PsbtWrapper) -> (Vec<String>, Vec<VUTXO>) {
        let (utxo_storage_keys, vutxos) = self.remove_vutxo_by_psbt(psbt);

        let input_utxo = vutxos
            .iter()
            .map(|v| TxOut {

                    .expect("Invalid address"),
            })
            .collect();

        (utxo_storage_keys, vutxos)
    }
