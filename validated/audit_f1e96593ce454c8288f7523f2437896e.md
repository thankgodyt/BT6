### Title
`validatePerasCert` Unconditionally Accepts All Inbound Peras Certificates Without Cryptographic Verification, Enabling Peer-Injected Chain-Selection Weight Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The sole `BlockSupportsPeras` instance in the codebase implements `validatePerasCert` as an unconditional `Right`, performing no cryptographic or structural validation whatsoever. Because the production node-to-node diffusion stack wires inbound Peras certificates directly through this stub validator before storing them in the `PerasCertDB` and triggering chain selection, any unprivileged peer can inject an arbitrary `PerasCert` (with any round number and any boosted-block point) that will be accepted, stored, and used to apply a weight boost of `perasWeight mkPerasParams = 15` to an attacker-chosen block, potentially causing the victim node to switch to a non-canonical chain.

---

### Finding Description

**Root cause — `validatePerasCert` always returns `Right`:**

The universal instance at `SupportsPeras.hs:320` is the only `BlockSupportsPeras` instance in the repository. Its `validatePerasCert` implementation is a degenerate stub:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature check, no committee membership check, no quorum proof, no round-number bounds check — every `PerasCert` is unconditionally promoted to a `ValidatedPerasCert` carrying the full `perasWeight` boost.

**Production wiring — `makePerasCertPoolWriterFromChainDB` uses this stub:**

`processCerts` in the production cert pool writer calls `validatePerasCert mkPerasParams` on every inbound cert batch:

```haskell
opwAddObjects = \certs ->
    processCerts
      systemTime
      (ChainDB.getPerasCertIds chainDB)
      -- TODO replace when actual plumbing is in place
      (validatePerasCert mkPerasParams)
      (void . ChainDB.addPerasCertAsync chainDB)
      certs
``` [2](#0-1) 

`processCerts` only rejects a cert if `validateCert` returns `Left`; since it never does, every cert passes and is forwarded to `ChainDB.addPerasCertAsync`. [3](#0-2) 

**Entry point — `hPerasCertDiffusionClient` in the node-to-node stack:**

The production `Handlers` record wires `makePerasCertPoolWriterFromChainDB` directly into the inbound side of the `PerasCertDiffusion` mini-protocol, reachable by any connected peer:

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      version
      controlMessageSTM
``` [4](#0-3) 

**Chain-selection consequence — `chainSelSync` triggers a fork switch on the injected cert:**

Once the cert reaches `ChainDB.addPerasCertAsync`, `chainSelSync` adds it to the `PerasCertDB` and calls `chainSelectionForBlock` for the attacker-chosen `boostedBlock`, applying the full `PerasWeight 15` boost to that block in the weight snapshot used by chain selection:

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  ...
  certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
  ...
  lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [5](#0-4) 

The `PerasWeightSnapshot` maps boosted block points to their accumulated `PerasWeight`; chain selection uses `totalWeightOfFragment` (length + weight boost) to prefer chains, so a fraudulent boost of 15 can tip the selection in favour of a shorter adversarial fork. [6](#0-5) 

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` with an arbitrary `pcCertRound` (not yet in the DB) and an arbitrary `pcCertBoostedBlock` pointing to a block on an adversarial fork. Because `validatePerasCert` never rejects anything, the cert is stored and chain selection is re-run with a weight boost of 15 applied to the adversarial block. If the adversarial fork is within `k` blocks of the current tip, the victim node may switch to it, diverging from the honest chain. This is a bypass of Peras certificate verification enabling unauthorized certificate acceptance and chain-selection manipulation by any connected peer.

**Impact: High** — chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain beyond the intended security assumptions.

---

### Likelihood Explanation

The `PerasCertDiffusion` protocol is enabled in the production node-to-node protocol bundle and is reachable by any peer that can establish a connection. No keys, stake, or operator access are required. The attacker only needs to send a well-formed CBOR-encoded `PerasCert` with a novel round number and a target block point that exists in the victim's VolatileDB.

**Likelihood: Medium** — the protocol is live, the entry path is direct, and the only precondition is a standard peer connection.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with real cryptographic validation: verify the certificate's aggregate BLS signature against the claimed committee members, check that the signers' combined stake meets the quorum threshold from the actual ledger stake distribution, and verify that the round number and boosted block satisfy the protocol's timing and eligibility rules. Until real validation is in place, the `PerasCertDiffusion` inbound handler should refuse all externally received certificates (e.g., by always returning `Left PerasValidationErr`) rather than accepting them unconditionally.

---

### Proof of Concept

1. Attacker connects to a victim node as a standard node-to-node peer.
2. Attacker identifies a block `B_adv` on an adversarial fork that is in the victim's VolatileDB (obtainable via the BlockFetch protocol) and whose chain is within `k` blocks of the victim's current tip.
3. Attacker sends a single `PerasCert` message over the `PerasCertDiffusion` channel:
   - `pcCertRound = <any round not yet in victim's PerasCertDB>`
   - `pcCertBoostedBlock = blockPoint B_adv`
4. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right (ValidatedPerasCert { vpcCertBoost = PerasWeight 15 })` unconditionally. [7](#0-6) 
5. `ChainDB.addPerasCertAsync` enqueues the cert; `chainSelSync` adds it to `PerasCertDB` and calls `chainSelectionForBlock` for `B_adv`. [8](#0-7) 
6. The adversarial fork now carries a weight of `length(fork) + 15`; if this exceeds the honest chain's weight, the victim switches to the adversarial fork.

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
