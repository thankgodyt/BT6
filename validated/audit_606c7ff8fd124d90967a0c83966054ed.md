### Title
Peras Certificate Validation Bypass via Unconditional `Right` in `validatePerasCert` Stub Triggers Attacker-Controlled Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance implements `validatePerasCert` as a stub that unconditionally returns `Right` (success) for every inbound certificate, performing zero cryptographic or structural checks. This stub is wired directly into the production `makePerasCertPoolWriterFromChainDB` path. Because `addPerasCertAsync` feeds accepted certificates straight into the chain-selection queue, an unprivileged peer can craft a certificate that boosts any block in the VolatileDB and force the local node to re-run chain selection with an attacker-chosen Peras weight boost, potentially causing it to switch to a non-canonical fork.

---

### Finding Description

**Root cause — `validatePerasCert` always returns `Right`** [1](#0-0) 

The comment at line 318 explicitly labels this a "degenerate instance … to get things to compile." The implementation at lines 353–358 wraps the raw, unverified certificate directly into a `ValidatedPerasCert` and returns `Right`, skipping every check that a real implementation would perform (round-number bounds, boosted-block existence, quorum proof, signature over the certificate body, etc.).

**Production wiring — `makePerasCertPoolWriterFromChainDB`** [2](#0-1) 

The production pool writer passes `validatePerasCert mkPerasParams` as the validation callback. Because that callback always returns `Right`, every certificate in every inbound batch passes `processCerts`'s `partitionEithers` check and is forwarded to `ChainDB.addPerasCertAsync`.

**Chain-selection consequence — `chainSelSync` / `chainSelectionForBlock`** [3](#0-2) 

`chainSelSync` processes the queued `ChainSelAddPerasCert` message: it stores the certificate in `PerasCertDB`, then calls `chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment` for the block named in the certificate's `pcCertBoostedBlock` field. This re-runs full chain selection with the Peras weight boost applied to the attacker-chosen block.

**ChainDB API confirms the boost semantics** [4](#0-3) 

The `addPerasCertAsync` docstring states: *"If this leads to a fork to be weightier than our current selection, this will trigger a fork switch."*

---

### Impact Explanation

An unprivileged peer that can speak the Peras object-diffusion miniprotocol can:

1. Craft a `PerasCert` naming any block hash present in the target node's VolatileDB as `pcCertBoostedBlock`.
2. Send it; `validatePerasCert` accepts it unconditionally.
3. The certificate is enqueued and processed by `chainSelSync`, which calls `chainSelectionForBlock` for the attacker-chosen block with the full Peras weight boost.
4. If the boosted fork accumulates more Peras-weighted chain quality than the current selection, the node switches to it.

This is a **chain-selection manipulation** bug: an adversary with no stake and no valid cryptographic material can make an honest node prefer a non-canonical or adversarially-chosen fork, violating the Peras safety guarantee that only legitimately certified blocks receive a boost.

---

### Likelihood Explanation

The Peras object-diffusion miniprotocol and the `makePerasCertPoolWriterFromChainDB` path are present in production source (not test or mock) files. The `ChainDB.addPerasCertAsync` → `chainSelSync` pipeline is fully implemented and connected. The only gate between a peer-supplied certificate and a chain-selection re-run is `validatePerasCert`, which is the stub. Any node that has the Peras certificate diffusion miniprotocol enabled is immediately exploitable by any connected peer.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that, at minimum:

- Verifies the certificate's cryptographic signature against the registered committee key.
- Checks that `pcCertRound` is within the acceptable window relative to the current slot.
- Verifies that `pcCertBoostedBlock` is a known, non-genesis point.
- Confirms the certificate encodes a valid quorum proof.

Until a real implementation is in place, the Peras certificate diffusion miniprotocol should be disabled at the network layer so that no peer-supplied certificate can reach `addPerasCertAsync`.

---

### Proof of Concept

1. Connect to a target node that has the Peras certificate diffusion miniprotocol enabled.
2. Observe (via ChainSync) a block hash `H` on a fork that the node has not yet adopted.
3. Construct a `PerasCert { pcCertRound = <any>, pcCertBoostedBlock = RealPoint <slot> H }`.
4. Send it via the object-diffusion protocol.
5. `processCerts` calls `validatePerasCert mkPerasParams cert` → `Right ValidatedPerasCert{vpcCert=cert, vpcCertBoost=perasWeight mkPerasParams}`.
6. `addPerasCertAsync` enqueues `ChainSelAddPerasCert`.
7. `chainSelSync` stores the cert and calls `chainSelectionForBlock` for block `H` with the Peras boost.
8. If the boosted fork is now heavier than the current selection, the node switches to it — without the attacker having produced any valid VRF proof, KES signature, or quorum.

  (StandardHash blk, IOLike m) =>
  SystemTime m ->
  ChainDB m blk ->
  ObjectPoolWriter PerasRoundNo (PerasCert blk) m
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwObjectId = getPerasCertRound
    , opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          -- We do not want to block the writer thread on waiting for ChainSel
          -- side-effects to complete, so we use the async version of adding
          -- certs to the ChainDB and ignore the returned promise.
          -- The async action is still launched and executed behind the scenes
          -- even though we drop the promise.
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    , opwHasObject = do
        certIds <- ChainDB.getPerasCertIds chainDB
        pure $ \roundNo -> Set.member roundNo certIds
    }

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
