### Title
`safe_mint` silently discards minted nBTC when recipient account is unregistered, while `mint` auto-registers accounts — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

The `safe_mint` function in the nBTC token contract mints tokens to `bridge_id` **before** checking whether the recipient account is registered. If the recipient is unregistered, it returns `U128(0)` early, leaving the freshly minted nBTC permanently stuck in the bridge's own token balance. The standard `mint` path avoids this entirely by auto-registering accounts via `mint_inner`. This is a direct feature-parity gap between the two minting paths, analogous to the reported pattern where one code path silently fails for inputs the other path handles correctly.

---

### Finding Description

**`mint` path — auto-registers, deposits directly to user:** [1](#0-0) 

`mint_inner` checks whether the account exists and registers it if absent, then deposits directly to the user. No tokens ever touch `bridge_id`.

**`safe_mint` path — deposits to `bridge_id` first, then checks registration:** [2](#0-1) 

The sequence is:
1. `self.token.internal_deposit(&self.bridge_id, amount.into())` — tokens are minted into the bridge's own nBTC balance.
2. `if self.token.accounts.get(&account_id).is_none() { return PromiseOrValue::Value(U128(0)); }` — if the recipient is not registered, the function returns `U128(0)` immediately.

The tokens already credited to `bridge_id` are **not rolled back** — the nBTC contract's state is committed. The satoshi-bridge's callback receives `U128(0)`, which the safe-deposit flow is documented to treat as a mint failure: [3](#0-2) 

Even if the satoshi-bridge reverts its own state (does not mark the UTXO as verified), the nBTC tokens already minted to `bridge_id` remain there — cross-contract state is not atomically rolled back in NEAR. If the bridge does **not** revert (treats `U128(0)` as success), the UTXO is marked verified, the user's BTC is locked, and the nBTC is stuck in `bridge_id` — a complete loss.

The `safe_deposit` field that triggers this path is a user-controlled field in `DepositMsg`: [4](#0-3) 

---

### Impact Explanation

**At minimum (bridge reverts its state):** nBTC tokens are minted to `bridge_id` but never reach the user. The tokens are stuck in the bridge's nBTC balance with no automatic recovery path. Operator intervention is required to redistribute them. This matches **Medium — stuck bridge state requiring operator intervention**.

**At worst (bridge treats `U128(0)` as success):** The UTXO is marked as verified, blocking any refund request. The user's BTC is permanently locked in the bridge's UTXO pool, and the corresponding nBTC is stuck in `bridge_id`. This matches **Critical — significant permanent locking of user funds**.

---

### Likelihood Explanation

Any user who:
1. Initiates a BTC deposit with `deposit_msg.safe_deposit = Some(SafeDepositMsg { msg: "..." })`, and
2. Has a NEAR account that has never registered storage in the nBTC token contract

will trigger this path. Account registration in NEP-141 tokens is not automatic and is a common state for new users. The `safe_deposit` path is the documented integration path for Omni Bridge and similar dApps, making this a realistic scenario for real users.

---

### Recommendation

Check account registration **before** minting to `bridge_id`, mirroring the `mint_inner` pattern:

```rust
// In safe_mint, before internal_deposit to bridge_id:
if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0)); // fail early, no tokens minted
}
self.token.internal_deposit(&self.bridge_id, amount.into());
// ... proceed with transfer
```

Or, auto-register the recipient account (as `mint_inner` does) so the transfer always succeeds.

---

### Proof of Concept

1. User creates a BTC deposit to the address derived from `DepositMsg { recipient_id: "alice.near", safe_deposit: Some(SafeDepositMsg { msg: "{...}" }), ... }`.
2. `alice.near` has never called `storage_deposit` on the nBTC contract and is therefore unregistered.
3. Relayer calls `verify_deposit_v2` with this `deposit_msg`. The bridge verifies the BTC inclusion proof and calls `safe_mint("alice.near", amount, Some("{...}"))` on the nBTC contract.
4. Inside `safe_mint`: `self.token.internal_deposit(&self.bridge_id, amount)` executes — `amount` nBTC is now credited to `bridge_id`.
5. `self.token.accounts.get(&"alice.near")` returns `None` → function returns `U128(0)`.
6. The satoshi-bridge callback receives `U128(0)`. Depending on callback logic: either the UTXO is marked verified (Critical: BTC locked, nBTC stuck) or not (Medium: nBTC stuck in bridge_id, operator must intervene).
7. `alice.near` receives zero nBTC. Her BTC is either permanently locked or requires operator action to recover. [5](#0-4)

            "safe_mint: account_id must not be the bridge"

        if self.token.accounts.get(&account_id).is_none() {
