### Title
`validatePerasCert` Unconditionally Accepts Peer-Supplied Peras Certificates with Arbitrary Round Numbers and Boosted Block Points — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The global catch-all `BlockSupportsPeras` instance's `validatePerasCert` function unconditionally returns `Right` for every certificate it receives, accepting any peer-supplied `PerasCert` with an arbitrary `pcCertRound` (`Word64`, range 0–2⁶⁴−1) and an arbitrary `pcCertBoostedBlock` (`Point blk`) without performing any cryptographic, range, or structural check. This is the direct analog of the external report's unchecked `customAttributes`: a caller-controlled field that should be constrained to a valid range is passed through to a state-mutating path without validation. An unprivileged peer can inject certificates that boost arbitrary blocks in Peras-aware chain selection, potentially causing an honest node to prefer a non-canonical chain.

### Finding Description

**Root cause — `validatePerasCert` is a no-op:** [1](#0-0) 

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This is the **global catch-all instance** (`instance StandardHash blk => BlockSupportsPeras blk`) that applies to every block type for which no more specific instance exists, including all current Cardano eras. [2](#0-1) 

The two attacker-controlled fields that are never checked:

| Field | Type | Constraint that should be enforced | Actual check |
|---|---|---|---|
| `pcCertRound` | `PerasRoundNo` (`Word64`) | Must correspond to a round for which a quorum of valid votes exists | None |
| `pcCertBoostedBlock` | `Point blk` | Must refer to a block that exists on the node's validated chain | None |

**Secondary no-op — `implAddCert` also skips validation:** [3](#0-2) 

```haskell
-- TODO: we will need to update this method with non-trivial validation logic
-- see https://github.com/tweag/cardano-peras/issues/120
implAddCert :: ...
```

`implAddCert` only deduplicates by round number; it performs no cryptographic or range check. [4](#0-3) 

**How the accepted certificate reaches chain selection:**

After `validatePerasCert` returns `Right`, the `ValidatedPerasCert` is stored in the `PerasCertDB`. `getWeightSnapshot` then maps every stored certificate's `pcCertBoostedBlock` to its boost weight: [5](#0-4) 

```haskell
implGetWeightSnapshot PerasCertDbEnv{pcdbState} = do
  ...
  let weights =
        mkPerasWeightSnapshot
          [ (getPerasCertBoostedBlock cert, getPerasCertBoost cert)
          | cert <- Map.elems (pcdsCertsByTicket pcds)
          ]
```

A malicious peer can therefore inject a certificate whose `pcCertBoostedBlock` points to a block on a competing fork. The Peras boost (`perasWeight params`) is then applied to that block during chain selection, potentially causing the honest node to prefer the adversary's fork over the canonical chain.

**Arbitrary `pcCertRound` also corrupts Peras voting rules:**

The `shelleyLedgerLatestPerasCertRound` field is updated from `getPerasCertRoundInBlock` without any range check: [6](#0-5) 

Voting rules VR-1A, VR-2A, and VR-2B all compare `currRoundNo` against the latest certificate round: [7](#0-6) 

A certificate with `pcCertRound = maxBound` would make `currRoundNo <= _A + latestCertSeenRoundNo` always true (integer overflow), permanently satisfying VR-1A and suppressing the cooldown path.

**Exploit path (end-to-end):**

1. Unprivileged peer connects via the Peras certificate mini-protocol.
2. Peer sends `PerasCert { pcCertRound = maxBound, pcCertBoostedBlock = blockPoint adversaryBlock }`.
3. Node calls `validatePerasCert` → always `Right`; certificate stored in `PerasCertDB`.
4. `getWeightSnapshot` returns a boost for `adversaryBlock`.
5. Chain selection applies the boost; node may switch to the adversary's fork.
6. `shelleyLedgerLatestPerasCertRound` is updated to `maxBound`, corrupting all future voting-rule evaluations.

### Impact Explanation

**High — Chain selection bug.** An unprivileged peer can make an honest node apply a Peras boost to an arbitrary block on a competing fork, causing the node to prefer a non-canonical or less-secure chain beyond the intended security assumptions. This directly matches the "High" impact category: *"Chain selection, rollback, forecast, genesis, or header-state bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

Additionally, the arbitrary round number permanently corrupts Peras voting-rule state in the ledger, breaking cross-era consensus invariants for any node running the Peras extension.

### Likelihood Explanation

Any peer that can establish a connection and speak the Peras certificate mini-protocol can trigger this. No stake, no keys, and no prior chain knowledge are required. The attack is deterministic and requires a single crafted message.

### Recommendation

1. **Implement real validation in `validatePerasCert`**: verify that the certificate carries a valid aggregate signature from a quorum of the voting committee for the claimed round, that `pcCertRound` is within the current epoch's valid round window, and that `pcCertBoostedBlock` refers to a block that exists on the node's validated chain.
2. **Add a range guard on `pcCertRound`** before updating `shelleyLedgerLatestPerasCertRound`: reject any certificate whose round number is not strictly greater than the current round or is implausibly large (e.g., more than one epoch ahead).
3. **Remove the global catch-all `BlockSupportsPeras` instance** or make it reject all certificates (`Left PerasValidationErr`) until a proper per-era instance is in place, so the compiler forces each era to provide real validation rather than silently inheriting a no-op.

```haskell
-- | VR-1A: the voter has seen the certificate for the previous round, and the
-- certificate was received in the first X slots after the start of the round.
perasVR1A ::
  HasPerasCertRound cert =>
  PerasVotingView cert ->
  Pred PerasVotingRule
perasVR1A
  PerasVotingView
    { perasParams
    , currRoundNo
    , latestCertSeen
    } =
    VR1A := vr1a1 :/\: vr1a2
   where
    -- The latest certificate seen is from the previous round
    vr1a1 =
      case latestCertSeen of
        -- We have seen a certificate ==> check its round number
        NotOrigin cert ->
          currRoundNo :==: getPerasCertRound (lcsCert cert) + 1
        -- We have never seen a certificate ==> check if we are voting in round 0
        Origin ->
          currRoundNo :==: PerasRoundNo 0

    -- The latest certificate seen was received within X slots from the start
    -- of its round
    vr1a2 =
      case latestCertSeen of
        -- We have seen a certificate ==> check its arrival time
        NotOrigin cert ->
          lcsArrivalSlot cert :<=: lcsRoundStartSlot cert + _X
        -- We have never seen a certificate ==> vacuously true
        Origin ->
          Bool True

    _X =
      SlotNo $
        unPerasCertArrivalThreshold $
          perasCertArrivalThreshold perasParams
```
