### Title
Peras Certificate Validation Bypass Allows Unprivileged Peer to Manipulate Chain Selection Weight - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production inbound-certificate pipeline calls `validatePerasCert` to gate acceptance of peer-supplied Peras certificates before they are stored and used to boost chain-selection weight. The only live implementation of `validatePerasCert` — the catch-all `instance StandardHash blk => BlockSupportsPeras blk` — unconditionally returns `Right` without performing any cryptographic or semantic check. An unprivileged peer can therefore inject an arbitrary `PerasCert` (any round number, any boosted block point) that is accepted as valid, stored in the `PerasCertDB`, and used to trigger chain selection for the boosted block, potentially causing the node to switch to an adversarial fork.

---

### Finding Description

**Root cause — missing validation step in the certificate acceptance pipeline**

The `BlockSupportsPeras` type class declares `validatePerasCert` as the required gate before a certificate may be treated as `ValidatedPerasCert`:

```haskell
validatePerasCert ::
  PerasCfg blk ->
  PerasCert blk ->
  Either (PerasValidationErr blk) (ValidatedPerasCert blk)
```

The only concrete instance in the codebase is the degenerate catch-all:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No aggregate BLS signature check, no voter eligibility check, no quorum-stake threshold check, and no round-number validity check are performed. Every certificate, regardless of content, is promoted to `ValidatedPerasCert`.

**Exploit path — peer → `processCerts` → `PerasCertDB` → chain selection**

The production writer for inbound peer certificates, `makePerasCertPoolWriterFromChainDB`, passes this stub directly as the validator:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` then calls `validateCert` on each inbound certificate and, if all pass (which they always do), adds them to the database: [3](#0-2) 

The accepted certificate is forwarded to `ChainDB.addPerasCertAsync`, which enqueues a `ChainSelAddPerasCert` message. `chainSelSync` then:

1. Looks up the boosted block in the `VolatileDB` by the hash embedded in the certificate.
2. If found, calls `chainSelectionForBlock` for that block — with the certificate's weight boost now recorded in the `PerasWeightSnapshot`. [4](#0-3) 

The `WeightedSelectView` comparison then uses `wsvTotalWeight`, which sums `BlockNo` and `wsvWeightBoost`: [5](#0-4) 

A crafted certificate pointing to a block on an adversarial fork can therefore make that fork's total weight exceed the honest chain's weight, causing the node to switch.

**Analog to M-30**

In M-30, `_setApprovalForYieldBox` was called (a partial setup step) but the downstream `pearlmit.transferFromERC1155` required a *different* approval that was never established — a required intermediate authorization step was silently absent. Here, `processCerts` calls `validatePerasCert` (the designated validation step), but the implementation of that step is a stub that skips all actual authorization checks. The structural pattern is identical: the call chain *assumes* a required check has been performed, but the check is absent.

---

### Impact Explanation

**High — chain selection bug enabling adversarial fork preference.**

When Peras is enabled, an unprivileged peer can send a `PerasCert` with:
- `pcCertRound` set to any round number not yet in the `PerasCertDB`.
- `pcCertBoostedBlock` pointing to a block on an adversarial fork that the peer has already diffused to the victim node (so it is present in the `VolatileDB`).

The node accepts the certificate without any cryptographic verification, records the weight boost, and may switch to the adversarial fork. This violates the Peras chain-selection invariant that only certificates backed by a genuine quorum of eligible voters may boost a block's weight.

---

### Likelihood Explanation

Any peer connected to the node via the object-diffusion mini-protocol can send `PerasCert` objects. No privileged access, no key material, and no stake are required. The attacker only needs to:
1. Diffuse a block on an adversarial fork to the victim (standard block diffusion).
2. Send a `PerasCert` naming that block as the boosted block with a fresh round number.

The only gate that would stop this — `validatePerasCert` — is a no-op. The condition is therefore trivially satisfiable whenever Peras is enabled.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real one that:
1. Verifies the aggregate BLS signature over `(electionId, candidate)` using the combined verification keys of the declared voters.
2. Checks each declared voter's eligibility (VRF proof for non-persistent voters, persistent-membership proof for persistent voters) against the current committee.
3. Confirms the total stake of the declared voters meets the quorum threshold.
4. Validates that `pcCertRound` falls within the acceptable window relative to the current chain tip.

Until the full HFC plumbing is in place (tracked in `cardano-peras/issues/73` and `issues/120`), Peras certificate diffusion should be disabled at the network layer rather than gated by a stub validator that unconditionally accepts all inputs.

---

### Proof of Concept

**Preconditions:** Peras is enabled; the attacker controls one peer connection to the victim node; the attacker has diffused a block `B_adv` on an adversarial fork to the victim (so `B_adv` is in the victim's `VolatileDB`).

**Steps:**

1. Attacker constructs a `PerasCert`:
   ```
   PerasCert { pcCertRound = <any fresh round>, pcCertBoostedBlock = point(B_adv) }
   ```
2. Attacker sends the certificate via the object-diffusion mini-protocol.
3. `makePerasCertPoolWriterFromChainDB` → `processCerts` → `validatePerasCert mkPerasParams cert` returns `Right ValidatedPerasCert{vpcCertBoost = perasWeight params}`.
4. Certificate is stored in `PerasCertDB`; `addPerasCertAsync` enqueues `ChainSelAddPerasCert`.
5. `chainSelSync` finds `B_adv` in the `VolatileDB`, calls `chainSelectionForBlock` with the boosted weight.
6. `WeightedSelectView` comparison: `wsvTotalWeight(adversarial fork) = blockNo(B_adv) + perasWeight > wsvTotalWeight(honest chain)` if the boost is large enough.
7. Node switches to the adversarial fork.

**Expected outcome:** The node adopts the adversarial chain, violating consensus safety.
