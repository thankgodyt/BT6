### Title
Missing Vote Signature Verification in `validatePerasVote` Allows Unauthorized Peras Certificate Forging — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasVote` function omits all cryptographic validation of incoming Peras votes — specifically vote signature and eligibility-proof verification. An unprivileged peer can send crafted `PerasVote` messages that impersonate any known committee member, bypass the authorization check, and cause the node to forge a Peras certificate for an attacker-chosen block. This is the direct analog of the missing `_spendAllowance()` check: a function that should verify the caller's authorization to act on behalf of another party simply does not perform that check.

---

### Finding Description

The `validatePerasVote` function in the default `BlockSupportsPeras` instance contains an explicit TODO acknowledging that actual validation is not yet performed:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right
        ValidatedPerasVote
          { vpvVote = vote
          , vpvVoteStake = stake
          }
  | otherwise =
      Left PerasValidationErr
``` [1](#0-0) 

The function accepts a vote as `ValidatedPerasVote` if and only if the claimed voter ID (`pvVoteVoterId`) appears in the stake distribution. It does **not** verify:

1. The BLS vote signature (`pvSignature`) — i.e., that the vote was actually signed by the private key corresponding to the claimed voter's public key.
2. The eligibility proof (`pvEligibilityProof`) — i.e., the VRF proof that a non-persistent committee member is entitled to vote in this election.

This validated vote is then consumed by `processVotes`, the network-facing handler that receives votes from peers via the Peras vote diffusion mini-protocol:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [2](#0-1) 

`processVotes` filters out already-seen votes, calls `validatePerasVote` on the remainder, and — if all pass — adds them to the vote DB via `addVote`: [3](#0-2) 

Once a `ValidatedPerasVote` is in the DB, `implAddVote` feeds it into `updatePerasRoundVoteStates`, which accumulates stake and forges a `ValidatedPerasCert` when quorum is reached: [4](#0-3) 

The `VotingCommittee` class defines `verifyVote` as the correct mechanism for cryptographic vote verification (checking the aggregate BLS signature against the voter's public key): [5](#0-4) 

The `EveryoneVotes` and `WFALS` implementations of `verifyCert` and `verifyVote` do perform full aggregate signature verification: [6](#0-5) [7](#0-6) 

However, `validatePerasVote` — the function actually called on the inbound network path — never invokes any of these checks.

---

### Impact Explanation

**Impact: High — Bypass of Peras vote/certificate verification enabling unauthorized certificate acceptance.**

A forged certificate produced from fake votes boosts an attacker-chosen block in chain selection. The Peras protocol's security guarantee is that a certificate can only be produced when a quorum of legitimately elected committee members have signed the same block. Skipping signature verification nullifies this guarantee: an attacker who knows the current stake distribution (public information) can impersonate any subset of committee members, accumulate enough fake stake-weighted votes to exceed the quorum threshold, and cause the node to forge and store a `ValidatedPerasCert` for an arbitrary block. This certificate is then used by the chain-selection logic to boost that block, potentially causing the node to prefer a non-canonical or adversarially controlled chain.

---

### Likelihood Explanation

**Likelihood: High.**

The attack requires only:
1. Knowledge of the current stake distribution (fully public on-chain data).
2. The ability to connect to a node's Peras vote diffusion endpoint (any unprivileged peer).
3. Sending well-formed `PerasVote` CBOR messages with valid voter IDs but arbitrary (e.g., zeroed) signatures.

No key compromise, stake majority, or operator access is required. The code path from network ingress (`processVotes`) to certificate forging (`implAddVote` → `updatePerasRoundVoteStates`) is direct and exercised on every inbound vote batch.

---

### Recommendation

Replace the stub `validatePerasVote` implementation with a call to the appropriate `VotingCommittee` method (`verifyVote`) that performs full cryptographic verification of the vote signature and eligibility proof before accepting the vote as `ValidatedPerasVote`. The `VotingCommittee` abstraction already provides the correct interface; the network-facing validation path must use it rather than only checking stake-distribution membership.

---

### Proof of Concept

1. Attacker connects to a node's Peras vote diffusion mini-protocol endpoint.
2. Attacker reads the current stake distribution (public chain data) to enumerate all committee member voter IDs and their stake weights.
3. Attacker constructs `PerasVote` messages for each committee member, all targeting the same attacker-chosen block hash, with valid `pvVoteVoterId` fields but zeroed/random `pvSignature` and `pvEligibilityProof` fields.
4. Attacker sends these votes in a batch to the node.
5. `processVotes` calls `validatePerasVote` for each vote; each passes because `lookupPerasVoteStake` finds the voter ID in the distribution.
6. Each vote is added to the `PerasVoteDB` as `ValidatedPerasVote`.
7. `updatePerasRoundVoteStates` accumulates stake; once the quorum threshold is exceeded, `forgePerasCert` is called and a `ValidatedPerasCert` is stored for the attacker's chosen block.
8. The certificate boosts the attacker's block in chain selection, causing the honest node to prefer the attacker's chain. [1](#0-0) [8](#0-7) [9](#0-8)

  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.

implAddVote perasCfg PerasVoteDbEnv{pvdeTracer, pvdeState} vote = do
  let voteId = getPerasVoteId vote
  addPerasVoteRes <- do
    WithFingerprint pvds fp <- readTVar pvdeState
    (res, pvds') <- addOrIgnoreVote pvds voteId
    writeTVar pvdeState (WithFingerprint pvds' (succ fp))
    pure res
  pure $ do
    traceWith pvdeTracer (AddVote voteId vote addPerasVoteRes)
    return addPerasVoteRes
 where
  addOrIgnoreVote pvds voteId
    -- Vote is already in the DB => ignore it
    | Set.member voteId (pvdsVoteIds pvds) = voteAlreadyInDB pvds
    -- New vote => try to add it to the DB
    | otherwise = tryAddVote pvds voteId

  voteAlreadyInDB pvds = pure (PerasVoteAlreadyInDB, pvds)

  tryAddVote pvds voteId = do
    let pvsVoteIds' = Set.insert voteId (pvdsVoteIds pvds)
        pvsLastTicketNo' = succ (pvdsLastTicketNo pvds)
        pvsVotesByTicket' = Map.insert pvsLastTicketNo' vote (pvdsVotesByTicket pvds)

    (addPerasVoteRes, pvsRoundVoteStates') <-
      case updatePerasRoundVoteStates vote perasCfg (pvdsRoundVoteStates pvds) of
        -- Added vote and reached a quorum, forging a new certificate
        Right (VoteGeneratedNewCert cert, pvsRoundVoteStates') ->
          pure (AddedPerasVoteAndGeneratedNewCert cert, pvsRoundVoteStates')
        -- Added vote but did not generate a new certificate, either
        -- because quorum was not reached yet, or because this vote was
        -- cast upon a target that had already won so a certificate was
        -- forged in a previous step.
        Right (VoteDidntGenerateNewCert, pvsRoundVoteStates') ->
          pure (AddedPerasVoteButDidntGenerateNewCert, pvsRoundVoteStates')
        -- Adding the vote led to more than one winner => internal error
        Left (RoundVoteStateLoserAboveQuorum winnerState loserState) ->
          throwSTM $
            MultipleWinnersInRound
              (getPerasVoteRound vote)
              ( ExistingPerasRoundWinner
                  ( getPerasVoteBlock winnerState
                  , ptvsTotalStake winnerState
                  )
              )
              ( BlockedPerasRoundWinner
                  ( getPerasVoteBlock loserState
                  , ptvsTotalStake loserState
                  )
              )
        -- Reached quorum but failed to forge a certificate
        Left (RoundVoteStateForgingCertError forgeErr) ->
          throwSTM $
            ForgingCertError forgeErr
