### Title
Withdrawal Stuck in `PendingSign` State Has No User or Operator Cancellation Path — (File: `contracts/satoshi-bridge/src/rbf/cancel_withdraw.rs`, `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary
When a user initiates a withdrawal via `ft_on_transfer`, their nBTC tokens are immediately and irrevocably transferred to the bridge contract and locked in its balance. The withdrawal enters `PendingSign` state awaiting MPC signing. If MPC signing permanently fails, neither the user nor privileged operators can cancel the withdrawal or recover the locked nBTC, because the only cancellation path (`cancel_withdraw`) is gated behind `PendingVerify` state — a state that is only reachable after successful MPC signing.

### Finding Description

The withdrawal flow proceeds as follows:

1. User calls `nbtc.ft_transfer_call(bridge, amount, WithdrawMsg)` — tokens transferred to bridge.
2. Bridge's `ft_on_transfer` calls `ft_on_transfer_withdraw_chain_specific`, which calls `create_btc_pending_info` and returns `PromiseOrValue::Value(U128(0))` — all tokens are kept by the bridge.
3. `BTCPendingInfo` is created in `PendingSign` state.
4. MPC must sign via `sign_btc_transaction` to advance to `PendingVerify`.
5. Only after `PendingVerify` can `verify_withdraw` burn the nBTC and complete the flow.

The problem chain:

```
✅ User transfers nBTC → tokens locked in bridge balance
✅ BTCPendingInfo created in PendingSign state
❌ MPC signing fails permanently (key version mismatch, MPC upgrade, unavailability)
❌ Withdrawal stays in PendingSign forever
❌ cancel_withdraw() requires PendingVerify → cannot cancel PendingSign withdrawal
❌ withdraw_rbf() requires PendingVerify → cannot RBF a PendingSign withdrawal
❌ No user-callable escape hatch exists
❌ No operator-callable escape hatch exists for PendingSign state
❌ claim_lost_found() only covers the lost_found map, not bridge token balance
❌ nBTC permanently locked in bridge contract
```

The `cancel_withdraw` function in `bridge.rs` is restricted to `Role::DAO` or `Role::Operator`: [1](#0-0) 

And its internal implementation unconditionally asserts `PendingVerify` state before proceeding: [2](#0-1) 

The assertion itself: [3](#0-2) 

This means a withdrawal in `PendingSign` state is completely uncancellable — even by DAO or Operator — because the only cancellation function requires a state that can only be reached after successful MPC signing.

The token lock happens synchronously in the Bitcoin path: [4](#0-3) 

And in the Zcash path, the callback also returns `U128(0)` on success, locking the tokens: [5](#0-4) 

The `claim_lost_found` recovery path does not help here, as it only covers the `lost_found` map, not the bridge's token balance holding the locked nBTC: [6](#0-5) 

### Impact Explanation

If MPC signing permanently fails for a given `BTCPendingInfo`, the user's nBTC is permanently locked in the bridge contract with no recovery path. The bridge's token balance grows with locked nBTC that can never be burned or returned. This constitutes a stuck bridge state where operator intervention is required but no operator function exists to resolve it — matching the Medium impact class of "stuck bridge state requiring operator intervention."

### Likelihood Explanation

MPC signing failure is a realistic scenario in several cases:
- A user submits an incorrect `key_version` parameter to `sign_btc_transaction`, causing the MPC callback to fail repeatedly.
- The MPC contract is upgraded in a breaking way, invalidating pending signing requests.
- The MPC service becomes permanently unavailable for a specific key path.
- A PSBT that passes `check_withdraw_psbt_valid` at submission time becomes unsignable due to a subsequent config change (e.g., change address rotation).

Any user who has initiated a withdrawal is exposed to this risk. The entry path is fully unprivileged: any nBTC holder can call `ft_transfer_call` to initiate a withdrawal.

### Recommendation

Add a time-gated, user-callable (or at minimum operator-callable) cancellation function that works on `PendingSign` state withdrawals. After a configurable timeout (e.g., `max_btc_tx_pending_sec`), the user should be able to call a function that removes the `BTCPendingInfo`, restores the UTXOs to the available pool, and returns the locked nBTC to the user. Alternatively, extend `cancel_withdraw` to also handle `PendingSign` state, not just `PendingVerify`.

### Proof of Concept

1. Alice holds 1 nBTC and calls `nbtc.ft_transfer_call(bridge, 1_nBTC, WithdrawMsg{...})`.
2. Bridge's `ft_on_transfer` succeeds, `create_btc_pending_info` creates a `BTCPendingInfo` in `PendingSign` state. Bridge now holds Alice's 1 nBTC.
3. Alice (or anyone) calls `sign_btc_transaction(btc_pending_sign_id, 0, 999)` with an invalid `key_version=999`. MPC signing fails. The pending info remains in `PendingSign`.
4. Alice tries `withdraw_rbf(btc_pending_sign_id, ...)` → panics: `"Not pending verify stage"`.
5. DAO tries `cancel_withdraw(btc_pending_sign_id, ...)` → panics: `"Not pending verify stage"` (via `assert_withdraw_original_pending_verify_tx`).
6. Alice tries `claim_lost_found()` → panics: `"The account does not have lostfound"`.
7. Alice's 1 nBTC is permanently locked in the bridge contract with no recovery path.

        assert_one_yocto();
        let user_account_id = self
            .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
            .account_id
            .clone();
        self.require_pending_sign_capacity(&user_account_id);

            user_account_id,
            original_btc_pending_verify_id,
            output,
            None,
        );
    }

    pub fn ft_on_transfer_callback(
        &mut self,
        sender_id: AccountId,
        amount: U128,
        target_btc_address: String,
        input: Vec<OutPoint>,
        output: Vec<TxOut>,
        max_gas_fee: Option<U128>,
        chain_specific_data: Option<ChainSpecificData>,
        #[callback_unwrap] last_block_height: u32,
    ) -> U128 {
        let expiry_height = self.get_expiry_height(&chain_specific_data, last_block_height);
        let orchard_bundle = chain_specific_data.map(|c| c.orchard_bundle_bytes.0);

        let psbt = PsbtWrapper::new(
            input,
            output,
            orchard_bundle,
            expiry_height,
            last_block_height,
            Some(target_btc_address.clone()),
            self.internal_config(),
        );

        self.create_btc_pending_info(sender_id, amount.0, target_btc_address, psbt, max_gas_fee);

        U128(0)
    }
