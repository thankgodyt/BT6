### Title
Misplaced Gas Fee Bounds Check Enables Arithmetic Underflow Panic in Withdrawal Path - (File: contracts/satoshi-bridge/src/psbt.rs)

### Summary
In `check_withdraw_psbt`, the gas fee range validation (`min_btc_gas_fee ≤ gas_fee ≤ max_btc_gas_fee`) is placed **after** the arithmetic that subtracts `gas_fee` from `amount - withdraw_fee`. Any unprivileged nBTC holder can craft a PSBT whose `gas_fee` is within the valid range but exceeds `amount - withdraw_fee`, triggering an arithmetic underflow panic before the range check is ever reached. With `overflow-checks = true` (confirmed in `CLAUDE.md`), this is a guaranteed panic.

### Finding Description

In `contracts/satoshi-bridge/src/psbt.rs`, `check_withdraw_psbt` computes:

```rust
let gas_fee = total_input_amount - total_output_amount;   // user-controlled
// ...
let max_received_amount = amount - withdraw_fee - gas_fee;          // line 242 — can underflow
let min_received_amount = max_received_amount - config.min_change_amount; // line 243
require!(
    actual_received_amount >= min_received_amount
        && actual_received_amount <= max_received_amount, ...
);
require!(
    gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee, // line 252-258
    ...
);
``` [1](#0-0) 

The gas fee range check at lines 252–258 is the intended guard, but it executes **after** the subtraction at line 242. A user who sets `gas_fee` to any value within `[min_btc_gas_fee, max_btc_gas_fee]` that is still greater than `amount - withdraw_fee` will cause the subtraction to underflow and panic before the guard fires.

The user controls `gas_fee` indirectly: `ft_on_transfer` accepts a user-supplied `output: Vec<TxOut>` directly in the `Withdraw` message. [2](#0-1) 

For the **BTC variant**, `ft_on_transfer_withdraw_chain_specific` calls `create_btc_pending_info` synchronously and returns `PromiseOrValue::Value(U128(0))`. A panic propagates directly out of `ft_on_transfer`. [3](#0-2) 

For the **Zcash variant**, the panic occurs inside `ft_on_transfer_callback` (a cross-contract callback), causing that promise to fail. [4](#0-3) 

In both cases, NEP-141's `ft_resolve_transfer` sees a failed promise and refunds the tokens to the sender. NEAR's atomic state rollback also restores any UTXOs removed by `generate_vutxos` before the panic. [5](#0-4) 

The root cause is the same as the external report: a value validation check is logically incorrect in placement — it does not guard the arithmetic that depends on the value being within bounds.

### Impact Explanation

The panic causes the withdrawal transaction to fail. Tokens are refunded to the user via NEP-141 and UTXOs are restored by NEAR's state rollback. There is no direct theft or permanent fund loss. However, this is a publicly reachable panic-driven fault in the production bridge withdrawal path, matching the **Low** allowed impact: *publicly reachable panic-driven fault in production bridge/token paths without direct theft*.

### Likelihood Explanation

Any nBTC holder can trigger this. The attack requires:
1. Holding nBTC (obtained via a normal deposit).
2. Calling `nbtc.ft_transfer_call` with a crafted `Withdraw` message where output amounts are set so that `gas_fee` is within `[min_btc_gas_fee, max_btc_gas_fee]` but exceeds `amount - withdraw_fee`.

With the deployed config (`fee_min = 50_000`, `min_withdraw_amount = 70_000`, `max_btc_gas_fee = 50_000`):

- `amount = 70_000`, `withdraw_fee = 50_000`, `amount − withdraw_fee = 20_000`
- Craft PSBT with `gas_fee = 30_000` (within `[10_000, 50_000]`)
- `70_000 − 50_000 − 30_000` → underflow panic [6](#0-5) 

No privileged access is required. Likelihood is **high** given the config values.

### Recommendation

Move the gas fee range check **before** the arithmetic that depends on it:

```rust
let gas_fee = total_input_amount - total_output_amount;
require!(
    gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee,
    format!("Invalid gas fee ({})...", gas_fee)
);
let max_received_amount = amount - withdraw_fee - gas_fee;
let min_received_amount = max_received_amount - config.min_change_amount;
```

Additionally, add a cross-field invariant in `Config::assert_valid()` to ensure `min_withdraw_amount > withdraw_bridge_fee.fee_min + max_btc_gas_fee`, so the configuration itself cannot create conditions where a valid gas fee causes underflow. [7](#0-6) 

### Proof of Concept

1. User deposits 70,000 satoshis of BTC → receives 70,000 nBTC (after zero deposit fee with `fee_rate = 0`, `fee_min = 0`).
2. User calls `nbtc.ft_transfer_call(bridge_id, "70000", msg)` where `msg` is:
   ```json
   {
     "Withdraw": {
       "target_btc_address": "<valid_btc_address>",
       "input": [{"txid": "<utxo_txid>", "vout": 0}],
       "output": [
         {"value": 30000, "script_pubkey": "<target_script>"}
       ],
       "max_gas_fee": null,
       "chain_specific_data": null
     }
   }
   ```
   Here `total_input_amount = 70_000` (the UTXO), `total_output_amount = 30_000`, so `gas_fee = 40_000` (within `[10_000, 50_000]`).
3. `check_withdraw_psbt` reaches line 242: `70_000 − 50_000 − 40_000 = −20_000` → **underflow panic** with `overflow-checks = true`.
4. Transaction fails; tokens are refunded to the user by `ft_resolve_transfer`.

    pub fn ft_on_transfer_callback(
        &mut self,
        sender_id: AccountId,
        amount: U128,
        target_btc_address: String,
        input: Vec<OutPoint>,
        output: Vec<TxOut>,
        max_gas_fee: Option<U128>,
        chain_specific_data: Option<ChainSpecificData>,

        let psbt = PsbtWrapper::new(

            output,

            expiry_height,
            last_block_height,
            Some(target_btc_address.clone()),
            self.internal_config(),
        );

        self.create_btc_pending_info(sender_id, amount.0, target_btc_address, psbt, max_gas_fee);

        U128(0)
    }
