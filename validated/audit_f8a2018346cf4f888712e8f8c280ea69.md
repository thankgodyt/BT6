### Title
Token Migration TOCTOU Race Allows Deposits to Be Stranded on Old nBTC Contract — (`contracts/satoshi-bridge/src/nbtc/migration.rs`)

### Summary

The `migrate_to_new_token_mint` callback in `contracts/satoshi-bridge/src/nbtc/migration.rs` performs a `sum == total_supply` consistency check using stale, asynchronously-fetched data. Because NEAR cross-contract calls execute across separate blocks, any nBTC minted on the old token between the query block and the callback block is invisible to both `total_supply` and `sum`, causing the check to pass with an under-counted supply. The bridge then updates `nbtc_account_id` to the new token, permanently stranding the post-query deposits on the old token.

### Finding Description

`internal_migrate_to_new_token` sends a batch of cross-contract queries (`ft_total_supply` + `ft_balance_of` for each account) to the old token in one NEAR receipt batch, then schedules `migrate_to_new_token_mint` as a callback: [1](#0-0) 

The callback reads the stale promise results and enforces: [2](#0-1) 

Because NEAR processes receipts across blocks, other transactions execute between the query block and the callback block. If a relayer calls `verify_deposit` during this window, the bridge mints nBTC on the **old** token. At callback time:

- `total_supply` (from query) = X (pre-deposit, stale)
- `sum` of balances (from query) = X (pre-deposit, stale)
- `sum == total_supply` → X == X → **passes**

The new token receives only X minted. The old token now holds X + `deposit_amount`. The callback then atomically switches the bridge's authoritative token pointer: [3](#0-2) 

After this point, the bridge's `nbtc_account_id` is the new token. Any nBTC the depositor received on the old token is unreachable through the bridge's withdrawal path, because `ft_on_transfer` (the withdrawal entry point) only accepts calls from the current `nbtc_account_id`. The `ConfigUpdate` path also exposes `nbtc_account_id` as a directly settable field without migration: [4](#0-3) 

There is no pause of deposit processing during migration, and no mechanism to detect or recover stranded balances automatically.

### Impact Explanation

Any user who deposits BTC during the migration window receives nBTC on the old token. After `nbtc_account_id` is updated, those tokens cannot be used to initiate a withdrawal through the bridge. The funds are permanently locked unless the operator manually intervenes (e.g., re-running a second migration or reverting `nbtc_account_id`). This matches the allowed medium impact: **stuck bridge state requiring operator intervention** and **temporary locking of bridged funds**.

### Likelihood Explanation

Token migration is an infrequent but documented operational procedure. The TOCTOU window spans at least one NEAR block (~1 second) between query execution and callback execution. On a live bridge with active depositors, at least one deposit being processed in that window is plausible. No malicious intent is required from either the operator or the depositor; both act in good faith.

### Recommendation

Before initiating migration, pause the `verify_deposit` (minting) path using the existing `Pausable` mechanism. Only unpause after `migrate_to_new_token_resolve` confirms success. Alternatively, re-query `ft_total_supply` inside `migrate_to_new_token_mint` at callback time (not from stale promise results) and compare it against the freshly-read supply to detect any drift before proceeding.

### Proof of Concept

1. `MigrationOperator` calls `migrate_to_new_token(new_token, accounts)`.
2. Bridge sends `ft_total_supply` + `ft_balance_of` queries to old token — all return snapshot value X.
3. In the next NEAR block (before the callback executes), a relayer calls `verify_deposit` for a legitimate BTC deposit. The bridge calls `mint` on the old token, increasing its total supply to X + D.
4. `migrate_to_new_token_mint` callback fires with stale results: `total_supply = X`, `sum = X`. Check passes.
5. New token receives X minted. Bridge sets `nbtc_account_id = new_token`.
6. The depositor holds D nBTC on the old token. The bridge's `ft_on_transfer` rejects any `ft_transfer_call` from the old token (caller ≠ `nbtc_account_id`). The depositor's D satoshis are permanently inaccessible through the bridge. [5](#0-4)

    pub fn migrate_to_new_token_mint(
        &mut self,
        new_token: AccountId,
        accounts: Vec<AccountId>,
    ) -> PromiseOrValue<()> {
        require!(
            env::promise_results_count() == accounts.len() as u64 + 1,
            "Unexpected number of promise results"
        );

        let total_supply = Self::parse_ft_result(0);
        let mut sum: u128 = 0;
        let mut entries: Vec<(AccountId, u128)> = Vec::new();
        for (index, account) in accounts.into_iter().enumerate() {
            let balance = Self::parse_ft_result(index as u64 + 1);
            sum += balance;
            if balance > 0 {
                entries.push((account, balance));
            }
        }
        require!(
            sum == total_supply,
            "Sum of account balances does not match total supply"
        );

        let accounts_count = entries.len();
        let mut mint_batch = Promise::new(new_token.clone());
        for (account, amount) in entries {
            let args = serde_json::to_vec(&json!({
                "mint_account_id": account,
                "mint_amount": U128(amount),
                "protocol_fee": U128(0),
                "relayer_account_id": env::current_account_id(),
                "relayer_fee": U128(0),
                "post_actions": null,
            }))
            .unwrap_or_else(|_| env::panic_str("Failed to serialize mint args"));
            mint_batch = mint_batch.function_call(
                "mint".to_string(),
                args,
                NearToken::from_yoctonear(0),
                GAS_FOR_MINT_ACTION,
            );
        }
        mint_batch
            .then(
                Self::ext(env::current_account_id())
                    .with_static_gas(GAS_FOR_MIGRATION_RESOLVE_CALL_BACK)
                    .migrate_to_new_token_resolve(new_token, accounts_count, U128(total_supply)),
            )
            .into()
    }
