### Title
Permissionless `sign_btc_transaction` with Caller-Controlled `key_version` Allows Griefing Attack That Permanently Blocks Withdrawals — (File: `contracts/satoshi-bridge/src/api/chain_signatures.rs`)

---

### Summary

The `sign_btc_transaction` function is callable by any NEAR account with no ownership check. It accepts a caller-controlled `key_version` parameter that is forwarded directly to the MPC chain-signatures service. An attacker can call this function for any victim's pending withdrawal, supplying a stale or wrong `key_version`. If the MPC service signs with the wrong key, the resulting invalid signature is stored in the slot. The slot is then permanently marked as signed, blocking the legitimate relayer from ever signing that input. The assembled transaction carries an invalid signature and cannot be broadcast on Bitcoin, locking the user's funds in the bridge.

---

### Finding Description

`sign_btc_transaction` in `contracts/satoshi-bridge/src/api/chain_signatures.rs` carries only `#[pause(except(roles(Role::DAO)))]` — no `#[trusted_relayer]`, no ownership assertion, no validation of `key_version`:

```rust
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn sign_btc_transaction(
    &mut self,
    btc_pending_sign_id: String,
    sign_index: usize,
    key_version: u32,          // ← fully attacker-controlled
) -> PromiseOrValue<bool> {
```

The function delegates to `internal_sign_btc_transaction`, which derives the expected public keys from the **current** root key but passes the caller-supplied `key_version` verbatim to the MPC service:

```rust
let public_keys: Vec<_> = pending_info
    .vutxos
    .iter()
    .map(|vutxo| self.generate_btc_public_key(&vutxo.get_path()))  // current root key
    .collect();
// ...
self.sign_promise(SignRequest {
    payload,
    path,
    key_version,   // ← attacker's value, not validated against current key version
})
```

The callback stores whatever the MPC service returns, with no verification that the signature matches the expected public key:

```rust
btc_pending_info.signatures[sign_index] = Some(signature.clone());
```

Once stored, the slot is permanently locked:

```rust
require!(
    btc_pending_info.signatures[sign_index].is_none(),
    "Already signed"
);
```

When all slots are filled, `is_all_signed()` returns `true`, the PSBT is finalized with the wrong signature, and the pending info advances to `PendingVerify`. The assembled Bitcoin transaction is unbroadcastable because the signature does not correspond to the public key committed in the PSBT.

This is a direct analog to the ECO Protocol rebase vulnerability: a permissionless function accepts a caller-controlled parameter (old `key_version` here, old inflation multiplier there) with no validation, and the resulting stale/wrong value is committed to bridge state, corrupting the pending operation.

---

### Impact Explanation

A user initiating a withdrawal transfers nBTC to the bridge via `ft_transfer_call`. The bridge holds those tokens while the BTC transaction is being signed and broadcast. If an attacker fills a signature slot with an invalid signature before the legitimate relayer acts:

- The assembled BTC transaction is invalid and cannot be broadcast.
- The user's nBTC remains locked in the bridge.
- Recovery requires a privileged `cancel_withdraw` call (DAO/Operator only), which creates a cancel-RBF transaction and eventually returns nBTC to the user minus gas fees.

This matches the allowed impact: **attacker-triggered temporary locking of bridged funds requiring operator intervention**.

---

### Likelihood Explanation

- `sign_btc_transaction` is callable by any NEAR account with no restrictions beyond the pause flag.
- Pending sign IDs are deterministic (SHA-256 of PSBT payload preimages) and are emitted in `GenerateBtcPendingInfo` events, so an attacker can observe them on-chain.
- The attacker simply needs to call `sign_btc_transaction(victim_id, 0, 0)` (or any stale `key_version`) before the legitimate relayer does.
- NEAR's MPC chain-signatures service supports `key_version` for key rotation; version 0 (or any previously valid version) is likely accepted, producing a real but wrong-key signature.
- No economic barrier exists; the attack costs only gas.

---

### Recommendation

1. **Add an ownership check**: require `env::predecessor_account_id() == btc_pending_info.account_id` or restrict the function to `#[trusted_relayer]`.
2. **Validate `key_version`**: store the expected `key_version` in `BTCPendingInfo` at creation time (from config) and assert it matches the caller-supplied value before forwarding to the MPC service.
3. **Verify the returned signature** against the expected public key in the callback before storing it, rejecting signatures that do not match.

---

### Proof of Concept

1. Alice calls `ft_transfer_call` on the nBTC contract to initiate a withdrawal. The bridge emits `GenerateBtcPendingInfo { btc_pending_id: "abcd..." }`.
2. Attacker observes the event and immediately calls:
   ```
   sign_btc_transaction("abcd...", 0, 0)
   ```
   with `key_version = 0` (a stale key version).
3. The MPC service signs the payload with key version 0 (a different key than the one committed in the PSBT). The callback stores the signature: `signatures[0] = Some(wrong_sig)`.
4. The legitimate relayer's subsequent call to `sign_btc_transaction("abcd...", 0, current_version)` panics with `"Already signed"`.
5. `is_all_signed()` returns `true`; the PSBT is finalized with the wrong signature and moved to `PendingVerify`.
6. The BTC transaction cannot be broadcast. Alice's nBTC is locked in the bridge until a DAO/Operator calls `cancel_withdraw`. [1](#0-0) [2](#0-1) [3](#0-2)

    pub fn internal_sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> Promise {
        let pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);

        let public_keys: Vec<_> = pending_info
            .vutxos
            .iter()
            .map(|vutxo| self.generate_btc_public_key(&vutxo.get_path()))
            .collect();

        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        require!(
            btc_pending_info.signatures[sign_index].is_none(),
            "Already signed"
        );
        let payload = btc_pending_info
            .get_psbt()
            .get_hash_to_sign(sign_index, &public_keys);
        let path = btc_pending_info.vutxos[sign_index].get_path();
        self.sign_promise(SignRequest {
            payload,
            path,
            key_version,
        })
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_SIGN_BTC_TRANSACTION_CALL_BACK)
                .sign_btc_transaction_callback(
                    btc_pending_info.account_id.clone(),
                    btc_pending_sign_id,
                    sign_index,
                ),
        )
    }

    #[private]
    pub fn sign_btc_transaction_callback(
        &mut self,
        account_id: AccountId,
        btc_pending_sign_id: String,
        sign_index: usize,
    ) -> bool {
        if let Ok(result_bytes) = env::promise_result_checked(0, MAX_SIGNATURE_RESULT) {
            let signature = serde_json::from_slice::<SignatureResponse>(&result_bytes)
                .expect("Invalid signature");

            let public_key = self
                .generate_btc_public_key(
                    &self
                        .internal_unwrap_btc_pending_info(&btc_pending_sign_id)
                        .vutxos[sign_index]
                        .get_path(),
                )
                .inner;
            let btc_pending_info = self.internal_unwrap_mut_btc_pending_info(&btc_pending_sign_id);
            require!(
                btc_pending_info.signatures[sign_index].is_none(),
                "Already signed"
            );
            btc_pending_info.signatures[sign_index] = Some(signature.clone());
