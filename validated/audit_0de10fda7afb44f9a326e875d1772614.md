### Title
Peras Vote and Certificate Signature Verification Bypass via Degenerate `BlockSupportsPeras` Instance - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `BlockSupportsPeras` catch-all instance contains degenerate `validatePerasVote` and `validatePerasCert` implementations that accept any vote or certificate from a known voter ID without verifying any cryptographic signature. An unprivileged peer can craft forged Peras votes for any voter in the public stake distribution, accumulate enough forged votes to reach quorum, and cause an honest node to forge a certificate boosting an attacker-chosen block, directly manipulating Peras-weighted chain selection.

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasVote` and `validatePerasCert` as the methods for validating Peras votes and certificates received from peers. The production codebase contains a catch-all degenerate instance for all `StandardHash blk` types:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/120
instance StandardHash blk => BlockSupportsPeras blk where
``` [1](#0-0) 

The `validatePerasVote` implementation in this instance only checks that the voter ID is present in the stake distribution, but **never verifies the vote's cryptographic signature**. The `_params` argument — which would carry the cryptographic parameters needed for signature verification — is explicitly discarded:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [2](#0-1) 

Similarly, `validatePerasCert` unconditionally returns `Right` for every certificate, performing zero cryptographic checks:

```haskell
validatePerasCert params cert =
  Right ValidatedPerasCert
    { vpcCert = cert
    , vpcCertBoost = perasWeight params
    }
``` [3](#0-2) 

The inbound vote processing pipeline `processVotes` calls this `validateVote` on every vote received from a peer: [4](#0-3) 

The inbound certificate processing pipeline `processCerts` similarly calls `validatePerasCert mkPerasParams` on every certificate received from a peer, with a comment explicitly acknowledging this is a placeholder: [5](#0-4) 

The analog to the external report's vulnerability is direct: just as the Nexus hook bypass occurs because `_installModule` is called directly (bypassing the `withHook` modifier's security context), here the degenerate `validatePerasVote`/`validatePerasCert` implementations are called through the normal diffusion pipeline but skip the cryptographic checks that the "proper" implementation would perform — the `_params` argument is the equivalent of the discarded security context.

Since the stake distribution is public information, an attacker can enumerate all valid `PerasVoterId` values and craft forged votes for any of them without possessing their private keys. These forged votes pass `validatePerasVote` and are added to the `PerasVoteDB`. When enough forged votes accumulate to reach quorum, the node internally calls `forgeCert`, producing a `ValidatedPerasCert` boosting the attacker's chosen block, which then influences chain selection. [6](#0-5) 

### Impact Explanation

**High.** An unprivileged peer bypasses Peras vote and certificate signature verification entirely. By forging votes for legitimate voter IDs (which are public), an attacker accumulates quorum and causes an honest node to forge a certificate boosting an arbitrary block. This directly manipulates Peras-weighted chain selection — the `vpcCertBoost` field is set to the full `perasWeight` for every accepted certificate — allowing the attacker to make an honest node prefer a non-canonical or attacker-chosen chain beyond the intended security assumptions of the Peras protocol. [7](#0-6) 

### Likelihood Explanation

**Low.** The Peras protocol is under active development and the degenerate instance is explicitly marked as a TODO placeholder. However, the diffusion protocol handlers are wired into the production codebase and the vulnerability is reachable on any network where Peras is activated. The attack requires only knowledge of the public stake distribution and the ability to connect as a peer.

### Recommendation

Replace the degenerate `validatePerasVote` and `validatePerasCert` implementations with proper cryptographic signature verification before enabling Peras on any network. The `_params` argument to `validatePerasVote` must be used to obtain the cryptographic parameters needed to verify the vote signature against the voter's public key from the stake distribution. The `validatePerasCert` implementation must verify the aggregate BLS signature over the certificate's voter set before returning `Right`.

### Proof of Concept

1. Observe the public stake distribution to enumerate valid `PerasVoterId` values (public key hashes).
2. Craft `PerasVote` values with valid `pvVoteVoterId` fields, all targeting an attacker-chosen block at a chosen round.
3. Send these votes to a target node via the Peras vote diffusion mini-protocol.
4. `processVotes` calls `validatePerasVote` on each vote; the degenerate instance accepts every vote whose voter ID appears in the stake distribution, with no signature check.
5. Repeat with distinct voter IDs until the accumulated `vpvVoteStake` exceeds the quorum threshold defined in `PerasCfg`.
6. The node's `PerasVoteDB.implAddVote` calls `updatePerasRoundVoteStates`, which triggers `forgeCert` upon quorum, producing a `ValidatedPerasCert` with full `perasWeight` boost for the attacker's chosen block.
7. Chain selection now weights the attacker's chosen block higher via the Peras boost, potentially causing the node to switch to a non-canonical chain. [8](#0-7) [2](#0-1)
