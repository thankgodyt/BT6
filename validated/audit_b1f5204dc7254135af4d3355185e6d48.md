### Title
Peras Certificate Validation Unconditionally Bypassed in Degenerate `BlockSupportsPeras` Instance — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance unconditionally accepts every inbound Peras certificate without performing any cryptographic or semantic validation. Because the certificate diffusion pipeline is fully wired up, an unprivileged peer can inject crafted certificates that boost arbitrary volatile blocks, causing the node to trigger chain selection for those blocks and potentially switch to a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` type class declares `validatePerasCert` as the gate that must be passed before a certificate is stored and acted upon. The only production instance of this class — a blanket `instance StandardHash blk => BlockSupportsPeras blk` — is explicitly labelled a "degenerate instance … to get things to compile" and implements `validatePerasCert` as an unconditional `Right`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature check, no committee-membership check, no round-number sanity check, and no boosted-block existence check is performed. Every certificate that arrives from a peer is stamped `ValidatedPerasCert` and assigned the full `perasWeight` boost.

The inbound processing path in `processCerts` partitions certificates into valid/invalid using exactly this function:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [2](#0-1) 

Because `validateCert` always returns `Right`, the `(errs, _)` branch is unreachable; every certificate is unconditionally added to the pool.

Once added, `chainSelSync` processes the certificate: it looks up the boosted block in the VolatileDB and, if found, calls `chainSelectionForBlock` for it:

```haskell
-- Trigger chain selection for the boosted block.
lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [3](#0-2) 

Chain selection then computes weighted select-views that include the Peras boost, potentially preferring the boosted fork over the current selection. [4](#0-3) 

The `getPerasCertInBlock` method is also a no-op stub (`_ = Nothing`), meaning certificates embedded in blocks are never extracted, compounding the inconsistency. [5](#0-4) 

---

### Impact Explanation

This is a **Critical** bypass of Peras certificate validation. An unprivileged peer can:

1. Craft a `PerasCert` pointing to any block hash in the node's VolatileDB.
2. Send it over the object-diffusion mini-protocol.
3. The node accepts it without any cryptographic check and assigns it the full `perasWeight` boost.
4. Chain selection is triggered for the boosted block; if the boosted fork's weighted length now exceeds the current selection, the node switches chains.

This enables an adversary to make an honest node prefer a non-canonical or adversarially-constructed chain, violating the chain-selection safety property of Ouroboros Peras. It also constitutes a complete bypass of the Peras certificate-verification requirement, which is the primary authorization gate for certificate-induced weight boosts.

---

### Likelihood Explanation

The Peras object-diffusion pipeline is fully wired into the running node (`addPerasCertAsync`, `getPerasCertsAfter`, `getPerasCertIds` are all live in the `ChainDB` API). [6](#0-5) 

Any peer that speaks the Peras certificate diffusion sub-protocol can trigger this path with zero privileges. The degenerate instance is in a production source file (not in a test or unstable library), and the TODO comment references an open issue rather than a completed fix. [7](#0-6) 

---

### Recommendation

Replace the degenerate `validatePerasCert` stub with a real implementation that performs, at minimum:

- **Aggregate BLS signature verification** over the certificate message (round number + boosted block hash).
- **Committee membership and seat-index checks** against the current epoch's committee selection data.
- **Round-number range validation** (certificate must not be for a round that is already immutable or in the future beyond the forecast horizon).
- **Boosted-block existence and era-compatibility checks**.

Until real validation is in place, the certificate diffusion endpoint should either be disabled or gated behind a feature flag so that the unauthenticated path is not reachable from untrusted peers.

---

### Proof of Concept

1. Connect to a node with a known VolatileDB block hash `H` on a minority fork.
2. Construct a `PerasCert { pcCertRound = r, pcCertBoostedBlock = H }` with arbitrary (even zeroed) signature bytes.
3. Send the certificate via the Peras certificate object-diffusion mini-protocol.
4. `processCerts` calls `validatePerasCert`, which returns `Right` unconditionally.
5. The certificate is stored; `chainSelSync` retrieves the header for `H` from the VolatileDB and calls `chainSelectionForBlock`.
6. Chain selection computes the weighted select-view including the Peras boost for `H`'s chain; if that chain's boosted weight exceeds the current selection, the node switches to the minority fork.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
