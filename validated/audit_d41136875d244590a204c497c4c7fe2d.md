### Title
`validatePerasCert` Stub Unconditionally Accepts All Inbound Peras Certificates Without Validation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The sole production implementation of `validatePerasCert` in the `BlockSupportsPeras` class unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or semantic checks. The certificate diffusion pipeline (`processCerts` / `makePerasCertPoolWriterFromChainDB`) relies entirely on this function to gate which peer-supplied certificates enter the `PerasCertDB`. Because the gate is always open, any unprivileged peer can inject arbitrary Peras certificates that are stored and used to boost blocks during chain selection, bypassing all Peras soundness guarantees.

---

### Finding Description

**Root cause — the stub validator** [1](#0-0) 

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This is the **only** instance of `BlockSupportsPeras` in the codebase. It is declared as a catch-all for every `StandardHash blk`: [2](#0-1) 

No more-specific instance exists for Cardano blocks (confirmed by `grep` — `validatePerasCert` appears only in `SupportsPeras.hs` and `PerasCert.hs`). The `PerasValidationErr` data type is also a stub with a single constructor and no fields, so it cannot carry any meaningful error information even if validation were attempted.

**Production call path**

`processCerts` is the inbound handler for peer-supplied certificates: [3](#0-2) 

It is wired into the production `ChainDB`-backed pool writer: [4](#0-3) 

The `validateCert` argument passed to `processCerts` is `validatePerasCert mkPerasParams`, which always returns `Right`. The `partitionEithers` call therefore always produces an empty error list, so every certificate from every peer is unconditionally accepted and stored.

**Analog to the external report**

The external report describes `FieldWordRangeChecker` assuming its operand is a valid word while nothing in `eval_ecall` constrains it — other code paths have implicit constraints (via ALU lookup) but this one does not. Here, `processCerts` assumes `validatePerasCert` will reject invalid certificates, but the only implementation of `validatePerasCert` never rejects anything. Every other code path that produces a `ValidatedPerasCert` (e.g., `forgePerasCert` called locally) implicitly constrains the certificate through the vote-collection and quorum logic; the inbound peer path has no such implicit constraint.

---

### Impact Explanation

Peras certificates boost blocks during chain selection. A `ValidatedPerasCert` carries a `vpcCertBoost` weight that is added to the boosted block's chain weight: [5](#0-4) 

Because `validatePerasCert` stamps every inbound certificate with `perasWeight params` regardless of its content, a malicious peer can:

1. Craft a `PerasCert` naming any `PerasRoundNo` and any `Point blk` (block hash) it chooses.
2. Send it via the object-diffusion mini-protocol.
3. The certificate passes `processCerts` without error and is stored in `PerasCertDB`.
4. Chain selection reads the weight snapshot from `PerasCertDB` and applies the boost to the attacker-chosen block.

This allows an unprivileged peer to arbitrarily boost a block on a weaker or adversarial chain, potentially causing an honest node to prefer a non-canonical chain over the canonical one. This is a **bypass of Peras certificate validation** and a **chain-selection manipulation** reachable from any peer connection.

**Severity**: Critical — it directly bypasses the Peras certificate check that is the core soundness mechanism of the Peras protocol extension, matching the "bypass of Peras voting or certificate checks" criterion in the allowed impact scope.

---

### Likelihood Explanation

- No privilege is required. Any node that can establish a peer connection and speak the object-diffusion mini-protocol can send crafted certificates.
- The attack requires only constructing a `PerasCert` value with an attacker-chosen `pcCertRound` and `pcCertBoostedBlock` — both are plain integers/hashes with no cryptographic material required.
- The deduplication check (`Set.member roundNo alreadyInDb`) only prevents re-insertion of a certificate for a round already seen; it does not prevent injection of a certificate for any new round number.
- There is no fallback validation anywhere in the pipeline.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
1. The certificate's aggregate BLS signature over `(pcRoundNo, pcBoostedBlock)` against the expected committee's aggregate verification key.
2. That the claimed voters form a quorum (sufficient stake weight).
3. VRF outputs for non-persistent voters (analogous to `implVerifyCert` in `WFALS.hs`).

Until a real implementation is available, the inbound certificate pipeline (`makePerasCertPoolWriterFromChainDB`) should reject all peer-supplied certificates rather than accept them unconditionally, to avoid the chain-selection manipulation described above.

### Proof of Concept

**Attacker-controlled entry path:**

```
Peer  →  ObjectDiffusion mini-protocol  →  makePerasCertPoolWriterFromChainDB
      →  processCerts  →  validatePerasCert mkPerasParams cert
      →  Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })
      →  addCert (stored in PerasCertDB)
      →  getWeightSnapshot returns boost for attacker-chosen block
      →  chain selection applies boost → non-canonical chain preferred
```

Concretely, an attacker constructs:

```haskell
craftedCert :: PerasCert blk
craftedCert = PerasCert
  { pcCertRound      = someRoundNo          -- any round not yet in DB
  , pcCertBoostedBlock = pointOfWeakerChain  -- hash of block on adversarial fork
  }
```

Sending this certificate causes `validatePerasCert` to return `Right` unconditionally, the certificate is stored, and the adversarial block receives `perasWeight params` extra weight in chain selection. [6](#0-5) [1](#0-0)

```haskell
  (StandardHash blk, IOLike m) =>
  SystemTime m ->
  ChainDB m blk ->
  ObjectPoolWriter PerasRoundNo (PerasCert blk) m
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwObjectId = getPerasCertRound
    , opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          -- We do not want to block the writer thread on waiting for ChainSel
          -- side-effects to complete, so we use the async version of adding
          -- certs to the ChainDB and ignore the returned promise.

          -- even though we drop the promise.

          certs

        certIds <- ChainDB.getPerasCertIds chainDB
```

```haskell
processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
```
