### Title
Peras Weight Boost Not Accounted for in ChainSync `checkPreferTheirsOverOurs`, Causing Premature Peer Disconnection and Non-Canonical Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

The `checkPreferTheirsOverOurs` function in the ChainSync client evaluates whether a candidate chain (beyond the forecast horizon) is preferable to the node's current selection using `emptyPerasWeightSnapshot` — ignoring all Peras weight boosts. However, the actual chain selection in `ChainDB` uses the real `PerasWeightSnapshot` (including Peras boosts). This mismatch causes a node to prematurely disconnect from peers offering a genuinely heavier (Peras-boosted) chain that appears equal or lighter when boosts are ignored, causing the node to remain on a non-canonical, lighter chain.

---

### Finding Description

When the ChainSync client receives a header beyond the forecast horizon, it calls `checkPreferTheirsOverOurs` to decide whether to keep or drop the peer connection. This function calls `preferAnchoredCandidate` with a hardcoded `emptyPerasWeightSnapshot`:

```haskell
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← Peras boosts ignored here
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
``` [1](#0-0) 

By contrast, the actual chain selection in `ChainDB` reads the real `PerasWeightSnapshot` from the `PerasCertDB` and passes it to `preferAnchoredCandidate`:

```haskell
chainSelectionForBlock cdb@CDB{..} blockCache hdr punish = electric $ do
  (invalid, curChain, weights) <-
    atomically $
      (,,)
        <$> (forgetFingerprint <$> readTVar cdbInvalid)
        <*> Query.getCurrentChain cdb
        <*> (forgetFingerprint <$> Query.getPerasWeightSnapshot cdb)  -- ← real weights
``` [2](#0-1) 

The same real-weight path is used in `NodeKernel` for the GSM's `getCandidateOverSelection`:

```haskell
GSM.getCandidateOverSelection = do
    weights <- ChainDB.getPerasWeightSnapshot chainDB
    pure $ \(headers, _lst) state ->
      ...
        preferAnchoredCandidate (configBlock cfg) (forgetFingerprint weights) headers (csCandidate state)
``` [3](#0-2) 

The `preferAnchoredCandidate` function, when given a non-empty `PerasWeightSnapshot`, computes the weighted total (block count + Peras boost) of each chain's suffix after the intersection and compares them:

```haskell
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights = ...  -- length-only comparison
  | otherwise =
      case AF.intersect ours cand of
        Just (_,_,oursSuffix, candSuffix) ->
          case preferCandidate ... (weightedSelectView cfg weights oursSuffix)
                                   (weightedSelectView cfg weights candSuffix) of ...
``` [4](#0-3) 

The `wsvTotalWeight` used in comparison is `blockNo + weightBoost`:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [5](#0-4) 

The mismatch is structurally identical to the reported DeFi bug: a "quote" path (`checkPreferTheirsOverOurs` with empty weights) omits a factor (Peras boosts) that the "execution" path (real chain selection) does include, causing the pre-check to reach a different conclusion than the actual operation.

---

### Impact Explanation

When Peras is active and a peer's candidate chain contains Peras-boosted blocks that make it heavier than the node's current selection, but the raw block count alone does not exceed the node's selection, `checkPreferTheirsOverOurs` returns `ShouldNotSwitch` and throws `CandidateTooSparse`, disconnecting from the peer. The node then never downloads the blocks needed to perform real chain selection, and remains on the lighter (non-canonical) chain. This is a **High** chain-selection bug: an honest node is made to prefer a non-canonical, less-secure chain beyond the intended security assumptions of Peras.

---

### Likelihood Explanation

This is triggered whenever Peras is enabled and a peer's candidate chain has Peras-boosted blocks that push it beyond the forecast horizon. The condition is realistic in any Peras-active network epoch where certificates have been issued. The code path is exercised by every ChainSync client that encounters a header beyond the forecast horizon, which is a normal occurrence during syncing. The TODO comment in the code (`-- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64`) confirms the developers are aware this is broken but have not yet fixed it.

---

### Recommendation

Replace the hardcoded `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the real `PerasWeightSnapshot` read from the `ChainDB`, consistent with how `getCandidateOverSelection` in `NodeKernel` and `chainSelectionForBlock` in `ChainSel` already operate. Alternatively, as the TODO suggests, remove the `checkPreferTheirsOverOurs` check entirely (issue #64), since it is a Genesis-specific density check that should not apply when Peras is active.

---

### Proof of Concept

Consider a Peras-active network with security parameter `k = 2160` and a Peras boost weight of `B`:

1. Our node's current chain has tip at block number `N` with no Peras boosts. Our selection's suffix weight = `N` (length only).
2. A peer offers a candidate chain that forks at block `N - 1`, has one block at `N` (same block number), but that block carries a Peras certificate boost of `B > 0`. The candidate's suffix weight = `1 + B`.
3. The candidate header at block `N` is beyond the forecast horizon (e.g., the intersection is `k` blocks back and the candidate extends further).
4. `checkPreferTheirsOverOurs` is called with `emptyPerasWeightSnapshot`. It computes `selectView` on the tip headers only (block-number comparison): both tips have block number `N`, so `ShouldNotSwitch EQ` → the node throws `CandidateTooSparse` and disconnects.
5. The real chain selection (if it were reached) would compute `weightedSelectView` with the real snapshot: candidate suffix weight = `1 + B > 1` = our suffix weight → `ShouldSwitch`. The node should have switched to the heavier chain.
6. The node remains on the lighter chain, diverging from the canonical Peras-weighted chain. [6](#0-5) [7](#0-6)

preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"
        Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
          case preferCandidate
            (projectChainOrderConfig cfg)
            (weightedSelectView cfg weights oursSuffix)
            (weightedSelectView cfg weights candSuffix) of
            ShouldSwitch r -> ShouldSwitch (Left r)
            ShouldNotSwitch o -> ShouldNotSwitch o
