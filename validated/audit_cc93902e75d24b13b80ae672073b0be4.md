### Title
Missing Cryptographic Validation in Peras Vote and Certificate Acceptance — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `BlockSupportsPeras` universal instance implements `validatePerasCert` as unconditionally returning `Right` (accepting every certificate without any check) and `validatePerasVote` without any cryptographic signature verification. An unprivileged peer can send crafted votes impersonating any staked voter, or send forged certificates, and the node will accept them. This is the direct analog of the external report's "missing set function": the validation functions exist in the type class but their only concrete implementation is a stub that omits the actual security-critical logic.

---

### Finding Description

`BlockSupportsPeras` declares `validatePerasCert` and `validatePerasVote` as the required entry points for verifying inbound Peras objects. The sole concrete instance — a universal instance covering every `StandardHash blk` — implements both as stubs:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }

-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
```

`validatePerasCert` accepts every certificate unconditionally. `validatePerasVote` only checks that the claimed voter ID appears in the stake distribution; it never verifies the cryptographic signature on the vote.

These stubs are wired directly into the production inbound-vote pipeline. `makePerasVotePoolWriterFromChainDB` (and its `VoteDB` variant) pass `validatePerasVote mkPerasParams sd vote` as the validation callback to `processVotes`:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
```

`processVotes` calls this callback for every inbound vote from a peer, and only rejects a batch when the callback returns `Left`. Because the callback never checks signatures, every vote whose claimed voter ID is in the stake distribution passes.

### Impact Explanation

**Impact: Critical** — Bypass of Peras vote and certificate signature validation enabling unauthorized vote and certificate acceptance.

An attacker who knows the stake distribution (publicly derivable from the ledger) can:

1. Craft `PerasVote` objects claiming any voter ID that appears in the distribution, with an arbitrary or zeroed-out signature field. `validatePerasVote` will return `Right` because it only checks `lookupPerasVoteStake`.
2. Flood the node with enough such forged votes to reach the quorum threshold for a chosen round and target block. `updatePerasRoundVoteStates` will then forge a `ValidatedPerasCert` boosting the attacker's chosen block.
3. Alternatively, send a crafted `PerasCert` directly; `validatePerasCert` returns `Right` for every input, so the certificate is accepted and its weight boost applied to chain selection.

The resulting fake certificate causes `getPerasWeightSnapshot` to return inflated weights for the attacker's chosen block, directly influencing `preferAnchoredCandidate` and chain selection. A node can be made to prefer a non-canonical chain that it would otherwise reject.

---

### Likelihood Explanation

**Likelihood: Medium.** The Peras object-diffusion miniprotocol is active in the codebase and wired into the running node. The stake distribution is public. No cryptographic key material is required to exploit this — the attacker only needs to know a valid voter ID. The only barrier is that Peras is not yet fully deployed on mainnet; however, the code is in production files and executes on any node that enables the Peras diffusion layer.

---

### Recommendation

Implement real cryptographic verification in both `validatePerasCert` and `validatePerasVote` before the Peras diffusion layer is enabled on any network. Specifically:

- `validatePerasVote` must verify the cryptographic signature on the vote body using the voter's public key from the stake distribution, not merely check that the voter ID is present.
- `validatePerasCert` must verify the aggregate signature over the certificate's claimed voter set and target block.

Until these are implemented, the Peras object-diffusion endpoint should be disabled or gated behind a feature flag that is off by default.

---

### Proof of Concept

**Entry path:**

1. Attacker connects to a node running the Peras vote diffusion miniprotocol.
2. Attacker reads the current `PerasVoteStakeDistr` (derivable from the public ledger state).
3. Attacker constructs `N` `PerasVote` objects, each claiming a distinct voter ID from the distribution, all targeting the same `(PerasRoundNo, Point blk)` of the attacker's choice. Signature fields are set to arbitrary bytes.
4. Attacker sends these votes via the object-diffusion protocol. The node's inbound handler calls `processVotes` → `validatePerasVote mkPerasParams sd vote` for each.
5. `validatePerasVote` returns `Right` for each vote whose claimed ID is in `sd`, regardless of the signature.
6. `processVotes` calls `addVote` for each accepted vote. `implAddVote` calls `updatePerasRoundVoteStates`, which accumulates stake. Once the quorum threshold is crossed, `VoteGeneratedNewCert` fires and a `ValidatedPerasCert` is stored boosting the attacker's chosen block.
7. `getPerasWeightSnapshot` now returns a non-zero boost for the attacker's block. `preferAnchoredCandidate` uses this weight, causing the node to prefer the attacker's chain over the honest chain.
