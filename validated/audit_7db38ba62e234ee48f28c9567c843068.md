Looking at the `migrate_from_poa` function in `contracts/nbtc/src/migrate.rs` versus the `new()` constructor in `contracts/nbtc/src/lib.rs`, there is a clear missing initialization step that is a direct analog to M-10's pattern of incomplete state preparation.

### Title
Incomplete Migration in `migrate_from_poa` Missing `bridge_id` Account Registration — (File: `contracts/nbtc/src/migrate.rs`)

### Summary

The `migrate_from_poa` function omits the `internal_register_account(&bridge_id)` step that is explicitly present in the `new()` constructor. After migration, the bridge's own account is not registered in the `FungibleToken` accounts map, causing `safe_mint` to panic on any subsequent deposit attempt.

### Finding Description

The `new()` constructor explicitly registers the bridge account in the token ledger: [1](#0-0) 

The `migrate_from_poa` function constructs a new state carrying over the old PoA token but never performs this registration: [2](#0-1) 

The `safe_mint` function — the bridge's deposit minting path — calls `internal_deposit` directly on `bridge_id` without any auto-registration guard: [3](#0-2) 

`FungibleToken::internal_deposit` panics if the account is not registered. Because the migrated token state comes from the old PoA contract (which had a different or absent `bridge_id`), the new `bridge_id` will not be present in the accounts map after migration.

By contrast, the `mint` function uses `mint_inner`, which auto-registers before depositing: [4](#0-3) 

`safe_mint` has no such guard, making it permanently broken after `migrate_from_poa` until a `mint` call happens to register `bridge_id` as a side effect.

### Impact Explanation

After `migrate_from_poa` is executed, any deposit flow that routes through `safe_mint` will panic. The bridge cannot complete the mint, leaving the user's BTC locked on the Bitcoin side with no corresponding nBTC issued. This is a stuck bridge state requiring operator intervention, matching the **Medium** impact class: *broken callback rollback, or stuck bridge state requiring operator intervention*.

### Likelihood Explanation

`migrate_from_poa` is a one-time upgrade path from the PoA token. Immediately after migration, the bridge resumes normal deposit processing. The first call to `safe_mint` — triggered by any ordinary user submitting a deposit proof — will panic. The failure is deterministic and reproducible on every `safe_mint` call until `bridge_id` is incidentally registered via a `mint` call.

### Recommendation

Add `internal_register_account` for `bridge_id` inside `migrate_from_poa`, mirroring what `new()` does:

```rust
// After constructing new_state, before returning:
new_state.token.internal_register_account(&new_state.bridge_id);
new_state
``` [5](#0-4) 

### Proof of Concept

1. Deploy the nBTC contract in PoA mode (with `NearIntentsState` storage layout).
2. Call `migrate_from_poa(controller, bridge_id, withdraw_relayer)` — succeeds, state is migrated.
3. From the `bridge_id` account, call `safe_mint(user_account, amount, None)`.
4. `safe_mint` calls `self.token.internal_deposit(&self.bridge_id, amount)`.
5. `internal_deposit` calls `internal_unwrap_balance_of(&bridge_id)`, which panics because `bridge_id` was never registered in the accounts map.
6. The deposit fails; the user receives no nBTC; the bridge is stuck until an operator manually triggers a `mint` call to register `bridge_id` as a side effect.
