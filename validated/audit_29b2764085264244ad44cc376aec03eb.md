Audit Report

## Title
Fee-on-Transfer Token Causes Escrow Mis-Accounting in `initTransfer` — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
`OmniBridge.initTransfer` calls `safeTransferFrom` to pull `amount` tokens into the vault, then unconditionally emits `InitTransfer` with the caller-supplied `amount` rather than the actual received balance. For fee-on-transfer ERC20 tokens the vault receives `amount − fee`, yet the NEAR relayer credits the full `amount` to the recipient, creating a permanent per-deposit shortfall in the EVM escrow that accumulates until the vault cannot satisfy withdrawal requests.

## Finding Description
In the regular-ERC20 branch of `initTransfer` (the `else` path at lines 406–412), the contract executes:

```solidity
IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
```

No `balanceOf` snapshot is taken before or after this call. `SafeERC20.safeTransferFrom` only guarantees the call did not revert or silently return `false`; it does not guarantee the contract received exactly `amount` tokens. Immediately after, the function emits:

```solidity
emit BridgeTypes.InitTransfer(..., amount, ...);  // lines 427–436
```

The NEAR-side `fin_transfer_callback` (lines 705–745 of `near/omni-bridge/src/lib.rs`) decodes this event and constructs a `TransferMessage` using `init_transfer.amount` directly — the value from the event, not a verified on-chain balance. It then mints or unlocks that full `amount` to the recipient. The vault is now short by `fee_on_transfer` per deposit. When those NEAR-side tokens are later bridged back, `finTransfer` calls `safeTransfer(recipient, amount)` (lines 351–354) against a vault that holds less than `amount`, either reverting (freezing user funds) or draining other depositors' balances. The identical structural flaw exists in the Starknet `init_transfer` at lines 303–306 and 316–330 of `starknet/src/omni_bridge.cairo`.

## Impact Explanation
This is a concrete instance of **escrow mis-accounting** — an explicitly listed Critical impact. Each deposit of a fee-on-transfer token inflates the NEAR-side credit by `fee_on_transfer`. The shortfall accumulates with every such deposit. Eventual consequences are either permanent freezing of bridged funds (withdrawal reverts) or direct loss of honest depositors' funds as the shortfall is covered by the shared vault. Both outcomes are within the Critical allowed scope.

## Likelihood Explanation
The `else` branch in `initTransfer` imposes no token whitelist; any ERC20 address is accepted. Fee-on-transfer tokens exist on mainnet (e.g., PAXG, STA, reflection tokens). A single unintentional deposit of such a token triggers the accounting error. A motivated attacker can amplify the shortfall by repeating deposits with a self-deployed fee-on-transfer token, requiring no special privileges — only the ability to call `initTransfer` as an ordinary external user.

## Recommendation
1. **Measure actual received amount** using a balance snapshot and revert if the received amount differs from `amount`:
```solidity
uint256 balanceBefore = IERC20(tokenAddress).balanceOf(address(this));
IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
uint256 received = IERC20(tokenAddress).balanceOf(address(this)) - balanceBefore;
require(received == amount, "FeeOnTransferToken");
```
2. Alternatively, emit `received` instead of `amount` and propagate the actual received value through the cross-chain message.
3. Apply the equivalent fix to the Starknet `init_transfer` (`starknet/src/omni_bridge.cairo` lines 303–306).

## Proof of Concept
1. Deploy an ERC20 that deducts a 10% fee on every `transferFrom`.
2. Register the token with the bridge so NEAR has its decimal metadata.
3. Call `initTransfer(feeToken, 1000, 0, 0, nearRecipient, "")` on EVM.
   - `safeTransferFrom` succeeds; vault receives **900**.
   - `InitTransfer(amount=1000)` is emitted.
4. NEAR relayer submits the proof; `fin_transfer_callback` credits `nearRecipient` with **1000** tokens.
5. `nearRecipient` bridges **1000** tokens back to EVM.
6. EVM `finTransfer` calls `safeTransfer(recipient, 1000)` — vault holds only **900** → reverts (funds frozen) or drains other depositors' balances.
7. Repeat step 3–6 to amplify the shortfall until the vault is insolvent.
