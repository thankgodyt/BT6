### Title
Missing Revert When `withdraw_relayer` Is Unset Causes Permanent nBTC Token Loss - (File: contracts/nbtc/src/lib.rs)

---

### Summary

The `ft_transfer` function in the nBTC contract implements a legacy withdrawal flow that redirects token transfers to a configured `withdraw_relayer` address. When `withdraw_relayer` is not set, the function silently falls through and transfers the user's nBTC tokens to the nBTC contract's own account — permanently locking them with no recovery path.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, the `FungibleTokenCore::ft_transfer` implementation contains a special-case branch for the legacy Near Intents withdrawal flow: [1](#0-0) 

```rust
fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
    // Legacy bridging flow used by Near Intents
    if receiver_id == env::current_account_id()
        && memo
            .as_ref()
            .is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
    {
        if let Some(withdraw_relayer) = Self::read_withdraw_relayer_address() {
            return self.token.ft_transfer(withdraw_relayer, amount, memo);
        }
    }

    self.token.ft_transfer(receiver_id, amount, memo);
}
```

When `receiver_id == env::current_account_id()` and the memo starts with `"WITHDRAW_TO:"`, the intent is to redirect the transfer to the `withdraw_relayer`. However, if `withdraw_relayer` is `None` (not configured), the inner `if let` block is skipped and execution falls through to the final `self.token.ft_transfer(receiver_id, amount, memo)` call — where `receiver_id` is still `env::current_account_id()`, i.e., the nBTC contract itself. [2](#0-1) 

The `read_withdraw_relayer_address` function returns `None` when the storage key is absent, which is the default state before `set_withdraw_relayer_address` is ever called: [2](#0-1) 

There is no recovery mechanism for tokens held in the nBTC contract's own account. The `burn` function exclusively withdraws from `self.bridge_id`'s balance: [3](#0-2) 

The nBTC contract's own account (`env::current_account_id()`) is distinct from `bridge_id`, and no `lost_found` or administrative sweep function exists for it.

---

### Impact Explanation

Any user who calls `ft_transfer` on the nBTC contract with `receiver_id = nBTC contract address` and a memo prefixed with `"WITHDRAW_TO:"` while `withdraw_relayer` is unset will have their nBTC tokens silently transferred into the nBTC contract's own balance. These tokens are permanently irrecoverable: the `burn` path only drains `bridge_id`'s balance, and no privileged sweep or `lost_found` mechanism covers the nBTC contract's own account. This constitutes a permanent, irreversible loss of user funds.

**Impact class**: Critical — permanent locking/destruction of user funds.

---

### Likelihood Explanation

The `withdraw_relayer` address is an optional, post-deployment configuration set via `set_withdraw_relayer_address`. It is not required at contract initialization and has no default value. Any deployment window or operational period during which `withdraw_relayer` has not been set exposes all users of the legacy Near Intents withdrawal flow to this loss. The entry path is fully unprivileged: any nBTC token holder can call `ft_transfer` with the triggering parameters.

**Likelihood**: Medium — requires `withdraw_relayer` to be unset, which is the default state and a realistic operational condition.

---

### Recommendation

Add an explicit revert when `withdraw_relayer` is `None` in the legacy withdrawal branch, preventing tokens from silently falling through to a self-transfer:

```rust
fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
    if receiver_id == env::current_account_id()
        && memo.as_ref().is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
    {
        let withdraw_relayer = Self::read_withdraw_relayer_address()
            .unwrap_or_else(|| env::panic_str("withdraw_relayer not configured"));
        return self.token.ft_transfer(withdraw_relayer, amount, memo);
    }
    self.token.ft_transfer(receiver_id, amount, memo);
}
```

This mirrors the recommendation in the reference report: add an explicit check for the relevant address before accepting the transfer, and revert if the precondition is not met.

---

### Proof of Concept

1. Deploy the nBTC contract without calling `set_withdraw_relayer_address` (default state).
2. As any nBTC token holder, call `ft_transfer` with:
   - `receiver_id` = nBTC contract's own account ID
   - `amount` = any positive balance
   - `memo` = `"WITHDRAW_TO:bc1q..."`
3. `read_withdraw_relayer_address()` returns `None`; the inner `if let` is skipped.
4. Execution reaches `self.token.ft_transfer(receiver_id, amount, memo)` where `receiver_id == env::current_account_id()`.
5. The NEP-141 `FungibleToken::ft_transfer` executes a standard transfer from the caller to the nBTC contract itself.
6. The tokens now reside in the nBTC contract's own account balance. No `burn`, `lost_found`, or administrative function can recover them — they are permanently locked. [1](#0-0) [4](#0-3) [5](#0-4)
