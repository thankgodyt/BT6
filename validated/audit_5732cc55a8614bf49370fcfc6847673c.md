### Title
Peras Certificate Validation is a No-Op Stub, Allowing Fraudulent Certificates to Manipulate Chain Selection — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` method in the catch-all `BlockSupportsPeras` instance unconditionally returns `Right` without performing any cryptographic or structural validation. When Peras is enabled, any unprivileged peer can send a crafted `PerasCert` over the object-diffusion mini-protocol, have it accepted without any check, and cause the receiving node to apply a spurious weight boost to an arbitrary block — potentially making the node prefer a non-canonical chain over the honest chain.

---

### Finding Description

The `BlockSupportsPeras` class defines `validatePerasCert` as the method responsible for validating incoming Peras certificates before they are stored and used in chain selection. The only concrete instance in the codebase is a degenerate catch-all stub:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/120
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all possible 'PerasValidationErr' variants
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
```

This stub always returns `Right`, meaning every certificate passes validation regardless of its content, round number, boosted block, or cryptographic authenticity. [1](#0-0) 

The `processCerts` function in `ObjectPool/PerasCert.hs` is the inbound handler for certificates received from peers over the object-diffusion mini-protocol. It calls this stub directly:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

Because `validatePerasCert` always succeeds, every inbound certificate is timestamped and forwarded to `PerasCertDB.addCert`. The `implAddCert` function in `PerasCertDB/Impl.hs` carries an explicit TODO for "non-trivial validation logic" and currently only deduplicates by round number — it performs no content validation: [3](#0-2) 

Once stored, each certificate contributes to the `PerasWeightSnapshot` via `implGetWeightSnapshot`, which maps each certificate's boosted block to its weight boost (`vpcCertBoost = perasWeight params`): [4](#0-3) 

Chain selection in `ChainSel.hs` reads this snapshot atomically and passes it to `preferAnchoredCandidate` / `compareAnchoredFragments` when comparing candidate fragments: [5](#0-4) 

The `forksAtMostKWeight` function in `AnchoredFragment.hs` also uses the snapshot to enforce the rollback bound under Peras, meaning fraudulent weight can widen the effective rollback window: [6](#0-5) 

The complete attack path is therefore: peer → object-diffusion protocol → `processCerts` → `validatePerasCert` (no-op) → `implAddCert` (no-op validation) → `PerasWeightSnapshot` → chain selection.

---

### Impact Explanation

When Peras is enabled, an unprivileged peer can send a single crafted `PerasCert` that:

1. Names any arbitrary block as the "boosted block" (`pcCertBoostedBlock`)
2. Passes `validatePerasCert` unconditionally
3. Adds the full configured Peras weight boost (`perasWeight params`) to that block in the `PerasWeightSnapshot`
4. Causes chain selection to prefer a candidate chain containing that block over the honest chain

A single fraudulent certificate is sufficient because `vpcCertBoost = perasWeight params` assigns the full configured boost. If the non-canonical chain's total weight (block count + boost) exceeds the canonical chain's weight, the node switches forks. This is a **chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain**, matching the High impact tier.

---

### Likelihood Explanation

Peras is disabled by default — the CHANGELOG explicitly states "if Peras is disabled (which is the default), there is no observable difference." However, the full Peras infrastructure (object-diffusion protocol, `PerasCertDB`, weight snapshot, chain-selection integration) is present and wired into the node. Any operator who enables Peras exposes their node to this attack. The attack requires only a network connection to the target node and the ability to send one crafted certificate message; no keys, stake, or privileged access are needed.

---

### Recommendation

Implement actual certificate validation in `validatePerasCert` before Peras is enabled in production. At minimum:

1. Verify the certificate's aggregate cryptographic signature against the committee's aggregate public key (the `EveryoneVotes`/`WFALS` committee schemes in `Committee/` already implement `verifyCert` with proper aggregate-signature and VRF checks — these should be wired in).
2. Check that the boosted block is within the valid range (not older than the immutable tip, within the current Peras round window).
3. Check that the certificate's round number is consistent with the current epoch/slot.
4. Reject equivocating certificates (same round, different boosted block) at the validation layer rather than relying on "first one wins" deduplication in `implAddCert`.

The `implAddCert` TODO for "non-trivial validation logic" (referencing the same issue `tweag/cardano-peras#120`) should be resolved in tandem. [7](#0-6) 

---

### Proof of Concept

On a private testnet with Peras enabled:

1. Attacker connects to a target node via the object-diffusion mini-protocol for `PerasCert`.
2. Attacker sends a `PerasCert` with `pcCertRound = <any round>` and `pcCertBoostedBlock = <point of a non-canonical block>`.
3. `processCerts` calls `validatePerasCert mkPerasParams` which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams })` unconditionally.
4. The certificate is stored in `PerasCertDB` with the full Peras weight boost.
5. `implGetWeightSnapshot` includes the fraudulent boost in the `PerasWeightSnapshot`.
6. Chain selection now considers the non-canonical block to have extra weight equal to `perasWeight params`.
7. If the non-canonical chain's total weight (length + boost) exceeds the canonical chain's weight, `preferAnchoredCandidate` returns `ShouldSwitch` and the node adopts the non-canonical chain. [8](#0-7)

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

forksAtMostKWeight ::
  ( StandardHash blk
  , HasHeader b
  , HeaderHash blk ~ HeaderHash b
  ) =>
  PerasWeightSnapshot blk ->
  -- | By how much weight can we roll back our chain at most?
  PerasWeight ->
  -- | Our chain @ours@.
  AnchoredFragment b ->
  -- | Their chain @theirs@.
  AnchoredFragment b ->
  -- | Indicates whether their chain forks at most the given the amount of
  -- weight. Returns 'False' if the two fragments do not intersect.
  Bool
forksAtMostKWeight weights maxWeight ours theirs =
  case ours `AF.intersect` theirs of
    Nothing -> False
    Just (_, _, ourSuffix, _) ->
      totalWeightOfFragment weights ourSuffix <= maxWeight
