### Title
Missing Round-Number Deadline Check in Peras Vote and Certificate Inbound Validation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasVote.hs` and `PerasCert.hs`)

---

### Summary

The Peras vote and certificate inbound processing pipeline (`processVotes` / `processCerts`) accepts network-delivered votes and certificates without checking whether their embedded round number corresponds to the current (or a recent) Peras round. An unprivileged peer can craft and send votes or certificates for an arbitrarily old or future round number, and the node will accept and store them as valid, potentially forging a spurious quorum certificate for a stale round and influencing chain selection.

---

### Finding Description

The external report's vulnerability class is **missing deadline/expiry check**: an operation that should only be valid within a specific time window accepts inputs without verifying that the time window has not passed, allowing stale or premature inputs to be processed with full effect.

The exact analog exists in the Peras vote/certificate diffusion layer.

**`processVotes`** in `ObjectPool/PerasVote.hs` (lines 170–201) receives a batch of `PerasVote blk` objects from a remote peer, filters out already-known vote IDs, calls `validatePerasVote`, and stores every vote that passes. The `validatePerasVote` implementation (the only production instance, `SupportsPeras.hs` lines 360–371) checks **only** that the voter's key appears in the current stake distribution:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
```

The `_params` argument (which carries `PerasParams`, including the round length `perasRoundLength`) is **ignored** (`_params`). The vote's `pvVoteRound` field is never compared against the current slot or current round number. There is no check that the vote belongs to the current round, a recent round, or any round within a permissible window.

The same pattern applies to **`processCerts`** in `ObjectPool/PerasCert.hs` (lines 156–185) and `validatePerasCert` (`SupportsPeras.hs` lines 350–358), which unconditionally returns `Right` for every certificate regardless of its `pcCertRound`.

Both `implAddVote` (`PerasVoteDB/Impl.hs` lines 172–192) and `implAddCert` (`PerasCertDB/Impl.hs` lines 167–201) are also explicitly annotated with `-- TODO: we will need to update this method with non-trivial validation logic / see https://github.com/tweag/cardano-peras/issues/120`, confirming the round-validity check is a known missing piece that has not yet been implemented.

---

### Impact Explanation

**Impact: High — Bypass of Peras certificate/vote verification that enables unauthorized certificate acceptance and chain-selection manipulation.**

Peras certificates boost the weight of a chain segment. A certificate for round `r` boosts the block it names by `perasWeight` (a large constant), making that chain segment strongly preferred in chain selection over any competing fork that lacks a certificate. If an attacker can cause a node to accept and store a certificate for an **arbitrary past round** (or a future round whose block already exists), the node's chain-selection logic will treat the boosted block as immutably preferred, potentially causing the node to diverge from the honest majority chain.

Concretely:
1. An attacker sends a `PerasCert` with `pcCertRound = 0` (or any round) and `pcCertBoostedBlock = <attacker-chosen block point>`. Because `validatePerasCert` always returns `Right`, the certificate is accepted.
2. The certificate is stored in `PerasCertDB` and its boost weight is applied via `getWeightSnapshot` to chain selection.
3. The node now permanently prefers the attacker-chosen chain segment, diverging from the canonical chain.

For votes: an attacker can send enough votes for a stale round (with valid voter keys from the stake distribution) to trigger quorum in `updatePerasRoundVoteStates`, forging a spurious certificate for a past round and applying its boost.

---

### Likelihood Explanation

**Medium-High.** The attack requires only:
- Knowledge of valid voter public keys (publicly available from the stake distribution, which is on-chain).
- The ability to connect as a peer and send object-diffusion messages (any unprivileged network peer).
- No cryptographic key compromise: the current `validatePerasVote` only checks stake-distribution membership, not a cryptographic vote signature (the signature check is part of the `TODO` at issue #120).

The attack is directly reachable via the object-diffusion mini-protocol, which is the standard peer-to-peer channel for Peras vote/cert propagation.

---

### Recommendation

1. In `validatePerasVote` and `validatePerasCert`, add a check that the vote's `pvVoteRound` / certificate's `pcCertRound` falls within the current round window (i.e., `currRound - maxStaleness <= voteRound <= currRound + maxFutureness`), using the node's current slot and the `PerasParams` round length to compute the current round number.
2. Pass the current slot (or current round number) into `processVotes` / `processCerts` so the deadline check can be performed at the inbound processing boundary, before the vote/cert reaches the DB.
3. Resolve the tracked issue https://github.com/tweag/cardano-peras/issues/120 which explicitly acknowledges that full validation logic is missing.

### Proof of Concept

**Entry path:**

1. Peer connects via the object-diffusion mini-protocol and sends a `PerasCert` with `pcCertRound = 0` and `pcCertBoostedBlock = <target block point>`.
2. `makePerasCertPoolWriterFromChainDB` calls `processCerts` (`PerasCert.hs:156`).
3. `processCerts` calls `validatePerasCert mkPerasParams cert` (`PerasCert.hs:168`).
4. `validatePerasCert` (`SupportsPeras.hs:353`) unconditionally returns `Right ValidatedPerasCert{...}` — no round check.
5. The certificate is stored via `ChainDB.addPerasCertAsync`, boosting the attacker-chosen block in chain selection.

```haskell
processVotes ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
```
