Audit Report

## Title
Fee Validation Without Normalization Check Causes Permanent Locking of User Funds - (File: near/omni-bridge/src/lib.rs)

## Summary

`init_transfer` (via `ft_on_transfer`) locks or burns user tokens after only checking `fee < amount`, without verifying that `normalize_amount(amount - fee, decimals) > 0`. When the net transfer amount is below the decimal-scaling divisor, `sign_transfer` later panics with `ERR_INVALID_AMOUNT_TO_TRANSFER` in a separate transaction, leaving the already-committed tokens permanently frozen with no recovery path.

## Finding Description

**Step 1 — Token commitment without normalization guard.**
In `init_transfer_internal` (L1829–1865), tokens are locked or burned unconditionally after the transfer message is stored. The only fee guard applied before this point is:

```rust
// near/omni-bridge/src/lib.rs L554-557
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```

This passes for any `fee = 0` and any `amount > 0`, regardless of whether the net amount survives normalization.

**Step 2 — Normalization check in a later, separate transaction.**
When a relayer calls `sign_transfer` (L447), the bridge computes:

```rust
// near/omni-bridge/src/lib.rs L475-485
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

`normalize_amount` uses floor division:

```rust
// near/omni-bridge/src/lib.rs L2784-2787
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

For `origin_decimals = 24`, `dest_decimals = 6`, the divisor is `10^18`. Any `amount_without_fee < 10^18` yoctoNEAR normalizes to 0, causing `sign_transfer` to panic.

**Step 3 — No recovery path.**
- `cancel_transfer` does not exist (confirmed by search).
- `update_transfer_fee` (L390–435) enforces `fee.fee >= current_fee.fee`, so the fee can only be increased, not decreased. Increasing the fee makes `amount_without_fee` smaller, not larger — it cannot rescue the transfer.
- The code comment at L2781–2783 explicitly acknowledges: *"When fee = 0, dust stays locked/burned. See SECURITY.md for details."* However, the referenced `SECURITY.md` contains only the generic Immunefi exclusion list and provides no documentation of this behavior or any recovery mechanism.

The panic in `sign_transfer` occurs in a separate NEAR transaction from `init_transfer_internal`. NEAR's transaction atomicity does not roll back the prior lock/burn, so the tokens remain committed with no on-chain path to reclaim them.

## Impact Explanation

This matches the Critical allowed impact: **permanent freezing of bridged funds**. For any token pair where `origin_decimals > dest_decimals`, a user who initiates a transfer with `amount_without_fee < 10^(origin_decimals - dest_decimals)` loses those tokens permanently. For the NEAR→EVM 24→6 decimal pair, the maximum loss per transfer is `10^18 - 1` yoctoNEAR (just under 1 NEAR). The loss is irreversible at the contract level.

## Likelihood Explanation

Any unprivileged user can trigger this through the standard `ft_on_transfer` callback — no special role or access is required. The condition is reachable on every token pair where `origin_decimals > dest_decimals`, which is the normal operating mode for NEAR-native tokens bridging to 6-decimal EVM tokens. A user who does not know the minimum transferable amount (which the contract never communicates or enforces at commitment time) can trigger this accidentally. The contract accepts the transaction and emits an `InitTransferEvent` log, giving no indication that the transfer is unserviceable.

## Recommendation

Add a normalization check inside `init_transfer` (or `init_transfer_internal`) **before** tokens are locked or burned. Retrieve the destination token's `Decimals` and assert `normalize_amount(amount_without_fee, decimals) > 0`. This mirrors the guard already present in `sign_transfer` but must be enforced at the point of commitment. Alternatively, implement a `cancel_transfer` function that allows the original sender to reclaim locked/burned tokens for transfers that cannot be signed, providing a recovery path for edge cases.

## Proof of Concept

1. Register a token with `origin_decimals = 24`, `dest_decimals = 6` (divisor = `10^18`).
2. Call `ft_on_transfer` transferring `amount = 5 * 10^17` yoctoNEAR with `fee = 0`.
3. `fee < amount` check passes (0 < 5×10^17). `init_transfer_internal` locks the tokens and stores the transfer message. `U128(0)` is returned — tokens are committed.
4. Relayer calls `sign_transfer` with the resulting `transfer_id`.
5. `normalize_amount(5 * 10^17, {24, 6}) = 5 * 10^17 / 10^18 = 0`.
6. `require!(0 > 0, ...)` panics → `ERR_INVALID_AMOUNT_TO_TRANSFER`. Transaction reverts.
7. The 0.5 NEAR remains locked in the bridge. No `cancel_transfer` exists. `update_transfer_fee` cannot decrease the fee. Funds are permanently frozen.
