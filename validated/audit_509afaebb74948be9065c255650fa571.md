### Title
Peras Weight Snapshot Omitted from ChainSync Candidate Preference Check Enables Chain Selection Bypass - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

The `checkPreferTheirsOverOurs` function in the ChainSync client hardcodes `emptyPerasWeightSnapshot` instead of the live `PerasWeightSnapshot` when deciding whether to disconnect from a peer. This is the direct analog of the external report's bug: a critical accounting variable (`totalLiquidity` / Peras weight) is not consulted during a key operation (chain preference check / ratio calculation), causing the comparison to always produce an incorrect result — zero Peras weight — regardless of the actual certificate-backed boosts on the chain.

---

### Finding Description

In `checkPreferTheirsOverOurs`, the ChainSync client evaluates whether a peer's candidate chain is preferable to the node's current chain. If the peer's chain is judged *not* preferable, the client throws `CandidateTooSparse` and disconnects from the peer. [1](#0-0) 

The call to `preferAnchoredCandidate` at line 1839 is passed `emptyPerasWeightSnapshot` — a constant zero-weight map — rather than the live `PerasWeightSnapshot` that is maintained by the ChainDB and used everywhere else in chain selection: [2](#0-1) 

The live snapshot is populated by `addToPerasWeightSnapshot` whenever a Peras certificate is processed, and it is the authoritative source for block weight boosts used in all other chain-selection paths: [3](#0-2) 

`preferAnchoredCandidate` branches on whether the snapshot is empty. When it is empty (as hardcoded here), it falls back to a pure block-count comparison, completely ignoring Peras weight boosts: [4](#0-3) 

The correct weighted comparison — `wsvTotalWeight = blockNo + weightBoost` — is only reached when the snapshot is non-empty: [5](#0-4) 

The developers acknowledge this is wrong with an explicit TODO referencing a known issue: [6](#0-5) 

---

### Impact Explanation

**Incorrect disconnection from peers serving the canonical Peras chain.**

Consider a Peras-active network where:

- **Our chain**: A → B → C → D (4 blocks, no boosts, total weight = 4)
- **Peer's chain**: A → B → C (3 blocks, C carries a Peras certificate boost of +2, total weight = 5)

When the peer sends a header beyond the forecast range, `checkPreferTheirsOverOurs` is invoked. With `emptyPerasWeightSnapshot`, `preferAnchoredCandidate` compares by block count only: peer has 3 blocks vs. our 4 → peer's chain is judged *not* preferable → `CandidateTooSparse` is thrown → the node disconnects from the peer.

With the real snapshot, total weight 5 > 4 → the peer's chain IS preferable → the node should keep the connection and eventually switch.

If the node disconnects from all peers serving the heavier (by Peras weight) canonical chain, it is left with only peers serving a lighter chain. The ChainDB's own chain selection (which correctly uses the live snapshot) would prefer the heavier chain, but the node can never receive it because it has disconnected from every peer that carries it. The node is permanently stuck on a less-preferred chain.

An adversary who has produced a slightly longer-by-block-count but lighter-by-Peras-weight fork can exploit this to cause an honest node to sever connections to all honest peers serving the certificate-boosted canonical chain, then adopt the adversarial fork.

This matches the **High** impact tier: *chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.*

---

### Likelihood Explanation

**Low-to-Medium.** The preconditions are:

1. Peras must be active and certificates must have been issued (boosting blocks on the canonical chain).
2. The node's current chain must be longer by raw block count than the canonical chain — achievable if an adversary withholds or delays Peras certificates while producing blocks, or if the node synced from an adversarial peer first.
3. The peer serving the canonical chain must trigger `checkPreferTheirsOverOurs` by sending a header beyond the forecast range — a normal occurrence during sync.

None of these require key compromise, admin access, or majority stake. A network-level adversary with modest stake who can time certificate delivery can reliably trigger this path.

---

### Recommendation

Replace `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live `PerasWeightSnapshot` read from the ChainDB (the same snapshot already threaded through `chainSelectionForBlock`, `constructPreferableCandidates`, and `initialChainSelection`). The TODO comment at line 1841–1842 already flags this as a known defect; the fix is to pass the real snapshot rather than deferring removal of the check. [7](#0-6) 

---

### Proof of Concept

```
Network: Peras enabled, quorum threshold = 60% stake

Slot 1:  Block B1 produced by honest pool, added to all nodes.
Slot 2:  Block B2 produced by honest pool.
Slot 3:  Block B3 produced by honest pool.
         Peras certificate issued for B2 (boost = +2).
         Canonical chain: B1→B2→B3, total weight = 3 + 2 = 5.

Adversary produces a competing fork:
         B1→B2'→B3'→B4' (4 blocks, no Peras cert, total weight = 4).

Victim node syncs from adversary first:
         Current chain = B1→B2'→B3'→B4' (block count = 4, weight = 4).

Honest peer connects and sends header B3 (beyond forecast range).
checkPreferTheirsOverOurs is called:
  preferAnchoredCandidate emptyPerasWeightSnapshot ourFrag theirFrag
  → compares block count: 4 (ours) vs 3 (theirs)
  → ShouldNotSwitch
  → throwSTM CandidateTooSparse
  → victim disconnects from honest peer.

Victim never receives the certificate-boosted canonical chain.
Victim remains on adversarial fork (weight 4) instead of canonical fork (weight 5).
```
