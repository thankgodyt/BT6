Audit Report

## Title
Parallel `burn.and(mint)` with No Error Callback in `swap_migrated_token` Causes Permanent Token Loss — (File: `near/omni-bridge/src/lib.rs`)

## Summary

`swap_migrated_token` schedules `burn` and `mint` as parallel, independent NEAR promises via `burn.and(mint)` and immediately detaches the combined promise. In NEAR Protocol, both sub-promises execute regardless of each other's outcome. If `mint` panics — for example because the recipient is not registered on the new token — the `burn` still executes and the user's old tokens are permanently destroyed with no new tokens issued and no refund path.

## Finding Description

**Entry point:** `ft_on_transfer` handles `BridgeOnTransferMsg::SwapMigratedToken` by returning `U128(0)` (bridge keeps all received tokens, no refund) and detaching the swap promise: [1](#0-0) 

**Root cause:** Inside `swap_migrated_token`, both cross-contract calls are composed with `.and()` and no `.then(callback)` is chained: [2](#0-1) 

In NEAR Protocol, `Promise::and()` schedules both sub-promises to execute in parallel and independently. A failure in one does not prevent the other from executing; the combined promise result is only "successful" if both succeed, but since the result is `.detach()`ed, no callback ever observes the outcome.

**Failure trigger — `mint` panics on unregistered account:** The `mint` implementation calls `self.token.internal_deposit(&account_id, amount.into())` in the `msg: None` branch: [3](#0-2) 

`internal_deposit` from NEAR's standard `FungibleToken` panics if `account_id` has no storage deposit on the new token. This is standard, documented NEAR FT behavior and requires no special attacker capability.

**`burn` succeeds regardless:** The `burn` call withdraws from `predecessor_account_id()` (the bridge contract), which holds the old tokens transferred in by the user: [4](#0-3) 

Because `burn` and `mint` are parallel, `burn` executes and succeeds even when `mint` panics. The old tokens are destroyed. No refund mechanism exists because `ft_on_transfer` already returned `U128(0)`.

**No existing guard prevents this:** There is no pre-check that `sender_id` is registered on the new token before issuing the burn, no sequential dependency (`burn.then(mint)`), and no error-handling callback.

## Impact Explanation

Permanent, unrecoverable loss of bridged user funds. Any user who calls `ft_transfer_call` on the old (migrated) token with `SwapMigratedToken` message, while not being registered on the new token, loses their entire transferred amount. This matches the critical impact class: *permanent freezing/loss of bridged funds*.

## Likelihood Explanation

Any unprivileged token holder can trigger this. The only precondition is that the recipient account is not registered on the new token — a common state for users who have never interacted with the new token contract. No attacker cooperation is needed; a user can accidentally trigger this themselves. The flow is reachable through a single public `ft_transfer_call` invocation. It is repeatable for every affected user.

## Recommendation

Replace the parallel composition with a sequential chain so that `mint` only executes if `burn` succeeds, and add a callback to handle `mint` failure by re-minting or logging an irrecoverable state:

```rust
// Option A: sequential — mint only if burn succeeded
burn.then(
    ext_token::ext(new_token)
        .mint(sender_id.clone(), amount, None)
)
.then(
    ext_self::ext(env::current_account_id())
        .on_swap_migrated_token(sender_id, old_token, amount)
)
```

The callback `on_swap_migrated_token` should inspect `promise_result` and, if `mint` failed, attempt recovery (e.g., re-issue old tokens or emit an alert). Additionally, consider pre-checking storage registration on the new token before burning, or attaching a storage deposit to the `mint` call to auto-register the recipient.

## Proof of Concept

1. Deploy old token (`old.token`) and new token (`new.token`) as omni-token contracts with the bridge as controller.
2. Register `new.token` migration: `bridge.add_migrated_token(old_token: "old.token", new_token: "new.token")`.
3. Mint some `old.token` balance to `alice.near` (bridge mints to alice).
4. **Do not** call `storage_deposit` for `alice.near` on `new.token`.
5. As `alice.near`, call `old.token.ft_transfer_call(receiver_id: bridge, amount: X, msg: "SwapMigratedToken")`.
6. Observe: `ft_on_transfer` returns `U128(0)` (bridge keeps tokens). `burn.and(mint)` is detached.
7. `burn` executes: bridge's balance of `old.token` decreases by X. ✓
8. `mint` executes: `internal_deposit` panics because `alice.near` is not registered on `new.token`. ✗
9. Final state: `alice.near` has 0 `old.token`, 0 `new.token`. Tokens are permanently lost.
