### Title
`validatePerasCert` Unconditionally Accepts Any Peras Certificate Without Cryptographic Verification — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The catch-all `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` for every inbound certificate, performing zero cryptographic verification. Any unprivileged peer can inject a crafted `PerasCert` for an arbitrary block via the ObjectDiffusion mini-protocol, causing the receiving node to accept it as valid, apply its chain-weight boost, and potentially switch to a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` typeclass declares `validatePerasCert` as the gate that must authenticate Peras certificates received from remote peers before they are stored and used to influence chain selection. The only instance in the codebase is the catch-all:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

Because no more-specific instance exists for any concrete block type (confirmed by `grep` — only `SupportsPeras.hs` and the two ObjectPool files reference `validatePerasCert`), this stub **is** the production code path for every block type.

The inbound certificate pipeline in `ObjectPool/PerasCert.hs` calls `validatePerasCert` before storing a certificate. Since the function always returns `Right`, every certificate a peer sends — regardless of its cryptographic content — is stamped `ValidatedPerasCert` and stored with a full `vpcCertBoost = perasWeight params` chain-weight boost. [2](#0-1) 

The same pattern applies to `validatePerasVote`: it checks only that the voter ID appears in the stake distribution (public information), but performs no cryptographic signature verification over the vote content. An attacker who knows any registered pool ID can forge votes attributed to that pool. [3](#0-2) 

These functions are wired into the production ObjectDiffusion inbound path: [4](#0-3) 

The `processVotes` function validates each vote via the injected `validateVote` callback (which resolves to `validatePerasVote`) and, on success, adds it to the `PerasVoteDB` where it accumulates toward quorum and certificate forging. [5](#0-4) 

---

### Impact Explanation

**Certificate path (`validatePerasCert`):** An attacker sends a single crafted `PerasCert` naming any block point on their own fork. The node accepts it unconditionally, applies `perasWeight` as a chain-weight boost to that block, and chain selection may immediately prefer the attacker's fork over the honest canonical chain. This is a direct bypass of Peras certificate authorization enabling unauthorized certificate acceptance and a chain-selection safety failure.

**Vote path (`validatePerasVote`):** An attacker who knows any registered pool ID (all are public via the stake distribution) can submit forged votes attributed to that pool. Because no signature is checked, the votes pass validation, accumulate stake weight, and — if enough are submitted — trigger `forgePerasCert` internally, producing a locally-forged certificate for an attacker-chosen block. The chain-weight boost then propagates to chain selection.

Both paths satisfy: *"Critical. Bypass of … certificate/signature validation … that enables unauthorized … certificate acceptance"* and *"High. Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain."*

---

### Likelihood Explanation

High. The ObjectDiffusion mini-protocol is reachable by any connected peer with no authentication prerequisite. No stake, no keys, and no special privileges are required. The attacker needs only to know a target block hash (for the certificate path) or any registered pool ID (for the vote path), both of which are public on-chain data. The attack is a single network message.

---

### Recommendation

1. **`validatePerasCert`**: Implement full aggregate-signature verification against the committee's public keys before returning `Right`. Until a real implementation exists, the function should return `Left` (reject) rather than `Right` (accept) for all inputs, so that the stub fails closed rather than open.

2. **`validatePerasVote`**: Add cryptographic signature verification of the vote body against the voter's registered public key in addition to the existing stake-distribution membership check.

3. Track both gaps under the existing issue [tweag/cardano-peras#120](https://github.com/tweag/cardano-peras/issues/120) and treat them as security-critical blockers before any Peras-enabled deployment.

---

### Proof of Concept

**Certificate injection (no stake required):**

1. Connect to a target node as a peer via the ObjectDiffusion protocol.
2. Construct a `PerasCert { pcCertRound = r, pcCertBoostedBlock = attackerBlockPoint }` for any block on an attacker-controlled fork.
3. Send it through the inbound `PerasCertDiffusionInboundPipelined` handler.
4. `validatePerasCert` returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }` unconditionally.
5. The certificate is stored; the attacker's block receives a full Peras chain-weight boost.
6. Chain selection now prefers the attacker's fork.

**Vote forgery (requires knowing one registered pool ID):**

1. Obtain any registered pool ID from the public stake distribution.
2. Construct `PerasVote { pvVoteRound = r, pvVoteBlock = attackerBlockPoint, pvVoteVoterId = knownPoolId }`.
3. Send a batch of such votes (attributed to different known pool IDs) via the ObjectDiffusion vote inbound path.
4. `validatePerasVote` passes each vote (stake-distribution membership check passes; no signature check exists).
5. Votes accumulate in `PerasVoteDB`; once quorum stake is reached, `forgePerasCert` fires internally.
6. The forged certificate boosts the attacker's block and influences chain selection.

processVotes ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
