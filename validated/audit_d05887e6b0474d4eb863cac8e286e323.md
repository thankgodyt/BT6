Audit Report

## Title
Missing Pre-flight Token Address Check Causes Permanent Loss of Burned/Locked Funds on Unregistered Destination Chains — (File: `near/omni-bridge/src/lib.rs`)

## Summary

`init_transfer_internal` burns deployed tokens and locks native tokens before verifying that a token address mapping exists for the chosen destination chain. If the mapping is absent, every subsequent `sign_transfer` call panics with `FailedToGetTokenAddress`, and no user-callable cancel or timeout mechanism exists to recover the funds. The pending transfer entry becomes immortal and the burned/locked tokens are permanently unrecoverable.

## Finding Description

**Step 1 — `init_transfer` performs no token-address pre-flight check.**

`init_transfer` (lines 523–619) validates only that the recipient chain is not `ChainKind::Near` and that the fee is below the amount. It never calls `get_token_address` to confirm the token is registered for the destination chain before proceeding to `init_transfer_internal`.

**Step 2 — Tokens are burned/locked inside `init_transfer_internal` with no rollback.**

`init_transfer_internal` (lines 1829–1865) first inserts the transfer into `pending_transfers` via `add_transfer_message`, then calls `burn_tokens_if_needed` (line 1851) and `lock_tokens_if_needed` (line 1853). `burn_tokens_if_needed` (lines 1806–1813) fires a detached cross-contract call (`.detach()`) that cannot be rolled back. The function returns `U128(0)`, giving the user no refund.

**Step 3 — `sign_transfer` unconditionally panics when the mapping is absent.**

`sign_transfer` (lines 462–469) calls `get_token_address` and panics with `FailedToGetTokenAddress` if the result is `None`. Because the mapping was never registered, every relayer attempt to sign the transfer fails at this point, leaving `pending_transfers` untouched.

**Step 4 — `sign_transfer_callback` does not clean up on signing failure.**

Lines 655–667 show that `remove_transfer_message` is called only when `call_result` is `Ok` **and** `fee.is_zero()`. A failed MPC signing call silently returns, leaving the pending entry alive.

**Step 5 — The only other removal paths require a destination-chain proof that can never arrive.**

`claim_fee_callback` (line 1094) removes the pending transfer only after successfully verifying a `ProverResult::FinTransfer` from the destination chain. If the destination chain never finalizes the transfer (because the token address was never registered there), no proof is ever produced and this path is permanently blocked.

**Step 6 — No public cancel, timeout, or expiry function exists.**

`remove_transfer_message` is reachable only through `sign_transfer_callback` (fee-zero + success), `claim_fee_callback` (destination-chain proof), and `remove_transfer_message_without_refund` inside `init_transfer_internal` (storage-failure path only). `pending_transfers` is a plain `LookupMap` with no TTL field in `TransferMessageStorage`.

## Impact Explanation

For **deployed (bridge-minted) tokens**: tokens are burned at `init_transfer` time via a detached, irreversible cross-contract call. A permanently stuck transfer means those tokens are destroyed with no mint-back path — direct, permanent loss of bridged funds.

For **non-deployed (native) tokens**: tokens are held by the bridge and tracked in `locked_tokens`. A stuck transfer permanently freezes those tokens inside the bridge with no user withdrawal path.

Both outcomes match the allowed critical impact: *permanent freezing or loss of bridged funds across supported chains*.

## Likelihood Explanation

The trigger requires no admin compromise, no relayer collusion, and no external dependency failure. Any user can reach this state by calling `ft_transfer_call` targeting the bridge with a destination chain for which the token address mapping has not yet been registered via `bind_token` or `deploy_token`. Given that the bridge supports multiple chains and tokens are onboarded incrementally, this is a realistic operational scenario. The user alone controls the destination chain field in `InitTransferMsg`.

## Recommendation

1. **Pre-flight check in `init_transfer_internal`**: Before calling `burn_tokens_if_needed` / `lock_tokens_if_needed`, assert that `get_token_address(destination_chain, token_id)` returns `Some`. If it returns `None`, call `remove_transfer_message_without_refund` and return the full amount to the caller.
2. **User-callable cancel with grace period**: Add a public `cancel_transfer(transfer_id)` function restricted to the original sender, callable only after a configurable timeout from transfer creation. For deployed tokens, mint back the burned amount; for native tokens, unlock and return them.
3. **Timestamp in `TransferMessageStorage`**: Record the block timestamp at insertion time so the grace period can be enforced on-chain.

## Proof of Concept

```
1. Token `wETH.near` is a deployed (bridge-minted) token.
   Its address is registered for ChainKind::Eth but NOT for ChainKind::Sol.

2. User calls:
     wETH.near::ft_transfer_call(
       receiver_id = omni-bridge.near,
       amount      = 1_000_000,
       msg         = InitTransfer { recipient: Sol(<address>), fee: 100, ... }
     )

3. omni-bridge::ft_on_transfer → init_transfer → init_transfer_internal:
   - add_transfer_message inserts entry into pending_transfers.
   - burn_tokens_if_needed fires detached burn of 1_000_000 wETH (irreversible).
   - Returns U128(0) — user receives no refund.

4. Trusted relayer calls omni-bridge::sign_transfer(transfer_id, ...):
   - get_token_address(ChainKind::Sol, wETH.near) → None
   - env::panic_str("ERR_FAILED_TO_GET_TOKEN_ADDRESS")
   - Transaction reverts; pending_transfers entry survives intact.

5. Step 4 repeats indefinitely. claim_fee requires a Sol-chain proof that
   never arrives. No cancel function exists.
   1_000_000 wETH are permanently destroyed with no recovery path.
```
