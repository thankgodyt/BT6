### Title
Unconditional `validatePerasCert` Acceptance Bypasses All Peras Certificate Validation, Enabling Unprivileged Chain-Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance unconditionally returns `Right` from `validatePerasCert`, accepting every inbound Peras certificate without performing any cryptographic or structural check. Because this stub is wired directly into the production certificate-diffusion path (`makePerasCertPoolWriterFromChainDB`), any unprivileged peer can inject an arbitrary `PerasCert` that will be stored in the `PerasCertDB` and used to boost a chosen block's chain weight, potentially causing the node to switch to an adversary-controlled fork.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must approve every inbound certificate before it is stored or acted upon. The only deployed instance — a universal `instance StandardHash blk => BlockSupportsPeras blk` — implements this gate as an unconditional pass-through:

```haskell

-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120

  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is not confined to tests. The production pool writer `makePerasCertPoolWriterFromChainDB` passes it verbatim as the `validateCert` argument to `processCerts`:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` maps `validateCert` over every new certificate received from a peer and, because the function never returns `Left`, the `partitionEithers` branch always takes the "all valid" path, adding every certificate to the pool:

```haskell

  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts

Each accepted certificate is forwarded to `ChainDB.addPerasCertAsync`, which enqueues a `ChainSelAddPerasCert` message. `chainSelSync` then stores the certificate in `PerasCertDB`, updates the `PerasWeightSnapshot`, and calls `chainSelectionForBlock` for the boosted block:

```haskell

``` [4](#0-3)

### Impact Explanation

An unprivileged peer can craft a `PerasCert` naming any block hash as `pcCertBoostedBlock`. Because `validatePerasCert` never rejects anything, the certificate is stored and the named block receives a weight boost of `perasWeight` (15 blocks by default). If the boosted block is on a fork, the fork's total weight can exceed the honest chain's weight, causing the node to switch to the adversary-controlled fork. This is a direct bypass of Peras certificate validation enabling unauthorized certificate acceptance and chain-selection manipulation.

**Impact class:** Critical — bypass of Peras certificate checks that enables unauthorized certificate acceptance and chain-selection divergence from the honest chain.

---

### Likelihood Explanation

The attack requires only network connectivity to a target node. No stake, keys, or privileged access are needed. The attacker simply sends a well-formed CBOR-encoded `PerasCert` over the Peras certificate diffusion mini-protocol. The stub is active in every build that uses the universal `StandardHash blk` instance, which covers all current Cardano block types. Likelihood is **High** once Peras is enabled on a live network.

---

### Recommendation

Replace the stub with a real implementation that verifies:
1. The certificate's aggregate vote signature against the claimed committee members' keys.
2. That the claimed voters constitute a quorum (stake ≥ `perasQuorumStakeThreshold`).
3. That the boosted block's slot satisfies `perasBlockMinSlots`.
4. That the certificate's round number is within the valid window (`perasCertMaxRounds`).

Until the real implementation is ready, the stub should at minimum reject all certificates (return `Left PerasValidationErr`) so that no peer-supplied certificate can influence chain selection, rather than accepting all of them.

---

### Proof of Concept

1. Connect to a target node as a peer via the Peras certificate diffusion mini-protocol.
2. Construct a `PerasCert` with `pcCertRound = <any round>` and `pcCertBoostedBlock = <hash of a block on a competing fork>`.
3. Send the certificate. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{vpcCertBoost = PerasWeight 15}` unconditionally.
4. The certificate is stored in `PerasCertDB`. `chainSelSync` triggers chain selection for the boosted block.
5. The fork's total weight is now `length + 15`; if this exceeds the honest chain's length, the node switches to the fork.
