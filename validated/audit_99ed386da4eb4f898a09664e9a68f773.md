Audit Report

## Title
Zero-Normalized Amount Causes Permanent Transfer Lock — (File: `near/omni-bridge/src/lib.rs`)

## Summary
When a user initiates an outbound NEAR→EVM transfer with an amount that floor-divides to zero under `normalize_amount`, the transfer is committed to `pending_transfers` and the user's tokens are burned or locked inside `init_transfer_internal`. Every subsequent call to `sign_transfer` for that `transfer_id` permanently reverts with `InvalidAmountToTransfer`, and no user-callable cancellation or refund path exists, causing permanent loss of the deposited funds.

## Finding Description
`normalize_amount` performs floor division to convert a NEAR-precision amount to the destination chain's precision:

```rust
// L2784-2787
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

For a token registered with `origin_decimals = 24` and `decimals = 18` (standard NEAR→EVM pairing), any amount below `1_000_000` yocto-units normalizes to `0`.

The zero-amount guard exists only inside `sign_transfer` (L482-485), which is called **after** the transfer has already been committed:

```rust
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

The transfer is committed and tokens consumed inside `init_transfer_internal` (L1829-1865), which has no pre-check that the post-normalization amount will be non-zero. When the token is a NEAR-native token (`OmniAddress::Near`), the function calls `burn_tokens_if_needed` and `lock_tokens_if_needed`, then returns `U128(0)` — signaling full consumption to the NEP-141 contract. The only removal paths for a `pending_transfers` entry (`claim_fee_callback`, `fin_transfer_callback`) require proof of destination-chain finalization that will never exist for a transfer that was never successfully signed. There is no user-callable cancel or refund function.

Notably, the `normalize_amount` docstring (L2781-2782) acknowledges that "dust stays locked/burned" when `fee = 0`, but this refers to sub-unit remainders on otherwise valid transfers. The zero-normalization case — where the **entire** transferred amount is lost — is a distinct and more severe scenario not covered by that acknowledgment.

## Impact Explanation
User funds (NEP-141 tokens or wNEAR) are permanently frozen inside the bridge contract. The `ft_on_transfer` callback returns `0`, so the NEP-141 contract does not refund the sender. Every call to `sign_transfer` for the affected `transfer_id` reverts, and no other code path removes the entry or recovers the funds. This constitutes permanent freezing of bridged funds, matching the Critical impact category: "permanent freezing of bridged funds across NEAR, EVM, … flows."

## Likelihood Explanation
The condition is reachable by any unprivileged user calling `ft_transfer_call` on a registered NEAR token with a small amount. For the common 24→18 decimal gap, amounts below `1_000_000` yocto-units (less than 1 µNEAR-equivalent) trigger the bug. A user sending dust, making a rounding error, or testing with a small amount can hit this silently — `ft_on_transfer` succeeds and returns no error to the sender. No special privileges or external conditions are required.

## Recommendation
Add a normalization check inside `init_transfer_internal` (or at the top of `ft_on_transfer`) before the transfer is committed to storage. If the normalized amount is zero, return the full amount to the caller as a refund:

```rust
let normalized = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

This mirrors the guard already present in `sign_transfer` (L482-485) but places it at the correct, earlier point in the lifecycle — before tokens are burned or locked and before the transfer is stored.

## Proof of Concept
1. Register a token with `origin_decimals = 24`, `decimals = 18`.
2. Call `ft_transfer_call` on that token, sending `500_000` yocto-units to the bridge with a valid `InitTransferMsg` (fee = 0).
3. `ft_on_transfer` invokes `init_transfer_internal`: the transfer is stored in `pending_transfers`, `burn_tokens_if_needed` is called, and `U128(0)` is returned — tokens are consumed with no refund.
4. Call `sign_transfer` for the resulting `transfer_id`.
5. `normalize_amount(500_000, {origin_decimals: 24, decimals: 18})` = `500_000 / 1_000_000` = `0`.
6. `require!(amount_to_transfer > 0, …)` panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.
7. Repeat step 4 indefinitely — it always reverts. The 500,000 yocto-units are permanently locked with no recovery path. [1](#0-0) [2](#0-1) [3](#0-2)

    fn init_transfer_internal(
        &mut self,
        transfer_message: TransferMessage,
        storage_owner: AccountId,
    ) -> U128 {
        let required_storage_balance = self
            .add_transfer_message(transfer_message.clone(), storage_owner.clone())
            .saturating_add(NearToken::from_yoctonear(transfer_message.fee.native_fee.0));

        if self
            .try_update_storage_balance(
                storage_owner,
                required_storage_balance,
                NearToken::from_yoctonear(0),
            )
            .is_err()
        {
            self.remove_transfer_message_without_refund(transfer_message.get_transfer_id());
            return transfer_message.amount;
        }

        if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
            self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);

            self.lock_tokens_if_needed(
                transfer_message.get_destination_chain(),
                &token_id,
                transfer_message.amount.0,
            );
        } else {
            self.remove_transfer_message_without_refund(transfer_message.get_transfer_id());
            return transfer_message.amount;
        }

        env::log_str(&OmniBridgeEvent::InitTransferEvent { transfer_message }.to_log_string());
        U128(0)
    }
