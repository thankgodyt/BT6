### Title
Corrupted UTXO `tx_bytes` in `safe_verify_deposit` Permanently Locks Bridge Funds - (File: contracts/satoshi-bridge/src/btc_light_client/deposit.rs)

---

### Summary
In `internal_safe_verify_deposit_entry`, when the caller-supplied `tx_bytes` exceeds 10 000 bytes, the code silently replaces the real transaction bytes with `vec![0u8; 300]` (300 zero bytes) **after** successfully decoding the transaction. This corrupted byte slice is then stored verbatim in the on-chain UTXO. Any subsequent attempt by the bridge to spend that UTXO (withdrawal PSBT construction) will call `WrappedTransaction::decode` on the garbage bytes, panic, and revert — permanently locking the deposited BTC inside the bridge while the corresponding nBTC has already been minted.

---

### Finding Description

In `internal_safe_verify_deposit_entry` the following block appears after the transaction has already been decoded and validated:

```rust
// contracts/satoshi-bridge/src/btc_light_client/deposit.rs  lines 204-209
let tx_bytes = if tx_bytes.len() > 10000 {
    env::log_str("tx_bytes length exceeds 10000, truncating to 300 bytes");
    vec![0u8; 300]          // ← replaces real bytes with 300 zero bytes
} else {
    tx_bytes
};
```

The corrupted `tx_bytes` is then placed directly into the `UTXO` struct that is forwarded through the callback chain and ultimately persisted by `internal_set_utxo`:

```rust
// lines 211-216
let utxo = UTXO {
    path,
    tx_bytes,          // ← now vec![0u8; 300]
    vout,
    balance: transaction.output()[vout].value.to_sat(),
};
```

The `balance` field is correct (taken from the real decoded transaction), so the UTXO appears healthy in the pool. However, every code path that later needs to reconstruct the original transaction from `utxo.tx_bytes` — most critically PSBT construction for withdrawals — will call:

```rust
WrappedTransaction::decode(&utxo.tx_bytes, &config.chain)
    .expect("Deserialization tx_bytes failed")
```

on 300 zero bytes, which is not a valid serialised transaction. The `.expect` panics, the withdrawal call reverts, and the UTXO remains in the pool but is permanently unspendable by the contract.

The `safe_verify_deposit` entry point requires only an attached storage deposit (no relayer-whitelist check is present in `internal_safe_verify_deposit_entry`), so any bridge user who attaches sufficient NEAR can trigger this path.

---

### Impact Explanation

**Permanent locking of bridge funds / stuck bridge state requiring operator intervention.**

1. nBTC is minted to the recipient (or forwarded via `safe_mint` / `ft_transfer_call`) — the user receives their wrapped tokens.
2. The on-chain UTXO record has a correct `balance` but corrupted `tx_bytes`.
3. Every future withdrawal attempt that selects this UTXO will panic during PSBT construction and revert.
4. The BTC UTXO is permanently locked inside the bridge's MPC-controlled address from the smart-contract's perspective; recovering it requires off-chain operator action (constructing a spend transaction outside the contract using the real `tx_bytes` fetched from the Bitcoin network).
5. If multiple such deposits accumulate, a growing portion of the bridge's BTC reserve becomes unspendable through the normal contract flow, breaking the nBTC backing guarantee.

---

### Likelihood Explanation

A Bitcoin transaction exceeds 10 000 bytes when it consolidates roughly 50 or more P2PKH/P2WPKH inputs. This is uncommon for typical retail deposits but is a realistic scenario for:

- Users consolidating many small UTXOs into a single deposit.
- Automated bridge relayers or liquidity providers handling high-volume flows.
- An attacker who deliberately constructs a large consolidation transaction to a deposit address they control, then submits the `safe_verify_deposit` proof.

The attacker must own the BTC being deposited (they lose the BTC), but they permanently lock a UTXO in the bridge and receive nBTC, breaking the bridge's accounting. The cost is the BTC deposit itself; the damage is the permanent loss of bridge operability for that UTXO.

---

### Recommendation

Remove the truncation block entirely. The `tx_bytes` size is already bounded upstream by `MAX_REQUEST_REFUND_TX_BYTES` (200 000 bytes) in the refund path; a similar explicit size cap with a hard `require!` rejection (not silent replacement) should be applied here if a limit is desired:

```rust
require!(
    tx_bytes.len() <= MAX_SAFE_DEPOSIT_TX_BYTES,
    "tx_bytes too large"
);
```

Never replace caller-supplied bytes with synthetic garbage and then store the result as authoritative on-chain state.

---

### Proof of Concept

1. Derive a `safe_verify_deposit` deposit address for a chosen `DepositMsg` (with `safe_deposit` field set).
2. Construct a Bitcoin transaction paying to that address that uses ≥ 50 P2PKH inputs so that the serialised transaction exceeds 10 000 bytes. Broadcast it and wait for inclusion.
3. Call `safe_verify_deposit` on the bridge contract with the real `tx_bytes` (> 10 000 bytes), a valid Merkle inclusion proof, and sufficient attached NEAR for storage.
4. The contract decodes the transaction successfully, validates the output, then silently replaces `tx_bytes` with `vec![0u8; 300]` and stores the UTXO. `safe_mint` fires; the recipient receives nBTC.
5. Attempt any withdrawal that causes the bridge to select this UTXO. PSBT construction calls `WrappedTransaction::decode` on the 300-zero-byte slice, panics with `"Deserialization tx_bytes failed"`, and reverts. The UTXO is permanently stuck. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
