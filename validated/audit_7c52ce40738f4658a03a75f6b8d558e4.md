### Title
Refund Timelock Read from Live Config Instead of Snapshotted at Request Time — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`execute_refund` resolves the required timelock by reading `refund_timelock_sec` / `unsafe_refund_timelock_sec` from the **current** global `Config` rather than from a value captured when `request_refund` was submitted. A DAO governance action that increases either timelock takes effect immediately on all pending refund requests, including those that had already satisfied the original timelock, causing user BTC deposits to be temporarily locked beyond the period the user was promised.

---

### Finding Description

`resolve_execute_refund_timelock` in `refund.rs` computes the required wait period at call time:

```rust
// refund.rs:215-227
let config = self.internal_config();          // reads CURRENT config
if refund_request.deposit_msg().refund_address.is_some() {
    if is_privileged { 0 } else { config.refund_timelock_sec }
} else {
    config.unsafe_refund_timelock_sec          // not snapshotted at request time
}
``` [1](#0-0) 

The `RefundRequest` struct records `created_at_sec` but stores no timelock value:

```rust
pub struct RefundRequest {
    ...
    pub created_at_sec: u32,
    pub executed: bool,
}
``` [2](#0-1) 

The timelock check in `load_refund_request_for_execute` then compares `created_at_sec` against the **live** timelock:

```rust
require!(
    u64::from(now) >= u64::from(refund_request.created_at_sec) + timelock_sec,
    "Refund timelock has not passed yet"
);
``` [3](#0-2) 

`update_config` applies changes immediately with no guard for in-flight refund requests:

```rust
pub fn update_config(&mut self, update: ConfigUpdate) {
    assert_one_yocto();
    update.apply(self.internal_mut_config());
}
``` [4](#0-3) 

`ConfigUpdate` includes both timelock fields:

```rust
pub refund_timelock_sec: Option<u64>,
pub unsafe_refund_timelock_sec: Option<u64>,
``` [5](#0-4) 

---

### Impact Explanation

**Medium — attacker-triggered (or governance-triggered) temporary locking of bridged funds.**

A user whose BTC deposit is stuck (never finalized via `verify_deposit`) submits `request_refund` when `unsafe_refund_timelock_sec = 14 days`. After waiting 14 days the user calls `execute_refund`. If the DAO has in the interim increased `unsafe_refund_timelock_sec` to, say, 30 days (a plausible security response to a suspicious refund wave), the call reverts with "Refund timelock has not passed yet." The user's BTC remains locked in the deposit address for an additional 16 days with no recourse — they cannot cancel the request themselves, and the DAO could also reject it outright. The same applies to `refund_timelock_sec` for pre-authorized refund addresses.

---

### Likelihood Explanation

**Low.** Requires a DAO governance action (`update_config`) to coincide with pending refund requests. However, the scenario is realistic: the DAO may legitimately increase timelocks in response to a security incident or policy change, inadvertently freezing already-matured refund requests. No malicious intent is required — the design flaw is that the timelock is not snapshotted at request creation time.

---

### Recommendation

Snapshot the applicable timelock into `RefundRequest` at the time `request_refund_callback` stores the request, and use that stored value in `resolve_execute_refund_timelock` instead of reading from the live config. For example:

```rust
pub struct RefundRequest {
    ...
    pub created_at_sec: u32,
    pub timelock_sec: u64,   // captured at request time
    pub executed: bool,
}
```

Then `resolve_execute_refund_timelock` simply returns `refund_request.timelock_sec` (with the existing privilege bypass for DAO/RefundOperator). This ensures that governance changes to the timelock only affect future requests, not requests already in flight.

---

### Proof of Concept

1. `unsafe_refund_timelock_sec = 14 days` in config.
2. User calls `request_refund(deposit_msg_with_no_refund_address, ...)`. `request_refund_callback` stores `RefundRequest { created_at_sec: T, ... }`.
3. 14 days pass. User is now eligible to call `execute_refund`.
4. DAO calls `update_config({ unsafe_refund_timelock_sec: "2592000" })` (30 days) — a legitimate security measure.
5. User calls `execute_refund(utxo_storage_key, None)`.
6. `resolve_execute_refund_timelock` reads `config.unsafe_refund_timelock_sec = 30 days`.
7. `load_refund_request_for_execute` checks `now >= T + 30 days` → **false** → panics "Refund timelock has not passed yet".
8. User's BTC deposit remains locked for an additional 16 days. The DAO could also call `reject_refund` during this window, permanently discarding the request.
