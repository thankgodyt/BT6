Audit Report

## Title
Missing Normalization Guard in `init_transfer` and `finish_withdraw_v2` Causes Permanent Fund Freezing — (`near/omni-bridge/src/lib.rs`)

## Summary

`init_transfer` locks or burns user tokens after passing only a single fee-vs-amount check, with no verification that the normalized transfer amount is nonzero. `sign_transfer`, the sole path to complete the transfer, enforces the zero-amount guard only after tokens are already irrecoverably locked. No cancel or refund path exists for stuck pending transfers, and `update_transfer_fee` cannot rescue the transfer because it only permits fee increases. The same gap exists in `finish_withdraw_v2`.

## Finding Description

`init_transfer` constructs the `TransferMessage` and enforces exactly one constraint before locking tokens: [1](#0-0) 

There is no call to `normalize_amount` here. Tokens are locked or burned during the `ft_transfer_call` → `init_transfer` flow before `sign_transfer` is ever invoked.

`normalize_amount` uses floor division: [2](#0-1) 

For any token where `origin_decimals > decimals` (e.g., 24 on NEAR, 6 on EVM, `diff = 18`), any `amount - fee < 10^18` normalizes to zero.

`sign_transfer` — the only path to finalize the transfer — enforces the zero-amount guard after the fact: [3](#0-2) 

`update_transfer_fee` cannot rescue the transfer because it requires `fee.fee >= current_fee.fee`, meaning the fee can only increase, making `amount - fee` smaller and keeping the normalized value at zero: [4](#0-3) 

`finish_withdraw_v2` creates a transfer with `fee = 0` and no normalization check, meaning any sub-threshold amount passed by the calling token contract results in a permanently stuck transfer: [5](#0-4) 

No public cancel or refund function for pending outbound transfers exists in the contract.

## Impact Explanation

This constitutes **permanent freezing of bridged funds**: native tokens remain locked in the bridge escrow forever; deployed bridge tokens are burned with no recovery. This matches the Critical impact class: *"permanent freezing of bridged funds across NEAR, EVM..."* and *"decimal/normalization abuse... that changes user or protocol balances."*

## Likelihood Explanation

Any unprivileged user can trigger this by calling `ft_transfer_call` on a NEP-141 token directed at the bridge with an amount below the normalization threshold and `fee = 0`. For a token with a 12-decimal gap (24 on NEAR, 12 on EVM), any amount below `10^12` base units is affected. This is a realistic accidental user action. The `finish_withdraw_v2` path is callable by any deployed bridge token contract and has no minimum-amount guard at all, widening the attack surface.

## Recommendation

Add a normalization check inside `init_transfer` before tokens are locked, mirroring the guard already present in `sign_transfer`:

```rust
let decimals = self.token_decimals.get(&token_address)
    .near_expect(BridgeError::TokenDecimalsNotFound);
let normalized = Self::normalize_amount(
    transfer_message.amount_without_fee()
        .near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

Apply the identical guard to `finish_withdraw_v2` before `add_transfer_message` is called.

## Proof of Concept

1. Register a token with `origin_decimals = 24`, `decimals = 6` (diff = 18) for an EVM destination.
2. User calls `ft_transfer_call` with `amount = 10^18 - 1`, `fee = 0`, targeting the bridge. `init_transfer` passes (`0 < 10^18 - 1`). Tokens are locked.
3. A trusted relayer calls `sign_transfer`. `normalize_amount(10^18 - 1, decimals) = 0`. The call panics with `InvalidAmountToTransfer`.
4. User calls `update_transfer_fee` attempting any fee change. Setting `fee = 0` is rejected (not `>= current_fee`). Any increase makes `amount - fee` smaller, still normalizing to 0.
5. No cancel function exists. Tokens remain locked permanently.
6. For `finish_withdraw_v2`: a deployed bridge token calls it with `amount < 10^18`. Tokens are burned. `sign_transfer` always reverts. No recovery path exists.
