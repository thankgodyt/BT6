Audit Report

## Title
Missing Chain ID in `deployToken` Signature Enables Cross-Chain Replay Across EVM Deployments — (`File: evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

The `deployToken` function in `OmniBridge.sol` verifies a NEAR MPC signature over a borsh-encoded hash that excludes `omniBridgeChainId`. Because the MPC signing path `bridge-1` is chain-agnostic, the derived `nearBridgeDerivedAddress` is identical across all EVM deployments. A valid `deployToken` signature obtained for one EVM chain can be replayed verbatim on any other EVM chain, deploying a bridge token and registering it on NEAR without chain-specific authorization.

## Finding Description

`OmniBridge.sol::deployToken` constructs its signed hash as:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
bytes32 hashed = keccak256(borshEncoded);
if (ECDSA.recover(hashed, signatureData) != nearBridgeDerivedAddress) {
    revert InvalidSignature();
}
```

No `omniBridgeChainId` is included. This is confirmed at lines 142–153 of `OmniBridge.sol`.

By contrast, `finTransfer` explicitly encodes `omniBridgeChainId` twice (lines 294 and 297), binding the signature to the specific chain. The asymmetry is intentional for `finTransfer` but absent for `deployToken`.

The NEAR MPC signing path is the constant `SIGN_PATH: &str = "bridge-1"` (`near/omni-bridge/src/lib.rs`, line 84), which is chain-agnostic. The `MetadataPayload` struct (`near/omni-types/src/lib.rs`, lines 694–702) contains no chain identifier field. Therefore, the same signature is cryptographically valid on every EVM chain simultaneously.

The Starknet `deploy_token` has the identical gap: it calls `payload.to_borsh()` without a chain ID argument (`starknet/src/omni_bridge.cairo`, line 205), while `fin_transfer` correctly calls `payload.to_borsh(self.omni_bridge_chain_id.read())` (line 252–254). `MetadataPayload::to_borsh` in `starknet/src/bridge_types.cairo` (lines 36–44) accepts no chain ID parameter.

The only existing guard against re-deployment is the `ERR_TOKEN_EXIST` check (lines 155–158 of `OmniBridge.sol`), which only prevents re-deployment on the **same** chain and does nothing to prevent cross-chain replay.

After a successful replay, `OmniBridgeWormhole::deployTokenExtension` (lines 48–70 of `OmniBridgeWormhole.sol`) publishes a Wormhole VAA containing `omniBridgeChainId` back to NEAR, causing NEAR to register the replayed token address as the canonical bridge token for that chain.

## Impact Explanation

This is a **Critical** authorization bypass. An attacker can perform a deployer-equivalent action — deploying a bridge token and registering it on NEAR — on any EVM chain without chain-specific NEAR authorization. Concretely:

1. NEAR registers the attacker-replayed token address as the canonical bridge token for the target chain, enabling `finTransfer` flows to it.
2. Any subsequent legitimate `deployToken` call for the same token on the target chain permanently reverts with `ERR_TOKEN_EXIST`, blocking authorized deployment at the intended address.
3. If the legitimate deployment was expected at a specific address (e.g., for protocol integrations), the attacker forces deployment at a different address (determined by the contract's nonce at replay time), breaking those integrations.

This matches the allowed impact class: **unauthorized deployer-equivalent action / authorization bypass** and **cross-chain replay / chain-domain separation flaw**.

## Likelihood Explanation

Exploitation requires only reading a confirmed `deployToken` transaction from any public block explorer and submitting the identical `(signatureData, metadata)` calldata to a different EVM chain's bridge contract. No privileged access, no private keys, no MEV infrastructure is required. Any public observer can perform this immediately after a legitimate deployment is confirmed on any chain. The only precondition is that the target chain's bridge contract is live and unpaused.

## Recommendation

Include `omniBridgeChainId` in the borsh-encoded payload verified in `deployToken`, mirroring the pattern already used in `finTransfer`:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
+   bytes1(omniBridgeChainId),
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
```

Apply the same fix to Starknet: add a `chain_id: u8` parameter to `MetadataPayload::to_borsh` and embed it in the encoding, then pass `self.omni_bridge_chain_id.read()` from `deploy_token`. Update the NEAR `MetadataPayload` struct and signing logic to include the destination chain ID before hashing.

## Proof of Concept

1. Observe a confirmed `deployToken(signatureData, metadata)` call on Ethereum mainnet (e.g., via Etherscan).
2. Submit the identical calldata to the Arbitrum `OmniBridgeWormhole` contract address.
3. Arbitrum computes `keccak256(borshEncoded)` with the same inputs (no chain ID), recovers the same `nearBridgeDerivedAddress`, and accepts the signature (lines 142–153 of `OmniBridge.sol`).
4. A `BridgeToken` proxy for `metadata.token` is deployed on Arbitrum; `isBridgeToken[proxy] = true`, `nearToEthToken[metadata.token] = proxy` are set (lines 190–192).
5. `OmniBridgeWormhole::deployTokenExtension` emits a Wormhole VAA containing Arbitrum's `omniBridgeChainId` and the new proxy address (lines 54–61 of `OmniBridgeWormhole.sol`); NEAR receives and registers the token for Arbitrum.
6. Any subsequent legitimate `deployToken` for the same `metadata.token` on Arbitrum reverts with `ERR_TOKEN_EXIST` (lines 155–158 of `OmniBridge.sol`), permanently blocking the authorized deployment.
