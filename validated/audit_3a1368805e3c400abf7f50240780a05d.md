Audit Report

## Title
Undetected `ft_transfer` Failure in `fin_transfer_send_tokens_callback` Causes Permanent Freezing of Bridged Funds — (File: `near/omni-bridge/src/lib.rs`)

## Summary

`fin_transfer_send_tokens_callback` delegates failure detection entirely to `is_refund_required(is_ft_transfer_call)`. When the token transfer uses a plain `ft_transfer` (empty `msg`), `is_ft_transfer_call` is `false` and `is_refund_required` unconditionally returns `false` without reading the promise result. If the token contract rejects the `ft_transfer`, the bridge still marks the transfer as permanently finalised, decrements `locked_tokens`, and emits `FinTransferEvent`, leaving the tokens irrecoverably stuck inside the bridge contract.

## Finding Description

`process_fin_transfer_to_near` performs three irreversible state mutations before dispatching `send_tokens`:

1. `add_fin_transfer` inserts the transfer ID into `finalised_transfers` (line 1875), preventing any replay.
2. `unlock_tokens_if_needed` decrements `locked_tokens` (lines 1881–1885).
3. `update_storage_balance` charges the relayer (line 1951).

`send_tokens` with an empty `msg` issues a plain `ft_transfer` (lines 2102–2106). The callback is chained with `is_ft_transfer_call = !msg.is_empty()` (line 1973), so it is `false` for the plain-transfer path.

Inside `fin_transfer_send_tokens_callback` (lines 1702–1746), the only branch that reverts state is guarded by `Self::is_refund_required(is_ft_transfer_call)`. `is_refund_required` (lines 1784–1804) reads the promise result only when `is_ft_transfer_call` is `true`; when it is `false`, it returns `false` unconditionally (lines 1800–1803) with the comment "Not ft_transfer_call: don't refund." NEAR always invokes the callback regardless of whether the predecessor promise succeeded or failed, so a failed `ft_transfer` silently falls through to the `else` branch, which emits `FinTransferEvent` and sends the fee — treating a failed delivery as a success.

`remove_fin_transfer` is called only inside the refund branch (line 1714). No public or admin function exists to remove a finalised transfer ID or re-credit `locked_tokens` after the fact, so the state corruption is permanent.

## Impact Explanation

When `ft_transfer` fails:
- The token contract reverts; tokens remain in the bridge's balance.
- The transfer ID is permanently consumed in `finalised_transfers`; the transfer cannot be replayed.
- `locked_tokens` is permanently decremented; bridge accounting is permanently wrong.
- No recovery path exists.

This constitutes **permanent freezing of bridged funds**, matching the Critical allowed impact: *"Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet, Bitcoin, Zcash, or Wormhole-routed flows."*

## Likelihood Explanation

NEAR hosts NEP-141 tokens with custom transfer restrictions (blacklists, pauses) — USDC-style tokens are a concrete example. Any such token registered with the bridge and locked on NEAR (via an outbound NEAR → EVM transfer) can trigger this path on the return leg (EVM → NEAR `fin_transfer`). The window between the storage-balance check (resolved in a prior receipt) and the `ft_transfer` execution (a subsequent receipt) is sufficient for a blacklisting event to occur. The token issuer blacklisting the recipient — a routine compliance action — is the realistic trigger. The relayer then calls `fin_transfer` with a valid proof, completing the exploit without any action from the bridge's own privileged roles.

## Recommendation

In `fin_transfer_send_tokens_callback`, explicitly check the promise result for the plain `ft_transfer` case. When `is_ft_transfer_call` is `false`, call `env::promise_result_checked(0, ...)` and treat `Err(_)` as a failure: invoke `revert_lock_actions`, `remove_fin_transfer`, and emit `FailedFinTransferEvent`, mirroring the existing refund path (lines 1703–1718). The `is_refund_required` helper should be extended (or replaced) to handle both cases, returning `true` on any promise failure regardless of transfer type.

## Proof of Concept

1. Deploy a NEP-141 token on NEAR with a blacklist (e.g., a USDC-style token). Register it with the Omni Bridge.
2. Bridge some amount to EVM: `init_transfer` locks tokens in the bridge and increments `locked_tokens`.
3. On EVM, initiate a return transfer back to NEAR targeting a specific NEAR recipient address.
4. Before the relayer submits `fin_transfer`, the token issuer blacklists the recipient on the NEAR token contract.
5. Relayer calls `fin_transfer` with a valid proof. `process_fin_transfer_to_near` executes:
   - `add_fin_transfer` inserts the transfer ID into `finalised_transfers`.
   - `unlock_tokens_if_needed` decrements `locked_tokens`.
   - `send_tokens` issues `ft_transfer(recipient, amount, None)` — the token contract panics (blacklisted); promise result is `Err`.
6. `fin_transfer_send_tokens_callback` is invoked with `is_ft_transfer_call = false`.
7. `is_refund_required(false)` returns `false`; the `else` branch fires, emitting `FinTransferEvent`.
8. Result: transfer ID permanently consumed, `locked_tokens` permanently decremented, tokens stuck in bridge, no recovery path.
