### Title
`checkPreferTheirsOverOurs` Uses Hardcoded Empty Peras Weight Snapshot, Causing Incorrect Chain Selection Disconnects - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

In `checkPreferTheirsOverOurs` inside the ChainSync client, the call to `preferAnchoredCandidate` is passed `emptyPerasWeightSnapshot` (a hardcoded zero-weight snapshot) instead of the actual live `PerasWeightSnapshot` from the ChainDB. This is structurally identical to the reported Dispenser bug: a weight-based comparison that should use the current, up-to-date weight state instead uses a zero/empty value, causing incorrect decisions in a security-critical path.

---

### Finding Description

When the ChainSync client receives a header that is beyond the forecast horizon, it cannot yet validate it. It calls `readLedgerState`, which in turn calls `checkPreferTheirsOverOurs` to decide whether to stay connected to the peer or disconnect. The logic is: if the candidate chain is not preferred over our current chain, we will never adopt it, so disconnect.

The relevant code in `readLedgerStateHelper`:

```haskell
case prj lst of
  Nothing -> do
    checkPreferTheirsOverOurs kis'
    retry
  Just ledgerView ->
    return $ return $ Intersects kis' ledgerView
```

And `checkPreferTheirsOverOurs`:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- <-- hardcoded zero weights
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse ...
```

The `emptyPerasWeightSnapshot` is `PerasWeightSnapshot Map.empty` — it contains no Peras vote boosts at all. When `isEmptyPerasWeightSnapshot weights = True`, `preferAnchoredCandidate` falls back to the pure longest-chain (block-number) rule, completely ignoring any Peras certificate boosts.

By contrast, every other call site that performs chain comparison reads the actual live snapshot from the ChainDB. For example, `readChainComparison` in `BlockFetch/ClientInterface.hs` does:

```haskell
readChainComparison =
  fmap mkChainComparison <$> getPerasWeightSnapshot chainDB
```

And the GSM in `NodeKernel.hs` does:

```haskell
GSM.getCandidateOverSelection = do
  weights <- ChainDB.getPerasWeightSnapshot chainDB
  pure $ \(headers, _lst) state -> ...
    preferAnchoredCandidate (configBlock cfg) (forgetFingerprint weights) ...
```

The `getPerasWeightSnapshot` API is available as an `STM` action on the `ChainDB`, so it is accessible inside the `STM` block where `checkPreferTheirsOverOurs` runs.

---

### Impact Explanation

When Peras is active and certificates have boosted blocks on the canonical chain, the following scenario causes a chain selection safety failure:

1. The node's current chain has a higher raw block number (more blocks) but lower Peras-weighted total than the canonical chain.
2. A peer offers the canonical (Peras-heavier) chain, but its headers are beyond the forecast horizon.
3. `checkPreferTheirsOverOurs` compares using `emptyPerasWeightSnapshot`, so it sees only block numbers. Our chain has more blocks → `shouldSwitch = False` → the node throws `CandidateTooSparse` and **disconnects from the peer offering the canonical chain**.
4. The node remains on its non-canonical chain.

If an adversary can keep the node's current chain ahead in raw block count while the canonical chain is ahead in Peras weight, the node will persistently disconnect from every peer offering the canonical chain, causing a durable chain selection safety failure: the node prefers a non-canonical, less-secure chain.

This matches the **High** impact category: a chain selection bug that lets an honest node prefer a non-canonical chain beyond the intended security assumptions.

---

### Likelihood Explanation

- Peras is an active protocol extension in this codebase with full infrastructure for vote/certificate tracking and weight snapshots.
- The scenario (canonical chain is Peras-heavier but shorter in raw blocks) is a normal operating condition when Peras certificates boost a fork that has fewer blocks.
- The entry path is fully externally reachable: any peer can send headers beyond the forecast horizon, triggering this code path.
- The `TODO` comment in the code (`-- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64`) confirms the developers are aware this check is problematic under Peras, but the code is still present and active.

---

### Recommendation

Replace the hardcoded `emptyPerasWeightSnapshot` with a live read of the actual `PerasWeightSnapshot` from the ChainDB. Since `checkPreferTheirsOverOurs` already runs inside an `STM` block, the fix is to read `getPerasWeightSnapshot` (which is an `STM m` action) and pass the result to `preferAnchoredCandidate`:

```haskell
checkPreferTheirsOverOurs kis = do
  WithFingerprint weights _ <- getPerasWeightSnapshot  -- read live snapshot
  if shouldSwitch $
       preferAnchoredCandidate (configBlock cfg) weights ourFrag theirFrag
    then pure ()
    else throwSTM $ CandidateTooSparse ...
```

Alternatively, if the intent of the linked issue is to remove this check entirely (since it is a Genesis-era check that may be superseded by Peras chain selection), the check should be removed rather than left in a broken state.

---

### Proof of Concept

**Setup**: Peras is active. Certificates have boosted blocks B1, B2 on the canonical chain C. An alternative chain A has more raw blocks (higher block number) but no Peras boosts, so `totalWeight(A) < totalWeight(C)`.

**Trigger**:
1. Node's current selection is chain A (e.g., it was syncing from an adversarial peer).
2. An honest peer P sends headers for chain C. The tip of C is beyond the forecast horizon.
3. `readLedgerState` is called; `prj lst = Nothing` (forecast horizon exceeded).
4. `checkPreferTheirsOverOurs` is called with `emptyPerasWeightSnapshot`.
5. `preferAnchoredCandidate ... emptyPerasWeightSnapshot ourFrag theirFrag` compares block numbers only. Chain A has more blocks → `shouldSwitch = False`.
6. `throwSTM CandidateTooSparse` → node disconnects from honest peer P.
7. Node remains on non-canonical chain A.
