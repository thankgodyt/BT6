### Title
Unguarded `sign_index` Bounds Access Causes Publicly-Reachable Panic in `sign_btc_transaction` - (`contracts/satoshi-bridge/src/chain_signature.rs`)

---

### Summary

`sign_btc_transaction` is a public, unpermissioned entrypoint. It passes the caller-supplied `sign_index` directly into `btc_pending_info.signatures[sign_index]` without a bounds check. Any caller who supplies an out-of-bounds index against a valid pending ID causes a Rust index-out-of-bounds panic, aborting the transaction. The claimed "block-wide bridge halt" is incorrect for NEAR (each transaction is independent), but the panic itself is a real, publicly-reachable invariant violation in a production bridge path.

---

### Finding Description

`sign_btc_transaction` in `contracts/satoshi-bridge/src/api/chain_signatures.rs` carries no caller-identity check — any account may call it with any `btc_pending_sign_id` and any `sign_index`. [1](#0-0) 

It delegates immediately to `internal_sign_btc_transaction`, which performs:

```rust
require!(
    btc_pending_info.signatures[sign_index].is_none(),
    "Already signed"
);
``` [2](#0-1) 

In Rust, `Vec::index` panics unconditionally when `sign_index >= len`. The `require!` condition is never evaluated — the panic fires first. `signatures` is initialized as `vec![None; psbt.get_input_num()]`, so its length equals the number of PSBT inputs (typically 1–3 for bridge transactions). [3](#0-2) 

The same unguarded pattern appears again at line 98 (`vutxos[sign_index]`) and in `sign_btc_transaction_callback` at lines 149 and 155, though the callback is `#[private]`. [4](#0-3) 

Valid pending IDs are fully enumerable by any observer via the public view function `get_btc_pending_infos_paged`. [5](#0-4) 

---

### Impact Explanation

**Actual impact (Low):** Each NEAR transaction executes independently. A panic in one transaction reverts only that transaction; it does not block other transactions in the same block or any subsequent block. The attacker's own transaction fails and their gas is consumed. No contract state is mutated, no funds are at risk, and no legitimate signing operation is disrupted. The impact is a publicly-reachable invariant violation (a public entrypoint panics on attacker-supplied input rather than returning a graceful error), matching the Low tier: *"Publicly reachable invariant-violation or panic-driven fault in production bridge/token paths without direct theft."*

**Overclaimed impact:** The question's assertion that this "temporarily blocks all bridge operations in that NEAR block" is incorrect. NEAR's transaction model provides no such cross-transaction blocking.

---

### Likelihood Explanation

Trivially reachable: enumerate pending IDs via `get_btc_pending_infos_paged`, then call `sign_btc_transaction(id, 999, 0)`. No privileged role, no special setup, no cost beyond gas.

---

### Recommendation

Add an explicit bounds check before the index access in `internal_sign_btc_transaction`:

```rust
require!(
    sign_index < btc_pending_info.signatures.len(),
    "sign_index out of range"
);
require!(
    btc_pending_info.signatures[sign_index].is_none(),
    "Already signed"
);
```

Apply the same guard before `vutxos[sign_index]` on line 98 and in `sign_btc_transaction_callback` before lines 149 and 155. [6](#0-5) 

---

### Proof of Concept

```
1. Call get_btc_pending_infos_paged() → obtain any valid btc_pending_sign_id
   (e.g. a pending refund with signatures.len() == 1)

2. Call sign_btc_transaction(
       btc_pending_sign_id = "<valid_id>",
       sign_index = 999,
       key_version = 0
   ) with any attached deposit ≥ 1 yoctoNEAR

3. Execution path:
   sign_btc_transaction (api/chain_signatures.rs:21)
     → assert_pending_sign() passes
     → internal_sign_btc_transaction (chain_signature.rs:76)
         → btc_pending_info.signatures[999]  ← PANIC: index out of bounds

4. Transaction reverts. No state change. Attacker's gas consumed.
   All other in-flight bridge transactions are unaffected.
```

    pub fn get_btc_pending_infos_paged(
        &self,
        from_index: Option<usize>,
        limit: Option<usize>,
    ) -> HashMap<String, BTCPendingInfo> {
        let len = usize::try_from(self.data().btc_pending_infos.len())
            .unwrap_or_else(|_| env::panic_str("Too many btc_pending_infos"));
        let skip_n = from_index.unwrap_or(0);
        let take_n = limit.unwrap_or(len - skip_n);
        self.data()
            .btc_pending_infos
            .iter()
            .skip(skip_n)
            .take(take_n)
            .map(|(k, v)| (k.clone(), v.into()))
            .collect()
    }
