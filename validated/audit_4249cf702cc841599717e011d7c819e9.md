### Title
Peras Certificate Validation Is a No-Op Stub, Enabling Unauthorized Certificate Acceptance and Chain-Selection Weight Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` function is a stub that unconditionally returns `Right` (success) for every inbound certificate, performing zero cryptographic or semantic checks. Because this universal instance is wired into the production certificate-ingestion path, any unprivileged peer can inject arbitrary Peras certificates that are accepted without verification and used to inflate chain-selection weights, potentially causing a node to prefer a non-canonical chain.

---

### Finding Description

**Root cause — stub validation in the universal `BlockSupportsPeras` instance**

`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs` defines a single universal instance that covers every block type:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

The function ignores every field of the certificate — round number, boosted-block point, voter bitmap, and the BLS aggregate signature — and unconditionally promotes the input to a `ValidatedPerasCert` carrying the full `perasWeight` boost. No more-specific instance exists for Cardano blocks; this stub is the only implementation.

**Production ingestion path**

`makePerasCertPoolWriterFromChainDB` wires this stub directly into the live certificate-diffusion pipeline:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)   -- ← stub called here
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

`processCerts` partitions the results of `validateCert` and, when all certificates pass (which they always do with the stub), adds every one to the `PerasCertDB` and triggers chain selection: [3](#0-2) 

**Chain-selection consequence**

Accepted certificates are stored in `PerasCertDB` and read back as a `PerasWeightSnapshot`. Chain selection uses `WeightedSelectView`, which adds the certificate boost to the block number when comparing candidate fragments:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [4](#0-3) 

A forged certificate boosting an adversarial block therefore directly shifts the outcome of `preferCandidate`, making the node switch to a heavier-looking but non-canonical chain.

The `PerasCertDB` implementation also carries an explicit note that its `implAddCert` method still lacks non-trivial validation logic: [5](#0-4)

### Impact Explanation

**Vulnerability class:** Bypass of Peras certificate verification that enables unauthorized certificate acceptance — matching the "Critical: bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance" criterion.

When Peras is enabled, an unprivileged peer can:

1. Craft a `PerasCert` naming any `pcCertRound` and any `pcCertBoostedBlock` (no signature required).
2. Deliver it via the object-diffusion mini-protocol.
3. The node accepts it unconditionally, stores it, and re-runs chain selection.
4. The boosted block's `wsvTotalWeight` is inflated by `perasWeight`, potentially exceeding the honest chain's weight.
5. The node switches to the adversarial chain, violating consensus safety.

This is the direct analog of the DeFi "no incentive for liquidation" class: a critical enforcement mechanism (`validatePerasCert`) exists in the type-class interface but its implementation is a no-op stub, so the protocol relies entirely on the assumption that no adversarial peer will ever send a certificate — an assumption that cannot hold in a public network.

---

### Likelihood Explanation

The object-diffusion protocol is reachable by any connected peer without special privileges. When Peras is enabled (via `rnFeatureFlags`), exploitation requires only the ability to open a connection and send a well-formed CBOR-encoded `PerasCert` message. No key material, stake, or operator access is needed. The CHANGELOG confirms the code path is live and integrated with chain selection.

---

### Recommendation

Replace the stub with a real implementation of `validatePerasCert` that:

1. Verifies the BLS aggregate signature (`pcSignature`) against the aggregated public keys of the claimed voters.
2. Checks each voter's committee eligibility (seat index, VRF eligibility proof).
3. Validates that `pcCertRound` is within the expected window relative to the current chain tip.
4. Confirms that `pcCertBoostedBlock` refers to a block that is a plausible candidate (e.g., on a known chain fragment).

Until the full implementation is ready, the Peras feature flag should remain disabled in all production deployments, and the stub should be guarded so it cannot be reached when Peras is off.

### Proof of Concept

```
Attacker (unprivileged peer) connects to a Peras-enabled node.

1. Craft a PerasCert:
     pcCertRound      = <current round>
     pcCertBoostedBlock = <hash of adversarial block B>
     pcVoters         = <any bitmap>
     pcSignature      = <any bytes — never checked>

2. Send the cert via the Peras object-diffusion mini-protocol.

3. Node calls:
     processCerts ... (validatePerasCert mkPerasParams) ...
   validatePerasCert returns Right unconditionally.

4. Cert is stored in PerasCertDB; PerasWeightSnapshot updated.

5. Next chain-selection run computes:
     wsvTotalWeight(B's fragment) = blockNo(B) + perasWeight
   If perasWeight > (honest tip blockNo - B's blockNo),
   the node switches to the adversarial chain containing B.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
