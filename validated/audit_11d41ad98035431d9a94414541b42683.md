### Title
`checkPreferTheirsOverOurs` Uses `emptyPerasWeightSnapshot`, Ignoring Peras Weight Boosts in Forecast-Horizon Disconnection Guard - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

The `checkPreferTheirsOverOurs` function in the ChainSync client evaluates whether a candidate chain is preferable to the local selection when a peer's header is beyond the forecast horizon. It calls `preferAnchoredCandidate` with a hardcoded `emptyPerasWeightSnapshot` instead of the live `PerasWeightSnapshot` from the `PerasCertDB`. This mirrors the DeFi vault bug's root cause: a decision about one component (candidate vs. current chain) is made without accounting for state held in a separate component (Peras certificate weight boosts).

---

### Finding Description

In `readLedgerStateHelper`, when `prj lst` returns `Nothing` (the peer's header is beyond the forecast horizon), the code calls `checkPreferTheirsOverOurs` before retrying:

```haskell
case prj lst of
  Nothing -> do
    checkPreferTheirsOverOurs kis'
    retry
  Just ledgerView ->
    return $ return $ Intersects kis' ledgerView
```

`checkPreferTheirsOverOurs` decides whether to disconnect (`CandidateTooSparse`) or continue tracking:

```haskell
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← hardcoded empty, ignores PerasCertDB
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
``` [1](#0-0) 

The actual Peras weight snapshot is available in the same STM context via `Query.getPerasWeightSnapshot cdb`, and is correctly used in every other chain-selection call site:

```haskell
-- chainSelectionForBlock:
(invalid, curChain, weights) <- atomically $
  (,,) <$> ...
       <*> Query.getCurrentChain cdb
       <*> (forgetFingerprint <$> Query.getPerasWeightSnapshot cdb)
``` [2](#0-1) 

`preferAnchoredCandidate` with a non-empty snapshot computes total weight as `blockNo + weightBoost` over the suffix after the intersection:

```haskell
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      -- purely block-number comparison
      ...
  | otherwise =
      case AF.intersect ours cand of
        Just (_, _, oursSuffix, candSuffix) ->
          preferCandidate cfg
            (weightedSelectView cfg weights oursSuffix)
            (weightedSelectView cfg weights candSuffix)
``` [3](#0-2) 

With `emptyPerasWeightSnapshot`, the comparison degenerates to a pure block-count comparison, ignoring all Peras certificate boosts recorded in the `PerasCertDB`. [4](#0-3) 

---

### Impact Explanation

**False-positive disconnection (primary security impact):** Suppose the local chain has `N` blocks and a Peras certificate boosts one of them by weight `W > 0`, giving total weight `N + W`. A peer offers a candidate chain with `N` blocks (equal count) but no boosts, total weight `N`. With actual weights, `preferAnchoredCandidate` returns `ShouldNotSwitch` for the candidate (correct: we should not switch), so `checkPreferTheirsOverOurs` would also return `ShouldNotSwitch` and disconnect. But now consider the reverse: the peer's chain has `N` blocks with a Peras boost `W'`, total weight `N + W'`, while our chain has `N` blocks and no boosts. With actual weights, `ShouldSwitch` → continue tracking (correct). With `emptyPerasWeightSnapshot`, if their block count equals ours, `ShouldNotSwitch` → disconnect. The node disconnects from a peer offering the heavier (canonical) chain and never adopts it.

**False-negative disconnection (secondary impact):** A peer offers a chain with `N+1` blocks but no boosts, total weight `N+1`. Our chain has `N` blocks with boost `W > 1`, total weight `N + W > N + 1`. With actual weights, `ShouldNotSwitch` → disconnect (correct). With `emptyPerasWeightSnapshot`, `ShouldSwitch` (N+1 > N) → continue tracking. The node wastes resources tracking a chain it will never adopt, and the Genesis Density Disconnection logic may be confused about which peers to keep.

The false-positive disconnection case directly matches the allowed impact class: **chain selection bug that lets an unprivileged peer (or the absence of one) cause an honest node to prefer a non-canonical or less-secure chain** — specifically, by causing the node to sever the connection to the peer serving the heavier canonical chain before the forecast horizon advances.

---

### Likelihood Explanation

Peras is under active development in this codebase (the `PerasCertDB`, `PerasWeightSnapshot`, and `addPerasCertAsync` infrastructure are all present and wired into `ChainSel`). The bug is reachable whenever:

1. Peras is enabled and at least one certificate has been received (non-empty `PerasWeightSnapshot`).
2. A peer sends a header whose slot is beyond the local forecast horizon (`OutsideForecastRange`).
3. The weight comparison outcome differs between the empty and actual snapshots.

Condition 2 is a normal occurrence during syncing and when a peer is slightly ahead. Condition 3 is guaranteed whenever any Peras certificate exists. The developers have already flagged this code path with a `TODO` referencing issue `cardano-peras#64`, confirming awareness of the problem. [5](#0-4) 

---

### Recommendation

Replace `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live snapshot read atomically from `PerasCertDB`:

```haskell
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis = do
  weights <- forgetFingerprint <$> getPerasWeightSnapshot chainDbView
  if shouldSwitch $ preferAnchoredCandidate (configBlock cfg) weights ourFrag theirFrag
    then pure ()
    else throwSTM $ CandidateTooSparse ...
```

This is consistent with how every other call site in `ChainSel.hs` obtains the weight snapshot. Alternatively, if the check is to be removed entirely (as the TODO suggests), remove it promptly to avoid the window of incorrect behavior.

### Proof of Concept

**Setup:**
- Peras is enabled; `perasWeight = 2`.
- Local chain: blocks `[B1, B2]`, `B2` is boosted by a certificate → total weight = `2 + 2 = 4`.
- Peer's candidate chain: blocks `[B1, B2', B3']` (3 blocks, no boosts) → total weight = `3`.
- Peer's header `B3'` is beyond the local forecast horizon.

**With actual weights (`PerasWeightSnapshot {B2 → 2}`):**
- `weightedSelectView` of our suffix after intersection: weight = `2 (blocks) + 2 (boost) = 4`.
- `weightedSelectView` of their suffix: weight = `3 (blocks) + 0 = 3`.
- `preferCandidate`: `3 < 4` → `ShouldNotSwitch` → `checkPreferTheirsOverOurs` throws `CandidateTooSparse` → correct disconnect.

**With `emptyPerasWeightSnapshot` (current code):**
- Comparison degenerates to block count: their `3 > our 2` → `ShouldSwitch` → `pure ()` → no disconnect.
- The node continues tracking a candidate with total weight 3 against our weight 4, wasting resources and potentially delaying adoption of the true canonical chain.

**Reverse scenario (false-positive disconnect):**
- Local chain: `[B1, B2]`, no boosts, weight = 2.
- Peer's chain: `[B1, B2']`, `B2'` boosted → weight = `2 + 2 = 4`.
- With actual weights: `ShouldSwitch` → continue tracking (correct).
- With `emptyPerasWeightSnapshot`: block counts equal → `ShouldNotSwitch` → `CandidateTooSparse` thrown → node disconnects from the peer serving the heavier canonical chain.

        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"
        Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
          case preferCandidate
            (projectChainOrderConfig cfg)
