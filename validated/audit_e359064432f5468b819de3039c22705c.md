Audit Report

## Title
Detached Burn Promise in `init_transfer_internal` Allows `InitTransferEvent` Emission Without Confirmed Token Destruction - (File: near/omni-bridge/src/lib.rs)

## Summary

`burn_tokens_if_needed` schedules the cross-contract `burn` call with `.detach()`, discarding the promise result entirely. `init_transfer_internal` then unconditionally emits `InitTransferEvent` on the next line. Because NEAR executes the burn receipt asynchronously in a future block, the event is logged and observable by relayers before the burn ever executes. If the burn receipt fails for any reason, the destination chain mints tokens against an event that was never backed by an actual token destruction, inflating cross-chain supply.

## Finding Description

`burn_tokens_if_needed` at lines 1806–1813 of `near/omni-bridge/src/lib.rs`:

```rust
fn burn_tokens_if_needed(&self, token: AccountId, amount: U128) {
    if self.is_deployed_token(&token) {
        ext_token::ext(token)
            .with_static_gas(BURN_TOKEN_GAS)
            .burn(amount)
            .detach();   // result is never observed
    }
}
```

`init_transfer_internal` at lines 1850–1863 calls this and immediately emits the event:

```rust
if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
    self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
    self.lock_tokens_if_needed(...);
}
// ...
env::log_str(&OmniBridgeEvent::InitTransferEvent { transfer_message }.to_log_string());
```

The NEAR runtime schedules the burn as a separate receipt executed in a subsequent block. The enclosing `ft_on_transfer` transaction — including the `InitTransferEvent` log — completes and is finalized before the burn receipt is ever processed. There is no callback, no guard, and no rollback path: if the burn receipt fails, the event has already been emitted and is irrevocable.

The same detached-burn pattern appears in `fin_transfer_send_tokens_callback` (lines 1700–1718) for the failed-inbound-transfer refund path, where a failed burn leaves minted tokens in the bridge's balance with no cleanup.

Existing guards (storage balance checks, transfer message deduplication) operate entirely within the synchronous portion of the call and do not protect against asynchronous burn failure.

## Impact Explanation

This directly enables unauthorized cross-chain token minting and permanent supply inflation — a Critical impact under the allowed scope. Concretely:

1. User calls `ft_transfer_call` on a deployed bridge token, transferring `amount` to the bridge.
2. Bridge emits `InitTransferEvent` unconditionally.
3. Burn receipt fails silently (detached — no callback, no revert of the event).
4. Relayer observes the event and submits proof to the destination chain.
5. Destination chain mints `amount` tokens to the recipient.
6. Bridge still holds `amount` of the deployed token (un-burned).

Result: `amount` tokens exist on the destination chain **and** `amount` tokens remain in the bridge on NEAR — total cross-chain supply is doubled. This is unauthorized minting and balance manipulation matching the Critical impact class.

## Likelihood Explanation

The entry path (`ft_transfer_call` on any deployed bridge token) is fully unprivileged — any token holder can trigger it. Burn failure can occur via:

- **Gas exhaustion**: `BURN_TOKEN_GAS` is a fixed static constant. Any upgrade to `OmniToken` that increases the gas cost of `burn` beyond this constant causes every subsequent outbound transfer for that token to silently fail the burn while the event is already emitted.
- **Token contract panic**: An arithmetic overflow (with `overflow-checks = true`), storage inconsistency, or any unexpected panic in `OmniToken.burn` causes the receipt to fail with no observable effect on the already-emitted event.
- **Token paused**: If the deployed token has a pause mechanism and is paused between the `ft_transfer_call` execution and the burn receipt execution, the burn reverts while the event stands.

The gas exhaustion scenario is particularly concerning because it is systematic: once `BURN_TOKEN_GAS` becomes insufficient (e.g., after a token upgrade), every outbound transfer for that token inflates supply until the constant is corrected.

## Recommendation

Replace the fire-and-forget pattern with a chained promise and callback:

1. In `init_transfer_internal`, when the token is a deployed token, return a `Promise` that chains the burn call to a new `#[private]` callback (e.g., `init_transfer_burn_callback`).
2. In `init_transfer_burn_callback`, inspect `env::promise_result(0)`. Only emit `InitTransferEvent` if the burn succeeded. On failure, refund the user (return the amount via `ft_on_transfer`'s return value or a separate `ft_transfer`) and remove the pending transfer message.
3. This mirrors the existing `fin_transfer` → `fin_transfer_send_tokens_callback` pattern already used for inbound flows.

Additionally, audit `fin_transfer_send_tokens_callback`'s detached burn (lines 1703–1710) under the same fix, ensuring minted-but-rejected tokens are verifiably destroyed before `FailedFinTransferEvent` is emitted.

## Proof of Concept

```
1. Deploy a bridged OmniToken T registered in bridge's `deployed_tokens`.
2. Arrange for T's burn receipt to fail:
     Option A – gas: set BURN_TOKEN_GAS below T's actual burn cost (simulate via
                token upgrade that adds storage writes to burn).
     Option B – pause: pause T between ft_transfer_call execution and burn receipt.
3. Call ft_transfer_call(bridge, amount, init_transfer_msg) on T as any token holder.
4. Observe init_transfer_internal executes:
     - burn_tokens_if_needed fires detached burn receipt (will fail)
     - InitTransferEvent is emitted and finalized on NEAR
5. Burn receipt executes in next block and fails silently (no callback).
6. Relayer observes InitTransferEvent, submits proof to destination chain.
7. Destination chain mints `amount` tokens to recipient.
8. Bridge still holds `amount` of T (un-burned).
   Cross-chain supply is now 2×amount instead of amount.

Invariant test: assert that after any ft_transfer_call sequence where the burn
receipt fails, the sum of (bridge balance of T on NEAR) + (total supply of T on
destination) equals the pre-transfer total supply. This invariant will be violated.
```
