### Title
Peras Vote and Certificate Cryptographic Validation Bypass — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The default `BlockSupportsPeras` instance ships two stub validation functions that skip all cryptographic checks. `validatePerasCert` unconditionally returns `Right` for every certificate, and `validatePerasVote` only checks stake-distribution membership without verifying the BLS vote signature or VRF eligibility proof. Both functions are wired into the live node's object-diffusion layer via `processCerts` / `processVotes`, so any unprivileged peer can inject structurally well-formed but cryptographically invalid votes and certificates that the node accepts and stores, enabling unauthorized Peras weight boosts that distort chain selection.

### Finding Description

**Root cause — `validatePerasCert` always returns `Right`** [1](#0-0) 

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

No BLS aggregate-signature verification is performed. Every inbound `PerasCert`, regardless of cryptographic validity, is wrapped in `ValidatedPerasCert` and returned as `Right`.

**Root cause — `validatePerasVote` skips signature and eligibility-proof checks** [2](#0-1) 

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
```

The check is limited to a stake-distribution lookup on the voter ID. The `pvSignature` (BLS vote signature) and `pvEligibilityProof` (VRF proof for non-persistent committee members) fields defined in `PerasVote.V1` are never verified. [3](#0-2) 

**Production call path**

`validatePerasCert` is called directly from `processCerts` inside `makePerasCertPoolWriterFromChainDB`: [4](#0-3) 

`validatePerasVote` is called from `processVotes` inside `makePerasVotePoolWriterFromChainDB`: [5](#0-4) 

Both writers are part of the live node's object-diffusion layer and are reachable from any connected peer. Accepted objects are added to the ChainDB: [6](#0-5) 

**Chain-selection consequence**

Accepted `ValidatedPerasVote` objects feed `votesReachQuorum`, which checks only total stake against the quorum threshold — not cryptographic validity: [7](#0-6) 

Once quorum is reached, a `ValidatedPerasCert` is forged and stored. Accepted `ValidatedPerasCert` objects carry `vpcCertBoost = perasWeight params`, the full Peras weight boost, which is applied during chain selection to prefer the boosted block over competing candidates.

### Impact Explanation

An unprivileged peer can:
1. Enumerate the public stake distribution to identify voter IDs with sufficient combined stake.
2. Craft `PerasVote` objects carrying those voter IDs with arbitrary (invalid) BLS signatures and VRF proofs.
3. Send the batch; `validatePerasVote` accepts each vote because only the stake-distribution lookup succeeds.
4. Once the fake votes' combined stake exceeds the quorum threshold, `votesReachQuorum` triggers certificate creation.
5. The resulting `ValidatedPerasCert` is stored in the ChainDB and applies the full Peras weight boost to an attacker-chosen block.
6. Alternatively, the attacker sends a crafted `PerasCert` directly; `validatePerasCert` accepts it unconditionally.

This constitutes a **bypass of Peras voting and certificate checks that enables unauthorized certificate acceptance and chain-weight manipulation**, matching the "Critical" scope item: *Bypass of … PBFT/Praos/TPraos/Peras voting or certificate checks … that enables unauthorized … vote, or certificate acceptance.*

### Likelihood Explanation

The stake distribution is public on-chain data. Constructing a structurally valid `PerasVote` with a known voter ID but a garbage BLS signature requires no privileged access and no cryptographic break — the signature field is simply not checked. The object-diffusion mini-protocol is open to any peer. The attack is deterministic and requires only knowledge of the public stake distribution and the ability to connect to the node.

### Recommendation

Replace the stub implementations with full cryptographic validation:

- **`validatePerasCert`**: verify the BLS aggregate signature in `pcSignature` against the aggregate public key derived from `pcVoters`, the round number, and the boosted-block hash.
- **`validatePerasVote`**: after the stake-distribution lookup, verify `pvSignature` (BLS vote signature) against the voter's public key, and for `NonPersistentPerasVoteEligibilityProof`, verify the VRF output in `pvEligibilityProof`.

The concrete V1 types already carry all necessary fields: [8](#0-7) [3](#0-2) 

The referenced GitHub issue (`cardano-peras#120`) tracks this gap; it should be resolved before Peras weight boosts are applied in chain selection on any network where the object-diffusion layer is active.

### Proof of Concept

1. Connect to a node as an unprivileged peer via the object-diffusion mini-protocol.
2. Read the current Peras stake distribution (public on-chain data) to identify voter IDs whose combined stake exceeds the quorum threshold.
3. Construct a list of `PerasVote` objects: set `pvVoteRound` to the current round, `pvVoteBlock` to the target block's point, `pvVoterId` to the chosen voter IDs, and `pvSignature` to any byte string of the correct length (signature is not checked).
4. Send the batch to `processVotes`; each vote passes `validatePerasVote` because `lookupPerasVoteStake` succeeds on the valid voter IDs.
5. `votesReachQuorum` fires; `forgePerasCert` produces a `ValidatedPerasCert` for the target block.
6. The certificate is stored in the ChainDB with `vpcCertBoost = perasWeight params`.
7. Chain selection now applies the full Peras weight boost to the attacker-chosen block, causing the node to prefer it over the honest canonical chain.

```haskell
-- It returns 'Nothing' if either of these conditions is not met.
votesReachQuorum ::
  StandardHash blk =>
  PerasCfg blk ->
  [ValidatedPerasVote blk] ->
  Maybe (ValidatedPerasVotesWithQuorum blk)
votesReachQuorum cfg votes =
  case votes of
    -- We need at least one vote to determine who these votes are for, so we
    -- can't vacuously reach a quorum, even if the quorum threshold is 0.
    [] -> Nothing
    -- If we have at least one vote, we must check that all votes are for the
    -- same target, and that their total stake of is above the quorum threshold.
    (v0 : vs)
      | not (allVotesMatchTarget v0 vs) ->
          Nothing
      | not votesHaveEnoughStake ->
          Nothing
      | otherwise ->
          Just
            ValidatedPerasVotesWithQuorum
              { vpvqTarget = getPerasVoteTarget v0
              , vpvqVotes = v0 :| vs
              , vpvqPerasCfg = cfg
              }
 where
  totalVoteStake =
    mconcat (vpvVoteStake <$> votes)
  votesHaveEnoughStake =
    stakeAboveThreshold cfg totalVoteStake
```

```haskell
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
```
