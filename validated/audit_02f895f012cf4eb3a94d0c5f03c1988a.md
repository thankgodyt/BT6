### Title
Peras Vote Validation Accepts Votes for Arbitrary Rounds Without Current-Round Check - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasVote` function used to validate all inbound Peras votes from peers does not check whether the vote's round number matches the current Peras round. As a result, an unprivileged peer can inject votes for any arbitrary round — past or future — directly into the local node's `PerasVoteDB`, bypassing the temporal boundary that defines a valid voting window. This is the direct analog of the external report's "voting allowed after voting period end" vulnerability.

---

### Finding Description

The inbound vote processing pipeline is:

1. A peer sends votes via the object-diffusion mini-protocol.
2. `processVotes` in `PerasVote.hs` is called, which calls `validatePerasVote` for each vote.
3. `validatePerasVote` (the only validation gate) checks only whether the voter ID appears in the stake distribution.
4. Validated votes are timestamped and stored in the `PerasVoteDB` via `implAddVote`, which calls `updatePerasRoundVoteStates` — creating a fresh round-vote-state for any round number if one does not already exist.
5. If the accumulated stake for any round/target crosses the quorum threshold, a certificate is forged immediately.

The `validatePerasVote` stub:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
```

There is no check that `pvVoteRound vote` equals the current Peras round. The `isPerasVotingAllowed` / `perasVotingRules` (VR-1A, VR-1B, VR-2A, VR-2B) are only consulted by the local node when deciding whether to cast its *own* vote; they are never applied to votes received from peers.

### Impact Explanation

**Unauthorized vote acceptance for arbitrary rounds (Critical — Bypass of Peras voting checks).**

- **Future-round vote pre-loading**: A committee member (whose voter ID is in the stake distribution) can send votes for a round that has not yet started. These votes are stored and counted immediately. When the round actually begins, the attacker's pre-cast votes are already in the tally. With knowledge of the current vote state, the attacker can strategically pre-load votes to steer the quorum outcome toward a preferred block, undermining the fairness and integrity of the Peras boosting mechanism.

- **Stale-round certificate forging**: After the `PerasVoteDB` garbage-collects a past round, an attacker can re-inject votes for that round. If enough stake is accumulated (e.g., by replaying votes from multiple committee members whose IDs remain in the stake distribution), a certificate can be forged for a round that has already concluded, introducing a spurious boost that corrupts chain selection.

Both scenarios directly compromise the Peras protocol's certificate/vote integrity guarantees.

---

### Likelihood Explanation

Any peer connected via the object-diffusion mini-protocol can send crafted `PerasVote` objects with an arbitrary `pvVoteRound` field. The only barrier is that the `pvVoteVoterId` must appear in the current stake distribution. Since stake distributions are public, an attacker who controls even one legitimate committee seat (or can observe the distribution) can exploit this. The attack requires no key compromise, no admin access, and no majority stake. [5](#0-4) 

---

### Recommendation

Add a round-currency check inside `validatePerasVote` (or at the `processVotes` boundary) that rejects any vote whose `pvVoteRound` does not equal the current Peras round derived from the current slot. Concretely:

1. Pass the current `PerasRoundNo` (derived from the current slot via `slotToPerasRoundNo`) into `validatePerasVote` or `processVotes`.
2. Reject votes where `pvVoteRound vote /= currentRound` with a dedicated `PerasValidationErr` variant (e.g., `VoteForWrongRound`).
3. Apply the same check in `implAddVote` as a defense-in-depth guard.

This mirrors the fix described in the external report: check the temporal boundary *before* recording the vote, not after. [6](#0-5) [7](#0-6) 

---

### Proof of Concept

**Setup**: A private testnet running Peras-enabled nodes. The attacker controls one pool whose ID appears in the stake distribution.

**Steps**:

1. Observe the current Peras round `R` and the current vote tally for round `R+1` (future round).
2. Craft a `PerasVote` with `pvVoteRound = R+1` and `pvVoteBlock` set to the attacker's preferred block, signed with the attacker's pool key.
3. Send this vote to a target node via the object-diffusion mini-protocol.
4. `processVotes` calls `validatePerasVote mkPerasParams sd vote`. Since the voter ID is in the stake distribution, the vote passes validation.
5. The vote is stored in `PerasVoteDB` under round `R+1` via `updatePerasRoundVoteStates`, creating a fresh `PerasRoundVoteState` for that round.
6. When round `R+1` actually begins, the attacker's vote is already counted. If the attacker's stake is sufficient to tip the quorum, the certificate is forged for the attacker's preferred block before honest votes arrive. [8](#0-7) [9](#0-8)

  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)

updatePerasRoundVoteStates ::
  forall blk.
  StandardHash blk =>
  WithArrivalTime (ValidatedPerasVote blk) ->
  PerasCfg blk ->
  Map PerasRoundNo (PerasRoundVoteState blk) ->
  Either
    (UpdateRoundVoteStateError blk)
    (PerasRoundVoteState blk, Map PerasRoundNo (PerasRoundVoteState blk))
updatePerasRoundVoteStates vote cfg =
  alterMapAndReturnUpdatedValue
    updateMaybePerasRoundVoteState
    (getPerasVoteRound vote)
 where
  -- We use the Functor instance of `Compose (Either e) ((,) s)` ≅
  -- `λt. Either e (s, t)` in `Map.alterF`. That way, we can return both the
  -- updated map and the updated leaf in one pass, and still handle errors.
  alterMapAndReturnUpdatedValue ::
    Ord k =>
    (Maybe a -> Either e (a, a)) ->
    k ->
    Map k a ->
    Either e (a, Map k a)
  alterMapAndReturnUpdatedValue f k =
    getCompose . Map.alterF (fmap Just . (Compose . f)) k

  -- If there is no existing state for the vote's round, create a fresh one.
  existingOrFreshRoundVoteState ::
    Maybe (PerasRoundVoteState blk) ->
    PerasRoundVoteState blk
  existingOrFreshRoundVoteState =
    fromMaybe (freshRoundVoteState (getPerasVoteRound vote))
