### Title
Excess Attached NEAR Deposit Not Returned in `execute_refund` - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary
The `execute_refund` function is publicly callable and marked `#[payable]`. It enforces a minimum attached deposit via `required_balance_for_execute_refund()`, but never refunds any excess NEAR sent beyond that minimum. Any caller who attaches more NEAR than the exact required amount permanently loses the surplus to the contract.

### Finding Description
`execute_refund` in `contracts/satoshi-bridge/src/api/bridge.rs` is decorated `#[payable]` and has no role restriction (only `#[pause]`), making it reachable by any unprivileged NEAR account. [1](#0-0) 

The first thing it does is call `resolve_execute_refund_timelock`, which enforces the minimum deposit: [2](#0-1) 

The check is a one-sided `>=` guard. After the guard passes, neither `resolve_execute_refund_timelock` nor `internal_execute_refund` contains any code that computes `env::attached_deposit() - required_balance_for_execute_refund()` and transfers the difference back to `env::predecessor_account_id()`. The entire attached deposit is absorbed by the contract. [3](#0-2) 

Contrast this with `request_refund`, whose NatSpec explicitly documents the non-refund as intentional anti-spam design:

> "The deposit is NOT refunded — it covers request storage and acts as an anti-spam fee." [4](#0-3) 

No equivalent documentation or design rationale exists for `execute_refund`, and the function's purpose (executing a BTC refund on behalf of a depositor) gives no reason to permanently retain excess NEAR.

### Impact Explanation
Any NEAR in excess of `required_balance_for_execute_refund()` that a caller attaches is permanently kept by the bridge contract with no mechanism for recovery. This constitutes a direct, irreversible loss of user funds (NEAR tokens). The lost funds accumulate in the contract's balance and are not tracked in any accounting field (`acc_collected_protocol_fee`, `lost_found`, etc.), so they are effectively destroyed from the user's perspective.

### Likelihood Explanation
`execute_refund` is callable by any NEAR account after the timelock elapses. Because the exact required deposit amount must be queried via a separate view call (`required_balance_for_execute_refund()`), users who are uncertain of the precise value — or who add a small buffer to guarantee the transaction does not revert — will routinely overpay. This is the same behavioral pattern described in the reference report: users overpay to guarantee success when the exact threshold is not obvious at call time.

### Recommendation
After the minimum-deposit guard, compute the excess and return it to the caller before proceeding:

```rust
pub fn execute_refund(
    &mut self,
    utxo_storage_key: String,
    chain_specific_data: Option<ChainSpecificData>,
) -> PromiseOrValue<()> {
    let timelock_sec = self.resolve_execute_refund_timelock(&utxo_storage_key);
    let required = self.required_balance_for_execute_refund();
    let excess = env::attached_deposit().saturating_sub(required);
    if excess > NearToken::from_yoctonear(0) {
        Promise::new(env::predecessor_account_id()).transfer(excess);
    }
    self.internal_execute_refund(utxo_storage_key, timelock_sec, chain_specific_data)
}
```

### Proof of Concept
1. Query `required_balance_for_execute_refund()` — suppose it returns 0.1 NEAR.
2. A user calls `execute_refund("txid@0", None)` with `attached_deposit = 0.5 NEAR` (adding a buffer to be safe).
3. `resolve_execute_refund_timelock` passes the `>= 0.1 NEAR` guard.
4. `internal_execute_refund` runs; no code returns the 0.4 NEAR surplus.
5. The user's NEAR account is debited 0.5 NEAR; the bridge contract retains all 0.5 NEAR; the 0.4 NEAR excess is permanently lost. [1](#0-0) [2](#0-1)

    pub(crate) fn resolve_execute_refund_timelock(&self, utxo_storage_key: &str) -> u64 {
        require!(
            env::attached_deposit() >= self.required_balance_for_execute_refund(),
            "Insufficient deposit for storage"
        );
        let caller = env::predecessor_account_id();
        let is_privileged =
            self.acl_has_any_role(vec![Role::DAO.into(), Role::RefundOperator.into()], caller);
        let refund_request: RefundRequest = self
            .data()
            .refund_requests
            .get(utxo_storage_key)
            .expect("Refund request not found")
            .into();
        let config = self.internal_config();
        if refund_request.deposit_msg().refund_address.is_some() {
            // Pre-authorized refund address: privileged users can fast-track.
            if is_privileged {
                0
            } else {
                config.refund_timelock_sec
            }
        } else {
            // Refund address supplied by caller of `request_refund`: longer
            // timelock to give DAO/Operator time to reject suspicious requests.
            config.unsafe_refund_timelock_sec
        }
    }
