## Title
Small Transfer Amount Normalizes to Zero, Permanently Freezing User Funds in `sign_transfer` — (File: `near/omni-bridge/src/lib.rs`)

## Summary
When a user initiates a NEAR→EVM transfer with an amount that, after decimal normalization, rounds down to zero, their tokens are burned or locked during `init_transfer_internal` but `sign_transfer` always panics with `InvalidAmountToTransfer`. There is no cancellation or refund path for the stuck pending transfer, so the user's funds are permanently frozen.

## Finding Description
The bridge stores token decimal mappings as a `Decimals { decimals, origin_decimals }` pair. `normalize_amount` at [1](#0-0)  performs floor division: for a 24→18 decimal token, any amount below `10^6` normalizes to zero.

`sign_transfer` enforces a non-zero result at [2](#0-1) , panicking with `InvalidAmountToTransfer` if the normalized amount is zero.

`init_transfer` only validates `fee < amount` at [3](#0-2)  — it does **not** pre-check that `normalize_amount(amount - fee) > 0`.

Immediately after this check, `init_transfer_internal` burns (for deployed tokens) or locks (for native tokens) the full amount at [4](#0-3) , before any normalization guard is applied.

The transfer is then stored in `pending_transfers`. A grep for `cancel_transfer` in `lib.rs` returns zero matches — there is no user-accessible cancellation or refund path. Because `sign_transfer` will always panic for this transfer, no MPC signature is ever produced, no EVM `finTransfer` can occur, and the burned tokens are permanently lost.

Note: the `normalize_amount` doc comment at [5](#0-4)  acknowledges that sub-unit *dust remainders* (where normalization yields a positive but truncated result) stay locked/burned and references `SECURITY.md` for details. However, the zero-normalization case — where the *entire* amount is lost and `sign_transfer` is permanently broken — is distinct from dust and is not addressed in `SECURITY.md`.

## Impact Explanation
Any user who sends an amount smaller than `10^(origin_decimals − decimals)` will have their tokens burned or locked with no recovery path. For a 24→18 decimal token pair (common on NEAR/EVM), the threshold is `10^6` yocto-units. This constitutes **permanent freezing/loss of bridged funds**, matching the Critical allowed impact: *"permanent freezing of bridged funds across NEAR, EVM, … flows."*

NEAR tokens commonly use 24 decimals while their EVM counterparts use 18. The vulnerable path is fully user-reachable via `ft_transfer_call` with no privileged access required. ## Title
Small Transfer Amount Normalizes to Zero, Permanently Freezing User Funds in `sign_transfer` — (File: `near/omni-bridge/src/lib.rs`)

## Summary

When a user initiates a NEAR→EVM transfer with an amount that, after decimal normalization, rounds down to zero, their tokens are burned or locked during `init_transfer_internal` but `sign_transfer` always panics with `InvalidAmountToTransfer`. There is no `cancel_transfer` or user-accessible refund path for the stuck pending transfer, so the user's funds are permanently frozen.

## Finding Description

The `normalize_amount` function at L2784–2787 performs floor division by `10^(origin_decimals − decimals)`:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

`sign_transfer` (L475–485) calls this and enforces a non-zero result, panicking with `InvalidAmountToTransfer` if the result is zero. This check is the only place normalization is validated.

`init_transfer` (L554–557) only validates `fee < amount` — it does not pre-check that `normalize_amount(amount − fee) > 0`. Immediately after this check, `init_transfer_internal` (L1850–1857) burns (for deployed tokens) or locks (for native tokens) the full amount and stores the transfer in `pending_transfers`.

Because `sign_transfer` will always panic for any transfer whose normalized amount is zero, and because a grep of `lib.rs` confirms there is no `cancel_transfer` function and the only removal path is `remove_transfer_message_without_refund` (inaccessible to users), the burned/locked funds are permanently irrecoverable.

The `normalize_amount` docstring (L2781–2783) acknowledges that "dust stays locked/burned" and references SECURITY.md, but this refers only to sub-unit remainders (e.g., 1 unit of dust from a 1,000,001-unit transfer). It does not cover the distinct case where the *entire* net amount normalizes to zero, which is what this vulnerability exploits. The SECURITY.md itself contains only a generic exclusion list and does not address this scenario.

## Impact Explanation

Any user who sends an amount smaller than `10^(origin_decimals − decimals)` (e.g., fewer than `10^6` yocto-units for a 24→18 decimal token pair) will have their tokens permanently burned or locked with no recovery path. This constitutes **permanent freezing of bridged funds**, which matches the Critical allowed impact scope.

## Likelihood Explanation

NEAR tokens commonly use 24 decimals while their EVM counterparts use 18, making the minimum transferable unit `10^6` yocto-tokens. Any user sending an amount below this threshold — whether by mistake, UI rounding, or intentional dust-amount input — triggers the freeze. No privileged access is required; the path is fully reachable by any unprivileged user via the public `ft_transfer_call` entry point.

## Recommendation

Add a normalization check inside `init_transfer` (before burning/locking) to reject transfers whose net amount normalizes to zero:

```rust
let token_address = self.get_token_address(destination_chain, token_id.clone())
    .near_expect(BridgeError::FailedToGetTokenAddress);
let decimals = self.token_decimals.get(&token_address)
    .near_expect(BridgeError::TokenDecimalsNotFound);
require!(
    Self::normalize_amount(amount_without_fee, decimals) > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

This mirrors the guard already present in `sign_transfer` and prevents tokens from being burned/locked for a transfer that can never be finalized.

## Proof of Concept

1. Token `foo.near` has `origin_decimals = 24` on NEAR and `decimals = 18` on EVM (scaling factor = `10^6`).
2. User calls `ft_transfer_call` with `amount = 500_000`, `fee = 0`.
3. `init_transfer` passes the `fee < amount` check at L554–557 and calls `init_transfer_internal`.
4. `burn_tokens_if_needed` at L1851 burns 500,000 units of `foo.near` from the user.
5. Transfer is stored in `pending_transfers`.
6. Relayer calls `sign_transfer`. `normalize_amount(500_000, {origin_decimals: 24, decimals: 18}) = 500_000 / 10^6 = 0`.
7. `require!(amount_to_transfer > 0, ...)` at L482–485 panics — `sign_transfer` always fails for this transfer.
8. No MPC signature is ever produced; no EVM `finTransfer` can occur.
9. The burned tokens are permanently lost; the pending transfer entry is irremovable by the user (no `cancel_transfer` exists in the contract). [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
