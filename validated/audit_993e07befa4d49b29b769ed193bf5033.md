Audit Report

## Title
No Cancel/Refund Mechanism for Pending Transfers Causes Permanent Fund Freezing - (File: near/omni-bridge/src/lib.rs)

## Summary
`init_transfer` unconditionally consumes user tokens and stores the transfer in `pending_transfers` without verifying that the token is registered on the destination chain. If the token is absent from `token_id_to_address` for the target chain, every subsequent `sign_transfer` call panics at `get_token_address`, and no user-accessible code path exists to remove the transfer or recover the tokens. The funds are permanently frozen from the user's perspective.

## Finding Description
When a user calls `ft_transfer_call` on a NEP-141 token with the bridge as receiver, `ft_on_transfer` dispatches to `init_transfer`. [1](#0-0) 

`init_transfer` validates only that the recipient chain is not NEAR, then unconditionally stores the `TransferMessage` in `pending_transfers` and returns `U128(0)`, consuming all tokens. No check is made that the token is registered on the destination chain. [2](#0-1) 

Later, when a relayer calls `sign_transfer`, the contract looks up the token address for the destination chain and panics if it is absent: [3](#0-2) 

The only code paths that call `remove_transfer_message` are:
1. `sign_transfer_callback` — only when `fee.is_zero()` **and** MPC signing succeeds.
2. `claim_fee_callback` — only after a successful on-chain proof of finalization. [4](#0-3) [5](#0-4) 

A search across the entire contract confirms there is no `cancel_transfer`, `refund_transfer`, or equivalent public function, and `pending_transfers` has no expiry or user-initiated removal path. The only admin escape hatch is `transfer_token_as_dao`, which requires DAO intervention and is not a user-accessible recovery mechanism. [6](#0-5) 

## Impact Explanation
A user whose transfer targets a destination chain where the token mapping has not been registered via `bind_token` or `deploy_token` will have their tokens permanently locked in the bridge contract. `sign_transfer` will always panic at `get_token_address`, so the transfer can never be signed, and no other code path removes it from `pending_transfers` or returns the tokens. This constitutes **permanent freezing of bridged funds**, matching the critical allowed impact class.

## Likelihood Explanation
The scenario is reachable by any unprivileged user through a standard `ft_transfer_call` invocation. It is a realistic mistake during token onboarding: a token may be registered on some chains but not yet on others. The user has no on-chain mechanism to detect this before submitting, and the contract provides no pre-flight validation. The condition is repeatable and requires no admin involvement to trigger.

## Recommendation
1. **Add a pre-flight check in `init_transfer`** that calls `get_token_address` for the destination chain before consuming the user's tokens, and returns the full amount if the token is not registered.
2. **Add a `cancel_transfer` function** that allows the original sender (stored as `transfer.sender`) to remove a pending transfer from `pending_transfers` and receive a refund of the locked tokens, provided the transfer has not yet been signed or finalized.
3. Optionally, add a time-based expiry so that transfers pending longer than a configurable window can be cancelled by the sender.

## Proof of Concept
1. Token `usdc.near` is registered on `ChainKind::Eth` but not on `ChainKind::Arb`.
2. User calls `usdc.near::ft_transfer_call(bridge, 1000, msg)` where `msg` specifies a recipient on Arbitrum.
3. `ft_on_transfer` → `init_transfer` stores the transfer in `pending_transfers` and returns `U128(0)` — tokens are consumed.
4. Relayer calls `sign_transfer(transfer_id, ...)`.
5. Inside `sign_transfer`, `get_token_address(ChainKind::Arb, usdc.near)` returns `None`, triggering `env::panic_str(BridgeError::FailedToGetTokenAddress)`.
6. The transfer remains in `pending_transfers` indefinitely. The user's 1000 USDC is permanently locked with no cancel path.

To reproduce as a unit/integration test: initialize the contract, register `usdc.near` only for `ChainKind::Eth`, simulate `ft_on_transfer` with an Arbitrum recipient, then call `sign_transfer` and assert it panics. Confirm that `get_transfer_message` still returns the stored transfer and that no public function can remove it or refund the sender.
