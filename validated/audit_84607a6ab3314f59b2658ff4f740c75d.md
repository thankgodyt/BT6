### Title
Stub `validatePerasCert` Accepts Any Forged Certificate, Enabling Adversarial Fork Boost via `chainSelSync` — (`Ouroboros/Consensus/Block/SupportsPeras.hs`, `ChainSel.hs`)

---

### Summary

The question's framing attributes the vulnerability to `AF.withinFragmentBounds` behaving incorrectly. That framing is **wrong**: `withinFragmentBounds` checks by full point identity (slot + hash) and returning `False` for a fork block is **correct, intended behavior** — it is the signal that the cert boosts something off the current chain and chain selection should evaluate the fork. The invariant "only switch if the fork has strictly greater total weight" is also **maintained** by `preferAnchoredCandidate`.

The **real** root cause is a separate, concrete flaw: the production `validatePerasCert` implementation is a stub that unconditionally returns `Right` for every certificate, performing zero cryptographic or semantic validation. This allows any unprivileged peer to inject a certificate boosting any fork block already in the VolatileDB, triggering `chainSelectionForBlock` with a `PerasWeight 15` boost applied to the fork, which can flip chain selection if the fork is at most 15 blocks shorter than the current chain.

---

### Finding Description

**Entry point — object diffusion inbound path:**

`makePerasCertPoolWriterFromChainDB` is the production writer used when certs arrive from peers. It calls `processCerts` with `validatePerasCert mkPerasParams` as the validation function. [1](#0-0) 

`processCerts` calls `validateCert` on each inbound cert; if all pass, they are timestamped and forwarded to `ChainDB.addPerasCertAsync`. [2](#0-1) 

**The stub — `validatePerasCert` always returns `Right`:**

The `BlockSupportsPeras` instance for all `StandardHash blk` (the only instance in the codebase) implements `validatePerasCert` as an unconditional `Right`, with a TODO referencing issue #120. No BLS aggregate signature is checked, no committee membership is verified, no round/slot constraints are enforced. [3](#0-2) 

**`chainSelSync` — the cert processing path:**

After the cert is accepted, `chainSelSync` for `ChainSelAddPerasCert`:

1. Checks `pointSlot boostedBlock < AF.anchorToSlotNo immTip` — skips only if the boosted slot is older than the immutable tip.
2. Calls `AF.withinFragmentBounds (castPoint boostedBlock) curChain` — returns `False` when the hash is a fork block (correct behavior; not a bug).
3. Extracts `BlockHash boostedHash` and calls `VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash`.
4. If the fork block is present in the VolatileDB, calls `chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment`. [4](#0-3) 

**`constructPreferableCandidates` + `preferAnchoredCandidate`:**

`chainSelectionForBlock` calls `constructPreferableCandidates`, which uses `Paths.isReachable` to find the fork diff, then filters by `preferAnchoredCandidate bcfg weights curChain (Diff.getSuffix chain)`. The `weights` snapshot includes the boost from the newly stored cert. With `perasWeight = PerasWeight 15`, a fork that is up to 15 blocks shorter than the current chain can now be preferred. [5](#0-4) [6](#0-5) 

**The boost value:**

`mkPerasParams` sets `perasWeight = PerasWeight 15`. The attacker cannot inflate this value (the stub ignores the cert's own fields and uses the configured weight), but 15 is sufficient to overcome a 15-block deficit on a fork. [7](#0-6) 

---

### Impact Explanation

An unprivileged peer can:

1. Observe a fork block `H` at slot `S` that was previously diffused and stored in the target node's VolatileDB (normal network operation).
2. Craft a `PerasCert blk` with `pcCertRound = R` (any unused round) and `pcCertBoostedBlock = BlockPoint S H`.
3. Send it via the object-diffusion miniprotocol. `validatePerasCert` accepts it unconditionally.
4. The cert is stored in `PerasCertDB` and the boost is added to the `PerasWeightSnapshot`.
5. `chainSelSync` triggers `chainSelectionForBlock` for `H`.
6. If the fork rooted at `H` is at most 15 blocks shorter than the current chain, `preferAnchoredCandidate` returns `ShouldSwitch` and the node rolls back to the fork.

This allows an adversary to force an honest node to adopt a minority fork, violating chain selection safety.

---

### Likelihood Explanation

- Requires no stake, no keys, no admin access — only the ability to send a cert over the object-diffusion protocol.
- Fork blocks are routinely present in the VolatileDB during normal operation.
- The stub is the **only** `validatePerasCert` implementation in the codebase; there is no override for any concrete block type.
- The boost of 15 is a realistic margin to overcome in practice.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
- Verifies the BLS aggregate signature over `(pcCertRound, pcBoostedBlock)` against the aggregated public keys of the claimed voters.
- Verifies each voter's VRF eligibility proof.
- Checks that the number of voters meets the quorum stake threshold.
- Validates that `pcBoostedBlock` satisfies `perasBlockMinSlots` age and round constraints.

Until issue #120 / #73 are resolved, the object-diffusion inbound path for certs should be disabled or gated behind a feature flag so that no external peer can inject certs into the chain selection pipeline.

### Proof of Concept

```
-- io-sim / ChainDB state-machine test sketch
--
-- Setup: node has current chain [G -> B1 -> B2 -> B3 -> B4 -> B5]
--        fork block F forks at B2: [G -> B1 -> B2 -> F]
--        F is already in the VolatileDB (received earlier, not preferred)
--        perasWeight = 15, so fork length deficit = 3 < 15
--
-- Step 1: craft cert
let cert = PerasCert { pcCertRound = 999, pcCertBoostedBlock = blockPoint F }
-- Step 2: inject via processCerts (validatePerasCert always returns Right)
processCerts systemTime alreadyInDb (validatePerasCert mkPerasParams) addCertAsync [cert]
-- Step 3: chainSelSync processes ChainSelAddPerasCert
--   withinFragmentBounds (blockPoint F) curChain  => False  (F not on current chain)
--   VolatileDB.getBlockComponent GetHeader (blockHash F) => Just hdrF
--   chainSelectionForBlock ... hdrF ...
--   constructPreferableCandidates finds fork [B1->B2->F]
--   weightedSelectView: fork suffix weight = 1 (length) + 15 (boost) = 16
--                       current suffix weight = 3 (length) + 0 = 3
--   preferAnchoredCandidate => ShouldSwitch
-- ASSERT: node tip is now F  -- chain selection switched to minority fork
```

The `withinFragmentBounds` call at line 506 is **not** the bug — it correctly identifies the fork. The bug is that `validatePerasCert` at lines 353–358 of `SupportsPeras.hs` never rejects any certificate, so the cert that triggers this path is never filtered out. [3](#0-2) [8](#0-7) [9](#0-8)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
