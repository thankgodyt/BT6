### Title
Unpermissioned `request_refund` Allows Any Caller to Redirect BTC Refunds to an Arbitrary Address - (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary
`request_refund` has no caller-identity check. When a deposit was made with `DepositMsg.refund_address = None`, any NEAR account can call `request_refund` for that UTXO and supply an arbitrary attacker-controlled BTC address as `refund_address`. Because only one refund request per UTXO is accepted, the legitimate depositor is locked out, and after `unsafe_refund_timelock_sec` elapses the bridge MPC-signs a transaction that sends the BTC to the attacker's address.

### Finding Description

`request_refund` is a public, permissionless function: [1](#0-0) 

Inside `internal_request_refund`, the only guard on `refund_address` is: [2](#0-1) 

This guard fires **only** when `deposit_msg.refund_address` is `Some`. When it is `None` — a fully supported and documented case — the provided `refund_address` is accepted without any check on who the caller is or whether the caller has any relationship to the deposit.

The callback then stores the attacker-supplied address verbatim: [3](#0-2) 

A duplicate-request guard then blocks any subsequent `request_refund` call for the same UTXO: [4](#0-3) 

So the legitimate depositor cannot overwrite the attacker's request. The only code-level mitigation is a longer `unsafe_refund_timelock_sec` that applies specifically to the `refund_address = None` case: [5](#0-4) 

This longer timelock is intended to give DAO/Operator time to reject suspicious requests, but it is not a code-level access control fix — it is a reactive, off-chain-dependent mitigation.

The `DepositMsg` used to derive the deposit address is fully public (emitted in a `LogDepositAddress` event by `get_user_deposit_address`), so an attacker can reconstruct it for any deposit. [6](#0-5) 

### Impact Explanation

**Critical.** When a user deposits BTC using a `DepositMsg` with `refund_address: None` and the deposit is never finalized via `verify_deposit`, an attacker can:

1. Call `request_refund` with the victim's `deposit_msg` and the attacker's own BTC address.
2. Block the victim from submitting their own refund request (duplicate guard).
3. Wait for `unsafe_refund_timelock_sec` to elapse.
4. Call `execute_refund` — the bridge builds and MPC-signs a Bitcoin transaction paying the attacker's address.
5. Broadcast the transaction; the victim's BTC is permanently transferred to the attacker.

This constitutes unauthorized redirection and theft of bridge-controlled BTC funds.

### Likelihood Explanation

**Medium.** The `DepositMsg` is public via on-chain events. The attacker only needs to pay the NEAR storage deposit for `request_refund` (a small, fixed cost). The attack window is open for every deposit where `refund_address` is `None` and `verify_deposit` has not yet been called. The only blocking factor is DAO/Operator actively monitoring and rejecting the malicious request within the `unsafe_refund_timelock_sec` window — a reactive, off-chain dependency that cannot be guaranteed.

### Recommendation

Restrict `request_refund` so that when `deposit_msg.refund_address` is `None`, only the `deposit_msg.recipient_id` (the intended NEAR beneficiary) may call the function and supply the `refund_address`. Concretely, add a check in `request_refund`:

```rust
if deposit_msg.refund_address.is_none() {
    require!(
        env::predecessor_account_id() == deposit_msg.recipient_id,
        "Only the deposit recipient may set refund_address when none is pre-authorized"
    );
}
```

This mirrors the M-13 recommendation: only the creator of the parameterized object (here, the deposit recipient) should be allowed to set the free parameter (`refund_address`).

### Proof of Concept

1. Alice calls `get_user_deposit_address` with `DepositMsg { recipient_id: "alice.near", refund_address: None, ... }`. The event reveals the full `deposit_msg`. Alice sends 1 BTC to the derived address. `verify_deposit` is never called (relayer is down).

2. Attacker Bob calls:
   ```
   request_refund(
       deposit_msg = { recipient_id: "alice.near", refund_address: None, ... },
       refund_address = "bc1q_BOB_ADDRESS",
       tx_bytes = <Alice's deposit tx>,
       vout = 0,
       proof = <valid Merkle proof>,
       gas_fee = None,
   )
   ```
   The `script_pubkey` check passes (Bob used the correct `deposit_msg`). The `refund_address` guard is skipped (`deposit_msg.refund_address` is `None`). The request is stored with `refund_address = "bc1q_BOB_ADDRESS"`.

3. Alice attempts `request_refund` with her own BTC address — it fails: `"Refund request already exists for this UTXO"`.

4. After `unsafe_refund_timelock_sec` elapses (assuming DAO does not reject), anyone calls `execute_refund`. The bridge builds a PSBT paying `bc1q_BOB_ADDRESS` and requests an MPC signature. [7](#0-6) 

5. The signed transaction is broadcast. Alice's 1 BTC is sent to Bob's address. Alice receives nothing.

    /// Build a transparent refund output paying `refund_amount` to `refund_address`.
    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
    }
