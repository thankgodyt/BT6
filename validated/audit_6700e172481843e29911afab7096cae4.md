### Title
Peras Certificate Validation Bypass Enables Arbitrary Chain-Weight Manipulation — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or structural validation. Any unprivileged peer can craft a `PerasCert` targeting any block and have it accepted by an honest node, injecting an arbitrary `PerasWeight` boost into that node's `PerasWeightSnapshot`. Because chain selection directly compares `wsvTotalWeight` (block-number + boost), the attacker can make an honest node prefer a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` instance in `SupportsPeras.hs` is the only instance in the codebase. Its `validatePerasCert` implementation is a stub that always succeeds:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature, quorum proof, round-number, or boosted-block validity check is performed. The function is declared as a "degenerate instance for all blks to get things to compile": [2](#0-1) 

The same stub pattern applies to `validatePerasVote`, which skips all cryptographic signature verification and only performs a stake-map lookup: [3](#0-2) 

Additionally, `getVotingCommitteeForElection` — the function that would resolve the correct epoch-snapshotted committee for verifying a vote or certificate — is entirely unimplemented and calls `error`: [4](#0-3) 

The accepted `ValidatedPerasCert` is fed into `addPerasCertAsync` on the `ChainDB`, which updates the `PerasWeightSnapshot`: [5](#0-4) 

Chain selection then uses `wsvTotalWeight` — the sum of block number and accumulated `PerasWeight` boost — to decide which chain to prefer: [6](#0-5) 

The `PerasWeightSnapshot` is read atomically during every chain-selection event: [7](#0-6) 

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` naming any block point and any round number, send it via the Peras certificate diffusion mini-protocol, and have it unconditionally accepted. The receiving node adds `perasWeight params` to that block's entry in `PerasWeightSnapshot`. Because `preferCandidate` switches to the chain with the higher `wsvTotalWeight`, the attacker can make an honest node switch to — and permanently prefer — a chain containing the artificially boosted block, even if that chain is non-canonical or less secure. This is a **Critical** bypass of Peras certificate verification enabling unauthorized chain-weight manipulation and chain-selection divergence.

---

### Likelihood Explanation

The attack requires only network access to a node running the Peras certificate diffusion mini-protocol. No stake, keys, or operator access is needed. The attacker sends a single well-formed (but cryptographically unverified) `PerasCert` message. The stub is the only `BlockSupportsPeras` instance in the repository and is compiled into all block types.

---

### Recommendation

1. **Implement real certificate validation** in `validatePerasCert`: verify the aggregate BLS signature, confirm the quorum threshold is met using the epoch-snapshotted stake distribution, and check that the certified block and round number are within valid bounds.
2. **Implement `getVotingCommitteeForElection`** in `AcrossEpochs.hs` so that vote and certificate verification can be performed against the correct epoch's committee.
3. **Implement real vote validation** in `validatePerasVote`: verify the cryptographic vote signature against the voter's registered public key, not just a stake-map lookup.
4. Until (1)–(3) are complete, gate the Peras certificate ingestion path behind a feature flag that is disabled in any deployment where the stub instance is active.

---

### Proof of Concept

A peer on a private testnet sends a crafted `PerasCert`:

```haskell
let fakeCert = PerasCert
      { pcCertRound    = PerasRoundNo 999
      , pcCertBoostedBlock = someAdversarialBlockPoint
      }
```

The receiving node calls `validatePerasCert mkPerasParams fakeCert`, which returns:

```haskell
Right ValidatedPerasCert
  { vpcCert      = fakeCert
  , vpcCertBoost = perasWeight mkPerasParams  -- e.g. PerasWeight 1000
  }
``` [8](#0-7) 

The `ValidatedPerasCert` is passed to `addPerasCertAsync`, updating `PerasWeightSnapshot` so that `someAdversarialBlockPoint` carries `PerasWeight 1000`. On the next chain-selection event, `preferCandidate` compares `wsvTotalWeight` values and switches to the adversarially boosted chain, even though no honest quorum ever certified it. [9](#0-8)
