### Title
`validatePerasCert` Unconditionally Accepts All Inbound Peras Certificates, Enabling Arbitrary Chain-Selection Weight Injection — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The sole production instance of `BlockSupportsPeras` implements `validatePerasCert` as an unconditional `Right`, performing zero cryptographic or structural checks on inbound Peras certificates. Because the object-diffusion mini-protocol feeds peer-supplied certificates directly through this no-op validator before inserting them into the `ChainDB`, any unprivileged peer can inject an arbitrary `PerasCert` that boosts any block hash it chooses. The boosted block's `PerasWeightSnapshot` entry is then used by `WeightedSelectView.preferCandidate` to decide chain selection, so a single crafted certificate can cause an honest node to switch to a non-canonical fork.

---

### Finding Description

**Analog mapping.** The ERC20Gauges bug checks only that a gauge is *not* in `_deprecatedGauges` while omitting the positive check that it *is* in `_gauges`, so an unregistered gauge silently receives weight. The Ouroboros analog is starker: `validatePerasCert` omits *every* check — not even one condition is verified — so any certificate, registered or not, legitimate or fabricated, silently receives a chain-selection weight boost.

**Root cause — `validatePerasCert` stub.**
The only instance of `BlockSupportsPeras` is a universal catch-all declared with the comment "degenerate instance for all blks to get things to compile":

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No round-number bounds check, no boosted-block existence check, no quorum-signature verification, and no committee-membership check are performed. The function returns `Right` for every input unconditionally.

**Production call sites — both pool writers use the stub.**
`makePerasCertPoolWriterFromChainDB` is the production path (the cert-DB-only variant is documented as "mostly meant for tests"). Both pass `validatePerasCert mkPerasParams` as the validator:

```haskell
processCerts
  systemTime
  (ChainDB.getPerasCertIds chainDB)
  -- TODO replace when actual plumbing is in place
  (validatePerasCert mkPerasParams)
  (void . ChainDB.addPerasCertAsync chainDB)
  certs
``` [2](#0-1) 

`processCerts` filters out round numbers already in the DB, then calls `validateCert` on each remaining certificate. Because `validatePerasCert` always returns `Right`, every new-round certificate passes and is forwarded to `addPerasCertAsync`. [3](#0-2) 

**Chain-selection side-effect — `chainSelSync` triggers a fork switch.**
`addPerasCertAsync` enqueues the certificate for synchronous processing by `chainSelSync`. That function adds the cert to `PerasCertDB` and, if the boosted block is present in the `VolatileDB`, immediately calls `chainSelectionForBlock` for it:

```haskell
-- Trigger chain selection for the boosted block.
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

**Weight snapshot drives chain preference.**
`chainSelectionForBlock` computes `weightedSelectView`, which sums `weightBoostOfFragment` from the `PerasWeightSnapshot`. The `WeightedSelectView` `Ord` instance prefers the candidate with the higher `wsvTotalWeight`:

```haskell
preferCandidate cfg ours cand =
  case compare (wsvTotalWeight ours) (wsvTotalWeight cand) of
    LT -> ShouldSwitch (Heavier $ ...)
    ...
``` [5](#0-4) 

A fake certificate that boosts a block on a minority fork therefore causes the node to switch to that fork.

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` naming any `pcCertBoostedBlock` hash. After the no-op validation, the certificate is stored and triggers `chainSelectionForBlock`. If the attacker has already diffused the corresponding block (or waits until the victim receives it), the victim's `PerasWeightSnapshot` is updated and chain selection switches to the attacker's fork. This is a **High** chain-selection bug: an honest node is made to prefer a non-canonical, less-secure chain without any stake majority or key compromise.

---

### Likelihood Explanation

The object-diffusion mini-protocol for Peras certificates is reachable by any peer that connects to the node. No credentials, stake, or cryptographic material are required to craft a `PerasCert` — it is a plain data record containing a `PerasRoundNo` and a `Point blk`. The only natural throttle is the per-round deduplication (`Set.member roundNo certIds`), which limits the attacker to one effective injection per round number; with many round numbers available this is not a meaningful barrier.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies, at minimum:

1. **Round validity** — the certificate's round number falls within the current or recent epoch window.
2. **Boosted-block plausibility** — the `pcCertBoostedBlock` point is structurally valid (non-genesis, slot within expected range).
3. **Quorum signature** — the aggregate vote signature covers a quorum of committee members for the claimed election ID and candidate, using the committee selection context for the relevant epoch.
4. **No equivocation** — only one certificate per round is accepted (already enforced by the DB deduplication, but should also be a validation error rather than a silent skip).

Until the full committee-selection plumbing (tracked in issue #73 / #120) is in place, a minimum guard should at least reject certificates whose `pcCertBoostedBlock` slot is in the future or whose round number is outside any plausible epoch window, preventing trivially crafted inputs from influencing chain selection.

---

### Proof of Concept

```
Private testnet setup:
  Node A  — honest node with Peras enabled
  Attacker — connects to Node A via the object-diffusion mini-protocol

1. Attacker diffuses a valid block B_fork on a minority fork to Node A
   (so B_fork is present in Node A's VolatileDB).

2. Attacker sends a PerasCert { pcCertRound = R, pcCertBoostedBlock = point(B_fork) }
   to Node A through the cert object-diffusion channel.

3. Node A's processCerts:
     alreadyInDb = getPerasCertIds  -- R not yet present
     validatePerasCert mkPerasParams cert  -- always returns Right
     addPerasCertAsync chainDB cert        -- enqueued

4. chainSelSync processes the cert:
     PerasCertDB.addCert  -- cert stored
     VolatileDB.getBlockComponent GetHeader (hash B_fork)  -- found
     chainSelectionForBlock ... boostedHdr  -- triggered

5. PerasWeightSnapshot now contains point(B_fork) -> perasWeight params.
   weightedSelectView for the fork containing B_fork now has higher
   wsvTotalWeight than the honest chain.

6. Node A switches to the minority fork.
``` [6](#0-5) [7](#0-6) [8](#0-7)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
