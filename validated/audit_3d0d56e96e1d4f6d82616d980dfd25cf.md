### Title
`validatePerasCert` Unconditionally Accepts All Inbound Peras Certificates Without Cryptographic Verification, Enabling Chain Selection Manipulation by Any Peer — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance in `SupportsPeras.hs` implements `validatePerasCert` as a stub that unconditionally returns `Right` for every certificate it receives, performing no cryptographic or structural validation whatsoever. This stub is wired directly into the production inbound certificate processing pipeline (`makePerasCertPoolWriterFromChainDB`). Any unprivileged peer can therefore inject arbitrary Peras certificates for any round and any block into the node's `PerasCertDB`, bypassing the certificate verification gate entirely. Because accepted certificates trigger `ChainDB.addPerasCertAsync`, which re-runs chain selection with the certificate's boost weight applied, a malicious peer can cause an honest node to prefer a weaker or attacker-controlled chain.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub wired into production:** [1](#0-0) 

The universal instance (`instance StandardHash blk => BlockSupportsPeras blk`) is the only `BlockSupportsPeras` instance in the codebase. Its `validatePerasCert` body is:

```haskell
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

It ignores every field of `cert` and returns `Right` unconditionally. No BLS signature check, no committee membership check, no round-number plausibility check — nothing.

**Production wiring — this stub is called on every inbound certificate from a peer:** [2](#0-1) 

`makePerasCertPoolWriterFromChainDB` is the production writer used when certificates arrive via the ObjectDiffusion mini-protocol. It passes `(validatePerasCert mkPerasParams)` as the validation callback to `processCerts`. Because `validatePerasCert` always returns `Right`, the `partitionEithers` branch in `processCerts` that would reject invalid certificates is never taken: [3](#0-2) 

Every certificate that is not already in the DB is therefore accepted and forwarded to `ChainDB.addPerasCertAsync`, which triggers chain selection with the certificate's boost weight.

**Chain selection side-effect — accepted certificates alter chain preference:**

The `addPerasCertAsync` call (line 132) causes the ChainDB to re-evaluate chain selection, applying `perasWeight` as a boost to the block named in the certificate. A fake certificate pointing to an attacker-controlled or weaker block can therefore cause the node to switch away from the honest canonical chain.

**Analog to the BakerFi finding:**

|---|---|
| `harvest()` has no `onlyOwner` guard | `validatePerasCert` has no actual validation |
| Anyone can call it to reset `_deployedAmount` | Any peer can send a cert that passes the validation gate |

### Impact Explanation

**Critical — Bypass of Peras certificate verification enabling unauthorized chain selection manipulation.**

An unprivileged peer with a standard network connection can:

1. Craft a `PerasCert` naming any block hash and any round number.
2. Send it via the ObjectDiffusion mini-protocol.
3. The cert passes `validatePerasCert` (always `Right`) and is stored in `PerasCertDB`.
4. `ChainDB.addPerasCertAsync` fires, applying `perasWeight` boost to the named block.
5. The node's chain selection now treats that block as having extra weight, potentially switching to a non-canonical or attacker-controlled chain.

This satisfies the allowed impact scope: **Critical — Bypass of certificate verification that enables unauthorized certificate acceptance**, and **High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain**.

---

### Likelihood Explanation

**High.** The ObjectDiffusion mini-protocol is a standard peer-to-peer protocol reachable by any node that can establish a connection. No privileged keys, no stake, and no special position in the network are required. The attacker only needs to connect and send a well-formed CBOR-encoded `PerasCert` message. The stub is in the production source tree and is the only instance of `BlockSupportsPeras` in the codebase, so there is no alternative code path that would perform real validation.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with one that performs full cryptographic validation before the Peras certificate diffusion mini-protocol is enabled on any production or pre-production network. Specifically:

1. Verify the BLS aggregate signature over the claimed committee votes.
2. Verify that the signers are eligible committee members for the claimed round (using the committee selection data / VRF proofs).
3. Verify that the certificate's `pcCertRound` is within the acceptable window relative to the current chain tip.
4. Verify that `pcCertBoostedBlock` refers to a block that actually exists on a known chain.

Until a real implementation is in place, the ObjectDiffusion certificate writer should not be instantiated in any node configuration that accepts inbound connections from untrusted peers. [4](#0-3)

### Proof of Concept

**Preconditions:** Attacker has a standard peer connection to an honest node running with Peras certificate diffusion enabled.

**Steps:**

1. Attacker identifies a block `B_weak` on a weaker competing chain (e.g., a chain with fewer blocks than the current tip).
2. Attacker constructs a `PerasCert` value:
   ```
   PerasCert { pcCertRound = <any round>, pcCertBoostedBlock = <point of B_weak> }
   ```
3. Attacker serialises it to CBOR and sends it via the ObjectDiffusion mini-protocol.
4. The honest node calls `processCerts`, which calls `validatePerasCert mkPerasParams cert`.
5. `validatePerasCert` returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams })` without inspecting any field of `cert`.
6. The cert is stored in `PerasCertDB` and `ChainDB.addPerasCertAsync` is invoked.
7. Chain selection re-runs with `B_weak` receiving `perasWeight` extra weight.
8. If `perasWeight` is large enough relative to the honest chain's length advantage, the node switches to the weaker chain.

**Expected outcome:** The honest node accepts the forged certificate and may switch to a non-canonical chain, violating chain selection safety. [5](#0-4) [4](#0-3)

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
```
