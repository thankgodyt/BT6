Audit Report

## Title
Cross-Chain Replay of `deployToken` Signature Due to Missing Chain ID in Metadata Hash — (`evm/src/omni-bridge/contracts/OmniBridge.sol`, `starknet/src/bridge_types.cairo`, `solana/programs/bridge_token_factory/src/state/message/deploy_token.rs`)

## Summary

The `deployToken`/`deploy_token` signature hash across EVM, Starknet, and Solana bridge contracts omits any destination chain identifier, while the same NEAR MPC-derived signing key (`nearBridgeDerivedAddress`) is used across all chains. A valid NEAR MPC signature for a `MetadataPayload` on one chain is therefore cryptographically valid on every other supported chain, allowing any observer to replay a `deployToken` transaction from one chain onto all others without NEAR ever authorizing the per-chain deployment. This constitutes an unauthorized deployer-equivalent action and permanently blocks legitimate deployment of the same token on the replayed chain.

## Finding Description

**EVM (`OmniBridge.sol` lines 142–149):**

The `deployToken` function constructs the signed hash as:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
bytes32 hashed = keccak256(borshEncoded);
if (ECDSA.recover(hashed, signatureData) != nearBridgeDerivedAddress) {
    revert InvalidSignature();
}
```

No `omniBridgeChainId` is included. By contrast, `finTransfer` (lines 289–309) embeds `omniBridgeChainId` twice in the hash, making those signatures chain-specific. The `omniBridgeChainId` state variable exists and is set at initialization but is never used in the `deployToken` hash.

**Starknet (`bridge_types.cairo` lines 36–44):**

`MetadataPayloadImpl::to_borsh()` serializes only `PayloadType::Metadata | token | name | symbol | decimals` with no `chain_id` parameter. In `omni_bridge.cairo`, `deploy_token` calls `payload.to_borsh()` with no argument (line 205), while `fin_transfer` calls `payload.to_borsh(self.omni_bridge_chain_id.read())` (line 253) — a direct asymmetry showing the protection was intentionally applied to transfers but omitted for token deployment.

**Solana (`deploy_token.rs` lines 19–26):**

`DeployTokenPayload::serialize_for_near()` writes only `IncomingMessageType::Metadata` followed by the borsh-encoded struct. No `SOLANA_OMNI_BRIDGE_CHAIN_ID` is written, unlike `FinalizeTransferPayload::serialize_for_near()` which writes `SOLANA_OMNI_BRIDGE_CHAIN_ID` for both the token and recipient fields (lines 30, 35).

**Same signing key across all chains:**

The `nearBridgeDerivedAddress` is derived from the NEAR MPC network using a fixed path `"bridge-1"` for all EVM deployments (`hardhat.config.ts` lines 78–82). It is chain-agnostic. A signature over `keccak256(Metadata | token | name | symbol | decimals)` is therefore cryptographically valid on Ethereum, Arbitrum, Base, BNB, Polygon, HyperEVM, and Abstract simultaneously.

**Exploit path:**

1. Observe a legitimate `deployToken(signatureData, metadata)` call on Ethereum mainnet. Extract `signatureData` from calldata.
2. Call `deployToken(signatureData, metadata)` on Arbitrum's `OmniBridge` with identical arguments.
3. Arbitrum computes `keccak256(Metadata | token | name | symbol | decimals)` — identical to Ethereum's hash — and `ECDSA.recover` returns the same `nearBridgeDerivedAddress`. Signature verification passes.
4. A new `BridgeToken` is deployed on Arbitrum and `isBridgeToken` is set, without NEAR ever signing a message for Arbitrum.
5. Any subsequent legitimate `deployToken` for the same NEAR token ID on Arbitrum reverts with `ERR_TOKEN_EXIST` (line 157), permanently blocking NEAR's authorized deployment path on that chain.

## Impact Explanation

This is a **Critical** cross-chain replay / chain-domain separation flaw enabling unauthorized deployer-equivalent actions. An unprivileged attacker can deploy bridge tokens on any EVM chain (and Starknet/Solana) without NEAR's per-chain authorization, executing an action that is exclusively reserved for the NEAR bridge's MPC-signed flow. The permanent `ERR_TOKEN_EXIST` revert on subsequent legitimate calls means NEAR loses the ability to deploy the canonical token on the affected chain through its own authorized flow. This matches the allowed impact class: "Unauthorized transaction, authorization bypass... that lets an attacker execute bridge, token, deployer, relayer, or admin-equivalent actions" and "Cross-chain replay... chain/domain separation flaw enabling invalid finalization."

## Likelihood Explanation

- All EVM `OmniBridge` deployments share the same `nearBridgeDerivedAddress` (same NEAR account + path `"bridge-1"`).
- Every `deployToken` transaction is public on-chain; the signature is trivially extractable from calldata.
- No special access, private keys, or admin compromise is required — any observer of a `deployToken` transaction on one chain can replay it on all others.
- The bridge is live on Ethereum, Arbitrum, Base, and Polygon simultaneously, making the replay surface immediately available.
- The attack is repeatable for every new token that gets deployed via `deployToken`.

## Recommendation

Include the destination chain identifier in the `MetadataPayload` hash for all three implementations:

**EVM** — add `omniBridgeChainId` to the `borshEncoded` bytes in `deployToken`:
```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
    bytes1(omniBridgeChainId),   // add this
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
```

**Starknet** — change `MetadataPayloadImpl::to_borsh()` to accept and embed `chain_id: u8`, mirroring `TransferMessagePayloadImpl::to_borsh(chain_id)`, and update `deploy_token` to pass `self.omni_bridge_chain_id.read()`.

**Solana** — write `SOLANA_OMNI_BRIDGE_CHAIN_ID` into `DeployTokenPayload::serialize_for_near()` before the token fields, mirroring the pattern already used in `FinalizeTransferPayload`.

The NEAR-side signing path (`sign_log_metadata` / `log_metadata`) must be updated to include the destination chain ID in the payload it signs, so that chain-bound signatures are produced correctly.

## Proof of Concept

1. Monitor Ethereum mainnet for a `deployToken(signatureData, metadata)` call. Extract `signatureData` from the transaction calldata.
2. Submit `deployToken(signatureData, metadata)` to Arbitrum's `OmniBridge` with identical arguments.
3. Verify: Arbitrum computes `keccak256(0x00 || borsh(token) || borsh(name) || borsh(symbol) || decimals)` — identical to Ethereum's hash. `ECDSA.recover` returns `nearBridgeDerivedAddress`. The check at line 151 passes.
4. Observe: A `BridgeToken` is deployed on Arbitrum, `nearToEthToken[metadata.token]` is set, `isBridgeToken` is marked `true`.
5. Attempt a legitimate `deployToken` for the same NEAR token ID on Arbitrum: it reverts with `ERR_TOKEN_EXIST` (line 157).
6. Repeat for Base, BNB, Polygon, HyperEVM, and Abstract using the same `signatureData`.

A local integration test can be written using Hardhat with two forked networks (Ethereum + Arbitrum), deploying `OmniBridge` on both with the same `nearBridgeDerivedAddress`, signing a `MetadataPayload` once, and calling `deployToken` on both — confirming both calls succeed with the same signature.
