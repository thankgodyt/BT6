### Title
Refund Gas Fee Locked at Request Time Causes Permanent Stuck State When BTC Fee Market Rises - (File: contracts/satoshi-bridge/src/refund.rs)

---

### Summary

The refund gas fee is immutably fixed at `request_refund` time and stored in `RefundRequest.gas_fee`. There is no mechanism for a user to increase this fee after submission. If the Bitcoin fee market rises between request and execution, the refund transaction will not confirm, and the user's deposit UTXO is permanently locked in the bridge until an operator manually rejects the request — a stuck bridge state requiring privileged intervention.

---

### Finding Description

When a user calls `request_refund`, the gas fee is resolved once and stored permanently: [1](#0-0) 

```rust
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
...
let refund_request = RefundRequest {
    ...
    gas_fee: resolved_gas_fee,
    ...
};
```

This `gas_fee` is then used verbatim in `refund_execution_inputs` to compute the refund output value: [2](#0-1) 

```rust
let refund_amount = refund_request
    .amount
    .checked_sub(refund_request.gas_fee)
    .expect("Deposit amount too small to cover gas fee");
```

And propagated unchanged into the `BTCPendingInfo` created by `finalize_refund_with_psbt`: [3](#0-2) 

If the Bitcoin fee market rises after the request is stored, the resulting refund transaction carries an insufficient fee and will not confirm. The user can call `execute_refund` again (the `executed` flag permits re-execution after a consensus branch change), but the gas fee is still read from the same immutable `RefundRequest`: [4](#0-3) 

A second `request_refund` for the same UTXO is blocked: [5](#0-4) 

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
```

The only escape is for a privileged operator to call `internal_reject_refund`: [6](#0-5) 

Unlike withdrawals, which have a full RBF subsystem (`internal_withdraw_rbf`, `internal_cancel_withdraw`), refunds have no fee-bump path at all.

---

### Impact Explanation

The user's deposit UTXO is marked in `verified_deposit_utxo` upon `execute_refund`, blocking any `verify_deposit` from minting nBTC for it. The UTXO is simultaneously unspendable by the bridge (it is not in the available UTXO set) and unrecoverable by the user without operator action. This is a **stuck bridge state requiring operator intervention** — matching the Medium allowed impact.

---

### Likelihood Explanation

Bitcoin fee markets are volatile. A user who submits a refund request during a low-fee window (e.g., weekend, off-peak) and whose refund transaction is not mined before a fee spike (e.g., inscription wave, halving congestion) will be stuck. The mandatory `refund_timelock_sec` delay between request and execution increases the window during which the fee market can move. This scenario is realistic and repeatable.

---

### Recommendation

1. Allow `execute_refund` to accept an optional updated `gas_fee` parameter. If provided and higher than the stored value, update `RefundRequest.gas_fee` before building the PSBT.
2. Alternatively, implement a `refund_rbf` path analogous to `internal_withdraw_rbf` that lets the user bump the fee on an already-submitted refund pending info.
3. At minimum, document that users should set a conservative (high) gas fee at request time, and ensure operators have a clear SLA for rejecting stuck requests.

---

### Proof of Concept

1. User sends BTC to deposit address; relayer never submits `verify_deposit`.
2. User calls `request_refund` with `gas_fee = 500 sat` (current market rate). `RefundRequest` is stored with `gas_fee = 500`.
3. Timelock elapses. User calls `execute_refund`. Bridge builds a PSBT paying `deposit_amount − 500` to the user and 500 sat as miner fee. UTXO is added to `verified_deposit_utxo`.
4. Bitcoin fee market spikes to 5 000 sat/vbyte. The 500-sat refund transaction is never mined.
5. User calls `execute_refund` again — permitted because `refund_request.executed == true` — but `refund_request.gas_fee` is still 500. Same unconfirmed transaction is re-created.
6. User attempts a new `request_refund` for the same UTXO — rejected: `"Refund request already exists for this UTXO"`.
7. User's BTC is permanently locked until an operator calls `internal_reject_refund`, clearing the request so the user can start over with a higher fee.
