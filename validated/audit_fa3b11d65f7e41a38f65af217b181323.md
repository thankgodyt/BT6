### Title
Fee-on-Transfer Token Escrow Mis-Accounting in `initTransfer` — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

### Summary
`OmniBridge.initTransfer` uses the caller-supplied `amount` parameter verbatim in the `InitTransfer` event without measuring the tokens actually received. For fee-on-transfer ERC-20 tokens the contract receives `amount − fee`, yet NEAR credits the user with the full `amount`, permanently undercollateralising the EVM escrow and eventually preventing later users from withdrawing their funds.

### Finding Description
In `initTransfer`, the non-bridge / non-custom-minter branch transfers tokens from the caller and then emits the event using the same `amount` argument:

```solidity
// lines 407-411
IERC20(tokenAddress).safeTransferFrom(
    msg.sender,
    address(this),
    amount          // ← requested, not verified
);
```

```solidity
// lines 427-436
emit BridgeTypes.InitTransfer(
    msg.sender,
    tokenAddress,
    currentOriginNonce,
    amount,         // ← same unverified value
    fee,
    nativeFee,
    recipient,
    message
);
```

The NEAR `omni-bridge` contract ingests the `InitTransfer` event as the sole source of truth for the transfer amount and credits the recipient with `amount` tokens on the destination chain. Because no balance-before / balance-after check is performed, any token that deducts a fee during `transferFrom` (fee-on-transfer tokens) causes the EVM contract to hold fewer tokens than NEAR believes it holds. The deficit compounds with every such transfer.

### Impact Explanation
The EVM escrow becomes undercollateralised by the cumulative fee-on-transfer deductions. When users later bridge tokens back to EVM, `finTransfer` attempts to release the full signed `amount` via `IERC20.safeTransfer`, but the contract's actual balance is insufficient. The last users to redeem are unable to withdraw, resulting in permanent, irrecoverable loss of bridged funds — matching the "permanent freezing of bridged funds" criterion.

### Likelihood Explanation
Any unprivileged user can call `initTransfer` with a fee-on-transfer ERC-20 token. No special role, leaked key, or admin action is required. Fee-on-transfer tokens are a well-established token category (e.g., tokens with auto-liquidity or reflection mechanics). The root cause is in the bridge code itself (absence of a received-amount check), not solely in the external token's behaviour.

### Recommendation
Measure the actual received amount with a balance snapshot:

```solidity
uint256 balanceBefore = IERC20(tokenAddress).balanceOf(address(this));
IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
uint128 actualReceived = uint128(
    IERC20(tokenAddress).balanceOf(address(this)) - balanceBefore
);
// use actualReceived in the event and downstream logic
```

Alternatively, explicitly block fee-on-transfer tokens via an allowlist or a pre-transfer balance check that reverts if `actualReceived < amount`.

### Proof of Concept
1. Deploy a fee-on-transfer ERC-20 (e.g., 1 % deducted on every `transferFrom`).
2. Alice calls `initTransfer(token, 1000, 0, 0, nearRecipient, "")`.
3. Bridge receives **990** tokens; `InitTransfer` event emits `amount = 1000`.
4. NEAR processes the event and releases/mints **1000** tokens to `nearRecipient`.
5. Repeat N times — each iteration widens the deficit by 10 tokens.
6. Bob, a legitimate user who bridged a standard token, calls `finTransfer` to redeem; the bridge's balance is exhausted and the call reverts, permanently freezing Bob's funds. [1](#0-0) [2](#0-1) [3](#0-2)
