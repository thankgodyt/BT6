Audit Report

## Title
Token-2022 TransferFeeConfig Causes Vault Under-Crediting While Cross-Chain Message Over-Reports Amount — (`solana/programs/bridge_token_factory/src/instructions/user/init_transfer.rs`)

## Summary

`InitTransfer::process` calls `transfer_checked` with `payload.amount` on a Token-2022 mint that has a `TransferFeeConfig` extension. The SPL Token-2022 runtime withholds a fee from the destination, so the vault receives `amount - fee` tokens while the Wormhole message encodes the original `payload.amount`. NEAR finalizes a release of `amount` tokens worth of assets against a vault that only holds `amount - fee`, permanently breaking the lock/mint invariant and progressively under-collateralizing the vault.

## Finding Description

In `InitTransfer::process`, the native-token branch transfers `payload.amount` into the vault: [1](#0-0) 

Immediately after, the Wormhole message is posted using the same unmodified `payload`: [2](#0-1) 

The serialized payload encodes `self.amount` directly without any fee adjustment: [3](#0-2) 

`log_metadata` creates the vault PDA and unpacks Token-2022 extensions only for `MetadataPointer` — it never inspects `TransferFeeConfig`: [4](#0-3) 

The `token_program` field is typed as `Interface<'info, TokenInterface>`, which accepts Token-2022, and `mint` is `InterfaceAccount<'info, Mint>`, which accepts Token-2022 mints with any extension set. Neither `InitTransfer` nor `LogMetadata` checks for a `TransferFeeConfig` extension. [5](#0-4) 

Under Token-2022 transfer fee semantics, `transfer_checked(amount=1000, fee_rate=10%)` debits the sender 1000, credits the vault's spendable balance 900, and withholds 100 in the vault's `TransferFeeAmount` extension (not spendable until harvested by the fee authority). The Wormhole message reports 1000. The invariant `vault_balance_increase == cross_chain_amount` is broken on every call.

`finalize_transfer` later attempts to transfer the full NEAR-reported amount from the vault: [6](#0-5) 

After N transfers with a 10% fee, the vault holds `N * 900` spendable tokens while NEAR has authorized release of `N * 1000`. Redemptions for later users will fail or drain the vault faster than it was filled.

`solana/SECURITY.md` explicitly acknowledges that Token-2022 transfer hooks are unsupported (runtime denial, not fund loss), but makes no mention of `TransferFeeConfig` and does not exclude it: [7](#0-6) 

## Impact Explanation

This is a concrete instance of **escrow mis-accounting / fee mis-accounting that changes user and protocol balances**, matching the allowed Critical impact class. Every `init_transfer` on a Token-2022 mint with a non-zero `TransferFeeConfig` causes NEAR to over-release assets by exactly the fee amount. Accumulated over multiple transfers, the Solana vault becomes permanently under-collateralized relative to NEAR's accounting. Users who bridge back will find the vault unable to satisfy their redemptions, resulting in permanent loss of bridged funds.

## Likelihood Explanation

Token-2022 is explicitly supported by the bridge (imports `token_2022`, `token_interface`, `TokenInterface` throughout). Any Token-2022 mint with a `TransferFeeConfig` extension — whether a legitimate DeFi token or an attacker-created mint — triggers this path. No special privilege is required. An attacker can create a Token-2022 mint with an arbitrary fee rate, mint tokens to themselves, register the mint via `log_metadata`, and repeatedly call `init_transfer` to widen the accounting gap. The attack is repeatable, permissionless, and requires no victim mistakes.

## Recommendation

After `transfer_checked` completes, read the vault's actual post-transfer spendable balance (e.g., reload the vault account and compute `post_balance - pre_balance`) and use that delta — not `payload.amount` — when constructing the Wormhole message. Alternatively, reject Token-2022 mints that have a `TransferFeeConfig` extension with a non-zero fee in both `log_metadata` and `init_transfer` by unpacking the mint's extension data (analogous to how `log_metadata` already unpacks `MetadataPointer`) and returning an error if a non-zero fee is detected.

## Proof of Concept

1. On localnet, create a Token-2022 mint with `TransferFeeConfig` set to 1000 bps (10%), `max_fee = u64::MAX`.
2. Mint 10,000 tokens to an attacker-controlled token account.
3. Call `log_metadata` to register the mint and create the vault PDA (succeeds — no fee extension check).
4. Call `init_transfer` with `payload.amount = 1000`, `payload.fee = 0`, `payload.native_fee = 0`.
5. Assert: vault spendable balance increased by **900** (Token-2022 withheld 100 as fee).
6. Assert: the Wormhole message payload encodes `amount = 1000`.
7. Observe the invariant violation: `vault_balance_increase (900) < payload.amount (1000)`.
8. Repeat N times; after N transfers the vault is under-collateralized by `N * 100` tokens while NEAR has authorized release of `N * 1000` tokens worth of assets. A subsequent `finalize_transfer` for the full NEAR-reported amount will fail once the deficit exceeds the vault's spendable balance.
