### Title
Premature Token Minting Before Registration Check Causes Permanent nBTC Lock — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

In `safe_mint`, the nBTC token contract mints `amount` tokens into the bridge's own account **before** checking whether the recipient account is registered. If the recipient is unregistered, the function returns `U128(0)` immediately, leaving the freshly minted tokens permanently stranded in the bridge's balance with no recovery path for the depositing user.

---

### Finding Description

`safe_mint` executes in this order:

1. `self.token.internal_deposit(&self.bridge_id, amount.into())` — unconditionally increases total supply and the bridge's token balance by `amount`.
2. `if self.token.accounts.get(&account_id).is_none() { return PromiseOrValue::Value(U128(0)); }` — if the recipient has no registered storage slot, the function exits early. [1](#0-0) 

The minted tokens are never transferred to the user and are never burned. There is no `lost_found` entry created, no rollback of the `internal_deposit`, and no operator-facing recovery hook inside `safe_mint` itself. The bridge's nBTC balance grows by `amount` while the user receives nothing.

This is structurally analogous to the reported `TokenState.sol` bug: a supply/accounting state transition (`purchasedToUnlocked` / `internal_deposit`) is triggered based on a condition that does not correctly represent the intended invariant. In the original report the wrong variable (`_purchased[holder]`) was compared; here the wrong ordering means the supply-inflating operation fires unconditionally before the gating check.

---

### Impact Explanation

- **Total nBTC supply is permanently inflated** by `amount` without a corresponding user balance — the bridge holds unbacked tokens.
- **The depositing user's BTC is locked** in the bridge-controlled address; they receive zero nBTC and have no on-chain path to reclaim either asset without operator intervention.
- Matches allowed impact: *"stuck bridge state requiring operator intervention"* and *"permanent burning below backed supply"* (supply/backing ratio is broken).

---

### Likelihood Explanation

NEAR NEP-141 token contracts require explicit `storage_deposit` registration before an account can hold tokens. New bridge users — especially those interacting via third-party integrations or automated scripts — may deposit BTC before registering with the nBTC contract. The bridge's deposit verification flow calls `safe_mint` on success; any such unregistered recipient silently triggers the stuck-state path.

---

### Recommendation

Move the registration check **before** `internal_deposit`, or add the stranded amount to `lost_found` (already used elsewhere in the bridge for failed transfers) so the user can recover after registering:

```rust
// Option A: gate on registration first
if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0));
}
self.token.internal_deposit(&self.bridge_id, amount.into());
```

```rust
// Option B: mint then recover via lost_found
self.token.internal_deposit(&self.bridge_id, amount.into());
if self.token.accounts.get(&account_id).is_none() {
    // credit lost_found so user can claim after registering
    self.lost_found.entry(account_id).and_modify(|v| *v += amount.0).or_insert(amount.0);
    return PromiseOrValue::Value(U128(0));
}
```

---

### Proof of Concept

1. User deposits BTC to a bridge address derived from a NEAR account that has **not** called `storage_deposit` on the nBTC contract.
2. A relayer submits the Merkle proof; the bridge verifies it and calls `safe_mint(unregistered_account, amount, None)`.
3. `internal_deposit(&self.bridge_id, amount)` executes — bridge balance `+amount`, total supply `+amount`. [2](#0-1) 
4. `self.token.accounts.get(&account_id).is_none()` returns `true`. [3](#0-2) 
5. Function returns `U128(0)` — user receives **zero** nBTC.
6. `amount` tokens are permanently held by the bridge with no on-chain claim record; user's BTC remains locked in the bridge-controlled UTXO.
