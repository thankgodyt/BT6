### Title
Peras Certificate Validation Unconditionally Accepts All Certificates, Enabling Unauthorized Chain Weight Manipulation — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production default `BlockSupportsPeras` instance implements `validatePerasCert` as a stub that unconditionally returns `Right` without performing any cryptographic or semantic checks. An unprivileged peer can inject an arbitrary `PerasCert` message via the Peras certificate diffusion mini-protocol; the certificate will pass validation, be stored in the `PerasCertDB`, and its weight boost will be applied during chain selection — potentially causing an honest node to prefer an adversarially-crafted fork over the canonical chain.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub:**

The degenerate `instance StandardHash blk => BlockSupportsPeras blk` in `SupportsPeras.hs` is the production fallback for all block types. Its `validatePerasCert` implementation unconditionally returns `Right`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature verification, no quorum check, no round-number bounds check, and no boosted-block existence check is performed. Every certificate presented by any peer is accepted as `ValidatedPerasCert`.

**Asymmetry with block header validation:**

Block header validation enforces KES and VRF signature checks via `updateChainDepState` (the `ConsensusProtocol` class), and these checks are applied to every header received from every peer before the header enters a candidate fragment. [2](#0-1) 

Peras certificate validation is the analogous gate for the certificate diffusion path, but it is absent. The asymmetry is structurally identical to the reported bug: one code path (block headers) has a mandatory check; the related code path (Peras certificates) does not.

**Attacker-controlled entry path:**

1. An unprivileged peer sends a crafted `PerasCert` via the Peras certificate diffusion mini-protocol.
2. `processCerts` in `ObjectPool/PerasCert.hs` calls `validatePerasCert mkPerasParams` on each inbound certificate. Because the stub always returns `Right`, the certificate is treated as valid. [3](#0-2) 
3. The validated certificate is passed to `ChainDB.addPerasCertAsync`, which enqueues a `ChainSelAddPerasCert` message. [4](#0-3) 
4. `chainSelSync` processes the message: it stores the certificate in `PerasCertDB` and calls `chainSelectionForBlock` for the boosted block. [5](#0-4) 
5. `preferAnchoredCandidate` now uses the updated `PerasWeightSnapshot` (which includes the adversarially-injected boost) to compare the candidate fragment against the current chain. [6](#0-5) 
6. If the boosted block is on a fork, the fork's total weight may now exceed the current chain's weight, causing the node to switch to the adversarial fork.

**Weight boost magnitude:**

The boost assigned to each accepted certificate is `perasWeight params` from `mkPerasParams`. The `SecurityParam` is reinterpreted as a weight budget under Peras: `k == 30` means a chain fragment with total weight 30 cannot be rolled back. A single injected certificate with boost ≥ k can therefore make a fork appear heavier than the honest chain by more than the rollback budget. [7](#0-6) 

---

### Impact Explanation

**Severity: High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain.**

An adversary who can send a single crafted `PerasCert` message (no stake, no keys required) can:

- Cause the receiving node to switch to a fork by artificially inflating that fork's Peras weight beyond the honest chain's weight.
- Bypass the Peras certificate quorum requirement entirely, since no quorum check is performed.
- Repeat the attack for successive rounds, continuously steering the node away from the canonical chain.

This directly matches the allowed impact scope: *"Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance"* and *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain."*

---

### Likelihood Explanation

**Condition:** Peras must be enabled (non-empty `PerasWeightSnapshot`). The CHANGELOG states Peras is disabled by default; when disabled, `isEmptyPerasWeightSnapshot weights` is true and the Peras branch of `preferAnchoredCandidate` is never taken. [8](#0-7) 

**When Peras is enabled:** The attack requires only network access. No stake, no keys, no privileged position. The certificate diffusion mini-protocol is a public peer-to-peer channel. The stub validation is the only gate, and it always passes. Likelihood is **high** for any deployment with Peras enabled.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:

1. The aggregate BLS signature over `(pcCertRound, pcCertBoostedBlock)` against the aggregated public keys of the claimed voters (using `verifyAggregateVoteSignature` from `PerasBLSCrypto`). [9](#0-8) 
2. That the claimed voters' combined stake meets the quorum threshold (`stakeAboveThreshold`). [10](#0-9) 
3. That the VRF eligibility proofs for non-persistent voters are valid (`batchVerifyVRFOutputs`). [11](#0-10) 
4. That `pcCertRound` and `pcCertBoostedBlock` are within acceptable bounds relative to the current chain state.

Until this is implemented, Peras certificate diffusion should remain disabled in any deployment where the weight-based chain selection path is reachable.

---

### Proof of Concept

**Setup:** Two nodes, A (honest) and B (adversary). Peras is enabled with weight boost W > 0. Node A's current chain has total weight T. A fork F exists in A's VolatileDB with total weight T − 1 (just below A's chain).

**Attack:**

```
B → A: PerasCert { pcCertRound = R, pcCertBoostedBlock = tip(F) }
```

**Trace through the code:**

1. `processCerts` calls `validatePerasCert mkPerasParams cert` → `Right (ValidatedPerasCert { vpcCertBoost = W })`. [12](#0-11) 
2. `addPerasCertAsync` enqueues `ChainSelAddPerasCert`. [13](#0-12) 
3. `chainSelSync` stores the cert; `getWeightSnapshot` now returns a snapshot with `tip(F) → W`. [14](#0-13) 
4. `chainSelectionForBlock` runs; `preferAnchoredCandidate` computes `totalWeightOfFragment` for F's suffix as `(T−1) + W`. If `W ≥ 2`, this exceeds T, and `ShouldSwitch` is returned. [15](#0-14) 
5. Node A switches to fork F — the adversarial chain — without B having produced any valid blocks or certificates.

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```

-- In weightiest-chain protocols (such as Ouroboros Peras), we interpret this as
-- the maximum amount of weight we can roll back. Here, the total weight of a
