### Title
Non-Standard `ft_transfer` Override Silently Locks User Tokens When `withdraw_relayer_address` Is Unset — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary
The nBTC contract overrides the standard NEP-141 `ft_transfer` with a non-standard legacy withdrawal redirect. When `withdraw_relayer_address` is not configured and the nBTC contract account is registered in its own token ledger (a permissionless action), any user invoking the legacy `WITHDRAW_TO:` flow will have their tokens silently transferred to the nBTC contract itself and permanently locked with no recovery path.

---

### Finding Description

The `FungibleTokenCore::ft_transfer` implementation in `contracts/nbtc/src/lib.rs` deviates from the NEP-141 standard by inserting a conditional redirect: [1](#0-0) 

```rust
fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
    if receiver_id == env::current_account_id()
        && memo.as_ref().is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
    {
        if let Some(withdraw_relayer) = Self::read_withdraw_relayer_address() {
            return self.token.ft_transfer(withdraw_relayer, amount, memo);
        }
        // ← NO early return / NO error here when relayer is unset
    }
    self.token.ft_transfer(receiver_id, amount, memo); // receiver_id == nbtc contract itself
}
```

The outer `if` block is entered whenever `receiver_id == nbtc_contract` AND the memo starts with `WITHDRAW_TO:`. Inside, `read_withdraw_relayer_address()` is called: [2](#0-1) 

If it returns `None` (relayer address not set), the inner `if let Some` arm is skipped and **no early return is issued**. Execution falls through to the unconditional `self.token.ft_transfer(receiver_id, amount, memo)` at line 195, where `receiver_id` is still `env::current_account_id()` — the nBTC contract itself.

The nBTC contract is **not** registered as an account in its own token ledger by the constructor: [3](#0-2) 

Only `bridge_id` is registered. However, `storage_deposit` is a permissionless public function: [4](#0-3) 

Any caller can invoke `storage_deposit(account_id: Some(nbtc_contract), registration_only: Some(true))` with a small NEAR deposit to register the nBTC contract as a valid token recipient. Once registered, the fallthrough `ft_transfer` to `receiver_id = nbtc_contract` succeeds, depositing the user's tokens into the contract's own ledger entry. There is no function in the contract to withdraw or recover tokens held under the contract's own account ID — they are permanently locked.

The `withdraw_relayer_address` is only set during `migrate_from_poa`: [5](#0-4) 

A fresh deployment via `new()` never sets it. The `new()` constructor has no provision for it: [6](#0-5) 

---

### Impact Explanation
Any user who calls `ft_transfer(receiver_id=nbtc_contract, amount=X, memo="WITHDRAW_TO:...")` — the documented Near Intents legacy withdrawal path — when `withdraw_relayer_address` is unset will permanently lose their tokens. The tokens are deposited into the nBTC contract's own ledger slot with no recovery mechanism. This constitutes **permanent locking of user funds**.

---

### Likelihood Explanation
- **Permissionless setup**: Registering the nBTC contract as an account requires only a `storage_deposit` call — no privileged access needed.
- **Deployment window**: Any fresh deployment of the nBTC contract (via `new()`) starts without `withdraw_relayer_address` set. During this window, the legacy flow is broken.
- **User-reachable**: The legacy `WITHDRAW_TO:` flow is the documented path for Near Intents users. It is a public, unprivileged entry point.
- **No warning**: The fallthrough is silent — no panic, no event, no error. The user's transaction succeeds and emits a standard `ft_transfer` event, making the loss non-obvious.

---

### Recommendation
Add an explicit guard in the legacy branch so that if `withdraw_relayer_address` is unset, the transaction panics rather than silently falling through:

```rust
fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
    if receiver_id == env::current_account_id()
        && memo.as_ref().is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
    {
        let withdraw_relayer = Self::read_withdraw_relayer_address()
            .unwrap_or_else(|| env::panic_str("Withdraw relayer address not configured"));
        return self.token.ft_transfer(withdraw_relayer, amount, memo);
    }
    self.token.ft_transfer(receiver_id, amount, memo);
}
```

This mirrors the recommendation in the original report: restore standard behavior and make deviations explicit and safe, rather than silently falling through to an unintended code path.

---

### Proof of Concept

1. Deploy nBTC contract via `new(controller, bridge_id, ...)` — `withdraw_relayer_address` is not set.
2. Attacker calls `storage_deposit(account_id: Some(nbtc_contract_id), registration_only: Some(true))` with a small NEAR deposit. The nBTC contract is now a registered token account.
3. User (Near Intents participant) calls `ft_transfer(receiver_id=nbtc_contract_id, amount=1_000_000, memo="WITHDRAW_TO:bc1q...")` attaching 1 yoctoNEAR.
4. Inside `ft_transfer`: `receiver_id == current_account_id()` ✓, memo starts with `WITHDRAW_TO:` ✓ → outer `if` entered.
5. `read_withdraw_relayer_address()` returns `None` → inner `if let Some` skipped, no `return`.
6. Falls through to `self.token.ft_transfer(nbtc_contract_id, 1_000_000, memo)`.
7. nBTC contract is registered → `internal_transfer(user, nbtc_contract, 1_000_000)` succeeds.
8. User's 1,000,000 nBTC units are now held under the nBTC contract's own account with no withdrawal path. Permanently locked.
