### Title
Missing `from.owner == user` Constraint Enables SPL-Delegate to Steal Victim Tokens Cross-Chain — (`solana/programs/bridge_token_factory/src/instructions/user/init_transfer.rs`)

---

### Summary

The `InitTransfer` accounts struct imposes no constraint linking the `from` token account to the `user` signer. Because SPL token's `transfer_checked` and `burn` instructions accept either the account owner **or** an approved delegate as authority, any attacker holding a delegate approval over a victim's ATA can call `init_transfer`, drain the victim's tokens into the vault or burn them, and have the Wormhole VAA encode the attacker's pubkey as sender and the attacker's NEAR address as recipient — completing a full cross-chain theft.

---

### Finding Description

The `from` account in `InitTransfer` is declared with only two semantic constraints:

```rust
#[account(
    mut,
    token::mint = mint,
    token::token_program = token_program,
)]
pub from: Box<InterfaceAccount<'info, TokenAccount>>,
``` [1](#0-0) 

There is no `constraint = from.owner == user.key()` or equivalent. The `user` account is independently validated only as a signer owned by the system program:

```rust
#[account(
    mut,
    owner = common.system_program.key(),
)]
pub user: Signer<'info>,
``` [2](#0-1) 

In `process()`, both the native-token path (`transfer_checked`) and the bridged-token path (`burn`) pass `self.user.to_account_info()` as the SPL authority: [3](#0-2) [4](#0-3) 

The SPL token program accepts either the account owner **or** an approved delegate as a valid authority for both operations. Therefore, if the attacker is a delegate on the victim's ATA, the CPI succeeds without any bridge-level rejection.

After the token operation, the Wormhole message is constructed with `self.user.key()` — the attacker's pubkey — serialized as the `sender` field:

```rust
self.common.post_message(payload.serialize_for_near((
    self.common.sequence.sequence,
    self.user.key(),   // ← attacker's pubkey
    self.mint.key(),
))?)?;
``` [5](#0-4) 

Inside `serialize_for_near`, `params.1` (the attacker's pubkey) is written as the sender, and `self.recipient` (the attacker's NEAR address, supplied in the payload) is written as the recipient: [6](#0-5) 

The Wormhole guardians threshold-sign this VAA as a valid outgoing bridge message. The attacker then presents the VAA on NEAR to claim the victim's tokens.

---

### Impact Explanation

An attacker who has obtained (or socially engineered) a delegate approval over any victim ATA can:
1. Burn or lock the victim's tokens without the victim's knowledge or consent.
2. Receive a Wormhole VAA signed by the guardian threshold-signing system that encodes the attacker as the legitimate sender.
3. Claim the full token value on NEAR to an address they control.

This is a complete, irreversible cross-chain theft of the victim's bridged assets.

---

### Likelihood Explanation

SPL `approve()` is a standard, widely-used primitive. Users routinely grant delegate approvals to DeFi protocols, aggregators, and other programs. Any such approval — even one granted to a seemingly legitimate contract that is later compromised — is sufficient to trigger this exploit. The precondition is realistic and requires no privileged access beyond a single prior `approve()` call by the victim.

---

### Recommendation

Add an explicit ownership constraint on the `from` account in the `InitTransfer` accounts struct:

```rust
#[account(
    mut,
    token::mint = mint,
    token::token_program = token_program,
    constraint = from.owner == user.key() @ ErrorCode::InvalidOwner,
)]
pub from: Box<InterfaceAccount<'info, TokenAccount>>,
```

This ensures that only the actual owner of the token account can initiate a bridge transfer, regardless of any outstanding delegate approvals.

---

### Proof of Concept

```rust
// 1. Victim approves attacker as delegate on victim_ata for amount X
spl_token::instruction::approve(
    &token_program_id,
    &victim_ata,
    &attacker_pubkey,
    &victim_pubkey,
    &[],
    X,
)?;

// 2. Attacker calls init_transfer:
//    from     = victim_ata        (passes token::mint = mint check)
//    user     = attacker_keypair  (passes Signer + system owner check)
//    recipient = attacker_near_account (caller-controlled field in payload)
//    amount   = X

// 3. SPL token program accepts burn/transfer_checked because attacker is delegate.
//    No bridge-level check rejects this.

// 4. Wormhole VAA is posted with:
//    sender    = attacker_pubkey
//    recipient = attacker_near_account
//    amount    = X

// 5. Wormhole guardians threshold-sign the VAA.
// 6. Attacker submits VAA on NEAR and claims X tokens.

// Assert: process() should return Err(ErrorCode::InvalidOwner) but instead returns Ok(()).
```
