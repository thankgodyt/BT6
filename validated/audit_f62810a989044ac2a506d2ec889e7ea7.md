### Title
Relayer's `signer_account_id()` Exposed to Untrusted Recipient Contract via `ft_transfer_call` During `fin_transfer` - (File: `near/omni-bridge/src/lib.rs`)

---

### Summary

When a relayer finalizes a cross-chain transfer by calling `fin_transfer`, NEAR's `env::signer_account_id()` — the protocol-level equivalent of EVM's `tx.origin` — is set to the relayer's account ID and propagates through the entire cross-contract call chain. If the transfer's `msg` field is non-empty, the bridge dispatches `ft_transfer_call` to the recipient contract, whose `ft_on_transfer` callback executes with `signer_account_id()` = relayer. A malicious recipient contract can read this value and use it to drain the relayer's funds from any third-party NEAR contract that uses `signer_account_id()` for authorization.

---

### Finding Description

The `fin_transfer` function in `near/omni-bridge/src/lib.rs` is the relayer-facing entry point for finalizing inbound cross-chain transfers. The relayer is the transaction signer, so `env::signer_account_id()` equals the relayer's account ID for the entire receipt chain spawned by this call. [1](#0-0) 

After proof verification, `fin_transfer_callback` reconstructs the `TransferMessage`, which includes the `msg` field set by the original user on the source chain: [2](#0-1) 

When the recipient is a NEAR account, `process_fin_transfer_to_near` is called. It passes `transfer_message.msg` directly to `send_tokens`: [3](#0-2) 

Inside `send_tokens`, when `msg` is non-empty and the token is **not** a deployed (bridge-minted) token (i.e., it is a locked token such as USDC), the code takes the `ft_transfer_call` branch: [4](#0-3) 

`ft_transfer_call` on the NEP-141 token contract triggers `ft_on_transfer` on the recipient contract. At that point, `env::signer_account_id()` inside the recipient's callback is still the relayer — NEAR propagates the original transaction signer through all receipts in the chain, exactly as EVM propagates `tx.origin`.

The same exposure exists in `fast_fin_transfer_to_near_callback`, which also calls `send_tokens` with the user-supplied `fast_transfer.msg`: [5](#0-4) 

---

### Impact Explanation

A malicious recipient contract's `ft_on_transfer` can:

1. Read `env::signer_account_id()` to obtain the relayer's account ID.
2. Issue a cross-contract call to any third-party NEAR contract (staking, lending, DEX, etc.) that uses `signer_account_id()` for withdrawal authorization, passing the relayer's account as the beneficiary of a withdrawal.
3. Because `signer_account_id()` propagates through all receipts, the third-party contract sees the relayer as the signer and authorizes the withdrawal, draining the relayer's funds without the relayer's consent.

This results in direct, unauthorized theft of the relayer's funds held in any `signer_account_id()`-gated contract.

---

### Likelihood Explanation

- The `msg` field and `recipient` field are both fully attacker-controlled: they are set by the user who calls `initTransfer` on the source chain (e.g., Ethereum) and are embedded verbatim in the proof that the relayer submits.
- The bridge performs no validation on the content of `msg` or the nature of the recipient contract.
- Any unprivileged user can craft such a transfer. No special role or privilege is required.
- Relayers are active, funded participants who are likely to hold balances in DeFi protocols on NEAR, making the attack profitable.
- The only precondition is that the relayer has funds in a contract that uses `signer_account_id()` for authorization — a common pattern in NEAR contracts.

---

### Recommendation

Relayers should be advised to use a dedicated, single-purpose NEAR account for signing `fin_transfer` transactions, holding no balances in any third-party contract. This mirrors the Connext recommendation: the relayer's EOA should be single-purpose. Additionally, the bridge documentation should explicitly warn that the relayer's signing account must not be used for any other on-chain activity, as the `signer_account_id()` is exposed to arbitrary recipient contract code during `ft_transfer_call` dispatch.

---

### Proof of Concept

**Setup:**

1. Attacker deploys `malicious.near` implementing `ft_on_transfer`:
   ```rust
   pub fn ft_on_transfer(&mut self, ...) -> PromiseOrValue<U128> {
       let relayer = env::signer_account_id(); // = relayer's account
       // Call a third-party contract where relayer has funds,
       // using signer_account_id() for authorization
       ext_staking::ext("staking.near")
           .withdraw_all(relayer)
           .detach();
       PromiseOrValue::Value(U128(0))
   }
   ```

2. Attacker calls `initTransfer` on the Ethereum `OmniBridge` contract with:
   - `token` = USDC (a locked, non-deployed token on NEAR)
   - `recipient` = `malicious.near`
   - `msg` = `"trigger"` (any non-empty string)

3. A relayer picks up the event and calls `fin_transfer` on `omni.bridge.near`.

**Execution chain:**

```
relayer → fin_transfer (signer = relayer)
  → verify_proof
  → fin_transfer_callback
    → process_fin_transfer_to_near
      → send_tokens(token=USDC, recipient=malicious.near, msg="trigger")
        → USDC.ft_transfer_call(malicious.near, amount, "trigger")
          → malicious.near.ft_on_transfer(...)
              env::signer_account_id() == relayer  ← exposed
              → staking.near.withdraw_all(relayer) ← relayer funds drained
```

The relayer's funds in `staking.near` are withdrawn to the attacker without the relayer's knowledge or consent. [6](#0-5) [7](#0-6)
