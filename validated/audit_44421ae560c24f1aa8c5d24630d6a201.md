### Title
Unprivileged Attacker Can Redirect Victim's BTC to Attacker-Controlled Address via `request_refund` When `deposit_msg.refund_address` Is `None` — (`contracts/satoshi-bridge/src/api/bridge.rs` / `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`request_refund` is callable by any unprivileged account. When the victim's `DepositMsg.refund_address` is `None`, the contract imposes **no ownership check** on the caller-supplied `refund_address`. An attacker who observes the victim's on-chain deposit can register a refund request pointing to the attacker's own BTC address. After `unsafe_refund_timelock_sec` elapses — the only mitigation — the attacker calls `execute_refund` and the bridge's MPC pipeline signs a transaction that permanently sends the victim's BTC to the attacker.

---

### Finding Description

**Step 1 — `request_refund` has no caller restriction and no ownership guard when `refund_address` is `None`.**

`request_refund` sits in an `impl Contract` block annotated `#[trusted_relayer]` at the block level, but the function itself carries **no** `#[trusted_relayer]` attribute: [1](#0-0) 

Compare with `verify_deposit`, `verify_deposit_v2`, `safe_verify_deposit`, `verify_withdraw`, etc., which each carry `#[trusted_relayer]` on the function itself and are confirmed to reject non-relayer callers with "Relayer is not active". `request_refund` and `execute_refund` carry only `#[payable]` and `#[pause(...)]` — no relayer gate.

**Step 2 — The only address-ownership check is skipped when `deposit_msg.refund_address` is `None`.**

Inside `internal_request_refund`: [2](#0-1) 

The `if let Some(...)` branch is the **only** guard. When the victim's `DepositMsg` was created without a `refund_address` (a common case — the field is `Option<String>` and `skip_serializing_if = "Option::is_none"`), the branch is never entered. The attacker's arbitrary `refund_address` string passes through unchecked and is forwarded to `request_refund_callback`. [3](#0-2) 

**Step 3 — `request_refund_callback` stores the attacker's address verbatim.** [4](#0-3) 

`RefundRequest.refund_address` is set to whatever the caller passed. No post-hoc ownership verification occurs.

**Step 4 — `resolve_execute_refund_timelock` applies `unsafe_refund_timelock_sec` but no cryptographic ownership check.** [5](#0-4) 

The longer timelock is the **sole** mitigation. After it elapses, `execute_refund` is callable by anyone (no `#[trusted_relayer]` on the function), and `load_refund_request_for_execute` only checks that the timelock has passed and the UTXO was not already finalized via deposit: [6](#0-5) 

**Step 5 — `internal_execute_refund` builds the PSBT using the stored (attacker-controlled) `refund_address`.** [7](#0-6) 

The MPC pipeline signs a transaction whose output is the attacker's BTC address. Once broadcast, the victim's BTC is gone with no recovery path.

---

### Impact Explanation

The victim's entire deposited BTC is permanently redirected to the attacker's address. The bridge's MPC key signs the transaction; once the signed transaction is broadcast to Bitcoin, the UTXO is spent and the victim has no recourse. This is a direct, permanent theft of user funds.

---

### Likelihood Explanation

- `request_refund` is fully permissionless (no role, no signature from the original depositor).
- The victim's `DepositMsg` is public: it is emitted in the `LogDepositAddress` event when `get_user_deposit_address` is called.
- The BTC deposit transaction is public on-chain.
- The only barrier is the `unsafe_refund_timelock_sec` window during which DAO/Operator must notice and call `reject_refund`. If the DAO/Operator is offline, slow, or overwhelmed with spam requests, the attack succeeds.
- The victim cannot cancel the malicious refund request themselves — `reject_refund` requires DAO/Operator role or proof that the UTXO was already deposited. [8](#0-7) 

---

### Recommendation

Require that the caller of `request_refund` either:
1. Matches the `recipient_id` encoded in `deposit_msg` (proving NEAR-side ownership), **or**
2. Provides a `refund_address` that was pre-committed in `deposit_msg.refund_address`.

When `deposit_msg.refund_address` is `None` and the caller is not the `recipient_id`, the call should be rejected. This makes the refund path cryptographically tied to the original depositor rather than relying solely on operational monitoring.

---

### Proof of Concept

```
// Victim setup
deposit_msg = DepositMsg {
    recipient_id: "victim.near",
    refund_address: None,   // <-- no pre-authorized address
    ...
}
deposit_address = get_user_deposit_address(deposit_msg)
// Victim sends BTC to deposit_address; verify_deposit is never called.

// Attacker observes LogDepositAddress event → gets deposit_msg + tx_bytes + proof

// Attacker calls (no role required, attach ~2 NEAR):
request_refund(
    deposit_msg,                  // victim's msg, refund_address: None
    "bc1q_ATTACKER_ADDRESS",      // attacker's BTC address — no check fires
    tx_bytes,
    vout,
    proof,
    None
)
// request_refund_callback stores RefundRequest { refund_address: "bc1q_ATTACKER_ADDRESS", ... }

// Wait unsafe_refund_timelock_sec (DAO/Operator does not reject)

// Attacker calls (no role required):
execute_refund(utxo_storage_key, None)
// PSBT built with output = "bc1q_ATTACKER_ADDRESS"
// MPC signs → victim's BTC sent to attacker permanently
```

    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
