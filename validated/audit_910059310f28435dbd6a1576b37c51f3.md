### Title
Non-Payable MPC Signing Callback Causes Signing Failures When Excess NEAR Is Refunded - (File: `contracts/satoshi-bridge/src/chain_signature.rs`)

### Summary

The `sign_btc_transaction` entry point forwards the full `env::attached_deposit()` to the Chain Signatures MPC contract. When the user sends more NEAR than the exact signing fee, the Chain Signatures contract refunds the excess back to the bridge. That refund is delivered as an attached deposit on the `sign_btc_transaction_callback`. Because the callback is not marked `#[payable]`, the NEAR SDK panics with "Method doesn't accept deposit", causing the entire signing step to fail and leaving the withdrawal or refund permanently stuck in `PendingSign` state until a successful retry.

### Finding Description

`sign_btc_transaction` in `contracts/satoshi-bridge/src/api/chain_signatures.rs` is correctly marked `#[payable]` and passes the full attached deposit to the MPC contract: [1](#0-0) 

Inside `internal_sign_btc_transaction`, `sign_promise` is called, which forwards `env::attached_deposit()` verbatim to the Chain Signatures `sign` function: [2](#0-1) 

The promise chain then registers `sign_btc_transaction_callback` as the continuation: [3](#0-2) 

The callback itself is declared `#[private]` but **not** `#[payable]`: [4](#0-3) 

The NEAR Chain Signatures contract's `sign` function requires a deposit to cover the MPC fee. When the caller sends more than the exact fee, the Chain Signatures contract refunds the excess NEAR to its predecessor — the bridge contract — by attaching it to the callback invocation. The NEAR SDK enforces that any method not annotated with `#[payable]` panics immediately if it receives a non-zero attached deposit. Therefore, whenever the user over-pays even by 1 yoctoNEAR, `sign_btc_transaction_callback` panics before executing any of its logic.

### Impact Explanation

When the callback panics:
- The MPC signature is never saved to `btc_pending_info.signatures[sign_index]`.
- The `BTCPendingInfo` entry remains in `PendingSign` state indefinitely.
- For withdrawals, the user's nBTC is already held by the bridge (transferred in `ft_on_transfer`) and cannot be recovered until a successful signing round completes.
- For refunds, the refund PSBT is never signed, leaving the deposited BTC unrecoverable until a successful retry.

This matches the **Medium** impact class: attacker-triggered (or user-triggered) temporary locking of bridged funds and a stuck bridge state requiring operator or user intervention.

### Likelihood Explanation

The NEAR Chain Signatures `sign` fee is determined at execution time by the MPC network and can fluctuate between the moment a user queries the fee off-chain and the moment the transaction lands. Any user who sends even a single yoctoNEAR above the exact fee triggers the failure. Because `sign_btc_transaction` is a public, unprivileged entry point callable by any NEAR account, this is reachable by any bridge user initiating a withdrawal or refund.

### Recommendation

Add `#[payable]` to `sign_btc_transaction_callback` so it can accept the refunded NEAR without panicking:

```rust
#[private]
#[payable]   // ← add this
pub fn sign_btc_transaction_callback(
    &mut self,
    account_id: AccountId,
    btc_pending_sign_id: String,
    sign_index: usize,
) -> bool {
```

Any excess NEAR received by the callback should then be forwarded back to the original caller (the account that called `sign_btc_transaction`) rather than left inside the bridge contract.

### Proof of Concept

1. User calls `sign_btc_transaction` with `attached_deposit = exact_fee + 1 yoctoNEAR`.
2. Bridge calls `chain_signatures.sign(request)` with the full deposit.
3. Chain Signatures contract processes the request, refunds `1 yoctoNEAR` to the bridge by attaching it to the callback.
4. NEAR runtime invokes `sign_btc_transaction_callback` with `attached_deposit = 1 yoctoNEAR`.
5. NEAR SDK panics: `"Method doesn't accept deposit"`.
6. The callback receipt fails; the signature is never recorded; `BTCPendingInfo` stays in `PendingSign`.
7. The user's nBTC (or refund UTXO) is locked until a retry with the exact fee succeeds.
