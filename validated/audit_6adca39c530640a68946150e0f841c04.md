### Title
Unconditional `validatePerasCert` Acceptance Allows Any Peer to Inject Arbitrary Peras Certificates and Manipulate Chain Selection - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `BlockSupportsPeras` instance for all `StandardHash blk` types implements `validatePerasCert` as a stub that unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or structural checks. The production node-to-node handler wires this stub directly into the `PerasCertDiffusion` inbound path, which feeds accepted certificates into `ChainDB.addPerasCertAsync`. Any unprivileged peer that can negotiate the Peras cert diffusion mini-protocol can therefore inject a certificate pointing at any block hash, causing the receiving node to trigger chain selection for that block and potentially switch to an attacker-chosen fork.

---

### Finding Description

**Root cause — stub validation always succeeds:**

The `BlockSupportsPeras` instance (the only instance, covering all `StandardHash blk`) implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

No round-number range check, no quorum-of-committee-members proof, no cryptographic signature verification — every certificate is unconditionally promoted to `ValidatedPerasCert`. [1](#0-0) 

**Inbound network path wires this stub directly into production:**

`makePerasCertPoolWriterFromChainDB` passes `validatePerasCert mkPerasParams` as the sole validation gate for all peer-supplied certificates:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

This writer is installed in the production node-to-node handler for every inbound peer connection:

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      ...
``` [3](#0-2) 

**Contrast with the vote path (which has a partial mitigation):**

For votes, the production handler passes `(pure (PerasVoteStakeDistr mempty))` — an empty stake distribution — which causes every vote to fail the `lookupPerasVoteStake` lookup and be rejected. Certificates have no equivalent safety net; `validatePerasCert` ignores the stake distribution entirely and always succeeds. [4](#0-3) 

**Chain selection consequence:**

Once a certificate passes `processCerts`, it is stored in the `PerasCertDB` and forwarded to `ChainDB.addPerasCertAsync`. The `chainSelSync` handler then:
1. Looks up the boosted block in the `VolatileDB`.
2. If found, calls `chainSelectionForBlock` for that block, potentially switching the node's preferred chain to the fork containing the attacker-chosen block. [5](#0-4) 

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` with an arbitrary `pcCertBoostedBlock` pointing to any block hash present in the victim node's `VolatileDB`. Because `validatePerasCert` never rejects any certificate, the crafted cert is accepted, stored, and used to trigger chain selection for the attacker-chosen block. This lets the attacker make an honest node prefer a non-canonical fork — a direct chain-selection manipulation. The Peras weight boost assigned to the fake certificate (`perasWeight params`) is added to the candidate chain's weight, potentially causing it to exceed the current selection.

**Impact category: High** — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain beyond the intended security assumptions. [1](#0-0) 

---

### Likelihood Explanation

The `hPerasCertDiffusionClient` handler is wired unconditionally into the production node-to-node application. Any peer that successfully negotiates a node-to-node connection and the Peras cert diffusion sub-protocol version can immediately send crafted certificates. No keys, stake, or special privileges are required. The attacker only needs to know a block hash present in the victim's VolatileDB (obtainable via the ChainSync protocol). The TODO comment and the referenced issue (`cardano-peras/issues/120`) confirm this is a known placeholder, not an intentional design. [6](#0-5) 

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real check that verifies:
1. The certificate's round number falls within the expected range relative to the current ledger tip.
2. The certificate carries a valid aggregate proof-of-quorum from eligible committee members (VRF/KES signatures over the boosted block hash and round number).
3. The boosted block hash is structurally valid (non-genesis, correct length).

Until real validation is implemented, the inbound cert diffusion handler should reject all inbound certificates (analogous to how the vote path uses `PerasVoteStakeDistr mempty` to reject all votes), preventing any peer from influencing chain selection via this path. [3](#0-2) 

---

### Proof of Concept

**Attacker preconditions:** A node-to-node TCP connection to the victim; knowledge of any block hash `H` in the victim's VolatileDB (obtained via ChainSync).

**Steps:**

1. Connect to the victim node and negotiate the Peras cert diffusion mini-protocol.
2. Send a `PerasCert` message:
   ```
   PerasCert { pcCertRound = <any round>, pcCertBoostedBlock = <Point H> }
   ```
3. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams })` unconditionally.
4. The validated cert is passed to `ChainDB.addPerasCertAsync`.
5. `chainSelSync` looks up block `H` in the VolatileDB, finds it, and calls `chainSelectionForBlock` for it.
6. Chain selection now considers the fork containing `H` to have additional Peras weight equal to `perasWeight mkPerasParams`, potentially causing the victim to switch to that fork.

**Expected outcome:** The victim node switches its preferred chain to the fork containing the attacker-chosen block `H`, diverging from the canonical chain. [7](#0-6)

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
