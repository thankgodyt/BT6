### Title
`batch_clear_invalid_pending_verify_rbf` Hard-Reverts Entire Batch on Any Single Item Failure, Enabling Griefing via Race Condition - (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary
`batch_clear_invalid_pending_verify_rbf` iterates over a list of stale RBF pending IDs and calls `internal_clear_invalid_pending_verify_rbf` for each. Because `internal_clear_invalid_pending_verify_rbf` panics (hard-reverts) if the pending info does not exist, any single item that was already cleared — by a concurrent `clear_invalid_pending_verify_rbf` call or a race between two relayers — causes the entire batch to revert. This is the direct analog of the PoolTogether `claimPrizes` front-running issue: a batch that should silently skip already-processed items instead aborts entirely.

### Finding Description

`batch_clear_invalid_pending_verify_rbf` is a publicly callable function (no access-control guard, only `#[pause]`) that accepts a `Vec<String>` of pending IDs and processes them in a loop:

```rust
pub fn batch_clear_invalid_pending_verify_rbf(&mut self, btc_pending_verify_ids: Vec<String>) {
    for btc_pending_verify_id in btc_pending_verify_ids {
        self.internal_clear_invalid_pending_verify_rbf(btc_pending_verify_id);
    }
}
``` [1](#0-0) 

The inner function `internal_clear_invalid_pending_verify_rbf` immediately removes the pending info from storage and then asserts invariants:

```rust
pub fn internal_clear_invalid_pending_verify_rbf(&mut self, btc_pending_id: String) {
    let btc_pending_info = self.internal_remove_btc_pending_info(&btc_pending_id);
    btc_pending_info.assert_pending_verify();
    let original_tx_id = btc_pending_info
        .get_original_tx_id()
        .expect("Not rbf transaction");
    require!(
        !self.data().rbf_txs.contains_key(original_tx_id),
        "Not invalid pending verify rbf"
    );
}

`internal_remove_btc_pending_info` panics with `"BTC pending info not exist"` if the key is absent:

The single-item variant `clear_invalid_pending_verify_rbf` is also publicly callable: [4](#0-3) 

**Attack path:**
1. A relayer observes several stale RBF pending IDs `[A, B, C, D, E]` and submits `batch_clear_invalid_pending_verify_rbf([A, B, C, D, E])`.
2. A malicious actor (or a competing relayer) submits `clear_invalid_pending_verify_rbf(E)` which lands in an earlier NEAR block or receipt.
3. When the batch call executes, item `E` is already gone; `internal_remove_btc_pending_info` panics, reverting the entire batch.
4. Items `A–D` remain uncleaned. The relayer's gas is wasted. The attacker can repeat this indefinitely to prevent batch cleanup.

### Impact Explanation
Stale RBF `BTCPendingInfo` entries accumulate in contract storage and cannot be cleaned up in bulk. Each failed batch wastes the relayer's gas. Persistent griefing forces the operator to fall back to individual `clear_invalid_pending_verify_rbf` calls, one per item, at much higher total cost. No funds are directly stolen, but the stuck state requires operator intervention to resolve. This maps to: **Low — publicly reachable stuck-state / panic-driven fault in production bridge paths without direct theft.**

### Likelihood Explanation
Both `batch_clear_invalid_pending_verify_rbf` and `clear_invalid_pending_verify_rbf` are unrestricted public entry points. Any NEAR account can call either at any time. A race between two honest relayers is sufficient to trigger the revert without any malicious intent; a deliberate attacker simply needs to call the single-item variant for one ID in the target batch before the batch lands.

### Recommendation
Mirror the PoolTogether mitigation: replace the hard panic with a silent skip. Change `internal_clear_invalid_pending_verify_rbf` (or add a batch-specific variant) to return a `bool` or `Option` indicating success, and have the batch loop log a warning and continue rather than propagating the panic:

```rust
pub fn batch_clear_invalid_pending_verify_rbf(&mut self, btc_pending_verify_ids: Vec<String>) {
    for btc_pending_verify_id in btc_pending_verify_ids {
        if self.data().btc_pending_infos.contains_key(&btc_pending_verify_id) {
            self.internal_clear_invalid_pending_verify_rbf(btc_pending_verify_id);
        }
        // else: already cleared, silently skip
    }
}
```

This ensures a batch succeeds for all valid items even if one was already processed by a concurrent call.

### Proof of Concept

1. Suppose stale RBF pending IDs `["rbf_A", "rbf_B", "rbf_C"]` exist on-chain, all in `PendingVerify` stage with their originals already verified.
2. Relayer submits: `batch_clear_invalid_pending_verify_rbf(["rbf_A", "rbf_B", "rbf_C"])`.
3. Attacker submits `clear_invalid_pending_verify_rbf("rbf_C")` in the same or an earlier block.
4. Attacker's single-item call succeeds; `"rbf_C"` is removed from `btc_pending_infos`.
5. Relayer's batch call processes `"rbf_A"` and `"rbf_B"` successfully, then reaches `"rbf_C"`.
6. `internal_remove_btc_pending_info("rbf_C")` calls `.expect("BTC pending info not exist")` → panic.
7. The entire batch transaction reverts. `"rbf_A"` and `"rbf_B"` are NOT cleaned up despite being valid targets.
8. Attacker repeats step 3 for any future batch the relayer attempts, permanently blocking bulk cleanup.
