### Title
Attacker Can Redirect BTC Refunds to an Arbitrary Address via Unbound `request_refund` - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary
`request_refund` accepts any caller-supplied `refund_address` without verifying that the caller is the `recipient_id` named in the `deposit_msg`. Because the BTC inclusion proof is not bound to the `refund_address`, an attacker can submit a refund request for a victim's unfinalized deposit and redirect the BTC to an address they control. This is the direct analog of the reported vulnerability: just as the original report shows that a signature does not commit to the wallet it was intended for, here the BTC proof does not commit to the refund destination.

### Finding Description

`get_deposit_path` hashes the entire `DepositMsg` (including `recipient_id`) to derive the deposit address, so the BTC proof is cryptographically bound to the NEAR recipient. However, the `refund_address` — the BTC address that receives the funds on a refund — is a **separate, caller-supplied parameter** that is never committed to by the proof.

`request_refund` (callable by any NEAR account — it carries no `#[trusted_relayer]` guard at the method level, unlike `verify_refund_finalize` and `remove_refund_pending_tx_id` in the same impl block) accepts:

```
deposit_msg   – public (emitted by get_user_deposit_address)
refund_address – arbitrary, supplied by the caller
tx_bytes / proof – public (Bitcoin blockchain)
```

The only guard against a mismatched `refund_address` is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
```

When `deposit_msg.refund_address` is `None` (the common case for standard deposits), **any** `refund_address` is accepted. The callback then stores the attacker-chosen address permanently:

```rust
let refund_request = RefundRequest {
    ...
    refund_address,   // attacker-controlled
    ...
};
self.data_mut().refund_requests.insert(utxo_storage_key, refund_request.into());
```

Once stored, a second `request_refund` for the same UTXO is rejected:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
```

So the first caller wins. After `unsafe_refund_timelock_sec` elapses, anyone can call `execute_refund` (also ungated) and the BTC is sent to the attacker's address.

### Impact Explanation

If the DAO does not reject the request within `unsafe_refund_timelock_sec`, the victim's BTC is transferred to the attacker's Bitcoin address. The legitimate user has no recourse: they cannot submit their own `request_refund` (duplicate rejected), and they cannot call `reject_refund` (only DAO/Operator can). This constitutes a direct theft of user BTC funds — a Critical impact.

### Likelihood Explanation

All inputs needed for the attack are public:
- `deposit_msg` is emitted in the `LogDepositAddress` event by `get_user_deposit_address`.
- The BTC transaction bytes and Merkle proof are on the public Bitcoin blockchain.

The attacker only needs to monitor for unfinalized deposits and submit `request_refund` before the legitimate user. The `unsafe_refund_timelock_sec` is the sole mitigation, relying on the DAO actively monitoring and rejecting within the window. If the DAO is slow or offline, the attack succeeds. Likelihood is **Medium**.

### Recommendation

Bind the `refund_address` to the caller's identity at submission time. The simplest fix is to require `env::predecessor_account_id() == deposit_msg.recipient_id` inside `internal_request_refund`. Alternatively, require that `deposit_msg.refund_address` is always set (non-`None`) so the BTC destination is committed to at deposit time and cannot be overridden by a third party.

### Proof of Concept

1. Alice calls `get_user_deposit_address(DepositMsg { recipient_id: "alice.near", refund_address: None, ... })`. The bridge emits a `LogDepositAddress` event revealing the full `deposit_msg`.
2. Alice sends BTC to the derived address. The deposit is never finalized (relayer is down or amount is below minimum).
3. Attacker Bob observes the `LogDepositAddress` event and the Bitcoin transaction on-chain.
4. Bob calls `request_refund(alice_deposit_msg, "bob_btc_address", tx_bytes, vout, proof, None)` with an attached storage deposit. The callback verifies the BTC proof (valid), finds no existing refund request, and stores `refund_address = "bob_btc_address"`.
5. Alice attempts `request_refund` — rejected: "Refund request already exists for this UTXO".
6. After `unsafe_refund_timelock_sec` elapses without DAO intervention, Bob calls `execute_refund(utxo_storage_key, None)`.
7. The bridge builds a BTC transaction paying Alice's deposit to `"bob_btc_address"` and routes it through the MPC signing pipeline. Alice's BTC is stolen. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5)
