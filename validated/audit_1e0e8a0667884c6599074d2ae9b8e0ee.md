Audit Report

## Title
ERC-1155 `safeTransferFrom` Recipient Hook Reverts Permanently Freeze Bridged Funds — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`finTransfer` in `OmniBridge.sol` uses `IERC1155.safeTransferFrom` to deliver ERC-1155 tokens to the recipient. The ERC-1155 standard mandates that `safeTransferFrom` calls `onERC1155Received` on any contract recipient. If that hook reverts, the entire `finTransfer` transaction reverts — including the `completedTransfers` write — so the nonce is never consumed. Because the MPC signature is bound to the exact `(destinationNonce, recipient, amount, token)` tuple, every subsequent relay attempt will hit the same revert. Tokens burned or locked on NEAR at `init_transfer` time are permanently unrecoverable.

## Finding Description

In `finTransfer`, the nonce is marked used at line 287 before any external call (the CEI pattern, per `CLAUDE.md`'s reentrancy invariant):

```solidity
// OmniBridge.sol L287
completedTransfers[payload.destinationNonce] = true;
```

After signature verification, the ERC-1155 branch executes:

```solidity
// OmniBridge.sol L323-330
} else if (multiToken.tokenAddress != address(0)) {
    IERC1155(multiToken.tokenAddress).safeTransferFrom(
        address(this),
        payload.recipient,
        multiToken.tokenId,
        payload.amount,
        ""
    );
}
```

`safeTransferFrom` unconditionally calls `onERC1155Received` on `payload.recipient` when it is a contract. If that call reverts (no implementation, explicit revert, or missing `IERC1155Receiver` support), the EVM unwinds the entire transaction, including the `completedTransfers[nonce] = true` write. The nonce is reset to `false`.

The MPC signature encodes `destinationNonce`, `recipient`, `amount`, and `tokenAddress` in the Borsh payload (lines 289–308). No alternative payload can be signed for the same origin transfer. Every subsequent relay attempt with the same signed payload will reach `safeTransferFrom` and revert identically. The transfer is permanently unfinalizable.

On the NEAR side, `init_transfer_internal` burns or locks tokens before emitting `InitTransferEvent` (near/omni-bridge/src/lib.rs L1851–1862). There is no timeout, cancellation, or admin escape hatch on either side. `SECURITY.md` and `CLAUDE.md` confirm no admin bypass of the signature gate exists.

The ETH branch (lines 317–322) uses a low-level `call` that captures the success bool and reverts with `FailedToSendEther()` — the same permanent-freeze outcome applies there, but the ERC-1155 case is the focus here because `safeTransferFrom` propagates the revert unconditionally with no success-bool escape.

## Impact Explanation

Any NEAR→EVM bridge user who specifies a contract recipient that does not correctly implement `IERC1155Receiver` will have their ERC-1155 tokens permanently frozen: burned/locked on NEAR, undeliverable on EVM, with no recovery path. This is a concrete instance of **permanent freezing of bridged funds across NEAR and EVM**, which is an explicitly listed Critical impact in the allowed scope.

## Likelihood Explanation

ERC-1155 support is a first-class feature of the bridge (`logMetadata1155`, `initTransfer1155`, `finTransfer`). Many real-world contract recipients — multisig wallets, DAO treasuries, DeFi vaults, and custom escrow contracts — do not implement `IERC1155Receiver`. A user bridging to any such address, even accidentally, permanently loses their funds. No special privilege is required; any bridge user initiating an ERC-1155 transfer via `initTransfer1155` is exposed. A malicious contract can also deliberately revert in `onERC1155Received` to grief a sender who specified it as recipient.

## Recommendation

Replace the push-to-recipient pattern with a **pull (claim) pattern** for ERC-1155 deliveries:

1. In `finTransfer`, when `multiToken.tokenAddress != address(0)`, store the pending claim in a mapping (e.g., `pendingClaims[recipient][multiToken.tokenAddress][multiToken.tokenId] += payload.amount`) instead of calling `safeTransferFrom` immediately. The nonce is consumed and `FinTransfer` is emitted normally.
2. Expose a separate `claimERC1155(address token, uint256 tokenId)` function that the recipient calls to pull their tokens. Any hook reversion in the recipient's own call context does not affect the bridge's finalization state.

This ensures the nonce is always consumed and bridge state is finalized regardless of whether the recipient can accept the token.

## Proof of Concept

1. Deploy `BadRecipient` on EVM — a contract with no `onERC1155Received` implementation (or one that explicitly reverts).
2. On NEAR, call `ft_transfer_call` to the bridge with an `InitTransferMsg` specifying an ERC-1155 token and `recipient = BadRecipient`. `init_transfer_internal` burns/locks the tokens and emits `InitTransferEvent`.
3. MPC signs a `TransferMessagePayload` with `recipient = BadRecipient`.
4. Relayer calls `finTransfer(signature, payload)` on `OmniBridge.sol`.
5. Execution reaches line 324: `IERC1155(...).safeTransferFrom(address(this), BadRecipient, ...)`.
6. `safeTransferFrom` calls `BadRecipient.onERC1155Received(...)`, which reverts (no implementation or explicit revert).
7. The entire transaction reverts. `completedTransfers[nonce]` is reset to `false`.
8. Every subsequent `finTransfer` attempt with the same signed payload repeats steps 5–7.
9. The user's tokens on NEAR are permanently burned/locked with no recovery path.

A local Hardhat/Foundry test can reproduce this by deploying a mock ERC-1155 token, registering it via `logMetadata1155`, deploying a `BadRecipient` contract, and calling `finTransfer` with a crafted payload signed by the test MPC key — confirming the transaction reverts and `completedTransfers[nonce]` remains `false` after each attempt.
