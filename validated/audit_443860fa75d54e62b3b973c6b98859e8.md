Audit Report

## Title
Fee Granularity Inconsistency Allows Permanent Freezing of Outbound Transfer Funds - (File: `near/omni-bridge/src/lib.rs`)

## Summary

`init_transfer` accepts a transfer if `fee < amount` using raw token units, but `sign_transfer` requires `normalize_amount(amount - fee) > 0` using floor division. For tokens where `origin_decimals > decimals` (e.g., 24 on NEAR, 18 on Ethereum), a user can create a transfer where `amount - fee` is positive but normalizes to zero, causing `sign_transfer` to always panic. No public recovery path exists, permanently locking the user's tokens in the bridge.

## Finding Description

**Stage 1 — `init_transfer` raw-amount check:** [1](#0-0) 

The only fee validity check is `fee.fee < transfer_message.amount`, operating entirely on raw NEAR-native token units with no awareness of destination-chain decimal precision.

**Stage 2 — `sign_transfer` normalized-amount check:** [2](#0-1) 

`normalize_amount` applies integer floor division: [3](#0-2) 

When `origin_decimals = 24` and `decimals = 18`, the normalization unit is `10^6`. Any `amount - fee < 10^6` normalizes to zero, causing the `require!` at L482–484 to panic with `InvalidAmountToTransfer`.

**No recovery path exists:**

`update_transfer_fee` enforces `fee.fee >= current_fee.fee`, so the fee can only be increased, never decreased: [4](#0-3) 

Additionally, only the sender can raise the fee (not an arbitrary caller): [5](#0-4) 

`remove_transfer_message` is called in `sign_transfer_callback` only when `fee.is_zero()`: [6](#0-5) 

There is no public `cancel_transfer` function. `claim_fee_callback` requires a proof from the destination chain that the transfer was finalized — impossible if `sign_transfer` always panics. The transfer is permanently stuck in `pending_transfers`.

## Impact Explanation

This constitutes **permanent freezing of bridged funds**, which is an explicitly listed Critical impact. The user's tokens are locked/burned on NEAR (the `ft_transfer_call` returns `U128(0)` to the token contract, keeping the tokens in the bridge), stored in `pending_transfers`, and irrecoverable. The bridge has no administrative escape hatch for this state.

## Likelihood Explanation

The precondition — a token registered with `origin_decimals > decimals` — is a common real-world configuration (e.g., a NEAR-native token with 24 decimals bridged to Ethereum where it is represented with 18 decimals). The triggering condition requires `amount - fee < 10^(origin_decimals - decimals)`, which can occur through user error when setting a high fee to attract relayers. The griefing vector described in the submission (attacker front-running to increase the fee) is **not valid** because `update_transfer_fee` restricts fee increases to the original sender only. However, the self-inflicted user-error path alone is sufficient to trigger the vulnerability and constitutes a realistic likelihood.

## Recommendation

Add a pre-flight normalization check inside `init_transfer_internal` that verifies `normalize_amount(amount - fee, decimals) > 0` before accepting the transfer and locking tokens. Additionally, implement a `cancel_transfer` function that allows the original sender to reclaim locked tokens for transfers that have not yet been signed, providing a recovery path for any stuck transfers.

## Proof of Concept

**Setup:** Token registered with `origin_decimals = 24`, `decimals = 18` (normalization unit = `10^6`).

1. User calls `ft_transfer_call` on the token contract with `amount = 1_000_001` and `fee = 999_999`.
2. Bridge's `ft_on_transfer` → `init_transfer` is called.
3. Fee check: `999_999 < 1_000_001` → **passes** at L554–557.
4. `init_transfer_internal` stores the `TransferMessage` in `pending_transfers` and returns `U128(0)` to the token contract → tokens are locked in the bridge.
5. Trusted relayer calls `sign_transfer` for this transfer.
6. `amount_without_fee() = 1_000_001 - 999_999 = 2`.
7. `normalize_amount(2, Decimals { decimals: 18, origin_decimals: 24 }) = 2 / 1_000_000 = 0`.
8. `require!(0 > 0, ...)` → **panics with `InvalidAmountToTransfer`** at L482–484.
9. Transfer remains in `pending_transfers`. User's `1_000_001` tokens are permanently locked. No recovery path exists.
