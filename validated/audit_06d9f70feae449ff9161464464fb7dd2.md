### Title
Overly Strict Orchard Bundle Action-Count Check Permanently Blocks All Zcash Orchard Withdrawals - (File: contracts/satoshi-bridge/src/zcash_utils/orchard_policy.rs)

### Summary
`extract_orchard_bundle` enforces an exact equality check (`!= EXPECTED_ACTIONS_NUMBER`) on the number of actions in a submitted Orchard bundle, where `EXPECTED_ACTIONS_NUMBER = 1`. The Orchard protocol's own builder pads every bundle to a minimum of 2 actions for privacy (as acknowledged in the code's own comment). Any real Orchard bundle produced by a standard Zcash wallet will therefore always fail this check, permanently blocking the Zcash Orchard withdrawal path for all users.

### Finding Description

`EXPECTED_ACTIONS_NUMBER` is set to `1`: [1](#0-0) 

The check in `extract_orchard_bundle` requires the bundle to have **exactly** that many actions: [2](#0-1) 

The code's own comment on `EXPECTED_ACTIONS_NUMBER` states: *"The Orchard builder automatically pads bundles to meet this minimum for privacy"* and references `https://github.com/zcash/orchard/blob/main/src/builder.rs#L36`, where the Orchard library defines `MIN_ACTIONS: usize = 2`. Every bundle produced by a conforming Zcash wallet will therefore contain **at least 2 actions**, never exactly 1. The strict `!=` equality (analogous to the `==` in the reference report) means every real Orchard bundle is unconditionally rejected.

A secondary strict equality appears in `validate_orchard_bundle`: [3](#0-2) 

This checks that `actual_value_balance == expected_value_balance` exactly. While this check is internally consistent for a single-action bundle, it compounds the fragility: any deviation in how a wallet encodes the value balance (e.g., due to shielded inputs) causes an additional hard failure.

### Impact Explanation

The Zcash Orchard withdrawal path is permanently and completely broken for all users. Any user who initiates a Zcash Orchard withdrawal will have their transaction rejected at the bundle-parsing stage. If nZEC tokens are already held by the bridge contract at the point of failure (depending on where in the callback chain this check executes), those funds become stuck and require operator intervention to recover. At minimum, the Orchard withdrawal feature is entirely non-functional, constituting a stuck bridge state.

### Likelihood Explanation

Likelihood is **high**. Every conforming Zcash wallet using the standard Orchard builder will produce a bundle with ≥ 2 actions. There is no user-side workaround; the rejection is deterministic and unconditional. Any user attempting an Orchard withdrawal triggers the failure immediately.

### Recommendation

Replace the strict equality with a minimum-count check:

```rust
// Before (broken):
if bundle.actions().len() != EXPECTED_ACTIONS_NUMBER {
    return Err(...);
}

// After (correct):
if bundle.actions().len() < EXPECTED_ACTIONS_NUMBER {
    return Err(...);
}
```

And update `EXPECTED_ACTIONS_NUMBER` to reflect the Orchard protocol's actual minimum of 2, consistent with the referenced `MIN_ACTIONS` constant in the Orchard library.

### Proof of Concept

1. User holds nZEC and initiates a Zcash Orchard withdrawal via `ft_transfer_call`, providing a valid Orchard bundle constructed by any standard Zcash wallet.
2. The wallet's Orchard builder pads the bundle to 2 actions (per `MIN_ACTIONS = 2` in the Orchard library).
3. `extract_orchard_bundle` is called; `bundle.actions().len()` returns `2`.
4. The check `2 != 1` evaluates to `true`; the function returns `Err("Orchard bundle must have 1 actions, got 2")`.
5. The withdrawal is rejected. This is deterministic for every real Orchard bundle — no attacker action is required; the strict equality alone is sufficient to permanently block the entire Orchard withdrawal path.
