### Title
Refund Request Front-Running via Incomplete UTXO Storage Key Allows Persistent DOS of User Refunds - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary

The `request_refund` function deduplicates refund requests using a key derived only from `tx_id` and `vout` (`{tx_id}@{vout}`), omitting the caller-supplied `refund_address`. When a deposit was made without a pre-authorized `deposit_msg.refund_address`, any unprivileged NEAR account can front-run a legitimate user's `request_refund` call with the same UTXO but a different (attacker-controlled) `refund_address`, permanently occupying the slot and blocking the legitimate refund. The attacker can repeat this after every DAO rejection, creating a persistent DOS that locks the user's BTC indefinitely.

### Finding Description

`request_refund` is a public, payable function callable by any NEAR account (it carries no `#[trusted_relayer]` guard on the function itself, only on `verify_refund_finalize` and `remove_refund_pending_tx_id` within the same impl block).

Inside `internal_request_refund`, the bridge verifies the BTC transaction via the Light Client and then fires a callback `request_refund_callback`. In that callback the duplicate-prevention check is:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
```

where `utxo_storage_key` is built as:

```rust
let utxo_storage_key = generate_utxo_storage_key(
    tx_id,
    u32::try_from(vout)...
);
```

which expands to `"{tx_id}@{vout}"` — containing only the Bitcoin outpoint, not the `refund_address`.

The `refund_address` is validated only when `deposit_msg.refund_address` is `Some`:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
```

When `deposit_msg.refund_address` is `None` (the common case — it is an optional field), any caller may supply any `refund_address`. Because the storage key does not include `refund_address`, the first caller to land in the callback wins the slot. All subsequent `request_refund` calls for the same UTXO revert with "Refund request already exists for this UTXO".

After the DAO rejects the attacker's request via `reject_refund`, the attacker immediately re-submits with a fresh `refund_address`, re-occupying the slot. There is no per-account cooldown, no rate limit, and no mechanism to prevent this cycle.

### Impact Explanation

The user's BTC is locked in the bridge indefinitely. The legitimate `request_refund` can never land as long as the attacker keeps front-running. Because the storage deposit is non-refundable, the attacker pays a small NEAR cost per cycle, but for any meaningful BTC value this cost is negligible. If the DAO is slow or offline during the `unsafe_refund_timelock_sec` window, the attacker's request can be executed by anyone via `execute_refund`, redirecting the BTC to the attacker's address — escalating from DOS to theft.

Primary impact: **Medium** — attacker-triggered persistent locking of user's bridged BTC requiring continuous operator intervention.
Secondary impact: **Critical** — if DAO fails to reject within `unsafe_refund_timelock_sec`, the attacker's `refund_address` receives the BTC.

### Likelihood Explanation

The `deposit_msg.refund_address` field is optional and `None` by default. Any deposit that did not pre-authorize a refund address is vulnerable. The `deposit_msg` is public (it is the hash input used to derive the deposit address and is emitted in events). The attack requires only a standard NEAR transaction with an attached storage deposit, executable by any NEAR account. The attacker does not need any privileged role, leaked key, or off-chain capability.

### Recommendation

Include `refund_address` in the storage key used to deduplicate refund requests, or bind the refund request to the caller's NEAR account ID so that only the original submitter (or a privileged role) can occupy the slot for a given UTXO. For example, the key could be `"{tx_id}@{vout}@{sha256(refund_address)}"` or `"{tx_id}@{vout}@{predecessor_account_id}"`. Alternatively, require that `deposit_msg.refund_address` always be set at deposit time, removing the open-address path entirely.

### Proof of Concept

1. Alice has a stuck deposit: `tx_id = "abc123"`, `vout = 0`, `deposit_msg.refund_address = None`.
2. Alice submits `request_refund(deposit_msg, "alice_btc_addr", tx_bytes, 0, proof, None)`.
3. Before Alice's callback lands, Bob submits `request_refund(deposit_msg, "bob_btc_addr", tx_bytes, 0, proof, None)` with the same `deposit_msg` and UTXO but `refund_address = "bob_btc_addr"`.
4. Bob's callback lands first; `refund_requests["abc123@0"]` is inserted with `refund_address = "bob_btc_addr"`.
5. Alice's callback hits the check at `refund.rs` line 544 and reverts: "Refund request already exists for this UTXO".
6. DAO calls `reject_refund("abc123@0")`. Bob immediately re-submits step 3.
7. Alice's BTC remains locked indefinitely. If the DAO misses a cycle, Bob calls `execute_refund("abc123@0", None)` after `unsafe_refund_timelock_sec` and receives Alice's BTC.

    #[allow(clippy::too_many_arguments)]
    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
