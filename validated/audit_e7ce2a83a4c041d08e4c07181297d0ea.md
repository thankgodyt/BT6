Audit Report

## Title
Permanent Freezing of Bridged Funds When EVM Recipient Is Blacklisted — (`evm/src/omni-bridge/contracts/OmniBridge.sol`, `near/omni-bridge/src/lib.rs`)

## Summary
When a user initiates a NEAR → EVM transfer to a recipient address that is (or becomes) blacklisted by the EVM token contract (e.g., USDC/USDT), `finTransfer` on EVM will always revert because the token transfer fails. The MPC signature is cryptographically bound to the fixed recipient, and the NEAR bridge has no cancel, refund, or recipient-update mechanism for failed EVM finalizations, causing the bridged funds to be permanently frozen.

## Finding Description
**Step 1 — Tokens burned/locked on NEAR:**
In `init_transfer_internal` (`near/omni-bridge/src/lib.rs`, lines 1851–1858), tokens are burned (for bridge-deployed tokens) or locked (for native tokens) immediately when the transfer is stored. The `recipient` field in `TransferMessage` is set from `init_transfer_msg.recipient` and is never modifiable afterward.

**Step 2 — Recipient fixed in MPC-signed payload:**
In `sign_transfer` (lines 491–500), `transfer_message.recipient` is embedded directly into `TransferMessagePayload` and the MPC signs the keccak256 hash of this payload. Any change to `recipient` would invalidate the signature.

**Step 3 — Transfer removed from `pending_transfers` when fee is zero:**
In `sign_transfer_callback` (lines 655–658), when `fee.is_zero()`, `self.remove_transfer_message(message_payload.transfer_id)` is called immediately after signing. The transfer record is gone from NEAR state with no on-chain trace of the pending obligation.

**Step 4 — `finTransfer` on EVM reverts on blacklisted recipient:**
In `OmniBridge.sol` (lines 283–355), `completedTransfers[payload.destinationNonce] = true` is set before the token transfer. If `IERC20(payload.tokenAddress).safeTransfer(payload.recipient, payload.amount)` (line 351–354) reverts (e.g., USDC's `Blacklistable` check), the entire transaction reverts, rolling back the nonce marking. The nonce is never permanently consumed, so the relayer can retry indefinitely — but every retry hits the same revert.

**Step 5 — No recovery path on NEAR:**
A grep for `cancel_transfer`, `refund_transfer`, and `update_recipient` returns no matches. `update_transfer_fee` (lines 386–436) only allows updating the fee amount, not the recipient. There is no `cancel_transfer` or refund function. The inbound (EVM → NEAR) direction has `fin_transfer_send_tokens_callback` which burns tokens and emits `FailedFinTransferEvent` on failure (lines 1700–1718), but no equivalent exists for the outbound direction.

## Impact Explanation
Bridged funds are permanently frozen: tokens are burned or locked on NEAR but can never be delivered to the EVM recipient. This directly matches the allowed critical impact: *"permanent freezing of bridged funds across NEAR, EVM … flows."* The loss is total and irreversible for the affected transfer amount.

## Likelihood Explanation
Two realistic, unprivileged trigger paths exist:
1. A user initiates a transfer to an address that is subsequently blacklisted by the token issuer (e.g., OFAC-sanctioned USDC address) before the relayer finalizes on EVM. USDC has a documented, ongoing history of post-issuance blacklisting.
2. A user mistakenly specifies a known blacklisted address as the recipient.

No admin compromise, MPC collusion, or privileged access is required. The entry path is the standard public `ft_transfer_call` → `ft_on_transfer` → `init_transfer` flow, callable by any token holder.

## Recommendation
1. **Recipient update before signing:** Allow the original sender to update `transfer_message.recipient` in `pending_transfers` before `sign_transfer` is called, so a valid recipient can be substituted without re-burning/re-locking funds.
2. **Timeout-based refund on NEAR:** After a configurable timeout or an explicit relayer report of repeated EVM revert, allow the NEAR bridge to refund the sender by unlocking/minting back the original tokens, mirroring the existing `FailedFinTransferEvent` recovery path used for inbound transfers.
3. **Do not remove from `pending_transfers` until EVM finalization is confirmed:** Retain the transfer record even when `fee.is_zero()` until a proof of successful EVM finalization is submitted, enabling a future refund path.
4. **Pre-flight validation:** Where feasible (e.g., for known tokens with on-chain blacklist interfaces), validate the recipient is not blacklisted before burning/locking funds on NEAR.

## Proof of Concept
```
1. Alice calls ft_transfer_call on NEAR USDC wrapper:
   receiver_id = omni-bridge.near
   amount      = 1000 USDC
   msg         = InitTransferMsg {
       recipient: OmniAddress::Eth(0xE1D865c3D669dCc8c57c8D023140CB204e672ee4),
       fee: U128(0),
       native_token_fee: U128(0),
       ...
   }

2. init_transfer_internal burns 1000 USDC on NEAR (near/omni-bridge/src/lib.rs:1851),
   stores TransferMessage in pending_transfers with fixed recipient.

3. Relayer calls sign_transfer(transfer_id, ...).
   MPC signs payload containing blacklisted recipient.
   fee.is_zero() == true → remove_transfer_message() called (lib.rs:657).
   Alice's 1000 USDC are burned; no pending record remains on NEAR.

4. Relayer calls OmniBridge.finTransfer(signature, payload) on Ethereum:
   → completedTransfers[nonce] = true  (OmniBridge.sol:287)
   → ECDSA.recover(...) == nearBridgeDerivedAddress  ✓
   → IERC20(usdc).safeTransfer(0xE1D865..., 1000e6)  (OmniBridge.sol:351)
   → REVERT: "Blacklistable: account is blacklisted"
   → entire tx reverts, nonce rolled back

5. Relayer retries → same revert, indefinitely.
   Alice's 1000 USDC are permanently lost with no recovery path.
```
