Audit Report

## Title
Missing Zero-Address Recipient Validation in `init_transfer` Allows Permanent Freezing of Bridged Funds — (File: `near/omni-bridge/src/lib.rs`)

## Summary
The `init_transfer` function in the NEAR bridge contract validates only that the recipient chain is not NEAR, but never checks whether the recipient address itself is zero. An unprivileged user can initiate a transfer to `address(0)` on any EVM chain, causing tokens to be permanently locked on NEAR: the MPC signature is cryptographically bound to the zero-address payload, making the transfer unreleasable, while EVM-side finalization either permanently burns ETH or reverts forever for ERC20/bridge tokens.

## Finding Description
In `near/omni-bridge/src/lib.rs`, `init_transfer` performs only a chain-kind check: [1](#0-0) 

There is no call to `recipient.is_zero()`, despite `OmniAddress::is_zero()` being fully implemented: [2](#0-1) 

And `BridgeError::InvalidRecipientAddress` already existing in the error enum: [3](#0-2) 

A grep search confirms neither `is_zero` nor `InvalidRecipientAddress` appears anywhere in `near/omni-bridge/src/lib.rs`. The transfer is stored with `recipient = address(0)` and proceeds to `sign_transfer`, which also performs no zero-address check and directly passes `transfer_message.recipient` into the MPC payload: [4](#0-3) 

The MPC produces a valid signature over a `TransferMessagePayload` whose `recipient` field is `address(0)`. Since the recipient is stored in NEAR contract state and cannot be changed, every future call to `sign_transfer` for this transfer ID will produce the same zero-address payload. On the EVM side, `finTransfer` has no zero-address guard on `payload.recipient`: [5](#0-4) 

- **Bridge tokens / ERC20**: `IBridgeToken.mint(address(0), amount)` or `safeTransfer(address(0), amount)` reverts (OpenZeppelin rejects zero-address recipients). The nonce marking at line 287 reverts with the transaction, but the MPC signature is permanently bound to `address(0)` — no valid signature for any other recipient can ever be produced. NEAR tokens are permanently locked.
- **Native ETH** (`tokenAddress == address(0)`): `address(0).call{value: amount}("")` succeeds; ETH is sent to the uncontrolled genesis address and permanently burned. Nonce is consumed. NEAR tokens are permanently locked.

## Impact Explanation
Permanent freezing or destruction of bridged funds. Tokens locked on NEAR have no corresponding release on the EVM side: either EVM finalization reverts forever (ERC20/bridge-token case) or ETH is destroyed (native ETH case). This matches the critical allowed impact: *permanent freezing of bridged funds*.

## Likelihood Explanation
Any unprivileged user who calls `ft_on_transfer` controls the `recipient` field — no special role or key is required. The trusted relayer processes the transfer automatically because `sign_transfer` contains no zero-address guard. Both accidental user error (uninitialized address) and deliberate self-grief are realistic triggers. The attack is repeatable for every token type supported by the bridge.

## Recommendation
Add a zero-address guard immediately after the chain-kind check in `init_transfer`:

```rust
require!(
    init_transfer_msg.recipient.get_chain() != ChainKind::Near,
    BridgeError::InvalidRecipientChain.as_ref()
);
require!(
    !init_transfer_msg.recipient.is_zero(),
    BridgeError::InvalidRecipientAddress.as_ref()
);
```

Both `OmniAddress::is_zero()` and `BridgeError::InvalidRecipientAddress` are already implemented — only the call site is missing.

## Proof of Concept
1. User calls `ft_on_transfer` on the NEAR bridge with `msg = InitTransferMsg { recipient: OmniAddress::Eth(H160::ZERO), fee: 0, ... }`.
2. `init_transfer` passes the chain-kind check (`Eth != Near`), locks tokens, stores the transfer at nonce N with `recipient = address(0)`.
3. Trusted relayer calls `sign_transfer(transfer_id, fee_recipient, fee)` — no zero check; MPC signs `TransferMessagePayload { recipient: 0x000…000, … }`.
4. Relayer submits `finTransfer(signature, payload)` on EVM:
   - **Bridge tokens**: `IBridgeToken.mint(address(0), amount)` reverts → entire transaction reverts → nonce reverts → but MPC signature is permanently bound to `address(0)`, so no valid signature for any other recipient can be obtained. NEAR tokens are permanently locked.
   - **Native ETH**: `address(0).call{value: amount}("")` succeeds → ETH permanently burned, nonce consumed. NEAR tokens are permanently locked.
5. User's NEAR tokens are irrecoverable in both cases.

**Local test plan**: Write a NEAR integration test that calls `ft_on_transfer` with `recipient = "eth:0x0000000000000000000000000000000000000000"`, assert the transfer is stored, then assert `sign_transfer` proceeds without panic and produces a payload with `recipient = address(0)`. For the EVM side, write a Hardhat/Foundry test that calls `finTransfer` with a valid MPC signature over a zero-address recipient payload and a bridge token — assert the transaction reverts while the NEAR-side transfer remains unreleasable.
