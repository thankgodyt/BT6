Audit Report

## Title
Permanent Fund Loss via Unchecked Promise Failure in `fin_transfer_send_tokens_callback` for wNEAR and `ft_transfer` Paths — (`near/omni-bridge/src/lib.rs`)

## Summary

In `process_fin_transfer_to_near`, `add_fin_transfer` permanently records the transfer ID in `finalised_transfers` before token delivery occurs. For the wNEAR path (and the plain `ft_transfer` path), if token delivery fails, `fin_transfer_send_tokens_callback` is invoked with a failed promise result but unconditionally takes the success branch because `is_refund_required(false)` returns `false` without inspecting the promise result. The transfer ID is never removed, making the transfer permanently unplayable and the user's funds permanently lost.

## Finding Description

**Step 1 — Early finalization.**
`process_fin_transfer_to_near` calls `add_fin_transfer` at line 1875 before any token delivery, inserting the transfer ID into `finalised_transfers`. [1](#0-0) 

**Step 2 — wNEAR promise chain.**
`send_tokens` for the wNEAR-with-empty-msg path builds: `near_withdraw() → near_withdraw_callback()`. The result of this chain is then chained with `fin_transfer_send_tokens_callback` via `.then(...)`, passing `is_ft_transfer_call = !msg.is_empty() = false`. [2](#0-1) [3](#0-2) 

**Step 3 — `near_withdraw_callback` panics on failure.**
If `near_withdraw` fails (e.g., insufficient wNEAR balance, paused contract, gas exhaustion), `near_withdraw_callback` calls `env::panic_str` instead of returning a failure value. This causes the promise representing `near_withdraw_callback` to fail. [4](#0-3) 

**Step 4 — `fin_transfer_send_tokens_callback` ignores the failure.**
`fin_transfer_send_tokens_callback` delegates to `is_refund_required(is_ft_transfer_call)`. When `is_ft_transfer_call = false` (wNEAR path or plain `ft_transfer` path), `is_refund_required` unconditionally returns `false` without reading the promise result at all. [5](#0-4) 

**Step 5 — Success branch executes on failure.**
Because `is_refund_required` returns `false`, the `else` branch runs: fees are sent and `FinTransferEvent` is logged as if the transfer succeeded. `remove_fin_transfer` is never called, so the transfer ID remains permanently in `finalised_transfers`. [6](#0-5) 

**Step 6 — Same flaw on plain `ft_transfer` path.**
The non-deployed, non-wNEAR, empty-msg branch also calls `ft_transfer` with `is_ft_transfer_call = false`. If `ft_transfer` fails, the same logic applies: `is_refund_required(false)` returns `false`, the success branch runs, and the transfer is permanently stuck. [7](#0-6) 

Any subsequent `fin_transfer` call with the same proof is rejected with `TransferAlreadyFinalised` because the ID remains in `finalised_transfers`. [8](#0-7) 

## Impact Explanation

This is a **critical** loss-of-funds vulnerability. The user's bridged funds are permanently frozen: the transfer ID is irrevocably recorded as finalized, the token delivery never occurred, and there is no replay or recovery path. This matches the allowed critical impact: *permanent freezing of bridged funds* and *escrow mis-accounting that changes user balances*.

## Likelihood Explanation

The wNEAR withdrawal failure is reachable by any user who initiates a legitimate cross-chain transfer of wNEAR to NEAR:
- The bridge contract's wNEAR balance can be insufficient due to decimal normalization discrepancies between the locked amount and the denormalized withdrawal amount.
- The wNEAR contract can be paused or temporarily unavailable.
- `WNEAR_WITHDRAW_GAS` may be insufficient for the wNEAR contract's execution under certain conditions.

The plain `ft_transfer` failure path is similarly reachable if the token contract panics for any reason after the storage deposit check passes. No special privileges are required; any user initiating a cross-chain transfer can trigger this.

## Recommendation

1. **Fix `near_withdraw_callback`**: Return a failure value (e.g., a rejected promise or a `PromiseOrValue::Value(false)`) instead of calling `env::panic_str`, so the failure propagates cleanly as a failed promise result to `fin_transfer_send_tokens_callback`.

2. **Fix `fin_transfer_send_tokens_callback`**: Check the promise result unconditionally for all token delivery paths, not only the `ft_transfer_call` path. Add a `#[callback_result]` parameter or call `env::promise_result_checked(0, ...)` before the `is_refund_required` check. If the promise result is `Err`, call `remove_fin_transfer` and `revert_lock_actions` regardless of `is_ft_transfer_call`.

3. **Fix `is_refund_required`**: For the `is_ft_transfer_call = false` branch, inspect the promise result and return `true` (trigger refund/revert) if the promise failed.

## Proof of Concept

**Setup:** Bridge a wNEAR transfer from Ethereum to NEAR where the bridge contract's wNEAR balance is less than the transfer amount (or the wNEAR contract is paused).

1. Relayer calls `fin_transfer` with a valid proof for a wNEAR transfer of amount `X`.
2. `fin_transfer_callback` → `process_fin_transfer_to_near` executes.
3. `add_fin_transfer` inserts `transfer_id` into `finalised_transfers` (L1875).
4. `send_tokens` schedules: `near_withdraw(X) → near_withdraw_callback → fin_transfer_send_tokens_callback`.
5. `near_withdraw` fails (insufficient balance or paused contract).
6. `near_withdraw_callback` is called with a failed promise result and panics (L1050), making its own promise fail.
7. `fin_transfer_send_tokens_callback` is called with the failed promise result. `is_refund_required(false)` returns `false` (L1801). The else branch logs `FinTransferEvent` as success (L1745).
8. `transfer_id` remains permanently in `finalised_transfers`. Any retry of `fin_transfer` with the same proof is rejected with `TransferAlreadyFinalised`. User's funds are permanently lost.

**Test plan:** Write a NEAR sandbox integration test that deploys a mock wNEAR contract configured to reject `near_withdraw`, then calls `fin_transfer` with a valid wNEAR proof. Assert that after the full promise chain resolves: (a) `transfer_id` is still in `finalised_transfers`, (b) the recipient received no NEAR, and (c) a second `fin_transfer` call with the same proof fails with `TransferAlreadyFinalised`.
