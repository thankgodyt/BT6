### Title
`safe_mint` Mints Tokens to `bridge_id` Before Verifying Recipient Registration, Permanently Inflating Total Supply on Early Return - (File: contracts/nbtc/src/lib.rs)

### Summary

In `contracts/nbtc/src/lib.rs`, the `safe_mint` function calls `internal_deposit` on `bridge_id` (increasing `ft_total_supply`) **before** checking whether the intended recipient `account_id` is registered. If the account is not registered, the function returns `U128(0)` early — but the tokens have already been minted into `bridge_id`. The deposit is not rolled back. This is a direct supply/accounting failure: the total supply is permanently inflated by tokens that are stuck in `bridge_id` and inaccessible to any user, breaking the 1:1 BTC-backing invariant and requiring operator intervention to resolve.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, `safe_mint` is structured as follows:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into()); // ← total supply increases HERE

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0)); // ← early return, mint NOT reversed
    }
    // transfer to account_id only happens if registered
    ...
}
```

`internal_deposit(&self.bridge_id, amount)` unconditionally increases `ft_total_supply` by `amount` and credits `bridge_id`. The subsequent check for account registration is too late — if `account_id` is unregistered, the function returns `U128(0)` (signaling failure to the caller) but the state mutation is **not** reverted. The `amount` tokens remain minted in `bridge_id` with no mechanism to transfer them to the intended recipient or burn them automatically.

This is structurally identical to the referenced ERC20 bug: a supply counter is incremented without a corresponding token allocation to the intended holder, causing `ft_total_supply()` to permanently overstate the actual circulating supply.

---

### Impact Explanation

1. **Inflated total supply**: `ft_total_supply()` returns a value higher than the actual tokens in user circulation. Any integration, DEX, or market-cap tool relying on `ft_total_supply` receives incorrect data.

2. **Stuck tokens in `bridge_id`**: The minted tokens accumulate in `bridge_id`. The `burn` function withdraws from `bridge_id` — these phantom tokens can be silently consumed by subsequent legitimate burn operations, causing the bridge to burn nBTC that was never legitimately deposited by a user. This erodes the 1:1 BTC-backing invariant.

3. **Stuck BTC**: The BTC deposited by the triggering user is locked in the bridge's custody with no corresponding nBTC ever reaching the user. Recovery requires privileged operator intervention.

4. **Broken callback rollback**: `safe_mint` is explicitly designed for atomic integrations (e.g., Omni Bridge). Returning `U128(0)` while leaving minted state in place violates the atomicity guarantee the function is supposed to provide.

Impact classification: **Medium** — broken callback rollback and stuck bridge state requiring operator intervention, with secondary supply invariant violation.

---

### Likelihood Explanation

Any user can trigger this by depositing BTC to a NEAR address that has not registered storage on the nBTC contract. This is a realistic scenario:

- A user generates a deposit address from a `DepositMsg` specifying a NEAR account that has never called `storage_deposit` on the nBTC contract.
- The relayer submits the inclusion proof; the satoshi-bridge calls `safe_mint` with the unregistered account.
- The bug fires unconditionally — no special attacker capability is needed beyond making a standard BTC deposit.

---

### Recommendation

Move the registration check **before** `internal_deposit`, or revert (panic) if the account is not registered, so no state mutation occurs on failure:

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "...");

    // Check registration BEFORE minting
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));
    }

    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ... proceed with transfer
}
```

This ensures `ft_total_supply` is only incremented when the full mint-and-transfer path can complete.

---

### Proof of Concept

1. Alice generates a deposit address from a `DepositMsg` with `receiver = "alice.near"` where `"alice.near"` has **not** called `storage_deposit` on the nBTC contract.
2. Alice sends 1 BTC to that deposit address on Bitcoin.
3. The relayer submits the inclusion proof to `satoshi-bridge::verify_deposit`.
4. The bridge calls `nbtc::safe_mint("alice.near", 100_000_000, None)`.
5. `internal_deposit(&bridge_id, 100_000_000)` executes — `ft_total_supply` becomes `100_000_000`, `bridge_id` balance becomes `100_000_000`.
6. `self.token.accounts.get(&"alice.near")` returns `None` → function returns `U128(0)`.
7. **Result**: `ft_total_supply()` returns `100_000_000` but Alice has `0` nBTC. The 100,000,000 satoshi-equivalent tokens are permanently stuck in `bridge_id`. Alice's 1 BTC is locked in the bridge with no recovery path for her. Any subsequent `burn` call can silently consume these phantom tokens, allowing the bridge to release BTC without a corresponding user burn. [1](#0-0) [2](#0-1) [3](#0-2)
