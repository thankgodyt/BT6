Audit Report

## Title
Silent `ft_transfer` Failure Not Detected in `fin_transfer_send_tokens_callback` Permanently Locks Bridged Funds — (File: `near/omni-bridge/src/lib.rs`)

## Summary

In `fin_transfer_send_tokens_callback`, the helper `is_refund_required` unconditionally returns `false` when `is_ft_transfer_call` is `false`, meaning the promise result of a plain `ft_transfer` is never inspected. If `ft_transfer` fails (e.g., token contract paused, recipient blacklisted), the callback still emits `FinTransferEvent` and leaves the transfer ID permanently recorded in `finalised_transfers`, with no recovery path for the user's funds.

## Finding Description

`process_fin_transfer_to_near` calls `add_fin_transfer` at line 1875, which inserts the transfer ID into `finalised_transfers` and commits that state in the current receipt. It then dispatches `send_tokens`, which — when the token is not a deployed bridge token and `msg` is empty — takes the plain `ft_transfer` path at lines 2102–2106. The `is_ft_transfer_call` flag passed to the callback is `!msg.is_empty()` (line 1973), so it is `false` for this path.

In the callback (lines 1692–1747), `is_refund_required(is_ft_transfer_call)` is called. The implementation at lines 1800–1802 returns `false` unconditionally when `is_ft_transfer_call` is `false`, without calling `env::promise_result_checked` or any equivalent. A failed `ft_transfer` receipt is therefore invisible to the callback. The callback falls into the `else` branch, emits `FinTransferEvent`, and returns — leaving the transfer ID in `finalised_transfers` and the tokens locked in the bridge contract.

The `ft_transfer_call` path, by contrast, correctly reads the promise result via `env::promise_result_checked(0, ...)` and triggers the refund branch (burn, revert lock actions, `remove_fin_transfer`, `FailedFinTransferEvent`) when the call fails.

## Impact Explanation

This directly matches the Critical impact class: **permanent freezing of bridged funds**. After a failed `ft_transfer`:

1. The transfer ID is irrevocably in `finalised_transfers`; any retry panics with `ERR_TRANSFER_ALREADY_FINALISED`.
2. The tokens remain in the bridge contract (the failed `ft_transfer` receipt reverts on the token side, but the bridge's state was committed in a prior receipt).
3. `FinTransferEvent` is emitted, so off-chain indexers and the MPC network consider the transfer complete.
4. There is no admin escape hatch or recovery function that can remove an entry from `finalised_transfers` and unblock the transfer.

## Likelihood Explanation

Several NEP-141 tokens supported by the bridge (USDC.e, USDT) implement pause and/or blacklist functionality. No attacker action is required: a legitimate cross-chain transfer initiated by any user can trigger this if the token contract is paused or the recipient is blacklisted at the moment the `ft_transfer` receipt executes. The window between `add_fin_transfer` committing and `ft_transfer` executing is one asynchronous receipt boundary, which is a normal operational condition. The scenario is fully reachable through the standard `fin_transfer` public entry point.

## Recommendation

In `is_refund_required`, remove the unconditional `false` return for the `!is_ft_transfer_call` branch and instead call `env::promise_result_checked(0, ...)`. If the result is `Err` (promise failed), return `true` to trigger the existing refund path (burn deployed tokens if needed, `revert_lock_actions`, `remove_fin_transfer`, emit `FailedFinTransferEvent`). The `ft_transfer_call` branch logic for parsing the returned `U128` is not needed here; a simple failed/succeeded check is sufficient.

## Proof of Concept

1. User initiates a transfer of a pausable NEP-141 token (e.g., USDC.e) from Ethereum to NEAR via `initTransfer` on the EVM side.
2. A relayer calls `fin_transfer` on the NEAR bridge with a valid proof.
3. `fin_transfer_callback` → `process_fin_transfer_to_near` → `add_fin_transfer` inserts the transfer ID into `finalised_transfers` (state committed).
4. `send_tokens` dispatches `ft_transfer` to the USDC.e contract (plain transfer, `msg` is empty).
5. The USDC.e contract is paused (or the recipient is blacklisted); the `ft_transfer` receipt fails.
6. `fin_transfer_send_tokens_callback` runs with `is_ft_transfer_call = false`.
7. `is_refund_required(false)` returns `false` at line 1801 — promise result is never read.
8. The callback emits `FinTransferEvent` and returns.
9. Any subsequent retry of the same transfer panics with `ERR_TRANSFER_ALREADY_FINALISED`.
10. The user's tokens are permanently locked in the bridge contract with no recovery mechanism.
