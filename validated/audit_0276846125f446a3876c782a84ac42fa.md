### Title
Refund Address Front-Running Enables Theft of User BTC Refunds - (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

The `request_refund` public entry point accepts a caller-supplied `refund_address` that is never validated against any pre-committed or identity-bound value when `deposit_msg.refund_address` is `None`. An unprivileged attacker can observe a victim's pending `request_refund` call on the NEAR mempool, front-run it with the same deposit proof but substituting their own BTC address, and — after the timelock — trigger `execute_refund` to redirect the victim's BTC to the attacker's wallet.

---

### Finding Description

**Analog to the Dojo report:** In Dojo, a namespace name and its hash are both provided by an untrusted caller without cross-validation, allowing an attacker to claim selectors by supplying a mismatched hash. Here, the `refund_address` is a caller-supplied identifier that is not validated against any pre-committed or identity-derived value, allowing an attacker to substitute their own BTC address and claim the refund.

**Root cause — `internal_request_refund` (refund.rs:154–158):**

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
```

This check is entirely skipped when `deposit_msg.refund_address` is `None` (the common case — the field is `#[serde(skip_serializing_if = "Option::is_none")]` and optional). When skipped, any caller may supply any BTC address as `refund_address`.

**Root cause — `request_refund_callback` (refund.rs:497–581):**

The callback validates that the transaction output's `script_pubkey` matches the deposit address derived from `deposit_msg` (lines 517–525), proving the deposit is real. However, it performs **no validation of `refund_address`** — it is stored verbatim:

```rust
let refund_request = RefundRequest {
    ...
    refund_address,   // ← stored as-is, never bound to caller or deposit
    ...
};
self.data_mut()
    .refund_requests
    .insert(utxo_storage_key, refund_request.into());
```

**First-writer-wins race (refund.rs:543–547):**

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
```

The storage key is `{tx_id}@{vout}` — fully deterministic from the public Bitcoin transaction. Whoever stores a request first wins. The victim's subsequent call is rejected.

**`execute_refund` is permissionless (bridge.rs:582–589):**

```rust
pub fn execute_refund(
    &mut self,
    utxo_storage_key: String,
    chain_specific_data: Option<ChainSpecificData>,
) -> PromiseOrValue<()> {
    let timelock_sec = self.resolve_execute_refund_timelock(&utxo_storage_key);
    self.internal_execute_refund(utxo_storage_key, timelock_sec, chain_specific_data)
}
```

No access control. After the timelock, anyone can call this to send BTC to whatever `refund_address` was stored.

---

### Impact Explanation

**Theft path (Critical):** If the DAO/Operator does not actively monitor and reject the attacker's fraudulent request within `unsafe_refund_timelock_sec`, the attacker calls `execute_refund` and the bridge's MPC pipeline sends the victim's BTC to the attacker's address. The victim loses their entire deposit.

**Permanent locking path (Medium):** If the DAO rejects the attacker's request, the attacker can immediately front-run the victim's next `request_refund` submission. This loop can be repeated indefinitely, permanently preventing the victim from recovering their BTC. The funds are locked in the bridge's MPC-controlled UTXO with no code-level recovery path for the victim.

---

### Likelihood Explanation

All inputs required to mount the attack are publicly available:
- `deposit_msg` — derivable from the deposit address (public on Bitcoin)
- `tx_bytes`, `vout` — the Bitcoin transaction is public
- `proof` — constructible from the Bitcoin blockchain by any observer
- `refund_address` — the attacker supplies their own

The attacker only needs to monitor the NEAR mempool for `request_refund` calls and submit a competing transaction with higher gas. This is a standard front-running technique requiring no privileged access, no leaked keys, and no operator collusion. The attack is feasible for any technically capable party who monitors the NEAR network.

---

### Recommendation

1. **Bind `refund_address` to the caller's identity:** Only allow the `recipient_id` from `deposit_msg` (the intended NEAR beneficiary) to submit a refund request, or require the `refund_address` to be pre-committed in `deposit_msg.refund_address` at deposit time.
2. **Store the requester's account ID and enforce it at execution:** Record `env::predecessor_account_id()` in `RefundRequest` and require that only the original requester (or DAO/Operator) can call `execute_refund`.
3. **Derive the storage key from the caller:** Include the caller's account ID in the storage key so different callers cannot collide on the same UTXO slot.

---

### Proof of Concept

1. Victim deposits BTC to the bridge address derived from `deposit_msg = {recipient_id: "victim.near", refund_address: None, ...}`.
2. The deposit is never finalized (relayer is offline or censored).
3. Victim submits:
   `request_refund(deposit_msg, "1VictimBtcAddress...", tx_bytes, vout, proof)`
4. Attacker monitors NEAR mempool, observes the pending call, and submits with higher gas:
   `request_refund(deposit_msg, "1AttackerBtcAddress...", tx_bytes, vout, proof)`
5. Attacker's transaction is included first. `refund_requests["{tx_id}@{vout}"]` is stored with `refund_address = "1AttackerBtcAddress..."`.
6. Victim's transaction executes: `request_refund_callback` panics at line 544–547: `"Refund request already exists for this UTXO"`. Victim's NEAR storage deposit is consumed with no recourse.
7. After `unsafe_refund_timelock_sec` elapses, attacker calls:
   `execute_refund("{tx_id}@{vout}")`
8. `internal_execute_refund` → `finalize_refund_with_psbt` → MPC signs a transaction paying `"1AttackerBtcAddress..."`.
9. `verify_refund_finalize` confirms the on-chain transaction. Victim's BTC is permanently transferred to the attacker. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
