### Title
Missing Peras Certificate Validation Allows Unauthorized Certificate Acceptance and Chain Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary
The `validatePerasCert` function in the production `BlockSupportsPeras` instance unconditionally accepts every inbound Peras certificate (always returns `Right`), while the analogous `validatePerasVote` function performs a stake-distribution membership check. An unprivileged peer connected via the ObjectDiffusion mini-protocol can send crafted `PerasCert` objects with arbitrary round numbers and boosted-block pointers; these bypass all cryptographic and semantic checks, are stored in the `PerasCertDB`, and trigger chain selection for the attacker-chosen block.

### Finding Description

**Asymmetric validation between votes and certificates**

`processVotes` (the inbound handler for Peras votes) runs its deduplication check **and** its per-vote validation atomically inside a single STM transaction:

```haskell
-- PerasVote.hs:178-182
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
```

`validatePerasVote` rejects any vote whose voter is absent from the stake distribution:

```haskell
-- SupportsPeras.hs:363-371
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
```

`processCerts` (the inbound handler for Peras certificates) runs its deduplication check atomically but performs validation **outside** the STM transaction, and the validation function itself is a no-op stub:

```haskell
-- PerasCert.hs:164-173
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
```

The `validateCert` argument is always `validatePerasCert mkPerasParams`, whose production implementation unconditionally returns `Right`:

```haskell
-- SupportsPeras.hs:350-358
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This is the direct analog of the reported vulnerability: `_interactions` (votes) are validated; `_hooks` (certificates) are not. An attacker can bypass the vote-validation gate entirely by injecting certificates directly.

**Reachable entry path**

`makePerasCertPoolWriterFromChainDB` wires `processCerts` into the ObjectDiffusion inbound handler:

```haskell
-- PerasCert.hs:118-133
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          (validatePerasCert mkPerasParams)   -- always Right
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
```

Any peer that speaks the ObjectDiffusion mini-protocol can send a `[PerasCert blk]` batch. No stake, no key, no proof is required.

**Chain-selection consequence**

Once a certificate is stored, `chainSelSync` triggers chain selection for the boosted block:

```haskell
-- ChainSel.hs:529-531
lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
```

The certificate's boost weight (`vpcCertBoost = perasWeight params`) is applied unconditionally, making the boosted chain heavier than it legitimately is.

### Impact Explanation

An unprivileged peer can inject a `PerasCert` that claims to boost any block the peer has previously diffused. Because `validatePerasCert` never rejects, the certificate is stored and the node runs chain selection as if a legitimate quorum of stake had voted for that block. This can cause the honest node to prefer a non-canonical, attacker-chosen chain over the canonical chain, constituting a **chain-selection safety failure** driven by unauthorized certificate acceptance — matching the "High" impact tier: *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions"* and the "Critical" tier: *"Bypass of … certificate … checks … that enables unauthorized … certificate acceptance."*

### Likelihood Explanation

**High.** The ObjectDiffusion mini-protocol is open to any connected peer. No special privilege, stake ownership, or key material is required. The attacker only needs to (a) connect to the target node, (b) diffuse a valid block via BlockFetch, and (c) immediately send a crafted `PerasCert` boosting that block. The entire path is exercised in normal node operation; no unusual conditions are needed.

### Recommendation

1. Implement full cryptographic and semantic validation inside `validatePerasCert` for every concrete block type, including BLS aggregate-signature verification over `(pcCertRound, pcCertBoostedBlock)`, committee-membership proof verification for each voter listed in `pcVoters`, and quorum-threshold checks — mirroring the checks already planned in the linked issue (cardano-peras#120).
2. Move certificate validation inside the same STM transaction as the deduplication check in `processCerts`, matching the atomic pattern already used in `processVotes`, to eliminate the TOCTOU window between the deduplication read and the subsequent `addCert` call.
3. Remove or gate the degenerate `instance StandardHash blk => BlockSupportsPeras blk` so that any block type lacking a real implementation fails to compile rather than silently accepting all certificates.

### Proof of Concept

```
Private testnet sequence
────────────────────────
1. Attacker node A connects to honest node H via the standard
   NodeToNode handshake (no special privileges required).

2. A diffuses a valid block B_fork at slot S on a minority fork
   via the BlockFetch mini-protocol. H stores B_fork in its
   VolatileDB but does not yet prefer the fork.

3. A opens the ObjectDiffusion (Peras certificate) mini-protocol
   and sends a single-element batch:

     [ PerasCert { pcCertRound    = someRound
                 , pcCertBoostedBlock = headerPoint B_fork } ]

   No BLS signature, no voter list, no eligibility proof is
   included or checked.

4. H's inbound handler calls:
     processCerts … (validatePerasCert mkPerasParams) … [cert]
   validatePerasCert returns Right unconditionally (SupportsPeras.hs:353-358).

5. The certificate is stored in H's PerasCertDB with boost weight
   perasWeight mkPerasParams.

6. chainSelSync triggers chainSelectionForBlock for B_fork
   (ChainSel.hs:531). The fork now carries artificial Peras weight
   and H switches to the attacker's chain.

Observable outcome: H's selected chain tip moves to B_fork,
diverging from the canonical chain, without any legitimate quorum
of stake having voted.
