### Title
`noCertsFromTwoRoundsAgo` Returns Inverted Boolean in Rounds 0–1, Permanently Blocking Peras Certificate Inclusion - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Peras/Cert/Inclusion.hs`)

---

### Summary

The `noCertsFromTwoRoundsAgo` predicate in the Peras certificate-inclusion logic hard-codes `Bool False` for Peras rounds 0 and 1. Because this predicate is the first conjunct of `needCertRules`, the entire conjunction evaluates to `False` in those rounds, and `needCert` always returns `DoNotIncludeCert`. No Peras certificate is ever embedded in a block during rounds 0 and 1, regardless of whether every other inclusion condition is satisfied. This is the direct analog of M-04: a time-gated gate uses the wrong reference value (current-time instead of expiry / `False` instead of vacuous `True`), causing the gate to fire incorrectly.

---

### Finding Description

`needCertRules` is a three-way conjunction that governs whether a block producer must embed a Peras certificate in the block it is forging:

```
needCertRules pciv =
  noCertsFromTwoRoundsAgo pciv
    :/\: latestCertSeenIsNotExpired pciv
    :/\: latestCertSeenIsNewerThanLatestCertOnChain pciv
``` [1](#0-0) 

The first conjunct, `noCertsFromTwoRoundsAgo`, is supposed to be `True` when the node has **not** yet seen a certificate from two rounds ago (meaning the latest certificate it holds is still "fresh" and should be propagated). For `currRoundNo >= 2` the implementation correctly returns `Not (Bool containsCertFromTwoRoundsAgo)`:

```haskell
| otherwise =
    NoCertsFromTwoRoundsAgo currRoundNo
      := Not (Bool containsCertFromTwoRoundsAgo)
``` [2](#0-1) 

For `currRoundNo < 2` the implementation returns a hard-coded `Bool False`:

```haskell
-- We cannot have possibly seen a certificate from two rounds ago if we are
-- in round 0 or 1. In that case, this is vacuously false.
| currRoundNo < 2 =
    NoCertsFromTwoRoundsAgo currRoundNo
      := Bool False
``` [3](#0-2) 

The comment says "vacuously false," but the predicate's semantics are the **opposite**: `noCertsFromTwoRoundsAgo = True` means "we have **not** seen a cert from two rounds ago → include the cert." In rounds 0 and 1 there are no rounds −2 or −1, so the node provably has **not** seen a cert from two rounds ago; the predicate should therefore be vacuously **`True`**. Returning `False` asserts the opposite — "we **have** seen a cert from two rounds ago" — which is factually impossible and permanently blocks inclusion.

The test-model in the test suite replicates the same error, confirming the bug propagated into the reference model:

```haskell
noCertsFromTwoRoundsAgo =
  if currRoundNo < 2
    then False          -- ← same wrong value
    else not ((currRoundNo - 2) `Set.member` certIds)
``` [4](#0-3) 

---

### Impact Explanation

**Classification: High — Peras voting/certificate check bug that breaks cross-era consensus invariants for production Cardano nodes.**

When Peras is enabled, the block producer calls `needCert` (via `needCertRules`) to decide whether to embed a `ValidatedPerasCert` in the block it is forging. Because `noCertsFromTwoRoundsAgo` is the first conjunct and short-circuits the conjunction, **no certificate is ever included in any block produced during Peras rounds 0 and 1**, even when:

- a valid, unexpired certificate exists (`latestCertSeenIsNotExpired = True`), and  
- that certificate is newer than anything already on-chain (`latestCertSeenIsNewerThanLatestCertOnChain = True`).

Peras chain selection assigns extra weight to chains that carry certificates. A chain that omits certificates in rounds 0–1 carries less weight than the protocol specifies. Any node running a spec-conformant implementation (or a patched version) would compute a higher weight for a competing chain that correctly includes those certificates, causing the two populations to diverge on which chain is canonical. This is a cross-implementation consensus split at the very start of every Peras epoch.

---

### Likelihood Explanation

- Peras is implemented in the production `ouroboros-consensus` package (not a test or unstable library) and is gated by a feature flag; it will be active on mainnet when the flag is enabled.  
- The bug fires deterministically in **every** Peras round 0 and round 1 — i.e., at the start of every Peras epoch — requiring no special attacker input.  
- The test model replicates the same wrong value, so existing property tests do not catch the divergence from the spec.  
- An unprivileged peer that serves a chain produced by a spec-conformant node (with certificates in rounds 0–1) will cause an honest node running the buggy code to compute a lower weight for that chain, potentially causing it to prefer a weaker chain.

---

### Recommendation

Change the early-round branch to return `Bool True` (vacuously true — we have not seen a cert from two rounds ago because those rounds do not exist):

```haskell
| currRoundNo < 2 =
    NoCertsFromTwoRoundsAgo currRoundNo
      := Bool True   -- vacuously TRUE: rounds -2/-1 do not exist
```

Update the test model in `Test.Consensus.Peras.Cert.Inclusion` correspondingly:

```haskell
noCertsFromTwoRoundsAgo =
  if currRoundNo < 2
    then True
    else not ((currRoundNo - 2) `Set.member` certIds)
```

### Proof of Concept

Consider a Peras-enabled node at `currRoundNo = 1` with:

- `latestCertSeen` = a valid certificate from round 0 (not expired, `_A ≥ 1`)  
- `latestCertOnChain` = `Origin` (no cert on chain yet)

Per the spec all three conditions are satisfied:

| Condition | Expected | Actual |
|---|---|---|
| `noCertsFromTwoRoundsAgo` | `True` (round −1 does not exist) | **`False`** ← bug |
| `latestCertSeenIsNotExpired` | `True` (`1 ≤ _A + 0`) | `True` |
| `latestCertSeenIsNewerThanLatestCertOnChain` | `True` (Origin) | `True` |

Because the first conjunct is `False`, `evalPred (needCertRules pciv)` returns `EFalse`, `needCert` returns `DoNotIncludeCert`, and the forged block carries no certificate. A spec-conformant peer forging the same block would include the certificate, producing a block with higher Peras weight. Honest nodes comparing the two chains via Peras-weighted chain selection would prefer the spec-conformant chain, causing a consensus split. [5](#0-4) [6](#0-5)
