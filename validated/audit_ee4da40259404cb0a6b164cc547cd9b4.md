### Title
Unconditional Peras Certificate Acceptance Bypasses All Cryptographic Verification, Enabling Unauthorized Chain Boost - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The default `BlockSupportsPeras` instance implements `validatePerasCert` as a stub that unconditionally returns `Right` (success) for every inbound certificate, performing zero cryptographic or structural verification. This stub is wired directly into the production peer-facing certificate ingestion pipeline (`processCerts` → `makePerasCertPoolWriterFromChainDB`). Any unprivileged peer can send a crafted `PerasCert` naming any block as the boosted target; the node will accept it, store it in the `PerasCertDB`, and apply its full `perasWeight` boost during chain selection, potentially causing the node to prefer a non-canonical chain.

### Finding Description

**Root cause — `validatePerasCert` stub always returns `Right`:**

In the default `BlockSupportsPeras` instance, the certificate validation function is a placeholder that accepts every certificate unconditionally:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No check is performed on:
- The aggregate vote signature attesting that a quorum of stake pools actually voted for the boosted block
- The round number's validity relative to the current epoch/slot
- The boosted block's existence or validity on any chain
- The issuer's membership in the voting committee

**This stub is the active production validator.** The comment on the enclosing instance reads:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
``` [2](#0-1) 

This is the only `BlockSupportsPeras` instance in the repository and is therefore the instance used for all block types in production.

**Attacker-controlled entry path — `makePerasCertPoolWriterFromChainDB`:**

The production certificate pool writer for the ChainDB passes `validatePerasCert mkPerasParams` directly as the validation function to `processCerts`:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [3](#0-2) 

`processCerts` applies `validateCert` to every inbound certificate and, if all pass, adds them to the database:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [4](#0-3) 

Because `validatePerasCert` never returns `Left`, the `(errs, _)` branch is unreachable. Every certificate a peer sends is accepted.

**Chain selection consequence:**

Once a `ValidatedPerasCert` is stored in the `PerasCertDB`, `chainSelSync` in `ChainSel.hs` uses it to boost the named block during chain selection:

```haskell
-- Trigger chain selection for the boosted block.
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [5](#0-4) 

The boost value is `perasWeight = PerasWeight 15` from `mkPerasParams`, which is the fixed default applied to every accepted certificate. [6](#0-5) 

**Analog to the external report:**

| ERC4626 vulnerability | Ouroboros Consensus analog |
|---|---|
| `withdraw(assets, receiver, owner)` checks no allowance between `msg.sender` and `owner` | `validatePerasCert params cert` checks no cryptographic relationship between the peer and the claimed certificate |
| Any caller can drain any owner's funds | Any peer can inject a certificate boosting any block |
| `_shareToken.spendSelfAllowance` is called but `msg.sender` authorization is never verified | `processCerts` calls `validateCert` but the implementation always returns `Right` |

### Impact Explanation

**High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain.**

An attacker with no stake and no keys can:

1. Connect to a target node as a normal peer via the object-diffusion mini-protocol.
2. Craft a `PerasCert` with `pcCertBoostedBlock` pointing to any block on a minority fork (or a block the attacker controls).
3. Send the certificate. The node accepts it unconditionally, stores it, and applies a `PerasWeight 15` boost to the named block.
4. If the boosted fork's accumulated weight (natural chain weight + 15) exceeds the honest chain's weight, the node switches to the adversarial fork.

This violates the core Peras security invariant: only a certificate backed by a quorum of honest stake should be able to boost a block. The missing check is the direct analog of the missing `msg.sender == owner` check in the ERC4626 report — in both cases, the authorization gate that should gate a privileged state change is simply absent.

### Likelihood Explanation

**High.** The object-diffusion mini-protocol for Peras certificates is a standard peer-to-peer channel. Any node that connects as a peer can send `PerasCert` messages. No stake, no keys, and no prior relationship with the target node are required. The only precondition is that the Peras certificate diffusion protocol is active, which is the case whenever the Peras extension is enabled. The exploit requires sending a single well-formed CBOR-encoded `PerasCert` message.

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:

1. Verifies the aggregate BLS vote signature in the certificate against the declared set of voters and the election ID (round number + boosted block hash).
2. Checks that the declared voters are members of the voting committee for the relevant epoch (i.e., their seat indices are within bounds and their stake is non-zero).
3. Checks that the total stake of the declared voters exceeds the quorum threshold (`perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin`).
4. Checks that the round number is within the valid acceptance window relative to the current slot.

The `EveryoneVotes` and `WFALS` committee implementations in `Committee/EveryoneVotes.hs` and `Committee/WFALS.hs` already provide `implVerifyCert` functions that perform these checks correctly and should be wired into `validatePerasCert` once the HFC plumbing (tracked in issue #73) is in place. [7](#0-6) 

### Proof of Concept

**Preconditions:** Peras certificate diffusion is active; the attacker has a standard peer connection to the target node.

**Steps:**

1. Identify a block `B_fork` on a minority fork that the attacker wants the target node to adopt.
2. Construct a `PerasCert` value:
   ```
   PerasCert { pcCertRound = <any valid round number>
             , pcCertBoostedBlock = <Point of B_fork> }
   ```
   Serialise it as CBOR (the `Serialise` instance is straightforward: a 2-element list of round number and block point).
3. Send the serialised certificate to the target node via the object-diffusion mini-protocol for Peras certificates.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{..}` unconditionally.
5. The certificate is stored in `PerasCertDB` and `chainSelSync` triggers chain selection for `B_fork` with a `PerasWeight 15` boost.
6. If `weight(fork containing B_fork) + 15 > weight(current honest chain)`, the node switches to the adversarial fork.

The attack requires no cryptographic material and no stake. The only constraint is that `B_fork` must be in the node's `VolatileDB` (i.e., the node must have already downloaded the block), which is achievable by first serving the block to the node via the standard block-fetch protocol.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

-- | Verify a certificate attesting the winner of a given election
implVerifyCert ::
  forall crypto.
  CryptoSupportsAggregateVoteSigning crypto =>
  VotingCommittee crypto EveryoneVotes ->
  Cert crypto EveryoneVotes ->
  Either
    (VotingCommitteeError crypto EveryoneVotes)
    (NE [EligibilityWitness crypto EveryoneVotes])
implVerifyCert committee = \case
  EveryoneVotesCert electionId candidate voters aggSig -> do
    -- Traverse the list of voters in ascending seat index order, collecting:
    -- 1. their membership status
    -- 2. their vote verification keys (to verify the aggregate vote signature)
    (members, voteVerificationKeys) <-
      fmap munzip . flip traverse (NESet.toAscList voters) $ \case
        seatIndex
          | Just (_, voterPublicKey, voterStake, _) <-
              getCandidateIfSeatWithinBounds seatIndex (extWFAStakeDistr committee) -> do
              let voterVerificationKey =
                    getVoteVerificationKey (Proxy @crypto) voterPublicKey
              case nonZero voterStake of
                Nothing ->
                  Left (PoolHasNoStake seatIndex)
                Just nonZeroVoterStake ->
                  pure
                    ( EveryoneVotesMember
                        seatIndex
                        nonZeroVoterStake
                    , voterVerificationKey
                    )
          | otherwise ->
              Left (MissingSeatIndex seatIndex)
    -- Verify aggregate signature
    aggVerificationKey <-
      bimap CryptoError id $ do
        aggregateVoteVerificationKeys
          (Proxy @crypto)
          voteVerificationKeys
    bimap InvalidCertSignature id $
      verifyAggregateVoteSignature
        (Proxy @crypto)
        aggVerificationKey
        electionId
        candidate
        aggSig

    -- Return the list of voters attesting the election winner
    pure members
