### Title
Attacker Can Front-Run `request_refund` to Permanently Block or Redirect a User's BTC Refund - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
`request_refund` is a two-step async operation: it first calls the BTC Light Client to verify the transaction, then in a callback stores the `RefundRequest` keyed by `utxo_storage_key` (`txid@vout`). Because the UTXO key is fully public and the async window between the Light Client call and the callback spans at least one NEAR block, an unprivileged attacker can observe Alice's pending `request_refund` transaction and submit their own `request_refund` for the same UTXO with an attacker-controlled `refund_address`. If the attacker's callback is processed first, Alice's callback panics with "Refund request already exists for this UTXO", her NEAR storage deposit is forfeited, and she is permanently blocked from re-submitting a refund for that UTXO. In the worst case the attacker's refund request is executed, redirecting Alice's BTC to the attacker's address.

### Finding Description

`request_refund` is a public, payable function callable by any NEAR account:

```rust
// contracts/satoshi-bridge/src/api/bridge.rs  lines 510-535
pub fn request_refund(
    &mut self,
    deposit_msg: DepositMsg,
    refund_address: String,
    tx_bytes: Base64VecU8,
    vout: usize,
    proof: TxInclusionProof,
    gas_fee: Option<U128>,
) -> Promise { ... }
```

It calls `internal_request_refund`, which dispatches an async cross-contract call to the BTC Light Client and schedules `request_refund_callback`. The callback is where the `RefundRequest` is actually stored:

```rust
// contracts/satoshi-bridge/src/refund.rs  lines 543-547
// Double-check no duplicate (another request_refund could have landed between our check and callback)
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
```

The developers acknowledge the race window in the comment, but the guard only prevents a second identical request — it does not prevent an attacker from racing with a *different* `refund_address`.

The `refund_address` parameter is validated against `deposit_msg.refund_address` only when the latter is `Some`:

```rust
// contracts/satoshi-bridge/src/refund.rs  lines 154-158
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
```

When `deposit_msg.refund_address` is `None` (a supported and common case — the field is `skip_serializing_if = "Option::is_none"`), the attacker is free to supply any `refund_address`. The `deposit_msg` itself must match the Bitcoin transaction output (verified in the callback via `get_deposit_path` → `generate_utxo_chain_address`), so the attacker simply copies Alice's `deposit_msg`, `tx_bytes`, `vout`, and `proof` verbatim, substituting only `refund_address`.

Once the attacker's `RefundRequest` is stored, Alice is permanently blocked:

- She cannot re-submit `request_refund` for the same UTXO (duplicate check rejects it).
- She cannot call `reject_refund` herself — only DAO/Operator can reject, or the UTXO must already be in `verified_deposit_utxo`.

```rust
// contracts/satoshi-bridge/src/api/bridge.rs  lines 564-568
require!(
    is_privileged || is_already_deposited,
    "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
);
```

After `unsafe_refund_timelock_sec` elapses, the attacker calls `execute_refund`, which builds a PSBT paying Alice's BTC to the attacker's `refund_address` and routes it through the MPC signing pipeline.

### Impact Explanation

**Minimum (DoS / stuck funds — Medium):** Alice's `request_refund_callback` panics, her NEAR storage deposit is forfeited, and she cannot re-submit a refund for that UTXO without DAO/Operator intervention. The attacker can repeat the front-run every time Alice retries, permanently locking her BTC in the bridge's MPC-controlled address with no trustless recovery path.

**Maximum (fund theft — Critical):** If the DAO/Operator does not reject the attacker's request within `unsafe_refund_timelock_sec`, the attacker executes the refund and receives Alice's BTC at their own address. The `unsafe_refund_timelock_sec` is a trusted-operator mitigation, not a trustless protocol guarantee.

Both impacts fall within the allowed scope:
- *Medium*: "Attacker-triggered temporary locking of bridged funds" / "stuck bridge state requiring operator intervention."
- *Critical*: "Significant loss, theft, or permanent locking of user funds."

### Likelihood Explanation

- `request_refund` is fully public and requires only a small NEAR storage deposit.
- All inputs needed to replicate Alice's call (`deposit_msg`, `tx_bytes`, `vout`, `proof`) are visible on-chain the moment Alice's transaction is included in a NEAR block.
- The async window (Light Client cross-contract call + callback scheduling) spans at least one NEAR block (~1 second), giving the attacker ample time to submit a competing transaction.
- The `deposit_msg.refund_address = None` path is explicitly supported and is the natural choice for users who did not pre-authorize a refund address at deposit time.
- No special privilege, leaked key, or off-chain coordination is required.

### Recommendation

1. **Bind the refund request to the caller's NEAR account ID.** Store `predecessor_account_id()` in the `RefundRequest` at the time of the initial call (before the async window) and enforce in the callback that only the original caller's request can be stored for a given UTXO.
2. **Require `deposit_msg.refund_address` to be set.** Eliminate the `None` path so the refund destination is always committed at deposit time and cannot be overridden by a racing caller.
3. **Alternatively, use a commit-reveal scheme** where the caller commits to a hash of `(utxo_storage_key, refund_address, caller)` synchronously before the Light Client call, and the callback verifies the commitment.

### Proof of Concept

**Attack steps:**

1. Alice calls `request_refund` with `deposit_msg = { recipient_id: "alice.near", refund_address: None }`, `refund_address = "bc1q_alice..."`, and a valid `tx_bytes`/`proof` for her stuck deposit.
2. Alice's call is included in NEAR block N. The Light Client cross-contract call is scheduled; the callback will land in block N+2 or later.
3. Eve observes Alice's transaction in block N. Eve immediately calls `request_refund` with the **identical** `deposit_msg`, `tx_bytes`, `vout`, and `proof`, but substitutes `refund_address = "bc1q_eve..."`.
4. Eve's Light Client call is also scheduled. Depending on transaction ordering, Eve's `request_refund_callback` lands before Alice's.
5. Eve's callback passes the duplicate check (no entry yet) and stores `RefundRequest { refund_address: "bc1q_eve...", ... }`.
6. Alice's callback arrives and panics: `"Refund request already exists for this UTXO"`. Alice's NEAR storage deposit is lost.
7. Alice attempts to call `request_refund` again — rejected: `"Refund request already exists for this UTXO"`.
8. Alice attempts `reject_refund` — rejected: `"Only DAO/Operator can reject, or UTXO must be already verified via deposit"`.
9. After `unsafe_refund_timelock_sec`, Eve calls `execute_refund`. The bridge builds a PSBT spending Alice's deposit UTXO and paying `"bc1q_eve..."`. MPC signs it. Eve broadcasts and receives Alice's BTC.

    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
