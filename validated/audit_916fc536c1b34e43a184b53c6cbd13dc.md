Audit Report

## Title
Missing Cancel/Refund Path Causes Permanent Fund Freeze When EVM Token Transfer Permanently Fails - (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

## Summary
In `finTransfer`, all token delivery paths (native ERC20 `safeTransfer`, ETH `.call`, ERC1155 `safeTransferFrom`, and bridge-token `mint`) revert the entire transaction if delivery fails. Because the recipient address is cryptographically bound in the MPC signature and no cancel or refund function exists on the NEAR side for failed EVM finalizations, a permanently undeliverable transfer (e.g., USDC-blacklisted recipient) leaves the user's funds irreversibly locked on NEAR.

## Finding Description
`finTransfer` marks the nonce at line 287 before performing the transfer, but because all state changes are atomic in EVM, a revert in the transfer leg rolls back the nonce mark as well. The transaction can therefore be retried indefinitely, but if the delivery condition is permanently broken the transfer can never be finalized.

The recipient is encoded into the MPC-signed borsh payload at line 298 (`Borsh.encodeAddress(payload.recipient)`). A different recipient requires a new MPC signature, which the MPC network will not issue for an already-initiated transfer. On the NEAR side, `remove_transfer_message` (line 2194) is an internal helper; no public function exposes a cancel or refund path for a transfer whose EVM finalization has permanently failed. The `pending_transfers` entry persists, but the burned/locked tokens on NEAR cannot be reclaimed.

Affected delivery paths:
- **Native ERC20** (line 351): `IERC20(payload.tokenAddress).safeTransfer(payload.recipient, payload.amount)` — reverts if the token's `transfer` reverts (e.g., USDC blacklist).
- **Native ETH** (line 319–322): `.call{value: payload.amount}("")` followed by `revert FailedToSendEther()` — reverts if the recipient contract rejects ETH.
- **ERC1155** (line 324–330): `safeTransferFrom` — reverts if the recipient does not implement `IERC1155Receiver`.

## Impact Explanation
Permanent freezing of bridged funds across NEAR and EVM, which is explicitly listed as a critical allowed impact. The user's tokens are burned or locked on NEAR at initiation time; if EVM finalization is permanently blocked, those tokens are unrecoverable. No privileged recovery path exists in the bridge contracts.

## Likelihood Explanation
Low but concrete. USDC — a primary asset expected to flow through the bridge — enforces a blacklist on every `transfer` and `transferFrom` call. USDC blacklisting of EVM addresses is a documented, recurring real-world event (OFAC compliance). If a recipient address is blacklisted between NEAR initiation and EVM finalization, the transfer is permanently undeliverable. The ETH-rejection variant is reachable by any user who specifies a smart-contract recipient whose `receive` function reverts. Neither variant requires privileged access or unrealistic assumptions.

## Recommendation
Adopt the pull pattern: instead of pushing tokens directly to `payload.recipient`, credit the amount to an internal `claimable[recipient][token]` mapping and expose a separate `claim(address token)` function. This guarantees `finTransfer` always succeeds (consuming the nonce permanently), and the recipient can claim tokens at any time. Alternatively, wrap the transfer in a `try/catch` and on failure credit the claimable balance, ensuring the nonce is consumed regardless of delivery outcome. A symmetric cancel/refund function should also be added to the NEAR bridge so that a transfer whose EVM finalization is provably impossible can be unwound on the origin chain.

## Proof of Concept
1. User initiates a USDC transfer from NEAR to EVM, specifying EVM address `R`. NEAR burns the USDC representation and stores the `TransferMessage` in `pending_transfers`.
2. The MPC network signs the transfer message, cryptographically binding `R` as recipient (encoded at line 298 of `OmniBridge.sol`).
3. USDC blacklists address `R` (e.g., OFAC compliance action by Circle).
4. Relayer calls `finTransfer(signatureData, payload)` on `OmniBridge.sol`.
5. Line 287 executes: `completedTransfers[payload.destinationNonce] = true`.
6. Signature verification passes (lines 311–313).
7. Line 351: `IERC20(payload.tokenAddress).safeTransfer(R, amount)` — USDC reverts because `R` is blacklisted.
8. Entire transaction reverts atomically, including the nonce mark at line 287.
9. Relayer retries — identical revert every time. Transfer can never be finalized.
10. User's USDC is permanently locked on NEAR. No public cancel or refund function exists in `near/omni-bridge/src/lib.rs` to recover the funds. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

    fn remove_transfer_message(&mut self, transfer_id: TransferId) -> TransferMessage {
        let storage_usage = env::storage_usage();
        let transfer = self
            .pending_transfers
            .remove(&transfer_id)
            .map(storage::TransferMessageStorage::into_main)
            .near_expect(BridgeError::TransferNotExist);

        let refund =
            env::storage_byte_cost().saturating_mul((storage_usage - env::storage_usage()).into());

        if let Some(mut storage) = self.accounts_balances.get(&transfer.owner) {
            storage.available = storage.available.saturating_add(refund);
            self.accounts_balances.insert(&transfer.owner, &storage);
        }

        transfer.message
    }
