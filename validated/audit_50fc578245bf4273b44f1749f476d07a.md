**`require_pending_sign_capacity` implementation** (`account.rs` lines 113-123):
- Checks `pending_sign_count() < get_max_pending_sign_txs(account_id)`
- Default max is **1** (line 110)

- Looks up `user_account_id` from the pending info
- Calls `require_pending_sign_capacity(&user_account_id)` — checking the **user's** slot, not the operator's

**Attack path:**
1. User initiates withdrawal → added to `btc_pending_sign_ids`, count = 1 = max (default)
2. Relayer signs it → moves to PendingVerify, removed from `btc_pending_sign_ids`, count = 0
3. User immediately initiates a second withdrawal → count = 1 = max again
4. Original withdrawal exceeds `max_btc_tx_pending_sec`
5. Operator calls `cancel_withdraw(original_id, output)` → `require_pending_sign_capacity` checks `1 < 1` → **panics**

The cancel is permanently blocked as long as the user keeps their second withdrawal in PendingSign. The user can keep refreshing this by letting it sign and immediately creating another.

### Title
Operator `cancel_withdraw` permanently blocked by user filling `pending_sign_count` to limit — (`contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary
`cancel_withdraw` checks the **victim user's** `pending_sign_capacity` before creating the cancel-RBF entry. A user can deliberately fill their own pending sign slot after their original withdrawal moves to `PendingVerify`, causing the operator's `cancel_withdraw` call to panic and permanently locking the bridge UTXO.

### Finding Description
`cancel_withdraw` in `bridge.rs` resolves the `user_account_id` from the stuck pending info and then calls `require_pending_sign_capacity(&user_account_id)` before proceeding: [1](#0-0) 

`require_pending_sign_capacity` enforces a strict `<` check against the per-account limit (default: **1**): [2](#0-1) 

The default limit is 1: [3](#0-2) 

When a withdrawal moves from `PendingSign` to `PendingVerify` (after the relayer signs it), it is removed from `btc_pending_sign_ids`, freeing the slot. The user can immediately initiate a new withdrawal to re-fill that slot. Once the original withdrawal exceeds `max_btc_tx_pending_sec`, the operator's `cancel_withdraw` call will always panic because the user's `pending_sign_count` (1) is not `< max_pending` (1).

The new withdrawal that fills the slot can itself be signed and moved to PendingVerify, and the user repeats the fill — maintaining the block indefinitely.

### Impact Explanation
The bridge UTXO locked by the original withdrawal cannot be reclaimed. The operator has no alternative path to cancel the stuck withdrawal. The BTC remains permanently locked in the bridge's UTXO set with no recovery mechanism available to the operator while the user maintains the block.

### Likelihood Explanation
Any user with a withdrawal in `PendingVerify` can execute this with a single additional `ft_transfer_call` (the public deposit/withdraw entrypoint). No special privileges are required. The default `max_pending` of 1 makes this trivially achievable — the user only needs one additional pending sign transaction. [4](#0-3) 

### Recommendation
Remove the `require_pending_sign_capacity` check from `cancel_withdraw` (and `cancel_active_utxo_management`). The cancel-RBF entry should be inserted unconditionally by the operator regardless of the user's current pending sign count, since the operator is acting on an already-expired transaction. Alternatively, exempt operator-initiated cancel paths from the per-user capacity guard.

### Proof of Concept
1. User calls `ft_transfer_call` → withdrawal W1 enters `PendingSign`, `pending_sign_count = 1`
2. Relayer calls `sign_btc_transaction` → W1 moves to `PendingVerify`, `pending_sign_count = 0`
3. User calls `ft_transfer_call` again → withdrawal W2 enters `PendingSign`, `pending_sign_count = 1`
4. Time advances past `max_btc_tx_pending_sec` for W1
5. Operator calls `cancel_withdraw(W1_id, output)` → `require_pending_sign_capacity` checks `1 < 1` → panics with "Too many pending sign transactions"
6. W1's UTXO is permanently locked; operator cannot cancel regardless of how many times they retry [5](#0-4)
