### Title
Peras Certificate Validation Bypass Allows Unprivileged Peer to Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` method in the sole production `BlockSupportsPeras` instance is a stub that unconditionally accepts every inbound Peras certificate without performing any cryptographic, structural, or eligibility checks. Because the ObjectDiffusion inbound path (`makePerasCertPoolWriterFromChainDB`) feeds peer-supplied certificates directly through this stub and then into `ChainDB.addPerasCertAsync`, an unprivileged peer can inject a crafted certificate that boosts an arbitrary block already present in the VolatileDB, causing the honest node to trigger chain selection for that block with artificially inflated Peras weight.

---

### Finding Description

The `BlockSupportsPeras` typeclass declares `validatePerasCert` as the mandatory gate for all inbound Peras certificates. The only instance in the codebase is the catch-all degenerate instance:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

This stub returns `Right` for every certificate regardless of its `pcCertRound`, `pcCertBoostedBlock`, aggregate BLS signature, or committee membership. No more-specific instance overrides it for Cardano blocks.

The production inbound path in `makePerasCertPoolWriterFromChainDB` passes this stub directly as the validator:

```haskell
processCerts
  systemTime
  (ChainDB.getPerasCertIds chainDB)
  -- TODO replace when actual plumbing is in place
  (validatePerasCert mkPerasParams)
  (void . ChainDB.addPerasCertAsync chainDB)
  certs
``` [2](#0-1) 

`processCerts` partitions results: if all certificates pass (which they always do), each is timestamped and forwarded to `addCert` (i.e., `ChainDB.addPerasCertAsync`). [3](#0-2) 

Inside `chainSelSync`, once a certificate is stored, the node looks up the boosted block in the VolatileDB and, if found, immediately calls `chainSelectionForBlock` with the certificate's weight applied:

```haskell
boostedHdr <-
  lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
    Nothing -> do
      lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
      idExitEarly $ addedCertRes
    Just boostedHdr -> pure boostedHdr

-- Trigger chain selection for the boosted block.
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3)

### Impact Explanation

Peras certificates exist precisely to add extra weight to a block so that chain selection prefers it over competing forks. By bypassing `validatePerasCert`, an attacker can:

1. Craft a `PerasCert` with an arbitrary `pcCertRound` and a `pcCertBoostedBlock` pointing to any block currently in the VolatileDB.
2. Send it over the ObjectDiffusion mini-protocol.
3. The honest node stores it and re-runs chain selection for the boosted block, now weighted by `perasWeight params`.

This lets an unprivileged peer make an honest node prefer a non-canonical or adversarially chosen fork, directly undermining the chain-selection security guarantees that Peras is designed to provide. The impact class is **High**: chain-selection manipulation by an unprivileged peer beyond the intended security assumptions.

---

### Likelihood Explanation

Any peer reachable via the ObjectDiffusion mini-protocol can send crafted certificates. No stake, key material, or operator access is required. The only prerequisite is knowing (or guessing) a block hash present in the target node's VolatileDB, which is publicly observable via ChainSync. Likelihood is **Medium**.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real one that:

1. Verifies the aggregate BLS signature over `(pcRoundNo, pcBoostedBlock)` against the committee's aggregate verification key.
2. Checks that `pcRoundNo` corresponds to a round that is plausible given the current slot (i.e., not from the far future or an expired round).
3. Verifies that the voters encoded in the certificate are legitimate committee members with sufficient combined stake to form a quorum.
4. Rejects certificates whose `pcBoostedBlock` slot is inconsistent with the claimed round number.

Until the real implementation is in place, the TODO at `https://github.com/tweag/cardano-peras/issues/120` should be treated as a security-critical blocker, not a deferred feature.

### Proof of Concept

```
Attacker node  ──ObjectDiffusion──►  Honest node
                                        │
  send PerasCert {                      │
    pcCertRound    = <any round>,       │
    pcCertBoostedBlock = <hash of       │
      block B already in VolatileDB>    │
  }                                     │
                                        ▼
                              processCerts calls
                              validatePerasCert mkPerasParams
                                        │
                              always returns Right
                                        │
                              ChainDB.addPerasCertAsync
                                        │
                              chainSelSync:
                              VolatileDB.getBlockComponent B
                                → Just hdr
                              chainSelectionForBlock B
                              (with Peras boost weight applied)
                                        │
                              Node may switch to chain
                              containing B, even if it
                              is not the canonical chain
```

The attacker needs only a TCP connection to the honest node and knowledge of any block hash in its VolatileDB (trivially obtained via ChainSync). No cryptographic material or stake is required.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
