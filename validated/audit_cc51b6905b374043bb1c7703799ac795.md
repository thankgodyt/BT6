### Title
`ft_transfer` silently self-transfers user nBTC when `withdraw_relayer` is unset, permanently locking funds — (File: contracts/nbtc/src/lib.rs)

---

### Summary

The `ft_transfer` function in the nbtc contract implements a legacy bridging path for Near Intents. When a user calls `ft_transfer` with `receiver_id = nbtc_contract` and a memo prefixed with `WITHDRAW_TO:`, the function is supposed to redirect tokens to the configured `withdraw_relayer`. However, if `withdraw_relayer` is not set, the function silently falls through and executes a regular transfer to the nbtc contract itself — permanently locking the user's tokens in the contract's own balance with no built-in recovery path.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, the `ft_transfer` override implements a legacy Near Intents withdrawal path:

```rust
fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
    // Legacy bridging flow used by Near Intents
    if receiver_id == env::current_account_id()
        && memo
            .as_ref()
            .is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
    {
        if let Some(withdraw_relayer) = Self::read_withdraw_relayer_address() {
            return self.token.ft_transfer(withdraw_relayer, amount, memo);
        }
    }

    self.token.ft_transfer(receiver_id, amount, memo);  // ← silent fallthrough
}
``` [1](#0-0) 

When `read_withdraw_relayer_address()` returns `None` (key absent from storage), the `return` inside the `if let Some(...)` branch is never reached. Execution falls through to `self.token.ft_transfer(receiver_id, amount, memo)` where `receiver_id == env::current_account_id()` — the nbtc contract itself. [2](#0-1) 

The nbtc contract has no mechanism to recover tokens from its own balance:
- `burn` withdraws exclusively from `bridge_id`, not from the nbtc contract's own account. [3](#0-2) 
- No admin sweep or rescue function exists.

For the fallthrough transfer to succeed (rather than panic), the nbtc contract must be registered as a storage account. This is a public precondition: anyone can call `storage_deposit(account_id = nbtc_contract)` to register it. Once registered, any user invoking the legacy flow while `withdraw_relayer` is unset will have their tokens locked.

The `withdraw_relayer` is set only during `migrate_from_poa` or via `set_withdraw_relayer_address` (controller-only). A fresh deployment, a misconfiguration window, or an accidental unset leaves the contract in the vulnerable state. [4](#0-3) 

---

### Impact Explanation

User nBTC tokens are transferred into the nbtc contract's own balance and cannot be recovered through any normal bridge operation. The only recovery path requires the controller to call `attach_full_access_key` and then manually invoke `ft_transfer` from the nbtc contract's account — requiring privileged operator intervention. This matches **Medium: harmful smart-contract behavior without direct funds theft, including stuck bridge state requiring operator intervention**.

---

### Likelihood Explanation

Two preconditions must hold simultaneously:

1. `withdraw_relayer` is not set — possible during initial deployment, upgrade windows, or misconfiguration.
2. The nbtc contract is registered as a storage account — any unprivileged account can satisfy this by calling `storage_deposit`.

A malicious actor can pre-register the nbtc contract at negligible cost, then wait for any Near Intents user to trigger the legacy flow. The Near Intents integration is a documented, production-facing path, making user exposure realistic.

---

### Recommendation

Replace the silent fallthrough with an explicit revert when `withdraw_relayer` is not configured:

```rust
fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
    if receiver_id == env::current_account_id()
        && memo
            .as_ref()
            .is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
    {
        let withdraw_relayer = Self::read_withdraw_relayer_address()
            .unwrap_or_else(|| env::panic_str("withdraw_relayer not configured"));
        return self.token.ft_transfer(withdraw_relayer, amount, memo);
    }
    self.token.ft_transfer(receiver_id, amount, memo);
}
```

This ensures the legacy flow either routes correctly or reverts, never silently self-transferring.

---

### Proof of Concept

1. **Setup**: Attacker calls `nbtc.storage_deposit(account_id = nbtc_contract_id)` to register the nbtc contract as a token holder (costs only storage deposit NEAR).
2. **Precondition**: `withdraw_relayer` is not set (fresh deployment or misconfiguration window).
3. **Trigger**: User (or Near Intents on behalf of user) calls:
   ```
   nbtc.ft_transfer(
       receiver_id = nbtc_contract_id,
       amount = 1_000_000,
       memo = "WITHDRAW_TO:bc1q..."
   )
   ```
   with 1 yoctoNEAR attached (standard NEP-141 requirement).
4. **Execution**: `read_withdraw_relayer_address()` returns `None`. The `if let Some(...)` branch is skipped. `self.token.ft_transfer(nbtc_contract_id, 1_000_000, memo)` executes, transferring 1,000,000 nBTC from the user to the nbtc contract's own balance.
5. **Result**: User loses 1,000,000 nBTC. The nbtc contract holds them with no standard recovery path. `ft_balance_of(nbtc_contract_id)` returns `1_000_000`; `ft_balance_of(user)` decreases by the same amount. No BTC withdrawal is initiated.
