### Title
Missing `set_bridge_id` Function in nBTC Contract Permanently Locks Minting/Burning on Bridge Migration — (File: `contracts/nbtc/src/lib.rs`)

### Summary
The nBTC token contract stores a `bridge_id` field that is the sole account authorized to call `mint()` and `burn()`. Unlike the `controller` field, which has a corresponding `set_controller()` function, `bridge_id` is immutable after initialization. If the satoshi-bridge contract must ever be redeployed to a new NEAR account ID, the nBTC contract cannot be updated to recognize the new bridge, permanently breaking all minting and burning and locking user funds.

### Finding Description
In `contracts/nbtc/src/lib.rs`, the `Contract` struct holds two privileged fields:

```rust
pub struct Contract {
    controller: AccountId,
    bridge_id: AccountId,
    ...
}
```

The `controller` field is mutable via `set_controller()`:

```rust
pub fn set_controller(&mut self, controller: AccountId) {
    assert_one_yocto();
    self.assert_controller();
    self.controller = controller;
}
```

But `bridge_id` has no equivalent setter. The `assert_bridge()` guard, which gates every `mint()` and `burn()` call, checks only against the immutable `bridge_id`:

```rust
fn assert_bridge(&self) {
    require!(self.bridge_id == env::predecessor_account_id(), "Not Allow");
}
```

`bridge_id` is set once at `new()` (line 69) and is never writable again. The `migrate_from_poa()` function in `migrate.rs` accepts a `bridge_id` argument, but that path is a one-time historical migration from a PoA system and is not callable in normal operation.

### Impact Explanation
If the satoshi-bridge contract must be redeployed to a new NEAR account (e.g., due to a critical vulnerability requiring a fresh deployment, or a protocol-level account migration), the nBTC contract's `bridge_id` cannot be updated. Consequences:

- The new bridge account fails every call to `mint()` and `burn()` with `"Not Allow"`.
- Deposits verified on-chain cannot be minted to users.
- Withdrawals cannot be finalized (burn step fails), permanently locking all BTC held by the bridge.
- The only recovery path is redeploying the nBTC contract itself, which destroys all existing token balances and breaks every holder's position.

This matches the allowed impact: **Critical — Bypass of bridge migration or upgrade controls with real security impact**, and **Critical — Significant loss or permanent locking of user or protocol funds**.

### Likelihood Explanation
NEAR contracts are normally upgraded in-place (same account ID), so `bridge_id` is stable under routine upgrades. However, the codebase already demonstrates that account-level migrations occur: `migrate_from_poa()` in `migrate.rs` shows the bridge previously migrated from a PoA system with a different `bridge_id`. A future critical bug, regulatory requirement, or architectural change could force another such migration. At that point, the missing setter becomes a hard blocker with no on-chain remedy.

### Recommendation
Add a privileged `set_bridge_id` function to the nBTC contract, gated by `assert_controller()` and `assert_one_yocto()`, mirroring the existing `set_controller()` pattern:

```rust
#[payable]
pub fn set_bridge_id(&mut self, bridge_id: AccountId) {
    assert_one_yocto();
    self.assert_controller();
    self.bridge_id = bridge_id;
}
```

This allows the controller (DAO/governance) to point the nBTC contract at a new bridge account without redeploying the token and destroying all balances.

### Proof of Concept

1. Bridge is deployed at `satoshi-bridge.near`; nBTC is initialized with `bridge_id = "satoshi-bridge.near"`.
2. A critical vulnerability is discovered in `satoshi-bridge.near`. The DAO deploys a patched bridge at `satoshi-bridge-v2.near`.
3. The DAO attempts to update nBTC to recognize the new bridge — no `set_bridge_id` function exists; the call fails.
4. `satoshi-bridge-v2.near` calls `mint()` on nBTC → panics with `"Not Allow"` (line 333).
5. `satoshi-bridge-v2.near` calls `burn()` on nBTC → panics with `"Not Allow"` (line 333).
6. All BTC deposited to the bridge is permanently locked: deposits cannot be minted, withdrawals cannot be burned/finalized.

        if !env::state_exists() {
            env::panic_str("Old state not found. Migration is not needed.")
        }

        let state = env::storage_read(STATE_KEY)
            .unwrap_or_else(|| env::panic_str("Failed to read state key."));

        if let Ok(state) = NearIntentsState::try_from_slice(&state) {
            require!(
                env::storage_remove(OWNABLE_KEY),
                "Wrong token version for migration: __OWNER__ key not found"

            env::storage_write(
                WITHDRAW_RELAYER_ADDRESS,
                &borsh::to_vec(withdraw_relayer).unwrap(),
            );

            let new_state = Self {
                controller,
                bridge_id,
                token: state.token,
                metadata: LazyOption::new(StorageKey::Metadata, Some(state.metadata.get())),
            };

            new_state
        } else {
