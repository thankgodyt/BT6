### Title
Unconditional Peras Certificate Acceptance Enables Fake Weight Boost Injection into Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` implementation is a stub that unconditionally accepts every inbound Peras certificate without performing any cryptographic or semantic checks. An unprivileged peer can send a crafted `PerasCert` message that claims to boost any block, bypassing all validation, injecting an arbitrary weight boost into the node's `PerasWeightSnapshot`, and causing chain selection to prefer a non-canonical adversarial chain.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must verify a certificate's aggregate BLS signature, voter eligibility proofs, quorum threshold, and round/block consistency before the certificate is allowed to influence chain selection. The catch-all instance at line 320 of `SupportsPeras.hs` — explicitly marked as a temporary degenerate placeholder — implements this gate as an unconditional `Right`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is the implementation that `processCerts` in the object diffusion layer actually calls when handling inbound certificates from peers:

```haskell
(validatePerasCert mkPerasParams)
``` [2](#0-1) 

`processCerts` validates each certificate in a batch and, if all pass, adds them to the ChainDB: [3](#0-2) 

Once added, `chainSelSync` processes the certificate, reads the `PerasWeightSnapshot` (which now contains the fake boost), and triggers `chainSelectionForBlock` for the boosted block: [4](#0-3) 

Chain selection then computes `weightedSelectView` using the manipulated snapshot, where `wsvTotalWeight` sums block number and the injected weight boost: [5](#0-4) 

The `PerasWeightSnapshot` itself is built directly from all accepted certificates in the DB without re-validation: [6](#0-5) 

The analog to the flash loan attack is exact: just as the Behodler contract uses LP balances at a single point in time (manipulable by a flash loan) to compute a `growth` variable that determines token output, the Ouroboros node uses the `PerasWeightSnapshot` at chain-selection time (manipulable by a fake certificate) to compute `wsvTotalWeight` that determines which chain is adopted. In both cases, the measurement feeding the security-critical calculation is not protected against adversarial injection.

---

### Impact Explanation

An unprivileged peer can cause an honest node to switch to a non-canonical adversarial chain by injecting a fake `PerasCert` that boosts a block on the adversarial fork. Because `perasWeight` can be a large value (set by `PerasParams`), a single fake certificate can add enough weight to make a shorter adversarial chain outweigh the honest chain in `wsvTotalWeight`. This constitutes a **bypass of Peras certificate verification** enabling **unauthorized chain selection manipulation** — a critical consensus safety failure reachable by any unprivileged network peer.

---

### Likelihood Explanation

The attack requires only that the adversary can send a well-formed (but cryptographically unverified) `PerasCert` CBOR message over the object diffusion miniprotocol. No stake, keys, or special privileges are needed. The stub is the only `BlockSupportsPeras` instance in the consensus layer and is unconditionally used in the production inbound certificate processing path. Likelihood is high whenever Peras is active.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a complete check that verifies:
1. The aggregate BLS signature over `(roundNo, boostedBlock)` against the declared voter set.
2. Each voter's eligibility proof (persistent seat membership or VRF output for non-persistent seats).
3. That the number of voters meets the quorum threshold from `PerasParams`.
4. That `pcCertRound` and `pcCertBoostedBlock` are within acceptable bounds relative to the current chain tip.

Until the real implementation is in place, the node should refuse to process inbound certificates entirely (return `Left PerasValidationErr` unconditionally) rather than accept all of them.

---

### Proof of Concept

1. Attacker connects to a victim node via the object diffusion miniprotocol.
2. Attacker constructs a `PerasCert` with `pcCertRound = <current round>` and `pcCertBoostedBlock = <point on adversarial fork>`.
3. Attacker sends the certificate. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{..}` unconditionally.
4. The certificate is added to `PerasCertDB` via `addPerasCertAsync`.
5. `chainSelSync` fires `chainSelectionForBlock` for the boosted block.
6. `chainSelectionForBlock` reads `getPerasWeightSnapshot`, which now maps the adversarial block's point to `perasWeight params`.
7. `constructPreferableCandidates` calls `weightedSelectView`, computing `wsvTotalWeight = blockNo + perasWeight`. If `perasWeight` is large enough, the adversarial chain's total weight exceeds the honest chain's, and the node switches to it.
