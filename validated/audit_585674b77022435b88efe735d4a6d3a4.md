Audit Report

## Title
`claim_fee()` `#[trusted_relayer]` Guard Permanently Freezes Fees Owed to Non-Relayer Recipients - (File: `near/omni-bridge/src/lib.rs`)

## Summary
`claim_fee` is decorated with `#[trusted_relayer]`, which blocks any caller that is not a registered trusted relayer, `Role::DAO`, or `Role::UnrestrictedRelayer`. Because `sign_transfer` freely accepts an arbitrary `fee_recipient: Option<AccountId>`, a trusted relayer can legitimately designate any account (e.g., a treasury or fee-splitting contract) as the fee recipient. If that account is not itself a trusted relayer, it is permanently blocked from calling `claim_fee`, and no other code path exists to release the locked fee funds.

## Finding Description

`claim_fee` carries `#[trusted_relayer]` at line 1055, enforced by the impl-level macro configuration at lines 245–249 with bypass roles `Role::DAO` and `Role::UnrestrictedRelayer`:

```rust
// near/omni-bridge/src/lib.rs:1054-1064
#[payable]
#[trusted_relayer]
#[pause(except(roles(Role::DAO)))]
pub fn claim_fee(&mut self, #[serializer(borsh)] args: ClaimFeeArgs) -> Promise {
    self.verify_proof(args.chain_kind, args.prover_args).then(
        Self::ext(env::current_account_id())
            .with_attached_deposit(env::attached_deposit())
            .with_static_gas(CLAIM_FEE_CALLBACK_GAS)
            .claim_fee_callback(&env::predecessor_account_id()),
    )
}
```

`sign_transfer` (lines 447–452) accepts `fee_recipient: Option<AccountId>` with no restriction on what account is named. The value is embedded verbatim into the signed `TransferMessagePayload` and propagated to the destination chain.

`claim_fee_callback` (lines 1083–1086) already performs the correct and sufficient authorization: it verifies that the on-chain proof's `fee_recipient` field equals the caller:

```rust
require!(
    fee_recipient == *predecessor_account_id,
    BridgeError::OnlyFeeRecipientCanClaim.as_ref()
);
```

The `#[trusted_relayer]` guard fires before the proof is even submitted to the prover, so a non-relayer fee recipient never reaches the callback. The DAO bypass role does not help: if the DAO calls `claim_fee`, `predecessor_account_id` becomes the DAO account, which will not equal the designated `fee_recipient`, causing the callback to panic with `BridgeError::OnlyFeeRecipientCanClaim`. No other function calls `remove_transfer_message` for a fee-bearing pending transfer, so the funds are permanently locked in `pending_transfers`.

## Impact Explanation

Fees owed to any non-relayer, non-DAO fee recipient are permanently frozen inside `pending_transfers`. `claim_fee` is the sole mechanism to release these funds; no admin escape hatch exists that can both pass the `#[trusted_relayer]` guard and satisfy the `fee_recipient == predecessor_account_id` check simultaneously. This constitutes permanent freezing of bridged fee funds and fee mis-accounting, matching the Critical impact categories.

## Likelihood Explanation

Medium. The precondition is that a trusted relayer designates a non-relayer account as `fee_recipient` in `sign_transfer`. This is a natural and explicitly supported operational pattern (routing fees to a DAO treasury, a fee-splitting contract, or a dedicated collector). Nothing in the protocol prevents it, and the parameter type (`Option<AccountId>`) signals that arbitrary accounts are intended to be valid. Once the destination chain finalizes the transfer, the fee is irrecoverable.

## Recommendation

Remove the `#[trusted_relayer]` attribute from `claim_fee`. The callback's proof-backed `fee_recipient == predecessor_account_id` check is sufficient and correct authorization. Any account that can produce a valid proof showing it is the fee recipient should be permitted to call `claim_fee`.

```diff
-    #[trusted_relayer]
-    #[pause(except(roles(Role::DAO)))]

+    #[payable]

```

## Proof of Concept

1. Trusted relayer calls `sign_transfer(transfer_id, Some("treasury.near"), None)`. `treasury.near` is not a trusted relayer.
2. MPC signs the payload; `SignTransferEvent` is emitted and picked up by the destination chain.
3. Destination chain finalizes the transfer, emitting a `FinTransfer` event recording `treasury.near` as `fee_recipient`.
4. `treasury.near` calls `claim_fee` with the destination-chain proof.
5. The `#[trusted_relayer]` guard panics immediately — before proof verification — because `treasury.near` is not in the trusted-relayer set and holds neither `Role::DAO` nor `Role::UnrestrictedRelayer`.
6. The DAO cannot rescue the fee: calling `claim_fee` as the DAO passes the guard but fails the `fee_recipient == predecessor_account_id` check in the callback (`"dao.near" != "treasury.near"`).
7. The fee remains locked in `pending_transfers` indefinitely with no release path.

**Reproducible test plan:** Deploy the bridge on a local NEAR sandbox. Register a trusted relayer. Call `sign_transfer` with `fee_recipient = Some("treasury.near")`. Simulate a `FinTransfer` proof from the destination chain. Attempt `claim_fee` from `treasury.near` — assert the call panics. Confirm `get_transfer_message` still returns the pending entry. Attempt `claim_fee` from the DAO account — assert the callback panics with `OnlyFeeRecipientCanClaim`. Confirm the fee is permanently unclaimable.
