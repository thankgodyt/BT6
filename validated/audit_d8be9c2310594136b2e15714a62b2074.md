### Title
Unconditional `validatePerasCert` Stub Accepts Any Inbound Certificate, Enabling Unauthenticated Chain-Weight Boost — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `BlockSupportsPeras` degenerate instance's `validatePerasCert` unconditionally returns `Right` for every inbound certificate. This stub is wired directly into the production NodeToNode Peras cert diffusion inbound handler (`makePerasCertPoolWriterFromChainDB`), which is registered as `perasCertDiffusionProtocol` in both `initiator` and `initiatorAndResponder` without any feature-flag gate. An unprivileged peer can send a syntactically valid `PerasCert blk` CBOR message (containing only a round number and a boosted block point — no signature field exists in the stub type at all) and have it accepted, stored in the `PerasCertDB`, and used to trigger `chainSelectionForBlock` for an adversarially chosen block on a competing fork.

---

### Finding Description

**Root cause — stub validation:** [1](#0-0) 

The `validatePerasCert` implementation in the universal `BlockSupportsPeras` instance (the only instance that exists) performs zero cryptographic or semantic checks and always returns `Right`. The stub `PerasCert blk` type itself has no signature field: [2](#0-1) 

Note: `V1.PerasCert` (with `pcSignature :: AggregateVoteSignature PerasBLSCrypto`) is a standalone type in `Peras/Cert/V1.hs` that is **not** connected to the `BlockSupportsPeras` type class at all — the stub type is what flows through the entire diffusion/chain-selection pipeline. [3](#0-2) 

**Production inbound path — no gate:**

`makePerasCertPoolWriterFromChainDB` passes the stub directly as the `validateCert` argument to `processCerts`: [4](#0-3) 

`processCerts` calls `validateCert` on every inbound cert; if all return `Right` (which the stub guarantees), every cert is timestamped and forwarded to `ChainDB.addPerasCertAsync`: [5](#0-4) 

**NodeToNode wiring — unconditional:**

`hPerasCertDiffusionClient` is wired directly to `makePerasCertPoolWriterFromChainDB` with no feature-flag guard: [6](#0-5) 

`perasCertDiffusionProtocol` is unconditionally included in both `initiator` and `initiatorAndResponder` bundles. The comment at line 1187 explicitly acknowledges that no version-conditional gating is currently applied: [7](#0-6) 

**Chain selection trigger:**

Once accepted into the `PerasCertDB`, `chainSelSync` triggers `chainSelectionForBlock` for the boosted block if it is present in the `VolatileDB` and not already on the current chain: [8](#0-7) 

The boost applied is `perasWeight params = PerasWeight 15` — a fixed additive weight that can tip chain selection toward the adversarially boosted fork.

---

### Impact Explanation

An unprivileged peer that negotiates `NodeToNodeV_16` can:

1. Observe (or guess) a block hash present in the target node's `VolatileDB` on a competing fork.
2. Send a `PerasCert blk` CBOR message with that block as `pcCertBoostedBlock` and any `pcCertRound` not already in the `PerasCertDB`.
3. The cert bypasses all validation (stub always returns `Right`).
4. The cert is stored and `chainSelectionForBlock` is triggered for the adversarial block.
5. The adversarial block receives a `+15` weight boost, potentially making the competing fork preferred over the honest chain.

This violates the invariant that only certificates with a valid BLS aggregate signature over the correct election identifier and boosted block hash must be accepted. The impact is an honest node switching to an adversarially chosen chain — a **High** chain-selection safety violation.

---

### Likelihood Explanation

- The Peras cert diffusion protocol is wired into the production NodeToNode handler bundle without any feature-flag gate.
- The attack requires only a valid peer connection negotiating `NodeToNodeV_16` and knowledge of a block hash in the target's `VolatileDB` (obtainable via ChainSync/BlockFetch observation).
- No stake, keys, or privileged access are required.
- The attack is locally reproducible with `io-sim` using the existing `makePerasCertPoolWriterFromChainDB` + `chainSelSync` infrastructure.

The primary mitigating factor is that `llrnNodeToNodeVersions` uses `limitToLatestReleasedVersion`, which may exclude `NodeToNodeV_16` from active negotiation if it has not yet been formally released. However, the stub is in the production code path with no structural barrier preventing activation.

---

### Recommendation

1. **Immediate:** Replace the stub `validatePerasCert` with a real BLS aggregate signature verification against the election identifier and boosted block hash before this code is activated in any released node version.
2. **Structural guard:** Gate the `perasCertDiffusionProtocol` handler behind a `CardanoFeatureFlag` or a `NodeToNodeVersion` check so that the stub cannot be reached until real validation is in place.
3. **Tracking:** The existing issue https://github.com/tweag/cardano-peras/issues/120 covers this; it should be treated as a security-critical blocker for any release that includes `NodeToNodeV_16`.

---

### Proof of Concept

An `io-sim` scenario:

1. Construct a two-node setup where node A has a current chain `C1` and a competing fork block `B_adv` in its `VolatileDB` (weight of `B_adv`'s chain < weight of `C1`).
2. Have a simulated peer send a `PerasCert blk { pcCertRound = r, pcCertBoostedBlock = blockPoint B_adv }` via the `objectDiffusionInbound` channel.
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → `Right` (stub).
4. `ChainDB.addPerasCertAsync` enqueues `ChainSelAddPerasCert`.
5. `chainSelSync` finds `B_adv` in the `VolatileDB`, calls `chainSelectionForBlock`.
6. Assert that node A's selected chain has switched to the fork containing `B_adv` — demonstrating that an unauthenticated certificate caused a chain switch.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
