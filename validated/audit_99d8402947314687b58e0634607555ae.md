### Title
Peras Quorum Check Compares Absolute Vote Stake Against Relative Threshold Without Normalization - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

`stakeAboveThreshold` in `SupportsPeras.hs` directly compares `PerasVoteStake` (an absolute ledger stake value) against `perasQuorumStakeThreshold` (a relative/normalized `Rational` fraction) without performing any normalization. This is an exact structural analog to the Caviar M-10 bug: one quantity is computed or compared in the wrong unit domain (absolute vs. relative), making the threshold check systematically incorrect. The code itself documents this inconsistency with explicit `NOTE` and `TODO` comments that have not been resolved.

### Finding Description

The `PerasVoteStake` type is defined as a `Rational` representing a voter's stake, but the accompanying `NOTE` at lines 136–143 explicitly states:

> "At the moment there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee (given that the quorum is expressed as a relative value of the voting committee total stake)." [1](#0-0) 

The `stakeAboveThreshold` function then compares this value directly against `perasQuorumStakeThreshold` (a relative `Rational`, e.g. `0.75` for 75%) with no normalization step:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
``` [2](#0-1) 

The function's own `TODO` comment acknowledges the problem:

> "this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [3](#0-2) 

The `PerasVoteStakeDistr` that feeds stake values into `validatePerasVote` is populated from the ledger's absolute stake distribution. The `validatePerasVote` implementation simply looks up the raw ledger stake and attaches it to the vote without normalization:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
``` [4](#0-3) 

This stake is then summed and compared against the relative quorum threshold in `votesReachQuorum`: [5](#0-4) 

The same flawed comparison is used in the `PerasVoteDB` model's `addVote` logic: [6](#0-5) 

The production vote ingestion path in `makePerasVotePoolWriterFromChainDB` calls `validatePerasVote mkPerasParams sd vote` where `sd` is the raw ledger `PerasVoteStakeDistr`, confirming the absolute-vs-relative mismatch is present in the live code path: [7](#0-6) 

### Impact Explanation

If `PerasVoteStake` carries an absolute ledger stake value (e.g., lovelace, which can be in the millions or billions) and `perasQuorumStakeThreshold` is a relative value such as `0.75`, then the comparison `1_000_000 >= 0.75` is trivially `True`. A single vote from any eligible voter — regardless of their actual fractional share of total stake — would immediately satisfy the quorum check. This causes a fraudulent `ValidatedPerasCert` to be forged and inserted into the `PerasCertDB`. The certificate boosts the weight of the voted-for block via `vpcCertBoost`: [8](#0-7) 

Chain selection then uses `wsvTotalWeight` — which adds `wsvBlockNo` and `wsvWeightBoost` — to prefer the boosted chain over the canonical one: [9](#0-8) 

An adversarial peer can therefore cause an honest node to switch to a non-canonical chain by sending a single crafted vote for a block on the adversarial fork, triggering a spurious certificate and a chain-selection fork switch. This is a **High** impact chain-selection bug.

### Likelihood Explanation

Peras is currently disabled by default (the CHANGELOG notes "if Peras is disabled (which is the default), there is no observable difference"), which limits immediate exposure. However, the bug is present in production code and is activated the moment Peras is enabled. The attacker-controlled entry path — sending a `PerasVote` via the ObjectDiffusion mini-protocol — requires no special privileges beyond being a connected peer. The inconsistency is explicitly documented in the source code as unresolved, indicating it has not been fixed. Likelihood is **Medium** given the current default-disabled state of Peras.

### Recommendation

1. **Normalize `PerasVoteStake` before comparison.** Before calling `stakeAboveThreshold`, divide each voter's absolute ledger stake by the total stake of the committee to obtain a relative value in `[0, 1]`.
2. **Enforce units at the type level.** Introduce distinct newtypes for absolute stake (`AbsolutePerasVoteStake`) and relative stake (`RelativePerasVoteStake`) so the compiler rejects unit-mismatched comparisons.
3. **Resolve the open NOTE/TODO.** The researchers and engineers must reach consensus on the normalization formula and encode it in `validatePerasVote` or in a dedicated normalization step before `stakeAboveThreshold` is called.
4. **Add a property test** asserting that `stakeAboveThreshold` returns `False` when a single voter with less than quorum-fraction of total stake casts a vote.

### Proof of Concept

Assume:
- Total committee stake = 10,000,000 lovelace
- `perasQuorumStakeThreshold` = `3 % 4` (75%)
- Adversarial voter stake = 100,000 lovelace (1% of total — far below quorum)

Under the current code:
```
stake = 100000          -- absolute lovelace, from PerasVoteStakeDistr
quorumThreshold = 0.75  -- relative Rational from PerasParams
safetyMargin = 0.01

stakeAboveThreshold: 100000 >= 0.75 + 0.01  →  True  ✗
```

A single vote from a 1%-stake adversarial peer satisfies the quorum check, forges a `ValidatedPerasCert`, and triggers a chain-selection fork switch to the adversarial chain. The correct check after normalization would be:
```
normalizedStake = 100000 / 10000000 = 0.01
0.01 >= 0.76  →  False  ✓
```
