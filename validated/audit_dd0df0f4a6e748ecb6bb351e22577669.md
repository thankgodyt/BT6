### Title
Missing Ownership Check in `withdraw_rbf` Allows Any Caller to Redirect Another User's BTC Withdrawal - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary
`withdraw_rbf` is a publicly callable function that accepts an arbitrary `original_btc_pending_verify_id` without verifying that the pending withdrawal belongs to the caller. Any NEAR account can invoke it against a victim's pending withdrawal, supply attacker-controlled `output` destinations, and cause the MPC to sign an RBF transaction that redirects the victim's BTC to the attacker.

### Finding Description

`withdraw_rbf` in `bridge.rs` reads:

```rust
#[pause(except(roles(Role::DAO)))]
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,
    output: Vec<TxOut>,
    chain_specific_data: Option<ChainSpecificData>,
) {
    let account_id = env::predecessor_account_id();   // ← caller, not owner
    self.require_pending_sign_capacity(&account_id);  // ← checked against caller

    self.withdraw_rbf_chain_specific(
        account_id,                          // ← caller's id forwarded
        original_btc_pending_verify_id,      // ← no ownership assertion
        output,
        chain_specific_data,
    );
}
``` [1](#0-0) 

There is no `require!(pending_info.account_id == env::predecessor_account_id(), ...)` guard. The function uses the **caller's** `AccountId` for the capacity check and forwards it to the chain-specific builder, while `original_btc_pending_verify_id` can reference any user's pending withdrawal.

Contrast this with the privileged `cancel_withdraw`, which explicitly resolves the **owner** from the stored pending info before proceeding:

```rust
let user_account_id = self
    .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
    .account_id
    .clone();
self.require_pending_sign_capacity(&user_account_id);
``` [2](#0-1) 

`withdraw_rbf` performs no equivalent lookup. The `BTCPendingInfo` struct stores the true owner in `account_id`: [3](#0-2) 

Because `withdraw_rbf_chain_specific` receives the **caller's** `AccountId` (not the stored owner's), the resulting RBF `BTCPendingInfo` is associated with the attacker, and the attacker-supplied `output` vector — which specifies the BTC destination addresses and amounts — is used to construct the replacement transaction that the MPC will sign.

### Impact Explanation

An attacker who observes a victim's `original_btc_pending_verify_id` (emitted as `GenerateBtcPendingInfo` event on-chain) can:

1. Call `withdraw_rbf(victim_pending_id, [attacker_output], ...)`.
2. The bridge builds an RBF PSBT spending the same UTXOs as the victim's original withdrawal but paying to the attacker's Bitcoin address.
3. The MPC signs the replacement transaction.
4. The attacker broadcasts it; it confirms and replaces the victim's transaction.
5. The victim's BTC is permanently redirected to the attacker.

This is a **Critical** impact: direct theft of user BTC funds held in bridge-controlled UTXOs.

### Likelihood Explanation

- `withdraw_rbf` is a public, permissionless entry point — no role or whitelist restriction.
- `GenerateBtcPendingInfo` events are emitted on-chain and trivially observable by any NEAR account.
- The only runtime guard (`require_pending_sign_capacity`) is checked against the **attacker's** account, which the attacker controls.
- No additional preconditions (deposit, timelock, proof) are required.

Likelihood is **High** for any withdrawal that reaches the `PendingVerify` stage.

### Recommendation

Add an ownership assertion at the top of `withdraw_rbf`, mirroring the pattern used in `cancel_withdraw`:

```rust
pub fn withdraw_rbf(...) {
    let account_id = env::predecessor_account_id();
    let owner = self
        .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
        .account_id
        .clone();
    require!(account_id == owner, "Only the withdrawal owner can RBF");
    self.require_pending_sign_capacity(&account_id);
    self.withdraw_rbf_chain_specific(account_id, original_btc_pending_verify_id, output, chain_specific_data);
}
```

### Proof of Concept

1. Alice calls `ft_transfer_call` → `ft_on_transfer` → `create_btc_pending_info`. A `GenerateBtcPendingInfo` event is emitted with `btc_pending_id = X`.
2. The MPC signs Alice's withdrawal; `sign_btc_transaction_callback` moves the entry to `PendingVerify` stage and emits `SignedBtcTransaction`.
3. Bob (attacker) observes `X` from on-chain events.
4. Bob calls `withdraw_rbf(X, [TxOut { value: ..., script_pubkey: bob_address }], None)`.
   - `env::predecessor_account_id()` = Bob.
   - `require_pending_sign_capacity(&Bob)` passes (Bob has capacity).
   - `withdraw_rbf_chain_specific(Bob, X, [bob_output], None)` builds an RBF PSBT spending Alice's UTXOs, paying Bob.
5. MPC signs the RBF transaction; Bob broadcasts it.
6. Alice's BTC is permanently sent to Bob. Alice's nBTC was already transferred to the bridge during `ft_on_transfer` and will eventually be burned, leaving Alice with nothing. [1](#0-0) [4](#0-3) [5](#0-4)
