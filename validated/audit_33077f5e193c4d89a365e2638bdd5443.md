Audit Report

## Title
Unchecked u128 Arithmetic Overflow in `denormalize_amount`/`normalize_amount` Enables Permanent Freezing of Bridged Funds via Malicious Token Registration - (`near/omni-bridge/src/lib.rs`)

## Summary

`denormalize_amount` and `normalize_amount` perform unchecked `u128` arithmetic that panics when `origin_decimals - decimals ≥ 39`, because `10_u128.pow(39)` exceeds `u128::MAX ≈ 3.4 × 10^38`. Because `log_metadata_callback` never validates `metadata.decimals`, a permissionless attacker can register a NEAR token with `decimals = 57`, causing every subsequent cross-chain transfer for that token to panic and permanently freeze user funds with no recovery path.

## Finding Description

**Root cause — unchecked arithmetic:**

`denormalize_amount` and `normalize_amount` in `near/omni-bridge/src/lib.rs` (L2776–2787) compute `10_u128.pow(diff_decimals)` with no overflow guard. No `checked_mul`, `checked_pow`, or `saturating_mul` exists anywhere in the file. With `decimals = 18` (the EVM cap applied by `_normalizeDecimals`) and `origin_decimals = 57`, `diff_decimals = 39`, and `10_u128.pow(39)` overflows, causing a NEAR runtime panic.

**Missing validation in `log_metadata_callback`:**

`log_metadata_callback` (L331–347) only checks that `metadata.name` and `metadata.symbol` are non-empty. It accepts any `u8` value (0–255) for `metadata.decimals` and passes it directly into the MPC-signed `MetadataPayload`. There is no upper-bound check.

**Permissionless registration path:**

`evm/SECURITY.md` explicitly states: *"logMetadata and deployToken are permissionless: Anyone can call logMetadata for any ERC20, and anyone can submit a valid MPC signature to deployToken."* The NEAR `log_metadata` function (L316–327) is similarly open to any caller.

**EVM preserves raw `originDecimals`:**

`OmniBridge.sol` (L159, L181–188) applies `_normalizeDecimals` to cap the EVM token's own decimal field at 18, but emits the raw `metadata.decimals` value (e.g., 57) as `originDecimals` in the `DeployToken` event. `bind_token_callback` (L1262–1267) then calls `add_token` with both values directly, storing `Decimals { decimals: 18, origin_decimals: 57 }` with no bounds check.

**Exploit flow:**

1. Deploy NEAR NEP-141 token `bad.near` with `ft_metadata()` returning `decimals: 57`.
2. Call `log_metadata({ token_id: "bad.near" })` — MPC signs `MetadataPayload { decimals: 57 }` because only `name`/`symbol` are validated.
3. Call `OmniBridge.deployToken(signature, { token: "bad.near", decimals: 57, ... })` on EVM — deploys `BridgeToken` with `decimals=18`, emits `DeployToken(..., decimals=18, originDecimals=57)`.
4. Call `bind_token` on NEAR with the EVM proof — stores `Decimals { decimals: 18, origin_decimals: 57 }`.
5. Any user bridges this token EVM→NEAR: tokens are burned on EVM; `fin_transfer_callback` calls `denormalize_amount(amount, Decimals { decimals: 18, origin_decimals: 57 })` → `10_u128.pow(39)` overflows → NEAR transaction panics → transfer permanently unfinalizable → funds lost.
6. Any user bridges NEAR→EVM: `sign_transfer` calls `normalize_amount` → same overflow → MPC signature never produced → NEAR tokens locked forever.

## Impact Explanation

This is a **critical** impact matching two allowed categories:

- **Permanent freezing of bridged funds**: EVM tokens are burned before the NEAR callback executes. Because the callback always panics for this token, there is no recovery path — funds are permanently lost.
- **Decimal/normalization abuse that changes user or protocol balances**: The stored `Decimals` pair causes every arithmetic operation on this token to panic, making the entire token bridge path permanently broken for all users.

## Likelihood Explanation

The entire attack path requires no privileged role, no leaked key, and no off-chain collusion. All four steps (deploy NEAR token, call `log_metadata`, call `deployToken` on EVM, call `bind_token` on NEAR) are permissionless public contract calls, explicitly confirmed by `evm/SECURITY.md`. The attacker needs only to deploy a standard NEP-141 token reporting an extreme decimal value. The attack is repeatable and affects all subsequent users of the poisoned token — not just the attacker.

## Recommendation

**Short term:**
- In `log_metadata_callback`, add: `require!(metadata.decimals <= 36, BridgeError::InvalidMetadata.as_ref())` (or a tighter bound consistent with the normalized cap of 18, ensuring `diff_decimals` can never reach 39).
- Add the same guard in `bind_token_callback` before calling `add_token`, validating that `origin_decimals - decimals < 39`.

**Long term:**
- Replace unchecked arithmetic in `denormalize_amount` and `normalize_amount` with `checked_mul` / `checked_pow`, returning an explicit error instead of panicking, so a malformed registration cannot permanently brick a transfer path.

## Proof of Concept

```
1. Deploy NEAR token bad.near: ft_metadata() returns { decimals: 57, name: "Bad", symbol: "BAD" }
2. Call omni_bridge.log_metadata({ token_id: "bad.near" })
   → log_metadata_callback: name/symbol checks pass, decimals=57 accepted
   → MPC signs MetadataPayload { decimals: 57 }
3. Call OmniBridge.deployToken(mpcSig, { token: "bad.near", decimals: 57, name: "Bad", symbol: "BAD" })
   → _normalizeDecimals(57) = 18
   → emit DeployToken(proxy, "bad.near", "Bad", "BAD", 18, 57)
4. Call omni_bridge.bind_token(evmProof)
   → bind_token_callback: add_token stores Decimals { decimals: 18, origin_decimals: 57 }
5. User calls OmniBridge.initTransfer(amount, ...) for bad.near bridge token
   → EVM tokens burned
6. Relayer submits proof to omni_bridge.fin_transfer
   → fin_transfer_callback: denormalize_amount(amount, Decimals{18,57})
   → diff_decimals = 39
   → 10_u128.pow(39) overflows u128::MAX
   → NEAR runtime panics
   → Transfer permanently unfinalizable, user funds lost
```

A local unit test in `near/omni-bridge/src/lib.rs` can reproduce step 6 directly:
```rust
#[test]
#[should_panic]
fn test_overflow_denormalize() {
    let decimals = Decimals { decimals: 18, origin_decimals: 57 };
    OmniBridge::denormalize_amount(1_000_000_000_000_000_000u128, decimals);
}
```
This test will panic in debug and release builds, confirming the overflow.
