### Title
Premature Token Minting in `safe_mint` Causes Irrecoverable Supply Inflation When Recipient Account Is Unregistered - (File: contracts/nbtc/src/lib.rs)

### Summary
The `safe_mint` function in the nBTC token contract unconditionally mints tokens to the bridge account (`bridge_id`) before checking whether the intended recipient (`account_id`) is registered. If the recipient is unregistered, the function returns early with `U128(0)` without reverting the mint, permanently stranding the freshly-minted tokens inside the bridge account and inflating total supply without any corresponding user delivery.

### Finding Description
In `safe_mint` (lines 101–124 of `contracts/nbtc/src/lib.rs`), the two sequential state-modifying operations are:

1. **Unconditional mint to bridge** (line 112):
   ```rust
   self.token.internal_deposit(&self.bridge_id, amount.into());
   ```
   This increases `bridge_id`'s balance and the global total supply by `amount`.

2. **Registration guard with silent early return** (lines 114–116):
   ```rust
   if self.token.accounts.get(&account_id).is_none() {
       return PromiseOrValue::Value(U128(0));
   }
   ```
   If `account_id` is not registered, the function exits immediately. No burn, no withdrawal, no revert of the deposit performed in step 1. [1](#0-0) 

The tokens minted to `bridge_id` in step 1 are never reclaimed. The total supply is permanently inflated by `amount`, while the user receives zero nBTC. Because `safe_mint` does not panic (it returns `U128(0)`), the bridge's upstream callback will observe a non-error result and is likely to mark the deposit UTXO as finalized, locking the user's BTC on the Bitcoin side with no recourse.

The `mint` function (lines 126–148) avoids this problem by calling `mint_inner`, which auto-registers the account before depositing. `safe_mint` was introduced specifically to handle the unregistered-account case, but the registration check is placed *after* the irreversible mint, inverting the correct order. [2](#0-1) 

### Impact Explanation
**Medium.** The minted tokens accumulate in `bridge_id`'s balance, inflating total supply beyond what is backed by delivered BTC. The user's deposited BTC is locked in the bridge with no nBTC delivered and no automatic refund triggered. Recovering the stranded tokens requires privileged operator intervention (manual burn from `bridge_id`). This matches the allowed impact: *"Harmful smart-contract behavior without direct funds theft, including permanent burning below backed supply, broken callback rollback, or stuck bridge state requiring operator intervention."*

### Likelihood Explanation
**Low–Medium.** Any user who deposits BTC to a bridge address derived from a NEAR account that has never called `storage_deposit` on the nBTC contract will trigger this path. New users who generate a deposit address before registering their NEAR account with the token contract are a realistic population. The bridge does not enforce pre-registration before accepting a deposit.

### Recommendation
Move the registration check **before** the `internal_deposit` call. If the account is unregistered, either panic (forcing the bridge to handle the failure and trigger a refund) or auto-register the account (matching the behavior of `mint_inner`):

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "...");

    // Guard BEFORE minting
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));
    }

    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ... transfer logic
}
```

### Proof of Concept
1. User generates a deposit address for NEAR account `alice.near` but never calls `storage_deposit` on the nBTC contract.
2. User sends BTC to the deposit address; a relayer submits the proof to the bridge.
3. Bridge verifies the proof and calls `safe_mint("alice.near", amount, None)` on the nBTC contract.
4. `internal_deposit(&self.bridge_id, amount)` executes — `bridge_id`'s balance and total supply increase by `amount`.
5. `self.token.accounts.get(&"alice.near")` returns `None`; function returns `PromiseOrValue::Value(U128(0))`.
6. No burn or revert occurs. `amount` tokens are permanently stranded in `bridge_id`.
7. The bridge callback receives a non-panic result, marks the deposit UTXO as verified, and the user's BTC is locked with no nBTC delivered and no refund path. [3](#0-2)

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }
