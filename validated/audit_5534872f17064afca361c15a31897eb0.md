Audit Report

## Title
Decimal Normalization Dust Permanently Locked/Burned When `fee = 0` — (`near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer` locks or burns the full user-supplied `amount` before `sign_transfer` applies `normalize_amount`. When a token has fewer decimals on the destination chain than on NEAR, any sub-unit remainder is truncated to zero by floor division. If `fee = 0` and the amount is smaller than the normalization factor, the tokens are permanently locked in escrow (native tokens) or burned (deployed tokens) with no user-callable recovery path.

## Finding Description
The only pre-lock validation in `init_transfer` is: [1](#0-0) 

This only requires `fee < amount`; it does not verify that `normalize_amount(amount − fee) > 0`.

`init_transfer_internal` then immediately locks or burns the full `transfer_message.amount`: [2](#0-1) 

Later, when a trusted relayer calls `sign_transfer`, the normalization check fires: [3](#0-2) 

`normalize_amount` uses floor division: [4](#0-3) 

If `amount − fee < normalization_factor`, `normalize_amount` returns 0 and `sign_transfer` panics with `InvalidAmountToTransfer`. The transfer message remains in storage but the tokens are already gone. The function name `remove_transfer_message_without_refund` (used in the failure paths of `init_transfer_internal`) confirms no token refund occurs. No user-callable cancel or refund function exists in the contract.

## Impact Explanation
This is a concrete, permanent loss of user funds matching two allowed Critical impact classes: **permanent freezing of bridged funds** (native tokens locked in escrow forever) and **decimal/normalization abuse that changes user balances** (deployed tokens burned with no recovery). The transfer message persists in storage in a terminal state — no relayer can complete it (normalized amount = 0) and no user can cancel it.

## Likelihood Explanation
Any unprivileged user calling `ft_transfer_call` on a token registered with `origin_decimals > decimals` (e.g., NEAR 24 → EVM 18, factor = 10⁶; or NEAR 24 → EVM 6, factor = 10¹⁸) with an `amount` that is not a multiple of the normalization factor and `fee = 0` triggers the bug. No special role or privilege is required. The condition is realistic: NEAR-native tokens bridged to EVM chains commonly use this decimal configuration.

## Recommendation
Add a pre-lock normalization check in `init_transfer` (or `init_transfer_internal`) mirroring the guard already present in `sign_transfer`, applied **before** funds are locked or burned:

```rust
let token_address = self.get_token_address(destination_chain, token_id.clone())
    .near_expect(BridgeError::TokenNotFound);
let decimals = self.token_decimals.get(&token_address)
    .near_expect(BridgeError::TokenDecimalsNotFound);
require!(
    Self::normalize_amount(
        transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
        decimals,
    ) > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

When `ft_on_transfer` receives this panic, the NEP-141 standard requires the token contract to refund the full amount to the sender, preventing any loss.

## Proof of Concept
1. Register a token with `origin_decimals = 24`, `decimals = 18` (normalization factor = 10⁶).
2. User calls `ft_transfer_call` on the token contract, transferring `amount = 500_000` (< 10⁶) with `fee = 0` and a valid EVM recipient.
3. `init_transfer` passes the `fee < amount` check (0 < 500_000). `init_transfer_internal` locks 500_000 units in the bridge escrow.
4. A trusted relayer calls `sign_transfer`. `normalize_amount(500_000, {24, 18}) = 500_000 / 1_000_000 = 0`. The `require!(amount_to_transfer > 0)` guard panics with `InvalidAmountToTransfer`.
5. The transfer message remains in storage; the 500_000 units remain locked forever. The user has no recourse — no cancel, no refund, no unlock function exists.

    /// Uses floor division — any sub-unit remainder ("dust") is truncated and not transferred
    /// to the destination chain. When fee > 0, dust is absorbed into the fee via `claim_fee`.
    /// When fee = 0, dust stays locked/burned. See SECURITY.md for details.
    fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
        let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
        amount / (10_u128.pow(diff_decimals))
    }
