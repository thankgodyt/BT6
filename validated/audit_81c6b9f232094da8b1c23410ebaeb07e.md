Audit Report

## Title
Pause Bypass via `init_transfer_resume` and `fin_transfer_callback` Lacking Pause Checks - (File: `near/omni-bridge/src/lib.rs`)

## Summary

The NEAR `omni-bridge` contract enforces pause checks on `ft_on_transfer` and `fin_transfer` but omits them from their async continuations `init_transfer_resume` and `fin_transfer_callback`. Because NEAR callbacks and yield-resume callbacks are independent function calls, a pause set between the entry-point call and the callback execution is silently bypassed. For `init_transfer_resume` specifically, yields can remain pending for hours or days, and any actor can trigger the resume by calling the public `storage_deposit` function, allowing token burns/locks and cross-chain event emission during a pause.

## Finding Description

`ft_on_transfer` is decorated with `#[pause(except(roles(Role::DAO, Role::UnrestrictedDeposit)))]`, enforcing the pause at the entry point. [1](#0-0) 

When the signer lacks sufficient storage, `ft_on_transfer` → `init_transfer` creates a NEAR yield promise targeting `init_transfer_resume` and suspends execution: [2](#0-1) 

`init_transfer_resume` is marked only `#[private]` — no pause check — and unconditionally calls `init_transfer_internal`, which burns/locks tokens and emits `InitTransferEvent`: [3](#0-2) 

The yield is triggered by the public `storage_deposit` function, which has no pause check and calls `resume_promise` → `env::promise_yield_resume`: [4](#0-3) [5](#0-4) 

The same pattern applies to `fin_transfer`. The entry point has `#[pause(except(roles(Role::DAO)))]`: [6](#0-5) 

But `fin_transfer_callback`, which mints/transfers tokens to the recipient, has no pause check: [7](#0-6) 

`init_transfer_internal` burns/locks tokens and emits the `InitTransferEvent` that relayers act on: [8](#0-7) 

## Impact Explanation

**`init_transfer_resume` bypass (primary impact):** This is a concrete pause bypass enabling unauthorized cross-chain fund movement. When the bridge is paused (e.g., due to a security incident), any pending yield can be resumed by any actor depositing storage for the virtual message-storage account ID. `init_transfer_resume` then burns/locks the user's NEAR-side tokens and emits `InitTransferEvent`. A relayer can finalize the transfer on the destination chain, completing a cross-chain transfer despite the NEAR-side pause. This matches the allowed critical impact: *pause bypass that lets an attacker execute bridge actions* and *stealing or unauthorized movement of bridged funds*.

**`fin_transfer_callback` bypass (secondary impact):** A relayer submits `fin_transfer` just before a pause. The proof verification and callback execute after the pause, minting tokens on NEAR despite the bridge being paused. If the pause was triggered due to a compromised prover or discovered exploit, fraudulent proofs submitted just before the pause can still be finalized.

## Likelihood Explanation

**`init_transfer_resume`:** Medium-high. NEAR yield promises remain pending until explicitly resumed or timed out (many blocks). Any actor — including the original user — can deposit storage for the virtual account ID at any time. The attacker does not need to race against the pause; they simply wait for the pause to be set and then deposit storage. The `storage_deposit` function is public, payable, and has no pause check.

**`fin_transfer_callback`:** Low-medium. The window between `fin_transfer` and its callback is only a few NEAR blocks (~1–2 seconds), requiring the admin to pause in that exact window. This is a narrow race condition.

## Recommendation

Add a pause check inside both callback functions:

```rust
// In init_transfer_resume:
#[private]
pub fn init_transfer_resume(...) -> U128 {
    self.assert_not_paused(Role::DAO, Role::UnrestrictedDeposit); // match ft_on_transfer roles
    ...
}

// In fin_transfer_callback:
#[private]
#[payable]
pub fn fin_transfer_callback(...) -> PromiseOrValue<Nonce> {
    self.assert_not_paused(Role::DAO); // match fin_transfer roles
    ...
}
```

Alternatively, apply the `#[pause]` macro with the same role exceptions as the corresponding entry point to both callback functions. For `init_transfer_resume`, also consider adding a pause check to `storage_deposit` or `resume_promise` to prevent the yield from being triggered at all when paused.

## Proof of Concept

**`init_transfer_resume` scenario (demonstrable on local sandbox):**

1. Alice calls `ft_transfer_call` → `ft_on_transfer` → `init_transfer` on the NEAR bridge with insufficient storage. A yield is created and stored in `init_transfer_promises` (as shown in the existing integration test `test_init_transfer_with_external_id` which exercises this exact yield/resume path). [9](#0-8) 

2. Admin pauses the bridge via `acl_grant_role(Role::PauseManager)` + pause call.

3. Any actor (Alice or an attacker) calls `storage_deposit` on the bridge contract for the virtual `message_storage_account_id`. This is a public function with no pause check. [4](#0-3) 

4. `storage_deposit` calls `resume_promise` → `env::promise_yield_resume`, which schedules `init_transfer_resume` as a callback. [5](#0-4) 

5. `init_transfer_resume` executes — no pause check — and calls `init_transfer_internal`, burning/locking Alice's tokens and emitting `InitTransferEvent`. [3](#0-2) 

6. A relayer picks up the `InitTransferEvent` and finalizes the transfer on the destination chain, completing the cross-chain transfer despite the NEAR-side pause.

The existing `zcash_stale_transfer_poc.rs` test file demonstrates the yield/resume mechanics on a local sandbox and can be extended to add a pause step between yield creation and the `storage_deposit` resume trigger to confirm the bypass. [10](#0-9)
