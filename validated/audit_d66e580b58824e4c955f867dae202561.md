### Title
Hardcoded Placeholder `PerasParams` Used in Production Peras Certificate Validation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs`)

---

### Summary

Both production Peras certificate pool writers — `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB` — validate inbound peer-supplied certificates using the hardcoded placeholder `mkPerasParams` instead of the actual node-configured `PerasCfg`. This is the direct analog of the FiinuCoin bug: a placeholder value that was meant to be replaced before deployment was left in place, causing critical logic to operate on wrong parameters.

---

### Finding Description

In `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs`, both production pool writers call:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [1](#0-0) [2](#0-1) 

`mkPerasParams` is an explicitly provisional constant whose own source comment reads:

> "Many of these parameters are provided with sensible default values for now, waiting for a final decision (in a future stage of the project) on the exact values to use." [3](#0-2) 

The changelog fragment for the patch that replaced the previous `error "yet undefined"` values confirms these were always placeholder values: [4](#0-3) 

The hardcoded values are:
- `perasQuorumStakeThreshold = 3/4`
- `perasQuorumStakeThresholdSafetyMargin = 2/100` (effective threshold: 77%)
- `perasWeight = 15` (chain selection boost per certificate)
- `perasCertMaxRounds = 487`, `perasIgnoranceRounds = 487`, `perasCooldownRounds = 1928` [5](#0-4) 

The `validatePerasCert` typeclass method takes `PerasCfg blk` as its first argument. By passing `mkPerasParams` here, the concrete block type's `PerasCfg blk` is being satisfied by the hardcoded placeholder rather than the actual per-node configuration. The `ValidatedPerasCert` produced by this call carries `vpcCertBoost = perasWeight params`, which is the hardcoded `15`, and is then stored in the `ChainDB` and used directly in chain selection. [6](#0-5) 

The `stakeAboveThreshold` function — which is the quorum gate — reads directly from `PerasParams`: [7](#0-6) 

This function itself carries an additional unresolved TODO noting that `PerasVoteStake` and the quorum threshold may not be in the same units, compounding the misconfiguration risk. [8](#0-7) 

---

### Impact Explanation

**Certificate validation bypass / chain selection manipulation (Critical/High).**

When Peras is enabled on a private testnet or future mainnet deployment, any peer can submit a `PerasCert` via the object diffusion mini-protocol. That certificate is validated against the hardcoded `mkPerasParams` rather than the actual network's configured parameters. Two concrete consequences:

1. **Quorum threshold mismatch**: If the actual network is configured with a quorum threshold higher than the hardcoded 77% (e.g., 80%), a certificate backed by only 78% of stake passes the hardcoded check and is accepted into the `ChainDB`. This constitutes a bypass of the Peras certificate quorum check — an unprivileged peer can cause an honest node to accept a certificate that does not represent genuine network consensus.

2. **Chain selection weight corruption**: The `vpcCertBoost` stored in the accepted `ValidatedPerasCert` is always `PerasWeight 15` regardless of what the actual network configures. The `ChainDB` uses this boost in `WeightedSelectView` to prefer chains. An attacker who can get a certificate accepted (via the quorum bypass above) causes the node to apply the wrong boost weight to chain selection, potentially making the node prefer a non-canonical chain. [6](#0-5) 

---

### Likelihood Explanation

**Medium-to-High** once Peras is enabled. The code path is production-ready infrastructure (`makePerasCertPoolWriterFromChainDB` is explicitly the production writer, as the comment on `makePerasCertPoolWriterFromCertDB` says "mostly meant for tests"). The `TODO` comments confirm the placeholder was never replaced. Any peer connected via the object diffusion mini-protocol can submit certificates. No special privileges, keys, or stake are required to trigger the validation path — only the ability to send a well-formed `PerasCert` message. The Peras protocol is currently disabled by default (`eraPerasRoundLength = NoPerasEnabled`), which limits immediate mainnet exposure, but the vulnerability is latent and will activate the moment Peras is enabled on any network. [9](#0-8) [10](#0-9) 

---

### Recommendation

Replace the hardcoded `mkPerasParams` in both `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB` with the actual node-configured `PerasCfg blk` (or `PerasParams`) threaded through from the `TopLevelConfig` or equivalent configuration record. The `TODO` comments already acknowledge this; the fix is to complete the plumbing before Peras is enabled on any network. Additionally, the `stakeAboveThreshold` unit-mismatch TODO should be resolved at the same time to ensure the quorum check is semantically correct end-to-end.

---

### Proof of Concept

On a private testnet with Peras enabled and a quorum threshold configured at 80%:

1. Connect to a target node as a peer via the object diffusion mini-protocol.
2. Construct a `PerasCert` for a target block, backed by votes representing 78% of total stake (below the real 80% threshold, but above the hardcoded 77%).
3. Submit the certificate to the target node.
4. The node calls `validatePerasCert mkPerasParams cert`, which evaluates `stakeAboveThreshold mkPerasParams (PerasVoteStake 0.78)` → `0.78 >= 0.75 + 0.02 = 0.77` → `True`.
5. The certificate is accepted, timestamped, and added to the `ChainDB` with `vpcCertBoost = PerasWeight 15`.
6. Chain selection now applies a boost of 15 to the block referenced by the certificate, potentially causing the node to prefer a chain that does not have genuine Peras quorum backing. [11](#0-10) [7](#0-6)

  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
