### Title
Peras Quorum Check Compares Absolute Vote Stake Against Relative Threshold Without Normalization — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` in `SupportsPeras.hs` directly compares a `PerasVoteStake` value (sourced from the ledger stake distribution, which is absolute) against `perasQuorumStakeThreshold` (a relative/normalized `Rational` between 0 and 1) without any normalization step. The function's own TODO comment explicitly acknowledges this unit mismatch. When the actual stake distribution plumbing is wired in, an unprivileged peer can send a single vote whose absolute ledger stake (e.g., 1,000,000,000,000 lovelace) trivially exceeds the relative quorum threshold (e.g., 0.75), causing a Peras certificate to be forged from a single vote and bypassing the quorum requirement entirely.

---

**Root cause — unit mismatch in `stakeAboveThreshold`:**

```haskell
-- TODO: this function assumes that the 'PerasVoteStake' and the quorum
-- threshold used in 'PerasParams' are expressed in the same units. That is,
-- both are either absolute or relative (normalized) values. Under the current
-- current implementation of 'PerasParams', this function only makes sense when

stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
``` [2](#0-1) 

The `perasQuorumStakeThreshold` is a relative `Rational` (e.g., `0.75`). The `PerasVoteStake` is sourced directly from the ledger stake distribution — absolute lovelace values (e.g., `1_000_000_000_000`). The comparison `stake >= quorumThreshold + safetyMargin` is therefore `1_000_000_000_000 >= 0.75 + ε`, which is always `True` for any voter with positive stake.

**Exploit path:**

1. An unprivileged peer sends a `PerasVote` message via the Peras vote diffusion mini-protocol (`hPerasVoteDiffusionClient`).
2. `processVotes` calls `validatePerasVote`, which calls `lookupPerasVoteStake` to retrieve the voter's `PerasVoteStake` from `PerasVoteStakeDistr`. [3](#0-2) 

3. The validated vote (carrying the absolute ledger stake) is added to the `PerasVoteDB`.
4. `updateCandidateVoteState` calls `votesReachQuorum`, which calls `stakeAboveThreshold` with the accumulated `PerasVoteStake`. [4](#0-3) 

5. Because absolute stake >> relative threshold, `stakeAboveThreshold` returns `True` on the very first vote.
6. `forgePerasCert` is called, producing a `ValidatedPerasCert` with `vpcCertBoost = perasWeight params`.
7. The certificate is accepted into the `ChainDB`, boosting the chain weight of the attacker's chosen block.
8. `weightedSelectView` / `wsvTotalWeight` now includes the fraudulent boost, causing chain selection to prefer the attacker's chain. [5](#0-4) 

**Current production state:** The production `NodeToNode.hs` wires in `(pure (PerasVoteStakeDistr mempty))` as a placeholder, causing all votes to be rejected (empty map → `lookupPerasVoteStake` returns `Nothing`). The vulnerability activates the moment the actual ledger stake distribution is plumbed in. [6](#0-5) 

---

### Impact Explanation

**Critical — Bypass of Peras certificate/quorum verification.**

When the actual stake distribution is wired in, a single vote from any voter with positive ledger stake (absolute lovelace >> relative threshold 0.75) trivially satisfies `stakeAboveThreshold`, causing `forgePerasCert` to produce a valid `ValidatedPerasCert`. This certificate is accepted by the `ChainDB` and adds `perasWeight` boost to the attacker's chosen block. Chain selection (`preferCandidate` via `wsvTotalWeight`) then prefers the boosted chain over the canonical chain, constituting an unauthorized chain weight manipulation and potential consensus safety failure.

---

### Likelihood Explanation

**Medium.** The vulnerability is not exploitable in the current production deployment because the stake distribution is hardcoded to empty. However, the actual stake distribution plumbing is actively under development (multiple TODO comments reference `cardano-peras` issue #120 and the committee selection context). When that work lands, if the `PerasVoteStakeDistr` is populated with raw ledger lovelace values (the natural representation from the ledger), the unit mismatch immediately becomes exploitable by any peer that can send a Peras vote message. The TODO comment in the source code itself confirms the developers are aware of the gap but have not yet resolved it.

---

### Recommendation

`stakeAboveThreshold` must not be called with unnormalized absolute stake. The fix must be applied at one of two points:

1. **At construction of `PerasVoteStakeDistr`**: normalize each voter's absolute ledger stake by dividing by the total stake of the committee before storing it in the map, so every `PerasVoteStake` is already a relative value in `[0, 1]`.
2. **Inside `stakeAboveThreshold`**: accept the total stake of the distribution as an additional parameter and perform the normalization internally before comparing against the threshold.

The type `PerasVoteStake` should be given a smart constructor that enforces the invariant `0 ≤ unPerasVoteStake ≤ 1`, making it impossible to accidentally pass absolute values.

### Proof of Concept

**Setup:** Wire in a non-empty `PerasVoteStakeDistr` containing a single voter with absolute ledger stake `1_000_000_000_000` (1 ADA in lovelace). Use `mkPerasParams` defaults where `perasQuorumStakeThreshold = 0.75`.

**Trigger:**
```haskell
let stakeDistr = PerasVoteStakeDistr $
      Map.singleton someVoterId (PerasVoteStake 1_000_000_000_000)
    vote = PerasVote { pvVoteRound = 0, pvVoteBlock = someBlock, pvVoteVoterId = someVoterId }
    Right validatedVote = validatePerasVote mkPerasParams stakeDistr vote
    -- validatedVote carries vpvVoteStake = 1_000_000_000_000

-- stakeAboveThreshold check:
-- stake = 1_000_000_000_000
-- quorumThreshold + safetyMargin ≈ 0.75 + ε
-- 1_000_000_000_000 >= 0.75 + ε  →  True  (quorum reached with 1 vote)
```

**Expected (correct) result:** Quorum not reached; certificate not forged.

**Actual result:** `stakeAboveThreshold` returns `True`; `forgePerasCert` is called; a `ValidatedPerasCert` is produced and accepted into the `ChainDB`; the attacker's block receives a weight boost of `perasWeight params`; chain selection may switch to the attacker's chain.
