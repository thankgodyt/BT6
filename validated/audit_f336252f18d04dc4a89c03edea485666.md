### Title
Permissionless Front-Running of `request_refund` Allows Attacker to Block User Refund or Redirect BTC to Attacker-Controlled Address - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
`request_refund` is a permissionless function whose storage key (`utxo_storage_key = {tx_id}@{vout}`) is fully deterministic from public Bitcoin data. When `deposit_msg.refund_address` is `None`, any caller may supply an arbitrary `refund_address`. An attacker who observes a pending `request_refund` call can front-run it with the same `deposit_msg`/`tx_bytes`/`vout`/`proof` but substitute their own BTC address. The first callback to land wins the slot; the victim's callback then panics with "Refund request already exists for this UTXO", permanently blocking their request until DAO/Operator intervenes. If DAO fails to reject the attacker's request within `unsafe_refund_timelock_sec`, `execute_refund` can be called by anyone and the BTC is sent to the attacker's address.

### Finding Description
`request_refund` is open to any NEAR account:

```
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn request_refund(
    &mut self,
    deposit_msg: DepositMsg,
    refund_address: String,   // ← attacker-controlled when deposit_msg.refund_address is None
    tx_bytes: Base64VecU8,
    vout: usize,
    proof: TxInclusionProof,
    gas_fee: Option<U128>,
) -> Promise
``` [1](#0-0) 

The only guard on `refund_address` is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [2](#0-1) 

When `deposit_msg.refund_address` is `None` (the common case for users who did not embed a refund address at deposit time), this guard is skipped entirely and any `refund_address` string is accepted.

The storage key is computed deterministically in `request_refund_callback`:

```rust
let utxo_storage_key = generate_utxo_storage_key(
    tx_id,
    u32::try_from(vout).unwrap_or_else(|_| env::panic_str("vout overflow")),
);
``` [3](#0-2) 

The duplicate check that blocks the victim's callback:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [4](#0-3) 

Once the attacker's request is stored, `execute_refund` is also permissionless (no role restriction at the method level) and uses the stored `refund_address` to build the BTC output:

```rust
let refund_address = refund_request.refund_address.clone();
``` [5](#0-4) 

The only mitigation is `unsafe_refund_timelock_sec`, which gives DAO/Operator a window to call `reject_refund`. But `reject_refund` itself requires DAO/Operator role:

```rust
require!(
    is_privileged || is_already_deposited,
    "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
);
``` [6](#0-5) 

### Impact Explanation
**Medium (DoS) escalating to Critical (theft):**

- **Guaranteed DoS**: The victim's `request_refund` call always fails with "Refund request already exists for this UTXO". The victim also loses their attached storage deposit (explicitly non-refundable per the doc comment). Recovery requires DAO/Operator to call `reject_refund`, after which the victim must re-submit and pay the storage deposit again.
- **Critical escalation**: If DAO/Operator does not reject the attacker's request within `unsafe_refund_timelock_sec`, anyone (including the attacker) can call `execute_refund`. The MPC pipeline then builds and signs a Bitcoin transaction paying the deposit UTXO to the attacker's BTC address. The victim permanently loses their BTC.

This matches: *Medium — attacker-triggered temporary locking of bridged funds* (guaranteed), escalating to *Critical — significant loss or theft of user funds* (conditional on DAO inaction).

### Likelihood Explanation
All inputs required for the attack are public:
- `deposit_msg` is reconstructable from the deposit address (which is public and logged via `Event::LogDepositAddress`)
- `tx_bytes`, `vout`, and the Merkle proof are all public on the Bitcoin blockchain

NEAR block times are ~1 second, making mempool front-running feasible for an attacker monitoring the RPC. The attacker only needs to attach the same storage deposit as the victim. The attack is cheap, repeatable, and requires no privileged access.

### Recommendation
1. **Bind `refund_address` to the caller**: Require that `env::predecessor_account_id()` matches `deposit_msg.recipient_id`, or store the caller's account and only allow them (or DAO) to set the `refund_address` at execution time.
2. **Alternatively, require `deposit_msg.refund_address` to be set**: Reject `request_refund` calls where `deposit_msg.refund_address` is `None`, forcing users to embed their BTC refund address at deposit time (where it is cryptographically bound to the deposit address derivation path).
3. **At minimum**: Check whether a refund request for the UTXO already exists *before* paying for the Light Client cross-contract call, and reject early if the caller is not the original requester.

### Proof of Concept
1. User A deposits BTC using `deposit_msg = { recipient_id: "user_a.near", refund_address: None, ... }`. The deposit is never finalized (e.g., the relayer misses it).
2. User A calls `request_refund(deposit_msg, refund_address="user_a_btc_addr", tx_bytes=<real_tx>, vout=0, proof=<valid_proof>)`.
3. Attacker observes this call in the NEAR mempool and immediately submits `request_refund(deposit_msg, refund_address="attacker_btc_addr", tx_bytes=<same_tx>, vout=0, proof=<same_proof>)` with higher priority.
4. Attacker's Light Client verification callback executes first. `utxo_storage_key = "{tx_id}@0"` is inserted into `refund_requests` with `refund_address="attacker_btc_addr"`.
5. User A's callback executes and panics: `"Refund request already exists for this UTXO"`. User A's storage deposit is lost.
6. If DAO does not call `reject_refund("{tx_id}@0")` within `unsafe_refund_timelock_sec`, the attacker calls `execute_refund("{tx_id}@0", None)`.
7. The bridge MPC pipeline signs a Bitcoin transaction sending the deposit UTXO to `"attacker_btc_addr"`. User A's BTC is stolen.

    #[allow(clippy::too_many_arguments)]
    #[payable]

    pub fn request_refund(

            vout,
