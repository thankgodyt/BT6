Audit Report

## Title
Transfer Permanently Frozen When `normalize_amount(amount - fee) == 0` Due to Missing Pre-validation — (`near/omni-bridge/src/lib.rs`)

## Summary

`init_transfer` accepts outbound transfers without verifying that the net amount after fee deduction survives decimal normalization to the destination chain. When `sign_transfer` is later called, it computes `normalize_amount(amount_without_fee())` and panics if the result is zero. Because the fee can only be increased (never decreased) and no user-accessible cancel or refund path exists, the transfer is permanently deadlocked and the user's locked tokens are irrecoverable.

## Finding Description

**Missing pre-validation in `init_transfer`**

`init_transfer` enforces only one amount constraint: [1](#0-0) 

It does not verify that `normalize_amount(amount - fee, decimals) > 0`. Tokens are immediately locked when `ft_on_transfer` returns `U128(0)`.

**Floor-division normalization** [2](#0-1) 

For a token with `origin_decimals = 18` and `decimals = 6`, `diff_decimals = 12`. Any `amount - fee < 10^12` normalizes to 0.

**`sign_transfer` panics and cannot proceed** [3](#0-2) 

Every call to `sign_transfer` for this transfer reverts. The transfer message stays in `pending_transfers` indefinitely.

**Fee update cannot rescue the transfer**

The fee update path enforces `fee.fee >= current_fee.fee`: [4](#0-3) 

Increasing the fee makes `amount_without_fee()` even smaller, worsening the situation. No user-accessible cancel or refund path for locked tokens exists in the contract.

**`amount_without_fee` implementation** [5](#0-4) 

## Impact Explanation

This constitutes **permanent freezing of bridged funds** — a concrete critical impact under the allowed scope. A user's tokens are locked in the bridge with no mechanism to recover them: `sign_transfer` always reverts, fee can only increase, and no cancel/refund entrypoint exists for the user.

## Likelihood Explanation

Any unprivileged bridge user can trigger this by calling `ft_transfer_call` with an `InitTransferMsg` whose net amount (`amount - fee`) is below the normalization threshold. For tokens with large decimal differences (e.g., 18 → 6), the threshold is `10^12` base units — a realistic transfer size (e.g., 0.000001 of an 18-decimal token). No special privileges or coordination are required.

## Recommendation

Add a normalization check inside `init_transfer_internal` (or at the end of `init_transfer`) before accepting the transfer, mirroring the check already present in `sign_transfer`:

```rust
let normalized = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

This ensures the transfer is rejected at initiation time (with a full token refund via `ft_on_transfer` returning the full amount) rather than silently accepted and permanently frozen.

## Proof of Concept

1. Register a token with `origin_decimals = 18`, `decimals = 6` (diff = 12).
2. Call `ft_transfer_call` with `amount = 999_999_999_999` (i.e., `10^12 - 1`) and `fee = 0`.
3. `init_transfer` accepts the message (`fee < amount` ✓). Tokens are locked.
4. Relayer calls `sign_transfer` for this transfer ID.
5. `normalize_amount(999_999_999_999, {origin: 18, dest: 6}) = 0`.
6. `require!(0 > 0, ...)` panics → transaction reverts.
7. Transfer remains in `pending_transfers`. Tokens remain locked.
8. Attempting to update the fee to a lower value is rejected with `ERR_INVALID_FEE` (confirmed by integration test at `near/omni-tests/src/init_transfer.rs` lines 859–892).
9. Funds are permanently frozen with no recovery path.
