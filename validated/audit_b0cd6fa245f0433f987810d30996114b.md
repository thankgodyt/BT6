### Title
Unprivileged Account Can Submit Refund Request for Any Deposit with Attacker-Controlled BTC Address — (`contracts/satoshi-bridge/src/refund.rs`, `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

The bridge's shared `refund_requests` map is accessible by any unprivileged NEAR account. `request_refund` imposes no ownership check on who may submit a refund for a given deposit UTXO. When a victim's `deposit_msg` omits `refund_address` (the common case), an attacker can supply their own BTC address, wait out the `unsafe_refund_timelock_sec`, and call `execute_refund` to redirect the victim's BTC to themselves — provided the relayer has not yet called `verify_deposit` and the DAO/Operator has not rejected the request.

---

### Finding Description

`request_refund` is a public, pausable-only-by-DAO function:

```rust
pub fn request_refund(
    &mut self,
    deposit_msg: DepositMsg,
    refund_address: String,
    tx_bytes: Base64VecU8,
    vout: usize,
    proof: TxInclusionProof,
    gas_fee: Option<U128>,
) -> Promise {
``` [1](#0-0) 

The only guard on `refund_address` is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [2](#0-1) 

When `deposit_msg.refund_address` is `None` — the default for ordinary deposits — **any caller may supply any BTC address**. There is no check that `env::predecessor_account_id()` matches `deposit_msg.recipient_id`.

In `request_refund_callback`, the contract verifies the output script matches the deposit address derived from `deposit_msg`, but this only proves the UTXO exists on-chain; it does not restrict who may file the refund: [3](#0-2) 

After the request is stored, `execute_refund` is also callable by anyone once the timelock elapses. For attacker-supplied addresses the applicable timelock is `unsafe_refund_timelock_sec`:

```rust
} else {
    // Refund address supplied by caller of `request_refund`: longer
    // timelock to give DAO/Operator time to reject suspicious requests.
    config.unsafe_refund_timelock_sec
}
``` [4](#0-3) 

`load_refund_request_for_execute` blocks execution only if the UTXO was already claimed by `verify_deposit`:

```rust
require!(
    !self.data().verified_deposit_utxo.contains(utxo_storage_key)
        || refund_request.executed,
    "UTXO already verified via deposit, cannot refund"
);
``` [5](#0-4) 

If the relayer has not yet called `verify_deposit`, this check passes and `finalize_refund_with_psbt` inserts the UTXO into `verified_deposit_utxo`, permanently blocking any future `verify_deposit` for the victim: [6](#0-5) 

The shared `refund_requests` map in `ContractData` is the root of the problem — it is a single global namespace over which any account can act on any other account's deposit: [7](#0-6) 

---

### Impact Explanation

**Critical.** A successful attack achieves two simultaneous outcomes:

1. The victim's BTC is sent to the attacker's address via the MPC signing pipeline.
2. The victim's deposit UTXO is permanently marked in `verified_deposit_utxo`, so `verify_deposit` can never mint nBTC for the victim — the victim loses both their BTC and any nBTC they expected.

This constitutes significant, permanent loss of user funds.

---

### Likelihood Explanation

**Medium.** The attack requires a window in which:

- The relayer has not yet called `verify_deposit` (e.g., relayer downtime, congestion, or a slow confirmation count), **and**
- The DAO/Operator does not call `reject_refund` within `unsafe_refund_timelock_sec`.

Both conditions are operationally plausible. The attacker's cost is only the small NEAR storage deposits for `request_refund` and `execute_refund`. All inputs (`deposit_msg`, `tx_bytes`, `vout`, Merkle proof) are publicly observable on the Bitcoin blockchain and in NEAR transaction history.

---

### Recommendation

1. **Bind refund requests to the depositor.** Record `env::predecessor_account_id()` as the `requester` in `RefundRequest` and require that only the original `deposit_msg.recipient_id` (or a privileged role) may submit a refund when `deposit_msg.refund_address` is `None`.
2. **Alternatively, require `deposit_msg.refund_address` to be set** for any permissionless refund path; treat the caller-supplied address path as privileged-only.
3. **Emit an on-chain alert event** immediately when a refund request is filed for a UTXO that has not yet been verified, to give monitoring systems a chance to trigger `verify_deposit` or `reject_refund` before the timelock expires.

---

### Proof of Concept

1. Victim sends 1 BTC to the bridge deposit address derived from `deposit_msg = {recipient_id: "victim.near", refund_address: None}`.
2. The BTC transaction is confirmed on Bitcoin; the relayer has not yet called `verify_deposit` (e.g., relayer is temporarily down).
3. Attacker observes the Bitcoin transaction on-chain, reconstructs `deposit_msg`, and calls:
   ```
   request_refund(
     deposit_msg = {recipient_id: "victim.near", refund_address: None},
     refund_address = "attacker_btc_address",
     tx_bytes = <victim's deposit tx>,
     vout = 0,
     proof = <valid Merkle proof>,
     gas_fee = None
   )
   ```
   with the required NEAR storage deposit attached.
4. `request_refund_callback` verifies the Merkle proof and the output script matches the deposit address — both pass. The request is stored in `refund_requests` with `refund_address = "attacker_btc_address"`.
5. Attacker waits for `unsafe_refund_timelock_sec` to elapse. DAO/Operator does not reject.
6. Attacker calls `execute_refund(utxo_storage_key, None)`. The timelock check passes. `finalize_refund_with_psbt` is called: the UTXO is inserted into `verified_deposit_utxo` (blocking any future `verify_deposit`) and a `BTCPendingInfo` is created to sign a transaction paying `"attacker_btc_address"`.
7. MPC signs the transaction; the relayer broadcasts it. Victim's 1 BTC (minus gas fee) is delivered to the attacker. Victim receives neither BTC nor nBTC.
