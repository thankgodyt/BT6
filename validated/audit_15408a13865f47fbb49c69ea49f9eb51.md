Audit Report

## Title
Reentrancy in `initTransfer1155` via Malicious ERC1155 Token Allows Unbacked Token Minting on NEAR - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
`initTransfer1155` increments `currentOriginNonce` before making an external call to an attacker-controlled ERC1155 token's `safeTransferFrom`, with no reentrancy guard. A malicious ERC1155 token can reenter `initTransfer1155` during this call, causing two `InitTransfer` events to be emitted with distinct nonces (N and N+1) while only one batch of tokens is actually held by the bridge. The NEAR side processes each event independently and mints tokens for both, resulting in unbacked token minting and theft of bridged funds.

## Finding Description

`initTransfer1155` increments `currentOriginNonce` at line 448, then calls `IERC1155(tokenAddress).safeTransferFrom(msg.sender, address(this), tokenId, amount, "")` at line 458 on an arbitrary, attacker-supplied address. There is no `nonReentrant` modifier and no `ReentrancyGuardUpgradeable` in the contract inheritance chain.

The `tokenAddress` parameter is not validated against the `multiTokens` mapping — any address can be passed. The malicious token's `safeTransferFrom` is fully attacker-controlled and can reenter `initTransfer1155` before returning:

- **Outer call** (nonce N): bridge calls `maliciousToken.safeTransferFrom(...)`. The malicious implementation reenters `initTransfer1155` (inner call), then returns without transferring any tokens and without calling `onERC1155Received`.
- **Inner call** (nonce N+1): bridge calls `maliciousToken.safeTransferFrom(...)` again. This time the malicious implementation actually updates balances and calls `onERC1155Received` with `operator = address(bridge)` (satisfying the check at line 530). The inner call emits `InitTransfer` with nonce N+1.
- After the inner call returns, the outer call emits `InitTransfer` with nonce N.

The `onERC1155Received` guard at line 530 (`operator != address(this)`) is irrelevant: it only blocks direct ERC1155 sends, not reentrancy through a malicious `safeTransferFrom` implementation. The bridge never verifies that `onERC1155Received` was actually invoked by the token.

On the NEAR side, `fin_transfer_callback` checks the factory address and calls `add_fin_transfer` which inserts `{origin_chain, origin_nonce}` into `finalised_transfers`. Since nonces N and N+1 are distinct `TransferId` values, both pass the replay check. For EVM-originated tokens, `unlock_tokens_if_needed` returns `LockAction::Unchanged` (because `get_token_origin_chain(token_id) == ChainKind::Eth == chain_kind`), so no locked-token balance check is performed. The NEAR side proceeds to mint tokens for both events via `send_tokens`.

## Impact Explanation

**Critical — unauthorized minting / escrow mis-accounting.**

Two `InitTransfer` events are emitted (nonces N and N+1, each for `amount` tokens) while only `amount` tokens are held by the bridge. The NEAR side mints `2 × amount` tokens. The attacker bridges the surplus `amount` tokens back to EVM via `finTransfer`, draining the bridge's ERC1155 reserves. This directly matches the allowed impact: "unauthorized minting" and "escrow mis-accounting that changes user or protocol balances."

## Likelihood Explanation

**High.** The attack is fully permissionless:
1. Deploy a malicious ERC1155 contract (no privileges required).
2. Call `logMetadata1155` with the malicious token (permissionless).
3. Wait for NEAR to process the `LogMetadata` event and deploy the token via `deploy_token`.
4. Call `initTransfer1155` with the malicious token.

No admin access, no leaked keys, no privileged role is required. The attack is repeatable.

## Recommendation

Import and inherit `ReentrancyGuardUpgradeable` and apply `nonReentrant` to `initTransfer`, `initTransfer1155`, and `finTransfer`:

```solidity
import {ReentrancyGuardUpgradeable} from
    "@openzeppelin/contracts-upgradeable/utils/ReentrancyGuardUpgradeable.sol";

contract OmniBridge is
    UUPSUpgradeable,
    AccessControlUpgradeable,
    SelectivePausableUpgradable,
    ReentrancyGuardUpgradeable,
    IERC1155Receiver
{
    function initTransfer1155(...) external payable nonReentrant whenNotPaused(PAUSED_INIT_TRANSFER) { ... }
    function initTransfer(...)    external payable nonReentrant whenNotPaused(PAUSED_INIT_TRANSFER) { ... }
    function finTransfer(...)     external payable nonReentrant whenNotPaused(PAUSED_FIN_TRANSFER)  { ... }
}
```

Additionally, consider validating that `tokenAddress` is registered in `multiTokens` before calling `safeTransferFrom` in `initTransfer1155`.

## Proof of Concept

**Exploit contract:**

```solidity
contract MaliciousERC1155 {
    IOmniBridge public bridge;
    bool public reentered;
    mapping(address => mapping(uint256 => uint256)) public balances;

    function attack(string calldata nearRecipient) external {
        bridge.initTransfer1155(address(this), 1, 100, 0, 0, nearRecipient, "");
    }

    function safeTransferFrom(address from, address to, uint256 id, uint256 amount, bytes calldata) external {
        if (!reentered) {
            reentered = true;
            // Reenter: nonce increments to N+1, inner call emits InitTransfer(N+1)
            bridge.initTransfer1155(address(this), 1, 100, 0, 0, "attacker.near", "");
            reentered = false;
            // Outer call returns WITHOUT transferring tokens or calling onERC1155Received
        } else {
            // Inner call: actually transfer tokens and satisfy onERC1155Received
            balances[from][id] -= amount;
            balances[to][id] += amount;
            bytes4 retval = IERC1155Receiver(to).onERC1155Received(address(bridge), from, id, amount, "");
            require(retval == IERC1155Receiver.onERC1155Received.selector);
        }
    }
    // ... minimal ERC1155 stubs
}
```

**Result:** Two `InitTransfer` events emitted on EVM (nonces N and N+1, each for 100 tokens). Only 100 tokens held by bridge. NEAR mints 200 tokens. Attacker bridges surplus 100 tokens back to EVM, stealing 100 tokens from bridge reserves.

**Verification:** Deploy on a local Hardhat fork, call `attack()`, confirm two `InitTransfer` events in the transaction receipt with distinct nonces, and confirm `erc1155.balanceOf(bridge, tokenId) == 100` (not 200).
