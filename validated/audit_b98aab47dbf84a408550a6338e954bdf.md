### Title
Peras Certificate Validation Bypass Allows Any Peer to Inject Arbitrary Chain-Selection Boosts - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance used in production unconditionally accepts every inbound Peras certificate from any peer without performing any cryptographic, quorum, or committee-membership check. Because accepted certificates are immediately forwarded to chain selection and can boost a competing block's weight, an unprivileged peer can craft a certificate that causes an honest node to prefer a non-canonical chain — a direct bypass of Peras certificate verification.

---

### Finding Description

`BlockSupportsPeras` is the typeclass that governs Peras certificate and vote validation. A degenerate catch-all instance is provided for all `StandardHash blk` types:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

This stub is wired directly into the production inbound-certificate pipeline. `makePerasCertPoolWriterFromChainDB` passes `(validatePerasCert mkPerasParams)` as the validation function to `processCerts`:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

`processCerts` partitions results into valid/invalid; because `validatePerasCert` always returns `Right`, every certificate passes and is timestamped and forwarded to `addPerasCertAsync`: [3](#0-2) 

`addPerasCertAsync` enqueues the certificate for `chainSelSync`, which — after checking the boosted block is not already immutable — calls `chainSelectionForBlock` for the boosted block:

```haskell
-- Trigger chain selection for the boosted block.
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

Chain selection now compares candidates by Peras weight (not just length). A certificate accepted with `vpcCertBoost = perasWeight mkPerasParams` (currently `PerasWeight 15`) is enough to tip a tie or a one-block deficit in favour of the boosted chain. [5](#0-4) 

---

### Impact Explanation

An unprivileged peer that can speak the Peras object-diffusion mini-protocol can:

1. Send a valid block on a competing fork to the target node (so the block lands in the VolatileDB).
2. Immediately send a crafted `PerasCert` whose `pcCertBoostedBlock` points to that block.
3. Because `validatePerasCert` performs zero checks (no BLS signature, no committee-membership proof, no quorum threshold), the certificate is accepted and stored.
4. Chain selection is re-run for the boosted block; the competing fork now carries extra weight and may become the preferred chain.
5. The node rolls back to the fork, accepting a chain that would otherwise have been rejected.

This is a **bypass of Peras certificate/vote verification** that enables unauthorized certificate acceptance and chain-selection manipulation — matching the "Critical" tier of the allowed impact scope.

---

### Likelihood Explanation

Peras is disabled by default (`Note that if Peras is disabled (which is the default), there is no observable difference`), so the attack surface is currently limited to nodes that explicitly enable Peras (private testnets, staging environments, or future production deployments). However:

- No stake, key material, or privileged access is required — any connected peer suffices.
- The object-diffusion mini-protocol for Peras certificates is unconditionally wired into the production `ChainDB` regardless of whether Peras is "enabled" at the application level.
- The TODO comment and linked issue (`cardano-peras/issues/120`) confirm the stub is intentionally temporary, meaning the window of exposure exists for the entire Peras development lifecycle until a real instance is provided.

Likelihood: **Medium** (currently gated by Peras being off by default; becomes High the moment Peras is switched on).

---

### Recommendation

1. **Remove or guard the degenerate instance.** Until a real `validatePerasCert` implementation exists, the catch-all instance should either be absent (forcing a compile error if Peras is wired up without a real instance) or should unconditionally return `Left PerasValidationErr` so that no certificate from the network is ever accepted.
2. **Implement full certificate validation** per the Peras specification: verify the BLS aggregate signature, confirm committee membership and seat indices, and check that the quorum threshold (`perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin`) is met before constructing a `ValidatedPerasCert`.
3. **Gate the object-diffusion mini-protocol** on the Peras feature flag so that nodes with Peras disabled never process inbound certificates at all.

### Proof of Concept

**Attacker-controlled entry path:**

```
Peer (any node) 
  → object-diffusion mini-protocol 
  → makePerasCertPoolWriterFromChainDB.opwAddObjects 
  → processCerts (validatePerasCert mkPerasParams) 
  → validatePerasCert always returns Right 
  → ChainDB.addPerasCertAsync 
  → chainSelSync ChainSelAddPerasCert 
  → chainSelectionForBlock (boosted block on adversarial fork)
  → node switches chain
```

**Minimal crafted certificate (pseudocode):**

```haskell
-- Attacker first sends a valid block `advBlock` on a competing fork.
-- Then sends:
let craftedCert = PerasCert
      { pcCertRound      = PerasRoundNo 1          -- any round not yet in DB
      , pcCertBoostedBlock = blockPoint advBlock    -- block on adversarial fork
      }
-- No signature, no committee proof, no quorum evidence needed.
-- validatePerasCert mkPerasParams craftedCert == Right (ValidatedPerasCert ...)
-- Chain selection re-runs; advBlock's chain gains PerasWeight 15 boost.
```

The boosted chain wins chain selection if it is within one block of the current tip, causing the honest node to roll back and adopt the adversarial fork.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
