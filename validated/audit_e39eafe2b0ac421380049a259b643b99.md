### Title
Unauthenticated `request_refund` Allows Attacker to Redirect Any User's BTC Refund to Attacker-Controlled Address - (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary
`request_refund` accepts a caller-supplied `refund_address` with no check that the caller owns or is authorized for the deposit being refunded. When `deposit_msg.refund_address` is `None`, any unprivileged NEAR account can submit a refund request for any other user's unfinalized BTC deposit and redirect the BTC to an attacker-controlled Bitcoin address.

---

### Finding Description

`request_refund` is a public, permissionless function. Its only caller-identity check is a narrow one: if the optional `gas_fee` parameter is set, the caller must be DAO or Operator. [1](#0-0) 

Inside `internal_request_refund`, the `refund_address` is validated against `deposit_msg.refund_address` **only when that field is `Some`**: [2](#0-1) 

When `deposit_msg.refund_address` is `None` — the common case for standard deposits — the caller's supplied `refund_address` is accepted unconditionally and stored verbatim in the `RefundRequest`: [3](#0-2) 

The `request_refund_callback` verifies only that the BTC transaction output script matches the deposit address derived from `deposit_msg`. It does **not** verify that the caller is the NEAR account associated with that `deposit_msg`: [4](#0-3) 

The `deposit_msg` needed to reconstruct the deposit address is publicly observable: `get_user_deposit_address` emits it in a `LogDepositAddress` event: [5](#0-4) 

After the `unsafe_refund_timelock_sec` elapses, `execute_refund` is also permissionless and sends the BTC to the stored `refund_address`: [6](#0-5) [7](#0-6) 

---

### Impact Explanation

An attacker who successfully executes this attack receives the victim's full deposit amount minus the gas fee, sent to an attacker-controlled Bitcoin address. The victim's BTC is permanently lost. This is a direct theft of user funds held by the bridge, matching the Critical impact class: **Significant loss or theft of user funds**.

---

### Likelihood Explanation

The attack requires:
1. The victim's `deposit_msg` — publicly emitted in `LogDepositAddress` events on NEAR.
2. The victim's BTC transaction bytes and Merkle proof — publicly available on the Bitcoin blockchain.
3. The victim's deposit to remain unfinalized (relayer delay, outage, or the attacker front-running before `verify_deposit` is called).
4. Operators to fail to reject the request within `unsafe_refund_timelock_sec`.

Conditions 1–3 are realistic (relayer outages occur; the BTC mempool and NEAR events are public). Condition 4 is the only operational mitigation. If the timelock window is missed — due to operator inattention, a surge of requests, or a coordinated attack submitting many requests simultaneously — the theft completes. Likelihood is **Medium**.

---

### Recommendation

Add an ownership check in `request_refund`: verify that `env::predecessor_account_id()` matches the NEAR account embedded in `deposit_msg` (e.g., `deposit_msg.account_id`), or require that `deposit_msg.refund_address` is always pre-set (i.e., reject requests where it is `None` and the caller is not DAO/Operator). This mirrors the recommended fix in H-07: always use the contract's own address (`address(this)`) as the recipient, then transfer to the rightful owner — here, always require the refund address to be pre-authorized in the deposit message rather than accepting it from an arbitrary caller.

---

### Proof of Concept

1. **Alice** calls `get_user_deposit_address(deposit_msg)` where `deposit_msg.refund_address = None`. The NEAR event `LogDepositAddress` emits `deposit_msg` publicly.
2. Alice sends BTC to the derived deposit address. The BTC transaction is confirmed on-chain.
3. The relayer is delayed and has not yet called `verify_deposit`.
4. **Attacker** reads Alice's `deposit_msg` from the NEAR event log and Alice's BTC transaction from the Bitcoin blockchain.
5. Attacker calls:
   ```
   request_refund(
     deposit_msg = alice_deposit_msg,   // obtained from LogDepositAddress event
     refund_address = "attacker_btc_address",
     tx_bytes = alice_tx_bytes,
     vout = alice_vout,
     proof = alice_merkle_proof,
     gas_fee = None
   )
   ```
   The light-client verification passes (the transaction is real). The callback stores `refund_address = attacker_btc_address` with no ownership check.
6. After `unsafe_refund_timelock_sec` elapses (operators miss or ignore the request), attacker calls `execute_refund(utxo_storage_key, None)`.
7. The bridge constructs a BTC transaction paying `alice_deposit_amount - gas_fee` to `attacker_btc_address`. Alice's BTC is stolen.

    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }

    /// Build a transparent refund output paying `refund_amount` to `refund_address`.
    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
    }
