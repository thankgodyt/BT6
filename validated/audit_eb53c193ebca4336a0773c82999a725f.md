### Title
`revalidateHeader` Silently Discards Envelope Validation Failure via CPP-Gated `assertWithMsg` — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/HeaderValidation.hs`)

---

### Summary

`revalidateHeader` is the fast-path header re-application used during chain selection and ImmutableDB replay. It guards its envelope check with `assertWithMsg`, a CPP-conditional helper that compiles to a **no-op** when the `ENABLE_ASSERTIONS` flag is absent. In any build where assertions are disabled — including the explicitly supported `noAsserts` Nix variant — the `validateEnvelope` result is silently discarded and the new `HeaderState` is unconditionally returned, regardless of whether the envelope check passed or failed. This is the direct structural analog of the reported `dropBoost` pattern: a prerequisite check whose failure indicator is ignored, allowing the state transition to proceed with incorrect state.

---

### Finding Description

`revalidateHeader` in `HeaderValidation.hs` is defined as:

```haskell
revalidateHeader cfg ledgerView hdr st =
  assertWithMsg envelopeCheck $
    HeaderState
      (NotOrigin (getAnnTip hdr))
      chainDepState'
 where
  chainDepState' =
    reupdateChainDepState
      (configConsensus cfg)
      (validateView (configBlock cfg) hdr)
      (blockSlot hdr)
      (tickedHeaderStateChainDep st)

  envelopeCheck =
    runExcept $ withExcept show $
      validateEnvelope cfg ledgerView (untickedHeaderStateTip st) hdr
``` [1](#0-0) 

`assertWithMsg` is defined as:

```haskell
assertWithMsg :: HasCallStack => Either String () -> a -> a
#if ENABLE_ASSERTIONS
assertWithMsg (Left msg) _ = error msg
#endif
assertWithMsg _ a = a
``` [2](#0-1) 

When `ENABLE_ASSERTIONS` is **not** defined, the `#if` branch is absent from the compiled binary. The function reduces to `assertWithMsg _ a = a` — it unconditionally returns its second argument. The `envelopeCheck` computation is still evaluated (it is not lazy in the first argument), but its `Left` result is silently thrown away.

The Nix build system explicitly provides a `noAsserts` variant that empties `cabal/asserts.cabal`, disabling `ENABLE_ASSERTIONS` across the entire library:

```nix
noAsserts = {
  src = lib.mkForce (final.applyPatches {
    name = "consensus-src-no-asserts";
    src = ouroborosConsensusSrc;
    postPatch = ''echo > cabal/asserts.cabal'';
  });
};
``` [3](#0-2) 

`validateEnvelope` performs two classes of checks: structural checks (consecutive block numbers, strictly increasing slots, hash linkage) and protocol-specific `additionalEnvelopeChecks`. For the Hard Fork Combinator, `additionalEnvelopeChecks` verifies that the header's era matches the era encoded in the supplied `LedgerView`. A mismatch returns `HardForkEnvelopeErrWrongEra`. [4](#0-3) 

`revalidateHeader` accepts a `LedgerView` parameter that is independent of the `HeaderState` parameter. The function's documented precondition — "the header has been validated before w.r.t. the same exact `HeaderState`" — constrains the `HeaderState` but places **no constraint on the `LedgerView`**. During chain selection across an era boundary, the caller may supply a `LedgerView` from the new era while replaying a header from the old era. In that scenario `validateEnvelope` returns `Left (HardForkEnvelopeErrWrongEra …)`, but in an assertions-disabled build `assertWithMsg` discards this `Left` and returns the freshly constructed `HeaderState` containing the result of `reupdateChainDepState` — which itself skips all cryptographic checks. [5](#0-4) 

---

### Impact Explanation

**High — Chain-selection / header-state bug reachable by an unprivileged peer.**

When assertions are disabled, `revalidateHeader` can silently accept a header whose era does not match the current `LedgerView`. The resulting `HeaderState` carries a `ChainDepState` computed by `reupdateChainDepState` against a mismatched ticked state. Downstream chain-selection logic (`preferCandidate`, `ChainDB` adoption) then operates on a corrupted `HeaderState`, potentially causing the node to prefer or permanently adopt a chain whose headers have not been correctly validated against the active era's rules. Because `reupdateChainDepState` also skips KES/VRF checks, the accepted `ChainDepState` may contain nonces or OCert counters derived from the wrong era's rules, breaking subsequent header validation for all blocks on that chain.

---

### Likelihood Explanation

**Medium.**

- The `noAsserts` Nix variant is an explicitly maintained, first-class build target, indicating that assertion-free production deployments are anticipated and supported.
- Era transitions occur on every Cardano network; the Byron→Shelley, Shelley→Allegra, …, Babbage→Conway sequence provides multiple windows where a peer-supplied chain can straddle an era boundary during chain selection.
- The attacker requires no special privileges: any peer that can present a competing chain fragment crossing an era boundary can trigger the vulnerable code path via the standard ChainSync miniprotocol.
- The precondition "same exact `HeaderState`" is documented but not enforced by the type system; callers that supply a mismatched `LedgerView` are not caught at compile time.

---

### Recommendation

Replace the `assertWithMsg` guard with a hard error that is unconditional on build flags:

```haskell
revalidateHeader cfg ledgerView hdr st =
  case runExcept (withExcept show (validateEnvelope cfg ledgerView (untickedHeaderStateTip st) hdr)) of
    Left err -> error ("revalidateHeader: envelope check failed: " <> err)
    Right () ->
      HeaderState
        (NotOrigin (getAnnTip hdr))
        (reupdateChainDepState
           (configConsensus cfg)
           (validateView (configBlock cfg) hdr)
           (blockSlot hdr)
           (tickedHeaderStateChainDep st))
```

Alternatively, strengthen the documented precondition to require that the `LedgerView` passed to `revalidateHeader` is always the same one used in the preceding `validateHeader` call, and enforce this at the call sites.

---

### Proof of Concept

1. Build the node with the `noAsserts` Nix variant (or any build where `ENABLE_ASSERTIONS` is absent), so `assertWithMsg` compiles to the identity function.
2. Arrange a private two-node testnet where node A is at the tip of era N and node B presents a competing chain that crosses the era-N→era-N+1 boundary.
3. Node A's ChainSync client calls `validateHeader` (full check) for the first header in era N+1, obtaining a valid `HeaderState`. Chain selection then calls `revalidateHeader` to replay earlier era-N headers against the new era-N+1 `LedgerView`.
4. `validateEnvelope` returns `Left (HardForkEnvelopeErrWrongEra …)` for each era-N header replayed against the era-N+1 view.
5. Because `assertWithMsg` is a no-op, each call returns a `HeaderState` built from `reupdateChainDepState` without any envelope enforcement.
6. Node A's `ChainDepState` is now derived from era-N headers validated against era-N+1 rules, producing incorrect nonces and OCert counters that corrupt all subsequent header validation on that chain.
