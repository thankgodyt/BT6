### Title
Peras Certificate Validation Bypass and First-Come-First-Served Deduplication Enables Adversarial Chain-Selection Weight Injection — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`, `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Storage/PerasCertDB/Impl.hs`, `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs`)

---

### Summary

The Peras certificate ingest pipeline contains two compounding defects that together allow an unprivileged peer to inject a crafted certificate that permanently displaces the honest certificate for a given round, causing the node to assign Peras weight boost to an adversarial block and potentially prefer a non-canonical chain over the honest one. The root causes are: (1) `validatePerasCert` is a stub that unconditionally accepts every certificate without any cryptographic, committee-membership, or quorum check; and (2) `implAddCert` deduplicates certificates by round number only — the first certificate received for a round is stored and all subsequent certificates for the same round are silently dropped as `PerasCertAlreadyInDB`, regardless of which block they boost. The outcome of chain selection therefore depends on the order in which certificates arrive, directly mirroring the VTVLVesting order-dependency class.

---

### Finding Description

**Root cause 1 — `validatePerasCert` stub (no validation)** [1](#0-0) 

The `BlockSupportsPeras` instance for all block types unconditionally returns `Right` for every certificate, performing zero cryptographic verification, no committee-membership check, and no quorum threshold check. This is the only validation gate before a certificate is timestamped and forwarded to the DB.

**Root cause 2 — `implAddCert` deduplicates by round number only** [2](#0-1) 

`implAddCert` checks `Set.member roundNo (pcdsCertIds pcds)`. If a certificate for round `R` is already present — regardless of which block it boosts — any subsequent certificate for round `R` is silently returned as `PerasCertAlreadyInDB` and discarded. The boosted-block field is never compared.

**Production call site — `processCerts` uses the stub** [3](#0-2) 

`makePerasCertPoolWriterFromChainDB` (the production writer used by the node) calls `processCerts` with `validatePerasCert mkPerasParams` as the validation function. Because the stub always returns `Right`, every inbound certificate passes validation and is forwarded to `ChainDB.addPerasCertAsync`.

**Chain-selection consequence** [4](#0-3) 

`chainSelSync` processes the accepted certificate: it adds it to the `PerasCertDB`, then calls `chainSelectionForBlock` for the boosted block. The weight snapshot used by `getCurrentChain` and `preferCandidate` is derived directly from the DB contents. [5](#0-4) 

`getCurrentChain` calls `takeVolatileSuffix weights k` where `weights` comes from `getPerasWeightSnapshot`, which in turn is built from every certificate in `pcdsCertsByTicket`. [6](#0-5) 

`implGetWeightSnapshot` iterates all entries in `pcdsCertsByTicket` to build the weight map. Whichever block was boosted by the first-accepted certificate for round `R` is the block that receives the weight boost in every subsequent chain comparison.

**The order-dependency (direct analog to VTVLVesting)**

| Arrival order | Outcome |
|---|---|
| Honest cert(R, B_honest) arrives first | B_honest receives boost; adversarial cert(R, B_adv) is silently dropped |
| Adversarial cert(R, B_adv) arrives first | B_adv receives boost; honest cert(R, B_honest) is silently dropped |

In VTVLVesting, calling `revokeClaim` before `withdraw` silently discards the already-vested amount. Here, sending a crafted certificate before the honest one silently discards the honest certificate's boost. In both cases, the "correct" state is permanently lost based solely on operation ordering, and the node has no way to recover.

---

### Impact Explanation

An adversary who races their crafted certificate to the victim node before the honest certificate arrives causes the node to assign Peras weight boost to an adversarial block. Because `wsvTotalWeight` adds block-number weight and boost weight, a sufficiently large boost (controlled by `perasWeight mkPerasParams`) can make a shorter adversarial fork outweigh the honest chain in `preferCandidate`, triggering a fork switch. This is a chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain beyond the intended security assumptions. [7](#0-6) 

---

### Likelihood Explanation

The ObjectDiffusion mini-protocol for Peras certificates is reachable by any connected peer. The adversary needs only to send a single well-formed (but cryptographically unverified) `PerasCert` message with an arbitrary round number and a block point on their fork before the honest certificate for that round propagates to the victim. No stake, no keys, and no special privileges are required. The race window is the network propagation delay between the honest certificate source and the victim node.

---

### Recommendation

1. **Implement real certificate validation in `validatePerasCert`**: verify the aggregate BLS/KES signature, confirm committee membership and quorum threshold against the ledger stake distribution, and reject certificates that do not meet the Peras protocol rules. The stub must not be used in any production code path.

2. **Reject equivocating certificates explicitly**: in `implAddCert`, when a certificate for round `R` already exists, compare the boosted block of the incoming certificate against the stored one. If they differ, the incoming certificate is equivocating and should be rejected with a distinct error (not silently dropped as `PerasCertAlreadyInDB`), and the peer should be penalised.

3. **Preserve the honest certificate**: analogous to the VTVLVesting fix that tracks `deactivationTimestamp` to preserve already-vested amounts, the DB should track the canonical certificate per round and refuse to silently overwrite it with an unvalidated one.

---

### Proof of Concept

```
1. Victim node V is connected to honest peer H and adversarial peer A.
2. Peras round R completes; honest quorum produces cert(R, B_honest).
3. A sends crafted cert(R, B_adv) to V via ObjectDiffusion before H does.
4. processCerts calls validatePerasCert(cert(R, B_adv)) → Right (stub, no check).
5. implAddCert stores cert(R, B_adv); pcdsCertIds now contains R.
6. H sends cert(R, B_honest) to V.
7. processCerts calls validatePerasCert(cert(R, B_honest)) → Right.
8. implAddCert: Set.member R pcdsCertIds == True → returns PerasCertAlreadyInDB.
   cert(R, B_honest) is silently discarded.
9. implGetWeightSnapshot returns boost for B_adv only.
10. getCurrentChain calls takeVolatileSuffix with weights boosting B_adv.
11. preferCandidate compares wsvTotalWeight: adversarial fork containing B_adv
    has higher total weight than honest fork → ShouldSwitch.
12. V switches to the adversarial fork.
```

implAddCert PerasCertDbEnv{pcdbTracer, pcdbState} cert = do
  let roundNo = getPerasCertRound cert
  addPerasCertRes <- do
    WithFingerprint pcds fp <- readTVar pcdbState
    if Set.member roundNo (pcdsCertIds pcds)
      then pure PerasCertAlreadyInDB
      else do
        let pcdsLastTicketNo' = succ (pcdsLastTicketNo pcds)
            pcdsCertIds' = Set.insert roundNo (pcdsCertIds pcds)
            pcdsCertsByTicket' = Map.insert pcdsLastTicketNo' cert (pcdsCertsByTicket pcds)
            pcdsLatestCertSeen' = case pcdsLatestCertSeen pcds of
              Nothing -> Just cert
              Just prev
                | getPerasCertRound cert > getPerasCertRound prev -> Just cert
                | otherwise -> Just prev
        writeTVar pcdbState $
          WithFingerprint
            PerasCertDbState
              { pcdsCertIds = pcdsCertIds'
              , pcdsCertsByTicket = pcdsCertsByTicket'
              , pcdsLastTicketNo = pcdsLastTicketNo'
              , pcdsLatestCertSeen = pcdsLatestCertSeen'
              }
            (succ fp)
        pure AddedPerasCertToDB
  pure $ do
    traceWith pcdbTracer (AddCert roundNo cert addPerasCertRes)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
