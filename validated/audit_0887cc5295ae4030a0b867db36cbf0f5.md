Audit Report

## Title
Missing Registered-Token Validation in `initTransfer` Allows Permanent Freezing of User Funds - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
`OmniBridge.initTransfer` contains a catch-all `else` branch that accepts any ERC20 token address and locks it in the contract without verifying the token is registered in `ethToNearToken`. When a relayer submits the resulting proof to NEAR, `fin_transfer_callback` panics with `TokenDecimalsNotFound` because the token has no entry in `token_decimals`. The EVM state is already committed, there is no cross-chain refund signal, and no admin rescue function exists for arbitrary locked ERC20 balances, permanently freezing the user's funds.

## Finding Description
In `initTransfer`, after handling the `customMinters` and `isBridgeToken` branches, the contract falls through to an unchecked `else`:

```solidity
} else {
    IERC20(tokenAddress).safeTransferFrom(
        msg.sender,
        address(this),
        amount
    );
}
``` [1](#0-0) 

There is no guard of the form `require(bytes(ethToNearToken[tokenAddress]).length > 0)` before this path. The `ethToNearToken` mapping is only populated for tokens registered via `deployToken` or `addCustomToken`. [2](#0-1) 

After locking, `InitTransfer` is emitted unconditionally: [3](#0-2) 

On the NEAR side, `fin_transfer_callback` immediately looks up the token in `token_decimals` and panics if absent:

```rust
let decimals = self
    .token_decimals
    .get(&init_transfer.token)
    .near_expect(BridgeError::TokenDecimalsNotFound);
``` [4](#0-3) 

The NEAR transaction reverts, but the EVM state is already committed. `OmniBridge.sol` contains no `rescueTokens` or equivalent admin function for arbitrary ERC20 balances. The `finTransfer` path (the only EVM-side release mechanism) requires a valid MPC-signed payload from NEAR, which is never generated because the NEAR side panics before producing one.

The `removeCustomToken` admin function compounds the risk: it clears `isBridgeToken`, `ethToNearToken`, and `customMinters` for a token on the EVM side, but does not coordinate removal on NEAR. After removal, `initTransfer` will still accept the token via the catch-all `else` branch. [5](#0-4) 

The same root cause exists in the Starknet contract: `init_transfer` in `omni_bridge.cairo` also accepts any `token_address` without checking `starknet_to_near_token`: [6](#0-5) 

## Impact Explanation
Any user who calls `initTransfer` with an ERC20 token not registered in the bridge will have their tokens permanently locked in the EVM bridge contract with no recovery path. This constitutes permanent freezing of bridged funds, which falls squarely within the Critical impact scope: "permanent freezing of bridged funds across EVM."

## Likelihood Explanation
The catch-all `else` branch silently accepts any ERC20 without reverting or emitting a warning. A user who holds a token that was previously supported and then deprecated via `removeCustomToken` would have no on-chain signal that the transfer will fail on NEAR. The `removeCustomToken` admin path is a realistic operational event (token migration, deprecation). Additionally, any user who mistakenly provides an unregistered token address triggers the same outcome. No attacker involvement is required beyond a normal bridge user making a public contract call.

## Recommendation
Add a registration check at the top of `initTransfer` for non-native, non-bridge-token, non-custom-minter paths:

```solidity
} else {
    require(
        bytes(ethToNearToken[tokenAddress]).length > 0,
        "ERR_TOKEN_NOT_REGISTERED"
    );
    IERC20(tokenAddress).safeTransferFrom(
        msg.sender,
        address(this),
        amount
    );
}
```

Apply the equivalent guard in `starknet/src/omni_bridge.cairo` `init_transfer` by asserting `self.starknet_to_near_token.read(token_address).len() > 0` before processing non-bridge tokens. Additionally, consider adding an admin rescue function for arbitrary ERC20 balances as a defense-in-depth measure.

## Proof of Concept
1. Deploy any ERC20 token `FakeToken` not registered in `OmniBridge` (i.e., `ethToNearToken[FakeToken] == ""`).
2. Approve `OmniBridge` to spend `1000 FakeToken`.
3. Call `OmniBridge.initTransfer(FakeToken, 1000, 0, 0, "victim.near", "")` with `msg.value >= nativeFee`.
4. The contract executes `safeTransferFrom(msg.sender, address(this), 1000)` — tokens are locked — and emits `InitTransfer`.
5. A relayer submits the proof to NEAR's `fin_transfer`. `fin_transfer_callback` calls `self.token_decimals.get(&init_transfer.token).near_expect(BridgeError::TokenDecimalsNotFound)` and panics.
6. The NEAR transaction reverts. The EVM transaction is already finalized. `FakeToken` balance of `OmniBridge` is permanently increased with no withdrawal path for the user.
