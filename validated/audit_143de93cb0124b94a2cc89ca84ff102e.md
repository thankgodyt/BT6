### Title
ChainSync Client Uses Empty Peras Weight Snapshot in Forecast-Horizon Disconnect Check, Diverging from ChainDB Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

The `checkPreferTheirsOverOurs` function in the ChainSync client compares a peer's candidate fragment against the node's current selection using a hardcoded `emptyPerasWeightSnapshot` (zero Peras boosts) rather than the live `PerasWeightSnapshot` that ChainDB uses for actual chain selection. This is the direct analog of the slippage-protection bug: a critical ordering decision is made with a stale/wrong state value, while the authoritative decision-maker (ChainDB) uses the real, up-to-date value. When Peras is active and boosted blocks exist, the two comparisons can disagree, causing the ChainSync client to disconnect from honest peers whose chains are canonically heavier but shorter in raw block count.

---

### Finding Description

When a peer's header slot falls beyond the forecast horizon, `readLedgerStateHelper` cannot yet obtain a `LedgerView` for that slot. It retries in a loop, but before each retry it calls `checkPreferTheirsOverOurs` to decide whether to keep waiting or disconnect:

```haskell
-- ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs
-- lines 1814-1817
case prj lst of
  Nothing -> do
    checkPreferTheirsOverOurs kis'
    retry
```

`checkPreferTheirsOverOurs` performs the comparison using `emptyPerasWeightSnapshot`:

```haskell
-- lines 1834-1857
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← always zero Peras weight
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse ...
```

`preferAnchoredCandidate` with `emptyPerasWeightSnapshot` falls into the `isEmptyPerasWeightSnapshot` fast path and compares chains purely by raw block count (`BlockNo`):

```haskell
-- ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Util/AnchoredFragment.hs
-- lines 186-203
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      ...
      (_ :> ourTip, _ :> theirTip) ->
        case preferCandidate
          (projectChainOrderConfig cfg)
          (selectView cfg (getHeader1 ourTip))   -- raw SelectView / BlockNo
          (selectView cfg (getHeader1 theirTip)) of ...
```

By contrast, ChainDB's actual chain selection reads the live snapshot atomically and uses it throughout:

```haskell
-- ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Storage/ChainDB/Impl/ChainSel.hs
-- lines 631-634
(,,)
  <$> (forgetFingerprint <$> readTVar cdbInvalid)
  <*> Query.getCurrentChain cdb
  <*> (forgetFingerprint <$> Query.getPerasWeightSnapshot cdb)   -- real weights
```

and passes those real weights to every `preferAnchoredCandidate` call (e.g. lines 777, 1130, 1180).

The result is a **two-tier comparison**: the ChainSync client's keep-or-disconnect gate uses block-count only, while ChainDB's authoritative selection uses total Peras weight. These can disagree whenever Peras certificates have boosted one or more blocks on the canonical chain.

---

### Impact Explanation

When Peras is active and the canonical chain contains boosted blocks, the canonical chain can be heavier in total weight yet shorter in raw block count than an adversary's competing fork. In that situation:

1. An honest peer serving the canonical (shorter but heavier) chain sends a header beyond the forecast horizon.
2. `checkPreferTheirsOverOurs` evaluates the honest peer's fragment as *not preferred* (fewer blocks) and throws `CandidateTooSparse`, disconnecting the peer.
3. An adversary serving a longer-but-lighter fork passes the same check (more blocks) and keeps the connection alive.
4. If the node is disconnected from all honest peers simultaneously, it loses access to the canonical chain and may ultimately select the adversary's lighter fork — a chain-selection safety failure.

This matches the **High** impact category: a chain-selection bug that lets an unprivileged peer cause an honest node to prefer a non-canonical chain beyond the intended security assumptions.

---

### Likelihood Explanation

- Peras is not yet active on Cardano mainnet; the vulnerability is dormant until Peras certificates are issued.
- The adversary needs a fork that is longer in raw block count than the canonical chain at the moment the forecast horizon is exceeded — achievable without a stake majority if the canonical chain has accumulated significant Peras weight boosts on a shorter suffix.
- The attack window is the period during which the honest peer's header is beyond the forecast horizon (up to one stability window, `3k/f` ≈ 36 hours on mainnet).
- The developers have already flagged this with a `TODO` comment referencing issue #64, confirming awareness but no fix yet.

Likelihood: **Low-to-Medium** once Peras is live; currently dormant.

---

### Recommendation

1. **Pass the live `PerasWeightSnapshot` into `checkPreferTheirsOverOurs`** so the disconnect decision uses the same weights as ChainDB. The snapshot is already read atomically in `addBlockAsync` and `chainSelectionForBlock`; it should be threaded into the ChainSync client's `ConfigEnv` or `DynamicEnv`.

2. **Alternatively, remove `checkPreferTheirsOverOurs` entirely**, as the existing TODO comment proposes. The check was introduced to prevent indefinite waiting on a chain that will never be selected; with Peras weights it is no longer a sound approximation of that condition.

3. If the check is retained in any form, ensure the comparison metric used here is identical to the one used in `chainSelection` in `ChainSel.hs`, so the two layers cannot disagree.

---

### Proof of Concept

```
Epoch e, Peras active.

Canonical chain (honest):
  G → A → B → C   (BlockNo 3, total Peras weight = 3 + boost(B) = 103)

Adversary's fork:
  G → A → B' → C' → D'  (BlockNo 4, total Peras weight = 4, no boosts)

Node's current selection: canonical chain (C).

1. Adversary peer sends header D' (slot beyond forecast horizon).
   checkPreferTheirsOverOurs: emptyPerasWeightSnapshot → BlockNo 4 > 3 → ShouldSwitch → stay connected.

2. Honest peer sends header C (slot beyond forecast horizon, same scenario on a different fork).
   checkPreferTheirsOverOurs: emptyPerasWeightSnapshot → BlockNo 3 < 4 (our current selection) → ShouldNotSwitch → CandidateTooSparse → disconnect honest peer.

3. Node is now connected only to the adversary.
   Forecast horizon eventually advances; adversary's headers are validated.
   ChainDB compares: adversary weight 4 < canonical weight 103 — but the canonical chain is no longer reachable.
   Node selects adversary's fork.
```
