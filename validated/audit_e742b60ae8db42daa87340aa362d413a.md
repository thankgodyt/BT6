Audit Report

## Title
Reentrancy in `initTransfer1155` via Malicious ERC-1155 `safeTransferFrom` Callback Allows Minting on NEAR Without Locking Tokens on EVM — (`File: evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
`initTransfer1155` increments `currentOriginNonce` before an external call to an untrusted ERC-1155 token, but then reads `currentOriginNonce` again — from storage — after that external call when passing it to `initTransferExtension` and `emit BridgeTypes.InitTransfer`. There is no reentrancy guard. A malicious ERC-1155 token can reenter `initTransfer1155` from within its `safeTransferFrom` implementation, causing both the reentrant and original invocations to emit `InitTransfer` with the same nonce while locking zero tokens, enabling unauthorized minting on NEAR.

## Finding Description

In `initTransfer1155` (lines 439–490 of `evm/src/omni-bridge/contracts/OmniBridge.sol`):

```solidity
currentOriginNonce += 1;          // L448: storage write, nonce = N

IERC1155(tokenAddress).safeTransferFrom(   // L458–464: untrusted external call
    msg.sender, address(this), tokenId, amount, ""
);

initTransferExtension(
    msg.sender, deterministicToken,
    currentOriginNonce,            // L471: storage READ after external call
    ...
);
emit BridgeTypes.InitTransfer(
    msg.sender, deterministicToken,
    currentOriginNonce,            // L483: storage READ after external call
    ...
);
```

The nonce is incremented at the top, but the storage variable `currentOriginNonce` is read again after the external call. No `nonReentrant` guard exists on this function or anywhere in the contract — only `slither-disable` comments (which provide no runtime protection) appear in the file.

The `onERC1155Received` guard (`operator != address(this)`) does not block this attack. The reentrancy occurs inside the malicious token's `safeTransferFrom` implementation, which can call back into `initTransfer1155` directly without invoking `onERC1155Received` at all.

**Attack trace (starting state: `currentOriginNonce = 0`):**

| Step | Actor | Action | `currentOriginNonce` |
|---|---|---|---|
| 1 | Bridge (original call) | `+= 1` | **1** |
| 2 | Malicious ERC-1155 `safeTransferFrom` | reenters `initTransfer1155` | — |
| 3 | Bridge (reentrant call) | `+= 1` | **2** |
| 4 | Malicious ERC-1155 `safeTransferFrom` (2nd) | returns, transfers 0 tokens | — |
| 5 | Bridge (reentrant call) | reads `currentOriginNonce` = **2**, emits `InitTransfer(nonce=2)` | — |
| 6 | Malicious ERC-1155 `safeTransferFrom` (1st) | returns, transfers 0 tokens | — |
| 7 | Bridge (original call) | reads `currentOriginNonce` = **2**, emits `InitTransfer(nonce=2)` | — |

Result: two `InitTransfer` events with `nonce=2` are emitted; nonce=1 is never emitted; zero tokens are locked on EVM. The NEAR side's `fin_transfer_callback` deduplicates by `destination_nonce` (not `origin_nonce`), so both events can be submitted and processed independently, each receiving a distinct `destination_nonce` and triggering a separate mint. Even if only one event is processed, the attacker receives bridged tokens on NEAR with no collateral locked on EVM.

This directly violates two documented invariants in `evm/CLAUDE.md`:
- *"State before external calls: Always mutate state before any external call. This is the primary reentrancy defense."*
- *"Event–transfer atomicity: `InitTransfer` must only be emitted in a code path where tokens have already been burned/locked in the same transaction."*

## Impact Explanation
**Critical.** An unprivileged attacker can mint an arbitrary amount of bridged tokens on NEAR without locking any corresponding collateral on EVM. This is unauthorized minting of bridged funds, directly matching the allowed critical impact: *"Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet, Bitcoin, Zcash, or Wormhole-routed flows."* The bridge's fundamental accounting invariant — that every NEAR-side mint corresponds to a locked EVM-side token — is broken.

## Likelihood Explanation
Any unprivileged user can deploy a malicious ERC-1155 contract and call `initTransfer1155` with it. No special privileges, leaked keys, or external dependencies are required. The attack is repeatable with no cooldown. The only precondition is that the NEAR side has registered the EVM bridge as a known factory (standard operational state). The attack is fully self-contained within public smart-contract calls.

## Recommendation
Apply the Checks-Effects-Interactions (CEI) pattern: capture the nonce into a local variable immediately after incrementing it, and use only the local variable in all subsequent reads:

```solidity
currentOriginNonce += 1;
uint64 nonce = currentOriginNonce;   // cache in local variable

IERC1155(tokenAddress).safeTransferFrom(...);  // external call

initTransferExtension(..., nonce, ...);
emit BridgeTypes.InitTransfer(..., nonce, ...);
```

Additionally, add OpenZeppelin's `ReentrancyGuardUpgradeable` to the contract and apply `nonReentrant` to both `initTransfer` and `initTransfer1155` as defense-in-depth. The same CEI fix should be audited for `initTransfer` (lines 373–437), which has the same pattern but is less immediately exploitable via ERC-20 (no mandatory callback).

## Proof of Concept

**Minimal Foundry test:**

```solidity
// MaliciousERC1155.sol
contract MaliciousERC1155 is ERC1155 {
    OmniBridge bridge;
    bool reentered;

    function safeTransferFrom(
        address from, address to, uint256 id, uint256 amount, bytes memory
    ) public override {
        if (!reentered) {
            reentered = true;
            // Reenter initTransfer1155 — transfers 0 tokens
            bridge.initTransfer1155(address(this), id, amount, 0, 0, "attacker.near", "");
        }
        // Transfer nothing — return without moving tokens
    }
}

// Test
function testReentrancy() public {
    MaliciousERC1155 token = new MaliciousERC1155(bridge);
    
    vm.recordLogs();
    bridge.initTransfer1155(address(token), 1, 100, 0, 0, "attacker.near", "");
    
    Vm.Log[] memory logs = vm.getRecordedLogs();
    // Assert: two InitTransfer events both with nonce=2
    // Assert: bridge holds 0 tokens of token ID 1
    // Assert: nonce=1 was never emitted
}
```

The test demonstrates two `InitTransfer` events with identical nonces emitted in a single transaction, with zero tokens locked in the bridge, satisfying the proof requirement for unauthorized minting on NEAR without EVM collateral.
