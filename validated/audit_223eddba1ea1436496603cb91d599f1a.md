### Title
`validatePerasCert` Excludes All Cryptographic Fields, Allowing Any Peer to Inject Arbitrary Peras Certificates That Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The default `BlockSupportsPeras` instance used for all block types implements `validatePerasCert` as an unconditional `Right` — it accepts every inbound certificate without verifying any cryptographic or semantic field. An unprivileged peer can therefore send a crafted `PerasCert` with an arbitrary `pcCertBoostedBlock` and `pcCertRound`, have it accepted as a `ValidatedPerasCert`, stored in `PerasCertDB`, and used to inflate the Peras weight of an attacker-chosen chain fragment, causing an honest node to switch to a non-canonical chain.

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub:**

The catch-all `instance StandardHash blk => BlockSupportsPeras blk` in `SupportsPeras.hs` implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

Every field of the certificate — the aggregate BLS signature (`pcSignature`), the voter set (`pcVoters`), the quorum threshold, the round number validity, and the boosted block's existence on any real chain — is **excluded from validation**. The function unconditionally wraps the raw certificate in `ValidatedPerasCert`. [1](#0-0) 

**Entry path — peer-to-node object diffusion:**

`makePerasCertPoolWriterFromChainDB` wires this stub directly into the production certificate ingest path:

```haskell
(validatePerasCert mkPerasParams)
``` [2](#0-1) 

`processCerts` calls `validateCert` on every inbound certificate from a peer. Because `validatePerasCert` always returns `Right`, the `partitionEithers` call always produces an empty error list, and every certificate is unconditionally accepted and timestamped: [3](#0-2) 

**Chain selection impact:**

The accepted certificate is forwarded to `addPerasCertAsync`, which enqueues a `ChainSelAddPerasCert` message. `chainSelSync` processes it: it stores the certificate in `PerasCertDB`, reads the boosted block header from `VolatileDB`, and calls `chainSelectionForBlock` for that header. [4](#0-3) 

`chainSelectionForBlock` reads the `PerasWeightSnapshot` (which now includes the attacker's certificate) and passes it to `constructPreferableCandidates`. Chain comparison uses `WeightedSelectView`, where `wsvTotalWeight = blockNo + wsvWeightBoost`. A fraudulent certificate with a large `vpcCertBoost` can make a shorter or otherwise non-preferred fork appear heavier than the honest chain: [5](#0-4) 

The `PerasWeightSnapshot` used in chain selection is derived directly from the `pcdsCertsByTicket` map in `PerasCertDB`, which stores every accepted `ValidatedPerasCert` without any post-acceptance re-validation: [6](#0-5) 

**Secondary issue — `validatePerasVote` also skips signature verification:**

`validatePerasVote` only checks that the voter ID exists in the stake distribution (`lookupPerasVoteStake`) but never verifies the vote's cryptographic signature. A peer can forge votes for any registered stake pool ID, accumulate a fake quorum, and trigger certificate generation internally: [7](#0-6) 

### Impact Explanation

**High — chain selection bug enabling non-canonical chain preference.**

When Peras is active, an unprivileged peer can inject a `PerasCert` with an arbitrary `pcCertBoostedBlock` pointing to any block in the VolatileDB and an arbitrarily large `vpcCertBoost`. The honest node will then re-run chain selection treating that block's chain as heavier than the canonical chain, potentially switching to a fork that the attacker controls or that is shorter/less secure. This directly violates the Peras chain selection invariant that only legitimately quorum-certified blocks receive weight boosts.

The `CHANGELOG` confirms that chain selection is now weight-based when Peras is enabled: *"the candidate fragment is now selected based on its Peras weight, instead of its length."* [8](#0-7) 

### Likelihood Explanation

The object diffusion mini-protocol for Peras certificates is fully wired into the production `ChainDB` and `NodeKernel`. Any peer that connects to a node running with Peras enabled can send a `PerasCert` message. No keys, stake, or special privileges are required. The only precondition is that Peras is enabled (the intended production state once the Peras era activates). The TODO comments explicitly acknowledge the validation is incomplete, confirming this is a known gap in a live code path, not a theoretical concern. [9](#0-8) 

### Recommendation

1. **`validatePerasCert`** must verify: (a) the aggregate BLS signature over `(pcRoundNo, pcBoostedBlock)` against the aggregated public keys of the claimed voter set; (b) that the voter set meets the quorum threshold; (c) that each voter in the set was eligible (persistent membership or valid VRF proof); (d) that `pcRoundNo` is within the valid range for the current era. Until this is implemented, the function must not be reachable from the network-facing certificate ingest path.

2. **`validatePerasVote`** must verify the vote's cryptographic signature (via `verifyVoteSignature`) in addition to the stake lookup, to prevent forged votes from accumulating into a fake quorum.

3. Consider gating the object diffusion mini-protocol handlers for Peras certificates and votes behind a runtime check that Peras is actually active, so that the incomplete validation stubs cannot be reached before the full implementation is in place.

### Proof of Concept

1. Connect to a target node with Peras enabled as an unprivileged peer via the object diffusion mini-protocol.
2. Identify a block `B` in the VolatileDB of the target node (e.g., via ChainSync) that is on a minority fork.
3. Craft a `PerasCert { pcCertRound = R, pcCertBoostedBlock = point(B) }` with any `R` not yet in the target's `PerasCertDB`.
4. Send the certificate to the target node. `processCerts` calls `validatePerasCert`, which returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight mkPerasParams }` without any signature check.
5. `addPerasCertAsync` enqueues the certificate; `chainSelSync` stores it and calls `chainSelectionForBlock` for `B`.
6. `constructPreferableCandidates` computes `wsvTotalWeight` for the fork containing `B` as `blockNo(B) + vpcCertBoost`. If `vpcCertBoost` is large enough, `preferCandidate` returns `ShouldSwitch`, and the node adopts the minority fork.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

-- Process a Peras certificate by adding it to the PerasCertDB and potentially
-- performing chain selection if a candidate is now better than our selection.
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```

wsvTotalWeight :: WeightedSelectView proto -> PerasWeight
-- could be cached, but then we need to be careful to maintain the invariant
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv

instance Ord (TiebreakerView proto) => Ord (WeightedSelectView proto) where
  compare =
    mconcat
      [ compare `on` wsvTotalWeight
      , compare `on` wsvTiebreaker
      ]

data WeightedSelectViewReasonForSwitch p
  = Heavier (Comparing PerasWeight)
  | WeightedSelectViewTiebreak (ReasonForSwitch (TiebreakerView p))

deriving instance
  Show (ReasonForSwitch (TiebreakerView p)) => Show (WeightedSelectViewReasonForSwitch p)

instance ChainOrder (TiebreakerView proto) => ChainOrder (WeightedSelectView proto) where
  type ChainOrderConfig (WeightedSelectView proto) = ChainOrderConfig (TiebreakerView proto)
  type ReasonForSwitch (WeightedSelectView proto) = WeightedSelectViewReasonForSwitch proto

  preferCandidate cfg ours cand =
    case compare (wsvTotalWeight ours) (wsvTotalWeight cand) of
      LT -> ShouldSwitch (Heavier $ Comparing (wsvTotalWeight ours) (wsvTotalWeight cand))
      EQ -> case preferCandidate cfg (wsvTiebreaker ours) (wsvTiebreaker cand) of
        ShouldSwitch r -> ShouldSwitch (WeightedSelectViewTiebreak r)
        ShouldNotSwitch o -> ShouldNotSwitch o
      GT -> ShouldNotSwitch GT
