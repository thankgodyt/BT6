### Title
Integer Division Truncation in `get_protocol_and_relayer_fee` Silently Zeroes Protocol Fee — (`contracts/satoshi-bridge/src/config.rs`)

---

### Summary

`BridgeFee::get_protocol_and_relayer_fee` performs an unguarded integer division that truncates to zero whenever `fee_amount * protocol_fee_rate < MAX_RATIO`. When this happens the protocol receives **zero** of its expected fee share and the entire collected fee is credited to the relayer. A bridge user can deliberately choose a deposit or withdrawal amount that triggers this truncation on every transaction, permanently bypassing the protocol-fee policy.

---

### Finding Description

`BridgeFee` in `config.rs` exposes two fee helpers:

```rust
pub const MAX_RATIO: u32 = 10000;

pub fn get_fee(&self, amount: u128) -> u128 {
    std::cmp::max(
        amount * u128::from(self.fee_rate) / u128::from(MAX_RATIO),
        self.fee_min,          // ← floor prevents total-fee from reaching 0
    )
}

pub fn get_protocol_and_relayer_fee(&self, fee_amount: u128) -> (u128, u128) {
    let protocol_fee =
        fee_amount * u128::from(self.protocol_fee_rate) / u128::from(MAX_RATIO);
    let relayer_fee = fee_amount - protocol_fee;   // ← no floor; protocol_fee can be 0
    (protocol_fee, relayer_fee)
}
```

`get_fee` is protected by `fee_min` via `std::cmp::max`, so the **total** fee charged to the user is always at least `fee_min`. However, `get_protocol_and_relayer_fee` has **no analogous floor**. When `fee_amount * protocol_fee_rate < MAX_RATIO`, Rust integer division truncates `protocol_fee` to `0`, and `relayer_fee` absorbs the entire `fee_amount`.

This function is called in both critical fee-collection paths:

- **Deposit path** — `internal_verify_deposit` in `btc_light_client/deposit.rs` (lines 52–56):
  ```rust
  let deposit_fee = config.deposit_bridge_fee.get_fee(deposit_amount);
  let (protocol_fee, relayer_fee) = config
      .deposit_bridge_fee
      .get_protocol_and_relayer_fee(deposit_fee);
  ```
- **Withdrawal path** — `verify_withdraw_burn_promise` in `nbtc/burn.rs` (lines 14–16):
  ```rust
  let (protocol_fee, relayer_fee) = config
      .withdraw_bridge_fee
      .get_protocol_and_relayer_fee(btc_pending_info.withdraw_fee);
  ```

**Concrete numeric example** (realistic mainnet parameters):

| Parameter | Value |
|---|---|
| `fee_rate` | 100 (1 %) |
| `protocol_fee_rate` | 10 (0.1 %) |
| `fee_min` | 1 000 satoshis |
| `deposit_amount` | 500 000 satoshis (0.005 BTC) |

`deposit_fee = max(500 000 × 100 / 10 000, 1 000) = max(5 000, 1 000) = 5 000`

`protocol_fee = 5 000 × 10 / 10 000 = 50 000 / 10 000 = 5` — non-zero here.

Now with `protocol_fee_rate = 1` (0.01 %) and `deposit_amount = 500 000`:

`protocol_fee = 5 000 × 1 / 10 000 = 5 000 / 10 000 = 0` ← truncates to zero.

The user still pays 5 000 satoshis in fees, but the protocol receives **none** of it; the relayer takes all 5 000.

---

### Impact Explanation

Every deposit and withdrawal where `fee_amount * protocol_fee_rate < MAX_RATIO` silently credits `protocol_fee = 0` to the bridge contract while the relayer receives the full fee. The `acc_collected_protocol_fee` and `cur_available_protocol_fee` accumulators are only incremented when `protocol_fee.0 > 0` (see `mint_callback` line 59 and `verify_withdraw_burn_callback` line 135), so the protocol's accounting is permanently understated. Over time this constitutes a systematic, attacker-controllable bypass of the protocol-fee policy — matching the **Medium: Bypass of bridge limits or policies** impact class.

---

### Likelihood Explanation

The condition is easy to reach. A user only needs to pick a deposit or withdrawal amount such that the resulting `fee_amount` (which is bounded below by `fee_min`, a small satoshi value) satisfies `fee_amount * protocol_fee_rate < 10 000`. With a low `protocol_fee_rate` (e.g., 1–10 basis points, which is competitive) and a `fee_min` in the hundreds-of-satoshis range, the truncation fires for any deposit below a few hundred thousand satoshis — a range that is entirely within normal bridge usage. No special privilege is required; any NEAR account that can call `verify_deposit_v2` or `ft_transfer_call` can trigger this path.

---

### Recommendation

Apply the same `fee_min`-style floor to the protocol-fee split, or use ceiling division for `protocol_fee`:

```rust
pub fn get_protocol_and_relayer_fee(&self, fee_amount: u128) -> (u128, u128) {
    // Ceiling division: ensures protocol_fee >= 1 whenever protocol_fee_rate > 0
    let protocol_fee = if self.protocol_fee_rate == 0 || fee_amount == 0 {
        0
    } else {
        (fee_amount * u128::from(self.protocol_fee_rate) + u128::from(MAX_RATIO) - 1)
            / u128::from(MAX_RATIO)
    };
    let relayer_fee = fee_amount.saturating_sub(protocol_fee);
    (protocol_fee, relayer_fee)
}
```

Alternatively, add a `protocol_fee_min` field to `BridgeFee` and apply `std::cmp::max` symmetrically with `get_fee`.

---

### Proof of Concept

1. Bridge is configured with `protocol_fee_rate = 1` (0.01 %), `fee_rate = 100` (1 %), `fee_min = 1000` satoshis.
2. User submits a valid BTC deposit of 500 000 satoshis (0.005 BTC) via `verify_deposit_v2`.
3. `get_fee(500_000)` → `max(5_000, 1_000)` = **5 000** satoshis total fee charged.
4. `get_protocol_and_relayer_fee(5_000)` → `protocol_fee = 5_000 × 1 / 10_000 = 0`.
5. `mint_callback` checks `if protocol_fee.0 > 0` — condition is false, so `acc_collected_protocol_fee` is **not incremented**.
6. Relayer receives all 5 000 satoshis; protocol receives 0.
