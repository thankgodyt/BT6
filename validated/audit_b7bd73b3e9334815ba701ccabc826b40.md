### Title
`safe_mint` Silently Discards Minted nBTC When Recipient Account Is Unregistered, Causing Permanent Fund Loss - (File: contracts/nbtc/src/lib.rs)

### Summary

The `safe_mint` function in the nBTC token contract mints tokens to the bridge's own account first, then silently returns `U128(0)` without transferring to the user if the recipient's storage account is not registered. No accounting entry records the shortfall. The minted nBTC is permanently stranded in the bridge's balance with no recovery path for the user.

### Finding Description

`safe_mint` in `contracts/nbtc/src/lib.rs` follows this sequence:

1. `self.token.internal_deposit(&self.bridge_id, amount.into())` — unconditionally mints `amount` nBTC into the bridge's own token balance, increasing total supply.
2. `if self.token.accounts.get(&account_id).is_none() { return PromiseOrValue::Value(U128(0)); }` — if the recipient has no registered storage account, the function returns zero silently, without reverting, without transferring, and without recording any debt. [1](#0-0) 

The minted tokens remain credited to `bridge_id` in the FT ledger. There is no `lost_found` entry created in the nBTC contract for this case, and the satoshi-bridge's `lost_found` map (populated only by `transfer_nbtc_callback` on failed `ft_transfer` calls) is never touched by this code path. [2](#0-1) 

The `safe_mint` function is gated by `assert_bridge()`, meaning it is called exclusively by the satoshi-bridge contract during the deposit/minting flow. [3](#0-2) 

### Impact Explanation

A user who deposits BTC to the bridge but whose NEAR account has not registered storage for the nBTC token will have their deposit processed (BTC locked in the bridge's MPC-controlled address), nBTC minted into the bridge's own balance (total supply increases), and yet receive zero nBTC. The minted tokens are permanently stranded in the bridge's nBTC balance with no on-chain record that they are owed to the user. The user's BTC is locked and their nBTC is unrecoverable without manual operator intervention — a permanent loss of user funds matching the **Medium** impact category (stuck bridge state requiring operator intervention) and potentially **Critical** (permanent locking of user funds).

### Likelihood Explanation

Any depositor whose NEAR account is not pre-registered for nBTC storage triggers this path. NEAR's storage-staking model requires explicit `storage_deposit` before receiving NEP-141 tokens. A first-time bridge user who deposits BTC without first calling `storage_deposit` on the nBTC contract will silently lose their deposit. This is a realistic, unprivileged, publicly reachable scenario requiring no special access.

### Recommendation

Replace the silent early-return with either:
- A hard `require!` / `panic` that reverts the entire `safe_mint` call when the recipient is unregistered (so the bridge can handle the failure and refund the user), or
- Auto-register the recipient's storage account before minting (analogous to `mint_inner` which calls `internal_register_account` if needed).

The `mint_inner` helper already demonstrates the correct pattern: [4](#0-3) 

`safe_mint` should adopt the same auto-registration approach, or revert on missing registration, rather than silently discarding the minted tokens.

### Proof of Concept

1. User Alice deposits 0.01 BTC to the bridge. Her NEAR account `alice.near` has never called `storage_deposit` on the nBTC contract.
2. The bridge's deposit verification succeeds and calls `safe_mint(alice.near, 1_000_000, None)` on the nBTC contract.
3. `internal_deposit(&bridge_id, 1_000_000)` executes — bridge's nBTC balance increases by 1,000,000 satoshis, total supply increases.
4. `self.token.accounts.get(&alice.near)` returns `None` (no storage registration).
5. `safe_mint` returns `PromiseOrValue::Value(U128(0))` — no transfer, no error, no `lost_found` entry.
6. Alice receives 0 nBTC. Her 0.01 BTC is locked in the bridge's MPC address. The 1,000,000 nBTC sits in the bridge's own balance with no accounting record linking it to Alice. [5](#0-4)

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }

    #[private]
    pub fn transfer_nbtc_callback(&mut self, account_id: AccountId, amount: U128) -> bool {
        let promise_success = is_promise_success();
        let event = Event::TransferNbtc {
            account_id: &account_id,
            amount,
            success: promise_success,
        };
        if !promise_success {
            self.data_mut()
                .lost_found
                .entry(account_id.clone())
                .and_modify(|v| *v += amount.0)
                .or_insert(amount.0);
            Event::LostFoundNbtc {
                account_id: &account_id,
                amount,
            }
            .emit();
        }
        event.emit();
        promise_success
    }
