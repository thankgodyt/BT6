### Title
Unregistered Recipient in `safe_mint` Causes Permanent Loss of Minted nBTC — (File: `contracts/nbtc/src/lib.rs`)

### Summary
In `contracts/nbtc/src/lib.rs`, the `safe_mint` function unconditionally deposits the full minted amount into `bridge_id`'s token balance **before** checking whether the recipient account is registered. If the recipient is not registered, the function returns `U128(0)` and exits — leaving the minted tokens permanently stranded in the bridge's own nBTC balance with no recovery path. The user's BTC deposit is simultaneously locked in the bridge's verified UTXO set, blocking any refund. This is the direct analog of the ERC20Rebasing bug: a state check (registration vs. Claimable mode) causes the pending/accumulated amount to be silently dropped instead of preserved.

### Finding Description
`safe_mint` in `contracts/nbtc/src/lib.rs` follows this sequence:

1. `self.token.internal_deposit(&self.bridge_id, amount.into())` — mints `amount` tokens into `bridge_id`'s balance unconditionally.
2. `if self.token.accounts.get(&account_id).is_none() { return PromiseOrValue::Value(U128(0)); }` — if the recipient is unregistered, the function returns immediately. [1](#0-0) 

The tokens are now credited to `bridge_id` (the bridge contract's own nBTC account). No `FtMint` event is emitted for the user, no `lost_found` entry is created, and no retry or claim mechanism exists. The minted tokens are silently absorbed into the bridge's balance.

The `burn` function later withdraws from `bridge_id` to settle withdrawals: [2](#0-1) 

This means the stranded tokens can be consumed by a future unrelated withdrawal, permanently destroying the accounting link to the original depositor.

On the bridge side, once a deposit is verified the UTXO is added to `verified_deposit_utxo`, which blocks any subsequent `request_refund`: [3](#0-2) 

So the user has no recourse: their BTC is locked in the verified UTXO pool and their nBTC is stranded in `bridge_id`.

### Impact Explanation
**Critical — Significant loss of user funds.**

A depositor whose NEAR account is not registered in the nBTC contract loses their entire deposit: the BTC is locked in the bridge's UTXO pool (marked verified, blocking refund) and the corresponding nBTC is minted into the bridge's own balance rather than the user's. The user receives nothing. The stranded nBTC can later be silently consumed by an unrelated withdrawal, making the bridge undercollateralized by exactly that amount.

### Likelihood Explanation
**Medium.** Any user who sends BTC to a deposit address derived from a NEAR account that has not yet called `storage_deposit` on the nBTC contract will trigger this path. This is a realistic scenario: users may generate a deposit address before completing NEAR-side registration, or a relayer may submit the proof before the user registers. The `safe_mint` entrypoint exists precisely to handle this case, but its current implementation silently destroys funds instead of deferring them.

### Recommendation
The deposit to `bridge_id` must not occur before confirming the recipient is registered, or the stranded amount must be recoverable. Two safe approaches:

1. **Check registration first:** Move the `accounts.get(&account_id).is_none()` guard before `internal_deposit`. If the user is unregistered, return early without minting anything, and let the bridge record the amount in `lost_found` for later claim.
2. **Preserve via `lost_found`:** If the deposit to `bridge_id` must happen first (e.g., for atomicity), add the stranded amount to the bridge's `lost_found` map keyed by `account_id` so the user can claim it after registering.

### Proof of Concept
1. Alice generates a deposit address derived from her NEAR account `alice.near` but has not yet called `storage_deposit` on the nBTC contract.
2. Alice sends 1 BTC to the deposit address.
3. A relayer submits the Merkle inclusion proof; the bridge verifies it and adds the UTXO to `verified_deposit_utxo`.
4. The bridge calls `safe_mint(alice.near, 100_000_000, None)` on the nBTC contract.
5. Inside `safe_mint`: `internal_deposit(&bridge_id, 100_000_000)` executes — 1 nBTC is now in the bridge's own balance.
6. `accounts.get(&alice.near)` returns `None` → function returns `U128(0)`.
7. Alice's account has 0 nBTC. Her UTXO is in `verified_deposit_utxo`, so `request_refund` panics with "UTXO already verified via deposit".
8. Alice's 1 BTC is permanently locked; the 1 nBTC sits in `bridge_id` and will be consumed by the next unrelated withdrawal burn. [4](#0-3) [5](#0-4)

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }
