### Title
Unconditional Peras Certificate Acceptance Allows Unprivileged Peer to Manipulate Chain Selection via Fake Weight Boosts — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The universal `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` for every inbound certificate, performing no cryptographic or committee-membership verification. Because the production NTN cert-diffusion handler wires this stub directly into `ChainDB.addPerasCertAsync`, any unprivileged peer can inject an arbitrary `PerasCert` that is stored in the `PerasCertDB` and triggers chain selection with a full Peras weight boost applied to the attacker-chosen block. This is the direct analog of M-10: a caller-controlled parameter (the certificate's boosted-block pointer) is trusted without whitelisting, and an unbounded privilege (the full `perasWeight` boost) is granted to it.

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub wired into production:**

The universal instance of `BlockSupportsPeras` (the only instance in the codebase, covering all block types including Cardano blocks) implements `validatePerasCert` as:

```haskell

  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No aggregate-signature check, no committee-membership check, no VRF proof check — every certificate is accepted and assigned the full `perasWeight` boost.

**`processCerts` — accepts the batch and calls `addPerasCertAsync`:**

`processCerts` calls `validateCert` on each inbound cert; since `validatePerasCert` always returns `Right`, the `([], validatedCerts)` branch is always taken and every cert is forwarded to `addCert`. [4](#0-3) 

**`chainSelSync` — the accepted cert triggers chain selection with the weight boost:**

```haskell

The `weights` (`PerasWeightSnapshot`) fed into `preferAnchoredCandidate` is derived from the `PerasCertDB`, so the injected certificate's boost is included in the comparison. [6](#0-5) 

### Impact Explanation

An unprivileged peer can craft a `PerasCert` whose `pcCertBoostedBlock` points to any block currently in the node's VolatileDB (i.e., any block on a competing fork). Because `validatePerasCert` performs no verification, the certificate is stored and the full `perasWeight` boost is applied to that block during chain selection. If the boosted block is the tip of an adversarial fork, the node may switch to that fork even though it would otherwise be rejected by the standard Praos longest-chain rule. This is a **High** chain-selection bug: an unprivileged peer can make an honest node prefer a non-canonical chain beyond the intended security assumptions of Ouroboros Peras.

### Likelihood Explanation

The attack requires only a standard NTN peer connection — no keys, no stake, no privileged access. The `PerasCertDiffusion` mini-protocol is unconditionally enabled in `mkHandlers` for every peer. The attacker needs to know (or guess) the hash of a block in the target node's VolatileDB, which is publicly observable via ChainSync. The attack is therefore trivially reachable by any node on the network.

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
1. Verifies the aggregate BLS vote signature against the committee's aggregate verification key.
2. Checks that the claimed voters are legitimate committee members for the given round (using the epoch nonce and stake distribution).
3. Verifies VRF eligibility proofs for non-persistent members.
4. Confirms the certificate's quorum threshold is met.

Until the real implementation is ready, the cert-diffusion inbound handler should be disabled or gated behind a feature flag so that no peer-supplied certificate can reach `ChainDB.addPerasCertAsync`.

### Proof of Concept

1. Attacker node connects to victim via NTN and learns a block hash `H` on a competing fork (via ChainSync).
2. Attacker sends a `PerasCertDiffusion` batch containing one `PerasCert { pcCertRound = R, pcCertBoostedBlock = H }`.
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }`.
4. `ChainDB.addPerasCertAsync` enqueues `ChainSelAddPerasCert`.
5. `chainSelSync` finds block `H` in the VolatileDB, calls `chainSelectionForBlock` with the boosted weight.
6. `preferAnchoredCandidate` now sees the adversarial fork as heavier; the node switches to it. [7](#0-6) [8](#0-7) [3](#0-2) [5](#0-4)

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
