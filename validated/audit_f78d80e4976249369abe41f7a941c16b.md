### Title
Peras Certificate Validation Completely Bypassed — Any Peer-Supplied Certificate Accepted Unconditionally - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `validatePerasCert` implementation in `BlockSupportsPeras.hs` is a stub that unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or structural validation. Because this function sits directly on the inbound certificate processing path from untrusted peers, any peer can inject a crafted `PerasCert` with an arbitrary round number and an arbitrary boosted-block point. The accepted certificate is stored and applied to chain selection, giving the attacker-chosen block a Peras weight boost that can cause an honest node to prefer an adversarial chain.

### Finding Description

**Root cause — unconditional acceptance in `validatePerasCert`:**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No round-number range check, no quorum-proof check, no BLS/committee-signature check, and no boosted-block existence check is performed. The function is the sole validation gate before a certificate is stamped `ValidatedPerasCert` and forwarded into the node's storage and chain-selection logic.

**Inbound path from an unprivileged peer:**

1. A remote peer sends a `PerasCert` message over the ObjectDiffusion mini-protocol.
2. `makePerasVotePoolWriterFromChainDB` (or the `VoteDB` variant) constructs an `ObjectPoolWriter` whose `opwAddObjects` calls `processCerts` with `validatePerasCert mkPerasParams` as the validator. [2](#0-1) 

3. `processCerts` filters out already-known round numbers, then calls `validateCert` on each remaining certificate. Because `validatePerasCert` always returns `Right`, every novel certificate passes. [3](#0-2) 

4. The `ValidatedPerasCert` (carrying `vpcCertBoost = perasWeight params`) is timestamped and added to the ChainDB via `ChainDB.addPerasCertAsync`.

**Chain-selection consequence:**

The Peras weight snapshot is read during `chainSelectionForBlock` and passed into `constructPreferableCandidates` / `weightedSelectView`. A certificate boosting block `B` adds `perasWeight` to `B`'s `SelectView`, making the chain containing `B` preferred over equally-long or even slightly-longer honest chains. [4](#0-3) 

**Analog to the external report:**

The external report's `cooldown()` is missing `whenNotPaused` — a guard that should block the function during a specific protocol state. Here, `validatePerasCert` is missing *all* guards — the checks that should block acceptance of certificates that lack a valid quorum proof, a valid round number, or a valid boosted-block reference. In both cases a function that must enforce a critical invariant before mutating protocol state simply does not do so, and an unprivileged actor can exploit the gap.

### Impact Explanation

**Critical — bypass of Peras certificate validation enabling unauthorized certificate acceptance and chain-selection manipulation.**

An unprivileged peer can craft a `PerasCert` that:
- Claims any `pcCertRound` (e.g., the current round, forcing VR-1A / VR-2B voting-rule paths to behave as if a legitimate quorum was reached).
- Claims any `pcCertBoostedBlock` (e.g., the tip of an adversarial fork).

The boosted block receives `perasWeight` in chain selection. If the adversarial chain is within the `k`-block rollback window and the weight boost tips the `preferAnchoredCandidate` comparison, the honest node switches to the adversarial chain. This is a direct chain-selection safety failure triggered by a single crafted network message.

This matches the allowed impact: *"Critical. Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance."*

### Likelihood Explanation

**High.** The ObjectDiffusion mini-protocol is a standard peer-to-peer channel; any connected peer can send `PerasCert` messages. No stake, no keys, and no prior relationship are required. The attacker needs only to:
1. Connect to the target node.
2. Send a `PerasCert` whose `pcCertRound` has not yet been seen by the node (trivially satisfied for any future round).
3. Set `pcCertBoostedBlock` to the tip of the adversarial chain.

The stub is present in the current production source tree and is guarded only by a `TODO` comment referencing issue #120.

### Recommendation

Replace the stub with a real implementation of `validatePerasCert` that enforces at minimum:

1. **Round-number validity**: the certificate's round must correspond to a completed Peras round within the current era.
2. **Quorum-proof verification**: the certificate must carry a valid aggregate BLS signature (or equivalent) from a committee whose combined stake exceeds the quorum threshold.
3. **Boosted-block existence**: `pcCertBoostedBlock` must refer to a block that is at least `perasBlockMinSlots` old and present on the node's chain.
4. **Single-certificate-per-round**: reject a certificate whose round is already present in the DB (this check already exists in `processCerts`, but the validation itself must be sound first).

Until the real implementation is available, the ObjectDiffusion certificate ingestion path should be disabled or gated behind a feature flag so that no peer-supplied certificate can influence chain selection.

### Proof of Concept

**Setup:** A private two-node testnet with Peras enabled. Node A is the honest node; Node B is the attacker.

1. Node B connects to Node A via the ObjectDiffusion mini-protocol.
2. Node B constructs a `PerasCert`:
   ```
   PerasCert { pcCertRound    = <current round>
             , pcCertBoostedBlock = <tip of adversarial fork> }
   ```
3. Node B sends the certificate to Node A.
4. `processCerts` on Node A calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams })`.
5. The certificate is stored. On the next `chainSelectionForBlock` trigger, `weightedSelectView` adds `perasWeight` to the adversarial fork's `SelectView`.
6. If the adversarial fork is within `k` blocks of Node A's current tip, `preferAnchoredCandidate` now returns `ShouldSwitch` for the adversarial chain, and Node A adopts it.

**Expected (correct) outcome:** Step 4 should return `Left PerasValidationErr` because the certificate carries no valid quorum proof.
**Actual outcome:** Step 4 returns `Right`, the certificate is accepted, and chain selection is manipulated. [5](#0-4) [6](#0-5) [4](#0-3)

  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch

chainSelectionForBlock cdb@CDB{..} blockCache hdr punish = electric $ do
  (invalid, curChain, weights) <-
    atomically $
      (,,)
        <$> (forgetFingerprint <$> readTVar cdbInvalid)
        <*> Query.getCurrentChain cdb
        <*> (forgetFingerprint <$> Query.getPerasWeightSnapshot cdb)

  -- The current chain we're working with here is not longer than @k@ blocks
  -- (see 'getCurrentChain' and 'cdbChain'), which is easier to reason about
  -- when doing chain selection, etc.
  assert (fromIntegral (AF.length curChain) <= unNonZero k) pure ()

  let
    immBlockNo :: WithOrigin BlockNo
    immBlockNo = AF.anchorBlockNo curChain

  if
    -- The chain might have grown since we added the block such that the
    -- block is older than the immutable tip.
    | olderThanImmTip hdr immBlockNo -> do
        traceWith addBlockTracer $ IgnoreBlockOlderThanImmTip p

    -- The block is invalid
    | Just (InvalidBlockInfo reason _) <- Map.lookup (headerHash hdr) invalid -> do
        traceWith addBlockTracer $ IgnoreInvalidBlock p reason

        -- We wouldn't know the block is invalid if its prefix was invalid,
        -- hence 'InvalidBlockPunishment.BlockItself'.
        InvalidBlockPunishment.enact
          punish
          InvalidBlockPunishment.BlockItself

    -- Try to select a chain involving the block.
    | otherwise -> do
        -- Construct all 'ChainDiff's involving the block.
        chainDiffs <-
          constructPreferableCandidates
            cdb
            weights
            curChain
            (Map.singleton (headerHash hdr) hdr)
            (headerRealPoint hdr)

        let traceNoChange = traceWith addBlockTracer $ StoreButDontChange p

            chainSelEnv = mkChainSelEnv cdb blockCache weights curChain (Just (p, punish))

        case NE.nonEmpty chainDiffs of
          Just chainDiffs' -> do
            -- Find the best valid candidate and, if valid, perform a
            -- switch. Log if none were found.
            flip whenNothing traceNoChange
              =<< chainSelection
                chainSelEnv
                chainDiffs'
                (switchTo cdb weights (Just p))
          -- No candidate better than our chain.
          Nothing -> traceNoChange
