### Title
Pausing the Contract While Withdrawals Are In `PendingSign` State Locks User nBTC with No Self-Service Recovery — (File: `contracts/satoshi-bridge/src/api/token_receiver.rs`, `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

When the satoshi-bridge contract is paused while a user's withdrawal is in `PendingSign` state — meaning nBTC has already been transferred to the bridge and UTXOs have been locked — the user has no self-service recovery path. All relevant functions (`sign_btc_transaction`, `cancel_withdraw`, `claim_lost_found`) are paused for non-DAO accounts. The `lost_found` mapping is never updated for in-flight withdrawals, leaving user funds stuck until DAO intervention. This is the direct analog to the Omni bridge's unsafe pause ordering issue.

---

### Finding Description

The withdrawal flow in the satoshi-bridge proceeds as follows:

1. User calls `ft_transfer_call` on the nBTC token → triggers `ft_on_transfer` on the bridge.
2. `ft_on_transfer` creates a `BTCPendingInfo` with state `WithdrawOriginal(PendingSign)`, moves UTXOs to `unavailable_utxos`, and retains the nBTC (returns `U128(0)` to the token resolver, keeping all tokens).
3. `sign_btc_transaction` is called to sign the PSBT via MPC.
4. The signed Bitcoin transaction is broadcast.
5. `verify_withdraw_v2` verifies on-chain inclusion and burns the nBTC.

Every function in this pipeline carries `#[pause(except(roles(Role::DAO)))]`: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

If the contract is paused after step 2 completes (nBTC committed, UTXOs locked) but before step 3 (signing):

- `sign_btc_transaction` is paused → the withdrawal cannot proceed.
- `cancel_withdraw` requires `Role::DAO` or `Role::Operator` via `#[access_control_any]`, **and** is paused for non-DAO accounts — so even the Operator is blocked when the contract is paused.
- `claim_lost_found` is paused → the user cannot claim even if they had a `lost_found` balance.

Critically, the `lost_found` mapping is **never updated** for in-flight withdrawals when the contract is paused. The only path that populates `lost_found` for a withdrawal is the `transfer_nbtc_callback` inside `cancel_withdraw`'s downstream flow: [6](#0-5) 

Since `cancel_withdraw` itself is inaccessible to non-DAO accounts when paused, this recovery path is never reached. There is no mechanism to ensure safe pause ordering (e.g., draining pending `PendingSign` withdrawals before pausing, or pausing `ft_on_transfer` first).

The `BTCPendingInfo` state machine confirms the stuck state — `PendingSign` has no self-service exit: [7](#0-6) 

---

### Impact Explanation

User nBTC is held by the bridge contract with no self-service recovery path. UTXOs are locked in `unavailable_utxos`. The `lost_found` mapping is not updated. The bridge is in a stuck state that requires DAO intervention to resolve — matching the allowed impact: **Medium. Harmful smart-contract behavior without direct funds theft, including stuck bridge state requiring operator intervention.**

If the DAO is slow to respond or unavailable (e.g., multi-sig quorum not reachable during the same emergency that triggered the pause), the stuck state can persist indefinitely.

---

### Likelihood Explanation

The `PauseManager` role can pause the contract at any time. Emergency pauses are precisely the scenarios where in-flight withdrawals are most likely to exist. The window between `ft_on_transfer` completing (nBTC committed) and `sign_btc_transaction` being called is non-zero — MPC signing is an asynchronous cross-contract call. Any pause during this window triggers the stuck state. This is a realistic operational scenario.

---

### Recommendation

1. **Safe pause ordering**: Before pausing, ensure all `BTCPendingInfo` entries in `PendingSign` state are either signed-through or cancelled by the Operator.
2. **User self-service cancel**: Implement a user-callable cancel path (analogous to the `OmniGasPump.owed` mapping suggested in the original report) that is accessible even when the contract is paused, so users can reclaim their nBTC without DAO intervention.
3. **Populate `lost_found` on pause**: When the contract is paused, update the `lost_found` mapping for all in-flight `PendingSign` withdrawals so users can claim their nBTC once unpaused.
4. **Document safe pause procedures** in offchain operator tooling, mirroring the Omni team's planned offchain checks.

---

### Proof of Concept

1. User calls `ft_transfer_call(bridge_id, 1_000_000, withdraw_msg)` on the nBTC token.
2. `ft_on_transfer` succeeds: `BTCPendingInfo` created with state `WithdrawOriginal(PendingSign)`, UTXOs moved to `unavailable_utxos`, nBTC held by bridge.
3. `PauseManager` calls `pa_pause_feature("ALL")` (emergency pause).
4. User calls `sign_btc_transaction(btc_pending_sign_id, 0, key_version)` → **panics**: "Pausable: method is paused".
5. User calls `cancel_withdraw(btc_pending_sign_id, output)` → **panics**: access control check fails (user lacks `Role::DAO`/`Role::Operator`), and even if they had `Operator`, the pause blocks it.
6. User calls `claim_lost_found()` → **panics**: "Pausable: method is paused".
7. User's 1,000,000 satoshi-equivalent nBTC is stuck in the bridge contract. `lost_found` is never populated. Recovery requires DAO to unpause and manually call `cancel_withdraw`. [8](#0-7) [9](#0-8) [10](#0-9)
