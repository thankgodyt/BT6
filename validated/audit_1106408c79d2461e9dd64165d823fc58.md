### Title
Unconstrained Caller in `request_refund` Enables BTC Theft via Refund Hijacking — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary
The `request_refund` function imposes no check that the caller is the intended deposit recipient (`deposit_msg.recipient_id`). When a deposit was made with `deposit_msg.refund_address = None`, any unprivileged NEAR account can submit a refund request pointing to an attacker-controlled BTC address. After the `unsafe_refund_timelock_sec` elapses, the attacker can call `execute_refund` and receive the victim's BTC.

### Finding Description

`request_refund` is a public, payable function with no `#[trusted_relayer]` attribute on the method itself: [1](#0-0) 

The impl block carries `#[trusted_relayer]` at the block level, but every method in the first impl block that is actually gated (e.g., `verify_deposit`, `verify_deposit_v2`, `safe_verify_deposit`) carries `#[trusted_relayer]` on the method itself as well. Within the refund impl block, `verify_refund_finalize` and `remove_refund_pending_tx_id` carry the per-method attribute, while `request_refund` and `execute_refund` do not — confirming the impl-level attribute is configuration, not an access gate on those two methods. [2](#0-1) 

Inside `internal_request_refund`, the only guard on `refund_address` is:

> If `deposit_msg.refund_address` is `Some`, it must equal the provided `refund_address`. [3](#0-2) 

When `deposit_msg.refund_address` is `None` (a common case — the field is optional), the provided `refund_address` is accepted verbatim with no ownership check: [4](#0-3) 

The callback verifies only that the on-chain output script matches the deposit address derived from `deposit_msg`, not that the caller has any relationship to the deposit: [5](#0-4) 

The stored `RefundRequest` records the attacker-supplied `refund_address` and is later used verbatim to build the PSBT output in `execute_refund` → `finalize_refund_with_psbt` → `build_refund_output`: [6](#0-5) 

`execute_refund` is also public and payable with no per-method `#[trusted_relayer]`: [7](#0-6) 

The deposit path is derived from the full JSON of `deposit_msg` (including `recipient_id`), so the attacker cannot change `recipient_id` without invalidating the script-pubkey check. However, because `refund_address` is serialized with `skip_serializing_if = "Option::is_none"`, a `deposit_msg` with `refund_address: None` hashes identically regardless of who calls `request_refund`: [8](#0-7) 

### Impact Explanation

An attacker who observes a confirmed BTC deposit whose `deposit_msg.refund_address` is `None` (and whose `verify_deposit` has not yet been called) can submit `request_refund` with their own BTC address. Once `unsafe_refund_timelock_sec` elapses and the DAO has not rejected the request, the attacker calls `execute_refund`. The MPC signs a PSBT paying the attacker's address, and the victim's BTC is permanently transferred to the attacker. This constitutes significant, irreversible loss of user funds.

            refund_address,
            tx_bytes,
            vout,

        )
    }
