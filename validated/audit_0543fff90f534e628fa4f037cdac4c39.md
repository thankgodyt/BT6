### Title
Inverted `ft_transfer_call` Return-Value Check in `is_refund_required` Causes Successful Safe-Deposits to Be Treated as Failures - (File: contracts/satoshi-bridge/src/btc_light_client/deposit.rs)

### Summary

`is_refund_required()` misreads the NEP-141 `ft_transfer_call` return-value convention. When `safe_mint` is called with a non-empty `msg` (the OmniBridge forwarding path), a return value of `0` from `safe_mint` means **all tokens were successfully consumed** by the receiver — yet the check `amount.0 == 0` treats this as a failure. The result is that every successful safe-deposit with a forwarding message is rolled back: the UTXO is removed from `verified_deposit_utxo`, a burn is attempted from the bridge account (which silently fails because the tokens are already with the receiver), and the UTXO becomes untracked while the receiver retains the minted nBTC.

### Finding Description

**`safe_mint` return-value semantics** (`contracts/nbtc/src/lib.rs`, lines 101–124):

```rust
pub fn safe_mint(&mut self, account_id: AccountId, amount: U128, msg: Option<String>)
    -> PromiseOrValue<U128>
{
    self.token.internal_deposit(&self.bridge_id, amount.into());

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));   // ← failure sentinel: account not registered
    }

    if let Some(msg) = msg {
        self.ft_transfer_call(account_id, amount, None, msg)  // ← returns ft_transfer_call result
    } else {
        self.ft_transfer(account_id, amount, None);
        PromiseOrValue::Value(amount)             // ← success: returns minted amount
    }
}
```

Under NEP-141, `ft_transfer_call` returns the amount **refunded back to the sender** (i.e., the unused portion). When the receiver's `ft_on_transfer` returns `0` (all tokens consumed = **success**), `ft_transfer_call` returns `0`. When `ft_on_transfer` returns the full amount (tokens rejected = **failure**), `ft_transfer_call` returns that non-zero amount.

**`is_refund_required()` check** (`contracts/satoshi-bridge/src/btc_light_client/deposit.rs`, lines 474–489):

```rust
fn is_refund_required() -> bool {
    match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
        Ok(value) => {
            if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {
                // BUG: comment says "refund if used token amount is zero"
                // but `amount` is the REFUNDED amount, not the USED amount.
                // amount.0 == 0  →  all tokens consumed  →  SUCCESS, not failure
                amount.0 == 0
            } else { false }
        }
        Err(_) => false,
    }
}
```

The developer confused "used amount" with "refunded amount". The condition is **inverted** for the `ft_transfer_call` path:

| Scenario | `safe_mint` returns | `is_refund_required()` | `is_success` | Correct? |
|---|---|---|---|---|
| Account not registered | `0` | `true` | `false` | ✓ |
| No msg (direct transfer) | `amount` (> 0) | `false` | `true` | ✓ |
| With msg, `ft_on_transfer` returns `0` (SUCCESS) | `0` | `true` | `false` | **✗ BUG** |
| With msg, `ft_on_transfer` returns `amount` (FAILURE) | `amount` (> 0) | `false` | `true` | **✗ BUG** |

**Consequence in `safe_mint_callback`** (lines 422–468) when `is_success = false` incorrectly:

```rust
// 1. UTXO removed from verified set — now untracked
self.data_mut().verified_deposit_utxo.remove(&pending_utxo_info.utxo_storage_key);

// 2. Burn attempted from bridge account — silently fails (.detach())
//    because tokens are already with the receiver via ft_transfer_call
ext_nbtc::ext(...).burn(env::current_account_id(), mint_amount, ...).detach();

// 3. Relayer gets NEAR storage deposit back
Promise::new(env::signer_account_id()).transfer(self.required_balance_for_safe_deposit()).detach();
```

The receiver holds the minted nBTC. The UTXO is no longer in `verified_deposit_utxo`. The burn silently fails. The same BTC UTXO can now be re-submitted via `verify_deposit_v2` or `verify_deposit` to mint a second batch of nBTC against the same on-chain BTC.

### Impact Explanation

**Critical / Medium.** The immediate impact is a broken callback rollback: every safe-deposit with a non-empty forwarding `msg` that the receiver accepts (returns `0` from `ft_on_transfer`) is incorrectly unwound. The receiver retains the minted nBTC while the UTXO becomes untracked. Because `verified_deposit_utxo` no longer contains the key, a second `verify_deposit_v2` call for the same BTC transaction will pass the `insert` guard and mint a second batch of nBTC — unauthorized reminting against already-spent BTC. This breaks the 1:1 backing invariant.

### Likelihood Explanation

The bug fires on every safe-deposit where `SafeDepositMsg.msg` is non-empty and the downstream receiver's `ft_on_transfer` returns `0` (the normal success path). This is the standard OmniBridge integration flow. The entry point `verify_deposit_v2` with `deposit_msg.safe_deposit = Some(SafeDepositMsg { msg: "..." })` is gated by `#[trusted_relayer]`, so the caller must be a whitelisted relayer. However, the OmniBridge relayer itself would trigger this bug in normal operation, making it a near-certain failure on every OmniBridge deposit with a forwarding message.

### Recommendation

`is_refund_required()` must distinguish the two zero-returning cases. The simplest fix is to change `safe_mint` to return a non-zero sentinel on success when using `ft_transfer_call`, or to invert the condition for the `ft_transfer_call` path. Concretely, `safe_mint` should return `amount` (the minted amount) on success regardless of path, and reserve `U128(0)` exclusively for the "account not registered" failure:

```rust
// In nbtc/src/lib.rs safe_mint:
if let Some(msg) = msg {
    // ft_transfer_call returns the refunded amount (0 = success, non-zero = failure).
    // Wrap the result so that 0 (success) maps to `amount` and non-zero (failure) maps to 0.
    // Alternatively, use a dedicated success/failure enum return type.
    self.ft_transfer_call(account_id, amount, None, msg)
        .map(|refunded| if refunded.0 == 0 { amount } else { U128(0) })
} else { ... }
```

Or equivalently, fix `is_refund_required()` to understand that when `safe_mint` went through `ft_transfer_call`, a zero result means success, not failure — but this requires knowing which path was taken, making the `safe_mint` return-value fix cleaner.

### Proof of Concept

1. Relayer calls `verify_deposit_v2` with `deposit_msg.safe_deposit = Some(SafeDepositMsg { msg: "<omni-bridge-forwarding-msg>" })` for a valid BTC UTXO.
2. `verify_safe_deposit_callback` inserts the UTXO into `verified_deposit_utxo` and calls `safe_mint(recipient, amount, Some(msg))`.
3. `safe_mint` calls `ft_transfer_call`; the receiver's `ft_on_transfer` returns `0` (all tokens consumed — normal success). `safe_mint` returns `U128(0)`.
4. `safe_mint_callback` calls `is_refund_required()`, which reads `U128(0)` and returns `true`.
5. `is_success = false`: UTXO removed from `verified_deposit_utxo`; burn attempted from bridge (fails silently); relayer refunded.
6. Receiver holds the minted nBTC. UTXO is untracked.
7. Relayer (or anyone with relayer role) calls `verify_deposit_v2` again for the same BTC UTXO — the `verified_deposit_utxo.insert(...)` guard passes (key was removed in step 5) — a second mint of nBTC is issued against the same BTC, breaking the backing invariant.

/// Refund only if `safe_mint` returned 0. Any other outcome (non-zero
/// amount, unparseable payload, panic) is treated as "UTXO spent, no
/// refund" — for safety, to avoid a potential double spend.
fn is_refund_required() -> bool {
    match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
        Ok(value) => {
            if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {
                // Normal case: refund if the used token amount is zero
                // The amount can be zero if the `ft_on_transfer` in the receiver contract returns an amount instead of `0`, or if it panics.
                amount.0 == 0
            } else {
                // Unexpected case: don't refund
                false
            }
        }
        // Unexpected case: don't refund
        Err(_) => false,
    }
}
