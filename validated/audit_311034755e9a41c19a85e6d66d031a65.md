Audit Report

## Title
Dust-Amount Transfer Permanently Freezes Bridged Tokens Due to Missing Pre-Normalization Validation — (`near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer` applies only a `fee < amount` guard before locking or burning tokens and storing the transfer in `pending_transfers`. For tokens where `origin_decimals > decimals`, any amount below the normalization threshold (`10^(origin_decimals - decimals)`) passes this guard but causes `sign_transfer` to permanently revert on the `require!(amount_to_transfer > 0)` check. Because no public cancel or refund path exists, the locked/burned tokens are permanently frozen.

## Finding Description
**Entry point — `init_transfer`**

The only amount-level guard in `init_transfer` is: [1](#0-0) 

A transfer with `amount = 500_000` and `fee = 0` satisfies `0 < 500_000` and proceeds. Tokens are immediately burned or locked inside `init_transfer_internal`: [2](#0-1) 

The `TransferMessage` is then stored in `pending_transfers` via `add_transfer_message`: [3](#0-2) 

**Failure point — `sign_transfer`**

When a relayer calls `sign_transfer`, the bridge normalizes the net amount: [4](#0-3) 

`normalize_amount` uses floor division: [5](#0-4) 

For a token with `origin_decimals = 24` and `decimals = 18` (diff = 6), any `amount < 10^6` normalizes to `0`. The `require!` panics, reverting `sign_transfer` before the MPC call is made.

**No recovery path**

`remove_transfer_message` is only called from `sign_transfer_callback` when the MPC signature succeeds and `fee.is_zero()`: [6](#0-5) 

Since `sign_transfer` panics before reaching the MPC call, `sign_transfer_callback` is never invoked. There is no public `cancel_transfer` or user-accessible refund function. The transfer entry remains in `pending_transfers` indefinitely, and the locked/burned tokens are unrecoverable.

The `normalize_amount` code comment acknowledges dust behavior ("When fee = 0, dust stays locked/burned") but this refers to sub-unit remainders after normalization, not the case where the entire net amount normalizes to zero — a materially more severe outcome. [7](#0-6) 

## Impact Explanation
This constitutes **permanent freezing of bridged funds**: tokens are burned or locked inside the bridge contract with no mechanism to release them. This matches the Critical impact tier: "permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet, Bitcoin, Zcash, or Wormhole-routed flows." The affected user suffers complete, irreversible loss of the transferred tokens.

## Likelihood Explanation
The condition requires: (1) a token registered with `origin_decimals > decimals` (common for NEAR-native tokens with 24 decimals bridging to EVM chains with 18 decimals), and (2) a user submitting an amount below the normalization threshold. No privileged access is required — any unprivileged user can trigger this via a standard `ft_transfer_call`. The likelihood is low but non-zero, as it can occur through user error (sending raw units instead of whole tokens) or a UI that does not enforce a minimum transfer amount.

## Recommendation
Add a pre-normalization check inside `init_transfer_internal` (before locking/burning tokens) that mirrors the guard already present in `sign_transfer`:

```rust
if let Some(token_address) = self.get_token_address(
    transfer_message.get_destination_chain(),
    self.get_token_id(&transfer_message.token),
) {
    if let Some(decimals) = self.token_decimals.get(&token_address) {
        let normalized = Self::normalize_amount(
            transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
            decimals,
        );
        require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
    }
}
```

This check should be placed after the `fee < amount` guard and before the `burn_tokens_if_needed` / `lock_tokens_if_needed` calls, so that the transfer is rejected (and tokens returned to the caller via the NEP-141 `ft_on_transfer` return value) rather than locked in an unsignable state.

## Proof of Concept
1. Register a token with `origin_decimals = 24`, `decimals = 18` (diff = 6; threshold = 1,000,000 raw units).
2. Alice calls `ft_transfer_call` with `amount = 500_000` and `fee = 0`.
3. `init_transfer` checks `0 < 500_000` → passes. Tokens are burned/locked. Transfer stored in `pending_transfers`.
4. Relayer calls `sign_transfer` for Alice's transfer.
5. `normalize_amount(500_000, {origin=24, dest=18}) = 500_000 / 10^6 = 0`.
6. `require!(0 > 0, BridgeError::InvalidAmountToTransfer)` panics → transaction reverts.
7. Steps 4–6 repeat indefinitely. Alice's 500,000 raw units are permanently frozen.

A unit test can reproduce this by constructing a `TransferMessage` with the above parameters, calling `init_transfer_internal` to confirm tokens are locked, then calling `sign_transfer` and asserting it panics with `InvalidAmountToTransfer`.
