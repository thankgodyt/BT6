Unconditional `validatePerasCert` Acceptance Enables Unauthorized Peras Certificate Injection and Chain Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance's `validatePerasCert` function enforces **no minimum requirements** on inbound Peras certificates — it unconditionally returns `Right` for every certificate it receives, assigning it the full `perasWeight` boost. Both production object-diffusion pool writers call this stub directly. An unprivileged peer can therefore inject a crafted `PerasCert` for any block point, have it accepted without any quorum, committee-membership, or signature check, and cause the receiving node to apply a weight boost of 15 to an adversary-chosen block, potentially triggering a chain switch to a non-canonical fork.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must verify a received certificate before it is stored and used in chain selection. The degenerate catch-all instance (the only one currently wired into production) implements this gate as a no-op:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

There is no check on:
- whether the certificate's `pcCertRound` is valid for the current epoch,
- whether the `pcCertBoostedBlock` was actually voted on by a quorum of the committee,
- whether any cryptographic signatures or VRF proofs are present and correct,
- whether the claimed committee members hold sufficient stake.

This is the direct analog of the external report's missing minimum threshold: the threshold for certificate acceptance is effectively **zero** — any certificate from any peer passes.

Both production inbound-certificate writers call this stub explicitly:

```haskell

-- makePerasCertPoolWriterFromChainDB
-- TODO replace when actual plumbing is in place
(validatePerasCert mkPerasParams)
``` [2](#0-1) 

`processCerts` then adds every certificate that passes `validateCert` (which always passes) to the database and triggers chain selection:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
``` [3](#0-2) 

Once stored, `implGetWeightSnapshot` builds the `PerasWeightSnapshot` from every certificate in the DB, including the injected one:

```haskell
let weights =
      mkPerasWeightSnapshot
        [ (getPerasCertBoostedBlock cert, getPerasCertBoost cert)
        | cert <- Map.elems (pcdsCertsByTicket pcds)
        ]
``` [4](#0-3) 

Chain selection then uses `wsvTotalWeight` — `BlockNo + weightBoost` — to compare candidates:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [5](#0-4) 

A fraudulent certificate injecting `perasWeight = 15` (the default) onto a fork block makes that fork appear 15 block-lengths heavier than it actually is, which can flip chain selection.

---

### Impact Explanation

**Critical — Bypass of Peras certificate verification enabling unauthorized certificate acceptance and chain selection manipulation.**

An adversary who controls a single peer connection can inject a `PerasCert` for any block on any fork. The receiving node will:

1. Accept the certificate unconditionally (no quorum, no signature, no committee check).
2. Store it in the `PerasCertDB` with a boost of `PerasWeight 15`.
3. Trigger `chainSelSync` → `chainSelectionForBlock` for the boosted block.
4. Potentially switch its preferred chain to the adversary-chosen fork.

This directly undermines the Peras protocol's fast-settlement and chain-quality guarantees. A node that has been manipulated into preferring a non-canonical chain will also propagate that preference to its downstream peers via ChainSync, amplifying the attack.

---

### Likelihood Explanation

**High.** The attack requires only a single peer connection and the ability to send a well-formed `PerasCert` message over the object-diffusion mini-protocol. No stake, no keys, no admin access, and no brute force are needed. The vulnerable code path (`makePerasCertPoolWriterFromChainDB` → `processCerts` → `validatePerasCert mkPerasParams`) is the sole production path for inbound certificates and is unconditionally active whenever Peras object diffusion is enabled.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that enforces, at minimum:

1. **Quorum proof**: the certificate must carry evidence that ≥ `perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin` of the committee's stake voted for `pcCertBoostedBlock` in round `pcCertRound`.
2. **Committee membership and signature verification**: each vote bundled in the certificate must be signed by a key that belongs to the committee for that round, verified against the epoch's stake distribution.
3. **Round validity**: `pcCertRound` must be consistent with the current epoch and not in a cooldown period.

Until real validation is implemented, inbound certificates from untrusted peers should be rejected entirely rather than accepted unconditionally.

---

### Proof of Concept

On a private testnet with Peras object diffusion enabled:

1. Connect a crafted peer to an honest node.
2. Construct a `PerasCert` with `pcCertRound = <current round>` and `pcCertBoostedBlock = <tip of an adversary-controlled fork>`.
3. Send the certificate via the Peras cert object-diffusion mini-protocol.
4. Observe that `processCerts` calls `validatePerasCert mkPerasParams`, which returns `Right` unconditionally.
5. The certificate is stored in `PerasCertDB`; `implGetWeightSnapshot` now returns a snapshot that adds `PerasWeight 15` to the adversary's fork tip.
6. `chainSelSync` triggers chain selection; `preferCandidate` compares `wsvTotalWeight` values and, if the fork is within 15 blocks of the honest tip, switches to the adversary's fork. [6](#0-5) [7](#0-6) [8](#0-7)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
