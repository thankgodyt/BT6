### Title
Missing Serialisation Version Bump for `shelleyLedgerLatestPerasCertRound` Causes LedgerDB Snapshot Rejection on Node Upgrade — (`ouroboros-consensus-cardano/src/shelley/Ouroboros/Consensus/Shelley/Ledger/Ledger.hs`)

---

### Summary

The `shelleyLedgerLatestPerasCertRound` field (a new Peras protocol field) was added to `ShelleyLedgerState` and encoded under the **existing** `serialisationFormatVersion2` without bumping the version number. The decoder strictly enforces a 4-element CBOR list via `enforceSize "ShelleyLedgerState" 4`. Any snapshot written by a pre-Peras node under version 2 with only 3 fields will permanently fail to decode on a post-Peras node, forcing a full genesis replay without operator fault.

---

### Finding Description

`ShelleyLedgerState` is serialised to disk (LedgerDB snapshots) via `encodeShelleyLedgerState` and deserialised via `decodeShelleyLedgerState`.

**Encoder** (current):

```haskell
encodeShelleyLedgerState ... =
  encodeVersion serialisationFormatVersion2 $
    mconcat $
      [ CBOR.encodeListLen 4          -- ← 4 fields
      , encodeWithOrigin encodeShelleyTip shelleyLedgerTip
      , toCBOR shelleyLedgerState
      , encodeShelleyTransition shelleyLedgerTransition
      , encodeStrictMaybe toCBOR shelleyLedgerLatestPerasCertRound  -- ← NEW Peras field
      ]
``` [1](#0-0) 

**Decoder** (current):

```haskell
decodeShelleyLedgerState =
  decodeVersion
    [ (serialisationFormatVersion2, Decode decodeShelleyLedgerState2) ]
 where
  decodeShelleyLedgerState2 = do
    enforceSize "ShelleyLedgerState" 4   -- ← strictly requires 4 fields
    ...
    shelleyLedgerLatestPerasCertRound <- decodeStrictMaybe fromCBOR
``` [2](#0-1) 

The version history comment in the same file confirms that `serialisationFormatVersion2` previously encoded only **3 fields** (tip with `BlockNo`, ledger state, transition info):

```
-- o 'serialisationFormatVersion1' did not include a 'BlockNo' at the tip of
--   the ledger, which was introduced in version 2.
``` [3](#0-2) 

`shelleyLedgerLatestPerasCertRound` is a Peras-specific field introduced recently (evidenced by changelog entry `20260413_094611_agustin.mista_generic_voting_committee_api.md`). It was appended to the existing version-2 list without incrementing the version number. The decoder now unconditionally calls `enforceSize "ShelleyLedgerState" 4`, which will throw a CBOR decode error on any snapshot written before this field existed (those snapshots encode a 3-element list under version 2).

The snapshot loading path in `loadSnapshot` (both InMemory and LSM backends) calls `readExtLedgerState`, which calls `decodeLBackwardsCompatible`, which in turn delegates to `decodeShelleyLedgerState`:

```haskell
readExtLedgerState hasFS decLedger decHash =
  ...
  decoder = decodeLBackwardsCompatible (Proxy @blk) decLedger decHash
``` [4](#0-3) 

`decodeLBackwardsCompatible` only handles the outer snapshot envelope versioning (old 3-tuple format vs. version-1 envelope). It does **not** add any backwards-compatibility layer for the inner `ShelleyLedgerState` field count:

```haskell
decodeLBackwardsCompatible _ decodeLedger decodeHash =
  decodeVersionWithHook
    decodeOldFormat
    [(snapshotEncodingVersion1, Decode decodeVersion1)]
 where
  decodeVersion1 = decodeLedger   -- ← directly calls decodeShelleyLedgerState
``` [5](#0-4) 

When `decodeShelleyLedgerState` is reached with an old 3-field snapshot, `enforceSize "ShelleyLedgerState" 4` fails, producing `InitFailureRead ReadSnapshotFailed`. The `initLedgerDB` loop then skips all snapshots and falls back to `InitFromGenesis`. [6](#0-5) 

---

### Impact Explanation

**High — LedgerDB snapshot replay/rollback bug causing permanent rejection of valid chain snapshots without operator fault.**

Every on-disk LedgerDB snapshot written by a pre-Peras node encodes `ShelleyLedgerState` as a 3-element CBOR list under `serialisationFormatVersion2`. After upgrading to a post-Peras node, all such snapshots are permanently and silently rejected by `enforceSize "ShelleyLedgerState" 4`. The node is forced to replay the entire chain from genesis. During replay the node is not validating new blocks, weakening the network. There is no operator-accessible migration path (the `snapshot-converter` tool migrates between storage backends, not between serialisation format versions). The rejection is durable: the snapshots can never be loaded by the new software.

---

### Likelihood Explanation

**High.** Any production Cardano node operator upgrading from a software version that predates the introduction of `shelleyLedgerLatestPerasCertRound` to a version that includes it will trigger this on the very first startup. No special configuration or adversarial input is required — the existing on-disk snapshot is the sole trigger. The Peras field was introduced recently (April 2026 changelog), so all existing mainnet/testnet snapshots predate it.

---

### Recommendation

1. **Bump the version number.** Introduce `serialisationFormatVersion3` for the 4-field format and keep `serialisationFormatVersion2` mapped to a 3-field decoder that supplies `SNothing` for `shelleyLedgerLatestPerasCertRound`:

```haskell
decodeShelleyLedgerState =
  decodeVersion
    [ (serialisationFormatVersion2, Decode decodeShelleyLedgerState2_legacy)
    , (serialisationFormatVersion3, Decode decodeShelleyLedgerState3)
    ]
 where
  decodeShelleyLedgerState2_legacy = do
    enforceSize "ShelleyLedgerState" 3
    shelleyLedgerTip        <- decodeWithOrigin decodeShelleyTip
    shelleyLedgerState      <- fromCBOR
    shelleyLedgerTransition <- decodeShelleyTransition
    return ShelleyLedgerState { ..., shelleyLedgerLatestPerasCertRound = SNothing }

  decodeShelleyLedgerState3 = do
    enforceSize "ShelleyLedgerState" 4
    ...
```

2. **Update the version comment** to document the new field and the version bump, following the existing pattern for versions 0→1→2.

3. **Add a golden-test** for the 3-field version-2 binary to prevent future regressions of the same class.

---

### Proof of Concept

**Reproduction (local testnet / db-analyser):**

1. Start a node at a software version that predates `shelleyLedgerLatestPerasCertRound`. Let it sync past the Shelley era and write a LedgerDB snapshot (3-field version-2 CBOR).
2. Stop the node. Upgrade to the post-Peras software.
3. Restart. Observe `InitFailure ... ReadSnapshotFailed` for every snapshot in the trace log, followed by `InitFromGenesis`.
4. The node replays the entire chain from genesis instead of loading the valid snapshot.

The root cause is confirmed at:
- Encoder: `encodeListLen 4` + `encodeStrictMaybe toCBOR shelleyLedgerLatestPerasCertRound` under `serialisationFormatVersion2` [1](#0-0) 
- Decoder: `enforceSize "ShelleyLedgerState" 4` under the same `serialisationFormatVersion2` with no fallback for 3-field snapshots [2](#0-1)

decodeLBackwardsCompatible _ decodeLedger decodeHash =
  decodeVersionWithHook
    decodeOldFormat
    [(snapshotEncodingVersion1, Decode decodeVersion1)]
 where
  decodeVersion1 :: forall s. Decoder s l
  decodeVersion1 = decodeLedger

  decodeOldFormat :: Maybe Int -> forall s. Decoder s l
  decodeOldFormat (Just 3) = do
    _ <-
      withOriginRealPointToPoint
        <$> decodeWithOrigin (decodeRealPoint @blk decodeHash)
    _ <- Dec.decodeWord64
    decodeLedger
  decodeOldFormat mbListLen =
    fail $
      "decodeSnapshotBackwardsCompatible: invalid start "
        <> show mbListLen
```
