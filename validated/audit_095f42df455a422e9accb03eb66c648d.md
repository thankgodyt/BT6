### Title
Any Caller Can Hijack Ownership of a User's Refund `BTCPendingInfo` by Front-Running `execute_refund` — (File: `contracts/satoshi-bridge/src/bitcoin_utils/refund.rs`)

---

### Summary

`execute_refund` is permissionless — anyone can call it after the timelock. However, the `caller` (`env::predecessor_account_id()`) is recorded as the `account_id` owner of the resulting `BTCPendingInfo`. Because Bitcoin PSBTs are deterministic (fixed inputs and outputs), the original refund requester cannot re-execute the refund once an attacker has already done so. The original requester loses control over signing their own refund transaction, and the attacker can grief by refusing to sign, leaving the user's BTC stuck in the deposit address until DAO/Operator intervention.

---

### Finding Description

`execute_refund` in `contracts/satoshi-bridge/src/api/bridge.rs` is open to any caller after the timelock:

```rust
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn execute_refund(
    &mut self,
    utxo_storage_key: String,
    chain_specific_data: Option<ChainSpecificData>,
) -> PromiseOrValue<()> {
    let timelock_sec = self.resolve_execute_refund_timelock(&utxo_storage_key);
    self.internal_execute_refund(utxo_storage_key, timelock_sec, chain_specific_data)
}
``` [1](#0-0) 

Inside `internal_execute_refund` (Bitcoin path), the `caller` is set to `env::predecessor_account_id()` — whoever called `execute_refund` — and passed directly into `finalize_refund_with_psbt`:

```rust
let caller = env::predecessor_account_id();
self.finalize_refund_with_psbt(
    caller,
    refund_request,
    psbt,
    refund_amount,
    utxo_storage_key,
);
``` [2](#0-1) 

Inside `finalize_refund_with_psbt`, this `caller` becomes the `account_id` of the `BTCPendingInfo` and the pending tx is inserted into **the caller's** `btc_pending_sign_ids`:

```rust
let btc_pending_info = BTCPendingInfo {
    account_id: caller.clone(),
    ...
};
// ...
self.internal_unwrap_mut_account(&caller)
    .btc_pending_sign_ids
    .insert(btc_pending_id.clone());
``` [3](#0-2) 

Because the Bitcoin PSBT is fully deterministic (same `outpoint` from stored `tx_bytes`/`vout`, same `refund_output` from stored `refund_address`/`refund_amount`), the `btc_pending_id` derived from it is always identical. When the original requester subsequently tries to call `execute_refund`, `finalize_refund_with_psbt` panics:

```rust
require!(
    self.data_mut()
        .btc_pending_infos
        .insert(btc_pending_id.clone(), btc_pending_info.into())
        .is_none(),
    "pending info already exist"
);
``` [4](#0-3) 

The original requester is permanently locked out of their own refund's signing pipeline. The attacker (who owns the `BTCPendingInfo`) can simply refuse to call `sign_btc_transaction`, leaving the refund stuck.

---

### Impact Explanation

- The original refund requester loses ownership of their refund's `BTCPendingInfo` to whoever front-runs `execute_refund`.
- For Bitcoin (deterministic PSBTs), the original requester cannot re-execute the refund — the second call panics with "pending info already exist".
- The attacker controls whether the refund transaction is ever signed. If they refuse, the user's BTC remains locked in the deposit address indefinitely.
- Recovery requires DAO/Operator to call `reject_refund` (removing the `RefundRequest`) followed by `remove_refund_pending_tx_id` (removing the stale `BTCPendingInfo`), after which the user must restart the entire refund lifecycle from scratch.

This matches: **Medium — stuck bridge state requiring operator intervention / attacker-triggered temporary locking of bridged funds.**

---

### Likelihood Explanation

NEAR transactions are public and observable. An attacker can monitor the chain for `RefundRequested` events, wait for the timelock to expire, and immediately call `execute_refund` before the original requester. The only cost to the attacker is the attached storage deposit (`required_balance_for_execute_refund()`), which is a small NEAR amount. No special privileges are required.

---

### Recommendation

Record the original refund requester's account ID at `request_refund` time (store it in `RefundRequest`), and use that stored account ID — not `env::predecessor_account_id()` — as the `account_id` in `BTCPendingInfo` inside `finalize_refund_with_psbt`. This mirrors the fix in the referenced ERC5164 report: use the original initiator's identity, not the caller of the execution function.

Concretely, add a `requester: AccountId` field to `RefundRequest`, populate it in `request_refund_callback`, and replace:

```rust
// bitcoin_utils/refund.rs
let caller = env::predecessor_account_id();
self.finalize_refund_with_psbt(caller, ...)
```

with:

```rust
let owner = refund_request.requester.clone();
self.finalize_refund_with_psbt(owner, ...)
```

---

### Proof of Concept

1. **User A** calls `request_refund(deposit_msg, refund_address, tx_bytes, vout, proof, None)`. The `RefundRequest` is stored with `refund_address = "bc1q...userA"`.
2. The timelock (`refund_timelock_sec`) expires.
3. **Attacker B** monitors the chain, sees the `RefundRequested` event, and immediately calls `execute_refund(utxo_storage_key, None)` with the required storage deposit.
4. Inside `internal_execute_refund`, `caller = env::predecessor_account_id()` = Attacker B's account. `finalize_refund_with_psbt(attackerB, ...)` is called. A `BTCPendingInfo` with `account_id = attackerB` is created and inserted into `btc_pending_infos`. The UTXO key is inserted into `verified_deposit_utxo` and `refund_request.executed = true`.
5. **User A** calls `execute_refund(utxo_storage_key, None)`. The timelock check passes (`executed == true` bypasses the deposit check). `finalize_refund_with_psbt` is called with the identical deterministic PSBT → same `btc_pending_id` → panics: **"pending info already exist"**.
6. User A cannot sign their refund. Attacker B holds the `BTCPendingInfo` and can refuse to call `sign_btc_transaction`. User A's BTC is stuck in the deposit address until DAO/Operator intervenes. [5](#0-4) [6](#0-5)

    pub(crate) fn internal_execute_refund(
        &mut self,
        utxo_storage_key: String,
        timelock_sec: u64,
        _chain_specific_data: Option<ChainSpecificData>,
    ) -> PromiseOrValue<()> {
        let refund_request = self.load_refund_request_for_execute(&utxo_storage_key, timelock_sec);
        let RefundExecutionInputs {
            outpoint,
            deposit_output,
            refund_amount,
        } = self.refund_execution_inputs(&refund_request);
        let refund_output = self.build_refund_output(&refund_request.refund_address, refund_amount);

        let mut psbt = PsbtWrapper::new(vec![outpoint], vec![refund_output]);
        psbt.set_input_utxo(vec![deposit_output]);

        let caller = env::predecessor_account_id();
        self.finalize_refund_with_psbt(
            caller,
            refund_request,
            psbt,
            refund_amount,
            utxo_storage_key,
        );
        PromiseOrValue::Value(())
    }

    pub(crate) fn finalize_refund_with_psbt(
        &mut self,
        caller: AccountId,
        mut refund_request: RefundRequest,
        psbt: PsbtWrapper,
        refund_amount: u128,
        utxo_storage_key: String,
    ) {
        let gas_fee = refund_request.gas_fee;
        let refund_address = refund_request.refund_address.clone();

        let deposit_msg = refund_request.deposit_msg();
        let path = get_deposit_path(&deposit_msg);
        let vutxo = VUTXO::Current(UTXO {
            path,
            tx_bytes: refund_request.tx_bytes.0.clone(),
            vout: refund_request.vout,
            balance: u64::try_from(refund_request.amount)
                .unwrap_or_else(|_| env::panic_str("Amount overflow")),
        });

        let psbt_hex = psbt.serialize();
        let btc_pending_id = psbt.get_pending_id();

        if !self.check_account_exists(&caller) {
            self.internal_set_account(&caller, crate::Account::new(&caller));
        }
        self.require_pending_sign_capacity(&caller);

        let btc_pending_info = BTCPendingInfo {
            account_id: caller.clone(),
            btc_pending_id: btc_pending_id.clone(),
            transfer_amount: 0,
            actual_received_amount: refund_amount,
            withdraw_fee: 0,
            gas_fee,
            burn_amount: 0,
            psbt_hex,
            vutxos: vec![vutxo],
            signatures: vec![None; 1],
            tx_bytes_with_sign: None,
            create_time_sec: nano_to_sec(env::block_timestamp()),
            last_sign_time_sec: 0,
            state: PendingInfoState::Refund(OriginalState {
                stage: PendingInfoStage::PendingSign,
                max_gas_fee: gas_fee,
                last_rbf_time_sec: None,
                cancel_rbf_reserved: None,
            }),
        };

        require!(
            self.data_mut()
                .btc_pending_infos
                .insert(btc_pending_id.clone(), btc_pending_info.into())
                .is_none(),
            "pending info already exist"
        );
        self.internal_unwrap_mut_account(&caller)
            .btc_pending_sign_ids
            .insert(btc_pending_id.clone());

        // Mark UTXO as verified to prevent verify_deposit later
        self.data_mut()
            .verified_deposit_utxo
            .insert(utxo_storage_key.clone());

        Event::RefundExecuted {
            utxo_storage_key: utxo_storage_key.clone(),
            amount: refund_request.amount.into(),
            refund_address,
        }
        .emit();

        Event::GenerateBtcPendingInfo {
            account_id: &caller,
            btc_pending_id: &btc_pending_id,
        }
        .emit();

        // Keep the request (so `execute_refund` can be called again to re-create
        // the transaction) but mark it executed; it is removed only when the
        // refund is finalized in `verify_refund_finalize`.
        refund_request.executed = true;
        self.data_mut()
            .refund_requests
            .insert(utxo_storage_key, refund_request.into());
    }
