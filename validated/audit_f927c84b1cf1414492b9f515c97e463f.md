### Title
`EXPECTED_ACTIONS_NUMBER = 1` Rejects All Standard-Wallet Orchard Bundles, Permanently Breaking Shielded Withdrawals and Refunds — (`contracts/satoshi-bridge/src/zcash_utils/orchard_policy.rs`)

---

### Summary

`extract_orchard_bundle` enforces an exact action count of `1` against every user-submitted Orchard bundle. The Orchard protocol's standard `BundleType::Transactional` builder pads every bundle to a minimum of 2 actions for privacy (the `MIN_ACTIONS = 2` constant referenced in the code's own comment). The bridge's test harness works around this by using the non-standard `BundleType::Coinbase`, which skips padding. Any bundle produced by a real Zcash wallet using the standard builder will have 2 actions and will be unconditionally rejected, causing `PsbtWrapper::new` to panic via `env::panic_str`, permanently breaking all Orchard-shielded withdrawals and refunds for standard-wallet users.

---

### Finding Description

**Root cause — wrong constant value:** [1](#0-0) 

The comment explicitly links to `https://github.com/zcash/orchard/blob/main/src/builder.rs#L36`, which is where the Orchard library defines `MIN_ACTIONS = 2`. Despite this, `EXPECTED_ACTIONS_NUMBER` is set to `1`, directly contradicting the referenced spec.

**Strict equality check:** [2](#0-1) 

Any bundle whose `actions().len()` is not exactly `1` returns `Err`, which is immediately converted to a contract panic: [3](#0-2) 

**Test harness masks the bug with a non-standard bundle type:**

The test helper uses `BundleType::Coinbase`, which is the only Orchard bundle type that bypasses the 2-action padding rule: [4](#0-3) 

A standard Zcash wallet uses `BundleType::Transactional` (the default), which always pads to `MIN_ACTIONS = 2`. The bridge's own tests never exercise this code path with a standard-wallet bundle.

**Reachable public entry points:**

1. **Withdrawal** — `ft_on_transfer` → `ft_on_transfer_withdraw_chain_specific` → `ft_on_transfer_callback` → `PsbtWrapper::new`: [5](#0-4) 

2. **Shielded refund** — `execute_refund` → `execute_refund_callback` → `PsbtWrapper::new` (same panic path via `from_original_psbt`): [6](#0-5) 

Both paths accept `orchard_bundle_bytes` from unprivileged public callers via `ChainSpecificData`: [7](#0-6) 

---

### Impact Explanation

Every Orchard-shielded withdrawal or refund submitted with a bundle produced by a standard Zcash wallet (2 actions) panics unconditionally. The NEAR transaction is reverted so user tokens are not lost, but the operation is permanently impossible for any standard-wallet user. The bridge's shielded withdrawal and shielded refund features are effectively non-functional in production.

---

### Likelihood Explanation

Likelihood is high within the Zcash-enabled deployment. Any user or integration that constructs an Orchard bundle with the standard `BundleType::Transactional` builder — which is the default for every Zcash wallet and SDK — will trigger the panic on every attempt. There is no workaround available to the user short of using the non-standard `BundleType::Coinbase`, which is not exposed by standard wallet software.

---

### Recommendation

Change `EXPECTED_ACTIONS_NUMBER` to `2` to match the Orchard protocol's `MIN_ACTIONS` constant, and update `extract_orchard_bundle` to accept bundles with `>= 1` real output action (i.e., `bundle.actions().len() >= EXPECTED_ACTIONS_NUMBER`) rather than requiring an exact count. The single-output recovery at index `0` remains valid as long as the bridge OVK is used to identify the correct output among the actions.

---

### Proof of Concept

1. Build a standard Orchard bundle using `BundleType::Transactional` (the default) with one real output paying the bridge OVK — the builder pads it to 2 actions.
2. Hex-encode the serialized bundle and submit it as `chain_specific_data.orchard_bundle_bytes` in an `ft_on_transfer` `Withdraw` message.
3. Observe that `extract_orchard_bundle` returns `Err("Orchard bundle must have 1 actions, got 2")` and the contract panics with `ERR_INVALID_ORCHARD_BUNDLE`.
4. Repeat for `execute_refund` with the same bundle — identical panic.
