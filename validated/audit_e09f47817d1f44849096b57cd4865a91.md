### Title
Hardcoded `boundX = 3` in `localSortitionNumSeats` Produces Incorrect Seat Counts for Non-Persistent Peras Voters, Enabling Inflated Vote Weight and Quorum Bypass - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/LS.hs`)

---

### Summary

`localSortitionNumSeats` in `LS.hs` calls `taylorExpCmpFirstNonLower` with a hardcoded `boundX = 3`. The function's own inline documentation states `boundX must be e^{|x|}` for correct error bounds. Because `x = -lambda`, the correct value is `e^lambda`. The constant `3` is only valid when `lambda ≤ ln(3) ≈ 1.099`. For any non-persistent voter whose `lambda` exceeds this threshold, the error interval is narrower than mathematically required, causing the Taylor-series comparison to misclassify Poisson thresholds. Depending on where the voter's normalized VRF output falls relative to the true `e^{-lambda}`, the returned seat count can be either too high or too low. The too-high case inflates the voter's `VoteWeight` in `implEligiblePartyVoteWeight`, and because `implVerifyVote` and `implVerifyCert` recompute seats with the same incorrect bound, the inflated weight is accepted by every verifying node, potentially allowing a Peras certificate to be forged with less honest stake than the quorum threshold requires.

---

### Finding Description

**Root cause — `LS.hs` lines 93–99:**

```haskell
expectedSeats :: Int
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      3          -- ← hardcoded; must be e^lambda for correctness
      orders
      (-lambda)
```

The `taylorExpCmpFirstNonLower` helper (lines 122–175) maintains a running Taylor approximation of `e^x` and uses `errorTerm = abs(err' * boundX)` as the uncertainty interval around the partial sum. When `boundX < e^{|x|}`, the interval `[acc' − errorTerm, acc' + errorTerm]` is narrower than the true remainder bound. This causes two classes of misclassification:

1. A threshold `orders[k]` that is genuinely in the uncertain region (close to `e^{-lambda}`) may be prematurely declared **ABOVE** (`cmp ≥ acc' + errorTerm` fires too early), returning the current index and granting the voter `k` seats when the correct answer is `k − 1` or fewer.
2. Conversely, a threshold may be prematurely declared **BELOW**, advancing to the next index and granting more seats.

The direction of the error for any specific VRF output is determined by whether `orders[k]` is slightly above or slightly below `e^{-lambda}`. For VRF outputs that land in the "ambiguous" band, the incorrect bound can grant **more** seats than the mathematically correct Poisson comparison would.

**Propagation — `WFALS.hs` lines 421–432:**

```haskell
WFALSNonPersistentMember _seatIndex (LedgerStake stake) _vrfOutput numSeats ->
  VoteWeight $
    fromIntegral (unLocalSortitionNumSeats (unNonZero numSeats))
      * stake
      / nonPersistentStake
```

`numSeats` flows directly into the `VoteWeight` numerator. An inflated `numSeats` produces an inflated `VoteWeight`.

**Verification uses the same broken bound — `WFALS.hs` lines 375–390 and 528–543:**

Both `implVerifyVote` and `implVerifyCert` independently call `localSortitionNumSeats` with the same `boundX = 3`. Because the verifier recomputes the seat count from the VRF output rather than trusting a claimed value, it will arrive at the same inflated count and accept the vote.

**Condition for `lambda > ln(3)`:**

```
lambda = numNonPersistentVoters × voterStake / totalNonPersistentStake
```

For a committee with 100 non-persistent seats, any voter holding more than ~1.1 % of the non-persistent stake has `lambda > 1.099`. For 1 000 non-persistent seats the threshold drops to ~0.11 %. In realistic Cardano stake distributions this condition is satisfied by the vast majority of non-persistent candidates.

The code itself acknowledges the problem with a TODO and a tracked issue reference:

### Impact Explanation

**Allowed scope match:** "Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance."

When a non-persistent voter's VRF output falls in the ambiguous band and the incorrect bound grants one or more extra seats, their `VoteWeight` is proportionally inflated. Because every honest verifying node runs the same `localSortitionNumSeats` with `boundX = 3`, the inflated weight is accepted network-wide. If an adversary controls a non-persistent voter with `lambda > ln(3)` and accumulates enough inflated weight across colluding voters, the Peras quorum check (`stakeAboveThreshold`) can be satisfied with less than the intended fraction of honest stake, producing a certificate for a block that would not have reached quorum under correct arithmetic. A certificate accepted by the chain boosts that block's weight by `perasWeight` in chain selection, potentially causing honest nodes to prefer an adversarially chosen chain tip.

---

### Likelihood Explanation

The condition `lambda > ln(3)` is satisfied by any non-persistent voter with more than `ln(3) / numNonPersistentVoters` of the non-persistent stake — a threshold that is routinely exceeded in realistic stake distributions. The adversary does not need to control their VRF output; they only need to participate in enough elections so that, by chance, their VRF output lands in the ambiguous band where the incorrect bound inflates their seat count. The probability of this occurring in any single election is non-negligible for large `lambda`, and the adversary can attempt it every Peras round. The adversary's entry point is simply casting a valid non-persistent vote — no special privileges are required.

---

### Recommendation

Replace the hardcoded `3` with a correct upper bound for `e^lambda`. The simplest fix is to compute `exp lambda` using the same `FixedPoint` arithmetic already in scope, or to use a conservative ceiling that is always ≥ `e^lambda` for the maximum possible `lambda` (bounded by `numNonPersistentVoters`, since `voterStake ≤ totalNonPersistentStake`). Alternatively, adopt the same approach used by `checkLeaderNatValue` in `cardano-ledger` once the relationship between the two computations is clarified (as noted in the existing TODO).

### Proof of Concept

Consider a committee with `numNonPersistentVoters = 50` and a voter holding 10 % of the non-persistent stake:

```
lambda = 50 × 0.10 = 5.0
e^lambda = e^5 ≈ 148.4
boundX used = 3   (underestimate by factor ~49×)
```

At `n = 1` of the Taylor expansion, `err' = (x * x) / 2 = 25/2 = 12.5`:

- Correct `errorTerm = 12.5 × 148.4 ≈ 1855`
- Actual `errorTerm  = 12.5 × 3     = 37.5`

The interval `[acc' − 37.5, acc' + 37.5]` is ~50× narrower than the mathematically valid interval. Any `orders[k]` value within the true uncertainty band but outside the shrunken band is misclassified. For a VRF output that places `orders[k]` just below `e^{-5} ≈ 0.0067`, the correct classification is BELOW (voter does not get `k` seats), but the shrunken interval may classify it as ABOVE (voter gets `k` seats). The voter's `VoteWeight` becomes `k × stake / totalNonPersistentStake` instead of `(k−1) × stake / totalNonPersistentStake`, and `implVerifyVote` accepts this inflated weight because it runs the identical broken computation.
