### Title
`revalidateHeader` Envelope Check Silently Discarded in Production via `assertWithMsg` No-Op — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/HeaderValidation.hs`)

---

### Summary

`assertWithMsg` is a CPP-gated function that is a **complete no-op in production builds** (when `ENABLE_ASSERTIONS` is not defined). `revalidateHeader` wraps its entire envelope validation result in `assertWithMsg`, meaning the check is computed but its failure is silently discarded in production. Because `reapplyBlockLedgerResult` calls `revalidateHeader` for every block during ImmutableDB startup replay and fork-switch chain selection, a crafted on-disk chain containing headers with invalid envelopes (wrong block number, non-monotone slot, broken hash chain) would be silently accepted, producing a durably wrong ledger state.

---

### Finding Description

**Root cause — `assertWithMsg` is a production no-op:** [1](#0-0) 

```haskell
assertWithMsg :: HasCallStack => Either String () -> a -> a
#if ENABLE_ASSERTIONS
assertWithMsg (Left msg) _ = error msg
#endif
assertWithMsg _ a = a   -- ← always reached in production; first arg is thrown away
```

When `ENABLE_ASSERTIONS` is absent (the default for production Cardano node builds), the function unconditionally returns its second argument, discarding the `Either String ()` check result entirely.

**The unchecked call site — `revalidateHeader`:** [2](#0-1) 

```haskell
revalidateHeader cfg ledgerView hdr st =
  assertWithMsg envelopeCheck $          -- ← no-op in production
    HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'
 where
  chainDepState' = reupdateChainDepState ...
  envelopeCheck  = runExcept $ withExcept show $
      validateEnvelope cfg ledgerView (untickedHeaderStateTip st) hdr
```

`validateEnvelope` enforces the critical structural invariants: block numbers are consecutive, slot numbers are strictly increasing, and hashes chain correctly. In production, the `Left` branch of `envelopeCheck` is never acted upon.

Compare with `validateHeader` (the full-validation path), which propagates the same check as a hard error via `withExcept HeaderEnvelopeError`: [3](#0-2) 

**The reachable call site — `reapplyBlockLedgerResult`:** [4](#0-3) 

```haskell
reapplyBlockLedgerResult evs cfg blk TickedExtLedgerState{..} =
    (\l -> ExtLedgerState l hdr) <$> castLedgerResult ledgerResult
  where
    ledgerResult = reapplyBlockLedgerResult ...
    hdr = revalidateHeader (getExtLedgerCfg cfg) ledgerView
                           (getHeader blk) tickedHeaderState
```

This is invoked for every block during:
1. **ImmutableDB startup replay** — reconstructing the in-memory ledger state from on-disk blocks.
2. **Fork-switch chain selection** — replaying blocks from the VolatileDB when switching to a candidate chain.

**Why ImmutableDB validation does not close the gap:**

`validateChunk` in `ImmutableDB/Impl/Validation.hs` checks checksums, hash-chain continuity between chunks, and deserialization integrity. [5](#0-4) 

It does **not** verify block-number monotonicity or slot-number strict increase. Those invariants are exclusively the responsibility of `validateEnvelope`, which is silently skipped in production via `assertWithMsg`.

---

### Impact Explanation

A crafted ImmutableDB or snapshot whose blocks violate envelope invariants (e.g., a header with a non-increasing slot number, a repeated block number, or a broken hash chain) will pass `validateChunk` but would fail `validateEnvelope`. Because `revalidateHeader` wraps that check in a production no-op, the node accepts the invalid block and produces a permanently wrong `ExtLedgerState`. This constitutes **durable use of the wrong ledger state** — the node's entire subsequent chain-selection, mempool validation, and state-query behavior is based on a corrupted ledger.

Impact category: **High — ImmutableDB/LedgerDB replay/rollback bug causing durable use of the wrong ledger state without operator fault.**

---

### Likelihood Explanation

The entry path is a crafted or corrupted ImmutableDB/snapshot on disk, which is explicitly within the stated scope ("DB/snapshot input in a local reproduction"). No cryptographic key compromise is required. The ImmutableDB's own validation does not cover all envelope invariants, so a carefully crafted chunk file passes startup validation but violates the envelope check that is silently discarded. Likelihood is **medium**: requires local disk access but no privileged credentials.

---

### Recommendation

Replace the `assertWithMsg` guard in `revalidateHeader` with an unconditional error that fires in all build configurations:

```haskell
revalidateHeader cfg ledgerView hdr st =
  case envelopeCheck of
    Left err -> error ("revalidateHeader: envelope invariant violated: " <> err)
    Right () -> HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'
```

The envelope check (`validateEnvelope`) is a lightweight structural check — it performs no cryptographic work — so there is no performance justification for gating it behind `ENABLE_ASSERTIONS`. The expensive checks intentionally skipped by `reupdateChainDepState` (KES/VRF signature verification) are a separate concern and remain correctly omitted.

---

### Proof of Concept

1. Craft an ImmutableDB chunk file in which one block header carries a slot number equal to (or less than) the previous block's slot number. Ensure checksums and the inter-block hash chain are otherwise valid so `validateChunk` accepts the file.
2. Start a node pointing at this crafted ImmutableDB. `validateAndReopen` completes successfully (ImmutableDB validation passes).
3. During ledger-state reconstruction, `reapplyBlockLedgerResult` is called for each block, invoking `revalidateHeader`.
4. `revalidateHeader` evaluates `envelopeCheck` → `Left "SlotNo not strictly increasing"`, but passes it to `assertWithMsg`, which in a production build returns the `HeaderState` unchanged without raising any error.
5. The node accepts the structurally invalid block and continues building its ledger state on top of it, permanently diverging from the canonical chain.
