Audit Report

## Title
Missing `MintCloseAuthority` Extension Check Enables Decimal Manipulation and Bridged Fund Loss — (File: `solana/programs/bridge_token_factory/src/instructions/user/log_metadata.rs`)

## Summary

The `LogMetadata` accounts struct constrains the mint only to exclude bridge-owned mints, with no rejection of Token-2022 mints carrying the `MintCloseAuthority` extension. An attacker can register a mint's decimal count via the permissionless `log_metadata` instruction, then use `MintCloseAuthority` to close and reinitialize the mint at the same address with a different decimal count. NEAR's `token_decimals` map retains the stale value, causing every subsequent cross-chain transfer for that token to apply the wrong normalization factor, resulting in permanent loss or incorrect minting of bridged funds.

## Finding Description

**Root cause — missing extension check:** [1](#0-0) 

The only constraint on the mint is `!mint.mint_authority.contains(authority.key)`. There is no check for the `MintCloseAuthority` extension. A grep across the entire Solana program confirms `MintCloseAuthority` is never referenced in production code — only in test helpers.

**Decimal snapshot from live state:** [2](#0-1) 

`self.mint.decimals` is read from the current on-chain mint account and broadcast via Wormhole. There is no idempotency guard; the instruction can be called again for the same mint after reinitialization.

**NEAR stores and uses the value permanently:** [3](#0-2) [4](#0-3) 

`fin_transfer_callback` reads `token_decimals` unconditionally and passes the stored `Decimals` struct to `denormalize_amount`. If the stored `origin_decimals` diverges from the actual token precision, every amount calculation is wrong.

**Normalization functions amplify the mismatch:** [5](#0-4) 

A mismatch of even 12 decimal places produces a `10^12` multiplier or divisor on every transfer amount.

**Exploit path:**
1. Attacker creates a Token-2022 keypair mint `M` at address `A` with `decimals = 6` and `MintCloseAuthority = attacker` (supply = 0).
2. Attacker calls `log_metadata` for mint `A`. NEAR stores `token_decimals[Sol(A)] = Decimals { origin_decimals: 6, decimals: 6 }`.
3. Attacker calls the Token-2022 `CloseAccount` instruction using the close authority, zeroing the account and reclaiming rent (valid because supply = 0).
4. Attacker reinitializes a new mint at address `A` (same keypair) with `decimals = 18`.
5. Attacker (or any user) deposits 1 token (= `1e18` base units) into the Solana vault and initiates a cross-chain transfer.
6. NEAR's `fin_transfer_callback` calls `denormalize_amount(1e18, Decimals { origin_decimals: 6, decimals: 6 })` → diff = 0, result = `1e18`. In 6-decimal representation this is `1e12` tokens minted on NEAR for a deposit of 1 token — a `10^12` inflation.

The reverse direction (18 → 6 reinitialization) causes `normalize_amount` to divide by `10^12`, reducing any real transfer to dust and permanently locking user funds in the vault escrow.

## Impact Explanation

**Critical — unauthorized minting and permanent freezing of bridged funds.** The 6→18 reinitialization path causes NEAR to mint `10^12×` more wrapped tokens than were locked on Solana (unauthorized minting). The 18→6 path causes `normalize_amount` to return 0 for any realistic deposit, locking user funds in the Solana vault with no recovery path (permanent freezing). Both outcomes match the allowed impact class: "Balance manipulation, decimal/normalization abuse that changes user or protocol balances" and "Stealing, loss, unauthorized minting, or permanent freezing of bridged funds."

## Likelihood Explanation

`log_metadata` is fully permissionless — any caller can invoke it for any non-bridge-owned mint. Token-2022 `MintCloseAuthority` is a standard, documented extension. The attacker needs only: (1) a Token-2022 keypair, (2) one `log_metadata` call, (3) one `CloseAccount` call (valid because supply is 0 at registration time), and (4) one `InitializeMint2` call with the same keypair. No admin access, no key leakage, no MPC collusion, and no threshold compromise is required. The attack is repeatable for any new token address.

## Recommendation

In `LogMetadata::process()`, before reading `self.mint.decimals`, unpack the Token-2022 extension list and reject any mint carrying `MintCloseAuthority`:

```rust
let mint_info = self.mint.to_account_info();
let mint_data = mint_info.try_borrow_data()?;
let mint_state =
    StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;
let extensions = mint_state.get_extension_types()?;
require!(
    !extensions.contains(&ExtensionType::MintCloseAuthority),
    ErrorCode::UnsupportedMintExtension
);
```

Additionally, the NEAR bridge's `log_metadata` message handler should treat a second registration for an already-registered token as a no-op (or require DAO approval), so that even if the Solana-side check is bypassed, the stored decimals cannot be silently overwritten.

## Proof of Concept

**Minimal private-testnet sequence:**

1. Deploy a Token-2022 mint `M` at keypair address `A` with `decimals = 6`, `MintCloseAuthority = attacker`, supply = 0.
2. Call `log_metadata` on the Solana bridge with mint `A`. Verify NEAR stores `Decimals { origin_decimals: 6, decimals: 6 }`.
3. Call Token-2022 `CloseAccount` on mint `A` with the close authority. Verify the account is zeroed.
4. Call `InitializeMint2` at address `A` (same keypair signs) with `decimals = 18`. Verify the mint is live with 18 decimals.
5. Mint 1 token (= `1e18` base units) to an attacker ATA and call `init_transfer` to bridge it to NEAR.
6. Relay the Wormhole VAA to NEAR and call `fin_transfer_callback`. Assert that NEAR mints `1e18` units of the wrapped token (= `1e12` tokens in 6-decimal representation) while only 1 token of real value was locked on Solana.
