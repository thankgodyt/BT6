Audit Report

## Title
Sequential `origin_nonce` Not Content-Bound Enables Permanent Fund Loss After EVM Re-org — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`, `near/omni-bridge/src/lib.rs`)

## Summary

`OmniBridge.sol::initTransfer()` assigns a purely sequential `currentOriginNonce` with no binding to transfer content. NEAR's `finalised_transfers` is a `LookupSet<TransferId>` keyed solely by `(origin_chain, origin_nonce)`. After an EVM re-org, a second user's `initTransfer()` call that inherits the same nonce as a previously-finalized transfer will be permanently rejected by NEAR, locking the second user's bridged tokens with no recovery path.

## Finding Description

**EVM — sequential nonce with no content binding:**

`OmniBridge.sol` L381 unconditionally increments `currentOriginNonce` before any transfer-specific data is recorded:

```solidity
currentOriginNonce += 1;
```

The emitted `InitTransfer` event (L427–436) carries this counter as the canonical cross-chain identifier. No hash of `(sender, tokenAddress, amount, fee, recipient)` is included in the identifier.

**NEAR — replay protection keyed only by `(chain, nonce)`:**

`TransferId` is defined as:

```rust
pub struct TransferId {
    pub origin_chain: ChainKind,
    pub origin_nonce: Nonce,
}
```

`Contract::finalised_transfers` is `LookupSet<TransferId>` (lib.rs L223). The insertion point in `add_fin_transfer` (lib.rs L2226–2234) panics with `BridgeError::TransferAlreadyFinalised` if the key already exists:

```rust
require!(
    self.finalised_transfers.insert(transfer_id),
    BridgeError::TransferAlreadyFinalised.as_ref()
);
```

Both `process_fin_transfer_to_near` (L1875) and `process_fin_transfer_to_other_chain` (L1985) call `add_fin_transfer` as their first action, before any token release. There is no public recovery function that removes an entry from `finalised_transfers` to unblock a re-orged nonce.

**Wormhole path — realistic timing window:**

`OmniBridgeWormhole.sol` publishes a Wormhole message immediately after the EVM transaction executes using a configurable `_consistencyLevel` (L143–147). When `_consistencyLevel` is set to a low value (e.g., 1 confirmation), Wormhole guardians issue a VAA for a transaction that can subsequently be re-orged away. That VAA is cryptographically valid and will be accepted by NEAR, permanently consuming nonce N.

**Exploit flow:**

1. Block B1 (EVM): User A calls `initTransfer(USDC, 1000, ...)` → `currentOriginNonce = N`. Wormhole VAA issued (1 confirmation).
2. NEAR: Relayer submits VAA → `fin_transfer_callback` decodes `origin_nonce = N` → `add_fin_transfer` inserts `(Eth, N)` → User A receives funds.
3. Re-org: Block B1 is dropped from the canonical chain.
4. Block B1′ (canonical): User B calls `initTransfer(USDC, 500, ...)` → `currentOriginNonce = N` (same nonce, different content, different recipient).
5. NEAR: Relayer submits proof for User B's transfer → `add_fin_transfer` panics: `(Eth, N)` already in `finalised_transfers`. User B's 500 USDC is permanently locked in `OmniBridge.sol` with no on-chain recovery path.

**Existing checks are insufficient:**

`fin_transfer_callback` verifies the emitter address against `factories` (L708–713) and checks token decimals (L715–718), but neither check prevents the nonce collision. The prover correctly validates the re-orged block's event data, but the `finalised_transfers` gate rejects it solely on the nonce key.

## Impact Explanation

This is a concrete instance of **permanent freezing of bridged funds**: User B's tokens are transferred into (or burned by) `OmniBridge.sol` on the EVM side, and the corresponding NEAR-side finalization is permanently blocked because the nonce slot is already occupied. There is no refund mechanism in `OmniBridge.sol` for proofs rejected by NEAR, and no public function removes an entry from `finalised_transfers` to unblock the affected nonce. This matches the critical impact class: "permanent freezing of bridged funds across EVM or Wormhole-routed flows."

## Likelihood Explanation

Polygon — a supported EVM chain — has experienced multi-block re-orgs in production (157-block re-org at block 39,599,624). With `_consistencyLevel = 1`, a Wormhole VAA can be issued within one block confirmation, making the window between VAA acceptance on NEAR and re-org detection realistic. The scenario requires only two independent users calling `initTransfer()` in close succession, which is normal bridge activity. No privileged access, no victim mistake, and no guardian compromise is required; the guardians operate correctly by signing what they observed before the re-org.

## Recommendation

Replace the purely sequential `origin_nonce` with a content-bound identifier. Compute the transfer ID as:

```solidity
bytes32 transferHash = keccak256(abi.encode(
    msg.sender, tokenAddress, amount, fee, nativeFee, recipient, currentOriginNonce
));
```

Emit `transferHash` alongside the nonce in `InitTransfer`. On the NEAR side, key `finalised_transfers` on this hash (or require the relayer to supply it and verify it against the proven event data) so that two transfers sharing the same sequential nonce but differing in content produce distinct keys and can both be finalized independently. Additionally, set `_consistencyLevel` to the chain's finality level (e.g., `200` / "finalized" on Ethereum, or the equivalent safe value for each supported chain) to reduce the re-org window.

## Proof of Concept

**Local integration test plan (near/omni-tests):**

1. Deploy `OmniBridgeWormhole` on a local EVM fork with `_consistencyLevel = 1`.
2. Submit User A's `initTransfer` (nonce = 5); capture the emitted `InitTransfer` event.
3. Construct a `ProverResult::InitTransfer` for User A's event and call `fin_transfer` on the NEAR locker; assert `finalised_transfers.contains((Eth, 5)) == true`.
4. Simulate a re-org by discarding User A's block state on the EVM fork; submit User B's `initTransfer` — the EVM contract assigns nonce = 5 again (different amount/recipient).
5. Construct a `ProverResult::InitTransfer` for User B's event and call `fin_transfer` on the NEAR locker; assert the call panics with `BridgeError::TransferAlreadyFinalised`.
6. Verify User B's tokens remain locked in `OmniBridge.sol` with no recovery path available.
