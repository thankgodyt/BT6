Looking at the actual code to verify all claims before rendering a verdict.

Audit Report

## Title
Undeployed Native Token Causes Permanent Revert of `fin_transfer_callback` for Transfers with `native_fee > 0` — (File: near/omni-bridge/src/lib.rs)

## Summary
When a cross-chain transfer arrives at NEAR with `native_fee > 0`, `process_fin_transfer_to_near` calls `get_native_token_id` to resolve the origin chain's native token. If `deploy_native_token` has never been called for that chain, `get_native_token_id` panics with `TokenNotRegistered`, reverting the entire `fin_transfer_callback` execution. Because the panic also reverts the preceding `add_fin_transfer` call, the proof can be resubmitted indefinitely — but every attempt fails identically — leaving the user's source-chain funds permanently locked or burned with no recovery path until the DAO acts.

## Finding Description

**Root cause — `get_native_token_id` panics on unregistered zero address:**

`get_native_token_id` constructs the zero address for the given chain and delegates to `get_token_id`:

```rust
// near/omni-bridge/src/lib.rs:1407-1412
pub fn get_native_token_id(&self, chain: ChainKind) -> AccountId {
    let native_token_address =
        get_native_token_address(chain).near_expect(BridgeError::FailedToGetNativeTokenAddress);
    self.get_token_id(&native_token_address)
}
```

`get_token_id` panics unconditionally if the zero address is absent from `token_address_to_id`:

```rust
// near/omni-bridge/src/lib.rs:1368-1376
pub fn get_token_id(&self, address: &OmniAddress) -> AccountId {
    if let OmniAddress::Near(token_account_id) = address {
        token_account_id.clone()
    } else {
        self.token_address_to_id
            .get(address)
            .near_expect(BridgeError::TokenNotRegistered)  // panics here
    }
}
```

The zero address is only inserted into `token_address_to_id` when `deploy_native_token` (DAO-only, lines 1200–1221) is called and its async callback succeeds. If that call was never made for the origin chain, the map entry is absent.

**Vulnerable call site 1 — `process_fin_transfer_to_near`:**

`add_fin_transfer` is called first (line 1875), then the `native_fee > 0` branch panics at line 1936:

```rust
// near/omni-bridge/src/lib.rs:1875
let mut required_balance = self.add_fin_transfer(&transfer_message.get_transfer_id());
// ... (lines 1877–1933) ...
// near/omni-bridge/src/lib.rs:1935-1936
if transfer_message.fee.native_fee.0 > 0 {
    let native_token_id = self.get_native_token_id(transfer_message.get_origin_chain()); // panics
```

Because NEAR execution is atomic within a callback, the panic reverts `add_fin_transfer` as well. The transfer ID is never persisted in `finalised_transfers`, so the proof can be resubmitted — but every resubmission panics identically.

**Vulnerable call site 2 — `fin_transfer_send_tokens_callback`:**

```rust
// near/omni-bridge/src/lib.rs:1736-1742
if transfer_message.fee.native_fee.0 > 0 {
    let native_token_id = self.get_native_token_id(transfer_message.get_origin_chain());
    ext_token::ext(native_token_id)
        .with_static_gas(MINT_TOKEN_GAS)
        .mint(fee_recipient.clone(), transfer_message.fee.native_fee, None)
        .detach();
}
```

**Vulnerable call site 3 — `send_fee_internal` (called from `claim_fee_callback`):**

```rust
// near/omni-bridge/src/lib.rs:2669-2672
ext_token::ext(self.get_native_token_id(origin_chain))
    .with_static_gas(MINT_TOKEN_GAS)
    .mint(fee_recipient.clone(), transfer_message.fee.native_fee, None)
    .detach();
```

`get_native_token_address` returns `OmniAddress::new_zero(chain_kind)` for all chains except Starknet (near/omni-types/src/lib.rs:944–961), confirming the zero-address lookup path is taken for every EVM and Solana chain.

## Impact Explanation

This is a **permanent freezing of bridged funds**, matching the Critical allowed impact. The user's tokens are locked or burned on the source chain at `initTransfer` time. Every subsequent `fin_transfer` call to NEAR panics before finalizing the transfer. There is no on-chain mechanism for the user to recover funds; recovery requires DAO intervention via `deploy_native_token`. If the DAO does not act, the funds are permanently frozen. Even with DAO action, there is an indefinite window during which funds are irrecoverable.

## Likelihood Explanation

The `native_fee` field is set by the user at the source chain and is not validated against NEAR state by the EVM bridge contract. Any user who sets `native_fee > 0` for a transfer from a chain whose native token has not been deployed on NEAR will trigger this failure. This is especially likely during new chain onboarding (e.g., `HyperEvm`, `Abs`, `Fogo` are all present in `ChainKind` and `get_native_token_address` but may not have had `deploy_native_token` called). No special privileges are required; any unprivileged user can trigger this by submitting a standard cross-chain transfer with a nonzero native fee.

## Recommendation

1. In `process_fin_transfer_to_near`, before calling `get_native_token_id`, check whether the native token for the origin chain is registered (e.g., via `token_address_to_id.get(&native_token_address)`). If absent, either reject the transfer with a clear error or treat `native_fee` as zero and refund it to the sender.
2. Change `get_native_token_id` to return `Option<AccountId>` instead of panicking, and update all call sites to handle the `None` case gracefully.
3. Alternatively, enforce on the source chain side that `native_fee > 0` is only accepted when the native token is known to be deployed on NEAR.

## Proof of Concept

1. DAO adds a new chain (e.g., `HyperEvm`) to the bridge via `add_factory` but does **not** call `deploy_native_token(HyperEvm, ...)`.
2. User calls `initTransfer` on the HyperEvm `OmniBridge` contract with `native_fee = 1000` and `amount = 100_000`. Tokens are locked in the EVM bridge.
3. Relayer submits the proof to NEAR via `fin_transfer(...)`.
4. `fin_transfer_callback` decodes the proof, calls `process_fin_transfer_to_near`.
5. Line 1875: `add_fin_transfer` is called and succeeds (transfer ID inserted into `finalised_transfers`).
6. Line 1936: `get_native_token_id(ChainKind::HyperEvm)` is called → `get_native_token_address(HyperEvm)` returns `OmniAddress::HyperEvm(H160::ZERO)` → `token_address_to_id.get(HyperEvm(H160::ZERO))` returns `None` → `near_expect(TokenNotRegistered)` panics.
7. The entire `fin_transfer_callback` execution reverts, including the `add_fin_transfer` write.
8. Every resubmission of the proof fails identically. User's tokens remain locked in the EVM bridge with no recovery path.

**Unit test to reproduce:** Add a test mirroring `test_fin_transfer_callback_near_success` but omit the `token_address_to_id` insertion for the native zero address and set `native_fee > 0` in the prover result. The test should panic with `ERR_TOKEN_NOT_REGISTERED`.
