### Title
Symmetric `slotDist` in `RestrictedVRFTiebreaker` incorrectly suppresses VRF chain-selection tiebreaker when the current chain's block was issued later than the candidate's - (`File: ouroboros-consensus-protocol/src/ouroboros-consensus-protocol/Ouroboros/Consensus/Protocol/Praos/Common.hs`)

---

### Summary

The `slotDist` helper inside `comparePraos` computes the **absolute** (symmetric) distance between two slot numbers. The `RestrictedVRFTiebreaker` feature is designed to disable the VRF tiebreaker only in one direction: when the **candidate** block was issued much later than ours (`slot(cand) > slot(ours) + maxDist`), because in that case the candidate's issuer should have built on top of our block instead of competing at the same height. However, the symmetric `slotDist` also disables the tiebreaker in the opposite direction — when `slot(ours) > slot(cand) + maxDist` — which is incorrect. In that direction, the candidate was issued *earlier* and its issuer could not have built on top of our block. The VRF tiebreaker should therefore remain active, but it is silently suppressed, causing the node to incorrectly retain its current chain even when the candidate has a strictly better VRF value.

---

### Finding Description

In `comparePraos` (`Praos/Common.hs`, lines 130–168), the `vrfArmed` predicate decides whether the VRF tiebreaker is applied:

```haskell
vrfArmed v1 v2 = case tiebreakerFlavor of
  UnrestrictedVRFTiebreaker -> True
  RestrictedVRFTiebreaker maxDist ->
    slotDist (ptvSlotNo v1) (ptvSlotNo v2) <= maxDist

slotDist :: SlotNo -> SlotNo -> SlotNo
slotDist s t
  | s >= t    = s - t
  | otherwise = t - s
```

`v1 = ours`, `v2 = cand`. `slotDist` returns `|slot(ours) − slot(cand)|`, which is symmetric.

The documented rationale for `RestrictedVRFTiebreaker` is explicitly **one-sided**:

> "When two blocks A and B with the same block number differ in their slot number by more than Δ, say `slot(A) + Δ < slot(B)`, the issuer of B should have been able to mint a block with a block number higher than A … we do not want to allow the block that was diffused later to still win by having a better VRF tiebreaker."

This describes only the case `slot(cand) > slot(ours) + maxDist`. The symmetric implementation additionally suppresses the tiebreaker when `slot(ours) > slot(cand) + maxDist`, i.e., when our current block was issued much *later* than the candidate's block. In that scenario the candidate's issuer could not have built on top of our block (our block did not exist yet), so the rationale for suppression does not apply. The tiebreaker should fire, but it does not.

This is the direct analog of the PegOracle bug: `min(p1,p2)/max(p1,p2)` is symmetric and triggers a depeg event in both directions, whereas only the direction `pegged < underlying` is the intended trigger. Here, `|slot_ours − slot_cand|` is symmetric and suppresses the tiebreaker in both directions, whereas only the direction `slot_cand > slot_ours + maxDist` is the intended suppression.

In Conway era and later, `maxDist = 5` is hardcoded:

```haskell
shelleyVRFTiebreakerFlavor
  | isBeforeConway (Proxy @era) = UnrestrictedVRFTiebreaker
  | otherwise                   = RestrictedVRFTiebreaker 5
```

---

### Impact Explanation

**Classification: High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain beyond the intended security assumptions.**

When a node's current chain tip was issued at a high slot number and a competing candidate tip was issued at a much lower slot number (same block height, difference > 5 slots in Conway), the VRF tiebreaker is incorrectly disabled. The node retains its current chain even if the candidate has a strictly better (lower) VRF value. Because the VRF tiebreaker is the mechanism that breaks ties between equal-length chains and prevents geographic concentration of block production (the "Frankfurt problem"), suppressing it in this direction means:

1. A node that first receives an adversarially-crafted block at a high slot number will be unable to switch to the honest chain's block at a lower slot number, even if the honest block has a better VRF value.
2. The adversary's chain is extended first, making it longer, and the honest chain can no longer catch up at that block height.
3. This can cause persistent chain divergence between nodes that saw the adversary's block first and nodes that saw the honest block first.

---

### Likelihood Explanation

**Medium.** The adversary only needs to be a legitimately elected block producer — no key compromise, stake majority, or privileged access is required. With `maxDist = 5` in Conway, any slot battle where the two competing blocks differ by more than 5 slots triggers the bug. Slot battles (multi-leader slots) occur in approximately 0.127% of all slots on mainnet. Among those, a slot difference > 5 is common when one pool is slow to propagate its block. An adversary who is elected at a slot number more than 5 slots after the honest block's slot can exploit this by ensuring their block reaches target nodes before the honest block does.

---

### Recommendation

Replace the symmetric `slotDist` with a directional check. The VRF tiebreaker should only be suppressed when the **candidate** was issued much later than ours:

```haskell
-- Correct: only suppress when cand was issued much later than ours
vrfArmed v1 v2 = case tiebreakerFlavor of
  UnrestrictedVRFTiebreaker -> True
  RestrictedVRFTiebreaker maxDist ->
    -- Only disable if slot(cand) > slot(ours) + maxDist
    -- i.e., the candidate was issued much later and should have built on top
    not (ptvSlotNo v2 > ptvSlotNo v1 + maxDist)
```

This preserves the intended protection against late-diffused blocks winning via VRF, while correctly allowing the tiebreaker to fire when the candidate was issued earlier than the current chain's tip.

### Proof of Concept

Setup (Conway era, `maxDist = 5`):

| | Slot | Block No | VRF value (lower = better) |
|---|---|---|---|
| **Adversary block** (ours) | 106 | N | 100 |
| **Honest block** (cand) | 100 | N | 1 |

1. Node starts syncing. Adversary presents their block (slot 106, block N) first. Node adopts it as current chain.
2. Honest block (slot 100, block N) arrives as a candidate.
3. `comparePraos` is called with `ours = adversary (slot 106)`, `cand = honest (slot 100)`.
4. `slotDist 106 100 = 6 > 5 = maxDist` → `vrfArmed = False` → VRF tiebreaker suppressed.
5. Result: `ShouldNotSwitch EQ` — node stays on adversary's chain.
6. **Correct behavior**: `slot(cand) = 100 < slot(ours) = 106` → the candidate was issued *earlier*, so the tiebreaker should fire → VRF comparison: `1 < 100` → `ShouldSwitch` → node switches to honest chain.
