### Title
Peras Vote Authorization Bypass via Missing Signature Verification in `validatePerasVote` — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance used for all block types implements `validatePerasVote` by only checking whether the attacker-controlled `pvVoteVoterId` field is present in the stake distribution. The `PerasVote` data type carries no cryptographic signature, so there is no proof-of-ownership check. Any unprivileged peer can forge votes claiming to be any registered stake pool, bypass the authorization gate, and potentially drive an honest node to accept a Peras certificate for an attacker-chosen block. `validatePerasCert` compounds the issue by accepting every certificate unconditionally.

---

### Finding Description

**Root cause — wrong identity checked, no proof of ownership:**

The `PerasVote` data type contains no signature field:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound  :: PerasRoundNo
  , pvVoteBlock  :: Point blk
  , pvVoteVoterId :: PerasVoterId   -- attacker-controlled KeyHash
  }
``` [1](#0-0) 

`validatePerasVote` performs only a stake-distribution membership lookup on that attacker-supplied field:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [2](#0-1) 

`lookupPerasVoteStake` resolves the stake purely from `pvVoteVoterId`:

```haskell
lookupPerasVoteStake vote distr =
  Map.lookup (pvVoteVoterId vote) (unPerasVoteStakeDistr distr)
``` [3](#0-2) 

This is the direct analog of the external report's `msg.sender` vs `_receiver` bug: the claimed identity (`pvVoteVoterId`) is checked against a whitelist (stake distribution), but there is no cryptographic proof that the network peer actually controls the key corresponding to that identity. Any peer can set `pvVoteVoterId` to any registered pool's `KeyHash` and the check passes.

`validatePerasCert` is equally broken — it accepts every certificate unconditionally:

```haskell
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [4](#0-3) 

**Attacker-controlled entry path:**

Inbound votes from peers are processed by `processVotes` in the vote diffusion layer:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [5](#0-4) 

This validator is wired into the production node-to-node diffusion layer via `makePerasVotePoolWriterFromChainDB`: [6](#0-5) 

The deduplication gate uses `PerasVoteId = (PerasRoundNo, PerasVoterId)`, so one forged vote per `(round, pool)` pair passes through. An attacker can submit one forged vote for every registered pool in a given round.

Once enough forged votes accumulate for the same target, `votesReachQuorum` returns `True`: [7](#0-6) 

`forgePerasCert` then produces a `ValidatedPerasCert` for the attacker-chosen block, which is stored and used for chain selection boosting.

---

### Impact Explanation

**High.** An unprivileged peer with network access can:

1. Enumerate registered pool key hashes from the public stake distribution.
2. Craft `PerasVote` messages with `pvVoteVoterId` set to those key hashes, `pvVoteRound` set to the current round, and `pvVoteBlock` pointing to any block.
3. Send these votes to an honest node; each passes `validatePerasVote` because the voter ID is in the stake distribution.
4. Once the forged votes' combined stake exceeds the quorum threshold, the node forges a Peras certificate for the attacker-chosen block.
5. That certificate boosts the attacker-chosen block in chain selection, potentially causing the honest node to prefer a non-canonical or adversarially-selected chain.

This constitutes a bypass of Peras vote/certificate authorization that lets an unprivileged peer influence chain selection beyond the intended security assumptions of the Peras protocol.

---

### Likelihood Explanation

**High.** The attack requires only:
- Network connectivity to a node running the Peras vote diffusion miniprotocol (no privileged keys, no stake, no special role).
- Knowledge of registered pool key hashes, which are publicly available on-chain.

The vulnerable code path is active in the production diffusion layer with no feature flag guarding it.

---

### Recommendation

1. Add a cryptographic signature field to `PerasVote` (e.g., a BLS or Ed25519 signature over `(round, block, voterId)` produced with the pool's registered signing key).
2. Implement proper signature verification in `validatePerasVote` — verify the signature against the public key registered for `pvVoteVoterId` in the stake distribution, not merely check membership.
3. Implement proper certificate verification in `validatePerasCert` — verify the aggregate signature over the claimed voter set.
4. Track the referenced GitHub issues (`#73`, `#120`) as security-critical blockers before enabling Peras vote diffusion on any production network.

---

### Proof of Concept

```
Attacker (unprivileged peer):

1. Query stake distribution → obtain pool key hashes {P1, P2, ..., Pn}
2. For each Pi with stake si:
     craft PerasVote { pvVoteRound = currentRound
                     , pvVoteBlock = targetBlock   -- attacker-chosen
                     , pvVoteVoterId = Pi }
3. Send all crafted votes to honest node via vote diffusion miniprotocol.
4. processVotes calls validatePerasVote for each vote.
   validatePerasVote only calls lookupPerasVoteStake(vote, stakeDistr)
   → Map.lookup Pi stakeDistr → Just si  (no signature checked)
   → vote accepted as ValidatedPerasVote with stake si
5. Once sum(si) > quorumThreshold:
   votesReachQuorum returns Just ValidatedPerasVotesWithQuorum
   → forgePerasCert produces ValidatedPerasCert for targetBlock
6. Honest node now holds a Peras certificate boosting targetBlock
   in chain selection, without any legitimate pool having voted.
```

votesReachQuorum ::
  StandardHash blk =>
  PerasCfg blk ->
  [ValidatedPerasVote blk] ->
  Maybe (ValidatedPerasVotesWithQuorum blk)
votesReachQuorum cfg votes =
  case votes of
    -- We need at least one vote to determine who these votes are for, so we
    -- can't vacuously reach a quorum, even if the quorum threshold is 0.
    [] -> Nothing
    -- If we have at least one vote, we must check that all votes are for the
    -- same target, and that their total stake of is above the quorum threshold.
    (v0 : vs)
      | not (allVotesMatchTarget v0 vs) ->
          Nothing
      | not votesHaveEnoughStake ->
          Nothing
      | otherwise ->
          Just
            ValidatedPerasVotesWithQuorum
              { vpvqTarget = getPerasVoteTarget v0
              , vpvqVotes = v0 :| vs
              , vpvqPerasCfg = cfg
              }
 where
  totalVoteStake =
    mconcat (vpvVoteStake <$> votes)
  votesHaveEnoughStake =
    stakeAboveThreshold cfg totalVoteStake
  allVotesMatchTarget target =
    all ((== (getPerasVoteTarget target)) . getPerasVoteTarget)
```

makePerasVotePoolWriterFromChainDB ::
  (StandardHash blk, IOLike m) =>
  SystemTime m ->
  -- | This is needed for validating votes (since its during the validation of
  -- votes that we give them a verified weight. In the future, we won't read it
  -- from the stake distr directly, but rather use the committee selection data)
  STM m PerasVoteStakeDistr ->
  ChainDB m blk ->
  ObjectPoolWriter (PerasVoteId blk) (PerasVote blk) m
makePerasVotePoolWriterFromChainDB systemTime getStakeDistrSTM chainDB =
  ObjectPoolWriter
    { opwObjectId = getPerasVoteId
    , opwAddObjects = \votes ->
        processVotes
          systemTime
          (ChainDB.getPerasVoteIds chainDB)
          -- TODO: in the future we won't need just the stake distribution for
          -- validating votes, but also the whole committee selection context
          -- (containing vote weights of committee members = voters)
          (\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
          -- We do not want to block the writer thread on waiting for ChainSel
          -- side-effects to complete, so we use the async version of adding
          -- votes to the ChainDB and ignore the returned promise.
          -- The async action (if any) is still launched and executed behind the
          -- scenes even though we drop the promise.
          (void . ChainDB.addPerasVoteWithAsyncCertHandling chainDB)
          votes
    , opwHasObject = do
        voteIds <- ChainDB.getPerasVoteIds chainDB
        pure $ \voteId -> Set.member voteId voteIds
    }
