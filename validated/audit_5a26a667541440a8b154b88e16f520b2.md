### Title
Silent Token Mint Without Delivery on Unregistered Recipient — (`contracts/nbtc/src/lib.rs`)

### Summary

`safe_mint` in the nBTC contract mints tokens to the bridge's own balance **before** checking whether the recipient account is registered. If the recipient is not registered, the function returns `U128(0)` without reverting the prior mint. The result is that nBTC supply is permanently inflated into the bridge's balance while the depositing user receives nothing, and their BTC UTXO is consumed by the deposit flow.

### Finding Description

In `contracts/nbtc/src/lib.rs`, `safe_mint` executes in this order:

1. **Line 112** — `self.token.internal_deposit(&self.bridge_id, amount.into())` — unconditionally mints `amount` nBTC into the bridge's own token balance, increasing total supply.
2. **Lines 114–116** — checks whether `account_id` has a storage-registered account. If not, the function **returns `PromiseOrValue::Value(U128(0))`** immediately, without reverting the deposit performed in step 1.
3. Only if the account is registered does the function proceed to transfer the minted tokens to the user (lines 118–123). [1](#0-0) 

The return value `U128(0)` is the same type used to signal "zero tokens transferred" in a successful `ft_transfer_call` resolution. The bridge's deposit callback receives this value and has no way to distinguish "recipient was not registered, tokens are stuck in bridge balance" from a legitimate zero-transfer outcome. The minted tokens remain in `bridge_id`'s nBTC balance with no automatic attribution to the user and no `lost_found` entry created.

This is the direct analog of the `create2` finding: just as `create2` always returns the deterministic address (never zero) regardless of whether deployment succeeded — making `iszero(result)` the wrong check — `internal_deposit` to `bridge_id` always succeeds regardless of whether the recipient is registered, making the subsequent `is_none()` check the wrong gate for reverting the mint.

### Impact Explanation

- The user's BTC UTXO is consumed by the deposit flow (marked in `verified_deposit_utxo`), permanently locking their BTC in the bridge's MPC-controlled address.
- No nBTC is credited to the user.
- nBTC total supply is inflated by `amount` into the bridge's balance, breaking the 1:1 BTC-backing invariant from the user's perspective.
- The user has no self-service recovery path: the UTXO is already verified so `request_refund` is blocked, and no `lost_found` entry is created.

This matches **Critical — significant loss or permanent locking of user funds** and **Medium — permanent burning below backed supply / broken callback rollback**. [2](#0-1) 

### Likelihood Explanation

Any user who deposits BTC without having previously called `storage_deposit` on the nBTC contract triggers this path. This is a realistic first-time-user scenario: the BTC deposit address is derived from the user's NEAR account ID and requires no prior nBTC interaction. A user can send BTC, have a relayer submit the proof, and lose their deposit entirely because they never registered storage on the token contract.

### Recommendation

Move `internal_deposit` to **after** the registration check, or revert (panic) when the recipient is not registered rather than returning `U128(0)`. The safest fix is:

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "...");

    // Check registration BEFORE minting
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0)); // no tokens minted
    }

    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ... proceed with transfer
}
```

Alternatively, auto-register the account before minting (as `mint_inner` does at line 342–343), which is the pattern already used by the `mint` function. [3](#0-2) 

### Proof of Concept

1. User `alice.near` derives their BTC deposit address from the bridge (no nBTC storage registration required).
2. Alice sends 0.01 BTC to that address.
3. A relayer calls `verify_deposit` on the satoshi-bridge with a valid `TxInclusionProof`.
4. The bridge calls `nbtc.safe_mint(account_id="alice.near", amount=1_000_000, msg=None)`.
5. Inside `safe_mint`: `internal_deposit(&bridge_id, 1_000_000)` executes — bridge's nBTC balance increases by 1,000,000 satoshis.
6. `self.token.accounts.get(&"alice.near")` returns `None` (not registered).
7. Function returns `U128(0)`.
8. Alice's UTXO is marked in `verified_deposit_utxo`; she cannot request a refund.
9. Alice has 0 nBTC. Bridge holds 1,000,000 extra nBTC. Alice's 0.01 BTC is permanently locked. [4](#0-3)

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }
