### Title
Front-Running `request_refund` with Attacker-Controlled `refund_address` Redirects User BTC to Attacker - (File: `contracts/satoshi-bridge/src/refund.rs`)

### Summary

When a user's `DepositMsg` does not pre-authorize a `refund_address` (i.e., `deposit_msg.refund_address` is `None`), any NEAR account can call `request_refund` with the same public BTC proof data but supply an attacker-controlled `refund_address`. Because the bridge enforces a one-refund-per-UTXO invariant keyed on `utxo_storage_key`, the attacker's front-run call consumes the slot, the victim's call reverts, and the stored refund request points to the attacker's Bitcoin address. After the timelock elapses, the attacker can execute the refund and receive the victim's BTC.

### Finding Description

**Root cause — `request_refund_callback` accepts any `refund_address` when `deposit_msg.refund_address` is `None`:**

In `internal_request_refund`, the only guard on `refund_address` is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [1](#0-0) 

When `deposit_msg.refund_address` is `None` (the common case for users who did not embed a refund address at deposit time), the `refund_address` argument is accepted verbatim from the caller with no further validation.

**One-time-use slot — `utxo_storage_key` is unique per UTXO:**

In `request_refund_callback`, the key is derived from the public Bitcoin `tx_id` and `vout`, then checked for uniqueness:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [2](#0-1) 

All inputs needed to compute `utxo_storage_key` (`tx_id`, `vout`) are derived from the Bitcoin transaction, which is public. The full `request_refund` call parameters (`deposit_msg`, `tx_bytes`, `vout`, `proof`) are visible in the NEAR mempool before inclusion.

**Stored refund address is the attacker's:**

The `RefundRequest` stored on-chain uses the caller-supplied `refund_address`:

```rust
let refund_request = RefundRequest {
    ...
    refund_address,
    ...
};
self.data_mut().refund_requests.insert(utxo_storage_key, refund_request.into());
``` [3](#0-2) 

**`finalize_refund_with_psbt` uses the stored `refund_address` to build the Bitcoin output:**

```rust
let refund_address = refund_request.refund_address.clone();
``` [4](#0-3) 

The refund PSBT is constructed paying to this address, and the MPC network signs it. Once signed, the BTC transaction sends funds to the attacker's address.

**`internal_sign_btc_transaction` has no caller-identity check:**

```rust
pub fn internal_sign_btc_transaction(
    &mut self,
    btc_pending_sign_id: String,
    sign_index: usize,
    key_version: u32,
) -> Promise {
    ...
    require!(
        btc_pending_info.signatures[sign_index].is_none(),
        "Already signed"
    );
``` [5](#0-4) 

No check verifies that the caller is the `account_id` stored in `BTCPendingInfo`. The attacker (who created the `BTCPendingInfo` via their front-run `execute_refund` call) can drive the signing flow.

**End-to-end exploit path:**

1. Victim sends BTC to a deposit address derived from `DepositMsg { recipient_id: victim, refund_address: None, ... }`.
2. Victim submits `request_refund(deposit_msg, refund_address="bc1qvictim...", tx_bytes, vout, proof)` to NEAR.
3. Attacker observes the pending NEAR transaction, extracts all parameters, and submits `request_refund(deposit_msg, refund_address="bc1qattacker...", tx_bytes, vout, proof)` with higher priority (or simply races it).
4. Attacker's call lands first; `request_refund_callback` stores `RefundRequest { refund_address: "bc1qattacker...", ... }`.
5. Victim's call reverts: `"Refund request already exists for this UTXO"`.
6. After `unsafe_refund_timelock_sec` elapses (if DAO does not reject), attacker calls `execute_refund(utxo_storage_key)`, creating a `BTCPendingInfo` with the attacker's account and address.
7. Attacker calls `sign_btc_transaction`; MPC signs the PSBT paying `bc1qattacker...`.
8. Attacker broadcasts the signed transaction; victim's BTC is transferred to the attacker.

### Impact Explanation

**Critical.** A fully unprivileged attacker can redirect a victim's BTC refund to an attacker-controlled Bitcoin address, constituting direct theft of user funds. The victim's BTC is locked in the deposit address until the DAO manually rejects the attacker's refund request (requiring active monitoring), and even then the victim must retry. If the DAO does not act within `unsafe_refund_timelock_sec`, the theft is irreversible once the BTC transaction is broadcast and confirmed on Bitcoin.

### Likelihood Explanation

**Medium-High.** All parameters needed to front-run are observable from the NEAR mempool. The attacker pays only a small storage deposit. The attack requires no privileged access, no leaked keys, and no cryptographic break. The only mitigation is the `unsafe_refund_timelock_sec` window and active DAO monitoring, which is an operational control, not a code-level guarantee. Any user whose `DepositMsg` omits `refund_address` is vulnerable.

### Recommendation

Bind the `refund_address` to the caller's identity at request time, or require that `refund_address` be committed in the `DepositMsg` before the deposit is made (i.e., reject `request_refund` when `deposit_msg.refund_address` is `None`). Alternatively, store the `requester_account_id` in `RefundRequest` and enforce in `execute_refund` that only the original requester (or a privileged role) can execute it, preventing the attacker from driving the signing flow even if they front-run the request.

### Proof of Concept

```
// Victim's DepositMsg (refund_address: None — common case)
deposit_msg = { recipient_id: "victim.near", refund_address: null }

// Victim submits to NEAR mempool (all params are observable):
request_refund(deposit_msg, "bc1qvictim...", tx_bytes, vout=0, proof)

// Attacker observes mempool, front-runs with attacker's BTC address:
request_refund(deposit_msg, "bc1qattacker...", tx_bytes, vout=0, proof)
// → succeeds; RefundRequest { refund_address: "bc1qattacker..." } stored

// Victim's call now reverts:
// → "Refund request already exists for this UTXO"

// After unsafe_refund_timelock_sec (DAO did not reject):
execute_refund(utxo_storage_key)          // attacker calls
sign_btc_transaction(pending_id, 0, 0)   // attacker calls; MPC signs
// → BTC transaction pays bc1qattacker...
// → Victim's BTC stolen
```
