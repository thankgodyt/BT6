### Title
Stub `validatePerasCert` Accepts Any Peer-Supplied Peras Certificate Without Cryptographic Verification, Enabling Fake Weight Boost Injection into Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` implementation is an acknowledged stub that unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or semantic checks. Because the Peras certificate diffusion mini-protocol is reachable by any unprivileged peer, an attacker can craft a `PerasCert` that names an adversarial block as the boosted block. The stub accepts it, the `PerasCertDB` stores it, and `implGetWeightSnapshot` feeds the resulting `PerasWeight` boost directly into chain selection. The adversarial fork thereby acquires an inflated `wsvTotalWeight`, potentially causing the honest node to switch away from the canonical chain.

---

### Finding Description

**Root cause — `validatePerasCert` stub always succeeds:** [1](#0-0) 

```haskell

-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This is the only `BlockSupportsPeras` instance in the production codebase. It skips every check that should be performed: BLS aggregate-signature verification, voter eligibility proofs, quorum threshold, round-number validity, and whether the boosted block actually exists on a valid chain. The `Cert/V1.hs` module itself warns that serialisation validation is minimal and that semantic/cryptographic checks must be performed later — but no such later check exists. [2](#0-1) 

**Inbound path — `processCerts` calls the stub on every peer-supplied cert:** [3](#0-2) 

`makePerasCertPoolWriterFromChainDB` (the production writer used by the `PerasCertDiffusion` mini-protocol) calls `processCerts … (validatePerasCert mkPerasParams)`. The `-- TODO replace when actual plumbing is in place` comment confirms this is placeholder code on the live inbound path. [4](#0-3) 

**Storage — `implAddCert` also carries an open TODO for validation:** [5](#0-4) 

The only guard in `implAddCert` is a duplicate-round-number check (`Set.member roundNo pcdsCertIds`). No boost-value bound, no signature check, no quorum check. [6](#0-5) 

**Weight propagation — every stored cert's boost flows into chain selection:**

`implGetWeightSnapshot` iterates all certs in `pcdsCertsByTicket` and calls `getPerasCertBoost cert` (which reads `vpcCertBoost`) to build the `PerasWeightSnapshot`. [7](#0-6) 

`chainSelectionForBlock` reads this snapshot and passes it to `preferAnchoredCandidate`, which compares `wsvTotalWeight` (= `BlockNo + weightBoost`) between the current chain and the candidate. [8](#0-7) 

`wsvTotalWeight` is the decisive comparison in `WeightedSelectView.preferCandidate`: [9](#0-8)

### Impact Explanation

An adversarial peer can send a `PerasCert` whose `pcCertBoostedBlock` points to any block on an adversarial fork. Because `validatePerasCert` always returns `Right`, the cert is stored with boost `perasWeight params`. `implGetWeightSnapshot` then includes this boost in the weight snapshot used by every subsequent chain-selection run. If the adversarial fork's `wsvTotalWeight` (its block count plus the injected boost) exceeds the honest chain's total weight, the node switches to the adversarial fork — accepting an invalid or non-canonical chain. This is a **chain-selection bug triggered by an unprivileged peer via a crafted protocol message**, matching the "High" impact tier: an honest node is made to prefer a non-canonical or less-secure chain beyond the intended security assumptions.

---

### Likelihood Explanation

The `PerasCertDiffusion` mini-protocol is exposed to every connected node-to-node peer. No stake, key material, or operator privilege is required to send a `PerasCert` message. The attacker only needs to connect as a normal peer and send a well-formed CBOR-encoded `PerasCert` (the serialisation checks are minimal per the module comment). The stub validation guarantees acceptance. Likelihood is **high** given the zero-barrier entry path.

---

### Recommendation

1. Replace the stub `validatePerasCert` with a real implementation that verifies the BLS aggregate signature over `(roundNo, boostedBlock)`, checks each voter's eligibility proof, and confirms the aggregate stake meets the quorum threshold defined in `PerasParams`.
2. In `implAddCert`, enforce that `vpcCertBoost` equals exactly `perasWeight params` and reject any cert whose boost deviates.
3. Add a bound check in `addToPerasWeightSnapshot` / `implGetWeightSnapshot` so that the total boost for any single block point cannot exceed `perasWeight params` (one cert per round, one boost per round).
4. Remove the `-- TODO replace when actual plumbing is in place` placeholder in `makePerasCertPoolWriterFromChainDB` and wire in the real `PerasCfg` before enabling the diffusion path on any network.

---

### Proof of Concept

On a private testnet with Peras enabled:

1. Connect a malicious peer to an honest node via the `PerasCertDiffusion` mini-protocol.
2. Craft a `PerasCert` with `pcCertRound = <any fresh round>` and `pcCertBoostedBlock = <tip of adversarial fork>`. Encode it as valid CBOR (the `FromCBOR` instance in `Cert/V1.hs` only checks list lengths and field counts).
3. Send the cert. `processCerts` calls `validatePerasCert mkPerasParams` → always `Right`. The cert is stored in `PerasCertDB` with `vpcCertBoost = perasWeight params`.
4. `implGetWeightSnapshot` now returns a snapshot where the adversarial fork's tip has boost `perasWeight params`.
5. The next `chainSelectionForBlock` call computes `wsvTotalWeight(adversarial) = blockNo + perasWeight params`. If this exceeds `wsvTotalWeight(honest)`, the node switches to the adversarial fork.
6. Repeat with a new round number (bypassing the duplicate-round guard) to stack additional boosts on the same adversarial block point, since `mkPerasWeightSnapshot` uses `Map.insertWith (<>)` to accumulate weights for the same point. [10](#0-9)
