### Title
`initBound` Hardcodes `NoPerasEnabled` for `boundPerasRound`, Silently Disabling Peras Round Queries for Peras-Enabled Eras — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/HardFork/History/Summary.hs`)

---

### Summary

The genesis `Bound` value `initBound` always sets `boundPerasRound = NoPerasEnabled`. The `mkUpperBound` function propagates this value to every subsequent era bound via the `PerasEnabled` applicative's `<*>` operator, which behaves like `Maybe`'s `<*>` and short-circuits to `NoPerasEnabled` whenever either operand is `NoPerasEnabled`. As a result, even when an era is explicitly configured with `eraPerasRoundLength = PerasEnabled rl`, every computed `Bound` retains `boundPerasRound = NoPerasEnabled`. The query interpreter in `Qry.hs` then fails all Peras-round expressions (`EAbsToRelPerasRoundNo`, `ERelToAbsPerasRoundNo`) for those eras, silently disabling Peras voting and certificate validation.

---

### Finding Description

**Root cause — `initBound` hardcodes `NoPerasEnabled`:** [1](#0-0) 

The genesis bound always carries `boundPerasRound = NoPerasEnabled`. The TODO comment at line 98–100 acknowledges this is unresolved.

**Propagation in `mkUpperBound`:** [2](#0-1) 

The critical line is:
```haskell
boundPerasRound = addPerasRounds <$> inEraPerasRounds <*> boundPerasRound lo
```
`PerasEnabled` is `Maybe`-like. When `boundPerasRound lo = NoPerasEnabled`, the `<*>` short-circuits to `NoPerasEnabled` regardless of `inEraPerasRounds`. So even if `eraPerasRoundLength = PerasEnabled rl` (making `inEraPerasRounds = PerasEnabled n`), the result is still `NoPerasEnabled`. Every era bound derived from `initBound` inherits this corruption.

**`neverForksSummary` accepts `PerasEnabled PerasRoundLength` but uses `initBound`:** [3](#0-2) 

The function signature accepts `PerasEnabled PerasRoundLength` (implying Peras can be enabled), but `eraStart = initBound` always has `boundPerasRound = NoPerasEnabled`. This is the direct analog of the external report: the type accepts multiple variants (Peras-enabled / disabled) but the initialization only handles one correctly.

**`summarize` (reference implementation) works around this with `initBoundWithPeras`:** [4](#0-3) 

The comment explicitly states this function is only used for testing and that it is "rather difficult to parameterise the test suite, as it requires also parameterise many non-test functions, like `HF.initBound`." The production path (`reconstructSummaryLedger`) does not have this workaround and uses `initBound` directly.

**Query interpreter fails for all Peras-round expressions:** [5](#0-4) 

`EAbsToRelPerasRoundNo` binds `eraStartPerasRound <- PerasEnabledT . Just $ boundPerasRound eraStart`. When `boundPerasRound eraStart = NoPerasEnabled`, the `PerasEnabledT Maybe` monad bind short-circuits to `Nothing`, causing `evalExprInEra` to return `Nothing` for this expression. The same failure occurs in `ERelToAbsPerasRoundNo`: [6](#0-5) 

**Downstream: Peras voting queries throw `PerasQryExceptionPerasDisabled`:** [7](#0-6) 

`perasRoundStart` calls `HF.perasRoundNoToSlot`, which returns `NoPerasEnabled` (because the query fails in every era), and then throws `PerasQryExceptionPerasDisabled`. This disables Peras round-start lookups entirely, breaking the voting view used for certificate validation and chain selection weight boosts.

---

### Impact Explanation

When a node is configured with Peras-enabled eras (via `eraPerasRoundLength = PerasEnabled rl`), the `boundPerasRound` field of every era bound is silently set to `NoPerasEnabled` due to the `initBound` initialization and `mkUpperBound` propagation. This causes:

1. `perasRoundNoToSlot` and `slotToPerasRoundNo` to return `NoPerasEnabled` for all slots, as if Peras were not configured.
2. `perasRoundStart` to throw `PerasQryExceptionPerasDisabled`, preventing any Peras round-based certificate validation.
3. Peras weight boosts to never be applied during chain selection, because the node cannot determine which Peras round any slot belongs to.

An unprivileged peer can exploit this by presenting a competing chain that lacks Peras certificate boosts. Because the honest node cannot apply Peras weights (all Peras queries fail), it cannot distinguish a Peras-boosted canonical chain from an unboosted adversarial fork. This directly undermines the chain-selection security guarantees that Peras is designed to provide, mapping to the **High** impact category: a chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.

---

### Likelihood Explanation

The bug is present in all code paths that start from `initBound`: `neverForksSummary` (used for single-era chains) and the production `reconstructSummaryLedger` path (which the codebase comment confirms does not use `initBoundWithPeras`). Any node that activates Peras (sets `eraPerasRoundLength = PerasEnabled rl`) will silently have all Peras round queries fail. No special attacker capability is required — the attacker only needs to present a valid competing chain. The TODO comment at `initBound` line 98–100 confirms this is a known unresolved issue.

---

### Recommendation

1. **Fix `initBound`**: Initialize `boundPerasRound` to `PerasEnabled (PerasRoundNo 0)` unconditionally, or make it configurable as the TODO suggests. The `summarize` reference implementation already demonstrates the correct approach via `initBoundWithPeras`.
2. **Fix `mkUpperBound`**: When `eraPerasRoundLength = PerasEnabled rl` but `boundPerasRound lo = NoPerasEnabled`, the function should initialize `boundPerasRound` to `PerasEnabled (PerasRoundNo 0)` rather than propagating `NoPerasEnabled`. The current `<*>` short-circuit silently discards Peras round information for Peras-enabled eras.
3. **Add an invariant check in `invariantSummary`**: Assert that if `eraPerasRoundLength = PerasEnabled _` then `boundPerasRound eraStart /= NoPerasEnabled`, catching this mismatch at summary construction time.

```haskell
      (EpochSize 100)

```

**Step 2**: Query the Peras round for slot 0:
```haskell
runQuery (slotToPerasRoundNo (SlotNo 0)) summary
-- Returns: Right NoPerasEnabled
-- Expected: Right (PerasEnabled (PerasRoundNo 0, 0, 10))
```

**Step 3**: Trace the failure:
- `summary` has `eraStart = initBound` with `boundPerasRound = NoPerasEnabled`
- `evalExprInEra` evaluates `EAbsToRelPerasRoundNo` → `PerasEnabledT . Just $ NoPerasEnabled` → bind short-circuits → `Nothing`
- `runQuery` finds no era where the expression succeeds → returns `Right NoPerasEnabled`
- `perasRoundStart (PerasRoundNo 0)` → `throwError PerasQryExceptionPerasDisabled`

**Step 4**: Confirm `summarize` (test path) does not exhibit this bug because it uses `initBoundWithPeras = initBound{boundPerasRound = PerasEnabled (PerasRoundNo 0)}`, confirming the fix is straightforward.

```haskell
mkUpperBound EraParams{..} lo hiEpoch =
  Bound
    { boundTime = addRelTime inEraTime $ boundTime lo
    , boundSlot = addSlots inEraSlots $ boundSlot lo
    , boundEpoch = hiEpoch
    , boundPerasRound = addPerasRounds <$> inEraPerasRounds <*> boundPerasRound lo
    }
```
