### Title
Duplicate `BTCPendingInfo` Accumulation on Zcash BranchId Boundary Re-execution — (`contracts/satoshi-bridge/src/zcash_utils/refund.rs` / `contracts/satoshi-bridge/src/refund.rs`)

### Summary

`execute_refund_callback` / `finalize_refund_with_psbt` intentionally allow re-execution after a consensus branch change, but do not remove the prior `BTCPendingInfo` before inserting a new one. When the Zcash block height crosses a `BranchId` activation boundary between two calls, `PsbtWrapper::new` derives a different `branch_id`, `get_pending_id()` returns a different txid, and `finalize_refund_with_psbt` inserts a second `BTCPendingInfo` keyed on the new txid while the first remains in `btc_pending_infos`. Both entries can be signed and broadcast, but only one can confirm on-chain; the other is orphaned in bridge state until a trusted relayer manually cleans it up.

### Finding Description

**Entry point:** `execute_refund` is a public, payable function with no role gate. [1](#0-0) 

**Guard that is intentionally bypassed:** `load_refund_request_for_execute` blocks re-execution only when the UTXO was claimed by a *deposit*. When `executed == true` (set by the first `execute_refund`), the guard explicitly passes:

```
!verified_deposit_utxo.contains(key) || refund_request.executed
= !true || true = true  → allowed
``` [2](#0-1) 

The code comment confirms this is intentional — re-execution is designed to handle consensus branch changes: [3](#0-2) 

**Branch-id derivation:** `PsbtWrapper::new` calls `get_branch_id(current_height, config)`, which returns `Nu6_1` or `Nu6_2` depending on whether the block height has crossed the activation boundary (mainnet: 3,364,600; testnet: 4,052,000). [4](#0-3) [5](#0-4) 

**Txid divergence:** `get_pending_id()` computes the Zcash txid by freezing a `TransactionData` that embeds `branch_id`. A different `branch_id` produces a cryptographically distinct txid. [6](#0-5) [7](#0-6) 

**Missing cleanup:** `finalize_refund_with_psbt` only checks whether the *new* txid already exists in `btc_pending_infos`. It never removes the prior pending info for the same UTXO: [8](#0-7) 

**Capacity gate:** The default `max_pending_sign_txs` is 1. For the second call to pass `require_pending_sign_capacity`, the first pending info must have already been signed (moved from `btc_pending_sign_ids` to `btc_pending_verify_list`) before the second `execute_refund` is submitted. This is the realistic sequence: sign txid_1, wait for the boundary, call `execute_refund` again. [9](#0-8) 

**Cleanup is gated on finalization:** `remove_refund_pending_tx_id` (the only cleanup path for orphaned refund pending infos) requires the refund request to already be gone — which only happens after `verify_refund_finalize_callback` confirms one of the two transactions on-chain. Until then, the orphaned entry is stuck. [10](#0-9) [11](#0-10) 

### Impact Explanation

Two `BTCPendingInfo` entries exist for the same deposit UTXO. Both are signed by the MPC chain-signature service (wasting signing budget). Both signed transactions are broadcastable to the Zcash network; only one can confirm (the UTXO is spent). The other is permanently orphaned in `btc_pending_infos` until a `#[trusted_relayer]`-gated cleanup call is made after finalization. During this window the orphaned entry occupies a slot in `btc_pending_sign_ids`, potentially blocking the user from creating new transactions if their limit is low. No funds are lost or stolen — the refund still reaches the user — but the bridge accumulates irrecoverable state without operator intervention.

Impact classification: **Medium** — stuck bridge state requiring operator intervention; no direct theft or permanent fund loss.

### Likelihood Explanation

The trigger condition (two `execute_refund` calls bracketing a `BranchId` activation boundary) is realistic: NU6.1 and NU6.2 are known, scheduled upgrades. Any user who submitted a refund request before the boundary and whose first pending info was signed before the boundary crossed can trivially call `execute_refund` again afterward. No privileged access is required.

### Recommendation

In `finalize_refund_with_psbt`, before inserting the new `BTCPendingInfo`, check whether any existing pending info for the same UTXO storage key already exists and remove it (along with its `btc_pending_sign_ids` entry). Alternatively, store the current `btc_pending_id` on the `RefundRequest` itself and reject a second `finalize_refund_with_psbt` call if the derived txid is identical, or remove the old entry atomically when the new one is created.

### Proof of Concept

```
1. request_refund(utxo_storage_key)          // creates RefundRequest{executed:false}
2. execute_refund(utxo_storage_key)           // block_height in Nu6_1 range
   → execute_refund_callback(height=Nu6_1)
   → PsbtWrapper{branch_id=Nu6_1} → txid_1
   → btc_pending_infos[txid_1] inserted
   → verified_deposit_utxo.insert(key)
   → refund_request.executed = true
3. sign_btc_transaction(txid_1)              // txid_1 moves to btc_pending_verify_list
                                             // btc_pending_sign_ids now empty
4. [Zcash block height crosses Nu6_2 boundary]
5. execute_refund(utxo_storage_key)           // block_height in Nu6_2 range
   → load_refund_request_for_execute:
       !true || true == true  → PASSES
   → execute_refund_callback(height=Nu6_2)
   → PsbtWrapper{branch_id=Nu6_2} → txid_2 ≠ txid_1
   → require_pending_sign_capacity: 0 < 1 → PASSES
   → btc_pending_infos[txid_2] inserted  (txid_1 still present)
   → refund_request.executed = true (no-op)

assert btc_pending_infos.contains(txid_1)  // true — orphaned
assert btc_pending_infos.contains(txid_2)  // true — active
// Both can be signed and broadcast; only one confirms on-chain.
// Orphaned entry cannot be removed until verify_refund_finalize clears the request.
```

    pub fn get_branch_id(&self, block_height: u32) -> BranchId {
        let block_height_update = BranchIdUpdateBlockHeight::new(self);
        if block_height_update.nu6_2_update != 0 && block_height >= block_height_update.nu6_2_update
        {
            return BranchId::Nu6_2;
        }
        if block_height_update.nu6_1_update != 0 && block_height >= block_height_update.nu6_1_update
        {
            return BranchId::Nu6_1;
        }

        BranchId::Nu6
    }
