### Title
Missing Vote Stake Normalization in Peras Quorum Check Enables Certificate Bypass - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` compares a `PerasVoteStake` value directly against a relative quorum threshold (`3/4 + 2/100 = 0.77`) without enforcing that the vote stake has been normalized to the same unit. The function's own TODO comment documents this assumption as unverified. Because `validatePerasVote` assigns the raw ledger stake lookup result as `vpvVoteStake` without normalization, any voter with positive absolute stake (e.g., 1,000,000 Lovelace) trivially satisfies the comparison, allowing a single crafted vote from an unprivileged peer to forge a Peras certificate for any block.

---

### Finding Description

**Root cause — `stakeAboveThreshold` in `SupportsPeras.hs`:** [1](#0-0) 

The function performs a bare numeric comparison:

```haskell
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
```

The code's own comment explicitly flags the problem:

> "this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … Under the current implementation of `PerasParams`, this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally."

The quorum threshold is a relative value (`3/4`) set in `mkPerasParams`: [2](#0-1) 

**Missing normalization in `validatePerasVote`:**

The default `BlockSupportsPeras` instance assigns the raw stake-distribution lookup result directly as `vpvVoteStake` with no normalization step: [3](#0-2) 

The `PerasVoteStake` type comment acknowledges there is no agreed-upon conversion from absolute ledger stake to relative committee stake: [4](#0-3) 

**Downstream certificate forging:**

`stakeAboveThreshold` is the sole gate in `votesReachQuorum`, which is called by `updateCandidateVoteState` on every incoming vote: [5](#0-4) 

When `votesReachQuorum` returns `Just`, `forgePerasCert` is called immediately and the resulting `ValidatedPerasCert` is stored in the `PerasVoteDB`: [6](#0-5) 

**Inbound vote path (attacker entry point):**

Votes arrive from peers via `processVotes` in the Peras vote miniprotocol handler, which calls `validatePerasVote` and then `addVote`: [7](#0-6) 

The production pool writer wires this together using `mkPerasParams` and the raw stake distribution: [8](#0-7) 

---

### Impact Explanation

If `PerasVoteStakeDistr` is populated with absolute ledger stake values (Lovelace), then for any voter with stake ≥ 1 Lovelace the comparison `stake >= 0.77` is trivially `True`. A single crafted vote from any voter present in the stake distribution immediately satisfies `votesReachQuorum`, causing `forgePerasCert` to produce a `ValidatedPerasCert` with `vpcCertBoost = PerasWeight 15`. This certificate is then used by chain selection via `weightedSelectView` / `wsvTotalWeight` to add 15 extra weight to the boosted block: [9](#0-8) 

An adversary can therefore make honest nodes prefer an adversarially chosen block over the honest chain, constituting a **bypass of Peras certificate/quorum validation** and a **chain-selection safety failure**.

---

### Likelihood Explanation

The entry path is the Peras vote miniprotocol, reachable by any connected peer. The only precondition is that the attacker's chosen `pvVoteVoterId` appears in the node's current `PerasVoteStakeDistr`. Because the stake distribution is derived from the public ledger, any pool operator (or anyone who can observe the ledger) can satisfy this condition. The unit mismatch is self-documented in the production source as an unresolved design gap, making it likely to persist until explicitly fixed.

---

### Recommendation

- **Short term:** Before calling `stakeAboveThreshold`, normalize `PerasVoteStake` by dividing by the total stake in `PerasVoteStakeDistr`. Alternatively, change `stakeAboveThreshold` to accept the full distribution and perform normalization internally, removing the caller's obligation to pre-normalize.
- **Long term:** Introduce a distinct `NormalizedPerasVoteStake` newtype (invariant: value ∈ [0,1]) and change `stakeAboveThreshold` to accept only that type, making unit mismatches a compile-time error. Resolve the open design question (referenced in the `PerasVoteStake` comment) about the canonical normalization procedure before the Peras protocol is activated on mainnet.

---

### Proof of Concept

1. Attacker observes the current `PerasVoteStakeDistr` from the public ledger and picks any `voterId` with positive absolute stake (e.g., 1,000,000 Lovelace).
2. Attacker sends a single `PerasVote { pvVoteRound = r, pvVoteBlock = adversarialBlock, pvVoteVoterId = voterId }` to the target node via the Peras vote miniprotocol.
3. `processVotes` calls `validatePerasVote mkPerasParams stakeDistr vote`. The lookup succeeds; `vpvVoteStake = PerasVoteStake (1_000_000 % 1)` (absolute Lovelace).
4. `updateCandidateVoteState` calls `votesReachQuorum mkPerasParams [validatedVote]`.
5. `stakeAboveThreshold` evaluates `1_000_000 >= 3/4 + 2/100` → `True`.
6. `forgePerasCert` produces `ValidatedPerasCert { vpcCertBoost = PerasWeight 15 }` for `adversarialBlock`.
7. The certificate is stored in `PerasVoteDB` and propagated; chain selection adds 15 weight to `adversarialBlock`, causing honest nodes to switch to the adversary's chain.

processVotes ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
