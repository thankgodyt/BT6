### Title
Wrong Amount Parameter Used in Withdrawal Confirmation Threshold Calculation - (File: `contracts/satoshi-bridge/src/btc_light_client/withdraw.rs`)

### Summary

`internal_verify_withdraw` passes `btc_pending_info.actual_received_amount` — the net BTC amount the user receives after fees — to `get_confirmations`, instead of `btc_pending_info.transfer_amount`, which is the full nBTC value burned and the true measure of BTC at risk. This mirrors the H-26 pattern exactly: a wrong parameter is substituted in a security-critical calculation, causing the bridge to under-enforce its own confirmation policy for large withdrawals.

### Finding Description

In `internal_verify_withdraw`, the number of Bitcoin confirmations required before the bridge finalizes a withdrawal is computed as:

```rust
let confirmations = self.get_confirmations(config, btc_pending_info.actual_received_amount);
``` [1](#0-0) 

`get_confirmations` implements a tiered strategy: larger satoshi amounts require more confirmations. [2](#0-1) 

The two relevant fields on `BTCPendingInfo` are:

- `transfer_amount` — the full nBTC amount the user burned, equal to the total BTC input value consumed from the bridge's UTXO pool.
- `actual_received_amount` — `transfer_amount − withdraw_fee − gas_fee`, i.e., the net BTC the user receives. [3](#0-2) 

For deposits, the full `deposit_amount` is correctly passed:

```rust
let confirmations = self.get_confirmations(config, deposit_amount)
``` [4](#0-3) 

For withdrawals, `actual_received_amount` is always strictly less than `transfer_amount`. When the deduction of `withdraw_fee + gas_fee` pushes `actual_received_amount` below a confirmation-tier boundary, the bridge requests fewer confirmations from the light client than the security policy intends for the actual transaction value.

### Impact Explanation

The confirmation threshold exists to protect against Bitcoin chain reorganizations. If the bridge finalizes a withdrawal (burns nBTC) before the Bitcoin transaction has accumulated enough confirmations, a reorg can reverse the BTC payment while the nBTC is already destroyed — causing a permanent loss of backed supply. By using `actual_received_amount` instead of `transfer_amount`, the bridge may request fewer confirmations than its own policy mandates for the true value at risk, weakening the reorg-resistance guarantee for large withdrawals that straddle a tier boundary.

This matches the allowed impact: **Medium — bypass of bridge limits or policies**.

### Likelihood Explanation

The discrepancy is triggered whenever `withdraw_fee + gas_fee` is large enough to push `actual_received_amount` below a confirmation-tier upper bound while `transfer_amount` remains above it. With a `fee_min`-dominated fee structure (e.g., a fixed minimum fee of 10,000–20,000 satoshis) and a tier boundary at, say, 1,000,000 satoshis, any withdrawal of `transfer_amount` in the range `[boundary, boundary + fee_min + max_btc_gas_fee)` triggers the under-confirmation. This range is reachable by any ordinary bridge user choosing their withdrawal amount.

### Recommendation

Replace `actual_received_amount` with `transfer_amount` in `internal_verify_withdraw`:

```rust
let confirmations = self.get_confirmations(config, btc_pending_info.transfer_amount);
```

This aligns withdrawal confirmation logic with deposit confirmation logic and ensures the full BTC value at risk governs the required confirmation count.

### Proof of Concept

1. Assume `confirmations_strategy = { "1000000": 3, "10000000": 6 }` (3 confirmations below 1,000,000 sat, 6 above).
2. `withdraw_bridge_fee.fee_min = 20000`, `max_btc_gas_fee = 50000`.
3. User calls `ft_transfer_call` with `amount = 1_020_000` satoshis (transfer_amount = 1,020,000 > 1,000,000 → should require 6 confirmations).
4. `withdraw_fee = 20000`, `gas_fee = 50000` → `actual_received_amount = 950_000` < 1,000,000.
5. Bridge calls `get_confirmations(config, 950_000)` → returns **3** confirmations.
6. Relayer submits a proof with only 3 confirmations; the light client accepts it.
7. Bridge burns 1,020,000 nBTC and finalizes the withdrawal with 3 confirmations instead of the 6 that the policy requires for a 1,020,000-satoshi transaction. [5](#0-4) [2](#0-1)

    pub fn get_confirmations(&self, satoshi_amount: u128) -> u64 {
        require!(
            !self.confirmations_strategy.is_empty(),
            "confirmations_strategy is empty"
        );
        // The key is constrained to U64 during assignment, so it won't panic.
        let mut keys = self
            .confirmations_strategy
            .keys()
            .map(|k| k.parse::<u128>().unwrap())
            .collect::<Vec<_>>();
        keys.sort_unstable();
        for key in &keys {
            if *key > satoshi_amount {
                return u64::from(*self.confirmations_strategy.get(&key.to_string()).unwrap());
            }
        }
        let max_key = keys.last().unwrap();
        u64::from(
            *self
                .confirmations_strategy
                .get(&max_key.to_string())
                .unwrap(),
        )
    }
