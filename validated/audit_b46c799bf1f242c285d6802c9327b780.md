### Title
Confirmation-threshold policy bypass via deposit splitting — (File: `contracts/satoshi-bridge/src/config.rs`)

---

### Summary
The bridge enforces a tiered confirmation requirement through `confirmations_strategy`, requiring more Bitcoin confirmations before minting nBTC for larger deposit amounts. This check is applied **per individual deposit transaction**, not cumulatively. An attacker can bypass the higher confirmation requirement for a large deposit by splitting it into multiple smaller deposits, each below the threshold that triggers the stricter confirmation count.

---

### Finding Description
`Config::get_confirmations` in `config.rs` maps a single deposit's satoshi amount to a required confirmation count: [1](#0-0) 

The field is documented as "Satoshi upper limit for amount checks -> confirmations": [2](#0-1) 

`Contract::get_confirmations` wraps this with a whitelist adjustment but still passes only the single-deposit amount: [3](#0-2) 

This same per-deposit call is used in the refund path: [4](#0-3) 

And the same pattern applies in the deposit verification path (via `verify_deposit` in `api/bridge.rs`), which calls `get_confirmations` with the individual deposit output's value.

Because the check is purely per-transaction, a user who wants to deposit an amount `A` that would require `N` confirmations can instead send `k` separate Bitcoin transactions each carrying `A/k` satoshis, where `A/k` falls below the threshold that triggers `N` confirmations. Each individual deposit is verified with the lower confirmation count, and the bridge mints nBTC for each one.

---

### Impact Explanation
**Medium.** The confirmation strategy is the bridge's primary defense against Bitcoin chain-reorganization risk for large deposits. A higher confirmation count for large amounts is intended to ensure sufficient finality before minting nBTC. By splitting a large deposit into smaller ones, an attacker can obtain nBTC with fewer confirmations than the policy intends for that aggregate value. If the underlying Bitcoin transactions are later reorganized out of the chain (more likely with fewer confirmations), the bridge has minted nBTC without a corresponding BTC backing — a broken accounting invariant and a bypass of the bridge's risk-management policy.

This matches the allowed impact: **"Medium. Bypass of bridge limits or policies."**

---

### Likelihood Explanation
**Medium.** Any unprivileged user can create multiple Bitcoin deposit transactions to separate bridge-derived deposit addresses. No special access, leaked keys, or operator cooperation is required. The only cost is Bitcoin transaction fees for the additional splits. There is a clear incentive when the attacker wants to move large amounts quickly (e.g., during a period of elevated reorg risk) with fewer confirmations than the policy mandates.

---

### Recommendation
Apply the confirmation requirement based on the **cumulative** deposit value associated with a single user/session rather than on each deposit in isolation, or enforce a global per-block or per-account minting cap that accounts for aggregate deposit value. At minimum, document that the `confirmations_strategy` threshold applies per-UTXO and cannot prevent a determined user from splitting deposits to obtain a lower confirmation count.

---

### Proof of Concept

Assume the operator configures:
```
confirmations_strategy = { "100000000": 3, "1000000000": 6 }
```
meaning deposits ≤ 1 BTC → 3 confirmations; deposits > 1 BTC → 6 confirmations.

1. Attacker wants to deposit 5 BTC (500 000 000 sat) and receive nBTC after only 3 confirmations.
2. Instead of one 5 BTC deposit, attacker sends 5 separate Bitcoin transactions of 1 BTC each (100 000 000 sat each) to 5 different bridge deposit addresses.
3. Each call to `get_confirmations(100_000_000)` returns `3` (the lower tier).
4. After 3 Bitcoin confirmations, a relayer submits 5 separate `verify_deposit` proofs.
5. The bridge mints nBTC for each, totalling 5 BTC worth of nBTC — all with only 3 confirmations, bypassing the 6-confirmation requirement that should have applied to this aggregate value. [5](#0-4)

```rust
    pub fn get_confirmations(&self, satoshi_amount: u128) -> u64 {
        require!(
            !self.confirmations_strategy.is_empty(),
            "confirmations_strategy is empty"
        );
        // The key is constrained to U64 during assignment, so it won't panic.
        let mut keys = self
            .confirmations_strategy
            .keys()
            .map(|k| k.parse::<u128>().unwrap())
            .collect::<Vec<_>>();
        keys.sort_unstable();
        for key in &keys {
            if *key > satoshi_amount {
                return u64::from(*self.confirmations_strategy.get(&key.to_string()).unwrap());
            }
        }
        let max_key = keys.last().unwrap();
        u64::from(
            *self
                .confirmations_strategy
                .get(&max_key.to_string())
                .unwrap(),
        )
    }
```
