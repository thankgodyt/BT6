### Title
nBTC Token Migration Race Condition Allows In-Flight Deposits to Mint to Deprecated Token, Causing Permanent Fund Loss - (File: contracts/satoshi-bridge/src/nbtc/migration.rs)

---

### Summary

`internal_migrate_to_new_token` initiates an async two-step migration: it first snapshots old-token balances via cross-contract calls, then mints equivalent tokens on the new contract in a callback. The bridge's `nbtc_account_id` is **not updated until the callback completes**. Any deposit verification that resolves during this async window mints nBTC to the old (deprecated) token using the stale `nbtc_account_id`, but those tokens are absent from the already-taken snapshot and are permanently stranded after migration.

---

### Finding Description

In `contracts/satoshi-bridge/src/nbtc/migration.rs`, `internal_migrate_to_new_token` executes as follows:

```
Step 1 (sync):   old_token = self.internal_config().nbtc_account_id   // snapshot config
Step 2 (async):  ext_nbtc::ext(old_token).ft_total_supply()           // query old balances
                 ext_nbtc::ext(old_token).ft_balance_of(account) × N
Step 3 (callback): migrate_to_new_token_mint(new_token, accounts)     // mint on new token,
                                                                       // update nbtc_account_id
``` [1](#0-0) 

`nbtc_account_id` is **not changed** until the callback at Step 3. During the async gap between Steps 2 and 3 (one or more NEAR block boundaries), the bridge's deposit path still reads `nbtc_account_id` and mints to the **old** token. Specifically, any `verify_deposit` call whose light-client callback resolves during this window will invoke `mint` against the old token contract. [2](#0-1) 

Because the balance snapshot was already captured at Step 2, those freshly minted old-token balances are **not included** in the migration. When `migrate_to_new_token_mint` runs, it mints on the new token only for the stale snapshot amounts. After `nbtc_account_id` flips to the new token, the user's old-token nBTC is permanently stranded — the old token is deprecated and the bridge no longer interacts with it.

This is structurally identical to the PirexGmx M-11 finding: a two-step migration leaves a stale reference (`nbtc_account_id` → old token) active during the async window, allowing a legitimate external actor (the relayer) to trigger a mint path that produces tokens outside the migration's accounting.

---

### Impact Explanation

Users whose deposits are verified during the migration window receive nBTC minted to the old (deprecated) token. Those tokens are not migrated to the new token and cannot be used for withdrawals (the bridge now routes all burns to the new token). The deposited BTC is locked in the bridge's UTXO pool while the corresponding nBTC is permanently inaccessible. This constitutes a **significant, permanent loss of user funds** — Critical under the allowed impact scope.

---

### Likelihood Explanation

NEAR cross-contract calls resolve across block boundaries. Any `verify_deposit` transaction submitted by a relayer in the same or adjacent block as the migration call can resolve during the async window. Relayers are whitelisted but not privileged operators; they submit proofs continuously as Bitcoin blocks confirm. No malicious intent is required — ordinary relayer operation during a migration is sufficient to trigger the loss. The window is narrow (1–2 blocks) but the bridge processes deposits continuously, making a collision realistic during any migration event.

---

### Recommendation

1. **Update `nbtc_account_id` to the new token before querying balances.** New deposits will then mint to the new token, and the snapshot of the old token captures a stable final state.
2. **Or, pause deposit processing** (set a migration-in-progress flag checked by `verify_deposit_callback` / `mint_callback`) before calling `internal_migrate_to_new_token`, and unpause only after the migration callback resolves.
3. **Or, perform the migration atomically** by burning all old-token supply and minting on the new token within a single transaction batch, eliminating the async window entirely.

---

### Proof of Concept

1. Admin calls `migrate_to_new_token(new_nbtc, [alice, bob])`.
2. Bridge issues async calls: `old_nbtc.ft_balance_of(alice)` → 1 BTC, `old_nbtc.ft_balance_of(bob)` → 2 BTC. Snapshot recorded.
3. **Simultaneously**, a relayer's `verify_deposit` for Alice (1 BTC deposit) was already submitted. The light-client callback resolves during the async window.
4. Bridge executes `mint(alice, 1_BTC)` against `nbtc_account_id` = **old_nbtc** (not yet updated). Alice now holds 2 BTC on old_nbtc.
5. `migrate_to_new_token_mint` callback fires with the Step-2 snapshot (alice = 1 BTC, bob = 2 BTC). It mints 1 BTC for Alice and 2 BTC for Bob on new_nbtc.
6. `nbtc_account_id` is updated to new_nbtc.
7. Alice's second 1 BTC (minted in Step 4) remains on old_nbtc. The bridge no longer interacts with old_nbtc. Alice's 1 BTC deposit is permanently lost. [3](#0-2)

    pub(crate) fn internal_migrate_to_new_token(
        &mut self,
        new_token: AccountId,
        accounts: Vec<AccountId>,
    ) -> Promise {
        let old_token = self.internal_config().nbtc_account_id.clone();
        require!(
            new_token != old_token,
            "New token must differ from the current token"
        );

        let mut queries = ext_nbtc::ext(old_token.clone())
            .with_static_gas(GAS_FOR_FT_QUERY)
            .ft_total_supply();
        for account in &accounts {
            queries = queries.and(
                ext_nbtc::ext(old_token.clone())
                    .with_static_gas(GAS_FOR_FT_QUERY)
                    .ft_balance_of(account.clone()),
            );
        }

        let callback_gas = Gas::from_gas(
            GAS_FOR_MIGRATION_MINT_CALL_BACK.as_gas()
                + GAS_FOR_MIGRATION_RESOLVE_CALL_BACK.as_gas()
                + GAS_FOR_MINT_ACTION.as_gas() * accounts.len() as u64,
        );
        queries.then(
            Self::ext(env::current_account_id())
                .with_static_gas(callback_gas)
                .migrate_to_new_token_mint(new_token, accounts),
        )
    }
