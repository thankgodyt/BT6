Audit Report

## Title
Token Metadata Binding Confusion via Unvalidated Metaplex `mint` Field in `parse_metadata_account` — (`File: solana/programs/bridge_token_factory/src/instructions/user/log_metadata.rs`)

## Summary

In `parse_metadata_account`, the only runtime check is that the caller-supplied `metadata` account key matches the address stored in the Token-2022 mint's `MetadataPointer` extension. After deserializing the Metaplex metadata, the code never verifies that `metadata.mint == self.mint.key()`. An attacker can create a Token-2022 mint whose `MetadataPointer` references the Metaplex metadata PDA of any legitimate token (e.g., USDC), causing the bridge to emit a Wormhole message to NEAR that binds the attacker's worthless mint to a reputable token's name and symbol.

## Finding Description

The `metadata` account is declared as a fully unchecked optional account with no PDA seed constraints:

```rust
/// CHECK: may be unitialized
pub metadata: Option<UncheckedAccount<'info>>,
``` [1](#0-0) 

For Token-2022 mints, when the `MetadataPointer` extension is present and its `metadata_address` is neither the mint itself nor `Pubkey::default()`, `parse_metadata_account` is called with the raw pointer address:

```rust
} else if metadata_pointer.metadata_address.0 != Pubkey::default() {
    // Third-party metadata
    self.parse_metadata_account(metadata_pointer.metadata_address.0)?
``` [2](#0-1) 

Inside `parse_metadata_account`, the only validation is a key equality check between the provided account and the pointer address. After that, if the account is owned by `MetaplexID`, the metadata is deserialized and `name`/`symbol` are returned directly — with no check that `metadata.mint` matches `self.mint.key()`:

```rust
require_keys_eq!(
    metadata.key(),
    address,
    ErrorCode::InvalidTokenMetadataAddress,
);
if metadata.owner == &MetaplexID {
    let data = metadata.try_borrow_data()?;
    let metadata = MplMetadata::try_deserialize(&mut data.as_ref())?;
    Ok((metadata.name.clone(), metadata.symbol.clone()))
``` [3](#0-2) 

The resulting payload uses the attacker's mint pubkey but the legitimate token's name and symbol:

```rust
let payload = LogMetadataPayload {
    token: self.mint.key(),
    name: name.trim_end_matches('\0').to_string(),
    symbol: symbol.trim_end_matches('\0').to_string(),
    decimals: self.mint.decimals,
``` [4](#0-3) 

The Metaplex `MetadataAccount` struct (confirmed by the test helper's serialization layout) contains a `mint: Pubkey` field at a fixed offset immediately after `update_authority`. This field is never read or validated against `self.mint.key()` anywhere in `parse_metadata_account`. [5](#0-4) 

## Impact Explanation

This is a **token metadata binding confusion** — an explicitly listed Critical impact class. NEAR receives a Wormhole message binding the attacker's worthless Token-2022 mint to the name "USD Coin" and symbol "USDC". NEAR then deploys a wrapped token for the attacker's mint under that identity. Users who receive and hold this fake wrapped "USDC" and attempt to bridge back receive the attacker's worthless tokens. This constitutes concrete user fund loss through deceptive token identity, matching the allowed Critical impact: "token metadata binding confusion that changes user or protocol balances."

## Likelihood Explanation

The attack requires no privileged access. Any unprivileged user can:
- Create a Token-2022 mint (Token-2022 allows setting `MetadataPointer` to any arbitrary address at initialization time).
- Use any non-bridge keypair as mint authority, trivially satisfying `!mint.mint_authority.contains(authority.key)`.
- Pass the legitimate token's publicly readable Metaplex metadata PDA as the `metadata` account argument.

The attack is fully permissionless, deterministic, and repeatable for any token whose Metaplex metadata PDA is known (i.e., all major tokens on Solana).

## Recommendation

Inside `parse_metadata_account`, after deserializing the Metaplex metadata, add a check that the metadata's `mint` field matches the actual mint being processed:

```rust
if metadata.owner == &MetaplexID {
    let data = metadata.try_borrow_data()?;
    let metadata = MplMetadata::try_deserialize(&mut data.as_ref())?;
    // ADD THIS CHECK:
    require_keys_eq!(
        metadata.mint,
        self.mint.key(),
        ErrorCode::InvalidTokenMetadataAddress,
    );
    Ok((metadata.name.clone(), metadata.symbol.clone()))
} else {
    Ok((String::default(), String::default()))
}
```

This ensures that even if an attacker's Token-2022 mint points its `MetadataPointer` at a legitimate token's Metaplex metadata PDA, the bridge will reject the instruction because the deserialized metadata's `mint` field will not match the attacker's mint pubkey.

## Proof of Concept

1. Derive USDC's Metaplex metadata PDA: `find_program_address([b"metadata", MetaplexID, USDC_MINT], MetaplexID).0`.
2. Create a Token-2022 mint `ATTACKER_MINT` with mint authority = attacker keypair and `MetadataPointer` extension initialized to USDC's metadata PDA address.
3. Call `log_metadata` with:
   - `mint` = `ATTACKER_MINT` (Token-2022, token_program = Token-2022 ID)
   - `metadata` = USDC's Metaplex metadata PDA account (publicly readable on-chain)
4. Observe: `metadata_pointer.metadata_address.0 != Pubkey::default()` → enters third-party metadata branch.
5. Observe: `require_keys_eq!(metadata.key(), metadata_pointer.metadata_address.0)` passes — both equal USDC's metadata PDA.
6. Observe: `metadata.owner == &MetaplexID` is true; deserialization returns `name="USD Coin"`, `symbol="USDC"`.
7. Observe: Wormhole message posted with `LogMetadataPayload { token: ATTACKER_MINT, name: "USD Coin", symbol: "USDC", decimals: <attacker_decimals> }`.
8. NEAR deploys a wrapped token for `ATTACKER_MINT` named "USD Coin" / "USDC".

A local integration test can reproduce this by constructing a Token-2022 mint account with a `MetadataPointer` extension set to a separately constructed Metaplex metadata account (owned by `MetaplexID`, with `mint` field set to a different pubkey than the Token-2022 mint), then invoking `log_metadata` and asserting the Wormhole message payload contains the mismatched name/symbol.
