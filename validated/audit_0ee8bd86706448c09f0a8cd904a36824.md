### Title
Unconditional Tip-Header Exemption from Invalid-Block Check Bypasses Peer Punishment in ChainSync — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

When diffusion pipelining is enabled (`DiffusionPipeliningOn`), the ChainSync client unconditionally assumes the tip header of every peer's candidate fragment is a "tentative" (unvalidated) header and exempts it from the invalid-block check. There is no explicit signal from the peer about whether the header is actually tentative. An unprivileged adversarial peer can exploit this by serving a block that is already known to be invalid as the tip of its candidate fragment, permanently avoiding the disconnect punishment while keeping the node's candidate fragment anchored to an invalid chain tip.

This is the direct analog of the BWGToken `costFreeList` bug: just as the criteria for being added to the cost-free list were undocumented and exploitable, the criteria for a header being "tentative" (and thus exempt from the invalid-block check) are implicit, unconditional, and exploitable.

---

### Finding Description

Two functions in `ChainSync/Client.hs` implement the invalid-block peer-punishment logic:

**1. `invalidBlockRejector`** — a watcher that fires whenever `cdbInvalid` gains a new entry. It scans the peer's candidate fragment from newest to oldest and disconnects if any header is known invalid. With `DiffusionPipeliningOn`, it unconditionally drops the first element (the tip) before scanning:

```haskell
$ ( case pipelining of
      DiffusionPipeliningOff -> id
      DiffusionPipeliningOn ->
        -- As mentioned in the comment above, if the
        -- header is tentative we skip the fragment tip,
        -- dropping the first element.
        drop 1
  )
$ AF.toNewestFirst theirFrag
```

The comment explicitly acknowledges the problem: *"Since they do not yet have a way to explicitly say whether it is tentative, we assume it is and therefore skip their tip here. TODO once it's explicit, only skip it if it's annotated as tentative."*

**2. `checkKnownInvalid`** — called per-header on every `rollForward`. With `DiffusionPipeliningOn`, it checks the *parent* of the incoming header rather than the header itself:

```haskell
scrutinee = case getDiffusionPipeliningSupport of
    DiffusionPipeliningOff -> BlockHash (headerHash hdr)
    -- Disconnect if the parent block of `hdr` is known to be invalid.
    DiffusionPipeliningOn -> headerPrevHash hdr
```

If the incoming header H is itself known invalid but its parent is valid, `scrutinee` resolves to a valid hash and no disconnection occurs.

The root cause in both cases is the same: the "tentative" status of the tip header is determined solely by structural position (being the tip when pipelining is on), not by any explicit, verifiable signal from the peer. This is the undocumented, implicit exemption criterion — directly analogous to the unclear `costFreeList` selection criteria in BWGToken.

---

### Impact Explanation

An adversarial peer can serve a block that is already present in `cdbInvalid` as the tip of its candidate fragment. Both `checkKnownInvalid` (which checks the parent, not the header itself) and `invalidBlockRejector` (which drops the tip) will fail to trigger a disconnect. The peer permanently avoids the punishment mechanism while its candidate fragment — containing a known-invalid tip — remains active in the node's chain selection state. This materially weakens the ChainSync miniprotocol's block-authorization enforcement: the peer punishment mechanism that is supposed to disconnect nodes serving invalid blocks is bypassed for the tip position whenever pipelining is enabled.

**Impact class**: Medium — public miniprotocol flaw that materially weakens block authorization without relying on DoS.

---

### Likelihood Explanation

- Pipelining (`DiffusionPipeliningOn`) is the production default for Cardano nodes (Shelley era and later).
- Any unprivileged peer can connect via ChainSync and serve arbitrary headers.
- The adversary only needs to know one block hash that is already in the target node's `cdbInvalid` map (e.g., from a prior interaction, or from a publicly known rejected block), then serve that block as the tip of its candidate fragment.
- No key compromise, stake majority, or privileged access is required.

**Likelihood**: Medium.

---

### Recommendation

1. Implement an explicit, verifiable per-header signal in the ChainSync protocol indicating whether the tip is tentative (as the TODO comment already acknowledges). Only exempt the tip from the invalid-block check when it carries this explicit annotation.
2. Until the protocol is extended, consider applying the invalid-block check to the tip header unconditionally in `invalidBlockRejector`, and checking `headerHash hdr` (not `headerPrevHash hdr`) in `checkKnownInvalid`, accepting that this may cause spurious disconnects from honest peers who pipeline trap headers — which is the lesser security risk.
3. Document the exact criteria under which a header is considered tentative and exempt from the invalid-block check, mirroring the recommendation in the BWGToken report to document `costFreeWallet` selection criteria.

---

### Proof of Concept

**Setup**: Node A (victim) has block H in its `cdbInvalid` map. Adversarial peer B connects via ChainSync with `DiffusionPipeliningOn`.

**Step 1**: B sends `MsgRollForward H theirTip` where H is the known-invalid block.

**Step 2**: `rollForward` calls `checkKnownInvalid` with H. [1](#0-0) 

With `DiffusionPipeliningOn`, `scrutinee = headerPrevHash H`. H's parent is valid → `isInvalidBlock (headerPrevHash H) = Nothing` → **no disconnect**. [2](#0-1) 

**Step 3**: H is added to the candidate fragment. `invalidBlockRejector` fires (fingerprint of `cdbInvalid` may have changed, or H was already there). It scans `AF.toNewestFirst theirFrag` but with `DiffusionPipeliningOn` applies `drop 1`, skipping H (the tip). **No disconnect**. [3](#0-2) 

**Result**: Peer B remains connected while advertising a known-invalid block as its chain tip. The exemption criterion — "tip position when pipelining is on" — is unconditional and undocumented, exactly mirroring the unclear `costFreeList` selection in BWGToken.
