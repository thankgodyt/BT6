### Title
Peras Certificate Validation Unconditionally Returns Success, Bypassing All Cryptographic Checks - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` (success) without performing any cryptographic or structural validation on inbound Peras certificates. This is the direct analog of the reported "missing check for successful transfer" pattern: a function with the correct `Either`-returning type signature exists and is called in the production inbound-certificate pipeline, but its body always succeeds, making the validation call a no-op. Any unprivileged peer can send an arbitrarily crafted Peras certificate and have it accepted and stored.

### Finding Description

In `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`, the default `BlockSupportsPeras` instance implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

The function's declared type is `PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)`, which is the correct shape for a failable validator. However, the implementation ignores the certificate's contents entirely and always returns `Right`, wrapping the unvalidated certificate in a `ValidatedPerasCert` phantom type.

This stub is wired directly into the production inbound-certificate processing pipeline. `makePerasCertPoolWriterFromChainDB` and `makePerasCertPoolWriterFromCertDB` both pass `(validatePerasCert mkPerasParams)` as the `validateCert` argument to `processCerts`:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          (validatePerasCert mkPerasParams)   -- always Right
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

Inside `processCerts`, the validator is applied to every new certificate received from a peer:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [3](#0-2) 

Because `validatePerasCert` always returns `Right`, the `(errs, _)` branch is never taken. Every certificate, regardless of its cryptographic content, round number plausibility, or boosted-block validity, is accepted and forwarded to `addCert`.

The contrast with the properly implemented committee-level certificate verification (`implVerifyCert` in `EveryoneVotes.hs` and `WFALS.hs`) makes the gap concrete: those paths verify aggregate BLS signatures, check voter eligibility, and verify VRF outputs before accepting a certificate. [4](#0-3) 

The same pattern applies to `validatePerasVote`, which only checks stake-distribution membership but never verifies the vote's cryptographic signature, allowing any peer to forge votes for any registered voter ID: [5](#0-4) 

### Impact Explanation

**Critical — Bypass of Peras certificate/vote validation enabling unauthorized certificate acceptance.**

An unprivileged peer can craft a `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock`, send it over the Peras certificate diffusion mini-protocol, and have it accepted into the local `PerasCertDB` or `ChainDB` without any signature, quorum, or eligibility check. Once stored, the certificate influences chain selection (via `vpcCertBoost`) and the Peras certificate-inclusion rules (`needCert`), which govern whether a block producer must embed a certificate in the next block. A stream of forged certificates for attacker-chosen blocks can therefore steer an honest node's chain-selection weight toward a non-canonical chain, constituting a Peras-layer chain-selection safety failure.

### Likelihood Explanation

The inbound certificate path is reachable by any peer that can establish a Peras object-diffusion connection. No stake, keys, or operator access is required. The only gate is the duplicate-round-number filter (`Set.member roundNo alreadyInDb`), which an attacker trivially bypasses by using a fresh round number for each forged certificate.

### Recommendation

Replace the stub with a real implementation that at minimum:
1. Verifies the aggregate BLS signature over the certificate's `(electionId, candidate)` pair against the aggregated public keys of the claimed voters (mirroring `implVerifyCert` in `EveryoneVotes.hs`/`WFALS.hs`).
2. Checks that the claimed voters are eligible members of the committee for the certificate's round.
3. Checks that the boosted block point is plausible (e.g., within the current chain's volatile window).

Until a real implementation is available, the stub should at minimum reject all inbound certificates (`Left PerasValidationErr`) rather than accept them all, so that the network-facing pipeline is not silently open.

### Proof of Concept

1. Connect to a node running the Peras certificate diffusion protocol.
2. Send a `PerasCert` with `pcCertRound = R` (any round not yet in the DB) and `pcCertBoostedBlock = <attacker-chosen block point>`.
3. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert cert boost)` unconditionally.
4. The certificate is timestamped and passed to `addCert`, entering the `PerasCertDB` or `ChainDB`.
5. The node's chain-selection logic now treats the attacker-chosen block as having received a Peras boost of `perasWeight params`, biasing chain selection toward it. [6](#0-5) [7](#0-6)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

                Nothing ->

        aggSig
