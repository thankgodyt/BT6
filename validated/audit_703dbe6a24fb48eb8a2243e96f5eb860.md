Audit Report

## Title
Reentrancy via ERC777 callback in `initTransfer` causes nonce collision and permanent fund loss - (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

## Summary

`OmniBridge.initTransfer` increments `currentOriginNonce` at line 381 before the external token call, but reads `currentOriginNonce` again after the external call at lines 418 and 430 for `initTransferExtension` and `emit InitTransfer`. An ERC777 token's `tokensToSend` hook can reenter `initTransfer` during `safeTransferFrom`, causing the inner call to increment the nonce a second time. Both the inner and outer calls then emit `InitTransfer` with the same nonce, while the outer transfer's original nonce is never emitted, permanently locking those tokens in the bridge with no NEAR-side finalization path.

## Finding Description

In `OmniBridge.initTransfer` (lines 373–437), the execution order is:

1. **Line 381**: `currentOriginNonce += 1` — nonce incremented to N; no local snapshot is stored.
2. **Lines 407–411**: `IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount)` — for any token not in `isBridgeToken` and not in `customMinters`, this external call is made. An ERC777 token fires its `tokensToSend` hook here.
3. Inside the hook, the attacker reenters `initTransfer`:
   - Line 381 again: `currentOriginNonce += 1` — nonce incremented to N+1.
   - Inner `safeTransferFrom` completes (no further hook).
   - Line 418: `initTransferExtension(..., currentOriginNonce, ...)` — passes N+1.
   - Line 430: `emit BridgeTypes.InitTransfer(..., currentOriginNonce, ...)` — emits with nonce N+1.
4. Outer call resumes after `safeTransferFrom` returns.
5. **Line 418**: `initTransferExtension(..., currentOriginNonce, ...)` — reads storage value N+1 (not the N that was intended).
6. **Line 430**: `emit BridgeTypes.InitTransfer(..., currentOriginNonce, ...)` — emits with nonce N+1 again.

The contract imports no `ReentrancyGuardUpgradeable` and applies no `nonReentrant` modifier to `initTransfer` or `initTransfer1155`. The CLAUDE.md invariant "State before external calls" is only partially satisfied: the nonce is incremented before the external call, but it is read again from storage after the external call rather than from a pre-call snapshot, breaking the invariant under reentrancy. The identical structural flaw exists in `initTransfer1155` (lines 447–490), where `currentOriginNonce` is incremented at line 448 and read again at lines 471 and 483 after `IERC1155.safeTransferFrom` (which triggers `onERC1155Received` on the recipient, enabling the same reentrant pattern).

## Impact Explanation

- Nonce N (the outer call's intended nonce) is never emitted in any `InitTransfer` event. The outer transfer's tokens are locked in the bridge contract with no corresponding event the NEAR side can process.
- Nonce N+1 is emitted twice — once by the inner call and once by the outer call. The NEAR side processes the first occurrence and rejects the second as a replay.
- The outer transfer's tokens are **permanently frozen** in the bridge contract: the NEAR side will never finalize a transfer for nonce N (no event exists) and will reject nonce N+1 as a duplicate.
- This constitutes permanent freezing of bridged funds triggered by an unprivileged user, matching the Critical impact class: "permanent freezing of bridged funds" and "nonce/replay misuse that changes user or protocol balances."

## Likelihood Explanation

ERC777 tokens are backward-compatible with ERC20 and deployed on Ethereum mainnet. The `initTransfer` non-bridge path (the `else` branch at lines 406–412) accepts any ERC20 token that is not registered as a bridge token or custom minter token. An attacker can deploy their own ERC777 token, register themselves as the `tokensToSend` operator/hook implementer for their own address, and call `initTransfer` with that token. No admin privileges are required; the bridge is explicitly permissionless for `initTransfer`. The attack is repeatable and requires only a single transaction.

## Recommendation

1. **Snapshot the nonce before external calls** and use the snapshot value in `initTransferExtension` and `emit`:
   ```solidity
   uint64 originNonce = currentOriginNonce + 1;
   currentOriginNonce = originNonce;
   // ... external calls ...
   initTransferExtension(..., originNonce, ...);
   emit BridgeTypes.InitTransfer(..., originNonce, ...);
   ```
2. **Add `ReentrancyGuardUpgradeable`** and apply `nonReentrant` to both `initTransfer` and `initTransfer1155`.
3. Apply the same nonce-snapshot fix to `initTransfer1155`.

## Proof of Concept

```
State: currentOriginNonce = 5

1. Attacker calls initTransfer(erc777Token, amount1, ...)
   → Line 381: currentOriginNonce = 6
   → Lines 407-411: safeTransferFrom fires tokensToSend hook on attacker

2. Attacker's hook calls initTransfer(erc777Token, amount2, ...)
   → Line 381: currentOriginNonce = 7
   → safeTransferFrom completes (no further hook)
   → Line 418: initTransferExtension(..., nonce=7, ...)
   → Line 430: emit InitTransfer(nonce=7, amount=amount2)   ← inner event

3. Outer call resumes
   → Line 418: initTransferExtension(..., nonce=7, ...)     ← reads currentOriginNonce=7
   → Line 430: emit InitTransfer(nonce=7, amount=amount1)   ← outer event, SAME nonce

Result:
- Two InitTransfer events with nonce 7 on EVM
- Nonce 6 never emitted → amount1 tokens permanently locked in bridge
- NEAR processes nonce 7 once (amount2), rejects second nonce 7 as replay
```

A Foundry invariant test can confirm this: deploy a mock ERC777 token whose `tokensToSend` hook reenters `initTransfer`, call `initTransfer` once, then assert that all emitted `InitTransfer` nonces are unique and that every nonce in `[initialNonce+1, currentOriginNonce]` has exactly one corresponding event. ```markdown
- **No replay attacks**: Every `destinationNonce` must be checked against `completedTransfers` and marked used before any token transfer. Every `originNonce` is incremented atomically. A nonce must never be reusable
- **Event completeness**: `InitTransfer` and `FinTransfer` events must contain every field needed to reconstruct the transfer. The NEAR side relies solely on these events — any missing or ambiguous field means lost funds or spoofable transfers. Fields must not be collapsible (e.g. two different transfers must never produce the same event data)
- **State before external calls**: Always mutate state (e.g. mark nonce used) before any external call (token transfer, ETH send, custom minter). This is the primary reentrancy defense
- **No token release without signature**: Never mint, transfer, or unlock tokens to a recipient without first verifying a valid MPC signature. No admin function, emergency path, or refactor may bypass this — it is the only authorization gate for finTransfer
- **Event–transfer atomicity**: `InitTransfer` must only be emitted in a code path where tokens have already been burned/locked in the same transaction. If the token transfer reverts or is skipped, the event must not emit — the NEAR side will treat any emitted event as proof that tokens are held
