After thorough investigation of the Peras certificate and vote validation pipeline, I found a direct analog to the external report's "only counting one side" accounting omission.

### Title
Peras Certificate Validation Bypass: `validatePerasCert` Unconditionally Accepts Any Certificate Without Cryptographic or Quorum Verification - (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The catch-all `instance StandardHash blk => BlockSupportsPeras blk` in `SupportsPeras.hs` provides a degenerate `validatePerasCert` that unconditionally returns `Right` for every certificate, wrapping it in `ValidatedPerasCert` with the configured boost weight and performing zero cryptographic or quorum checks. This is structurally identical to the external report's root cause: just as `suppliedBalance()` reads only the supply field and silently drops borrow liabilities, `validatePerasCert` reads only the certificate's identity and silently drops all validity conditions (aggregate signature, quorum stake, round eligibility, block eligibility). The result in both cases is a phantom "validated" value that passes every downstream gate.

---

### Finding Description

In `SupportsPeras.hs`, the universal `BlockSupportsPeras` instance at line 320 is the only concrete instance in the repository. Its `validatePerasCert` implementation is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

A legitimate Peras certificate must prove that a quorum of stake-weighted votes (≥ `perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin`, default 3/4 + 2/100 of total stake) was cast for the boosted block in the given round. The validation must check:

1. The certificate's BLS aggregate signature over the constituent votes
2. That the aggregated vote stake exceeds the quorum threshold (the same check `stakeAboveThreshold` performs for vote aggregation)
3. That the round number is within the valid window (`perasCertMaxRounds`)
4. That the boosted block is old enough (`perasBlockMinSlots`)

None of these checks are performed. The function accepts the raw `PerasCert` from a peer and unconditionally promotes it to `ValidatedPerasCert` with the full configured boost weight.

The downstream chain-selection path trusts this validation result completely. `chainSelSync` in `ChainSel.hs` receives a `WithArrivalTime (ValidatedPerasCert blk)`, adds it to the `PerasCertDB`, and triggers `chainSelectionForBlock` for the boosted block. The `weightedSelectView` function in `SelectView.hs` then calls `weightBoostOfFragment` which sums all `PerasWeightSnapshot` entries for the fragment, and `wsvTotalWeight` adds this boost to the block number for the chain comparison in `preferCandidate`. A fake certificate thus injects `perasWeight params` (default: 15) phantom weight units into chain selection for any block the adversary names.

The `stakeAboveThreshold` quorum gate that correctly guards vote aggregation in `Aggregation.hs` is never reached for certificates, because `validatePerasCert` short-circuits before any quorum check can occur. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

### Impact Explanation

**Impact: Critical — Peras certificate/vote verification bypass enabling unauthorized certificate acceptance and chain-selection manipulation.**

Once Peras is enabled, any unprivileged peer can craft a `PerasCert` naming any block on any fork and send it via the Peras certificate diffusion mini-protocol. The degenerate `validatePerasCert` promotes it to `ValidatedPerasCert` with `vpcCertBoost = perasWeight params` (default 15). The `PerasCertDB` stores it, `chainSelSync` triggers chain selection for the boosted block, and `weightBoostOfFragment` adds 15 phantom weight units to every chain fragment containing that block.

With the default `perasWeight = 15` and security parameter `k = 2160`, a single fake certificate is equivalent to 15 additional blocks of chain weight. An adversary controlling a minority fork that is within 15 weight units of the canonical tip can cause honest nodes to switch to the adversary's fork. Multiple fake certificates compound: `n` fake certificates inject `n × 15` phantom weight, making arbitrarily deep rollbacks possible regardless of the honest chain's length advantage. This directly violates the Peras security guarantee that chain selection is based on certified stake-weighted votes. [5](#0-4) [6](#0-5) 

---

### Likelihood Explanation

**Likelihood: Medium.**

The attack requires Peras to be enabled. Peras is currently disabled by default (`emptyPerasWeightSnapshot` is used when no certs exist), but the infrastructure is fully wired: `addPerasCertAsync` is exposed on the `ChainDB` API, `chainSelSync` handles `ChainSelAddPerasCert`, and the object-diffusion layer for Peras certs is present. Any peer connected to a Peras-enabled node can send a crafted certificate with no stake, no keys, and no VRF proof — the degenerate instance accepts it unconditionally. The attack requires no privileged access, no key material, and no stake. [7](#0-6) 

---

### Recommendation

Implement real cryptographic and quorum verification in `validatePerasCert` before Peras is enabled in any deployment. Concretely:

1. Verify the BLS aggregate signature in the certificate against the set of constituent votes and the election ID for the claimed round.
2. Reconstruct the total vote stake from the constituent votes and call `stakeAboveThreshold` (already correct in `Aggregation.hs`) to confirm quorum was reached.
3. Validate the round number is within `perasCertMaxRounds` of the current round.
4. Validate the boosted block's slot satisfies `perasBlockMinSlots`.

The existing `stakeAboveThreshold` and `votesReachQuorum` functions in `SupportsPeras.hs` already implement the quorum gate correctly for vote aggregation; `validatePerasCert` must apply the same gate to the certificate's embedded vote set. [8](#0-7)

### Proof of Concept

On a private testnet with Peras enabled:

1. An adversarial peer connects to an honest node via the Peras certificate diffusion mini-protocol.
2. The adversary constructs a `PerasCert { pcCertRound = r, pcCertBoostedBlock = adversaryBlockPoint }` for a block on a minority fork, with no valid aggregate signature and no quorum of votes.
3. The adversary sends this certificate to the honest node.
4. The honest node calls `validatePerasCert mkPerasParams cert` (the degenerate instance at `SupportsPeras.hs:353`).
5. The function returns `Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = PerasWeight 15 }` without any verification.
6. `chainSelSync` adds the certificate to `PerasCertDB` and calls `chainSelectionForBlock` for `adversaryBlockPoint`.
7. `weightedSelectView` computes `wsvTotalWeight` for the adversary's fragment, which now includes 15 phantom weight units from `weightBoostOfFragment`.
8. `preferCandidate` in `SelectView.hs` compares `wsvTotalWeight ours` vs `wsvTotalWeight cand`; if the adversary's fragment is within 15 weight units of the honest chain, `ShouldSwitch` is returned and the honest node rolls back to the adversary's fork.
9. Repeating with additional fake certificates compounds the phantom weight, enabling rollbacks beyond `k`. [9](#0-8) [10](#0-9)

    -- We need at least one vote to determine who these votes are for, so we
    -- can't vacuously reach a quorum, even if the quorum threshold is 0.
    [] -> Nothing
    -- If we have at least one vote, we must check that all votes are for the

-- Process a Peras certificate by adding it to the PerasCertDB and potentially
-- performing chain selection if a candidate is now better than our selection.
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
