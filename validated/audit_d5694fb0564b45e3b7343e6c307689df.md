### Title
Unregistered Recipient in `safe_mint` Causes Permanent Token Stranding After BTC Deposit — (`contracts/nbtc/src/lib.rs`)

---

### Summary

`safe_mint` in the nBTC token contract mints tokens to the bridge's own account before checking whether the intended recipient is registered. If the recipient is not registered, the function returns `U128(0)` immediately, leaving the minted tokens permanently stranded in the bridge's account with no recovery path. The depositing user's BTC is locked in the bridge and they receive zero nBTC.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, the `safe_mint` function executes in this order:

```rust
// Line 112: tokens are minted to the bridge's own account FIRST
self.token.internal_deposit(&self.bridge_id, amount.into());

// Line 114-116: THEN the recipient registration is checked
if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0));   // early return — tokens stay in bridge
}

// Lines 118-123: only reached if account IS registered
if let Some(msg) = msg {
    self.ft_transfer_call(account_id, amount, None, msg)
} else {
    self.ft_transfer(account_id, amount, None);
    PromiseOrValue::Value(amount)
}
``` [1](#0-0) 

The operation sequence is:

1. `internal_deposit(&self.bridge_id, amount)` — increases the bridge's nBTC balance by `amount`. The total supply is now inflated.
2. `accounts.get(&account_id).is_none()` — checks whether the recipient has a registered storage slot.
3. If the recipient is **not** registered → `return PromiseOrValue::Value(U128(0))`. The `amount` tokens now sit in the bridge's account with no on-chain record linking them to the depositor and no code path to recover them to the user.

The `lost_found` map in `ContractData` is never written here, so there is no built-in recovery mechanism triggered by this path. [2](#0-1) 

---

### Impact Explanation

A user who sends BTC to a bridge deposit address and whose NEAR account is not yet registered in the nBTC token contract will:

- Have their BTC permanently locked in the bridge (the deposit UTXO is consumed and marked verified).
- Receive **zero** nBTC.
- Have no on-chain mechanism to reclaim the stranded tokens, because `safe_mint` does not write to `lost_found` and does not revert the `internal_deposit`.

The minted tokens accumulate in the bridge's own account, inflating the bridge's nBTC balance beyond what it should hold, breaking the 1:1 BTC-to-nBTC backing invariant.

This matches the **Medium** allowed impact: *broken callback rollback / stuck bridge state requiring operator intervention*, and potentially **Critical** if the stranded supply is large enough to be exploited via the bridge's own withdrawal path (bridge account holds real nBTC it did not earn).

---

### Likelihood Explanation

The `safe_deposit` deposit message field exists precisely to support users who may not have pre-registered their NEAR account. Any user who:

1. Constructs a `DepositMsg` with `safe_deposit` set, **or**
2. Deposits BTC to a bridge address before calling `storage_deposit` on the nBTC contract,

will trigger this path. No privileged access is required. The entry point is the public `verify_deposit` → bridge callback → `safe_mint` chain, reachable by any BTC sender. [3](#0-2) 

---

### Recommendation

Reorder the operations so that the registration check (and optional auto-registration) happens **before** `internal_deposit`, or write the stranded amount to `lost_found` before returning, so the user can later claim their tokens:

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "...");

    // Check registration BEFORE minting
    if self.token.accounts.get(&account_id).is_none() {
        // Option A: auto-register
        self.token.internal_register_account(&account_id);
        // Option B: record in lost_found and return 0
    }

    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ... transfer logic
}
```

Alternatively, align with the existing `mint_inner` helper (lines 341–352) which already calls `internal_register_account` when the account is absent, and use it here instead of the manual `internal_deposit` + conditional transfer pattern. [4](#0-3) 

---

### Proof of Concept

1. Alice sends 0.01 BTC to her bridge deposit address. Her `DepositMsg` has `safe_deposit: Some(...)` set.
2. A relayer calls `verify_deposit` with a valid Merkle proof.
3. The bridge's deposit callback calls `nbtc.safe_mint(alice.near, 1_000_000, None)`.
4. Inside `safe_mint`:
   - `internal_deposit(&bridge_id, 1_000_000)` — bridge's nBTC balance increases by 1,000,000 satoshis.
   - `accounts.get(&alice.near)` returns `None` (Alice never called `storage_deposit` on nBTC).
   - Function returns `U128(0)`.
5. Alice's UTXO is marked as verified (`verified_deposit_utxo.insert(...)`), so she cannot request a refund via `request_refund` either (the UTXO is already consumed).
6. Alice has lost 0.01 BTC. The bridge holds 1,000,000 extra nBTC with no owner. [5](#0-4) [6](#0-5)
