### Title
Unbounded Re-execution of `execute_refund` Creates Multiple Competing Pending Refund Transactions for the Same UTXO - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
The `execute_refund` function explicitly permits re-execution after the first execution by bypassing the `verified_deposit_utxo` guard when `refund_request.executed == true`. Any caller (including multiple distinct accounts) can invoke `execute_refund` repeatedly after the timelock passes, each time creating a new `BTCPendingInfo` entry and triggering a fresh MPC signing request for the same deposit UTXO. Only one refund transaction can ever be confirmed on-chain; all others become permanently stale pending entries that require privileged operator cleanup.

### Finding Description

In `load_refund_request_for_execute`, the guard that is supposed to prevent re-execution of an already-executed refund is explicitly bypassed when `executed == true`:

```rust
require!(
    !self.data().verified_deposit_utxo.contains(utxo_storage_key)
        || refund_request.executed,
    "UTXO already verified via deposit, cannot refund"
);
``` [1](#0-0) 

The first call to `execute_refund` sets `executed = true` and inserts the UTXO into `verified_deposit_utxo`:

```rust
self.data_mut()
    .verified_deposit_utxo
    .insert(utxo_storage_key.clone());
// ...
refund_request.executed = true;
self.data_mut()
    .refund_requests
    .insert(utxo_storage_key, refund_request.into());
``` [2](#0-1) 

After this point, the UTXO is in `verified_deposit_utxo` AND `executed == true`, so the guard above evaluates to `true || true` — always passing. Every subsequent call to `execute_refund` by any account proceeds through `finalize_refund_with_psbt`, which creates a brand-new `BTCPendingInfo` (keyed by the PSBT hash, which differs if gas fee or other parameters differ) and issues a new MPC signing request:

```rust
require!(
    self.data_mut()
        .btc_pending_infos
        .insert(btc_pending_id.clone(), btc_pending_info.into())
        .is_none(),
    "pending info already exist"
);
``` [3](#0-2) 

The `execute_refund` public entry point has no access control — any NEAR account can call it:

```rust
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn execute_refund(
    &mut self,
    utxo_storage_key: String,
    chain_specific_data: Option<ChainSpecificData>,
) -> PromiseOrValue<()> {
``` [4](#0-3) 

The `require_pending_sign_capacity` check inside `finalize_refund_with_psbt` is per-caller account, so N different accounts can each call `execute_refund` once and each create their own `BTCPendingInfo` entry for the same UTXO, each triggering a separate MPC signing round. [5](#0-4) 

When one refund transaction is eventually confirmed on-chain and `verify_refund_finalize_callback` runs, it removes only the single `BTCPendingInfo` associated with that confirmed tx_id and removes the refund request:

```rust
self.data_mut()
    .refund_requests
    .remove(&utxo_storage_keys[0]);
self.internal_remove_btc_pending_info(&tx_id);
``` [6](#0-5) 

All other `BTCPendingInfo` entries created by the repeated `execute_refund` calls remain in `btc_pending_infos` indefinitely. They can never be confirmed (the UTXO is already spent) and can only be removed via the privileged `remove_refund_pending_tx_id` path, which itself requires the refund request to already be gone:

```rust
require!(
    !self
        .data()
        .refund_requests
        .contains_key(&utxo_storage_keys[0]),
    "refund request still active"
);
``` [7](#0-6) 

### Impact Explanation
Multiple competing `BTCPendingInfo` entries are created for the same deposit UTXO. Each triggers a real MPC signing round, wasting chain-signature quota. All but one become permanently stale entries that block the affected accounts' `pending_sign_capacity` and require privileged operator intervention (`remove_refund_pending_tx_id`) to clean up. If the operator does not intervene, the affected accounts' pending-sign slots are permanently consumed, preventing future withdrawals or refunds for those accounts. This is a stuck bridge state requiring operator intervention, matching the Medium impact class.

### Likelihood Explanation
`execute_refund` is a public, permissionless function callable by any NEAR account after the timelock elapses. The only cost is the `required_balance_for_execute_refund()` NEAR storage deposit per call. A griefing attacker or a race between multiple honest callers (e.g., competing relayers) can trigger this without any privileged access.

### Recommendation
Track the set of `BTCPendingInfo` IDs created for each refund request (e.g., store them in the `RefundRequest` struct). Before creating a new `BTCPendingInfo` in `finalize_refund_with_psbt`, require that no live pending info already exists for this refund request (i.e., enforce at most one active refund pending info per UTXO at a time). Alternatively, add an explicit cap (e.g., one active pending info per refund request) and reject `execute_refund` calls that would exceed it, analogous to how the zAuction fix introduced a stateful auction ID that invalidates all competing bids once one is accepted.

### Proof of Concept

1. User deposits BTC; deposit is never finalized via `verify_deposit`.
2. User calls `request_refund` with the deposit UTXO → `RefundRequest` created with `executed = false`.
3. Timelock elapses. Account A calls `execute_refund(utxo_key, None)` → `BTCPendingInfo #1` created under account A, `executed = true`, UTXO inserted into `verified_deposit_utxo`.
4. MPC signs `BTCPendingInfo #1` → it moves to `PendingVerify`, freeing A's pending-sign slot.
5. Account B calls `execute_refund(utxo_key, None)` with a different gas fee → guard passes because `executed == true`; `BTCPendingInfo #2` created under account B.
6. Account C calls `execute_refund(utxo_key, None)` → `BTCPendingInfo #3` created under account C.
7. All three refund transactions are signed by MPC and broadcast to Bitcoin.
8. One is confirmed on-chain; `verify_refund_finalize` cleans up only that one entry and removes the refund request.
9. `BTCPendingInfo #2` and `#3` remain in `btc_pending_infos` permanently. Their accounts' pending-sign capacity is consumed. `remove_refund_pending_tx_id` now fails because the refund request is gone — wait, actually it would succeed since the request is gone. But the operator must manually call it for each stale entry; there is no automatic cleanup and no bound on how many such entries can accumulate.
