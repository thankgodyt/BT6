### Title
`safe_mint` Returns Zero Instead of Reverting When User Account Is Unregistered, Permanently Locking Minted Tokens in Bridge Balance — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

The `safe_mint` function in the nBTC token contract deviates from the "safe deposit" specification. When a user's account is not registered in the nBTC contract, `safe_mint` first mints tokens into the bridge's own token balance via `internal_deposit`, then silently returns `U128(0)` instead of reverting. Because NEAR cross-contract state changes are not atomic across contract boundaries, the bridge's callback cannot undo the already-committed mint. The minted tokens are permanently stuck in the bridge's nBTC balance, and the depositing user never receives their nBTC despite their BTC being locked on-chain.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, the `safe_mint` function is the entry point used by the bridge during the "safe deposit" flow (`verify_deposit_v2` with `deposit_msg.safe_deposit = Some(..)`). The bridge documentation explicitly states this flow should **"revert the whole transaction if minting fails (no lost & found)"**.

The implementation, however, does the following:

```rust
// contracts/nbtc/src/lib.rs  lines 101-124
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into()); // ← tokens minted HERE

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));  // ← returns 0 instead of panicking
    }
    ...
}
```

**Root cause**: `internal_deposit` commits a state change to the nBTC contract (minting `amount` tokens into `bridge_id`'s balance) *before* the account-registration check. When the check fails, the function returns `PromiseOrValue::Value(U128(0))` — a silent zero — rather than calling `env::panic_str(...)`. In NEAR Protocol, each cross-contract call's state changes are committed independently. The bridge's callback can revert its own state (e.g., un-mark the deposit as processed), but it **cannot** roll back the `internal_deposit` that already executed inside the nBTC contract. The minted tokens remain permanently credited to `bridge_id`'s nBTC balance with no user-facing recovery path (they are not placed in `lost_found`; `claim_lost_found` only covers the bridge's own `lost_found` map, not the nBTC contract's internal balances).

This is a direct analog to the reported vulnerability class: a function deviates from its interface/specification by returning a silent default value (zero) instead of the expected failure signal (revert/panic), causing callers to observe an inconsistent state.

---

### Impact Explanation

- **Permanent token loss**: Tokens are minted into `bridge_id`'s nBTC balance and are irrecoverable for the user. The user's BTC remains locked in the bridge's Bitcoin address.
- **No recovery mechanism**: The `lost_found` map and `claim_lost_found` entrypoint only cover tokens explicitly placed there by the bridge's own callbacks. Tokens silently absorbed into `bridge_id`'s nBTC balance via `internal_deposit` are not tracked anywhere and cannot be claimed.
- **Supply inflation without backing**: The nBTC total supply increases by `amount`, but no user holds those tokens — they sit in the bridge's own balance, inflating supply relative to the actual user-accessible backed supply.

Impact classification: **Critical** — significant permanent locking of user funds.

---

### Likelihood Explanation

The safe deposit flow (`verify_deposit_v2` with `safe_deposit = Some(..)`) is the path used by Omni Bridge and similar integrators. A user who deposits BTC without first calling `storage_deposit` on the nBTC contract to register their account will trigger this path. This is a realistic and reachable condition: the nBTC contract requires explicit storage registration (NEP-145), and a first-time user or an integrator that omits the registration step will silently lose funds. No privileged access or malicious operator is required — only a normal deposit by an unregistered account.

---

### Recommendation

Move the account-registration check **before** `internal_deposit`, and replace the silent `return PromiseOrValue::Value(U128(0))` with a hard panic so the entire call reverts without any state change:

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "...");

    // Check BEFORE minting
    require!(
        self.token.accounts.get(&account_id).is_some(),
        "safe_mint: account not registered"
    );

    self.token.internal_deposit(&self.bridge_id, amount.into());
    ...
}
```

Alternatively, auto-register the account before minting (mirroring `mint_inner`'s behavior), if the design intent is to never fail silently.

### Proof of Concept

1. User `alice.near` deposits BTC to the bridge's deposit address but has **never** called `storage_deposit` on the nBTC contract.
2. Relayer calls `verify_deposit_v2` with `deposit_msg.safe_deposit = Some(..)`.
3. Bridge verifies the deposit via the BTC Light Client (succeeds).
4. Bridge issues a cross-contract call to `safe_mint(alice.near, amount, msg)` on the nBTC contract.
5. Inside `safe_mint`:
   - `self.token.internal_deposit(&self.bridge_id, amount)` executes — `amount` nBTC is now credited to `bridge_id`'s balance in the nBTC contract. **This state change is committed.**
   - `self.token.accounts.get(&alice.near)` returns `None`.
   - Function returns `PromiseOrValue::Value(U128(0))`.
6. Bridge's safe-deposit callback receives `0`, recognizes failure, and panics to revert its own state (deposit record, etc.).
7. The nBTC contract's `internal_deposit` is **not** rolled back — `amount` nBTC remains in `bridge_id`'s balance.
8. Alice's BTC is locked on-chain. Alice holds 0 nBTC. The bridge holds `amount` extra nBTC with no user claim on it. [1](#0-0) [2](#0-1) [3](#0-2)
