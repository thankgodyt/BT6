### Title
`validatePerasCert` Stub Unconditionally Accepts All Inbound Peras Certificates, Enabling Unprivileged Chain-Selection Manipulation — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance ships a `validatePerasCert` implementation that unconditionally returns `Right` without performing any cryptographic or structural check. The inbound-certificate handler `processCerts` uses this stub as its sole gate before persisting certificates to `PerasCertDB`. Because every accepted certificate immediately contributes a weight boost to the `PerasWeightSnapshot` that drives chain selection, an unprivileged peer can inject arbitrarily crafted certificates that steer an honest node toward an adversary-chosen chain.

---

### Finding Description

**Root cause — stub validation that always succeeds**

The catch-all `BlockSupportsPeras` instance, explicitly labelled *"degenerate instance for all blks to get things to compile"*, provides:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature, no committee membership check, no round-number bounds check — every `PerasCert` is unconditionally wrapped in `ValidatedPerasCert` and returned as `Right`.

**Inconsistency mirrors the external report exactly**

| Object type | Validation path | Outcome |
|---|---|---|
| Block header | `updateChainDepState` → `validateKESSignature` + `validateVRFSignature` | Full cryptographic check |
| Peras certificate | `validatePerasCert` (stub) | Always `Right`, no check | [2](#0-1) 

**Inbound handler uses the stub as its sole gate**

`processCerts` — the function that handles all certificates received from remote peers — calls `validatePerasCert mkPerasParams` as its validation function:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
``` [3](#0-2) 

`processCerts` partitions the batch into `(errors, validCerts)` and only rejects if `errors` is non-empty. Because the stub never produces an error, every certificate in every batch is accepted: [4](#0-3) 

**`implAddCert` also carries an explicit TODO for missing validation**

Even at the storage layer, the developer acknowledged that non-trivial validation logic is absent:

```haskell
-- TODO: we will need to update this method with non-trivial validation logic
-- see https://github.com/tweag/cardano-peras/issues/120
implAddCert ...
``` [5](#0-4) 

**Accepted certificates directly drive chain selection**

Every accepted certificate's `pcCertBoostedBlock` is inserted into the `PerasWeightSnapshot`: [6](#0-5) 

`chainSelectionForBlock` reads this snapshot atomically and passes it to `constructPreferableCandidates` / `preferAnchoredCandidate`, which uses `totalWeightOfFragment` (block count + Peras boost) to rank candidates: [7](#0-6) 

**End-to-end exploit path**

1. Attacker connects to a Peras-enabled node as an ordinary peer.
2. Attacker sends a crafted `PerasCert` via the Peras certificate object-diffusion mini-protocol, with `pcCertBoostedBlock` pointing to an adversary-controlled block.
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right`.
4. `addPerasCertAsync` enqueues the cert; `implAddCert` stores it in `PerasCertDB`.
5. `implGetWeightSnapshot` returns a snapshot that now includes the adversary's boost.
6. On the next chain-selection run, `preferAnchoredCandidate` scores the adversary's chain higher than an equally-long honest chain.
7. The node switches to the adversary-controlled fork.

---

### Impact Explanation

**High — chain-selection manipulation by an unprivileged peer.**

An adversary with no special keys or stake can inject certificates that grant arbitrary weight boosts to chosen block points. This directly violates the Peras security model, which requires certificates to be cryptographically attested by a quorum of eligible committee members before they may influence chain selection. A node that accepts forged certificates can be steered onto a non-canonical chain, breaking the safety guarantees of the Ouroboros Peras protocol.

---

### Likelihood Explanation

**Medium.** The attack requires Peras to be active (the `eraPerasRoundLength` field in `EraParams` must be `PerasEnabled`). Peras is currently in development and not yet deployed on Cardano mainnet, but the code is fully wired in production files and is reachable in any private-testnet or staging environment where Peras is enabled. No privileged access, stake, or key material is required — any peer connection suffices.

---

### Recommendation

1. **Replace the stub immediately.** `validatePerasCert` must perform real cryptographic verification (committee membership, aggregate signature, round-number bounds) before any certificate is accepted. The degenerate instance should be removed or made a compile-time error so that no block type can accidentally inherit it.
2. **Add a provenance check at `implAddCert`.** The `PerasCertDB` storage layer should independently verify that the `ValidatedPerasCert` it receives was produced by a real validation call, not a stub — analogous to how `isPair` is checked for standard pairs in the external report's context.
3. **Gate the object-diffusion handler on a real `PerasCfg`.** Remove the `-- TODO replace when actual plumbing is in place` placeholder in `makePerasCertPoolWriterFromChainDB` before enabling Peras in any networked environment.

---

### Proof of Concept

On a private testnet with Peras enabled:

```
-- Craft a certificate boosting an adversary block
let fakeCert = PerasCert
      { pcCertRound        = someRoundNo
      , pcCertBoostedBlock = adversaryBlockPoint
      }

-- Send via the Peras cert object-diffusion protocol to the target node.
-- processCerts calls (validatePerasCert mkPerasParams fakeCert)
-- which returns Right ValidatedPerasCert unconditionally.
-- The cert is stored; adversaryBlockPoint receives a weight boost.
-- On next chain selection, the node prefers the adversary's chain.
```

Expected: `chainSelectionForBlock` selects the adversary-boosted chain over an equally-long honest chain, confirmed by observing `ShouldSwitch` with `ReasonForSwitch` attributing the preference to the Peras weight boost from the injected certificate.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

chainSelectionForBlock cdb@CDB{..} blockCache hdr punish = electric $ do
  (invalid, curChain, weights) <-
    atomically $
      (,,)
        <$> (forgetFingerprint <$> readTVar cdbInvalid)
        <*> Query.getCurrentChain cdb
        <*> (forgetFingerprint <$> Query.getPerasWeightSnapshot cdb)

  -- The current chain we're working with here is not longer than @k@ blocks
  -- (see 'getCurrentChain' and 'cdbChain'), which is easier to reason about
  -- when doing chain selection, etc.
  assert (fromIntegral (AF.length curChain) <= unNonZero k) pure ()

  let
    immBlockNo :: WithOrigin BlockNo
    immBlockNo = AF.anchorBlockNo curChain

  if
    -- The chain might have grown since we added the block such that the
    -- block is older than the immutable tip.
    | olderThanImmTip hdr immBlockNo -> do
        traceWith addBlockTracer $ IgnoreBlockOlderThanImmTip p

    -- The block is invalid
    | Just (InvalidBlockInfo reason _) <- Map.lookup (headerHash hdr) invalid -> do
        traceWith addBlockTracer $ IgnoreInvalidBlock p reason

        -- We wouldn't know the block is invalid if its prefix was invalid,
        -- hence 'InvalidBlockPunishment.BlockItself'.
        InvalidBlockPunishment.enact
          punish
          InvalidBlockPunishment.BlockItself

    -- Try to select a chain involving the block.
    | otherwise -> do
        -- Construct all 'ChainDiff's involving the block.
        chainDiffs <-
          constructPreferableCandidates
            cdb
            weights
            curChain
            (Map.singleton (headerHash hdr) hdr)
            (headerRealPoint hdr)

        let traceNoChange = traceWith addBlockTracer $ StoreButDontChange p

            chainSelEnv = mkChainSelEnv cdb blockCache weights curChain (Just (p, punish))

        case NE.nonEmpty chainDiffs of
          Just chainDiffs' -> do
            -- Find the best valid candidate and, if valid, perform a
            -- switch. Log if none were found.
            flip whenNothing traceNoChange
              =<< chainSelection
                chainSelEnv
                chainDiffs'
                (switchTo cdb weights (Just p))
          -- No candidate better than our chain.
          Nothing -> traceNoChange
