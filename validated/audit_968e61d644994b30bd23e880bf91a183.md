### Title
Peras Vote Signature and Committee Eligibility Bypass Allows Unauthorized Certificate Forging - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `validatePerasVote` implementation (the degenerate `BlockSupportsPeras` instance used for all block types) only checks whether a voter ID exists in the stake distribution. It performs no cryptographic signature verification and no committee eligibility check. An unprivileged peer can craft votes for any voter in the public stake distribution, submit them via the ObjectDiffusion miniprotocol, and cause the receiving node to accept forged votes, reach quorum, and forge a certificate for an attacker-chosen block — directly manipulating chain selection.

---

### Finding Description

The `BlockSupportsPeras` instance in `SupportsPeras.hs` provides the following `validatePerasVote` implementation:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote{ vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [1](#0-0) 

This stub accepts any `PerasVote` whose `pvVoteVoterId` appears in the stake distribution. It ignores `_params` entirely and performs no check on:
- The vote's cryptographic signature
- The voter's committee eligibility (VRF proof for non-persistent WFALS members)
- Whether the vote is for the correct round

The degenerate `PerasVote` data type for this instance carries no signature field at all:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound   :: PerasRoundNo
  , pvVoteBlock   :: Point blk
  , pvVoteVoterId :: PerasVoterId
  }
``` [2](#0-1) 

This stub is the `validateVote` callback passed into `processVotes` by both `makePerasVotePoolWriterFromVoteDB` and `makePerasVotePoolWriterFromChainDB`:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [3](#0-2) 

`processVotes` is the inbound handler for all Peras votes received from peers. It runs the validation inside an `atomically` block, then calls `addVote` for every vote that passes:

```haskell
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    ([], validatedVotes) ->
      mapM_ (addVote . WithArrivalTime now) validatedVotes
    (errs, _) ->
      throw (PerasVoteValidationError errs)
``` [4](#0-3) 

The only deduplication guard is `alreadyInDbSTM`, which checks whether a `PerasVoteId = (roundNo, voterId)` is already present. This prevents the same `(round, voter)` pair from being counted twice, but it does **not** prevent an attacker from submitting forged votes for **different** voter IDs in the same round. Since the stake distribution is public ledger state, an attacker can enumerate all eligible voter IDs and craft one forged vote per voter, each of which passes `validatePerasVote` and is accepted into the `PerasVoteDB`.

Once enough forged votes accumulate, `updatePerasRoundVoteStates` reaches quorum and `implAddVote` forges a certificate for the attacker-chosen block:

```haskell
Right (VoteGeneratedNewCert cert, pvsRoundVoteStates') ->
  pure (AddedPerasVoteAndGeneratedNewCert cert, pvsRoundVoteStates')
``` [6](#0-5)

### Impact Explanation

A forged certificate boosts the chain weight of the attacker-chosen block via `addPerasCertAsync` → `addPerasVoteWithAsyncCertHandling`. Chain selection in Peras uses these weight boosts to prefer certified blocks over uncertified ones. An attacker who can forge enough votes to reach quorum can therefore cause an honest node to prefer a non-canonical chain, constituting a **Peras voting/certificate check bypass** that enables unauthorized certificate acceptance and chain selection manipulation.

This matches the allowed critical impact: *"Bypass of … PBFT/Praos/TPraos/Peras voting or certificate checks … that enables unauthorized … vote, or certificate acceptance."*

---

### Likelihood Explanation

The attack requires only:
1. **Knowledge of the stake distribution** — public ledger state, readable by any node.
2. **Ability to connect as a peer** — no special privileges; any node on the network qualifies.
3. **Ability to craft `PerasVote` messages** — trivial; the degenerate `PerasVote` type carries only `(roundNo, blockPoint, voterId)` with no signature field.

No cryptographic keys, admin access, stake majority, or VRF/KES compromise is required.

---

### Recommendation

Implement a complete `validatePerasVote` that:
1. Verifies the vote's cryptographic signature against the voter's registered public key.
2. Verifies committee eligibility — for WFALS non-persistent members, this requires checking the VRF proof against the epoch nonce and election ID (as already implemented in `implVerifyVote` in `Committee/WFALS.hs`).
3. Rejects votes whose `pvVoteRound` does not correspond to the current or recent voting window.

The concrete committee implementations (`WFALS`, `EveryoneVotes`) already provide `verifyVote` methods that perform these checks. The degenerate instance should delegate to the appropriate committee's `verifyVote` rather than bypassing it. This is tracked upstream at `https://github.com/tweag/cardano-peras/issues/120`.

---

### Proof of Concept

An attacker peer sends a crafted batch via the ObjectDiffusion miniprotocol targeting round `R` and block `attacker_block`:

```
votes = [
  PerasVote { pvVoteRound = R, pvVoteBlock = attacker_block, pvVoteVoterId = voter_A },
  PerasVote { pvVoteRound = R, pvVoteBlock = attacker_block, pvVoteVoterId = voter_B },
  PerasVote { pvVoteRound = R, pvVoteBlock = attacker_block, pvVoteVoterId = voter_C },
  -- ... enough voter IDs from the public stake distribution to exceed quorum threshold
]
```

Each vote passes `validatePerasVote` (voter IDs are in the stake distribution; no signature is checked). `processVotes` adds all of them to the `PerasVoteDB`. `updatePerasRoundVoteStates` accumulates their stake. When the quorum threshold is crossed, `implAddVote` returns `AddedPerasVoteAndGeneratedNewCert cert` for `attacker_block`. The certificate is propagated to `ChainDB` via `addPerasCertAsync`, boosting `attacker_block`'s chain weight and causing chain selection to prefer it.
