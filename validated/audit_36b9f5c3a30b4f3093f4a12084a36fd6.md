### Title
Unrestricted `request_refund` Allows Front-Running to Redirect BTC Refunds or Permanently DoS Legitimate Refund Requests - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary

`request_refund` is publicly callable by any NEAR account. The refund-request map is keyed by `utxo_storage_key` (`{tx_id}@{vout}`) and the first writer wins. A malicious actor who observes a pending `request_refund` call on NEAR can front-run it with an identical `deposit_msg` / `tx_bytes` / `proof` but a different `refund_address` (their own BTC address). The legitimate user's subsequent call is then rejected with "Refund request already exists for this UTXO", and if the DAO/Operator fails to reject the malicious request before `unsafe_refund_timelock_sec` elapses, the attacker can call `execute_refund` and redirect the deposited BTC to their own address.

### Finding Description

`request_refund` sits inside a `#[trusted_relayer] #[near] impl Contract` block but carries **no** per-method `#[trusted_relayer]` attribute of its own:

```rust
// contracts/satoshi-bridge/src/api/bridge.rs  lines 480-535
#[trusted_relayer]
#[near]
impl Contract {
    #[allow(clippy::too_many_arguments)]
    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise { ... }
```

Compare with `verify_refund_finalize` and `remove_refund_pending_tx_id` in the same block, which carry their own `#[trusted_relayer]` and are therefore relayer-gated. The impl-level attribute is used for code-generation only; individual methods require their own attribute to be access-controlled. `get_user_deposit_address` in the first impl block (no per-method `#[trusted_relayer]`) confirms this: it is intentionally public.

The callback that stores the request enforces a first-writer-wins rule:

```rust
// contracts/satoshi-bridge/src/refund.rs  lines 544-547
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
```

The stored `refund_address` is taken verbatim from the caller when `deposit_msg.refund_address` is `None`:

```rust
// contracts/satoshi-bridge/src/refund.rs  lines 154-159
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
```

After `unsafe_refund_timelock_sec` elapses, **anyone** can call `execute_refund` and the BTC is sent to the stored `refund_address`.

All inputs needed to mount the attack (`deposit_msg`, `tx_bytes`, `vout`, Merkle proof) are publicly visible on the Bitcoin blockchain.

### Impact Explanation

**Critical / Medium.**

- **Fund theft (Critical):** If the attacker front-runs with their own BTC address and the DAO/Operator does not reject the request within `unsafe_refund_timelock_sec`, the attacker calls `execute_refund` and the bridge's MPC pipeline signs a transaction paying the deposited BTC to the attacker's address. The legitimate depositor loses their BTC permanently.
- **Permanent DoS (Medium):** Even if the DAO/Operator rejects each malicious request, the attacker can immediately re-submit after every rejection (paying the storage deposit each time). The legitimate user can never land their own request while the attacker keeps front-running, permanently locking the deposited BTC in the bridge's UTXO set with no recovery path.

### Likelihood Explanation

**High.** The attack requires only:
1. Watching the NEAR mempool (or the Bitcoin chain) for a `request_refund` call targeting a UTXO whose `deposit_msg.refund_address` is `None`.
2. Submitting an identical call with a different `refund_address` at a higher gas price.

All data is public. The only cost is the attached NEAR storage deposit, which is negligible compared to the BTC value at risk. Deposits without a pre-set `refund_address` are the common case (the field is optional and many users will omit it).

### Recommendation

Apply one or both of the following fixes, analogous to the nested-mapping fix in the EthenaMinting report:

1. **Bind the refund request to the caller.** Store `(utxo_storage_key, predecessor_account_id)` as the composite key, or record the submitter and require that only the submitter (or DAO/Operator) can execute the refund. This prevents a third party from hijacking the slot.

2. **Require `deposit_msg.refund_address` to be set.** Reject `request_refund` calls where `deposit_msg.refund_address` is `None`. Because `deposit_msg` is hashed to derive the deposit address, the refund address is then committed at deposit time and cannot be overwritten by a front-runner.

3. **Add per-method `#[trusted_relayer]` to `request_refund`.** If only trusted relayers should be able to submit refund requests, add the attribute explicitly (matching the pattern of `verify_refund_finalize`). This is a simpler short-term fix but changes the permissioning model.

### Proof of Concept

1. Alice deposits 1 BTC to the bridge using a `deposit_msg` with `refund_address: None`. The deposit is never finalized (e.g., wrong amount sent).
2. Alice constructs a `request_refund` call with `refund_address = "alice_btc_address"` and broadcasts it to NEAR.
3. Bob (attacker) observes Alice's pending transaction in the NEAR mempool. Bob submits an identical call — same `deposit_msg`, `tx_bytes`, `vout`, `proof` — but with `refund_address = "bob_btc_address"`, at a higher gas price.
4. Bob's transaction lands first. `request_refund_callback` stores `RefundRequest { refund_address: "bob_btc_address", ... }` under `utxo_storage_key`.
5. Alice's transaction lands and reverts: `"Refund request already exists for this UTXO"`.
6. If the DAO/Operator does not call `reject_refund` before `unsafe_refund_timelock_sec` elapses, Bob calls `execute_refund`. The bridge builds a PSBT paying 1 BTC to `"bob_btc_address"`, the MPC signs it, and Alice's BTC is stolen.
7. If the DAO/Operator does reject, Bob immediately re-submits step 3, repeating indefinitely and permanently blocking Alice's refund. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
