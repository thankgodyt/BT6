### Title
Peras Certificate Validation Stub Unconditionally Accepts All Inbound Certificates, Enabling Unauthorized Chain-Weight Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The sole production instance of `BlockSupportsPeras` implements `validatePerasCert` as a stub that unconditionally returns `Right` for every certificate it receives, performing no cryptographic or structural checks. Because this is the only instance wired into the live Peras certificate diffusion inbound handler, any unprivileged peer can inject arbitrary `PerasCert` objects that will be accepted without validation and stored in the `ChainDB`, where they apply a configurable chain-weight boost to an attacker-chosen block.

---

### Finding Description

The `BlockSupportsPeras` type class declares `validatePerasCert` as the mandatory gate for all inbound Peras certificates. The only concrete instance — a catch-all `instance StandardHash blk => BlockSupportsPeras blk` — implements this method as a stub that always succeeds:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

The production inbound certificate pool writer, `makePerasCertPoolWriterFromChainDB`, passes this stub directly as the validation callback:

```haskell
(validatePerasCert mkPerasParams)  -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` then calls this callback on every new certificate received from a peer. Because the callback always returns `Right`, the `([], validatedCerts)` branch is always taken and every certificate is timestamped and forwarded to `ChainDB.addPerasCertAsync`: [3](#0-2) 

This pool writer is wired directly into the live node-to-node `hPerasCertDiffusionClient` handler:

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      ...
``` [4](#0-3) 

The analog to the Gravity bridge bug is exact: just as `SubmitBadSignatureEvidence` was defined but its handler omitted — making the security check unreachable — here `validatePerasCert` is defined in the class but its only live implementation is a no-op stub, making the security check permanently bypassed.

---

### Impact Explanation

A `ValidatedPerasCert` carries a `vpcCertBoost` equal to `perasWeight params` (default: 15). Once stored in the `ChainDB`, this boost is applied to the certified block during chain selection, causing the node to prefer the boosted chain over competing forks. An attacker who can inject a certificate pointing to an adversarially chosen block can therefore make an honest node switch to a non-canonical chain without holding any stake or keys.

This matches the **High** impact category: *chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions*, and also the **Critical** category: *bypass of Peras certificate checks that enables unauthorized certificate acceptance*. [5](#0-4) 

---

### Likelihood Explanation

The `PerasCertDiffusion` mini-protocol is active in the live node-to-node application stack. Any peer that connects to a node running this code can send a crafted `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock`. No stake, keys, or special privileges are required. The only prerequisite is a standard peer connection, which is available to any participant in the network. [6](#0-5) 

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real one that verifies:
1. The certificate's aggregate BLS signature over the claimed voters and election target.
2. That the claimed voters are eligible committee members (via the `CryptoSupportsVotingCommittee` interface already present in the codebase).
3. That the total weight of the certified voters meets the quorum threshold.

Until real validation is implemented, the `hPerasCertDiffusionClient` handler should not be exposed to untrusted peers, or inbound certificates should be silently dropped rather than unconditionally accepted. [7](#0-6) 

---

### Proof of Concept

1. Connect to a node as a peer via the `PerasCertDiffusion` mini-protocol.
2. Send a `PerasCert` with `pcCertRound = <target round>` and `pcCertBoostedBlock = <attacker-chosen block point>`.
3. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = 15 })` unconditionally.
4. The certificate is stored in the `ChainDB` via `addPerasCertAsync`.
5. Chain selection now applies a weight boost of 15 to the attacker-chosen block, causing the honest node to prefer the adversarial chain. [8](#0-7) [9](#0-8)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do

    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
