### Title
Peras Vote Signature Verification Bypass in Stub `validatePerasVote` / `validatePerasCert` Instances — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `BlockSupportsPeras` instance for all block types ships with stub implementations of `validatePerasVote` and `validatePerasCert` that perform no cryptographic verification. `validatePerasCert` unconditionally returns `Right` for every certificate, and `validatePerasVote` only checks that the claimed voter ID exists in the stake distribution — no signature is verified in either case. Because these stubs are the only implementations in the codebase and are wired into the live vote-ingestion path reachable from unprivileged peers, an adversary can inject crafted votes or certificates that are accepted as legitimate, forge quorum certificates for arbitrary blocks, and manipulate Peras-weighted chain selection.

These stubs are consumed directly by the live vote-ingestion pipeline. In `makePerasVotePoolWriterFromChainDB` (`Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasVote.hs`, lines 131–148), inbound peer votes are processed via `processVotes`, which calls the `validatePerasVote` closure:

```haskell

```

`processVotes` (lines 170–) accepts any vote that passes this check and timestamps and stores it. Once stored, `implAddVote` in `PerasVoteDB/Impl.hs` (lines 174–240) calls `updatePerasRoundVoteStates`, which calls `votesReachQuorum` → `stakeAboveThreshold`. If the accumulated fake-vote stake exceeds the quorum threshold (default 3/4 + 2/100 = 0.77), a `ValidatedPerasCert` is forged and returned to the caller for chain-selection processing.

### Impact Explanation

**Impact: Critical — Bypass of Peras vote/certificate verification enabling unauthorized certificate acceptance and chain-selection manipulation.**

An adversary who can send `PerasVote` messages to a node (any unprivileged peer connected via the object-diffusion mini-protocol) can:

1. Claim to be any `PerasVoterId` present in the current stake distribution.
2. Have the vote accepted with that voter's full stake weight, because no signature is checked.
3. Repeat with different voter IDs until the accumulated stake exceeds the quorum threshold.
4. Trigger automatic forging of a `ValidatedPerasCert` boosting an adversarially chosen block.
5. Cause honest nodes to assign extra `PerasWeight` to that block during chain selection (`constructPreferableCandidates` / `compareChainDiffs`), potentially making a weaker or adversarial chain appear preferred.

This directly satisfies the "Critical — Bypass of certificate/vote verification checks that enables unauthorized certificate acceptance" impact class.

### Likelihood Explanation

**Likelihood: Medium.**

The Peras vote-diffusion path (`makePerasVotePoolWriterFromChainDB`, `processVotes`) is wired into the node's network layer and is reachable from any connected peer without authentication. The stub instance applies to all block types via `instance StandardHash blk => BlockSupportsPeras blk`, so there is no concrete block type that overrides it with real verification. The only mitigating factor is that Peras is still under active development and may not yet be enabled on mainnet; however, the code is in the production source tree and the ingestion path is live.

### Recommendation

1. Implement real cryptographic signature verification in `validatePerasVote` before the Peras vote-diffusion path is enabled in any network-connected environment. The `BlockSupportsPeras` class already provides the correct interface; the stub must be replaced with an implementation that verifies the vote's signature against the claimed voter's public key from the stake distribution.
2. Implement real certificate verification in `validatePerasCert` (aggregate-signature check over the constituent votes).
3. Resolve the unit-mismatch in `stakeAboveThreshold` by normalizing `PerasVoteStake` to a relative value before comparison, or by passing the total stake into the function.
4. Gate the vote-ingestion path behind a feature flag that is disabled until all three items above are complete.

### Proof of Concept

An attacker connected to a node via the Peras vote object-diffusion mini-protocol:

1. Reads the current `PerasVoteStakeDistr` (available via the ledger state query interface).
2. Constructs a `PerasVote { pvVoteRound = r, pvVoteBlock = adversarialPoint, pvVoteVoterId = legitimateVoterId }` for each high-stake voter ID in the distribution — no private key is needed.
3. Sends these votes to the target node. `processVotes` calls `validatePerasVote mkPerasParams sd vote`; since `lookupPerasVoteStake` finds the voter ID in the distribution, each vote is accepted and stored with the voter's full stake.
4. Once accumulated stake exceeds `perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin` (0.77 by default), `updatePerasRoundVoteStates` forges a `ValidatedPerasCert` for `adversarialPoint`.
5. The certificate is passed to `ChainDB.addPerasVoteWithAsyncCertHandling`, which triggers chain selection with the boosted block weight, potentially causing the node to switch to the adversarial chain.

-- | Check whether a given vote stake is above the quorum threshold.
--
-- TODO: this function assumes that the 'PerasVoteStake' and the quorum
-- threshold used in 'PerasParams' are expressed in the same units. That is,
-- both are either absolute or relative (normalized) values. Under the current
-- current implementation of 'PerasParams', this function only makes sense when
-- both values are relative (normalized) values, so we should either normalize
-- the 'PerasVoteStake' before calling this function, or change this function to
-- accept a stake distribution and perform the normalization internally.
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin

    unPerasVoteStake voteStake
  quorumThreshold =
    unPerasQuorumStakeThreshold
