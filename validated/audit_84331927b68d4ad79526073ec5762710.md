### Title
Silent Discard of Envelope Validation in `revalidateHeader` Due to `assertWithMsg` Being a No-Op in Production Builds — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Util/Assert.hs`, `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/HeaderValidation.hs`)

---

### Summary

`assertWithMsg` is a compile-time conditional guard that **silently discards** its `Either String ()` argument in production builds (when `ENABLE_ASSERTIONS` is not defined). `revalidateHeader` relies exclusively on `assertWithMsg` to enforce the header envelope check (block number, slot number, and prev-hash chain integrity). In production, this check is never enforced. Any block with an invalid envelope that reaches the `reapplyBlockLedgerResult` path — e.g., via a crafted snapshot or ImmutableDB input — will be silently accepted into the extended ledger state.

---

### Finding Description

**Root cause — `assertWithMsg` is a no-op in production:**

`assertWithMsg` in `Assert.hs` is defined as:

```haskell
assertWithMsg :: HasCallStack => Either String () -> a -> a
#if ENABLE_ASSERTIONS
assertWithMsg (Left msg) _ = error msg
#endif
assertWithMsg _ a = a
``` [1](#0-0) 

When `ENABLE_ASSERTIONS` is not defined (the default in production/optimized builds), the only active equation is `assertWithMsg _ a = a`. The `Either String ()` argument — the validation result — is **unconditionally discarded**. This is the direct analog of the ERC-20 unchecked return value: the check is computed, but its failure branch is silently thrown away.

**Propagation — `revalidateHeader` relies solely on this guard:**

`revalidateHeader` uses `assertWithMsg envelopeCheck` as its only enforcement of the header envelope invariants:

```haskell
revalidateHeader cfg ledgerView hdr st =
  assertWithMsg envelopeCheck $
    HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'
 where
  envelopeCheck = runExcept $ withExcept show $
    validateEnvelope cfg ledgerView (untickedHeaderStateTip st) hdr
``` [2](#0-1) 

`validateEnvelope` checks that block numbers are consecutive, slot numbers are strictly increasing, and the `prevHash` field chains correctly to the previous tip. [3](#0-2) 

In production, `assertWithMsg envelopeCheck $ HeaderState ...` reduces to `HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'` regardless of whether `envelopeCheck` is `Left` (invalid) or `Right` (valid). The envelope check is never enforced.

**Call site — `reapplyBlockLedgerResult` in the production `ApplyBlock` instance:**

`revalidateHeader` is called unconditionally from `reapplyBlockLedgerResult` in the `ApplyBlock ExtLedgerState blk` instance:

```haskell
reapplyBlockLedgerResult evs cfg blk TickedExtLedgerState{..} =
    (\l -> ExtLedgerState l hdr) <$> castLedgerResult ledgerResult
   where
    hdr = revalidateHeader (getExtLedgerCfg cfg) ledgerView (getHeader blk) tickedHeaderState
``` [4](#0-3) 

This is the production reapply path for the extended ledger state, used whenever a block is in the `prevApplied` set (i.e., `ReapplyRef` or `ReapplyVal` in the forker): [5](#0-4) 

---

### Impact Explanation

In production builds, `revalidateHeader` **never enforces** the header envelope invariants (block number, slot number, prev-hash). A block with an invalid envelope — wrong block number, non-monotone slot, or broken hash chain — that reaches `reapplyBlockLedgerResult` will be silently accepted into the `ExtLedgerState`. This can cause durable use of a wrong ledger state, breaking the chain integrity invariants that the rest of the consensus layer depends on.

This matches: **High — LedgerDB/snapshot replay/rollback bug that causes durable use of the wrong ledger state.**

---

### Likelihood Explanation

The `reapplyBlockLedgerResult` path is triggered for any block whose `RealPoint` is in the `prevApplied` set. The attacker-controlled entry paths are:

1. **Crafted on-disk snapshot or ImmutableDB data**: A node that loads a snapshot or replays blocks from a corrupted/crafted ImmutableDB will call `reapplyBlockLedgerResult` for those blocks. Since `revalidateHeader` silently passes any envelope, a block with a broken hash chain or wrong block number will be accepted without error.
2. **Any future or existing code path that incorrectly marks an unvalidated block as previously applied**: Because the guard is a no-op, there is no safety net.

The `ENABLE_ASSERTIONS` flag is not set in standard production builds (it is an opt-in cabal flag), so this is the default behavior for all deployed nodes. [1](#0-0) 

---

### Recommendation

Replace the `assertWithMsg`-guarded envelope check in `revalidateHeader` with an unconditional enforcement. Either:

1. **Throw an impure error unconditionally** (matching the intent of the existing code, but without the compile-time gate):
   ```haskell
   revalidateHeader cfg ledgerView hdr st =
     case envelopeCheck of
       Left msg -> error ("revalidateHeader: envelope check failed: " <> msg)
       Right () -> HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'
   ```
2. **Return `Either` and propagate the error** to callers, making the failure visible in the type system and forcing callers to handle it.

The `assertWithMsg` pattern is appropriate only for invariants that are guaranteed by construction and where a debug-only check is sufficient. Header envelope integrity during reapplication is a chain-safety invariant and must be enforced unconditionally.

---

### Proof of Concept

1. Compile the node **without** the `ENABLE_ASSERTIONS` cabal flag (the default).
2. Craft an ImmutableDB or snapshot containing a block `B` at slot `s` whose `headerPrevHash` does not match the hash of the preceding block (i.e., `validateEnvelope` would return `Left`).
3. Start the node so that it loads the snapshot and calls `reapplyBlockLedgerResult` for `B`.
4. Observe that `revalidateHeader` returns a valid `HeaderState` for `B` without error, and the node proceeds with the corrupted ledger state — the `envelopeCheck` `Left` result is silently discarded by `assertWithMsg _ a = a`. [1](#0-0) [2](#0-1) [4](#0-3)
