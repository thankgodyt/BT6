### Title
Whitelisted `post_action` Receiver Without Msg Templates Accepts Arbitrary User-Controlled `msg` - (File: `contracts/satoshi-bridge/src/deposit_msg.rs`)

### Summary

The `check_deposit_msg` function only validates `post_actions[].msg` against configured templates when templates exist for a given whitelisted receiver. When a contract is added to `post_action_receiver_id_white_list` without a corresponding entry in `post_action_msg_templates`, any user can embed an arbitrary `msg` string in `DepositMsg.post_actions[].msg`. That string is then passed verbatim to the whitelisted contract's `ft_on_transfer` via `handle_post_action` in the nBTC contract.

### Finding Description

In `check_deposit_msg` (`contracts/satoshi-bridge/src/deposit_msg.rs`, lines 117–143), the template check is guarded by an `if let Some(msg_templates) = ...` branch:

```rust
if let Some(msg_templates) = self
    .data()
    .post_action_msg_templates
    .get(&post_action.receiver_id)
{
    // validate msg against templates
    ...
    if !is_match {
        return None;
    }
}
// ← If no templates exist for this receiver, ANY msg passes through
``` [1](#0-0) 

When no templates are registered for a whitelisted receiver, the `msg` field is completely unconstrained. The validated `post_actions` are then forwarded through `verify_deposit_callback` → `nbtc.mint(post_actions)` → `handle_post_actions` → `handle_post_action`, which executes:

```rust
ext_ft_receiver::ext(receiver_id.clone())
    .with_static_gas(receiver_gas)
    .ft_on_transfer(sender_id.clone(), amount.into(), msg)
``` [2](#0-1) 

The `msg` is user-supplied and reaches the whitelisted contract's `ft_on_transfer` without any content restriction. The only guard in `handle_post_action` is that `receiver_id != self.bridge_id` (the bridge contract), but the nBTC contract itself and any other whitelisted contract are not blocked. [3](#0-2) 

This is the direct analog to H-1: the bridge makes a call to a user-specified target (`receiver_id`, constrained to a whitelist) with user-specified call data (`msg`, unconstrained when no templates exist).

### Impact Explanation

If a whitelisted DeFi contract (e.g., a lending protocol like Burrowland) has `ft_on_transfer` logic that interprets `msg` as instructions — such as "deposit collateral and borrow on behalf of `sender_id`" — an attacker can craft a `msg` that triggers unintended operations in that contract. Because `ft_on_transfer` is called with the depositor as `sender_id`, the whitelisted contract attributes the action to the depositor, who controls the `msg` content. This bypasses the bridge's own message-validation policy (the template system) and can cause harmful smart-contract behavior in whitelisted protocols without direct theft from the bridge itself.

### Likelihood Explanation

The `post_action_msg_templates` map is optional and separate from the whitelist. The DAO can whitelist a receiver via `extend_post_action_receiver_id_white_list` without ever calling `extend_post_action_msg_templates` for it. [4](#0-3) [5](#0-4) 

Any user can then craft a `DepositMsg` with an arbitrary `msg` for that receiver, send BTC to the derived deposit address, and rely on an automated relayer to call `verify_deposit`. The relayer does not inspect `msg` content — it only verifies the BTC transaction inclusion proof.

### Recommendation

1. **Require templates for all whitelisted receivers**: In `check_deposit_msg`, treat the absence of a template entry for a whitelisted receiver as a validation failure (reject the post_action rather than silently accepting any `msg`).
2. **Alternatively**, document explicitly that whitelisting a receiver without templates grants users unrestricted `msg` control, and enforce that templates are always configured before a receiver is added to the whitelist.

### Proof of Concept

1. DAO calls `extend_post_action_receiver_id_white_list(["defi.near"])` but does **not** call `extend_post_action_msg_templates("defi.near", ...)`.
2. Attacker crafts:
   ```json
   {
     "recipient_id": "attacker.near",
     "post_actions": [{
       "receiver_id": "defi.near",
       "amount": "1",
       "msg": "<arbitrary_exploit_payload>",
       "gas": "50000000000000"
     }]
   }
   ```
3. Attacker calls `get_user_deposit_address(deposit_msg)` to derive the deposit address, then sends BTC to it.
4. Automated relayer calls `verify_deposit(deposit_msg, tx_bytes, ...)`.
5. `check_deposit_msg` finds `defi.near` on the whitelist, finds **no** templates for it, and returns the post_action as valid.
6. After BTC proof verification, `nbtc.mint(..., post_actions)` is called; `handle_post_action` transfers 1 nBTC to `defi.near` and calls `defi.near.ft_on_transfer("attacker.near", 1, "<arbitrary_exploit_payload>")`.
7. `defi.near` processes the arbitrary payload, potentially performing unintended operations on behalf of `attacker.near`. [1](#0-0) [6](#0-5)

    #[private]
    pub fn handle_post_action(
        &mut self,
        sender_id: AccountId,
        receiver_id: AccountId,
        amount: U128,
        memo: Option<String>,
        msg: String,
    ) {
        require!(
            env::prepaid_gas() > GAS_FOR_FT_TRANSFER_CALL,
            "More gas is required"
        );
        require!(
            receiver_id != self.bridge_id,
            "handle_post_action: receiver_id must not be the bridge"
        );
        let amount = amount.into();
        self.token
            .internal_transfer(&sender_id, &receiver_id, amount, memo);
        let receiver_gas = env::prepaid_gas()
            .checked_sub(GAS_FOR_FT_TRANSFER_CALL)
            .unwrap_or_else(|| env::panic_str("Prepaid gas overflow"));
        // Initiating receiver's call and the callback
        ext_ft_receiver::ext(receiver_id.clone())
            .with_static_gas(receiver_gas)
            .ft_on_transfer(sender_id.clone(), amount.into(), msg)
            .then(
                ext_ft_resolver::ext(env::current_account_id())
                    .with_static_gas(GAS_FOR_RESOLVE_TRANSFER)
                    .ft_resolve_transfer(sender_id, receiver_id, amount.into()),
            )
            .detach();

    #[payable]
    #[access_control_any(roles(Role::DAO))]
    pub fn extend_post_action_msg_templates(
        &mut self,
        contract_id: AccountId,
        templates: HashSet<String>,
    ) {
        assert_one_yocto();
        require!(!templates.is_empty(), "empty templates.");
        if let Some(msg_templates) = self
            .data_mut()
            .post_action_msg_templates
            .get_mut(&contract_id)
        {
            for template in templates {
                let is_success = msg_templates.insert(template.clone());
                require!(is_success, format!("{:?} is exist.", template));
            }
        } else {
            self.data_mut()
                .post_action_msg_templates
                .insert(contract_id, templates);
        }
    }
