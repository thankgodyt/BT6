### Title
Unconditional `validatePerasCert` Stub Allows Any Peer to Inject Arbitrary Peras Weight Boosts, Corrupting Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance implements `validatePerasCert` as an unconditional stub that returns `Right` for every input, performing no cryptographic or structural verification. Because the inbound Peras certificate diffusion path calls this function to gate admission into the `PerasCertDB`, any connected peer can inject arbitrary `PerasCert` values — with any round number and any boosted block point — that are stored as `ValidatedPerasCert` and immediately influence chain selection via Peras weight boosts. This is a direct analog to the `releaseTokens()` missing access control: the function that is supposed to restrict who can produce a validated certificate has no guard at all.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub:** [1](#0-0) 

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

Every `PerasCert` — regardless of its content, round number, boosted block, or whether any quorum of committee members ever signed it — is unconditionally wrapped in `Right (ValidatedPerasCert ...)`. No signature, no committee membership check, no quorum threshold check.

**Inbound diffusion path wires this stub directly into the ChainDB:**

The production handler `makePerasCertPoolWriterFromChainDB` passes `validatePerasCert mkPerasParams` as the sole validation gate before storing a peer-supplied certificate: [2](#0-1) 

`processCerts` then calls this function on every inbound certificate not already in the DB, and on a clean pass (`[]` errors) adds all of them to the ChainDB: [3](#0-2) 

**The stored certificates directly drive chain selection:**

`PerasCertDB.implGetWeightSnapshot` builds a `PerasWeightSnapshot` from every stored certificate's `(boostedBlock, boost)` pair. `compareAnchoredFragments` and `preferAnchoredCandidate` read this snapshot and compute `wsvTotalWeight = blockNo + weightBoost` for each candidate fragment: [4](#0-3) [5](#0-4) 

A fragment whose tip block has been boosted by an injected certificate will have a higher `wsvTotalWeight` and will be preferred over an honest chain of equal or even greater block number.

**The `implAddCert` implementation also carries an explicit TODO confirming validation is absent:** [6](#0-5) 

---

### Impact Explanation

**High — chain selection manipulation by an unprivileged peer.**

An attacker who is a connected peer can craft a `PerasCert` naming any `pcCertBoostedBlock` (any `Point blk`) and any `pcCertRound`. Because `validatePerasCert` accepts it unconditionally, the certificate is stored and its boost is added to the `PerasWeightSnapshot`. Chain selection then uses `wsvTotalWeight` (block number + boost) to compare fragments. By injecting a certificate that boosts a block on the attacker's fork, the attacker can make an honest node prefer a non-canonical chain over the honest chain, even when the honest chain has more blocks. This breaks the Peras chain-selection invariant and constitutes a consensus safety failure: the node diverges from the canonical chain based on fabricated weight evidence.

---

### Likelihood Explanation

**High.** The attack requires only a standard node-to-node connection — no keys, no stake, no privileged access. The Peras certificate diffusion mini-protocol (`hPerasCertDiffusionClient`) is wired into the production node-to-node handler and is reachable by any peer the node connects to: [7](#0-6) 

The attacker needs only to send a well-formed CBOR-encoded `PerasCert` message over the ObjectDiffusion protocol. No brute force, no cryptographic break, no social engineering.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real one that:
1. Verifies the aggregate BLS/committee signature over the certificate body.
2. Checks that the signing committee members constitute a valid quorum (total stake ≥ threshold) for the round's committee.
3. Verifies the boosted block point is a known, valid block on a plausible chain.

Until the real implementation is ready, the inbound certificate diffusion handler should refuse all peer-supplied certificates (e.g., by always returning `Left PerasValidationErr`) rather than accepting them unconditionally. The `ValidatedPerasCert` newtype wrapper should only be constructible via a function that enforces these checks.

---

### Proof of Concept

1. Connect to a target node as a standard peer.
2. Initiate the `PerasCertDiffusion` mini-protocol (ObjectDiffusion variant for certs).
3. Send a `PerasCert` with:
   - `pcCertRound = <any round number not yet in the DB>`
   - `pcCertBoostedBlock = <Point of a block on the attacker's fork>`
4. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams })`.
5. The certificate is stored via `ChainDB.addPerasCertAsync`.
6. `implGetWeightSnapshot` now includes `(attackerForkBlock, perasWeight)` in the snapshot.
7. On the next chain selection event, `preferAnchoredCandidate` computes `wsvTotalWeight` for the attacker's fork as `blockNo + perasWeight`, which exceeds the honest chain's `blockNo + 0`.
8. The node switches to the attacker's fork. [8](#0-7) [9](#0-8) [10](#0-9) [11](#0-10)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
