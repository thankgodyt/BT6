Audit Report

## Title
`fin_transfer_send_tokens_callback` Ignores `ft_transfer`/`mint` Failure, Permanently Freezing Inbound Bridged Funds — (File: `near/omni-bridge/src/lib.rs`)

## Summary
When an inbound transfer (foreign chain → NEAR) is finalized via `fin_transfer`, `process_fin_transfer_to_near` commits the transfer ID to `finalised_transfers` via `add_fin_transfer` before token delivery executes. The callback `fin_transfer_send_tokens_callback` delegates failure detection to `is_refund_required`, which only inspects the promise result when `is_ft_transfer_call = true`. For all plain token deliveries (`msg` is empty), `is_ft_transfer_call = false` and `is_refund_required` returns `false` unconditionally — never reading the promise result. A failed `ft_transfer` or `mint` is silently treated as success, the transfer ID is permanently stuck in `finalised_transfers`, and the user's funds are frozen with no recovery path.

## Finding Description

**Root cause — `is_refund_required` does not inspect the promise result for non-`ft_transfer_call` paths.**

In `process_fin_transfer_to_near` (`near/omni-bridge/src/lib.rs`, L1875), `add_fin_transfer` is called first, inserting the transfer ID into `finalised_transfers` in the same receipt as `fin_transfer_callback`. This state change is irrevocably committed before the chained `send_tokens` receipt executes. [1](#0-0) 

`unlock_tokens_if_needed` is also called in the same receipt, decreasing `locked_tokens` accounting before delivery is confirmed. [2](#0-1) 

`send_tokens` is then dispatched. For the common case (`msg` is empty), it calls `ft_transfer` (non-deployed token) or `mint` (deployed token) with no message argument. [3](#0-2) 

The `is_ft_transfer_call` flag passed to the callback is `!msg.is_empty()`, which is `false` for all plain deliveries. [4](#0-3) 

Inside `fin_transfer_send_tokens_callback`, `is_refund_required(false)` is called. The `else` branch returns `false` unconditionally without calling `env::promise_result_checked`, so the callback cannot distinguish a successful delivery from a failed one. [5](#0-4) 

Because `is_refund_required` returns `false`, the else-branch executes: the fee is paid out and `FinTransferEvent` is emitted as if delivery succeeded. `remove_fin_transfer` is never called. [6](#0-5) 

The transfer ID remains in `finalised_transfers` permanently. Any retry of `fin_transfer` with the same proof panics with `TransferAlreadyFinalised` at `add_fin_transfer`. [7](#0-6) 

The same issue applies to the wNEAR path: `near_withdraw_callback` panics on failure, causing the `send_tokens` promise to fail, but `fin_transfer_send_tokens_callback` still takes the success path because `is_ft_transfer_call = false`. [8](#0-7) 

**Existing guards are insufficient.** The storage balance check in `process_fin_transfer_to_near` (L1905–1913) runs in a prior receipt; the actual `ft_transfer` executes in a subsequent receipt where the token contract state may have changed. No guard in `fin_transfer_send_tokens_callback` inspects the promise result for the non-`ft_transfer_call` case. [9](#0-8) 

## Impact Explanation

**Critical — permanent freezing of bridged funds.**

For native tokens (originated on NEAR, locked in the bridge on outbound): `unlock_tokens_if_needed` decreases `locked_tokens` accounting, but the tokens remain in the bridge contract because `ft_transfer` failed. The transfer is permanently in `finalised_transfers` and cannot be re-submitted. The tokens are frozen in the bridge contract with no on-chain recovery mechanism. [2](#0-1) 

For deployed/bridged tokens: `mint` fails, no tokens are created for the user, yet the transfer is marked finalized. The user's cross-chain value is destroyed with no recourse. [10](#0-9) 

This matches the allowed critical impact: permanent freezing of bridged funds.

## Likelihood Explanation

**Moderate.** No special privilege over the bridge contract is required. The token delivery step (`ft_transfer` / `mint`) can fail in several realistic ways:

1. **Token contract paused** — many NEP-141 tokens implement a pause mechanism. If the token contract is paused between the storage-check receipt and the `ft_transfer` receipt, delivery fails silently. The token contract owner is external to the bridge and can act at any time.
2. **Recipient unregisters storage** — the storage check and `ft_transfer` execute in separate receipts. A recipient can call `storage_unregister` in the window between the two receipts, causing `ft_transfer` to panic.
3. **Token contract bug or upgrade** — any panic in the token contract during `ft_transfer` or `mint` triggers the same silent-success path.

Any inbound transfer to a NEAR recipient is affected. No bridge admin action is required to trigger the bug; the failure condition arises from normal token contract behavior.

## Recommendation

`fin_transfer_send_tokens_callback` must inspect the promise result for **all** token delivery paths, not only `ft_transfer_call`:

1. Extend `is_refund_required` (or add a separate check) to call `env::promise_result_checked(0, …)` when `is_ft_transfer_call = false`, treating a failed promise as requiring a refund.
2. On failure, call `remove_fin_transfer`, call `revert_lock_actions` to restore `locked_tokens` accounting, and emit `FailedFinTransferEvent` — mirroring the existing refund path — so the transfer can be retried.
3. Alternatively, move `add_fin_transfer` into `fin_transfer_send_tokens_callback` so it is only committed after confirmed delivery. [11](#0-10) 

## Proof of Concept

1. A user bridges a native NEAR token from Ethereum back to NEAR (inbound transfer).
2. The token contract owner pauses the token contract (or the recipient calls `storage_unregister` on the token contract).
3. A relayer calls `fin_transfer` with a valid proof.
4. `fin_transfer_callback` → `process_fin_transfer_to_near`:
   - `add_fin_transfer` commits the transfer ID to `finalised_transfers`. [1](#0-0) 
   - `unlock_tokens_if_needed` decreases `locked_tokens` accounting. [2](#0-1) 
   - `send_tokens` dispatches `ft_transfer` on the paused token contract. [12](#0-11) 
5. `ft_transfer` panics (contract is paused). The promise result is `Failed`.
6. `fin_transfer_send_tokens_callback` is called with `is_ft_transfer_call = false`.
7. `is_refund_required(false)` returns `false` without reading the promise result. [5](#0-4) 
8. The else-branch executes: fee is minted to the relayer, `FinTransferEvent` is emitted. [13](#0-12) 
9. The transfer ID is permanently in `finalised_transfers`. Any retry panics with `TransferAlreadyFinalised`. [7](#0-6) 
10. The user's tokens are frozen in the bridge contract with no on-chain recovery mechanism.

**Test plan:** Write a NEAR sandbox integration test that (a) registers a token, (b) submits a valid `fin_transfer` proof, (c) has the mock token contract return a panic on `ft_transfer`, and (d) asserts that `is_transfer_finalised` returns `true` while the recipient balance remains zero and `locked_tokens` is incorrectly decremented. This directly demonstrates the silent-success path and the permanent freeze. [14](#0-13)
