### Title
Peras Weight Snapshot Ignored in ChainSync Client Forecast-Horizon Disconnection Check — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

### Summary

When Peras is enabled, the `checkPreferTheirsOverOurs` function in the ChainSync client hardcodes `emptyPerasWeightSnapshot` instead of using the live `PerasWeightSnapshot` when deciding whether to disconnect from a peer whose header is beyond the forecast horizon. This is the direct analog of the `riskPoolBalance is not used` pattern: the Peras weight state is fully accumulated and used everywhere else in the system, but is silently zeroed out in this one critical chain-preference gate. The result is that the disconnection decision is made purely on block count, ignoring Peras certificate boosts, which can cause a node to disconnect from a peer offering the canonically heavier chain or to remain connected to a peer offering a lighter chain.

### Finding Description

The `PerasWeightSnapshot` is properly accumulated in `PerasCertDB`, propagated into `ChainSel`, and used in `chainSelectionForBlock`, `constructPreferableCandidates`, and `preferAnchoredCandidate` throughout the production chain-selection path. However, in `checkPreferTheirsOverOurs` — the gate that decides whether to throw `CandidateTooSparse` and disconnect from a peer when a header is beyond the forecast horizon — the actual snapshot is replaced with `emptyPerasWeightSnapshot`:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← hardcoded empty; real weights ignored
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
```

`preferAnchoredCandidate` with `emptyPerasWeightSnapshot` falls into its `isEmptyPerasWeightSnapshot`-guarded branch and compares chains purely by block number (`selectView`/`BlockNo`), completely ignoring any Peras certificate boosts.

**Attack path — false-positive disconnection (chain-selection failure):**

1. Peras is enabled on the network; certificates have been issued boosting blocks on the canonical chain C₁.
2. C₁ is shorter in block count than the node's current chain C₀ but heavier in total Peras weight.
3. An honest peer P₁ advertises C₁. One of P₁'s headers falls beyond the node's forecast horizon (large slot gap), triggering `readLedgerState` → `checkPreferTheirsOverOurs`.
4. With `emptyPerasWeightSnapshot`, `preferAnchoredCandidate ourFrag theirFrag` compares by block number only. Since C₁ has fewer blocks than C₀, `ShouldNotSwitch` is returned.
5. The node throws `CandidateTooSparse` and disconnects from P₁.
6. The node never receives the blocks of C₁ and remains on C₀, the lighter non-canonical chain.

**Attack path — false-negative connection (adversary keeps node on lighter chain):**

1. Peras is enabled; the canonical chain C₁ has Peras boosts.
2. An adversary A serves chain C₂: more blocks than C₁ but no Peras boosts, with a large slot gap.
3. When the node's forecast horizon is exceeded for C₂, `checkPreferTheirsOverOurs` compares by block count only. C₂ has more blocks → `ShouldSwitch` → node stays connected to A.
4. Simultaneously, the honest peer offering C₁ (fewer blocks, heavier) is disconnected via the false-positive path above.
5. The node is left connected only to A's lighter chain.

### Impact Explanation

When Peras is active, the `checkPreferTheirsOverOurs` gate makes incorrect peer-retention decisions. In the false-positive case, the node disconnects from peers offering the canonically heavier chain, causing it to prefer a less-secure, lighter chain — a direct chain-selection failure. This matches the **High** impact category: "Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions." The adversary requires no privileged keys; serving a chain with more blocks but fewer Peras boosts (or simply being an honest peer whose canonical chain has fewer blocks) is sufficient to trigger the bug.

### Likelihood Explanation

Peras is currently disabled by default (CHANGELOG confirms "if Peras is disabled (which is the default), there is no observable difference"), so the bug is dormant on mainnet today. Once Peras is enabled, any network epoch in which certificates have been issued and a peer's header crosses the forecast horizon will trigger the vulnerable path. The TODO comment and linked issue (`tweag/cardano-peras#64`) confirm the developers are aware the check is incomplete but have not yet resolved it.

### Recommendation

Pass the live `PerasWeightSnapshot` (obtained from `getCandidateOverSelection` / `getPerasWeightSnapshot`) into `checkPreferTheirsOverOurs` and supply it to `preferAnchoredCandidate` instead of `emptyPerasWeightSnapshot`. This mirrors exactly how the snapshot is already threaded into `chainSelectionForBlock` and `constructPreferableCandidates`. Alternatively, if the TODO intent ("remove this entire check") is pursued, the check should be removed before Peras is enabled in production, not after.
