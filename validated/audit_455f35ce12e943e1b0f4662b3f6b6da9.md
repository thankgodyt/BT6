Audit Report

## Title
NEAR-native tokens permanently frozen when transferred to chain without registered token address — (File: `near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer_internal` locks NEAR-native tokens and returns zero refund without verifying that the token has a registered foreign-chain address. The subsequent `sign_transfer` call unconditionally panics when `get_token_address` returns `None` for the unregistered token. No cancel or refund path exists, leaving the tokens permanently frozen in the bridge contract.

## Finding Description
**Root cause:** `init_transfer` (L523–534) only checks that the recipient chain is not NEAR. It does not verify that the token has a registered address on the destination chain via `token_id_to_address`.

`init_transfer_internal` (L1829–1865) then:
1. Stores the transfer in `pending_transfers` via `add_transfer_message`.
2. Calls `burn_tokens_if_needed` — a no-op for non-deployed NEAR-native tokens.
3. Calls `lock_tokens_if_needed` — updates accounting, locking the tokens.
4. Emits `InitTransferEvent`.
5. Returns `U128(0)` — zero tokens refunded to the caller.

When a relayer later calls `sign_transfer`, the code at L462–469 calls `get_token_address(destination_chain, token_id)`, which performs a plain lookup in `token_id_to_address` (L1360–1366). For a NEAR-native token never deployed or bound on the destination chain, this returns `None`, triggering `env::panic_str(BridgeError::FailedToGetTokenAddress)`. No MPC signature is produced, `finTransfer` on EVM is never called, and no recovery path exists — `grep` confirms zero occurrences of `cancel_transfer` or `refund_transfer` in `lib.rs`.

## Impact Explanation
Any user who initiates `ft_transfer_call` for a NEAR-native token targeting a foreign chain where that token is not yet registered will have their entire transferred amount permanently frozen inside the bridge contract. This directly matches the Critical impact class: **permanent freezing of bridged funds**.

## Likelihood Explanation
The path is reachable by any unprivileged token holder with no special roles. NEAR has many native tokens (liquid-staking tokens, DeFi tokens) that may not yet be deployed on every supported EVM chain. A user who bridges before the corresponding `deploy_token`/`bind_token` step completes triggers this path. The bridge UI/SDK does not prevent specifying an EVM recipient for an unregistered token.

## Recommendation
Add a registration check inside `init_transfer` (or `init_transfer_internal`) before locking tokens:

```rust
require!(
    self.get_token_address(
        init_transfer_msg.get_destination_chain(),
        token_id.clone(),
    ).is_some(),
    "Token not registered on destination chain"
);
```

Alternatively, implement a user-callable `cancel_transfer` function that returns locked tokens when no MPC signature has yet been produced for a pending transfer.

## Proof of Concept
1. `token.near` is a NEAR-native token with no entry in `token_id_to_address` for `(ChainKind::Eth, "token.near")`.
2. User calls `ft_transfer_call` on `token.near`, transferring 1000 tokens to the bridge with `msg = {"InitTransfer": {"recipient": "eth:0xRecipient", "fee": "0", "native_token_fee": "0"}}`.
3. Bridge's `ft_on_transfer` → `init_transfer` (L523) → `init_transfer_internal` (L1829):
   - `burn_tokens_if_needed("token.near", 1000)` → no-op (not a deployed token).
   - `lock_tokens_if_needed(ChainKind::Eth, "token.near", 1000)` → accounting updated.
   - Transfer stored in `pending_transfers`; `InitTransferEvent` emitted.
   - Returns `U128(0)` → no refund to caller.
4. Relayer calls `sign_transfer(transfer_id, ...)`:
   - `get_token_address(ChainKind::Eth, "token.near")` (L1360–1366) → `None`.
   - `unwrap_or_else` at L467–469 → `env::panic_str("ERR_FAILED_TO_GET_TOKEN_ADDRESS")`.
5. No MPC signature produced; `finTransfer` on EVM never called.
6. 1000 `token.near` tokens are permanently locked in the bridge contract with no recovery path. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
