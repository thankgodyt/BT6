### Title
Peras Certificate Validation Bypass: `validatePerasCert` Unconditionally Accepts All Peer-Supplied Certificates — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` method unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or committee-membership checks. The production NTN diffusion handler wires this validator directly into the Peras certificate inbound path, meaning any unprivileged peer can inject arbitrary `PerasCert` objects that are accepted as `ValidatedPerasCert` and forwarded to chain selection, where they boost the weight of attacker-chosen blocks.

---

### Finding Description

**Root cause — unconditional acceptance in `validatePerasCert`**

The `BlockSupportsPeras` typeclass provides a universal default instance for every `StandardHash blk`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature is verified, no committee membership is checked, no round-number bounds are enforced, and no boosted-block existence is confirmed. Every certificate, regardless of origin or content, is wrapped in `ValidatedPerasCert` and returned as `Right`.

**Attacker-controlled entry path — production NTN handler**

The production node-to-node handler in `NodeToNode.hs` wires up Peras certificate ingestion from every connected peer:

```haskell
, hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      version
      controlMessageSTM
``` [2](#0-1) 

`makePerasCertPoolWriterFromChainDB` calls `validatePerasCert` on each inbound certificate before forwarding it to `ChainDB.addPerasCertAsync`. Because `validatePerasCert` always returns `Right`, every certificate a peer sends passes validation and is enqueued for chain selection processing.

**Chain selection consequence**

`addPerasCertAsync` enqueues the certificate for `chainSelSync`, which calls `chainSelAddPerasCert`. That function adds the certificate to `PerasCertDB` and, if the boosted block is on a candidate fragment that is now heavier than the current selection, triggers a chain switch: [3](#0-2) 

A `ValidatedPerasCert` carries a `vpcCertBoost` weight equal to `perasWeight params`. An attacker who injects a certificate pointing at a block on a weaker fork can make that fork appear heavier than the honest chain, causing the node to roll back and switch to the attacker's preferred fork.

**Contrast with the vote path (which is correctly broken)**

The analogous vote handler explicitly acknowledges that it uses an empty stake distribution and that this causes all votes to be rejected:

```haskell
-- Note that the empty stake distribution will cause all votes to
-- be considered invalid.
(pure (PerasVoteStakeDistr mempty))
``` [4](#0-3) 

The certificate path has no equivalent guard: `validatePerasCert` accepts everything.

---

### Impact Explanation

An unprivileged peer can send a crafted `PerasCert` that names any block as the boosted block. The certificate is accepted without any cryptographic check, stored in `PerasCertDB`, and used to increase the Peras weight of the named block in chain selection. If the boosted block is on a fork, the node may switch away from the canonical chain. This is a bypass of Peras certificate verification that enables unauthorized certificate acceptance and chain-selection manipulation — matching the "Critical: bypass of Peras voting or certificate checks" impact category.

---

### Likelihood Explanation

The Peras diffusion protocol is wired into the production NTN handler and is reachable by any peer that negotiates a protocol version that enables it. The bypass is unconditional: there is no code path in `validatePerasCert` that can reject a certificate. The only prerequisite is that the Peras cert diffusion mini-protocol is active for the negotiated version. The code is explicitly marked as a placeholder (`TODO: degenerate instance for all blks to get things to compile`), meaning the missing validation is a known gap, not an intentional design choice. [5](#0-4) 

---

### Recommendation

Replace the unconditional `Right` in `validatePerasCert` with real validation before the Peras cert diffusion protocol is enabled in any production version negotiation. At minimum, the implementation must:

1. Verify the certificate's cryptographic signature against the committee's public keys.
2. Confirm the claimed boosted block exists and is within the valid Peras round window.
3. Confirm the certificate was produced by a quorum of eligible committee members for the stated round.

Until real validation is in place, the `hPerasCertDiffusionClient` handler should be gated behind a feature flag that is disabled in all released protocol versions, preventing peers from reaching the inbound path entirely.

---

### Proof of Concept

A peer connecting to a node with Peras cert diffusion enabled sends a single `PerasCert` message:

```
PerasCert { pcCertRound = <any round>, pcCertBoostedBlock = <point of a minority-fork block> }
```

The inbound handler calls `validatePerasCert mkPerasParams cert`, which returns:

```haskell
Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams }
``` [6](#0-5) 

The validated certificate is forwarded to `ChainDB.addPerasCertAsync`. Chain selection runs, finds the minority-fork block now has a Peras boost, and — if the boosted block's fragment is otherwise competitive — switches the node's selection to the attacker's fork. [7](#0-6)
