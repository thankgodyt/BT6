### Title
Unauthenticated `request_refund` Allows Attacker to Redirect Victim's BTC Refund to Attacker-Controlled Address - (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary

`request_refund` does not verify that the caller (`env::predecessor_account_id()`) is the owner of the deposit (i.e., `deposit_msg.recipient_id`). When a user deposited BTC with `deposit_msg.refund_address = None`, any attacker can call `request_refund` with the victim's public `deposit_msg` and supply their own BTC address as `refund_address`. After `unsafe_refund_timelock_sec` elapses without DAO/Operator intervention, the attacker calls `execute_refund` and the victim's BTC is sent to the attacker's address.

### Finding Description

`request_refund` is a public, permissionless entry point: [1](#0-0) 

It delegates to `internal_request_refund`, which contains the only check on `refund_address`: [2](#0-1) 

This check only enforces consistency when `deposit_msg.refund_address` is already set. When it is `None` — which is the common case for users who did not pre-authorize a refund address — the caller-supplied `refund_address` is accepted verbatim with **no verification that the caller is `deposit_msg.recipient_id`**.

The `DepositMsg` struct shows that `refund_address` is an optional field: [3](#0-2) 

All inputs needed to call `request_refund` on behalf of a victim are fully public: the `deposit_msg` is derived from the BTC deposit address (itself public), and `tx_bytes` plus the inclusion proof are on the Bitcoin blockchain.

The stored `refund_address` is later used unconditionally in `internal_execute_refund` to build the refund output: [4](#0-3) 

The only mitigation is `unsafe_refund_timelock_sec`, a longer timelock applied when `deposit_msg.refund_address` is `None`: [5](#0-4) 

This is a governance/operational control, not a technical access control. It requires the DAO/Operator to actively monitor every incoming refund request, identify that the supplied `refund_address` does not belong to `deposit_msg.recipient_id` (an off-chain, non-trivial determination), and reject it before the timelock expires.

### Impact Explanation

An attacker can permanently redirect a victim's deposited BTC — which was never minted as nBTC — to an attacker-controlled Bitcoin address. The victim loses their entire deposit with no on-chain recourse once `execute_refund` is finalized. This constitutes direct theft of user funds.

### Likelihood Explanation

- All required inputs (`deposit_msg`, `tx_bytes`, inclusion proof) are publicly observable on-chain.
- The attacker only needs to front-run the victim's own `request_refund` call, or target deposits where the victim has not yet submitted a refund request.
- The `unsafe_refund_timelock_sec` window requires continuous DAO/Operator vigilance and off-chain identity verification to catch; any lapse allows the attack to complete.
- No special privileges, leaked keys, or third-party compromise are required.

### Recommendation

Add an ownership check at the start of `request_refund` (or inside `internal_request_refund`) that verifies the caller is the depositor:

```rust
pub fn request_refund(
    &mut self,
    deposit_msg: DepositMsg,
    refund_address: String,
    ...
) -> Promise {
    let caller = env::predecessor_account_id();
    require!(
        caller == deposit_msg.recipient_id,
        "request_refund: caller must be the deposit recipient"
    );
    ...
}
```

Alternatively, if permissionless refund submission is intentional (e.g., for relayer support), enforce that `deposit_msg.refund_address` must be `Some` when the caller is not the `recipient_id`, so the destination address is always pre-authorized by the depositor.

### Proof of Concept

1. Alice deposits 1 BTC to the bridge with `deposit_msg = { recipient_id: "alice.near", refund_address: None }`. The deposit is never finalized (e.g., relayer is down).
2. Attacker Bob observes Alice's BTC transaction on-chain and reconstructs her `deposit_msg` (the deposit address is derived deterministically from it).
3. Bob calls `request_refund(deposit_msg=alice_msg, refund_address="attacker_btc_addr", tx_bytes=..., vout=0, proof=...)`. No ownership check exists; the call succeeds.
4. Because `deposit_msg.refund_address` is `None`, `resolve_execute_refund_timelock` applies `unsafe_refund_timelock_sec`.
5. After the timelock elapses without DAO/Operator rejection, Bob calls `execute_refund(utxo_storage_key=...)`.
6. `internal_execute_refund` builds a PSBT paying `refund_request.refund_address` (Bob's address) and submits it to MPC for signing.
7. Alice's 1 BTC is sent to Bob's Bitcoin address. Alice receives nothing. [6](#0-5) [7](#0-6) [8](#0-7)

    pub(crate) fn internal_request_refund(
        &self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<u128>,
    ) -> Promise {
        require!(
            env::attached_deposit() >= self.required_balance_for_request_refund(),
            "Insufficient deposit for storage"
        );
        require!(
            tx_bytes.0.len() <= MAX_REQUEST_REFUND_TX_BYTES,
            "tx_bytes too large for refund request"
        );
        if let Some(msg_refund_address) = &deposit_msg.refund_address {
            require!(
                msg_refund_address == &refund_address,
                "refund_address does not match deposit_msg.refund_address"
            );
        }

        let transaction =
            crate::WrappedTransaction::decode(&tx_bytes.0, &self.internal_config().chain)
                .expect("Deserialization tx_bytes failed");
        let tx_id = transaction.compute_txid().to_string();

        let config = self.internal_config();
        let deposit_amount = u128::from(transaction.output()[vout].value.to_sat());
        let confirmations = self.get_confirmations(config, deposit_amount);

        self.verify_transaction_inclusion_promise(
            config.btc_light_client_account_id.clone(),
            tx_id,
            proof.tx_block_blockhash,
            proof.tx_index,
            proof.merkle_proof,
            Some((proof.coinbase_tx_id, proof.coinbase_merkle_proof)),
            confirmations,
        )
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_REQUEST_REFUND_CALLBACK)
                .request_refund_callback(deposit_msg, refund_address, tx_bytes, vout, gas_fee),
        )
    }

    pub(crate) fn internal_execute_refund(
        &mut self,
        utxo_storage_key: String,
        timelock_sec: u64,
        _chain_specific_data: Option<ChainSpecificData>,
    ) -> PromiseOrValue<()> {
        let refund_request = self.load_refund_request_for_execute(&utxo_storage_key, timelock_sec);
        let RefundExecutionInputs {
            outpoint,
            deposit_output,
            refund_amount,
        } = self.refund_execution_inputs(&refund_request);
        let refund_output = self.build_refund_output(&refund_request.refund_address, refund_amount);

        let mut psbt = PsbtWrapper::new(vec![outpoint], vec![refund_output]);
        psbt.set_input_utxo(vec![deposit_output]);

        let caller = env::predecessor_account_id();
        self.finalize_refund_with_psbt(
            caller,
            refund_request,
            psbt,
            refund_amount,
            utxo_storage_key,
        );
        PromiseOrValue::Value(())
    }
