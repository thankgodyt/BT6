Audit Report

## Title
Mint Failure Silently Ignored in `fin_transfer_send_tokens_callback` Enables Permanent Transfer Finalization With No Token Minting — (File: `near/omni-bridge/src/lib.rs`)

## Summary

In `deploy_token_internal`, all token registration state and the `DeployTokenEvent` are written in the same receipt before the cross-contract deployer call completes. During the resulting async window, a relayer can submit a valid `fin_transfer` proof for the newly-registered token. Because `fin_transfer_send_tokens_callback` unconditionally skips the mint promise-result check when `is_ft_transfer_call = false`, a failed `mint` call against the not-yet-existing token contract is silently ignored, the transfer ID is permanently consumed in `finalised_transfers`, and no tokens are ever minted — resulting in permanent, irrecoverable loss of bridged funds.

## Finding Description

**Step 1 — State written before deployer completes.**
In `deploy_token_internal` (lines 2413–2453), `add_token`, `deployed_tokens.insert`, `deployed_tokens_v2.insert`, and `env::log_str(DeployTokenEvent)` all execute in the current receipt. Only after these writes does `ext_deployer::ext(deployer).deploy_token(...)` get dispatched as a cross-contract call (line 2446), with `deploy_token_by_deployer_callback` as its continuation. The cleanup in the callback (lines 1190–1195) only runs if the deployer call *fails*; it cannot undo a `fin_transfer` that already consumed the transfer ID.

**Step 2 — `fin_transfer_callback` succeeds during the async window.**
`fin_transfer_callback` (line 715–718) checks `token_decimals.get(&init_transfer.token)` — this lookup succeeds because the state was already written in Step 1. `process_fin_transfer_to_near` then calls `add_fin_transfer` (line 1875), which permanently inserts the transfer ID into `finalised_transfers` with no possibility of removal on a downstream failure.

**Step 3 — `send_tokens` dispatches `mint` against a non-existent account.**
`send_tokens` (line 2094–2101) calls `ext_token::ext(token).mint(recipient, amount, None)` with no prior existence check. If the token contract account does not yet exist on NEAR, this cross-contract call fails.

**Step 4 — `fin_transfer_send_tokens_callback` ignores the mint failure.**
The callback is wired as `.then(fin_transfer_send_tokens_callback(..., !msg.is_empty(), ...))` (line 1973). For a plain transfer (no `msg`), `is_ft_transfer_call = false`. Inside the callback, `is_refund_required(false)` (lines 1800–1803) returns `false` unconditionally — `env::promise_result_checked` is never called, so the failed mint promise result is completely ignored. The callback falls into the `else` branch (line 1719), emits `FinTransferEvent`, and the transfer is permanently finalized with no tokens minted.

**Why existing guards are insufficient.**
The `deploy_token_by_deployer_callback` cleanup (lines 1190–1195) can remove the token registration if the deployer call fails, but it cannot remove a transfer ID already inserted into `finalised_transfers` by a concurrent `fin_transfer`. The `is_refund_required` function was designed only to handle `ft_transfer_call` return-value semantics; it has no branch to handle a failed `mint` promise.

## Impact Explanation

This matches the Critical allowed impact: **permanent freezing/loss of bridged funds**. The user's tokens are locked or burned on the source chain (EVM, Solana, etc.), the `fin_transfer` proof is consumed, the transfer ID is permanently recorded in `finalised_transfers` (preventing any retry), and no tokens are ever minted on NEAR. The loss is irrecoverable by design — `finalised_transfers` is append-only for valid transfers.

## Likelihood Explanation

The `DeployTokenEvent` is emitted on-chain in the same receipt as the state writes, before the deployer receipt executes. Any relayer monitoring NEAR logs will observe this event and may immediately submit a `fin_transfer` proof for a pending cross-chain transfer of the newly-registered token. This is a realistic scenario during first-time bridging of a new token: a user initiates a transfer on the source chain, the DAO deploys the token on NEAR, and a relayer (honest or malicious) submits the `fin_transfer` proof during the multi-block async window. No special privileges are required — `fin_transfer` is a public entry point callable by any account with a valid proof.

## Recommendation

1. **Check the mint promise result unconditionally.** In `fin_transfer_send_tokens_callback`, call `env::promise_result_checked(0, usize::MAX)` regardless of `is_ft_transfer_call`. If the result is an error, treat it as a refund-required case (revert the finalization, remove the transfer ID, emit `FailedFinTransferEvent`).

2. **Alternatively, defer state writes until after the deployer callback succeeds.** Move `add_token`, `deployed_tokens.insert`, `deployed_tokens_v2.insert`, and the `DeployTokenEvent` emission into `deploy_token_by_deployer_callback`'s success branch (line 1183–1188), so the token is not visible to `fin_transfer` until the contract actually exists on NEAR.

3. **Add a "deployment pending" guard.** Introduce a separate set (e.g., `pending_deployment_tokens`) that is checked in `fin_transfer_callback` to reject finalization attempts for tokens whose deployer call has not yet completed.

## Proof of Concept

1. Deploy the bridge contract on a local NEAR testnet.
2. Call `deploy_token` for a new EVM token (e.g., `0xTOKEN` on chain `Eth`). Observe that `DeployTokenEvent` is emitted and `token_decimals` is populated in the same block, while the deployer receipt is pending.
3. Before the deployer receipt executes (i.e., in the same or next block), submit `fin_transfer` with a valid prover proof for an `InitTransfer` of `0xTOKEN` with a NEAR recipient and no `msg`.
4. Observe that `fin_transfer_callback` succeeds (decimals lookup passes), `add_fin_transfer` inserts the transfer ID, `send_tokens` dispatches `mint` to the non-existent token account, and `fin_transfer_send_tokens_callback` emits `FinTransferEvent` despite the mint failure.
5. Confirm: `finalised_transfers` contains the transfer ID, no tokens exist in the recipient's balance, and re-submitting the same proof is rejected with `TransferAlreadyFinalised`.
