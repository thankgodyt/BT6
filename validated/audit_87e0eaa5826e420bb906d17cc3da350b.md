### Title
Peras Vote and Certificate Validation Bypass via Missing Signature Verification — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance used for all blocks implements `validatePerasVote` and `validatePerasCert` without performing any cryptographic signature verification. `validatePerasVote` only checks whether the claimed voter ID (`pvVoteVoterId`) exists in the stake distribution, while `validatePerasCert` unconditionally returns `Right`. An unprivileged peer can therefore forge votes attributed to any registered stake pool and forge arbitrary certificates, causing unauthorized Peras certificate acceptance and chain-weight manipulation.

---

### Finding Description

The external report describes a **state/identity mismatch**: a function reads accumulated state from entity A (the `user` parameter) but debits entity B (`msg.sender`), allowing an attacker to impersonate A's accumulated value while only consuming B's cheap fresh state.

The structural analog in this codebase is in the Peras vote and certificate validation path. The default `BlockSupportsPeras` instance, which is the only instance compiled for all block types, implements:

**`validatePerasVote`** — reads the stake weight keyed by the vote's `pvVoteVoterId` field (attacker-controlled), but never verifies the cryptographic signature that would prove the vote was actually produced by the private key of that pool:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
```

The `pvVoteVoterId` field is set by the sender of the vote message. The function looks up the stake for that ID and stamps the vote as valid with that stake weight — without verifying any signature. This is the direct analog of reading `user`'s `ethBacked`/`cumulativeRate` while debiting `msg.sender`: the attacker supplies a victim pool's ID to borrow its stake weight, while the actual signing key is never checked.

**`validatePerasCert`** — unconditionally accepts every certificate:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
```

Both functions are wired into the live object-diffusion inbound path. `processVotes` in `PerasVote.hs` calls `validatePerasVote mkPerasParams sd vote` for every vote received from a peer, and `processCerts` in `PerasCert.hs` calls `validatePerasCert mkPerasParams` for every certificate received from a peer. Validated votes are forwarded to `ChainDB.addPerasVoteWithAsyncCertHandling`, and validated certificates are forwarded to `ChainDB.addPerasCertAsync`, both of which affect chain selection weight.

---

### Impact Explanation

Peras certificates boost the chain-selection weight of the block they certify by `perasWeight params`. An attacker who can inject accepted certificates for an arbitrary block causes honest nodes to prefer that block over the canonical chain, constituting a **chain-selection safety failure**. Forged votes that reach quorum trigger certificate forging internally, compounding the effect. This matches:

> **Critical. Bypass of … Peras voting or certificate checks … that enables unauthorized … vote, or certificate acceptance.**
> **High. Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain.**

---

### Likelihood Explanation

The attack path is fully reachable by any unprivileged peer connected via the object-diffusion mini-protocol. No key material, stake majority, or operator access is required. The attacker only needs to know a registered pool's `KeyHash` (publicly visible on-chain) to forge a vote attributed to that pool with its full stake weight. The `processCerts` path requires no knowledge at all — any well-formed certificate struct is accepted.

---

### Recommendation

1. **`validatePerasVote`**: Verify the cryptographic signature on the vote using the public key associated with `pvVoteVoterId` before accepting the vote. The stake-distribution lookup must be a secondary check, not the sole check.
2. **`validatePerasCert`**: Implement full certificate verification — check that the certificate's aggregate signature (BLS or otherwise) is valid over the claimed set of votes, and that those votes themselves were validly signed.
3. Until real validation is implemented, the object-diffusion inbound handlers (`processVotes`, `processCerts`) should not forward unverified objects to `ChainDB`.

---

### Proof of Concept

1. Attacker connects to a target node via the Peras object-diffusion mini-protocol.
2. Attacker observes any registered pool's `KeyHash` from the public stake distribution.
3. Attacker constructs a `PerasVote` with `pvVoteVoterId = <victim pool KeyHash>`, `pvVoteRound = <current round>`, `pvVoteBlock = <attacker-chosen block point>`.
4. Attacker sends the vote to the target node. `processVotes` calls `validatePerasVote`, which finds the victim pool's stake in the distribution and returns `Right` — no signature check occurs.
5. The vote is added to `ChainDB` with the victim pool's full stake weight. If enough such forged votes are sent (one per registered pool), `updatePerasRoundVoteStates` reaches quorum and `forgePerasCert` is called, producing a certificate that boosts the attacker-chosen block's chain-selection weight.
6. Alternatively, the attacker skips step 3–5 entirely and sends a `PerasCert` directly. `processCerts` calls `validatePerasCert`, which returns `Right` unconditionally, and the certificate is added to `ChainDB` immediately. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5)

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
