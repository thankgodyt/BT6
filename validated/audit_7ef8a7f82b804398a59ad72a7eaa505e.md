### Title
Stub `validatePerasCert` Unconditionally Accepts Any Peer-Supplied Certificate, Enabling Arbitrary Peras Weight Injection into Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `validatePerasCert` implementation is a no-op stub that unconditionally returns `Right` for every inbound certificate, regardless of its cryptographic content or semantic validity. Because the resulting `ValidatedPerasCert` is immediately inserted into the `PerasCertDB` and its `vpcCertBoost` is folded into the live `PerasWeightSnapshot`, an unprivileged peer can inject an arbitrary weight boost onto any block of its choosing. Chain selection then uses that snapshot to compare candidate fragments, so the attacker can make a shorter adversarial chain appear heavier than the honest chain and force the node to switch to it.

---

### Finding Description

**Root cause — stub validator always succeeds**

The catch-all `BlockSupportsPeras` instance (the only instance in the codebase) implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params   -- always 15 on mainnet
      }
``` [1](#0-0) 

No signature check, no committee membership check, no round-number range check, no boosted-block existence check — every certificate is accepted.

**Inbound path — network-facing pool writer calls the stub**

Both the `PerasCertDB`-backed and `ChainDB`-backed pool writers pass this stub as the validator for all inbound certificates received over the object-diffusion mini-protocol:

```haskell

`processCerts` only deduplicates by round number; it performs no other gate: [4](#0-3) 

**Storage — `implAddCert` also carries a TODO for non-trivial validation** [5](#0-4) 

**Weight snapshot construction — every stored cert contributes its boost**

`implGetWeightSnapshot` folds all certificates in `pcdsCertsByTicket` into a `PerasWeightSnapshot` via `getPerasCertBoost`: [6](#0-5) 

**Chain selection — snapshot drives both fragment comparison and rollback window**

`chainSelectionForBlock` and `chainSelSync` both read the live snapshot and pass it to `constructPreferableCandidates` / `switchTo`: [7](#0-6) 

`preferAnchoredCandidate` uses `weightedSelectView` → `wsvTotalWeight` to compare fragments: [8](#0-7)

### Impact Explanation

An unprivileged peer can send one crafted `PerasCert` per Peras round (the deduplication key is `PerasRoundNo`). With `perasWeight = 15`, a single certificate makes the targeted chain appear 15 weight units heavier. Because `preferCandidate` switches whenever `wsvTotalWeight(candidate) > wsvTotalWeight(ours)`, an adversarial chain that is up to 15 blocks shorter than the honest chain will be preferred after one injected certificate. The attacker can also shrink the volatile suffix, causing honest blocks to be treated as immutable prematurely, which prevents future rollback to the correct chain. This is a **High** chain-selection bug: an unprivileged peer can make an honest node prefer a non-canonical chain beyond the intended security assumptions of Ouroboros Peras.

---

### Likelihood Explanation

The object-diffusion mini-protocol for Peras certificates is a standard peer-to-peer channel. Any connected peer can send a `PerasCert` message. The `PerasCert` wire type contains only `pcCertRound :: PerasRoundNo` and `pcCertBoostedBlock :: Point blk` — both are trivially forgeable with no key material. The only deduplication guard is round-number membership, which the attacker trivially bypasses by using a fresh round number. No stake, no key, no quorum is required. Likelihood is **High** for any deployment that enables the Peras object-diffusion subsystem.

---

### Recommendation

1. Implement real cryptographic and semantic validation inside `validatePerasCert` before the Peras certificate path is enabled in production. At minimum: verify the aggregate BLS signature against the committee's aggregate verification key, verify each voter's VRF eligibility proof, check that the total voting stake exceeds the quorum threshold, and verify that `pcCertBoostedBlock` refers to a block that is old enough (`perasBlockMinSlots`) and within the valid round window.
2. Until full validation is in place, gate the entire Peras certificate inbound path behind a feature flag so that nodes without a complete `BlockSupportsPeras` instance cannot receive or process certificates.
3. Add an explicit invariant check in `implAddCert` that rejects any certificate whose `vpcCertBoost` exceeds the protocol-configured `perasWeight`, to prevent boost inflation even after the stub is replaced.

### Proof of Concept

**Private-testnet sequence:**

1. Start a node with the Peras object-diffusion subsystem enabled (uses `makePerasCertPoolWriterFromChainDB`).
2. Connect a malicious peer.
3. The peer sends a `PerasCert` message with:
   - `pcCertRound = PerasRoundNo <fresh_round>` (any round not yet in the DB)
   - `pcCertBoostedBlock = blockPoint <tip_of_adversarial_fork>`
   - No valid signature or voter data required.
4. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right ValidatedPerasCert{vpcCertBoost = PerasWeight 15}` unconditionally. [11](#0-10) 
5. The certificate is stored in `PerasCertDB`; `implGetWeightSnapshot` now includes `(adversarial_tip_point, PerasWeight 15)`.
6. `chainSelSync` (triggered by `ChainSelAddPerasCert`) calls `chainSelectionForBlock` for the boosted block.
7. `constructPreferableCandidates` computes `wsvTotalWeight` for the adversarial fragment: `blockNo + 15`. If the adversarial chain is within 15 blocks of the honest tip, `preferCandidate` returns `ShouldSwitch`.
8. `switchTo` is called; the node adopts the adversarial chain. [12](#0-11)
