### Title
Attacker Can Front-Run `request_refund` to Redirect BTC Refund to Attacker-Controlled Address — (File: `contracts/satoshi-bridge/src/api/bridge.rs`, `contracts/satoshi-bridge/src/refund.rs`)

### Summary
When `deposit_msg.refund_address` is `None`, any NEAR account can call `request_refund` with an arbitrary `refund_address`. An attacker who observes a victim's pending `request_refund` transaction can race it with an identical call using the same UTXO proof but substituting their own BTC address. If the attacker's async callback lands first, the victim's callback is rejected, the victim's non-refundable NEAR deposit is lost, and the stored refund destination becomes the attacker's address — from which `execute_refund` (callable by anyone) will eventually pay out.

### Finding Description

`request_refund` is a public, payable function callable by any NEAR account: [1](#0-0) 

When `deposit_msg.refund_address` is `None`, the `refund_address` parameter is accepted verbatim from the caller with no ownership check: [2](#0-1) 

The function is asynchronous: it first calls the Light Client to verify the Bitcoin transaction, then stores the `RefundRequest` in a callback. The deduplication key (`utxo_storage_key = tx_id@vout`) is derived from the public Bitcoin transaction, so any observer can compute it: [3](#0-2) 

The callback itself acknowledges the race window with an explicit comment: [4](#0-3) 

The stored `refund_address` is later used verbatim by `execute_refund`, which has no caller restriction and pays out to whatever address is in the `RefundRequest`: [5](#0-4) 

`execute_refund` is callable by anyone after the timelock: [6](#0-5) 

**Attack steps:**
1. Victim deposits BTC with `DepositMsg { refund_address: None, recipient_id: victim_near_id }`.
2. Victim calls `request_refund(deposit_msg, victim_btc_addr, tx_bytes, vout, proof, None)`.
3. Attacker observes this NEAR transaction and immediately submits `request_refund(deposit_msg, attacker_btc_addr, tx_bytes, vout, proof, None)` — same UTXO proof, different `refund_address`.
4. Whichever callback executes first wins. If the attacker wins: `RefundRequest.refund_address = attacker_btc_addr` is stored; victim's callback panics with `"Refund request already exists for this UTXO"`.
5. Victim's non-refundable NEAR deposit is consumed (per the docs: "The deposit is NOT refunded").
6. After `unsafe_refund_timelock_sec`, anyone calls `execute_refund` and BTC is sent to the attacker's address.

### Impact Explanation
- **Certain**: Victim loses the non-refundable NEAR storage deposit on every failed `request_refund`.
- **Critical path**: BTC is redirected to the attacker's address. The DAO has `unsafe_refund_timelock_sec` to reject the request, but this requires continuous monitoring; if the DAO misses the window, the BTC is permanently lost to the victim. This constitutes significant theft of user funds.

### Likelihood Explanation
NEAR transactions are observable before finalization. The attacker only needs to submit a competing transaction in the same or next block. The attack is cheap (only the NEAR storage deposit is required), repeatable, and targets a common pattern: users who deposit BTC without pre-specifying a `refund_address` in `DepositMsg`. The code's own comment ("another request_refund could have landed between our check and callback") confirms the race is a known, unmitigated condition.

### Recommendation
1. **Bind `refund_address` to caller identity**: When `deposit_msg.refund_address` is `None`, require that the caller is the `recipient_id` from `deposit_msg`, or require a signed proof of BTC address ownership.
2. **Alternatively**: Require `deposit_msg.refund_address` to always be set (non-`None`) so the refund destination is committed at deposit time and cannot be overridden by a racing caller.
3. **Partial mitigation**: Make the NEAR storage deposit refundable when `request_refund_callback` fails due to a duplicate, so victims are not penalized for the race they did not cause.

### Proof of Concept

```
// Victim's deposit_msg has refund_address: None
let deposit_msg = DepositMsg { recipient_id: victim_near_id, refund_address: None, ... };

// Victim submits:
bridge.request_refund(deposit_msg, "victim_btc_addr", tx_bytes, vout, proof, None)
  // → async: verify_transaction_inclusion → request_refund_callback

// Attacker observes victim's tx and immediately submits:
bridge.request_refund(deposit_msg, "attacker_btc_addr", tx_bytes, vout, proof, None)
  // → async: verify_transaction_inclusion → request_refund_callback

// If attacker's callback lands first:
//   refund_requests["txid@0"] = RefundRequest { refund_address: "attacker_btc_addr", ... }
//   Victim's callback: panic!("Refund request already exists for this UTXO")
//   Victim loses NEAR deposit.

// After unsafe_refund_timelock_sec (if DAO does not reject):
bridge.execute_refund("txid@0", None)
  // → BTC sent to "attacker_btc_addr"
```

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
