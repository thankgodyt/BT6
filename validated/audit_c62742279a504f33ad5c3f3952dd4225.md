### Title
Peras Vote Validation Stub Accepts Unsigned Votes, Enabling Unauthorized Certificate Forging and Chain Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasVote` method is a stub that performs no cryptographic verification whatsoever. Any unprivileged peer can send crafted `PerasVote` messages claiming to be any registered stake pool, bypassing the intended vote-eligibility check entirely. Because the vote diffusion pipeline (`processVotes`) feeds directly into the `PerasVoteDB` quorum accumulator, an attacker can accumulate enough fake votes to forge a `ValidatedPerasCert` for an attacker-chosen block, artificially boosting that block's chain weight and manipulating chain selection.

---

### Finding Description

The `BlockSupportsPeras` instance (the only production instance, used for all block types) implements `validatePerasVote` as a stub:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote
        { vpvVote = vote
        , vpvVoteStake = stake
        }
  | otherwise =
      Left PerasValidationErr
``` [1](#0-0) 

The `_params` argument is explicitly discarded. The only check performed is `lookupPerasVoteStake`, which is a plain `Map.lookup` on the public stake distribution:

```haskell
lookupPerasVoteStake vote distr =
  Map.lookup (pvVoteVoterId vote) (unPerasVoteStakeDistr distr)
``` [2](#0-1) 

No signature verification, no eligibility proof (VRF output), no round-number validity, and no block-point validity is checked. The `PerasVote` data type carries a `pvVoteVoterId` field that is entirely attacker-controlled over the wire:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound  :: PerasRoundNo
  , pvVoteBlock  :: Point blk
  , pvVoteVoterId :: PerasVoterId
  }
``` [3](#0-2) 

The network-facing entry point `processVotes` calls this stub for every inbound vote from a peer, then unconditionally adds all passing votes to the `PerasVoteDB`:

```haskell
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb =
          filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    ([], validatedVotes) ->
      mapM_ (addVote . WithArrivalTime now) validatedVotes
    (errs, _) ->
      throw (PerasVoteValidationError errs)
``` [4](#0-3)

Once votes are in the `PerasVoteDB`, `updateTargetVoteTally` accumulates their stake. When the total crosses the quorum threshold, `updateCandidateVoteState` calls `forgePerasCert` — also a stub that unconditionally returns a certificate — producing a `ValidatedPerasCert` that boosts the attacker's chosen block in chain selection:

```haskell
updateCandidateVoteState cfg vote oldState =
  let newVoteTally = updateTargetVoteTally vote (ptvsVoteTally oldState)
      voteList = forgetArrivalTime <$> Map.elems (ptvtVotes newVoteTally)
   in case votesReachQuorum cfg voteList of
        Just votesWithQuorum -> do
          cert <- forgePerasCert cfg votesWithQuorum
          pure $ BecameWinner (PerasTargetVoteWinner newVoteTally cert)
        Nothing ->
          pure $ RemainedCandidate (PerasTargetVoteCandidate newVoteTally)
``` [6](#0-5) 

The analog to the external report is exact: just as `MAX_ASSIGNER_CREDITS` and `MAX_CREDITS_ASSIGNED` were bypassed by calling functions repeatedly without checking the accumulated balance, here the per-vote limit (cryptographic eligibility) is bypassed by sending votes repeatedly with different registered voter IDs — the check never verifies the actual credential, only that the ID exists in the public distribution.

---

### Impact Explanation

An unprivileged peer can forge a Peras certificate for any block of its choosing by sending crafted votes that impersonate registered stake pools. The forged certificate is stored in the `PerasCertDB` and used by chain selection to boost the attacker's target block with `PerasWeight`. This lets the attacker make an honest node prefer a non-canonical chain, constituting a chain-selection safety failure reachable without any key compromise.

---

### Likelihood Explanation

High. The registered stake pool IDs (`PerasVoterId = KeyHash StakePool`) are public ledger data. The attacker needs only to enumerate them and craft `PerasVote` messages with the desired `pvVoteVoterId`, `pvVoteRound`, and `pvVoteBlock`. The object diffusion miniprotocol is the standard peer-to-peer channel, reachable by any connected peer. No privileged access, leaked keys, or stake majority is required.

---

### Recommendation

Implement full cryptographic validation inside `validatePerasVote` before this code reaches production:

1. Verify the vote's BLS signature against the voter's registered verification key (as already defined in `CryptoSupportsVoteSigning.verifyVoteSignature`).
2. For non-persistent committee members, verify the VRF eligibility proof against the epoch nonce and election ID.
3. Validate that `pvVoteRound` corresponds to the current or recent Peras round.
4. Validate that `pvVoteBlock` refers to a known block within the valid voting window.

The `WFALS` committee scheme already implements the correct verification logic in `implVerifyVote`; `validatePerasVote` should delegate to an equivalent path rather than remaining a stub. [7](#0-6) 

---

### Proof of Concept

1. Query the ledger for any registered stake pool ID, e.g. `voterId = PerasVoterId <pool_key_hash>`.
2. Craft `N` distinct `PerasVote` messages, each with a different `voterId` drawn from the public stake distribution, all targeting the same `(pvVoteRound, pvVoteBlock)`.
3. Send the batch via the object diffusion miniprotocol to the target node.
4. `processVotes` calls `validatePerasVote mkPerasParams sd vote` for each; since `lookupPerasVoteStake` finds each `voterId` in the distribution, all votes return `Right ValidatedPerasVote{..., vpvVoteStake = <their stake>}`.
5. Each vote is added to the `PerasVoteDB` via `implAddVote`; `updateTargetVoteTally` accumulates their stake.
6. Once the accumulated stake crosses `perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin`, `votesReachQuorum` returns `Just`, `forgePerasCert` is called, and a `ValidatedPerasCert` boosting the attacker's `pvVoteBlock` is stored.
7. Chain selection now treats the attacker's block as having additional `PerasWeight`, causing the node to prefer it over the honest canonical chain.

  WFALSPersistentVote seatIndex electionId candidate sig
    | Just (_, voterPublicKey, voterStake, _) <-
        getCandidateIfSeatWithinBounds seatIndex (extWFAStakeDistr committee)
    , isPersistentMember seatIndex committee -> do
        let voterVerificationKey =

        pure $
          WFALSPersistentMember
            seatIndex

    | otherwise -> do
        Left (NotAPersistentMember seatIndex)
  WFALSNonPersistentVote seatIndex electionId message vrfOutput sig
    | Just (_, voterPublicKey, voterStake, _) <-
        getCandidateIfSeatWithinBounds seatIndex (extWFAStakeDistr committee)
    , not (isPersistentMember seatIndex committee) -> do
        let voterVoteVerificationKey =
              getVoteVerificationKey (Proxy @crypto) voterPublicKey

            electionId
            message
