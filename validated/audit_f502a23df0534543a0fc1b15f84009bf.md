### Title
Hardcoded Empty `PerasVoteStakeDistr` in Peras Vote Diffusion Inbound Handler Causes All Received Votes to Always Fail Validation - (`File: ouroboros-consensus-diffusion/src/ouroboros-consensus-diffusion/Ouroboros/Consensus/Network/NodeToNode.hs`)

---

### Summary

The production `mkHandlers` wiring for the Peras vote diffusion inbound miniprotocol passes a hardcoded empty stake distribution (`PerasVoteStakeDistr mempty`) to `makePerasVotePoolWriterFromChainDB`. Because `validatePerasVote` requires a voter's ID to be present in the stake distribution to accept a vote, every inbound Peras vote will always fail validation. `processVotes` then throws a `PerasVoteInboundException`, disconnecting the sending peer. The Peras vote diffusion miniprotocol is therefore completely non-functional: no Peras vote can ever be accepted, quorum can never be reached, and the Peras chain-selection weight boost is permanently disabled.

---

### Finding Description

In `mkHandlers` inside `NodeToNode.hs`, the `hPerasVoteDiffusionClient` field is wired as follows:

```haskell
, hPerasVoteDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      ( makePerasVotePoolWriterFromChainDB
          systemTime
          -- TODO: when actual plumbing for Peras is ready, we will have to
          -- extract the committee selection data from the chainDB to pass
          -- it here, instead of relying on an empty the stake distribution.
          --
          -- Note that the empty stake distribution will cause all votes to
          -- be considered invalid.
          (pure (PerasVoteStakeDistr mempty))
          getChainDB
      )
      ...
``` [1](#0-0) 

The `STM m PerasVoteStakeDistr` argument is consumed inside `makePerasVotePoolWriterFromChainDB` as the validation oracle:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [2](#0-1) 

`validatePerasVote` (the default instance for all `StandardHash blk`) performs:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [3](#0-2) 

`lookupPerasVoteStake` does `Map.lookup (pvVoteVoterId vote) (unPerasVoteStakeDistr distr)`. With `mempty` (an empty `Map`), this always returns `Nothing`, so `validatePerasVote` always returns `Left PerasValidationErr` for every vote regardless of its actual validity. [4](#0-3) 

`processVotes` then throws on any validation failure:

```haskell
(errs, _) -> throw (PerasVoteValidationError errs)
``` [5](#0-4) 

This exception propagates through the miniprotocol runner and disconnects the peer. The code comment in `NodeToNode.hs` explicitly acknowledges this: *"Note that the empty stake distribution will cause all votes to be considered invalid."*

---

### Impact Explanation

**Impact: High** — Chain-selection bug that permanently disables the Peras weight-boost mechanism, weakening chain selection security below the intended Peras security assumptions.

The Peras protocol is designed to provide additional chain-selection weight to blocks that have accumulated a quorum of votes, making it harder for an adversary to mount long-range or short-range fork attacks. Because every inbound Peras vote is unconditionally rejected:

1. No Peras vote received over the network can ever be stored in the `PerasVoteDB`.
2. Quorum can never be reached from network-received votes, so no Peras certificate can ever be generated via the diffusion path.
3. The `PerasWeightSnapshot` used in chain selection (`getPerasWeightSnapshot` in `ChainDB.API`) will never reflect any Peras weight boost from network votes.
4. Chain selection therefore operates without the Peras security layer, exactly as if Peras were not deployed — an adversary who knows this can exploit the weaker (non-Peras) chain-selection rules.

Any honest peer that participates in Peras and sends votes to this node will be disconnected, further degrading the network's ability to propagate votes and reach quorum. [6](#0-5) 

---

### Likelihood Explanation

**Likelihood: High** — The defect is unconditional. Every Peras vote received from every peer will always fail validation because the stake distribution is always empty. There is no configuration, runtime state, or code path that can make `PerasVoteStakeDistr mempty` non-empty. The code comment confirms the developers are aware of this behavior.

---

### Recommendation

Replace the hardcoded `(pure (PerasVoteStakeDistr mempty))` with an STM action that reads the actual stake distribution from the `ChainDB` (or the ledger state), analogous to how `makePerasCertPoolWriterFromChainDB` is wired with a real `ChainDB` reference. The TODO comment in the source already identifies the correct fix: extract the committee selection data from the `ChainDB` and pass it as the `STM m PerasVoteStakeDistr` argument. [7](#0-6) 

---

### Proof of Concept

**Attacker-controlled entry path:**

1. Any unprivileged peer connects to the node and negotiates the `PerasVoteDiffusion` miniprotocol (enabled in `NodeToNodeVersion`).
2. The peer sends one or more valid `PerasVote` objects via `objectDiffusionOutboundPeer`.
3. The node's `hPerasVoteDiffusionClient` handler receives the votes and calls `opwAddObjects` on the `ObjectPoolWriter` produced by `makePerasVotePoolWriterFromChainDB`.
4. `processVotes` calls `validatePerasVote mkPerasParams (PerasVoteStakeDistr mempty) vote` for each vote.
5. `lookupPerasVoteStake vote (PerasVoteStakeDistr mempty)` returns `Nothing` (empty map lookup always fails).
6. `validatePerasVote` returns `Left PerasValidationErr`.
7. `processVotes` throws `PerasVoteValidationError [PerasValidationErr, ...]`.
8. The miniprotocol runner catches the exception and disconnects the peer.
9. No vote is ever stored; no certificate is ever generated; the Peras weight boost is never applied to chain selection.

This sequence is deterministic and requires no special privileges, keys, or stake — any peer sending any Peras vote triggers it. [8](#0-7) [9](#0-8)

    { opwObjectId = getPerasVoteId
    , opwAddObjects = \votes ->
        processVotes
          systemTime
          (ChainDB.getPerasVoteIds chainDB)
          -- TODO: in the future we won't need just the stake distribution for
          -- validating votes, but also the whole committee selection context
          -- (containing vote weights of committee members = voters)
          (\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
          -- We do not want to block the writer thread on waiting for ChainSel
          -- side-effects to complete, so we use the async version of adding
          -- votes to the ChainDB and ignore the returned promise.
          -- The async action (if any) is still launched and executed behind the
          -- scenes even though we drop the promise.
          (void . ChainDB.addPerasVoteWithAsyncCertHandling chainDB)
          votes
    , opwHasObject = do
        voteIds <- ChainDB.getPerasVoteIds chainDB
        pure $ \voteId -> Set.member voteId voteIds
    }

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
