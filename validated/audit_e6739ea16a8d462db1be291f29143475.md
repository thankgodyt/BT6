### Title
`revalidateHeader`'s `LedgerView` Parameter Is Silently Ignored in Production Builds, Bypassing All Header Envelope Validation During Block Reapplication — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/HeaderValidation.hs`)

---

### Summary

`revalidateHeader` accepts a `LedgerView` parameter that is only consumed inside an `assertWithMsg` call. Because `assertWithMsg` is a compile-time no-op when the `asserts` Cabal flag is disabled — which is the **default** — the `LedgerView` and the entire `validateEnvelope` call it feeds are silently discarded in every production build. This is structurally identical to the external report's pattern: a parameter present in the function signature that is intended to provide a protection check but is never actually used in the execution path that matters.

---

### Finding Description

**`assertWithMsg` is a no-op by default.**

`Ouroboros/Consensus/Util/Assert.hs` defines:

```haskell
assertWithMsg :: HasCallStack => Either String () -> a -> a
#if ENABLE_ASSERTIONS
assertWithMsg (Left msg) _ = error msg
#endif
assertWithMsg _ a = a
```

`ENABLE_ASSERTIONS` is only set when the `asserts` Cabal flag is enabled. That flag defaults to `False`:

```
flag asserts
  description: Enable assertions
  manual: False
  default: False
```

So in every standard production build, `assertWithMsg _ a = a` — a complete no-op.

**`revalidateHeader` wraps its entire envelope check in that no-op.**

```haskell
revalidateHeader cfg ledgerView hdr st =
  assertWithMsg envelopeCheck $          -- ← no-op in production
    HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'
 where
  chainDepState' =
    reupdateChainDepState                -- skips VRF/KES by design
      (configConsensus cfg)
      (validateView (configBlock cfg) hdr)
      (blockSlot hdr)
      (tickedHeaderStateChainDep st)

  envelopeCheck =                        -- never evaluated in production
    runExcept $ withExcept show $
      validateEnvelope cfg ledgerView    -- ← ledgerView only used here
        (untickedHeaderStateTip st) hdr
```

The `ledgerView` parameter is referenced exclusively inside `envelopeCheck`, which is exclusively passed to `assertWithMsg`. In production, neither `envelopeCheck` nor `ledgerView` is ever evaluated. The function signature advertises a `LedgerView` input that provides no protection.

**`revalidateHeader` is called on every block reapplication.**

`reapplyBlockLedgerResult` in `Extended.hs` calls `revalidateHeader` unconditionally:

```haskell
reapplyBlockLedgerResult evs cfg blk TickedExtLedgerState{..} =
  (\l -> ExtLedgerState l hdr) <$> castLedgerResult ledgerResult
 where
  ...
  hdr = revalidateHeader
          (getExtLedgerCfg cfg) ledgerView (getHeader blk) tickedHeaderState
```

This path is exercised during:
- **ImmutableDB replay** at node initialisation (blocks streamed back from disk via `replayStartingWith`)
- **Chain selection fork switching** via `LedgerDB.validateFork` → `validateCandidate`

In both cases, in a production binary, `revalidateHeader` performs **zero validation**: no block-number check, no slot-number check, no prev-hash check, and no `additionalEnvelopeChecks` (which for Shelley calls `envelopeChecks` to verify max header size and other protocol-specific constraints; for Byron it checks EBB slot validity).

---

### Impact Explanation

An attacker who can supply a crafted on-disk DB or snapshot — the entry path explicitly listed as in-scope ("DB/snapshot input in a local reproduction") — can inject a block that would be rejected by `validateHeader` (wrong block number, wrong slot, wrong prev-hash, oversized header, invalid EBB placement, etc.). When the node replays that block via `reapplyBlockLedgerResult` → `revalidateHeader`, the block is accepted unconditionally in production. The node then builds its entire in-memory ledger state on top of an invalid block, producing a durably incorrect ledger state that diverges from the canonical chain.

This matches the allowed impact: **"ChainDB, ImmutableDB, VolatileDB, LedgerDB, snapshot, or LSM corruption/replay/rollback bug that causes durable use of the wrong ledger state."**

---

### Likelihood Explanation

**Medium.** The attacker must be able to write to the node's on-disk storage (ImmutableDB, VolatileDB, or a snapshot file). This is realistic in a local reproduction or private-testnet scenario. The vulnerability requires no cryptographic material, no stake, and no network access — only the ability to craft a binary-compatible block structure and place it in the database before the node starts. The `asserts` flag being off by default means every standard Cardano node binary is affected.

---

### Recommendation

**Short term:** Remove the `LedgerView` parameter from `revalidateHeader` entirely and document explicitly that envelope validation is skipped. This makes the contract honest and eliminates the misleading signature. Callers that currently pass a `LedgerView` will receive a compile error, prompting review.

**Long term:** Perform the basic structural envelope checks (block number, slot, prev-hash) unconditionally in `revalidateHeader` — they are cheap and do not require cryptographic work. Reserve the `assertWithMsg` pattern only for invariants that are genuinely too expensive to check in production. Protocol-specific `additionalEnvelopeChecks` (e.g., max header size) should also be enforced unconditionally during reapplication, not gated behind a disabled assertion.

---

### Proof of Concept

1. Compile `ouroboros-consensus` without the `asserts` flag (the default: `cabal build` with no extra flags).
2. Obtain or synthesise a valid ImmutableDB chunk file for a short chain.
3. Patch one block's header to carry an incorrect `blockNo` (e.g., increment it by 2 instead of 1), producing a block that `validateEnvelope` would reject with `UnexpectedBlockNo`.
4. Place the patched chunk file in the node's ImmutableDB directory.
5. Start the node. It calls `replayStartingWith` → `initReapplyBlock` → `reapplyBlockLedgerResult` → `revalidateHeader`.
6. Because `assertWithMsg` is a no-op, `envelopeCheck` is never run. The patched block is accepted; the node's `HeaderState` records the wrong `BlockNo` as the tip.
7. All subsequent chain-selection and header-validation decisions are made against this corrupted `HeaderState`, causing the node to diverge from honest peers.
