### Title
Off-by-one boundary error in `get_confirmations` causes deposits at exact tier thresholds to require excess confirmations - (File: contracts/satoshi-bridge/src/config.rs)

### Summary
`Config::get_confirmations` uses a strict `>` comparison when matching a deposit amount against the `confirmations_strategy` tier keys. Because the keys are documented as "Satoshi upper limit for amount checks", amounts that land exactly on a tier boundary are silently bumped into the next (higher-confirmation) tier, violating the intended policy and causing those deposits to fail light-client verification until additional Bitcoin blocks are mined.

### Finding Description
`confirmations_strategy` is a `HashMap<String, u8>` whose keys are satoshi upper-limit thresholds and whose values are the required confirmation counts for amounts within that tier.

`get_confirmations` iterates the sorted keys and returns the first tier whose key **strictly exceeds** the deposit amount:

```rust
// contracts/satoshi-bridge/src/config.rs  line 208-211
for key in &keys {
    if *key > satoshi_amount {          // ← strict >, not >=
        return u64::from(...);
    }
}
```

When `satoshi_amount == key` the condition is `false`, so the loop falls through to the next tier. For example, with tiers `{1_000_000 → 3 confs, 20_000_000 → 6 confs}`:

| Deposit amount | Expected confs | Actual confs |
|---|---|---|
| 999 999 sat | 3 | 3 ✓ |
| **1 000 000 sat** | **3** | **6 ✗** |
| 1 000 001 sat | 6 | 6 ✓ |

The same function is called for every deposit verification path (`internal_verify_deposit_entry`, `internal_safe_verify_deposit_entry`) and for refund verification (`internal_request_refund`, `internal_verify_refund_finalize`).

### Impact Explanation
A deposit whose satoshi value equals any intermediate tier boundary is submitted to the light client with a confirmation requirement one tier higher than the protocol intends. The light client call returns `false` (insufficient confirmations), the deposit callback reverts, and the UTXO cannot be minted until the relayer waits for the extra confirmations and retries. For the standard deposit path this routes the failure to lost-and-found rather than reverting, leaving the user's nBTC inaccessible until a manual `claim_lost_found` after the relayer eventually succeeds. This is a publicly reachable stuck-state fault on a production bridge path with no direct theft.

**Severity: Low** — matches "Publicly reachable invariant-violation, stuck-state, or panic-driven fault in production bridge/token paths without direct theft."

### Likelihood Explanation
Any unprivileged user can trigger this by sending a BTC deposit whose output value in satoshis equals exactly one of the configured tier thresholds. The thresholds are round numbers (e.g. 1 000 000 sat = 0.01 BTC), making accidental collisions plausible. No special role or leaked key is required.

### Recommendation
Change the comparison from strict `>` to `>=` so that an amount exactly equal to a tier's upper limit is handled by that tier, not the next one:

```rust
// contracts/satoshi-bridge/src/config.rs
for key in &keys {
    if *key >= satoshi_amount {   // was: *key > satoshi_amount
        return u64::from(*self.confirmations_strategy.get(&key.to_string()).unwrap());
    }
}
```

### Proof of Concept

Assume `confirmations_strategy = { "1000000": 3, "20000000": 6 }`.

1. User sends exactly 1 000 000 satoshis to their deposit address.
2. Relayer calls `verify_deposit_v2` once 3 blocks have confirmed the transaction.
3. Contract calls `get_confirmations(1_000_000)`:
   - key `1_000_000 > 1_000_000` → `false`, loop continues.
   - key `20_000_000 > 1_000_000` → `true`, returns **6**.
4. Light client is queried for 6 confirmations; only 3 exist → returns `false`.
5. `verify_deposit_callback` receives `false`, emits a lost-and-found event instead of minting nBTC.
6. User's nBTC is stuck in lost-and-found until the relayer retries after 3 more blocks.
