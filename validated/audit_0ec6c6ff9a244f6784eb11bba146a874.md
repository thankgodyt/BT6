### Title
Silent Token Lock When `withdraw_relayer` Is Unset in Legacy Withdrawal Path - (File: `contracts/nbtc/src/lib.rs`)

### Summary

The overridden `ft_transfer` in the nBTC contract contains a legacy withdrawal shortcut for Near Intents. When a user sends tokens to the nBTC contract itself with a `WITHDRAW_TO:` memo and `withdraw_relayer` is not configured, the code silently falls through and transfers the tokens to the nBTC contract itself — permanently locking them — instead of reverting with an error.

### Finding Description

In `contracts/nbtc/src/lib.rs`, the `ft_transfer` override implements a legacy bridging path: [1](#0-0) 

```rust
fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
    // Legacy bridging flow used by Near Intents
    if receiver_id == env::current_account_id()
        && memo.as_ref().is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
    {
        if let Some(withdraw_relayer) = Self::read_withdraw_relayer_address() {
            return self.token.ft_transfer(withdraw_relayer, amount, memo);
        }
    }

    self.token.ft_transfer(receiver_id, amount, memo);
}
```

The outer `if` matches when the user explicitly targets the nBTC contract with a `WITHDRAW_TO:` memo — a clear signal of withdrawal intent. The inner `if let Some(withdraw_relayer)` only redirects to the relayer when one is configured. When `withdraw_relayer` is `None` (not yet set, or cleared), the inner block is skipped and execution falls through to:

```rust
self.token.ft_transfer(receiver_id, amount, memo);
```

Here `receiver_id` is still `env::current_account_id()` — the nBTC contract itself. If the nBTC contract has a registered storage account (which any party can create via `storage_deposit`), the standard `ft_transfer` succeeds and the user's tokens are deposited into the nBTC contract's own balance. No error is raised. The user believes the withdrawal was initiated; in reality the tokens are locked with no recovery path.

The `withdraw_relayer` address is stored in raw contract storage and is optional by design: [2](#0-1) 

The `set_withdraw_relayer_address` function requires the controller role, meaning there are deployment windows (initial deploy, controller rotation, intentional clearing) where `withdraw_relayer` is `None`. [3](#0-2) 

### Impact Explanation

Any nBTC sent to the nBTC contract via the legacy `WITHDRAW_TO:` path while `withdraw_relayer` is unset is permanently locked. The nBTC contract exposes no function to recover tokens held in its own balance — `burn` only withdraws from `bridge_id`'s balance, and no sweep/rescue function exists. [4](#0-3) 

This constitutes a **permanent, irrecoverable loss of user funds** — matching the "Critical: significant loss or permanent locking of user funds" impact category.

### Likelihood Explanation

The precondition — `withdraw_relayer` being `None` — is realistic during:
- Initial contract deployment before the controller calls `set_withdraw_relayer_address`
- Any period after the controller intentionally clears or rotates the relayer address
- A misconfigured deployment

The storage-account precondition (nBTC contract registered with itself) can be satisfied by any unprivileged account calling `storage_deposit` with `account_id = nbtc_contract_id`. This is a one-time, permissionless setup step costing only the storage deposit. An attacker can front-run the deployment window to ensure the condition is met before users interact.

### Recommendation

When the outer condition matches (user explicitly targets the nBTC contract with a `WITHDRAW_TO:` memo) but `withdraw_relayer` is `None`, the function must revert instead of silently falling through:

```rust
fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
    if receiver_id == env::current_account_id()
        && memo.as_ref().is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
    {
        let withdraw_relayer = Self::read_withdraw_relayer_address()
            .expect("Legacy withdrawal relayer not configured; cannot process WITHDRAW_TO transfer");
        return self.token.ft_transfer(withdraw_relayer, amount, memo);
    }
    self.token.ft_transfer(receiver_id, amount, memo);
}
```

This mirrors the M-05 recommended fix: when the user's stated intent cannot be fulfilled, revert with an informative error rather than silently executing a different, harmful operation.

### Proof of Concept

1. Attacker calls `storage_deposit` on the nBTC contract with `account_id = nbtc_contract_id` to register the contract as a token holder (one-time, permissionless).
2. The controller has not yet called `set_withdraw_relayer_address` (or has cleared it), so `read_withdraw_relayer_address()` returns `None`.
3. User calls `ft_transfer(receiver_id = nbtc_contract_id, amount = X, memo = "WITHDRAW_TO:bc1q...")` with 1 yoctoNEAR attached, intending to use the legacy Near Intents withdrawal path.
4. The outer `if` condition is true; the inner `if let Some(...)` is false; execution falls through to `self.token.ft_transfer(nbtc_contract_id, X, memo)`.
5. The standard NEP-141 transfer succeeds (receiver is registered, sender ≠ receiver, 1 yocto attached). `X` nBTC is credited to the nBTC contract's own balance.
6. No error is emitted. The user's tokens are permanently locked; no bridge withdrawal is initiated. [1](#0-0) [5](#0-4)
