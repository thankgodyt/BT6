### Title
Degenerate `BlockSupportsPeras` Instance Bypasses All Peras Certificate and Vote Validation, Allowing Any Peer to Inject Unauthorized Certificates - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary
The `BlockSupportsPeras` typeclass has a degenerate catch-all instance that unconditionally returns `Right` (success) for both `validatePerasCert` and `validatePerasVote`, bypassing all cryptographic and semantic validation. Because the NTN Peras diffusion handlers call these validation functions directly when processing inbound certificates and votes from any peer, an unprivileged remote peer can inject arbitrary Peras certificates and votes that will always be accepted, be stored in the ChainDB, and trigger chain selection — potentially causing an honest node to switch to a non-canonical chain.

### Finding Description

**Root cause — always-passing validation in the degenerate instance:**

The file `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs` defines a catch-all instance for all `StandardHash blk` types:

```haskell

-- see https://github.com/tweag/cardano-peras/issues/120
instance StandardHash blk => BlockSupportsPeras blk where
  ...

  -- possible 'PerasValidationErr' variants
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }

  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  validatePerasVote ...  -- also returns Right unconditionally
``` [1](#0-0) 

Both `validatePerasCert` and `validatePerasVote` return `Right` unconditionally — no BLS signature check, no committee membership check, no VRF eligibility proof check, no stake-weight check.

**Exploit path — inbound cert processing:**

`makePerasVotePoolWriterFromChainDB` in `PerasCert.hs` wires the inbound NTN cert handler directly to `validatePerasCert mkPerasParams`:

```haskell
, opwAddObjects = \certs ->
    processCerts
      systemTime
      (ChainDB.getPerasCertIds chainDB)
      (validatePerasCert mkPerasParams)          -- always Right
      (void . ChainDB.addPerasCertAsync chainDB) -- triggers chain selection
      certs
``` [2](#0-1) 

`processCerts` validates each cert with the supplied function and, if all pass, calls `addCert` for each:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [3](#0-2) 

Because `validateCert` is `validatePerasCert mkPerasParams` which always returns `Right`, the `(errs, _)` branch is never taken. Every inbound certificate is accepted and forwarded to `ChainDB.addPerasCertAsync`, which triggers chain selection.

The same pattern applies to votes via `makePerasVotePoolWriterFromChainDB`:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [4](#0-3) 

**NTN handler wiring:**

The `hPerasCertDiffusionClient` and `hPerasVoteDiffusionClient` handlers in `NodeToNode.hs` are the NTN entry points reachable by any peer: [5](#0-4) 

Any peer that connects via the standard NTN protocol can send crafted `PerasCert` or `PerasVote` objects. These are deserialized, pass through `processCerts`/`processVotes`, and are unconditionally accepted.

### Impact Explanation

**Impact: Critical / High**

An unprivileged remote peer can:
1. Craft a `PerasCert` referencing any block point already known to the target node.
2. Send it via the `PerasCertDiffusion` NTN mini-protocol.
3. The cert passes `validatePerasCert` (always `Right`), is stored in the `PerasCertDB`, and `addPerasCertAsync` triggers chain selection with the injected boost weight.
4. If the boosted block is on a minority fork, the node may switch away from the canonical chain.

This is a bypass of Peras certificate/vote verification that enables unauthorized certificate and vote acceptance, directly matching the "Critical" allowed impact: *"Bypass of … Peras voting or certificate checks … that enables unauthorized … vote, or certificate acceptance."*

It also matches "High": *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

### Likelihood Explanation

**Likelihood: High**

- No privileged access, leaked keys, or stake majority required.
- Any peer that can establish a standard NTN connection can send crafted Peras objects.
- The degenerate instance is the only instance in scope for the block type used by the diffusion layer unless a more specific instance is defined for `CardanoBlock` — the TODO comment and the issue reference (`#120`) confirm no such override exists yet.
- The attack requires only constructing a valid CBOR-encoded `PerasCert` or `PerasVote` struct with an arbitrary `Point blk` — no cryptographic material needed.

### Recommendation

1. **Remove the degenerate catch-all instance** or make it an explicit compile error so that any block type used in production must provide a real implementation.
2. **Implement actual cryptographic validation** in `validatePerasCert` and `validatePerasVote` for the Cardano block type: verify the aggregate BLS signature, check committee membership via the VRF eligibility proof, and verify the seat index against the stake distribution before accepting any inbound certificate or vote.
3. Until real validation is in place, **gate the Peras diffusion mini-protocols** behind a feature flag that is disabled in production builds, preventing any peer from submitting Peras objects.

### Proof of Concept

1. Connect to a target node as a standard NTN peer (no special privileges needed).
2. Negotiate the NTN version that includes `PerasCertDiffusion`.
3. Construct a CBOR-encoded `PerasCert` with:
   - `pcCertRound` = any round number not yet in the DB
   - `pcCertBoostedBlock` = the `Point` of a known minority-fork block
4. Send it via the `PerasCertDiffusion` inbound channel.
5. **Expected (vulnerable) result**: `processCerts` calls `validatePerasCert mkPerasParams cert` → `Right ValidatedPerasCert{…}` → `addPerasCertAsync` is called → chain selection runs with the injected boost → node may switch to the minority fork.
6. **Expected (fixed) result**: `validatePerasCert` verifies the aggregate BLS signature and committee membership; the crafted cert (lacking a valid signature) is rejected and the peer is disconnected.

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
