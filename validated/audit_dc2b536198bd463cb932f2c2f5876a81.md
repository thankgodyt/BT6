### Title
Unconditional Peras Certificate Acceptance Bypasses All Validation, Enabling Unauthorized Chain-Weight Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` implementation is a stub that unconditionally accepts every inbound certificate without performing any cryptographic, structural, or committee-membership checks. This stub is wired directly into the production ObjectDiffusion mini-protocol path that processes certificates received from untrusted peers. An unprivileged peer can therefore send an arbitrary crafted `PerasCert` that will be accepted, stored in the `PerasCertDB`, and used to trigger chain selection with a full Peras weight boost for any block the attacker names — including blocks on adversarial forks.

---

### Finding Description

The `BlockSupportsPeras` type class declares `validatePerasCert` as the mandatory gate for all inbound Peras certificates:

```haskell
validatePerasCert ::
  PerasCfg blk ->
  PerasCert blk ->
  Either (PerasValidationErr blk) (ValidatedPerasCert blk)
```

The universal default instance (which covers all block types until era-specific instances are provided) implements this as an unconditional pass-through:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

No signature is verified, no committee membership is checked, no quorum threshold is enforced, and no round-number bounds are validated. The returned `ValidatedPerasCert` carries the full configured `perasWeight` boost regardless of the certificate's content.

This stub is bound directly into both production ObjectDiffusion pool writers:

- `makePerasCertPoolWriterFromCertDB` passes `(validatePerasCert mkPerasParams)` as the `validateCert` argument to `processCerts`.
- `makePerasCertPoolWriterFromChainDB` does the same, with an explicit `-- TODO replace when actual plumbing is in place` comment.

`processCerts` is the function that handles batches of certificates received from a remote peer over the ObjectDiffusion mini-protocol. It calls `validateCert` on each certificate not already in the database, and if all pass, adds them via `addCert`:

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _) ->
      throw (PerasCertValidationError errs)
```

Because `validateCert` is the stub, `partitionEithers` always produces an empty error list, and every peer-supplied certificate is added to the database.

When a certificate is added via `makePerasCertPoolWriterFromChainDB`, the `addCert` callback is `void . ChainDB.addPerasCertAsync chainDB`, which enqueues a `ChainSelAddPerasCert` event. `chainSelSync` in `ChainSel.hs` then processes it: it reads the `pcCertBoostedBlock` field from the attacker-controlled certificate, looks up that block in the `VolatileDB`, and calls `chainSelectionForBlock` for it — potentially switching the node's preferred chain to a fork containing the attacker-named block.

The `PerasCertDB.implAddCert` also carries its own TODO acknowledging missing validation logic, but the primary gap is upstream in `validatePerasCert`.

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` naming any block hash present in the target node's `VolatileDB` as `pcCertBoostedBlock`, with an arbitrary `pcCertRound`. The node will:

1. Accept the certificate unconditionally (no crypto check).
2. Store it in the `PerasCertDB` with the full configured `perasWeight` boost.
3. Trigger `chainSelectionForBlock` for the attacker-named block.
4. Compute `WeightedSelectView` for all candidate fragments using the now-inflated `PerasWeightSnapshot`, potentially switching to a fork that would otherwise be rejected.

This directly violates the Peras chain-selection invariant: only blocks certified by a legitimate quorum of committee members should receive a weight boost. An attacker with no stake and no committee membership can manufacture that boost for any block, making an honest node prefer a non-canonical chain. This is a **bypass of Peras certificate validation** enabling unauthorized chain-weight manipulation and a chain-selection safety failure.

---

### Likelihood Explanation

The Peras ObjectDiffusion mini-protocol is wired into the production `NodeKernel` and `ChainDB` code paths. Any peer that can establish an ObjectDiffusion connection (i.e., any node-to-node peer) can send a `PerasCert` message. The attack requires no special privileges, no stake, and no cryptographic material — only the ability to connect as a peer and send a well-formed CBOR-encoded `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock`. The TODO comments confirm this is a known gap, not an intentional design choice, and the code is in production (non-test) modules.

---

### Recommendation

Replace the stub `validatePerasCert` default implementation with a real implementation that:

1. Verifies the aggregate vote signature against the claimed committee members' keys.
2. Checks that each claimed voter is a legitimate committee member for the given round (committee membership proof / VRF eligibility).
3. Verifies that the aggregate stake of the voters meets the quorum threshold (`stakeAboveThreshold`).
4. Validates that `pcCertRound` is within an acceptable range (not expired, not from the future beyond the safe zone).
5. Validates that `pcCertBoostedBlock` is a non-genesis point.

Until a real implementation is available, the stub should return `Left PerasValidationErr` (reject all) rather than `Right` (accept all), so that the code fails safely rather than silently accepting every peer-supplied certificate.

### Proof of Concept

**Entry path (peer → chain selection):**

1. Attacker peer connects via ObjectDiffusion and sends a `PerasCert` with:
   - `pcCertRound = PerasRoundNo 999` (a round not yet in the DB)
   - `pcCertBoostedBlock = blockPoint adversarialForkTip` (a block in the node's VolatileDB on a competing fork)

2. `processCerts` is called with `validateCert = validatePerasCert mkPerasParams`.

3. `validatePerasCert` returns `Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams }` — unconditionally. [1](#0-0) 

4. `processCerts` adds the cert via `addCert . WithArrivalTime now`. [2](#0-1) 

5. `ChainDB.addPerasCertAsync` enqueues `ChainSelAddPerasCert`; `chainSelSync` reads `boostedBlock`, finds it in the VolatileDB, and calls `chainSelectionForBlock`. [3](#0-2) 

6. `preferAnchoredCandidate` now computes `wsvTotalWeight` for the fork fragment including the attacker-injected boost, potentially making the fork heavier than the honest chain. [4](#0-3) 

7. The node switches to the adversarial fork.

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
