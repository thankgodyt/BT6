### Title
`stakeAboveThreshold` Compares Un-normalized `PerasVoteStake` Against a Relative Quorum Threshold Without Unit Enforcement, Enabling Quorum Bypass or Permanent Quorum Failure - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` directly compares the accumulated `PerasVoteStake` (a `Rational` that may hold an absolute ledger stake value) against `perasQuorumStakeThreshold` (a relative value, hardcoded to `3/4`). No normalization step exists anywhere in the call chain between vote ingestion and the quorum check. The function's own TODO comment acknowledges this unit mismatch. If the `PerasVoteStakeDistr` supplied at runtime contains absolute ledger stakes rather than pre-normalized relative fractions, a single vote from any voter with positive stake trivially satisfies the quorum condition (absolute lovelace >> `3/4`), forging a Peras certificate with far less than the required quorum of stake. Conversely, if the distribution is populated with values that are all < `77/100` individually and never sum above it due to a different scaling, quorum can become permanently unreachable.

---

### Finding Description

**Root cause — `stakeAboveThreshold` (lines 162–173):**

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake         = unPerasVoteStake voteStake          -- raw Rational, unit unknown
  quorumThreshold = unPerasQuorumStakeThreshold ...   -- 3/4 (relative)
  safetyMargin    = unPerasQuorumStakeThresholdSafetyMargin ... -- 2/100 (relative)
```

The function's own documentation explicitly flags the problem:

> *"TODO: this function assumes that the 'PerasVoteStake' and the quorum threshold used in 'PerasParams' are expressed in the same units … this function only makes sense when both values are relative (normalized) values, so we should either normalize the 'PerasVoteStake' before calling this function, or change this function to accept a stake distribution and perform the normalization internally."*

**How vote stake enters the system — `validatePerasVote` (lines 363–371):**

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
```

The stake is taken verbatim from `PerasVoteStakeDistr` with no normalization. The `PerasVoteStakeDistr` is a `Map PerasVoterId PerasVoteStake` whose values are `Rational`. The comment on `PerasVoteStake` itself admits:

> *"At the moment there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee."*

**Quorum check call chain:**

`processVotes` → `validatePerasVote` (assigns raw stake) → `addVote` / `addPerasVoteWithAsyncCertHandling` → `updatePerasRoundVoteStates` → `updateCandidateVoteState` → `votesReachQuorum` → `stakeAboveThreshold`

In `votesReachQuorum` (lines 267–270):
```haskell
totalVoteStake = mconcat (vpvVoteStake <$> votes)
votesHaveEnoughStake = stakeAboveThreshold cfg totalVoteStake
```

The accumulated `totalVoteStake` is compared directly against `3/4 + 2/100 = 77/100` with no normalization step anywhere in this chain.

---

### Impact Explanation

**Scenario A — absolute ledger stakes in `PerasVoteStakeDistr`:**  
If the distribution is populated with absolute lovelace-denominated values (e.g., a voter with 1,000,000 lovelace is stored as `PerasVoteStake (1000000 % 1)`), then `1000000 >= 77/100` is trivially `True`. A **single vote** from any voter with positive stake causes `votesReachQuorum` to return `Just`, and `forgePerasCert` is called immediately. This is a complete bypass of the Peras quorum requirement: an unprivileged peer can cause the local node to forge and accept a Peras certificate backed by a single voter's stake, regardless of whether honest quorum was actually reached. The forged certificate then boosts a block in chain selection, potentially causing the node to prefer an adversarially chosen chain.

**Scenario B — stakes scaled in a range that never sums to `>= 77/100`:**  
If the distribution is populated with values that individually and collectively never reach the threshold (e.g., each voter's stake is stored as a small fraction of some non-total denominator), quorum can never be reached for any round, permanently disabling Peras certificate forging and degrading chain security to base Praos.

Both scenarios arise from the same root cause: the absence of a normalization step between ledger stake lookup and the quorum comparison.

---

### Likelihood Explanation

The entry path is fully reachable by an unprivileged peer: Peras votes arrive via the miniprotocol, are processed by `processVotes`, and flow directly into the quorum check. The `PerasVoteStakeDistr` is supplied at runtime via `getStakeDistrSTM` — a parameter whose concrete implementation determines whether absolute or relative values are used. The TODO comment and the explicit note that "there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake" confirm that the normalization contract is not enforced at any type or runtime boundary. Any caller that populates `PerasVoteStakeDistr` with raw ledger stakes (the most natural interpretation of "stake distribution") triggers Scenario A.

---

### Recommendation

1. **Enforce units at the type level**: Introduce distinct newtypes for absolute ledger stake and normalized relative vote stake so that `stakeAboveThreshold` can only accept the latter.
2. **Normalize inside `validatePerasVote`**: Accept the total stake of the distribution as an additional parameter and divide each voter's stake by the total before assigning `vpvVoteStake`, ensuring the accumulated value passed to `stakeAboveThreshold` is always in `[0, 1]`.
3. **Alternatively**, change `stakeAboveThreshold` to accept the full `PerasVoteStakeDistr` and perform normalization internally, as the TODO suggests.
4. **Add an invariant assertion** that `unPerasVoteStake` of any `ValidatedPerasVote` is in `[0, 1]` at the point of insertion into the tally.

```haskell
votesReachQuorum ::
  StandardHash blk =>
  PerasCfg blk ->
  [ValidatedPerasVote blk] ->
  Maybe (ValidatedPerasVotesWithQuorum blk)
votesReachQuorum cfg votes =
  case votes of
    -- We need at least one vote to determine who these votes are for, so we
    -- can't vacuously reach a quorum, even if the quorum threshold is 0.
    [] -> Nothing
    -- If we have at least one vote, we must check that all votes are for the
    -- same target, and that their total stake of is above the quorum threshold.
    (v0 : vs)
      | not (allVotesMatchTarget v0 vs) ->
          Nothing
      | not votesHaveEnoughStake ->
          Nothing
      | otherwise ->
          Just
            ValidatedPerasVotesWithQuorum
              { vpvqTarget = getPerasVoteTarget v0
              , vpvqVotes = v0 :| vs
              , vpvqPerasCfg = cfg
              }
 where
  totalVoteStake =
    mconcat (vpvVoteStake <$> votes)
  votesHaveEnoughStake =
    stakeAboveThreshold cfg totalVoteStake
  allVotesMatchTarget target =
    all ((== (getPerasVoteTarget target)) . getPerasVoteTarget)
```
