### Title
GDD Peer Disconnection Uses Raw Block-Count Density While Peras-Enabled Chain Selection Uses Certificate-Boosted Weight — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Genesis/Governor.hs`)

---

### Summary

When Peras is enabled, the Genesis Density Disconnection (GDD) rule evaluates peer chains using raw block count (density), while the chain-selection function evaluates the same chains using Peras weight (block count + certificate boosts). An adversary can craft a chain with more raw blocks but zero Peras boosts, causing GDD to disconnect the honest peer whose chain has fewer blocks but enough certificate weight to win chain selection. The node is then left with only the adversarial chain, which it would not have selected had both peers remained connected.

---

### Finding Description

`densityDisconnect` in `Governor.hs` computes each peer's quality exclusively as a raw block count:

```haskell
lowerBound = fromIntegral $ AF.length clippedFragment   -- line 423
upperBound = lowerBound + potentialSlots                 -- line 425
```

and disconnects peer0 when peer1's lower bound meets or exceeds peer0's upper bound:

```haskell
guard $ lb1 >= (if idling0 then lb0 else ub0)           -- line 486
```

No `PerasWeightSnapshot` is accepted by `densityDisconnect`; its signature carries only `GenesisWindow`, `SecurityParam`, `ChainSyncState`, candidate fragments, and the LoE fragment.

When Peras is enabled, `preferAnchoredCandidate` in `AnchoredFragment.hs` takes a completely different path:

```haskell
| otherwise =                                            -- line 204
    case AF.intersect ours cand of
      Just (_, _, oursSuffix, candSuffix) ->
        case preferCandidate cfg
          (weightedSelectView cfg weights oursSuffix)
          (weightedSelectView cfg weights candSuffix) of ...
```

`weightedSelectView` builds a `WeightedSelectView` whose total weight is:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv  -- SelectView.hs line 60-61
```

i.e. **absolute block number + certificate-boost sum over the suffix**. The ordering used for chain selection is therefore `wsvTotalWeight`, not raw block count.

The two metrics are independent: a fragment with `N−1` blocks and a Peras boost `W > 1` has `wsvTotalWeight = (N−1+anchor) + W`, which exceeds the `wsvTotalWeight = N+anchor` of a fragment with `N` blocks and no boost. Yet GDD sees only `N−1 < N` and disconnects the boosted peer.

---

### Impact Explanation

**High — chain-selection error induced by an unprivileged peer.**

A syncing node running with Peras enabled can be made to permanently disconnect from the peer serving the honest (certificate-boosted) chain and retain only the adversarial (block-dense, boost-free) chain. After disconnection the node's chain selection, even operating correctly on Peras weight, cannot recover the honest chain because the peer that served it has been expelled. This satisfies the "High" criterion: an unprivileged peer with a crafted chain causes an honest node to prefer a non-canonical, less-secure chain beyond the intended security assumptions.

---

### Likelihood Explanation

**Low** on current mainnet (Peras is disabled by default; the CHANGELOG explicitly notes "if Peras is disabled (which is the default), there is no observable difference"). **Medium** once Peras is activated: the attack requires only that the adversary serve a valid chain with more raw blocks than the honest chain inside the genesis window, which is achievable without any key compromise or stake majority. The entry path is the standard ChainSync miniprotocol, reachable by any unprivileged peer.

---

### Recommendation

Pass a `PerasWeightSnapshot` into `densityDisconnect` (or into a wrapper that calls it) and replace the raw-length bounds with Peras-weighted bounds when the snapshot is non-empty. Concretely, `lowerBound` and `upperBound` should be computed using `totalWeightOfFragment` (already defined in `Weight.hs`) rather than `AF.length`, so that the disconnection criterion is consistent with the `wsvTotalWeight` ordering used by `preferAnchoredCandidate`. The `offersMoreThanK` guard should similarly compare total Peras weight against `k`, mirroring `takeVolatileSuffix` which already uses `totalWeightOfFragment` for the immutable-tip calculation.

---

### Proof of Concept

Assume Peras is enabled with boost weight `W = 2`, genesis window `sgen`, security parameter `k`, and two peers both syncing from the same LoE anchor:

| Peer | Blocks in genesis window | Peras boosts | GDD `lowerBound` | `wsvTotalWeight` (suffix) |
|------|--------------------------|--------------|------------------|---------------------------|
| Adversary (A) | N | 0 | N | N |
| Honest (H) | N−1 | W=2 | N−1 | N−1+2 = N+1 |

**GDD evaluation** (`Governor.hs` line 486):
`lb_A = N ≥ lb_H = N−1` → peer H is classified as a losing peer and disconnected.

**Chain-selection evaluation** (`SelectView.hs` line 82):
`wsvTotalWeight(H) = N+1 > wsvTotalWeight(A) = N` → chain H would be preferred.

After GDD disconnects H, the node retains only A. Chain selection on the remaining single candidate trivially adopts A's chain. The node has adopted the non-canonical adversarial chain, a result that would not have occurred had the GDD used Peras weight instead of raw density.
