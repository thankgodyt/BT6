Audit Report

## Title
Promise Failure in `send_tokens()` Silently Treated as Success in `fin_transfer_send_tokens_callback` — (File: `near/omni-bridge/src/lib.rs`)

## Summary
`is_refund_required` returns `false` unconditionally for all non-`ft_transfer_call` paths and for `ft_transfer_call` promise errors, causing `fin_transfer_send_tokens_callback` to enter the success branch even when `send_tokens()` fails. This permanently decrements `locked_tokens` without delivering tokens, emits a false `FinTransferEvent`, pays the relayer fee, and consumes the proof — leaving bridged funds permanently frozen with no on-chain recovery path.

## Finding Description
`process_fin_transfer_to_near` executes the following sequence:

1. Calls `unlock_tokens_if_needed` at line 1881, which decrements `locked_tokens` and records the action in `lock_actions`.
2. Calls `send_tokens()` at line 1957, dispatching one of `ft_transfer`, `ft_transfer_call`, `mint`, or `near_withdraw → near_withdraw_callback`.
3. Chains `fin_transfer_send_tokens_callback` as the result handler at line 1967, passing `!msg.is_empty()` as `is_ft_transfer_call`.

Inside `fin_transfer_send_tokens_callback` (line 1702), the decision to revert is delegated entirely to `is_refund_required(is_ft_transfer_call)`.

`is_refund_required` (lines 1784–1804) has two critical failure paths:

- **`is_ft_transfer_call = false`** (line 1801–1803): When `msg` is empty — covering `ft_transfer` (non-deployed tokens), `mint` with no msg (deployed tokens), and `near_withdraw` — the function returns `false` **without inspecting the promise result at all**. Any promise failure from these paths is silently treated as success.
- **`is_ft_transfer_call = true`, promise error** (line 1798): When the token contract panics during `ft_transfer_call`, `env::promise_result_checked` returns `Err(_)`, and the function returns `false` with the comment "Unexpected case: don't refund."

When `is_refund_required` returns `false`, the `else` branch (lines 1719–1746):
- Sends the fee to the relayer via `ft_transfer` or `mint` (detached, no rollback).
- Emits `FinTransferEvent` signaling success to off-chain observers.
- Does **not** call `revert_lock_actions`, so the `locked_tokens` decrement from step 1 is permanent.
- Does **not** call `remove_fin_transfer`, but `add_fin_transfer` was already called at line 1875, so the proof is consumed and cannot be resubmitted.

## Impact Explanation
For non-deployed (locked) tokens (e.g., USDC, wETH): the bridge holds the physical tokens in its balance inside the token contract. After `ft_transfer` fails, the tokens remain in the bridge's balance but `locked_tokens` has been decremented. The recipient receives nothing. There is no admin function, retry path, or DAO escape hatch. The funds are permanently frozen. This matches the allowed impact: **permanent freezing of bridged funds**.

The `locked_tokens` under-count creates a secondary accounting inconsistency: the bridge believes fewer tokens are locked than are actually present, which could allow additional outbound transfers beyond the true reserve — matching **balance/escrow mis-accounting**.

For deployed (minted) tokens: `mint()` failing means no tokens are created, but `FinTransferEvent` is still emitted, creating a false record of a completed transfer.

## Likelihood Explanation
Medium. The trigger is a promise error from the token contract during `ft_transfer` / `ft_transfer_call` / `mint`. Realistic causes requiring no privileged access:

- **Token pause**: USDC, USDT, and many bridged ERC-20s have pause functionality. If the NEAR-side token contract is paused between the storage-check step and the `ft_transfer` step, the transfer panics.
- **Recipient account deletion**: A NEAR account can be deleted between the storage deposit check and the actual `ft_transfer`, causing the transfer to panic.
- **Gas exhaustion**: `send_tokens` computes `ft_transfer_call_gas` dynamically; if the remaining gas falls below `MIN_FT_TRANSFER_CALL_GAS`, the `require!` guard at line 2089 panics, propagating as a promise error to the callback.

None of these require privileged access; any user whose inbound transfer lands in one of these conditions is affected.

## Recommendation
In `fin_transfer_send_tokens_callback`, treat a promise error from `send_tokens()` the same as a refund:

- For the `is_ft_transfer_call = false` path: explicitly check `env::promise_result_checked(0, ...)` in `is_refund_required` (or directly in the callback) and return `true` on `Err(_)`.
- For the `ft_transfer_call` path: change the `Err(_)` arm at line 1798 to return `true` instead of `false`.

In both error cases, the callback should call `revert_lock_actions`, `remove_fin_transfer`, and emit `FailedFinTransferEvent` instead of proceeding to the success branch.

## Proof of Concept
**Scenario**: USDC (non-deployed, locked token) is paused on NEAR between the storage-check step and the `ft_transfer` step.

1. User initiates transfer of 1000 USDC from Ethereum → NEAR recipient `alice.near`.
2. Relayer calls `fin_transfer()` with valid EVM proof.
3. `fin_transfer_callback` verifies proof, calls `process_fin_transfer_to_near`.
4. `unlock_tokens_if_needed` (line 1881) decrements `locked_tokens[Eth][usdc.near]` by 1000.
5. `send_tokens` (line 1957) dispatches `ft_transfer(alice.near, 1000)` on `usdc.near` (non-deployed token, empty msg → line 2102–2106).
6. USDC contract is paused → `ft_transfer` panics → promise result is `Err(_)`.
7. `fin_transfer_send_tokens_callback` is called with `is_ft_transfer_call = false` (because `msg.is_empty()` → `!msg.is_empty() = false` at line 1973).
8. `is_refund_required(false)` returns `false` unconditionally at line 1801–1803, without inspecting the promise result.
9. Callback enters `else` branch (line 1719): sends fee to relayer, emits `FinTransferEvent`.
10. `revert_lock_actions` is never called; `locked_tokens` remains decremented by 1000.
11. `alice.near` receives 0 USDC. The proof is consumed (transfer in `finalised_transfers`). No retry is possible.
12. 1000 USDC remain in the bridge's balance with no on-chain recovery path.

**Test plan**: Write a NEAR sandbox integration test that deploys a mock FT contract with a pausable `ft_transfer`, submits a valid `fin_transfer` proof, pauses the token between the storage-check callback and the `ft_transfer` dispatch, and asserts that after `fin_transfer_send_tokens_callback` executes: (a) `alice.near` balance is 0, (b) `locked_tokens` is decremented, (c) `FinTransferEvent` was emitted, and (d) the transfer ID is still in `finalised_transfers`.
