### Title
Unauthenticated `request_refund` Allows Any Caller to Redirect Stuck Deposits to an Attacker-Controlled BTC Address — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

`request_refund` imposes no check that the caller is the original depositor. When a deposit's `deposit_msg.refund_address` field is `None`, any unprivileged NEAR account can supply an arbitrary attacker-controlled BTC address as the `refund_address`. After the `unsafe_refund_timelock_sec` elapses, the same (or any) account can call `execute_refund`, causing the bridge's MPC pipeline to sign a transaction that sends the victim's BTC to the attacker.

---

### Finding Description

`request_refund` is a public, permissionless entry point: [1](#0-0) 

The only caller-identity check inside the function body is on the optional `gas_fee` parameter; the `refund_address` argument is completely unrestricted: [2](#0-1) 

`internal_request_refund` enforces a match only when `deposit_msg.refund_address` is already `Some`: [3](#0-2) 

When that field is `None` — the common case for standard deposits — the function stores whatever `refund_address` the caller supplied, with no verification that the caller is `deposit_msg.recipient_id` or any other authorized party: [4](#0-3) 

The `deposit_msg` is the only key needed to reconstruct the deposit address (it is hashed to derive the on-chain path): [5](#0-4) 

Because the `deposit_msg` is passed in plain-text to `verify_deposit` by relayers and is derivable from public BTC on-chain data, an attacker can reconstruct it for any unfinalized deposit.

After the refund request is stored, `execute_refund` is also permissionless: [6](#0-5) 

`resolve_execute_refund_timelock` itself acknowledges the risk but treats the longer `unsafe_refund_timelock_sec` as the sole mitigation: [7](#0-6) 

Once the timelock expires, `finalize_refund_with_psbt` creates a `BTCPendingInfo` that routes the deposit UTXO to the attacker's address through the MPC signing pipeline: [8](#0-7) 

---

### Impact Explanation

An attacker who races to call `request_refund` before the legitimate depositor — supplying their own BTC address — will, after the timelock, receive the victim's BTC via the bridge's MPC-signed transaction. The original depositor loses their entire deposit permanently. This constitutes a **significant theft of user funds** matching the Critical impact tier.

---

### Likelihood Explanation

- All inputs required (`deposit_msg`, raw `tx_bytes`, Merkle proof) are derivable from public BTC blockchain data.
- The attacker only needs to pay a small NEAR storage deposit.
- The race is easily won by monitoring the BTC mempool/chain for bridge deposits that have not yet been finalized by a relayer.
- The sole mitigation — DAO/Operator rejection within `unsafe_refund_timelock_sec` — is an off-chain operational control that can be missed, especially during high-volume periods or operator downtime.
- No special privilege, leaked key, or majority-hash-power is required.

---

### Recommendation

Add a caller-identity check in `request_refund`: require that `env::predecessor_account_id() == deposit_msg.recipient_id` (or a DAO/Operator role) before accepting a caller-supplied `refund_address` when `deposit_msg.refund_address` is `None`. Alternatively, require that `deposit_msg.refund_address` always be set at deposit time and reject refund requests that lack a pre-authorized address unless the caller is privileged.

---

### Proof of Concept

1. Alice sends 1 BTC to the bridge with `deposit_msg = { recipient_id: "alice.near", refund_address: None, ... }`. The relayer never calls `verify_deposit` (e.g., due to a bug or downtime).
2. Attacker Bob reconstructs Alice's `deposit_msg` from the BTC transaction's OP_RETURN / relayer logs and obtains the raw `tx_bytes` and Merkle proof from the BTC chain.
3. Bob calls `request_refund(deposit_msg, "bob_btc_address", tx_bytes, vout, proof, None)` with the required NEAR storage deposit attached. The Light Client verifies the transaction; the refund request is stored with `refund_address = "bob_btc_address"`.
4. After `unsafe_refund_timelock_sec` elapses (and assuming DAO/Operator does not reject), Bob calls `execute_refund(utxo_storage_key, None)`.
5. `finalize_refund_with_psbt` creates a `BTCPendingInfo` targeting Bob's address; the MPC service signs the transaction; the bridge broadcasts it; Alice's 1 BTC arrives at Bob's address.
6. Alice's deposit is permanently lost.

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
