### Title
Silent `Word64` Wraparound in `countEpochs`/`countSlots` Due to `assert`-Only Guards Disabled in Optimized Production Builds — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/HardFork/History/Util.hs`)

---

### Summary

`countEpochs`, `countSlots`, `subSlots`, and `countPerasRounds` in `Util.hs` guard their `Word64` subtractions with `assert` from `Control.Exception`. In GHC, `assert` is compiled away to a no-op when optimizations are enabled (`-O`), which is the standard production build flag. If any caller passes inverted arguments (e.g., `to < fr`), the subtraction silently wraps around to a huge `Word64` value. The most critical call site is `mkUpperBound` in `Summary.hs`, which feeds the result directly into the hard fork `Summary` used for all slot/epoch/time translations across every era.

---

### Finding Description

**Root cause — `Util.hs`:**

```haskell
-- countSlots (SlotNo to) (SlotNo fr) = assert (to >= fr) $ to - fr
-- countEpochs (EpochNo to) (EpochNo fr) = assert (to >= fr) $ to - fr
-- subSlots n (SlotNo x) = assert (x >= n) $ SlotNo (x - n)
-- countPerasRounds (PerasRoundNo to) (PerasRoundNo fr) = assert (to >= fr) $ to - fr
```

In a `-O` build, every `assert` becomes `\_ r -> r`, so the body `to - fr` executes unconditionally. `Word64` arithmetic in Haskell is modular; `5 - 10 :: Word64` silently yields `18446744073709551611`.

**Critical call site — `mkUpperBound` in `Summary.hs`:**

```haskell
mkUpperBound EraParams{..} lo hiEpoch =
  Bound { ..., boundSlot = addSlots inEraSlots $ boundSlot lo, ... }
 where
  inEraEpochs = countEpochs hiEpoch (boundEpoch lo)   -- ← no runtime guard
  inEraSlots  = inEraEpochs * unEpochSize eraEpochSize
```

`hiEpoch` is supplied by `singleEraTransition`, whose contract states it must not return an epoch less than the era-start epoch. That contract is documented but **not enforced at runtime**. If `hiEpoch < boundEpoch lo`:

1. `countEpochs` wraps to `~2^64`.
2. `inEraSlots = ~2^64 * epochSize` overflows `Word64`.
3. `addSlots inEraSlots (boundSlot lo)` produces a completely wrong `boundSlot`.
4. The resulting `Bound` is stored as the era's upper bound in the `Summary`.

`mkUpperBound` is called from `reconstructSummaryLedger` → `hardForkSummary` on every block application:

```haskell
instance All SingleEraBlock xs => HasHardForkHistory (HardForkBlock xs) where
  hardForkSummary cfg =
    State.reconstructSummaryLedger cfg
      . hardForkLedgerStatePerEra
```

and from `reconstructSummary` in the `TransitionKnown` branch:

```haskell
TransitionKnown epoch ->
  let currentEnd = History.mkUpperBound params currentStart epoch
```

The corrupted `Summary` is then used by `summaryToEpochInfo`, which feeds `EpochInfo` to the Praos/TPraos leader-eligibility check, the `additionalEnvelopeChecks` header validator, and all `LocalStateQuery` responses.

**Secondary call site — `isNewEpoch` in `Protocol/Ledger/Util.hs`:**

```haskell
let epochsAfter = (countSlots newSlot firstSlot) `div` unEpochSize epochSize
```

The precondition "the two slots must be in the same era" is documented but not checked. If the `EpochInfo` passed in is already corrupted (e.g., by the `mkUpperBound` path above), `firstSlot` can exceed `newSlot`, triggering a second wraparound during header validation.

---

### Impact Explanation

A corrupted `Summary` / `EpochInfo` breaks every downstream consumer:

- **Leader-schedule check** (`checkIsLeader` in Praos/TPraos): wrong epoch → wrong stake snapshot → unauthorized block production or denial of legitimate leaders.
- **Header envelope validation** (`additionalEnvelopeChecks`): wrong `EpochInfo` → wrong epoch boundary → valid headers rejected or invalid headers accepted.
- **Era-transition gating** (`extendToSlot`): wrong era-end `Bound` → premature or missed hard-fork transition → nodes diverge on which era they are in.
- **`LocalStateQuery` responses**: wrong slot/epoch/time answers returned to wallets and explorers.

This matches the **High** allowed-impact category: *"Hard-fork, era transition, ledger-view, query, or network-version mismatch that breaks cross-era consensus or ledger invariants for production Cardano nodes."*

---

### Likelihood Explanation

The trigger requires `singleEraTransition` to return an `EpochNo` less than the current era's start epoch. The contract forbids this, but it is not enforced at runtime by the consensus layer. Realistic paths:

1. **Crafted block on a private/test network**: a ledger implementation with a bug in its `singleEraTransition` that can be triggered by a specific transaction or block body. An unprivileged peer submitting such a block causes the node to compute a corrupted `Summary` on the next `hardForkSummary` call.
2. **Future era regression**: a new era's `singleEraTransition` implementation inadvertently returns an epoch in the past (e.g., off-by-one in epoch arithmetic). Because the consensus layer has no runtime guard, the error propagates silently rather than failing loudly.
3. **Snapshot/DB replay**: a node replaying from a snapshot where the stored `TransitionInfo` is inconsistent with the current `Shape` (e.g., after a misconfigured genesis rollback) can feed an invalid epoch into `mkUpperBound`.

For current Cardano mainnet the ledger's `singleEraTransition` implementations are well-tested, making this unlikely in normal operation. However, the absence of any runtime guard means the failure mode is **silent corruption** rather than a loud crash, making it harder to detect and diagnose.

---

### Recommendation

Replace every `assert`-guarded subtraction in `Util.hs` with an explicit runtime check that either throws a descriptive error or, analogously to the Ajna mitigation, saturates to zero:

```haskell
-- Option A: fail loudly (preferred for consensus-critical code)
countEpochs :: HasCallStack => EpochNo -> EpochNo -> Word64
countEpochs (EpochNo to) (EpochNo fr)
  | to >= fr  = to - fr
  | otherwise = error $ "countEpochs: underflow: to=" <> show to <> " fr=" <> show fr

-- Option B: saturate (analogous to Ajna mitigation)
countEpochs :: HasCallStack => EpochNo -> EpochNo -> Word64
countEpochs (EpochNo to) (EpochNo fr) = if to >= fr then to - fr else 0
```

Apply the same fix to `countSlots`, `subSlots`, and `countPerasRounds`. Additionally, add a runtime assertion in `mkUpperBound` that `hiEpoch >= boundEpoch lo` before calling `countEpochs`, so that a contract violation by any `singleEraTransition` implementation is caught immediately at the consensus boundary rather than propagating silently.

---

### Proof of Concept

In a GHC `-O` build, `assert` is a no-op. Suppose an era starts at `EpochNo 10` and `singleEraTransition` returns `EpochNo 5`:

```
countEpochs (EpochNo 5) (EpochNo 10)
  = 5 - 10  :: Word64
  = 18446744073709551611          -- wraps around

inEraSlots = 18446744073709551611 * 432000  -- Cardano epoch size
           = overflows Word64 → some small garbage value

addSlots garbageSlots (boundSlot lo)
  → boundSlot of the era-end Bound is completely wrong
```

The corrupted `Bound` is stored in the `Summary`. Every subsequent call to `summaryToEpochInfo` returns wrong epoch/slot/time mappings. The Praos leader check uses the wrong stake snapshot epoch; `additionalEnvelopeChecks` accepts or rejects headers based on wrong era boundaries; `extendToSlot` may skip or repeat an era transition.
