### Title
Peras Certificate Validation Stub Always Returns `Right`, Enabling Unauthenticated Chain-Selection Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance implements `validatePerasCert` as a stub that unconditionally returns `Right` (success) without performing any cryptographic or structural verification. Any crafted `PerasCert` received from an unprivileged peer via the Peras object-diffusion mini-protocol is therefore accepted as a `ValidatedPerasCert` carrying a full boost weight, which is then fed into chain selection. This is the direct analog of the Clearpool `resolveAuctionWithoutGoverment` pattern: guard conditions that are trivially satisfied by default/zero values (here, the absence of any guard at all) allow an unauthorized state transition (here, chain-selection manipulation).

---

### Finding Description

`SupportsPeras.hs` declares a universal overlapping instance for all block types:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

No signature check, no round-number bound check, no issuer-eligibility check, and no VRF proof verification is performed. The function always returns `Right`, wrapping the attacker-supplied `cert` verbatim and assigning it the full configured `perasWeight`.

The inbound path for peer-supplied certificates is `makePerasVotePoolWriterFromChainDB` / `makePerasVotePoolWriterFromVoteDB` in the object-diffusion layer, which calls `validatePerasCert` before storing the result: [2](#0-1) 

Once stored as a `ValidatedPerasCert`, the boost weight is incorporated into `compareAnchoredFragments` via `PerasWeightSnapshot`: [3](#0-2) 

A secondary, compounding issue exists in `revalidateHeader`, which guards its entire envelope check (block number, slot number, hash chain) behind `assertWithMsg`:

```haskell
revalidateHeader cfg ledgerView hdr st =
  assertWithMsg envelopeCheck $
    HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'
``` [4](#0-3) 

`assertWithMsg` is a CPP no-op when the `asserts` flag is off, which is the **default** (`default: False`): [5](#0-4) [6](#0-5) 

In a default production build, `revalidateHeader` therefore skips the envelope check entirely and also skips VRF/KES validation (via `reupdateChainDepState` instead of `updateChainDepState`). While `revalidateHeader` is intended only for previously-validated blocks, the combination with the certificate stub means an attacker can influence which chain is "previously validated" in the first place.

---

### Impact Explanation

**High — Chain selection bug.** An unprivileged peer can send a crafted `PerasCert` (arbitrary `pcCertRound` and `pcCertBoostedBlock`) over the Peras object-diffusion mini-protocol. Because `validatePerasCert` always returns `Right`, the certificate is stored as a `ValidatedPerasCert` with full boost weight. `compareAnchoredFragments` then uses this weight to prefer the attacker's chain over the honest canonical chain, causing the victim node to switch to a non-canonical or attacker-controlled fork. This breaks the chain-selection invariant without requiring any stake, key material, or operator compromise.

---

### Likelihood Explanation

**High.** The Peras object-diffusion mini-protocol is reachable by any peer that can establish a node-to-node connection. No authentication, stake ownership, or special privilege is required to send a `PerasCert` message. The stub is the only instance in the codebase for all block types (the TODO comment and issue reference confirm no override exists yet). The attack requires only constructing a well-formed CBOR-encoded `PerasCert` with a desired `pcCertBoostedBlock` pointing to the attacker's block.

---

### Recommendation

1. **Remove or gate the degenerate `validatePerasCert` stub.** Until a real implementation exists, `validatePerasCert` should return `Left PerasValidationErr` (reject all) rather than `Right` (accept all). Accepting unverified certificates is strictly worse than rejecting them from a security standpoint.

2. **Implement cryptographic certificate validation** per the Peras specification (CIP-0140): verify the aggregate signature, check that the certificate's round number is within the expected window, and confirm that the boosted block is on the node's current chain.

3. **Promote the `assertWithMsg` envelope check in `revalidateHeader` to an unconditional runtime check**, or document precisely which callers guarantee the precondition and add a type-level or runtime guard at those call sites.
