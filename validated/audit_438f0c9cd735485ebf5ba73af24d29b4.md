### Title
Peer-Injected Certificate Resets Peras Voting Cooldown, Permanently Suppressing Node Votes - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs`, `File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Storage/PerasCertDB/Impl.hs`)

### Summary

The Peras voting rules (VR-1A and VR-2A) both depend on `latestCertSeen`, which is the certificate with the highest round number ever received by the node. Any peer can inject a certificate with an arbitrarily high round number via the ObjectDiffusion mini-protocol because `validatePerasCert` is a production stub that unconditionally returns `Right`. Once `latestCertSeen` is advanced to round `N`, the node cannot satisfy VR-1A (requires cert from round `currRound - 1`) or VR-2A (requires cert from at least `R` rounds ago) until `currRound` catches up — which the attacker can prevent by re-injecting a fresh certificate each round. This is a direct structural analog to the external report: just as an attacker resets a victim's share-lock timer by buying shares on their behalf, here an attacker resets the victim node's Peras voting cooldown by injecting a certificate on its behalf.

---

### Finding Description

**Root cause 1 — stub validation accepts every certificate unconditionally.**

In the production `BlockSupportsPeras` instance:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This is not test code. It is the live `BlockSupportsPeras` instance used by `processCerts` in the ObjectDiffusion inbound path.

**Root cause 2 — `implAddCert` advances `latestCertSeen` to the highest round number ever seen.**

```haskell
pcdsLatestCertSeen' = case pcdsLatestCertSeen pcds of
  Nothing -> Just cert
  Just prev
    | getPerasCertRound cert > getPerasCertRound prev -> Just cert
    | otherwise -> Just prev
``` [2](#0-1) 

`latestCertSeen` is a monotonically advancing high-water mark. It is never rolled back, and it is the direct input to both VR-1A and VR-2A.

**Root cause 3 — VR-1A and VR-2A both fail when `latestCertSeen` is from the current round.**

VR-1A requires `currRoundNo == getPerasCertRound(lcsCert) + 1` (cert must be from the *previous* round): [3](#0-2) 

VR-2A requires `getPerasCertRound(lcsCert) + R <= currRoundNo` (cert must be at least `R` rounds old): [4](#0-3) 

If an attacker injects a certificate with `roundNo = currRound`, then:
- VR-1A: `currRound == currRound + 1` → **false**
- VR-2A: `currRound + R <= currRound` → **false** (since `R > 0`)

Both paths fail; `isPerasVotingAllowed` returns `NoVote`. [5](#0-4) 

**Root cause 4 — the inbound path stamps the attacker's arrival time, not the certificate's slot.**

`processCerts` timestamps the certificate with `systemTimeCurrent` at the moment of receipt:

```haskell
now <- systemTimeCurrent systemTime
...
addCert . WithArrivalTime now
``` [6](#0-5) 

VR-1A's `lcsArrivalSlot` check uses this wall-clock arrival time, so the attacker can also trivially satisfy the arrival-time sub-check (VR-1A part 2) by sending the certificate early in the round.

---

### Impact Explanation

A node whose `latestCertSeen` has been advanced to round `N ≥ currRound` cannot vote in any round until `currRound > N + R` (VR-2A exit) or `currRound == N + 1` (VR-1A, which the attacker immediately breaks again). By re-injecting a certificate with `roundNo = currRound` at the start of each round, the attacker permanently suppresses the victim node's Peras votes. This materially weakens vote authorization: the victim node is silently excluded from every quorum computation. If enough nodes are targeted, quorum is never reached, Peras certificates are never generated, and the fast-finality guarantee of the Peras protocol is permanently disabled for the targeted partition of the network. This fits the allowed impact scope: *"Public node API or miniprotocol flaw that... materially weakens... vote... authorization without relying on DoS."*

---

### Likelihood Explanation

The attack requires only a single TCP connection to the victim node's ObjectDiffusion endpoint. No stake, no keys, no committee membership, and no chain knowledge are needed because `validatePerasCert` is an unconditional stub. The attacker sends one `PerasCert` message per round (a few bytes) with `pcCertRound = currRound`. The `opwHasObject` deduplication check only prevents re-adding a certificate for a round already in the database; the attacker simply increments the round number each time. [7](#0-6) 

---

### Recommendation

1. **Implement `validatePerasCert` before enabling the ObjectDiffusion endpoint in any environment.** The stub at `BlockSupportsPeras.hs:353–358` must reject certificates whose round number is in the future relative to the node's current slot, and must verify the aggregate BLS signature and committee eligibility proofs. The linked issue [#120](https://github.com/tweag/cardano-peras/issues/120) tracks this.

2. **Bound `latestCertSeen` updates to certificates whose round number does not exceed `currRound`.** `implAddCert` should refuse to advance `pcdsLatestCertSeen` to a certificate from a round strictly greater than the current Peras round. This prevents the high-water mark from being poisoned by future-dated certificates even if validation is temporarily incomplete.

3. **Add a round-number range check in `processCerts`** before calling `validateCert`, rejecting certificates whose `getPerasCertRound` is more than one round ahead of the node's current round.

---

### Proof of Concept

1. Attacker connects to victim node's ObjectDiffusion port.
2. At the start of round `r`, attacker sends a `PerasCert` with `pcCertRound = r` and any `pcCertBoostedBlock`.
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right` unconditionally.
4. `implAddCert` stores the cert; `pcdsLatestCertSeen` is updated to round `r`.
5. Victim node evaluates `isPerasVotingAllowed`:
   - VR-1A: `r == r + 1` → false.
   - VR-2A: `r + R <= r` → false (R ≥ 1).
   - Result: `NoVote`.
6. Attacker repeats at round `r+1` with `pcCertRound = r+1`. The victim never votes. [1](#0-0) [8](#0-7) [9](#0-8) [10](#0-9)

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
