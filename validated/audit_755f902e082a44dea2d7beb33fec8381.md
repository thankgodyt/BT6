### Title
Caller-Controlled `refund_address` in `request_refund` Enables Front-Running Theft of Another User's BTC Refund — (`contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

`request_refund` is a permissionless function that accepts a caller-supplied `refund_address` (a Bitcoin address). When the original `deposit_msg` does not embed a `refund_address`, the contract imposes no ownership check on who may submit the refund request for a given UTXO. An attacker who observes a victim's `deposit_msg` (publicly emitted by `get_user_deposit_address`) can front-run the victim's refund submission, locking in their own Bitcoin address as the refund destination. After the timelock elapses, `execute_refund` sends the victim's BTC to the attacker's address. The only defense is an off-chain DAO/Operator rejection, which is an operational control, not a code-level invariant.

`request_refund` is callable by any NEAR account: [1](#0-0)

This check fires **only** when `deposit_msg.refund_address` is `Some`. When the victim's original deposit used a `deposit_msg` without a `refund_address` field (the common case for standard deposits), the caller may supply any Bitcoin address.

The `deposit_msg` is publicly observable because `get_user_deposit_address` emits it in a `LogDepositAddress` event: [3](#0-2) 

Once a refund request is stored, a duplicate is rejected: [4](#0-3) 

So whichever request lands first wins. After the timelock, `execute_refund` builds the PSBT using the stored `refund_address` with no further ownership check: [5](#0-4) 

The stored `refund_address` is taken verbatim from the attacker's submission: [6](#0-5)

### Impact Explanation

If the DAO/Operator does not actively monitor and reject the malicious request within the timelock window, the victim's BTC is sent to the attacker's Bitcoin address. This constitutes a **significant loss of user funds**. Even if the DAO/Operator rejects the request, the victim's refund is blocked until the request is cleared, causing temporary fund lockup.

---

### Likelihood Explanation

- `get_user_deposit_address` is the standard on-chain entry point for users to obtain their deposit address; calling it publicly broadcasts the `deposit_msg`.
- `request_refund` requires only a NEAR storage deposit (non-refundable anti-spam fee), a trivial cost for an attacker.
- The attacker only needs to submit their transaction before the victim's `request_refund` call confirms — a standard front-running scenario on NEAR.
- Deposits that are never finalized (relayer inactivity, user change of mind) are the exact scenario the refund flow is designed for, making this a realistic attack surface.

---

### Recommendation

Bind the refund request to the submitter's identity and enforce that only the original depositor (or a pre-authorized address) may claim the refund:

1. **Require `deposit_msg.refund_address` to be set** for all new deposits, making the refund destination immutable at deposit time. Reject `request_refund` calls where `deposit_msg.refund_address` is `None` and the caller is not the `recipient_id` in the `deposit_msg`.
2. Alternatively, **require the caller of `request_refund` to be the `deposit_msg.recipient_id`** (the NEAR account that was to receive nBTC), so only the intended beneficiary can initiate a refund.
3. As a defense-in-depth measure, ensure `unsafe_refund_timelock_sec` is **longer** than `refund_timelock_sec` (the current naming and wiki description suggest the opposite of the intended semantics), giving the DAO/Operator more time to reject suspicious requests.

---

### Proof of Concept

1. **Victim** calls `get_user_deposit_address(deposit_msg)` where `deposit_msg.refund_address = None`. The contract emits `LogDepositAddress { deposit_msg, ... }`.
2. Victim sends BTC to the derived address. The relayer never calls `verify_deposit` (e.g., relayer is down).
3. **Attacker** reads `deposit_msg` from the emitted event. Attacker constructs a `request_refund` call with the victim's `deposit_msg`, the victim's `tx_bytes`/`proof`, but `refund_address = <attacker_btc_address>`.
4. Attacker submits this call before the victim's own `request_refund` (front-run). The Light Client validates the proof; `request_refund_callback` stores the request with the attacker's `refund_address`.
5. After `unsafe_refund_timelock_sec` elapses (and assuming the DAO/Operator does not reject), attacker calls `execute_refund(utxo_storage_key, None)`.
6. `internal_execute_refund` → `build_refund_output(&refund_request.refund_address, ...)` builds a PSBT paying the attacker's Bitcoin address. The MPC signs and broadcasts it. Victim's BTC is gone. [2](#0-1) [4](#0-3) [5](#0-4)

    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
