### Title
Peras Certificate Validation Stub Always Accepts Any Certificate, Enabling Chain Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The degenerate `BlockSupportsPeras` instance, which is the **only** instance in production and covers all block types via `instance StandardHash blk => BlockSupportsPeras blk`, implements `validatePerasCert` as an unconditional `Right` — it accepts every inbound Peras certificate without performing any cryptographic or structural validation. This is the direct analog of the ShadowFactory bug: a required check is never initialized/implemented, so it always passes. Because `validatePerasCert` is wired into the live `makePerasCertPoolWriterFromChainDB` path, an unprivileged peer can inject arbitrary crafted Peras certificates that boost any block, directly manipulating Peras-weighted chain selection on the receiving node.

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub:** [1](#0-0) 

The catch-all instance (line 320) covers every `StandardHash blk`, making it the sole implementation in production. The `validatePerasCert` method (lines 353–358) unconditionally returns `Right ValidatedPerasCert{...}` — no signature check, no round-number check, no committee membership check, no quorum check.

**Entry path — the stub is wired into the live ChainDB writer:** [2](#0-1) 

`makePerasCertPoolWriterFromChainDB` passes `validatePerasCert mkPerasParams` as the validation callback to `processCerts`. Because `validatePerasCert` always returns `Right`, every certificate received from any peer passes the `partitionEithers` check inside `processCerts`: [3](#0-2) 

**Chain selection consequence — accepted certificates directly affect chain weight:**

Once a certificate is stored in the `PerasCertDB`, `chainSelSync` is triggered for the boosted block: [4](#0-3) 

The `PerasWeightSnapshot` used in chain selection accumulates the boost from every accepted certificate. Chain selection then compares total weight (block number + weight boost) rather than block number alone: [5](#0-4) 

An attacker who injects a certificate boosting a block on a fork can push that fork's total weight above the honest chain's weight, causing the node to switch.

### Impact Explanation

**High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain.**

A peer with no special privileges can craft a `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock`, send it via the ObjectDiffusion mini-protocol, and have it unconditionally accepted and stored. The resulting weight boost is then used in `WeightedSelectView` comparisons. If the boost is large enough (controlled by `perasWeight` in `mkPerasParams`), the node will switch to the attacker's fork, violating chain safety beyond the intended Peras security assumptions.

### Likelihood Explanation

**High.** The vulnerable code path is the only production implementation of `BlockSupportsPeras`. The ObjectDiffusion mini-protocol for Peras certificates is an externally reachable network endpoint. No keys, stake, or operator access are required — any connected peer can send a crafted certificate. The CHANGELOG confirms this path is active: *"Make the ChainDB aware of the PerasCertDB, and modify the chain selection function accordingly."* [6](#0-5) 

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
1. The certificate's aggregate BLS signature against the declared committee members' verification keys.
2. That each declared voter is a legitimate committee member for the given round (VRF eligibility).
3. That the total stake of the voters meets the quorum threshold.
4. That the boosted block hash and round number are internally consistent.

Until a real implementation exists, the `makePerasCertPoolWriterFromChainDB` path must not be reachable from untrusted peers (e.g., gate it behind a feature flag that is off by default in production).

### Proof of Concept

1. Connect to a node as an unprivileged peer via the ObjectDiffusion mini-protocol.
2. Craft a `PerasCert` with `pcCertRound = R` and `pcCertBoostedBlock = B` where `B` is the tip of a fork that is shorter than the honest chain by `N` blocks, and `perasWeight * (number of certs sent) > N`.
3. Send the crafted certificate(s) to the node.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{vpcCertBoost = perasWeight mkPerasParams}` unconditionally.
5. The certificate is stored in `PerasCertDB`; `chainSelSync` triggers chain selection for block `B`.
6. `weightedSelectView` computes the fork's total weight as `blockNo(B) + boost`, which now exceeds the honest chain's `blockNo`.
7. The node switches to the attacker's fork. [7](#0-6) [8](#0-7)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
