### Title
Hardcoded Zcash Consensus Branch IDs Cause All Zcash Withdrawals and Refunds to Panic After Any Future Network Upgrade - (File: contracts/satoshi-bridge/src/zcash_utils/psbt_wrapper.rs)

### Summary

`PsbtWrapper::to_bytes` and `PsbtWrapper::deserialize` hardcode exactly three Zcash consensus branch IDs (Nu6, Nu6_1, Nu6_2). When Zcash activates any subsequent network upgrade, `get_branch_id` returns a new `BranchId` variant not covered by these hardcoded arms, causing `to_bytes` to panic via `unreachable!()` and `deserialize` to panic with "ERR_INVALID_PSBT: unsupported branch_id". This is directly analogous to the `INFLATION_PROTECTION_TIME` issue: a hardcoded time-dependent constant that makes bridge functionality silently break at a specific point in time (the block height of the next Zcash network upgrade).

### Finding Description

In `PsbtWrapper::to_bytes`, the branch ID is serialized via an exhaustive match that only covers three variants:

```rust
// contracts/satoshi-bridge/src/zcash_utils/psbt_wrapper.rs, lines 219-224
match self.branch_id {
    BranchId::Nu6   => buf.write_all(&[7u8; 1]).unwrap(),
    BranchId::Nu6_1 => buf.write_all(&[8u8; 1]).unwrap(),
    BranchId::Nu6_2 => buf.write_all(&[9u8; 1]).unwrap(),
    _ => unreachable!(),
}
```

In `PsbtWrapper::deserialize`, the inverse mapping is equally rigid:

```rust
// contracts/satoshi-bridge/src/zcash_utils/psbt_wrapper.rs, lines 289-294
match branch_id_u8 {
    7 => BranchId::Nu6,
    8 => BranchId::Nu6_1,
    9 => BranchId::Nu6_2,
    _ => env::panic_str("ERR_INVALID_PSBT: unsupported branch_id"),
}
```

The branch ID stored in `PsbtWrapper` is populated dynamically at construction time via:

```rust
// contracts/satoshi-bridge/src/zcash_utils/psbt_wrapper.rs, lines 86, 141
branch_id: get_branch_id(current_height, config),
```

where `get_branch_id` delegates to `config.chain.get_branch_id(current_height)` — a function that correctly returns the live consensus branch for the current block height. When Zcash activates a new network upgrade (e.g., Nu7), this function will return a new `BranchId` variant. That variant is not in the `to_bytes` match arm, so `unreachable!()` fires, panicking the NEAR transaction.

A second hardcoded-branch-ID issue exists in `Transaction::decode`:

```rust
// contracts/satoshi-bridge/src/zcash_utils/transaction.rs, lines 51-55
pub fn decode(data: &[u8], _chain: &network::Chain) -> Result<Self, std::io::Error> {
    let mut cursor = std::io::Cursor::new(data);
    let branch_id = BranchId::Nu6_2;   // hardcoded; _chain is ignored
    let tx = ZCashTransaction::read(&mut cursor, branch_id)?;
    Ok(Self { inner_tx: tx })
}
```

The `_chain` parameter is completely ignored and `BranchId::Nu6_2` is unconditionally used. This function is called from `request_refund_callback` and `refund_execution_inputs` to decode user-submitted deposit transactions. If `ZCashTransaction::read` validates the passed branch ID against the one embedded in a V5 transaction, any deposit transaction created under Nu6 or Nu6_1 would fail to decode, blocking refund requests for those deposits.

### Impact Explanation

When Zcash activates a new network upgrade:

1. **Zcash withdrawals break entirely.** `ft_on_transfer_callback` calls `PsbtWrapper::new`, which stores the new `BranchId`. When `to_bytes` is subsequently called to serialize the PSBT, `unreachable!()` panics. The NEAR transaction fails. The user's nZEC is returned via the NEP-141 callback, but no withdrawal can ever succeed until the contract is upgraded.

2. **Zcash refunds break entirely.** `execute_refund_callback` calls `PsbtWrapper::new` with the new branch ID, then `finalize_refund_with_psbt` calls `psbt.serialize()` → `to_bytes()` → panic. The user's ZEC deposit remains locked in the bridge's deposit address with no path to recovery until a contract upgrade.

3. **All Zcash RBF and cancel-withdraw operations break.** The same `to_bytes` path is exercised by `withdraw_rbf_callback`, `cancel_withdraw_callback`, `active_utxo_management_rbf_callback`, and `cancel_active_utxo_management_callback` via `generate_psbt_from_original_psbt_and_new_output`.

The result is a complete, protocol-wide freeze of all Zcash bridge operations — a stuck bridge state requiring operator intervention (contract upgrade) to resolve.

### Likelihood Explanation

Zcash has a regular network upgrade cadence. Nu6 activated in November 2024; Nu6_1 and Nu6_2 followed. As of July 2026, a subsequent upgrade (Nu7 or equivalent) is plausible or imminent. The trigger is automatic and unprivileged: any user initiating a Zcash withdrawal or refund after the upgrade activation height will hit the panic. No special access or coordination is required.

### Recommendation

Replace the hardcoded branch-ID match arms with a dynamic mapping that does not panic on unknown variants:

```rust
// to_bytes: encode branch_id as its u32 consensus value
let branch_id_bytes = u32::from(self.branch_id).to_le_bytes();
buf.write_all(&branch_id_bytes).unwrap();

// deserialize: decode branch_id from its u32 consensus value
let branch_id_u32 = read_u32_le(&mut rdr)...;
let branch_id = BranchId::try_from(branch_id_u32)
    .unwrap_or_else(|_| env::panic_str("ERR_INVALID_PSBT: unsupported branch_id"));
```

Alternatively, store the branch ID as its raw `u32` consensus value (which is stable across library versions) rather than as a library enum variant. For `Transaction::decode`, pass the actual chain's current branch ID (derived from the current block height) instead of hardcoding `BranchId::Nu6_2`, and stop ignoring the `_chain` parameter.

### Proof of Concept

1. Zcash activates network upgrade Nu7 at block height H.
2. User calls `ft_transfer_call` on the nBTC contract to initiate a Zcash withdrawal.
3. Bridge calls `get_last_block_height_promise()` → returns height H+1.
4. `ft_on_transfer_callback` is invoked with `last_block_height = H+1`.
5. `get_expiry_height` calls `get_branch_id(H+1, config)` → returns `BranchId::Nu7`.
6. `PsbtWrapper::new` stores `branch_id: BranchId::Nu7`.
7. `create_btc_pending_info` calls `psbt.serialize()` → `to_bytes()`.
8. `to_bytes` reaches `_ => unreachable!()` → NEAR transaction panics.
9. nZEC is returned to the user; no withdrawal is possible.
