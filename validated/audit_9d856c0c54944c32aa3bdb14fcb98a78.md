### Title
Peras Certificate Validation Bypass Allows Unauthorized Chain-Selection Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance — the only instance in the codebase, applied to all block types — implements `validatePerasCert` as an unconditional `Right`, accepting every inbound certificate without any cryptographic or structural check. The production node-to-node handler registers a live `hPerasCertDiffusionClient` that feeds peer-supplied certificates through this stub and into `ChainDB.addPerasCertAsync`, which explicitly triggers a fork switch when the certificate makes a fork weightier. An unprivileged peer can therefore inject a crafted certificate that causes an honest node to prefer an attacker-chosen fork.

---

### Finding Description

**Root cause — `validatePerasCert` stub:**

The `BlockSupportsPeras` class declares `validatePerasCert` as the mandatory gate for all inbound Peras certificates. The only concrete instance in the repository is the catch-all degenerate instance:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

No signature check, no committee-membership check, no round-validity check, and no boosted-block existence check are performed. Every certificate is returned as `ValidatedPerasCert` carrying the full `perasWeight` boost.

**Production entry point — `hPerasCertDiffusionClient`:**

The production node-to-node handler record registers this path unconditionally:

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
        ...
        (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
``` [2](#0-1) 

**Downstream chain-selection trigger — `addPerasCertAsync`:**

The `ChainDB` API documents the consequence of accepting a certificate:

```haskell
addPerasCertAsync :: WithArrivalTime (ValidatedPerasCert blk) -> m (AddPerasCertPromise m)
-- ^ Asynchronously insert a certificate to the DB. If this leads to a fork to
-- be weightier than our current selection, this will trigger a fork switch.
``` [3](#0-2) 

**Corroborating missing validation in `implAddVote`:**

The same pattern exists for votes. `implAddVote` in `PerasVoteDB/Impl.hs` carries an explicit TODO:

```haskell
-- TODO: we will need to update this method with non-trivial validation logic
-- see https://github.com/tweag/cardano-peras/issues/120
implAddVote ...
``` [4](#0-3) 

The vote inbound path (`makePerasVotePoolWriterFromChainDB`) currently passes an empty stake distribution, so all votes are rejected in practice. No equivalent safety net exists for the certificate path. [5](#0-4) 

---

### Impact Explanation

Once the Peras miniprotocol version is negotiated, any peer can send a `PerasCert` with an arbitrary `pcCertBoostedBlock` pointing to a block on a minority fork. Because `validatePerasCert` always returns `Right`, the certificate is stored as `ValidatedPerasCert` with the full `perasWeight` boost and forwarded to `addPerasCertAsync`. Chain selection then re-evaluates all candidate fragments using the boosted weight, and if the attacker-chosen fork now outweighs the honest chain, the node switches to it. This constitutes a **bypass of Peras certificate validation** enabling unauthorized certificate acceptance and attacker-directed chain-selection manipulation — matching the "Critical: bypass of Peras voting or certificate checks" impact category.

---

### Likelihood Explanation

The attack requires only that the Peras miniprotocol version is negotiated between the attacker and the victim. The `hPerasCertDiffusionClient` handler is registered unconditionally in the production handler record. No privileged keys, stake majority, or operator access are needed. The attacker constructs a well-formed `PerasCert` CBOR value (the serialisation instance is public) and sends it over the object-diffusion miniprotocol. The stub validation guarantees acceptance. Likelihood is **high** once Peras is activated on any network running this codebase.

---

### Recommendation

1. Implement real cryptographic validation inside `validatePerasCert` before enabling the Peras miniprotocol in any production environment. At minimum: verify the certificate's aggregate signature, confirm the boosted block exists within the valid window, and check that the round number is current.
2. Resolve issue `https://github.com/tweag/cardano-peras/issues/120` before the Peras miniprotocol version is negotiated on mainnet or any public testnet.
3. Apply the same treatment to `validatePerasVote` — the current implementation only checks stake-distribution membership and performs no signature verification.
4. Add a guard in `makePerasCertPoolWriterFromChainDB` analogous to the empty-stake-distribution guard already present in `makePerasVotePoolWriterFromChainDB`, so that the certificate inbound path is explicitly disabled until real validation is in place.

---

### Proof of Concept

1. Connect to a target node that has negotiated the Peras object-diffusion miniprotocol version.
2. Craft a `PerasCert` value with `pcCertRound` set to the current Peras round and `pcCertBoostedBlock` set to the tip of a minority fork known to the target.
3. Serialise and send the certificate via the `hPerasCertDiffusionClient` channel.
4. `validatePerasCert` returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })` unconditionally.
5. The certificate is inserted into `PerasCertDB` and `addPerasCertAsync` is called.
6. Chain selection re-runs; the minority fork now carries the attacker-supplied weight boost and is preferred over the honest chain, causing the node to switch forks. [6](#0-5) [2](#0-1) [3](#0-2)
