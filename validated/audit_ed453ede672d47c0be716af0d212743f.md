### Title
Peras Vote and Certificate Acceptance Without Cryptographic Validation Enables Chain-Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`, `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Storage/PerasVoteDB/Impl.hs`)

### Summary
The Peras protocol extension's vote and certificate validation pipeline contains stub implementations that accept any vote or certificate without performing cryptographic checks (signature verification, VRF proof of committee membership). An unprivileged peer can inject fake Peras votes with arbitrary voter identities, causing the local node to forge a fraudulent quorum certificate and apply an unearned weight boost to a non-canonical chain during chain selection.

### Finding Description
The `BlockSupportsPeras` typeclass in `SupportsPeras.hs` provides default implementations for `validatePerasVote` and `validatePerasCert` that are explicitly marked as stubs pending real validation logic (all three TODOs reference issue `tweag/cardano-peras#120`).

`validatePerasVote` only checks whether the claimed voter ID appears in the stake distribution map — it performs no cryptographic signature verification and no VRF proof-of-eligibility check: [1](#0-0) 

`validatePerasCert` unconditionally wraps any incoming certificate in `Right` without inspecting its contents at all: [2](#0-1) 

The `implAddVote` function in `PerasVoteDB/Impl.hs` carries an explicit TODO acknowledging that the "non-trivial validation logic" required before storing a vote has not yet been implemented: [3](#0-2) 

Once a vote passes the trivial stake-presence check it is immediately inserted into the `PerasVoteDbState` and its stake is accumulated toward the quorum threshold: [4](#0-3) 

When accumulated stake crosses the quorum threshold, `updateCandidateVoteState` calls `forgePerasCert` and stores the resulting `ValidatedPerasCert` — which then contributes a weight boost to the target block during chain selection via `PerasWeight`: [5](#0-4) 

The `ValidatedPerasVote` type carries a `vpvVoteStake` field that is taken directly from the stake distribution lookup, meaning an attacker who controls a voter ID present in the distribution (even with minimal stake) can submit votes for arbitrary rounds and targets without any cryptographic proof: [6](#0-5) 

### Impact Explanation
A malicious peer can send a stream of Peras votes claiming to be from many distinct voter IDs that exist in the stake distribution. Because `validatePerasVote` performs no signature or VRF check, each vote is accepted as `ValidatedPerasVote` and stored. Once the accumulated `vpvVoteStake` values exceed the quorum threshold, the node automatically forges a `ValidatedPerasCert` for the attacker-chosen target block. That certificate is then used by the Peras chain-selection logic to apply a weight boost (`PerasWeight`) to the attacker's preferred chain, causing the honest node to prefer a non-canonical or adversarially-controlled chain over the honest chain. This is a bypass of Peras certificate/vote authorization that enables unauthorized certificate acceptance and chain-selection manipulation.

### Likelihood Explanation
The Peras vote diffusion miniprotocol is the direct network entry point. Any connected peer can submit `PerasVote` objects. The only gate before storage is the stake-distribution lookup, which is trivially satisfied for any voter ID that appears in the current epoch's stake snapshot. No key material, VRF proof, or BLS signature is required. The attack requires only network connectivity to a Peras-enabled node.

### Recommendation
1. Implement full cryptographic validation in `validatePerasVote`: verify the BLS/KES vote signature and, for non-persistent committee members, verify the VRF proof of eligibility against the epoch nonce and committee parameters (as already implemented in `WFALS.implVerifyVote` and `EveryoneVotes.implVerifyVote`).
2. Implement full cryptographic validation in `validatePerasCert`: verify the aggregate BLS signature and each voter's committee membership (as already implemented in `WFALS.implVerifyCert` and `EveryoneVotes.implVerifyCert`).
3. Remove the stub default implementations and require each `BlockSupportsPeras` instance to provide a concrete, cryptographically sound implementation.
4. Add the missing validation gate inside `implAddVote` (as noted by the existing TODO referencing issue #120) so that the DB itself rejects votes that fail cryptographic checks even if the caller omits pre-validation.

### Proof of Concept
1. Connect to a Peras-enabled node on a private testnet.
2. Enumerate voter IDs present in the current epoch's `PerasVoteStakeDistr`.
3. Craft `PerasVote` objects for each voter ID, all targeting the same attacker-chosen block point in the current round, with arbitrary (or zeroed) `pvSignature` and `pvEligibilityProof` fields.
4. Submit these votes via the Peras vote diffusion miniprotocol.
5. Because `validatePerasVote` only calls `lookupPerasVoteStake` and does not verify signatures, each vote is wrapped in `ValidatedPerasVote` with the real stake value from the distribution.
6. `implAddVote` stores each vote; `updatePerasRoundVoteStates` accumulates stake.
7. Once the quorum threshold is crossed, `forgePerasCert` is called and a `ValidatedPerasCert` is stored for the attacker's target block.
8. The Peras chain-selection logic applies the weight boost to the attacker's block, causing the node to prefer the attacker's chain. [7](#0-6) [8](#0-7)
