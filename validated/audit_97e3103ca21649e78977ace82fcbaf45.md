### Title
Zcash `execute_refund` Callable by Any Account Without Rate Limiting, Producing Multiple Stale MPC Signing Requests for the Same UTXO - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary
`execute_refund` carries no role restriction and is callable by any NEAR account after the timelock passes. On Zcash, the refund PSBT is non-deterministic (it embeds the current block height), so successive calls at different block heights produce different transaction IDs and thus distinct `BTCPendingInfo` entries for the same deposit UTXO. Multiple callers can each create their own stale refund pending transaction, all of which require operator intervention to clean up.

### Finding Description

**Public entry point — no role guard**

`execute_refund` in `contracts/satoshi-bridge/src/api/bridge.rs` carries only `#[payable]` and `#[pause(except(roles(Role::DAO)))]`. Any NEAR account that attaches the required storage deposit can call it once the timelock has elapsed. [1](#0-0) 

**Re-execution gate is intentionally permissive**

`load_refund_request_for_execute` in `contracts/satoshi-bridge/src/refund.rs` blocks re-execution only when the UTXO was claimed by a *deposit*. Once `execute_refund` has run once and set `executed = true`, the guard passes for every subsequent caller:

```rust
require!(
    !self.data().verified_deposit_utxo.contains(utxo_storage_key)
        || refund_request.executed,   // ← always true after first execution
    "UTXO already verified via deposit, cannot refund"
);
``` [2](#0-1) 

**Bitcoin is safe; Zcash is not**

On Bitcoin, `internal_execute_refund` builds the PSBT synchronously from fixed inputs and outputs. The resulting txid is deterministic, so a second call collides on the same `btc_pending_id` and is rejected with `"pending info already exist"`. [3](#0-2) 

The repository's own test confirms this: [4](#0-3) 

On Zcash, `internal_execute_refund` defers PSBT construction to an async callback that receives the current block height. The PSBT embeds `expiry_height = last_block_height + gap`, making the txid block-height-dependent. Two calls at different block heights produce two different txids and therefore two distinct `BTCPendingInfo` entries. [5](#0-4) 

**`require_pending_sign_capacity` does not prevent multi-account abuse**

`finalize_refund_with_psbt` checks pending-sign capacity against the *caller* captured at call time. Each distinct NEAR account has its own budget, so accounts A, B, C … can each call `execute_refund` once and each create a separate `BTCPendingInfo` (owned by A, B, C respectively) for the same UTXO. [6](#0-5) 

**Cleanup requires privileged operator action**

`remove_refund_pending_tx_id` — the only mechanism to purge stale refund pending transactions — is gated behind `#[trusted_relayer]`. Ordinary users cannot self-clean the stale entries; an operator must intervene for each one. [7](#0-6) 

### Impact Explanation
Multiple `BTCPendingInfo` entries accumulate in contract storage for the same deposit UTXO. Only one Zcash transaction can spend the UTXO; all others become permanently stale. Each stale entry consumes storage and holds a pending-sign slot, and none can be removed without a trusted-relayer call. This constitutes **stuck bridge state requiring operator intervention** (Medium).

### Likelihood Explanation
Any NEAR account can trigger this after the timelock passes by attaching the `required_balance_for_execute_refund()` deposit — no special role or leaked key is needed. An attacker with a handful of funded accounts can create multiple stale entries at negligible cost. The attack window is open indefinitely once the timelock elapses.

### Recommendation
In `load_refund_request_for_execute` (or at the top of `execute_refund`), add a guard that prevents re-execution once `executed == true` unless the caller holds a privileged role (DAO / RefundOperator):

```rust
if refund_request.executed {
    let caller = env::predecessor_account_id();
    require!(
        self.acl_has_any_role(
            vec![Role::DAO.into(), Role::RefundOperator.into()],
            caller
        ),
        "Refund already executed; only DAO/RefundOperator may re-execute"
    );
}
```

This preserves the intended "re-execute after consensus branch change" use-case for privileged operators while closing the public re-execution path.

### Proof of Concept
1. User deposits ZEC and calls `request_refund` with a valid Merkle proof; `RefundRequest` is stored with `executed = false`.
2. Timelock elapses.
3. Account A calls `execute_refund(utxo_storage_key)` at block height N → Zcash callback builds PSBT with `expiry_height = N + gap`, creates `BTCPendingInfo` id `tx_A`; `executed` is set to `true`.
4. Account B calls `execute_refund(utxo_storage_key)` at block height N+k → `load_refund_request_for_execute` passes (`executed == true`); callback builds PSBT with `expiry_height = N+k + gap`, creates `BTCPendingInfo` id `tx_B` (different txid).
5. Both `tx_A` and `tx_B` can be signed via `sign_btc_transaction` and broadcast to Zcash.
6. Only one UTXO exists; only one transaction confirms. The other `BTCPendingInfo` is permanently stale.
7. Operator must call `remove_refund_pending_tx_id` (trusted-relayer only) to purge the stale entry — stuck bridge state requiring operator intervention.

    pub(crate) fn internal_execute_refund(
        &mut self,
        utxo_storage_key: String,
        timelock_sec: u64,
        _chain_specific_data: Option<ChainSpecificData>,
    ) -> PromiseOrValue<()> {
        let refund_request = self.load_refund_request_for_execute(&utxo_storage_key, timelock_sec);
        let RefundExecutionInputs {
            outpoint,
            deposit_output,
            refund_amount,
        } = self.refund_execution_inputs(&refund_request);
        let refund_output = self.build_refund_output(&refund_request.refund_address, refund_amount);

        let mut psbt = PsbtWrapper::new(vec![outpoint], vec![refund_output]);
        psbt.set_input_utxo(vec![deposit_output]);

        let caller = env::predecessor_account_id();
        self.finalize_refund_with_psbt(
            caller,
            refund_request,
            psbt,
            refund_amount,
            utxo_storage_key,
        );
        PromiseOrValue::Value(())
    }
