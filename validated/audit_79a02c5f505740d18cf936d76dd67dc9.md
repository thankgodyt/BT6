### Title
Truncated Division in `normalize_amount` Permanently Locks User Funds When Token Fee Is Zero — (`near/omni-bridge/src/lib.rs`)

---

### Summary

The `normalize_amount` helper in the NEAR omni-bridge contract uses integer floor division to scale a NEAR-side token amount down to the destination chain's decimal precision. When a user initiates an outbound transfer (NEAR → EVM/Solana/Starknet) with `fee = 0`, any sub-unit remainder ("dust") produced by this division is permanently locked inside the bridge escrow and is never recoverable by the user or any other party.

---

### Finding Description

`normalize_amount` is defined as:

```rust
// near/omni-bridge/src/lib.rs  line 2784-2787
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [1](#0-0) 

It is called inside `sign_transfer` on the user's net amount (total minus fee):

```rust
// near/omni-bridge/src/lib.rs  line 475-480
let amount_to_transfer = Self::normalize_amount(
    transfer_message
        .amount_without_fee()
        .near_expect(BridgeError::InvalidFee),
    decimals,
);
``` [2](#0-1) 

The code's own comment acknowledges the two outcomes of this floor division:

> *"When fee > 0, dust is absorbed into the fee via `claim_fee`. When fee = 0, dust stays locked/burned."* [3](#0-2) 

**When `fee > 0`** the dust is recoverable: `claim_fee_callback` computes `fee = transfer_message.amount.0 − denormalized_amount` and pays it to the relayer. [4](#0-3) 

**When `fee = 0`** there is no `claim_fee` call, so the dust is never extracted. For non-deployed (locked) tokens it stays locked in the bridge forever; for deployed (minted) tokens it is burned. Neither path returns the dust to the user.

The `amount_without_fee` helper is a simple subtraction:

```rust
// near/omni-types/src/lib.rs  line 593-595
pub fn amount_without_fee(&self) -> Option<u128> {
    self.amount.0.checked_sub(self.fee.fee.0)
}
``` [5](#0-4) 

When `fee = 0`, `amount_without_fee()` returns the full transfer amount, and the entire dust remainder is silently discarded.

---

### Impact Explanation

The maximum dust per transfer is `10^(origin_decimals − decimals) − 1` units of the NEAR-side token. For a NEAR-native token with 24 decimals bridged to an EVM token with 18 decimals (`diff = 6`), the maximum dust is `10^6 − 1` yoctoNEAR ≈ 0.000001 NEAR per transfer. For a 12-decimal gap (e.g., 18-decimal NEAR token → 6-decimal EVM token), the maximum dust is `10^12 − 1` units, which equals 0.000001 of the NEAR-side token per transfer.

While each individual loss is small, the funds are **permanently and irrecoverably locked** in the bridge escrow with no admin escape hatch, matching the "permanent freezing of bridged funds" criterion. Across many transfers the aggregate locked dust grows monotonically and is never claimable.

---

### Likelihood Explanation

The condition is triggered whenever:
1. A user calls `ft_transfer_call` → `ft_on_transfer` → `init_transfer` with `fee = 0` (a common, user-controlled parameter), **and**
2. The bridged token has `origin_decimals > decimals` (e.g., any NEAR-native token bridged to a lower-precision EVM representation).

Both conditions are reachable by any unprivileged user with no special role or access. The `fee = 0` path is explicitly tested in the integration suite (`test_native_fee` uses `fee: U128(0)`), confirming it is a supported and expected usage. [6](#0-5) 

---

### Recommendation

Before calling `normalize_amount`, verify that `amount % 10^diff_decimals == 0`, or refund the remainder to the sender. Alternatively, reject transfers where the normalized amount would differ from the original (i.e., where dust would be produced) when `fee = 0`, so users are forced to either round their amount or set a non-zero fee to absorb the dust.

---

### Proof of Concept

**Setup**: NEAR-native token with `origin_decimals = 18`, EVM token with `decimals = 6` (`diff = 12`).

**User action**: `ft_transfer_call` with `amount = 1_000_000_000_001` (1 micro-token + 1 unit), `fee = 0`.

**Execution**:
- `amount_without_fee()` = `1_000_000_000_001`
- `normalize_amount(1_000_000_000_001, {decimals:6, origin_decimals:18})` = `1_000_000_000_001 / 10^12` = **`1`** (dust = `1` unit discarded)
- `amount_to_transfer = 1` → passes the `> 0` guard
- MPC signs a payload for `amount = 1` on EVM
- The `1` unit of dust remains locked in the bridge with no recovery path

The user sent `1_000_000_000_001` units and the destination chain receives `1_000_000_000_000` units worth; the `1`-unit remainder is permanently frozen.
