### Title
Peras Certificate Validation Permanently Bypassed: Degenerate `validatePerasCert` Always Returns `Right` — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The sole production `BlockSupportsPeras` instance unconditionally accepts every inbound Peras certificate without performing any cryptographic verification. Because no Cardano-specific override exists, an unprivileged peer can inject an arbitrarily crafted certificate that will be stored and used to boost the weight of a non-canonical chain, causing an honest node to prefer it over the canonical chain.

---

### Finding Description

The `BlockSupportsPeras` type class declares `validatePerasCert` as the mandatory gate that must be passed before a certificate is stored and its weight boost applied to chain selection. The only production instance — a blanket `StandardHash blk` instance — unconditionally returns `Right` with the full weight boost, skipping every cryptographic check:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This is the **only** `BlockSupportsPeras` instance in the production codebase; a grep across all `.hs` files confirms no Cardano-specific override exists. [2](#0-1) 

The companion function `getPerasCertInBlock` is similarly stubbed to always return `Nothing`, meaning certificates embedded in blocks are never extracted either:

```haskell
-- TODO: extract actual Peras certificates from blocks when the HFC plumbing
-- is in place.
getPerasCertInBlock _ = Nothing
``` [3](#0-2) 

The certificate ingestion path is fully wired in production. `addPerasCertAsync` is exported from `ChainSel` and is part of the public `ChainDB` API: [4](#0-3) 

The `ChainDB` API exposes `addPerasCertAsync` as a first-class operation that triggers chain selection re-evaluation: [5](#0-4) 

The vote pool writer, which feeds into this path, already calls `validatePerasVote` (the analogous vote-level check), confirming the validation hooks are live: [6](#0-5) 

The analogy to the external report is direct: just as `SwapToRewardDenom` was restricted to the dispatcher but the dispatcher never called it (making the swap permanently inaccessible), here `validatePerasCert` is the mandatory validation gate but the only production instance makes it permanently a no-op — the validation is permanently bypassed rather than permanently unreachable.

---

### Impact Explanation

**High — Chain selection manipulation via forged Peras certificates.**

Peras certificates carry a weight boost (`perasWeight`) that is applied during chain selection to prefer the boosted chain. Because `validatePerasCert` always returns `Right`, a peer can send a certificate claiming to boost any block it chooses. The certificate will be stored and its weight applied, causing the receiving node to prefer a non-canonical chain over the honest canonical chain. This violates the chain selection security assumption that only legitimately quorum-signed certificates may influence chain preference.

---

### Likelihood Explanation

**Medium.** The Peras certificate diffusion infrastructure is fully wired in the production codebase and the `addPerasCertAsync` path is reachable from any connected peer. The only mitigating factor is that Peras is under active development and may not yet be activated on mainnet. Once activated, any peer can exploit this without any special privileges, keys, or stake.

---

### Recommendation

Implement real cryptographic validation inside `validatePerasCert` before the Peras feature is activated. The `EveryoneVotes` committee scheme already provides a complete `implVerifyCert` function with aggregate-signature verification: [7](#0-6) 

The `validatePerasCert` implementation should delegate to this (or the equivalent for the production committee scheme) rather than unconditionally returning `Right`. The tracked issue is `https://github.com/tweag/cardano-peras/issues/120`.

---

### Proof of Concept

1. Connect a malicious peer to a node running the Peras-enabled build.
2. Craft a `PerasCert` pointing to any block on a minority fork (e.g., `pcCertBoostedBlock = <minority fork tip>`).
3. Send it via the certificate diffusion mini-protocol, which calls `addPerasCertAsync`.
4. `addPerasCertAsync` calls `validatePerasCert`; the degenerate instance returns `Right ValidatedPerasCert{vpcCertBoost = perasWeight params}` unconditionally.
5. The certificate is stored and its weight boost is applied during the next chain selection pass.
6. If `perasWeight` is large enough, the node switches to the minority fork, diverging from the honest canonical chain.

-- | Verify a certificate attesting the winner of a given election
implVerifyCert ::
  forall crypto.
  CryptoSupportsAggregateVoteSigning crypto =>
  VotingCommittee crypto EveryoneVotes ->
  Cert crypto EveryoneVotes ->
  Either
    (VotingCommitteeError crypto EveryoneVotes)
    (NE [EligibilityWitness crypto EveryoneVotes])
implVerifyCert committee = \case
  EveryoneVotesCert electionId candidate voters aggSig -> do
    -- Traverse the list of voters in ascending seat index order, collecting:
    -- 1. their membership status
    -- 2. their vote verification keys (to verify the aggregate vote signature)
    (members, voteVerificationKeys) <-
      fmap munzip . flip traverse (NESet.toAscList voters) $ \case
        seatIndex
          | Just (_, voterPublicKey, voterStake, _) <-
              getCandidateIfSeatWithinBounds seatIndex (extWFAStakeDistr committee) -> do
              let voterVerificationKey =
                    getVoteVerificationKey (Proxy @crypto) voterPublicKey
              case nonZero voterStake of
                Nothing ->
                  Left (PoolHasNoStake seatIndex)
                Just nonZeroVoterStake ->
                  pure
                    ( EveryoneVotesMember
                        seatIndex
                        nonZeroVoterStake
                    , voterVerificationKey
                    )
          | otherwise ->
              Left (MissingSeatIndex seatIndex)
    -- Verify aggregate signature
    aggVerificationKey <-
      bimap CryptoError id $ do
        aggregateVoteVerificationKeys
          (Proxy @crypto)
          voteVerificationKeys
    bimap InvalidCertSignature id $
      verifyAggregateVoteSignature
        (Proxy @crypto)
        aggVerificationKey
        electionId
        candidate
        aggSig
