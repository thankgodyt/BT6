### Title
Stub `validatePerasCert` Unconditionally Accepts Any Peras Certificate, Enabling Forged-Certificate Chain Selection Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance ships a stub `validatePerasCert` that unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or semantic checks. Any unprivileged peer can therefore send a crafted `PerasCert` over the Peras certificate diffusion mini-protocol, have it accepted as "validated," and cause the receiving node to re-run chain selection with an artificially boosted adversarial fork — making the node prefer a non-canonical chain.

---

### Finding Description

`BlockSupportsPeras` is the typeclass that governs Peras certificate and vote handling for all block types. Its universal instance (the only instance in the codebase) implements `validatePerasCert` as a stub that always succeeds:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is the **only** instance; no Cardano-specific override exists. The grep confirms `validatePerasCert` is defined only in `SupportsPeras.hs` and called only in `PerasCert.hs`.

The inbound certificate processing path in `processCerts` calls this stub directly:

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _) ->
      throw (PerasCertValidationError errs)
``` [2](#0-1) 

Both production pool writers (`makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB`) pass `validatePerasCert mkPerasParams` as the validator: [3](#0-2) [4](#0-3) 

Once a forged certificate passes this non-validation, `chainSelSync` adds it to the `PerasCertDB` and immediately triggers chain selection for the boosted block:

```haskell
-- Trigger chain selection for the boosted block.
lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [5](#0-4) 

Chain selection then uses `preferAnchoredCandidate` with the updated `PerasWeightSnapshot`. When the snapshot is non-empty (Peras enabled), it computes `wsvTotalWeight = blockNo + weightBoost` and prefers the heavier chain:

```haskell
preferCandidate cfg ours cand =
  case compare (wsvTotalWeight ours) (wsvTotalWeight cand) of
    LT -> ShouldSwitch (Heavier $ Comparing (wsvTotalWeight ours) (wsvTotalWeight cand))
    ...
``` [6](#0-5) 

The `perasWeight` assigned by the stub is taken directly from `PerasParams`, which can be a large value, easily overwhelming the honest chain's block-number advantage. [7](#0-6) 

---

### Impact Explanation

When Peras is enabled, an unprivileged peer can send a single crafted `PerasCert` naming any block hash present in the receiving node's VolatileDB. The certificate bypasses all validation, is stored, and triggers chain selection. The adversarial fork containing the boosted block now has `blockNo + perasWeight` total weight, which can exceed the honest chain's block number. The node switches to the adversarial fork — a chain selection safety failure driven entirely by a forged network message.

This maps to the **High** impact class: *"Chain selection, rollback, forecast, genesis, or header-state bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

---

### Likelihood Explanation

The attack requires Peras to be enabled (not the default today, but the intended production configuration). Once enabled, the attack requires only: (1) a TCP connection to the target node, (2) knowledge of any block hash in the node's VolatileDB (trivially obtained via ChainSync), and (3) crafting a `PerasCert` CBOR message with that hash. No stake, no keys, no mining power needed. Likelihood is **High** once Peras is activated.

---

### Recommendation

1. Replace the stub `validatePerasCert` with a real implementation that verifies the aggregate BLS signature over `(roundNo, boostedBlock)` against the aggregate public key of the claimed voters, checks quorum, and validates voter eligibility — mirroring the complete checks already present in `implVerifyCert` for `WFALS` and `EveryoneVotes`.
2. Until a real implementation is ready, gate `processCerts` so that it rejects all inbound certificates when Peras is enabled but `validatePerasCert` is still a stub (e.g., always return `Left` rather than `Right`).
3. Similarly audit `validatePerasVote`, which only checks stake-distribution membership but skips signature verification. [8](#0-7)

### Proof of Concept

**Attacker-controlled entry path:**

1. Attacker connects to a Peras-enabled node as a peer via the Peras certificate diffusion mini-protocol (`ObjectDiffusion`).
2. Attacker observes a block hash `H` on a short adversarial fork via ChainSync (or sends their own valid block to the node first).
3. Attacker crafts a `PerasCert { pcCertRound = R, pcCertBoostedBlock = BlockPoint slot H }` with an arbitrary (invalid) aggregate signature and sends it.
4. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }` unconditionally. [7](#0-6) 
5. The certificate is stored in `PerasCertDB`; `chainSelSync` triggers `chainSelectionForBlock` for block `H`. [5](#0-4) 
6. `preferAnchoredCandidate` computes the adversarial fork's total weight as `blockNo(H) + perasWeight`, which exceeds the honest chain's block number. [6](#0-5) 
7. The node switches to the adversarial fork, rolling back up to `k` honest blocks.
