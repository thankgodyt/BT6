Audit Report

## Title
Missing Supported-Token Validation in `init_transfer` Enables Permanent Fund Lock — (File: `starknet/src/omni_bridge.cairo`)

## Summary

`OmniBridge.init_transfer()` accepts any ERC20 `token_address` without verifying the token is registered in the bridge. Tokens transferred in are locked in escrow and an `InitTransfer` event is emitted, but the NEAR-side `fin_transfer_callback` panics when it cannot find decimals for the unregistered token. Because the Starknet contract has no refund or recovery path, the locked tokens are permanently unrecoverable.

## Finding Description

`init_transfer` (lines 281–331) performs only three semantic checks before accepting tokens: pause flag, `amount > 0`, and `fee < amount`. [1](#0-0) 

The `is_bridge_token` helper (lines 378–380) checks `starknet_to_near_token` only to decide *how* to handle the token (burn vs. lock), not *whether* the token is supported. [2](#0-1) 

There is no check that `token_address` has a registered NEAR counterpart in `starknet_to_near_token` (for bridge-deployed tokens) or in any whitelist of approved native tokens. Any ERC20 whose `transfer_from` succeeds will be accepted and locked.

On the NEAR side, `fin_transfer_callback` immediately panics when it cannot find decimals for the unregistered token: [3](#0-2) 

The Starknet contract contains no `refund`, `rescue`, `recover`, `unlock`, or `emergency` function. Once locked, the tokens have no recovery path.

## Impact Explanation

**Critical — Permanent freezing of bridged funds.** Any user who calls `init_transfer` with a token not registered in the NEAR bridge's `token_decimals` map will have their tokens permanently locked in the Starknet bridge contract. This directly matches the allowed Critical impact class: "permanent freezing of bridged funds."

## Likelihood Explanation

**Medium.** The function is publicly callable by any Starknet account with no role restriction. A user could accidentally supply a token that exists on Starknet but has not yet been registered on NEAR (e.g., a newly listed token, or a token whose binding is pending). No privileged access is required. The scenario is realistic in normal bridge usage, not just adversarial.

## Recommendation

Add an explicit supported-token check at the top of `init_transfer`. Require that the token has a registered NEAR counterpart:

```cairo
let near_token_id = self.starknet_to_near_token.read(token_address);
assert(near_token_id.len() > 0, 'ERR_UNSUPPORTED_TOKEN');
```

This reuses the existing `starknet_to_near_token` mapping (already populated by `deploy_token`) and adds zero storage overhead. Alternatively, maintain a separate whitelist for approved native (non-bridge-deployed) tokens and validate against it before accepting any transfer.

## Proof of Concept

1. `token_X` is a valid ERC20 on Starknet but has **not** been registered in the NEAR bridge (no entry in `token_decimals` or `token_address_to_id`).
2. User calls:
   ```
   OmniBridge.init_transfer(token_X, 1000, 0, 0, "recipient.near", "")
   ```
3. `is_bridge_token(token_X)` returns `false` (no `starknet_to_near_token` entry).
4. `IERC20Dispatcher { contract_address: token_X }.transfer_from(caller, bridge, 1000)` succeeds — 1000 `token_X` are now held by the bridge.
5. `InitTransfer` event is emitted with `token_address = token_X`.
6. Relayer submits the proof to NEAR `fin_transfer`.
7. NEAR `fin_transfer_callback` executes `self.token_decimals.get(&token_X).near_expect(BridgeError::TokenDecimalsNotFound)` → **panics and reverts**.
8. The 1000 `token_X` remain permanently locked in the Starknet bridge. No refund is issued.

**Local test plan:** Deploy a mock ERC20 on a Starknet devnet without registering it in the NEAR bridge. Call `init_transfer` with that token. Confirm tokens are transferred to the bridge contract. Simulate the NEAR `fin_transfer_callback` with the emitted event data and confirm it panics with `TokenDecimalsNotFound`. Confirm no recovery function exists on the Starknet contract.
