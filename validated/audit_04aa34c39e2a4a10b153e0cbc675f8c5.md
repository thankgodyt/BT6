### Title
`safe_mint_callback` misclassifies `safe_mint` panics as successful mints, permanently locking depositor BTC without minting nBTC — (`contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

---

### Summary

When `safe_mint` panics (e.g., because `recipient_id` equals the bridge's own account ID), `safe_mint_callback` incorrectly treats the panic as a successful mint. The UTXO is permanently added to the bridge's available pool and marked in `verified_deposit_utxo`, but no nBTC is ever minted to the user. The depositor's BTC is irrecoverably locked with no refund path.

---

### Finding Description

The `safe_mint_callback` function determines success via the helper `is_refund_required()`:

```rust
// contracts/satoshi-bridge/src/btc_light_client/deposit.rs
fn is_refund_required() -> bool {
    match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
        Ok(value) => {
            if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {
                amount.0 == 0
            } else {
                false  // Unexpected case: don't refund
            }
        }
        Err(_) => false,  // Unexpected case: don't refund  ← BUG
    }
}
``` [1](#0-0) 

The `Err(_)` arm fires whenever the `safe_mint` cross-contract call panics. Returning `false` means `is_refund_required() = false`, so `is_success = !false = true` in `safe_mint_callback`:

```rust
let is_success = !is_refund_required();
...
if is_success {
    self.internal_set_utxo(&pending_utxo_info.utxo_storage_key, pending_utxo_info.utxo);
}
``` [2](#0-1) 

When `safe_mint` panics, NEAR rolls back all state changes inside that call — no tokens are deposited, no transfer occurs, no nBTC is minted. Yet `safe_mint_callback` proceeds to permanently commit the UTXO to the bridge's available set.

The concrete panic trigger is in `safe_mint` itself:

```rust
// contracts/nbtc/src/lib.rs
require!(
    account_id != self.bridge_id,
    "safe_mint: account_id must not be the bridge"
);
self.token.internal_deposit(&self.bridge_id, amount.into());
``` [3](#0-2) 

If `recipient_id` in the `DepositMsg` equals the bridge contract's account ID, `safe_mint` panics before any token state is mutated. The panic propagates as an `Err` to `safe_mint_callback`, which then falsely records success.

There is no validation of `recipient_id` anywhere in the deposit entry path:

```rust
// contracts/satoshi-bridge/src/btc_light_client/deposit.rs
self.internal_safe_verify_deposit(
    deposit_amount, ...,
    deposit_msg.recipient_id,   // ← passed through unchecked
    safe_deposit_msg,
)
``` [4](#0-3) 

And `get_user_deposit_address` accepts any `DepositMsg` without validating `recipient_id`: [5](#0-4) 

**Contrast with the standard flow**: `mint_callback` (used by `verify_deposit`) correctly uses `is_promise_success()`, which returns `false` on panic, and removes the UTXO from `verified_deposit_utxo` on failure:

```rust
// contracts/satoshi-bridge/src/nbtc/mint.rs
let is_success = is_promise_success();
if is_success { ... } else {
    self.data_mut().verified_deposit_utxo.remove(&pending_utxo_info.utxo_storage_key);
}
``` [6](#0-5) 

`safe_mint_callback` has no equivalent rollback on panic.

---

### Impact Explanation

When `safe_mint` panics:
- The UTXO is inserted into `verified_deposit_utxo` (done in `verify_safe_deposit_callback` before the call) and into the bridge's available UTXO pool (done in `safe_mint_callback` on false-success).
- No nBTC is minted to the user.
- Because the UTXO is in `verified_deposit_utxo`, `request_refund` is permanently blocked ("UTXO already verified via deposit").
- The user's BTC is irrecoverably locked in the bridge's UTXO pool with no recovery mechanism short of operator intervention.

This matches the allowed impact: **permanent locking of user funds** / **broken callback rollback requiring operator intervention**.

---

### Likelihood Explanation

The trigger is reachable by any bridge user without any privileged role:

1. `get_user_deposit_address` is a public view function — any account can call it with `recipient_id = bridge_contract_id` and receive a valid deposit address.
2. The user sends BTC to that address on-chain.
3. A relayer (who does not validate `recipient_id`) submits the proof via `safe_verify_deposit` or `verify_deposit_v2`.
4. The panic fires and the UTXO is permanently consumed without minting nBTC.

The scenario can also be triggered by any future panic inside `safe_mint` (e.g., an overflow in `internal_deposit` if total supply approaches `u128::MAX`, or any future nBTC contract change that introduces a new panic path), making the surface broader than just the `bridge_id` check.

---

### Recommendation

**Option 1 (preferred):** Validate `recipient_id` in `internal_safe_verify_deposit_entry` before dispatching the cross-contract call:

```rust
require!(
    deposit_msg.recipient_id != self.internal_config().nbtc_account_id
        && deposit_msg.recipient_id != env::current_account_id(),
    "recipient_id must not be the bridge or token contract"
);
```

**Option 2:** Change `is_refund_required` to treat `Err` (panic) as a refund-required condition, mirroring the standard `mint_callback` behavior:

```rust
Err(_) => true,  // safe_mint panicked → no tokens minted → refund required
```

This requires ensuring the rollback path in `safe_mint_callback` (burn + NEAR refund) is safe to execute even when `safe_mint` panicked before depositing tokens — which it is, since the bridge's nBTC balance would be zero for this deposit and the burn call would simply fail harmlessly (or be guarded).

---

### Proof of Concept

```
1. User calls get_user_deposit_address(DepositMsg {
       recipient_id: "<bridge_contract_id>",
       safe_deposit: Some(SafeDepositMsg { msg: "" }),
       refund_address: Some("bc1q..."),
       ...
   })
   → Bridge returns a valid BTC deposit address (no recipient_id validation)

2. User sends N satoshis to that address on Bitcoin.

3. Relayer calls safe_verify_deposit(deposit_msg, tx_bytes, vout, ...)
   → verify_safe_deposit_callback: UTXO inserted into verified_deposit_utxo ✓
   → ext_nbtc::safe_mint(bridge_id, N, None) called

4. Inside safe_mint:
   require!(account_id != self.bridge_id, ...)  ← PANIC
   (all state changes in safe_mint rolled back by NEAR runtime)

5. safe_mint_callback fires:
   is_refund_required() → Err(_) → false
   is_success = !false = true
   → internal_set_utxo(...) called  ← UTXO permanently committed

6. Result:
   - verified_deposit_utxo contains the UTXO key
   - Bridge UTXO pool contains the UTXO
   - User nBTC balance: 0
   - request_refund → panics "UTXO already verified via deposit"
   - User's BTC permanently locked, no recovery path
```
