Audit Report

## Title
Reentrancy via Hookable ERC20 `transferFrom` Causes Nonce Collision and Permanent Freezing of Bridged Funds — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`OmniBridge.initTransfer` increments `currentOriginNonce` before making an external call to a user-supplied ERC20 token, but reads `currentOriginNonce` from storage — not a captured local variable — when passing it to `initTransferExtension` and `emit BridgeTypes.InitTransfer`. A malicious ERC20 with a `transferFrom` hook can reenter `initTransfer`, increment `currentOriginNonce` a second time, and cause both the outer and inner calls to emit `InitTransfer` events carrying the same (post-reentrant) nonce. The NEAR bridge, which relies solely on `InitTransfer` events, processes one and permanently ignores the other, freezing the corresponding tokens in the bridge contract.

## Finding Description

`OmniBridge.initTransfer` (lines 373–437) has no `nonReentrant` modifier and no `ReentrancyGuardUpgradeable` in its inheritance chain. The execution order is:

1. **Line 381**: `currentOriginNonce += 1` — incremented to N.
2. **Lines 407–411** (else branch): `IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount)` — external call to an arbitrary, user-supplied token address.
3. **Lines 415–425**: `initTransferExtension(..., currentOriginNonce, ...)` — reads `currentOriginNonce` from storage.
4. **Lines 427–436**: `emit BridgeTypes.InitTransfer(..., currentOriginNonce, ...)` — reads `currentOriginNonce` from storage.

Because `currentOriginNonce` is never captured into a local variable before the external call, any reentrant call that increments it corrupts the value seen by the outer call's extension invocation and event emission.

**Reentrant execution trace:**

| Step | `currentOriginNonce` | Action |
|---|---|---|
| Outer call enters | N-1 → **N** | `currentOriginNonce += 1` |
| `safeTransferFrom` fires hook | — | Malicious token reenters `initTransfer` |
| Inner call enters | N → **N+1** | `currentOriginNonce += 1` |
| Inner `safeTransferFrom` | — | Hook stops recursion |
| Inner `initTransferExtension` | reads **N+1** | Extension with nonce N+1 |
| Inner `emit InitTransfer` | reads **N+1** | Event with nonce N+1 |
| Inner call returns | — | — |
| Outer `initTransferExtension` | reads **N+1** | Extension with nonce N+1 ← **collision** |
| Outer `emit InitTransfer` | reads **N+1** | Event with nonce N+1 ← **collision** |

Nonce N is **never emitted**. Nonce N+1 is **emitted twice** with different transfer parameters.

The same structural flaw exists in `initTransfer1155` (lines 439–490): `currentOriginNonce` is incremented at line 448, an external `IERC1155.safeTransferFrom` is made at lines 458–464 (which triggers `onERC1155Received` on the recipient — here `address(this)` — but a malicious ERC1155 can also hook the sender side), and `currentOriginNonce` is read from storage at lines 471 and 483.

The `customMinters` path (lines 394–399) also calls `IERC20(tokenAddress).safeTransferFrom` to a user-supplied token before the nonce is used in the extension/emit, so it shares the same exposure.

The CLAUDE.md invariant explicitly states: *"Fields must not be collapsible (e.g. two different transfers must never produce the same event data)"* — this invariant is broken by the reentrancy.

## Impact Explanation

The `InitTransfer` event is the sole data source the NEAR bridge uses to finalize inbound transfers from EVM chains. When two events share the same `originNonce`, the NEAR bridge processes one and permanently ignores the other. The ERC20 tokens transferred to the bridge in the ignored call are locked with no release path. This constitutes **permanent freezing of bridged funds across EVM flows**, matching the critical impact category.

## Likelihood Explanation

`initTransfer` accepts any ERC20 token address with no whitelist for non-bridge tokens. An attacker deploys a malicious ERC20 whose `transferFrom` implementation reenters `initTransfer` once before returning `true`. No admin compromise, no front-running of other users, and no special permissions are required. The bridge is explicitly designed to be permissionless for `initTransfer`. The attack is repeatable and can target any nonce range.

## Recommendation

Capture `currentOriginNonce` into a local variable immediately after incrementing it, before any external call, and use that local variable exclusively for all subsequent reads within the function:

```solidity
function initTransfer(...) external payable whenNotPaused(PAUSED_INIT_TRANSFER) {
    currentOriginNonce += 1;
    uint64 nonce = currentOriginNonce; // capture before any external call
    // ...
    IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);

    initTransferExtension(msg.sender, tokenAddress, nonce, ...);
    emit BridgeTypes.InitTransfer(msg.sender, tokenAddress, nonce, ...);
}
```

Apply the identical fix to `initTransfer1155`. Alternatively, add OpenZeppelin's `ReentrancyGuardUpgradeable` to the inheritance chain and apply `nonReentrant` to both functions (accounting for the `__gap` storage layout requirement noted in SECURITY.md L-04).
