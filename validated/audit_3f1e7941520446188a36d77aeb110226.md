### Title
Peras Certificate Validation Bypass: `validatePerasCert` Stub Unconditionally Accepts All Peer-Supplied Certificates — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `BlockSupportsPeras` instance for all block types contains a stub implementation of `validatePerasCert` that unconditionally returns `Right` for every certificate it receives, performing no cryptographic, committee-membership, round-number, or block-point checks. Any unprivileged peer can send a crafted `PerasCert` through the Peras certificate diffusion mini-protocol; the certificate will pass "validation" and be injected into chain selection with a full Peras weight boost, allowing an attacker to manipulate chain selection without holding any stake or committee membership.

### Finding Description

The `BlockSupportsPeras` instance declared for all `StandardHash blk` types in `SupportsPeras.hs` is explicitly marked as a degenerate TODO stub:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

This stub accepts every certificate unconditionally and assigns it the full configured Peras weight boost (`perasWeight params`). No signature, no committee membership, no round-number, and no boosted-block-point check is performed.

The attacker-controlled entry path is the Peras certificate diffusion mini-protocol handler in `NodeToNode.hs`:

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      ...
``` [2](#0-1) 

This handler is wired to every untrusted NTN peer. Inbound certificates flow through `makePerasCertPoolWriterFromChainDB`, which calls `validatePerasCert` before forwarding accepted certificates to `addPerasCertAsync`:

```haskell

  ...
  ChainDbEnv m blk ->
  WithArrivalTime (ValidatedPerasCert blk) ->
  m (AddPerasCertPromise m)
addPerasCertAsync CDB{cdbTracer, cdbChainSelQueue} =
  addPerasCertToQueue ...
``` [3](#0-2) 

Once enqueued, the certificate is processed by `chainSelSync`, which uses the Peras weight snapshot (`getPerasWeightSnapshot`) to influence `preferAnchoredCandidate` during chain selection: [4](#0-3) 

The full exploit path is:

1. Attacker peer connects via NTN (no privilege required).
2. Attacker sends a crafted `PerasCert` with an arbitrary `pcCertBoostedBlock` pointing to a non-canonical block.
3. `validatePerasCert` returns `Right` unconditionally.
4. The certificate is enqueued via `addPerasCertAsync` with `vpcCertBoost = perasWeight params`.
5. Chain selection reads the Peras weight snapshot and assigns the attacker-chosen block a weight boost.
6. The node may prefer the attacker's non-canonical chain over the honest canonical chain.

The analog to the external report is direct: just as `setHooks` in `Vault.sol` allowed arbitrary user-supplied hooks to execute without restriction, `validatePerasCert` here allows arbitrary peer-supplied certificates to be accepted without any cryptographic or committee restriction, with the accepted certificate then influencing a critical consensus state transition (chain selection weight).

### Impact Explanation

**Critical — Bypass of Peras certificate validation enabling unauthorized certificate acceptance and chain selection manipulation.**

An unprivileged peer can inject certificates for any block of its choice, causing the victim node to assign a Peras weight boost to a non-canonical block. If the boosted block's chain becomes preferred, the node will switch to a fork chosen by the attacker, constituting a consensus safety failure: the node accepts an invalid ledger state derived from an attacker-selected chain. This maps directly to the allowed critical impact: "Bypass of … certificate … checks … that enables unauthorized … certificate acceptance."

### Likelihood Explanation

**High.** The attack requires only a standard NTN peer connection — no stake, no keys, no privileged access. The Peras certificate diffusion mini-protocol is active in the production `mkHandlers` path for all NTN peers. The stub is the only `BlockSupportsPeras` instance in the codebase (it covers all `StandardHash blk` types), so there is no override with real validation. Any peer that can connect to the node can trigger this.

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that checks:
- Cryptographic signature of the certificate against the committee's verification keys.
- Committee membership and quorum threshold for the claimed round.
- That `pcCertBoostedBlock` is a known, valid block on a plausible chain.
- That `pcCertRound` is within the expected range relative to the current slot.

Until real validation is implemented, the certificate diffusion inbound handler should be disabled or should reject all inbound certificates rather than accepting them unconditionally. The TODO at `https://github.com/tweag/cardano-peras/issues/120` must be resolved before the Peras certificate diffusion path is exposed to untrusted peers.

### Proof of Concept

1. Connect to a target node as an NTN peer.
2. Send a `PerasCert` message via the Peras certificate diffusion mini-protocol with:
   - `pcCertRound` = any round number
   - `pcCertBoostedBlock` = the `Point` of a non-canonical block already in the node's VolatileDB
3. Observe that `validatePerasCert` returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }` without any check.
4. The certificate is enqueued via `addPerasCertAsync` and processed by `chainSelSync`.
5. The Peras weight snapshot now includes a boost for the attacker-chosen block.
6. On the next chain selection event, `preferAnchoredCandidate` uses the boosted weight, potentially causing the node to switch to the non-canonical chain.
