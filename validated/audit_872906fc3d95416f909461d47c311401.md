### Title
`safe_mint` deposits nBTC to bridge balance before account-registration check, permanently stranding tokens when recipient is unregistered — (`contracts/nbtc/src/lib.rs`)

---

### Summary

The `safe_mint` function in the nBTC token contract unconditionally credits `amount` nBTC to the bridge's own token balance (`bridge_id`) **before** checking whether the recipient account is registered. When the recipient is unregistered, the function silently returns `U128(0)` without transferring the tokens. Because NEAR cross-contract call reverts are not atomic across contract boundaries, the bridge contract's callback panic rolls back only the bridge's state — the nBTC token contract's `internal_deposit` to `bridge_id` is **not** rolled back. The minted nBTC is permanently stranded in the bridge's balance, the user receives nothing, and the 1:1 BTC-backing invariant is broken.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, `safe_mint` (lines 101–124):

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into()); // ← state mutation in nBTC contract

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));                   // ← tokens never leave bridge_id
    }
    ...
}
``` [1](#0-0) 

The ordering is wrong: `internal_deposit(&self.bridge_id, amount)` is a committed state write in the nBTC token contract. It executes before the account-registration guard. When the guard fires and the function returns `U128(0)`, the bridge contract's callback is expected to panic (the wiki documents the safe-deposit path as "reverts the whole transaction if minting fails"). However, NEAR's cross-contract execution model means that a panic in the bridge contract's callback only rolls back **the bridge contract's** state — the nBTC contract's `internal_deposit` is already finalized and is **not** rolled back.

The analogous asymmetry to M-04 is:

| Stage | PrePO M-04 | This bridge |
|---|---|---|
| Entry | NFT holder allowed to deposit collateral | User allowed to deposit BTC (safe_deposit path) |
| Exit | NFT holder blocked from redeeming (only account-list checked) | User receives no nBTC (tokens stranded in bridge_id) |
| Root cause | Different access-control checks at deposit vs. redeem | State mutation before guard; cross-contract revert non-atomicity |

---

### Impact Explanation

1. **Broken 1:1 backing invariant**: The bridge's nBTC balance (`bridge_id`) grows by `amount` without a corresponding verified BTC deposit. The total nBTC supply is inflated relative to locked BTC.
2. **User funds stuck**: The user's BTC UTXO remains in the bridge's deposit address (bridge contract state was rolled back, so the UTXO is not marked verified). The user has no nBTC and must wait through the refund timelock (2–14 days) to recover BTC via `request_refund` / `execute_refund`.
3. **No automatic recovery**: The stranded nBTC in `bridge_id`'s balance has no self-service recovery path for the user; operator intervention is required to account for the discrepancy.

Matches allowed impact: **Medium — broken callback rollback / stuck bridge state requiring operator intervention**. [2](#0-1) 

---

### Likelihood Explanation

The `safe_deposit` path is activated when `deposit_msg.safe_deposit.is_some()`. The `deposit_msg` is user-controlled: the user generates their deposit address from it. Any user who:

1. Includes `safe_deposit` in their `deposit_msg` (e.g., routing through the Omni Bridge integration), **and**
2. Has not called `storage_deposit` on the nBTC token contract to register their account

will trigger this bug. New users and users interacting programmatically via Omni Bridge are realistic candidates. The condition is fully attacker-reachable without any privileged access. [3](#0-2) 

---

### Recommendation

Move the account-registration guard **before** the `internal_deposit` call so that no state mutation occurs when the recipient is unregistered:

```rust
// Check registration FIRST — before any state mutation
if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0));
}
// Only deposit to bridge_id after confirming the recipient exists
self.token.internal_deposit(&self.bridge_id, amount.into());
```

Alternatively, require registration and revert explicitly:

```rust
require!(
    self.token.accounts.get(&account_id).is_some(),
    "safe_mint: recipient account not registered"
);
self.token.internal_deposit(&self.bridge_id, amount.into());
```

This mirrors how `mint_inner` handles the case by auto-registering the account before depositing. [4](#0-3) 

---

### Proof of Concept

1. User constructs `deposit_msg` with `safe_deposit = Some(...)` and generates the corresponding BTC deposit address.
2. User sends BTC to that address **without** calling `storage_deposit` on the nBTC contract (account unregistered).
3. Relayer calls `verify_deposit_v2` on the bridge contract.
4. Bridge verifies the Merkle proof via the Light Client, then calls `safe_mint(account_id, amount, msg)` on the nBTC contract.
5. Inside `safe_mint`: `self.token.internal_deposit(&self.bridge_id, amount)` executes — nBTC contract state is mutated; `bridge_id` balance += `amount`.
6. `self.token.accounts.get(&account_id).is_none()` → `true`; function returns `U128(0)`.
7. Bridge contract's callback receives `U128(0)`, treats it as failure, and panics to revert.
8. Bridge contract state rolls back: UTXO is **not** marked as verified.
9. nBTC contract state does **not** roll back: `bridge_id` retains the extra `amount` nBTC.
10. **Result**: User has no nBTC; BTC UTXO is stuck pending a refund; bridge's nBTC balance is inflated by `amount` with no backing BTC deposit recorded. [5](#0-4)
