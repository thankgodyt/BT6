### Title
Attached NEAR Deposit Permanently Stuck in Contract on Failed `request_refund` Callback - (File: `contracts/satoshi-bridge/src/refund.rs`, `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary
`request_refund` requires a 2 NEAR attached deposit and explicitly documents it as non-refundable. However, when the asynchronous `request_refund_callback` panics — due to a failed light-client proof, a race-condition deposit win, a duplicate UTXO, or a script-pubkey mismatch — no `RefundRequest` is stored (no storage is consumed), yet the 2 NEAR deposit is permanently absorbed by the contract. There is no admin or DAO function to withdraw these accumulated stuck NEAR deposits.

---

### Finding Description

`request_refund` is marked `#[payable]` and enforces a minimum attached deposit of 2 NEAR: [1](#0-0) 

The public documentation explicitly states the deposit is non-refundable: [2](#0-1) 

The function then makes a cross-contract call to the light client and chains `request_refund_callback`: [3](#0-2) 

Inside `request_refund_callback`, multiple `require!` guards can panic and abort the callback: [4](#0-3) 

In NEAR Protocol, when a callback panics, the attached deposit from the *original* call is **not** returned to the predecessor — it remains in the contract. Because the callback panicked, no `RefundRequest` entry was written and no storage was actually consumed, yet the 2 NEAR is permanently locked.

The `required_balance_for_request_refund` view confirms the amount: [5](#0-4) 

The only NEAR-withdrawal function in the contract is `withdraw_protocol_fee`, which only drains `cur_available_protocol_fee` (an nBTC accounting field), not raw NEAR balance: [6](#0-5) 

No other function in `management.rs`, `bridge.rs`, or any other production file provides a mechanism to recover stuck NEAR deposits.

---

### Impact Explanation

Every failed `request_refund` call permanently removes 2 NEAR from the caller and adds it to the contract's unrecoverable balance. Realistic failure paths include:

- Light client returns `false` (insufficient confirmations, wrong block hash, invalid merkle proof).
- Race condition: `verify_deposit` finalizes the UTXO between the original call and the callback, triggering `"UTXO already verified via deposit"`.
- Duplicate concurrent `request_refund` calls for the same UTXO.
- Caller supplies a `deposit_msg` whose derived `script_pubkey` does not match the transaction output.

In each case, no storage is consumed, but 2 NEAR is permanently lost. The contract has no DAO-accessible withdrawal path for this balance. Over time, across many legitimate users hitting race conditions or proof failures, this constitutes a growing pool of permanently locked user funds with no recovery mechanism.

**Impact class: Medium** — permanent loss of user NEAR with no recovery path, matching "stuck bridge state requiring operator intervention" (no intervention is even possible here).

---

### Likelihood Explanation

The race condition between `request_refund` and `verify_deposit` is explicitly documented and tested in the codebase: [7](#0-6) 

Any user who calls `request_refund` while a relayer concurrently calls `verify_deposit` for the same UTXO will lose 2 NEAR. Invalid or under-confirmed proofs submitted by non-whitelisted callers (who face a `confirmations_delta` penalty) are also a realistic path. Both scenarios are reachable by any unprivileged NEAR account.

---

### Recommendation

Two mitigations, analogous to the fix applied in the referenced report:

1. **Refund on callback failure**: In `request_refund_callback`, when any `require!` fails, transfer `env::attached_deposit()` back to the original predecessor before panicking. This requires threading the predecessor account ID through the callback arguments.

2. **Admin withdrawal function**: Add a DAO-gated function to withdraw excess NEAR balance (total balance minus storage staking reserve) to a designated treasury account, analogous to `withdraw_protocol_fee` but for raw NEAR.

---

### Proof of Concept

1. Alice calls `request_refund` with 2 NEAR attached for a UTXO that has a valid BTC transaction.
2. Concurrently, a relayer calls `verify_deposit` for the same UTXO and it finalizes first, inserting the key into `verified_deposit_utxo`.
3. Alice's `request_refund_callback` executes and hits:
   ```rust
   require!(
       !self.data().verified_deposit_utxo.contains(&utxo_storage_key),
       "UTXO already verified via deposit"
   );
   ```
4. The callback panics. No `RefundRequest` is stored. Alice's 2 NEAR remains in the contract.
5. Alice calls `request_refund` again for the same UTXO — it now fails at the initial check `"UTXO already verified via deposit"` (before the cross-contract call), so this second 2 NEAR IS returned. But the first 2 NEAR is gone.
6. No DAO or admin function exists to recover the first 2 NEAR. The contract's `withdraw_protocol_fee` only touches `cur_available_protocol_fee`, not raw NEAR balance. [8](#0-7) [9](#0-8)

    pub fn required_balance_for_execute_refund(&self) -> NearToken {
        // Measured real storage: ~0.012 NEAR (Bitcoin) up to ~0.134 NEAR (Zcash shielded,
        // whose pending info embeds the Orchard bundle). The deposit is NOT refunded, so
        // 1 NEAR covers the heaviest case and acts as an anti-spam fee on this
        // permissionless entrypoint — refunds are a rare, abnormal event anyway.
        NearToken::from_near(1)
    }

    pub fn required_balance_for_request_refund(&self) -> NearToken {
        // request_refund stores a RefundRequest holding the deposit tx_bytes verbatim, so
        // storage grows ~1:1 with tx size (measured: storage ≈ tx_bytes + ~442 bytes). A
        // normal deposit (1-2 inputs, ~500 bytes) costs ~0.005 NEAR, but tx_bytes is capped
        // at MAX_REQUEST_REFUND_TX_BYTES (200 KB) — at that worst case storage is ~2 NEAR.
        // We size the deposit to cover that worst case; for normal deposits the bulk of it
        // is an anti-spam fee on this permissionless entrypoint (the deposit is NOT refunded).
        // Refunds are a rare, abnormal event anyway.
        NearToken::from_near(2)
    }

async fn test_refund_race_deposit_wins() {
    let worker = near_workspaces::sandbox().await.unwrap();
    let context = Context::new(&worker, Some(CHAIN.to_string())).await;

    let deposit_msg = DepositMsg {
        recipient_id: context.get_account_by_name("alice").sdk_id(),
        post_actions: None,
        extra_msg: None,
        safe_deposit: None,
        refund_address: Some(TARGET_ADDRESS.to_string()),
    };

    let deposit_address = context
        .get_user_deposit_address(deposit_msg.clone())
        .await
        .unwrap();

    let tx_bytes = generate_transaction_bytes(
        vec![(
            "f7f7069f02ad4ca31a16113903ab9fe9e8da6ddf20cad4b461b71e8b96050f24",
            0,
            None,
        )],
        vec![(deposit_address.as_str(), 100_000)],
    );
    let vout: u32 = 0;
    let blockhash = "0000000000000c3f818b0b6374c609dd8e548a0a9e61065e942cd466c426e00d".to_string();

    // 1. Request refund
    check!(
        print "request_refund"
        context.request_refund(
            "alice",
            deposit_msg.clone(),
            TARGET_ADDRESS,
            tx_bytes.clone(),
            vout,
            blockhash.clone(),
            1,
            vec![],
            None
        )
    );

    // 2. During timelock, Relayer calls verify_deposit — deposit succeeds
    check!(
        print "verify_deposit"
        context.verify_deposit(
            "relayer",
            deposit_msg.clone(),
            tx_bytes.clone(),
            vout,
            blockhash.clone(),
            1,
            vec![]
        )
    );

    // 3. nBTC minted to alice
    assert_eq!(context.ft_balance_of("alice").await.unwrap().0, 100_000);

    // 4. Set timelock to 0
    context
        .get_account_by_name("root")
        .call(context.bridge_contract.id(), "update_config")
        .args_json(json!({"update": {"refund_timelock_sec": 0}}))
        .deposit(near_sdk::NearToken::from_yoctonear(1))
        .max_gas()
        .transact()
        .await
        .unwrap()
        .unwrap();

    // 5. execute_refund fails — UTXO already verified via deposit
    let key = utxo_storage_key(&tx_bytes, vout);
    check!(
        context.execute_refund("alice", &key),
        "UTXO already verified via deposit, cannot refund"
    );

    // 6. nBTC still there — deposit was the winner
    assert_eq!(context.ft_balance_of("alice").await.unwrap().0, 100_000);
}
