### Title
Expired Peras Certificates Accepted Without Round-Age Validation, Enabling Illegitimate Chain-Selection Weight Boosts — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs`)

---

### Summary

The inbound Peras certificate processing path (`processCerts`) accepts certificates from any round without checking whether the certificate's round number is expired relative to the current Peras round. The validation function passed to `processCerts` is structurally incapable of performing this check (it receives only the certificate, not the current round). Downstream, `chainSelSync` only guards against slot-age (immutability), not round-age expiry. An adversarial peer can therefore send arbitrarily old Peras certificates that pass all checks, get stored in the `PerasCertDB`, and trigger chain selection with illegitimate weight boosts — the direct consensus analog of the smart-contract bug where expired locks keep claiming rewards.

---

### Finding Description

**Root cause 1 — structural absence of round-age check in `processCerts`.**

`processCerts` is the entry point for all inbound Peras certificates received from peers via the object-diffusion mini-protocol:

```haskell
processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
``` [1](#0-0) 

The validation callback `(PerasCert blk -> Either ...)` takes **only the certificate** as input. It has no access to the current Peras round number. This makes it structurally impossible for the validator to check whether the certificate's round is expired (i.e., whether `currRoundNo > latestCertRound + _A`). The only deduplication performed before validation is a membership check against the set of already-known round numbers:

```haskell
let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
``` [2](#0-1) 

**Root cause 2 — placeholder validation explicitly marked TODO.**

Both production pool-writer constructors pass `validatePerasCert mkPerasParams` as the validation function, with an explicit comment acknowledging the validation is incomplete:

**Root cause 3 — `chainSelSync` guards only slot-age, not round-age.**

When a certificate is processed for chain selection, the only staleness guard is:

```haskell
when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
  lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
  idExitEarly PerasCertIgnoredTooOld
``` [6](#0-5) 

This rejects a certificate only if the boosted block has already been made immutable. A certificate from round 0 boosting a block that is still in the volatile DB passes this guard unconditionally, regardless of how many rounds have elapsed since round 0.

**Root cause 4 — the expiry check exists only on the block-production path, not the acceptance path.**

The `latestCertSeenIsNotExpired` predicate (`currRoundNo <= _A + latestCertSeenRoundNo`) is evaluated only when deciding whether to *include* a certificate in a block being built:

```haskell
latestCertSeenIsNotExpired
  PerasCertInclusionView { perasParams, currRoundNo, latestCertSeen } =
    LatestCertSeenIsNotExpired latestCertSeenRoundNo
      := Bool (currRoundNo <= _A + latestCertSeenRoundNo)
``` [7](#0-6) 

There is no equivalent guard on the *inbound acceptance* path. The `PerasCertMaxRounds` parameter (`_A`) is defined precisely to bound certificate age:

```haskell
-- | Maximum age for a certificate to be included in a block, in rounds.
newtype PerasCertMaxRounds
  = PerasCertMaxRounds {unPerasCertMaxRounds :: Word64}
``` [8](#0-7) 

This bound is enforced for block production but not for certificate acceptance or chain selection.

---

### Impact Explanation

When Peras is enabled, an adversarial peer connected via the object-diffusion mini-protocol can:

1. Observe a block hash still in the target node's volatile DB (publicly available via ChainSync).
2. Craft a `PerasCert` with an arbitrarily old round number (e.g., round 0) and a large `vpcCertBoost` weight, targeting that block on a fork.
3. Send the certificate. `processCerts` filters only for duplicates, then calls the placeholder validator, which cannot check round-age. The certificate is accepted.
4. `chainSelSync` receives the certificate, passes the slot-age guard (the block is still volatile), stores it in the `PerasCertDB`, and triggers chain selection for the boosted block.
5. `totalWeightOfFragment` now includes the illegitimate boost. If `length(fork) + boost > length(current chain)`, the node switches to the fork.

This is a **High** impact chain-selection bug: an unprivileged peer can make an honest node prefer a non-canonical chain beyond the intended security assumptions of the Peras protocol, by replaying expired certificates that should carry no weight.

---

### Likelihood Explanation

- **Entry path is fully reachable**: any peer connected via the object-diffusion mini-protocol can send `PerasCert` objects; no special privilege is required.
- **No cryptographic barrier to crafting old-round certificates**: the round number is a plain `Word64` field; the adversary only needs to know a valid block point in the target's volatile DB.
- **Peras is currently disabled by default**, which limits immediate exposure. However, the code path is present in production files and will become active when Peras is enabled.
- **Likelihood: Medium** (gated on Peras activation; attack is otherwise trivially constructable).

---

### Recommendation

1. **Add the current round number to `processCerts`** (or derive it from the `SystemTime` and the era parameters already available) and reject any certificate whose round satisfies `currRoundNo > certRound + _A`.

2. **Replace the TODO placeholder** `validatePerasCert mkPerasParams` with a validator that receives the current round and enforces the `PerasCertMaxRounds` bound, mirroring the `latestCertSeenIsNotExpired` logic already present in `Cert/Inclusion.hs`.

3. **Add a round-age guard in `chainSelSync`** analogous to the existing slot-age guard, rejecting certificates whose round is more than `_A` rounds behind the current round before triggering chain selection.

---

### Proof of Concept

```
Attacker (unprivileged peer) ──object-diffusion──► Honest node

1. Via ChainSync, observe block B at slot S still in the volatile DB.
2. Construct:
     PerasCert { pcCertRound    = PerasRoundNo 0   -- arbitrarily old
               , pcCertBoostedBlock = blockPoint B  -- valid volatile block
               }
   with vpcCertBoost = PerasWeight (k + 1)          -- exceeds security param
3. Send the certificate batch to the honest node.
4. processCerts:
     - certsNotAlreadyInDb: round 0 not yet seen → passes dedup filter
     - validatePerasCert mkPerasParams: placeholder, no round-age check → Right validatedCert
     - addCert: certificate stored in PerasCertDB
5. chainSelSync:
     - pointSlot B >= anchorToSlotNo immTip → passes slot-age guard
     - certificate stored, chain selection triggered for B
     - totalWeightOfFragment(fork containing B) = length(fork) + (k+1)
       > totalWeightOfFragment(current chain) = length(current chain)
     → node switches to the fork
```

The fix mirrors the smart-contract patch: check `currRoundNo > certRound + _A` before accepting the certificate, exactly as `latestCertSeenIsNotExpired` does on the block-production path. [9](#0-8) [10](#0-9)

  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
