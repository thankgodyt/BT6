### Title
Peras Certificate Validation Bypass Enables Arbitrary Chain Weight Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` performs **zero cryptographic or semantic validation**, unconditionally returning `Right` for any certificate. An unprivileged peer can craft arbitrary `PerasCert` objects that are accepted without verification, injecting weight boosts into the `PerasWeightSnapshot` and manipulating `wsvTotalWeight` used in chain selection to prefer an adversarial chain.

---

### Finding Description

In `Ouroboros/Consensus/Block/SupportsPeras.hs`, the only `BlockSupportsPeras` instance in the codebase defines `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This function is called in the Peras object diffusion miniprotocol's certificate pool when a certificate arrives from a peer: [2](#0-1) 

Because `validatePerasCert` always returns `Right`, any crafted `PerasCert` — regardless of its `pcCertRound`, `pcCertBoostedBlock`, or any aggregate BLS signature — is accepted as a `ValidatedPerasCert` with a boost of `perasWeight params`.

The accepted certificate is then inserted into the `PerasCertDB` via `addPerasCertAsync`, which triggers chain selection: [3](#0-2) 

Chain selection computes `wsvTotalWeight` as `BlockNo + wsvWeightBoost`, where `wsvWeightBoost` is the sum of all boosts from the `PerasWeightSnapshot` for blocks on the fragment: [4](#0-3) 

The `preferCandidate` function then compares `wsvTotalWeight` values to decide whether to switch chains: [5](#0-4) 

The same incomplete validation applies to `validatePerasVote`, which only checks stake distribution membership but performs no cryptographic signature verification: [6](#0-5) 

This means an attacker can also impersonate legitimate voters by ID to forge quorum and produce certificates from scratch.

The analog to the reported TWAP manipulation is direct: just as `mark_price` is bounded within ±5% of `index_price` yet can still be manipulated within that range to skew the time-weighted average, here the per-certificate boost is bounded to `perasWeight params`, yet an attacker can freely choose **which block** to boost — the manipulation vector — injecting boosts onto adversarial blocks to skew `wsvTotalWeight` used in chain selection.

---

### Impact Explanation

When Peras is enabled, an unprivileged peer can craft a `PerasCert` with `pcCertBoostedBlock` pointing to a block on an adversarial fork. The certificate passes `validatePerasCert` unconditionally, receives a boost of `perasWeight params`, and is stored in the `PerasWeightSnapshot`. If the adversarial chain's `wsvTotalWeight` (block count + accumulated boosts) exceeds the honest chain's, the node switches to the adversarial chain. This constitutes a **bypass of Peras certificate validation enabling unauthorized chain selection manipulation** — a crafted network message causes an honest node to prefer a non-canonical chain. [7](#0-6) 

---

### Likelihood Explanation

**Medium.** The attack requires Peras to be enabled (currently not the default per the CHANGELOG: *"if Peras is disabled (which is the default), there is no observable difference"*). Once Peras is enabled, the attack requires only a connected peer and a crafted certificate message — no cryptographic keys, stake, or VRF material are needed. The code path is reachable via the standard Peras object diffusion miniprotocol. [8](#0-7) 

---

### Recommendation

Implement actual cryptographic validation in `validatePerasCert` before merging Peras into production:
- Verify the BLS aggregate signature over `(pcCertRound, pcCertBoostedBlock)` against the declared voter set.
- Validate that `pcCertRound` is within the acceptable range relative to the current chain tip.
- Validate that `pcCertBoostedBlock` refers to a known, non-ancient block.
- Implement equivalent signature verification in `validatePerasVote` to prevent vote impersonation.

The referenced GitHub issue (`https://github.com/tweag/cardano-peras/issues/120`) should be resolved before Peras is enabled on any production network.

---

### Proof of Concept

1. Connect to a node with Peras enabled as an unprivileged peer.
2. Craft a `PerasCert` with `pcCertBoostedBlock = blockPoint adversarialBlock` for a block on an adversarial fork.
3. Deliver the certificate via the Peras object diffusion miniprotocol.
4. `validatePerasCert` is called; it returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }` unconditionally.
5. `addPerasCertAsync` inserts the certificate into the `PerasCertDB` and triggers chain selection.
6. `weightBoostOfFragment` accumulates the boost for the adversarial block; `wsvTotalWeight` of the adversarial fragment increases by `perasWeight params`.
7. `preferCandidate` compares total weights; if the adversarial chain's total weight now exceeds the honest chain's, the node switches to the adversarial chain. [9](#0-8)

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
