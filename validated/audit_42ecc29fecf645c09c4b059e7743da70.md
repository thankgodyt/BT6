### Title
Stub `validatePerasCert` Accepts Any Peer-Supplied Certificate Without Quorum or Signature Checks, Enabling Chain-Selection Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The `validatePerasCert` implementation in the degenerate `BlockSupportsPeras` instance unconditionally returns `Right` for every certificate, performing no quorum, signature, or round validity checks. An unprivileged peer can therefore inject a crafted `PerasCert` that boosts an arbitrary block point, inflating the `PerasWeightSnapshot` used by chain selection and causing an honest node to prefer a non-canonical or adversarial fork over the honest chain.

### Finding Description

**Root cause — stub validation always succeeds**

The `BlockSupportsPeras` instance used for all block types contains a placeholder `validatePerasCert` that unconditionally accepts every certificate:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

No quorum threshold, no aggregate signature, no round-number bounds, and no check that `pcCertBoostedBlock` refers to a real block are performed.

**Entry path — peer-supplied certificates reach the stub**

`processCerts` in the Peras cert object pool is the network-facing handler. It calls the stub directly:

```haskell
(validatePerasCert mkPerasParams)
``` [2](#0-1) 

Because the stub always returns `Right`, every certificate in the batch passes, and each is forwarded to `addPerasCertAsync chainDB`.

**State mutation — fake cert enters PerasCertDB and inflates the weight snapshot**

`implAddCert` stores the certificate without further validation: [3](#0-2) 

`implGetWeightSnapshot` then builds the `PerasWeightSnapshot` from every stored certificate, including the attacker-injected one:

```haskell
let weights =
      mkPerasWeightSnapshot
        [ (getPerasCertBoostedBlock cert, getPerasCertBoost cert)
        | cert <- Map.elems (pcdsCertsByTicket pcds)
        ]
``` [4](#0-3) 

**Chain selection uses the inflated snapshot**

`chainSelectionForBlock` reads the snapshot atomically and passes it to `preferAnchoredCandidate`:

```haskell
(invalid, curChain, weights) <-
  atomically $
    (,,)
      <$> (forgetFingerprint <$> readTVar cdbInvalid)
      <*> Query.getCurrentChain cdb
      <*> (forgetFingerprint <$> Query.getPerasWeightSnapshot cdb)
``` [5](#0-4) 

`preferAnchoredCandidate` compares `wsvTotalWeight` (block count + weight boost) between the current chain and the candidate: [6](#0-5) 

A sufficiently large fake boost on an adversarial block causes `ShouldSwitch`, making the node roll back to and adopt the adversarial fork.

### Impact Explanation

**High — chain selection manipulation by an unprivileged peer.**

By injecting a `PerasCert` with `pcCertBoostedBlock` pointing to a block on an adversarial fork and `vpcCertBoost` set to a value exceeding the honest chain's length advantage, an attacker can cause an honest node to switch away from the canonical chain. This violates the Peras security assumption that only a certified quorum of stake-weighted committee members can boost a block. The node may permanently adopt a non-canonical chain, breaking the Common Prefix property.

### Likelihood Explanation

Any peer that can reach the Peras cert diffusion miniprotocol can exploit this. No privileged keys, stake majority, or VRF/KES compromise is required. The attacker only needs to:
1. Connect to the target node's Peras cert diffusion endpoint.
2. Send a `PerasCert` with an arbitrary `pcCertBoostedBlock` and a large `vpcCertBoost`.

The TODO comment at `SupportsPeras.hs:350` and `PerasCertDB/Impl.hs:167` confirms this is known incomplete code that is deployed in the production path, not isolated to tests.

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
1. Verifies the aggregate BLS/committee signature over `(electionId, candidate)`.
2. Checks that the number of signers meets the quorum threshold.
3. Validates that `pcCertRound` is within the expected range relative to the current ledger state.
4. Validates that `pcCertBoostedBlock` refers to a block that is a valid candidate (e.g., present in the VolatileDB or ImmutableDB).

Until real validation is in place, the Peras cert diffusion miniprotocol should be disabled or gated behind a feature flag so that no peer-supplied certificates can reach `addPerasCertAsync`.

### Proof of Concept

**Attacker-controlled entry path:**

1. Attacker connects to the target node's Peras cert diffusion miniprotocol.
2. Attacker sends a batch containing one `PerasCert`:
   ```
   PerasCert
     { pcCertRound    = <any round not yet in DB>
     , pcCertBoostedBlock = <block point on adversarial fork>
     }
   ```
3. `processCerts` calls `validatePerasCert mkPerasParams` → returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }` unconditionally.
4. Certificate is stored in `PerasCertDB` via `implAddCert`.
5. `implGetWeightSnapshot` includes `(adversarialBlockPoint, perasWeight)` in the snapshot.
6. When the adversarial block arrives (or is already in the VolatileDB), `chainSelSync` calls `chainSelectionForBlock` with the inflated snapshot.
7. `preferAnchoredCandidate` computes `wsvTotalWeight` for the adversarial candidate as `blockNo + perasWeight`, which exceeds the honest chain's `blockNo`.
8. `ShouldSwitch` is returned; the node rolls back and adopts the adversarial fork.

**Expected outcome:** The node's selected chain tip changes to the adversarial block, diverging from the honest chain.
