### Title
Unconditional Peras Certificate Acceptance Bypasses All Cryptographic Validation, Enabling Unauthorized Chain-Selection Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance's `validatePerasCert` implementation is a stub that unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or structural checks. Because this function is the sole validation gate in the production Peras certificate inbound pipeline (`makePerasCertPoolWriterFromChainDB`), any unprivileged peer that negotiates the Peras diffusion miniprotocol can inject an arbitrary crafted `PerasCert` — pointing at any block hash in the VolatileDB — and cause the receiving node to boost that block's chain-selection weight and potentially switch to a weaker or adversary-controlled chain.

---

This is the **only** implementation of `validatePerasCert` in the codebase (the universal instance declared at line 320 covers all `StandardHash blk`). No per-era override exists. Every certificate received from a peer is immediately wrapped in `ValidatedPerasCert` with a full `perasWeight` boost, regardless of its content.

**Production inbound pipeline wires this stub directly:** [2](#0-1) 

`makePerasCertPoolWriterFromChainDB` passes `(validatePerasCert mkPerasParams)` as the validation callback to `processCerts`, then forwards every "validated" cert to `ChainDB.addPerasCertAsync`. There is no secondary check.

**The inbound handler is wired to every peer connection:** [3](#0-2) 

`hPerasCertDiffusionClient` calls `objectDiffusionInbound` with `makePerasCertPoolWriterFromChainDB` for every peer that negotiates the Peras cert diffusion miniprotocol. No origin/peer-trust check gates this path.

**Accepted certificates trigger chain selection:** [4](#0-3) 

`chainSelSync` processes each queued `ChainSelAddPerasCert` entry: it adds the cert to `PerasCertDB` and then calls `chainSelectionForBlock` for the boosted block. The CHANGELOG confirms chain selection now ranks candidates by Peras weight rather than length alone: [5](#0-4)

### Impact Explanation

An unprivileged peer that negotiates `PerasSupported` can craft a `PerasCert` whose `pcCertBoostedBlock` points to any block hash present in the receiving node's VolatileDB. Because `validatePerasCert` returns `Right` unconditionally, the cert is accepted, stored, and used to artificially inflate that block's chain-selection weight by `perasWeight`. This can cause the honest node to:

1. **Prefer a shorter or weaker adversary-controlled fork** over the canonical chain, constituting a chain-selection safety failure.
2. **Permanently record a fraudulent certificate** in the `PerasCertDB`, which persists across the node's lifetime for that round (one cert per round is accepted; duplicates are silently dropped).

This maps to: **Critical — bypass of Peras certificate checks enabling unauthorized certificate acceptance and chain-selection manipulation.**

---

### Likelihood Explanation

- The Peras diffusion miniprotocol is already wired into the production `NodeToNodeProtocols` bundle and is negotiated at the version-data level.
- The attack requires only that a peer negotiates `PerasSupported` — no stake, no keys, no prior relationship.
- The attacker needs to know (or guess) a valid block hash in the target's VolatileDB, which is trivially obtained via the ChainSync miniprotocol.
- Peras is not yet the default on mainnet, but the code is active in the codebase and the vulnerability is present in any private testnet or deployment that enables Peras.

Likelihood: **Medium** (Peras not yet default) → **High** once Peras is activated.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
1. The certificate's BLS aggregate signature against the claimed committee members' public keys.
2. That the claimed voters are members of the correct Peras voting committee for the stated round (using the stake distribution from the ledger, analogous to how `validatePerasVote` uses `PerasVoteStakeDistr`).
3. That the boosted block's slot falls within the valid range for the certificate's round number.

Until real validation is implemented, the Peras cert diffusion handler should be disabled or gated behind an explicit feature flag that is off by default, preventing any peer from injecting certificates.

---

### Proof of Concept

**Attacker-controlled entry path:**

```
Malicious peer
  → negotiates NodeToNodeV{Peras=PerasSupported}
  → sends ObjectDiffusion message containing PerasCert{
        pcCertRound  = <any round not yet in DB>,
        pcCertBoostedBlock = <hash of a known VolatileDB block on a weaker fork>
    }
  → objectDiffusionInbound calls opwAddObjects [craftedCert]
  → processCerts calls validatePerasCert mkPerasParams craftedCert
      -- returns Right (ValidatedPerasCert { vpcCert = craftedCert, vpcCertBoost = perasWeight })
      -- NO signature check, NO committee membership check, NO round-slot check
  → addCert (WithArrivalTime now validatedCert)
  → ChainDB.addPerasCertAsync chainDB validatedCert
  → chainSelSync: chainSelectionForBlock triggered for boosted block
  → node switches to the weaker fork boosted by the fraudulent certificate
```

The only existing guard — `filter (not . Set.member roundNo) certIds` — only deduplicates by round number. The **first** crafted cert for any unseen round number passes through unconditionally. [6](#0-5) [7](#0-6) [3](#0-2)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
