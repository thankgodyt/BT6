### Title
Missing Chain Discriminator in `deployToken` Borsh Encoding Enables Cross-Chain Replay of NEAR MPC Signatures — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

### Summary
The `deployToken` function in `OmniBridge.sol` constructs a Borsh-encoded message for NEAR MPC signature verification that omits `omniBridgeChainId`. Because the same NEAR MPC key (`nearBridgeDerivedAddress`) is shared across all EVM deployments, a valid signature obtained for chain A is cryptographically valid on chain B, enabling unauthorized token deployment on any chain where the token has not yet been registered.

### Finding Description

In `OmniBridge.deployToken`, the signed payload is:

```
PayloadType.Metadata | token | name | symbol | decimals
``` [1](#0-0) 

No `omniBridgeChainId` is included. The only replay guard is a same-chain idempotency check: [2](#0-1) 

This check only prevents re-deployment on the *same* chain. It does not prevent replaying the signature on a *different* chain where the token has not yet been deployed.

By direct contrast, `finTransfer` encodes `omniBridgeChainId` **twice** in its signed payload, providing proper chain binding: [3](#0-2) 

The same missing-chain-ID pattern is present in the Starknet implementation's `MetadataPayload.to_borsh()`: [4](#0-3) 

While Starknet's `TransferMessagePayload.to_borsh()` correctly includes `chain_id`: [5](#0-4) 

The `MetadataPayload` struct itself carries no chain field: [6](#0-5) 

### Impact Explanation

After a successful replay on chain B:

1. `isBridgeToken`, `nearToEthToken`, and `ethToNearToken` mappings are populated on chain B for the replayed token. [7](#0-6) 

2. `OmniBridgeWormhole.deployTokenExtension` publishes a Wormhole message containing `omniBridgeChainId` for chain B. [8](#0-7) 

3. The NEAR bridge, observing this Wormhole message, records the token as legitimately deployed on chain B. Subsequent `finTransfer` calls to chain B for that token will mint tokens against the replayed (unauthorized) contract, producing unbacked bridged tokens on chain B.

4. The legitimate deployment of that token on chain B is permanently blocked (`ERR_TOKEN_EXIST` will fire for any future authorized call).

### Likelihood Explanation

- **Precondition is the intended production model**: all EVM deployments of `OmniBridgeWormhole` share the same `nearBridgeDerivedAddress` (the NEAR MPC derived key). [9](#0-8) 
- `deployToken` is a permissionless external function — no role check, no allowlist. [10](#0-9) 
- The attacker only needs one valid `signatureData` from any prior `deployToken` call on any chain (observable on-chain).
- The attack is a single transaction on the target chain.

### Recommendation

Include `omniBridgeChainId` in the Borsh-encoded bytes that are signed for `deployToken`, mirroring the pattern already used in `finTransfer`:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals),
    bytes1(omniBridgeChainId)   // <-- add this
);
```

Apply the same fix to the Starknet `MetadataPayload.to_borsh()` and ensure the NEAR MPC signing logic includes the destination chain ID when producing `MetadataPayload` signatures.

### Proof of Concept

```solidity
// Local hardhat test — no mainnet interaction
// 1. Deploy two OmniBridgeWormhole instances with the same nearBridgeDerivedAddress
//    but different omniBridgeChainId values (e.g., 0 for Ethereum, 1 for Arbitrum).
// 2. Obtain a valid deployToken signature for chain A (omniBridgeChainId=0).
// 3. Call deployToken on chain B (omniBridgeChainId=1) with the identical
//    signatureData and MetadataPayload.
// 4. Assert the call succeeds: nearToEthToken[token] != address(0) on chain B,
//    isBridgeToken[...] == true, and DeployToken event emitted.
// 5. Confirm chain A's signature was accepted on chain B without any
//    chain-B-specific authorization from NEAR MPC.
```

The root cause is the structural asymmetry: `finTransfer` binds signatures to a chain via `omniBridgeChainId` in the signed bytes; `deployToken` does not.
