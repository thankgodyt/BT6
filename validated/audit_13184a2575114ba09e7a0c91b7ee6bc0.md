### Title
`sync_chain_signatures_root_public_key` is permanently one-shot: MPC root-key rotation irreversibly bricks all withdrawals and refunds — (`contracts/satoshi-bridge/src/api/management.rs`)

---

### Summary

The bridge stores the NEAR Chain Signatures MPC root public key exactly once via `sync_chain_signatures_root_public_key`. A hard `require!(is_none())` guard prevents any future re-sync, and `ConfigUpdate` contains no field for `chain_signatures_root_public_key`. If the MPC network performs a root-key rotation (a normal resharing ceremony), the bridge has no on-chain path to update the stale key. Every subsequent withdrawal and refund will produce signatures that are cryptographically invalid for the old key-derived UTXO addresses, permanently locking all BTC held in the bridge.

---

### Finding Description

**Step 1 — One-shot sync guard**

`sync_chain_signatures_root_public_key` in `management.rs` enforces:

```rust
require!(
    self.internal_config()
        .chain_signatures_root_public_key
        .is_none(),
    "Already sync"
);
```

Once the key is written, this function can never be called again — even by the DAO.

**Step 2 — No update path in `ConfigUpdate`**

`ConfigUpdate` (in `config.rs`) lists every field that `update_config` can mutate. It includes `btc_light_client_account_id` and `nbtc_account_id`, but **not** `chain_signatures_root_public_key` and **not** `chain_signatures_account_id`. `ConfigUpdate::apply` therefore has no branch that touches either field.

**Step 3 — `change_address` is also frozen**

`sync_root_public_key_callback` derives and stores `change_address` from the root public key in the same single callback. `ConfigUpdate` has no `change_address` field either, so the change address is equally frozen.

**Step 4 — How the stale key breaks signing**

`internal_sign_btc_transaction` calls `sign_promise`, which forwards the signing request to the MPC contract. After a key rotation the MPC signs with the **new** root key. The bridge, however, still derives UTXO addresses and verifies signatures using the **old** stored root key. The resulting signatures are invalid for the old-key-derived P2WPKH scripts, so every `sign_btc_transaction_callback` either produces a bad signature or the final broadcast transaction is rejected by the Bitcoin network. Withdrawals, cancel-withdrawals, active UTXO management, and refunds all go through this path and all fail.

---

### Impact Explanation

All BTC held in bridge-controlled UTXOs (addresses derived from the old root key) becomes permanently unspendable from the bridge's perspective. Users who have already burned nBTC and are waiting for a withdrawal receive nothing. Users who have not yet withdrawn hold nBTC tokens that can never be redeemed. The bridge's entire BTC reserve is effectively frozen with no recovery path short of a contract upgrade that re-derives all UTXO paths under the new key — a complex migration that the current upgrade machinery does not provide.

This matches the allowed impact: **permanent locking of user or protocol funds**.

---

### Likelihood Explanation

NEAR Chain Signatures is an MPC threshold-signature network. Root-key rotation (resharing ceremonies) is a documented operational event in such systems and is part of the NEAR MPC security model. It does not require any attacker action; it is a routine infrastructure operation by the MPC operators. The bridge has no control over when this occurs. The Amphora analog was rated Medium for the same reason — external operational event, not an attacker-controlled trigger.

---

### Recommendation

1. **Remove the `is_none()` guard** from `sync_chain_signatures_root_public_key` (or add a separate privileged `force_resync_chain_signatures_root_public_key`) so the DAO can re-fetch the current root public key from the MPC contract at any time.

2. **Add `chain_signatures_account_id` to `ConfigUpdate`** so the bridge can be pointed at a new MPC contract account if the service migrates.

3. **Re-derive `change_address`** automatically whenever the root public key is updated, or expose it as an independently updatable config field.

---
