### Title
Missing Chain ID in `deployToken` Signature Allows Cross-Chain Replay Across EVM Deployments — (`File: evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

The `deployToken` function in `OmniBridge.sol` verifies a NEAR MPC signature over a borsh-encoded hash that does **not** include `omniBridgeChainId`. Because the same `nearBridgeDerivedAddress` is used across all EVM deployments (Ethereum, Arbitrum, Base, BNB), a valid `deployToken` signature obtained for one EVM chain can be replayed verbatim on any other EVM chain to deploy a bridge token without chain-specific NEAR authorization.

---

### Finding Description

`OmniBridge.sol::deployToken` constructs its signed hash as:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
bytes32 hashed = keccak256(borshEncoded);
if (ECDSA.recover(hashed, signatureData) != nearBridgeDerivedAddress) {
    revert InvalidSignature();
}
``` [1](#0-0) 

No `omniBridgeChainId` is included. Contrast this with `finTransfer`, which explicitly encodes `omniBridgeChainId` **twice** in the hash — once for the token address chain and once for the recipient chain — providing full chain binding:

```solidity
bytes1(omniBridgeChainId),   // token chain
Borsh.encodeAddress(payload.tokenAddress),
Borsh.encodeUint128(payload.amount),
bytes1(omniBridgeChainId),   // recipient chain
Borsh.encodeAddress(payload.recipient),
``` [2](#0-1) 

The NEAR bridge signs `MetadataPayload` using the MPC key at path `bridge-1`: [3](#0-2) 

The `MetadataPayload` struct itself contains no chain identifier:

```rust
pub struct MetadataPayload {
    pub prefix: PayloadType,
    pub token: String,
    pub name: String,
    pub symbol: String,
    pub decimals: u8,
}
``` [4](#0-3) 

Because the MPC key derivation path is chain-agnostic, the resulting `nearBridgeDerivedAddress` is identical across all EVM deployments. A signature over `MetadataPayload` is therefore valid on every EVM chain simultaneously.

The Starknet `deploy_token` has the same structural gap — `MetadataPayload::to_borsh` also omits the chain ID: [5](#0-4) 

called from `fin_transfer` without a chain ID argument, while `fin_transfer` correctly passes `self.omni_bridge_chain_id.read()`: [6](#0-5) 

---

### Impact Explanation

An attacker who observes a legitimate `deployToken` call on Ethereum (fully public on-chain data) can immediately replay the identical `(signatureData, metadata)` tuple on Arbitrum, Base, or BNB. Each target chain will:

1. Accept the signature as valid (same `nearBridgeDerivedAddress`, same hash).
2. Deploy a new `BridgeToken` proxy and mark it as `isBridgeToken = true`.
3. Call `deployTokenExtension`, which in `OmniBridgeWormhole` posts a Wormhole VAA back to NEAR. [7](#0-6) 

NEAR receives the Wormhole message and registers the token for the replayed chain. The bridge now treats the token as legitimately deployed on that chain, enabling `finTransfer` flows to it. This constitutes an unauthorized deployer-equivalent action: the attacker forces token registration on chains the NEAR operators never authorized, bypassing the intended chain-by-chain deployment governance. If the legitimate deployment on the target chain is attempted afterward, it will revert with `ERR_TOKEN_EXIST`, permanently blocking the authorized deployment at that address.

---

### Likelihood Explanation

Exploitation requires only reading a confirmed `deployToken` transaction from any EVM block explorer and submitting the same calldata to a different EVM chain's bridge contract. No privileged access, no private keys, no MEV infrastructure. Any public relayer or observer can perform this. The only precondition is that the target chain's bridge contract is live and unpaused.

---

### Recommendation

Include `omniBridgeChainId` in the borsh-encoded payload that is signed and verified in `deployToken`, mirroring the pattern already used in `finTransfer`:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
+   bytes1(omniBridgeChainId),          // bind to this chain
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
```

Apply the same fix to the Starknet `MetadataPayload::to_borsh` (pass and embed `chain_id` as done in `TransferMessagePayload::to_borsh`), and update the NEAR signing path to include the destination chain in `MetadataPayload` before hashing.

---

### Proof of Concept

1. Observe a confirmed `deployToken(signatureData, metadata)` call on Ethereum mainnet (e.g., via Etherscan).
2. Submit the identical calldata to the Arbitrum `OmniBridge` contract address.
3. The Arbitrum contract computes the same `keccak256(borshEncoded)` (no chain ID in the hash), recovers the same `nearBridgeDerivedAddress`, and accepts the signature.
4. A `BridgeToken` proxy for `metadata.token` is deployed on Arbitrum; `isBridgeToken[proxy] = true` and `nearToEthToken[metadata.token] = proxy` are set.
5. `OmniBridgeWormhole::deployTokenExtension` emits a Wormhole VAA; NEAR registers the token for Arbitrum.
6. Any subsequent legitimate `deployToken` call for the same `metadata.token` on Arbitrum reverts with `ERR_TOKEN_EXIST`, permanently blocking the authorized deployment. [8](#0-7) [9](#0-8)
