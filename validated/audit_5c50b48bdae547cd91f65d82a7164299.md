### Title
`validatePerasCert` Stub Unconditionally Accepts All Certificates, Disabling Peras Certificate Validation and Enabling Arbitrary Chain-Weight Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The catch-all `BlockSupportsPeras` instance's `validatePerasCert` implementation always returns `Right` (success) without performing any cryptographic or structural validation. This is the direct analog of the reported "wrong location" bug class: instead of checking the certificate's actual validity, the function checks nothing — constructing a `ValidatedPerasCert` unconditionally from any input. The result is that the entire Peras certificate validation gate is disabled, allowing any unprivileged peer to inject arbitrary certificates that manipulate chain-selection weight.

### Impact Explanation

**High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain.**

Because `validatePerasCert` never rejects any certificate, a peer can craft a `PerasCert` that claims to boost any block on any fork. Once accepted into `PerasCertDB`, the fake boost is reflected in the `PerasWeightSnapshot`. Chain selection then uses this inflated weight when comparing the adversary's fork against the honest chain via `wsvTotalWeight`:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [7](#0-6) 

A sufficiently large fake boost can cause the node to switch to a shorter, non-canonical fork, violating the chain-selection invariant and potentially enabling double-spend or chain divergence.

---

### Likelihood Explanation

**High.** The entry path requires only that a peer send a well-formed `PerasCert` message over the Peras certificate mini-protocol. No keys, stake, or privileged access are needed. The `processVotes`-style inbound handler calls `validatePerasCert` before passing the result to `addPerasCertAsync`; since `validatePerasCert` always returns `Right`, every inbound certificate is accepted. The catch-all instance is the only instance in the codebase, so this affects all block types including production Cardano blocks.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
1. The certificate's aggregate BLS signature against the claimed voter set and boosted block.
2. That the claimed voters are eligible members of the committee for the certificate's round.
3. That the total stake of the signers meets the quorum threshold.

Until a proper `BlockSupportsPeras` instance for `CardanoBlock` is provided, the stub should at minimum reject all certificates (return `Left PerasValidationErr`) rather than accept all of them, so that the Peras weight mechanism is inert rather than exploitable.

---

### Proof of Concept

1. Connect to a node as an unprivileged peer via the Peras certificate mini-protocol.
2. Send a `PerasCert` with `pcCertRound = <any round>` and `pcCertBoostedBlock = <tip of a short fork>`.
3. The node calls `validatePerasCert`, which returns `Right ValidatedPerasCert{..}` unconditionally.
4. The certificate is stored in `PerasCertDB`; `implGetWeightSnapshot` now includes the fake boost for the fork tip.
5. When `chainSelectionForBlock` next runs, `compareAnchoredFragments` computes `wsvTotalWeight` for the fork as `blockNo + fakeBoost`, which exceeds the honest chain's `blockNo`.
6. `preferCandidate` returns `ShouldSwitch`, and the node adopts the non-canonical fork. [8](#0-7) [9](#0-8)
