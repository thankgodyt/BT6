### Title
Peras Certificate Validation Unconditionally Accepts All Peer-Supplied Certificates, Bypassing Cryptographic Checks — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance provides a `validatePerasCert` implementation that **always returns `Right`** — performing zero cryptographic or semantic validation. The companion `validatePerasVote` only checks stake-table membership but skips vote-signature verification entirely. Both functions are wired directly into the production ObjectDiffusion inbound pipeline (`makePerasCertPoolWriterFromChainDB`, `makePerasVotePoolWriterFromChainDB`). An unprivileged peer can therefore inject arbitrary Peras certificates that pass "validation" and are stored in the `PerasCertDB`, after which the ChainDB triggers chain selection for the boosted block — potentially causing an honest node to prefer a non-canonical chain.

---

### Finding Description

**Root cause — `SupportsPeras.hs` lines 318–371:**

The file contains a single catch-all instance for every `StandardHash blk`:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  validatePerasCert params cert =
    Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }

  validatePerasVote _params stakeDistr vote
    | Just stake <- lookupPerasVoteStake vote stakeDistr =
        Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
    | otherwise = Left PerasValidationErr
```

`validatePerasCert` is unconditionally `Right`: it never inspects the aggregate BLS signature, the round number plausibility, or the boosted-block point. `validatePerasVote` only checks that the voter's key appears in the stake distribution; it never calls `verifyVoteSignature`.

No Cardano-specific override exists — a grep for `BlockSupportsPeras` across `ouroboros-consensus-cardano/**/*.hs` returns zero matches, confirming the degenerate instance is the operative one for all production block types.

**Production call sites — `PerasCert.hs` lines 96–137 and `PerasVote.hs` lines 101–152:**

```haskell
-- PerasCert.hs line 126
(validatePerasCert mkPerasParams)

-- PerasVote.hs line 141
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
```

Both are passed as the `validateCert`/`validateVote` argument to `processCerts`/`processVotes`, which are the inbound handlers for peer-received objects in the ObjectDiffusion mini-protocol.

**`processCerts` (lines 156–185 of `PerasCert.hs`):**

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) -> mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _)            -> throw (PerasCertValidationError errs)
```

Because `validatePerasCert` always returns `Right`, the `([], validatedCerts)` branch is always taken and every peer-supplied certificate is stored.

**Chain selection trigger — `ChainSel.hs` lines 483–532:**

Once a certificate is stored, `chainSelSync` calls `chainSelectionForBlock` for the boosted block, potentially switching the node's preferred chain.

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` with an arbitrary `pcCertBoostedBlock` pointing to any block in the VolatileDB. Because `validatePerasCert` never verifies the aggregate BLS signature, the certificate passes "validation" and is stored. The ChainDB then runs chain selection treating that block as carrying a Peras weight boost (`vpcCertBoost = perasWeight params`). If the boosted fork is otherwise equal in length to the current selection, the artificial boost causes the node to switch to the attacker-chosen fork — a chain-selection manipulation that violates the Peras security assumption that only legitimately quorum-certified blocks receive a boost.

For votes: a peer can forge a `PerasVote` for any voter key that appears in the stake distribution (public information). Because `validatePerasVote` skips signature verification, the forged vote is accepted, accumulates stake toward quorum, and may trigger `forgePerasCert` → `addPerasCertAsync` → chain selection.

**Impact class:** High — chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain, and bypass of certificate/signature validation enabling unauthorized certificate acceptance.

---

### Likelihood Explanation

The CHANGELOG notes that "if Peras is disabled (which is the default), there is no observable difference." The vulnerability is therefore latent today but becomes immediately exploitable the moment Peras is enabled on any network. The ObjectDiffusion mini-protocol is reachable by any connected peer without authentication. Crafting a structurally valid `PerasCert` CBOR payload requires only knowledge of the serialization format (public) and a target block hash (observable from the chain). No key material, stake majority, or privileged access is required.

---

### Recommendation

1. **Remove or gate the degenerate instance.** The catch-all `instance StandardHash blk => BlockSupportsPeras blk` should either be removed or replaced with a compile-time error so that any block type that reaches the ObjectDiffusion pipeline must provide a real implementation.

2. **Implement cryptographic validation before the Peras feature flag is enabled.** `validatePerasCert` must verify the aggregate BLS signature over `(pcRoundNo, pcBoostedBlock)` using the committee's aggregate verification key. `validatePerasVote` must call `verifyVoteSignature` (as the `EveryoneVotes` and `WFALS` committee implementations already do in `Committee/EveryoneVotes.hs` and `Committee/WFALS.hs`).

3. **Add a feature-flag guard in `processCerts`/`processVotes`.** Until full validation is implemented, reject all inbound Peras objects when the degenerate instance is in use.

---

### Proof of Concept

1. Connect to a node with Peras enabled as an unprivileged peer via the ObjectDiffusion mini-protocol.
2. Observe a block hash `H` in the VolatileDB (e.g., via ChainSync).
3. Craft a CBOR-encoded `PerasCert` with `pcCertRound = <any round>` and `pcCertBoostedBlock = H`. No valid BLS signature is needed.
4. Send the certificate batch to the node.
5. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right ValidatedPerasCert{..}` unconditionally.
6. The certificate is stored in `PerasCertDB` and `chainSelectionForBlock` is triggered for `H`.

```haskell
processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
```

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
