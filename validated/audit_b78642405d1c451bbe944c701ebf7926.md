Audit Report

## Title
Missing Chain-ID Binding in `deploy_token` Signed Message Enables Cross-Chain Replay — (Files: `starknet/src/bridge_types.cairo`, `solana/programs/bridge_token_factory/src/state/message/deploy_token.rs`, `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

The Borsh-encoded `MetadataPayload` used to authorize `deploy_token` on Starknet, Solana, and EVM omits any chain identifier. A valid NEAR MPC signature authorizing token deployment on one chain can be replayed verbatim on any other chain that shares the same `nearBridgeDerivedAddress`/`derived_near_bridge_address`. This is a concrete chain/domain-separation flaw: the signed bytes are chain-agnostic, so signature verification passes on every bridge instance.

## Finding Description

**Starknet — `MetadataPayload::to_borsh()` takes no `chain_id` and emits none:** [1](#0-0) 

The serialized bytes are exactly `[0x01 (PayloadType::Metadata), token, name, symbol, decimals]` — no chain identifier.

**Contrast with `TransferMessagePayload::to_borsh(chain_id)`**, which receives and embeds `chain_id` twice: [2](#0-1) 

**Starknet call-site asymmetry** — `deploy_token` passes no chain_id; `fin_transfer` does: [3](#0-2) [4](#0-3) 

**Solana — `DeployTokenPayload::serialize_for_near()` writes no `SOLANA_OMNI_BRIDGE_CHAIN_ID`:** [5](#0-4) 

**Contrast with `FinalizeTransferPayload::serialize_for_near()`**, which writes `SOLANA_OMNI_BRIDGE_CHAIN_ID` at positions 3 and 5: [6](#0-5) 

**EVM — `deployToken` Borsh encoding also omits `omniBridgeChainId`:** [7](#0-6) 

**Contrast with `finTransfer`**, which embeds `omniBridgeChainId` twice: [8](#0-7) 

**Signature verification** on both Starknet and Solana checks only that the recovered signer equals the shared `nearBridgeDerivedAddress`/`derived_near_bridge_address` — no chain context is included: [9](#0-8) [10](#0-9) 

The Starknet `CLAUDE.md` explicitly documents chain-ID binding only for `fin_transfer`, confirming the omission for `deploy_token` is a security gap: [11](#0-10) 

## Impact Explanation

An attacker who observes a valid `deploy_token` transaction on chain A (all data is public on-chain) can submit the identical `(signature, MetadataPayload)` to chain B's bridge contract. The bridge on chain B:

1. Verifies the signature — **passes**, because the signed bytes are chain-agnostic and the same `nearBridgeDerivedAddress` is used on all chains.
2. Checks `ERR_TOKEN_ALREADY_DEPLOYED` / `ERR_TOKEN_EXIST` — **passes** if the token has not yet been deployed on chain B.
3. Deploys the bridge token contract and registers it in `near_to_starknet_token` / `nearToEthToken` / Solana mint mappings.

Concrete impacts:
- **Unauthorized token deployment**: A token is registered in chain B's bridge as a valid bridge token without NEAR's per-chain authorization — a direct authorization bypass for a deployer-equivalent action.
- **Permanent DoS on legitimate deployment**: The `ERR_TOKEN_ALREADY_DEPLOYED` / `ERR_TOKEN_EXIST` guard permanently blocks the legitimate NEAR-authorized deployment of the same token on chain B.
- **Pathway to unauthorized minting**: Once the token is registered as a bridge token on chain B, it becomes eligible for `fin_transfer` minting. If NEAR's backend treats the emitted `DeployToken` event as proof of authorized deployment (a reasonable assumption for an event-driven system), it will subsequently sign `fin_transfer` for this token on chain B, enabling unauthorized minting of bridged assets without a corresponding lock/burn on the origin chain.

This maps directly to the allowed critical impact: *chain/domain separation flaw enabling invalid finalization*, *authorization bypass that lets an attacker execute bridge/token/deployer actions*, and *unauthorized minting of bridged funds*.

## Likelihood Explanation

The attack requires zero privileged access. The attacker only needs to observe a `deploy_token` transaction on any supported chain (all data is public on-chain) and submit the same `(signature, payload)` to another chain's bridge contract. No key material, admin role, or off-chain coordination is needed. The precondition — a `deploy_token` signature existing for at least one chain — is met every time a new token is bridged for the first time, which is a routine bridge operation.

## Recommendation

Include the destination chain ID in the `MetadataPayload` Borsh encoding, mirroring the pattern already used for `TransferMessagePayload`/`FinalizeTransferPayload`/`finTransfer`.

- **Starknet**: Change `MetadataPayload::to_borsh()` to accept a `chain_id: u8` parameter and append it at a fixed position. Update the `deploy_token` call-site to pass `self.omni_bridge_chain_id.read()`.
- **Solana**: In `DeployTokenPayload::serialize_for_near()`, write `SOLANA_OMNI_BRIDGE_CHAIN_ID` into the serialized buffer at a fixed position after the `IncomingMessageType::Metadata` prefix, matching the pattern in `FinalizeTransferPayload::serialize_for_near()`.
- **EVM**: In `deployToken`, include `omniBridgeChainId` in the `borshEncoded` bytes at a fixed position, matching the pattern in `finTransfer`.

## Proof of Concept

1. NEAR backend signs `MetadataPayload { token: "usdc.near", name: "USD Coin", symbol: "USDC", decimals: 6 }` to authorize deployment on Solana. Signed bytes: `[0x01, "usdc.near", "USD Coin", "USDC", 6]`.
2. Attacker observes the Solana `deploy_token` transaction and extracts `(signature, payload)`.
3. Attacker calls `deploy_token(signature, MetadataPayload { token: "usdc.near", name: "USD Coin", symbol: "USDC", decimals: 6 })` on the Starknet bridge.
4. Starknet's `_verify_borsh_signature` hashes the identical Borsh bytes and recovers the same `nearBridgeDerivedAddress` — **signature accepted**.
5. `ERR_TOKEN_ALREADY_DEPLOYED` check passes (token not yet on Starknet).
6. "usdc.near" bridge token is deployed on Starknet and registered in `near_to_starknet_token` / `starknet_to_near_token`.
7. Legitimate NEAR-authorized deployment of "usdc.near" on Starknet is now permanently blocked.
8. The same attack applies symmetrically to EVM chains using the identical chain-agnostic Borsh encoding confirmed at `OmniBridge.sol` lines 142–148.

A local integration test can prove this: deploy two bridge instances with different `omni_bridge_chain_id` values but the same `nearBridgeDerivedAddress`, sign a `MetadataPayload` for chain A, and submit it to chain B — the `deploy_token` call will succeed on chain B without any chain-B-specific authorization.

```rust
impl<P: Payload> SignedPayload<P> {
    pub fn verify_signature(
        &self,
        params: P::AdditionalParams,
        derived_near_bridge_address: &[u8; 64],
    ) -> Result<()> {
        let serialized = self.payload.serialize_for_near(params)?;
        let hash = keccak::hash(&serialized);

        let signature_bytes = &self.signature[0..64];

        let signature = libsecp256k1::Signature::parse_standard_slice(signature_bytes)
            .map_err(|_| ProgramError::InvalidArgument)?;
        require!(!signature.s.is_high(), ErrorCode::MalleableSignature);

        let signer = secp256k1_recover(&hash.to_bytes(), self.signature[64], signature_bytes)
            .map_err(|_| error!(ErrorCode::SignatureVerificationFailed))?;

        require!(
            signer.0 == *derived_near_bridge_address,
            ErrorCode::SignatureVerificationFailed
        );

        Ok(())
    }
```
