### Title
Missing Role-Based Access Control on `clear_invalid_pending_verify_rbf` / `batch_clear_invalid_pending_verify_rbf` — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary
`clear_invalid_pending_verify_rbf` and `batch_clear_invalid_pending_verify_rbf` are state-mutating bridge functions that carry no role restriction. Any unprivileged NEAR account can invoke them. The inline comment explicitly states these are intended for "the off-chain program," yet no on-chain access control enforces that intent.

### Finding Description
Both functions are decorated only with `#[pause(except(roles(Role::DAO)))]` — which gates them behind the contract-wide pause flag but imposes no caller identity check: [1](#0-0) 

Every other sensitive bridge mutator in the same file carries either `#[access_control_any(roles(...))]` (e.g., `cancel_withdraw`, `active_utxo_management`) or `#[trusted_relayer]` (e.g., `verify_withdraw_v2`, `verify_refund_finalize`). These two cleanup functions are the sole exceptions.

The comment at line 431–434 reads:

> "Since there can be many RBFs, removing all RBF pending info at once after verifying the transaction on-chain might not have enough gas. Therefore, the off-chain program uses this interface to perform the cleanup." [2](#0-1) 

This confirms the functions are designed for a specific privileged caller, yet the contract enforces nothing about who that caller is.

The bridge's RBAC system defines `Role::Operator` and `Role::DAO` precisely for maintenance tasks of this kind: [3](#0-2) 

All other operator-level maintenance methods (`cancel_withdraw`, `active_utxo_management`, `active_utxo_management_rbf`, `cancel_active_utxo_management`) are gated with `#[access_control_any(roles(Role::DAO, Role::Operator))]`: [4](#0-3) 

### Impact Explanation
An unprivileged attacker can call `clear_invalid_pending_verify_rbf` or `batch_clear_invalid_pending_verify_rbf` with arbitrary `btc_pending_verify_id` values. If `internal_clear_invalid_pending_verify_rbf` does not independently re-validate that the targeted entry is truly invalid before deletion, the attacker can prematurely purge live RBF pending-info records. This severs the bridge's on-chain tracking of in-flight RBF transactions: the MPC signing pipeline loses its reference, the relayer can no longer call `verify_withdraw_v2` against the cleaned-up ID, and the corresponding user withdrawal becomes permanently stuck — requiring operator intervention to reconstruct state. This matches the **Medium** impact class: stuck bridge state requiring operator intervention.

### Likelihood Explanation
The entry point is fully public and requires no special token balance, deposit, or proof. Any NEAR account can craft a transaction targeting a known `btc_pending_verify_id` (observable from on-chain events emitted by `GenerateBtcPendingInfo`). Likelihood is **High** once a motivated attacker identifies an active RBF pending ID.

### Recommendation
Apply the same role guard used by all other operator-level maintenance functions:

```rust
#[payable]
#[access_control_any(roles(Role::DAO, Role::Operator))]
#[pause(except(roles(Role::DAO)))]
pub fn clear_invalid_pending_verify_rbf(&mut self, btc_pending_verify_id: String) {
    assert_one_yocto();
    self.internal_clear_invalid_pending_verify_rbf(btc_pending_verify_id);
}

#[payable]
#[access_control_any(roles(Role::DAO, Role::Operator))]
#[pause(except(roles(Role::DAO)))]
pub fn batch_clear_invalid_pending_verify_rbf(&mut self, btc_pending_verify_ids: Vec<String>) {
    assert_one_yocto();
    for id in btc_pending_verify_ids {
        self.internal_clear_invalid_pending_verify_rbf(id);
    }
}
```

### Proof of Concept
1. A user initiates a withdrawal via `ft_on_transfer` → `ft_on_transfer_withdraw_chain_specific`. The bridge emits `GenerateBtcPendingInfo { btc_pending_id: "abc123" }`.
2. The user later calls `withdraw_rbf("abc123", ...)`, creating an RBF entry. The bridge emits another `GenerateBtcPendingInfo` for the RBF candidate.
3. Before the relayer calls `verify_withdraw_v2` to finalize, the attacker calls:
   ```
   clear_invalid_pending_verify_rbf("abc123")
   ```
   with no attached deposit, no role, no proof — the call succeeds because the only guard is the pause flag.
4. The pending-info record for `"abc123"` is removed. The relayer's subsequent `verify_withdraw_v2("abc123", proof)` panics with "pending info not found." The user's withdrawal is stuck; their nBTC has already been transferred to the bridge but the Bitcoin transaction can no longer be finalized on-chain through normal flow.
