### Title
RBF `sign_btc_transaction` Early-Exit Deletes In-Flight Pending Info, Causing `sign_btc_transaction_callback` to Panic — (`contracts/satoshi-bridge/src/api/chain_signatures.rs`)

---

### Summary

When `sign_btc_transaction` is called for an RBF tx that already has an MPC sign promise in-flight, and the original tx is subsequently removed from `btc_pending_infos` before the callback lands, a second call to `sign_btc_transaction` for the same RBF tx will take the early-exit cleanup path and delete the RBF `BTCPendingInfo`. The already-scheduled `sign_btc_transaction_callback` then calls `internal_unwrap_btc_pending_info` on the now-deleted entry and panics with `"BTC pending info not exist"`.

---

### Finding Description

**Entrypoint:** `sign_btc_transaction` — public, `#[payable]`, no ACL check beyond `#[pause]`.

**Step 1 — MPC sign dispatched:**
`sign_btc_transaction(rbf_tx_id, ...)` is called. The RBF entry exists, `assert_pending_sign()` passes, `check_btc_pending_info_exists(original_tx_id)` returns `true`, so `internal_sign_btc_transaction` is called, dispatching an MPC sign promise with `sign_btc_transaction_callback` scheduled as a receipt. [1](#0-0) [2](#0-1) 

**Step 2 — Original tx removed:**
Before the callback receipt is processed (MPC sign takes multiple blocks), the original tx is verified and confirmed on Bitcoin. The burn callback calls `internal_remove_btc_pending_info(original_tx_id)`, deleting the original entry. [3](#0-2) 

**Step 3 — Early-exit triggered (publicly callable):**
Any caller (no ACL check) calls `sign_btc_transaction(rbf_tx_id, ...)` again. The RBF entry still exists and is still in `PendingSign` state (callback hasn't fired), so `assert_pending_sign()` passes. `get_original_tx_id()` returns `Some(original_tx_id)`. `check_btc_pending_info_exists(original_tx_id)` now returns `false`. The early-exit branch fires: it removes `rbf_tx_id` from `btc_pending_sign_ids` and calls `internal_remove_btc_pending_info(&btc_pending_sign_id)`, deleting the RBF entry. [4](#0-3) 

**Step 4 — Callback panics:**
The in-flight `sign_btc_transaction_callback` receipt fires. If the MPC sign succeeded, the callback immediately calls `internal_unwrap_btc_pending_info(&btc_pending_sign_id)` on the now-deleted entry, which calls `.expect("BTC pending info not exist")` and panics. [5](#0-4) [6](#0-5) 

---

### Impact Explanation

The callback transaction panics and fails. The MPC signature result is discarded. The RBF `BTCPendingInfo` is already deleted (step 3), so there is nothing to roll back in the callback. Because the original tx was already confirmed on Bitcoin before step 2, the user's withdrawal is complete and no funds are lost or permanently locked. The impact is confined to: a publicly reachable panic-driven fault in a production bridge callback path, a wasted MPC sign fee (attached deposit), and a failed receipt that may confuse off-chain monitoring.

---

### Likelihood Explanation

The window between step 1 (MPC sign dispatched) and the callback landing spans multiple NEAR blocks — the MPC sign latency. During this window, the original tx can be verified and confirmed, and any unprivileged account can call `sign_btc_transaction` with the observable `btc_pending_sign_id` (emitted via `GenerateBtcPendingInfo` event) to trigger the early-exit. No privileged role is required. The scenario can also occur naturally without an attacker if a relayer calls `sign_btc_transaction` for cleanup after observing the original was confirmed.

---

### Recommendation

In `sign_btc_transaction_callback`, guard the `internal_unwrap_btc_pending_info` call with an existence check. If the entry no longer exists (it was cleaned up by the early-exit path), return `false` gracefully instead of panicking:

```rust
// In sign_btc_transaction_callback, replace the unwrap with:
if !self.check_btc_pending_info_exists(&btc_pending_sign_id) {
    return false;
}
```

Alternatively, the early-exit path in `sign_btc_transaction` could be made safe by checking whether a sign is already in-flight (e.g., by tracking in-flight sign count in the `BTCPendingInfo`), and deferring cleanup until no callbacks are pending.

---

### Proof of Concept

Sequence (unit-testable without privileged roles):

1. Create an RBF `BTCPendingInfo` with `original_tx_id` pointing to an existing original entry.
2. Call `sign_btc_transaction(rbf_tx_id, 0, 0)` — dispatches MPC sign promise (callback pending).
3. Directly call `internal_remove_btc_pending_info(original_tx_id)` to simulate the original being verified.
4. Call `sign_btc_transaction(rbf_tx_id, 0, 0)` again — `assert_pending_sign()` passes, `check_btc_pending_info_exists(original_tx_id)` returns `false`, early-exit removes the RBF entry.
5. Invoke `sign_btc_transaction_callback(account_id, rbf_tx_id, 0)` with a mock successful MPC result — assert it panics with `"BTC pending info not exist"`. [7](#0-6)
