### Title
Attacker Can Redirect Any Victim's Unfinalized BTC Deposit by Supplying Arbitrary `refund_address` in Public `request_refund` - (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

`request_refund` is publicly callable by any NEAR account. When the victim's `deposit_msg.refund_address` is `None` (the standard case for most deposits), the caller-supplied `refund_address` is accepted without any proof of ownership over the deposit. An attacker who observes an unfinalized BTC deposit on-chain can race to submit a refund request pointing to their own BTC address, and after the `unsafe_refund_timelock_sec` elapses, call the equally-public `execute_refund` to redirect the victim's UTXO to themselves.

---

### Finding Description

**Entry point — `request_refund` is public:** [1](#0-0) 

The function carries only `#[payable]` and `#[pause]` guards. There is no `#[trusted_relayer]` attribute at the function level (unlike `verify_deposit_v2`, `verify_withdraw_v2`, etc.), so any NEAR account can call it after attaching the required storage deposit.

**The ownership gap — `refund_address` is unconstrained when `deposit_msg.refund_address` is `None`:** [2](#0-1) 

The only guard is: *if* the original `deposit_msg` already contains a `refund_address`, the caller must match it. When `deposit_msg.refund_address` is `None` — the common case for standard deposits — the caller's arbitrary string is stored verbatim as the refund destination with no further check.

**Deposit address derivation does not include `refund_address`-as-None as a distinguishing factor:** [3](#0-2) 

`get_deposit_path` hashes the full JSON of `deposit_msg`. Because `refund_address` is `skip_serializing_if = "Option::is_none"`, a `deposit_msg` with `refund_address: None` serialises identically whether the original depositor intended a refund or not. The attacker therefore passes the exact same `deposit_msg` the victim used, the script-pubkey check in `request_refund_callback` passes, and the malicious `refund_address` is stored. [4](#0-3) 

**Duplicate-request guard only prevents two requests for the same UTXO — it does not protect the victim:** [5](#0-4) 

Whoever calls `request_refund` first for a given UTXO wins. If the attacker front-runs the victim, the victim cannot submit a corrective request.

**`execute_refund` is also public:** [6](#0-5) 

After the `unsafe_refund_timelock_sec` elapses, the attacker calls `execute_refund` themselves. No privileged role is required.

**The only mitigation is an operator-dependent timelock:** [7](#0-6) 

The longer `unsafe_refund_timelock_sec` is applied precisely because the refund address was supplied by an untrusted caller. The DAO/Operator must notice and call `reject_refund` within that window. If they do not, the attacker's `execute_refund` succeeds and the victim's BTC is sent to the attacker's address.

---

### Impact Explanation

A successful attack redirects the victim's entire deposit UTXO to the attacker's BTC address. The victim receives nothing; their nBTC is never minted. This constitutes a significant loss of user funds. The impact is **Critical** if the operator window is missed, and **Medium** (attacker-triggered stuck state requiring operator intervention) if the operator acts in time.

---

### Likelihood Explanation

- BTC transactions are public; any observer can identify deposits that have not yet been finalized by a `verify_deposit` call on NEAR.
- The attacker only needs to pay a small NEAR storage deposit and submit a valid Merkle proof (also publicly available from any BTC node).
- The attack is a simple race: call `request_refund` before the relayer calls `verify_deposit`. Deposits that are delayed (e.g., low-fee transactions, relayer downtime, or deposits below the minimum threshold) are especially vulnerable.
- The operator must actively monitor and reject every suspicious refund request within the `unsafe_refund_timelock_sec` window; a single missed request results in theft.

Likelihood: **Medium** (requires an unfinalized deposit window, but such windows are routine and the on-chain data needed is fully public).

---

### Recommendation

Require the caller of `request_refund` to prove they are the intended recipient of the deposit. The simplest fix is to enforce that the caller's NEAR account matches `deposit_msg.recipient_id` when `deposit_msg.refund_address` is `None`:

```rust
// In internal_request_refund, before storing the request:
if deposit_msg.refund_address.is_none() {
    require!(
        env::predecessor_account_id() == deposit_msg.recipient_id,
        "Only the deposit recipient may specify a refund_address"
    );
}
```

Alternatively, require that `refund_address` always be pre-committed inside `deposit_msg` (i.e., disallow `None`) so that the BTC address is fixed at deposit-address-derivation time and cannot be overridden by a third party.

---

### Proof of Concept

1. Victim calls `get_user_deposit_address` with `deposit_msg = { recipient_id: "victim.near", refund_address: null }` and sends 0.1 BTC to the returned address.
2. The relayer is slow; `verify_deposit` has not been called yet.
3. Attacker observes the BTC transaction on-chain, reconstructs the same `deposit_msg`, and calls:
   ```
   request_refund(
     deposit_msg    = { recipient_id: "victim.near", refund_address: null },
     refund_address = "attacker_btc_address",
     tx_bytes       = <victim's raw BTC tx>,
     vout           = 0,
     proof          = <valid Merkle proof>,
     gas_fee        = null,
   )
   ```
   with the required NEAR storage deposit attached.
4. `request_refund_callback` verifies the Merkle proof, checks that the output script matches the deposit address derived from `deposit_msg` (it does — the victim sent BTC there), and stores `RefundRequest { refund_address: "attacker_btc_address", … }`.
5. The duplicate-request guard now blocks the victim from submitting their own corrective request.
6. After `unsafe_refund_timelock_sec` passes without operator intervention, the attacker calls `execute_refund(utxo_storage_key)`.
7. The bridge's MPC pipeline signs a transaction paying 0.1 BTC (minus gas fee) to `attacker_btc_address`. The victim's deposit is stolen.
