Audit Report

## Title
Decimal Normalization Dust Permanently Locked When Transfer Fee Is Zero - (File: `near/omni-bridge/src/lib.rs`)

## Summary
`normalize_amount` applies floor integer division when converting token amounts from higher-decimal source chains to lower-decimal destination chains. The truncated remainder ("dust") is permanently locked in the NEAR bridge contract (native tokens) or burned (deployed tokens) whenever a transfer is initiated with `fee = 0`. When `fee > 0`, the dust is recoverable via `claim_fee_callback`, but no equivalent recovery path exists for the zero-fee case.

## Finding Description

**Root cause — floor division in `normalize_amount`:** [1](#0-0) 

`amount / 10^diff_decimals` discards any sub-unit remainder. For a token with `origin_decimals = 24` on NEAR and `decimals = 6` on EVM, `diff_decimals = 18`, so the maximum dust per transfer is `10^18 - 1` NEAR-side units.

**Full amount (including dust) is locked/burned in `init_transfer_internal`:** [2](#0-1) 

**Only the normalized (truncated) amount is signed and sent to the destination chain:** [3](#0-2) 

**When `fee > 0`, dust is recovered:** `claim_fee_callback` computes `fee = transfer_message.amount.0 - denormalized_amount`, which naturally absorbs the normalization remainder into the relayer's fee: [4](#0-3) 

**When `fee = 0`, the transfer message is deleted immediately after signing with no dust recovery:** [5](#0-4) 

After this removal, `claim_fee` is never called, so `amount % 10^diff_decimals` remains permanently locked or burned with no recovery path.

**Note on PoC arithmetic:** The submitted PoC contains a mathematical error. For `amount = 1_999_999_999_999_999_999_000_000` with `diff_decimals = 18`, the correct normalized result is `1_999_999_999` (not `1_999_999`), and the correct dust is `999_999_999_000_000` NEAR units (not `999_000_000_000_000_000`). The claim that the user receives "only 1 token" is also incorrect — they receive `1_999_999_999` EVM units. Despite these errors, the underlying mechanism is real and confirmed by the code.

## Impact Explanation

This is a concrete instance of decimal/normalization abuse causing permanent mis-accounting of bridged user funds. The maximum dust per transfer is `10^18 - 1` NEAR-side units, which equals `10^-6` tokens for a 24-decimal token. For high-value tokens this can represent meaningful monetary loss per transfer. The funds are irrecoverably locked in the bridge escrow (native tokens) or burned (deployed tokens), constituting permanent freezing/loss of bridged user funds — matching the Critical allowed impact scope of "decimal/normalization abuse that changes user or protocol balances" and "permanent freezing of bridged funds."

## Likelihood Explanation

`ft_transfer_call` is fully public and permissionless. Any token holder can supply `fee = 0` and a non-round amount (i.e., `amount % 10^diff_decimals != 0`), triggering the dust loss. No special role, privilege, or external dependency is required. The condition fires on every such transfer, is repeatable, and requires no victim cooperation beyond the user's own action.

## Recommendation

1. **Round down the transfer amount before locking:** In `init_transfer_internal` (or before calling it), compute `effective_amount = normalize_amount(amount_without_fee) * 10^diff_decimals + fee` and return the remainder `dust = amount - effective_amount` to the sender via `ft_transfer` before locking/burning.
2. **Alternatively, reject non-round zero-fee transfers:** When `fee = 0` and `origin_decimals != decimals`, require `amount % 10^diff_decimals == 0`, reverting otherwise with a clear error.
3. **Or enforce a minimum fee:** Require `fee > 0` whenever `origin_decimals > decimals`, ensuring dust is always absorbed by the relayer fee path in `claim_fee_callback`.

## Proof of Concept

**Setup:** Token with `origin_decimals = 24` on NEAR, `decimals = 6` on EVM, `diff_decimals = 18`.

1. User calls `ft_transfer_call` with `amount = 1_500_000_000_000_000_000_500_000` and `fee = 0`.
2. `init_transfer_internal` locks the full `1_500_000_000_000_000_000_500_000` NEAR units.
3. `sign_transfer` computes `normalize_amount(1_500_000_000_000_000_000_500_000, {decimals:6, origin_decimals:24})` = `1_500_000_000_000_000_000_500_000 / 10^18` = `1_500_000` (EVM units).
4. MPC signs payload for `amount = 1_500_000` EVM units.
5. `sign_transfer_callback`: `fee.is_zero()` → `remove_transfer_message(transfer_id)`. Transfer message deleted.
6. EVM contract receives `1_500_000` EVM units.
7. Dust = `1_500_000_000_000_000_000_500_000 - 1_500_000 * 10^18` = `500_000` NEAR units remains permanently locked in the NEAR bridge with no recovery path.

A local integration test can confirm this by: (a) calling `ft_transfer_call` with a non-round amount and `fee = 0`, (b) asserting the MPC-signed amount equals `normalize_amount(amount)`, (c) asserting the bridge's locked balance decreases by the full amount while the user receives only the normalized amount on the destination side, and (d) verifying no `claim_fee` path exists to recover the remainder.
