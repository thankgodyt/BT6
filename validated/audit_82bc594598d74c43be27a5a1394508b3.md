Peras Certificate Validation Stub Always Accepts Any Peer-Supplied Certificate, Enabling Unauthorized Chain Selection Weight Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` function is an unimplemented stub that unconditionally returns `Right` (success) for every certificate it receives, performing zero cryptographic or committee-membership checks. Any unprivileged peer connected via the Peras certificate mini-protocol can inject an arbitrary `PerasCert` pointing to any block hash. The certificate bypasses validation, is stored in the `PerasCertDB`, and triggers chain selection with an attacker-controlled weight boost, allowing a shorter or non-canonical fork to be preferred over the honest chain.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must verify a certificate's cryptographic proof and committee eligibility before the certificate is admitted to the node's state. The universal production instance, which applies to all block types, implements this gate as a no-op:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is wired directly into the production inbound certificate handler `makePerasCertPoolWriterFromChainDB`, which is the writer used when Peras certificates arrive from remote peers:

```haskell
(validatePerasCert mkPerasParams)
``` [2](#0-1) 

`processCerts` calls this validator on every inbound certificate. Because the validator always returns `Right`, the `([], validatedCerts)` branch is always taken and every certificate is forwarded to `ChainDB.addPerasCertAsync`: [3](#0-2) 

`chainSelSync` then processes the certificate: it stores it in `PerasCertDB`, looks up the boosted block in `VolatileDB`, and calls `chainSelectionForBlock` for that block, injecting the attacker-chosen weight boost into the `PerasWeightSnapshot`: [4](#0-3) 

Chain selection then uses `weightedSelectView`, which computes `wsvTotalWeight = blockNo + weightBoost`. The `preferCandidate` comparison in `WeightedSelectView` switches to a candidate chain whenever its total weight exceeds the current chain's total weight: [5](#0-4) 

Because `PerasWeight` is additive and unbounded, an attacker who sends multiple certificates all boosting the same block on a shorter fork can accumulate enough weight to override the honest longest-chain rule.

---

### Impact Explanation

An unprivileged peer can cause an honest node to permanently prefer a non-canonical, shorter fork over the honest chain by injecting fabricated Peras certificates. The Peras weight boost is added on top of block number in `wsvTotalWeight`, so a fork that is `N` blocks shorter than the honest chain can be made to appear heavier by sending `N` or more fake certificates all boosting a block on that fork. This is a **chain selection safety failure**: the node adopts a chain that the honest network has not selected, breaking the Ouroboros security guarantee.

---

### Likelihood Explanation

Any peer that can establish a Peras certificate mini-protocol connection (i.e., any network peer) can exploit this. No keys, stake, or privileged access are required. The attack requires only sending a well-formed CBOR-encoded `PerasCert` with an arbitrary `pcCertBoostedBlock` field. The Peras mini-protocol is already wired into the production `ChainDB` path. The TODO comment and linked issue confirm this is a known incomplete implementation shipped in production code, not a test stub.

---

### Recommendation

Until real cryptographic committee-membership and signature verification is implemented for `validatePerasCert`, the Peras certificate inbound mini-protocol handler must not be enabled in production builds. The stub instance should either:
1. Return `Left PerasValidationErr` unconditionally (reject all certs until real validation is in place), or
2. Be guarded by a feature flag that is disabled in production.

The `makePerasCertPoolWriterFromChainDB` function should not be wired into the node's network stack until `validatePerasCert` performs real cryptographic verification.

---

### Proof of Concept

**Attacker-controlled entry path:**

1. Attacker connects to a victim node as a normal peer and establishes the Peras certificate ObjectDiffusion mini-protocol session.
2. Attacker constructs a `PerasCert` with:
   - `pcCertRound` = any round number not yet in the victim's `PerasCertDB`
   - `pcCertBoostedBlock` = the `Point` (slot + hash) of a block on a shorter competing fork
3. Attacker sends this certificate to the victim node.
4. `processCerts` calls `validatePerasCert mkPerasParams cert` → always returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })`.
5. The certificate is added to `PerasCertDB` via `ChainDB.addPerasCertAsync`.
6. `chainSelSync` processes `ChainSelAddPerasCert`, finds the boosted block in `VolatileDB`, and calls `chainSelectionForBlock` for it.
7. `constructPreferableCandidates` builds candidate fragments containing the boosted block; `weightedSelectView` computes their `wsvTotalWeight` including the injected boost.
8. If the boosted fork's total weight now exceeds the current chain's total weight, the node switches to the attacker's preferred fork.
9. Attacker repeats with additional fake certificates (different `pcCertRound` values, same `pcCertBoostedBlock`) to accumulate enough weight to overcome any length deficit.

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
