### Title
Silent nBTC Supply Inflation via `safe_mint` When Recipient Account Is Unregistered — (File: `contracts/nbtc/src/lib.rs`)

### Summary
The `safe_mint` function in the nBTC token contract mints tokens to the bridge's own account before checking whether the intended recipient is registered. If the recipient is not registered, the function returns `U128(0)` without reverting the already-executed `internal_deposit`. This permanently inflates the nBTC total supply without delivering tokens to the user, and the corresponding BTC UTXO is marked as verified — locking the user's funds with no recovery path.

### Finding Description
In `contracts/nbtc/src/lib.rs`, `safe_mint` executes in two distinct steps:

**Step 1 — unconditional supply inflation:**
```rust
self.token.internal_deposit(&self.bridge_id, amount.into());
```
This call increases `total_supply` and credits the bridge's own nBTC balance by `amount`. It is not guarded by any check on the recipient's registration status.

**Step 2 — silent early return when recipient is unregistered:**
```rust
if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0));
}
```
If `account_id` has no storage slot in the token contract, the function returns `U128(0)` synchronously — without panicking, without reverting the `internal_deposit`, and without any lost-and-found entry. The minted tokens remain stranded in the bridge's nBTC balance. [1](#0-0) 

The bridge's `verify_deposit_v2` path (with `deposit_msg.safe_deposit = Some(..)`) calls `safe_mint` and is documented to "revert the whole transaction if minting fails." However, `safe_mint` does not fail — it returns `U128(0)` as a successful synchronous value. The bridge callback receives a success signal with a zero-amount result. Meanwhile:

- The nBTC `total_supply` has already been permanently increased.
- The UTXO is marked in `verified_deposit_utxo`, blocking any future `request_refund` for the same UTXO.
- The user's BTC is irrecoverably locked. [2](#0-1) 

### Impact Explanation
- **nBTC total supply is inflated** beyond the amount of BTC actually backing it. The bridge holds extra nBTC in its own balance that was never legitimately earned.
- **User's BTC is permanently locked**: the UTXO is marked verified, so `request_refund` is blocked (`"UTXO already verified via deposit, cannot refund"`).
- **User receives zero nBTC** despite a confirmed on-chain BTC deposit.
- This constitutes: *permanent supply inflation below backed supply* and *stuck bridge state requiring operator intervention* — matching the Medium impact tier. [3](#0-2) 

### Likelihood Explanation
The `safe_deposit` flow is the standard path for Omni Bridge integrations. A user who deposits BTC before their NEAR account has called `storage_deposit` on the nBTC contract (a common ordering in cross-chain onboarding flows) will have no registered account slot. The relayer processes the deposit in good faith; the bug fires silently. No malicious actor is required — this is a normal operational race condition between BTC confirmation and NEAR account registration.

### Recommendation
Move the recipient-registration check **before** `internal_deposit`, or replace the early-return with a `panic!`/`require!` so the entire call reverts atomically:

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "...");
    // Check registration BEFORE minting
    require!(
        self.token.accounts.get(&account_id).is_some(),
        "safe_mint: recipient account not registered"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ... transfer logic
}
```

This ensures that if the recipient is unregistered, no supply inflation occurs and the bridge callback correctly observes a failed cross-contract call, allowing it to revert the deposit state.

### Proof of Concept

1. User `alice.near` sends 0.01 BTC to their bridge deposit address, embedding `safe_deposit = Some(..)` in the deposit message.
2. `alice.near` has **not** called `storage_deposit` on the nBTC contract — her account slot does not exist.
3. The relayer calls `verify_deposit_v2` → light-client proof passes → bridge calls `safe_mint(alice.near, 1_000_000, None)` on the nBTC contract.
4. `internal_deposit(&bridge_id, 1_000_000)` executes: `total_supply += 1_000_000`, bridge nBTC balance `+= 1_000_000`.
5. `self.token.accounts.get(&alice.near)` returns `None` → function returns `U128(0)`.
6. Bridge callback receives success + zero amount. UTXO is inserted into `verified_deposit_utxo`.
7. Alice's 0.01 BTC is permanently locked. She cannot call `request_refund` (UTXO already verified). She holds 0 nBTC. The bridge holds 1,000,000 sat worth of unbacked nBTC in its own balance. [1](#0-0) [4](#0-3)

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }
