### Title
Multiple Accounts Can Execute the Same Refund Request, Creating Duplicate MPC Signing Entries for the Same UTXO - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary

After the first `execute_refund` call marks a `RefundRequest` as `executed = true`, the guard in `load_refund_request_for_execute` explicitly re-admits any subsequent caller. Because `execute_refund` is an unrestricted public function, any number of distinct NEAR accounts can each call it for the same `utxo_storage_key`, each creating an independent `BTCPendingInfo` entry and triggering a separate MPC chain-signature request — all spending the same deposit UTXO. Only one refund transaction can ever confirm on Bitcoin; the rest become permanently stale pending entries that require privileged operator cleanup.

### Finding Description

`execute_refund` is a public, payable function with no caller restriction beyond the `#[pause]` guard:

```rust
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn execute_refund(
    &mut self,
    utxo_storage_key: String,
    chain_specific_data: Option<ChainSpecificData>,
) -> PromiseOrValue<()> {
    let timelock_sec = self.resolve_execute_refund_timelock(&utxo_storage_key);
    self.internal_execute_refund(utxo_storage_key, timelock_sec, chain_specific_data)
}
``` [1](#0-0) 

Inside `load_refund_request_for_execute`, the guard that is supposed to block re-execution reads:

```rust
require!(
    !self.data().verified_deposit_utxo.contains(utxo_storage_key)
        || refund_request.executed,
    "UTXO already verified via deposit, cannot refund"
);
``` [2](#0-1) 

After the first `execute_refund` call, `finalize_refund_with_psbt` both inserts the UTXO key into `verified_deposit_utxo` **and** sets `refund_request.executed = true`:

```rust
self.data_mut()
    .verified_deposit_utxo
    .insert(utxo_storage_key.clone());
// ...
refund_request.executed = true;
self.data_mut()
    .refund_requests
    .insert(utxo_storage_key, refund_request.into());
``` [3](#0-2) 

The guard evaluates to `!true || true = true`, so it always passes for any subsequent caller once the request is executed. Each new caller then reaches `finalize_refund_with_psbt`, which creates a fresh `BTCPendingInfo` keyed by the new PSBT's pending ID (different each time because the PSBT is rebuilt):

```rust
require!(
    self.data_mut()
        .btc_pending_infos
        .insert(btc_pending_id.clone(), btc_pending_info.into())
        .is_none(),
    "pending info already exist"
);
self.internal_unwrap_mut_account(&caller)
    .btc_pending_sign_ids
    .insert(btc_pending_id.clone());
``` [4](#0-3) 

The only per-caller throttle is `require_pending_sign_capacity`, which defaults to **1** pending sign per account:

```rust
pub fn get_max_pending_sign_txs(&self, account_id: &AccountId) -> u32 {
    self.data()
        .pending_tx_limits
        .get(account_id)
        .copied()
        .unwrap_or(1)
}
``` [5](#0-4) 

Because NEAR accounts are trivially cheap to create, an attacker with N accounts can issue N independent `execute_refund` calls, each producing a distinct `BTCPendingInfo` and a distinct MPC signing request — all for the same deposit UTXO. There is no mapping from UTXO → existing pending sign ID that would block this.

### Impact Explanation

**Medium.** No funds are redirected — the refund amount is always paid to the `refund_address` embedded in the `RefundRequest`. However:

1. **Wasted MPC chain-signature resources**: Each duplicate `execute_refund` triggers a full MPC signing round (gas + MPC computation) for a transaction that can never confirm.
2. **Stuck bridge state requiring operator intervention**: The stale `BTCPendingInfo` entries cannot self-clean. Cleanup requires a trusted relayer to call `remove_refund_pending_tx_id` for each stale entry, which itself requires the refund request to already be gone. Until cleaned, each stale entry occupies a pending-sign slot in the attacker's account and pollutes `btc_pending_infos`.
3. **Potential DoS of the refund pipeline**: If the MPC service is rate-limited or has bounded concurrency, flooding it with duplicate signing requests for the same UTXO can delay or block legitimate refunds for other users.

### Likelihood Explanation

**Medium.** The attack requires:
- Multiple NEAR accounts (trivially cheap).
- An attached deposit per call (`required_balance_for_execute_refund()`), which is a storage-sized NEAR amount — not a meaningful economic barrier.
- The timelock to have elapsed (or the caller to hold `RefundOperator`/`DAO` role for fast-track).

Any user who submitted the original `request_refund` knows the `utxo_storage_key` and can immediately begin duplicating executions once the timelock passes. A griefing attacker monitoring on-chain events can do the same.

### Recommendation

Enforce a one-to-one invariant between a `RefundRequest` and its active `BTCPendingInfo` by storing the pending ID inside the request and blocking re-execution while a live pending entry exists:

```rust
// In RefundRequest, add:
pub active_pending_id: Option<String>,
```

In `finalize_refund_with_psbt`, before inserting the new `BTCPendingInfo`:

```rust
require!(
    refund_request.active_pending_id.is_none()
        || !self.data().btc_pending_infos.contains_key(
            refund_request.active_pending_id.as_ref().unwrap()
        ),
    "A pending refund sign already exists for this UTXO"
);
refund_request.active_pending_id = Some(btc_pending_id.clone());
```

Alternatively, restrict re-execution of an already-executed refund to `DAO`/`RefundOperator` roles only, since the stated use-case (consensus branch change) is an operator-level recovery action.

### Proof of Concept

1. Alice submits `request_refund` for UTXO `abc@0` with `refund_address = "bc1qalice..."`. The timelock elapses.
2. Alice calls `execute_refund("abc@0", None)` with the required attached deposit.
   - `load_refund_request_for_execute`: `verified_deposit_utxo` does not contain `"abc@0"` → check passes.
   - `finalize_refund_with_psbt`: inserts `BTCPendingInfo` with ID `psbt_A`, inserts `"abc@0"` into `verified_deposit_utxo`, sets `refund_request.executed = true`.
3. Bob (a fresh NEAR account) calls `execute_refund("abc@0", None)` with the required attached deposit.
   - `load_refund_request_for_execute`: `verified_deposit_utxo` contains `"abc@0"` **but** `refund_request.executed == true` → `!true || true = true` → check passes.
   - `finalize_refund_with_psbt`: PSBT is rebuilt (different fee schedule or nonce) → `btc_pending_id = psbt_B ≠ psbt_A` → uniqueness check passes → inserts a second `BTCPendingInfo` with ID `psbt_B` under Bob's account.
4. Charlie, Dave, … repeat step 3 with fresh accounts, each producing `psbt_C`, `psbt_D`, …
5. The MPC service signs all N PSBTs. Only one can confirm on Bitcoin. The remaining N-1 `BTCPendingInfo` entries are permanently stale and require a trusted relayer to call `remove_refund_pending_tx_id` for each.
