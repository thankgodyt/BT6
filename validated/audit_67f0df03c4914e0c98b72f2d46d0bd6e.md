### Title
Peras Certificate Validation Stub Unconditionally Accepts Any Certificate, Enabling Chain-Selection Weight Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate catch-all `BlockSupportsPeras` instance ships a `validatePerasCert` stub that unconditionally returns `Right` for every certificate, assigning it the full configured `perasWeight` boost without performing any cryptographic or semantic check. This stub is wired into the production certificate-ingestion path. An unprivileged peer can send crafted `PerasCert` messages that pass "validation", accumulate weight boosts on an adversarial fork, and cause honest nodes to prefer that fork over the canonical chain.

---

### Finding Description

**Root cause — stub validation always succeeds**

The `BlockSupportsPeras` class requires a `validatePerasCert` method. The only instance in the codebase is the degenerate catch-all:

### Impact Explanation

When Peras is enabled, an unprivileged peer can:

1. Send one crafted `PerasCert` per round, each pointing to a block on their adversarial fork.
2. Every certificate passes `validatePerasCert` unconditionally and is stored with the full `perasWeight` boost.
3. `weightBoostOfFragment` sums the boosts for all blocks in the adversarial fragment.
4. Once the adversarial fragment's `wsvTotalWeight` exceeds the honest chain's, `preferAnchoredCandidate` returns `ShouldSwitch`, and the honest node adopts the attacker's non-canonical chain.

This is a **chain-selection safety failure**: an honest node is made to prefer a less-secure or adversarially-controlled chain solely through unauthenticated certificate injection, with no stake, keys, or special privileges required.

**Allowed impact class matched**: *High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions*; and *Critical — bypass of Peras certificate checks that enables unauthorized certificate acceptance*.

---

### Likelihood Explanation

- **Entry point is fully reachable**: any connected peer can send `PerasCert` objects via the Peras certificate mini-protocol; `processCerts` is the production handler.
- **No privileges required**: no stake, no cryptographic keys, no operator access.
- **Condition**: Peras must be enabled (non-default but explicitly configurable). The CHANGELOG confirms the feature is present and the weight-based chain selection is active when enabled.
- **Stub is the only instance**: there is no more-specific `BlockSupportsPeras` instance for Cardano blocks that would override the degenerate one; the TODO comment and linked issue confirm this is intentional scaffolding, not a test artifact. [7](#0-6) 

---

### Recommendation

1. **Implement real validation** in `validatePerasCert` before Peras is enabled in any production deployment: verify the BLS aggregate signature over `(roundNo, boostedBlock)`, check committee-member eligibility against the stake distribution, and enforce round-number monotonicity constraints.
2. **Gate the feature**: keep Peras disabled (current default) until the validation is complete and audited.
3. **Remove the degenerate catch-all instance** or replace it with one that always returns `Left` (reject), so that any block type without a proper implementation fails closed rather than open.

---

### Proof of Concept

1. Enable Peras in the node configuration (`rnFeatureFlags`).
2. Connect as a peer to an honest node via the Peras certificate mini-protocol.
3. Craft a `PerasCert` with `pcCertRound = R` and `pcCertBoostedBlock = <point on adversarial fork>`.
4. Send it; `processCerts` calls `validatePerasCert mkPerasParams` → `Right ValidatedPerasCert{vpcCertBoost = perasWeight}`.
5. The certificate is stored; `implGetWeightSnapshot` returns a snapshot with the adversarial block boosted by `perasWeight`.
6. Repeat for rounds `R+1, R+2, …` targeting successive blocks on the adversarial fork.
7. `preferAnchoredCandidate` computes `wsvTotalWeight` for both fragments; once the adversarial fork's accumulated boost exceeds the honest chain's block-number advantage, `ShouldSwitch` is returned and the honest node rolls back to the adversarial chain.

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
