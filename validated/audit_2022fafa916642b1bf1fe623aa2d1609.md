Audit Report

## Title
`fin_transfer_send_tokens_callback` Ignores `ft_transfer` Failure, Permanently Freezing Native Tokens — (`near/omni-bridge/src/lib.rs`)

## Summary

When finalizing an inbound NEAR transfer with an empty `msg`, `process_fin_transfer_to_near` records the transfer as finalized via `add_fin_transfer` before dispatching `ft_transfer`. If `ft_transfer` fails (e.g., recipient is blacklisted by a USDC-style NEP-141 token), the callback `fin_transfer_send_tokens_callback` receives `is_ft_transfer_call = false`, causing `is_refund_required` to return `false` unconditionally without inspecting the promise result. No recovery path is taken, the transfer ID is consumed, and the bridged tokens are permanently locked.

## Finding Description

`process_fin_transfer_to_near` calls `add_fin_transfer` at line 1875, committing the transfer ID to `finalised_transfers` in the same receipt — before `send_tokens` is dispatched at line 1957. The callback is registered with `!msg.is_empty()` as `is_ft_transfer_call`, which is `false` when `msg` is empty. [1](#0-0) [2](#0-1) 

For native (non-deployed) tokens with an empty `msg`, `send_tokens` issues a plain `ft_transfer`: [3](#0-2) 

Inside `fin_transfer_send_tokens_callback`, the entire recovery path is gated on `is_refund_required`: [4](#0-3) 

`is_refund_required(false)` returns `false` unconditionally — it never calls `env::promise_result_checked`: [5](#0-4) 

When `ft_transfer` panics (e.g., blacklisted recipient), NEAR's receipt model reverts only the token contract's state. The bridge's `add_fin_transfer` state change is already committed. The callback takes the `else` branch, sends fees, and emits `FinTransferEvent` as if the transfer succeeded: [6](#0-5) 

`remove_fin_transfer` and `revert_lock_actions` are never called. The transfer ID is consumed, preventing any retry, and the tokens remain locked in the bridge with no admin escape hatch.

## Impact Explanation

This causes **permanent freezing of bridged funds**: native tokens (e.g., USDC as NEP-141) locked in the bridge on behalf of an inbound transfer become irrecoverable when `ft_transfer` to the recipient fails. The transfer ID is consumed from `finalised_transfers`, so the proof cannot be replayed. This matches the Critical impact category of permanent freezing of bridged funds.

## Likelihood Explanation

Circle's native USDC on NEAR implements a blacklist. A user whose NEAR address is blacklisted after initiating a cross-chain transfer — or already blacklisted when a relayer finalizes — triggers this path. The relayer cannot substitute a different recipient because the recipient is embedded in the verified proof. This is reachable by any unprivileged bridge user whose address is blacklisted by any supported NEP-141 token that can revert `ft_transfer`.

## Recommendation

1. Extend `is_refund_required` (or add a parallel check) to inspect `env::promise_result_checked(0, …)` even when `is_ft_transfer_call` is `false`. If the promise failed, execute the full recovery path: `burn_tokens_if_needed`, `revert_lock_actions`, `remove_fin_transfer`, and emit `FailedFinTransferEvent`.
2. Consider moving `add_fin_transfer` to after a successful `send_tokens` result, or use a two-phase commit pattern.
3. Add an admin escape hatch to forcibly remove a stuck finalized transfer and return locked tokens to a designated address as a last-resort recovery mechanism.

## Proof of Concept

1. Alice initiates a transfer of native USDC (NEP-141, blacklist-enabled) from Ethereum to `alice.near`.
2. Circle blacklists `alice.near` before the relayer finalizes.
3. Relayer calls `fin_transfer` on NEAR. `process_fin_transfer_to_near` runs:
   - `add_fin_transfer` records the transfer ID in `finalised_transfers` (line 1875) — state committed.
   - `send_tokens` dispatches `ft_transfer(alice.near, amount, None)` (lines 2102–2106).
4. USDC's `ft_transfer` panics because `alice.near` is blacklisted. Promise result is `Failed`.
5. `fin_transfer_send_tokens_callback` is called with `is_ft_transfer_call = false`.
6. `is_refund_required(false)` returns `false` without inspecting the promise result (lines 1800–1803).
7. The `else` branch runs: fees are sent and `FinTransferEvent` is logged as success (lines 1719–1746).
8. `remove_fin_transfer` and `revert_lock_actions` are never called. Alice's USDC is permanently locked. The transfer ID is consumed; no retry is possible.
