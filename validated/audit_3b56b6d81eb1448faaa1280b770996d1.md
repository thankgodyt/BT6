### Title
`withdraw_rbf` Missing Caller-Ownership Check Allows Any Account to Hijack a User's Pending Withdrawal — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary
`withdraw_rbf` reads `account_id` from `env::predecessor_account_id()` (the caller) instead of from the existing `BTCPendingInfo.account_id` (the original withdrawal owner). Any unprivileged NEAR account can invoke `withdraw_rbf` against another user's pending withdrawal, become the recorded owner of the resulting RBF `BTCPendingInfo`, and supply an attacker-controlled `output` vector. This is the direct analog of the Unlock Protocol H-03 bug: a state-transition branch that fails to preserve/reset the correct ownership field, leaving the original owner's account in a permanently inconsistent state and opening the door to output manipulation.

### Finding Description

`cancel_withdraw` correctly derives the owner from the stored pending info:

```rust
// bridge.rs lines 287-290
let user_account_id = self
    .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
    .account_id
    .clone();
```

`withdraw_rbf`, however, blindly uses the transaction predecessor:

```rust
// bridge.rs lines 265-273
pub fn withdraw_rbf(...) {
    let account_id = env::predecessor_account_id();   // ← attacker-controlled
    self.require_pending_sign_capacity(&account_id);
    self.withdraw_rbf_chain_specific(
        account_id,                                    // ← written into new BTCPendingInfo
        original_btc_pending_verify_id,
        output,                                        // ← fully attacker-controlled
        chain_specific_data,
    );
}
```

`BTCPendingInfo.account_id` is the field that governs:
- which account's `btc_pending_sign_ids` / `btc_pending_verify_list` is updated on creation and cleanup
- which account's pending-sign capacity is consumed

When an attacker calls `withdraw_rbf` on a victim's pending withdrawal:
1. A new `BTCPendingInfo` is inserted with `account_id = attacker`.
2. The victim's original pending info remains in `btc_pending_sign_ids` and is never cleaned up by the RBF lifecycle (cleanup targets `attacker`'s account).
3. The attacker supplies an arbitrary `output: Vec<TxOut>` — the Bitcoin outputs of the replacement transaction — which is passed directly into `withdraw_rbf_chain_specific`.

### Impact Explanation

**Confirmed Medium impact — attacker-triggered stuck state:**
The victim's account permanently retains the original stale pending ID in `btc_pending_sign_ids`. Because `require_pending_sign_capacity` enforces a per-account limit, the victim's withdrawal slot is consumed indefinitely, blocking all future withdrawals until an operator intervenes.

**Potential Critical impact — fund redirection:**
The `output` parameter is the set of Bitcoin `TxOut` values for the replacement transaction. If `withdraw_rbf_chain_specific` does not re-validate that the primary output still targets the original `target_btc_address` (the victim's BTC address), the attacker can redirect the bridge-held BTC to an address they control. The original withdrawal's nBTC has already been transferred to the bridge contract; the only remaining protection is output validation inside `withdraw_rbf_chain_specific`, which was not accessible for review.

### Likelihood Explanation

`withdraw_rbf` is a public, unpermissioned function callable by any NEAR account. No attached deposit, role, or prior relationship with the victim is required. The attacker only needs to know the `original_btc_pending_verify_id` of a pending withdrawal, which is emitted as a public on-chain event (`GenerateBtcPendingInfo`). Likelihood is **high** for the stuck-state impact and **conditional** (on output validation gaps) for the Critical fund-redirection impact.

### Recommendation

Mirror the pattern used in `cancel_withdraw`: derive `account_id` from the stored `BTCPendingInfo` rather than from the caller, and add an explicit ownership assertion:

```rust
pub fn withdraw_rbf(&mut self, original_btc_pending_verify_id: String, output: Vec<TxOut>, ...) {
    let caller = env::predecessor_account_id();
    let owner = self
        .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
        .account_id
        .clone();
    require!(caller == owner, "Only the withdrawal owner can submit an RBF");
    self.require_pending_sign_capacity(&owner);
    self.withdraw_rbf_chain_specific(owner, original_btc_pending_verify_id, output, ...);
}
```

Additionally, ensure `withdraw_rbf_chain_specific` re-validates that the primary output address matches the original `target_btc_address` stored in the pending info.

### Proof of Concept

1. Alice calls `ft_on_transfer` with a `Withdraw` message. A `BTCPendingInfo` is created with `account_id = alice`, `btc_pending_id = X`, and `target_btc_address = alice_btc`. The event `GenerateBtcPendingInfo { btc_pending_id: X }` is emitted publicly.
2. MPC signs the PSBT; the pending info advances to `PendingVerify`.
3. Attacker observes `X` on-chain and calls `withdraw_rbf(X, [TxOut { value: ..., script_pubkey: attacker_btc_script }], None)`.
4. Inside `withdraw_rbf`, `account_id = attacker` (not Alice). A new `BTCPendingInfo` with `account_id = attacker` and `btc_pending_id = Y` is inserted. Alice's account retains `X` in `btc_pending_sign_ids` forever.
5. If output validation is absent, the MPC network signs a transaction paying `attacker_btc_address`. Alice's nBTC (already held by the bridge) is burned, and the BTC is sent to the attacker. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
