### Title
Peras Certificate Validation Stub Unconditionally Accepts Any Peer-Supplied Certificate, Enabling Chain-Selection Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` method in the universal `BlockSupportsPeras` instance is a stub that always returns `Right` without performing any cryptographic or structural validation. Because Peras certificates are received from unprivileged peers via the object-diffusion mini-protocol and fed directly into chain selection, a peer can inject a certificate boosting any block of its choice. When Peras is active, this causes the node to use a manipulated `PerasWeightSnapshot` in `preferAnchoredCandidate`, potentially switching to a non-canonical chain.

---

### Finding Description

**Vulnerability class (analog to the external report):** The external report describes asymmetric output validation — one output (`baseProceeds`) is guarded by a slippage parameter while another (`withdrawalShares`) is not, letting an attacker manipulate the unguarded output. The analog here is that header validation is fully enforced (KES/VRF signatures, envelope checks), while Peras certificate validation is entirely absent — the "second output" of the chain-selection pipeline has no guard at all.

**Root cause — `validatePerasCert` stub:**

```haskell

This is the **universal instance** (`instance StandardHash blk => BlockSupportsPeras blk`), covering all block types including Cardano blocks. No signature verification, no quorum check, no round-number validity check, and no check that the boosted block is on a valid chain is performed. Any certificate supplied by a peer is wrapped in `ValidatedPerasCert` and returned as `Right`. [2](#0-1)

`implAddCert` only deduplicates by round number; it performs no content validation.

Once a certificate is added to the `PerasCertDB`, `chainSelSync` triggers chain selection for the boosted block:

The `weights` (`PerasWeightSnapshot`) is populated directly from the `PerasCertDB` via `implGetWeightSnapshot`, which reads every stored certificate without re-validating it. [6](#0-5) 

**Contrast with the validated path:** Header validation fully enforces KES/VRF signatures and envelope checks via `validateHeader` → `updateChainDepState` → `validateEnvelope`. The Peras certificate path has no equivalent enforcement. [7](#0-6) 

---

### Impact Explanation

When Peras is active (non-empty `PerasWeightSnapshot`), chain selection uses `WeightedSelectView.preferCandidate`, which compares `wsvTotalWeight = blockNo + weightBoost`. [8](#0-7) 

An attacker who injects a certificate boosting a block on an adversarial fork adds `perasWeight` (the configured boost, e.g. a value comparable to `k`) to that fork's total weight. If the adversarial fork is within `perasWeight` of the honest chain's total weight, the node will switch to it — a chain-selection safety failure triggered by a single unauthenticated network message. This matches the **High** impact category: an unprivileged peer causes an honest node to prefer a non-canonical chain beyond the intended security assumptions.

---

### Likelihood Explanation

**Medium.** The attack requires Peras to be enabled. The CHANGELOG notes Peras is disabled by default, but the code is shipped in production releases (introduced in v1.0.0.0, 2026-03-16) and can be enabled via configuration. Once enabled, the attack requires only that the adversary can connect to the target node and send a single object-diffusion message — no stake, no keys, no privileged access. The `implAddCert` deduplication (one cert per round) limits the attacker to one boost per round, but each round is a fresh opportunity.

---

### Recommendation

1. Implement actual cryptographic validation in `validatePerasCert`: verify the aggregate BLS signature over `(roundNo, boostedBlock)`, check that the claimed voters were eligible committee members for that round, and verify that the total stake of the voters meets the quorum threshold. The concrete `PerasCert` type in `Peras/Cert/V1.hs` already carries `pcSignature` and `pcVoters` for this purpose. [9](#0-8) 

2. Until real validation is implemented, gate `addPerasCertAsync` behind a feature flag that is enforced at the network layer, so that nodes with Peras disabled cannot receive certificates at all.

3. Track the open issue (tweag/cardano-peras#120) as a security-critical item, not merely a correctness TODO.

---

### Proof of Concept

**Attacker-controlled entry path:**

```
Adversarial peer
  → object-diffusion mini-protocol (MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs)
  → validatePerasCert cfg cert          -- always returns Right, no checks
  → ChainDB.addPerasCertAsync cert      -- certificate stored in PerasCertDB
  → chainSelSync (ChainSelAddPerasCert) -- chain selection triggered for boostedBlock
  → preferAnchoredCandidate ... weights -- adversarial fork gains perasWeight boost
  → node switches to adversarial chain  -- if boost tips the balance
```

**Concrete scenario:**

1. Honest chain tip is at block `N` with total weight `W_honest`.
2. Adversarial fork tip is at block `N` with total weight `W_adv = W_honest - perasWeight + 1` (just below the switch threshold).
3. Attacker sends a `PerasCert` for any block on the adversarial fork.
4. `validatePerasCert` returns `Right` unconditionally.
5. `implGetWeightSnapshot` now returns a snapshot with `perasWeight` boost for the adversarial block.
6. `preferAnchoredCandidate` computes `W_adv + perasWeight > W_honest` → `ShouldSwitch`.
7. Node rolls back to the adversarial fork.
