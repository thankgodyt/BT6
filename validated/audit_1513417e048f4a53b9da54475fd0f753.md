### Title
Safe Deposit Path Fails to Deduct Deposit Fee, Allowing Full-Amount nBTC Minting Without Fee Payment - (File: contracts/satoshi-bridge/src/btc_light_client/deposit.rs)

### Summary
The `internal_safe_verify_deposit` function passes the raw `deposit_amount` to `verify_safe_deposit_callback` without deducting the configured `deposit_bridge_fee`. As a result, users who trigger the safe-deposit path receive nBTC equal to the full deposited BTC amount, bypassing the protocol and relayer fee entirely.

### Finding Description
The regular deposit path in `internal_verify_deposit` correctly computes and deducts the fee before minting:

```rust
let deposit_fee = config.deposit_bridge_fee.get_fee(deposit_amount);
let mint_amount = deposit_amount - deposit_fee;
let (protocol_fee, relayer_fee) = config
    .deposit_bridge_fee
    .get_protocol_and_relayer_fee(deposit_fee);
// ...
.verify_deposit_callback(
    recipient_id,
    mint_amount.into(),      // fee-reduced amount
    protocol_fee.into(),
    relayer_fee.into(),
    ...
)
``` [1](#0-0) 

The safe deposit path in `internal_safe_verify_deposit` performs **no fee deduction at all** and passes the full `deposit_amount` directly as the `mint_amount` argument:

```rust
promise.then(
    Self::ext(env::current_account_id())
        .with_static_gas(GAS_FOR_VERIFY_DEPOSIT_CALL_BACK)
        .verify_safe_deposit_callback(
            recipient_id,
            deposit_amount.into(),   // ← full amount, no fee subtracted
            deposit_msg.msg,
            pending_utxo_info,
        ),
)
``` [2](#0-1) 

`verify_safe_deposit_callback` then calls `safe_mint` with this full amount, and `safe_mint_callback` confirms the omission by hardcoding `protocol_fee: U128(0)` and `relayer_fee: U128(0)` in the emitted event: [3](#0-2) 

The `BridgeFee::get_fee` function is defined and used for the regular path but is never called in the safe deposit path: [4](#0-3) 

The naming inconsistency is a strong indicator of a bug: the callback parameter is named `mint_amount` but receives the raw `deposit_amount`, whereas in the regular path `mint_amount` is always `deposit_amount - deposit_fee`. [5](#0-4) 

### Impact Explanation
Every user who uses the safe deposit path (by attaching the required NEAR storage deposit) receives `deposit_amount` nBTC instead of `deposit_amount - deposit_bridge_fee` nBTC. The protocol collects zero protocol fee and the relayer collects zero relayer fee for every such deposit. Over time this drains the protocol's fee revenue and removes the economic incentive for relayers to process safe deposits. This is a bypass of the bridge's fee policy.

### Likelihood Explanation
The safe deposit path is publicly reachable by any NEAR account that attaches the required NEAR storage deposit (`required_balance_for_safe_deposit()`). No privileged role is required. Any depositor who learns of this discrepancy can consistently exploit it to avoid paying the deposit fee on every BTC deposit. [6](#0-5) 

### Recommendation
Apply the same fee-deduction logic to the safe deposit path as is applied to the regular deposit path. Before calling `verify_safe_deposit_callback`, compute `deposit_fee`, `mint_amount`, `protocol_fee`, and `relayer_fee`, and pass them through to the callback so that `safe_mint` is called with the fee-reduced amount and the fees are properly accounted for.

### Proof of Concept
1. Alice deposits 1,000,000 satoshis to her safe-deposit address.
2. A relayer calls `safe_verify_deposit` with the valid Merkle proof and attaches the required NEAR storage deposit.
3. `internal_safe_verify_deposit` is called with `deposit_amount = 1_000_000`.
4. The function skips all fee computation and schedules `verify_safe_deposit_callback` with `mint_amount = 1_000_000`.
5. `safe_mint` mints 1,000,000 nBTC to Alice.
6. `safe_mint_callback` emits `protocol_fee = 0`, `relayer_fee = 0`.
7. If the configured `deposit_bridge_fee` has `fee_min = 10_000` and `protocol_fee_rate = 9000`, Alice should have received only 990,000 nBTC, with 9,000 going to the protocol and 1,000 to the relayer. Instead she receives the full 1,000,000 nBTC and neither the protocol nor the relayer receives any fee.
