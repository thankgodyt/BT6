### Title
Detached Burn Call in `safe_mint_callback` Silently Ignores Failure, Enabling Double-Mint — (`contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

---

### Summary

In `safe_mint_callback`, when the upstream `safe_mint` cross-contract call signals that a refund is required (by returning `U128(0)`), the bridge first removes the UTXO from `verified_deposit_utxo` and then fires a `burn` call on the nbtc contract using `.detach()`. Because `.detach()` is NEAR's fire-and-forget pattern — no callback is registered to observe the result — a failure of the `burn` call is silently swallowed. This leaves the bridge holding unbacked nBTC tokens while the UTXO guard is already cleared, making the same UTXO re-submittable for a second deposit.

---

### Finding Description

The `safe_mint` flow in the bridge is:

1. `verify_safe_deposit_callback` calls `safe_mint` on the nbtc contract.
2. `safe_mint` (`contracts/nbtc/src/lib.rs` lines 101–124) first deposits `amount` tokens into the bridge's own balance, then either returns `U128(0)` immediately (recipient not registered) or calls `ft_transfer_call` to the recipient.
3. `safe_mint_callback` is invoked as the next promise in the chain.

Inside `safe_mint_callback`, the helper `is_refund_required()` returns `true` when `safe_mint` returned `U128(0)` — meaning the tokens were never transferred out of the bridge's balance (or were fully refunded back to it). The callback then:

```rust
// contracts/satoshi-bridge/src/btc_light_client/deposit.rs  lines 439–451
self.data_mut()
    .verified_deposit_utxo
    .remove(&pending_utxo_info.utxo_storage_key);   // ← UTXO guard cleared

ext_nbtc::ext(self.internal_config().nbtc_account_id.clone())
    .with_static_gas(GAS_FOR_BURN_CALL)
    .burn(
        env::current_account_id(),
        mint_amount,
        relayer_account_id,
        U128(0),
    )
    .detach();                                        // ← fire-and-forget, no callback
``` [1](#0-0) 

The UTXO guard is removed **before** the burn is dispatched, and the burn result is never observed. Contrast this with every other critical cross-contract call in the codebase — `verify_withdraw_burn_promise`, `internal_mint_promise`, `internal_transfer_nbtc` — all of which register a callback that checks `is_promise_success()` and rolls back state on failure. [2](#0-1) [3](#0-2) 

The `burn` function in the nbtc contract withdraws from `self.bridge_id`'s balance:

```rust
// contracts/nbtc/src/lib.rs  lines 150–177
pub fn burn(&mut self, burn_account_id: AccountId, burn_amount: U128, ...) {
    self.assert_bridge();
    self.token.internal_withdraw(&self.bridge_id, burn_amount.into());
    ...
}
``` [4](#0-3) 

If `internal_withdraw` panics (bridge balance insufficient, nbtc contract upgraded/paused, or gas exhausted within the 5 Tgas budget), the panic is silently discarded because `.detach()` registers no callback.

---

### Impact Explanation

When the detached `burn` fails:

1. `verified_deposit_utxo` no longer contains the UTXO key — the double-spend guard is gone.
2. The bridge's nbtc balance retains `mint_amount` tokens that were never burned — unbacked supply exists.
3. Any relayer (or the original depositor) can re-submit the same Bitcoin UTXO through `verify_deposit` or `safe_verify_deposit`. The light-client proof is valid (the BTC transaction is real), the UTXO key is absent from `verified_deposit_utxo`, so the deposit passes the deduplication check and mints a second batch of nBTC against the same on-chain BTC.

This constitutes unauthorized minting and permanent inflation of nBTC supply beyond its BTC backing.

---

### Likelihood Explanation

The burn fails silently whenever the nbtc contract panics during `internal_withdraw`. Concrete triggers:

- **Gas exhaustion**: `GAS_FOR_BURN_CALL` is only 5 Tgas. If the nbtc contract is upgraded to add logic before or after `internal_withdraw`, this budget may be insufficient.
- **nbtc contract upgrade**: The nbtc contract is controlled by a `controller` account. A future upgrade adding a pause mechanism (analogous to Lido's `pauseStaking`) would cause `burn` to revert. Since the call is `.detach()`, the revert is invisible to the bridge.
- **Balance race**: Although unlikely under NEAR's sequential execution model, any accounting discrepancy that leaves the bridge's nbtc balance below `mint_amount` at burn time causes `internal_withdraw` to panic.

The nbtc contract is explicitly designed to be upgradeable, making the "future pause" scenario a realistic operational risk rather than a purely theoretical one.

---

### Recommendation

Replace the fire-and-forget `.detach()` burn with a proper callback chain. If the burn fails, the callback should re-insert the UTXO key into `verified_deposit_utxo` to restore the double-spend guard:

```rust
// Instead of:
ext_nbtc::ext(...).burn(...).detach();

// Use:
ext_nbtc::ext(...).burn(...).then(
    Self::ext(env::current_account_id())
        .with_static_gas(GAS_FOR_SAFE_MINT_BURN_CALLBACK)
        .safe_mint_burn_callback(pending_utxo_info.utxo_storage_key.clone()),
);

// In safe_mint_burn_callback:
#[private]
pub fn safe_mint_burn_callback(&mut self, utxo_storage_key: String) {
    if !is_promise_success() {
        // Restore the guard so the UTXO cannot be re-deposited
        self.data_mut().verified_deposit_utxo.insert(utxo_storage_key);
        // Optionally emit an alert event for operator intervention
    }
}
```

This mirrors the pattern already used by `verify_withdraw_burn_callback` and `mint_callback`, which both check `is_promise_success()` and revert state on failure. [5](#0-4) 

---

### Proof of Concept

**Entry path** (unprivileged NEAR account):

1. Attacker deposits BTC to a bridge-derived address. The BTC transaction is confirmed on-chain.
2. Attacker calls `safe_verify_deposit` with a valid Merkle proof and a `recipient_id` whose NEAR account is **not registered** in the nbtc contract.
3. `verify_safe_deposit_callback` passes the light-client check, inserts the UTXO key into `verified_deposit_utxo`, and calls `safe_mint(recipient, amount, msg)`.
4. Inside `safe_mint`, `self.token.accounts.get(&account_id).is_none()` is `true` → returns `U128(0)` immediately. The bridge's nbtc balance now holds `amount` tokens.
5. `safe_mint_callback` runs: `is_refund_required()` → `true`; `is_success = false`. The UTXO key is removed from `verified_deposit_utxo`.
6. `burn(bridge, amount)` is dispatched with `.detach()`. Suppose the nbtc contract has been upgraded to include a pause check that reverts — the burn panics and the panic is discarded.
7. Bridge state: `verified_deposit_utxo` does not contain the UTXO key; bridge nbtc balance holds `amount` unbacked tokens.
8. Attacker (or any relayer) re-submits the same `safe_verify_deposit` call with the same proof. The UTXO key is absent from `verified_deposit_utxo`, so the deduplication `require!` passes. A second `safe_mint` is issued, minting another `amount` nBTC against the same BTC UTXO. [6](#0-5) [7](#0-6) [8](#0-7)

        }
    }
