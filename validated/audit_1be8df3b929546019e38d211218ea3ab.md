Audit Report

## Title
`send_fee_internal` Detaches Native-Fee Promise and Emits `ClaimFeeEvent` Before Token Transfer Resolves, With No Failure Recovery — (`near/omni-bridge/src/lib.rs`)

## Summary

In `send_fee_internal`, the native-fee sub-transfer is fire-and-forgotten via `.detach()`, `unlock_tokens_if_needed` and `ClaimFeeEvent` are committed synchronously, and the token-fee cross-contract call is returned with no chained failure callback. Because `remove_transfer_message` has already executed in `claim_fee_callback`, any failure in either sub-transfer permanently destroys the relayer's fee with no recovery path. The same detach-then-mutate-then-log pattern in `utxo_fin_transfer_fast` and `process_fin_transfer_to_other_chain` causes identical permanent fund loss for fast-transfer relayers.

## Finding Description

**Call chain for `claim_fee`:**

```
claim_fee [#trusted_relayer]
  → verify_proof (cross-contract)
    → claim_fee_callback [#private]
        → remove_transfer_message (L1094)   ← state permanently removed
        → send_fee_internal
            → Promise::transfer / mint .detach() (L2665–2673)  ← result ignored
            → unlock_tokens_if_needed (L2684)                  ← escrow updated
            → env::log_str(ClaimFeeEvent) (L2677–2682)         ← event committed
            → ft_transfer / mint returned (L2686–2698)         ← no failure callback
```

**Issue A – Native fee is detached.** At lines 2664–2673, `Promise::new(fee_recipient).transfer(...)` and `ext_token::ext(...).mint(...).detach()` both discard their result. If the NEAR transfer fails (non-existent or zero-balance account) or the wrapped-token mint fails (out-of-gas, paused token), the native fee is silently lost.

**Issue B – `ClaimFeeEvent` and `unlock_tokens_if_needed` precede the token-fee transfer.** At line 2684, `unlock_tokens_if_needed` decrements the locked-token counter before the transfer executes. At lines 2677–2682, `ClaimFeeEvent` is logged synchronously. The token-fee cross-contract call at lines 2686–2698 is returned as a bare `PromiseOrValue<()>` with no `.then(callback)`. If `ft_transfer` panics (e.g., recipient not registered for NEP-141 storage), the failure receipt is silently dropped: the event is already on-chain, the locked-token counter is already decremented, and the transfer message is already gone.

**Same pattern in `utxo_fin_transfer_fast` (L2542–2558):** `send_tokens(...).detach()` is called, then `remove_fast_transfer` / `mark_fast_transfer_as_finalised` mutates state, then `UtxoTransferEvent` is logged — all before any confirmation that tokens moved.

**Same pattern in `process_fin_transfer_to_other_chain` (L2029–2053):** `send_tokens(...).detach()` is called, then `mark_fast_transfer_as_finalised` permanently marks the entry finalised, then `FinTransferEvent` is logged.

The developer-inserted `// TODO: check how to deal with failed send_tokens` comment at line 2484 confirms awareness that `send_tokens` failure handling is unresolved.

## Impact Explanation

This matches two allowed Critical impact classes:

1. **Loss of bridged/relayer funds**: The relayer's earned fee (native NEAR and/or bridged token) is permanently unrecoverable. `remove_transfer_message` has already executed; there is no stored state to retry from. The relayer receives nothing.

2. **Escrow mis-accounting / fee mis-accounting**: `unlock_tokens_if_needed` decrements the locked-token counter at line 2684 before the transfer succeeds. If the transfer fails, the contract's internal accounting records fewer locked tokens than actually exist, corrupting the escrow ledger permanently.

## Likelihood Explanation

The failure conditions are realistic and reachable by any relayer operating through normal bridge flows:

1. **NEP-141 storage registration**: Any fee recipient that has not called `storage_deposit` on the bridged token contract will cause `ft_transfer` to panic. This is a standard NEP-141 requirement and a common operational oversight.
2. **Fixed static gas constants**: `MINT_TOKEN_GAS` and `FT_TRANSFER_GAS` are compile-time constants. Under network congestion or token contract complexity, these can be exhausted.
3. **Token contract panic**: A paused, blacklisted, or otherwise restricted token contract will cause the sub-call to fail silently.

Condition 1 alone is sufficient and requires no special attacker capability — a relayer simply needs to not have pre-registered storage for the token they are claiming fees in.

## Recommendation

1. **Remove `.detach()` on native-fee transfers** and chain them with the token-fee promise so both are part of a single promise chain.
2. **Move `env::log_str(ClaimFeeEvent)` and `unlock_tokens_if_needed` into a `#[private]` callback** that fires only after both the native-fee and token-fee promises resolve successfully.
3. **Add a failure branch** in that callback that re-inserts the transfer message (or credits the fee to a claimable escrow) so the relayer can retry.
4. Apply the same pattern to `utxo_fin_transfer_fast` and `process_fin_transfer_to_other_chain`: replace `.detach()` with a chained callback that emits the event and mutates state only on success, and restores state on failure.

## Proof of Concept

1. Relayer (trusted) calls `claim_fee` for a transfer with `fee.native_fee == 0` and `token_fee > 0`, where `fee_recipient` has never called `storage_deposit` on the bridged token contract.
2. `claim_fee_callback` executes: `remove_transfer_message` removes the transfer at line 1094 — state is permanently gone.
3. `send_fee_internal` is entered. Native-fee branch is skipped (`native_fee == 0`).
4. `unlock_tokens_if_needed` decrements the locked-token counter at line 2684 — escrow is now mis-accounted.
5. `ClaimFeeEvent` is logged at lines 2677–2682 — event is committed on-chain.
6. `ft_transfer(fee_recipient, token_fee, None)` is dispatched at line 2696. Because the recipient has no storage registration, the NEP-141 token contract panics and the receipt fails.
7. No callback exists to catch this failure. The failed receipt is silently dropped.
8. **Result**: transfer message is gone, locked-token counter is decremented, `ClaimFeeEvent` is on-chain, relayer received zero fee. No retry is possible.

To reproduce locally: deploy the omni-bridge contract and a NEP-141 token contract on a NEAR sandbox; submit a valid `claim_fee` proof for a transfer whose `fee_recipient` has no storage registration on the token contract; observe that the `ClaimFeeEvent` is emitted in the transaction logs while the `ft_transfer` receipt fails, and confirm that `get_transfer_message` returns nothing (message is gone) and the locked-token balance is decremented.
