Audit Report

## Title
Fee and Escrow Mis-Accounting on `ft_transfer` Failure in `send_fee_internal` — (`near/omni-bridge/src/lib.rs`)

## Summary

`claim_fee_callback` permanently removes the pending transfer record and credits storage back to the owner before `send_fee_internal` dispatches the `ft_transfer` promise. `send_fee_internal` additionally emits `ClaimFeeEvent` and decrements `locked_tokens` before the promise is dispatched, and attaches no failure callback. If `ft_transfer` fails, the fee tokens remain in the bridge's NEP-141 balance but are no longer tracked by `locked_tokens`, the `TransferId` is gone from `pending_transfers`, and there is no recovery path short of a contract upgrade.

## Finding Description

The call chain is confirmed by the code:

1. `claim_fee_callback` (line 1094) calls `remove_transfer_message`, which permanently removes the entry from `pending_transfers` and credits the storage refund to the transfer owner. [1](#0-0) 

2. `claim_fee_callback` then calls `send_fee_internal` (line 1133). [2](#0-1) 

3. Inside `send_fee_internal`, `ClaimFeeEvent` is emitted (lines 2677–2682) and `unlock_tokens_if_needed` decrements `locked_tokens` (line 2684) **before** the `ft_transfer` promise is returned. No `.then(callback)` is attached to the returned promise. [3](#0-2) 

4. `unlock_tokens_if_needed` unconditionally decrements the `locked_tokens` map entry for the token/chain pair. [4](#0-3) 

In NEAR's execution model, all state mutations in `claim_fee_callback` and `send_fee_internal` are committed when those functions return. The `ft_transfer` executes in a subsequent receipt. If it fails (e.g., the fee recipient has no storage deposit on the NEP-141 token contract), there is no callback to revert the deletion or re-increment `locked_tokens`. The fee tokens remain in the bridge's NEP-141 balance but are permanently untracked.

The BTC path in `submit_transfer_to_btc_connector_callback` demonstrates the correct pattern — it re-inserts the transfer on failure — but this guard is absent from the non-BTC `claim_fee` path. [5](#0-4) 

## Impact Explanation

This concretely matches the Critical allowed impact: **fee mis-accounting and escrow mis-accounting that changes protocol balances**. `locked_tokens` is decremented (signaling the bridge released the tokens) while the bridge's actual NEP-141 balance still holds them. The `ClaimFeeEvent` is emitted and the transfer record is deleted before delivery is confirmed, permanently breaking the bridge's escrow invariant with no on-chain recovery path.

## Likelihood Explanation

`claim_fee` is gated by `#[trusted_relayer]`, but relayer flows are explicitly listed as a valid trigger path in the scope rules. The trigger condition — a trusted relayer whose account lacks a storage deposit on the specific bridged NEP-141 token — is operationally plausible for newly listed tokens or tokens the relayer has never interacted with. No adversarial third party is required; the relayer can trigger this accidentally. The condition is repeatable across any token for which the relayer lacks storage registration. [6](#0-5) [7](#0-6) 

## Recommendation

Attach a failure callback to the `ft_transfer` promise in `send_fee_internal` for non-deployed tokens. On failure, re-insert the transfer message into `pending_transfers` and re-increment `locked_tokens`. Alternatively, move `remove_transfer_message` and `unlock_tokens_if_needed` into the success callback so state is only mutated after confirmed delivery. `ClaimFeeEvent` should also be emitted only inside the success callback. The existing `revert_lock_actions` helper and the BTC path's re-insertion pattern provide the building blocks for this fix. [8](#0-7) 

## Proof of Concept

1. Deploy the bridge on localnet with a standard NEP-141 token contract.
2. Initiate a cross-chain transfer with a non-zero fee; confirm the entry exists in `pending_transfers` via `get_transfer_message`.
3. Register a trusted relayer account that has **no storage deposit** on the NEP-141 token contract.
4. Call `claim_fee` from the relayer account with a valid `FinTransfer` proof where `fee_recipient` equals the relayer.
5. Observe: `claim_fee_callback` succeeds; `ClaimFeeEvent` appears in logs; `get_transfer_message` returns `TransferNotExist`; `get_locked_tokens` for the token is decremented; but the relayer's token balance on the NEP-141 contract is unchanged and the bridge's NEP-141 balance still holds the fee tokens — permanently untracked.
