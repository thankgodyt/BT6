Audit Report

## Title
Cross-Chain Replay of `deployToken` Signature Due to Missing Chain ID in Metadata Hash — (`evm/src/omni-bridge/contracts/OmniBridge.sol`, `starknet/src/bridge_types.cairo`, `solana/programs/bridge_token_factory/src/state/message/deploy_token.rs`)

## Summary

The `deployToken`/`deploy_token` signature hash across EVM, Starknet, and Solana bridge contracts omits any chain identifier from the signed payload. Because the same NEAR MPC-derived address (`nearBridgeDerivedAddress`) is used across all destination chains, a single valid NEAR MPC signature for a `MetadataPayload` is cryptographically valid on every supported chain simultaneously. An unprivileged attacker who observes a legitimate `deployToken` transaction on one chain can replay the identical calldata on every other chain, deploying bridge tokens without NEAR ever authorizing the deployment on those chains.

## Finding Description

**EVM root cause (`OmniBridge.sol` lines 142–149):**

The `deployToken` function constructs the signed hash as:

```
keccak256(PayloadType.Metadata | token | name | symbol | decimals)
``` [1](#0-0) 

No `omniBridgeChainId` is included. By contrast, `finTransfer` (lines 289–309) embeds `omniBridgeChainId` twice in the hash, making those signatures chain-specific. [2](#0-1) 

**Starknet root cause (`bridge_types.cairo` lines 36–44):**

`MetadataPayloadImpl::to_borsh()` serializes only `PayloadType::Metadata | token | name | symbol | decimals` with no `chain_id` argument accepted or included. [3](#0-2) 

`TransferMessagePayloadImpl::to_borsh(chain_id: u8)` accepts and embeds `chain_id` at lines 61–71, demonstrating the pattern exists and was intentionally applied to transfers but not to metadata. [4](#0-3) 

The Starknet `deploy_token` calls `payload.to_borsh()` with no argument, while `fin_transfer` calls `payload.to_borsh(self.omni_bridge_chain_id.read())`. [5](#0-4) [6](#0-5) 

**Solana root cause (`deploy_token.rs` lines 19–26):**

`DeployTokenPayload::serialize_for_near()` writes only `IncomingMessageType::Metadata` followed by the borsh-encoded struct. No `SOLANA_OMNI_BRIDGE_CHAIN_ID` is written, unlike `FinalizeTransferPayload::serialize_for_near()` which writes `SOLANA_OMNI_BRIDGE_CHAIN_ID` for both the token and recipient fields. [7](#0-6) [8](#0-7) 

**NEAR signing root cause (`lib.rs` lines 341–365):**

`log_metadata_callback` constructs a `MetadataPayload` with only `prefix | token | name | symbol | decimals` and signs it via MPC. No destination chain ID is included in the payload before signing. [9](#0-8) 

**Same key across all chains:**

The deployment script derives `nearBridgeDerivedAddress` using a fixed path `"bridge-1"` and the same MPC root public key for all EVM chains. Every EVM `OmniBridge` deployment shares the same `nearBridgeDerivedAddress`. [10](#0-9) 

**Exploit flow:**

1. Attacker observes a legitimate `deployToken(signatureData, metadata)` call on Ethereum. Extracts `signatureData` from public calldata.
2. Calls `deployToken(signatureData, metadata)` on Arbitrum's `OmniBridge` with identical arguments.
3. Arbitrum computes `keccak256(Metadata | token | name | symbol | decimals)` — identical to Ethereum's hash — and `ECDSA.recover` returns the same `nearBridgeDerivedAddress`. Signature verification passes.
4. A new `BridgeToken` is deployed on Arbitrum and `nearToEthToken[metadata.token]` is set, `isBridgeToken` is marked.
5. Any subsequent legitimate `deployToken` for the same NEAR token ID on Arbitrum reverts with `ERR_TOKEN_EXIST`. [11](#0-10) 

6. Attacker submits a proof of the replayed `DeployToken` event to NEAR's `deploy_token`. The `deploy_token_callback` checks only that the emitter is the registered factory for that chain — which it is — and registers the attacker-triggered token address as canonical. [12](#0-11) 

## Impact Explanation

This is a **Critical** finding matching two allowed impact classes:

1. **Cross-chain replay / chain/domain separation flaw**: A signature valid on one chain is accepted on all other chains due to the absence of a chain identifier in the signed payload. This is a direct chain/domain separation failure.

2. **Unauthorized deployer-equivalent action / authorization bypass**: An unprivileged attacker executes the deployer role (deploying bridge tokens and registering them on NEAR) on chains for which NEAR never issued authorization. Once the replayed deployment is registered on NEAR via proof submission, NEAR treats an unauthorized deployment as canonical, permanently locking out the legitimate deployment path for that token on that chain (`ERR_TOKEN_EXIST`).

## Likelihood Explanation

- All EVM `OmniBridge` deployments share the same `nearBridgeDerivedAddress` (same MPC key, same derivation path `"bridge-1"`).
- Every `deployToken` transaction is public on-chain; the signature is trivially extractable from calldata.
- No special access, private keys, or admin compromise is required — any observer of a `deployToken` transaction on one chain can replay it on all others.
- The bridge is live on Ethereum, Arbitrum, Base, and Polygon simultaneously, making the replay surface immediately available.
- The attack is repeatable for every new token that gets deployed via `deployToken`.

## Recommendation

Include the destination chain identifier in the `MetadataPayload` hash for all three implementations:

**EVM** — add `omniBridgeChainId` to the `borshEncoded` bytes in `deployToken`:
```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
    bytes1(omniBridgeChainId),   // add this
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
```

**Starknet** — change `MetadataPayloadImpl::to_borsh()` to accept and embed `chain_id: u8`, mirroring `TransferMessagePayloadImpl::to_borsh(chain_id)`. Update the `deploy_token` call site to pass `self.omni_bridge_chain_id.read()`.

**Solana** — write `SOLANA_OMNI_BRIDGE_CHAIN_ID` into `DeployTokenPayload::serialize_for_near()` before the token fields, mirroring the pattern already used in `FinalizeTransferPayload`.

**NEAR** — update `log_metadata_callback` to include the destination chain ID in the payload it signs, so that chain-bound signatures are produced correctly. This requires `log_metadata` to accept a destination chain parameter.

## Proof of Concept

**Minimal reproducible test (Hardhat/EVM):**

1. Deploy two `OmniBridge` instances with the same `nearBridgeDerivedAddress` but different `omniBridgeChainId` values (simulating Ethereum and Arbitrum).
2. Call `deployToken(signatureData, metadata)` on instance 1 with a valid signature (as done in the existing test suite via `metadataSignature`).
3. Call `deployToken(signatureData, metadata)` on instance 2 with the **identical** `signatureData` and `metadata`.
4. Assert that the call on instance 2 succeeds and a `BridgeToken` is deployed — demonstrating the replay.

The existing test infrastructure in `evm/tests/BridgeToken.ts` already constructs valid `metadataSignature` values and calls `deployToken`; extending it with a second bridge instance with a different `omniBridgeChainId` is sufficient to demonstrate the replay. [13](#0-12)
