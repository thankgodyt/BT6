### Title
Unconditional `validatePerasCert` Acceptance Allows Any Peer to Inject Fake Peras Certificates and Manipulate Chain Selection — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` for every certificate it receives, performing zero cryptographic verification. This stub is wired directly into the production Peras certificate diffusion inbound handler in `NodeToNode.hs`. Any unprivileged peer can send a crafted `PerasCert` targeting any block, have it accepted as "validated," and trigger a Peras-weight-boosted chain selection that may cause the honest node to switch to a non-canonical chain.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub used in production:**

The universal `BlockSupportsPeras` instance in `SupportsPeras.hs` provides a default implementation for all block types:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This function accepts every certificate unconditionally. No signature is checked, no committee quorum is verified, no round/slot constraints are enforced. The `PerasValidationErr` data type is itself a stub with a single opaque constructor:

```haskell
data PerasValidationErr blk = PerasValidationErr
``` [2](#0-1) 

This universal instance (`instance StandardHash blk => BlockSupportsPeras blk`) applies to all block types including the Cardano block, because no more-specific override exists in the audited production source. [3](#0-2) 

**Attacker-controlled entry path — production cert diffusion inbound handler:**

The production node-to-node handler in `NodeToNode.hs` wires the inbound Peras certificate diffusion directly to `makePerasCertPoolWriterFromChainDB`:

```haskell
, hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      version
      controlMessageSTM
``` [4](#0-3) 

The pool writer calls `validatePerasCert` on each received certificate. Because `validatePerasCert` always returns `Right`, every certificate from every peer passes validation and is forwarded to `addPerasCertAsync`.

**State mutation — cert is added to ChainDB and triggers chain selection:**

`addPerasCertAsync` enqueues the accepted certificate into the chain-selection queue:

```haskell
addPerasCertAsync CDB{cdbTracer, cdbChainSelQueue} =
  addPerasCertToQueue (TraceAddPerasCertEvent >$< cdbTracer) cdbChainSelQueue
``` [5](#0-4) 

The ChainDB API exposes `addPerasCertAsync` as a first-class operation that "may trigger a fork switch": [6](#0-5) 

Once the certificate is accepted, the Peras weight boost (`vpcCertBoost = perasWeight params`) is applied to the attacker-chosen block, making that block's chain heavier in chain selection.

**Contrast with the vote path (partially mitigated):**

The vote diffusion handler passes an empty stake distribution `(pure (PerasVoteStakeDistr mempty))`, which causes all votes to fail the stake-lookup check in `validatePerasVote` and be rejected. The certificate path has no equivalent guard — `validatePerasCert` ignores its `params` argument entirely and never fails. [7](#0-6)

### Impact Explanation

**Severity: High — Chain selection manipulation by an unprivileged peer.**

An attacker who can establish a node-to-node connection (any peer on the network) can:

1. Craft a `PerasCert` naming any block point and any round number.
2. Send it via the Peras certificate diffusion miniprotocol.
3. The node accepts it unconditionally, applies the Peras weight boost to the attacker's chosen block, and may switch its preferred chain to a fork that would otherwise lose chain selection.

This directly violates the Peras security invariant: only a certificate backed by a genuine quorum of committee signatures should be able to boost a block's chain weight. Without signature verification, the weight boost is freely grantable by any peer, breaking the chain-selection security assumption that Peras is designed to strengthen.

This falls under: **High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.**

---

### Likelihood Explanation

**High likelihood.** The attack requires only a standard node-to-node connection, which any participant on the Cardano network can establish. No keys, stake, or special privileges are needed. The attacker simply sends a well-formed (but cryptographically unsigned/invalid) `PerasCert` message over the Peras certificate diffusion miniprotocol. The code path is unconditional — there is no guard that could accidentally block the attack.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real one that:

1. Verifies the aggregate BLS signature over the certificate against the committee's aggregate verification key.
2. Confirms the certificate's round number and boosted block point are within valid bounds.
3. Checks that the signers constitute a valid quorum per the `PerasCfg`.

Until the real implementation is ready, the inbound cert diffusion handler should reject all incoming certificates (analogous to how the vote handler uses an empty stake distribution to reject all votes), preventing any peer from influencing chain selection via the Peras weight mechanism.

---

### Proof of Concept

**Preconditions:** Attacker has a standard node-to-node TCP connection to the target node (no keys or stake required).

**Steps:**

1. Attacker connects to the target node and negotiates the Peras certificate diffusion miniprotocol.
2. Attacker constructs a `PerasCert` with:
   - `pcCertRound` = any round number
   - `pcCertBoostedBlock` = the `Point` of a block on the attacker's preferred (weaker) fork
3. Attacker sends the certificate via `objectDiffusionInbound`.
4. `makePerasCertPoolWriterFromChainDB` calls `validatePerasCert` on the received cert.
5. `validatePerasCert` returns `Right ValidatedPerasCert{vpcCertBoost = perasWeight params}` without any check.
6. `addPerasCertAsync` enqueues the cert into `cdbChainSelQueue`.
7. The chain-selection loop processes the cert, applies the Peras weight boost to the attacker's block, and — if the boosted weight exceeds the honest chain's weight — switches the node's preferred chain to the attacker's fork.

**Expected outcome:** The honest node's `getCurrentChain` now returns the attacker-chosen fork, and the node begins building on and diffusing that fork to its own peers. [1](#0-0) [4](#0-3) [5](#0-4)
