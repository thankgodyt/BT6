### Title
Whole-batch Peras vote rejection on any invalid vote silently drops all valid votes in the batch — (`processVotes` in `ObjectPool/PerasVote.hs`)

---

### Summary

`processVotes`, the sole inbound handler for Peras votes received over the `PerasVoteDiffusion` miniprotocol, throws a `PerasVoteValidationError` exception and discards the **entire batch** whenever any single vote fails validation. Valid votes present in the same batch are silently dropped. An unprivileged peer can exploit this by injecting one trivially-crafted invalid vote alongside valid votes from legitimate committee members, causing the receiving node to lose those valid votes and potentially preventing quorum from being reached for a Peras round. This is the direct structural analog of M-5: a "throw instead of skip/continue" pattern that allows a crafted network input to suppress a legitimate consensus operation.

---

### Finding Description

The root cause is in `processVotes`:

```haskell
case partitionEithers validationResults of
  -- All votes are valid => add them to the pool
  ([], validatedVotes) ->
    mapM_ (addVote . WithArrivalTime now) validatedVotes
  -- Some votes are invalid => reject the whole batch
  (errs, _) ->
    throw (PerasVoteValidationError errs)
``` [1](#0-0) 

The `(errs, _)` arm of `partitionEithers` discards the `_` component — the list of already-validated valid votes — whenever `errs` is non-empty. The function's own documentation confirms the intent: "if *any* vote in the batch fails validation, the entire batch is rejected by throwing a `PerasVoteInboundException` (which should make us disconnect from the distant peer)." [2](#0-1) 

Vote validation (`validatePerasVote`) currently only checks whether the voter's ID appears in the stake distribution:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr = Right ...
  | otherwise = Left PerasValidationErr
``` [3](#0-2) 

`lookupPerasVoteStake` is a plain `Map.lookup` on the voter ID: [4](#0-3) 

An attacker therefore needs only to supply a `PerasVoterId` (a `KeyHash StakePool`) that is absent from the stake distribution — no cryptographic secret is required. The production wiring in `NodeToNode.hs` passes an **empty** stake distribution today:

```haskell
( makePerasVotePoolWriterFromChainDB
    systemTime
    -- Note that the empty stake distribution will cause all votes to
    -- be considered invalid.
    (pure (PerasVoteStakeDistr mempty))
    getChainDB
)
``` [5](#0-4) 

This means that in the current production build every inbound vote is already invalid, so the batch-rejection path is always taken. Once a real stake distribution is wired in (the stated TODO), the mixed-batch attack becomes directly exploitable.

---

### Impact Explanation

Peras certificates are forged only when a quorum of valid votes accumulates for the same target block in a round. A certificate causes the boosted block's chain to receive additional `PerasWeight`, which is added to the block number when comparing candidate chains:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [6](#0-5) 

Chain selection uses `wsvTotalWeight` as the primary comparator: [7](#0-6) 

If an attacker suppresses quorum for a round, no certificate is forged, no weight boost is applied to the honest chain, and chain selection may prefer a competing chain that already carries a boost from a prior round. This is a **chain-selection weakening** caused by a miniprotocol flaw that materially weakens vote authorization — matching the "Medium" allowed impact scope.

---

### Likelihood Explanation

The attack requires only that the adversary:

1. Be a connected peer (unprivileged, no stake, no keys required).
2. Observe valid votes being broadcast on the network (votes are public objects diffused to all peers).
3. Craft one vote with an arbitrary `PerasVoterId` not in the stake distribution (no cryptographic material needed — the voter ID is a plain `KeyHash`).
4. Send a batch containing the crafted invalid vote plus the observed valid votes to the target node before those valid votes arrive from other peers.

The attacker is then disconnected, but can reconnect and repeat for subsequent rounds. The valid votes that were dropped are not retransmitted by the disconnected peer; whether they arrive from other peers depends on network topology and timing.

---

### Recommendation

Replace the all-or-nothing batch rejection with per-vote handling: skip (log and discard) invalid votes and add valid ones, analogous to the M-5 fix of using `continue` instead of reverting. The corrected logic would use the `validatedVotes` component of `partitionEithers` unconditionally:

```haskell
case partitionEithers validationResults of
  ([], validatedVotes) ->
    mapM_ (addVote . WithArrivalTime now) validatedVotes
  (errs, validatedVotes) -> do
    logInvalidVotes errs          -- trace/log, optionally disconnect peer
    mapM_ (addVote . WithArrivalTime now) validatedVotes
```

If disconnecting the peer on any invalid vote is a deliberate policy (to punish misbehaving peers), the valid votes should still be added to the DB **before** disconnecting, so that honest votes in the same batch are not lost.

---

### Proof of Concept

**Setup**: A private testnet with Peras enabled and a real stake distribution wired in. Node A is connected to attacker peer P and honest peer H.

1. Honest committee members broadcast votes for block B in round R. Peer H has collected votes `[v1, v2, v3]` sufficient for quorum.
2. Attacker P also observes `[v1, v2, v3]` from the network.
3. P crafts `v_bad`: a `PerasVote` with `pvVoteVoterId = PerasVoterId (arbitrary KeyHash not in stake distribution)`.
4. P connects to node A and sends the batch `[v_bad, v1, v2, v3]` via the `PerasVoteDiffusion` miniprotocol before H sends its batch.
5. Node A calls `processVotes`. `validatePerasVote` returns `Left PerasValidationErr` for `v_bad` and `Right` for `v1, v2, v3`. `partitionEithers` yields `([err], [vv1, vv2, vv3])`. The `(errs, _)` branch fires, throwing `PerasVoteValidationError`. Node A disconnects P.
6. `v1, v2, v3` are never added to node A's `PerasVoteDB`. When H later sends its batch `[v1, v2, v3]`, they are accepted — but if the round's voting window has closed, quorum is never reached.
7. No certificate is forged for round R. The Peras boost is not applied to block B. A competing chain with a boost from round R-1 may now be preferred by node A's chain selection. [8](#0-7) [3](#0-2) [9](#0-8)

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
