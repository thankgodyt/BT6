### Title
Unconditional `validatePerasCert` Acceptance in Degenerate `BlockSupportsPeras` Instance Enables Unauthorized Certificate Acceptance and Chain-Selection Manipulation — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The only compiled `BlockSupportsPeras` instance (`instance StandardHash blk => BlockSupportsPeras blk`) implements `validatePerasCert` as an unconditional `Right`, performing zero cryptographic or committee-membership checks. This instance is wired directly into the production ObjectDiffusion inbound path. Any peer that can negotiate `NodeToNodeV_16` on a node with the Peras feature flag enabled can send a `PerasCert` with an arbitrary round number and arbitrary boosted block point, have it accepted into the `PerasCertDB`, and trigger chain selection for the boosted block, violating the invariant that only certificates backed by a valid quorum of authorized committee members may be accepted.

---

### Finding Description

**Root cause — `validatePerasCert` (lines 353–358):**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

No signature, aggregate BLS, committee-membership, round-range, or any other check is performed. Every `PerasCert` value, regardless of content, is returned as `Right (ValidatedPerasCert ...)`. [1](#0-0) 

**Production wiring — `makePerasCertPoolWriterFromChainDB`:**

`processCerts` is called with `validatePerasCert mkPerasParams` as the validation function, and `void . ChainDB.addPerasCertAsync chainDB` as the sink. This is the function used in the production `NodeToNode` handler. [2](#0-1) 

**Network handler — `hPerasCertDiffusionClient`:**

The production `mkHandlers` wires `makePerasCertPoolWriterFromChainDB` directly into the ObjectDiffusion inbound handler for every `NodeToNodeV_16` connection. [3](#0-2) 

**`processCerts` — no independent guard:**

`processCerts` calls `validateCert` (which is `validatePerasCert mkPerasParams`) on each cert not already in the DB. Because `validatePerasCert` always returns `Right`, the `([], validatedCerts)` branch is always taken and every cert is forwarded to `addCert`. [4](#0-3) 

**`chainSelSync` — cert accepted and chain selection triggered:**

After the cert is added to the `PerasCertDB`, if the boosted block is present in the `VolatileDB`, `chainSelectionForBlock` is called for it. The boosted block receives `perasWeight params` (= 15 by default) of additional chain weight, which can cause the node to switch to a fork it would not otherwise prefer. [5](#0-4) 

The only guards in `chainSelSync` are slot-age (too old), already-on-current-chain, genesis hash, and block-not-yet-received — none of which verify certificate authenticity. [6](#0-5) 

---

### Impact Explanation

An unprivileged peer on a node with the Peras feature flag enabled can:

1. Send a `PerasCert` naming any block hash in the target node's `VolatileDB` as the boosted block.
2. The cert bypasses all validation and is stored in the `PerasCertDB`.
3. Chain selection is triggered for the boosted block with +15 weight, potentially causing the node to switch to a fork it would not otherwise prefer.
4. The invariant that only certificates backed by a valid quorum of authorized committee members may be accepted is broken.

This matches the target scope: **Critical — bypass of Peras certificate checks enabling unauthorized certificate acceptance and chain-selection manipulation.**

---

### Likelihood Explanation

- **Precondition:** The Peras feature flag must be enabled. The CHANGELOG notes "if Peras is disabled (which is the default), there is no observable difference." This limits exposure to nodes that have explicitly opted into the experimental Peras feature.
- **Attack complexity:** Low. Any peer that can negotiate `NodeToNodeV_16` with a Peras-enabled node can send a crafted `PerasCert` with no special knowledge or keys.
- **Detectability:** The TODO comments at lines 318 and 350–352 explicitly acknowledge the missing validation, confirming this is a known incomplete implementation compiled into production code paths. [7](#0-6) [8](#0-7) 

---

### Recommendation

1. **Do not enable the Peras feature flag on any node until `validatePerasCert` performs real aggregate BLS signature verification and committee-membership checks** (tracked in https://github.com/tweag/cardano-peras/issues/120).
2. Replace the degenerate `instance StandardHash blk => BlockSupportsPeras blk` with a compile-time guard (e.g., a type-level flag or a `Void`-returning stub) that prevents the degenerate instance from being used in any production network path.
3. Add a property test asserting that `validatePerasCert` rejects certs with invalid/missing aggregate BLS signatures before the real implementation is merged.

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
```

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
