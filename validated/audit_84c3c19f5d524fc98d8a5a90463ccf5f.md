### Title
Peras Certificate Validation Bypass via Stub `validatePerasCert` Allows Unprivileged Peers to Inject Arbitrary Chain Weight Boosts — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The degenerate `BlockSupportsPeras` instance used for all block types provides a stub `validatePerasCert` that unconditionally returns `Right` without performing any cryptographic or committee-membership verification. Both network-facing Peras certificate pool writers (`makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB`) wire this stub as the validation callback. Any unprivileged peer can therefore inject crafted `PerasCert` objects that are accepted without verification, added to the `PerasCertDB`, and reflected in the `PerasWeightSnapshot` used by chain selection, potentially causing a node to prefer a non-canonical fork.

### Finding Description

**Root cause — stub validation always succeeds**

The `BlockSupportsPeras` class declares `validatePerasCert` as a required method. The degenerate instance that covers every `StandardHash blk` provides:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature check, no committee-membership check, no round-number sanity check — every `PerasCert` is unconditionally wrapped in `ValidatedPerasCert` and returned as `Right`.

**Wiring — stub is used for all inbound peer certificates**

Both pool writers that handle certificates arriving from the network pass this stub as the `validateCert` callback:

**Processing — accepted certificates enter the DB and affect chain selection**

`processCerts` partitions the validated results; because the stub never produces a `Left`, the `(errs, _)` branch is never reached and every certificate is timestamped and forwarded to `addCert`: [4](#0-3) 

Accepted certificates are stored in `PerasCertDB`. The `getWeightSnapshot` field of `PerasCertDB` derives a `PerasWeightSnapshot` from every stored certificate: [5](#0-4) 

This snapshot is read during chain selection in `compareAnchoredFragments`:

```haskell
| otherwise =
    case AF.intersect frag1 frag2 of
      ...
        compare
          (weightedSelectView cfg weights oursSuffix)

``` [6](#0-5) 

The total weight used for comparison is `PerasWeight(blockNo) + wsvWeightBoost`, so a fake boost on a shorter fork can make it outweigh the canonical chain: [7](#0-6) 

The ChainDB also reads the snapshot at startup for initial chain selection: [8](#0-7) 

**Attacker-controlled entry path**

A peer connected via the Peras certificate object-diffusion mini-protocol sends a batch of `PerasCert` objects. Each certificate carries only `pcCertRound :: PerasRoundNo` and `pcCertBoostedBlock :: Point blk` — both fully attacker-controlled. Because `validatePerasCert` is a no-op, the peer can specify any volatile block point as the boosted block. The only guard is the immutability check in `addPerasCertAsync` (certificates for already-immutable blocks are silently dropped), but volatile blocks within the last `k` slots are eligible. [9](#0-8) 

### Impact Explanation

**High — chain selection manipulation.** An unprivileged peer can inject fake Peras certificates that boost blocks on a minority fork. Because `wsvTotalWeight = blockNo + weightBoost`, a fork with fewer blocks but a large injected boost can exceed the canonical chain's weight, causing the victim node to switch to the attacker's fork. This violates the chain-selection invariant and constitutes a consensus safety failure reachable from a single unauthenticated peer connection.

### Likelihood Explanation

Any peer that can open a Peras certificate diffusion connection to the node can exploit this. No stake, no keys, and no prior relationship are required. The Peras certificate diffusion mini-protocol is wired into the production node kernel via `makePerasCertPoolWriterFromChainDB`. The `PerasParams` defaults are now non-zero (per the recent changelog entry), so the injected weight boost is non-trivial.

### Recommendation

Replace the stub `validatePerasCert` call in both `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB` with a real implementation that:
1. Verifies the certificate's cryptographic aggregate signature against the voting committee for the claimed round.
2. Confirms the boosted block point exists in the local volatile DB and is on a known chain.
3. Checks the round number is within the valid Peras window.

Until the real validation is in place, the Peras certificate diffusion mini-protocol should be disabled or the `processCerts` path should reject all inbound certificates rather than accepting them unconditionally.

### Proof of Concept

1. Attacker connects to a victim node via the Peras certificate object-diffusion mini-protocol.
2. Attacker observes the victim's current chain tip (e.g., block `B_canonical` at height `h`).
3. Attacker identifies a competing fork block `B_fork` at height `h - d` (for small `d`) that is still in the volatile DB.
4. Attacker crafts `PerasCert { pcCertRound = r, pcCertBoostedBlock = blockPoint B_fork }` with a large round number `r` not yet in the victim's `PerasCertDB`.
5. Attacker sends this certificate to the victim via the diffusion protocol.
6. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight defaultParams }` unconditionally.
7. The certificate is added to `PerasCertDB`; `getWeightSnapshot` now returns a snapshot boosting `B_fork`.
8. On the next chain selection event, `compareAnchoredFragments` computes `wsvTotalWeight(fork) = (h-d) + perasWeight > h = wsvTotalWeight(canonical)` if `perasWeight > d`.
9. The victim node switches to the attacker's fork, diverging from the honest chain. [1](#0-0) [10](#0-9) [11](#0-10)

```haskell
processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

```haskell
compareAnchoredFragments cfg weights frag1 frag2
  -- Optimize the case where Peras is disabled.
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition frag1 frag2) $
        case (frag1, frag2) of
          (Empty _, Empty _) ->
            -- The fragments intersect but are equal: their anchors must be equal,
            -- and hence the fragments represent the same chain. They are therefore
            -- equally preferable.
            EQ
          (Empty anchor, _ :> tip') ->
            -- Since the fragments intersect, but the first one is empty, its anchor
            -- must lie somewhere along the the second. If it is the tip, the two
            -- fragments represent the same chain and are equally preferable. If
            -- not, the second chain is a strict extension of the first and is
            -- therefore strictly preferable.
            if blockPoint tip' == AF.castPoint (AF.anchorToPoint anchor)
              then EQ
              else LT
          (_ :> tip, Empty anchor') ->
            -- This case is symmetric to the previous
            if blockPoint tip == AF.castPoint (AF.anchorToPoint anchor')
              then EQ
              else GT
          (_ :> tip, _ :> tip') ->
            -- Case 4
            compare
              (selectView cfg (getHeader1 tip))
              (selectView cfg (getHeader1 tip'))
  | otherwise =
      case AF.intersect frag1 frag2 of
        Nothing -> error "precondition violated: fragments must intersect"
        Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
          compare
            (weightedSelectView cfg weights oursSuffix)
            (weightedSelectView cfg weights candSuffix)
