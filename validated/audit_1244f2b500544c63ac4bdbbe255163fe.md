Audit Report

## Title
Unregistered ERC20 Tokens Accepted by `initTransfer()` Are Permanently Locked With No Recovery Path - (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

## Summary
`OmniBridge.initTransfer()` contains no guard verifying that a token address is registered in `ethToNearToken` before accepting a transfer. Any ERC20 token not in `customMinters` or `isBridgeToken` is silently pulled into the bridge via the `else` branch. When a relayer submits the resulting proof to the NEAR `fin_transfer_callback`, the call panics with `BridgeError::TokenDecimalsNotFound` because the token was never registered through the `logMetadata` → `deployToken` flow. No cross-chain refund is triggered and no admin rescue function exists in the EVM contract, making the loss permanent.

## Finding Description
In `OmniBridge.sol` lines 394–412, `initTransfer` routes token handling through three branches. The catch-all `else` branch executes `IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount)` for any token that is neither in `customMinters` nor `isBridgeToken` — including tokens that have never been registered with the bridge at all. There is no `require(bytes(ethToNearToken[tokenAddress]).length > 0, ...)` guard before the transfer occurs.

After the transfer, `InitTransfer` is emitted unconditionally (lines 427–436). A relayer then submits the proof to the NEAR `fin_transfer` function (lib.rs line 673), which calls `fin_transfer_callback`. At lines 715–718 of lib.rs, the callback performs:

```rust
let decimals = self
    .token_decimals
    .get(&init_transfer.token)
    .near_expect(BridgeError::TokenDecimalsNotFound);
```

For any token that was never registered via `log_metadata` + `deployToken`, `token_decimals` has no entry and the call panics. The NEAR transaction reverts. No cross-chain refund message is sent back to the EVM side. A search of all EVM `.sol` files confirms there is no `rescueToken`, `withdrawToken`, `emergencyWithdraw`, or equivalent admin function — the tokens remain locked in the bridge contract indefinitely.

The same pattern exists in the Starknet bridge: `init_transfer` (omni_bridge.cairo lines 300–307) accepts any ERC20 in its `else` branch without checking `starknet_to_near_token`.

## Impact Explanation
Any user who calls `initTransfer` with an ERC20 token that has not completed the `logMetadata` → `deployToken` registration flow loses their tokens permanently. The tokens are transferred into the bridge contract, the `InitTransfer` event is emitted consuming the user's nonce, the NEAR finalization panics, and no on-chain mechanism exists to return the funds. This is a direct, permanent loss of bridged funds triggered by a single unprivileged user action, matching the Critical impact class: **permanent freezing of bridged funds**.

## Likelihood Explanation
`initTransfer` is a public, non-paused entry point callable by any EVM address. The `logMetadata` function is itself permissionless and entirely decoupled from `initTransfer` — there is no coupling that prevents a user from calling `initTransfer` before `logMetadata` + `deployToken` have been executed for their token. A user holding a legitimate ERC20 that has not yet been registered (e.g., a newly launched token, a token whose `logMetadata` call was never submitted, or a token on a chain where the bridge was recently deployed) can trigger this loss accidentally. The SECURITY.md explicitly confirms the bridge is "fully permissionless," increasing the likelihood that users will interact with it without understanding the registration prerequisite.

## Recommendation
Add a registration check at the top of `initTransfer` before any token transfer occurs:

```solidity
require(
    tokenAddress == address(0) ||
    isBridgeToken[tokenAddress] ||
    customMinters[tokenAddress] != address(0) ||
    bytes(ethToNearToken[tokenAddress]).length > 0,
    "ERR_TOKEN_NOT_SUPPORTED"
);
```

Apply the same guard to `initTransfer1155`. Apply an equivalent check in the Starknet `init_transfer` against `starknet_to_near_token`.

## Proof of Concept
1. Alice holds 1000 units of `NEWTOKEN`, a legitimate ERC20 that has not had `logMetadata` called on the OmniBridge.
2. Alice calls `OmniBridge.initTransfer(NEWTOKEN_ADDRESS, 1000, 0, 0, "alice.near", "")`.
3. The `else` branch at lines 406–411 executes: `IERC20(NEWTOKEN_ADDRESS).safeTransferFrom(alice, address(this), 1000)` — Alice's tokens are now in the bridge.
4. `InitTransfer` event is emitted at lines 427–436 with `tokenAddress = NEWTOKEN_ADDRESS`.
5. A relayer submits the proof to the NEAR `fin_transfer` function (lib.rs line 673).
6. `fin_transfer_callback` at lib.rs lines 715–718 calls `self.token_decimals.get(&init_transfer.token).near_expect(BridgeError::TokenDecimalsNotFound)` — this panics because `NEWTOKEN` was never registered.
7. The NEAR transaction reverts. Alice's 1000 `NEWTOKEN` remain locked in the EVM bridge contract with no recovery path.

To reproduce: write a Hardhat/Foundry test that deploys a mock ERC20, skips `logMetadata`/`deployToken`, calls `initTransfer`, and asserts the bridge holds the tokens. Then simulate the NEAR callback with an empty `token_decimals` map and assert it panics with `TokenDecimalsNotFound`.
