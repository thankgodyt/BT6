Audit Report

## Title
`finish_withdraw_v2` Missing Pause Guard Allows Transfer Initiation and Token Burning While Bridge Is Paused — (`near/omni-bridge/src/lib.rs`)

## Summary
`finish_withdraw_v2` is a public callback invokable by any registered legacy bridge token contract. Unlike every other transfer-initiation entry point in the contract, it carries no `#[pause]` attribute. When the bridge is paused, a user can still burn their NEAR-side legacy tokens and record a pending outbound transfer, defeating the admin's intent to halt all new transfer activity and risking permanent fund loss if the bridge is subsequently shut down.

## Finding Description
Every transfer-initiation path in the contract is guarded:

- `ft_on_transfer` (L252): `#[pause(except(roles(Role::DAO, Role::UnrestrictedDeposit)))]`
- `sign_transfer` (L446): `#[pause(except(roles(Role::DAO)))]`
- `fin_transfer` (L672): `#[pause(except(roles(Role::DAO)))]`
- `claim_fee` (L1056): `#[pause(except(roles(Role::DAO)))]`

`finish_withdraw_v2` (L1314–1354) has no such attribute. Its only access control is `require!(self.is_deployed_token(&token_id))` (L1322), which passes for any account in `deployed_tokens` or `deployed_tokens_v2` (L1356–1357). When called, it unconditionally increments `current_origin_nonce`, allocates a destination nonce, stores a `TransferMessage` in `pending_transfers`, and emits `InitTransferEvent` (L1324–1353). The storage cost is charged to `env::current_account_id()` (L1347–1350), not the caller.

Exploit path:
1. Admin pauses the bridge in response to a security incident.
2. User holds tokens in a registered legacy bridge token (e.g., `eth-<token>.factory.bridge.near`).
3. User calls the legacy token's `withdraw(amount, recipient)`.
4. The legacy token burns the user's balance and calls `finish_withdraw_v2` on the bridge.
5. `finish_withdraw_v2` executes without reverting — no pause check — records the pending transfer, and emits `InitTransferEvent`.
6. The user's NEAR-side tokens are now burned. `sign_transfer` is paused, so no relayer can complete the transfer.
7. If the bridge is permanently shut down, the burned tokens are irrecoverable.

## Impact Explanation
This is a concrete pause bypass (allowed critical impact class: "pause bypass that lets an attacker execute bridge actions") and, under the realistic scenario of a permanent bridge shutdown following a severe incident, results in permanent freezing of bridged funds (allowed critical impact class: "permanent freezing of bridged funds"). The tokens are burned on the NEAR side with no corresponding release on Ethereum, and no admin action can recover them once the bridge is shut down.

## Likelihood Explanation
The preconditions are minimal: the bridge must be paused (a routine emergency response) and the user must hold any legacy bridge token registered in `deployed_tokens` or `deployed_tokens_v2`. No special role, permission, or privileged access is required. The legacy token set exists for backward compatibility and is populated on mainnet. Any ordinary token holder can trigger this path through a standard `withdraw` call on the legacy token contract.

## Recommendation
Add the same pause guard used on every other transfer-initiation path:

```rust
#[pause(except(roles(Role::DAO)))]
pub fn finish_withdraw_v2(
    &mut self,
    #[serializer(borsh)] sender_id: &AccountId,
    #[serializer(borsh)] amount: u128,
    #[serializer(borsh)] recipient: String,
) { ... }
```

Additionally, charge storage costs to `sender_id` rather than `env::current_account_id()` (L1347–1350) to prevent repeated calls from exhausting bridge storage at no cost to the caller.

## Proof of Concept
1. Deploy a local NEAR testnet with the bridge contract and a registered legacy bridge token.
2. Pause the bridge via the `PauseManager` role.
3. Call `withdraw(amount, eth_recipient)` on the legacy token as an unprivileged user.
4. Observe that `finish_withdraw_v2` executes successfully (no panic), `current_origin_nonce` is incremented, and `InitTransferEvent` is emitted.
5. Confirm the user's legacy token balance is reduced (burned) and a `TransferMessage` exists in `pending_transfers`.
6. Attempt `sign_transfer` for the new transfer ID — confirm it panics due to the pause guard.
7. Simulate bridge shutdown (remove relayers/signers); confirm the pending transfer can never be finalized and the burned tokens are permanently frozen.

The contrast is direct: repeating step 3 via `ft_on_transfer` (the guarded path) would panic at step 4 for any non-DAO caller, while `finish_withdraw_v2` does not.
