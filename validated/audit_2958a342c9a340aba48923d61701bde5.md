### Title
Degenerate `validatePerasCert` Instance Unconditionally Accepts Any Peer-Supplied Peras Certificate, Enabling Chain-Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance in `SupportsPeras.hs` implements `validatePerasCert` as an unconditional `Right` — it performs zero cryptographic or structural checks and accepts every certificate it receives. This instance is wired directly into the production inbound-certificate pipeline (`makePerasCertPoolWriterFromChainDB`). Because accepted certificates are fed into `ChainDB` chain selection and grant a configurable weight boost to the block they reference, an unprivileged peer can fabricate a certificate for any block hash and any round number, have it accepted without question, and cause the receiving node to re-run chain selection with an artificially boosted candidate fragment.

---

### Finding Description

**Root cause — stub implementation shipped as the universal instance**

The `BlockSupportsPeras` type class declares `validatePerasCert` as the mandatory gate that must verify a certificate before it may influence chain selection:

```haskell
validatePerasCert ::
  PerasCfg blk ->
  PerasCert blk ->
  Either (PerasValidationErr blk) (ValidatedPerasCert blk)
```

The only concrete instance in the codebase is the catch-all degenerate instance introduced with the comment `-- TODO: degenerate instance for all blks to get things to compile`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

No signature is verified, no quorum is checked, no round-number bounds are enforced, and no boosted-block ancestry is confirmed. Every certificate, regardless of content or origin, is wrapped in `Right` and returned as `ValidatedPerasCert`. [1](#0-0) 

**Production call sites — the stub is wired into the live inbound pipeline**

Both production pool-writer constructors pass `validatePerasCert mkPerasParams` directly as the validation callback for inbound certificates received from peers:

```haskell

**Validation pipeline — accepted certificates reach chain selection**

`processCerts` partitions the validated results; any certificate that passes `validateCert` (i.e., every certificate) is timestamped and forwarded to `addCert`:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [3](#0-2) 

When the `ChainDB` pool writer is used, `addCert` is `ChainDB.addPerasCertAsync`, which enqueues the certificate for `chainSelSync`. Inside `chainSelSync`, the certificate is stored in `PerasCertDB` and then `chainSelectionForBlock` is called for the boosted block:

```haskell
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

The Peras weight boost (`vpcCertBoost = perasWeight params`) is then reflected in `getPerasWeightSnapshot` and used by the `WeightedSelectView` to prefer the boosted fragment over the current selection. [5](#0-4) 

**Analog to the external report**

The external report describes `MockVesting.sol` — a stub with an empty `vest()` body — being silently used in place of the real implementation, causing the real transfer logic to be skipped. Here, the degenerate `BlockSupportsPeras` instance plays exactly the same role: it is a stub with an empty validation body that is silently used in production, causing all certificate authentication to be skipped.

### Impact Explanation

**Critical — Bypass of Peras certificate validation enabling unauthorized certificate acceptance and chain-selection manipulation.**

An unprivileged peer connected via the Peras object-diffusion mini-protocol can:

1. Craft a `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock` pointing to any block hash the attacker knows is in the target node's VolatileDB.
2. Send the certificate over the wire. `processCerts` calls `validatePerasCert`, which unconditionally returns `Right`.
3. The certificate is stored in `PerasCertDB` and `chainSelectionForBlock` is triggered for the boosted block.
4. The boosted block's fragment now carries extra `perasWeight` in `WeightedSelectView`, potentially making it preferred over the honest canonical chain.
5. The node switches to the attacker-chosen fork, diverging from the honest majority.

This satisfies the "Critical — Bypass of Peras voting or certificate checks that enables unauthorized certificate acceptance" and "High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain" impact categories.

---

### Likelihood Explanation

**High.** The attack requires only a peer connection to the Peras object-diffusion endpoint, which is an externally reachable network interface. No keys, stake, or operator access are needed. The attacker only needs to know a block hash present in the target's VolatileDB (trivially obtained via the ChainSync mini-protocol). The degenerate instance is the only instance in the codebase and is unconditionally used in both production pool-writer constructors.

---

### Recommendation

Replace the degenerate `validatePerasCert` stub with a real implementation that:

1. Verifies the aggregate BLS/committee signature over `(electionId, candidate)` using the committee's aggregate verification key derived from the current stake distribution.
2. Confirms the certificate's `pcCertRound` falls within the valid window relative to the current slot.
3. Confirms `pcCertBoostedBlock` is a known descendant of the last certified block.

Until the real implementation is ready, the degenerate instance should be guarded by a feature flag that is disabled by default, and the production pool-writer constructors must not call `validatePerasCert mkPerasParams` when Peras is not fully activated.

### Proof of Concept

A node running with Peras enabled receives the following crafted certificate from a peer:

```
PerasCert
  { pcCertRound      = <any round number>
  , pcCertBoostedBlock = <hash of a block on a minority fork in the target's VolatileDB>
  }
```

Execution path:

1. Peer sends the certificate via the Peras cert diffusion mini-protocol.
2. `makePerasCertPoolWriterFromChainDB` → `processCerts` → `validatePerasCert mkPerasParams cert` → `Right ValidatedPerasCert{vpcCertBoost = perasWeight params}`.
3. `partitionEithers` sees zero errors → `addCert (WithArrivalTime now validatedCert)` → `ChainDB.addPerasCertAsync`.
4. `chainSelSync` stores the cert in `PerasCertDB` and calls `chainSelectionForBlock` for the boosted block.
5. `WeightedSelectView` now scores the minority fork higher than the honest chain by `perasWeight params`.
6. The node switches to the minority fork, diverging from the honest network. [6](#0-5) [7](#0-6) [8](#0-7)

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
