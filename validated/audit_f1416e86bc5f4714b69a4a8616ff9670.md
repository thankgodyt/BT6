Audit Report

## Title
`deploy_token` Missing Pause Check Allows Token Deployment During Full Bridge Pause — (`solana/programs/bridge_token_factory/src/lib.rs`)

## Summary
The Solana `bridge_token_factory` program defines only two pause bits (`INIT_TRANSFER_PAUSED`, `FINALIZE_TRANSFER_PAUSED`) and `ALL_PAUSED` covers only those two. The `deploy_token` entry point contains no pause guard, so any relayer holding a valid MPC-signed `DeployTokenPayload` can call it after `pause()` has been invoked. The EVM counterpart explicitly defines and enforces a third `PAUSED_DEPLOY_TOKEN` bit in both `deployToken` and `pauseAll`, making this an intentional design feature that was not ported to Solana.

## Finding Description
`constants.rs` defines exactly two pause flags and `ALL_PAUSED` as their union: [1](#0-0) 

`pause.rs` sets `config.paused = ALL_PAUSED`, which only covers the two transfer bits: [2](#0-1) 

All four transfer entry points correctly gate on the relevant bit before proceeding: [3](#0-2) [4](#0-3) 

`deploy_token`, however, performs no pause check — it only verifies the MPC signature and immediately initializes the token mint: [5](#0-4) 

The EVM bridge defines a third pause bit and enforces it on `deployToken`: [6](#0-5) [7](#0-6) 

And `pauseAll` on EVM includes `PAUSED_DEPLOY_TOKEN`: [8](#0-7) 

The Solana program has no equivalent protection, making the omission a concrete gap rather than a design choice.

## Impact Explanation
This is a **pause bypass** that allows an unprivileged relayer to execute deployer-equivalent actions (registering new token mints and their metadata on-chain) while the bridge is supposed to be fully halted. This matches the allowed critical impact: *"pause bypass… that lets an attacker execute bridge, token, deployer, relayer, or admin-equivalent actions."* Newly registered mints become immediately usable in `finalize_transfer` once the pause is lifted, and if the deployment was submitted during an incident window where the admin intended to block all state changes, the resulting on-chain state (mint accounts, metadata) may be inconsistent with the intended post-incident recovery state.

## Likelihood Explanation
No key compromise or threshold collusion is required. Any relayer who obtained a valid `SignedPayload<DeployTokenPayload>` through the normal bridge flow before the pause can submit it at any time afterward. The MPC signature remains valid indefinitely. The window between an emergency pause and the expiry of all in-flight signed payloads is realistic in production incident response. The call is permissionless beyond holding the signed payload.

## Recommendation
1. Add `pub const DEPLOY_TOKEN_PAUSED: u8 = 1 << 2;` to `constants.rs`.
2. Update `ALL_PAUSED` to `INIT_TRANSFER_PAUSED | FINALIZE_TRANSFER_PAUSED | DEPLOY_TOKEN_PAUSED`.
3. Add the following guard at the top of `deploy_token` in `lib.rs`:
   ```rust
   require!(
       ctx.accounts.common.config.paused & DEPLOY_TOKEN_PAUSED == 0,
       error::ErrorCode::Paused
   );
   ```

## Proof of Concept
1. Admin or pausable-admin calls `pause()` → `config.paused = 0b11` (`ALL_PAUSED`).
2. Relayer holds a `SignedPayload<DeployTokenPayload>` obtained before the pause (normal operational artifact).
3. Relayer calls `deploy_token(ctx, signed_payload)`.
4. The function skips any pause check, `data.verify_signature(...)` succeeds (signature is valid), and `ctx.accounts.initialize_token_metadata(data.payload)` executes.
5. A new token mint is registered on Solana while the program is supposed to be fully paused.
6. After the pause is lifted, `finalize_transfer` can use this mint to distribute tokens, with state changes that occurred against the admin's explicit intent during the pause window.
