### Title
BLS Rogue Key Attack Allows Forging Peras Certificates Without Proof of Possession - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/Crypto/BLS.hs`)

---

### Summary

`aggregatePublicKeys` in `BLS.hs` carries an unverified precondition that proof of possession has already been checked for all input keys, but `verifyProofOfPossession` is never called anywhere in the production certificate-verification path. An attacker who registers a BLS public key equal to the elliptic-curve negation of a legitimate voter's key causes `aggregatePublicKeys` to produce the point at infinity. Because `aggregatePublicKeys` — unlike `linearizeAndVerifyVRFs` — contains no `blsIsInf` guard on the resulting aggregate key, the attacker can then submit a crafted Peras certificate carrying the point at infinity as the aggregate signature, which passes `verifyAggregateVoteSignature` and causes an honest node to accept a certificate for an arbitrary boosted block.

---

### Finding Description

**Root cause — missing infinity guard in `aggregatePublicKeys`**

`aggregatePublicKeys` documents a critical precondition but does not enforce it:

```haskell
-- PRECONDITION: this assumes that proofs of possession have already been
-- verified for all keys in advance.
aggregatePublicKeys ::
  NE [PublicKey r] ->
  Either String (PublicKey r)
aggregatePublicKeys keys@(firstKey :| restKeys) = do
  when (any (/= publicKeyScope firstKey) (fmap publicKeyScope restKeys)) $
    Left "Cannot aggregate public keys with different scopes"
  aggKey <-
    uncheckedAggregateVerKeysDSIGN   -- ← "unchecked" by design
      . fmap unPublicKey
      . NonEmpty.toList
      $ keys
  pure $ PublicKey { unPublicKey = aggKey, ... }
``` [1](#0-0) 

There is no call to `blsIsInf` on `aggKey`. Compare this with `linearizeAndVerifyVRFs`, which explicitly guards against the same condition:

```haskell
when (blsIsInf linearizedKeyPoint) $
  Left "Resulting key point is at infinity, cannot linearize"
``` [2](#0-1) 

The asymmetry is the vulnerability: the VRF path is protected; the vote-signature aggregation path is not.

**Proof of possession is never verified in production**

`verifyProofOfPossession` is defined in `BLS.hs` but a grep across all `.hs` files shows it is only referenced within `BLS.hs` itself — it is never called from any certificate-verification or key-registration path. The precondition on `aggregatePublicKeys` is therefore never satisfied. [3](#0-2) 

**Certificate verification path — `implVerifyCert` in `WFALS.hs`**

When a Peras certificate arrives over the network, `implVerifyCert` collects voter verification keys from the ledger stake distribution and calls `aggregateVoteVerificationKeys`, which delegates directly to `aggregatePublicKeys`:

```haskell
aggVerificationKey <-
  bimap CryptoError id $
    aggregateVoteVerificationKeys
      (Proxy @crypto)
      voteVerificationKeys
bimap InvalidCertSignature id $
  verifyAggregateVoteSignature
    (Proxy @crypto)
    aggVerificationKey
    electionId
    candidate
    aggSig
``` [4](#0-3) 

The same pattern exists in `EveryoneVotes.hs`: [5](#0-4) 

`aggregateVoteVerificationKeys` for `PerasBLSCrypto` calls `BLS.aggregatePublicKeys @SIGN` with no additional guard: [6](#0-5) 

**The rogue key construction**

On BLS12-381, every point `P` has an additive inverse `-P` such that `P + (-P) = O` (the point at infinity). An attacker who can register a BLS vote-verification key equal to `-pk_victim` for any legitimate voter `pk_victim` causes:

```
aggregatePublicKeys([pk_victim, -pk_victim]) = O
```

Because `uncheckedAggregateVerKeysDSIGN` performs raw elliptic-curve addition with no validity check on the output, `aggKey = O` is returned and wrapped in a `PublicKey`. The attacker then submits a certificate whose `aggSig` is also the point at infinity. In BLS12-381 MinSig, `e(O, g2) = 1_GT = e(H(m), O)`, so `verifyDSIGN` (called by `verifyWithRole`) succeeds, accepting the forged certificate. [7](#0-6) 

---

### Impact Explanation

A successful attack allows an unprivileged peer to submit a crafted Peras certificate that passes `verifyCert` for an **arbitrary `VoteCandidate` (boosted block)**. This is a bypass of Peras vote/certificate signature validation. The accepted certificate can cause an honest node to prefer a non-canonical chain (the attacker-chosen boosted block), constituting a **consensus safety failure** under the Peras protocol's chain-selection rules. Impact is **Critical** under the allowed scope: bypass of certificate/signature validation enabling unauthorized certificate acceptance.

---

### Likelihood Explanation

The attacker needs only to:
1. Register a BLS public key equal to `-pk_victim` for any pool already in the stake distribution. Since all BLS public keys are broadcast on-chain and negating a curve point is a trivial computation, this is feasible for any external participant who can submit a pool registration transaction.
2. Ensure both keys appear in the same certificate's voter set (both must be in the stake distribution with positive stake).
3. Craft a certificate with the point at infinity as the aggregate signature and submit it to a node via the Peras diffusion protocol.

No privileged access, no key compromise, and no brute force is required. Likelihood is **High**.

---

### Recommendation

1. **Add an infinity guard in `aggregatePublicKeys`** immediately after computing `aggKey`:
   ```haskell
   when (blsIsInf (unVerKeyBLS12381 (unPublicKey aggKey))) $
     Left "Aggregate public key is the point at infinity"
   ```
   This mirrors the existing guard in `linearizeAndVerifyVRFs`.

2. **Enforce proof of possession at key registration time** — call `verifyProofOfPossession` when a pool registers its BLS vote-verification key in the ledger, before that key is admitted to the stake distribution used to construct `VotingCommitteeInput`. This is the standard defense against rogue-key attacks on BLS aggregate signatures (IETF draft-irtf-cfrg-bls-signature §3.3).

3. **Add an infinity guard in `verifyAggregateVoteSignature`** as a defense-in-depth measure, rejecting any aggregate key or signature that is the point at infinity before calling `verifyDSIGN`.

### Proof of Concept

```
Setup:
  - victim_sk, victim_pk = legitimate BLS key pair already in stake distribution
  - attacker computes rogue_pk = -victim_pk  (negate the G2 point)
  - attacker registers rogue_pk as their pool's BLS vote-verification key
    (no proof of possession is checked at registration)

Attack:
  1. Both victim_pk and rogue_pk are in the ExtWFAStakeDistr with positive stake.
  2. Attacker crafts a WFALSCert (or EveryoneVotesCert) listing both seat indices
     and any desired VoteCandidate (e.g., an attacker-controlled block hash).
  3. Attacker sets aggSig = point at infinity (serialised as the standard
     compressed infinity encoding for BLS12-381 G1).
  4. Node receives the certificate via the Peras diffusion miniprotocol.
  5. implVerifyCert collects [victim_pk, rogue_pk] and calls aggregatePublicKeys.
  6. aggregatePublicKeys returns O (no blsIsInf check).
  7. verifyAggregateVoteSignature calls verifyWithRole with key=O, sig=O.
  8. verifyDSIGN succeeds: e(O, g2) = 1_GT = e(H(m), O).
  9. Certificate is accepted; node boosts the attacker's chosen block.

Expected (correct) outcome: step 6 should return Left "Aggregate public key is
the point at infinity" and the certificate should be rejected.
```
