Audit Report

## Title
Pause Bypass via `init_transfer_resume` and `fin_transfer_callback` Lacking Pause Checks - (File: `near/omni-bridge/src/lib.rs`)

## Summary

The NEAR `omni-bridge` contract enforces pause checks on `ft_on_transfer` and `fin_transfer` but omits those checks from their async continuations `init_transfer_resume` and `fin_transfer_callback`. Because NEAR callbacks and yield resumes are independent function calls dispatched by the runtime, a pause set between the entry-point call and the callback execution is silently bypassed. For `init_transfer_resume` specifically, the yield can remain pending for hours or days, giving an attacker a wide window to trigger the resume after a pause is set, burning/locking user tokens and emitting `InitTransferEvent` that a relayer can finalize on the destination chain.

## Finding Description

`ft_on_transfer` is decorated with `#[pause(except(roles(Role::DAO, Role::UnrestrictedDeposit)))]` at line 252, enforcing the pause at the entry point. When storage is insufficient, `ft_on_transfer` → `init_transfer` creates a NEAR yield promise via `env::promise_yield_create("init_transfer_resume", ...)` at lines 586–598, suspending execution until storage is deposited. The yield resumes via `init_transfer_resume` (lines 621–646), which is marked only `#[private]` — no `#[pause]` macro and no manual `assert_not_paused()` call. Upon resume, it unconditionally calls `init_transfer_internal` at line 645, which burns/locks tokens and emits `InitTransferEvent` (lines 1829–1865).

The same structural gap exists for `fin_transfer` (line 672, `#[pause(except(roles(Role::DAO)))]`) and its callback `fin_transfer_callback` (lines 698–746), which carries only `#[private]` and `#[payable]` — no pause check — and proceeds to mint/transfer tokens to the recipient.

The root cause is that NEAR's async execution model dispatches callbacks and yield resumes as independent top-level calls. The pause check on the entry point does not propagate to these continuations, and neither function re-checks the pause state before executing state-changing bridge logic.

## Impact Explanation

This is a **pause bypass enabling unauthorized cross-chain fund movement**, matching the Critical allowed impact: *"Unauthorized transaction, authorization bypass, role bypass, pause bypass, or signer/prover verification bypass that lets an attacker execute bridge, token, deployer, relayer, or admin-equivalent actions."*

For `init_transfer_resume`: tokens are burned/locked on NEAR and `InitTransferEvent` is emitted despite the bridge being paused. A relayer can then finalize the transfer on the destination chain, completing a cross-chain fund movement that the pause was intended to block. The pause mechanism — the primary emergency stop for the bridge — is rendered ineffective for any in-flight yield.

For `fin_transfer_callback`: fraudulent or otherwise undesired proofs submitted just before a pause can still be finalized (minting tokens on NEAR) after the pause takes effect, defeating the purpose of the emergency stop.

## Likelihood Explanation

For `init_transfer_resume`: **Medium-high**. Yields can remain pending for hours or days (until the yield timeout). Any actor — including the original user — can deposit storage to trigger the resume. The attacker does not need to race against the pause; they simply wait for the pause to be set and then deposit storage. No special privileges are required; `storage_deposit` is a standard NEAR call.

For `fin_transfer_callback`: **Low-medium**. The window between `fin_transfer` and its callback is only a few NEAR blocks (~1–2 seconds), requiring the admin to pause in that exact window. This is a much narrower and less exploitable race condition.

## Recommendation

Add a pause check at the top of both callback functions:

```rust
// In init_transfer_resume (line 623):
#[private]
#[allow(clippy::needless_pass_by_value)]
pub fn init_transfer_resume(...) -> U128 {
    self.assert_not_paused(); // add this
    ...
}

// In fin_transfer_callback (line 700):
#[private]
#[payable]
pub fn fin_transfer_callback(...) -> PromiseOrValue<Nonce> {
    self.assert_not_paused(); // add this
    ...
}
```

Alternatively, apply the `#[pause]` macro with the same role exceptions as the corresponding entry point to both callback functions. For `init_transfer_resume`, if the bridge is paused and the resume is blocked, the yield will eventually time out and the user's tokens should be refunded via the existing error-return path at lines 641–642.

## Proof of Concept

**`init_transfer_resume` scenario (primary):**

1. Alice calls `ft_transfer_call` on a bridged token → `ft_on_transfer` → `init_transfer` on the NEAR bridge with insufficient storage for the message account. A yield promise is created and stored in `init_transfer_promises` (lines 586–605).
2. Admin pauses the bridge (e.g., via `acl_grant_role(Role::PauseManager)` + pause call).
3. Alice (or any actor) calls `storage_deposit` for the virtual `message_storage_account_id`, which triggers `env::promise_yield_resume` internally.
4. `init_transfer_resume` executes at line 623 — **no pause check** — successfully transfers balance from the message account (line 635), and calls `init_transfer_internal` at line 645.
5. Alice's tokens are burned/locked and `InitTransferEvent` is emitted (line 1865) despite the bridge being paused.
6. A relayer picks up the event and calls `fin_transfer` on the destination chain, completing the cross-chain transfer during a pause.

**Reproducible test plan:** Deploy the contract on a NEAR localnet. Call `ft_transfer_call` with a message that triggers the yield path (insufficient storage). Set the pause. Then call `storage_deposit` for the message storage account. Observe that `init_transfer_resume` executes and `InitTransferEvent` is emitted, confirming the bypass.
