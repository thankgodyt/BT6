### Title
Silent nBTC Permanent Lock via Self-Transfer in Legacy `ft_transfer` Withdrawal Path When Relayer Is Unset — (`contracts/nbtc/src/lib.rs`)

### Summary

The nBTC contract's `ft_transfer` override contains a legacy Near Intents withdrawal shortcut. When `receiver_id` equals the nBTC contract itself and the memo starts with `"WITHDRAW_TO:"`, the code attempts to redirect to a configured withdraw relayer. If no relayer is set, the function silently falls through and executes a standard transfer to the nBTC contract itself. Because the nBTC contract has no recovery mechanism for tokens held in its own account, those tokens are permanently locked, reducing backed supply below total supply.

### Finding Description

In `contracts/nbtc/src/lib.rs` lines 183–196, the `ft_transfer` override handles the legacy withdrawal flow:

```rust
fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
    // Legacy bridging flow used by Near Intents
    if receiver_id == env::current_account_id()
        && memo.as_ref().is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
    {
        if let Some(withdraw_relayer) = Self::read_withdraw_relayer_address() {
            return self.token.ft_transfer(withdraw_relayer, amount, memo);
        }
    }
    self.token.ft_transfer(receiver_id, amount, memo);
}
``` [1](#0-0) 

When the outer condition is satisfied (`receiver_id == nbtc_contract` AND memo starts with `"WITHDRAW_TO:"`) but `read_withdraw_relayer_address()` returns `None`, the function does **not** revert. It falls through to `self.token.ft_transfer(receiver_id, amount, memo)`, where `receiver_id` is the nBTC contract itself — a self-transfer. [2](#0-1) 

For the self-transfer to succeed, the nBTC contract's own account must be registered in the token storage. The `new` constructor only registers `bridge_id`: [3](#0-2) 

Any unprivileged user can register the nBTC contract's own account by calling `storage_deposit(account_id = Some(nbtc_contract_address))`. Once registered, the self-transfer succeeds and the tokens are deposited into the nBTC contract's own balance.

The nBTC contract has no function to recover tokens held in its own account. The `burn` function withdraws from `bridge_id`, not from the nBTC contract's own account: [4](#0-3) 

The `set_withdraw_relayer_address` function is controller-only and is not set at construction time, meaning the contract starts in the vulnerable state: [5](#0-4) 

This is the direct analog to M-02: just as Cally allowed a vault to be created with the contract's own address as `token` — causing the vault's ownership to pass to the contract and ETH to be locked — here the nBTC contract allows tokens to be transferred to itself via the legacy withdrawal path when the relayer is unconfigured, with no recovery path.

### Impact Explanation

Any nBTC tokens transferred to the nBTC contract via this path are permanently locked. The total supply remains unchanged but the locked tokens are no longer backed by any BTC (no withdrawal was initiated), permanently reducing backed supply below total supply. This matches the **Medium** impact category: *"permanent burning below backed supply"* and *"stuck bridge state requiring operator intervention."*

### Likelihood Explanation

Two preconditions are required:

1. **Withdraw relayer not set**: The contract starts with no relayer configured (`read_withdraw_relayer_address()` returns `None` by default). The relayer is only set by the controller via `set_withdraw_relayer_address`. Any window between deployment and relayer configuration is exploitable. Additionally, if the controller ever removes the relayer, the window reopens.

2. **nBTC contract's own storage account registered**: Any unprivileged user can call `storage_deposit(account_id = Some(nbtc_contract_address))` for a small NEAR deposit. This is a one-time, permissionless setup step.

Near Intents users relying on the legacy `"WITHDRAW_TO:"` memo flow are the realistic victim population. An attacker who registers the nBTC contract's own account during the initial deployment window (before the relayer is set) creates a permanent trap for any such user.

### Recommendation

Replace the silent fallthrough with an explicit revert when the relayer is not configured:

```rust
fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
    if receiver_id == env::current_account_id()
        && memo.as_ref().is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
    {
        let withdraw_relayer = Self::read_withdraw_relayer_address()
            .unwrap_or_else(|| env::panic_str("Withdraw relayer not configured"));
        return self.token.ft_transfer(withdraw_relayer, amount, memo);
    }
    self.token.ft_transfer(receiver_id, amount, memo);
}
```

This ensures that any attempt to use the legacy withdrawal flow when no relayer is set reverts cleanly rather than silently locking tokens.

### Proof of Concept

1. Attacker calls `storage_deposit(account_id = Some("<nbtc_contract_address>"), registration_only = Some(true))` on the nBTC contract, paying the minimum storage deposit. This registers the nBTC contract's own account in the token storage.
2. The controller has not yet called `set_withdraw_relayer_address` (initial deployment state), so `read_withdraw_relayer_address()` returns `None`.
3. Victim (a Near Intents user) calls `ft_transfer(receiver_id = "<nbtc_contract_address>", amount = X, memo = Some("WITHDRAW_TO:bc1q..."))` expecting to initiate a legacy BTC withdrawal.
4. The condition `receiver_id == env::current_account_id() && memo.starts_with("WITHDRAW_TO:")` is `true`.
5. `read_withdraw_relayer_address()` returns `None`; the inner `if let Some(...)` branch is skipped.
6. Execution falls through to `self.token.ft_transfer(nbtc_contract_address, X, memo)`.
7. The nBTC contract's own account is registered (step 1), so the transfer succeeds: `X` nBTC is deposited into the nBTC contract's own balance.
8. No BTC withdrawal was initiated. The `X` nBTC tokens are permanently locked with no recovery function available. Total supply exceeds backed supply by `X` satoshis.
