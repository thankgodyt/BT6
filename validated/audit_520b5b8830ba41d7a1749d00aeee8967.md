Audit Report

## Title
Decimal Normalization Dust Permanently Locked When Transfer Fee Is Zero - (File: `near/omni-bridge/src/lib.rs`)

## Summary
`normalize_amount` uses floor integer division to convert token amounts from higher-decimal source chains to lower-decimal destination chains. When a user initiates a transfer with `fee = 0`, the truncated remainder ("dust") is permanently locked in the NEAR bridge contract (for native tokens) or burned (for deployed tokens), with no recovery path. When `fee > 0`, the `claim_fee` flow absorbs dust into the relayer fee, but this mechanism is entirely absent for zero-fee transfers.

## Finding Description

**Root cause — floor division in `normalize_amount`:** [1](#0-0) 

The function divides by `10^diff_decimals` with no rounding or remainder return.

**Full amount (including dust) is locked/burned in `init_transfer_internal`:** [2](#0-1) 

The entire `transfer_message.amount` is locked or burned before any normalization occurs.

**`sign_transfer` normalizes only `amount_without_fee()` for the MPC payload:** [3](#0-2) 

`amount_without_fee()` returns `amount - fee.fee` (see `near/omni-types/src/lib.rs` line 593–595). With `fee = 0`, this is the full `amount`, and floor division silently drops `amount % 10^diff_decimals`.

**`sign_transfer_callback` removes the transfer message immediately when `fee.is_zero()`:** [4](#0-3) 

After removal, no `claim_fee` call is ever made, so the dust has no recovery path.

**Contrast with `fee > 0` path — dust is absorbed into the relayer fee in `claim_fee_callback`:** [5](#0-4) 

`fee = transfer_message.amount.0 - denormalized_amount` captures both the user-specified fee and the normalization remainder. This mechanism is entirely skipped when `fee = 0`.

**`Fee::is_zero()` checks both `fee` and `native_fee`:** [6](#0-5) 

A user setting both to zero triggers the immediate removal path with no dust recovery.

## Impact Explanation

This is a concrete instance of **decimal/normalization abuse causing escrow mis-accounting**: the NEAR bridge locks `X` units but only authorizes `X / 10^diff_decimals * 10^diff_decimals` units to be claimed on the destination chain. The remainder `X % 10^diff_decimals` is permanently irrecoverable. For tokens with `origin_decimals = 24` and `decimals = 6` (e.g., a NEAR-native token bridged to EVM), the maximum dust per transfer is `10^18 - 1` native units — nearly one full token. This is a direct, permanent loss of bridged user funds qualifying as escrow mis-accounting and decimal/normalization abuse under the allowed Critical impact scope.

## Likelihood Explanation

The exploit requires no special role or privilege. Any user can call `ft_transfer_call` targeting the bridge with `fee = 0` and a non-round amount. The condition fires on every transfer where `amount % 10^diff_decimals != 0` and `fee.is_zero()`. The bridge is fully permissionless for initiating transfers, making this trivially repeatable by any token holder.

## Recommendation

Before locking/burning tokens in `init_transfer_internal`, compute the effective transferable amount and return the dust to the sender:

```rust
let dust = amount.0 % 10_u128.pow(diff_decimals);
let effective_amount = amount.0 - dust;
// lock/burn only effective_amount; return dust to sender
```

Alternatively, reject transfers where `fee = 0` and `origin_decimals != decimals`, requiring a non-zero fee to ensure dust is always recoverable via `claim_fee`.

## Proof of Concept

**Setup:** Token with `origin_decimals = 24` on NEAR, `decimals = 6` on EVM. `diff_decimals = 18`.

1. User calls `ft_transfer_call` with `amount = 1_999_999_999_999_999_999_000_000` and `fee = 0`.
2. `init_transfer_internal` locks the full `1_999_999_999_999_999_999_000_000` units.
3. `sign_transfer` computes `normalize_amount(1_999_999_999_999_999_999_000_000, {decimals:6, origin_decimals:24})` = `1_999_999_999_999_999_999_000_000 / 10^18` = `1_999_999`.
4. MPC signs a payload for `amount = 1_999_999` (6 decimals).
5. `sign_transfer_callback`: `fee.is_zero()` → `remove_transfer_message(transfer_id)`. Transfer message deleted.
6. EVM contract receives `1_999_999` units (6 decimals).
7. Dust = `1_999_999_999_999_999_999_000_000 - 1_999_999 * 10^18` = `999_000_000_000_000_000` units (≈0.000999 tokens, 24 decimals) remains permanently locked in the NEAR bridge with no recovery path.

A local integration test can confirm this by: (a) calling `ft_transfer_call` with the above parameters, (b) asserting the bridge's locked balance increased by the full amount, (c) asserting the signed payload amount equals only the floor-divided value, and (d) asserting no subsequent `claim_fee` call is possible for the transfer ID after `sign_transfer_callback` removes it.
