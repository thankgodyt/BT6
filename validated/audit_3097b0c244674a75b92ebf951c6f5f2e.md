### Title
Peras Certificate Validation Unconditionally Accepts Any Inbound Certificate Without Checking Parameters - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` function unconditionally returns `Right` for every certificate it receives, performing zero validation of the certificate's fields. This is the live production code path used when processing inbound Peras certificates from peers via the object-diffusion miniprotocol. An unprivileged peer can inject a crafted certificate with an arbitrary round number and boosted-block point; the certificate will be accepted, stored in the `PerasCertDB`, and fed into chain selection, where its boost weight will influence which chain the node prefers.

### Finding Description

`processCerts` is the function that handles every batch of `PerasCert` objects received from a remote peer. It filters out already-known certificates, calls `validateCert` on each remaining one, and — if all pass — timestamps and stores them:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [4](#0-3) 

Because `validatePerasCert` never returns `Left`, the `(errs, _)` branch is unreachable. Every certificate — regardless of its `pcCertRound`, `pcCertBoostedBlock`, or any cryptographic content — is accepted and stored.

The stored certificate is then fed into chain selection via `addPerasCertAsync chainDB`, which applies the certificate's `vpcCertBoost` weight to the boosted block during `preferAnchoredCandidate` comparisons: [5](#0-4) 

The `ValidatedPerasCert` carries a `vpcCertBoost :: PerasWeight` field that is unconditionally set to `perasWeight params` regardless of the certificate's actual content: [6](#0-5) 

### Impact Explanation

An unprivileged peer can craft a `PerasCert` with:
- An arbitrary `pcCertRound` (e.g., round 0, a far-future round, or a round that already has a legitimate certificate for a different block)
- An arbitrary `pcCertBoostedBlock` pointing to any block hash, including one on an adversarial fork

The injected certificate passes `validatePerasCert` unconditionally, is stored in `PerasCertDB`, and its boost weight is applied during chain selection. This allows the attacker to artificially inflate the weight of a non-canonical chain fragment, potentially causing the honest node to prefer it over the canonical chain. This is a bypass of Peras certificate validation that enables unauthorized certificate acceptance and chain-selection manipulation — matching the **Critical** impact tier: bypass of Peras certificate checks that enables unauthorized certificate acceptance.

### Likelihood Explanation

The object-diffusion miniprotocol for Peras certificates is part of the production node and is reachable by any peer that connects to the node. No privileged keys, stake majority, or operator access are required. The attacker only needs to be a connected peer and send a well-formed CBOR-encoded `PerasCert` message. The stub implementation is the only instance in the codebase and is used unconditionally for all block types.

### Recommendation

Replace the stub `validatePerasCert` implementation with one that performs the required checks before accepting a certificate:

1. **Round-number bounds**: Reject certificates whose `pcCertRound` is in the past (older than the immutable tip's round) or implausibly far in the future.
2. **Boosted-block existence**: Reject certificates that boost a block point not present in the VolatileDB or ImmutableDB.
3. **Aggregate signature verification**: Verify the BLS aggregate signature in `pcSignature` against the claimed voters and the certificate message `(pcCertRound, pcCertBoostedBlock)`.
4. **Quorum check**: Verify that the claimed voters collectively hold sufficient stake to meet the quorum threshold.

Until the full cryptographic validation is in place, the node should at minimum enforce the structural/range checks (1) and (2) to prevent trivially crafted certificates from influencing chain selection.

### Proof of Concept

1. Connect to a target node as a peer via the Peras certificate object-diffusion miniprotocol.
2. Send a `PerasCert` message with:
   - `pcCertRound = <round of a block on an adversarial fork>`
   - `pcCertBoostedBlock = <point of a block on the adversarial fork>`
3. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{vpcCertBoost = perasWeight mkPerasParams}` without inspecting any field of `cert`.
4. The certificate is stored in `PerasCertDB` via `addCert`.
5. `addPerasCertAsync chainDB` is called, triggering chain selection.
6. During chain selection, `preferAnchoredCandidate` applies the boost weight to the adversarial fork's block, potentially making it preferred over the honest chain. [7](#0-6) [8](#0-7)

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
