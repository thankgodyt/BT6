### Title
Missing Upper Bound on Caller-Supplied `gas_fee` in Refund Request Allows Near-Zero User Refund — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

The `request_refund_callback` function accepts a caller-supplied `gas_fee` with no upper bound validation. Unlike the withdrawal PSBT flow, which enforces `config.min_btc_gas_fee` and `config.max_btc_gas_fee` bounds, the refund path only checks that `gas_fee < amount`. A public caller can submit a refund request with `gas_fee = amount − 1`, causing the user to receive 1 satoshi from their refund while the remainder is consumed as miner fees.

---

### Finding Description

In `request_refund_callback`, the caller-supplied `gas_fee` is resolved and stored with only a single guard:

```rust
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
``` [1](#0-0) 

This `resolved_gas_fee` is then stored verbatim in the `RefundRequest`: [2](#0-1) 

Later, in `refund_execution_inputs`, the refund amount is computed as `amount − gas_fee` with only a `> 0` guard:

```rust
let refund_amount = refund_request
    .amount
    .checked_sub(refund_request.gas_fee)
    .expect("Deposit amount too small to cover gas fee");
require!(refund_amount > 0, "Refund amount is zero after gas fee");
``` [3](#0-2) 

**Contrast with the withdrawal flow.** In `check_withdraw_psbt`, the gas fee is validated against protocol-configured bounds:

```rust
require!(
    gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee,
    ...
);
``` [4](#0-3) 

The refund path has no equivalent check. The `internal_request_refund` function does not verify the caller's identity against the depositor: [5](#0-4) 

This means any public caller who observes a deposit transaction on-chain can race to submit a refund request with an arbitrarily high `gas_fee`.

---

### Impact Explanation

A malicious actor who front-runs the depositor's own `request_refund` call can set `gas_fee = deposit_amount − 1`. The stored `RefundRequest.gas_fee` is then used directly to compute `refund_amount = 1 satoshi`. After the timelock elapses and `execute_refund` is called, the user receives 1 satoshi while the rest is paid to miners. This constitutes a significant, attacker-triggered loss of user funds routed through the bridge refund path.

**Allowed impact match:** Medium — harmful smart-contract behavior without direct theft; the bridge state requires operator (DAO) intervention to reject the malicious request before the timelock expires.

---

### Likelihood Explanation

The `internal_request_refund` function imposes no identity check on the caller relative to the depositor. Any NEAR account can submit a refund request for any observed deposit UTXO. The only mitigation is the DAO's ability to call `internal_reject_refund` during the timelock window. If the DAO is slow, offline, or the attacker times the submission close to timelock expiry, the malicious request proceeds to execution. [6](#0-5) 

---

### Recommendation

Add a maximum cap on the caller-supplied `gas_fee` in `request_refund_callback`, mirroring the withdrawal flow:

```rust
require!(
    resolved_gas_fee <= config.max_btc_gas_fee,
    "Gas fee exceeds protocol maximum"
);
```

This ensures the refund amount cannot be reduced below a meaningful floor, analogous to a `minAmountOut` guard.

---

### Proof of Concept

1. Alice sends 100,000 satoshis to her bridge deposit address.
2. Bob (attacker) observes the deposit transaction on-chain before Alice calls `request_refund`.
3. Bob calls `request_refund` with `gas_fee = 99_999` (one less than the deposit amount).
4. `request_refund_callback` stores `RefundRequest { amount: 100_000, gas_fee: 99_999, refund_address: alice_address, ... }`.
5. The timelock elapses (DAO does not reject in time).
6. `execute_refund` is called; `refund_execution_inputs` computes `refund_amount = 100_000 − 99_999 = 1`.
7. The check `require!(refund_amount > 0, ...)` passes.
8. Alice receives 1 satoshi; 99,999 satoshis are paid to miners. [1](#0-0) [3](#0-2)
