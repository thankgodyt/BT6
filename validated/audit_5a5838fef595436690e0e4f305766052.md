### Title
Unconditional `validatePerasCert` Stub Bypasses All Peras Certificate Validation, Enabling Peer-Crafted Certificates to Influence Chain Selection — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance's `validatePerasCert` function unconditionally accepts every inbound certificate from a peer without performing any cryptographic or semantic check. This stub is the only instance in the codebase and is called directly in the production inbound-certificate processing path. An unprivileged peer can send a crafted `PerasCert` naming any block in the VolatileDB for any round number; the certificate will be accepted, stored, and used to boost that block's chain weight, potentially causing the honest node to switch to a non-canonical chain.

---

### Finding Description

**Root cause — `validatePerasCert` stub**

`BlockSupportsPeras` declares `validatePerasCert` as the mandatory validation gate for every inbound Peras certificate. The only instance in the repository is a degenerate stub:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

The stub skips every check that a real implementation must perform:
- BLS aggregate-signature verification over `(roundNo, boostedBlock)`
- Round-number validity (not expired, not from the future, not already certified)
- Voter eligibility and seat-index verification
- Confirmation that the boosted block is a descendant of the most-recently certified block

**Production call site — `processCerts`**

The inbound-certificate handler in the Peras miniprotocol calls this stub directly:

```haskell
(validatePerasCert mkPerasParams)
``` [2](#0-1) 

`processCerts` filters out duplicate round numbers, then calls `validateCert` on every new certificate. Because the stub always returns `Right`, every certificate passes and is timestamped and forwarded to `addPerasCertAsync`: [3](#0-2) 

**Chain-selection consequence — `chainSelSync`**

`addPerasCertAsync` enqueues the certificate for the background chain-selection thread. `chainSelSync` then:
1. Checks only that the boosted block's slot is not older than the immutable tip
2. Looks up the boosted block header in the VolatileDB
3. Calls `chainSelectionForBlock` for that header, applying the full Peras weight boost [4](#0-3) 

No check is made on whether the certificate's round number is plausible, whether the aggregate signature is valid, or whether the voters were eligible. The boost is applied unconditionally.

**Secondary root cause — `validatePerasVote` stub**

The same degenerate instance also stubs out `validatePerasVote`, checking only that the voter ID appears in the stake distribution and ignoring the BLS signature, VRF eligibility proof, and round-number validity: [5](#0-4) 

The vote ingest path (`makePerasVotePoolWriterFromChainDB`) calls this stub for every inbound vote: [6](#0-5) 

A peer that knows any valid voter ID (public information from the stake distribution) can fabricate votes for arbitrary rounds and blocks. Once enough fabricated votes accumulate to reach quorum, `implAddVote` forges a certificate and feeds it into `addPerasCertAsync`, completing the same chain-selection attack without even needing to send a direct certificate: [7](#0-6) 

---

### Impact Explanation

**Certificate path (direct):** A single crafted `PerasCert` naming any block in the VolatileDB is accepted unconditionally. If that block is on a fork, chain selection will re-evaluate the fork with the full Peras weight boost and may switch the node's preferred chain to a non-canonical tip. This is a bypass of Peras certificate validation that enables unauthorized certificate acceptance and a chain-selection deviation beyond the protocol's intended security assumptions.

**Vote path (indirect):** A peer that knows any voter ID in the current stake distribution can send fabricated votes for an arbitrary round and block. Once quorum is reached, a certificate is auto-forged and the same chain-selection attack follows. Because `validatePerasVote` does not verify the BLS signature or VRF eligibility proof, the attacker does not need to hold the corresponding private key.

---

### Likelihood Explanation

The attack requires only a standard peer connection via the Peras object-diffusion miniprotocol. No key material, stake majority, or operator access is needed. Voter IDs are derived from the public stake distribution. The degenerate instance is the only `BlockSupportsPeras` instance in the repository and is unconditionally selected for all block types, so there is no production code path that performs real validation today.

---

### Recommendation

1. Implement a concrete `BlockSupportsPeras` instance for Cardano blocks that performs full BLS aggregate-signature verification, round-number range checks (against the current slot and the latest on-chain certificate round), and voter-eligibility verification before returning `Right`.
2. In `validatePerasVote`, verify the BLS vote signature and the VRF eligibility proof before accepting the vote.
3. In `implAddVote`, add a round-number validity check against the current chain state (analogous to the `ACTIVATION_DEADLINE` / `GRACE_PERIOD` guards in the governance contract) so that votes for expired or far-future rounds are rejected at the DB layer.
4. Remove or gate the degenerate universal instance behind a compile-time flag so it cannot be selected in production builds.

---

### Proof of Concept

```
1. Attacker connects to an honest node via the Peras certificate miniprotocol.

2. Attacker observes the VolatileDB tip of a competing fork (e.g., via ChainSync)
   and constructs:
     PerasCert { pcCertRound = <any round>, pcCertBoostedBlock = <fork tip hash> }

3. Attacker sends the crafted PerasCert to the honest node.

4. processCerts filters duplicates (none), calls validatePerasCert mkPerasParams,
   which returns Right unconditionally.

5. The certificate is timestamped and forwarded to addPerasCertAsync.

6. chainSelSync receives ChainSelAddPerasCert, checks only that the boosted
   block's slot >= immutable tip slot, finds the fork-tip header in VolatileDB,
   and calls chainSelectionForBlock with the full Peras weight boost applied.

7. If the fork's boosted weight now exceeds the honest chain's weight, the node
   switches to the attacker-chosen fork.
```

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes

implAddVote ::
  ( IOLike m
  , StandardHash blk
  , Typeable blk
  ) =>
  PerasCfg blk ->
  PerasVoteDbEnv m blk ->
  WithArrivalTime (ValidatedPerasVote blk) ->
  STM m (m (AddPerasVoteResult blk))
implAddVote perasCfg PerasVoteDbEnv{pvdeTracer, pvdeState} vote = do
  let voteId = getPerasVoteId vote
  addPerasVoteRes <- do
    WithFingerprint pvds fp <- readTVar pvdeState
    (res, pvds') <- addOrIgnoreVote pvds voteId
    writeTVar pvdeState (WithFingerprint pvds' (succ fp))
    pure res
  pure $ do
    traceWith pvdeTracer (AddVote voteId vote addPerasVoteRes)
    return addPerasVoteRes
 where
  addOrIgnoreVote pvds voteId
    -- Vote is already in the DB => ignore it
    | Set.member voteId (pvdsVoteIds pvds) = voteAlreadyInDB pvds
    -- New vote => try to add it to the DB
    | otherwise = tryAddVote pvds voteId

  voteAlreadyInDB pvds = pure (PerasVoteAlreadyInDB, pvds)

  tryAddVote pvds voteId = do
    let pvsVoteIds' = Set.insert voteId (pvdsVoteIds pvds)
        pvsLastTicketNo' = succ (pvdsLastTicketNo pvds)
        pvsVotesByTicket' = Map.insert pvsLastTicketNo' vote (pvdsVotesByTicket pvds)

    (addPerasVoteRes, pvsRoundVoteStates') <-
      case updatePerasRoundVoteStates vote perasCfg (pvdsRoundVoteStates pvds) of
        -- Added vote and reached a quorum, forging a new certificate
        Right (VoteGeneratedNewCert cert, pvsRoundVoteStates') ->
          pure (AddedPerasVoteAndGeneratedNewCert cert, pvsRoundVoteStates')
        -- Added vote but did not generate a new certificate, either
        -- because quorum was not reached yet, or because this vote was
        -- cast upon a target that had already won so a certificate was
        -- forged in a previous step.
        Right (VoteDidntGenerateNewCert, pvsRoundVoteStates') ->
          pure (AddedPerasVoteButDidntGenerateNewCert, pvsRoundVoteStates')
        -- Adding the vote led to more than one winner => internal error
        Left (RoundVoteStateLoserAboveQuorum winnerState loserState) ->
          throwSTM $
            MultipleWinnersInRound
              (getPerasVoteRound vote)
              ( ExistingPerasRoundWinner
                  ( getPerasVoteBlock winnerState
                  , ptvsTotalStake winnerState
                  )
              )
              ( BlockedPerasRoundWinner
                  ( getPerasVoteBlock loserState
                  , ptvsTotalStake loserState
                  )
              )
        -- Reached quorum but failed to forge a certificate
        Left (RoundVoteStateForgingCertError forgeErr) ->
          throwSTM $
            ForgingCertError forgeErr
