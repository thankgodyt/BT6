### Title
Missing Ownership Check on `withdraw_rbf` Allows Any Account to Initiate RBF for Another User's Pending Withdrawal - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary
The `withdraw_rbf` function in the bridge contract does not verify that the caller is the owner of the pending withdrawal being replaced. Any unprivileged NEAR account can call `withdraw_rbf` with a victim's `original_btc_pending_verify_id`, injecting an attacker-controlled `output` and creating an RBF transaction under the attacker's account that replaces the victim's in-flight withdrawal. This is a broken access control issue directly analogous to the external report's finding: authorization is expected but never enforced at the contract level.

### Finding Description

The `withdraw_rbf` function is documented as a user-initiated action to accelerate their own withdrawal by increasing the gas fee: [1](#0-0) 

The function derives `account_id` from `env::predecessor_account_id()` (the caller) and passes it directly to `withdraw_rbf_chain_specific`, without ever loading the pending info to verify that `predecessor == pending_info.account_id`. The only guard is `require_pending_sign_capacity(&account_id)`, which checks the *caller's* capacity, not the victim's.

Contrast this with `cancel_withdraw`, which is the operator-facing equivalent. There, the code explicitly retrieves the owner from the pending info before acting: [2](#0-1) 

In `cancel_withdraw`, `user_account_id` is read from `internal_unwrap_btc_pending_info(...).account_id`. In `withdraw_rbf`, no such lookup is performed — the caller's identity is used unconditionally. This asymmetry is the root cause.

The `BTCPendingInfo` struct stores the true owner in `account_id`: [3](#0-2) 

Because `withdraw_rbf` never compares `env::predecessor_account_id()` against `btc_pending_info.account_id`, any NEAR account can supply an arbitrary `original_btc_pending_verify_id` belonging to a different user and an attacker-chosen `output` vector, and the contract will proceed to build and sign an RBF transaction.

The same pattern applies to `clear_invalid_pending_verify_rbf` and `batch_clear_invalid_pending_verify_rbf`, which carry no role restriction and allow any caller to remove pending-verify RBF entries from contract state: [4](#0-3) 

### Impact Explanation

An attacker who calls `withdraw_rbf` with a victim's `original_btc_pending_verify_id` causes the bridge to build and MPC-sign a replacement Bitcoin transaction. The replacement transaction is linked to the victim's original UTXO set. Once broadcast, it invalidates the victim's original pending transaction on the Bitcoin network. The victim's original `BTCPendingInfo` entry (under their account) now references a transaction that can never confirm, leaving their withdrawal in a permanently stuck state until operator intervention via `cancel_withdraw`. This matches the allowed impact: *attacker-triggered temporary locking of bridged funds* and *stuck bridge state requiring operator intervention*.

Additionally, because the attacker supplies the `output` parameter, they control the fee structure of the replacement transaction. If output validation in `withdraw_rbf_chain_specific` is less strict than in the initial `check_withdraw_psbt_valid` path, the attacker may be able to drain additional value from the victim's locked nBTC as inflated fees.

### Likelihood Explanation

The function is public, requires no role, and is callable by any NEAR account. The only prerequisite is knowing a valid `original_btc_pending_verify_id`, which is emitted as a public on-chain event (`Event::GenerateBtcPendingInfo`) at withdrawal initiation: [5](#0-4) 

Any observer of NEAR chain events can collect these IDs and immediately target any in-flight withdrawal. No privileged access, leaked key, or social engineering is required.

### Recommendation

Add an ownership assertion at the top of `withdraw_rbf` before any state mutation:

```rust
pub fn withdraw_rbf(...) {
    let account_id = env::predecessor_account_id();
    // Verify caller owns the pending info
    let pending_info = self.internal_unwrap_btc_pending_info(&original_btc_pending_verify_id);
    require!(
        pending_info.account_id == account_id,
        "Only the withdrawal owner can initiate RBF"
    );
    self.require_pending_sign_capacity(&account_id);
    self.withdraw_rbf_chain_specific(account_id, original_btc_pending_verify_id, output, chain_specific_data);
}
```

Apply the same ownership check to any other user-facing RBF entry points that currently use `env::predecessor_account_id()` without verifying it against the stored `account_id`. Also restrict `clear_invalid_pending_verify_rbf` and `batch_clear_invalid_pending_verify_rbf` to trusted relayer or operator roles, consistent with the comment that "the off-chain program uses this interface."

### Proof of Concept

1. Victim calls `ft_transfer_call` on the nBTC contract with a `Withdraw` message, initiating a withdrawal. The bridge emits `Event::GenerateBtcPendingInfo` with `btc_pending_id = X`.
2. Attacker observes the event and records `X` as `original_btc_pending_verify_id`.
3. Attacker calls `withdraw_rbf(original_btc_pending_verify_id: X, output: [...attacker_chosen_outputs...], chain_specific_data: None)` from their own NEAR account.
4. The contract executes without any ownership check. `account_id = attacker`. `withdraw_rbf_chain_specific(attacker, X, ...)` is called.
5. A new RBF `BTCPendingInfo` is created under the attacker's account, linked to the victim's original UTXO.
6. `sign_btc_transaction` is called (also unrestricted) to MPC-sign the RBF transaction.
7. The RBF transaction is broadcast and replaces the victim's original transaction on Bitcoin.
8. The victim's original pending info references a now-invalid transaction. The victim cannot call `verify_withdraw` successfully. Their nBTC remains locked. Only a DAO/Operator `cancel_withdraw` can recover the funds. [6](#0-5) [7](#0-6)
