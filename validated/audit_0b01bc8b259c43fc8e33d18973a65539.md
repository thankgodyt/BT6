### Title
Peras Certificate and Vote Validation Bypass: `validatePerasCert` Stub Always Accepts Any Peer-Supplied Certificate Without Cryptographic Checks — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance in `SupportsPeras.hs` provides a stub `validatePerasCert` that unconditionally returns `Right` (success) for every peer-supplied Peras certificate, performing zero cryptographic or structural validation. The companion `validatePerasVote` only checks stake-distribution membership and never verifies the vote's cryptographic signature. Both stubs are wired into the live object-diffusion inbound path. An unprivileged peer can therefore inject arbitrary Peras certificates or forged votes that are accepted as valid, causing the node to apply weight boosts to attacker-chosen blocks and potentially triggering a chain-selection switch to a non-canonical fork.

---

### Finding Description

**Root cause — `validatePerasCert` stub:**

The only `BlockSupportsPeras` instance in the codebase is a universal one:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

Every call to `validatePerasCert` returns `Right` regardless of the certificate's content. No signature, no committee membership, no round-number, and no boosted-block validity check is performed.

**Root cause — `validatePerasVote` stub:**

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [2](#0-1) 

This only checks whether the claimed voter ID exists in the stake distribution. It never calls `verifyVoteSignature`, so any peer can forge a vote attributed to any legitimate voter ID.

**Production call site — certificate inbound path:**

`makePerasVotePoolWriterFromChainDB` (and the `PerasCert` pool writer) call these stubs directly on peer-supplied objects:

```haskell
opwAddObjects = \certs ->
  processCerts
    systemTime
    (ChainDB.getPerasCertIds chainDB)
    (validatePerasCert mkPerasParams)   -- ← always Right
    (void . ChainDB.addPerasCertAsync chainDB)
    certs
``` [3](#0-2) 

`processCerts` partitions results with `partitionEithers (validateCert <$> certsNotAlreadyInDb)`. Because `validatePerasCert` never returns `Left`, every peer-supplied certificate lands in the "all valid" branch and is forwarded to `ChainDB.addPerasCertAsync`. [4](#0-3) 

**Chain-selection consequence:**

`chainSelSync` processes each accepted certificate. If the boosted block is in the VolatileDB and not already on the current chain, it calls `chainSelectionForBlock` for that block, potentially switching the node to a fork:

```haskell
-- Trigger chain selection for the boosted block.
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [5](#0-4) 

The Peras weight boost (`vpcCertBoost`) is applied during candidate comparison, making the boosted fork heavier than the honest chain.

### Impact Explanation

**Impact class: Critical — bypass of certificate/vote verification enabling unauthorized certificate acceptance and chain-selection manipulation.**

An unprivileged peer connected via the Peras object-diffusion miniprotocol can:

1. **Forge a `PerasCert`** pointing to any block hash in the VolatileDB. Because `validatePerasCert` always succeeds, the certificate is stored and triggers `chainSelectionForBlock` for the attacker-chosen block. The Peras weight boost (`perasWeight params`) is applied, making a minority fork appear heavier than the honest chain. The node switches to the attacker's fork.

2. **Forge `PerasVote`s** attributed to any legitimate voter ID in the stake distribution (no signature check). By sending enough forged votes to reach quorum, the node internally generates a `ValidatedPerasCert` and adds it to the ChainDB, achieving the same chain-selection manipulation without even needing to send a certificate directly.

Both paths lead to a **chain-selection safety failure**: the node accepts an invalid certificate and may irreversibly prefer a non-canonical chain, violating the Ouroboros Common Prefix property.

---

### Likelihood Explanation

The Peras object-diffusion miniprotocol is wired into the production node initialization path (see `makePerasVotePoolWriterFromChainDB` and the cert pool writer). Any peer that negotiates the Peras miniprotocol version can send crafted objects. No stake, no keys, and no prior knowledge beyond a valid voter ID (publicly visible in the stake distribution) are required. The attack is deterministic and requires a single well-formed network message.

---

### Recommendation

1. **Implement real cryptographic validation** in `validatePerasCert` before the Peras miniprotocol is enabled in production. At minimum, verify the aggregate BLS signature over `(pcCertRound, pcCertBoostedBlock)` against the aggregate public key of the claimed voters, and verify each voter's committee membership and eligibility proof. The concrete BLS machinery already exists in `Ouroboros.Consensus.Peras.Crypto.BLS` and the committee implementations (`EveryoneVotes`, `WFALS`).

2. **Implement vote-signature verification** in `validatePerasVote`. The `verifyVoteSignature` function is already defined and used in `implVerifyVote`; it must be called here before a vote is accepted.

3. **Gate the miniprotocol** behind a feature flag or era check so that the stub instance cannot be reached in production until the real validation is in place.

4. **Track the open TODO** at `https://github.com/tweag/cardano-peras/issues/120` as a security-critical item, not merely a correctness improvement.

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
