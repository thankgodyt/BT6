### Title
Unbound `refund_address` Parameter Allows Any Caller to Redirect BTC Refunds to Attacker-Controlled Address - (File: contracts/satoshi-bridge/src/refund.rs)

---

### Summary

When `deposit_msg.refund_address` is `None`, the `refund_address` argument passed to `request_refund` is accepted from any caller without ownership verification. Because the full `DepositMsg` is publicly emitted on-chain and the BTC transaction is public, an attacker can call `request_refund` before the legitimate depositor, storing their own BTC address as the refund destination and ultimately receiving the victim's BTC.

---

### Finding Description

`request_refund` is a publicly callable function. Its only guard on the `refund_address` parameter is:

```rust
// contracts/satoshi-bridge/src/refund.rs lines 154-158
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [1](#0-0) 

This check is only enforced when `deposit_msg.refund_address` is `Some`. When it is `None`, **any caller may supply any `refund_address`** and the contract accepts it unconditionally. The supplied address is then forwarded to the callback and stored as the authoritative refund destination:

```rust
// contracts/satoshi-bridge/src/refund.rs lines 179-183
.then(
    Self::ext(env::current_account_id())
        .with_static_gas(GAS_FOR_REQUEST_REFUND_CALLBACK)
        .request_refund_callback(deposit_msg, refund_address, tx_bytes, vout, gas_fee),
)
``` [2](#0-1) 

The `refund_address` is not part of the `DepositMsg` that cryptographically determines the deposit address. It is a free parameter with no binding to the depositor's identity.

The full `DepositMsg` is publicly broadcast on-chain the moment a user calls `get_user_deposit_address`:

```rust
// contracts/satoshi-bridge/src/api/bridge.rs lines 462-471
pub fn get_user_deposit_address(&self, deposit_msg: DepositMsg) -> String {
    let path = get_deposit_path(&deposit_msg);
    let deposit_address = self.generate_utxo_chain_address(&path).to_string();
    Event::LogDepositAddress {
        deposit_msg,
        path,
        deposit_address: deposit_address.clone(),
    }
    .emit();
``` [3](#0-2) 

An attacker who observes this event has everything needed to call `request_refund` first: the `deposit_msg`, the BTC transaction bytes (public on Bitcoin), the `vout`, and the Merkle proof. The first stored `RefundRequest` wins; a subsequent call for the same UTXO will fail because the key already exists.

The `unsafe_refund_timelock_sec` is applied in this case specifically to allow DAO/Operator to reject suspicious requests:

```rust
// contracts/satoshi-bridge/src/refund.rs lines 223-227
} else {
    // Refund address supplied by caller of `request_refund`: longer
    // timelock to give DAO/Operator time to reject suspicious requests.
    config.unsafe_refund_timelock_sec
}
``` [4](#0-3) 

However, this is a trusted-operator mitigation, not a cryptographic one. If the operator is offline, slow, or the attack is timed carefully, the attacker's `RefundRequest` executes and the BTC is sent to the attacker's address.

---

### Impact Explanation

An attacker who calls `request_refund` before the legitimate depositor (when `deposit_msg.refund_address` is `None`) causes the bridge's MPC-signed BTC refund transaction to send the victim's BTC to the attacker's address. This is a direct, complete theft of the depositor's BTC with no recovery path once `execute_refund` is signed and broadcast.

This matches: **Critical — Significant loss or theft of user funds.**

---

### Likelihood Explanation

All inputs required to mount the attack are public:
- `DepositMsg` is emitted via `LogDepositAddress` event on NEAR.
- The BTC transaction bytes and Merkle proof are available from the Bitcoin network.
- `vout` is deterministic from the transaction.

The attacker only needs to observe the NEAR event log and submit `request_refund` before the victim. On NEAR there is no traditional mempool, but the attacker can act at any time between the BTC confirmation and the victim's own `request_refund` call — a window that may be hours or days. The DAO/Operator rejection mechanism is the only mitigation, and it is not guaranteed.

**Likelihood: Medium** (requires attacker awareness and timely action, but all data is public and no special privilege is needed).

---

### Recommendation

Require `deposit_msg.refund_address` to always be set (non-`None`) when the deposit address is generated, so the refund destination is cryptographically committed to the deposit path before any BTC is sent. Alternatively, bind the `refund_address` to the NEAR `predecessor_account_id` of the original depositor and verify it at `request_refund` time. This mirrors the fix recommended in the PaymentProcessor report: include the sensitive routing parameter in the signed/committed data so it cannot be substituted by a third party.

---

### Proof of Concept

1. Alice calls `get_user_deposit_address(DepositMsg { recipient_id: "alice.near", refund_address: None, ... })`. The contract emits a `LogDepositAddress` event containing the full `DepositMsg`.
2. Alice sends BTC to the returned deposit address. The transaction is confirmed on Bitcoin.
3. The relayer never calls `verify_deposit` (relayer is down, or Alice changed her mind).
4. Bob (attacker) reads the `LogDepositAddress` event from NEAR and fetches Alice's BTC transaction and Merkle proof from Bitcoin.
5. Bob calls `request_refund(alice_deposit_msg, "bc1q_bob_address", alice_tx_bytes, 0, alice_proof, None)` — this passes all validation because `deposit_msg.refund_address` is `None`, so the `refund_address` check at line 154 is skipped entirely.
6. The `RefundRequest` is stored with `refund_address = "bc1q_bob_address"`.
7. Alice attempts `request_refund` with her own address — it fails because a `RefundRequest` already exists for that UTXO.
8. After `unsafe_refund_timelock_sec` elapses (assuming DAO/Operator does not reject), anyone calls `execute_refund`. The bridge builds and MPC-signs a BTC transaction sending Alice's BTC to Bob's address.
9. Bob broadcasts the transaction. Alice's BTC is permanently lost to Bob.
