### Title
Peras quorum check uses unverified stake-unit assumption, enabling false certificate forging - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` compares accumulated `PerasVoteStake` values against the quorum threshold without verifying that both quantities are expressed in the same units. The production code itself documents this as an unresolved assumption. If the `PerasVoteStakeDistr` supplied at runtime contains absolute ledger-stake values (e.g., lovelace) while the quorum threshold is a relative fraction (e.g., `0.75`), then any single vote from a voter with positive stake will satisfy the threshold, allowing an unprivileged peer to trigger certificate forging for an arbitrary block and cause chain-selection divergence.

---

### Finding Description

**Root cause — unverified unit assumption in `stakeAboveThreshold`**

The function compares the accumulated `PerasVoteStake` directly against the configured quorum threshold:

```haskell
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
```

The code itself carries an explicit, unresolved TODO:

> "this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … Under the current implementation of `PerasParams`, this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [1](#0-0) 

**How the stake value is assigned — no normalization**

`validatePerasVote` (the default implementation used in production) assigns the stake from the distribution directly to the `ValidatedPerasVote` without any normalization step:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
``` [2](#0-1) 

**Accumulation without normalization**

`updateTargetVoteTally` accumulates `vpvVoteStake` values directly into `ptvtTotalStake`:

```haskell
| (Nothing, votes') <- swapVote vote ptvtVotes =
    (votes', ptvtTotalStake + vpvVoteStake (forgetArrivalTime vote))
``` [3](#0-2) 

**Quorum check uses the un-normalized total**

`votesReachQuorum` passes the raw accumulated total to `stakeAboveThreshold`:

```haskell
totalVoteStake = mconcat (vpvVoteStake <$> votes)
votesHaveEnoughStake = stakeAboveThreshold cfg totalVoteStake
``` [4](#0-3) 

**Production call path**

`implAddVote` in `PerasVoteDB.Impl` calls `updatePerasRoundVoteStates`, which calls `updateCandidateVoteState`, which calls `votesReachQuorum`. This is the live path triggered by every inbound vote received from a peer via the object-diffusion mini-protocol. [5](#0-4) 

The pool writer that feeds this path reads the stake distribution from an STM action (`getStakeDistrSTM`) whose concrete value is injected at node startup: [6](#0-5)

### Impact Explanation

The Cardano ledger naturally represents stake in absolute units (lovelace). If `PerasVoteStakeDistr` is populated with absolute values — which is the natural representation — while `perasQuorumStakeThreshold` is a relative fraction (e.g., `3 % 4`), then for any voter whose absolute stake is a positive integer the comparison

```
1_000_000 % 1  >=  3 % 4  +  safetyMargin
```

is trivially `True`. A single vote from any voter with positive stake would satisfy the quorum check, causing `updateCandidateVoteState` to call `forgePerasCert` and produce a `ValidatedPerasCert`. That certificate is then stored in the `PerasVoteDB` and propagated to the `ChainDB`, where it boosts the targeted block's chain-selection weight by `perasWeight`. An honest node would then prefer that block over the canonical chain, causing a chain-selection divergence analogous to the over-minting in the original report: the system credits more "weight" than the actual stake warrants, and other nodes that do not receive the spurious certificate diverge.

This maps to the allowed impact class: **bypass of Peras voting/certificate checks enabling unauthorized certificate acceptance**, and **chain-selection bug letting an unprivileged peer make an honest node prefer a non-canonical chain**.

---

### Likelihood Explanation

The attacker-controlled entry path is the Peras vote object-diffusion mini-protocol. Any connected peer can send a well-formed, cryptographically valid vote (correct signature, correct round, correct voter ID present in the stake distribution). No key compromise, stake majority, or operator access is required. The only precondition is that the node's `PerasVoteStakeDistr` is populated with absolute ledger-stake values, which is the natural outcome of reading from the ledger's stake snapshot. The TODO comment confirms the normalization step is absent and the mismatch is a known open issue.

---

### Recommendation

1. **Normalize at ingestion**: when populating `PerasVoteStakeDistr`, divide each voter's absolute stake by the total stake to produce a relative value before storing it.
2. **Enforce units at the type level**: introduce distinct newtypes for absolute and relative stake so the compiler rejects unit-mismatched comparisons.
3. **Fix `stakeAboveThreshold`**: accept the total stake as an additional parameter and perform normalization internally, as the TODO comment suggests.

---

### Proof of Concept

1. A peer connects and sends a `PerasVote` for block `B` in round `R`, signed with a valid key whose `PerasVoterId` appears in the node's `PerasVoteStakeDistr` with an absolute stake value `s > 0`.
2. `processVotes` calls `validatePerasVote mkPerasParams stakeDistr vote`, which returns `ValidatedPerasVote { vpvVoteStake = s }` where `s` is the raw absolute lovelace value.
3. `implAddVote` calls `updatePerasRoundVoteStates`, which calls `updateCandidateVoteState`.
4. `updateTargetVoteTally` sets `ptvtTotalStake = 0 + s`.
5. `votesReachQuorum` calls `stakeAboveThreshold cfg (PerasVoteStake s)`.
6. Since `s` (e.g., `1_000_000`) ≥ `quorumThreshold` (e.g., `0.75`) + `safetyMargin`, the check passes.
7. `forgePerasCert` produces a `ValidatedPerasCert` boosting block `B` by `perasWeight`.
8. The certificate is committed to the `PerasVoteDB` and forwarded to `ChainDB`, which now weights `B`'s chain higher than the honest chain tip, causing the node to switch to the attacker-chosen fork. [7](#0-6) [8](#0-7)

updateCandidateVoteState cfg vote oldState =
