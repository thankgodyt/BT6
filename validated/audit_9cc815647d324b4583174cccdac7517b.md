In `internal_request_refund`, the wrong txid is computed and passed directly to the light client: [4](#0-3)

### Title
Hardcoded `BranchId::Nu6_2` in `Transaction::decode` permanently locks pre-Nu6.2 Zcash deposits — (`contracts/satoshi-bridge/src/zcash_utils/transaction.rs`)

### Summary
`Transaction::decode` unconditionally uses `BranchId::Nu6_2` when parsing any Zcash transaction, ignoring the `_chain` parameter. Because the Zcash v5 txid (ZIP-244) commits to `nConsensusBranchId`, any transaction mined under `Nu6` or `Nu6_1` consensus rules will have a different on-chain txid than the one the contract computes. Both `request_refund` and `verify_deposit` pass this wrong txid to the light client, which rejects it. The result is that any ZEC deposited before Nu6.2 activation (mainnet block 3,364,600) is permanently unrecoverable.

### Finding Description
`Transaction::decode` (line 53) hardcodes `BranchId::Nu6_2` regardless of the chain or the actual consensus rules under which the transaction was mined. For a v5 Zcash transaction mined under `Nu6_1` (blocks 3,146,400–3,364,599 on mainnet), the real on-chain txid was computed with `nConsensusBranchId = Nu6_1`. The contract recomputes the txid with `Nu6_2`, producing a different 32-byte hash. This wrong txid is submitted to `verify_transaction_inclusion`; the merkle proof (which is for the real txid) does not match, so the light client returns false and the call reverts. Neither `request_refund` nor `verify_deposit` can succeed for such transactions.

### Impact Explanation
Any user who deposited ZEC to the bridge before Nu6.2 activation has their funds permanently locked: the deposit cannot be credited (nZEC never minted) and a refund cannot be requested. There is no operator path to recover these funds because the on-chain state never records the deposit or refund request. This is a permanent, irrecoverable loss of user ZEC — Critical impact under "permanent locking of user or protocol funds."

### Likelihood Explanation
The bridge supports `ZcashMainnet` and `ZcashTestnet`. Nu6.2 activated on mainnet at block 3,364,600. Any deposit made before that block (or before testnet block 4,052,000) is affected. The bug is present in every code path that decodes a user-supplied transaction (`request_refund`, `verify_deposit`, `refund_execution_inputs`). No privileged role is required; any user with a pre-Nu6.2 deposit is affected.

### Recommendation
Replace the hardcoded `BranchId::Nu6_2` in `Transaction::decode` with a branch-ID lookup that uses the block height at which the transaction was mined (passed alongside `tx_bytes`) or, at minimum, use `chain.get_branch_id(block_height)` consistently. The `get_branch_id` helper already exists in `network.rs` and is used correctly in `PsbtWrapper::new`; it must also be applied in `Transaction::decode`.

### Proof of Concept
1. On Zcash mainnet, mine a deposit transaction at block 3,200,000 (Nu6_1 era). Its real txid is `H(Nu6_1, ...)`.
2. Call `request_refund` with `tx_bytes` of that transaction and a valid merkle proof for `H(Nu6_1, ...)`.
3. The contract calls `Transaction::decode` → computes txid as `H(Nu6_2, ...)` ≠ `H(Nu6_1, ...)`.
4. `verify_transaction_inclusion` is called with `H(Nu6_2, ...)` and the merkle proof for `H(Nu6_1, ...)`.
5. Light client returns false → `request_refund_callback` panics → no refund request stored.
6. Repeat for `verify_deposit` → same failure.
7. User's ZEC is permanently locked with no recovery path.
