### Title
Stub `validatePerasCert` Unconditionally Accepts Any Peras Certificate Without Cryptographic Verification, Enabling Unauthorized Chain-Selection Weight Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance ships a production-active `validatePerasCert` implementation that unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or structural checks. Because Peras certificates directly influence chain-selection weights via `addPerasCertAsync`, any unprivileged peer connected to the node can inject arbitrary certificates that boost attacker-chosen blocks, causing the honest node to prefer a non-canonical chain.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub:**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This is the **only** `BlockSupportsPeras` instance in the repository — a blanket instance over all `StandardHash blk` — so it is the production implementation for every block type including Cardano blocks. [2](#0-1) 

**Attacker-controlled entry path:**

1. A peer connects via the node-to-node Peras cert diffusion mini-protocol (`hPerasCertDiffusionClient` / `hPerasCertDiffusionServer`). [3](#0-2) 

2. Inbound certificates are processed by the `ObjectPoolWriter` for Peras certs (analogous to `makePerasVotePoolWriterFromChainDB` for votes), which calls `validatePerasCert` as the sole gatekeeper. [4](#0-3) 

3. Because `validatePerasCert` always returns `Right`, the crafted certificate is wrapped in `ValidatedPerasCert` and forwarded to `addPerasCertAsync`. [5](#0-4) 

4. `addPerasCertAsync` enqueues the certificate into the `ChainSelQueue`, which is processed by `chainSelSync`. The certificate is stored in `PerasCertDB`, updating the `PerasWeightSnapshot`. [6](#0-5) 

5. Chain selection reads `getPerasWeightSnapshot` and uses the injected weight boost when comparing candidate chains via `compareCandidateChains`. [7](#0-6) 

**Secondary amplifier — `validatePerasVote` also skips signature verification:**

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
``` [8](#0-7) 

A vote is accepted if the claimed voter ID appears in the stake distribution — no BLS signature over the round number and boosted block is checked. An attacker who knows any registered pool ID can forge votes for that pool, accumulate a quorum, and trigger `forgePerasCert` (which is also a stub returning `Right`), producing a `ValidatedPerasCert` that boosts an adversarial block. [9](#0-8) 

---

### Impact Explanation

**Impact: High — chain-selection manipulation by an unprivileged peer.**

A connected peer with no keys or credentials can:

1. Craft a `PerasCert` naming any `pcCertBoostedBlock` (an adversarial fork tip) and any `pcCertRound`.
2. Submit it via the Peras cert diffusion protocol.
3. The node accepts it unconditionally, stores it in `PerasCertDB`, and updates `PerasWeightSnapshot` to assign a `perasWeight` boost to the adversarial block.
4. On the next chain-selection run, `compareCandidateChains` sees the boosted adversarial fork as heavier than the honest chain and switches to it.

This satisfies the "High" impact criterion: *chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.*

---

### Likelihood Explanation

**Likelihood: Medium.**

- The Peras cert diffusion mini-protocol handlers are wired into the production `NodeToNode.Handlers` record and are active whenever the node runs with Peras support compiled in.
- The attacker needs only a standard peer connection — no keys, no stake, no privileged access.
- Pool IDs are public on-chain, so forging votes for any registered pool requires only knowledge of its ID (no private key needed given the missing signature check).
- The only limiting factor is whether Peras weight boosts are large enough relative to chain length to actually flip chain selection in a given deployment configuration.

---

### Recommendation

1. **Implement real cryptographic validation in `validatePerasCert`**: verify the aggregate BLS signature over the election ID and boosted block against the declared committee members' verification keys, and verify any VRF eligibility proofs. Remove the unconditional `Right` stub.

2. **Implement real signature verification in `validatePerasVote`**: call `verifyVoteSignature` (already defined in `CryptoSupportsVoteSigning`) to check the BLS signature over `(roundNo, boostedBlock)` before accepting a vote.

3. **Track issue #120** (`https://github.com/tweag/cardano-peras/issues/120`) as a security-critical blocker before enabling Peras cert/vote diffusion on any network where the weight boost can influence chain selection.

---

### Proof of Concept

**Deterministic reasoning (no mainnet required):**

```
Attacker (peer P) → node N:

1. P connects to N via the Peras cert diffusion protocol.

2. P sends PerasCert { pcCertRound = R, pcCertBoostedBlock = adversarialTip }
   where adversarialTip is the tip of a fork P controls.

3. Node N calls:
     validatePerasCert mkPerasParams cert
   which returns:
     Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })
   — no signature check, no committee membership check.

4. N calls addPerasCertAsync, enqueuing the cert into cdbChainSelQueue.

5. chainSelSync processes ChainSelAddPerasCert, stores cert in PerasCertDB,
   updates PerasWeightSnapshot to boost adversarialTip by perasWeight.

6. On next chain selection, compareCandidateChains sees:
     adversarialFork weight = length + perasWeight  >  honestFork weight = length
   and switches N's selection to the adversarial fork.
``` [1](#0-0) [6](#0-5) [10](#0-9)
