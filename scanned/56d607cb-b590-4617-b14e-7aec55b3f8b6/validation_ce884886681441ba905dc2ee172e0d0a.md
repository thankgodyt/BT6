### Title
Silent Discard of Cross-Chain Message in `BridgeToken::mint()` Causes Permanent Token Freezing — (File: `evm/src/omni-bridge/contracts/BridgeToken.sol`)

---

### Summary

`BridgeToken.mint(address, uint256, bytes)` accepts a `bytes` message payload but silently discards it, calling only `_mint(account, value)`. When a user bridges tokens from NEAR to EVM with a `message` field intended to trigger a DeFi callback on the recipient contract, the message is dropped and no callback is invoked. If the recipient is a contract that processes tokens exclusively via a callback hook, the bridged tokens are permanently frozen.

---

### Finding Description

`BridgeToken` exposes two `mint` overloads. The 3-argument variant has an unnamed, completely unused `bytes memory` parameter:

```solidity
function mint(
    address account,
    uint256 value,
    bytes memory          // ← unnamed, never read
) external virtual onlyOwner {
    _mint(account, value);
}
``` [1](#0-0) 

`OmniBridge.finTransfer()` explicitly branches on `payload.message.length` and calls the 3-arg overload when a message is present:

```solidity
} else if (isBridgeToken[payload.tokenAddress]) {
    if (payload.message.length == 0) {
        IBridgeToken(payload.tokenAddress).mint(payload.recipient, payload.amount);
    } else {
        IBridgeToken(payload.tokenAddress).mint(
            payload.recipient, payload.amount, payload.message   // message silently dropped
        );
    }
}
``` [2](#0-1) 

The branching logic implies the protocol intends the message to be acted upon when present, but `BridgeToken` never processes it. `HlBridgeToken` inherits the same defect in its override:

```solidity
function mint(address account, uint256 value, bytes memory) external override onlyOwner {
    _mint(account, value);
    _update(account, _systemAddress, value);
}
``` [3](#0-2) 

On the NEAR side, the `OmniToken.mint()` implementation correctly uses `ft_transfer_call` when a `msg` is present, notifying the recipient contract via the NEP-141 callback:

```rust
if let Some(msg) = msg {
    self.token.internal_deposit(&env::predecessor_account_id(), amount.into());
    self.ft_transfer_call(account_id, amount, None, msg)
} else {
    self.token.internal_deposit(&account_id, amount.into());
    PromiseOrValue::Value(amount)
}
``` [4](#0-3) 

The NEAR side correctly implements the safe/callback path; the EVM `BridgeToken` does not, creating an asymmetry that silently breaks cross-chain message delivery.

---

### Impact Explanation

The `message` field in the bridge protocol exists specifically to enable cross-chain DeFi integrations — e.g., a user bridges tokens to a yield vault and encodes deposit instructions in the message, expecting the vault's `onTokenReceived` (or equivalent) hook to be called. Because `BridgeToken.mint()` discards the message and calls only `_mint()`, no callback is ever triggered. If the recipient contract processes tokens exclusively via its callback and has no generic ERC20 rescue path, the bridged tokens are permanently frozen at that address. This satisfies the "permanent freezing of bridged funds" impact criterion.

---

### Likelihood Explanation

The `message` field is a first-class protocol feature, surfaced in `OmniBridge.finTransfer()` with explicit branching. Any user who bridges tokens to a contract recipient with a non-empty message — a common DeFi integration pattern — will silently lose the callback. The attacker-controlled entry path is fully unprivileged: a user initiates a transfer from NEAR with a `msg` field, a relayer submits the signed payload to `finTransfer()`, and the message is dropped. No admin compromise or special role is required.

---

### Recommendation

Implement a callback in `BridgeToken.mint(address, uint256, bytes)` that notifies the recipient when a message is present, analogous to ERC-777's `tokensReceived` hook or a custom `IERC20Receiver.onTokenReceived(address, uint256, bytes)` interface. At minimum, if a full callback mechanism is not desired, revert when `bytes.length > 0` rather than silently discarding the message, so users receive an explicit error instead of losing their callback silently.

---

### Proof of Concept

1. User initiates a transfer from NEAR to EVM with `msg = abi.encode(depositInstructions)`, targeting a DeFi vault at `vaultAddress`.
2. The NEAR bridge signs the `TransferMessagePayload` including the message.
3. A relayer calls `OmniBridge.finTransfer()` with `payload.recipient = vaultAddress` and `payload.message = depositInstructions`.
4. Because `payload.message.length > 0`, `IBridgeToken(tokenAddress).mint(vaultAddress, amount, depositInstructions)` is dispatched.
5. `BridgeToken.mint(vaultAddress, amount, depositInstructions)` executes `_mint(vaultAddress, amount)` and returns — `depositInstructions` is never read.
6. The vault's `onTokenReceived` hook is never called; the vault has no record of the deposit.
7. If the vault has no generic ERC20 sweep function, `amount` tokens are permanently frozen at `vaultAddress`.
