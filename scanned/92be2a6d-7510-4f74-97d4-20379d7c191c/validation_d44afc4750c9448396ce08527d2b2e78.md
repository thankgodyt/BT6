### Title
Normalization Dust Extracted by Trusted Relayer on Zero-Fee Transfers via `claim_fee_callback` - (File: near/omni-bridge/src/lib.rs)

### Summary
When a user initiates a NEAR→foreign transfer with `fee = 0` for a token whose NEAR decimals differ from the destination chain's decimals, a trusted relayer can call `claim_fee` to extract the normalization dust (the floor-division remainder) to themselves. The protocol comment explicitly states "When fee = 0, dust stays locked/burned," but the code does not enforce this invariant.

### Finding Description

`normalize_amount` uses floor division to scale amounts from NEAR's decimal precision to the destination chain's precision: [1](#0-0) 

The comment documents the intended invariant: when `fee = 0`, the truncated dust should remain locked or burned. However, `claim_fee_callback` computes the fee to send as: [2](#0-1) 

The computed `fee` is `transfer_message.amount - denormalize(fin_transfer.amount)`, which equals `amount mod scale` — the normalization dust — regardless of whether the user set `fee = 0`. This value is then passed to `send_fee_internal`, which sends it to `fee_recipient` whenever `token_fee > 0`: [3](#0-2) 

Critically, `sign_transfer` places no restriction on setting `fee_recipient` when the stored `transfer_message.fee.fee == 0`: [4](#0-3) 

The signed `TransferMessagePayload` carries `fee_recipient` into the EVM `FinTransfer` event, which the relayer then uses as proof in `claim_fee`.

**Attack path:**
1. User calls `ft_transfer_call` with `fee = 0` for a token with `origin_decimals = 24`, `dest_decimals = 6` (scale = 10^18).
2. Trusted relayer calls `sign_transfer(transfer_id, fee_recipient=Some(relayer), fee=None)` — no check prevents this when `fee = 0`.
3. Relayer submits `finTransfer` on EVM; EVM emits `FinTransfer` with `feeRecipient = relayer`.
4. Relayer calls `claim_fee` on NEAR with the EVM proof.
5. `claim_fee_callback` computes `fee = amount mod 10^18` (dust) and sends it to the relayer.

For a user transferring 1.9999999 NEAR to an EVM chain with 6 decimals, the dust is `0.9 NEAR` — a meaningful loss on a zero-fee transfer.

### Impact Explanation
Users lose normalization dust to the relayer even when they explicitly set `fee = 0`. For tokens with large decimal differences (e.g., NEAR 24 decimals → EVM 6 decimals, scale = 10^18), the dust per transfer can approach 1 NEAR. This is a direct balance mis-accounting: the user's locked/burned tokens are partially redirected to the relayer contrary to the documented protocol invariant and the user's intent.

### Likelihood Explanation
Requires a trusted relayer (DAO-approved role) to actively set `fee_recipient` and call `claim_fee` on zero-fee transfers. Only affects tokens with differing decimals across chains. Likelihood is medium given that trusted relayers are the primary bridge operators and decimal mismatches are common (NEAR 24 decimals vs EVM 18 or 6 decimals).

### Recommendation
In `claim_fee_callback`, check whether the stored `transfer_message.fee.fee` is zero before sending the computed dust. If the user-specified fee is zero, the dust should not be forwarded to the fee recipient:

```rust
// Only send token fee if the user actually set a non-zero fee
let token_fee = if transfer_message.fee.fee.0 > 0 {
    transfer_message.amount.0 - denormalized_amount
} else {
    0
};
self.send_fee_internal(&transfer_message, fee_recipient, token_fee)
```

Alternatively, enforce in `sign_transfer` that `fee_recipient` must be `None` when `transfer_message.fee.is_zero()`.

### Proof of Concept

Given:
- Token: NEAR-native, `origin_decimals = 24`, `dest_decimals = 6`, scale = 10^18
- User transfer: `amount = 1_999_999_900_000_000_000_000_000` yoctoNEAR, `fee = 0`

Step 1 — `sign_transfer` normalizes:
```
amount_to_transfer = 1_999_999_900_000_000_000_000_000 / 10^18 = 1_999_999
```

Step 2 — EVM `finTransfer` emits `FinTransfer(amount=1_999_999, feeRecipient=relayer)`.

Step 3 — `claim_fee_callback`:
```
denormalized_amount = 1_999_999 * 10^18 = 1_999_999_000_000_000_000_000_000
fee = 1_999_999_900_000_000_000_000_000 - 1_999_999_000_000_000_000_000_000
    = 900_000_000_000_000_000  // 0.9 NEAR
```

`send_fee_internal` sends 0.9 NEAR to the relayer. The user set `fee = 0` but loses 0.9 NEAR. [1](#0-0) [5](#0-4) [6](#0-5)

        &mut self,
        transfer_id: TransferId,
        fee_recipient: Option<AccountId>,

        let transfer_message = self.get_transfer_message(transfer_id);

        if let Some(fee) = &fee {
            require!(

                BridgeError::InvalidFee.as_ref()
            );
        }

        let token_address = self
            .get_token_address(
                transfer_message.get_destination_chain(),
                self.get_token_id(&transfer_message.token),

            .unwrap_or_else(|| {
                env::panic_str(BridgeError::FailedToGetTokenAddress.to_string().as_str())
            });

        let decimals = self
            .token_decimals
            .get(&token_address)
            .near_expect(BridgeError::TokenDecimalsNotFound);
        let amount_to_transfer = Self::normalize_amount(
            transfer_message
                .amount_without_fee()
                .near_expect(BridgeError::InvalidFee),
            decimals,

            BridgeError::InvalidAmountToTransfer.as_ref()

            transfer_id,
            token_address,
            amount: U128(amount_to_transfer),
            recipient: transfer_message.recipient,
            fee_recipient,
            message,
        };

    /// Uses floor division — any sub-unit remainder ("dust") is truncated and not transferred
    /// to the destination chain. When fee > 0, dust is absorbed into the fee via `claim_fee`.
    /// When fee = 0, dust stays locked/burned. See SECURITY.md for details.
    fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
        let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
        amount / (10_u128.pow(diff_decimals))
    }
