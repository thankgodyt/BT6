### Title
Trusted Relayer Can Sign the Same Transfer Multiple Times with Distinct `fee_recipient` Values, Enabling Unauthorized Fee Diversion — (`near/omni-bridge/src/lib.rs`)

---

### Summary

`sign_transfer` contains no idempotency guard. When a transfer has `fee > 0`, `sign_transfer_callback` deliberately leaves the transfer in `pending_transfers`. A trusted relayer can therefore call `sign_transfer` an arbitrary number of times for the same `transfer_id`, each time supplying a different `fee_recipient`. Because `fee_recipient` is part of the Borsh-serialized, keccak-hashed payload that the MPC signs, each call produces a cryptographically distinct, fully valid signature. The relayer selects whichever signature routes the fee to an account they control and submits it to the destination chain.

---

### Finding Description

**Entry point — `sign_transfer`**

`sign_transfer` reads the pending transfer but never removes or locks it:

```rust
let transfer_message = self.get_transfer_message(transfer_id); // read-only
``` [1](#0-0) 

The only fee-related check is that the caller-supplied `fee` matches the stored fee amount — it says nothing about `fee_recipient`:

```rust
if let Some(fee) = &fee {
    require!(&transfer_message.fee == fee, BridgeError::InvalidFee.as_ref());
}
``` [2](#0-1) 

`fee_recipient` is taken verbatim from the caller and embedded in the signed payload:

```rust
let transfer_payload = TransferMessagePayload {
    ...
    fee_recipient,   // ← caller-controlled, unvalidated
    ...
};
let payload = near_sdk::env::keccak256_array(
    transfer_payload.encode_hashable()...
);
ext_signer::ext(self.mpc_signer.clone()).sign(SignRequest { payload, ... })
``` [3](#0-2) 

**Callback — conditional removal**

`sign_transfer_callback` only removes the transfer when the fee is zero:

```rust
if fee.is_zero() {
    self.remove_transfer_message(message_payload.transfer_id);
}
``` [4](#0-3) 

When `fee > 0` the transfer stays in `pending_transfers` indefinitely (until `claim_fee` is called), so the relayer can immediately call `sign_transfer` again with a different `fee_recipient`.

**`fee_recipient` is part of the signed hash**

`TransferMessagePayload.encode_hashable()` serializes the full struct, including `fee_recipient`:

```rust
pub struct TransferMessagePayload {
    pub prefix: PayloadType,
    pub destination_nonce: Nonce,
    pub transfer_id: TransferId,
    pub token_address: OmniAddress,
    pub amount: U128,
    pub recipient: OmniAddress,
    pub fee_recipient: Option<AccountId>,   // ← in the hash
    pub message: Vec<u8>,
}
``` [5](#0-4) 

Two calls with different `fee_recipient` values produce two different 32-byte payloads and therefore two independent, valid MPC signatures.

**Fee claim path confirms the impact**

`claim_fee_callback` on NEAR reads `fee_recipient` from the destination-chain proof and sends the fee to that account:

```rust
let fee_recipient = fin_transfer.fee_recipient.unwrap_or_else(|| { ... });
require!(fee_recipient == *predecessor_account_id, ...);
...
self.send_fee_internal(&transfer_message, fee_recipient, fee)
``` [6](#0-5) 

The destination chain (EVM) encodes `feeRecipient` in the `FinTransfer` event that the NEAR prover later verifies:

```solidity
completedTransfers[payload.destinationNonce] = true;
// ...
emit FinTransfer(..., payload.feeRecipient);
``` [7](#0-6) 

The nonce prevents double-finalization on the destination chain, but the relayer freely chooses *which* of the two valid signatures to submit — and therefore which `fee_recipient` ends up in the on-chain event that NEAR's prover will later accept.

---

### Impact Explanation

A malicious trusted relayer can:

1. Call `sign_transfer(id, fee_recipient=attacker_account, fee=Some(fee))` → MPC produces `sig_B`.
2. Submit `sig_B` + payload to the destination chain → `FinTransfer` event records `feeRecipient = attacker_account`.
3. Call `claim_fee` on NEAR from `attacker_account` with the proof → NEAR sends the full fee to the attacker.

The principal amount (`amount - fee`) is unaffected, but the entire fee component of every pending transfer with `fee > 0` can be diverted. This is fee mis-accounting / unauthorized access to MPC signing capability for a payload the protocol did not intend to authorize.

---

### Likelihood Explanation

The attack requires only a single trusted relayer to act maliciously. The `#[trusted_relayer]` role is granted by `RelayerManager` / `DAO`, so the set of potential attackers is bounded but non-trivial in a live deployment. No additional privileges, leaked keys, or external collusion are needed.

---

### Recommendation

Add an "already-signed" guard. The simplest approach is to mark the transfer as signed in storage before dispatching to the MPC and reject any second call for the same `transfer_id`:

```rust
// In sign_transfer, before calling ext_signer:
require!(
    !self.signed_transfers.contains(&transfer_id),
    "Transfer already signed"
);
self.signed_transfers.insert(&transfer_id);
```

Alternatively, store the `fee_recipient` chosen at first signing inside the `TransferMessageStorage` and require subsequent calls to supply the identical value, or simply remove the transfer from `pending_transfers` immediately upon a successful signing (moving fee-claim state to a separate, smaller record).

---

### Proof of Concept

```
// localnet / sandbox test (no mainnet interaction)
1. Deploy bridge; register token; fund user; grant relayer role to `relayer.test`.
2. User calls ft_transfer_call → init_transfer with fee = 100, amount = 1000.
   → transfer_id T is inserted into pending_transfers.
3. relayer.test calls sign_transfer(T, fee_recipient="legitimate.near", fee=Some(100))
   → MPC signs payload_A; sign_transfer_callback fires; fee != 0 → transfer NOT removed.
4. relayer.test calls sign_transfer(T, fee_recipient="attacker.near", fee=Some(100))
   → MPC signs payload_B; sign_transfer_callback fires again; transfer still NOT removed.
5. Assert: two distinct SignTransferEvent logs were emitted, each with a different
   fee_recipient in the payload.
6. Submit payload_B + sig_B to destination chain → FinTransfer event with
   feeRecipient="attacker.near".
7. attacker.near calls claim_fee on NEAR with proof of step 6 → fee (100 tokens)
   transferred to attacker.near.
```

pub struct TransferMessagePayload {

    pub transfer_id: TransferId,
    pub token_address: OmniAddress,
    pub amount: U128,

impl TransferMessagePayload {
    pub fn encode_hashable(&self) -> Result<Vec<u8>, String> {
        if self.message.is_empty() {
            borsh::to_vec(&TransferMessagePayloadV1::from(self.clone())).map_err(stringify)
        } else {
            borsh::to_vec(self).map_err(stringify)
        }
    }
