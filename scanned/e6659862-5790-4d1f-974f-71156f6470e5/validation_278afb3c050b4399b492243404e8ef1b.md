### Title
Missing Pause Check in `finish_withdraw_v2` Allows Transfer Initiation During Emergency Pause - (File: `near/omni-bridge/src/lib.rs`)

---

### Summary
The NEAR omni-bridge contract's `finish_withdraw_v2` function lacks a pause guard, allowing any deployed bridge token contract — and by extension any user who can trigger it — to initiate new cross-chain transfers to Ethereum even when the bridge is in an emergency-paused state.

---

### Finding Description

The NEAR omni-bridge contract derives `Pausable` and applies pause guards to every transfer-initiating public function:

- `ft_on_transfer` — `#[pause(except(roles(Role::DAO, Role::UnrestrictedDeposit)))]`
- `sign_transfer` — `#[pause(except(roles(Role::DAO)))]`
- `fin_transfer` — `#[pause(except(roles(Role::DAO)))]`
- `claim_fee` — `#[pause(except(roles(Role::DAO)))]`
- `deploy_token` — `#[pause(except(roles(Role::DAO)))]`
- `bind_token` — `#[pause(except(roles(Role::DAO)))]` [1](#0-0) [2](#0-1) [3](#0-2) 

However, `finish_withdraw_v2` — a public, non-`#[private]` function — carries **no pause attribute**: [4](#0-3) 

The function:
1. Accepts any caller whose `predecessor_account_id()` is a registered deployed token (`require!(self.is_deployed_token(&token_id))`).
2. Increments `current_origin_nonce` and `destination_nonces` for `ChainKind::Eth`.
3. Constructs and stores a full `TransferMessage` via `add_transfer_message`.
4. Emits `OmniBridgeEvent::InitTransferEvent`, which relayers observe to trigger `sign_transfer`. [5](#0-4) 

This is the legacy withdrawal path used by old bridge token factory contracts (registered as deployed tokens). A user holding tokens in such a factory can call its `withdraw` function, which cross-contract-calls `finish_withdraw_v2` on the bridge, bypassing the pause entirely.

---

### Impact Explanation

During an emergency pause, an attacker can:

1. Call `withdraw` on any deployed bridge token factory contract.
2. That contract calls `finish_withdraw_v2` on the bridge — no pause check fires.
3. A new `TransferMessage` is persisted in `pending_transfers`, nonces are incremented, and `InitTransferEvent` is emitted.

When the bridge is unpaused, relayers will process the queued `InitTransferEvent` and call `sign_transfer`, completing the transfer to Ethereum. If the bridge was paused precisely because a vulnerability in the transfer path was discovered, these pre-queued transfers can exploit that vulnerability the moment the bridge resumes. Additionally, the bridge's own account is charged storage for each pending transfer (`update_storage_balance(env::current_account_id(), ...)`), enabling storage drain. [6](#0-5) 

---

### Likelihood Explanation

`finish_withdraw_v2` is a public function with no access control beyond requiring the predecessor to be a registered deployed token. Old bridge token factory contracts — which are registered in `deployed_tokens` — expose user-facing withdrawal functions that cross-contract-call `finish_withdraw_v2`. Any user holding tokens in such a factory can trigger this path without any special privilege. The bridge's pause mechanism is therefore bypassable by any ordinary token holder.

---

### Recommendation

Add `#[pause(except(roles(Role::DAO)))]` to `finish_withdraw_v2`, consistent with every other transfer-initiating function in the contract:

```rust
#[pause(except(roles(Role::DAO)))]
pub fn finish_withdraw_v2(
    &mut self,
    #[serializer(borsh)] sender_id: &AccountId,
    #[serializer(borsh)] amount: u128,
    #[serializer(borsh)] recipient: String,
) { ... }
``` [7](#0-6) 

---

### Proof of Concept

1. Admin calls `pa_pause_feature` (or equivalent) to pause the bridge due to a discovered vulnerability.
2. User holds tokens in a deployed bridge token factory (registered in `deployed_tokens`).
3. User calls `withdraw(amount, eth_recipient)` on the token factory.
4. Token factory cross-contract-calls `finish_withdraw_v2(&user, amount, eth_recipient)` on the bridge.
5. Bridge executes without any pause check: nonces increment, `TransferMessage` is stored, `InitTransferEvent` is emitted.
6. Relayer observes the event and, once the bridge is unpaused, calls `sign_transfer` — completing the transfer to Ethereum and potentially exploiting the vulnerability that triggered the pause.

```rust
    #[allow(clippy::needless_pass_by_value)]
    pub fn finish_withdraw_v2(
        &mut self,
        #[serializer(borsh)] sender_id: &AccountId,
        #[serializer(borsh)] amount: u128,
        #[serializer(borsh)] recipient: String,
    ) {
        let token_id = env::predecessor_account_id();
        require!(self.is_deployed_token(&token_id),);

        self.current_origin_nonce += 1;
        let destination_nonce = self.get_next_destination_nonce(ChainKind::Eth);

        let transfer_message = TransferMessage {
            origin_nonce: self.current_origin_nonce,
            token: OmniAddress::Near(token_id),
            amount: U128(amount),
            recipient: OmniAddress::Eth(
                H160::from_str(&recipient).near_expect(BridgeError::InvalidRecipientAddress),
            ),
            fee: Fee {
                fee: U128(0),
                native_fee: U128(0),
            },
            sender: OmniAddress::Near(sender_id.clone()),
            msg: String::new(),
            destination_nonce,
            origin_transfer_id: None,
        };

        let required_storage_balance =
            self.add_transfer_message(transfer_message.clone(), sender_id.clone());

        self.update_storage_balance(
            env::current_account_id(),
            required_storage_balance,
            NearToken::from_yoctonear(0),
        );

        env::log_str(&OmniBridgeEvent::InitTransferEvent { transfer_message }.to_log_string());
    }
