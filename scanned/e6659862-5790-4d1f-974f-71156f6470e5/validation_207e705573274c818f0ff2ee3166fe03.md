### Title
Pending Transfers Permanently Frozen After `migrate_deployed_token` Removes Old Token Address Binding — (File: `near/omni-bridge/src/lib.rs`)

---

### Summary

`migrate_deployed_token` removes the old token's entry from `token_id_to_address` without handling in-flight pending transfers that still reference the old token ID. Any transfer initiated before migration is permanently uncompletable: the user's tokens are already burned or locked, but `sign_transfer` and `claim_fee_callback` both panic when they cannot resolve the old token's address. There is no cancel or refund path for pending transfers.

---

### Finding Description

**Step 1 — Token address binding at transfer initiation.**

When a user calls `ft_transfer_call` with an `InitTransfer` message, `init_transfer_internal` burns or locks the tokens and stores the transfer message with `token: OmniAddress::Near(old_token)`: [1](#0-0) 

The `TransferMessage` is persisted in `pending_transfers` keyed by `TransferId`. The token field is permanently bound to the NEAR account ID at the time of initiation.

**Step 2 — Migration removes the old binding.**

`migrate_deployed_token` (DAO-only) removes `(origin_chain, old_token)` from `token_id_to_address` and inserts `(origin_chain, new_token)`: [2](#0-1) 

After this call, `get_token_address(destination_chain, old_token)` returns `None` for any chain.

**Step 3 — `sign_transfer` panics on the orphaned transfer.**

`sign_transfer` resolves the token address from the stored transfer message: [3](#0-2) 

`get_token_id(&OmniAddress::Near(old_token))` returns `old_token` (Near variant is returned directly). Then `get_token_address(destination_chain, old_token)` returns `None` because the mapping was deleted. The `unwrap_or_else` branch calls `env::panic_str`. The transfer is permanently stuck.

**Step 4 — `claim_fee_callback` has the identical failure.** [4](#0-3) 

Same lookup, same panic, same outcome.

**Step 5 — No recovery path exists.**

`remove_transfer_message` is only called internally after a successful signing or fee claim. There is no public cancel or refund function. The burned tokens are gone; locked native tokens remain in the bridge contract with no retrieval mechanism. [5](#0-4) 

---

### Impact Explanation

Any user who initiated a transfer of `old_token` before the DAO migration suffers **permanent, irrecoverable loss of bridged funds**:

- For deployed (bridged) tokens: tokens are burned on NEAR at initiation; the corresponding foreign-chain tokens are never released.
- For native NEAR tokens: tokens are locked in the bridge contract with no retrieval path.

This matches the allowed impact scope: *permanent freezing of bridged funds* and *escrow mis-accounting that changes user balances*.

---

### Likelihood Explanation

Token migrations are an expected operational event (the codebase explicitly implements `migrate_deployed_token` and `swap_migrated_token`). Pending transfers are a normal bridge state — transfers can remain pending for minutes to hours while waiting for relayer action. The probability that at least one pending transfer exists at the moment of any migration is high. No attacker action is required; the DAO executing a routine migration is sufficient to trigger the loss.

---

### Recommendation

1. **Before migration**: enumerate and reject (or complete) all pending transfers for `old_token` before calling `migrate_deployed_token`, or add an on-chain check that `pending_transfers` contains no entries for `old_token`.
2. **Rewrite pending transfers**: in `migrate_deployed_token`, iterate over pending transfers referencing `old_token` and rewrite their `token` field to `new_token` (or provide a separate admin function to do so).
3. **Add a user-facing cancel/refund**: allow the original sender to cancel a pending transfer and receive a refund of locked tokens (or a mint of burned tokens), guarded by a time-lock or DAO approval.

---

### Proof of Concept

```
1. Alice calls ft_transfer_call(bridge_contract, 1000, msg=InitTransfer{recipient: Eth(0xAlice)})
   → old_token.burn(1000) executes
   → pending_transfers[{Eth, nonce=42}] = TransferMessage { token: Near(old_token), amount: 1000, ... }

2. DAO calls migrate_deployed_token(Eth, old_token, new_token)
   → token_id_to_address.remove(&(Eth, old_token))   // binding deleted
   → token_id_to_address.insert(&(Eth, new_token), &eth_address)

3. Relayer calls sign_transfer({Eth, 42}, fee_recipient=relayer, fee=None)
   → get_token_id(&Near(old_token)) = old_token
   → get_token_address(Eth, old_token) = None          // mapping gone
   → env::panic_str("FailedToGetTokenAddress")         // transfer permanently stuck

4. Alice's 1000 old_token are burned. No new_token is minted. No ETH-side release occurs.
   Alice has no recourse.
```

    fn remove_transfer_message(&mut self, transfer_id: TransferId) -> TransferMessage {
        let storage_usage = env::storage_usage();
        let transfer = self
            .pending_transfers
            .remove(&transfer_id)
            .map(storage::TransferMessageStorage::into_main)
            .near_expect(BridgeError::TransferNotExist);

        let refund =
            env::storage_byte_cost().saturating_mul((storage_usage - env::storage_usage()).into());

        if let Some(mut storage) = self.accounts_balances.get(&transfer.owner) {
            storage.available = storage.available.saturating_add(refund);
            self.accounts_balances.insert(&transfer.owner, &storage);
        }

        transfer.message
    }
