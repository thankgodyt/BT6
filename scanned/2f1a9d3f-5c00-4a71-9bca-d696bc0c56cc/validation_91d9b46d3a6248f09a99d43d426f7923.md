### Title
Native ETH (`nativeFee`) Permanently Locked in `OmniBridge` With No Rescue Mechanism - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

### Summary

`OmniBridge.sol` accepts native ETH as a `nativeFee` payment in every `initTransfer` and `initTransfer1155` call, but provides no function to withdraw or rescue that ETH. The contract also exposes a bare `receive() external payable {}` that silently accepts arbitrary ETH. There is no admin withdrawal, no `rescueETH`, and no accounting separation between bridged ETH and fee ETH. All `nativeFee` ETH paid by users is permanently frozen in the contract.

### Finding Description

`initTransfer` is `external payable`. When `tokenAddress == address(0)` (native ETH bridge), the caller must send `msg.value = amount + nativeFee`. When `tokenAddress != address(0)` (ERC20 bridge), the caller must send `msg.value = nativeFee`. In both cases the `nativeFee` portion is subtracted from `msg.value` to compute `extensionValue`, which is passed to `initTransferExtension`. The `nativeFee` itself is never forwarded anywhere — it stays in the contract's ETH balance. [1](#0-0) 

In the base `OmniBridge`, `initTransferExtension` only checks that `extensionValue == 0` and reverts otherwise — it does nothing with `nativeFee`. [2](#0-1) 

In `OmniBridgeWormhole`, `initTransferExtension` passes `value` (= `extensionValue`, not `nativeFee`) to Wormhole. The `nativeFee` portion is still left in the contract. [3](#0-2) 

The contract also has a bare `receive()` that silently accepts any ETH sent directly to it. [4](#0-3) 

A full audit of all functions in `OmniBridge.sol` confirms there is no `withdrawETH`, `rescueETH`, or any admin function that transfers ETH out of the contract. [5](#0-4) 

### Impact Explanation

Every user who calls `initTransfer` or `initTransfer1155` with `nativeFee > 0` permanently loses that ETH. The fee is never forwarded to the relayer on the EVM side (relayers are compensated on NEAR), so the ETH accumulates in the contract with no path out. Over time, all `nativeFee` ETH paid across all bridge users is frozen. Additionally, any ETH sent directly to the contract via `receive()` is also irrecoverable. This constitutes permanent freezing of user funds and permanent loss of protocol fee revenue — matching the "permanent freezing of bridged funds / fee mis-accounting" impact class.

### Likelihood Explanation

The likelihood is high. Every EVM-side bridge transfer that specifies a non-zero `nativeFee` (which is the normal case for incentivizing relayers) triggers this loss. The README explicitly documents that transfers require a fee payable in the native chain token (ETH), making this a routine code path exercised by every paying user. [6](#0-5) 

### Recommendation

Add an admin-gated ETH rescue function, for example:

```solidity
function rescueETH(address payable recipient, uint256 amount)
    external
    onlyRole(DEFAULT_ADMIN_ROLE)
{
    (bool success, ) = recipient.call{value: amount}("");
    require(success, "ETH rescue failed");
}
```

Alternatively, track bridged ETH separately from fee ETH and enforce that only the fee portion is withdrawable.

### Proof of Concept

1. Deploy `OmniBridge` (or `OmniBridgeWormhole`) on a testnet.
2. Call `initTransfer(erc20Token, 1000, 0, 1e17, "recipient.near", "")` with `msg.value = 1e17` (0.1 ETH as `nativeFee`).
3. Observe that `address(OmniBridge).balance` increases by `1e17`.
4. Attempt to call any function to withdraw that ETH — none exists.
5. The 0.1 ETH is permanently locked. Repeat for every user transfer with `nativeFee > 0`. [7](#0-6)
