### Title
Fee-on-Transfer Token Escrow Mis-Accounting in `initTransfer` — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

`OmniBridge.initTransfer` accepts a caller-supplied `amount` parameter, passes it directly to `safeTransferFrom`, and then emits that same `amount` in the `InitTransfer` event without verifying the actual tokens received. For fee-on-transfer ERC-20 tokens the bridge locks fewer tokens than the event declares, causing the NEAR side to mint more tokens than the bridge holds, permanently undercollateralising the escrow.

---

### Finding Description

In `initTransfer`, the non-bridge, non-custom-minter token path is:

```solidity
IERC20(tokenAddress).safeTransferFrom(
    msg.sender,
    address(this),
    amount          // caller-supplied, not verified against actual receipt
);
```

followed immediately by:

```solidity
emit BridgeTypes.InitTransfer(
    msg.sender,
    tokenAddress,
    currentOriginNonce,
    amount,          // same caller-supplied value, not actual received amount
    fee,
    nativeFee,
    recipient,
    message
);
``` [1](#0-0) [2](#0-1) 

No balance-before / balance-after check is performed. For a fee-on-transfer token (e.g. PAXG, STA, or any token whose `transfer`/`transferFrom` silently deducts a fee), the bridge receives `amount − fee_on_transfer` tokens but the `InitTransfer` event records `amount`.

The NEAR `omni-bridge` contract treats every emitted `InitTransfer` event as authoritative proof that the declared amount is held in escrow — this is an explicit protocol invariant:

> *"Event–transfer atomicity: `InitTransfer` must only be emitted in a code path where tokens have already been burned/locked in the same transaction … the NEAR side will treat any emitted event as proof that tokens are held."* [3](#0-2) 

Consequently, NEAR mints or unlocks `amount` tokens for the user while the bridge only holds `amount − fee_on_transfer`. The bridge's ERC-20 balance is permanently short by `fee_on_transfer` per such transfer.

---

### Impact Explanation

Every fee-on-transfer token bridged via `initTransfer` inflates the NEAR-side supply relative to the EVM-side escrow. After enough such transfers the bridge becomes insolvent: later users who bridge back to EVM cannot withdraw because the bridge's token balance is insufficient. This constitutes permanent loss of bridged funds for honest users — a critical escrow mis-accounting impact.

---

### Likelihood Explanation

`initTransfer` is a public, permissionless function. No allowlist restricts which ERC-20 tokens may be passed as `tokenAddress`. Fee-on-transfer tokens are deployed on mainnet today (PAXG charges a 0.02 % fee; STA, USDT on some configurations, and others). Any user — including an attacker who deliberately bridges a fee-on-transfer token — can trigger the discrepancy. No admin action or special privilege is required.

---

### Recommendation

Replace the fixed-`amount` transfer with a balance-before / balance-after pattern to compute the actual received amount, and use that value in the event:

```solidity
uint256 balanceBefore = IERC20(tokenAddress).balanceOf(address(this));
IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
uint256 received = IERC20(tokenAddress).balanceOf(address(this)) - balanceBefore;
require(received > 0, "ZeroReceived");
// use `received` (cast to uint128) in the event and downstream logic
```

This is the same class of fix applied to the Linea `TokenBridge` in the referenced report. Alternatively, maintain an explicit allowlist of supported tokens and reject any token whose `balanceOf` delta does not equal `amount`.

---

### Proof of Concept

1. Deploy or identify a mainnet ERC-20 token with a 1 % fee-on-transfer (e.g. a fork of STA).
2. Approve the `OmniBridge` for `1000` tokens.
3. Call `OmniBridge.initTransfer(tokenAddress, 1000, 0, 0, "attacker.near", "")`.
4. `safeTransferFrom` executes; the bridge receives `990` tokens (1 % fee deducted by the token).
5. The `InitTransfer` event is emitted with `amount = 1000`.
6. The NEAR relayer reads the event and mints `1000` omni-tokens to `attacker.near`.
7. The attacker now holds `1000` NEAR-side tokens backed by only `990` EVM-side tokens.
8. Repeating this drains the bridge's real ERC-20 reserve while inflating NEAR-side supply, eventually preventing honest users from withdrawing their funds. [4](#0-3)

        currentOriginNonce += 1;
        if (fee >= amount) {
            revert InvalidFee();

            if (fee != 0) {
                revert InvalidFee();

            extensionValue = msg.value - amount - nativeFee;

            extensionValue = msg.value - nativeFee;
            if (customMinters[tokenAddress] != address(0)) {
