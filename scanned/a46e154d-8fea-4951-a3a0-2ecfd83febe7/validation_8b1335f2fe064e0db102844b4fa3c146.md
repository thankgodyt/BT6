### Title
Excess ETH Forwarded to Wormhole `publishMessage` Without Fee Validation Is Permanently Lost - (File: evm/src/omni-bridge/contracts/OmniBridgeWormhole.sol)

### Summary
`OmniBridgeWormhole.sol` forwards `msg.value` (or a derived value) directly to `_wormhole.publishMessage` in multiple extension hooks without first validating that the amount equals `_wormhole.messageFee()`. Because Wormhole's `publishMessage` does not refund excess ETH, any overpayment is permanently lost to the caller.

### Finding Description

In `OmniBridgeWormhole.sol`, three extension hooks blindly forward `msg.value` to Wormhole:

`finTransferExtension` (line 109): [1](#0-0) 

`deployTokenExtension` (line 63): [2](#0-1) 

`logMetadataExtension` (line 87): [3](#0-2) 

For `initTransferExtension`, the forwarded `value` is `msg.value - nativeFee` (ERC-20) or `msg.value - amount - nativeFee` (ETH), computed in the base contract: [4](#0-3) 

This `extensionValue` is then forwarded to Wormhole: [5](#0-4) 

The Wormhole interface exposes `messageFee()` to query the exact required fee: [6](#0-5) 

None of the four extension functions call `_wormhole.messageFee()` to validate the forwarded amount before the call. The Wormhole contract keeps any excess ETH and does not refund it, as confirmed by the test stub which enforces exact equality: [7](#0-6) 

The production Wormhole contract does **not** enforce exact equality — it accepts `>= messageFee()` and retains the surplus.

### Impact Explanation

Any caller of `finTransfer` or `initTransfer` (both `external payable`, no role restriction) who sends more ETH than `_wormhole.messageFee()` permanently loses the excess. This is fee mis-accounting that directly reduces user and relayer ETH balances with no recovery path. The Wormhole fee is also upgradeable and can change between the time a user queries it off-chain and the time the transaction executes, making accidental overpayment a realistic scenario.

### Likelihood Explanation

`finTransfer` and `initTransfer` are the primary public entry points for bridge users and relayers on Wormhole-connected chains. Callers must supply ETH for the Wormhole fee, but the contract provides no on-chain guard against overpayment. Fee changes in the Wormhole contract between query and execution create a realistic window for loss.

### Recommendation

Before forwarding ETH to `_wormhole.publishMessage`, validate the exact fee in each extension:

```solidity
function finTransferExtension(...) internal override {
    uint256 fee = _wormhole.messageFee();
    require(msg.value == fee, "InvalidWormholeFee");
    _wormhole.publishMessage{value: fee}(...);
}
```

Apply the same pattern to `deployTokenExtension`, `logMetadataExtension`, and `initTransferExtension` (comparing `value` against `_wormhole.messageFee()`).

### Proof of Concept

1. Deploy `OmniBridgeWormhole` pointing at a real Wormhole endpoint where `messageFee() == 0.001 ether`.
2. Call `finTransfer(signatureData, payload)` with `{value: 0.1 ether}`.
3. `finTransferExtension` executes `_wormhole.publishMessage{value: 0.1 ether}(...)`.
4. Wormhole deducts `0.001 ether` as its fee and retains the remaining `0.099 ether`.
5. The caller's balance is reduced by `0.1 ether`; only `0.001 ether` was required. The `0.099 ether` is permanently lost.
