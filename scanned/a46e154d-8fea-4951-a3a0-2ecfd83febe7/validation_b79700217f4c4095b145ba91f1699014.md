### Title
Blacklisted Recipient Permanently Freezes Bridged Funds in `finTransfer` - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

`OmniBridge.finTransfer()` uses a push-transfer pattern that directly calls `safeTransfer` (or `mint`) to `payload.recipient`. If that address is blacklisted by a token with an on-chain blocklist (e.g., USDC, USDT), every `finTransfer` attempt reverts. Because the EVM contract has no refund, cancel, or recipient-change mechanism, the source-chain tokens that were already locked or burned during `initTransfer` are permanently unrecoverable. The same root cause exists in the Starknet contract's `fin_transfer`.

---

### Finding Description

**EVM — `OmniBridge.finTransfer`**

The function marks the destination nonce as consumed at line 287, then unconditionally pushes tokens to `payload.recipient`:

```solidity
completedTransfers[payload.destinationNonce] = true;   // line 287
// ...
IERC20(payload.tokenAddress).safeTransfer(             // line 351-354
    payload.recipient,
    payload.amount
);
```

`SafeERC20.safeTransfer` propagates any revert from the token contract. USDC's `transfer` reverts when either the sender or receiver is blacklisted. Because Solidity reverts atomically, the nonce flag is also rolled back, so the call can be retried — but every retry will revert for the same reason. There is no `cancelTransfer`, `refund`, or `setRecipient` function anywhere in the EVM contract. [1](#0-0) 

The source-chain side of the transfer is already settled before `finTransfer` is ever called:
- **EVM → NEAR → EVM**: the origin EVM `initTransfer` either burns bridge tokens (`BridgeToken.burn`) or locks native ERC-20s inside the bridge contract via `safeTransferFrom`. Neither action is reversible from the EVM side. [2](#0-1) 

**Starknet — `omni_bridge.fin_transfer`**

The identical push pattern exists in Cairo:

```cairo
let success = IERC20Dispatcher { contract_address: payload.token_address }
    .transfer(payload.recipient, payload.amount.into());
assert(success, 'ERR_TRANSFER_FAILED');
```

A `false` return from a blacklist-enforcing token causes the `assert` to panic, reverting the whole transaction. No recovery path exists. [3](#0-2) 

---

### Impact Explanation

When a recipient EVM or Starknet address is blacklisted by the destination token:

1. Every `finTransfer` call reverts — the destination nonce is never durably consumed.
2. The source-chain tokens (locked in the EVM bridge or burned on NEAR) cannot be recovered because there is no refund or cancel path.
3. Bridged funds are **permanently frozen**: the user loses the full bridged amount.

This matches the allowed impact: *permanent freezing of bridged funds*. [4](#0-3) 

---

### Likelihood Explanation

- USDC (Circle) and USDT (Tether) both maintain on-chain blacklists and are primary bridge tokens.
- Blacklisting can happen due to regulatory action, sanctions compliance, or a malicious report — none of which require attacker capability beyond being a normal token holder.
- The recipient address is fixed at `initTransfer` time and is part of the MPC-signed payload; it cannot be changed after signing.
- A user whose address is blacklisted after initiating a transfer has no recourse. [5](#0-4) 

---

### Recommendation

1. **Pull pattern**: Instead of pushing tokens to `payload.recipient` inside `finTransfer`, store the claimable balance in a mapping (`claimable[recipient][token] += amount`) and add a separate `claim()` function. This decouples delivery failure from transfer finalization.

2. **Recipient override**: Allow the original sender (authenticated via the signed payload or a NEAR-side message) to designate an alternative withdrawal address before the destination-side claim is executed.

3. **Refund path**: If `finTransfer` fails to deliver to the recipient, emit a `FailedFinTransfer` event and allow the NEAR bridge to re-credit the sender — mirroring the existing `FailedFinTransferEvent` logic already present on the NEAR side. [6](#0-5) 

---

### Proof of Concept

**Setup**: User bridges 1,000 USDC from Ethereum to Ethereum (via NEAR hub). The recipient EVM address is subsequently blacklisted by Circle.

**Step 1 — `initTransfer` on source EVM** (succeeds, tokens locked):
```solidity
// User calls on source chain
OmniBridge.initTransfer(USDC, 1000e6, fee, nativeFee, "recipient.near", "");
// USDC.safeTransferFrom(user, bridge, 1000e6) — succeeds, tokens now in bridge
```

**Step 2 — NEAR hub processes proof** (succeeds, destination nonce assigned).

**Step 3 — Relayer calls `finTransfer` on destination EVM** (always reverts):
```solidity
// USDC.transfer(blacklistedRecipient, 1000e6) reverts
// → safeTransfer propagates revert
// → completedTransfers[nonce] = true is rolled back
// → call can be retried but will always revert
OmniBridge.finTransfer(sig, payload); // reverts: "ERC20: transfer to blacklisted address"
```

**Result**: 1,000 USDC is permanently locked in the source EVM bridge contract. No admin function, no cancel path, no refund mechanism exists to recover it. [7](#0-6) [8](#0-7)
