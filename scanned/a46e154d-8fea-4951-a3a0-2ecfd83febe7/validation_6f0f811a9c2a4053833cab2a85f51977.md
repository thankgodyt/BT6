### Title
Pause Bypass via `finish_withdraw_v2()` Allows Transfer Initiation During Emergency Stop - (File: `near/omni-bridge/src/lib.rs`)

### Summary
The `finish_withdraw_v2()` function in the NEAR omni-bridge contract lacks a pause guard. Every other transfer-initiating entry point enforces the pause check, but `finish_withdraw_v2` is omitted. Any legacy deployed token contract (whose account is in the `deployed_tokens` set) can call it on behalf of a user to create a pending `TransferMessage` and emit an `InitTransferEvent` while the bridge is in a paused/emergency state.

### Finding Description
The NEAR omni-bridge uses the `near-plugins` `Pausable` trait for an emergency stop. When paused, the following public functions are blocked for non-DAO callers via `#[pause]` or `#[pause(except(roles(Role::DAO)))]`:

- `ft_on_transfer` — primary transfer initiation path
- `fin_transfer`
- `sign_transfer`
- `claim_fee`
- `deploy_token`
- `bind_token`
- `log_metadata`
- `update_transfer_fee`

However, `finish_withdraw_v2()` carries **no** `#[pause]` attribute: [1](#0-0) 

It is a public function gated only by `require!(self.is_deployed_token(&token_id))`, meaning any account in the `deployed_tokens` / `deployed_tokens_v2` sets can call it. When invoked it:

1. Increments `current_origin_nonce` [2](#0-1) 
2. Constructs a full `TransferMessage` targeting `ChainKind::Eth` [3](#0-2) 
3. Stores it in `pending_transfers` via `add_transfer_message` [4](#0-3) 
4. Emits `InitTransferEvent` [5](#0-4) 

This is functionally identical to the `init_transfer` path that is correctly blocked through the paused `ft_on_transfer`. [6](#0-5) 

The contrast with every other guarded entry point is stark:

```rust
// ft_on_transfer — paused
#[pause(except(roles(Role::DAO, Role::UnrestrictedDeposit)))]
pub fn ft_on_transfer(...)

// fin_transfer — paused
#[pause(except(roles(Role::DAO)))]
pub fn fin_transfer(...)

// finish_withdraw_v2 — NO pause check
pub fn finish_withdraw_v2(...)   // ← missing guard
``` [6](#0-5) [7](#0-6) [8](#0-7) 

### Impact Explanation
When the bridge is paused in response to a security incident, a user holding legacy bridge tokens (whose token contract is in `deployed_tokens`) can still initiate a new outbound transfer to Ethereum. The legacy token contract burns the user's NEAR-side tokens and calls `finish_withdraw_v2`; the bridge stores the pending transfer. Once the bridge is unpaused, a relayer calls `sign_transfer` and the transfer completes on the EVM side. The user has successfully moved funds through a code path that the pause was intended to freeze, potentially exploiting whatever vulnerability triggered the pause in the first place.

### Likelihood Explanation
The `deployed_tokens` set contains legacy bridge tokens from the old `factory.bridge.near` / `factory.sepolia.testnet` infrastructure, which are still registered. [9](#0-8)  Any user holding such tokens can trigger their token contract's withdrawal function, which in turn calls `finish_withdraw_v2` on the bridge. No special role or privilege is required beyond holding legacy bridge tokens.

### Recommendation
Add the same pause guard used on every other transfer-initiating function:

```rust
#[pause(except(roles(Role::DAO)))]
pub fn finish_withdraw_v2(
    &mut self,
    #[serializer(borsh)] sender_id: &AccountId,
    #[serializer(borsh)] amount: u128,
    #[serializer(borsh)] recipient: String,
) { ... }
```

### Proof of Concept
1. `PauseManager` triggers a full pause on the NEAR bridge (all flags set).
2. `ft_on_transfer` is now blocked — the normal `init_transfer` path is frozen.
3. User holds legacy ETH bridge tokens (e.g., `eth-connector.bridge.near` or any account in `deployed_tokens`).
4. User calls the legacy token contract's `withdraw(recipient, amount)` function.
5. The legacy token contract burns the user's tokens and calls `finish_withdraw_v2` on the bridge with `sender_id`, `amount`, and `recipient`.
6. `finish_withdraw_v2` has no pause check: it increments `current_origin_nonce`, creates a `TransferMessage`, writes it to `pending_transfers`, and emits `InitTransferEvent`. [1](#0-0) 
7. A relayer observes the event. Once the bridge is unpaused, the relayer calls `sign_transfer` and the MPC network signs the payload.
8. The relayer submits `finTransfer` on the EVM bridge; the user receives tokens on Ethereum — having bypassed the emergency stop entirely.

    #[allow(clippy::needless_pass_by_value)]
    pub fn finish_withdraw_v2(
        &mut self,
        #[serializer(borsh)] sender_id: &AccountId,
        #[serializer(borsh)] amount: u128,
        #[serializer(borsh)] recipient: String,
    ) {
        let token_id = env::predecessor_account_id();
        require!(self.is_deployed_token(&token_id),);

        self.current_origin_nonce += 1;
        let destination_nonce = self.get_next_destination_nonce(ChainKind::Eth);

        let transfer_message = TransferMessage {
            origin_nonce: self.current_origin_nonce,
            token: OmniAddress::Near(token_id),
            amount: U128(amount),
            recipient: OmniAddress::Eth(
                H160::from_str(&recipient).near_expect(BridgeError::InvalidRecipientAddress),
            ),
            fee: Fee {
                fee: U128(0),
                native_fee: U128(0),
            },
            sender: OmniAddress::Near(sender_id.clone()),
            msg: String::new(),
            destination_nonce,
            origin_transfer_id: None,
        };

        let required_storage_balance =
            self.add_transfer_message(transfer_message.clone(), sender_id.clone());

        self.update_storage_balance(
            env::current_account_id(),
            required_storage_balance,
            NearToken::from_yoctonear(0),
        );

        env::log_str(&OmniBridgeEvent::InitTransferEvent { transfer_message }.to_log_string());
    }
