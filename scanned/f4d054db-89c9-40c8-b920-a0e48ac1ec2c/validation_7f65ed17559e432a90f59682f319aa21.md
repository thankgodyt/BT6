### Title
Tokens Permanently Burned/Locked When Normalized Transfer Amount Rounds to Zero - (File: `near/omni-bridge/src/lib.rs`)

### Summary
When a user initiates a NEAR → Foreign chain transfer with an amount that is too small to survive decimal normalization (floor division by `10^(origin_decimals − dest_decimals)`), the user's tokens are permanently burned or locked inside `init_transfer_internal` with no refund path. The zero-amount guard exists only in `sign_transfer`, which is called later by a relayer — after the irreversible token burn/lock has already occurred.

### Finding Description

`init_transfer` (called via `ft_on_transfer`) validates only that `fee < amount`: [1](#0-0) 

It then calls `init_transfer_internal`, which unconditionally burns or locks the full `transfer_message.amount`: [2](#0-1) 

Later, when a relayer calls `sign_transfer`, the bridge normalizes `amount_without_fee` using floor division: [3](#0-2) 

Only at this point is the zero check enforced: [4](#0-3) 

If `normalize_amount(amount − fee, decimals) == 0`, `sign_transfer` reverts with `InvalidAmountToTransfer`. The `TransferMessage` remains in `pending_transfers` indefinitely, and the burned/locked tokens are irrecoverable — there is no cancel or refund function exposed to users.

The `normalize_amount` comment itself acknowledges the floor-division truncation but frames it as a "dust remainder" concern, not the case where the **entire** `amount_without_fee` rounds to zero: [5](#0-4) 

### Impact Explanation

A user who sends any amount strictly less than `10^(origin_decimals − dest_decimals)` with `fee = 0` will have their tokens permanently burned (for bridge-deployed tokens) or permanently locked (for native tokens) with zero tokens delivered on the destination chain. For a token registered with 24 origin decimals and 6 destination decimals (`diff = 18`), any transfer of fewer than `10^18` base units — i.e., less than `1 × 10^{-6}` of the token — triggers this loss. This constitutes escrow mis-accounting and decimal/normalization abuse resulting in permanent loss of bridged funds.

### Likelihood Explanation

Tokens with large decimal spreads (e.g., NEAR-native 24-decimal tokens bridged to 6-decimal EVM representations) are a supported and documented configuration. A user who sends a "dust" amount — or who miscalculates the minimum viable transfer — will silently lose funds. No UI or contract-level guard prevents the submission. The entry point (`ft_transfer_call` → `ft_on_transfer`) is fully public and requires no special role.

### Recommendation

Add a decimal-normalization check inside `init_transfer`, **before** `init_transfer_internal` is called, to reject transfers whose `amount_without_fee` normalizes to zero:

```rust
// Fetch decimals for the destination token and reject dust-only transfers
if let Some(token_address) = self.get_token_address(
    transfer_message.get_destination_chain(),
    self.get_token_id(&transfer_message.token),
) {
    if let Some(decimals) = self.token_decimals.get(&token_address) {
        let normalized = Self::normalize_amount(
            transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
            decimals,
        );
        require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
    }
}
```

This mirrors the guard already present in `sign_transfer` but places it at the point where the user's tokens have not yet been touched.

### Proof of Concept

1. A token is registered with `origin_decimals = 24`, `decimals = 6` (diff = 18).
2. User calls `ft_transfer_call` transferring `amount = 10^17` base units, `fee = 0`.
3. `init_transfer` passes the `fee < amount` check (0 < 10^17). [1](#0-0) 
4. `init_transfer_internal` burns/locks `10^17` tokens. [2](#0-1) 
5. Relayer calls `sign_transfer`. `normalize_amount(10^17, {decimals:6, origin_decimals:24}) = 10^17 / 10^18 = 0`. [3](#0-2) 
6. `require!(amount_to_transfer > 0, ...)` reverts. [4](#0-3) 
7. The `TransferMessage` is never removed; the user's `10^17` tokens are permanently burned/locked with no recourse.

    /// Uses floor division — any sub-unit remainder ("dust") is truncated and not transferred
    /// to the destination chain. When fee > 0, dust is absorbed into the fee via `claim_fee`.
    /// When fee = 0, dust stays locked/burned. See SECURITY.md for details.
    fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
        let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
        amount / (10_u128.pow(diff_decimals))
    }
