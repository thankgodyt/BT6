### Title
Fee-on-Transfer Token Escrow Mis-Accounting in `initTransfer` Allows Draining Bridge Reserves - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

### Summary

`OmniBridge.initTransfer()` uses the caller-supplied `amount` parameter in the emitted `InitTransfer` event and Wormhole message after performing a `safeTransferFrom`, without accounting for the actual tokens received. For fee-on-transfer tokens (e.g. stETH, PAXG, USDT with fees enabled), the bridge locks fewer tokens than it signals to the destination chain, creating a permanent escrow deficit that can be exploited to drain the bridge's token reserves.

### Finding Description

In `OmniBridge.initTransfer()`, when the token is a plain ERC-20 (not a bridge token and not a custom minter), the function pulls tokens from the caller and then emits the event using the original `amount` argument:

```solidity
// OmniBridge.sol lines 407-411
IERC20(tokenAddress).safeTransferFrom(
    msg.sender,
    address(this),
    amount          // <-- requested amount, not actual received
);
```

After the transfer, the function passes the original `amount` to `initTransferExtension` and emits the event:

```solidity
// OmniBridge.sol lines 415-436
initTransferExtension(
    msg.sender, tokenAddress, currentOriginNonce,
    amount, fee, nativeFee, recipient, message, extensionValue
);

emit BridgeTypes.InitTransfer(
    msg.sender, tokenAddress, currentOriginNonce,
    amount, fee, nativeFee, recipient, message   // <-- original amount, not actual received
);
```

For fee-on-transfer tokens, `safeTransferFrom` delivers `amount - delta` to the bridge, but the `InitTransfer` event records `amount`. The NEAR side (or Wormhole-routed destination via `OmniBridgeWormhole.initTransferExtension`) reads this event and releases/mints the full `amount` to the recipient. The bridge has locked `delta` fewer tokens than it will eventually release, making it insolvent by `delta` per transaction.

`OmniBridgeWormhole.initTransferExtension` encodes the original `amount` directly into the Wormhole VAA payload:

```solidity
// OmniBridgeWormhole.sol lines 136-137
Borsh.encodeUint128(amount),   // <-- original amount, not actual received
Borsh.encodeUint128(fee),
```

### Impact Explanation

**Critical — escrow mis-accounting leading to loss of bridged funds.**

Each `initTransfer` call with a fee-on-transfer token locks `amount - delta` on EVM but instructs the destination to release `amount`. The bridge's ERC-20 reserve is underfunded by `delta` per call. An attacker can repeat this to progressively drain the bridge's entire reserve of any supported fee-on-transfer token, causing legitimate users' withdrawal (`finTransfer`) calls to revert due to insufficient balance.

### Likelihood Explanation

**Medium.** Fee-on-transfer tokens (stETH, PAXG, STA, USDT with fees toggled on) are widely used ERC-20 tokens. The bridge does not restrict which ERC-20 tokens can be bridged via `initTransfer` — any token not in `isBridgeToken` and not in `customMinters` takes the vulnerable code path. An unprivileged user can trigger this with a single public call.

### Recommendation

Measure the actual received balance before and after the transfer, and use that value for the event and cross-chain message:

```solidity
} else {
    uint256 balanceBefore = IERC20(tokenAddress).balanceOf(address(this));
    IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
    uint256 actualReceived = IERC20(tokenAddress).balanceOf(address(this)) - balanceBefore;
    amount = uint128(actualReceived); // use actual received for event + cross-chain message
}
```

Apply the same fix to `initTransfer1155` if ERC-1155 tokens with transfer fees are ever supported.

### Proof of Concept

1. Deploy or use any fee-on-transfer ERC-20 token (e.g. stETH, which delivers 1–2 wei less than requested) that is not registered as a bridge token or custom minter in `OmniBridge`.
2. Call `OmniBridge.initTransfer(tokenAddress, 1_000_000, 0, 0, "attacker.near", "")`.
3. The bridge receives `1_000_000 - delta` tokens but emits `InitTransfer(..., amount=1_000_000, ...)`.
4. The NEAR bridge contract processes the event and mints/releases `1_000_000` wrapped tokens to `attacker.near`.
5. The attacker bridges back: NEAR burns `1_000_000` wrapped tokens and `finTransfer` on EVM releases `1_000_000` native tokens — but the bridge only holds `1_000_000 - delta`.
6. Repeat until the bridge's reserve is exhausted; subsequent legitimate `finTransfer` calls revert.
