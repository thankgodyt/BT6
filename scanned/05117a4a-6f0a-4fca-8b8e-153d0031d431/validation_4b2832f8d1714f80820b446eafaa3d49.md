### Title
ETH Permanently Locked in `OmniBridge` — No Withdrawal Path for `receive()` Accumulation and `nativeFee` Residue - (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

### Summary
`OmniBridge.sol` declares a bare `receive() external payable {}` and accepts ETH via `initTransfer` as `nativeFee`, but contains no function to withdraw ETH. Any ETH that enters the contract through the `receive()` fallback or as accumulated `nativeFee` residue from bridge operations is permanently locked with no recovery path.

### Finding Description
`OmniBridge.sol` has two distinct ETH-accumulation paths with no corresponding withdrawal:

**Path 1 — bare `receive()` fallback** [1](#0-0) 

Any address can send ETH directly to the contract. The function body is empty; the ETH is accepted and silently retained. No admin or user function exists to recover it (confirmed: zero matches for any `withdraw`/`rescue` pattern across all `.sol` files).

**Path 2 — `nativeFee` residue in `initTransfer`**

For ERC-20 token transfers, `initTransfer` computes: [2](#0-1) 

`extensionValue = msg.value - nativeFee`. Only `extensionValue` is forwarded downstream to `initTransferExtension`. In `OmniBridgeWormhole`, that value is forwarded to Wormhole: [3](#0-2) 

The `nativeFee` portion is never forwarded anywhere — it stays in the contract after every ERC-20 `initTransfer` call. For native-ETH transfers the residue is `msg.value - amount - nativeFee` (the `nativeFee` component again stays in the contract): [4](#0-3) 

There is no `withdrawETH`, `rescueETH`, or any equivalent function anywhere in the contract or its Wormhole extension. [5](#0-4) 

### Impact Explanation
Every `initTransfer` call for an ERC-20 token that includes a non-zero `nativeFee` permanently locks that ETH in the contract. Over the lifetime of the bridge, this accumulates into a material sum of user-paid ETH that can never be recovered by the protocol or returned to users. ETH sent directly via `receive()` is similarly irrecoverable. This constitutes permanent freezing of user funds deposited into the bridge.

### Likelihood Explanation
The `nativeFee` path is triggered by every normal ERC-20 bridge operation that includes a relayer fee — the standard, expected usage of the bridge. The `receive()` path is reachable by any external address. Both paths are exercised in normal protocol operation, making this a near-certain accumulation issue on mainnet.

### Recommendation
1. Remove `receive() external payable {}` if the contract does not need to accept plain ETH transfers.
2. Add an admin-gated ETH withdrawal function (e.g., `withdrawETH(address payable to, uint256 amount) external onlyRole(DEFAULT_ADMIN_ROLE)`) to allow recovery of accumulated `nativeFee` residue and any ETH sent via `receive()`.
3. Alternatively, forward `nativeFee` directly to a designated fee recipient inside `initTransfer` rather than leaving it in the contract.

### Proof of Concept
1. Deploy `OmniBridgeWormhole` on a testnet.
2. Call `initTransfer(erc20Token, 1e18, 0, 1e16, "near-recipient", "")` with `msg.value = 1e16` (the `nativeFee`). `extensionValue = 1e16 - 1e16 = 0`; Wormhole receives 0 ETH; the contract balance increases by `1e16`.
3. Repeat N times. The contract balance grows by `N * 1e16`.
4. Attempt to call any function to withdraw ETH — none exists. The ETH is permanently locked.
5. Additionally, send 1 ETH directly to the contract address. The `receive()` function accepts it silently. It is also permanently locked. [6](#0-5)
