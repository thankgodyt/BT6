### Title
Missing Chain ID in `deployToken` Signature Hash Enables Cross-Chain Replay of Deployment Signatures - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

### Summary
The `deployToken` function in `OmniBridge.sol` constructs a Borsh-encoded hash for MPC signature verification that omits `omniBridgeChainId`. In contrast, `finTransfer` correctly binds its hash to the destination chain via `omniBridgeChainId`. A valid `deployToken` signature obtained from one EVM chain (e.g., Ethereum) can be replayed verbatim on any other EVM chain (e.g., Arbitrum, Base, BNB) to deploy tokens without NEAR explicitly authorizing deployment on those chains. The same structural flaw exists in the Starknet and Solana implementations.

### Finding Description
In `OmniBridge.sol::deployToken()`, the Borsh-encoded hash used for signature verification is:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
bytes32 hashed = keccak256(borshEncoded);
```

No `omniBridgeChainId` is included. [1](#0-0) 

In contrast, `finTransfer()` includes `omniBridgeChainId` twice in its hash, binding the signature to the specific destination chain: [2](#0-1) 

Because the `deployToken` hash is identical across all EVM chains for the same token metadata, the same MPC signature is valid on every deployed instance of `OmniBridge.sol`.

The same structural omission exists in:

- **Starknet**: `MetadataPayloadImpl::to_borsh()` encodes only `PayloadType::Metadata`, token, name, symbol, and decimals — no chain ID. [3](#0-2) 

- **Solana**: `DeployTokenPayload::serialize_for_near()` serializes only `IncomingMessageType::Metadata` and the payload fields — no chain ID. [4](#0-3) 

The Starknet CLAUDE.md explicitly documents that chain ID binding in `fin_transfer` prevents cross-chain replay, but makes no such claim for `deploy_token`: [5](#0-4) 

This confirms the design intent was to bind `fin_transfer` to a chain, but the same protection was never applied to `deploy_token`.

**Attack path (EVM)**:
1. NEAR MPC signs a metadata payload for `"token.near"` to authorize deployment on Ethereum.
2. A relayer calls `deployToken(signature, payload)` on Ethereum — the signature is publicly visible in calldata.
3. Attacker extracts the signature from the Ethereum transaction.
4. Attacker calls `deployToken(signature, payload)` on Arbitrum with the identical arguments.
5. `OmniBridge.sol::deployToken()` computes the same hash (no chain ID) and the `ECDSA.recover` check passes. [6](#0-5) 
6. `"token.near"` is deployed on Arbitrum, registered in `isBridgeToken`, `ethToNearToken`, `nearToEthToken`.
7. A `DeployToken` event is emitted on Arbitrum.
8. The NEAR bridge's light client or Wormhole relay picks up this event and registers `"token.near"` as deployed on Arbitrum.
9. NEAR will now sign `finTransfer` payloads for Arbitrum for `"token.near"`, enabling bridging to a chain NEAR never explicitly authorized.

### Impact Explanation
This is a chain/domain separation flaw. The NEAR MPC's signature over a `MetadataPayload` is intended to authorize deployment of a specific token on a specific chain. Because the chain ID is absent from the signed hash, a single MPC signature authorizes deployment on **every** EVM chain simultaneously. An unprivileged attacker can replay any publicly observed `deployToken` signature across all EVM chains (Ethereum, Arbitrum, Base, BNB, HyperEVM, Abs), deploying tokens on chains where NEAR has not granted authorization. Once the NEAR bridge processes the resulting `DeployToken` event from the unauthorized chain, it registers the token there and begins signing `finTransfer` payloads for that chain — enabling token flows to a chain the NEAR MPC never explicitly approved. This undermines the MPC's role as the sole authoritative gate for cross-chain token deployment decisions and constitutes a chain/domain separation flaw enabling invalid finalization of transfers on unauthorized chains.

### Likelihood Explanation
High. The `deployToken` signature is publicly available in transaction calldata on any EVM chain. No privileged access, leaked keys, or admin compromise is required. The only precondition is that a valid `deployToken` signature exists for the target token on any one EVM chain — which is true for every token already deployed through the bridge.

### Recommendation
Include `omniBridgeChainId` in the Borsh-encoded hash for `deployToken` signature verification, mirroring the pattern used in `finTransfer`:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
    bytes1(omniBridgeChainId),          // ← add chain binding
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
```
