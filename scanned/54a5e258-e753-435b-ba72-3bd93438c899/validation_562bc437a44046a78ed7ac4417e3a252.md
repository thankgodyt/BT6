### Title
Unhandled `ft_transfer` Failure in `fin_transfer_send_tokens_callback` Causes Permanent Freezing of Bridged Funds — (File: `near/omni-bridge/src/lib.rs`)

---

### Summary

When finalizing an inbound transfer to NEAR with a simple token transfer (empty `msg`), if the `ft_transfer` to the recipient fails, the bridge callback unconditionally treats the failure as success. The locked-token counter is permanently decremented without the tokens being delivered, and the transfer is marked finalized, blocking any re-execution. The user's bridged funds are permanently frozen inside the bridge contract.

---

### Finding Description

`process_fin_transfer_to_near` performs three state mutations before the token transfer resolves:

1. `add_fin_transfer` — marks the transfer ID as finalized (replay-prevention).
2. `unlock_tokens_if_needed` — decrements the locked-token counter for the origin chain.
3. `send_tokens` — dispatches `ft_transfer` (for non-deployed tokens with empty `msg`) and chains `fin_transfer_send_tokens_callback`. [1](#0-0) [2](#0-1) 

Inside the callback, the refund/revert decision is delegated to `is_refund_required`, which receives `is_ft_transfer_call = !msg.is_empty()`. For a simple transfer (empty `msg`) this is always `false`, and the function unconditionally returns `false` — it never inspects the actual promise result of the `ft_transfer`: [3](#0-2) 

Consequently, when `ft_transfer` fails (promise result is `Err`), the callback enters the `else` branch: [4](#0-3) 

- `revert_lock_actions` is **not** called → the locked-token counter stays decremented.
- `remove_fin_transfer` is **not** called → the transfer ID stays in the finalized set.
- The fee is fire-and-forget dispatched with `.detach()`.
- The tokens remain physically in the bridge contract, unaccounted for.

The only path that correctly reverts state (`revert_lock_actions` + `remove_fin_transfer`) is gated on `is_refund_required` returning `true`, which is structurally impossible for a non-`ft_transfer_call` path. [5](#0-4) 

---

### Impact Explanation

For any non-deployed (natively locked) token whose `ft_transfer` can fail after storage registration is confirmed — e.g., a token contract that is paused, or one that enforces a transfer blocklist — the following permanent state corruption occurs:

| State field | Expected after success | Actual after silent failure |
|---|---|---|
| `finalised_transfers` | transfer ID present | transfer ID present (replay blocked) |
| `locked_tokens[chain][token]` | decremented | decremented (mis-accounting) |
| recipient token balance | credited | unchanged |
| bridge token balance | decremented | unchanged (tokens stranded) |

The user's bridged funds are permanently frozen. The transfer cannot be re-submitted (replay protection blocks it). There is no admin escape hatch to recover stranded tokens for a specific user.

---

### Likelihood Explanation

The trigger requires a non-deployed NEP-141 token whose `ft_transfer` can revert after the relayer has already satisfied the storage-deposit pre-check. Realistic triggers include:

- **Token-level pause**: Many production stablecoins (USDC, USDT) expose a `pause` or `freeze` function callable by the token issuer. A pause activated between the relayer's `fin_transfer` call and the inner `ft_transfer` execution satisfies the condition.
- **Per-account blocklist**: Tokens that implement address-level blocking (common in regulated stablecoins) can reject `ft_transfer` even for a registered recipient.

The relayer is an unprivileged, publicly callable role; any relayer can trigger `fin_transfer` for any pending proof. The recipient is attacker-controlled (the user who initiated the cross-chain transfer). No admin compromise is required.

---

### Recommendation

Extend `is_refund_required` (or add a parallel check) to inspect the `ft_transfer` promise result even when `is_ft_transfer_call` is `false`. On failure, execute the same revert path already used for the `ft_transfer_call` case:

```rust
// In fin_transfer_send_tokens_callback, replace the bare `false` branch:
fn is_refund_required(is_ft_transfer_call: bool) -> bool {
    // Always check promise result, regardless of transfer type
    match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
        Err(_) => true,   // ft_transfer panicked → revert
        Ok(value) if is_ft_transfer_call => {
            near_sdk::serde_json::from_slice::<U128>(&value)
                .map_or(false, |a| a.0 == 0)
        }
        Ok(_) => false,   // ft_transfer succeeded
    }
}
```

This ensures `revert_lock_actions` and `remove_fin_transfer` are called on any delivery failure, restoring the bridge's escrow accounting and allowing the transfer to be retried once the token contract is unpaused or the blocklist entry is removed.

---

### Proof of Concept

1. User initiates a transfer of a pausable non-deployed token (e.g., bridged USDC) from Ethereum to NEAR.
2. The token issuer pauses the USDC contract on NEAR (or the recipient's address is added to the blocklist).
3. A relayer calls `fin_transfer` with a valid proof and correct `storage_deposit_actions` (recipient has storage registered).
4. `process_fin_transfer_to_near` runs: `add_fin_transfer` fires, `unlock_tokens_if_needed` decrements the locked counter, `send_tokens` dispatches `ft_transfer`.
5. `ft_transfer` fails (USDC contract paused / recipient blocked).
6. `fin_transfer_send_tokens_callback` runs with `is_ft_transfer_call = false`.
7. `is_refund_required(false)` returns `false` without inspecting the promise result.
8. Callback enters the success branch: fee dispatched with `.detach()`, no state revert.
9. **Result**: transfer ID is finalized (replay blocked), locked-token counter is decremented, USDC tokens remain stranded in the bridge contract, user balance is zero. No recovery path exists. [3](#0-2) [6](#0-5) [7](#0-6)
