### Title
Missing Setter for `omniBridgeChainId` Causes Permanent Freezing of Bridged Funds if Misconfigured - (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

### Summary

`OmniBridge.sol` sets `omniBridgeChainId` once during `initialize()` with no update function. This value is embedded into every Borsh-encoded payload that `finTransfer` signature-verifies against the NEAR-derived signer. If the deployer supplies the wrong chain ID, every `finTransfer` call permanently reverts with `InvalidSignature`, freezing all in-flight bridged funds that were already burned or locked on the source chain. A parallel setter exists for `nearBridgeDerivedAddress` but was never added for `omniBridgeChainId`.

### Finding Description

`omniBridgeChainId` is stored as a mutable state variable but is only ever written in `initialize()`:

```solidity
// OmniBridge.sol line 72-86
function initialize(
    address tokenImplementationAddress_,
    address nearBridgeDerivedAddress_,
    uint8 omniBridgeChainId_
) public initializer {
    ...
    omniBridgeChainId = omniBridgeChainId_;
    ...
}
``` [1](#0-0) 

In `finTransfer`, `omniBridgeChainId` is embedded **twice** into the Borsh payload (once for the token-chain field and once for the recipient-chain field) before the ECDSA signature is verified:

```solidity
// OmniBridge.sol lines 289-312
bytes memory borshEncoded = bytes.concat(
    ...
    bytes1(omniBridgeChainId),   // token chain
    Borsh.encodeAddress(payload.tokenAddress),
    ...
    bytes1(omniBridgeChainId),   // recipient chain
    Borsh.encodeAddress(payload.recipient),
    ...
);
bytes32 hashed = keccak256(borshEncoded);
if (ECDSA.recover(hashed, signatureData) != nearBridgeDerivedAddress) {
    revert InvalidSignature();
}
``` [2](#0-1) 

The NEAR side signs the payload using the correct chain ID for the target EVM network. If the deployed contract has a wrong `omniBridgeChainId`, the reconstructed hash will never match the NEAR-signed hash, and every `finTransfer` call reverts.

The developer recognized the need for a post-deploy setter for `nearBridgeDerivedAddress`:

```solidity
// OmniBridge.sol lines 568-572
function setNearBridgeDerivedAddress(
    address nearBridgeDerivedAddress_
) external onlyRole(DEFAULT_ADMIN_ROLE) {
    nearBridgeDerivedAddress = nearBridgeDerivedAddress_;
}
``` [3](#0-2) 

No equivalent `setOmniBridgeChainId` function exists anywhere in the contract. The same omission exists in `OmniBridgeWormhole.sol`, which also embeds `omniBridgeChainId` into every Wormhole message payload: [4](#0-3) 

### Impact Explanation

If `omniBridgeChainId` is misconfigured at deployment:

1. Every call to `finTransfer` reverts with `InvalidSignature` — no user can ever receive tokens on this EVM chain.
2. Tokens that were already burned or locked on the NEAR side (or source chain) cannot be released. They are permanently frozen with no on-chain recovery path short of a contract upgrade.
3. The `OmniBridgeWormhole` variant additionally emits malformed Wormhole messages (wrong chain ID in `initTransfer` and `finTransfer` extension payloads), causing NEAR-side proof verification to reject all inbound messages from this chain.

This matches the **permanent freezing of bridged funds** impact category.

### Likelihood Explanation

`omniBridgeChainId` is a NEAR-protocol-specific `ChainKind` byte (e.g., `0` for Eth, `2` for Sol, `12` for Fogo) that is distinct from Wormhole chain IDs and EVM chain IDs. The Makefile documents `SOL_OMNI_CHAIN_ID := 2` and `FOGO_OMNI_CHAIN_ID := 12` as separate from Wormhole's `CHAIN_ID`, making confusion between these namespaces realistic during deployment. The parameter is manually supplied with no on-chain validation, and the contract is deployed across multiple EVM networks each requiring a different value. The absence of a setter means a deployment error cannot be corrected without a full UUPS upgrade, which introduces delay and operational risk.

### Recommendation

Add an admin-gated setter for `omniBridgeChainId`, mirroring the existing `setNearBridgeDerivedAddress`:

```solidity
function setOmniBridgeChainId(
    uint8 omniBridgeChainId_
) external onlyRole(DEFAULT_ADMIN_ROLE) {
    omniBridgeChainId = omniBridgeChainId_;
}
```

Apply the same fix to `OmniBridgeWormhole.sol` if it overrides or extends the chain ID usage. Additionally, emit an event on change and consider adding a validation check that the supplied value matches a known `ChainKind` enum range.

### Proof of Concept

1. Deploy `OmniBridge` with `omniBridgeChainId_ = 1` (wrong value; correct value for Ethereum is `0`).
2. A user initiates a transfer from NEAR to Ethereum: NEAR burns the user's tokens and the MPC signer signs a `TransferMessagePayload` with `omniBridgeChainId = 0` embedded in the Borsh encoding.
3. A relayer calls `finTransfer(signatureData, payload)` on the EVM contract.
4. The contract reconstructs the Borsh payload using `omniBridgeChainId = 1` (the wrong stored value), producing a different `keccak256` hash.
5. `ECDSA.recover(hashed, signatureData)` returns an address that does not equal `nearBridgeDerivedAddress`.
6. The call reverts with `InvalidSignature()`.
7. The user's tokens are permanently burned on NEAR with no way to release them on Ethereum, since no `setOmniBridgeChainId` function exists to correct the misconfiguration without a full contract upgrade. [5](#0-4) [6](#0-5) [7](#0-6)
