### Title
`OmniToken.set_withdraw_relayer_address()` Is Controller-Gated But Permanently Unreachable Through the Controller — (`near/omni-token/src/lib.rs`)

### Summary
`OmniToken.set_withdraw_relayer_address()` enforces `assert_controller()`, meaning only the omni-bridge contract (the designated `controller`) can invoke it. However, the omni-bridge contract exposes no function that calls `set_withdraw_relayer_address()` on any omni-token instance. The function is therefore permanently inaccessible after deployment, and the withdraw-relayer address can never be updated through the intended control path.

### Finding Description
`OmniToken` stores a `controller` field set at construction time to the omni-bridge contract address. [1](#0-0) 

`set_withdraw_relayer_address()` enforces this guard: [2](#0-1) 

The omni-bridge's `ext_token` cross-contract trait — the only mechanism by which the bridge calls into token contracts — does not include `set_withdraw_relayer_address`: [3](#0-2) 

A repository-wide search for `set_withdraw_relayer_address` returns exactly one result: the definition in `near/omni-token/src/lib.rs`. No call site exists in the omni-bridge. The function is therefore dead code from the controller's perspective.

The withdraw-relayer address is consumed in `ft_transfer` to redirect legacy Near Intents withdrawals: [4](#0-3) 

When `withdraw_relayer` is `None` (never set or unable to be updated), the fallthrough path executes `self.token.ft_transfer(receiver_id, amount, memo)` where `receiver_id == env::current_account_id()` — the token contract itself — silently locking the transferred tokens inside the token contract with no recovery path.

The only place the withdraw-relayer address is ever written is inside the one-time migration function `migrate_from_poa`: [5](#0-4) 

Once migration completes, the address is frozen. If the relayer account changes, is compromised, or was set incorrectly, there is no on-chain mechanism to correct it.

### Impact Explanation
Any user who sends tokens to the omni-token contract with a `"WITHDRAW_TO:"` memo (the legacy Near Intents bridging path) will have their tokens silently redirected to the token contract itself when the withdraw-relayer address is stale or unset. Those tokens are permanently locked — the token contract has no withdrawal function for its own balance. This constitutes permanent freezing of bridged funds, satisfying the critical impact threshold.

### Likelihood Explanation
The legacy Near Intents flow is an active migration path for tokens migrated from Near Intents. The withdraw-relayer address is a live operational parameter: relayer key rotation, infrastructure changes, or a compromised relayer key all require updating it. Because the omni-bridge provides no function to do so, any such event leaves the legacy flow permanently broken and user funds at risk of being locked. Likelihood is medium given the operational reality of relayer key management.

### Recommendation
Add a privileged function to the omni-bridge contract (restricted to `Role::DAO` or an equivalent role) that calls `set_withdraw_relayer_address()` on a specified omni-token instance via a cross-contract call. Additionally, add `set_withdraw_relayer_address` to the `ext_token` trait so the bridge can dispatch it:

```rust
// In ext_token trait (near/omni-bridge/src/lib.rs)
fn set_withdraw_relayer_address(relayer: &AccountId);

// New bridge method
#[access_control_any(roles(Role::DAO))]
pub fn update_token_withdraw_relayer(
    &self,
    token_id: AccountId,
    relayer: AccountId,
) -> Promise {
    ext_token::ext(token_id)
        .set_withdraw_relayer_address(&relayer)
}
```

### Proof of Concept
1. `set_withdraw_relayer_address()` in `near/omni-token/src/lib.rs` line 113 calls `self.assert_controller()` — only the omni-bridge can call it.
2. Search `set_withdraw_relayer_address` across the entire repository: zero occurrences in `near/omni-bridge/`.
3. The `ext_token` trait (lines 131–171 of `near/omni-bridge/src/lib.rs`) lists every cross-contract call the bridge makes to token contracts; `set_withdraw_relayer_address` is absent.
4. The withdraw-relayer address is written only once, inside `migrate_from_poa` (a `#[private]` `#[init(ignore_state)]` function that runs exactly once during migration).
5. After migration, any user calling `ft_transfer(token_contract_id, amount, "WITHDRAW_TO:...")` on an omni-token whose relayer address needs updating will trigger the fallthrough at line 206, sending tokens to `env::current_account_id()` (the token contract itself), where they are permanently locked.     pub fn migrate_from_poa(controller: AccountId, withdraw_relayer: &AccountId) -> Self {
        if !env::state_exists() {
            env::panic_str("Old state not found. Migration is not needed.")
        }

        let state = env::storage_read(STATE_KEY)
            .unwrap_or_else(|| env::panic_str("Failed to read state key."));

        if let Ok(state) = NearIntentsState::try_from_slice(&state) {
            require!(
                env::storage_remove(OWNABLE_KEY),
                "Wrong token version for migration: __OWNER__ key not found"
            );

            env::storage_write(
                WITHDRAW_RELAYER_ADDRESS,
                &borsh::to_vec(withdraw_relayer).unwrap(),
            );

            let new_state = Self {
                controller,
                token: state.token,
                metadata: LazyOption::new(b"m".to_vec(), Some(state.metadata.get())),
            };

            let mut old_metadata = state.metadata;
            old_metadata.remove();

            new_state
        } else {
            env::panic_str("Old state not found. Migration is not needed.")
        }
    }
