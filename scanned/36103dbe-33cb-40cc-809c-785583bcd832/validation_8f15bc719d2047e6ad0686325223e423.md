### Title
ERC1155 Transfer to Non-Contract Address Succeeds Silently in `initTransfer1155`, Enabling Unauthorized NEAR Token Minting — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

`initTransfer1155` performs a raw `IERC1155(tokenAddress).safeTransferFrom(...)` call with no check that `tokenAddress` contains contract code. In the EVM, calling a void-returning function on an EOA or empty address always returns success. An attacker can supply a zero-code address, bypass the deposit entirely, and still trigger the cross-chain message that causes the NEAR bridge to mint tokens.

---

### Finding Description

`OmniBridge.sol` uses OpenZeppelin's `SafeERC20` wrapper for all ERC-20 transfers. That wrapper internally calls `Address.functionCall`, which asserts `address(token).code.length > 0` before proceeding, so a non-contract token address reverts. [1](#0-0) 

The ERC-1155 path in `initTransfer1155` does **not** use any such wrapper. It issues a direct interface call: [2](#0-1) 

`IERC1155.safeTransferFrom` is declared `void` (no return value). Under the EVM, a `CALL` to an address whose code length is zero always returns `(success=1, returndata="")`. Because Solidity only reverts on a failed call or on ABI-decoding failure, and there is nothing to decode here, the call completes without reverting. No tokens are actually moved.

Immediately after, `initTransferExtension` is invoked, which in `OmniBridgeWormhole` publishes a Wormhole VAA: [3](#0-2) 

This VAA carries an `InitTransfer` payload that the NEAR bridge treats as proof of a legitimate deposit and uses to mint the corresponding bridged tokens on NEAR.

The `logMetadata1155` function, also publicly callable with any address, registers the fake token and publishes a `LogMetadata` Wormhole message that primes the NEAR side to accept the token: [4](#0-3) 

---

### Impact Explanation

An unprivileged attacker can mint an arbitrary quantity of any ERC-1155-backed bridged token on NEAR without depositing any real ERC-1155 tokens on the EVM side. This is unauthorized minting / escrow mis-accounting: the EVM bridge holds zero tokens while NEAR records a positive balance, breaking the 1:1 peg and allowing the attacker to drain real assets on the NEAR side.

---

### Likelihood Explanation

The entry points (`logMetadata1155` and `initTransfer1155`) are public, require no special role, and are protected only by the pause flag. The attacker needs only to pay the Wormhole message fee (`nativeFee`) and craft a call with a non-contract address. No privileged access, leaked keys, or external collusion is required.

---

### Recommendation

Before executing the ERC-1155 transfer, verify that `tokenAddress` contains contract code, mirroring what OpenZeppelin's `SafeERC20` does for ERC-20:

```solidity
require(tokenAddress.code.length > 0, "ERC1155: not a contract");
```

Alternatively, wrap the call in OpenZeppelin's `Address.functionCall` or use a helper analogous to `SafeERC20` for ERC-1155 (e.g., check code length, then call). Apply the same guard in `finTransfer` for the `multiToken` path: [5](#0-4) 

---

### Proof of Concept

```
// 1. Deploy no-code address (use a fresh EOA or a CREATE2 salt that has never been deployed)
address fakeERC1155 = address(0xdead...); // code.length == 0

// 2. Register the fake token so NEAR side accepts it
OmniBridge.logMetadata1155(fakeERC1155, tokenId);
// → emits LogMetadata, Wormhole VAA published, NEAR registers token

// 3. Initiate a transfer with zero real deposit
OmniBridge.initTransfer1155{value: nativeFee}(
    fakeERC1155,
    tokenId,
    1_000_000e18,   // arbitrary large amount
    0,              // fee
    nativeFee,
    "attacker.near",
    ""
);
// → IERC1155(fakeERC1155).safeTransferFrom(...) returns success silently
// → InitTransfer Wormhole VAA published
// → NEAR bridge mints 1_000_000e18 tokens to attacker.near
// → EVM bridge holds 0 real ERC-1155 tokens
```
