### Title
Unprivileged Caller Can Trigger MPC Signing of Arbitrary Token Metadata, Enabling Fake Token Deployment on Destination Chains - (File: near/omni-bridge/src/lib.rs)

### Summary

`log_metadata` in the NEAR bridge contract is callable by any unprivileged NEAR account. It accepts any `token_id`, fetches its metadata via a cross-contract call, and then unconditionally requests an MPC signature over the resulting `MetadataPayload`. The signed payload is the exact artifact used to deploy bridge tokens on EVM, Solana, and Starknet destination chains. There is no check that the token is registered, known, or legitimate. Any attacker can cause the bridge's MPC key to sign metadata for a malicious NEAR token they control, then use that signature to deploy a fake token on destination chains.

### Finding Description

`log_metadata` lives inside the `#[trusted_relayer(...)]` impl block, but it carries **no function-level `#[trusted_relayer]`** attribute and no other caller-authentication guard beyond the global pause flag:

```rust
// near/omni-bridge/src/lib.rs:316-327
#[pause(except(roles(Role::DAO)))]
pub fn log_metadata(&self, token_id: &AccountId) -> Promise {
    ext_token::ext(token_id.clone())
        .with_static_gas(LOG_METADATA_GAS)
        .ft_metadata()
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(LOG_METADATA_CALLBACK_GAS)
                .with_attached_deposit(env::attached_deposit())
                .log_metadata_callback(token_id),
        )
}

The resulting `SignatureResponse` is emitted in a `LogMetadataEvent`. This is the exact artifact consumed by `deployToken` on EVM chains to deploy a new bridge token:

```solidity

}
``` [5](#0-4) 

There is no check on the EVM side that the NEAR token ID corresponds to a legitimate or previously registered token — only that it has not already been deployed:

```solidity
nearToEthToken[metadata.token] = address(bridgeTokenProxy);
``` [6](#0-5) 

### Impact Explanation

An attacker who controls a NEAR account (e.g., `fake-usdc.near`) can deploy a contract there that returns `name="USD Coin"`, `symbol="USDC"`, `decimals=6` from `ft_metadata()`. They call `log_metadata("fake-usdc.near")`, receive a valid MPC-signed `MetadataPayload`, and submit it to `deployToken` on Ethereum. A new ERC-20 token named "USD Coin / USDC" is deployed and registered in the bridge's `nearToEthToken` mapping. Because the attacker controls `fake-usdc.near`, they can mint arbitrary amounts of it on NEAR, bridge them to Ethereum to receive the fake ERC-20, and sell it to users who mistake it for the legitimate USDC bridge token. Users who purchase the fake token lose their funds. This is token metadata binding confusion that directly changes user balances through the bridge mechanism.

### Likelihood Explanation

The attack requires only a NEAR account and gas. No privileged role, no stake, no leaked key. The attacker controls the metadata returned by their token contract. The only barrier is the cost of deploying a NEAR contract and paying MPC signing fees. Likelihood is high.

### Recommendation

Add a caller-authentication guard to `log_metadata` equivalent to the one on `sign_transfer`. At minimum, restrict it to trusted relayers or require that the `token_id` is already registered in `token_address_to_id` or `deployed_tokens` before triggering MPC signing. This mirrors the principle from the external report: require authentication before any action that exercises the signing key.

### Proof of Concept

1. Attacker deploys a NEAR contract at `fake-usdc.near` implementing `ft_metadata()` returning `name="USD Coin"`, `symbol="USDC"`, `decimals=6`.
2. Attacker calls `omni-bridge.near::log_metadata("fake-usdc.near")` with sufficient attached deposit for MPC gas.
3. The bridge's `log_metadata_callback` validates only that name/symbol are non-empty — both pass.
4. The bridge calls `v1.signer::sign(keccak256(borsh(MetadataPayload{prefix:Metadata, token:"fake-usdc.near", name:"USD Coin", symbol:"USDC", decimals:6})))`.
5. The MPC returns a valid ECDSA signature; the bridge emits `LogMetadataEvent{signature, metadata_payload}`.
6. Attacker reads the signature from the event log and calls `OmniBridge.deployToken(signature, {token:"fake-usdc.near", name:"USD Coin", symbol:"USDC", decimals:6})` on Ethereum.
7. `ECDSA.recover` succeeds; a new ERC-20 "USD Coin (USDC)" is deployed and mapped to `fake-usdc.near`.
8. Attacker mints `fake-usdc.near` tokens, bridges them to Ethereum, and sells the resulting fake ERC-20 to unsuspecting users.
