### Title
STRK Native Fees Permanently Locked in Starknet Bridge Contract With No Retrieval Mechanism - (File: `starknet/src/omni_bridge.cairo`)

### Summary

The Starknet `OmniBridge` contract collects STRK native fees from users during `init_transfer`, transferring them into the contract itself, but provides no function to withdraw or distribute those accumulated STRK tokens. Every STRK native fee paid by any bridge user is permanently locked in the contract.

### Finding Description

In `init_transfer`, when a caller supplies a non-zero `native_fee`, the contract pulls that amount of STRK from the caller into itself:

```cairo
if native_fee > 0 {
    let native_token = self.strk_token_address.read();
    let success = IERC20Dispatcher { contract_address: native_token }
        .transfer_from(caller, get_contract_address(), native_fee.into());
    assert(success, 'ERR_FEE_TRANSFER_FAILED');
}
```

The entire public interface of `IOmniBridge` is:
- `log_metadata`, `deploy_token`, `fin_transfer`, `init_transfer` — operational
- `upgrade_token`, `set_pause_flags`, `pause_all` — admin/pauser
- `get_token_address`, `is_bridge_token`, `is_transfer_finalised` — view

None of these functions transfer STRK out of the contract. The `fin_transfer` function only releases the bridged token amount (`payload.amount` of `payload.token_address`) to `payload.recipient`; it has no path that touches the accumulated STRK balance. There is no admin withdrawal, no fee-claim, and no sweep function.

On the EVM side, the project's own `evm/SECURITY.md` acknowledges that native ETH fees are recoverable via `finTransfer` with `tokenAddress=address(0)`. No equivalent recovery path exists on Starknet.

### Impact Explanation

Every STRK native fee paid by any user who calls `init_transfer` with `native_fee > 0` is permanently locked in the Starknet bridge contract. The relayer that processed the transfer receives its fee on the NEAR side (minted as a wrapped token), but the STRK tokens that were supposed to compensate for gas costs on Starknet are irrecoverably stuck. This constitutes permanent, cumulative loss of user-paid STRK tokens — a fee mis-accounting issue where the contract's STRK balance grows monotonically with no outflow path.

### Likelihood Explanation

Any unprivileged bridge user who initiates a Starknet → NEAR transfer and sets `native_fee > 0` triggers this loss. The bridge's own README and fee-provider API actively encourage users to set native fees to incentivize relayers. Every such transfer permanently locks STRK in the contract.

### Recommendation

Add an admin-gated function to withdraw accumulated STRK native fees to a designated recipient, analogous to how the EVM side recovers native ETH fees via `finTransfer` with `tokenAddress=address(0)`:

```cairo
fn withdraw_native_fees(ref self: ContractState, recipient: ContractAddress, amount: u128) {
    self.accesscontrol.assert_only_role(DEFAULT_ADMIN_ROLE);
    let native_token = self.strk_token_address.read();
    let success = IERC20Dispatcher { contract_address: native_token }
        .transfer(recipient, amount.into());
    assert(success, 'ERR_WITHDRAW_FAILED');
}
```

### Proof of Concept

1. Alice calls `init_transfer(token, 1000, 10, 500, "near:bob", "")` on the Starknet bridge.
2. The contract executes `transfer_from(Alice, contract, 500)` for STRK (the `native_fee`).
3. The NEAR-side relayer finalizes the transfer and claims its fee in wrapped STRK on NEAR.
4. The 500 STRK now sit in the Starknet contract's balance.
5. No function in `IOmniBridge` can move those 500 STRK out — not by Alice, not by the relayer, not by the admin.
6. Repeat for every user who pays a native fee: the locked STRK balance grows without bound and is permanently irrecoverable.

The root cause is the absence of any outflow path for the STRK balance accumulated at `get_contract_address()`. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

            _verify_borsh_signature(

            );

            if self.is_bridge_token(payload.token_address) {
