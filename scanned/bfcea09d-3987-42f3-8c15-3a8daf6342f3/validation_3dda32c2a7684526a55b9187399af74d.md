### Title
`finalised_transfers` Marked Before Token Delivery Confirmed; Failed `send_tokens` Permanently Freezes Bridged Funds — (File: `near/omni-bridge/src/lib.rs`)

### Summary

In `process_fin_transfer_to_near`, the transfer ID is inserted into `finalised_transfers` before the actual token delivery succeeds. When `send_tokens` is called with an empty `msg` (the common case for plain transfers), the callback `fin_transfer_send_tokens_callback` receives `is_ft_transfer_call = false`. The helper `is_refund_required(false)` unconditionally returns `false` without inspecting the promise result, so any failure of the underlying `ft_transfer` or `mint` call is silently treated as success. The transfer remains permanently finalized, the `locked_tokens` counter has already been decremented, and the recipient never receives their tokens — permanently freezing bridged funds with no recovery path.

### Finding Description

**Step 1 — Finalization flag set before delivery.**

`process_fin_transfer_to_near` calls `add_fin_transfer` on the very first line of its body:

```rust
// near/omni-bridge/src/lib.rs:1875
let mut required_balance = self.add_fin_transfer(&transfer_message.get_transfer_id());
```

`add_fin_transfer` inserts the `TransferId` into the `finalised_transfers` `UnorderedSet`. Any subsequent call to `fin_transfer` for the same transfer ID will panic with `BridgeError::TransferAlreadyFinalised`.

**Step 2 — Token delivery dispatched with `is_ft_transfer_call = !msg.is_empty()`.**

```rust
// near/omni-bridge/src/lib.rs:1957-1976
self.send_tokens(token.clone(), recipient, U128(...), &msg)
    .then(
        Self::ext(env::current_account_id())
            .fin_transfer_send_tokens_callback(
                transfer_message,
                &fee_recipient,
                !msg.is_empty(),   // ← false when msg is empty
                predecessor_account_id,
                lock_actions,
            ),
    )
```

For the common case where `msg` is empty (a plain token transfer, not a DeFi integration), `is_ft_transfer_call` is `false`. `send_tokens` then dispatches either `ft_transfer` (non-deployed token, line 2102–2106) or `mint` (deployed bridge token, line 2094–2101).

**Step 3 — Callback ignores promise result when `is_ft_transfer_call = false`.**

```rust
// near/omni-bridge/src/lib.rs:1784-1803
fn is_refund_required(is_ft_transfer_call: bool) -> bool {
    if is_ft_transfer_call {
        match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
            Ok(value) => { /* check returned amount */ }
            Err(_) => false,
        }
    } else {
        // Not ft_transfer_call: don't refund
        false   // ← promise result is NEVER checked
    }
}
```

When `is_ft_transfer_call = false`, `is_refund_required` returns `false` unconditionally. The callback therefore always takes the "success" path:

```rust
// near/omni-bridge/src/lib.rs:1702-1746
if Self::is_refund_required(is_ft_transfer_call) {
    // revert: burn tokens, revert lock actions, remove_fin_transfer
} else {
    // "success": send fee to relayer, emit FinTransferEvent
}
```

If `ft_transfer` or `mint` panicked (promise failed), the callback still emits `FinTransferEvent` and pays the relayer fee — without ever reverting the finalization or restoring `locked_tokens`.

**Step 4 — No recovery path exists.**

Because `finalised_transfers` now contains the transfer ID, any retry of `fin_transfer` for the same proof will panic with `TransferAlreadyFinalised`. The `locked_tokens` counter was already decremented at line 1881–1885. For non-deployed tokens the underlying tokens are stuck in the bridge contract with no admin escape hatch. For deployed (bridge) tokens the tokens were burned on the source chain and the NEAR-side mint failed, making them permanently unrecoverable.

### Impact Explanation

**Critical — permanent freezing / loss of bridged funds.**

- For non-deployed tokens (e.g., USDC locked on Ethereum, to be unlocked on NEAR): the tokens remain locked in the bridge contract but `locked_tokens` is decremented, breaking the accounting invariant. The recipient never receives them and no retry is possible.
- For deployed bridge tokens (burned on source chain, to be minted on NEAR): the tokens are burned on the source chain and the NEAR mint fails silently. The user loses the full bridged amount with no recourse.
- The relayer still collects its fee (minted/transferred in the "success" branch of the callback), creating a perverse incentive: a malicious relayer that can cause `ft_transfer` to fail after the storage check passes profits from the fee while the user loses funds.

### Likelihood Explanation

The trigger requires `send_tokens` to fail for a transfer with an empty `msg`. Realistic failure modes include:

1. **Non-standard token contracts**: A token whose `ft_transfer` implementation panics under edge conditions (e.g., transfer-hook logic, fee-on-transfer tokens registered as non-deployed tokens).
2. **wNEAR path**: `send_tokens` for wNEAR with empty `msg` dispatches `near_withdraw → near_withdraw_callback`. If `near_withdraw` fails, `near_withdraw_callback` panics, the outer promise result is `Failed`, but `is_refund_required(false)` still returns `false`.
3. **Gas exhaustion**: If the gas forwarded to `ft_transfer` or `mint` is insufficient, the call panics. The callback receives a failed promise but treats it as success.
4. **Bridge token contract bug or upgrade**: A deployed bridge token whose `mint` reverts for any reason.

Likelihood is **medium**: the common happy path works correctly, but the structural absence of a promise-result check for the non-`ft_transfer_call` branch means any of the above edge cases silently finalizes the transfer and loses funds.

### Recommendation

In `fin_transfer_send_tokens_callback`, check the promise result regardless of `is_ft_transfer_call`. Specifically, when `is_ft_transfer_call = false`, inspect `env::promise_result_checked(0, ...)` and treat a failed promise as a condition requiring revert (call `revert_lock_actions`, `remove_fin_transfer`, and emit `FailedFinTransferEvent`), mirroring the existing revert logic in the `is_refund_required` branch. The `is_refund_required` helper should be extended or replaced with a broader check that covers both `ft_transfer_call` refund semantics and plain `ft_transfer`/`mint` failure detection.

### Proof of Concept

1. A user initiates a transfer of a non-deployed token (e.g., USDC) from Ethereum to a NEAR account with no `msg` field.
2. The EVM-side `initTransfer` locks the tokens and emits an event.
3. A relayer calls `fin_transfer` on the NEAR bridge with a valid proof.
4. `process_fin_transfer_to_near` runs: `add_fin_transfer` marks the transfer finalized; `unlock_tokens_if_needed` decrements `locked_tokens`; `send_tokens` dispatches `ft_transfer` to the NEAR token contract.
5. The `ft_transfer` call panics (e.g., the token contract has a non-standard guard that rejects the transfer).
6. `fin_transfer_send_tokens_callback` is invoked. `is_ft_transfer_call = false`, so `is_refund_required` returns `false` without reading the promise result.
7. The callback enters the "success" branch: mints/transfers the fee to the relayer, emits `FinTransferEvent`.
8. The transfer ID remains in `finalised_transfers`. Any retry of `fin_transfer` with the same proof panics with `ERR_TRANSFER_ALREADY_FINALISED`.
9. The user's USDC is permanently stuck in the bridge contract; the relayer collected its fee.

        require!(
