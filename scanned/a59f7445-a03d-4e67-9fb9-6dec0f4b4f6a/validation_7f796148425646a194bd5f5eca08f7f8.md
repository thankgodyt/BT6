### Title
Unrestricted `log_metadata` Allows MPC Signing of Arbitrary Token Metadata — (File: `near/omni-bridge/src/lib.rs`)

---

### Summary

The `log_metadata` function is publicly callable by any unprivileged user with any arbitrary `token_id`. The bridge fetches metadata from the caller-supplied token contract and has the MPC signer sign it, without verifying that the token is registered or trusted in the bridge. This is the direct analog of the iframe CSP finding: just as the wallet accepted data from any external iframe source without restricting origins, the bridge accepts metadata from any external NEAR token contract without restricting which contracts are trusted sources.

---

### Finding Description

`log_metadata` in `near/omni-bridge/src/lib.rs` carries only a `#[pause(except(roles(Role::DAO)))]` decorator — no role restriction, no allowlist check: [1](#0-0) 

The callback `log_metadata_callback` validates only that `name` and `symbol` are non-empty, then immediately signs the payload with the MPC signer and emits a `LogMetadataEvent`: [2](#0-1) 

There is no check that the provided `token_id` is:
- Present in `token_id_to_address` or `token_address_to_id`
- A member of `deployed_tokens` or `deployed_tokens_v2`
- Otherwise a known/trusted bridge token

Notably, the contract already defines a `Role::MetadataManager` role: [3](#0-2) 

This role exists but is never applied to `log_metadata`, indicating the restriction was intended but omitted.

The signed `MetadataPayload` includes the caller-supplied `token_id` as the `token` field: [4](#0-3) 

The MPC then signs a keccak256 hash of this payload and the result is broadcast as a `LogMetadataEvent` consumed by relayers on foreign chains to bind or deploy tokens.

---

### Impact Explanation

An attacker deploys a malicious NEAR token contract returning crafted metadata (e.g., `name="USD Coin"`, `symbol="USDC"`, `decimals=6`) and calls `log_metadata` with it. The bridge produces a valid MPC-signed `LogMetadataEvent` for the malicious token. Relayers pick up this event and can use it on foreign chains to deploy or bind a token that carries the same human-readable metadata as a legitimate bridged asset. This constitutes **token metadata binding confusion**: the bridge's cross-chain token registry can be polluted with attacker-controlled, MPC-authenticated metadata entries, enabling users to be directed toward malicious tokens that appear identical to legitimate ones, resulting in loss of bridged funds.

---

### Likelihood Explanation

The entry path requires only:
1. Deploying a standard NEAR NEP-141 token contract with crafted metadata (trivial, permissionless on NEAR).
2. Calling the public `log_metadata` function on the bridge with the malicious token's account ID.

No privileged role, no leaked key, no validator collusion is needed. The bridge is not paused in normal operation. Likelihood: **Medium**.

---

### Recommendation

Add a registry check at the start of `log_metadata` to ensure the token is already registered in the bridge before its metadata is signed:

```rust
#[pause(except(roles(Role::DAO)))]
pub fn log_metadata(&self, token_id: &AccountId) -> Promise {
    require!(
        self.token_address_to_id.contains_key(&OmniAddress::Near(token_id.clone())),
        BridgeError::TokenNotFound.as_ref()
    );
    // ... existing logic
}
```

Alternatively, gate the function with the already-defined `Role::MetadataManager` role so only trusted operators can trigger MPC signing of token metadata.

---

### Proof of Concept

1. Attacker deploys `fake-usdc.attacker.near` — a valid NEP-141 contract whose `ft_metadata()` returns `{name: "USD Coin", symbol: "USDC", decimals: 6}`.
2. Attacker calls `omni-bridge.near::log_metadata("fake-usdc.attacker.near")` (public, no role required).
3. Bridge calls `fake-usdc.attacker.near::ft_metadata()`, receives the crafted metadata.
4. `log_metadata_callback` passes the non-empty name/symbol check and constructs:
   ```
   MetadataPayload { token: "fake-usdc.attacker.near", name: "USD Coin", symbol: "USDC", decimals: 6 }
   ```
5. Bridge sends this payload to the MPC signer; MPC returns a valid signature.
6. Bridge emits `LogMetadataEvent { signature, metadata_payload }` — indistinguishable in structure from a legitimate metadata event.
7. Relayers forward this event to foreign chains. Foreign chain token deployment/binding logic processes the MPC-authenticated metadata and associates `"USD Coin" / "USDC"` with the attacker's NEAR account ID.
8. Users interacting with the foreign-chain token that appears to be USDC but is backed by `fake-usdc.attacker.near` lose funds when they attempt to bridge back, as the NEAR-side token is worthless.

    #[private]
    #[result_serializer(borsh)]
    pub fn log_metadata_callback(
        &self,
        #[callback] metadata: FungibleTokenMetadata,
        token_id: &AccountId,
    ) -> Promise {
        require!(
            !metadata.name.is_empty() && !metadata.symbol.is_empty(),
            BridgeError::InvalidMetadata.as_ref()
        );

        let metadata_payload = MetadataPayload {
            prefix: PayloadType::Metadata,
            token: token_id.to_string(),
            name: metadata.name,
            symbol: metadata.symbol,
            decimals: metadata.decimals,
        };

        let payload = near_sdk::env::keccak256_array(
            borsh::to_vec(&metadata_payload).near_expect(BridgeError::Borsh),
        );

        ext_signer::ext(self.mpc_signer.clone())
            .with_static_gas(MPC_SIGNING_GAS)
            .with_attached_deposit(env::attached_deposit())
            .sign(SignRequest {
                payload,
                path: SIGN_PATH.to_owned(),
                key_version: 0,
            })
            .then(
                Self::ext(env::current_account_id())
                    .with_static_gas(SIGN_LOG_METADATA_CALLBACK_GAS)
                    .sign_log_metadata_callback(metadata_payload),
            )
    }
