### Title
Reentrancy in `initTransfer1155` via Malicious ERC1155 Callback Allows Emitting `InitTransfer` Events Without Locking Tokens — (`File: evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

`OmniBridge.initTransfer1155` increments `currentOriginNonce` and then makes an external call to an untrusted ERC1155 token contract via `IERC1155.safeTransferFrom`. Because ERC1155's `safeTransferFrom` triggers an `onERC1155Received` callback on the recipient (the bridge itself), a malicious ERC1155 token can re-enter `initTransfer1155` during that external call. There is no `nonReentrant` guard. The re-entrant call increments the nonce again and emits a second `InitTransfer` event — without any tokens ever being locked. The NEAR side treats every emitted `InitTransfer` event as proof that tokens are held, so it releases bridged assets for both events, giving the attacker double (or more) the tokens for zero collateral.

---

### Finding Description

`initTransfer1155` follows this sequence:

1. `currentOriginNonce += 1` — nonce is incremented.
2. `IERC1155(tokenAddress).safeTransferFrom(msg.sender, address(this), tokenId, amount, "")` — **untrusted external call** to an arbitrary ERC1155 contract.
3. `emit BridgeTypes.InitTransfer(...)` — event emitted. [1](#0-0) 

The ERC1155 standard mandates that `safeTransferFrom` calls `onERC1155Received` on the recipient. Here the recipient is `address(this)` (the bridge). The bridge implements `IERC1155Receiver` and its `onERC1155Received` hook only checks `operator == address(this)` — but the malicious token's `safeTransferFrom` is free to call **any** function on the bridge before or instead of calling `onERC1155Received`. Specifically, it can call `bridge.initTransfer1155(...)` again. [2](#0-1) 

Because `currentOriginNonce` was already incremented in the outer call, the re-entrant call increments it again (to a fresh nonce) and proceeds to emit a second `InitTransfer` event. The malicious token's inner `safeTransferFrom` can return without transferring any tokens. Both the inner and outer calls then emit `InitTransfer` events — with distinct nonces — but zero tokens were ever locked in the bridge.

There is no `ReentrancyGuard` / `nonReentrant` modifier on `initTransfer1155`, and no whitelist restricting which ERC1155 tokens may be used. [3](#0-2) 

The CLAUDE.md security invariant states: *"State before external calls: Always mutate state (e.g. mark nonce used) before any external call. This is the primary reentrancy defense."* For `finTransfer` this is correctly applied — `completedTransfers[nonce] = true` is set before any token transfer, so re-entry with the same nonce fails. But for `initTransfer1155`, incrementing `currentOriginNonce` before the external call does **not** prevent re-entry — it only ensures the re-entrant call gets a fresh nonce, which is exactly what the attacker wants. [4](#0-3) 

The NEAR-side `fin_transfer_callback` accepts any `InitTransfer` proof whose `origin_nonce` has not been seen before. Since the two re-entrant events carry distinct nonces (e.g., 1 and 2), both are accepted as independent transfers and tokens are released twice. [5](#0-4) 

---

### Impact Explanation

**Critical.** The attacker emits N `InitTransfer` events (one per re-entrant depth) while locking zero tokens on the EVM side. The NEAR bridge treats each event as proof of a locked deposit and mints/releases the corresponding amount to the attacker's NEAR address. This is a direct theft of bridged funds from the NEAR-side liquidity pool. The stolen amount is bounded only by the NEAR-side token supply and the gas limit of the EVM transaction.

This violates the documented invariant: *"InitTransfer must only be emitted in a code path where tokens have already been burned/locked in the same transaction."* [6](#0-5) 

---

### Likelihood Explanation

**High.** `initTransfer1155` is a public, permissionless function. `logMetadata1155` (also permissionless) allows any ERC1155 token to be registered. An attacker needs only to:

1. Deploy a malicious ERC1155 contract whose `safeTransferFrom` re-enters `initTransfer1155`.
2. Call `logMetadata1155` to register it (optional, not required for the exploit).
3. Call `initTransfer1155` with the malicious token.

No admin access, no privileged role, no leaked keys, and no external dependency compromise is required. The attack is fully self-contained in a single transaction. [7](#0-6) 

---

### Recommendation

Add OpenZeppelin's `ReentrancyGuardUpgradeable` to `OmniBridge` and apply the `nonReentrant` modifier to both `initTransfer` and `initTransfer1155`:

```diff
 import {ReentrancyGuardUpgradeable} from
     "@openzeppelin/contracts-upgradeable/utils/ReentrancyGuardUpgradeable.sol";

 contract OmniBridge is
     UUPSUpgradeable,
     AccessControlUpgradeable,
     SelectivePausableUpgradable,
+    ReentrancyGuardUpgradeable,
     IERC1155Receiver
 {
     ...
     function initTransfer(...) external payable
+        nonReentrant
         whenNotPaused(PAUSED_INIT_TRANSFER) { ... }

     function initTransfer1155(...) external payable
+        nonReentrant
         whenNotPaused(PAUSED_INIT_TRANSFER) { ... }
```

Also add `nonReentrant` to `finTransfer` as defense-in-depth, even though its CEI ordering already prevents nonce replay.

### Proof of Concept

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import {IERC1155Receiver} from "@openzeppelin/contracts/token/ERC1155/IERC1155Receiver.sol";

interface IBridge {
    function initTransfer1155(
        address tokenAddress,
        uint256 tokenId,
        uint128 amount,
        uint128 fee,
        uint128 nativeFee,
        string calldata recipient,
        string calldata message
    ) external payable;
}

contract MaliciousERC1155 {
    IBridge public bridge;
    bool public reentrant = true;

    constructor(address _bridge) {
        bridge = IBridge(_bridge);
    }

    // Called by bridge.initTransfer1155 → safeTransferFrom
    function safeTransferFrom(
        address, address, uint256, uint256, bytes calldata
    ) external {
        if (reentrant) {
            reentrant = false; // prevent infinite loop
            // Re-enter: emit a second InitTransfer with nonce+1, no tokens locked
            bridge.initTransfer1155(
                address(this), 1, 100, 0, 0, "attacker.near", ""
            );
        }
        // Return without transferring any tokens.
        // Call onERC1155Received on bridge to satisfy the interface.
        IERC1155Receiver(msg.sender).onERC1155Received(
            address(this), address(this), 1, 100, ""
        );
    }

    // Minimal ERC1155 stubs
    function balanceOf(address, uint256) external pure returns (uint256) { return 1e18; }
    function isApprovedForAll(address, address) external pure returns (bool) { return true; }
    function supportsInterface(bytes4) external pure returns (bool) { return true; }
}

// Attack:
// 1. Deploy MaliciousERC1155(bridgeAddress)
// 2. Call bridge.initTransfer1155(malicious, 1, 100, 0, 0, "attacker.near", "")
// 3. Two InitTransfer events emitted (nonce 1 and nonce 2), zero tokens locked.
// 4. NEAR side releases 100 tokens twice to attacker.near.
