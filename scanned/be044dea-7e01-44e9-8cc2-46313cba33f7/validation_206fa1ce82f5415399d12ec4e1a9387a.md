### Title
Fee-on-Transfer Token Causes EVM Vault Undercollateralization and NEAR Over-Release - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

### Summary
`OmniBridge.sol`'s `initTransfer` uses the caller-supplied `amount` parameter directly in the emitted `InitTransfer` event without checking the actual balance received. For fee-on-transfer ERC20 tokens, the vault receives `amount - transferFee` but the event records `amount`. The NEAR bridge finalizes the full `amount` on the destination side, permanently draining the EVM vault relative to its NEAR-side obligations.

### Finding Description
In `initTransfer`, when the token is a plain ERC20 (not a bridge token or custom minter), the contract executes:

```solidity
IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
```

and then immediately emits:

```solidity
emit BridgeTypes.InitTransfer(msg.sender, tokenAddress, currentOriginNonce, amount, ...);
``` [1](#0-0) [2](#0-1) 

The `amount` in the event is the parameter passed by the caller, not the actual tokens received. No pre/post balance check is performed. For a fee-on-transfer token (e.g., USDT with fee enabled, or any deflationary ERC20), the vault receives `amount - transferFee` but the event asserts `amount` was locked.

On the NEAR side, `fin_transfer_callback` decodes the proven `InitTransfer` event and calls `unlock_tokens_if_needed` with the full `amount` from the event, then sends `amount - bridgeFee` tokens to the recipient: [3](#0-2) [4](#0-3) 

The `locked_tokens` map on NEAR tracks how many tokens the EVM vault is supposed to hold. Each `initTransfer` from EVM increments this by `amount`, but the vault only holds `amount - transferFee`. The discrepancy accumulates with every transfer. [5](#0-4) 

### Impact Explanation
Every `initTransfer` call with a fee-on-transfer token creates a deficit of `transferFee` tokens in the EVM vault. The NEAR bridge releases the full `amount` to the recipient, but the EVM contract only holds `amount - transferFee`. After N transfers, the EVM vault is short by `N * transferFee` tokens. When users later bridge back from NEAR to EVM, the EVM vault cannot fulfill all withdrawals — the last users to withdraw lose their funds permanently. This is a direct escrow mis-accounting leading to loss of bridged funds.

### Likelihood Explanation
USDT on Ethereum already has fee-on-transfer logic in its contract (the fee is currently set to 0, but can be activated by the USDT issuer at any time without any action from the bridge). USDT is a commonly bridged asset. Any future token added to the bridge that charges transfer fees would trigger this immediately. An unprivileged user only needs to call `initTransfer` with a fee-on-transfer token — no special role or privilege is required. [6](#0-5) 

### Recommendation
Use the balance-check pattern: record the contract's token balance before and after `safeTransferFrom`, and use the difference as the actual received amount in the event:

```solidity
uint256 balanceBefore = IERC20(tokenAddress).balanceOf(address(this));
IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
uint128 actualReceived = uint128(IERC20(tokenAddress).balanceOf(address(this)) - balanceBefore);
// use actualReceived instead of amount in the event and downstream logic
```

### Proof of Concept
1. A fee-on-transfer ERC20 token (e.g., USDT with fee = 1%) is supported by the bridge.
2. Attacker (or any user) calls `initTransfer(tokenAddress, 1000, 0, 0, nearRecipient, "")`.
3. `safeTransferFrom` moves 1000 tokens from the user, but the token contract deducts a 1% fee — the vault receives 990.
4. The event emits `amount = 1000`.
5. NEAR relayer proves the event; `fin_transfer_callback` releases 1000 tokens on NEAR to the recipient.
6. EVM vault now holds 990 but NEAR has released 1000 — a 10-token deficit per transfer.
7. After 100 such transfers, the EVM vault is short 1000 tokens. The 100th user to bridge back to EVM cannot withdraw. [7](#0-6) [8](#0-7)

    fn lock_tokens(
        &mut self,
        chain_kind: ChainKind,
        token_id: &AccountId,
        amount: u128,
    ) -> LockAction {
        let key = (chain_kind, token_id.clone());
        let Some(current_amount) = self.locked_tokens.get(&key) else {
            return LockAction::Unchanged;
        };
        let new_amount = current_amount
            .checked_add(amount)
            .near_expect(TokenLockError::LockedTokensOverflow);

        self.locked_tokens.insert(&key, &new_amount);

        LockAction::Locked {
            chain_kind,
            token_id: token_id.clone(),
            amount,
        }
