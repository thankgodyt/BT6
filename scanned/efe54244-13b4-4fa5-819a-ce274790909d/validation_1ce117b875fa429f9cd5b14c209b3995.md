### Title
ERC1155 `safeTransferFrom` in `finTransfer` Permanently Freezes Bridged Tokens When Recipient Is a Non-Receiver Contract - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

### Summary
`finTransfer` uses `IERC1155.safeTransferFrom` to deliver ERC1155 tokens to `payload.recipient`. If the recipient is a contract that does not implement `IERC1155Receiver`, the call reverts unconditionally. Because the recipient is embedded in the MPC-signed payload and cannot be changed, every subsequent relay attempt also reverts, permanently locking the ERC1155 tokens inside the bridge escrow with no user-accessible recovery path.

### Finding Description
In `OmniBridge.finTransfer`, the ERC1155 delivery branch is:

```solidity
IERC1155(multiToken.tokenAddress).safeTransferFrom(
    address(this),
    payload.recipient,
    multiToken.tokenId,
    payload.amount,
    ""
);
``` [1](#0-0) 

Per EIP-1155, `safeTransferFrom` calls `onERC1155Received` on the recipient when it is a contract and reverts if the selector is not returned correctly. Contracts that do not implement `IERC1155Receiver` (multisigs, DAOs, generic vaults, many DeFi protocols) will cause this call to revert every time.

The `completedTransfers[payload.destinationNonce] = true` write happens before the transfer: [2](#0-1) 

Because the entire transaction reverts when `safeTransferFrom` fails, the nonce is never durably consumed. However, the signed payload fixes `payload.recipient` — the MPC signature covers the recipient address: [3](#0-2) 

No alternative recipient can be substituted without a new MPC signature. There is no admin rescue function for locked ERC1155 tokens. The tokens are permanently frozen in the bridge.

By contrast, `initTransfer1155` also uses `safeTransferFrom` to pull tokens into the bridge: [4](#0-3) 

The bridge correctly implements `onERC1155Received` to accept that inbound call (gated to `operator == address(this)`): [5](#0-4) 

But no equivalent receiver guard exists for the outbound delivery in `finTransfer` — the recipient contract is entirely user-controlled and may not implement the interface.

### Impact Explanation
Any ERC1155 tokens bridged from EVM to NEAR and then back to an EVM contract address that does not implement `IERC1155Receiver` are permanently frozen inside `OmniBridge`. The user loses the full bridged amount with no on-chain recovery path. This is a permanent, irreversible loss of bridged funds — matching the critical impact class of permanent freezing of bridged assets.

### Likelihood Explanation
The scenario is realistic and requires no privileged access. A user bridging ERC1155 tokens to a Gnosis Safe multisig, a DAO treasury, a yield vault, or any other contract that does not implement `IERC1155Receiver` triggers the freeze. Such contracts are common recipients in DeFi. The user need only specify a contract address as the EVM recipient when initiating the return transfer on NEAR.

### Recommendation
Replace `safeTransferFrom` with `transferFrom` in the `finTransfer` ERC1155 delivery branch. `transferFrom` does not invoke `onERC1155Received` and therefore succeeds regardless of whether the recipient implements `IERC1155Receiver`, mirroring the fix recommended in the original report (use `transferFrom` instead of `safeTransferFrom` to avoid the receiver-callback requirement):

```solidity
// Before
IERC1155(multiToken.tokenAddress).safeTransferFrom(
    address(this), payload.recipient, multiToken.tokenId, payload.amount, ""
);

// After
IERC1155(multiToken.tokenAddress).transferFrom(
    address(this), payload.recipient, multiToken.tokenId, payload.amount
);
```

This is consistent with how ERC20 delivery in the same function already uses `safeTransfer` (which has no receiver-callback requirement) rather than a safe variant that could block on contract recipients.

### Proof of Concept
1. Deploy a minimal contract `NoReceiver` that does **not** implement `IERC1155Receiver`.
2. User holds ERC1155 token `T` on EVM. User calls `initTransfer1155(T, tokenId, amount, ...)` specifying `NoReceiver`'s address as the NEAR-side recipient string that maps back to an EVM address.
3. ERC1155 tokens are locked in `OmniBridge`. NEAR side mints wrapped tokens.
4. User initiates return transfer on NEAR, specifying `NoReceiver` as the EVM recipient. MPC signs a `TransferMessagePayload` with `recipient = address(NoReceiver)` and `tokenAddress = deterministicAddress(T, tokenId)`.
5. Relayer calls `finTransfer(signature, payload)` on EVM.
6. `finTransfer` reaches the ERC1155 branch and calls `IERC1155(T).safeTransferFrom(bridge, NoReceiver, tokenId, amount, "")`.
7. The ERC1155 token calls `NoReceiver.onERC1155Received(...)` — `NoReceiver` has no such function → revert.
8. The entire transaction reverts. `completedTransfers[nonce]` is not persisted.
9. Every subsequent relay attempt with the same signed payload reverts identically.
10. The ERC1155 tokens remain locked in `OmniBridge` forever with no user-accessible rescue. [1](#0-0)
