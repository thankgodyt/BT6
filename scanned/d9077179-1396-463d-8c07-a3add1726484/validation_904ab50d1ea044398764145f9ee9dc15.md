### Title
Permanently Un-Executable NEAR→Foreign Transfer Due to Missing Decimal-Normalization Guard at Transfer Creation — (`File: near/omni-bridge/src/lib.rs`)

### Summary

The NEAR bridge's `init_transfer` function validates only that `fee < amount`, but does not validate that the net amount after fee deduction survives decimal normalization (`normalize_amount(amount - fee, decimals) > 0`). When a user creates a transfer where `(amount - fee) < 10^(origin_decimals - decimals)`, the subsequent `sign_transfer` call will always panic with `InvalidAmountToTransfer`, and because no cancellation path exists, the user's tokens are permanently locked in the bridge contract.

### Finding Description

The NEAR bridge supports tokens whose on-chain NEAR representation uses more decimal places than the destination-chain representation (e.g., a token with `origin_decimals = 24` on NEAR bridging to an EVM token with `decimals = 18`). The bridge stores the raw NEAR-side amount in `TransferMessage.amount` and normalises it at signing time via `normalize_amount`, which performs floor division:

```rust
// near/omni-bridge/src/lib.rs  line 2784-2787
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

`sign_transfer` then enforces:

```rust
// near/omni-bridge/src/lib.rs  lines 475-485
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

However, `init_transfer` only checks:

```rust
// near/omni-bridge/src/lib.rs  lines 554-557
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```

There is no check that `normalize_amount(amount - fee, decimals) > 0`. A user can therefore create a transfer where `1 ≤ (amount - fee) < 10^(origin_decimals - decimals)`, which passes creation but always produces `amount_to_transfer = 0` at signing time.

Because `sign_transfer` panics before it ever calls the MPC signer, `sign_transfer_callback` is never reached, so `remove_transfer_message` is never called. `update_transfer_fee` only allows the fee to be *increased* (line 400: `fee.fee >= current_fee.fee`), so the user cannot widen the net amount. There is no `cancel_transfer` or refund path for NEAR-origin transfers. The transfer message and the locked tokens remain in the contract indefinitely.

### Impact Explanation

The user's tokens are locked in the NEAR bridge contract with no recovery mechanism. Every call to `sign_transfer` for that `transfer_id` will revert with `InvalidAmountToTransfer`. The transfer is permanently frozen. This constitutes **permanent freezing of bridged funds**, which falls squarely within the Critical impact scope.

### Likelihood Explanation

Any unprivileged user who calls `ft_transfer_call` → `init_transfer` with a `(amount - fee)` value below the decimal-normalization threshold triggers this condition. For tokens with a 6-decimal gap (e.g., 24 → 18), the threshold is 10^6 raw units; for a 2-decimal gap it is only 100 raw units. The condition is reachable without any special privilege, and the bridge frontend does not prevent it for all token/decimal combinations. Likelihood is **medium**.

### Recommendation

Add a normalization guard inside `init_transfer` (or `init_transfer_internal`) immediately after the fee check:

```rust
// After: require!(transfer_message.fee.fee < transfer_message.amount, ...)
// Add:
if let Some(token_address) = self.get_token_address(
    transfer_message.get_destination_chain(),
    self.get_token_id(&transfer_message.token),
) {
    if let Some(decimals) = self.token_decimals.get(&token_address) {
        require!(
            Self::normalize_amount(
                transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
                decimals,
            ) > 0,
            BridgeError::InvalidAmountToTransfer.as_ref()
        );
    }
}
```

Alternatively, add a `cancel_transfer` function that allows the original sender to reclaim locked tokens for transfers that have not yet been signed.

### Proof of Concept

Assume a token registered with `origin_decimals = 20`, `decimals = 18` (diff = 2, divisor = 100).

1. Alice calls `ft_transfer_call` with `amount = 150` and `fee = 100`.
2. `init_transfer` checks `100 < 150` → passes. Transfer is stored; 150 tokens are locked.
3. Relayer calls `sign_transfer` for Alice's `transfer_id`.
4. `amount_without_fee() = 150 - 100 = 50`.
5. `normalize_amount(50, {decimals:18, origin_decimals:20}) = 50 / 100 = 0`.
6. `require!(0 > 0, ...)` → **panics with `InvalidAmountToTransfer`**.
7. No callback fires; transfer message is never removed.
8. Alice's 150 tokens remain locked forever. `update_transfer_fee` cannot help because it only allows increasing the fee (which would make `amount - fee` even smaller). [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
