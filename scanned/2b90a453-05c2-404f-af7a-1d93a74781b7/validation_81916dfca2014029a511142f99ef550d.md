### Title
Unhandled `ft_transfer` Failure in `fin_transfer_send_tokens_callback` Causes Permanent Freezing of Bridged Funds — (`File: near/omni-bridge/src/lib.rs`)

### Summary
When finalizing an inbound transfer to a NEAR recipient with no message payload, the bridge uses `ft_transfer` (not `ft_transfer_call`) to deliver tokens. The callback `fin_transfer_send_tokens_callback` is invoked with `is_ft_transfer_call = false`, causing `is_refund_required` to unconditionally return `false` without inspecting the promise result. If `ft_transfer` fails for any reason, the bridge treats the delivery as successful: the transfer is permanently marked as finalised, locked-token accounting is updated, and the `FinTransferEvent` is emitted — but the recipient never receives their tokens.

### Finding Description

**Step 1 — Transfer is marked finalised before delivery.**
In `process_fin_transfer_to_near`, `add_fin_transfer` is called first, inserting the transfer ID into `finalised_transfers` before `send_tokens` is ever attempted. [1](#0-0) 

**Step 2 — `send_tokens` uses `ft_transfer` when `msg` is empty.**
When the transfer carries no message (the common case), `send_tokens` dispatches a plain `ft_transfer` call. [2](#0-1) 

**Step 3 — Callback is registered with `is_ft_transfer_call = false`.**
The callback argument `!msg.is_empty()` evaluates to `false` for message-less transfers. [3](#0-2) 

**Step 4 — `is_refund_required(false)` never inspects the promise result.**
When `is_ft_transfer_call` is `false`, the function returns `false` unconditionally, bypassing any check of whether the preceding `ft_transfer` promise succeeded or failed. [4](#0-3) 

**Step 5 — Callback always takes the "success" path.**
Because `is_refund_required` returns `false`, `fin_transfer_send_tokens_callback` proceeds to emit `FinTransferEvent` and pay the fee — regardless of whether the recipient actually received tokens. [5](#0-4) 

The refund/recovery path (`remove_fin_transfer`, `revert_lock_actions`) is never reached, so the transfer ID stays in `finalised_transfers` permanently with no replay possible. [6](#0-5) 

### Impact Explanation
If `ft_transfer` fails (token contract paused, custom transfer logic rejection, gas exhaustion, or any panic in the token contract), the outcome is:
- Transfer permanently finalised — cannot be re-submitted.
- Locked tokens on the origin chain are unlocked (accounting updated as if delivery succeeded).
- `FinTransferEvent` emitted — origin-chain state considers the transfer complete.
- Recipient receives nothing; tokens are frozen inside the bridge contract with no recovery path.

This is a permanent freezing of bridged funds, matching the critical impact scope.

### Likelihood Explanation
The trigger requires `ft_transfer` to fail after storage registration is confirmed. Realistic triggers include:
- A bridged token contract with a pause mechanism (common in DeFi tokens) being paused between proof submission and delivery.
- A token contract with custom `ft_transfer` logic that rejects transfers under certain conditions (e.g., blacklisting, transfer limits).
- Gas exhaustion if `FT_TRANSFER_GAS` is insufficient for a particular token's implementation.

Any user who initiates a foreign-to-NEAR transfer with no message (the default path) is exposed. The attacker does not need special privileges; they only need to be the recipient of a transfer involving a token whose `ft_transfer` can fail.

### Recommendation
In `fin_transfer_send_tokens_callback`, always inspect the promise result regardless of `is_ft_transfer_call`. When the preceding `ft_transfer` promise fails (i.e., `env::promise_result(0)` is `Failed`), execute the same recovery path as the `ft_transfer_call` refund: call `revert_lock_actions`, call `remove_fin_transfer`, and emit `FailedFinTransferEvent`. This mirrors the existing recovery logic already present for the `ft_transfer_call` case.

### Proof of Concept

1. Register a NEP-141 token with the bridge that has a pause mechanism.
2. Initiate a transfer from Ethereum to a NEAR account with no message payload.
3. Relayer submits the proof via `fin_transfer`.
4. Before the scheduled `ft_transfer` executes, the token admin pauses the token contract.
5. `ft_transfer` panics; the NEAR promise fails.
6. `fin_transfer_send_tokens_callback` is invoked with `is_ft_transfer_call = false`.
7. `is_refund_required(false)` returns `false` without reading the promise result.
8. Callback emits `FinTransferEvent` and pays the relayer fee.
9. The transfer ID remains in `finalised_transfers`; the recipient's tokens are permanently frozen in the bridge. [4](#0-3) [7](#0-6) [2](#0-1)

                        // The amount can be zero if the `ft_on_transfer` in the receiver contract returns an amount instead of `0`, or if it panics.

                        // Unexpected case: don't refund
                        false
                    }
                }
                // Unexpected case: don't refund
                Err(_) => false,
            }
        } else {
            // Not ft_transfer_call: don't refund
            false
