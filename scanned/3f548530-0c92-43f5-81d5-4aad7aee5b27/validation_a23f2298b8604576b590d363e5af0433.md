### Title
Trusted Relayer Can Obtain Multiple MPC Signatures for the Same Non-Zero-Fee Transfer with Different Fee Recipients, Enabling Fee Theft — (`near/omni-bridge/src/lib.rs`)

### Summary

`sign_transfer` does not mark a transfer as "signed" or remove it from `pending_transfers` when the fee is non-zero. `sign_transfer_callback` only removes the transfer when `fee.is_zero()`. This allows a trusted relayer to call `sign_transfer` repeatedly for the same `transfer_id` with different `fee_recipient` values, causing the MPC to produce multiple distinct valid signatures for the same transfer — violating the invariant that the MPC should sign at most one payload per transfer.

### Finding Description

In `sign_transfer` (lines 447–521), the function:

1. Reads the transfer from `pending_transfers` via `get_transfer_message` [1](#0-0) 
2. Builds a `TransferMessagePayload` embedding the caller-supplied `fee_recipient` [2](#0-1) 
3. Hashes and submits the payload to the MPC signer [3](#0-2) 
4. Does **not** remove or lock the transfer before the async MPC call

In `sign_transfer_callback` (lines 648–668), the transfer is only removed when `fee.is_zero()`:

```rust
if fee.is_zero() {
    self.remove_transfer_message(message_payload.transfer_id);
}
``` [4](#0-3) 

For any transfer with a non-zero fee, the entry persists in `pending_transfers` after signing. There is no "already signed" flag, no lock, and no idempotence guard. A trusted relayer can therefore call `sign_transfer` a second (or third) time with a different `fee_recipient`, and the MPC will sign a completely different payload hash — producing two valid, distinct signatures for the same `transfer_id`.

### Impact Explanation

Two valid MPC signatures exist for the same transfer but with different `fee_recipient` fields. The destination chain's replay protection (nonce-based) prevents both from being finalized, but the attacker controls which one is submitted. By submitting the signature with `fee_recipient = attacker_account`, the attacker claims the fee on the destination chain instead of the legitimate relayer. This is direct fee mis-accounting: the user's fee escrow is consumed correctly on NEAR, but the fee is paid to an unauthorized recipient on the destination chain.

### Likelihood Explanation

The preconditions are:
- A non-zero fee transfer (common in production)
- A trusted relayer (required by `#[trusted_relayer]` on `sign_transfer`)

A trusted relayer who turns malicious — or a compromised relayer key — can execute this with two sequential transactions. No special timing or front-running is required; the relayer controls both signing calls and the submission to the destination chain. The attack is fully deterministic and locally reproducible on unmodified code.

### Recommendation

Before dispatching the MPC signing request, atomically mark the transfer as "signing in progress" (e.g., store a `signed: bool` flag in `TransferMessageStorage`) and reject subsequent `sign_transfer` calls for the same `transfer_id` if the flag is set. Alternatively, remove the transfer from `pending_transfers` before the MPC call and re-insert it (with the signed `fee_recipient` locked in) only if the MPC call fails — mirroring the pattern used in `submit_transfer_to_utxo_chain_connector` which calls `remove_transfer_message` before the external call. [5](#0-4) 

### Proof of Concept

```
1. Deploy bridge; register trusted relayer; configure token + MPC mock.
2. User calls ft_transfer_call → init_transfer with fee = {fee: 100, native_fee: 0}.
   → transfer_id T is stored in pending_transfers.
3. Relayer calls sign_transfer(T, Some("relayer.near"), None).
   → MPC receives payload_A = keccak256(encode({..., fee_recipient: "relayer.near"}))
   → sign_transfer_callback fires; fee != 0 → transfer NOT removed.
   → SignTransferEvent emitted with fee_recipient = "relayer.near".
4. Relayer calls sign_transfer(T, Some("attacker.near"), None).
   → MPC receives payload_B = keccak256(encode({..., fee_recipient: "attacker.near"}))
   → sign_transfer_callback fires; fee != 0 → transfer still NOT removed.
   → SignTransferEvent emitted with fee_recipient = "attacker.near".
5. Assert: two SignTransferEvents exist for the same transfer_id with different
   fee_recipient values and different signatures — both cryptographically valid.
6. Attacker submits signature_B to destination chain → fee paid to "attacker.near".
```

The root cause is confirmed at:
- `sign_transfer` line 453 (reads transfer without locking) [1](#0-0) 
- `sign_transfer_callback` lines 656–658 (only removes when fee is zero) [4](#0-3)
