### Title
Dust Transfers Permanently Lock User Funds Due to Missing Pre-Validation of Normalized Amount - (File: near/omni-bridge/src/lib.rs)

### Summary

The `init_transfer` function accepts and locks user tokens without verifying that the normalized transfer amount (after decimal scaling) is greater than zero. When a user sends a "dust" amount smaller than the decimal scaling factor, their tokens are locked permanently in the bridge with no recovery path, because the subsequent `sign_transfer` call will always revert.

### Finding Description

The bridge normalizes token amounts between chains with different decimal precisions using floor division in `normalize_amount`:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [1](#0-0) 

For tokens with a large decimal gap (e.g., a NEAR-native token with `origin_decimals = 24` bridged to an EVM chain where `decimals = 18`, giving `diff_decimals = 6`), any transfer amount below `10^6` base units normalizes to zero.

The `init_transfer` function only validates that `fee < amount`, but never checks that `normalize_amount(amount - fee, decimals) > 0`:

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
``` [2](#0-1) 

The transfer message is then stored and the user's tokens are locked in the contract. Later, when a relayer calls `sign_transfer`, the zero-amount check fires and the call reverts:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee()...,
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
``` [3](#0-2) 

There is no `cancel_transfer` or user-initiated refund function in the contract. The pending transfer entry remains in `pending_transfers` indefinitely, and the locked tokens cannot be recovered.

### Impact Explanation

Any user who initiates a NEAR → foreign-chain transfer with a dust amount (below the decimal scaling threshold) will have their tokens **permanently frozen** in the `omni-bridge` contract. The transfer can never be signed or finalized, and no refund path exists. This satisfies the "permanent freezing of bridged funds" impact criterion.

### Likelihood Explanation

This is realistically triggered by any unprivileged user who:
- Bridges a token with a non-trivial decimal gap (e.g., 24 → 18, common for NEAR-native tokens going to EVM)
- Sends an amount below the scaling threshold (e.e., fewer than 1,000,000 yocto-units for a 6-decimal gap)

No attacker action is required; a well-meaning user making a small test transfer or a UI rounding error is sufficient. The `ft_transfer_call` entry point is fully public.

### Recommendation

Add a pre-validation check inside `init_transfer` (or at the start of `init_transfer_internal`) that computes `normalize_amount(amount - fee, decimals)` and requires it to be greater than zero before locking the user's tokens. This mirrors the guard already present in `sign_transfer` but must be enforced earlier, at deposit time, to prevent irrecoverable locking.

### Proof of Concept

1. A token is registered with `origin_decimals = 24` on NEAR and `decimals = 18` on Ethereum (scaling factor = `10^6`).
2. User calls `ft_transfer_call` on the token contract with `amount = 500_000` (below `10^6`) and `fee = 0`, targeting the bridge with an `InitTransfer` message to an Ethereum recipient.
3. `init_transfer` passes the `fee < amount` check and stores the `TransferMessage`, locking 500,000 base units in the bridge.
4. A trusted relayer calls `sign_transfer` for this transfer ID.
5. `normalize_amount(500_000, Decimals { origin_decimals: 24, decimals: 18 })` returns `500_000 / 1_000_000 = 0`.
6. The `require!(amount_to_transfer > 0, ...)` check panics, reverting the call.
7. The relayer cannot sign the transfer; no other path exists to release the user's 500,000 tokens. They are permanently locked. [4](#0-3) [3](#0-2) [1](#0-0)
