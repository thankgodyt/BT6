### Title
Missing `nativeFee` Withdrawal Function Permanently Locks Collected ETH — (`File: evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

`OmniBridge.initTransfer()` collects a `nativeFee` in ETH from every bridge user, retaining it in the contract's balance. No function exists anywhere in `OmniBridge.sol` or `OmniBridgeWormhole.sol` to withdraw or claim these accumulated fees. The `PayloadType.ClaimNativeFee` enum entry in `BridgeTypes.sol` confirms the feature was intended but never implemented. All `nativeFee` ETH paid by users is permanently locked.

---

### Finding Description

In `OmniBridge.initTransfer()`, the caller must supply `msg.value` covering both the bridged `amount` (for native ETH transfers) and a `nativeFee`:

- For native ETH: `extensionValue = msg.value - amount - nativeFee` [1](#0-0) 
- For ERC-20: `extensionValue = msg.value - nativeFee` [2](#0-1) 

Only `extensionValue` is forwarded (to Wormhole in `OmniBridgeWormhole`, or rejected if non-zero in the base contract). The `nativeFee` portion is never forwarded — it stays in the contract. [3](#0-2) 

The contract has a bare `receive()` function that also allows arbitrary ETH to accumulate: [4](#0-3) 

Searching the entire contract surface (`OmniBridge.sol`, `OmniBridgeWormhole.sol`, `HlBridgeToken.sol`) reveals **no function** with a signature resembling `withdrawNativeFee`, `claimFee`, `rescueETH`, or any equivalent. There is no admin-gated ETH withdrawal path.

Critically, `BridgeTypes.sol` defines a `PayloadType` enum with a `ClaimNativeFee` variant at index 2, proving the protocol designers anticipated this claim flow but it was never implemented in the contract: [5](#0-4) 

---

### Impact Explanation

Every call to `initTransfer` or `initTransfer1155` with a non-zero `nativeFee` permanently locks that ETH in the `OmniBridge` contract. There is no owner, admin, or protocol-level function to recover it. This constitutes **fee mis-accounting** (collected fees can never be disbursed) and **permanent freezing** of ETH that users paid as bridge fees. Over the lifetime of the bridge, this accumulates to a material loss of ETH for the protocol and its relayers.

---

### Likelihood Explanation

Every bridge user who pays a non-zero `nativeFee` triggers this. The `nativeFee` parameter is a standard part of the `initTransfer` interface and is expected to be non-zero in normal operation (it is the fee paid to incentivize relayers). This is not an edge case — it is the normal operating path for every transfer.

---

### Recommendation

Add an `onlyRole(DEFAULT_ADMIN_ROLE)`-gated withdrawal function to `OmniBridge.sol`, for example:

```solidity
function withdrawNativeFees(address payable recipient, uint256 amount)
    external
    onlyRole(DEFAULT_ADMIN_ROLE)
{
    (bool success, ) = recipient.call{value: amount}("");
    if (!success) revert FailedToSendEther();
}
```

This mirrors the remediation described for `BazaarManagerBlast` and completes the `PayloadType.ClaimNativeFee` intent already declared in `BridgeTypes.sol`. [6](#0-5) 

---

### Proof of Concept

1. Alice calls `OmniBridge.initTransfer(USDC, 1000e6, 0, 1e15, "near:alice.near", "")` sending `msg.value = 1e15` (the `nativeFee`). [7](#0-6) 
2. `extensionValue = 1e15 - 1e15 = 0`. The `nativeFee` of `1e15` wei stays in the contract.
3. In `OmniBridgeWormhole.initTransferExtension`, `_wormhole.publishMessage{value: 0}(...)` is called — Wormhole receives nothing. [3](#0-2) 
4. After thousands of such transfers, the contract holds a large ETH balance from accumulated `nativeFee` payments.
5. No function exists to withdraw it. The ETH is permanently locked. [4](#0-3)
