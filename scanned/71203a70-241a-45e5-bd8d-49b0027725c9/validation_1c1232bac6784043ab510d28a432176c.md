### Title
User Tokens Permanently Locked/Burned When Normalized Transfer Amount Rounds to Zero - (File: near/omni-bridge/src/lib.rs)

### Summary

When a user initiates a NEAR → Foreign chain transfer with an amount that, after fee subtraction, is smaller than the decimal normalization factor, their tokens are permanently locked or burned. The zero-amount check exists only in `sign_transfer` — after the tokens are already irrecoverably committed in `init_transfer_internal`.

### Finding Description

`normalize_amount` performs floor division to reduce a NEAR-precision amount to the destination chain's lower precision:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [1](#0-0) 

If `amount_without_fee < 10^(origin_decimals - decimals)`, this returns `0`.

The zero-amount guard exists only in `sign_transfer`, which is called in a **separate, later transaction** by a trusted relayer:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
``` [2](#0-1) 

However, by the time `sign_transfer` is called, the user's tokens have already been locked or burned in `init_transfer_internal` — a prior, committed transaction:

```rust
self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
self.lock_tokens_if_needed(
    transfer_message.get_destination_chain(),
    &token_id,
    transfer_message.amount.0,
);
``` [3](#0-2) 

`init_transfer` only validates `fee < amount`, with no check that `normalize_amount(amount_without_fee) > 0`:

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
``` [4](#0-3) 

When `sign_transfer` panics, the transfer message remains in `pending_transfers` and there is no cancel or refund path. The tokens are permanently lost.

The existing code comment acknowledges dust loss for remainders but does not address the total-loss case where the entire `amount_without_fee` normalizes to zero:

```rust
/// Uses floor division — any sub-unit remainder ("dust") is truncated and not transferred
/// to the destination chain. When fee > 0, dust is absorbed into the fee via `claim_fee`.
/// When fee = 0, dust stays locked/burned. See SECURITY.md for details.
``` [5](#0-4) 

### Impact Explanation

A user's entire bridged token amount is permanently locked in the escrow (for native tokens) or burned (for deployed bridge tokens) with no recovery path. This is a direct, irreversible loss of bridged funds — matching the Critical impact category of escrow mis-accounting and decimal/normalization abuse that changes user balances.

### Likelihood Explanation

Any token registered with `origin_decimals > decimals` is affected. For example, a token with `origin_decimals = 24` and `decimals = 18` (diff = 6) loses all tokens when `amount_without_fee < 1_000_000` base units. A token with `origin_decimals = 18` and `decimals = 6` (diff = 12) loses all tokens when `amount_without_fee < 1_000_000_000_000`. These thresholds are realistic for low-value or dust transfers. No special privilege is required — any bridge user can trigger this by calling `ft_transfer_call` with a qualifying small amount.

### Recommendation

Add a normalization check inside `init_transfer` (or `init_transfer_internal`) **before** locking or burning tokens. Retrieve the destination token's `Decimals` at `init_transfer` time and verify:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

This mirrors the guard already present in `sign_transfer` but places it at the correct point — before the irreversible lock/burn.

### Proof of Concept

1. A token is registered with `origin_decimals = 24`, `decimals = 18` (normalization factor = 10^6).
2. User calls `ft_transfer_call` on the token contract with `amount = 500_000`, `fee = 0`, targeting an EVM recipient.
3. `init_transfer` passes: `fee (0) < amount (500_000)` ✓. Tokens are burned via `burn_tokens_if_needed`.
4. Transfer message is stored in `pending_transfers`.
5. Trusted relayer calls `sign_transfer` for this transfer.
6. `normalize_amount(500_000, {origin: 24, dest: 18}) = 500_000 / 1_000_000 = 0`.
7. `require!(amount_to_transfer > 0)` panics — `sign_transfer` reverts.
8. The transfer message remains in `pending_transfers`. There is no cancel function.
9. The user's 500,000 base-unit tokens are permanently burned with no assets received on any chain.
