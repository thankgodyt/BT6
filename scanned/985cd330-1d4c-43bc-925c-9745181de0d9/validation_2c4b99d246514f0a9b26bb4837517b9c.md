### Title
Bridged Funds Permanently Locked When Transfer Amount Normalizes to Zero - (`near/omni-bridge/src/lib.rs`)

### Summary

`init_transfer` (via `ft_on_transfer`) accepts any token amount greater than the fee with no minimum check, but `sign_transfer` enforces an implicit minimum by requiring `normalize_amount(amount - fee) > 0`. For tokens with a large decimal difference between NEAR and the destination chain (e.g., `origin_decimals = 24`, `decimals = 18`), any bridged amount below the normalization factor (10^6 in this example) will cause `sign_transfer` to permanently revert with `ERR_INVALID_AMOUNT_TO_TRANSFER`. Since there is no cancel or refund mechanism for pending transfers, the tokens are permanently locked or burned on NEAR with no recovery path.

### Finding Description

**Root cause — `init_transfer` (no minimum):**

`init_transfer` in `near/omni-bridge/src/lib.rs` only validates that `fee < amount`:

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```

It then immediately burns or locks the tokens via `init_transfer_internal`:

```rust
self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
self.lock_tokens_if_needed(...);
```

**Root cause — `sign_transfer` (implicit minimum):**

`sign_transfer` normalizes the amount for the destination chain using floor division:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

`normalize_amount` divides by `10^(origin_decimals - decimals)`:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

For a token registered with `origin_decimals = 24` and `decimals = 18`, the divisor is `10^6`. Any `amount - fee < 1_000_000` normalizes to `0`, causing `sign_transfer` to always revert.

**No recovery path:**

There is no `cancel_transfer` or `refund_transfer` function. The transfer remains in `pending_transfers` indefinitely, and the tokens are already burned or locked.

### Impact Explanation

A user who bridges a small amount of a token with a large decimal difference (e.g., a NEAR-native token with 24 decimals bridged to an EVM chain where it is represented with 18 decimals) will have their tokens permanently burned or locked on NEAR with no way to recover them. The `sign_transfer` call will always revert with `ERR_INVALID_AMOUNT_TO_TRANSFER`, and no cancel mechanism exists.

This is a permanent, irrecoverable loss of bridged funds — matching the "permanent freezing of bridged funds" impact category.

### Likelihood Explanation

- NEAR tokens commonly use 24 decimals; EVM tokens commonly use 18 decimals. This 6-decimal gap is the standard configuration, giving a normalization factor of `10^6`.
- Any user bridging fewer than `10^6` base units (e.g., less than `0.000001` of a 24-decimal token) will trigger this.
- The user has no way to know this limit in advance because `init_transfer` accepts the transaction without error.
- No admin action or external condition is required — the user triggers this entirely through normal bridge usage.

### Recommendation

Add a minimum amount check in `init_transfer` (or `ft_on_transfer`) that ensures `normalize_amount(amount - fee) > 0` before accepting the transfer and burning/locking tokens. The check should use the registered `token_decimals` for the destination chain:

```rust
let amount_to_transfer = Self::normalize_amount(
    amount.0.checked_sub(init_transfer_msg.fee.0)
        .near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

Alternatively, implement a `cancel_transfer` function that allows the sender to reclaim tokens from a pending transfer that cannot be signed.

### Proof of Concept

1. A token is registered with `origin_decimals = 24` (NEAR) and `decimals = 18` (EVM). The normalization factor is `10^6`.
2. Alice calls `ft_transfer_call` with `amount = 500_000` and `fee = 0`. `init_transfer` accepts this (500_000 > 0, fee < amount). Alice's tokens are burned/locked.
3. A relayer calls `sign_transfer` for Alice's transfer. `normalize_amount(500_000, {decimals:18, origin_decimals:24}) = 500_000 / 1_000_000 = 0`. The `require!(amount_to_transfer > 0, ...)` check panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.
4. No `cancel_transfer` exists. Alice's 500_000 base units are permanently burned/locked on NEAR. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
