Looking at the `swap_migrated_token` function and the `ft_on_transfer` handler in the NEAR omni-bridge contract, I can identify a valid analog to the external report's vulnerability class (missing output validation in a swap operation leading to balance loss).

---

### Title
`swap_migrated_token` Executes Non-Atomic Burn-and-Mint with Detached Promise, Causing Permanent Token Loss on Mint Failure — (File: `near/omni-bridge/src/lib.rs`)

---

### Summary

The `swap_migrated_token` function burns old tokens and mints new tokens using `Promise::and()`, but the resulting promise is `.detach()`ed — the bridge never checks whether the swap succeeded. Because NEAR cross-contract calls have no atomicity guarantee, if `burn` succeeds but `mint` fails (e.g., the recipient is not registered in the new token contract), the old tokens are permanently destroyed without the user receiving new tokens. There is no callback, no refund path, and no minimum-output guard.

---

### Finding Description

When a user calls `ft_transfer_call` on the old (migrated) token with `msg = "SwapMigratedToken"`, the bridge's `ft_on_transfer` handler processes it as:

```rust
BridgeOnTransferMsg::SwapMigratedToken => {
    self.swap_migrated_token(sender_id, token_id, amount)
        .detach();
    PromiseOrPromiseIndexOrValue::Value(U128(0))
}
``` [1](#0-0) 

Returning `U128(0)` means the bridge retains all the old tokens — no refund to the sender. The swap promise is then `.detach()`ed, so the bridge never awaits or inspects the result.

Inside `swap_migrated_token`:

```rust
fn swap_migrated_token(&mut self, sender_id: AccountId, old_token: AccountId, amount: U128) -> Promise {
    let new_token = self.migrated_tokens.get(&old_token).near_expect(BridgeError::TokenNotMigrated);
    let burn = ext_token::ext(old_token).burn(amount);
    let mint = ext_token::ext(new_token).mint(sender_id, amount, None);
    burn.and(mint)
}
``` [2](#0-1) 

`burn` and `mint` are scheduled as independent cross-contract calls via `Promise::and()`. In NEAR, these execute in separate transactions with no atomicity guarantee. If `burn` succeeds but `mint` panics, the old tokens are permanently destroyed with no recourse.

The `OmniToken::mint` function (when `msg = None`) calls `self.token.internal_deposit(&account_id, amount.into())`: [3](#0-2) 

`internal_deposit` panics if `account_id` is not registered in the token contract. The `migrate_deployed_token` function only registers the bridge contract itself in the new token — not individual users: [4](#0-3) 

Any user who holds old tokens but has not previously registered in the new token contract will trigger this failure path.

---

### Impact Explanation

A user who holds old (migrated) tokens and attempts to swap them via `SwapMigratedToken` can permanently lose their entire token balance if they are not registered in the new token contract. The old tokens are burned from the bridge's balance (which received them via `ft_on_transfer` returning `U128(0)`), but the new tokens are never minted. The bridge has no mechanism to detect this failure or refund the user, resulting in permanent, irreversible loss of bridged funds on NEAR.

---

### Likelihood Explanation

`migrate_deployed_token` (DAO-only) registers only the bridge contract itself in the new token. Any user who holds old tokens but has not previously interacted with the new token contract (and thus is not storage-registered) will trigger this failure when attempting to swap. This is a realistic scenario for users who acquired old tokens before the migration was announced or who simply never registered in the new token.

---

### Recommendation

1. Replace `.detach()` with a proper callback that checks the result of `burn.and(mint)` and refunds the user (by minting back old tokens or returning them) if either call fails.
2. Alternatively, use a sequential approach: burn in the first call, then mint in a callback, and refund if the mint fails.
3. Or, ensure the user is registered in the new token before attempting the mint (e.g., by calling `storage_deposit` for the user as part of the swap flow).

---

### Proof of Concept

1. DAO calls `migrate_deployed_token(origin_chain, old_token, new_token)`.
2. User holds `amount` of `old_token` but has never registered in `new_token`.
3. User calls `old_token.ft_transfer_call(bridge, amount, "SwapMigratedToken")`.
4. Bridge's `ft_on_transfer` returns `U128(0)` — bridge retains all old tokens.
5. Bridge calls `swap_migrated_token(user, old_token, amount).
