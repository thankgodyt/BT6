### Title
Unchecked Empty/Invalid `recipient` String in `initTransfer` and `initTransfer1155` Causes Permanent Loss of Bridged Funds — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

### Summary
`OmniBridge.initTransfer` and `OmniBridge.initTransfer1155` accept a caller-supplied `string calldata recipient` with no validation that it is non-empty or parseable as a valid `OmniAddress`. A user who passes an empty string or a malformed address causes their tokens to be permanently burned/locked on EVM while the NEAR-side finalization fails to parse the recipient and cannot complete the transfer.

### Finding Description
`initTransfer` (lines 373–437) and `initTransfer1155` (lines 439–490) in `OmniBridge.sol` perform the following steps unconditionally:

1. Increment `currentOriginNonce`.
2. Burn or lock the caller's tokens (irreversible on-chain action).
3. Emit `InitTransfer` with the raw, unvalidated `recipient` string. [1](#0-0) 

The only input check present is `fee >= amount → revert InvalidFee()`. There is no check that `recipient` is non-empty, non-zero, or parseable as a valid `OmniAddress` (e.g., `"eth:0x..."`, `"near:alice.near"`). [2](#0-1) 

On the NEAR side, the prover parses the emitted `InitTransfer` event and calls `OmniAddress::from_str(recipient_str)`: [3](#0-2) 

`OmniAddress::from_str` for an empty string defaults to `("eth", "")` and attempts to parse `""` as an `H160`, which fails: [4](#0-3) 

The NEAR `fin_transfer` call panics, the transfer is never finalized, and the tokens burned/locked on EVM are unrecoverable. There is no refund or rescue path in the EVM contract.

The same pattern exists in `initTransfer1155`: [5](#0-4) 

This issue is **not** listed in `evm/SECURITY.md` as a known or accepted issue (unlike the analogous Solana finding which is explicitly acknowledged in `solana/SECURITY.md`): [6](#0-5) [7](#0-6) 

### Impact Explanation
Any user who calls `initTransfer` or `initTransfer1155` with `recipient = ""` (or any string that does not parse as a valid `OmniAddress`) permanently loses their bridged tokens. The EVM burn/lock is irreversible; the NEAR finalization fails; no recovery mechanism exists. This constitutes permanent freezing of bridged funds.

### Likelihood Explanation
The entry path is fully permissionless — any externally-owned account can call `initTransfer` directly. The scenario is reachable by user error (mistyped recipient), by a malicious actor self-harming to grief the protocol's accounting, or by a buggy integration that passes an empty string. The `OmniAddress` string format (`"chain:address"`) is non-obvious to EVM users unfamiliar with the NEAR bridge convention, making accidental misuse realistic.

### Recommendation
Add a non-empty recipient check in `initTransfer` and `initTransfer1155` before any token transfer occurs:

```solidity
if (bytes(recipient).length == 0) revert InvalidRecipient();
```

For stronger protection, validate that `recipient` contains a `:` separator and that the chain prefix is a recognized value before burning/locking tokens.

### Proof of Concept

1. User approves `OmniBridge` to spend 1000 USDC.
2. User calls:
   ```solidity
   OmniBridge.initTransfer(
       usdcAddress,
       1000,   // amount
       0,      // fee
       0,      // nativeFee
       "",     // recipient — empty string, no validation
       ""
   );
   ```
3. `BridgeToken.burn(msg.sender, 1000)` executes — tokens are destroyed.
4. `InitTransfer` event is emitted with `recipient = ""`.
5. NEAR prover parses the event; `OmniAddress::from_str("")` returns `Err(...)`.
6. NEAR `fin_transfer` panics; transfer is never finalized.
7. User's 1000 USDC are permanently lost with no recovery path. [1](#0-0) [4](#0-3)

# Security Notes

## Design Decisions (Non-Issues)

These patterns have been reviewed and confirmed as intentional. Do not flag or "fix" them.

- **Fee-on-transfer tokens not supported**: `initTransfer` emits the requested `amount`, not the actual received balance. Fee-on-transfer and rebasing tokens are intentionally unsupported
- **`logMetadata` and `deployToken` are permissionless**: Anyone can call `logMetadata` for any ERC20, and anyone can submit a valid MPC signature to `deployToken`. This is by design — the bridge is fully permissionless
- **`ENearProxy.burn` uses empty NEAR recipient**: `eNear.transferToNear(amount, "")` is intentional — `transferToNear` is a legacy method used purely as a burn mechanism. The actual NEAR recipient is tracked in the OmniBridge `InitTransfer` event
- **`deployToken` signature has no chain ID**: Metadata signatures are intentionally chain-agnostic — one NEAR-side signature deploys the same token on all EVM chains

## Known Issues

Low-severity items acknowledged but not yet addressed:

- **`addCustomToken` can overwrite existing mappings** (H-01): Admin-only function. No existence check — calling with an already-mapped `nearTokenId` silently overwrites `nearToEthToken`. Accepted as operational risk
- **`pause(flags)` replaces all flags** (H-02): `_pause(flags)` does full replacement, not bitwise OR. Calling `pause(PAUSED_INIT_TRANSFER)` when `PAUSED_FIN_TRANSFER` is set will unpause finTransfer. Use `pauseAll()` for emergencies
- **`BridgeToken.initialize` stores metadata redundantly** (L-01): `__ERC20_init(name_, symbol_)` writes to parent storage that is never read (getters are overridden). Minor gas waste on init
- **`require` strings instead of custom errors** (L-02): Several locations use `require` with string messages instead of custom errors (`OmniBridge.sol:150,204,556`, `SelectivePausableUpgradable.sol:100,107`, `ENearProxy.sol:56,76,86`)
- **`OmniBridgeWormhole` has no `__gap`** (L-04): Three storage variables with no gap array. Safe as a leaf contract but would need a gap if inherited from
- **`PayloadType.ClaimNativeFee` defined but unused** (L-05): Enum value 2 is never referenced. Native fees are recovered via `finTransfer` with `tokenAddress=address(0)`
