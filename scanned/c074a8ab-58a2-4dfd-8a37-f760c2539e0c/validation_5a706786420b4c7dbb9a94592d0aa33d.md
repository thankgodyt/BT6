### Title
Missing Pre-Transfer Normalization Check Causes Permanent Fund Loss for Sub-Unit Amounts — (File: `near/omni-bridge/src/lib.rs`)

### Summary

The NEAR bridge's `init_transfer` path burns or locks user tokens **before** validating that the transfer amount survives decimal normalization. When a user initiates a NEAR→EVM transfer with an amount smaller than the normalization factor (`10^(origin_decimals − decimals)`), the tokens are irreversibly consumed on NEAR but the transfer can never be signed, resulting in permanent fund loss with no recovery path.

### Finding Description

The bridge normalizes amounts when producing the MPC-signed payload for the destination chain. `normalize_amount` performs integer floor-division:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [1](#0-0) 

`sign_transfer` then enforces a post-normalization guard:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
``` [2](#0-1) 

However, by the time `sign_transfer` is called, `init_transfer_internal` has already **burned** deployed tokens or **locked** native tokens:

```rust
self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
self.lock_tokens_if_needed(
    transfer_message.get_destination_chain(),
    &token_id,
    transfer_message.amount.0,
);
``` [3](#0-2) 

The only pre-acceptance check in `init_transfer` is:

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
``` [4](#0-3) 

There is **no check** that `normalize_amount(amount − fee, decimals) > 0` before tokens are consumed. Because `sign_transfer` is restricted to trusted relayers and there is no `cancel_transfer` function, the user has no self-service recovery path once the tokens are burned/locked.

### Impact Explanation

For any token pair where `origin_decimals > decimals`, a user who sends fewer tokens than the normalization factor loses those tokens permanently:

- **Deployed tokens** (originated from another chain): burned on NEAR, unrecoverable.
- **Native NEAR tokens**: locked in the bridge; recoverable only via privileged DAO intervention (`set_locked_tokens`), which is not a guaranteed or timely remedy.

This is a direct, permanent loss of bridged funds triggered by a normal, unprivileged user action.

### Likelihood Explanation

The condition is reachable for any registered token pair with a decimal gap. Concrete examples:

| Origin decimals | Destination decimals | Normalization factor | Threshold amount |
|---|---|---|---|
| 24 (NEAR) | 6 (EVM stablecoin) | 10¹⁸ | < 0.000001 NEAR |
| 18 (EVM) | 6 (EVM stablecoin) | 10¹² | < 0.000001 ETH |

A user could trigger this accidentally (dust amounts, UI rounding) or be induced to do so by a malicious front-end. The bridge currently accepts and consumes the tokens without warning.

### Recommendation

Add a normalization guard inside `init_transfer` (or at the top of `init_transfer_internal`) **before** burning or locking tokens. Retrieve the token's `Decimals` record and assert:

```rust
let decimals = self.token_decimals.get(&token_address)
    .near_expect(BridgeError::TokenDecimalsNotFound);
require!(
    Self::normalize_amount(
        transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
        decimals,
    ) > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

This mirrors the existing guard in `sign_transfer` but places it at the point where the user's funds are still safe.

### Proof of Concept

1. A token is registered with `origin_decimals = 24`, `decimals = 6` (normalization factor = 10¹⁸).
2. User calls `ft_transfer_call` with `amount = 1` (1 yoctoNEAR), `fee = 0`.
3. `init_transfer` passes the only check: `0 < 1`. [4](#0-3) 
4. `init_transfer_internal` burns 1 yoctoNEAR and stores the transfer message. [3](#0-2) 
5. A trusted relayer calls `sign_transfer`.
6. `normalize_amount(1, Decimals{decimals:6, origin_decimals:24})` = `1 / 10¹⁸` = **0**. [1](#0-0) 
7. `require!(amount_to_transfer > 0, …)` panics; the transaction reverts. [5](#0-4) 
8. The user's 1 yoctoNEAR is permanently burned. No cancel or refund mechanism exists.
