### Title
Migration Drops Relayer Stake State, Causing Permanent Loss of Staked NEAR — (File: `near/omni-bridge/src/migrate.rs`)

### Summary
The `migrate()` function in the NEAR `omni-bridge` contract reads the old on-chain state into `OldState`, which includes `relayers` (a map of all relayer stakes and application records) and `relayer_config`. However, neither field is carried into the new `Contract` struct. After migration, all relayer stake records are silently discarded, permanently locking staked NEAR inside the contract with no recovery path.

### Finding Description

The `OldState` struct in `migrate.rs` explicitly captures both relayer-related fields that were part of the previous contract state: [1](#0-0) 

The `migrate()` function constructs the new `Contract` from `old_state`, but maps only 21 of the 23 fields — `old_state.relayers` and `old_state.relayer_config` are read from storage and then silently dropped: [2](#0-1) 

The new `Contract` struct (after `#[trusted_relayer]` macro expansion) does not include `relayers` or `relayer_config` as explicit fields: [3](#0-2) 

The `StorageKey` enum retains `_Relayers` with a leading underscore, indicating the old storage slot is deprecated and the macro uses its own internal keys — meaning the new contract's relayer state starts completely empty after migration: [4](#0-3) 

Relayer applicants stake NEAR (the default config requires 1,000 NEAR) by calling `apply_for_trusted_relayer`. Their stake is held inside the contract and recorded in `relayers`. After migration, the `relayers` map is gone from the new state. The staked NEAR remains locked in the contract's account balance with no reference to it, and no function can return it to the applicants.

### Impact Explanation

Every relayer applicant who staked NEAR before the migration permanently loses their staked funds. The default `stake_required` is 1,000 NEAR per relayer. With multiple active relayers, the total loss can be substantial. Additionally, all trusted-relayer status is reset, so previously authorized relayers are no longer recognized as trusted, disrupting bridge operations until relayers re-apply and re-stake.

### Likelihood Explanation

Medium. The migration must be triggered by the DAO (`#[private]` + `#[init(ignore_state)]`), so it requires a contract upgrade event. Contract upgrades are a routine operational action for the bridge. Any relayer who staked before an upgrade is affected without any action on their part.

### Recommendation

Carry `old_state.relayers` and `old_state.relayer_config` into the new state inside `migrate()`, analogous to how all other `LookupMap` fields are transferred. If the `#[trusted_relayer]` macro uses different internal storage keys, explicitly migrate the data entry-by-entry into the new storage layout, or expose a post-migration admin function to restore individual relayer records before the upgrade window closes.

### Proof of Concept

1. Relayer applicant calls `apply_for_trusted_relayer` with a 1,000 NEAR deposit. Their `RelayerState` is written into `self.relayers` under their account ID.
2. DAO deploys a new contract binary and calls `migrate()`.
3. `migrate()` deserializes `OldState` — `old_state.relayers` is populated with the applicant's record.
4. The new `Self { ... }` is constructed without `relayers` or `relayer_config`; `old_state.relayers` is dropped.
5. The new contract's trusted-relayer storage (managed by the `#[trusted_relayer]` macro) is empty.
6. The applicant calls `resign_trusted_relayer` or any stake-recovery function — it panics or returns nothing because their record no longer exists.
7. The 1,000 NEAR remains locked in the contract's balance permanently.
