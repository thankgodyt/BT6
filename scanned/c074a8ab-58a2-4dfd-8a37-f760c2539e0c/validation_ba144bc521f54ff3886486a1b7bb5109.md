### Title
Permanently Locked ETH (`nativeFee`) in `OmniBridge.sol` with No Withdrawal Mechanism — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

Every call to `initTransfer` or `initTransfer1155` on the EVM `OmniBridge` contract that includes a non-zero `nativeFee` permanently locks that ETH inside the contract. No admin or user withdrawal function exists to recover it.

---

### Finding Description

`OmniBridge.sol` accepts ETH via `initTransfer` and `initTransfer1155` as a `nativeFee` payment. In both functions the caller must supply `msg.value >= nativeFee`. The contract retains the full `msg.value` but only ever disburses `payload.amount` on `finTransfer` (for native-ETH transfers). The `nativeFee` portion is never forwarded to any address on the EVM side.

In `initTransfer` for an ERC-20 token transfer:

```
extensionValue = msg.value - nativeFee;   // == 0 when msg.value == nativeFee
``` [1](#0-0) 

`initTransferExtension` is called with `value = 0` (or reverts if `value != 0`), so the `nativeFee` ETH is simply absorbed by the contract with no further action. [2](#0-1) 

On `finTransfer`, only `payload.amount` is sent to the recipient; the `nativeFee` is never touched: [3](#0-2) 

The contract has a bare `receive()` fallback but zero withdrawal logic: [4](#0-3) 

The relayer is compensated on the NEAR side by minting wrapped-ETH tokens (`native_fee` amount) to the fee recipient in `fin_transfer_send_tokens_callback`: [5](#0-4) 

So the protocol design pays the relayer in wrapped tokens on NEAR, but the actual ETH `nativeFee` deposited on EVM is never disbursed and accumulates permanently in `OmniBridge.sol`. There is no `withdrawETH`, `rescueETH`, or any admin function to recover it. [6](#0-5) 

---

### Impact Explanation

Every `initTransfer` / `initTransfer1155` call with `nativeFee > 0` permanently removes that ETH from circulation by locking it in `OmniBridge.sol`. Over the lifetime of the bridge this accumulates to an unbounded amount of irretrievably frozen ETH. This constitutes permanent freezing of user funds with no recovery path, matching the critical/medium impact class of permanently locked bridged value.

---

### Likelihood Explanation

The `nativeFee` mechanism is the primary way EVM users pay relayers for cross-chain transfers. It is documented in the README as a standard transfer option: [7](#0-6) 

Any user who pays a non-zero `nativeFee` triggers the lock. This is a routine, expected usage path, making likelihood **High**.

---

### Recommendation

Add an admin-only ETH withdrawal function to `OmniBridge.sol`, for example:

```solidity
function withdrawETH(address payable recipient, uint256 amount)
    external
    onlyRole(DEFAULT_ADMIN_ROLE)
{
    (bool success, ) = recipient.call{value: amount}("");
    require(success, "ETH transfer failed");
}
```

Alternatively, if the design intent is that `nativeFee` ETH should be forwarded directly to a designated fee collector at the time of `initTransfer`, implement that forwarding inside `initTransfer` rather than leaving the ETH in the contract.

---

### Proof of Concept

1. Alice calls `initTransfer(usdcAddress, 1000e6, 10e6, 0.01 ether, "alice.near", "")` with `msg.value = 0.01 ether`.
2. `extensionValue = 0.01 ether - 0.01 ether = 0`. USDC is pulled from Alice. The `0.01 ether` stays in `OmniBridge`.
3. A relayer submits the proof on NEAR; `fin_transfer_send_tokens_callback` mints `0.01 ether` worth of wrapped-ETH tokens to the relayer on NEAR.
4. The `0.01 ether` in `OmniBridge.sol` is never sent anywhere. No function exists to retrieve it.
5. After 10,000 such transfers at `0.01 ether` each, `100 ETH` is permanently locked with no recovery mechanism. [8](#0-7)
