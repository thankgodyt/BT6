### Title
Lack of BTC/Zcash Address Normalization Causes Permanent Locking of Bridged UTXO Funds - (`near/omni-bridge/src/btc.rs`, `near/omni-types/src/lib.rs`)

### Summary

`OmniAddress::Btc` and `OmniAddress::Zcash` store recipient addresses as raw, unnormalized `String` values. The `PartialEq` and `Hash` implementations are derived from the raw string, making all comparisons and map lookups case-sensitive. When a user submits a BTC or Zcash address in non-canonical case (e.g., uppercase Bech32), the bridge stores it verbatim. The trusted relayer's BTC/Zcash connector, which normalizes addresses to lowercase per protocol convention, then supplies a lowercase `target_btc_address` in `submit_transfer_to_utxo_chain_connector`. The case-sensitive equality check fails unconditionally, and the pending transfer can never be finalized — permanently locking the user's bridged funds.

### Finding Description

`UTXOChainAddress` is defined as a plain `String`:

```rust
pub type UTXOChainAddress = String;
```

`OmniAddress` derives `PartialEq` and `Hash` from its inner types, so for the `Btc` and `Zcash` variants, equality and hashing are byte-for-byte string comparisons with no case folding:

```rust
#[near(serializers=[borsh])]
#[derive(Debug, Clone, Hash, PartialEq, Eq)]
pub enum OmniAddress {
    ...
    Btc(UTXOChainAddress),
    Zcash(UTXOChainAddress),
    ...
}
```

`OmniAddress::from_str` accepts the raw string without normalization:

```rust
"btc"   => Ok(Self::Btc(recipient.to_string())),
"zcash" => Ok(Self::Zcash(recipient.to_string())),
```

The stored address is compared against the relayer-supplied `target_btc_address` in `submit_transfer_to_utxo_chain_connector`:

```rust
if let Some(btc_address) = transfer.message.recipient.get_utxo_address() {
    if let TokenReceiverMessage::Withdraw { target_btc_address, .. } = message {
        require!(
            btc_address == target_btc_address,
            BridgeError::IncorrectTargetUtxoAddress.as_ref()
        );
```

`btc_address` is the raw `String` extracted from the stored `OmniAddress::Btc(...)`. `target_btc_address` is the string the BTC connector supplies, which follows the Bech32 standard of lowercase. If the user stored `"BC1QXXX..."` and the connector supplies `"bc1qxxx..."`, the `==` check fails every time. The transfer is never removed from `pending_transfers` and can never be finalized.

A secondary impact exists in the `FastTransfer` matching path. `FastTransfer::id()` is computed as `sha256(borsh(self))`, and `self` includes `recipient: OmniAddress`. If the fast relayer registered the fast transfer with `OmniAddress::Btc("bc1q...")` but the stored pending transfer has `OmniAddress::Btc("BC1Q...")`, `FastTransfer::from_transfer` produces a different ID, the `get_fast_transfer_status` lookup returns `None`, and the fast relayer's advanced funds are not reimbursed.

### Impact Explanation

A user who submits a BTC or Zcash recipient address in non-lowercase form (e.g., uppercase Bech32 `"BC1Q..."`) causes their bridged tokens to be permanently locked in the NEAR bridge contract. The trusted relayer's BTC/Zcash connector normalizes addresses to lowercase per Bech32 convention; the case-sensitive `require!` in `submit_transfer_to_utxo_chain_connector` then always fails, and no code path exists to recover or redirect the stuck transfer. This matches the "permanent freezing of bridged funds" criterion.

### Likelihood Explanation

Bech32 (BTC `bc1q...`, `bc1p...`) and Bech32m (Zcash `u1...`, `zs1...`) addresses are defined as lowercase by their respective BIPs/ZIPs, but the bridge imposes no such constraint. Any user who submits an address in uppercase or mixed case — whether by mistake, through a non-conforming wallet, or deliberately — triggers the lock. The bridge's own test suite acknowledges that `OmniAddress::Zcash(String)` accepts arbitrary strings without format validation. The BTC connector is expected to normalize to lowercase, making the mismatch systematic rather than incidental.

### Recommendation

Normalize BTC and Zcash addresses to lowercase at the point of ingestion — either in `OmniAddress::from_str` for the `"btc"` and `"zcash"` arms, or in `init_transfer` before constructing the `TransferMessage`. Apply the same normalization to the `target_btc_address` extracted from the relayer's `TokenReceiverMessage::Withdraw` before the equality check in `submit_transfer_to_utxo_chain_connector`.

### Proof of Concept

**Entry path (unprivileged user):**

1. User calls `ft_transfer_call` on the nBTC token with `msg` containing:
   ```json
   {"recipient": "btc:BC1QW508D6QEJXTDG4Y5R3ZARVARY0C5XW7KV8F3T4", "fee": "0", "native_token_fee": "0"}
   ```
2. `ft_on_transfer` → `init_transfer` stores `OmniAddress::Btc("BC1QW508D6QEJXTDG4Y5R3ZARVARY0C5XW7KV8F3T4")` in `pending_transfers`.
3. Trusted relayer calls `submit_transfer_to_utxo_chain_connector` with `msg`:
   ```json
   {"Withdraw": {"target_btc_address": "bc1qw508d6qejxtdg4y5r3zarvary0c5xw7kv8f3t4", ...}}
   ```
4. Inside `submit_transfer_to_utxo_chain_connector`:
   - `btc_address` = `"BC1QW508D6QEJXTDG4Y5R3ZARVARY0C5XW7KV8F3T4"` (from storage)
   - `target_btc_address` = `"bc1qw508d6qejxtdg4y5r3zarvary0c5xw7kv8f3t4"` (from relayer msg)
   - `require!(btc_address == target_btc_address, ...)` → **panics with `IncorrectTargetUtxoAddress`**
