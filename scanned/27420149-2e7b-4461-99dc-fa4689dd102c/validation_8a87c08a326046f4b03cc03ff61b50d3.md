### Title
Missing Zero-Address Validation for `nearBridgeDerivedAddress` in `initialize()` Enables Signature Verification Bypass — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

The `initialize()` function in `OmniBridge.sol` stores the `nearBridgeDerivedAddress_` parameter without validating it is non-zero. This address is the sole authority used to verify all inbound bridge signatures in `finTransfer()` and `deployToken()`. If the contract is deployed or redeployed (e.g., on a new network or protocol version) with `nearBridgeDerivedAddress_ = address(0)`, the ECDSA signature check degenerates: on OpenZeppelin ECDSA versions prior to 4.7.3, `ECDSA.recover()` can return `address(0)` for a crafted invalid signature, causing the equality check to pass and bypassing signature verification entirely.

---

### Finding Description

`OmniBridge.initialize()` accepts `nearBridgeDerivedAddress_` and writes it directly to storage with no zero-address guard:

```solidity
function initialize(
    address tokenImplementationAddress_,
    address nearBridgeDerivedAddress_,
    uint8 omniBridgeChainId_
) public initializer {
    tokenImplementationAddress = tokenImplementationAddress_;
    nearBridgeDerivedAddress = nearBridgeDerivedAddress_;   // ← no require(... != address(0))
    omniBridgeChainId = omniBridgeChainId_;
    ...
}
``` [1](#0-0) 

`nearBridgeDerivedAddress` is then used as the sole trusted signer in both public entry points:

```solidity
if (ECDSA.recover(hashed, signatureData) != nearBridgeDerivedAddress) {
    revert InvalidSignature();
}
``` [2](#0-1) [3](#0-2) 

The same gap exists in the admin setter, which also lacks a zero-address check:

```solidity
function setNearBridgeDerivedAddress(
    address nearBridgeDerivedAddress_
) external onlyRole(DEFAULT_ADMIN_ROLE) {
    nearBridgeDerivedAddress = nearBridgeDerivedAddress_;
}
``` [4](#0-3) 

On OpenZeppelin ECDSA versions prior to 4.7.3, `ECDSA.recover()` does not revert when the underlying `ecrecover` precompile returns `address(0)` (which it does for malformed/invalid signatures). It simply returns `address(0)`. If `nearBridgeDerivedAddress` is also `address(0)`, the comparison `address(0) != address(0)` evaluates to `false`, so the `revert InvalidSignature()` branch is never taken — signature verification is silently bypassed.

---

### Impact Explanation

An attacker who observes that the deployed contract has `nearBridgeDerivedAddress == address(0)` can:

1. Call `finTransfer()` with an arbitrary `TransferMessagePayload` (any recipient, any amount, any token) and a crafted invalid signature that causes `ECDSA.recover()` to return `address(0)`.
2. The signature check passes. The contract mints or transfers the specified token amount to the attacker-controlled recipient.
3. Repeat for any token registered in the bridge, draining or inflating supply at will.

Similarly, `deployToken()` can be called with a forged signature to register arbitrary token mappings, corrupting the bridge's token registry.

Impact: **Critical** — unauthorized minting of bridged tokens and unauthorized token deployment, directly matching the allowed impact scope (unauthorized minting, signer/prover verification bypass).

---

### Likelihood Explanation

The precondition is that `nearBridgeDerivedAddress` is `address(0)` at deployment. This is not attacker-controlled during normal operation, but it is a realistic risk during:

- First-time deployment on a new network where the derived address has not yet been computed.
- Redeployment after a protocol upgrade where initialization scripts are incomplete.
- Automated deployment pipelines that pass a placeholder zero address.

The original audit report for the analogous `Validator.sol` finding explicitly identifies redeployment on new networks or protocol versions as the realistic trigger. The same applies here. Likelihood is **Low** but non-negligible, and the consequence is catastrophic.

---

### Recommendation

Add a non-zero address check in `initialize()` and in `setNearBridgeDerivedAddress()`:

```solidity
function initialize(
    address tokenImplementationAddress_,
    address nearBridgeDerivedAddress_,
    uint8 omniBridgeChainId_
) public initializer {
    require(nearBridgeDerivedAddress_ != address(0), "Zero bridge address");
    require(tokenImplementationAddress_ != address(0), "Zero token impl");
    tokenImplementationAddress = tokenImplementationAddress_;
    nearBridgeDerivedAddress = nearBridgeDerivedAddress_;
    ...
}
```

Apply the same guard to `setNearBridgeDerivedAddress()`. Additionally, ensure the OpenZeppelin ECDSA library is at version ≥ 4.7.3, where `ECDSA.recover()` reverts rather than returning `address(0)` for invalid signatures, providing defense-in-depth.

---

### Proof of Concept

1. Deploy `OmniBridge` proxy and call `initialize(tokenImpl, address(0), chainId)` — no revert occurs. [1](#0-0) 

2. Construct a `TransferMessagePayload` with `recipient = attacker`, `amount = 1_000_000e18`, `tokenAddress = <any registered bridge token>`.

3. Craft a 65-byte signature of all zeros (or any bytes that cause the `ecrecover` precompile to return `address(0)`). On OZ ECDSA < 4.7.3, `ECDSA.recover(hashed, zeroSig)` returns `address(0)`.

4. Call `finTransfer(zeroSig, payload)`.

5. The check `ECDSA.recover(hashed, zeroSig) != nearBridgeDerivedAddress` evaluates to `address(0) != address(0)` → `false` → no revert. [3](#0-2) 

6. The contract proceeds to mint `1_000_000e18` tokens to the attacker. [5](#0-4)
