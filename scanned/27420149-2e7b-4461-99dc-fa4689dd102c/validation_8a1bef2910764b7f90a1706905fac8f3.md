### Title
`sign_transfer` Permanently Freezes Bridged Funds When Normalized Amount Rounds to Zero — (`near/omni-bridge/src/lib.rs`)

### Summary

When a user initiates a NEAR-originated transfer with an amount small enough that `normalize_amount(amount - fee, decimals)` floors to zero, the transfer is stored in `pending_transfers` with the user's tokens locked in the bridge contract. The only function that can progress the transfer — `sign_transfer` — unconditionally panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`. No cancel or refund path exists, so the tokens are permanently frozen.

### Finding Description

**Root cause — missing pre-validation in `init_transfer`:**

`init_transfer` enforces only that `fee.fee < amount`: [1](#0-0) 

It does **not** verify that `normalize_amount(amount - fee, decimals) > 0`. Tokens are immediately transferred to the bridge contract and the `TransferMessage` is stored in `pending_transfers`.

**The blocking check in `sign_transfer`:**

`sign_transfer` is the only function that can advance a NEAR-originated pending transfer. It computes: [2](#0-1) 

`normalize_amount` performs floor division: [3](#0-2) 

For a token with `origin_decimals = 24` (NEAR) and `decimals = 6` (EVM), the divisor is `10^18`. Any `amount_without_fee < 10^18` yoctoNEAR produces `amount_to_transfer = 0`, causing `sign_transfer` to panic on every call for that transfer.

**`amount_without_fee` definition:** [4](#0-3) 

**No recovery path exists.** The only ways `remove_transfer_message` is called are:
- Inside `sign_transfer_callback` (only reached if `sign_transfer` succeeds — it never does here)
- Inside `claim_fee_callback` (requires a proof of finalization on the destination chain — impossible since the transfer was never signed)

There is no `cancel_transfer` or emergency-withdraw function.

**Exploit path:**

1. User calls `ft_transfer_call` on a NEAR token contract, routing to the bridge with `amount = X` where `0 < X < 10^(origin_decimals − decimals)` and `fee = 0`.
2. `init_transfer` passes the `fee < amount` check, stores the `TransferMessage`, and the tokens are held by the bridge.
3. Any trusted relayer calls `sign_transfer` for this transfer ID — it panics with `ERR_INVALID_AMOUNT_TO_TRANSFER` every time.
4. No finalization event is ever emitted on the destination chain, so `claim_fee` cannot be called.
5. The user's tokens are permanently locked.

### Impact Explanation

Bridged funds are permanently frozen. The threshold below which a transfer becomes unrecoverable depends on the decimal gap between origin and destination chains. For NEAR (24 decimals) → EVM (6 decimals), any transfer where `amount − fee < 10^18` yoctoNEAR is permanently stuck. For chains with a smaller decimal gap (e.g., NEAR → Solana with 9 decimals, diff = 15), the threshold is `10^15` yoctoNEAR = 0.001 NEAR. The locked amount is whatever the user sent; there is no admin escape hatch.

### Likelihood Explanation

Any unprivileged user can trigger this by calling `ft_transfer_call` with a sub-threshold amount. No special role or privileged key is required. The `init_transfer` validation does not prevent it.

### Recommendation

Add a pre-validation in `init_transfer` (or in `init_transfer_internal`) that computes the normalized amount and rejects the transfer before tokens are locked:

```rust
let token_address = self.get_token_address(
    transfer_message.get_destination_chain(),
    self.get_token_id(&transfer_message.token),
);
if let Some(addr) = token_address {
    if let Some(decimals) = self.token_decimals.get(&addr) {
        let normalized = Self::normalize_amount(
            transfer_message.amount_without_fee()
                .near_expect(BridgeError::InvalidFee),
            decimals,
        );
        require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
    }
}
```

This mirrors the check already present in `sign_transfer` and ensures the transfer is rejected at initiation rather than after tokens are locked.

### Proof of Concept

1. Deploy the bridge with a NEAR token mapped to an EVM token with `origin_decimals = 24`, `decimals = 6`.
2. Call `ft_transfer_call` with `amount = 10^17` (0.0000001 NEAR), `fee = 0`, valid EVM recipient.
3. Observe `InitTransferEvent` emitted — tokens are now held by the bridge.
4. Call `sign_transfer` for the resulting `transfer_id` from any trusted relayer.
5. Observe panic: `ERR_INVALID_AMOUNT_TO_TRANSFER`.
6. Repeat step 4 indefinitely — always panics.
7. Attempt `claim_fee` — fails because no finalization proof exists.
8. Tokens are permanently locked with no recovery path. [2](#0-1) [1](#0-0) [3](#0-2) [4](#0-3)
