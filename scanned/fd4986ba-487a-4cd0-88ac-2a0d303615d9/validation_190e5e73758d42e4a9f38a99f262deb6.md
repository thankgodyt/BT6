### Title
Pause Check Missing on `deploy_token` in Solana `bridge_token_factory` - (`solana/programs/bridge_token_factory/src/lib.rs`)

### Summary
The Solana `bridge_token_factory` program's `deploy_token` instruction does not check the `paused` flag in the program's `Config` account, unlike every other state-changing instruction in the same program and unlike the equivalent `deploy_token`/`deployToken` functions in the Starknet and EVM implementations. When an admin pauses the bridge (setting `ALL_PAUSED`), any holder of a previously obtained valid MPC-signed `DeployTokenPayload` can still call `deploy_token` on Solana, bypassing the intended emergency freeze.

### Finding Description

The Solana `bridge_token_factory` program defines a selective pause system using a bitmask stored in `Config.paused`. The pause constants are defined in `constants.rs`:

- `INIT_TRANSFER_PAUSED`
- `FINALIZE_TRANSFER_PAUSED`
- `ALL_PAUSED`

Every user-facing state-changing instruction checks the pause flag before proceeding:

- `init_transfer` checks `INIT_TRANSFER_PAUSED` [1](#0-0) 
- `init_transfer_sol` checks `INIT_TRANSFER_PAUSED` [2](#0-1) 
- `finalize_transfer` checks `FINALIZE_TRANSFER_PAUSED` [3](#0-2) 
- `finalize_transfer_sol` checks `FINALIZE_TRANSFER_PAUSED` [4](#0-3) 

However, `deploy_token` performs **no pause check whatsoever**:

```rust
pub fn deploy_token(
    ctx: Context<DeployToken>,
    data: SignedPayload<DeployTokenPayload>,
) -> Result<()> {
    msg!("Deploying token");
    data.verify_signature((), &ctx.accounts.common.config.derived_near_bridge_address)?;
    ctx.accounts.initialize_token_metadata(data.payload)?;
    Ok(())
}
``` [5](#0-4) 

The `pause` instruction sets `config.paused = ALL_PAUSED`, which is intended to freeze all bridge operations: [6](#0-5) 

The `Config` struct stores the `paused` bitmask: [7](#0-6) 

**Contrast with other chain implementations:**

The EVM `OmniBridge.sol` guards `deployToken` with `whenNotPaused(PAUSED_DEPLOY_TOKEN)`: [8](#0-7) 

The Starknet `omni_bridge.cairo` guards `deploy_token` with an explicit pause assertion: [9](#0-8) 

The Solana implementation is the only one missing this guard, and there is no `DEPLOY_TOKEN_PAUSED` bitmask constant defined at all in the Solana program.

### Impact Explanation

When the bridge admin triggers a pause (e.g., in response to a security incident), the intent is to freeze all bridge operations. Because `deploy_token` skips the pause check, any party holding a previously obtained valid MPC-signed `DeployTokenPayload` — which is publicly derivable from on-chain NEAR events emitted by `sign_log_metadata_callback` — can still call `deploy_token` on Solana while the bridge is fully paused.

This constitutes a **pause bypass** allowing an attacker to execute a deployer-equivalent action (registering a new token mapping and initializing token metadata on Solana) during an emergency freeze. A maliciously timed token deployment during a pause could:

1. Register a token mapping that the admin intended to block (e.g., for a token under active exploit).
2. Create an on-chain state that enables subsequent `finalize_transfer` calls once the bridge is unpaused, potentially enabling unauthorized minting of bridge tokens.

This matches the allowed impact scope: *"pause bypass that lets an attacker execute bridge, token, deployer, relayer, or admin-equivalent actions."*

### Likelihood Explanation

MPC-signed `DeployTokenPayload` messages are generated by the NEAR bridge and their signatures are emitted as public on-chain log events. Any observer can collect these signatures before a pause event. The attacker-controlled entry path is fully permissionless: call `deploy_token` on the Solana program with a previously collected valid signed payload. No admin compromise, key leak, or collusion is required — only a valid signature that was already publicly broadcast.

### Recommendation

Add a pause check to `deploy_token` in `solana/programs/bridge_token_factory/src/lib.rs`, consistent with the EVM and Starknet implementations. Introduce a `DEPLOY_TOKEN_PAUSED` bitmask constant in `constants.rs` and include it in `ALL_PAUSED`. Then guard the instruction:

```rust
pub fn deploy_token(
    ctx: Context<DeployToken>,
    data: SignedPayload<DeployTokenPayload>,
) -> Result<()> {
    require!(
        ctx.accounts.common.config.paused & DEPLOY_TOKEN_PAUSED == 0,
        error::ErrorCode::Paused
    );
    msg!("Deploying token");
    data.verify_signature((), &ctx.accounts.common.config.derived_near_bridge_address)?;
    ctx.accounts.initialize_token_metadata(data.payload)?;
    Ok(())
}
```

Also update `ALL_PAUSED` in `constants.rs` to include the new `DEPLOY_TOKEN_PAUSED` bit.

### Proof of Concept

1. Admin calls `pause` on the Solana `bridge_token_factory`, setting `config.paused = ALL_PAUSED`. All `init_transfer` and `finalize_transfer` calls now revert.
2. Attacker retrieves a previously emitted `SignTransferEvent` / `sign_log_metadata_callback` log from NEAR containing a valid MPC signature over a `DeployTokenPayload` for token `X`.
3. Attacker calls `deploy_token` on the Solana program with that signed payload.
4. The instruction executes successfully — no pause check is present — and token `X` is registered in the Solana program's state with initialized metadata, bypassing the emergency freeze entirely. [5](#0-4)
