### Title
Partial `ft_on_transfer` Rejection Leaves Tokens Permanently Stuck in Bridge, Inflating Deployed-Token Supply — (`near/omni-bridge/src/lib.rs`)

---

### Summary

`fin_transfer_send_tokens_callback` / `is_refund_required` only handles the **all-or-nothing** case for `ft_transfer_call` results. When a recipient contract partially accepts tokens (returning `0 < unused < amount` from `ft_on_transfer`), the bridge treats the transfer as fully successful, leaving the undelivered remainder permanently stuck in the bridge's own balance. For deployed (bridge-minted) tokens this directly inflates the circulating supply on NEAR while the source-chain tokens were already fully burned.

---

### Finding Description

When finalizing an inbound cross-chain transfer that carries a non-empty `msg`, `process_fin_transfer_to_near` calls `send_tokens` with that `msg`, which in turn calls `mint(recipient, amount, Some(msg))` on the deployed token contract. [1](#0-0) 

Inside `OmniToken::mint`, when `msg` is `Some`, the full `amount` is first deposited to the bridge's own account (`env::predecessor_account_id()` = bridge), then forwarded to the recipient via `ft_transfer_call`: [2](#0-1) 

NEP-141's `ft_resolve_transfer` handles the callback: if the recipient's `ft_on_transfer` returns `unused > 0`, it transfers `unused` tokens back to the sender (the bridge) and returns `used = amount - unused` as the promise result.

The bridge's callback `fin_transfer_send_tokens_callback` then calls `is_refund_required`: [3](#0-2) 

The critical flaw is on line 1791:

```rust
amount.0 == 0   // only triggers refund when ALL tokens were rejected
```

A partial rejection (`used = 50, unused = 50`) produces `amount.0 = 50 ≠ 0`, so `is_refund_required` returns `false`. The `else` branch of `fin_transfer_send_tokens_callback` executes — it sends fees and emits `FinTransferEvent` as if the full amount was delivered: [4](#0-3) 

The `unused` tokens returned by `ft_resolve_transfer` now sit in the bridge's own token balance. No burn is scheduled, no revert of the fin-transfer record occurs, and no recovery path exists. For native (non-deployed) tokens the same flow applies via the direct `ft_transfer_call` branch: [5](#0-4) 

---

### Impact Explanation

**For deployed (bridge-minted) tokens:** The bridge mints `amount` tokens but only `used < amount` reach the recipient. The `unused` portion is permanently stranded in the bridge's balance without being burned. The source chain already burned the full `amount`. Result: circulating supply on NEAR exceeds the locked/burned supply on the source chain — a direct token-supply mis-accounting / unauthorized minting equivalent.

**For native (escrowed) tokens:** The bridge transfers `amount` from its escrow but `unused` tokens return to the bridge's balance. The `fin_transfer` is marked complete. The bridge's internal locked-token accounting does not credit these returned tokens, so they are unrecoverable and the bridge's escrow balance drifts from its accounting.

Both cases constitute permanent loss of bridged funds for the user and/or supply inflation exploitable by anyone who can control a recipient contract.

---

### Likelihood Explanation

The trigger requires:
1. A cross-chain transfer with a non-empty `msg` field (standard DeFi-integration path, fully user-controlled).
2. The NEAR recipient is a contract whose `ft_on_transfer` returns a non-zero unused amount (attacker deploys such a contract).

Both conditions are reachable by an unprivileged bridge user with no admin involvement. The attacker initiates the transfer on the source chain, names their malicious NEAR contract as recipient, and the relayer finalizes it normally.

---

### Recommendation

In `fin_transfer_send_tokens_callback`, read the actual `used` amount from the promise result and compare it to `transfer_message.amount_without_fee()`. If `used < expected`, burn the difference (for deployed tokens) or emit a recoverable-stuck-funds event (for native tokens), and do **not** emit `FinTransferEvent` for the full amount. Concretely, replace the binary `amount.0 == 0` check with a comparison against the full expected amount:

```rust
fn is_refund_required(is_ft_transfer_call: bool, expected: u128) -> bool {
    if is_ft_transfer_call {
        match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
            Ok(value) => {
                if let Ok(used) = near_sdk::serde_json::from_slice::<U128>(&value) {
                    used.0 < expected   // refund/burn if ANY tokens were not delivered
                } else { false }
            }
            Err(_) => false,
        }
    } else { false }
}
```

For partial delivery, burn only the undelivered portion and emit a partial-failure event so the source chain can be informed.

---

### Proof of Concept

1. Attacker deploys `MaliciousReceiver` on NEAR implementing `ft_on_transfer` that always returns `amount / 2` (half unused).
2. On EVM, attacker calls `OmniBridge.initTransfer(token, 1000, 0, 0, "near:malicious.near", "trigger_ft_transfer_call")` — the non-empty `message` field propagates as `msg`.
3. Relayer submits proof; `fin_transfer` → `process_fin_transfer_to_near` → `send_tokens(token, malicious.near, 1000, "trigger_ft_transfer_call")`.
4. `mint(malicious.near, 1000, Some("trigger_ft_transfer_call"))` mints 1000 tokens to bridge, calls `ft_transfer_call(malicious.near, 1000, ...)`.
5. `MaliciousReceiver::ft_on_transfer` returns `500` (unused). `ft_resolve_transfer` returns 500 to bridge, result = `U128(500)`.
6. `is_refund_required`: `500 != 0` → `false`. Callback emits `FinTransferEvent` for 1000 tokens.
7. EVM: 1000 tokens burned. NEAR: 500 tokens in `malicious.near`, 500 tokens stuck in bridge (not burned). Supply inflated by 500. [6](#0-5) [7](#0-6) [8](#0-7)
