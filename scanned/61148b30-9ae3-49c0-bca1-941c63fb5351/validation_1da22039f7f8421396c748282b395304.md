### Title
Pause Bypass via `init_transfer_resume` Yield Callback — (File: `near/omni-bridge/src/lib.rs`)

### Summary
The NEAR `omni-bridge` contract uses a yield-resume pattern for `init_transfer` when storage is unavailable. The entry point `ft_on_transfer` is correctly guarded with `#[pause(except(roles(Role::DAO, Role::UnrestrictedDeposit)))]`, but the yield callback `init_transfer_resume` carries no pause check. An in-flight yield created before a pause is applied will still execute `init_transfer_internal` — storing the transfer and emitting the event that triggers relayer signing — after the contract has been paused.

### Finding Description
`ft_on_transfer` is the NEP-141 callback that drives outbound transfers. It is decorated with the `near-plugins` pause guard: [1](#0-0) 

When the signer lacks sufficient storage balance, `init_transfer` does not store the transfer immediately. Instead it suspends execution via `env::promise_yield_create`, registering `init_transfer_resume` as the future callback and persisting the yield ID: [2](#0-1) 

`init_transfer_resume` is the function that ultimately calls `init_transfer_internal` and finalises the transfer record. It carries only `#[private]` — no pause guard: [3](#0-2) 

Because yield callbacks are resolved in a completely separate NEAR transaction (triggered when `promise_yield_resume` is called, e.g. after a storage deposit arrives), the pause state at the time of the original `ft_on_transfer` call is irrelevant. Whatever pause flags are set when the yield fires are never consulted.

### Impact Explanation
When the contract is paused — typically in response to a security incident — the intent is to halt all new outbound transfer activity. Any transfer whose `init_transfer_resume` yield is still pending will bypass this halt: `init_transfer_internal` stores the `TransferMessage`, increments nonces, and emits the `OmniBridgeEvent` that relayers monitor. A trusted relayer can then call `sign_transfer` (which does respect the pause, but only for the DAO-exempt path) or, if the DAO role is active, sign and deliver the transfer to the destination chain, moving funds out of the bridge during a period when the operator believed all outbound activity was frozen.

Impact class: **pause bypass enabling unauthorized bridge action** — funds can leave the bridge escrow on the destination chain despite the NEAR contract being paused.

### Likelihood Explanation
The preconditions are realistic and require no privileged access:
1. A normal user initiates an outbound transfer via `ft_transfer_call` at a moment when the bridge is unpaused and their storage account balance is insufficient — a common situation for first-time users.
2. The yield is created and the yield ID is stored on-chain.
3. An admin pauses the contract (e.g., in response to a discovered vulnerability).
4. The user (or anyone) deposits storage to the `message_storage_account_id`, resolving the yield.
5. `init_transfer_resume` executes without any pause check.

Steps 1 and 4 are fully attacker-controlled with no privileged keys required.

### Recommendation
Add the same pause guard to `init_transfer_resume` that protects `ft_on_transfer`. Using the `near-plugins` macro:

```rust
#[private]
#[pause(except(roles(Role::DAO)))]   // mirror the guard on ft_on_transfer
pub fn init_transfer_resume(
    &mut self,
    transfer_message: TransferMessage,
    message_storage_account_id: AccountId,
    storage_owner: AccountId,
    #[callback_result] response: Result<(), PromiseError>,
) -> U128 { ... }
```

If the contract is paused when the yield fires, the callback should revert (or return the full token amount to trigger a refund), consistent with how `ft_on_transfer` itself would behave under a pause.

### Proof of Concept

1. Alice calls `ft_transfer_call(bridge, 1000, msg)` on a NEP-141 token. The bridge is unpaused.
2. `ft_on_transfer` passes the pause check and calls `init_transfer`.
3. Alice's signer account has no storage balance → `env::promise_yield_create("init_transfer_resume", ...)` is called; the yield ID is stored in `self.init_transfer_promises`.
4. An admin detects a vulnerability and calls `pa_pause` (the `near-plugins` pause entry point), setting the pause flag.
5. Alice (or any third party) calls the bridge's storage-deposit resolver with Alice's yield ID, triggering `promise_yield_resume`.
6. The NEAR runtime invokes `init_transfer_resume` in a new transaction. No pause check exists: [3](#0-2) 

7. `init_transfer_internal` stores the `TransferMessage` and emits the `InitTransferEvent`.
8. A relayer observes the event and calls `sign_transfer` (DAO-exempt path) or waits for the contract to be unpaused, then signs and delivers the transfer to the destination chain.
9. Funds leave the bridge escrow on the destination chain despite the NEAR contract having been paused.

    #[allow(clippy::needless_pass_by_value)]
    pub fn init_transfer_resume(
        &mut self,
        transfer_message: TransferMessage,
        message_storage_account_id: AccountId,
        storage_owner: AccountId,
        #[callback_result] response: Result<(), PromiseError>,
    ) -> U128 {
        self.remove_promise(&message_storage_account_id);
        if response.is_err() {
            env::log_str("Init transfer resume timeout");
        }

        if let Err(err) = self.try_to_transfer_balance_from_message_account(
            &message_storage_account_id,
            NearToken::from_yoctonear(transfer_message.fee.native_fee.0),
            &storage_owner,
            self.required_balance_for_init_transfer_message(transfer_message.clone()),
        ) {
            env::log_str(&format!("Error paying native fee and storage: {err}"));
            return transfer_message.amount;
        }

        self.init_transfer_internal(transfer_message, storage_owner)
    }
