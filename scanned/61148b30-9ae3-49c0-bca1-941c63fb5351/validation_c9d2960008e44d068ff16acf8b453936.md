### Title
`nativeFee` ETH Permanently Locked in `OmniBridge` Contract with No Withdrawal Mechanism — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary
The `initTransfer` and `initTransfer1155` functions in `OmniBridge.sol` accept a user-supplied `nativeFee` amount of ETH that is permanently retained in the contract. No withdrawal, rescue, or distribution function exists anywhere in the EVM codebase, making this ETH irrecoverable.

---

### Finding Description

In `initTransfer`, the contract splits `msg.value` into two parts:

- `extensionValue` — forwarded to `initTransferExtension`, which in `OmniBridgeWormhole` passes it to `_wormhole.publishMessage{value: value}(...)`.
- `nativeFee` — the remainder, which stays in the contract and is **never forwarded, distributed, or withdrawable**. [1](#0-0) 

For ERC-20 transfers:
```
extensionValue = msg.value - nativeFee   // goes to Wormhole
nativeFee                                // stays in contract forever
```

For native ETH transfers:
```
extensionValue = msg.value - amount - nativeFee   // goes to Wormhole
amount                                            // held for finTransfer payout
nativeFee                                         // stays in contract forever
``` [2](#0-1) 

The `nativeFee` parameter is also accepted in `initTransfer1155` under the same accounting: [3](#0-2) 

Compounding this, the contract exposes a bare `receive()` function that accepts arbitrary ETH from any sender with no corresponding withdrawal path: [4](#0-3) 

A search across all EVM Solidity files confirms there is **no** `withdraw`, `rescue`, or `sweep` function anywhere in the contract suite.

---

### Impact Explanation

Every user who calls `initTransfer` or `initTransfer1155` with `nativeFee > 0` permanently loses that ETH. The `nativeFee` field is a first-class parameter in the public bridge interface and is emitted in the `InitTransfer` event, indicating it is expected to carry real value in production flows. Over the lifetime of the bridge, the cumulative locked ETH could be substantial. This constitutes **fee mis-accounting that permanently changes user balances** — a critical impact under the allowed scope. [5](#0-4) 

---

### Likelihood Explanation

The vulnerability is triggered by any unprivileged bridge user who calls `initTransfer` with a non-zero `nativeFee`. The function has no access control. The `nativeFee` parameter is structurally part of the bridge protocol (present in the emitted event, passed through `initTransferExtension`, and encoded in the Wormhole payload), so it is realistic that bridge UIs or relayer tooling will instruct users to supply a non-zero value. [6](#0-5) 

---

### Recommendation

1. **Add an admin withdrawal function** to recover accumulated ETH (analogous to the fix applied in Ion Protocol PR #23):
   ```solidity
   function withdrawEth(address payable to, uint256 amount) external onlyRole(DEFAULT_ADMIN_ROLE) {
       (bool ok,) = to.call{value: amount}("");
       require(ok);
   }
   ```
2. **Alternatively**, if `nativeFee` is intended to be paid to the relayer who calls `finTransfer`, distribute it inside `finTransfer` to `msg.sender` or `payload.feeRecipient`.
3. **Remove `payable`** from `addCustomToken`, `logMetadata`, and `logMetadata1155` in the base `OmniBridge` contract if no ETH is consumed by those paths, to prevent accidental locking.

---

### Proof of Concept

1. User calls `initTransfer(erc20Token, 100e18, 0, 1e18 /*nativeFee*/, "alice.near", "")` sending `msg.value = wormholeFee + 1e18`.
2. Contract computes `extensionValue = msg.value - 1e18 = wormholeFee`.
3. `OmniBridgeWormhole.initTransferExtension` calls `_wormhole.publishMessage{value: wormholeFee}(...)` — Wormhole receives exactly its fee.
4. The `1e18` wei (`nativeFee`) remains in `OmniBridge`'s balance.
5. No function exists to withdraw it. The ETH is permanently locked.
6. Repeat for every user who bridges with `nativeFee > 0`; the locked balance grows monotonically. [7](#0-6)
