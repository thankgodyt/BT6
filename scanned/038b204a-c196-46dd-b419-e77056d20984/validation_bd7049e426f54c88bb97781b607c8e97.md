### Title
Malicious or Non-Compliant ERC1155 Recipient Can Permanently Block `finTransfer`, Freezing Bridged Funds — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

`OmniBridge.finTransfer` uses `IERC1155.safeTransferFrom` to deliver ERC1155 tokens to the recipient. This call invokes the `onERC1155Received` callback on the recipient contract. A malicious recipient contract can return an invalid selector or revert inside that callback, causing the entire `finTransfer` transaction to revert. Because there is no on-chain refund path on NEAR for a transfer whose EVM finalization permanently fails, the user's bridged funds are frozen indefinitely.

---

### Finding Description

In `OmniBridge.finTransfer`, after verifying the MPC signature and marking the nonce as used, the contract dispatches tokens to the recipient. For ERC1155 multi-tokens the dispatch is:

```solidity
IERC1155(multiToken.tokenAddress).safeTransferFrom(
    address(this),
    payload.recipient,
    multiToken.tokenId,
    payload.amount,
    ""
);
```

`safeTransferFrom` on ERC1155 mandates that if `payload.recipient` is a contract, it must implement `IERC1155Receiver.onERC1155Received` and return the correct 4-byte selector. If the recipient contract returns any other value, or reverts, the ERC1155 token contract itself reverts, which bubbles up and reverts the entire `finTransfer` call.

Because `completedTransfers[payload.destinationNonce] = true` is written **before** the `safeTransferFrom` call, a revert rolls back that state change too, leaving the nonce unconsumed. The relayer can retry, but every retry will revert identically. The signed payload fixes the recipient address; no alternative recipient can be substituted without invalidating the MPC signature.

On the NEAR side, when a user initiates a transfer, tokens are burned or locked in `pending_transfers`. There is no `cancel_transfer` or refund function in the NEAR `omni-bridge` contract that would allow recovery of those tokens if EVM finalization is permanently blocked. The funds are frozen.

---

### Impact Explanation

**Critical — permanent freezing of bridged funds.**

Any user who bridges ERC1155 tokens to a contract address that:
- deliberately returns `bytes4(0xdeadbeef)` from `onERC1155Received`, or
- reverts inside `onERC1155Received`, or
- simply does not implement `IERC1155Receiver` at all (e.g., a multisig, DAO treasury, or any contract deployed before ERC1155 existed)

will have their NEAR-side tokens permanently locked with no recovery path. The bridge contract on EVM holds the ERC1155 tokens indefinitely; the NEAR-side locked/burned tokens cannot be reclaimed.

---

### Likelihood Explanation

**Medium.**

Two realistic paths exist:

1. **Accidental**: A user bridges ERC1155 tokens to a contract address (e.g., a Gnosis Safe, a DAO vault, a DEX pool) that does not implement `onERC1155Received`. This is common; most contract wallets and DeFi contracts do not support ERC1155 reception.

2. **Deliberate griefing of a third party**: An attacker who controls a contract address convinces or tricks a user into specifying that address as the EVM recipient. The attacker then makes the contract revert in `onERC1155Received`, permanently freezing the victim's funds on NEAR. The attacker needs no profit motive beyond causing harm; the victim loses real bridged value.

---

### Recommendation

Replace the push-to-recipient pattern with a pull pattern for ERC1155 tokens:

```solidity
// Instead of safeTransferFrom directly to recipient:
// 1. Record the claimable balance
claimable[payload.recipient][multiToken.tokenAddress][multiToken.tokenId] += payload.amount;

// 2. Expose a separate claim function
function claimERC1155(address tokenAddress, uint256 tokenId) external {
    uint256 amount = claimable[msg.sender][tokenAddress][tokenId];
    claimable[msg.sender][tokenAddress][tokenId] = 0;
    IERC1155(tokenAddress).safeTransferFrom(address(this), msg.sender, tokenId, amount, "");
}
```

Alternatively, wrap the `safeTransferFrom` in a try/catch and emit a `ClaimableToken` event so the recipient can retrieve tokens via a separate function, analogous to the mitigation applied in Revert Lend (approve + pull instead of push).

### Proof of Concept

**Attacker contract (Solidity):**

```solidity
contract MaliciousERC1155Recipient {
    address public bridge;

    constructor(address _bridge) {
        bridge = _bridge;
    }

    // Returns invalid selector when called by the bridge, blocking finTransfer
    function onERC1155Received(
        address operator,
        address,
        uint256,
        uint256,
        bytes calldata
    ) external view returns (bytes4) {
        if (operator == bridge) return bytes4(0xdeadbeef); // invalid
        return this.onERC1155Received.selector;
    }

    function onERC1155BatchReceived(address, address, uint256[] calldata, uint256[] calldata, bytes calldata)
        external pure returns (bytes4) { return bytes4(0); }

    function supportsInterface(bytes4) external pure returns (bool) { return false; }
}
```

**Attack flow:**

1. User (or attacker) initiates an ERC1155 bridge transfer on NEAR, specifying `MaliciousERC1155Recipient` as the EVM recipient. Tokens are locked/burned on NEAR.
2. Relayer calls `finTransfer` on `OmniBridge` with the signed payload.
3. Execution reaches line 324: `IERC1155(...).safeTransferFrom(address(this), payload.recipient, ...)`.
4. The ERC1155 token contract calls `MaliciousERC1155Recipient.onERC1155Received`, which returns `0xdeadbeef`.
5. The ERC1155 token contract reverts with `"ERC1155: transfer to non ERC1155Receiver implementer"`.
6. `finTransfer` reverts; `completedTransfers[nonce]` is rolled back.
7. Every subsequent retry by the relayer reverts identically.
8. The user's tokens on NEAR are permanently locked with no recovery path.
