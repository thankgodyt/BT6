### Title
Unvalidated `decimals` in `log_metadata_callback` Causes Arithmetic Overflow in `normalize_amount`, Permanently Freezing Bridged Funds — (File: `near/omni-bridge/src/lib.rs`)

### Summary

The `log_metadata_callback` function in the NEAR bridge contract accepts the `decimals` field from an arbitrary NEAR token's `ft_metadata()` response with no bounds validation beyond checking that `name` and `symbol` are non-empty. A token creator can set `decimals = 255`. After the token is registered via the full `log_metadata → deployToken (EVM) → bind_token (NEAR)` flow, the bridge stores `Decimals { decimals: 18, origin_decimals: 255 }`. Any subsequent call to `sign_transfer` for this token invokes `normalize_amount`, which computes `10_u128.pow(237)`, overflowing `u128` and causing a panic. All pending transfers of this token are permanently frozen.

### Finding Description

**Root cause — missing field-level validation in `log_metadata_callback`:** [1](#0-0) 

The only guard is:

```rust
require!(
    !metadata.name.is_empty() && !metadata.symbol.is_empty(),
    BridgeError::InvalidMetadata.as_ref()
);
```

`metadata.decimals` (a `u8`, range 0–255) is accepted blindly and packed into `MetadataPayload` for MPC signing. [2](#0-1) 

**Propagation through the token-registration flow:**

1. MPC signs the payload containing `decimals = 255`.
2. EVM `deployToken` verifies the signature and normalizes: `_normalizeDecimals(255) → 18`. [3](#0-2) 

3. EVM emits `DeployToken(decimals=18, originDecimals=255)`.
4. NEAR `bind_token_callback` parses the EVM proof and calls `add_token(token, address, decimals=18, origin_decimals=255)`. [4](#0-3) 

5. `token_decimals` now stores `Decimals { decimals: 18, origin_decimals: 255 }`. [5](#0-4) 

**Overflow in `normalize_amount` during `sign_transfer`:** [6](#0-5) 

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    // diff_decimals = 255 - 18 = 237
    amount / (10_u128.pow(237))  // 10^237 >> u128::MAX (~3.4×10^38) → overflow
}
```

`u128::MAX ≈ 3.4 × 10^38`, so `10_u128.pow(237)` overflows. With `overflow-checks = true` (standard for NEAR contracts), this panics. With wrapping, the divisor becomes an unpredictable small value, producing a wildly inflated `amount_to_transfer` that the MPC would sign, enabling unauthorized minting on the destination chain.

`sign_transfer` calls this function unconditionally: [7](#0-6) 

### Impact Explanation

Once a token with `origin_decimals − decimals > 38` is registered, every call to `sign_transfer` for that token panics. Tokens locked or burned on NEAR during `init_transfer` can never be released because the MPC signature step is permanently broken. This constitutes **permanent freezing of bridged funds** — a critical impact in the allowed scope. Alternatively, if overflow wraps to a small divisor, `normalize_amount` returns an inflated amount that the MPC signs, enabling **unauthorized minting** of bridge tokens on EVM/Starknet/Solana.

### Likelihood Explanation

The entire attack path is permissionless:

1. Deploy a NEAR NEP-141 token with `decimals = 255` — no privilege required.
2. Call `log_metadata(token_id)` on the NEAR bridge — open to any caller.
3. Call EVM `deployToken(signature, metadata)` — open to any caller.
4. Call NEAR `bind_token(prover_args)` — open to any caller.

No admin compromise, no key leakage, and no social engineering is required beyond convincing users to bridge the token (or the attacker bridges their own tokens to demonstrate the freeze). The four-step registration flow is the standard documented path for bridging any new token.

### Recommendation

Add an explicit upper-bound check on `decimals` in `log_metadata_callback` before signing:

```rust
require!(
    !metadata.name.is_empty() && !metadata.symbol.is_empty(),
    BridgeError::InvalidMetadata.as_ref()
);
require!(
    metadata.decimals <= 24,  // or whatever the protocol maximum is
    BridgeError::InvalidMetadata.as_ref()
);
```

Additionally, add a saturating/checked guard in `normalize_amount` and `denormalize_amount` to prevent overflow regardless of stored values:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    let divisor = 10_u128.checked_pow(diff_decimals)
        .unwrap_or_else(|| env::panic_str("DecimalsOverflow"));
    amount / divisor
}
```

### Proof of Concept

1. Deploy NEAR NEP-141 token `evil.near` with `decimals = 255`, `name = "Evil"`, `symbol = "EVIL"`.
2. Call `bridge.log_metadata("evil.near")` with sufficient attached deposit. `log_metadata_callback` passes the `!name.is_empty()` check; MPC signs `MetadataPayload { decimals: 255, ... }`.
3. Call EVM `OmniBridge.deployToken(signature, { token: "evil.near", name: "Evil", symbol: "EVIL", decimals: 255 })`. EVM normalizes to 18, emits `DeployToken(decimals=18, originDecimals=255)`.
4. Call NEAR `bridge.bind_token({ chain_kind: Eth, prover_args: <proof of step 3> })`. Bridge stores `Decimals { decimals: 18, origin_decimals: 255 }`.
5. Transfer 1 `evil.near` token to the bridge via `ft_transfer_call`. Transfer is stored in `pending_transfers`.
6. Call `bridge.sign_transfer(transfer_id, ...)`. Execution reaches `normalize_amount(1, Decimals { 18, 255 })` → `10_u128.pow(237)` → overflow → panic. The transfer can never be signed; the locked token is permanently frozen. [8](#0-7) [6](#0-5) [4](#0-3) [3](#0-2)
