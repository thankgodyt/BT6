### Title
Missing Chain ID in `deployToken` Signature Allows Cross-Chain Replay of Token Deployment — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

The `deployToken` function in `OmniBridge.sol` (and its Starknet analog in `omni_bridge.cairo`) verifies a NEAR MPC signature over a Borsh-encoded `MetadataPayload` that **does not include the destination chain ID**. Because the bridge is deployed on multiple EVM chains (Ethereum, Arbitrum, Base, BNB, Polygon) sharing the same `nearBridgeDerivedAddress`, a signature authorizing token deployment on one chain is valid on every other chain. This is the exact cross-chain replay class described in the reference report.

---

### Finding Description

`finTransfer` correctly binds its signed payload to the destination chain by embedding `omniBridgeChainId` twice in the Borsh encoding: [1](#0-0) 

`deployToken`, however, constructs its signed payload with only the token metadata — no chain identifier is present: [2](#0-1) 

The recovered signer is checked against `nearBridgeDerivedAddress`: [3](#0-2) 

Because `nearBridgeDerivedAddress` is the same derived address across all EVM deployments, any valid `deployToken` signature for chain A is also a valid `deployToken` signature for chains B, C, D, etc.

The same flaw exists in Starknet. `TransferMessagePayloadTrait::to_borsh` accepts a `chain_id` parameter and embeds it: [4](#0-3) 

But `MetadataPayloadTrait::to_borsh` takes no chain ID and encodes only the four metadata fields: [5](#0-4) 

`deploy_token` calls the chain-ID-free variant: [6](#0-5) 

while `fin_transfer` correctly passes the stored chain ID: [7](#0-6) 

---

### Impact Explanation

An attacker who observes a valid `deployToken` transaction on chain A can submit the identical `(signatureData, metadata)` to `OmniBridge.deployToken` on chains B, C, … N. Each call will:

1. Pass signature verification (same signer, same payload hash, no chain binding).
2. Write `isBridgeToken[bridgeTokenProxy] = true` and populate `nearToEthToken` / `ethToNearToken` on the target chain. [8](#0-7) 

Consequences:

- **Permanent blocking of legitimate deployment**: Once the attacker deploys the token on chain B, the guard `require(!isBridgeToken[nearToEthToken[metadata.token]], "ERR_TOKEN_EXIST")` prevents any future legitimate deployment of that token on chain B. The NEAR bridge can never properly register the token there. [9](#0-8) 

- **Unauthorized bridge token existence**: The deployed token is a fully functional `BridgeToken` (mintable/burnable by the bridge). If the NEAR side later authorizes transfers to chain B for this token, the attacker-deployed contract — which the attacker triggered — becomes the canonical bridge token, undermining the integrity of the deployment authorization model.

---

### Likelihood Explanation

The attack requires only:
1. Watching any public EVM chain for a `deployToken` transaction (trivially observable on-chain).
2. Replaying the calldata on any other EVM chain where the token is not yet deployed.

No privileged access, leaked keys, or off-chain coordination is needed. The bridge is live on at least five EVM chains (Ethereum, Arbitrum, Base, BNB, Polygon), so every new token deployment on any one chain is immediately replayable on the others. Likelihood is **high**.

---

### Recommendation

Include `omniBridgeChainId` in the Borsh-encoded payload that is signed for `deployToken`, mirroring the pattern already used in `finTransfer`:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
+   bytes1(omniBridgeChainId),          // bind to destination chain
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
```

Apply the same fix to `MetadataPayloadTrait::to_borsh` in `starknet/src/bridge_types.cairo` and `DeployTokenPayload::serialize_for_near` in `solana/programs/bridge_token_factory/src/state/message/deploy_token.rs`, passing the respective chain constant in each case. [10](#0-9) 

---

### Proof of Concept

1. NEAR MPC signs a `MetadataPayload{token:"usdc.near", name:"USD Coin", symbol:"USDC", decimals:6}` for Ethereum. The relayer calls `OmniBridge.deployToken(sig, payload)` on Ethereum — succeeds, USDC bridge token deployed at address `T_eth`.

2. Attacker copies `(sig, payload)` verbatim and calls `OmniBridge.deployToken(sig, payload)` on Arbitrum. The Borsh encoding is identical; `ECDSA.recover` returns `nearBridgeDerivedAddress`; the call succeeds. USDC bridge token is now deployed at `T_arb` on Arbitrum without NEAR ever authorizing it.

3. When the NEAR bridge later attempts the legitimate deployment on Arbitrum, `nearToEthToken["usdc.near"]` is already set and `isBridgeToken[T_arb]` is `true`, so the call reverts with `ERR_TOKEN_EXIST`. The token is permanently blocked from legitimate deployment on Arbitrum.
