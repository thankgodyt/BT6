### Title
Token-2022 Transfer Fee Not Accounted for in Solana `init_transfer`, Causing Escrow Over-Minting on NEAR — (`solana/programs/bridge_token_factory/src/instructions/user/init_transfer.rs`)

---

### Summary

The Solana `bridge_token_factory` program's `init_transfer` instruction locks tokens in a vault via `transfer_checked` and then posts a Wormhole message containing the user-supplied `payload.amount`. For Token-2022 tokens that have the **transfer fee extension** enabled, `transfer_checked` causes the vault to receive `amount − transfer_fee` while the fee is withheld in the recipient's account. The Wormhole message still carries the full `payload.amount`, so the NEAR side mints `amount` tokens when only `amount − transfer_fee` was actually escrowed on Solana. This is the direct structural analog of the external report: a fee is silently deducted from the actual received quantity, but the calling code uses the pre-fee figure for all downstream accounting.

---

### Finding Description

In `init_transfer.rs`, the `process` function performs two sequential operations:

1. **Lock tokens** via `transfer_checked` using `payload.amount`:

```rust
transfer_checked(
    CpiContext::new(
        self.token_program.to_account_info(),
        TransferChecked {
            from: self.from.to_account_info(),
            to: vault.to_account_info(),
            authority: self.user.to_account_info(),
            mint: self.mint.to_account_info(),
        },
    ),
    payload.amount.try_into()...,
    self.mint.decimals,
)?;
```

2. **Post a Wormhole message** that serialises `self.amount` (i.e. `payload.amount`) for the NEAR side to consume:

```rust
self.common.post_message(payload.serialize_for_near((
    self.common.sequence.sequence,
    self.user.key(),
    self.mint.key(),
))?)?;
``` [1](#0-0) 

The `InitTransferPayload` serialised into the Wormhole message contains the raw `self.amount` field:

```rust
// 4. amount
self.amount.serialize(&mut writer)?;
``` [2](#0-1) 

Under the **Token-2022 transfer fee extension**, `transfer_checked(amount)` causes the vault to receive `amount − fee` (the fee is withheld from the recipient's credited balance). The program never reads the vault's post-transfer balance; it simply forwards `payload.amount` verbatim in the Wormhole message. The NEAR bridge then denormalises and mints that full figure to the recipient.

The NEAR `fin_transfer_callback` trusts the amount field from the prover result without any independent verification of what was actually locked on Solana:

```rust
amount: Self::denormalize_amount(init_transfer.amount.0, decimals).into(),
``` [3](#0-2) 

The program explicitly supports Token-2022 via `token_interface` and `InterfaceAccount<Mint>`, and `log_metadata` (which registers a token and creates its vault) is permissionless: [4](#0-3) 

---

### Impact Explanation

An attacker who controls a Token-2022 mint with a transfer fee can:

- Lock `amount − fee` tokens in the Solana vault.
- Receive `amount` tokens minted on NEAR.
- Bridge the full `amount` back to Solana, forcing the vault to unlock `amount` tokens when it only holds `amount − fee`.

Each round trip extracts `fee` tokens from the vault at the expense of other depositors. Repeated iterations drain the vault entirely. This is a critical **escrow mis-accounting / balance manipulation** vulnerability: the bridge's invariant that `locked_on_Solana == mintable_on_NEAR` is broken for every Token-2022 token with a non-zero transfer fee.

---

### Likelihood Explanation

- `log_metadata` is permissionless — any user can register a Token-2022 mint with a transfer fee.
- `init_transfer` is permissionless — any user can call it.
- Token-2022 transfer fees are a standard, production-deployed extension on Solana mainnet.
- No whitelist or fee-extension check exists in the bridge code.

The attack requires no privileged access, no key compromise, and no collusion.

---

### Recommendation

After `transfer_checked` completes, read the vault's actual post-transfer balance and compute the net deposited amount as `vault_balance_after − vault_balance_before`. Use that net figure — not `payload.amount` — when constructing the Wormhole message. Alternatively, explicitly reject Token-2022 mints that have a non-zero transfer fee configured (check the mint's `TransferFeeConfig` extension before accepting a registration via `log_metadata`).

---

### Proof of Concept

1. Attacker deploys a Token-2022 mint `M` with a 5 % transfer fee and mints themselves 10 000 tokens.
2. Attacker calls `log_metadata` on `M`; the bridge creates a vault PDA and posts metadata to NEAR. NEAR registers the token.
3. Attacker calls `init_transfer` with `payload.amount = 10 000`.
   - `transfer_checked(10 000)` → vault receives **9 500**; 500 withheld as fee.
   - Wormhole message carries `amount = 10 000`.
4. NEAR relayer submits the VAA; `fin_transfer_callback` mints **10 000** tokens to the attacker on NEAR.
5. Attacker calls NEAR `ft_transfer_call` to bridge **10 000** tokens back to Solana.
   - NEAR burns 10 000 tokens.
   - Solana `finalize_transfer` unlocks **10 000** from the vault (which only holds 9 500) → vault is over-drawn by 500.
6. Repeating this loop drains the vault, stealing funds from legitimate depositors.
