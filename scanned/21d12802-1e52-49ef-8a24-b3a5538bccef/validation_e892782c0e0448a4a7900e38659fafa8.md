### Title
Fee-on-Transfer Token Mis-Accounting in `initTransfer` Causes EVM Escrow Under-Collateralization - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

`OmniBridge.sol`'s `initTransfer` function calls `safeTransferFrom(msg.sender, address(this), amount)` for native (non-bridge, non-custom-minter) ERC20 tokens and then emits an `InitTransfer` event carrying the caller-supplied nominal `amount`. For fee-on-transfer tokens, the contract actually receives `amount - transfer_fee`, but the event records `amount`. The NEAR bridge reads this event and mints or releases the full nominal `amount` to the recipient, permanently over-issuing tokens relative to what is locked on the EVM side. The same structural flaw exists in `starknet/src/omni_bridge.cairo`.

---

### Finding Description

In `OmniBridge.sol`, the `initTransfer` function handles native ERC20 tokens via the `else` branch:

```solidity
// lines 407-411
IERC20(tokenAddress).safeTransferFrom(
    msg.sender,
    address(this),
    amount
);
```

Immediately after, the function emits:

```solidity
// lines 427-436
emit BridgeTypes.InitTransfer(
    msg.sender,
    tokenAddress,
    currentOriginNonce,
    amount,   // <-- nominal caller-supplied value, not actual received
    fee,
    nativeFee,
    recipient,
    message
);
```

No balance snapshot is taken before and after the transfer to compute the actual received amount. For any ERC20 token that deducts a fee on every transfer (e.g., deflationary tokens, tokens with configurable transfer taxes), the contract receives `amount - token_transfer_fee` while the event records `amount`.

The NEAR bridge's prover verifies this EVM event and passes `amount` to `fin_transfer`, which mints or unlocks the full nominal `amount` on NEAR. The EVM escrow is now under-collateralized by exactly `token_transfer_fee` per bridging operation.

The identical pattern exists in `starknet/src/omni_bridge.cairo` `init_transfer`:

```cairo
// lines 304-306
let success = IERC20Dispatcher { contract_address: token_address }
    .transfer_from(caller, get_contract_address(), amount.into());
```

followed by emitting `amount` in the `InitTransfer` event at lines 316–330, with no actual-received-amount check.

---

### Impact Explanation

**Critical — escrow mis-accounting / permanent loss of bridged funds.**

Each `initTransfer` call with a fee-on-transfer token inflates the NEAR-side supply relative to the EVM-side escrow. Over multiple operations the deficit compounds. When any user attempts to bridge tokens back from NEAR to EVM, `finTransfer` on the EVM side calls:

```solidity
// OmniBridge.sol lines 351-354
IERC20(payload.tokenAddress).safeTransfer(
    payload.recipient,
    payload.amount
);
```

The bridge may not hold enough tokens to satisfy this transfer, causing either:
- A revert that permanently freezes the user's funds (they burned tokens on NEAR but cannot receive on EVM), or
- Drainage of tokens deposited by other users to cover the shortfall, constituting direct theft of bridged funds.

---

### Likelihood Explanation

Any ERC20 token with a transfer fee that is registered as a native (non-bridge) token on the EVM OmniBridge is affected. The `else` branch in `initTransfer` imposes no whitelist restriction — any token not in `isBridgeToken` or `customMinters` reaches this path. An unprivileged user needs only to call `initTransfer` with such a token; no special role or privileged access is required. Fee-on-transfer tokens are a well-known token class (e.g., STA, REFLECT, tokens with configurable tax mechanisms), and the bridge's design explicitly supports arbitrary native ERC20s.

---

### Recommendation

Record the contract's token balance before and after `safeTransferFrom` and use the delta as the canonical bridged amount in the emitted event:

```solidity
uint256 balanceBefore = IERC20(tokenAddress).balanceOf(address(this));
IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
uint256 actualReceived = IERC20(tokenAddress).balanceOf(address(this)) - balanceBefore;
// use actualReceived (cast to uint128 with overflow check) in the event and downstream accounting
```

Apply the same fix to `starknet/src/omni_bridge.cairo`'s `init_transfer`. Alternatively, explicitly document and enforce that fee-on-transfer tokens are not supported, and add an on-chain guard (e.g., a balance-delta check that reverts if `actualReceived != amount`).

---

### Proof of Concept

1. Deploy or use any ERC20 token with a 1% transfer fee that is registered as a native token on the EVM OmniBridge (not in `isBridgeToken`, not in `customMinters`).
2. Call `OmniBridge.initTransfer(tokenAddress, 1000, 0, 0, "near:alice.near", "")` with `amount = 1000`.
3. The bridge receives `990` tokens (1% fee deducted by the token contract).
4. The `InitTransfer` event records `amount = 1000`.
5. The NEAR prover verifies the event; NEAR `fin_transfer` mints `1000` tokens to `alice.near`.
6. Alice bridges `1000` tokens back from NEAR to EVM: NEAR burns `1000`, EVM `finTransfer` attempts `safeTransfer(alice_evm, 1000)`.
7. The EVM bridge only holds `990` → `safeTransfer` reverts → Alice's `1000` NEAR-side tokens are burned with no EVM-side release (permanent fund loss).
8. Repeating step 2–5 multiple times compounds the deficit, eventually causing all subsequent `finTransfer` calls for this token to fail, freezing all users' bridged funds. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
