### Title
Relayer Permanently Loses Fronted BTC Tokens When `send_tokens` Fails in `utxo_fin_transfer_fast` — (`near/omni-bridge/src/lib.rs`)

### Summary
In `utxo_fin_transfer_fast`, the fast-transfer record is irrevocably removed or marked finalised **before** the repayment transfer to the relayer is dispatched, and that transfer is fired with `.detach()` (no callback, no rollback). If the `send_tokens` call fails for any reason — most concretely, the relayer account not being registered for the BTC NEP-141 token — the relayer's fronted tokens are permanently lost with no recovery path.

### Finding Description

`utxo_fin_transfer` is the callback entry point triggered when the BTC connector calls `ft_transfer_call` with a UTXO proof. When a matching fast-transfer record exists, it delegates to `utxo_fin_transfer_fast`: [1](#0-0) 

Inside `utxo_fin_transfer_fast`, the fast-transfer state is mutated first:

- For NEAR-destination transfers: `remove_fast_transfer` is called at line 2530, permanently deleting the record.
- For other-chain transfers: `mark_fast_transfer_as_finalised` is called at line 2533, permanently sealing the record. [2](#0-1) 

Immediately after, the relayer repayment is dispatched as a **fire-and-forget** promise: [3](#0-2) 

`.detach()` means no callback is registered. If `send_tokens` panics or the underlying `ft_transfer` fails (e.g., relayer account not registered for the BTC token, insufficient storage deposit, or any other NEP-141 rejection), the failure is silently swallowed. The fast-transfer record is already gone, so there is no way to retry or recover.

The developers themselves flagged this exact gap with a TODO comment: [4](#0-3) 

The connector authenticity check at line 2471–2474 ensures only the legitimate BTC connector can reach this path, but that does not protect against the relayer repayment failing silently: [5](#0-4) 

### Impact Explanation
A relayer who fronted BTC tokens for a fast transfer is entitled to repayment when the UTXO proof arrives. If the repayment `ft_transfer` fails after the fast-transfer record has been removed/finalised, the relayer's fronted tokens are permanently lost. There is no retry mechanism, no rollback, and no event that would allow off-chain recovery. This constitutes a permanent, unrecoverable loss of bridged BTC funds held by the relayer.

### Likelihood Explanation
The most realistic trigger is a relayer account that is not registered (no storage deposit) for the BTC NEP-141 token at the time the UTXO proof is finalised. This can happen naturally if the relayer's storage registration lapses, or it can be deliberately induced by an adversary who fronts a fast transfer using a relayer account that is not registered for the token. The BTC connector itself is trusted and behaves correctly; the failure mode is entirely within the NEAR contract's own promise handling.

### Recommendation
Replace the `.detach()` pattern with a proper callback that checks whether `send_tokens` succeeded. If it failed, the fast-transfer record must be restored (or the relayer repayment must be retried). Concretely:

1. Do **not** call `remove_fast_transfer` / `mark_fast_transfer_as_finalised` before the token transfer succeeds.
2. Register a `#[private]` callback on the `send_tokens` promise.
3. In the callback, only remove/finalise the fast-transfer record on success; on failure, leave the record intact so the transfer can be retried or the relayer can be repaid via an alternative path.

### Proof of Concept

1. Register a fast transfer for a UTXO ID where the relayer account (`relayer.near`) is **not** registered for the BTC NEP-141 token (no storage deposit).
2. Have the BTC connector call `ft_transfer_call` with the matching UTXO proof, triggering `utxo_fin_transfer` → `utxo_fin_transfer_fast`.
3. Observe that `remove_fast_transfer` (line 2530) executes and the record is gone.
4. Observe that `send_tokens(...).detach()` (lines 2542–2548) fires but the underlying `ft_transfer` to `relayer.near` fails silently because the account is not registered.
5. Assert: fast-transfer record no longer exists; relayer's BTC token balance is unchanged from before the proof was submitted. The relayer has permanently lost their fronted tokens.
