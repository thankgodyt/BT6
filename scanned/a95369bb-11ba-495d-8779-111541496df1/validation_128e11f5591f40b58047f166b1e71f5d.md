### Title
Escrow Mis-Accounting via Fee-on-Transfer Tokens Due to Missing Balance-Before/After Check in `initTransfer` - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

The `initTransfer` function in `OmniBridge.sol` accepts a caller-supplied `amount` and transfers it from the sender to the contract without verifying the actual received balance. For fee-on-transfer ERC-20 tokens, the contract receives less than `amount` but emits `InitTransfer` with the full `amount`. The NEAR bridge then mints the full `amount` on NEAR, while the EVM escrow is permanently underfunded by the fee difference — a direct profit for the attacker and a loss for later withdrawers.

---

### Finding Description

In `initTransfer`, the standard ERC-20 branch (lines 406–412) performs:

```solidity
IERC20(tokenAddress).safeTransferFrom(
    msg.sender,
    address(this),
    amount
);
``` [1](#0-0) 

No balance-before/after check is performed. The function then emits `InitTransfer` with the caller-supplied `amount`:

```solidity
emit BridgeTypes.InitTransfer(
    msg.sender,
    tokenAddress,
    currentOriginNonce,
    amount,   // ← user-supplied, not actual received
    fee,
    nativeFee,
    recipient,
    message
);
``` [2](#0-1) 

For a fee-on-transfer ERC-20 token (e.g., a reflection token that deducts 1% on every transfer), `safeTransferFrom` causes the contract to receive `amount × (1 - fee_rate)`, but the event records `amount`. The NEAR light-client or Wormhole prover verifies this event and the NEAR bridge mints the full `amount` on NEAR: [3](#0-2) 

The only guard on `amount` is `if (fee >= amount) revert InvalidFee()`, which ensures `amount > 0` but does not protect against the actual-received-vs-recorded discrepancy. [4](#0-3) 

---

### Impact Explanation

**Critical — Escrow mis-accounting / permanent freezing of bridged funds.**

Each time an attacker bridges a fee-on-transfer token:
- EVM escrow receives `amount × (1 - fee_rate)` tokens.
- NEAR bridge mints `amount` tokens.
- The attacker profits `amount × fee_rate` tokens at the protocol's expense.

After repeated bridging, the EVM escrow deficit accumulates. When later users attempt to bridge back from NEAR to EVM, `finTransfer` on EVM will attempt to release the full recorded amount but the escrow is short. The last users to withdraw are permanently unable to recover their funds — a direct loss of bridged assets.

---

### Likelihood Explanation

**Medium.** Fee-on-transfer tokens (reflection tokens, tokens with burn-on-transfer) are a well-established token class deployed on mainnet Ethereum. The `initTransfer` function imposes no allowlist on which ERC-20 tokens can be bridged via the standard path. Any unprivileged user can call `initTransfer` with such a token. The attack is repeatable, profitable, and requires no special access.

---

### Recommendation

Apply a balance-before/after check and use the actual received amount in the emitted event:

```solidity
uint256 balanceBefore = IERC20(tokenAddress).balanceOf(address(this));
IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
uint256 balanceAfter = IERC20(tokenAddress).balanceOf(address(this));
uint128 actualReceived = uint128(balanceAfter - balanceBefore);
require(actualReceived == amount, "Fee-on-transfer tokens not supported");
```

Alternatively, emit the event with `actualReceived` instead of `amount` and propagate that value through the cross-chain message.

---

### Proof of Concept

1. Deploy a fee-on-transfer ERC-20 token `FeeToken` that deducts 1% on every `transferFrom`.
2. Mint 100,000 `FeeToken` to attacker address.
3. Approve `OmniBridge` to spend 100,000 `FeeToken`.
4. Call `initTransfer(FeeToken, 100_000, 0, 0, "attacker.near", "")`.
5. `OmniBridge` receives 99,000 `FeeToken` (1% deducted), but emits `InitTransfer` with `amount = 100_000`.
6. NEAR prover verifies the event; NEAR bridge mints 100,000 tokens to `attacker.near`.
7. Attacker has gained 1,000 tokens net. EVM escrow is 1,000 tokens short.
8. Repeat until the escrow deficit makes the last legitimate withdrawer's `finTransfer` call fail permanently. [5](#0-4)

        address tokenAddress,
        uint128 amount,
        uint128 fee,

        currentOriginNonce += 1;
        if (fee >= amount) {
            revert InvalidFee();

            if (fee != 0) {
                revert InvalidFee();
            }
            extensionValue = msg.value - amount - nativeFee;
        } else {
            extensionValue = msg.value - nativeFee;
            if (customMinters[tokenAddress] != address(0)) {
                IERC20(tokenAddress).safeTransferFrom(
                    msg.sender,

                    amount

                    address(this),
                    amount
                );
