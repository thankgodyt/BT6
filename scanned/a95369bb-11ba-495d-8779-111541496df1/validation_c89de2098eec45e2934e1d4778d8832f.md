### Title
Fee-on-Transfer Token Mis-Accounting in `initTransfer` Inflates Locked Amount, Causing Last Bridger's Funds to Be Permanently Frozen - (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

### Summary

`OmniBridge.sol::initTransfer` performs a `safeTransferFrom` of a user-specified `amount` from the caller into the bridge escrow, then emits `InitTransfer` with that same `amount`. For Fee-on-Transfer (FoT) tokens, the bridge actually receives `amount - transferFee`, but the event records `amount`. The NEAR hub treats the emitted event as authoritative proof of what is escrowed, so it mints the full `amount` of wrapped tokens on NEAR. The EVM escrow is now under-collateralized by exactly the transfer fee. When users bridge back (NEAR → EVM), the EVM bridge will eventually be unable to pay the last claimant(s), permanently freezing their funds.

### Finding Description

In `OmniBridge.sol::initTransfer`, the non-bridge-token path locks tokens via:

```solidity
IERC20(tokenAddress).safeTransferFrom(
    msg.sender,
    address(this),
    amount          // user-supplied; actual receipt may be less for FoT tokens
);
```

Immediately after, the event is emitted with the same user-supplied `amount`:

```solidity
emit BridgeTypes.InitTransfer(
    msg.sender,
    tokenAddress,
    currentOriginNonce,
    amount,         // NOT the actual received amount
    fee,
    nativeFee,
    recipient,
    message
);
``` [1](#0-0) [2](#0-1) 

The NEAR side parses this event (via light client or Wormhole proof) and treats the emitted `amount` as the canonical locked value, as explicitly documented in `evm/CLAUDE.md`:

> "The NEAR side will treat any emitted event as proof that tokens are held." [3](#0-2) 

The `InitTransfer` event structure confirms `amount` is the sole field used to represent the locked quantity: [4](#0-3) 

For a FoT token with a 1% transfer fee:
- User calls `initTransfer(fotToken, 1000, ...)`.
- Bridge receives `990` tokens.
- Event emits `amount = 1000`.
- NEAR mints `1000` wrapped tokens to the recipient.
- EVM escrow deficit: `10` tokens per transfer.

After N such transfers, the EVM bridge holds `N × 990` tokens but has promised `N × 1000`. The Nth user to bridge back from NEAR to EVM triggers `safeTransfer(recipient, 1000)` when the bridge balance is insufficient, reverting and permanently freezing their funds.

### Impact Explanation

**Critical — permanent loss/freezing of bridged funds.** The EVM escrow becomes progressively under-collateralized with each FoT `initTransfer`. The shortfall accumulates silently. When the bridge's actual token balance is exhausted, the final `finTransfer` call on EVM reverts, and the corresponding NEAR-side wrapped tokens become unbridgeable — permanently frozen. The NEAR-minted surplus also represents unauthorized token inflation on the NEAR side.

### Likelihood Explanation

FoT tokens (e.g., USDT on some chains, PAXG, STA, and many DeFi tokens) are widely deployed on EVM chains. The `initTransfer` function accepts any ERC-20 token address without restricting FoT tokens. Any unprivileged user can call `initTransfer` with a FoT token. No admin action, special role, or external dependency failure is required — the vulnerability is triggered by normal bridge usage with a qualifying token.

### Recommendation

Measure the actual received amount by comparing the bridge's token balance before and after the `safeTransferFrom`, and use that delta as the canonical `amount` in the emitted event:

```solidity
uint256 balanceBefore = IERC20(tokenAddress).balanceOf(address(this));
IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
uint256 received = IERC20(tokenAddress).balanceOf(address(this)) - balanceBefore;
// Use `received` (cast to uint128) in place of `amount` for the event and downstream logic
```

Alternatively, maintain an explicit allowlist of supported tokens and reject FoT tokens at the protocol level.

### Proof of Concept

1. Deploy a FoT ERC-20 token `FOT` with a 1% transfer fee on Ethereum.
2. Alice calls `OmniBridge.initTransfer(FOT, 10_000, 0, 0, "alice.near", "")`.
   - Bridge receives `9_900 FOT`.
   - Event emits `amount = 10_000`.
3. NEAR hub reads the event proof and mints `10_000 wFOT` to `alice.near`.
4. Bob calls `OmniBridge.initTransfer(FOT, 10_000, 0, 0, "bob.near", "")`.
   - Bridge receives `9_900 FOT` (total: `19_800 FOT`).
   - Event emits `amount = 10_000`.
5. NEAR hub mints `10_000 wFOT` to `bob.near`.
6. Alice bridges back: NEAR burns `10_000 wFOT`, EVM `finTransfer` calls `safeTransfer(alice, 10_000)` — succeeds (bridge now holds `9_800 FOT`).
7. Bob bridges back: NEAR burns `10_000 wFOT`, EVM `finTransfer` calls `safeTransfer(bob, 10_000)` — **reverts** (bridge only holds `9_800 FOT`). Bob's `10_000 wFOT` on NEAR are burned but he receives nothing on EVM — **permanent fund loss**. [5](#0-4)
