### Title
Callback panic in `send_fee_internal` after committed `remove_transfer_message` permanently destroys transfer record and freezes fee tokens — (`near/omni-bridge/src/btc.rs`, `near/omni-bridge/src/lib.rs`)

### Summary
When a UTXO-chain (BTC) transfer is created with `native_fee > 0`, calling `submit_transfer_to_utxo_chain_connector` removes the transfer from storage (committed), then on connector success, the callback calls `send_fee_internal`, which panics with `NativeFeeForUtxoChain`. The panic reverts only the callback's own state, leaving the transfer permanently deleted and the fee tokens permanently frozen in the bridge contract.

### Finding Description
`submit_transfer_to_utxo_chain_connector` calls `self.remove_transfer_message(transfer_id)` at line 84 before dispatching the async `ft_transfer_call`. In NEAR's execution model this state change is committed. The callback `submit_transfer_to_btc_connector_callback` handles the success path by calling `send_fee_internal`. Inside `send_fee_internal`, if `native_fee != 0` and `origin_chain.is_utxo_chain()`, `env::panic_str` is called. This panics the callback, reverting only the callback's own state changes. The `remove_transfer_message` is not reverted. The `token_fee` amount (withheld from the connector at line 39) remains in the bridge contract with no recovery path, since the transfer record no longer exists.

No validation at `ft_on_transfer` or at the entry of `submit_transfer_to_utxo_chain_connector` prevents `native_fee > 0` for UTXO-chain transfers. The e2e test at line 118 of `04_btc_transfer.smk` demonstrates this is a supported user-facing input.

### Impact Explanation
Fee tokens (`token_fee` in nBTC) are permanently frozen in the bridge contract. The transfer record is irrecoverably deleted. The relayer receives no fee. This is a fee mis-accounting and permanent fund-freezing issue within the allowed Critical impact scope.

### Likelihood Explanation
Any user who sets `native_token_fee > 0` on a BTC transfer (as shown in the e2e test) and whose transfer is processed by a relayer via `submit_transfer_to_utxo_chain_connector` with a cooperating connector will trigger this. No special attacker capability is needed beyond initiating a standard BTC bridge transfer.

### Recommendation
Validate `native_fee == 0` for UTXO-chain transfers at `ft_on_transfer` time (or at the entry of `submit_transfer_to_utxo_chain_connector`), before `remove_transfer_message` is called. Do not rely on `send_fee_internal` as the sole rejection point, since it executes inside a callback after state has already been committed.

### Proof of Concept
1. User calls `ft_transfer_call` on the nBTC token contract with `msg` containing `native_token_fee: 162` and a BTC recipient address.
2. Bridge stores the transfer with `native_fee = 162`.
3. Trusted relayer calls `submit_transfer_to_utxo_chain_connector` with a connector that accepts tokens (returns `result.0 > 0`).
4. `remove_transfer_message` commits at line 84.
5. Connector's `ft_on_transfer` returns 0 (all tokens accepted).
6. Callback runs: `send_fee_internal` is called with `native_fee = 162`.
7. `origin_chain.is_utxo_chain()` is true → `env::panic_str(NativeFeeForUtxoChain)`.
8. Assert: transfer no longer exists in `pending_transfers`; fee tokens are in bridge contract; relayer received no fee; no refund to user.
