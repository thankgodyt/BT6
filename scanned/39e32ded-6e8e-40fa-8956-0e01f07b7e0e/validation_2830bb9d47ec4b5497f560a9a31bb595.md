Now I have a complete picture of the OmniBridge EVM contract. Let me analyze the exact analog to H-06.

The H-06 vulnerability class is **token type/standard confusion** — the wrong transfer path is selected based on incorrect type detection, causing the wrong amount or type of asset to be transferred. In OmniBridge, the analog is in `finTransfer`'s dispatch logic, which relies entirely on the `multiTokens` mapping to distinguish ERC1155 tokens from ERC20 tokens. The critical flaw is that `initTransfer1155` **never populates** that mapping.

---

### Title
`initTransfer1155` Does Not Populate `multiTokens`, Causing `finTransfer` to Take the Wrong Token-Type Path and Permanently Fail — (`File: evm/src/omni-bridge/contracts/OmniBridge.sol`)

### Summary

`initTransfer1155` locks ERC1155 tokens in the bridge and emits an `InitTransfer` event using a deterministic pseudo-address, but it never writes to the `multiTokens` mapping. `finTransfer` uses that mapping as the sole signal to distinguish ERC1155 tokens from ERC20 tokens. When the mapping is absent, `finTransfer` falls through to the ERC20 branch and calls `IERC20(deterministicToken).safeTransfer(...)` on an address that has no ERC20 code, causing every finalization attempt to revert. Because the NEAR side has already processed the inbound event and burned the user's NEAR-side tokens, the ERC1155 tokens become permanently unrecoverable from the bridge escrow.

### Finding Description

`finTransfer` dispatches on token type using a priority chain:

```solidity
MultiTokenInfo memory multiToken = multiTokens[payload.tokenAddress]; // (1)

if      (payload.tokenAddress == address(0))          { /* ETH */      }
else if (multiToken.tokenAddress != address(0))        { /* ERC-1155 */ }  // (2)
else if (customMinters[payload.tokenAddress] != address(0)) { /* custom */ }
else if (isBridgeToken[payload.tokenAddress])          { /* mint */     }
else    { IERC20(payload.tokenAddress).safeTransfer(...); }              // (3)
``` [1](#0-0) 

The ERC1155 branch at `(2)` fires only when `multiTokens[payload.tokenAddress].tokenAddress != address(0)`. That mapping is written in exactly one place: `logMetadata1155`. [2](#0-1) 

`initTransfer1155`, however, computes the same `deterministicToken` address and locks the ERC1155 tokens, but **never writes to `multiTokens`**: [3](#0-2) 

There is no `require` or guard in `initTransfer1155` that enforces a prior call to `logMetadata1155`. Both functions are permissionless and independent. A user who calls `initTransfer1155` directly — without a preceding `logMetadata1155` — leaves `multiTokens[deterministicToken]` zeroed. When `finTransfer` is later called with `payload.tokenAddress = deterministicToken`, branch `(2)` is skipped and execution falls to branch `(3)`, which calls `IERC20(deterministicToken).safeTransfer(...)`. Because `deterministicToken` is a hash-derived phantom address with no contract code, `safeTransfer` reverts unconditionally.

### Impact Explanation

The ERC1155 tokens are held in the bridge escrow. Every `finTransfer` call for that nonce reverts (the nonce is not consumed because the revert rolls back `completedTransfers[nonce] = true`), so the relayer can retry indefinitely — but every retry fails for the same reason. Meanwhile, the NEAR bridge has already minted (and the user may have already burned) the NEAR-side representation. The ERC1155 tokens are effectively frozen in the bridge with no on-chain path to release them, because `finTransfer` will always take the ERC20 branch for that `deterministicToken`. This constitutes permanent freezing of bridged funds.

### Likelihood Explanation

`initTransfer1155` is a public, permissionless function callable by any token holder. `logMetadata1155` is a separate, optional, permissionless call with no on-chain enforcement linking it to `initTransfer1155`. Any user who reads the ABI and calls `initTransfer1155` directly — without knowing the off-chain convention that `logMetadata1155` must precede it — will trigger this condition. The protocol provides no revert, warning, or guard to prevent it.

### Recommendation

`initTransfer1155` should write to `multiTokens` itself (mirroring the logic in `logMetadata1155`) before emitting the event, so the mapping is always populated when tokens are locked:

```solidity
function initTransfer1155(...) external payable whenNotPaused(PAUSED_INIT_TRANSFER) {
    // ...
    address deterministicToken = deriveDeterministicAddress(tokenAddress, tokenId);

    // Populate mapping so finTransfer can identify this as ERC-1155
    MultiTokenInfo storage info = multiTokens[deterministicToken];
    if (info.tokenAddress == address(0)) {
        info.tokenAddress = tokenAddress;
        info.tokenId = tokenId;
    } else if (info.tokenAddress != tokenAddress || info.tokenId != tokenId) {
        revert ERC1155MappingMismatch();
    }

    IERC1155(tokenAddress).safeTransferFrom(msg.sender, address(this), tokenId, amount, "");
    // ...
}
```

Alternatively, require that `multiTokens[deterministicToken].tokenAddress != address(0)` at the top of `initTransfer1155`, forcing callers to invoke `logMetadata1155` first.

### Proof of Concept

1. Deploy the bridge. Do **not** call `logMetadata1155`.
2. User calls `initTransfer1155(erc1155Addr, tokenId, 5, 0, 0, "alice.near", "")`.
   - ERC1155 tokens are transferred to the bridge.
   - `multiTokens[deterministicToken]` remains `{address(0), 0}`.
3. NEAR bridge processes the `InitTransfer` event and mints 5 units on NEAR for `alice.near`.
4. Alice burns her NEAR tokens; NEAR bridge signs a `finTransfer` payload with `payload.tokenAddress = deterministicToken`.
5. Relayer calls `finTransfer(sig, payload)`.
   - `multiTokens[deterministicToken].tokenAddress == address(0)` → ERC1155 branch skipped.
   - Falls to `IERC20(deterministicToken).safeTransfer(alice, 5)` → reverts (no code at `deterministicToken`).
6. Transaction reverts; ERC1155 tokens remain locked; NEAR tokens are already burned. Funds are permanently frozen. [4](#0-3) [5](#0-4) [6](#0-5)
