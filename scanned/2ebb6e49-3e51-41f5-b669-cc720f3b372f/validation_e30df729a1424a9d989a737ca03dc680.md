### Title
Partial `ft_on_transfer` Refund Permanently Freezes Bridged Tokens in `fin_transfer_send_tokens_callback` — (`near/omni-bridge/src/lib.rs`)

---

### Summary

`is_refund_required` uses a binary all-or-nothing check (`amount.0 == 0`) on the `ft_transfer_call` result. When a NEAR recipient contract partially rejects tokens — returning `R > 0` but `R < amount_without_fee` from `ft_on_transfer` — the bridge treats the transfer as fully successful, finalizes the nonce, and sends the relayer fee. The `R` tokens returned to the bridge by the token contract's `ft_resolve_transfer` are permanently stuck in the bridge contract with no recovery path.

---

### Finding Description

In `fin_transfer_send_tokens_callback`, the bridge sends `amount_without_fee` tokens to the recipient via `ft_transfer_call` when a `msg` is present. The callback then calls `is_refund_required` to decide whether to revert the transfer:

```rust
fn is_refund_required(is_ft_transfer_call: bool) -> bool {
    if is_ft_transfer_call {
        match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
            Ok(value) => {
                if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {
                    // Normal case: refund if the used token amount is zero
                    amount.0 == 0   // ← only handles full rejection
                } else {
                    false
                }
            }
            Err(_) => false,
        }
    } else {
        false
    }
}
``` [1](#0-0) 

In NEP-141, `ft_transfer_call` returns the amount **used** (i.e., `sent - refund`). If `ft_on_transfer` returns a partial refund `R` where `0 < R < amount_without_fee`, then `ft_transfer_call` returns `amount_without_fee - R > 0`. The check `amount.0 == 0` is false, so `is_refund_required` returns `false`. The bridge:

1. Does **not** call `revert_lock_actions` — the `locked_tokens` counter is not restored.
2. Does **not** call `burn_tokens_if_needed` — for bridged tokens, the `R` minted tokens are not burned.
3. Sends the relayer fee and emits `FinTransferEvent` — the transfer is permanently finalized. [2](#0-1) 

The `R` tokens returned to the bridge by `ft_resolve_transfer` are now orphaned in the bridge contract's balance with no function to recover them.

The same `is_refund_required` logic is reused in `resolve_fast_transfer` and `resolve_utxo_fin_transfer`, making those paths equally affected. [3](#0-2) [4](#0-3) 

---

### Impact Explanation

Bridged funds are permanently frozen. The transfer nonce is consumed (`finalised_transfers` is marked), so the transfer cannot be re-submitted. The `R` tokens are stuck in the bridge contract with no admin recovery function. For native (non-bridged) tokens, the bridge holds `R` extra tokens not tracked by `locked_tokens`. For bridged tokens, `R` extra minted tokens exist in the bridge's balance and are never burned, inflating supply relative to the locked collateral on the source chain.

---

### Likelihood Explanation

Any user who initiates a transfer to a NEAR contract recipient and includes a non-empty `msg` field triggers `ft_transfer_call` instead of `ft_transfer`. Many legitimate NEAR DeFi contracts (DEXes, vaults, lending protocols) implement `ft_on_transfer` with capacity limits or conditional acceptance that can return a non-zero partial refund. This is a standard NEP-141 pattern, not an adversarial one. The user controls the `msg` field and the recipient address — both are unprivileged inputs accepted by the bridge.

---

### Recommendation

In `fin_transfer_send_tokens_callback`, read the actual used amount from the promise result and compare it against `amount_without_fee`. If `used_amount < amount_without_fee`, treat the difference as a partial refund and handle it explicitly — either by re-locking the partial refund tokens (restoring the `locked_tokens` counter), burning them (for bridged tokens), or returning them to the original sender. The check should be:

```rust
// Instead of: amount.0 == 0
// Use:
amount.0 < expected_amount_without_fee
```

and handle the partial-refund case with the same revert logic currently applied to the full-rejection case.

---

### Proof of Concept

The existing integration test at `near/omni-tests/src/fin_transfer.rs` lines 533–544 directly demonstrates the stuck-token outcome:

```rust
#[case(FinTransferWithMsgCase {
    amount: 1000,
    fee: 1,
    msg: TokenReceiverMessage {
        return_value: U128(1),   // receiver returns 1 token unused
        panic: false,
        extra_msg: String::new(),
    },
    expected_recipient_balance: 998,   // recipient receives 998, not 999
    expected_relayer_balance: 1,       // relayer gets fee — transfer "succeeded"
    expected_locker_balance: 1,        // 1 token permanently stuck in bridge
})]
``` [5](#0-4) 

The `expected_locker_balance: 1` confirms that 1 token is permanently frozen in the bridge contract after a partial rejection. The transfer nonce is consumed, the fee is paid, and there is no mechanism to recover the stuck token.
