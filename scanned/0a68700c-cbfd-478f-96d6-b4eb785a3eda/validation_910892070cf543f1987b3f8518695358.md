### Title
Unchecked Arithmetic in `denormalize_amount` Produces Wrong Token Amounts Due to Missing Decimal Validation — (`near/omni-bridge/src/lib.rs`)

### Summary

The `add_token` helper stores `decimals` and `origin_decimals` without validating that `origin_decimals >= decimals`. The `denormalize_amount` function then performs a bare `u8` subtraction followed by an unchecked `u128` multiplication. If a token is registered with `origin_decimals < decimals`, the subtraction underflows (wraps in Rust release mode), producing a large exponent, and the subsequent multiplication overflows, yielding a completely wrong denormalized amount that is minted or transferred to the recipient.

### Finding Description

`add_token` inserts a `Decimals` struct into storage with no invariant check: [1](#0-0) 

`denormalize_amount` then computes the scale factor with two unchecked operations: [2](#0-1) 

- **Line 2777**: `decimals.origin_decimals - decimals.decimals` is a `u8` subtraction. If `origin_decimals < decimals`, it wraps (e.g., `6u8 - 18u8 = 246u8` in release mode).
- **Line 2778**: `amount * (10_u128.pow(diff_decimals))` — with `diff_decimals = 246`, `10_u128.pow(246)` overflows `u128` and wraps to an arbitrary value; the subsequent multiplication is equally wrong.

The same unchecked subtraction appears in `normalize_amount`: [3](#0-2) 

`denormalize_amount` is called directly in the critical `fin_transfer_callback` path that determines how many tokens are minted or released to the recipient: [4](#0-3) 

It is also called in `fast_fin_transfer` and `claim_fee_callback`: [5](#0-4) [6](#0-5) 

The `Decimals` struct itself imposes no ordering constraint: [7](#0-6) 

The `bind_token_callback` path, which is the only path that stores `origin_decimals != decimals`, passes the values from the prover result directly into `add_token` without any range check: [8](#0-7) 

The prover result fields originate from the EVM `DeployToken` event: [9](#0-8) 



### Impact Explanation

If a token is registered with `origin_decimals < decimals`, every subsequent call to `denormalize_amount` for that token produces a wrapped, incorrect `u128` value. In `fin_transfer_callback` this wrong value becomes the `amount` field of the `TransferMessage`, so the recipient is minted or released a completely wrong number of tokens — either far too many (unauthorized minting / balance inflation) or effectively zero (permanent loss of bridged funds). In `claim_fee_callback` the wrong denormalized amount feeds the fee computation `transfer_message.amount.0 - denormalized_amount`, which can underflow and panic or produce an inflated fee that drains the transfer. All affected transfers for that token are permanently broken.

### Likelihood Explanation

The `bind_token` entry point requires a valid proof verified by the registered prover, so the `DeployToken` event must originate from the registered EVM factory contract. If the EVM contract emits `originDecimals < decimals` — whether by a logic bug, a misconfigured token, or a future upgrade — the NEAR contract has no defense-in-depth check to reject it. The NEAR contract is the last line of defense and it performs no validation. Likelihood is low-to-medium: it requires the EVM bridge contract to emit inverted decimal values, but the NEAR contract provides zero protection against this.

### Recommendation

1. **Short term**: Add an explicit invariant check in `add_token` that `origin_decimals >= decimals`, reverting if violated.
2. **Short term**: Replace the bare `*` in `denormalize_amount` with `checked_mul`, and the bare `-` in both functions with `checked_sub`, panicking with a descriptive error on overflow/underflow.
3. **Long term**: Consider using a fuzzer (e.g., `cargo-fuzz`) or property-based tests to verify that `denormalize_amount(normalize_amount(x)) <= x` holds for all valid decimal configurations and that no arithmetic operation panics or wraps.

### Proof of Concept

1. EVM bridge contract emits a `DeployToken` event with `decimals = 18` and `originDecimals = 6` (inverted).
2. A relayer submits a valid proof of this event via `bind_token`.
3. `bind_token_callback` calls `add_token(token_id, token_address, 18, 6)` — no validation fires.
4. A user bridges tokens from EVM to NEAR; `fin_transfer_callback` is invoked.
5. `denormalize_amount(amount, Decimals { decimals: 18, origin_decimals: 6 })` executes:
   - `diff_decimals = 6u8 - 18u8` → wraps to `246u8` → cast to `246u32`
   - `10_u128.pow(246)` → overflows `u128`, wraps to an arbitrary value `W`
   - `amount * W` → produces a wrong result `R`
6. `TransferMessage { amount: R, … }` is stored and `R` tokens are minted to the recipient.
7. The recipient receives a completely wrong token balance; the correct bridged amount is lost or inflated permanently. [2](#0-1) [1](#0-0) [10](#0-9)
