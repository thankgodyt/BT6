### Title
Chain-Level ID Without Contract-Address Binding in `finTransfer` Signed Message Enables Cross-Contract Replay — (`evm/src/omni-bridge/contracts/OmniBridge.sol`, `starknet/src/bridge_types.cairo`, `solana/programs/bridge_token_factory/src/state/message/finalize_transfer.rs`)

### Summary
The Borsh-encoded message signed by the NEAR MPC key for `finTransfer` / `fin_transfer` / `finalize_transfer` across all three foreign-chain bridge implementations binds only to a chain-level identifier (`omniBridgeChainId` / `omni_bridge_chain_id` / `SOLANA_OMNI_BRIDGE_CHAIN_ID`) and never to the specific bridge contract address. This is the direct analog of the reported `allowedDiscriminator1` (open/network-level discriminator) vulnerability: a valid MPC signature produced for one bridge contract on a given chain is cryptographically valid on any other bridge contract deployed on the same chain with the same chain-ID byte, because the `completedTransfers` / `is_transfer_finalised` / `UsedNonces` replay guard is per-contract, not global.

### Finding Description

**EVM (`OmniBridge.sol` / `OmniBridgeWormhole.sol`)**

`finTransfer` constructs the signed payload as:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.TransferMessage)),
    Borsh.encodeUint64(payload.destinationNonce),
    bytes1(payload.originChain),
    Borsh.encodeUint64(payload.originNonce),
    bytes1(omniBridgeChainId),          // ← chain-level byte only
    Borsh.encodeAddress(payload.tokenAddress),
    Borsh.encodeUint128(payload.amount),
    bytes1(omniBridgeChainId),          // ← chain-level byte only
    Borsh.encodeAddress(payload.recipient),
    ...
);
bytes32 hashed = keccak256(borshEncoded);
if (ECDSA.recover(hashed, signatureData) != nearBridgeDerivedAddress) {
    revert InvalidSignature();
}
```

`address(this)` is never included. The replay guard is `completedTransfers[payload.destinationNonce]`, which is a per-contract mapping. [1](#0-0) 

**Starknet (`bridge_types.cairo`)**

`TransferMessagePayloadImpl::to_borsh` encodes `chain_id` (the `omni_bridge_chain_id` storage value) twice but never the contract's own address:

```cairo
fn to_borsh(self: @TransferMessagePayload, chain_id: u8) -> ByteArray {
    ...
    borsh_bytes.append_byte(chain_id);   // ← chain-level byte only
    borsh_bytes.append(@borsh::encode_address(*self.token_address));
    ...
    borsh_bytes.append_byte(chain_id);   // ← chain-level byte only
    borsh_bytes.append(@borsh::encode_address(*self.recipient));
    ...
}
```

The replay guard is `completed_transfers` (a per-contract bitmap). [2](#0-1) [3](#0-2) 

**Solana (`finalize_transfer.rs`)**

`FinalizeTransferPayload::serialize_for_near` encodes `SOLANA_OMNI_BRIDGE_CHAIN_ID` (a compile-time constant) but never the program ID:

```rust
writer.write_all(&[SOLANA_OMNI_BRIDGE_CHAIN_ID])?;  // ← chain-level byte only
params.0.serialize(&mut writer)?;  // mint pubkey
...
writer.write_all(&[SOLANA_OMNI_BRIDGE_CHAIN_ID])?;  // ← chain-level byte only
params.1.serialize(&mut writer)?;  // recipient pubkey
```

The replay guard is the per-program `UsedNonces` PDA. [4](#0-3) 

The `nearBridgeDerivedAddress` / `omni_bridge_derived_address` / `derived_near_bridge_address` is the same NEAR MPC key across all bridge deployments, so any signature that passes on one contract is structurally valid on another contract with the same chain-ID byte. [5](#0-4) [6](#0-5) 

### Impact Explanation

If two bridge contracts sharing the same `omniBridgeChainId` coexist on the same chain (e.g., during a protocol migration from `OmniBridge` to `OmniBridgeWormhole` on Ethereum, or deployment of a new bridge version alongside the old one), a relayer or attacker can:

1. Obtain a valid MPC-signed `finTransfer` payload for bridge A (nonce N, amount X).
2. Submit it to bridge A → tokens released, nonce N marked used **only in A's** `completedTransfers`.
3. Submit the identical signature to bridge B → nonce N is **not** marked used in B's `completedTransfers`; signature verification passes because the signed bytes are identical; bridge B releases tokens again.

Result: double-spending of bridged funds. The attacker receives 2× the intended amount, draining bridge B's token reserves.

### Likelihood Explanation

The current production deployment has exactly one bridge contract per chain, so the vulnerability is not immediately exploitable. However, the likelihood becomes concrete in the following realistic scenarios:

- **Protocol migration**: deploying a new bridge version (e.g., upgrading from light-client to Wormhole on Ethereum) while the old contract remains live during a transition window.
- **Parallel deployments**: the codebase contains both `OmniBridge.sol` and `OmniBridgeWormhole.sol`, which are separate deployable contracts (not just an in-place upgrade), both using the same `omniBridgeChainId` byte.
- **Starknet**: the constructor takes `omni_bridge_chain_id` as a parameter; a second deployment with the same value is trivially possible. [7](#0-6) [8](#0-7) 

### Recommendation

Include the specific bridge contract address in the signed payload so that a signature is cryptographically bound to exactly one contract:

**EVM**: append `Borsh.encodeAddress(address(this))` to `borshEncoded` before hashing.

**Starknet**: append `get_contract_address()` (as a felt252/address) to the borsh bytes inside `to_borsh`.

**Solana**: include the program ID (`crate::ID`) in `serialize_for_near`.

This mirrors the `allowedDiscriminator2 = allowedDiscriminator1 + uint160(address(this))` fix recommended in the external report — binding the signature to the specific contract, not just the chain.

### Proof of Concept

1. Deploy two EVM bridge contracts on Ethereum (`omniBridgeChainId = 0`), both pointing to the same `nearBridgeDerivedAddress`. Call them `BridgeA` and `BridgeB`. Both hold locked USDC.
2. User initiates a transfer of 1000 USDC from NEAR → Ethereum, recipient = attacker.
3. NEAR MPC signs `TransferMessage{destinationNonce=42, originChain=1, originNonce=7, omniBridgeChainId=0, tokenAddress=USDC, amount=1000, recipient=attacker, ...}`.
4. Attacker calls `BridgeA.finTransfer(sig, payload)` → `completedTransfers[42] = true` in BridgeA; attacker receives 1000 USDC from BridgeA.
5. Attacker calls `BridgeB.finTransfer(sig, payload)` → `completedTransfers[42]` in BridgeB is `false`; `ECDSA.recover(keccak256(borshEncoded), sig) == nearBridgeDerivedAddress` passes (identical bytes, identical signature); attacker receives another 1000 USDC from BridgeB.
6. Net result: 2000 USDC extracted for a 1000 USDC transfer — double-spend. [9](#0-8) [10](#0-9)
