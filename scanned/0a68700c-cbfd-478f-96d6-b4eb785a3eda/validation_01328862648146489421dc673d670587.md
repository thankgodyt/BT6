### Title
`#[trusted_relayer]` on `claim_fee` permanently locks earned fees for resigned or revoked relayers — (`File: near/omni-bridge/src/lib.rs`)

### Summary

The `claim_fee` function in the NEAR `omni-bridge` contract is gated by `#[trusted_relayer]`, which prevents any caller who is not currently an active trusted relayer from invoking it. However, `claim_fee_callback` already enforces `fee_recipient == *predecessor_account_id`, meaning only the legitimate fee recipient can ever succeed. The trusted-relayer check is therefore redundant for security but creates an overly restrictive gate: a relayer who earned fees and then resigned (or was revoked) can never claim those fees, permanently locking them in the contract.

### Finding Description

`claim_fee` is decorated with `#[trusted_relayer]`: [1](#0-0) 

Inside `claim_fee_callback`, the contract already enforces that only the fee recipient recorded in the on-chain proof can claim: [2](#0-1) 

The `#[trusted_relayer]` gate therefore adds no security value — it only restricts *who can submit the call*, while the callback independently restricts *who can receive the funds*. These two checks are orthogonal: a relayer's trusted status has no bearing on whether they legitimately earned a fee.

The trusted-relayer lifecycle allows two paths that strip a relayer of their status:

1. **Self-resignation** — a relayer calls `resign_trusted_relayer` to recover their staked NEAR. After this, `is_trusted_relayer` returns `false`.
2. **DAO revocation** — the DAO calls `reject_relayer_application` on an active relayer, which also strips trusted status and transfers the stake to the DAO. [3](#0-2) [4](#0-3) 

In both cases, any fees the relayer earned (recorded in `pending_transfers` with their account as `fee_recipient`) become permanently unclaimable. No other account can claim them either, because the callback rejects any caller who is not the `fee_recipient`. There is no admin recovery path.

### Impact Explanation

Earned bridge fees are permanently frozen inside the NEAR `omni-bridge` contract. The `pending_transfers` entry for the transfer remains, but neither the relayer (no longer trusted) nor anyone else (not the fee recipient) can ever call `claim_fee` successfully. This is a direct, permanent loss of bridged-asset-denominated funds for the relayer.

### Likelihood Explanation

The resign path is self-triggered and realistic: a relayer completes a batch of `fin_transfer` operations, resigns to recover their 1,000 NEAR stake, and then discovers that the `claim_fee` proofs (which require waiting for destination-chain finality) can no longer be submitted. The DAO-revocation path is less common but equally effective. Neither path requires any privileged compromise — resignation is a normal, documented relayer action.

### Recommendation

Remove `#[trusted_relayer]` from `claim_fee`. The `claim_fee_callback` check `fee_recipient == *predecessor_account_id` is the correct and sufficient authorization gate. Claiming a fee does not affect the caller's trusted-relayer status, so the trusted-relayer check is both unnecessary and harmful.

### Proof of Concept

1. Relayer `R` stakes 1,000 NEAR and becomes a trusted relayer.
2. `R` calls `fin_transfer` for a user's EVM→NEAR transfer. The transfer message is stored in `pending_transfers` with `fee_recipient = R`.
3. `R` calls `resign_trusted_relayer` to recover their stake. `is_trusted_relayer(R)` now returns `false`.
4. The destination-chain `fin_transfer` transaction is finalized. `R` constructs a valid `ClaimFeeArgs` proof.
5. `R` calls `claim_fee(args)`. The `#[trusted_relayer]` macro panics before the function body executes.
6. No other account can call `claim_fee` with this proof and succeed, because `claim_fee_callback` enforces `fee_recipient == predecessor_account_id`.
7. The fee is permanently locked in `pending_transfers`. [1](#0-0) [5](#0-4)
