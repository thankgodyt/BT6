### Title
Pause Bypass via `finish_withdraw_v2` Allows Transfer Initiation When Bridge Is Paused — (File: `near/omni-bridge/src/lib.rs`)

### Summary
The `finish_withdraw_v2` function in the NEAR bridge contract lacks a pause check. Any deployed bridge token contract can call it to initiate an outbound transfer even when the bridge is fully paused, burning the user's tokens and creating a pending transfer that cannot be completed until the bridge is unpaused.

### Finding Description
The NEAR bridge contract implements a selective pause mechanism via `near_plugins::Pausable`. Every public transfer-initiation and transfer-finalization entry point is decorated with `#[pause]` or `#[pause(except(roles(...)))]`:

- `ft_on_transfer` — `#[pause(except(roles(Role::DAO, Role::UnrestrictedDeposit)))]` [1](#0-0) 
- `sign_transfer` — `#[pause(except(roles(Role::DAO)))]` [2](#0-1) 
- `fin_transfer` — `#[pause(except(roles(Role::DAO)))]` [3](#0-2) 
- `claim_fee` — `#[pause(except(roles(Role::DAO)))]` [4](#0-3) 

However, `finish_withdraw_v2` carries **no pause attribute at all**:

```rust
pub fn finish_withdraw_v2(
    &mut self,
    #[serializer(borsh)] sender_id: &AccountId,
    #[serializer(borsh)] amount: u128,
    #[serializer(borsh)] recipient: String,
) {
    let token_id = env::predecessor_account_id();
    require!(self.is_deployed_token(&token_id),);

    self.current_origin_nonce += 1;
    let destination_nonce = self.get_next_destination_nonce(ChainKind::Eth);
    ...
    env::log_str(&OmniBridgeEvent::InitTransferEvent { transfer_message }.to_log_string());
}
``` [5](#0-4) 

This function is a public cross-contract entry point. A deployed bridge token contract calls it as part of its withdrawal flow (the token burns the user's balance and then calls `finish_withdraw_v2` on the bridge). Because the pause guard is absent, the call succeeds even when the bridge is paused.

### Impact Explanation
When the bridge is paused (typically in response to a security incident), a user can still:

1. Call `ft_transfer_call` on a deployed bridge token contract.
2. The token contract burns the user's tokens and calls `finish_withdraw_v2` on the bridge.
3. `finish_withdraw_v2` executes without checking the pause state, increments `current_origin_nonce` and `destination_nonces`, stores a `TransferMessage` in `pending_transfers`, and emits an `InitTransferEvent`.
4. The transfer is permanently stuck in pending state because `sign_transfer` is paused and cannot produce the MPC signature needed to finalize on the EVM side.

The user's tokens are irreversibly burned at step 2. If the bridge remains paused indefinitely, or if a subsequent upgrade removes or ignores the stale pending transfers, those funds are permanently lost. Even in the best case the user suffers an unintended, indefinite freeze of bridged assets — exactly the class of harm the pause mechanism is designed to prevent.

### Likelihood Explanation
Any holder of a deployed bridge token (e.g., `eth.bridge.near` wrapped tokens) can trigger this path without any special role or permission. The only precondition is that the bridge is paused, which is precisely the emergency state where the protection is most needed. Users who are unaware of the bridge-level pause (they only interact with the token contract) will naturally attempt withdrawals and unknowingly burn their tokens.

### Recommendation
Add the same pause guard used on every other transfer-initiation function:

```rust
#[pause(except(roles(Role::DAO)))]
pub fn finish_withdraw_v2(
    &mut self,
    ...
```

This mirrors the pattern already applied to `ft_on_transfer`, `sign_transfer`, `fin_transfer`, and `claim_fee`.

### Proof of Concept
1. Admin calls `pause` on the NEAR bridge contract, setting the paused state.
2. User calls `ft_transfer_call` on a deployed bridge token contract (e.g., `eth.bridge.near`) with a withdrawal message.
3. The token contract burns the user's balance and cross-contract-calls `finish_withdraw_v2` on the bridge.
4. `finish_withdraw_v2` executes: `current_origin_nonce` is incremented, a `TransferMessage` is inserted into `pending_transfers`, and `InitTransferEvent` is emitted — all without any pause check.
5. A relayer attempts to call `sign_transfer` to produce the MPC signature; the call reverts because `sign_transfer` is paused.
6. The user's tokens remain burned with no path to recovery while the bridge is paused.

    #[allow(clippy::needless_pass_by_value)]
    pub fn finish_withdraw_v2(
        &mut self,
        #[serializer(borsh)] sender_id: &AccountId,
        #[serializer(borsh)] amount: u128,
        #[serializer(borsh)] recipient: String,
    ) {
        let token_id = env::predecessor_account_id();
        require!(self.is_deployed_token(&token_id),);

        self.current_origin_nonce += 1;
        let destination_nonce = self.get_next_destination_nonce(ChainKind::Eth);

        let transfer_message = TransferMessage {
            origin_nonce: self.current_origin_nonce,
            token: OmniAddress::Near(token_id),
            amount: U128(amount),
            recipient: OmniAddress::Eth(
                H160::from_str(&recipient).near_expect(BridgeError::InvalidRecipientAddress),
            ),
            fee: Fee {
                fee: U128(0),
                native_fee: U128(0),
            },
            sender: OmniAddress::Near(sender_id.clone()),
            msg: String::new(),
            destination_nonce,
            origin_transfer_id: None,
        };

        let required_storage_balance =
            self.add_transfer_message(transfer_message.clone(), sender_id.clone());

        self.update_storage_balance(
            env::current_account_id(),
            required_storage_balance,
            NearToken::from_yoctonear(0),
        );

        env::log_str(&OmniBridgeEvent::InitTransferEvent { transfer_message }.to_log_string());
    }
