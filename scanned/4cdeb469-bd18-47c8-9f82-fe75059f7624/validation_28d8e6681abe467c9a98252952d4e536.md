### Title
Fee-on-Transfer Token Balance Mis-Accounting Enables Unbacked Token Minting on NEAR — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

`OmniBridge.initTransfer` uses the caller-supplied `amount` parameter to emit the `InitTransfer` event without verifying the actual tokens received. For fee-on-transfer tokens, the bridge locks fewer tokens than the event claims. The NEAR `fin_transfer_callback` trusts the event's `amount` field verbatim to mint or unlock tokens, creating unbacked token supply and eventual bridge insolvency for that token.

---

### Finding Description

**Root cause — EVM side (`OmniBridge.sol`):**

In `initTransfer`, for non-bridge, non-custom ERC20 tokens, the code path is:

```solidity
IERC20(tokenAddress).safeTransferFrom(
    msg.sender,
    address(this),
    amount          // caller-supplied, not verified
);
```

followed immediately by:

```solidity
emit BridgeTypes.InitTransfer(
    msg.sender,
    tokenAddress,
    currentOriginNonce,
    amount,         // same caller-supplied value, no balance-delta check
    fee,
    nativeFee,
    recipient,
    message
);
``` [1](#0-0) 

No `balanceOf` snapshot is taken before or after the transfer. The emitted `amount` is whatever the caller passed in, not the actual tokens received by the contract.

**Root cause — NEAR side (`near/omni-bridge/src/lib.rs`):**

`fin_transfer_callback` parses the verified `InitTransferMessage` (reconstructed from the EVM event by the prover) and builds the `TransferMessage` using the event's `amount` field directly:

```rust
let transfer_message = TransferMessage {
    origin_nonce: init_transfer.origin_nonce,
    token: init_transfer.token,
    amount: Self::denormalize_amount(init_transfer.amount.0, decimals).into(),
    ...
};
``` [2](#0-1) 

For deployed (bridged) tokens this amount is minted; for native NEAR tokens it is unlocked from the bridge's reserves. The NEAR side has no way to know the EVM bridge received fewer tokens than the event claims.

**Event structure confirms the gap:**

The `InitTransfer` event carries `uint128 amount` as a plain field with no on-chain proof of actual receipt. [3](#0-2) 

**Acknowledged but unmitigated:**

The EVM `SECURITY.md` explicitly states: *"Fee-on-transfer tokens not supported: `initTransfer` emits the requested `amount`, not the actual received balance."* [4](#0-3) 

"Not supported" is a documentation note, not an on-chain guard. There is no `require` or allowlist preventing a fee-on-transfer token from being used with `initTransfer`.

---

### Impact Explanation

**Critical — escrow mis-accounting / unauthorized minting.**

For a fee-on-transfer token with a `k%` fee:
- EVM bridge receives `amount × (1 − k/100)` tokens.
- NEAR mints `amount` tokens to the recipient.
- The bridge is immediately insolvent by `amount × k/100` tokens per transfer.

An attacker who accumulates these extra NEAR-side tokens and bridges them back forces the EVM bridge to release tokens it does not hold, permanently freezing the shortfall for later redeemers. This is a direct, quantifiable loss of bridged funds for honest users.

---

### Likelihood Explanation

The bridge is fully permissionless: `logMetadata` and `deployToken` are callable by anyone, and `initTransfer` accepts any ERC20 address. A malicious actor can:
1. Deploy or reuse an existing fee-on-transfer ERC20.
2. Register it via `logMetadata` → `deployToken`.
3. Repeatedly call `initTransfer` to accumulate unbacked NEAR-side tokens.
4. Bridge those tokens back to drain the EVM escrow.

No admin compromise, no key leak, and no threshold-signature collusion is required. The entry path is a standard public EVM call.

---

### Recommendation

Measure the actual balance delta after `safeTransferFrom` and use that value — not the caller-supplied `amount` — in the emitted event:

```solidity
uint256 balanceBefore = IERC20(tokenAddress).balanceOf(address(this));
IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
uint256 actualReceived = IERC20(tokenAddress).balanceOf(address(this)) - balanceBefore;
// Use actualReceived (cast to uint128 with overflow check) in the event and downstream logic.
```

This pattern eliminates the discrepancy for both fee-on-transfer and rebasing tokens without requiring an allowlist.

---

### Proof of Concept

1. Deploy `FeeToken` — a standard ERC20 that deducts 10% on every `transferFrom`.
2. Call `OmniBridge.logMetadata(feeTokenAddress)` → relayer submits proof to NEAR → NEAR deploys `omni-fee-token.bridge.near`.
3. Approve OmniBridge for 1 000 `FeeToken`. Call `initTransfer(feeTokenAddress, 1000, 0, 0, "near:attacker.near", "")`.
   - Bridge receives 900 tokens (10% fee).
   - `InitTransfer` event emits `amount = 1000`.
4. Relayer submits the light-client / Wormhole proof to NEAR `fin_transfer`. `fin_transfer_callback` reads `init_transfer.amount = 1000`, calls `ext_token::mint(attacker, 1000)`.
   - Attacker now holds 1 000 NEAR-side bridge tokens backed by only 900 EVM tokens.
5. Attacker calls `ft_transfer_call` on NEAR to bridge 1 000 tokens back to EVM. NEAR burns 1 000 bridge tokens; MPC signs a `finTransfer` payload for 1 000 tokens.
6. Attacker submits `finTransfer` on EVM. Bridge attempts `safeTransfer(attacker, 1000)` but only holds 900 — **reverts for the attacker** if balance is exactly 900, or **drains 100 tokens from other users' deposits** if the pool has been topped up by other transfers.
7. Repeated across many transfers, the bridge accumulates a growing shortfall, permanently freezing the last redeemers' funds. [5](#0-4) [6](#0-5)
