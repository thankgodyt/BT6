### Title
Unauthenticated `log_metadata` Allows Any Caller to Obtain MPC-Signed Token Metadata, Enabling Fake Bridge Token Deployment on Foreign Chains — (File: `near/omni-bridge/src/lib.rs`)

---

### Summary

The `log_metadata` function in the NEAR omni-bridge contract carries no caller authentication. Any NEAR account can invoke it with an arbitrary `token_id`, including a malicious token contract that returns fabricated metadata. The bridge will fetch that metadata via `ft_metadata()`, sign it with the MPC key, and emit a `LogMetadataEvent`. The resulting MPC-signed payload is sufficient to call `deploy_token` on Starknet or Solana, deploying a fake bridge token with attacker-chosen name, symbol, and decimals — with no further authorization required on those chains.

---

### Finding Description

`log_metadata` is decorated only with `#[pause(except(roles(Role::DAO)))]` and carries no role-based access control on the caller: [1](#0-0) 

Any NEAR account may call this function with any `token_id`. The bridge unconditionally calls `ft_metadata()` on that account and forwards the result to the MPC signer: [2](#0-1) 

The MPC-signed `MetadataPayload` is then emitted as a `LogMetadataEvent`. On Starknet, `deploy_token` accepts this payload and verifies only the MPC signature — no factory or registry check is performed: [3](#0-2) 

The same is true on Solana — `deploy_token` verifies only the MPC signature against `derived_near_bridge_address`: [4](#0-3) 

The `_verify_borsh_signature` helper on Starknet confirms that the only gate is the MPC-derived Ethereum address: [5](#0-4) 

There is no check that the `token_id` passed to `log_metadata` is a token already registered in the bridge, a token deployed through the official deployer, or a token belonging to a known factory.

---

### Impact Explanation

An attacker deploys a malicious NEAR token contract whose `ft_metadata()` returns fabricated values — for example `name = "USD Coin"`, `symbol = "USDC"`, `decimals = 6`. After calling `log_metadata` on the bridge, the attacker holds a valid MPC signature over that payload. They submit it to `deploy_token` on Starknet or Solana, where a new bridge token is created and registered as a legitimate bridge-issued asset. Users who discover this token by name or symbol — e.g., through a DEX aggregator or wallet token list — may bridge real assets to it, receiving worthless tokens in return. This constitutes token metadata binding confusion leading to user fund loss, which falls within the critical impact scope.

---

### Likelihood Explanation

The attack is fully permissionless. Deploying a NEAR token contract is cheap and requires no special role. Calling `log_metadata` requires only a small attached deposit for MPC gas. The attacker needs no insider access, no compromised key, and no admin role. The only prerequisite is that users can be directed to the fake token — a realistic social-engineering or front-end poisoning scenario given that the fake token carries an identical name and symbol to a well-known asset.

---

### Recommendation

Add caller authentication to `log_metadata`. The simplest fix is to restrict it to accounts holding an appropriate role, for example:

```rust
#[access_control_any(roles(Role::DAO, Role::MetadataManager))]
#[pause(except(roles(Role::DAO)))]
pub fn log_metadata(&self, token_id: &AccountId) -> Promise { ... }
```

Alternatively, require that `token_id` is already registered in `token_address_to_id` or `deployed_tokens` before proceeding, so only tokens that have gone through the official proof-verified deployment path can have their metadata signed.

---

### Proof of Concept

1. Attacker deploys `fake-usdc.attacker.near` — a NEAR contract whose `ft_metadata()` returns `{ name: "USD Coin", symbol: "USDC", decimals: 6 }`.
2. Attacker calls `omni-bridge.near::log_metadata("fake-usdc.attacker.near")` with sufficient attached deposit for MPC gas.
3. The bridge calls `ft_metadata()` on `fake-usdc.attacker.near`, receives the fabricated metadata, and forwards it to the MPC signer.
4. The MPC signer returns a valid `SignatureResponse`; the bridge emits `LogMetadataEvent { signature, metadata_payload }`.
5. Attacker extracts the signature and `MetadataPayload` from the event.
6. Attacker calls `deploy_token(signature, payload)` on the Starknet `OmniBridge` contract. The contract verifies the MPC signature (passes), checks that no token with this `token_id` hash is already deployed (passes, since this is a new fake token), and deploys a new `BridgeToken` named "USD Coin / USDC".
7. The fake USDC token is now a registered bridge token on Starknet. Any user who bridges to it receives worthless tokens while their real assets are locked or burned on the origin chain.

    #[private]
    #[result_serializer(borsh)]
    pub fn log_metadata_callback(
        &self,
        #[callback] metadata: FungibleTokenMetadata,
        token_id: &AccountId,
    ) -> Promise {
        require!(
            !metadata.name.is_empty() && !metadata.symbol.is_empty(),
            BridgeError::InvalidMetadata.as_ref()
        );

        let metadata_payload = MetadataPayload {
            prefix: PayloadType::Metadata,
            token: token_id.to_string(),
            name: metadata.name,
            symbol: metadata.symbol,
            decimals: metadata.decimals,
        };

        let payload = near_sdk::env::keccak256_array(
            borsh::to_vec(&metadata_payload).near_expect(BridgeError::Borsh),
        );

        ext_signer::ext(self.mpc_signer.clone())
            .with_static_gas(MPC_SIGNING_GAS)
            .with_attached_deposit(env::attached_deposit())
            .sign(SignRequest {
                payload,
                path: SIGN_PATH.to_owned(),
                key_version: 0,
            })
            .then(
                Self::ext(env::current_account_id())
                    .with_static_gas(SIGN_LOG_METADATA_CALLBACK_GAS)
                    .sign_log_metadata_callback(metadata_payload),
            )
    }

    fn _verify_borsh_signature(
        ref self: ContractState, borsh_bytes: @ByteArray, signature: Signature,
    ) {
        let message_hash_le = compute_keccak_byte_array(borsh_bytes);
        let message_hash = reverse_u256_bytes(message_hash_le);

        let sig = signature_from_vrs(signature.v, signature.r, signature.s);
        verify_eth_signature(message_hash, sig, self.omni_bridge_derived_address.read());
    }
