### Title
`deploy_token` Executes Without Pause Check, Bypassing `ALL_PAUSED` Gate — (`solana/programs/bridge_token_factory/src/lib.rs`)

### Summary

The Solana bridge program defines a two-bit pause bitmask but only enforces it on transfer instructions. `deploy_token` has no pause guard, so it executes unconditionally even when `Config.paused == ALL_PAUSED (0x03)`, violating the protocol invariant that all bridge actions halt during a full pause.

### Finding Description

`constants.rs` defines the pause bitmask constants: [1](#0-0) 

`ALL_PAUSED` is `INIT_TRANSFER_PAUSED | FINALIZE_TRANSFER_PAUSED = 0x03`. There is no `DEPLOY_TOKEN_PAUSED` bit.

`lib.rs` applies pause guards to exactly four instructions: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

`deploy_token` has no such guard: [6](#0-5) 

The instruction verifies the NEAR secp256k1 signature and then unconditionally calls `initialize_token_metadata`, which creates the on-chain mint and emits a Wormhole message: [7](#0-6) 

### Impact Explanation

When the protocol is fully paused (e.g., in response to a live exploit), `deploy_token` remains callable by anyone who holds a valid NEAR-signed `DeployTokenPayload`. This:

1. Creates a new SPL mint on Solana during a security pause.
2. Emits a Wormhole `DeployToken` response message back to NEAR, potentially advancing cross-chain state while the protocol is supposed to be frozen.

This is a concrete pause bypass — the category explicitly listed as Critical in the scope.

### Likelihood Explanation

The constraint is that the caller must supply a valid NEAR secp256k1 signature over the payload. This cannot be forged. However, in the normal bridge flow, NEAR signs `DeployTokenPayload` messages that are then relayed to Solana. These signed payloads are observable on-chain (NEAR or Wormhole). If a pause is triggered while a signed-but-unsubmitted payload is in flight, any party (not just the designated relayer) can submit it to Solana, bypassing the pause. This is a realistic race condition during incident response.

Replay protection is structural (the `init` constraint on the mint PDA prevents the same token from being deployed twice), but it does not prevent a first-time deployment from occurring during a pause. [8](#0-7) 

### Recommendation

Add a pause check to `deploy_token` in `lib.rs`, using a dedicated `DEPLOY_TOKEN_PAUSED` bit or by reusing `ALL_PAUSED` directly:

```rust
pub fn deploy_token(
    ctx: Context<DeployToken>,
    data: SignedPayload<DeployTokenPayload>,
) -> Result<()> {
    require!(
        ctx.accounts.common.config.paused & ALL_PAUSED == 0,
        error::ErrorCode::Paused
    );
    // ...
}
```

Alternatively, define a dedicated `DEPLOY_TOKEN_PAUSED: u8 = 1 << 2` bit and include it in `ALL_PAUSED` so the bitmask semantics remain consistent. [9](#0-8) 

### Proof of Concept

1. Deploy the program on localnet.
2. Call `pause` (sets `config.paused = ALL_PAUSED = 0x03`).
3. Obtain or construct a valid NEAR-signed `DeployTokenPayload` (in tests, the NEAR bridge signing key is known).
4. Call `deploy_token` with that payload.
5. Assert the instruction succeeds, the mint account is created, and a Wormhole message is posted — all while `config.paused == 0x03`.

The existing test infrastructure in `tests/mollusk/` already demonstrates how to set `paused` and invoke instructions; the same pattern applies here. [6](#0-5)
