### Title
`HyperliquedBridgeToken.mint(address,uint256,bytes)` silently redirects all minted tokens to `_systemAddress`, causing permanent loss of bridged funds for any `finTransfer` with a non-empty message — (`evm/src/omni-bridge/contracts/HlBridgeToken.sol`)

---

### Summary

The 3-argument `mint` override in `HyperliquedBridgeToken` first mints `value` tokens to `account`, then immediately transfers the entire minted balance from `account` to `_systemAddress`. When `OmniBridge.finTransfer` is called with `payload.message.length > 0` targeting a registered `HyperliquedBridgeToken`, the recipient receives zero tokens while `_systemAddress` silently absorbs the full amount.

---

### Finding Description

**Step 1 — Entry point: `OmniBridge.finTransfer`**

`finTransfer` dispatches to the 3-arg `IBridgeToken.mint` whenever `isBridgeToken[payload.tokenAddress]` is true **and** `payload.message.length > 0`: [1](#0-0) 

**Step 2 — The destructive `mint` override**

`HyperliquedBridgeToken.mint(address account, uint256 value, bytes memory)` executes two sequential ERC-20 internal calls: [2](#0-1) 

- `_mint(account, value)` — credits `account` with `value` tokens (balance: `+value`)
- `_update(account, _systemAddress, value)` — immediately transfers `value` tokens **from** `account` **to** `_systemAddress` (balance: net `0`)

The net effect on `account` is zero. `_systemAddress` absorbs the entire minted amount.

**Step 3 — No recovery path for the recipient**

The only way to release tokens from `_systemAddress` is via `coreReceiveWithData`, which is gated to `msg.sender == _systemAddress`: [3](#0-2) 

The declared recipient has no mechanism to reclaim their tokens. The loss is permanent unless the HyperCore system address operator manually intervenes.

---

### Impact Explanation

Any inbound cross-chain transfer to a `HyperliquedBridgeToken` that carries a non-empty `message` field results in:
- `balanceOf(recipient) == 0` after finalization
- `balanceOf(_systemAddress) += amount`

This violates the core bridge invariant: *a finalized inbound transfer must credit the declared recipient with exactly the declared amount*. The bridged funds are permanently lost to the recipient.

---

### Likelihood Explanation

The `message` field is a general-purpose cross-chain messaging field used for DeFi composability (e.g., DEX swaps, lending protocol calls on arrival). Any user on NEAR who initiates a transfer to a `HyperliquedBridgeToken` address with a non-empty message — a fully supported and documented bridge feature — will trigger this path. The NEAR bridge signs whatever payload is submitted; it has no knowledge of the destination token type. The relayer submits the signed payload faithfully. No attacker capability beyond initiating a standard NEAR-side transfer with a message is required.

---

### Recommendation

The 3-arg `mint` in `HyperliquedBridgeToken` must not unconditionally redirect tokens to `_systemAddress`. Options:

1. **Parse the message to determine routing**: Only redirect to `_systemAddress` when the message explicitly encodes a HyperCore destination; otherwise mint directly to `account`.
2. **Separate entry points**: Do not reuse the generic `IBridgeToken.mint(address,uint256,bytes)` interface for HyperCore routing. Introduce a dedicated HyperCore finalization path that is not reachable via the standard `finTransfer` message-length branch.
3. **Guard on message content**: At minimum, validate that `message` encodes a recognized HyperCore action before redirecting; revert otherwise so funds are not silently lost.

---
