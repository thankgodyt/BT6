### Title
Fee-on-Transfer Token Escrow Over-Accounting Enables Drain of Bridge Reserves — (`evm/src/omni-bridge/contracts/OmniBridge.sol`, `starknet/src/omni_bridge.cairo`)

---

### Summary

`initTransfer` on both the EVM and Starknet bridge contracts emits a cross-chain `InitTransfer` event using the caller-supplied `amount` rather than the actual tokens received. For fee-on-transfer or deflationary ERC20 tokens, the contract receives fewer tokens than `amount`, but the destination chain mints/releases the full `amount`. This creates a permanent escrow deficit that grows with each such transfer, eventually preventing legitimate users from redeeming their tokens.

---

### Finding Description

In `OmniBridge.sol`, the non-bridge-token path of `initTransfer` calls `safeTransferFrom` with the caller-supplied `amount` and then immediately emits `BridgeTypes.InitTransfer` with that same `amount`:

```solidity
// evm/src/omni-bridge/contracts/OmniBridge.sol lines 407-412
IERC20(tokenAddress).safeTransferFrom(
    msg.sender,
    address(this),
    amount
);
``` [1](#0-0) 

The event is then emitted with the original `amount` parameter — not the actual balance delta:

```solidity
emit BridgeTypes.InitTransfer(
    msg.sender,
    tokenAddress,
    currentOriginNonce,
    amount,   // <-- requested amount, not actual received amount
    ...
);
``` [2](#0-1) 

The identical pattern exists in the Starknet bridge:

```cairo
// starknet/src/omni_bridge.cairo lines 304-306
let success = IERC20Dispatcher { contract_address: token_address }
    .transfer_from(caller, get_contract_address(), amount.into());
assert(success, 'ERR_TRANSFER_FROM_FAILED');
``` [3](#0-2) 

followed by emitting `amount` in the event: [4](#0-3) 

On the destination side, `finTransfer` releases exactly `payload.amount` tokens — the value from the signed cross-chain message, which was derived from the over-stated event:

```solidity
// evm/src/omni-bridge/contracts/OmniBridge.sol lines 351-354
IERC20(payload.tokenAddress).safeTransfer(
    payload.recipient,
    payload.amount
);
``` [5](#0-4) 

There is no token allowlist restricting which ERC20s can be used in `initTransfer`; any non-bridge-token ERC20 is accepted through the else-branch. [6](#0-5) 

---

### Impact Explanation

For every `initTransfer` call with a fee-on-transfer token of fee rate `f`:

- EVM escrow receives: `amount × (1 - f)`
- Cross-chain message records: `amount`
- Destination chain mints/releases: `amount`

The escrow is underfunded by `amount × f` per transfer. After `N` transfers the deficit is `N × amount × f`. When users bridge back from the destination chain, `finTransfer` on EVM attempts to release the full `amount` per redemption. Once the cumulative deficit exceeds the contract's actual balance, `safeTransfer` reverts and legitimate users permanently lose access to their bridged tokens. This is a direct, permanent loss of bridged funds — a Critical impact.

---

### Likelihood Explanation

Fee-on-transfer ERC20 tokens are a well-established token class on EVM (e.g., tokens with redistribution mechanics, reflection tokens, or tokens with configurable transfer fees). The bridge imposes no allowlist on which ERC20 tokens can be bridged via `initTransfer`. Any unprivileged user can call `initTransfer` with such a token. The attacker does not need any special role, leaked key, or admin access — only the ability to hold and transfer a fee-on-transfer ERC20. The attack is profitable for the attacker (they receive more on the destination than they deposited on the source) and repeatable.

---

### Recommendation

Measure the actual received amount by comparing the contract's token balance before and after the transfer, and use that delta in the emitted event:

```solidity
uint256 balanceBefore = IERC20(tokenAddress).balanceOf(address(this));
IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
uint128 receivedAmount = uint128(IERC20(tokenAddress).balanceOf(address(this)) - balanceBefore);
// use receivedAmount in the event and downstream accounting instead of amount
```

Apply the same fix to `initTransfer1155` and to the Starknet `init_transfer`. Additionally, consider enforcing that `receivedAmount == amount` (i.e., reverting on fee-on-transfer tokens) if the bridge does not intend to support them.

---

### Proof of Concept

1. Deploy or use an existing ERC20 with a 1% transfer fee on EVM.
2. Call `OmniBridge.initTransfer(feeToken, 1_000_000, 0, 0, nearRecipient, "")`.
3. The contract receives 990,000 tokens but emits `InitTransfer(..., amount=1_000_000, ...)`.
4. The NEAR bridge relayer picks up the event and calls `fin_transfer` on NEAR, minting 1,000,000 tokens to `nearRecipient`.
5. `nearRecipient` bridges back 1,000,000 tokens to EVM via NEAR's `init_transfer`.
6. The MPC signs a `finTransfer` payload for 1,000,000 tokens on EVM.
7. `OmniBridge.finTransfer` calls `safeTransfer(recipient, 1_000_000)` — succeeds because the contract still has enough balance from other depositors.
8. Repeat steps 2–7 many times. Each iteration drains 10,000 tokens from other users' deposits.
9. Eventually the contract's actual balance is exhausted; legitimate users' `finTransfer` calls revert, permanently freezing their funds.
