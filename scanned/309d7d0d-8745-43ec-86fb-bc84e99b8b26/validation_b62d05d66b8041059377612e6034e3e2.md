### Title
Permanent Fund Loss When wNEAR Withdrawal Fails in `fin_transfer` Flow — (`near/omni-bridge/src/lib.rs`)

### Summary

In the NEAR Omni Bridge, when finalizing an inbound transfer of wNEAR (NEAR → NEAR via `fin_transfer`), the transfer is marked as finalized in `finalised_transfers` **before** the token delivery succeeds. If the wNEAR withdrawal subsequently fails, `near_withdraw_callback` panics instead of returning a failure result, and `fin_transfer_send_tokens_callback` does not check the promise result for the non-`ft_transfer_call` path. The transfer remains permanently in `finalised_transfers` with no recovery path, causing permanent loss of the user's bridged funds.

### Finding Description

The `fin_transfer` flow for inbound transfers to NEAR follows this promise chain:

1. `fin_transfer()` → `fin_transfer_callback()` → `process_fin_transfer_to_near()`
2. Inside `process_fin_transfer_to_near()`, `add_fin_transfer()` is called **first**, inserting the transfer ID into `finalised_transfers` before any token delivery occurs.
3. `send_tokens()` is then called. For wNEAR with an empty message, it builds the chain: `near_withdraw() → near_withdraw_callback() → fin_transfer_send_tokens_callback()`. [1](#0-0) [2](#0-1) 

If `near_withdraw` fails (e.g., insufficient wNEAR balance in the bridge contract), `near_withdraw_callback` explicitly panics: [3](#0-2) 

This panic causes the `near_withdraw_callback` promise to fail. `fin_transfer_send_tokens_callback` is then called with that failed promise result. However, `fin_transfer_send_tokens_callback` does not use `#[callback_result]` and does not inspect the promise result for the non-`ft_transfer_call` path. It delegates to `is_refund_required(is_ft_transfer_call)`: [4](#0-3) 

Since `msg` is empty for the wNEAR path, `is_ft_transfer_call = false`. `is_refund_required(false)` unconditionally returns `false`: [5](#0-4) 

The `else` branch executes, sending fees and logging `FinTransferEvent` as if the transfer succeeded — without calling `remove_fin_transfer`. The transfer ID remains permanently in `finalised_transfers`: [6](#0-5) 

The same structural flaw applies to the plain `ft_transfer` path (non-deployed, non-wNEAR, empty msg): if `ft_transfer` fails, `fin_transfer_send_tokens_callback` is called with `is_ft_transfer_call = false`, `is_refund_required` returns `false`, and the transfer is permanently stuck. [7](#0-6) 

### Impact Explanation

The transfer ID is permanently recorded in `finalised_transfers`. Any subsequent call to `fin_transfer` with the same proof will be rejected with `TransferAlreadyFinalised`. The user's bridged funds are permanently lost with no replay or recovery mechanism. This is a critical loss-of-funds vulnerability.

### Likelihood Explanation

The wNEAR withdrawal can fail if:
- The bridge contract's wNEAR balance is insufficient due to a decimal normalization discrepancy between the locked amount and the denormalized withdrawal amount.
- The wNEAR contract is paused or temporarily unavailable.
- Gas allocated via `WNEAR_WITHDRAW_GAS` is insufficient for the wNEAR contract's execution.

The `ft_transfer` failure path is similarly reachable if the token contract panics for any reason after the storage deposit check passes. Both paths are reachable by any user who initiates a legitimate cross-chain transfer.

### Recommendation

`fin_transfer_send_tokens_callback` must check the promise result for **all** token delivery paths, not only the `ft_transfer_call` path. Specifically:

1. Add a `#[callback_result]` parameter or call `env::promise_result_checked(0, ...)` unconditionally.
2. If the promise result is `Err` (token delivery failed), call `remove_fin_transfer` and `revert_lock_actions` to restore the transfer to a replayable state, regardless of whether `is_ft_transfer_call` is true or false.
3. Fix `near_withdraw_callback` to return a failure value instead of panicking, so the failure propagates cleanly to `fin_transfer_send_tokens_callback`.

### Proof of Concept

**Setup:** A user bridges wNEAR from Ethereum to NEAR. The bridge contract's wNEAR balance is exactly equal to the locked amount.
