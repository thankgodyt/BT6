### Title
Payable Functions Accept ETH Without Consuming It, Permanently Trapping Caller Funds — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

`logMetadata` and `logMetadata1155` in `OmniBridge.sol` are declared `external payable` but never consume `msg.value` in the base contract. Any ETH attached to these calls is silently absorbed into the contract's balance with no refund path, permanently destroying the caller's funds.

---

### Finding Description

Two publicly callable functions carry the `payable` modifier but perform no ETH accounting:

**`logMetadata`** (line 224):
```solidity
function logMetadata(address tokenAddress) external payable {
    string memory name  = IERC20Metadata(tokenAddress).name();
    string memory symbol = IERC20Metadata(tokenAddress).symbol();
    uint8  decimals = IERC20Metadata(tokenAddress).decimals();
    logMetadataExtension(tokenAddress, name, symbol, decimals);   // no-op in base
    emit BridgeTypes.LogMetadata(tokenAddress, name, symbol, decimals);
}
```

**`logMetadata1155`** (line 234):
```solidity
function logMetadata1155(address tokenAddress, uint256 tokenId) external payable {
    ...
    logMetadataExtension(deterministicToken, ...);   // no-op in base
    emit BridgeTypes.LogMetadata(...);
}
```

`logMetadataExtension` is defined as:
```solidity
function logMetadataExtension(...) internal virtual {}
``` [1](#0-0) [2](#0-1) [3](#0-2) 

Neither function references `msg.value` anywhere in its body. The contract also exposes an unconditional `receive()`:

```solidity
receive() external payable {}
``` [4](#0-3) 

This means any ETH sent with `logMetadata` or `logMetadata1155` is silently merged into the contract's ETH balance — the same pool that backs native-ETH `finTransfer` payouts — with no record and no refund.

The same pattern applies to `deployToken` (line 138) and `finTransfer` (line 282) in the base contract: both are `payable`, and in the base `OmniBridge` their extension hooks are no-ops, so `msg.value` is silently swallowed for any ERC-20 token path. [5](#0-4) [6](#0-5) 

In `OmniBridgeWormhole`, `logMetadataExtension` and `finTransferExtension` do forward `msg.value` to Wormhole's `publishMessage`, so the Wormhole variant partially mitigates the issue for those two hooks — but `logMetadata` and `logMetadata1155` remain callable with arbitrary ETH on any deployment, and any excess above `wormhole.messageFee()` is still silently lost inside the Wormhole core contract. [7](#0-6) 

---

### Impact Explanation

ETH sent with `logMetadata` or `logMetadata1155` is permanently merged into the bridge's native-ETH escrow pool. The caller receives no refund and no on-chain record of the accidental deposit. Because the contract's ETH balance is the sole source of funds for native-ETH `finTransfer` payouts, the inflated balance is indistinguishable from legitimately bridged ETH and cannot be recovered by the original sender. This constitutes a permanent, irreversible loss of user funds with no protocol-level recovery path.

---

### Likelihood Explanation

`logMetadata` and `logMetadata1155` are permissionless entry points — no role, no signature, no prior registration is required. Any wallet, script, or front-end integration that attaches a non-zero ETH value (e.g., copy-paste from an `initTransfer` call, a wallet that auto-fills `msg.value`, or a scripting error) will silently lose that ETH. The pattern is identical to the Dexter scenario: a user intending to pay a fee or mistakenly attaching value to a non-value function loses funds with no revert.

---

### Recommendation

**Short term:** Add an explicit guard at the top of every `payable` function that does not intentionally consume ETH:

```solidity
function logMetadata(address tokenAddress) external payable {
    if (msg.value != 0) revert InvalidValue();
    ...
}

function logMetadata1155(address tokenAddress, uint256 tokenId) external payable {
    if (msg.value != 0) revert InvalidValue();
    ...
}
```

Apply the same guard to `deployToken` and `finTransfer` for the ERC-20 token path in the base contract (where `extensionValue` / `msg.value` is not forwarded anywhere).

**Long term:** Audit every `payable` function in both `OmniBridge` and `OmniBridgeWormhole` to confirm that `msg.value` is either fully consumed, fully forwarded, or explicitly rejected. Consider removing `payable` from functions that never need ETH rather than relying on runtime guards.

---

### Proof of Concept

1. Alice wants to register her ERC-20 token for bridging and calls:
   ```
   omniBridge.logMetadata{value: 0.5 ether}(tokenAddress)
   ```
2. The function reads `name`, `symbol`, `decimals` from the token contract.
3. `logMetadataExtension` is a no-op (base contract).
4. A `LogMetadata` event is emitted.
5. The function returns. Alice's 0.5 ETH is now part of `address(omniBridge).balance`.
6. There is no event, no storage entry, and no function that allows Alice to reclaim it.
7. The 0.5 ETH is permanently lost; it silently subsidises future native-ETH `finTransfer` payouts for unrelated users.
