### Title
Permanent Freezing of Bridged Funds When Normalized Transfer Amount Rounds to Zero - (File: near/omni-bridge/src/lib.rs)

### Summary
The `sign_transfer` function enforces a post-normalization guard (`require!(amount_to_transfer > 0)`) that can permanently freeze user funds. When a user initiates a NEAR → foreign-chain transfer with an amount that, after decimal normalization, floors to zero, the transfer is stored in `pending_transfers` with tokens already locked or burned, but `sign_transfer` panics and no MPC signature is ever produced. Because the only paths that remove a transfer from `pending_transfers` require a finalization proof derived from an MPC signature, the funds are irrecoverably frozen. This is the bridge analog of M-08: a threshold check that silently blocks critical operations and leaves no recovery path.

### Finding Description

**Step 1 – Transfer initiation (tokens locked, no normalization check)**

`init_transfer` in `near/omni-bridge/src/lib.rs` stores the transfer and locks/burns the user's tokens. Its only fee/amount validation is:

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
``` [1](#0-0) 

There is no check that `normalize_amount(amount − fee) > 0`. A transfer where the net amount is below the normalization threshold passes this guard and is stored in `pending_transfers`.

**Step 2 – Normalization in `sign_transfer` (panic, no recovery)**

When a relayer later calls `sign_transfer`, the bridge normalizes the amount to the destination chain's decimal precision:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message
        .amount_without_fee()
        .near_expect(BridgeError::InvalidFee),
    decimals,
);

require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
``` [2](#0-1) 

`normalize_amount` uses floor division:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [3](#0-2) 

If `amount_without_fee < 10^(origin_decimals − decimals)`, the result is `0` and `sign_transfer` panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`. The transfer remains in `pending_transfers` indefinitely.

**Step 3 – No recovery path exists**

The only functions that remove a transfer from `pending_transfers` are `claim_fee_callback` and `fin_transfer_send_tokens_callback`, both of which require a valid finalization proof derived from an MPC signature. [4](#0-3) [5](#0-4) 

Since `sign_transfer` panics before producing a signature, no proof can ever be generated, and no cancel/refund function exists. The user's tokens are permanently frozen.

**Why this is NOT covered by CLAUDE.md false-positive #2**

The documented false positive ("Decimal Arithmetic Underflow") concerns the case where `origin_decimals < decimals`, causing an integer underflow in `origin_decimals − decimals`. The scenario here uses a valid configuration (`origin_decimals ≥ decimals`) with a legitimately small transfer amount. The CLAUDE.md explicitly states the design "expects `origin_decimals >= decimals`" — this scenario satisfies that expectation and is therefore not a misconfiguration. [6](#0-5) 

### Impact Explanation

User tokens are permanently locked in the bridge contract (or burned with no corresponding mint on the destination chain). The impact scales with the token's decimal gap:

- Token with `origin_decimals=6`, `decimals=0`: any transfer where `amount − fee < 10^6` (i.e., less than 1 full token) freezes. A user sending 0.999999 of a token loses it permanently.
- Token with `origin_decimals=18`, `decimals=6`: threshold is `10^12`; amounts below 0.000001 of the token freeze.

This satisfies the "permanent freezing of bridged funds" critical impact category.

### Likelihood Explanation

The condition is reachable by any unprivileged user on any token registered with `origin_decimals > decimals` (the standard configuration for precision-reducing normalization). The `init_transfer` fee check (`fee < amount`) does not prevent it. A user who sends a small amount, or who sets a fee close to the transfer amount, can inadvertently trigger this. No special privileges or external conditions are required.

### Recommendation

Perform the normalization check at `init_transfer` time, before tokens are locked or burned, so the transaction is rejected cleanly with a refund rather than after funds are already committed:

```rust
// In init_transfer, after computing transfer_message:
if let Some(token_address) = self.get_token_address(
    transfer_message.get_destination_chain(),
    self.get_token_id(&transfer_message.token),
) {
    if let Some(decimals) = self.token_decimals.get(&token_address) {
        let normalized = Self::normalize_amount(
            transfer_message.amount_without_fee()
                .near_expect(BridgeError::InvalidFee),
            decimals,
        );
        require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
    }
}
```

This mirrors the M-08 recommendation: fail early with a clear error rather than entering an unrecoverable frozen state.

### Proof of Concept

1. Register a token with `origin_decimals=6`, `decimals=0` (6-decimal NEAR token bridging to a 0-decimal destination).
2. User calls `ft_transfer_call` to the bridge with `amount=500_000` (0.5 of the token) and `fee=0`.
3. `init_transfer` stores the transfer in `pending_transfers` and burns the user's 500,000 tokens. Validation passes because `0 < 500_000`.
4. Relayer calls `sign_transfer`:
   - `amount_without_fee = 500_000`
   - `normalize_amount(500_000, Decimals { decimals: 0, origin_decimals: 6 }) = 500_000 / 10^6 = 0`
   - `require!(0 > 0, ...)` → panic: `ERR_INVALID_AMOUNT_TO_TRANSFER`
5. Transfer remains in `pending_transfers` forever. The user's 500,000 tokens (0.5 of the token) are permanently lost with no recovery path. [7](#0-6) [3](#0-2)
