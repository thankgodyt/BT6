### Title
CEI Violation in `initTransfer` / `initTransfer1155` Allows Nonce Collision via Malicious Token Reentrancy — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

`OmniBridge.initTransfer()` and `OmniBridge.initTransfer1155()` increment `currentOriginNonce` before making external token calls, but then read `currentOriginNonce` again **after** those external calls to populate the Wormhole message and the `InitTransfer` event. Because no reentrancy guard exists, a malicious ERC-20 or ERC-1155 token can reenter `initTransfer` during its own `safeTransferFrom`, increment `currentOriginNonce` a second time, and cause the outer call to emit an `InitTransfer` event with the same nonce as the inner call. The resulting nonce collision permanently freezes one of the two bridged transfers.

---

### Finding Description

In `initTransfer`:

```solidity
currentOriginNonce += 1;          // ← nonce captured here (= N)
...
IERC20(tokenAddress).safeTransferFrom(   // ← external call; reentrant call
    msg.sender, address(this), amount    //   increments nonce to N+1
);
...
initTransferExtension(
    msg.sender, tokenAddress,
    currentOriginNonce,            // ← reads N+1, not N  (stale!)
    ...
);
emit BridgeTypes.InitTransfer(
    msg.sender, tokenAddress,
    currentOriginNonce,            // ← reads N+1, not N  (stale!)
    ...
);
``` [1](#0-0) [2](#0-1) [3](#0-2) 

The identical pattern exists in `initTransfer1155`:

```solidity
currentOriginNonce += 1;          // ← nonce captured here (= N)
...
IERC1155(tokenAddress).safeTransferFrom(  // ← external call; reentrant call
    msg.sender, address(this), tokenId, amount, ""
);
...
initTransferExtension(..., currentOriginNonce, ...);  // reads N+1
emit BridgeTypes.InitTransfer(..., currentOriginNonce, ...);  // reads N+1
``` [4](#0-3) [5](#0-4) [6](#0-5) 

Neither function carries a `nonReentrant` modifier, and the contract does not import OpenZeppelin's `ReentrancyGuard`. [7](#0-6) 

In `OmniBridgeWormhole`, `initTransferExtension` publishes the nonce into a Wormhole VAA, making the stale nonce observable cross-chain. [8](#0-7) 

---

### Impact Explanation

**Nonce collision / permanent freezing of bridged funds.**

After the attack, two `InitTransfer` events carry the same `originNonce = N+1`. The NEAR `omni-bridge` contract records finalised transfers in `finalised_transfers` (a set keyed by `(origin_chain, origin_nonce)`). [9](#0-8) 

When a relayer submits proof for nonce N+1 a second time, NEAR rejects it as already finalised. The tokens locked in the EVM bridge for the rejected transfer are permanently frozen — they cannot be reclaimed because the corresponding NEAR-side record was consumed by the first submission. Nonce N is also permanently skipped, creating a gap that may break downstream accounting.

If the attacker is also a relayer (or races to submit first), they can choose which of the two conflicting events NEAR processes, deciding whose funds are frozen.

---

### Likelihood Explanation

Any unprivileged user can deploy a malicious ERC-20 or ERC-1155 token and call `initTransfer` / `initTransfer1155` with it. The bridge imposes no whitelist on token addresses for these entry points. The reentrant call can itself use a legitimate token, so the attacker can target a victim's concurrent transfer or manufacture the collision entirely with their own tokens to grief the protocol's nonce sequence. No admin keys, MPC compromise, or validator collusion is required.

---

### Recommendation

1. **Read `currentOriginNonce` before the external call** and pass the captured value to `initTransferExtension` and `emit`:

```solidity
currentOriginNonce += 1;
uint64 nonce = currentOriginNonce;   // capture before external call
...
IERC20(tokenAddress).safeTransferFrom(...);
...
initTransferExtension(..., nonce, ...);
emit BridgeTypes.InitTransfer(..., nonce, ...);
```

2. **Add `nonReentrant`** (OpenZeppelin `ReentrancyGuard`) to `initTransfer` and `initTransfer1155` as defence-in-depth.

---

### Proof of Concept

1. Attacker deploys `MalToken` whose `safeTransferFrom` reenters `initTransfer` with a legitimate token `LegitToken`.
2. Attacker calls `initTransfer(MalToken, ...)`. `currentOriginNonce` becomes `N`.
3. `MalToken.safeTransferFrom` fires; inside it calls `initTransfer(LegitToken, ...)`. `currentOriginNonce` becomes `N+1`. Inner call emits `InitTransfer(nonce=N+1, token=LegitToken)`. `LegitToken` is locked in the bridge.
4. Outer call resumes. Reads `currentOriginNonce = N+1`. Emits `InitTransfer(nonce=N+1, token=MalToken)`.
5. Two events share nonce `N+1`; nonce `N` is never emitted.
6. Relayer submits the `MalToken` event first. NEAR finalises nonce `N+1` for `MalToken`.
7. Relayer submits the `LegitToken` event. NEAR rejects it — nonce `N+1` already finalised.
8. `LegitToken` (amount locked in step 3) is permanently frozen in the EVM bridge.
