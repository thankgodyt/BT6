### Title
No Minimum Transfer Amount Check Allows Permanently Frozen Funds via Decimal Normalization — (`near/omni-bridge/src/lib.rs`)

### Summary

The NEAR omni-bridge contract accepts outbound transfers (NEAR → foreign chain) of arbitrarily small token amounts without verifying that the amount will survive decimal normalization. When `normalize_amount(amount - fee) == 0`, `sign_transfer` always reverts with `InvalidAmountToTransfer`, yet no cancellation path exists. The user's tokens are permanently locked or burned with no recovery mechanism.

### Finding Description

`init_transfer` on NEAR enforces only one constraint on the transfer amount: `fee.fee < amount`. There is no check that `normalize_amount(amount - fee) > 0`. [1](#0-0) 

`normalize_amount` uses floor division: [2](#0-1) 

For any token whose NEAR representation has more decimals than the destination chain (e.g., a token stored with 24 decimals on NEAR but 6 decimals on EVM, giving `diff_decimals = 18`), any `amount - fee < 10^18` normalizes to zero.

`sign_transfer` — the only path to complete the transfer — enforces the zero-amount guard **after** the tokens are already locked/burned: [3](#0-2) 

`update_transfer_fee` cannot rescue the transfer: it only allows the fee to be **increased** (never decreased), and the new fee must still be `< amount`. Increasing the fee makes `amount - fee` even smaller, keeping the normalized value at zero. [4](#0-3) 

There is no public cancel or refund function for a pending outbound transfer. The transfer entry sits in `pending_transfers` indefinitely, and the locked/burned tokens are irrecoverable.

The same gap exists in the legacy `finish_withdraw_v2` path, which creates a transfer with `fee = 0` and no minimum-amount guard: [5](#0-4) 

### Impact Explanation

A user who sends a sub-threshold amount of a token with a large decimal gap between NEAR and the destination chain will have their tokens permanently locked in the bridge escrow (for native tokens) or permanently burned (for deployed bridge tokens), with no way to recover them. This constitutes permanent freezing of bridged funds.

### Likelihood Explanation

Any unprivileged user can trigger this by calling `ft_transfer_call` on a NEP-141 token directed at the bridge with a small `amount` and `fee = 0`. For tokens with a 12-decimal gap (e.g., 24 on NEAR, 12 on EVM), any amount below `10^12` base units is affected. This is a realistic user mistake, and the protocol provides no safety net.

### Recommendation

Add a normalization check inside `init_transfer` (before tokens are locked/burned) that mirrors the guard already present in `sign_transfer`:

```rust
let decimals = self.token_decimals.get(&token_address)
    .near_expect(BridgeError::TokenDecimalsNotFound);
let normalized = Self::normalize_amount(
    transfer_message.amount_without_fee()
        .near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

Apply the same guard to `finish_withdraw_v2`.

### Proof of Concept

1. A token is registered with `origin_decimals = 24`, `decimals = 6` (diff = 18) for the EVM destination.
2. User calls `ft_transfer_call` with `amount = 10^18 - 1` and `fee = 0` targeting the bridge.
3. `init_transfer` passes the only check (`0 < 10^18 - 1`). Tokens are locked.
4. Any trusted relayer calls `sign_transfer`. `normalize_amount(10^18 - 1, decimals) = 0`. The call panics with `InvalidAmountToTransfer`.
5. User calls `update_transfer_fee` attempting to set `fee = 0` (no change allowed to decrease). Any increase makes `amount - fee` smaller, still normalizing to 0.
6. No cancel function exists. Tokens remain locked forever. [6](#0-5) [7](#0-6)

    /// Uses floor division — any sub-unit remainder ("dust") is truncated and not transferred
    /// to the destination chain. When fee > 0, dust is absorbed into the fee via `claim_fee`.
    /// When fee = 0, dust stays locked/burned. See SECURITY.md for details.
    fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
        let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
        amount / (10_u128.pow(diff_decimals))
    }
