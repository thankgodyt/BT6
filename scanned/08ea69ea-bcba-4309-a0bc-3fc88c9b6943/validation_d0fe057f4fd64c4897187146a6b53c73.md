### Title
Fee-on-Transfer Token Escrow Mis-Accounting in `initTransfer` - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

`OmniBridge.sol`'s `initTransfer` function uses the caller-supplied `amount` parameter both for the `safeTransferFrom` call and for the emitted `InitTransfer` event. When a fee-on-transfer (deflationary) ERC20 token is bridged, the contract receives fewer tokens than `amount`, but the event records the full `amount`. The NEAR bridge finalizes the transfer using the event's `amount`, releasing more tokens than were ever locked on the EVM side, draining the bridge's EVM escrow.

---

### Finding Description

In `initTransfer`, for a standard (non-bridge, non-custom-minter) ERC20 token, the code path is:

```solidity
IERC20(tokenAddress).safeTransferFrom(
    msg.sender,
    address(this),
    amount          // requested amount, not verified received amount
);
```

Immediately after, the event is emitted with the same caller-supplied `amount`:

```solidity
emit BridgeTypes.InitTransfer(
    msg.sender,
    tokenAddress,
    currentOriginNonce,
    amount,         // emitted as-is, not actual received balance
    fee,
    nativeFee,
    recipient,
    message
);
```

There is no balance-before/balance-after check to verify how many tokens were actually received. For a fee-on-transfer token with a `k%` fee, the bridge receives `amount * (1 - k/100)` tokens but the event records `amount`.

On the NEAR side, `fin_transfer_callback` parses the `InitTransferMessage` from the prover result, which was derived from this event log:

```rust
amount: near_sdk::json_types::U128(event.data.amount),
```

The NEAR bridge then calls `process_fin_transfer_to_near` or `process_fin_transfer_to_other_chain` using this inflated `amount`, releasing the full `amount` to the recipient via `send_tokens` or minting it via `ft_transfer`/`mint`.

---

### Impact Explanation

**Critical — Escrow mis-accounting / loss of bridged funds.**

Each `initTransfer` with a fee-on-transfer token creates a deficit: the EVM bridge holds `amount * (1 - fee_rate)` tokens but the NEAR bridge releases `amount` tokens. Repeated bridging of such tokens progressively drains the EVM bridge's token reserves. Legitimate users who later attempt to bridge back (EVM → NEAR → EVM unlock) will find the EVM bridge insolvent for that token, permanently freezing their funds.

---

### Likelihood Explanation

Fee-on-transfer tokens are a well-known ERC20 variant (e.g., USDT on some chains historically, STA, REFLECT-style tokens). The bridge does not whitelist tokens — any ERC20 can be passed as `tokenAddress`. An attacker can deploy or use an existing fee-on-transfer token and call `initTransfer` directly. No special privileges are required; the entry point is fully public and `whenNotPaused(PAUSED_INIT_TRANSFER)` is the only guard.

---

### Recommendation

Replace the static `amount` in the event emission with the actual received amount, computed via a balance-before/balance-after pattern:

```solidity
uint256 balanceBefore = IERC20(tokenAddress).balanceOf(address(this));
IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
uint256 actualReceived = IERC20(tokenAddress).balanceOf(address(this)) - balanceBefore;
require(actualReceived == amount, "Fee-on-transfer tokens not supported");
```

Alternatively, emit `actualReceived` instead of `amount` and propagate it through the cross-chain message. The simplest and safest mitigation is to revert if the received amount does not match the requested amount, explicitly rejecting fee-on-transfer tokens.

---

### Proof of Concept

1. Deploy or use an ERC20 token with a 10% transfer fee.
2. Approve the EVM `OmniBridge` for 1000 tokens.
3. Call `initTransfer(feeToken, 1000, 0, 0, "alice.near", "")`.
   - Bridge receives 900 tokens (10% fee deducted by the token contract).
   - Event emits `amount = 1000`.
4. A relayer submits the Ethereum receipt proof to the NEAR bridge via `fin_transfer`.
5. `fin_transfer_callback` parses `InitTransferMessage { amount: 1000, ... }` from the proof.
6. NEAR bridge calls `send_tokens(token, alice, U128(1000), "")` — releasing 1000 tokens.
7. Net: attacker deposited 900 tokens on EVM, received 1000 tokens on NEAR. 100-token deficit per round trip accumulates in the EVM escrow.
