### Title
Fee Granularity Inconsistency Allows Permanent Freezing of Outbound Transfer Funds - (`near/omni-bridge/src/lib.rs`)

### Summary

`init_transfer` validates the fee using raw NEAR-native token amounts, while `sign_transfer` validates the net transfer amount only after decimal normalization (floor division). When a token has more decimals on NEAR than on the destination chain, a user can create a transfer where `amount - fee > 0` (passes `init_transfer`) but `normalize_amount(amount - fee) == 0` (permanently fails `sign_transfer`). The user's tokens are locked in the bridge with no recovery path.

### Finding Description

The bridge enforces two different granularity checks at two different stages of the outbound transfer lifecycle:

**Stage 1 — `init_transfer` (raw-amount check):** [1](#0-0) 

The only fee validity check is `fee.fee < amount`. This operates on raw NEAR-native token units with no awareness of the destination chain's decimal precision.

**Stage 2 — `sign_transfer` (normalized-amount check):** [2](#0-1) 

`normalize_amount` uses integer floor division: [3](#0-2) 

If `origin_decimals > decimals` (e.g., 24 on NEAR, 18 on Ethereum → normalization unit = `10^6`), any `amount - fee` that is less than `10^(origin_decimals - decimals)` normalizes to zero, causing `sign_transfer` to panic with `InvalidAmountToTransfer`.

**No recovery path exists.** The `update_transfer_fee` function only allows the fee to be *increased*, not decreased: [4](#0-3) 

So the user cannot reduce the fee to push `amount - fee` above the normalization threshold. There is no public `cancel_transfer` function. `remove_transfer_message` is internal and only reachable via `sign_transfer_callback` (when `fee.is_zero()`) or `claim_fee_callback` (which requires a proof from the destination chain that the transfer was finalized — impossible if `sign_transfer` always fails). [5](#0-4) 

### Impact Explanation

A user's tokens are permanently frozen in the bridge. The transfer is stored in `pending_transfers`, the tokens are locked/burned on NEAR (the `ft_transfer_call` returns 0 to the token contract, keeping the tokens), and `sign_transfer` will always revert. The transfer can never be finalized, cancelled, or refunded. This constitutes permanent loss of bridged funds.

### Likelihood Explanation

This requires a token registered with `origin_decimals > decimals` (e.g., a NEAR-native token with 24 decimals bridged to Ethereum where it is represented with 18 decimals — a common real-world configuration). The user must set a fee such that `amount - fee < 10^(origin_decimals - decimals)`. This can happen through user error (setting a high fee to attract relayers) or through a griefing vector where an attacker front-runs a user's transfer and manipulates the fee via `update_transfer_fee` to push `amount - fee` into the dust range. The `update_transfer_fee` function allows any caller to increase the fee on a pending transfer as long as they are the sender: [6](#0-5) 

### Recommendation

Add a pre-flight normalization check inside `init_transfer` (or `init_transfer_internal`) that verifies `normalize_amount(amount - fee, decimals) > 0` before accepting the transfer and locking tokens. Additionally, implement a `cancel_transfer` function that allows the original sender to reclaim locked tokens for transfers that have not yet been signed, providing a recovery path for stuck transfers.

### Proof of Concept

**Setup:** Token registered with `origin_decimals = 24`, `decimals = 18` (normalization unit = `10^6 = 1_000_000`).

1. User calls `ft_transfer_call` on the token contract with `amount = 1_000_001` and `fee = 999_999`.
2. Bridge's `ft_on_transfer` → `init_transfer` is called.
3. Fee check: `999_999 < 1_000_001` → **passes**.
4. `init_transfer_internal` stores the `TransferMessage` in `pending_transfers` and returns `U128(0)` to the token contract → tokens are locked in the bridge.
5. Relayer calls `sign_transfer` for this transfer.
6. `amount_without_fee() = 1_000_001 - 999_999 = 2`.
7. `normalize_amount(2, Decimals { decimals: 18, origin_decimals: 24 }) = 2 / 1_000_000 = 0`.
8. `require!(0 > 0, ...)` → **panics with `InvalidAmountToTransfer`**.
9. Transfer remains in `pending_transfers`. User's `1_000_001` tokens are permanently locked. No recovery path exists.
