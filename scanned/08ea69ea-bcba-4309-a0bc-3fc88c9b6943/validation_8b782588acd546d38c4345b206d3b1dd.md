### Title
Native ETH Transfer to Arbitrary Recipient in `finTransfer` Can Permanently Freeze Bridged Funds - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

### Summary

In `OmniBridge.finTransfer`, when finalizing a native ETH bridge transfer (`tokenAddress == address(0)`), the contract sends ETH directly to `payload.recipient` via a low-level call. If the recipient is a contract that rejects ETH, the call fails and the entire `finTransfer` reverts. Because the recipient address is set by the user on the source chain and cannot be changed after initiation, the transfer can never be finalized, permanently freezing the user's bridged funds.

### Finding Description

In `OmniBridge.sol`, the `finTransfer` function handles native ETH delivery as follows:

```solidity
if (payload.tokenAddress == address(0)) {
    // slither-disable-next-line arbitrary-send-eth
    (bool success, ) = payload.recipient.call{value: payload.amount}(
        ""
    );
    if (!success) revert FailedToSendEther();
}
``` [1](#0-0) 

The `payload.recipient` is an arbitrary EVM address encoded in the signed `TransferMessagePayload` originating from the NEAR side. It is set by the user when initiating the transfer on the source chain and is immutable once the cross-chain message is signed. [2](#0-1) 

If `payload.recipient` is a contract with no `receive`/`fallback` function, or one that explicitly reverts on ETH receipt, the `.call{value: ...}("")` returns `success = false`, triggering `revert FailedToSendEther()`. This reverts the entire transaction, including the `completedTransfers[payload.destinationNonce] = true` state update set at line 287. [3](#0-2) 

Because the nonce is not permanently consumed (the revert undoes it), the relayer can retry — but every retry will fail identically. The transfer is permanently unfinalizeable.

### Impact Explanation

The user's native ETH equivalent is locked/burned on the source chain (NEAR) at `initTransfer` time. On the EVM destination, `finTransfer` can never succeed because the recipient always rejects ETH. There is no recovery path: the signed payload is fixed, the recipient cannot be changed, and no fallback mechanism exists to redirect funds or wrap them as WETH. The result is **permanent freezing of bridged native ETH funds**.

### Likelihood Explanation

This is reachable by any bridge user. It can occur accidentally — e.g., a user specifying a multisig, DAO treasury, or smart contract wallet that lacks a `receive` function as the EVM recipient. It can also be triggered intentionally by a user who deploys an ETH-rejecting contract and uses its address as the recipient. No admin access or special privileges are required.

### Recommendation

Replace the bare ETH call with a try-WETH fallback pattern: attempt the native ETH transfer, and if it fails, wrap the ETH into WETH and transfer WETH to the recipient instead. This is a well-known pattern used in production bridges and AMMs:

```solidity
(bool success, ) = payload.recipient.call{value: payload.amount}("");
if (!success) {
    IWETH(weth).deposit{value: payload.amount}();
    IERC20(weth).safeTransfer(payload.recipient, payload.amount);
}
```

Alternatively, always deliver native ETH transfers as WETH to contract recipients (detected via `payload.recipient.code.length > 0`).

### Proof of Concept

1. Deploy a contract `EthRejecter` on the EVM destination chain:
   ```solidity
   contract EthRejecter {
       receive() external payable { revert("NO ETH"); }
   }
   ```
2. On NEAR, call `initTransfer` (or equivalent) for a native ETH bridge transfer, specifying `address(ethRejecter)` as the EVM recipient.
3. The NEAR bridge locks/burns the user's funds and produces a signed `TransferMessagePayload`.
4. A relayer calls `OmniBridge.finTransfer(signatureData, payload)` on the EVM side.
5. Execution reaches line 319: `payload.recipient.call{value: payload.amount}("")` — `EthRejecter.receive()` reverts.
6. `finTransfer` reverts with `FailedToSendEther()`. The nonce is not consumed.
7. Every subsequent relay attempt fails identically. The user's funds are permanently frozen. [1](#0-0)
