### Title
Cross-Chain Replay of `deployToken` Signature Enables Unauthorized Token Deployment on Any Supported Chain - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`, `starknet/src/bridge_types.cairo`, `solana/programs/bridge_token_factory/src/state/message/deploy_token.rs`)

### Summary
The `deployToken`/`deploy_token` signature payload omits the destination chain ID across all three bridge implementations (EVM, Starknet, Solana). A valid MPC-signed `deployToken` authorization for chain A can be replayed verbatim on any other supported chain, bypassing the MPC authorization requirement for that chain.

### Finding Description
The bridge's `finTransfer`/`finalize_transfer` functions correctly bind their signed payloads to the destination chain by embedding the chain ID in the Borsh-encoded message. The `deployToken`/`deploy_token` functions do not.

**EVM (`OmniBridge.sol::deployToken`)** — the signed payload is:

```
PayloadType::Metadata | token | name | symbol | decimals
```

No `omniBridgeChainId` is included. [1](#0-0) 

Compare to `finTransfer`, which embeds `omniBridgeChainId` twice (for token address and recipient fields): [2](#0-1) 

**Starknet (`bridge_types.cairo::MetadataPayloadImpl::to_borsh`)** — the signed payload is:

```
PayloadType::Metadata | token | name | symbol | decimals
```

No chain ID is included. [3](#0-2) 

Compare to `TransferMessagePayloadImpl::to_borsh`, which takes and embeds `chain_id` twice: [4](#0-3) 

The Starknet CLAUDE.md even documents this design intent for `fin_transfer` — "Chain ID binding: Destination chain_id encoded in message hash (not in payload) - prevents cross-chain replay" — but this protection was never applied to `deploy_token`. [5](#0-4) 

**Solana (`deploy_token.rs::DeployTokenPayload::serialize_for_near`)** — the signed payload is:

```
IncomingMessageType::Metadata | token | name | symbol | decimals
```

No `SOLANA_OMNI_BRIDGE_CHAIN_ID` is included. [6](#0-5) 

Compare to `FinalizeTransferPayload::serialize_for_near`, which writes `SOLANA_OMNI_BRIDGE_CHAIN_ID` twice (for token and recipient): [7](#0-6) 

### Impact Explanation
An attacker who observes a valid `deployToken` transaction on chain A (e.g., Ethereum) can extract the `(signatureData, metadata)` tuple and submit it to the same function on any other supported chain (Arbitrum, Base, Polygon, BNB, Solana, Starknet). The signature check passes because the signed hash is chain-agnostic. The result is:

- A bridge token is deployed on chain B without the NEAR MPC network ever authorizing deployment on chain B. This directly violates the documented security invariant: "No tokens are ever minted or released on a foreign chain without a valid signature from the NEAR MPC network."
- Once deployed, the token is registered in `nearToEthToken`/`near_to_starknet_token` on chain B. Any subsequent legitimate attempt to deploy the same token on chain B with corrected parameters (e.g., different decimals, different implementation) will be permanently blocked by the `ERR_TOKEN_EXIST` / `ERR_TOKEN_ALREADY_DEPLOYED` guard.
- Users who bridge to chain B after the unauthorized deployment interact with a token that was deployed outside the intended operational timeline, potentially before liquidity, relayer infrastructure, or other dependencies are in place.

### Likelihood Explanation
All `deployToken` transactions are public on-chain. Any observer can extract the calldata from a confirmed transaction on chain A and replay it on chain B with zero additional privileges. The attacker needs only a funded wallet to pay gas. The bridge is live on multiple EVM chains simultaneously, making cross-chain replay immediately actionable.

### Recommendation
Embed the destination chain ID in the `deployToken` signed payload, mirroring the pattern already used in `finTransfer`. For EVM:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
    bytes1(omniBridgeChainId),   // <-- add this
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
```

Apply the equivalent fix to `MetadataPayload::to_borsh` in Starknet and `DeployTokenPayload::serialize_for_near` in Solana. The NEAR signing service must also include the target chain ID when constructing the payload to sign, so that signatures are chain-specific.

### Proof of Concept

1. The NEAR MPC network signs a `deployToken` payload for token `"usdc.near"` on Ethereum (chain ID `0x01`). A relayer submits the transaction; it succeeds.
2. An attacker reads the confirmed Ethereum transaction and extracts `(signatureData, metadata)`.
3. The attacker calls `deployToken(signatureData, metadata)` on the Arbitrum `OmniBridge` contract (chain ID `0x02`).
4. The Arbitrum contract computes `keccak256(Metadata | "usdc.near" | "USD Coin" | "USDC" | 6)` — identical to the Ethereum hash because no chain ID is included.
5. `ECDSA.recover(hashed, signatureData) == nearBridgeDerivedAddress` passes.
6. A new `BridgeToken` proxy is deployed on Arbitrum and registered as the canonical USDC bridge token, without the NEAR MPC network ever authorizing this action for Arbitrum.
7. The same replay works on Base, Polygon, BNB, Solana, and Starknet using the same extracted signature.

    fn serialize_for_near(&self, params: Self::AdditionalParams) -> Result<Vec<u8>> {
        let mut writer = BufWriter::new(Vec::with_capacity(DEFAULT_SERIALIZER_CAPACITY));
        // 0. prefix
        IncomingMessageType::InitTransfer.serialize(&mut writer)?;
        // 1. destination_nonce
        self.destination_nonce.serialize(&mut writer)?;
        // 2. transfer_id
        writer.write_all(&[self.transfer_id.origin_chain])?;
        self.transfer_id.origin_nonce.serialize(&mut writer)?;
        // 3. token
        writer.write_all(&[SOLANA_OMNI_BRIDGE_CHAIN_ID])?;
        params.0.serialize(&mut writer)?;
        // 4. amount
        self.amount.serialize(&mut writer)?;
        // 5. recipient
        writer.write_all(&[SOLANA_OMNI_BRIDGE_CHAIN_ID])?;
        params.1.serialize(&mut writer)?;
        // 6. fee_recipient
        self.fee_recipient.serialize(&mut writer)?;

        writer
            .into_inner()
            .map_err(|_| error!(ErrorCode::InvalidArgs))
    }
