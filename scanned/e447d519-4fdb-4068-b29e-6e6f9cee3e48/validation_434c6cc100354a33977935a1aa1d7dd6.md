### Title
Blacklisted Recipient Permanently Freezes Bridged Funds in `finTransfer` - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

### Summary

When a user initiates a NEAR → EVM bridge transfer, their tokens are locked or burned on NEAR. The relayer then calls `finTransfer` on the EVM contract to release or mint tokens to `payload.recipient`. If `payload.recipient` is blacklisted by the token contract (e.g., USDC) after the transfer was initiated on NEAR, every call to `finTransfer` will revert via `safeTransfer`, and there is no alternative finalization path. The source-chain funds are permanently frozen with no recovery mechanism.

### Finding Description

The EVM `OmniBridge.finTransfer` function unconditionally sends the full bridged amount to `payload.recipient` using `IERC20.safeTransfer` for non-bridge tokens:

```solidity
} else {
    IERC20(payload.tokenAddress).safeTransfer(
        payload.recipient,
        payload.amount
    );
}
``` [1](#0-0) 

`safeTransfer` reverts if the recipient is blacklisted by the token (USDC, USDT, etc.). Because the entire `finTransfer` transaction reverts atomically, the nonce/finalization flag is also rolled back, meaning the call can be retried — but the recipient remains blacklisted, so every retry also reverts.

Meanwhile, on the NEAR side, the tokens were already locked or burned when the user called `init_transfer` / `ft_transfer_call`. The NEAR contract has no mechanism to reverse a completed lock or burn based on a failed EVM finalization. The `fin_transfer_send_tokens_callback` on NEAR only handles the NEAR-side state: [2](#0-1) 

There is no cross-chain "unwind" path: the NEAR side considers the transfer initiated and the EVM side can never finalize it. The funds are permanently frozen.

### Impact Explanation

A user whose EVM address is blacklisted by USDC (or any token with blacklist functionality) after initiating a NEAR → EVM bridge transfer loses their bridged funds permanently. The tokens are burned/locked on NEAR and can never be released on EVM. This is a direct, irreversible loss of bridged funds matching the critical impact scope.

### Likelihood Explanation

USDC and USDT both implement address blacklisting. OFAC sanctions, exchange compliance actions, or protocol-level blacklisting can affect any address at any time. A user who initiates a bridge transfer and is subsequently blacklisted (even due to an unrelated on-chain interaction) triggers this condition. The bridge has no time-bound expiry or cancellation mechanism for in-flight transfers, making this a realistic and permanent loss scenario.

### Recommendation

Separate the finalization from the delivery, analogous to the Axis Finance fix. Options include:

1. **Pull-based delivery**: Mark the transfer as finalized and record the claimable amount for the recipient. The recipient (or anyone on their behalf) calls a separate `claimTransfer` function. If the recipient is blacklisted, only they are affected; the finalization record is already committed.
2. **Fallback recipient**: Allow the original sender (proven via the transfer message) to specify an alternative recipient address if the primary recipient cannot receive tokens.
3. **Cancellation path**: Allow the NEAR contract to accept a proof of failed EVM finalization and refund the locked/burned tokens to the original sender.

### Proof of Concept

1. Alice holds USDC and initiates a NEAR → EVM bridge transfer of 10,000 USDC to her EVM address `0xAlice`. On NEAR, 10,000 USDC is burned from her account.
2. Before the relayer calls `finTransfer` on EVM, Alice's address `0xAlice` is blacklisted by the USDC contract (e.g., due to an OFAC sanction).
3. The relayer calls `finTransfer` on EVM. The call reaches:
   ```solidity
   IERC20(payload.tokenAddress).safeTransfer(payload.recipient, payload.amount);
   ```
   USDC's `transfer` reverts because `0xAlice` is blacklisted. The entire transaction reverts.
4. The relayer retries — same result. No other address can be substituted because `payload.recipient` is fixed in the signed transfer message.
5. Alice's 10,000 USDC is permanently lost: burned on NEAR, undeliverable on EVM. [3](#0-2)

    pub fn fin_transfer_send_tokens_callback(
        &mut self,
        #[serializer(borsh)] transfer_message: TransferMessage,
        #[serializer(borsh)] fee_recipient: &AccountId,
        #[serializer(borsh)] is_ft_transfer_call: bool,
        #[serializer(borsh)] storage_owner: &AccountId,
        #[serializer(borsh)] lock_actions: Vec<LockAction>,
    ) {
        let token = self.get_token_id(&transfer_message.token);

        if Self::is_refund_required(is_ft_transfer_call) {
            self.burn_tokens_if_needed(
                token.clone(),
                U128(
                    transfer_message
                        .amount_without_fee()
                        .near_expect(BridgeError::InvalidFee),
                ),
            );

            self.revert_lock_actions(&lock_actions);

            self.remove_fin_transfer(&transfer_message.get_transfer_id(), storage_owner);

            env::log_str(
                &OmniBridgeEvent::FailedFinTransferEvent { transfer_message }.to_log_string(),
            );
