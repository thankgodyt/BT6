### Title
Undetected `ft_transfer` Failure in `fin_transfer_send_tokens_callback` Causes Permanent Loss of Bridged Funds — (File: `near/omni-bridge/src/lib.rs`)

---

### Summary

`fin_transfer_send_tokens_callback` only checks the promise result of the token-delivery step when `is_ft_transfer_call = true` (i.e., when a non-empty `msg` triggers `ft_transfer_call`). When the delivery uses a plain `ft_transfer` (`msg` is empty), the callback unconditionally treats the transfer as successful regardless of whether the underlying `ft_transfer` promise failed. Because the transfer is already marked finalized in `finalised_transfers` before `send_tokens` is called, a failed `ft_transfer` permanently destroys the recipient's bridged funds with no recovery path.

---

### Finding Description

The inbound finalization flow for NEAR-destined transfers is:

1. `fin_transfer` → proof verification → `fin_transfer_callback`
2. `fin_transfer_callback` → `process_fin_transfer_to_near`
3. `process_fin_transfer_to_near` calls `add_fin_transfer` (marks the transfer finalized in `finalised_transfers`) and then calls `send_tokens`
4. `send_tokens` dispatches either `ft_transfer` (empty `msg`) or `ft_transfer_call` (non-empty `msg`)
5. The result is handled by `fin_transfer_send_tokens_callback` [1](#0-0) 

The critical flaw is in `is_refund_required`: [2](#0-1) 

When `is_ft_transfer_call = false`, the function returns `false` unconditionally — it never reads the promise result. Consequently, `fin_transfer_send_tokens_callback` always takes the `else` branch: [3](#0-2) 

The `else` branch sends the fee and emits `FinTransferEvent` as if delivery succeeded, even when the `ft_transfer` promise failed: [4](#0-3) 

The `send_tokens` path for a plain `ft_transfer` (non-deployed token, empty `msg`): [5](#0-4) 

Because the prover marks the proof as used in its own contract state (not reverted by a later callback panic), and `add_fin_transfer` has already written to `finalised_transfers`, there is no mechanism to retry the delivery. The transfer ID is consumed permanently.

---

### Impact Explanation

A recipient whose `ft_transfer` fails (e.g., because the token contract has a blocklist and the token issuer has blocked that address) permanently loses their bridged funds. The proof is consumed, the transfer is finalized, the fee is paid to the relayer, and the recipient receives nothing. There is no emergency-withdrawal or retry path in the contract.

This matches the allowed impact: **permanent freezing / loss of bridged funds**.

---

### Likelihood Explanation

Several production tokens registered with the bridge (e.g., USDC, which has an on-chain blocklist controlled by Circle) can reject `ft_transfer` to specific addresses. The token issuer is entirely independent of the bridge DAO. A user whose address is added to such a blocklist after initiating a cross-chain transfer — or who is targeted by the token issuer — will have their funds permanently destroyed upon finalization. No admin compromise of the bridge is required; only the token issuer's normal administrative capability over their own token is needed.

---

### Recommendation

`fin_transfer_send_tokens_callback` must check the promise result of the `ft_transfer` step regardless of whether `msg` is empty. If the promise failed, the transfer should be removed from `finalised_transfers` (or a retry mechanism should be provided), and the locked tokens should be restored via `revert_lock_actions`. The pattern already used for `ft_transfer_call` (checking `is_refund_required`) should be extended to cover the plain `ft_transfer` case by inspecting `env::promise_result_checked(0, ...)` and treating a `Failed` result as a refund trigger.

---

### Proof of Concept

1. USDC (a native NEAR token with a Circle-controlled blocklist) is registered with the bridge.
2. Alice initiates a transfer of 10,000 USDC from Ethereum to her NEAR address.
3. Circle adds Alice's NEAR address to the USDC blocklist (e.g., due to a compliance action).
4. A relayer calls `fin_transfer` with a valid proof.
5. `fin_transfer_callback` → `process_fin_transfer_to_near`:
   - `add_fin_transfer` writes Alice's transfer ID to `finalised_transfers`. [1](#0-0) 
   - `send_tokens` dispatches `ft_transfer(alice, 10000, None)`. [5](#0-4) 
6. USDC's `ft_transfer` panics because Alice is blocklisted. The promise result is `Failed`.
7. `fin_transfer_send_tokens_callback` is called with `is_ft_transfer_call = false`.
8. `is_refund_required(false)` returns `false` unconditionally. [6](#0-5) 
9. The callback emits `FinTransferEvent` and pays the relayer fee. Alice receives 0 USDC.
10. Any retry of `fin_transfer` with the same proof is rejected by the prover (proof already used) and by `finalised_transfers`. Alice's 10,000 USDC is permanently lost.
