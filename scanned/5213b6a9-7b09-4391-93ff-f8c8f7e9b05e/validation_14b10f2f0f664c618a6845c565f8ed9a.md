### Title
Native ETH `finTransfer` to a rejecting contract recipient permanently freezes bridged funds — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

When finalizing a cross-chain transfer of native ETH on the EVM side, `OmniBridge.finTransfer` sends ETH to the recipient via a raw low-level call. If the recipient is a contract that lacks a `receive()` / `fallback()` function or whose `receive()` reverts, the call fails and the entire transaction reverts. Because the recipient address is cryptographically bound to the MPC-signed payload and cannot be changed, no relayer can ever successfully finalize the transfer. The corresponding transfer message on NEAR has no user-accessible cancellation path, so the bridged ETH is permanently frozen.

---

### Finding Description

In `OmniBridge.sol`, `finTransfer` first marks the destination nonce as consumed, then dispatches the asset to the recipient. For native ETH (`payload.tokenAddress == address(0)`) the dispatch is:

```solidity
(bool success, ) = payload.recipient.call{value: payload.amount}("");
if (!success) revert FailedToSendEther();
``` [1](#0-0) 

Because the whole transaction reverts on failure, the `completedTransfers[payload.destinationNonce] = true` write at line 287 is also rolled back: [2](#0-1) 

This means the nonce is never consumed and the relayer can retry — but the signed `payload.recipient` is immutable (it is part of the MPC-signed `borshEncoded` blob verified at line 311): [3](#0-2) 

No alternative recipient can be substituted. On the NEAR side, the transfer message is stored by `add_transfer_message` and is only removed by `remove_transfer_message` (called from `claim_fee_callback` or `sign_transfer_callback`) or `remove_transfer_message_without_refund`. Neither path is reachable by the user once the MPC signature has been issued: [4](#0-3) 

There is no user-callable cancel or refund function. The locked/burned tokens on the source chain are therefore irrecoverable.

---

### Impact Explanation

A user who bridges native ETH to a contract recipient that cannot accept a plain ETH transfer (no `receive()`, a reverting `receive()`, or a proxy that was upgraded after the transfer was initiated) will have their funds permanently frozen. The source-chain escrow (locked or burned tokens on NEAR) can never be released because `finTransfer` will always revert, and no on-chain mechanism exists to cancel the pending transfer message and refund the sender.

This satisfies the allowed critical impact: **permanent freezing of bridged funds**.

---

### Likelihood Explanation

The scenario is realistic and reachable by any unprivileged bridge user:

1. **Accidental**: A user bridges ETH to a DeFi contract (e.g., a vault, a multisig, a proxy) that does not implement `receive()`. This is common — many contracts intentionally reject plain ETH to avoid accidental sends.
2. **Intentional grief**: A malicious recipient deploys a contract that accepts ETH during the transfer-initiation window, then upgrades (or self-destructs and redeploys) to reject ETH before the relayer calls `finTransfer`. The sender's funds are permanently locked.
3. **No admin escape hatch**: There is no DAO or operator function to forcibly finalize or cancel a stuck transfer.

---

### Recommendation

Wrap native ETH as WETH before delivering it to the recipient, mirroring the fix described in the referenced report. This eliminates the recipient's ability to reject the transfer:

```solidity
if (payload.tokenAddress == address(0)) {
    IWETH(wethAddress).deposit{value: payload.amount}();
    IERC20(wethAddress).safeTransfer(payload.recipient, payload.amount);
}
```

Alternatively, use a pull-payment pattern: credit the recipient's claimable balance on failure and allow them to withdraw later, so a single bad recipient cannot permanently block the protocol-level nonce or lock source-chain funds.

---

### Proof of Concept

1. Deploy a malicious contract `Rejecter` on the target EVM chain:
   ```solidity
   contract Rejecter {
       receive() external payable { revert("no ETH"); }
   }
   ```
2. On NEAR, call `ft_on_transfer` (or the equivalent init-transfer entry) to bridge `N` ETH, setting `recipient = address(Rejecter)`.
3. The NEAR bridge locks/burns the tokens and stores the transfer message via `add_transfer_message`.
4. The MPC network signs the payload; `sign_transfer_callback` is called.
5. Any relayer calls `OmniBridge.finTransfer` on the EVM chain. The call to `Rejecter.receive()` reverts → `FailedToSendEther` → entire tx reverts.
6. The relayer retries indefinitely — every attempt reverts.
7. The NEAR transfer message is never removed; the user's ETH is permanently frozen with no recovery path. [1](#0-0) [5](#0-4)
