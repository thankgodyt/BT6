### Title
ERC1155 tokens permanently locked in `OmniBridge` when recipient contract does not implement `IERC1155Receiver` - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

The `finTransfer` function in `OmniBridge.sol` uses `IERC1155.safeTransferFrom` to deliver ERC1155 tokens to the recipient when finalizing a cross-chain transfer. If the recipient is a contract that does not implement `IERC1155Receiver`, the call reverts unconditionally, and the bridged ERC1155 tokens become permanently locked in the bridge contract with no recovery path.

---

### Finding Description

When a user bridges ERC1155 tokens from NEAR to an EVM chain, the tokens are first deposited into the bridge via `initTransfer1155`, which calls `IERC1155.safeTransferFrom` from the user to `address(this)` (the bridge contract). The NEAR side then processes the outbound transfer (burning or locking the NEAR-side representation).

On the EVM finalization side, `finTransfer` is called with an MPC-signed payload. When the `tokenAddress` maps to a registered ERC1155 multi-token, the function executes:

```solidity
IERC1155(multiToken.tokenAddress).safeTransferFrom(
    address(this),
    payload.recipient,
    multiToken.tokenId,
    payload.amount,
    ""
);
``` [1](#0-0) 

The ERC1155 standard mandates that `safeTransferFrom` calls `onERC1155Received` on the recipient if it is a contract, and reverts if the return value is not the correct selector. If `payload.recipient` is a contract that does not implement `IERC1155Receiver`, this call reverts every time.

The `payload.recipient` is cryptographically bound inside the MPC-signed Borsh payload: [2](#0-1) 

There is no mechanism in the protocol to re-route the transfer to a different recipient after the MPC signature has been issued. Every subsequent call to `finTransfer` with the same payload will revert at the same point, leaving the ERC1155 tokens permanently locked inside the bridge contract.

---

### Impact Explanation

**Critical — Permanent freezing of bridged ERC1155 funds.**

A user who specifies a contract address as their EVM recipient (e.g., a multisig, DAO treasury, or any contract without `IERC1155Receiver`) will have their ERC1155 tokens permanently locked in the `OmniBridge` contract. The NEAR-side transfer has already been finalized (tokens burned/locked on NEAR), and the EVM-side `finTransfer` can never succeed for that recipient. There is no admin escape hatch, no recipient-change mechanism, and no refund path in the protocol.

---

### Likelihood Explanation

**Medium.** Many legitimate EVM contract wallets (Gnosis Safe prior to ERC1155 support, custom DAO treasuries, proxy contracts, etc.) do not implement `IERC1155Receiver`. A user who bridges ERC1155 tokens to such an address — a realistic and common use case — will trigger this condition. No special attacker capability is required; the victim simply needs to specify a non-receiver contract as their EVM recipient.

---

### Recommendation

Replace `safeTransferFrom` with a direct low-level transfer that does not invoke the receiver callback. For ERC1155, the standard does not define a non-safe variant, so the recommended approach is to use a low-level call bypassing the callback check, or to implement a pull-based withdrawal pattern where the bridge holds the tokens and the recipient claims them via a separate function. A minimal fix is to wrap the call in a try/catch and store unclaimed tokens in a claimable mapping keyed by recipient, allowing the user to later claim from a different address or after upgrading their contract.

---

### Proof of Concept

1. User calls `initTransfer1155` on the EVM bridge, depositing 10 units of ERC1155 token ID 42 into the bridge. The bridge now holds the tokens.
2. The NEAR side processes the transfer and the MPC network signs a `TransferMessagePayload` with `recipient = address(VaultContract)`, where `VaultContract` is a Gnosis Safe that does not implement `IERC1155Receiver`.
3. A relayer calls `finTransfer(signatureData, payload)`.
4. Signature verification passes at line 311.
5. The branch at line 323 is taken because `multiTokens[payload.tokenAddress].tokenAddress != address(0)`.
6. `IERC1155(multiToken.tokenAddress).safeTransferFrom(address(this), VaultContract, 42, 10, "")` is called.
7. The ERC1155 token contract calls `VaultContract.onERC1155Received(...)`, which does not exist, causing a revert.
8. The entire `finTransfer` transaction reverts. The nonce is not consumed (state reverts), but the payload is permanently undeliverable because the recipient is fixed in the MPC signature.
9. The 10 ERC1155 tokens remain locked in the bridge contract indefinitely with no recovery mechanism. [3](#0-2) [4](#0-3)
