### Title
Missing Normalization Check in `init_transfer` Permanently Locks Tokens When `sign_transfer` Enforces `amount_to_transfer > 0` - (File: `near/omni-bridge/src/lib.rs`)

---

### Summary

The `init_transfer` function accepts and locks any token amount satisfying `fee < amount`, but `sign_transfer` later enforces that the decimal-normalized net amount is strictly greater than zero. For tokens whose NEAR-side decimals exceed the destination-chain decimals (e.g., a 24-decimal NEAR token bridging to an 18-decimal EVM chain), any deposit whose `amount - fee` is smaller than `10^(origin_decimals - decimals)` normalizes to zero. Because there is no cancel-transfer path, those tokens are permanently locked in the bridge escrow with no recovery mechanism.

---

### Finding Description

**Step 1 – `init_transfer` accepts the deposit without checking the normalized net amount.**

`init_transfer` only validates that `fee.fee < amount`:

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```

No check is made that `normalize_amount(amount - fee, decimals) > 0`. The token decimals are not even consulted at this stage.

**Step 2 – `normalize_amount` uses floor division.**

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

For a token registered with `origin_decimals = 24` and `decimals = 18`, any net amount below `1_000_000` (i.e., below 1 micro-unit on NEAR) divides to zero.

**Step 3 – `sign_transfer` hard-blocks on the zero result.**

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

Every call to `sign_transfer` for this transfer will panic. The transfer message is never removed from storage.

**Step 4 – No cancel/refund path exists.**

`remove_transfer_message` is only called inside `sign_transfer_callback` (when fee is zero and the MPC signature succeeds) and `claim_fee_callback`. Neither is reachable when `sign_transfer` itself panics before reaching the MPC call. There is no user-callable cancel function.

**Two concrete entry paths:**

| Path | How it reaches the stuck state |
|---|---|
| Small deposit | User calls `ft_transfer_call` with `amount < 10^(origin_decimals - decimals)` and `fee = 0`. Passes `init_transfer`'s `fee < amount` check; normalizes to 0 in `sign_transfer`. |
| Fee update | User calls `update_transfer_fee` setting `fee = amount - 1` (allowed by `fee < amount` guard). Net amount becomes 1; normalizes to 0 for any token with `origin_decimals > decimals`. |

---

### Impact Explanation

Tokens transferred into the bridge via `ft_transfer_call` are either held by the bridge contract (native tokens) or burned (bridge tokens). If `sign_transfer` permanently panics, native tokens are locked in the contract forever and bridge tokens are burned with no corresponding mint on the destination chain. This is a permanent, irrecoverable loss of user funds — a critical escrow mis-accounting / decimal normalization abuse issue.

---

### Likelihood Explanation

The condition is reachable by any unprivileged user through the public `ft_transfer_call` → `init_transfer` path. It is especially likely for high-decimal NEAR tokens (24 decimals) bridging to 18-decimal EVM chains, where the normalization divisor is `10^6`. A user depositing fewer than `1_000_000` base units (a plausible dust amount) triggers the bug. The `update_transfer_fee` path additionally allows a user to self-inflict the condition on an existing transfer of any size.

---

### Recommendation

Add a normalization check inside `init_transfer` before locking the tokens. The token decimals are already stored in `self.token_decimals` and can be looked up at this point:

```rust
// After building transfer_message, before locking tokens:
if let Some(token_address) = self.get_token_address(
    transfer_message.get_destination_chain(),
    self.get_token_id(&transfer_message.token),
) {
    if let Some(decimals) = self.token_decimals.get(&token_address) {
        let net = transfer_message.amount_without_fee()
            .near_expect(BridgeError::InvalidFee);
        require!(
            Self::normalize_amount(net, decimals) > 0,
            BridgeError::InvalidAmountToTransfer.as_ref()
        );
    }
}
```

Apply the same guard inside `update_transfer_fee` when the new fee is accepted, to prevent an existing transfer from being driven into the unrecoverable state.

---

### Proof of Concept

1. A NEAR token is registered with `origin_decimals = 24`, `decimals = 18` (normalization divisor = `10^6`).
2. Alice calls `ft_transfer_call` with `amount = 500_000` (500,000 yoctoNEAR) and `fee = 0`.
3. `init_transfer` passes: `0 < 500_000`. Tokens are transferred to the bridge contract. A `TransferMessage` is stored.
4. A relayer calls `sign_transfer` for Alice's transfer.
5. `normalize_amount(500_000, {decimals:18, origin_decimals:24})` = `500_000 / 1_000_000` = `0`.
6. `require!(0 > 0, ...)` panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.
7. The MPC signing call is never made. The transfer message remains in storage permanently.
