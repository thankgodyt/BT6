### Title
Double-Finalization via `remove_fin_transfer` in Failed `ft_transfer_call` Callback — (`near/omni-bridge/src/lib.rs`)

### Summary

When an inbound transfer to a NEAR recipient uses `ft_transfer_call` (i.e., `msg` is non-empty) and the recipient's `ft_on_transfer` returns `U128(0)`, the callback `fin_transfer_send_tokens_callback` calls `remove_fin_transfer`, which **permanently deletes the transfer ID from `finalised_transfers`**. This allows the same proof to be submitted a second time, passing the `add_fin_transfer` uniqueness check, and minting or unlocking tokens a second time.

### Finding Description

The call chain is:

1. **`fin_transfer` → `fin_transfer_callback` → `process_fin_transfer_to_near`** (line 1875): `add_fin_transfer` inserts the transfer ID into `finalised_transfers` as the replay-prevention guard. [1](#0-0) 

2. **`process_fin_transfer_to_near`** then calls `send_tokens` (which issues `ft_transfer_call` to the recipient) and chains `fin_transfer_send_tokens_callback` as the resolution callback. [2](#0-1) 

3. **`fin_transfer_send_tokens_callback`** (line 1702): when `is_refund_required` is true (i.e., `ft_on_transfer` returned `U128(0)`), it burns the returned tokens, reverts lock actions, and then calls `remove_fin_transfer`, **erasing the transfer ID from `finalised_transfers`**. [3](#0-2) 

4. **`remove_fin_transfer`** (line 2322–2333): unconditionally removes the entry and refunds storage — no permanent tombstone is left. [4](#0-3) 

5. After removal, the attacker submits the **same proof** again via `fin_transfer`. `add_fin_transfer` succeeds because the ID is absent from `finalised_transfers`. Tokens are minted or unlocked a second time.

`is_refund_required` is determined solely by the return value of `ft_on_transfer`: [5](#0-4) 

An attacker-controlled recipient contract can return `U128(0)` on the first call (triggering the removal) and then accept tokens normally on the second call.

### Impact Explanation

- **Deployed (bridged) tokens**: On the first call, tokens are minted and sent via `ft_transfer_call`; the recipient returns them; the bridge burns them. Transfer ID is removed. On the second call, tokens are minted again and kept by the attacker. Net result: **unauthorized double-minting**.
- **Native NEAR tokens (locked on NEAR side)**: On the first call, tokens are unlocked and sent; the recipient returns them; `revert_lock_actions` re-locks them. Transfer ID is removed. On the second call, tokens are unlocked again and kept. Net result: **double-spending of locked funds**.

### Likelihood Explanation

The attacker only needs:
1. A valid inbound proof for a transfer they initiated from the source chain (a normal user action).
2. A recipient contract they control that returns `U128(0)` from `ft_on_transfer` on the first invocation and accepts tokens on the second.

No admin compromise, key leakage, or validator collusion is required. The exploit is fully self-contained within the NEAR smart contract and is reproducible on a local testnet.

### Recommendation

**Never remove a transfer ID from `finalised_transfers` after tokens have been released or attempted to be released.** The fix is to keep the ID permanently in `finalised_transfers` regardless of whether the `ft_transfer_call` succeeded or failed. If a refund is needed, the bridge should handle it without erasing the replay-prevention record. Alternatively, replace `remove_fin_transfer` in the failure path with a "failed" tombstone state so that re-submission of the same proof is still rejected.

### Proof of Concept

```
1. Attacker deploys `MaliciousReceiver` on NEAR:
   - First call to `ft_on_transfer`: returns U128(0) (triggers refund path)
   - Second call to `ft_on_transfer`: returns U128(amount) (accepts tokens)

2. Attacker initiates a transfer from EVM → NEAR with:
   - recipient = MaliciousReceiver
   - msg = "<non-empty>" (forces ft_transfer_call path)

3. Attacker calls `fin_transfer(proof)`:
   - add_fin_transfer inserts transfer_id into finalised_transfers ✓
   - ft_transfer_call → MaliciousReceiver.ft_on_transfer returns U128(0)
   - fin_transfer_send_tokens_callback: is_refund_required = true
   - burn_tokens_if_needed (tokens burned / re-locked)
   - remove_fin_transfer removes transfer_id from finalised_transfers ← BUG

4. Attacker immediately calls `fin_transfer(same proof)`:
   - add_fin_transfer: transfer_id not in finalised_transfers → INSERT succeeds
   - ft_transfer_call → MaliciousReceiver.ft_on_transfer returns U128(amount)
   - fin_transfer_send_tokens_callback: is_refund_required = false
   - Tokens minted/unlocked and kept by attacker

5. Assert: attacker holds tokens from a proof that was already "finalized" once.
```

        if is_ft_transfer_call {

                Ok(value) => {
                    if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {

                        // The amount can be zero if the `ft_on_transfer` in the receiver contract returns an amount instead of `0`, or if it panics.

                    } else {
                        // Unexpected case: don't refund
                        false
                    }
                }
                // Unexpected case: don't refund
                Err(_) => false,
            }
        } else {
            // Not ft_transfer_call: don't refund
            false
        }

    fn remove_fin_transfer(&mut self, transfer_id: &TransferId, storage_owner: &AccountId) {
        let storage_usage = env::storage_usage();
        self.finalised_transfers.remove(transfer_id);

        let refund =
            env::storage_byte_cost().saturating_mul((storage_usage - env::storage_usage()).into());

        if let Some(mut storage) = self.accounts_balances.get(storage_owner) {
            storage.available = storage.available.saturating_add(refund);
            self.accounts_balances.insert(storage_owner, &storage);
        }
    }
