### Title
Premature Burn of Deployed Tokens in `init_transfer_internal` Causes Permanent Token Loss if Destination Finalization Fails — (`File: near/omni-bridge/src/lib.rs`)

### Summary

In the NEAR Omni Bridge, when a user initiates an outbound transfer of a **deployed (bridged) token** (e.g., wETH on NEAR back to Ethereum), the token is burned immediately inside `init_transfer_internal` before any confirmation that the destination chain has successfully finalized the transfer. There is no cancel or refund path. If the destination chain execution permanently fails, the user's tokens are burned on NEAR while the corresponding locked tokens remain stranded on the destination chain — a direct analog to the BurnUnlock vulnerability class.

---

### Finding Description

The NEAR → Foreign chain outbound flow for deployed tokens follows this sequence:

1. User calls `ft_transfer_call` on the token contract → triggers `ft_on_transfer` on the bridge.
2. Bridge calls `init_transfer` → `init_transfer_internal`.
3. Inside `init_transfer_internal`, `burn_tokens_if_needed` is called **immediately and unconditionally** for deployed tokens.
4. An `InitTransferEvent` is emitted.
5. A relayer later calls `sign_transfer` to obtain an MPC signature.
6. The relayer submits the signed transaction to the destination chain (`finTransfer` on EVM, `finalize_transfer` on Solana, `fin_transfer` on Starknet).

The burn at step 3 is irreversible and happens with no dependency on steps 5 or 6 succeeding. [1](#0-0) 

```rust
if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
    self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
    self.lock_tokens_if_needed(
        transfer_message.get_destination_chain(),
        &token_id,
        transfer_message.amount.0,
    );
```

`burn_tokens_if_needed` fires a detached cross-contract call to burn the token with no result check: [2](#0-1) 

```rust
fn burn_tokens_if_needed(&self, token: AccountId, amount: U128) {
    if self.is_deployed_token(&token) {
        ext_token::ext(token)
            .with_static_gas(BURN_TOKEN_GAS)
            .burn(amount)
            .detach();   // ← fire-and-forget, no callback
    }
}
```

The `sign_transfer_callback` — the only callback in the outbound path — does nothing on MPC failure: it silently returns, leaving the transfer in `pending_transfers` with the tokens already burned and no recovery path: [3](#0-2) 

```rust
pub fn sign_transfer_callback(...) {
    if let Ok(signature) = call_result {   // ← error branch: no refund, no cancel
        ...
        env::log_str(...);
    }
}
```

There is no `cancel_transfer` function. The only way to remove a transfer from `pending_transfers` is via `claim_fee`, which requires a proof that the destination chain **successfully finalized** the transfer: [4](#0-3) 

So if finalization never happens, the transfer record is orphaned in `pending_transfers` forever, and the burned tokens are unrecoverable.

The same premature-burn pattern also appears in `fast_fin_transfer_to_other_chain`, which burns tokens before the destination chain leg is confirmed: [5](#0-4) 

---

### Impact Explanation

For any deployed/bridged token (e.g., wETH, wSOL, or any token whose origin chain is not NEAR), a user who initiates an outbound transfer loses their tokens on NEAR the moment `init_transfer_internal` executes. If the destination chain finalization permanently fails, the user's tokens are burned on NEAR while the corresponding locked tokens remain stranded on the destination chain — permanent, irrecoverable loss of bridged funds on both chains.

This matches the **Critical** allowed impact: *"Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds."*

---

### Likelihood Explanation

Permanent finalization failure can occur via several realistic, non-admin-compromise paths:

1. **Destination bridge paused**: If the destination chain bridge contract is paused (e.g., due to a security incident on the destination side) after the NEAR burn but before the relayer submits the transaction, the transfer cannot be finalized. The NEAR tokens are already burned.

2. **Token not registered on destination**: If the token address mapping is missing or incorrect on the destination chain, `finTransfer`/`finalize_transfer` reverts. The NEAR side does not re-check this after burning.

3. **MPC signing permanently unavailable for a specific transfer**: If the MPC network is temporarily unavailable and the transfer's pending state is eventually garbage-collected or the user cannot retry (e.g., storage balance exhausted), the burned tokens are unrecoverable.

4. **Destination chain nonce collision or contract bug**: Any permanent revert on the destination chain leaves the burned NEAR tokens with no recovery path.

None of these require admin key compromise, MPC threshold collusion, or NEAR validator collusion.

---

### Recommendation

Adopt the same lock-then-burn pattern used by the Chakra `MintBurn` mode and by the NEAR bridge's own inbound path (`fin_transfer_send_tokens_callback` correctly reverts lock actions on failure):

1. **Do not burn in `init_transfer_internal`**. Instead, keep the tokens locked in the bridge contract (they are already transferred in via `ft_transfer_call`).
2. **Burn only after confirmed destination finalization** — i.e., when `claim_fee` is called with a valid destination-chain proof, burn the tokens at that point.
3. **Add a cancel/refund path**: If a transfer has been pending for too long with no finalization proof, allow the original sender to cancel and recover their tokens.

This mirrors the safe pattern already present in `fin_transfer_send_tokens_callback`, which correctly calls `revert_lock_actions` on failure: [6](#0-5) 

---

### Proof of Concept

1. Alice holds 1000 wETH (a deployed token on NEAR, origin chain = Ethereum).
2. Alice calls `ft_transfer_call` on wETH.near to bridge back to Ethereum.
3. `init_transfer_internal` burns 1000 wETH.near immediately. Alice now has 0 wETH.near.
4. The Ethereum `OmniBridge` contract is paused due to a security incident on the Ethereum side.
5. The relayer cannot call `finTransfer` — it reverts with `PAUSED_FIN_TRANSFER`.
6. The Ethereum bridge is never unpaused (or is unpaused only after the transfer's pending record is stale).
7. Alice's 1000 wETH.near are permanently burned. The 1000 ETH remain locked in the Ethereum bridge contract. Alice has lost her funds on both chains with no on-chain recovery mechanism.
