### Title
Uncapped User-Controlled Fee in `coreReceiveWithData` ACTION_INIT_TRANSFER Allows Near-Total Value Redirection — (`evm/src/omni-bridge/contracts/HlBridgeToken.sol`)

---

### Summary

`HyperliquedBridgeToken.coreReceiveWithData` decodes `fee` directly from attacker-controlled calldata and forwards it verbatim to `OmniBridge.initTransfer`. The only guard in `initTransfer` is `fee >= amount`, which means `fee = amount - 1` is accepted. A HyperCore user can set this value to redirect nearly the entire bridged amount to the relayer (themselves), leaving the declared recipient with 1 wei.

---

### Finding Description

In `coreReceiveWithData`, the `ACTION_INIT_TRANSFER` branch decodes `fee` from the `data` bytes supplied by the HyperCore user and passes it directly to `initTransfer` with no intermediate bounds check: [1](#0-0) 

The only fee guard lives in `OmniBridge.initTransfer`: [2](#0-1) 

`fee >= amount` rejects equality and overflow, but `fee = amount - 1` satisfies `fee < amount` and passes. The resulting `InitTransfer` event carries `fee = amount - 1`: [3](#0-2) 

On the NEAR side, `fin_transfer_callback` denormalizes the fee from the event and constructs a `TransferMessage` where `fee.fee = amount - 1`. The recipient receives `amount_without_fee() = 1`, and the relayer (`predecessor_account_id`) receives `amount - 1`: [4](#0-3) [5](#0-4) [6](#0-5) 

---

### Impact Explanation

An attacker who is both the HyperCore sender and the NEAR relayer:

1. Sends `amount` tokens from HyperCore with `fee = amount - 1` and `recipient = "near:victim"`.
2. The `InitTransfer` event is accepted by `OmniBridge` (fee < amount passes).
3. The attacker relays the proof on NEAR, receiving `amount - 1` tokens as the fee recipient.
4. The victim receives 1 wei.

Net: attacker recovers `amount - 1` tokens on NEAR while the victim is deprived of `amount - 1` tokens they were owed. This is a direct, profitable fee mis-accounting exploit — not mere griefing.

---

### Likelihood Explanation

- The entry point (`sendToEvmWithData` → `coreReceiveWithData`) is a supported production path for HyperCore users.
- The attacker fully controls the `data` bytes, including the `fee` field.
- No privileged role or key compromise is required; any HyperCore user with a token balance can execute this.
- Being a NEAR relayer is permissionless in the protocol.

---

### Recommendation

Add an explicit fee cap in `coreReceiveWithData` before delegating to `initTransfer`. For example:

```solidity
} else if (action == ACTION_INIT_TRANSFER) {
    (uint128 fee, string memory recipient, string memory message) = abi
        .decode(tail, (uint128, string, string));
    uint128 amount128 = amount.toUint128();
    // Enforce a protocol-defined maximum fee ratio, e.g. fee must be 0 or
    // within a small percentage of amount, not amount - 1.
    if (fee >= amount128) revert InvalidFee();
    // Optionally: require(fee <= maxFeeRatio * amount128 / 1e18, "FeeTooHigh");
    _update(_systemAddress, address(this), amount);
    IOmniBridgeInitTransfer(owner()).initTransfer(
        address(this), amount128, fee, 0, recipient, message
    );
}
```

The root fix is that `coreReceiveWithData` must not blindly trust the user-supplied `fee`. A strict cap (e.g., fee ≤ some protocol-defined maximum percentage of amount) should be enforced at the `HlBridgeToken` layer before the call reaches `OmniBridge`.

---

### Proof of Concept

```solidity
// Foundry test (local fork, no mainnet interaction)
function test_feeManipulation() public {
    // Setup: HyperliquedBridgeToken initialized, registered in OmniBridge
    // _systemAddress pool has `amount` tokens (minted via 3-arg mint)
    uint256 amount = 1000e18;
    uint128 fee = uint128(amount) - 1; // amount - 1

    bytes memory data = abi.encodePacked(
        uint8(1), // ACTION_INIT_TRANSFER
        abi.encode(fee, "near:victim", "")
    );

    vm.prank(systemAddress);
    token.coreReceiveWithData(
        attacker,
        bytes32(0),
        0,
        amount,
        0,
        data
    );

    // Assert: InitTransfer event emitted with fee = amount - 1
    // On NEAR finalization: victim gets 1 wei, relayer (attacker) gets amount - 1
}
```

The call succeeds because:
- `msg.sender == _systemAddress` passes the `NotSystemAddress` guard. [7](#0-6) 
- `fee = amount - 1` satisfies `fee < amount` in `initTransfer`. [2](#0-1) 
- No other guard in `coreReceiveWithData` validates the fee magnitude. [1](#0-0)
