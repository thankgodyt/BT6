### Title
Missing Zero-Address Recipient Validation in `init_transfer` Causes Permanent Fund Loss - (File: near/omni-bridge/src/lib.rs)

### Summary
The NEAR bridge's `init_transfer` function accepts any `OmniAddress` as a recipient without checking whether it is a zero address. A user can intentionally or accidentally specify a zero address on a destination chain (e.g., `eth:0x0000000000000000000000000000000000000000`). Tokens are immediately locked or burned on NEAR, and the NEAR MPC signs a payload committing to that zero-address recipient. The resulting `finTransfer` call on EVM either permanently burns native ETH (sent to `address(0)` via `.call`) or permanently freezes ERC-20/bridge tokens (every `finTransfer` attempt reverts because OpenZeppelin rejects minting/transferring to `address(0)`, yet the funds on NEAR are already gone). There is no cancellation or refund path.

### Finding Description
In `near/omni-bridge/src/lib.rs`, the `init_transfer` function validates only that the recipient chain is not NEAR:

```rust
require!(
    init_transfer_msg.recipient.get_chain() != ChainKind::Near,
    BridgeError::InvalidRecipientChain.as_ref()
);
``` [1](#0-0) 

No check is made that the recipient address is non-zero. The `OmniAddress` type already exposes an `is_zero()` method in `near/omni-types/src/lib.rs`:

```rust
pub fn is_zero(&self) -> bool {
    match self {
        Self::Eth(address) | Self::Arb(address) | ... => address.is_zero(),
        Self::Near(address) => *address == ZERO_ACCOUNT_ID,
        Self::Sol(address) | Self::Fogo(address) => address.is_zero(),
        Self::Btc(address) | Self::Zcash(address) => address.is_empty(),
        Self::Strk(address) => address.is_zero(),
    }
}
``` [2](#0-1) 

This utility is never called in `init_transfer`. The zero-address recipient is then embedded into the `TransferMessage` and stored in `pending_transfers`: [3](#0-2) 

When `sign_transfer` is later called, the zero-address recipient is included verbatim in the `TransferMessagePayload` that the NEAR MPC signs: [4](#0-3) 

On the EVM side, `finTransfer` in `OmniBridge.sol` has no zero-address guard on `payload.recipient`: [5](#0-4) 

Two distinct loss scenarios follow:

1. **Native ETH (`tokenAddress == address(0)`):** ETH is sent to `address(0)` via a low-level `.call`, which succeeds silently. The ETH is permanently burned.
2. **ERC-20 / bridge tokens:** OpenZeppelin's `_transfer` and `_mint` both revert on a zero-address recipient. The entire `finTransfer` transaction reverts (including the nonce write), so the nonce is never consumed. Every subsequent relay attempt also reverts. The tokens remain locked/burned on NEAR with no recovery mechanism.

### Impact Explanation
Permanent, irrecoverable loss of bridged funds. Any amount of tokens a user bridges to a zero address is destroyed. For native ETH this is a direct burn; for ERC-20/bridge tokens the funds are frozen on NEAR indefinitely. This matches the **Critical** impact class: permanent freezing or loss of bridged funds.

### Likelihood Explanation
Any unprivileged bridge user can trigger this by passing a zero `OmniAddress` as the recipient in `InitTransferMsg`. It requires no special role, no admin compromise, and no external dependency failure. A single malformed (or malicious) call to `ft_on_transfer` with a zero-address recipient is sufficient.

### Recommendation
Add a zero-address guard immediately after the chain-kind check in `init_transfer`:

```rust
require!(
    init_transfer_msg.recipient.get_chain() != ChainKind::Near,
    BridgeError::InvalidRecipientChain.as_ref()
);
require!(
    !init_transfer_msg.recipient.is_zero(),
    BridgeError::InvalidRecipient.as_ref()  // add this error variant
);
```

The `is_zero()` method already exists on `OmniAddress` and covers all supported chain types.

### Proof of Concept
1. Attacker holds 1 wETH (NEP-141) on NEAR.
2. Attacker calls `ft_transfer_call` on the wETH token contract, targeting the NEAR bridge, with `msg` set to:
   ```json
   {"InitTransfer": {"recipient": "eth:0x0000000000000000000000000000000000000000", "fee": "0", "native_token_fee": "0"}}
   ```
3. `ft_on_transfer` → `init_transfer` passes the chain-kind check (Eth ≠ Near) and stores the transfer with `recipient = OmniAddress::Eth(H160::ZERO)`. The 1 wETH is locked/burned on NEAR.
4. A relayer calls `sign_transfer`; the NEAR MPC signs a `TransferMessagePayload` with `recipient = 0x0000000000000000000000000000000000000000`.
5. The relayer calls `finTransfer` on the EVM `OmniBridge` with the signed payload.
   - If `tokenAddress` is the EVM wETH address (ERC-20): `safeTransfer(address(0), amount)` reverts. The 1 wETH equivalent is permanently frozen on NEAR.
   - If `tokenAddress == address(0)` (native ETH path): `address(0).call{value: amount}("")` succeeds; ETH is permanently burned.
6. No cancellation or refund function exists in the NEAR bridge contract to recover the locked/burned tokens.
