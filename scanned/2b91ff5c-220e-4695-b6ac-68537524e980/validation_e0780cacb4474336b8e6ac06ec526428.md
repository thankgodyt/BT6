### Title
Missing Minimum Transfer Amount Validation Causes Permanent Fund Freezing — (`near/omni-bridge/src/lib.rs`)

### Summary
The `init_transfer` function in the NEAR bridge contract enforces no minimum transfer amount beyond `fee < amount`. When a user initiates an outbound transfer (NEAR → EVM/Solana/etc.) with an amount that is too small to survive decimal normalization, the tokens are irreversibly burned or locked, but `sign_transfer` always panics, permanently freezing the user's funds with no recovery path.

### Finding Description
The `init_transfer` function validates only that the fee is strictly less than the amount: [1](#0-0) 

After this check passes, `init_transfer_internal` immediately burns or locks the full token amount and returns `U128(0)` to the FT contract, consuming all tokens with no refund: [2](#0-1) 

Later, when a relayer calls `sign_transfer`, the bridge normalizes the amount for the destination chain using floor division: [3](#0-2) 

`sign_transfer` then calls `normalize_amount(amount - fee, decimals)` and enforces: [4](#0-3) 

If `amount - fee < 10^(origin_decimals - decimals)`, `normalize_amount` returns `0` via integer floor division, and `sign_transfer` panics with `InvalidAmountToTransfer`. Because the tokens were already burned/locked in `init_transfer_internal` and `ft_on_transfer` returned `U128(0)` (consuming all tokens), there is no cancel or refund mechanism for the pending transfer. The transfer entry remains in `pending_transfers` indefinitely but can never be finalized.

**Concrete example:** For a token with `origin_decimals = 24` (NEAR) and `decimals = 18` (EVM), the decimal difference is 6. Any transfer where `amount - fee < 1_000_000` (i.e., less than 10^6 yocto-units) will normalize to 0. The user's tokens are permanently burned/locked.

The `denormalize_fee` function used in `fast_fin_transfer` applies the same arithmetic, confirming the decimal gap is a real protocol-level property: [5](#0-4) 

The SECURITY.md comment in the code acknowledges dust loss for the remainder case but does not address the case where the entire net amount normalizes to zero: [6](#0-5) 

### Impact Explanation
**Critical.** A user who sends an amount below the decimal normalization threshold permanently loses their bridged tokens. The tokens are burned (for deployed/bridged tokens) or locked (for native tokens) in the NEAR bridge contract, and no `sign_transfer` call can ever succeed for that transfer. There is no cancel, withdraw, or refund entrypoint for pending transfers. This constitutes permanent freezing of bridged funds.

### Likelihood Explanation
**Medium.** Tokens with a large decimal gap between their NEAR representation and their destination-chain representation (e.g., wNEAR: 24 NEAR decimals vs. 18 EVM decimals, threshold = 10^6 yocto-units ≈ 0.000001 NEAR) are directly affected. A user who accidentally sends a dust amount, or a token with an unusually large decimal difference, triggers the freeze. The entry path is the standard public `ft_transfer_call` → `ft_on_transfer` → `init_transfer` flow, requiring no special privileges.

### Recommendation
Add a pre-burn validation in `init_transfer` (before tokens are consumed) that checks the net amount survives normalization:

```rust
let decimals = self.token_decimals.get(&token_address)
    .near_expect(BridgeError::TokenDecimalsNotFound);
let normalized = Self::normalize_amount(
    transfer_message.amount.0 - transfer_message.fee.fee.0,
    decimals,
);
require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

This mirrors the existing guard in `sign_transfer` but places it before the irreversible burn/lock step.

### Proof of Concept
1. Register a token with `origin_decimals = 24`, `decimals = 18` (decimal diff = 6, threshold = 1,000,000 units).
2. Call `ft_transfer_call` with `amount = 500_000` and `fee = 0` targeting the NEAR bridge.
3. `init_transfer` passes the `fee < amount` check (0 < 500,000 ✓).
4. `init_transfer_internal` burns 500,000 units and returns `U128(0)` — tokens consumed.
5. Relayer calls `sign_transfer` for this transfer.
6. `normalize_amount(500_000, {24, 18})` = `500_000 / 10^6` = `0`.
7. `require!(0 > 0, ...)` panics — `sign_transfer` always fails.
8. No cancel/refund path exists; 500,000 units are permanently frozen.

    /// Uses floor division — any sub-unit remainder ("dust") is truncated and not transferred
    /// to the destination chain. When fee > 0, dust is absorbed into the fee via `claim_fee`.
    /// When fee = 0, dust stays locked/burned. See SECURITY.md for details.
    fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
        let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
        amount / (10_u128.pow(diff_decimals))
    }
