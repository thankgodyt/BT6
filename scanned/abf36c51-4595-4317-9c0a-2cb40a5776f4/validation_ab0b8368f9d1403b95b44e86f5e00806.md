### Title
Transfer Permanently Frozen When `normalize_amount(amount - fee) == 0` Due to Missing Pre-validation — (`near/omni-bridge/src/lib.rs`)

### Summary

The NEAR Omni Bridge accepts outbound transfer messages at `init_transfer` time without verifying that the net amount (after fee deduction) survives decimal normalization to the destination chain. When `sign_transfer` is later called, it computes `normalize_amount(amount_without_fee())` and panics if the result is zero. Because the fee can only be increased (never decreased) and there is no cancel path, the transfer is permanently deadlocked: it cannot be signed, and the user's locked tokens cannot be recovered.

### Finding Description

**Root cause — missing pre-validation in `init_transfer`**

`init_transfer` enforces only one amount constraint: [1](#0-0) 

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```

It does **not** verify that `normalize_amount(amount - fee, decimals) > 0`. Tokens are immediately locked (the NEP-141 `ft_on_transfer` callback returns `U128(0)`, keeping all tokens in the bridge).

**Normalization uses floor division** [2](#0-1) 

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

For a token with `origin_decimals = 18` and `decimals = 6` (a common ERC-20 bridged to a 6-decimal chain), `diff_decimals = 12`. Any `amount - fee < 10^12` normalizes to 0.

**`sign_transfer` panics and cannot proceed** [3](#0-2) 

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

Every call to `sign_transfer` for this transfer reverts. The transfer message stays in `pending_transfers` indefinitely.

**Fee update cannot rescue the transfer**

The fee update path rejects any decrease in the token fee (integration tests confirm `ERR_INVALID_FEE` on a lower fee): [4](#0-3) 

Increasing the fee makes `amount_without_fee()` even smaller, worsening the situation. There is no cancel or refund path exposed to the user.

**`amount_without_fee` implementation** [5](#0-4) 

```rust
pub fn amount_without_fee(&self) -> Option<u128> {
    self.amount.0.checked_sub(self.fee.fee.0)
}
```

### Impact Explanation

A user who initiates an outbound transfer where `amount - fee < 10^(origin_decimals - dest_decimals)` will have their tokens permanently locked in the bridge with no recovery mechanism. This constitutes **permanent freezing of bridged funds** — a critical impact under the allowed scope.

### Likelihood Explanation

Any unprivileged bridge user can trigger this by calling `ft_transfer_call` with an `InitTransferMsg` whose net amount is below the normalization threshold. For tokens with large decimal differences (e.g., 18 → 6), the threshold is `10^12` base units, which is a realistic transfer size (e.g., 0.000001 of an 18-decimal token). No special privileges or coordination are required.

### Recommendation

Add a normalization check inside `init_transfer_internal` (or at the end of `init_transfer`) before accepting the transfer:

```rust
let token_address = self.get_token_address(
    transfer_message.get_destination_chain(),
    self.get_token_id(&transfer_message.token),
).near_expect(BridgeError::FailedToGetTokenAddress);

let decimals = self.token_decimals
    .get(&token_address)
    .near_expect(BridgeError::TokenDecimalsNotFound);

let normalized = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

This mirrors the check already present in `sign_transfer` and ensures the transfer is rejected at initiation time (with a full token refund) rather than silently accepted and permanently frozen.

### Proof of Concept

1. Register a token with `origin_decimals = 18`, `decimals = 6` (diff = 12).
2. Call `ft_transfer_call` with `amount = 10^12 - 1` (e.g., 999,999,999,999) and `fee = 0`.
3. `init_transfer` accepts the message (`fee < amount` ✓). Tokens are locked.
4. Relayer calls `sign_transfer` for this transfer ID.
5. `normalize_amount(999_999_999_999, {origin: 18, dest: 6}) = 0`.
6. `require!(0 > 0, ...)` panics → transaction reverts.
7. Transfer remains in `pending_transfers`. Tokens remain locked. No cancel path exists.
8. Attempting to update the fee to a lower value is rejected with `ERR_INVALID_FEE`.
9. Funds are permanently frozen.
