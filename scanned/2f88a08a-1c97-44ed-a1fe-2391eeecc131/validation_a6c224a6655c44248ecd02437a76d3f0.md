### Title
Solana `bridge_token_factory` pause flag is set but never enforced in any user instruction — complete pause bypass - (File: `solana/programs/bridge_token_factory/src/instructions/admin/pause.rs`)

### Summary
The Solana `bridge_token_factory` program stores a `paused: u8` field in its `Config` account and exposes an admin `pause` instruction that sets it to `ALL_PAUSED`. However, none of the user-facing instructions (`finalize_transfer`, `finalize_transfer_sol`, `init_transfer`, `init_transfer_sol`, `deploy_token`) ever read or check `config.paused`. The pause mechanism is therefore completely inert: an admin cannot stop bridge operations on Solana even in an emergency.

### Finding Description

The `Config` account declares a `paused` field: [1](#0-0) 

The admin `pause` instruction writes `ALL_PAUSED` to it: [2](#0-1) 

A `grep` across all user instruction files (`user/finalize_transfer.rs`, `user/finalize_transfer_sol.rs`, `user/init_transfer.rs`, `user/init_transfer_sol.rs`, `user/deploy_token.rs`, `user/log_metadata.rs`) returns **zero matches** for `paused`, `pause`, or `ALL_PAUSED`. The flag is written by the admin path and read by nobody.



The pattern mirrors the reported vulnerability exactly: the flag is checked only in the admin assignment path (the `pause` instruction itself) but is absent from every execution path that matters (`finalize_transfer`, `init_transfer`).

### Impact Explanation

When an operator calls `pause` to halt the Solana bridge in response to an active exploit or critical bug, every user-facing instruction continues to execute without restriction. Specifically:

- `finalize_transfer` / `finalize_transfer_sol` can still mint bridge tokens to arbitrary recipients.
- `init_transfer` / `init_transfer_sol` can still lock/burn user tokens and emit transfer events that the NEAR hub will act on.

The emergency circuit breaker provides zero protection. An attacker exploiting a concurrent vulnerability can continue draining funds through the Solana leg of the bridge even after the admin has "paused" it, because the pause state is never consulted.

### Likelihood Explanation

The pause mechanism exists precisely for emergency use. Any scenario that motivates an admin to call `pause` (active exploit, MPC key compromise, critical bug discovery) is also a scenario where the bypass is directly harmful. The attacker entry path requires no special privilege — any user can call `finalize_transfer` or `init_transfer` at any time, including after a pause.

### Recommendation

Add a pause check at the start of every user instruction handler. For example, in each `process` method:

```rust
require!(
    self.config.paused == 0,
    ErrorCode::ProgramPaused
);
```

Or introduce a reusable constraint on the `Config` account in each `#[derive(Accounts)]` struct:

```rust
#[account(
    seeds = [CONFIG_SEED],
    bump = config.bumps.config,
    constraint = config.paused == 0 @ ErrorCode::ProgramPaused,
)]
pub config: Box<Account<'info, Config>>,
```

This mirrors how the EVM `OmniBridge.sol` applies `whenNotPaused(PAUSED_FIN_TRANSFER)` and `whenNotPaused(PAUSED_INIT_TRANSFER)` to the corresponding entry points.

### Proof of Concept

1. Admin calls `pause` → `config.paused` is set to `ALL_PAUSED` (e.g., `0xFF`).
2. Attacker (any user) submits a valid Wormhole VAA and calls `finalize_transfer`.
3. The `finalize_transfer` handler loads `config` only to read `max_used_nonce`, `derived_near_bridge_address`, and bump seeds — it never reads `config.paused`.
4. The instruction executes successfully, minting tokens to the attacker's recipient address despite the bridge being "paused." [3](#0-2) [4](#0-3)
