### Title
Missing Registered-Token Validation in `initTransfer` Allows Permanent Freezing of User Funds - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

### Summary
The EVM `OmniBridge.initTransfer` function accepts any arbitrary ERC20 token address without verifying that the token is registered in the bridge's `ethToNearToken` mapping. When a user submits an unregistered token, the EVM contract locks the tokens and emits an `InitTransfer` event, but the NEAR side panics with `TokenDecimalsNotFound` when a relayer attempts to finalize the transfer. Because there is no cross-chain refund path and no EVM-side rescue mechanism for arbitrary locked tokens, the funds are permanently frozen.

### Finding Description
`initTransfer` in `OmniBridge.sol` routes token handling through three branches — custom minter, bridge token (burn), and a catch-all `else` that simply calls `safeTransferFrom` into the contract for any other ERC20:

```solidity
} else {
    IERC20(tokenAddress).safeTransferFrom(
        msg.sender,
        address(this),
        amount
    );
}
``` [1](#0-0) 

There is no guard of the form `require(bytes(ethToNearToken[tokenAddress]).length > 0)` before this path. The `ethToNearToken` mapping is only populated for tokens registered via `deployToken` or `addCustomToken`. [2](#0-1) 

After locking, the function unconditionally emits `InitTransfer`: [3](#0-2) 

On the NEAR side, `fin_transfer_callback` immediately looks up the token in `token_decimals` and panics if it is absent:

```rust
let decimals = self
    .token_decimals
    .get(&init_transfer.token)
    .near_expect(BridgeError::TokenDecimalsNotFound);
``` [4](#0-3) 

The NEAR transaction reverts, but the EVM state is already committed. There is no cross-chain refund signal and no admin rescue function for arbitrary locked ERC20 balances in `OmniBridge.sol`, so the tokens are permanently frozen.

The same root cause exists in the Starknet contract: `init_transfer` in `starknet/src/omni_bridge.cairo` also accepts any `token_address` without checking `starknet_to_near_token`: [5](#0-4) 

The `removeCustomToken` admin function compounds the risk: it clears `isBridgeToken` and `ethToNearToken` for a token, but `initTransfer` will still accept it via the catch-all `else` branch, locking tokens that can no longer be finalized on NEAR. [6](#0-5) 

### Impact Explanation
Any user who calls `initTransfer` with an ERC20 token that is not registered in the bridge (either never registered, or deprecated via `removeCustomToken` without a corresponding NEAR-side removal) will have their tokens permanently locked in the EVM bridge contract with no recovery path. This constitutes permanent freezing of bridged funds, which is within the critical impact scope.

### Likelihood Explanation
The likelihood is medium-high. The catch-all `else` branch silently accepts any ERC20 without emitting a warning or reverting. A user who holds a token that was previously supported and then deprecated (via `removeCustomToken`) would have no on-chain signal that the transfer will fail on NEAR. The `removeCustomToken` admin path is a realistic operational event (token migration, deprecation), making this scenario plausible without any attacker involvement beyond a normal bridge user.

### Recommendation
Add a registration check at the top of `initTransfer` for non-native, non-bridge-token paths:

```solidity
function initTransfer(
    address tokenAddress,
    uint128 amount,
    uint128 fee,
    uint128 nativeFee,
    string calldata recipient,
    string calldata message
) external payable whenNotPaused(PAUSED_INIT_TRANSFER) {
+   if (tokenAddress != address(0) &&
+       !isBridgeToken[tokenAddress] &&
+       customMinters[tokenAddress] == address(0)) {
+       require(
+           bytes(ethToNearToken[tokenAddress]).length > 0,
+           "ERR_TOKEN_NOT_REGISTERED"
+       );
+   }
    ...
}
```

Apply the equivalent guard in `starknet/src/omni_bridge.cairo` `init_transfer` by asserting `self.starknet_to_near_token.read(token_address).len() > 0` before processing non-bridge tokens.

### Proof of Concept
1. Deploy any ERC20 token `FakeToken` that is not registered in `OmniBridge` (i.e., `ethToNearToken[FakeToken] == ""`).
2. Approve `OmniBridge` to spend `1000 FakeToken`.
3. Call `OmniBridge.initTransfer(FakeToken, 1000, 0, 0, "victim.near", "")` with `msg.value >= nativeFee`.
4. The contract executes `safeTransferFrom(msg.sender, address(this), 1000)` — tokens are locked — and emits `InitTransfer`.
5. A relayer submits the proof to NEAR's `fin_transfer`. `fin_transfer_callback` calls `self.token_decimals.get(&init_transfer.token).near_expect(BridgeError::TokenDecimalsNotFound)` and panics.
6. The NEAR transaction reverts. The EVM transaction is already finalized. `FakeToken` balance of `OmniBridge` is permanently increased with no withdrawal path for the user.
