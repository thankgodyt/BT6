### Title
Missing Chain ID in `deployToken` Message Hash Enables Cross-Chain Signature Replay — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

### Summary
The `deployToken` function in `OmniBridge.sol` hashes the `MetadataPayload` without including `omniBridgeChainId`. Because the Omni Bridge is deployed on multiple EVM chains (Ethereum, Arbitrum, Base, Polygon, BNB), a valid NEAR-MPC-signed `deployToken` signature obtained for one chain can be replayed verbatim on every other EVM chain, deploying the token there without NEAR's explicit per-chain authorization.

### Finding Description
`finTransfer` correctly embeds `omniBridgeChainId` twice in its Borsh-encoded hash (for the token address and the recipient address): [1](#0-0) 

`deployToken`, however, hashes only `PayloadType.Metadata + token + name + symbol + decimals` — no chain ID anywhere: [2](#0-1) 

The Starknet contract has the same asymmetry. `fin_transfer` passes `omni_bridge_chain_id` into `to_borsh`: [3](#0-2) 

But `deploy_token` calls `payload.to_borsh()` with no chain argument: [4](#0-3) 

And `MetadataPayload::to_borsh` contains no chain ID field: [5](#0-4) 

The Solana `DeployTokenPayload::serialize_for_near` likewise omits any chain discriminator: [6](#0-5) 

### Impact Explanation
An attacker who observes a legitimate `deployToken` call on chain A (e.g., Ethereum) can immediately replay the identical `(signatureData, metadata)` tuple on chains B, C, D (Arbitrum, Base, Polygon, BNB). Each target chain's `OmniBridge.sol` will:

1. Recover the signer as `nearBridgeDerivedAddress` — the check passes because the hash is identical.
2. Deploy a `BridgeToken` proxy and register it in `isBridgeToken` / `nearToEthToken`.

Consequences:
- **Unauthorized token deployment**: The NEAR MPC authorized deployment on chain A only; the attacker causes deployment on every other EVM chain without any additional MPC authorization.
- **Permanent blocking of legitimate deployments**: Once `nearToEthToken[metadata.token]` is set on chain B, the guard `require(!isBridgeToken[nearToEthToken[metadata.token]], "ERR_TOKEN_EXIST")` permanently prevents the legitimate relayer from ever deploying that token on chain B through the normal flow.
- **Unauthorized NEAR-side registration**: The attacker can submit the chain-B `DeployToken` event as a proof to NEAR's `deploy_token` → `deploy_token_callback`, which checks only that the emitter matches the registered factory for that chain — a check that passes for any legitimately registered EVM spoke. [7](#0-6) 

This constitutes an unauthorized transaction (token deployer action) executed without per-chain MPC authorization, and a chain/domain separation flaw that corrupts the token registry state on both the EVM spoke and the NEAR hub.

### Likelihood Explanation
Exploitation requires only: (a) watching the mempool or on-chain events for a legitimate `deployToken` call on any one EVM chain, and (b) submitting the same calldata to the other chains. No funds, no special role, no private key — just a public RPC call. The Omni Bridge is live on at least five EVM networks simultaneously, making the replay surface wide.

### Recommendation
Include `omniBridgeChainId` in the Borsh-encoded payload that is hashed and signed for `deployToken`, mirroring the pattern already used in `finTransfer`:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
    bytes1(omniBridgeChainId),          // ← add this
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
```

Apply the same fix to `MetadataPayload::to_borsh` in `starknet/src/bridge_types.cairo` and `DeployTokenPayload::serialize_for_near` in the Solana program. The NEAR signing side (`sign_transfer` / MPC payload construction) must include the destination chain ID in the signed bytes correspondingly.

### Proof of Concept

1. Observe a legitimate `deployToken(sig, {token:"usdc.near", name:"USD Coin", symbol:"USDC", decimals:6})` transaction on Ethereum mainnet's `OmniBridge`.
2. Copy `sig` and the `metadata` struct verbatim.
3. Call `deployToken(sig, metadata)` on Arbitrum's `OmniBridge` — the `ECDSA.recover` check passes because the hash is chain-agnostic.
4. "usdc.near" is now deployed on Arbitrum without NEAR MPC authorization for Arbitrum.
5. Submit the Arbitrum `DeployToken` event proof to NEAR's `deploy_token`; NEAR's `deploy_token_callback` accepts it because Arbitrum's `OmniBridge` is a registered factory.
6. Any future attempt by the legitimate relayer to deploy "usdc.near" on Arbitrum reverts with `"ERR_TOKEN_EXIST"`. [8](#0-7)

        );

            revert InvalidSignature();
        }

    fn to_borsh(self: @MetadataPayload) -> ByteArray {
        let mut borsh_bytes: ByteArray = Default::default();
        borsh_bytes.append_byte(PayloadType::Metadata.into());
        borsh_bytes.append(@borsh::encode_byte_array(self.token));
        borsh_bytes.append(@borsh::encode_byte_array(self.name));
        borsh_bytes.append(@borsh::encode_byte_array(self.symbol));
        borsh_bytes.append_byte(*self.decimals);
        borsh_bytes
    }
