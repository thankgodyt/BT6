### Title
Tokens Permanently Stuck in Bridge When `swap_migrated_token` Promise Fails - (File: `near/omni-bridge/src/lib.rs`)

---

### Summary

In `ft_on_transfer`, the `SwapMigratedToken` branch detaches the `swap_migrated_token` promise and immediately returns `U128(0)` — meaning zero tokens are refunded to the sender regardless of whether the swap succeeds or fails. If the swap fails for any reason, the user's tokens are permanently locked in the bridge contract with no recovery path.

---

### Finding Description

The `ft_on_transfer` function in `near/omni-bridge/src/lib.rs` dispatches on the parsed message type. For the `SwapMigratedToken` variant, the implementation is: [1](#0-0) 

```rust
BridgeOnTransferMsg::SwapMigratedToken => {
    self.swap_migrated_token(sender_id, token_id, amount)
        .detach();
    PromiseOrPromiseIndexOrValue::Value(U128(0))
}
```

Under NEAR's NEP-141 standard, the value returned by `ft_on_transfer` is the number of tokens to **refund** to the sender. Returning `U128(0)` means the bridge keeps all tokens. The `.detach()` call schedules the `swap_migrated_token` promise but **discards its result** — the return value of `ft_on_transfer` is fixed at `U128(0)` before the promise even executes.

This breaks the zero-balance invariant that the bridge is designed to maintain: if `swap_migrated_token` fails (e.g., the token is absent from `migrated_tokens`, the target token transfer is rejected, or any cross-contract call in the chain panics), the user's tokens remain in the bridge contract permanently with no refund and no recovery mechanism.

Compare this to the other branches in the same function, which either return a live promise (so the callback controls the refund amount) or call synchronous logic that panics atomically on failure: [2](#0-1) 

All other branches (`InitTransfer`, `FastFinTransfer`, `UtxoFinTransfer`) propagate a `Promise` whose callback determines the refund. Only `SwapMigratedToken` detaches and hard-codes `U128(0)`.

---

### Impact Explanation

**Critical.** Any user who calls `ft_transfer_call` on a token contract with a `SwapMigratedToken` message, where the subsequent `swap_migrated_token` promise fails, permanently loses their tokens. The bridge contract holds the tokens with no admin-accessible sweep function visible in the audited scope. This is a direct, irreversible loss of bridged funds triggered by a normal user action.

---

### Likelihood Explanation

**Medium.** The `SwapMigratedToken` path is a migration utility, so it is exercised during token migration events. Any user who sends a token that is not yet (or no longer) in the `migrated_tokens` map, or whose target token account has no storage deposit, will trigger the failure silently. The attacker-controlled entry path is simply calling `ft_transfer_call` on any NEP-141 token with the `SwapMigratedToken` message — no special privileges required.

---

### Recommendation

Replace the detach-and-return-zero pattern with a callback that inspects the promise result and refunds the full amount on failure, mirroring the pattern used by `UtxoFinTransfer`:

```rust
BridgeOnTransferMsg::SwapMigratedToken => {
    self.swap_migrated_token(sender_id.clone(), token_id, amount)
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(SWAP_MIGRATED_TOKEN_CALLBACK_GAS)
                .swap_migrated_token_callback(sender_id, amount),
        )
        .into()
}
```

The callback should return `amount` on failure and `U128(0)` on success, ensuring the zero-balance invariant is maintained.

---

### Proof of Concept

1. Attacker (or any user) holds token `A` which is listed in `migrated_tokens` mapping as mapping to token `B`.
2. User calls `A.ft_transfer_call(bridge, amount, SwapMigratedToken_msg)`.
3. Bridge's `ft_on_transfer` is called; it calls `swap_migrated_token(...).detach()` and immediately returns `U128(0)`.
4. Token contract `A` sees return value `0` → keeps all `amount` tokens at the bridge address (no refund).
5. The detached `swap_migrated_token` promise executes and fails (e.g., bridge has no storage deposit on token `B`, or `B.ft_transfer` panics).
6. Failure is silently discarded. User's `amount` of token `A` is now held by the bridge with no recovery path. [1](#0-0)
