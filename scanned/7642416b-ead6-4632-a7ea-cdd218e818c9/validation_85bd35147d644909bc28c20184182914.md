### Title
Fee-on-Transfer Token Escrow Mis-Accounting in `initTransfer` — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

`OmniBridge.initTransfer` pulls a caller-specified `amount` from the user via `safeTransferFrom`, then unconditionally emits an `InitTransfer` event carrying that same `amount`. For fee-on-transfer ERC20 tokens the contract actually receives `amount − transfer_fee`, yet the event records the full `amount`. The NEAR side treats the event as the sole source of truth and mints or unlocks the full `amount` to the recipient, creating a permanent shortfall in the EVM escrow.

---

### Finding Description

In `OmniBridge.initTransfer`, the non-bridge, non-custom-minter branch executes:

```solidity
IERC20(tokenAddress).safeTransferFrom(
    msg.sender,
    address(this),
    amount          // ← requested amount, not verified received amount
);
```

Immediately after, without measuring the actual post-transfer balance, the function emits:

```solidity
emit BridgeTypes.InitTransfer(
    msg.sender,
    tokenAddress,
    currentOriginNonce,
    amount,          // ← same caller-supplied value, not actual received
    fee,
    nativeFee,
    recipient,
    message
);
```

The NEAR bridge contract's `fin_transfer_callback` reconstructs the transfer exclusively from the event:

```rust
amount: Self::denormalize_amount(init_transfer.amount.0, decimals).into(),
```

It then mints (for deployed tokens) or unlocks (for locked tokens) exactly that `amount` to the NEAR recipient. There is no cross-check against what the EVM contract actually holds.

The identical pattern exists on Starknet in `starknet/src/omni_bridge.cairo`:

```cairo
let success = IERC20Dispatcher { contract_address: token_address }
    .transfer_from(caller, get_contract_address(), amount.into());
// ...
Event::InitTransfer(InitTransfer { ..., amount, ... })
```

---

### Impact Explanation

Every transfer of a fee-on-transfer token through `initTransfer` causes the EVM escrow to hold `transfer_fee` fewer tokens than NEAR believes are locked. After N transfers the EVM escrow is short by `N × transfer_fee`. When legitimate users later bridge back from NEAR to EVM, `unlock_tokens` will eventually underflow (`ERR_INSUFFICIENT_LOCKED_TOKENS`) or the bridge will be unable to release funds, permanently freezing bridged assets. An attacker who controls a fee-on-transfer token registered with the bridge can exploit this deliberately to drain the escrow relative to NEAR's minted supply, effectively minting unbacked tokens on NEAR.

---

### Likelihood Explanation

Any ERC20 token with a transfer fee that is registered with the bridge (via `deployToken` or `bindToken`) triggers this path. USDT's fee mechanism is currently set to zero but is contractually activatable at any time by Tether. Other tokens (e.g. deflationary tokens, tokens with protocol fees) may have non-zero fees from deployment. No special privilege is required beyond initiating a normal `initTransfer` call.

---

### Recommendation

Measure the actual received amount using a balance-before / balance-after pattern and use that value in the emitted event:

```solidity
uint256 balanceBefore = IERC20(tokenAddress).balanceOf(address(this));
IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
uint256 actualReceived = IERC20(tokenAddress).balanceOf(address(this)) - balanceBefore;
require(actualReceived > 0, "ZeroReceived");
// use actualReceived in place of amount for the event and all downstream accounting
```

Apply the same fix to the Starknet `init_transfer`. Alternatively, explicitly disallow fee-on-transfer tokens at the registration layer and enforce this invariant in documentation and token-vetting processes.

---

### Proof of Concept

1. Deploy or identify a fee-on-transfer ERC20 (e.g. 1 % fee) registered with the bridge.
2. Call `OmniBridge.initTransfer(tokenAddress, 1_000_000, 0, 0, "alice.near", "")`.
3. `safeTransferFrom` moves 1 000 000 tokens from the caller; the bridge receives 990 000 (1 % fee taken by the token).
4. The `InitTransfer` event records `amount = 1_000_000`.
5. The NEAR relayer submits the event proof to `fin_transfer`; `fin_transfer_callback` reads `init_transfer.amount = 1_000_000` and mints / unlocks 1 000 000 tokens to `alice.near`.
6. The EVM escrow is now short by 10 000 tokens per transfer.
7. After 100 such transfers the escrow is short by 1 000 000 tokens; the next legitimate EVM withdrawal of that size will revert with `ERR_INSUFFICIENT_LOCKED_TOKENS`, permanently freezing those funds.
