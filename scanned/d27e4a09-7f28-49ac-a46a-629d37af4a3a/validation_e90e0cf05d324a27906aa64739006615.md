### Title
Trusted Relayer Can Substitute Arbitrary Token in Fast Transfer, Causing Recipient to Receive Wrong Asset — (File: `near/omni-bridge/src/lib.rs`)

---

### Summary

The `fast_fin_transfer` function accepts whatever token the relayer sends without verifying it matches the token in the original source-chain transfer. A malicious trusted relayer can substitute any registered token, causing the recipient to receive a different (potentially less valuable) asset than what was originally transferred.

---

### Finding Description

`fast_fin_transfer` is invoked via `ft_on_transfer` when a relayer fronts liquidity for a pending cross-chain transfer. The token being fronted is determined solely by `env::predecessor_account_id()` (the token contract that called `ft_on_transfer`), and is stored directly into the `FastTransfer` struct: [1](#0-0) 

The function resolves `origin_token` — the address of the relayer's token on the origin chain — and uses its decimals for an amount check: [2](#0-1) 

The `fast_fin_transfer_msg.transfer_id` carries only `origin_chain` and a nonce/UTXO kind — **no token information**: [3](#0-2) 

There is no lookup of the original source-chain transfer's token to compare against the relayer-supplied `token_id`. The `FastTransfer` struct is stored with whatever `token_id` the relayer chose: [4](#0-3) 

The amount check only validates that the relayer sent the correct quantity of *their chosen token* (using that token's decimals), not that the token itself is correct: [5](#0-4) 

---

### Impact Explanation

A malicious trusted relayer observing an original transfer of Token A (e.g., USDC) from a source chain to NEAR can call `ft_transfer_call` on Token B (e.g., a depegged stablecoin or a lower-value registered token) with the original transfer's ID. The bridge accepts Token B, stores `FastTransfer{token_id: Token B}`, and delivers Token B to the recipient. The recipient receives a different asset than what was originally transferred — a direct token substitution / escrow mis-accounting. If Token B is worth less than Token A, the recipient suffers a financial loss. The relayer fronts less value than required while the bridge records the fast transfer as satisfied.

---

### Likelihood Explanation

Exploitation requires the attacker to be a trusted relayer, a permissioned role managed by `Role::RelayerManager`. The audit scope explicitly includes "custom relayer" as a valid attacker. A relayer that is approved but turns malicious, or a relayer whose key is compromised, can execute this attack against any pending fast transfer they choose to front. [6](#0-5) 

---

### Recommendation

Inside `fast_fin_transfer`, after resolving `origin_token`, verify it matches the token recorded in the original source-chain transfer. Because the transfer ID alone carries no token information, one approach is to maintain a mapping from `UnifiedTransferId` to expected token address when the source-chain `InitTransfer` event is first observed (e.g., during `fin_transfer_callback`), and require the relayer's `origin_token` to match that expected address before accepting the fast transfer.

---

### Proof of Concept

1. User initiates a transfer of 1,000 USDC (Token A, 6 decimals) from Ethereum to NEAR. The normalized amount on-chain is `1_000_000` (6-decimal units).
2. Malicious trusted relayer calls `ft_transfer_call` on Token B (a depegged stablecoin, also 6 decimals, worth $0.80 each) with `msg = FastFinTransfer { transfer_id: {Eth, nonce}, amount: 1_000_000, fee: 0, recipient: Near(victim), ... }` and sends `1_000_000` units of Token B.
3. `fast_fin_transfer` resolves `origin_token` = Token B's Eth address, gets Token B's decimals (6), and the amount check passes: `denormalize(1_000_000, 6) == 1_000_000 == 1_000_000 + 0`. ✓
4. `FastTransfer { token_id: Token B, amount: 1_000_000, ... }` is stored and Token B is sent to the victim.
5. Victim receives 1,000 Token B (worth $800) instead of 1,000 USDC (worth $1,000) — a $200 loss.
6. The relayer fronted only $800 of value while the original transfer was worth $1,000.

    #[allow(clippy::needless_pass_by_value)]
    fn fast_fin_transfer(
        &mut self,
        token_id: AccountId,
        amount: U128,
        signer_id: AccountId,
        fast_fin_transfer_msg: FastFinTransferMsg,
    ) -> PromiseOrPromiseIndexOrValue<U128> {
        require!(self.is_trusted_relayer(&signer_id), "Relayer is not active");

        let origin_token = self
            .get_token_address(
                fast_fin_transfer_msg.transfer_id.origin_chain,
                token_id.clone(),
            )
            .near_expect(BridgeError::TokenNotFound);

        let decimals = self
            .token_decimals
            .get(&origin_token)
            .near_expect(BridgeError::TokenDecimalsNotFound);

        let denormalized_amount =
            Self::denormalize_amount(fast_fin_transfer_msg.amount.0, decimals);
        let denormalized_fee = Self::denormalize_fee(&fast_fin_transfer_msg.fee, decimals);
        require!(
            denormalized_amount == amount.0 + denormalized_fee.fee.0,
            BridgeError::InvalidFastTransferAmount.as_ref()
        );

        if self.is_unified_transfer_finalised(&fast_fin_transfer_msg.transfer_id) {
            env::panic_str(BridgeError::TransferAlreadyFinalised.to_string().as_str());
        }

        let fast_transfer = FastTransfer {
            token_id: token_id.clone(),
            recipient: fast_fin_transfer_msg.recipient.clone(),
            amount: U128(denormalized_amount),
            fee: denormalized_fee,
            transfer_id: fast_fin_transfer_msg.transfer_id,
            msg: fast_fin_transfer_msg.msg,
        };
