### Title
`finish_withdraw_v2` Bypasses Pause Check, Allowing Outbound Transfers When Bridge Is Paused — (`near/omni-bridge/src/lib.rs`)

### Summary

The NEAR bridge contract exposes a public function `finish_withdraw_v2` that creates outbound transfer messages to Ethereum without checking the bridge's pause state. Every other user-facing transfer-initiation path in the contract is guarded by a `#[pause]` attribute, but this legacy withdrawal path is not. When the bridge is paused in response to a security incident, users can still burn their NEAR-side tokens and create pending transfer records, which the admin has no power to prevent.

### Finding Description

The NEAR bridge contract uses the `near-plugins` `Pausable` trait and applies `#[pause(except(roles(Role::DAO)))]` to all critical entry points:

- `ft_on_transfer` (covers `InitTransfer`, `FastFinTransfer`, `UtxoFinTransfer`) [1](#0-0) 
- `sign_transfer` [2](#0-1) 
- `fin_transfer` [3](#0-2) 
- `claim_fee` [4](#0-3) 

However, `finish_withdraw_v2` carries **no pause attribute at all**:

```rust
pub fn finish_withdraw_v2(
    &mut self,
    #[serializer(borsh)] sender_id: &AccountId,
    #[serializer(borsh)] amount: u128,
    #[serializer(borsh)] recipient: String,
) {
    let token_id = env::predecessor_account_id();
    require!(self.is_deployed_token(&token_id),);
    ...
    env::log_str(&OmniBridgeEvent::InitTransferEvent { transfer_message }.to_log_string());
}
``` [5](#0-4) 

The function is callable by any account that `is_deployed_token` returns `true` for — i.e., any legacy bridge token contract registered with the bridge. It increments the origin nonce, allocates a destination nonce, stores a `TransferMessage` in `pending_transfers`, and emits an `InitTransferEvent` — all without consulting the pause flag.

### Impact Explanation

When the bridge is paused (e.g., because a vulnerability is discovered in `finTransfer` or the MPC signer is compromised), the admin's intent is to halt all new transfer activity. `finish_withdraw_v2` defeats this intent:

1. A user calls the legacy bridge token's `withdraw` function, which burns the user's NEAR-side tokens and calls `finish_withdraw_v2` on the bridge.
2. The bridge records a pending outbound transfer — tokens are already burned.
3. `sign_transfer` is paused, so no relayer can sign the transfer while the pause is active.
4. The user's tokens are burned with no corresponding release on Ethereum.

If the bridge is later unpaused the transfer can be completed. But if the bridge is permanently shut down (the realistic outcome of a severe security incident), the burned tokens are irrecoverable — a permanent freeze of bridged funds. Additionally, the storage cost for the pending transfer record is charged to `env::current_account_id()` (the bridge contract itself), not the user, enabling repeated calls to exhaust bridge storage.

### Likelihood Explanation

The entry path requires only that a deployed legacy bridge token exists (which it does — the bridge maintains a `deployed_tokens` set for backward compatibility) and that the bridge is paused. Pausing is a routine emergency response. Any user holding legacy bridge tokens can trigger this path without any special role or permission.

### Recommendation

Add the same pause guard used on every other transfer-initiation path:

```rust
#[pause(except(roles(Role::DAO)))]
pub fn finish_withdraw_v2(...) { ... }
```

Additionally, charge storage costs to the `sender_id` rather than `env::current_account_id()` to prevent storage-exhaustion abuse.

### Proof of Concept

1. Admin pauses the bridge (e.g., via `PauseManager` role) in response to a security incident.
2. User holds tokens in a legacy deployed bridge token (e.g., `eth-<token>.factory.bridge.near`).
3. User calls the legacy token's `withdraw(amount, recipient_eth_address)`.
4. The legacy token burns the user's balance and calls `finish_withdraw_v2` on the bridge with the user's `sender_id`, `amount`, and `recipient`.
5. `finish_withdraw_v2` executes without reverting — no pause check — and stores a `TransferMessage` in `pending_transfers`, emitting `InitTransferEvent`.
6. The user's NEAR-side tokens are now burned. `sign_transfer` is paused, so no relayer can complete the transfer.
7. If the bridge is permanently shut down, the user's funds are permanently frozen.

The contrast with the guarded path is direct: `ft_on_transfer` at line 252 would have reverted at step 3 for any non-DAO caller, but `finish_withdraw_v2` at line 1315 does not. [6](#0-5)

```rust
    #[allow(clippy::needless_pass_by_value)]
    pub fn finish_withdraw_v2(
        &mut self,
        #[serializer(borsh)] sender_id: &AccountId,
        #[serializer(borsh)] amount: u128,
        #[serializer(borsh)] recipient: String,
    ) {
        let token_id = env::predecessor_account_id();
        require!(self.is_deployed_token(&token_id),);

        self.current_origin_nonce += 1;
        let destination_nonce = self.get_next_destination_nonce(ChainKind::Eth);

        let transfer_message = TransferMessage {
            origin_nonce: self.current_origin_nonce,
            token: OmniAddress::Near(token_id),
            amount: U128(amount),
            recipient: OmniAddress::Eth(
                H160::from_str(&recipient).near_expect(BridgeError::InvalidRecipientAddress),
            ),
            fee: Fee {
                fee: U128(0),
                native_fee: U128(0),
            },
            sender: OmniAddress::Near(sender_id.clone()),
            msg: String::new(),
            destination_nonce,
            origin_transfer_id: None,
        };

        let required_storage_balance =
            self.add_transfer_message(transfer_message.clone(), sender_id.clone());

        self.update_storage_balance(
            env::current_account_id(),
            required_storage_balance,
            NearToken::from_yoctonear(0),
        );

        env::log_str(&OmniBridgeEvent::InitTransferEvent { transfer_message }.to_log_string());
    }
