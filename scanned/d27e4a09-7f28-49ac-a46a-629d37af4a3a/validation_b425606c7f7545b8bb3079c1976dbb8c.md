### Title
Missing Chain Identifier in `deployToken` Signature Hash Enables Cross-Chain Replay — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

The `deployToken` function in `OmniBridge.sol` verifies a NEAR MPC-produced ECDSA signature over a Borsh-encoded message that contains **no chain identifier** — neither the EVM `block.chainid` nor the bridge-specific `omniBridgeChainId`. Because the same `OmniBridge` contract is deployed on multiple EVM chains (Ethereum, Arbitrum, Base, etc.), a valid `deployToken` signature obtained for one chain can be replayed verbatim on any other chain, causing unauthorized bridge-token deployment on unintended chains and permanently blocking legitimate future deployment of that token on the target chain.

---

### Finding Description

In `OmniBridge.sol::deployToken()`, the message that is hashed and then signature-checked is constructed as:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
bytes32 hashed = keccak256(borshEncoded);

if (ECDSA.recover(hashed, signatureData) != nearBridgeDerivedAddress) {
    revert InvalidSignature();
}
``` [1](#0-0) 

The five fields encoded are: payload type tag, NEAR token ID string, name, symbol, and decimals. **No chain identifier of any kind is included.** The hash is therefore identical for the same token metadata regardless of which EVM chain the contract is running on.

By contrast, the `finTransfer` function in the same contract correctly embeds `omniBridgeChainId` twice in its signed payload (once for the token address field and once for the recipient address field):

```solidity
bytes1(omniBridgeChainId),
Borsh.encodeAddress(payload.tokenAddress),
Borsh.encodeUint128(payload.amount),
bytes1(omniBridgeChainId),
Borsh.encodeAddress(payload.recipient),
``` [2](#0-1) 

This inconsistency shows the developers understood the need for chain binding in transfer messages but omitted it from the token-deployment message.

The `omniBridgeChainId` is a `uint8` bridge-specific chain identifier set at initialization time: [3](#0-2) 

It is distinct per chain (e.g., Ethereum vs. Arbitrum vs. Base), but it is never included in the `deployToken` hash.

---

### Impact Explanation

An attacker who observes a successful `deployToken(signatureData, metadata)` call on chain A can immediately replay the identical calldata on chain B:

1. The `ECDSA.recover` check passes because the hash is chain-agnostic and the signature is still valid.
2. A new `BridgeToken` proxy is deployed on chain B and registered in `nearToEthToken[metadata.token]` and `isBridgeToken`.
3. The guard `require(!isBridgeToken[nearToEthToken[metadata.token]], "ERR_TOKEN_EXIST")` now permanently blocks any future legitimate `deployToken` call for that NEAR token on chain B. [4](#0-3) 

Consequences:
- **Unauthorized deployer action**: the attacker executes a privileged bridge-token deployment without NEAR's authorization for that chain.
- **Permanent DoS of token bridging on the target chain**: once the replay-deployed token occupies the registry slot, NEAR can never legitimately deploy or bind that token on chain B, effectively freezing the bridging capability for that token on that chain.
- This is a concrete **chain/domain separation flaw** and **cross-chain replay** of a signed bridge message, both of which are explicitly in scope.

---

### Likelihood Explanation

- All `deployToken` calls are public on-chain; the calldata (signature + metadata) is trivially observable.
- The bridge is already deployed on multiple EVM chains sharing the same NEAR MPC signer (`nearBridgeDerivedAddress`).
- No special access, leaked keys, or admin compromise is required — any unprivileged observer can replay the transaction.
- The attack is a single transaction with no preconditions beyond observing a legitimate `deployToken` on any one chain.

---

### Recommendation

Include a chain-binding field in the `deployToken` signed payload, consistent with how `finTransfer` already does it. The simplest fix is to prepend `omniBridgeChainId` into the Borsh-encoded message before hashing:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
+   bytes1(omniBridgeChainId),          // chain binding
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
```

The corresponding NEAR-side signing logic must be updated to include the target chain ID when producing the metadata signature, mirroring the existing pattern used for transfer messages.

---

### Proof of Concept

**Setup**: `OmniBridge` is deployed on Ethereum (`omniBridgeChainId = 1`) and Arbitrum (`omniBridgeChainId = 2`). NEAR signs a `deployToken` payload for token `"usdc.near"` on Ethereum.

**Attack**:
1. Observe the Ethereum `deployToken` transaction; extract `signatureData` and `metadata` from calldata.
2. Call `OmniBridge.deployToken(signatureData, metadata)` on the Arbitrum deployment.
3. `keccak256(borshEncoded)` is identical on both chains (no chain ID in the hash).
4. `ECDSA.recover(hashed, signatureData) == nearBridgeDerivedAddress` → passes.
5. `BridgeToken` for `"usdc.near"` is deployed on Arbitrum and registered in `nearToEthToken["usdc.near"]`.
6. Any subsequent legitimate `deployToken` call for `"usdc.near"` on Arbitrum reverts with `"ERR_TOKEN_EXIST"`. [5](#0-4)

        bytes calldata signatureData,
        BridgeTypes.MetadataPayload calldata metadata
    ) external payable whenNotPaused(PAUSED_DEPLOY_TOKEN) returns (address) {
        if (tokenImplementationAddress == address(0)) {
            revert TokenImplementationNotSet();
        }
        bytes memory borshEncoded = bytes.concat(
            bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
            Borsh.encodeString(metadata.token),
            Borsh.encodeString(metadata.name),
            Borsh.encodeString(metadata.symbol),
            bytes1(metadata.decimals)
        );
        bytes32 hashed = keccak256(borshEncoded);

        if (ECDSA.recover(hashed, signatureData) != nearBridgeDerivedAddress) {
            revert InvalidSignature();
        }

        require(
            !isBridgeToken[nearToEthToken[metadata.token]],
            "ERR_TOKEN_EXIST"
        );
        uint8 decimals = _normalizeDecimals(metadata.decimals);

        // slither-disable-next-line reentrancy-no-eth

            new ERC1967Proxy(

                    BridgeToken.initialize.selector,
                    metadata.name,
                    metadata.symbol,
                    decimals
                )
            )
        );

        deployTokenExtension(
            metadata.token,
            bridgeTokenProxy,
            decimals,

        );

            metadata.decimals

        ethToNearToken[address(bridgeTokenProxy)] = metadata.token;

    }
