### Title
Non-Atomic Burn-Then-Mint in `swap_migrated_token` Causes Permanent Token Loss on Mint Failure — (`near/omni-bridge/src/lib.rs`)

---

### Summary

`swap_migrated_token` uses `burn.and(mint)` — a NEAR parallel joint promise — with no callback and no rollback. If the `mint` call panics (e.g., recipient not registered on the new token), the `burn` has already executed and the user's tokens are permanently destroyed.

---

### Finding Description

The function `swap_migrated_token` is invoked from `ft_on_transfer` when a user sends old tokens to the bridge with the `SwapMigratedToken` message: [1](#0-0) 

The function itself: [2](#0-1) 

`burn.and(mint)` in NEAR SDK schedules **both sub-promises as independent parallel receipts**. There is no causal dependency: if `mint` panics, `burn` is not rolled back. The promise is also `.detach()`ed, so `ft_on_transfer` immediately returns `U128(0)` — signaling to the old token contract that all transferred tokens are consumed. There is no callback to verify the mint outcome.

The `mint` function on the new token calls `internal_deposit(&account_id, ...)`: [3](#0-2) 

NEAR's `FungibleToken::internal_deposit` panics if `account_id` has no storage registration. `migrate_deployed_token` only registers the bridge contract itself on the new token — not individual users: [4](#0-3) 

Any user who has not previously registered storage on the new token contract will trigger a panic in `mint`, while the `burn` receipt executes successfully and destroys the old tokens.

---

### Impact Explanation

Permanent, irreversible loss of user funds. Old tokens are burned from the bridge's balance on the old token contract. New tokens are never minted. There is no recovery path: the `migrated_tokens` mapping still maps old→new, so a retry attempt would fail because the bridge no longer holds the old tokens (they were already burned). The user receives nothing.

---

### Likelihood Explanation

Any user who calls `ft_transfer_call` on the old token with `SwapMigratedToken` before registering storage on the new token contract will lose their funds. This is a realistic scenario: the new token is a freshly deployed contract, and users are expected to migrate from the old one — most will not have pre-existing storage registrations on the new token. No attacker action is required; the user's own migration attempt is sufficient to trigger the loss.

---

### Recommendation

Replace the fire-and-forget `burn.and(mint)` pattern with a sequential, callback-guarded flow:

1. Call `burn` on the old token first.
2. In the burn callback, verify success.
3. Only if burn succeeded, call `mint` on the new token.
4. In the mint callback, verify success; if mint failed, re-mint the old tokens to the user (or store a claimable balance).

Alternatively, reverse the order: mint first, then burn only if mint succeeded. This is safer because a failed mint leaves the old tokens intact in the bridge's custody, and the bridge can return them via the `ft_on_transfer` refund mechanism (returning `amount` instead of `0`).

Additionally, ensure storage registration for the recipient on the new token is performed (and confirmed) before or during the swap, similar to how `fin_transfer` handles `storage_deposit_actions`.

---

### Proof of Concept

**Localnet reproduction:**

1. Deploy old token (`old.token`) and new token (`new.token`), both `OmniToken` contracts.
2. Deploy bridge, call `migrate_deployed_token(Eth, old.token, new.token)`.
3. Create a user account that has storage on `old.token` but **not** on `new.token`.
4. Mint 1000 old tokens to the user.
5. User calls `old.token.ft_transfer_call(bridge, 1000, "SwapMigratedToken")`.
6. Observe: `old.token` balance of bridge is burned (supply decreases by 1000). `new.token` mint panics (user not registered). `new.token` supply unchanged.
7. Assert: user holds 0 old tokens, 0 new tokens. 1000 tokens permanently destroyed. [5](#0-4)

    fn swap_migrated_token(
        &mut self,
        sender_id: AccountId,
        old_token: AccountId,
        amount: U128,
    ) -> Promise {
        let new_token = self
            .migrated_tokens
            .get(&old_token)
            .near_expect(BridgeError::TokenNotMigrated);

        let burn = ext_token::ext(old_token).burn(amount);
        let mint = ext_token::ext(new_token).mint(sender_id, amount, None);

        burn.and(mint)
    }
