### Title
Detached `send_tokens` to Relayer with No Failure Callback Permanently Locks Relayer Funds - (`near/omni-bridge/src/lib.rs`)

### Summary
In `process_fin_transfer_to_other_chain` and `utxo_fin_transfer_fast`, the bridge irrevocably updates fast-transfer state (marking it finalised or removing it) **before** the token repayment to the relayer is confirmed, and the repayment promise is fired with `.detach()` — meaning no callback ever runs on failure. If the `send_tokens` call fails, the relayer's fronted funds are permanently locked inside the bridge with no recovery path.

### Finding Description

Two functions share the same pattern:

**`process_fin_transfer_to_other_chain`** (called from `fin_transfer_callback`):

```rust
if let Some(relayer) = recipient {
    self.send_tokens(token, relayer, amount, "")
        .detach();                                    // ← no failure callback
    self.mark_fast_transfer_as_finalised(&fast_transfer.id()); // ← state committed
}
```

The fast transfer is marked finalised immediately after the detached promise is scheduled. If `send_tokens` fails (e.g., `ft_transfer` panics because the relayer has no storage for the token), the state is already committed and the relayer can never be repaid.

**`utxo_fin_transfer_fast`** (called from `utxo_fin_transfer`):

```rust
let amount = if fast_transfer.get_destination_chain() == ChainKind::Near {
    self.remove_fast_transfer(&fast_transfer.id());   // ← state committed
    fast_transfer.amount
} else {
    self.mark_fast_transfer_as_finalised(&fast_transfer.id()); // ← state committed
    ...
};

self.send_tokens(fast_transfer.token_id.clone(), fast_transfer_status.relayer, amount, "")
    .detach();   // ← no failure callback
```

The developers themselves acknowledge this gap with a `// TODO: check how to deal with failed send_tokens` comment at the call site in `utxo_fin_transfer`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Impact Explanation

A trusted relayer who executes a fast transfer fronts the recipient's tokens out of their own balance. When the canonical proof later arrives, the bridge is supposed to repay the relayer via `send_tokens`. If that `ft_transfer` fails (e.g., the relayer's account lacks storage registration for the specific token, or the token contract is temporarily paused), the fast-transfer record is already removed or marked finalised — there is no retry mechanism and no refund path. The relayer's bridged tokens are permanently frozen inside the bridge contract.

This matches the allowed impact: **permanent freezing of bridged funds**.

### Likelihood Explanation

`send_tokens` with an empty `msg` resolves to `ft_transfer`, which requires the recipient to have a storage deposit for the token. A trusted relayer operating across many tokens may not have pre-registered storage for every token they relay. Additionally, any transient panic in the token contract (e.g., a paused token) causes the same outcome. The developer-acknowledged TODO comment confirms this is a known unresolved risk. [4](#0-3) 

### Recommendation

Replace `.detach()` with a proper callback that handles failure. On failure, the fast-transfer record should be restored (un-finalised / re-inserted) so the relayer repayment can be retried. This mirrors the fix recommended in M-09: handle the reply on both success **and** failure rather than only on success.

```rust
self.send_tokens(token, relayer, amount, "")
    .then(
        Self::ext(env::current_account_id())
            .with_static_gas(REPAY_RELAYER_CALLBACK_GAS)
            .repay_relayer_callback(&fast_transfer_id, relayer, amount),
    );
// In callback: if failed, restore fast_transfer state so it can be retried
```

### Proof of Concept

1. Relayer calls `ft_transfer_call` on the bridge token, triggering `fast_fin_transfer` with a NEAR recipient.
2. Bridge records the fast transfer and sends tokens to the recipient.
3. Canonical proof arrives; trusted relayer calls `fin_transfer` → `fin_transfer_callback` → `process_fin_transfer_to_other_chain`.
4. Bridge calls `send_tokens(token, relayer, amount, "").detach()` and immediately calls `mark_fast_transfer_as_finalised`.
5. The `ft_transfer` to the relayer fails (relayer has no storage for this token).
6. No callback fires. Fast transfer is permanently finalised. Relayer's fronted tokens are locked in the bridge with no recovery path. [5](#0-4) [6](#0-5)

    fn utxo_fin_transfer_fast(
        &mut self,
        fast_transfer: FastTransfer,
        fast_transfer_status: FastTransferStatus,
        utxo_fin_transfer_msg: UtxoFinTransferMsg,
    ) -> PromiseOrPromiseIndexOrValue<U128> {
        require!(
            !fast_transfer_status.finalised,
            BridgeError::FastTransferAlreadyFinalised.as_ref()
        );

        let amount = if fast_transfer.get_destination_chain() == ChainKind::Near {
            self.remove_fast_transfer(&fast_transfer.id());
            fast_transfer.amount
        } else {
            self.mark_fast_transfer_as_finalised(&fast_transfer.id());
            // With transfers to other chain the fee will be claimed after finalization on the destination chain
            U128(
                fast_transfer
                    .amount_without_fee()
                    .near_expect(BridgeError::InvalidFee),
            )
        };

        self.send_tokens(
            fast_transfer.token_id.clone(),
            fast_transfer_status.relayer,
            amount,
            "",
        )
        .detach();
