### Title
Unchecked Burn Result via `.detach()` Allows Silent Burn Failure and Cross-Chain Token Supply Inflation — (`File: near/omni-bridge/src/lib.rs`)

### Summary

`burn_tokens_if_needed` fires a cross-contract `burn` call with `.detach()`, meaning the promise result is never observed. If the burn fails for any reason (gas exhaustion at the tight 3 TGas budget, or any panic in the token contract), the bridge silently proceeds: the `InitTransferEvent` is emitted, the MPC signs the transfer, and the destination chain mints tokens — while the NEAR-side supply is never reduced.

### Finding Description

`burn_tokens_if_needed` is the NEAR analog of the ignored `transferFrom` return value in the Amp.sol report. In Solidity the call simply discards a `bool`; in NEAR the equivalent is `.detach()`, which schedules a promise but never awaits or inspects its outcome. [1](#0-0) 

This function is called in two critical paths:

**Path 1 — outbound transfer (`init_transfer_internal`)** [2](#0-1) 

The sequence is:
1. User calls `ft_transfer_call` on a deployed bridge token → tokens land at the bridge.
2. Bridge's `ft_on_transfer` → `init_transfer` → `init_transfer_internal`.
3. `burn_tokens_if_needed` fires the burn with only `BURN_TOKEN_GAS = 3 TGas` and `.detach()`. [3](#0-2) 

4. `InitTransferEvent` is emitted unconditionally.
5. A relayer calls `sign_transfer`; MPC signs the payload.
6. User finalises on the destination chain and receives minted tokens.

If the burn at step 3 fails (e.g., 3 TGas is insufficient once `internal_withdraw` emits a `FtBurn` NEP-141 event and performs storage I/O), the bridge retains the tokens that were supposed to be destroyed, while the destination chain still mints the full amount.

**Path 2 — inbound transfer refund (`fin_transfer_send_tokens_callback`)** [4](#0-3) 

When `is_refund_required` is true (recipient's `ft_on_transfer` returned 0 or panicked), `burn_tokens_if_needed` is called to destroy the already-minted tokens. If this detached burn fails silently, the tokens remain in circulation on NEAR even though the cross-chain transfer was supposed to be rolled back — inflating the NEAR-side supply.

### Impact Explanation

A silent burn failure on the outbound path allows the same token value to exist simultaneously on NEAR (held by the bridge, unburned) and on the destination chain (freshly minted). This is a direct cross-chain double-spend / unauthorized minting of bridged funds. On the inbound refund path, a silent failure inflates the NEAR-side token supply without a corresponding backing on the origin chain.

Both outcomes fall squarely within the allowed impact scope: *unauthorized minting* and *balance/escrow mis-accounting that changes protocol balances*.

### Likelihood Explanation

`BURN_TOKEN_GAS = 3 TGas` is extremely tight for a cross-contract call that must cover scheduling overhead (~0.5 TGas), `assert_controller` storage read, `internal_withdraw` storage read+write, and any NEP-141 `FtBurn` event emission. If the actual execution cost exceeds 3 TGas the promise is silently dropped. Additionally, any future upgrade to the token contract that adds even minor logic would push the cost over the budget. Because the result is never checked, no on-chain signal indicates the failure.

### Recommendation

Replace the fire-and-forget pattern with a chained callback that verifies the burn succeeded before emitting `InitTransferEvent` or finalising the refund path. At minimum, increase `BURN_TOKEN_GAS` to a safe margin (≥ 10 TGas) and add a callback that panics or reverts state if the burn promise failed, analogous to the `require(swapToken.transferFrom(...))` fix in the Amp.sol report.

### Proof of Concept

1. Deploy a bridge token whose `burn` function emits an additional log or performs one extra storage touch, pushing execution past 3 TGas.
2. Call `ft_transfer_call` on that token targeting the bridge with a valid `InitTransferMsg`.
3. Observe: `ft_on_transfer` returns `U128(0)` (bridge keeps tokens), `InitTransferEvent` is emitted, the burn promise silently fails (gas exhausted), and the bridge's token balance is not reduced.
4. A relayer calls `sign_transfer`; MPC produces a valid signature.
5. Present the signature on the EVM destination chain via `finTransfer`; the destination chain mints the full amount.
6. Result: tokens exist both at the bridge on NEAR (unburned) and freshly minted on the destination chain — a complete cross-chain double-spend. [5](#0-4) [6](#0-5) [3](#0-2)

    fn burn_tokens_if_needed(&self, token: AccountId, amount: U128) {
        if self.is_deployed_token(&token) {
            ext_token::ext(token)
                .with_static_gas(BURN_TOKEN_GAS)
                .burn(amount)
                .detach();
        }
    }

    fn init_transfer_internal(
        &mut self,
        transfer_message: TransferMessage,
        storage_owner: AccountId,
    ) -> U128 {
        let required_storage_balance = self
            .add_transfer_message(transfer_message.clone(), storage_owner.clone())
            .saturating_add(NearToken::from_yoctonear(transfer_message.fee.native_fee.0));

        if self
            .try_update_storage_balance(
                storage_owner,
                required_storage_balance,
                NearToken::from_yoctonear(0),
            )
            .is_err()
        {
            self.remove_transfer_message_without_refund(transfer_message.get_transfer_id());
            return transfer_message.amount;
        }

        if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
            self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);

            self.lock_tokens_if_needed(
                transfer_message.get_destination_chain(),
                &token_id,
                transfer_message.amount.0,
            );
        } else {
            self.remove_transfer_message_without_refund(transfer_message.get_transfer_id());
            return transfer_message.amount;
        }

        env::log_str(&OmniBridgeEvent::InitTransferEvent { transfer_message }.to_log_string());
        U128(0)
    }
