### Title
Dust Transfers Below Minimum Representable Unit Permanently Lock User Funds Due to Missing Validation in `init_transfer` - (`near/omni-bridge/src/lib.rs`)

---

### Summary

The `init_transfer` function in the NEAR omni-bridge contract accepts any transfer where `fee < amount`, but does not validate that the amount (minus fee) is representable on the destination chain after decimal normalization. When a user initiates a transfer with an amount smaller than the minimum representable unit on the destination chain, tokens are locked or burned on NEAR, but `sign_transfer` will always revert with `ERR_INVALID_AMOUNT_TO_TRANSFER` because `normalize_amount(amount - fee, decimals) = 0`. No cancel or refund mechanism exists for these stuck transfers, resulting in permanent loss of user funds.

---

### Finding Description

The bridge normalizes token amounts between chains with different decimal precisions using floor division: [1](#0-0) 

The `sign_transfer` function enforces that the normalized amount is non-zero: [2](#0-1) 

However, `init_transfer` only checks that `fee < amount`, with no check that `normalize_amount(amount - fee, decimals) > 0`: [3](#0-2) 

Tokens are locked or burned immediately inside `init_transfer_internal` before any normalization check occurs: [4](#0-3) 

When `sign_transfer` is subsequently called and panics due to `amount_to_transfer == 0`, the transfer message remains in `pending_transfers` indefinitely. The `sign_transfer_callback` only removes the transfer message on a successful MPC signing response: [5](#0-4) 

Since `sign_transfer` panics before reaching the MPC call, the callback never fires, and the transfer message is never cleaned up. There is no public `cancel_transfer` or refund function in the contract.

The protocol's own documentation acknowledges the dust-locking behavior but frames it as only affecting the sub-unit remainder, not the entire transfer amount: [1](#0-0) 

---

### Impact Explanation

For any token pair where `origin_decimals > decimals` (e.g., a NEAR token with 24 decimals bridging to an EVM chain where it is registered with 18 decimals, giving a scaling factor of `10^6`), any transfer of fewer than `10^6` base units results in a normalized amount of zero. The user's tokens are permanently locked in the bridge escrow (for native tokens) or permanently burned (for deployed bridge tokens), with no recovery path. This constitutes a permanent, irreversible loss of bridged funds caused by a decimal/normalization gap between the acceptance point (`init_transfer`) and the validation point (`sign_transfer`).

---

### Likelihood Explanation

Any unprivileged user calling `ft_transfer_call` on a NEAR token can trigger this condition by specifying an amount below the minimum representable unit on the destination chain. The decimal difference between NEAR tokens (commonly 24 decimals) and EVM tokens (commonly 6 or 18 decimals) creates a scaling factor of `10^6` to `10^18`, meaning amounts below those thresholds silently round to zero. A user unfamiliar with the decimal normalization behavior, or one using a UI that does not enforce a minimum, can accidentally trigger permanent fund loss. The condition is reachable without any privileged access.

---

### Recommendation

Add a normalization check inside `init_transfer` (or in `ft_on_transfer` before tokens are locked/burned) to verify that `normalize_amount(amount - fee, decimals) > 0` for the destination chain. Since `token_decimals` is already stored in contract state and the destination chain is known from `init_transfer_msg.recipient.get_chain()`, this check can be performed at acceptance time:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

This guard already exists in `sign_transfer` but must be moved earlier, to `init_transfer`, before tokens are locked or burned.

---

### Proof of Concept

1. A NEAR token is registered with `origin_decimals = 24`, `decimals = 18` for an EVM destination (scaling factor = `10^6`).
2. A user calls `ft_transfer_call` with `amount = 500_000` (below the `10^6` threshold) and `fee = 0`.
3. `init_transfer` accepts the transfer: `fee (0) < amount (500_000)` passes. [3](#0-2) 
4. `init_transfer_internal` locks 500,000 tokens in the bridge escrow. [6](#0-5) 
5. A trusted relayer calls `sign_transfer` for this transfer.
6. `normalize_amount(500_000, Decimals { decimals: 18, origin_decimals: 24 }) = 500_000 / 10^6 = 0`. [7](#0-6) 
7. `require!(amount_to_transfer > 0)` panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`. [8](#0-7) 
8. The transfer message remains in `pending_transfers` forever; the 500,000 tokens are permanently locked with no recovery path.

    /// Uses floor division — any sub-unit remainder ("dust") is truncated and not transferred
    /// to the destination chain. When fee > 0, dust is absorbed into the fee via `claim_fee`.
    /// When fee = 0, dust stays locked/burned. See SECURITY.md for details.
    fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
        let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
        amount / (10_u128.pow(diff_decimals))
    }
