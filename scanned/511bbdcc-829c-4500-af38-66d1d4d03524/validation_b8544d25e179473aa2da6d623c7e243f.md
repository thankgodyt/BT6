The proposed attack path requires careful tracing through two distinct phases. Let me verify the key precondition — whether a native token can end up with `mint_authority == bridge_authority_PDA` after vault creation.

### Title
Vault-Omission Bypass Enables Unauthorized `mint_to` on Native Solana Tokens — (`solana/programs/bridge_token_factory/src/instructions/user/finalize_transfer.rs`)

---

### Summary

The `finalize_transfer` instruction uses `vault: Option<...>` to distinguish native tokens (release from vault) from bridged tokens (mint). Because Anchor does **not** enforce that an optional PDA must be provided when it exists on-chain, an attacker who controls a token's `mint_authority` can register it as a native token (creating the vault), then transfer `mint_authority` to the bridge authority PDA via SPL Token's `set_authority`, and subsequently call `finalize_transfer` with `vault=None`. The program enters the `mint_to` branch, passes the `mint_authority` check, and mints tokens without releasing any from the vault — inflating supply beyond locked collateral.

---

### Finding Description

**Step 1 — Registration (vault creation):**
`log_metadata` enforces `!mint.mint_authority.contains(authority.key)` at registration time. [1](#0-0) 
An attacker-controlled token (where attacker is `mint_authority`) passes this check. The vault PDA `[VAULT_SEED, mint]` is created on-chain. [2](#0-1) 

**Step 2 — Post-registration authority transfer:**
After `log_metadata` succeeds, the attacker calls SPL Token's `set_authority` instruction (external to the bridge program) to transfer `mint_authority` to the bridge authority PDA. The bridge program has no mechanism to detect or prevent this. The vault PDA still exists on-chain.

**Step 3 — Legitimate lock to obtain a valid NEAR MPC signature:**
The attacker calls `init_transfer` providing the vault account. The vault path executes (`transfer_checked` into vault), tokens are locked, and the NEAR bridge receives them. [3](#0-2) 
The attacker then initiates a transfer back from NEAR to Solana, causing the NEAR MPC to sign a valid `FinalizeTransferPayload` for the attacker's Solana address.

**Step 4 — Exploit: `finalize_transfer` with `vault=None`:**
The attacker submits `finalize_transfer` omitting the vault account. Anchor's `Option<Account>` deserialization sets `self.vault = None` without checking whether the vault PDA exists on-chain. The program enters the `else` branch: [4](#0-3) 
The check `self.mint.mint_authority.contains(self.authority.key)` now passes (because `mint_authority` was transferred to the bridge authority PDA in Step 2). `mint_to` executes, minting tokens to the recipient's ATA. The vault still holds the originally locked tokens — supply is inflated by the minted amount with no additional collateral.

---

### Impact Explanation

- The vault retains the locked tokens from Step 3.
- The attacker receives freshly minted tokens via `mint_to`.
- Total circulating supply of the native token increases beyond the amount locked in the vault.
- This breaks the core bridge invariant: *native tokens must only be released from the vault and never minted*.
- The attacker can repeat this for any amount they can lock and for which they can obtain a valid NEAR MPC signature, bounded only by their own token supply (which they control as the original issuer).

---

### Likelihood Explanation

The attacker must:
1. Control a token's `mint_authority` — trivial for any token they deploy.
2. Call `log_metadata` — permissionless.
3. Call SPL Token `set_authority` — permissionless for the current authority.
4. Execute a round-trip bridge transfer to obtain a valid NEAR MPC signature — achievable through normal bridge usage.
5. Call `finalize_transfer` with `vault=None` — permissionless (any relayer can submit).

No admin compromise, key leak, or threshold MPC collusion is required. The entire attack is executable by a single actor on a private testnet or mainnet.

---

### Recommendation

In `finalize_transfer`, add an explicit on-chain check: if the vault PDA for the given mint exists (i.e., its account is initialized and owned by the token program), the caller **must** provide it. One concrete approach:

```rust
// After account deserialization, before the vault branch:
let vault_pda = Pubkey::find_program_address(
    &[VAULT_SEED, self.mint.key().as_ref()],
    &crate::ID,
).0;
let vault_account_info = ctx.remaining_accounts.iter()
    .find(|a| a.key == &vault_pda);
// If vault PDA is initialized on-chain, require it to be provided
```

Or more simply, add a constraint that if `vault` is `None`, the vault PDA must not exist on-chain (e.g., check that the account at the derived PDA address has zero lamports / is uninitialized). Alternatively, require that when `vault=None`, `mint_authority == authority` AND no vault PDA exists for this mint.
