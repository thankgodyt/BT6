### Title
No Cancellation Mechanism for Stuck NEAR→Foreign Transfers Causes Permanent Loss of Bridged Funds - (File: `near/omni-bridge/src/lib.rs`)

### Summary
Once a user initiates a NEAR→Foreign transfer via `ft_on_transfer` → `init_transfer_internal`, their tokens are immediately burned or locked inside the bridge. If the relayer never calls `sign_transfer`, or if the MPC signing call fails, the `sign_transfer_callback` silently does nothing — leaving the transfer permanently stuck in `pending_transfers` with no user-callable cancellation path. There is no `cancel_transfer` function anywhere in the contract.

### Finding Description
The NEAR→Foreign outbound transfer flow proceeds as follows:

1. User calls `ft_transfer_call` on a NEP-141 token, triggering `ft_on_transfer` → `init_transfer` → `init_transfer_internal`.
2. Inside `init_transfer_internal`, the user's tokens are **immediately and irrevocably** burned (for bridge-deployed tokens) or locked (for native tokens), and the transfer is inserted into `pending_transfers`.
3. A trusted relayer must then call `sign_transfer`, which requests an MPC signature from the external `mpc_signer` contract.
4. In `sign_transfer_callback`, if the MPC call **fails** (`call_result` is `Err`), the entire `if let Ok(signature) = call_result` block is skipped — no refund is issued, no cleanup is performed, and the transfer remains in `pending_transfers` indefinitely.

```rust
// near/omni-bridge/src/lib.rs:648-668
pub fn sign_transfer_callback(
    &mut self,
    #[callback_result] call_result: Result<SignatureResponse, PromiseError>,
    #[serializer(borsh)] message_payload: TransferMessagePayload,
    #[serializer(borsh)] fee: &Fee,
) {
    if let Ok(signature) = call_result {   // <-- Err branch: nothing happens
        if fee.is_zero() {
            self.remove_transfer_message(message_payload.transfer_id);
        }
        env::log_str(...);
    }
    // No else branch: MPC failure leaves tokens burned/locked forever
}
```

A grep across all of `near/omni-bridge/src/` for `cancel`, `withdraw_transfer`, `reclaim`, or `abort` returns **zero matches**. The only paths that remove a transfer from `pending_transfers` are:
- `sign_transfer_callback` on MPC **success** with zero fee
- `claim_fee` callback after a relayer submits a fee proof
- Internal error-path helpers (`remove_transfer_message_without_refund`) that are never exposed publicly

Neither the user nor any unprivileged caller has any way to cancel a pending transfer and recover the burned/locked tokens.

### Impact Explanation
- For **bridge-deployed tokens**: `burn_tokens_if_needed` is called inside `init_transfer_internal` before the transfer is even signed. If the transfer is never finalized, those tokens are permanently destroyed — the total supply on NEAR is reduced with no corresponding mint on the destination chain.
- For **native/locked tokens**: `lock_tokens_if_needed` increments `locked_tokens` and the tokens sit in the bridge contract forever, unrecoverable by the user.

This constitutes **permanent freezing and effective destruction of bridged funds** — a Critical impact under the allowed scope.

### Likelihood Explanation
The scenario is realistic and requires no privileged compromise:
- The MPC signing service can be temporarily or permanently unavailable (network partition, key rotation, service outage).
- A trusted relayer can go offline, be deregistered, or simply never process a specific transfer.
- The user has no fallback: `sign_transfer` is gated by `#[trusted_relayer]`, so the user cannot call it themselves even to retry.
- There is no timeout, no expiry, and no user-initiated escape hatch.

Any user who initiates a NEAR→Foreign transfer while the relayer/MPC layer is degraded will permanently lose their full transfer amount.

### Recommendation
Introduce a user-callable `cancel_transfer` function that:
1. Verifies the caller is the original `sender` stored in the `TransferMessage`.
2. Optionally enforces a minimum waiting period (e.g., after N blocks) to prevent griefing of in-flight relayer operations.
3. Removes the transfer from `pending_transfers`.
4. Mints back (for deployed tokens) or unlocks (for native tokens) the full `transfer_message.amount` to the original sender.
5. Decrements `locked_tokens` if applicable.

This mirrors the cancellation pattern recommended by the Starknet messaging documentation cited in the original report and is the standard mitigation for this class of vulnerability.
